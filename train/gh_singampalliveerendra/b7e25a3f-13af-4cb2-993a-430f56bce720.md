Two policies missing on `farmers`: **INSERT** (for auto-signup) and **UPDATE** (for profile edit). Everything else in your list is already correct for the flows I built.

Run this in the Supabase SQL editor:

```sql
-- Let any visitor create a farmer row (self-signup by phone, no OTP)
CREATE POLICY "Allow insert farmers"
ON public.farmers
FOR INSERT
TO anon
WITH CHECK (true);

-- Let any visitor update a farmer row (profile edit)
CREATE POLICY "Allow update farmers"
ON public.farmers
FOR UPDATE
TO anon
USING (true)
WITH CHECK (true);
```

## ⚠️ Security tradeoff — read this

`UPDATE … TO anon USING (true)` means **any visitor can edit any farmer's profile**, not just their own. With no OTP / no auth, there's no way for RLS to know "this person owns this row" — the only identifier we have is a phone number they typed, which is trivially spoofable.

For a **closed test** with your 400-person WhatsApp group, this is fine — no one's going to mess with it, and you need the testing data fast. For **public launch**, you should migrate to Supabase phone-OTP auth and tighten the policy to `USING (auth.uid() = user_id)`. I'd budget this as P3 work after the MVP test tells you whether the product works at all.

If you're uncomfortable with open UPDATE even for the test, a middle-ground is to move the profile edit server-side (Next.js API route using the Supabase service role key) and only expose INSERT to anon. Takes ~30 mins to wire. Tell me if you want that instead.
