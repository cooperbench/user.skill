The protection is two layers deep, so the answer holds even when two riders tap at the exact same millisecond. **Layer 1 — atomic conditional UPDATE** (`src/app/api/rider/orders/[id]/accept/route.ts:36-48`) ```js .update({ delivery_boy_id: session.riderId, delivery_status: 'assigned', assigned_at: now, }) .eq('id', id) .eq('delivery_type', 'home_delivery') .eq('status', 'approved') .is('delivery_boy_id', null) // ← only succeeds if still unclaimed .select('id') ``` Postgres applies the WHERE clause row-locked under the hood. The first rider's UPDATE flips `delivery_boy_id` from `NULL` → their id. When the second rider's UPDATE arrives a millisecond later, the `delivery_boy_id IS NULL` predicate is now false, so 0 rows match, `claimed.length === 0`, and the API returns: ```js return NextResponse.json( { error: 'This order was already taken or is no longer available.' }, { status: 409 }, ) ``` The losing rider sees a clear "already taken" error. **Layer 2 — the Available feed filters out claimed orders** (`src/app/api/rider/orders/route.ts:58-68`) ``` .is('delivery_boy_id', null) .or('delivery_status.is.null,delivery_status.eq.unassigned') ``` So on the next refresh, the order disappears from every other rider's "Available" tab.
