## 1. Project & Product
**Q: Tell me about this project in 60 seconds.**
> A mobile-first PWA connecting natural farmers in Andhra Pradesh directly to buyers — no app download, built for slow Android 4G. Next.js 14 + TypeScript on the frontend, Supabase (Postgres + Storage) as backend, Vercel hosting, Razorpay for payments, Twilio WhatsApp for onboarding. Roles: farmers, buyers, moderators, and delivery riders.

**Q: Why a PWA instead of a native app?**
> Target users are on cheap Androids with poor connectivity. A PWA means zero install friction, instant access via a link, smaller payload, and one codebase. Native would add download barriers and store overhead with no real benefit at MVP.

**Q: What was the hardest constraint?**
> "Under 3 seconds on 4G." It forced choices everywhere: no heavy client libraries (e.g., I generate the PDF report via the browser's print dialog instead of bundling a PDF library), mobile-first 390px layouts, and minimal JS.

## 2. Architecture & Tech Choices
**Q: Why Supabase over a custom backend?**
> It gives Postgres, auth, storage, and row-level security out of the box, so a small team ships fast without building/maintaining a server. Realtime subscriptions let the orders list update live. The trade-off is vendor lock-in and learning RLS deeply.

**Q: Next.js App Router — why, and server vs. client components?**
> App Router for file-based routing, layouts, and easy static/dynamic rendering per route. Public pages (farmer/region profiles) are static for speed; interactive dashboards are client components talking to Supabase.

**Q: How does authentication work for farmers?**
> The farmer dashboard authenticates via localStorage (farmer id), not a cookie session — so data writes go through the anon client gated by RLS rather than cookie-protected API routes. *(Be ready to defend this: it's simpler for the MVP, but the real security boundary is RLS in the DB, not the client.)*

## 3. Security (very common — they'll dig here)
**Q: If the client is "just localStorage," what stops a user reading another farmer's orders?**
> Row-Level Security in Postgres. Every query is scoped (`farmer_id = …`), and RLS policies enforce it at the database, so even a guessed/forged id returns nothing. The detail page also scopes its read by farmer id as defense-in-depth.

**Q: How do you keep sensitive data out of the wrong browser?**
> Example: the pickup handover OTP is deliberately **never fetched** into the farmer's browser — it must come from the buyer. Principle: don't send a secret to a client that shouldn't be able to act on it.

**Q: How do you handle untrusted text in the PDF report?**
> All farmer/buyer-supplied fields are HTML-escaped before injection — prevents injection/XSS in the generated report.

## 4. Data Model & Order Lifecycle
**Q: Walk me through an order's lifecycle.**
> Placed → Approved by farmer → Shipped → Delivered. Unified flow: farmer taps "Shipped," buyer taps "Delivered," regardless of self-pickup / home delivery / courier. Payment can be COD (cash at pickup) or online (UPI/Razorpay).

**Q: A bug example you fixed?** *(great to volunteer)*
> Delivered orders still showed "Payment Pending." Root cause: payment was only "settled" when `payment_status = completed`, but COD/pickup cash is never flipped to that automatically. Fix: a collected/received order implies money changed hands, so I derive paid-status from delivery — a delivered order can't still be "pending."

## 5. Performance & UX
**Q: Concrete things you did for slow 4G?**
> Dependency-free PDF (browser print), native `<input type="date">` for the calendar instead of a date-picker library, static public pages, mobile-first layouts, minimal images/JS.

**Q: How does the farmer get a filtered report?**
> On-device filtering by status (the 5 buckets) and a date range (preset chips + custom From–To calendar). The same filter drives the on-screen view and the downloadable PDF — single source of truth, no server round-trip.

## 6. Scaling & Trade-offs (senior-level)
**Q: Where does this break at scale, and what would you change?**
> localStorage auth doesn't scale to strong security needs — I'd move to proper Supabase Auth sessions. Realtime subscriptions per farmer are fine now but I'd watch connection limits. Reports filter client-side (fine for hundreds of orders); at thousands I'd push filtering/pagination to the DB.

**Q: How would you add WhatsApp onboarding?**
> Twilio WhatsApp API webhook → guided flow that creates the farmer profile. It's planned but not built; the challenge is conversational state and number verification.
