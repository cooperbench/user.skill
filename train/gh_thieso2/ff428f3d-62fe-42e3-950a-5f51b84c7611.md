# Plan: TCP Port-Forward Routes

## Context

Routes currently support only HTTPS (layer 7, domain-based via Traefik `Host()` rules on port 443).
The new "tcp" mode adds layer-4 port forwarding: Traefik listens on a public port (e.g. 3000)
and forwards raw TCP to the container port. This is useful for databases, raw TCP services, or
anything that isn't HTTP. Port range: 3000–3099 (100 slots), pre-declared in the Traefik static
config and opened in UFW by the installer.

---

**`add_route`** — accept `mode: "http"` (default) or `mode: "tcp"`
- HTTP mode: same as today (requires `domain:`)
- TCP mode: call `allocate_tcp_port` inside a transaction, create route without domain

**New private `allocate_tcp_port`**
```ruby
def allocate_tcp_port
  used = Route.where(mode: "tcp").lock.pluck(:public_port).to_set
  TCP_PORT_RANGE.find { |p| !used.include?(p) } ||
    raise Error, "No TCP ports available (pool 3000–3099 exhausted)"
end
```
Wrap the create + allocate in `Route.transaction` to prevent races.

**`write_config`** — split into http and tcp sections in the same `sandbox-{id}.yml`:
```yaml
http:
  routers:
    sandbox-5-r1:
      rule: "Host(`app.example.com`)"
      entryPoints: [websecure]
      ...
  services: ...
tcp:
  routers:
    sandbox-5-r2:
      rule: "HostSNI(`*`)"
      entryPoints: [tcp-3042]
      service: sandbox-5-r2
  services:
    sandbox-5-r2:
      loadBalancer:
        servers:
          - address: "alice-mybox:8080"
```

TCP router key: `sandbox-{sandbox.id}-tcp-r{route.id}`
HTTP router key: `sandbox-{sandbox.id}-r{route.id}` (unchanged)

## Traefik static config — on-demand entrypoints

Traefik entrypoints are static (require restart to add). Rather than pre-declaring the full range,
entrypoints are added **on demand**: when a TCP route is created for a port not yet in `traefik.yml`,
the app adds the entrypoint and restarts the Traefik container (~1 s downtime).

**`RouteManager#ensure_tcp_entrypoint(port)`** (new private method):
1. Read `TRAEFIK_STATIC_CONFIG` path (e.g. `/data/traefik/traefik.yml`)
2. Parse YAML; check if entrypoint `tcp-{port}` already exists
3. If missing: add it, write the file back, then `Docker::Container.get("sandcastle-traefik").restart`
4. If already present: no-op

**`add_route` for tcp mode calls `ensure_tcp_entrypoint(public_port)` before writing dynamic config.**

The `SANDCASTLE_TRAEFIK_CONFIG` env var (default `/data/traefik/traefik.yml`) tells Rails where the
static config lives. The Traefik container name is `sandcastle-traefik` (configurable via
`SANDCASTLE_TRAEFIK_CONTAINER`).

The full stack for making a TCP route reachable has three layers, all handled:

```
Client → Host port 3042
         ↓ Docker publishes 3000-3099 on Traefik container (docker-compose.yml line 8)
         UFW allows 3000-3099/tcp (installer.sh)
         ↓ Traefik listens on entrypoint tcp-3042 (traefik.yml, written on-demand by ensure_tcp_entrypoint)
         ↓ Traefik forwards to sandbox container:port (sandbox-N.yml dynamic config)
         Sandbox container port inside sysbox
```

**Layer 1 — Docker port binding** (already done): The range `3000-3099:3000-3099` is pre-published on the Traefik container at startup. Docker binds all 100 host ports to the container. This is a static operation — done once at install/deploy time.

**Layer 2 — UFW** (already done): `ufw allow 3000:3099/tcp` opens those ports in the firewall at install time.

**Layer 3 — Traefik entrypoint** (on-demand): When a TCP route is created, `ensure_tcp_entrypoint(port)` adds `tcp-3042: address: ":3042"` to `traefik.yml` and restarts the Traefik container. The port is already published by Docker, so Traefik immediately starts accepting connections on restart.

One thing to note: I also removed `:ro` from the `traefik.yml` volume mount in Traefik's container definition, so the file stays writable on the host (Rails writes to it via its `/data` bind mount). Traefik itself never writes to that file — only reads it on startup.

| Container | Mount | Sees `traefik.yml` at |

The differences are meaningful but there's one important inconsistency introduced by our changes. Here's the comparison:

**Structural differences (intentional, appropriate)**:

| | Installer | deploy:local |
|---|---|---|
| Data storage | Host bind-mounts (`/sandcastle/data/…`) | Named Docker volumes |
| Bootstrap | Installer pre-creates all files before compose starts | `init-traefik` / `init-data` init containers write at first boot |
| Images | Registry pull | Local build |
| `runtime:` | `runc` on all services | Not set |
| Encryption keys | Required (`AR_ENCRYPTION_*`) | Skipped (dev) |

**The inconsistency we introduced in Traefik's volume layout**:

The installer template has Traefik reading dynamic configs from `/data/dynamic` (a separate bind-mount):
```yaml
# installer template
- ${DATA_MOUNT}/traefik/traefik.yml:/etc/traefik/traefik.yml   # static config
- ${DATA_MOUNT}/traefik/dynamic:/data/dynamic:ro               # ← /data/dynamic in Traefik
- ${DATA_MOUNT}/traefik/acme.json:/data/acme.json
- ${DATA_MOUNT}/traefik/certs:/data/certs:ro
```

But the local setups now have Traefik reading from `/etc/traefik/dynamic` (because the whole volume is at `/etc/traefik`):
```yaml
# docker-compose.local.yml
- traefik-data:/etc/traefik                    # dynamic is at /etc/traefik/dynamic
```

The `traefik.yml` written by `init-traefik` reflects this: `directory: /etc/traefik/dynamic`. That's self-consistent locally, but diverged from what the installer does. That's fine — because the traefik.yml is always written by its respective bootstrap mechanism and hard-codes the correct internal path for that environment.

**The one thing that IS shared and must stay consistent**: `SANDCASTLE_TRAEFIK_CONFIG` always points to where **Rails** sees the file, which is always `/data/traefik/traefik.yml` — whether that's a host path (installer) or the named volume mounted there (local). That's consistent across all three compose files.

So the structures are intentionally different (volumes vs bind-mounts, init containers vs installer pre-bootstrap), and the Traefik internal path divergence is fine because the config file itself documents the correct internal path. Nothing is broken.
