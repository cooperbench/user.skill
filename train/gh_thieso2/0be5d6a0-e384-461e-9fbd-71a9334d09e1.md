> AGENT

Both already coexist in the current image — the trick is `CLAUDE_INSTALL_DIR`. `Dockerfile.base:121-127` installs the `claude` binary to `/usr/local/bin/claude` (outside `$HOME`), and `Dockerfile.base:148` sets `CLAUDE_INSTALL_DIR=/usr/local/bin` in `/etc/environment`. That env var tells `claude --update` to write the new binary to `/usr/local/bin/claude` instead of `~/.local/bin/claude`. `entrypoint.sh:16` then chowns the binary to the sandbox user so updates work without sudo (commit d07852e). So even when `/home/$USER` is bind-mounted from the host, `claude` lives entirely under `/usr/local/bin` and never touches `~/.local`. The host's `~/.local` (which on macOS would be the wrong arch anyway) is simply ignored. If you ever wanted Claude to live under `~`, the alternatives would be: (a) mount a container-local volume on top of `~/.local` to mask the host's copy, or (b) have the entrypoint symlink `~/.local/bin/claude` → `/usr/local/bin/claude`. But the env-var override is the cleanest and is what's in place today.

why not inject claude and codex auth like we do for ssh.key? - how could we add files to inject?

> AGENT

Injection is the right model for *static* credentials but has one real footgun for *OAuth-style* ones. Let me lay out both the mechanism and the gotcha. ## Why injection works (mostly) The SSH key case is simple because the credential is **read-only inside the sandbox** — sshd consumes `authorized_keys`, never rewrites it. Inject once, done. Claude Code and Codex are different: - **API key auth** (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`): static, never written back. Injection is perfect — could be plain env vars, no file needed. - **OAuth login** (Claude Pro/Max, Codex sign-in): the CLI refreshes the access token periodically and rewrites `~/.claude/.credentials.json` (and Codex's `auth.json`). With injection + no write-back, every new sandbox starts with a stale token and forces a refresh — usually fine, but **if Anthropic rotates the refresh token on use, sandbox A's copy gets invalidated when sandbox B refreshes.** Race condition with real consequences. So: injection is great for API keys and the *initial* OAuth credential. For OAuth long-term, you either need (a) write-back, or (b) a bind-mount on just `~/.claude` and `~/.codex` (the previous sketch). ## Two injection mechanisms (both already exist as patterns in the codebase) **Pattern A — env var, like SSH keys** (`entrypoint.sh:22-34`): simple, but env vars are visible in `docker inspect` and survive in container metadata. Fine for SSH pubkeys (already public). Risky for OAuth tokens. **Pattern B — `docker exec` after start, like SMB password** (`sandbox_manager.rb:877-889`): set after container is up, never appears in env or `docker inspect`.
