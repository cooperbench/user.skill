> DEVELOPER

explain whet the routs do.

> AGENT

Routes let you expose a service running inside a sandbox on a public URL with automatic TLS. **Without routes**, a sandbox is only reachable via SSH (or the web terminal/VNC). The services running inside — a web app on port 3000, an API on port 8080, etc. — have no way to receive external HTTP traffic. **With a route**, you map a public domain to a container port: ``` app.example.com → sandbox container port 3000 api.example.com → sandbox container port 8080 ``` Traefik (the reverse proxy in front of everything) picks up a dynamically generated YAML config file and starts forwarding HTTPS requests for that domain directly into the container over the internal Docker network. Let's Encrypt TLS is handled automatically. **Lifecycle behaviour:** - Routes are persisted in the DB — they survive sandbox restarts - When the sandbox **stops**, the Traefik config is removed (routes go dark) - When the sandbox **starts** again, routes are automatically reconnected - When the sandbox is **destroyed**, routes are deleted entirely **What the web UI adds** is the ability to manage this without the CLI — you can add a domain + port and delete existing routes directly from the sandbox detail page. The sandbox must be running to add a route (because RouteManager also connects the container to the Traefik Docker network at that point), but you can delete routes regardless of status.

can traffic do ssh multi-home or only https?

> AGENT

Traefik can handle TCP (including SSH), but **hostname-based SSH routing isn't possible** with standard SSH clients — here's why: **HTTPS routing works** because TLS has SNI — the client sends the hostname *before* the encrypted handshake, so Traefik can read `app.example.com` and route accordingly, all on port 443. **SSH has no equivalent**. A raw SSH connection opens with the server's protocol banner (`SSH-2.0-OpenSSH_9.x`) — there's no hostname field. Traefik has no information to route on, so it can't distinguish `sandbox-a` from `sandbox-b` on the same port. **What Traefik *can* do for TCP/SSH:** - **Port-based routing** — one dedicated port per sandbox. That's essentially what Sandcastle already does (ports 2201–2299 bound directly on the host via Docker). Traefik would just be a pass-through middleman, adding no value. - **SNI-based TCP routing** — works only if SSH is wrapped in TLS first (e.g. `ssh` over a TLS tunnel). Standard `ssh` clients don't do this. **So the current Sandcastle architecture is correct:** - HTTP/S traffic → Traefik → container (routes, terminal, VNC) - SSH → Tailscale → container directly (no proxy needed, no port collision problem) If you wanted public SSH without Tailscale, the realistic options are a jump host / `ProxyCommand` approach, or something like [sslh](https://github.com/yrutschle/sslh) that multiplexes SSH+HTTPS on port 443 — but none of that is hostname-aware, so you still can't share a single port across multiple sandboxes.

explain SNI-based TCP routing — works only if SSH is wrapped in TLS first (e.g. ssh over a TLS tunnel). Standard ssh clients don't do this.

> AGENT

**SNI (Server Name Indication)** is a TLS extension added in the ClientHello — the very first packet a TLS client sends. Before any encryption happens, the client announces which hostname it wants: ``` Client → Server: "ClientHello, I want to talk to api.example.com" Server → Client: "Here's the certificate for api.example.com" ... encrypted from here ... ``` Traefik sits in front and reads that SNI field *without decrypting anything*. It just peeks at the hostname and forwards the raw TCP stream to the right backend. The backend terminates TLS itself. This is called **TLS passthrough**. ``` Browser ──TLS(SNI=api.example.com)──▶ Traefik ──▶ sandbox-a:443 Browser ──TLS(SNI=db.example.com)───▶ Traefik ──▶ sandbox-b:443 ``` Same port (443), different destinations, zero decryption by Traefik. --- **Why SSH can't use this directly** A normal SSH connection looks like this on the wire: ``` Client → Server: (TCP connect) Server → Client: "SSH-2.0-OpenSSH_9.7\r\n" ← server speaks first Client → Server: "SSH-2.0-OpenSSH_9.3\r\n" ← client replies ... key exchange ... ``` There is no hostname in any of this. The client just connected to an IP and port — it never said *which* server it wanted. Traefik has nothing to route on. --- **SSH over TLS would fix it**, but requires a wrapper on both ends: ``` ssh → stunnel/socat (wraps in TLS with SNI=sandbox-a.example.com) │ ▼ Traefik (reads SNI, routes TCP stream) │ ▼ stunnel/socat in sandbox (unwraps TLS, hands plain TCP to sshd) ``` The client side would need something like: ``` # ~/.ssh/config Host sandbox-a.example.com ProxyCommand openssl s_client -quiet -connect %h:443 -servername %h ``` This works but it's awkward — every user needs the ProxyCommand configured, the sandbox needs a TLS unwrapper running alongside sshd, and the latency adds up (TLS handshake on top of SSH handshake). --- **Bottom line**: SNI routing is elegant for HTTPS because TLS is …
