- Warn only: log to `/run/docker-status` if runc ≠ 1.1.x so it surfaces in the admin dashboard / banner.
- Self-heal: re-download v1.1.15 before starting dockerd. Adds a network dep at boot, but would have silently fixed this class of bug.

**Can we fix it in the sysbox fork?**

In principle yes, but it's real work, not a patch. The root issue is architectural: sysbox-fs mounts `/proc/sys` as a FUSE filesystem to virtualize a handful of sysctls. runc's new check walks up from the file and rejects any FUSE ancestor — correct for its threat model (prevents a malicious procfs substitute), and we can't change runc's mind cheaply.

Options in the fork, roughly in order of effort:
1. **Narrow the FUSE mount.** Instead of FUSE-mounting `/proc/sys`, keep `/proc/sys` as procfs and only FUSE-mount the specific files sysbox needs to virtualize (e.g. bind-mount individual FUSE-backed files over real procfs entries). This is the "right" fix and what nestybox/sysbox#973 is asking for upstream. Touches sysbox-fs mount setup and handler registration — meaningful but bounded.
2. **Patch runc inside the sandbox.** Ship a sysbox-aware runc build that trusts `0x65735546` when a sysbox marker is present. Pushes the problem into our image maintenance forever.
3. **Stay pinned to runc 1.1.x inside sandboxes.** What we do now. Works, but means we can't ship CVE-2025-52881's fix to nested workloads.

Option 1 is the only one that actually unblocks modern runc. Upstream nestybox is stuck on it (last activity Feb 2026 per the comment). If we want it before upstream does, that's a dedicated sprint on sysbox-fs, not a quick patch.
