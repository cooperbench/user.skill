> AGENT

Found the issue. The tmux config has `set -sg escape-time 10` (10ms). When `sandcastle connect` runs tmux inside the sandbox over SSH, tmux sends OSC 10/11 queries to detect the outer terminal's colors. The responses travel back through SSH and arrive fragmented — the `\033` (escape) arrives, tmux waits only 10ms, gives up, and the rest of the response (`]10;rgb:86be/940d/9624`) leaks into the shell as literal text. The fix is to increase `escape-time` to give tmux enough time to parse escape sequences arriving over SSH:

> AGENT

The fix bumps `escape-time` from 10ms to 50ms. With 10ms, tmux gives up waiting for the rest of an escape sequence before it arrives through the SSH tunnel. At 50ms, tmux has enough time to parse the full OSC response and consume it properly instead of dumping it into the shell. The tradeoff: pressing Escape in vim will feel ~40ms slower. That's imperceptible to most people, and 50ms is still well below the default tmux value of 500ms. To apply this to running sandboxes, you'll need to rebuild the sandbox image. For an immediate fix on existing sandboxes, you could patch the running config: ```bash ssh sandman "/sandcastle/dockyard/bin/docker exec <container> sed -i 's/escape-time 10/escape-time 50/' /etc/tmux.conf" ``` Or users can run `tmux set -sg escape-time 50` inside their session.
