Here is a concise summary of current best practices for running Samba (SMB) inside Docker containers.

---

## 1. Best Base Images

There are three strong options, each with different trade-offs:

| Image | Base | Status | Notes |
|---|---|---|---|
| **`ghcr.io/servercontainers/samba`** | Alpine | Actively maintained | Env-var driven config, optional Avahi/WSDD2, multi-arch (x86+arm). Best for "configure via env vars" approach. |
| **`dockur/samba`** | Alpine/Debian | Actively maintained | Simple env-var config (`USER`, `PASS`, `UID`, `GID`), supports `users.conf` for multi-user, custom `smb.conf` bind mount. Newest of the three. |
| **`dperson/samba`** | Alpine | Legacy/low maintenance | Widely used historically but updates have slowed. Still functional. |
| **Roll your own** (Ubuntu/Alpine + `apt install samba`) | Any | You maintain it | Best option when you need full control and minimal attack surface. Just `samba-server` package, no extras. |

**Recommendation for Sandcastle:** Rolling your own inside the existing sandbox image (Ubuntu 24.04) is the most practical approach since you already control the image build and need tight integration with per-user home directories. Alternatively, running a sidecar `servercontainers/samba` container (similar to the WeTTY pattern) keeps concerns separated.

---

## 2. Minimal Config for SMB-Only (No NetBIOS)

NetBIOS/nmbd is unnecessary for modern SMB over TCP (port 445). Only expose port 445:

```
docker run -p 445:445 ...
```

In `smb.conf`:
```ini
[global]
    disable netbios = yes
    smb ports = 445
    dns proxy = no
```

This eliminates ports 137-139 entirely.

---

## 3. Security Best Practices: SMB3-Only, Encryption, No Guest

```ini
[global]
    server min protocol = SMB3
    server max protocol = SMB3_11
    smb encrypt = required
    server signing = mandatory

    # Disable guest/anonymous
    map to guest = never
    restrict anonymous = 2
    guest ok = no

    # Disable printing (attack surface reduction)
    load printers = no
    printing = bsd
    printcap name = /dev/null
    disable spoolss = yes

    # Disable NetBIOS
    disable netbios = yes
    smb ports = 445
```

Key points:
- `smb encrypt = required` enforces AES encryption on all connections (AES-128-GCM by default with SMB 3.1.1, AES-256 available).
- `server min protocol = SMB3` rejects all SMB1/SMB2 clients.
- `map to guest = never` ensures failed auth attempts are rejected rather than mapped to guest.
- macOS, Windows 10+, and modern Linux (`smbclient`, `mount.cifs`) all support SMB3 with encryption natively.

---

## 4. Programmatic Password Management

Two tools, prefer `smbpasswd` for simplicity in Docker entrypoints:

**smbpasswd (non-interactive):**
```bash
# The -s flag reads from stdin; password must be provided twice
echo -e "${PASSWORD}\n${PASSWORD}" | smbpasswd -a -s "${USERNAME}"
```

**pdbedit (more control, also non-interactive):**
```bash
# Add user with password from stdin
echo -e "${PASSWORD}\n${PASSWORD}" | pdbedit -a -t "${USERNAME}"
```

**In a Docker entrypoint pattern:**
```bash
#!/bin/bash
# Create system user (Samba requires a matching Unix user)
useradd -M -s /usr/sbin/nologin "$SMB_USER"
# Set Samba password non-interactively
echo -e "${SMB_PASS}\n${SMB_PASS}" | smbpasswd -a -s "$SMB_USER"
# Start Samba in foreground (no daemon)
exec smbd --foreground --no-process-group
```

The `servercontainers/samba` image offers a `create-hash.sh` script to pre-generate password hashes, avoiding plaintext passwords in env vars.

---

## 5. Performance Considerations

- **Do NOT use SMB for latency-sensitive workloads** (databases, git repos with many small files). It adds meaningful overhead vs. direct filesystem access.
- **Remove `socket options`** from `smb.conf` -- the default kernel settings are better tuned than manual overrides in most cases.
- **Use `case sensitive = yes`** and `preserve case = yes` if clients are all Linux/macOS -- avoids directory scanning for case variations.
- **Bind-mount the shared directory directly** into the Samba container rather than using Docker named volumes when possible, to reduce I/O layers.
- **Memory limit** the Samba container (`--memory 256m` or similar) since `smbd` forks per-connection and can grow.
- For large file transfers, SMB3 multichannel can help but requires multiple NICs (unlikely in Docker).

---

## 6. Gotchas with Samba Inside Sysbox Containers

Sysbox runs all containers with Linux user namespaces, which creates specific challenges:

- **UID mapping**: Sysbox remaps UIDs. A process running as UID 1000 inside the container maps to a different UID on the host. Samba needs the Unix user's UID to match file ownership. If Samba runs *inside* a Sysbox container, this is fine (UIDs are consistent within the namespace). If Samba runs *outside* and accesses bind-mounted files owned by a Sysbox container's user, UIDs will mismatch.
- **Overlayfs permission issues**: Known Sysbox issue -- mounting overlayfs directories into Sysbox containers can result in `nobody:nogroup` permissions. Avoid overlayfs for Samba shares; use bind mounts to real directories.
- **Filesystem operation failures**: There is a known (intermittent) Sysbox issue on AWS EC2 where inner Docker containers can fail filesystem operations on first run. This could affect a Samba container running inside a Sysbox sandbox.
- **No `--net=host` needed**: Since you only need SMB over TCP/445 (no NetBIOS broadcast), standard Docker port mapping works fine. nmbd would require host networking, but you do not need nmbd.
- **Recommendation**: Run Samba as a **sidecar container** on the host Docker daemon (like WeTTY), not nested inside Sysbox. This avoids UID mapping complexity and the overlayfs gotchas.

## 7. Minimal smb.conf for a Single-User Share

```ini
[global]
    workgroup = WORKGROUP
    server string = Sandcastle SMB
    server role = standalone server

    # SMB3 only, encrypted
    server min protocol = SMB3
    server max protocol = SMB3_11
    smb encrypt = required
    server signing = mandatory

    # No NetBIOS
    disable netbios = yes
    smb ports = 445
    dns proxy = no

    # No guest access
    map to guest = never
    restrict anonymous = 2

    # No printing
    load printers = no
    printing = bsd
    printcap name = /dev/null
    disable spoolss = yes

    read only = no
    valid users = %U
    guest ok = no
    create mask = 0644
    directory mask = 0755
    force user = %U
```

This config:
- Requires SMB3 with encryption on all connections
- Disables all legacy protocols, NetBIOS, guest access, and printing
- Shares `/workspace` with access restricted to the authenticated user
- `force user = %U` ensures files are created as the connecting user

- **User-defined network MASQUERADE**: `POSTROUTING -s ${DOCKYARD_POOL_BASE} -j MASQUERADE` (entire /16)
- **FORWARD rules allow**:
  - Bridge-to-bridge: `FORWARD -i ${BRIDGE} -o ${BRIDGE} -j ACCEPT`
  - Bridge outbound: `FORWARD -i ${BRIDGE} ! -o ${BRIDGE} -j ACCEPT`
  - Pool-to-pool (all networks): `FORWARD -s ${DOCKYARD_POOL_BASE} -j ACCEPT` and `-d ${DOCKYARD_POOL_BASE} -j ACCEPT`

#### **5. WeTTY Terminal Access Flow**
- **WeTTY sidecar** created on-demand when terminal opens (TerminalManager)
- **Traefik config** written to `/data/traefik/dynamic/terminal-{sandbox_id}.yml` (lines 53-121)
- **Routes to**: `http://{sandbox_container_name}:{TMUX_PORT}` (line 107) — assumes sandbox is on same network
- **ForwardAuth** validates session at `http://sandcastle-web:80/terminal/auth` (line 93) — Rails must be reachable

#### **6. SSH/Connect Access Flow**
- **No SSH on host ports** — all SSH access goes through Tailscale
- `SandboxManager.connect_info()` (line 635) requires Tailscale enabled
- Returns Tailscale IP (`sandbox_tailscale_ip()` from line 283)
- User SSHes to sandbox via tailnet: `ssh {user}@{tailscale_ip}`

### **Current Isolation Model**

| Scope | Current Behavior |
|-------|------------------|
| **Sandbox-to-sandbox (same user)** | Can reach each other on `sandcastle-web` network |
| **Sandbox-to-sandbox (different users)** | **Can reach each other on `sandcastle-web` network** ⚠️ |
| **Tailscale connectivity** | Isolated per-user (different networks: `sc-ts-net-{user1}` vs `sc-ts-net-{user2}`) |
| **Data directory isolation** | Full — users are remapped UIDs inside Sysbox; `/data/users/{user}` bind-mounted read-only to user |
| **Entrypoint.sh SSH keys** | Per-sandbox SSH keys, appended to shared `/home/{user}` bind-mount |
| **Application-level access control** | Policy-based: `Sandbox#user_id` checked in all controllers; API tokens scoped to user |

### **What Would Need to Change for Per-Tenant Network Isolation**

#### **1. Database Schema**
Add to `Sandbox` model:
- `network_name: string` — unique per sandbox (e.g. `sc-net-{user_id}-{sandbox_id}`)
- `network_subnet: cidr` — assigned at creation (e.g. `10.89.3.0/24`)

#### **3. TerminalManager & VncManager Changes**
- **Current assumption** (line 27 in vnc_manager.rb): `"Requires the sandbox to already be connected to the sandcastle-web network"`
- **Problem**: WeTTY sidecars and VNC sidecars need to reach the sandbox container
- **Solution 1**: Create WeTTY/VNC sidecars on the same per-sandbox network
- **Solution 2**: Create a shared **sidecar network** separate from sandboxes, but then route from Traefik through sidecars to sandboxes
- **Solution 3**: Keep Rails/Traefik on a separate management network; sidecars bridge between management and user networks

#### **4. Traefik Routing**
- **Current**: Traefik routes directly to `http://{sandbox_name}:{port}` DNS name (assumed same network)
- **Would need**:
  - Traefik on a management network that can reach all sandboxes
  - Routes to each sandbox via its own network
  - Or: route through WeTTY/VNC sidecars that are per-sandbox-network, with those sidecars connecting to management network

#### **5. iptables Rules**
- **Current**: MASQUERADE entire `DOCKYARD_POOL_BASE` /16
- **Would need**:
  - Individual rules per sandbox subnet (or keep blanket rule, but restrict FORWARD)
  - Alternative: per-sandbox FORWARD rules to prevent cross-sandbox traffic while keeping NAT at /16 level
  - Example: `FORWARD -i br-{sandbox1_net} -o br-{sandbox2_net} -j DROP` (block inter-sandbox)

#### **6. TailscaleManager Integration**
- **Least impact** — already creates per-user networks; would be easy to create per-sandbox networks instead
- Or: create per-user **umbrella network** that contains all user's sandboxes + Tailscale sidecar

#### **7. Rails/Worker Container Networking**
- **Current**: Joined to `sandcastle-web` which is on a single auto-allocated subnet
- **Issue**: If per-sandbox networks exist, how do Rails/Worker reach them?
- **Options**:
  - A. Rails/Worker join **all** per-sandbox networks (creates hundreds of network interfaces — not scalable)
  - B. Create a **management/control network** separate from user networks; sidecars bridge between them
  - C. Use **network namespaces or VRF** to segregate without full Docker network isolation
  - D. **API-only approach**: Don't let Rails directly reach sandboxes; only sidecars (WeTTY, VNC) do

### **Recommended Approach for Minimal Change**

   - Its own isolated network (for inter-sandbox isolation)
4. **Add iptables rules** to block cross-sandbox traffic on the shared network (or use firewall at application level)

1. `initialize_database(db_config)` for each database config
2. For the errors DB: checks if `schema_migrations` table exists
3. If **no** `schema_migrations` → loads `db/errors_schema.rb` → creates tables ✓
4. If **yes** `schema_migrations` → skips schema load, runs pending migrations (none) → no tables created

So the scenario is:
- **First deploy**: postgres fresh → init-databases.sh creates empty errors DB → `db:prepare` → no `schema_migrations` → loads schema → **works** ✓

The tables should persist unless the database was dropped and recreated. Since `init-databases.sh` uses `CREATE DATABASE IF NOT EXISTS`, re-running it won't drop existing data.

**That's the root cause.**

The `init-databases.sh` is written to `$SANDCASTLE_HOME/etc/postgres/` only during `cmd_install` (line 1283). The `cmd_update` path (line 1476) only calls `write_compose` and `write_helper_scripts` — it **never updates the init-databases.sh**.

Here's what happened:
1. Sandcastle was installed **before** solid_errors was added
2. `init-databases.sh` on the server only creates cache, queue, and cable databases — **no errors database**
3. Later, solid_errors was added, the new `init-databases.sh` includes the errors DB, but...
4. `installer.sh update` was run → it didn't update `init-databases.sh` on disk
5. Even if it did, PostgreSQL `docker-entrypoint-initdb.d` scripts only run on **first** init — the existing postgres data means the script never re-runs
6. `db:prepare` runs → tries to connect to `sandcastle_production_errors` → **database doesn't exist** → the `initialize_database` method catches `NoDatabaseError`, calls `create(db_config)` → but the postgres user may not have CREATE DATABASE privileges in this context... or it does create it, but then the schema load might fail silently
