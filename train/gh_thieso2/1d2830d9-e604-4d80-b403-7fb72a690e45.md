Adding WeTTY (butlerx/wetty) provides browser-based terminal access — click a terminal icon on the dashboard and get a shell in a new tab. No client needed. **Key idea:** Generate an ephemeral SSH keypair per terminal session. Inject the public key into the sandbox's `authorized_keys`. Mount the private key into a WeTTY sidecar container. WeTTY auto-connects via SSH — user gets a shell instantly. ## Architecture ``` Browser ──HTTPS──▶ Traefik ──forwardAuth──▶ Rails /terminal/auth (session check) │ │ │◀── 200 OK ──────────────┘ │ ▼ WeTTY container ──SSH──▶ Sandbox container (sc-wetty-{full_name}) ({full_name}:22) on sandcastle-web on sandcastle-web ``` - **One WeTTY sidecar per sandbox**, created on-demand when user clicks "Terminal" - **Ephemeral ED25519 keypair** — pubkey appended to sandbox `authorized_keys` via `docker exec`, privkey mounted into WeTTY - **Traefik forwardAuth** — every request to `/terminal/{id}/wetty/*` validated by Rails (session cookie + sandbox ownership) - **No database changes** — terminal state is purely ephemeral (container exists or not) ### Why forwardAuth? WeTTY has no built-in auth. Once you reach it, you get a shell. Traefik's forwardAuth middleware calls a Rails endpoint on every HTTP request (including WebSocket upgrade). Rails checks the session cookie and sandbox ownership. If invalid → 401, Traefik blocks. This reuses the existing session auth with zero custom token plumbing. ### Network Both WeTTY and the sandbox must be on `sandcastle-web` Docker network so WeTTY can reach `{sandbox.full_name}:22` via Docker DNS. `RouteManager` already has `connect_to_network` for this — we reuse the same pattern. ## Implementation ### Step 1: Create `TerminalManager` service **New file:** `app/services/terminal_manager.rb` Follows the `TailscaleManager` / `RouteManager` patterns. ```ruby class TerminalManager DATA_DIR = ENV.fetch("SANDCASTLE_DATA_DIR", "/data") WETTY_IMAGE = "wettyoss/wetty:latest" NETWORK_NAME = "sandcastle-web" DYNAMIC_DIR = File.join(DATA_DIR, "traefik", …
