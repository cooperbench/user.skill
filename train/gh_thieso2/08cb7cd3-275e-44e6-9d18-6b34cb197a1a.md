    77→Each sandbox = one Sysbox container (`sysbox-runc` runtime) with:
    78→- SSH on a unique host port (range 2201–2299)
    79→- User home bind-mounted from `/data/users/{name}/home`
    80→- Optional persistent volume at `/data/sandboxes/{name}/vol:/workspace`
    81→- Optional Tailscale connectivity via per-user bridge network + sidecar
    82→
    83→The sandbox image (`images/sandbox/`) is Ubuntu 24.04 with Docker-in-Docker, SSH server, and dev tools. Key details:
    84→- runc pinned to v1.1.15 (1.2+ fails in Sysbox)
    85→- Docker daemon MTU matches container's eth0 to avoid fragmentation
    86→- The `entrypoint.sh` creates the user, injects SSH keys, starts dockerd, then runs sshd
    87→
    88→### Web Terminal (WeTTY)
    89→
    90→Browser-based terminal access via [WeTTY](https://github.com/butlerx/wetty) sidecar containers. Each terminal open spawns an ephemeral WeTTY container that SSH's into the sandbox.
    91→
    92→**Architecture:**
    93→- WeTTY container: `sc-wetty-{user}-{sandbox}` on the `sandcastle-web` Docker network
    94→- SSH keypair: generated per-open in `/data/wetty/{full_name}/`, private key copied into WeTTY container via `docker exec` + base64 (bind mounts don't work because Rails runs inside a container with a named Docker volume for `/data`)
    95→- Traefik dynamic config: `terminal-{id}.yml` in `/data/traefik/dynamic/` with forwardAuth middleware
    96→- WeTTY uses `COMMAND` env var with full SSH command including tmux (`tmux new-session -A -s main`)
    97→- `SANDCASTLE_TERMINAL_URL` env var controls the redirect target (needed when Rails is behind a different port than Traefik)
    98→
    99→**ForwardAuth flow (`TerminalController#auth`):**
   100→- Traefik sends each request to `http://sandcastle-web:80/terminal/auth` with `X-Forwarded-Uri`
   101→- Rails validates the session cookie and sandbox ownership (owner or admin)
   102→- Unauthenticated users get redirected to the login page with `return_to_after_authenticating` set to the terminal URL
   103→- Returns 200 to allow, redirect to login, or 401 for unauthorized
   104→
   105→**Important gotchas:**
   106→- Sandbox entrypoint must **append** SSH keys (not overwrite) because all sandboxes for the same user share `/home/{user}` via bind mount
   107→- `remove_pubkey` uses end-of-line regex anchor (`$`) to avoid substring collisions between sandbox names
   108→- Traefik config is written early in `TerminalManager#open` (before container creation) with a 1-second sleep to allow Traefik to detect the new route before the browser redirect arrives
   109→
   110→### Tailscale System
   111→
   112→Per-user Tailscale sidecars connect sandbox containers to a user's own tailnet. Each user gets their own sidecar joining **their** tailnet (not a shared one).
   113→
   114→**Two authentication flows in `TailscaleManager`:**
   115→- **Auth key flow** (`enable`): One-shot with `TS_AUTHKEY` env var, uses default `containerboot` entrypoint
   116→- **Interactive login flow** (`start_login` → `check_login`): Overrides entrypoint to `tailscaled` directly, runs `tailscale up --reset --timeout=10s` to get a browser login URL, polls `tailscale status --json` for `BackendState == "Running"`
   117→
   118→**User `tailscale_state` field:** `disabled` → `pending` (during interactive login) → `enabled`
   119→
   120→**Sidecar architecture:**
   121→- Bridge network: `sc-ts-net-{username}` with subnet `172.{100+user_id%100}.0.0/16`
   122→- Container: `sc-ts-{username}` running `tailscale/tailscale:latest`
   123→- State persisted at `/data/users/{name}/tailscale`
   124→- Advertises subnet routes so sandboxes on the bridge are reachable from the tailnet
   125→- `tailscale_auto_connect` user setting auto-joins new sandboxes to the bridge network
   126→
   127→**Important:** `containerboot` (default Tailscale image entrypoint) conflicts with manual `tailscale up` when no auth key is provided. The interactive flow must override the entrypoint to run `tailscaled` directly.
   128→
   129→### Background Jobs
   130→
   131→Solid Queue with recurring schedule in `config/recurring.yml`:
   132→- `ContainerSyncJob` — every 5 min, reconciles DB sandbox status with actual Docker container state and Tailscale sidecar health
   133→
   134→### Database
   135→
   136→PostgreSQL with 4 separate databases in production (`config/database.yml`):
   137→- `sandcastle_production` — primary (users, sandboxes, api_tokens, sessions)
   138→- `sandcastle_production_cache` — Solid Cache
   139→- `sandcastle_production_queue` — Solid Queue
   140→- `sandcastle_production_cable` — Solid Cable
   141→
   142→The primary database is created by PostgreSQL's `POSTGRES_DB` env var. The other 3 are created by a PostgreSQL init script (`docker/postgres/init-databases.sh`, mounted into `/docker-entrypoint-initdb.d/`). The installer writes this script to `$REDACTED.sh`. When adding or removing Solid* databases, update both the init script and `database.yml`.
   143→
   144→**Database password preservation:**
   145→- Password stored in `$SANDCASTLE_HOME/data/postgres/.secrets` (600 perms)
   146→- On fresh install: generates random password and saves to `.secrets`
   147→- On reinstall: reuses password from `.secrets` to match existing postgres data
   148→- Preserved during uninstall/reset (user data)
   149→- Prevents authentication failures when reinstalling with existing database
   150→
   151→Key constraints:
   152→- Sandbox names and SSH ports are unique only among non-destroyed sandboxes (partial unique indexes: `WHERE status != 'destroyed'`)
   153→- SSH port auto-assigned from 2201–2299 on create
   154→
   155→### Frontend
   156→
   157→ERB templates with Tailwind CSS (v4). Turbo Frames for async container stats. No heavy JS framework — Stimulus controllers only where needed. The Tailscale pending state uses vanilla JS polling (fetch every 3s) to detect auth completion.
