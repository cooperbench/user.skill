what went wrong when the image was generated - do we not know what UID will be used when the container is launched? (1000)

> AGENT

Good question. Two reasons we can't bake `~/.local` correctly at build time: 1. **Username is dynamic, but UID is predictable.** `useradd` runs in `entrypoint.sh` with `$USERNAME` from the per-sandbox env var (e.g. `thies`, `alice`). The UID is whatever `useradd` picks — effectively always `1001` since `ubuntu` already holds `1000`. So yes, UID 1001 is predictable; the path `/home/<USERNAME>` is not. 2. **Even if we hardcoded the username, the bind mount masks anything we'd pre-create.** `/home/<USERNAME>` is bind-mounted from the host (`/data/users/<name>/home/...`). Whatever the image stored at `/home/sandbox/.local` would be hidden under the mount the moment the container starts. So the home dir always starts as whatever's on the host BTRFS subvolume — for a fresh project, that's an empty dir owned by UID 22051 on the host (which Sysbox idmap remaps to UID 1001 inside). Then `entrypoint.sh` (running as root) does `install -d ...local/bin` to seed the Claude binary, and that's where the root-owned intermediate `.local` got created. The bug was a coreutils gotcha, not a UID-knowledge gap. The real fix would have been to use `runuser -u "$USERNAME" -- mkdir -p .local/bin` (or `sudo -u`) so the dirs are created as the user from the start — that's arguably cleaner than `install -d -o user` plus naming each intermediate.
