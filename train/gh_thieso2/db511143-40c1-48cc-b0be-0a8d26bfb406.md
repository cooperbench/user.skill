## Root Cause: `ssh-keygen` fails when key file already exists

**Error chain:**
- `POST /sandboxes/18/terminal` → `TerminalManager#open` → `generate_keypair` → ssh-keygen exits 1
- `terminal_manager.rb:180-181` calls `FileUtils.rm_f(key_path)` but it **silently fails** (likely permissions from a previous session)
- `ssh-keygen` finds `/sandcastle/data/wetty/thies-warm-phoenix/key` still exists, prompts "Overwrite (y/n)?" — with no TTY it exits 1
- The `exception: true` flag turns this into a `RuntimeError`

**Why did the retry (~80s later) succeed?** The second POST at 10:52:27 returned in 25ms via the idempotent check (`container_running?` at line 19) — there's a concurrent earlier request `[e16d2dc3]` that was still running in the background and eventually succeeded in ~12.5s, creating the WeTTY container. The second explicit retry found the container already up.

**The fix:** Replace the `rm_f` on individual files with `rm_rf` on the entire key directory — this is more robust against stale files with bad permissions from a prior session:

## What happened

`POST /sandboxes/18/terminal` → 500 at `terminal_manager.rb:183`

**Root cause:** `generate_keypair` tried to delete existing key files with `FileUtils.rm_f`, which **silently fails** on permission errors (from a key left by a prior session with different ownership). `ssh-keygen` then found the file still there, prompted "Overwrite (y/n)?" with no TTY, and exited 1. The `exception: true` flag turned that into a `RuntimeError`.

**Fix:** Replaced the per-file `rm_f` calls with `rm_rf` on the entire key directory before recreating it. This is atomic enough and handles stale files with bad permissions cleanly.

The second terminal open 80s later worked immediately because a concurrent request (`[e16d2dc3]`) had already successfully created the WeTTY container in the background — so the idempotent `container_running?` check short-circuited, bypassing keypair generation entirely.
