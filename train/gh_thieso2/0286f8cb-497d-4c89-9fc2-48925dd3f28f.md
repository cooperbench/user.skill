The ssh-agent-switcher daemon was fundamentally broken — it could discover forwarded agent sockets but couldn't actually proxy through them ("No agent found; cannot proxy request"). Its `profile.d` script also overrode `SSH_AUTH_SOCK` in every tmux shell, pointing to the dead daemon socket.

It was replaced with a simpler **symlink-based approach**:
- `sc-tmux` symlinks `~/.ssh/agent_sock` → the forwarded agent socket before starting tmux
- A `profile.d` script sets `SSH_AUTH_SOCK` to that symlink
- Default protocol was changed from mosh to SSH (mosh drops the SSH connection after bootstrap, killing the forwarded agent)
- Mosh is still available via `--mosh` flag

# ssh-agent-switcher Overview

## Purpose
ssh-agent-switcher is a daemon that "proxies SSH agent connections to any valid forwarded agent provided by sshd." It solves a specific problem: when you detach a tmux session, log out, reconnect via SSH, and reattach, the original forwarded agent socket becomes invalid, breaking SSH operations within the session.

## How It Works
The daemon "exposes an SSH agent socket at a well-known location, allowing you to set `SSH_AUTH_SOCK` to a path that does _not_ change across different connections." Rather than pointing to a connection-specific socket, you point to the daemon's stable socket. The daemon then searches for a valid forwarded agent socket on each request and forwards traffic to it.

## Command Line Flags & Usage
The primary flag mentioned is `--daemon`, which launches the daemon process. The typical setup involves adding this to your login script:

```bash
~/.local/bin/ssh-agent-switcher --daemon 2>/dev/null || true
export SSH_AUTH_SOCK="/tmp/ssh-agent.${USER}"
```

## Discovery Mechanism
The documentation doesn't explicitly detail the socket discovery algorithm, but it indicates the daemon "looks for a valid socket every time it receives a request" to determine which forwarded agent to proxy to.

## Implementation
The project is written in Rust and emphasizes security: it's intended for unprivileged accounts and doesn't cross security boundaries—it simply forwards requests between sockets you already have access to.

# SSH Agent Socket Discovery Analysis

## Search Patterns

The code searches for forwarded SSH agent sockets in two naming schemes:

1. **HOME-based paths**: Looks directly in directories under the user's home directory for socket files matching pre-OpenSSH 10.1 format ("agent.*") or OpenSSH 10.1+ format (containing ".sshd.")

2. **Shared directories**: Scans subdirectories starting with "ssh-" prefix, then searches within those for matching socket files

## Socket Validation Process

The validation chain includes:

- **Name format check**: Socket must start with "agent." or contain ".sshd."
- **Metadata verification**: File must exist and be readable
- **Socket type confirmation**: "Path is not a socket" error if not a socket file type
- **Connection test**: Attempts actual `UnixStream::connect()` to verify the socket is active
- **Ownership check** (for shared dirs): Socket's parent directory must be owned by the current user

## Potential Failure Points

Even with a valid socket present, discovery fails if:

1. **Directory permissions**: Cannot read the directory containing sockets (`Failed to read directory entries`)
2. **Naming mismatch**: Socket filename doesn't match expected patterns (missing "agent." or ".sshd.")
3. **Dead sockets**: File exists but connection attempt fails (process may have exited)
4. **Ownership violation**: Directory owned by different user than current session
5. **Type mismatch**: File exists but isn't actually a socket (filesystem corruption edge case)

The code gracefully skips invalid candidates and continues searching rather than failing immediately.
