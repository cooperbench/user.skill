I've traced the problem. Let me summarize before touching anything:

**Diagnosis**

- Inside `thies-sandcastle`, `/etc/resolv.conf` points to Docker's embedded resolver `127.0.0.11` — works for the sandbox itself, but unreachable from grandchild containers.
- So when the nested dockerd launches alpine, it falls back to its hardcoded defaults `8.8.8.8`/`8.8.4.4`.
- Packets leave with sandbox IP → masqueraded to host `195.201.204.55` → out eth0. tcpdump confirms TX but **zero RX**.
- Hetzner blocks outbound UDP/53 to public resolvers. I verified from the host itself: `dig @8.8.8.8` and `@1.1.1.1` both time out; Hetzner's own `185.12.64.1`/`.2` work. ICMP to `1.1.1.1` works (hence your `ping 1.1.1.1` success) because it's a different protocol/policy.
- Proof: `docker run --dns 185.12.64.1 alpine nslookup www.heise.de` inside the sandbox resolves correctly.

**Fix options**

1. **Quick, runtime-only** (reversible, scoped to this container): write `/etc/docker/daemon.json` in `thies-sandcastle` with `"dns": ["185.12.64.1","185.12.64.2"]` and restart its dockerd. Doesn't survive sandbox recreation.
2. **Permanent, per-host**: add `Dns` to `HostConfig` in `SandboxManager#create_container_and_start`, driven by a `SANDCASTLE_DOCKER_DNS` env var so the host operator picks resolvers that actually work from their network. All new sandboxes inherit it; nested dockerd picks them up from the sandbox's resolv.conf. This is the correct fix.
3. **Image-level**: bake dnsmasq into the sandbox image and forward to `127.0.0.11`. More moving parts; not worth it if #2 works.

My recommendation: do #2 (code change + env var), then recreate `thies-sandcastle` so it takes effect. I'd also apply #1 right now so Thies isn't blocked while you decide.

- **Root cause**: Hetzner blocks outbound UDP/53 to public DNS (1.1.1.1, 8.8.8.8, 9.9.9.9) from this host; only their own recursors `185.12.64.1/.2` work. The sandbox's `/etc/resolv.conf` only contains Docker's embedded resolver `127.0.0.11` (unreachable from grandchild containers), so the inner dockerd hands nested containers its default `8.8.8.8`/`8.8.4.4` — which Hetzner silently drops. `ping 1.1.1.1` worked because ICMP isn't blocked; DNS queries aren't.

- **Immediate fix** (applied to `thies-sandcastle`): wrote `/etc/docker/daemon.json` with `{"dns": ["185.12.64.1","185.12.64.2"]}` and restarted the inner dockerd. Survives dockerd restart; will not survive sandbox recreation.

- **Permanent fix** (new code, deployed live):
  - `app/services/sandbox_manager.rb`: reads `SANDCASTLE_DOCKER_DNS` env var and passes it as `HostConfig.Dns` when creating sandbox containers. Inner dockerd inherits these via the sandbox's resolv.conf.
  - `docker-compose.yml` + `installer/templates/docker-compose.yml.template`: plumb `SANDCASTLE_DOCKER_DNS` through to web + worker.
  - `/sandcastle/.env` on sandman: `SANDCASTLE_DOCKER_DNS="185.12.64.1,185.12.64.2"`.
  - `sandbox_manager.rb` docker-cp'd into running web+worker and restarted.

All new sandboxes created from now on will have working nested DNS without the daemon.json workaround. Unchanged is that I left the workaround in `thies-sandcastle` — safe to keep; will be overridden if/when it's recreated.
