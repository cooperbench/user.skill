Here's what I found: --- ## The Problem Today, shell interception only works in the **first pane**. The chain is: 1. `cmd_launch()` writes RC file to `~/.dual/rc/dual-repo-branch.sh` 2. `create_session()` creates tmux session, sends `source ~/.dual/rc/...` via `send_keys` into pane 0 3. User splits a pane → new shell starts → **no interception** → `pnpm dev` runs on host The `DUAL_CONTAINER` env var is set inside the first pane's shell process, not in tmux's session environment. New panes don't inherit it. ## The Fix — Two Parts ### Part 1: `tmux set-environment` (code change) After creating the session, set session-level env vars that **all new panes automatically inherit**: ``` tmux set-environment -t {session} DUAL_ACTIVE 1 tmux set-environment -t {session} DUAL_RC_PATH ~/.dual/rc/{container}.sh tmux set-environment -t {session} DUAL_CONTAINER {container} ``` This goes in `tmux_backend.rs` after the `new-session` call. ### Part 2: Shell RC snippet (user setup) User adds 3 lines to their `~/.bashrc` or `~/.zshrc`: ```bash # Dual workspace command interception if [ -n "$DUAL_ACTIVE" ] && [ -n "$DUAL_RC_PATH" ] && [ -f "$DUAL_RC_PATH" ]; then source "$DUAL_RC_PATH" fi ``` Every new pane inherits `DUAL_ACTIVE` + `DUAL_RC_PATH` from tmux → shell RC detects them → auto-sources the interception file. Non-Dual sessions don't have these vars, so the snippet is a no-op everywhere else. ### Why not tmux hooks or `default-command`? - **Hooks** (`after-split-window` + `send-keys`): Works but the `source` command is visible to the user and pollutes shell history - **`default-command`**: Shell-specific (bash `--init-file` vs zsh `ZDOTDIR`), may break user's shell config The `set-environment` + shell RC approach is invisible, shell-agnostic, and doesn't affect non-Dual sessions. --- Research saved to `thoughts/shared/research/2026-02-16-shell-interception-pane-propagation.md`.
