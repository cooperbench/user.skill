explain to me all the different types of github oauth possibilities.

> AGENT

GitHub has a few distinct auth mechanisms that get lumped together as "OAuth." Here's the full picture: ## 1. OAuth Apps (legacy) - Standard OAuth 2.0 authorization code flow → user redirected to `github.com/login/oauth/authorize`. - One token per (user, app). Token acts **as the user**. - Scopes are coarse: `repo`, `read:org`, `user`, etc. — all-or-nothing across all repos the user can see. - No install/uninstall concept. No per-repo selection. No built-in expiry. - GitHub now recommends GitHub Apps over OAuth Apps for almost everything. ## 2. GitHub Apps A separate app type with its own identity and two distinct token types: **a. Installation access tokens (server-to-server)** - You sign a JWT with the app's private key → exchange for a short-lived installation token (1h). - Token acts **as the app itself** on a specific installation (user account or org). - Permissions are fine-grained (e.g., "Contents: read", "Pull requests: write") and chosen per repo at install time. - This is what you use for webhooks, bots, automation. **b. User access tokens (user-to-server)** - Triggered by "Request user authorization (OAuth) during installation" or a standalone user-auth flow. - Same `/login/oauth/authorize` endpoint but on the GitHub App — token is scoped to the intersection of (user's permissions, installation's permissions). - Can be **non-expiring** or **expiring with refresh tokens** (app setting). - Use when you need to make calls *as the user* (e.g., show their private repos in a picker). ## 3. Device Flow - OAuth 2.0 Device Authorization Grant. Works with both OAuth Apps and GitHub Apps. - Your CLI shows a code; user goes to `github.com/login/device` and enters it. - Use for CLIs, desktop apps, TVs — anywhere browser redirect is awkward. ## 4. what do you mean by Alice's user-to-server token?

> AGENT

"User-to-server" is GitHub's own term. It names the token by *who authorized it* and *who uses it*: - **Server-to-server** = installation token. Your server → GitHub. No user involved. App acts as itself. - **User-to-server** = user access token. A user clicked "Authorize", your server got a token back, now your server → GitHub *on behalf of that user*. ## How Alice gets one 1. Alice is in Lightfast and clicks "Connect GitHub" (or hits a feature that needs it). 2. You redirect her to `https://github.com/login/oauth/authorize?client_id=<your_app>&...` — **the GitHub App's** authorize endpoint, not an OAuth App's. 3. Alice sees "Lightfast wants to act on your behalf" and approves. 4. GitHub redirects back to your callback with a `code`. 5. You exchange the code at `/login/oauth/access_token` → you get back: - `access_token` (Alice's user-to-server token, ~8h lifetime) - `refresh_token` (~6 months) - `expires_in` 6. You store both against her Lightfast user row, keyed by her `github_user_id`. ## What it does When you call `GET /user/repos` with Alice's token, GitHub responds *as if Alice made the call*. You see her private repos, her starred repos, her orgs. If you `POST /repos/acme/widgets/pulls`, the PR shows **opened by @alice**, not by "lightfast-bot". The installation token can't do that. An installation token opening a PR shows "opened by lightfast-bot" — useful for automation, wrong for "Alice just clicked merge." ## The permission math Alice's user-to-server token can do **only the intersection** of: - What Alice herself can do on GitHub, AND - What the GitHub App installation grants. So if the install has "Pull requests: write" on repo X, and Alice has write access on X → her token can open PRs on X.
