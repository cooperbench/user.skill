## Research Summary: oRPC Observability Middleware

**Document**: `thoughts/shared/research/2026-04-07-orpc-observability-middleware.md`

### Current State
The oRPC `/v1/[...rest]/` layer has **no observability middleware** — only manual `log.info`/`log.error` calls in the route handler and procedure handlers. No Sentry spans, no isolation scopes, no ALS context seeding, no request journal, no error classification.

### What the tRPC/Inngest Middlewares Provide (that oRPC lacks)
1. **Sentry isolation scope** per request
2. **Sentry span** (`trpc/<path>` / `inngest/<fnId>`)
3. **ALS context seeding** via `withRequestContext` — auto-enriches all `log.*` calls
4. **Duration tracking**
5. **Error classification** — client errors (4xx) logged, server errors (5xx) captured to Sentry
6. **Request journal** emission as structured log

### Key Findings for Implementation
- oRPC middleware has the **same signature** as tRPC: `async ({ context, next, path }) => ...` — making the pattern directly portable
- `ORPCError` exposes `.status` directly (no helper needed) — `error.status >= 500` for server error classification
- The middleware should be inserted **before** `authMiddleware` in the `.use()` chain so auth errors are also covered
- New file: `vendor/observability/src/orpc.ts` with new export `./orpc` in `package.json`
- `emitJournal` currently hardcodes `"[trpc] request journal"` — needs parameterization or an oRPC-specific variant
- `requestId` is already in `context.requestId` from the route handler — no need to generate a new one

### Open Questions
1. Whether to parameterize `emitJournal`'s log prefix or create an oRPC-specific journal emitter
2. Whether `requestId` generation should stay in `route.ts` or move into the observability middleware
