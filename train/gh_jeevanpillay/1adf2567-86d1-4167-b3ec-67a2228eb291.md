## Recommendation: split GitHub out, keep the rest unified Looking at the current schema, GitHub is actually structurally different from Linear/Sentry/Vercel/Apollo in two ways that matter under the new funnel: **1. The 1:1 binding has no schema anchor today.** `gateway_installations` enforces `UNIQUE(provider, external_id)` (`db/app/src/schema/tables/gateway-installations.ts:74-76`) so one GitHub account can't install twice — but `orgId` is just a varchar with no uniqueness. Nothing stops two Clerk orgs from pointing at different GitHub accounts and later colliding, or from an org ending up with two GitHub installations from some migration bug. App-layer checks drift; a `UNIQUE(clerk_org_id)` on a GitHub-specific binding table makes the invariant self-proving. **2. Repos are first-class in v2, nowhere else is.** The funnel's landing page is a repo grid with sync progress and PR counts (`GROUP BY resource_id`). Today "repo" is a `provider_resource_id` string on `lightfast_org_integrations` (`db/app/src/schema/tables/org-integrations.ts:29-103`) — no name, no `full_name`, no `default_branch`, no `is_active`. That metadata lives in transient GitHub API responses and `org_repo_indexes`. No other provider has this problem: Linear's workspace ≈ one row, Vercel projects are flat, Sentry is sparse. ### Shape I'd propose ``` gateway_installations ← keep unified (OAuth tokens are generic) ↑ ├── github_org_binding ← NEW: PK(clerk_org_id), UNIQUE(github_account_id) │ ↓ │ github_repos ← NEW: repo metadata + sync state + is_active │ └── org_integrations ← keep for Linear/Sentry/Vercel/Apollo only ``` - `github_org_binding` replaces the single "GitHub row" in `org_integrations`. PK on `clerk_org_id` gives you the 1:1 for free. - `github_repos` gives the landing page a real home (name, owner, default_branch, last_synced_at, event counts) and lets `gateway_backfill_runs` FK into it instead of referencing an opaque string. - Existing `org_integrations` stays for the resource-scoped providers where the "one row per project/workspace" shape actually fits. ### Where the unified table would actively cause pain - **Enforcing the 1:1** becomes a check-constraint-with-subquery or a partial unique index …
