34	Commands can be chained with `&&` in a single shell invocation. The browser persists between commands via a background daemon, so chaining is safe and more efficient than separate calls.

267	## Efficiency Strategies
268	
269	These patterns minimize tool calls and token usage.
270

273	**Snapshot once, act many times.** Never re-snapshot the same page. Extract all needed info (refs, URLs, text) from a single snapshot, then batch the remaining actions.

569	## Timeouts and Slow Pages
570	
571	The default timeout is 25 seconds. This can be overridden with the `AGENT_BROWSER_DEFAULT_TIMEOUT` environment variable (value in milliseconds).
572	
573	**Important:** `open` already waits for the page `load` event before returning. In most cases, no additional wait is needed before taking a snapshot or screenshot. Only add an explicit wait when content loads asynchronously after the initial page load.
574	
575	```bash
576	# Wait for a specific element to appear (preferred for dynamic content)
577	agent-browser wait "#content"

579	
580	# Wait a fixed duration (good default for slow SPAs)
581	agent-browser wait 2000
582	
583	# Wait for a specific URL pattern (useful after redirects)
584	agent-browser wait --url "**/dashboard"
585	
586	# Wait for text to appear on the page
587	agent-browser wait --text "Results loaded"

690	## JavaScript Evaluation (eval)
691	
692	Use `eval` to run JavaScript in the browser context. **Shell quoting can corrupt complex expressions** -- use `--stdin` or `-b` to avoid issues.
693	
694	```bash
695	# Simple expressions work with regular quoting
696	agent-browser eval 'document.title'
697	agent-browser eval 'document.querySelectorAll("img").length'
698	
699	# Complex JS: use --stdin with heredoc (RECOMMENDED)
700	agent-browser eval --stdin <<'EVALEOF'
701	JSON.stringify(
702	  Array.from(document.querySelectorAll("img"))
703	    .filter(i => !i.alt)
704	    .map(i => ({ src: i.src.split("/").pop(), width: i.width }))
705	)
706	EVALEOF
707	
708	# Alternative: base64 encoding (avoids all shell escaping issues)
709	agent-browser eval -b "$(echo -n 'Array.from(document.querySelectorAll("a")).map(a => a.href)' | base64)"
710	```
711	
712	**Why this matters:** When the shell processes your command, inner double quotes, `!` characters (history expansion), backticks, and `$()` can all corrupt the JavaScript before it reaches agent-browser. The `--stdin` and `-b` flags bypass shell interpretation entirely.
713	
714	**Rules of thumb:**
715	
716	- Single-line, no nested quotes -> regular `eval 'expression'` with single quotes is fine
717	- Nested quotes, arrow functions, template literals, or multiline -> use `eval --stdin <<'EVALEOF'`
718	- Programmatic/generated scripts -> use `eval -b` with base64

## Analysis: PostgreSQL/MySQL MCP Servers for Local Development

### 1. `@modelcontextprotocol/server-postgres` (Official)

- **Source**: `npm install -y @modelcontextprotocol/server-postgres` / GitHub: `modelcontextprotocol/servers/src/postgres`
- **Tools**: One tool — `query` (executes read-only SQL). Also exposes table schema as MCP resources (`postgres://<host>/<table>/schema`) with column names and data types.
- **Config**: Pass a Postgres connection string as the only argument.
- **Read-only vs read-write**: Strictly read-only. All queries run inside a `READ ONLY` transaction. No writes possible.
- **Limitations**: Single tool, no write path, Postgres only (no MySQL). Minimal feature surface — effectively a schema inspector + `SELECT` runner.

### 2. `drizzle-mcp` (Community, GitHub only)

- **Source**: `npx github:defrex/drizzle-mcp` — no npm package yet. GitHub: `defrex/drizzle-mcp`. 12 stars, created July 2025, one contributor.
- **Tools**: `drizzle_generate_migration`, `drizzle_run_migrations`, `drizzle_introspect_schema`, `execute_query`, `initialize_database`. Resources: `database://tables`, `database://schema`.
- **Config**: Point it at your `drizzle.config.ts`. Loads `.env.local` / `.env` automatically — directly compatible with this repo's setup.
- **Read-only vs read-write**: Read-write. `execute_query` runs arbitrary SQL. No safety guardrails documented.
- **Limitations**: No MySQL support (planned). Requires `pg` or `postgres` driver already installed. Extremely early-stage (12 stars, no npm release, one contributor). Not suitable for production use.

### 3. PlanetScale MCP Server (Official, hosted)

- **Source**: Hosted MCP server accessed via OAuth. Not an npm package — configured as a remote MCP URL.
- **Tools**: `get_branch_schema`, `execute_read_query`, `execute_write_query`, `get_insights`, `list_databases`, `list_branches`, and more.
- **Config**: OAuth authentication against PlanetScale's API. Requires a live PlanetScale account and branch.
- **Read-only vs read-write**: Both. Write access is configurable per-scope. Built-in safeguards: replica routing, ephemeral credentials, blocks `UPDATE`/`DELETE` without `WHERE`, requires human confirmation for DDL.
- **Limitations**: Cloud-only — cannot target a local MySQL instance or a non-PlanetScale database. Not useful for local dev against a direct connection string.

### 4. `mcp-server-mysql` (Community)

- **Source**: npm `mcp-server-mysql` (benborla29), GitHub. 4 stars on `sajithrw/mcp-mysql` variant.
- **Tools**: Query execution, schema inspection. Supports AWS RDS.
- **Config**: Environment variables for host, user, password, database.
- **Read-only vs read-write**: Read-write capable.
- **Limitations**: Low adoption, community-only, no meaningful maintenance signal.

For local schema inspection and querying during development against a **Postgres** database: `@modelcontextprotocol/server-postgres` is the only production-grade, officially maintained option. It is read-only, which is appropriate for dev-time inspection.

For **PlanetScale (MySQL)** specifically: the official PlanetScale MCP is the only credible option, but it requires a live PlanetScale connection — it cannot target a local MySQL socket or a raw connection string.
