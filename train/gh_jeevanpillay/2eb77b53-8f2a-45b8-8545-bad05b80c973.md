## Key Findings

**The two packages follow the same structural pattern** — `client.ts`, `react.tsx`, `server.tsx`, `types.ts` — with platform-trpc adding an extra `caller.ts` for non-React backend contexts.

### Differences

| Aspect | app-trpc | platform-trpc |
|---|---|---|
| URL | `/api/trpc` | `/api/trpc/platform` |
| Default port | 4104 | 4112 |
| Auth | Cookie/Clerk (implicit) | Service JWT (explicit) |
| Extra export | — | `./caller` for backend use |
| React provider used? | Yes (`apps/app/layout.tsx`) | **No — never mounted** |

### The URL question

`PlatformTRPCReactProvider` points to `${baseUrl}/api/trpc/platform`, but:
1. **It's never mounted anywhere** — no app layout uses it
2. All platform tRPC calls go through `createPlatformCaller` (direct server-side caller, no HTTP)
3. If it *were* mounted, the URL `/api/trpc/platform` wouldn't work with the platform's `[trpc]` route handler (which expects `/api/trpc/<procedure>`, not `/api/trpc/platform/<procedure>`)

So the `/api/trpc/platform` URL looks like a leftover from when the platform was proxied through the app under a `/platform` sub-path. It's not actively broken because the component is unused.

### Open questions

1. Should `PlatformTRPCReactProvider` be removed as dead code, or is it planned for future use?
2. If kept, should its URL be `${baseUrl}/api/trpc` to match the platform's actual route handler?
