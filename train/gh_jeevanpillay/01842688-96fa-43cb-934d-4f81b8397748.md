Based on my research, here's what I've found:

**Current state**: `@repo/app-clerk-cache` wraps `clerkClient().users.getOrganizationMembershipList()` with a 300s Redis TTL. Cache invalidation was never implemented — zero callers of `invalidateUserOrgMemberships`.

**Key discovery**: `api/app/src/router/user/organization.ts:34` already calls the same Clerk API directly without caching. This confirms the cache layer is redundant.

**Consumer analysis** — the 5 consumers have 3 distinct usage patterns:

| Pattern | Consumers | What they need |
|---|---|---|
| Full membership lookup | `trpc.ts` `verifyOrgMembership` | All 5 fields (role, id, name, slug, imageUrl) |
| Role-only check | `org-access-clerk.ts` | `.find()` by orgId, reads `role` only |
| Boolean membership check | `orpc-middleware.ts`, `with-dual-auth.ts` | `.some()` by orgId — yes/no only |
| Slug-based redirect | `welcome/page.tsx` | `.find()` by truthy slug, reads `organizationSlug` |

**Design decision (open question #1 from research)**: Rather than creating a shared helper, I propose each consumer calls the Clerk API directly and works with the Clerk response type. Reasons:
- The `CachedUserOrgMembership` flattened type only existed for Redis serialization — without caching, consumers can access `m.organization.id` directly
- The Clerk call is a one-liner; the mapping was only needed for the cache layer
- 2 consumers only need a boolean, making a full mapping wasteful
- Avoids creating a new abstraction to replace the one we're deleting

**For open question #2**: Let the `clerk:user-orgs:*` Redis keys expire naturally (300s TTL). No cleanup needed.

Here's my proposed plan structure:

## Overview
Delete `@repo/app-clerk-cache` and replace all 5 consumers with direct Clerk API calls.

## Implementation Phases:
1. **Replace consumers** — Update all 5 files to call Clerk API directly, remove imports
2. **Remove package & config** — Delete package directory, remove dependency/config references
3. **Verify** — Build, typecheck, and lockfile regeneration

Does this phasing and the inline-replacement approach (no shared helper) make sense? Any adjustments before I write the detailed plan?
