## The Verdict: Your Direction is Right, 6 Gaps Remain

The diff is doing the correct thing — consolidating from 3 error-handling layers to 2, replacing hardcoded error code sets with HTTP status derivation, and creating a unified `createObservabilityMiddleware` that replaces Sentry's `trpcMiddleware` with a superset that includes structured logging, trace correlation, and request journals.

### What's solid

- **`beforeSend` with `getHTTPStatusCodeFromError < 500`** — This is exactly what Sentry's own maintainers recommend (PR #9482: "only capture 500s"). The `beforeSend` is a safety net for errors that bypass the middleware, not the primary classification point.
- **Removing `trpcMiddleware`** — Justified. Your custom middleware reimplements everything it does (`withIsolationScope`, `startSpan`, `getRawInput`) and adds structured logging, request journals, auth enrichment, and selective capture that `trpcMiddleware` can't do.
- **Removing `onError` from route handlers** — Correct. The middleware fires for ALL procedure invocations (HTTP, server-side callers, Inngest triggers), not just HTTP requests.

### The 6 gaps for 100x

| Priority | Gap | Impact |
|---|---|---|
| **CRITICAL** | Inngest functions have no `withRequestContext` — log lines have zero automatic enrichment, no way to correlate Sentry exceptions to BetterStack logs | Can't debug background job failures |
| **CRITICAL** | Webhook ingest route has no request context — most failure-prone path has no correlation IDs | Can't trace webhook deliveries through the system |
| **MODERATE** | Client `httpClientIntegration` captures HTTP 400-599 — should be 500-599 | Sentry noise from expected client errors (401, 403, 404) |

The current architecture achieves this for **tRPC requests**. It does NOT achieve this for **Inngest functions** or **webhook routes** — the two paths most likely to fail in production.

## Verdict: The Consolidation Is Directionally Correct

The current diff solves the right problems — triple-logging, duplicate Sentry captures, incomplete error code constants, RSC coverage gaps. The `createObservabilityMiddleware` factory is well-structured and the traceId→log correlation is the most valuable piece for debugging velocity.

## Three Gaps That Will Hurt in Production

### 1. Client-Side Sentry Noise (Critical)

`apps/app/src/instrumentation-client.ts:38-40` — `httpClientIntegration({ failedRequestStatusCodes: [[400, 599]] })` sends **every** tRPC 4xx response to Sentry as a client-side event. Combined with `captureConsoleIntegration` capturing `loggerLink`'s `console.error`, each 4xx creates **two** client-side Sentry events. The server-side cleanup is irrelevant here.

In production: hundreds of UNAUTHORIZED (expired sessions), NOT_FOUND, BAD_REQUEST events flooding the Sentry dashboard, making it unusable for finding real bugs.

**Fix**: Add a `beforeSend` filter to client-side instrumentation that drops `TRPCClientError` where `data.httpStatus < 500`.

### 2. Lost Original Error in Sentry for 500s (High Impact)

`vendor/observability/src/trpc.ts:125` — When tRPC wraps a raw `Error("DB connection refused")` in `TRPCError(INTERNAL_SERVER_ERROR)`, the middleware sends the **wrapper** to Sentry. The issue title becomes "An error occurred in the tRPC handler." for every single 500 — they all look identical. The actual error is hidden in `.cause`.

**Fix**: For `INTERNAL_SERVER_ERROR`, send `result.error.cause` (the original error) to Sentry instead of the wrapper. The tRPC context is already on the scope via `setTag`/`setExtra`.

### 3. `parseError` Utility Is a Footgun (Low Priority Now)

`vendor/observability/src/error/next.ts` — Always calls `captureException` with no classification. Not currently used in tRPC paths, but it's a trap for future developers.

## What's Working Well

- **Single middleware ownership** — no more triple-logging or duplicate captures
- **`getHTTPStatusCodeFromError` over constants** — zero maintenance, covers all 20 tRPC error codes
- **`beforeSend` as defense-in-depth** — catches any TRPCError that leaks through other Sentry integration points
- **traceId→log correlation** — Sentry alert → copy traceId → BetterStack search → full request journal. Collapses 20-minute debugging into 30 seconds.
- **Request journal pattern** — accumulated per-request log entries emitted as one structured entry
- **RSC coverage** — middleware fires for both HTTP and RSC callers
