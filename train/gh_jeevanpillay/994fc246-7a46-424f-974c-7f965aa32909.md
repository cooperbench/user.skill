Based on the research document and my codebase investigation, here's what I understand we're building:

## Understanding

We need to rework the changelog system to fix four issues:

1. **Layout problem**: The "Changelog" heading + RSS link live in `changelog/layout.tsx` which wraps both the listing and `[slug]` pages. Individual entries shouldn't show this header.

2. **Field conflation**: `ogImage` (a required `z.url()` on `BasePageSchema`) serves two unrelated purposes — `<meta>` tags (overridden anyway by programmatic `opengraph-image.tsx`) AND in-page hero image rendering. These should be separate concerns.

3. **Missing `featuredImage`**: No dedicated field exists for in-page hero images. Both `changelog/[slug]/page.tsx:90-101` and `blog/[slug]/page.tsx:135-145` hack around this by conditionally rendering `ogImage`.

4. **Incomplete OG coverage**: Legal and docs pages have no `opengraph-image.tsx` handlers — they fall back to the static `ogImage` URL in meta tags.

## Design Options

**Layout restructuring** — I'd follow the blog's proven pattern:
- Make `changelog/layout.tsx` a bare pass-through (like `blog/layout.tsx`)
- Move "Changelog" heading + RSS into the listing page itself (`changelog/page.tsx`)
- Entry page (`[slug]/page.tsx`) owns its own `max-w-2xl pt-24 pb-32` centering

**`ogImage` removal** — Two options:
- **A) Remove from `BasePageSchema` entirely** — Since all four content types will have programmatic `opengraph-image.tsx`, the frontmatter URL is redundant. This means removing `ogImage` from all MDX frontmatter files and from `seo-bundle.ts` metadata construction.
- **B) Make optional, deprecate** — Keep it as `z.url().optional()` as a fallback for pages without programmatic OG handlers.

I'd recommend **A** — clean break, since we're adding handlers for all types.

**`featuredImage` field** — Add as `z.string().optional()` on `ContentPageSchema` (blog + changelog only, not legal/docs). Accepts relative paths like `/images/changelog/v010-hero.png`.
