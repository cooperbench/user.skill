## Things to decide before I write a plan

**1. "MIT/Apache" — which one, and are you splitting?**
Not interchangeable. MIT is 3 paragraphs, no patent grant. Apache 2.0 has an **explicit patent grant and patent-retaliation clause**, which matters if (a) you ever file patents, (b) you want downstream users protected from contributor patent claims. My recommendation: **Apache 2.0 for everything that was FSL** (the platform), **leave MIT where it is** (SDKs, vendor shims, UI). Mixing MIT libs into an Apache app is fine; the reverse also works but Apache downstream of MIT is standard. A single license across the whole repo is simpler but you'd be downgrading MIT packages that are currently maximally permissive.

**2. You're giving up the only protection FSL gave you.**
The competing-use clause is the entire point of FSL. Drop it and AWS, Cloudflare, or any competitor can legally stand up "hosted Lightfast" tomorrow. Sentry, GitButler, Sourcegraph chose FSL specifically to block this. If you're fine with that (bet is that execution + network effects + hosted ops beat any fork), the decision is coherent. If you're nervous, BSL 1.1 or Elastic License 2.0 keep the anti-rehosting clause with a cleaner story than FSL. **What changed in your thinking here?** Is this about fundraising signal, community pull, enterprise procurement friction, or something else?

**3. FSL already auto-converts to Apache 2.0 after 2 years.**
So "move to Apache" is really "accelerate the conversion by up to 2 years" for the platform code. If the motivation is "we want to be seen as real open source today," fine. If it's something else, the glide path was already there.

**4. Trademark policy.**
FSL has a trademark clause. MIT/Apache don't (trademarks are separate IP anyway, but your `LICENSING.md` currently gestures at it). If "Lightfast" as a brand matters commercially — which it does — you'll want a separate `TRADEMARK.md` to say nobody can ship "Lightfast Cloud" even though they can fork the code. This should ship **with** the relicense, not after.

**5. Irreversibility for shipped versions.**
Once a release is tagged under MIT/Apache, anyone can fork that commit and keep it permissive forever. You can still re-license *future* commits back to FSL, but the SHAs you already publish are free forever. Low risk given no one's shipped an enterprise fork yet, but worth acknowledging.

**6. Contributor agreement.**
`CONTRIBUTING.md:217` still says contributions are licensed under FSL-1.1-ALv2. Needs updating. Worth deciding whether you want a DCO (`Signed-off-by:` on commits) or a CLA — Apache ecosystem convention is DCO, which is lower friction.

## The decision: Apache 2.0, unified across the repo.

Not close. Here's why, from Lightfast's actual shape:

**1. Lightfast is a platform, not a library.** From SPEC.md and README: operating layer, temporal graph, event store, reasoning runtime, action resolver, REST + SDK + MCP surfaces. The commercial product is the hosted service; the OSS is infrastructure. Every serious infra OSS uses Apache 2.0 — Kubernetes, Kafka, Airflow, Spark, TensorFlow, Supabase, Mastra, Inngest, Trigger.dev. MIT is the **library** vernacular (React, Next.js, shadcn). License choice is positioning: Apache 2.0 reads "real infrastructure," MIT reads "dev tool." You want the first one.

**2. Patent surface is real.** Lightfast integrates with GitHub, Linear, Sentry, Vercel — and the roadmap adds Slack, Notion, Stripe, HubSpot, Apollo. Contributors from those ecosystems may carry employer patents around event correlation, graph sync, entity resolution, action orchestration. Apache 2.0 §3 grants a patent license from contributors to users. MIT says nothing about patents — silence ≠ safety. For a platform touching this many APIs, the grant is actual insurance.

**3. Patent retaliation clause.** If anyone sues Lightfast or a user claiming patent infringement on the Software, their license terminates. MIT has no equivalent. This is a defensive moat that costs you nothing.

**4. Enterprise roadmap demands it.** README line 199: *"Self-hosted option — Coming soon for enterprises with strict data residency."* Enterprise procurement reads licenses. Both pass, but Apache 2.0 is preferred — patent terms are explicit and every Fortune 500 legal team has pre-approved it. This is a deal-velocity issue, not a technical one.

**5. NOTICE + modified-file attribution.** Forces forks to surface their lineage. MIT lets someone silently rebrand Lightfast and ship it. Apache at least forces them to say where it came from. Not enforcement teeth, but a signal that compounds when the brand matters.

**6. Foundation path.** If Lightfast ever joins CNCF, LF AI & Data, or Apache Software Foundation — they *require* Apache 2.0. MIT disqualifies. Keep the door open.

**7. Ecosystem vernacular for agent infra.** Mastra, Inngest, Trigger.dev, LangGraph — all Apache 2.0. When the agents-as-infra category consolidates, you want the same license story as peers, not the outlier.

## What I'm rejecting

- *"MIT is simpler for SDK consumers."* 99% run `npm install` and never touch source — zero impact. The 1% who fork add a NOTICE file. Not friction.
- *"JS/TS is MIT-dominated."* True for libraries, false for platforms. The split is product shape, not language.
- *"MIT attracts more drive-by contributors."* With DCO (`Signed-off-by:` — zero paperwork), Apache is functionally identical. Kubernetes runs on DCO + Apache and out-contributes every MIT project in existence.

## Tradeoffs I'm accepting

- `core/*` SDK packages go from MIT → Apache 2.0. Slightly heavier license for library-shaped code, negligible practical impact.
- ~8KB license file vs 1KB. Nobody reads either.
