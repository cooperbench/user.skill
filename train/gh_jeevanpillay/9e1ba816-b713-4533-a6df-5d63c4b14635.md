> AGENT

Good question. Let me assess the actual attack surface of this design.

**The internal router is not HTTP-reachable.** `internalRouter` is never passed to `fetchRequestHandler` or any `serve()` call. The only way to invoke it is through `createInternalCaller()`, which is a direct in-process JavaScript function call — there's no network endpoint an attacker can hit.

The HTTP surface is unchanged:
- `/api/trpc/[trpc]` → routes to `platformRouter` only (JWT-authenticated via `serviceProcedure`)
- `/api/ingest/[provider]` → HMAC-verified webhook ingestion
- `/api/connect/[provider]/*` → OAuth flows

`internalRouter` is a completely separate router tree that none of these handlers reference.

**What are the real risks?**

| Risk | Severity | Mitigation |
|------|----------|------------|
| Developer accidentally wires `internalRouter` into an HTTP handler | Medium | Code review. Could add a lint rule or comment guard. |
| `internalProcedure` has no auth — if exposed over HTTP, full access | High *if* exposed | By design: never served over HTTP. The "if" is the human error above. |
| `source` parameter is a label, not auth | None | Correct — it's for observability, not access control. Trusted code passes it. |
| Any monorepo package can import `@api/platform/internal` | Low | All monorepo code is first-party and trusted. Same as any internal module. |

**Could an external attacker reach it?** No — not without achieving arbitrary code execution on your server first, at which point the internal caller is the least of your problems.

**The one thing worth hardening:** If you want defense-in-depth against accidental HTTP exposure, you could add a guard in `internalProcedure` that throws if headers contain an `Authorization` or `Origin` header (signals that it's coming from HTTP, not in-process). But this is belt-and-suspenders — the primary protection (not serving it) is solid.

Want me to add that guard to the plan, or is the current design sufficient?
