Here's the picture:

**Your current system is already doing structured logging in production.** Every `log.*` call flows through a 28-line wrapper (`log/next.ts`) that:
1. Merges ALS context (requestId, traceId, auth fields) into metadata automatically
2. Pushes to an in-memory request journal (50-entry cap)
3. Ships structured JSON to BetterStack via `@logtail/next`

The tRPC and Inngest middlewares both seed the ALS store, so all downstream `log.*` calls get enriched without manual threading — conceptually the same as pino's `.child()` but via AsyncLocalStorage.

**The gap is local development.** In dev, `baseLog` is `console`, so you get `msg { key: 'value' }` plain text instead of machine-parseable JSON. Other gaps: no log level filtering, no built-in error serialization, no redaction, no transport pluggability.

**What pino would actually change:**

| | Today | With pino |
|---|---|---|
| Dev output | `console` plain text | ndjson, pipe to `pino-pretty` |
| Level filtering | None | `logger.level = 'info'` suppresses debug |
| Error handling | Manual `parseError()` | Built-in Error serializer |
| Call sites (~40 files) | No change needed | Same `log.info(msg, meta)` signature |
| ALS enrichment | Keep as-is | Keep as-is (pino doesn't replace ALS) |
| Journal system | Keep as-is | Keep as-is (pino doesn't have this) |
| BetterStack shipping | `@logtail/next` | pino transport to BetterStack, or keep logtail |

The swap surface is small — you'd replace the 28-line `log/next.ts` to instantiate pino instead of choosing between logtail/console. The 40 consumer files wouldn't need changes since the call signature matches. The ALS enrichment, journal, and middleware layers would stay exactly as they are.

The real question is whether the dev experience gap justifies the dependency. Research doc saved at `thoughts/shared/research/2026-04-07-structured-logging-pino-evaluation.md`.

You're right. `@logtail/pino` (`v0.5.8`) is an official Better Stack pino transport — first-party, actively maintained, ~64K weekly downloads.

**What this means for your setup:**

The migration path would be clean. Instead of the current `@logtail/next` → `console` fallback in `log/next.ts`, you'd instantiate pino with `@logtail/pino` as the transport:

```ts
import pino from "pino";

const logger = pino({
  transport: {
    target: "@logtail/pino",
    options: {
      sourceToken: env.BETTERSTACK_SOURCE_TOKEN,
      options: { endpoint: env.BETTERSTACK_INGESTING_HOST },
    },
  },
});
```

In dev you'd just use pino's default stdout + pipe to `pino-pretty`, giving you structured ndjson locally that's actually readable.

**One thing to flag:** there's an open issue ([logtail/logtail-js#112](https://github.com/logtail/logtail-js/issues/112)) about `@logtail/pino` not flushing reliably in serverless environments. Pino uses a worker-thread transport, and the `close`/`flush` lifecycle doesn't map cleanly to short-lived Vercel functions. Your current `@logtail/next` avoids this because it ships via `fetch`/`sendBeacon` directly — no worker thread.

That said, `@logtail/next` is a completely separate SDK (different repo, custom `Logger` class, no pino internally). So it wouldn't be "adding pino to logtail" — it would be **replacing** `@logtail/next` with `pino` + `@logtail/pino`. The `withBetterStack()` Next.js config wrapper for client-side log proxying would still be needed separately.

The serverless flush concern is worth spiking before committing — especially for Inngest functions where `beforeResponse` currently calls `flush(2000)` on Sentry. You'd need pino's flush to be equally reliable there.
