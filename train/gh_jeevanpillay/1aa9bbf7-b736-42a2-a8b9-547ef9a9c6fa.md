Short answer: blogs need the same AEO bones as the changelog (chunk-level structure, answer-first, FAQ schema) but a different **shape** depending on what the post is trying to win.

## The universal bones (apply to every post)

These come straight from Profound's ML model signals — they're non-negotiable regardless of category:

1. **Answer-first lede** — 30-60 word direct answer to the post's core question, before any "hook" or narrative setup. The days of burying the thesis under a witty intro are over for AEO.
2. **Question-based H2/H3s** — every heading should mirror a query a reader would type into ChatGPT/Perplexity. "Why we chose Drizzle" → "Why did Lightfast choose Drizzle over Prisma?"
3. **Atomic sections** — each H2 must be retrievable as a standalone chunk. Readers (and AI engines) should never need the previous section for context.
4. **FAQPage schema** — 5-7 FAQ items per post in frontmatter. Same as changelog, same reason: it's the single highest-signal structured data type.
5. **Trust block** — author + jobTitle + date + tldr near the top. You already have this infrastructure.

## Shape by category (your 5 existing categories)

Your `BlogPostSchema` already has `category: engineering | product | company | tutorial | research`. Each one has a different optimal structure:

### Engineering posts (the hardest)
**Target shape**: **How-To Guide** or **Technical Deep Dive**
- Lead with the problem in concrete terms ("We were seeing 400ms p99 latency on X")
- Show code. Lots of code. With language-tagged blocks (syntax highlighting is an AEO signal — heading density + code block density together score well)
- Include a "before/after" comparison — Profound's data shows comparison tables are one of the 5 most-cited content formats
- End with a **runnable** takeaway, not a philosophical one
- **Avoid**: "the journey" narratives, "we learned that…" endings, stock illustrations

### Research posts (the highest-leverage)
**Target shape**: **Ultimate Guide** or **Data Story**
- Lead with the finding ("We analyzed X events and found Y")
- Methodology as a collapsible section, not inline
- Charts with text summaries beneath each one (AI engines can't read your SVG — the text caption is what gets cited)
- Cite specific numbers aggressively — these are what get pulled as snippets
- This is the category most likely to earn external citations on G2/Gartner/Reddit, which is how you win Perplexity specifically

### Tutorial posts
**Target shape**: **How-To Guide** (schema.org `HowTo` — you should actually emit HowTo JSON-LD for these, not Article)
- Numbered step format, non-negotiable
- Each step as its own H3 with question-form ("Step 2: How do I authenticate the webhook?")
- Include prerequisites explicitly in a box at the top
- "Common mistakes" section near the end — it captures a different query fanout ("why does X error?")

### Product posts
**Target shape**: **Listicle** or **Feature Announcement**
- These are closest to changelog entries in structure
- Difference: blogs justify the *why*, changelog entries document the *what*
- Lead with use case, not feature name
- Include 1-2 customer scenarios (even hypothetical) — these get pulled into answers more than feature lists

### Company posts
**Target shape**: **Narrative / Thought Leadership**
- The only category where a narrative opening is acceptable — but the tldr still needs to be answer-first
- Author authority matters most here (jobTitle + sameAs signals)
- Shortest of the categories — don't pad

## The three things I'd stop doing

1. **Stop writing intros that "set up" the post.** AI engines skip them. Humans skim them. Lead with the answer.
2. **Stop using clever headings.** "The Great Migration" is invisible to query fanout. "How did we migrate from Prisma to Drizzle?" gets cited.
3. **Stop treating posts as one page.** Every H2 is its own mini-page in retrieval. Write each one to stand alone, even if it means slight repetition — repetition helps chunk retrieval, it doesn't hurt it.

## The one thing worth adding that you don't have

Your current `BlogPostSchema` emits `BlogPosting` JSON-LD. For tutorial category posts specifically, you should emit **`HowTo` schema** in addition to (or instead of) BlogPosting. It's the schema type Google and AI engines most reliably parse for step-based content. You'd need a new builder (`buildTutorialJsonLd`) that branches on `category === "tutorial"`.

## How to use it

When writing a tutorial-category blog post, add this to frontmatter:

```yaml
category: "tutorial"
howToSteps:
  - name: "Install the Lightfast SDK"
    text: "Run npm install lightfast to add the SDK to your project. The package includes typed clients for the search and entity APIs."
    url: "https://lightfast.ai/docs/sdk/install"
  - name: "Create an API key"
    text: "Navigate to Settings → API Keys in the Lightfast dashboard and click Create Key. Copy the key immediately — it's shown only once."
```

The builder will emit both `BlogPosting` (for article metadata, dates, author, FAQ) and `HowTo` (for the step-based content that AI engines parse directly into answers). Non-tutorial posts can omit the field entirely and nothing changes for them.
