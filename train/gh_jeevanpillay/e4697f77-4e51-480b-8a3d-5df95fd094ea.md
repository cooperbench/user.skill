### Key Design Question: Load All vs. Selective

**Option A: Load all skills, let the agent decide** (your current thinking)

- Simpler runtime — no routing logic needed
- Works well with <10-20 skills (which is realistic for most orgs)
- The agent's system prompt includes all skill descriptions, and it pattern-matches against the incoming event
- Cost: slightly more tokens per invocation

**Option B: Pre-filter with `triggers` frontmatter**

- Parse the `triggers` field as a structured filter
- Only load skills whose triggers match the incoming event's provider/type
- Agent gets fewer skills in context = cheaper, faster, more focused
- Cost: more rigid, users have to declare triggers precisely

**My recommendation: Hybrid.** Use the `triggers` field as an optional fast-path filter. If a skill has explicit triggers and the event doesn't match, skip it. If a skill has no triggers (or uses `triggers: all`), always load it. This gives you:
- Cheap pre-filtering for obvious cases (Sentry critical → notify)
- Flexibility for ambient skills ("track what the user is building" has no single trigger)

### The "Knows What User Is Building" Feature

This is an **ambient skill** — it doesn't fire on a single event type. Instead it accumulates context:
- Watches commit patterns, PR activity, branch names
- Maintains a running summary in some state (Redis? a `.lightfast/state/` file?)
- Other skills can reference this context: "the user is currently working on X, so this error in Y is likely related"

This could be a special skill type: `type: ambient` — always loaded, always consulted, but doesn't produce actions on its own. It enriches context for other skills.

### Post-Processing Hook Point

In your pipeline, the natural insertion point is after `platform/event.stored`:

```
platform/event.stored → platform/skill.evaluate (new Inngest function)
```

This function:
1. Loads the org's `.lightfast` config (from repo or stored in DB)
2. Filters skills by triggers
3. Builds agent context (SPEC.md + matched skills + event payload + ambient state)
4. Runs the agent with available tools (Slack, Discord, GitHub comments, etc.)
5. Logs the decision (acted / skipped / deferred)

## Claude Code Skill Execution (The Real Mechanics)

### The `Skill` Tool
Skills are a **real tool** in Claude's tool list (like Bash, Read, Edit). When Claude decides to invoke a skill, it makes an actual `tool_use` call: `Skill({ skill: "name", args: "..." })`.

### What happens on invocation:

1. **$ARGUMENTS** gets string-interpolated (plain find-and-replace)
2. The rendered SKILL.md content is injected as a **user message** (tagged `isMeta: true`) into the conversation
3. Claude gets a **fresh turn** to respond — it's not mid-turn continuation, it's a new API call with the expanded history
4. The skill content **stays permanently** in the conversation from that point forward

### Two paths for invocation:
- **User types `/skill-name`**: Pre-processed before the API call, content injected as user message. Skill tool is NOT called.
- **Claude auto-invokes**: Real `tool_use` block → Claude Code intercepts → injects content → new turn.

### `context: fork` (isolated execution):
Spawns a real sub-agent via `runAgent()` with its own message history. Parent conversation gets back a summary as a tool result. The sub-agent has no access to parent context.

### `allowed-tools`:
Actually mutates runtime permissions — not advisory. Grants tool auto-approval for the session.

### The `skill({ name: '...' })` pattern in your command files:
**Not a real function.** It's instructional text that Claude reads and interprets as "call the Skill tool with this name." Claude then makes the actual tool call.

---

## What This Means For Your Agent

Your agent runtime is **not interactive** — it's event-driven, single-pass. So you don't need the two-path complexity. The analog is:

1. Event arrives → build context (system prompt + SPEC.md + skill descriptions)
2. Agent decides: "this event warrants skill X"
3. Load full SKILL.md + command/*.md for skill X
4. **Inject as additional context** and re-run the agent with tools available
5. Agent executes (sends Slack message, writes memory, etc.)

It's basically the same as Claude Code's `context: fork` path — a fresh agent turn with skill content as the prompt, tools available, and the event as input. The key difference: no conversation history to persist (stateless per-event), but memory files bridge context across events.
