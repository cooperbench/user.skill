very nice. one question. use removing onError from trpc's route.ts what does that do?

> AGENT

`onError` is a callback on tRPC's `fetchRequestHandler` that fires **after** a procedure throws. It was doing two things: 1. **Logging** — classifying errors as expected vs unexpected and logging them 2. **Sentry capture** — calling `captureException` for unexpected errors The problem was this created **duplicate work** with the middleware: ``` Before (error fires both): middleware logs + captures → onError logs + captures again = 2 log entries, 2 Sentry events for the same error ``` Now the middleware handles all of that — classification (via `getHTTPStatusCodeFromError`), logging, and Sentry capture — **before** the error reaches the adapter layer. By the time `fetchRequestHandler` would call `onError`, everything is already handled. ``` After: middleware logs + captures → done = 1 log entry, 1 Sentry event ``` RSC callers (server components calling tRPC directly) never go through `fetchRequestHandler` at all, so `onError` never covered them. The middleware covers both HTTP and RSC paths uniformly. The `beforeSend` filter in `instrumentation.ts` stays as defense-in-depth — if somehow a client error still reaches Sentry, it gets dropped there.
