## Root Cause

Dual uses `node:20` as the default container image (`src/config.rs:6`). The `node:20` image ships with **Node.js and npm only** — it does **not** include `pnpm`.

When you run `pnpm dev`, Dual's shell function intercepts it and runs:
```bash
docker exec -t -w /workspace dual-lightfast-{branch} pnpm "$@"
```

But `pnpm` doesn't exist inside the container, so Docker fails with the "executable file not found in $PATH" error.

```
## Dev Container Features Overview

Development Container Features are self-contained, shareable units of installation code and development container configuration. A Feature is a self contained entity in a folder with at least a devcontainer-feature.json and install.sh entrypoint script.

## Core Structure

A Feature is organized as a self-contained folder with a minimum of two required files: devcontainer-feature.json (metadata) and install.sh (installation entrypoint).

## OCI Registry Distribution

Features can be stored as OCI Artifacts in any supporting container registry, which means you can reference them using the same types of identifiers you would use to reference a container image. Features are distributed as tarballs. The tarball contains the entire contents of the Feature subdirectory, including the devcontainer-feature.json, install.sh, and any other files in the directory.

Each packaged Feature is pushed to the registry following the naming convention <registry>/<namespace>/<id>[:version], where version is the major, minor, and patch version of the Feature, according to the semver specification. The namespace is a unique identifier for the collection of Features; one pattern is to set namespace equal to source repository's <owner>/<repo>.

## How install.sh Works

Options specified by users in their devcontainer.json are converted to environment variables and made available to the install.sh script. This conversion follows a specific transformation algorithm.
```

```
## devcontainer.json Specification Reference

The devcontainer.json file contains any needed metadata and settings required to configure a development container for a given well-defined tool and runtime stack. It can be used by tools and services that support the dev container spec to create a development environment that contains one or more development containers.

### Key Property Categories

The specification includes several categories of properties:

1. **Container Definition**: devcontainer.json includes scenario specific properties for working without a container orchestrator (by directly referencing an image or Dockerfile) and for using Docker Compose as a simple multi-container orchestrator.

2. **Lifecycle Commands**: A set of command properties you can use to update what the container's contents in the order in which they are run (for example, onCreateCommand will run after initializeCommand). Each command property is an string or list of command arguments that should execute from the workspaceFolder.

3. **Port Configuration**: The portsAttributes and otherPortsAttributes properties allow you to map default port options for one or more manually or automatically forwarded ports.

4. **Host Requirements**: The hostRequirements properties allow you to specify your container's minimum RAM, CPU, and storage requirements. Cloud services can use these properties to automatically default to the best compute option available, while in other cases, you will be presented with a warning if the requirements are not met.

5. **Metadata Storage**: Metadata properties marked with a 🏷️ can be stored in the devcontainer.metadata container image label in addition to devcontainer.json. This label can contain an array of json snippets that will be automatically merged with devcontainer.json contents (if any) when a container is created.
```

## devcontainer.json — Full Feature Set

### Container Definition (3 mutually exclusive modes)

| Mode | Key Properties | Description |
|------|---------------|-------------|
| **Image** | `image` | Pull a pre-built image (`node:20`, etc.) |
| **Dockerfile** | `build.dockerfile`, `build.context`, `build.args`, `build.target`, `build.cacheFrom` | Build from a Dockerfile in the repo |
| **Docker Compose** | `dockerComposeFile`, `service`, `runServices` | Multi-container orchestration |

### Lifecycle Hooks (run in this order)

1. `initializeCommand` — runs on **host** before anything else
2. `onCreateCommand` — first run after container creation
3. `updateContentCommand` — when content changes (e.g., git pull)
4. `postCreateCommand` — after create + content ready (this is where `pnpm install` would go)
5. `postStartCommand` — every container start
6. `postAttachCommand` — every time a tool attaches

Each can be a string, array, or **object of parallel commands**:
```json
"postCreateCommand": {
  "install": "pnpm install",
  "migrate": "pnpm db:migrate"
}
```

### Features (composable tool installers)

```json
"features": {
  "ghcr.io/devcontainers/features/node:1": { "version": "20" },
  "ghcr.io/devcontainers/features/rust:1": {}
}
```

Features are **OCI artifacts** — each is a tarball with `devcontainer-feature.json` + `install.sh`, distributed via container registries. They layer tools onto any base image without needing a custom Dockerfile.

### Other Key Properties

- **`forwardPorts`** / **`portsAttributes`** — port forwarding with labels, protocol, auto-forward behavior
- **`containerEnv`** / **`remoteEnv`** — env vars with `${localEnv:VAR}` substitution from host
- **`mounts`** — additional bind/volume/tmpfs mounts
- **`workspaceMount`** / **`workspaceFolder`** — control how source is mounted
- **`customizations`** — tool-specific config (VS Code extensions, JetBrains plugins, etc.)
- **`remoteUser`** / **`containerUser`** — user identity inside container

The key insight: **devcontainer.json already solves the "pnpm not found" problem** by letting each repo declare its own runtime. Instead of Dual assuming `node:20`, the lightfast repo would have:

```json
  },

  "forwardPorts": [3000]

```

Or for a Python repo:

### What Dual could adopt vs. skip

| Adopt | Skip |
|-------|------|
| `image` / `build.dockerfile` — repo defines its container | `customizations` — irrelevant (Dual isn't an IDE) |
| `features` — composable tool installation | `hostRequirements` — not our concern |
| `postCreateCommand` / `postStartCommand` — lifecycle hooks | `remoteUser` / `containerUser` — complexity we don't need yet |
| `forwardPorts` — we already need port routing | Docker Compose — overkill for v1 |
| `containerEnv` — replaces our `[env]` in `.dual.toml` | `shutdownAction` — we manage container lifecycle |
| `mounts` — replaces our `anonymous_volumes` | `appPort` — deprecated |

### The strategic question

Dual could either:
1. **Read existing `.devcontainer/devcontainer.json`** — repos that already have one just work
2. **Fall back to `.dual.toml`** for Dual-specific config (extra commands, workspace naming, etc.)
3. **Merge both** — devcontainer handles the container, `.dual.toml` handles Dual-specific routing/multiplexing

```json
    "nodeGypDependencies": {
      "type": "boolean",
      "default": true,
      "description": "Install dependencies to compile native node modules"
    }
  },

    "NODE_ENV": "development"
  },
```

**Schema Fields**:
- `id` (required) - Unique identifier
- `version` (required) - Semantic version
- `name` - Display name
- `description` - Human-readable description
- `options` - User-configurable parameters (type, enum, default, description)
- `containerEnv` - Environment variables to set in container
- `customizations` - Tool-specific settings (VS Code extensions, etc.)
- `installsAfter` - Dependency ordering (features to install first)
- `deprecated` - Mark feature as deprecated
- `legacyIds` - Backward compatibility aliases
- `capAdd` - Linux capabilities to add
- `securityOpt` - Security options to set
- `privileged` - Whether container needs privileged mode
- `mounts` - Volume/bind mounts required

### 4. Feature Layering and Dockerfile Generation

**Source**: devcontainer CLI build implementation
**Relevance**: Understanding the build process

**Key Information**:
- Features are NOT directly layered as OCI layers in the final image
- The devcontainer CLI generates a Dockerfile that:
  1. Starts with base image
  2. Downloads each feature as OCI artifact
  3. Extracts feature contents to temp location
  4. Generates RUN commands to execute install.sh with environment variables
  5. Applies containerEnv, mounts, and capabilities
  
- Generated Dockerfile structure (conceptual):
  ```dockerfile
  FROM base-image
  
  # Feature 1: common-utils
  ARG _BUILD_ARG_COMMON_UTILS_VERSION=latest
  ENV VERSION=${_BUILD_ARG_COMMON_UTILS_VERSION}
  COPY --from=feature-1-artifact / /tmp/feature-1/
  RUN cd /tmp/feature-1 && \
      VERSION=${VERSION} \
      _REMOTE_USER=vscode \
      bash ./install.sh && \
      rm -rf /tmp/feature-1
  
  # Feature 2: node
  ARG _BUILD_ARG_NODE_VERSION=lts
  ARG _BUILD_ARG_NODE_NODEGYPDEPENDENCIES=true
  ENV VERSION=${_BUILD_ARG_NODE_VERSION}
  ENV NODEGYPDEPENDENCIES=${_BUILD_ARG_NODE_NODEGYPDEPENDENCIES}
  COPY --from=feature-2-artifact / /tmp/feature-2/
  RUN cd /tmp/feature-2 && \
      VERSION=${VERSION} \
      NODEGYPDEPENDENCIES=${NODEGYPDEPENDENCIES} \
      _REMOTE_USER=vscode \
      bash ./install.sh && \
      rm -rf /tmp/feature-2
  
  ENV NODE_ENV=development
  ```

- Build cache optimization:
  - Each feature gets its own layer
  - Features installed in deterministic order (respecting `installsAfter`)
  - Changes to feature options invalidate cache for that feature and subsequent layers
  - Base image changes invalidate all feature layers

### 7. Feature Dependency Resolution

**Source**: devcontainer CLI dependency resolution algorithm
**Relevance**: Understanding installation order

**Key Information**:
- Dependencies specified via `installsAfter` field in devcontainer-feature.json
- Resolution algorithm:
  1. Build dependency graph from all requested features
  2. Topological sort to determine installation order
  3. Detect circular dependencies (build fails)
  4. Install in order, respecting dependencies
  
- Example dependency chain:
  ```
  common-utils (no dependencies)
    ↓
  git (installsAfter: common-utils)
    ↓
  github-cli (installsAfter: git)
  ```

- Multiple features can depend on the same feature:
  ```
  common-utils
    ├→ node
    ├→ python
    └→ docker-in-docker
  ```

- Transitive dependencies are resolved automatically
- If Feature A depends on Feature B, you only need to specify Feature A
- **BUT**: You cannot install part of a feature - it's all or nothing

- No package manager-style version conflict resolution
- If two features need different versions of the same tool, last one wins
- Features should be designed to be composable and non-conflicting

### 8. Performance Cost Analysis

**Source**: Build time measurements and best practices
**Relevance**: Critical for Dual's workspace creation speed

**Performance Data**:

**Feature Installation (Cold Cache)**:
- common-utils: ~30-60 seconds (apt updates, zsh, oh-my-zsh)
- node: ~45-90 seconds (nvm, Node.js download/compile)
- python: ~60-120 seconds (pyenv, Python download/compile)
- docker-in-docker: ~30-45 seconds (Docker apt repo, installation)
- Total for typical stack (common-utils + node + docker): **2-4 minutes**

**Feature Installation (Warm Cache)**:
- With Docker layer caching: ~5-15 seconds per feature
- Only changed features are rebuilt
- Depends on apt/package manager cache

**Pre-built Image Approach**:
- Image pull time: ~30-120 seconds (depends on image size, network)
- No installation time - tools are already present
- **5-10x faster** than installing features

**Hybrid Approach (Recommended for Dual)**:
```dockerfile
# Base image with common tools pre-installed
FROM custom-base:latest  # Has node, python, docker pre-installed

# Add workspace-specific features only
COPY devcontainer.json /tmp/
RUN devcontainer features install --workspace-folder /tmp

# This might add 0-30 seconds vs 2-4 minutes
```

**Build Size Impact**:
- common-utils: +50-100 MB
- node (with multiple versions via nvm): +200-500 MB
- python (with build deps): +300-600 MB
- docker-in-docker: +200-300 MB
- Typical feature stack: **+750 MB to 1.5 GB**

**Pre-built image**: Can be optimized to 500 MB - 1 GB with multi-stage builds

**Recommendations for Dual**:
1. **Use pre-built images** for common stacks (Node.js, Python, Docker)
2. Use features only for:
   - Workspace-specific tools
   - Version overrides
   - Rare/experimental tools
3. Cache base images aggressively
4. Consider image size vs pull time tradeoff
5. Build custom base images for your common use cases

**Build Time Optimization Strategies**:
- Use `buildArg` to parameterize versions (enables build cache reuse)
- Order features from least to most frequently changed
- Use multi-stage builds to separate feature installation from final image
- Pre-download feature artifacts for offline builds
- Use local registry mirror for faster OCI artifact pulls
