## Key Findings

### What's Working
- **tRPC observability is comprehensive**: `observabilityMiddleware` wraps every procedure in ALS, logs outcome/identity/timing, emits journal, and classifies errors for Sentry
- **Sentry error classification is complete**: Both apps have `EXPECTED_TRPC_ERRORS` + `beforeSend` filtering — 4xx noise is eliminated
- **Provider body capture is done**: `readErrorBody` utility used across all providers (1 minor outlier in `sentry/index.ts:62`)
- **The 6 blind files have logging**: All now import `@vendor/observability/log/next`

### 9 Identified Gaps

| # | Gap | Impact |
|---|---|---|
| 1 | **No ALS in Inngest functions** | 12 functions get no auto-enrichment — `requestId`/`correlationId` manually threaded ~40 times |
| 2 | **No lifecycle middleware in Inngest** | Manual `log.info("[fn] starting/complete")` in each function — inconsistent coverage |
| 3 | **No auto correlationId propagation** | Every `step.sendEvent` must manually include `correlationId` — missing it breaks the trace |
| 4 | **`parseError` is architecturally redundant** | Dual-fires captureException + log.error without classification — conflicts with EXPECTED_TRPC_ERRORS pattern. 1 consumer. |
| 5 | **Inngest Sentry captures all retries** | `sentryMiddleware()` has no options — 4 Sentry events for a 3-retry failure. `onlyCaptureFinalAttempt` requires v4 |
| 6 | **oRPC has no ALS integration** | Generates `requestId` but never calls `withRequestContext` |
| 7 | **Sentry provider outlier** | `sentry/index.ts:62` logs body via `console.error` but doesn't include it in thrown Error |
| 8 | **Silent catches in cron functions** | `health-check.ts` and `delivery-recovery.ts` swallow errors without logging details |
| 9 | **`console.error` in SSE stream route** | `gateway/stream/route.ts:108` bypasses structured logger |

### On `parseError` — Should It Be Integrated Architecture-Wide?

**No.** The rest of the codebase has correctly separated the three concerns `parseError` bundles (error extraction, Sentry capture, logging). Its unclassified `captureException` call would send expected errors to Sentry, defeating the `EXPECTED_TRPC_ERRORS` pattern. It should either be **deprecated** or **refactored** to accept classification. The one consumer in the early-access server action should be evaluated for replacement with direct `log.error` + `captureException` calls.

## Key Findings

### What's Done (Tier 1 + ALS + tRPC Consolidation)

All four Tier 1 phases are **fully implemented**. The architecture has evolved beyond the original plan:

- **6 blind files**: All instrumented with structured logging (16 log sites total)
- **Provider body capture**: `readErrorBody` used across 12 sites (2 intentional exceptions)
- **tRPC observability**: Single `createObservabilityMiddleware` factory in `@vendor/observability/trpc` replaces 3 separate layers (timingMiddleware, trpcMiddleware, onError callbacks)
- **Error classification**: Dynamic via `getHTTPStatusCodeFromError()` — no maintained constant sets
- **ALS request context**: Opens scope for every tRPC call, auto-enriches all `log.*` calls with `requestId`, `traceId`, auth fields
- **Journal system**: Accumulates per-request, emitted as single structured log line
- **Sentry quality**: 3-layer defense (middleware capture, server beforeSend, client beforeSend), cause unwrapping for INTERNAL_SERVER_ERROR

### What's Not Done

| Gap | Impact |
|---|---|
| **Inngest ALS** | 12 functions run without request context — no auto-enrichment, no journal |
| **Inngest observability middleware** | `InngestMiddleware` exported but unused |
| **`correlationId` auto-propagation** | Manual pass-through in event data across 6 functions |
| **`parseError` adoption** | 0 imports, 30+ manual `err instanceof Error ? err.message : String(err)` sites |
| **Client-side console cleanup** | 12 `console.*` calls in `apps/app/src/` |
| **Provider console.error** | 1 site in `sentry/index.ts:62` |
| **Inngest silent catches** | 4 catch blocks with no logging |

### `parseError` from `@vendor/observability/error/next`

Pure string-extraction function (Sentry side-effects removed in `ee31e2f96`). Handles `instanceof Error`, duck-typed `.message` objects, raw strings, and fallback `String()`. **Zero imports anywhere** — the utility is orphaned while 30+ call sites manually replicate a subset of its logic.

### Inngest — Highest Leverage Next Step

The v3 `InngestMiddleware` API (`init -> onFunctionRun -> beforeExecution/afterExecution`) is already available. A middleware could wrap each function in `requestStore.run()` to enable ALS auto-enrichment and journal for all 12 functions — no version upgrade needed. This extends the ALS investment to the code paths that need it most.
