## Analysis: @t3-oss/env-core in Electron Forge + Vite

### Summary

`@t3-oss/env-core` works cleanly in Electron's main and preload processes (Node context, `runtimeEnv: process.env`). It does not work as a single shared schema across all three bundles without explicit per-bundle wiring — the renderer requires `import.meta.env` and Vite's `VITE_*` prefix mechanism, which is fundamentally incompatible with a Node-native `process.env` schema. No public GitHub example of a fully integrated Electron + t3-env setup across all three bundles was found, which is itself a signal: this is an unsolved pattern with documented footguns.

---

### Key Findings

#### 1. t3-env in the Main Process (Node.js)
- **Confidence**: HIGH
- **Claim**: `createEnv` from `@t3-oss/env-core` works in the Electron main process with `runtimeEnv: process.env`. No framework adapter needed. Node's `process.env` is the expected runtimeEnv for server-side use.
- **Quote**: "What object holds the environment variables at runtime. This is usually `process.env` or `import.meta.env`." — https://env.t3.gg/docs/core
- **Quote** (source code): `const runtime = opts.runtimeEnvStrict ?? opts.runtimeEnv ?? process.env;` — https://github.com/t3-oss/t3-env/blob/main/packages/core/src/index.ts
- **Provenance**: Official docs + source code agree. No Electron-specific examples found on GitHub, but the Node.js path is unambiguous.
- **Caveat**: t3-env is ESM-only. Electron main process (Forge + Vite) must be compiled as ESM or bundled through Vite with `Bundler` module resolution in tsconfig. The Forge Vite plugin handles bundling, so this is safe if your `vite.main.config.ts` bundles the file rather than externalizing it.

#### 2. Bridging a Schema Across All Three Bundles
- **Confidence**: MEDIUM (pattern is reasoned from first principles + forum evidence; no canonical "official" guide found)
- **Claim**: There is no single-schema approach that works unmodified across all three Electron+Vite bundles. The correct pattern is two separate schemas with a shared Zod type, not one `createEnv` call.
- **Reasoning**:
  - Main + preload: `runtimeEnv: process.env`, `server: { ... }` only (no `clientPrefix`). These are Node contexts. The Forge Vite plugin builds main and preload with `ssr: true`/`resolve.browserField: false` semantics, so `process.env` is live.
  - Renderer: `runtimeEnv: import.meta.env`, `clientPrefix: "VITE_"`. Vite statically bakes `VITE_*` values at build time. Non-`VITE_*` vars are not available in renderer at all.
  - The renderer schema **cannot** reference main-process-only vars. You must decide at schema-definition time which vars are renderer-safe and give them the `VITE_` prefix.
- **Pattern used in practice** (from t3-env GitHub issue #87 + Vite Forge issue #3558): Define `mainEnv.ts` with `runtimeEnv: process.env` for all server vars; define `rendererEnv.ts` with `runtimeEnv: import.meta.env` and `clientPrefix: "VITE_"` for renderer-visible vars. For vars the renderer needs, expose them via preload `contextBridge` (IPC pattern) — not by importing the main env schema into the renderer bundle.
- **The Vite `define` injection pattern** (baking values at build time into renderer) is used but is a footgun with t3-env specifically — see Finding 5 below.
- **Quote**: "Vite doesn't automatically load `.env` files into `process.env` when evaluating the config file." — https://docs.sentry.io/platforms/javascript/guides/electron/sourcemaps/uploading/vite.md
- **Quote**: "In order to trigger the validation during build time, you can import the `env.ts` in `vite.config.ts`" — https://github.com/t3-oss/t3-env/discussions/314 and issue #87

#### 4. `createEnv` Throws at Module-Load Time
- **Confidence**: HIGH
- **Claim**: `createEnv` evaluates synchronously at module import time. If validation fails, it calls `onValidationError` which by default logs and throws `new Error("Invalid environment variables")`. This satisfies build-fail-fast if the env file is imported during `vite.config.ts` evaluation.
- **Quote** (source code): `const onValidationError = opts.onValidationError ?? The `env.ts` import will run during config evaluation but `import.meta.env` will be empty unless you manually call `loadEnv` first. For the main process (which uses `process.env` natively), this is not a problem — `process.env` is populated from the shell environment or dotenv before Vite runs. - **Quote**: "Hmm, wasn't realize that Vite doesn't load env in configuration file. However, there's a workaround for that, it feels hacky." — https://github.com/t3-oss/t3-env/issues/87

#### 5. Footguns with t3-env + Electron/Vite
- **Confidence**: HIGH

**a. ESM-only package, CJS interop required.** t3-env is ESM-only. If your main process Vite config outputs CJS (Electron Forge's default for older templates), you'll hit import errors unless Vite bundles t3-env into the output rather than externalizing it. The fix: set `ssr.noExternal: ['@t3-oss/env-core']` in your `vite.main.config.ts` or confirm it is bundled. The `electron-vite` alt-tool shows this is `ssr.noExternal: true` by default — Electron Forge's Vite plugin does NOT set this by default, so you must configure it explicitly.
- **Quote** (electron-vite defaults): "`ssr.noExternal` | `true`, alway" — https://electron-vite.org/config/

**b. Tree-shaking of `NODE_ENV`-gated code breaks when proxied through t3-env.** When `process.env.NODE_ENV` is read through the t3-env proxy object, bundlers (Vite/Turbo) no longer recognize it as a static string that can be used to dead-code-eliminate dev branches.
- **Quote**: "When `process.env.NODE_ENV` is indirected on another object, this behavior breaks." — https://github.com/t3-oss/t3-env/issues/396

**c. `isServer` detection is wrong in Electron preload.** t3-env defaults `isServer` to `typeof window === "undefined"`. In Electron's preload context, `window` IS defined (preload runs in the browser context but with Node access). This means t3-env will treat the preload as a client environment and throw `"Attempted to access a server-side environment variable on the client"` if you try to read `server` vars from a shared env file imported in preload. The fix: pass `isServer: true` explicitly in any env schema used in the preload.
- **Source**: t3-env issue #154 (jsdom/window detection problem), official docs `isServer` option — https://github.com/t3-oss/t3-env/issues/154
- **Quote**: "I'd say this is an app-concern and you should use the option to override the default behavior." — t3-env maintainer in issue #154

**d. Vite `define` string-replace + Sentry = build error.** If you use Vite's `define: { 'process.env.SENTRY_DSN': JSON.stringify(...) }`, the Sentry SDK may fail to build because `define` replaces occurrences of `process` globally, breaking Sentry's internal `process.env` references.
- **Quote**: "This might be because the `define` option in your Vite config is string-replacing some variable used by the Sentry SDK, like `global`... Vite recommends using `define` for CONSTANTS only, and not putting `process` or `global` into the options." — https://docs.sentry.io/platforms/javascript/guides/electron/troubleshooting/
- **Fix**: Use `define: { '__SENTRY_DSN__': JSON.stringify(process.env.SENTRY_DSN) }` with a custom token, not `process.env.*`.

**e. `experimental__runtimeEnv: process.env` is a Next.js-specific escape hatch.** Do not use it in Electron. It relies on Next.js static analysis of `process.env` references. In Electron's Vite bundles it will silently read a live `process.env` object reference at runtime rather than inlining values, meaning build-time validation succeeds but runtime access may differ. Use `runtimeEnv: process.env` (the standard option) instead.
- **Evidence**: t3-env issue #397 — https://github.com/t3-oss/t3-env/issues/397
