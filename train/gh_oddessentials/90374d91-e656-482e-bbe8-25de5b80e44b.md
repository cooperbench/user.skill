We have T042, T050 the three new issues below. /plan fixes and test coverage so we can confidently wrap up. * **Low-sample threshold cliff (9 → 10 jump)**
  Right now, the UI applies a binary “low sample” indicator based on a hard cutoff (e.g., fewer than 10 data points). This means a dataset with 9 samples is flagged as low-confidence, while 10 samples is treated as acceptable, even though there is almost no real difference between them. This creates a misleading visual cliff where users may over-trust metrics just above the threshold and under-trust those just below it. For someone unfamiliar with the system, it can look like the data suddenly becomes reliable at 10, which is not statistically true. The issue is not the threshold itself, but the abrupt transition in how it is communicated. A better approach would be to represent confidence as a gradient (e.g., gradually increasing opacity, color intensity, or a multi-tier indicator) so users can see that confidence improves continuously, not instantly. This would reduce the risk of misinterpretation without changing the underlying data. However, implementing this requires design decisions around visual encoding and thresholds, not just a code change.

* **Median-of-medians not documented**
  The system calculates metrics like cycle time and review time using weekly rollups, then aggregates those weekly values (e.g., taking the median of weekly medians). This is different from calculating a true median across all individual pull requests, but the UI currently presents the result as if it were a standard median. For most users, this distinction is invisible, but for more technical or analytical users, it can lead to incorrect assumptions about accuracy and distribution. For example, a “median of medians” can behave differently if weekly sample sizes vary significantly. Someone new to the project would reasonably assume the metric is computed from all underlying data points, which is not the case. The issue is not that the calculation is wrong—it is a valid and often practical approach—but that the UI does not disclose how it is derived. A fix would involve adding a small clarification in the tooltip (e.g., “calculated from weekly aggregates”) to set correct expectations. The challenge is balancing transparency with simplicity so the UI does not become overly technical for general users.

* **Delta “vs prev” period unclear**
  The UI shows changes in metrics using a “vs prev” label, but it does not specify what “previous” refers to. For example, if the current data reflects the last 8 weeks, it is unclear whether the comparison is against the immediately preceding 8 weeks, a rolling window, or some other baseline. This ambiguity makes it difficult for users to interpret whether a change is meaningful or just a short-term fluctuation. Someone unfamiliar with the system might assume a different comparison window than what is actually used, leading to incorrect conclusions. The problem is not with the calculation itself, but with the lack of explicit context in the UI. A fix would involve clearly labeling the comparison period, such as “vs previous 8 weeks” or even showing the exact date ranges. This ensures users understand exactly what is being compared and can trust the direction and magnitude of the change. Implementing this may require minor UI adjustments to accommodate the additional text without cluttering the layout.
