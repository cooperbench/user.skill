## Fix Plan: Version Resolution Regression

### Problem

`importlib.metadata.version()` reports the version at `pip install -e .` time, not at execution time. When a developer switches branches or tags without reinstalling, `--version` and `run_summary.json` report a stale version that doesn't match the checked-out code.

### Root Cause

Four independent call sites each implemented their own version resolution, and all four were changed to use `importlib.metadata` exclusively — removing the VERSION file fallback that was accurate for source checkouts.

---

### Design: Single Canonical Resolver

**New file**: `src/ado_git_repo_insights/utils/version.py`

One function, one contract, one module. All four call sites delegate to it.

```python
def resolve_version() -> str:
```

**Precedence contract** (documented in the function docstring):

| Priority | Source | When used | Rationale |
|----------|--------|-----------|-----------|
| 1 | `importlib.metadata.version()` | Package is installed (wheel or editable) AND not running from a repo checkout with a VERSION file | Canonical for installed packages |
| 2 | `VERSION` file at repo root | Running from a source checkout (detected by `VERSION` file existing at the expected repo-relative path) AND either metadata is absent OR metadata is stale (editable install where VERSION differs) | Reflects checked-out code accurately |
| 3 | `"unknown (dev)"` + WARNING | Neither metadata nor VERSION file available | Explicit fallback, never silent |

**"Stale metadata" detection** — explicit, not inferred:

The resolver detects a repo checkout by probing for the VERSION file at a known relative path from `__file__`. If found, this means we're running from a source tree. In that context:
- If `importlib.metadata` succeeds but the VERSION file contains a *different* base version (e.g., metadata says `5.27.2.dev89` but VERSION says `5.28.1`), the VERSION file wins because it reflects the current checkout state.
- If `importlib.metadata` fails entirely, the VERSION file is used as the fallback.
- If no VERSION file exists (wheel install, container, etc.), metadata is the sole source.

**"Repo checkout" detection** — the VERSION file's existence at the expected path IS the signal. No heuristics about `.git` directories or `pip show --editable`. If the file is there, we're in a source tree.

**Stale comparison logic**: Extract the base version (strip `.devN+gHASH` suffixes) from the metadata string and compare to the VERSION file content. If they differ, VERSION wins. If they match (or VERSION has a dev suffix too), metadata wins (it's more precise with the git hash).

### Implementation

**Step 1**: Create `src/ado_git_repo_insights/utils/version.py`

```python
"""Canonical version resolver. Single source of truth for all version reporting."""

import logging
from pathlib import Path

logger = logging.getLogger(__name__)

# Sentinel: repo-root VERSION file relative to this module's location.
# utils/ -> ado_git_repo_insights/ -> src/ -> repo_root/
_REPO_VERSION_FILE = Path(__file__).parent.parent.parent.parent / "VERSION"


def resolve_version() -> str:
    """Resolve the package version using strict precedence.

    Precedence contract:
    1. If running from a source checkout (VERSION file exists at repo root)
       AND installed metadata is absent or stale: use VERSION file.
    2. If installed metadata is present and not overridden: use metadata.
    3. If neither is available: return "unknown (dev)" and log a warning.

    "Stale" means the metadata base version differs from the VERSION file,
    indicating the editable install has not been refreshed since the checkout
    changed (e.g., branch switch, tag bump).
    """
    metadata_version = _read_metadata_version()
    repo_version = _read_repo_version()

    if repo_version:
        # Running from a source checkout
        if not metadata_version:
            return repo_version
        if _is_metadata_stale(metadata_version, repo_version):
            return repo_version
        return metadata_version

    if metadata_version:
        return metadata_version

    logger.warning(
        "Package metadata not found. Version will report as 'unknown (dev)'. "
        "Run: pip install -e ."
    )
    return "unknown (dev)"


def _read_metadata_version() -> str | None:
    """Read version from installed package metadata, or None."""
    try:
        from importlib.metadata import PackageNotFoundError, version
        return version("ado-git-repo-insights")
    except PackageNotFoundError:
        return None


def _read_repo_version() -> str | None:
    """Read version from repo-root VERSION file, or None."""
    if _REPO_VERSION_FILE.exists():
        content = _REPO_VERSION_FILE.read_text().strip()
        if content:
            return content
    return None


def _is_metadata_stale(metadata_version: str, repo_version: str) -> bool:
    """Check if metadata version is stale relative to repo VERSION.

    Stale means the base version in metadata (stripping .devN+gHASH)
    does not match the repo VERSION file content.
    """
    # Extract base version: "5.27.2.dev89+g3bf5b3ba7" -> "5.27.2"
    base = metadata_version.split(".dev")[0].split("+")[0]
    repo_base = repo_version.split(".dev")[0].split("+")[0]
    return base != repo_base
```

## Finding 1: Staleness check ignores commit hash (P2)

**Verified.** The reviewer is correct about the mechanism:

```python
_is_metadata_stale("5.28.1.dev2+gOLDHASH", "5.28.1")  # → False (not stale)
```

When a developer switches commits within the same release cycle (VERSION file unchanged at `5.28.1`), the metadata `+gOLDHASH` suffix points to the wrong commit, but the resolver considers it "fresh" because the base versions match.

**However, the practical impact is narrow:**

- The **base version number** (`5.28.1`) IS correct — only the `+gHASH` suffix is stale
- `run_summary.json` already tracks the real commit via `get_git_sha()` which calls `git rev-parse HEAD` directly — it does NOT use the version string's hash
- The VERSION file only changes on semantic-release commits, so this window exists between releases
- Every major Python tool (setuptools_scm, pip, hatch) treats editable metadata as a frozen snapshot — none re-validate the hash at runtime

**Options:**

| Option | Tradeoff |
|--------|----------|
| A: Always prefer VERSION file when it exists | Loses `.dev2+gHASH` precision in the common fresh-install case |
| B: Compare full string (not just base) | Same as A in practice — metadata always has `.devN` suffix vs clean VERSION |
| C: Accept, document the limitation | Base version is correct; hash is cosmetic; `git_sha` already tracks real commit |
| D: Hash check only in `doctor` command | Targeted fix, but adds subprocess call and git dependency to diagnostics |

**Recommendation:** Option C — add a clarifying docstring noting the `+gHASH` limitation and that `get_git_sha()` provides authoritative commit identity. The base version is always correct. If you want the hash checked too, Option D (only in `doctor`) is the most targeted approach.
