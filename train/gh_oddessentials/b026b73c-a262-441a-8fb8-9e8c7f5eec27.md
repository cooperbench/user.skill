Good question. Here's what happened and why it matters.

### The problem

The `azure-devops-extension-api` package (which provides `CoreRestClient`, `getClient()`, and typed REST clients) ships its JavaScript in **AMD format** (`define(["require", "exports", ...], function() {...})`). Our bundler, esbuild, cannot resolve AMD module exports — it produces "import will always be undefined" warnings and the values are literally `undefined` at runtime.

The `azure-devops-extension-sdk` has the same AMD problem in its main JS, *but* also ships an `esm/` directory that esbuild can resolve. The API package has no ESM variant.

### What the spec planned vs. what happened

The spec (FR-005b) and research (R-03) planned:
```typescript
import { CoreRestClient } from "azure-devops-extension-api/Core";
import { getClient } from "azure-devops-extension-api";
const client = getClient(CoreRestClient);
const projects = await client.getProjects();
```

What was actually implemented in `settings.ts`:
```typescript
const collectionUri = await getCollectionUri();
const token = await getAccessToken();
const response = await fetch(`${collectionUri}_apis/projects?api-version=7.1`, {
  headers: { Authorization: `Bearer ${token}`, Accept: "application/json" },
});
const data = await response.json();
return data.value as VSSProject[];
```

### Implications

**What you lose:**
- No compile-time type safety on the REST response shape (the `TeamProjectReference` type from the API package)
- No automatic base URL resolution from the SDK's internal host connection
- If Microsoft changes the Projects API, the compiler won't catch it — you'd find out at runtime

**What you gain:**
- Consistent pattern — `artifact-client.ts` already does 6+ raw `fetch()` calls to ADO REST APIs with the same Bearer token pattern
- No AMD bundling workaround (esbuild plugin, external + host AMD loader, etc.)
- Simpler dependency surface — the API package is now types-only, no runtime code

**What the alternatives were:**
1. **esbuild AMD plugin** — Would let `getClient(CoreRestClient)` work, but adds a build dependency and the AMD plugin ecosystem for esbuild is immature
2. **Mark API package as `external`** — Let the Azure DevOps host's built-in AMD loader resolve it at runtime. This is how the old `VSS.require()` pattern worked. But our bundles are IIFE format loaded via script tags — there's no AMD loader in our HTML pages
3. **Vendor the ESM source** — Copy and transform the API package's AMD JS to ESM. Maintenance burden.

### Is this acceptable?

The `/_apis/projects` endpoint is a stable, versioned Azure DevOps REST API (api-version=7.1). It's the same endpoint `CoreRestClient.getProjects()` calls internally. The project listing is the **only** place that used the API package's REST client — everything else already used raw `fetch()`.

If you'd prefer the typed `getClient()` pattern, the cleanest path would be option 2 (mark `azure-devops-extension-api` as external in esbuild and rely on the ADO host's AMD loader). That would require adding it back to `externals` in `bundle-ui.mjs` and testing that the host resolves it correctly at runtime. Want me to explore that?

## Fix Plan

Both issues are real runtime regressions. Here's the analysis and proposed fix:

### Issue 1: Duplicate SDK copies (P1)

**Root cause**: `artifact-client.ts` imports `getCollectionUri` and `getAccessToken` from `./modules`, which transitively pulls `import * as SDK from "azure-devops-extension-sdk"` into the `artifact-client.js` bundle. Since `dashboard.js` also bundles the SDK through its own import chain, the dashboard HTML page (`index.html`) loads both bundles and evaluates **two independent SDK instances** — each registering its own XDM message channel with the host.

**Dependency chain**:
```
artifact-client.ts → ./modules → ./modules/sdk.ts → azure-devops-extension-sdk
dashboard.ts       → ./modules → ./modules/sdk.ts → azure-devops-extension-sdk
```

Both are separate esbuild entry points with `bundle: true` and no externals.

**Fix**: Move `getCollectionUri()` and `getAccessToken()` out of `artifact-client.ts`'s import surface. Instead, have `ArtifactClient.initialize()` accept `collectionUri` and `authToken` as parameters — the caller (dashboard.ts, settings.ts) already has SDK access and can pass these in. This way `artifact-client.ts` has zero SDK imports, and only `dashboard.js` bundles the SDK.

This is also architecturally cleaner: the artifact client becomes a pure HTTP client that receives its configuration at initialization, rather than reaching into the SDK itself.

### Issue 2: Missing resize bridge (P2)

**Root cause**: Removing `<script src="VSS.SDK.min.js">` from `settings.html` removed the `globalThis.VSS` object. The `host-resize.ts` module calls `globalThis.VSS?.resize()` to notify the Azure DevOps host when the settings iframe height changes. Without it, longer settings forms get clipped.

**Fix**: The new SDK exports `resize(width?, height?): void` with identical semantics. Update `host-resize.ts` to call `SDK.resize()` instead of `globalThis.VSS?.resize()`. Since `host-resize.ts` is only used by `settings.ts` (which already bundles the SDK), this adds no new bundle duplication. The function should be guarded with a try/catch since it may be called before SDK init completes.
