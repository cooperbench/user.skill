P1 Badge Avoid calling shutdown() from SIGINT handler thread

_signal_shutdown calls httpd.shutdown() from the same main thread that is executing httpd.serve_forever(), which can deadlock on Ctrl+C. In Python’s socketserver.BaseServer, shutdown() blocks waiting for serve_forever() to finish and explicitly requires being called from another thread; when invoked inside the signal handler, the serve loop cannot progress to completion, so the CLI can hang instead of stopping.

## Changes made to PR #228

### Critical fix: deadlock in signal handler (`cli.py`)

The original PR called `httpd.shutdown()` directly from the SIGINT signal handler. This deadlocks because:
- `signal.SIGINT` handlers run on the **main thread** (same thread as `serve_forever()`)
- `shutdown()` blocks waiting for `serve_forever()` to exit
- `serve_forever()` can't exit because the signal handler is blocking its thread

**Fix**: Dispatch `httpd.shutdown()` to a **daemon thread** so the signal handler returns immediately, allowing `serve_forever()` to see the shutdown request and exit its loop.

### Additional hardening
1. **Proper typing**: `types.FrameType | None` instead of `object` for the frame parameter
2. **Handler restoration**: Original SIGINT handler is saved and restored in a `finally` block, so the custom handler doesn't leak beyond the server's lifetime
3. **Error resilience**: The `finally` block ensures handler restoration even if `serve_forever()` raises
