In `review_time.py:80`, the code uses Python string comparison (`vote_ts < earliest_votes[key]`) on ISO 8601 timestamps. ADO timestamps can have **variable fractional second precision**: `2026-01-15T12:00:00Z` vs `2026-01-15T12:00:00.123Z`. String comparison fails when comparing different precisions:
- `"2026-01-15T12:00:00.456Z" < "2026-01-15T12:00:00Z"` → `True` (WRONG: .456Z is actually later)
- Lexicographic sort breaks once microseconds are involved.

**FIX:** Use `datetime.fromisoformat()` to parse both timestamps before comparing.

**2. Inconsistent INSERT strategy — POTENTIAL ISSUE**

In `repository.py`, only `upsert_reviewer` (line 284) was changed to `INSERT ON CONFLICT`. All other upsert methods (`upsert_pr`, `upsert_user`, `upsert_organization`) still use `INSERT OR REPLACE`. This is intentional to preserve `reviewed_at` during re-extractions, but it creates an **asymmetry**: if `pull_requests` or `users` gain a new nullable column in the future that should be preserved on re-upsert, developers won't have the pattern established and may accidentally use `INSERT OR REPLACE` again.

In `review_time.py:88-98`, individual UPDATE statements execute in a loop without a transaction. If extraction crashes after updating reviewer 5 of 10, the PR will have partial `reviewed_at` values. Step 4 (lines 105-133) then computes `review_time_minutes` from the **incomplete** set of reviewers.

**IMPACT:** review_time_minutes may be incorrect if re-run after crash. Not fatal (re-running should fix it), but violates Invariant 9 (recoverable).

**FIX:** Wrap both loops in `db.transaction()` if available, or execute as bulk UPDATE with WHERE clause.

You asked if `review_time_minutes` is recomputed on every run. The code at line 130 **unconditionally UPDATEs** the column for every PR in `pr_uids`. So yes, it's recalculated correctly if a new reviewer is added incrementally. ✓ No issue.

**5. NaN leaking into JSON — FALSE ALARM**

In `aggregators.py:678-689`, the code checks `notna().sum() >= self._ROLLUP_MIN_SAMPLE` **before calling `.quantile()`**. If the count is below threshold, it returns `None` (not NaN). The `_NumpySafeEncoder` then converts numpy floats to Python floats. If `notna().sum()` is exactly `_ROLLUP_MIN_SAMPLE` but all values are identical, `quantile()` returns a scalar (not NaN). The `allow_nan=False` check will catch any stray NaN from malformed data. ✓ Properly guarded.

**6. Synthetic data statistical incoherence — CONFIRMED BUG**

In `generate-demo-data.py:1044-1045`, `_derive_review_time()` calls `RNG.uniform(REVIEW_TIME_RATIO_LOW, REVIEW_TIME_RATIO_HIGH)` **independently for p50 and p90**:

```python
# Line 1157:

```

Each call draws a **different random ratio**. Example:
- `cycle_time_p50=100`, ratio=0.6 → `review_time_p50=60`
- `cycle_time_p90=200`, ratio=0.4 → `review_time_p90=80`
- Result: `review_time_p50 (60) > review_time_p90 (80)` ❌

**FIX:** Generate a single ratio once per entity, then apply it to both p50 and p90.

---

**7. Migration transaction in autocommit mode — CONFIRMED BUG**

In `migrations.py:31`, the code calls `cursor.execute("BEGIN TRANSACTION")` but `database.py:78` connects with `isolation_level=None` (autocommit). 

SQLite in autocommit mode **ignores `BEGIN TRANSACTION` commands**—each statement commits immediately. The explicit `conn.commit()` at line 39 is a no-op. If `ALTER TABLE` succeeds but `INSERT OR IGNORE` fails, the ALTER is already committed and rollback does nothing.

**IMPACT:** Medium risk. Schema is partially applied on failure. Not data corruption, but inconsistent state.

**FIX:** Either set `isolation_level=""` (not None) to enable explicit transaction control, OR remove the transaction wrapper since autocommit is acceptable for DDL.
