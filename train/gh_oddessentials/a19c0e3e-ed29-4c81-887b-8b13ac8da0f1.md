### Decision 5: Preflight error contract — exit codes and message categories

**Decision**: Introduce structured error categorization without changing exit codes.

**Current state**: Everything exits with code 1 (or propagated subprocess code). There's no way to distinguish "you need to install gitleaks" from "your tests are failing."

**New contract**:

| Category | Message prefix | Exit code | Degraded-mode behavior |
|----------|---------------|-----------|----------------------|
| **SETUP** | `[SETUP]` | 2 | Fatal even in degraded mode — machine is not ready |
| **INFRA** | `[INFRA]` | 3 | Skippable with `--allow-local-degraded` |
| **GATE** | `[GATE]` | 1 | Always fatal — code quality regression |

**SETUP** (missing tool / capability):
- Python not found or wrong version
- pnpm not found
- Node.js not found
- `.husky/` directory missing
- `pre-commit` not found

**INFRA** (environment / network):
- `git fetch origin/main` failed
- Suppression baseline unavailable
- Node child-process check failed
- gitleaks not found (CI parity tool, not core capability)

**GATE** (code quality regression):
- All quality checks (mypy, pytest, ESLint, suppressions, coverage, etc.)
- Propagated subprocess exit codes from quality tools

**How degraded mode works with this**:
- `--allow-local-degraded` converts **INFRA** failures to warnings and skips dependent gates
- **SETUP** failures always block — your machine isn't configured
- **GATE** failures always block — your code has regressions
- Degraded completion still returns exit code 0 with explicit `[WARNING]` summary

**Message format**: Each failure prints:
```
[SETUP] pnpm not found on PATH.
  Install: https://pnpm.io/installation
  Required for: Extension type checking, linting, and testing
```

Or:
```
[GATE] Extension lint failed (exit code 1)
  Command: pnpm run lint
  Fix: Run 'cd extension && pnpm run lint' to see details
```

## Root Cause Analysis

There are **two distinct Windows friction sources**, and they have different root causes:

### 1. `.coverage` access denial (repo root)

**What happens:** `pyproject.toml` line 89 sets `addopts = "--cov=src/ado_git_repo_insights --cov-report=term-missing"`, which means **every `pytest` invocation** writes a `.coverage` SQLite database to the repo root. On Windows, SQLite files are subject to OS-level file locking. If any process holds a handle (anti-virus scanner, VS Code file watcher, a crashed previous pytest, Windows Search indexer), the next `pytest` run fails with `PermissionError` trying to open `.coverage` for writing.

**Why preflight doesn't hit this:** `run_pr_preflight.py:350` redirects coverage via `extra_env={"COVERAGE_FILE": str(coverage_file("python"))}` to `%TEMP%/ado-git-repo-insights/pr-preflight/coverage/.coverage.python`. This keeps the coverage SQLite off the repo root entirely.

**Why bare `pytest` does hit this:** There's no `COVERAGE_FILE` override in `pyproject.toml` or `conftest.py`. The developer running `pytest` directly (the most common workflow) writes to `$REPO_ROOT/.coverage`. That path is inside the repo working tree, which is a hot zone for Windows file-handle contention.

**The fix direction:** Move the default `COVERAGE_FILE` out of the repo root. Options:
- Set `data_file` under `[tool.coverage.run]` in `pyproject.toml` to a path under `.pytest_cache/` or similar
- Set `COVERAGE_FILE` in a `conftest.py` fixture or `pytest_configure` hook
- Or: set `data_file = .pytest_cache/.coverage` in pyproject.toml (stays in the repo but inside the already-gitignored cache dir, which is less contended)

### 2. Inaccessible pytest temp directories (`%LOCALAPPDATA%\Temp\pytest-of-petep`)

**What happens:** pytest's `tmp_path` fixture creates directories under `%LOCALAPPDATA%\Temp\pytest-of-<user>/pytest-<N>/`. pytest retains the last 3 runs by default (configurable via `tmp_path_retention_policy`). On Windows, if a previous test created a file that a background process later locks (SQLite DB, log file, anything), pytest's cleanup of older runs fails with `PermissionError`. The cascading failure mode: pytest can't clean old directories, accumulates stale ones, and eventually the entire parent directory becomes unhealthy.

**Why preflight doesn't hit this:** `run_pr_preflight.py` passes `--basetemp str(base_temp("python"))` which redirects to `%TEMP%/ado-git-repo-insights/pr-preflight/tmp/python/`. This is a dedicated path that preflight manages (it cleans up the build dir explicitly at line 770-771, and the temp paths are scoped to the preflight lifecycle).

**Why bare `pytest` does hit this:** Again, no `basetemp` override in `pyproject.toml`. The default location accumulates directories over time, and Windows file locking makes cleanup unreliable.

**The fix direction:** Options:
- Set `basetemp` in `pyproject.toml` `addopts` to a stable, dedicated path (risky — absolute paths in config aren't portable across machines)
- Add a `conftest.py` `pytest_configure` hook that sets basetemp dynamically to `%TEMP%/ado-git-repo-insights/pytest/`
- Set `tmp_path_retention_policy = "none"` in `pyproject.toml` (don't retain old temp dirs at all — eliminates the accumulation problem)

### Why these are the same root issue

Both problems share one cause: **the repo's pytest configuration assumes Unix-like file semantics where handles are released immediately, but Windows uses mandatory file locking.** The preflight script already has workarounds for both — `COVERAGE_FILE` redirection and `--basetemp` — but these workarounds only apply to the preflight invocation path, not to bare `pytest`.

The gap is: a developer who runs `pytest` directly (the Quick Start workflow) is on a different code path than a developer who runs `python scripts/run_pr_preflight.py`, and only the latter is Windows-safe.

### Connection to our branch

Our branch fixed the *shell dependency* dimension of Windows friction (PowerShell, Bash, sh) but didn't touch the *file locking* dimension. The ACL health check we ported probes `.git/` and `.pytest-tmp*` for write access, but it doesn't cover `.coverage` or the system temp directory — those are outside its scope.
