## Gate Fragility Analysis: 047-close-suppression-blindspot

### 1. Baseline Merge Conflicts -- **BLOCKER**

`.suppression-baseline.json` is a flat JSON file with no merge-safe structure. Two PRs touching different scopes (e.g., one cleaning `python-tests`, another cleaning `python-scripts`) will produce textual merge conflicts in `by_scope`, `scope_policy`, `by_rule`, and `total`. JSON has no union-merge strategy; a naive conflict resolution (accept-theirs or accept-ours) produces **wrong totals** that silently pass validation if they happen to satisfy `total == sum(by_scope)`. The plan has no `--update-baseline` post-merge reconciliation step.

**Blast radius**: CI on main goes red or, worse, goes green with an inflated baseline that masks new suppressions.

### 2. Artifact Staleness Race -- **GAP**

The plan states CI verifies `.rule-disable-audit-S603.json` matches the codebase (Phase C, step 4). But the verification mechanism is unspecified. If it is a committed artifact checked via `git diff`, then PR-A (adding a new `subprocess.run`) will carry a stale artifact. The guardrail script (step 3) catches the *violation*, but only if it runs on the PR branch. If CI only checks artifact-vs-codebase consistency and PR-A's artifact was generated before the new call site, the check passes with stale data. **The guardrail and the artifact check have overlapping but non-identical coverage, and neither is defined as authoritative.**

### 3. Two-Phase Transition Timing -- **RISK**

Developer pushes a suppression to an advisory scope. Someone else commits the Phase 2 baseline (advisory-&gt;blocking). Developer rebases. The `cmd_diff()` function checks `scope_policy` from the *committed baseline* file, which now says `"blocking"`. The diff will correctly fail with a count increase. However, the error message will say "suppression count increased in scope python-scripts" with no mention that the scope *just became blocking*. The developer must correlate baseline commit history to understand why their previously-passing branch now fails. **Not a silent failure, but a confusing one.** The plan has no transition notification mechanism.

### 4. Tokenize Failure Modes -- **CONFIRMED (plan-acknowledged, insufficiently mitigated)**

Plan line 121: `TokenError` handling returns empty list. This means a file with a syntax error has **zero detected suppressions**, which matches or improves the baseline. A developer could add `# type: ignore` to a syntactically broken file and the scanner would report 0 for that file. The `--check-coverage` gate confirms the file exists in a scope, but the scanner silently produces a false negative. **No warning propagates to the diff exit code.**

### 5. File Coverage vs .gitignore -- **GAP**

`EXCLUDED_DIRS` (line 154) is a hardcoded set: `{node_modules, dist, .venv, venv, build, coverage, __pycache__, .git}`. The `.gitignore` is not consulted. Any gitignored directory not in this set (e.g., `run_artifacts/`, `htmlcov/`, `eggs/`, `.mypy_cache/`) that contains `.py` files will be enumerated by the coverage check and either flagged as uncovered (noisy false positive) or incorrectly assigned to a scope. The plan's file-coverage check (Phase B, step 2) will walk the repo tree using `rglob`, which does not respect `.gitignore`. **`.mypy_cache/` is notably absent from `EXCLUDED_DIRS` and commonly contains `.py` stubs.**

### 6. Phase A/B Ordering and Cross-Branch Scanner Divergence -- **RISK**

If Phase A (tokenize scanner) merges to main, and a parallel branch still running the old regex scanner adds test data containing string-literal `# noqa` patterns, the old branch will count those as real suppressions. When that branch rebases onto the tokenize scanner, the count *drops*, which passes the ratchet. The reverse is more dangerous: if Phase B (new scopes) merges first and someone on an old-scanner branch gets the new scope definitions but still has the regex scanner, string literals in `scripts/` or `tests/` could inflate counts. **The plan assumes linear merge order but does not enforce it via a feature flag or scanner-version check in the baseline.**
