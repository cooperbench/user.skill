Great choices. Here's the design:

## Design: Local Dev Scripts & Integration Tests

### 1. `docker-compose.yml` — Local infrastructure

Provides the services the app depends on:

```yaml
services:
  postgres:
    image: postgres:16
    ports: ["5432:5432"]
    environment:
      POSTGRES_DB: releaseguard
      POSTGRES_USER: postgres  
      POSTGRES_PASSWORD: postgres
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck: pg_isready
```

Just Postgres. The Go server and Next.js dev server run natively (faster iteration, better logs). Docker-compose is for dependencies, not the app itself.

### 2. `Makefile` — Unified command interface

**Infrastructure:**
- `make up` / `make down` — start/stop docker-compose services
- `make db-reset` — drop and recreate the database

**Backend:**
- `make build` — `go build -o releaseguard ./cmd/server`
- `make run` — build + run server (depends on `up`)
- `make test` — `go test ./...`
- `make vet` — `go vet ./...`
- `make lint` — vet + any other checks

**Frontend:**
- `make frontend-install` — `npm install` in `web/`
- `make frontend-dev` — `npm run dev` in `web/`
- `make frontend-build` — `npm run build` in `web/`

**Integration:**
- `make integration-test` — runs the full integration test suite

**Convenience:**
- `make dev` — starts Postgres + runs server (single command to get going)

### 3. `scripts/integration-test.sh` — Updated & expanded

Fix the existing script and expand it:

- **Fix:** Update job kind from `pipeline_process` to `notify_release`
- **Add API tests:** CRUD operations for projects, sources, subscriptions
- **Add release flow test:** Create project → add source → webhook → verify release + notification job
- **Use docker-compose Postgres** when available, fall back to spinning up its own container
- **Structured output:** Clear pass/fail per test case with summary

### Approach trade-offs

I considered two alternatives:

1. **Go-based integration tests** (using `testing` package + `testcontainers-go`) — More idiomatic Go, but adds a heavy dependency and the existing bash approach works well for HTTP-level testing.

2. **Everything in docker-compose** (app + Postgres in containers) — Slower iteration cycle, harder to debug, and the static binary approach means you'd need to rebuild the container image on every change.

The **Makefile + docker-compose for deps + bash integration tests** approach is the sweet spot: fast iteration, minimal dependencies, easy to understand.

Does this design look right? Anything you'd add or change?

    48→## Architecture
    49→
    50→Four decoupled layers communicate exclusively through PostgreSQL:
    51→
    52→1. **Ingestion Layer** — Polling workers behind `IIngestionSource` interface discover new releases from upstream registries
    53→2. **Notification Routing** — River `NotifyWorker` sends source-level notifications to subscribed channels on new releases
    54→3. **Agent Layer** — ADK-Go agent (`internal/agent/`) researches releases via project-scoped tools and produces semantic release reports
    55→4. **Routing & Output** — Notification channels (Slack, Discord, webhooks) behind `Sender` interface
    56→
    57→### Transactional Outbox Pattern
    58→
    59→The critical data integrity pattern: release insert + River job enqueue happen in the same SQL transaction (`internal/ingestion/pgstore.go`). If either fails, both rollback — zero-loss guarantee.
    60→
    61→### Key Interfaces
    62→
    63→- `IIngestionSource` (`internal/ingestion/source.go`) — Polling-based providers implement `FetchNewReleases(ctx) ([]IngestionResult, error)`
    64→- `ReleaseStore` (`internal/ingestion/store.go`) — Persistence: `IngestRelease(ctx, sourceID string, result *IngestionResult) error`
    65→- `Sender` (`internal/routing/sender.go`) — Notification channel output: `Send(ctx, channel, msg) error`
    66→- `NotifyStore` (`internal/routing/worker.go`) — Data access for the notification worker
    67→- `AgentDataStore` (`internal/agent/tools.go`) — Data access for agent tools (releases, context sources)
    68→- `OrchestratorStore` (`internal/agent/orchestrator.go`) — Full data access for agent orchestrator (project, agent runs, semantic releases)
    69→
    70→### Data Flow
    71→
    72→```
    73→IIngestionSource.FetchNewReleases() → IngestionResult
    74→    → Service.ProcessResults() processes results
    75→    → PgStore.IngestRelease() in single TX: INSERT release + River InsertTx(NotifyJobArgs)
    76→    → NotifyWorker picks up job → sends source notifications + checks agent rules
    77→    → If rules match → enqueue AgentJobArgs
    78→    → AgentWorker picks up → runs ADK-Go agent → creates semantic release
    79→    → Sends project notifications
    80→```
