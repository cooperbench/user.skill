Given your choices (centered dialogs for all CRUD, styled delete confirmations), there are two main architectural approaches: ## Approach A: Dialog-per-Page (Recommended) Each list page owns its dialogs internally. The "New" and "Edit" buttons on each list page open a `<Dialog>` containing the existing form component. No routing changes needed — state is managed with `useState`. **Pros:** - Simple — each page is self-contained - No URL-based modal state to manage - Existing form components (ProjectForm, SourceForm, etc.) can be reused with minimal changes - Delete old `/new` and `/edit` page files entirely **Cons:** - Refreshing the page closes any open dialog (no deep-linking to "edit project X") - Browser back doesn't close the dialog (it navigates away) ## Approach B: URL-Driven Dialogs (Intercepting Routes) Use Next.js parallel/intercepting routes (`@modal/(.)projects/new`) so dialogs are URL-backed. Opening `/projects/new` from the projects list shows a dialog overlay; navigating directly shows the full page as fallback. **Pros:** - Deep-linkable — sharing a URL opens the dialog - Browser back closes the dialog naturally **Cons:** - Significantly more complex routing setup - Intercepting routes in Next.js App Router can be brittle - More files to manage (parallel route slots, default.tsx fallbacks) **My recommendation: Approach A.** The forms are short admin-style CRUD — deep-linking to "create project" isn't a real user need. The simplicity tradeoff is well worth it. We reuse the existing form components, wrap them in `<Dialog>`, and delete the standalone page files.
