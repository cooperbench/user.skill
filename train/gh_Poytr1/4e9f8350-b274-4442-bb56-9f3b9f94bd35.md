# ADK-Go: CLI and Web UI Architecture

## 1. How the ADK CLI Works with Go Agents

Unlike Python ADK (which has a separate `adk` CLI tool), Go agents **embed the launcher directly in the agent code itself**. The agent's `main()` function uses the `launcher` and `full` packages to create a self-contained executable:

```go
l := full.NewLauncher()
if err = l.Execute(ctx, config, os.Args[1:]); err != nil {
    log.Fatalf("Run failed: %v\n\n%s", err, l.CommandLineSyntax())
}
```

The launcher parses `os.Args[1:]`, meaning command-line arguments control the agent's behavior. When run with **no arguments**, the agent starts in interactive command-line mode:

```bash
go run agent.go
```

This produces a terminal-based chat interface where you can interact with the agent directly.

## 2. Running the Web UI

To launch the web interface, you pass specific subcommands as arguments:

```bash
go run agent.go web api webui
```

This tells the launcher to start three components: a **web server**, an **API server**, and the **web UI**. The interface becomes available at `http://localhost:8080`, where you can select your agent and chat with it through a browser.

> **Important caveat:** "ADK Web is **_not meant for use in production deployments_**." It's intended only for development and debugging.

## 3. Architecture

The architecture connects these pieces:

- **Agent definition** → Created via `llmagent.New()` with a model, tools, instructions, and configuration
- **Agent loader** → `agent.NewSingleLoader(timeAgent)` wraps the agent for the launcher
- **Launcher** → `full.NewLauncher()` provides both CLI and web serving capabilities
- **Model** → The agent connects to Gemini (or other models) via `gemini.NewModel()` using an API key
- **Tools** → Built-in tools like `geminitool.GoogleSearch{}` are passed in the agent config

The key architectural insight is that the Go agent is a **self-contained binary** — the launcher, API server, and web UI are all compiled into the same executable, controlled by command-line arguments.

## Design: ADK-Web Dev Entrypoint

### Architecture

A new `cmd/agent/main.go` binary that wires up the existing agent components and hands them to the ADK launcher:

```
cmd/agent/main.go
    ├── Parse --project-id flag
    ├── Connect to Postgres (DATABASE_URL)
    ├── Validate project exists in DB
    ├── Read LLM config from env vars
    ├── Create LLM model via existing NewLLMModel()
    ├── Create project-scoped tools via existing NewTools()
    ├── Create agent via llmagent.New()
    ├── Wrap in agent.NewSingleLoader()
    └── full.NewLauncher().Execute() → serves adk-web UI
```

No changes to production code. The new entrypoint reuses `internal/agent` (model, tools), `internal/db` (pool), and `internal/api` (PgStore for read-only data access).

### Data Flow

```
User ──browser──▶ adk-web UI (localhost:8080)
                      │
                      ▼
              ADK Launcher (API server)
                      │
                      ▼
              llmagent "release_analyst"
                 ├── get_releases       ──▶ PgStore ──▶ PostgreSQL
                 ├── get_release_detail  ──▶ PgStore ──▶ PostgreSQL
                 └── list_context_sources──▶ PgStore ──▶ PostgreSQL
                      │
                      ▼
              LLM (Gemini / OpenAI)
```

The agent runs interactively through the web UI instead of headlessly via River. Same tools, same model, same prompt — but you can chat with it, inspect events, and debug tool calls.

### New file: `cmd/agent/main.go`

Responsibilities:
1. `--project-id` flag (required, validated against DB)
2. `DATABASE_URL` env var → `db.NewPool()`
3. `PgStore` with `river=nil` (no queue needed)
4. Load project to build instruction (custom prompt + default)
5. `NewLLMModel()` with same env var config as server
6. `NewTools(store, projectID)` for project-scoped tools
7. `llmagent.New()` with same config shape as orchestrator
8. `agent.NewSingleLoader()` → `launcher.Config`
9. `full.NewLauncher().Execute(ctx, config, os.Args[1:])` — passes remaining args after flag parsing

### Dependency: `launcher/full` package

ADK-Go v0.5.0 should include `google.golang.org/adk/cmd/launcher/full`. A `go mod tidy` will pull it in when the import is added.

### Makefile target

```makefile
agent-dev:
	DATABASE_URL=$(DATABASE_URL) go run ./cmd/agent \
		--project-id=$(PROJECT_ID) web api webui
```

Usage: `make agent-dev PROJECT_ID=<uuid>`

### What's NOT changing

- `cmd/server/main.go` — untouched
- `internal/agent/orchestrator.go` — untouched
- `internal/agent/tools.go` — untouched  
- `internal/agent/model.go` — untouched
- Production agent flow via River — untouched

## Root Cause

Found it. `ReleaseItem.RawData` (line 35) and `GetReleaseDetailOutput.RawData` (line 58) are typed as `json.RawMessage`, which is `type RawMessage []byte`.

When ADK-Go's `functiontool` generates the JSON schema from the Go struct, it sees `[]byte` → infers JSON type `"array"` (array of bytes). But the actual database content in `raw_data` is a JSON **object** (e.g., `{"changelog": "...", "release_url": "..."}`).

This works fine with the production River worker because the orchestrator just consumes the raw text output. But the ADK launcher validates tool return values against the schema, causing this validation error.

**The fix:** Change `json.RawMessage` to `any` (or `map[string]any`) so the schema says "object" or accepts any type. Since `raw_data` can be any JSON shape, `any` is the correct type.
