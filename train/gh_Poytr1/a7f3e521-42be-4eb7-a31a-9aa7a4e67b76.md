Great question. There's a fundamental reason polling exists alongside webhooks — it's not redundant. **The core issue: you can't install webhooks on repos you don't own.** ReleaseBeacon's primary use case is monitoring *upstream dependencies* — `library/golang`, `nginx/nginx`, `hashicorp/vault`, etc. You don't have admin access to those repos, so you can't register a webhook on them. Polling their releases API is the only option. Webhooks only work for repos where you have admin/owner permissions — typically your own internal projects. So the two mechanisms serve different use cases: | Mechanism | Use case | Example | |-----------|----------|---------| | **Polling** | Third-party repos you don't own | Tracking `golang/go`, `docker-library/postgres` | | **Webhooks** | Repos you own or have admin access to | Your internal `myorg/token-compiler` | ### Other concerns with webhook-only Even for repos you *do* own, relying solely on webhooks has risks: 1. **Missed events** — If your server is down when GitHub sends the webhook, GitHub retries for a limited window (~3 days). Extended outages mean lost events. 2. **No backfill** — When you first add a repository to track, webhooks only fire for *future* releases. You need polling (or at least one API call) to discover existing releases. 3. **Webhook delivery is not guaranteed** — GitHub documents that webhook delivery is "best effort." The transactional outbox protects downstream, but the inbound side still has a gap. Polling acts as the safety net — it catches anything webhooks miss, and it's the only mechanism for the majority of tracked repos. ### What we could improve One thing worth noting: for GitHub specifically, there's a lighter alternative to REST API polling — **Atom feeds** (`https://github.com/{owner}/{repo}/releases.atom`).
