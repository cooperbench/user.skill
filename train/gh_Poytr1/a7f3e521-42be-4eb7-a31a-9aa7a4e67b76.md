## Architecture Overview

**ReleaseBeacon** (internal name: ReleaseGuard) is an **event-driven release management system** designed to centralize release discovery, automate validation, and distribute targeted notifications. It combines:

- **Go backend** for high-concurrency polling
- **PostgreSQL** for persistent storage, message brokering (River job queue), and pub/sub (LISTEN/NOTIFY)
- **Next.js frontend** for dashboard
- **Single binary deployment** via `go:embed`
- **LLM agents** for intelligent changelog analysis and autonomous validation

### Core Design Principles

1. **Transactional Outbox Pattern** - Release insert + River job enqueue within same SQL transaction (zero-loss)
2. **Idempotent Ingestion** - Unique constraint on `(repository, version)` prevents duplicates
3. **Decoupled Layers** - All components communicate exclusively through PostgreSQL, not synchronously
4. **Provider Interfaces** - Abstractions for pluggable sources and outputs

Now, before diving into endpoint details, I want to propose the **routing architecture** — how we structure the Go HTTP layer:

**Approach A: stdlib `net/http` + custom router (Recommended)**
- Use Go 1.22+ enhanced `http.ServeMux` with method-based routing (`GET /api/v1/releases`)
- Zero external dependencies — aligns with the project's minimal dependency approach
- Go 1.25 already in use, so the new `ServeMux` patterns are available
- Trade-off: slightly more boilerplate for middleware chaining

**Approach B: chi router**
- Lightweight, idiomatic Go router with middleware support
- Clean sub-routing (`r.Route("/api/v1", ...)`)
- Trade-off: adds a dependency, but it's battle-tested and small

**Approach C: Echo/Gin framework**
- Full framework with built-in middleware, validation, binding
- Trade-off: heavy for what we need, opinionated, large dependency surface

I recommend **Approach A** — Go 1.22+ `ServeMux` now supports `GET /path/{id}` patterns natively, which covers everything we need. It keeps the zero-framework philosophy and matches the project's existing style (pgx raw driver, no ORM, no framework).

## Section 3: SSE Real-Time Events

### Endpoint

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/v1/events` | SSE stream of real-time events |

Query params: `?topics=releases,pipeline` (optional filter — defaults to all topics)

### How It Works

```
PostgreSQL LISTEN/NOTIFY  →  Go listener goroutine  →  SSE broadcaster  →  connected clients
```

1. When a release is ingested (transactional outbox commits), a PostgreSQL trigger fires `NOTIFY release_events, '{release_id}'`
2. A Go goroutine holds a persistent `LISTEN release_events` connection
3. On notification, it fetches the full resource and broadcasts to all connected SSE clients
4. Clients filter by topic if specified

### Event Format

Standard SSE with JSON payloads:

```
event: release.created
data: {"id":"550e8400...","source":"dockerhub","repository":"library/golang","raw_version":"1.21.0","created_at":"2026-02-24T10:30:00Z"}

event: pipeline.status_changed
data: {"release_id":"550e8400...","status":"completed","node":"ai_urgency_scorer"}

event: source.error
data: {"source_id":1,"repository":"library/golang","error":"rate limited","timestamp":"2026-02-24T10:31:00Z"}
```

### Event Types

| Event | Triggered When |
|-------|---------------|
| `release.created` | New release ingested |
| `pipeline.status_changed` | Pipeline job transitions state |
| `pipeline.completed` | Pipeline finishes for a release |
| `pipeline.failed` | Pipeline job goes to dead-letter queue |
| `source.error` | Polling source encounters an error |
| `source.polled` | Successful poll completed |

## Section 4: Authentication & Middleware

### API Key Auth

Simple bearer token in the `Authorization` header:

```
Authorization: bearer [REDACTED]
```

- Keys are stored hashed (SHA-256) in a `api_keys` table
- Keys are prefixed with `rg_live_` (production) or `rg_test_` (development) for easy identification
- The `/api/v1/health` endpoint is public (no auth required) for load balancer health checks
- Webhook endpoints (`/webhook/github`) use their own auth (HMAC signatures), not API keys

### New DB Table

```sql
CREATE TABLE api_keys (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    key_hash VARCHAR(64) NOT NULL UNIQUE,
    key_prefix VARCHAR(12) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    last_used_at TIMESTAMPTZ
);
```

The raw key is only shown once at creation time — only the hash is stored.

### Middleware Stack

Applied in order to every `/api/v1/*` request:

1. **Request ID** — generates UUID, sets `X-Request-ID` header, injects into context
2. **Logger** — structured JSON logging with request ID, method, path, duration, status
3. **Recovery** — catches panics, returns 500 with request ID
4. **Auth** — validates API key, rejects with 401 if missing/invalid (skipped for `/api/v1/health`)
5. **CORS** — allows frontend origin, standard headers

All middleware uses the stdlib `func(http.Handler) http.Handler` pattern — no framework needed.

### Error Codes

| HTTP Status | Error Code | When |
|-------------|------------|------|
| 400 | `bad_request` | Invalid query params, malformed JSON |
| 401 | `unauthorized` | Missing or invalid API key |
| 404 | `not_found` | Resource doesn't exist |
| 409 | `conflict` | Duplicate subscription |
| 422 | `validation_error` | Valid JSON but invalid field values |
| 500 | `internal_error` | Unexpected server error |

## Section 5: Go Package Architecture

Here's how the API layer fits into the existing codebase:

### New Packages

```
internal/
  api/
    server.go          — HTTP server setup, route registration, graceful shutdown
    middleware.go       — Request ID, logger, recovery, auth, CORS
    auth.go            — API key validation, key store interface
    response.go        — Envelope helpers (JSON, Error, Paginated)
    releases.go        — GET /releases, GET /releases/{id}, GET /releases/{id}/pipeline
    subscriptions.go   — Full CRUD handlers
    sources.go         — Full CRUD handlers
    health.go          — Health check + stats
    events.go          — SSE broadcaster, LISTEN/NOTIFY integration
```

### Key Design Decisions

1. **Handler struct pattern** — Each resource gets a handler struct that holds its dependencies (store interfaces). Not global state, proper DI.

```go
type ReleasesHandler struct {
    store ReleasesStore
}

func (h *ReleasesHandler) List(w http.ResponseWriter, r *http.Request) { ... }
func (h *ReleasesHandler) Get(w http.ResponseWriter, r *http.Request)  { ... }
```

2. **Store interfaces per resource** — Each handler defines its own store interface (what it needs from the DB), implemented by a shared PostgreSQL layer. Keeps handlers testable.

3. **Route registration** — A single `RegisterRoutes(mux *http.ServeMux, deps Dependencies)` function wires everything. Called from `main.go`.

4. **SSE broadcaster** — A `Broadcaster` struct manages connected clients. The LISTEN/NOTIFY goroutine pushes events to it. Thread-safe via channels.

### Integration with main.go

```go
func main() {
    // ... existing DB pool, River client setup ...
    
    mux := http.NewServeMux()
    api.RegisterRoutes(mux, api.Dependencies{
        DB:          pool,
        RiverClient: riverClient,
    })
    
    // Webhook routes (outside /api/v1, separate auth)
    mux.Handle("POST /webhook/github", githubHandler)
    
    srv := &http.Server{Addr: ":8080", Handler: mux}
    // ... graceful shutdown ...
}
```

## Schema Bugs (things that are wrong right now)

### 1. `releases` table is missing the `source` column

The `ReleaseEvent` IR has a `source` field (`"dockerhub"`, `"github"`), but the DB schema doesn't store it as a column — it's buried in the JSONB `payload`. You can't efficiently filter or index releases by source.

```sql
-- Current (DESIGN.md line 72)

-- Missing: source VARCHAR(50) NOT NULL
-- Missing: UNIQUE(repository, version) constraint (mentioned in prose but not in schema)
```

The unique constraint is mentioned in Section 4 prose but isn't actually in the `CREATE TABLE` statement.

### 2. No `sources` table in the DB schema

The API design assumes a `sources` table exists (CRUD for configured ingestion sources), but DESIGN.md defines no such table. There's nowhere to persist what repositories to poll, at what interval, or whether they're enabled.

### 3. No `notification_channels` table

Subscriptions reference `notification_target` as a bare string (`"slack_channel_id"`), but there's no table to register the actual channels — Slack webhook URLs, PagerDuty routing keys, etc. The `INotificationChannel` interface exists architecturally but has no backing storage.

---

## Product Gaps (missing from the design)

### 4. No pipeline execution tracking

`pipeline_jobs` tracks job state (`available`, `running`, `completed`, `retry`) but has no visibility into **which DAG node** a job is at or what each node produced. When the dashboard shows pipeline status, there's nothing to query. Missing:
- Current node position
- Per-node results (e.g., urgency score from AI scorer, regex normalizer output)
- Node-level error messages
- Execution timestamps per node

### 5. No version exclusion / filtering config per source

newreleases.io allows `exclude_version_regexp`, `exclude_prereleases`, `exclude_updated` per project. Our pipeline handles filtering downstream (Subscription Router), but there's no way for users to configure exclusion rules per source. This means:
- You can't say "ignore all `-rc` tags for this Docker image"
- You can't exclude pre-releases at the source level (before they even enter the pipeline)

### 6. No notification frequency / digest control

newreleases.io supports per-project notification preferences: `none`, `instant`, `hourly`, `daily`, `weekly`. Our design sends everything immediately through the pipeline. There's no concept of batching low-priority notifications into a daily digest.

### 7. Subscriptions model is too thin

The current subscriptions table has three fields: `repository`, `channel_type`, `notification_target`. Missing:
- Notification frequency (instant vs digest)
- Version pattern filter (e.g., "only notify for major releases")
- Enabled/disabled toggle
- Created/updated timestamps

### 8. No system configuration table

There's no way to persist system-wide settings: default poll intervals, AI model preferences, notification defaults, rate limits. These are either hardcoded or don't exist.

Great question. There's a fundamental reason polling exists alongside webhooks — it's not redundant.

**The core issue: you can't install webhooks on repos you don't own.**

ReleaseBeacon's primary use case is monitoring *upstream dependencies* — `library/golang`, `nginx/nginx`, `hashicorp/vault`, etc. You don't have admin access to those repos, so you can't register a webhook on them. Polling their releases API is the only option.

Webhooks only work for repos where you have admin/owner permissions — typically your own internal projects.

So the two mechanisms serve different use cases:

| Mechanism | Use case | Example |
|-----------|----------|---------|
| **Polling** | Third-party repos you don't own | Tracking `golang/go`, `docker-library/postgres` |
| **Webhooks** | Repos you own or have admin access to | Your internal `myorg/token-compiler` |

### Other concerns with webhook-only

Even for repos you *do* own, relying solely on webhooks has risks:

1. **Missed events** — If your server is down when GitHub sends the webhook, GitHub retries for a limited window (~3 days). Extended outages mean lost events.
2. **No backfill** — When you first add a repository to track, webhooks only fire for *future* releases. You need polling (or at least one API call) to discover existing releases.
3. **Webhook delivery is not guaranteed** — GitHub documents that webhook delivery is "best effort." The transactional outbox protects downstream, but the inbound side still has a gap.

Polling acts as the safety net — it catches anything webhooks miss, and it's the only mechanism for the majority of tracked repos.

### What we could improve

One thing worth noting: for GitHub specifically, there's a lighter alternative to REST API polling — **Atom feeds** (`https://github.com/{owner}/{repo}/releases.atom`). These are public, don't count against API rate limits, and are cheaper to parse. Could be worth supporting as a third ingestion mode.

Good catch. Yes — there's a conceptual gap. Right now the architecture has:

- **`sources`** — *how* to ingest (poller config, intervals, exclusion filters)
- **`releases`** — *what* was ingested (individual versions)

But there's no **`projects`** table — the entity that represents a tracked software project as a whole. Currently, `repository` is just a bare string scattered across `sources`, `releases`, and `subscriptions` with no single source of truth.

This causes real problems:

1. **No single entity to attach metadata to** — display name, description, project URL, icon
2. **Orphaned references** — if you rename a repository string in `sources`, existing `releases` and `subscriptions` still reference the old string
3. **No way to link multiple sources to one project** — e.g., `golang/go` on GitHub (webhooks) AND `library/golang` on Docker Hub (polling) are the same project, but the system treats them as unrelated
4. **Subscriptions reference repositories by string** — should reference a project ID instead

The fix is a `projects` table that becomes the central entity, with `sources`, `releases`, and `subscriptions` all referencing it by FK.

   154→## 4. Error Handling & Idempotency
   155→
   156→* **Idempotent Ingestion:** The `releases` table enforces a `UNIQUE(repository, version)` constraint. If a polling worker and a webhook both report the same release simultaneously, the database rejects the duplicate, preventing duplicate pipeline jobs.
   157→* **Source-Level Filtering:** Before events enter the pipeline, the ingestion layer applies source-level exclusion rules (`exclude_version_regexp`, `exclude_prereleases`). Filtered releases are never inserted, reducing pipeline load.
   158→* **Dead-Letter Queue (DLQ):** If a DAG pipeline job fails `max_attempts` (e.g., the LLM API is down), the `pipeline_jobs` state is updated to `discarded` and `error_message` captures the failure reason.    159→* **Pipeline Observability:** Each pipeline job tracks its `current_node` and accumulates `node_results` as it progresses through the DAG. If a job fails mid-pipeline, the exact failure point and partial results are preserved for debugging.
   160→* **Agent Fallback:** If the SRE Agent sandbox deployment fails due to infrastructure timeout (unrelated to the software release itself), the agent safely aborts the validation phase, flags the release event as "Unverified," and routes it to a human reviewer rather than dropping the notification.

    53→Components do not call each other synchronously. Instead, they rely on PostgreSQL to guarantee delivery:
