## The Bug: `id` Always Reads `"0"` from Static Page Props

### What happens at build time

In `next.config.ts`, production uses `output: "export"` — a fully static export. Next.js calls `generateStaticParams()` in each dynamic route page and pre-renders exactly the files it returns.

```typescript
// web/app/projects/[id]/page.tsx
export async function generateStaticParams() {
  return [{ id: "0" }]; // only ONE file is generated
}
```

This produces a **single file** at build time: `out/projects/0.html`.

### What happens at request time

The Go server receives a request for `/projects/some-uuid`. Because this is a static export with no server-side rendering, the Go binary serves the only file that exists for that route: `projects/0.html`.

### How the page gets its `id`

```typescript
// web/app/projects/[id]/page.tsx
export default async function ProjectDetailPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;  // <-- reads from static page props, NOT the URL
  return <ProjectDetail id={id} />;
}
```

In a static export, `params` is **baked-in at build time**. When the browser loads `/projects/some-uuid`, it is actually loading `projects/0.html`, and the `params` object embedded in that HTML snapshot has `id = "0"`. The page receives `"0"` as its `id` prop — never `"some-uuid"`.

### What `ProjectDetail` does with that `"0"`

```typescript
// web/components/projects/project-detail.tsx  line 85
const { data, isLoading, mutate: mutateProject } = useSWR(`project-${id}`, () => projectsApi.get(id));
// ...
const project = data?.data;
if (!project) {
  return <div>Project not found</div>;  // <-- this fires because API GET /projects/0 returns 404
}
```

The SWR call fires `GET /api/projects/0`. No project with id `"0"` exists, so the API returns a 404, `data` is undefined/null, and the component renders **"Project not found"**.

### The same problem exists for releases

`web/app/releases/[id]/page.tsx` and `web/components/releases/release-detail.tsx` have the identical pattern — static params `[{ id: "0" }]`, single HTML file, `id` prop always `"0"`, API call for release `"0"` fails, renders **"Release not found"**.

### The fix

The client components need to read the real UUID from the **browser URL** at runtime, not from the static page `params`. The correct approach is to use the `useParams()` hook from `next/navigation` inside the `"use client"` components:

// Inside ProjectDetail / ReleaseDetail (already "use client")
import { useParams } from "next/navigation";

export function ProjectDetail() {  // drop the id prop
  const { id } = useParams<{ id: string }>();
  // now id is "some-uuid" taken from the real browser URL
  ...
}
```

**Root cause confirmed.** The RSC payload contains:

```
"c":["","projects","0"]
```
and
```
["id","0","d"]
```

This is the Next.js router tree baked at build time. When the browser loads this HTML at URL `/projects/some-uuid`, Next.js hydrates with the **baked** route segments `["projects", "0"]`, not the actual URL. So `useParams()` returns `{ id: "0" }` — it reads from the RSC data, not `window.location`.

**The fix:** `useParams()` won't work in this static export scenario. The components need to parse the ID directly from `window.location.pathname`.
