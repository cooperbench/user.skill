# Image Request Workflow - Implementation Plan

## Context

End users (developers, platform teams) currently need to manually edit `images.yaml` and submit PRs to request new images. This creates friction — not everyone is comfortable editing YAML or knows the schema. A self-service `workflow_dispatch` workflow lets users fill in a form in the GitHub Actions UI, which automatically modifies `images.yaml`, creates a branch, and opens a PR for review.

## Files to Create/Modify

### 1. NEW: `.github/workflows/request-image.yml`

A `workflow_dispatch` workflow with form inputs:

**Inputs:**
- `registry` — choice: `dockerhub`, `ghcr`, `quay`, `custom` (required)
- `image_name` — upstream image path, e.g. `nginx` or `bitnami/redis` (required)
- `tag` — explicit version pin, e.g. `1.25-alpine` (required)
- `target_name` — name in AR, defaults to last path segment (optional)
- `description` — what this image is for (optional)
- `custom_host` — registry host, only for custom registries (optional)
- `auth_required` — whether source registry needs credentials (boolean, default false)
- `justification` — why this image is needed, included in PR body (required)

**Steps:**
1. Checkout `main`
2. Install `ruamel.yaml` (preserves YAML comments and formatting)
3. Run `scripts/add-image.py` with the input parameters to modify `images.yaml`
4. Run `scripts/validate-manifest.py` to verify the result is valid
5. Create branch `image-request/<target_name>-<tag>`
6. Commit the change
7. Create PR via `gh pr create` with structured body including justification, image details, and the requester

**Permissions:** `contents: write`, `pull-requests: write`

### 2. NEW: `scripts/add-image.py`

Python script that programmatically adds an image entry to `images.yaml`.

**Behavior:**
- Uses `ruamel.yaml` to preserve comments and formatting

- Finds existing source group matching the registry (and host for custom), or creates a new source group
- Checks for duplicates (same target_name:tag already exists) — exits with error if so
- Appends the new image entry to the matching source group's images list

**Step 3: Parse issue body**

This is the new core logic. The issue body rendered by GitHub Issue Forms has this structure:

```
### Registry

dockerhub

### Image Name

bitnami/redis

### Tag

7.2.4

### Description

Redis cache for session storage

### Custom Registry Host

_No response_

### Authentication Required

### Justification

```

The parsing approach uses `awk` in bash -- no external dependencies. Each field value sits between its heading and the next heading (or end of body). The value `_No response_` means the user left an optional field blank.

```yaml
- name: Parse issue form fields
  id: parse
  env:
    ISSUE_BODY: ${{ github.event.issue.body }}
  run: |
    set -euo pipefail

    # Extract value between a given heading and the next heading (or EOF)
    extract_field() {
      local field_name="$1"
      echo "$ISSUE_BODY" | awk -v field="### $field_name" '
        $0 == field { found=1; next }
        found && /^### / { exit }
        found { print }
      ' | sed '/^$/d' | sed 's/^[[:space:]]*//;s/[[:space:]]*$//'
    }

    REGISTRY=$(extract_field "Registry")
    IMAGE_NAME=$(extract_field "Image Name")
    TAG=$(extract_field "Tag")
    DESCRIPTION=$(extract_field "Description")
    CUSTOM_HOST=$(extract_field "Custom Registry Host")
    AUTH_REQUIRED=$(extract_field "Authentication Required")
    JUSTIFICATION=$(extract_field "Justification")

    # Normalize _No response_ to empty
    [ "$DESCRIPTION" = "_No response_" ] && DESCRIPTION=""
    [ "$CUSTOM_HOST" = "_No response_" ] && CUSTOM_HOST=""
    [ "$JUSTIFICATION" = "_No response_" ] && JUSTIFICATION=""

    # Parse checkbox: "- [X]" means true, "- [ ]" means false
    if echo "$AUTH_REQUIRED" | grep -qi '\[x\]'; then
      AUTH_REQUIRED="true"
    else
      AUTH_REQUIRED="false"
    fi

    # Validate required fields are present
    if [ -z "$REGISTRY" ] || [ -z "$IMAGE_NAME" ] || [ -z "$TAG" ]; then
      echo "::error::Missing required fields: registry='$REGISTRY', image_name='$IMAGE_NAME', tag='$TAG'"
      exit 1
    fi

    # Export to outputs
    {
      echo "registry=$REGISTRY"
      echo "image_name=$IMAGE_NAME"
      echo "tag=$TAG"
      echo "description=$DESCRIPTION"
      echo "custom_host=$CUSTOM_HOST"
      echo "auth_required=$AUTH_REQUIRED"
      echo "justification=$JUSTIFICATION"
    } >> "$GITHUB_OUTPUT"
```

**Why bash parsing instead of `stefanbuck/github-issue-parser`:** The requirements explicitly recommend bash parsing to avoid external dependencies. The `awk`/`sed` approach is deterministic for the GitHub Issue Forms markdown format. The Issue Forms spec guarantees the heading format `### <label>`, so this is reliable.

**Why not a Python script for parsing:** A Python script would be equally valid but adds a file to maintain. The bash approach keeps the logic inline and visible in the workflow. If the parsing grows more complex in the future, extracting to a `scripts/parse-issue-body.py` would be warranted.

### Security Considerations

1. **Input sanitization:** The `${{ github.event.issue.body }}` is passed via the `ISSUE_BODY` environment variable, not interpolated directly into a `run:` block. This is critical -- direct interpolation of issue body content into `run:` creates a script injection vulnerability. The current design correctly uses `env:` to pass the body, which prevents injection.

2. **Branch name sanitization:** The branch name includes user-supplied `image_name` and `tag` values (via the derived target name). These come from the issue form and could theoretically contain special characters. The `add-image.py` script validates the inputs, and the git branch name creation would fail on invalid characters, which is an acceptable safeguard. For extra safety, the branch name could be sanitized with `tr -cd 'a-zA-Z0-9._-/'`.

3. **Permissions scope:** The workflow needs `contents: write` (to push branches) and `issues: write` (to comment). These are appropriately scoped -- no broader permissions are needed.

The issue number in the branch name (`image-request/42-redis-7.2.4` vs `image-request/43-redis-7.2.4`) prevents branch name collisions.
