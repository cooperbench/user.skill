but how will a release of the cli now trigger an update in devcontainer-feature repo?

> AGENT

Good question. Right now there's no link between the two repos. You have a few options: **Option A: Repository dispatch from CLI release** Add a step to the CLI's release workflow that sends a `repository_dispatch` event to the devcontainer-features repo, then update `release.yml` in devcontainer-features to trigger on that event. This way every CLI release auto-publishes a new feature version. **Option B: Workflow dispatch (manual trigger)** Add `workflow_dispatch` to the devcontainer-features release workflow so you can trigger it manually or from the CLI repo. **Option C: Don't — it doesn't need to** The devcontainer feature's `install.sh` resolves `latest` at install time by hitting the GitHub Releases API. The feature itself doesn't bundle the binary — it downloads it fresh. So a new CLI release is automatically picked up by anyone installing the feature, without republishing the feature. You'd only need to republish the feature if you change the feature metadata (options, description) or the install script itself. --- Option C is the simplest and is how most devcontainer features work (e.g., `devcontainers/features` does the same pattern). Option A is worth adding if you want the feature version to track the CLI version for auditability. Which approach do you want?
