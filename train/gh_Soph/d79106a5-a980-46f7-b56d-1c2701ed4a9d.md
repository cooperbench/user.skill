OK here's my thinking on the three issues:

### 1. SSH vs HTTPS auth — the setting URL should support both

Currently the setting stores a raw URL string (`checkpoint_remote: "git@github.com:org/repo.git"` or `https://github.com/org/repo.git"`). This already works since `ensureGitRemote` just passes it through to `git remote add/set-url`, and git handles both protocols natively.

The real question is: **should the setting store a full URL at all, or just an org/repo identifier?** If you store `"org/checkpoints-repo"`, you could derive the URL at push-time by looking at the *existing* origin remote's URL format — if origin uses `git@github.com:`, generate SSH; if it uses `https://github.com/`, generate HTTPS. This means the user doesn't need to care about the protocol and it automatically matches whatever auth they have set up.

### 2. Known remote name + detecting user changes

Current code uses `entire-checkpoints` as the remote name and silently overwrites the URL if it differs (the exact thing pjbgf flagged). A better approach:

- **Create-only, never overwrite.** If the `entire-checkpoints` remote already exists and the URL differs from the setting, that means someone deliberately changed it. Respect that — warn and use whatever URL is already on the remote.
- **But there's a bootstrap problem**: when the setting changes (user updates `checkpoint_remote` in settings.json), the remote URL should update too. You could handle this by: only treating it as "user changed" if the existing URL doesn't match *any* known variant of the configured value (e.g., SSH vs HTTPS form of the same repo). If the existing URL is a completely different repo, warn and don't touch it.

Alternatively — since you own the remote name `entire-checkpoints`, you could store the "last configured URL" somewhere (e.g., git config `entire.checkpointRemoteConfigured`) and compare: if the current URL differs from both the setting *and* the last-configured value, it was manually changed. If it only differs from the setting but matches last-configured, the setting was updated and the remote should be updated.

### 3. Forks

This is the trickiest one. If someone forks a repo that has `checkpoint_remote` in `.entire/settings.json`, they'll get a URL pointing to the *upstream's* checkpoint repo, which they almost certainly can't push to.

Options:
- **Don't commit `checkpoint_remote` to `.entire/settings.json`** — put it in `.entire/settings.local.json` instead (which is gitignored). Then forks never inherit it. The `--checkpoint-remote` flag would write to local settings.
- **Detect fork situation** at push-time: compare origin's URL to the checkpoint remote URL. If they point to different GitHub orgs/owners, skip with a warning like "checkpoint remote appears to be for a different org, skipping".
- **Use org/repo format instead of full URL** (ties back to point 1): if you store just `"org/checkpoints-repo"` and derive the URL from origin's format, forks would naturally fail validation since their origin points to `fork-owner/repo` not `org/repo` — you could detect this and skip.

1. Protocol matches whatever auth the user has
2. The remote name `entire-checkpoints` is fully owned by you; store last-known config to detect manual changes
3. Forks: compare the origin owner to the checkpoint repo owner — if they differ, skip with a message

### Settings structure

      "repo": "org/checkpoints-repo"

Extensible — future providers (`"gitlab"`, `"bitbucket"`, a self-hosted Entire backend, etc.) slot in by adding a new provider value. The `repo` field is always `owner/name`.

### URL derivation at runtime

Instead of storing a URL, derive it from origin's protocol:

1. Read origin's URL (`git remote get-url origin`)
2. Parse protocol:
   - `git@github.com:...` → SSH → `git@github.com:{repo}.git`
   - `https://github.com/...` → HTTPS → `https://github.com/{repo}.git`
3. This automatically matches whatever auth the user already has working

### Fork detection

Before creating/using the remote:

1. Parse origin URL → extract owner (e.g. `fork-user` from `git@github.com:fork-user/original-repo.git`)
2. Compare to checkpoint_remote repo owner (`org` from `org/checkpoints-repo`)
3. If they differ → skip silently (or with a debug log). The fork can't push to the upstream checkpoint repo anyway.

### Remote management rules

`entire-checkpoints` is **our** remote — we own it, users shouldn't touch it:

- **Doesn't exist** → create it with the derived URL
- **Exists, URL matches** → use it
- **Exists, URL differs** → update it (setting changed, or user switched SSH↔HTTPS on origin). It's our remote.

But before pushing, check: if `entire/checkpoints/v1` is already being pushed to a remote that's **neither the default nor `entire-checkpoints`** — someone set up a custom remote for this branch manually. Don't override that. In practice this means: in `resolvePushSettings`, if the branch has an explicit push remote configured in git config that isn't origin or `entire-checkpoints`, respect it and skip the checkpoint_remote logic.

User switches origin from SSH to HTTPS (or vice versa). Next push: we re-derive the checkpoint URL from origin, see it differs from what `entire-checkpoints` currently has, update it. Seamless.
