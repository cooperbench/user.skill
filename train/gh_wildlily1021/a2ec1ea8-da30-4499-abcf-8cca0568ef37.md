## 讨论一：构帧管线完整流程

### 选项分析

**Pipeline 需要覆盖的步骤**：

```
SendRequest(frameId, userFieldValues?, variables?, targetId?)
  │
  ├─ 1. validate request（frameId 存在、字段可配置性检查）
  │
  ├─ 2. resolve frame（FrameAssetReader.getFrame → ReadonlyFrameAsset）
  │
  ├─ 3. resolve field values（逐字段）
  │     ├─ 3a. 用户提供了值 → 直接用
  │     ├─ 3b. 字段有 expressionConfig → 表达式求值
  │     ├─ 3c. 字段有 defaultValue → 用默认
  │     └─ 3d. 都没有 → zero fill + warning
  │
  ├─ 4. apply factor inverse（rawValue = physicalValue / factor）
  │
  ├─ 5. build byte buffer（按 dataType + length + endianness 编码）
  │
  ├─ 6. auto checksum（如果 autoChecksum 且有 validOption）
  │
  ├─ 7. auto length field（如果 includeLengthField）
  │
  ├─ 8. resolve target（targetResolver adapter）
  │
  ├─ 9. transport write（transportWriter adapter）
  │
  └─ 10. emit result + update stats
```

### 关键设计决策

**D1: 字段值解析优先级**

```
用户输入 > 表达式求值 > defaultValue > zero fill
```

理由：
- 用户手动填的值是最高优先级（configurable 字段）
- expressionConfig 是帧定义声明的自动计算逻辑
- defaultValue 是静态 fallback
- zero fill 是最后兜底（encode.ts 已实现，带 warning）

**D2: Factor 逆换算位置**

factor 必须在"值解析完成之后、字节编码之前"执行。新系统 factor 语义（与 frame-real 对齐）：

- **接收方向**：`物理值 = 原始值 * factor`
- **发送方向（逆换算）**：`原始值 = 物理值 / factor`

旧系统是 `value * factor`，但旧 factor 定义方向与新系统相反。新 send 必须用 `/`，不是 `*`。

⚠️ **需要验证**：frame-real 实现中 factor 的实际存储方向是否与 design 一致。如果 frame JSON 迁移时 factor 沿用旧值（`10` 而不是 `0.1`），则发送时仍应是 `*`。这是一个必须通过读代码确认的事实，不能猜。

**D3: autoChecksum 策略**

frame-real 定义了 `checksumMethod: sum8 | xor8 | crc16 | crc32 | custom`，checksum 字段通过 `validOption.startFieldIndex/endIndex` 指定计算范围。

当前 send `core/checksum.ts` 已存在。需确认：
- 4 种算法是否全部覆盖
- custom 算法如何处理（是否本期支持）
- checksum 字段本身在 buildFrame 时先 zero fill，checksum 计算后回填

**D4: includeLengthField 策略**

部分帧协议要求包含"帧总长度"字段。需要：
- buildFrame 先构造完整 buffer
- 找到 length 字段位置
- 回填总长度值

这是一个 post-build 回填步骤，类似 checksum。

### 本点结论

管线 10 步是完整闭环。步骤 3（值解析）是核心复杂度所在，需要表达式引擎集成。步骤 4（factor）和步骤 6/7（checksum/length 回填）是后处理步骤，逻辑简单但必须严格按序。

## 讨论二：Target 解析策略

### 事实

旧系统 targetId 格式：`serial:path` 或 `network:connectionId[:remoteHost]`

新架构约束：
- connection feature owns 连接生命周期
- send 通过 adapter 访问传输能力
- send 不直接管理串口/网络连接

### 当前设计

`send-service.ts` 已有依赖注入模式：

```typescript
targetResolver: (targetId: string) => TargetResolution
transportWriter: (target: TargetResolution, buffer: Uint8Array) => Promise<void>
```

这是干净的。send/core 不碰 platform，adapter 实现由外部注入。

### 方案

**采用 adapter 注入，send 不碰具体传输协议**：

1. `targetResolver`：接收 targetId，返回 `TargetResolution`
   - `{ type: 'serial', path: string }`
   - `{ type: 'tcp', connectionId: string }`
   - `{ type: 'udp', connectionId: string, remoteHost?: string, remotePort?: number }`
2. `transportWriter`：接收 TargetResolution + buffer，执行实际写入
3. targetId 格式和解析规则由 connection feature 定义，send 只消费

### 待确认

- targetId 格式是否由 connection feature 统一定义，还是 send 自己定义格式？
- SendRequest 中 targetId 是否必填？如果帧定义中有默认 target，是否自动填充？

**建议**：targetId 格式由 connection feature 定义（它是连接的 owner），send 只消费。SendRequest.targetId 必填，由调用方（task/runtime/page）负责提供。

## 讨论三：表达式求值集成方式

### 这是 send-real 最核心的设计决策

### 选项

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A: 调用方求值 | Task/runtime/page 在调用 send 前，用表达式引擎求值，把 resolved fieldValues 传给 send | Send 最简单，无跨 feature 数据依赖 | 每个调用方重复实现；frame expressionConfig 未被 send 消费；frame 定义声明的自动计算逻辑散落在各调用方 |
| B: Send 内部求值 | Send service 读取 frame expressionConfig，注入 VariableProvider，内部执行 compileGroup + evaluateGroup | 逻辑集中，frame 定义的自然延伸，可测试 | Send 需要 VariableProvider adapter；复杂度增加 |
| C: 混合 | 用户输入的 configurable 字段由调用方提供；expressionConfig 字段由 send 内部求值 | 最灵活，两个来源都支持 | 需要明确优先级规则；最复杂 |

### 分析

**选方案 C（混合），理由**：

1. Frame 定义已经声明了 `expressionConfig`，这是帧 schema 的一部分。Send 作为构帧管线，自然应该消费这个字段。
2. 有些字段是用户手填的（configurable = true），有些是自动计算的（expressionConfig 存在），两者共存是常态。
3. 调用方不需要理解 frame 内部的表达式依赖关系——这是 send 管线的能力。
4. 通过 adapter 注入 VariableProvider，send/core 保持纯函数可测试。

**具体集成方式**：

```typescript
// send-service 新增 adapter
interface SendVariableProvider {
  getVariables(): VariableMap;
}

// SendRequest 扩展
interface SendRequest {
  frameId: string;
  userFieldValues?: Record<string, number>;  // 用户填的 configurable 字段
  variables?: VariableMap;                    // 可选：调用方预提供的变量
  targetId: string;
}

// send service pipeline step 3 (resolve field values):
// 对每个字段：
//   if userFieldValues[field.id] exists → 使用用户值
//   else if field.expressionConfig → compileGroup + evaluateGroup
//   else if field.defaultValue → 使用默认值
//   else → zero fill + warning
```

**变量来源处理**：

| 变量类型 | 来源 | 提供方 |
|---|---|---|
| 遥测当前值 | receive feature read model | VariableProvider adapter（运行时从 receive selector 获取） |
| 全局参数 | 全局参数 store | VariableProvider adapter |
| 同帧其他字段 | 已解析的前序字段 | send 内部（evaluateGroup 依赖排序自动处理） |
| 任务上下文 | task runtime | 调用方通过 `variables` 参数注入 |

**关键约束**：send/core 只接收 `VariableMap`（纯数据），不直接依赖 receive/task/global 的 store 或 selector。adapter 在服务创建时注入，core 层零耦合。

### 待确认

- VariableProvider 的生命周期：每次 send 调用时获取最新值？还是 snapshot？
- 是否需要 `getRequiredVariables(frameId)` helper 供调用方提前知道需要哪些变量？

**建议**：每次 execute 调用时获取最新值（通过 adapter 调用 selector）。`getRequiredVariables` 是好的工具函数，但不阻塞本期。

## Brainstorm 结论

### 1. 要做什么（构帧管线核心行为）

Send-real 实现完整的单帧发送管线：

**SendRequest → validate → resolve frame → resolve field values（用户输入 / 表达式求值 / 默认值 / zero fill）→ factor 逆换算 → build byte buffer → auto checksum → auto length → resolve target → transport write → emit SendResult**

核心新增能力（相对已有骨架）：
- 表达式求值集成（compileGroup + evaluateGroup + VariableProvider adapter）
- Factor 逆换算
- Auto checksum（基于 validOption 范围 + checksumMethod）
- Auto length field
- defaultValue / configurable / options 字段消费
- direction 过滤

### 2. 不做什么

- 不做帧实例管理、SCOE 语义、northbound、报告、调度、UI、连接管理、变量存储、custom checksum、重试策略、发送队列

### D2 Factor 方向 — 发现矛盾，需要深挖

代码证据出现分歧：

| **旧代码** (dataProcessor.ts:121) | `value * factor` | `value * factor` |
| **frame-real design** | `物理值 = 原始值 * factor` | `原始值 = 物理值 / factor` |

**双向都用乘法在数学上不可能对同一 factor 值成立**（除非 factor ≡ 1）。可能的解释：

帧是 **单向的**（`direction: 'send' | 'receive'`）。旧系统中同一个协议的收帧和发帧是**不同的 FrameAsset**，各自存了不同方向的 factor 值。比如温度字段：
- 收帧 factor = 0.01（raw 255 → 物理 2.55）
- 发帧 factor = 100（物理 2.55 → raw 255）
- 两边都做乘法，但 factor 值不同

**新系统设计文档的约定更优雅**：统一存一个方向的 factor，发送用除法。但这意味着 legacy migration 时，**发送帧的 factor 可能需要取倒数**，而不是原样保留。

这个必须现在验证。我派一个 agent 去查实际帧 JSON 数据。

> AGENT

关键发现：**发送帧 factor 全部为 1**。

这彻底解决了 D2 矛盾：

| 方向 | factor 值 | 操作 | 效果 |
|---|---|---|---|
| 接收帧 | 100, 0.390625, 0.000001 等 | `raw * factor = 物理` | 实际转换 |
| 发送帧 | **全部为 1** | `value * 1 = value` | 无转换 |

旧系统双向都做乘法，实际上发送帧没有转换需求。frame-real design 的约定（发送用 `/`）在 factor=1 时等价于无操作，所以完全兼容。Legacy migration 原样保留是正确的。

### 一、构帧管线完整流程（已确认）

```
SendRequest { frameId, userFieldValues?, variables?, targetId }
  │
  ├─ 1. validate（frameId 存在、targetId 非空）
  │
  ├─ 2. resolve frame（FrameAssetReader.getFrame，direction='send'）
  │
  ├─ 3. resolve field values（逐字段，优先级）
  │     ├─ 3a. userFieldValues[field.id] 存在 → 使用用户值
  │     ├─ 3b. field.expressionConfig 存在 → compileGroup + evaluateGroup
  │     ├─ 3c. field.defaultValue 存在 → 使用默认值
  │     └─ 3d. 以上都没有 → zero fill + warning（已有实现）
  │
  ├─ 4. apply factor（rawValue = value / factor，当前数据全部 factor=1）
  │
  ├─ 5. build byte buffer（已有 encode.ts，按 dataType+length+endianness）
  │
  ├─ 6. auto checksum（新增：按 validOption 范围 + checksumMethod）
  │
  ├─ 7. auto length field（新增：按 includeLengthField 回填）
  │
  ├─ 8. resolve target（已有 adapter：targetId → TransportTargetSnapshot → connectionId）
  │
  ├─ 9. enqueue / transport write（新增轻量 FIFO + 已有 adapter）

  └─ 10. emit SendResult + update stats（已有实现）
```
