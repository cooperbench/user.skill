### F2：旧系统事实

- `receiveFramesStore` 1387 行 + `dataDisplayStore` 1074 行，跨 store 耦合
- SCOE 硬编码在通用接收流程（`sourceId === 'scoe-tcp-server'` 硬判断）

### F3：架构约束

- receive 不拥有存储逻辑、可视化逻辑、条件触发行为

- 高速存储命中后可短路普通 receive/display/trigger 链（边界例外）

## 关键设计决策点

### D1：表达式求值在管线中的位置

**问题**：表达式求值是在字段解析阶段（field-parser 内）还是独立阶段？

**选项**：

- **A：field-parser 内完成**（当前 brainstorm 建议）
  - `parsePrimitive` 里读 `field.expressionConfig`，有表达式则 `compileConditional + evaluateConditional`
  - 优点：简单，3 行代码集成
  - 缺点：field-parser 需要知道遥测维持参数和全局参数（`VariableMap` 输入扩大）

- **B：独立表达式求值阶段**（processor 后）
  - field-parser 只做 raw 解析 + factor
  - processor 增加表达式求值 pass：收集同帧依赖 → 排序 → 批量求值
  - 优点：关注点分离，field-parser 不需要外部变量
  - 缺点：多一个阶段，field 值有中间态（raw vs resolved）

**倾向**：**B**，理由是表达式变量来源包含跨帧数据（遥测维持参数），这不是 field-parser 该知道的。但需要确认帧内字段间依赖排序的需求量级。

**不确定**：真实场景中帧内字段间表达式依赖有多频繁？如果很少，A 的简单性可能更优。

### D2：遥测维持参数的 owner

**问题**：跨帧参数当前值（旧系统 `frameDataCache`）由谁持有？

**选项**：

- **A：receive read model 持有**
  - receive 维护 `Map<frameId, Map<fieldId, latestValue>>`
  - 表达式求值时从中读取
  - 优点：receive 管线内部闭环
  - 缺点：receive 承担了"参数当前值"的语义

- **B：独立 parameter-current-value store**
  - 作为 receive 输出的消费结果，由独立模块维护
  - receive 只输出解析结果，不维护跨帧状态
  - 优点：receive 无状态化
  - 缺点：表达式求值需要等独立模块更新后才能取到跨帧值

**倾向**：**A**。receive 输出的参数事实天然需要维护"当前值"语义，这跟旧系统 `frameDataCache` 一致。关键是要把它作为 read model（只读快照）暴露给外部消费。

### D3：扇出分发模型

**问题**：5 个目的地如何分发？

| # | 目的地 | 频率 | 数据形态 | 已有接线 |
|---|---|---|---|---|
| 1 | Read Model（参数当前值） | 每帧 | field latest value | receive-state 部分有 |
| 2 | 可视化 | 节流后 | table/chart/constellation 各异 | 无 |
| 3 | 存储（持久化） | 可配 | field value + timestamp | 无 |
| 4 | 条件匹配 → 触发 | 每帧 | ConditionMatchInput | bridge 已接 task |
| 5 | 未匹配记录 | 每帧 | raw bytes + metadata | 无 |

**选项**：

- **A：同步管道，依次调用**
  - processor 完成后，同步调用各分发目标
  - 优点：简单，结果立即可见
  - 缺点：高频时阻塞

- **B：产出事件，由 runtime/bridge 分发**
  - receive 只产出 `ReceiveBatchOutcome`（已有），runtime 层 bridge 分发到各 feature
  - 优点：receive 不感知消费者，解耦
  - 缺点：runtime 层复杂度增加

**倾向**：**B**。receive 只产出明确结果，分发归 runtime。当前 `routingTick` 已经是 runtime 层，只需要扩展 bridge 接线。

### D4：背压策略

**问题**：高速数据场景下如何控制？

**事实**：
- `routingTick` 是同步 drain 模型
- 一个 tick 可能积了几百个 batch
- receive 解析同步阻塞

**策略**：

1. **main 侧**：批处理缓冲、队列背压（已有 connection feature 负责）
2. **routingTick 侧**：按预算截断（每 tick 最多处理 N 个 batch，剩余留给下一 tick）
3. **receive 侧**：无状态解析，单次 ingest 是纯函数，天然可中断
4. **可视化侧**：节流 + 增量合并（不属于 receive，但 receive 需要提供节流友好接口）
5. **星座图特殊**：I/Q 采样点可能需要独立数据通道，不走普通参数扇出

**不确定**：预算截断的 N 值应该是多少？需要真实数据率基准。

### D5：星座图数据通道

**问题**：I/Q 采样点是走普通参数扇出还是独立通道？

**事实**：
- 一个帧可能带几十到几百个 I/Q 采样点
- 高频帧一秒几十帧
- 旧系统用 `collectConstellationFieldData` 独立收集，`iValues/qValues` 持续累积

**选项**：

- **A：普通参数扇出 + 可视化侧节流**
  - I/Q 字段跟普通参数一样走扇出
  - visualization 负责节流和采样
  - 优点：receive 不感知星座图
  - 缺点：数据量大，扇出通道压力大

- **B：receive 标记高速字段，走独立分发通道**
  - receive 识别 I/Q 类型字段，产出独立的高速数据事件
  - 可视化直接消费高速通道
  - 优点：普通扇出不受影响
  - 缺点：receive 需要感知数据类型

**倾向**：**待定**。需要确认 frame-real 中 I/Q 字段是否有类型标记（如 `dataType: 'iq-samples'`）。如果有，B 方案可行且干净；如果没有，需要 frame-real 先支持。

## 要做什么

### 核心管线（receive feature 边界内）

```
字节流输入
  → 批次承接（ReceiveInputBatch，已有）
  → 帧匹配（frame-matcher，已有，消费 frame feature 的 identifierRules）
  → 字段原始解析（field-parser，已有，dataType + factor）
  → 表达式求值（新增，消费 shared/expression + 遥测维持参数 + 全局参数）
  → 产出 ReceiveBatchOutcome（扩展：含表达式结果）
```

### 扇出分发（runtime 层，不在 receive 内部）

```
ReceiveBatchOutcome
  ├→ 更新 receive read model（参数当前值）
  ├→ emit 到 visualization bridge（节流）
  ├→ emit 到 storage bridge
  ├→ emit 到 condition-match bridge（已有 receiveEventSourceBridge）
  └→ 记录未匹配帧
```

### 背压（跨层协作）

- main 侧缓冲（connection feature）
- routingTick 按预算截断
- receive 无状态解析
- 可视化独立节流

| 不做 | 理由 |
|---|---|
| receive 不自建帧列表 | 帧定义全局唯一，归 frame feature |
| receive 不拥有可视化逻辑 | 归 visualization feature |
| receive 不拥有存储逻辑 | 归 storage feature |

| receive 不做业务运算 | 表达式求值委托 shared/expression 纯函数 |
| receive 不直接写历史/报告 | 归 storage / result feature |

## 调查结果汇总

### I/Q 星座图：不是 receive 的事

- frame-real 没有 I/Q 专用 dataType，只用 `bytes`
- 旧系统星座图字段：480 bytes，12-bit 位宽，I/Q 混存在同一字段（前半 I 后半 Q）
- `bitWidth`、`sampleCount`、`iDataSource`/`qDataSource` 全是运行时 UI 配置，不在帧定义里
- **结论：receive 只管按 `bytes` 解析出 hex 字符串，I/Q 提取和星座图绘制全归 display/visualization。D5 不需要在 receive 内建特殊通道。**

### 表达式依赖：帧内依赖是真实需求，有拓扑排序

旧系统已有完整机制：
- 4 种变量来源：`CURRENT_FIELD`（同帧其他字段）、`FRAME_FIELD`（跨帧）、`GLOBAL_STAT`（全局统计）、`SCOE_DATA`
- `analyzeDependencies()` → `topologicalSort()`（Kahn 算法）→ 按序计算，计算后立即更新 context 供后续字段使用
- 跨帧通过 `allFrameData: Map<frameId, Map<fieldId, value>>` 传入

新系统 shared/expression 引擎已在编译阶段做依赖排序（D5 决策），所以：
- `refreshFrameReferences()` 时预编译 → `Map<frameId, CompiledGroup>`
- 运行时只需 `evaluateGroup(compiledGroup, variableMap)` 一调用

**D1 结论：选 B（独立阶段）。field-parser 只做 raw 解析 + factor，表达式求值是独立 pass。理由：表达式需要跨帧参数（read model）和全局参数，field-parser 不该知道这些。**

### 全局参数：旧系统有，新系统来源待定

- 旧系统 `GLOBAL_STAT`：运行时间、通信统计等
- 新系统 `shared/expression` 的 `VariableMap` 是扁平 Map，不感知命名空间
- receive 只需接收一个 `globalParams: VariableMap` 输入，实际来源（settings? runtime?）**留空给后续**

### 消费者接口：display 和 storage 都已有 public API

| 目的地 | 状态 | 接口 |
|---|---|---|
| task（条件匹配） | 已接线 | `ReceiveEventSourceBridge.emit(ConditionMatchInput[])` |
| display | 有 API，未接线 | `displayService.ingestSourceMaterial(DisplaySourceMaterial)` |
| storage | 有 API，未接线 | `storageService.appendLocalRecords(StorageLocalRecord[])` |
| 未匹配 | receive outcome 已有 `kind: 'unmatched'`，旧系统只记计数器 | 统计层面足够 |

## 最终方案

### 核心管线

```
refreshFrameReferences(frames):
  → 预编译各帧表达式 → Map<frameId, CompiledGroup>
  → 缓存在 receive service 内部

ingestBatch(batch):
  → 帧匹配（已有，消费 frame identifierRules）
  → 字段原始解析（已有，dataType + factor）
  → 表达式求值（新增 pass）:
      VariableMap = merge(当前帧 raw 值, read model 跨帧值, globalParams)
      evaluateGroup(compiledGroup, variableMap)
      合并结果到 outcome
  → 更新 read model（参数当前值快照）
  → 产出 ReceiveBatchOutcome（扩展：含表达式结果）

routingTick (runtime 层):
  → drainInputSource → ReceiveBatchOutcome[]
  → 预算截断（每 tick 最多 N 个 batch）
  → 扇出分发:
      ├→ displayService.ingestSourceMaterial()（节流）
      ├→ storageService.appendLocalRecords()（可配开关）
      ├→ receiveEventSourceBridge.emit()（已有）
      └→ unmatched 计数
```

### 拆分方案：2 个子 feature

**Sub-feature 1：receive-real-pipeline**

完整管线（匹配 → 解析 → 表达式 → read model → 扇出）。一个 design，checklist 分阶段实施。
