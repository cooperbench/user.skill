## 1. SCOE 复杂完成条件的本质：关联匹配（Correlation）

旧 SCOE 的"参数化完成条件"核心能力是：**我发了什么，就检查回复里对应字段是否匹配**。

典型场景：
- 发送遥控帧，字段 `code_seq` 值为 `7`，等确认帧的 `ack_seq` 也等于 `7`
- 发送参数设置，值 `X`，等遥测帧确认参数已变为 `X`

这不是 SCOE 专属需求。任何"发指令等确认"的 task 都有：**步骤 N 的发送值 → 步骤 M 的条件阈值之间的关联**。

所以 wait-condition 的 threshold 应该支持两种来源：

```typescript
interface WaitCondition {
  frameId: string;
  fieldId: string;
  operator: ComparisonOperator;
  value:
    | { kind: 'literal'; value: string | number }
    | { kind: 'correlate'; fromStepId: string; fromFieldId: string };
}
```

`correlate` 的语义：运行时从 `fromStepId` 的执行结果中取 `fromFieldId` 的值，作为比较阈值。这样"发 X 等 X 回来"就是一个通用的 wait-condition step，不依赖 SCOE。

**SCOE 指令接入 feature 的职责**就简化为：翻译 SCOE 命令 → 构造 TaskDefinition，其中 wait-condition 用 `correlate` 引用前序 send-step 的字段值。task 核心不需要知道 SCOE 存在。

## 2. 三种模式统一：调度驱动 × 迭代控制 正交分解

你说得对，三种模式拆成两个正交维度会更干净。

### 当前设计的问题

```
sequence = timed 的 count=1 特例
timed    = 定时 + 计数
trigger  = 事件触发 + 无限
```

sequence 和 timed 本质是同一个调度策略，只是迭代次数不同。trigger 和 timed 的迭代控制也可能重叠（"触发 5 次后停止"）。强行分三种模式导致代码里有 `if mode === 'sequence'` 的特判。

### 提议：正交分解

**调度驱动（ScheduleDriver）**：每轮迭代怎么发起

```typescript
type ScheduleDriver =
  | { kind: 'immediate' }
  | { kind: 'timer'; intervalMs: number }
  | { kind: 'event'; trigger: ConditionSet }
```

**迭代控制（IterationControl）**：总共执行几轮

```typescript
type IterationControl =
  | { kind: 'fixed'; count: number }
  | { kind: 'unlimited' }
  | { kind: 'until'; exit: ConditionSet }
```

### 旧模式映射

| 旧模式 | ScheduleDriver | IterationControl |
|--------|---------------|-----------------|
| sequence | immediate | fixed(1) |
| timed-fixed | timer(N ms) | fixed(count) |
| timed-infinite | timer(N ms) | unlimited |
| trigger | event(cond) | unlimited |
| **新的组合** | timer(N ms) | until(exitCond) |
| **新的组合** | event(cond) | fixed(5) |

代码层面，循环引擎只实现一个统一的 `IterationLoop`：

```typescript
async function runIterationLoop(ctx) {
  const driver = createDriver(ctx.definition.schedule);
  const shouldContinue = createIterationGuard(ctx.definition.iteration);
  
  while (shouldContinue(ctx.state)) {
    await driver.waitForNext(ctx);      // immediate 立即返回 / timer 等 / event 等条件
    ctx.state = advanceIteration(ctx);
    await executeStepSequence(ctx);     // 每轮执行 steps
  }
}
```

`waitForNext` 和 `shouldContinue` 是纯策略注入，没有 if/else 分支判断模式类型。暂停/恢复只影响 driver（暂停时 stop waiting，恢复时重新开始等待）。

### 一个需要注意的点

trigger 模式下，`event trigger` 和 `until exit` 都基于 receive events。它们可能是不同的条件集：
- trigger：什么条件触发一轮执行（比如"帧 X 到达"）
- exit：什么条件停止整个任务（比如"帧 Y 字段 Z == 0"）

两者独立，不冲突。

## 3. G1（fieldVariations）：Phase 1 必须有

### 设计

send-step 的 field value 支持表达式：

```typescript
interface SendStepConfig {
  frameId: string;
  targetId: string;
  fieldValues: Record<string, FieldValueSpec>;
}

type FieldValueSpec =
  | { kind: 'literal'; value: string | number }
```

| 变量 | 含义 |
|------|------|

- 递增序列号：`expr: "__roundIndex__ + 1"`
- 周期性参数：`expr: "baseValue + __roundIndex__ * step"`

## 4. wait-condition 弄全

同意，现在补比后面加容易得多。

### 完整 WaitCondition schema

```typescript
interface WaitCondition {
  frameId: string;
  fieldId: string;
  operator: ComparisonOperator;  // 复用 shared/condition-operators 的 9 种
  value:
    | { kind: 'literal'; value: string | number }
    | { kind: 'correlate'; fromStepId: string; fromFieldId: string };
  sourceId?: string;  // 数据源过滤
}

interface ConditionSet {
  conditions: WaitCondition[];
  logic: 'and' | 'or';
}
```

覆盖的能力：

| 能力 | 支持方式 |
|------|---------|
| 单条件匹配 | `ConditionSet { conditions: [cond], logic: 'and' }` |
| AND 组合 | `logic: 'and'` |
| OR 组合 | `logic: 'or'` |
| 关联匹配（SCOE） | `value: { kind: 'correlate', ... }` |
| 9 种比较算子 | 复用 condition-operators |
| 多帧联合判断 | 不同 frameId 的 conditions + AND/OR |

这里 `ConditionSet` 同时用于三处：
1. **event driver 的 trigger**：什么 receive event 触发一轮
2. **until 的 exit**：什么条件终止整个任务
3. **wait-condition step**：步骤内等待什么条件满足

同一个类型，同一个匹配引擎（shared/condition-operators + correlate 查找），三处复用。

## 5. 定时器精度

你说的对，Chromium 渲染进程的 `setInterval` 有两个问题：
1. **精度抖动**：主线程忙时 jitter 可达数十毫秒
2. **后台节流**：窗口非活跃时 throttled 到 1 tick/秒

### 方案比较

| 方案 | 精度 | 复杂度 | 架构风险 |
|------|------|--------|---------|
| A: `backgroundThrottling: false` + setInterval | 一般 | 最低 | 无 |
| B: Web Worker 定时器 | 好 | 低 | 无 |
| C: main process 定时器 | 最好 | 高 | 违反"main 不承载领域规则" |

- 不跨 IPC 边界，不违反 main process 规则

## 修正 1：correlate 应该移除

架构审查发现 **旧系统没有任何 step 间值引用的证据**。我之前提议的 correlate 理解有误。

### 旧 SCOE 参数关联的真实流程

```
接收指令帧 → extractAndResolveParams() → resolvedParams
    ↓
发送帧: field.value = resolvedParams[param.targetFieldId]  ← 直接赋值
    ↓
接收回复帧 → checkCompletionConditions():
    用 param.options[index].matchValue 比较（索引匹配）
```

关键发现：**参数值在指令接入翻译时就已经知道了**。SCOE adapter 从指令帧解析出参数值后，既用这些值填充发送字段，也用这些值构造完成条件阈值。TaskDefinition 创建时，所有 literal 值都已经 resolve 好了。

**结论**：不需要 correlate。SCOE 指令接入 feature 在翻译阶段 resolve 所有参数值，构造 TaskDefinition 时直接填 literal。task 引擎不需要理解参数关联。

## 修正 2：OR 组合应该移除

旧系统所有条件检查都是 AND 遍历：
- SCOE `checkCompletionConditions`：逐条件检查，任一不满足 return false → AND
- Task 触发条件：逐条件检查 → AND
- 无任何 OR 组合的 UI 入口或代码逻辑

**结论**：移除 `logic: 'and' | 'or'`，只保留 AND 语义。条件数组就是 AND，与旧系统一致。

```typescript
function resolveIteration(def: TaskDefinition): IterationControl {

    return { kind: 'fixed', count: maxLen };

}
```

## 循环引擎的执行逻辑变得更简单

```typescript
async function runTask(ctx: TaskContext) {
  const driver = createDriver(ctx.definition.schedule);
  const stop = createStopGuard(ctx.definition.stopCondition);

  while (!stop.shouldStop(ctx.state)) {
    await driver.waitForNext(ctx);   // immediate 立即 / timer 等 / event 等触发
    
    for (const step of ctx.definition.steps) {
      if (stop.shouldStop(ctx.state)) break;
      
      if (step.kind === 'send' && step.config.repeat) {
        await executeRepeatableSend(ctx, step);  // 重复发送直到 until 或 maxCount
      } else {
        await executeStep(ctx, step);             // 单次执行
      }
    }
    ctx.state = advanceIteration(ctx.state);
    injectFieldVariations(ctx);  // 按轮次注入值
  }
}
```

`waitForNext` 和 `shouldStop` 两个纯策略，没有模式分支判断。step 级别的 repeat 是 send-step 自己的事，不影响整体循环结构。

### 设计思路说明

**子 agent 分两批**（研究 3 个并行 + 自检 3 个并行），中间是主线程写设计。不边写边查，先查完再写，写完再验。

**Phase 1 的重点是验证**，不是重新调研。brainstorm 已经做了大量调研，design 阶段需要的是**精确到字段名和行号的验证**，避免再出现上一轮的引用不准确问题。

**Phase 3 自检是必须的**。上一轮 review 暴露的核心问题就是"引用没对照实际代码验证"。自检 agent 的唯一职责就是拿 design 产出对照实际代码做 diff，不是做设计判断。

**文件数和 OR 证据**这类问题在 design 阶段不会再现，因为 Phase 1 Agent 1 会给出 26 个文件的完整清单，Phase 1 Agent 3 会给出 OR 的完整证据。
