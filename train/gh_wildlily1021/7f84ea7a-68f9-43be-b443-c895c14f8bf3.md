## 1. SCOE 复杂完成条件的本质：关联匹配（Correlation）

旧 SCOE 的"参数化完成条件"核心能力是：**我发了什么，就检查回复里对应字段是否匹配**。

典型场景：
- 发送遥控帧，字段 `code_seq` 值为 `7`，等确认帧的 `ack_seq` 也等于 `7`
- 发送参数设置，值 `X`，等遥测帧确认参数已变为 `X`

这不是 SCOE 专属需求。任何"发指令等确认"的 task 都有：**步骤 N 的发送值 → 步骤 M 的条件阈值之间的关联**。

所以 wait-condition 的 threshold 应该支持两种来源：

```typescript
interface WaitCondition {
  frameId: string;
  fieldId: string;
  operator: ComparisonOperator;
  value:
    | { kind: 'literal'; value: string | number }
    | { kind: 'correlate'; fromStepId: string; fromFieldId: string };
}
```

`correlate` 的语义：运行时从 `fromStepId` 的执行结果中取 `fromFieldId` 的值，作为比较阈值。这样"发 X 等 X 回来"就是一个通用的 wait-condition step，不依赖 SCOE。

**SCOE 指令接入 feature 的职责**就简化为：翻译 SCOE 命令 → 构造 TaskDefinition，其中 wait-condition 用 `correlate` 引用前序 send-step 的字段值。task 核心不需要知道 SCOE 存在。

## 2. 三种模式统一：调度驱动 × 迭代控制 正交分解

你说得对，三种模式拆成两个正交维度会更干净。

### 当前设计的问题

```
sequence = timed 的 count=1 特例
timed    = 定时 + 计数
trigger  = 事件触发 + 无限
```

sequence 和 timed 本质是同一个调度策略，只是迭代次数不同。trigger 和 timed 的迭代控制也可能重叠（"触发 5 次后停止"）。强行分三种模式导致代码里有 `if mode === 'sequence'` 的特判。

### 提议：正交分解

**调度驱动（ScheduleDriver）**：每轮迭代怎么发起

```typescript
type ScheduleDriver =
  | { kind: 'immediate' }
  | { kind: 'timer'; intervalMs: number }
  | { kind: 'event'; trigger: ConditionSet }
```

**迭代控制（IterationControl）**：总共执行几轮

```typescript
type IterationControl =
  | { kind: 'fixed'; count: number }
  | { kind: 'unlimited' }
  | { kind: 'until'; exit: ConditionSet }
```

### 旧模式映射

| 旧模式 | ScheduleDriver | IterationControl |
|--------|---------------|-----------------|
| sequence | immediate | fixed(1) |
| timed-fixed | timer(N ms) | fixed(count) |
| timed-infinite | timer(N ms) | unlimited |
| trigger | event(cond) | unlimited |
| **新的组合** | timer(N ms) | until(exitCond) |
| **新的组合** | event(cond) | fixed(5) |

代码层面，循环引擎只实现一个统一的 `IterationLoop`：

```typescript
async function runIterationLoop(ctx) {
  const driver = createDriver(ctx.definition.schedule);
  const shouldContinue = createIterationGuard(ctx.definition.iteration);
  
  while (shouldContinue(ctx.state)) {
    await driver.waitForNext(ctx);      // immediate 立即返回 / timer 等 / event 等条件
    ctx.state = advanceIteration(ctx);
    await executeStepSequence(ctx);     // 每轮执行 steps
  }
}
```

`waitForNext` 和 `shouldContinue` 是纯策略注入，没有 if/else 分支判断模式类型。暂停/恢复只影响 driver（暂停时 stop waiting，恢复时重新开始等待）。

### 一个需要注意的点

trigger 模式下，`event trigger` 和 `until exit` 都基于 receive events。它们可能是不同的条件集：
- trigger：什么条件触发一轮执行（比如"帧 X 到达"）
- exit：什么条件停止整个任务（比如"帧 Y 字段 Z == 0"）

两者独立，不冲突。

## 3. G1（fieldVariations）：Phase 1 必须有

同意，这个很关键。有了解 expression engine，可以做得比旧系统的 `fieldVariations` 更干净。

### 设计

send-step 的 field value 支持表达式：

```typescript
interface SendStepConfig {
  frameId: string;
  targetId: string;
  fieldValues: Record<string, FieldValueSpec>;
}

type FieldValueSpec =
  | { kind: 'literal'; value: string | number }
  | { kind: 'expression'; expr: string };
```

task 引擎每轮注入内置变量：

| 变量 | 含义 |
|------|------|
| `__roundIndex__` | 当前轮次（0-based） |
| `__totalRounds__` | 计划总轮次（fixed 模式有值，unlimited 为 Infinity） |
| `__timestamp__` | 当前时间戳（ms） |

典型用法：
- 递增序列号：`expr: "__roundIndex__ + 1"`
- 周期性参数：`expr: "baseValue + __roundIndex__ * step"`
- 时间戳：`expr: "__timestamp__"`

**与 send-real 的对接**：task 把 `fieldValues` + `variables`（含内置变量）一起传给 `SendRequest`，send-real 负责用 expression engine 解析表达式并构帧。task 自己不做表达式求值。

## 4. wait-condition 弄全

同意，现在补比后面加容易得多。

### 完整 WaitCondition schema

```typescript
interface WaitCondition {
  frameId: string;
  fieldId: string;
  operator: ComparisonOperator;  // 复用 shared/condition-operators 的 9 种
  value:
    | { kind: 'literal'; value: string | number }
    | { kind: 'correlate'; fromStepId: string; fromFieldId: string };
  sourceId?: string;  // 数据源过滤
}

interface ConditionSet {
  conditions: WaitCondition[];
  logic: 'and' | 'or';
}
```

覆盖的能力：

| 能力 | 支持方式 |
|------|---------|
| 单条件匹配 | `ConditionSet { conditions: [cond], logic: 'and' }` |
| AND 组合 | `logic: 'and'` |
| OR 组合 | `logic: 'or'` |
| 关联匹配（SCOE） | `value: { kind: 'correlate', ... }` |
| 9 种比较算子 | 复用 condition-operators |
| 多帧联合判断 | 不同 frameId 的 conditions + AND/OR |

这里 `ConditionSet` 同时用于三处：
1. **event driver 的 trigger**：什么 receive event 触发一轮
2. **until 的 exit**：什么条件终止整个任务
3. **wait-condition step**：步骤内等待什么条件满足

同一个类型，同一个匹配引擎（shared/condition-operators + correlate 查找），三处复用。

## 5. 定时器精度

你说的对，Chromium 渲染进程的 `setInterval` 有两个问题：
1. **精度抖动**：主线程忙时 jitter 可达数十毫秒
2. **后台节流**：窗口非活跃时 throttled 到 1 tick/秒

### 方案比较

| 方案 | 精度 | 复杂度 | 架构风险 |
|------|------|--------|---------|
| A: `backgroundThrottling: false` + setInterval | 一般 | 最低 | 无 |
| B: Web Worker 定时器 | 好 | 低 | 无 |
| C: main process 定时器 | 最好 | 高 | 违反"main 不承载领域规则" |

**推荐方案 B：Web Worker 定时器**，通过 platform facade 抽象。

### 设计

```typescript
// platform/timer-service.ts — renderer facade
interface TimerHandle { readonly id: string }

interface TimerService {
  startInterval(cb: () => void, intervalMs: number): TimerHandle;
  pause(handle: TimerHandle): void;
  resume(handle: TimerHandle): void;
  stop(handle: TimerHandle): void;
  getRemainingTime(handle: TimerHandle): number;
}
```

实现方式：开一个轻量 Web Worker，只负责精确计时，通过 `postMessage` 通知 renderer tick。

**为什么不用 main process**：
- 定时器本身不是领域逻辑，是平台能力
- 放 platform facade 后面，task core 不关心定时器在哪跑
- Web Worker 精度已经很好（~1ms jitter），对 100ms+ 间隔足够
- 不跨 IPC 边界，不违反 main process 规则

**为什么不用方案 A**：
- `backgroundThrottling: false` 只解决后台节流，不解决主线程忙时的抖动
- Web Worker 天然不受主线程阻塞影响

**task core 的使用方式**：

```typescript
// task-iteration-loop.ts — core 层，纯 TS
function createTimerDriver(config: TimerDriverConfig, timerService: TimerService) {
  return {
    async waitForNext(ctx) {
      return new Promise<void>(resolve => {
        const handle = timerService.startInterval(() => resolve(), config.intervalMs);
        ctx.currentTimerHandle = handle;
      });
    },
    pause(ctx) { timerService.pause(ctx.currentTimerHandle); },
    resume(ctx) { timerService.resume(ctx.currentTimerHandle); },
  };
}
```

task core 通过接口依赖 `TimerService`，单元测试用 fake，运行时注入 Web Worker 实现。完全遵循 adapter pattern。

    const values = result.content.split(/[\n\r]+/).map(v => v.trim()).filter(v => v !== '');
    fieldVariationsMap[param.id] = values;
  } else {

    fieldVariationsMap[param.id] = resolvedParams[param.id]?.split(',') || [''];
  }
}

for (const param of command.params) {

  }

## 核心问题答案

### Q1: SCOE 命令发送时，哪些字段值是"动态关联"的？

**答案**：通过 `ScoeCommandParams.targetFieldId` 指定的发送字段。这些字段的值来自接收帧中解析出的参数值（`resolvedParams[param.id]`），而不是固定配置值。

### Q2: 旧系统的"文件读取逐个发送"是怎么实现的？

**答案**：
1. 接收帧的参数值可以是 `.txt` 文件名或逗号分隔的值列表
2. 从文件读取按行分割，或从逗号字符串 split，得到值数组
3. 构建 `FieldVariation[]`，将值数组绑定到 `targetFieldId`
4. 创建定时任务，`repeatCount` = 值数组长度
5. 每轮发送前，通过 `updateCachedInstanceFields` 根据 `variationIndex` 从数组中取值赋给字段

### Q3: correlate 的 fromFieldId 到底应该引用什么？

**答案**：`fromFieldId` 应该引用**发送帧的某个 field 的 ID**（即 `param.targetFieldId`）。

**原因**：
- 旧系统中，完成条件通过 `condition.useParam` 和 `condition.targetParamId` 来引用参数
- 参数通过 `param.targetFieldId` 绑定到发送帧的字段
- 当使用参数关联时，完成条件会比较：
  1. 接收帧的 `sourceFieldId` 字段值
  2. 与参数选项对应的 `condition.options[].matchValue`
- 参数选项通过索引匹配：`param.options[index].value === resolvedParams[paramId]`

**关键理解**：
- `targetFieldId` 标识的是"发送时被参数动态赋值的字段"
- 完成条件不需要直接引用 `targetFieldId`，而是通过 `targetParamId` 间接关联
- 如果新系统需要 `fromFieldId`，它应该等价于 `param.targetFieldId`，即"被参数化的发送字段ID"

## 总结

提议的 task-real 统一模型在 feature 边界上总体合理，但存在 2 项边界违规风险、3 处过度设计嫌疑和 2 个正确性冲突。核心问题是 `ScheduleDriver` 的 `event` 变体绕过了 receive public API 直接消费 receive events 的假象，以及 `ConditionSet` 在三个语义不同位置被复用。

## 分析

### A. Feature 边界

**A1. ScheduleDriver 的 'event' 模式是否越界？**

**concern**

提议的 `ScheduleDriver = { kind: 'event'; trigger: ConditionSet }` 让 task 的 `trigger` 条件直接描述 receive event 的匹配结构（`frameId/fieldId/operator/value`）。但已有实现通过显式的 adapter port 消费 receive events：

- `rewrite/src/features/task/adapters/ports.ts:9-11` 定义了 `ReceiveEventSource` 接口，handler 接收的是 `ConditionMatchInput`（已解耦的扁平结构），不是 receive 内部类型。
- `rewrite/src/features/task/services/task-service.ts:107-109` 在 `ensureSubscription()` 中通过 `receiveSource.subscribe()` 获取输入，再交给 `conditionRegistry.processInput()`。
- `ConditionMatchInput`（`task/core/types.ts:223-228`）已经从 receive 内部解耦，是 task 自己定义的只读结构。

所以 `ScheduleDriver` 的 `event` 变体本身不越界——它描述的是 task 自身的触发配置，不是直接耦合 receive 内部。**但如果 `ConditionSet` 被定义在 shared/ 或 receive/ 而不是 task/ 内部，就会产生归属问题。**只要 `ConditionSet` 和 `WaitCondition` 一样归 task feature own，边界成立。

然而，`trigger` 和 `wait-condition` 语义不同：`trigger` 是"匹配到就启动一个完整的 task instance"，`wait-condition` 是"在 task 执行中间等待某个条件满足"。两者复用同一个 `ConditionSet` 类型掩盖了这种语义差异。建议在 `trigger` 位置使用更具体的命名（如 `TriggerCondition`），不与 `wait-condition` 共享类型定义。

**A2. ConditionSet 在 trigger/exit/wait-condition 三处复用是否语义相同？**

**concern**

三处语义差异显著：

1. **trigger**（启动触发）：无超时概念，匹配即启动，是 task 实例生命周期入口。
2. **exit**（迭代退出条件）：有超时或 maxDuration 兜底，但不像 wait-condition 那样需要 per-step timeout 和 onTimeout 策略。实际是"满足条件后提前结束迭代"。
3. **wait-condition step**：有 `timeoutMs` 和 `onTimeout` 三路策略（`continue/skip/fail`），是 step 级别阻塞等待。

已有实现中，`WaitCondition`（`task/core/types.ts:26-31`）只有 `frameId/fieldId/operator/threshold/sourceId`，没有 `logic` 组合字段。提议的 `ConditionSet` 增加了 `conditions: WaitCondition[]` + `logic: 'and' | 'or'`，这是一个语义扩展。

三处复用会导致：
- `trigger` 位置不需要 `logic: 'or'`（旧系统只有单条件 `trigger`）。
- `exit` 位置需要但旧系统没有证据（见 B4）。
- `wait-condition` 位置需要 `timeoutMs/onTimeout`，这些字段在 `ConditionSet` 中不存在，必须在外层配置。

建议拆成三个独立类型：`TriggerCondition`（单条件或组合条件）、`ExitCondition`（组合条件 + 超时兜底）、`WaitCondition`（保持现有结构，单条件 + `timeoutMs` + `onTimeout`）。类型可以共享底层的条件谓词（如 `ConditionTerm`），但外层包装应各自表达语义。

**A3. correlate 的 fromStepId 是否产生不健康的 step 间耦合？**

**concern**

提议的 `WaitCondition.value = { kind: 'correlate'; fromStepId; fromFieldId }` 让一个 step 的条件值引用前序 step 的结果。旧系统中 **没有发现任何此类引用模式的证据**：

- Grep `correlate`、`fromStep`、`上一步`、`前一步` 在旧 `src/` 下均无匹配。
- 旧 SCOE 的完成条件引用的是 `receive result`（`allFrameData`），不是 `send step` 的输出。
- 旧 `send task` 只有 `send step`（发送同一帧），没有 `multi-step` 序列。

这意味着 `correlate` 是纯"可能的需求"。如果引入，会带来：
- `task service` 必须维护 `step result` 索引供后续 `step` 查询。
- `step` 之间产生数据依赖图，需要 `DAG` 校验防止循环引用。
- 测试复杂度显著增加。

建议从提议中移除 `correlate`，当前用 `literal` 值足够覆盖旧系统行为。如果未来确实需要 `step` 间传值，再作为增量特性加入。

**A4. TimerService 放 platform/ 是否正确？**

**pass**

已有实现中 `sleep()`（`task-step-executors.ts:9-15`）直接用 `setTimeout`，没有依赖 `platform facade`。但 `CLAUDE.md` 明确写了"文件、串口、网络、定时器、窗口能力都要有明确 `platform API`"（`quality rules R5`），且 `interaction matrix` 的 `timer wrapper` 条目（6.5 节）提到"定时能力可能是 `platform/runtime` 装配材料"。

`TimerService` 放 `platform/` 合理，前提是：
- `TimerService` 只提供定时器调度能力（`setTimeout/setInterval` 的抽象）。
- `task lifecycle` 状态推进仍然在 `task service/core`。
- `platform/` 的 `TimerService` 不承载任何业务语义。

但 `TimerService` 不应该成为独立 `feature`，也不应该进 `shared/`（`shared/` 禁止有副作用的基础设施）。作为 `platform/` 的能力模块是正确的位置。

### B. 过度设计检查

**B1. IterationControl 三种变体是否都有真实需求？**

**concern（partial over-design）**

| 变体 | 旧系统证据 | 判定 |
|------|-----------|------|
| `{ kind: 'fixed'; count }` | `TimedTaskConfig.repeatCount`（`sendTasksStore.ts:83`） | 有真实需求 |
| `{ kind: 'unlimited' }` | `TimedTaskConfig.isInfinite`（`sendTasksStore.ts:84`） | 有真实需求 |
| `{ kind: 'until'; exit: ConditionSet }` | **无证据**。旧系统 `stopCondition` 只有 `maxIterations` 和 `maxDurationMs`（`task/core/types.ts:106-109`），没有基于条件匹配的退出 | **过度设计** |

旧 SCOE 的 `completionConditions`（`scoeFrame.ts:420`）是"指令执行完后检查是否成功"，不是"迭代循环何时退出"。SCOE 完成条件归 `scoe feature` 定义，通过 `task` 的 `stop` 语义表达，不需要 `IterationControl.until`。

建议只保留 `fixed` 和 `unlimited`，退出条件通过 `TaskStopCondition`（`maxDurationMs` + `maxIterations`）+ 用户主动 `stop` 覆盖。`until` 作为 `future work` 记录，不进入当前提议。

**B2. FieldValueSpec 的 'expression' 是否应该在 task 中定义？**

**pass（轻微 concern）**

已有 `SendStepConfig`（`task/core/types.ts:36-40`）中 `fieldValues` 是 `Record<string, string | number | boolean>`，直接传给 `SendRequest.userFieldValues`。`SendRequest`（`send/core/types.ts:33-39`）同时接受 `userFieldValues` 和 `variables`，其中 `variables: VariableMap` 是给 send service 的表达式引擎用的。

提议的 `FieldValueSpec = { kind: 'expression'; expr: string }` 让 task 层也定义表达式。但这与已有架构冲突：
- 表达式编译和求值已经归 `shared/expression`。
- `SendRequest` 已经有 `variables` 字段传给 send 的表达式引擎。
- 如果 task 层再定义表达式，就需要 task service 自己编译/求值，然后传 `literal` 给 send。

当前 `buildSendRequest`（`task-step-executors.ts:17-29`）直接把 `stepConfig.fieldValues` 透传给 `SendRequest.fieldValues`，不经过表达式处理。如果 task step 需要动态值，正确的做法是让 `SendRequest.variables` 或 `SendRequest.userFieldValues` 承担，不需要 task 自身理解表达式。

建议 `FieldValueSpec` 的 `expression` 变体移除，task step 只提供 `literal` 值或 `variable` 引用。表达式求值由 send feature 的 `frame-resolver` 处理（已有实现：`send/services/send-service.ts:160-166`）。

**B3. WaitCondition 的 correlate 模式是否过度抽象？**

**over-design**

如 A3 分析，旧系统无任何 `step` 间值引用的证据。`SCOE` 的参数解析是 `SCOE adapter` 内部逻辑，不是 `task step` 间的 `correlate`。直接传 `literal` 值覆盖所有旧系统行为。

**B4. ConditionSet 的 OR 组合有旧系统证据吗？**

**over-design**

- 旧 SCOE 的 `checkCompletionConditions`（`scoeFrame.ts:427-490`）对 `conditions` 数组做的是 **AND** 遍历：`for (const condition of conditions)` 中任何一个不满足就 `return false`。
- 旧 `send task` 的 `TriggerCondition` 是单条件列表，旧代码中没有 `logic` 字段区分 `AND/OR`。
- 已有 `WaitCondition` 是单条件，不支持组合。
- 旧 `TriggerTaskConfig.conditions`（`sendTasksStore.ts:94`）虽然是一个数组，但从旧代码 `useSendTaskTriggerListener` 的使用方式看，是逐条件检查（`AND` 语义），没有 `OR` 组合选项。

建议移除 `logic: 'and' | 'or'`，只保留 `AND` 语义（与旧系统一致）。如果确实需要 `OR`，后续增量加入。如果不移除，至少必须标注为 `future capability` 而非当前需求驱动。

### C. 正确性

**C1. 提议类型与已有 task 骨架的冲突点**

**concern**

| 提议 | 已有实现 | 冲突 |
|------|---------|------|
| `ScheduleDriver` 联合类型 | `TaskDefinition.schedulingMode: TaskSchedulingMode`（`'timed' \| 'trigger' \| 'sequence'`） + `triggerSource: TaskTriggerSource` + `intervalMs` + `triggerCondition` | 提议用 `discriminated union` 替代扁平字段，迁移需要改 `TaskDefinition` 结构 |
| `IterationControl` | `TaskStopCondition`（`maxIterations?` + `maxDurationMs?`）| 提议把迭代控制从 `stopCondition` 独立出来，结构不兼容 |
| `ConditionSet`（多条件 + `logic`） | `WaitCondition`（单条件）| `condition-matcher.ts` 和 `condition-registry.ts` 只支持单条件匹配，需要重写 |
| `TaskDefinition.schedule` | `TaskDefinition.schedulingMode` + `triggerSource` + `intervalMs` + `triggerCondition` + `cooldownMs` + `delayBeforeStartMs` | 字段重组 |

迁移成本评估：
- `TaskDefinition` 结构变化影响 `task-service.ts`、`task-iteration-loops.ts`、`task-step-executors.ts` 三个文件的核心逻辑。
- `ConditionRegistry` 和 `evaluateCondition` 需要支持多条件组合。
- `task-fixtures.ts` 和所有测试需要更新。
- 估计涉及 **6-8 个文件**，**300+ 行** 已有代码需要适配。

但这是设计讨论阶段的预期成本，不算阻断性。只要设计确定后一次性迁移即可，不是反对理由。

**C2. 与 send public API 的对接方式**

**concern（轻微）**

提议的 `FieldValueSpec` 与 `SendRequest` 签名不完全兼容：

- `SendRequest.userFieldValues` 期望 `Record<string, string | number | boolean>`（`send/core/types.ts:35`）。
- `SendRequest.variables` 期望 `VariableMap`（`send/core/types.ts:36`）。
- 提议的 `FieldValueSpec = { kind: 'literal'; value } | { kind: 'expression'; expr }` 是一个联合类型，不直接映射到 `SendRequest` 的扁平结构。

如果 task step 使用 `FieldValueSpec`，`buildSendRequest` 需要在翻译层把 `FieldValueSpec[]` 拆成 `userFieldValues` + `variables`。这不是阻断性问题，但增加了一层翻译复杂度。

建议 task step 保持现有 `fieldValues: Record<string, string | number | boolean>` 结构，直接透传给 `SendRequest`。如果确实需要动态值，通过 `variables` 字段传递给 send service。

**C3. 与 receive public API 的对接方式**

**pass**

提议的 `ScheduleDriver.event` 变体的 trigger 条件匹配，在运行时仍然是 task service 订阅 `ReceiveEventSource`，收到 `ConditionMatchInput` 后用 `ConditionRegistry` 做匹配。只要 `ConditionSet` 的 `WaitCondition` 字段与 `ConditionMatchInput`（`frameId/fieldId/value/sourceId`）兼容，对接没有问题。

`ConditionMatchInput.value` 是 `number | string | null`（`task/core/types.ts:225`），提议的 `WaitCondition.value = { kind: 'literal'; value: string | number }` 需要一个映射，但非常直接。

**C4. 错误策略在正交分解后是否还适用？**

**pass**

已有 `TaskErrorPolicy`（`task/core/types.ts:98-102`）定义了 `onFailure: retry | skip-step | stop | pause`，加可选 `retryCount` 和 `retryDelayMs`。`task-error-policy.ts` 完整实现了这四种策略。

提议的 `errorPolicy` 字段与已有结构一致，`ScheduleDriver` 和 `IterationControl` 的正交分解不影响错误策略的适用性——错误策略作用于 `step` 执行层面，与调度方式和迭代控制是正交的。

## 根本原因

提议的核心问题不是类型设计本身，而是 **用统一抽象（`ConditionSet`、`IterationControl`、`FieldValueSpec`）覆盖了三个不同语义层**，同时在没有旧系统证据的地方做了前瞻性扩展（`until`、`OR`、`correlate`、`expression-in-task`）。

## 建议

1. **[最高优先级] 保留 `ScheduleDriver` 的 `discriminated union` 结构，但内部命名区分语义** - 低成本 - 高影响
   - `immediate` 和 `timer` 直接复用。
   - `event` 重命名为 `trigger`，内部使用 `TriggerCondition`（不是 `ConditionSet`），强调"触发启动"语义。
   - `TriggerCondition` 和 `WaitCondition` 共享底层 `ConditionTerm` 类型（`frameId/fieldId/operator/value`），但外层包装各自独立。

2. **[高优先级] 移除 `IterationControl.until`** - 低成本 - 中影响
   - 只保留 `fixed` 和 `unlimited`，与旧系统证据对齐。
   - 退出条件用 `TaskStopCondition`（`maxDurationMs + maxIterations`）+ 用户主动 `stop`。
   - `until` 记录为 `future work`。

3. **[高优先级] 移除 `ConditionSet.logic: 'or'`** - 低成本 - 中影响
   - 只保留 `AND` 语义，与旧系统证据对齐。
   - 如果确实需要 `OR`，后续增量加入。

4. **[中优先级] 移除 `WaitCondition` 的 `correlate` 模式** - 低成本 - 中影响
   - 旧系统无证据。
   - 当前 `literal` 值足够。
   - 减少 `step` 间耦合风险和 `DAG` 校验需求。

5. **[中优先级] 移除 `FieldValueSpec.expression`，改用 `SendRequest.variables`** - 低成本 - 高影响
   - 表达式求值归 send feature。
   - task step 只传 `literal` 值或 `variable` 引用。

6. **[低优先级] 在迁移前明确 `TaskDefinition` 结构变化的影响范围** - 中成本 - 中影响
   - 涉及 6-8 个文件，300+ 行已有代码。
   - 建议在 `design` 文档中写明迁移映射表（旧字段 -> 新字段），而非直接开始改代码。

## 权衡

| 选项 | 优势 | 劣势 |
|------|------|------|
| A: 接受提议全部类型 | 统一抽象，前瞻性覆盖所有可能场景 | 引入无证据驱动的复杂度，`correlate` 需要 `DAG` 校验，`OR` 无旧需求，迁移成本高 |
| B: 采纳建议 1-6 的精简版 | 与旧系统证据对齐，迁移成本可控，减少无驱动复杂度 | 未来确实需要 `until/OR/correlate` 时需要增量扩展 |
| C: 保持现有 `TaskDefinition` 不改 | 零迁移成本 | 现有 `schedulingMode + triggerSource + intervalMs + ...` 扁平字段结构不如 `discriminated union` 清晰 |

建议选 B。`discriminated union` 的 `ScheduleDriver` 是合理的结构改进，但 `ConditionSet` 的 `OR`、`IterationControl.until`、`correlate` 和 `FieldValueSpec.expression` 应该在出现真实驱动需求时再增量加入。

规则：**当 `fieldVariations` 存在时，iteration 自动锁定为 `fixed(maxLength)`，忽略用户设置的 iteration**。`maxLength` = 所有 fieldVariation 中 `values.length` 的最大值。

```typescript
function resolveIteration(def: TaskDefinition): IterationControl {
  if (def.fieldVariations && def.fieldVariations.length > 0) {
    const maxLen = Math.max(...def.fieldVariations.map(v => v.values.length));
    return { kind: 'fixed', count: maxLen };
  }
  return def.iteration;
}
```

一轮纯函数，没有复杂逻辑。消费方在创建运行时实例时调一次就行。

## 第三部分：C 类潜在需求评估

### C1. 条件 OR 组合

**判定：纳入当前模型**

旧系统证据：`TriggerCondition.logicOperator: 'and' | 'or'`（`sendInstances.ts:123`），`useSendTaskTriggerListener.ts:115-155` 实现了 AND/OR 组合。

当前 `ConditionTerm[]` 数组隐式为 AND 语义。要支持 OR，有两种方案：
1. 在 `ConditionTerm` 中增加 `logicOperator?: 'and' | 'or'`（与旧系统一致）
2. 将 `conditions` 改为嵌套结构（如 `ConditionGroup`）

方案 1 改动最小，且旧系统已验证。建议纳入。

### C2. step 间值传递（correlate）

**判定：future work 不预留**

当前没有明确的业务需求要求 step A 的输出作为 step B 的输入。send step 的输出是 `SendResult`（成功/失败），wait-condition 的输出是 boolean。如果未来需要"从接收帧提取字段值填入后续发送帧"，这涉及更复杂的 correlate 机制，当前无需预留。

### C3. 条件退出循环（until）

**判定：需要用户确认**

旧系统中 `TriggerTaskConfig` 没有显式的 until 条件，但 `continueListening: false` + 触发一次等效于 until-first-match。定时任务通过 `repeatCount` 控制退出。

当前 `TaskStopCondition` 包含 `maxIterations` 和 `maxDurationMs`，但没有"条件满足即停止"。如果用户需要"定时发送直到某个接收条件满足"，当前模型无法直接表达。

建议：如果需要，可以在 `TaskStopCondition` 中增加 `condition?: ConditionTerm`。

### C4. 表达式动态字段值（每轮用表达式计算）

**判定：future work 不预留**

旧系统的 `fieldVariations` 是静态值数组。当前模型的 `FieldVariation.values` 也是静态数组。表达式引擎已在 `shared/` 实现但尚未与 task 集成。表达式动态字段值是一个自然扩展点，但当前无业务需求驱动。未来可以通过在 `FieldVariation` 中增加 `expressionId?` 来实现。

### C5. 多任务并发协调（同 target 互斥/排队）

**判定：future work 不预留**

### C7. 任务模板/预设复用

**判定：future work 不预留**

旧系统没有任务模板功能。这是 UI/storage 层面的关注点，`TaskDefinition` 本身就是可序列化的配置对象，天然支持存储和复用。不需要在模型中预留额外字段。

### C8. 任务执行历史持久化

**判定：future work 不预留**

这是 storage/result/report 层面的关注点。`TaskInstanceCompletion` 事件可作为持久化的输入。定义态模型不需要为此预留字段。

### C9. 嵌套任务（任务中的步骤是另一个任务）

**判定：future work 不预留**

**判定：future work 不预留**

## 关键发现：OR 组合有旧系统证据

之前的架构审查说 OR 没有证据，但自检 agent 在旧代码中找到了：

- `sendInstances.ts:123` — `TriggerCondition` 有 `logicOperator: 'and' | 'or'`

### 修正方案

最简改动——在 `ConditionTerm` 加一个可选字段：

```typescript
interface ConditionTerm {
  frameId: string;
  fieldId: string;
  operator: ComparisonOperator;
  threshold: string | number;
  sourceId?: string;
  logicOperator?: 'and' | 'or';  // 默认 and，与旧系统一致
}
```

这样 `conditions: ConditionTerm[]` 既支持纯 AND（默认），也支持 AND/OR 混合（与旧系统行为完全一致）。匹配引擎遍历数组时按 `logicOperator` 组合布尔结果。

  const stop = createStopGuard(ctx.definition.stopCondition);

### 1. 要做什么

**统一执行引擎**，核心类型：

```typescript
interface TaskDefinition {
  id: string;
  name: string;
  steps: readonly TaskStepDefinition[];
  schedule: ScheduleDriver;
  stopCondition?: TaskStopCondition;
  fieldVariations?: readonly FieldVariation[];
  errorPolicy: TaskErrorPolicy;
}

type ScheduleDriver =
  | { kind: 'immediate' }
  | { kind: 'timer'; intervalMs: number }
  | { kind: 'event'; conditions: readonly ConditionTerm[] };

interface TaskStopCondition {
  maxIterations?: number;
  maxDurationMs?: number;
  exitCondition?: readonly ConditionTerm[];
}

type TaskStepDefinition =
  | { kind: 'send'; id: string; config: SendStepConfig }
  | { kind: 'wait-condition'; id: string; config: WaitConditionConfig }
  | { kind: 'delay'; id: string; config: { durationMs: number } };

interface SendStepConfig {
  frameId: string;
  targetId: string;
  fieldValues: Readonly<Record<string, string | number | boolean>>;
  intervalAfterMs?: number;
  repeat?: {
    intervalMs: number;
    until?: readonly ConditionTerm[];
    maxCount?: number;
  };
}

interface WaitConditionConfig {
  conditions: readonly ConditionTerm[];
  timeoutMs?: number;
  onTimeout: 'continue' | 'skip' | 'fail';
}

interface ConditionTerm {
  frameId: string;
  fieldId: string;
  operator: ComparisonOperator;
  threshold: string | number;
  sourceId?: string;
  logicOperator?: 'and' | 'or';
}

interface FieldVariation {
  fieldId: string;
  values: readonly (string | number)[];
}

interface TaskErrorPolicy {
  onFailure: 'retry' | 'skip-step' | 'stop' | 'pause';
  retryCount?: number;
  retryDelayMs?: number;
}
```

**循环引擎**：统一一个 `runTask`，ScheduleDriver 注入等待策略，stopCondition 注入停止策略，send-step.repeat 处理单步重复。无模式分支。

**单帧发送**：走同一个引擎，UI 简化表单，背后构造最简 TaskDefinition。

### 2. 不做什么

- 不做 correlate / step 间值传递
- 不做表达式动态字段值（fieldVariations 值数组够用）
- 不做嵌套任务 / 动态步骤
- 不做 SCOE 专属逻辑（SCOE 只翻译成 TaskDefinition）
- 不做 UI / runtime 装配 / storage / result 内部逻辑

### 3. Lane 判断

**Lane B: cs-feat-design**。不拆 roadmap。单 design 文档可覆盖。

### 4. SCOE / 指令接入复用

- SCOE 唯一职责：外部指令 → TaskDefinition
- SCOE 参数解析归 SCOE feature 自己
- 翻译后的 TaskDefinition 与 UI 创建的无区别
- 可复用 ConditionTerm 等类型，但模块边界不交叉

### 5. 关键设计决策

| 决策 | 结论 |
|------|------|
| 三种模式 → 正交分解 | ScheduleDriver + stopCondition + step.repeat |
| IterationControl | 移除，由 stopCondition.maxIterations 替代 |
| until 退出 | stopCondition.exitCondition + step.repeat.until |
| OR 组合 | ConditionTerm.logicOperator，有旧系统证据 |
| correlate | 不做，SCOE 翻译时 resolve |
| fieldVariations | 自动设定 maxIterations |
| 单帧发送 | 走同引擎，UI 差异 |
| TimerService | platform/ facade，Web Worker 实现 |
| 条件匹配 | 复用 shared/condition-operators |

**子 agent 分两批**（研究 3 个并行 + 自检 3 个并行），中间是主线程写设计。不边写边查，先查完再写，写完再验。
