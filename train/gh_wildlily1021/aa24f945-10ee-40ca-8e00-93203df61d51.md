你说得对。**send → receive 回环**完全没有覆盖。

实际场景：下位机收到帧后会回复，发送出去的数据会触发接收管线。具体来说：

**send → connection → 外部设备 → connection → receive 这条回环**

在我们的测试中，外部设备用 TCP echo server 或 loopback 模拟：

1. **send 写出字节 → TCP 传输 → receive 收到并解析** — 这是真实使用中最核心的闭环。用户配置好帧、连接好设备后，发的数据能被正确收回来。

2. **task 定时发送 → 每次发送的响应都被 receive 正确解析** — 定时任务不是发了就完，每发一次都可能收到响应。

3. **SCOE 命令 → 发送 → 收到响应 → 条件匹配 → 下一步** — command-ingress 的 LOAD→SEND_FRAME→ACK→READ_FILE_AND_SEND 链路依赖回环。

这条回环还隐含了几个子测试点：

- **checksum 回环**：send 构帧时写 checksum → receive 解析时验证 checksum → 值一致
- **factor 回环**：send 构帧时 apply factor 逆换算 → receive 解析时 apply factor → 原始值还原
- **字节序回环**：send 大端写入 → receive 大端读出 → 值一致
- **expression 回环**：send 时 expression 字段求值写入 → receive 时 expression 字段读出 → 值正确
- **length field 回环**：send auto length 回填 → receive 用 length 字段截取 → 字节对齐

这些在 S002 的 send 9 步 pipeline 和 receive 6 步 pipeline 里都有描述，但从来没测过"发出去的能原样收回来"。

这应该是 **P0 最高优先级**——比单独测 receive 通路或单独测 send 通路更接近真实使用场景。单独的 T001（receive）和 T003（task→send）只是单向验证，没有闭环。
