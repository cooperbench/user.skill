## Findings

### Medium

**M1: EventRouter 把 runtime 推过了 composition root 边界**

runtime 的硬边界是"composition root 和 wiring layer only"。但 EventRouter 引入了：
- 调度器（pollIntervalMs 驱动的 tick 循环）
- 状态（RoutingStats、isRunning）
- 生命周期（start/stop）

这使 runtime 变成了一个 mini 事件总线，不是单纯的装配层。当真实 platform 提供推送能力时，整个 EventRouter 需要重写或丢弃——RoutingStats、tick 管理、轮询逻辑都是 throwaway。

**替代方案**：用无状态的 `routingTick(features)` 函数替代 EventRouter。调用方（app、测试、或未来的 platform adapter）决定何时调用。runtime 保持 composition root 本色。

```ts
// 替代 EventRouter 的状态机
function routingTick(features: RewriteWiredFeatures): RoutingTickResult {
  const outcome = features.connectionService.drainAdapterEvents();
  if (!outcome.ok) return { ok: false, error: outcome.error };
  const dataEvents = outcome.events.filter(e => e.kind === 'data');
  if (dataEvents.length === 0) return { ok: true, eventsRouted: 0 };
  const source = new ConnectionToReceiveInputSource(dataEvents);
  const receiveOutcome = features.receiveService.drainInputSource(source);
  // extract matches → bridge.emit()
  return { ok: true, eventsRouted: dataEvents.length, matchesEmitted };
}
```

好处：
- runtime 保持无状态
- 测试只需调 `routingTick()`，不需要等 setInterval
- 未来接真实 platform 时，platform 的 data callback 直接调 `routingTick()`
- 不需要 EventRouter 的 start/stop/isRunning/getRoutingStats 四个方法

### Low

**L1: bridge adapter 数量会增长**

当前 4 个 bridge（connection→receive、send→connection、receive→task、frame→send）。后续加 status/display/result 时还需要更多。每个都很薄，模式一致，但数量会到 8-10 个。当前可接受，但建议在 runtime/ 下建 `bridges/` 子目录集中管理，不要全塞在 feature-wiring.ts 里。

**L2: lifecycle.ts 可能过于薄**

如果 EventRouter 简化为无状态函数，lifecycle.ts 就只剩 `init()` = wireFeatures + destroy() = cleanup。这可以是 index.ts 里的两个函数，不需要单独模块。但单独模块也无害，看偏好。

---

## 没问题的部分

- **3 层 wiring（L0→L3）**：依赖关系正确，层级合理
- **ConnectionToReceiveInputSource 设计**：不持有底层 adapter 引用、不竞争事件队列，正确
- **ConnectionBackedSendWriter**：send→connection 的参数映射清晰
- **ReceiveEventSourceBridge**：pub/sub 模式与 task 的 ReceiveEventSource port 对齐
- **错误处理（D4）**：失败即停、记录不吞，务实
- **向后兼容**：overview snapshot 和 resetSettings 保留
- **功能边界**：不接 platform/UI/SCOE/result/report/northbound，范围克制

---

## 总结

设计本身不复杂，feature-wiring 和 bridge adapter 部分做得好。唯一的结构问题是 EventRouter 把 runtime 推过了边界。简化为无状态 `routingTick()` 后，整体就是干净的 composition root + thin lifecycle，符合架构约束。
