  ## 已确认的前提（不需要重新讨论）

  1. **用例 = 任务中的帧**：甲方的"用例"在我们系统里就是 task 里的帧操作。这是之前设计时就定好的。不需要强行一一对应，只需要确保甲方用例的"入参"能传到我们的帧字段里。设备、弧段信息和我们无关。

  2. **核心链路就 4 个接口**：
     - setTestTask（甲方 → 我们）：下发任务
     - controlTestTask（甲方 → 我们）：控制执行
     - testCaseResultReport（我们 → 甲方）：上报用例结果
     - msgReport（我们 → 甲方）：上报步骤进度

  3. **其余 27 个接口是细枝末节**：设备管理、用例查询、参数配置、心跳、告警、FTP 文件传输等，后面按需补，不在本轮讨论范围。


  ## 必须讨论清楚的问题

  ### Q1: 任务闭环是否完整？

  从甲方下发到我们回传，逐段检查：
  - 甲方怎么知道我们有哪些任务/用例可以执行？（文档里有 getTestCaseAll 接口）
  - setTestTask 下发后，我们怎么翻译成 TaskDefinition？
  - 执行过程中 msgReport 怎么触发？由 task 的哪个事件驱动？
  - 用例执行完 testCaseResultReport 怎么触发？result feature 的 verdict 怎么翻译成甲方的 success/fail/tbd？
  - 甲方怎么拿到执行过程中的测试数据文件？（文档有 testDataFileTranslationComplete）
  - 测试报告文件怎么生成和回传？

  ### Q2: HTTPS 服务放哪里？

  我们是 Electron 桌面应用。甲方要 POST 请求到 `https://127.0.0.1:5001`。
  - 放 main process？违反 CLAUDE.md "main 不承载业务规则"约束，但 HTTPS server 本身是平台能力
  - 放独立进程？Node.js 子进程？
  - 用什么库？Express/Fastify/Koa？
  - 怎么和 renderer 的 feature service 通信？IPC？

  ### Q3: 翻译层的形状

  甲方的 Task 模型和我们的 TaskDefinition 差异不小：
  - 甲方：executionPlan（层序串并行）→ nodes（用例 ID 列表）
  - 我们：scheduling driver → steps → 条件/循环

  需要一个翻译层。这个翻译层：
  - 应该是独立 feature？还是 command-ingress 的一部分？还是 northbound 独立 feature？
  - 放在 shared/（纯函数）还是 feature 内？
  - 翻译是双向的吗（甲方格式 ↔ 内部格式）？

  ### Q4: 与现有 command-ingress 的关系

  command-ingress 当前对接 SCOE 串口协议。现在甲方要走 HTTPS。
  - command-ingress 是变成 HTTPS 版本？还是 northbound 独立出来？
  - 两套协议（SCOE 串口 + HTTPS）能否共存？同一个 feature 通过不同 adapter？
  - 还是说 HTTPS 完全替代 SCOE？

  ### Q5: 之前 northbound gap 分析的有效性

  codestable/compound/2026-04-28-northbound-overlap-and-gap-map.md 是基于旧甲方文档写的。
  对照新甲方文档，之前的 gap 分析还有多少成立？需要更新哪些结论？

## 甲方对接闭环分析

### Q1: 任务闭环是否完整？

逐段分析甲方 → 我们 → 甲方的闭环链路：

**1.1 甲方获取可用用例：getTestCaseAll**

甲方通过 `getTestCaseAll` 查询我们有哪些测试用例。我们响应方式是上传一个 JSON 文件到甲方指定的 FTP。

JSON 文件结构是**树形菜单 + 用例列表**，每个用例含：
- `id`（testCaseId）、`name`、`type`（land/orbit）
- `inputPars`：参数定义（parId、cnName、type、defaultValue、unit、remark）
- `execSteps`：执行步骤文本描述
- `checkPoints`：检查点及期望值
- `preHandle`/`afterHandle`：前置/后置处理

**断点：我们的系统没有"用例"这个实体。** 我们有帧定义（frame），但没有从 testCaseId → 帧操作序列的映射。当前 frame feature 只管理单个帧的结构和字段，不承载"用例"语义。

**需要新建的能力：**
- 用例定义库：testCaseId → steps 的映射关系
- 用例参数定义：parId → frame fieldId 的映射
- 用例目录树：菜单结构管理
- getTestCaseAll 响应：将用例库序列化为甲方 JSON 格式并上传 FTP

**1.2 任务下发：setTestTask → TaskDefinition**

甲方下发的 setTestTask 包含：
- `executionPlan.layers`：层级串并行模型（每层 parallel=true/false + testCaseId 列表）
- `testCaseInfo[].inputPars`：用例入参（parId + value）
- `repeatCount`：重复次数
- `immediate`：是否立即执行
- `isEnd`：是否最后一批（多次下发拼装一个完整任务）

**翻译需求：**

| 甲方字段 | 翻译目标 | 可行性 |
|---------|---------|--------|
| executionPlan.layers | steps + 并行执行 | 需要新增并行执行能力 |
| testCaseInfo.testCaseId → inputPars | frame field values | 需要用例库映射 |
| repeatCount | stopCondition.maxIterations | 直接映射 |
| immediate=true | schedule: immediate | 直接映射 |
| immediate=false | createTask 不 startTask | 直接映射 |
| isEnd | 多批次拼装逻辑 | 需要新增状态管理 |

**关键断点：executionPlan 的层级并行模型。** 我们的 TaskDefinition.steps 是平铺列表，steps 串行执行。甲方的 executionPlan.layers 支持同一层内多个用例并行执行。目前 task service 不支持 step 级并行。

**1.3 控制任务：controlTestTask → TaskService**

| 甲方 action | 我们 API | 状态映射 |
|------------|---------|---------|
| abort | stopTask() | 直接映射 |
| pause | pauseTask() | 直接映射 |
| continue | resumeTask() | 直接映射 |
| stop | stopTask() | 直接映射 |

**这段通了。** 唯一歧义是 abort 和 stop 是否有语义差异（目前都映射到 stopTask）。

**1.4 步骤进度上报：msgReport**

甲方期望实时上报步骤信息（stepInfo 数组），每个 stepInfo 含 id/name/result/msg/msgTime。

**需要的事件驱动：** task 执行每个 step 完成后触发。当前 task service 在 step 完成后记录 `TaskStepResult`，但没有外部事件发射机制。

**需要的能力：**
- task step 完成回调/事件（当前只有 onSettled 等终态）
- step name 映射（stepIndex → 甲方的步骤名称如"入网成功"、"呼叫"）
- msgReport 构造和发送（HTTPS POST）

**断点：缺少 step 级事件机制和步骤名称映射。**

**1.5 用例结果上报：testCaseResultReport**

甲方期望：每个用例完成后上报 result（success/fail/tbd）+ loopIndex。

我们的 result MVP：`judgeCaseVerdict` → "passed"/"failed"/"stopped"

**映射：**
- "passed" → "success" ✓
- "failed" → "fail" ✓
- "stopped" → "tbd"（需确认：用户主动 stop 算 tbd 还是 fail？）

**需要的能力：**
- 用例粒度的完成事件（不是 task 级 onSettled，而是用例级）
- loopIndex 从 task iteration 映射
- result verdict 翻译

**断点：当前 result MVP 只有 task 级 verdict，没有用例级。** 如果一个 task 包含多个用例（按 executionPlan），需要用例级别的结果判断和上报。

**1.6 测试数据文件：testDataFileTranslationComplete**

甲方期望：测试过程中产生的数据文件上传到 FTP，上传完成后通知甲方。

**完全缺失。** 我们的系统没有：
- 测试数据文件生成机制
- FTP 上传能力（platform facade 中无 FTP）
- testDataFileTranslationComplete 通知

**1.7 测试报告：完整 JSON 报告**

甲方期望详细的 JSON 报告文件，包含：
- 任务级结果、时间
- testCaseList：每个用例的 checkPoints、statisticsItems、processAndDatas、testParsInfo
- checkPoints 含 checkPoint/expectValue/testValue/result

**断点：** 我们的 report MVP 是硬编码 `generateReport`，没有：
- checkPoint 数据收集（期望值 vs 实际值的对比）
- statisticsItems 统计项
- processAndDatas 步骤级数据

### Q2: HTTPS 服务放哪里？

**结论：main process 放 HTTP server，renderer 处理业务逻辑，通过 IPC 通信。**

理由：
1. **CLAUDE.md 允许 main 做平台资源访问**（网络监听是平台能力）
2. **CLAUDE.md 禁止 main 承载业务规则**（请求翻译、协议语义在 renderer）
3. 这是项目既有的架构模式——serialport、TCP 连接同理：main 管传输层，renderer 管语义层

**架构切分：**

```
甲方 HTTPS POST
    │
    ▼
main process (HTTPS server + TLS)
    │  ← 只负责：listen、TLS、raw request/response
    │  ← 通过 IPC 把 request body 传给 renderer
    │
    ▼
renderer (via preload facade)
    │  ← 负责：解析请求、翻译为 TaskDefinition、调用 task service
    │  ← 返回响应给 main → 回给甲方
    │
    ▼
task service / result service / ...
```

**库选择建议：Fastify**。理由：轻量、TypeScript 友好、性能好、插件生态足够。Express 也行，没有强偏好。

**需要用户决策的：**
- 是否用自签名证书？（甲方文档写的是 `https://127.0.0.1:5001`，本地通信）
- 是否需要双向 TLS？
- 并发上限？（桌面应用通常 1-2 个连接足够）

### Q3: 翻译层的形状

**结论：northbound feature 内的独立模块，不是 shared/，不是 command-ingress 的一部分。**

理由：
1. **翻译是外部协议特有的**——甲方 JSON 格式 → 内部 TaskDefinition，这个映射只在甲方对接场景出现，不是通用能力
2. **command-ingress 负责另一个外部系统**（SCOE），它不应扩展为通用适配器框架
3. **shared/ 只放纯工具函数**——翻译涉及外部 schema 知识，不是纯函数

**翻译层结构：**

```
northbound feature
  ├── adapter/
  │   ├── inbound-translator.ts    // 甲方请求 → TaskDefinition
  │   │   ├── translateSetTestTask()     // executionPlan + testCaseInfo → steps
  │   │   ├── translateControlAction()   // abort/pause/continue/stop → lifecycle action
  │   │   └── resolveInputPars()         // parId+value → fieldId+fieldValue
  │   ├── outbound-translator.ts   // 内部事实 → 甲方格式
  │   │   ├── buildMsgReport()           // step result → stepInfo[]
  │   │   ├── buildTestCaseResult()      // verdict → success/fail/tbd
  │   │   └── buildTestReport()          // TaskExecutionSummary → 甲方 JSON 报告
  │   └── config.ts                // 映射表：testCaseId→steps、parId→fieldId
```

**翻译是双向的**：入站（甲方请求 → 内部）和出站（内部事实 → 甲方格式）都需要，但两方向独立、不对称。

**关键设计问题（需要用户决策）：**

1. **用例映射表从哪来？**
   - 方案 A：用户在 UI 手动配置（testCaseId → 帧操作序列的映射）
   - 方案 B：从甲方用例 JSON 导入，用户补充帧映射
   - 方案 C：预置一批标准用例，甲方直接引用
   
2. **executionPlan 并行层如何处理？**
   - 方案 A：一个 task 一个用例，多层 → 多个 task 实例，上层管理串并行
   - 方案 B：扩展 TaskDefinition 支持 step-group 并行
   - 方案 C：runtime 层管理多个 task 实例的串并行编排

### Q4: 与现有 command-ingress 的关系

**结论：独立 feature，复用模式但不共享实现。**

对比：

| 维度 | command-ingress (SCOE) | northbound (甲方) |
|------|----------------------|------------------|
| 传输层 | 串口/TCP 字节流 | HTTPS JSON |
| 协议 | SCOE 自定义二进制 | RESTful JSON |
| 命令模型 | 6 种固定功能码 | 4 类入口（任务/控制/查询/保活） |
| 任务翻译 | command → TaskDefinition | setTestTask → TaskDefinition |
| 确认机制 | 发确认帧 | HTTPS 响应 |
| 生命周期 | 无（单次命令） | 有（sessionId、多批次、控制） |

**两者共用的模式：**
- 外部请求 → 翻译 → TaskDefinition → task service
- 这正是架构文档定义的"接入层"模式

**两者不应该合并的原因：**
- 协议完全不同，合并会增加耦合
- SCOE 和甲方是两个独立外部系统，各自演进
- 甲方有 session 生命周期、多批次拼装等 SCOE 没有的概念
- CLAUDE.md 明确说 northbound 是独立边界

**建议：两套协议长期共存。** command-ingress 继续服务 SCOE 场景，northbound 作为新 feature 处理甲方对接。两者最终都翻译为 TaskDefinition 交给 task service。

**核心闭环有 3 个重大断点：**

4. **abort vs stop 是否有语义差异**（影响 controlTestTask 翻译）
5. **用户主动 stop 对应甲方 result 是 tbd 还是 fail**
