## 审查维度

### A. 跨 feature 类型重复与合并机会

检查以下模式：
- 相同或高度相似的 interface/type 在多个 feature 中各自定义了一份（如 SendResult 被多处 clone、ConditionMatchInput 与 receive 的类型关系）
- 可以下沉到 shared/ 的通用工具函数（比较函数、格式化、clone 模式）
- feature A 的 core 依赖了 feature B 的内部类型（应该只依赖 public API）

### B. Adapter / Fake 模式一致性

检查：
- 各 feature 的 fake adapter 是否遵循相同模式（构造参数、结果队列、call recording）
- fake adapter 的默认值是否硬编码了不必要的魔法值
- real adapter 与 fake adapter 的接口契约是否完全对齐

### C. 跨 feature 隐式耦合

检查：
- 一个 feature 是否 import 了另一个 feature 的非 public API 路径（如 core/state/services 内部）
- 运行时是否有通过类型断言 `as` 绕过接口边界的情况
- 是否有 feature 直接操作另一个 feature 的内部状态

### D. 内部代码质量

对每个 feature 独立检查：
- core/ 是否有 Vue/Pinia/Electron 依赖（禁止）
- 是否有 `as` 类型断言可以消除
- 重复的 helper 函数（同一 feature 内部多份相同逻辑）
- 过长的单文件（>500 行）是否需要拆分建议
- 是否有 TODO/FIXME 标记未追踪

### E. Public API 边界完整性

检查：
- index.ts 导出的类型是否完整（有遗漏的公开类型）
- index.ts 是否泄露了内部实现（mutable state、fake、具体类实例）
- selector 返回的是否都是 immutable snapshot
