## 讨论点

### 1. 三个子 feature 的拆法和边界

当前规划给出的三个子 feature：
- **PF-1：TCP/UDP transport**（main handlers + preload bridge + facade + adapter）
- **PF-2：文件系统桥接**（文件读写、目录、对话框、路径解析）
- **PF-3：facade API 收敛**（清理 API 表面、统一能力注册）

**问题 A**：PF-1 的 adapter 层（connection adapter）是 platform-expansion 的范围还是 connection-complete 的范围？

我的判断：adapter 层应该留在 connection-complete。platform-expansion 的 PF-1 只负责 **main handlers + preload bridge + platform facade**，即让 renderer 能通过 facade 调用 TCP/UDP 能力。adapter 将 facade 包装成 `ConnectionTransportAdapter` 是 connection feature 的工作。理由：
- platform 不应该知道 connection 的 adapter 接口
- 当前串口 adapter 也在 connection feature 里，不是在 platform 里
- 保持了 platform 和 feature 的单向依赖

**问题 B**：PF-3（facade API 收敛）是否应该和 PF-1/PF-2 合并，还是作为独立子 feature？

两种选项：
- **合并**：PF-1/PF-2 做完时自然收敛，不需要独立子 feature
- **独立**：旧 API 表面清理、`RewritePlatformCapability` 扩展、bridge 注册统一化等工作量足够独立

我的倾向：**作为 PF-1/PF-2 的验收条件之一**，不独立为子 feature。每次加新能力时，同步扩展 `RewritePlatformCapability`、统一 bridge 注册模式、确保 API 表面一致。额外单开一个子 feature 收益不高。

### 2. TCP/UDP facade 设计：统一还是分立？

当前 `TransportBridge` 只有串口方法（`enumerateSerialPorts`、`connectSerial`）。有两种扩展方式：

**方案 X：统一连接方法**
```ts
interface TransportBridge {
  connect(config: TransportConfig): Promise<TransportCommandResult>
  disconnect(connectionId: string): Promise<TransportCommandResult>
  write(connectionId: string, bytes: Uint8Array): Promise<TransportCommandResult>
  enumerateResources(kind: TransportKind): Promise<...>
  // ...
}
```
- 优点：多态，adapter 不需要知道 transport 类型
- 缺点：`TransportConfig` 需要是 discriminated union，main 侧需要 type switch

**方案 Y：分立连接方法**
```ts
interface TransportBridge {
  // serial
  enumerateSerialPorts(): Promise<...>
  connectSerial(config): Promise<...>
  // TCP
  connectTcp(config): Promise<...>
  listenTcp(config): Promise<...>
  // UDP
  connectUdp(config): Promise<...>
  // shared
  disconnect(connectionId: string): Promise<...>
  write(connectionId: string, bytes: Uint8Array): Promise<...>
}
```
- 优点：类型安全、和现有串口模式一致
- 缺点：每加一种 transport 就扩展 interface

我的倾向：**方案 X 的变体**——`connect(config: TransportConfig)` 统一入口，`disconnect`/`write` 按 connectionId 多态。理由：
- connectionId 已经是连接的唯一标识，不关心底层类型
- 和 `ConnectionTransportAdapter` 的 `connect(config: ConnectionConfig)` 模式一致
- main 侧的 type switch 是不可避免的（socket 创建方式不同），但只在这一处
- `enumerateResources` 只对串口有意义（TCP/UDP 没有可枚举硬件资源），可以用 optional 方法处理

### 3. 文件系统桥接的范围

旧系统文件能力有四层，需要明确哪些是 platform 范围：

| 能力 | 旧位置 | 是否 platform 范围 | 理由 |
|---|---|---|---|
| 基础文件读写（readFile/writeFile） | fileMetadataHandlers | **是** | 纯平台能力 |
| 目录操作（mkdir、list） | fileMetadataHandlers | **是** | 纯平台能力 |

| 历史时序数据（HistoryDataHandler） | historyDataHandlers | **部分** | gzip 压缩/文件 rotation 是平台，CSV 生成/时桶分桶是业务 |

**问题 C**：PF-2 文件系统桥接的范围到哪里？

我的判断：**PF-2 只做基础文件能力**：
- 文件/目录读写
- 系统对话框
- 路径解析（userData、resolve、isPackaged）
- 文件流式写入（stream append）——这是高速存储的前置依赖
- 文件 rotation（按大小/时间的文件轮转）——可选，可以作为存储 feature 的内部实现

不做的：
- 任何领域语义的文件操作（配置 CRUD、CSV 导出、时桶分桶）
- 高速存储的帧头匹配和协议解析
- import/export 业务语义

### 4. 依赖顺序

```
PF-2 文件系统桥接 ─┐
                    ├─→ PF-3 facade 收敛（验收条件）
PF-1 TCP/UDP ──────┘
```

PF-1 和 PF-2 **没有相互依赖**，可以并行。PF-3 是两者的验收条件。

但考虑到实际执行：
- PF-1 是 connection-complete 的前置，优先级更高
- PF-2 的消费者是 storage-real 和后续的 report/northbound，时间窗口更宽

### 5. 不确定的点

1. **TCP Server 多客户端管理**：旧系统支持 TCP Server 模式（一个 listener 多个 client）。这个在 connection-complete 的 scope 内还是 platform-expansion 的 scope 内？如果 connection 只管理到"一个连接"粒度，那 TCP Server 的 listener 和 client 连接映射需要提前设计。

2. **高频数据缓冲策略**：串口已有 batch+queue+overflow。TCP/UDP 的数据模式不同（可能更高频、更大包），是沿用串口策略还是需要独立的背压参数？

3. **文件流式写入**：高速存储用 stream append 写二进制。这个能力是放在 platform 还是作为存储 feature 的 adapter？如果是 platform，需要定义 stream 写入的 bridge 接口；如果留给 feature，platform 只提供基础 writeFile。

389	## 四、十一个业务流程详细描述
390	
391	AI 对每个流程做了详细描述，用户确认后进行了多轮纠正。
392	
393	### Flow 1：设备连接管理
394	
395	**是什么**：管理上位机和被测设备之间的物理连接。是所有数据流的底层依赖。
396	
397	**涉及传输类型**：串口、TCP client、TCP server、UDP。
398	
399	**完整过程**：
400	1. 用户在连接页面选择传输类型（串口/TCP/UDP）
401	2. 选择或输入目标参数（串口：端口+波特率；TCP client：IP+端口；TCP server：监听等待设备连入；UDP：绑定本地端口+对端地址）
402	3. 点击连接 → connection service 通过 adapter 调用 platform transport → 建立物理连接
403	4. 连接成功后进入"已连接"状态，成为后续收发的 target
404	5. 持续监听连接状态（意外断线、设备热插拔）
405	6. 意外断线时：检测到 → 状态变为"已断开" → 可选自动重连策略 → 通知上层
406	7. 用户主动断开 → 清理资源 → 状态变为"空闲"
407	8. 支持同时存在多个连接
408	
409	**产出**：一组活着的连接，每个有 ID、状态、配置。
410	
411	### Flow 2：遥测接收
412	
413	**是什么**：从已建立的连接接收设备上报的遥测数据，解析出具体参数值并存储。
414	
415	**涉及传输类型**：串口、TCP/UDP。
416	
417	**完整过程**：
418	1. 设备通过已建立连接主动上报数据（字节流）
419	2. main 侧串口/网络 handler 收到原始字节 → 批处理缓冲 → 通过 preload bridge 推到 renderer
420	3. routingTick 定期排空 connection 的事件队列
421	4. routingTick 识别这是遥测数据，分发到 receive 路径
422	5. receive service 处理：帧匹配 → 字段解析 → 归一化
423	6. 解析成功的参数值存入 receive read model
424	7. 如果参数值满足预设触发条件，emit 条件匹配事件
425	8. 条件匹配事件可以被 task service 消费
426	
427	**产出**：当前参数最新值（read model）、条件匹配事件、接收统计。
428	
429	### Flow 3：遥控发送
430	
431	**是什么**：通过已建立的连接向设备发送控制指令。
432	
433	**涉及传输类型**：串口、TCP/UDP。
434	
435	**完整过程**：
436	1. 触发来源：用户手动操作，或任务步骤自动触发
437	2. send service 处理：帧构造 → 目标解析 → 传输写入
438	3. 返回发送结果：成功/失败
439	
440	**产出**：发送结果。
441	
442	### Flow 4：SCOE 协议处理（后被重命名为"指令接入"）
443	
444	**是什么**：SCOE 是一套专门的设备控制协议。**后经用户纠正，SCOE 和新甲方统一为"指令接入"模块。**
445	
446	**涉及传输类型**：TCP/UDP（网口）。
447	
448	**完整过程**（按纠正后的理解）：
449	1. 外部系统（SCOE TCP / 新甲方 HTTPS）发指令给我们
450	2. connection adapter 接收（不同传输，同一层）
451	3. 指令解析（各自协议格式）
452	4. 翻译成内部动作（大多情况：生成一个 task 去执行）
453	5. task system 执行
454	6. 结果回传给外部系统
455	
456	**特殊点**：入站 bypass receive，走指令接入路径。
457	
458	### Flow 5：任务执行
459	
460	**是什么**：自动化测试的核心。
461	
462	**完整过程**：
463	1. 用户创建/选择任务定义（步骤、执行模式）
464	2. 启动 → 创建任务实例，状态"执行中"
465	3. 按执行模式进入循环（定时/触发/序列）
466	4. 每步骤执行（send / wait-condition / delay / SCOE）
467	5. 所有步骤完成 → 任务完成 → 汇总结果
468	6. 异常处理（步骤失败策略、超时策略、手动停止）
469	7. 完成后交给 result 处理
470	
471	**产出**：任务执行结果。
472	
473	### Flow 6：结果收集
474	
475	**是什么**：把任务执行过程数据收集归口。
476	
477	**完整过程**：task 完成步骤 → emit 步骤结果 → task 整体完成 → emit 任务完成事件 → result 收集步骤结果、参数快照、汇总信息。
478	
479	**产出**：结构化测试结果数据。
480	
481	### Flow 7：数据存储
482	
483	**是什么**：持久化存储遥测参数历史、任务结果等。
484	
485	**注意**：用户确认不需要兼容旧格式，新系统从零开始。
486	
487	### Flow 8：帧定义管理
488	
489	**是什么**：定义系统中所有帧的结构——解析和构造的"字典"。
490	
491	**注意**：用户确认新系统重新定义格式（JSON），旧数据写迁移脚本。帧定义全局唯一，不存在第二套帧结构。
492	
493	### Flow 9：报告生成
494	
495	**是什么**：根据任务结果按甲方要求格式生成测试报告。
496	
497	### Flow 10：北向交付
498	
499	**是什么**：把结果/报告推给甲方系统（HTTPS）。
500	
501	### Flow 11：系统设置
502	
503	**是什么**：管理应用各类配置。

507	## 五、SCOE 重命名为"指令接入"
508	
509	### 用户的纠正
510	
511	用户原话：
512	
513	> SCO其实和新甲方他们一样，指令码（新甲方是https接口）控我们，可能是跟新甲方任务一样，发一系列遥控帧，可能是运维方面，可能是什么乱七八糟的（这些感觉都可以算到任务？毕竟触发源一样，中间过同一处之后分开）。所以我一直觉得，SCOE得改个名字，叫什么都行，然后SCOE和新甲方都是这里面一部分
514	
515	用户原话：
516	
517	> SCOE那块，当时我弄的就比较接近现在任务希望的，不过弄的挺乱的，搞了独立帧列表，独立的条件啥的，一堆乱七八糟的，这都得好好分解，想想哪里需要什么
518	
519	### 架构纠正
520	
521	之前的理解（有问题）：
522	- SCOE = 独立 feature，有 bypass receive 特殊路径
523	- 北向 = 独立 feature，HTTP/FTP 交付
524	- 两者不相关
525	
526	纠正后的理解：
527	- **指令接入 feature**：统一收 SCOE + 新甲方，解析外部命令，翻译成内部动作（通常是 task），执行后回应。传输层差异只是 adapter 不同。
528	- **北向交付 feature**：我们把结果/报告主动推给外部系统。这是出站方向，和指令接入是两个独立能力。
529	- SCOE 的"bypass receive"不再是架构例外——它根本就不走 receive 路径，它走的是指令接入路径。
530	
531	三条路在 routingTick 层分流，各走各的：
532	- 遥测走 receive
533	- 遥控走 send
534	- 外部指令走指令接入
535	
536	### 指令接入内部的分发
537	
538	大多数外部指令进来后是"发一系列遥控帧 + 等条件"，和手动创建的 task 结构一样。但有几类可能不是 task：
539	- 查询类：外部系统问"当前设备状态" → 直接返回 read model 快照
540	- 运维类：重连、重启采集、清理数据 → 直接调对应 service
541	- 纯控制类：立即发一帧，不等待条件 → 可能就是一个 send
542	
543	指令接入 feature 的设计：解析完命令后根据命令类型分发到不同处理器——task 只是其中一种处理器。feature 保留分发权，具体执行委托给已有 feature（task / send / connection / storage）。

547	## 六、五大风险识别
548	
549	AI 提出了五个"不修后面必炸"的问题，用户基本认可。
550	
551	### 风险 1：routingTick 无背压
552	
553	routingTick 是同步 drain 模型。一个 tick 里可能积了几百个 batch，receive 解析同步阻塞，整个链路在同一个微任务里跑完。
554	
555	经用户纠正后降级：routingTick 本身只是轻量分发，重的活在各自 context 里跑。真正要注意背压的是 receive 解析那一环。
556	
557	**建议**：B 组预留背压和分批处理口子，routingTick 内部按预算截断。
558	
559	### 风险 2：无断线重连
560	
561	connection service 能连能断，但断线后没有自动重连闭环。
562	
563	**建议**：在 connection 实现时一起做，指数退避 + 用户可感知的状态。
564	
565	### 风险 3：Bridge 胶水膨胀
566	
567	当前四个 bridge 是手写薄适配器。后面加 SCOE→task、task→result、result→report 等每条交互路径都多一个 bridge 文件。
568	
569	**建议**：不提前做框架，观察重复模式后考虑提取 `drainBridge(producer, transform, consumer)` 工具函数。
570	
571	### 风险 4：Storage 和 Result 是完全空壳
572	
573	正常，先铺骨架后填肉。但 E 组工作量可能比预期大。
574	
575	### 风险 5：无端到端集成测试路径
576	
577	330+ 单元测试覆盖 feature 内部逻辑，但没有"fake adapter → routingTick → receive → task → send → result"的端到端测试。
578	
579	**建议**：A 组完成后立刻补一条端到端集成测试，后续每组扩展。

583	## 七、表达式引擎 — 最关键的共用件
584	
585	### 用户的深入说明
586	
587	用户原话：
588	
589	> 表达式这个，应该是和发送那边一模一样吧？都是放到共用那边的，两边用的时候就几行？
590	
591	用户原话：
592	
593	> 但表达式里面可能用到各种东西，比如发送的时候，可能用到当前帧参数，可能用到遥测（可视化）那边维持的参数，可能用到一些全局的参数（比如时间啥的），那它是作为一个功能模块？不然shared里不方便获取这些吧？还是说打算全部外部传入？也不是不行。
594	
595	用户原话（关于表达式的问题细节）：
596	
597	> 接一个帧，它里面可能有表达式运算（这个发送、接收都有，而且之前写的不好，这个必须考虑变量先后顺序，比如前面变量算完了，后面得用算完的接着算，而不是算之前的，还得考虑性能。总之之前写的很烂，来回打了不少补丁）
598	
599	### 表达式引擎的使用场景
600	
601	用在：
602	- **接收**：帧内字段值经过表达式计算得到最终参数值
603	- **发送**：用户填的参数值经过表达式计算得到要写入帧的字节
604	- **任务**：条件判断、步骤参数填充
605	- **指令接入**：外部命令参数翻译
606	- **报告**：统计计算
607	
608	### 核心难点
609	
610	**变量依赖顺序**：A 表达式算完得出值，B 表达式依赖 A 的结果，必须用 A 算完后的值继续算，不能用原始值。加上性能要求，这不是简单 eval，需要正经的求值器。
611	
612	### 表达式变量的来源
613	
614	- 当前帧参数（本帧上下文）
615	- 遥测当前值（receive 的 read model）
616	- 全局参数（时间、系统计数器等）
617	
618	### 设计决策：纯函数 + 外部传参
619	
620	路线 B（全部外部传入）胜出。表达式引擎是 shared/ 纯函数：
621	
622	- 输入：一堆变量（Map<name, value>）+ 一堆表达式文本
623	- 输出：按依赖排序求值的结果
624	- 引擎不管变量从哪来，调用方自己收集
625	
626	调用方知道需要哪些变量源：
627	- send service 调用表达式时：读 receive selector（公开只读）+ 读 settings（公开只读）+ 本帧上下文（自己的）
628	- 不存在"表达式引擎反向依赖 receive/send/settings"的问题
629	
630	变量命名空间约定：`$遥测.温度`、`$本帧.系数`、`$global.时间`，在帧定义里约定，引擎按名字查 map。
631

634	## 八、接收管线 — 比预期复杂得多
635	
636	### 用户的深入说明
637	
638	用户原话：
639	
640	> 最需要慎重考虑的就是接收。比如接一个帧，它里面可能有表达式运算……然后可能得更新星座图（演示这些，比如表格、折线图、星座图啥的，你是不是忘了？星座图特殊，还得单独记，别的考虑到存储也是有些麻烦，容易爆炸），得更新表格，可能触发别的发送一帧或者一个任务里某个步骤推进或者触发别的什么；然后表达式不仅是帧内参数，别的地方也都有很多。
641	
642	### 正确的接收管线
643	
644	```
645	收到字节 → 帧匹配 → 提取原始字段
646	  → 表达式求值（带依赖排序）
647	  → 得到最终参数值
648	
649	最终参数值出来之后，多条岔路同时走：
650	  ├→ ① 存参数值（read model，当前最新值）
651	  ├→ ② 更新可视化：
652	  │     - 表格（参数值填进表格行）
653	  │     - 折线图（参数值追加到时间序列）
654	  │     - 星座图（特殊 — 需要单独记录 I/Q 采样点，数据量大，存储策略不同）
655	  ├→ ③ 存历史（持久化，但要控制量，容易爆炸）
656	  ├→ ④ 检查条件匹配 → 可能触发：
657	  │     - 发一帧（立即 send）
658	  │     - 推进任务步骤
659	  │     - 触发其他什么
660	  └→ ⑤ 如果没匹配到任何已知帧 → 记录为未匹配
661	```
662	
663	这不是"receive feature 内部的事"，输出扇出到好几个地方：可视化（UI 层）、存储（持久化层）、条件匹配（task 层）、直接触发 send（send 层）。
664	
665	### 星座图特殊性
666	
667	- 普通参数：一个帧一个值，数据量可控
668	- 星座图：一个帧可能带几十到几百个 I/Q 采样点，高频帧一秒几十帧，数据量爆炸
669	- 不能和其他参数用同一个存储策略，必须有独立的采样/存储/清理机制
670	
671	### 接收管线的五个子问题
672	
673	1. 帧匹配 + 字段提取（依赖帧定义）
674	2. 表达式求值（依赖 shared 表达式引擎）
675	3. 参数值存储（read model + 持久化，持久化策略要考虑数据量控制）
676	4. 可视化数据管道（表格/折线图/星座图各自不同的数据形态）
677	5. 条件匹配 + 副作用触发（send / task step / 其他）

681	## 九、最终模块划分
682	
683	### 用户的纠正原则
684	
685	用户原话：
686	
687	> 表达式这个，应该是和发送那边一模一样吧？都是放到共用那边的，两边用的时候就几行？然后，整个系统，帧的结构不应该出现第二个？这样所有地方都能通用一套工具（我怀疑你之前没遵守这个）。存储则是单独模块，接收这边调用而已。可视化同样是单独模块，条件触发我觉得也算单独的？毕竟，输入很多（接收、发送、别人给的都可以算做这个？），输出很多（感觉这些都能统一，但也可能是我想错了）
688	
689	### 纠正后的归属
690	
691	- **表达式引擎**：shared/ 纯工具，两边调用就是几行
692	- **帧结构**：全局唯一，不存在第二个帧模型
693	- **存储**：独立模块，receive 只是调用方
694	- **可视化**：独立模块
695	- **条件匹配**：分两层——匹配逻辑（shared/ 纯函数）+ 触发行为（各 feature 自己管）
696	
697	### 条件匹配的两层分离
698	
699	**匹配层（shared/ 纯函数）**：
700	"这个事件满不满足这个条件？"——纯逻辑，无状态。接收参数值 > 阈值、发送结果 == 失败、外部命令类型 == 某个值，底层都是"输入事实 + 条件定义 → 是否匹配"。
701	
702	**触发层（各 feature 自己管）**：
703	"匹配了之后干嘛？"——业务语义，每个 feature 不一样：
704	- task 的 wait-condition 步骤：匹配了 → 推进当前步骤
705	- 指令接入：匹配了 → 回应外部系统
706	- 发送失败重试：匹配了 → 重新发送
707	
708	不统一也不应该统一——统一了就是事件总线，架构明确禁止。
709	
710	### 最终模块全景
711	
712	| 模块 | 性质 | 核心职责 | 被谁消费 |
713	|------|------|---------|---------|
714	| **表达式引擎** | shared/ 纯工具 | 带依赖排序的表达式求值 | receive、send、task、指令接入、报告 |
715	| **帧定义** | frame feature | 唯一帧模型，解析+构造 | receive、send、指令接入、task 引用 |
716	| **条件匹配** | shared/ 纯工具 | 事实 + 条件 → 是否匹配 | task、指令接入、任何需要条件判断的地方 |
717	| **connection** | connection feature | 传输管理，串口/TCP/UDP adapter | receive、send、指令接入 |
718	| **receive** | receive feature | 帧匹配→表达式求值→产出参数事实→分发 | 给可视化/存储/条件匹配提供输入 |
719	| **send** | send feature | 参数+帧定义→构造字节→写入连接 | task、指令接入、条件触发 |
720	| **task** | task feature | 步骤序列执行引擎 | 手动任务、指令接入触发 |
721	| **指令接入** | 指令接入 feature | 接收外部命令→翻译→分发执行→回应 | SCOE、新甲方 |
722	| **storage** | storage feature | 持久化+查询+导出+清理策略 | receive 存参数、task 存结果、报告存文件 |
723	| **可视化** | visualization feature | 表格/折线图/星座图数据管道+渲染 | receive 推送参数数据 |
724	| **result** | result feature | 结果收集+归口 | task 产出、报告消费、指令接入回应 |
725	| **报告** | report feature | 按模板生成报告文件 | result 输入、北向交付消费 |
726	| **北向交付** | northbound feature | HTTPS 推送结果/报告给外部 | report 输出 |
727	| **settings** | settings feature | 配置管理 | 所有 feature |

731	## 十、跨模块交互 — 旧 store 教训与新架构
732	
733	### 用户的核心担忧
734	
735	用户原话：
736	
737	> 不同模块之间怎么跨模块交互。我之前是全部用的store，结果就是成一坨屎山了。新的架构说实话我没咋看，也不知道行不行，挺担忧的。
738	
739	### 旧系统怎么烂的
740	
741	```
742	Feature A 的 store ← Feature B 直接 import 并读写
743	Feature B 的 store ← Feature C 直接 import 并读写
744	Feature C 的 store ← Feature A 直接 import 并读写
745	```
746	
747	结果：没有单向数据流、没有 owner、没有边界、没法测试。
748	
749	### 新架构的四种合法跨模块交互方式
750	
751	**1. 调用 public service（命令）**
752	```
753	task 调 sendService.sendRequest({ frameId, targetId, params })
754	```
755	task 不知道 send 内部怎么实现，只知道 public API。
756	
757	**2. 读 public selector（只读查询）**
758	```
759	send 读 receiveSelector.getCurrentValues()
760	```
761	send 需要遥测当前值来算表达式，通过 receive 暴露的只读 selector 拿。send 只能读不能改。
762	
763	**3. Bridge（runtime 接线）**
764	```
765	receive 产出事件 → runtime 通过 bridge 转换格式 → task 消费
766	```
767	receive 和 task 互不知道。runtime 在中间接线。
768	
769	**4. 显式事件（高频/异步场景）**
770	```
771	receive emit 条件匹配事件 → receiveEventSourceBridge → task condition registry
772	```
773	
774	### 旧 store vs 新架构对比
775	
776	| | 旧 store | 新架构 |
777	|---|---|---|
778	| 谁写 | 谁都能写 | 只有 owner feature 写 |
779	| 谁读 | 直接 import store | 通过 public selector（只读） |
780	| 跨 feature 通信 | A 写 B 的 store | service 调用 / bridge / 事件 |
781	| 数据流方向 | 双向乱串 | 单向：producer → bridge → consumer |
782	| 改一个 feature 影响 | 不可预测 | 只影响消费它 public API 的地方 |
783	
784	### 四个真实风险
785	
786	**风险 1：selector 返回可变引用**
787	selector 必须返回深拷贝或 readonly 冻结对象，否则消费方一个 `.push()` 就绕过保护。
788	
789	**风险 2：bridge 里塞业务逻辑**
790	bridge 应该只做格式转换。如果开始做"判断要不要转发"、"根据条件选择路由"，就成了隐式业务逻辑。
791	
792	**风险 3："我就读这一个值"的诱惑**
793	开发中容易想直接 import 内部 state。一次破例变成两次、三次。防御：feature 内部文件不从 public.ts 导出，外部 import 不到。
794	
795	**风险 4：runtime 膨胀**
796	runtime 是唯一知道所有 feature 的地方。如果开始做业务判断，就成了新的屎山中心。runtime 必须只做接线不做判断。

847	### 12.2 旧系统调研结论
848	
849	#### 表达式引擎（旧代码 1385 行核心）
850	
851	已有机制：
852	- Kahn 算法拓扑排序解决变量顺序问题（O(V+E) 时间复杂度）

866	- 必须保留：Kahn 拓扑排序、configHash 缓存失效、数学函数简化绑定
867	- 必须消灭：store 依赖、无预编译、并行计算
868	- 必须：解析和求值分离、纯函数化、支持预编译

957	## 十三、全局原则总结
958	
959	1. **传输层是一个整体**：串口、TCP/UDP、HTTPS 都是 connection 的 adapter，不按类型拆阶段
960	2. **帧结构全局唯一**：不存在第二套帧模型，旧 SCOE 独立帧列表必须消灭
961	3. **表达式引擎是 shared/ 纯函数**：带依赖排序的求值器，全部外部传参，不持有状态
962	4. **条件匹配分两层**：匹配逻辑（shared/）+ 触发行为（各 feature）
963	5. **SCOE 和新甲方统一为"指令接入"**：外部系统控我们，走同一套指令接入路径
964	6. **存储、可视化、条件触发是独立模块**：receive 只是调用方，不拥有它们
965	7. **单点写入**：每个状态只有 owner feature 能写，外部只能读 selector
966	8. **runtime 只做接线不做判断**：composition root，不承载业务逻辑
967	9. **main 不装业务逻辑**：只做平台资源和必要的高频性能处理
968	10. **跨模块共用件时刻注意**：最容易耦合深的地方，必须严格通过 public API
969	11. **子 agent 积极使用**：brainstorm 用 explore agent 并行查旧代码和架构文档；design 用 explore agent 确认 public API 对接；impl 拆 executor agent 并行；accept 用独立 verifier agent

## 冲突与遗漏

### 1. 窗口控制是 P0，但 brainstorm 完全没提

规划文档 12.4 P0 阻断项第一条：

> Platform Facade — renderer 无法访问桌面能力（网络/文件/窗口全缺）

窗口控制（close/minimize/maximize/isMaximized）+ 菜单可见性，旧 preload 有完整实现，量很小（5-7 个方法）。但我 brainstorm 时只讨论了 TCP/UDP 和文件系统，漏了窗口。

**修正**：PF-2 应该从"文件系统桥接"扩展为"基础桌面能力"——文件读写/目录/对话框/路径解析 + 窗口控制 + 菜单。这些都不涉及业务逻辑，都是 main 天然承载的平台能力，打包在一起合理。

### 2. PF-3 合并的偏差

规划文档 14.3 明确写 3 个子 feature：

> 3（TCP/UDP main+preload+facade、文件系统桥接、facade API 收敛）

我提出把"facade API 收敛"合并为 PF-1/PF-2 的验收条件。重新审视后，我觉得这个偏差是合理的，但需要说明理由：

- facade 收敛的核心工作是：每次加新能力时同步扩展 `RewritePlatformCapability` 类型、统一 bridge 注册模式、确保 API 表面一致
- 这不是独立可交付的工作，而是做 PF-1/PF-2 的**过程中自然完成**的事
- 单独开一个子 feature 容易变成"最后统一收口"，反而拖延

**但需要确认**：你是否同意合并？还是觉得 facade 收敛有独立价值（比如删除旧 API 表面、统一错误处理模式、capability 发现机制等）？

### 3. HTTP transport 的扩展路径没讨论

规划文档 Wave 6 northbound 依赖"platform HTTPS 能力"。当前 transport 架构是 `TransportBridge`，只管串口/TCP/UDP。未来 HTTPS 作为 transport adapter 接入时，facade 需要能扩展。

**如果现在用统一 connect 方案**（方案 X），未来加 HTTPS transport 只需要：
- 新增 `HttpsTransportConfig` 到 discriminated union
- main 侧加一个 HTTPS handler
- facade 层零改动（connect 已经是多态的）

**如果用分立方法方案**（方案 Y），未来需要改 interface 加 `connectHttps`。

这是方案 X 的一个额外优势——对后续 northbound 的扩展更友好。

### 4. TCP Server 多客户端的边界不清

Flow 1 明确有 TCP Server 模式："监听等待设备连入"。Flow 4 指令接入也涉及 TCP Server（外部系统连接到我们）。

问题：TCP Server 的 listener 和 client 连接映射，边界在哪？

- **platform 层**：负责创建 `net.Server`、监听、accept 新连接、给每个 client 分配 connectionId、关闭 listener
- **connection 层**：负责把 listener + 多个 client 连接作为独立的 `ConnectionTransportAdapter` 实例管理

这个拆分合理，但 platform 的 TCP Server handler 需要在 listener accept 新 client 时 emit 一个特殊事件（类似"新连接接入"），让 connection 层知道要创建新 adapter。这个事件设计需要在 PF-1 design 阶段明确。

### 5. 现有串口接口迁移路径

当前 `TransportBridge` 有串口专属方法：`enumerateSerialPorts()`、`connectSerial()`。

如果走统一方案，需要：
1. 新增 `connect(config: TransportConfig)` 通用方法
2. 保留 `enumerateSerialPorts()` 作为串口专属（只有串口有可枚举硬件资源）
3. `disconnect`/`write`/`cleanup` 已经是通用的（按 connectionId）
4. **迁移**：`RealSerialAdapter` 从调 `connectSerial` 改为调 `connect({ kind: 'serial', ... })`

这个迁移影响面不大（只有 `RealSerialAdapter` 一个消费者 + preload 一处实现），但需要作为 PF-1 checklist 的一项。

## TCP/UDP 平台能力 — 范围说明

### 做完之后能干什么

renderer 里可以通过 platform facade 建立 TCP 和 UDP 连接，收发数据。和现有串口一样：main 管真实 socket，preload 桥接，facade 暴露干净 API。

connection feature 拿到这个能力后，就能创建 TCP/UDP 的 transport adapter，和串口 adapter 并列使用。

### 要做什么

四层，每层的工作：

**第 1 层：main process — `network-handlers.ts`（新建）**

用 Node.js 的 `net` 和 `dgram` 模块管理真实 socket。参考旧系统 `networkHandlers.ts` 但去掉业务逻辑。

- **TCP Client**：连到远程 IP:Port，收发数据，断开
- **TCP Server**：监听本地 IP:Port，接受外部连入，给每个连入客户端分配 connectionId，收发数据，关闭
- **UDP**：绑定本地端口，向目标发数据，收数据，关闭
- **数据批处理**：复用串口已有的 batch/queue/overflow 策略，TCP/UDP 参数可能不同
- **IPC channel**：注册到 `ipcMain`，供 preload 调用

**第 2 层：preload — 扩展 `TransportBridge`（改现有）**

在现有 `transportBridge` 对象上新增方法，每个方法转发到 main 的 IPC channel。

现有的 `enumerateSerialPorts` / `connectSerial` 保留不动。新增 TCP/UDP 的连接方法。

**第 3 层：shared 类型 — 扩展 `platform-bridge.ts`（改现有）**

在 `TransportBridge` 接口上新增 TCP/UDP 相关方法签名。类型已存在（`TcpClientTransportConfig` 等），只需要把接口对齐。

**第 4 层：facade — 扩展 `TransportFacade`（改现有）**

在 `TransportFacade` 上暴露新的连接方法。`RealSerialAdapter` 做一个小迁移：从调 `connectSerial` 改为调新的统一 `connect` 方法。行为不变，只是走新的入口。

### 不做什么

| 不做 | 理由 |
|---|---|
| TCP/UDP adapter（connection 层的 `RealTcpAdapter`） | 这是 connection-complete 的范围 |
| 断线重连 | connection-complete 的范围 |
| 文件系统、窗口控制、对话框 | Wave 5-7 按需做 |
| HTTP/FTP | northbound (Wave 6) 的范围 |
| 旧系统业务逻辑（帧头匹配、存储路由） | main 不承载业务逻辑，硬规则 |
| UI 页面 | 不在这个 feature 范围 |

### 需要在 design 阶段定的决策

1. **接口是统一还是分立**：一个 `connect(config)` 万能入口，还是 `connectTcp` / `listenTcp` / `connectUdp` 分开写。影响 facade 和 preload 的 API 长什么样
2. **TCP Server 的事件设计**：外部客户端连入时，怎么通知 renderer（事件格式、connectionId 谁分配）
3. **batch 参数**：TCP/UDP 和串口用同一套默认值，还是各自可配

### 验收标准

- TCP Client：连到真实 TCP Server，收发数据，断开
- TCP Server：监听端口，接受外部连接，给连入客户端收发数据，关闭
- UDP：绑定端口，收发数据，关闭
- 现有串口功能不受影响
- renderer 不直接访问 Node/Electron，全部通过 facade
- main 不包含任何业务逻辑

### 旧代码参考

| 用什么 | 从哪找 | 怎么用 |
|---|---|---|
| TCP/UDP socket 管理 | 旧 `networkHandlers.ts` | 参考 socket 创建、连接、收发的技术实现 |
| 数据批处理模式 | 现有 `serial-handlers.ts` | 复用 batch/queue/overflow 架构 |
| 业务逻辑分离 | 旧 `handleDataReceived()` | **反面教材**——帧头匹配和存储路由不能搬进 main |

- main 侧新建 `http-handlers.ts`，不影响 `network-handlers.ts`
- facade 和 adapter 不需要改动

结论：扩展路径清晰，设计决策正确。

**事实 6：文件系统桥接（Wave 5）的扩展路径。**

文件系统不走 transport 通道，而是独立 bridge section（例如 `FilesystemBridge`）。当前 `RewritePlatformBridge` 只有 `transport` 属性，扩展方式是加一个 `filesystem` 属性。这与 transport 扩展不冲突，`RewritePlatformCapability` 需要加 `'filesystem'`。

design 中 `RewritePlatformBridge` 接口不在本 feature 修改范围（只改 `TransportBridge` 子接口），这个决策是合理的——文件系统是独立 feature，不应该在本设计中预留具体类型。但设计可以提一句扩展方向。

**事实 7：UDP 多目标发送（writeTo）的预留口子。**

design.md D4 明确："多目标发送留给未来 `writeTo()` 扩展"。但 `TransportBridge` 和 `TransportFacade` 接口中没有 `writeTo` 方法签名。

这属于合理的 Out of Scope。未来加 `writeTo` 需要改 `TransportBridge` 接口、preload 路由和 main handler。因为 `writeTo` 是新方法（不是修改现有方法），不会破坏已有代码。

**事实 8：TCP Server 事件的 clientId 生成策略。**

design.md D2 定义：`connectionId = ${serverId}::client:${remoteAddress}:${remotePort}`。

问题：如果同一客户端断开后重连，`remoteAddress:remotePort` 可能相同，产生 connectionId 冲突。这在长期运行中是一个真实的维护痛点。但考虑到当前 TCP Server 用例（SCOE 设备连入），重连频率不高，且 adapter 层（connection-complete 范围）会处理状态管理，当前策略可接受。应作为已知限制在设计中文档化。

---

### 三、维护路径清晰度

**事实 9：preload 路由模式的复杂度。**

design.md Section 5 引入了 `connectionTypes: Map<string, 'serial' | 'network'>` 作为路由表。填充时机有 4 个，清理时机有 2 个：

填充：
1. `connect()` 返回 ok 时（design.md:247-248,251-252）
2. 事件中收到 `connected` 且 role 含 `tcp-server-client`（design.md:234）
3. 隐含：network-handlers 的 listener connected 事件也会触发（因为 `transport:event` 是共享 channel）

清理：
1. `disconnect()` 时（design.md:258）
2. 事件中收到 `disconnected`（design.md:237）

**问题 [风险-2]：TCP Server listener 断开时，client connectionId 可能不在 preload Map 中。**

场景：
1. TCP Server listener 连接成功 -> Map 设 `listenerId -> 'network'`
2. 客户端 A 连入 -> main 推 `connected` 事件 -> preload 收到，设 `clientAId -> 'network'`
3. **如果客户端 A 的 connected 事件丢失**（IPC 在极端情况下可能丢事件），preload Map 中没有 `clientAId`
4. 之后客户端 A 断开 -> main 推 `disconnected` -> preload 收到，从 Map 删 `clientAId`（delete 不存在的 key 不报错，OK）
5. 但如果在第 3 步之前有人调 `write(clientAId, ...)` -> Map 中没有 clientAId -> `type === undefined` -> 走到 `network` 分支（因为 `undefined !== 'serial'`） -> 恰好正确

实际上，设计中的 fallback 逻辑（`undefined` 走 network 分支）在大多数情况下是正确的。但这属于"碰巧对了"而不是"设计对了"。建议在代码中加注释说明这个 fallback 行为是故意的。

**问题 [风险-3]：`cleanup()` 的竞态。**

design.md:276-282 中 `cleanup()` 的实现：

```ts
async cleanup(): Promise<TransportCommandResult> {
  connectionTypes.clear();
  const [serialResult, networkResult] = await Promise.all([...]);
  ...
}
```

`connectionTypes.clear()` 在 IPC 调用之前执行。如果 `Promise.all` 期间有延迟到达的 `disconnected` 事件回调，会尝试 delete 一个已经被 clear 的 Map 中的 key。这不会报错（Map.delete 不存在的 key 是 no-op），但如果有 late-arriving `connected` 事件，就会向已 clear 的 Map 中泄漏一条记录。

建议：cleanup 完成后再次 clear，或者在事件监听器中加一个 `cleanupInProgress` flag。

**事实 10：batch 策略的可维护性。**

design.md D5 选择复用串口 batch 基础设施（maxBatchBytes=4096, maxBatchWindowMs=50, maxQueueDepth=100），TCP/UDP 参数独立可配。

对照 `serial-handlers.ts:26-29`，现有 `BatchConfig` 接口已经定义了这三个参数。network-handlers 需要独立复制这套基础设施。

**问题 [建议-1]：batch 基础设施在 serial-handlers 和 network-handlers 之间重复。**

`serial-handlers.ts:58-87` 的 `flushBatch` + `scheduleBatchFlush` + `cleanupConnection` 是通用 batch 逻辑，与具体的传输类型无关。如果 network-handlers 完全复制一套，未来修改 batch 策略（例如加 backpressure 信号）需要改两个地方。

建议（非阻断）：在设计中标注"batch 基础设施可在后续提取为 main 内部共享模块"，但不影响当前实施。当前复制是合理的——避免在第一个网络 feature 中同时重构串口。

**事实 11：与 connection 层 adapter 的映射清晰度。**

design.md Section 3 映射表标注了 platform bridge config 与 connection feature `TransportConfig` 的对应关系。`real-serial-adapter.ts:105` 当前调用 `transport.connectSerial(...)`，迁移后改为 `transport.connect({ kind: 'serial', ... })`。

`mapBridgeEvent` 函数（`real-serial-adapter.ts:33-78`）中：
- 第 49 行：`kind: event.target.kind as 'serial'` -- 硬编码 cast 为 `'serial'`
- 第 50 行：`role: event.target.role as 'serial-port'` -- 硬编码 cast 为 `'serial-port'`

设计 A2 要求改为 `as TransportKind` 和 `as TransportTargetRole`。对照 `connection/core/types.ts:4,52`，`TransportKind` 和 `TransportTargetRole` 都是 string literal union，这个 cast 是安全的（因为 bridge event 的 `TransportBridgeEventTarget.kind` 和 `role` 类型是 `string`，比 connection 层的 union 更宽）。

但注意：`real-serial-adapter.ts` 只处理串口连接。当 future `RealTcpAdapter` 复制类似逻辑时，`mapBridgeEvent` 需要重新实现。这是 connection-complete 的范围，但当前设计中 `mapBridgeEvent` 的 cast 修复只改了类型安全，没有改变架构。合理。

## 权衡

| 选项 | 优势 | 劣势 |
|---|---|---|
| 统一 connect（当前设计） | 对后续 HTTP 扩展友好；与 connection adapter 模式一致；disconnect/write 已按 connectionId 多态 | preload 路由需要 Map 维护；类型 discriminate 需要在 3 个地方保持一致 |
| 分立 connectTcp/connectUdp | preload 路由简单，无需 Map；每个方法语义明确 | 接口膨胀；加 HTTP 时需要第 N 个方法；与 disconnect/write 的多态模式不统一 |
| serial-handlers 不动 + 新建 network-handlers（当前设计） | 零回归风险；职责清晰 | batch 逻辑重复；main 内部有两个 handler 文件 |
| 提取 batch 共享模块 | 消除重复；统一修改点 | 额外重构风险；本 feature 范围扩大 |

当前设计在所有关键决策点上都选择了更保守的路径（不重构串口、不提取共享模块、统一接口但分立 handler），这在第一个网络 feature 中是合理的。
