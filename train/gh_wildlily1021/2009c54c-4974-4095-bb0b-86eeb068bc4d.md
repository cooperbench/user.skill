## Summary: Connection Feature Boundaries and Interactions

### Connection Feature Boundaries

**What Connection Owns:**
- Transport connection models: serial, TCP, TCP server, UDP remote host
- Connection instances and their state
- Target routing and availability
- Transport send/receive availability
- Connection events and status
- Connection instance and transport state facts

**What Connection Does NOT Own:**
- Northbound `deviceId` or business device identity
- Byte parsing (receive's responsibility)
- Business results or reports
- Task lifecycle management
- Northbound device identity mapping

**Key Boundary Rules:**
- Transport target ≠ business device identity
- Must separate transport availability from business device status
- Connection provides platform IO and necessary buffering only
- Main process only handles platform IO, not business semantics

### Connection Feature Interactions

**Connection → Other Features (Producer):**

1. **Connection → Receive**
   - Fact owner: Connection owns transport/source facts; Receive owns parse facts
   - Interaction: Explicit event, runtime orchestration, selector for source status
   - High frequency: Yes
   - Platform: Yes (main/preload/platform may buffer only, not parse)
   - Key decision: Batch/backpressure boundary and high-speed storage short-circuit behavior

2. **Connection → Send**
   - Fact owner: Connection owns target availability; Send owns send result
   - Interaction: Selector, public service, runtime orchestration
   - Platform: Yes (actual write goes through platform/main)
   - Key decision: Target identity separation from northbound device identity

3. **Connection → SCOE**
   - Fact owner: Connection owns transport; SCOE owns SCOE lifecycle/status
   - Interaction: Runtime orchestration, selector, boundary exception record
   - Platform: Yes
   - Key decision: SCOE fixed TCP/UDP lifecycle owner and exception record

4. **Connection → Status**
   - Fact owner: Connection owns transport truth; Status owns status read model
   - Interaction: Selector, optional explicit event for status changes
   - Platform: Yes (platform is source of transport facts)
   - Key decision: Status refresh/throttle boundary without status owning connection truth

5. **Connection → Display**
   - Fact owner: Connection owns transport truth; Display owns display context projection
   - Interaction: Selector, runtime orchestration
   - Key rule: Display must NOT own connection facts or lifecycle

**Other Features → Connection (Consumer):**

1. **Settings → Connection**
   - Fact owner: Settings owns config; Connection owns runtime transport facts
   - Interaction: Selector, runtime orchestration at init
   - Key decision: Config application timing and rollback/error handling

### Critical Interaction Constraints

**High-Risk Areas:**
- High-speed storage may short-circuit normal receive event stream (must be registered as boundary exception)
- SCOE has fixed TCP/UDP connection requirements (boundary exception)
- Real serial/TCP/UDP hardware validation required for connection operations
- Connection target identity must be separated from northbound business device identity

**Validation Requirements:**
- Real serial port enumeration, connection, disconnect, send/receive and event ordering
- TCP/TCP server/UDP disconnect, reconnect, high-frequency data, remote host changes
- Runtime/hardware validation for all connection operations

**Platform Dependencies:**
- Strong involvement with platform/main/preload
- Main only does platform IO and necessary buffering
- No business semantics in main process

The connection feature serves as the transport layer foundation, providing raw connectivity and data flow capabilities while explicitly avoiding business logic, device identity management, and higher-level protocol semantics.

141	### 4.5 Transport lifecycle, event and error posture
142	
143	Connection lifecycle uses state concepts such as idle, connecting, connected, disconnecting, disconnected and error, but this design does not freeze enum names.
144	
145	Lifecycle rules:
146	
147	- connect / disconnect / cleanup must be idempotent enough for duplicate user actions, stale platform events and app shutdown.
148	- duplicate open/connect, close on already closed resource and app quit cleanup are preserved as observable lifecycle categories, not as exact implementation shape.
149	- changing serial options while connected is deferred; if preserved, close/reopen must be explicit and user-visible enough to validate.
150	- automatic reconnect is not assumed. If later implemented, it must define retry policy, cancellation, UI visibility and runtime/hardware validation in the implementation design.
151	- connection lifecycle events are low-frequency read model updates; high-frequency bytes must use separate batch/delta flow.
152	
153	Error rules:
154	
155	- Transport errors are connection facts until a consumer explicitly interprets them.
156	- Connection may normalize open/connect/listen/bind/write/timeout/close/resource-unavailable categories, but this document does not freeze error code names.
157	- A write failure can be returned to send/SCOE as transport-level material; send/task/SCOE decide business result or lifecycle under their own designs.
158	- A transport error must not directly define result/report/northbound failure semantics.
159	- Error visibility belongs to connection pages/status read model; UI displays sanitized summary, not platform resource internals.
160	
161	High-frequency rules:
162	
163	- Main may buffer, batch, throttle, queue or apply backpressure only for platform-resource or performance reasons.
164	- Main may not classify bytes as frame match, task trigger, SCOE success, result truth, report material or northbound delivery.
165	- connection may normalize source/target and byte availability; receive consumes byte batches and owns parse/match.
166	- UI must consume throttled snapshots and selectors, not raw serial/network event streams.
167	- Queue depth, batch window, overflow/drop policy, target throughput and UI refresh strategy are deferred to implementation/runtime evidence.
168	
169	### 4.6 Public API necessity
170	
171	connection needs a public API because receive, send, task, SCOE, status, pages and runtime all depend on transport availability. This is a boundary rule, not a required file shape and not a schema definition.
172	
173	Allowed capability categories only:
174	
175	- Transport config category: create, inspect, update and validate transport static config through controlled feature entry.
176	- Discovery category: expose available serial resources or transport resources as read-only candidates where platform supports discovery.
177	- Lifecycle command category: request connect, disconnect, cleanup and optional recovery actions.
178	- Target availability category: provide immutable target route, target status and availability snapshot for send/task/SCOE/pages.
179	- Byte input category: publish incoming byte batches or normalized transport input events to receive through runtime or explicit event.
180	- Byte output category: accept transport-level write requests from send/SCOE/runtime and return transport acceptance/failure material.
181	- Lifecycle/error event category: publish transport-level state and error events for status/pages/runtime.
182	- Test adapter category: allow fake serial/TCP/TCP server/UDP adapter substitution without exposing platform/main objects.
183	
184	Explicitly not connection public API:
185	
186	- receive frame match/process/result API.
187	- send frame build/business result API.
188	- task start/pause/resume/stop lifecycle API.
189	- SCOE command/complete/tool-record API.
190	- result/report/northbound projection or delivery API.
191	- mutable store, platform adapter, socket, serialport, raw Electron object, raw channel or DTO schema.
192	
193	### 4.7 Runtime involvement
194	
195	connection requires runtime involvement for application composition and cross-feature routing, but runtime must not own transport semantics.
196	
197	runtime may:
198	
199	- create and release connection service, connection state, fake/real transport adapters and platform subscriptions.
200	- route platform facade events into connection service and ensure listener cleanup.
201	- route connection byte batches to receive without letting receive import connection internals.
202	- route send/SCOE transport write requests to connection public service when the flow spans feature boundaries.
203	- combine read-only connection snapshot with status/page view model.
204	- coordinate cleanup when app exits, page scope closes, profile/settings change, hardware disconnects or stale events arrive.
205	- register boundary exceptions for high-frequency buffer/backpressure, high-speed storage short-circuit, SCOE fixed source/target, package/native-module behavior or optional northbound HTTP/FTP transport.
206	
207	runtime must not:
208	
209	- parse bytes, match frames or process fields.
210	- build send frames or define business send result.
211	- own task lifecycle or retry policy.
212	- interpret SCOE protocol or completion condition.
213	- define result, report, northbound or customer semantics.
214	- become a global service locator or hidden event bus.
215	- directly access Electron, Node, `serialport`, socket handles, file system or raw IPC.
216	
217	### 4.8 Platform / preload / main involvement
218	
219	Platform facade:
220	
221	- Is the renderer-side desktop capability boundary used by connection adapters.
222	- May expose transport primitive capability categories only after connection/platform implementation design accepts them.
223	- Does not own transport config semantics, target identity, receive parsing, send result, task lifecycle, SCOE protocol, result/report/northbound meaning.
224	- Must not reproduce old `src/api/common` as a one-to-one facade.
225	
226	Preload:
227	
228	- Exposes minimal typed bridge capabilities, not `window.electron`, not bare `invoke/send/on`, not arbitrary channel subscription.
229	- May bridge bounded serial/network lifecycle, byte I/O and event delivery after accepted capability design.
230	- Must not expose receive processing, high-speed storage business rules, task/SCOE commands, report semantics or northbound transaction semantics as platform abilities.
231	
232	Main process:
233	
234	- Owns live platform resources: serial port handles, TCP sockets, TCP server handles, UDP sockets, resource cleanup and OS-level I/O.
235	- May retain platform-side buffer, batch, queue, throttle, stream/file write or backpressure only when tied to platform resources or performance pressure.
236	- Must not own frame parsing, receive classification, task state transition, SCOE command/completion, result attribution, report generation, northbound error conversion or business device identity.
237	- Any main-side exception must record why renderer/TypeScript core cannot own it, what main retains, where business semantics live, validation required and exit condition.

239	### 4.9 Cross-feature communication
240	
241	| Consumer / collaborator | May consume from connection | Must not do |
242	| --- | --- | --- |
243	| pages / connection UI | connection config snapshot, lifecycle commands, status/error summary, target list, test workflow entry. | access platform primitive directly, store runtime truth in page snapshot, subscribe to raw transport stream. |
244	| settings | provide defaults or persisted preference input if connection design accepts it. | own connection state, open serial/TCP/UDP, validate runtime availability, map target to northbound device. |
245	| receive | incoming byte batches, source snapshot, lifecycle/error material relevant to input availability. | import connection internal state, parse in connection, decide target availability, write connection facts. |
246	| send | target availability, transport write capability, write failure/acceptance material. | own connection lifecycle, hardcode SCOE/northbound targets, define task/result/report semantics. |
247	| task | target availability snapshot and transport failure material indirectly through send result or runtime. | query raw transport internals to mutate lifecycle, treat connection failure as task truth without task-owned rule. |
248	| SCOE | declared fixed source/target availability and write capability through runtime exception. | make connection own SCOE command semantics, hide SCOE fixed route in generic send/receive internals. |
249	| status | read-only connection summary, lifecycle/error events and transport health material. | own transport truth, import connection internal state, read raw platform resources. |
250	| storage / high-speed storage | only through explicit runtime exception when high-frequency file path is designed. | let connection call storage business rules, let main classify storage semantics without owner/exit condition. |
251	| result / report | no direct connection API in this feature. Future consumers may read transport failure material only through result/report design. | derive result/report truth directly from connection facts. |
252	| northbound | no direct transport target consumption. If external projection later needs connection state, it must go through status/task/result/report/northbound design. | treat serial/network target, TCP client, TCP server client or UDP remote host as customer deviceId. |

254	Allowed interaction patterns:
255	
256	- public service for lifecycle commands, target query and transport write.
257	- read-only selector for config/status/target snapshots.
258	- explicit event for transport lifecycle/error and byte batches when async decoupling or batching is needed.
259	- runtime orchestration for connection + receive, connection + send/SCOE and lifecycle cleanup.
260	
261	Prohibited interaction patterns:
262	
263	- feature A imports connection internal state, adapter, composable, private service or platform bridge.
264	- connection imports receive/send/task/SCOE/status/result/report/northbound internal state to push business side effects.
265	- pages/widgets subscribe to raw platform transport events.
266	- status or task backfills connection truth by reading a shared global store.

14	## 2. Design Decisions
15	
16	### D1: 统一 connect 接口
17	
18	`TransportBridge.connect(config: TransportConnectConfig)` 统一入口，discriminated union 区分传输类型。替代分立方法（connectTcp / listenTcp / connectUdp），理由：
19	- disconnect/write/cleanup 已经按 connectionId 多态，connect 也应该统一
20	- 对后续 HTTP transport 扩展友好（只加 config 变体，不改 interface）
21	
22	影响：
23	- `connectSerial` 从 `TransportBridge` 和 `TransportFacade` 中移除
24	- `SerialConnectConfig` 新增 `kind: 'serial'` discriminant
25	- `RealSerialAdapter` 迁移到 `connect({ kind: 'serial', ... })`
26	
27	### D2: TCP Server 事件设计
28	
29	listener 和每个 accepted client 各自拥有独立 connectionId：
30	- listener 的 connectionId = config 中的 `id`
31	- client 的 connectionId = `${listenerId}::client:${remoteAddress}:${remotePort}`
32	
33	事件流：
34	1. `connect(tcpServerConfig)` → listener 的 `connected`（`role: 'tcp-server-listener'`）
35	2. 客户端连入 → `connected`（`role: 'tcp-server-client'`，新 connectionId）
36	3. 客户端断开 → `disconnected`
37	4. `disconnect(listenerId)` → 关闭所有客户端 + listener，返回所有 `disconnected` 事件
38	
39	### D3: 主进程架构 — Preload 路由
40	
41	preload 维护 `connectionId → transport type` 映射，将 disconnect/write/cleanup 路由到正确的 IPC channel。serial-handlers.ts 不做任何修改。
42	
43	- serial-handlers.ts：完全不动，保持现有 IPC channels
44	- network-handlers.ts：新建，独立管理 TCP/UDP 连接，使用新的 IPC channels
45	- 两者共享 `transport:event` 事件 channel
46	- preload 的 `TransportBridge` 实现做路由分发
47	
48	### D4: UDP 写入目标
49	
50	UDP `connect` 时指定 `remoteHost`/`remotePort`。`write()` 发送到配置目标。未配置目标时 `write()` 返回错误。多目标发送留给未来 `writeTo()` 扩展。

52	### D5: Batch 参数
53	
54	TCP/UDP 复用串口策略（maxBatchBytes=4096, maxBatchWindowMs=50, maxQueueDepth=100），参数独立可配。batch 基础设施在 network-handlers 中独立复制一份（与 serial-handlers 不共享），后续可提取为 main 内部共享模块，但不阻塞本 feature。

**[HIGH] Reconnect编排流中 service 自身调度的 drainEvents 循环入口未明确**  
File: `codestable/features/rewrite-connection/rewrite-connection-design.md` (4.12 重连编排流)  
The flow states: "drainEvents() 返回 disconnected 事件 -> service 检查 reconnect policy". But the current `ConnectionService.drainAdapterEvents()` (line 286-301 of `connection-service.ts`) calls `adapter.drainEvents()` then applies events. The problem: who calls `drainAdapterEvents` after a reconnect-attempt failure? The timer only calls `connect()`, not `drainAdapterEvents()`. A failed `connect()` does not produce a `disconnected` event -- it produces an `error` event. The design conflates the initial disconnect-detection path (triggered by `drainAdapterEvents`) with the reconnect-attempt-failure path. This needs a clear second entry point: either the reconnect timer calls both `connect()` and then `drainAdapterEvents()`, or the connect-failure path directly re-schedules without waiting for drainEvents.  
Fix: Clarify the reconnect loop's entry points. The design should specify: (1) initial trigger = `drainAdapterEvents()` returning `disconnected`; (2) reconnect attempt = timer fires -> `service.connect(originalConfig)` -> if ok, done; if fail, increment attempt and directly schedule next timer (no drainEvents round-trip needed for connect failure).
