## Expression Engine Brainstorm

### 事实汇总

**旧系统核心机制（~1385 行）：**
- 求值：`new Function(...keys, 'return (expression)')` 动态构造，每次创建新 Function
- 变量：4 种数据源（current_field / frame_field / global_stat / scoe_data），引擎内部持有 store
- 排序：Kahn 拓扑排序 O(V+E)，循环依赖回退安全模式——**可复用**
- 缓存：configHash + timestamp + LRU(50) + 5min 过期——**思路可复用**
- 数学：`abs: Math.abs` 简名绑定，支持三角/对数/指数/幂
- 条件：`ConditionalExpression`（condition + expression 对），按序短路求值
- 性能瓶颈：高频 receive 同步阻塞主线程，无预编译，无表达式级缓存

**已确定架构决策：**
- 路线 B：纯函数，全部变量外部传入，引擎不持有 store
- 归口 `shared/`，零 Vue/Pinia/Electron 依赖
- 条件匹配两层：匹配逻辑（shared/）+ 触发行为（各 feature）
- 命名空间约定：`$遥测.温度` / `$本帧.系数` / `$global.时间`

**消费者现状：**
- receive：已有简单 factor 转换（`factor: 0.1`），需要通用表达式替换
- send：当前用静态字段值，设计文档明确"本轮不执行 expression，使用 resolved values"
- task：WaitCondition（单帧单字段比较），需要扩展多条件表达式
- 三个 feature 都假设表达式在调用侧完成，内部只用 resolved values

### 讨论点 1：预编译策略

**选项分析：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A: AST 解析 + 预编译为 Function** | 一次解析多次求值；可在解析阶段做依赖分析和校验；安全可控 | 需要 AST parser 或手写 tokenizer |
| **B: 直接缓存 `new Function` 结果** | 实现简单，旧代码思路延续 | 无法做静态分析和安全校验；Function 构造受限 |
| **C: 手写递归下降解释器** | 完全可控，无需 eval/Function | 开发量大；性能可能不如 JIT |

**我的倾向：方案 A，两阶段设计。**

理由：
1. 表达式语法量级不大（算术+比较+逻辑+函数调用+变量引用），不需要引入外部 parser 库
2. 手写 tokenizer + recursive descent parser 可控，预计 200-300 行
3. parse 阶段产出 AST，AST 可以缓存、可以做依赖提取、可以做安全校验
4. compile 阶段把 AST 编译为 `(...args) => value` 的 JS 函数，V8 JIT 优化
5. 调用方拿到编译产物后高频调用成本接近零

**两阶段 API 草案：**
```typescript
// 阶段 1: 编译（低频，配置变更时调用）
const compiled = compileExpression('a * 0.1 + b');

// 阶段 2: 求值（高频，每帧调用）
const result = evaluate(compiled, { a: 250, b: 10 });
```

**待决问题：** 是否需要支持字符串拼接/条件三元运算符，还是只做算术+比较+逻辑？旧系统有 `ConditionalExpression`（condition + expression 对），这个是否纳入引擎核心还是留在调用方？

### 讨论点 2：多数据源变量解析（命名空间设计）

旧系统 4 种 DataSourceType 硬编码在引擎内部。新系统引擎是纯函数，不关心变量来源。

**设计要点：**

1. **引擎侧：扁平 Map 输入**
   ```typescript
   type VariableMap = ReadonlyMap<string, number | string | boolean>;
   ```
   引擎只认 key-value，不做命名空间解析。`$遥测.温度` 对引擎来说就是一个 key。

2. **调用方负责拼 key 和收集值**
   ```typescript
   // receive service 调用示例
   const vars = new Map([
     ['$遥测.温度', receiveSnapshot.fields['temp-frame'].temperature],
     ['$本帧.原始值', rawValue],
     ['$global.时间', globalStats.runtime],
   ]);
   ```

3. **命名空间规范由帧定义约定，不硬编码到引擎**
   - `$遥测.*` — receive 当前值
   - `$本帧.*` — 当前帧上下文（正在解析/构建的字段值）
   - `$global.*` — 全局参数
   - `$发送.*` — send 历史值（如果需要）

**好处：** 引擎不关心命名空间语义，新增数据源只需调用方多传一个变量，零引擎改动。

**待决问题：** 变量名里的 `$` 前缀和 `.` 分隔符是 UI 约定还是引擎强制？如果引擎不限制字符集，表达式语法里变量名可能和函数名冲突。建议引擎侧做一个简单的标识符规则：变量以 `$` 开头，函数名不以 `$` 开头。

### 讨论点 3：依赖排序

**旧系统做法（可复用）：**
1. `extractFieldReferences()` — 从表达式文本提取引用的变量
2. `analyzeDependencies()` — 构建依赖图
3. `topologicalSort()` — Kahn 算法

**新系统改进方向：**

| 旧系统 | 新系统 |
|--------|--------|
| 从表达式文本正则提取依赖 | 从 AST 提取依赖（编译阶段免费获得） |
| 依赖分析结果缓存在 configHash 里 | 依赖信息直接存在 CompiledExpression 里 |
| 排序后按拓扑序逐个求值 | 排序后逐个求值，但用预编译函数 |
| 循环依赖回退到并行模式 | 循环依赖报错，不回退（调用方决定降级策略） |

**关键变化：** 依赖分析是编译阶段的副产品，不需要单独做。AST 节点里已经有所有变量引用信息。

**批量求值 API 草案：**
```typescript
interface ExpressionGroup {
  readonly expressions: ReadonlyMap<string, CompiledExpression>;
}

interface EvalResult {
  readonly values: ReadonlyMap<string, number>;
  readonly errors: ReadonlyMap<string, string>;
}

// 编译+排序+求值一体化
const result = evaluateGroup(group, initialVars);
// 内部：拓扑排序 → 逐个 evaluate → 每步更新 vars → 下一步用更新后的 vars
```

### 讨论点 4：数学函数绑定

旧系统做法：`abs: Math.abs` 简名绑定，通过 `new Function` 的参数传入。

新系统方案：
```typescript
// 编译阶段识别函数调用节点
// 求值阶段从函数表查找
type FunctionTable = ReadonlyMap<string, (...args: number[]) => number>;

const defaultMathFunctions: FunctionTable = new Map([
  ['abs', Math.abs],
  ['floor', Math.floor],
  ['ceil', Math.ceil],
  ['round', Math.round],
  ['min', Math.min],
  ['max', Math.max],
  ['sqrt', Math.sqrt],
  ['pow', Math.pow],
  ['sin', Math.sin],
  ['cos', Math.cos],
  ['tan', Math.tan],
  ['log', Math.log],
  ['exp', Math.exp],
]);
```

**好处：**
1. 编译阶段可以校验函数名是否存在（不存在→编译错误）
2. 调用方可以注入自定义函数（测试时 mock，或业务扩展）
3. 不污染变量空间，函数名和变量名通过 AST 节点类型区分（CallExpression vs Identifier）

**待决问题：** 是否允许调用方覆盖默认数学函数？建议允许，FunctionTable 是参数而非全局。

### 讨论点 5：性能策略

**场景分析：**

| 场景 | 频率 | 优化优先级 |
|------|------|-----------|
| receive 帧字段后处理 | 每秒数十帧 | P0 |
| send 构帧前计算 | 每次发送 1 次 | P1 |
| task 条件评估 | 每次收到帧时检查 | P1 |
| UI 编辑器预览 | 用户输入时 | P2 |

**优化手段：**

1. **预编译**（P0）— 配置加载时编译，运行时只执行 JS 函数。旧系统每帧 `new Function`，新系统一次编译反复执行。

2. **输入不变跳过**（P0）— 如果变量值没变，直接返回缓存结果。旧系统缺少这个。

3. **批量拓扑求值**（P1）— 一次 evaluateGroup 内按拓扑序串行，共享中间结果，避免重复收集变量。

4. **结果不可变**（all）— 所有输出 `ReadonlyMap`，无深拷贝开销。

**不需要做的：**
- 不需要 Web Worker（表达式计算本身很快，瓶颈在 IPC 和数据收集，不在求值）
- 不需要 JIT（V8 已经对纯函数做了 JIT）
- 不需要增量计算（表达式通常很短，全量重算成本远低于增量追踪复杂度）

**预估性能：** 单个预编译表达式求值 ~100ns 级别（纯算术+函数调用），50 个表达式批量求值 ~5-10μs。高频 receive 场景完全够用。

### 讨论点 6：API 表面

**目标：** 调用方 3-5 行代码搞定。

```typescript
import { compileExpression, evaluate, evaluateGroup, sortDependencies } from '@/shared/expression';

// === 场景 1: 单表达式（receive 字段后处理）===

// 初始化时编译一次
const compiled = compileExpression('$本帧.原始值 * 0.1 + $本帧.偏移');
if (!compiled.success) {
  console.error(compiled.error); // 编译错误：语法/未定义函数
}

// 每帧求值
const result = evaluate(compiled, variableMap);
// result: { success: true, value: 25.3 } | { success: false, error: '...' }


// === 场景 2: 批量表达式（receive 帧全部字段）===

// 初始化时编译+排序
const group = compileExpressionGroup({
  expressions: new Map([
    ['temp', compileExpression('$本帧.rawTemp * 0.1')],
    ['pressure', compileExpression('$本帧.rawPressure + $遥测.气压偏移')],
    ['altitude', compileExpression('44330 * (1 - pow($遥测.压力 / 1013.25, 0.19))')],
  ]),
});
// group 已含拓扑排序结果

// 每帧批量求值
const results = evaluateGroup(group, initialVars);
// results.values: ReadonlyMap<string, number>
// 每步自动更新 vars，后续表达式可用前序结果


// === 场景 3: 条件表达式（task wait-condition）===

const condition = compileExpression('$遥测.温度 > 100 && $遥测.模式 === "加热"');
const match = evaluate(condition, vars);
// match.success && match.value === true → 条件满足


// === 场景 4: 自定义函数 ===

const customFns = new Map([...defaultMathFunctions, ['toHex', (n: number) => n.toString(16)]]);
const compiled = compileExpression('toHex($本帧.地址)', customFns);
```

**核心 API 列表：**
- `compileExpression(text, functions?)` → `CompileResult`
- `evaluate(compiled, variables)` → `EvalResult`
- `compileExpressionGroup({ expressions })` → `CompiledGroup`
- `evaluateGroup(group, variables)` → `GroupEvalResult`

**不暴露的：**
- AST 节点类型（内部实现细节）
- 拓扑排序算法（compileExpressionGroup 内部自动执行）
- 缓存管理（编译产物本身就是缓存）

**真实表达式样本（18 个配置文件）：**

4. **条件表达式是多分支** — 典型 5 个 condition+expression 对，按序短路

## 锁定设计决策

基于事实和"不易出问题、性能好、代码干净"原则，锁定以下决策：

### D1: 预编译 — 手写 tokenizer + recursive descent parser

理由：实际语法极简（四则运算+比较+括号），parser 预计 150-200 行。编译产物是 JS 函数，V8 JIT 优化，运行时零解析开销。比 `new Function` 安全（可做白名单校验），比引入外部库轻量。

### D2: 变量规则

- 引擎侧接受扁平 `Map<string, number | string | boolean>`
- 变量名支持中文、英文、下划线、数字（首字非数字）
- 不用 `$` 前缀做引擎级强制——旧数据是裸名 `var1`/`速度`，新系统命名空间由帧定义约定，引擎不感知

### D3: 函数表

虽然当前零函数调用，但保留 `FunctionTable` 参数注入。默认提供 Math.* 简名，调用方可扩展。这样以后加自定义函数不改引擎。

### D4: 条件表达式

**纳入引擎核心。** 理由：多分支 condition+expression 是实际数据中最复杂的模式，引擎内置支持比让调用方自己编排更干净。API：

```typescript
// 多分支条件表达式的编译结果
type ConditionalExpr = ReadonlyArray<{
  readonly condition: string;   // 条件表达式
  readonly expression: string;  // 满足条件时计算的表达式
}>;

// compileConditional(conditionals, fallbackValue?, functions?)
// evaluateConditional(compiled, variables) → { value, matchedIndex }
```

### D5: 依赖排序

AST 提取变量引用 → Kahn 拓扑排序。编译阶段完成排序，运行时按预排顺序执行。循环依赖编译阶段报错。

### D6: 运算符范围

锁定 **只支持实际用到的**：
- 算术：`+ - * /`（数值）
- 比较：`> < >= <= == !=`（数值+字符串）
- 括号：`( )`
- 字面量：数值（含大数/小数）、字符串（单引号）、布尔（true/false）
- 逻辑：`&& ||`（条件表达式中需要）

**不支持的（明确排除）：** 位运算、三元运算符、赋值、正则、模板字符串。

### D7: 与 compareValues 共存

表达式引擎内部处理比较运算符，**不复用** `compareValues`。理由：表达式引擎的比较是 AST 节点级操作，返回 boolean 值参与逻辑运算；`compareValues` 是独立工具函数用于 WaitCondition 等结构化条件。两者场景不同，强行复用增加耦合。WaitCondition 可以在后续版本逐步迁移到表达式条件。

### D8: 运行时类型

表达式返回值统一为 `number | string | boolean`。编译阶段不推断类型，运行时由实际求值决定。

## API 最终设计

```typescript
// === 核心 API ===

// 单表达式编译
function compileExpression(
  text: string,
  functions?: FunctionTable,
): CompileResult
// CompileResult = { success: true, compiled: CompiledExpr }
//               | { success: false, error: string, position?: number }

// 单表达式求值
function evaluate(
  compiled: CompiledExpr,
  variables: VariableMap,
): EvalResult
// EvalResult = { success: true, value: number | string | boolean }
//            | { success: false, error: string }

// 条件表达式编译（多分支）
function compileConditional(
  branches: ReadonlyArray<{ condition: string; expression: string }>,
  fallback?: number,
  functions?: FunctionTable,
): CompileResult  // compiled 里含 CompiledExpr[]

// 条件表达式求值
function evaluateConditional(
  compiled: CompiledConditional,
  variables: VariableMap,
): ConditionalEvalResult
// ConditionalEvalResult = { success: true, value, matchedIndex }
//                       | { success: false, error: string }

// 批量表达式编译+排序
function compileGroup(
  expressions: ReadonlyMap<string, string>,
  functions?: FunctionTable,
): GroupCompileResult
// 内部：逐个 compile → AST 提取依赖 → Kahn 排序

// 批量求值
function evaluateGroup(
  group: CompiledGroup,
  variables: VariableMap,
): GroupEvalResult
// 内部：按拓扑序逐个 evaluate，每步结果加入 variables 供后续使用

// === 类型 ===
type VariableMap = ReadonlyMap<string, number | string | boolean>;
type FunctionTable = ReadonlyMap<string, (...args: number[]) => number>;

// 内部不导出 AST 节点类型
```

**调用方使用示例（receive）：**
```typescript
// 初始化时编译一次
const expr = compileExpression(field.expressionConfig);
if (!expr.success) { /* 配置错误处理 */ return; }

// 每帧求值，3 行代码
const vars = new Map([
  ['var1', rawParsedValue],
  ['var2', otherFieldValue],
]);
const result = evaluate(expr.compiled, vars);
const finalValue = result.success ? result.value : rawParsedValue;
```
