```typescript
const generateConfigHash = (expressionConfigs) => {
  const configStr = JSON.stringify(expressionConfigs.map(({fieldId, config}) => ({
    fieldId,
    expressions: config.expressions,
    variables: config.variables,

  // 简单哈希算法
  let hash = 0;
  for (let i = 0; i < configStr.length; i++) {
    const char = configStr.charCodeAt(i);
    hash = (hash << 5) - hash + char;
    hash = hash & hash;

};
```

**来源：** `rewrite-target-structure.md:127`, `rewrite-target-structure.md:165-176`

**shared/ 可以包含：**
- 纯类型、通用工具、协议常量、无副作用 helper

**触发层（各 feature 自己管）：**
- "匹配了之后干嘛？"——业务语义

## Expression Engine Brainstorm

### 事实汇总

**旧系统核心机制（~1385 行）：**
- 求值：`new Function(...keys, 'return (expression)')` 动态构造，每次创建新 Function
- 变量：4 种数据源（current_field / frame_field / global_stat / scoe_data），引擎内部持有 store
- 排序：Kahn 拓扑排序 O(V+E)，循环依赖回退安全模式——**可复用**
- 缓存：configHash + timestamp + LRU(50) + 5min 过期——**思路可复用**
- 数学：`abs: Math.abs` 简名绑定，支持三角/对数/指数/幂
- 条件：`ConditionalExpression`（condition + expression 对），按序短路求值
- 性能瓶颈：高频 receive 同步阻塞主线程，无预编译，无表达式级缓存

**已确定架构决策：**
- 路线 B：纯函数，全部变量外部传入，引擎不持有 store
- 归口 `shared/`，零 Vue/Pinia/Electron 依赖
- 条件匹配两层：匹配逻辑（shared/）+ 触发行为（各 feature）
- 命名空间约定：`$遥测.温度` / `$本帧.系数` / `$global.时间`

**消费者现状：**
- receive：已有简单 factor 转换（`factor: 0.1`），需要通用表达式替换
- send：当前用静态字段值，设计文档明确"本轮不执行 expression，使用 resolved values"
- task：WaitCondition（单帧单字段比较），需要扩展多条件表达式
- 三个 feature 都假设表达式在调用侧完成，内部只用 resolved values

### 讨论点 1：预编译策略

**选项分析：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A: AST 解析 + 预编译为 Function** | 一次解析多次求值；可在解析阶段做依赖分析和校验；安全可控 | 需要 AST parser 或手写 tokenizer |
| **B: 直接缓存 `new Function` 结果** | 实现简单，旧代码思路延续 | 无法做静态分析和安全校验；Function 构造受限 |
| **C: 手写递归下降解释器** | 完全可控，无需 eval/Function | 开发量大；性能可能不如 JIT |

**我的倾向：方案 A，两阶段设计。**

理由：
1. 表达式语法量级不大（算术+比较+逻辑+函数调用+变量引用），不需要引入外部 parser 库
2. 手写 tokenizer + recursive descent parser 可控，预计 200-300 行
3. parse 阶段产出 AST，AST 可以缓存、可以做依赖提取、可以做安全校验
4. compile 阶段把 AST 编译为 `(...args) => value` 的 JS 函数，V8 JIT 优化
5. 调用方拿到编译产物后高频调用成本接近零

**两阶段 API 草案：**
```typescript
// 阶段 1: 编译（低频，配置变更时调用）
const compiled = compileExpression('a * 0.1 + b');

// 阶段 2: 求值（高频，每帧调用）
const result = evaluate(compiled, { a: 250, b: 10 });
```

**待决问题：** 是否需要支持字符串拼接/条件三元运算符，还是只做算术+比较+逻辑？旧系统有 `ConditionalExpression`（condition + expression 对），这个是否纳入引擎核心还是留在调用方？

### 讨论点 2：多数据源变量解析（命名空间设计）

旧系统 4 种 DataSourceType 硬编码在引擎内部。新系统引擎是纯函数，不关心变量来源。

**设计要点：**

1. **引擎侧：扁平 Map 输入**
   ```typescript
   type VariableMap = ReadonlyMap<string, number | string | boolean>;
   ```
   引擎只认 key-value，不做命名空间解析。`$遥测.温度` 对引擎来说就是一个 key。

2. **调用方负责拼 key 和收集值**
   ```typescript
   // receive service 调用示例
   const vars = new Map([
     ['$遥测.温度', receiveSnapshot.fields['temp-frame'].temperature],
     ['$本帧.原始值', rawValue],
     ['$global.时间', globalStats.runtime],
   ]);
   ```

3. **命名空间规范由帧定义约定，不硬编码到引擎**
   - `$遥测.*` — receive 当前值
   - `$本帧.*` — 当前帧上下文（正在解析/构建的字段值）
   - `$global.*` — 全局参数
   - `$发送.*` — send 历史值（如果需要）

**好处：** 引擎不关心命名空间语义，新增数据源只需调用方多传一个变量，零引擎改动。

**待决问题：** 变量名里的 `$` 前缀和 `.` 分隔符是 UI 约定还是引擎强制？如果引擎不限制字符集，表达式语法里变量名可能和函数名冲突。建议引擎侧做一个简单的标识符规则：变量以 `$` 开头，函数名不以 `$` 开头。

### 讨论点 3：依赖排序

**旧系统做法（可复用）：**
1. `extractFieldReferences()` — 从表达式文本提取引用的变量
2. `analyzeDependencies()` — 构建依赖图
3. `topologicalSort()` — Kahn 算法

**新系统改进方向：**

| 旧系统 | 新系统 |
|--------|--------|
| 从表达式文本正则提取依赖 | 从 AST 提取依赖（编译阶段免费获得） |
| 依赖分析结果缓存在 configHash 里 | 依赖信息直接存在 CompiledExpression 里 |
| 排序后按拓扑序逐个求值 | 排序后逐个求值，但用预编译函数 |
| 循环依赖回退到并行模式 | 循环依赖报错，不回退（调用方决定降级策略） |

**关键变化：** 依赖分析是编译阶段的副产品，不需要单独做。AST 节点里已经有所有变量引用信息。

**批量求值 API 草案：**
```typescript
interface ExpressionGroup {
  readonly expressions: ReadonlyMap<string, CompiledExpression>;
}

interface EvalResult {
  readonly values: ReadonlyMap<string, number>;
  readonly errors: ReadonlyMap<string, string>;
}

// 编译+排序+求值一体化
const result = evaluateGroup(group, initialVars);
// 内部：拓扑排序 → 逐个 evaluate → 每步更新 vars → 下一步用更新后的 vars
```

### 讨论点 4：数学函数绑定

旧系统做法：`abs: Math.abs` 简名绑定，通过 `new Function` 的参数传入。

新系统方案：
```typescript
// 编译阶段识别函数调用节点
// 求值阶段从函数表查找
type FunctionTable = ReadonlyMap<string, (...args: number[]) => number>;

const defaultMathFunctions: FunctionTable = new Map([
  ['abs', Math.abs],
  ['floor', Math.floor],
  ['ceil', Math.ceil],
  ['round', Math.round],
  ['min', Math.min],
  ['max', Math.max],
  ['sqrt', Math.sqrt],
  ['pow', Math.pow],
  ['sin', Math.sin],
  ['cos', Math.cos],
  ['tan', Math.tan],
  ['log', Math.log],
  ['exp', Math.exp],

```

**好处：**
1. 编译阶段可以校验函数名是否存在（不存在→编译错误）
2. 调用方可以注入自定义函数（测试时 mock，或业务扩展）
3. 不污染变量空间，函数名和变量名通过 AST 节点类型区分（CallExpression vs Identifier）

**待决问题：** 是否允许调用方覆盖默认数学函数？建议允许，FunctionTable 是参数而非全局。

### 讨论点 5：性能策略

**场景分析：**

| 场景 | 频率 | 优化优先级 |
|------|------|-----------|
| receive 帧字段后处理 | 每秒数十帧 | P0 |
| send 构帧前计算 | 每次发送 1 次 | P1 |
| task 条件评估 | 每次收到帧时检查 | P1 |
| UI 编辑器预览 | 用户输入时 | P2 |

**优化手段：**

1. **预编译**（P0）— 配置加载时编译，运行时只执行 JS 函数。旧系统每帧 `new Function`，新系统一次编译反复执行。

2. **输入不变跳过**（P0）— 如果变量值没变，直接返回缓存结果。旧系统缺少这个。

3. **批量拓扑求值**（P1）— 一次 evaluateGroup 内按拓扑序串行，共享中间结果，避免重复收集变量。

4. **结果不可变**（all）— 所有输出 `ReadonlyMap`，无深拷贝开销。

**不需要做的：**
- 不需要 Web Worker（表达式计算本身很快，瓶颈在 IPC 和数据收集，不在求值）
- 不需要 JIT（V8 已经对纯函数做了 JIT）
- 不需要增量计算（表达式通常很短，全量重算成本远低于增量追踪复杂度）

**预估性能：** 单个预编译表达式求值 ~100ns 级别（纯算术+函数调用），50 个表达式批量求值 ~5-10μs。高频 receive 场景完全够用。

### 讨论点 6：API 表面

**目标：** 调用方 3-5 行代码搞定。

```typescript

// === 场景 1: 单表达式（receive 字段后处理）===

// 初始化时编译一次

    ['pressure', compileExpression('$本帧.rawPressure + $遥测.气压偏移')],
    ['altitude', compileExpression('44330 * (1 - pow($遥测.压力 / 1013.25, 0.19))')],
  ]),

// group 已含拓扑排序结果

// 每帧批量求值
const results = evaluateGroup(group, initialVars);
// results.values: ReadonlyMap<string, number>
// 每步自动更新 vars，后续表达式可用前序结果


// === 场景 3: 条件表达式（task wait-condition）===

const condition = compileExpression('$遥测.温度 > 100 && $遥测.模式 === "加热"');
```

**核心 API 列表：**
- `compileExpression(text, functions?)` → `CompileResult`
- `evaluate(compiled, variables)` → `EvalResult`
- `compileExpressionGroup({ expressions })` → `CompiledGroup`
- `evaluateGroup(group, variables)` → `GroupEvalResult`

**不暴露的：**
- AST 节点类型（内部实现细节）
- 拓扑排序算法（compileExpressionGroup 内部自动执行）
- 缓存管理（编译产物本身就是缓存）

| D2 | 变量解析 | 扁平 Map 输入，引擎不关心命名空间语义 | 纯函数约束，新增数据源零引擎改动 |

## 锁定设计决策

基于事实和"不易出问题、性能好、代码干净"原则，锁定以下决策：

### D1: 预编译 — 手写 tokenizer + recursive descent parser

理由：实际语法极简（四则运算+比较+括号），parser 预计 150-200 行。编译产物是 JS 函数，V8 JIT 优化，运行时零解析开销。比 `new Function` 安全（可做白名单校验），比引入外部库轻量。

### D2: 变量规则

- 引擎侧接受扁平 `Map<string, number | string | boolean>`
- 变量名支持中文、英文、下划线、数字（首字非数字）
- 不用 `$` 前缀做引擎级强制——旧数据是裸名 `var1`/`速度`，新系统命名空间由帧定义约定，引擎不感知

### D3: 函数表

虽然当前零函数调用，但保留 `FunctionTable` 参数注入。默认提供 Math.* 简名，调用方可扩展。这样以后加自定义函数不改引擎。

### D4: 条件表达式

**纳入引擎核心。** 理由：多分支 condition+expression 是实际数据中最复杂的模式，引擎内置支持比让调用方自己编排更干净。API：

```typescript
// 多分支条件表达式的编译结果
type ConditionalExpr = ReadonlyArray<{
  readonly condition: string;   // 条件表达式
  readonly expression: string;  // 满足条件时计算的表达式
}>;

// compileConditional(conditionals, fallbackValue?, functions?)
// evaluateConditional(compiled, variables) → { value, matchedIndex }
```

### D5: 依赖排序

AST 提取变量引用 → Kahn 拓扑排序。编译阶段完成排序，运行时按预排顺序执行。循环依赖编译阶段报错。

### D6: 运算符范围

锁定 **只支持实际用到的**：
- 算术：`+ - * /`（数值）
- 比较：`> < >= <= == !=`（数值+字符串）
- 括号：`( )`
- 字面量：数值（含大数/小数）、字符串（单引号）、布尔（true/false）
- 逻辑：`&& ||`（条件表达式中需要）

**不支持的（明确排除）：** 位运算、三元运算符、赋值、正则、模板字符串。

### D7: 与 compareValues 共存

表达式引擎内部处理比较运算符，**不复用** `compareValues`。理由：表达式引擎的比较是 AST 节点级操作，返回 boolean 值参与逻辑运算；`compareValues` 是独立工具函数用于 WaitCondition 等结构化条件。两者场景不同，强行复用增加耦合。WaitCondition 可以在后续版本逐步迁移到表达式条件。

### D8: 运行时类型

表达式返回值统一为 `number | string | boolean`。编译阶段不推断类型，运行时由实际求值决定。

```
3. 变量/函数名冲突 -- 发现一个设计漏洞。
4. `evaluateGroup` 可变性 -- 没有问题，易于解决。
5. 性能 -- 在当前限制内，没有问题。

**关键问题** -- 无。

**重要问题**（设计需明确，可临时解决）：

**1. 一元减号语法在表达式中未被覆盖**

设计声明了运算符 `+ - * / ( ) > < >= <= == != && ||`。这描述了二元中缀运算符。问题在于：当一元 `-` 出现在何处时，语法必须明确处理它？

从真实的表达式中：
- `温度 - 5` -- 二元减号，没问题
- `-5` -- 需要一元减号作为主要表达式
- `(-5)` -- 需要在括号内使用一元减号
- `(-速度)` -- 一元取反变量
- `(-5+速度)` -- 一元后跟二元

一个没有一元规则的递归下降解析器（`primary := NUMBER | IDENT | '(' expr ')'`）会拒绝 `-5` 作为语法错误，因为 `-` 不是预期的主要开始标记。解析器需要扩展为：`primary := NUMBER | IDENT | '(' expr ')' | '-' primary`，或者一个显式的 `unary` 层：`unary := ('-' | '+')? primary`。

这是一个实现细节，而不是架构上的担忧。但它必须在设计文档中明确指出，否则实现者将构建一个没有一元规则的语法，然后在真实表达式上进行静默失败或崩溃。解析器大约150-200行很容易遗漏这种情况。

- **置信度**：高
- **重要性**：真实表达式如 `(-速度)` 或以负偏移量开头的公式将无法解析。
- **修复**：在语法规范中添加显式的一元规则。建议：
  ```
  unary := ('-' | '+')? primary
  primary := NUMBER | STRING | IDENT | '(' expr ')'
  ```
  确保解析器函数正确处理一元加号/减号优先级（高于乘法/除法，低于主要表达式）。

**2. 变量名与 `FunctionTable` 键冲突 -- 没有优先规则**

设计说明变量是 `Map<string, number | string | boolean>`，函数有 `FunctionTable`，带有 `Math.*` 短名称（`abs`、`sin` 等）。但存在冲突时会发生什么？

场景：用户配置一个名为 `abs` 的变量（可能是“绝对值”的缩写）。表达式 `abs*2` -- `abs` 是变量还是函数调用？

旧的引擎没有这个问题，因为变量通过 `VariableMapping.identifier` 映射（像 `a`、`ab` 这样的短标识符），这些标识符由配置器控制，而不是最终用户显示名称。新设计使用中文变量名，如 `速度`、`距离`，这些名称与数学函数自然冲突。但有人可能会合理地创建名为 `speed` 或 `abs` 或 `min` 或 `max` 的变量。

编译时解析需要一条明确规则。选项：
- (a) 函数优先 -- `abs` 始终是函数，创建一个名为 `abs` 的变量是配置错误
- (b) 变量优先 -- 屏蔽数学函数，可能令人惊讶
- (c) 基于语法消歧 -- 如果后面跟着 `(`，则为函数；否则为变量

选项 (c) 是最自然的，因为表达式已经区分了 `abs(x)`（函数调用）和 `abs`（变量引用）。解析器可以处理这个问题 -- 标识符标记后跟着 `(` 触发函数调用路径，否则触发变量查找。

- **置信度**：高
- **重要性**：如果没有规则，实现者会做出任意选择，行为会变得隐晦。选项 (c) 最符合用户的直觉。
- **修复**：在设计中声明消歧规则：“标识符后跟 `(` 解析为函数调用；否则解析为变量查找。在编译时，如果存在同名函数和变量，编译器会发出警告。”

**次要问题**（次优但功能正常）：

**3. 除零行为未指定**

JavaScript 的除法自然返回 `Infinity` 或 `-Infinity`（或非零模的 `NaN`）。这些值会通过 `IEEE 754` 正确传播。问题在于这是否符合设计意图。如果消费者（`receive field-parser`、`task condition-matcher`）将 `Infinity` 馈送到显示逻辑，`UI` 可能会显示“Infinity”而不是有意义的错误。

现有代码库中的证据：`field-parser.ts:86` 中的 `formatNumber()` 使用 `Number.parseFloat(value.toFixed(5))`，这会在 `Infinity.toFixed(5)` 上抛出 `RangeError`。因此，在 `factor` 是表达式的接收路径中，未受保护的 `Infinity` 会导致崩溃。

- **修复**：在设计中声明：`evaluate()` 从未捕获的 `JS` 异常中返回错误，但如果结果是 `NaN` 或 `Infinity`，则返回一个 `EvalResult`，其中包含一个 `warning/error` 字段。或者让消费者处理。只需选择一个并记录下来。

**4. `FunctionTable` 类型限制为数字到数字**

设计声明 `(...args: number[]) => number`。如果以后需要字符串函数（如 `toString`、`format`、`concat`），这个类型签名会阻止它们。目前，真实的表达式示例只显示算术和比较。但是，旧引擎的 `processValueByDataType` 存在是因为类型强制转换在配置数据中，而字符串字面量如 `'RS编码'` 已经是设计的一部分。

- **修复**：考虑是否将类型加宽到 `(...args: unknown[]) => unknown`，或者现在就将其保持为数字并记录为有意的限制。这只是一个设计选择，而不是一个漏洞。

**5. `13743895344000` 常数的精度**

`13743895344000` 是 `2^37 * 125`。它在 `IEEE 754` 双精度浮点数的 53 位尾数限制内。该值可以精确表示。`13743895344000 / 299792458 = 45836.4158...` 这对于双精度浮点数来说没问题。这里的精度不是问题。

- **结论**：无需操作。`JS` 数字对于此范围内的遥测计算足够。无需 `BigInt`。

**6. `evaluateGroup` 可变性 -- 无问题，文档完善**

设计说明“每一步的结果都会添加到变量中，供后续使用”并且变量是 `ReadonlyMap`。实现明显会创建一个可变副本（`new Map(variables)`），按顺序添加结果，并返回一个带有输入和所有结果的新的 `readonly` 快照。旧引擎在 `useFrameExpressionManager.ts:256` 中已经完全做到了这一点：`context.frameData.set(fieldId, processedValue)`。这是标准做法。

- **结论**：只需在设计文档中明确指出“`evaluateGroup` 在内部创建输入映射的可变副本；原始输入保持不变。”

**7. 迁移路径 -- 绑定逻辑是一个差距，但不在引擎范围内**

旧系统的 `VariableMapping` 有 `sourceType + sourceId + frameId + fieldId` 将变量名绑定到数据源。新引擎采用扁平映射。问题在于：“哪个调用者负责填充这个映射？”对于三个消费者：

- **接收**：`field-parser.ts` 有字段值在本地可用。映射：字段名到解析值。简单。
- **任务**：`condition-matcher.ts` 接收一个 `ConditionMatchInput`。表达式扩展会添加更多变量。服务层构建映射。可管理。
- **发送**：`encode.ts` 接收 `fieldValues: Record<string, SendFieldValue>`。表达式在编码之前进行评估。映射：字段 `ID` 到值。

这些都不是引擎的职责。调用者负责将它们的领域数据扁平化为 `Map<string, value>`。设计是正确的。但是从旧的 `VariableMapping[].sourceType` 配置到新“谁收集变量”映射的迁移指南在设计中缺失。

- **修复**：在设计文档中添加一个简短的迁移说明：“旧 `VariableMapping` 绑定逻辑移至每个功能的配置/服务层。接收服务从字段值构建映射；任务服务从条件输入构建映射；发送服务从字段值解析构建映射。”

---

**缺失之处**：

- **没有提到字符串比较运算符语义**。设计说 `==` 处理 `模式=='RS编码'`。但是 `==` 是严格相等吗？还是宽松的？如果用户比较 `5 == '5'` 会怎样？需要决定：严格的 `===` 语义（类型必须匹配）还是类型强制的比较。旧引擎的 `compareValues`（`compare.ts:24-30`）具有自动数字检测功能。新引擎的设计说明它不重用 `compareValues` 但有自己的比较。语义必须明确。

- **没有提到表达式错误部分求值**。在 `compileGroup` 中，如果表达式 A 通过，但依赖于 A 的表达式 B 失败，B 的变量槽会获得什么值？`undefined`？先前的值？错误？这会影响下游消费者。

- **没有提到 `compileExpression` 缓存**。设计说拓扑排序发生在编译时，但是 `compileExpression` 本身是否缓存？如果一个接收帧以 50fps 到达，并且每次调用 `compileExpression`，那么分配的 ~150 行 `AST + JS function` 将产生 `GC` 压力。消费者应该编译一次并重用 `CompileResult`，但这必须是明确的。

---

**歧义风险**：

- `"Flat Map<string, number | string | boolean>"` -- 这是否意味着引擎拒绝任何不是这三种类型的变量？如果消费者传入 `null`（例如，一个尚未接收的字段）会怎样？是编译错误？运行时错误？还是隐式地视为 `0`/`false`/`""`？两种解释对调用者都有重大影响。

- `"compileConditional(branches, fallback?, functions?)"` -- `branches` 是 `{condition: string, expression: string}[]` 吗？`fallback` 是字符串表达式还是字面值？设计在伪代码中没有显示类型签名，留下了歧义。
```

102	#### 2.2 编排层：主流程与控制流

148	#### 2.5 结构健康度与微重构
149	
150	固定节，每个 design 都要写。**评估对象**：第 2.1 / 2.2 节"变化"涉及的源码文件（新增不算，只看要改的）。

152	**评估维度**（任一显著就算"偏胖"）：
153	
154	- 行数：单文件 > 500 行（语言略有差异，TS/JS/Vue 偏严，Python 略松）
155	- 职责：一个文件混了 2 个以上不相关概念（编排 + 计算混写、UI + 数据请求 + 业务逻辑混写）
156	- 改动密度：本次要在同一文件改 / 加 3 处以上，且每处之间逻辑独立
157	
158	**结论二选一，必须显式写出来**：

160	```markdown

162	- {文件路径} — {行数 / 职责 / 改动密度三个观察点}
163	- ...
164	
165	##### 结论：{不做 | 微重构}
166	
167	##### 方案（仅"微重构"时填）

171	- 步骤序列（provable refactor）：

173	  2. ...
174	
175	##### 超出范围的观察（可选，仅提示不阻塞）

177	  → 建议后续走 `cs-refactor` 处理，本 feature 不动
178	```

180	**判据**：
181	
182	- 选"微重构"必须满足"只搬不改行为"——能用 IDE 的 rename / move + 编译器校验完成。一旦涉及改函数签名 / 改返回值结构 / 改调用关系语义 / 模块拆合，**不要在 design 里做也不要作为前置依赖**——写进"超出范围的观察"提示用户走 `cs-refactor`，本 feature 照常推进

### IMPORTANT 问题

**[IMPORTANT-1] `&&`/`||` 返回 boolean (`!!`)，丢失了原始值语义**

文件: `compile.ts:77-78`
```typescript
case '&&': return (v) => !!(left(v)) && !!(right(v));
case '||': return (v) => !!(left(v)) || !!(right(v));
```

设计文档定义 `EvalResult.value` 类型为 `number | string | boolean`，`&&`/`||` 返回 boolean 是合理的。但 JS 的 `&&`/`||` 实际会短路返回原始值，`!!()` 强制转换后丢失了 `number` 类型的短路语义。例如 `(a > 0) && (b > 0)` 本应返回 boolean，当前实现也确实返回 boolean，这不是 bug。

但存在一个更微妙的问题: 如果 `left(v)` 抛异常（例如变量不存在），JS `&&` 短路不会执行 `right(v)`，这是正确的。但如果 `left(v)` 返回 0 (falsy)，`!!(left(v))` 仍然会求值 `right(v)`，这也是正确的 JS `&&` 语义。**当前实现语义正确，此项降级为 NOTE。**

实际评估: **非问题**，维持原实现。

**[IMPORTANT-3] `evaluateConditional` 对 condition 结果只检查 `=== true`，不处理 truthy number/string**

```
### 差距

- **`_internal.ts` 未在设计目录结构中列出** — 风险: 低 — 设计文档列出 `types.ts`/`compile.ts`/`evaluate.ts`/`functions.ts`/`tokenizer.ts`/`parser.ts`/`dependency.ts`/`index.ts` 共 8 个文件，实际多出 `_internal.ts`。这是一个合理的内部类型集中文件，将 `Token`/`ASTNode`/`BinaryOp` 等从各模块共享的类型定义集中管理。功能上不违反任何设计约束（不导出公开 API）。建议在设计文档中补录此文件。
- **`CompiledExpr`/`CompiledConditional`/`CompiledGroup` 的公开导出** — 风险: 低 — 设计中标注"不透明编译产物 — 调用方不访问内部结构"，但 `index.ts` 和 `shared/index.ts` 都导出了这三个接口的类型。调用方可以看到 `_fn`/`_deps`/`_branches`/`_order`/`_compiled` 属性。这些属性以下划线前缀暗示内部使用，但 TypeScript 无法阻止访问。严格意义上违反了"不透明"的设计意图，但实际风险极低（调用方正常使用 `compileExpression`/`evaluate` 即可，无动机直接访问内部属性）。若要严格执行，可改为 `class` 并将属性标记为 `private`，但这不是阻断性问题。
- **E1 数值精度** — 风险: 低 — 设计期望 `value 近似 0.000778`，测试用 `toBeCloseTo(0.000778, 5)`。实际计算 `(2500+100)*0.299792458/1000000 = 0.00077946`。测试断言精度 5 位有效数字（即 `0.0007794...` 在 `0.000778` 的 5 位有效范围内），通过但不完全精确。数值差异来源于浮点精度，属于正常范围。
```
