Two clarification points:

**1. Three.js 不是这个场景的工具**

Three.js 是 WebGL 3D 渲染库（做 3D 图形/场景用的）。拖拽排序和面板调整是 2D 交互，用它属于杀鸡用牛角——引入一个 ~600KB 的 3D 引擎只为了拖拽 div，完全不合适。

**2. 实际上有两类不同的"拖拽"需求**

| 需求 | 场景 | 正确方案 |
|------|------|---------|
| **字段排序拖拽** | 帧编辑页字段列表 | vuedraggable（~15KB，SortableJS 的 Vue 封装） |
| **面板宽度拖拽调整** | display 页表格面板、历史分析左右分栏 | QSplitter（Quasar 内建） |

**面板可调宽度**：Quasar 的 QSplitter 就是干这个的，零额外依赖。架构设计里已经为历史分析预留了 QSplitter。display 页面的多面板布局如果要做可调宽度，同样用 QSplitter 包裹面板容器即可。

```
┌─────────────────────────┬─╫─┬─────────────────────────┐
│  Panel 1                │ ║ │  Panel 2                │
│  (可拖拽 ╫ 调整宽度)     │   │                         │
└─────────────────────────┴───┴─────────────────────────┘
                      QSplitter
```

**建议**：
- 字段排序 → vuedraggable（或者 MVP 先上移下移，后续升级）
- 面板调整 → QSplitter（display 页和历史分析页需要时加）

**关键点**：

| 项 | 方案 |
|---|---|
| 面板增删 | 数组 push/splice，每个面板有 [✕] 关闭按钮 + 页面有 [+ 添加面板] |
| 面板配置持久化 | DisplayPreferences 里存 panels 数组（帧分组+模式+位置） |

## 方案对比

| 方案 | 效果 | 复杂度 | 依赖 |
|------|------|--------|------|
| **A: QSplitter + 增删面板** | 线性分栏，可调宽度，可增删 | 低 | Quasar 内建 |
| **B: vue-grid-layout** | 任意网格，拖拽位置+拖拽尺寸，类 Grafana | 中 | 第三方库 ~30KB |

**方案 B（vue-grid-layout）** 是业界标准做法，Grafana、Kibana 这类仪表盘都靠它或同类库：

## 我的判断

| 维度 | 评估 |
|------|------|
| **需求真实性** | 工业上位机经常需要同时看多个参数组，可调布局是真实需求 |
| **收益** | 方案 A 能覆盖 80% 场景（线性分栏够用），方案 B 覆盖 100% |
| **成本** | B 比 A 多约 1-2 天开发量 + 引入一个依赖 |
| **风险** | vue-grid-layout 社区活跃度中等，Vue 3 版本有 grid-layout-plus 维护 |

**建议**：分两步走——

1. **MVP 用方案 A**（QSplitter + 增删面板），先跑通功能
2. 如果用户反馈确实需要自由布局，再升级到方案 B，作为 display 页面的二期增强

从设计文档里挑出 5 个值得在实施前讨论的点。

### 1. `replaceFrames` 读-改-写模式会污染页面代码

每个单帧操作（收藏切换、删除、复制）都是"读全量 → 改一条 → 写回全量"。页面组件会充斥这种模板：

```ts
// 收藏切换
const frames = findFrameAssets(source)
const idx = frames.findIndex(f => f.id === id)
frames[idx] = { ...frames[idx], isFavorite: !frames[idx].isFavorite }
replaceFrames(frames)
```

每个操作都要写一遍，而且 `findFrameAssetSummaries` 返回的是摘要不是完整帧，还得额外调 `findFrameAssets` 拿全量数据。

**建议**：在页面和 service 之间抽一个轻量 composable（如 `useFrameMutations`），封装 `toggleFavorite(id)`、`cloneFrame(id)`、`deleteFrame(id)` 这些高频操作，页面只调一行。不改变 service 层 API，只在消费方做糖。

### 2. `JSON.stringify` dirty tracking 对复杂帧对象有隐患

帧对象包含 `fields[]`（含 expression 变量映射、条件表达式嵌套对象）、`identifierRules[]`、`options` 等。`JSON.stringify` 全量比较：
- 每次字段编辑对话框关闭都会触发一次 stringify
- expression 对象有函数不可序列化的风险（虽然当前设计是纯数据）
- 未来如果帧对象变大（比如 display 用到的 chart 配置挂上去），成本会线性增长

**建议**：用版本号或脏标记代替 stringify 比较。帧编辑器维护一个 `dirtyVersion` ref，每次修改 workingFrame 的子组件 emit 时递增。保存时重置。比 stringify 可靠且零成本。

### 3. `startTickDriver` 连接页的副作用过大

design 写连接页用 `runtime.startTickDriver()` 刷新状态。但 `startTickDriver` 触发的是完整数据管线：`drainAdapterEvents → consumer chain → receive → display fanout → storage fanout`。连接页只需要连接 lifecycle 状态，不需要驱动整条数据管线。

如果连接页是用户打开的第一个页面（或唯一页面），startTickDriver 会启动整个数据引擎，但实际上没有任何帧数据需要路由。

**建议**：连接页直接用 `setInterval` + `service.getSnapshot()` + `selectConnectionSummaries()` 轮询连接状态。tick driver 留给需要数据流转的页面（receive/display）启动。或者给 `startTickDriver` 加一个 `mode` 参数，连接页只启动轻量模式（只 drain adapter events 更新连接状态，不走 consumer chain）。

### 4. `discoverResources` 要求 UI 穿透到 adapter 层

设计写串口枚举调用 `RealSerialAdapter.discoverResources()`，但 adapter 不是 service 的公开 API。UI 页面不应该知道 adapter 的存在——它应该只依赖 `ConnectionService` 或 `ConnectionReader`。

当前 `ConnectionService` 接口没有 `discoverResources`，只有 adapter 上有。

**建议**：在 `ConnectionService` 或 `ConnectionReader` 接口上加 `discoverResources(): Promise<ConnectionResourceCandidate[]>`，内部委托给对应的 adapter。UI 只调 service，不碰 adapter。

### 5. 连接页 composable 缺位

连接页的状态管理比帧列表复杂：`operatingIds`（防重入）、`serialCandidates`（串口枚举）、autoConnect toggle、连接/断开/删除三套异步流程。这些都写在 `ConnectionPage.vue` 里会让页面组件膨胀。

**建议**：抽 `useConnectionPage` composable，封装连接操作（含防重入、错误处理、notify）和串口枚举。页面组件只管渲染和事件绑定。

### 补丁 1：`replaceFrames` 读-改-写模板

**根源**：service 层只暴露了 `replaceFrames`（全量替换），但 UI 的所有操作都是单帧级别（收藏、复制、删除）。每个操作被迫写成"读全量 → 改一条 → 写回全量"。

**补丁代码长这样**：
```ts
// useFrameMutations 内部 — 为了切一个 boolean 要读 500 条帧
async function toggleFavorite(id: string) {
  const all = findFrameAssets(source)           // 读全量
  const modified = all.map(f => 
    f.id === id ? { ...f, isFavorite: !f.isFavorite } : f  // 改一条
  )
  await replaceFrames(modified)                  // 写回全量
}
```

**问题**：`useFrameMutations` composable 本身就是为这个模式打的补丁。而且 `frame-state.ts` 里已经有 `upsertFrame` 方法，只是没通过 service 暴露。

### 补丁 2：`connect(config: unknown)` 类型不安全

**根源**：service 签名是 `connect(config: unknown)`，UI 层被迫用工厂函数补类型安全。

**补丁代码**：

```ts
// 为了绕过 unknown，在 UI 层建了一套工厂函数
export function buildSerialConfig(input: { portPath: string; baudRate: number }): SerialTransportConfig {

}
```

**问题**：类型安全是 service 层该保证的，不应该推给消费方。service 内部 `normalizeTransportConfig(input)` 本来就能处理 `TransportConfig` 类型。

**建议**：改 service 签名为 `connect(config: TransportConfig)`。内部 `normalizeTransportConfig` 不变，只是类型更精确。工厂函数可以保留（构造便捷），但不再是类型安全的唯一防线。

### 补丁 3：连接页用 tick driver 刷新 UI

**根源**：design 写"startTickDriver → getSnapshot → selectConnectionSummaries"，但 tick driver 是全局数据路由引擎（drain → consumer chain → receive → display → storage）。连接页只需要连接状态，不需要驱动整条数据管线。

**补丁代码**：
```ts
// 为了看 5 个连接的状态，启动了整条数据路由引擎
```

**建议**：连接页用独立的 `setInterval` + `service.getSnapshot()` + `selectConnectionSummaries()`，和 tick driver 完全无关。简单、干净、不产生副作用。

### 补丁 4：connect 失败后清 config
