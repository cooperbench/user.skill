## 1. 旧代码共性分析

### Task Executor 模式（`useSendTaskExecutor.ts`）

- **序列执行**：`processMultipleInstances` 按顺序 await 每个实例，前一帧完成后发下一帧
- **发送调用**：`sendFrameInstanceUnified(targetId, instance)` → `useUnifiedSender`
- **结果处理**：检查 `result.success`，失败时检查 `isTargetAvailable`，不可用时 pause
- **错误策略**：any-fail-stop，无显式重试；pause-on-disconnect
- **进度追踪**：`currentCount`、`percentage`、`currentInstanceIndex`，批量更新走 `updateTaskProgressCached`
- **定时器**：`useTimerManager` 管理 interval/timeout 生命周期，pause 时 cleanup，resume 时重建

### SCOE Command Executor 模式（`useScoeCommandExecutor.ts`）

- **命令路由**：`executorMap` 将 `ScoeCommandFunction` 映射到具体执行函数（策略模式）
- **发送调用**：同走 `useUnifiedSender.sendFrameInstance`，**硬编码** target `'network:scoe-udp:scoe-udp-remote'`
- **结果处理**：检查 `result.success`，维护 `commandSuccessCount`/`commandErrorCount`
- **完成条件**：`waitForCompletionConditions(command, params)` 异步轮询等待 SCOE 响应满足条件
- **确认帧**：完成条件满足后 `sendSuccessFrame()` 发确认帧
- **定时器**：scoeStore 1 秒 interval 调 `updateStatus()` → `sendScoeFrames()`

### SCOE Store 的 `sendScoeFrames`

- `forEach(async ...)` 遍历所有 sendInstances — **有 bug**：forEach + async 不等前一帧完成
- 实际上是"逐帧发送但不等待"，不是真正的序列

### 共性对照表

| 模式 | Task Executor | SCOE Executor | 共性程度 |
|---|---|---|---|
| 序列执行（await 前一帧再发下一帧） | `processMultipleInstances` 严格顺序 | 单命令执行；`sendScoeFrames` 有 bug | **低** |
| 发送调用方式 | `useUnifiedSender` | 同 `useUnifiedSender` | **高** |
| 结果检查 | `result.success` + target availability | `result.success` + 错误计数 | **中** |
| 错误策略 | pause/skip/stop（可配置） | 直接计数，无 pause/retry | **低** |
| 重试 | 无（task 层策略） | 无 | **无** |
| 进度追踪 | currentCount/percentage/instanceIndex | commandSuccessCount/ErrorCount | **低** — 概念不同 |
| 定时器管理 | `useTimerManager` | `useTimerManager` 1秒轮询 | **高** |
| 领域特有逻辑 | 无 | 完成条件轮询 + 确认帧 + 命令路由 | **无共性** |

### 关键发现

1. **共性集中在基础设施层**（发送入口、定时器管理），不在编排逻辑层
2. **Task 的编排模式更复杂**：三种调度模式 + 完整 lifecycle + error policy
3. **SCOE 的核心模式是"命令-响应-确认"**：收命令 → 执行 → 等完成条件 → 发确认帧。这与 task 的"按序列发多帧"在结构上完全不同
4. **SCOE 不存在真正的多命令序列编排**：当前是单命令执行，`sendScoeFrames` 的 forEach+async 是 bug 不是序列语义

## 2. 三种方案对比

### 方案 A：当前设计不变

task 和 SCOE 各自编排，send 只做 transport queue。

- send design §4.3 QueueModel = transport-level FIFO
- task design §4.4 执行循环 = `await sendService.execute(request)` 实现编排级等待
- SCOE 通过 runtime 或 send public service 发送单命令

**优点**：feature 边界清晰，不引入新抽象
**缺点**：如果 SCOE 未来需要多命令序列，可能重复实现 task 已有的调度逻辑

### 方案 B：引入通用执行引擎

task 和 SCOE 共享序列执行、错误策略、进度追踪等编排原语。

**问题**：
- 违反架构原则：runtime 不承载领域算法，shared 不承载业务 owner
- SCOE 的"命令-完成条件-确认帧"模式与 task 的"定时/触发/序列"差异远大于共性
- 引入的抽象层增加理解成本和耦合
- 当前 evidence 不支撑：共性在基础设施层不在编排层

### 方案 C：中间方案 — SCOE 复用 task 编排能力

**不引入新抽象层**。task 已提供的 scheduling/lifecycle/error policy 作为通用编排能力暴露给 SCOE。

- 单命令执行：SCOE 直接调 send service，不经过 task
- 多命令序列：SCOE 翻译为 TaskDefinition（schedulingMode=sequence），通过 task public service 创建任务
- SCOE 特有逻辑（完成条件、确认帧、状态循环）留在 SCOE feature 内
- send QueueModel 保持 transport-level FIFO 不变

这正是 task design §5.1 已经预见但未锁定的方向。

## 3. 推荐方案：C

**理由**：

1. **共性不足以支撑新抽象**。真正的共性在发送入口和定时器，不在编排逻辑。旧代码中 task 的 `processMultipleInstances`（严格序列+状态管理+错误策略）与 SCOE 的 `executeCommand`（单命令+完成条件轮询+确认帧）结构完全不同。
2. **task 已经是通用编排能力**。task design 定义了 timed/trigger/sequence 三种模式 + pause/resume/stop + error policy，足够 SCOE 复用。
3. **新抽象层违反架构原则**。target structure 和 quality rules 明确 runtime 不承载领域算法。一个跨 task/SCOE 的"执行引擎"要么归 runtime（违反原则），要么归 shared（不承载业务 owner），要么新建 feature（过度设计）。
4. **SCOE 实际需求不明确**。当前 SCOE 是单命令执行模式，`sendScoeFrames` 的 forEach+async 是 bug 不是序列语义。过早为假设需求引入抽象是已知的 anti-pattern。
5. **send QueueModel 当前定义足够**。task 通过 `await SendResult` 实现编排级等待；send queue 只处理 transport-level 并发 write。SCOE 直接调 send service 或通过 task 编排，不需要额外队列语义。

## 4. 对 send/task design 的修订建议

### send design 修订

**§4.6 SCOE interaction** 补充一段：

> SCOE 如需多命令序列编排，优先通过 task public service 创建任务（schedulingMode=sequence），不直接操作 send queue。send 不感知 SCOE 命令序列语义。SCOE 单命令发送直接通过 send public service 或 runtime 路由。

**§4.3 QueueModel** 不变。transport-level FIFO 已经足够。task 的"等前一次完成再发下一帧"通过 `await SendResult` 在 task 层实现，不在 send queue 层。

### task design 修订

**§5.1 SCOE 与 task 的边界** 锁定建议 1：

> SCOE 多命令序列通过 task public service 创建任务。SCOE 将命令序列翻译为 TaskDefinition（schedulingMode=sequence，每个命令对应一个 TaskCaseDefinition）。SCOE 领域特有的完成条件判断和确认帧发送留在 SCOE feature 内，通过以下方式之一与 task lifecycle 配合：

> - 方案 b：SCOE 监听 SendResult event，在 SCOE 内部执行完成条件逻辑
> - 方案 c：TaskDefinition.stopCondition 支持自定义条件回调（需 task design 扩展）
> 
> 具体方案在 SCOE design 中确定。

### 不需要修改的部分

- send QueueModel 定义
- send service contract（Promise\<SendResult\>）
- task lifecycle 状态机
- task error policy 模型
- send/task 的跨 feature 交互契约

## 重新理解

你指出的事实是：

- **SCOE 命令**：收到指令码 → 执行一系列帧发送 → 处理结果
- **Northbound task**：收到外部命令 → 执行一系列帧发送（用例）→ 处理结果
- **本地定时/触发**：用户配置 → 定时/触发器激发 → 执行一系列帧发送 → 处理结果
- **手动序列发送**：用户配置 → 点击开始 → 执行一系列帧发送 → 处理结果

**四者的核心模式完全相同**：入口触发 → 按计划执行一系列发送 → 错误策略 → 进度追踪。

区别仅在于**入口适配**：
- SCOE：TCP/UDP 收到指令码，解析后翻译为执行计划
- Northbound：HTTP 收到外部命令，翻译为执行计划
- 本地：用户 UI / 定时器 / 接收触发器 触发
- SCOE 的领域特有后处理（完成条件判断、确认帧发送）是执行计划的前/后步骤

## 这意味着什么

**task 不是"本地发送任务调度"—— task 就是通用的执行引擎。**

task 的核心职责是"接收一个执行计划（一系列发送步骤），按顺序执行，处理错误，追踪进度"。触发来源只是入口适配的不同。当前 send design 和 task design 把 task 定位得太窄了——限定为"本地定时/触发/序列发送"，SCOE 只是"可选复用"。实际上 SCOE 和 task **是同一类东西**。

## 需要修订什么

### task design 需要重新定位

当前 task design 的定位：

> 定时发送、甲方任务/用例执行上下文、调度、取消/停止/暂停/恢复语义

应调整为：

> 通用执行引擎——接收执行计划（一系列发送步骤），按顺序执行，处理错误策略，追踪进度。触发来源包括：用户 UI 配置、定时器、接收事件触发、SCOE 命令、northbound 外部命令。入口适配由调用方负责，执行逻辑由 task 统一提供。

核心类型需要体现"入口无关"：

- `TaskTriggerSource`：`user-ui` | `timer` | `receive-trigger` | `scoe-command` | `northbound-command`
- `TaskCaseDefinition` 就是"一个发送步骤"的抽象，SCOE 命令、northbound 用例、本地发送实例都是它的实例
- error policy、lifecycle、progress tracking 完全通用，不区分来源

### send design 的影响

send design 本身不需要大改，但需要明确：

- send **只做单帧发送**（构帧 + target 路由 + transport write + 结果输出）
- **任何"一系列发送"的编排都是 task 的事**，包括用户在 send 页面创建的定时/触发/序列
- send 页面的定时发送对话框、触发发送对话框、序列发送对话框本质上是在创建 TaskDefinition，通过 task service 执行
- send page 是 task 的一个入口适配器（triggerSource = user-ui）

### SCOE design 的方向（待写）

- SCOE 领域层：命令解析、完成条件判断、确认帧构建、SCOE 状态管理
- SCOE 执行层：**直接复用 task service**，SCOE 命令翻译为 TaskDefinition（triggerSource = scoe-command）
- SCOE 特有的后处理（完成条件轮询 → 确认帧发送）可以作为 TaskCaseDefinition 的 post-step 或 task completion event 的 SCOE 订阅者
- SCOE 不需要自己的"命令执行器"编排逻辑

### QueueModel 不受影响

send 的 transport-level FIFO 不变。task 的编排级等待通过 `await SendResult` 实现。

## 统一模型

task 的执行计划由多态 step 组成：

| Step 类型 | 语义 | 谁用 |
|---|---|---|
| `send` | 构帧 → 发送 → 得到 SendResult | 所有场景 |
| `wait-condition` | 订阅 receive 事件，等待条件满足或超时 | SCOE 完成条件、trigger 触发、northbound 等确认 |
| `delay` | 等待指定时长 | 帧间延迟 |

这样 SCOE 命令执行就是三个 step：

```
send-step（执行命令帧）
  → wait-condition-step（等 SCOE 完成条件：收到特定响应帧+字段匹配）
  → send-step（发确认帧）
```

本地定时发送就是一个 step 循环：

```
每轮: send-step（发配置帧）
```

触发发送是：

```
wait-condition-step（等 receive 触发条件）
  → send-step（发配置帧）
```

**同一个执行引擎，step 编排不同，入口适配不同。**

## 对各 design 的影响

### task design — 核心修订

1. **TaskCaseDefinition → TaskStepDefinition**（多态）
   - `kind: 'send' | 'wait-condition' | 'delay'`
   - `sendConfig`：frameId / fieldValues / targetId / options
   - `waitConfig`：condition（frameId + fieldId + operator + threshold）+ timeoutMs + onTimeout 策略
   - `delayConfig`：durationMs

2. **条件匹配逻辑归 task/core**
   - `wait-condition` 和 `trigger` 模式共用同一套条件匹配（frameId + fieldId + operator + threshold）
   - 纯 TypeScript，订阅 receive public event，匹配条件
   - SCOE 定义条件内容，task 执行匹配

3. **task 定位重写**
   - 不是"本地定时/触发发送调度"
   - 是"通用执行引擎"：接收 step 序列，按顺序执行，处理错误，追踪进度
   - 触发来源通过 `triggerSource` 和 `schedulingMode` 表达

4. **error policy 适用于所有 step 类型**
   - send-step 失败：retry / skip / stop / pause
   - wait-condition 超时：同上
   - delay 不可失败

### send design — 不变

send 只做单帧发送。所有 step 编排都是 task 的事。send 页面的定时/触发/序列对话框本质上是 task 的 UI 入口。

### SCOE design 方向

- **SCOE 不需要自己的执行器**。`useScoeCommandExecutor` 的编排逻辑完全由 task 承接
- SCOE 负责：命令解析（指令码 → step 定义）、完成条件定义、确认帧配置、SCOE 领域状态
- SCOE 命令 → task 的入口适配：把 SCOE 命令翻译为 TaskDefinition（triggerSource = scoe-command），通过 task service 创建并启动
- SCOE 订阅 task lifecycle event 更新自己的领域状态（commandSuccessCount 等）

## 架构过度复杂的地方

**1. 每个特征必须 8 层目录 — 不是每个特征都需要**

- `status` 是纯读模型聚合器，不需要 adapters，service 也很薄
- `display` 是偏好 + 投影，不需要 adapters
- `settings` 是配置事实，不需要 adapters/composables/components

建议：目录结构是约定不是强制。设计文档中已经写了"Do not assume all features need adapters"，应该推广到整个分层——**只创建该特性需要的层**。

**2. status 和 display 是否需要是独立特征？**

- **status** = 读 connection health + 读 receive stats + 读 task state → 聚合为健康摘要。没有自己的底层事实，纯聚合。可以是 runtime 层的 composition + 一组纯函数，不一定要完整特性。

**3. TaskExecutionSummary 是否多余？**

TaskInstanceState 在完成时已经有 lifecycle + progress + stepResults。TaskExecutionSummary 是 completion 时刻的快照，可以从 InstanceState 派生。作为独立类型存在增加了维护负担——改一处要同步改另一处。

建议：**去掉 TaskExecutionSummary 类型，完成时 emit TaskInstanceState 的 completion 快照即可。** result feature 消费 InstanceState，不需要中间类型。

**4. errorPolicy 中的 retry 是否应该更简单？**

当前 errorPolicy 有 retry/skip/stop/pause 四种，retry 还有 retryCount + retryDelay。但对于大多数场景（本地发送、SCOE），retry 的需求很有限。旧代码中 SCOE 没有 retry，task 的 retry 也是简单重试。

这不是过度复杂，只是比必要多一些。可以先保留，实现时看是否简化。
