54	## 3. Hard Decisions
55	
56	### 3.1 Scope
57	
58	- 旧功能尽量保留，除非明确高成本低价值、只是旧占位、与新需求冲突，或会污染新模型。
59	- frame asset 是独立业务对象；收藏可以保留；不要求兼容旧 JSON 内部格式。
60	- 旧 JSON 通过迁移脚本或导入适配进入新模型，不污染新核心类型。
61	- 定时发送是已使用能力，必须保留。
62	- 旧 task 的其他形态默认作为兼容候选，不作为新系统中心模型。
63	- SCOE 保留为专项能力和复用材料，但不直接并入当前甲方 northbound 身份。
64	
65	### 3.2 Architecture
66	
67	- 目标目录按职责组织，不按旧文件热点组织。
68	- `features/frame`、`connection`、`receive`、`send`、`task`、`scoe`、`storage`、`settings`、`status`、`result`、`report`、`northbound` 是当前功能归口。
69	- `runtime` 只做应用级装配、跨域编排和边界例外登记，不承载领域算法。
70	- 页面和组件只负责交互、展示和调用公开入口，不直接拥有复杂业务流程。
71	- receive/send/task/SCOE/storage/status/result/report/northbound 之间必须通过显式输入输出、service、command、event 或 runtime 编排交互。
72	
73	### 3.3 Electron
74	
75	重写口径固定为：

77	```ts

79	contextIsolation: true
80	sandbox: false
81	```

51	## 4. Hard Rules
52	
53	### R1. Preserve behavior, replace structure
54	
55	MUST:
56	
57	- 默认保留旧系统用户可见能力。
58	- 只在明确低价值、高成本、冲突或旧占位时，才把功能列入排除候选。
59	- 将旧功能重写到新的边界中，而不是把旧目录、旧 store 和旧 IPC 复制一遍。
60	
61	MUST NOT:
62	
63	- 因为质量规则而顺手砍旧功能。
64	- 把“旧代码很脏”理解成“旧行为不重要”。
65	- 把未讨论的功能降级成 future work。
66	
67	### R2. Feature ownership must be explicit
68	
69	MUST:
70	
71	- 按 `features/frame`、`connection`、`receive`、`send`、`task`、`scoe`、`storage`、`settings`、`status`、`result`、`report`、`northbound` 归口业务能力。
72	- 每个 feature 只能直接修改自己的状态。
73	- 跨 feature 流程必须通过公开 service、runtime 编排、显式事件或边界输入输出发生。
74	- 每个 feature 的外部入口必须明确；外部只能通过 public API 调用，不直接依赖内部实现。
75	
76	MUST NOT:
77	
78	- feature A 直接 import feature B 的内部 `state` 并修改。
79	- feature A 直接 import feature B 的内部 service、adapter、composable 或私有 helper。
80	- 用一个大 store 同时承载主状态、展示态、缓存态、任务调度和多下游副作用。
81	- 让页面组件长期持有运行主状态或任务生命周期事实。
82	
83	### R3. Core logic must be testable TypeScript
84	
85	MUST:
86	
87	- 将 receive 解析、send 构帧、SCOE 协议、task 状态推进、storage 迁移、result/report 生成等核心规则放在可测试的 TypeScript 层。
88	- `features/*/core` 不依赖 Vue、Pinia、Electron、`window.electron`、`ipcRenderer`、`fs`、`serialport`。
89	- 核心逻辑通过明确输入和输出表达行为。
90	
91	MUST NOT:
92	
93	- 把解析、构帧、协议校验、任务推进写在 Vue 组件里。
94	- 在 core 逻辑里读取全局 store 补上下文。
95	- 在 core 逻辑里直接访问平台能力。
96	
97	### R4. UI is not the business workflow owner
98	
99	MUST:
100	
101	- 页面和组件只负责用户交互、表单状态、展示和调用公开入口。
102	- 复杂流程由 feature service 或 runtime 编排承接。
103	- composable 只做 UI-facing 组合，例如表单状态、对话框状态、生命周期订阅、selector 组合和调用公开 service。
104	
105	MUST NOT:
106	
107	- UI 组件直接创建并启动任务状态机。
108	- UI 组件直接读写文件、串口、网络 socket。
109	- UI 组件直接修改其他 feature 的内部状态。
110	- UI 组件承担导入校验、任务策略分支、实例引用检查等完整业务流程。
111	- composable 承载协议解析、任务状态机、统计累加、跨域业务流程或跨 feature 写状态。
112	
113	### R5. Electron capability boundary must stay narrow
114	
115	MUST:
116	
117	```ts
118	nodeIntegration: false
119	contextIsolation: true
120	sandbox: false
121	```
122	
123	MUST:
124	
125	- renderer 只通过 `rewrite/src/platform` facade 访问桌面能力。
126	- preload 只暴露 typed API。
127	- main 只承接平台资源访问和生命周期。
128	- main 可以承接与平台资源绑定且性能压力明显的高频数据缓冲、批处理、聚合、节流、队列和背压。
129	- 文件、串口、网络、定时器、窗口能力都要有明确 platform API。
130	
131	MUST NOT:
132	
133	- 暴露裸 `invoke/send/on`。
134	- 在 renderer 直接使用 `ipcRenderer`、`fs`、`path`、`net`、`serialport`。
135	- 把领域业务规则放进 main 进程。
136	- 把业务运算、协议语义、任务状态推进、报告语义或 northbound 领域规则搬进 main 进程。
137	- 允许任意路径读写成为常规业务 API。
138	
139	### R6. IPC must be coarse-grained and intentional
140	
141	MUST:
142	
143	- 以业务能力为单位设计 typed platform API。
144	- 对高频串口/网络数据使用批量、缓冲、聚合或节流策略。
145	- 明确哪些数据在 main 处理、哪些结果进入 renderer。
146	- 性能处理优先使用数据流设计、队列、背压、采样和事件压缩，不用主进程业务化换取表面简单。
147	
148	MUST NOT:
149	
150	- 为每个组件动作散落一堆小 IPC。
151	- 高频字节流逐包无节制穿透到页面和全局 store。
152	- 让 IPC 通道名成为业务流程本身。
153	
154	### R7. Runtime state must have one owner
155	
156	MUST:
157	
158	- 区分主状态、派生态、展示态、记录态、缓存态。
159	- 主状态单点写入。
160	- 派生态、展示态、记录态、缓存态只能消费或展示事实，不得反向塑造主状态语义。
161	- store 只承载本 feature 的状态、read model、selector 和很薄的本域 action。
162	
163	MUST NOT:
164	
165	- 用接收缓存、页面监控状态、历史记录状态、测试工具状态替代运行主状态。
166	- 让 receive/send/SCOE/status/report 各自宣布系统当前生命周期。
167	- 让本地发送 task 直接等同甲方中心 task。
168	- 把 store 当作 service locator、跨域编排器或平台能力入口。
169	- store A 直接修改 store B 的内部 state。
170	
171	### R8. Receive and send chains must remain explicit
172	
173	MUST:
174	
175	- receive 主链只承接输入、解析、归一和输出明确接收结果。
176	- send 主链只承接发送请求、构帧、目标落地和输出发送结果。
177	- receive/send 与 task、SCOE、storage、status、result 通过显式输入输出交互。
178	
179	MUST NOT:
180	
181	- receive 主链直接决定任务生命周期。
182	- send 主链硬编码 SCOE、northbound 或 report 语义。
183	- 把显示、历史、触发、SCOE、统计继续作为 receive 解析尾部同步副作用堆在一起。
184	
185	### R9. SCOE must be a declared domain exception
186	
187	MUST:
188	
189	- 将 SCOE 作为领域模块或领域例外处理。
190	- 固定来源、固定目标、命令语义、完成条件、反馈语义、测试工具记录都应归在 SCOE 边界内。
191	- SCOE 进入 receive/send/task 时，必须通过显式领域入口、显式发送请求或显式任务请求。
192	
193	MUST NOT:
194	
195	- 把 SCOE 固定 source/target 硬编码在通用 receive/send 主链里。
196	- 让 SCOE 通过共享状态回读定义任务是否完成。
197	- 把 SCOE 测试工具记录抬成统一运行主状态。
198	
199	### R10. Northbound must be a boundary, not a feature shortcut
200	
201	MUST:
202	
203	- `northbound` 独立承接中心协同接入、对外投影、对外交付和外部错误语义。
204	- 外部任务、状态、心跳、结果、报告、文件回传都必须经过 northbound 边界转换。
205	- northbound 从 task/status/result/report/storage 读取内部事实或素材，但不得直接定义这些内部事实。
206	
207	MUST NOT:
208	
209	- 把旧 send task 当作 `setTestTask/controlTestTask`。
210	- 把 history/CSV 当作 TestReport 交付闭环。
211	- 把 serial/network target 当作 northbound device/deviceId。
212	- 把外部成功/失败/拒绝/不可执行语义散落到 task/send/report/storage 内部。
213	
214	### R11. Result, report, delivery must stay separate
215	
216	MUST:
217	
218	- `result` 归口内部结果事实。
219	- `report` 归口报告对象和报告文件生成。
220	- `northbound` 归口对外交付、回执和错误语义转换。
221	
222	MUST NOT:
223	
224	- 因为报告交付失败而反向改写内部结果事实。
225	- 在 task/send/receive 中直接拼外部报告。
226	- 把报告对象生成和 FTP/HTTP 上传写成同一个职责。
227	
228	### R12. Legacy JSON compatibility must not pollute new models
229	
230	MUST:
231	
232	- 旧 JSON 通过迁移脚本或导入适配进入新模型。
233	- 新核心类型和存储结构按重写后的业务边界设计。
234	
235	MUST NOT:
236	
237	- 为兼容旧 `framesConfig` 或旧路径常量扭曲新领域模型。
238	- 在新核心逻辑里到处判断旧 JSON 形态。
239	- 把旧 data path 直接固化为新长期存储设计。
240	
241	### R13. Statistics must not pollute source models
242	
243	MUST:
244	
245	- 将静态资产、运行事实、统计 read model 和 UI snapshot 分开。
246	- 帧定义、字段定义、表达式和展示配置等静态对象只表达配置事实。
247	- 接收命中数、最近值、错误计数、速率、发送结果等统计由对应 feature 的 read model 按稳定 key 增量维护。
248	- 高频统计更新使用 batch、delta、队列、节流或 snapshot，避免全量替换大对象。
249	- 每个统计项必须有明确 owner、reader、reset 时机、生命周期、是否持久化和验证方式。
250	
251	MUST NOT:
252	
253	- 把运行统计写回 frame list、字段定义、配置对象或其他静态资产对象。
254	- 为了页面展示把多个 feature 的状态揉成一个可写全局对象。
255	- 让页面组件订阅底层高频事件并参与统计累加。
256	- 通过全局事件总线隐式修改其他 feature 的内部 state。
257	- 用全量刷新 frame array 或大 store 对象响应每次接收/发送事件。
258	
259	### R14. Services and dependency wiring must stay explicit
260	
261	MUST:
262	
263	- feature service 作为业务用例入口，负责调用 core、写入本 feature store、调用 adapter 或通过公开接口协作。
264	- `runtime/` 作为组合根，负责 service、adapter 和上下文的创建、显式注入和释放。
265	- 依赖通过构造函数、工厂函数或明确 runtime context 传入，以便测试替换。
266	- 组件和页面通过 feature composable 或 runtime 页面级 API 调用公开入口。
267	
268	MUST NOT:
269	
270	- 使用全局 singleton service 到处 import。
271	- 在 store 中创建 service、保存 platform adapter 或访问 Electron/Node 能力。
272	- 组件直接 import service 内部实现并绕过 composable / runtime 入口。
273	- 为了“解耦”引入无明确生命周期、测试收益或跨域装配收益的复杂 DI 容器。
274	- 让 service 绕过公开接口直接修改其他 feature 的内部 state。
275	
276	### R15. Contracts and gate outcomes must be explicit
277	
278	MUST:
279	
280	- 每轮实现和审查必须列出 `Direct contract` 与 `Boundary guards`。
281	- 直接合同缺失、用户决策缺失、甲方口径缺失、关键 baseline 缺失时，结论必须是 `blocked`。
282	- 边界违规、跨 feature 内部写入、runtime/store/composable 业务化、main 业务化时，结论必须是 `revise-required`。
283	- `pass-with-known-gaps` 只用于语义已锁定但 runtime/hardware/customer 环境验证尚未完成的情况。
284	
285	MUST NOT:
286	
287	- 用 handoff、摘要、临时 prompt 或边界护栏替代正式直接合同。
288	- 用 `pass-with-known-gaps` 掩盖 northbound 语义、schema/枚举、task/case、deviceId、stop 状态、result/report/delivery 口径缺失。
289	- 用 build/lint 通过替代合同完整性、边界合规性或 runtime/hardware 证据。
290	
291	### R16. Rewrite infrastructure must stay minimal and explicit
292	
293	MUST:
294	
295	- 将 `rewrite/` 作为新的独立应用根目录，而不是只把源码挪到一个子目录。
296	- 新 renderer 源码落在 `rewrite/src/`，新 Electron 边界落在 `rewrite/src-electron/main/` 和 `rewrite/src-electron/preload/`。
297	- 从旧配置复用依赖类别和构建能力前，重新收缩 package scripts、Quasar entry/boot、Electron entry、public/extraResources、tsconfig、ESLint、UnoCSS、Vitest 和 auto-import 配置。
298	- 使用 Vitest 作为 `core`、`services`、`adapters`、`selectors` 的默认单测栈。
299	- 页面交互先以 manual checklist 验证；Electron runtime、package、hardware 和 customer validation 单独登记。
300	
301	MUST NOT:
302	
303	- 把旧 Quasar boot、旧 `src/api/common`、旧 `window.electron`、旧 preload 聚合、旧 main business handlers 或旧 `public` 数据目录策略原样搬入 `rewrite/`。
304	- 用 Vitest 声明 Electron runtime、打包态 package、真实串口/TCP/UDP/SCOE 硬件或 customer closure 已完成。
305	- 用 auto-import 隐藏业务依赖；若引入 auto-import，只允许 Vue、Vue Router、Pinia 等基础框架 API，禁止自动导入 feature service、platform facade、runtime、store、feature public API、adapter 或带业务 owner 的 helper。
306	
307	## 5. Boundary Exceptions
308	
309	边界例外允许存在，但必须登记。
310	
311	每个例外至少写明：
312	
313	- 例外名称。
314	- 所属 feature。
315	- 为什么不能表达为通用输入 / 输出。
316	- 正式入口。
317	- 正式输出。
318	- 消费者。
319	- 自动 fixture、手工 checklist 或 runtime validation 方式。
320	
321	已知例外候选：
322	
323	- SCOE 固定来源进入 receive。
324	- SCOE 固定目标进入 send。
325	- SCOE 领域完成条件。
326	- 高速存储命中后短路普通 receive/display/trigger 链。
327	- northbound 外部拒绝、不可执行、失败语义转换。
328	
329	## 6. Anti-Patterns
330	
331	以下模式在重写代码中默认判为质量问题：
332	
333	- 页面组件里直接写串口、网络、文件、SCOE 协议或任务状态机。
334	- store 互相 import、互相修改内部状态。
335	- `receive` 逻辑直接调用 `send/task/storage/status` 的内部状态。
336	- `send` 逻辑硬编码 SCOE target 或 northbound 语义。
337	- `scoe` 逻辑散落在 receive/send/task 多处。
338	- main 进程写领域业务规则。
339	- preload 暴露裸 IPC 或大而全 `window.electron` 能力包。
340	- 高频数据逐包穿过 main -> renderer -> store -> 多 store 副作用链。
341	- 高频统计写回帧列表或静态配置对象，导致页面全量刷新。
342	- 页面组件直接订阅底层高频事件并累加统计。
343	- 用一个可写全局 store 同时承载静态资产、运行事实、统计和 UI 展示态。
344	- store 变成跨域 service locator 或平台能力入口。
345	- composable 变成隐藏业务 service。
346	- 组件直接 import service 内部实现并绕过公开入口。
347	- 为旧 JSON 兼容把新模型设计扭歪。
348	- 为了架构感堆 manager/event/command，但没有明确生命周期、跨域流程或验证收益。
349	
350	## 7. Required Review Evidence
351	
352	每个重写功能域合入前，至少提供：
353	
354	- 合同说明：`Direct contract` 和 `Boundary guards` 分别是什么。
355	- 行为范围说明：保留了哪些旧可观测能力。
356	- 边界说明：代码落在哪些 feature，依赖方向是否符合 `rewrite-target-structure.md`。
357	- 状态说明：主状态、派生态、展示态、记录态、缓存态分别在哪里。
358	- 统计说明：统计 read model 的 owner、key、reset 时机、生命周期、UI snapshot 更新策略。
359	- 分层说明：core、store、service、adapter、composable、page/component 各自承担什么。
360	- 注入说明：service / adapter / runtime context 如何创建和替换，是否存在全局 singleton。
361	- Electron 说明：是否通过 `platform` facade，是否新增 preload/main API。

151	## 7. Recommended Internal Feature Layout
152	
153	不是每个 feature 都必须完整拥有以下子目录。只有当职责确实存在时才创建。
154	
155	```text
156	features/<feature>/
157	  core/          # 纯 TS 规则、类型、算法；不得依赖 Vue/Electron/Pinia
158	  services/      # feature 内应用服务和用例入口
159	  state/         # feature 自己的状态归口，通常由 Pinia 或明确状态容器承载
160	  adapters/      # 调用 platform 或外部能力的适配层
161	  composables/   # 面向页面/组件的 Vue 组合层；不得拥有领域规则
162	  components/    # feature 内复用 UI；页面仍放 pages/
163	  fixtures/      # 领域测试样例、oracle 输入输出
164	```
165	
166	Rules:
167	
168	- `core/` 必须可单测，不依赖 UI、Electron 和全局 store。
169	- `state/` 只维护本 feature 的状态、read model、selector 和很薄的本域 action；不得直接修改其他 feature 的内部状态。
170	- `services/` 是业务用例入口，可以协调本 feature 内部对象；跨 feature 流程优先进入 `runtime/`。
171	- `adapters/` 可以调用 `platform/` facade，但不得把平台 API 继续向 `core/` 泄漏。
172	- `composables/` 只做 UI-facing 组合，例如表单状态、对话框状态、生命周期订阅、selector 组合和调用公开 service；不得承载协议解析、任务状态机、统计累加或跨域业务流程。
173	- `components/` 只服务本 feature 的局部 UI，不承担跨域流程编排。
174	
175	Top-level `rewrite/src/composables` 不作为重写默认归口。确需跨页面复用的 Vue 组合逻辑，必须先判断归属：属于某 feature 的放入该 feature，属于应用壳或全局 UI 行为的放入 `app/` 或 `widgets/` 对应边界；没有明确归属时不得新建万能 composable。
176	
177	### Fixture, oracle, and test placement
178	
179	测试材料跟随业务归口，不建立脱离 feature 的第二套事实来源。
180	
181	Rules:
182	
183	- feature 自己的输入样本、期望输出、失败样本、边界样本和旧系统 oracle 映射，优先放入 `features/<feature>/fixtures/` 或该 feature 对应测试目录。
184	- `core/` 测试只依赖明确输入输出，不依赖 Vue、Pinia、Electron、platform facade、真实文件系统或真实串口网络。
185	- 跨 feature 的 runtime 编排测试可以放在 `runtime/` 对应测试材料中，但测试断言必须通过 feature public API 和显式事件观察结果。
186	- 旧 JSON、历史文件、CSV、甲方材料和硬件采样可以作为 fixture 输入或 oracle 来源；进入新核心模型前必须经过 feature design 确认，不得直接污染核心类型。
187	- 每个 feature design 必须列出自动 fixture、手工 checklist、runtime / hardware validation 三类验证材料；没有运行证据时只能声明静态或 fixture 通过。
188	
189	### Feature public API
190	
191	feature public API 是跨 feature 访问边界，不是必须新增的接口层、文件模板或 schema。只有当外部 feature、page、widget 或 runtime 需要访问该 feature 时，才需要在对应 feature design 中说明允许入口。
192	
193	允许入口可以是已有 store/composable/service 中被明确认可的调用面，也可以是后续新增的 service、只读 selector、runtime 页面级入口或显式事件/command。Batch 0 不要求每个 feature 都创建 `public.ts`，不要求统一 event bus / command bus，也不要求没有外部消费者的 feature 预先定义 public API。
194	
195	Rules:
196	
197	- 外部 feature、page、widget 不得 import 其他 feature 的 `state/`、`adapters/`、内部 composable、内部 service 实现文件或私有 helper。
198	- feature 内部可以自由组织实现细节；同一 feature 内部不需要通过 public API 绕行。
199	- 如果存在外部消费者，feature design 或实现说明必须写清楚外部可用入口和禁止绕过的内部状态。
200	- 通过 public API 暴露的数据不得授予外部写入本 feature 内部 state 的能力。
201	- 有跨 feature 写入或流程推进时，必须说明 owner、调用方、输入输出边界、错误或拒绝语义和验证方式；没有跨 feature 消费时可以明确记录为不需要额外 public API。
202	- 事件/command 只在确实有异步广播、跨域解耦或多消费者收益时使用；使用时必须列出生产者、消费者、owner、触发时机和失败处理口径。
203	- 只读 selector 可以面向页面或其他 feature 暴露 read model / UI snapshot，但不得暴露可变引用，也不得让调用方回写主状态。
204	
205	### Pages, widgets, and feature components
206	
207	UI 代码按用户入口和复用范围归口，不按视觉相似度随意放置。
208	
209	Rules:
210	
211	- `pages/` 放路由页面、页面级布局和页面动作连接；页面可以调用 runtime 页面级 API 或 feature public API，但不拥有业务规则。
212	- `features/<feature>/components/` 放只服务该 feature 的组件，可以调用本 feature composable / selector / public service，不编排其他 feature 内部状态。
213	- `widgets/` 放跨页面复用、纯展示或全局 UI 行为组件；它只能消费明确传入的 props、只读 snapshot 或公开 selector，不直接订阅运行主状态。
214	- UI snapshot 是页面展示投影，不是事实源；页面可以筛选、分页、虚拟滚动和节流展示，但不得反向定义运行事实。
215	- 当一个组件同时需要多个 feature 的事实时，优先由 `runtime/` 或页面层组合只读输入，再传给组件；组件不得自己 import 多个 feature 内部 state 拼业务流程。
216	
217	## 8. Dependency Direction
218	
219	默认依赖方向：
220	
221	```text
222	pages/widgets
223	  -> feature composables or runtime page APIs
224	  -> features/<feature>/services or state selectors
225	  -> features/<feature>/core
226	  -> shared
227	
228	features/<feature>/adapters
229	  -> platform
230	```
231	
232	Allowed:
233	
234	- `pages` 调用 runtime 提供的页面级操作入口。
235	- `runtime` 调用多个 feature 的公开服务，完成应用级流程。
236	- feature 内部从 `services` 调用 `core`、`state`、`adapters`。
237	- composable 可以读取本 feature 的 store selector、管理 UI 生命周期并调用公开 service。
238	- `adapters` 调用 `platform` facade。
239	- `platform` 调用 preload 暴露的 typed API。
240	
241	Not allowed:
242	
243	- `core` 依赖 Vue、Pinia、Electron、`window.electron`、`ipcRenderer`、`fs`、`serialport`。
244	- feature A 直接 import feature B 的内部 `state` 并修改它。
245	- feature A 绕过 feature B 的 public API，直接 import B 的内部 service、adapter、composable 或私有 helper。
246	- 页面组件直接创建任务状态机、直接发串口/网络、直接读写本地文件。
247	- composable 变成隐藏 service，承载协议语义、任务推进、统计累加或跨 feature 写状态。
248	- store 变成 service locator，负责创建 service、保存 adapter 或访问 platform。
249	- `receive` 通过共享状态回读决定任务生命周期。
250	- `send` 为 SCOE 或 northbound 写硬编码特例。
251	- `northbound` 直接改写内部运行主状态或收发主链内部对象。
252	
253	## 9. Runtime Layer
254	
255	`runtime/` 不是新的大而全业务域。它只负责应用级装配和跨域编排。
256	
257	Recommended responsibilities:
258	
259	- 应用启动和销毁顺序。
260	- 确有跨 feature 或平台装配需要时，负责 manager / service 的创建、显式依赖注入和释放。
261	- 确有多消费者、异步解耦或跨域流程收益时，提供事件 broker 或 command dispatcher；它只表达路由、调用顺序和边界输入输出。
262	- 运行主状态归口层的装配。
263	- 边界例外清单和显式例外入口。
264	- 页面动作到 feature service 的路由。
265	
266	Must not:
267	
268	- 承载 receive 解析算法。
269	- 承载 SCOE 协议细节。
270	- 承载 report 字段生成规则。
271	- 承载协议判断、任务状态推进、统计含义、结果归因或 northbound 语义转换。
272	- 直接访问 Electron/Node 原生能力。
273	- 变成所有 feature 都依赖的全局杂物箱。
274	
275	### Service wiring and dependency injection
276	
277	重写默认采用轻量、按需的依赖装配，而不是全局 singleton 或重型 DI 框架。只有当生命周期、测试替换、平台资源装配或跨域编排有实际收益时，`runtime/` 才作为组合根创建 feature service、adapter 和必要上下文。
278	
279	Rules:
280	
281	- service 的依赖应通过构造函数、工厂函数或明确 context 传入，便于测试时替换 fake adapter、fake store 或 fake service。
282	- Pinia store 不是 service locator，不负责创建 service，不保存 Electron/platform 原生对象。
283	- 组件和页面不直接 import service 内部实现；单 feature 页面优先通过本 feature composable / store 调用，跨 feature 页面动作才考虑 runtime 页面级 API。
284	- 跨 feature 调用只通过明确认可的入口、runtime 编排、显式事件或边界输入输出发生。
285	- 不为“架构感”引入复杂容器；只有在生命周期、测试替换或跨域装配有实际收益时才增加抽象。
286	
287	### Runtime state and statistics read models
288	
289	重写后不得用一个全局大 store 承载所有运行事实、统计数据和页面展示态。全局编排可以存在，但事实源和写入权必须留在明确的 feature 边界内。
290	
291	Layering:
292	
293	- 静态资产：帧定义、字段定义、表达式和 frame-owned 展示元数据等低频可编辑对象，归 `features/frame`；运行中的展示偏好、表格/图表/星座图 projection 和 UI-safe snapshot 归 `features/display`。
294	- 运行事实：连接状态、接收结果、发送结果、任务状态、SCOE 状态等，由对应 feature 单点写入。
295	- 统计 read model：由对应 feature 基于显式事件或结果增量维护，按 `frameId`、`fieldId`、`targetId`、`taskId` 等稳定 key 索引。
296	- UI snapshot：面向页面的只读展示投影，可以节流、分页、虚拟滚动或按需组合，不反向写入主事实。
297	
298	Rules:
299	
300	- 帧列表和其他静态资产对象不得承载高频运行统计；接收命中数、最近值、错误计数、速率等统计不得写回 frame definition。
301	- 高频链路应以 batch / delta 推进：平台侧批量输入，领域 core 处理批次，统计 read model 增量更新，页面消费节流后的 snapshot。
302	- 页面和组件不得直接订阅底层高频事件，不参与统计累加，只调用公开入口和展示只读投影。
303	- 事件只能作为 feature 边界输出或 runtime 编排输入；事件类型和消费者必须明确，禁止把事件总线变成隐式跨 feature 写状态的通道。
304	- 每个统计项必须说明 owner、reader、reset 时机、生命周期、是否持久化以及验证方式。
305	- main 可以做平台侧缓冲、批处理、聚合、节流、队列和背压，但业务统计含义仍归口到可测试 TypeScript 层。
306	
307	## 10. Electron Boundary
308	
309	重写目标配置：
310	
311	```ts
312	nodeIntegration: false
313	contextIsolation: true
314	sandbox: false
315	```
316	
317	Directory implications:
318	
319	```text
320	rewrite/src/platform/          # renderer facade
321	rewrite/src-electron/preload/  # typed bridge
322	rewrite/src-electron/main/     # platform resources
323	```
324	
325	Rules:
326	
327	- `platform/` 是 renderer 业务代码访问桌面能力的唯一正式入口。
328	- preload 只暴露 typed API，不暴露裸 `invoke/send/on`。
329	- main 负责串口、网络 socket、文件系统、系统对话框、窗口控制、定时器等平台资源。
330	- main 不承载 receive/send/SCOE/task/report 的领域规则。
331	- main 可以承接与平台资源绑定且性能压力明显的高频数据缓冲、批处理、聚合、节流、队列和背压；业务运算、协议语义、任务状态推进、报告语义仍归口到可测试 TypeScript 层。
332	- 高频串口/网络数据不得逐包无节制穿透到页面和全局 store；需要批量、缓冲、聚合或节流策略。
333	
334	## 11. Boundary Exception Registry
335	
336	领域例外可以存在，但必须显式登记，不能隐式沉积在通用链路里。
337	
338	Exception record should include:
339	
340	- 例外名称。
341	- 所属 feature。
342	- 为什么不能表达为通用输入 / 输出。
343	- 正式入口。
344	- 正式输出。
345	- 谁消费它。
346	- 如何测试或手工验证。
347	
348	Known candidates:
349	
350	- SCOE 固定来源进入接收主链。
351	- SCOE 固定目标进入发送主链。
352	- SCOE 领域完成条件。
353	- 高速存储命中后短路普通 receive/display/trigger 链。
354	- northbound 外部拒绝 / 不可执行 / 失败语义转换。
355	
356	## 12. Northbound Placement
357	
358	`northbound/` 是独立边界 feature，不是 task、status、report 的别名。
359	
360	Responsibilities:
361	
362	- 接收中心侧任务、控制、查询、保活、文件请求。
363	- 把外部请求转换为内部显式输入。
364	- 从内部 task/status/result/report 读取投影。
365	- 统一转换对外成功、失败、拒绝、不可执行、异常语义。
366	- 承接对外回执、结果上报、报告交付和文件回传。
367	
368	Must not:
369	
370	- 直接占有任务系统定义权。
371	- 直接把外部字段写成内部主状态字段。
372	- 直接把 history/CSV 文件当作 report 交付闭环。
373	- 把外部响应语义散落到 task/send/report/storage 各处。
374	
375	## 13. Result, Report, Delivery Split
376	
377	三者必须分开：
378	
379	| Layer | Owns | Does not own |
380	| --- | --- | --- |
381	| `result/` | 内部结果事实、用例结果、执行摘要 | 报告文件格式、对外交付动作 |
382	| `report/` | 报告对象和报告文件生成 | HTTP/FTP 上传、外部回执 |
383	| `northbound/` | 对外结果上报、报告交付、文件回传、错误语义转换 | 内部结果事实定义 |
384	
385	Reason:
386	
387	- 结果事实需要先在内部归口。
388	- 报告对象可以由内部结果和历史材料生成。
389	- 交付动作属于外部协议边界，成功或失败不能反向改写内部事实本身。
390	
391	## 14. Placement Examples
392	
393	| Need | Target |
394	| --- | --- |
395	| 解析接收字节并匹配帧 | `features/receive/core/` |
396	| 接收结果进入任务触发候选 | `features/receive/services/` 输出显式事件，`runtime/` 或 `task/` 消费 |
397	| 构造发送字节 | `features/send/core/` |
398	| 实际写串口 / socket | `platform/` facade -> preload -> main |
399	| 定时发送 | `features/task/`，调用 `features/send/` 的公开发送入口 |
400	| SCOE 命令识别和完成条件 | `features/scoe/core/` |
401	| SCOE 发帧 | `features/scoe/services/` 翻译成显式发送请求，再进入 `features/send/` |
402	| 历史记录和 CSV | `features/storage/` |
403	| 报告 JSON 生成 | `features/report/` |
404	| FTP/HTTP 回传和完成通知 | `features/northbound/` + `platform/` |
405	| 状态灯颜色映射 | `features/status/` |
406	| 表格/图表/星座图展示投影 | `features/display/` |
407	| 实时/历史展示偏好和 UI-safe snapshot | `features/display/` |
408	| 设置页表单 | `pages/` + `features/settings/` |
409	
410	## 15. Architecture Entry Conditions For Later Batches
411	
412	每个后续 Batch 进入 `cs-feat-design` 前，必须先补齐本节检查项；缺失项必须在 design 中标为 blocking、deferred 或只读调查范围，不能在实现阶段临场扩大边界。
413	
414	Required before design:
415	
416	- 明确本批涉及哪些 feature 归口，以及哪些旧系统可观测行为属于 `preserve`、`candidate drop`、`deferred` 或 `not touched`。
417	- 若本批存在外部消费者或跨 feature 协作，明确允许入口；若没有，说明不需要额外 public API。
418	- 明确本批是否需要 `runtime/` 编排；若需要，说明 runtime 只负责装配、调用顺序、事件路由和生命周期，不承载领域规则；若不需要，不为形式感新增 runtime 层。
419	- 明确是否新增或调整 platform / preload / main API；若涉及 main 高频处理，说明哪些只是平台侧缓冲、批处理、聚合、节流、队列或背压；若触达现有 main 业务化路径，必须把它登记为迁移风险或边界例外。
420	- 明确静态资产、运行事实、统计 read model、UI snapshot 的 owner、reader、写入权、reset 时机、生命周期和是否持久化。
421	- 明确跨 feature 通信方式，禁止以内部 state import、全局 store 回读或隐式事件总线替代公开接口。
422	- 明确 pages、widgets、feature components 的放置和职责，不让 UI 承载任务机、协议语义、统计累加、文件/串口/网络访问。
423	- 明确自动 fixture、手工 checklist、runtime / hardware validation 的边界和未验证项。
424	- 涉及 SCOE、高速存储、真实串口、TCP/UDP、打包态 data path、HTTP/FTP 或 northbound 时，必须读取对应边界材料并登记例外或 runtime validation。
425	
426	## 16. Infrastructure Baseline
427	
428	最小基础设施搬运原则：
429	
430	- 可复用：Vue 3、Quasar、Pinia、Vue Router、UnoCSS、Electron、serialport、TypeScript、ESLint/Prettier 等经确认仍需要的依赖类别；窗口安全配置；Quasar/Electron/Vite 的必要构建能力；现有主题 token 和样式经验中无业务耦合的部分。
431	- 禁止直接搬：旧 Quasar boot 业务初始化、旧 `src/api/common`、旧 `window.electron`、旧 preload all-in-one 聚合、旧 main IPC business handlers、旧 `public` data path 读写策略、旧 root package scripts 中对 `src*/**` 和 `src-electron` 的路径假设。
432	- 必须重新收缩：`package.json` scripts 和依赖；Quasar `sourceFiles`、Electron main/preload entry、boot 列表、public/extraResources 策略、builder files 规则；`tsconfig` include/path alias；ESLint scope 与 globals；UnoCSS preset、safelist 和 shortcuts；Vitest config 与 coverage/test include；auto-import 配置若引入也必须白名单化。
433	
434	`rewrite/` 的基础设施调整必须先服务最小可运行应用壳和测试基线，不能以“复用配置”为理由把旧业务初始化、旧数据目录、旧 API 包或旧 main handler 带入新工程。
435	
436	## 17. Test Baseline and Validation Layers
437	
438	默认测试基线：
439	
440	- 使用 Vitest 作为 `core`、`services`、`adapters`、`selectors` 的默认单测栈。
441	- 页面交互先以 manual checklist 验证，不用 Vitest 代替真实用户路径确认。
442	- Electron runtime、打包态 package、真实串口/TCP/UDP/SCOE 硬件和 customer validation 不能由 Vitest 代替。
443	- `pnpm build`、`pnpm lint` 是实现轮默认静态验证，但不能替代单测、manual、runtime、hardware 或 customer 层级证据。
444	
445	## 18. Auto-Import Decision
446	
447	当前基线默认保持显式 import；这能让 feature service、platform facade、runtime、store 和 public API 的依赖方向在 review 中可见。
448	
449	若后续为了 Vue/Quasar 工程体验引入 auto-import，只允许白名单导入 Vue、Vue Router、Pinia 等基础框架 API。禁止自动导入 feature service、platform facade、runtime、store、feature public API、adapter 或任何带业务 owner 的 helper。auto-import 不能成为隐藏业务依赖、跨 feature 调用或绕过 `rewrite/src/platform` facade 的机制。

16	# Task-SCOE-Send 执行引擎统一决策
17	
18	## 1. 背景与问题
19	
20	send design 和 task design 分别完成后，发现三个场景的核心模式高度相似：
21	
22	| 场景 | 触发来源 | 执行内容 |
23	| --- | --- | --- |
24	| 本地定时/触发发送 | 用户 UI、定时器、receive 事件 | 按计划发一系列帧 |
25	| SCOE 命令执行 | SCOE TCP 收到指令码 | 发命令帧 → 等完成条件 → 发确认帧 |
26	| Northbound 外部任务 | HTTP 收到外部命令 | 按用例序列发一系列帧 |
27	
28	三者都是"入口触发 → 按计划执行一系列发送操作 → 错误处理 → 进度追踪"，区别仅在入口适配。send design 和 task design 原本把 task 定位为"本地发送任务调度"，SCOE 只是"可选复用"——这个定位太窄了。
29	
30	## 2. 旧代码 evidence
31	
32	### 2.1 共性
33	
34	| 模式 | Task Executor | SCOE Executor | 共性程度 |
35	| --- | --- | --- | --- |
36	| 发送调用方式 | `useUnifiedSender.sendFrameInstance` | 同 | 高 |
37	| 结果检查 | `result.success` + target availability | `result.success` + 错误计数 | 中 |
38	| 定时器管理 | `useTimerManager` | `useTimerManager` 1秒轮询 | 高 |
39	
40	### 2.2 差异（旧代码结构层面）
41	
42	| 模式 | Task Executor | SCOE Executor |
43	| --- | --- | --- |
44	| 编排模式 | 三种调度（timed/trigger/sequence）+ error policy | 单命令执行 + 完成条件轮询 + 确认帧 |
45	| 错误策略 | pause/skip/stop 可配置 | 直接计数，无 pause/retry |
46	| 进度追踪 | currentCount/percentage/instanceIndex | commandSuccessCount/ErrorCount |
47	
48	差异来自旧代码的组织方式，不是来自业务语义的必然差异。统一后 task 的执行引擎可以覆盖所有场景。
49	
50	### 2.3 SCOE 不需要多命令序列
51	
52	用户确认：SCOE 命令是单命令执行模式（收一个指令码 → 执行一个命令）。不存在多命令按序列执行的需求。SCOE 的完整执行流程是：发命令帧 → 等完成条件 → 发确认帧。
53	
54	## 3. 决策
55	
56	### 3.1 task 是通用执行引擎
57	
58	task 的核心职责不是"本地定时/触发发送调度"，而是：
59	
60	**接收一个执行计划（step 序列），按顺序执行，处理错误，追踪进度。**
61	
62	触发来源只是入口适配的不同：
63	- `user-ui`：send 页面的定时/触发/序列对话框
64	- `timer`：定时器自动触发
65	- `receive-trigger`：receive 事件匹配触发
66	- `scoe-command`：SCOE 指令码解析后触发
67	- `northbound-command`：northbound 外部命令触发
68	
69	入口适配由调用方负责（SCOE 翻译命令、northbound 翻译外部请求、send 页面翻译用户配置），执行逻辑由 task 统一提供。
70	
71	### 3.2 TaskStepDefinition 多态化
72	
73	TaskCaseDefinition 重命名为 TaskStepDefinition，支持多态 step 类型：
74	
75	**send-step**：构帧 → 通过 send service 发送 → 得到 SendResult
76	
77	- `frameId`、`fieldValues`、`targetId`、`options`
78	
79	**wait-condition-step**：订阅 receive 事件，等待条件满足或超时
80	
81	- `condition`：frameId + fieldId + operator + threshold
82	- `timeoutMs`：超时时间
83	- `onTimeout`：超时策略（fail / skip / continue）
84	
85	**delay-step**：等待指定时长
86	
87	- `durationMs`
88	
89	### 3.3 各场景如何映射
90	
91	**本地定时发送**（schedulingMode = timed）：
92	
93	```
94	每轮: [send-step]
95	```
96	
97	**本地触发发送**（schedulingMode = trigger）：
98	
99	```
100	循环: [wait-condition-step(等触发条件)] → [send-step]
101	```
102	
103	**本地序列发送**（schedulingMode = sequence）：
104	
105	```
106	[send-step-1] → [delay-step] → [send-step-2] → [delay-step] → [send-step-3] → ...
107	```
108	
109	**SCOE 命令执行**（triggerSource = scoe-command）：
110	
111	```
112	[send-step(命令帧)] → [wait-condition-step(SCOE 完成条件)] → [send-step(确认帧)]
113	```
114	
115	**Northbound 外部任务**（triggerSource = northbound-command）：
116	
117	```
118	[send-step(case-1)] → [delay-step] → [send-step(case-2)] → ...
119	```
120	
121	### 3.4 SCOE 不需要自己的执行器
122	
123	`useScoeCommandExecutor` 的编排逻辑完全由 task 承接。SCOE 的职责是：
124	
125	- 命令解析（指令码 → step 定义）
126	- 完成条件定义
127	- 确认帧配置
128	- SCOE 领域状态管理（commandSuccessCount 等，通过订阅 task lifecycle event 更新）
129	
130	SCOE 不拥有 send 编排、错误策略、进度追踪——这些都由 task 提供。
131	
132	### 3.5 send 不变
133	
134	send 只做单帧发送（构帧 + target 路由 + transport write + 结果输出）。send 页面的定时/触发/序列对话框本质上是 task 的 UI 入口，创建 TaskDefinition 并通过 task service 执行。
135	
136	### 3.6 条件匹配归属
137	
138	wait-condition 和 trigger 共用同一套条件匹配逻辑（frameId + fieldId + operator + threshold）。归属：
139	
140	- 条件类型定义和匹配算法归 `task/core`（纯 TypeScript，可单测）
141	- 条件内容由调用方定义（SCOE 定义完成条件、trigger 配置定义触发条件）
142	- task service 通过 receive public API 的 `ReceiveInputEvent` 订阅事件源，在 task/core 中匹配条件
143	- runtime 只负责服务装配时把 receive event source 注入 task service
144	
145	### 3.7 error policy 适用于所有 step 类型
146	
147	- send-step 失败：retry / skip / stop / pause
148	- wait-condition 超时：retry / skip / stop / pause
149	- delay-step 不可失败
150	
151	### 3.8 QueueModel 不受影响
152	
153	send 的 transport-level FIFO 不变。task 的编排级等待通过 `await SendResult` 实现。
154

134	### 4.3 Core types
135	
136	本轮不冻结最终类型名和字段 schema，只定义类型职责和分类。
137	
138	**TaskStepKind** — step 类型：
139	
140	- `send`：通过 send service 发送一帧。参数：frameId、fieldValues、targetId、options。
141	- `wait-condition`：订阅 receive 事件，等待条件满足或超时。参数：condition（WaitCondition）、timeoutMs、onTimeout。
142	- `delay`：等待指定时长。参数：durationMs。
143	
144	**TaskStepDefinition** — 多态 step（替代原 TaskCaseDefinition）：
145	
146	- `id`、`name`。
147	- `kind`：TaskStepKind。
148	- `sendConfig`（kind = send 时）：frameId、fieldValues（字段值映射或表达式引用）、targetId（可选覆盖）、options（构帧选项）。
149	- `waitConfig`（kind = wait-condition 时）：condition（WaitCondition）、timeoutMs、onTimeout（fail / skip / continue）。
150	- `delayConfig`（kind = delay 时）：durationMs。
151	
152	**WaitCondition** — 条件匹配（wait-condition-step 和 trigger 模式共用）：
153	
154	- `frameId`：监听的接收帧。
155	- `fieldId`：监听的字段。
156	- `operator`：比较运算（eq / neq / gt / lt / gte / lte / change / any）。
157	- `threshold`：比较阈值。
158	- `sourceId`：可选 source 过滤。
159	
160	**TaskTriggerSource** — 触发来源（入口适配标识，信息性，不改变执行逻辑）：
161	
162	- `user-ui`：send 页面的定时/触发/序列对话框。
163	- `timer`：定时器自动触发。
164	- `receive-trigger`：receive 事件匹配触发。
165	- `scoe-command`：SCOE 指令码解析后触发。
166	- `northbound-command`：northbound 外部命令触发。
167	
168	**TaskSchedulingMode** — 调度模式：
169	
170	- `timed`：定时重复执行 step 序列。参数：interval、maxCount（infinite if absent）、delayBeforeStart。
171	- `trigger`：条件触发执行 step 序列。参数：triggerCondition（WaitCondition）、cooldown、maxTriggerCount。
172	- `sequence`：单次执行 step 序列。step 序列天然有序。无循环，执行完即 completed。
173	
174	schedulingMode 与 step 类型的组合约束（validation 层强制）：
175	
176	| | send-step | wait-condition | delay |
177	|---|---|---|---|
178	| timed | 合理 | 需 warn（每轮可能阻塞等超时） | 合理 |
179	| trigger | 合理 | 合理 | 合理 |
180	| sequence | 合理 | 合理 | 合理 |
181	
182	timed + wait-condition 不禁止但 validate 时产生 warning：每 iteration 会等条件，如果条件不频繁满足会导致大量超时。
183	
184	**TaskDefinition** — 任务静态配置：
185	
186	- `id`、`name`（用户可见）。
187	- `schedulingMode`。
188	- `triggerSource`：TaskTriggerSource（信息性，不改变执行逻辑）。从 definitionRef 可推导，此处冗余存储仅供快速查询。
189	- `steps`：TaskStepDefinition[]（至少一个）。
190	- `targetId`：默认 target（可被 step 覆盖）。send-step 执行时若 step.targetId 为 null 则 fallback 到此值。用于 northbound adapter（D2）和用户配置中未逐 step 指定 target 的场景。参见 `2026-05-06-outbound-routing-and-response-decisions.md` D2。
191	- `errorPolicy`：on-failure 行为（retry / skip-step / stop / pause）。含 retryCount、retryDelay。适用于所有 step 类型。
192	- `stopCondition`：可选完成条件（maxDuration、maxIterations、expression-based）。
193	
194	**TaskLifecycleStatus**：
195	
196	- `created` | `running` | `paused` | `stopped` | `completed` | `failed`
197	
198	注意：旧系统 `stop -> completed` 不保留。新系统中 stopped 和 completed 是不同终态：completed 表示正常结束（所有步骤执行完毕），stopped 表示被用户或外部主动停止。
199	
200	**TaskInstanceState** — 运行时实例状态：
201	
202	- `instanceId`（运行时生成）。
203	- `definitionRef`：引用 TaskDefinition。
204	- `lifecycle`：TaskLifecycleStatus。
205	- `startedAt`、`pausedAt`、`stoppedAt`、`completedAt`、`failedAt`。
206	- `currentStepIndex`、`currentIteration`。
207	- `stepResults`：per-iteration per-step 的执行结果列表（TaskStepResult[]）。按 iteration 分组，保留最近 maxStepResultHistory 轮（默认 100），超出丢弃最早。用于进度计算和 UI 展示。
208	- `error`：最后错误信息（如有）。
209	
210	**TaskProgress** — 进度：
211	
212	- `stepsTotal`、`stepsCompleted`、`stepsFailed`、`stepsSkipped`。
213	- `iterationsCompleted`、`iterationsTotal`（timed 模式；infinite 时 iterationsTotal 为 null）。
214	- `elapsedMs`、`estimatedRemainingMs`（可估算时）。
215	- `lastStepResult`：最近一次 step 执行结果快照。
216	
217	**TaskStepResult** — 多态 step 执行结果（stepResults 的元素类型）：
218	
219	- `stepIndex`、`iteration`（所属 iteration，0-indexed）。
220	- `kind`：与 TaskStepKind 对应。
221	- send-step：`sendResult`（SendResult）。
222	- wait-condition-step：`matched`（boolean）、`matchedValue`（匹配时的值，可选）、`timedOut`（boolean）。
223	- delay-step：`completed`（boolean，始终 true）。
224	- `appliedPolicy`：如果触发了 errorPolicy，记录实际执行的策略动作。
225	
226	**TaskInstanceCompletion** — 任务执行结果摘要（内部事实，不等同 report）：
227	
228	- `kind`：completed / stopped / failed。
229	- `summary`：steps total/succeeded/failed/skipped。
230	- `durationMs`。
231	- `startedAt`、`finishedAt`。
232	- 不包含 report schema、northbound 字段或外部错误码。
233	
234	### 4.4 Service contract
235	
236	task 的主服务合约是 task lifecycle：
237	
238	```
239	TaskService:
240	  createTask(definition) → TaskInstanceState
241	  startTask(instanceId) → void
242	  pauseTask(instanceId) → void
243	  resumeTask(instanceId) → void
244	  stopTask(instanceId) → void
245	  removeTask(instanceId) → void  // 从列表移除已停止/已完成任务
246	```
247	
248	执行循环（伪代码）：
249	
250	```
251	startTask(definition):
252	  set lifecycle = running
253	  loop on schedulingMode:
254	    timed:  for each iteration (up to maxCount):
255	              executeSteps(definition.steps, iteration)
256	              wait interval
257	    trigger: subscribe to receive events via triggerCondition (WaitCondition)
258	              on match + cooldown check:
259	                executeSteps(definition.steps, iteration)
260	    sequence:
261	              executeSteps(definition.steps, iteration=0)
262	              // 无循环，执行完即 completed
263	  on loop exit:
264	    set lifecycle = completed
265	    emit TaskInstanceCompletion
266	
267	executeSteps(steps, iteration):
268	  for each step in steps:
269	    if lifecycle is stopped/paused: break
270	    switch step.kind:
271	      send:
272	        build SendRequest from step.sendConfig
273	        result = await sendService.execute(request)
274	        record TaskStepResult(stepIndex, iteration, kind=send, sendResult)
275	        if result is error: apply errorPolicy
276	      wait-condition:
277	        subscribe to receive events (single shared stream, filtered by frameId index)
278	        match against step.waitConfig.condition
279	        on match within timeout:
280	          unsubscribe  // 条件满足后立即取消订阅，生命周期 = 直到匹配或超时
281	          record TaskStepResult(stepIndex, iteration, kind=wait-condition, matched=true)
282	        on timeout:
283	          unsubscribe
284	          onTimeout 决定本 step 结果：
285	            continue → 记录 matched=false, timedOut=true，继续下一步
286	            fail → 记录 matched=false, timedOut=true，交给 errorPolicy 处理
287	            skip → 记录 skipped，跳到下一步
288	      delay:
289	        await setTimeout(step.delayConfig.durationMs)
290	        record TaskStepResult(stepIndex, iteration, kind=delay, completed=true)
291	```
292	
293	**onTimeout 与 errorPolicy 的两层交互**：
294	
295	wait-condition-step 的 `onTimeout` 是 step 本地策略，决定超时后这一步算什么。errorPolicy 是 task 级别全局策略，决定某步失败后整个 task 怎么办。流程：
296	
297	1. wait-condition 超时 → `onTimeout` 先生效
298	2. `onTimeout = continue`：本 step 视为通过，继续下一步。errorPolicy 不介入。
299	3. `onTimeout = skip`：本 step 视为 skipped，继续下一步。errorPolicy 不介入。
300	4. `onTimeout = fail`：本 step 视为失败 → 交给 errorPolicy 决定 task 级行为（retry/skip/stop/pause）。
301	
302	**trigger 外层与 wait-condition-step 内层的关系**：
303	
304	两层条件等待机制语义不同，互不干扰：
305	
306	- **外层 trigger**：决定"什么时候启动 step 序列"。trigger 命中后进入 executeSteps。
307	- **内层 wait-condition-step**：step 序列内部的阻塞等待。
308	
309	step 序列的 wait-condition 超时或失败只影响当前 iteration 的 executeSteps，不重置 trigger 的 cooldown 或 maxTriggerCount。trigger 只管"触发下一轮"，不管上一轮内部出了什么。
310	
311	**条件匹配订阅模型**：
312	
313	- task service 持有一个共享的 receive event subscription，按 frameId 建索引 map。
314	- wait-condition-step 执行时向索引注册条件，不新建 subscription。
315	- 条件满足或超时后从索引移除，subscription 不变。
316	- pause 时移除所有活跃条件并保留 subscription（或暂停 push），resume 时重建。
317	- stop 时移除所有条件并取消 subscription。
318	
319	**多态 step 执行的关键特性**：
320	
321	- 每个 step 按顺序执行，前一个完成（或被 skip）后才进入下一个。
322	- send-step 的错误和 wait-condition-step 的超时使用同一套 errorPolicy。
323	- delay-step 不可失败。
324	- 条件匹配逻辑（WaitCondition evaluation）是 task/core 的纯 TypeScript，用于 wait-condition-step 和 trigger 模式。
325	- task service 通过 receive public API 订阅 `ReceiveInputEvent` 用于条件匹配。
326	
327	**Pause/Resume**：
328	
329	- pause：暂停当前循环，停止定时器和 trigger/wait-condition 订阅。保留 progress。
330	- resume：从暂停点继续。不重置 progress。
331	- 触发 pause 的来源：用户操作、errorPolicy=pause、northbound 暂停命令（经 runtime）。
332	
333	**Stop**：
334	
335	- stop：终止执行循环。lifecycle 设为 stopped（不是 completed）。保留 progress 供查看。
336	- 移除：从活跃列表移除已停止/已完成任务。history/material 由 storage 处理。
337	
338	**Error policy**（适用于所有 step 类型）：
339	
340	- `retry`：重试当前 step（最多 retryCount 次，间隔 retryDelay）。超过后按 fallback 处理。
341	- `skip-step`：跳过当前 step，继续下一个。记录为 skipped。
342	- `stop`：立即 stop 任务。
343	- `pause`：暂停任务，等待用户手动 resume 或外部恢复。
344	
345	**入口适配**：
346	
347	task service 不区分触发来源。入口适配由调用方负责：
348	
349	- SCOE：`scoe-command` → 解析指令码 → 构造 TaskDefinition（steps = [send-step, wait-condition-step, send-step]）→ task service.createTask + startTask
350	- Northbound：`northbound-command` → 翻译外部请求 → 构造 TaskDefinition → task service.createTask + startTask
351	- Send 页面：`user-ui` → 用户配置 → 构造 TaskDefinition → task service.createTask + startTask
352

454	### 4.7 Timer, scheduling, and condition matching
455	
456	定时和条件匹配是 task 的核心基础设施。
457	
458	**Timer**：
459	
460	- Timer 在 renderer TypeScript 层实现（`setInterval`/`setTimeout` 或等效机制）。
461	- 不需要 platform/main 提供定时器。renderer 侧 timer 足够满足定时发送需求。
462	- Timer lifecycle 随 task lifecycle：pause 时清除 timer，resume 时重建。
463	- Timer 不进入 `shared/`。Timer 的创建/清除逻辑归 task service。
464	
465	**条件匹配**：
466	
467	- wait-condition-step 和 trigger 模式共用同一套 WaitCondition 匹配逻辑。
468	- 匹配算法在 `task/core` 中实现，纯 TypeScript，可单测。
469	- task service 通过 receive public API 的 `ReceiveInputEvent` 订阅事件源。
470	- pause 时取消订阅，resume 时重建订阅。
471	- 条件内容由调用方定义（SCOE 定义完成条件、trigger 配置定义触发条件），task 只执行匹配。
472	
473	**性能设计原则**：
474	
475	- **条件匹配 O(1) 查找**：收到 receive event 时按 frameId 查索引 map，只检查注册在该 frameId 下的活跃条件。不是遍历所有活跃条件。
476	- **共享事件流**：task service 持有一个 receive event subscription，所有 wait-condition-step 和 trigger 共用。不按 step 各自订阅。
477	- **stepResults 有上限**：默认保留最近 100 轮 iteration 结果，超出丢弃最早。防止 timed 模式长时间运行导致内存增长。
478	- **trigger 事件驱动**：trigger 模式不轮询，receive event push 过来才匹配。
479	- **条件注册/注销 O(1)**：wait-condition-step 开始时向索引 map 注册，条件满足/超时/stop 时注销。注册和注销都是 map 操作。
480	
481	### 4.8 Runtime involvement
482	
483	task 需要 runtime 参与：
484	
485	- **服务装配**：runtime 创建 task service，注入 send service、frame reader、receive event source。
486	- **跨 feature 路由**：receive trigger event → task；SCOE task request → task service；northbound command → task service。
487	- **事件分发**：TaskInstanceCompletion event → result/status/northbound。
488	- **生命周期**：app startup/shutdown 时清理活跃任务。
489	
490	runtime 不得：
491	- 实现 trigger 匹配逻辑。
492	- 决定 task error policy。
493	- 解释 SendResult 的业务含义。
494	- 变成所有 task 消费者的总路由器。

497

499

657	## 5. Open questions
658	
659	### 5.1 SCOE 与 task 的边界（已锁定）
660	
661	SCOE 和 task 是同一类东西：都是"收到指令 → 执行一系列操作（发送帧）"。区别仅在于入口适配。
662	
663	已锁定决策：
664	
665	1. **SCOE 不需要自己的执行器。** `useScoeCommandExecutor` 的编排逻辑完全由 task 承接。SCOE 翻译领域命令为 TaskDefinition（triggerSource = scoe-command），通过 task public service 创建执行。
666	
667	2. **SCOE 命令执行是三个 step：**
668	   - send-step（执行命令帧）
669	   - wait-condition-step（等待 SCOE 完成条件：收到特定响应帧+字段匹配）
670	   - send-step（发送确认帧）
671	
672	3. **完成条件等待和确认帧发送是 task step 类型，不是 SCOE 特有逻辑。** wait-condition-step 是通用的 step 类型，SCOE 只是定义了条件内容。
673	
674	4. **SCOE 领域逻辑留在 SCOE feature：** 命令解析（指令码 → step 定义）、完成条件定义、确认帧配置、SCOE 状态管理。SCOE 订阅 task lifecycle event 更新自己的领域状态（commandSuccessCount 等）。
675	
676	5. **SCOE 任务是否出现在用户可见的任务列表中：** deferred。需要用户确认。
677	
678	### 5.2 多态 step 的扩展性
679	
680	未来可能新增的 step 类型：
681	
682	- `receive-step`：显式等待并接收一帧（当前通过 wait-condition-step 覆盖）。
683	- `parallel-step`：并行执行多个 sub-steps（当前不支持）。
684	- `branch-step`：根据条件选择执行路径（当前不支持）。
685	
686	首轮只实现 send / wait-condition / delay。新增 step 类型时只需扩展 TaskStepKind 和 executeSteps 的 switch，不改变引擎核心。
687	
688	### 5.3 result/report 与 task 的边界
689	
690	1. TaskInstanceCompletion 是否直接进入 result feature？
691	   - 建议：task 输出 TaskInstanceCompletion 作为内部事实。result feature 消费它并构建 case/task result truth。report feature 从 result 和 storage 读取素材生成报告。
692	   - task 不生成 report，不定义 result schema，不对外交付。
693	
694	2. northbound 如何获得 task 状态？
695	   - northbound 通过 selector 读取 task projection，不直接访问 task internal state。外部 task/control 语义由 northbound 翻译。
696	
697	### 5.4 本地 task 与 northbound task 的映射
698	
699	1. 本地任务和甲方任务共享同一个 TaskDefinition 模型吗？
700	   - 建议：共享 core lifecycle 和 scheduling 模型。northbound 通过 runtime 翻译外部请求为 TaskDefinition，task service 不区分来源。
701	   - 但 northbound task 可能有额外的控制语义（pause/continue/abort），这些需要在 task lifecycle 中预留，但语义解释归 northbound。
702	
703	2. `startTestCaseList` 的粒度？
704	   - 按 charter 暂按 task start 处理。如果后续确认是部分 case list start，task service 需要支持 subset start。本轮列为 deferred。
705	
706	### 5.5 Trigger condition 表达能力
707	
708	1. Trigger condition 是否支持跨帧条件（如"帧 A 的字段 X > 10 且帧 B 的字段 Y == 'ok'"）？
709	   - 建议：首轮只支持单帧单字段条件。多条件组合和表达式 trigger 由后续版本按需扩展。
710	
711	2. Trigger condition 的 source 过滤是否需要支持多 source？
712	   - 建议：首轮只支持单 source 或 all-sources。

726	## 7. Answers to send design open questions
727	
728	基于 task design（通用执行引擎定位），回答 send design §5 的 open questions：
729	
730	### 7.1 Write queue 归属
731	
732	**回答：send owns transport-level write queue。**
733	
734	- send 拥有轻量 transport-level write queue，保证同一 target 的 write 顺序。
735	- task 拥有 step-level 序列编排（step 执行顺序、间隔、条件）。
736	- 两者不冲突：task await SendResult 后再发下一个 send-step，send queue 只处理 transport-level 的并发 write。
737	- task 不感知 send queue 的存在。
738	
739	### 7.2 SendResult 同步/异步
740	
741	**回答：Promise\<SendResult\> 为主，可选 event emission。**
742	
743	- send public service 返回 `Promise<SendResult>` 作为主要调用方式。
744	- task 的 send-step 使用 `await sendService.execute(request)` 获取结果。
745	- send 可选 emit SendResult event 供其他消费者（status/storage/result）订阅。
746	- 这保证了 task 可以按 step 顺序推进，同时不阻塞 event-driven 的消费者。
747	
748	### 7.3 Send failure 是否影响 task lifecycle
749	
750	**回答：task 决定，send 不参与。**
751	
752	- send 只输出 SendResult（含 error kind 和详情）。
753	- task 根据 `errorPolicy` 决定如何处理 send-step 失败：retry、skip、stop 或 pause。
754	- wait-condition-step 超时同样适用 errorPolicy。
755	- send 不了解 task lifecycle，不写 task state。
756	
757	### 7.4 Send instance 配置持久化归谁
758	
759	**回答：send own config / settings / storage 联合确认，不归 frame。**
760	
761	- per-frame 的"发送配置模板"（如默认字段值、target 偏好）如果需要持久化，可能归 send own config 或 settings。
762	- 不归 frame：frame 只 owns 静态帧定义，不拥有发送配置。
763	- 具体归口在实现阶段由 send/settings/storage design 联合确认。
764	- TaskDefinition 本身归 task own config，持久化经 storage。
765	
766	### 7.5 Send 是否了解 task 的存在
767	
768	**回答：不。**
769	
770	- send 只接收 SendRequest（含 context 字段供追踪），不区分调用方。
771	- context 中的 source/taskId/stepIndex 是纯信息性的，send 不基于它们改变行为。
772	
773	### 7.6 wait-condition-step 如何获取 receive 事件
774	
775	**回答：task service 通过 receive public API 订阅 ReceiveInputEvent。**
776	
777	- task service 在创建时通过依赖注入接收 receive event source。
778	- wait-condition-step 执行时订阅事件，在 task/core 中匹配 WaitCondition。
779	- pause 时取消订阅，resume 时重建。
780	- runtime 只负责服务装配时把 receive event source 注入 task service，不参与事件分发。
781	
782	### 7.7 SCOE 完成条件和确认帧如何表达
783	
784	**回答：作为 task 的 step 序列。**
785	
786	- SCOE 命令 = TaskDefinition（triggerSource = scoe-command），steps = [send-step, wait-condition-step, send-step]。
787	- 完成条件 = wait-condition-step 的 WaitCondition（由 SCOE 定义具体内容）。
788	- 确认帧 = 最后一个 send-step（由 SCOE 定义 frameId 和 fieldValues）。
789	- task 不理解"SCOE 完成条件"的语义，只执行 wait-condition-step 的通用匹配逻辑。
790
