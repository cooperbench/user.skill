## Findings

### High

**H1: settleResolvers 泄漏 — stop 后 onSettled 永远挂起**

`task-service.ts:699-706`。`onSettled()` 创建 Promise 存入 settleResolvers，只有 `completeTask` 和 `failTask` 会 resolve 它。但 `stopTask` 不调用 resolveSettle。如果外部 await `service.onSettled(id)` 后任务被 stop，该 Promise 永远不 resolve。

修复建议：`stopTask` 中也调用 `resolveSettle`，或 `runExecutionLoop` finally 中清理。

**H2: Pause→Resume 端到端流程未测试**

`ta[REDACTED_SK].spec.ts` 的 "resume continues execution" 测试（L491-523）实际上是创建第二个 task 并验证 service 仍然工作，**没有测试 pause→resume 流程**。唯一测试 pause 的用例（L456-489）在 pause 后直接 stop，未验证 resume 后执行是否正确继续。

### Medium

**M1: sourceId 过滤边界 gap**

`condition-matcher.ts:10`。当 condition 指定了 sourceId 但 input 没有 sourceId 时，条件 `condition.sourceId !== undefined && input.sourceId !== undefined` 第二项为 false，整个过滤被跳过，导致匹配通过。语义上，如果 condition 要求特定 source，input 无 sourceId 时不应匹配。

**M2: delay-step 中断时 setTimeout 泄漏**

`task-service.ts:107-109`。`sleep()` 创建 setTimeout 但在 Promise.race 被中断时不会 clearTimeout。对于短 delay 无影响，但如果 delayStep 设置 60s，中断后 timer 仍挂在事件循环上直到超时。

**M3: stopCondition 定义但未实现**

`types.ts:105-108` 定义了 `TaskStopCondition`（maxDurationMs, maxIterations），`TaskDefinition` 包含可选 stopCondition 字段，但 `runTimedLoop`/`runTriggerLoop` 完全不检查它。对 timed 模式 maxCount 替代了 maxIterations，但 maxDurationMs 从未生效。

**M4: errorPolicy=pause 后 resume 跳过失败 step**

当 step 失败触发 pause 时，失败 step 的 result（含 appliedPolicy='pause'）已写入 state。Resume 后 executeSteps 从 startIndex = completedInIter.length 开始，跳过了该 step。如果意图是"暂停让用户修复后重试"，当前行为不符合。Design 未明确此处语义。

**M5: TaskProgress 缺少 design 声明的字段**

Design §4.3 声明 TaskProgress 含 `estimatedRemainingMs` 和 `lastStepResult`，实现中两者都缺失。不影响核心功能但对 UI 消费者不完整。

**M6: retry 耗尽后 lifecycle 设为 'failed'**

`task-service.ts:380`。retry 耗尽后 `updateLifecycle(instanceId, 'fail')`。Design 只说 retry 超过 retryCount 后按 fallback 处理，未明确应该 fail 还是 stop。failed 意味着不可恢复，但 retry 是用户配置的策略，用户可能期望 stop 后可以手动 resume。Design gap。

### Low

**L1: FakeReceiveEventSourceOptions 声明但未使用**

`fake-receive-event-source.ts:4-7` 定义了含 autoEmit 的 options interface，但 `createFakeReceiveEventSource()` 不接受参数。Dead interface。

**L2: makeSendResult 类型 cast 不准确**

`task-fixtures.ts:234`：`kind: (overrides.kind ?? 'sent') as 'sent'`。当 overrides.kind 存在时（如 'transport-error'），类型仍是 `'sent'`。运行时值正确但类型声明不诚实。

**L3: nextInstanceId 是模块级变量**

`task-service.ts:128`。多次调用 `createTaskService` 共享同一个计数器。不影响功能但阻止独立 service 实例有隔离的 ID 空间。

**L4: any operator + null value 导致 matchedValue 类型不安全**

`condition-matcher.ts:22-23`。`any` operator 对 null 值返回 true，但 `ConditionRegistry.processInput` 将 `input.value`（可能为 null）cast 为 `number | string` 传给 onMatch。WaitConditionStepResult.matchedValue 类型声明为 `number | string` 但实际可能为 null。

**L5: delayBeforeStartMs 未测试**

Types 和 runTimedLoop 中实现了 delayBeforeStartMs，但测试文件未覆盖。

**L6: 无 infinite timed task 测试**

Design 提到 timed 模式支持无限迭代（maxCount 为空），测试中所有 timed 用例都设了 maxCount。
