## 修订方案

### 事件驱动模型

关键变更：runtime 不做轮询，而是创建桥接 adapter 把 connection 事件对接到 receive 已有的 `ReceiveInputSource` 接口。

```
ConnectionAdapter.drainEvents()
       ↓
ConnectionToReceiveInputSource (implements ReceiveInputSource)
  .drainEvents() → 把 ConnectionAdapterEvent.data 转为 ReceiveInputEvent[]
       ↓
receiveService.drainInputSource(source)
       ↓
ReceiveServiceOutcome.outcomes
  过滤 kind==='matched'，提取字段 → ConditionMatchInput[]
       ↓
ReceiveEventSourceBridge.emit(inputs)
  → task 已注册的 subscribe handler 收到回调
```

这完全复用了 receive 的批处理逻辑，runtime 不手动调 `ingestBatch()`，不手动提取 matched fields。

### feature-wiring.ts 修订 — 按层级创建

```ts
// Level 0: 无外部依赖
interface WiringLevel0 {
  readonly frameReader: FrameAssetReader;
  readonly settingsService: SettingsService;
  readonly storageReader: StorageLocalReader;  // 保留现有
}

// Level 1: 依赖 adapter
interface WiringLevel1 extends WiringLevel0 {
  readonly connectionService: ConnectionService;
}

// Level 2: 依赖 frame
interface WiringLevel2 extends WiringLevel1 {
  readonly receiveService: ReceiveService;
}

// Level 3: 依赖 frame + connection
interface WiringLevel3 extends WiringLevel2 {
  readonly sendService: SendService;
}

// Level 4: 依赖 send + receive bridge
interface WiringLevel4 extends WiringLevel3 {
  readonly taskService: TaskService;
  readonly receiveEventSourceBridge: ReceiveEventSourceBridge;
}

function wireLevel0(options?): WiringLevel0;
function wireLevel1(adapter: ConnectionTransportAdapter, prev: WiringLevel0): WiringLevel1;
function wireLevel2(prev: WiringLevel1): WiringLevel2;
function wireLevel3(prev: WiringLevel2): WiringLevel3;
function wireLevel4(prev: WiringLevel3): WiringLevel4;
```

每个 level 是独立函数，失败只影响本层。测试可以只测某一层的 wiring。

**1. ConnectionToReceiveInputSource** (implements `ReceiveInputSource`)

```ts
  constructor(private connectionAdapter: ConnectionTransportAdapter) {}
  
  async drainEvents(): Promise<ReceiveInputEvent[]> {
    const outcome = await this.connectionAdapter.drainEvents();
    // ConnectionAdapterEvent.data → ReceiveInputEvent.batch
  }
}
```

**2. ConnectionBackedSendWriter** (implements `SendTransportWriter`)

```ts
// SendTransportWriter.writeBytes(cid, bytes) → ConnectionService.write({connectionId, bytes})
// 注意 TransportWriteRequest 结构: {connectionId, bytes, targetId?}
// 返回值转换: ConnectionOperationOutcome → SendTransportWriteOutcome
```

**3. ConnectionBackedTargetResolver** (implements `SendTargetResolver`)
```ts
// SendTargetResolver.resolveTarget(id) → ConnectionService.listTransportTargets()
// TransportTargetSnapshot 类型两边一致，直接委托
```

### event-router.ts 修订 — event-driven

```ts
interface EventRouter {
  start(): void;     // 开始路由
  stop(): void;      // 停止路由
  isRunning(): boolean;
}

function createEventRouter(wiring: WiringLevel4, options?: {
  pollIntervalMs?: number;  // 仅用于驱动 drainAdapterEvents 的调度
}): EventRouter;
```

路由节拍（由调度器驱动，不是同步 tick）：
1. 调用 `connectionToReceiveInputSource`（内部 drain connection adapter）
2. 调用 `receiveService.drainInputSource(connToReceiveAdapter)`
3. 从 `outcomes` 中提取 matched → `ConditionMatchInput[]`
4. `receiveEventSourceBridge.emit(inputs)`

与 tick() 的本质区别：
- 不手动调 `ingestBatch()`，用 `drainInputSource` 复用 receive 批处理
- 不手动提取 matched fields，从 `outcomes` 中取结构化结果
- 不串 task+send，task 通过 `ReceiveEventSource.subscribe` 异步回调
- 调度只负责驱动 drain，不做业务逻辑

### settings 分发

在 wiring 层处理，不在 event-router 里：
- `wireLevel0` 创建 `settingsService`
- `wireLevel2` 创建 receive 时，settings 已在 level0 中可访问
- 后续需要运行时分发时，在 event-router 中加 settings change → 各 feature 的 routeSettingsChange()

当前阶段 settings 主要通过各 feature 构造时注入或 selector 读取，暂不需要运行时推送。

  问题 1（会出 bug）：ConnectionToReceiveInputSource 绕过了 ConnectionService

  方案设计的流程：

  ConnectionAdapter.drainEvents()       ← 桥接 adapter 直接调底层 adapter
         ↓
  ConnectionToReceiveInputSource

  但 ConnectionService 已经持有 ConnectionTransportAdapter。如果桥接 adapter 也调 adapter.drainEvents()，会出现：

  1. ConnectionService 和桥接 adapter 竞争同一个 adapter 的事件队列
  2. ConnectionService 的 state 不会更新——它的 counters、event history、lastError 全部丢失
  3. 串口/TCP 断线、连接状态变化等非 data 事件也被桥接 adapter 吃掉，ConnectionService 看不到

  正确流程必须先经过 ConnectionService：

  event-router 调用 connectionService.drainAdapterEvents()
    → ConnectionService 内部 drain adapter，更新自身 state，返回 ConnectionOperationOutcome
    → outcome.events 里有 data 事件
         ↓
  event-router 把 data 事件推入 ConnectionToReceiveInputSource
    → 桥接 adapter 缓存这些事件
         ↓
  receiveService.drainInputSource(bridge)
    → receive 内部调 bridge.drainEvents()，拿到 ReceiveInputEvent[]

  ConnectionToReceiveInputSource 不是包装 ConnectionTransportAdapter，而是接收 ConnectionService 已经处理过的事件，做格式转换。它应该是无状态的事件转换器，不是 adapter 的代理。

  ---
  问题 2（过度设计）：5 层 wiring 拆得太细

  6 个 service 5 个 level，其中 4 个 level 各自只创建 1 个 service。维护 5 个函数 + 5 个接口的成本高于收益。

  Level 0 (无 feature 依赖): frame, settings, storage
  Level 1 (需 adapter):      connection
  Level 2 (需 level 0+1):    receive, send
  Level 3 (需 level 2):      task + bridge

  3 层足够，每层内的 service 互相独立可以并行创建。Level 2 的 receive 和 send 可以同时创建（receive 依赖 frame，send 依赖 frame+connection，都在前置层已有）。

  function routingTick(features: RewriteWiredFeatures): RoutingTickResult {
    const outcome = features.connectionService.drainAdapterEvents();
    if (!outcome.ok) return { ok: false, error: outcome.error };
