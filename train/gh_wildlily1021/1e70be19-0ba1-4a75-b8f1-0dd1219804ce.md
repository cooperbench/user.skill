### 6.2 实现验证

**来源：task-real-design.md:479-512**

**evaluateConditionGroup 纯函数设计**：

```typescript
function evaluateConditionGroup(
  conditions: readonly ConditionTerm[],
  fieldValues: Readonly<Record<string, number | string | null>>,
): boolean {
  if (conditions.length === 0) return true;
  
  let result = evaluateSingleCondition(conditions[0], fieldValues);
  
  for (let i = 1; i < conditions.length; i++) {
    const op = conditions[i].logicOperator ?? 'and';
    const current = evaluateSingleCondition(conditions[i], fieldValues);
    
    if (op === 'or') {
      result = result || current;
      if (result) break;   // OR 短路
    } else {
      result = result && current;
      if (!result) break;  // AND 短路
    }
  }
  
  return result;
}
```

**纯函数验证点**：
- ✅ 无副作用：不修改输入参数
- ✅ 引用透明：相同输入永远返回相同输出
- ✅ 无外部依赖：只依赖 `compareValues`（shared 纯函数）
- ✅ 不可变输入：`readonly` 类型约束

**非纯函数边界**：
- ❌ Cooldown/maxCount：由 ConditionRegistry 管理（非纯）
- ❌ sourceId 过滤：在 `ConditionRegistry.processInput` 中处理

**验证方法**（checklist.yaml:57-60）：
- vitest-unit 单元测试
- fixture-test 用例覆盖

## 2. ScheduleDriver 4 种模式的验收条件

**来源**: `rewrite-task-design.md` §4.3 (第 168-182 行); `task-real-brainstorm.md` §决策 1 (第 56-76 行)

### 2.1 旧系统三种模式（验收基准）

| 模式 | 旧配置 | 旧行为 | 验收条件 |
|------|--------|--------|----------|
| **顺序发送** | `FrameInstanceInTask[]` | 单次，按序发完 | 执行完所有 steps 后 lifecycle = completed |

| **顺序发送** | `schedule: immediate` | 无 stopCondition，无 repeat；执行完所有 steps 后 lifecycle = completed |

## 3. Step 多态化验收

### 3.1 三种 Step 类型定义

**来源**: `rewrite-task-design.md` §4.3 (第 137-150 行); `index.ts` (第 8-36 行)

| Step 类型 | 配置字段 | 验收条件 |
|-----------|----------|----------|
| **send-step** | `sendConfig: { frameId, fieldValues, targetId?, options }` | 通过 send service 发帧；记录 TaskStepResult(kind=send, sendResult)；失败时应用 errorPolicy |
| **wait-condition-step** | `waitConfig: { condition, timeoutMs?, onTimeout }` | 订阅 receive 事件；条件满足或超时后取消订阅；记录 TaskStepResult(kind=wait-condition, matched, timedOut)；超时时 onTimeout 先生效（continue/skip/fail），fail 时才交 errorPolicy |

### 3.2 Step 执行顺序验收

**来源**: `rewrite-task-design.md` §4.4 (第 267-291 行)

| 验收项 | 验收条件 |
|--------|----------|
| **顺序执行** | 前一个 step 完成（或被 skip）后才进入下一个 |
| **错误策略统一** | send-step 的错误和 wait-condition-step 的超时使用同一套 errorPolicy |
| **订阅生命周期** | wait-condition-step 条件满足或超时后立即取消订阅；pause 时移除所有活跃条件；resume 时重建 |

### 3.3 onTimeout 与 errorPolicy 的两层交互验收

**来源**: `rewrite-task-design.md` §4.4 (第 293-300 行)

| onTimeout 值 | 验收条件 |

## 7. Task-Real Brainstorm 中锁定的关键设计决策

**来源**: `task-real-brainstorm.md` (第 8-111 行)

### 7.1 核心设计决策

| 决策编号 | 决策内容 | 理由 |
|----------|----------|------|
| **决策 1** | **去掉 IterationControl，用 stopCondition + step.repeat 替代** | IterationControl.fixed(N) 与 stopCondition.maxIterations 语义完全重复；三个正交机制表达：ScheduleDriver（每轮如何触发）+ stopCondition（何时停止）+ step.repeat（单步重复） |
| **决策 2** | **step.repeat 只加在 send step 上** | wait-condition 本身就是"重复检查直到条件满足"，delay 重复无意义 |
| **决策 3** | **OR 组合保留** | 旧系统有完整类型定义、运行时逻辑和 UI 入口；默认值始终为 'and' |
| **决策 4** | **correlate 不做** | 旧 SCOE 参数关联是 SCOE adapter 内部逻辑；adapter 在翻译时 resolve 参数值为 literal，task 引擎不需要 step 间值传递 |
| **决策 5** | **FieldValueSpec.expression 不做** | 表达式求值归 send feature（SendRequest.variables）；task 的 fieldVariations 是静态值数组，按 roundIndex 取值 |
| **决策 6** | **fieldVariations 自动决定迭代** | fieldVariations 存在时，stopCondition.maxIterations 自动设为 `max(values.length)`，消费方不需要手动对齐 |
| **决策 7** | **单帧发送走同引擎** | 单帧发送 = `schedule: immediate` + 一个 send step + 无 stopCondition；UI 给简化表单，背后构造最简 TaskDefinition；好处：验证、错误处理、SendResult 全走同一路径 |
| **决策 8** | **SCOE 保持"翻译成 TaskDefinition"单一职责** | SCOE feature 唯一职责是把外部指令翻译成 TaskDefinition；参数解析、文件读取、命令映射全部在 SCOE 内部完成；翻译后的 TaskDefinition 与 UI 创建的无区别 |
| **决策 9** | **TimerService 放 platform facade** | renderer 进程 setInterval 受主线程阻塞和后台节流影响；Web Worker 实现精度 ~1ms，不跨 IPC 边界；具体位置待确认 |

### 7.3 循环引擎核心逻辑

**来源**: `task-real-brainstorm.md` 第 200-223 行

```typescript
async function runTask(ctx: TaskContext) {
  const driver = createDriver(ctx.definition.schedule);
  const stop = createStopGuard(resolveStopCondition(ctx.definition));

  while (!stop.shouldStop(ctx.state)) {
    await driver.waitForNext(ctx);

    for (const step of ctx.definition.steps) {
      if (stop.shouldStop(ctx.state)) break;

      if (step.kind === 'send' && step.config.repeat) {
        await executeRepeatableSend(ctx, step, stop);
      } else {
        await executeStep(ctx, step);
      }
    }
    ctx.state = advanceIteration(ctx.state);
    injectFieldVariations(ctx);
  }
}
```

根据 `rewrite-feature-boundaries.md` 第 70-87 行（Feature Boundary Table）和第 88-180 行：

#### 所有权边界清晰的 feature：
- **frame**（第 90-95 行）：拥有帧资产、字段编辑、校验、序列化、导入导出；不拥有接收运行状态、发送执行状态、SCOE 命令流程

- **send**（第 111-116 行）：拥有单帧发送（SendRequest→SendResult）、transport-level FIFO 队列；不拥有 task/case lifecycle、SCOE completion
- **task**（第 118-123 行）：拥有通用执行引擎、多态 step、多触发来源入口适配、条件匹配逻辑；不拥有 northbound 对外协议、send 局部状态
- **scoe**（第 125-130 行）：拥有 SCOE 协议、命令解析、完成条件定义、SCOE 领域状态；不拥有通用执行引擎（task owns）、单帧发送（send owns）
- **storage**（第 132-137 行）：拥有本地持久化、history、CSV、高速存储；不拥有 result truth、report object semantics
- **settings**（第 139-144 行）：拥有设置模型、默认值、持久化；不拥有运行事实、状态解释、领域流程
- **status**（第 146-151 行）：拥有状态指示、健康状态、状态视图、内部状态摘要；不拥有 heartbeat 协议、task 主状态
- **display**（第 153-158 行）：拥有展示偏好、展示配置校验/规范化、projection、UI-safe snapshot；不拥有 receive runtime facts、connection facts、settings persistence
- **result**（第 160-165 行）：拥有内部结果事实、结果归因和聚合规则；不拥有 report file generation、HTTP/FTP delivery
- **report**（第 167-172 行）：拥有报告对象生成、报告素材归集、报告文件准备；不拥有 HTTP/FTP delivery、内部结果事实定义

#### 所有权边界存在交叉风险的 feature：
- **status**（第 82 行）：指示灯配置属于 status/settings 交叉，需在 design 定 owner
- **display**（第 83 行）：display preference semantics 是静态定义，但持久化容器需由 settings/storage 合同声明

#### 所有权边界 Deferred 的 feature：
- **northbound**（第 174-179 行）：拥有 customer-facing inbound/outbound boundary、外部投影、对外交付；但涉及 customer schema/enum，本轮禁止冻结，当前代码没有 northbound 边界

#### 合并/拆分风险（第 272-285 行）：
- frame vs receive：分开。frame owns static assets；receive consumes explicit snapshots
- send vs task：分开。send owns send result；task owns lifecycle
- task vs northbound task：分开。旧 task 是 local oracle；northbound task 是 external transaction
- SCOE vs receive/send：SCOE 独立 owner，通过 explicit receive input / send request 接入
