16	# Task-SCOE-Send 执行引擎统一决策
17	
18	## 1. 背景与问题
19	
20	send design 和 task design 分别完成后，发现三个场景的核心模式高度相似：
21	
22	| 场景 | 触发来源 | 执行内容 |
23	| --- | --- | --- |
24	| 本地定时/触发发送 | 用户 UI、定时器、receive 事件 | 按计划发一系列帧 |
25	| SCOE 命令执行 | SCOE TCP 收到指令码 | 发命令帧 → 等完成条件 → 发确认帧 |
26	| Northbound 外部任务 | HTTP 收到外部命令 | 按用例序列发一系列帧 |
27	
28	三者都是"入口触发 → 按计划执行一系列发送操作 → 错误处理 → 进度追踪"，区别仅在入口适配。send design 和 task design 原本把 task 定位为"本地发送任务调度"，SCOE 只是"可选复用"——这个定位太窄了。
29	
30	## 2. 旧代码 evidence
31	
32	### 2.1 共性
33	
34	| 模式 | Task Executor | SCOE Executor | 共性程度 |
35	| --- | --- | --- | --- |
36	| 发送调用方式 | `useUnifiedSender.sendFrameInstance` | 同 | 高 |
37	| 结果检查 | `result.success` + target availability | `result.success` + 错误计数 | 中 |
38	| 定时器管理 | `useTimerManager` | `useTimerManager` 1秒轮询 | 高 |
39	
40	### 2.2 差异（旧代码结构层面）
41	
42	| 模式 | Task Executor | SCOE Executor |
43	| --- | --- | --- |
44	| 编排模式 | 三种调度（timed/trigger/sequence）+ error policy | 单命令执行 + 完成条件轮询 + 确认帧 |
45	| 错误策略 | pause/skip/stop 可配置 | 直接计数，无 pause/retry |
46	| 进度追踪 | currentCount/percentage/instanceIndex | commandSuccessCount/ErrorCount |
47	
48	差异来自旧代码的组织方式，不是来自业务语义的必然差异。统一后 task 的执行引擎可以覆盖所有场景。
49	
50	### 2.3 SCOE 不需要多命令序列
51	
52	用户确认：SCOE 命令是单命令执行模式（收一个指令码 → 执行一个命令）。不存在多命令按序列执行的需求。SCOE 的完整执行流程是：发命令帧 → 等完成条件 → 发确认帧。
53	
54	## 3. 决策
55	
56	### 3.1 task 是通用执行引擎
57	
58	task 的核心职责不是"本地定时/触发发送调度"，而是：
59	
60	**接收一个执行计划（step 序列），按顺序执行，处理错误，追踪进度。**
61	
62	触发来源只是入口适配的不同：
63	- `user-ui`：send 页面的定时/触发/序列对话框
64	- `timer`：定时器自动触发
65	- `receive-trigger`：receive 事件匹配触发
66	- `scoe-command`：SCOE 指令码解析后触发
67	- `northbound-command`：northbound 外部命令触发
68	
69	入口适配由调用方负责（SCOE 翻译命令、northbound 翻译外部请求、send 页面翻译用户配置），执行逻辑由 task 统一提供。
70	
71	### 3.2 TaskStepDefinition 多态化
72	
73	TaskCaseDefinition 重命名为 TaskStepDefinition，支持多态 step 类型：
74	
75	**send-step**：构帧 → 通过 send service 发送 → 得到 SendResult
76	
77	- `frameId`、`fieldValues`、`targetId`、`options`
78	
79	**wait-condition-step**：订阅 receive 事件，等待条件满足或超时
80	
81	- `condition`：frameId + fieldId + operator + threshold
82	- `timeoutMs`：超时时间
83	- `onTimeout`：超时策略（fail / skip / continue）
84	
85	**delay-step**：等待指定时长
86	
87	- `durationMs`
88	
89	### 3.3 各场景如何映射
90	
91	**本地定时发送**（schedulingMode = timed）：
92	
93	```
94	每轮: [send-step]
95	```
96	
97	**本地触发发送**（schedulingMode = trigger）：
98	
99	```
100	循环: [wait-condition-step(等触发条件)] → [send-step]
101	```
102	
103	**本地序列发送**（schedulingMode = sequence）：
104	
105	```
106	[send-step-1] → [delay-step] → [send-step-2] → [delay-step] → [send-step-3] → ...
107	```
108	
109	**SCOE 命令执行**（triggerSource = scoe-command）：
110	
111	```
112	[send-step(命令帧)] → [wait-condition-step(SCOE 完成条件)] → [send-step(确认帧)]
113	```
114	
115	**Northbound 外部任务**（triggerSource = northbound-command）：
116	
117	```
118	[send-step(case-1)] → [delay-step] → [send-step(case-2)] → ...
119	```
120	
121	### 3.4 SCOE 不需要自己的执行器
122	
123	`useScoeCommandExecutor` 的编排逻辑完全由 task 承接。SCOE 的职责是：
124	
125	- 命令解析（指令码 → step 定义）
126	- 完成条件定义
127	- 确认帧配置
128	- SCOE 领域状态管理（commandSuccessCount 等，通过订阅 task lifecycle event 更新）
129	
130	SCOE 不拥有 send 编排、错误策略、进度追踪——这些都由 task 提供。
131	
132	### 3.5 send 不变
133	
134	send 只做单帧发送（构帧 + target 路由 + transport write + 结果输出）。send 页面的定时/触发/序列对话框本质上是 task 的 UI 入口，创建 TaskDefinition 并通过 task service 执行。
135	
136	### 3.6 条件匹配归属
137	
138	wait-condition 和 trigger 共用同一套条件匹配逻辑（frameId + fieldId + operator + threshold）。归属：
139	
140	- 条件类型定义和匹配算法归 `task/core`（纯 TypeScript，可单测）
141	- 条件内容由调用方定义（SCOE 定义完成条件、trigger 配置定义触发条件）
142	- task service 通过 receive public API 的 `ReceiveInputEvent` 订阅事件源，在 task/core 中匹配条件
143	- runtime 只负责服务装配时把 receive event source 注入 task service
144	
145	### 3.7 error policy 适用于所有 step 类型
146	
147	- send-step 失败：retry / skip / stop / pause
148	- wait-condition 超时：retry / skip / stop / pause
149	- delay-step 不可失败
150	
151	### 3.8 QueueModel 不受影响
152	
153	send 的 transport-level FIFO 不变。task 的编排级等待通过 `await SendResult` 实现。
154	
155	## 4. 对现有 design 的修订影响
156	
157	### 4.1 task design
158	
159	需要修订的部分：
160	
161	1. **定位重写**：从"本地发送任务调度"调整为"通用执行引擎"

198	- SCOE 领域逻辑（命令解析、条件定义、确认帧配置）留在 SCOE feature
199	- SCOE 不拥有 send 编排、错误策略或进度追踪
200	- SCOE 订阅 task lifecycle event 更新自己的领域状态

90	### 4.1 Owner / not owner
91	
92	| 分类 | send owner | send not owner |
93	| --- | --- | --- |
94	| 构帧 | 接收 send request，基于 frame snapshot 执行字段编码、字节组装、checksum 计算，输出 FrameBuildOutput。 | frame definition truth、field definition truth、expression definition truth、expression runtime 执行。 |
95	| 发送请求 | 接收外部 SendRequest，验证参数完整性，编排构帧→target 解析→transport write→结果输出。 | task scheduling、trigger logic、timed execution、sequence orchestration。 |
96	| target 路由 | 将 SendRequest.targetId 解析为 connection TransportTargetSnapshot，检查可用性。 | connection lifecycle、target creation/deletion、transport resource handle、northbound deviceId。 |
97	| 队列 | 可选内部 write queue，保证同一 target 的 transport write 顺序。 | task-level step 序列编排、多帧执行顺序、pause/resume 语义。任何多步骤发送编排都是 task 职责，send 只做单帧发送。 |
98	| 发送结果 | 输出 SendResult（sent / build-error / target-unavailable / transport-error / timeout / cancelled）。 | task progress、case result、report generation、northbound response。 |
99	| 统计 read model | 按 stable key 维护 send count、success/failure count、bytes sent、per-frame stats、per-target stats、last send timestamp。 | global system lifecycle、receive stats、task progress stats。 |
100	| 平台能力 | 构帧和 send 编排在 renderer TypeScript 完成；transport write 通过 connection public service。 | 直接访问 Node/Electron/serialport/socket。 |
101	
102	send 的核心职责是把一个 SendRequest 转化为一个 SendResult。send 不是 task 的子集，也不是 task 的替代。task 是通用执行引擎，负责编排"按什么顺序执行哪些步骤"（含 send-step、wait-condition-step、delay-step）；send 负责"这一次怎么构帧、写到哪个 target、结果是什么"。所有多步骤发送编排（定时、触发、序列、SCOE 命令、northbound 用例）都通过 task 执行，send 只被 task 的 send-step 调用。

123	### 4.3 Core types
124	
125	本轮不冻结最终类型名和字段 schema，只定义类型职责和分类。
126	
127	**SendRequest** — 发送请求输入：
128	- `frameId`：目标帧引用。
129	- `fieldValues`：字段值映射（字段 ID → 用户/系统提供的值）。
130	- `targetId`：目标 transport target 引用。
131	- `options`：构帧选项（checksum 策略、编码选项）。
132	- `context`：请求来源标识（user / task / SCOE / test），含可选 taskId、caseId、stepIndex 用于追踪。
133	
134	**FrameBuildInput** — 构帧内部输入：
135	- `frameSnapshot`：从 frame public API 获取的只读帧资产。
136	- `fieldDefinitions`：对应字段定义列表。
137	- `fieldValues`：已解析的字段值。
138	- `options`：构帧选项。
139	
140	**FrameBuildOutput** — 构帧内部输出：
141	- `bytes`：组装完成的 Uint8Array。
142	- `resolvedFields`：实际写入的字段值映射（含编码后值）。
143	- `checksumValue`：校验和计算结果。
144	- `issues`：构建过程中的警告/错误（字段缺失、值溢出、编码问题等）。
145	
146	**SendResult** — 发送结果公开输出：
147	- `kind`：sent / build-error / target-unavailable / transport-error / timeout / cancelled。
148	- `requestRef`：回引原始请求标识。
149	- `bytesBuilt`：构帧产生的字节数。
150	- `bytesSent`：实际写入 transport 的字节数。
151	- `timestamp`：发送完成时间戳。
152	- `error`：transport-level 错误详情（如可用）。
153	- `buildIssues`：构帧阶段的问题列表（如有）。
154	
155	**TargetResolution** — target 解析结果：
156	- `target`：解析到的 TransportTargetSnapshot。
157	- `available`：target 当前是否可用。
158	- `error`：解析失败原因（如 target 不存在、连接未建立）。
159	
160	**SendStatistics** — 统计 read model：
161	- 按 stable key（frameId / targetId / resultKind）维护计数。
162	- 包含 total requests、total sent、total errors、total bytes sent。
163	- 包含 last send timestamp。
164	- 不包含 task progress、case result、report 或 northbound 语义。
165	
166	**QueueModel** — 写入队列（可选）：
167	- 同一 target 的 transport write 请求按 FIFO 排队。
168	- 队列深度、溢出策略和优先级由实现阶段结合 runtime 证据决定。
169	- 队列是 send 内部优化，不是 task-level 序列编排的替代。
170	
171	### 4.4 Service contract
172	
173	send 的主服务合约是单次发送生命周期：
174	
175	```
176	SendRequest
177	  → validate (参数完整性、frameId/targetId 存在性)
178	  → resolve frame snapshot (通过 frame public API)
179	  → build frame (core 构帧逻辑)
180	  → resolve target (通过 connection public API)
181	  → check availability
182	  → [queue write if needed]
183	  → execute transport write (通过 connection public service)
184	  → emit SendResult
185	  → update statistics read model
186	```
187	
188	任何步骤失败都提前返回对应 kind 的 SendResult，不继续后续步骤。
189	
190	**同步 vs 异步**：
191	
192	- 构帧（validate → build）是同步计算，可在 core 层单测。
193	- target 解析是同步查询，读取 connection selector 当前值。
194	- transport write 是异步操作，通过 connection service 发起。
195	- SendResult 通过 service 返回值或 explicit event 输出，由调用方（task/runtime/page）选择消费方式。
196	
197	**调用方式**：
198	
199	- task 通过 send public service 调用，获得 SendResult。
200	- page 通过 send composable/service 调用，更新 UI snapshot。
201	- SCOE 通过 runtime 编排或 send public service 调用，将 SCOE 命令翻译为 SendRequest。
202	- 测试通过 fake adapter 调用，验证构帧和结果逻辑。
203	
204	### 4.5 State shape and selector surface
205	
206	| 状态类别 | 写入 owner | 读取方 | reset / lifecycle | 设计约束 |
207	| --- | --- | --- | --- | --- |
208	| Send runtime facts | send service | task、status、result、storage、SCOE、pages（通过 selector/event） | 随 send lifecycle、app cleanup 驱动；通常 transient | 单点写入；不保存 connection/frame/task/SCOE 状态 |
209	| Send statistics read model | send service 基于 SendResult 增量更新 | pages、status、result、task（通过只读 selector） | 按 stable key 增量；reset 由 send lifecycle 或显式 action 驱动 | 不写回 frame definition 或其他静态资产 |
210	| Send result history | send service | pages、storage、result（通过 selector/event） | 有限窗口；超出部分由 storage 持久化 | 不等同于 task result 或 report |
211	| UI snapshot | pages / send composables | UI 组件 | 页面生命周期 | 不定义 send truth |
212	
213	**Selector surface**：
214	
215	- `selectSendStatistics`：send 统计 read model。
216	- `selectSendResults`：近期 send result 只读列表。
217	- `selectSendSnapshot`：面向 UI 的安全 snapshot。
218	- `selectSendStatus`：当前 send 服务状态（idle / sending / error）。
219	
220	Selector 不暴露可变 state 引用、内部 service 实例、connection adapter 或 frame store。

222	### 4.6 Cross-feature interaction contracts
223	
224	#### send → frame（消费帧定义构帧）
225	
226	| 维度 | 契约 |
227	| --- | --- |
228	| 方向 | send 读取 frame public API |
229	| send 需要 | `getFrameAsset(frameId)` 获取 `ReadonlyFrameAsset`；字段定义从 frame snapshot 中读取；`FrameDirection` 过滤 send 方向帧 |
230	| frame 提供 | 只读 frame asset snapshot、field definition、expression definition |
231	| 禁止 | send 写入 frame state；send 让 frame 拥有 send instance 或 send queue；send import frame internal state |
232	
233	#### send → connection（通过 adapter port 发送字节）
234	
235	| 维度 | 契约 |
236	| --- | --- |
237	| 方向 | send 调用 connection public service |
238	| send 需要 | `selectTransportTargets()` 获取 target availability；`ConnectionService` write 方法提交字节；write result 返回 transport acceptance/failure |
239	| connection 提供 | target snapshot、transport write capability、transport-level error |
240	| 禁止 | send 管理 connection lifecycle；send import connection internal state；send 硬编码 SCOE/northbound target；send 把 transport failure 等同 task/result failure |
241	
242	#### task → send（被 task 编排调度）
243	
244	| 维度 | 契约 |
245	| --- | --- |
246	| 方向 | task 调用 send public service |
247	| task 提供 | SendRequest（含 frameId、fieldValues、targetId、context） |
248	| send 返回 | SendResult（sent / error kind） |
249	| 禁止 | send 写入 task state；send 决定 task lifecycle；send 拥有 pause/resume/stop 语义 |
250	
251	**与 task 的边界**：
252	
253	- send 执行单帧发送，返回结果。
254	- task 是通用执行引擎，拥有 step 序列编排（send-step / wait-condition-step / delay-step），决定按什么顺序执行哪些步骤。
255	- send 内部 write queue 只保证同一 target 的 transport-level 顺序，不等于 task-level step 序列。
256	- task 的 send-step 通过 `await sendService.execute(request)` 实现编排级等待。
257	- send 不了解 task 的存在，只接收 SendRequest 和 context。task 是 send 的唯一编排方（含 SCOE、northbound、本地定时/触发/序列）。
258	
259	#### send → status
260	
261	| 维度 | 契约 |
262	| --- | --- |
263	| 方向 | status 消费 send statistics/result |
264	| send 提供 | 只读 send statistics selector、send result event |
265	| 禁止 | send 写入 status read model；status import send internal state |
266	
267	#### send → result
268	
269	| 维度 | 契约 |
270	| --- | --- |
271	| 方向 | result 消费 send result 作为 result material |
272	| send 提供 | SendResult event / selector |
273	| 禁止 | send 定义 case/task result truth；send 直接写 result state |
274	
275	#### send → storage
276	
277	| 维度 | 契约 |
278	| --- | --- |
279	| 方向 | storage 消费 send result 作为 local history/material |
280	| send 提供 | SendResult event |
281	| 禁止 | send 执行文件写入；send 定义 storage 路径或 history schema |
282	
283	#### send → SCOE
284	
285	| 维度 | 契约 |
286	| --- | --- |
287	| 方向 | SCOE 翻译命令为 TaskDefinition（triggerSource = scoe-command），通过 task public service 创建执行。task 的 send-step 调用 send public service。 |
288	| SCOE 提供 | TaskDefinition（含 send-step + wait-condition-step + send-step）。send 只被 task 的 send-step 调用，不感知 SCOE。 |
289	| send 返回 | 普通 SendResult（给 task，不直接给 SCOE） |
290	| 禁止 | send 硬编码 SCOE fixed target；send 解释 SCOE 命令语义；send 判断 SCOE 完成条件；send 感知 task 或 SCOE 的存在 |
291	
292	SCOE 不直接调用 send service。SCOE 通过 task 创建执行计划，task 的 send-step 调用 send。send 的唯一调用方是 task（含各种 triggerSource 的 task 实例）和 send 页面（单次发送）。
293	
294	#### send → receive
295	
296	| 维度 | 契约 |
297	| --- | --- |
298	| 方向 | 无直接依赖 |
299	| 说明 | 若 receive trigger 需要发帧，通过 task/runtime 编排，send 不直接调用 receive |
300	
301	#### send → report / northbound
302	
303	| 维度 | 契约 |
304	| --- | --- |
305	| 方向 | 无直接依赖 |
306	| 说明 | report 和 northbound 从 task/result/storage 读取事实，不直接消费 send internals |

343	| 层 | 目标职责 |

353	### 4.9 Runtime involvement
354	
355	send 需要 runtime 参与的场景：
356	
357	- **服务装配**：runtime 创建 send service，注入 frame reader、connection service、event emitter。

359	- **send result 分发**：runtime 可将 SendResult event 路由到 task/status/result/storage。

364	- 决定发送策略或 task lifecycle。

369	
370	send 不直接访问 platform：
371	
372	- 构帧在 renderer TypeScript 完成，不需要 platform 能力。

376	### 4.11 High-frequency data flow
377	
378	send 的数据流不是高频入站流，但存在以下需要注意的场景：
379	
380	- **task 快速连发**：task 按序列快速调用 send，send 内部 write queue 需要处理背压。
381	- **transport write 耗时**：某些 transport 的 write 操作可能阻塞或延迟，send 需要异步处理。
382	- **统计更新频率**：快速连发时统计更新使用 batch/delta，不逐次刷新 UI snapshot。
383	
384	本轮不冻结队列深度、窗口大小、延迟阈值或丢弃策略，只要求实现阶段声明并验证。

473	## 5. Open questions
474	
475	### 5.1 send 与 task 的边界
476	
477	以下问题需要 task design 联合确认：
478	
479	1. **send 是否拥有内部 write queue？**
480	   - 建议是：send 拥有轻量 transport-level write queue，保证同一 target 的 write 顺序。
481	   - task 拥有 task-level 序列编排（多帧执行顺序、间隔、条件）。
482	   - 两者不冲突：task 等前一次 SendResult 后再发下一帧。
483	
484	2. **SendResult 是 sync return 还是 async event？**
485	   - 建议是：send public service 返回 Promise\<SendResult\>，同时可选 emit SendResult event。
486	   - task 可以 await SendResult，也可以通过 event 消费。
487	   - 这避免了 send 需要了解 task 的存在。
488	
489	3. **send instance 配置归谁？**
490	   - 旧系统 `sendFrameInstancesStore` 承载 per-frame 的发送配置（字段默认值、target 偏好等）。
491	   - 建议：send own send-time 的 request 组装；per-frame 的"发送配置模板"如果需要持久化，可能归 storage 或 send own config，不归 frame。
492	   - 需 task design 和 settings design 联合确认。
493	
494	4. **send 是否了解 task 的存在？**
495	   - 建议是：不。send 只接收 SendRequest（含 context 字段供追踪），不区分调用方。
496	   - context 中的 source/taskId/caseId/stepIndex 是纯信息性的，send 不基于它们改变行为。
497	
498	5. **send 失败是否影响 task lifecycle？**
499	   - send 只输出 SendResult。task 根据 SendResult.kind 决定是否 pause/stop/retry。
500	   - send 不直接写 task state。
501	
502	### 5.2 expression runtime 在 send 中的角色
503	
504	- 旧发送支持 expression 计算（如从其他帧的接收值填充发送字段）。
505	- 问题：expression 执行归谁？frame definition 归 frame，但 expression 执行需要运行时上下文（receive values、global stats 等）。
506	- 建议：本轮 send design 不执行 expression；SendRequest.fieldValues 已包含 resolved values。expression runtime 的归属由后续单独设计决定。
507	- 如果需要 send-time expression，应在 send design 中显式声明为新增入口，不偷偷引入。
508	
509	### 5.3 checksum 策略完整列表
510	
511	- 旧系统有多种 checksum 策略。本轮不冻结完整列表。
512	- 建议：send/core 提供可扩展的 checksum 计算接口，具体策略在实现阶段补充。
513	
514	### 5.4 send 与 receive trigger 的关系
515	
516	- receive design 明确 receive 不直接调用 send。
517	- receive trigger → task → send 是建议路径。
518	- 是否允许 receive 直接触发 send（不经 task）？建议否：所有发送都经过 send public service，触发方可以是 task/runtime，不是 receive。
519	
520	## 6. Implementation confirmation questions
521	
522	实现前必须确认以下问题：
523	
524	1. **task design 是否确认 send-task 调用方式？** — SendResult 是 Promise return、event 还是两者兼有。
525	2. **expression runtime 归属是否已确认？** — send 是否需要执行 expression，还是只接受 resolved values。
526	3. **send instance 配置是否需要持久化？** — 如果需要，归 send own config、settings 还是 storage。
527	4. **connection bridge 是否已 ready？** — send 需要 connection 的 target write 实际可用。

529	6. **旧 send instance JSON 样例是否可用？** — 作为 migration fixture 输入。
530	7. **queue 行为是否需要 runtime 证据？** — 快速连发时的背压和队列深度。
531	
532	## 7. Task boundary suggestions
533	
534	以下建议供 task design 参考：
535	
536	1. **task owns scheduling and sequencing**：task 决定何时调 send、调几次、按什么顺序。send 只执行单帧发送。
537	2. **task awaits SendResult**：task 通过 await send public service 的返回值或监听 SendResult event 来推进 task progress。
538	3. **task owns pause/resume/stop**：这些 lifecycle 语义在 task 内部处理。send 不知道自己是否属于一个 task。
539	4. **task owns retry strategy**：如果 SendResult.kind 是 transport-error，task 决定是否重试、重试几次、间隔多久。send 不自动重试。
540	5. **task 不 import send internal state**：task 只通过 send public service 和 selector 交互。
541	6. **建议 task design 为 send 定义最小调用契约**：确认 SendRequest 和 SendResult 的最终形态，以及 task 如何消费 SendResult 来推进 lifecycle。
