53	## 设计决策
54	
55	### 决策 1：去掉 IterationControl，用 stopCondition + step.repeat 替代
56	
57	**理由**：IterationControl.fixed(N) 与 stopCondition.maxIterations 语义完全重复。去掉 IterationControl，迭代行为由三个正交机制表达：
58	
59	- ScheduleDriver：每轮 step 序列如何触发（immediate / timer / event）
60	- stopCondition：整个任务何时停止（maxIterations / maxDurationMs / exitCondition）
61	- step.repeat：单个 send step 的重复发送（until / maxCount）
62	
63	**旧模式映射**：
64	
65	| 旧模式 | 新表达 |
66	|--------|--------|
67	| 顺序发送 | `schedule: immediate`，无 stopCondition，无 repeat |
68	| 定时固定 N 次 | `schedule: timer(intervalMs)` + `stopCondition: { maxIterations: N }` |
69	| 定时无限 | `schedule: timer(intervalMs)`，无 stopCondition |
70	| 条件触发 | `schedule: event(conditions)` |
71	| 一直发 A 直到 X，再发 B | `schedule: immediate`，step A `repeat.until: X`，step B 无 repeat |
72	| 定时发送整个序列直到 Y | `schedule: timer` + `stopCondition: { exitCondition: Y }` |
73	| 文件逐行发送 | `fieldVariations` 自动 maxIterations + `schedule: timer` |
74	| 单帧发送 | `schedule: immediate`，一个 send step，无 repeat |
75	
76	### 决策 2：step.repeat 只加在 send step 上
77	
78	**理由**：wait-condition 本身就是"重复检查直到条件满足"的语义，delay 重复无意义。repeat 只加在 send step 上，不引入独立的 repeat wrapper type。
79	
80	### 决策 3：OR 组合保留
81	
82	**理由**：旧系统 OR 组合有完整的类型定义、运行时逻辑和 UI 入口：
83	- 类型：`TriggerCondition.logicOperator?: 'and' | 'or'`（`sendInstances.ts:123`）
84	- 运行时：`useSendTaskTriggerListener.ts:149` 使用 `condition.logicOperator` 做短路 AND/OR 评估
85	- UI：`TriggerConditionList.vue:36` 有 AND/OR 下拉选项；`TriggerSendDialog.vue:503` 显示逻辑操作符
86	- 默认值始终为 `'and'`
87	
88	通过 ConditionTerm.logicOperator 可选字段表达，默认 AND。
89	
90	### 决策 4：correlate 不做
91	
92	**理由**：旧 SCOE 参数关联是 SCOE adapter 内部逻辑。adapter 在翻译时 resolve 参数值为 literal，构造 TaskDefinition 时所有阈值已知。task 引擎不需要 step 间值传递。
93	
94	### 决策 5：FieldValueSpec.expression 不做
95	
96	**理由**：表达式求值归 send feature（SendRequest.variables）。task 的 fieldVariations 是静态值数组，按 roundIndex 取值。动态计算用表达式时由 send 侧处理。
97	
98	### 决策 6：fieldVariations 自动决定迭代
99	
100	**理由**：fieldVariations 存在时，stopCondition.maxIterations 自动设为 `max(values.length)`。消费方不需要手动对齐。
101	
102	### 决策 7：单帧发送走同引擎
103	
104	**理由**：单帧发送 = `schedule: immediate` + 一个 send step + 无 stopCondition。UI 给简化表单，背后构造最简 TaskDefinition。好处：验证、错误处理、SendResult 全走同一路径，不维护两套发送逻辑。
105	
106	### 决策 8：SCOE 保持"翻译成 TaskDefinition"单一职责
107	
108	**理由**：SCOE feature 唯一职责是把外部指令翻译成 TaskDefinition。参数解析、文件读取、命令映射全部在 SCOE 内部完成。翻译后的 TaskDefinition 与 UI 创建的无区别。可复用 ConditionTerm 等类型，但模块边界不交叉。
109	
110	**非 task 场景说明**：部分 SCOE 命令（health_check、link_check 等）不需要创建 task，指令接入 feature 自行处理这些轻量查询/状态类命令。task-real 只负责"需要执行 step 序列"的命令，指令接入 feature 决定哪些命令走 task 路径、哪些自行处理。这不在 task-real 范围内。

476	
477	替代现有 `evaluateCondition`（core/condition-matcher.ts），支持 AND/OR 组合。
478	
479	```typescript
480	function evaluateConditionGroup(
481	  conditions: readonly ConditionTerm[],
482	  fieldValues: Readonly<Record<string, number | string | null>>,
483	): boolean {
484	  if (conditions.length === 0) return true;
485	
486	  let result = evaluateSingleCondition(conditions[0], fieldValues);
487	
488	  for (let i = 1; i < conditions.length; i++) {
489	    const op = conditions[i].logicOperator ?? 'and';
490	    const current = evaluateSingleCondition(conditions[i], fieldValues);
491	
492	    if (op === 'or') {
493	      result = result || current;
494	      if (result) break;   // OR 短路
495	    } else {
496	      result = result && current;
497	      if (!result) break;  // AND 短路
498	    }
499	  }
500	
501	  return result;
502	}
503	
504	function evaluateSingleCondition(
505	  condition: ConditionTerm,
506	  fieldValues: Readonly<Record<string, number | string | null>>,
507	): boolean {
508	  const value = fieldValues[condition.fieldId];
509	  if (value === undefined || value === null) return false;
510	  return compareValues(value, condition.threshold, condition.operator);
511	}
512	```
513

517	### 3.2 ConditionRegistry 改造
518	
519	从单条件注册（condition-registry.ts:11-56）改为条件组注册。
520	
521	```typescript
522	interface ConditionGroup {
523	  readonly id: string;
524	  readonly conditions: readonly ConditionTerm[];
525	  readonly onSatisfied: () => void;
526	}
527	
528	class ConditionRegistry {
529	  private groups = new Map<string, ConditionGroup>();
530	  private frameIndex = new Map<string, Set<string>>();
531	  private nextGroupId = 1;
532	
533	  registerGroup(conditions: readonly ConditionTerm[], onSatisfied: () => void): ConditionGroup {
534	    const id = `cg-${this.nextGroupId++}`;
535	    const group: ConditionGroup = { id, conditions, onSatisfied };
536	    this.groups.set(id, group);
537	
538	    const frameIds = new Set(conditions.map(c => c.frameId));
539	    for (const frameId of frameIds) {
540	      if (!this.frameIndex.has(frameId)) this.frameIndex.set(frameId, new Set());
541	      this.frameIndex.get(frameId)!.add(id);
542	    }
543	
544	    return group;
545	  }
546	
547	  unregisterGroup(group: ConditionGroup): void {
548	    this.groups.delete(group.id);
549	    for (const set of this.frameIndex.values()) set.delete(group.id);
550	  }
551	
552	  processInput(input: ConditionMatchInput): void {
553	    const groupIds = this.frameIndex.get(input.frameId);
554	    if (!groupIds) return;
555	
556	    for (const groupId of groupIds) {
557	      const group = this.groups.get(groupId);
558	      if (!group) continue;
559	
560	      // sourceId 过滤
561	      if (input.sourceId !== undefined) {
562	        const hasSourceMatch = group.conditions.some(
563	          c => c.sourceId === undefined || c.sourceId === input.sourceId
564	        );
565	        if (!hasSourceMatch) continue;
566	      }
567	
568	      if (evaluateConditionGroup(group.conditions, input.fieldValues)) {
569	        group.onSatisfied();
570	      }
571	    }
572	  }
573	
574	  clear(): void {
575	    this.groups.clear();
576	    this.frameIndex.clear();
577	  }
578	
579	  get size(): number {
580	    return this.groups.size;
581	  }
582	}
583	```

### 发现的问题

**[高] `SendStepConfig.variables` 类型不匹配 `SendRequest.variables`**
文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/core/types.ts:63`
问题：`SendStepConfig.variables` 被类型化为 `ReadonlyMap<string, unknown>`，但 `SendRequest.variables`（来自 `send/core/types.ts`）是 `VariableMap`，即 `ReadonlyMap<string, VariableValue>`，其中 `VariableValue = string | number | boolean`。使用 `unknown` 而不是 `VariableValue` 丧失了类型安全性，并且意味着 `buildSendRequest` 无法将 `stepConfig.variables` 赋值给 `SendRequest.variables`，除非进行类型转换。这直接违背了设计规范的第 4.1 节，该节规定 `variables` 直接映射。
修复：将类型更改为 `ReadonlyMap<string, string | number | boolean>` 或从 `@/shared/expression/types` 导入并使用 `VariableMap`，以匹配 `SendRequest`。

**[高] `buildSendRequest` 未传递 `variables` 且未实现 `resolveFieldValues`**
文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/services/task-step-executors.ts:17-28`
问题：设计规范（第 4.1 节和第 2.5 节）规定 `buildSendRequest` 应该 (1) 传递 `variables: stepConfig.variables` 和 (2) 通过 `resolveFieldValues` 合并 `fieldVariations`。当前实现两者都未实现——它只设置 `frameId`、`targetId`、条件性的 `userFieldValues` 和 `context`。这并非阶段 1 的阻碍（`variables` 和 `fieldVariations` 尚未被消费），但这意味着当阶段 2 添加 `fieldVariations` 注入时，`buildSendRequest` 需要额外的参数 (`iteration`、`definition`)，而目前 `executeSendStep` 已经传递了这些参数，但它们被忽略了。这应作为技术债务进行跟踪。
修复：不是阶段 1 的阻碍，但添加一条注释，指示 `variables` 传递和 `resolveFieldValues` 集成待阶段 2 进行。或者现在就传递 `variables`（它已经是 `SendStepConfig` 上的一个可选字段，零风险）。

**[中] 当输入没有 `sourceId` 时，`sourceId` 过滤绕过}
文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/services/condition-registry.ts:44-48`
问题：当 `input.sourceId` 为 `undefined` 时，`sourceId` 过滤块被完全跳过。这意味着带有 `sourceId: 'source-A'` 条件的组，会被来自完全不同来源的输入触发。设计规范没有明确指定这种行为。测试文件 `ta[REDACTED_SK].spec.ts:226-233` 明确测试并断言这种行为是正确的（“输入没有 `sourceId` -> 过滤器被跳过”），因此这是有意为之的。然而，这与直觉相反：如果任务正在监听特定来源，则没有来源信息的输入不应自动匹配。
修复：将此决定记录在代码注释中。如果未来表明更严格的行为更可取，请修改过滤器，要求输入具有匹配的 `sourceId` 或两者都未指定 `sourceId`。

**[中] `wait-condition` 步骤的默认超时值是硬编码的**
文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/services/task-step-executors.ts:80`
问题：当 `timeoutMs` 为 `undefined` 时，代码默认使用 `setTimeout(..., timeoutMs ?? 30000)`——硬编码的 30 秒。设计规范指出 `timeoutMs?: number` 其中“undefined = 无限期等待直到信号中断”（设计规范第 1.2 节，WaitConditionConfig 表）。硬编码的 30 秒默认值直接与此规范相矛盾。
修复：当 `timeoutMs` 为 `undefined` 时，不要设置超时计时器。仅当 `timeoutMs` 具有显式值时才创建 `setTimeout`。这符合设计规范中 `timeoutMs` 的可选语义。

**[低] `evaluateConditionGroup` 具有冗余的空值检查**
文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/core/condition-matcher.ts:19-20`
问题：在 `conditions.length === 0` 检查（第 17 行）返回 `true` 之后，第 20 行的 `if (!first) return true;` 是多余的。由于数组长度已验证为 `>= 1`，因此 `conditions[0]` 不能是 `undefined`。这是防御性代码，是无害的，但增加了微不足道的认知负荷。
修复：可选——移除第 20 行的 `if (!first) return true;` 检查，因为它在第 17 行的长度检查之后是不可达的。

**[低] `task-service.ts` 中的 `nextInstanceId` 是模块级可变状态**
文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/services/task-service.ts:51`
问题：`let nextInstanceId = 1` 位于模块级别，这意味着 `createTaskService` 的所有调用共享相同的计数器。这阻碍了测试隔离，并可能在热重载场景中导致 ID 冲突。在实践中，每个测试创建一个新的服务，但相同的计数器递增。目前这还不是一个问题，因为 ID 只需是唯一的，而不是可预测的。
修复：可选——将计数器移动到 `createTaskService` 闭包内部，以便每个服务实例都有自己的计数器。
