**[HIGH] #1 -- `real-serial-adapter.ts:23`：`toAdapterErrorKind` 返回 `string`，而不是窄化的联合类型**

文件：`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/connection/adapters/real-serial-adapter.ts`
行：23

```
error TS2322: Type 'string' is not assignable to type '"write-failed" | "stale-event" | ... | "invalid-config"'.
```

`TRANSPORT_ERROR_KIND_SET` 是 `Set<string>`。`Set.has()` 返回 `boolean`，但当条件为真时，TypeScript 无法将 `kind` 从 `string` 窄化为 `TransportErrorKind`。返回的表达式 `kind` 仍然是 `string` 类型。

修复方法：在检查后进行类型转换：
```ts
if (kind !== undefined && TRANSPORT_ERROR_KIND_SET.has(kind)) return kind as TransportErrorKind;
```

或使用包含 `TRANSPORT_ERROR_KINDS` 的类型谓词辅助函数：
```ts
function isErrorKind(kind: string): kind is TransportErrorKind {
  return TRANSPORT_ERROR_KIND_SET.has(kind);
}
```

这会在 `tsc --noEmit` 中产生一个编译时错误。它曾在代码中存在（该文件是新的），因此从技术上讲，它是在该功能的适配器迁移工作中引入的。

return {

server.on('error', (err: Error) => {

与通过 `settled` 标志防止双重解析的 TCP 客户端不同，TCP 服务器没有此标志。如果 `server.listen()` 回调（行 354）触发后，`server.on('error')` 又触发（例如，在监听后的绑定错误），`promise` 将解析两次。Node.js `net.Server` 保证在调用监听回调后不会触发错误，因此这在实践中是安全的，但 TCP 客户端和服务器之间不一致的模式值得注意。

31	## Batch 0 Architecture Baseline
32	
33	本文是 Batch 0 的整体架构基线。后续每个功能域进入 `cs-feat-design` 前，都必须把本文列为直接合同或边界护栏，并说明本批如何遵守本文的目录、依赖、状态和平台边界。
34	
35	Batch 0 只固定后续功能必须遵守的架构骨架：
36	
37	- 顶层目录固定为 `app / platform / shared / features / runtime / pages / widgets`。
38	- feature 内部通用分层固定为 `core / services / state / adapters / composables / components / fixtures`，按实际职责创建，不为了填满模板而建空层。
39	- feature public API 只是跨 feature 访问边界，不是必须新增的接口层；外部不得 import 其他 feature 的内部 `state`、`adapters`、内部 composable、内部 service 实现或私有 helper。
40	- `runtime/` 只在应用生命周期、平台资源装配或跨 feature 编排确有需要时出现，不是新的全局业务中心。
41	- renderer、platform、preload、main 的边界按本文和质量规则执行；现有 main 业务化只作为迁移风险处理，不作为新架构目标。
42	- 状态必须分清静态资产、运行事实、统计 read model 和 UI snapshot；运行统计不得写回 frame definition、字段定义或其他静态资产。
43	- 高频数据按 batch、delta、队列、节流、snapshot 和背压处理，页面不直接消费底层逐包事件。
44	- 跨 feature 通信只允许公开 service、runtime 编排、显式事件或边界输入输出，不允许互相 import 内部 state。
45	- pages、widgets、feature components 只承担各自 UI 边界，不拥有协议语义、任务推进、平台访问或跨域流程。
46	- 测试、fixture 和 oracle 必须放在可复用、可审查的位置，优先归入对应 feature 的 `fixtures/` 或 `core` 测试材料。
47	
48	Batch 0 不固定以下内容：
49	
50	- 不写字段 schema、接口签名、事件 payload 或 northbound 字段。
51	- 不设计 receive、send、task、SCOE、result、report、northbound 的内部算法和流程细节。
52	- 不给高频链路写具体队列深度、窗口大小或延迟阈值；这些参数必须在对应 feature design 中结合目标硬件、runtime 证据或压测计划确定。
53	- 不为每个 feature 预先创建 public API 清单；只有出现外部消费者或跨 feature 协作时，才在对应 `cs-feat-design` 中定义允许入口。

151	## 7. Recommended Internal Feature Layout
152	
153	不是每个 feature 都必须完整拥有以下子目录。只有当职责确实存在时才创建。
154	
155	```text
156	features/<feature>/
157	  core/          # 纯 TS 规则、类型、算法；不得依赖 Vue/Electron/Pinia
158	  services/      # feature 内应用服务和用例入口
159	  state/         # feature 自己的状态归口，通常由 Pinia 或明确状态容器承载
160	  adapters/      # 调用 platform 或外部能力的适配层
161	  composables/   # 面向页面/组件的 Vue 组合层；不得拥有领域规则
162	  components/    # feature 内复用 UI；页面仍放 pages/
163	  fixtures/      # 领域测试样例、oracle 输入输出
164	```
165	
166	Rules:
167	
168	- `core/` 必须可单测，不依赖 UI、Electron 和全局 store。
169	- `state/` 只维护本 feature 的状态、read model、selector 和很薄的本域 action；不得直接修改其他 feature 的内部状态。
170	- `services/` 是业务用例入口，可以协调本 feature 内部对象；跨 feature 流程优先进入 `runtime/`。
171	- `adapters/` 可以调用 `platform/` facade，但不得把平台 API 继续向 `core/` 泄漏。
172	- `composables/` 只做 UI-facing 组合，例如表单状态、对话框状态、生命周期订阅、selector 组合和调用公开 service；不得承载协议解析、任务状态机、统计累加或跨域业务流程。
173	- `components/` 只服务本 feature 的局部 UI，不承担跨域流程编排。
174	
175	Top-level `rewrite/src/composables` 不作为重写默认归口。确需跨页面复用的 Vue 组合逻辑，必须先判断归属：属于某 feature 的放入该 feature，属于应用壳或全局 UI 行为的放入 `app/` 或 `widgets/` 对应边界；没有明确归属时不得新建万能 composable。
176	
177	### Fixture, oracle, and test placement
178	
179	测试材料跟随业务归口，不建立脱离 feature 的第二套事实来源。
180	
181	Rules:
182	
183	- feature 自己的输入样本、期望输出、失败样本、边界样本和旧系统 oracle 映射，优先放入 `features/<feature>/fixtures/` 或该 feature 对应测试目录。
184	- `core/` 测试只依赖明确输入输出，不依赖 Vue、Pinia、Electron、platform facade、真实文件系统或真实串口网络。
185	- 跨 feature 的 runtime 编排测试可以放在 `runtime/` 对应测试材料中，但测试断言必须通过 feature public API 和显式事件观察结果。
186	- 旧 JSON、历史文件、CSV、甲方材料和硬件采样可以作为 fixture 输入或 oracle 来源；进入新核心模型前必须经过 feature design 确认，不得直接污染核心类型。
187	- 每个 feature design 必须列出自动 fixture、手工 checklist、runtime / hardware validation 三类验证材料；没有运行证据时只能声明静态或 fixture 通过。
188	
189	### Feature public API
190	
191	feature public API 是跨 feature 访问边界，不是必须新增的接口层、文件模板或 schema。只有当外部 feature、page、widget 或 runtime 需要访问该 feature 时，才需要在对应 feature design 中说明允许入口。
192	
193	允许入口可以是已有 store/composable/service 中被明确认可的调用面，也可以是后续新增的 service、只读 selector、runtime 页面级入口或显式事件/command。Batch 0 不要求每个 feature 都创建 `public.ts`，不要求统一 event bus / command bus，也不要求没有外部消费者的 feature 预先定义 public API。
194	
195	Rules:
196	
197	- 外部 feature、page、widget 不得 import 其他 feature 的 `state/`、`adapters/`、内部 composable、内部 service 实现文件或私有 helper。
198	- feature 内部可以自由组织实现细节；同一 feature 内部不需要通过 public API 绕行。
199	- 如果存在外部消费者，feature design 或实现说明必须写清楚外部可用入口和禁止绕过的内部状态。
200	- 通过 public API 暴露的数据不得授予外部写入本 feature 内部 state 的能力。
201	- 有跨 feature 写入或流程推进时，必须说明 owner、调用方、输入输出边界、错误或拒绝语义和验证方式；没有跨 feature 消费时可以明确记录为不需要额外 public API。
202	- 事件/command 只在确实有异步广播、跨域解耦或多消费者收益时使用；使用时必须列出生产者、消费者、owner、触发时机和失败处理口径。
203	- 只读 selector 可以面向页面或其他 feature 暴露 read model / UI snapshot，但不得暴露可变引用，也不得让调用方回写主状态。
204	
205	### Pages, widgets, and feature components
206	
207	UI 代码按用户入口和复用范围归口，不按视觉相似度随意放置。
208	
209	Rules:
210	
211	- `pages/` 放路由页面、页面级布局和页面动作连接；页面可以调用 runtime 页面级 API 或 feature public API，但不拥有业务规则。
212	- `features/<feature>/components/` 放只服务该 feature 的组件，可以调用本 feature composable / selector / public service，不编排其他 feature 内部状态。
213	- `widgets/` 放跨页面复用、纯展示或全局 UI 行为组件；它只能消费明确传入的 props、只读 snapshot 或公开 selector，不直接订阅运行主状态。
214	- UI snapshot 是页面展示投影，不是事实源；页面可以筛选、分页、虚拟滚动和节流展示，但不得反向定义运行事实。
215	- 当一个组件同时需要多个 feature 的事实时，优先由 `runtime/` 或页面层组合只读输入，再传给组件；组件不得自己 import 多个 feature 内部 state 拼业务流程。
216	
217	## 8. Dependency Direction
218	
219	默认依赖方向：
220	
221	```text
222	pages/widgets
223	  -> feature composables or runtime page APIs
224	  -> features/<feature>/services or state selectors
225	  -> features/<feature>/core
226	  -> shared
227	
228	features/<feature>/adapters
229	  -> platform
230	```
231	
232	Allowed:
233	
234	- `pages` 调用 runtime 提供的页面级操作入口。
235	- `runtime` 调用多个 feature 的公开服务，完成应用级流程。
236	- feature 内部从 `services` 调用 `core`、`state`、`adapters`。
237	- composable 可以读取本 feature 的 store selector、管理 UI 生命周期并调用公开 service。
238	- `adapters` 调用 `platform` facade。
239	- `platform` 调用 preload 暴露的 typed API。
240	
241	Not allowed:
242	
243	- `core` 依赖 Vue、Pinia、Electron、`window.electron`、`ipcRenderer`、`fs`、`serialport`。
244	- feature A 直接 import feature B 的内部 `state` 并修改它。
245	- feature A 绕过 feature B 的 public API，直接 import B 的内部 service、adapter、composable 或私有 helper。
246	- 页面组件直接创建任务状态机、直接发串口/网络、直接读写本地文件。
247	- composable 变成隐藏 service，承载协议语义、任务推进、统计累加或跨 feature 写状态。
248	- store 变成 service locator，负责创建 service、保存 adapter 或访问 platform。
249	- `receive` 通过共享状态回读决定任务生命周期。
250	- `send` 为 SCOE 或 northbound 写硬编码特例。
251	- `northbound` 直接改写内部运行主状态或收发主链内部对象。
252	
253	## 9. Runtime Layer
254	
255	`runtime/` 不是新的大而全业务域。它只负责应用级装配和跨域编排。
256	
257	Recommended responsibilities:
258	
259	- 应用启动和销毁顺序。
260	- 确有跨 feature 或平台装配需要时，负责 manager / service 的创建、显式依赖注入和释放。
261	- 确有多消费者、异步解耦或跨域流程收益时，提供事件 broker 或 command dispatcher；它只表达路由、调用顺序和边界输入输出。
262	- 运行主状态归口层的装配。
263	- 边界例外清单和显式例外入口。
264	- 页面动作到 feature service 的路由。
265	
266	Must not:
267	
268	- 承载 receive 解析算法。
269	- 承载 SCOE 协议细节。
270	- 承载 report 字段生成规则。
271	- 承载协议判断、任务状态推进、统计含义、结果归因或 northbound 语义转换。
272	- 直接访问 Electron/Node 原生能力。
273	- 变成所有 feature 都依赖的全局杂物箱。
274	
275	### Service wiring and dependency injection
276	
277	重写默认采用轻量、按需的依赖装配，而不是全局 singleton 或重型 DI 框架。只有当生命周期、测试替换、平台资源装配或跨域编排有实际收益时，`runtime/` 才作为组合根创建 feature service、adapter 和必要上下文。
278	
279	Rules:
280	
281	- service 的依赖应通过构造函数、工厂函数或明确 context 传入，便于测试时替换 fake adapter、fake store 或 fake service。
282	- Pinia store 不是 service locator，不负责创建 service，不保存 Electron/platform 原生对象。
283	- 组件和页面不直接 import service 内部实现；单 feature 页面优先通过本 feature composable / store 调用，跨 feature 页面动作才考虑 runtime 页面级 API。
284	- 跨 feature 调用只通过明确认可的入口、runtime 编排、显式事件或边界输入输出发生。
285	- 不为“架构感”引入复杂容器；只有在生命周期、测试替换或跨域装配有实际收益时才增加抽象。
286	
287	### Runtime state and statistics read models
288	
289	重写后不得用一个全局大 store 承载所有运行事实、统计数据和页面展示态。全局编排可以存在，但事实源和写入权必须留在明确的 feature 边界内。
290	
291	Layering:
292	
293	- 静态资产：帧定义、字段定义、表达式和 frame-owned 展示元数据等低频可编辑对象，归 `features/frame`；运行中的展示偏好、表格/图表/星座图 projection 和 UI-safe snapshot 归 `features/display`。
294	- 运行事实：连接状态、接收结果、发送结果、任务状态、SCOE 状态等，由对应 feature 单点写入。
295	- 统计 read model：由对应 feature 基于显式事件或结果增量维护，按 `frameId`、`fieldId`、`targetId`、`taskId` 等稳定 key 索引。
296	- UI snapshot：面向页面的只读展示投影，可以节流、分页、虚拟滚动或按需组合，不反向写入主事实。
297	
298	Rules:
299	
300	- 帧列表和其他静态资产对象不得承载高频运行统计；接收命中数、最近值、错误计数、速率等统计不得写回 frame definition。
301	- 高频链路应以 batch / delta 推进：平台侧批量输入，领域 core 处理批次，统计 read model 增量更新，页面消费节流后的 snapshot。
302	- 页面和组件不得直接订阅底层高频事件，不参与统计累加，只调用公开入口和展示只读投影。
303	- 事件只能作为 feature 边界输出或 runtime 编排输入；事件类型和消费者必须明确，禁止把事件总线变成隐式跨 feature 写状态的通道。
304	- 每个统计项必须说明 owner、reader、reset 时机、生命周期、是否持久化以及验证方式。
305	- main 可以做平台侧缓冲、批处理、聚合、节流、队列和背压，但业务统计含义仍归口到可测试 TypeScript 层。
306	
307	## 10. Electron Boundary
308	
309	重写目标配置：
310	
311	```ts
312	nodeIntegration: false
313	contextIsolation: true
314	sandbox: false
315	```
316	
317	Directory implications:
318	
319	```text
320	rewrite/src/platform/          # renderer facade
321	rewrite/src-electron/preload/  # typed bridge
322	rewrite/src-electron/main/     # platform resources
323	```
324	
325	Rules:
326	
327	- `platform/` 是 renderer 业务代码访问桌面能力的唯一正式入口。
328	- preload 只暴露 typed API，不暴露裸 `invoke/send/on`。
329	- main 负责串口、网络 socket、文件系统、系统对话框、窗口控制、定时器等平台资源。
330	- main 不承载 receive/send/SCOE/task/report 的领域规则。
331	- main 可以承接与平台资源绑定且性能压力明显的高频数据缓冲、批处理、聚合、节流、队列和背压；业务运算、协议语义、任务状态推进、报告语义仍归口到可测试 TypeScript 层。
332	- 高频串口/网络数据不得逐包无节制穿透到页面和全局 store；需要批量、缓冲、聚合或节流策略。
333	
334	## 11. Boundary Exception Registry
335	
336	领域例外可以存在，但必须显式登记，不能隐式沉积在通用链路里。
337	
338	Exception record should include:
339	
340	- 例外名称。
341	- 所属 feature。
342	- 为什么不能表达为通用输入 / 输出。
343	- 正式入口。
344	- 正式输出。
345	- 谁消费它。
346	- 如何测试或手工验证。
347	
348	Known candidates:
349	
350	- SCOE 固定 TCP server 入站字节流 bypass receive 主链，直接从 connection transport event 到 SCOE adapter。
351	- SCOE 出站通过 task→send 路径（非直接调 send），targetId 由 ScoeCommand.frameInstances[0].targetId 声明。
352	- SCOE 领域完成条件翻译为 task wait-condition-step 的 WaitCondition，由 task/core 执行匹配。
353	- 高速存储命中后短路普通 receive/display/trigger 链。
354	- northbound 外部拒绝 / 不可执行 / 失败语义转换。
355	
356	## 12. Northbound Placement
357	
358	`northbound/` 是独立边界 feature，不是 task、status、report 的别名。
359	
360	Responsibilities:
361	
362	- 接收中心侧任务、控制、查询、保活、文件请求。
363	- 把外部请求转换为内部显式输入。
364	- 从内部 task/status/result/report 读取投影。
365	- 统一转换对外成功、失败、拒绝、不可执行、异常语义。
366	- 承接对外回执、结果上报、报告交付和文件回传。
367	
368	Must not:
369	
370	- 直接占有任务系统定义权。
371	- 直接把外部字段写成内部主状态字段。
372	- 直接把 history/CSV 文件当作 report 交付闭环。
373	- 把外部响应语义散落到 task/send/report/storage 各处。
374	
375	## 13. Result, Report, Delivery Split
376	
377	三者必须分开：
378	
379	| Layer | Owns | Does not own |
380	| --- | --- | --- |
381	| `result/` | 内部结果事实、用例结果、执行摘要 | 报告文件格式、对外交付动作 |
382	| `report/` | 报告对象和报告文件生成 | HTTP/FTP 上传、外部回执 |
383	| `northbound/` | 对外结果上报、报告交付、文件回传、错误语义转换 | 内部结果事实定义 |
384	
385	Reason:
386	
387	- 结果事实需要先在内部归口。
388	- 报告对象可以由内部结果和历史材料生成。
389	- 交付动作属于外部协议边界，成功或失败不能反向改写内部事实本身。
390	
391	## 14. Placement Examples
392	
393	| Need | Target |
394	| --- | --- |
395	| 解析接收字节并匹配帧 | `features/receive/core/` |

410	## 15. Architecture Entry Conditions For Later Batches
411	
412	每个后续 Batch 进入 `cs-feat-design` 前，必须先补齐本节检查项；缺失项必须在 design 中标为 blocking、deferred 或只读调查范围，不能在实现阶段临场扩大边界。
413	
414	Required before design:
415	
416	- 明确本批涉及哪些 feature 归口，以及哪些旧系统可观测行为属于 `preserve`、`candidate drop`、`deferred` 或 `not touched`。
417	- 若本批存在外部消费者或跨 feature 协作，明确允许入口；若没有，说明不需要额外 public API。
418	- 明确本批是否需要 `runtime/` 编排；若需要，说明 runtime 只负责装配、调用顺序、事件路由和生命周期，不承载领域规则；若不需要，不为形式感新增 runtime 层。
419	- 明确是否新增或调整 platform / preload / main API；若涉及 main 高频处理，说明哪些只是平台侧缓冲、批处理、聚合、节流、队列或背压；若触达现有 main 业务化路径，必须把它登记为迁移风险或边界例外。
420	- 明确静态资产、运行事实、统计 read model、UI snapshot 的 owner、reader、写入权、reset 时机、生命周期和是否持久化。
421	- 明确跨 feature 通信方式，禁止以内部 state import、全局 store 回读或隐式事件总线替代公开接口。
422	- 明确 pages、widgets、feature components 的放置和职责，不让 UI 承载任务机、协议语义、统计累加、文件/串口/网络访问。
423	- 明确自动 fixture、手工 checklist、runtime / hardware validation 的边界和未验证项。
424	- 涉及 SCOE、高速存储、真实串口、TCP/UDP、打包态 data path、HTTP/FTP 或 northbound 时，必须读取对应边界材料并登记例外或 runtime validation。

167	## 7. Data flow boundary
168	
169	Target flow:
170	
171	```text
172	native resource in main
173	  -> resource lifecycle / byte I/O
174	  -> main-side buffer / batch / queue / backpressure when justified
175	  -> minimal typed preload bridge
176	  -> rewrite/src/platform facade
177	  -> connection real transport adapter
178	  -> connection service/state/read model
179	  -> runtime route or explicit feature event
180	  -> receive / send / SCOE / status public boundary
181	  -> feature-owned read model
182	  -> throttled UI snapshot
183	```
184	
185	Rules:
186	
187	- Low-frequency lifecycle/error facts and high-frequency byte input must use separate design lanes.
188	- Byte input reaches receive as transport bytes/batches plus source material. connection does not parse it.
189	- Byte output reaches main as transport write material. send/SCOE own business request and business result.
190	- Status may read connection summary, but does not own connection truth.
191	- Runtime may route bytes and writes, but does not inspect protocol semantics.
192	- UI consumes snapshots and commands, not raw transport events.
193	
194	## 8. Event, buffer, and backpressure principles
195	
196	Main may retain only these platform-side or performance-side processing categories:
197	
198	- input byte batching for serial/TCP/UDP data.
199	- write queueing tied to a live native resource.
200	- subscription queueing and cleanup to prevent stale event delivery.
201	- bounded lifecycle/error event buffering for renderer synchronization.
202	- throttle or coalesce for high-frequency telemetry and UI-safe event delivery.
203	- overflow/backpressure signal when queue/batch policy is exceeded.
204	- resource cleanup drain on close, app shutdown or stale connection generation.
205	
206	Rules:
207	
208	- Queue depth、batch window、overflow/drop policy、sampling、UI refresh interval and target throughput are deferred to implementation/runtime evidence.
209	- Overflow must be observable as transport-level material, not silently converted into receive/send/task/result failure.
210	- Main may compress or batch events for transport pressure, but may not classify bytes as frame match、task trigger、SCOE success、report material or northbound delivery status.
211	- connection may maintain transport counters and recent event snapshots, but business statistics belong to receive/send/task/SCOE/status/result owners.
212	- Runtime exception records are required for high-frequency buffer/backpressure, high-speed storage short-circuit, packaged native module behavior and SCOE fixed route.
213	- Development-time fake adapter tests can simulate backpressure categories, but real steady-state behavior requires runtime/hardware validation after parameters are designed.
214	
215	## 9. Error and lifecycle boundary
216	
217	Principles:
218	
219	- Main emits raw resource outcomes and technical failures.
220	- Platform/preload carry typed technical results without exposing raw IPC or raw handles.
221	- Connection normalizes transport-level lifecycle and error facts.
222	- Consumers interpret those facts under their own feature designs.
223	
224	Lifecycle boundaries:
225	
226	- connect、disconnect、cleanup and app shutdown must be idempotent enough for duplicate user actions, stale events and already-closed resources.
227	- Automatic reconnect is not assumed. If introduced, retry policy、cancellation、UI visibility and runtime/hardware validation must be declared separately.
228	- TCP server client lifecycle is transport availability material, not a business session.
229	- UDP remote route is transport route material, not a customer device identity.
230	
231	Error boundaries:
232	
233	- A transport write failure is input material for send/SCOE; it does not define task lifecycle.
234	- A disconnect or timeout is a connection fact; it does not define result/report/northbound failure.
235	- Missing resource, port unavailable, socket error or cleanup failure can be normalized by connection, but this document does not freeze error code names.
236	- User-visible error text belongs to pages/status projection and must not leak raw platform internals.

135	
136	- `connection` 是 transport domain owner；`platform/main` 是平台资源 owner。
137	- main 可以产生 raw platform facts，但 canonical renderer-side connection facts、target availability 和 transport read model 归 `connection`。
138	- `connection` 的 target identity 只表示 transport target，不表示 northbound `deviceId`、业务设备、case、task 或 SCOE 领域对象。
139	- TCP server 的 client 连接可以是 transport-level availability material，但不能自动成为业务会话或 northbound 设备。
140	- UDP remote host 是 transport route material，不冻结字段 schema，也不等同 customer device。

142	### 3.2 Connection owns
143	
144	`connection` owns:
145	
146	- serial / TCP client / TCP server / UDP 的 connection profile 和 transport static config。
147	- 连接实例生命周期：idle、connecting、connected、disconnecting、disconnected、error 等状态概念的归口。本文不冻结枚举名称。
148	- target route 和 target availability 的 read model。
149	- transport-level event：connected、disconnected、error、data available、write accepted、write failed、resource unavailable 等能力类别。本文不冻结事件名称或 payload。
150	- transport-level error：端口不存在、打开失败、socket 关闭、timeout、写入失败、资源释放失败等归一类别。本文不冻结错误码。
151	- 平台事件到 connection read model 的归一规则。
152	- 面向 receive / send / task / SCOE / status / runtime 的公开能力类别。
153	- fake transport adapter 所需的测试替换边界。

155	### 3.3 Connection does not own
156	
157	`connection` must not own:
158	
159	- frame byte parsing、identifier matching、field extraction、expression input 或 receive result。
160	- send frame construction、send instance stats、send task lifecycle 或 task progress。
161	- SCOE protocol semantics、command parse、completion condition、tool record 或 fixed source / target 的业务含义。
162	- result truth、report object、history/CSV/report material、northbound delivery、HTTP/FTP transaction。
163	- northbound `deviceId`、subsystem identity、customer-facing task/control/status/result/error semantics。
164	- UI page state、dialog state、form dirty state、table pagination 或 chart refresh state。

183	## 5. Platform / preload / main / renderer boundary
184	
185	Renderer:
186	
187	- Uses only `rewrite/src/platform` facade for desktop capability access.
188	- Does not access `window.electron`, Electron, Node, `ipcRenderer`, `fs`, `path`, `net` or `serialport`.
189	- Does not subscribe directly to raw transport events from preload.
190	- Pages and widgets call connection public service, feature composables, or runtime page-level entry, not platform transport primitives.
191	
192	Platform facade:
193	
194	- Lives in renderer and hides preload details from features.
195	- Exposes capability categories only after corresponding foundation / feature design accepts the capability.
196	- Can expose transport primitives to connection adapters, not to arbitrary pages or features.
197	- Does not own connection config semantics, target identity, receive parsing, send result semantics, task lifecycle, SCOE protocol, result/report/northbound meaning.
198	
199	Preload:
200	
201	- Exposes a minimal typed bridge.
202	- Does not expose raw `invoke/send/on`, arbitrary channel subscription, or all-in-one `window.electron`.
203	- Does not expose `receive` business processing, high-speed storage business rules, history/report semantics, or task/SCOE commands as platform abilities.
204	- For transport, preload may bridge bounded lifecycle, byte I/O and bounded event delivery only after the connection design fixes the capability category.
205	
206	Main process:
207	
208	- Owns platform resources: serial port handles, TCP sockets, TCP server handles, UDP sockets, resource cleanup, app lifecycle, and necessary OS-level I/O.
209	- May retain platform-side buffering, batching, throttling, queueing, stream/file writing and backpressure when tied to platform resources or performance pressure.
210	- Must not define frame parsing, receive classification, task state transitions, SCOE completion, result attribution, report generation, northbound error conversion or business device identity.
211	- Any main-side exception must record why renderer / TypeScript core cannot reasonably own it, what main retains, where business semantics live, and how validation is done.
212	
213	Connection feature:
214	
215	- Is the renderer-side transport domain owner.
216	- Consumes platform transport primitives through adapters.
217	- Normalizes platform facts into transport facts.
218	- Publishes only public service, read-only selector, explicit event, or runtime-facing capabilities.
219	- Does not expose internal state to receive / send / task / SCOE.

221	## 6. Connection public API necessity
222	
223	`connection` needs a public API because receive, send, task, SCOE, status, pages and runtime all depend on transport availability. This public API is a boundary rule, not a required file shape and not a schema definition.
224	
225	Allowed capability categories:
226	
227	- Lifecycle command category: request connect, disconnect, reconnect attempt, resource cleanup, and lifecycle recovery. This does not define method names.
228	- Config query / update category: read or update transport static config through controlled entry; settings may provide defaults, but connection owns transport meaning.
229	- Target selector category: read target availability, target route, connection kind, and status snapshot as immutable read model.
230	- Byte input category: expose incoming transport byte batches or normalized transport input events to receive through runtime or explicit event.
231	- Byte output category: accept transport-level write requests from send / SCOE through public service or runtime; return transport-level acceptance or failure, not business send result.
232	- Error / lifecycle event category: publish transport-level lifecycle and error events for status, pages and runtime.
233	- Test adapter category: allow fake transport adapter injection in tests without exposing platform/main objects.
234	
235	Rules:
236	
237	- Public API must not leak mutable connection state, platform resource handles, raw Electron objects, raw socket instances or serialport instances.
238	- Public API must not freeze DTO, channel names, error code names or enum values in this document.
239	- Public API must not make receive / send / task / SCOE depend on connection store implementation.
240	- If a future feature has no external connection consumer, no extra public API is required for that feature.
241	- If a future flow requires cross-feature write or lifecycle progression, it must state owner, caller, input/output boundary, failure handling and validation level in its feature design.
242	
243	## 7. Runtime involvement
244	
245	`runtime/` is needed only as an application composition and cross-feature orchestration layer.
246	
247	Runtime may:
248	
249	- Create and release connection service, transport adapters and platform subscriptions at application startup and shutdown.
250	- Wire platform facade events into connection service.
251	- Route connection byte batches to receive without letting receive import connection internals.
252	- Route send / SCOE transport write requests to connection public service when the flow spans feature boundaries.
253	- Coordinate lifecycle cleanup when pages close, app exits, user switches profiles, or hardware disconnects.
254	- Register boundary exceptions such as high-frequency buffer / batch / backpressure, high-speed storage short-circuit, SCOE fixed source/target, packaged data path or optional HTTP/FTP transport.
255	- Combine read-only connection snapshot with status or page view model.
256	
257	Runtime must not:
258	
259	- Parse receive bytes.
260	- Build send frames.
261	- Own task lifecycle.
262	- Interpret SCOE protocol.
263	- Define result, report or northbound semantics.
264	- Become a global service locator or hidden event bus.
265	- Directly access Electron, Node, `serialport`, socket handles or file system.

267	## 8. High-frequency data principles
268	
269	Target high-frequency flow:
270	
271	```text
272	platform resource
273	  -> main-side buffer / batch / queue / backpressure when justified
274	  -> typed preload bridge
275	  -> platform facade
276	  -> connection adapter and connection read model
277	  -> runtime route or explicit event
278	  -> receive / send / storage / SCOE public boundary
279	  -> feature read model delta
280	  -> throttled UI snapshot
281	```
282	
283	Rules:
284	
285	- Main may batch, buffer, throttle, queue or apply backpressure for platform-resource reasons.
286	- Main may not classify bytes as receive result, task result, SCOE command success, report material, or northbound delivery status.
287	- Connection may normalize transport-level data availability and transport stats; it does not parse frames or define business result.
288	- Receive consumes byte batches, not raw unbounded per-packet renderer events.
289	- UI consumes throttled snapshots and read-only selectors; UI does not subscribe to raw serial/network events.
290	- Backpressure and overflow policy must be declared in future connection / receive design; this document does not set queue depth, window size, sampling rate or timeout thresholds.
291	- High-speed storage short-circuit is a boundary exception candidate. It must state whether data bypasses normal receive/display/trigger, which feature owns the decision, and what runtime/hardware evidence is required.
292	- Transport-level counters must not become global business statistics. Business stats belong to receive/send/task/SCOE/result/status owners as appropriate.

294	## 9. Disconnect, reconnect, errors, and lifecycle events
295	
296	Principles:
297	
298	- Disconnect and error facts are transport-level facts owned by connection.
299	- Automatic reconnect is not assumed. If added, it must be explicit connection behavior with retry policy, cancellation, UI visibility and validation plan.
300	- A failed send should not itself decide task lifecycle. send may report transport failure; task decides task lifecycle through task-owned rules.
301	- A transport error should not define result/report/northbound failure semantics. result/report/northbound may consume transport facts through public projections.
302	- Close, cleanup and app shutdown must be idempotent and observable enough for runtime/manual validation.
303	- Connection lifecycle events should be low-frequency read model updates; high-frequency data flow should use batch/delta channels separately.

311	## 10. Cross-feature communication
312	
313	Allowed patterns:
314	
315	- Public service: send, SCOE, task or pages call connection-owned command/query capabilities through explicit public entry.
316	- Runtime orchestration: runtime coordinates connection + receive or connection + send/SCOE when a flow crosses feature boundaries.
317	- Explicit event: connection emits declared transport-level events for receive/status/runtime consumers when async decoupling or batching is needed.
318	- Read-only selector: status/pages/widgets consume immutable snapshots or view models.
319	
320	Prohibited patterns:
321	
322	- receive / send / task / SCOE import connection internal `state`.
323	- receive / send / task / SCOE import connection internal adapter or private service implementation.
324	- connection imports receive/send/task/SCOE internal state to push business side effects.
325	- connection writes task status, send stats, receive parse result, SCOE command record, result truth, report file state or northbound transaction.
326	- pages/widgets subscribe to raw platform transport event streams.
327	- status reads raw connection internals instead of public snapshot.
328	
329	Feature consumption boundaries:
330	
331	| Consumer | May consume from connection | Must not do |
332	| --- | --- | --- |
333	| `receive` | incoming byte batches, source snapshot, lifecycle/error events relevant to input availability | import connection state, decide target availability, own transport lifecycle |
334	| `send` | target availability, transport write capability, transport-level write failure | own connection lifecycle, hardcode SCOE/northbound targets, define task result |
335	| `task` | target availability snapshot, explicit send/transport failure material via send result | import connection state, decide low-level retry by reading raw transport |
336	| `scoe` | declared fixed source/target availability through runtime exception, transport write capability | hardcode generic send internals, make connection own SCOE semantics |
337	| `status` | read-only connection summary and lifecycle events | own transport truth or raw platform resources |
338	| `northbound` | only internal projection if later needed through status/task/result/report; no direct transport target = deviceId mapping | treat serial/network target as customer device identity |
