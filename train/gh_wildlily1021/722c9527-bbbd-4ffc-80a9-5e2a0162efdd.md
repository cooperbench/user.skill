## D1. Widget API 适配面

### 🔴 D1-1: StatusBadge 硬编码 ConnectionLifecycleStatus，无法复用

**问题:** StatusBadge 的 prop 类型是 `ConnectionLifecycleStatus`，状态映射表写死在组件内。

**影响推演:** 任务页需要 `TaskStatus`、发送页需要 `SendStatus`、指令接入页需要 `ConfigStatus`。每个状态类型要创建独立组件或改写 StatusBadge，到第 4 页时至少有 3 个功能重复的 badge 组件。

**证据:**
- `widgets/StatusBadge.vue:2-6` — prop 只接受 `ConnectionLifecycleStatus`
- `widgets/StatusBadge.vue:8-18` — STATUS_MAP 硬编码 6 种状态

**修复方向:** 改为泛型组件，接受 `statusMap: Record<string, { label: string; color: string }>` + `currentStatus: string`，或定义 `StatusDefinition` 接口由调用方传入。

### 🟡 D1-2: DataTable 插槽透传无类型约束

**问题:** DataTable 通过 `v-for="(_, slot) in $slots"` 透传所有插槽，但调用方无法获得列名和行类型的 TypeScript 提示。

**证据:** `widgets/DataTable.vue:62-64` — 无类型约束的插槽透传

**影响推演:** 局部。后续每个页面的 `#body-cell-xxx` 模板确实要手写，但这不是系统性问题而是 QTable wrapper 的固有限制。Vue 3 的插槽类型推导本身就不支持动态列名的自动补全。

### 🟡 D1-3: TableToolbar 的 filters/actions slot 无布局约束

**问题:** `#filters` 和 `#actions` 是裸 slot，没有统一间距或按钮样式约束。

**证据:**
- `widgets/TableToolbar.vue:35-39` — slot 无包裹
- `pages/FrameListPage.vue:190-213` — 直接放 3 个 `q-btn`，间距依赖父容器的 `gap-3`

**影响推演:** 局部。FrameListPage 的按钮已经用了统一的 `outline dense no-caps` 模式，后续页面开发者可以照搬。但如果要全局调整过滤按钮样式，需要逐页修改。

### 🟢 D1-4: DataTable containerHeight 默认值硬编码 calc 表达式

**证据:** `widgets/DataTable.vue:21` — 默认 `calc(100vh - 200px)`

## D2. CSS Token 与 UnoCSS 完整性

### 🔴 D2-1: 大量 inline style 消费 token 但未提取为语义 class

**问题:** 颜色 token（`--rw-color-text-primary/muted/secondary`、`--rw-color-border-subtle` 等）通过 `style="color: var(--rw-color-text-muted)"` 消费，未提取为 CSS class。

**统计（实际 grep 结果）:**
- `color: var(--rw-color-text-muted)` — 9 处（DataTable:1, FrameDetailPanel:8）
- `color: var(--rw-color-text-primary)` — 8 处（FrameListPage:1, ImportFrameDialog:1, FrameDetailPanel:6）
- `color: var(--rw-color-text-secondary)` — 3 处（ImportFrameDialog:1, FrameDetailPanel:2）
- `color: var(--rw-color-status-danger)` — 2 处（ImportFrameDialog:2）
- `border-bottom: var(--rw-border-width-subtle) solid var(--rw-color-border-subtle)` — 2 处
- `background: var(--rw-color-surface-base)` — 1 处

**影响推演:** 到第 4 个页面时，这些 inline style 会扩散到 50-60 处。如果要调整"标签文字颜色"或"分隔线样式"的视觉映射，需要逐文件搜索替换，极易遗漏。FrameDetailPanel 一个组件就有 20+ 处 inline style。

**证据:**
- `features/frame/components/FrameDetailPanel.vue:19-77` — 几乎每个元素都用 inline style
- `features/frame/components/ImportFrameDialog.vue:62,81,85,91,92`

**修复方向:** 提取语义 class 到 `_utilities.scss`：
- `.rw-text-label` → `color: var(--rw-color-text-muted)` （字段标签）
- `.rw-text-value` → `color: var(--rw-color-text-primary)` （字段值）
- `.rw-text-desc` → `color: var(--rw-color-text-secondary)` （描述文字）
- `.rw-border-divider` → `border-bottom: var(--rw-border-width-subtle) solid var(--rw-color-border-subtle)`
- `.rw-panel-surface` → `background: var(--rw-color-surface-base)`

### 🟡 D2-2: SCSS spacing token 与 UnoCSS spacing scale 不完全对齐

## D3. Feature Service 消费边界

### 🟡 D3-1: 页面通过 runtime.features 直接持有可变 service 实例

**问题:** 页面直接 `runtime.features.connectionService` 获取完整 service（含读写），无读写分离。

**证据:**
- `pages/ConnectionPage.vue:11` — `const service = runtime.features.connectionService;`
- `pages/FrameListPage.vue:22` — `const frameService = runtime.features.frameService;`

**影响推演:** 局部而非系统性。当前页面调用 service 的公开方法（connect、disconnect、listFrames、upsertFrame），这些就是 intended public API。没有跨 feature 直接访问内部 state。真正的风险是：如果页面需要"只读"消费但误调了写方法，TypeScript 不会阻止。但实际代码中页面确实需要写操作（连接/断开/删除帧），所以读写分离在这个阶段不是瓶颈。

**备注:** `RewriteWiredFeatures` 同时暴露了 `frameReader` 和 `frameService`，其中 `frameService` 继承了 `frameReader`。ConnectionPage 和 FrameListPage 都选择了 `*Service`，这是合理的——它们确实需要写操作。

### 🟡 D3-2: 手动 refreshKey 模式

**问题:** FrameListPage 用 `refreshKey` ref 触发 computed 重算，因为 service state 非响应式。

**证据:** `pages/FrameListPage.vue:25-28` — `refreshKey` + `void refreshKey.value`

**影响推演:** 局部。这个模式语义清晰且实际可用。但如果 6 个页面都用不同方式刷新（有的用 refreshKey、有的用 rAF、有的用事件），刷新模式会混乱。

### 🟢 D3-3: selector 返回值基本是 readonly

已验证 `FrameStateSnapshot` 的 `frames` 是 `readonly ReadonlyFrameAsset[]`，`cloneFrameAsset` 返回深拷贝。

## D4. 状态管理模式

### 🔴 D4-1: 页面级 composable 体系完全缺失，核心模式会逐页复制

**问题:** 三个跨页面重复的模式没有抽象为 composable：

1. **operatingIds（操作锁）**: ConnectionPage 手动管理 `Set<string>` + add/remove + finally 清理（`ConnectionPage.vue:14,50-68,73-88`），FrameListPage 不需要因为操作是同步的，但后续任务页（启动/停止/暂停任务）一定需要。

2. **disposed flag + rAF 轮询**: ConnectionPage 手写 rAF + 节流 + disposed 检查（`ConnectionPage.vue:16,31-42`），FrameListPage 不需要轮询但后续发送页（实时发送状态）一定需要。

3. **async 错误处理 + $q.notify**: 每个 async 操作都重复 try-catch/try-finally + `$q.notify({ type: 'negative', message: ... })` 模式。

**影响推演:** 到第 4 个页面时，至少 3 个页面各自实现了 operatingIds、disposed/rAF、async error 的变体。修改任何一个模式（比如给操作锁加超时、给错误处理加日志上报）都要改 N 个文件。

**证据:**
- `pages/ConnectionPage.vue:14` — `operatingIds`
- `pages/ConnectionPage.vue:16` — `disposed`
- `pages/ConnectionPage.vue:31-42` — rAF 手写
- `pages/ConnectionPage.vue:48-68` — try-finally + operatingIds 管理
- `pages/ConnectionPage.vue:71-89` — 同样的 try-finally + operatingIds 管理重复第二次

**修复方向:** 创建三个 composable：
- `useAsyncAction()` — 返回 `{ execute(id, fn), isOperating(id) }`，内置 operatingIds 管理和 finally 清理
- `usePolling(fn, intervalMs)` — 返回 `{ start(), stop() }`，内置 disposed flag + rAF 节流 + onUnmounted 清理
- `useNotify()` — 封装 `$q.notify` 的成功/失败/警告模式

### 🟡 D4-2: 状态声明无分层约定

**问题:** ConnectionPage 把业务数据（summaries）、UI 操作状态（operatingIds）、UI 开关（showNewDialog）、生命周期（disposed）平铺在一起。FrameListPage 也类似。

**证据:**
- `pages/ConnectionPage.vue:13-16` — 四种状态类型无分组
- `pages/FrameListPage.vue:25-38` — refreshKey/search/filter/selection/dialog 混在一起

**影响推演:** 局部。当前 2 个页面各约 15 个 ref/computed，还 manageable。到第 6 个页面时如果状态增加到 25+，需要分组注释或 reactive 对象来保持可读性。

## D7. 错误处理一致性

### 🟡 D7-1: routingTick 错误被静默吞掉

**问题:** `runtime/index.ts:172` — `routingTick(wiredFeatures).catch(() => {})` 完全静默。

**证据:** `runtime/index.ts:172`

**影响推演:** 局部（只有一处）。但 routingTick 涉及 connection/receive/task 多个 feature，如果失败，整个 tick 链静默中断，用户看到的是"数据不更新"但无任何错误提示。建议至少 `console.error` 或 emit 到 error handler。

### 🟡 D7-2: async 操作的错误处理模式不统一

**问题:** 两种模式并存：
1. ConnectionPage: try-finally + 检查 `result.ok` + `$q.notify`（`ConnectionPage.vue:48-68`）
2. FrameListPage: 直接检查 `result.ok` + `$q.notify`，无 try-catch（`FrameListPage.vue:94-99`）

**证据:**
- `pages/ConnectionPage.vue:51-62` — try-finally + result.ok 分支
- `pages/FrameListPage.vue:94-99` — 只检查 result.ok，无 try-catch

**影响推演:** 局部。FrameListPage 的操作是同步的（service 方法返回 Result 而非 throw），所以不需要 try-catch。ConnectionPage 的 connect/disconnect 是 async，所以需要 try-finally。两种场景不同。但如果后续有 async 操作忘记 try-catch（比如 onExport），会导致 unhandled promise rejection。

### 🟢 D7-3: 删除操作都有二次确认

import { ref } from 'vue';

export function useStableKeys(prefix = 'key') {
  let uid = 0;

# Rewrite 前端速查卡

> 写新页面/新组件前先看。详细规则见 rewrite-frontend-conventions.md。

## 必用基础设施

| 用途 | import | 备注 |
|------|--------|------|
| 异步操作 | `useAsyncAction()` | 替代手写 operatingIds |
| 轮询刷新 | `usePolling(fn, ms)` | 替代手写 rAF/disposed |
| 通知 | `useNotify()` | 替代 $q.notify 散落 |
| v-for stable key | `useStableKeys(prefix)` | 列表编辑器必用 |

## 语义 class（不用 inline style 消费 token）

文本：`rw-text-label` / `rw-text-value` / `rw-text-desc` / `rw-text-error` / `rw-text-warn`
边框：`rw-divider-b` / `rw-divider-t` / `rw-divider-l`
面板：`rw-panel-base`
弹窗：`rw-dialog-sm` / `-md` / `-lg` / `-xl`
滚动区：`rw-dialog-scroll-body`

## 绝对禁止

- `catch {}` / `catch () {}` 空错误吞没
- `style="color: var(--rw-color-...)"` inline token → 用语义 class
- `v-for ... :key="i"` index key → 用稳定 ID
- 组件超 300 行不拆
- 选项数组/标签映射写在 setup 内 → 放模块级或常量文件
- 同一逻辑出现 2+ 处不提取（O3）

## 状态声明顺序（O1）

Service 引用 → 业务数据 → 查询/筛选 → UI 状态 → 派生数据 → 操作

## 新页面检查清单

1. composable 用了没？（useAsyncAction / usePolling / useNotify）
2. 标签/选项提取了没？（模块级或常量文件）
3. 语义 class 用了没？（grep `style=".*var(--rw-`)
4. v-for key 稳定吗？
5. catch 都有处理吗？
6. 组件超 300 行吗？该拆吗？
```
