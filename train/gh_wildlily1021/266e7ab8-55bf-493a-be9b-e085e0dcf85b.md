**风险点:** serialport 12.x 的 `@serialport/bindings-cpp` 是 C++ addon，必须针对 Electron 35 的 V8 版本重新编译。这是整个桥接方案的核心技术风险。

**状态: 待处理**

旧项目用 `electron-rebuild@^3.2.9`（已废弃），新项目应使用 `@electron/rebuild`（官方维护）。旧项目 rebuild 命令为 `electron-rebuild -f -w serialport`。

### G4: asarUnpack / package 配置

**状态: 待处理 — 当前配置不完整**

| 项目 | 当前值 | 需要 |
|---|---|---|
| `asar` | `true` | 保持 `true` |

旧项目直接 `asar: false`（packager 层面），这是最简单的做法但不推荐（全部不压缩）。正确的做法是 `asar: true` + `asarUnpack` 排除 native module。

**需要的配置:**

```ts
  '**/node_modules/serialport/**',
  '**/node_modules/@serialport/**',
],
```

### G5: typed preload bridge shape

**状态: 通过 — 形状已确认**

当前 preload bridge 最小形状：
```ts
const rewriteBridge: RewritePlatformBridge = Object.freeze({
  getBridgeInfo: () => createRewriteBridgeInfo('0.0.0'),
});
```

Bridge implementation design §3 定义了 transport 需要 的 category:
- 发现 (枚举串口)
- 生命周期命令 (连接/断开/清理)
- 字节 I/O (写请求)
- 事件排空 (拉取 main 缓冲事件)
- 背压查询

`RewritePlatformCapability` 当前为 `never`，需要扩展为 transport capability 联合类型。`ConnectionTransportAdapter` port 接口已经覆盖 connect/disconnect/write/cleanup/drainEvents，与 design §4 一致。

**结论: 结构可以承载，无需改 port 接口。**

### G6: main resource handle lifecycle

**状态: 通过 — 需要确认的已列出**

当前 main 是裸 BrowserWindow，无 IPC handler。Design §7 已定义完整的 lifecycle mapping:
- 打开成功 → 已连接 event
- Native close → 已断开 event
- Native error → error event
- App shutdown → 清理 drains all resources

关键确认项:
1. **打开/关闭幂等性** — 对已关闭资源断开应返回 accepted，对不存在的也返回 accepted
2. **错误映射** — resource-unavailable, open-failed, connect-failed, timeout 等 → 已在 design §7.2 列出
3. **App 退出清理** — 必须 驱除 所有 native handles，目前 main 无 `will-quit` handler

### G7: queue/batch/backpressure 参数

**状态: 通过 — 建议先用保守默认值，不跑基准测试**

Design §6 只定义了原则，具体参数需要 基准测试。评估：

| 参数 | 保守默认值 | 理由 |
|---|---|---|
| maxBatchBytes | 4096 | 旧系统 serial 115200 baud ≈ 11520 bytes/s，4KB 约 350ms 批次 |
| maxBatchWindowMs | 50 | 低频数据不超过 50ms 延迟，高频自动触发 字节大小限制 |
| maxQueueDepth | 100 | 约 400KB 内存占用上限（per-connection） |

**建议:** 先用保守默认值实现，后续有 硬件环境 再跑 基准测试 调参。不需要预先跑 基准测试。
