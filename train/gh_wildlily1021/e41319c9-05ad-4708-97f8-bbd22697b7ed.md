## 逐点决策建议

### 1. 命名

Feature 目录用 `command-ingress/`，中文仍叫"指令接入"（planning doc 已固化）。理由：ingress 语义精确（入站方向），和 northbound（出站）形成对称，不和其他 feature 撞名。

### 2. 入站数据路由

推荐**三层分发**：

```
TransportEvent 到达
  ↓
① Runtime routingTick（已规划）
   command-ingress 注册为 ingress listener，声明匹配条件
   匹配的事件路由到 command-ingress feature
  ↓
② Command-inggress feature 内：ProtocolAdapter 匹配
   每个 adapter 声明 canHandle(event) → bool
   feature 找到声称"我处理这个"的 adapter
  ↓
③ Adapter 内：命令分发
   adapter 解析协议 → 得到 ParsedCommand
   按 command type 分发到 handler
```

为什么这样分层：

| 层 | 职责 | 扩展点 |
|---|---|---|
| Runtime routingTick | 区分 receive / send / ingress 三路 | 新的入站来源（未来 HTTPS） |
| ProtocolAdapter | 协议识别 + 字节→领域命令 | 新协议（新甲方） |
| Handler 分发 | 领域命令→执行 | 新命令类型 |

每一层只做一件事，新协议只需要加 adapter，不改 routingTick 不改 handler。

### 3. 非 Task 路由

**不建议建 executor 抽象**。看旧 SCOE 6 种命令的实际分布：

| 命令 | 本质 | 走什么 |
|---|---|---|
| SEND_FRAME | 发帧 + 等条件 | Task |
| READ_FILE_AND_SEND | 读文件 + 发帧 | Task |
| LOAD_SATELLITE_ID | 设置内部状态 | 直接 handler |
| UNLOAD_SATELLITE_ID | 清除内部状态 | 直接 handler |
| HEALTH_CHECK | 返回快照 | 直接 handler |
| LINK_CHECK | 返回快照 | 直接 handler |

4/6 是简单操作，不需要 executor 框架。推荐用**最薄的 handler map**：

```typescript
type CommandHandler = (
  command: ParsedCommand,
  ctx: CommandContext
) => Promise<CommandResult>;

// adapter 内部：一个 Map 搞定
const handlers: Map<CommandType, CommandHandler> = new Map([...]);
```

`CommandContext` 提供可读 snapshot（连接状态、统计）和可写操作（taskService 引用）。Handler 不需要知道是"Task 执行"还是"直接操作"，它就是一个函数。Task handler 内部调 `taskService.createTask + startTask`，其他 handler 直接读写状态或返回快照。

不需要 `CommandExecutor` 接口、不需要抽象类、不需要执行器模式。一个函数签名够了。

### 4. Task step 扩展

deferred，等你另一个对话的 brainstorm 文档。

### 5. 新甲方 HTTPS

先做 stub adapter（实现 `canHandle` 返回 false，占位接口），不实现任何协议细节。

### 6. 协议适配器 vs 分发路由的分界

确认：adapter 负责"识别+解析"，feature 负责"匹配 adapter + 分发 handler + 管理领域状态"。adapter 不知道 handler 的存在，handler 不知道 adapter 的存在。

## 完整结论

### 一、要做什么

**command-ingress feature 的核心行为**：

1. **注册入站路由**：向 runtime 声明自己处理哪类 transport event
2. **协议适配**：每个外部协议（SCOE TCP、未来 HTTPS）实现 `CommandProtocolAdapter`，负责"这批字节我能处理吗？→ 解析成领域命令"
3. **命令分发**：解析后的命令按类型路由到 handler。大多数 handler 创建 Task，少数直接操作状态或返回快照
4. **Task 生命周期消费**：订阅 task lifecycle event，更新领域统计（接收数/成功数/错误数/最后命令码）
5. **回应机制**：Task 完成（或直接操作完成）后，通过 connection `write()` 发送协议对应的回应帧
6. **领域状态**：维护 `CommandIngressState`（统计、加载的卫星 ID、当前活跃命令等），通过 selector 暴露只读快照

**命令生命周期**：

```
外部系统 → TCP/UDP 连接
  → Connection TransportEvent
  → Runtime routingTick → command-ingress
  → ProtocolAdapter.matchTransport → ProtocolAdapter.parse
  → ParsedCommand
  → Handler 分发
    ├→ Task handler: taskService.createTask + startTask + onSettled
    ├→ 查询 handler: 返回 snapshot
    └→ 状态 handler: 修改领域状态
  → 回应构造（协议适配器负责格式）
  → Connection.write() 发出
```

### 二、不做什么

| 不做什么 | 为什么 |
|---|---|
| 不建独立帧列表 | 帧定义全局唯一，SCOE 帧通过 frame feature 查询 |
| 不建独立条件系统 | 条件匹配归 shared/，Task 的 wait-condition-step 已用 ComparisonOperator |
| 不在通用 receive 流程里硬编码 SCOE 识别 | 入站走独立路由，bypass receive |
| 不把业务逻辑塞进 main process | 协议解析、命令翻译、条件判断全在 renderer TypeScript 层 |
| 不提前冻结新甲方 HTTPS 契约 | schema 未确认，只留 adapter stub |
| 不建 CommandExecutor 抽象框架 | handler map 函数签名够了 |
| 不让 adapter 直接依赖 connection service | 入站由 runtime 路由，出站由 Task → send → connection |

### 三、与 task-real 的复用边界

| 由 task 提供 | 由 command-ingress 提供 |
|---|---|
| TaskDefinition 类型 | 命令→TaskDefinition 的翻译逻辑 |
| TaskService（create/start/stop/onSettled） | triggerSource = `'scoe-command'` |
| Step 执行（send/wait-condition/delay） | 每个 SCOE 命令对应的 step 序列定义 |
| Lifecycle event 发布 | Lifecycle event 消费→更新领域统计 |
| WaitCondition + ComparisonOperator | 完成条件的配置值（阈值、超时、onTimeout 策略） |
| ErrorPolicy 处理 | 哪些 SCOE 命令用什么 errorPolicyOverride |
| Progress 统计 | SCOE 领域统计（和 task progress 分开） |

简单说：**task 提供执行引擎和 step 原语，command-ingress 提供翻译配置和领域状态**。

### 四、是否走 cs-roadmap

**建议走 cs-roadmap，拆 3 个子 feature**：

| Item | 内容 | 依赖 |
|---|---|---|
| 1. command-ingress-core | ProtocolAdapter 接口、Handler 分发、领域状态、selector、runtime 注册 | task-real 完成 |
| 2. command-ingress-scoe | SCOE TCP 协议适配器、6 种命令的 parse+handler、回应帧构造 | core + connection-network |
| 3. command-ingress-northbound-stub | 新甲方 HTTPS adapter stub，接口占位 | core |

理由：
- Item 1 和 2 有明确的交付边界，可以独立验收
- Item 3 是占位，工作量极小但需要接口对齐
- 不拆的话单 feature 跨协议适配 + 领域逻辑 + 旧行为迁移，scope 不好控

## 验证结果：4 个假设被推翻

### 修正 1：入站数据不是订阅，是 tick 拉取

**假设**：command-ingress 可订阅 connection transport events
**实际**：ConnectionService 只有拉取 API（`drainAdapterEvents()`、`listTransportEvents()`），没有订阅机制。runtime 用 `routingTick()` 以 100ms 间隔驱动所有数据分发。

**当前 routingTick 硬编码了 connection → receive 流**，没有扩展点。command-ingress 必须在 routingTick 中增加分支，不能独立获取 transport events。

关键代码：`routing-tick.ts:27-54` — 先 drain events，再硬编码转换给 receiveService。

### 修正 2：回应机制比假设简单得多

**假设**：回应需要协议适配器动态构造
**实际**：
- 只有 UDP 发成功帧，**没有 TCP 回复，没有失败帧**
- 成功帧是预配置的固定帧模板（`successFrameId`），从全局帧库查找、实例化、发送
- 超时 = 只记录错误状态，不发送任何回应
- 发送目标固定：`network:scoe-udp:scoe-udp-remote`

这意味着回应逻辑不需要 adapter 理解协议——它只需要知道 successFrameId 和 target。

### 修正 3：参数 resolve 是预配置选项匹配，不是动态计算

**假设**：参数可能需要表达式引擎动态 resolve
**实际**：
- 参数值从指令帧字节按 offset/length 提取 → 转十六进制 → 匹配预配置的 `options[].receiveCode` → 取 `option.value`
- 完成条件阈值也是预配置的，通过参数选项索引匹配
- **所有值在 adapter 翻译时都能 resolve 为 literal**

这确认了 task-real brainstorm 决策 4（no correlate）。

### 修正 4：READ_FILE_AND_SEND 实际可以映射到 TaskDefinition

验证 agent 说"不可翻译"，但我认为**可以翻译**：

旧系统做的事：读文件 → 按行 split → 构造 FieldVariation → 创建定时任务（interval + repeatCount = 文件行数）

新系统映射：
```typescript
TaskDefinition {
  schedule: { kind: 'timer', intervalMs: command.sendInterval },
  steps: [
    { kind: 'send', config: { frameId, targetId, fieldValues } },
    { kind: 'wait-condition', config: { conditions, timeoutMs } }
  ],
  fieldVariations: [{ fieldId, values: fileLines }],
  stopCondition: { maxIterations: maxLineCount }
}
```

文件读取在 adapter 层完成（通过 platform facade），结果变成 `FieldVariation`。handler 调用 `taskService.createTask + startTask`。**handler map 函数签名完全够用**——handler 通过 `ctx` 访问 platform facade 读文件。

| 文档类型 | 例子 | 什么时候读 | 读的目的 |
|---|---|---|---|

### 子 agent 怎么派

从这两轮 brainstorm（task-real 和 command-ingress）总结出派 agent 的模式：

**初始探索**（4 个并行）：规划 + 架构 + 已有设计/代码 + 旧系统。目的是快速建立全景。
