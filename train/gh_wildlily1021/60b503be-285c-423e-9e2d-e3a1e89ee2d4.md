### 问题 1: 历史记录数据流描述错误

Design 写的是 "TaskService 完成任务时自动归入历史 selector，不需要 moveToHistory"。

实际代码（`task/state/task-state.ts:176`）：
```typescript
// removeTask 才归入历史
instances.delete(instanceId);
history = [...history, cloneInstanceState(existing)].slice(-MAX_HISTORY);
```

完成的任务仍留在 `instances` 中，只有显式 `removeTask` 才入 history。

**如果按 design 实施**：composable 会发现 "完成的任务还在 active 列表里"，要么在 composable 里手动 filter lifecycle（绕过 state 的 history 机制），要么偷偷调 removeTask（副作用不透明）。两者都是补丁。

**修正方案**：composable 的活动/历史 Tab 应该基于 state 自身的机制：
- 活动任务: `selectTaskInstances` — 包含所有未 remove 的实例（含已完成的）
- 历史记录: `selectTaskHistory` — removeTask 后的实例
- 用户在活动 Tab 看到 completed/failed 任务时，有 [移至历史] 按钮 → 调 removeTask

### 问题 2: evaluateFieldExpressions 类型链路断裂

Design 说 FieldEditWidget 接收 `FrameFieldDefinition[]`，预览 composable 按字段粒度调 `evaluateFieldExpressions`。

实际代码签名：
```typescript
// frame-resolver.ts:98
evaluateFieldExpressions(
  field: SendFieldEncodingDef,  // 不是 FrameFieldDefinition
  mergedVariables: VariableMap,
)
```

中间需要转换链：`FrameFieldDefinition` → `frameToBuildInput` → `SendFieldEncodingDef` → `evaluateFieldExpressions`。

Design 没提这个转换。`FrameFieldDefinition` 是 frame feature 的类型，`SendFieldEncodingDef` 是 send/core 的内部类型。FieldEditWidget 的 props 声明为接收 `FrameFieldDefinition[]`，但实际调 evaluateFieldExpressions 需要 `SendFieldEncodingDef`。

**如果按 design 实施**：composable 里会出现一段"先把 frame 类型转成 send 内部编码类型再调函数"的代码，但读 design 的人完全不知道为什么需要这个转换。

**修正方案**：Design 显式描述这个链路。useFramePreview composable 的职责应包括：
1. 从 frame feature 获取 `ReadonlyFrameAsset`
2. 调 `frameToBuildInput(frame)` 得到 `SendFieldEncodingDef[]`
3. 对每个字段调 `evaluateFieldExpressions(field, mergedVars)`

FieldEditWidget 的 props 保持 `FrameFieldDefinition[]`（面向 frame 的公共类型），composable 负责内部转换。

### 问题 3: Platform facade 无文件系统能力

Design 反复说"持久化走 platform facade"。但 platform 当前只有 `TransportFacade`（串口/TCP/UDP），无任何文件读写能力。

**如果按 design 实施**：composable 调 `platform.readFile(...)` 直接报错，需要临时在 platform 加文件 facade，但没有 design 指导接口长什么样。
