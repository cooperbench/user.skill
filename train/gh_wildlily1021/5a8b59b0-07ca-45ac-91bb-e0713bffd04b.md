329	## 6. Anti-Patterns
330	
331	以下模式在重写代码中默认判为质量问题：
332	
333	- 页面组件里直接写串口、网络、文件、SCOE 协议或任务状态机。
334	- store 互相 import、互相修改内部状态。
335	- `receive` 逻辑直接调用 `send/task/storage/status` 的内部状态。
336	- `send` 逻辑硬编码 SCOE target 或 northbound 语义。
337	- `scoe` 逻辑散落在 receive/send/task 多处。
338	- main 进程写领域业务规则。
339	- preload 暴露裸 IPC 或大而全 `window.electron` 能力包。
340	- 高频数据逐包穿过 main -> renderer -> store -> 多 store 副作用链。
341	- 高频统计写回帧列表或静态配置对象，导致页面全量刷新。
342	- 页面组件直接订阅底层高频事件并累加统计。
343	- 用一个可写全局 store 同时承载静态资产、运行事实、统计和 UI 展示态。
344	- store 变成跨域 service locator 或平台能力入口。
345	- composable 变成隐藏业务 service。
346	- 组件直接 import service 内部实现并绕过公开入口。
347	- 为旧 JSON 兼容把新模型设计扭歪。
348	- 为了架构感堆 manager/event/command，但没有明确生命周期、跨域流程或验证收益。

31	## Batch 0 Architecture Baseline
32	
33	本文是 Batch 0 的整体架构基线。后续每个功能域进入 `cs-feat-design` 前，都必须把本文列为直接合同或边界护栏，并说明本批如何遵守本文的目录、依赖、状态和平台边界。
34	
35	Batch 0 只固定后续功能必须遵守的架构骨架：
36	
37	- 顶层目录固定为 `app / platform / shared / features / runtime / pages / widgets`。
38	- feature 内部通用分层固定为 `core / services / state / adapters / composables / components / fixtures`，按实际职责创建，不为了填满模板而建空层。
39	- feature public API 只是跨 feature 访问边界，不是必须新增的接口层；外部不得 import 其他 feature 的内部 `state`、`adapters`、内部 composable、内部 service 实现或私有 helper。
40	- `runtime/` 只在应用生命周期、平台资源装配或跨 feature 编排确有需要时出现，不是新的全局业务中心。
41	- renderer、platform、preload、main 的边界按本文和质量规则执行；现有 main 业务化只作为迁移风险处理，不作为新架构目标。
42	- 状态必须分清静态资产、运行事实、统计 read model 和 UI snapshot；运行统计不得写回 frame definition、字段定义或其他静态资产。
43	- 高频数据按 batch、delta、队列、节流、snapshot 和背压处理，页面不直接消费底层逐包事件。
44	- 跨 feature 通信只允许公开 service、runtime 编排、显式事件或边界输入输出，不允许互相 import 内部 state。
45	- pages、widgets、feature components 只承担各自 UI 边界，不拥有协议语义、任务推进、平台访问或跨域流程。
46	- 测试、fixture 和 oracle 必须放在可复用、可审查的位置，优先归入对应 feature 的 `fixtures/` 或 `core` 测试材料。
47	
48	Batch 0 不固定以下内容：
49	
50	- 不写字段 schema、接口签名、事件 payload 或 northbound 字段。
51	- 不设计 receive、send、task、SCOE、result、report、northbound 的内部算法和流程细节。
52	- 不给高频链路写具体队列深度、窗口大小或延迟阈值；这些参数必须在对应 feature design 中结合目标硬件、runtime 证据或压测计划确定。
53	- 不为每个 feature 预先创建 public API 清单；只有出现外部消费者或跨 feature 协作时，才在对应 `cs-feat-design` 中定义允许入口。

151	## 7. Recommended Internal Feature Layout
152	
153	不是每个 feature 都必须完整拥有以下子目录。只有当职责确实存在时才创建。
154	
155	```text
156	features/<feature>/
157	  core/          # 纯 TS 规则、类型、算法；不得依赖 Vue/Electron/Pinia
158	  services/      # feature 内应用服务和用例入口
159	  state/         # feature 自己的状态归口，通常由 Pinia 或明确状态容器承载
160	  adapters/      # 调用 platform 或外部能力的适配层
161	  composables/   # 面向页面/组件的 Vue 组合层；不得拥有领域规则
162	  components/    # feature 内复用 UI；页面仍放 pages/
163	  fixtures/      # 领域测试样例、oracle 输入输出
164	```
165	
166	Rules:
167	
168	- `core/` 必须可单测，不依赖 UI、Electron 和全局 store。
169	- `state/` 只维护本 feature 的状态、read model、selector 和很薄的本域 action；不得直接修改其他 feature 的内部状态。
170	- `services/` 是业务用例入口，可以协调本 feature 内部对象；跨 feature 流程优先进入 `runtime/`。
171	- `adapters/` 可以调用 `platform/` facade，但不得把平台 API 继续向 `core/` 泄漏。
172	- `composables/` 只做 UI-facing 组合，例如表单状态、对话框状态、生命周期订阅、selector 组合和调用公开 service；不得承载协议解析、任务状态机、统计累加或跨域业务流程。
173	- `components/` 只服务本 feature 的局部 UI，不承担跨域流程编排。
174	
175	Top-level `rewrite/src/composables` 不作为重写默认归口。确需跨页面复用的 Vue 组合逻辑，必须先判断归属：属于某 feature 的放入该 feature，属于应用壳或全局 UI 行为的放入 `app/` 或 `widgets/` 对应边界；没有明确归属时不得新建万能 composable。
176	
177	### Fixture, oracle, and test placement
178	
179	测试材料跟随业务归口，不建立脱离 feature 的第二套事实来源。
180	
181	Rules:
182	
183	- feature 自己的输入样本、期望输出、失败样本、边界样本和旧系统 oracle 映射，优先放入 `features/<feature>/fixtures/` 或该 feature 对应测试目录。
184	- `core/` 测试只依赖明确输入输出，不依赖 Vue、Pinia、Electron、platform facade、真实文件系统或真实串口网络。
185	- 跨 feature 的 runtime 编排测试可以放在 `runtime/` 对应测试材料中，但测试断言必须通过 feature public API 和显式事件观察结果。
186	- 旧 JSON、历史文件、CSV、甲方材料和硬件采样可以作为 fixture 输入或 oracle 来源；进入新核心模型前必须经过 feature design 确认，不得直接污染核心类型。
187	- 每个 feature design 必须列出自动 fixture、手工 checklist、runtime / hardware validation 三类验证材料；没有运行证据时只能声明静态或 fixture 通过。
188	
189	### Feature public API
190	
191	feature public API 是跨 feature 访问边界，不是必须新增的接口层、文件模板或 schema。只有当外部 feature、page、widget 或 runtime 需要访问该 feature 时，才需要在对应 feature design 中说明允许入口。
192	
193	允许入口可以是已有 store/composable/service 中被明确认可的调用面，也可以是后续新增的 service、只读 selector、runtime 页面级入口或显式事件/command。Batch 0 不要求每个 feature 都创建 `public.ts`，不要求统一 event bus / command bus，也不要求没有外部消费者的 feature 预先定义 public API。
194	
195	Rules:
196	
197	- 外部 feature、page、widget 不得 import 其他 feature 的 `state/`、`adapters/`、内部 composable、内部 service 实现文件或私有 helper。
198	- feature 内部可以自由组织实现细节；同一 feature 内部不需要通过 public API 绕行。
199	- 如果存在外部消费者，feature design 或实现说明必须写清楚外部可用入口和禁止绕过的内部状态。
200	- 通过 public API 暴露的数据不得授予外部写入本 feature 内部 state 的能力。
201	- 有跨 feature 写入或流程推进时，必须说明 owner、调用方、输入输出边界、错误或拒绝语义和验证方式；没有跨 feature 消费时可以明确记录为不需要额外 public API。
202	- 事件/command 只在确实有异步广播、跨域解耦或多消费者收益时使用；使用时必须列出生产者、消费者、owner、触发时机和失败处理口径。
203	- 只读 selector 可以面向页面或其他 feature 暴露 read model / UI snapshot，但不得暴露可变引用，也不得让调用方回写主状态。
204	
205	### Pages, widgets, and feature components
206	
207	UI 代码按用户入口和复用范围归口，不按视觉相似度随意放置。
208	
209	Rules:
210	
211	- `pages/` 放路由页面、页面级布局和页面动作连接；页面可以调用 runtime 页面级 API 或 feature public API，但不拥有业务规则。
212	- `features/<feature>/components/` 放只服务该 feature 的组件，可以调用本 feature composable / selector / public service，不编排其他 feature 内部状态。
213	- `widgets/` 放跨页面复用、纯展示或全局 UI 行为组件；它只能消费明确传入的 props、只读 snapshot 或公开 selector，不直接订阅运行主状态。
214	- UI snapshot 是页面展示投影，不是事实源；页面可以筛选、分页、虚拟滚动和节流展示，但不得反向定义运行事实。
215	- 当一个组件同时需要多个 feature 的事实时，优先由 `runtime/` 或页面层组合只读输入，再传给组件；组件不得自己 import 多个 feature 内部 state 拼业务流程。
216	
217	## 8. Dependency Direction
218	
219	默认依赖方向：
220	
221	```text
222	pages/widgets
223	  -> feature composables or runtime page APIs
224	  -> features/<feature>/services or state selectors
225	  -> features/<feature>/core
226	  -> shared
227	
228	features/<feature>/adapters
229	  -> platform
230	```
231	
232	Allowed:
233	
234	- `pages` 调用 runtime 提供的页面级操作入口。
235	- `runtime` 调用多个 feature 的公开服务，完成应用级流程。
236	- feature 内部从 `services` 调用 `core`、`state`、`adapters`。
237	- composable 可以读取本 feature 的 store selector、管理 UI 生命周期并调用公开 service。
238	- `adapters` 调用 `platform` facade。
239	- `platform` 调用 preload 暴露的 typed API。
240	
241	Not allowed:
242	
243	- `core` 依赖 Vue、Pinia、Electron、`window.electron`、`ipcRenderer`、`fs`、`serialport`。
244	- feature A 直接 import feature B 的内部 `state` 并修改它。
245	- feature A 绕过 feature B 的 public API，直接 import B 的内部 service、adapter、composable 或私有 helper。
246	- 页面组件直接创建任务状态机、直接发串口/网络、直接读写本地文件。
247	- composable 变成隐藏 service，承载协议语义、任务推进、统计累加或跨 feature 写状态。
248	- store 变成 service locator，负责创建 service、保存 adapter 或访问 platform。
249	- `receive` 通过共享状态回读决定任务生命周期。
250	- `send` 为 SCOE 或 northbound 写硬编码特例。
251	- `northbound` 直接改写内部运行主状态或收发主链内部对象。
252	
253	## 9. Runtime Layer
254	
255	`runtime/` 不是新的大而全业务域。它只负责应用级装配和跨域编排。
256	
257	Recommended responsibilities:
258	
259	- 应用启动和销毁顺序。
260	- 确有跨 feature 或平台装配需要时，负责 manager / service 的创建、显式依赖注入和释放。
261	- 确有多消费者、异步解耦或跨域流程收益时，提供事件 broker 或 command dispatcher；它只表达路由、调用顺序和边界输入输出。
262	- 运行主状态归口层的装配。
263	- 边界例外清单和显式例外入口。
264	- 页面动作到 feature service 的路由。
265	
266	Must not:
267	
268	- 承载 receive 解析算法。
269	- 承载 SCOE 协议细节。
270	- 承载 report 字段生成规则。
271	- 承载协议判断、任务状态推进、统计含义、结果归因或 northbound 语义转换。
272	- 直接访问 Electron/Node 原生能力。
273	- 变成所有 feature 都依赖的全局杂物箱。
274	
275	### Service wiring and dependency injection
276	
277	重写默认采用轻量、按需的依赖装配，而不是全局 singleton 或重型 DI 框架。只有当生命周期、测试替换、平台资源装配或跨域编排有实际收益时，`runtime/` 才作为组合根创建 feature service、adapter 和必要上下文。
278	
279	Rules:
280	
281	- service 的依赖应通过构造函数、工厂函数或明确 context 传入，便于测试时替换 fake adapter、fake store 或 fake service。
282	- Pinia store 不是 service locator，不负责创建 service，不保存 Electron/platform 原生对象。
283	- 组件和页面不直接 import service 内部实现；单 feature 页面优先通过本 feature composable / store 调用，跨 feature 页面动作才考虑 runtime 页面级 API。
284	- 跨 feature 调用只通过明确认可的入口、runtime 编排、显式事件或边界输入输出发生。
285	- 不为“架构感”引入复杂容器；只有在生命周期、测试替换或跨域装配有实际收益时才增加抽象。
286	
287	### Runtime state and statistics read models
288	
289	重写后不得用一个全局大 store 承载所有运行事实、统计数据和页面展示态。全局编排可以存在，但事实源和写入权必须留在明确的 feature 边界内。
290	
291	Layering:
292	
293	- 静态资产：帧定义、字段定义、表达式和 frame-owned 展示元数据等低频可编辑对象，归 `features/frame`；运行中的展示偏好、表格/图表/星座图 projection 和 UI-safe snapshot 归 `features/display`。
294	- 运行事实：连接状态、接收结果、发送结果、任务状态、SCOE 状态等，由对应 feature 单点写入。
295	- 统计 read model：由对应 feature 基于显式事件或结果增量维护，按 `frameId`、`fieldId`、`targetId`、`taskId` 等稳定 key 索引。
296	- UI snapshot：面向页面的只读展示投影，可以节流、分页、虚拟滚动或按需组合，不反向写入主事实。
297	
298	Rules:
299	
300	- 帧列表和其他静态资产对象不得承载高频运行统计；接收命中数、最近值、错误计数、速率等统计不得写回 frame definition。
301	- 高频链路应以 batch / delta 推进：平台侧批量输入，领域 core 处理批次，统计 read model 增量更新，页面消费节流后的 snapshot。
302	- 页面和组件不得直接订阅底层高频事件，不参与统计累加，只调用公开入口和展示只读投影。
303	- 事件只能作为 feature 边界输出或 runtime 编排输入；事件类型和消费者必须明确，禁止把事件总线变成隐式跨 feature 写状态的通道。
304	- 每个统计项必须说明 owner、reader、reset 时机、生命周期、是否持久化以及验证方式。
305	- main 可以做平台侧缓冲、批处理、聚合、节流、队列和背压，但业务统计含义仍归口到可测试 TypeScript 层。
306	
307	## 10. Electron Boundary
308	
309	重写目标配置：
310	
311	```ts
312	nodeIntegration: false
313	contextIsolation: true
314	sandbox: false
315	```
316	
317	Directory implications:
318	
319	```text
320	rewrite/src/platform/          # renderer facade
321	rewrite/src-electron/preload/  # typed bridge
322	rewrite/src-electron/main/     # platform resources
323	```
324	
325	Rules:
326	
327	- `platform/` 是 renderer 业务代码访问桌面能力的唯一正式入口。
328	- preload 只暴露 typed API，不暴露裸 `invoke/send/on`。
329	- main 负责串口、网络 socket、文件系统、系统对话框、窗口控制、定时器等平台资源。
330	- main 不承载 receive/send/SCOE/task/report 的领域规则。
331	- main 可以承接与平台资源绑定且性能压力明显的高频数据缓冲、批处理、聚合、节流、队列和背压；业务运算、协议语义、任务状态推进、报告语义仍归口到可测试 TypeScript 层。
332	- 高频串口/网络数据不得逐包无节制穿透到页面和全局 store；需要批量、缓冲、聚合或节流策略。
333	
334	## 11. Boundary Exception Registry
335	
336	领域例外可以存在，但必须显式登记，不能隐式沉积在通用链路里。
337	
338	Exception record should include:
339	
340	- 例外名称。
341	- 所属 feature。
342	- 为什么不能表达为通用输入 / 输出。
343	- 正式入口。
344	- 正式输出。
345	- 谁消费它。
346	- 如何测试或手工验证。
347	
348	Known candidates:
349	
350	- SCOE 固定来源进入接收主链。
351	- SCOE 固定目标进入发送主链。
352	- SCOE 领域完成条件。
353	- 高速存储命中后短路普通 receive/display/trigger 链。
354	- northbound 外部拒绝 / 不可执行 / 失败语义转换。
355	
356	## 12. Northbound Placement
357	
358	`northbound/` 是独立边界 feature，不是 task、status、report 的别名。
359	
360	Responsibilities:
361	
362	- 接收中心侧任务、控制、查询、保活、文件请求。
363	- 把外部请求转换为内部显式输入。
364	- 从内部 task/status/result/report 读取投影。
365	- 统一转换对外成功、失败、拒绝、不可执行、异常语义。
366	- 承接对外回执、结果上报、报告交付和文件回传。
367	
368	Must not:
369	
370	- 直接占有任务系统定义权。
371	- 直接把外部字段写成内部主状态字段。
372	- 直接把 history/CSV 文件当作 report 交付闭环。
373	- 把外部响应语义散落到 task/send/report/storage 各处。
374	
375	## 13. Result, Report, Delivery Split
376	
377	三者必须分开：
378	
379	| Layer | Owns | Does not own |
380	| --- | --- | --- |
381	| `result/` | 内部结果事实、用例结果、执行摘要 | 报告文件格式、对外交付动作 |
382	| `report/` | 报告对象和报告文件生成 | HTTP/FTP 上传、外部回执 |
383	| `northbound/` | 对外结果上报、报告交付、文件回传、错误语义转换 | 内部结果事实定义 |
384	
385	Reason:
386	
387	- 结果事实需要先在内部归口。
388	- 报告对象可以由内部结果和历史材料生成。
389	- 交付动作属于外部协议边界，成功或失败不能反向改写内部事实本身。
390

410	## 15. Architecture Entry Conditions For Later Batches
411	
412	每个后续 Batch 进入 `cs-feat-design` 前，必须先补齐本节检查项；缺失项必须在 design 中标为 blocking、deferred 或只读调查范围，不能在实现阶段临场扩大边界。
413	
414	Required before design:
415	
416	- 明确本批涉及哪些 feature 归口，以及哪些旧系统可观测行为属于 `preserve`、`candidate drop`、`deferred` 或 `not touched`。
417	- 若本批存在外部消费者或跨 feature 协作，明确允许入口；若没有，说明不需要额外 public API。
418	- 明确本批是否需要 `runtime/` 编排；若需要，说明 runtime 只负责装配、调用顺序、事件路由和生命周期，不承载领域规则；若不需要，不为形式感新增 runtime 层。
419	- 明确是否新增或调整 platform / preload / main API；若涉及 main 高频处理，说明哪些只是平台侧缓冲、批处理、聚合、节流、队列或背压；若触达现有 main 业务化路径，必须把它登记为迁移风险或边界例外。
420	- 明确静态资产、运行事实、统计 read model、UI snapshot 的 owner、reader、写入权、reset 时机、生命周期和是否持久化。
421	- 明确跨 feature 通信方式，禁止以内部 state import、全局 store 回读或隐式事件总线替代公开接口。
422	- 明确 pages、widgets、feature components 的放置和职责，不让 UI 承载任务机、协议语义、统计累加、文件/串口/网络访问。
423	- 明确自动 fixture、手工 checklist、runtime / hardware validation 的边界和未验证项。
424	- 涉及 SCOE、高速存储、真实串口、TCP/UDP、打包态 data path、HTTP/FTP 或 northbound 时，必须读取对应边界材料并登记例外或 runtime validation。
425	
426	## 16. Infrastructure Baseline
427	
428	最小基础设施搬运原则：
429	
430	- 可复用：Vue 3、Quasar、Pinia、Vue Router、UnoCSS、Electron、serialport、TypeScript、ESLint/Prettier 等经确认仍需要的依赖类别；窗口安全配置；Quasar/Electron/Vite 的必要构建能力；现有主题 token 和样式经验中无业务耦合的部分。
431	- 禁止直接搬：旧 Quasar boot 业务初始化、旧 `src/api/common`、旧 `window.electron`、旧 preload all-in-one 聚合、旧 main IPC business handlers、旧 `public` data path 读写策略、旧 root package scripts 中对 `src*/**` 和 `src-electron` 的路径假设。

436	## 17. Test Baseline and Validation Layers
437	
438	默认测试基线：
439	
440	- 使用 Vitest 作为 `core`、`services`、`adapters`、`selectors` 的默认单测栈。

53	| `revise-required` | 存在边界、功能范围或验证证据问题，需要修改后再过。 |
54	| `blocked` | 缺少用户决策、硬件条件、甲方口径或关键 baseline，不能继续声明完成。 |
55	
56	不得用“看起来能跑”替代上述结论。
57	
58	Outcome gate:
59	
60	- 缺少 `Direct contract`、用户决策、甲方口径、关键 baseline、northbound 语义、阻断性 schema/枚举时，必须是 `blocked`。
61	- 存在边界违规、跨 feature 内部写入、runtime/store/composable 业务化、main 业务化时，必须是 `revise-required`。
62	- 只有语义已锁定但真实硬件、打包态、HTTP/FTP 或客户环境证据未完成，且每个 gap 都登记 validation level、owner、blocker 和后续验证方式时，才允许 `pass-with-known-gaps`。
63	- 缺少本轮触达旧行为的 evidence source、owner feature、strategy 和 validation level 时，必须是 `revise-required`；关键 oracle 或 evidence 缺失导致范围无法判断时，必须是 `blocked`。
64	- 用 static scan、Vitest unit、fixture test、oracle comparison、fake adapter test、build 或 lint 通过宣称 hardware、package、HTTP/FTP、northbound 或 customer closure 完成时，必须是 `revise-required`。
65	
66	每轮 review 开头必须列：
67	
68	- `Direct contract:` 当前轮正式合同。
69	- `Boundary guards:` 辅助边界材料。

94	## 5. Structure and Dependency Checklist
95	
96	必须检查：
97	
98	- 新代码是否落在 `rewrite/` 独立应用根目录内，而不是旧 `src/`、`src-electron/` 或 `public/`。

102	- `core` 是否保持纯 TS，不依赖 Vue、Pinia、Electron、platform facade 或全局 store。
103	- `state` / store 是否只承载本 feature 的状态、read model、selector 和很薄的本域 action。
104	- `services` 是否作为业务用例入口，而不是把流程塞进 store、composable 或组件。
105	- `composables` 是否只做 UI-facing 组合，没有承载协议语义、任务状态机、统计累加或跨域流程。
106	- `pages` 和 `widgets` 是否只做交互、展示和调用公开入口。
107	- `runtime` 是否只做应用级装配和跨域编排，没有吞掉领域内部规则。
108	- `runtime` 是否只表达生命周期、调用顺序、路由和边界输入输出，没有承载协议判断、任务状态推进、统计含义、结果归因或 northbound 语义转换。
109	- `platform` 是否只做 renderer 侧桌面能力 facade，没有业务规则。

116	- UI 组件直接访问 Electron、Node、串口、文件系统或 socket。
117	- store 创建 service、保存 platform adapter 或访问 Electron/Node 能力。
118	- composable 变成隐藏 service。
119	- 组件直接 import service 内部实现并绕过 feature composable 或 runtime 入口。
120	- `shared` 中出现 Vue/Electron/Pinia 依赖。
121	- `runtime` 变成所有 feature 依赖的杂物箱。
122	
123	依赖注入必须检查：
124	
125	- `runtime` 是否是 service、adapter 和上下文的组合根。
126	- service 依赖是否通过构造函数、工厂函数或明确 context 传入，便于测试替换。
127	- 是否没有全局 singleton service 到处 import。
128	- 跨 feature 协作是否通过公开 service 接口、runtime 编排、显式事件或边界输入输出。
129	- 是否没有为了形式化而引入无明确生命周期、测试收益或装配收益的复杂 DI 容器。

167	## 7. Data flow boundary
168	
169	Target flow:
170	
171	```text
172	native resource in main
173	  -> resource lifecycle / byte I/O
174	  -> main-side buffer / batch / queue / backpressure when justified
175	  -> minimal typed preload bridge
176	  -> rewrite/src/platform facade
177	  -> connection real transport adapter
178	  -> connection service/state/read model
179	  -> runtime route or explicit feature event
180	  -> receive / send / SCOE / status public boundary
181	  -> feature-owned read model
182	  -> throttled UI snapshot
183	```
184	
185	Rules:
186	
187	- Low-frequency lifecycle/error facts and high-frequency byte input must use separate design lanes.
188	- Byte input reaches receive as transport bytes/batches plus source material. connection does not parse it.
189	- Byte output reaches main as transport write material. send/SCOE own business request and business result.
190	- Status may read connection summary, but does not own connection truth.
191	- Runtime may route bytes and writes, but does not inspect protocol semantics.
192	- UI consumes snapshots and commands, not raw transport events.

194	## 8. Event, buffer, and backpressure principles
195	
196	Main may retain only these platform-side or performance-side processing categories:
197	
198	- input byte batching for serial/TCP/UDP data.
199	- write queueing tied to a live native resource.
200	- subscription queueing and cleanup to prevent stale event delivery.
201	- bounded lifecycle/error event buffering for renderer synchronization.
202	- throttle or coalesce for high-frequency telemetry and UI-safe event delivery.
203	- overflow/backpressure signal when queue/batch policy is exceeded.
204	- resource cleanup drain on close, app shutdown or stale connection generation.
205	
206	Rules:
207	
208	- Queue depth、batch window、overflow/drop policy、sampling、UI refresh interval and target throughput are deferred to implementation/runtime evidence.
209	- Overflow must be observable as transport-level material, not silently converted into receive/send/task/result failure.
210	- Main may compress or batch events for transport pressure, but may not classify bytes as frame match、task trigger、SCOE success、report material or northbound delivery status.
211	- connection may maintain transport counters and recent event snapshots, but business statistics belong to receive/send/task/SCOE/status/result owners.
212	- Runtime exception records are required for high-frequency buffer/backpressure, high-speed storage short-circuit, packaged native module behavior and SCOE fixed route.
213	- Development-time fake adapter tests can simulate backpressure categories, but real steady-state behavior requires runtime/hardware validation after parameters are designed.

215	## 9. Error and lifecycle boundary
216	
217	Principles:
218	
219	- Main emits raw resource outcomes and technical failures.
220	- Platform/preload carry typed technical results without exposing raw IPC or raw handles.
221	- Connection normalizes transport-level lifecycle and error facts.
222	- Consumers interpret those facts under their own feature designs.
223	
224	Lifecycle boundaries:
225	
226	- connect、disconnect、cleanup and app shutdown must be idempotent enough for duplicate user actions, stale events and already-closed resources.
227	- Automatic reconnect is not assumed. If introduced, retry policy、cancellation、UI visibility and runtime/hardware validation must be declared separately.
228	- TCP server client lifecycle is transport availability material, not a business session.
229	- UDP remote route is transport route material, not a customer device identity.
230	
231	Error boundaries:
232	
233	- A transport write failure is input material for send/SCOE; it does not define task lifecycle.
234	- A disconnect or timeout is a connection fact; it does not define result/report/northbound failure.
235	- Missing resource, port unavailable, socket error or cleanup failure can be normalized by connection, but this document does not freeze error code names.
236	- User-visible error text belongs to pages/status projection and must not leak raw platform internals.

170	## 5. Event model
171	
172	### 5.1 Event classification
173	
174	Transport events 分为三类：lifecycle、data、backpressure/signal。
175	
176	| Category | Events | Frequency | Producer | Consumer | Design lane |
177	| --- | --- | --- | --- | --- | --- |
178	| Lifecycle | connected、disconnected、error（open-failed、connect-failed、listen-failed、bind-failed、timeout、close-failed、resource-unavailable、stale-event、invalid-config） | Low | main resource handler -> preload bridge -> platform facade -> connection adapter -> connection service | connection state、status read model、pages | Direct event delivery，no batching needed |
179	| Data | data（incoming bytes with connectionId、byteLength、source target） | High | main byte input handler -> batching in main -> preload bridge -> platform facade -> connection adapter drainEvents | connection service -> runtime route -> receive | Batched delivery，main-side buffer，separate from lifecycle |
180	| Backpressure/Signal | queue-full、queue-drained、write-backpressure（write queue full） | Low-Medium | main buffer management | connection adapter、runtime、status | Event-based signal，不自动转成业务错误 |
181	
182	### 5.2 Event flow
183	
184	```text
185	Main process:
186	  native resource event (serial data / socket data / socket close / socket error)
187	    -> main-side per-connection buffer:
188	       - lifecycle/error: immediate -> bounded lifecycle event queue
189	       - data: accumulate in byte batch buffer until window or flush trigger
190	    -> backpressure check:
191	       - if batch buffer exceeds threshold: emit queue-full signal
192	    -> typed event delivery to preload bridge
193	
194	Preload bridge:
195	  receives main events via IPC
196	  -> lifecycle events: immediate forward
197	  -> data events: forward batch as single event
198	  -> backpressure signals: forward as event
199	
200	Platform facade (renderer):
201	  wraps preload bridge API
202	  -> exposes drainEvents() for connection adapter
203	  -> exposes lifecycle command methods (connect/disconnect/write/cleanup)
204	
205	Connection real adapter:
206	  implements ConnectionTransportAdapter port
207	  -> drainEvents() pulls from platform facade
208	  -> maps platform events to ConnectionAdapterEvent[]
209	  -> no platform handle leakage
210	
211	Connection service:
212	  consumes adapter events via existing service logic
213	  -> routes data events to runtime for receive
214	  -> updates connection state for lifecycle events
215	  -> updates transport counters for all events
216	```
217	
218	### 5.3 Event ordering rules
219	
220	- 同一 connectionId 的 lifecycle 和 data 事件必须保序。
221	- 不同 connectionId 的事件可以交错，不需要全局序列号。
222	- `connected` event 必须在 data event 之前到达 service。
223	- `disconnected` event 后不应有同 connectionId 的 data event；若出现，connection service 标记为 `stale-event`。
224	- `write-accepted` 和 `write-failed` 是 command response 的一部分，不是异步 event queue 内容。
225	- Backpressure signal 不中断事件顺序，只是状态标记。
226	
227	### 5.4 Subscription lifecycle
228	
229	```text
230	Runtime startup:
231	  -> create connection service with real adapter
232	  -> adapter subscribes to platform facade event channel
233	  -> platform facade registers preload event listener
234	
235	Connection connect:
236	  -> service calls adapter.connect(config)
237	  -> adapter calls platform facade connect command (IPC invoke to main)
238	  -> main creates native resource, starts buffering
239	  -> main emits 'connected' event via preload bridge
240	  -> adapter drainEvents() picks up 'connected'
241	
242	App shutdown / page close:
243	  -> runtime calls service.cleanup()
244	  -> adapter calls platform facade cleanup command
245	  -> main drains all resources, closes handles
246	  -> platform facade removes event listener
247	  -> stale events after cleanup are discarded by adapter
248	```

250	## 6. Queue / backpressure / batching principles
251	
252	### 6.1 Principles
253	
254	本节只定原则和验证点，不写最终参数。
255	
256	| Principle | Rationale | Verification point |
257	| --- | --- |--- |
258	| Main-side per-connection byte batch buffer | 减少 IPC 消息数量，避免旧系统的逐包穿透 | 验证 serial 115200 baud 和 TCP 高频场景下 IPC 消息速率下降 |
259	| Bounded batch buffer with flush trigger | 防止 batch buffer 无界增长 | 验证 buffer 达到上限时自动 flush，不等待时间窗口 |
260	| Time-window flush for low-frequency data | 低频数据不应因 batch 而延迟过长 | 验证空载或低频场景下 data event 在合理时间内到达 renderer |
261	| Bounded async event queue with overflow signal | eventQueue 不可无界 | 验证 queue 超限时 backpressure signal 到达 connection adapter |
262	| Overflow must be observable transport material | 丢弃不是静默行为 | 验证 overflow event 包含丢弃的 connectionId 和 byte count |
263	| Per-connection queue isolation | 一个连接的背压不应阻塞其他连接 | 验证 serial 和 TCP 同时高频时，serial 背压不影响 TCP 事件 |
264	| Main does not classify bytes | main 只做 buffer/batch/queue，不判断 frame content | 验证 main handler 代码不包含 frame matching、SCOE rule 或 receive classification |
265	| Overflow must not auto-convert to business error | 丢弃是 transport material，receive/send/task 自己决定业务含义 | 验证 overflow event 不进入 receive 作为 parse failure |
266	
267	### 6.2 Batch buffer design lane
268	
269	```text
270	Main per-connection byte input:
271	  native data callback
272	    -> append to per-connection byte buffer
273	    -> if buffer size >= maxBatchBytes: flush immediately
274	    -> else if time since last flush >= maxBatchWindowMs: flush
275	    -> flush: emit single 'data' event with accumulated bytes + source info
276	    -> if event queue depth >= maxQueueDepth: emit queue-full signal, apply drop policy
277	    -> drop policy candidate: drop oldest batch (latest data is more relevant for real-time systems)
278	```
279	
280	具体参数（maxBatchBytes、maxBatchWindowMs、maxQueueDepth）在 implementation 阶段根据 runtime evidence 和 hardware testing 确定。
281	
282	### 6.3 Write queue design lane
283	
284	```text
285	Main per-connection write:
286	  write request from renderer
287	    -> if native resource is live: write bytes directly
288	    -> if write callback indicates backpressure (drain event): queue subsequent writes
289	    -> if write queue exceeds threshold: return write-backpressure to adapter
290	    -> on drain: flush queued writes
291	```
292	
293	Write queue 与 input queue 独立管理，互不影响。
294	
295	### 6.4 What must NOT happen
296	
297	- 不可让 main 根据 byte content 决定 data 是否进入 renderer（旧 high-speed storage short-circuit 模式）。
298	- 不可让 batch window 导致低频数据无限延迟。
299	- 不可让 eventQueue 无界增长（旧 receiveFramesStore 模式）。
300	- 不可让一个连接的背压阻塞其他连接的事件传递（旧全局 processingLock 模式）。
301	- 不可让 renderer-to-main 的 IPC round-trip 成为每包处理的瓶颈（旧 receiveHandler invoke 模式）。

94	- 性能问题优先通过数据流设计、批处理、缓冲、队列、背压、采样和事件压缩解决；不能为了减少 IPC 把业务逻辑塞进 main。

96	任何 main 进程边界例外都必须说明：
97	
98	- 为什么 renderer / TypeScript core 无法合理承载。
99	- main 中只保留了哪些平台侧或性能侧处理。
100	- 业务语义最终在哪里归口。
101	- 如何测试、压测或手工验证。

103	## 目录与职责
104	
105	目标结构以 `codestable/architecture/rewrite-target-structure.md` 为准：
106	
107	```text
108	rewrite/
109	  src/
110	  src-electron/
111	    main/
112	    preload/
113	```
114	
115	`rewrite/` 是新的独立应用根目录，不只是源码目录。旧 `src/`、`src-electron/`、`public/` 只作为旧系统 evidence、oracle 或 migration input，不作为新代码落点。
116	
117	renderer 源码结构：
118	
119	```text
120	rewrite/src/
121	  app/
122	  platform/
123	  shared/
124	  features/
125	  runtime/
126	  pages/
127	  widgets/
128	```
129	
130	基本职责：
131	
132	- `app/`：应用启动、路由、布局壳、全局 provider、生命周期装配。
133	- `platform/`：renderer 侧平台 facade，唯一正式桌面能力入口。
134	- `shared/`：纯类型、通用工具、协议常量、无副作用 helper。
135	- `features/`：按业务能力归口领域规则、应用服务、状态和领域内 UI。
136	- `runtime/`：应用级装配、跨域编排、边界例外登记，不承载领域内部规则。
137	- `pages/`：路由页面、页面级布局、连接用户操作到 runtime / feature 公开入口。
138	- `widgets/`：跨页面 UI 组件和纯展示组件。
139	
140	核心规则必须放在可测试 TypeScript 层。`features/*/core` 不依赖 Vue、Pinia、Electron、platform facade、全局 store 或 Node 能力。
141	
142	基础设施基线：
143	
144	- `rewrite/` 下配置必须重新收缩，不能原样搬旧 Quasar boot、旧 `src/api/common`、旧 `window.electron`、旧 preload 聚合、旧 main business handlers 或旧 `public` data path。
145	- Vitest 是 core/service/adapter/selector 默认单测栈；页面交互先走 manual checklist。
146	- Electron runtime、打包态 package、真实串口/TCP/UDP/SCOE 硬件和 customer validation 不由 Vitest 代替。
147	- 默认保持显式 import；如后续引入 auto-import，只允许 Vue、Vue Router、Pinia 等基础框架 API，禁止自动导入 feature service、platform facade、runtime、store、feature public API、adapter 或带业务 owner 的 helper。
148	- rewrite UI 样式以 Quasar + `rewrite/src/css` SCSS token 为主系统；颜色、背景、状态色、边框、阴影、间距、圆角、z-index 和字体层级必须先归口到 token，业务组件、页面、widget、UnoCSS class 和 inline style 不得硬编码这些视觉 token。
149	- Quasar 官方组件 prop 和 helper class 可作为 Quasar token scale 使用，例如 `color="primary"`、`q-pa-*`、`row/col`、`text-h*`、`shadow-*`；app-specific surface、selected、device/status 等视觉语义仍必须写语义 class 并消费 token。
150	- UnoCSS 只允许承担结构性布局 utility 和 token-backed shortcut，不作为业务样式主系统；组件 class 按 app/page/widget/feature ownership 使用语义化命名，跨页面通用 visual utility 只能进入 token-backed `.rw-*` 基线类。
151	- `rewrite/src/css/tokens/*` 是 primitive 视觉值的唯一落点；新增颜色、间距、尺寸、字体层级、边框、圆角、阴影或 z-index 时，必须先扩展 token，再通过 `--rw-*`、Quasar brand/helper 或语义 class 消费。`app/pages/widgets/features/*/components`、`uno.config.ts` 和 inline style 不得新增裸 hex/rgb/hsl/px/rem/em 视觉值。
152	- 涉及 rewrite UI 样式实现或审查时，完成前必须静态扫描 app/pages/widgets/feature components/UnoCSS 配置中的硬编码视觉值和 Uno 视觉 utility；样式入口、Quasar config、token 或 UnoCSS config 变更后至少运行 `pnpm -C rewrite lint`，触达构建入口时运行 `pnpm -C rewrite build`。

154	## CodeStable 推进规则
155	
156	### Lane C
157	
158	Lane C 不使用旧 slice 体系。全局拆解、依赖和状态只放在：
159	
160	- `codestable/roadmap/{slug}/{slug}-roadmap.md`
161	- `codestable/roadmap/{slug}/{slug}-items.yaml`
162	
163	每个 roadmap item 启动后，按单 feature 流程推进：
164	
165	1. `cs-feat-design`：读取 roadmap item 和相关合同，产出 feature design/checklist。
166	2. `cs-feat-impl`：按 feature design/checklist 实施。
167	3. `cs-feat-accept`：验收后回写 roadmap item 状态。
168	
169	实施中重新出现开放分歧、接口契约不成立、依赖顺序错误或代码现实冲突时，回到 `cs-roadmap update` 或当前 feature design 阶段，不在实现阶段临场扩大边界。
170	
171	### 实施对话
172	
173	实施以单 feature 或单 issue 为单位。若来自 roadmap，当前 feature 的直接合同是：
174	
175	- 对应 roadmap item。
176	- 当前 feature 的 `{slug}-design.md`。
177	- 当前 feature 的 `{slug}-checklist.yaml`。
178	
179	若存在 handoff，handoff 只补充跨对话上下文和边界，不能推翻上述直接合同。
180	
181	每轮实施和审查开头必须列出：
182	
183	- `Direct contract:` 当前轮真正据此判断范围和完成度的正式工件。
184	- `Boundary guards:` 只用于补边界、术语和上下文的辅助材料。
185	
186	未列出直接合同，或把 handoff、摘要、临时 prompt 当成正式合同，不能进入实现结论。
187	
188	### 审查对话
189	
190	独立审查只看直接合同、边界护栏和实际改动，不依赖实施过程讨论。审查结论按 `rewrite-review-checklist.md` 使用：
191	
192	- `pass`
193	- `pass-with-known-gaps`
194	- `revise-required`
195	- `blocked`
196	
197	`pass-with-known-gaps` 只用于语义已锁定但 runtime/hardware/customer 环境证据尚未完成的情况。缺少用户决策、甲方口径、关键 baseline、直接合同、northbound 语义或阻断性 schema/枚举时，结论必须是 `blocked`。
198	
199	## 实施前检查
200	
201	进入代码实施前，必须明确：
202	
203	- 当前轮直接合同是什么。
204	- 覆盖哪些旧系统可观测行为。
205	- 涉及哪些 feature 归口。
206	- 外部是否只通过明确 public API 访问 feature。

209	- 哪些行为可自动 fixture，哪些只能手工 checklist，哪些必须 runtime / hardware validation。

211	不写业务代码的规则整理、文档收口和只读分析，可以只说明读取证据和判断依据，不强制进入 feature 实施流程。

232	## 子 agent 调度
233	
234	代码阅读、文件扫描、事实调查类任务优先判断是否适合子 agent。主对话负责目标、边界、集成结果和最终判断；子 agent 只接收边界清楚、可验证、可并行的任务。
235	
236	中等以上任务：
237	
238	- 讨论阶段积极派 explore agent 并行检索相关代码和文档。
239	- 执行阶段有多个独立任务时拆给 executor 子 agent 并行。
240	- 验证阶段尽量由独立 verifier / code-reviewer 做，不自审自验。
241	
242	小任务默认主线程完成；如果子 agent 能更快获得独立事实或低成本复核，可以派轻量子 agent。
243	
244	## `.sessions/` 轻量过程层
245	
246	`.sessions/` 只在确有需要时使用：
247	
248	- 跨对话交接。
249	- 多轮讨论过程需要保留。
250	- 需要 topic-index 帮助定位上下文。
251	- handoff 能显著降低下一轮误读风险。
