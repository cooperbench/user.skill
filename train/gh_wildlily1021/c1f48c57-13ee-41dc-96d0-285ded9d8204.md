  东方红上位机 rewrite 项目已完成 9 个 feature 的骨架搭建（core/service/state/selector/public），runtime wiring 完成，330+ 测试通过。现在需要全面审计已有代码的架构风险，在任何进一步实现之前把问题揪出来。

  ## 任务

  用子 agent 并行审计以下维度，每个 agent 独立汇报。要求用中文汇报，facts-first。

  ### Agent 1：Feature 边界隔离审计
  扫描 rewrite/src/features/ 下所有 feature 目录，检查：
  - 每个 feature 的 public.ts 是否只导出了service、selector、类型？
  - 有没有 feature 的内部文件（core/service/state/adapters 下的）被其他 feature 直接 import？
  - 有没有 feature A 的 store/state 被 feature B 直接读写？
  - runtime/ 目录有没有绕过 public API 直接访问 feature 内部？
  列出所有违规 import，给出文件路径和行号。

  ### Agent 2：Store 单点写入审计
  扫描所有 feature 的 state/ 目录：
  - 每个 store/state 有几个写入点？
  - 是否存在外部 feature 直接调用 $patch / 赋值修改别的 feature 的状态？
  - selector 返回的是只读快照还是可变引用？（检查返回类型有没有 readonly、是否用了深拷贝）
  列出所有"非 owner 写入"的违规。

  ### Agent 3：Runtime 职责审计
  读 rewrite/src/runtime/ 下所有文件：
  - wireFeatures / routingTick / destroy 里有没有业务判断逻辑（if-else 根据业务语义做路由决策）？
  - routingTick 是否只做 drain→transform→emit 的纯接线？
  - runtime 有没有直接持有业务状态（不是 feature service 引用，而是可变业务数据）？
  - bridge 文件里有没有超出"格式转换"的业务逻辑？

  ### Agent 4：Shared 层纯净性审计
  扫描 rewrite/src/shared/ 下所有文件：
  - 有没有 import 任何 feature 的内容（应该零依赖）？
  - 有没有 import Vue / Pinia / Electron 相关的东西？
  - 有没有持有可变全局状态？
  - 确认 platform-bridge.ts 的类型是否只定义了 preload/renderer 的桥接接口，没有业务语义

  ### Agent 5：Platform 边界审计
  读 rewrite/src/platform/ 下所有文件：
  - platform facade 是否只暴露桌面能力（transport 等），不承载业务语义？
  - 有没有直接 import Node/Electron 模块？
  - TransportFacade 接口签名是否和 preload 暴露的 TransportBridge 完全对齐？
  - getTransportFacade() 的 bridge 检测逻辑是否健壮（SSR 保护、类型校验等）？

  ### Agent 6：测试质量审计
  扫描所有测试文件（*.spec.ts）：
  - 测试是否只通过 public API 测试行为，还是直接访问内部 state？
  - 有没有 mock 了不应该 mock 的东西（比如跳过了 boundary 检查）？
  - 端到端测试覆盖了哪些链路？缺了哪些关键链路？
  - 测试之间的隔离性（一个测试的副作用是否影响另一个）

  每个 agent 汇报格式：
  - 发现的问题（按严重程度排序：违规 > 风险 > 建议）
  - 每个问题给出文件路径、行号、具体描述
  - 最后给一个整体评估

  所有 agent 完成后，汇总成一份架构风险报告。
