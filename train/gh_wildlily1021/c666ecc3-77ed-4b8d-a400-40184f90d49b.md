### 核心设计问题

1. **`compareValues()` 本身已经满足"事实+条件→是否匹配"的纯函数要求**。这个 feature 可能主要不是从零建，而是补齐 + 清理。
2. **`FieldCondition` 类型**（带 frameId/fieldId）放在 shared/ 是否合理？它是不是应该归 task feature？
3. **需要补哪些运算符**？`contains` 看起来确定要加。`range`（如 `between 10 and 20`）是否需要？
4. **逻辑组合（AND/OR 多条件）** 属于本 feature 还是消费方自己组合？

> DEVELOPER

旧对话的评价：FieldCondition（带 frameId/fieldId）不应该在 shared/。它绑定了"从哪个帧的哪个字段取值"这个 task 领域知识，不是纯匹配逻辑。shared/ 应该只留 compareValues() +
  ComparisonOperator（纯比较），FieldCondition 归 task feature（它决定"比什么"是 task 的业务语义）。

  剩下两个设计问题我的判断：

  - contains：加。旧系统有，通用需求。
