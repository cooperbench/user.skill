  ### 批次 1：事实收集 + 外部参考（10 个 agent 并行）

  **Agent 1：旧系统全部页面行为清单**
  - 搜索 src/ 下所有 .vue 页面文件
  - 提取每个页面的：页面名称、路由、主要功能、用户操作列表、数据来源
  - 按 CLAUDE.md "旧代码看行为不看架构" 原则，只列用户能看到和操作的东西
  - 输出：完整的旧行为清单表格

  **Agent 2：旧系统布局和导航行为**
  - 读旧系统的布局组件、路由配置、导航菜单
  - 提取：导航结构（几级菜单、分组方式）、布局模式（侧边栏/标签页/弹窗）、页面间跳转关系
  - 重点关注用户实际使用的导航路径，不是代码组织方式

  **Agent 3：新系统已有 UI 代码**
  - 搜索 rewrite/src/pages/ 和 rewrite/src/widgets/ 和 rewrite/src/app/ 下所有 .vue 文件
  - 搜索 rewrite/src/features/*/components/ 下所有 .vue 文件
  - 提取：已有哪些页面/组件、使用了哪些 Quasar 组件、布局模式
  - 标注：完成的 / 骨架的 / 空的

  **Agent 4：前端规范精读**
  - 精读 codestable/quality/rewrite-frontend-conventions.md 全文
  - 按设计维度归类规则：
    - 布局相关（页面结构、间距、响应式）
    - 导航相关（菜单、面包屑、标签页）
    - 表格相关（列定义、排序、筛选、虚拟滚动）
    - 表单相关（布局、校验、错误提示）
    - 颜色/状态色相关（token 使用）
    - 组件选型相关（Quasar 组件使用约束）
  - 每条标注约束力度和设计影响

  **Agent 5：CSS token + Quasar 主题现状**
  - 读 rewrite/src/css/ 全部文件（tokens、主入口、quasar 变量）
  - 读 rewrite/quasar.config.ts 的 brand/theme 配置
  - 提取：已有 token 清单（颜色、间距、字体、圆角、阴影、z-index）
  - 提取：Quasar brand 色、暗色模式配置
  - 标注：token 是否完整覆盖 UI 需要的维度

  **Agent 6：Web 搜索 — 工业监控/SCADA UI 最佳实践**
  - 搜索关键词：
    - "industrial monitoring dashboard UI design best practices 2025"
    - "SCADA HMI modern web interface design"
    - "real-time data monitoring dashboard layout patterns"
  - 提取：布局模式、信息密度策略、状态展示方式、报警设计
  - 重点关注：桌面端 Electron 应用的 UI 模式，不是移动端

  **Agent 7：Web 搜索 — Quasar admin/dashboard 模板参考**
  - 搜索关键词：
    - "Quasar framework admin dashboard template 2025"
    - "Quasar v2 layout best practices sidebar navigation"
    - "Quasar data table real-time update pattern"
  - 提取：成熟的布局模式、导航方案、共享组件组织方式
  - 重点关注：与 Electron 桌面应用兼容的方案

  **Agent 8：Web 搜索 — 实时数据表格 UI 设计**
  - 搜索关键词：
    - "real-time data table UI design virtual scroll"
    - "high frequency data update table performance React Vue"
    - "industrial parameter monitoring table design"
  - 提取：大量参数（100+）场景的表格设计、虚拟滚动方案、更新策略
  - 重点关注：不阻塞 UI 的实时更新方案

  **Agent 9：Web 搜索 — Vue/Quasar 组件库补充**
  - 搜索关键词：
    - "Quasar QSplitter QTabPanels QTree best practices"
    - "Vue 3 component layout patterns composable"
    - "Quasar dark mode implementation 2025"
  - 提取：适合本项目的 Quasar 组件使用模式
  - 重点关注：列表-详情分栏、可折叠面板、标签页嵌套等复合布局

  **Agent 10：参考项目 UI 规范复查**
  - 读 refactor/docs/quality/frontend.md 和 refactor/docs/conventions/frontend.md
  - 提取与布局、导航、页面结构相关的规则
  - 与 rewrite-frontend-conventions.md 对比，看是否有遗漏

  ### 批次 2：设计分析（6 个 agent，基于批次 1 产出）

  **Agent 11：页面清单与功能映射**
  - 输入：Agent 1（旧页面行为）+ Agent 3（新系统现状）+ 全局规划文档的功能清单
  - 产出：完整的页面清单，每页标注：
    - 页面名称和职责
    - 对应的 feature
    - 主要数据来源（哪个 feature 的 selector/service）
    - 主要用户操作
    - 优先级（P0 核心页面 / P1 重要页面 / P2 辅助页面）

  **Agent 12：导航体系设计**
  - 输入：Agent 2（旧导航行为）+ Agent 6/7（外部参考）+ Agent 4（规范约束）
  - 分析：
    - 导航层级（一级/二级菜单 or 标签页 or 混合）
    - 导航分组逻辑（按功能域 / 按工作流 / 按用户角色）
    - 多连接场景下的导航（是否需要连接上下文切换）
    - 快捷键和工具栏
  - 产出：导航结构图 + 导航状态管理方案

  **Agent 13：布局骨架设计**
  - 输入：Agent 5（token 现状）+ Agent 6/7（外部参考）+ Agent 4（规范约束）
  - 分析：
    - 应用级布局（侧边栏+内容区？顶部导航+内容区？混合？）
    - 页面级布局模式（列表-详情分栏？全宽表格？卡片网格？）
    - 面板/分栏/折叠等复合布局组件选型（QSplitter/QTabPanels/QExpansionItem）
    - 页面间布局一致性保障
  - 产出：2-3 种布局骨架方案对比 + 推荐

  **Agent 14：共享 widget 清单**
  - 输入：Agent 1（旧行为）+ Agent 3（新系统现状）+ Agent 9（Quasar 组件）
  - 分析：哪些 UI 元素跨页面复用：
    - 数据表格（参数列表、帧列表、任务列表...）
    - 表单（连接配置、帧编辑、任务编辑...）
    - 状态指示器（连接状态、运行状态、告警状态）
    - 对话框（确认、导入导出、错误提示）
    - 工具栏（搜索、筛选、操作按钮）
  - 产出：共享 widget 清单 + 每个的接口草案

  **Agent 15：实时数据展示架构**
  - 输入：Agent 8（表格设计参考）+ display-ui-design（已有设计）+ Agent 4（规范）
  - 分析：
    - 实时数据的展示层管道（从 selector 到 DOM 的更新路径）
    - 更新频率控制（requestAnimationFrame / 定时 / 事件驱动）
    - 大量参数的性能策略（虚拟滚动 / 分组折叠 / 分页）
    - 与 display feature 已有设计对齐
  - 产出：实时展示层架构方案

  **Agent 16：暗色模式 + 主题策略**
  - 输入：Agent 5（token 现状）+ Agent 7（Quasar 参考）
  - 分析：
    - 是否需要暗色模式（工业监控通常暗色更常见）
    - token 体系是否已支持主题切换
    - Quasar dark mode 与 CSS token 的协调方式
    - 状态色在亮/暗模式下的表现
  - 产出：主题策略建议

  ### 批次 3：自检（3-4 个 agent）

  **Agent 17：旧行为覆盖度检查**
  - 逐项检查旧系统每个页面行为在新 UI 架构中是否有对应
  - 标注：覆盖 / 合并 / 降级 / 删除+原因
  - 特别关注：旧系统有但新架构可能遗漏的操作入口

  **Agent 18：过度设计审查**
  - 按 CLAUDE.md 过度设计审查 5 维度检查 UI 架构：
    - 上游消费：feature 提供的数据 vs 页面需要展示的数据，粒度匹配
    - 下游需求：用户真正需要的页面 vs 设计的页面，有没有"可能需要"的页面
    - 驱动需求真实性：每个布局模式是否有旧行为支撑
    - 链路位置：共享 widget 放 widgets/ vs features/ 内部组件，位置是否合适
    - 跨页面一致性：同类交互（列表CRUD、表单保存）在不同页面是否一致

  **Agent 19：前端规范合规检查**
  - 用 rewrite-frontend-checklist.md 逐项检查 UI 架构设计
  - 标注每条规则的合规状态
  - 列出冲突点和解决方案

  **Agent 20：跨 feature 标识对齐检查（CLAUDE.md 新增项）**
  - 检查 UI 层使用的标识（页面路由、组件 key、列表 ID）是否与 feature 层的标识对齐
  - 特别是：页面路由设计是否与 feature 归口对齐
  - 组件 props 传递是否引入新的标识映射层

  ### 批次 4：收口（1 个 agent）

  **Agent 21：跨验证与冲突汇总**
  - 检查批次 2 和批次 3 之间的矛盾
  - 检查与 display-ui-design 已有设计是否冲突
  - 检查与 CSS token 现状是否匹配
  - 汇总所有 open question

  ## brainstorm 产出要求

  brainstorm 文档按 CLAUDE.md 三轮自检结构：

  1. **事实层**
     - 旧系统页面行为完整清单
     - 新系统 UI 现状
     - 外部参考精华（不是全抄，只提取适用的）
     - 规范约束汇总
  2. **决策层**（每条用"现状 → 变化"两段式）
     - D1：导航体系方案
     - D2：布局骨架方案
     - D3：共享 widget 划分
     - D4：实时数据展示架构
     - D5：主题/暗色模式策略
     - D6：页面清单与优先级
  3. **自检层**
     - R1：所有布局假设有外部参考或旧行为支撑
     - R2：旧页面行为逐项覆盖
     - R3：边界场景（窗口缩放、多连接、无数据、加载中、错误态）

  ## design 产出要求

  - 只写结论和变化，不重复 brainstorm 分析过程
  - 包含：
    - 页面清单表格（名称、路由、feature、布局模式、优先级）
    - 导航结构图（ASCII 或文字描述）
    - 布局骨架图（2-3 种典型布局的 ASCII mockup）
    - 共享 widget 清单（名称、用途、接口草案）
    - 路由表草案
  - checklist.yaml 格式的验收清单
  - 标注哪些需要 manual validation（布局/交互）vs runtime validation（性能）

  ## 硬约束

  - 所有设计必须符合 rewrite-frontend-conventions.md
  - 样式必须消费 CSS token，不硬编码颜色/间距
  - 不为"未来可能的需求"设计页面
  - 不讨论单个页面的具体表单/表格字段设计（后续逐页面设计时做）
  - display 页面已设计，本轮不推翻但检查对齐
  - 导航和布局方案最多给 3 个备选，必须推荐一个
  - 实时更新不能阻塞 UI
  - 桌面端优先，不考虑移动端适配
