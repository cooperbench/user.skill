### 四、Feature Public API 消费规则

**10 条核心规则：**

1. **默认边界**：feature root `index.ts` 是默认外部导入边界
2. **能力导向**：root export 应保持能力导向——reader、service、selector、validation result、只读快照、常量和稳定的公共类型
3. **读写分离**：外部可调 `create*Reader`（只读流）和 `create*Service`（变更流），但不得持有或修改 feature state 容器
4. **显式结果**：变更结果应作为显式操作结果处理（ok/validation/snapshot/error），UI 应从返回的 read model 推导显示状态
5. **只读输入**：read model 和 snapshot 是展示和编排的输入，不是写入 feature 事实的权限
6. **Runtime 创建权**：runtime 可在需要时创建服务和适配器（生命周期、测试替换、平台资源装配），页面不应创建适配器支持的服务
7. **同 feature composable**：同 feature 页面可使用 feature 拥有的 UI composable（明确限定为 UI 投影和 service 调用）
8. **Widget 只读**：widget 应接收已成型的 props 或 UI 快照，不应调用写服务
9. **新增操作**：如 feature 需暴露新外部操作，应先更新 feature design/checklist
10. **内部 subpath 禁止**：如消费者需要导入内部 subpath，这是设计异味——要么提升窄 public API，要么将 UI 移入 owning feature

### 五、UI 快照与 Feature 状态分离

**三层命名模型：**

| 层级 | Owner | 写入规则 | 典型示例 |
|------|-------|---------|----------|
| **Feature core state** | Owning feature state/service | 只有 owning feature service/state 写入 | frame asset collection、settings snapshot、storage local records |
| **Feature read model** | Owning feature selectors/readers | 从 feature core state 或显式 feature 输出派生；消费者只读 | frame summaries、field reference options、CSV export preference |
| **UI snapshot** | Page、feature UI composable 或 widget boundary | UI 只写展示关心；永不回写为 feature truth | 搜索文本、筛选、分页、选中标签、对话框草稿、loading 状态 |

**关键规则：**
- UI 快照可以整形数据以供展示（排序、筛选、分页、虚拟滚动、节流、临时错误）
- UI 快照不能定义任务是否成功、设备是否连接、接收值含义、报告是否有效、交付是否成功
- Feature service 返回在 page/composable 边界转换为 read model 或 UI 快照
- 高频数据只能以节流 read model 或 UI 快照进入页面；页面/ widgets 不得订阅底层包事件
- 如 widget 需要多个 feature 的数据，page/runtime 应先组合只读 view model 再传 props 给 widget

### 六、Feature 交互矩阵核心原则

#### 6.1 交互候选类型

- **`public service`**：调用目标 feature 明确公开的用例入口或 command/query service
- **`selector`**：读取目标 feature 公开的只读 snapshot/read model/asset selector
- **`runtime orchestration`**：由 `runtime/` 装配多个公开入口、处理生命周期、顺序和边界路由
- **`explicit event`**：异步、多消费者、高频、结果通知或跨域解耦需要的显式事件

#### 6.2 全局禁止项（对所有后续 cs-feat-design 生效）

```
✗ feature 之间 import 对方内部 state
✗ feature 绕过 public API import 对方内部 service/adapter/composable/私有 helper
✗ 统计 read model 写回 frame definition/field definition/表达式/展示配置
✗ receive/send/task/SCOE/result/report/northbound 的领域规则放进 runtime/
✗ runtime/ 变成全局业务中心
✗ main 承载业务语义（只能承接平台资源、生命周期和高频缓冲/批处理/背压）
✗ renderer 直接访问 Node/Electron/ipcRenderer/fs/path/net/serialport
✗ preload 暴露裸 invoke/send/on 或大而全能力包
✗ widgets 直接调用 feature 内部 composable 或内部 state
✗ pages 拥有协议语义/任务推进/平台访问/报告语义/跨 feature 内部状态写入
✗ storage/history/CSV/local export 等同 TestReport 或 northbound delivery closure
✗ SCOE 固定 source/target 沉积在通用 receive/send 主链
```

#### 6.3 高频与异步处理原则

**优先使用显式事件的场景：**
- `connection → receive`：入站 bytes/batches 是高频异步输入，需队列/背压/事件顺序验证
- `receive → task/status/result/storage/SCOE`：receive result/delta 可能有多消费者，不能同步堆副作用
- `receive → display`：display 刷新可能高频且面向 UI-safe snapshot，需节流/合批/背压边界
- `send → task/status/result/storage/SCOE`：send result 是结果通知，多消费者各写自己的 read model
- `task → result/report/northbound/status`：lifecycle transitions 应作为显式状态输出
- `result → report/northbound/status`：result finalization 是下游生成报告和外部投影的触发点

## 核心约束总结

**Runtime Bootstrap 的黄金法则：**
1. **薄装配**：runtime 是轻量组合根，不是重业务中心
2. **显式依赖**：通过构造函数/工厂函数/明确 context 传入依赖，便于测试替换
3. **单向数据流**：feature core state → feature read model → UI snapshot，不反向写入
4. **边界例外显式登记**：SCOE、高速存储、northbound 等例外必须记录在案
5. **验证层级严格分离**：static/fixture/manual < runtime < package < hardware/customer

**Feature Wiring 的黄金法则：**
1. **Public API 唯一入口**：外部只从 feature root import，禁止导入内部 subpath
2. **读写分离**：reader 只读、service 写入、结果显式返回
3. **UI 不持有事实**：页面/ widgets 只管理 UI snapshot，不拥有运行主状态
4. **高频异步事件化**：高频、多消费者、跨域场景优先用显式事件
5. **跨域必须通过 runtime 或显式事件**：禁止 feature 之间直接 import 内部 state

这些约束确保了重写后的架构具有清晰的边界、可测试性和可维护性。
