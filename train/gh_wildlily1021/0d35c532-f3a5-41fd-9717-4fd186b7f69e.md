24	## 1. 决策与约束
25	
26	### 需求摘要
27	
28	- **做什么**：在 `runtime/` 层创建 feature service 实例、桥接适配器和路由函数，把 frame/connection/receive/send/task/settings + storage-local-baseline 串成可运行的数据通路。
29	- **为谁**：为后续 pages/widgets/runtime facade 消费；为集成测试和手动验证提供可运行的 runtime。
30	- **成功标准**：
31	  1. `createRewriteRuntime()` 返回的 runtime 包含所有 feature service 引用
32	  2. `routingTick()` 能将 connection data 事件经 receive 解析后触发 task 条件匹配
33	  3. task 的 send-step 能通过 send service + connection 写出
34	  4. 现有 overview snapshot 和 resetSettings 向后兼容
35	  5. build + lint 通过
36	- **明确不做**：
37	  - 不接 platform/preload/main 真实能力，只用 fake adapter
38	  - 不做 UI
39	  - 不引入 Pinia 或全局 store
40	  - 不接 SCOE/result/report/northbound/status/display
41	  - 不实现定时器调度、运行时 settings 变更推送、打包态 data path
42	  - 不实现重试/退避/断路器
43	  - runtime 不持有任何可变业务 state
44	  - runtime 不使用 setTimeout/setInterval

46	### 复杂度档位
47	
48	走内部工具默认档位，无偏离。
49	
50	### 关键决策
51	
52	**D1: 无状态 routingTick 函数，不建 EventRouter 状态机**
53	
54	runtime 保持 composition root 本色。路由逻辑是无状态函数 `routingTick(features): RoutingTickResult`，由外部（app、测试、或未来 platform callback）决定何时调用。
55	
56	为什么不用 EventRouter 状态机：EventRouter 引入调度器、运行状态、start/stop 生命周期，使 runtime 变成 mini 事件总线，越过 composition root 边界。当真实 platform 提供推送能力时，EventRouter 的 pollIntervalMs、RoutingStats、tick 管理全部是 throwaway。
57	
58	换回 EventRouter 会怎样：runtime 变为有状态调度层，与 architecture 定义的"只做装配、生命周期、事件路由、边界例外登记"的薄层定位冲突。
59	
60	**D2: 桥接 adapter 不直接持有 ConnectionTransportAdapter**
61	
62	ConnectionToReceiveInputSource 接收 ConnectionService.drainAdapterEvents() 返回的已处理事件，做纯格式转换。不持有 adapter 引用，不与 ConnectionService 竞争事件队列。
63	
64	如果桥接 adapter 直接调 adapter.drainEvents()：ConnectionService 的 state 不会更新（counters、event history、lastError 丢失），非 data 事件被桥接 adapter 吃掉。
65	
66	**D3: 3 层 wiring 而非 5 层**
67	
68	实际依赖关系只有 3 个层级边界：
69	- L0（无互依赖）：frame, settings, storage-local-baseline
70	- L1（需 adapter）：connection
71	- L2（需 L0+L1）：receive, send（可并行）
72	- L3（需 L2）：task + ReceiveEventSourceBridge
73	
74	每层内 feature 互相独立，可以并行创建。
75	
76	**D4: 错误处理——失败即停，返回错误结果**
77	
78	routingTick 中每步检查 outcome.ok。失败时在返回值中记录错误，跳过后续步骤。不做重试、退避或断路。
79	
80	**D5: lifecycle 合并到 index.ts，不单独建模块**
81	
82	D1 简化后 lifecycle 只剩 init（wireFeatures）和 destroy（cleanup + bridge.clear），不需要独立文件。直接在 index.ts 的 `createRewriteRuntime` 和新增的 `destroy` 方法中处理。
83	
84	**D6: bridge adapter 集中在 runtime/bridges/ 子目录**
85	
86	当前 4 个 bridge（connection→receive、send→connection、receive→task、frame→send），后续加 status/display/result 时会到 8-10 个。集中在 `runtime/bridges/` 避免全塞在 feature-wiring.ts 里。
87

195	**ConditionMatchInput 提取规则：**
196	
197	```
198	遍历 receiveOutcome.outcomes 中 kind==='matched' 的每条
199	  → 遍历该 outcome.fields 中每个 ReceiveParsedFieldValue
200	  → 每个字段生成一个 {frameId: outcome.matchedFrame.frameId, fieldId: field.fieldId, value: field.value, sourceId: outcome.input?.sourceId}
201	```
202	一个 matched outcome 可能产生多个 ConditionMatchInput（每个解析出的字段一个）。bridge 发全部字段，不做筛选——task 的 condition-matcher 内部做过滤。

204	### 2.2 编排层
205	
206	#### 主流程图
207	
208	```mermaid
209	sequenceDiagram
210	    participant App as App / Test
211	    participant RW as createRewriteRuntime
212	    participant FW as FeatureWiring
213	
214	    App->>RW: createRewriteRuntime()
215	    RW->>FW: wireLevel0() → frame, settings, storage
216	    RW->>FW: wireLevel1(adapter) → connection
217	    RW->>FW: wireLevel2(L0, L1) → receive, send
218	    RW->>FW: wireLevel3(L2) → task + bridge
219	    RW-->>App: runtime { features, routingTick, getOverview, ... }
220	
221	    App->>RW: routingTick()
222	    RW->>RW: connectionService.drainAdapterEvents()
223	    alt ok=false
224	        RW-->>App: {ok: false, error: ...}
225	    else has data events
226	        RW->>RW: ConnectionToReceiveInputSource(dataEvents)
227	        RW->>RW: receiveService.drainInputSource(source)
228	        alt has matched outcomes
229	            RW->>RW: extract ConditionMatchInput[]
230	            RW->>RW: receiveEventSourceBridge.emit(inputs)
231	        end
232	        RW-->>App: {ok: true, eventsRouted, matchesEmitted}
233	    end
234	
235	    App->>RW: destroy()
236	    RW->>RW: connectionService.cleanup()
237	    RW->>RW: receiveEventSourceBridge.clear()
238	```

240	#### 现状
241	
242	runtime/index.ts 的 `createRewriteRuntime` 只做一件事：创建 3 个 feature 的只读端口，聚合为 overview snapshot。无启动/销毁流程，无事件路由，无跨 feature 调用。拓扑是单函数线性初始化。
243	
244	#### 变化
245	
246	在 runtime/ 下新增 bridges/ 子目录 + 2 个模块 + 重构 1 个：
247	
248	1. **bridges/**：4 个 bridge adapter 文件，各实现一个跨 feature 桥接。
249	2. **feature-wiring.ts**：3 层创建 + bridge 装配。拓扑从单函数线性初始化变为分层 DAG（L0→L1→L2→L3）。
250	3. **routing-tick.ts**：无状态路由函数。拓扑是线性 pipeline（drain → filter → convert → drain receive → extract → emit），每步有错误检查。
251	4. **index.ts**：从"直接聚合 reader"变为"委托 wiring + routingTick"。保持向后兼容的 overview/resetSettings 接口，新增 features 暴露、routingTick 方法、destroy 方法。
252	
253	#### 跨层纪律
254	
255	- **错误语义**：routingTick 中每步失败在返回值中记录 error，跳过后续步骤，不抛异常。feature service 本身的错误由各 feature 的 outcome/result 承载。
256	- **幂等性**：drainAdapterEvents 和 drainInputSource 是 drain 语义（取后清空），天然幂等。destroy() 可重复调用（再调用无副作用）。
257	- **并发/顺序**：当前阶段所有操作在主线程 await 串行执行。routingTick 不做并发保护——调用方负责不在上一 tick 未完成时发起下一 tick。
258	- **扩展点**：ConnectionTransportAdapter 注入点（fake → real 切换不改动 wiring 逻辑）。ReceiveEventSourceBridge 可被替换。未来 platform callback 可直接调用 routingTick。
259	- **可观测点**：RoutingTickResult 暴露 ok/error/eventsRouted/matchesEmitted。

322	- 输入：connectionService.drainAdapterEvents() 返回 `ok: false`
323	- 期望：routingTick 返回 `{ok: false, error: '...'}`，receive drain 和 bridge emit 不执行

325	**S6: 生命周期——destroy**
326	- 输入：runtime.destroy()
327	- 期望：connectionService.cleanup() 被调用，bridge.clear() 被调用

329	**S7: 向后兼容——overview snapshot**
330	- 输入：createRewriteRuntime() 无参数
