287	
288	#### H14. API 调用统一通过 useQuery / useMutation
289	
290	不使用原始 `fetch` 或直接调用 SDK 函数做数据查询。下拉选项等场景也必须用 `useQuery`，TanStack Query 会自动缓存去重。

300	#### H15. 不使用 `onError` 处理 API 错误
301	
302	全局 HTTP 拦截器已统一处理错误提示。在 `useQuery` / `useMutation` 中写 `onError` 会导致双重处理（用户看到两次 toast）。
303	
304	```typescript
305	// ❌ — 双重错误提示

307	  ...adminTemplateUpdateMutation(),
308	  onSuccess: () => { toast.success('修改成功'); },
309	  onError: (err) => { toast.error(err.message); }, // 全局拦截器已经 toast 了

312	// ✅ — 只处理成功，错误交给全局拦截器
313	const { mutate } = useMutation({
314	  ...adminTemplateUpdateMutation(),
315	  onSuccess: () => { toast.success('修改成功'); },

329	};

331	// ✅ — FormDialog 只负责自己

335	  emit('success');

346	## 经验规则
347	
348	### 组件拆分时机
349	
350	#### E1. 超过 250 行时主动评估拆分
351	
352	不要等到 300 行红线。拆分信号：
353	
354	- 模板中有 3 个以上逻辑独立的区域
355	- 有重复的 DOM 结构出现两次以上
356	- 有独立的加载 / 错误 / 空状态处理
357	- `script setup` 中有超过 3 段不相关的逻辑
358	
359	### 页面组件职责
360	
361	#### E2. 页面文件只做数据获取 + 布局编排
362	
363	`pages/` 下的文件不应包含复杂业务逻辑。业务逻辑提取到 composable 或 business 组件。
364	
365	```vue
366	<!-- ❌ — 页面文件 200 行数据处理逻辑 -->
367	<script setup lang="ts">
368	// 各种 filter、transform、业务判断...
369	</script>
370	
371	<!-- ✅ — 页面只做编排 -->
372	<script setup lang="ts">
373	const { data, isLoading } = useQuery(...);
374	const { mutate } = useMutation(...);
375	const columns = createColumns({ onEdit, onDelete });
376	</script>
377	```
378	
379	### 条件查询
380	
381	#### E3. 弹窗/条件面板内的查询使用 `enabled` 控制
382	
383	避免组件挂载时就发无用请求。
384	
385	```typescript
386	// ❌ — 弹窗未打开就发请求
387	const { data } = useQuery(adminXxxListAllOptions());
388	
389	// ✅ — 弹窗打开时才查询
390	const { data } = useQuery(
391	  computed(() => ({
392	    ...adminXxxListAllOptions(),
393	    enabled: dialogOpen.value,
394	  })),
395	);
396	```

398	### 抽取时机
399	
400	#### E4. 不要过早提取
401	
402	不是所有重复都需要立刻消除：
403	
404	- 只出现两次，且变化节奏不同
405	- 提取后需要传大量 props / emit（组件接口反而更复杂）
406	- "相似"但语义不同（只是恰好长得像）
407	
408	遵循三次法则：等第三次出现再提取。提取前先检查 `components/common/` 是否已有可复用组件。

411	
412	#### E5. 使用语义化颜色 + CSS 禁令
413	
414	使用 shadcn 语义化 CSS 变量（`text-destructive`、`text-muted-foreground` 等），不直接写色值。
415	
416	```vue
417	<!-- ❌ -->
418	<span class="text-red-500">错误</span>
419	<span class="text-gray-500">次要信息</span>
420	
421	<!-- ✅ -->
422	<span class="text-destructive">错误</span>
423	<span class="text-muted-foreground">次要信息</span>
424	```

427	
428	| 禁止 | 原因 |
429	|------|------|
430	| 引入第二个 CSS 引擎（UnoCSS / WindiCSS） | 项目只用 TailwindCSS |
431	| 创建第二套 CSS 变量 | 所有变量在 `:root` 和 `.dark` 中统一定义 |
432	| 使用 SCSS | 不需要嵌套语法时不引入额外编译器 |
433	| 硬编码 z-index | 如需多层级管理，定义 CSS 变量 |

435	### 数据不可变性
436	
437	#### E6. 修改 props 传入的对象前必须深拷贝
438	
439	直接修改 props 对象违反单向数据流，会导致难以追踪的 bug。
440	
441	```typescript
442	// ❌ — 直接修改 props 对象
443	function handleUpdate(row: Item) {
444	  row.status = 'active';
445	}
446	
447	// ✅ — 深拷贝后修改
448	function handleUpdate(row: Item) {
449	  const updated = structuredClone(row);
450	  updated.status = 'active';
451	  mutate(updated);
452	}
453	```

469	### 全局状态
470	
471	#### E8. 全局 composable 有清晰的 scope / owner 管理
472

491	#### T1. `<Teleport>` 必须加 `defer` 属性
492	
493	初始页面加载时挂载点可能还没渲染，不加 `defer` 会崩溃。
494	
495	```vue
496	<!-- ❌ — 挂载点不存在时报错 -->

498	
499	<!-- ✅ -->
500	<Teleport defer to="#header-actions">
501	```
502	
503	#### T2. `SelectItem` 的 value 必须是非空 string
504	
505	传数字或空字符串会导致组件行为异常（选中不回显、清不掉等）。
506	
507	```vue
508	<!-- ❌ -->
509	<SelectItem :value="0">禁用</SelectItem>
510	<SelectItem :value="">请选择</SelectItem>
511	
512	<!-- ✅ -->
513	<SelectItem value="0">禁用</SelectItem>
514	<SelectItem value="_none_">请选择</SelectItem>
515	```
516	
517	#### T3. `setTabs` 的 `tabOwner` 不能用 `computed`
518	
519	`onUnmounted` 执行时路由参数已变，computed 会算出错误的 owner，导致 `clearTabs` 匹配失败、tabs 残留。必须在 setup 时用固定字符串赋值。
520	
521	```typescript
522	// ❌
523	const tabOwner = computed(() => `/admin/domain/${id.value}`);
524	
525	// ✅
526	const tabOwner = `/admin/domain/${id.value}`;
527	```
528	
529	#### T4. `watch` 外部数据源（useQuery 结果）无条件覆盖表单
530	
531	服务端数据刷新后覆盖用户正在编辑的内容。
532	
533	```typescript
534	// ❌ — 每次服务端数据变化都覆盖表单
535	watch(data, (newData) => {
536	  if (newData) setValues(newData);
537	});
538	
539	// ✅ — 加防护，只在首次加载时填充
540	const hasLoaded = ref(false);
541	watch(data, (newData) => {
542	  if (newData && !hasLoaded.value) {
543	    setValues(newData);
544	    hasLoaded.value = true;
545	  }
546	});
547	```
548	
549	#### T5. Vite HMR 对递归组件有 bug
550	
551	修改递归组件（如树）后 HMR 表现诡异，子层级卡旧缓存。修改后必须 `F5` 硬刷新页面。
552	
553	#### T6. 列表行内放交互式 Checkbox 导致事件冒泡死锁
554	
555	行点击和 Checkbox 点击互相触发。改用纯 CSS + SVG（如 `<Check>` 图标）渲染视觉假 Checkbox，由整行统管点击事件。

51	## 4. Hard Rules
52	
53	### R1. Preserve behavior, replace structure
54	
55	MUST:
56	
57	- 默认保留旧系统用户可见能力。
58	- 只在明确低价值、高成本、冲突或旧占位时，才把功能列入排除候选。
59	- 将旧功能重写到新的边界中，而不是把旧目录、旧 store 和旧 IPC 复制一遍。
60	
61	MUST NOT:
62	
63	- 因为质量规则而顺手砍旧功能。
64	- 把“旧代码很脏”理解成“旧行为不重要”。
65	- 把未讨论的功能降级成 future work。
66	
67	### R2. Feature ownership must be explicit
68	
69	MUST:
70	
71	- 按 `features/frame`、`connection`、`receive`、`send`、`task`、`scoe`、`storage`、`settings`、`status`、`result`、`report`、`northbound` 归口业务能力。
72	- 每个 feature 只能直接修改自己的状态。
73	- 跨 feature 流程必须通过公开 service、runtime 编排、显式事件或边界输入输出发生。
74	- 每个 feature 的外部入口必须明确；外部只能通过 public API 调用，不直接依赖内部实现。
75	
76	MUST NOT:
77	
78	- feature A 直接 import feature B 的内部 `state` 并修改。
79	- feature A 直接 import feature B 的内部 service、adapter、composable 或私有 helper。
80	- 用一个大 store 同时承载主状态、展示态、缓存态、任务调度和多下游副作用。
81	- 让页面组件长期持有运行主状态或任务生命周期事实。
82	
83	### R3. Core logic must be testable TypeScript
84	
85	MUST:
86	
87	- 将 receive 解析、send 构帧、SCOE 协议、task 状态推进、storage 迁移、result/report 生成等核心规则放在可测试的 TypeScript 层。
88	- `features/*/core` 不依赖 Vue、Pinia、Electron、`window.electron`、`ipcRenderer`、`fs`、`serialport`。
89	- 核心逻辑通过明确输入和输出表达行为。
90	
91	MUST NOT:
92	
93	- 把解析、构帧、协议校验、任务推进写在 Vue 组件里。
94	- 在 core 逻辑里读取全局 store 补上下文。
95	- 在 core 逻辑里直接访问平台能力。
96	
97	### R4. UI is not the business workflow owner
98	
99	MUST:
100	
101	- 页面和组件只负责用户交互、表单状态、展示和调用公开入口。
102	- 复杂流程由 feature service 或 runtime 编排承接。
103	- composable 只做 UI-facing 组合，例如表单状态、对话框状态、生命周期订阅、selector 组合和调用公开 service。
104	
105	MUST NOT:
106	
107	- UI 组件直接创建并启动任务状态机。
108	- UI 组件直接读写文件、串口、网络 socket。
109	- UI 组件直接修改其他 feature 的内部状态。
110	- UI 组件承担导入校验、任务策略分支、实例引用检查等完整业务流程。
111	- composable 承载协议解析、任务状态机、统计累加、跨域业务流程或跨 feature 写状态。

113	### R5. Electron capability boundary must stay narrow
114	
115	MUST:
116	
117	```ts
118	nodeIntegration: false
119	contextIsolation: true
120	sandbox: false
121	```
122	
123	MUST:
124	
125	- renderer 只通过 `rewrite/src/platform` facade 访问桌面能力。
126	- preload 只暴露 typed API。
127	- main 只承接平台资源访问和生命周期。
128	- main 可以承接与平台资源绑定且性能压力明显的高频数据缓冲、批处理、聚合、节流、队列和背压。
129	- 文件、串口、网络、定时器、窗口能力都要有明确 platform API。
130	
131	MUST NOT:
132	
133	- 暴露裸 `invoke/send/on`。
134	- 在 renderer 直接使用 `ipcRenderer`、`fs`、`path`、`net`、`serialport`。
135	- 把领域业务规则放进 main 进程。
136	- 把业务运算、协议语义、任务状态推进、报告语义或 northbound 领域规则搬进 main 进程。
137	- 允许任意路径读写成为常规业务 API。

139	### R6. IPC must be coarse-grained and intentional
140	
141	MUST:
142	
143	- 以业务能力为单位设计 typed platform API。
144	- 对高频串口/网络数据使用批量、缓冲、聚合或节流策略。
145	- 明确哪些数据在 main 处理、哪些结果进入 renderer。
146	- 性能处理优先使用数据流设计、队列、背压、采样和事件压缩，不用主进程业务化换取表面简单。
147	
148	MUST NOT:
149	
150	- 为每个组件动作散落一堆小 IPC。
151	- 高频字节流逐包无节制穿透到页面和全局 store。
152	- 让 IPC 通道名成为业务流程本身。
153	
154	### R7. Runtime state must have one owner
155	
156	MUST:
157	
158	- 区分主状态、派生态、展示态、记录态、缓存态。
159	- 主状态单点写入。
160	- 派生态、展示态、记录态、缓存态只能消费或展示事实，不得反向塑造主状态语义。
161	- store 只承载本 feature 的状态、read model、selector 和很薄的本域 action。
162	
163	MUST NOT:
164	
165	- 用接收缓存、页面监控状态、历史记录状态、测试工具状态替代运行主状态。
166	- 让 receive/send/SCOE/status/report 各自宣布系统当前生命周期。
167	- 让本地发送 task 直接等同甲方中心 task。
168	- 把 store 当作 service locator、跨域编排器或平台能力入口。
169	- store A 直接修改 store B 的内部 state。
170	
171	### R8. Receive and send chains must remain explicit
172	
173	MUST:
174	
175	- receive 主链只承接输入、解析、归一和输出明确接收结果。
176	- send 主链只承接发送请求、构帧、目标落地和输出发送结果。
177	- receive/send 与 task、SCOE、storage、status、result 通过显式输入输出交互。
178	
179	MUST NOT:
180	
181	- receive 主链直接决定任务生命周期。
182	- send 主链硬编码 SCOE、northbound 或 report 语义。
183	- 把显示、历史、触发、SCOE、统计继续作为 receive 解析尾部同步副作用堆在一起。
184	
185	### R9. SCOE must be a declared domain exception
186	
187	MUST:
188	
189	- 将 SCOE 作为领域模块或领域例外处理。
190	- 固定来源、固定目标、命令语义、完成条件、反馈语义、测试工具记录都应归在 SCOE 边界内。
191	- SCOE 进入 receive/send/task 时，必须通过显式领域入口、显式发送请求或显式任务请求。
192	
193	MUST NOT:
194	
195	- 把 SCOE 固定 source/target 硬编码在通用 receive/send 主链里。
196	- 让 SCOE 通过共享状态回读定义任务是否完成。
197	- 把 SCOE 测试工具记录抬成统一运行主状态。
198	
199	### R10. Northbound must be a boundary, not a feature shortcut
200	
201	MUST:
202	
203	- `northbound` 独立承接中心协同接入、对外投影、对外交付和外部错误语义。
204	- 外部任务、状态、心跳、结果、报告、文件回传都必须经过 northbound 边界转换。
205	- northbound 从 task/status/result/report/storage 读取内部事实或素材，但不得直接定义这些内部事实。
206	
207	MUST NOT:
208	
209	- 把旧 send task 当作 `setTestTask/controlTestTask`。
210	- 把 history/CSV 当作 TestReport 交付闭环。
211	- 把 serial/network target 当作 northbound device/deviceId。
212	- 把外部成功/失败/拒绝/不可执行语义散落到 task/send/report/storage 内部。
213	
214	### R11. Result, report, delivery must stay separate
215	
216	MUST:
217	
218	- `result` 归口内部结果事实。
219	- `report` 归口报告对象和报告文件生成。
220	- `northbound` 归口对外交付、回执和错误语义转换。
221	
222	MUST NOT:
223	
224	- 因为报告交付失败而反向改写内部结果事实。
225	- 在 task/send/receive 中直接拼外部报告。
226	- 把报告对象生成和 FTP/HTTP 上传写成同一个职责。
227	
228	### R12. Legacy JSON compatibility must not pollute new models
229	
230	MUST:
231	
232	- 旧 JSON 通过迁移脚本或导入适配进入新模型。
233	- 新核心类型和存储结构按重写后的业务边界设计。
234	
235	MUST NOT:
236	
237	- 为兼容旧 `framesConfig` 或旧路径常量扭曲新领域模型。
238	- 在新核心逻辑里到处判断旧 JSON 形态。
239	- 把旧 data path 直接固化为新长期存储设计。
240	
241	### R13. Statistics must not pollute source models
242	
243	MUST:
244	
245	- 将静态资产、运行事实、统计 read model 和 UI snapshot 分开。
246	- 帧定义、字段定义、表达式和展示配置等静态对象只表达配置事实。
247	- 接收命中数、最近值、错误计数、速率、发送结果等统计由对应 feature 的 read model 按稳定 key 增量维护。
248	- 高频统计更新使用 batch、delta、队列、节流或 snapshot，避免全量替换大对象。
249	- 每个统计项必须有明确 owner、reader、reset 时机、生命周期、是否持久化和验证方式。
250	
251	MUST NOT:
252	
253	- 把运行统计写回 frame list、字段定义、配置对象或其他静态资产对象。
254	- 为了页面展示把多个 feature 的状态揉成一个可写全局对象。
255	- 让页面组件订阅底层高频事件并参与统计累加。
256	- 通过全局事件总线隐式修改其他 feature 的内部 state。
257	- 用全量刷新 frame array 或大 store 对象响应每次接收/发送事件。
258	
259	### R14. Services and dependency wiring must stay explicit
260	
261	MUST:
262	
263	- feature service 作为业务用例入口，负责调用 core、写入本 feature store、调用 adapter 或通过公开接口协作。
264	- `runtime/` 作为组合根，负责 service、adapter 和上下文的创建、显式注入和释放。
265	- 依赖通过构造函数、工厂函数或明确 runtime context 传入，以便测试替换。
266	- 组件和页面通过 feature composable 或 runtime 页面级 API 调用公开入口。
267	
268	MUST NOT:
269	
270	- 使用全局 singleton service 到处 import。
271	- 在 store 中创建 service、保存 platform adapter 或访问 Electron/Node 能力。
272	- 组件直接 import service 内部实现并绕过 composable / runtime 入口。
273	- 为了“解耦”引入无明确生命周期、测试收益或跨域装配收益的复杂 DI 容器。
274	- 让 service 绕过公开接口直接修改其他 feature 的内部 state。
275	
276	### R15. Contracts and gate outcomes must be explicit
277	
278	MUST:
279	
280	- 每轮实现和审查必须列出 `Direct contract` 与 `Boundary guards`。
281	- 直接合同缺失、用户决策缺失、甲方口径缺失、关键 baseline 缺失时，结论必须是 `blocked`。
282	- 边界违规、跨 feature 内部写入、runtime/store/composable 业务化、main 业务化时，结论必须是 `revise-required`。
283	- `pass-with-known-gaps` 只用于语义已锁定但 runtime/hardware/customer 环境验证尚未完成的情况。
284	
285	MUST NOT:
286	
287	- 用 handoff、摘要、临时 prompt 或边界护栏替代正式直接合同。
288	- 用 `pass-with-known-gaps` 掩盖 northbound 语义、schema/枚举、task/case、deviceId、stop 状态、result/report/delivery 口径缺失。
289	- 用 build/lint 通过替代合同完整性、边界合规性或 runtime/hardware 证据。
290	
291	### R16. Rewrite infrastructure must stay minimal and explicit
292	
293	MUST:
294	
295	- 将 `rewrite/` 作为新的独立应用根目录，而不是只把源码挪到一个子目录。
296	- 新 renderer 源码落在 `rewrite/src/`，新 Electron 边界落在 `rewrite/src-electron/main/` 和 `rewrite/src-electron/preload/`。
297	- 从旧配置复用依赖类别和构建能力前，重新收缩 package scripts、Quasar entry/boot、Electron entry、public/extraResources、tsconfig、ESLint、UnoCSS、Vitest 和 auto-import 配置。
298	- 使用 Vitest 作为 `core`、`services`、`adapters`、`selectors` 的默认单测栈。
299	- 页面交互先以 manual checklist 验证；Electron runtime、package、hardware 和 customer validation 单独登记。
300	
301	MUST NOT:
302	
303	- 把旧 Quasar boot、旧 `src/api/common`、旧 `window.electron`、旧 preload 聚合、旧 main business handlers 或旧 `public` 数据目录策略原样搬入 `rewrite/`。
304	- 用 Vitest 声明 Electron runtime、打包态 package、真实串口/TCP/UDP/SCOE 硬件或 customer closure 已完成。
305	- 用 auto-import 隐藏业务依赖；若引入 auto-import，只允许 Vue、Vue Router、Pinia 等基础框架 API，禁止自动导入 feature service、platform facade、runtime、store、feature public API、adapter 或带业务 owner 的 helper。
306	
307	## 5. Boundary Exceptions
308	
309	边界例外允许存在，但必须登记。
310	
311	每个例外至少写明：
312	
313	- 例外名称。
314	- 所属 feature。
315	- 为什么不能表达为通用输入 / 输出。
316	- 正式入口。
317	- 正式输出。
318	- 消费者。
319	- 自动 fixture、手工 checklist 或 runtime validation 方式。
320	
321	已知例外候选：
322	
323	- SCOE 固定来源进入 receive。
324	- SCOE 固定目标进入 send。
325	- SCOE 领域完成条件。
326	- 高速存储命中后短路普通 receive/display/trigger 链。
327	- northbound 外部拒绝、不可执行、失败语义转换。
328	
329	## 6. Anti-Patterns
330	
331	以下模式在重写代码中默认判为质量问题：
332	
333	- 页面组件里直接写串口、网络、文件、SCOE 协议或任务状态机。
334	- store 互相 import、互相修改内部状态。

136	## TanStack Query 数据流
137	
138	### 核心原则
139	
140	1. **Query 用于查询**，Mutation 用于变更
141	2. **Pinia 只放全局认证状态**，服务端数据一律走 TanStack Query
142	
143	> API 调用的详细规则（useQuery 统一、onError 禁用、enabled 控制等）见 [前端代码质量规则](../quality/frontend.md)。
144	
145	### Query / Mutation Options (自动生成)
146	
147	`@hey-api/openapi-ts` 会从 Swagger 自动生成 TanStack Vue Query 的 `queryOptions` 和 `mutationOptions`，**不需要手动维护 Query Key**:
148	
149	```typescript
150	import {
151	  adminTemplateFindAllOptions,
152	  adminTemplateCreateMutation,
153	} from "@/api/@tanstack/vue-query.gen";
154	```
155	
156	### Query 示例
157	
158	```typescript
159	// 静态参数
160	const { data } = useQuery({
161	  ...adminTemplateFindOneOptions({ path: { id: props.id } }),
162	});
163	
164	// 响应式参数 -- 用 computed 包裹
165	const { data } = useQuery(
166	  computed(() => adminTemplateFindOneOptions({ path: { id: id.value } })),
167	);
168	
169	// 条件查询 -- 弹窗打开时才发请求
170	const { data } = useQuery(
171	  computed(() => ({
172	    ...adminXxxListAllOptions(),
173	    enabled: dialogOpen.value,
174	  })),
175	);
176	```
177	
178	### Mutation 示例
179	
180	```typescript
181	const queryClient = useQueryClient();
182	const { mutate } = useMutation({
183	  ...adminTemplateUpdateMutation(),
184	  onSuccess: () => {
185	    toast.success("修改成功");
186	    // 用 queryKey 部分匹配失效缓存
187	    queryClient.invalidateQueries({
188	      queryKey: [{ _id: "adminTemplateFindAll" }],
189	    });
190	  },
191	});
192	```
193	
194	> **invalidateQueries**: 用 `queryKey: [{ _id }]` 部分匹配即可命中所有同接口不同参数的缓存，不要用 predicate。多处调用时提取为 `const invalidateList = () => queryClient.invalidateQueries({ queryKey: [{ _id: 'xxx' }] })` 局部函数。
195	
196	### 分页数据提取
197	
198	分页 API 返回 `{ records, total, page, pageSize }`，后端 Response DTO 已定义分页 Schema，SDK 会自动推导正确类型：
199	
200	```typescript
201	const { data: rawData, isLoading } = useQuery(queryOptions);
202	const tableData = computed(() => rawData.value?.records ?? []);
203	const total = computed(() => rawData.value?.total ?? 0);
204	```

387	
388	对于所有系统枚举（如状态、分类、优先级等），**完全禁止前端硬编码 options**，必须基于后端的动态字典系统开发：

407	  />

411	    v-model="filters.statusArray"

中定义，本文不重复，只引用。\n\n**代码质量规则**（类型安全、组件行数、导入规范、业务分层）见 `codestable/quality/rewrite-quality-rules.md`。\n\n---\n\n## 1. 表格设计规范\n\n### T1. 表格使用 QTable 或基于 QTable 的项目封装组件\n\n**规则**：所有数据表格使用 Quasar `QTable` / `QMarkupTable` 或项目 `widgets/` 下基于 QTable 的封装组件。不使用第三方表格库（ag-Grid、TanStack Table 等）。\n\n**为什么**：QTable 是 Quasar 内建组件，与项目 token 体系和主题系统集成最紧密。引入第三方表格库增加 bundle 体积和主题对齐成本。\n\n**适用范围**：所有 `pages/`、`widgets/`、`features/*/components/` 中的数据表格。\n\n**反例**：\n```vue\n<!-- 使用第三方表格库 -->\n<AgGridVue :rowData=\"data\" :columnDefs=\"columns\" />\n```\n\n### T2. 列定义抽取到独立文件\n\n**规则**：列数 ≥ 3 或含自定义渲染（slot / `h()`）时，列定义必须抽取到同目录下的 `columns.ts`。\n\n**为什么**：列定义是纯数据配置，与页面逻辑分离可降低页面组件行数，提高可测试性。\n\n**适用范围**：所有 `pages/` 下的列表页。\n\n**反例**：\n```vue\n<!-- 300+ 行页面组件中内联 15 列定义 -->\n<q-table :columns=\"[\n  { name: 'id', label: 'ID', field: 'id' },\n  { name: 'name', label: '名称', field: 'name' },\n  <!-- ... 更多列 -->\n]\" />\n```\n\n### T3. 列宽分配策略\n\n**规则**：\n- 文本列（名称、描述）不设固定宽度，由内容自适应（`auto`）。\n- 状态/标签列按内容最长值设 `min-width`。\n- 操作列设固定宽度，按按钮数量计算（单按钮 ~80px，双按钮 ~140px）。\n- 序号列、选择列设固定宽度（序号 ~60px，选择列 ~48px）。\n- 不使用百分比宽度。\n\n**为什么**：桌面应用窗口可调，百分比宽度在窄窗口下挤压文本列，固定宽度可预测。\n\n**适用范围**：所有 QTable 列定义。\n\n**反例**：\n```typescript\n// 百分比宽度\n{ name: 'name', style: 'width: 30%' }\n// 超宽固定宽度导致横向滚动\n{ name: 'status', style: 'width: 300px' }\n```\n\n### T4. 排序必须服务端排序或明确标记为前端排序\n\n**规则**：\n- 数据量 > 100 行时，排序走服务端（`@request` 事件 + API 参数）。\n- 数据量 ≤ 100 行时，可使用 QTable 内建前端排序（`sort-method` / `binary-state-sort`）。\n- 不支持排序的列设置 `sortable: false`（默认值），不在 UI 上暗示可排序但实际无响应。\n\n**为什么**：前端排序在大数据集下性能差且与分页冲突，用户会困惑\"为什么排序后数据不全\"。\n\n**适用范围**：所有可排序列。\n\n**反例**：\n```vue\n<!-- 所有列都有排序箭头但只有当前页数据参与排序 -->\n<q-table :columns=\"columns\" sort-method=\"frontendSort\" />\n```\n\n### T5. 分页使用 QPagination + server-side 模式\n\n**规则**：\n- 数据量 > 50 行时，使用 QTable 的 `server-side` 模式 + `@request` 事件。\n- 分页器放在表格底部右侧，显示\"共 N 条\"+ 页码。\n- 每页条数默认 20，可选 10 / 20 / 50 / 100。\n- 数据量 ≤ 50 行时，可使用前端分页或隐藏分页器。\n\n**为什么**：桌面应用数据量通常可控，但接收帧列表等场景数据量可能很大。统一分页模式避免后续迁移。\n\n**适用范围**：所有分页数据表格。\n\n**反例**：\n```vue\n<!-- 一次加载全部数据到前端，渲染 10000 行 -->\n<q-table :data=\"allData\" :rows-per-page-options=\"[0]\" />\n```\n\n### T6. 空状态必须显式处理\n\n**规则**：表格无数据时必须展示空状态。使用 QTable 的 `no-data` slot 或项目空状态组件。\n\n**为什么**：空白表格让用户不确定\"数据为空\"还是\"加载失败\"。\n\n**适用范围**：所有数据表格。\n\n**反例**：\n```vue\n<!-- 无数据时只显示表头，内容区完全空白 -->\n<q-table :data=\"data\" :columns=\"columns\" />\n```\n\n**正例**：\n```vue\n<q-table :data=\"data\" :columns=\"columns\">\n  <template #no-data>\n    <div class=\"rw-empty-state\">\n      <q-icon name=\"o_inbox\" size=\"48px\" />\n      <p>暂无数据</p>\n    </div>\n  </template>\n</q-table>\n```\n\n### T7. Loading 态必须使用 QTable 内建 loading\n\n**规则**：数据加载时使用 QTable 的 `:loading` prop。不自行覆盖遮罩。\n\n**为什么**：QTable loading 遮罩与表格布局一体，不会因遮罩导致表格跳动。\n\n**适用范围**：所有异步数据表格。\n\n**反例**：\n```vue\n<!-- 自制 loading 遮罩 -->\n<div v-if=\"loading\" class=\"my-loading-overlay\">加载中...</div>\n<q-table v-else :data=\"data\" />\n```\n\n### T8. 行选中态使用 QTable selection + 语义 class\n\n**规则**：\n- 多选用 QTable 的 `selection=\"multiple\"` + `v-model:selected`。\n- 选中行高亮使用 `surface-selected` token 或 `rw-row-selected` 语义 class。\n- 不在行数据上添加 `selected` / `checked` 字段管理选中态。\n\n**为什么**：QTable 内建选中管理处理了键盘、Shift 多选等交互。自己管理容易遗漏边界情况。选中态走 token 保证主题一致性。\n\n**适用范围**：所有需要行选择的表格。\n\n**反例**：\n```typescript\n// 在数据对象上添加选中标记\nrows.forEach(row => { row._selected = false; });\n// 硬编码选中背景色\n:style=\"{ background: selectedRows.includes(row) ? '#e8f1ff' : '' }\"\n```\n\n---\n\n## 2. 表单设计规范\n\n### F1. 表单使用 QForm + Quasar 表单组件\n\n**规则**：所有表单使用 `QForm` + Quasar 表单组件（QInput、QSelect、QToggle、QField 等）。不混用 HTML 原生表单元素。\n\n**为什么**：Quasar 表单组件内建验证、label、hint、error slot、dense 模式，与 QForm 的 `validate()` / `reset()` 协同。\n\n**适用范围**：所有表单场景，含弹窗内表单、页面内表单、行内编辑。\n\n**反例**：\n```vue\n<!-- 混用原生 HTML 表单元素 -->\n<form @submit.prevent=\"submit\">\n  <input v-model=\"name\" type=\"text\" />\n  <select v-model=\"type\">...</select>\n</form>\n```\n\n### F2. 校验规则使用 QForm rules 或 feature service 校验\n\n**规则**：\n- 简单校验（必填、长度、格式）使用 QInput/QSelect 的 `:rules` prop。\n- 复杂校验（跨字段、业务规则）在 feature service 层执行。\n- 校验时机：`lazy` 模式（失焦校验）或 `submit` 时统一校验。\n- 不使用第三方校验库（vee-validate 等）。\n\n**为什么**：QForm rules 覆盖桌面应用绝大多数校验场景。引入额外校验库增加复杂度和 Quasar 集成成本。\n\n**适用范围**：所有表单校验。\n\n**反例**：\n```typescript\n// 手写校验函数散落在组件中\nconst validateName = (val: string) => {\n  if (!val) return '请输入名称';\n  if (val.length > 50) return '名称不超过50字';\n  return true;\n};\n// 但没有接入 QForm，靠 onSubmit 手动调一遍所有校验函数\n```\n\n### F3. 错误提示必须使用组件 error slot / bottom-slots\n\n**规则**：\n- 校验错误信息通过 QInput/QSelect 的 `:error` + `:error-message` 或 `bottom-slots` 展示。\n- 错误信息文字使用 `status-danger` token 色。\n- 不使用 QTooltip、floating div 或 toast 展示校验错误。\n\n**为什么**：行内错误提示位置固定，用户视线不需要跳转。toast 用于异步操作反馈，不适合校验错误。\n\n**适用范围**：所有表单校验错误展示。\n\n**反例**：\n```vue\n<!-- 用 toast 显示校验错误 -->\n<q-input v-model=\"name\" />\n<!-- on submit: if (!name.value) toast.error('请输入名称') -->\n\n<!-- 用浮动 div -->\n<q-input v-model=\"name\" />\n<div v-if=\"!name\" class=\"text-red-500 absolute -bottom-6\">请输入名称</div>\n```\n\n### F4. 禁用态必须视觉明确\n\n**规则**：\n- 不可编辑字段使用 QInput 的 `readonly` 或 `disable` prop。\n- `disable`：字段灰显且不可聚焦（用于条件性隐藏交互）。\n- `readonly`：字段正常显示但不可编辑（用于展示型字段）。\n- 不通过 CSS `opacity` / `pointer-events` 自行模拟禁用态。\n\n**为什么**：Quasar 的 disable/readonly 有正确的 ARIA 属性和键盘行为。CSS 模拟缺少无障碍语义。\n\n**适用范围**：所有有条件禁用的表单字段。\n\n**反例**：\n```vue\n<!-- CSS 模拟禁用 -->\n<q-input v-model=\"value\" class=\"opacity-50 pointer-events-none\" />\n```\n\n### F5. 表单提交防重复\n\n**规则**：提交按钮在请求进行中必须 disable 或显示 loading。使用 mutation 的 `isPending` / service 的 loading 状态控制。\n\n**为什么**：防止用户快速双击或网络慢时重复提交。\n\n**适用范围**：所有表单提交按钮。\n\n**反例**：\n```vue\n<!-- 提交按钮无状态保护 -->\n<q-btn label=\"提交\" @click=\"submit\" />\n```\n\n**正例**：\n```vue\n<q-btn label=\"提交\" :loading=\"isSubmitting\" @click=\"submit\" />\n```\n\n---\n\n## 3. 页面布局规范\n\n### L1. 页面结构三段式\n\n**规则**：列表页结构分为工具栏区、内容区、可选的底部操作区。使用语义化容器 class。\n\n```\n┌─────────────────────────────┐\n│ 工具栏（筛选、操作按钮）       │\n├─────────────────────────────┤\n│ 内容区（表格/卡片/详情）       │\n├─────────────────────────────┤\n│ 底部操作区（分页、批量操作）    │  ← 可选\n└─────────────────────────────┘\n```\n\n**为什么**：固定布局结构降低页面间认知负担，用户在不同页面间切换时能快速定位操作区域。\n\n**适用范围**：所有列表页、详情页。\n\n### L2. 页面内边距使用 `page` / `page-compact` spacing token\n\n**规则**：\n- 页面内容区内边距使用 `rw-space('page')`（24px）或 `rw-space('page-compact')`（16px）。\n- 密集数据页面（帧列表、监控）使用 compact。\n- 设置页、表单页使用 page。\n- 不硬编码 `16px` / `24px` / `32px`。\n\n**为什么**：spacing token 保证页面间距一致。修改间距只需改 token 值。\n\n**适用范围**：所有页面级容器。\n\n**反例**：\n```vue\n<div class=\"q-pa-lg\"><!-- 使用 Quasar 间距 class，不经过 token --></div>\n<div style=\"padding: 20px;\"><!-- 硬编码 --></div>\n```\n\n### L3. 侧边栏使用 QDrawer + 固定宽度 token\n\n**规则**：\n- 侧边栏使用 `QDrawer`。\n- 宽度使用 `rw-size('app-drawer')` token（232px）。\n- 侧边栏内容使用 `QList` + `QItem` 构建导航。\n\n**为什么**：QDrawer 提供响应式折叠、mini 模式、overlay 模式。固定宽度保证内容区稳定。\n\n**适用范围**：应用主布局侧边栏。\n\n**反例**：\n```vue\n<!-- 自己实现侧边栏 -->\n<div class=\"sidebar\" style=\"width: 200px;\">...</div>\n```\n\n### L4. 工具栏与内容区间距一致\n\n**规则**：工具栏（筛选行、操作行）与下方内容区间距使用 `rw-space('4')`（16px）。工具栏内部元素间距使用 `rw-space('2')`（8px）。\n\n**为什么**：一致的间距让页面呼吸感均匀。\n\n**适用范围**：所有含工具栏的页面。\n\n### L5. 弹窗使用 QDialog + 语义宽度 class\n\n**规则**：\n- 弹窗使用 `QDialog`。\n- 弹窗宽度通过语义 class（如 `rw-dialog-sm` / `rw-dialog-md` / `rw-dialog-lg`）或 token 控制，不硬编码 `width`。\n- 弹窗内容使用 `QCard` 包裹，含 `QCardSection` 头部 + 内容 + 操作区。\n- 不使用 `window.alert` / `window.confirm`。\n\n**为什么**：QDialog 与 Quasar 主题一致，支持 transition、maximized、persistent 等桌面场景。\n\n**适用范围**：所有弹窗。\n\n**反例**：\n```vue\n<!-- 硬编码弹窗宽度 -->\n<q-dialog>\n  <q-card style=\"width: 600px; max-width: 80vw;\">\n```\n\n**正例**：\n```vue\n<q-dialog>\n  <q-card class=\"rw-dialog-md\">\n```\n\n---\n\n## 4. Quasar 组件使用规范\n\n### Q1. 组件选型优先使用 Quasar 内建组件\n\n**规则**：UI 需求优先从 Quasar 组件库寻找方案。只在 Quasar 无法满足时才引入第三方组件。\n\n**为什么**：减少依赖体积，保证主题一致性，减少升级维护成本。\n\n**适用范围**：所有 UI 组件选型。\n\n**常见映射**：\n\n| 需求 | Quasar 组件 |\n|------|------------|\n| 按钮 | `QBtn` |\n| 输入框 | `QInput` |\n| 下拉选择 | `QSelect` |\n| 开关 | `QToggle` |\n| 表格 | `QTable` |\n| 弹窗 | `QDialog` |\n| 通知 | `Notify` quasar plugin |\n| 确认对话框 | `Dialog` quasar plugin |\n| 标签页 | `QTabs` + `QTabPanels` |\n| 工具提示 | `QTooltip` |\n| 徽章 | `QBadge` |\n| 进度 | `QLinearProgress` / `QCircularProgress` |\n| 加载 | `QSpinner` / `QInnerLoading` |\n| 日期 | `QDate` |\n| 时间 | `QTime` |\n| 文件选择 | `QFile` |\n| 分割线 | `QSeparator` |\n| 折叠面板 | `QExpansionItem` |\n| 树 | `QTree` |\n\n### Q2. 禁止在 QBtn 上硬编码颜色\n\n**规则**：\n- 使用 Quasar brand 色：`color=\"primary\"` / `color=\"negative\"` / `color=\"positive\"` 等。\n- 次要操作使用 `flat` / `outline` variant。\n- 不在 style 或 class 中硬编码按钮颜色。\n\n**为什么**：Quasar brand 色通过 `$primary` 等 Sass 变量统一管理，修改主题只需改一处。\n\n**适用范围**：所有 QBtn 使用。\n\n**反例**：\n```vue\n<q-btn style=\"background: #1f6feb; color: white;\" label=\"提交\" />\n<q-btn class=\"bg-blue-600 text-white\" label=\"提交\" />\n```\n\n**正例**：\n```vue\n<q-btn color=\"primary\" label=\"提交\" />\n<q-btn flat color=\"primary\" label=\"取消\" />\n```\n\n### Q3. 确认对话框使用 Quasar Dialog plugin\n\n**规则**：\n- 简单确认使用 `Quasar.dialog()` plugin。\n- 复杂确认（级联删除、二次确认）使用项目封装的确认组件。\n- 不使用 `window.confirm()` 或自制确认弹窗。\n\n**为什么**：`Quasar.dialog()` 返回 Promise，与 async/await 配合良好，且与 Quasar 主题一致。\n\n**适用范围**：所有需要用户确认的操作。\n\n**反例**：\n```typescript\nif (window.confirm('确定删除？')) { doDelete(); }\n```\n\n**正例**：\n```typescript\nimport { useQuasar } from 'quasar';\nconst $q = useQuasar();\n\n$q.dialog({\n  title: '确认删除',\n  message: '删除后不可恢复',\n  cancel: true,\n  persistent: true,\n}).onOk(() => { doDelete(); });\n```\n\n### Q4. 通知使用 Quasar Notify plugin\n\n**规则**：\n- 操作反馈（成功/失败/警告）使用 `Quasar.notify()` 或 `$q.notify()`。\n- 不引入第三方 toast 库（vue-sonner、vue-toastification 等）。\n- 成功：`type: 'positive'`，失败：`type: 'negative'`，警告：`type: 'warning'`。\n\n**为什么**：Notify 是 Quasar 内建通知系统，位置、动画、超时均可配置，与主题一致。\n\n**适用范围**：所有操作反馈通知。\n\n**反例**：\n```typescript\nimport { toast } from 'vue-sonner';\ntoast.success('操作成功');\n```\n\n### Q5. 禁止直接操作 DOM 样式替代 Quasar prop\n\n**规则**：Quasar 组件提供了 prop 控制的视觉行为（dense、disable、flat、outline 等），必须通过 prop 设置，不通过 CSS 覆盖实现。\n\n**为什么**：CSS 覆盖 Quasar 内部样式在版本升级时容易失效。\n\n**适用范围**：所有 Quasar 组件使用。\n\n**反例**：\n```vue\n<!-- 用 CSS 模拟 dense -->\n<q-input v-model=\"val\" style=\"padding: 4px 8px; height: 32px;\" />\n\n<!-- 用 CSS 模拟 flat 按钮 -->\n<q-btn color=\"primary\" style=\"box-shadow: none; background: transparent;\" />\n```\n\n**正例**：\n```vue\n<q-input v-model=\"val\" dense />\n<q-btn flat color=\"primary\" />\n```\n\n---\n\n## 5. 响应式与间距规范\n\n### S1. 间距只用 token 值或 Quasar spacing class\n\n**规则**：\n- 组件内间距使用 SCSS token `rw-space($name)` 或对应的 CSS 变量 `var(--rw-space-*)`。\n- 快速布局可使用 Quasar spacing class（`q-pa-*`、`q-ma-*`、`q-gutter-*`）。\n- 不硬编码 `padding` / `margin` / `gap` 的 px / rem 值。\n- UnoCSS spacing utility 只用于 token-backed shortcut，不作为间距主系统。\n\n**为什么**：间距走 token 保证一致性。Quasar spacing class 基于固定 scale，可预测。\n\n**适用范围**：所有 `features/*/components/`、`pages/`、`widgets/`。\n\n**反例**：\n```vue\n<div style=\"padding: 12px; margin-bottom: 16px; gap: 8px;\">\n```\n\n### S2. 布局间距 scale\n\n**规则**：使用以下间距 scale（与 `_spacing.scss` token 对齐）：\n\n| Token 名 | 值 | 典型用途 |\n|----------|------|---------|\n| `0` | 0 | 无间距 |\n| `0-5` | 2px | 极小间距（图标与文字） |\n| `1` | 4px | 紧密元素间距 |\n| `1-5` | 6px | 紧密列表行间距 |\n| `2` | 8px | 同组元素间距 |\n| `3` | 12px | 小分组间距 |\n| `4` | 16px | 区块间距 / card 内边距 |\n| `6` | 24px | 大区块间距 |\n\n**为什么**：有限 scale 减少随意间距值，保持视觉节奏一致。\n\n**适用范围**：所有布局间距。\n\n### S3. 632	## 7. 数据展示规范
633	
634	### D1. 数字格式化
635	
636	**规则**：
637	- 整数不显示小数点：`1234`。
638	- 浮点数保留有效精度，末尾零可省略：`12.34`，`0.5`。
639	- 大数字加千分位分隔：`1,234,567`。
640	- 百分比值显示 `%` 符号：`85.3%`。
641	- 格式化函数统一放在 `shared/` 下。
642	
643	**为什么**：数字格式不一致（有的 `1,234`，有的 `1234`）降低数据可读性。
644	
645	**适用范围**：所有数字展示。
646	
647	**反例**：
648	```vue
649	<!-- 原始值直接展示 -->
650	<span>{{ rawValue }}</span>  <!-- 1234567.890000001 -->
651	```
652	
653	### D2. 时间格式化
654	
655	**规则**：
656	- 日期时间：`YYYY-MM-DD HH:mm:ss`（如 `2026-05-11 14:30:00`）。
657	- 仅日期：`YYYY-MM-DD`。
658	- 仅时间：`HH:mm:ss`。
659	- 相对时间（"3分钟前"）用于实时更新场景（日志、状态变化），不用于历史记录。
660	- 时间戳（毫秒）用于数据传输和存储，不直接展示给用户。
661	- 格式化函数统一放在 `shared/` 下。
662	
663	**为什么**：统一时间格式降低认知负担。桌面应用显示绝对时间更可靠。
664	
665	**适用范围**：所有时间展示。
666	
667	**反例**：
668	```vue
669	<!-- 直接展示 ISO 字符串 -->
670	<span>{{ item.createdAt }}</span>  <!-- 2026-05-11T06:30:00.000Z -->
671	<!-- 历史记录用相对时间 -->
672	<span>{{ timeAgo(item.createdAt) }}</span>  <!-- "3天前" — 不利于精确比对 -->
673	```
674	
675	### D3. 状态标签使用 QBadge + 状态色映射
676	
677	**规则**：
678	- 状态展示使用 `QBadge` + Quasar `color` prop 或自定义状态标签组件。
679	- 颜色按 C2 状态色映射表使用。
680	- 状态文字简短（2-4 字），不写长描述。
681	- 不用纯文字 + 文字颜色替代 badge。
682	
683	**为什么**：Badge 提供视觉分隔，状态色让用户无需读文字即可判断。
684	
685	**适用范围**：所有状态展示（连接状态、任务状态、设备状态等）。
686	
687	**反例**：
688	```vue
689	<!-- 纯文字 + 硬编码颜色 -->
690	<span style="color: green;">已连接</span>
691	<span style="color: red;">断开</span>
692	```
693	
694	**正例**：
695	```vue
696	<q-badge color="positive">已连接</q-badge>
697	<q-badge color="negative">断开</q-badge>
698	```
699	
700	### D4. 空值展示
701	
702	**规则**：
703	- 数值空值：显示 `--`。
704	- 字符串空值：不显示（留空）或显示 `--`。
705	- 不显示 `null` / `undefined` / `NaN` 文字。
706	
707	**为什么**：`null` / `undefined` 是技术术语，不应暴露给用户。
708	
709	**适用范围**：所有数据展示。
710	
711	**反例**：
712	```vue
713	<span>{{ item.value }}</span>  <!-- 可能显示 "undefined" 或 "NaN" -->
714	```
715	
716	**正例**：
717	```vue
718	<span>{{ item.value ?? '--' }}</span>
719	```
720	
721	### D5. 单位必须标注
722	
723	**规则**：物理量展示必须标注单位。单位与数值间加一个空格。
724	
725	- 电压：`12.5 V`
726	- 电流：`1.23 A`
727	- 温度：`25.3 ℃`
728	- 时间：`125 ms` / `2.5 s`
729	- 频率：`10 Hz`
730	- 百分比：`85.3%`（无空格）
731	
732	**为什么**：工业上位机数据量大，无单位的数值容易误读。
733	
734	**适用范围**：所有物理量展示。
735	
736	**反例**：
737	```vue
738	<span>{{ voltage }}</span>  <!-- 12.5 — 是电压还是电流？ -->
739	```
740	
741	### D6. 长文本截断 + Tooltip
742	
743	**规则**：
744	- 表格列、列表项中的长文本使用 CSS 截断（`text-overflow: ellipsis`）。
745	- 截断内容使用 `QTooltip` 展示完整文本。
746	- 不使用 `title` 属性（样式不可控）。
747	
748	**为什么**：桌面应用窗口宽度有限，长文本截断保证布局稳定。
749	
750	**适用范围**：所有可能超长的文本展示。
751	
752	**反例**：

757	<span title="{{ item.longDescription }}">{{ item.longDescription }}</span>

759	
760	**正例**：
761	```vue
762	<td class="rw-text-truncate">
763	  {{ item.longDescription }}
764	  <q-tooltip>{{ item.longDescription }}</q-tooltip>
765	</td>
766	```

:key=\"index\">\n```\n\n**正例**：\n```vue\n<div v-for=\"item in receiveDataList\" :key=\"item.id\">\n```\n\n### P8. v-memo 限制高频更新组件的重渲染范围\n\n**规则**：\n- 仪表盘页面中，只有自身数据变化的指标卡片才重渲染，使用 `v-memo` 精准跳过。\n- 表格行数据更新时，只有变化的行重渲染。\n- 不在所有组件上滥用 `v-memo`，只在确认有性能问题的场景使用。\n\n**为什么**：仪表盘页面通常同时展示连接状态、帧数据、统计数据、图表等多个区域，一个区域数据变化不应导致其他区域重渲染。\n\n**适用范围**：仪表盘、总览页、监控页等多区域布局。\n\n**正例**：\n```vue\n<ConnectionPanel v-memo=\"[connectionState]\" :state=\"connectionState\" />\n<FrameMetrics v-memo=\"[frameSnapshot]\" :data=\"frameSnapshot\" />\n<ChartPanel v-memo=\"[chartData]\" :data=\"chartData\" />\n```\n\n### P9. 大表单必须拆分为子组件\n\n**规则**：\n- 单个 QForm 内超过 20 个表单字段时，必须按逻辑分组拆分为子组件。\n- 每个子组件管理自己的响应式数据，隔离 Vue 依赖追踪范围。\n- 字段数量动态且可能超过 50 时（如帧参数配置表），使用 `QVirtualScroll` 承载字段列表。\n- QInput 校验使用 `lazy-rules=\"ondemand\"` 减少验证频率。\n\n**为什么**：一个组件内 50+ 个 QInput 全部绑定同一个 reactive 表单对象，一个字段变化导致 Vue 遍历所有依赖（Quasar GitHub Issue #12369）。\n\n**适用范围**：所有超过 20 个字段的表单。\n\n**反例**：\n```vue\n<QForm @submit=\"onSubmit\">\n  <QInput v-model=\"form.field1\" />\n  <QInput v-model=\"form.field2\" />\n  <!-- ... 48 more QInput all bound to same reactive form -->\n</QForm>\n```\n\n**正例**：\n```vue\n<QForm @submit=\"onSubmit\">\n  <BasicInfoSection v-model=\"form.basic\" />\n  <ParamConfigSection v-model=\"form.params\" />\n  <AdvancedSection v-model=\"form.advanced\" />\n</QForm>\n```\n\n### P10. 模板中禁止内联复杂计算\n\n**规则**：\n- 模板中不得使用 `.filter()` / `.map()` / `.reduce()` 等数组操作。\n- 模板中不得使用三元嵌套超过 2 层的表达式。\n- 复杂计算必须提取到 `computed` 或方法中。\n\n**为什么**：模板中内联表达式每次渲染都执行，无法被 Vue 缓存。旧系统中 `DataGroupManager.vue` 在模板中 `group.dataItems.filter(item => item.isVisible).length`，每次渲染都重新过滤。\n\n**适用范围**：所有 template 表达式。\n\n**反例**：\n```vue\n<span>{{ group.dataItems.filter(item => item.isVisible).length }}</span>\n<span>{{ items.length > 0 ? items[0].name : items.length > 1 ? items[1].name : 'none' }}</span>\n```\n\n**正例**：\n```vue\n<!-- 提取到 computed -->\n<span>{{ visibleItemCount }}</span>\n```\n\n---\n\n## 12. CSS 动画规范\n\n### A1. 禁止 `transition: all`\n\n**规则**：\n- 所有 `transition` 必须列出具体属性（如 `transition: background-color 0.2s, opacity 0.2s`）。\n- 禁止 `transition: all` / `transition: all 0.3s`。\n\n**为什么**：`transition: all` 会对所有 CSS 属性应用过渡，包括 `width`、`height`、`margin` 等 layout 属性，触发重排（reflow）。旧系统中 6 处使用 `transition: all`（MainLayout、HighSpeedStoragePage、FrameInstanceList 等）。\n\n**适用范围**：所有 `transition` 声明。\n\n**反例**：\n```css\n.status-card { transition: all 0.2s ease-in-out; }\n.q-drawer { transition: all 0.3s; }\n```\n\n**正例**：\n```css\n.status-card { transition: background-color 0.2s ease-in-out, border-color 0.2s ease-in-out; }\n.q-drawer { transition: transform 0.3s ease; }\n```\n\n### A2. 动画只使用 composite 属性\n\n**规则**：\n- CSS 动画和过渡只允许使用 `transform` 和 `opacity`。\n- 禁止动画 `width`、`height`、`top`、`left`、`margin`、`padding`、`border-width` 等 layout 属性。\n- 需要\"展开/折叠\"动画时，使用 `transform: scaleY()` 或 `max-height` 配合 `overflow: hidden`。\n\n**为什么**：`transform` 和 `opacity` 只触发 composite 阶段（GPU 加速），不触发 layout 和 paint。layout 属性动画每次都导致浏览器重新计算布局，代价高昂。旧系统中 `@keyframes fadeIn` 正确使用了 opacity，但多处 `transition: all` 隐式动画了 layout 属性。\n\n**适用范围**：所有 CSS 动画和过渡。\n\n**反例**：\n```css\n@keyframes expand {\n  from { height: 0; }\n  to { height: 200px; }\n}\n.panel { transition: width 0.3s; }\n```\n\n**正例**：\n```css\n@keyframes fadeIn {\n  from { opacity: 0; transform: translateY(-10px); }\n  to { opacity: 1; transform: translateY(0); }\n}\n.panel { transition: transform 0.3s ease, opacity 0.3s ease; }\n```\n\n### A3. will-change 只用于 composite 属性\n\n**规则**：\n- `will-change` 只用于 `transform` 和 `opacity`。\n- 禁止 `will-change: width`、`will-change: height`、`will-change: top` 等 layout 属性。\n- `will-change` 只在元素即将变化前设置，变化完成后移除。不永久挂载。\n- 优先使用 `transform: translateZ(0)` 触发 GPU 层提升，而非 `will-change`。\n\n**为什么**：旧系统中 3 处 `will-change: width`（DataItemList、FrameInstanceList、DataTable），`width` 是 layout 属性，`will-change` 无法将其提升到 GPU 合成层，反而增加内存开销。\n\n**适用范围**：所有 `will-change` 使用。\n\n**反例**：\n```css\n.data-item-table { will-change: width; }\n```\n\n**正例**：\n```css\n.data-item-table { transform: translateZ(0); }\n/* 或在即将动画时 */\n.animated-element { will-change: transform, opacity; }\n```\n\n### A4. 状态指示器动画用 CSS 而非 JS\n\n**规则**：\n- 连接状态、设备状态等指示器动画使用 CSS `transition` / `@keyframes`。\n- 不使用 `setInterval` 或 `requestAnimationFrame` 驱动状态指示器闪烁/脉冲。\n- 脉冲动画使用 `@keyframes` + `animation: pulse 1s infinite`。\n\n**为什么**：CSS 动画由 GPU 合成线程处理，不占用 JS 主线程。JS 驱动动画在主线程繁忙时掉帧。\n\n**适用范围**：所有状态指示器、loading 动画。\n\n**正例**：\n```css\n.status-dot {\n  transition: background-color 0.3s ease;\n}\n.status-dot.connected {\n  background-color: var(--rw-color-status-success);\n}\n.status-dot.error {\n  background-color: var(--rw-color-status-danger);\n  animation: pulse 1s infinite;\n}\n@keyframes pulse {\n  0%, 100% { opacity: 1; }\n  50% { opacity: 0.5; }\n}\n```\n\n---\n\n## 13. Electron UI 规范\n\n### E1. IPC 消息必须批量化\n\n**规则**：\n- 高频数据（串口帧、网络数据）不得逐条发 IPC。main 进程必须缓冲后批量发送。\n- 批量间隔 16ms（~60fps）或按数据量自适应。\n- renderer 侧接收批量数据后，走 P2 缓冲模式刷新 UI。\n- 低频操作（用户触发的查询、配置变更）可直接 IPC。\n\n**为什么**：Electron IPC 使用结构化克隆序列化数据。旧系统中串口数据 10ms 一包 = 每秒 100 次 IPC + 序列化 + 反序列化 + Vue 响应式更新 = 必定卡顿。这也是 `rewrite-quality-rules.md` R6 的具体落地。\n\n**适用范围**：所有 main → renderer 高频数据路径。\n\n**反例**：\n```typescript\n// main process：每帧数据都发 IPC\nserialPort.on('data', (data) => {\n  mainWindow.webContents.send('serial:data', data);\n});\n```\n\n**正例**：\n```typescript\n// main process：积累后批量发送\nclass SerialDataBuffer {\n  private buffer: Frame[] = [];\n  private timer: NodeJS.Timeout | null = null;\n\n  push(frame: Frame) {\n    this.buffer.push(frame);\n    if (!this.timer) {\n      this.timer = setTimeout(() => this.flush(), 16);\n    }\n  }\n\n  private flush() {\n    if (this.buffer.length > 0) {\n      mainWindow.webContents.send('serial:data-batch', this.buffer);\n      this.buffer = [];\n    }\n    this.timer = null;\n  }\n}\n```\n\n### E2. 提供硬件加速开关\n\n**规则**：\n- 应用设置中提供\"硬件加速\"开关，默认开启。\n- 用户遇到 GPU 问题（白屏、闪烁）时可关闭。\n- 启动时处理 `app.on('gpu-process-crashed')` 事件，提示用户切换到软件渲染。\n- 支持 `--disable-gpu` 命令行参数作为 fallback。\n\n**为什么**：Electron v38+ 即使调用 `disableHardwareAcceleration()` GPU 进程仍会运行（SwiftShader 软渲染）。部分用户的显卡驱动不兼容，需要用户可控的开关。旧系统无此机制，GPU 崩溃时直接白屏。\n\n**适用范围**：应用启动流程和设置页面。\n\n### E3. QDialog 生命周期必须正确管理\n\n**规则**：\n- 含表单的弹窗使用 `@hide` 事件重置表单，而非 `@before-show`（避免闪烁）。\n- 不需要保持状态的弹窗使用 `v-if` 销毁内容，而非 `v-show`。\n- 弹窗内的定时器、订阅、watch 必须在弹窗关闭时清理。\n- 弹窗使用 `v-model` 双向绑定，不使用单向 `:value`。\n\n**为什么**：QDialog 内容在隐藏时默认不销毁。不清理的定时器和订阅会在弹窗关闭后继续运行。`v-show` 不销毁 DOM，隐藏表单仍在内存中。\n\n**适用范围**：所有 QDialog 使用。\n\n**反例**：\n```vue\n<!-- 单向绑定，无法关闭 -->\n<q-dialog :model-value=\"show\">\n  <q-card>\n    <q-form>...</q-form>\n  </q-card>\n</q-dialog>\n```\n\n**正例**：\n```vue\n<q-dialog v-model=\"show\" @hide=\"resetForm\">\n  <q-card>\n    <q-form @submit=\"onSubmit\">...</q-form>\n
