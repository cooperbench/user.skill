24	## 1. 决策与约束
25	
26	### 需求摘要
27	
28	**做什么**：为 rewrite 项目提供统一的表达式求值能力，归口 `shared/`，纯 TypeScript，零框架依赖。
29	
30	**为谁**：receive（帧字段后处理）、send（构帧前动态计算）、task（条件匹配与参数计算）三个 feature。
31	
32	**成功标准**：
33	- 单表达式编译后求值 < 1μs
34	- 50 表达式批量求值 < 20μs
35	- 旧系统所有真实表达式样本均可解析和正确求值
36	- API 表面让调用方 3-5 行代码完成集成
37	
38	**明确不做**：
39	- 不做位运算、三元运算符、赋值、正则、模板字符串
40	- 不做引擎内部缓存（编译结果由调用方持有和复用）
41	- 不做 Web Worker / 异步求值
42	- 不做 BigInt 支持（IEEE 754 double 满足当前所有真实表达式精度需求）
43	- 不做表达式→类型推断
44	- 不做 UI 编辑器或表达式配置管理
45	- 不做旧 `VariableMapping`（sourceType/sourceId）的绑定逻辑，绑定归调用方
46	
47	### 复杂度档位
48	
49	走内部工具库默认档位，无偏离。核心是纯函数计算库，无 I/O、无状态机、无 UI、无并发。
50	
51	### 关键决策
52	
53	**D1：手写 tokenizer + recursive descent parser**
54	- 换 `new Function`：无静态分析能力，无法做安全校验和依赖提取，与预编译目标矛盾
55	- 换外部 parser 库：实际语法极简（四则运算+比较+逻辑+括号），引入依赖不合理
56	
57	**D2：编译阶段产 AST，AST 含依赖信息，Kahn 排序在编译阶段完成**
58	- 换运行时排序：每帧重复排序，浪费 CPU
59	- 换正则提取依赖（旧系统做法）：中文变量名和字符串字面量会干扰正则，AST 提取更可靠
60	
61	**D3：条件表达式纳入引擎核心**
62	- 换调用方自行编排：多分支 condition+expression 是真实数据中最复杂的模式，引擎内置比散落在三个 feature 里更干净
63	
64	**D4：`==` 严格语义（不自动类型转换）**
65	- 换宽松语义：`5 == '5'` 返回 true 会掩盖配置错误，严格语义更安全
66	
67	**D5：变量/函数名冲突用语法消歧**
68	- 标识符后跟 `(` → 函数调用；否则 → 变量查找
69	- 编译时同名存在 → warning（不阻塞编译）
70	
71	**D6：引擎不持有状态，不持有缓存**
72	- 编译结果是普通 JS 对象，由调用方持有和复用
73	- 求值是纯函数，输入相同输出相同
74	
75	### 被拒方案
76	
77	- **`new Function` 缓存**：旧系统做法，无法做 AST 级分析和安全校验
78	- **外部 parser 库（mathjs/formula-parser）**：语法量级不匹配，引入体积和依赖
79	- **手写递归下降解释器（每次遍历 AST 求值）**：性能不如编译为 JS 函数后利用 V8 JIT
80	- **引擎内置变量绑定（DataSourceType）**：违反纯函数约束，旧系统 store 依赖必须消灭

235	### 2.2 编排层
236	
237	#### 主流程图
238	
239	```mermaid
240	flowchart TD
241	    A[调用方] -->|表达式文本| B[compile]
242	    B --> C[tokenizer: 文本 → Token 数组]
243	    C --> D[parser: Token → AST]
244	    D --> E{编译类型?}
245	
246	    E -->|单表达式| F[compileExpression]
247	    E -->|条件表达式| G[compileConditional: 多分支分别编译]
248	    E -->|批量| H[compileGroup: 逐个编译 → AST 提取依赖 → Kahn 排序]
249	
250	    F --> I[返回 CompiledExpr]
251	    G --> J[返回 CompiledConditional]
252	    H --> K[返回 CompiledGroup]
253	
254	    A -->|编译产物 + VariableMap| L[evaluate]
255	    L --> M{求值类型?}
256	
257	    M -->|单表达式| N[执行编译后函数 → EvalResult]
258	    M -->|条件表达式| O[按序求值 condition，首个 true 时求 expression]
259	    M -->|批量| P[按拓扑序逐个 evaluate，每步结果写入内部可变 Map]
260	
261	    N --> Q[返回结果]
262	    O --> R[返回 ConditionalEvalResult]
263	    P --> S[返回 GroupEvalResult]
264	```
265	
266	**现状**：无表达式引擎。receive 用硬编码 `applyFactor`，task 用结构化 `WaitCondition` + `compareValues`，send 用静态字段值。
267	
268	**变化**：新增共享表达式引擎，三个 feature 各自在合适的集成点调用。
269	
270	#### 编排关键规则
271	
272	1. **编译与求值严格分离**：编译低频（配置加载/变更时），求值高频（每帧/每次匹配）。调用方持有编译产物，反复调用 evaluate。
273	
274	2. **compileGroup 的拓扑排序**：
275	   - 从每个表达式的 AST 提取变量引用
276	   - 如果变量名与其他表达式的 key 相同，建立依赖边
277	   - Kahn 算法排序，O(V+E)
278	   - 循环依赖 → `GroupCompileResult.success = false`，返回循环中涉及的表达式
279	
280	3. **evaluateGroup 的顺序求值**：
281	   - 内部创建输入 Map 的可变副本
282	   - 按预编译的拓扑序逐个 evaluate
283	   - 成功的结果写入内部 Map，供后续表达式引用
284	   - 失败的表达式：该 key 不写入 values，记录到 errors；依赖它的后续表达式也失败
285	
286	4. **evaluateConditional 的短路求值**：
287	   - 按数组顺序，先 evaluate condition
288	   - 首个 `success && value === true` 的条件 → evaluate 对应 expression → 返回
289	   - 所有条件都不满足 → 返回 fallback（默认 0）
290	
291	#### 跨层纪律
292	
293	**错误语义**：
294	- 编译错误：不可恢复，返回 `{ success: false, error, position? }`。调用方应阻止进入求值路径。
295	- 运行时错误（除零、变量缺失、类型不匹配）：返回 `{ success: false, error }`。不抛异常。
296	- 部分失败（evaluateGroup）：失败的 key 记入 errors，不阻断其他无依赖的表达式。
297	
298	**幂等性**：所有函数都是纯函数，相同输入必定返回相同输出。
299	
300	**并发/顺序**：引擎本身无状态，天然线程安全（JS 单线程下无竞争）。evaluateGroup 内部按拓扑序串行执行。
301	
302	**扩展点**：FunctionTable 允许调用方注入自定义函数，无需修改引擎。
303	
304	**可观测点**：编译错误含 position（字符偏移），方便 UI 标注。运行时错误含表达式 key 或错误类型描述。
