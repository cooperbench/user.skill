31	## 2. Boundary guards
32	
33	- 本轮是 Lane B 单 feature design，只产出 design/checklist，不进入实现，不迁移代码，不写接口 schema。
34	- frame 本轮只设计静态帧资产、字段、表达式定义、校验、导入导出的 owner 和边界。
35	- 不设计 receive、send、task、SCOE、report、northbound 内部细节。
36	- 不冻结 northbound、result、report、TestReport schema。
37	- 不把旧 JSON 当成新核心模型；旧 JSON 只能作为迁移输入、fixture 或 oracle。
38	- 不把统计 read model 写回 frame definition、field definition 或静态配置。
39	- 不把 frame helper 提前抽到 `shared`，除非后续实现证明它满足 shared 纯工具条件。
40	- 不写 preload、main、renderer API schema。
41	- 不读取或引用前端自动生成 types 文件作为证据。

43	## 3. Evidence summary
44	
45	### 3.1 Contract evidence
46	
47	- 目标结构要求 `features/frame` 承担帧定义、字段定义、静态校验、序列化、导入导出和旧 JSON 迁移入口；领域规则应在可测试 TypeScript 层，不依赖 Vue、Pinia、Electron、platform facade、全局 store 或 Node 能力。
48	- feature 边界和 interaction matrix 将 receive、send、task、SCOE、report 视为 frame 静态资产的消费者；它们可以读取 frame selector 或快照，但不能 import frame internal state。
49	- 状态分层要求静态资产、运行事实、统计 read model、UI snapshot 分离；统计 read model 由对应 owner feature 基于运行事件维护，不能写回 frame definition。
50	- platform surface reduction 要求 file、path、dialog 只是受控平台能力；旧 `window.electron` 大包、dataStorage/history/highSpeed 不能原样升级为新 platform API。
51	- shared tooling audit 要求旧 `src/utils/frames/*` 中的 frame 业务校验和表达式定义规则回归 frame feature；只有纯通用、无业务语义、无副作用工具才可能进入 `shared`。
52	- pre-design gate 要求第一批业务 feature design 明确 legacy observable behavior ledger，登记旧可观测行为、owner、处理策略、证据和验证等级。
53	- rewrite root placement 要求 frame 新代码落在 `rewrite/src/features/frame`；旧 `src/` 和 `public/` 路径只作为 legacy evidence、fixture 或 oracle 输入。

66	## 4. Design
67	
68	### 4.1 Owner / not owner
69	
70	| 分类 | frame owner | frame not owner |
71	| --- | --- | --- |
72	| 静态资产 | 帧定义、字段定义、表达式定义、展示/编辑用静态配置、收藏标记、导入导出语义、旧 JSON 迁移入口。 | receive 配置、send 实例、task 配置、SCOE 专属实例、result/report/northbound schema。 |
73	| 领域规则 | frame asset 校验、field 校验、表达式定义校验、导入内容校验、序列化/反序列化规则、迁移规则。 | 串口/TCP/UDP 数据接收、发送执行、任务调度、SCOE 命令流程、报告生成和交付。 |
74	| 状态写入 | 静态 frame asset collection 和 frame 页面局部 UI snapshot。 | 接收运行事实、发送运行事实、任务运行事实、SCOE 状态、连接状态、统计 read model、报告交付状态。 |
75	| 外部读取 | 提供只读 snapshot、selector 或 service 给明确消费者读取 frame asset。 | 反向拥有消费者状态，或替 receive/send/task/SCOE/report 维护运行投影。 |
76	| 平台能力 | 定义 frame JSON 语义、校验、迁移和导入导出领域结果。 | 文件选择、路径解析、对话框、打包态 data path、主进程缓存。 |
77	
78	frame 的目标是成为静态帧资产和字段/表达式定义规则的单一 owner。它不成为所有帧相关行为的总入口，也不把历史上聚集在旧 store/composable 中的 receive、send、task、SCOE 运行行为收回到 frame。

103	### 4.3 State ownership
104	
105	| 状态类别 | 写入 owner | 读取方 | 本轮设计约束 |
106	| --- | --- | --- | --- |
107	| 静态 frame assets | frame | frame pages、receive、send、task、SCOE、未来 report | 包含帧、字段、表达式定义和静态展示配置。写入只来自 frame 的创建、编辑、复制、删除、收藏、导入、迁移服务。 |
108	| 运行事实 | receive、send、task、SCOE、connection、result 等对应 feature | 各自页面、runtime 编排、统计/报告消费者 | frame 不写入、不缓存、不重放运行事实。表达式运行输入属于消费者 feature 或运行编排输入，不属于 frame 静态资产。 |
109	| 统计 read model | 对应 owner feature，例如 receive/status/result | 页面、报告、任务触发等明确消费者 | 统计只作为 read model 或运行投影，不写回 frame definition、field definition 或静态配置。 |
110	| UI snapshot | frame 页面、组件、composable 或 feature state 的 UI 子层 | frame 页面和局部组件 | 搜索词、筛选条件、当前选中帧、编辑草稿、对话框状态等是 UI snapshot，不是 frame asset truth。若需要持久化，必须单独标记，不混入静态定义。 |
111	| 导入/迁移过程状态 | frame service 和页面流程 | frame 页面、验证结果展示 | 迁移报告、导入错误、兼容警告只描述导入过程，不成为核心 schema。 |
112	
113	### 4.4 Public API necessity
114	
115	frame 不为所有能力强行设计同构 public API。后续实现只给真实外部消费者提供最小只读入口。
116	
117	需要 frame public selector/service 的消费者：
118	
119	- frame 页面：读取 frame 列表、详情、编辑草稿初始化数据，并调用 frame service 进行创建、更新、复制、删除、收藏、导入、导出。
120	- receive：读取接收方向可用的 frame asset snapshot、字段定义和必要匹配信息；不得写入 frame state，不得 import frame internal store。
121	- send：读取发送方向可用的 frame asset snapshot 和字段定义，用于 send instance 配置与发送构造；发送执行结果不回写 frame。
122	- task：读取稳定的 frame/field 引用选项，用于触发条件或任务配置；task 运行状态和触发执行归 task。
123	- SCOE：在 SCOE 设计明确需要时读取 generic frame asset snapshot；SCOE 专属帧实例、命令流程和设备状态归 SCOE。
124	- report：本轮不设计 schema；未来若 report 需要 frame metadata，只能通过只读 selector/service 读取，不从 frame internal state 取数。
125	- import/export adapter：调用 frame service 完成 JSON 语义校验、迁移和序列化；文件读写由 app/platform 能力承担。
126	
127	不需要 frame public API 的对象：
128	
129	- connection、serial/network platform：它们不直接理解 frame 领域语义。
130	- status 纯展示组件：应读取对应 owner 的 read model，而不是直接 import frame internals。
131	- northbound/result/report 交付闭环：本轮不冻结 schema，也不建立 frame 到 northbound 的直接合同。
132	- shared tools/widgets：除非后续有明确纯展示或纯工具需求，否则不作为 frame 领域 API 消费者。
133	
134	禁止形态：
135	
136	- 不暴露可变 frame collection 引用。
137	- 不暴露 internal store、Pinia state、Vue ref、全局 singleton 给其他 feature。
138	- 不把 receive/send/task/SCOE/report 的运行方法挂在 frame API 上。
139	- 不为了形式统一创建空壳 `public.ts`、同构 service 或同构 event bus。
140	
141	### 4.5 Runtime involvement
142	
143	frame core、service、state、adapter 自身不需要 runtime 承载领域规则。
144	
145	runtime 只有在以下场景可以参与：
146	
147	- 应用启动装配：在 receive/send/task 等消费者读取前加载 frame assets，或注册 frame asset snapshot 的刷新顺序。
148	- 跨 feature 输入输出：当某个消费者需要订阅 frame asset 更新时，runtime 可以负责装配订阅关系，不能解释 frame 字段、表达式或迁移语义。
149	- 生命周期：应用退出、刷新、导入后重载等流程中，runtime 可协调加载顺序和错误上报。
150	- 边界例外登记：若后续 receive/send 为性能或平台原因需要 main 侧缓存 frame snapshot，例外只登记平台/生命周期原因；frame 领域规则仍归 frame core/service。
151	
152	runtime 不得包含：
153	
154	- frame/field/expression 校验规则。
155	- 旧 JSON 迁移规则。
156	- frame import/export JSON 语义。
157	- receive/send/task/SCOE/report 的领域决策。
158	
159	### 4.6 Platform involvement
160	
161	platform 与 app shell 在 frame 中只承担文件、路径、对话框等能力边界：
162	
163	- 导入：选择文件、读取文本或结构化内容、返回失败原因的技术错误。
164	- 导出：选择目标路径、写入文件、返回文件系统结果。
165	- 数据路径：解析开发态/打包态存储位置。
166	- 对话框：确认覆盖、选择文件、错误提示所需的 app shell 能力。
167	
168	frame 必须自己承担：
169	
170	- frame JSON 的语义识别。
171	- 导入内容校验。
172	- 旧 JSON 迁移和兼容警告。
173	- 导出结构的稳定性和可测试性。
174	- 导入/导出结果如何反馈给 frame 页面。
175	
176	本设计不定义最终 platform API schema。后续实现只能通过目标架构允许的 renderer platform facade 或 app shell 能力进入 file/path/dialog，不直接访问 Node、Electron、`fs`、`path`、`ipcRenderer` 或旧 `window.electron` 大包。
177	
178	### 4.7 Cross-feature boundaries
179	
180	| Feature | 如何读取 frame | 明确禁止 |
181	| --- | --- | --- |
182	| receive | 读取只读 frame asset snapshot，用于识别帧、字段解释、接收配置中 frame/field 引用选项。 | import frame internal state；把接收数据、global stats、frameStats、表达式运行结果写回 frame。 |
183	| send | 读取发送方向 frame snapshot 和字段定义，用于 send instance 配置和发送构造。 | 让 frame 拥有发送实例、发送队列、连接状态、执行结果或错误重试策略。 |
184	| task | 读取 frame/field reference selector，用于 trigger/timer 配置和校验。 | 让 frame 拥有 task 生命周期、触发执行、任务运行日志。 |
185	| SCOE | 在 SCOE 设计允许时读取 generic frame asset snapshot。 | 把 SCOE command、设备状态、SCOE 专属实例或硬件语义塞入 frame。 |
186	| report/result | 后续如需读取 frame metadata，只能通过明确只读 selector/service。 | 在本轮冻结 report/TestReport schema；把本地 history/CSV 导出等同 report delivery。 |
187	| status/statistics | 读取对应 owner 的统计 read model，必要时可展示 frame 名称/字段名快照。 | 将统计 read model 写回 frame definition。 |
188	| northbound | 本轮无直接 frame public API。 | 把 northbound deviceId、result、file delivery 与 frame/serial target 直接等价。 |

190	### 4.8 Target internal layering
191	
192	后续实现的目标分层只描述职责，不在本设计中冻结字段 schema。
193	
194	| 层 | 目标职责 |
195	| --- | --- |
196	| `core` | 纯 TypeScript 领域规则。负责 frame asset、field、expression definition 的校验；旧 JSON 识别、迁移和规范化；序列化/反序列化规则；只接收显式输入，不依赖 Vue、Pinia、Electron、platform、Node 或全局 store。 |
197	| `services` | 组织用例流程。负责 create/update/delete/duplicate/favorite/import/export/migrate/validate 等应用服务，协调 core、state 和 adapter，但不承载平台细节。 |
198	| `state` | frame 静态资产集合、只读 selector、必要的 frame UI snapshot。state action 应保持薄层，不直接访问其他 feature internal state，不维护运行事实或统计 read model。 |
199	| `adapters` | 与 storage、file import/export、legacy sample loading 等边界适配。adapter 只做技术转换，调用 frame service/core 解释 JSON 语义。 |
200	| `composables` | frame 页面交互层。负责表单草稿、列表筛选、导入导出对话流程、错误展示和 service 调用，不承载核心校验规则。 |
201	| `components` | frame list、frame editor、field editor、expression editor 等 UI 组件。组件通过 props/events/composables 使用 feature 能力，不直接读取 platform 或跨 feature internal state。 |
202	| `fixtures` | 旧 JSON 正例/反例、迁移输入、预期输出、表达式定义校验样本、导入导出 round-trip 样本。fixtures 是 oracle，不是新核心模型。 |

204	### 4.9 Fixture / oracle / test plan
205	
206	Vitest 可覆盖的自动验证：
207	
208	- 重写新应用已在 `rewrite/` 独立根目录引入 Vitest 基线；`pnpm -C rewrite test` 当前运行最小 infra smoke test。旧根 `package.json` 的 `test` script 仍只属于旧应用，不作为 rewrite feature 验证入口。

359	
360	#### 纠正 1：网口和串口是同一个模块
361	
362	用户原话：
363	
364	> 遥控遥测是串口、网口，scoe是网口，新的甲方的是https（我没记错的话），这些应该算在一起吧？

369	
370	用户原话：

375

377	connection events
378	  ↓
379	routingTick 分流
380	  ├→ receive（遥测）：解析帧 → 存参数 → 部分参数作为条件触发 task
381	  ├→ SCOE / 指令码：bypass receive，直接走自己的 adapter
382	  └→ （未来可能有其他领域模块）
383	```
384	
385	三条路是独立的，routingTick 只负责分发，不是把 receive 和 task 串成一条线。

389	## 四、十一个业务流程详细描述
390	
391	AI 对每个流程做了详细描述，用户确认后进行了多轮纠正。
392	
393	### Flow 1：设备连接管理
394	
395	**是什么**：管理上位机和被测设备之间的物理连接。是所有数据流的底层依赖。
396	
397	**涉及传输类型**：串口、TCP client、TCP server、UDP。
398	
399	**完整过程**：
400	1. 用户在连接页面选择传输类型（串口/TCP/UDP）
401	2. 选择或输入目标参数（串口：端口+波特率；TCP client：IP+端口；TCP server：监听等待设备连入；UDP：绑定本地端口+对端地址）
402	3. 点击连接 → connection service 通过 adapter 调用 platform transport → 建立物理连接
403	4. 连接成功后进入"已连接"状态，成为后续收发的 target
404	5. 持续监听连接状态（意外断线、设备热插拔）
405	6. 意外断线时：检测到 → 状态变为"已断开" → 可选自动重连策略 → 通知上层
406	7. 用户主动断开 → 清理资源 → 状态变为"空闲"
407	8. 支持同时存在多个连接
408	
409	**产出**：一组活着的连接，每个有 ID、状态、配置。
410	
411	### Flow 2：遥测接收
412	
413	**是什么**：从已建立的连接接收设备上报的遥测数据，解析出具体参数值并存储。
414	
415	**涉及传输类型**：串口、TCP/UDP。
416	
417	**完整过程**：
418	1. 设备通过已建立连接主动上报数据（字节流）
419	2. main 侧串口/网络 handler 收到原始字节 → 批处理缓冲 → 通过 preload bridge 推到 renderer
420	3. routingTick 定期排空 connection 的事件队列
421	4. routingTick 识别这是遥测数据，分发到 receive 路径
422	5. receive service 处理：帧匹配 → 字段解析 → 归一化
423	6. 解析成功的参数值存入 receive read model
424	7. 如果参数值满足预设触发条件，emit 条件匹配事件
425	8. 条件匹配事件可以被 task service 消费
426	
427	**产出**：当前参数最新值（read model）、条件匹配事件、接收统计。
428	
429	### Flow 3：遥控发送
430	
431	**是什么**：通过已建立的连接向设备发送控制指令。
432	
433	**涉及传输类型**：串口、TCP/UDP。
434	
435	**完整过程**：
436	1. 触发来源：用户手动操作，或任务步骤自动触发
437	2. send service 处理：帧构造 → 目标解析 → 传输写入
438	3. 返回发送结果：成功/失败
439	
440	**产出**：发送结果。
441	
442	### Flow 4：SCOE 协议处理（后被重命名为"指令接入"）
443	
444	**是什么**：SCOE 是一套专门的设备控制协议。**后经用户纠正，SCOE 和新甲方统一为"指令接入"模块。**
445	
446	**涉及传输类型**：TCP/UDP（网口）。
447	
448	**完整过程**（按纠正后的理解）：
449	1. 外部系统（SCOE TCP / 新甲方 HTTPS）发指令给我们
450	2. connection adapter 接收（不同传输，同一层）
451	3. 指令解析（各自协议格式）
452	4. 翻译成内部动作（大多情况：生成一个 task 去执行）
453	5. task system 执行
454	6. 结果回传给外部系统
455	
456	**特殊点**：入站 bypass receive，走指令接入路径。
457	
458	### Flow 5：任务执行
459	
460	**是什么**：自动化测试的核心。
461	
462	**完整过程**：
463	1. 用户创建/选择任务定义（步骤、执行模式）
464	2. 启动 → 创建任务实例，状态"执行中"
465	3. 按执行模式进入循环（定时/触发/序列）
466	4. 每步骤执行（send / wait-condition / delay / SCOE）
467	5. 所有步骤完成 → 任务完成 → 汇总结果
468	6. 异常处理（步骤失败策略、超时策略、手动停止）
469	7. 完成后交给 result 处理
470	
471	**产出**：任务执行结果。
472	
473	### Flow 6：结果收集
474	
475	**是什么**：把任务执行过程数据收集归口。
476	
477	**完整过程**：task 完成步骤 → emit 步骤结果 → task 整体完成 → emit 任务完成事件 → result 收集步骤结果、参数快照、汇总信息。
478	
479	**产出**：结构化测试结果数据。
480	
481	### Flow 7：数据存储
482	
483	**是什么**：持久化存储遥测参数历史、任务结果等。
484	
485	**注意**：用户确认不需要兼容旧格式，新系统从零开始。
486	
487	### Flow 8：帧定义管理
488	
489	**是什么**：定义系统中所有帧的结构——解析和构造的"字典"。
490	
491	**注意**：用户确认新系统重新定义格式（JSON），旧数据写迁移脚本。帧定义全局唯一，不存在第二套帧结构。
492	
493	### Flow 9：报告生成
494	
495	**是什么**：根据任务结果按甲方要求格式生成测试报告。
496	
497	### Flow 10：北向交付
498	
499	**是什么**：把结果/报告推给甲方系统（HTTPS）。
500	
501	### Flow 11：系统设置
502	
503	**是什么**：管理应用各类配置。

507	## 五、SCOE 重命名为"指令接入"
508	
509	### 用户的纠正
510	
511	用户原话：
512	
513	> SCO其实和新甲方他们一样，指令码（新甲方是https接口）控我们，可能是跟新甲方任务一样，发一系列遥控帧，可能是运维方面，可能是什么乱七八糟的（这些感觉都可以算到任务？毕竟触发源一样，中间过同一处之后分开）。所以我一直觉得，SCOE得改个名字，叫什么都行，然后SCOE和新甲方都是这里面一部分
514	
515	用户原话：
516	
517	> SCOE那块，当时我弄的就比较接近现在任务希望的，不过弄的挺乱的，搞了独立帧列表，独立的条件啥的，一堆乱七八糟的，这都得好好分解，想想哪里需要什么
518	
519	### 架构纠正
520	
521	之前的理解（有问题）：
522	- SCOE = 独立 feature，有 bypass receive 特殊路径
523	- 北向 = 独立 feature，HTTP/FTP 交付
524	- 两者不相关
525	
526	纠正后的理解：
527	- **指令接入 feature**：统一收 SCOE + 新甲方，解析外部命令，翻译成内部动作（通常是 task），执行后回应。传输层差异只是 adapter 不同。
528	- **北向交付 feature**：我们把结果/报告主动推给外部系统。这是出站方向，和指令接入是两个独立能力。
529	- SCOE 的"bypass receive"不再是架构例外——它根本就不走 receive 路径，它走的是指令接入路径。
530	
531	三条路在 routingTick 层分流，各走各的：
532	- 遥测走 receive
533	- 遥控走 send
534	- 外部指令走指令接入
535	
536	### 指令接入内部的分发
537	
538	大多数外部指令进来后是"发一系列遥控帧 + 等条件"，和手动创建的 task 结构一样。但有几类可能不是 task：
539	- 查询类：外部系统问"当前设备状态" → 直接返回 read model 快照
540	- 运维类：重连、重启采集、清理数据 → 直接调对应 service
541	- 纯控制类：立即发一帧，不等待条件 → 可能就是一个 send
542	
543	指令接入 feature 的设计：解析完命令后根据命令类型分发到不同处理器——task 只是其中一种处理器。feature 保留分发权，具体执行委托给已有 feature（task / send / connection / storage）。

547	## 六、五大风险识别
548	
549	AI 提出了五个"不修后面必炸"的问题，用户基本认可。
550	
551	### 风险 1：routingTick 无背压
552	
553	routingTick 是同步 drain 模型。一个 tick 里可能积了几百个 batch，receive 解析同步阻塞，整个链路在同一个微任务里跑完。
554	
555	经用户纠正后降级：routingTick 本身只是轻量分发，重的活在各自 context 里跑。真正要注意背压的是 receive 解析那一环。
556	
557	**建议**：B 组预留背压和分批处理口子，routingTick 内部按预算截断。
558	
559	### 风险 2：无断线重连
560	
561	connection service 能连能断，但断线后没有自动重连闭环。
562	
563	**建议**：在 connection 实现时一起做，指数退避 + 用户可感知的状态。
564	
565	### 风险 3：Bridge 胶水膨胀
566	
567	当前四个 bridge 是手写薄适配器。后面加 SCOE→task、task→result、result→report 等每条交互路径都多一个 bridge 文件。
568	
569	**建议**：不提前做框架，观察重复模式后考虑提取 `drainBridge(producer, transform, consumer)` 工具函数。
570	
571	### 风险 4：Storage 和 Result 是完全空壳
572	
573	正常，先铺骨架后填肉。但 E 组工作量可能比预期大。
574	
575	### 风险 5：无端到端集成测试路径
576	
577	330+ 单元测试覆盖 feature 内部逻辑，但没有"fake adapter → routingTick → receive → task → send → result"的端到端测试。
578	
579	**建议**：A 组完成后立刻补一条端到端集成测试，后续每组扩展。

583	## 七、表达式引擎 — 最关键的共用件
584	
585	### 用户的深入说明
586	
587	用户原话：
588	
589	> 表达式这个，应该是和发送那边一模一样吧？都是放到共用那边的，两边用的时候就几行？
590	
591	用户原话：
592	
593	> 但表达式里面可能用到各种东西，比如发送的时候，可能用到当前帧参数，可能用到遥测（可视化）那边维持的参数，可能用到一些全局的参数（比如时间啥的），那它是作为一个功能模块？不然shared里不方便获取这些吧？还是说打算全部外部传入？也不是不行。
594	
595	用户原话（关于表达式的问题细节）：
596	
597	> 接一个帧，它里面可能有表达式运算（这个发送、接收都有，而且之前写的不好，这个必须考虑变量先后顺序，比如前面变量算完了，后面得用算完的接着算，而不是算之前的，还得考虑性能。总之之前写的很烂，来回打了不少补丁）
598	
599	### 表达式引擎的使用场景
600	
601	用在：
602	- **接收**：帧内字段值经过表达式计算得到最终参数值
603	- **发送**：用户填的参数值经过表达式计算得到要写入帧的字节
604	- **任务**：条件判断、步骤参数填充
605	- **指令接入**：外部命令参数翻译
606	- **报告**：统计计算
607	
608	### 核心难点
609	
610	**变量依赖顺序**：A 表达式算完得出值，B 表达式依赖 A 的结果，必须用 A 算完后的值继续算，不能用原始值。加上性能要求，这不是简单 eval，需要正经的求值器。
611	
612	### 表达式变量的来源
613	
614	- 当前帧参数（本帧上下文）
615	- 遥测当前值（receive 的 read model）
616	- 全局参数（时间、系统计数器等）
617	
618	### 设计决策：纯函数 + 外部传参
619	
620	路线 B（全部外部传入）胜出。表达式引擎是 shared/ 纯函数：
621	
622	- 输入：一堆变量（Map<name, value>）+ 一堆表达式文本
623	- 输出：按依赖排序求值的结果
624	- 引擎不管变量从哪来，调用方自己收集
625	
626	调用方知道需要哪些变量源：
627	- send service 调用表达式时：读 receive selector（公开只读）+ 读 settings（公开只读）+ 本帧上下文（自己的）
628	- 不存在"表达式引擎反向依赖 receive/send/settings"的问题
629	
630	变量命名空间约定：`$遥测.温度`、`$本帧.系数`、`$global.时间`，在帧定义里约定，引擎按名字查 map。
631

634	## 八、接收管线 — 比预期复杂得多
635	
636	### 用户的深入说明
637	
638	用户原话：
639	
640	> 最需要慎重考虑的就是接收。比如接一个帧，它里面可能有表达式运算……然后可能得更新星座图（演示这些，比如表格、折线图、星座图啥的，你是不是忘了？星座图特殊，还得单独记，别的考虑到存储也是有些麻烦，容易爆炸），得更新表格，可能触发别的发送一帧或者一个任务里某个步骤推进或者触发别的什么；然后表达式不仅是帧内参数，别的地方也都有很多。
641	
642	### 正确的接收管线
643	
644	```
645	收到字节 → 帧匹配 → 提取原始字段
646	  → 表达式求值（带依赖排序）
647	  → 得到最终参数值
648	
649	最终参数值出来之后，多条岔路同时走：
650	  ├→ ① 存参数值（read model，当前最新值）
651	  ├→ ② 更新可视化：
652	  │     - 表格（参数值填进表格行）
653	  │     - 折线图（参数值追加到时间序列）
654	  │     - 星座图（特殊 — 需要单独记录 I/Q 采样点，数据量大，存储策略不同）
655	  ├→ ③ 存历史（持久化，但要控制量，容易爆炸）
656	  ├→ ④ 检查条件匹配 → 可能触发：
657	  │     - 发一帧（立即 send）
658	  │     - 推进任务步骤
659	  │     - 触发其他什么
660	  └→ ⑤ 如果没匹配到任何已知帧 → 记录为未匹配
661	```
662	
663	这不是"receive feature 内部的事"，输出扇出到好几个地方：可视化（UI 层）、存储（持久化层）、条件匹配（task 层）、直接触发 send（send 层）。
664	
665	### 星座图特殊性
666	
667	- 普通参数：一个帧一个值，数据量可控
668	- 星座图：一个帧可能带几十到几百个 I/Q 采样点，高频帧一秒几十帧，数据量爆炸
669	- 不能和其他参数用同一个存储策略，必须有独立的采样/存储/清理机制
670	
671	### 接收管线的五个子问题
672	
673	1. 帧匹配 + 字段提取（依赖帧定义）
674	2. 表达式求值（依赖 shared 表达式引擎）
675	3. 参数值存储（read model + 持久化，持久化策略要考虑数据量控制）
676	4. 可视化数据管道（表格/折线图/星座图各自不同的数据形态）
677	5. 条件匹配 + 副作用触发（send / task step / 其他）

681	## 九、最终模块划分
682	
683	### 用户的纠正原则
684	
685	用户原话：
686	
687	> 表达式这个，应该是和发送那边一模一样吧？都是放到共用那边的，两边用的时候就几行？然后，整个系统，帧的结构不应该出现第二个？这样所有地方都能通用一套工具（我怀疑你之前没遵守这个）。存储则是单独模块，接收这边调用而已。可视化同样是单独模块，条件触发我觉得也算单独的？毕竟，输入很多（接收、发送、别人给的都可以算做这个？），输出很多（感觉这些都能统一，但也可能是我想错了）
688	
689	### 纠正后的归属
690	
691	- **表达式引擎**：shared/ 纯工具，两边调用就是几行
692	- **帧结构**：全局唯一，不存在第二个帧模型
693	- **存储**：独立模块，receive 只是调用方
694	- **可视化**：独立模块
695	- **条件匹配**：分两层——匹配逻辑（shared/ 纯函数）+ 触发行为（各 feature 自己管）
696	
697	### 条件匹配的两层分离
698	
699	**匹配层（shared/ 纯函数）**：
700	"这个事件满不满足这个条件？"——纯逻辑，无状态。接收参数值 > 阈值、发送结果 == 失败、外部命令类型 == 某个值，底层都是"输入事实 + 条件定义 → 是否匹配"。
701	
702	**触发层（各 feature 自己管）**：
703	"匹配了之后干嘛？"——业务语义，每个 feature 不一样：
704	- task 的 wait-condition 步骤：匹配了 → 推进当前步骤
705	- 指令接入：匹配了 → 回应外部系统
706	- 发送失败重试：匹配了 → 重新发送
707	
708	不统一也不应该统一——统一了就是事件总线，架构明确禁止。
709

711

731	## 十、跨模块交互 — 旧 store 教训与新架构
732	
733	### 用户的核心担忧
734	
735	用户原话：
736	
737	> 不同模块之间怎么跨模块交互。我之前是全部用的store，结果就是成一坨屎山了。新的架构说实话我没咋看，也不知道行不行，挺担忧的。
738	
739	### 旧系统怎么烂的
740	
741	```
742	Feature A 的 store ← Feature B 直接 import 并读写
743	Feature B 的 store ← Feature C 直接 import 并读写
744	Feature C 的 store ← Feature A 直接 import 并读写
745	```
746	
747	结果：没有单向数据流、没有 owner、没有边界、没法测试。
748	
749	### 新架构的四种合法跨模块交互方式
750	
751	**1. 调用 public service（命令）**
752	```
753	task 调 sendService.sendRequest({ frameId, targetId, params })
754	```
755	task 不知道 send 内部怎么实现，只知道 public API。
756	
757	**2. 读 public selector（只读查询）**
758	```
759	send 读 receiveSelector.getCurrentValues()
760	```
761	send 需要遥测当前值来算表达式，通过 receive 暴露的只读 selector 拿。send 只能读不能改。
762	
763	**3. Bridge（runtime 接线）**
764	```
765	receive 产出事件 → runtime 通过 bridge 转换格式 → task 消费
766	```
767	receive 和 task 互不知道。runtime 在中间接线。
768	
769	**4. 显式事件（高频/异步场景）**
770	```
771	receive emit 条件匹配事件 → receiveEventSourceBridge → task condition registry
772	```
773	
774	### 旧 store vs 新架构对比
775	
776	| | 旧 store | 新架构 |
777	|---|---|---|
778	| 谁写 | 谁都能写 | 只有 owner feature 写 |
779	| 谁读 | 直接 import store | 通过 public selector（只读） |
780	| 跨 feature 通信 | A 写 B 的 store | service 调用 / bridge / 事件 |
781	| 数据流方向 | 双向乱串 | 单向：producer → bridge → consumer |
782	| 改一个 feature 影响 | 不可预测 | 只影响消费它 public API 的地方 |
783	
784	### 四个真实风险
785	
786	**风险 1：selector 返回可变引用**
787	selector 必须返回深拷贝或 readonly 冻结对象，否则消费方一个 `.push()` 就绕过保护。
788	
789	**风险 2：bridge 里塞业务逻辑**
790	bridge 应该只做格式转换。如果开始做"判断要不要转发"、"根据条件选择路由"，就成了隐式业务逻辑。
791	
792	**风险 3："我就读这一个值"的诱惑**
793	开发中容易想直接 import 内部 state。一次破例变成两次、三次。防御：feature 内部文件不从 public.ts 导出，外部 import 不到。
794	
795	**风险 4：runtime 膨胀**
796	runtime 是唯一知道所有 feature 的地方。如果开始做业务判断，就成了新的屎山中心。runtime 必须只做接线不做判断。

819	### 12.1 架构风险审计结论
820	
821	**整体评估：架构根基扎实，零生产代码违规。**
822	
823	| 维度 | 违规数 | 评级 |
824	|------|--------|------|
825	| Feature ↔ Feature（17 处跨 feature import） | 0 | A+ |
826	| Runtime ↔ Feature（~20 处引用） | 0 | A |
827	| Pages/Widgets ↔ Feature（3 个文件） | 0 | A |
828	| Shared 自身合规 | 0 | A- |
829	| Store 单点写入（36 个写入点） | 0 违规 | A |

831	关键事实：
832	- 17 处跨 feature import 全部通过 index.ts（public API），16/17 是 type-only
833	- 依赖方向形成 DAG 无环：frame/connection → receive/send → task
834	- Runtime 4 个 bridge 只做格式转换，不承载业务逻辑
835	- Shared 零 feature/框架依赖，ReadonlyDeep 被 10 个 feature 复用

841	
842	**P0 阻塞项：端到端集成测试完全缺失**
843	- 已有 23 个测试文件、417 个测试用例，全是单元级
844	- 缺失：fake adapter → routingTick → receive → task → send → result 完整链路

847	### 12.2 旧系统调研结论
848	
849	#### 表达式引擎（旧代码 1385 行核心）
850	
851	已有机制：
852	- Kahn 算法拓扑排序解决变量顺序问题（O(V+E) 时间复杂度）
853	- `configHash + timestamp` 缓存失效机制，LRU 最多 50 项，5 分钟过期
854	- 4 种数据源类型：CURRENT_FIELD / FRAME_FIELD / GLOBAL_STAT / SCOE_DATA
855	- `new Function(...keys, 'return (expression)')` 动态构造函数
856	- 数学函数直接绑定 Math.*，可省略 Math. 前缀
857	
858	旧实现问题：
859	- 并行计算导致顺序问题（原始实现并行计算所有表达式字段，字段 A 依赖 B 时可能用旧值）
860	- 无预编译机制（每次 new Function）
861	- 无表达式级缓存（相同表达式+相同输入不跳过）
862	- 持有 store 依赖（从 allFrameData 直接读，不纯）
863	- 循环依赖检测有但只回退不报错
864	
865	新系统指导：
866	- 必须保留：Kahn 拓扑排序、configHash 缓存失效、数学函数简化绑定
867	- 必须消灭：store 依赖、无预编译、并行计算
868	- 必须：解析和求值分离、纯函数化、支持预编译
869	
870	#### SCOE（旧代码 22 个文件）
871	
872	可复用模式：
873	- 策略模式执行器映射：`Record<ScoeCommandFunction, CommandExecutor>` 字典映射指令类型到执行器
874	- 统一执行上下文：`CommandExecutionContext` + `CommandExecutionResult` 标准化输入输出
875	- 异步轮询条件等待：`waitForCompletionConditions()` 100ms 间隔轮询，可配置超时
876	- 分层验证流程：帧识别→校验和→参数解析→指令执行→条件检查→回应
877	- 分层状态结构：`ScoeStatus` 包含接收数/成功数/错误数/运行时长
878	
879	需要消灭的问题：
880	- 跨 store 循环依赖（`receiveFramesStore.ts` 延迟初始化 `let scoeStore = null`）
881	- 重复帧实例管理（`scoeFrameInstancesStore.ts` 完整复制帧实例管理逻辑）
882	- SCOE 逻辑硬编码在通用接收流程（`receiveFramesStore.ts:922-1000`）
883	- 校验和逻辑散落、`Record<string, unknown>` 类型不安全传参、测试工具耦合核心 store
884	
885	#### 可视化（旧代码 1074 行核心 store）
886	
887	验证过的好模式：
888	- 循环缓冲区 `CircularBuffer<T>` 自动覆盖旧数据，容量按活跃图表数动态调整（0 图表:1000, 1 图表:5000, 2 图表:3000）
889	- ECharts 增量更新 `notMerge: false, silent: true, lazyUpdate: true`
890	- 时间格式化批量缓存 `formatTimestampsBatch()` + Map（最多 10000 条）
891	- 单次遍历同时处理时间戳和所有系列数据
892	- 配置持久化 `useStorage`
893	
894	需要改进：
895	- 多层定时器嵌套需要统一为单一定时器 + 事件分发
896	- 星座图无长期数据量上限（高频帧 + 长刷新间隔 = 内存累积）
897	- 表格硬编码 500ms 定时器
898	- 性能监控代码被注释
899	
900	#### 交叉发现：条件匹配散落三处
901	
902	| 位置 | 实现内容 |
903	|------|----------|
904	| SCOE 完成条件 | `CompletionCondition { sourceFrameId, sourceFieldId, useParam, targetParamId, targetFixedValue, operator, options }` |
905	| 表达式条件 | `ConditionalExpression { condition: string, expression: string }` |
906	| 任务触发条件 | 独立的 trigger check 逻辑 |

908	三套独立实现是新系统 shared/condition/ 统一收口的重点目标。

957	## 十三、全局原则总结
958	
959	1. **传输层是一个整体**：串口、TCP/UDP、HTTPS 都是 connection 的 adapter，不按类型拆阶段
960	2. **帧结构全局唯一**：不存在第二套帧模型，旧 SCOE 独立帧列表必须消灭
961	3. **表达式引擎是 shared/ 纯函数**：带依赖排序的求值器，全部外部传参，不持有状态
962	4. **条件匹配分两层**：匹配逻辑（shared/）+ 触发行为（各 feature）
963	5. **SCOE 和新甲方统一为"指令接入"**：外部系统控我们，走同一套指令接入路径
964	6. **存储、可视化、条件触发是独立模块**：receive 只是调用方，不拥有它们
965	7. **单点写入**：每个状态只有 owner feature 能写，外部只能读 selector
966	8. **runtime 只做接线不做判断**：composition root，不承载业务逻辑
967	9. **main 不装业务逻辑**：只做平台资源和必要的高频性能处理
968	10. **跨模块共用件时刻注意**：最容易耦合深的地方，必须严格通过 public API
969	11. **子 agent 积极使用**：brainstorm 用 explore agent 并行查旧代码和架构文档；design 用 explore agent 确认 public API 对接；impl 拆 executor agent 并行；accept 用独立 verifier agent

## 总结

frame-real design 总体覆盖了全局规划的三项核心需求（JSON schema、frameReader、迁移），与 shared/expression 的对接可行，与旧系统的类型映射基本到位。但存在五个实质性缺口：`factor` 字段在新类型中完全缺失（1918 处旧使用）、`identifierRules` 的 `startIndex/endIndex` 存在字符串与数字的类型不一致未被设计提及、checksum 方法枚举未定稿、消费者接口（特别是 send 构帧和 receive 帧匹配）缺少显式契约声明、以及 `ExpressionSourceType` 扩展策略未纳入 design。

## A. 需求覆盖度

### A1. 三项核心需求覆盖

- ✅ **JSON schema 定稿**：Design FR-NOUN-003 定义了 `FrameAssetFile { schemaVersion: 1, frames: FrameAsset[] }`，序列化/反序列化规则、旧格式识别策略（缺 schemaVersion 走 legacy path）都有明确描述。SC1 和 SC6 验收场景覆盖了 round-trip。
- ✅ **真实 frameReader 实现**：Design FR-NOUN-004 确认了 `FrameAssetReader` 接口已有骨架代码（`rewrite/src/features/frame/services/frame-asset-service.ts:26-34`），并明确了构造函数注入到 L2 消费者的路径。SC3 验收场景覆盖了只读快照不可变性。
- ✅ **旧格式迁移脚本**：Design FR-ORCH-001 定义了完整迁移流程，`core/legacy.ts` 和 `core/legacy-normalizers.ts` 已有骨架。SC2 验收场景覆盖了旧样本迁移。

### A2. "全系统基础字典"定位

- ✅ Design 的 cross-feature interface registry（Section 4）列出了 receive/send/task/指令接入/runtime/bootstrap 六个消费者，接口方向和层级都有说明。
- ⚠️ **receive 的帧匹配能力契约不够显式**。Design FR-NOUN-001 定义了 `IdentifierRule` 类型，但未明确说明 receive 做帧匹配时需要从 frameReader 获取哪些数据。旧系统实际的帧匹配流程（`receiveFramesStore` 中的 `identifierRules` 消费逻辑）没有在 design 中作为 receive 的接口契约来声明。当前 `FrameAssetReader` 只暴露 `getFrame()` 返回整个 `ReadonlyFrameAsset`（包含 `identifierRules`），receive 需要自己解析。这是可行的，但缺少一个明确的"receive 如何消费 identifierRules 做帧匹配"的接口说明。
- ⚠️ **send 的帧构造契约不够显式**。Send 需要：字段定义、options（autoChecksum/bigEndian/includeLengthField）、checksum 计算参数（validOption）、表达式定义。当前 `FrameAssetReader.getFrame()` 返回完整 `FrameAsset`，send 可以直接读取所有这些信息，但 design 没有显式列出 send 构帧时从 frame asset 读取哪些字段。建议在 cross-feature interface registry 中补充 send/receive 的具体字段消费清单。

### A3. 关键路径 frame-real -> receive-real

- ✅ 关键路径已在全局规划 14.5 明确。frame-real 产出 `FrameAssetReader`，receive-real 通过构造函数注入消费。
- ⚠️ receive-real 需要的核心能力——帧匹配（identifierRules 匹配字节流）、字段提取（按 dataType/length 从字节偏移提取值）、表达式求值（按 expressionConfig 计算间接字段）——都在 `FrameAsset` 类型中有对应字段，但没有在 design 中作为"receive 对 frame 的最小接口需求"显式列出。这不会阻碍实现，但会在 receive-real 进入 design 时产生重复确认成本。

## B. 扩展性风险

### B1. 新字段类型

- ⚠️ `FRAME_DATA_TYPES` 在 `core/types.ts:2-14` 是 `as const` 元组，扩展需要修改这个元组并同步修改所有 switch/case 或类型判断。当前类型覆盖了 uint8/16/32/64、int8/16/32/64、float、double、bytes。如果未来要加 BCD 码、位域（bitfield）等，需要：
  1. 在元组中新增值
  2. 在 legacy-normalizers.ts 的 `normalizeDataType` 中处理
  3. 在 receive/send 的编解码逻辑中处理
  - 当前 design 没有讨论 dataType 扩展策略。`as const` 元组模式本身是可扩展的，但缺少版本化策略。

### B2. 新 identifierRule operator

- ✅ Design FR-NOUN-001 定义了 `operator: 'eq' | 'neq' | 'gt' | 'lt' | 'range' | 'mask' | 'any'`。这是字面量联合类型，扩展方式明确：添加新的字面量值。旧 JSON 样本（`3.json`、`5.json`）中实际只使用了 `eq`，说明当前 operator 集合是前瞻性的。风险可控。

### B3. 新 ExpressionSourceType

- ⚠️ 当前 `EXPRESSION_SOURCE_TYPES` 是 `['current_field', 'frame_field', 'global_stat']`（`core/types.ts:17`）。旧系统还有 `'scoe_data'`，design 明确说"归入指令接入 runtime 提供"。但未来如果有新的数据源（比如"任务参数"、"northbound 回传值"），需要修改这个常量。Design 没有讨论 `ExpressionSourceType` 的扩展策略和版本兼容。建议：至少记录一个"新增 sourceType 时的检查清单"。

### B4. schemaVersion 演进策略

- ✅ Design FR-NOUN-003 使用 `schemaVersion: 1` 作为版本标识，缺省走 legacy path。这是标准做法。
- ⚠️ Design 没有讨论 schemaVersion 从 1 升到 2 时的迁移策略。比如：旧版本文件如何被新版本 reader 识别和升级？建议至少声明一条原则："新 reader 必须能读旧 schemaVersion 的文件，必要时做 inline migration"。

### B5. 附加 metadata（如 report 用帧描述）

- ✅ `FrameAsset` 当前有 `description`、`frameType`、`protocol` 等可选字符串字段。未来附加 metadata 可以通过新增可选字段实现，`FrameAssetFile` 的"多余字段忽略"策略（SC1 边界条件）确保了前向兼容。
- ⚠️ Design 没有明确声明"未来新增字段的 schema 兼容原则"。建议补充一条：新字段必须是可选的，旧 reader 遇到未知字段必须忽略不报错。

## C. 与消费者的接口充分性

### C1. receive 做帧匹配

- ✅ receive 通过 `frameReader.getFrame(id)` 获取完整 `FrameAsset`，其中包含 `identifierRules`、`fields`（含 `dataType`、`length`、`expressionConfig`）。帧匹配所需的所有元数据都在 `FrameAsset` 上。
- ⚠️ **缺少"按方向批量查询 receive 帧列表"的便利方法**。当前 `findFrames({ direction: 'receive' })` 返回所有 receive 方向帧的完整深拷贝。如果 receive 有几十个帧定义，每帧几十个字段，每次调用都深拷贝所有帧可能成为性能瓶颈。建议考虑提供一个轻量级的 `listFramesForDirection(direction)` 只返回 id + identifierRules 摘要。但这不是阻断项，可以在 receive-real 实现时根据实际性能数据决定。

### C2. send 做帧构造

- ✅ send 通过 `frameReader.getFrame(id)` 获取完整 `FrameAsset`，其中包含 `fields`（含 `defaultValue`、`configurable`、`options`、`inputType`）、`options`（`autoChecksum`、`bigEndian`、`includeLengthField`）、`validOption`（checksum 配置）。构造所需的所有信息都在 `FrameAsset` 上。
- ⚠️ Design 没有显式列出 send 构帧时对 `FrameAsset` 各字段的使用方式。checksum 计算尤其值得关注——`validOption` 的 `startFieldIndex` 和 `endFieldIndex` 是 string 类型（`core/types.ts:32-33`），在实际计算时需要 parseInt。这个 string 类型是旧系统遗留，新 design 的 FR-NOUN-001 只类型化了 `identifierRules`，没有处理 `validOption` 的类型。

### C3. task 做条件配置

- ✅ task 通过 `frameReader.listFieldReferences()` 获取 `FrameFieldReference[]`，其中包含 `frameId`、`fieldId`、`fieldName`、`dataType`、`inputType`、`dataParticipationType`。task 条件配置需要的帧/字段引用选项都在这个接口中。
- ✅ `frameReader.listFrameReferences()` 提供了帧级别的引用选项（id + name + direction + fieldCount）。

### C4. 指令接入做命令翻译

- ✅ 指令接入通过 `frameReader.getFrame(id)` 获取帧定义，可以将外部命令中的帧 ID 映射到内部帧定义。
- ⚠️ Design 明确说"frame-real 的 public API 不提供创建帧实例副本能力"（Section 1.5）。指令接入如需执行帧快照，由其 runtime context 内部管理。这意味着指令接入需要自己实现"根据 FrameAsset 构造发送字节"的逻辑（或委托 send service）。这个决策是合理的（避免帧实例副本回到 frame），但需要在指令接入 design 中明确。

### E4. factor 字段

- ❌ **`factor` 字段在旧 JSON 中大量使用（1918 处、17 个文件），但在新 `FrameFieldDefinition` 类型中完全缺失**。旧类型定义（`src/types/frames/fields.ts:53`）有 `factor?: number`，实际数据中 factor 既有数字（`"factor": 1`）也有字符串（`"factor": "10"`、`"factor": "0.01"`、`"factor": "0.390625"`）。factor 是接收端做值换算的系数（raw_value * factor = 物理值），也是发送端做逆换算的依据。frame-real design 完全没有提及 factor 的处置策略——是保留到新类型？还是移到表达式引擎处理？如果用表达式替代，迁移脚本需要为每个有 factor 的字段自动生成 `raw_value * factor` 的表达式配置。这不是小工作量，且会改变旧数据语义。

### E5. checksumMethod 值域

- ⚠️ 旧 JSON 中 `checksumMethod` 的实际值包括 `"sum8"`、`"xor8"`、`"crc16"`、`"crc32"`、`"custom"`（见 `src/types/frames/fields.ts:87` 的注释）。新 `FrameChecksumDefinition.checksumMethod` 是 `string?` 类型，没有枚举约束。Design 没有讨论 checksumMethod 的值域定稿。这不会阻断 frame-real，但会在 send-real 实现时成为缺口——send 构帧时需要知道支持哪些 checksum 算法。

### E6. expressionConfig.cache

- ✅ 旧 `ExpressionConfig` 有 `cache` 字段（`src/types/frames/fields.ts:41-45`），包含 `lastVariableValues`、`lastResult`、`timestamp`。这是运行时缓存，不是帧定义的一部分。新 design 刻意不保留。`legacy-normalizers.ts:165-188` 的 `normalizeExpression` 只提取 `expressions` 和 `variables`，不提取 `cache`。处理正确。

---

## 总体评估

frame-real design 整体质量较高，架构决策对齐检查（Section 1）逐一核对了 6 项后续架构决策，push strategy 和 acceptance contract 都有明确的退出信号。FrameReader 的接口设计与现有代码骨架吻合度高，与 shared/expression 的类型对接验证了实际可行性。

主要风险集中在两个方面：

1. **factor 字段缺失**——这不是 design 遗漏可以简单补上的问题，而是需要做一个架构决策：factor 是作为字段属性保留在 FrameAsset 中，还是用表达式引擎替代？前者简单直接但增加了 frame 类型的复杂度；后者保持了 frame 的纯粹性但增加了迁移成本和表达式引擎的负担。

2. **identifierRules 迁移归一化缺失**——这是一个实现层面的 bug，但需要在 design 中明确修正方向。

## 改进建议列表

| # | 建议 | 优先级 | 风险等级 | 说明 |
|---|------|--------|---------|------|
| 1 | **factor 字段决策** | P0 | 高 | 需要在 frame-real design 中明确 factor 的处置策略。如果保留，添加到 `FrameFieldDefinition` 并更新 legacy-normalizers；如果用表达式替代，迁移脚本需要自动生成 `raw * factor` 表达式。无论哪种，1918 处使用不能忽略。 |
| 2 | **identifierRules 归一化** | P0 | 中 | legacy-normalizers.ts 的 `normalizeFrame` 需要对 identifierRules 内部的 `startIndex`/`endIndex` 做字符串到数字的转换，`operator` 做枚举校验。当前直接透传会导致类型不匹配。 |
| 3 | **validOption 字段类型化** | P1 | 中 | `startFieldIndex`/`endFieldIndex` 在旧 JSON 和新类型中都是 string，但实际使用时需要 parseInt。建议在新类型中改为 number，迁移时做转换。 |
