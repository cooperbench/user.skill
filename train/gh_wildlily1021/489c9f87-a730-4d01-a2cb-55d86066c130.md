架构已明确 result / report / northbound 必须独立 feature，各有专属 owner：

| Feature | Owns | Does NOT own |
|---------|------|-------------|
| `result/` | 内部结果事实、归因规则、结果 read model | 报告文件生成、外部交付 |
| `report/` | 报告对象生成、报告素材收集、报告文件准备 | HTTP/FTP 上传、内部结果定义 |
| `northbound/` | HTTPS 推送、外部投影、外部错误语义 | 内部 task/result/report 真相 |

三层链路：`task → result → report → northbound`。外部交付失败不得重写内部结果事实。

### F2. Task 已有但缺关键事件

**已有**：
- `TaskInstanceState`：lifecycle 状态 + stepResults[]
- `TaskStepResult`：SendStepResult / WaitConditionStepResult / DelayStepResult
- `TaskExecutionSummary`：kind (completed/stopped/failed) + 步骤统计 + 耗时
- `onSettled()` Promise：任务终态通知

**缺失**：
- `TaskInstanceCompletion` 事件类型——旧 design 提到但代码中未实现
- 跨 feature 的任务完成事件发射机制

### F3. Command-ingress 结果通过 task 间接产出

SCOE 外部命令 → command-ingress 解析 → 创建 task 实例 → task 执行 → TaskInstanceCompletion。command-ingress 自身只维护 success/error count 统计，不产出独立结果类型。

### F4. 旧系统无独立 result owner

旧系统结果相关能力分散在多个 store：
- `historyAnalysis`：历史数据查询、图表展示
- `dataDisplayStore`：实时采集、录制、环形缓冲
- `globalStatsStore`：系统统计
- `scoeStore`：SCOE 命令计数
- CSV 导出：唯一的报告格式

**旧系统没有 northbound**。数据全本地闭环。

### F5. 旧系统可观测行为清单

| 行为 | 新系统归属 |
|------|-----------|
| 定时采集帧数据、存 JSON 小时文件 | storage-real（已有） |
| 按时间范围查询历史数据 | storage-real |
| CSV 导出 | report（本 feature） |
| 图表展示 | visualization |
| 系统统计（收发计数、匹配率） | 各 feature 的 read model |
| SCOE 命令执行跟踪 | command-ingress + task |
| 多图表配置持久化 | visualization / settings |

### F6. 当前进度与依赖

```
expression-engine ✅ → frame-real ✅ → receive-real 🔄 → task-real ✅ → command-ingress ✅ → result-report ⏳ → northbound ⏳
```

result-report 只依赖 task（已完成），可立即启动。report 的素材收集可能需要 storage（依赖 receive-real），但 result 核心收集不依赖。

## 关键设计决策讨论

### D1: 结果收集的输入通道

result 消费什么？

**方案 A（推荐）**：result 只消费 `TaskInstanceCompletion` 事件。send/receive 的原始事实经 task step 包装后才进入 result。与已有 design 一致。

**方案 B**：result 也接受手动操作入口（手动发帧、手动操作）的独立结果。

**分析**：
- 方案 B 增加复杂度——需要定义"手动结果"的语义，而手动操作没有步骤结构
- 如果用户需要记录手动操作为结果，可以通过 UI 创建单步 task
- command-ingress 的外部命令已经通过 task 包装，不需要额外通道
- **建议选 A**，手动操作的需求通过 task 包装解决

**需要确认**：是否有"纯手动操作也必须出报告"的业务场景？如果有，方案 B 必须支持。

### D2: TaskInstanceCompletion 的形状

旧 design 定义了但未实现。建议：

```typescript
interface TaskInstanceCompletion {
  readonly instanceId: string;
  readonly taskDefinitionId: string;
  readonly kind: 'completed' | 'stopped' | 'failed';
  readonly summary: {
    readonly stepsTotal: number;
    readonly stepsSucceeded: number;
    readonly stepsFailed: number;
    readonly stepsSkipped: number;
  };
  readonly durationMs: number;
  readonly startedAt: string;
  readonly finishedAt: string;
  readonly stepResults: readonly TaskStepResult[];
}
```

**关键问题**：stepResults 是内嵌在 completion 事件中，还是 result 通过 selector 回查 task？

**建议**：内嵌在 completion 中。理由——result 收集时需要完整的步骤结果快照，不应依赖 task feature 的状态还在内存中。

### D3: CaseResult 与 ResultAggregationRule

每个 task instance 完成后，result 需要产出 CaseResult（用例结果）。关键问题：

1. **CaseResult.kind 枚举**：`pass | fail | skip | inconclusive`？还是更细粒度？
2. **归因规则**：如何从 step results 推导 case result kind？
   - 简单方案：所有步骤成功 → pass，任一步骤失败 → fail，被跳过 → skip
   - 复杂方案：可配置的 ResultAggregationRule（表达式引擎驱动）
3. **一个 task definition 多次执行**：每次执行产出一个 CaseResult，汇总为 TaskResultSummary

**建议**：MVP 用简单方案（步骤全 pass → case pass，有 fail → case fail），复杂归因作为后续增强。ResultAggregationRule 的接口先预留，实现先用硬编码规则。

### D4: 手动操作结果的统一收集

这是任务列表中明确提到的问题。分析：

| 操作类型 | 旧系统如何处理 | 新系统建议 |
|---------|--------------|-----------|
| 自动 task 执行 | 无独立跟踪 | TaskInstanceCompletion → result |
| SCOE 外部命令 | SCOE store 计数 | 通过 command-ingress → task → TaskInstanceCompletion → result |
| 手动发帧 | dataDisplayStore 记录 | 只走 send + storage，不产生 result |
| 手动操作 | 无跟踪 | 不产生 result，除非包装成 task |

**结论**：result 只消费 task 产出的结果。手动操作如需出报告，创建 task 包装。"统一收集"的"统一"体现在——所有需要出结果的都通过 task 走。

### D5: 报告生成与素材来源

Report 从哪里拿素材？

```
素材来源：
├── result feature → CaseResult[], TaskResultSummary
├── storage feature → 历史参数数据（可选）
├── task feature → task 定义、参数配置
├── settings → 报告模板、输出路径
└── frame feature → 帧定义、字段定义
```

**报告格式优先级**：
1. **MVP**：JSON TestReport（结构化数据，方便 northbound 消费）
2. **V1**：CSV 导出（保留旧行为）
3. **V2**：PDF（甲方需求确认后）
4. **V3**：Word/Excel（甲方需求确认后）

**关键约束**：JSON TestReport 的 schema 需要甲方确认，当前阶段只能做内部格式，不能冻结甲方 schema。

### D6: 报告持久化策略

| 策略 | 说明 | 建议 |
|------|------|------|
| 内存 | 结果 read model 在 Pinia store | 是，result 的 read model |
| 本地文件 | 报告文件存磁盘 | 是，通过 platform facade |
| 数据库 | SQLite/IndexedDB | 不建议，当前阶段用 JSON 文件 |
| 远程 | 上传到外部系统 | northbound 的职责 |

**建议**：
- Result：内存 + 可选的 JSON 快照持久化（用于断电恢复）
- Report：文件系统存储，通过 platform facade 写文件
- 导出格式按 D5 优先级逐步添加

## Conclusions

### 1. 要做什么

**Result feature（结果收集归口）**：
- 消费 `TaskInstanceCompletion` 事件（task 终态时发射）
- 为每个 task instance 产出 `CaseResult`（用例结果：pass/fail/skip）
- 为每个 task definition 维护 `TaskResultSummary`（多次执行汇总）
- 提供 `ResultReadModel`（面向 UI 的只读快照）
- 结果归因规则（MVP：步骤全 pass → case pass，有 fail → case fail）

**Report feature（报告生成）**：
- 从 result + storage + settings 收集素材
- 生成结构化报告对象（JSON TestReport）
- 支持报告文件准备和本地存储
- MVP 支持 JSON 格式，V1 支持 CSV 导出

**先验预测**：在一个客户格式未知且 `result/`、`report/` 和 `northbound/` 代码尚不存在的项目中，针对“结果报告”的头脑风暴中，最有可能出现的问题是：（1）过早的模板抽象，（2）为了“未来可能需要”而设计的层级，这些层级在MVP中并未实际需要，（3）将结果与现有任务（task）状态分离的人为边界。所有三项预测都得到了证实。

### 1. 模板驱动的报告格式 -- 截断 (CUT)

头脑风暴声称“模板驱动的报告生成具有可配置的字段映射”，以处理客户格式变更。

**为什么它是错的**：客户尚未确认任何格式。northbound overlap map (`codestable/compound/2026-04-28-northbound-overlap-and-gap-map.md` 第186行) 明确指出：

> "What exact JSON TestReport depth is required: task layer, case layer, details, checkpoints, statistics items?"

以及第188行：

> "What are the required file naming, directory, overwrite, retry, and retention rules for FTP?"

未确认的格式数量为零。构建一个模板引擎来“处理未来的格式变更”是在为一个不存在的需求进行优化。这正是“模板驱动报告”这一反模式：它为一个静态格式增加了一层配置复杂性，而当你最终了解了该格式时，该复杂性并不能为你节省任何工作，然后你还得将模板引擎迁移到实际格式上。

**如何截断**：对当前已知的结构进行硬编码。单个 `generateReport(taskInstanceCompletion)` 函数，它生成一个 JSON 对象。当客户确认格式后，你将修改该函数。如果你发现自己在为同一个客户手动修改了3次，那么再提取模板引擎也不迟。此时你将拥有实际的需求来驱动模板设计。

**更简单的替代方案**：
```ts
function generateCaseReport(completion: TaskInstanceCompletion): CaseReportJson {
  return {
    taskId: completion.definitionRef.id,
    taskName: completion.definitionRef.name,
    result: completion.summary.kind === 'completed' ? 'pass' : 'fail',
    steps: completion.stepResults.map(s => ({
      index: s.stepIndex,
      kind: s.kind,
      status: isStepFailed(s) ? 'fail' : 'pass',
    })),
    startedAt: completion.startedAt,
    finishedAt: completion.finishedAt,
    durationMs: completion.summary.durationMs,
  };
}
```

以后再添加模板引擎只需进行局部重构，不会破坏任何架构。

### 2. CaseResult 作为独立概念 -- 简化 (SIMPLIFY)

头脑风暴声称 `CaseResult` 不同于 `TaskExecutionSummary`。任务（task）已经包含了 `TaskExecutionSummary` (`rewrite/src/features/task/core/types.ts:227-238`)，其中有：

```ts
export interface TaskExecutionSummary {
  readonly kind: 'completed' | 'stopped' | 'failed';
  readonly summary: {
    readonly stepsTotal: number;
    readonly stepsSucceeded: number;
    readonly stepsFailed: number;
    readonly stepsSkipped: number;
  };
  readonly durationMs: number;
  readonly startedAt: string;
  readonly finishedAt: string;
}
```

此外，`TaskInstanceState` 已包含完整的 `stepResults: readonly TaskStepResult[]`。任务实例已经拥有了结果功能所需的所有信息。

头脑风暴声称“所有步骤都通过则通过，任何步骤失败则失败”是MVP的规则。这是一个可以直接在 `TaskExecutionSummary` 上计算的判断，无需单独的概念。

**为什么需要简化**：`CaseResult` 与 `TaskExecutionSummary` 加一个通过/失败判断的组合完全重叠。该判断是一个函数 `(summary: TaskExecutionSummary) => 'pass' | 'fail'`，而不是一种新的数据类型。

**更简单的替代方案**：结果功能（Result feature）直接消费 `TaskInstanceState`（其中包含 `stepResults` 和生命周期终端状态）。通过/失败的判断是一个纯函数。无需单独的 `CaseResult` 类型。如果northbound以后需要一个不同的概念，那时再进行映射。

### 3. TaskResultSummary (多执行聚合) -- 截断 (CUT)

头脑风暴声称“按任务定义维护 `TaskResultSummary`”。这意味着跨同一任务定义的多次执行进行聚合。

**为什么它是错的**：MVP中是否存在将同一任务定义运行多次并聚合结果的实际用户场景？查看 `TaskStatisticsSnapshot` (`rewrite/src/features/task/state/task-state.ts:14-23`)，任务功能已经跟踪：

```ts
export interface TaskStatisticsSnapshot {
  readonly totalCreated: number;
  readonly totalCompleted: number;
  readonly totalStopped: number;
  readonly totalFailed: number;
  readonly totalStepsExecuted: number;
  readonly totalStepsSucceeded: number;
  readonly totalStepsFailed: number;
  readonly totalStepsSkipped: number;
}
```

这些是全局统计数据，而不是按定义的。但问题是：谁会在MVP中消费按定义的聚合？不是UI（尚未有结果页面）。不是报告（它处理的是单个执行）。也不是northbound（尚未构建，并且无论如何都会定义自己的外部语义）。

**如何截断**：这完全是一个YAGNI（你不会需要它）。如果以后某个消费者需要按定义的聚合，它可以查询历史记录（`selectTaskHistory` 已返回带有 `definitionRef` 的已完成实例）并进行自身的聚合。无需在结果功能（Result feature）中进行提前实现。

### 4. ResultReadModel 作为独立概念 -- 截断 (CUT)

头脑风暴声称结果提供了“用于UI的 `ResultReadModel`”。

**为什么它是错的**：任务功能已暴露：
- `getSnapshot()` 返回 `TaskStateSnapshot`，包含 `instances` 和 `history`
- `getInstance(id)` 返回 `TaskInstanceState`，包含 `stepResults`、`lifecycle`、时间戳
- `getProgress(id)` 返回 `TaskProgress`，包含步进级别的进度
- `getStatistics()` 返回 `TaskStatisticsSnapshot`
- `selectTaskHistory()` 返回历史实例

如果一个 `ResultReadModel` 包含“任务的结果数据”，那么它就是任务选择器（task selectors）已经提供的功能的一个子集。如果一个 `ResultReadModel` 包含“通过/失败判断”，那么这就是一个函数，而不是一个读取模型（read model）。

**如何截断**：MVP的UI将使用任务选择器来显示任务完成状态。通过/失败的判断作为从 `TaskInstanceState` 派生的显示级计算（一个选择器函数或计算属性）。无需单独的结果状态容器。

如果northbound以后需要内部模型的不同投影，northbound可以自行拥有该投影。

### 5. 独立的 `result/` 和 `report/` 目录 -- 简化 (SIMPLIFY)

头脑风暴声称 `result/` 和 `report/` 是独立的功能目录，采用三层结构：`result` -> `report` -> `northbound`。

**该主张中有效的一部分**：Feature interaction matrix (`codestable/architecture/rewrite-feature-interaction-matrix.md` 第204行) 确实将 `result -> report` 和 `report -> northbound` 列为独立的交互。目标结构文档将它们分开。因此，架构愿景是正确的。

**为什么需要简化**：MVP无需如此。剥离了头脑风暴中多余的层级后，实际需要编写的代码如下：
- 一个当任务（task）终止时运行的函数，用于判断通过/失败（10行代码）
- 一个将任务完成数据结构化为 JSON 的函数（30行代码）
- 一个写入 JSON 的函数（10行代码）

这总共约50行代码。将这50行代码拆分成两个功能目录，每个目录包含 `core/`、`services/`、`adapters/`、`selectors/`、`state/`、`index.ts`、`fixtures/` 和 `__tests__/`，这种做法是不合比例的。

**更简单的替代方案**：一个包含结果收集和报告生成的 `result/` 功能。内部的模块边界（一个 `result/` 目录用于收集+判断，一个 `report/` 目录用于生成）无需在功能级别进行分离。当northbound实际构建时，报告生成可能会成为一个独立的功能，届时你将了解实际的格式。

交互矩阵在4.11节（`result -> report`）中的预设计门控写道：“在报告设计前决定结果/报告的分离”。该决定可以是：**本阶段不分离**。

### 6. 事件发射机制 -- 简化 (SIMPLIFY)

头脑风暴建议向任务功能（task feature）添加一个正式的事件发射机制，以便结果功能（result feature）能够消费“`TaskInstanceCompletion`”。

**为什么需要简化**：任务功能（Task feature）已经有 `onSettled(instanceId): Promise<void>`，它是一个 Promise，当实例达到终端状态时会解析。这是一种现有机制，不涉及任何新的基础设施。

交互矩阵中 `task -> result` 的交互 (`rewrite-feature-interaction-matrix.md` 第146行) 指出：

> "Decided: stop->stopped (not completed); result only consumes TaskInstanceCompletion, not raw send/receive events"

“`TaskInstanceCompletion`”这个概念尚不存在。`TaskExecutionSummary` 存在。`TaskInstanceState` 在其生命周期变为 `completed`、`stopped` 或 `failed` 时存在。带有时间戳和统计信息的“完成”已经嵌入其中。

**更简单的替代方案**：结果功能（Result feature）无需任何新的任务功能代码，通过以下方式之一消费任务完成事件：
1. **运行时编排（Runtime orchestration）**（最简单）：在运行时连接（runtime wiring）中，调用 `taskService.onSettled(id)` 后，将终端实例传递给结果收集。无需事件发射器，无需新的接口。
2. **轮询（Polling）**（也简单）：`selectTaskHistory()` 已经返回带有完整 `stepResults` 和 `lifecycle` 的已完成实例。结果功能只需读取历史记录。

运行时编排模式（Runtime orchestration pattern）已存在于项目中——`routingTick` 从连接（connection）排空事件到接收（receive）再通过桥接到任务（task）。对任务完成进行相同的操作（运行时连接（runtime wiring）在完成时调用结果功能（result feature））保持一致，无需新的事件基础设施。

**不需要**：正式的事件发射器、事件类型、订阅管理器或新适配器。

### 7. 来自 4+ 个功能的报告材料 -- 截断 (CUT)

头脑风暴声称报告从 `result + storage + settings + frame` 收集材料。

**为什么它是错的**：这不是MVP。这是完整的northbound交付愿景。对于MVP，最小可行的报告需要：
- 任务执行结果（已在 `TaskInstanceState` 中）
- 通过/失败判断（已从步进结果计算得出）

而已。设置（Settings）中有什么是MVP报告需要的？元数据？先硬编码。帧定义（Frame definitions）中有什么是报告需要的？帧名称？已在 `definitionRef.steps[].name` 中。存储（Storage）中有什么是报告需要的？历史参数值？那是“完整”的报告，不是MVP。

northbound的差距图（overlap map）本身明确表示客户格式未知。在格式未知的情况下，你不知道需要哪些材料。先构建最简单的东西（仅包含任务结果），然后在知道格式后再添加材料。

**如何截断**：MVP报告只消耗 `TaskInstanceState`。当客户确认格式并指定“我们需要帧X的字段Y”时，再通过公共选择器（public selectors）添加从帧/存储/设置中读取的功能。

### 8. Lane B 的声称 -- 修订 (REVISE)

头脑风暴声称这是“Lane B 单一功能设计”。

**为什么它是错的**：Lane B 被定义为“需要设计、实现和接受的闭环；单一会话能稳定地保持上下文；无需大的需求分解；无需跨会话交接。”

头脑风暴涉及：
- 2个独立的功能（结果 + 报告）
- 对任务功能（task feature）的修改（事件发射）
- 4个以上的跨功能依赖
- 未知的客户格式
- 未确认的northbound模式

这并非 Lane B。这要么是：
- **两个 Lane B 功能**（首先是结果，然后是报告），各自限定范围，或者
- 如果将范围严格界定为“收集任务完成 + 生成一个 JSON blob”，则是一个 **Lane A 快进通道**。

全球规划文档（`codestable/compound/2026-05-07-runtime-next-phase-global-planning.md` 第996行）中写道：

> "8 | result-report | 结果收集归口 + 报告生成 | 否 | 10% | Wave 5，仅有骨架"

这被列为一个 `cs-feat`。但是 `cs-feat` 拆分规则（第979-981行）写道：“如果在设计过程中发现范围超出预期（检查清单步骤 > 8 或估计行数接近1000），则在设计阶段主动拆分为两个独立的功能。”

考虑到当前头脑风暴的范围，它应拆分为：
1. **结果收集（Result collection）**：消费任务完成，计算通过/失败，存储结果事实。这是一个 Lane B 的 `cs-feat`。
2. **报告生成（Report generation）**：将结果事实转化为结构化 JSON/文件。在客户确认格式之前，这还是一个空壳。

**[CRITICAL] 1. Task feature does not emit any completion event -- the brainstorm's core prerequisite does not exist yet.**

Evidence: The task service (`/mnt/d/code/frontend/dongfanghong/rewrite/src/features/task/services/task-service.ts`) has no event emission mechanism whatsoever. The existing result design doc (`rewrite-result-design.md`, section 4.15) already lists this as a blocker: "task service needs to output TaskInstanceCompletion event."

The brainstorm correctly identifies this gap but underestimates its scope. Adding a task completion event requires:
- Defining the `TaskInstanceCompletion` payload type (the brainstorm and design doc assume it exists but neither specifies where it lives -- in task types? a shared event type?).

- Deciding the emission mechanism: callback, explicit event source interface, or runtime polling of task state.
- The existing result checklist line 123 confirms this is still blocked.

Fix: The brainstorm must either (a) explicitly scope task event emission as a prerequisite task within the result-report feature and specify the mechanism, or (b) treat it as a separate mini-feature to complete first.
