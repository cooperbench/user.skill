## 关键设计决策讨论

### D1: 结果收集的输入通道

result 消费什么？

**方案 A（推荐）**：result 只消费 `TaskInstanceCompletion` 事件。send/receive 的原始事实经 task step 包装后才进入 result。与已有 design 一致。

**方案 B**：result 也接受手动操作入口（手动发帧、手动操作）的独立结果。

**分析**：
- 方案 B 增加复杂度——需要定义"手动结果"的语义，而手动操作没有步骤结构
- 如果用户需要记录手动操作为结果，可以通过 UI 创建单步 task
- command-ingress 的外部命令已经通过 task 包装，不需要额外通道
- **建议选 A**，手动操作的需求通过 task 包装解决

**需要确认**：是否有"纯手动操作也必须出报告"的业务场景？如果有，方案 B 必须支持。

### D2: TaskInstanceCompletion 的形状

旧 design 定义了但未实现。建议：

```typescript
interface TaskInstanceCompletion {
  readonly instanceId: string;
  readonly taskDefinitionId: string;
  readonly kind: 'completed' | 'stopped' | 'failed';
  readonly summary: {
    readonly stepsTotal: number;
    readonly stepsSucceeded: number;
    readonly stepsFailed: number;
    readonly stepsSkipped: number;
  };
  readonly durationMs: number;
  readonly startedAt: string;
  readonly finishedAt: string;
  readonly stepResults: readonly TaskStepResult[];
}
```

**关键问题**：stepResults 是内嵌在 completion 事件中，还是 result 通过 selector 回查 task？

**建议**：内嵌在 completion 中。理由——result 收集时需要完整的步骤结果快照，不应依赖 task feature 的状态还在内存中。

### D3: CaseResult 与 ResultAggregationRule

每个 task instance 完成后，result 需要产出 CaseResult（用例结果）。关键问题：

1. **CaseResult.kind 枚举**：`pass | fail | skip | inconclusive`？还是更细粒度？
2. **归因规则**：如何从 step results 推导 case result kind？
   - 简单方案：所有步骤成功 → pass，任一步骤失败 → fail，被跳过 → skip
   - 复杂方案：可配置的 ResultAggregationRule（表达式引擎驱动）
3. **一个 task definition 多次执行**：每次执行产出一个 CaseResult，汇总为 TaskResultSummary

**建议**：MVP 用简单方案（步骤全 pass → case pass，有 fail → case fail），复杂归因作为后续增强。ResultAggregationRule 的接口先预留，实现先用硬编码规则。

### D4: 手动操作结果的统一收集

这是任务列表中明确提到的问题。分析：

| 操作类型 | 旧系统如何处理 | 新系统建议 |
|---------|--------------|-----------|
| 自动 task 执行 | 无独立跟踪 | TaskInstanceCompletion → result |
| SCOE 外部命令 | SCOE store 计数 | 通过 command-ingress → task → TaskInstanceCompletion → result |
| 手动发帧 | dataDisplayStore 记录 | 只走 send + storage，不产生 result |
| 手动操作 | 无跟踪 | 不产生 result，除非包装成 task |

**结论**：result 只消费 task 产出的结果。手动操作如需出报告，创建 task 包装。"统一收集"的"统一"体现在——所有需要出结果的都通过 task 走。

### D5: 报告生成与素材来源

Report 从哪里拿素材？

```
素材来源：
├── result feature → CaseResult[], TaskResultSummary
├── storage feature → 历史参数数据（可选）
├── task feature → task 定义、参数配置
├── settings → 报告模板、输出路径
└── frame feature → 帧定义、字段定义
```

**报告格式优先级**：
1. **MVP**：JSON TestReport（结构化数据，方便 northbound 消费）
2. **V1**：CSV 导出（保留旧行为）
3. **V2**：PDF（甲方需求确认后）
4. **V3**：Word/Excel（甲方需求确认后）

**关键约束**：JSON TestReport 的 schema 需要甲方确认，当前阶段只能做内部格式，不能冻结甲方 schema。

### D6: 报告持久化策略

| 策略 | 说明 | 建议 |
|------|------|------|
| 内存 | 结果 read model 在 Pinia store | 是，result 的 read model |
| 本地文件 | 报告文件存磁盘 | 是，通过 platform facade |
| 数据库 | SQLite/IndexedDB | 不建议，当前阶段用 JSON 文件 |
| 远程 | 上传到外部系统 | northbound 的职责 |

**建议**：
- Result：内存 + 可选的 JSON 快照持久化（用于断电恢复）
- Report：文件系统存储，通过 platform facade 写文件
- 导出格式按 D5 优先级逐步添加

## Conclusions

### 1. 要做什么

**Result feature（结果收集归口）**：
- 消费 `TaskInstanceCompletion` 事件（task 终态时发射）
- 为每个 task instance 产出 `CaseResult`（用例结果：pass/fail/skip）
- 为每个 task definition 维护 `TaskResultSummary`（多次执行汇总）
- 提供 `ResultReadModel`（面向 UI 的只读快照）
- 结果归因规则（MVP：步骤全 pass → case pass，有 fail → case fail）

**Report feature（报告生成）**：
- 从 result + storage + settings 收集素材
- 生成结构化报告对象（JSON TestReport）
- 支持报告文件准备和本地存储
- MVP 支持 JSON 格式，V1 支持 CSV 导出

### 2. 不做什么

- 不做 HTTP/FTP 推送（northbound）
- 不直接消费 send/receive 原始事件
- 不承载 task step 执行逻辑
- 不做甲方 schema 冻结
- 不把 history/CSV 直接等同 TestReport
- 不把 northbound deviceId 等同串口 target
- 不在 main process 放结果/报告语义
- 不为手动操作建立独立结果通道（通过 task 包装）

### 3. 上游 feature 需要提供的接口

| Feature | 接口 | 当前状态 |
|---------|------|---------|

| storage | 历史参数数据查询 API | 待 storage-real 完成 |
| settings | 报告模板、输出路径 | 待确认 |
| frame | 帧定义、字段定义 | 已有 |

### 4. 是否需要走 cs-roadmap

**建议：不需要走 cs-roadmap，走 Lane B。**

- 可以在一个 design 文档中覆盖 result 和 report，明确两者边界

**实现分两阶段**：先 result（结果收集核心），再 report（报告生成）。

## 自检结果：需要修正的问题

### 坑 2：CaseResult 没必要独立存在

Task 已经有 `TaskExecutionSummary`（kind: completed/stopped/failed + 步骤统计 + 耗时）和 `stepResults[]`。pass/fail 判断就是一个纯函数 `(summary) => 'passed' | 'failed' | 'stopped'`，不需要新建类型。

### 坑 3：TaskResultSummary 聚合——没人消费

MVP 没有消费者需要"同一 task definition 多次执行汇总"。task 已经有 history + statistics。砍掉。

### 坑 4：ResultReadModel 多余

Task selectors 已经提供了 instance、progress、history、statistics。result 不需要自己的 read model，pass/fail 判断是一个 derived computation。

### 坑 5：我说"没有业务规则"但 result 确实拥有归因规则

归因判断（步骤结果 → 用例结论）就是 result 的业务规则。正确的说法是：result 不拥有 task/send/receive/SCOE 的执行规则和报告格式规则。

### 坑 6：我用错了 CaseResult kind 枚举

我写的 pass/fail/skip，但已有 design 和架构决策用的是 **passed/failed/stopped/partial**。`stopped` 是一等公民（架构决策：stop → stopped，不等于 failed）。

### 坑 7：不需要新的事件发射机制

Task 已有 `onSettled()` Promise。项目里已有 runtime 编排模式（routing-tick 从 connection 排到 receive 再到 task）。同样的模式：task 完成 → runtime 调 result 收集。不需要搞 event emitter。

### 坑 8：报告素材不用跨 4 个 feature

MVP 报告只需要 `TaskInstanceState`（已有 stepResults + lifecycle + timestamps）。frame/storage/settings 的素材等甲方确认格式再加。
