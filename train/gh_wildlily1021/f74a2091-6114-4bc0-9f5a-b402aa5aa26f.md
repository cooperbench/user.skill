几个我看到的：

**1. resolveFieldValues 拿来当预览引擎不太对**

这个函数是 send build 管线的内部步骤，一次性 resolve 所有字段。预览场景是用户改一个字段，只影响依赖它的表达式字段。用 resolveFieldValues 做预览 = 每次击键全量重算，字段多的时候浪费。而且直接 re-export 内部函数给 composable 用，等于 UI 耦合了 send core 的实现细节。

更好的做法：composable 按字段粒度调 `evaluateFieldExpressions`，只重算受影响的字段，不要全量走 resolveFieldValues。

**2. 配置持久化归属不清**

brainstorm 写了新建 `command-ingress/services/config-storage-service.ts`，等于 feature 内部做文件 I/O。但 CLAUDE.md 说文件读写是 platform facade 的事。如果 config-storage-service 直接调 platform facade 读写 JSON，那它只是个薄 wrapper；如果它自己管理存储逻辑，就违反了分层。

建议：composable 层直接调 platform facade 读写 JSON，不建 config-storage-service。feature service 不碰持久化。

**3. 帧实例持久化同理**

useSendInstances composable 存 ref + 调 platform facade 读写 JSON。那 command-ingress 的配置也走同样的路。两个模块用同一种持久化模式但没有共享抽象——各自写一遍 JSON 读写逻辑。

建议：如果两个地方都要"ref 状态 + JSON 持久化"这个模式，design 阶段考虑提取一个 `useJsonPersistence` 通用 composable 到 shared/ 或 widgets/，不各自重复。

**4. 任务详情组件复用的接口设计**

中心对接 Tab 复用任务页的执行监控组件（D-T5）。但甲方下发的任务和用户自建任务的元数据不同——甲方任务有上报状态、JSON 报告交付状态，用户任务没有。如果直接复用组件，要么组件 props 膨胀（加一堆可选的甲方专用字段），要么通过 slot/扩展点注入，要么拆成基础组件 + 甲方扩展组件。

这个不做决定也行，但 design 阶段要明确：复用的是整个组件还是拆出核心部分。

**5. Tab 切换丢状态**

QTab 默认销毁非激活 Tab 的组件。测试工具正在录 HEX 数据，切到配置 Tab 再切回来，录制状态丢了。任务编辑器填了一半，切到历史 Tab 再切回来，表单丢了。

解决：用 `keep-alive` 包裹 Tab 内容，或关键状态提升到 composable 层不受组件生命周期影响。这应该在 conventions 或 design 里明确。

## 设计范围

为 3 个页面产出 design 文件 + checklist：

### 页面 1: 帧发送页 /frames/send（模式B 三栏）
- 左栏帧格式列表、中栏帧实例表(DataTable)、右栏预览面板
- 帧实例数据模型 SendFrameInstance + useSendInstances composable
- 帧预览 useFramePreview composable（按字段粒度调 evaluateFieldExpressions）
- 字段编辑 Widget（共享组件）：字段分组渲染、表达式实时联动、视觉重设计
- 单帧发送流程（SendService.execute）
- 帧实例 JSON 持久化（platform facade）
- 不含任务管理，无跳转任务页入口

### 页面 2: 任务管理页 /tasks（模式A 主从双栏，独立页面）
- 左侧任务列表（Tab: 活动/历史）+ 右侧面板（定义态=编辑器 / 运行态=监控）
- 任务编辑器：调度配置(immediate/timer/event)、步骤编辑器(SendStep/WaitConditionStep/DelayStep)、高级配置(可变参数/停止条件/错误策略)
- 执行监控：StatusBadge + QLinearProgress + 步骤状态 + 操作按钮
- 任务状态映射：6 种 lifecycle + UI 层从 schedule.kind 推导 waiting-trigger/waiting-schedule
- SendStep 字段值方案 A（copy-on-create，独立 fieldValues，可用"复制上一步"）
- 任务导入导出（serialization）
- TaskExecutionDetail 基础组件（供本页和中心对接 Tab 复用）

### 页面 3: 指令接入页 /command-ingress（3 Tab）
- Tab 1 SCOE 运行与测试：统计卡片 + 命令日志 + 测试工具（HEX 收发/高亮）
- Tab 2 SCOE 配置：左右分栏（卫星列表 + 编辑区），命令配置用展开折叠（不用大弹窗）
- Tab 3 中心对接：连接状态 + [对接配置]弹窗 + [任务上报]弹窗 + 内部 Tab（任务列表|设备列表），任务详情弹窗复用 TaskExecutionDetail + 甲方扩展（上报状态）
- 甲方主流程：上报任务 → 接收任务 → 执行 → 用例结果上报 → JSON 报告交付
- SCOE 配置 JSON 持久化（platform facade）

### 跨页面共享
- useJsonPersistence 通用 composable（shared/composables/）
- TaskExecutionDetail 基础组件（widgets/），甲方扩展通过 slot/wrapper
- 字段编辑 Widget（widgets/），发送页和任务页 SendStep 共用

## Design 必须遵守的约束

1. 预览按字段粒度重算，不全量 resolveFieldValues
2. 持久化走 platform facade，feature service/core 不碰文件 I/O
3. 多个 composable 共享 useJsonPersistence 模式
4. TaskExecutionDetail 拆基础 + 扩展，不 props 膨胀
5. Tab 内容 keep-alive
6. 8+ composable 审视合并可能性
7. waitingFor 不改 core，UI 层从 instance.definitionRef.schedule.kind + lifecycle 推导
8. 不新建 config-storage-service，composable 直接调 platform facade
9. 甲方接口 schema 未确认，UI 骨架先设计，字段映射留扩展点
10. evaluateFieldExpressions 必须从 send/index.ts re-export
