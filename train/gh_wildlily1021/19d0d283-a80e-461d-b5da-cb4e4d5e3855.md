  高优先级

  1. 入站路径问题：SCOE 入站字节是"帧"吗？

  §4.6 的路径是 SCOE TCP → connection → receive 解析 → runtime 路由 → SCOE adapter。但 SCOE 入站字节是"指令码"，可能不符合 receive 通用帧格式。旧代码在 receiveFramesStore 里专门有 SCOE
  分支处理，说明它需要特殊解析。

  如果 SCOE 入站有自己协议（帧头/校验/帧尾），receive 按 frame definition 解析能覆盖吗？如果不能，SCOE 入站字节是否应该直接从 connection transport event 到 SCOE adapter（绕过 receive）？还是 receive
  需要支持"SCOE 帧格式"作为特殊帧定义？

  这个问题决定了 receive 是否需要知道 SCOE 的存在（违反边界），还是 SCOE 入站有自己的解析层。

  2. ExternalCommandAdapter 应该直接放 shared/

  当前决定放在 SCOE/core，理由是"只有两个消费者还不满足提取条件"。但 SCOE 和 northbound 已经是明确的两个消费者，满足 CLAUDE.md 刚加的 shared 提取规则。而且如果放在 SCOE/core，northbound design 时需要 import
  SCOE 的 core 来引用接口，这违反 feature boundary。

  建议：直接放 shared/external-command-adapter/，接口定义 + 类型。实现留在各自 feature。

  3. TaskExecutionSummary 应合并

  之前的讨论同意"合并 TaskExecutionSummary 到 InstanceState completion 快照"。但 SCOE design §4.1.1、§4.4、§4.10 都还在引用 TaskExecutionSummary。另一个对话可能不知道这个决定。后续同步时需要统一。

  4. translateResponse 对 SCOE 无意义但被强制实现

  §4.10 中 translateResponse(summary) → ScoeCommandOutcome 直接 return summary。接口强制实现一个空操作。如果只有 northbound 需要输出翻译，考虑拆分接口：base adapter 只有 translate + lifecycle，output
  translation 作为可选扩展。

  中优先级

  5. 状态循环应该用 shared/timer/TimerRegistry

  §4.9 说"SCOE service 内部维护一个定时器（setInterval）"。但刚决定提取 TimerRegistry 到 shared/。SCOE 的状态循环应该引用 TimerRegistry。

  6. errorPolicy 硬编码 stop 是否合理？

  §4.4 命令翻译流程中 errorPolicy = { retry: 0, on-failure: stop }。某些 SCOE 命令（如 health_check）可能需要 retry。是否应该按命令可配置？

  7. sourceId 归属不明

  入站路由依赖 sourceId 匹配 SCOE 固定 source，但 sourceId 是 connection 分配的还是 SCOE 声明的？需要明确。
