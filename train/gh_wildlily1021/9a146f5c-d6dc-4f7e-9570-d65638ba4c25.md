279	### 决策 1：消费者链入站分发
280	
281	**架构约束**：`CLAUDE.md` 和 `rewrite-target-structure.md` 明确规定 runtime 只负责装配、调用顺序、事件路由和生命周期，不承载领域规则。routingTick 不能评估任何领域条件（如"这个字节是不是 SCOE 协议"）。
282	
283	**方案**：routingTick 定义通用的 `TransportEventConsumer` 接口，消费者链依次处理：
284	
285	```typescript
286	// runtime 层——纯接线，不评估领域条件
287	interface TransportEventConsumer {
288	  consume(events: readonly TransportEventSnapshot[]):
289	    Promise<ConsumerResult>;
290	}
291	
292	interface ConsumerResult {
293	  readonly consumed: readonly TransportEventSnapshot[];
294	  readonly remaining: readonly TransportEventSnapshot[];
295	}
296	```
297	
298	**数据流**：
299	
300	```
301	routingTick drainAdapterEvents()
302	  ↓ 过滤 data events（结构性判断，非领域判断）
303	  ↓ data events: [...]
304	  ↓
305	① command-ingress.consume(data events)
306	   adapter 检查协议头/连接类型 → 消耗 SCOE events → 返回 remaining
307	  ↓ remaining: [非 SCOE events]
308	  ↓
309	② receive.drainInputSource(remaining)
310	   正常 receive 处理流程，完全不知道 command-ingress 存在
311	```
312	
313	**关键设计**：
314	- routingTick 不知道"SCOE"或"command-ingress"，只知道一个有序的消费者列表
315	- 消费者顺序是装配时决策（feature-wiring 中确定 command-ingress 先于 receive），属于接线
316	- command-ingress 的 `consume()` 内部做所有领域判断（协议头检查、功能码匹配）
317	- receive 不需要添加"跳过 SCOE"的逻辑，天然隔离
318	- 互斥通过 `remaining` 链传递实现，不需要 routingTick 做过滤
319	
320	**routingTick 改动**：增加消费者注册 + 链式调用逻辑。`RewriteWiredFeatures` 增加 commandIngressConsumer。约 20-30 行改动。
321	
322	### 决策 2：handler map 函数签名，不建 executor 框架
323	
324	```typescript
325	type CommandHandler = (
326	  command: ParsedCommand,
327	  ctx: CommandContext
328	) => Promise<CommandResult>;
329	```
330	
331	**理由**：6 种命令中 4 种是简单操作（状态/查询），2 种翻译为 TaskDefinition。不需要 CommandExecutor 抽象类或执行器框架。一个 Map 搞定。
332	
333	**CommandContext 提供**：
334	- `taskService`：创建和启动 task
335	- `stateReader`：读领域状态（loadedSatelliteId、统计等）
336	- `frameAssetReader`：查帧定义
337	- `connectionSnapshot`：读连接状态（HEALTH_CHECK 用）
338	- `receiveSnapshot`：读接收状态（LINK_CHECK 用）
339	- `fileReader`：读文件（READ_FILE_AND_SEND 用，通过 platform facade）
340	
341	### 决策 3：SCOE 命令翻译为 TaskDefinition
342	
343	**SEND_FRAME**：
344	```typescript
345	TaskDefinition {
346	  schedule: { kind: 'immediate' },
347	  steps: [
348	    { kind: 'send', config: { frameId: instance1.frameId, fieldValues: resolvedParams, targetId: 'udp-target' } },
349	    { kind: 'delay', config: { durationMs: command.sendInterval } },
350	    { kind: 'send', config: { frameId: instance2.frameId, ... } },
351	    // ... 每个帧实例一个 send step
352	    { kind: 'wait-condition', config: { conditions: completionConditions, timeoutMs: command.completionTimeout, onTimeout: 'fail' } }
353	  ]
354	}
355	// 确认帧：adapter 在 taskService.onSettled() 成功后，通过 connection.write() 发送 successFrameId 帧
356	```
357	
358	**READ_FILE_AND_SEND**：
359	```typescript
360	TaskDefinition {
361	  schedule: { kind: 'timer', intervalMs: command.sendInterval },
362	  steps: [
363	    { kind: 'send', config: { frameId, fieldValues, targetId } },
364	    { kind: 'wait-condition', config: { conditions, timeoutMs, onTimeout: 'fail' } }
365	  ],
366	  fieldVariations: [{ fieldId, values: fileLines }],  // adapter 通过 platform facade 读文件
367	  stopCondition: { maxIterations: maxLineCount }
368	}
369	// 确认帧：adapter 在 taskService.onSettled() 成功后，通过 connection.write() 发送 successFrameId 帧
370	```
371	
372	**参数 resolve**：adapter 在翻译阶段从指令帧字节提取参数 → 匹配 options → resolve 为 literal 值，直接填入 TaskDefinition。task 引擎不需要理解参数关联。
373	
374	### 决策 4：并发策略——允许并发，不加锁不排队
375	
376	**理由**：实际只有一个 SCOE 客户端连接，并发是理论风险。旧系统就是这么干的。多客户端保留在 connection 层，command-ingress 不额外管理。
377	
378	**防护措施**：handler 内加领域状态前置条件检查（LOAD 门控、卫星 ID 状态）。
379	
380	### 决策 5：回应机制——adapter 在 task 完成后独立发送
381	
382	- 成功：adapter 订阅 `taskService.onSettled()`，task 成功完成后通过 `connection.write()` 发送 `successFrameId` 帧（UDP），不作为 task step
383	- 失败/超时：只更新领域状态（errorCount++、lastErrorReason），不发任何回应帧
384	- 校验和：由 send service 的 frameToBuffer 自动计算，command-ingress 不关心
385	- 确认帧不走 task step 的理由：READ_FILE_AND_SEND 是多轮迭代任务，确认帧只应发一次；统一策略让所有命令类型行为一致，且 task 不需要知道回应协议
386	
387	### 决策 6：连接断开清理
388	
389	监听 connection disconnect event，取消与该连接关联的正在执行的 task。旧系统没有这个机制，新系统补上。
390	
391	### 决策 7：校验和不提取 shared/
392	
393	校验和算法只有 `sum % 256` 一种，SCOE 领域特定。留在 ProtocolAdapter 内部。如果未来 send/receive 也有类似校验和需求，届时再提取。
394	
395	### 决策 8：Feature 命名与目录
396	
397	目录：`rewrite/src/features/command-ingress/`，中文仍叫"指令接入"。
398	
399	### 决策 9：新甲方 HTTPS 先做 stub
400	
401	`canHandle()` 返回 false，接口占位，不实现任何协议细节。schema 未确认前不冻结契约。

407	## 边界
408	
409	### command-ingress 拥有
410	
411	- ProtocolAdapter 接口定义和注册
412	- SCOE 协议解析（功能码/校验和/参数提取）

429	### Feature 间交互
430	
431	| 方向 | 交互方式 | 说明 |
432	|------|---------|------|
433	| runtime → command-ingress | routingTick 分流 transport events | 互斥过滤，command-ingress 先消费 |
434	| command-ingress → task | `taskService.createTask(def)` + `startTask(id)` + `onSettled(id)` | 翻译后的 TaskDefinition 与 UI 创建的无区别 |
435	| task → command-ingress | task lifecycle event | command-ingress 订阅，更新领域统计 |
436	| command-ingress → frame | `FrameAssetReader` 只读查询 | 查帧定义和字段 |
437	| command-ingress → connection | `write(request)` 发送确认帧 | adapter 在 onSettled 后直接调用，不经过 task |
438	| command-ingress → platform | `fileReader` 读文件 | READ_FILE_AND_SEND handler 通过 ctx |

456	  readonly values: Record<string, SendFieldValue>;
457	  readonly direction: 'send' | 'receive';
458	}

460	
461	Events:
462	- `update:values` — 字段值变化时 emit
463	
464	字段分组渲染（使用 Quasar brand 色，不硬编码(C1)）:
465	- 可调字段: `color="info"` 标识，用户可编辑
466	- 计算参数: `color="warning"` 标识，表达式字段
467	- 不可配置: `color="grey"` 文字，只读展示
468	
469	表达式实时联动: 字段值变化 → `evaluateFieldPreview` 重算依赖字段 → emit 更新后的 values。`evaluateFieldPreview` 是 send feature 面向 UI 的公共函数，内部封装 FrameFieldDefinition → frameToBuildInput → SendFieldEncodingDef → evaluateFieldExpressions 的转换链路。UI composable 只传 frame + fieldId + userFieldValues，不接触 send 内部编码类型。按字段粒度调用，不全量 resolveFieldValues。computed 缓存 + 字段级依赖追踪。
470	
471	消费方:
472	- 发送页实例编辑对话框
473	- 任务页编辑器对话框 SendStep 字段值编辑
