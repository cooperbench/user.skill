## Findings（按重要性排列）

### F1. SCOE 命令帧的 targetId 归属是未覆盖的路由 gap

SCOE design §4.10 明确写了：
> send-step: targetId = 下位机连接 target（非 SCOE UDP target，该帧发往下位机执行）

但没有说明这个"下位机连接 target"从哪来。

旧代码 evidence：`scoeReceiveCommands.json` 中帧实例的 targetId 为 `"network:scoe-tcp-server"` 或 `"network:scoe-udp:scoe-udp-remote"`——这些是 SCOE 自己的连接，不是卫星（下位机）的连接。

**这是一个需要决策的 gap。**

### F2. 并发协调只到 transport level，task-level 缺调度

现有设计：
- send QueueModel：同 target 的 transport write FIFO
- task：step 顺序执行，await SendResult

但如果用户定时任务和 SCOE 命令同时往同一下位机发帧：
- send QueueModel 保证 transport 层不乱序
- 但 task 层面没有优先级、互斥或资源协调
- 可能导致 SCOE 命令帧夹在用户定时任务帧中间

### F3. 确认帧内容来源是配置驱动的，但遥测选取规则未定义

SCOE design 允许 ack frame fieldValues 为"固定/硬编码数据，或从遥测中选取的数据"。但：
- 哪些字段从遥测选取？
- 选取规则在 SCOE 配置里定义还是代码写死？
- 旧代码：确认帧主要用帧模板默认值，部分字段可能用表达式从 SCOE 状态动态计算

### F4. Northbound 回报需要额外遥测数据，但需求未锁

TaskInstanceCompletion 只含执行摘要（steps 数、成功/失败数、耗时）。Northbound 可能需要：
- 每个用例的具体遥测字段值（误码率、信号强度等）
- 客户定义的结果枚举

这依赖甲方确认，已 deferred。

### F5. 所有来源共享同一个 connection target 池

connection 的 `selectTransportTargets()` 是统一 target 池。用户、SCOE、northbound 的 send request 都通过 targetId 引用同一个池。**已由现有 design 覆盖。**

## 逐问题分析

### 一、出站路由

**Q1: send-step 的 targetId 怎么解析到实际连接？**

**已解决。** send design §4.4 明确：SendRequest.targetId → send 调用 connection `selectTransportTargets()` 解析为 `TransportTargetSnapshot`，检查可用性，不可用返回 `target-unavailable`。无额外映射层，直接引用 connection target ID。

**Q2: SCOE 命令帧的 targetId 从哪来？**

**需要新增决策。** 有三个选项：

| 选项 | 描述 | 优劣 |
|---|---|---|
| A. SCOE 命令配置声明 | ScoeCommand 中增加 `targetId` 字段，翻译时写入 send-step | 灵活，不同命令可发往不同下位机；配置项多 |
| B. SCOE 全局配置声明 | ScoeGlobalConfig 声明一个 `defaultDownlinkTargetId` | 简单；不灵活 |
| C. 系统级 target 映射 | 运行时维护"下位机 target"映射表 | 解耦；引入新概念 |

**建议选项 A**，理由：
- 旧代码 SCOE 帧实例配置中已有 targetId 字段（虽然旧值指向 SCOE 连接）
- 不同 SCOE 命令理论上可能需要发往不同下位机（多目标场景）
- 与 TaskDefinition 的 step.targetId 语义一致
- SCOE 配置翻译时已有解析 frameInstances 的逻辑，targetId 可从同一路径提取

**Q3: Northbound 任务帧的 targetId 从哪来？**

**需要新增决策。** 同样三个选项。建议同样走配置声明路径，但具体放在哪取决于 northbound task schema 的最终形态。当前建议：

- Northbound adapter 翻译外部任务时，从 TaskDefinition 的 step.targetId 或 defaultTargetId 取值
- 如果甲方外部请求中包含 target 信息（如 deviceId），northbound adapter 负责将 deviceId 映射为 connection targetId
- 如果不包含，使用系统默认 target 配置

**Q4: 同一个 target 池？**

**已解决。** 是，所有来源共享 connection 的 target 池。

**Q5: 多来源同时发帧时 QueueModel 够不够？**

**需要新增决策。** QueueModel 保证 transport-level 不乱序，但 task-level 没有协调。核心问题：

- SCOE 命令有实时性要求（收到指令后应尽快执行）
- 用户定时任务可中断
- Northbound 任务也有执行约束

建议在 task service 层增加一个轻量级 **target lock** 概念：

```
TaskService 执行 send-step 前:
  1. 获取 targetId 的发送锁
  2. 执行 send
  3. 释放锁

锁的语义：
  - SCOE 命令任务（triggerSource=scoe-command）优先级最高
  - 其他任务等待锁释放后继续
  - 等待超时触发 errorPolicy
```

但这引入了复杂度。另一个更简单的方案：

**建议：首轮不做 task-level 调度，依赖 QueueModel + 文档约束。**

理由：
- 实际场景中，SCOE 命令频率不高（按秒级），用户定时发送也可控
- QueueModel 保证 transport 层顺序，不会出现半个帧交错
- 真正的冲突（同时往同一 target 发不同命令序列）需要 runtime 证据才能量化
- 后续如有冲突问题，可在 task service 层加 target lock

---

### 二、回报构造

**Q6: 遥测全量接收后怎么存储？**

**已解决。** receive 解析 → 输出 ReceiveInputEvent → storage 持久化（经 runtime 路由）。receive owns 解析结果，storage owns 持久化。

**Q7: SCOE 确认帧内容规则？**

**已部分解决。** SCOE design 中 ScoeAckFrameConfig 承载确认帧配置：
- `frameId`：确认帧引用（固定）
- `fieldValues`：字段值（可固定或从遥测选取）
- `targetId`：SCOE UDP target（固定）

规则定义位置的建议：

| 内容类型 | 定义位置 | 理由 |
|---|---|---|
| 固定值（大多数确认帧） | ScoeAckFrameConfig.fieldValues | 配置驱动，可直接测试 |
| 从遥测选取的值 | 不在首轮支持 | 需要表达式 runtime，expression runtime 归属未定 |

**建议首轮确认帧只支持固定值。** 遥测选取值等 expression runtime 归属确定后再支持。

**Q8: Northbound 回报够不够？**

**已 deferred。** TaskInstanceCompletion 是内部事实，northbound 的 ExternalResponseTranslator 负责转换为外部响应。是否需要额外遥测数据依赖甲方确认。

**Q9: 用户回报？**

**已解决。** Task progress（steps 进度、iteration 计数、elapsedMs）通过 task selector 暴露给 pages。TaskInstanceCompletion 作为终态展示。

---

### 三、并发和冲突

**Q10: 用户手动发和 SCOE 命令同时进行？**

见 Q5 分析。建议首轮依赖 QueueModel，不加 task-level 调度。

**Q11: 需不需要"出站调度器"？**

**建议不需要独立概念。** 如果未来需要 task-level 协调，可以：
1. 在 task service 的 send-step 执行中加 target lock（轻量方案）
2. 或在 runtime 层加 target 发送互斥（中等方案）

不需要单独建一个"出站调度器"feature 或模块。

## 场景 1：用户在 send 页面配置了一个定时任务

**配置阶段：**
1. 用户打开定时发送对话框
2. 选择一个发送方向帧 → 从 frame selector 读取
3. 填写字段值
4. **选择目标连接** → 从 connection `selectTransportTargets()` 拿到当前可用的 target 列表（如 `serial:COM3`、`network:tcp-conn-1`），用户选了 `serial:COM3`
5. 配置间隔 1 秒、次数 100 次
6. 点"启动"

**翻译为 TaskDefinition：**
```
TaskDefinition {
  triggerSource: 'user-ui',
  schedulingMode: 'timed',
  defaultTargetId: 'serial:COM3',       // ← 用户在 UI 选的
  steps: [
    { kind: 'send', sendConfig: {
        frameId: 'frame-001',
        fieldValues: { field1: '0x01', field2: '0x02' },
        targetId: null                   // ← null 表示用 defaultTargetId
    }}
  ],
  errorPolicy: { action: 'stop' }
}
```

**执行阶段：**
```
taskService.startTask(instanceId)
  → 循环 100 次，每次：
    executeSteps:
      send-step:
        targetId = step.targetId ?? definition.defaultTargetId   // 'serial:COM3'
        构造 SendRequest { frameId, fieldValues, targetId: 'serial:COM3' }
        → sendService.execute(request)
          → resolve target: connection.selectTransportTargets() 找到 'serial:COM3'
          → 检查 target.available == true
          → 构帧（core 纯计算）
          → connection.write('serial:COM3', bytes)
          → 返回 SendResult { kind: 'sent', bytesSent: 8 }
        ← await 拿到 SendResult
        记录 TaskStepResult
    等 1 秒
  → 100 次完成 → lifecycle = completed
  → emit TaskInstanceCompletion
```

**用户看到什么：** task selector 推送进度更新，pages 展示"已发送 45/100"。

## 场景 2：SCOE 发了一个 `load_satellite_id` 指令码

**前提：**
- SCOE 全局配置声明了固定 TCP server（端口 6000）和固定 UDP target（192.168.1.100:7000）
- ScoeCommand 配置中：
  ```
  ScoeCommand {
    code: '01',
    function: 'load_satellite_id',
    frameInstances: [{ frameId: 'cmd-frame-load', targetId: 'serial:COM3' }],  // ← D1: 命令帧发往下位机
    completionCondition: { frameId: 'recv-frame-status', fieldId: 'status', operator: 'eq', threshold: '0x55', timeoutMs: 5000 },
    ackFrameConfig: { frameId: 'ack-frame-01', fieldValues: {}, targetId: 'scoe-udp-target' }  // ← 固定发回 SCOE
  }
  ```

**入站：**
```
SCOE TCP server (port 6000) 收到字节 [0xAA, 0x01, 0x02, ...checksum]
  → connection 输出 transport event { sourceId: 'scoe-tcp-server', bytes: [...] }
  → runtime 按 sourceId 匹配 → 路由到 SCOE adapter
  → SCOE core 协议解析：帧头0xAA + 指令码0x01 + 参数0x02 + 校验
```

**翻译：**
```
ScoeCommandAdapter.translateToTaskDefinition({ rawBytes, sourceId: 'scoe-tcp-server' })
  → 查找 ScoeCommand by code '01' → load_satellite_id
  → 提取参数
  → 构建 TaskDefinition:
    TaskDefinition {
      triggerSource: 'scoe-command',
      schedulingMode: 'sequence',
      steps: [
        { kind: 'send', sendConfig: {
            frameId: 'cmd-frame-load',           // 命令帧
            fieldValues: { param: '0x02' },       // 解析后的参数
            targetId: 'serial:COM3'               // ← 发往下位机（D1）
        }},
        { kind: 'wait-condition', waitConfig: {
            condition: { frameId: 'recv-frame-status', fieldId: 'status', operator: 'eq', threshold: '0x55' },
            timeoutMs: 5000,
            onTimeout: 'fail'
        }},
        { kind: 'send', sendConfig: {
            frameId: 'ack-frame-01',              // 确认帧（固定内容，D3）
            fieldValues: {},                       // 首轮只支持固定值
            targetId: 'scoe-udp-target'           // ← 发回 SCOE 设备
        }}
      ],
      errorPolicy: { action: 'retry', retryCount: 2 }
    }

  taskService.createTask(definition) → instanceId
  taskService.startTask(instanceId)
```

**执行：**
```
Step 0 (send-step → 下位机):
  targetId = 'serial:COM3'
  SendRequest { frameId: 'cmd-frame-load', targetId: 'serial:COM3', ... }
  → sendService.execute → 构帧 → connection.write('serial:COM3', bytes)
  → SendResult { kind: 'sent' }

Step 1 (wait-condition-step):
  订阅 receive 的 ReceiveInputEvent
  下位机遥测进来 → receive 解析 → emit ReceiveInputEvent
  → task/core 匹配 WaitCondition: recv-frame-status.status == 0x55?
  → 匹配成功！记录 TaskStepResult { matched: true, matchedValue: '0x55' }
  
  （如果 5 秒超时 → onTimeout='fail' → errorPolicy retry → 重试整个序列最多 2 次）

Step 2 (send-step → SCOE):
  targetId = 'scoe-udp-target'                      // SCOE 固定 UDP
  SendRequest { frameId: 'ack-frame-01', targetId: 'scoe-udp-target', ... }
  → sendService.execute → 构帧 → connection.write('scoe-udp-target', bytes)
  → SendResult { kind: 'sent' }

→ lifecycle = completed
→ emit TaskInstanceCompletion
→ SCOE adapter.onExecutionEvent(task-completed) → commandSuccessCount++
```

**路径示意：**
```
SCOE设备 ──TCP──→ [我们] ──serial──→ 下位机
                    ↑                    │
                    │                    │ (遥测)
                  UDP ←── [确认帧] ←─────┘
                              ↑
                        receive 解析 → task wait-condition 匹配
```

- HTTP server 收到外部请求：`POST /api/task { taskId: 'T001', cases: [...] }`

**入站：**
```
platform HTTP event → runtime → northbound adapter
  → 解析 JSON → 翻译外部 task 描述
```

**翻译：**
```
NorthboundCommandAdapter.translateToTaskDefinition(externalTask)
  → 翻译每个 case 为 send-step
  → targetId 来源（D2）：
    - 如果外部请求含 deviceId → adapter 将 deviceId 映射为 connection targetId
    - 如果不含 → 使用 TaskDefinition.defaultTargetId（系统默认配置）
    
  TaskDefinition {
    triggerSource: 'northbound-command',
    schedulingMode: 'sequence',
    defaultTargetId: 'serial:COM3',        // ← 系统默认（D2）
    steps: [
      { kind: 'send', sendConfig: { frameId: 'case-1', targetId: null /* 用 default */ }},
      { kind: 'delay', delayConfig: { durationMs: 500 }},
      { kind: 'send', sendConfig: { frameId: 'case-2', targetId: null }},
    ],
    errorPolicy: { action: 'stop' }
  }
```

**执行：** 与场景 1 相同的 task 执行循环。

**回报：**
```
task 完成 → emit TaskInstanceCompletion
  → northbound adapter.onExecutionEvent(task-completed)
  → northbound adapter.translateResponse(completion)
    → 构造 HTTP response:
      { taskId: 'T001', status: 'completed', 
        caseResults: [...], duration: 5200, ... }
  → runtime 通过 platform 发送 HTTP response
```

---

## 三条路径的共性

```
              入站触发                    翻译                         执行
用户 UI  ──→ 用户配置 ──────→ TaskDefinition ──→ taskService.startTask
SCOE TCP ──→ 协议解析 ──────→ TaskDefinition ──→ taskService.startTask  ──→ 统一执行引擎
HTTP     ──→ JSON解析 ──────→ TaskDefinition ──→ taskService.startTask

                                                        │
                                                        ▼
                                              send-step 执行时:
                                              targetId 解析 → connection target → transport write
                                                        │
                                                        ▼
                                              回报路径:
                                              SCOE → 确认帧（send-step 固定在序列末尾）
                                              Northbound → ExternalResponseTranslator（HTTP response）
                                              用户 → task selector（UI 展示进度和结果）
```

核心点：**三条入站路径最终都汇聚到同一个 TaskDefinition → taskService 的入口**。区别只在入站适配（谁翻译、怎么翻译）和回报路径（谁消费 TaskInstanceCompletion）。
