## 核心问题：tick() 轮询模型是错误的抽象

方案最关键的问题是 **event-router.ts 用 `tick()` 做轮询**。这违反了架构文档的核心约束，也忽略了 feature 已有的 adapter 机制。

### 证据一：架构文档明确要求 explicit event

交互矩阵对 connection→receive 的要求：

> interaction candidate: `explicit event`, `runtime orchestration`, `selector`
> High freq: Yes

对 receive→task：

> receive result/delta 可能有多消费者，不能同步堆副作用
> 应优先考虑 explicit event 或 runtime orchestration

`tick()` 把 5 个 feature 的数据流同步串在一个函数调用里，本质上是**用 runtime 重写了旧 receiveFramesStore 的尾部副作用链**——这正是架构文档反复强调要避免的。

### 证据二：feature 已经提供了 event-driven 接口，方案没用到

实际 public API 比方案假设的更完善：

| Feature | 已有接口 | 方案怎么用的 |
|---------|---------|------------|
| connection | `drainAdapterEvents(): Promise<ConnectionOperationOutcome>` 包含 `events[]` | ✅ 方案注意到了 |
| receive | **`drainInputSource(source: ReceiveInputSource): Promise<ReceiveServiceOutcome>`** | ❌ 方案没看到，自己手动调 `ingestBatch()` 做转换 |
| receive | **`ReceiveInputSource` adapter 接口** `drainEvents(): Promise<ReceiveInputEvent[]>` | ❌ 方案自己手动做 connection event → ReceiveInputBatch 转换 |
| task | `ReceiveEventSource.subscribe(handler)` — 回调注册模式 | ⚠️ 方案用了 bridge 但在 tick() 里同步触发 |

关键发现：**receive 已经设计了 `ReceiveInputSource` adapter 接口和 `drainInputSource()` 方法**。正确做法是：

```
runtime 创建 ConnectionToReceiveInputSource adapter
  → 包装 connection adapter events 为 ReceiveInputEvent[]
  → 调用 receiveService.drainInputSource(adapter)
  → 检查 outcomes，bridge 到 task 的 ReceiveEventSource
```

这比 tick() 里手动 ingestBatch + 手动提取 matched fields 简单得多，而且复用了 receive 已有的批处理逻辑。

### 证据三：同步 tick 链不适合高频数据

串口 115200 baud ≈ 11KB/s，TCP 可能更高。tick() 如果不能在一个 tick 内处理完所有待处理数据，就会积压；如果能，那就是在一个同步调用里处理大量数据 + 触发 task + 触发 send，和旧系统一次 receiveFramesStore.handleReceivedData() 完成所有副作用没有区别。

## 其他问题

### 1. ConnectionService.write() 的签名对不上

方案说 `SendTransportWriter.writeBytes() 委托 connectionService.write()`。实际：

```typescript
// connection public API
write(request: TransportWriteRequest): Promise<ConnectionOperationOutcome>;

// send adapter port  
writeBytes(connectionId: string, bytes: readonly number[]): Promise<SendTransportWriteOutcome>;
```

两者签名不同，bridge adapter 需要正确转换，方案没提 TransportWriteRequest 的结构。

### 2. storage-local-baseline 被丢弃

当前 runtime/index.ts 已经接了 storage-local-baseline（overview 里的 storage 字段），方案的 5 条链路和模块设计完全没提它。重构后会丢失现有功能。

### 3. settings 消费机制缺失

方案在依赖顺序里列了 settings，但 wiring 和 event-router 都没展示 settings snapshot 如何分发到消费 feature。架构文档说 settings → 各 feature 用 `selector` 或 `runtime orchestration`，但方案没设计这个。

### 4. wireFeatures() 太粗

一个函数创建 6 个 service + 4 个 bridge adapter，任何一个失败全部失败。应该按依赖层级逐步创建，每步返回结果。

## 问题 1（会出 bug）：ConnectionToReceiveInputSource 绕过了 ConnectionService

方案设计的流程：

```
ConnectionAdapter.drainEvents()       ← 桥接 adapter 直接调底层 adapter
       ↓
ConnectionToReceiveInputSource
```

但 **ConnectionService 已经持有 ConnectionTransportAdapter**。如果桥接 adapter 也调 adapter.drainEvents()，会出现：

1. ConnectionService 和桥接 adapter **竞争同一个 adapter 的事件队列**
2. ConnectionService 的 state 不会更新——它的 counters、event history、lastError 全部丢失
3. 串口/TCP 断线、连接状态变化等非 data 事件也被桥接 adapter 吃掉，ConnectionService 看不到

正确流程必须**先经过 ConnectionService**：

```
event-router 调用 connectionService.drainAdapterEvents()
  → ConnectionService 内部 drain adapter，更新自身 state，返回 ConnectionOperationOutcome
  → outcome.events 里有 data 事件
       ↓
event-router 把 data 事件推入 ConnectionToReceiveInputSource
  → 桥接 adapter 缓存这些事件
       ↓
receiveService.drainInputSource(bridge)
  → receive 内部调 bridge.drainEvents()，拿到 ReceiveInputEvent[]
```

ConnectionToReceiveInputSource 不是包装 ConnectionTransportAdapter，而是**接收 ConnectionService 已经处理过的事件**，做格式转换。它应该是无状态的事件转换器，不是 adapter 的代理。

## 问题 2（过度设计）：5 层 wiring 拆得太细

6 个 service 5 个 level，其中 4 个 level 各自只创建 1 个 service。维护 5 个函数 + 5 个接口的成本高于收益。

实际依赖关系：

```
Level 0 (无 feature 依赖): frame, settings, storage
Level 1 (需 adapter):      connection
Level 2 (需 level 0+1):    receive, send
Level 3 (需 level 2):      task + bridge
```

3 层足够，每层内的 service 互相独立可以并行创建。Level 2 的 receive 和 send 可以同时创建（receive 依赖 frame，send 依赖 frame+connection，都在前置层已有）。

---

## 问题 3（缺失）：错误处理完全没提

event-router 的路由节拍中任何一个环节都可能失败：

- `connectionService.drainAdapterEvents()` 返回 error outcome
- `receiveService.drainInputSource()` 返回 issues
- bridge emit 时 task handler 抛异常

方案没有设计：
- 单步失败后是否继续后续步骤
- 错误如何暴露给上层（lifecycle / UI）
- 是否需要重试 / 退避 / 断路

不需要复杂方案，但至少需要：路由节拍中每步检查 outcome.ok，失败时记录并跳过后续步骤，不吞错误。

## 问题 4（表述不诚实）：pollIntervalMs 说明不是纯 event-driven

方案标题写"事件驱动模型"，但 event-router 仍然用 pollIntervalMs 做轮询调度。这不是真正的 event-driven（adapter 不主动 push），是**轮询驱动的批处理**。

这个设计本身**没有错**——桌面应用轮询串口/TCP adapter 是合理的抽象层级。真正的 event-driven 需要平台层提供 callback/push 能力，那是 platform facade 的事，不是 runtime 的事。但标题应该诚实，避免后续实现者误解。

## 三个小问题

### 1. event-router 禁止 timer 但有 start/stop + pollIntervalMs

反向核对项写"runtime/ 不应使用 setTimeout/setInterval（event-router 的调度由外部驱动）"。但 EventRouter 接口有 `start()`/`stop()` + `pollIntervalMs` 选项。如果不用 timer，start() 做什么？

两种解法，选一个：
- **A**：删掉 pollIntervalMs，event-router 只暴露 `tick()` 方法，由 lifecycle 或外部驱动调用。start/stop 只控制 isRunning 标志。
- **B**：event-router 内部允许用 timer（删掉这条禁止项），但在测试时用 `now` 注入或手动 tick。

当前阶段 fake adapter 不需要真实调度，建议走 **A**——event-router 是被动执行者，外部驱动。等 platform facade 提供真实 push 能力时再改调度模型。

### 2. ConditionMatchInput 提取逻辑缺一行说明

设计说"从 outcomes 中 extract ConditionMatchInput[]"，但没写提取规则。实际需要：

```
遍历 outcomes 中 kind==='matched' 的每条
  → 遍历该 outcome.fields 中每个 parsedField
  → 每个字段生成一个 {frameId, fieldId, sourceId?, value}
```

一个 matched outcome 可能产生多个 ConditionMatchInput（每个解析出的字段一个）。task 的 condition-matcher 内部做过滤，所以 bridge 应发全部字段，不做筛选。

加一行就行，不影响结构。

### 3. send bridge 返回映射的边界情况

```
ok=true + events 含 write-accepted → {ok: true, bytesWritten: event.byteLength}
```

如果 ok=true 但 events 里没有 write-accepted 类型的 event（理论不应该，但防御性编码），应该返回什么？建议 fallback 到 `{ok: true, bytesWritten: 0}`。
