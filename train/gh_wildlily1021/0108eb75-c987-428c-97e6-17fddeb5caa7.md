## 1. connection design 的验收标准

来源：`codestable/features/rewrite-connection/rewrite-connection-design.md`

**验收标准逐条原文提取：**

### 4.2 Owner / not owner 验收
- connection owns transport config、runtime connection facts、target availability、transport-level lifecycle、error 和 event
- connection does not own frame parsing、receive matching、send task state、SCOE semantics、result、report、northbound

### 4.5 Transport lifecycle, event and error posture 验收
**Lifecycle rules：**
- connect / disconnect / cleanup must be idempotent enough for duplicate user actions, stale platform events and app shutdown
- duplicate open/connect, close on already closed resource and app quit cleanup are preserved as observable lifecycle categories
- changing serial options while connected is deferred
- automatic reconnect is not assumed. If later implemented, it must define retry policy, cancellation, UI visibility and runtime/hardware validation
- connection lifecycle events are low-frequency read model updates; high-frequency bytes must use separate batch/delta flow

**Error rules：**
- Transport errors are connection facts until a consumer explicitly interprets them
- Connection may normalize open/connect/listen/bind/write/timeout/close/resource-unavailable categories
- A write failure can be returned to send/SCOE as transport-level material
- A transport error must not directly define result/report/northbound failure semantics

**High-frequency rules：**
- Main may buffer, batch, throttle, queue or apply backpressure only for platform-resource or performance reasons
- Main may not classify bytes as frame match, task trigger, SCOE success, result truth, report material or northbound delivery
- connection may normalize source/target and byte availability; receive consumes byte batches and owns parse/match
- UI must consume throttled snapshots and selectors, not raw serial/network event streams

### 4.6 Public API necessity 验收
**Allowed capability categories only：**
- Transport config category：create, inspect, update and validate transport static config
- Discovery category：expose available serial resources or transport resources as read-only candidates
- Lifecycle command category：request connect, disconnect, cleanup and optional recovery actions
- Target availability category：provide immutable target route, target status and availability snapshot
- Byte input category：publish incoming byte batches or normalized transport input events
- Byte output category：accept transport-level write requests and return transport acceptance/failure material
- Lifecycle/error event category：publish transport-level state and error events
- Test adapter category：allow fake serial/TCP/TCP server/UDP adapter substitution

## 2. connection 与 platform/transport 的交互契约

来源：`codestable/features/rewrite-connection/rewrite-connection-design.md`

### 4.8 Platform / preload / main involvement

**Platform facade：**
- 是 renderer-side desktop capability boundary used by connection adapters
- May expose transport primitive capability categories only after connection/platform implementation design accepts them
- Does not own transport config semantics, target identity, receive parsing, send result, task lifecycle, SCOE protocol, result/report/northbound meaning
- Must not reproduce old `src/api/common` as a one-to-one facade

**Preload：**
- Exposes minimal typed bridge capabilities, not `window.electron`, not bare `invoke/send/on`, not arbitrary channel subscription
- May bridge bounded serial/network lifecycle, byte I/O and event delivery after accepted capability design
- Must not expose receive processing, high-speed storage business rules, task/SCOE commands, report semantics or northbound transaction semantics

**Main process：**
- Owns live platform resources：serial port handles, TCP sockets, TCP server handles, UDP sockets, resource cleanup and OS-level I/O
- May retain platform-side buffer, batch, queue, throttle, stream/file write or backpressure only when tied to platform resources or performance pressure
- Must not own frame parsing, receive classification, task state transition, SCOE command/completion, result attribution, report generation, northbound error conversion or business device identity

### 4.9 Cross-feature communication

**交互契约表：**
| Consumer | May consume from connection | Must not do |
|---|---|---|

## 3. bridge-implementation design 的增量验收标准

来源：`codestable/features/rewrite-connection/rewrite-connection-bridge-implementation-design.md`

### 3.1 Owner split 验收
**main owns：**
- serial port handle、TCP socket、TCP server、UDP socket 等 native resource handle
- 资源生命周期、OS I/O
- per-connection input byte batching
- write queue per live resource
- subscription cleanup
- bounded lifecycle/error event buffer
- backpressure signal 当 queue 超限时
- app shutdown resource drain

**main must not own：**
- frame matching、receive classification、send task state、SCOE completion、result attribution、report generation、northbound error conversion、business device identity、TCP line splitting protocol semantics

### 4.1 Port compatibility rules 验收
- Real adapter 必须遵守 `ConnectionTransportAdapter` port 接口，不修改 port 定义
- `connect(config)`：通过 platform facade 调用 main IPC，main 创建 native resource
- `disconnect(id)`：对已关闭资源返回 accepted with `disconnected` event；对不存在资源也返回 accepted（幂等）
- `write(request)`：返回 `write-accepted` 或 `write-failed`；携带 `byteLength`
- `cleanup()`：返回所有断开连接的 `disconnected` events
- `drainEvents()`：返回 `ConnectionAdapterEvent[]`

### 5.3 Event ordering rules 验收
- 同一 connectionId 的 lifecycle 和 data 事件必须保序
- 不同 connectionId 的事件可以交错
- `connected` event 必须在 data event 之前到达 service
- `disconnected` event 后不应有同 connectionId 的 data event
- `write-accepted` 和 `write-failed` 是 command response 的一部分，不是异步 event queue 内容

### 6.1 Queue/backpressure principles 验收
- Main-side per-connection byte batch buffer：减少 IPC 消息数量
- Bounded batch buffer with flush trigger：防止 batch buffer 无界增长
- Time-window flush for low-frequency data：低频数据不应因 batch 而延迟过长
- Bounded async event queue with overflow signal：eventQueue 不可无界
- Overflow must be observable transport material：丢弃不是静默行为
- Per-connection queue isolation：一个连接的背压不应阻塞其他连接
- Main does not classify bytes：main 只做 buffer/batch/queue
- Overflow must not auto-convert to business error：丢弃是 transport material

### 7.3 Error boundary rules 验收
- Transport error 只作为 connection fact 或 consumer input material
- Write failure 只向 send/SCOE 提供 transport-level material
- Disconnect 或 timeout 是 connection fact，不直接定义 result/report/northbound failure
- Error visibility 属于 connection pages/status read model
- 不让 main 根据 error kind 决定 task lifecycle、SCOE completion 或 report semantics

### 8.1-8.5 Forbidden surfaces 验收
**Main forbidden：**
- 禁止解析 frame、匹配 receive、构造 send result、推进 task、解释 SCOE、生成 report 或转换 northbound error
- 禁止用 high-speed storage rule、receive rule 或 SCOE rule 决定 bytes 是否进入 renderer
- 禁止全窗口无差别广播 raw high-frequency bytes
- 禁止在 main handler 中做 TCP `\r\n` 分包
- 禁止在 main 中维护业务统计
- 禁止使用 `webContents.getAllWebContents()` 无差别广播

**Preload forbidden：**
- 禁止暴露裸 `invoke/send/on` 或任意 channel 订阅
- 禁止暴露 `window.electron` 大包
- 禁止暴露 receive processing、high-speed storage rule、task command、SCOE command 或 report API

**Platform facade forbidden：**
- 禁止复制旧 `src/api/common/serialApi.ts` 或 `networkApi.ts` 的一一映射
- 禁止暴露 raw socket、serialport handle 或 IPC channel 名
- 禁止定义连接配置 schema、target id 格式或业务错误码
- 禁止持有 mutable connection state

**Connection adapter forbidden：**
- 禁止暴露 platform resource handle、raw IPC channel 或 main process object
- 禁止 import Node.js、Electron 或 serialport
- 禁止解析 frame content、匹配 receive 或决定 task lifecycle

**Connection service/state/core forbidden：**
- 不因 real adapter 而增加任何平台依赖
- core 保持纯 TypeScript，不 import Vue、Pinia、Electron、platform、Node、socket 或 serialport

### 10.1-10.3 Runtime/Package/Hardware validation 验收

**Runtime validation：**
- app startup/shutdown wiring：connection service 和 adapter 正确创建和释放
- Platform subscription cleanup：preload event listener 在 cleanup 后移除
- Event ordering：connected before data, no data after disconnected
- Fake/real adapter wiring：runtime 可在 fake 和 real adapter 间切换
- Batch buffer flush：低频数据不因 batch 而无限延迟
- Multi-connection isolation：多连接互不阻塞

**Hardware validation：**
- Serial：enumerate、open、close、reopen、write、receive、error、unplug
- TCP client：connect、send、receive、close、error、timeout
- TCP server：listen、client accept、multiple client、per-client data、broadcast、client disconnect、server close cleanup
- UDP：bind、message、send、remote host route、broadcast candidate
- High-frequency：batch behavior、queue overflow、backpressure signal、UI snapshot stability

**Package validation：**
- Native module loading：packaged app 中 serialport 能正确 load
- asarUnpack：.node 文件在 asar 外可访问
- Resource path：packaged app 中 path resolve 正确
- Build target：Linux AppImage 和 deb 正确包含 native module

### 2. receive 消费 frame 的方式

#### 与 frame feature 的交互契约

**通过什么接口获取帧定义：**
- receive 通过 **frame public selector** 读取只读 frame asset snapshot
- receive 通过 **runtime injection** 获取 frame reference snapshot
- receive 读取 **receive-direction frame references**（即 `direction === 'receive'` 的帧）

**具体接口方式：**
```typescript
// 从 public API 可以看出 receive service 的 frame reference refresh
interface ReceiveService {
  refreshFrameReferences(frames?: readonly ReadonlyFrameAsset[]): ReceiveServiceOutcome;
}
```

**交互契约约束：**
- receive **只能读取** frame asset/reference snapshot、field definitions、expression definitions
- receive **禁止**让 receive mutate frame definitions、write stats into fields、import frame internal state 或 depend on frame store shape
- receive 对 frame reference 的使用只覆盖：
  - identifier rules（用于帧匹配）
  - fields（字段定义用于解析）
  - expression definition input（表达式定义输入）
  - 必要 display/reference metadata（展示/引用元数据）

**数据流向：**
```
frame static assets -> frame public selector -> receive frame reference snapshot -> receive core matching/parsing
```

**验证方式：**
- fixture test
- static scan（确保 receive 不 import frame internal state）

### 3. receive 与 expression engine 的集成契约

**来源：`rewrite/src/features/receive/core/processor.ts` 和 `expression-pass.ts`**

#### expression 集成到 receive pipeline 的方式

**集成位置：**
- expression evaluation 发生在 **field parsing 之后**，在 receive pipeline 的最终输出阶段

**处理流程：**
```typescript

1. normalizeByteArray() - 字节规范化
2. matchReceiveFrame() - 帧匹配
3. parseReceiveFrameFields() - 字段解析

**集成契约细节：**

1. **编译阶段（service 层）：**

   - 通过 `frame.id` 从缓存获取编译结果
   - 如果编译失败，返回 `config-error` 类型的 outcome
   - 如果编译成功，调用 `evaluateFrameExpressions()` 计算字段值

3. **变量来源（ExpressionEvalInput）：**

     readonly compiled: FrameExpressionCompiled;

     readonly currentFrameRawValues: ReadonlyMap<string, VariableValue>;  // 当前帧原始值

     readonly globalParams: ReadonlyMap<string, VariableValue>;  // 全局参数
   }
   ```

4. **变量解析优先级（buildVariableMap）：**
   - `current_field`: 当前字段已解析值
   - `frame_field`: 同帧或其他帧字段值
   - `global_stat`: 全局统计值

- 影响范围：

  - receive 不拥有系统级全局统计，只拥有 receive source stats

### 4. 扇出到 display/storage/task 的设计

**来源：`codestable/features/rewrite-receive/rewrite-receive-design.md` 第 4.5 节 Public API necessity 和第 4.8 节 Cross-feature communication**

#### 扇出路径和验收条件

**receive -> task 扇出：**
- **输出内容**：trigger candidate 或 receive result material
- **契约**：task owns trigger strategy and lifecycle
- **验收条件**：receive 不直接写 task state，不决定 running/completed/paused/stopped
- **交互方式**：explicit event 或 runtime orchestration
- **证据来源**：旧实现中 receive 成功后直接调用 send task trigger，需改为显式事件边界

**receive -> status 扇出：**
- **输出内容**：receive health/material
- **契约**：status owns health summary
- **验收条件**：receive 不 own system health truth，status 不 import receive internal state
- **交互方式**：read-only selector 或 explicit event
- **证据来源**：旧 globalStatsStore 记录 received packets/bytes 统计，需明确 owner split

**receive -> result 扇出：**
- **输出内容**：source facts
- **契约**：result owns result truth and attribution
- **验收条件**：receive 不定义 final case result、report result 或 external success/failure semantics
- **交互方式**：explicit receive output as result material
- **证据来源**：本轮不设计 result 内部流程，只提供材料边界

**receive -> storage 扇出：**
- **输出内容**：local material
- **契约**：storage owns persistence/history/file writing
- **验收条件**：receive 不执行任意文件写入，不定义 storage path policy，不声明 TestReport/file delivery closure
- **交互方式**：explicit material consumption
- **证据来源**：旧 history/CSV/export 读取接收材料，需明确不等同 TestReport 或 northbound delivery

**receive -> SCOE 扇出：**
- **输出内容**：explicit SCOE candidate input（如果 SCOE design 接受）
- **契约**：SCOE owns command semantics and completion
- **验收条件**：不隐藏 SCOE fixed source/target 或 command completion inside generic receive parser
- **交互方式**：declared SCOE candidate/exception
- **证据来源**：旧 receive 内有 SCOE source special-case，需 SCOE design 决定边界

**receive -> display（pages/widgets）扇出：**
- **输出内容**：UI-safe snapshots、stats、result projections
- **契约**：pages 只读不写
- **验收条件**：
  - UI 通过 throttled snapshot、selector、pagination、virtualization 读取
  - 不订阅 raw transport bytes
  - 不 parse frames、不 accumulate stats、不 mutate receive runtime facts
  - 表格/图表/近期事件使用 UI snapshot，不逐包闪烁
- **交互方式**：read-only selector
- **证据来源**：旧 DataTable 约 500ms 刷新，dataDisplayStore 约 1s 采样，需明确 UI 不逐包参与解析

#### 设计文档中的扇出描述

**第 4.5 节 Public output rules：**
```
- receive -> task outputs trigger candidate or receive result material; task owns trigger strategy and lifecycle.
- receive -> status outputs receive health/material; status owns health summary.
- receive -> result outputs source facts; result owns result truth and attribution.
- receive -> storage outputs local material; storage owns persistence/history/file writing.
- receive -> SCOE outputs explicit candidate input if SCOE design accepts it; SCOE owns command semantics and completion.
- receive -> report/northbound has no direct public API in this feature design.
```

**第 4.8 节 Cross-feature communication table：**
| Collaborator | May consume / provide | Must not do |
|---|---|---|
| task | Consume receive result or trigger candidate through explicit event/runtime | Let receive directly call task internal state or decide running/completed/paused/stopped |
| status | Consume receive stats/material and build status summary in status owner | Let receive own system health truth or let status import receive internal state |
| result | Consume explicit receive output as result material | Let receive define final case result, report result or external success/failure semantics |
| storage/history | Consume receive material for local history, snapshots or high-speed storage exception once designed | Let receive perform arbitrary file writes, define storage path policy or claim TestReport/file delivery closure |
| SCOE | Consume explicit SCOE candidate input if SCOE design accepts it | Hide SCOE fixed source/target or command completion inside generic receive parser |
| pages/widgets | Read receive UI-safe snapshots, stats and result projections | Subscribe to raw transport bytes, parse frames, accumulate stats or mutate receive runtime facts |

### 6. receive pipeline 的完整处理链

**来源：`rewrite/src/features/receive/core/processor.ts` 和 design.md 第 4.9 节 Target internal layering**

#### 从字节输入到最终产出的处理步骤

**完整处理链（processReceiveBatch 函数）：**

```
1. 输入层（ReceiveInputBatch）
   ↓
   - id: string
   - bytes: readonly number[]  // 原始字节数组
   - receivedAt: string
   - source: ReceiveSourceSnapshot  // 来源快照
   - sequence?: number
   - referenceVersion?: number  // 用于 stale input 检测

2. 字节规范化（normalizeByteArray）
   ↓
   - 验证字节数组有效性
   - 生成规范化后的 bytes
   - 收集字节级 validation issues

3. 帧匹配（matchReceiveFrame）
   ↓
   - 过滤 direction === 'receive' 的帧
   - 检查 identifier rules 是否存在
   - 按 identifier rules 匹配（AND 逻辑）
   - 生成 matchedFrame 或 unmatched issues

4. 字段解析（parseReceiveFrameFields）
   ↓
   - 遍历 frame.fields
   - 按 offset/length/dataType/big endian/factor 解析字段
   - 生成 parsed field values
   - 收集字段级 parse errors

5. 表达式计算（evaluateFrameExpressions，条件执行）
   ↓
   - 检查 expressionCache 是否存在该 frame 的编译结果
   - 如果编译失败，返回 config-error
   - 如果编译成功：
     * 按拓扑序执行字段表达式
     * 解析变量引用（current_field/frame_field/global_stat）
     * 更新字段值（expressionApplied = true）
     - 收集表达式执行 errors

6. 产出构建（ReceiveBatchOutcome）
   ↓
   - id: string
   - kind: ReceiveOutcomeKind  // matched/unmatched/config-error/parse-error/input-error/stale-input
   - processedAt: string
   - input?: ReceiveInputBatch
   - matchedFrame?: ReceiveMatchedFrameSummary
   - fields: readonly ReceiveParsedFieldValue[]
   - issues: readonly ReceiveIssue[]
   - statsDelta: ReceiveStatsDelta  // 增量统计，用于更新 read model
```

**各层职责：**

| 层 | 职责 | 不得依赖 |
|---|---|---|
| core | 纯 TypeScript 规则：byte batch -> frame reference match -> field parse -> receive result | Vue、Pinia、Electron、platform、Node、global store、connection store、frame store |
| services | ingest input batch、调用 core、写入 receive state、输出 explicit result event | platform、preload、main、connection internal state、frame internal state |
| state | receive runtime facts、statistics read model、recent input snapshot、UI-independent selector | platform adapter、其他 feature state |
| adapters | fake input source、legacy oracle loader、runtime event adapter | 解释 frame definition owner 或 connection lifecycle |
| composables | 面向 UI 的组合：筛选、分页、表格/图表 snapshot、selector 组合 | 协议解析、统计累计 |
| components | UI 展示：帧选择、统计面板、数据表、近期事件、错误展示 | platform 或其他 feature internals |

**关键验收条件：**
- core 无 Vue/Pinia/Electron/platform/Node/global store 依赖
- 每个步骤都是 **确定性的纯函数**，便于测试
- statsDelta 按 **stable key 增量更新**，不全量替换大对象
- 支持 **stale input rejection**（通过 referenceVersion）
- 支持 **error classification**（6 种 outcome kind）

## 3. **expression 集成到 receive/send/task 时的契约变化**

来源：`codestable/features/2026-05-08-expression-engine/expression-engine-brainstorm.md` 第 4 节 + design.md 第 3 节

### Receive 集成契约
- **集成点**：`field-parser.ts:applyFactor`（~行 39）
- **当前**：硬编码 `value * factor`
- **接入后**：`compileExpression` 替代 `applyFactor`，3-5 行代码
- **变量**：rawParsedValue + 同帧其他字段值
- **验收证据**：design.md 第 3 节 I1 场景

### Task 集成契约
- **集成点**：`condition-matcher.ts:evaluateCondition`（~行 4）
- **当前**：结构化 `WaitCondition { frameId, fieldId, operator, threshold }` + `compareValues`
- **接入后**：`compileConditional` + `evaluateConditional` 作为 WaitCondition 的超集
- **变量**：current input values + task context + latest field values
- **注意**：`ConditionRegistry.processInput` 签名需扩展传递更多上下文
- **共存**：`compareValues` 和表达式引擎是独立工具，WaitCondition 可后续逐步迁移
- **验收证据**：design.md 第 3 节 I2 场景

### Send 集成契约
- **集成点**：`encode.ts:buildFrame` 前
- **当前**：静态 `fieldValues: Record<string, SendFieldValue>`
- **接入后**：`compileGroup` + `evaluateGroup`，构帧前批量解析
- **注意**：send 需访问 receive 最新快照，这是跨 feature 数据流设计点
- **验收证据**：design.md 第 3 节 I3 场景

### 集成边界关键规则
1. **编译与求值严格分离**：编译低频（配置加载/变更时），求值高频（每帧/每次匹配）
2. **变量收集归调用方**：引擎不感知 DataSourceType/sourceType/sourceId，调用方构建 VariableMap
3. **纯函数约束**：引擎不持有状态、不持有缓存、不持有 store
4. **编译结果由调用方缓存**：引擎不内置缓存

### 2. send-real design 的 9 步 pipeline 验收标准

**文件来源**：`codestable/features/rewrite-send/send-real-design.md` §3

| **SC2** | 表达式字段求值 | 帧有 `expressionConfig` 字段，variables 包含所需变量 | 表达式求值结果填入正确字段，buffer 编码正确 |

| **SC8** | Zero fill warning | 字段无用户输入、无表达式、无 defaultValue | 使用 0 填充 + buildIssues 记录 warning |
| **SC9** | Auto checksum | `autoChecksum=true`，有 `isChecksum` 字段 + validOption 范围 | buffer 中 checksum 字段位置写入正确的校验和值 |

| **SC12** | Target 不可用 | targetId 对应的 target 不可用 | `SendResult.kind='target-unavailable'` |
| **SC13** | Transport 写入失败 | transportWriter 抛出错误 | `SendResult.kind='transport-error'` |

### 5. checksum/patch 的边界情况

**文件来源**：`codestable/features/rewrite-send/send-real-design.md` §2.1、§2.2、§3

#### 5.1 Checksum 边界情况

**支持的算法**：
- `sum8`：字节累加和 mod 256
- `xor8`：字节异或
- `crc16-modbus`：CRC16-MODBUS
- `crc32`：CRC32（新增）

**边界情况**：

| 场景 | 行为 | 来源 |
|------|------|------|
| Checksum 范围计算 | 按 `validOption.startFieldIndex` 和 `validOption.endFieldIndex` 确定 buffer 范围 | send-real-design.md §2.1 |
| Checksum 回填位置 | 找到 `isChecksum=true` 的字段，回填到该字段在 buffer 中的位置 | send-real-design.md §2.2 |
| Checksum 值溢出 | checksum 值超出字段字节宽度时返回 build-error，**不截断** | send-real-design.md SC16 |
| Checksum 字段缺失 | `autoChecksum=true` 但无 `isChecksum` 字段 → 跳过回填 + buildIssues warning | 推断 |
| Checksum 算法未指定 | `validOption.checksumMethod` 未指定 → 待确认（可能使用默认算法或报错） | 待确认 |
| 自定义算法 | 不支持 custom checksum，frame-real 类型已预留 | send-real-design.md §1.2 |

#### 5.2 Length Field 边界情况

| 场景 | 行为 | 来源 |
|------|------|------|
| Length 回填触发 | `frame.options.includeLengthField === true` | send-real-design.md §2.2 |
| Length 字段定位 | 通过 `frame.options.lengthFieldId` 查找字段 | send-real-design.md §2.1 |
| Length 字段缺失 | `lengthFieldId` 未配置或指向不存在的字段 → **跳过回填 + buildIssues warning，发送正常执行** | send-real-design.md SC17 |
| Length 值编码 | 按 `dataType + length + endianness` 编码帧总长度值 | send-real-design.md §2.2 |
| Length 字段类型限制 | frame-real types 需新增 `lengthFieldId?: string`（**前置依赖，尚未补齐**） | send-real-design.md §1.3 |

#### 5.3 测试级别要求

**Checksum 测试覆盖**（`send-real-checklist.yaml` c10）：
- 4 种算法（sum8, xor8, crc16-modbus, crc32）全部有测试
- 范围参数测试
- 回填逻辑测试
- 溢出场景测试（SC16）

**Length Field 测试覆盖**（`send-real-design.md` SC10, SC17）：
- 正常回填场景
- Length 字段缺失场景
- Length 字段无效引用场景

### 2. Settings 作为 7 个下游 feature 的配置输入源

**来源：** `/mnt/d/code/frontend/dongfanghong/codestable/features/rewrite-settings/rewrite-settings-design.md` §2.1, §F

#### 下游 feature 列表
1. **frame** - 无直接依赖，frame 已拥有 frame 静态资产
2. **connection** - 通过 settings 只读 defaults snapshot 或 connection 自己的 config service 读取低频默认参数
3. **receive** - 通常不直接读取 settings；如需要低频显示或解析配置，应通过显式输入传入
4. **send** - 通常不直接读取 settings；如存在默认发送偏好，只读取只读 snapshot
5. **storage** - 读取 CSV 默认路径、保存间隔、自动记录偏好、历史保留时长、自动保存等设置输入
6. **status** - 读取 indicator config snapshot
7. **display/chart/widgets** - 读取 chart/display 偏好快照或由 page/runtime 传入 props

#### 契约机制

**Selector 模式：**
```typescript
// settings 提供纯函数投影
selectRecordingSettings(source: SettingsSource): ReadonlySettingsRecordingConfig
selectStorageSettings(source: SettingsSource): ReadonlySettingsStorageConfig
selectGeneralSettings(source: SettingsSource): ReadonlySettingsGeneralConfig
```

**关键契约原则：**
- Settings 不知道消费 feature 的存在（selector 只接收 `SettingsSource`，不 import 任何 feature）
- Consumer 只能读、不能写 settings
- Selector 返回克隆副本，不泄露内部 state 引用
- 单向依赖：consumer → settings，settings 不反向依赖
