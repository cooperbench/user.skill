## 6. Duplicate Analysis

### 6.1 Potential Duplicates with Task Feature

**Question**: Does command-ingress share identifiers with task?

**Answer**: **NO** — they operate at different levels:

| Level | Command-Ingress | Task Feature |
|-------|-----------------|--------------|
| Definition ID | Generates: `scoe-send-${commandId}` | Accepts: any string |
| Instance ID | References: `task-inst-${n}` | Generates: `task-inst-${n}` |
| Step ID | Generates: `send-${instanceId}` | Accepts: any string |

**Key Finding**: Command-ingress generates **definition IDs** but task feature generates **instance IDs**. These are distinct namespaces with no overlap.

### 6.2 Potential Duplicates with Connection Feature

**Question**: Does command-ingress duplicate connection identifiers?

**Answer**: **NO** — command-ingress only references connection identifiers, never generates them.

- `connectionId` is **copied** from `TransportEventSnapshot.connectionId`
- `commandId` is **derived** from `TransportEventSnapshot.id` (not a duplicate)
- No collision risk: different prefixes (`scoe-cmd-` vs raw event IDs)

## 7. Critical Identity Dependencies

### 7.1 Hard Dependencies

1. **Connection Event ID Format**
   - Command-ingress assumes event IDs are string-coercible
   - Breaking change: if connection changes ID format, commandId generation breaks

2. **Task Instance ID Format**
   - Command-ingress assumes task IDs are strings for tracking
   - Breaking change: if task changes instanceId type, tracking map breaks

3. **Frame ID Stability**
   - Command-ingress stores frameIds in configuration
   - Breaking change: if frame IDs change, configs become invalid

### 7.2 Soft Dependencies

1. **Satellite ID Format**
   - 4-byte hex string (e.g., `"A1B2C3D4"`)
   - Extracted from raw bytes via offsets
   - Assumption: encoding is stable

2. **Command Code Format**
   - 2-digit hex string (e.g., `"01"`, `"05"`)
   - Mapped to functions via config
   - Assumption: hex parsing is consistent
