   196→```

   279→Regression tests in `hard_reset_test.go` verify this behavior - if go-git v6 fixes this issue, those tests can be used to validate switching back.

   281→#### Repo Root vs Current Working Directory
   282→
   283→**Always use repo root (not `os.Getwd()`) when working with git-relative paths.**
   284→
   285→Git commands like `git status` and `worktree.Status()` return paths relative to the **repository root**, not the current working directory. When an agent runs from a subdirectory (e.g., `/repo/frontend`), using `os.Getwd()` to construct absolute paths will produce incorrect results for files in sibling directories.
   286→
   287→```go
   288→// WRONG - breaks when running from subdirectory
   289→cwd, _ := os.Getwd()  // e.g., /repo/frontend
   290→absPath := filepath.Join(cwd, file)  // file="api/src/types.ts" → /repo/frontend/api/src/types.ts (WRONG)
   291→
   292→// CORRECT - use repo root
   293→repoRoot, _ := paths.RepoRoot()  // or strategy.GetWorktreePath()
   294→absPath := filepath.Join(repoRoot, file)  // → /repo/api/src/types.ts (CORRECT)
   295→```
   296→
   297→**When to use `os.Getwd()`:** Only when you actually need the current directory (e.g., finding agent session directories that are cwd-relative).
   298→
   299→**When to use repo root:** Any time you're working with paths from git status, git diff, or any git-relative file list.

   303→### Session Strategies (`cmd/entire/cli/strategy/`)
   304→
   305→The CLI uses a strategy pattern for managing session data and checkpoints. Each strategy implements the `Strategy` interface defined in `strategy.go`.
   306→
   307→#### Core Interface
   308→All strategies implement:
   309→- `SaveStep()` - Save session step checkpoint (code + metadata)
   310→- `SaveTaskStep()` - Save subagent task step checkpoint
   311→- `GetRewindPoints()` / `Rewind()` - List and restore to checkpoints
   312→- `GetSessionLog()` / `GetSessionInfo()` - Retrieve session data
   313→- `ListSessions()` / `GetSession()` - Session discovery
   314→
   315→#### Available Strategies
   316→
   317→| Strategy | Main Branch | Metadata Storage | Use Case |
   318→|----------|-------------|------------------|----------|
   319→| **manual-commit** (default) | Unchanged (no commits) | `entire/<HEAD-hash>-<worktreeHash>` branches + `entire/checkpoints/v1` | Recommended for most workflows |
   320→| **auto-commit** | Creates clean commits | Orphan `entire/checkpoints/v1` branch | Teams that want code commits from sessions |
   321→
   322→#### Strategy Details
   323→
   324→**Manual-Commit Strategy** (`manual_commit*.go`) - Default
   325→- **Does not modify** the active branch - no commits created on the working branch
   326→- Creates shadow branch `entire/<HEAD-commit-hash[:7]>-<worktreeHash[:6]>` per base commit + worktree
   327→- Session logs are condensed to permanent `entire/checkpoints/v1` branch on user commits
   328→- Builds git trees in-memory using go-git plumbing APIs
   329→- Rewind restores files from shadow branch commit tree (does not use `git reset`)
   330→- **Location-independent transcript resolution** - transcript paths are always computed dynamically from the current repo location (via `agent.GetSessionDir` + `agent.ResolveSessionFile`), never stored in checkpoint metadata
   331→- Tracks session state in `.git/entire-sessions/` (shared across worktrees)
   332→- PrePush hook can push `entire/checkpoints/v1` branch alongside user pushes
   333→- `AllowsMainBranch() = true` - safe to use on main/master since it never modifies commit history
   334→
   335→**Auto-Commit Strategy** (`auto_commit.go`)
   336→- Code commits to active branch with **clean history** (commits have `Entire-Checkpoint` trailer only)
   337→- Metadata stored on orphan `entire/checkpoints/v1` branch at sharded paths: `<id[:2]>/<id[2:]>/`
   338→- Uses `checkpoint.WriteCommitted()` for metadata storage
   339→- Checkpoint ID (12-hex-char) links code commits to metadata on `entire/checkpoints/v1`
   340→- Full rewind allowed if commit is only on current branch (not in main); otherwise logs-only
   341→- Rewind via `git reset --hard`
   342→- PrePush hook can push `entire/checkpoints/v1` branch alongside user pushes
   343→- `AllowsMainBranch() = true` - creates commits on active branch
   344→
   345→#### When Modifying Strategies
   346→- All strategies must implement the full `Strategy` interface
   347→- Register new strategies in `init()` using `Register()`
   348→- Test with `mise run test` - strategy tests are in `*_test.go` files

   138→### Error Handling
   139→
   140→The CLI uses a specific pattern for error output to avoid duplication between Cobra and main.go.
   141→
   142→**How it works:**
   143→- `root.go` sets `SilenceErrors: true` globally - Cobra never prints errors
   144→- `main.go` prints errors to stderr, unless the error is a `SilentError`
   145→- Commands return `NewSilentError(err)` when they've already printed a custom message
   146→
   147→**When to use `SilentError`:**
   148→Use `NewSilentError()` when you want to print a custom, user-friendly error message instead of the raw error:
   149→
   150→```go
   151→// In a command's RunE function:
   152→if _, err := paths.RepoRoot(); err != nil {
   153→    cmd.SilenceUsage = true  // Don't show usage for prerequisite errors
   154→    fmt.Fprintln(cmd.ErrOrStderr(), "Not a git repository. Please run 'entire enable' from within a git repository.")
   155→    return NewSilentError(errors.New("not a git repository"))
   156→}
   157→```
   158→
   159→**When NOT to use `SilentError`:**
   160→For normal errors where the default error message is sufficient, just return the error directly. main.go will print it:
   161→
   162→```go
   163→// Normal error - main.go will print "unknown strategy: foo"
   164→return fmt.Errorf("unknown strategy: %s", name)
   165→```
   166→
   167→**Key files:**
   168→- `errors.go` - Defines `SilentError` type and `NewSilentError()` constructor
   169→- `root.go` - Sets `SilenceErrors: true` on root command
   170→- `main.go` - Checks for `SilentError` before printing

   216→### Git Operations
   217→
   218→We use github.com/go-git/go-git for most git operations, but with important exceptions:
   219→
   220→#### go-git v5 Bugs - Use CLI Instead
   221→
   222→**Do NOT use go-git v5 for `checkout` or `reset --hard` operations.**
   223→
   224→go-git v5 has a bug where `worktree.Reset()` with `git.HardReset` and `worktree.Checkout()` incorrectly delete untracked directories even when they're listed in `.gitignore`. This would destroy `.entire/` and `.worktrees/` directories.
   225→
   226→Use the git CLI instead:
   227→```go
   228→// WRONG - go-git deletes ignored directories
   229→worktree.Reset(&git.ResetOptions{
   230→    Commit: hash,
   231→    Mode:   git.HardReset,
   232→})
   233→
   234→// CORRECT - use git CLI
   235→cmd := exec.CommandContext(ctx, "git", "reset", "--hard", hash.String())
   236→```
   237→
   238→See `HardResetWithProtection()` in `common.go` and `CheckoutBranch()` in `git_operations.go` for examples.
   239→
   240→Regression tests in `hard_reset_test.go` verify this behavior - if go-git v6 fixes this issue, those tests can be used to validate switching back.
   241→
   242→#### Repo Root vs Current Working Directory
   243→
   244→**Always use repo root (not `os.Getwd()`) when working with git-relative paths.**
   245→
   246→Git commands like `git status` and `worktree.Status()` return paths relative to the **repository root**, not the current working directory. When Claude runs from a subdirectory (e.g., `/repo/frontend`), using `os.Getwd()` to construct absolute paths will produce incorrect results for files in sibling directories.
   247→
   248→```go
   249→// WRONG - breaks when running from subdirectory
   250→cwd, _ := os.Getwd()  // e.g., /repo/frontend
   251→absPath := filepath.Join(cwd, file)  // file="api/src/types.ts" → /repo/frontend/api/src/types.ts (WRONG)
   252→
   253→// CORRECT - use repo root
   254→repoRoot, _ := paths.RepoRoot()  // or strategy.GetWorktreePath()
   255→absPath := filepath.Join(repoRoot, file)  // → /repo/api/src/types.ts (CORRECT)
   256→```
   257→
   258→This also affects path filtering. The `paths.ToRelativePath()` function rejects paths starting with `..`, so computing relative paths from cwd instead of repo root will filter out files in sibling directories:
   259→
   260→```go
   261→// WRONG - filters out sibling directory files
   262→cwd, _ := os.Getwd()  // /repo/frontend
   263→relPath := paths.ToRelativePath("/repo/api/file.ts", cwd)  // returns "" (filtered out as "../api/file.ts")
   264→
   265→// CORRECT - keeps all repo files
   266→repoRoot, _ := paths.RepoRoot()
   267→relPath := paths.ToRelativePath("/repo/api/file.ts", repoRoot)  // returns "api/file.ts"
   268→```
   269→
   270→**When to use `os.Getwd()`:** Only when you actually need the current directory (e.g., finding agent session directories that are cwd-relative).
   271→
   272→**When to use repo root:** Any time you're working with paths from git status, git diff, or any git-relative file list.
   273→
   274→Test case in `state_test.go`: `TestFilterAndNormalizePaths_SiblingDirectories` documents this bug pattern.

   276→### Session Strategies (`cmd/entire/cli/strategy/`)
   277→
   278→The CLI uses a strategy pattern for managing session data and checkpoints. Each strategy implements the `Strategy` interface defined in `strategy.go`.
   279→
   280→#### Core Interface
   281→All strategies implement:
   282→- `SaveStep()` - Save session step checkpoint (code + metadata)
   283→- `SaveTaskStep()` - Save subagent task step checkpoint
   284→- `GetRewindPoints()` / `Rewind()` - List and restore to checkpoints
   285→- `GetSessionLog()` / `GetSessionInfo()` - Retrieve session data
   286→- `ListSessions()` / `GetSession()` - Session discovery
   287→
   288→#### Available Strategies
   289→
   290→| Strategy | Main Branch | Metadata Storage | Use Case |
   291→|----------|-------------|------------------|----------|
   292→| **manual-commit** (default) | Unchanged (no commits) | `entire/<HEAD-hash>-<worktreeHash>` branches + `entire/checkpoints/v1` | Recommended for most workflows |
   293→| **auto-commit** | Creates clean commits | Orphan `entire/checkpoints/v1` branch | Teams that want code commits from sessions |
   294→
   295→#### Strategy Details
   296→
   297→**Manual-Commit Strategy** (`manual_commit*.go`) - Default
   298→- **Does not modify** the active branch - no commits created on the working branch
   299→- Creates shadow branch `entire/<HEAD-commit-hash[:7]>-<worktreeHash[:6]>` per base commit + worktree
   300→- **Worktree-specific branches** - each git worktree gets its own shadow branch namespace, preventing conflicts
   301→- **Supports multiple concurrent sessions** - checkpoints from different sessions in the same directory interleave on the same shadow branch
   302→- Session logs are condensed to permanent `entire/checkpoints/v1` branch on user commits
   303→- Builds git trees in-memory using go-git plumbing APIs
   304→- Rewind restores files from shadow branch commit tree (does not use `git reset`)
   305→- **Location-independent transcript resolution** - transcript paths are always computed dynamically from the current repo location (via `agent.GetSessionDir` + `agent.ResolveSessionFile`), never stored in checkpoint metadata. This ensures restore/rewind works after repo relocation or across machines.
   306→- Tracks session state in `.git/entire-sessions/` (shared across worktrees)
   307→- **Shadow branch migration** - if user does stash/pull/rebase (HEAD changes without commit), shadow branch is automatically moved to new base commit
   308→- **Orphaned branch cleanup** - if a shadow branch exists without a corresponding session state file, it is automatically reset when a new session starts
   309→- PrePush hook can push `entire/checkpoints/v1` branch alongside user pushes
   310→- `AllowsMainBranch() = true` - safe to use on main/master since it never modifies commit history
   311→
   312→**Auto-Commit Strategy** (`auto_commit.go`)
   313→- Code commits to active branch with **clean history** (commits have `Entire-Checkpoint` trailer only)
   314→- Metadata stored on orphan `entire/checkpoints/v1` branch at sharded paths: `<id[:2]>/<id[2:]>/`
   315→- Uses `checkpoint.WriteCommitted()` for metadata storage
   316→- Checkpoint ID (12-hex-char) links code commits to metadata on `entire/checkpoints/v1`
   317→- Full rewind allowed if commit is only on current branch (not in main); otherwise logs-only
   318→- Rewind via `git reset --hard`
   319→- PrePush hook can push `entire/checkpoints/v1` branch alongside user pushes
   320→- `AllowsMainBranch() = true` - creates commits on active branch, safe to use on main/master

   353→#### Session Phase State Machine
   354→
   355→Sessions track their lifecycle through phases managed by a state machine in `session/phase.go`:
   356→
   357→**Phases:** `ACTIVE`, `IDLE`, `ENDED`
   358→
   359→**Events:**
   360→- `TurnStart` - Agent begins a turn (UserPromptSubmit hook)
   361→- `TurnEnd` - Agent finishes a turn (Stop hook)
   362→- `GitCommit` - A git commit was made (PostCommit hook)
   363→- `SessionStart` - New session started
   364→- `SessionStop` - Session explicitly stopped
   365→
   366→**Key transitions:**
   367→- `IDLE + TurnStart → ACTIVE` - Agent starts working
   368→- `ACTIVE + TurnEnd → IDLE` - Agent finishes turn
   369→- `ACTIVE + GitCommit → ACTIVE` - User commits while agent is working (condense immediately)
   370→- `IDLE + GitCommit → IDLE` - User commits between turns (condense immediately)
   371→- `ENDED + GitCommit → ENDED` - Post-session commit (condense if files touched)
   372→
   373→The state machine emits **actions** (e.g., `ActionCondense`, `ActionUpdateLastInteraction`) that hook handlers dispatch to strategy-specific implementations.
   374→
   375→#### Metadata Structure
   376→
   377→**Shadow Strategy** - Shadow branches (`entire/<commit-hash[:7]>-<worktreeHash[:6]>`):
   378→```
   379→.entire/metadata/<session-id>/
   380→├── full.jsonl               # Session transcript
   381→├── prompt.txt               # User prompts
   382→├── context.md               # Generated context
   383→└── tasks/<tool-use-id>/     # Task checkpoints
   384→    ├── checkpoint.json      # UUID mapping for rewind
   385→    └── agent-<id>.jsonl     # Subagent transcript
   386→```
   387→
   388→**Both Strategies** - Metadata branch (`entire/checkpoints/v1`) - sharded checkpoint format:
   389→```
   390→<checkpoint-id[:2]>/<checkpoint-id[2:]>/
   391→├── metadata.json            # CheckpointSummary (aggregated stats)
   392→├── 0/                       # First session (0-based indexing)
   393→│   ├── metadata.json        # Session-specific metadata
   394→│   ├── full.jsonl           # Session transcript
   395→│   ├── prompt.txt           # User prompts
   396→│   ├── context.md           # Generated context
   397→│   ├── content_hash.txt     # SHA256 of transcript
   398→│   └── tasks/<tool-use-id>/ # Task checkpoints (if applicable)
   399→│       ├── checkpoint.json  # UUID mapping
   400→│       └── agent-<id>.jsonl # Subagent transcript
   401→├── 1/                       # Second session (if multiple sessions)
   402→│   ├── metadata.json
   403→│   ├── full.jsonl
   404→│   └── ...
   405→└── ...
   406→```
   407→
   408→**Multi-session metadata.json format:**
   409→```json
   410→{
   411→  "checkpoint_id": "abc123def456",
   412→  "session_id": "2026-01-13-uuid",      // Current/latest session
   413→  "session_ids": ["2026-01-13-uuid1", "2026-01-13-uuid2"],  // All sessions
   414→  "session_count": 2,                    // Number of sessions in this checkpoint
   415→  "strategy": "manual-commit",
   416→  "created_at": "2026-01-13T12:00:00Z",
   417→  "files_touched": ["file1.txt", "file2.txt"]  // Merged from all sessions
   418→}
   419→```
   420→
   421→When multiple sessions are condensed to the same checkpoint (same base commit):
   422→- Sessions are stored in numbered subfolders using 0-based indexing (`0/`, `1/`, `2/`, etc.)
   423→- Latest session is always in the highest-numbered folder
   424→- `session_ids` array tracks all sessions, `session_count` increments
   425→
   426→**Session State** (filesystem, `.git/entire-sessions/`):
   427→```
   428→<session-id>.json            # Active session state (base_commit, checkpoint_count, etc.)
   429→```

   431→#### Checkpoint ID Linking
   432→
   433→Both strategies use a **12-hex-char random checkpoint ID** (e.g., `a3b2c4d5e6f7`) as the stable identifier linking user commits to metadata.
   434→
   435→**How checkpoint IDs work:**
   436→
   437→1. **Generated once per checkpoint**: Either when saving (auto-commit) or when condensing (manual-commit)
   438→
   439→2. **Added to user commits** via `Entire-Checkpoint` trailer:
   440→   - **Auto-commit**: Added programmatically when creating the commit
   441→   - **Manual-commit**: Added via `prepare-commit-msg` hook (user can remove it before committing)
   442→
   443→3. **Used for directory sharding** on `entire/checkpoints/v1` branch:
   444→   - Path format: `<id[:2]>/<id[2:]>/`
   445→   - Example: `a3b2c4d5e6f7` → `a3/b2c4d5e6f7/`
   446→   - Creates 256 shards to avoid directory bloat
   447→
   448→4. **Appears in commit subject** on `entire/checkpoints/v1` commits:
   449→   - Format: `Checkpoint: a3b2c4d5e6f7`
   450→   - Makes `git log entire/checkpoints/v1` readable and searchable
   451→
   452→**Bidirectional linking:**
   453→
   454→```
   455→User commit → Metadata:
   456→  Extract "Entire-Checkpoint: a3b2c4d5e6f7" trailer
   457→  → Read a3/b2c4d5e6f7/ directory from entire/checkpoints/v1 tree at HEAD
   458→
   459→Metadata → User commits:
   460→  Given checkpoint ID a3b2c4d5e6f7
   461→  → Search user branch history for commits with "Entire-Checkpoint: a3b2c4d5e6f7" trailer
   462→```
   463→
   464→Note: Commit subjects on `entire/checkpoints/v1` (e.g., `Checkpoint: a3b2c4d5e6f7`) are
   465→for human readability in `git log` only. The CLI always reads from the tree at HEAD.
   466→
   467→**Example:**
   468→```
   469→User's commit (on main branch):
   470→  "Implement login feature
   471→
   472→  Entire-Checkpoint: a3b2c4d5e6f7"
   473→       ↓ ↑
   474→       Linked via checkpoint ID
   475→       ↓ ↑
   476→entire/checkpoints/v1 commit:
   477→  Subject: "Checkpoint: a3b2c4d5e6f7"
   478→
   479→  Tree: a3/b2c4d5e6f7/
   480→    ├── metadata.json (checkpoint_id: "a3b2c4d5e6f7")
   481→    ├── full.jsonl (session transcript)
   482→    ├── prompt.txt
   483→    └── context.md
   484→```
   485→
   486→#### Commit Trailers
   487→
   488→**On user's active branch commits (both strategies):**
   489→- `Entire-Checkpoint: <checkpoint-id>` - 12-hex-char ID linking to metadata on `entire/checkpoints/v1`
   490→  - Auto-commit: Always added when creating commits
   491→  - Manual-commit: Added by hook; user can remove to skip linking
   492→
   493→**On shadow branch commits (`entire/<commit-hash[:7]>-<worktreeHash[:6]>`) - manual-commit only:**
   494→- `Entire-Session: <session-id>` - Session identifier
   495→- `Entire-Metadata: <path>` - Path to metadata directory within the tree
   496→- `Entire-Task-Metadata: <path>` - Path to task metadata directory (for task checkpoints)
   497→- `Entire-Strategy: manual-commit` - Strategy that created the commit
   498→
   499→**On metadata branch commits (`entire/checkpoints/v1`) - both strategies:**
   500→
   501→Commit subject: `Checkpoint: <checkpoint-id>` (or custom subject for task checkpoints)
   502→
   503→Trailers:
   504→- `Entire-Session: <session-id>` - Session identifier
   505→- `Entire-Strategy: <strategy>` - Strategy name (manual-commit or auto-commit)
   506→- `Entire-Agent: <agent-name>` - Agent name (optional, e.g., "Claude Code")
   507→- `Ephemeral-branch: <branch>` - Shadow branch name (optional, manual-commit only)
   508→- `Entire-Metadata-Task: <path>` - Task metadata path (optional, for task checkpoints)
   509→
   510→**Note:** Both strategies keep active branch history **clean** - the only addition to user commits is the single `Entire-Checkpoint` trailer. Manual-commit never creates commits on the active branch (user creates them manually). Auto-commit creates commits but only adds the checkpoint trailer. All detailed session data (transcripts, prompts, context) is stored on the `entire/checkpoints/v1` orphan branch or shadow branches.
   511→
   512→#### Multi-Session Behavior
   513→
   514→**Concurrent Sessions:**
   515→- When a second session starts in the same directory while another has uncommitted checkpoints, a warning is shown
   516→- Both sessions can proceed - their checkpoints interleave on the same shadow branch
   517→- Each session's `RewindPoint` includes `SessionID` and `SessionPrompt` to help identify which checkpoint belongs to which session
   518→- On commit, all sessions are condensed together with archived sessions in numbered subfolders
   519→- Note: Different git worktrees have separate shadow branches (worktree-specific naming), so concurrent sessions in different worktrees do not conflict
   520→
   521→**Orphaned Shadow Branches:**
   522→- A shadow branch is "orphaned" if it exists but has no corresponding session state file
   523→- This can happen if the state file is manually deleted or lost
   524→- When a new session starts with an orphaned branch, the branch is automatically reset
   525→- If the existing session DOES have a state file (concurrent session in same directory), a `SessionIDConflictError` is returned
   526→
   527→**Shadow Branch Migration (Pull/Rebase):**
   528→- If user does stash → pull → apply (or rebase), HEAD changes but work isn't committed
   529→- The shadow branch would be orphaned at the old commit
   530→- Detection: base commit changed AND old shadow branch still exists (would be deleted if user committed)
   531→- Action: shadow branch is renamed from `entire/<old-hash>-<worktreeHash>` to `entire/<new-hash>-<worktreeHash>`
   532→- Session continues seamlessly with checkpoints preserved
   533→
