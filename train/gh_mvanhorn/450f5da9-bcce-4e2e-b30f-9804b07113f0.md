Trails answer "why/what" (human intent) while Checkpoints answer "how/when" (machine snapshots). They're linked by branch name. This plan adds the CLI counterpart: an `entire trail` command that creates and manages trail metadata locally in git. When pushed (via pre-push hook), the web UI picks it up via webhooks automatically. Additionally, trails are auto-created when an agent session starts on a non-main branch. ## Command Structure ``` entire trail # Show current branch's trail (or list if none) entire trail list # List all trails (with optional --status filter) entire trail create # Create a trail for current or new branch entire trail update # Update trail metadata (status, title, etc.) ``` ## Key Design Decisions - **Storage**: Dedicated `entire/trails` orphan branch (matches web PR) - **ID format**: 12 hex char IDs with `<id[:2]>/<id[2:]>/` sharding (same as checkpoints) - **Auto-create**: On session start (UserPromptSubmit hook), if on a non-main branch without a trail, auto-create one with status `in_progress` - **Push**: Pre-push hook pushes `entire/trails` alongside `entire/checkpoints/v1` - **Linking**: Trail ↔ Checkpoints linked by branch name (no foreign key) ## Data Format ### `entire/trails` branch structure ``` <trail_id[:2]>/<trail_id[2:]>/ metadata.json discussion.json # Empty initially, comments come later ``` ### `metadata.json` (matches web PR format) ```json { "trail_id": "abcdef123456", "branch": "feature/auth", "base": "main", "title": "Add user authentication", "description": "", "status": "in_progress", "author": "alice", "assignees": [], "labels": [], "created_at": "2026-02-18T10:30:00Z", "updated_at": "2026-02-20T14:22:00Z" } ``` ### Trail Status Lifecycle ``` draft → open → in_progress → in_review → done → closed ``` ## Implementation Steps ### 1.
