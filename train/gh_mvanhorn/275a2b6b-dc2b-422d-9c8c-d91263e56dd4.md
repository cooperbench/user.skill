Here's the breakdown: ## `e2e_test/` vs `integration_test/` — Key Differences ### 1. Real Agents vs Simulated Hooks The fundamental difference is **what drives the session**. **`e2e_test/`** launches a **real AI agent** (Claude Code, Gemini CLI, etc.) as a subprocess. The `AgentRunner` interface (`agent_runner.go`) actually invokes `claude -p "Create a file..."` and waits for it to finish. The agent creates real files, makes real API calls, and fires real hooks. **`integration_test/`** **simulates** the agent's hook lifecycle by calling the CLI hook commands directly. The `HookRunner` (`hooks.go`) manually invokes `entire hooks claude-code user-prompt-submit`, `entire hooks claude-code stop`, etc. with crafted JSON input. Transcripts are fabricated with `TranscriptBuilder` — no actual LLM is called. ### 2. Build Tags & Cost | | `e2e_test/` | `integration_test/` | |---|---|---| | Build tag | `//go:build e2e` | `//go:build integration` | | Run command | `E2E_AGENT=claude-code go test -tags=e2e` | `mise run test:integration` | | API calls | Yes (costs real tokens) | No | | CI default | Excluded (opt-in) | Included in `test:ci` | ### 3. TestEnv Design Both suites have a `TestEnv` but they're designed differently: - **Integration `TestEnv`** imports internal packages (`strategy`, `checkpoint`, `paths`, `agent`, `trailers`) and has rich hook simulation — `SimulateUserPromptSubmit`, `SimulateStop`, `SimulatePreTask`, `SimulatePostTask`, etc. for Claude, Gemini, and Factory Droid. It constructs fake transcripts and manually orchestrates the full session lifecycle step by step. - **E2E `TestEnv`** is a thinner wrapper. It has `RunAgent(prompt)` which delegates to the real agent binary and `RunEntireEnable(strategy)` which calls the actual `entire enable` CLI command. It doesn't import internal packages — it exercises the system purely through the CLI binary and agent subprocesses. ### 4.
