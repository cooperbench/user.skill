> DEVELOPER

how do I define more steps for the validate command?

> AGENT

Add proofs to `.entire/settings.json` under `strategy_options.validation`:

```json
{
  "strategy_options": {
    "validation": {
      "enabled": true,
      "proofs": [
        {"type": "test", "command": "mise run test", "required": true},
        {"type": "lint", "command": "mise run lint", "required": true},
        {"type": "typecheck", "command": "go build ./...", "required": true},
        {"type": "security", "command": "gosec ./...", "required": false}
      ]
    }
  }
}
```

Each proof has three fields:
- **`type`** — a label for the check (used for filtering with `--proof`)
- **`command`** — shell command that must exit 0 to pass
- **`required`** — if `true`, a failure means overall validation fails. If `false`, it's advisory only

You can then run specific proofs with `entire validate --proof lint` or get machine-readable output with `entire validate --json`. Each proof gets a 10-minute timeout.

> DEVELOPER

can you look at the dark-factory md and help me what the next step would be?

> AGENT

Looking at the roadmap, Phase 1 (the validate command) is done. The next phase is:

**Phase 2: Validation Storage** — storing proof results alongside checkpoint metadata.

The idea is that every time a checkpoint is saved, the validation results get attached to it. This gives you a historical record of what passed/failed per checkpoint.

But honestly, I think **Phase 3 (Feedback Injection)** is the more impactful next step. Here's why:

- **Phase 2** (storage) is bookkeeping — useful for observability later, but doesn't change the development loop
- **Phase 3** (feedback injection) is where the autonomy actually starts — when validation fails, the agent sees the errors on its next turn and can self-correct without human intervention

You could combine them: run proofs after a checkpoint, store the results (Phase 2), and if something failed, write a feedback file the agent reads on its next prompt (Phase 3). That's one coherent feature rather than two separate ones.

The practical implementation would be:
1. Hook into the `Stop` event (agent finished a turn)
2. Run configured proofs automatically
3. Write failures to something like `.entire/validation-feedback.md`
4. Agent hooks read that file on `SessionStart`/`UserPromptSubmit` and inject it as context

Want me to plan out the implementation for this?
