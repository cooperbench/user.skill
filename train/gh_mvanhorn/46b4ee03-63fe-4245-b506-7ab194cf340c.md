## Research Summary: Go Static Analysis Tools for UTF-8 Safe String Truncation

Based on my comprehensive web research, here are my findings regarding Go linters and static analysis tools that can detect unsafe byte-based string truncation:

### 1. **Current Status: No Dedicated Built-in Linter**

Unfortunately, **there is no existing linter in the standard golangci-lint ecosystem that specifically detects unsafe byte-based string truncation** (patterns like `str[:n]` that could split multi-byte UTF-8 characters). This gap exists even though the problem is well-documented and common.

### 2. **Closest Existing Tools**

#### Staticcheck (SA1011)
Staticcheck includes **SA1011** which "flags issues where various methods in the `strings` package expect valid UTF-8, but invalid input is provided." However, this check focuses on validating UTF-8 input to string functions, not detecting slicing operations that could corrupt UTF-8.

#### Forbidigo (Already in Your Project)
Your project already uses **forbidigo** (enabled in `.golangci.yaml`). Forbidigo is designed to forbid identifiers using regex patterns and supports:
- Pattern matching with optional custom messages
- Type analysis via `analyze_types: true` (which you have enabled)
- Both simple patterns and complex JSON/YAML regex patterns

**Important note:** While forbidigo can match function calls and identifiers, **it cannot detect slice operations** like `str[:n]` because these are not function calls—they're AST operations (index expressions). Forbidigo is designed to match patterns in the expanded expression text or AST method calls, not for this type of syntactic operation.

### 3. **Existing Community Solutions (Not Linters)**

Several Go packages provide **safe string truncation implementations** rather than linters to detect unsafe code:
- **aquilax/truncate** - Provides UTF-8 aware string truncation strategies
- **cdfmlr/ellipsis** - Truncates long strings safely without cutting multi-byte characters
- **golang.org/x/exp/utf8string** - UTF-8 string handling utilities
- **huandu/xstrings** - Extended string algorithms with rune-aware operations

However, these are helper libraries, not static analysis tools.

### 4. **Custom Analyzer Option: golang.org/x/tools/go/analysis**

The **only viable path forward for automated detection** would be to create a **custom analyzer** using `golang.org/x/tools/go/analysis`. This would require:

- Building a custom analyzer that inspects the AST for slice operations (`ast.SliceExpr`) on string-typed expressions
- Analyzing the slice bounds to determine if they're literal byte indexes (which are unsafe) vs. rune-aware calculations
- Registering this as a custom linter compatible with golangci-lint

This is technically feasible since:
- The Go standard library provides powerful AST analysis tools
- Multiple examples exist of custom analyzers integrated with golangci-lint
- The `golang.org/x/tools` framework is designed exactly for this purpose

### 5. **Related Existing Checks**

The only tangentially related checks found in the linting ecosystem:
- **gocritic**: Includes `preferWriteByte` (suggests using `WriteByte` instead of `WriteRune` for single-byte runes), but this doesn't catch string slicing
- **gosec**: Focuses on security vulnerabilities; doesn't detect UTF-8 truncation issues
- **S1029** (Staticcheck): Recommends ranging directly over strings rather than converting to rune slices (optimization, not safety)
- **bidichk**: Checks for dangerous unicode character sequences (bidi attacks), not truncation

### 6. **Forbidigo Cannot Be Used for This**

While forbidigo is powerful, it **cannot** detect the pattern you need because:
- It matches identifiers, function calls, and expanded expressions
- Slice operations like `str[:n]` are syntactic constructs (index expressions in the AST), not function calls
- You would need an AST-based analyzer that walks the syntax tree looking for `IndexExpr` or `SliceExpr` nodes

   137→### Error Handling
   138→
   139→The CLI uses a specific pattern for error output to avoid duplication between Cobra and main.go.
   140→
   141→**How it works:**
   142→- `root.go` sets `SilenceErrors: true` globally - Cobra never prints errors
   143→- `main.go` prints errors to stderr, unless the error is a `SilentError`
   144→- Commands return `NewSilentError(err)` when they've already printed a custom message
   145→
   146→**When to use `SilentError`:**
   147→Use `NewSilentError()` when you want to print a custom, user-friendly error message instead of the raw error:
   148→
   149→```go
   150→// In a command's RunE function:
   151→if _, err := paths.RepoRoot(); err != nil {
   152→    cmd.SilenceUsage = true  // Don't show usage for prerequisite errors
   153→    fmt.Fprintln(cmd.ErrOrStderr(), "Not a git repository. Please run 'entire enable' from within a git repository.")
   154→    return NewSilentError(errors.New("not a git repository"))
   155→}
   156→```
   157→
   158→**When NOT to use `SilentError`:**
   159→For normal errors where the default error message is sufficient, just return the error directly. main.go will print it:
   160→
   161→```go
   162→// Normal error - main.go will print "unknown strategy: foo"
   163→return fmt.Errorf("unknown strategy: %s", name)
   164→```
   165→
   166→**Key files:**
   167→- `errors.go` - Defines `SilentError` type and `NewSilentError()` constructor
   168→- `root.go` - Sets `SilenceErrors: true` on root command
   169→- `main.go` - Checks for `SilentError` before printing

   215→### Git Operations
   216→
   217→We use github.com/go-git/go-git for most git operations, but with important exceptions:
   218→
   219→#### go-git v5 Bugs - Use CLI Instead
   220→
   221→**Do NOT use go-git v5 for `checkout` or `reset --hard` operations.**
   222→
   223→go-git v5 has a bug where `worktree.Reset()` with `git.HardReset` and `worktree.Checkout()` incorrectly delete untracked directories even when they're listed in `.gitignore`. This would destroy `.entire/` and `.worktrees/` directories.
   224→
   225→Use the git CLI instead:
   226→```go
   227→// WRONG - go-git deletes ignored directories
   228→worktree.Reset(&git.ResetOptions{
   229→    Commit: hash,
   230→    Mode:   git.HardReset,
   231→})
   232→
   233→// CORRECT - use git CLI
   234→cmd := exec.CommandContext(ctx, "git", "reset", "--hard", hash.String())
   235→```
   236→
   237→See `HardResetWithProtection()` in `common.go` and `CheckoutBranch()` in `git_operations.go` for examples.
   238→
   239→Regression tests in `hard_reset_test.go` verify this behavior - if go-git v6 fixes this issue, those tests can be used to validate switching back.
   240→
   241→#### Repo Root vs Current Working Directory
   242→
   243→**Always use repo root (not `os.Getwd()`) when working with git-relative paths.**
   244→
   245→Git commands like `git status` and `worktree.Status()` return paths relative to the **repository root**, not the current working directory. When Claude runs from a subdirectory (e.g., `/repo/frontend`), using `os.Getwd()` to construct absolute paths will produce incorrect results for files in sibling directories.
   246→
   247→```go
   248→// WRONG - breaks when running from subdirectory
   249→cwd, _ := os.Getwd()  // e.g., /repo/frontend
   250→absPath := filepath.Join(cwd, file)  // file="api/src/types.ts" → /repo/frontend/api/src/types.ts (WRONG)
   251→
   252→// CORRECT - use repo root
   253→repoRoot, _ := paths.RepoRoot()  // or strategy.GetWorktreePath()
   254→absPath := filepath.Join(repoRoot, file)  // → /repo/api/src/types.ts (CORRECT)
   255→```
   256→
   257→This also affects path filtering. The `paths.ToRelativePath()` function rejects paths starting with `..`, so computing relative paths from cwd instead of repo root will filter out files in sibling directories:
   258→
   259→```go
   260→// WRONG - filters out sibling directory files
   261→cwd, _ := os.Getwd()  // /repo/frontend
   262→relPath := paths.ToRelativePath("/repo/api/file.ts", cwd)  // returns "" (filtered out as "../api/file.ts")
   263→
   264→// CORRECT - keeps all repo files
   265→repoRoot, _ := paths.RepoRoot()
   266→relPath := paths.ToRelativePath("/repo/api/file.ts", repoRoot)  // returns "api/file.ts"
   267→```
   268→
   269→**When to use `os.Getwd()`:** Only when you actually need the current directory (e.g., finding agent session directories that are cwd-relative).
   270→
   271→**When to use repo root:** Any time you're working with paths from git status, git diff, or any git-relative file list.
   272→
   273→Test case in `state_test.go`: `TestFilterAndNormalizePaths_SiblingDirectories` documents this bug pattern.

   275→### Session Strategies (`cmd/entire/cli/strategy/`)
   276→
   277→The CLI uses a strategy pattern for managing session data and checkpoints. Each strategy implements the `Strategy` interface defined in `strategy.go`.
   278→
   279→#### Core Interface
   280→All strategies implement:
   281→- `SaveStep()` - Save session step checkpoint (code + metadata)
   282→- `SaveTaskStep()` - Save subagent task step checkpoint
   283→- `GetRewindPoints()` / `Rewind()` - List and restore to checkpoints
   284→- `GetSessionLog()` / `GetSessionInfo()` - Retrieve session data
   285→- `ListSessions()` / `GetSession()` - Session discovery
   286→
   287→#### Available Strategies
   288→
   289→| Strategy | Main Branch | Metadata Storage | Use Case |
   290→|----------|-------------|------------------|----------|
   291→| **manual-commit** (default) | Unchanged (no commits) | `entire/<HEAD-hash>-<worktreeHash>` branches + `entire/checkpoints/v1` | Recommended for most workflows |
   292→| **auto-commit** | Creates clean commits | Orphan `entire/checkpoints/v1` branch | Teams that want code commits from sessions |
   293→
   294→#### Strategy Details
   295→
   296→**Manual-Commit Strategy** (`manual_commit*.go`) - Default
   297→- **Does not modify** the active branch - no commits created on the working branch
   298→- Creates shadow branch `entire/<HEAD-commit-hash[:7]>-<worktreeHash[:6]>` per base commit + worktree
   299→- **Worktree-specific branches** - each git worktree gets its own shadow branch namespace, preventing conflicts
   300→- **Supports multiple concurrent sessions** - checkpoints from different sessions in the same directory interleave on the same shadow branch
   301→- Session logs are condensed to permanent `entire/checkpoints/v1` branch on user commits
   302→- Builds git trees in-memory using go-git plumbing APIs
   303→- Rewind restores files from shadow branch commit tree (does not use `git reset`)
   304→- **Location-independent transcript resolution** - transcript paths are always computed dynamically from the current repo location (via `agent.GetSessionDir` + `agent.ResolveSessionFile`), never stored in checkpoint metadata. This ensures restore/rewind works after repo relocation or across machines.
   305→- Tracks session state in `.git/entire-sessions/` (shared across worktrees)
   306→- **Shadow branch migration** - if user does stash/pull/rebase (HEAD changes without commit), shadow branch is automatically moved to new base commit
   307→- **Orphaned branch cleanup** - if a shadow branch exists without a corresponding session state file, it is automatically reset when a new session starts
   308→- PrePush hook can push `entire/checkpoints/v1` branch alongside user pushes
   309→- `AllowsMainBranch() = true` - safe to use on main/master since it never modifies commit history
   310→
   311→**Auto-Commit Strategy** (`auto_commit.go`)
   312→- Code commits to active branch with **clean history** (commits have `Entire-Checkpoint` trailer only)
   313→- Metadata stored on orphan `entire/checkpoints/v1` branch at sharded paths: `<id[:2]>/<id[2:]>/`
   314→- Uses `checkpoint.WriteCommitted()` for metadata storage
   315→- Checkpoint ID (12-hex-char) links code commits to metadata on `entire/checkpoints/v1`
   316→- Full rewind allowed if commit is only on current branch (not in main); otherwise logs-only
   317→- Rewind via `git reset --hard`
   318→- PrePush hook can push `entire/checkpoints/v1` branch alongside user pushes
   319→- `AllowsMainBranch() = true` - creates commits on active branch, safe to use on main/master

   352→#### Session Phase State Machine
   353→
   354→Sessions track their lifecycle through phases managed by a state machine in `session/phase.go`:
   355→
   356→**Phases:** `ACTIVE`, `IDLE`, `ENDED`
   357→
   358→**Events:**
   359→- `TurnStart` - Agent begins a turn (UserPromptSubmit hook)
   360→- `TurnEnd` - Agent finishes a turn (Stop hook)
   361→- `GitCommit` - A git commit was made (PostCommit hook)
   362→- `SessionStart` - New session started
   363→- `SessionStop` - Session explicitly stopped
   364→
   365→**Key transitions:**
   366→- `IDLE + TurnStart → ACTIVE` - Agent starts working
   367→- `ACTIVE + TurnEnd → IDLE` - Agent finishes turn
   368→- `ACTIVE + GitCommit → ACTIVE` - User commits while agent is working (condense immediately)
   369→- `IDLE + GitCommit → IDLE` - User commits between turns (condense immediately)
   370→- `ENDED + GitCommit → ENDED` - Post-session commit (condense if files touched)
   371→
   372→The state machine emits **actions** (e.g., `ActionCondense`, `ActionUpdateLastInteraction`) that hook handlers dispatch to strategy-specific implementations.
   373→
   374→#### Metadata Structure
   375→
   376→**Shadow Strategy** - Shadow branches (`entire/<commit-hash[:7]>-<worktreeHash[:6]>`):
   377→```
   378→.entire/metadata/<session-id>/
   379→├── full.jsonl               # Session transcript
   380→├── prompt.txt               # User prompts
   381→├── context.md               # Generated context
   382→└── tasks/<tool-use-id>/     # Task checkpoints
   383→    ├── checkpoint.json      # UUID mapping for rewind
   384→    └── agent-<id>.jsonl     # Subagent transcript
   385→```
   386→
   387→**Both Strategies** - Metadata branch (`entire/checkpoints/v1`) - sharded checkpoint format:
   388→```
   389→<checkpoint-id[:2]>/<checkpoint-id[2:]>/
   390→├── metadata.json            # CheckpointSummary (aggregated stats)
   391→├── 0/                       # First session (0-based indexing)
   392→│   ├── metadata.json        # Session-specific metadata
   393→│   ├── full.jsonl           # Session transcript
   394→│   ├── prompt.txt           # User prompts
   395→│   ├── context.md           # Generated context
   396→│   ├── content_hash.txt     # SHA256 of transcript
   397→│   └── tasks/<tool-use-id>/ # Task checkpoints (if applicable)
   398→│       ├── checkpoint.json  # UUID mapping
   399→│       └── agent-<id>.jsonl # Subagent transcript
   400→├── 1/                       # Second session (if multiple sessions)
   401→│   ├── metadata.json
   402→│   ├── full.jsonl
   403→│   └── ...
   404→└── ...
   405→```
   406→
   407→**Multi-session metadata.json format:**
   408→```json
   409→{
   410→  "checkpoint_id": "abc123def456",
   411→  "session_id": "2026-01-13-uuid",      // Current/latest session
   412→  "session_ids": ["2026-01-13-uuid1", "2026-01-13-uuid2"],  // All sessions
   413→  "session_count": 2,                    // Number of sessions in this checkpoint
   414→  "strategy": "manual-commit",
   415→  "created_at": "2026-01-13T12:00:00Z",
   416→  "files_touched": ["file1.txt", "file2.txt"]  // Merged from all sessions
   417→}
   418→```
   419→
   420→When multiple sessions are condensed to the same checkpoint (same base commit):
   421→- Sessions are stored in numbered subfolders using 0-based indexing (`0/`, `1/`, `2/`, etc.)
   422→- Latest session is always in the highest-numbered folder
   423→- `session_ids` array tracks all sessions, `session_count` increments
   424→
   425→**Session State** (filesystem, `.git/entire-sessions/`):
   426→```
   427→<session-id>.json            # Active session state (base_commit, checkpoint_count, etc.)
   428→```

   430→#### Checkpoint ID Linking
   431→
   432→Both strategies use a **12-hex-char random checkpoint ID** (e.g., `a3b2c4d5e6f7`) as the stable identifier linking user commits to metadata.
   433→
   434→**How checkpoint IDs work:**
   435→
   436→1. **Generated once per checkpoint**: Either when saving (auto-commit) or when condensing (manual-commit)
   437→
   438→2. **Added to user commits** via `Entire-Checkpoint` trailer:
   439→   - **Auto-commit**: Added programmatically when creating the commit
   440→   - **Manual-commit**: Added via `prepare-commit-msg` hook (user can remove it before committing)
   441→
   442→3. **Used for directory sharding** on `entire/checkpoints/v1` branch:
   443→   - Path format: `<id[:2]>/<id[2:]>/`
   444→   - Example: `a3b2c4d5e6f7` → `a3/b2c4d5e6f7/`
   445→   - Creates 256 shards to avoid directory bloat
   446→
   447→4. **Appears in commit subject** on `entire/checkpoints/v1` commits:
   448→   - Format: `Checkpoint: a3b2c4d5e6f7`
   449→   - Makes `git log entire/checkpoints/v1` readable and searchable
   450→
   451→**Bidirectional linking:**
   452→
   453→```
   454→User commit → Metadata:
   455→  Extract "Entire-Checkpoint: a3b2c4d5e6f7" trailer
   456→  → Read a3/b2c4d5e6f7/ directory from entire/checkpoints/v1 tree at HEAD
   457→
   458→Metadata → User commits:
   459→  Given checkpoint ID a3b2c4d5e6f7
   460→  → Search user branch history for commits with "Entire-Checkpoint: a3b2c4d5e6f7" trailer
   461→```
   462→
   463→Note: Commit subjects on `entire/checkpoints/v1` (e.g., `Checkpoint: a3b2c4d5e6f7`) are
   464→for human readability in `git log` only. The CLI always reads from the tree at HEAD.
   465→
   466→**Example:**
   467→```
   468→User's commit (on main branch):
   469→  "Implement login feature
   470→
   471→  Entire-Checkpoint: a3b2c4d5e6f7"
   472→       ↓ ↑
   473→       Linked via checkpoint ID
   474→       ↓ ↑
   475→entire/checkpoints/v1 commit:
   476→  Subject: "Checkpoint: a3b2c4d5e6f7"
   477→
   478→  Tree: a3/b2c4d5e6f7/
   479→    ├── metadata.json (checkpoint_id: "a3b2c4d5e6f7")
   480→    ├── full.jsonl (session transcript)
   481→    ├── prompt.txt
   482→    └── context.md
   483→```
   484→
   485→#### Commit Trailers
   486→
   487→**On user's active branch commits (both strategies):**
   488→- `Entire-Checkpoint: <checkpoint-id>` - 12-hex-char ID linking to metadata on `entire/checkpoints/v1`
   489→  - Auto-commit: Always added when creating commits
   490→  - Manual-commit: Added by hook; user can remove to skip linking
   491→
   492→**On shadow branch commits (`entire/<commit-hash[:7]>-<worktreeHash[:6]>`) - manual-commit only:**
   493→- `Entire-Session: <session-id>` - Session identifier
   494→- `Entire-Metadata: <path>` - Path to metadata directory within the tree
   495→- `Entire-Task-Metadata: <path>` - Path to task metadata directory (for task checkpoints)
   496→- `Entire-Strategy: manual-commit` - Strategy that created the commit
   497→
   498→**On metadata branch commits (`entire/checkpoints/v1`) - both strategies:**
   499→
   500→Commit subject: `Checkpoint: <checkpoint-id>` (or custom subject for task checkpoints)
   501→
   502→Trailers:
   503→- `Entire-Session: <session-id>` - Session identifier
   504→- `Entire-Strategy: <strategy>` - Strategy name (manual-commit or auto-commit)
   505→- `Entire-Agent: <agent-name>` - Agent name (optional, e.g., "Claude Code")
   506→- `Ephemeral-branch: <branch>` - Shadow branch name (optional, manual-commit only)
   507→- `Entire-Metadata-Task: <path>` - Task metadata path (optional, for task checkpoints)
   508→
   509→**Note:** Both strategies keep active branch history **clean** - the only addition to user commits is the single `Entire-Checkpoint` trailer. Manual-commit never creates commits on the active branch (user creates them manually). Auto-commit creates commits but only adds the checkpoint trailer. All detailed session data (transcripts, prompts, context) is stored on the `entire/checkpoints/v1` orphan branch or shadow branches.
   510→
   511→#### Multi-Session Behavior
   512→
   513→**Concurrent Sessions:**
   514→- When a second session starts in the same directory while another has uncommitted checkpoints, a warning is shown
   515→- Both sessions can proceed - their checkpoints interleave on the same shadow branch
   516→- Each session's `RewindPoint` includes `SessionID` and `SessionPrompt` to help identify which checkpoint belongs to which session
   517→- On commit, all sessions are condensed together with archived sessions in numbered subfolders
   518→- Note: Different git worktrees have separate shadow branches (worktree-specific naming), so concurrent sessions in different worktrees do not conflict
   519→
   520→**Orphaned Shadow Branches:**
   521→- A shadow branch is "orphaned" if it exists but has no corresponding session state file
   522→- This can happen if the state file is manually deleted or lost
   523→- When a new session starts with an orphaned branch, the branch is automatically reset
   524→- If the existing session DOES have a state file (concurrent session in same directory), a `SessionIDConflictError` is returned
   525→
   526→**Shadow Branch Migration (Pull/Rebase):**
   527→- If user does stash → pull → apply (or rebase), HEAD changes but work isn't committed
   528→- The shadow branch would be orphaned at the old commit
   529→- Detection: base commit changed AND old shadow branch still exists (would be deleted if user committed)
   530→- Action: shadow branch is renamed from `entire/<old-hash>-<worktreeHash>` to `entire/<new-hash>-<worktreeHash>`
   531→- Session continues seamlessly with checkpoints preserved
   532→
