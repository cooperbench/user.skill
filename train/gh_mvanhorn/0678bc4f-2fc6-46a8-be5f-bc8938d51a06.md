Here's the full picture. The **`waitForTranscriptFlush`** function is the bottleneck. It:

1. Waits up to **3 seconds** per call for a sentinel in the transcript file
2. It's called **multiple times per commit** — once during `prepare-commit-msg` content detection, and again multiple times during `post-commit` for each session that needs condensation
3. In your logs, the sentinel is **never found** (always times out), meaning you get the full 3s penalty every single call

From the logs, your most recent commit had about **8-9 sentinel timeouts** at 3s each = ~27s of pure waiting.

The sentinel never being found suggests that either:
- The Claude Code session has already ended when you commit (so no new sentinel is written)
- The sentinel format changed in a newer Claude Code version

**Summary:**

| Component | Time | Issue |
|-----------|------|-------|
| `prepare-commit-msg` | ~12-15s | Multiple `waitForTranscriptFlush` calls timing out at 3s each |
| `commit-msg` | ~0.3s | Fine |
| `post-commit` | ~15-19s | Multiple `waitForTranscriptFlush` calls timing out at 3s each per session |
| `go run` overhead | ~0.3s each | Negligible with warm cache |

The fix would be to either skip the sentinel wait when the session has already ended, or reduce the timeout, or make the calls concurrent. Want me to dig into what would be the best fix?

what is the sentinel?

> AGENT

The sentinel is a mechanism to wait for Claude Code to finish writing its transcript file before reading it.

When Claude Code runs hooks (like the `stop` hook), it writes a `hook_progress` entry to the transcript JSONL file. The sentinel logic looks for a line containing `"hooks claude-code stop"` in the transcript file — that entry signals "Claude Code has flushed all pending writes to this transcript, it's safe to read now."

The flow is:

1. Claude Code finishes a turn → fires the `stop` hook → your CLI hook runs
2. Your CLI wants to read the transcript (to extract files touched, check for new content, etc.)
3. But Claude Code writes to the transcript **asynchronously** — the hook fires before the transcript is fully flushed
4. So `waitForTranscriptFlush` polls the last 4KB of the transcript every 50ms for up to **3 seconds**, looking for that `hook_progress` entry with a matching timestamp
5. If found → safe to read. If timeout → read anyway and hope for the best.

The problem is that in your case, the sentinel is **never found** — every call hits the full 3s timeout. This happens because you're committing after the session has already ended (phase = `ended`/`idle`), so Claude Code isn't running any hooks and no new sentinel gets written. But the code still calls `PrepareTranscript` → `waitForTranscriptFlush` on every session it processes, burning 3s each time.
