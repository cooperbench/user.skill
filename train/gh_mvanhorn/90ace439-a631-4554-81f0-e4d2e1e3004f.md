The `revive` linter has a rule called `var-naming` that warns when your package name matches a Go standard library package name. This helps avoid confusion and potential import shadowing issues.

In Go 1.26, the standard library added a new package: `debug/buildinfo`. This package provides functionality for reading build information embedded in Go binaries.

Your codebase has a package at `cmd/entire/cli/buildinfo/` that stores CLI version and build metadata. Before Go 1.26, this name was fine. After Go 1.26, `revive` flags it:

```
cmd/entire/cli/buildinfo/buildinfo.go:1:9: var-naming: avoid package names 
that conflict with Go standard library package names (revive)
package buildinfo
        ^
```

The options were:
1. **Rename the package** (e.g., `cliversion`, `build`) - more disruptive, requires updating all imports
2. **Add a lint exclusion** - acknowledges the conflict but keeps existing code

I chose option 2 since:
- Your package is fully qualified as `github.com/entireio/cli/cmd/entire/cli/buildinfo` so there's no actual import ambiguity
- The stdlib package is `debug/buildinfo`, not just `buildinfo`
