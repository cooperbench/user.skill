## Configuration File Format & Location

**File Locations (Priority Order):**
- Enterprise/Global: `/Library/Application Support/Cursor/hooks.json` (macOS), `/etc/cursor/hooks.json` (Linux/WSL), `C:\\ProgramData\\Cursor\\hooks.json` (Windows)
- Project-level: `<project-root>/.cursor/hooks.json` (runs from project root)
- User-level: `~/.cursor/hooks.json` (runs from `~/.cursor/`)

**Configuration Structure:**
```json
{

  "hooks": {
    "hookName": [
      {
        "command": "string (required)",
        "type": "command|prompt (default: command)",

        "loop_limit": "number | null (optional)",
        "matcher": "string (optional)"
      }

```

**Key Locations Distinction:** "Project hooks run in any trusted workspace and are checked into version control with your project." User hooks apply globally across all projects.

## Session/Conversation ID Handling

The `conversation_id` field represents "Stable ID of the conversation across many turns" and remains consistent throughout a session. The `generation_id` "changes with every user message." These IDs are included in every hook's input payload, enabling session-aware tracking and behavior.

In `sessionStart`, the output's `env` object allows setting "Environment variables to set for this session" that become "Available to all subsequent hook executions."

## Tool Use Hooks Details

**preToolUse:** "Called before any tool execution. This is a generic hook that fires for all tool types (Shell, Read, Write, MCP, Task, etc.)." It enables blocking or modifying tool behavior before execution.

**postToolUse:** Fires "after successful tool execution" and "Useful for auditing and analytics." For MCP tools specifically, `updated_mcp_tool_output` can replace what the model sees.

**postToolUseFailure:** Activated when tools fail, timeout, or face permission denial. It's "Useful for error tracking and recovery logic" without blocking capability.

**Matchers for Tool Filtering:** The `matcher` field enables filtering by "tool type — Shell, Read, Write, Grep, Delete, MCP, Task, etc."

## Version Requirements

The documentation specifies `"version": 1` as the required configuration schema version. No minimum Cursor application version is explicitly stated, but hooks are positioned as a current feature. The `cursor_version` field provided to hooks reflects "Cursor application version (e.g. '1.7.2')" format.

**Hook Execution Types:** Two execution models exist—"command-based (default)" and "prompt-based (LLM-evaluated)" with optional `model` field override capability.

   229→func waitForTranscriptFlush(transcriptPath string, hookStartTime time.Time) {
   230→	const (
   231→		maxWait      = 3 * time.Second
   232→		pollInterval = 50 * time.Millisecond
   233→		tailBytes    = 4096
   234→		maxSkew      = 2 * time.Second
   235→	)
   236→
   237→	logCtx := logging.WithComponent(context.Background(), "agent.claudecode")

   241→			logging.Debug(logCtx, "transcript flush sentinel found",
   242→				slog.Duration("wait", time.Since(hookStartTime)),
   243→			)
   244→			return
   245→		}
   246→		time.Sleep(pollInterval)
   247→	}
   248→	logging.Warn(logCtx, "transcript flush sentinel not found within timeout, proceeding",
   249→		slog.Duration("timeout", maxWait),
   250→	)
   251→}

   253→// checkStopSentinel reads the tail of the transcript file and looks for the sentinel.
   254→func checkStopSentinel(path string, tailBytes int64, hookStartTime time.Time, maxSkew time.Duration) bool {
   255→	f, err := os.Open(path) //nolint:gosec // path comes from agent hook input
   256→	if err != nil {
   257→		return false
   258→	}
   259→	defer f.Close()
   260→
   261→	info, err := f.Stat()
   262→	if err != nil {
   263→		return false
   264→	}
   265→	offset := info.Size() - tailBytes
   266→	if offset < 0 {
   267→		offset = 0
   268→	}
   269→	buf := make([]byte, info.Size()-offset)
   270→	if _, err := f.ReadAt(buf, offset); err != nil {
   271→		return false
   272→	}
   273→
   274→	lines := strings.Split(string(buf), "\n")
   275→	for _, line := range lines {
   276→		line = strings.TrimSpace(line)
   277→		if line == "" || !strings.Contains(line, stopHookSentinel) {
   278→			continue
   279→		}
   280→
   281→		var entry struct {
   282→			Timestamp string `json:"timestamp"`
   283→		}
   284→		if json.Unmarshal([]byte(line), &entry) != nil || entry.Timestamp == "" {
   285→			continue
   286→		}
   287→		ts, err := time.Parse(time.RFC3339Nano, entry.Timestamp)
   288→		if err != nil {
   289→			ts, err = time.Parse(time.RFC3339, entry.Timestamp)
   290→			if err != nil {
   291→				continue
   292→			}
   293→		}
   294→		// Validate timestamp is within acceptable range:
   295→		// - Not too far in the past (before hook started minus skew)
   296→		// - Not too far in the future (after hook started plus skew)
   297→		lowerBound := hookStartTime.Add(-maxSkew)
   298→		upperBound := hookStartTime.Add(maxSkew)
   299→		if ts.After(lowerBound) && ts.Before(upperBound) {
   300→			return true
   301→		}
   302→	}
   303→	return false
   304→}

### Data Model Differences Discovered

The dedicated `subagentStart/subagentStop` hooks have a **different data model** than the tool-based approach:

| Field | Tool Hooks (`preToolUse[Task]`) | Dedicated Hooks (`subagentStart`) |
|-------|--------------------------------|----------------------------------|
| Task ID | `tool_use_id` | Not provided |
| Task type | Extract from `tool_input` | `subagent_type` field |
| Task prompt | Extract from `tool_input` | `prompt` field |
| Transcript | Build from `SubagentID` | `agent_transcript_path` |
| Status | Implicit | `status` field ("completed"/"error") |

**Trade-off:** The dedicated hooks are more semantic but don't provide `tool_use_id`, which the current framework uses for pre/post task state correlation. This may need downstream changes in `lifecycle.go` if task state tracking relies on that ID.

CLI subcommand                    Hook name string              HookType enum

```

**`GetSupportedHooks()` appears to be dead code** - it's only called in tests, not production. It was likely used by the legacy `ParseHookInput(HookType, reader)` method, but the new architecture uses `ParseHookEvent(hookName string, reader)` which takes the string directly.
