---

## MarkItDown -- Summary

**Repository:** https://github.com/microsoft/markitdown  
**Purpose:** Converts a wide variety of file formats into Markdown text, primarily for use in LLM pipelines and text analysis.  
**Requires:** Python 3.10+

---

### Supported File Formats

| Category | Formats |
|----------|---------|
| Documents | PDF, DOCX, PPTX, XLSX, XLS |
| Web & Data | HTML, CSV, JSON, XML, YouTube URLs |
| Media | Images (EXIF + OCR), Audio (metadata + speech transcription) |
| eBooks | EPub |
| Archives | ZIP (iterates over contents) |
| Email | Outlook messages (optional dependency) |

---

### Installation

```bash
# Full install with all optional dependencies
pip install 'markitdown[all]'

# Selective install (only what you need)
pip install 'markitdown[pdf, docx, pptx]'
```

Available optional dependency groups: `all`, `pptx`, `docx`, `xlsx`, `xls`, `pdf`, `outlook`, `az-doc-intel`, `audio-transcription`, `youtube-transcription`.

---

### CLI Usage

```bash
# Basic conversion (stdout)
markitdown path-to-file.pdf

# Output to file
markitdown path-to-file.pdf -o document.md

# Pipe from stdin
cat path-to-file.pdf | markitdown

# Azure Document Intelligence mode
markitdown path-to-file.pdf -o document.md -d -e "<endpoint>"
```

**Key flags:**

| Flag | Purpose |
|------|---------|
| `-o` | Output file path |
| `-d` | Enable Azure Document Intelligence |
| `-e "<endpoint>"` | Azure Document Intelligence endpoint URL |
| `--list-plugins` | Show installed plugins |
| `--use-plugins` | Enable third-party plugins |

---

### Python API

```python
from markitdown import MarkItDown

# Basic usage
md = MarkItDown()
result = md.convert("test.xlsx")
print(result.text_content)

# With LLM-powered image descriptions
from openai import OpenAI
client = OpenAI()
md = MarkItDown(llm_client=client, llm_model="gpt-4o")
result = md.convert("photo.jpg")
print(result.text_content)

# With Azure Document Intelligence
md = MarkItDown(docintel_endpoint="<endpoint>")
result = md.convert("complex.pdf")
```

**Constructor parameters:**
- `enable_plugins` -- Boolean to activate third-party plugins (default: `False`)
- `llm_client` -- An OpenAI-compatible client for image descriptions
- `llm_model` -- Model identifier (e.g., `"gpt-4o"`)
- `llm_prompt` -- Custom prompt for image description generation
- `docintel_endpoint` -- Azure Document Intelligence endpoint URL

---

### Special Features

1. **LLM Image Descriptions** -- Pass an OpenAI client to get AI-generated descriptions of images and PowerPoint slide visuals.

2. **Azure Document Intelligence** -- Advanced PDF/document conversion using Microsoft's AI service for higher fidelity output.

3. **Plugin System** -- Third-party plugins can extend format support. Disabled by default for security; enable with `--use-plugins` or `enable_plugins=True`. Plugins are discoverable via the `#markitdown-plugin` GitHub topic.

4. **MCP Server** -- A separate `markitdown-mcp` package provides Model Context Protocol integration, usable with Claude Desktop and other MCP clients.

5. **Docker Support** -- Can be built and run as a container:
   ```bash
   docker build -t markitdown:latest .
   docker run --rm -i markitdown:latest < file.pdf > output.md
   ```

## Analysis: `hikagami0210/speakerdeck_to_markdown_mcp`

### What It Does

This is an MCP (Model Context Protocol) server that converts SpeakerDeck presentations into Markdown documents. The pipeline works as follows:

1. **Scraping** (`src/scraper.js`): Uses Puppeteer (headless Chrome) to navigate to a SpeakerDeck URL, extract the presentation ID from slide image `src` attributes matching `presentations/[hex-id]/slide_N.jpg`, determine the total slide count, and download every slide as a JPEG buffer.

2. **OCR** (`src/image-processor.js`): Each downloaded image is preprocessed with Sharp (resize to 2560x1440, grayscale, normalize, sharpen, brightness/contrast adjust, threshold at 180, blur 0.3, sharpen again) and then fed to Tesseract.js for `jpn+eng` OCR with a restricted character whitelist (Japanese hiragana/katakana, Latin alphanumerics, and punctuation).

3. **Markdown generation** (`src/markdown-generator.js`): Builds a Markdown document with a header (title extracted from URL slug, source URL, generation date in Japanese locale), an overview section (summaries from the first 5 non-empty slides), and detailed per-slide sections with summaries and raw OCR text in code blocks.

### Scraping Approach (Detailed)

The scraper's strategy has multiple layers:

- **Primary**: Navigate to the SpeakerDeck URL, then `page.evaluate()` queries the DOM for `img[src*="files.speakerdeck.com"]` elements. It regex-matches `presentations/([a-f0-9]+)/slide_(\d+)\.jpg` to extract the presentation ID and the highest detected slide number.

- **ID fallback**: If no images are found in the DOM, it searches all `<script>` tag contents for the `presentations/([a-f0-9]+)` pattern.

- **Slide count detection**: Tries `<meta>` tag content and `document.body.textContent` for patterns like `N slides`. If nothing works, it enters a **dynamic probe loop** -- it navigates Puppeteer to `slide_0.jpg`, `slide_1.jpg`, ... up to 100, checking HTTP status 200 to find where slides end. This is notably slow (up to 100 sequential HTTP requests with 5s timeout each).

- **DOM fallback**: If no presentation ID is found at all, it collects all `<img>` elements whose `src` contains `files.speakerdeck.com`, `speakerdeckcdn`, or `slidesharecdn`.

- **Download**: Each slide URL is fetched by navigating the Puppeteer page to the image URL and calling `response.buffer()`. Failures on individual slides are logged but don't halt the pipeline.

### Potential Issues and Concerns

1. **Debug mode hardcoded ON**: `ImageProcessor` has `this.debugMode = true` hardcoded. Every run creates `~/speakerdeck_debug_images/` and writes original + processed PNGs for every slide. This is a **disk space leak** -- there is no cleanup mechanism. For a 50-slide deck, that is 100 PNG files dumped into your home directory per invocation.

2. **Destructive image preprocessing**: The Sharp pipeline applies aggressive thresholding (`threshold(180)`) which binarizes the image. This destroys gradient text, colored text on colored backgrounds, and chart/diagram details. The OCR quality on real-world slides (which often have images, gradients, and non-trivial layouts) will be poor.

3. **Puppeteer as image downloader is inefficient**: The scraper uses `page.goto()` to download each slide image, navigating the entire browser to each image URL sequentially. A simple `fetch()` or `https.get()` would be far faster and more resource-efficient.

4. **Dynamic slide count detection is extremely slow**: When the slide count cannot be determined from the page (which may be common given SpeakerDeck's evolving DOM), it probes up to 100 URLs sequentially with 5-second timeouts each. Worst case: 500 seconds (8+ minutes) of waiting.

5. **No input validation/sanitization**: The `url` parameter is passed directly to `page.goto()` with no validation. A malicious or malformed URL could cause unexpected behavior. There is no check that the URL actually points to `speakerdeck.com`.

6. **Arbitrary file write via `output_file`**: The `output_file` parameter is passed directly to `writeFile()` with no path validation or sandboxing. An MCP client could write to any path the process has access to (e.g., `../../.bashrc`).

9. **Fragile scraping**: The scraper relies on SpeakerDeck's current DOM structure and URL patterns (`files.speakerdeck.com/presentations/[id]/slide_N.jpg`). Any change to SpeakerDeck's frontend will break this tool with no fallback.

10. **Tesseract.js character whitelist is incomplete**: The whitelist includes hiragana, katakana, and basic Latin, but omits all kanji. Since Japanese presentations heavily use kanji, the OCR will fail to recognize most Japanese text. This is a critical functional bug.

    }

        } else {
          content += `**検出テキスト:** なし\n\n`;
        }

        return content;
      })
      .join("---\n\n");
  }

    try {
      const urlObj = new URL(url);
      const pathSegments = urlObj.pathname.split("/").filter(Boolean);

      if (pathSegments.length >= 2) {
        const titleSlug = pathSegments[pathSegments.length - 1];
        return titleSlug
          .split("-")
          .map((word) => word.charAt(0).toUpperCase() + word.slice(1))
          .join(" ");
      }
    } catch (error) {
      console.error("URL解析エラー:", error);
    }

    return "SpeakerDeck プレゼンテーション";
  }
}

---

## 1. How `bun build --compile` Works

`bun build --compile` produces a **standalone single-file executable** by bundling the Bun runtime itself together with your application code. The resulting binary can run on machines that do not have Bun (or Node) installed. **Cross-compilation** is supported via the `--target` flag (e.g., `--target=bun-linux-x64`), so you can build Linux binaries from macOS, etc.

## 2. Dependency Handling

- **Static imports are fully bundled.** Normal `import` / `require` statements get resolved at build time and embedded into the binary. No `node_modules` directory is needed at runtime.
- **Dynamic imports with variable specifiers do NOT work.** If your code does something like `import(variableName)` where the module path is determined at runtime, those modules will **not** be included in the binary.
- **Workaround:** The article describes how Secretlint had to build a custom resolver (`@secretlint/resolver`) that intercepts dynamic imports and rewrites them as static imports before compilation, so they can be picked up by the bundler. Packages must be explicitly/statically imported to be included.

## 3. Gotchas and Limitations

- **Dynamic plugin/rule loading breaks.** Tools that rely on dynamic package loading at runtime (like ESLint, textlint, or Secretlint's original architecture) require **significant rework** to produce a single-file binary. The set of bundled modules is fixed at build time.
- **Bun's Plugin API (`onResolve` hook) was unreliable** for this use case -- the author could not depend on it as a general solution.
- **Adding new rules/plugins post-compilation is not possible** without rebuilding, since everything is baked in at compile time.
- **Best suited for applications with a predetermined, static dependency set.** If your tool's value proposition is dynamic extensibility, the single-binary approach requires architectural compromise.
