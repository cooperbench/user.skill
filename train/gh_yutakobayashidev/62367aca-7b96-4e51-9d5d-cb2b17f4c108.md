## repiq Codebase Exploration Report

### 1. **What is repiq?**

**repiq** is a fast, non-reasoning CLI tool for fetching objective metrics about OSS repositories and packages. Built for AI agents (Claude Code, Cursor, Copilot) that need quick access to structured library/repository data for informed selection decisions.

**Key Philosophy:**
- **No judgments**: Returns only raw data, no recommendations or scoring
- **Agent-first**: JSON/NDJSON output, fixed schema, deterministic
- **Speed optimized**: Targets <3 seconds per request (vibe coding friendly)
- **Role separation**: repiq handles data fetching → AI handles reasoning → humans make decisions

---

### 2. **Current Architecture & Patterns**

**Layered Design (4 tiers):**
```
cmd/repiq/main.go                    # Entry point
  ↓
internal/cli/cli.go                  # Flag parsing, orchestration
  ↓
internal/provider/*                  # Provider interface + implementations
  ├── provider.go                     # Provider interface + Result types
  ├── registry.go                     # Scheme-to-provider mapping
  ├── target.go                       # Scheme:identifier parser
  ├── github/github.go               # GitHub API provider
  └── npm/npm.go                      # npm registry provider
  ↓
internal/{auth,format}/              # Support utilities
  ├── auth/auth.go                   # Token resolution (gh → GITHUB_TOKEN)
  └── format/format.go               # JSON/NDJSON/Markdown formatters
```

**Provider Pattern:**
```go
type Provider interface {
    Scheme() string
    Fetch(ctx context.Context, identifier string) (Result, error)
}
```

Each provider:
- Returns a `Result` struct with both metrics and errors (no Go errors)
- Validates identifiers before API calls
- Runs parallel fetch jobs via goroutines + sync.WaitGroup
- Supports partial failures (partial metrics + error messages)
- Uses httptest-compatible base URLs for testing

**Key Design Principles:**
- Parallel fetching within and across providers
- Registry-based provider lookup (extensible without modifying core)
- 30-second HTTP timeout per client
- Error collection rather than short-circuit failure
- Markdown tables grouped by scheme when mixed

type CachingProvider struct {
	underlying provider.Provider
	cache      Cache // interface with Get/Set
	noCache    bool

func (cp *CachingProvider) Scheme() string {
	return cp.underlying.Scheme()
}

func (cp *CachingProvider) Fetch(ctx context.Context, identifier string) (provider.Result, error) {

> DEVELOPER

LRU evictionってなに？

> AGENT

**LRU (Least Recently Used) eviction** は、キャッシュが容量上限に達したとき、**最も長い間使われていないエントリから順に削除する**方式です。

例: 上限 100 エントリのキャッシュで 101 個目を書き込むとき、最後にアクセスされた時刻が最も古いエントリを削除して空きを作る。

repiq では Out of Scope にしています。理由:

- 1 エントリ数 KB 程度で、実用上ディスクを圧迫しない
- TTL 24h で自然に古いエントリは無効になる
- 必要なら `rm -rf ~/.cache/repiq` で十分

## 概要

repiq のプロバイダーレスポンスをディスクにキャッシュし、API レート制限の消費を抑えつつ、繰り返しクエリのレスポンスタイムを大幅に短縮する。

## 背景・目的

AI エージェントの比較ワークフローで同一ターゲットへの重複クエリが頻発し、レート制限の浪費と不要なレイテンシが発生している。MVP 完了後・P3 (registries) の前にキャッシュレイヤーを入れることで、今後追加されるプロバイダーも自動的にキャッシュの恩恵を受けられる。

- **仮説 1**: キャッシュヒット時のレスポンスタイムが 3 秒未満 → 100ms 未満に短縮
- **仮説 2**: 典型的ワークフローで API コール数 60-70% 削減
