### 6. 参照メカニズムのポイント

- **`callPackage` の使用**: `prev.callPackage ./nix/packages/<name>.nix { }` で、各パッケージは自動的に引数を解決
- **overlay の単一定義**: すべてのパッケージが1つのoverlayで統一的に管理
- **外部パッケージとの混在**: llm-agents, ghostty などの外部フレーク入力と同じメカニズムで統合
- **moonbit-overlay の併用**: 複数のoverlayをリストで並べることで簡単に合成可能

## ryoppippi/dotfiles の overlays パターン

**ディレクトリ構造:**
- `nix/overlays/` に個別の `.nix` ファイル（`ai-tools.nix`, `claude-code.nix` など）
- `nix/overlays/default.nix` で全オーバーレイを `builtins.foldl'` で集約

**各オーバーレイファイルの形式:**
- `final: prev:` を引数に取る overlay 関数として定義
- `final.stdenv.mkDerivation` や `final.buildGoModule` などを使用

**flake.nix での統合:**
- `mkPkgs` 関数内で overlays リストに `nix/overlays/default.nix` を追加
- 外部 flake の overlay も同じリストで適用

## 現在の dotnix との違い

| | dotnix (現在) | ryoppippi/dotfiles |
|---|---|---|
| ディレクトリ | `nix/packages/` | `nix/overlays/` |
| ファイル形式 | `callPackage` 用の通常の derivation | `final: prev:` の overlay 関数 |
| 統合方法 | `flake.nix` 内で1つの `overlay` に全て列挙 | `default.nix` で自動集約 |

**1. `nix/packages/` → `nix/overlays/` にリネーム・変換**

各パッケージファイルを `callPackage` 形式から `final: prev:` の overlay 関数形式に変換しました。

```nix
# Before (callPackage形式)

# After (overlay関数形式)
```

新しいパッケージを追加する場合は、`nix/overlays/` に `final: prev: { パッケージ名 = ...; }` 形式のファイルを作成し、`nix/overlays/default.nix` の `overlayFiles` リストに追加するだけで済みます。

良い質問です。実質的な違いを説明します。

## callPackage 形式（旧）

```nix
# nix/packages/polycat.nix - 依存関係を引数で受け取る
{ lib, stdenv, fetchFromGitHub }:
stdenv.mkDerivation { ... }

# flake.nix - callPackage が引数名を見て自動で依存を注入する
overlay = final: prev: {
  polycat = prev.callPackage ./nix/packages/polycat.nix { };
};
```

`callPackage` は関数の引数名（`lib`, `stdenv` 等）を見て、`pkgs` から同名の属性を自動的に渡す仕組みです。

## overlay 関数形式（新）

```nix
# nix/overlays/polycat.nix - final/prev から直接アクセスする
final: prev: {
  polycat = final.stdenv.mkDerivation { ... };
}
```

依存関係を `final.stdenv`、`final.fetchFromGitHub` のように直接参照します。

## 実際の違い

| | callPackage | overlay 関数 |
|---|---|---|
| 依存解決 | 引数名から自動注入 | `final.*` で明示的に参照 |
| ファイル単体の意味 | ただの関数（callPackageが必要） | それ自体が完全な overlay |
| flake.nix での統合 | 1行ずつ `prev.callPackage` を書く | `default.nix` で自動集約 |

正直に言うと、**機能的にはほぼ同じ**です。最終的に overlay として pkgs に注入される点は変わりません。違いは主に：

- **`callPackage`** は nixpkgs の慣習的なパターンで、依存の自動解決が便利
- **overlay 関数** は `final`/`prev` を直接使うので、`flake.nix` 側のボイラープレート（`callPackage` の羅列）が `default.nix` の自動集約で不要になる

ryoppippi パターンのメリットは、新しいパッケージ追加時に **overlay ファイルを作って `default.nix` のリストに1行足すだけ** で済み、`flake.nix` を触らなくてよくなる点です。
