## Discussion #374: Browserless container crashes with permission issue **Problem:** The `browserless/chrome` container runs Chrome as uid 999 (the `chrome` user baked into the image). When Moltis creates the host profile directory with `std::fs::create_dir_all()`, it's owned by the user running Moltis (e.g., uid 1000 or root). The bind mount preserves host ownership, so Chrome inside the container can't write to `/data/browser-profile` — crash. **Root cause in code:** 1. `crates/browser/src/pool.rs:381-389` — creates the host directory with default permissions (owned by current user) 2. `crates/browser/src/container.rs:452-460` — mounts it into the container with `:rw`, but no `--user` flag is passed to match container's expected uid **Fix approach — two complementary changes:** ### 1. Set directory permissions to be world-writable (simplest, most portable) After `create_dir_all()` in `pool.rs`, explicitly `chmod 0o777` the profile directory so any uid inside the container can write to it. This is safe because: - It's a Moltis-managed data directory, not system-wide - It only contains Chrome profile data (cache, cookies) - It's under `~/.moltis/browser/profile/` ### 2. Alternatively: pass `--user` to match host uid (Docker/Podman only) Add `--user $(id -u):$(id -g)` to the `docker run` args so the container process runs as the same uid that owns the directory. However, this can conflict with the browserless image's expectations (it expects to run as uid 999 with specific Chrome sandbox setup). **Recommendation:** Option 1 is the right fix — `chmod` the directory after creation. It's cross-platform (works for Docker, Podman, Apple Container), doesn't fight the container image's user setup, and matches what the `setfacl` workaround from the discussion achieves. The changes would be in: - **`crates/browser/src/pool.rs`** — after `create_dir_all`, set permissions to `0o777` - Same treatment for per-session sandbox subdirectories (`pool.rs:676-681`) Want me to implement this?
