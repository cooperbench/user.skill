The probe's only purpose is a **connectivity/credential check** — "can we actually talk to this endpoint and get a response from at least one model?" It returns a simple `{ "valid": true, "models": [...] }` or `{ "valid": false, "error": "..." }`. The model list itself comes from the `/models` endpoint (already fetched before probing). The probe doesn't discover anything new — it just confirms the server can actually serve completions, not just list models. So in practice it answers: "is this API key + base URL actually working end-to-end?" The model list is already known; the chat completion request is purely a smoke test. For cloud providers (OpenAI, Anthropic) this makes sense — it validates the API key works. For local servers like LemonadeSDK/Ollama where there's no auth, the `/models` response already proves connectivity, making the chat probe redundant and expensive. The user's complaint is valid — a `GET /models` success should be sufficient for custom OpenAI-compatible providers, or at minimum probe only one model rather than cycling through up to 8.
