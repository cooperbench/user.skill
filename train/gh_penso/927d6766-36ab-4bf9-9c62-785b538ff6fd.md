## Already Working

1. **Session isolation by topic** — `default_channel_session_key` in `crates/gateway/src/channel_events.rs` includes `thread_id` in the key: `telegram:account:chat_id:thread_id`. Each forum topic gets its own session, meaning separate context/memory/history.

2. **Session metadata respects topics** — `get_active_session()` takes the full `(channel_type, account_id, chat_id, thread_id)` tuple, so session overrides (model, agent) can be set per-topic.

3. **Explicit topic addressing** — `send_message` tool supports `chat_id:thread_id` format via `parse_chat_target()` in `crates/telegram/src/topic.rs`. Agents can send to specific topics.

4. **Cron delivery to topics** — Cron jobs support the same `chat_id:thread_id` composite address in the `to` field.

5. **Reply routing** — `ChannelReplyTarget` carries `thread_id` and has `outbound_to()` which constructs the composite address.

## Potential Bug Found

`ChannelReplyTargetKey` in `crates/chat/src/lib.rs` does **not** include `thread_id`:

```rust
struct ChannelReplyTargetKey {
    channel_type: ChannelType,
    account_id: String,
    chat_id: String,
    message_id: Option<String>,
}
```

This means streaming target deduplication treats all topics in the same supergroup as equivalent — it could incorrectly skip streaming updates for topic-specific replies. Also, several outbound calls in `deliver_channel_replies_to_targets` use `&target.chat_id` directly instead of `&target.outbound_to()`, which would lose the topic routing.

## TL;DR

The feature described in the discussion **is already possible** — forum topics are isolated sessions with their own context. The main gap is the `ChannelReplyTargetKey` missing `thread_id` and some outbound calls not using `outbound_to()`, which could cause streaming/reply issues in multi-topic supergroups. ## Two distinct bugs — both in `crates/chat/src/lib.rs`

### Bug 1: `ChannelReplyTargetKey` missing `thread_id` (line 5155)

```rust
struct ChannelReplyTargetKey {
    channel_type: ChannelType,
    account_id: String,
    chat_id: String,
    message_id: Option<String>,
    // ← thread_id is missing
}
```

This key is used as a `HashSet` element in the `completed` set of `ChannelStreamDispatcher` (line 5187). When a stream worker finishes successfully, it inserts its key into `completed`. Later, `deliver_channel_replies_to_targets` checks `streamed_target_keys.contains(...)` (line 7721) to decide whether to skip text delivery (because it was already streamed via edit-in-place).

**Impact**: If two forum topics in the same supergroup are being replied to concurrently:
- Topic A's stream completes → inserts `ChannelReplyTargetKey { chat_id: "-100999", ... }`
- Topic B checks `completed` → finds the key matches (same `chat_id`, no `thread_id` to distinguish) → **incorrectly thinks text was already streamed** → skips text delivery, only sends voice/logbook
- **Result**: Topic B gets a silent reply — the text response is swallowed

**Fix**: Add `thread_id: Option<String>` to `ChannelReplyTargetKey` and include it in the `From` impl.

### Bug 2: All outbound calls use `target.chat_id` instead of `target.outbound_to()`

Every single `send_text`, `send_html`, `send_media`, `send_text_silent`, `send_text_with_suffix`, and `send_stream` call in `lib.rs` passes `&target.chat_id` as the `to` parameter.
