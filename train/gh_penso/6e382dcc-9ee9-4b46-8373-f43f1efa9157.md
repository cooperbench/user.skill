I’ve really been enjoying contributing to Moltis over the last few days. I've been making some local changes to streamline my own workflow and have found the project incredibly useful. In fact I do my Moltis contributions in Moltis :+1: 

As I've spent more time in the codebase, I’ve encountered some friction with the size of a few core files—specifically chat/src/lib.rs and gateway/src/server.rs. These "God Objects" handle many mixed concerns, which makes parsing the logic and onboarding new contributors a bit more challenging than it needs to be.

To help with long-term maintainability, I’m planning to spend today on my fork refactoring these crates into smaller, decomposed modules. My goal is to follow idiomatic Rust patterns (as outlined in the [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) and [The Rust Book, Ch. 7](https://doc.rust-lang.org/book/ch07-00-managing-growing-projects-with-packages-crates-and-modules.html)) to separate concerns and simplify the logic.

I plan on following your contribution and security guides closely but wanted to reach out and see if you had any specific preferences or architectural constraints I should keep in mind before I get too far along. I have attached an audit that I am using to guide my refactor work.
 
I'm happy to share the progress on my fork once it's in a reviewable state! 

[moltis-rust-canvas.md](https://github.com/user-attachments/files/26659962/moltis-rust-canvas.md)
