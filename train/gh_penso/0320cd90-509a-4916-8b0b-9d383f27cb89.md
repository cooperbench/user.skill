Here's a summary of the investigation and fix for **GitHub issue #684**: ## Root Cause When `save_config_to_path()` saves the config, it: 1. Serializes with `toml::to_string_pretty(config)` → produces TOML with struct field order 2. Merges the serialized values into the existing document via `merge_toml_preserving_comments()` The merge function (`merge_toml_tables`) correctly preserves existing section order for keys that exist in both documents. However, when **new sub-tables** are inserted (e.g., `[channels.telegram]`, `[voice.tts.elevenlabs]`), the old code did `current.insert(key, updated_item.clone())`. The problem: `clone()` copies the `doc_position` metadata from the **serialized** document. `toml_edit` uses these positions for rendering, which are meaningless in the context of the **current** document. This caused new sub-tables to be scattered/interleaved among unrelated sections instead of appearing after their parent section. ## Fix Instead of `updated_item.clone()`, use `clone_item_without_positions(updated_item)` which deep-clones the item but creates fresh `Table` objects with `doc_position = None`. When position is `None`, `toml_edit` auto-positions the table — placing it correctly after its parent section. ## Changes - `crates/config/src/loader.rs`: - Modified `merge_toml_tables` to strip positions when inserting new entries - Added `clone_item_without_positions()` and `clone_table_without_positions()` helpers - Added 2 regression tests: full template roundtrip order check + minimal sub-table interleaving check Shall I commit this?
