```rust
fn merge_toml_preserving_comments(path: &Path, updated_toml: &str) -> crate::Result<()> {
    // 1. Read current file
    let current_toml = std::fs::read_to_string(path)?;
    
    // 2. Parse both into toml_edit::DocumentMut (preserves structure/comments)
    let mut current_doc = current_toml.parse::<toml_edit::DocumentMut>()?;
    let updated_doc = updated_toml.parse::<toml_edit::DocumentMut>()?;

    // 3. Recursively merge updated values INTO current document
    merge_toml_tables(current_doc.as_table_mut(), updated_doc.as_table());
    
    // 4. Write back the merged document (preserves original section order)
    std::fs::write(path, current_doc.to_string())?;
}

fn merge_toml_tables(current: &mut toml_edit::Table, updated: &toml_edit::Table) {
    // Remove keys from current that don't exist in updated
    let current_keys: Vec<String> = current.iter().map(|(key, _)| key.to_string()).collect();
    for key in current_keys {
        if !updated.contains_key(&key) {
            let _ = current.remove(&key);
        }
    }

    // Update/insert keys from updated into current (maintains current's order)
    for (key, updated_item) in updated.iter() {
        if let Some(current_item) = current.get_mut(key) {
            merge_toml_items(current_item, updated_item);  // Recursive for nested tables
        } else {
            current.insert(key, updated_item.clone());
        }
    }
}
```

Here's a summary of the investigation and fix for **GitHub issue #684**:

## Root Cause

When `save_config_to_path()` saves the config, it:
1. Serializes with `toml::to_string_pretty(config)` → produces TOML with struct field order
2. Merges the serialized values into the existing document via `merge_toml_preserving_comments()`

The merge function (`merge_toml_tables`) correctly preserves existing section order for keys that exist in both documents. However, when **new sub-tables** are inserted (e.g., `[channels.telegram]`, `[voice.tts.elevenlabs]`), the old code did `current.insert(key, updated_item.clone())`.

The problem: `clone()` copies the `doc_position` metadata from the **serialized** document. `toml_edit` uses these positions for rendering, which are meaningless in the context of the **current** document. This caused new sub-tables to be scattered/interleaved among unrelated sections instead of appearing after their parent section.

## Fix

Instead of `updated_item.clone()`, use `clone_item_without_positions(updated_item)` which deep-clones the item but creates fresh `Table` objects with `doc_position = None`. When position is `None`, `toml_edit` auto-positions the table — placing it correctly after its parent section.

## Changes

- `crates/config/src/loader.rs`:
  - Modified `merge_toml_tables` to strip positions when inserting new entries
  - Added `clone_item_without_positions()` and `clone_table_without_positions()` helpers
  - Added 2 regression tests: full template roundtrip order check + minimal sub-table interleaving check
