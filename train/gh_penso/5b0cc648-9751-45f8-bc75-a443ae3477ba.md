I have enough to answer clearly. Here's what's going on:

## How Moltis currently exposes skills to the model

Short version: **it doesn't read them for the model — it just hands the model a file path and tells it to read the file itself.**

The flow is entirely prompt-based:

1. **Discovery + registry** (`crates/skills/src/discover.rs`, `registry.rs`) find every `SKILL.md` under `<data_dir>/skills/`, plugin dirs, etc., and load just the YAML frontmatter (`name`, `description`).
2. **Prompt injection** (`crates/skills/src/prompt_gen.rs:4` `generate_skills_prompt`) builds an `<available_skills>` XML block into the system prompt that looks like:
   ```
   <skill name="inbox-contacts" source="skill" path="/Users/.../.moltis/skills/inbox-contacts/SKILL.md">
   Email contact tracker - analyzes two-way email relationships...
   </skill>
   ```
   followed by the literal instruction: *"To activate a skill, read its SKILL.md file for full instructions."* (`prompt_gen.rs:33`).
3. That block is appended to the system prompt by `append_skills_section` in `crates/agents/src/prompt.rs:698`.
4. The tool registry wired in `crates/gateway/src/server.rs:3867-3882` only registers `CreateSkillTool`, `UpdateSkillTool`, `DeleteSkillTool`, and (optionally) `WriteSkillFilesTool`. **There is no `ReadSkillTool` and no built-in `read_file` tool.** `moltis_skills::registry::InMemoryRegistry::load_skill` exists in Rust (`registry.rs:68`) but it is never exposed to the model — only the CLI `moltis skills load` path uses it.
5. So the model is told "go read this path" and then left to find *whatever* file-reading tool happens to be wired up.

## Why it's failing in the screenshot

The user has no native Moltis file-read tool, so the model improvises with whatever MCP servers are attached:

- **Attempt 1** — `mcp__filesystem__read_text_file`: errors with "expected number, received string" on `head`/`tail`. That's the NPM `@modelcontextprotocol/server-filesystem` tool. The schema requires numeric `head`/`tail`; the model passed strings. Even if it had gotten the args right, that server is only allowed to read paths inside the roots it was configured with, which usually is not `~/.moltis/skills/...`.
- **Attempt 2** — `mcp__knylehub__read_note`: the model then treats the skill path as a *relative* note key `skills/inbox-contacts/SKILL.md` and asks a personal "knylehub" notes server for it → `File not found`.
- **Fallback** — `memory_search`: now the model gives up on the filesystem entirely and tries to reconstruct the skill from semantic memory. That's the "fugue / makes up stuff from memory" behaviour you're seeing. The prompt told it the skill exists and even supplied the description, so the model hallucinates a plausible body rather than admit defeat.

This is not intended behaviour, it's the direct consequence of: *prompt says "read this file", runtime provides no tool that can read that file.*

## Why the current design exists

It mirrors the Anthropic "Agent Skills" pattern where the harness *has* a built-in file reader (Claude Code has `Read`). Moltis inherited the pattern but never shipped the corresponding `Read` tool, so the contract is broken whenever the user doesn't happen to have a correctly-scoped filesystem MCP server configured.

## How to fix it

There are three tiers of fix, in order of impact:

**1. Add a first-class `read_skill` / `activate_skill` agent tool (right fix).**
Register a new tool in `crates/tools/src/skill_tools.rs` alongside `CreateSkillTool`:

- Takes `{ name: string }` (not a path — names are the stable identifier).
- Looks the skill up via the same `SkillRegistry` the prompt was built from, calls `load_skill` / `load_skill_from_path` (already exists at `registry.rs:109`), and returns the parsed body plus the list of sidecar files.
- Wire it in `crates/gateway/src/server.rs` next to the existing `CreateSkillTool::new(data_dir.clone())` registration.
- Update `prompt_gen.rs:32-34` to say *"To activate a skill, call the `read_skill` tool with its name"* instead of instructing a filesystem read, and drop the absolute path from the XML (name + description is enough — the path is an attractive nuisance that pushes the model toward raw fs access).

This removes the dependency on any MCP filesystem server, makes the behaviour deterministic across users, and means the tool can enforce safety (only return files under `<data_dir>/skills/`, respect enabled/trusted state, size limits, etc.).

**2. Alternatively / additionally: inline the body on first mention.**
For small skills, the server could embed the full SKILL.md body inside the `<skill>` element when the total fits a budget (say, <4KB), falling back to the `read_skill` tool only for large skills with sidecar files. This removes a round trip entirely for the common case. The parse layer already returns both `metadata` and `body` (`types.rs`), so this is cheap — just extend `generate_skills_prompt` with a budget-aware variant.

**3. A quick stopgap if you don't want to ship a tool yet:**
Change the prompt instruction to be explicit about *which* tool to use if a filesystem server is available, and only emit the `<available_skills>` block when such a tool is actually in the registry. Right now the prompt makes an unconditional promise ("read its SKILL.md file") that the runtime can't keep. At minimum, detecting "no file-read tool is registered" and degrading to "skill bodies are unavailable in this session" would stop the memory-fabrication failure mode — the model would refuse or ask, instead of confabulating.

My recommendation: do **(1) + (2)**. The `read_skill` tool is ~150 lines plus tests, it reuses `load_skill_from_path` that's already there, and combined with inlining small bodies it makes skills actually work the same way for every user regardless of which MCP servers they've wired up. It also lets you drop the absolute-path leak in the system prompt, which is a nice side benefit.
