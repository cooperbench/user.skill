Since the frame is exactly terminal-height rows tall, that final newline on the bottom line forces the terminal to scroll the entire screen up one line on every single frame. The next repaint starts with `\x1b[H` (cursor home) and redraws everything one line lower again. At 10+ Hz that's the "line constantly added and removed" / whole-screen blink you saw.

> AGENT

Yes — fixed. Here's what was happening, and your two observations were the exact fingerprint of the bug:

**The DAS auto-repeat had no way to know you released the key.** Raw terminal input only delivers key *presses* — there is no key-up event. The code in `pkg/tui/tui.go` armed a timer on every left/right press: after 167 ms it spawned a background loop that moved the piece every 33 ms, and the only thing that stopped that loop was pressing a *different* key. So:

- **"starts when I press a key"** — every left/right tap armed the timer. 167 ms after your last left/right press, the auto-glide kicked in and slammed the piece into the wall. I reproduced this in tmux: one single Left keypress moved the piece from spawn to the left wall in about a quarter second, and every following piece kept gliding left too.
- **"fixed when I press up"** — Up (rotate) is not left/right, so the handler cancelled the DAS state, which finally let the background loop exit. Any non-direction key would have "fixed" it.

It was actually inverted from the spec's intent: while you *held* the key, the OS's own key autorepeat kept restarting the 167 ms timer, so the internal DAS never fired during a hold — it fired 167 ms *after you let go*, which is precisely when it shouldn't. There was also a goroutine leak: switching from left to right didn't kill the left loop, so the piece could end up being pushed both ways at 30 Hz each, which also fed the screen blinking.

**The fix** (in your working tree, uncommitted, alongside the earlier render scroll fix): removed the internal repeat timer entirely — each key event now moves exactly one cell, and holding a key repeats at your terminal's own autorepeat rate. `go vet`, build, 168 unit + 61 acceptance tests all pass, and I verified in tmux that a single tap now moves one cell with no glide.

One thing for the swarm backlog: the spec'd DAS timing (167 ms / 33 ms in EXPERIENCE.md and the feature file) is **unimplementable** in a plain raw-mode terminal — it requires key-release events, e.g. the kitty keyboard protocol (which Ghostty supports). I left the constants and a comment in `tui.go` explaining this, so `TestQA_MR8_DASConstantsMatchSpec` still passes, but the spec should eventually be revised or the kitty protocol adopted as its own delivery.

## TL;DR

Both bugs lived in the same blind spot: **the terminal boundary, which the process declares exempt from all test tooling, and whose two human-eye gates (ux-engineer live observation, QA "through the UI only") silently degraded into in-process tests against internal APIs.** The process did not fail for lack of rigor — it ran mutation testing, CRAP, DRY, 168 unit + 61 acceptance + property tests. All of that rigor was pointed at the pure modules, and none of it at the seam where the program meets the terminal. Worse: the spec actually predicted the bug, and the code actually admitted it.

## Gate-by-gate

**1. Specifier — did its job, then nobody listened.** `QA-MR-8` says verbatim: *"On release, movement stops immediately."* That is exactly the behavior that was broken. The spec also contains an unimplementable NFR — DAS 167/33 requires key-release events, which raw-mode terminals don't deliver — and no later role was obligated to challenge feasibility.

**2. Implementation — the conflict was known and shipped anyway.** The shipped code contained this comment: *"Key-up is not available in raw terminal reads; we detect release implicitly: any key other than the held direction cancels DAS."* That's the bug, described by its author. The coder rule "if UX Intent and Gherkin conflict, stop and report" exists, but there's no analogous rule for "spec conflicts with platform reality" — so the implementer invented a silent workaround instead of escalating. Also notable: DAS was implemented by the **ux-engineer** (per the PR commits), the same role that then verified it — the verifier verified its own work.

**3. Architecture rules pushed logic into the dark zone.** Engineering rules 15–16: only testable modules participate in *any* test tooling. `Run()` is boundary, so the DAS machinery — which is **pure timing logic**, a state machine over key events and a clock — was written inline in the one file no tool ever touches. It should have been an extracted, testable module with the boundary only feeding it events. Nobody owns the question "is this code that landed in the boundary actually boundary code?" The blink is the dual case: `Frame.String()` *is* in a testable module and *has* tests — but they assert `PlainRows()` (ANSI-stripped), so the only thing `String()` adds — escape sequences and newline placement — was asserted by nothing. Mutation testing passed because the tests couldn't see the mutation surface that mattered.

**4. QA — the procedure was degraded with no fidelity check.** The QA prompt requires running the suite "through the user interface only; do not use an API into the project." What actually exists: `qa_movement_rotation_test.go` calls `mrSession()` / `handleKey()` / `Render()` — internal APIs. And the conversion of QA-MR-8/9 turned a five-bullet timing procedure into `assert dasDelay == 167ms`. A behavior check became a constants check, while keeping the name `TestQA_MR8`, so the gap is invisible in any report. Nothing in the process forces the executable script to preserve the procedure's "Expected" bullets, or to declare "this step is not automatable" and escalate.

**5. Nobody ever ran the program.** The ux-engineer is the only role told to "run the binary and observe the live experience." The blink shipped in delivery #1 and survived **three deliveries** — it's visible within one second of launch. So that step was either skipped or performed in a way that cannot observe (a single frame capture can't show jitter; no keypress can be "held"). There's no enforcement: no PTY harness, no required evidence artifact at handoff.

## What's missing from the process

1. **A PTY/tmux end-to-end harness as a first-class tool**, alongside crap4go/mutate4go: spawn the real binary in a pseudo-terminal, send raw byte sequences, capture screens over time, assert. Everything I used to find both bugs today was ~10 lines of tmux shell (`capture-pane` diffs caught the blink via scrollback growth; one `ESC[D` byte caught the runaway). Without this tool, QA's "UI only" rule is unenforceable and *will* collapse into in-process tests again.
2. **A fidelity rule for QA conversion**: each executable `QA-MR-N` test must assert every "Expected" bullet of its procedure, or QA must explicitly mark it `NOT AUTOMATED — <reason>` and route it back. Asserting constants may never substitute for asserting behavior.
3. **A platform-feasibility stop-rule** at spec or implementation time: any NFR depending on a platform capability (key-release, sub-frame timing) must name its mechanism; if the platform can't deliver, stop and report — the same escalation that already exists for UX-vs-Gherkin conflicts. A workaround comment in code is the tell that this rule fired and was suppressed.
4. **A boundary-minimization audit** (architect or cleaner): boundary files may contain only thin IO adaptation. Timers, tickers, state machines, serialization policy found in a boundary file get extracted into testable modules. And "testable but only tested stripped" counts as untested — `Frame.String()` needed byte-level assertions.

## The one-sentence diagnosis

SwarmForge verifies **artifacts about the system** (tests, mutation scores, CRAP, specs) but has no gate that verifies **the running system through its real interface**. Every escaped bug followed from that single gap — and it's surface-agnostic: the same hole exists for web (no browser ever loads the page), APIs (no request ever hits a running service), or platform services (no event ever flows through the deployed topology).

## The principle to add

> **Every project must have an Observation Harness: a tool that drives the real, running system through the same interface its users use, and captures observable state for assertion.**

PTY/tmux for a TUI, Playwright for web, HTTP client against a live instance for an API, event injection for a platform service. This is the keystone — three of the five process gaps below are only enforceable once it exists. Today the rules that *assume* it ("run the binary and observe", "QA through the UI only, no project API") silently collapse into in-process tests because there's nothing to run them on.

## The fidelity ladder

Four tiers, decided per dependency by asking questions in order:

**Tier 0 — The system itself.** *Does it ship in this PR?* → Run real, exactly as it ships (real binary, real container, real process). Never substituted, never shortcut. This is what the harness observes.

**Tier 1 — Owned infrastructure.** *Can the production engine run locally?* → Run the real engine in a container. Postgres in Docker **is** Postgres; same for Redis, Kafka, RabbitMQ. These are not emulators — they're the real dependency, locally provisioned. No justification needed beyond version pinning.

**Tier 2 — Platform services with official twins.** *Is there a vendor or de-facto-standard emulator?* → Use it (LocalStack/AWS emulators, Firebase emulator, fake-gcs-server…). Only for things that *cannot* run real locally. Each use must declare its known fidelity gaps (e.g., "LocalStack doesn't enforce IAM") — those gaps are precisely where bugs can still escape, so they must be written down, not discovered later.

**Tier 3 — External domain.** Everything you don't own the lifecycle of: third-party APIs (Stripe, email), *and other teams' services inside the platform*. → Wire-level stub (WireMock-class) backed by a recorded or agreed contract. Never called real in the verification loop — you can't control their state, their side effects, or their availability, so "real" here makes verification flaky rather than more honest. Note the deliberate choice: **in-platform but other-domain counts as external** for the swarm's gates, because the swarm can't reset or version their state. Cross-domain truth is a platform-CI/contract-testing concern (consumer-driven contracts can ride on the same stubs), not a swarm role's gate.

## The two invariants that make this generalize

**1. The seam is always the wire, never the code.** Whatever gets substituted, the system under test must reach it over the same protocol it uses in production — TCP, HTTP, SQL, terminal bytes. In-process fakes are unit-test machinery and stay in the unit loop. This is the direct generalization of the tetris lesson: QA called `handleKey()` in-process instead of sending `ESC[D` to a PTY, and that in-process seam is exactly what blinded every gate. The same failure on web is driving React components instead of a browser; on a service, calling handlers instead of sending requests.

**2. Environment inputs are inputs.** Clock, OS input timing, randomness — the things you can't containerize — must be injectable *through the same wire* (the tetris harness sends bytes at controlled intervals; a service harness controls event timing at ingress). The DAS bug lived entirely in this category: OS key-repeat timing was an environment input nobody could synthesize, so nobody did.

- It's a set of **hand-implemented stateful re-implementations** of each API: a TypeScript HTTP server per service, built on a shared `@emulators/core` providing a generic `Store` with typed `Collection<T>` (CRUD, indexing, filtering, pagination). Persistence adapters: in-memory, file, or KV.
- It implements **real protocols**, not just shapes: full OAuth2/OIDC authorization-code flows with RS256 ID tokens, PKCE, JWKS discovery; AWS XML responses and SigV4-style endpoints; Slack cursor pagination; GitHub App JWT auth + installation tokens; **real outbound HTTP webhook delivery** to registered URLs.
- **Stateful and relational**: *"Create a GitHub repo, push commits, open a PR. … State persists across requests."* Mutations cascade to related entities.
- Seeding via YAML/JSON config (`emulate.config.yaml`) defining users, tokens, orgs, repos, OAuth apps, etc.

## 3. How emulations are created and kept faithful

This is the weakest documented area:

- Emulations are **manually authored** by maintainers (monorepo packages under `packages/@emulators/*`). There is no codegen-from-OpenAPI pipeline and no documented process for contributing new services.
- Fidelity verification is via **SDK conformance tests**: the v0.6.0 changelog cites "SDK conformance tests" for Slack, and I confirmed the Slack package has the official `@slack/web-api` SDK as a devDependency used in its vitest suite — i.e., the real official client is run against the emulator. That validates client-compatibility, not full behavioral equivalence.
- **No drift handling**: no automated comparison against the live API, no contract-diffing, no recorded-traffic replay, no versioned fidelity manifests. Fidelity gaps are documented as prose "not implemented" lists per service (e.g., Slack: Connect, Enterprise Grid, SCIM, Socket Mode, slash commands/interactions, workflows; AWS: no real rate-limiting or paid-plan behavior).
