- **acceptance/runtime/mod.rs `World`**: add `#[allow(dead_code)]` on the struct (not per-field) — runtime is `include!`-ed across multiple test binaries with differing step coverage. explainin general all the dead_code, what is that and why do we need it?

> AGENT

The `#[allow(dead_code)]` attribute tells the Rust compiler "don't warn me that this item is unused." Rust's dead-code lint fires when a field, function, or struct is defined but never referenced in the current compilation unit. The reason it's needed here is specific to how the APS acceptance tests are structured. The `runtime/mod.rs` file containing `World` is not compiled once — it's `include!`-ed into multiple separate test binaries (one per feature). Each binary only uses the step handlers for its own feature, so fields on `World` that exist for *other* features' steps appear unused from any single binary's perspective. The compiler sees each binary in isolation and warns on anything not referenced in that binary. Putting `#[allow(dead_code)]` on the struct suppresses that across all fields at once, rather than annotating each field individually as the set of "which binary uses which field" shifts over time. So the note isn't about dead code in the general sense — it's about the compiler's limited view when the same source file is compiled into multiple independent binaries. The code isn't actually dead; the lint just can't see across binary boundaries. Whether the note belongs in AGENTS.md at all is debatable — it's really a Rust/APS architectural fact that a reader could infer once they understand the `include!` pattern. Want me to drop it or move it to a reference file?

> DEVELOPER

Is this expeced? why many executabes?

> AGENT

Yes, it's expected — it's how the APS (Acceptance Pipeline Specification) works. Each `.feature` file gets its own test binary. The reason is isolation: each binary links only the step handlers it needs, so a step definition change in one feature can't accidentally affect another feature's tests. It also means features can run in parallel without shared state. The `World` struct holds the test context (things like captured stdout, exit codes, temp dirs). It lives in `runtime/mod.rs` and gets `include!`-ed into every binary. But each binary only exercises the steps for its own feature — so `World` fields added for feature A appear unused when compiling the binary for feature B. In this project specifically there are currently two feature binaries: `duplicate_detection` and `cli_surface`. As more features are added, each gets its own binary, and the `World` dead-code pressure grows. The alternative would be one combined binary with all step handlers linked together — but then you lose isolation and the compile-time "which steps are actually exercised" signal. APS chose the per-binary model deliberately.
