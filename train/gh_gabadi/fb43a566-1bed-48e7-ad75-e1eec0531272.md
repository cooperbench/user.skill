`#[ignore]` in Rust marks a test as **skipped by default** in `cargo test`. To run ignored tests you must explicitly opt in with `--include-ignored`.

The reason it's combined with proptest here: proptest runs **hundreds of randomized iterations** per test (`parse_rust_source_never_panics`, etc.), making the suite slow. By tagging them `#[ignore]`, normal `cargo test` stays fast (unit/integration tests only), while the slow property sweep is opt-in:

```
# normal fast run
cargo test

# explicit property run
cargo test --test parse_rust_source_property_test -- --include-ignored
```

The comment at the top of `tests/parse_rust_source_property_test.rs:2` documents exactly this. The architect's retro item was confirming this separation was the right design — the architect had used it during the session and it worked, so no rule change was needed.

> DEVELOPER

its the proper way? its strange to have ignored tests

> AGENT

It's a legitimate pattern but not the only one, and it has a real downside worth knowing.

**Why it works here:** `cargo test` runs all integration test files by default, so without `#[ignore]`, plain `cargo test` would invoke hundreds of proptest iterations and be slow every time. `#[ignore]` opts them out of the default run while keeping them in the same repo.

**The real problem with `#[ignore]`:** it's easy to forget. If CI just runs `cargo test`, the property tests never execute. They become dead code that nobody runs.

**More explicit alternatives:**

Feature flag — opt-in at compile time, CI can add a separate job:
```toml
# Cargo.toml
[features]
property-tests = []
```
```rust
#[cfg(feature = "property-tests")]
mod property_tests { ... }
```
```
cargo test --features property-tests
```

Environment variable via `ProptestConfig` — always compiles, controls iteration count:
```rust
ProptestConfig::with_cases(
    std::env::var("PROPTEST_CASES").ok()
        .and_then(|v| v.parse().ok())
        .unwrap_or(10)
)
```
Fast locally (10 cases), thorough in CI (1000 cases).

**Verdict:** `#[ignore]` is idiomatic Rust and the standard library uses it too, but it only makes sense if CI explicitly passes `--include-ignored` in a dedicated job. If the pipeline just runs `cargo test`, those tests are silently never running. Worth checking whether CI actually invokes them.

Three honest takes:

**Unit tests — correct and idiomatic.** Inline `#[cfg(test)]` module in `src/lib.rs` is exactly the Rust convention. Nothing to improve.

**Property tests — the `#[ignore]` is fine structurally, but the risk is real.** The pattern is used in the standard library, so it's not wrong. The question is purely operational: does CI run `--include-ignored`? If not, those tests are decorative. A feature flag (`#[cfg(feature = "property-tests")]`) would make the intent explicit and force CI to opt in deliberately rather than accidentally opt out. For a project this small the `#[ignore]` is probably fine, but it's the kind of thing that quietly rots.

**Acceptance tests — the machinery is disproportionate.** Using generated Gherkin step dispatch to test "binary exits 0 with no args" is a lot of indirection. Idiomatic Rust for CLI acceptance testing is just `std::process::Command`:

```rust
let out = Command::new("./target/release/drywall").output().unwrap();
assert!(out.status.success());
```

The Gherkin layer makes sense if the swarm uses feature files as a shared specification language between human and agents — that's a workflow reason, not a code quality reason. But from pure Rust best practices it's overhead that obscures what the test actually does. The generated file's own comment ("DO NOT EDIT") is a sign: when you can't read and modify a test directly, it's harder to debug failures.

**Bottom line:** unit tests are solid. Property tests are fine if CI runs them. Acceptance tests are over-engineered for the code they cover, but probably intentional given the swarm's Gherkin-driven workflow.

Yes it makes sense — tool installs (especially `cargo install` from source) are expensive. The good news: `jdx/mise-action` already caches by default (`cache: true`) keyed on the `.mise.toml` hash. When `.mise.toml` doesn't change, tools are restored from cache instantly on the next run.

So two caches are already in play:

| Cache | Managed by | Key | What it stores |
|-------|-----------|-----|----------------|
| mise tools | `jdx/mise-action` (implicit) | hash of `.mise.toml` | nextest, llvm-cov, crap, mutants binaries in `~/.local/share/mise` |
| Cargo build | `actions/cache` (explicit) | hash of `Cargo.lock` | registry, git deps, `target/` |

No changes needed — the mise-action cache is already active without any explicit configuration. If you want to make it visible/explicit in the yaml you can add `cache: true` to the mise step, but it's redundant.

The only gap worth knowing: if mise falls back to `cargo install` (compiling from source) on first run rather than downloading prebuilt binaries, that first run will be slow. After that it's cached. Whether it compiles or downloads depends on whether `cargo-binstall` is available in the mise-action environment.

> DEVELOPER

one extra question, Why drywall works as a command line vs other tools as cargo? whats the advantage of each option?

> AGENT

The distinction maps to whether the tool needs Cargo's build pipeline or just source files.

**`cargo <subcommand>` (nextest, llvm-cov, crap, mutants):**
- Named `cargo-<name>`, cargo discovers them automatically in PATH
- Get cargo context for free: manifest path, target dir, workspace metadata
- Need it because they interact with the build system:
  - nextest — runs compiled test binaries
  - llvm-cov — instruments compiled code
  - crap — reads coverage data from compiled test runs
  - mutants — modifies source, recompiles, re-runs tests

**Standalone binary (drywall):**
- Just walks source files and parses ASTs via tree-sitter
- No build step needed — analysis is purely on source text
- Language-agnostic in principle: same binary could analyze Go, Rust, Java with different grammars
- Simpler to invoke across projects and languages: `drywall ./src` works anywhere

The rule of thumb: if a tool needs to build or execute code, it belongs in Cargo's world. If it only reads source files, a standalone binary is simpler and more portable.

There's also a practical reason for drywall specifically: it's the project itself, so it can't depend on cargo subcommand infrastructure to analyze its own source — it just builds a release binary and runs it.

> DEVELOPER

CARP only reads code once the coverage runs

> AGENT

Good correction. CRAP at analysis time only reads:
1. Source files — for cyclomatic complexity (static analysis)
2. `lcov.info` — already generated by `cargo llvm-cov`

It doesn't compile or run anything itself. So it's closer to drywall in nature than to nextest or llvm-cov.

The reason it's still a cargo subcommand is likely **workspace discovery** — it uses `Cargo.toml` to know which source files are in scope, which are lib vs test, what the project boundaries are. That's cargo integration for project structure, not for building.

Drywall sidesteps this by taking an explicit path argument (`drywall ./src`) — the caller decides scope. Simpler, but less "cargo-aware."

So the real distinction is more nuanced:

| Need | Approach |
|------|----------|
| Build or run code | cargo subcommand |
| Cargo workspace metadata | cargo subcommand |
| Pure source file analysis, explicit scope | standalone binary |

CRAP falls in the middle — no build, but cargo metadata for scoping.

    Auto-excluded always: `.git/`, `target/`, `node_modules/`, `__pycache__/`, `vendor/`, `dist/`, `.next/`
    
    ### Text output format (mirrors dry4go)
    
    ```
    DUPLICATE score=0.89
      src/billing/invoice.rs:12-25
      src/billing/receipt.rs:30-44  (88 nodes / 91 nodes)
    ```
    
    ### JSON output format (mirrors dry4go)
    
    ```json
    {
      "candidates": [
        {
          "score": 0.89,
          "left":  {"file": "src/billing/invoice.rs", "start_line": 12, "end_line": 25, "nodes": 88},
          "right": {"file": "src/billing/receipt.rs", "start_line": 30, "end_line": 44, "nodes": 91}
        }
      ]
    }
    ```
    
    ### Exit codes
    
    - `0` — no duplicates above threshold found
    - `1` — one or more duplicate pairs reported
    - `2` — error (parse failure, invalid arguments, unreadable path)
    
    ### Implementation order (language targets)
    
    1. **Rust** (`tree-sitter-rust`) — first target; validates algorithm by running drywall on its own source (dogfood). Rust function forms: `fn`, `impl` methods, closures assigned to `let` bindings, trait implementations.
    2. **JS/TS** (`tree-sitter-javascript` + `tree-sitter-typescript`) — second target. Function forms: function declarations, arrow functions, class methods, exported named functions.
    3. **Python** (`tree-sitter-python`) — third target. Function forms: `def`, class `def` methods, `async def`.
    
    ### Distribution
    
    Single static binary via `cargo build --release`. No runtime dependencies. Cross-compilation to Linux/macOS/Windows via `cross` or `cargo-zigbuild`. WASM via `wasm-pack` is deferred.
    
    ### Scaling
    
    Validated on the largest known target repo: ~350 qualifying fragments → ~61,000 candidate pairs → ~6M hash comparisons. Runs in under 1 second in Python equivalent; Rust will be substantially faster. Brute-force O(n²) Jaccard is sufficient — no MinHash or LSH needed.
    
    ## Testing Decisions
    
    A good test for drywall tests observable CLI behavior (stdout, exit code) given fixture input files. It does NOT test internal data structures (hash sets, inverted index, intermediate representations). Fixtures are minimal synthetic source files — small enough to reason about by hand, large enough to pass the qualification gates.
    
    ### What to test
    
    - **Algorithm correctness**: two fixture functions structurally identical modulo identifier/literal names → score = 1.0; two completely different functions → score below threshold; pair not reported when one function is below gate
    - **Qualification gates**: functions below `--min-lines` or `--min-nodes` excluded; CLI flag changes take effect
    - **Threshold flag**: pair with score 0.75 reported at `--threshold 0.70`, not at `--threshold 0.80`
    - **Language auto-detection**: `.rs` → Rust grammar; `.ts` → TypeScript grammar; `.py` → Python grammar
    - **`--lang` override**: file with non-standard extension analyzed correctly when language forced
    - **JSON output**: `--format json` produces valid JSON with correct shape
    - **Exit codes**: `0` when no duplicates, `1` when duplicates found, `2` on bad input
    - **Auto-exclusions**: files inside `node_modules/` or `target/` ignored even when path is explicitly passed
    - **Dogfood test**: `drywall ./src` on drywall's own Rust source exits `0`
    
    ### Testing seams
    
    - **Primary**: CLI integration tests — spawn the compiled binary as a subprocess, pass fixture directories, assert on stdout and exit code. This is the highest viable seam.
    - **Secondary**: Unit tests only for the normalization function (tree-sitter node → normalized string), as this is the most algorithm-sensitive component and the only case where a unit test is more diagnostic than a CLI test.
    
    ## Out of Scope
    
    - WASM / npm distribution (deferred)
    - Sub-function block-level duplicate detection (only whole-function Jaccard; block extraction is a future extension)
    - Cross-language duplicate detection (a Rust function matching a Python function is not in scope)
    - IDE integration or LSP server
    - Historical trending or per-PR delta reporting
    - Configuration file (CLI flags only)
    - Languages beyond Rust, JS/TS, Python
    - Threshold auto-calibration
    - crap4js patches (tracked separately)
    - Python CRAP script (tracked separately)
    
    ## Further Notes
    
    **Reference implementation:** `dry4go` (github.com/unclebob/dry4go) is the behavioral reference. drywall's text and JSON output formats mirror it exactly.
    
    **Threshold calibration:** dry4go's `0.82` threshold was tuned for Go. JS and Python have different idiom distributions. The default may need calibration after first real-world runs on those stacks — this is a known open question, not a blocker.
    
    **Relation to jscpd v5:** jscpd detects copy-paste (token-sequence); drywall detects semantic duplication (same structure, different names). They are complementary. Running both on a JS/TS codebase surfaces both classes of violation.
    
    **Dogfood commitment:** drywall's CI must run `drywall ./src` as a build step. Any self-duplicate above threshold is a build failure. This is both a correctness gate and a design constraint.
    
    **Full background research:** `docs/tool-analysis-crap-dry-mutation.md` in `gabadi/gabadi-swarm-forge` contains the complete analysis covering all three tool families (CRAP, DRY, mutation), all stacks (JS/TS, Python, Rust), full LCOV format spec, and open questions.

From the PRD, drywall solves scoping with **explicit paths + smart auto-exclusions**:

```
drywall [path ...]
```

The caller decides scope. Auto-excluded always: `.git/`, `target/`, `node_modules/`, `__pycache__/`, `vendor/`, `dist/`, `.next/`. Additional exclusions via `--exclude` glob patterns.

So it sidesteps cargo workspace metadata entirely — it doesn't need to know what's "in scope" for the project because noise directories are excluded by default and the caller passes the paths. `drywall ./src` just works.

This is a deliberate design choice stated in the PRD: the goal is a **single static binary with no runtime dependencies** that works in any CI environment without managing toolchains. Cargo subcommand status would tie it to Rust projects; as a standalone binary it can analyze any polyglot monorepo (`drywall ./src ./packages ./services`) regardless of language or build system.

The tradeoff vs `cargo-crap`: crap knows it's in a Rust workspace so it can automatically scope to the right files. drywall puts that responsibility on the caller — less magic, more portable.

Yes, easily. Cargo subcommand discovery is just a naming convention: any binary named `cargo-<name>` in PATH is invocable as `cargo <name>`. The binary itself doesn't change — both call styles work:

```
drywall ./src          # direct
cargo drywall ./src    # via cargo subcommand (if named cargo-drywall)
```

The simplest approach: ship the binary as `cargo-drywall`. Direct invocation still works (`cargo-drywall ./src`), and cargo discovers it automatically. This is exactly how `cargo-nextest` works — the binary is `cargo-nextest`, users call it as `cargo nextest`.

The more interesting question is whether the cargo subcommand path could be smarter: when invoked as `cargo drywall` with no explicit path, it could read `Cargo.toml` to infer `src/` automatically. When invoked as `drywall` with no path, it falls back to the current directory. Two levels of convenience without breaking anything.

The PRD doesn't preclude this — the binary name is the only thing to decide. Want me to open an issue for it or note it somewhere?
