97	### Formatting
98	
99	Indentation is significant. Blocks opened by a colon (`:`) after `for`, `if`, `else`, `ensures`, `exposes`, `provides`, `contracts`, `related` and `timeout` are delimited by consistent indentation relative to the parent clause. Named blocks opened by a keyword and PascalCase name followed by `{ ... }` (`contract`, `invariant`) use brace delimiters. Prose annotations prefixed with `@` (`@invariant`, `@guarantee`, `@guidance`) are followed by indented comment lines that form their body. `contracts:` entries use `demands`/`fulfils` modifiers followed by a contract name. Comments use `--`. Commas may be used as field separators for single-line entity and value type declarations; newlines are the standard separator for multi-line declarations.
100	
101	### Naming conventions
102	
103	- **PascalCase**: entity names, variant names, rule names, trigger names, actor names, surface names, contract names, invariant names (`InterviewSlot`, `CandidateSelectsSlot`, `DeterministicEvaluation`, `Purity`)
104	- **snake_case**: field names, config parameters, derived values, enum literals, relationship names (`expires_at`, `max_login_attempts`, `pending`). Enum literals that reference external standards may use backtick-quoted forms containing characters outside the snake_case set (`` `de-CH-1996` ``, `` `no-cache` ``)
105	- **Entity collections**: natural English plurals of the entity name (`Users`, `Documents`, `Candidacies`)

109	## Module given
110	
111	A `given` block declares the entity instances a module operates on. All rules in the module inherit these bindings.
112	
113	```
114	given {
115	    pipeline: HiringPipeline
116	    calendar: InterviewCalendar
117	}
118	```
119	
120	Rules then reference `pipeline.status`, `calendar.available_slots`, etc. without ambiguity about what they refer to.
121	
122	Not every module needs a `given` block. Rules scoped by triggers on domain entities (e.g., `when: invitation: Invitation.expires_at <= now`) get their entities from the trigger binding. `given` is for specs where rules operate on shared instances that exist once per module scope, such as a pipeline, a catalog or a processing engine.
123	
124	`given` bindings must reference entity types declared in the same module or imported via `use`. Imported module instances are accessed via qualified names (`scheduling/calendar`) and do not need to appear in the local `given` block. Modules that operate only on imported instances may omit the `given` block entirely.
125	
126	This is distinct from surface `context`, which binds a parametric scope for a boundary contract (e.g., `context assignment: SlotConfirmation`).
127

130	## Contracts
131	
132	A `contract` declaration defines a named, direction-agnostic obligation at module level. Surfaces reference contracts in a `contracts:` clause using `demands` (the counterpart must implement) or `fulfils` (this surface supplies) direction markers.
133	
134	### Declaration syntax
135	
136	```
137	contract Codec {
138	    serialize: (value: Any) -> ByteArray
139	    deserialize: (bytes: ByteArray) -> Any
140	
141	    @invariant Roundtrip
142	        -- deserialize(serialize(value)) produces a value
143	        -- equivalent to the original for all supported types.
144	
145	    @guidance
146	        -- Implementations should handle versioned payloads
147	        -- by inspecting a version prefix in the byte array.
148	}
149	```
150	
151	Contract bodies contain typed signatures and annotations (`@invariant`, `@guidance`). Entity, value, enum and variant declarations are prohibited inside contracts. Types referenced in signatures must be declared at module level or imported via `use`.
152	
153	### Referencing contracts in surfaces
154	
155	Surfaces reference contracts in a `contracts:` clause. Each entry uses `demands` or `fulfils` to indicate the direction of the obligation:
156	
157	```
158	surface DomainIntegration {
159	    facing framework: FrameworkRuntime
160	
161	    contracts:
162	        demands Codec
163	        demands DeterministicEvaluation
164	        fulfils EventSubmitter
165	
166	    @guarantee AllOperationsIdempotent
167	        -- All operations exposed by this surface are safe to retry.
168	}
169	```
170	
171	`@guarantee` is a surface-level prose assertion about the boundary as a whole; see [Surfaces](#surfaces) for the full clause reference.
172	
173	The surface inherits all signatures, invariants and guidance from each referenced contract. Each contract name may appear at most once per surface.
174	
175	### Contract identity
176	
177	Contract identity is determined by module-qualified name, consistent with entity and value type identity rules. Two contracts are "the same" if and only if they resolve to the same module-qualified declaration. Composed surfaces referencing the same module-qualified contract are not in conflict. Surfaces referencing identically named contracts from different modules are a structural error.
178	
179	### Imports
180	
181	Contracts are importable across modules via `use`, following the same coordinate system as entity imports. Contract imports are atomic: a contract is imported as a complete unit. Partial imports (importing individual signatures from a contract) are not supported.
182	
183	### No type parameters
184	
185	Contracts do not support type parameters. Signatures may use `Any` where type generality is needed, with invariants expressing the type relationships in prose.

189	## Entities
190	
191	### External entities
192	
193	Entities referenced but managed outside this specification:
194	
195	```
196	external entity Role {
197	    title: String
198	    required_skills: Set<Skill>
199	    location: Location
200	}
201	```
202	
203	External entities define their structure but not their lifecycle. The specification checker will warn when external entities are referenced, reminding that another spec or system governs them.
204	
205	External entities can also serve as **type placeholders**: an entity with minimal or no fields that the consuming spec substitutes with a concrete type. This enables reusable patterns where the library spec depends on an abstraction and the consumer provides the implementation.
206	
207	```
208	-- In a comments library spec
209	external entity Commentable {}
210	
211	entity Comment {
212	    parent: Commentable
213	    ...
214	}
215	
216	-- The consuming spec provides its own entity as the Commentable
217	```
218	
219	The consuming spec maps its entity to the placeholder by using it wherever the library expects the placeholder type. This is dependency inversion at the spec level: the library depends on the abstraction, the consumer supplies the concrete type.
220	
221	### Internal entities
222	
223	```
224	entity Candidacy {
225	    -- Fields (required)
226	    candidate: Candidate
227	    role: Role
228	    status: pending | active | completed | cancelled
229	
230	    -- Relationships (navigate to related entities)
231	    invitation: Invitation with candidacy = this
232	    slots: InterviewSlot with candidacy = this
233	
234	    -- Projections (filtered subsets)
235	    confirmed_slots: slots where status = confirmed
236	    pending_slots: slots where status = pending
237	
238	    -- Derived (computed values)
239	    is_ready: confirmed_slots.count >= 3
240	    has_expired: invitation.expires_at <= now
241	}
242	```

244	### Value types
245	
246	Structured data without identity. No lifecycle, compared by value not reference. Use for concepts such as time ranges and addresses.
247	
248	```
249	value TimeRange {
250	    start: Timestamp
251	    end: Timestamp
252	
253	    -- Derived
254	    duration: end - start
255	}
256	
257	value Location {
258	    name: String
259	    timezone: String
260	    country: String?
261	}
262	```
263	
264	Value types have no identity, are immutable and are embedded within entities. Entities have identity, lifecycle and rules that govern them.
265	
266	### Sum types
267	
268	Sum types (discriminated unions) specify that an entity is exactly one of several alternatives.
269	
270	```
271	entity Node {
272	    path: Path
273	    kind: Branch | Leaf              -- discriminator field
274	}
275	
276	variant Branch : Node {
277	    children: List<Node?>            -- variant-specific field
278	}
279	
280	variant Leaf : Node {
281	    data: List<Integer>              -- variant-specific fields
282	    log: List<Integer>
283	}
284	```
285	
286	A sum type has three parts: a **discriminator field** whose type is a pipe-separated list of variant names, **variant declarations** using `variant X : BaseEntity`, and **variant-specific fields** that only exist for that variant. Variants inherit all fields from the base entity; the discriminator is set automatically on creation.
287	
288	**Distinguishing sum types from enums:** unquoted lowercase values are enum literals (`status: pending | active`), unquoted capitalised values are variant references (`kind: Branch | Leaf`). Backtick-quoted values are always enum literals regardless of case (`` `de-CH-1996` ``). The validator checks that unquoted capitalised names correspond to `variant` declarations.
289	
290	**Creating variant instances** — always via the variant name, not the base:
291	
292	```
293	ensures: MentionNotification.created(user: recipient, comment: comment, mentioned_by: author)
294	-- Not: Notification.created(...)  -- Error: must specify which variant
295	```
296	
297	**Type guards** narrow an entity to a specific variant, enabling access to its fields. They appear in `requires` clauses (guarding the entire rule) and `if` expressions (guarding a branch):
298	
299	```
300	-- requires guard: entire rule assumes Leaf
301	rule ProcessLeaf {
302	    when: ProcessNode(node)
303	    requires: node.kind = Leaf
304	    ensures: Results.created(data: node.data + node.log)
305	}
306	
307	-- if guard: branch-level narrowing
308	rule ProcessNode {
309	    when: ProcessNode(node)
310	    ensures:
311	        if node.kind = Branch:
312	            for child in node.children: ProcessNode(child)
313	        else:
314	            Results.created(data: node.data + node.log)
315	}
316	```
317	
318	Accessing variant-specific fields outside a type guard is an error. Sum types guarantee exhaustiveness (all variants declared upfront), mutual exclusivity (exactly one variant), type safety (variant fields only within guards) and automatic discrimination (set on creation).
319	
320	A `.created` trigger on the base entity fires when any variant is created. The bound variable holds the specific variant instance, and type guards can narrow it:
321	
322	```
323	rule HandleNotification {
324	    when: notification: Notification.created
325	    ensures:
326	        if notification.kind = MentionNotification:
327	            ...
328	}
329	```
330	
331	Use sum types when variants have fundamentally different data or behaviour. Do not use when simple status enums suffice or variants share most of their structure.
332	
333	### Field types
334	
335	**Primitive types:**
336	- `String` — text
337	- `Integer` — whole numbers. Underscores are ignored in numeric literals for readability: `100_000_000`
338	- `Decimal` — numbers with fractional parts (use for money, percentages)
339	- `Boolean` — `true` or `false`
340	- `Timestamp` — point in time. The built-in value `now` evaluates to the current timestamp. Its evaluation model depends on context: in derived values, `now` re-evaluates on each read (making the derived value volatile); in ensures clauses, `now` is bound to the rule execution timestamp (a snapshot); in temporal triggers, `now` is the evaluation timestamp with fire-once semantics.
341	- `Duration` — length of time, written as a numeric literal with a unit suffix: `.seconds`, `.minutes`, `.hours`, `.days`, `.weeks`, `.months`, `.years` (e.g., `24.hours`, `7.days`, `30.seconds`). Both singular and plural forms are valid: `1.hour` and `24.hours`.
342	
343	Primitive types have no properties or methods. For domain-specific string types (email addresses, URLs), use value types or plain `String` fields with descriptive names. For operations on primitives beyond the built-in operators, use black box functions (e.g., `length(password)`, `hash(password)`).
344	
345	**Compound types:**
346	- `Set<T>` — unordered collection of unique items
347	- `List<T>` — ordered collection (use when order matters). A compound field type declared explicitly on entities
348	- `Sequence<T>` — ordered collection produced by ordered relationships and their projections. `Sequence` is a subtype of `Set`: an ordered collection is assignable where an unordered one is expected, but not the reverse. `List<T>` is a field type you declare explicitly; `Sequence` is the collection type the checker infers when a relationship is ordered. Both carry ordering semantics, but they occupy different positions in the grammar
349	- `T?` — optional (may be absent). Reserved for genuinely optional fields: a user's nickname, a note that may or may not exist. For fields whose presence depends on lifecycle state, use a `when` clause instead (see below).
350	
351	**Checking for absent values:**
352	```
353	requires: request.reminded_at = null      -- field is absent/unset
354	requires: request.reminded_at != null     -- field has a value
355	```
356	
357	`null` represents the absence of a value for optional fields.
358	
359	`field = null` and `field != null` are presence checks, not comparisons. `field = null` is true when the field is absent; `field != null` is true when the field has a value. Comparisons with null produce false: `null <= now` is false, `null > 0` is false. Arithmetic with null produces null: `null + 1.day` is null. This means temporal triggers on optional fields (e.g., `when: user: User.next_digest_at <= now`) do not fire when the field is absent.
360	
361	**State-dependent field presence (`when` clause):**
362	
363	A field declaration may carry a `when` clause tying its presence to lifecycle state:
364	
365	```
366	entity Order {
367	    status: pending | confirmed | shipped | delivered | cancelled
368	    customer: Customer
369	    total: Money
370	    tracking_number: String when status = shipped | delivered
371	    shipped_at: Timestamp when status = shipped | delivered
372	    delivery_confirmed_at: Timestamp when status = delivered
373	
374	    transitions status {
375	        pending -> confirmed
376	        confirmed -> shipped
377	        shipped -> delivered
378	        terminal: delivered, cancelled
379	    }
380	}
381	```
382	
383	Fields without `when` are present in all states. Fields with `when` are present only when the named status field holds one of the listed values. The `when` clause references a single status field; that field must have a `transitions` block.
384	
385	`?` and `when` are orthogonal. `reviewer_notes: String? when review = approved | rejected` means the field exists in those states but may be null within them. `?` is genuine optionality; `when` is lifecycle-dependent presence. A field may carry both.
386	
387	Entities with multiple status fields use the qualified form to disambiguate:
388	
389	```
390	entity Document {
391	    status: draft | published | archived
392	    review: pending | approved | rejected
393	
394	    transitions status { ... }
395	    transitions review { ... }
396	
397	    published_at: Timestamp when status = published | archived
398	    reviewer_notes: String when review = rejected
399	}
400	```
401	
402	Each `when` clause references one status field. Compound conditions across multiple status fields (`when status = published and review = rejected`) are not supported; use invariants for cross-field constraints.
403	
404	The `when` keyword appears in three syntactic positions: rule triggers (`when: TriggerCondition`, with colon), surface and provides guards (`Action(...) when condition`, without colon, after an action), and field declarations (`field: Type when status = value`, without colon, after a type). The grammar is unambiguous at each position. Rule triggers are identified by the colon. Surface guards follow an action or related clause. Field `when` clauses follow a type declaration.
405	
406	**Presence and absence obligations.** Obligations fire when a rule crosses the boundary of a field's `when` set:
407	
408	- **Entering** (source state outside `when` set, target state inside): the rule must set the field.
409	- **Leaving** (source state inside `when` set, target state outside): the rule must clear the field.
410	- **Moving within** (both states inside): no obligation. The field is already present and remains present; the rule may update it but need not.
411	- **Moving outside** (both states outside): no obligation.
412	
413	```
414	entity Document {
415	    status: active | deleted
416	    deleted_at: Timestamp when status = deleted
417	    deleted_by: User when status = deleted
418	
419	    transitions status {
420	        active -> deleted
421	        deleted -> active
422	        terminal: active
423	    }
424	}
425	
426	rule SoftDelete {
427	    when: SoftDelete(document, actor)
428	    requires: document.status = active
429	    ensures:
430	        document.status = deleted
431	        document.deleted_at = now        -- entering when set: must set
432	        document.deleted_by = actor      -- entering when set: must set
433	}
434	
435	rule RestoreDocument {
436	    when: RestoreDocument(document)
437	    requires: document.status = deleted
438	    ensures:
439	        document.status = active
440	        document.deleted_at = null       -- leaving when set: must clear
441	        document.deleted_by = null       -- leaving when set: must clear
442	}
443	```
444	
445	**Access without guard.** Accessing a `when`-qualified field without a `requires` guard narrowing to a qualifying state is an error:
446	
447	```
448	-- Error: tracking_number requires status in {shipped, delivered}
449	rule BadAccess {
450	    when: SomeEvent(order)
451	    ensures: Label.created(tracking: order.tracking_number)
452	}
453	
454	-- Valid: requires narrows to a qualifying state
455	rule GenerateLabel {
456	    when: GenerateLabel(order)
457	    requires: order.status = shipped
458	    ensures: Label.created(tracking: order.tracking_number)
459	}
460	```
461	
462	**Convergent transitions.** If two rules reach the same state and the entity requires a field at that state, both must set it:
463	
464	```
465	rule CancelByCustomer {
466	    when: CustomerCancels(order)
467	    requires: order.status = pending
468	    ensures:
469	        order.status = cancelled
470	        order.cancelled_at = now         -- required: entering when set
471	        order.cancelled_by = customer    -- required: entering when set
472	}
473	
474	rule CancelByTimeout {
475	    when: order: Order.created_at + 48.hours <= now
476	    requires: order.status = pending
477	    ensures:
478	        order.status = cancelled
479	        order.cancelled_at = now         -- required: entering when set
480	        -- Error: cancelled_by not set
481	}
482	```
483	
484	**Enumerated types (inline):**
485	```
486	status: pending | confirmed | declined | expired
487	```
488	
489	**Named enumerations:**
490	```
491	enum Recommendation { strong_yes | yes | no | strong_no }
492	enum DayOfWeek { monday | tuesday | wednesday | thursday | friday | saturday | sunday }
493	```
494	
495	Named enumerations define a reusable set of values. Declare them in the Enumerations section of the file. Reference them as field types: `recommendation: Recommendation`. Inline enums (`status: pending | active`) are equivalent but anonymous; use named enums when the same set of values appears in multiple fields or entities.
496	
497	**Backtick-quoted enum literals:**
498	
499	Enum values that reference external standards may contain characters outside the snake_case set (hyphens, dots, mixed case, leading digits). Enclose these in backticks:
500	
501	```
502	enum InterfaceLanguage { en | de | fr | `de-CH-1996` | es | `zh-Hant-TW` | `sr-Latn` }
503	enum CacheDirective { `no-cache` | `no-store` | `must-revalidate` | `max-age` }
504	```
505	
506	Backtick-quoted literals are values, not identifiers. They participate in equality comparison and assignment. The checker does not apply case convention rules inside backticks. Comparison is byte-exact after UTF-8 encoding; authors are responsible for using the canonical form from the external standard. Quoted and unquoted forms are distinct values with no implicit normalisation: `de_ch_1996` and `` `de-CH-1996` `` are different values.
507	
508	Backtick-quoted literals are permitted in enum declarations (named and inline), literal comparisons in rules and `ensures` clauses. They are not permitted in identifier positions (field names, entity names, variant names, config parameter names, derived value names, rule/trigger/invariant names). They cannot appear in arithmetic expressions.
509	
510	Inline enums are anonymous: they have no type identity. Two inline enum fields cannot be compared with each other, whether on the same entity or across entities; the checker reports an error. Use a named enum when values need to be compared across fields. Named enums are distinct types: a field typed `Recommendation` cannot be compared with a field typed `DayOfWeek`, even if they happen to share a literal.
511	
512	This catches a common mistake when tracking previous state:
513	
514	```
515	-- Error: cannot compare two inline enum fields
516	entity Order {
517	    status: pending | shipped | delivered
518	    previous_status: pending | shipped | delivered
519	}
520	requires: order.status != order.previous_status    -- checker error
521	
522	-- Fix: extract a named enum
523	enum OrderStatus { pending | shipped | delivered }
524	entity Order {
525	    status: OrderStatus
526	    previous_status: OrderStatus
527	}
528	requires: order.status != order.previous_status    -- valid
529	```

531	### Transition graphs
532	
533	A transition graph declares the valid lifecycle transitions for an enum status field. When present, the graph is authoritative: rules whose `ensures` clauses produce transitions not in the graph are validation errors. Entities without a declared graph continue to derive transition validity from rules alone, with no change in checker behaviour.
534	
535	The graph lives inside the entity body, below the field it governs, introduced by the `transitions` keyword followed by the field name:
536	
537	```
538	entity Order {
539	    status: pending | confirmed | shipped | delivered | cancelled
540	
541	    transitions status {
542	        pending -> confirmed
543	        confirmed -> shipped
544	        shipped -> delivered
545	        pending -> cancelled
546	        confirmed -> cancelled
547	        terminal: delivered, cancelled
548	    }
549	}
550	```
551	
552	**Edges.** Each line in the block is a directed edge using `->`: `from_state -> to_state`. The graph declares which transitions are possible (structural topology), not when or why they occur (conditional logic). Conditions remain in rules. The graph says "this edge exists"; the rule says "this edge fires under these conditions". A complete understanding of lifecycle behaviour requires reading both the graph and the rules.
553	
554	**Terminal states.** Terminal states are declared with a `terminal:` clause listing the terminal values. This is the sole mechanism for terminal marking. Absence of outbound edges does not imply terminal status; the checker requires explicit declaration.
555	
556	**Completeness obligations.** When a graph is declared, the checker enforces two obligations:
557	1. Every non-terminal state has at least one outbound edge in the graph.
558	2. Every declared edge is witnessed by at least one rule whose `requires`/`ensures` pair can produce that transition.
559	
560	The converse (every rule transition appears in the graph) is enforced by the authoritative relationship itself. The graph is identified by entity and field name (e.g. `Order.status`) in error messages; no separate name declaration is needed.
561	
562	**Enum reference, not redeclaration.** The graph references enum values already declared on the field. The checker enforces exact correspondence: every value in the graph must exist on the field, and every field value must appear in at least one edge or as a terminal. Drift is a hard error.
563	
564	**Opt-in.** The checker does not emit warnings or suggestions about missing graphs on entities that lack them. The construct earns adoption through demonstrated value, not through tooling pressure.
565	
566	**Multiple status fields.** Entities with multiple status fields use independent single-field graphs. Cross-field constraints are expressed through invariants.
567	
568	**Generality.** Transition graphs currently target enum status fields. The syntax is designed to extend to variant discriminators and other lifecycle-bearing fields in future versions without structural changes.
569	
570	**Interaction with state-dependent fields.** When a transition graph is declared, the checker uses its structure alongside `when` clauses on field declarations to enforce presence and absence obligations at each transition (see [Field types](#field-types)) and to verify that `when`-qualified fields are only accessed within qualifying state guards.
571	
572	**Entity references:**
573	```
574	candidate: Candidate
575	role: Role
576	```

578	### Relationships
579	
580	Always use singular entity names; the relationship name indicates plurality:
581	
582	```
583	-- One-to-one (singular relationship name)
584	invitation: Invitation with candidacy = this
585	
586	-- One-to-many (plural relationship name, but singular entity name)
587	slots: InterviewSlot with candidacy = this
588	feedback_requests: FeedbackRequest with interview = this
589	
590	-- Self-referential
591	replies: Comment with reply_to = this
592	```
593	
594	The `with X = this` syntax declares a relationship by naming the field on the related entity that points back. `this` refers to the enclosing entity instance. The syntax is the same whether the relationship is one-to-one, one-to-many or self-referential.
595	
596	The relationship name determines the cardinality:
597	
598	- **Singular name** (e.g., `invitation`) — at most one related entity. The value is the entity instance, or `null` if none exists. Equivalent to `T?`. If multiple entities match a singular relationship, the specification is in error and the checker should report it.
599	- **Plural name** (e.g., `slots`) — zero or more related entities. The value is a collection, empty if none exist.
600	
601	Relationships currently produce `Set` (unordered). The declaration syntax for ordered relationships (which would produce `Sequence`) is pending a follow-up ALP. The semantic model for ordered collections is defined; see [Collection operations](#collection-operations) for the type-level rules.
602	
603	### Projections
604	
605	Named filtered views of relationships:
606	
607	```
608	-- Simple status filter
609	confirmed_slots: slots where status = confirmed
610	
611	-- Multiple conditions
612	active_requests: feedback_requests where status = pending and requested_at > cutoff
613	
614	-- Projection with mapping
615	confirmed_interviewers: confirmations where status = confirmed -> interviewer
616	```
617	
618	The `-> field` syntax extracts a field from each matching entity. When the extracted field is optional (`T?`), null values are excluded from the result: the projection produces `Set<T>`, not `Set<T?>`.
619	
620	Projections preserve ordering. If the source collection is a `Sequence`, the projection result is also a `Sequence` in the same relative order. This applies to both `where` filtering and `-> field` extraction. Field extraction on ordered collections retains duplicates (two source elements navigating to the same target produce two entries in sequence order); use `.unique` to deduplicate, which produces an unordered `Set`.
621	
622	### Derived values
623	
624	Computed from other fields. Always read-only and automatically updated.
625	
626	```
627	-- Boolean derivations
628	is_valid: interviewers.any(i => i.can_solo) or interviewers.count >= 2
629	is_expired: expires_at <= now
630	all_responded: pending_requests.count = 0
631	
632	-- Value derivations
633	time_remaining: deadline - now
634	
635	-- Parameterised derived values
636	can_use_feature(f): f in plan.features
637	has_permission(p): p in role.effective_permissions
638	```
639	
640	Parameters are locally scoped to the expression. Parameterised derived values cannot reference module `given` bindings or global state; they operate only on the entity's own fields and their parameter. No side effects.

644	## Rules
645	
646	Rules define behaviour: what happens when triggers occur.
647	
648	### Rule structure
649	
650	```
651	rule RuleName {
652	    when: TriggerCondition
653	
654	    let binding1 = expression      -- bindings can appear before requires
655	
656	    requires: Precondition1
657	    requires: Precondition2
658	
659	    let binding2 = expression      -- or between requires and ensures
660	
661	    ensures: Postcondition1
662	    ensures: Postcondition2
663	
664	    @guidance                       -- optional, always last
665	        -- Non-normative implementation advice.
666	}
667	```
668	
669	| Clause | Purpose |
670	|--------|---------|
671	| `when` | What triggers this rule |
672	| `for` | Iterate: apply the rule body for each element in a collection |
673	| `let` | Local variable bindings (can appear anywhere after `when`) |
674	| `requires` | Preconditions that must be true (rule fails if not met) |
675	| `ensures` | What becomes true after the rule executes |
676	| `@guidance` | Non-normative implementation advice (optional, always last) |
677	
678	Place `let` bindings where they make the rule most readable, typically just before the clause that first uses them.
679	
680	### Derived value `when` propagation
681	
682	Derived values computed from `when`-qualified fields inherit the intersection of their inputs' `when` sets:
683	
684	```
685	entity Order {
686	    status: pending | confirmed | shipped | delivered
687	    shipped_at: Timestamp when status = shipped | delivered
688	    delivery_confirmed_at: Timestamp when status = delivered
689	
690	    transitions status {
691	        pending -> confirmed
692	        confirmed -> shipped
693	        shipped -> delivered
694	        terminal: delivered
695	    }
696	
697	    -- Inferred: when status = delivered
698	    -- (intersection of {shipped, delivered} and {delivered})
699	    days_in_transit: delivery_confirmed_at - shipped_at
700	}
701	```
702	
703	The checker infers this; the author does not declare it. If the intersection is empty, the derived value is unreachable and the checker reports an error.
704	
705	An author may optionally annotate a derived value with an explicit `when` clause as documentation:
706	
707	```
708	days_in_transit: delivery_confirmed_at - shipped_at when status = delivered
709	```
710	
711	When present, the checker verifies it matches the inferred set. A mismatch is an error. When absent, the inferred set applies silently. The checker exports inferred `when` sets as structured data alongside state-level summaries.
712	
713	**Cross-entity access.** Accessing a `when`-qualified field on a related entity requires a guard narrowing the related entity's status to a qualifying state. `candidacy.order.tracking_number` requires that the rule's context narrows `order.status` to a qualifying state.
714	
715	### Rule-level iteration
716	
717	A `for` clause applies the rule body once per element in a collection. The binding variable is available in all subsequent clauses.
718	
719	```
720	rule ProcessDigests {
721	    when: schedule: DigestSchedule.next_run_at <= now
722	    for user in Users where notification_setting.digest_enabled:
723	        let settings = user.notification_setting
724	        ensures: DigestBatch.created(user: user, ...)
725	}
726	```
727	
728	The `where` keyword filters the collection, consistent with projection syntax. The indented body contains the rule's `let`, `requires` and `ensures` clauses scoped to each element.
729	
730	This is the same `for x in collection:` construct used in ensures blocks and surfaces. The body inherits the constraints of its enclosing context: at rule level it wraps `let`, `requires` and `ensures` clauses; inside an ensures block it wraps postconditions (state changes, entity creation, trigger emissions, removal assertions); inside a surface it wraps the items permitted by the enclosing clause (`exposes`, `provides` or `related`).
731	
732	### Multiple rules for the same trigger
733	
734	When multiple rules share a trigger, their `requires` clauses determine which fires. If preconditions overlap such that multiple rules could match simultaneously, this is a spec ambiguity. The specification checker should warn when rules with the same trigger have overlapping preconditions.
735	
736	### Trigger types
737	
738	**External stimulus** — action from outside the system:
739	```
740	when: AdminApprovesInterviewers(admin, suggestion, interviewers, times)
741	when: CandidateSelectsSlot(invitation, slot)
742	```
743	
744	**Optional parameters** use the `?` suffix:
745	```
746	when: InterviewerReportsNoInterview(interviewer, interview, reason, details?)
747	```
748	
749	**State transition** — entity changed state:
750	```
751	when: interview: Interview.status transitions_to scheduled
752	when: confirmation: SlotConfirmation.status transitions_to confirmed
753	```
754	
755	The variable before the colon binds the entity that triggered the transition. `transitions_to` fires when a field transitions to the specified value from a different value, not on initial entity creation (use `.created` for that). It is valid for enum fields, boolean fields and entity reference fields. When a transition graph is declared for the field, only transitions in the graph are structurally valid; rules producing other transitions are validation errors.
756	
757	**State becomes** — entity has a value, whether by creation or transition:
758	```
759	when: interview: Interview.status becomes scheduled
760	```
761	
762	`becomes` fires both when an entity is created with the specified value and when a field transitions to that value from a different value. Like `transitions_to`, it is valid for enum fields, boolean fields and entity reference fields. It is equivalent to writing a `transitions_to` rule and a `.created` rule with a `requires` guard, combined into a single trigger. Use `becomes` when the rule should apply regardless of how the entity arrived at the state. Use `transitions_to` when the rule should only apply to transitions (e.g., sending a "rescheduled" notification that doesn't apply on initial creation).
763	
764	**Temporal** — time-based condition:
765	```
766	when: invitation: Invitation.expires_at <= now
767	when: interview: Interview.slot.time.start - 1.hour <= now
768	when: request: FeedbackRequest.requested_at + 24.hours <= now
769	```
770	
771	Temporal triggers use explicit `var: Type` binding, the same as state transitions and entity creation. The binding names the entity instance and its type. Temporal triggers fire once when the condition becomes true. Always include a `requires` clause to prevent re-firing:
772	```
773	rule InvitationExpires {
774	    when: invitation: Invitation.expires_at <= now
775	    requires: invitation.status = pending  -- prevents re-firing
776	    ensures: invitation.status = expired
777	}
778	```
779	
780	**Derived condition becomes true:**
781	```
782	when: interview: Interview.all_feedback_in
783	when: slot: InterviewSlot.is_valid
784	```
785	
786	Derived condition triggers fire when the value transitions from false to true, the same semantics as temporal triggers. If the derived value could revert to false and become true again, include a `requires` clause to prevent re-firing, just as with temporal triggers.
787	
788	**Entity creation** — fires when a new entity is created:
789	```
790	when: batch: DigestBatch.created
791	when: mention: CommentMention.created
792	```
793	
794	**Chained from another rule's trigger emission:**
795	```
796	when: AllConfirmationsResolved(candidacy)
797	```
798	
799	A rule chains from another by subscribing to a trigger emission. The emitting rule includes the event in an ensures clause:
800	
801	```
802	ensures: AllConfirmationsResolved(candidacy: candidacy)
803	```
804	
805	The receiving rule subscribes via its `when` clause. This uses the same syntax as external stimulus triggers, but the stimulus comes from another rule rather than from outside the system.
806	
807	### Preconditions (requires)
808	
809	Preconditions must be true for the rule to execute. If not met, the trigger is rejected.
810	
811	```
812	requires: invitation.status = pending
813	requires: not invitation.is_expired
814	requires: slot in invitation.slots
815	requires: interviewer in interview.interviewers
816	requires:
817	    interviewers.count >= 2
818	    or interviewers.any(i => i.can_solo)
819	```
820	
821	**Precondition failure behaviour:**
822	- For external stimulus triggers: The action is rejected; caller receives an error
823	- For temporal/derived triggers: The rule simply does not fire; no error
824	- For chained triggers: The chain stops; previous rules' effects still apply
825	
826	### Local bindings (let)
827	
828	```
829	let confirmation = SlotConfirmation{slot, interviewer}
830	let time_until = interview.slot.time.start - now
831	let is_urgent = time_until < 24.hours
832	let is_modified =
833	    interviewers != suggestion.suggested_interviewers
834	    or proposed_times != suggestion.suggested_times
835	```
836	
837	### Discard bindings
838	
839	Use `_` where a binding is required syntactically but the value is not needed. Multiple `_` bindings in the same scope do not conflict.
840	
841	```
842	when: _: LogProcessor.last_flush_check + flush_timeout_hours <= now
843	when: SomeEvent(_, slot)
844	for _ in items: Counted(batch)
845	```
846	
847	### Postconditions (ensures)
848	
849	Postconditions describe what becomes true. They are declarative assertions about the resulting state, not imperative commands.
850	
851	In state change assignments (`entity.field = expression`), the expression on the right references pre-rule field values. This avoids circular definitions: `user.count = user.count + 1` means the resulting count equals the original count plus one. Conditions within ensures blocks (`if` guards, creation parameters, trigger emission parameters) reference the resulting state as defined by the state changes. A `let` binding within an ensures block introduces a name visible to all subsequent statements in that block.
852	
853	Worked example: suppose `account.balance` is 100 before the rule fires.
854	
855	```
856	ensures: account.balance = account.balance + 50       -- RHS reads pre-rule value: 100 + 50 = 150
857	ensures:
858	    if account.balance > 120:                          -- condition reads resulting state: 150 > 120, true
859	        Notification.created(account: account, type: high_balance)
860	```
861	
862	The assignment reads 100 (the pre-rule value). The `if` guard reads 150 (the resulting state after the assignment).
863	
864	Common mistake: assuming `if` guards in ensures read pre-rule values. Suppose `order.status` is `pending` before the rule fires.
865	
866	```
867	ensures: order.status = shipped
868	ensures:
869	    if order.status = pending:                             -- WRONG: reads resulting state (shipped), so this is false
870	        Notification.created(to: order.customer, template: order_pending_reminder)
871	    if order.status = shipped:                             -- reads resulting state (shipped), so this is true
872	        Notification.created(to: order.customer, template: order_shipped)
873	```
874	
875	The author likely meant "if the order was pending before we changed it". But the `if` guard inside ensures reads the resulting state, not the pre-rule state. To test pre-rule values, use a `let` binding or `requires` clause before the ensures block.
876	
877	Ensures clauses have four forms:
878	
879	**State changes** — modify an existing entity's fields:
880	```
881	ensures: slot.status = booked
882	ensures: invitation.status = accepted
883	ensures: candidacy.retry_count = candidacy.retry_count + 1
884	ensures: user.locked_until = null              -- clearing an optional field
885	```
886	
887	Setting an optional field to `null` asserts the field becomes absent. Only valid for fields typed as optional (`T?`).
888	
889	**Entity creation** — create a new entity using `.created()`:
890	```
891	ensures: Interview.created(
892	    candidacy: invitation.candidacy,
893	    slot: slot,
894	    interviewers: slot.confirmed_interviewers,
895	    status: scheduled
896	)
897	
898	ensures: Email.created(
899	    to: candidate.email,
900	    template: interview_invitation,
901	    data: { slots: slots }
902	)
903	
904	ensures: CalendarInvite.created(
905	    attendees: interviewers + candidate,
906	    time: slot.time,
907	    duration: interview_type.duration
908	)
909	```
910	
911	Entity creation uses `.created()` exclusively. Domain meaning lives in entity names and rule names, not in creation verbs. `Email.created(...)` not `Email.sent(...)`.
912	
913	When creating entities that need to be referenced later in the same ensures block, use explicit `let` binding:
914	```
915	ensures:
916	    let slot = InterviewSlot.created(time: time, candidacy: candidacy, status: pending)
917	    for interviewer in interviewers:
918	        SlotConfirmation.created(slot: slot, interviewer: interviewer)
919	```
920	
921	A `let` binding within an ensures block is visible to all subsequent statements in that block, including nested `for` loops. It does not leak outside the ensures block.
922	
923	**Trigger emission** — emit a named event that other rules can chain from:
924	```
925	ensures: CandidateInformed(
926	    candidate: candidacy.candidate,
927	    about: slot_unavailable,
928	    data: { available_alternatives: remaining_slots }
929	)
930	
931	ensures: UserMentioned(user: mention.user, comment: comment, mentioned_by: author)
932	ensures: FeatureUsed(workspace: workspace, feature: feature, by: user)
933	```
934	
935	Trigger emissions are observable outcomes, not entity creation. They have no `.created()` call and are referenced by other rules' `when` clauses. Parameter values follow normal expression resolution: bound names are resolved first, then enum literals if the parameter has a declared type on the receiving rule. Bare identifiers that resolve to neither a binding nor an enum literal are a checker warning.
936	
937	**Entity removal:**
938	```
939	ensures: not exists target_membership
940	ensures: not exists CommentMention{comment, user}
941	```
942	
943	See [Existence](#existence) in the expression language for the full syntax including bulk removal and the distinction from soft delete.
944	
945	**Bulk updates:**
946	```
947	ensures:
948	    for s in invitation.proposed_slots:
949	        s.status = cancelled
950	```
951	
952	**Conditional outcomes:**
953	```
954	ensures:
955	    if candidacy.retry_count < 2:
956	        candidacy.status = pending_scheduling
957	    else:
958	        candidacy.status = scheduling_stalled
959	        Notification.created(...)
960	```

964	## Expression language
965	
966	### Navigation
967	
968	```
969	-- Field access
970	interview.status
971	candidate.email
972	
973	-- Relationship traversal
974	interview.feedback_requests
975	candidacy.slots
976	
977	-- Chained navigation
978	interview.candidacy.candidate.email
979	feedback_request.interview.slot.time
980	
981	-- Optional navigation (short-circuits to null if left side is null)
982	inherits_from?.effective_permissions
983	reply_to?.author
984	
985	-- Null coalescing (provides default when left side is null)
986	identity.timezone ?? "UTC"
987	inherits_from?.effective_permissions ?? {}
988	
989	-- State-dependent fields: ?. is not needed for when-qualified fields
990	-- when the requires clause narrows to a qualifying state
991	order.tracking_number         -- valid when requires: order.status = shipped
992	
993	-- Self-reference
994	this                                        -- the instance being defined or identified
995	replies: Comment with reply_to = this       -- all Comments whose reply_to is this entity
996	```
997	
998	`this` refers to the instance of the enclosing type. It is valid in two contexts:
999	
1000	- **Entity declarations**: `this` is the current entity instance. Available in relationships, projections and derived values.
1001	- **Actor `identified_by` expressions**: `this` is the entity instance being tested for actor membership (see [Actor declarations](#actor-declarations)).
1002	
1003	### Join lookups
1004	
1005	For entities that connect two other entities (join tables):
1006	
1007	```
1008	let confirmation = SlotConfirmation{slot, interviewer}
1009	let feedback_request = FeedbackRequest{interview, interviewer}
1010	```
1011	
1012	Curly braces with field names look up the specific instance where those fields match. Any number of fields can be specified. Each name serves as both the field name on the entity and the local variable whose value is matched. The lookup must match at most one entity; if the fields do not uniquely identify a single instance, the specification is ambiguous and the checker should report an error. If no entity matches, the binding is null. Use `exists` to test whether a lookup matched before accessing fields on it; accessing fields on a null binding is an error.
1013	
1014	When the local variable name differs from the field name, use the explicit form:
1015	
1016	```
1017	let actor_membership = WorkspaceMembership{user: actor, workspace: workspace}
1018	let share = ResourceShare{resource: resource, user: inviter}
1019	requires: not exists User{email: new_email}
1020	```
1021	
1022	### Collection operations
1023	
1024	```
1025	-- Count
1026	slots.count
1027	pending_requests.count
1028	
1029	-- Membership
1030	slot in invitation.slots
1031	interviewer in interview.interviewers
1032	
1033	-- Any/All (always use explicit lambda)
1034	interviewers.any(i => i.can_solo)
1035	confirmations.all(c => c.status = confirmed)
1036	
1037	-- Filtering (in projections and expressions)
1038	slots where status = confirmed
1039	requests where status in {submitted, escalated}
1040	
1041	-- Iteration (introduces a scope block)
1042	for slot in slots: ...
1043	
1044	-- Set mutation (ensures-only, modifies a relationship)
1045	interviewers.add(new_interviewer)
1046	interviewers.remove(leaving_interviewer)
1047	
1048	-- Set arithmetic (expression-level, produces a new set)
1049	all_permissions: permissions + inherited_permissions
1050	removed_mentions: old_mentions - new_mentions
1051	
1052	-- First/last (ordered collections only: Sequence or List<T>)
1053	attempts.first
1054	attempts.last
1055	
1056	-- Deduplicate (produces unordered Set)
1057	ordered_interviewers.unique
1058	```
1059	
1060	`.first` and `.last` are restricted to ordered collections (`Sequence` or `List<T>`). Using them on a `Set` is a warning in the current version, becoming a hard error in the next version.
1061	
1062	`.unique` deduplicates a collection. Because deduplication discards positional information, the result is always an unordered `Set`, even when the source is ordered.
1063	
1064	`for item in collection:` iterates in declared order when the source is a `Sequence` or `List<T>`. When the source is a `Set`, iteration order is unspecified.
1065	
1066	`.add()` and `.remove()` are ensures-only mutations on a relationship. Set `+` and `-` are expression-level operations that produce new sets without mutating anything. When applied to ordered collections (`Sequence` or `List<T>`), `+` and `-` produce unordered results (`Set<T>`). The checker reports the type change if the result is used where ordering is expected.
1067	
1068	Dot-method syntax on collections is reserved for built-in operations. The built-in dot-methods are: `.count`, `.any()`, `.all()`, `.first`, `.last`, `.unique`, `.add()`, `.remove()`. The checker rejects any dot-method call on a collection whose name is not in this set. Domain-specific collection operations use free-standing black box function syntax with the collection as the first argument (see [Black box functions](#black-box-functions)).
1069	
1070	### Comparisons
1071	
1072	```
1073	status = pending
1074	status != proposed
1075	count >= 2
1076	expires_at <= now
1077	time_until < 24.hours
1078	status in {confirmed, declined, expired}
1079	provider not in user.linked_providers
1080	```
1081	
1082	`{value1, value2, ...}` is a set literal used with `in` and `not in` for membership tests. This is the same set literal syntax used in field declarations and expressions.
1083	
1084	### Arithmetic
1085	
1086	```
1087	candidacy.retry_count + 1
1088	interview.slot.time.start - now
1089	feedback_request.requested_at + 24.hours
1090	now + 7.days
1091	recent_failures.count / config.window_sample_size
1092	price * quantity
1093	```
1094	
1095	Four operators: `+`, `-`, `*`, `/`. Standard precedence: `*` and `/` bind tighter than `+` and `-`. Use parentheses to override. Arithmetic involving null produces null (e.g., `null + 1.day` is null). Derived values computed from optional fields are implicitly optional.
1096	
1097	### Boolean logic
1098	
1099	```
1100	interviewers.count >= 2 or interviewers.any(i => i.can_solo)
1101	invitation.status = pending and not invitation.is_expired
1102	not (a or b)  -- equivalent to: not a and not b
1103	```
1104	
1105	`and` and `or` short-circuit left to right. If the left operand of `or` is true, the right operand is not evaluated; if the left operand of `and` is false, the right operand is not evaluated. This permits patterns like `not exists x or not x.is_valid`, where the right side is only reached when `x` exists.
1106	
1107	### Implication
1108	
1109	```
1110	account.status = closed implies account.balance = 0
1111	not user.is_verified implies user.permissions.count = 0
1112	```
1113	
1114	`implies` has the lowest precedence of any boolean operator, binding looser than `and` and `or`. `a implies b` is equivalent to `not a or b`. Available in all expression contexts. Its primary use case is invariant assertions, but it reads naturally in `requires` guards and derived boolean values as well.
1115	
1116	### Conditional expressions
1117	
1118	```
1119	-- Inline (single values)
1120	email_status: if settings.email_on_mention = never: skipped else: pending
1121	thread_depth: if is_reply: reply_to.thread_depth + 1 else: 0
1122	
1123	-- Block (multiple outcomes)
1124	ensures:
1125	    if candidacy.retry_count < 2:
1126	        candidacy.status = pending_scheduling
1127	    else:
1128	        candidacy.status = scheduling_stalled
1129	        Notification.created(...)
1130	```
1131	
1132	Both forms use the same `if condition: ... else: ...` syntax. The inline form is for single-value assignments only. If either branch needs multiple statements or entity creation, use block form. Omit `else` when only the true branch has an effect.
1133	
1134	Multi-branch conditionals use `else if`:
1135	
1136	```
1137	let preference =
1138	    if notification.kind = MentionNotification: settings.email_on_mention
1139	    else if notification.kind = ReplyNotification: settings.email_on_comment
1140	    else if notification.kind = ShareNotification: settings.email_on_share
1141	    else: immediately
1142	```
1143	
1144	Each `else if` adds a branch. The final `else` provides a fallback.
1145	
1146	`exists` can also be used as a condition in `if` expressions, not just in `requires`. When `exists x` is used as an `if` condition, `x` is guaranteed non-null within the `if` body and can be accessed safely:
1147	
1148	```
1149	ensures:
1150	    if exists existing:
1151	        not exists existing
1152	    else:
1153	        CommentReaction.created(comment: comment, user: user, emoji: emoji)
1154	```
1155	
1156	### Existence
1157	
1158	The `exists` keyword checks whether an entity instance exists. Use `not exists` for negation.
1159	
1160	```
1161	-- Entity looked up via let binding
1162	let user = User{email}
1163	requires: exists user
1164	
1165	-- Join entity lookup
1166	requires: exists WorkspaceMembership{user, workspace}
1167	
1168	-- Negation
1169	requires: not exists User{email: email}
1170	requires: not exists ResourceInvitation{resource, email}
1171	```
1172	
1173	In `ensures` clauses, `not exists` asserts that an entity has been removed from the system:
1174	
1175	```
1176	-- Entity removal
1177	ensures: not exists target_membership
1178	ensures: not exists CommentMention{comment, user}
1179	
1180	-- Bulk removal
1181	ensures:
1182	    for d in workspace.deleted_documents:
1183	        not exists d
1184	```
1185	
1186	If the entity is already absent, the postcondition is trivially satisfied (no error, no operation). This follows from declarative semantics: `not exists x` asserts a property of the resulting state, not an imperative command.
1187	
1188	This is distinct from soft delete, which changes a field rather than removing the entity:
1189	
1190	```
1191	-- Soft delete (entity still exists, status changes)
1192	ensures: document.status = deleted
1193	
1194	-- Hard delete (entity no longer exists)
1195	ensures: not exists document
1196	```
1197	
1198	### Literals
1199	
1200	```
1201	-- Set literals
1202	permissions: { "documents.read", "documents.write" }
1203	features: { basic_editing, api_access }
1204	
1205	-- Object literals (anonymous records, used in creation parameters and trigger emissions)
1206	data: { candidate: candidate, time: time }
1207	data: { slots: remaining_slots }
1208	data: { unlocks_at: user.locked_until }
1209	```
1210	
1211	Object literals are anonymous record types. They carry named fields but have no declared type. Use them for ad-hoc data in entity creation parameters and trigger emission payloads where defining a named type would add ceremony without clarity. Object literals always require explicit `key: value` pairs; `{ x }` is a set literal containing `x`, not an object with shorthand.
1212	
1213	### Black box functions
1214	
1215	Black box functions represent domain logic too complex or algorithmic for the spec level. They appear in expressions and their behaviour is described by comments or deferred specifications. Black box functions always use free-standing call syntax; they never use dot-method syntax.
1216	
1217	```
1218	-- Scalar black box functions
1219	hash(password)                              -- black box
1220	verify(password, user.password_hash)        -- black box
1221	parse_mentions(body)                        -- black box: extracts @username
1222	next_digest_time(user)                      -- black box: uses digest_day_of_week
1223	
1224	-- Collection-operating black box functions (collection as first argument)
1225	filter(events, e => e.recent)               -- black box
1226	grouped_by(copies, r => r.output_payloads)  -- black box
1227	min_by(pending, e => e.offset)              -- black box
1228	flatMap(groups, g => g.deferred_events)     -- black box
1229	```
1230	
1231	Black box functions are pure (no side effects) and deterministic for the same inputs within a rule execution.
1232	
1233	The distinction between built-in operations and black box functions is syntactic: dot-method calls on collections (`.count`, `.any()`, `.all()`, `.first`, `.last`, `.unique`, `.add()`, `.remove()`) are built-in with language-defined semantics. Free-standing function calls are black box with implementation-defined semantics. The checker enforces this boundary: an unrecognised dot-method on a collection is an error. Built-in operations may chain from the result of a black box function call, since the result is a collection: `filter(events, e => e.recent).count` is valid.
1234	
1235	### The `with` and `where` keywords
1236	
1237	`with` declares how entities are connected. `where` selects from those connections.
1238	
1239	A relationship declaration says "these are the InterviewSlots that belong to this Candidacy". A projection says "of those slots, show me the confirmed ones":
1240	
1241	```
1242	-- Relationship: declares which InterviewSlots belong to this Candidacy
1243	slots: InterviewSlot with candidacy = this
1244	
1245	-- Projection: of those slots, keep the confirmed ones
1246	confirmed_slots: slots where status = confirmed
1247	```
1248	
1249	Because `with` defines a relationship from the universe of all instances, it needs `this` as an anchor — the predicate must reference the enclosing entity to establish the link. Because `where` filters an already-scoped collection, `this` would be meaningless and must not appear.
1250	
1251	- **`with`** appears in relationship declarations. The predicate defines the structural link and must reference `this`.
1252	- **`where`** appears in projections, iteration, surface context, actor identification and surface `let` bindings. The predicate filters an existing collection and must not reference `this`.
1253	
1254	```
1255	-- Surface context (where)
1256	context assignment: SlotConfirmation where interviewer = viewer
1257	
1258	-- Actor identification (where)
1259	User where role = admin
1260	
1261	-- Iteration (where)
1262	for user in Users where notification_setting.digest_enabled:
1263	
1264	-- Surface let binding (where)
1265	let comments = Comments where parent = parent and status = active
1266	```
1267	
1268	Both `with` and `where` predicates support the same expression language as `requires` clauses: field navigation (including chained), comparisons, arithmetic, boolean combinators (`and`, `or`, `not`), bare boolean expressions and `in` for set membership. `where notification_setting.digest_enabled` and `where notification_setting.digest_enabled = true` are equivalent.
1269	
1270	### Entity collections
1271	
1272	The pluralised type name refers to all instances of that entity:
1273	
1274	```
1275	for user in Users where notification_setting.digest_enabled:
1276	    ...
1277	```
1278	
1279	`Users` means all instances of `User`. Use natural English plurals: `Users`, `Documents`, `Workspaces`, `Candidacies`.
1280	
1281	Entity collections are typically used in rule-level `for` clauses and surface `let` bindings to iterate or filter across all instances of a type.

1285	## Invariants
1286	
1287	Invariants are named assertions about properties that must hold over entity state. They appear at two scopes: top-level (system-wide properties) and entity-level (properties of individual instances).
1288	
1289	### Top-level invariants
1290	
1291	Top-level invariants assert properties over entity collections. They appear in the Invariants section after Rules:
1292	
1293	```
1294	invariant NonNegativeBalance {
1295	    for account in Accounts:
1296	        account.balance >= 0
1297	}
1298	
1299	invariant NoOverlappingInterviews {
1300	    for a in Interviews:
1301	        for b in Interviews:
1302	            a != b and a.candidate = b.candidate
1303	                implies not (a.start < b.end and b.start < a.end)
1304	}
1305	
1306	invariant UniqueEmail {
1307	    for a in Users:
1308	        for b in Users:
1309	            a != b implies a.email != b.email
1310	}
1311	```
1312	
1313	Each invariant has a PascalCase name and a brace-delimited body containing an expression that evaluates to a boolean.
1314	
1315	### Entity-level invariants
1316	
1317	Entity-level invariants assert properties scoped to a single entity type. They appear inside entity declarations alongside fields, relationships and derived values:
1318	
1319	```
1320	entity Account {
1321	    balance: Decimal
1322	    credit_limit: Decimal
1323	    status: active | frozen | closed
1324	
1325	    invariant SufficientFunds {
1326	        balance >= -credit_limit
1327	    }
1328	
1329	    invariant FrozenAccountsCannotTransact {
1330	        status = frozen implies pending_transactions.count = 0
1331	    }
1332	}
1333	```
1334	
1335	Within an entity-level invariant, field names resolve to the enclosing entity's fields without qualification. `this` refers to the entity instance.
1336	
1337	### Expression language
1338	
1339	Invariant expressions use the existing expression language without extension:
1340	
1341	| Construct | Example |
1342	|-----------|---------|
1343	| Navigation | `account.balance`, `slot.interview.candidate` |
1344	| Optional navigation | `parent?.status` |
1345	| Comparisons | `balance >= 0`, `status = active`, `status in {active, pending}` |
1346	| Boolean logic | `a and b`, `a or b`, `not a`, `a implies b` |
1347	| Arithmetic | `balance + pending`, `count * rate` |
1348	| Collection operations | `slots.count`, `slots.any(s => s.status = confirmed)` |
1349	| Quantification | `for x in Collection: expression` (universal, all elements must satisfy) |
1350	| Existence | `exists entity`, `not exists entity` |
1351	| Null coalescing | `field ?? default` |
1352	| Let bindings | `let total = debit + credit` (must be pure) |
1353	
1354	`for x in Collection:` in an invariant body is a universal quantifier: the invariant holds when the expression is true for every element. This reuses the existing `for` iteration syntax with assertion semantics rather than ensures semantics. Nested quantification is permitted.
1355	
1356	### Purity constraints
1357	
1358	Invariant expressions must be pure:
1359	
1360	- **No side effects.** Invariants cannot use `.add()`, `.remove()`, `.created()` or trigger emissions.
1361	- **No `now`.** `now` is prohibited because it is volatile (re-evaluates on each read). Stored timestamp fields like `created_at` are permitted because they are stored state. The distinction is volatility, not temporality.
1362	- **`let` bindings** are permitted but must themselves be pure expressions, subject to the same restrictions.
1363	
1364	### Checking semantics
1365	
1366	Invariants are logical assertions over entity state, not runtime checks. Checking frequency and strategy are tooling concerns: PBT checks invariants after rule sequences, the model checker checks exhaustively, the trace validator checks against reconstructed state.
1367	
1368	Invariant expressions that reference `when`-qualified fields must scope their quantification to qualifying states. `for o in Orders: o.tracking_number != null` is an error if `tracking_number` carries a `when` clause, because the field does not exist in all states. Use a guard: `for o in Orders: o.status in {shipped, delivered} implies o.tracking_number != null`.
1369	
1370	### Prose-only vs expression-bearing invariants
1371	
1372	Two syntactically distinct forms exist:
1373	
1374	- `@invariant Name` (sigil prefix, followed by indented comments) — prose annotation, used in contracts
1375	- `invariant Name { expression }` (no sigil, braces) — expression-bearing, at top-level and entity-level scopes
1376	
1377	The prose annotation describes a property informally. The expression-bearing form is a machine-readable assertion that tooling can exercise. When a prose annotation is promoted to the expression-bearing form, the `@` is dropped and a `{ expr }` body is added in its place.
1378	
1379	### Recognising expressible invariants
1380	
1381	Expression-bearing invariants assert properties over entity state at a single point in time. They answer the question "given the current state of all entities, does this property hold?" Not all important properties have this shape.
1382	
1383	**Expressible** (use `invariant Name { expr }`):
1384	
1385	- Uniqueness across entity instances: "no two instances share a priority"
1386	- Relationships between fields on the same entity: "save_block = must_save implies expected_save_version != null"
1387	- Bounds on field values: "gap >= 1", "version >= 1"
1388	- Structural relationships between collections: "L1 and L2 never hold the same key", "distinct causal groups have disjoint entity key sets"
1389	- Subset and partition relationships: "processed events are a subset of group events", "processed and deferred together cover all events"
1390	
1391	The common thread: the property can be checked by reading current field values and navigating current relationships. No knowledge of history, ordering or external state is required.
1392	
1393	**Not expressible** (use prose comments or `@invariant` in contracts):
1394	
1395	- Cross-instance agreement: "all instances produce byte-identical outputs for the same input." This compares the behaviour of independent processes, not entity state.
1396	- Temporal ordering: "event 2 sees the entity state left by event 1." This is about the order in which rules executed, not a static property.
1397	- Evaluation function contracts: "the function is pure and deterministic." This constrains code behaviour, not entity state. Use `@invariant` inside a `contract` declaration.
1398	- Counterfactual properties: "if a crash occurred, recovery could reconstruct this state." This reasons about a hypothetical scenario, not the current state.
1399	- Monotonicity: "the watermark never decreases." This compares current state to prior state. A single-point-in-time invariant can assert a lower bound (`watermark >= -1`) but not that the value has not decreased since last observed.
1400	
1401	When in doubt, try writing the expression. If it requires comparing two moments in time, reasoning about what another process would do, or referencing the order in which rules fired, it belongs in prose.

1406	
1407	Reference detailed specifications defined elsewhere:

1425	
1426	Unlike black box functions, which model opaque external computations, deferred specifications represent Allium logic that is fully specified elsewhere. The deferred declaration signals that the detail exists and is maintained separately.

1443	## Config
1444	
1445	A `config` block declares configurable parameters for the specification. Each parameter has a name, type and default value.
1446	
1447	```
1448	config {
1449	    min_password_length: Integer = 12
1450	    max_login_attempts: Integer = 5
1451	    lockout_duration: Duration = 15.minutes
1452	    reset_token_expiry: Duration = 1.hour
1453	}
1454	```
1455	
1456	Rules reference config values with dot notation:
1457	
1458	```
1459	requires: length(password) >= config.min_password_length
1460	ensures: token.expires_at = now + config.reset_token_expiry
1461	```
1462	
1463	External specs declare their own config blocks. Consuming specs configure them via the qualified name:
1464	
1465	```
1466	oauth/config {
1467	    session_duration: 8.hours
1468	    link_expiry: 15.minutes
1469	}
1470	```
1471	
1472	External config values are referenced as `oauth/config.session_duration`.
1473	
1474	### Config parameter references
1475	
1476	A config parameter's default value can reference a parameter from an imported module's config block using a qualified name:
1477	
1478	```
1479	use "./core.allium" as core
1480	
1481	config {
1482	    instance_id: String                                     -- mandatory, no default
1483	    required_copies: Integer = core/config.required_copies  -- defaults to core's value
1484	    publish_delay: Duration = core/config.publish_delay     -- defaults to core's value
1485	}
1486	```
1487	
1488	The local parameter can still be overridden by any consuming module. Resolution order:
1489	
1490	1. If the consuming module sets the parameter explicitly, that value wins.
1491	2. Otherwise, the qualified reference is followed. If the referenced parameter was itself overridden, the overridden value is used.
1492	3. Otherwise, the referenced parameter's own default value is used.
1493	
1494	Chains of references resolve transitively: if A defaults to B and B defaults to C, A resolves to C's value. The checker warns on chains longer than two levels of indirection.
1495	
1496	The config reference graph must be acyclic. The checker reports an error if resolving a config default would revisit a parameter already in the resolution chain. When two modules both override the same parameter in a shared dependency (diamond dependency), the checker reports a conflict rather than silently picking one.
1497	
1498	Renaming is permitted. The local parameter name need not match the referenced parameter's name, allowing domain-appropriate vocabulary.
1499	
1500	### Expression-form config defaults
1501	
1502	Config parameter defaults can be expressions combining qualified references, local config references and literal values with arithmetic operators:
1503	
1504	```
1505	use "./core.allium" as core
1506	
1507	config {
1508	    base_timeout: Duration = core/config.base_timeout
1509	    extended_timeout: Duration = core/config.base_timeout * 2
1510	    buffer_size: Integer = core/config.batch_size + 10
1511	    retry_limit: Integer = max_attempts - 1                 -- local reference
1512	}
1513	```
1514	
1515	Operators: `+`, `-`, `*`, `/` with standard precedence. Parenthesised sub-expressions are permitted for explicit precedence (`(base + 1) * 2`). Both local and qualified references are valid in expressions. The acyclicity rule applies uniformly to both cross-module and local reference edges. Expression-form defaults are evaluated once at config resolution time, after all overrides have been applied. They are not re-evaluated dynamically.
1516	
1517	Type compatibility table for config default expressions:
1518	
1519	| Left | Operator | Right | Result |
1520	|------|----------|-------|--------|
1521	| Integer | `+` `-` `*` `/` | Integer | Integer |
1522	| Duration | `+` `-` | Duration | Duration |
1523	| Duration | `*` `/` | Integer | Duration |
1524	| Integer | `*` | Duration | Duration |
1525	| Decimal | `+` `-` `*` `/` | Decimal | Decimal |
1526	| Decimal | `*` `/` | Integer | Decimal |
1527	| Integer | `*` | Decimal | Decimal |
1528	
1529	Integer division uses truncation toward zero. All other type combinations are type errors. `Duration * Decimal` and `Decimal * Duration` are type errors; duration scaling uses Integer multipliers only. Commutative rows are listed for scalar multiplication only; addition and subtraction require matching types (Integer with Integer, Duration with Duration, Decimal with Decimal). Config default expressions are restricted to arithmetic operators and config references; boolean expressions are not permitted.
1530	
1531	For default entity instances (seed data, base configurations), use `default` declarations.

1557	
1558	### Namespaces
1559	
1560	Namespaces are prefixes that organise names. Use qualified names to reference entities and triggers from other specs:
1561	
1562	```
1563	entity Candidacy {
1564	    candidate: Candidate
1565	    authenticated_via: google-oauth/Session
1566	}
1567	```

1569	### Using other specs
1570	
1571	The `use` keyword brings in another spec with an alias:
1572	
1573	```
1574	use "github.com/allium-specs/google-oauth/abc123def" as oauth
1575	use "github.com/allium-specs/feedback-collection/def456" as feedback
1576	
1577	entity Candidacy {
1578	    authenticated_via: oauth/Session
1579	    ...
1580	}
1581	```
1582	
1583	Coordinates are immutable references (git SHAs or content hashes), not version numbers. No version resolution algorithms, no lock files. A spec is immutable once published.
1584	
1585	### Referencing external entities and triggers
1586	
1587	External specs' entities are used directly with qualified names:
1588	
1589	```
1590	rule RequestFeedback {
1591	    when: interview: Interview.slot.time.start + 5.minutes <= now
1592	    ensures: feedback/Request.created(
1593	        subject: interview,
1594	        respondents: interview.interviewers,
1595	        deadline: 24.hours
1596	    )
1597	}
1598	```
1599	
1600	### Responding to external triggers
1601	
1602	Any trigger or state transition from another spec can be responded to. No extension points need to be declared:
1603	
1604	```
1605	rule AuditLogin {
1606	    when: oauth/SessionCreated(session)
1607	    ensures: AuditLog.created(event: login, user: session.user)
1608	}
1609	
1610	rule NotifyOnFeedbackSubmitted {
1611	    when: feedback/Request.status transitions_to submitted
1612	    ensures:
1613	        for admin in Users where role = admin:
1614	            Notification.created(to: admin, template: feedback_received)
1615	}
1616	```
1617	
1618	### Configuration
1619	
1620	Imported specs expose their own config parameters. Consuming specs set values via the qualified name:
1621	
1622	```
1623	use "github.com/allium-specs/google-oauth/abc123def" as oauth
1624	
1625	oauth/config {
1626	    session_duration: 8.hours
1627	    link_expiry: 15.minutes
1628	}
1629	```
1630	
1631	Reference external config values as `oauth/config.session_duration`. This uses the same `config` mechanism as local config blocks (see [Config](#config)).
1632	
1633	### Breaking changes
1634	
1635	Avoid breaking changes: accrete (add new fields, triggers, states; never remove or rename). If a breaking change is necessary, publish under a new name rather than a new version. Consumers update at their own pace; old coordinates remain valid forever.
1636	
1637	### Local specs
1638	
1639	For specs within the same project, use relative paths:
1640	
1641	```
1642	use "./candidacy.allium" as candidacy
1643	use "./scheduling.allium" as scheduling
1644	```
1645	
1646	External entities in one spec may be internal entities in another. The boundary is determined by the `external` keyword, not by file location.

1650	## Surfaces
1651	
1652	A surface defines a contract at a boundary. A boundary exists wherever two parties interact: a user and an application, a framework and its domain modules, a service and its consumers. Each surface names the boundary and specifies what each party exposes and provides, with a `contracts:` clause for programmatic integration obligations.
1653	
1654	Surfaces serve two purposes:
1655	- **Documentation**: Capture expectations about what each party sees, must contribute and can use
1656	- **Test generation**: Generate tests that verify the implementation honours the contract
1657	
1658	Surfaces do not specify implementation details (database schemas, wire protocols, thread models, UI layout). They specify the behavioural contract both sides must honour.
1659	
1660	### Actor declarations
1661	
1662	When a surface has a specific external party, declare actor types:
1663	
1664	```
1665	actor Interviewer {
1666	    identified_by: User where role = interviewer
1667	}
1668	
1669	actor Admin {
1670	    identified_by: User where role = admin
1671	}
1672	
1673	actor AuthenticatedUser {
1674	    identified_by: User where active_sessions.count > 0
1675	}
1676	```
1677	
1678	The `identified_by` expression specifies the entity type and condition that identifies the actor. It takes the form `EntityType where condition`, where the condition uses the entity's own fields, derived values and relationships. When an actor type is used in a `facing` clause, the binding variable has the entity type from the actor's `identified_by` expression. For example, `facing viewer: Interviewer` where `Interviewer` has `identified_by: User where role = interviewer` binds `viewer` as type `User`.
1679	
1680	When an actor's identity depends on a context that varies per surface, declare the expected context type with a `within` clause and reference it in `identified_by`:
1681	
1682	```
1683	actor WorkspaceAdmin {
1684	    within: Workspace
1685	    identified_by: User where WorkspaceMembership{user: this, workspace: within}.can_admin = true
1686	}
1687	```
1688	
1689	The `within` clause declares the entity type this actor requires from the surface's `context` binding. This makes the dependency explicit: the checker can verify that any surface using this actor provides a compatible context.
1690	
1691	Two keywords are available inside `identified_by`:
1692	
1693	- `this` — the entity instance being tested (here, the User). Same semantics as `this` in entity declarations.
1694	- `within` — the entity bound by the `context` clause of the surface that uses this actor, constrained to the type declared in the actor's `within` clause.
1695	
1696	```
1697	surface WorkspaceManagement {
1698	    facing admin: WorkspaceAdmin
1699	    context workspace: Workspace    -- matches WorkspaceAdmin's within: Workspace
1700	    ...
1701	}
1702	```
1703	
1704	An actor declaration with a `within` clause can only be used in surfaces that declare a `context` clause. The surface's context type must match the actor's declared `within` type.
1705	
1706	The `facing` clause accepts either an actor type or an entity type directly. Use actor declarations when the boundary has specific identity requirements (e.g., `WorkspaceAdmin` requires admin membership). Use entity types directly when any instance of that entity can interact (e.g., `facing visitor: User` for a public-facing surface). For integration surfaces where the external party is code rather than a person, declare an actor type with a minimal `identified_by` expression rather than leaving the type undeclared.
1707	
1708	### Surface structure
1709	
1710	```
1711	surface SurfaceName {
1712	    facing party: ActorType
1713	    context item: EntityType [where predicate]
1714	    let binding = expression
1715	
1716	    exposes:
1717	        item.field [when condition]
1718	        ...
1719	
1720	    provides:
1721	        Action(party, item, ...) [when condition]
1722	        ...
1723	
1724	    contracts:
1725	        demands ContractName             -- counterpart must implement
1726	        fulfils ContractName             -- this surface supplies
1727	
1728	    @guarantee ConstraintName
1729	        -- Constraint description.
1730	
1731	    @guidance
1732	        -- Non-normative advice.
1733	
1734	    related:
1735	        OtherSurface(item.relationship) [when condition]
1736	        ...
1737	
1738	    timeout:
1739	        RuleName [when temporal_condition]
1740	}
1741	```
1742	
1743	Variable names (`party`, `item`) are user-chosen, not reserved keywords. All clauses are optional.
1744	
1745	| Clause | Purpose |
1746	|--------|---------|
1747	| `facing` | Who is on the other side of the boundary |
1748	| `context` | What entity or scope this surface applies to (one surface instance per matching entity; absent when no entity matches) |
1749	| `let` | Local bindings, same as in rules |
1750	| `exposes` | Visible data (supports `for` iteration over collections) |
1751	| `provides` | Available operations with optional when-guards (parameters are per-action inputs from the party) |
1752	| `contracts` | References to module-level `contract` declarations with direction markers. `demands ContractName` indicates the counterpart must implement; `fulfils ContractName` indicates this surface supplies |
1753	| `@guarantee` | Named constraint that must hold across the boundary (prose annotation; PascalCase name required) |
1754	| `@guidance` | Non-normative implementation advice (prose annotation; no name; must appear last) |
1755	| `related` | Associated surfaces reachable from this one; the parenthesised expression evaluates to the entity instance that the target surface's `context` clause binds to, and its type must match the target surface's context type |
1756	| `timeout` | References to temporal rules that apply within this surface's context (the rule name must correspond to a defined rule with a temporal trigger) |

1835	**Invariant annotations** — `@invariant` inside a contract is a named, scoped prose annotation about a property of the operations in that contract. It carries a PascalCase name and a prose description in indented comment lines. Invariant names must be unique within their contract.
1836	
1837	`@invariant` is distinct from `@guarantee`. `@guarantee` is a surface-level annotation about the boundary contract as a whole. `@invariant` describes a property scoped to a specific contract. The expression-bearing `invariant Name { expression }` construct (no sigil, no colon, brace-delimited body) is a separate form that appears at top-level and entity-level scopes (see [Invariants](#invariants)).
1838	
1839	**Timeout example** — a `timeout` clause references an existing temporal rule by name and binds it to the surface's context. The rule name must correspond to a rule with a temporal trigger defined elsewhere in the spec. The `when` condition is optional: include it to restate the temporal expression for readability, or omit it when the rule name is self-explanatory. When present, the checker verifies the `when` condition matches the referenced rule's trigger.
1840	
1841	```
1842	surface InvitationView {
1843	    facing recipient: Candidate
1844	
1845	    context invitation: ResourceInvitation where email = recipient.email
1846	
1847	    exposes:
1848	        invitation.resource.name
1849	        invitation.is_valid
1850	
1851	    provides:
1852	        AcceptInvitation(invitation, recipient) when invitation.is_valid
1853	
1854	    timeout:
1855	        InvitationExpires when invitation.expires_at <= now
1856	}
1857	```
1858	
1859	The rule name alone is sufficient when the temporal condition is clear from the rule's name:
1860	
1861	```
1862	    timeout:
1863	        InvitationExpires
1864	```
1865	
1866	When the `when` condition is included, it serves as inline documentation. The checker verifies it matches the referenced rule's trigger, preventing drift between the surface and the rule.

1870	## Validation rules
1871	
1872	A valid Allium specification must satisfy:
1873	
1874	**Structural validity:**
1875	1. All referenced entities and values exist (internal, external or imported)
1876	2. All entity fields have defined types
1877	3. All relationships reference valid entities (singular names) and include a backreference to `this` in their `with` predicate. `with` is used for relationship declarations and must reference `this`; `where` is used for filtering (projections, iteration, surface context, actor identification, surface `let`) and must not reference `this`
1878	4. All rules have at least one trigger and at least one ensures clause
1879	5. All triggers are valid (external stimulus, state transition, state becomes, entity creation, temporal, derived or chained)
1880	6. All rules sharing a trigger name must use the same parameter count and positional types. Parameter binding names may differ between rules. Optional parameters (typed `T?`) may be omitted at call sites; omitted optional parameters bind to `null`
1881	
1882	**State machine validity (without transition graph):**
1883	7. All status values are reachable via some rule
1884	8. All non-terminal status values have exits
1885	9. No undefined states: rules cannot set status to values not in the enum
1886	
1887	**Transition graph validity (when a `transitions` block is declared):**
1888	7a. Rules whose `ensures` clauses produce transitions not in the declared graph are errors (authoritative relationship)
1889	7b. Every non-terminal state in the graph has at least one outbound edge
1890	7c. Every declared edge in the graph is witnessed by at least one rule whose `requires`/`ensures` pair can produce that transition
1891	7d. Every enum value on the field appears in at least one edge or in the `terminal:` clause; every value in the graph exists on the field (exact correspondence)
1892	7e. Terminal states must be explicitly declared with a `terminal:` clause
1893	
1894	**State-dependent field validity (when `when` clauses are present):**
1895	7f. Every state in a `when` clause must be a valid value of the referenced status field
1896	7g. The field referenced in a `when` clause must have a `transitions` block
1897	7h. Rules transitioning into the `when` set (source state outside, target state inside) must set the field
1898	7i. Rules transitioning out of the `when` set (source state inside, target state outside) must clear the field
1899	7j. Transitions within the `when` set (both states inside) or outside it (both states outside) carry no obligation
1900	7k. Accessing a `when`-qualified field without a `requires` guard narrowing to a qualifying state is an error
1901	7l. Optional explicit `when` on derived values must match the checker's inferred intersection of input `when` sets
1902	7m. Tautological invariant (off by default, opt-in): an expression-bearing invariant whose assertion is provably true given lifecycle analysis from `when` clauses and transition reachability
1903	
1904	**Expression validity:**
1905	10. No circular dependencies in derived values
1906	11. All variables are bound before use
1907	12. Type consistency in comparisons and arithmetic
1908	13. All lambdas are explicit (use `i => i.field` not `field`)
1909	14. Inline enum fields cannot be compared with each other (whether on the same entity or across entities); use a named enum to share values across fields
1910	14a. Dot-method calls on collections must use a recognised built-in name (`.count`, `.any()`, `.all()`, `.first`, `.last`, `.unique`, `.add()`, `.remove()`). Unrecognised dot-methods are errors. Domain-specific collection operations use free-standing black box function syntax
1911	
1912	**Sum type validity:**
1913	15. Sum type discriminators use the pipe syntax with capitalised variant names (`A | B | C`)
1914	16. All names in a discriminator field must be declared as `variant X : BaseEntity`
1915	17. All variants that extend a base entity must be listed in that entity's discriminator field
1916	18. Variant-specific fields are only accessed within type guards (`requires:` or `if` branches)
1917	19. Base entities with sum type discriminators cannot be instantiated directly
1918	20. Discriminator field names are user-defined (e.g., `kind`, `node_type`), no reserved name
1919	21. The `variant` keyword is required for variant declarations
1920	
1921	**Given validity:**
1922	22. `given` bindings must reference entity types declared in the module or imported via `use`
1923	23. Each binding name must be unique within the `given` block
1924	24. Unqualified instance references in rules must resolve to a `given` binding, a `let` binding, a trigger parameter or a default entity instance
1925	
1926	**Config validity:**
1927	25. Config parameters must have explicit types. Parameters with default values must declare them explicitly (literal, qualified reference or expression). Parameters without defaults are mandatory: consuming modules must supply a value
1928	26. Config parameter names must be unique within the config block
1929	27. References to `config.field` in rules must correspond to a declared parameter in the local config block or a qualified external config (`alias/config.field`)
1930	
1931	**Surface validity:**
1932	28. Types in `facing` clauses must be either a declared `actor` type or a valid entity type (internal, external or imported)
1933	29. All fields referenced in `exposes` must be reachable from bindings declared in the surface (`facing`, `context`, `let`), via relationships, or be declared types from imported specifications
1934	30. All triggers referenced in `provides` must be defined as external stimulus triggers in rules
1935	31. All surfaces referenced in `related` must be defined, and the type of the parenthesised expression must match the target surface's `context` type
1936	32. Bindings in `facing` and `context` clauses must be used consistently throughout the surface
1937	33. `when` conditions must reference valid fields reachable from the party or context bindings
1938	34. `for` iterations must iterate over collection-typed fields or bindings and are valid in block scopes that produce per-item content (`exposes`, `provides`, `related`)
1939	35. Rule names referenced in `timeout` clauses must correspond to a defined rule with a temporal trigger. If a `when` condition is present, it must match the referenced rule's temporal trigger expression
1940	
1941	**Contract clause validity:**
1942	36. `contracts:` entries must use `demands` or `fulfils` followed by a PascalCase contract name
1943	37. Each contract name appears at most once per surface
1944	38. Referenced contract names must resolve to a `contract` declaration in scope (local or imported via `use`)
1945	39. Same-named contracts from different modules on the same surface are a structural error
1946	
1947	**Contract validity:**
1948	40. `contract` declarations must have a PascalCase name followed by a brace-delimited block body
1949	41. Contract bodies may contain only typed signatures and annotations (`@invariant`, `@guidance`)
1950	42. Types in contract signatures must be declared at module level or imported via `use`
1951	43. Contract names must be unique at module level
1952	44. `@invariant` annotations within contracts must have a PascalCase name and be followed by at least one indented comment line
1953	45. `@invariant` names must be unique within their contract
1954	
1955	**Config reference validity:**
1956	46. A qualified config reference in a default expression must resolve to a declared parameter in an imported module's config block
1957	47. The declared type of a parameter with a qualified default must match the referenced parameter's type
1958	48. The config reference graph must be acyclic
1959	
1960	**Config expression validity:**
1961	49. Expression-form config defaults must use only arithmetic operators (`+`, `-`, `*`, `/`), literal values, local config parameter references and qualified config references
1962	50. Both sides of an arithmetic operator in a config default must resolve to type-compatible operands per the type compatibility table
1963	
1964	**Invariant validity:**
1965	51. Top-level `invariant` blocks must have a PascalCase name followed by a brace-delimited expression body
1966	52. Entity-level `invariant` blocks must have a PascalCase name followed by a brace-delimited expression body
1967	53. Invariant names must be unique within their scope (module-level for top-level invariants, entity declaration for entity-level invariants)
1968	54. Invariant expressions must evaluate to a boolean type
1969	55. Invariant expressions must not contain side-effecting operations (`.add()`, `.remove()`, `.created()`, trigger emissions)
1970	56. Invariant expressions must not reference `now` (volatile; stored timestamp fields are permitted)
1971	57. Entity collection references in top-level invariants must correspond to declared entity types
1972	
1973	**Ordered collection validity:**
1974	58. `.first` and `.last` on unordered collections (`Set`) produce a warning in the current version, becoming a hard error in the next version
1975	59. Set arithmetic (`+`, `-`) on ordered collections produces unordered results. The checker reports an error if the result is used where an ordered collection is expected
1976	60. `.unique` produces an unordered `Set` regardless of the source collection's ordering
1977	
1978	**Enum literal validity:**
1979	61. Backtick-quoted enum literals must contain only printable Unicode characters (categories L, M, N, P, S) excluding backtick and whitespace
1980	62. Backtick-quoted literals are permitted only in enum declarations (named and inline), literal comparisons and `ensures` clauses; they are not permitted in identifier positions
1981	63. Backtick-quoted literals cannot appear in arithmetic expressions
1982	
1983	**Annotation validity:**
1984	64. `@invariant` requires a PascalCase name; names must be unique within their containing construct (contract or surface)
1985	65. `@guarantee` requires a PascalCase name; names must be unique within their surface
1986	66. `@guidance` must not have a name; must appear after all structural clauses and after all other annotations in its containing construct
1987	67. All annotations must be followed by at least one indented comment line; unindented comment lines after an annotation are not part of the annotation body
1988	68. Within a construct, `@invariant` and `@guarantee` annotations may appear in any order relative to each other but must appear after all structural clauses; `@guidance` must appear last
1989	
1990	The checker should warn (but not error) on:
1991	- External entities without known governing specification
1992	- Open questions
1993	- Deferred specifications without location hints
1994	- Unused entities or fields
1995	- Rules that can never fire (preconditions always false)
1996	- Temporal rules without guards against re-firing
1997	- Surfaces that reference fields not used by any rule (may indicate dead code)
1998	- Items in `provides` with `when` conditions that can never be true
1999	- Actor declarations that are never used in any surface
2000	- Rules whose ensures creates an entity for a parent, where sibling rules on the same parent don't guard against that entity's existence
2001	- Surface `provides` when-guards weaker than the corresponding rule's requires
2002	- Rules with the same trigger and overlapping preconditions (spec ambiguity)
2003	- Parameterised derived values that reference fields outside the entity (scoping violation)
2004	- Actor `identified_by` expressions that are trivially always-true or always-false
2005	- Rules where all ensures clauses are conditional and at least one execution path produces no effects
2006	- Temporal triggers on optional fields (trigger will not fire when the field is null)
2007	- Surfaces that use a raw entity type in `facing` when actor declarations exist for that entity type (may indicate a missing access restriction)
2008	- `transitions_to` triggers on values that entities can be created with (the rule will not fire on creation; consider `becomes` if the rule should also fire on creation)
2009	- Multiple fields on the same entity with identical inline enum literals (suggests extraction to a named enum; will error if the fields are later compared)
2010	- `@invariant` prose that resembles a formal expression (informational: promote to expression-bearing `invariant Name { expression }` when the assertion is machine-readable)
2011	- Config reference chains deeper than two levels of indirection
2012	- Diamond dependency conflicts in config overrides
2013	- Tautological invariant (off by default, opt-in): an expression-bearing invariant whose assertion is provably true given lifecycle analysis from `when` clauses and transition reachability
2014	- `.first` or `.last` on unordered collections (warning in current version, error in next)

2018	## Anti-patterns
2019	
2020	**Implementation leakage:**
2021	```
2022	-- Bad
2023	let request = FeedbackRequest.find(interview_id, interviewer_id)
2024	
2025	-- Good
2026	let request = FeedbackRequest{interview, interviewer}
2027	```
2028	
2029	**UI/UX in spec:**
2030	```
2031	-- Bad
2032	ensures: Button.displayed(label: "Confirm", onClick: ...)
2033	
2034	-- Good
2035	ensures: CandidateInformed(about: options_available, data: { slots: slots })
2036	```
2037	
2038	**Algorithm in rules:**
2039	```
2040	-- Bad
2041	ensures: selected = filter(take(sortBy(interviewers, load), 3), available)
2042	
2043	-- Good
2044	ensures: Suggestion.created(
2045	    interviewers: InterviewerMatching.suggest(considering: [...])
2046	)
2047	```
2048	
2049	**Queries in rules:**
2050	```
2051	-- Bad
2052	let pending = SlotConfirmation.where(slot: slot, status: pending)
2053	
2054	-- Good
2055	let pending = slot.pending_confirmations
2056	```
2057	
2058	**Implicit shorthand in lambdas:**
2059	```
2060	-- Bad
2061	interviewers.any(can_solo)
2062	
2063	-- Good
2064	interviewers.any(i => i.can_solo)
2065	```
2066	
2067	**Missing temporal guards:**
2068	```
2069	-- Bad: can fire repeatedly
2070	rule InvitationExpires {
2071	    when: invitation: Invitation.expires_at <= now
2072	    ensures: invitation.status = expired
2073	}
2074	
2075	-- Good: guard prevents re-firing
2076	rule InvitationExpires {
2077	    when: invitation: Invitation.expires_at <= now
2078	    requires: invitation.status = pending
2079	    ensures: invitation.status = expired
2080	}
2081	```
2082	
2083	**Overly broad status enums:**
2084	```
2085	-- Bad
2086	status: draft | pending | active | paused | resumed | completed |
2087	        cancelled | expired | archived | deleted
2088	
2089	-- Good
2090	status: pending | active | completed | cancelled
2091	is_archived: Boolean
2092	```
2093	
2094	**`transitions_to` doesn't fire on creation:**
2095	```
2096	-- Bad: won't fire when Interview is created with status = scheduled
2097	rule NotifyOnScheduled {
2098	    when: interview: Interview.status transitions_to scheduled
2099	    ensures: Email.created(to: interview.candidate.email, template: interview_scheduled)
2100	}
2101	
2102	-- Good: use becomes when the rule should fire regardless of how the state was reached
2103	rule NotifyOnScheduled {
2104	    when: interview: Interview.status becomes scheduled
2105	    ensures: Email.created(to: interview.candidate.email, template: interview_scheduled)
2106	}
2107	
2108	-- Also good: handle creation and transition separately when the response differs
2109	rule NotifyOnRescheduled {
2110	    when: interview: Interview.status transitions_to scheduled
2111	    ensures: Email.created(to: interview.candidate.email, template: interview_rescheduled)
2112	}
2113	
2114	rule NotifyOnCreatedScheduled {
2115	    when: interview: Interview.created
2116	    requires: interview.status = scheduled
2117	    ensures: Email.created(to: interview.candidate.email, template: interview_scheduled)
2118	}
2119	```
2120	
2121	**Magic numbers in rules:**
2122	```
2123	-- Bad
2124	requires: attempts < 3
2125	ensures: deadline = now + 48.hours
2126	
2127	-- Good
2128	requires: attempts < config.max_attempts
2129	ensures: deadline = now + config.confirmation_deadline
2130	```

2134	## Glossary
2135	
2136	| Term | Definition |
2137	|------|------------|
2138	| **Given (module)** | Entity instances a module operates on, declared with `given { ... }`; inherited by all rules in the module. Binds singleton instances at module scope. Contrast with **Context**, which is parametric |
2139	| **Context (surface)** | Parametric scope binding for a boundary contract, declared with `context` inside a surface. Creates one surface instance per matching entity. Contrast with **Given**, which binds singleton instances at module scope |
2140	| **Entity** | A domain concept with identity and lifecycle |
2141	| **Value** | Structured data without identity, compared by structure |
2142	| **Sum Type** | Entity constrained to exactly one of several variants via a discriminator field |
2143	| **Discriminator** | Field whose pipe-separated capitalised values name the variants |
2144	| **Variant** | One alternative in a sum type, declared with `variant X : Base { ... }` |
2145	| **Type Guard** | Condition (`requires:` or `if`) that narrows to a variant, unlocking its fields |
2146	| **Field** | Data stored on an entity or value |
2147	| **Relationship** | Navigation from one entity to related entities. Unordered relationships produce `Set`; ordered relationships produce `Sequence`. Declaration syntax for ordered relationships is pending |
2148	| **Projection** | A filtered view of a relationship. Preserves the ordering of the source collection: a projection of a `Sequence` is a `Sequence` |
2149	| **Sequence** | Ordered collection type that will be produced by ordered relationships and their projections when declaration syntax is introduced (pending follow-up ALP). A subtype of `Set`: assignable where an unordered collection is expected, but not the reverse. Distinct from `List<T>`, which is a compound field type declared explicitly. Ordering propagates through `where` and field extraction; set arithmetic (`+`, `-`) and `.unique` produce unordered results |
2150	| **Ordered collection** | A collection whose elements have a meaningful sequence (intrinsic order). `Sequence` and `List<T>` are the two ordered collection types. `.first`, `.last` and deterministic `for` iteration are restricted to ordered collections |
2151	| **Derived Value** | A computed value based on other fields |
2152	| **Parameterised Derived Value** | A derived value that takes arguments, e.g. `can_use_feature(f): f in plan.features` |
2153	| **Rule** | A specification of behaviour triggered by some condition |
2154	| **Trigger** | The condition that causes a rule to fire |
2155	| **Trigger Emission** | An ensures clause that emits a named event; other rules chain from it via their `when` clause |
2156	| **Precondition** | A requirement that must be true for a rule to execute |
2157	| **Postcondition** | An assertion about what becomes true after a rule executes |
2158	| **`when` clause (field)** | Clause on a field declaration tying its presence to lifecycle state: `field: Type when status = value1 \| value2`. The field is present only in the listed states. The referenced status field must have a `transitions` block. Orthogonal to `?` (genuine optionality) |
2159	| **Presence obligation** | When a rule transitions an entity into a field's `when` set (source state outside, target state inside), the rule must set the field |
2160	| **Absence obligation** | When a rule transitions an entity out of a field's `when` set (source state inside, target state outside), the rule must clear the field |
2161	| **Derived value `when` inference** | The checker infers `when` sets for derived values by intersecting the `when` sets of their inputs. Authors may optionally annotate with an explicit `when` clause, verified against the inference. The checker exports inferred `when` sets as structured data |
2162	| **Black Box Function** | Domain logic referenced but not defined in the spec; pure and deterministic. Always use free-standing call syntax, never dot-method syntax. For collection-operating functions, the collection is the first argument: `filter(events, predicate)`. Common examples include `hash()`, `verify()`, `filter()`, `grouped_by()` |
2163	| **External Entity** | An entity managed by another specification; referenced but not governed here |
2164	| **Config** | Configurable parameters for a specification, referenced via `config.field` |
2165	| **Default** | A named entity instance used as seed data or base configuration |
2166	| **Deferred Specification** | Complex logic defined in a separate file |
2167	| **Open Question** | An unresolved design decision |
2168	| **Entity Collection** | Pluralised type name referring to all instances of that entity (e.g., `Users` for all `User` instances) |
2169	| **Exists** | Keyword for checking entity existence (`exists x`) or asserting removal (`not exists x`) |
2170	| **`within`** | Clause in actor declarations that names the required context type; also a keyword in `identified_by` expressions that resolves to the surface's context entity |
2171	| **`this`** | The instance of the enclosing type; valid in entity declarations and actor `identified_by` expressions |
2172	| **Enum** | A set of values. **Named enums** (`enum Recommendation { ... }`) have type identity and are reusable across fields and entities. **Inline enums** (`status: pending \| active`) are anonymous, scoped to a single field, and cannot be compared across fields. Enum literals referencing external standards may use backtick quoting (`` `de-CH-1996` ``) to preserve the standard's canonical form; quoted and unquoted literals are distinct values with no implicit normalisation |
2173	| **Transition Graph** | An authoritative, opt-in declaration of valid lifecycle transitions for an enum status field. Declared inside the entity body with `transitions field_name { ... }` using `->` edge notation and a `terminal:` clause. When present, rules producing transitions not in the graph are validation errors. Entities without a graph derive transition validity from rules alone |
2174	| **Discard Binding** | `_` used where a binding is syntactically required but the value is not needed |
2175	| **Actor** | An entity type that can interact with surfaces, declared with explicit identity mapping |
2176	| **`facing`** | Surface clause naming the external party on the other side of the boundary |
2177	| **Surface** | A boundary contract between two parties specifying what each side exposes and provides, with optional `contracts:` clause for programmatic integration obligations |
2178	| **Contract** | A named, direction-agnostic obligation declared at module level with `contract Name { ... }`. Surfaces reference contracts in a `contracts:` clause with `demands`/`fulfils` direction markers. Identity determined by module-qualified name |
2179	| **`demands`** | Direction marker in a `contracts:` clause indicating the counterpart must implement this contract |
2180	| **`fulfils`** | Direction marker in a `contracts:` clause indicating this surface supplies the contract's operations |
2181	| **Invariant** | A named, scoped assertion about a property. Two syntactic forms: `@invariant Name` (prose annotation, in contracts) and `invariant Name { expression }` (expression-bearing, at top-level and entity-level). Expression-bearing invariants are logical assertions over entity state, not runtime checks. Distinct from `@guarantee`, which annotates properties of the boundary as a whole |
2182	| **`@guarantee`** | Named prose annotation on a surface asserting a property of the boundary as a whole. PascalCase name required, unique within the surface. Structurally validated by the checker; prose content is not evaluated. Distinct from `@invariant` (scoped to a contract) and expression-bearing `invariant Name { }` (machine-readable) |
2183	| **`@guidance`** | Unnamed prose annotation providing non-normative implementation advice. Permitted in contracts, rules and surfaces. Must appear after all structural clauses and after all other annotations in its containing construct. Structurally validated; prose content is not evaluated |
2184	| **`implies`** | Boolean operator. `a implies b` is `not a or b`. Lowest boolean precedence, binding looser than `and` and `or`. Available in all expression contexts |

4. **QA-GL-10** — "play until game over" is not concrete enough; links to other checks but doesn't stand alone.
5. Missing: a check that **R is ignored in waiting phase** (covered by Gherkin-9 but missing from QA).
6. Missing: explicit **observable state** after game over — which keys are accepted and which are not.
