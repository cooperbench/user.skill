91	    if a.is_empty() && b.is_empty() {

93	    }

95	    let set_b: HashSet<u64> = b.iter().copied().collect();

Clear picture now. Two root causes:

**1. Single-threaded file walk + parse** (`scan.rs:164-168`)
The `for entry in walker` loop is sequential. 2,701 Python files (after `__pycache__`/`.venv` are excluded) are all parsed one-by-one on one core.

**2. O(n²) Jaccard comparison with per-pair HashSet allocation** (`core.rs:144-154`)
`find_duplicate_pairs` does a nested double-loop. For every pair, `jaccard()` allocates two `HashSet<u64>` from scratch. With ~2,700 files × maybe 20 qualifying functions each = ~54,000 candidates → **54,000² / 2 ≈ 1.4 billion** comparisons. Even at nanoseconds each, this dominates. The 95% CPU / 161 seconds confirms it's all compute on one thread.

Three fixes in priority order:

| Fix | Effort | Expected impact |
|-----|--------|-----------------|
| Parallelize `find_duplicate_pairs` outer loop with `rayon::par_iter` | Low — add `rayon` dep, one `par_iter` call | ~8–12× on 8-core machine |
| Replace per-pair `HashSet` allocation in `jaccard()` with sorted-slice merge | Medium — pre-sort `node_hashes`, two-pointer merge | ~5× (eliminates heap alloc per comparison) |
| Parallelize file walk with `WalkBuilder::build_parallel()` | Medium — restructure collection loop | ~4× on I/O side (likely minor vs compare) |

The comparison phase is almost certainly the bottleneck (O(n²) with allocations), so fixing that first is the right call. Want me to implement the Rayon parallelization of `find_duplicate_pairs` and the sorted-slice Jaccard optimization?
