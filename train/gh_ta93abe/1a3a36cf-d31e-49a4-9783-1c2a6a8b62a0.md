# Cloudflare Sandbox SDK (ベータ版)について

## 概要
Cloudflare Sandboxは、「untrusted codeを安全に隔離された環境で実行できるSDK」です。Containersをベースに構築されており、Workers アプリケーションからコマンド実行、ファイル管理、バックグラウンドプロセス、サービス公開が可能です。

## 主な機能

**コード実行**
Python、JavaScriptなどのコードを直接実行でき、チャートやテーブルなどのリッチな出力をサポートします。

**コマンド実行**
シェルコマンドやPythonスクリプト、Node.jsアプリケーションをストリーミング出力対応で実行できます。

**ファイル操作**
サンドボックス内のファイルシステムの読み書きや、バックグラウンドプロセスの管理が可能です。

**ファイル監視**
ファイル変更をリアルタイムで検出し、ホットリロードやビルド自動化に活用できます。

**ターミナルアクセス**
WebSocket経由でブラウザベースのターミナルをサンドボックスシェルに直接接続できます。

**プレビューURL**
サンドボックス内で実行するHTTPサービスを自動生成されたURLで公開できます。

## 利用可能環境
Workers有料プランで利用可能です。各サンドボックスは独立したLinuxコンテナで動作し、強力なセキュリティ境界を提供しながらパフォーマンスを維持します。

## ユースケース

- **AI コード実行**：LLMが生成したコードを安全に実行。Workers AIとの統合で関数呼び出しに対応
- **データ分析**：pandas、NumPyを使用した対話的な分析環境
- **開発環境**：クラウドIDE、コーディング練習環境の構築
- **CI/CD**：テスト実行、コンパイル、ビルドパイプラインの隔離実行

## ContainersとSandboxの関係
SandboxはContainersを基盤技術として活用しており、シンプルなAPIで安全なコード実行環境を提供する上位レイヤーの位置付けです。

## Sandbox vs Containers

| 観点 | Sandbox | Containers |
|------|---------|------------|

| **コード実行** | SDK 経由で直接コマンド実行可能 | 自前で Dockerfile を書く |
| **ファイル操作** | API でファイル読み書きできる | 自前で実装 |
| **セットアップ** | シンプル | Dockerfile + ルーティング等を自前構築 |
| **ステータス** | ベータ | GA |

## dbt × Sandbox の組み合わせ

Sandbox なら Worker から直接こういう操作ができます:

```

  → Sandbox 起動
  → R2 から前回の target/ をファイル書き込み

  → Sandbox 停止

## Implementation Plan: sandbox-dbt Worker

Below is a comprehensive design for a Cloudflare Worker that executes the `transform/core` dbt project inside a Cloudflare Sandbox container, stores artifacts in R2, and exposes API/Cron triggers.

---

### 1. Design Decisions

**dbt project file placement: Method A (Dockerfile COPY)**

The entire `transform/core` directory is small (seeds total ~89 lines of CSV, ~20 SQL model files, YAML configs). Baking it into the Docker image via `COPY` provides the fastest cold-start time and eliminates the need to transfer files at runtime. When the dbt project changes, a new image is built and deployed alongside the Worker -- which is the natural git-driven workflow already used for Workers deployment.

**Python dependencies: Method A (pre-installed in Dockerfile)**

`dbt-duckdb`, `elementary-data`, and `dbt-osmosis` plus their transitive dependencies are large. Installing them at runtime would take 60-120+ seconds. Pre-installing via `pip install` in the Dockerfile yields a container that is ready to run `dbt` in seconds.

**profiles.yml target: `ci` (in-memory DuckDB)**

The `ci` target uses `:memory:` which is ideal for a stateless Sandbox execution. No persistent DuckDB file needs to be managed. The dbt artifacts (manifest, run_results, compiled SQL) and logs are uploaded to R2 after execution. If later we need persistence, we can switch to the `prod` target with a file path and persist the .duckdb file to R2.

**R2 access from Sandbox**: R2 credentials (endpoint, access key, secret key) are passed as environment variables to the Sandbox process via `startProcess` or `exec` with `env` option. The `profiles.yml` already reads these from env vars via Jinja (`env_var('R2_ENDPOINT', '')`), so no profile changes are needed.

│  Worker         │     │  (Container)               │     │ data-lake│
│                 │     │                            │     │          │
│ 1. getSandbox() ├────>│  Container starts          │     │          │
│                 │     │                            │     │          │
│ 2. exec(dbt..)  ├────>│  dbt seed/run/test         │     │          │
│    env: R2_*    │     │  ├─ DuckDB :memory:        │     │          │
│                 │     │  └─ httpfs → R2 ──────────>├────>│ read/    │
│                 │     │                            │     │ write    │
│ 3. readFile()   │<────┤  target/manifest.json      │     │ parquet  │
│    readFile()   │<────┤  target/run_results.json   │     │          │
│    readFile()   │<────┤  logs/dbt.log              │     │          │
│                 │     │                            │     │          │
│ 4. R2.put()     ├────────────────────────────────────────>│ artifacts│
│                 │     │                            │     │          │
└─────────────────┘     └───────────────────────────┘     └──────────┘
```

Flow details:
1. Worker acquires a sandbox instance via `getSandbox(env.SANDBOX, 'dbt-runner')`
2. Worker calls `sandbox.exec()` with R2 credentials as env vars. The dbt `profiles.yml` already uses `env_var()` Jinja to read these
3. dbt runs inside the container using DuckDB in-memory mode. DuckDB's `httpfs` extension can read/write parquet files from R2 via S3 API
4. After dbt completes, the Worker reads artifact files from the sandbox via `sandbox.readFile()` and uploads them to R2 via the `R2_ARTIFACTS` binding

### 8. Core Service Implementation (dbt-runner.ts)

Pseudocode for the main execution logic:

```typescript
import { getSandbox } from "@cloudflare/sandbox";

export async function runDbt(env: Env, commands: string[] = ["seed", "run", "test"]): Promise<DbtRunResult> {
  const runId = new Date().toISOString().replace(/[:.]/g, "-");
  const sandbox = getSandbox(env.SANDBOX, "dbt-runner");

  const r2Env = {
    R2_ENDPOINT: env.R2_ENDPOINT,
    R2_ACCESS_KEY_ID: env.R2_ACCESS_KEY_ID,
    R2_SECRET_ACCESS_KEY: env.R2_SECRET_ACCESS_KEY,
  };

  const results: CommandResult[] = [];

  for (const cmd of commands) {
    const start = Date.now();
    const result = await sandbox.exec(`dbt ${cmd} --profiles-dir . --target ci`, {
      // Note: cwd and env may need to be passed differently
      // depending on final SDK API surface
    });
    results.push({
      command: `dbt ${cmd}`,
      success: result.success,
      exitCode: result.exitCode,
      stdout: result.stdout,
      stderr: result.stderr,
      durationMs: Date.now() - start,
    });

    if (!result.success) break; // Stop on failure
  }

  // Read artifacts from sandbox
  const artifacts = await readArtifacts(sandbox);

  // Upload to R2
  await uploadArtifacts(env.R2_ARTIFACTS, runId, artifacts);

  return { runId, commands: results, success: results.every(r => r.success), artifacts: /* keys */ };
}
```

Important note on `exec` env vars: The Sandbox SDK `exec()` does not directly support `env` in its options (that is `startProcess`'s capability). The recommended approach is either:
- Set env vars during `startProcess` and then interact with the running process, or
- Write a shell wrapper script that exports the env vars before calling dbt, or
- Write a `.env` file and source it: `sandbox.exec("export R2_ENDPOINT=... && dbt run ...")`

The simplest approach is to inline the env vars in the exec command string:
```typescript
const envPrefix = `R2_ENDPOINT=${env.R2_ENDPOINT} R2_ACCESS_KEY_ID=${env.R2_ACCESS_KEY_ID} R2_SECRET_ACCESS_KEY=${env.R2_SECRET_ACCESS_KEY}`;
await sandbox.exec(`${envPrefix} dbt run --profiles-dir . --target ci`);
```

### 10. Keeping dbt-project in Sync

There are two strategies:

**Strategy A (Recommended): Build-time copy script**
Add a `prebuild` script in `package.json` that copies `../transform/core` into `./dbt-project/` before Docker build. This keeps a single source of truth in `transform/core`.

```json
{
  "scripts": {
    "prebuild": "rsync -av --exclude='target' --exclude='dbt_packages' --exclude='dev.duckdb' --exclude='prod.duckdb' --exclude='logs' --exclude='.venv' ../transform/core/ ./dbt-project/",
    "build": "echo 'dbt-project synced'",
    "dev": "pnpm prebuild && wrangler dev",
    "deploy": "pnpm prebuild && wrangler deploy --minify"
  }
}
```

**Strategy B: Git submodule or shared directory**
Reference `transform/core` via a relative Dockerfile `COPY` path. This requires the Docker build context to include the parent directory, which complicates the build.

Strategy A is simpler and more explicit.

### 12. Potential Challenges

| Challenge | Mitigation |
|-----------|-----------|
| **Sandbox cold start time** | Pre-installing dbt in Docker image minimizes startup. The container stays warm for subsequent calls if using the same sandbox ID |
| **dbt deps network access** | Run `dbt deps` at Docker build time. No network call needed at runtime |
| **Large stdout from dbt** | Truncate or stream stdout. Store full logs in R2 |
| **Sandbox exec timeout** | dbt run on this small project should complete in <30s. Set explicit timeout on `exec()` |
| **R2 credentials in exec** | Pass as inline env vars in command string. Avoid writing credentials to files |
| **dbt-project sync drift** | The `prebuild` rsync script ensures sync at build/deploy time. CI can validate this |
| **Container image size** | dbt-duckdb pulls in many Python packages. Consider using `uv` instead of `pip` in Dockerfile for faster install. Exclude dbt-snowflake |
