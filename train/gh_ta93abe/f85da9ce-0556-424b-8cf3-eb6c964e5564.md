# Catalog-Linked Database は `EXTERNAL_VOLUME` を **1 つだけ** 参照する `LINKED_CATALOG` に複数 Volume を紐づける構文は存在しないので、**どちらか 1 つを選ぶ**必要があります。整理すると以下のパターン: ## パターン A: 書き込み用 Volume 1 本に寄せる（シンプル・推奨） `ALLOW_WRITES = TRUE` の Volume は **読み取りにも問題なく使える**（書き込み "も" できるだけ）。実際の読み書き制御は `ALLOWED_WRITE_OPERATIONS` で Snowflake 側に寄せる。 ```sql CREATE DATABASE r2_lakehouse LINKED_CATALOG = ( CATALOG = 'r2_data_catalog_lake', ALLOWED_WRITE_OPERATIONS = ALL -- 書き込みを許可 ) EXTERNAL_VOLUME = 'ext_vol_r2_rw'; ``` - 読み取り専用で運用したい時期は `ALLOWED_WRITE_OPERATIONS = NONE` に `ALTER` で切り替えるだけ。 - 読み取り専用 Volume (`ext_vol_r2`) はこの DB には不要になる（削除するか、別用途に残す）。 > ✅ **通常はこのパターンで OK**。2 種類の Volume を持っておく意味はあまり出ない。 ## パターン B: 読み取り専用 Volume に固定する（安全寄り） 「Snowflake から書かれると困る」ことを物理的に担保したい場合。 ```sql CREATE DATABASE r2_lakehouse LINKED_CATALOG = ( CATALOG = 'r2_data_catalog_lake', ALLOWED_WRITE_OPERATIONS = NONE -- 明示（デフォルトも NONE） ) EXTERNAL_VOLUME = 'ext_vol_r2'; -- ALLOW_WRITES = FALSE の方 ``` - 仮に誰かが `ALTER DATABASE ... SET LINKED_CATALOG = (ALLOWED_WRITE_OPERATIONS = ALL)` したとしても、**Volume 側が `ALLOW_WRITES = FALSE` なので実データ書き込みで失敗する**（二段構えの防御）。 - 書き込みが必要になったら `EXTERNAL_VOLUME` を `ext_vol_r2_rw` に貼り替える。 ## パターン C: 読み書きを DB レベルで分離する（オーバーキル気味） 同じ R2 catalog に対して **2 つの linked DB** を作り、用途で使い分ける: ```sql -- 読み取り専用 DB（BI / アナリストに GRANT） CREATE DATABASE r2_lakehouse_ro LINKED_CATALOG = (CATALOG = 'r2_data_catalog_lake') EXTERNAL_VOLUME = 'ext_vol_r2'; -- 書き込み可能 DB（ETL サービスアカウント用） CREATE DATABASE r2_lakehouse_rw LINKED_CATALOG = ( CATALOG = 'r2_data_catalog_lake', ALLOWED_WRITE_OPERATIONS = ALL ) EXTERNAL_VOLUME = 'ext_vol_r2_rw'; ``` - 同じテーブルが `r2_lakehouse_ro.raw.events` と `r2_lakehouse_rw.raw.events` の両方で見える。 - Snowflake RBAC で DB 単位に GRANT を分けられるので、**書き込みロール分離**をガッチリやりたい時に有効。 - ただし運用コスト（命名・権限・dbt プロジェクトの参照先）が倍になる。 ## 選び方の目安 | 状況 | 推奨 | |---|---| | とりあえず書き込みも試したい | **A**（rw Volume 1 本） | | ほぼ読み取り、誤書き込みを物理的に止めたい | **B**（ro Volume 1 本） | | 役割ごとに権限分離を徹底したい・監査要件がある | **C**（DB を 2 本） | | `ALLOW_WRITES` を途中で切り替えたい | Volume は **2 本残しておき `ALTER DATABASE SET EXTERNAL_VOLUME` で付け替える**運用も可 | --- 使い分けのイメージは湧きましたか？ どのパターンで進めるか決まれば、実際の DDL を Step 3 用に組みます。

それ、まさに `CATALOG_CASE_SENSITIVITY` の出番です。 ## 原因 Snowflake はデフォルトで **未クォートの識別子を大文字化**してマッチングするため、R2 側の `raw.events`（小文字）を探しても `RAW.EVENTS` と突き合わせて見つからず、ダブルクォートで強制的に小文字指定する羽目になります。 ## 解決: `CATALOG_CASE_SENSITIVITY = CASE_INSENSITIVE` Catalog-Linked DB にこのオプションを付けると、**Snowflake 側の未クォート識別子（大文字扱い）と R2 側の小文字名を自動で突き合わせてくれる**ので、以下のように書けるようになります: ```sql -- Before（今の状態） SELECT * FROM r2_lakehouse."raw"."events"; -- After（CASE_INSENSITIVE 適用後） SELECT * FROM r2_lakehouse.raw.events; ``` ## 適用方法 ### 既存 DB に `ALTER` で付ける ```sql ALTER DATABASE r2_lakehouse SET CATALOG_CASE_SENSITIVITY = CASE_INSENSITIVE; ``` ### `ALTER` が通らない場合は作り直し Catalog-Linked DB 内にはユーザデータが持たれていない（全て R2 側）ので、`CREATE OR REPLACE` しても **データは失われません**。紐づいているのはメタデータキャッシュだけ。 ```sql CREATE OR REPLACE DATABASE r2_lakehouse LINKED_CATALOG = ( CATALOG = 'r2_data_catalog_lake', SYNC_INTERVAL_SECONDS = 60 -- 元の設定も全部ここに書き直す ) EXTERNAL_VOLUME = 'ext_vol_r2_rw' CATALOG_CASE_SENSITIVITY = CASE_INSENSITIVE; ``` > ⚠️ 注意点: > - この DB に対して発行済みの **GRANT は OR REPLACE で消える**ので、権限設定していたなら再付与が必要 > - dbt プロジェクトから参照している場合、プロジェクト側は変更不要（クォートを外せるだけ） ## 動作確認 ```sql -- クォートなしで引けることを確認 SELECT * FROM r2_lakehouse.raw.events LIMIT 1; -- SHOW でも小文字の schema/table 名が出るようになる（表示は大文字のままだが引ける） SHOW ICEBERG TABLES IN SCHEMA r2_lakehouse.raw; ``` ## ついでの補足 - **dbt を通す予定があるなら CASE_INSENSITIVE 必須級**。dbt は小文字識別子を前提に SQL を生成するので、CASE_SENSITIVE のままだと `"my_model"` と `MY_MODEL` の不一致であちこち壊れます（dbt-labs/dbt-core #12073 でも報告されている既知問題）。 - R2 側を小文字で作ったのは **むしろ正しい選択**。Iceberg コミュニティ全般（Spark, Trino, PyIceberg, dbt）が小文字前提なので、大文字で作ると他のツールとの相性で逆に苦しみます。 --- `ALTER` でサクッと切り替わるか試してみてください。もし `Unsupported alter operation` 的なエラーで弾かれたら `CREATE OR REPLACE` に倒しましょう。
