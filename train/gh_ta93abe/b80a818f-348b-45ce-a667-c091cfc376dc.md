# Plan: transform/core を Cloudflare Sandbox で実行する Worker

## Context

transform/core（dbt + DuckDB）は現在ローカルや CI で `uv run dbt run` として実行している。これを Cloudflare Sandbox 上で実行する Worker を作ることで、API/Cron トリガーで dbt パイプラインを Cloudflare 内で完結させる。成果物は R2 に保存する。

## 設計判断

| 判断 | 選択 | 理由 |
|------|------|------|
| dbt プロジェクトの配置 | Dockerfile に COPY | プロジェクトは小さい（seeds ~4KB×5, models ~20ファイル）。起動が最速 |
| Python 依存関係 | Dockerfile で事前 install | dbt-duckdb 等は重い。実行時 install だと 60s+ かかる |
| profiles.yml ターゲット | `ci`（:memory:） | ステートレス実行。永続化不要。成果物は R2 へ |
| dbt-project の同期 | prebuild スクリプトで rsync | transform/core を単一ソースに保つ |

## ディレクトリ構成

```
sandbox-dbt/
├── Dockerfile                  # cloudflare/sandbox ベース + dbt 事前 install
├── dbt-project/                # transform/core のコピー（build 時に rsync）
├── src/
│   ├── index.ts                # Hono app: API + scheduled handler
│   ├── types.ts                # Env bindings, 結果型
│   └── services/
│       ├── dbt-runner.ts       # Sandbox で dbt 実行するコアロジック
│       └── r2-artifacts.ts     # R2 への成果物アップロード/取得
├── wrangler.jsonc
├── package.json
├── tsconfig.json
├── vitest.config.ts
└── biome.json
```

## 主要ファイルの設計

### Dockerfile

```dockerfile
FROM docker.io/cloudflare/sandbox:0.3.3

RUN apt-get update && apt-get install -y python3-pip && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir \
    "dbt-duckdb>=1.9.0" \
    "elementary-data>=0.16.1"

COPY dbt-project/ /workspace/dbt/
WORKDIR /workspace/dbt
RUN dbt deps --profiles-dir . --target ci
```

### API エンドポイント

| Method | Path | 説明 |
|--------|------|------|
| GET | /health | ヘルスチェック |
| POST | /run | dbt 実行（seed + run + test） |
| POST | /run?command=seed\|run\|test | 個別コマンド実行 |
| GET | /runs | 実行履歴一覧（R2 から） |
| GET | /runs/:runId | 実行結果詳細 |

### dbt-runner.ts の実行フロー

```
1. getSandbox(env.SANDBOX, 'dbt-runner')
2. sandbox.writeFile('/workspace/dbt/.env', 'R2_ENDPOINT=...\n...')
3. sandbox.exec('set -a && source /workspace/dbt/.env && dbt seed --profiles-dir . --target ci')
4. sandbox.exec('set -a && source /workspace/dbt/.env && dbt run --profiles-dir . --target ci')
5. sandbox.exec('set -a && source /workspace/dbt/.env && dbt test --profiles-dir . --target ci')
6. sandbox.readFile('/workspace/dbt/target/manifest.json')
7. sandbox.readFile('/workspace/dbt/target/run_results.json')
8. sandbox.readFile('/workspace/dbt/logs/dbt.log')
9. env.R2_ARTIFACTS.put('runs/{runId}/manifest.json', ...)
```

R2 認証情報は `.env` ファイルとして Sandbox に書き込み、`source` で読み込む。profiles.yml の `env_var()` Jinja がそのまま機能する。

### package.json scripts

```json
{
  "prebuild": "rsync -av --exclude='target' --exclude='dbt_packages' --exclude='*.duckdb' --exclude='logs' --exclude='.venv' ../transform/core/ ./dbt-project/",
  "dev": "pnpm prebuild && wrangler dev",
  "deploy": "pnpm prebuild && wrangler deploy --minify"
}
```

import { getSandbox, proxyToSandbox, type Sandbox } from "@cloudflare/sandbox";


export { Sandbox } from "@cloudflare/sandbox";


type Env = {

  Sandbox: DurableObjectNamespace<Sandbox>;

};


export default {

  async fetch(request: Request, env: Env): Promise<Response> {

    const url = new URL(request.url);


    // Get or create a sandbox instance

    const sandbox = getSandbox(env.Sandbox, "my-sandbox");


    // Execute Python code

    if (url.pathname === "/run") {

      const result = await sandbox.exec('python3 -c "print(2 + 2)"');

      return Response.json({

        output: result.stdout,

        error: result.stderr,

        exitCode: result.exitCode,

        success: result.success,

      });

    }


    // Work with files

    if (url.pathname === "/file") {

      await sandbox.writeFile("/workspace/hello.txt", "Hello, Sandbox!");

      const file = await sandbox.readFile("/workspace/hello.txt");

      return Response.json({

        content: file.content,

      });

    }


    return new Response("Try /run or /file");

  },

};


```

**Key concepts**:

* `getSandbox()` \- Gets or creates a sandbox instance by ID. Use the same ID to reuse the same sandbox instance across requests.
* `sandbox.exec()` \- Execute shell commands in the sandbox and capture stdout, stderr, and exit codes.
* `sandbox.writeFile()` / `readFile()` \- Write and read files in the sandbox filesystem.

## Best practices

* **Check exit codes** \- Always verify `result.success` and `result.exitCode`
* **Validate inputs** \- Escape or validate user inpu
**Execution error** \- Command couldn't start (throws exception)

try {

  const result = await sandbox.exec("python analyze.py");


  if (!result.success) {

    // Command failed (non-zero exit code)

    console.error("Analysis failed:", result.stderr);

    console.log("Exit code:", result.exitCode);


    // Handle specific exit codes

    if (result.exitCode === 1) {

      throw new Error("Invalid input data");

    } else if (result.exitCode === 2) {

      throw new Error("Missing dependencies");

    }

  }


  // Success - process output

  return JSON.parse(result.stdout);

} catch (error) {

  // Execution error (couldn't start command)

  throw error;

}

Sandboxes are ideal for building AI agents that need to execute code, interactive development environments, data analysis platforms, CI/CD systems, and any application that needs secure code execution at the edge. With Sandbox, you can execute Python scripts, run Node.js applications, analyze data, compile code, and perform complex computations — all with a simple TypeScript API and no infrastructure to manage.

Sandbox state exists only while the container is active. Understanding this is critical for building reliable applications.

**While the container is active** (typically minutes to hours of activity):

* Files written to `/workspace`, `/tmp`, `/home` remain available
* Background processes continue running
* Shell sessions maintain their working directory and environment
* Code interpreter contexts retain variables and imports

**When the container stops** (due to inactivity or explicit destruction):

* All files are deleted
* All processes terminate
* All shell state resets
* All code interpreter contexts are cleared

The next request creates a fresh container with a clean environment.

## Naming strategies

### Per-user sandboxes

TypeScript

```

const sandbox = getSandbox(env.Sandbox, `user-${userId}`);


```

User's work persists while actively using the sandbox. Good for interactive environments, playgrounds, and notebooks where users work continuously.

### Per-session sandboxes

TypeScript

```

const sessionId = `session-${Date.now()}-${Math.random()}`;

const sandbox = getSandbox(env.Sandbox, sessionId);

// Later:

await sandbox.destroy();


```

Fresh environment each time. Good for one-time execution, CI/CD, and isolated tests.

### Per-task sandboxes

TypeScript

```

const sandbox = getSandbox(env.Sandbox, `build-${repoName}-${commit}`);


```

Idempotent operations with clear task-to-sandbox mapping. Good for builds, pipelines, and background jobs.

## Request routing

The first request to a sandbox determines its geographic location. Subsequent requests route to the same location.

**For global apps**:

* Option 1: Multiple sandboxes per user with region suffix (`user-123-us`, `user-123-eu`)
* Option 2: Single sandbox per user (simpler, but some users see higher latency)

## Container isolation

Each sandbox runs in a separate VM, providing complete isolation:

* **Filesystem isolation** \- Sandboxes cannot access other sandboxes' files
* **Process isolation** \- Processes in one sandbox cannot see or affect others
* **Network isolation** \- Sandboxes have separate network stacks
* **Resource limits** \- CPU, memory, and disk quotas are enforced per sandbox

For complete security details about the underlying container platform, see [Containers architecture](/containers/platform-details/architecture/).

## Within a sandbox

All code within a single sandbox shares resources:

* **Filesystem** \- All processes see the same files
* **Processes** \- All sessions can see all processes
* **Network** \- Processes can communicate via localhost

For complete isolation, use separate sandboxes per user:

TypeScript

```

// Good - Each user in separate sandbox

const userSandbox = getSandbox(env.Sandbox, `user-${userId}`);


// Bad - Users sharing one sandbox

const shared = getSandbox(env.Sandbox, 'shared');

// Users can read each other's files!


```

### 1. DuckDB 対応: ○ → ◎

**課題**: コンテナのメモリ/ディスク制限で大規模データ処理が不安

**ソリューション**: **dbt のモデルを Parquet on R2 で完結させる設計にする**

- seeds は小さい CSV（現状 ~4KB×5）→ 問題なし
- marts の materialization を `external` (dbt-duckdb の `write_to_source` / Parquet export) にして、結果を R2 に直接書き出す
- DuckDB の `:memory:` モードでも httpfs 経由で R2 上の Parquet を直接 scan できるので、コンテナのディスクに依存しない
- → コンテナはあくまで計算エンジン、永続データは R2

---

### 2. セットアップ容易性: ○ → ◎

**課題**: prebuild rsync + Dockerfile が独自手順、新メンバーが迷う

**ソリューション**: **`wrangler dev` 一発で動く状態にする**

- `pnpm dev` が `prebuild && wrangler dev` を実行（実装済み）
- `Makefile` or `justfile` をルートに追加して `just sandbox-dev` で起動
- dbt-project/ が無くても prebuild が自動で作る（冪等）
- → 実質「clone → `pnpm install` → `pnpm dev`」で動く。これは ◎ に近い

---

### 3. 安定性: △ → ◎

**課題**: ベータ版。API 変更リスクが最大の懸念

**ソリューション**: **GitHub Actions フォールバック + Adapter パターン**

```
src/services/
├── dbt-runner.ts          # インターフェース（共通型）
├── sandbox-runner.ts      # Sandbox 実装
└── github-actions-runner.ts  # GA フォールバック（workflow_dispatch）
```

- `dbt-runner.ts` を interface として抽出
- Sandbox がダウン/API 変更時は GitHub Actions にフォールバック
- 環境変数 `DBT_RUNNER=sandbox|github-actions` で切替
- Sandbox が GA になったらフォールバック削除
- **Sandbox の API 変更は sandbox-runner.ts だけの修正で済む**

さらに:
- `@cloudflare/sandbox` のバージョンを `package.json` で固定（`^` ではなく exact）
- Wrangler の compatibility_date で動作バージョンを固定

### 4. コスト: ? → ◎

**課題**: 料金が未確定で予算計画が立てられない

**ソリューション**: **コスト上限を設計で担保する**

- **実行頻度の制御**: Cron を 1日1回に限定（現状 `0 2 * * *`）
- **コンテナ寿命の最小化**: 実行後即 `destroy()`（実装済み）
- **R2 の成果物にTTL**: 古い run 結果を自動削除する lifecycle rule
- **実行時間の監視**: Workers Analytics で実行時間を記録し、異常を検知
- **月間実行数の上限**: API に rate limit を追加（例: 10回/日）

```typescript
// index.ts に追加
app.post("/run", async (c) => {
  const todayRuns = await countTodayRuns(c.env.R2_ARTIFACTS);
  if (todayRuns >= 10) {
    return c.json({ error: "Daily run limit reached" }, 429);
  }
  // ...
});
```

GA 時の料金が判明したら、この設計で月額上限を計算できる。

### 5. 運用負荷: ○ → ◎

**課題**: 障害時の切り分けが難しい、手動復旧が必要

**ソリューション**: **構造化ログ + 自動リトライ + アラート**

- **構造化ログ**: Workers Observability に JSON ログを出力
  ```typescript
  console.log(JSON.stringify({ event: "dbt_run_start", runId, commands }));
  ```
- **自動リトライ**: Sandbox の exec 失敗時に1回だけリトライ（一時的なコンテナ起動失敗対策）
- **アラート**: 失敗時に通知（Workers Observability のアラート or Webhook → Slack）
- **ヘルスチェック**: `/health` で Sandbox の起動可否もチェック
- → 「何もしなくても動く、壊れたら通知が来る」状態

### 6. 観測可能性: ○ → ◎

**課題**: コンテナ内のログが stdout/stderr 経由のみ

- **manifest.json からリネージ**: モデル依存関係を抽出して R2 に保存
- **dbt.log を完全保存**: デバッグ用に R2 に保存（実装済み）
- **カスタムダッシュボード**: `/runs/:runId` のレスポンスに解析済みメトリクスを追加

```typescript

  status: "success" | "error" | "skipped";

marts を **R2 Parquet 直接書き出し** にする。DuckDB の `COPY TO` で httpfs 経由で R2 に書けるので、コンテナのディスク/メモリに成果物が残らない。コンテナは純粋な計算エンジンになり、リソース制限の影響が最小化される。

**`run_results.json` の解析**。dbt は実行結果を構造化 JSON で出力するので、それをパースしてモデル別の成否・実行時間・行数を `/runs/:runId` のレスポンスに含める。生ログを見に行く必要がなくなる。

   342→## 4. R2 SQL
   343→
   344→### 4.1 概要
   345→
   346→R2 SQLは、R2 Data Catalogに保存されたApache Icebergテーブルに対してSQLクエリを実行するサーバーレスの分散クエリエンジンです。ペタバイトスケールのデータセットを効率的に処理します。
   347→
   348→### 4.2 分散クエリアーキテクチャ
   349→
   350→R2 SQLは、I/O最適化とコンピュート分散の2つの課題に対応する高度なアーキテクチャを採用しています。
   351→
   352→```
   353→[ユーザー]
   354→    │ SQL Query
   355→    ▼
   356→┌─────────────────────────────┐
   357→│  Query Coordinator          │
   358→│  (プランニング + 結果集約)     │
   359→│                             │
   360→│  ┌────────────────────────┐ │
   361→│  │ Streaming Planner      │ │
   362→│  │ ・マニフェスト解析       │ │
   363→│  │ ・パーティションプルーニング│ │
   364→│  │ ・Row Groupプルーニング  │ │
   365→│  └──────────┬─────────────┘ │
   366→└─────────────┼───────────────┘
   367→              │ Work Units (ストリーミング)
   368→    ┌─────────┼─────────┐
   369→    ▼         ▼         ▼
   370→┌────────┐┌────────┐┌────────┐
   371→│Worker 1││Worker 2││Worker N│
   372→│DataFusion│DataFusion│DataFusion│
   373→│(ベクトル化)│(ベクトル化)│(ベクトル化)│
   374→└────┬───┘└────┬───┘└────┬───┘
   375→     │         │         │
   376→     └─────────┼─────────┘
   377→               │ Apache Arrow (gRPC)
   378→               ▼
   379→         [結果返却]
   380→```
   381→
   382→#### ストリーミングプランニングパイプライン
   383→
   384→従来のモノリシックなクエリ計画とは異なり、**計画と実行を並行処理**します。
   385→
   386→1. スナップショットとマニフェストリストを取得
   387→2. マニフェストを読み込みながら、マッチするデータファイル/Row Groupをワークユニットとして即座に発行
   388→3. コンピュートノードがプランナーの完了を待たずにデータI/Oを開始
   389→
   390→#### メタデータベースのプルーニング（3段階）
   391→
   392→| 段階 | 統計情報の場所 | 効果 |
   393→|------|-------------|------|
   394→| パーティションレベル | Icebergマニフェストリスト | 値の範囲でパーティション除外 |
   395→| 列レベル | 個別ファイルのmin/max値 | ファイル単位のスキップ |
   396→| Row Groupレベル | Parquetフッター | 行グループ単位のスキップ |
   397→
   398→#### Early Termination（早期終了）
   399→
   400→`LIMIT`句を含むクエリでは、`ORDER BY`句に基づきマニフェスト処理順序を最適化します。残りのワークユニットが最終結果に影響しないと判断された時点でパイプラインを停止し、データの一部分のみで正確な結果を返します。
   401→
   402→#### 実行エンジン
   403→
   404→各ワーカーで[Apache DataFusion](https://datafusion.apache.org/)が動作します。
   405→
   406→- Row GroupをDataFusionパーティションとしてマッピングし並列処理
   407→- ベクトル化実行で解釈オーバーヘッドを削減
   408→- Parquetの列指向フォーマットにより必要な列のみ読み込み
   409→- 結果はApache Arrow形式でgRPC経由で集約
   410→
   411→### 4.3 サポートされるSQL
   412→
   413→**集約関数（2026年1月追加）:**
   414→
   415→| 関数 | 説明 |
   416→|------|------|
   417→| `SUM()` | 合計 |
   418→| `COUNT()` | カウント |
   419→| `AVG()` | 平均 |
   420→| `MIN()` | 最小値 |
   421→| `MAX()` | 最大値 |
   422→
   423→`GROUP BY`句、`HAVING`句もサポートされています。
   424→
   425→**クエリ例:**
   426→
   427→```sql
   428→-- 基本的なフィルタクエリ
   429→SELECT user_id, event_type, amount
   430→FROM my_namespace.events
   431→WHERE __ingest_ts > '2026-01-01T00:00:00Z'
   432→  AND event_type = 'purchase'
   433→LIMIT 100
   434→
   435→-- 集約クエリ
   436→SELECT
   437→  merchant_category,
   438→  COUNT(*) as transaction_count,
   439→  SUM(amount) as total_amount,
   440→  AVG(amount) as avg_amount
   441→FROM fraud_detection.transactions
   442→WHERE is_fraud = true
   443→GROUP BY merchant_category
   444→HAVING COUNT(*) > 10
   445→```
   446→
   447→### 4.4 CLIでのクエリ実行
   448→
   449→```bash
   450→# 認証トークン設定
   451→export WRANGLER_R2_SQL_AUTH_TOKEN=[your-token]
   452→
   453→# クエリ実行
   454→npx wrangler r2 sql query "{WAREHOUSE}" \
   455→  "SELECT user_id, event_type FROM my_namespace.events WHERE amount > 100 LIMIT 10"
   456→```
   457→
   458→### 4.5 現在の制約
   459→

   461→- JOINは未サポート（2026年上半期に予定）

If your[Wrangler configuration](/workers/wrangler/configuration/#containers) sets the `image` attribute to a local path, the image will be built using the local Dockerfile. If the `image` attribute is set to a URL, the image will be pulled from the Cloudflare registry.

Note

Currently, the Cloudflare Vite-plugin does not support registry links in local development, unlike `wrangler dev`. As a workaround, you can create a minimal Dockerfile that uses `FROM <registry-link>`. Make sure to `EXPOSE` a port for local dev as well.

Container instances will be launched locally when your Worker code calls to create a new container. Requests will then automatically be routed to the correct locally-running container.

When the dev session ends, all associated container instances should be stopped, but local images are not removed, so that they can be reused in subsequent builds.

Note

If your Worker app creates many container instances, your local machine may not be able to run as many containers concurrently as is possible when you deploy to Cloudflare.

Also, `max_instances` configuration option does not apply during local development.

Additionally, if you regularly rebuild containers locally, you may want to clear out old container images (using `docker image prune` or similar) to reduce disk used.

To develop Container-enabled Workers locally, you will need to first ensure that a Docker compatible CLI tool and Engine are installed. For instance, you could use [Docker Desktop ↗](https://docs.docker.com/desktop/) or [Colima ↗](https://github.com/abiosoft/colima).

When you start a dev session, your container image will be built or downloaded. If your[Wrangler configuration](/workers/wrangler/configuration/#containers) sets the `image` attribute to a local path, the image will be built using the local Dockerfile. If the `image` attribute is set to a URL, the image will be pulled from the Cloudflare registry.

Note

Currently, the Cloudflare Vite-plugin does not support registry links in local development, unlike `wrangler dev`. As a workaround, you can create a minimal Dockerfile that uses `FROM <registry-link>`. Make sure to `EXPOSE` a port for local dev as well.

Container instances will be launched locally when your Worker code calls to create a new container. Requests will then automatically be routed to the correct locally-running container.

When the dev session ends, all associated container instances should be stopped, but local images are not removed, so that they can be reused in subsequent builds.

Note

If your Worker app creates many container instances, your local machine may not be able to run as many containers concurrently as is possible when you deploy to Cloudflare.

Also, `max_instances` configuration option does not apply during local development.

Additionally, if you regularly rebuild containers locally, you may want to clear out old container images (using `docker image prune` or similar) to reduce disk used.

When you develop with Wrangler or Vite, your Worker's code is automatically reloaded each time you save a change, but code running within the container is not.

> AGENT

公式ドキュメントでは **「Docker compatible CLI tool」** として Docker Desktop と Colima のみ言及。Podman の記載はありません。

Wrangler は内部で `docker` CLI を呼び出しているので、Podman を使うには:

```bash
# podman を docker コマンドとしてエイリアス
# macOS (Homebrew)
brew install podman
podman machine init
podman machine start

# docker CLI 互換にする
sudo ln -s $(which podman) /usr/local/bin/docker
# または
alias docker=podman
```

ただし **公式サポート外** なので、動く保証はありません。Colima の方が安全です:

```bash
brew install colima docker
colima start
```

Colima は Docker CLI 互換の軽量ランタイムで、公式ドキュメントにも記載されています。README は現状「Docker Desktop または Colima」としているので、このままで良いと思います。
