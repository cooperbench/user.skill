- **表示**: `slides` を map してカードリンク化。`href` は `${SITE.slidesUrl}${slide.url}` で外部遷移（`target="_blank"` + `rel="noopener noreferrer"`）。日付は `utils/date.ts` の `formatDate` で整形。

`★ Insight ─────────────────────────────────────`
- Astro のフロントマターは **ビルド時に 1 度だけ** 実行されるので、この `fetch` は訪問者ごとには走らず、`pnpm build` 時の外部 JSON の状態がそのまま焼き込まれます。スライド追加時は本体サイト再ビルド or 再デプロイが必要。

## Workers Deploy Hooks 要約

**何？** Workers Builds に対して **POST** するだけでビルド＆デプロイをキックできる専用 URL。Git push を待たずに任意タイミングで再ビルドできる仕組み。

**作り方:** Cloudflare ダッシュボード → Workers & Pages → 対象 Worker → Settings → Builds → Deploy Hooks。名前とブランチを指定すると URL が発行される。

**叩き方:** `curl -X POST <hook_url>` だけ。Authorization ヘッダ不要（URL 内の ID が認証トークン兼用）。レスポンスに `build_uuid` が返りビルド状況を追える。同時に複数回叩いても初期化中は既存ビルドを返す**冪等性**あり。

**制限:** Worker あたり 10 builds/min、アカウント全体で 100 builds/min。

**セキュリティ:** URL 即トークン。漏れたら誰でもビルド発火できるので環境変数/シークレット管理必須、漏洩時は削除して再発行。

## このプロジェクトでの使いどころ

`src/pages/slides.astro` は **ビルド時 fetch** で `slides.json` を取り込む構造（前ターンで確認）。つまりスライドを追加しても **me 側を再ビルドしない限り一覧が更新されません**。ここが Deploy Hook の出番です。

`★ Insight ─────────────────────────────────────`
- **推奨フロー**: スライド配信側リポジトリ（`slidesUrl` のホスト元）の CI 末尾に `curl -X POST $ME_DEPLOY_HOOK` を足すと、スライド公開直後に me 側もビルド走らせて一覧反映できる。GitHub Actions なら `secrets.ME_DEPLOY_HOOK` に URL を入れて `run: curl -fsS -X POST "$ME_DEPLOY_HOOK"` だけ。
- **代替**: スライド追加が稀なら cron-triggers 系サービス（例: GitHub Actions の `schedule:` で 1 日 1 回叩く）でも十分。10 builds/min の枠は個人運用だと事実上無制限。
- **注意**: Deploy Hook は「そのブランチの最新コミット」をビルドする。つまり me のコード自体に変更がなくても、外部 JSON が変われば新しい静的出力が生成されるのがポイント — `fetch` がビルド時評価だからこそ成り立つ。SSR/ISR にしたい場合はそもそも Deploy Hook 不要で、ページ側を `export const prerender = false` に切り替える別解になる。
`─────────────────────────────────────────────────`

2. **`slides.astro` を SSR 化**してリクエスト時 fetch に変える（Deploy Hook 不要だが Workers 実行コスト & レイテンシ増）

## 提案する最小構成

3. slides リポジトリに以下の workflow を追加:

```yaml
# ../slides/.github/workflows/trigger-me-rebuild.yml
name: Trigger me rebuild
on:
  push:
    branches: [main]
    paths:
      - "contents/**"
      - "build.js"
jobs:
  trigger:
    runs-on: ubuntu-latest
    steps:
      - name: Wait for Cloudflare Workers Build
        run: sleep 90
      - name: POST deploy hook
        run: |
          curl -fsS -X POST "$ME_DEPLOY_HOOK" \
            -H "Content-Type: application/json"
        env:
          ME_DEPLOY_HOOK: ${{ secrets.ME_DEPLOY_HOOK }}
```

`★ Insight ─────────────────────────────────────`
- **`sleep 90` の理由**: Cloudflare Workers Builds は push を検知してから独立にビルドするので、GitHub Actions 側で直ちに hook を叩くと me が**古い** `slides.json` を fetch してしまう競合が起きます。90 秒は slides の単純ビルド（`node build.js`）が確実に完了する安全マージン。正確を期すなら Cloudflare API で build status をポーリングする手もあるが、個人運用ではオーバーエンジニアリング。
- **`paths` フィルタ**: README やワークフロー自身の変更で余計な me ビルドを走らせないためのガード。`contents/**` がスライド本体、`build.js` が `slides.json` 生成器という前提。違っていれば教えてください。
- **なぜ slides 側に置くか**: me 側の cron で定期的に叩く案もあるけど、「スライド追加 → すぐ一覧に出る」体験を作るなら **イベント駆動（push 起点）** の方が無駄ビルドが少なく cache も汚れない。

  schedule:

  workflow_dispatch:

`★ Insight ─────────────────────────────────────`

## Hono が効く場面 / 効かない場面

Hono は **HTTP ルーティング**のためのフレームワーク。`scheduled` ハンドラは HTTP リクエストではなく Cloudflare のイベントで直接呼ばれるので、Hono の恩恵（ルータ、ミドルウェア、バリデータ）はゼロ。

```typescript
// Hono で書いた場合
import { Hono } from "hono";

const app = new Hono();
// ↑ この行、scheduled では一度も使われない

export default {
  fetch: app.fetch,
  async scheduled(_e, env: Env) {
    await fetch(env.DEPLOY_HOOK_URL, { method: "POST" });
  },
} satisfies ExportedHandler<Env>;
```

→ `Hono` インスタンスが完全に飾り。依存追加・bundle size 増・読む人の混乱だけ残る。

## Hono を入れる意味が出るパターン

もし **手動トリガ用 HTTP エンドポイント**も欲しくなったら話が変わります:

```typescript
import { Hono } from "hono";
import { bearerAuth } from "hono/bearer-auth";

const app = new Hono<{ Bindings: Env }>();

app.post(
  "/api/rebuild",
  async (c, next) => bearerAuth({ token: c.env.TRIGGER_TOKEN })(c, next),
  async (c) => {
    const res = await fetch(c.env.DEPLOY_HOOK_URL, { method: "POST" });
    return c.json({ ok: res.ok, status: res.status });
  },
);

export default {
  fetch: app.fetch,
  async scheduled(_e, env: Env) {
    await fetch(env.DEPLOY_HOOK_URL, { method: "POST" });
  },
} satisfies ExportedHandler<Env>;
```

これなら「ブラウザから手動で叩けるボタン」とか「スマホから curl で発火」とかの拡張余地が生まれ、`bearerAuth` や CORS ミドルウェアが Hono で数行になる。

`★ Insight ─────────────────────────────────────`
- **Assets バインディングとの共存の注意点**: `main` に `fetch` ハンドラを書くと、`assets` にマッチしないリクエストだけ Worker に来る…のではなく、**デフォルトでは全リクエストが Worker の `fetch` に来る**。静的 assets を配信したい場合は `c.env.ASSETS.fetch(c.req.raw)` で明示的にフォールバックさせる必要がある。あるいは `wrangler.jsonc` の `assets.run_worker_first` を `false`（デフォルト）にしておき、assets にないパスだけ Worker に来るようにする。ここを誤ると **全ページが 404 になる**ので、Hono 導入 = 既存の静的配信を壊すリスクがある点が一番のコスト。
- **Bundle size**: Hono 本体は ~14KB gzipped、起動オーバーヘッドは無視できるレベル。サイズは理由にならない。
- **TypeScript DX**: `Hono<{ Bindings: Env }>` で `c.env` の型が効くのは気持ち良いが、`scheduled` 側には無関係（`Env` 型を自分で書く必要あり）。

## PR #95 の内容

| 変更 | 理由 |
|---|---|
| `biome.json`: `css.parser.tailwindDirectives: true` | Tailwind v4 の `@plugin` / `@apply` / `@theme` / `@utility` を Biome にパースさせる |
| `global.css`: `@plugin` を `@import` の後ろへ移動 | CSS 仕様上 `@import` は他の at-rule より前に置く必要があるため |
| `src/utils/ogp.ts`: import 順の微修正 | `biome --write` が自動で直した副産物 |

`★ Insight ─────────────────────────────────────`
- **Tailwind v4 の `@plugin` ディレクティブ**は、v3 までの JS 設定ファイル（`tailwind.config.js`）での `plugins: []` 指定を CSS 側に移した新機能。Biome v2 はデフォルトでこれを認識せず、ビルドは通るのに lint だけ落ちる状態でした。`tailwindDirectives` フラグでまとめて解決。
- **`@import` の順序制約**は CSS 仕様レベルの縛りで、Tailwind 固有ではない。`@layer` と `@charset` だけが例外的に `@import` より前に置ける。ここを外すと実際のブラウザ読み込みでも `@import` が無視されるリスクがあるので、Biome が警告するのは正しい。
- **ビルド成功の裏側**: build が通っていたのは Astro/Vite が内部で LightningCSS を使っており、そちらは Tailwind v4 のディレクティブを正しく解釈するから。Biome と Vite で CSS パーサが別なのが混乱の原因で、biome.json で明示的にフラグを立てる必要があった。
`─────────────────────────────────────────────────`
