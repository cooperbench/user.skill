### 2. Can dlt Run in Pyodide/WASM (Cloudflare Python Workers)?

**Short answer: No, not currently feasible.** The blockers are:

1. **`requests` library is fundamentally incompatible.** Cloudflare Python Workers only support async HTTP libraries (`aiohttp`, `httpx`). The `requests` library is synchronous and blocked. dlt uses `requests` extensively throughout its core for API calls. JSPI (JavaScript Promise Integration) may eventually allow synchronous Python HTTP in Pyodide, but this is not yet available in Cloudflare Workers.

2. **`pendulum` has C extensions** that are not compiled for Pyodide/WASM. This is a hard dependency used throughout dlt for timestamp handling.

3. **`gitpython` requires git binary access**, which is unavailable in any WASM sandbox.

4. **Package size**: On AWS Lambda (250 MB limit), dlt already requires Docker image deployment due to its dependency footprint. Cloudflare Workers have even tighter memory constraints (128 MB).

5. **No raw TCP/IP connections** in Pyodide/WASM, which means most database destinations would not work anyway.

### 3. dlt's Own WASM Playground

dlt does have a browser-based WASM playground using marimo + Pyodide, but with **severe limitations**: no database connections (no TCP/IP), only HTTP sources with correct CORS headers, and limited to demonstration/exploration purposes. This confirms dlt can partially load in Pyodide but cannot perform real data loading work.

### 4. Known Serverless Deployments

dlt has been successfully deployed on **AWS Lambda**, but:
- Requires Docker image deployment (exceeds 250 MB zip limit)
- Taktile runs dlt on Lambda processing millions of daily events
- State must be persisted externally (S3)
- Cold starts are a concern with the large dependency tree

No known attempts to run dlt on Cloudflare Workers, Deno Deploy, or other edge/WASM runtimes were found.

### 5. Alternative Approaches for Your Project

Given that dlt cannot run in Cloudflare Workers, here are viable alternatives:

**A. Keep your current TypeScript-native approach (recommended)**
Your existing ingestion Worker already handles GitHub, Linear, Withings, and Oura data extraction in TypeScript with Hono. This is the correct pattern for Cloudflare Workers -- lightweight, fast, and native to the runtime.

**B. Use dlt externally, load into R2/D1**
Run dlt on a traditional compute platform (Lambda, Cloud Run, or a VM) and write results to R2 via S3-compatible API. Workers then read from R2. This decouples extraction from the edge.

**C. Use dlt's REST API source pattern as inspiration**
dlt's declarative REST API source configuration pattern (schema inference, pagination handling, incremental loading) can be replicated in TypeScript without dlt itself. Libraries like `zod` for schema validation and your existing Parquet encoding approach already cover much of what dlt provides.

**D. Cloudflare Workers + external Python Worker (hybrid)**
Use a Cloudflare Queue to dispatch extraction jobs to an external Python service running dlt, then have results written back to R2.

### Conclusion

dlt is fundamentally incompatible with Cloudflare Workers due to synchronous HTTP dependencies (`requests`), C-extension dependencies (`pendulum`), system-level dependencies (`gitpython`), and the constrained WASM/Pyodide sandbox. Your current approach of writing TypeScript-native ingestion services that run directly on Workers is architecturally sound and better suited to the edge computing model.

**dlt-runner.ts** — ここが核心。sandbox 内で Python スクリプトを実行：

```typescript
// sandbox-dbt の cloneRepo → installDeps → runDbt と同じ流れ
// 1. リポジトリ clone（dlt パイプライン定義を取得）
// 2. uv sync（追加依存があれば）
// 3. sandbox.exec("python -m dlt_pipelines.github") のように実行
// 4. R2 に出力された Parquet/JSON をアーティファクトとして記録
```

### sandbox-dbt と sandbox-dlt の比較

| 観点 | sandbox-dbt | sandbox-dlt |
|------|------------|------------|
| **コンテナ内実行** | `uv run dbt run` | `python -m pipeline` or `uv run dlt` |
| **入力** | SQL モデル（リポジトリ内） | Python パイプライン定義 |
| **出力** | manifest.json, run_results.json | Parquet ファイル、state ファイル |
| **R2 保存** | `dbt-runs/{runId}/` | `dlt-runs/{runId}/` + `raw/{source}/` |
| **Secrets** | R2 + GitHub | R2 + 各データソースの API キー |
| **Dockerfile** | git + uv のみ | git + uv + `dlt[filesystem]` プリインストール |
| **cron** | 毎日 AM2:00 | ソースごとにスケジュール可 |

### ここであなたに判断してほしいポイント

`★ Insight ─────────────────────────────────────`
**dlt の destination 選択** がアーキテクチャを大きく左右します。dlt は「どこにデータを書き出すか」でパイプラインの振る舞いが変わります。
`─────────────────────────────────────────────────`

**dlt の destination をどうするか？** 3つの選択肢があります：

| Destination | メリット | デメリット |
|-------------|---------|-----------|
| **A. `filesystem` (R2/S3互換)** | 既存の data-lake バケットに直接 Parquet 書き出し。dbt と同じ R2 に統一 | dbt から直接読むには external source 設定が必要 |
| **B. `duckdb`** | sandbox 内で DuckDB に書いて Parquet export。transform/core の dbt-duckdb と親和性高い | 一時ファイル→R2 の二段階になる |
| **C. `motherduck`/`snowflake` 等の外部DB** | 本格的な DWH に直接ロード | 外部接続が必要、sandbox の制約に注意 |

現在の ingestion Worker は TypeScript で API → R2 Parquet という流れなので、**A の `filesystem` destination で R2 に直接 Parquet を書く**のが最もシンプルに既存アーキテクチャと合います。

```
GitHub API → ingestion Worker (TypeScript) → R2 に Parquet 保存
```

## 回答: 「external source 設定が必要」とは

現在のプロジェクトの状況を踏まえて説明します。

### 現在の transform/core（dbt-duckdb）の仕組み

```
seeds/orders.csv  →  dbt seed  →  DuckDB テーブル "orders"
                                        ↓
                     stg_orders.sql が {{ ref('orders') }} で参照
```

staging モデルは `{{ ref('orders') }}` で seed を参照しています。**R2 の Parquet は一切読んでいません。**

### dlt が R2 に Parquet を書いた場合の問題

dlt が R2 に `raw/github/contributions/*.parquet` を書き出すとします。dbt からこれを読むには：

```sql
-- ❌ dbt の ref() では R2 のファイルを参照できない
select * from {{ ref('contributions') }}  -- そんな seed/model は無い

-- ✅ DuckDB の read_parquet() で直接読む必要がある
select * from read_parquet('s3://data-lake/raw/github/contributions/*.parquet')
```

この「R2 上の Parquet を dbt のソースとして定義する」のが **external source** です：

```yaml
# models/staging/_sources.yml
sources:
  - name: r2_raw
    schema: main
    meta:
      external_location: "s3://data-lake/raw/{name}/**/*.parquet"
    tables:
      - name: github_contributions
      - name: linear_issues
```

```sql
-- models/staging/stg_github_contributions.sql
select * from {{ source('r2_raw', 'github_contributions') }}
```

`★ Insight ─────────────────────────────────────`
**dbt-duckdb の `external_location`** は dbt-duckdb アダプター固有の機能です。`meta.external_location` に S3/R2 パスを書くと、dbt が内部的に `read_parquet()` に変換してくれます。つまり dbt の `{{ source() }}` 関数で R2 Parquet をシームレスに参照できるようになります。

ただし、これは **設定を追加するだけ**の話で、大きなハードルではありません。dlt → R2 → dbt の ELT パイプラインを繋ぐための「配線」にすぎません。
`─────────────────────────────────────────────────`

### まとめ

| パターン | dbt 側の設定 |
|---------|-------------|
| **seed（現状）** | CSV をリポジトリに入れるだけ。`ref()` で参照 |
| **dlt → R2 Parquet → dbt** | `_sources.yml` に `external_location` を定義。`source()` で参照 |

「設定が必要」と言いましたが、YAML 数行の追加で済むので、R2 destination で問題ありません。
