Now, what 7.31.1 / 7.31.2 (+ the reg-33 semantics) tell us:

**7.31.1 SerialCount (reg 30, byte 0)** — this *is* the answer to "can ASCII carry a timestamp?": **yes.** Set to a non-zero mode, the device appends a field to every serial async (ASCII) message, just before the checksum:
- mode 1 `SYNCIN_COUNT` → a counter, mode 2 `SYNCIN_TIME` → a µs time, mode 3 `SYNCOUT_COUNT` → a counter. Prefixed with `T`: `$VNYPR,…,T1162704*2F`.

**7.31.2 SerialStatus (reg 30, byte 1)** — appends a 4-hex sensor/filter status, prefixed `S`: `$VNYPR,…,S0000*1F`. If both are on, status comes first.

**The gotcha (reg 33 SyncInTime, why I checked):** these values come from the Synchronization Status register, and they're keyed to the **SyncIn pin**. `SyncInCount` = number of SyncIn trigger events; `SyncInTime` = µs since the last trigger. With **no GPS/PPS wired to SyncIn** (our bench), the counter (mode 1) stays **0** — useless as a sequence — and the time (mode 2) we *think* free-runs from boot but that needs device confirmation. `SYNCOUT_COUNT` (mode 3) could increment if SyncOut is configured device-side.

**How this lands against our goals:**

1. It's still **device-stamp time, not host arrival time** — same limitation as the binary `TimeStartup`. So SerialCount alone does *not* measure host-side jitter.
2. But it's the **complement** to the host read-timestamp we were about to build: pairing a device stamp (SerialCount on ASCII, `TimeStartup` on binary) with the host read-timestamp gives `host_arrival − device_stamp` per message → the transport/buffering latency, and its variance is exactly the jitter we want, cleanly separated from device cadence. That's a *better* instrument than host-timestamps alone.
3. For the **pure-ASCII experiment**, enabling SerialCount gives ASCII frames their own sequence/time — making ASCII-only runs as analyzable (drop detection, ground-truth bytes) as binary-only is via `TimeStartup`.
