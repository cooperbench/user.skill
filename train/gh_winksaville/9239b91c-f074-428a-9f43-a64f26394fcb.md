# Plan: Add `toolchain` field to translation specs

## Context

When testing packages in rlibc-x that use `-Z build-std` (nightly-only), tspec currently auto-detects the need for nightly and hardcodes `+nightly`. A `toolchain` field lets specs explicitly declare which toolchain to use (e.g., `nightly`, `stable`, `nightly-2025-01-15`, `1.75`), giving users control and making specs self-documenting. When set, it overrides auto-detection; when absent, current behavior is preserved.

**Verbosity levels:**

- `-vv`: Same plus spec resolution details (which spec file, expanded target_dir, profile resolution, nightly auto-detection reasoning)

**Placement:** Global flag on the top-level `Cli` struct (not per-subcommand), so `tspec -v build ...` and `tspec -vv test ...` work uniformly. Clap supports `#[arg(short = 'v', action = ArgAction::Count)]` for this.

**Threading it through:** The `Execute` trait currently takes only `project_root`. Options:
1. Add `verbosity: u8` parameter to `Execute::execute()` — clean but touches every command impl
2. Add a lightweight context struct (`struct Context { project_root, verbosity }`) — more future-proof
3. Pass verbosity into `build_package()`, `test_package()`, `execute_cargo_subcommand()` directly

I'd lean toward option 1 (or 2 if you want room for future context like `--dry-run`). The actual printing would happen right before `cmd.status()` calls in `cargo_build.rs`, `testing.rs`, and `cmd/mod.rs`.
