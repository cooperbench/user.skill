> AGENT

Clap makes it straightforward via the `clap_complete` crate. Here's the gist:

**What it does**: Generates shell completion scripts (bash, zsh, fish, powershell, elvish) that handle completing subcommands, flags, and arguments.

**Effort**: Minimal — typically 10-20 lines of code added to your project:

1. Add `clap_complete` dependency to Cargo.toml
2. Add a `completions` subcommand (or a `--generate-completions` flag)
3. Call `clap_complete::generate()` with your CLI struct and the target shell
4. User runs something like `vc-x1 completions bash > ~/.bash_completion.d/vc-x1` once

**What you get for free** (since you use `#[derive(Parser)]`):
- All subcommand names (`chid`, `desc`, `list`, `show`, `fix-desc`, etc.)
- All flags (`--repo`, `--label`, `--indent`, etc.)
- Short flags (`-R`, `-l`, `-i`, etc.)

**What you don't get automatically**:
- Dynamic completions (e.g., completing bookmark names, revision IDs) — those need custom `completer` attributes or runtime logic
- File path completions for specific arguments — possible but requires extra work

**Typical implementation**:
```rust
// In your CLI enum:
/// Generate shell completions
Completions { shell: clap_complete::Shell },

// In your match:
Command::Completions { shell } => {
    clap_complete::generate(shell, &mut Cli::command(), "vc-x1", &mut std::io::stdout());
}
```

It's one of the easier features to add. Want to implement it?

This is the newer **runtime completion** approach. Here's how it works:

**Key idea**: Instead of generating a static shell script, your binary itself handles completions. When the shell needs completions, it calls your binary with `COMPLETE=<shell>` set in the environment. `CompleteEnv` intercepts that, outputs completions, and exits — your normal app logic never runs.

**Setup in code** — very minimal:

```rust
fn cli() -> clap::Command {
    // your existing clap command definition
}

// Add this before your normal argument parsing:
CompleteEnv::with_factory(cli)
    .complete();
```

**User-side shell setup** (one-time):
```bash
# bash
source <(COMPLETE=bash vc-x1)

# zsh
source <(COMPLETE=zsh vc-x1)

# fish
source (COMPLETE=fish vc-x1 | psub)
```

Typically added to `.bashrc` / `.zshrc`.

**Advantages over the static approach**:
- Completions always match the installed binary version — no stale scripts
- Supports dynamic completions out of the box (via `ValueHint`, `ArgValueCandidates`, custom `ArgValueCompleter`)

> AGENT

Here's how each shell handles completion discovery:

### Bash
Bash itself has [programmable completion builtins](https://www.gnu.org/software/bash/manual/html_node/Programmable-Completion.html) (`complete`, `compgen`), but the heavy lifting is done by the [**bash-completion** project](https://github.com/scop/bash-completion) — a separate package installed on most distros. It lazy-loads completion scripts from `/usr/share/bash-completion/completions/`. That's exactly what your `_jj` file is — a stub that runs `jj util completion bash` on first tab-complete.

### Zsh
Zsh has its own [built-in completion system](https://zsh.sourceforge.io/Doc/Release/Completion-System.html). Completion functions are files named `_commandname` placed in directories on `$fpath`. When you run `compinit`, zsh scans those directories and autoloads them on demand. The [zsh-completions](https://github.com/zsh-users/zsh-completions) project provides additional third-party completions.

### Fish
Fish has the simplest model — it [automatically discovers](https://fishshell.com/docs/current/completions.html) completion files from `$fish_complete_path`, typically `~/.config/fish/completions/`. Just drop a file named `vc-x1.fish` there and it's loaded on demand.

### Summary

| Shell | Discovery location | Lazy? |
|-------|-------------------|-------|
| Bash  | `/usr/share/bash-completion/completions/` | Yes, via bash-completion |
| Zsh   | Dirs on `$fpath` (e.g. `/usr/share/zsh/site-functions/`) | Yes, via `compinit` |
| Fish  | `~/.config/fish/completions/` or vendor dir | Yes, automatic |

So all three shells have a "drop a file in the right place" mechanism. For vc-x1, we could either:
1. **Keep the `source <(COMPLETE=bash vc-x1)` approach** — user adds one line to rc file
2. **Generate a stub file** (like jj's `_jj`) that the user drops into the completions directory
3. **Add a subcommand** like `vc-x1 setup-completions` that writes the stub to the right place
