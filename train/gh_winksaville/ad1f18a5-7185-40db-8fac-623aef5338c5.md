## Overview

The `clap_complete::env` module provides dynamic shell completion through environment variable activation. Rather than generating static completion files, this system activates completions at runtime via the `COMPLETE` environment variable.

## Key Architecture

**Core Types:**

The system centers on [`CompleteEnv`](struct.CompleteEnv.html), which implements the completion trigger mechanism. It works alongside shell-specific adapter structs: `Bash`, `Zsh`, `Fish`, `Elvish`, and `Powershell`. These adapters inherit from the [`EnvCompleter`](trait.EnvCompleter.html) trait, which defines the shell-integration contract.

The [`Shells`](struct.Shells.html) struct aggregates multiple shell adapters into a unified collection.

## Setup Pattern

The implementation follows a factory-based initialization:

```rust
fn cli() -> clap::Command {
    // ... command definition
}

CompleteEnv::with_factory(cli)
    .complete();

// ... rest of application logic
```

This pattern allows `CompleteEnv` to intercept execution when the `COMPLETE` environment variable is set, generating completions before normal application logic runs.

## Shell Integration

Users source completions dynamically rather than saving static files. For example, Bash users add:

```bash

```

This approach ensures completions stay synchronized with the application version, avoiding mismatches between shell code and the program.

The system supports completion refinement through:
- `ValueHint` enum for contextual suggestions
- `ValueEnum` trait for predefined value sets
- `ArgValueCandidates` struct for custom candidate generation
- `ArgValueCompleter` for advanced completion logic

## Key Integration Points

The struct provides these configuration methods:
- `with_factory()` - Creates the completion handler
- `var()` - Overrides the environment variable

Here's how each shell handles completion discovery:

### Bash
Bash itself has [programmable completion builtins](https://www.gnu.org/software/bash/manual/html_node/Programmable-Completion.html) (`complete`, `compgen`), but the heavy lifting is done by the [**bash-completion** project](https://github.com/scop/bash-completion) — a separate package installed on most distros. It lazy-loads completion scripts from `/usr/share/bash-completion/completions/`. That's exactly what your `_jj` file is — a stub that runs `jj util completion bash` on first tab-complete.

### Zsh
Zsh has its own [built-in completion system](https://zsh.sourceforge.io/Doc/Release/Completion-System.html). Completion functions are files named `_commandname` placed in directories on `$fpath`. When you run `compinit`, zsh scans those directories and autoloads them on demand. The [zsh-completions](https://github.com/zsh-users/zsh-completions) project provides additional third-party completions.

### Fish
Fish has the simplest model — it [automatically discovers](https://fishshell.com/docs/current/completions.html) completion files from `$fish_complete_path`, typically `~/.config/fish/completions/`. Just drop a file named `vc-x1.fish` there and it's loaded on demand.

### Summary

| Shell | Discovery location | Lazy? |
|-------|-------------------|-------|
| Bash  | `/usr/share/bash-completion/completions/` | Yes, via bash-completion |
| Zsh   | Dirs on `$fpath` (e.g. `/usr/share/zsh/site-functions/`) | Yes, via `compinit` |
| Fish  | `~/.config/fish/completions/` or vendor dir | Yes, automatic |

So all three shells have a "drop a file in the right place" mechanism. For vc-x1, we could either:
1. **Keep the `source <(COMPLETE=bash vc-x1)` approach** — user adds one line to rc file
