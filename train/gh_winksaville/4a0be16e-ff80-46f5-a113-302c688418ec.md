**On the git dep question** — no blocking issue, but trade-offs. You'd change `Cargo.toml`:

```toml
# path (current)
zc-ring-x1 = { path = "../zc-ring-x1" }

# git
zc-ring-x1 = { git = "https://github.com/winksaville/zc-ring-x1" }
```

Things to weigh:

- **The API removal must be on the pushed branch.** Your local `../zc-ring-x1` is at `0.9.0` with only `reserve_slot_with`. A bare git dep tracks the default branch tip at lock time — so GitHub's default branch needs to already have `reserve_slot`/`reserve_slot_spin` removed, or the build breaks. Worth confirming that's pushed.
- **Pin for reproducibility.** A bare git dep floats until `Cargo.lock` locks it. Pin explicitly to be safe: `{ git = "...", tag = "v0.9.0" }` or `{ ..., rev = "<sha>" }` (or `branch = "main"`). The lockfile records the exact commit either way, but a tag/rev is intent-visible.
- **Co-development friction.** The path dep is why you can edit both repos and rebuild instantly. With a git dep, every zc-ring-x1 change has to be pushed before iiac-perf sees it, and you `cargo update -p zc-ring-x1` to re-pin. If you're still iterating on the library, path is much smoother.

My take: keep `path` while co-developing; switch to a **tag-pinned git dep** when you want iiac-perf buildable standalone (CI, fresh clone, or publish). They're not mutually exclusive either — a `[patch]` can point a git dep back at the local path during dev.
