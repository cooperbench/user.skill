# Plan: Always include `cargo --release` baseline in compare

## Context

The `tspec compare` command currently only compares builds using tspec files. If no tspec files exist, it errors out. The user wants a plain `cargo build --release` result always included as a baseline, so there's always a reference point — even with zero tspec files.

## Problem

1. `build_package(pkg_name, None, release)` auto-discovers default `tspec.ts.toml` if it exists — no way to force a plain build
2. `find_tspecs()` errors when no tspec files match — compare can't run without specs
3. `compare_specs()` only iterates spec paths, no baseline concept

Now continuing the design discussion. The key open question is **how does the library find the spec at build time?**

The cleanest approach: tspec already knows which spec file is being used when it invokes `cargo build`. It could set an environment variable before calling cargo:

```rust
cmd.env("TSPEC_SPEC_FILE", spec_path);
```

Then in the library:

```rust
pub fn emit_linker_flags() {
    let spec_path = env::var("TSPEC_SPEC_FILE")
        .expect("TSPEC_SPEC_FILE not set — are you building via tspec?");
    let spec = load_spec(&spec_path);
    let bin_name = env::var("CARGO_PKG_NAME").unwrap();
    for arg in &spec.linker.args {
        println!("cargo:rustc-link-arg-bin={bin_name}={arg}");
    }
}
```

This keeps the library dumb — it just reads what tspec tells it. No spec discovery logic duplicated. And `CARGO_PKG_NAME` is already set by cargo in build scripts.

That's expected cargo behavior, not a tspec bug. The difference:

- `tspec clean` → no `-p` flag → `cargo clean` → removes everything in target/
- `tspec clean .` → resolves to `-p hw` → `cargo clean -p hw` → removes only that package's artifacts

`cargo clean -p <pkg>` is more targeted — it leaves behind shared artifacts (CACHEDIR.TAG, directory structure, some index files) that don't belong to any specific package. The 3 extra files are those shared leftovers.

For a POP it's a bit odd since there's only one package, but in a workspace `tspec clean .` being package-specific is the right behavior (you wouldn't want `tspec clean .` from inside `apps/hw-x1/` to nuke the entire workspace target/).

So the semantics are:
- `tspec clean` = "clean everything" (no `-p`)
- `tspec clean .` = "clean this package" (`-p hw`)
- `tspec clean -w` = "clean everything" (no `-p`)

The total size is the same (7.5MiB) — the 3 extra files are just tiny metadata. I'd leave this as-is since the behavior is consistent and correct for the workspace case where it matters more.
