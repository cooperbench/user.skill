1	# copying (design stub)
2	
3	Forward-looking design capture from the 0.61.0 parity audit
4	cycle. No implementation yet — concrete work lands when a
5	follow-on cycle picks it up.
6	
7	Generalizes "copy these files into the new workspace at
8	init time" into one composable mechanism that subsumes
9	today's `--config <path>` (deprecated under the
10	`.vc-config.toml` write axis collapse —
11	see [[1]]), a hypothetical `--gitignore <path>`, and
12	today's `--use-template <CODE[,BOT]>`.
13	
14	The mechanism is **pure file copy** — no variable
15	substitution, no transformation. The bot deliberately
16	avoided "templating" / "seeding" as concept names; "seed"
17	implies growth and "template" implies parameterization,
18	neither of which this mechanism does. It just copies.
19	
20	## Goal
21	
22	One mechanism for "copy these files into the workspace at
23	init time" rather than per-file flags. The user supplies
24	one or more source paths; init copies them into the new
25	workspace during the copy phase, before commits.
26	
27	## Surface
28	
29	- `--init-from-code=<glob>` — copy files matched by
30	  `<glob>` into the code repo (non-recursive).
31	- `--init-from-bot=<glob>` — same, into the `.claude/`
32	  companion. Only meaningful under dual.
33	- `--init-from=<glob>` — shorthand for `--init-from-code`
34	  (since por only has code, and dual users typically copy
35	  into code more often than bot).
36	- `--init-from-recursive=<glob>` /
37	  `--init-from-code-recursive=<glob>` /
38	  `--init-from-bot-recursive=<glob>` — recursive variants.
39	
40	Each flag accepts a **shell glob** (expansion done by the
41	shell; `vc-x1` receives the expanded path list). Each may
42	be specified multiple times — the result is the additive
43	union of all sources. Order matters for collisions (see
44	below).
45	
46	## Behavior
47	
48	- **Copy semantics** — files only; preserves relative
49	  layout under the source root. The bot's working
50	  assumption is `cp -a` semantics (preserve symbolic
51	  links and executable bits); confirm at design time.
52	- **Collision: last writer wins, with a warning.** If two
53	  `--init-from*` flags resolve to the same destination
54	  file, the later one overwrites the earlier; `vc-x1`
55	  emits a warning naming both sources. The bot thinks
56	  warnings are right here — silent overwrite is a
57	  footgun; erroring would block valid layering use cases
58	  (a base directory + per-project tweaks).
59	- **Canned writes suppressed when copying is engaged.**
60	  Today `init` writes a canned `.vc-config.toml` and
61	  `.gitignore`. With any `--init-from*` present, **both
62	  canned writes are suppressed entirely**. The user opted
63	  in to full control of the copied content; init doesn't
64	  layer canned defaults underneath.
65	- **Dual post-copy check (deferred).** After copying
66	  completes for a dual workspace, if `.vc-config.toml`
67	  is missing or lacks `[workspace] other-repo`, init
68	  **warns** (does not error). The workspace looks dual
69	  (has `.claude/`) but acts por at runtime; downstream
70	  subcommands enforce the invariant. See
71	  [Deferred-validation](#deferred-validation).
72	
73	## Deferred-validation
74	
75	Init's `.vc-config.toml` check is a **warning**, not an
76	error, to support workflows where the user plans to
77	supply the config post-init (e.g. checking in the
78	workspace shell first, then populating config files in a
79	follow-up commit).
80	
81	The error happens at the **first downstream invocation**:
82	`default_scope` (or a new explicit check) detects the
83	broken-dual state — `.claude/` exists but `.vc-config.toml`
84	doesn't (or lacks `other-repo`) — and refuses to proceed
85	with a clear error pointing at the missing file.
86	
87	Today `default_scope` silently falls back to
88	`Scope([Code])` when `.vc-config.toml` is absent
89	(`src/common.rs:594`). That silent fallback is exactly
90	the "looks dual, acts por" surprise this design avoids;
91	fixing it is a prerequisite for the post-init copy
92	workflow.
93	
94	## Fixed filename
95	
96	`.vc-config.toml` stays the fixed name; overriding it is
97	deferred until a real use case surfaces (would ripple
98	through every subcommand's lookup code — `default_scope`,
99	`find_workspace_root_from`, `validate-desc`, `fix-desc`,
100	`push`, `clone`, …).
101	
102	## Subsumes
103	
104	- `--config <path>` — never really built; the
105	  `.vc-config.toml` write axis's collapse
106	  left the capability un-claimed. Equivalent under
107	  copying: `--init-from=<src>/.vc-config.toml`.
108	- `--gitignore <path>` — never built; equivalent under
109	  copying: `--init-from=<src>/.gitignore`.
110	- `--use-template <CODE[,BOT]>` — today's coarse
111	  whole-repo flag. Subsumed by recursive variants:
112	  - `--use-template code-tpl/` →
113	    `--init-from-code-recursive=code-tpl/*`.
114	  - `--use-template code-tpl/,bot-tpl/` → two flags:
115	    `--init-from-code-recursive=code-tpl/*` +
116	    `--init-from-bot-recursive=bot-tpl/*`.
117	
118	The bot thinks `--use-template` can be retired once
119	copying ships, but a back-compat shim that translates
120	old form → new form is cheap and worth keeping for one
121	release cycle.
122	
123	## Naming rationale
124	
125	The mechanism is named **copying** (not "templating," not
126	"seeding," not "scaffolding") because all three imply
127	something the mechanism doesn't do:
128	
129	- "Templating" implies parameterization / variable
130	  substitution. We deliberately don't do that.
131	- "Seeding" implies growth (a seed grows into a plant);
132	  the copied files don't grow — they sit where they
133	  landed.
134	- "Scaffolding" implies project-structure generation
135	  (Rails generators, Yeoman); the mechanism is just
136	  `cp -r`, no structure-aware logic.
137	
138	"Copying" is literal: source files go to destination
139	paths. The flag family `--init-from*` keeps the verb out
140	of the surface — the flag describes *what* (source-to-
141	destination), not *what kind of operation*. If a future
142	mechanism does layer substitution on top of copy, it's a
143	separate feature with its own name.
144	
145	## Open questions (resolve at design time)
146	
147	- **Variable substitution.** Should the copy step support
148	  `{{name}}` / `{{account}}` substitution? The bot
149	  thinks **no** — keep the mechanism pure copy. Users
150	  who need substitution can pre-process and pass the
151	  result. Adding substitution invites a substitution-
152	  language rabbit hole and breaks the "copying" framing
153	  we just settled on.
154	- **Symbolic links and executable bits.** Preserve, or
155	  flatten? Probably preserve — `cp -a` semantics.
156	  Worth confirming at design time.
157	- **Source-not-found behavior.** Hard error (typo
158	  protection) or soft skip (let globs return empty)?
159	  Probably hard error — a missing source is almost
160	  always user mistake. Empty glob expansion (the shell
161	  passing zero paths) is fine.
162	- **Interaction with `vc-x1 clone`.** Clone seeds from
163	  an existing remote, so copying overlays *on top of*
164	  the cloned content. Same flag set, same collision
165	  rules.
166	- **Mechanism beyond init?** A future
167	  `vc-x1 <subcommand> --copy-from=<glob>` to layer
168	  files into an existing workspace would be the same
169	  mechanism with a different host command. The bot
170	  thinks defer until a real use surfaces; `--init-from*`
171	  is the only surface today.
172

1	# Cycle protocol
2	
3	## Cycles
4	
5	A cycle has three phases:
6	
7	- **[Preparation](#preparation)** (`X.Y.Z-0`) — the cycle's
8	  first commit. Sets up the cycle:
9	  - Backfill the previous cycle's chores `Commits:` ref.
10	  - Bump `Cargo.toml` to `X.Y.Z-0`.
11	  - Pick up a `## Todo` item (typically via `## Priorities`)
12	    into `## In Progress` (bold title + succinct problem
13	    statement + plan ladder).
14	  - Open the [chores section](#chores-sections).
15	- **[Work-N](#work-n)** (`X.Y.Z-1`, `X.Y.Z-2`, …) — the
16	  commits that implement the change. As many as the change
17	  needs; each runs through the
18	  [per-commit flow](#per-commit-flow).
19	- **[Close-out](#close-out)** (bare `X.Y.Z`) — the cycle's
20	  last commit. Bookkeeping only:
21	  - Move the picked-up item to a one-line entry in
22	    `## Done`.
23	  - Move the `## In Progress` block into the
24	    [chores section](#chores-sections).
25	  - Optionally update `notes/README.md` if functionality
26	    changed.
27	
28	A cycle's commits are published to the project remote
29	either incrementally or as one batch at close-out; the
30	result must always be published at close-out. See
31	[Pushing](#pushing).
32	
33	**Sub-cycles.** When a Work commit's scope grows enough to
34	warrant its own ladder, it subdivides — `X.Y.Z-3.0`
35	Preparation, `X.Y.Z-3.1` / `X.Y.Z-3.2` Work, `X.Y.Z-3`
36	Close-out. The same three-phase shape applies recursively
37	at every depth. See [Numbering](#numbering) for the
38	suffix rule and [Sub-cycle ladders](#sub-cycle-ladders)
39	for the local-ladder mechanics.
40	
41	## Chores sections
42	
43	A **chores section** is a `##` section in
44	`notes/chores/chores-NN.md` recording one cycle:
45	
46	- One section per cycle is the default.
47	- Per-commit sections (like 0.55.0's four) are a
48	  deliberate alternative.
49	
50	The phrase **"Open" the chores section** means append a
51	`##` header to the current `notes/chores/chores-NN.md`
52	with the cycle's anticipated close-out title (e.g.
53	`## refactor: foo bar (X.Y.Z)`). The body is empty;
54	content arrives at close-out (see [Close-out](#close-out)).
55	
56	Fuller chores conventions (content rules, header sync,
57	design subsection pattern, `Commits:` formatting) live in
58	CLAUDE.md [Chores conventions](../CLAUDE.md#chores-conventions).
59	
60	## Preparation
61	
62	The cycle's first commit (`X.Y.Z-0`):
63	
64	- **Backfill the previous cycle's chores section
65	  `Commits:` ref** — see
66	  [Chores commit references](../CLAUDE.md#chores-commit-references).
67	- **Bump the version** in `Cargo.toml` to `X.Y.Z-0`.
68	- **Pick up a `## Todo` item** (if the cycle has one).
69	  Move into `## In Progress` as:
70	  - A **bold title line** — exact match of the chores
71	    section header, minus the `## ` prefix.
72	  - A **succinct problem statement**.
73	  - A **plan ladder**.
74	
75	  See [Prose form](../CLAUDE.md#prose-form). A Todo that
76	  duplicates current `## In Progress` work is a process
77	  bug.
78	- **Open the [chores section](#chores-sections)** —
79	  append a `##` header with the cycle's anticipated
80	  close-out title.
81	
82	## Work-N
83	
84	The cycle's work commits (`X.Y.Z-1`, `X.Y.Z-2`, …)
85	implement the change. As many as needed:
86	
87	- Each commit runs through the
88	  **[per-commit flow](#per-commit-flow)**.
89	- **Interim pushes** are optional (backup, progress
90	  visibility).
91	- Close-out is the only mandatory push (see
92	  [Pushing](#pushing)).
93	- **Subdivide into a sub-cycle** if a Work commit's
94	  scope grows enough (see
95	  [Sub-cycle ladders](#sub-cycle-ladders)).
96	
97	## Close-out
98	
99	The cycle's last commit (bare `X.Y.Z`) does bookkeeping
100	only — the commit body describes that bookkeeping, not
101	what happens post-squash:
102	
103	- **Move the picked-up item** from `## In Progress` to a
104	  one-line entry (with a chores `[N]` ref) in `## Done`.
105	- **Move the `## In Progress` block into the
106	  [chores section](#chores-sections)** (the title-only
107	  placeholder opened during Preparation):
108	  - Cut the problem statement + plan ladder out of
109	    `## In Progress` (drop the bold title line — the
110	    chores `##` header already carries that string).
111	  - Paste under the chores `##` header.
112	  - Sync the chores header to the **final** commit title
113	    if the cycle's scope shifted; update every anchor
114	    back-reference.
115	  - Add an `### As-built ladder` listing the cycle's
116	    commits; optional `### Outcome` notes.
117	  - Replace `## In Progress` with
118	    `_No cycle currently in progress._`.
119	- **Update `notes/README.md`** if functionality changed
120	  (new flags, new subcommands, changed behavior).
121	
122	Whether to **squash** the cycle into one commit before the
123	publishing push, or push as-is, is decided at push time —
124	see [Pushing](#pushing).
125	
126	## Numbering
127	
128	The version suffix on each commit encodes its phase —
129	the **final identifier `0` marks a Preparation**:
130	
131	- `X.Y.Z-0` — Preparation
132	- `X.Y.Z-1`, `X.Y.Z-2`, … — Work commits
133	- `X.Y.Z` — Close-out (bare version, no suffix)
134	
135	Disambiguation:
136	
137	- `-10` — Work commit #10 (final identifier `10`), not a
138	  Preparation.
139	- `-1.0` — Preparation of the `-1` sub-cycle (final
140	  identifier `0`).
141	
142	**Nesting.** Sub-cycles append another level, recursively:
143	
144	- `X.Y.Z-3.0` — Preparation of the `-3` sub-cycle
145	- `X.Y.Z-3.1`, `X.Y.Z-3.2` — its Work
146	- `X.Y.Z-3` — its Close-out
147	- `X.Y.Z-3.1.0` — Preparation of the `-3.1` sub-sub-cycle
148	
149	Sub-cycles needing no Preparation omit `.0` (`-3.1`,
150	`-3.2`, `-3`); one that grows a Preparation later adds
151	`-3.0` without renumbering siblings.
152	
153	Bump `Cargo.toml` at the start of each phase so `vc-x1 -V`
154	reports the active phase at build time.
155	
156	## Per-commit flow
157	
158	Every commit (Preparation, each Work commit, Close-out) goes
159	through:
160	
161	1. **Mark this commit `(current)`** as the first edit in
162	   `notes/todo.md > ## In Progress`.
163	2. **Do the work** (see [Iterative work](#iterative-work)
164	   for the loop-and-squash technique).
165	3. **Flip this commit `(current)` → `(done)`** in `## In
166	   Progress` — before the cargo cycle and the commit.
167	4. **Cargo cycle** (skip-able for purely-docs commits; full
168	   cycle mandatory at close-out):
169	   1. `cargo fmt`
170	   2. `cargo clippy --all-targets -- -D warnings`
171	   3. `cargo test`
172	   4. `cargo install --path . --locked`
173	   5. (re-test if anything substantive changed)
174	5. **Work review.** Stop *before* writing any description;
175	   tell the user "ready to commit." The user reviews the
176	   changes and we iterate until complete.
177	6. **Write the commit description** — see
178	   [Commit description](#commit-description).
179	7. **Commit Description review.** Show the title + body
180	   and stop. The user reviews the description. Iterate.
181	8. **Commit.** `jj commit -m "title" -m "body" -R .` for
182	   the app repo, `-R .claude` for the bot repo (`-R` last
183	   keeps the verb visible):
184	
185	   ```
186	   jj commit -m \
187	   "<type>: <short description> (<version>)" \
188	   -m "<intro paragraph>
189	
190	   - file1: gist
191	   - file2: gist
192	
193	   ochid: /.claude/<chid>" \
194	   -R .
195	   ```
196

198	
199	- **Deviation or question** — any time the work deviates
200	  from the agreed plan, or a question arises, stop and
201	  surface it; don't push through.
202	- **ESC-ESC** — the user can interrupt at any point to pull
203	  a review or question forward.
204

227	  changed (file plus a one-line gist). Sub-bullets for
228	  files with multiple distinct changes:

233	    - second distinct change, wrapping to next line
234	       with continuation indented 5
235	  ```
236	
237	  The file-by-file list is the source of truth for the
238	  cycle's mechanical change record. Chores carries the
239	  narrative + design, not a copy of it. Promote any
240	  "why" beyond one sentence to a chores `###` subsection.
241	
242	- **Session-repo (`.claude`) body**: bullets describe
243	  in-session activity rather than code changes.
244	
245	### Trailer

247	`ochid:` as the last line of the body — see
248	[ochid trailers](#ochid-trailers).

250	## Reviewing changes
251	
252	Work review looks at the **uncommitted working-copy diff**,
253	on the way to commit. The user opens diffs in their
254	editor (Zed, VSCode); jj commands are for terminal:
255	
256	- `jj diff` — working-copy diff (uncommitted)
257	- `jj diff -r @-` — diff of the previous commit
258	- `jj diff --from <X> --to <Y>` — any two revisions
259	- `jj show -r <X>` — description + diff for one rev
260	
261	Don't `jj edit -r @-` to view a past commit — that marks
262	it mutable and shifts `@`; use `jj diff -r @-` or
263	`jj show -r @-`.
264	
265	See [Sub-cycle ladders](#sub-cycle-ladders) for the
266	close-out squash recipe and recovery; revset primitives
267	are in [`jj-revsets.md`](jj-revsets.md).

269	## Pushing
270	
271	### Policy
272	
273	Push is **discretionary** during the cycle (backup,
274	progress visibility) and **mandatory at close-out** —
275	the cycle's result must be published.
276	
277	### Shape at close-out push
278	
279	Decide the shape and get user approval before pushing —
280	the choice is hard to undo once on the target. Surface
281	the options, wait for the user.
282	
283	- **Squash to one commit** — single entry on the target.
284	  Right for straightforward changes where the Work-N is
285	  focused on one or two files.
286	- **Merge non-ff** — `main` gains a merge commit
287	  (`X.Y.Z`); cycle commits stay reachable via two
288	  parents. `jj log -r ..@ -n <N>` shows the trapezoidal
289	  shape. Set up: `jj rebase -r <tip> --onto <prev>
