2	
3	## Cycles
4	
5	A cycle has three phases:
6	
7	- **[Preparation](#preparation)** (`X.Y.Z-0`) — the cycle's
8	  first commit. Sets up the cycle:
9	  - Backfill the previous cycle's chores `Commits:` ref.
10	  - Bump `Cargo.toml` to `X.Y.Z-0`.
11	  - Pick up a `## Todo` item (typically via `## Priorities`)
12	    into `## In Progress` (bold title + succinct problem
13	    statement + plan ladder).
14	  - Open the [chores section](#chores-sections).
15	- **[Work-N](#work-n)** (`X.Y.Z-1`, `X.Y.Z-2`, …) — the
16	  commits that implement the change. As many as the change
17	  needs; each runs through the
18	  [per-commit flow](#per-commit-flow).
19	- **[Close-out](#close-out)** (bare `X.Y.Z`) — the cycle's
20	  last commit. Bookkeeping only:
21	  - Move the picked-up item to a one-line entry in
22	    `## Done`.
23	  - Move the `## In Progress` block into the
24	    [chores section](#chores-sections).
25	  - Optionally update `notes/README.md` if functionality
26	    changed.
27	
28	A cycle's commits are published to the project remote
29	either incrementally or as one batch at close-out; the
30	result must always be published at close-out. See
31	[Pushing](#pushing).
32	
33	**Sub-cycles.** When a Work commit's scope grows enough to
34	warrant its own ladder, it subdivides — `X.Y.Z-3.0`
35	Preparation, `X.Y.Z-3.1` / `X.Y.Z-3.2` Work, `X.Y.Z-3`
36	Close-out. The same three-phase shape applies recursively

157	
158	Every commit (Preparation, each Work commit, Close-out) goes
159	through:
160

419	## Sub-cycle ladders
420	
421	When a Work commit subdivides into a sub-cycle (see
422	[Numbering](#numbering) for suffix nesting), its Work
423	commits typically live as a local jj `@` chain and
424	**collapse into the sub-cycle's Close-out** before the
425	parent cycle continues. Ladder commits are scratch —
426	for review and bisection only.
427	
428	### Per-Work-commit contract within a ladder
429	
430	For each Work commit in the ladder:
431	
432	1. `jj new -R .` — create a fresh empty `@`.
433	2. Do the commit's work.
434	3. Run `cargo test --bins`. **Non-negotiable** — build
435	   and clippy alone miss regressions until a later
436	   commit runs the full suite, raising bisection cost.
437	4. `jj describe -m "..." -m "..." -R .` — working title
438	   only (no version suffix); the sub-cycle Close-out
439	   collects everything into one final commit with the
440	   `(X.Y.Z-N)` marker.
441	
442	### Navigating the ladder
443	
444	Common moves:
445	
446	- `jj log -r '<base>::' -R .` — see the whole ladder
447	  from its base.
448	- `jj edit -r <prefix> -R .` — jump `@` to any ladder
449	  commit by chid prefix; useful for bisection.
450	- `jj edit @-- -R .` — quick-jump back two commits.
451	- `jj diff -r <chid> -R .` — review one commit in
452	  isolation.
453	
454	Modifications to any ladder commit rewrite it in place;
455	descendants auto-rebase.
456	
457	### Close-out: squash the ladder
458	
459	When all ladder Work commits are done and tests pass:
460	
461	```
462	jj squash --from "<base>..@-" --into @ -u -R .
463	```
464	
465	`<base>` is the parent of the first ladder commit; `-u`
466	keeps `@`'s description and discards the sources'.
467	After squash, history is linear: `<base> → @`;
468	intermediate commits are auto-abandoned.
469	
470	Then `vc-x1 push <bookmark>` as for any other commit.
471	
472	For N = 1 the squash is a no-op (`<base>..@-` is empty
473	when `@-` is `<base>`); push the single commit directly.
474	
475	### Recovery
476	
477	If a ladder commit goes wrong, back out without losing
478	prior commits:
479	
480	- **Discard the current commit.** `jj abandon @ -R .`
481	  drops it; you get a fresh empty `@` on the same
482	  parent.
483	- **Edit an earlier commit.** `jj edit -r <chid> -R .`,
484	  make corrections, then `jj edit -r <last-ladder-chid>`
485	  to return. Descendants auto-rebase.
486	- **Discard the entire ladder.** `jj op log -R .` shows
487	  the op history; `jj op restore <op-id> -R .` reverts
488	  to that point. Full undo — removes *all* ladder work
489	  after the chosen op. Use only to start over.

12	today's `--use-template <CODE[,BOT]>`.
13	
14	The mechanism is **pure file copy** — no variable
15	substitution, no transformation. The bot deliberately
16	avoided "templating" / "seeding" as concept names; "seed"
17	implies growth and "template" implies parameterization,
18	neither of which this mechanism does. It just copies.
19	
20	## Goal
21	
22	One mechanism for "copy these files into the workspace at
23	init time" rather than per-file flags. The user supplies
24	one or more source paths; init copies them into the new
25	workspace during the copy phase, before commits.
26	
27	## Surface
28	
29	- `--init-from-code=<glob>` — copy files matched by
30	  `<glob>` into the code repo (non-recursive).
31	- `--init-from-bot=<glob>` — same, into the `.claude/`
32	  companion. Only meaningful under dual.
33	- `--init-from=<glob>` — shorthand for `--init-from-code`
34	  (since por only has code, and dual users typically copy
35	  into code more often than bot).
36	- `--init-from-recursive=<glob>` /
37	  `--init-from-code-recursive=<glob>` /
38	  `--init-from-bot-recursive=<glob>` — recursive variants.
39	
40	Each flag accepts a **shell glob** (expansion done by the
41	shell; `vc-x1` receives the expanded path list). Each may
42	be specified multiple times — the result is the additive
43	union of all sources. Order matters for collisions (see
44	below).
45	
46	## Behavior
47	
48	- **Copy semantics** — files only; preserves relative
49	  layout under the source root. The bot's working
50	  assumption is `cp -a` semantics (preserve symbolic
51	  links and executable bits); confirm at design time.
52	- **Collision: last writer wins, with a warning.** If two
53	  `--init-from*` flags resolve to the same destination
54	  file, the later one overwrites the earlier; `vc-x1`
55	  emits a warning naming both sources. The bot thinks
56	  warnings are right here — silent overwrite is a
57	  footgun; erroring would block valid layering use cases
58	  (a base directory + per-project tweaks).
59	- **Canned writes suppressed when copying is engaged.**
60	  Today `init` writes a canned `.vc-config.toml` and
61	  `.gitignore`. With any `--init-from*` present, **both
62	  canned writes are suppressed entirely**. The user opted
63	  in to full control of the copied content; init doesn't
64	  layer canned defaults underneath.
65	- **Dual post-copy check (deferred).** After copying
66	  completes for a dual workspace, if `.vc-config.toml`
67	  is missing or lacks `[workspace] other-repo`, init
68	  **warns** (does not error). The workspace looks dual
69	  (has `.claude/`) but acts por at runtime; downstream
70	  subcommands enforce the invariant. See
71	  [Deferred-validation](#deferred-validation).
72	
73	## Deferred-validation
74	
75	Init's `.vc-config.toml` check is a **warning**, not an
76	error, to support workflows where the user plans to
77	supply the config post-init (e.g. checking in the
78	workspace shell first, then populating config files in a
79	follow-up commit).
80	
81	The error happens at the **first downstream invocation**:
82	`default_scope` (or a new explicit check) detects the
83	broken-dual state — `.claude/` exists but `.vc-config.toml`
84	doesn't (or lacks `other-repo`) — and refuses to proceed
85	with a clear error pointing at the missing file.
86	
87	Today `default_scope` silently falls back to
88	`Scope([Code])` when `.vc-config.toml` is absent
89	(`src/common.rs:594`). That silent fallback is exactly
90	the "looks dual, acts por" surprise this design avoids;
91	fixing it is a prerequisite for the post-init copy
92	workflow.
93	
94	## Fixed filename
95	
96	`.vc-config.toml` stays the fixed name; overriding it is
97	deferred until a real use case surfaces (would ripple
98	through every subcommand's lookup code — `default_scope`,
99	`find_workspace_root_from`, `validate-desc`, `fix-desc`,
100	`push`, `clone`, …).
101	
102	## Subsumes
103	
104	- `--config <path>` — never really built; the
105	  `.vc-config.toml` write axis's collapse
106	  left the capability un-claimed. Equivalent under
107	  copying: `--init-from=<src>/.vc-config.toml`.
108	- `--gitignore <path>` — never built; equivalent under
109	  copying: `--init-from=<src>/.gitignore`.
110	- `--use-template <CODE[,BOT]>` — today's coarse
111	  whole-repo flag. Subsumed by recursive variants:
112	  - `--use-template code-tpl/` →
113	    `--init-from-code-recursive=code-tpl/*`.
114	  - `--use-template code-tpl/,bot-tpl/` → two flags:
115	    `--init-from-code-recursive=code-tpl/*` +
116	    `--init-from-bot-recursive=bot-tpl/*`.
117	
118	The bot thinks `--use-template` can be retired once
119	copying ships, but a back-compat shim that translates
120	old form → new form is cheap and worth keeping for one
121	release cycle.
122	
123	## Naming rationale
124	
125	The mechanism is named **copying** (not "templating," not
126	"seeding," not "scaffolding") because all three imply
127	something the mechanism doesn't do:
128	
129	- "Templating" implies parameterization / variable
130	  substitution. We deliberately don't do that.
131	- "Seeding" implies growth (a seed grows into a plant);
132	  the copied files don't grow — they sit where they
133	  landed.
134	- "Scaffolding" implies project-structure generation
135	  (Rails generators, Yeoman); the mechanism is just
136	  `cp -r`, no structure-aware logic.
137	
138	"Copying" is literal: source files go to destination
139	paths. The flag family `--init-from*` keeps the verb out
140	of the surface — the flag describes *what* (source-to-
141	destination), not *what kind of operation*. If a future
142	mechanism does layer substitution on top of copy, it's a
143	separate feature with its own name.
144	
145	## Open questions (resolve at design time)
146	
147	- **Variable substitution.** Should the copy step support
148	  `{{name}}` / `{{account}}` substitution? The bot
149	  thinks **no** — keep the mechanism pure copy. Users
150	  who need substitution can pre-process and pass the
151	  result. Adding substitution invites a substitution-
152	  language rabbit hole and breaks the "copying" framing
153	  we just settled on.
154	- **Symbolic links and executable bits.** Preserve, or
155	  flatten? Probably preserve — `cp -a` semantics.
156	  Worth confirming at design time.
157	- **Source-not-found behavior.** Hard error (typo
158	  protection) or soft skip (let globs return empty)?
159	  Probably hard error — a missing source is almost
160	  always user mistake. Empty glob expansion (the shell
161	  passing zero paths) is fine.
162	- **Interaction with `vc-x1 clone`.** Clone seeds from
163	  an existing remote, so copying overlays *on top of*
164	  the cloned content. Same flag set, same collision
165	  rules.
166	- **Mechanism beyond init?** A future
167	  `vc-x1 <subcommand> --copy-from=<glob>` to layer
168	  files into an existing workspace would be the same
169	  mechanism with a different host command. The bot
170	  thinks defer until a real use surfaces; `--init-from*`
171	  is the only surface today.

774	### Resolution chain
775	
776	The per-axis sections above each say "CLI → user-config →
777	default (or error)." That's a sketch; the full resolution
778	chain has **five layers**, with the bottom varying per
779	axis. The same chain applies to **every axis** and every
780	field a config carries (account, repo category/value,
781	privacy, topology, copying sources, …) — nothing axis-
782	specific.
783	
784	#### Layers (highest precedence first)
785	
786	1. **CLI flag** — `--por`, `--account`, `--private`,
787	   `--config <path>`, `--global-config <path>`, etc. The
788	   per-invocation surface. CLI is god — wins over every
789	   other layer when present. CLI carries *values* only;
790	   there are **no per-axis "default-X" flags** (to change
791	   a default, edit a config — local, global, or the
792	   baked-in starting point).
793	2. **Environment variable** — `VC_X1_<KEY>`. The
794	   per-session surface, set via `export` or one-shot
795	   prefix. Loses to CLI.
796	3. **Local config** — `./.vc-config.toml` (the workspace
797	   metadata file), or whatever `--config <path>` resolved
798	   to. Per-project durable intent. Loses to env-var and
799	   CLI; **may carry any field a CLI flag exposes** — no
800	   carve-outs (a local config can pin
801	   `[global] config-path` just as it pins `account`).
802	4. **Global config** — `~/.config/vc-x1/config.toml`
803	   (XDG-aware), or whatever `--global-config <path>` /
804	   `VC_X1_GLOBAL_CONFIG` / a local-config
805	   `[global] config-path` resolved to. Per-user durable
806	   defaults. Lowest user-editable layer.
807	5. **Baked-in default config** — a `default-config.toml`
808	   compiled into the binary via `include_str!`. Acts as
809	   the bottom-of-chain fallback for axes with natural
810	   defaults. The user can extract it with **`vc-x1
811	   config dump`** (a new subcommand), modify, and save
812	   as their global config or as a local override. Future:
813	   `linkme`-style registry could ship multiple baked-in
814	   profiles selectable at install or post-install
815	   (deferred).
816	
817	Each user-facing layer (1–4) is optional. Layer 5
818	(baked-in) is always present.
819	
820	#### Two-class resolution (per axis)
821	
822	Not every key has a natural default. The chain resolves
823	differently for the two classes:
824	
825	- **Natural-default keys** — Topology, Privacy, Remote
826	  category, Copying. The baked-in supplies a default
827	  (`dual`, `public`, `github-create`, `none`). The chain
828	  effectively ends at layer 5, never at "error" — naked
829	  `vc-x1 init foo` with no user config works.
830	- **User-specific keys** — `[default].account`, account
831	  repo URLs (`[account.<a>].repo.category.remote = "..."`),
832	  account repo fixtures. The baked-in cannot supply these
833	  — there's no universal `git@github.com:<your-handle>`
834	  to bake in. The chain ends at "Error" if layers 1–4
835	  don't supply: *"no `<key>` specified; set it in
836	  `~/.config/vc-x1/config.toml` or via the appropriate
837	  CLI flag."*
838	
839	The principle is **"defaults where natural; errors only
840	for user-specific keys"** — it matches what `resolve_repo`
841	already does today for `--account` / `--repo` (errors
842	specifically when those keys are missing, not when any
843	key is missing).
844	
845	#### Escape hatches
846	
847	- **`--no-local-config`** — skip layer 3 entirely for this
848	  invocation. Today functionally equivalent to runtime
849	  `--por` (because local config carries only topology
850	  metadata); add as a peer flag once local config gains
851	  non-topology fields.
852	- **`--no-global-config`** — skip layer 4 entirely.
853	  Necessary for tests / CI / "ignore my defaults this
854	  once."
855	
856	Both flags are layer-1 (CLI) — they can't themselves be
857	pinned by config, since their purpose is to ignore config.

## What's genuinely good

- **Three-pass methodology** (audit → commonality inversion → axes). The inversion in `-2` is the cycle's pivotal move: reframed "we have a problem everywhere" to "the right pattern already exists, extend it." That mental flip is what made the rest tractable.
- **Axis decomposition is correct decomposition.** Calling out that `--por` is a *bundle* of (Topology, Vc-config, Remote, Privacy, Copying, Scaffolding) opens design space the bundle hid. The litmus is `audit.md:752` — "A user wanting a fully-plain single repo today can't spell it." That's a real defect of the bundle framing.
- **A2 collapse was earned.** You didn't keep `.vc-config.toml` write as an axis just because you initially listed it. The correlation argument is correct: presence of `.vc-config.toml` ≡ Topology. Honest housekeeping.
- **Two-class principle is sound** ("defaults where natural; errors only for user-specific keys"). This is the correct generalization of what `resolve_repo` already does. Baked-in default config + `vc-x1 config dump` closes the "what does layer-4-empty mean?" question elegantly.
- **T7-only promotion.** Resisting the urge to seed all 14 Gaps into Todo is the right call. Cheapest concrete equalization that validates the topology-from-config rule = good prototype choice.
- **Status note + "implementation will diverge" framing** (`audit.md:19-37`) is humility I'll thank you for in 0.65.0.

## Concerns I'd raise, ordered by conviction

### 1. Runtime `--por` everywhere is overloaded — I'd not ship this

`audit.md:530-534` says `--por` becomes a runtime override on every subcommand, short-circuiting `default_scope → Scope([Code])` regardless of workspace state. That mounts two meanings on one spelling:

- **Creation-time `--por`**: "this workspace is single."
- **Runtime `--por`**: "ignore the bot side for this invocation."

These are different things. Topology of an existing workspace is *not* mutable per-invocation (the `.claude/` dir either exists or doesn't). And the runtime escape already exists as `--scope code` / `-R .` for the `CommonArgs` family — the right pattern (per your own `## Commonality` summary).

**Push:** reserve `--por` for creation-time. For runtime "just my code," lean on `--scope code` (existing, well-understood) or add an unambiguous `--ignore-bot` if `--scope` doesn't fit the call site. This also makes Gap #8 ("Runtime `--por` on all subcommands") evaporate — and that's a *good* outcome; one fewer surface to maintain.

### 2. "Exactly-one-of `--por` / `--dual` with default-dual" is contradictory phrasing

`audit.md:521-522` says clap-enforced exactly-one-of; `:525` says default-dual. If neither flag is passed, either clap rejects (true exactly-one-of, friction for the common case) or it accepts (default kicks in, "exactly-one-of" is misleading). Same shape on `--private` / `--public` at `:643-647`.

**Push:** spell it "**at most one of**; absence → workspace-config or baked-in default." Honest about what the default does. Same fix for Privacy.

### 3. `--init-from-recursive` doubles the surface for the same capability

`copying.md:29-38` defines six flags: `--init-from`, `--init-from-code`, `--init-from-bot`, and `-recursive` variants of each. But recursion is a property of the *operand*, not the flag: `cp src/* dst/` is recursive whether you said `-r` or not; `cp src/foo.txt dst/` isn't. The shell expands the glob; vc-x1 walks each resolved path.

**Push:** one flag per side. `--init-from-code=<glob>` does the right thing per resolved path (file → file copy; dir → recursive copy). Cuts the surface in half, matches `cp` semantics users already have in their head. The "recursive" naming muddies what the flag controls vs. what the operand controls.

### 4. `--repo none` × Topology interaction isn't spelled out

The Remote axis Decisions (`audit.md:596-624`) introduces `--repo none` as a peer category, with `--account` skipped under it. Fine in isolation. But `--repo none` × `--dual` means "dual workspace with no remote for either side." The bot/sync/push workflow assumes remote-backed `.claude/`. Is dual+no-remote first-class, or rejected at parse time?

**Push:** add one paragraph to the Remote axis (or matrix footnotes) on the Topology × Remote=none interaction. Don't leave it implicit — a future user will try `init --dual --repo none` and get a confused error later in the workflow.

### 5. Resolution chain "CLI replaces config" for list-typed copying — call out the choice

`audit.md:697-699` says: "If user passes any `--init-from*` on CLI, the config-pinned list is ignored — match the broader chain rule."

The "broader chain rule" is about scalar values where "wins" unambiguously means "replaces." For list-valued axes, users coming from `LD_LIBRARY_PATH` / `PATH` expect merge, not replace. The replace choice is defensible (predictability beats expressivity) but it's not the obvious choice.
