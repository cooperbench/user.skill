> AGENT

The exact 2× is arithmetic, not physical. Two-point fit has:

```
framing = min_low − N_LOW · (min_high − min_low) / (N_HIGH − N_LOW)
d(framing)/d(min_low) = N_HIGH / (N_HIGH − N_LOW) = 1000/900 ≈ 1.11
```

Reverse-engineering your numbers: run 1 had `min_low=60, min_high=500` → framing 11.11. Run 2 had `min_low=70, min_high=500` → framing 22.22. Only `min_low` moved, by ~10 ns, which the fit amplifies 1.11× into +11 ns on framing. The "2×" is just 11 + 11. So the real problem isn't a 2× cost — it's that `min_low` picked up ~10 ns of slop while `min_high` stayed clean.

Why `min_low` is noisy but `min_high` isn't: calibration runs on the **unpinned main thread** and `measure(N_LOW=100)` is called first, right after a mere 1000-iter warmup. That's ~500 µs of work — too short to guarantee full boost-clock ramp. By the time `measure(N_HIGH=1000)` runs, the CPU is at peak, so `min_high` reliably hits its ~500 ns floor. `min_low`'s floor varies between runs depending on how far the boost ramp had progressed.

The fit is also structurally fragile here: with only 10k samples and a 10× inner-size ratio, the slope/intercept are very sensitive to small endpoint noise, and the `black_box(1)` body is so cheap that `min_low` is dominated by framing rather than loop cost — exactly where we're trying to measure.

Ranked fixes (pick one or combine):
1. **Pin the main thread** to the first `--pin` core for calibration (same thermal/boost state as the bench). Single biggest coherence win — calibration should run under the conditions the bench runs under.
2. **Longer warmup + more samples**, e.g. `CAL_WARMUP=100_000`, `CAL_SAMPLES=100_000`. Cheap, ensures boost ramp and gives min a better shot at its floor.
3. **Wider N spread** (`N_LOW=10, N_HIGH=10_000`) drops the noise-amplification coefficient from 1.11× to ~1.01×, so any remaining noise barely perturbs framing.
4. **Sanity-check loop** — run calibration N=3–5 times, require framing/loop to be within e.g. 20% tolerance; retry or warn otherwise. Belt-and-suspenders.

My recommendation: do (1) + (2) first — they address the root cause (calibration running under different conditions than the bench, before boost) rather than papering over it. (3) is a nice-to-have robustness improvement. Which direction do you want to take?

Now I have the full picture. Short answer first:

**On "should we unpin after calibration?":** functionally irrelevant. When `--pin` is set, the main thread parks in `pthread_join` during the bench, so its affinity doesn't compete with anything. The *actually useful* related move is the **inverse**: pin main *for calibration* even when the user didn't specify `--pin`. The empirical gap is stark: with `--pin 5,10` calibration gives framing 11.11 ns / stdev 787 ns / p99.99 tail 272 µs; without `--pin`, framing jumps to **27.78 ns** and tail blows out to **5.5 ms**. The noise doesn't come from the bench — it comes from running calibration unpinned.

So the cleaner contract is: calibration always runs pinned (stable environment), bench runs per `--pin` (user's choice), main's pinning during bench is a don't-care. Unpinning after calibration is neither necessary nor harmful; skip unless a concrete reason shows up later.

**What's happening:** with `--no-pin-cal` (main unpinned entirely), bench threads get scheduler flexibility and land where co-location is best — same CCX, shared L3 — hitting the spin-spin fast path (min-p1 at **130–410 ns**, sub-µs).
