**1. Simple macro (no dependencies)**

```rust
macro_rules! timed {
    ($label:expr, $block:expr) => {{
        let start = std::time::Instant::now();
        let result = $block;
        eprintln!("{}: {:?}", $label, start.elapsed());
```

**2. `#[tracing::instrument]` from the `tracing` crate** — attribute macro on functions, gives you structured timing with spans. More machinery than you likely need here.

**3. Drop guard** — a struct that prints elapsed time when it goes out of scope:

```rust
struct Timer(&'static str, std::time::Instant);
impl Timer {
    fn new(label: &'static str) -> Self { Self(label, std::time::Instant::now()) }
}
impl Drop for Timer {
    fn drop(&mut self) { eprintln!("{}: {:?}", self.0, self.1.elapsed()); }
}
```

Usage: `let _t = Timer::new("resolve_files");` — times the enclosing scope.

For your use case (a handful of sections in `main`), the **simple macro** is the sweet spot — zero dependencies, one line per timed block, and captures the return value. The drop guard is nice for function-level timing without touching the return. `tracing` is overkill here.

> DEVELOPER

The total_start_time spans the entire main so the drop seems better but I do I know when the compiler will actually drop and _t?

> AGENT

At the end of the scope it's declared in — for a local in `main()`, that's when `main` returns. Rust's drop order is deterministic: locals drop in **reverse declaration order** at the end of their enclosing scope.

So `let _t = Timer::new("total");` at the top of `main` would fire its `Drop` as the very last thing (well, after all locals declared after it drop, since it's reverse order).

The `_t` prefix matters too: `_t` is a named binding that lives to end of scope. A bare `_` would drop **immediately** — that's a common gotcha:

```rust
let _t = Timer::new("total");  // drops at end of scope ✓
let _ = Timer::new("total");   // drops immediately, useless ✗
```

So for your case, the drop timing is predictable and correct. The one caveat is you can't control *exactly* where in the cleanup sequence it prints relative to other drops, but since your other locals are just `Vec`s and primitives, that's irrelevant here.
