**Thread control**: Too vague to design against yet. Worth naming what you're after — thread count per bench? Per-thread pinning lists? NUMA awareness? — and adding a todo, but I wouldn't speculate on the API until a concrete bench needs it.

Order I'd suggest: reframe docs first (shapes the vocabulary), then add per-item doc comments in that new voice, then the rename, then todo/done move as a small tail commit. Thread-control as a separate future feature.

11	effect — it's the arithmetic of the two-point fit amplifying ~10 ns
12	of endpoint noise.
13	
14	### Analysis
15	
16	Two-point fit:
17	
18	```
19	framing  = min_low − N_LOW · (min_high − min_low) / (N_HIGH − N_LOW)
20	d(framing)/d(min_low)  = N_HIGH / (N_HIGH − N_LOW) = 1000 / 900 ≈ 1.11
21	d(framing)/d(min_high) = −N_LOW / (N_HIGH − N_LOW) = −100 / 900 ≈ −0.11
22	```
23	
24	Reverse-engineering two observed runs (3900X, `--pin 5,10`, `-D 1`):
25	
26	- Run A: `min_low = 60 ns, min_high = 500 ns` → framing 11.11 ns,
27	  loop/iter 0.4889 ns.
28	- Run B: `min_low = 70 ns, min_high = 500 ns` → framing 22.22 ns,
29	  loop/iter 0.4778 ns.
30	
31	Only `min_low` moved (+10 ns). The fit amplified that by 10/9 = 1.11
32	→ +11.11 ns on framing. 11.11 + 11.11 = 22.22. The "exact 2×" is
33	numerology; the real defect is ~10 ns of slop on `min_low`.
34	
35	Why `min_low` floats but `min_high` is stable: `measure(N_LOW=100)`
36	runs first, right after a mere 1,000-iter warmup (~500 µs of work).
37	That's too short to guarantee the CPU has reached peak boost. By the
38	time `measure(N_HIGH=1000)` runs, boost is fully ramped, so
39	`min_high` reliably hits its ~500 ns floor.
40	
41	### --pin vs unpinned main thread
42	
43	`main.rs` already pins the main thread to `pin_cores.first()` before
44	calibration. Measured on 3900X, `-d 3`:
45	
46	| configuration             | framing    | stdev      | p99.99 tail |
47	|---------------------------|-----------:|-----------:|------------:|
48	| `--pin 5,10`              |  11.11 ns  |    787 ns  |    272 µs   |
49	| no `--pin` (main unpinned)|  27.78 ns  | 12,967 ns  |    5.5 ms   |
50	
51	So when `--pin` is omitted, calibration itself inherits the unpinned
52	jitter (migrations, frequency wobble, CCX changes), and the framing
53	number is clearly elevated beyond the true floor. The adjustment we
54	subtract is then derived from a different measurement regime than the
55	one we want.
56	
57	### Should main be unpinned after calibration?
58	
59	Functionally irrelevant. When bench threads run, the main thread
60	blocks in `pthread_join` — it's parked, not runnable, so its affinity
61	doesn't compete with anything. Keeping or dropping the pin changes
62	nothing observable.
63	
64	The cleaner contract is:
65	
66	- Calibration always runs pinned (stable environment, reliable
67	  framing/loop numbers).
68	- Bench runs per `--pin` (user's requested environment).
69	- Main's pinning during the bench phase is a don't-care.
70	
71	So: leave main's pin state alone after calibration; don't add a
72	ceremonial unpin step unless a concrete reason emerges later.
73	
74	### Recommended changes
75	
76	1. **Pin main for calibration regardless of `--pin`.** Even when the
77	   user didn't specify `--pin`, briefly pin main (to `pin_cores[0]`
78	   if set, otherwise a fixed default such as core 0, or a new
79	   `--cal-pin` flag) so calibration always runs in a stable
80	   environment. Biggest coherence win — calibration stops depending
81	   on how the bench is configured.
82	
83	   Add a `--no-pin-cal` flag that reverts to the pre-0.6.0 behavior
84	   (skip the calibration-time pin, so main stays unpinned when
85	   `--pin` is absent). Makes A/B comparison easy — run the same
86	   bench with and without `--no-pin-cal` to see the calibration
87	   difference directly, and gives a quick escape hatch if the new
88	   default ever misbehaves on someone else's box.
89	
90	   **Resolved in dev6** — semantics of `--pin` + `--no-pin-cal`:
91	   `--no-pin-cal` now always wins, regardless of `--pin`. With
92	   `--pin 5,10 --no-pin-cal`, bench threads still pin to 5,10 but
93	   calibration runs with main unpinned (affinity = full startup
94	   mask). Lets the user decouple the calibration environment from
95	   the bench pinning pool when they want the bench pool fixed but
96	   the cal free-running.
97	2. **Longer warmup.** Bump `CAL_WARMUP` from 1,000 to ~100,000
98	   iterations so boost ramp completes before `measure(N_LOW)` runs.
99	3. **More samples.** Bump `CAL_SAMPLES` from 10,000 to ~100,000 so
100	   the min-of-samples estimator reliably hits the theoretical floor.
101	4. **Wider N spread.** Raise `N_HIGH` to ~10,000 (or drop `N_LOW` to
102	   ~10). This drops the noise-amplification coefficient on `min_low`
103	   from 1.11× to ~1.01×, so any remaining endpoint noise barely
104	   perturbs framing.
105	5. *(Optional)* **Sanity-check retry.** Run calibration 3–5 times;
106	   require framing/loop to agree within a tolerance. Retry or warn
107	   otherwise. Belt-and-suspenders for the rare bad run.
108	
109	### Interpretation note: the low min-p1 / p1-p10 bands are real
110	
111	Unpinned `mpsc-2t` runs show a very low `min-p1` band — e.g. `first
112	= 240 ns, last = 6,003 ns` in the 3s unpinned run above, while the
113	pinned `--pin 5,10` run's `min-p1` sits at `7,935…8,175 ns`. That
114	gap isn't calibration noise or a measurement artifact.
115	
116	When both round-trip endpoints stay hot (scheduler co-locates them
117	on the same CCX, neither parks in a futex, both spin on the
118	channel), `std::sync::mpsc` — `crossbeam-channel` under the hood on
119	modern Rust — can round-trip in well under a microsecond. Pinning
120	to `5,10` on a 3900X likely forces cross-CCX placement (cores 5 and
121	10 are on different chiplets), which adds cache-coherence latency
122	and raises the floor. So the low bands in unpinned runs are a real
123	operating regime — "both ends hot and spinning" — not a glitch, and
124	the calibration rework here should not distort them.

90	/// Format a CPU set as a compact range list with a count suffix,
91	/// e.g. `"0-11,13-15 (15 cpus)"` or `"5 (1 cpu)"`.
92	pub fn affinity_summary(set: &libc::cpu_set_t) -> String {
93	    let cpus: Vec<usize> = (0..libc::CPU_SETSIZE as usize)
94	        .filter(|&i| unsafe { libc::CPU_ISSET(i, set) })
95	        .collect();
96	    if cpus.is_empty() {
97	        return "<empty>".to_string();
98	    }

100	    let mut start = cpus[0];
101	    let mut prev = cpus[0];
102	    for &c in &cpus[1..] {
103	        if c == prev + 1 {
104	            prev = c;
105	        } else {
106	            ranges.push(if start == prev {
107	                start.to_string()
108	            } else {
109	                format!("{start}-{prev}")
110	            });
111	            start = c;
112	            prev = c;
113	        }
114	    }
115	    ranges.push(if start == prev {
116	        start.to_string()
117	    } else {
118	        format!("{start}-{prev}")
119	    });
120	    format!(
121	        "{} ({} cpu{})",
122	        ranges.join(","),
123	        cpus.len(),
124	        if cpus.len() == 1 { "" } else { "s" }
125	    )
126	}

51	    //

55	    // the cause of the "exact 2×" framing anomaly pre-0.6.0.

57	        (min_high - min_low) as f64 / (N_HIGH - N_LOW) as f64
58	    } else {
