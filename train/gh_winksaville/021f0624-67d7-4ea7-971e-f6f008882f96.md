6	## Calibration robustness (0.6.0)
7	
8	Calibration in `overhead.rs` occasionally produces a framing value
9	exactly 2× the typical — e.g. 11.11 ns one run, 22.22 ns the next,
10	on `iiac-perf mpsc-2t --pin 5,10 -D 1` (3900X). Not a physical 2×
11	effect — it's the arithmetic of the two-point fit amplifying ~10 ns
12	of endpoint noise.
13	
14	### Analysis
15	
16	Two-point fit:
17	
18	```
19	framing  = min_low − N_LOW · (min_high − min_low) / (N_HIGH − N_LOW)
20	d(framing)/d(min_low)  = N_HIGH / (N_HIGH − N_LOW) = 1000 / 900 ≈ 1.11
21	d(framing)/d(min_high) = −N_LOW / (N_HIGH − N_LOW) = −100 / 900 ≈ −0.11
22	```
23	
24	Reverse-engineering two observed runs (3900X, `--pin 5,10`, `-D 1`):
25	
26	- Run A: `min_low = 60 ns, min_high = 500 ns` → framing 11.11 ns,
27	  loop/iter 0.4889 ns.
28	- Run B: `min_low = 70 ns, min_high = 500 ns` → framing 22.22 ns,
29	  loop/iter 0.4778 ns.
30	
31	Only `min_low` moved (+10 ns). The fit amplified that by 10/9 = 1.11
32	→ +11.11 ns on framing. 11.11 + 11.11 = 22.22. The "exact 2×" is
33	numerology; the real defect is ~10 ns of slop on `min_low`.
34	
35	Why `min_low` floats but `min_high` is stable: `measure(N_LOW=100)`
36	runs first, right after a mere 1,000-iter warmup (~500 µs of work).
37	That's too short to guarantee the CPU has reached peak boost. By the
38	time `measure(N_HIGH=1000)` runs, boost is fully ramped, so
39	`min_high` reliably hits its ~500 ns floor.

1	# iiac-perf
2	
3	A general-purpose latency microbenchmark harness for Rust. Each
4	bench runs against a wall-clock time budget with auto-sized loop
5	counts, reports a percentile-band histogram in nanoseconds, and
6	subtracts calibrated apparatus overhead (timer-pair framing +
7	loop-per-iter) so the output reflects the workload, not the
8	measurement loop.
9	
10	Highlights:
11	
12	- Time-based runs (`-d SECONDS` per bench, `-D SECONDS` total)
13	  with auto-sized outer/inner loop counts.
14	- Band-based histogram (min→p1, p1→p10, …, p99→max) with count,
15	  mean, range, and an adjusted-mean column.
16	- Per-thread CPU pinning (`--pin`) with independent calibration
17	  pinning (`--no-pin-cal`), so the cal environment stays stable
18	  regardless of where bench threads land.
19	- Plug in new workloads by implementing the `Bench` trait and
20	  registering in `src/benches/`.
21	
22	The first benches measure Inter-Intra Application Communication
23	— function calls, async calls, channels, serde — which is what
24	seeded the project name. The harness itself is workload-agnostic.
25	
26	## Design (0.2.0)
27	
28	Design a Rust app that can measure the cost of various (IIAC) techniques.
29	By IIAC I mean all communication techniques between and within
30	applications such as regular function calls vs async function calls vs
31	channels vs serde/deser of json or zero-copy messaging using io_uring and
32	potentially any other technique. It would include between threads or
33	processes or apps on the same computer or between apps on the same LAN or
34	between apps over a WAN.
35	
36	Ideally I'd like to be able to see a histogram of the range of times of the
37	send and receive costs, not just the mean/average of 10^3 or 10^6 invocations.
38	So the cost of the work should or could be something near-zero such as just
39	echoing the input, but maybe there is value in doing some constant but
40	variable amount of work to verify it's in-consequential. One thing I think we
41	need to be aware of is that if we make the work too simple the compiler could
42	just keep things in registers which would not be representative of "real" work.
43	
44	We should start simple, like comparing normal and async function calls and
45	later expand to other techniques.
46	
47	## Usage
48	
49	```
50	iiac-perf [BENCH...] [-d SECONDS] [-o OUTER] [-i INNER]
51	```
52	
53	`BENCH` is one or more registered bench names, or `all` for every
54	registered bench. **With no arguments, `iiac-perf` prints the
55	available list and exits — that's the source of truth for which
56	benches the current build registers.**
57	
58	Flags (also visible via `-h` / `--help`):
59	- `-d`, `--duration SECONDS` — target wall-clock seconds per bench
60	  (default `5.0`); the outer loop runs until this time is reached
61	  (inner auto-sizes). See chores `0.3.1-dev1` for the empirical
62	  study behind the default — longer (`-d 30`+) gives
63	  publication-grade stability. Mutually exclusive with `-D`.
64	- `-D`, `--total-duration SECONDS` — target total wall-clock seconds
65	  across all requested benches; budget is split equally per bench
66	  (e.g. `-D 30` with 6 benches → 5 s each). Mutually exclusive with
67	  `-d`.
68	- `-o`, `--outer N` — override outer loop count (forces count-based
69	  mode instead of time-based; inner still adapts).
70	- `-i`, `--inner N` — override inner loop count per histogram sample.
71	  `inner=1` measures single-call latency (each sample = one step).
72	  Higher inner measures back-to-back / burst rate (each sample = N
73	  steps averaged, hides per-call jitter and parking costs).
74	- `--pin CORES` — pin bench threads to logical CPUs. `CORES` is a
75	  comma-separated list with optional ranges: `0,1`, `0-5`, `0,3-5,7`.
76	  Treated as a **core pool** indexed positionally with wrap-around, so
77	  thread `i` gets `pool[i % pool.len()]`. Examples:
78	  - `--pin 0,1` pins a 2-thread bench to logical CPUs 0 and 1.
79	  - `--pin 0,0` co-locates two threads on the same CPU
80	    (oversubscription — measures contention).

Back-to-back `mpsc-2t` vs `probe-mpsc-2t` runs, subtract the whole-histogram means → "per-step probe overhead" falls out as a number. Same CPU state, minimal drift.

A few things to pin before writing code:

**1. Measurement vs overhead balance (you already flagged).** `std::sync::mpsc::send()` on an unbounded channel is ~15–30 ns. Two probes in the hot path add ~20 ns (one timer pair each). So on this particular target we'll mostly be measuring *probe overhead itself*, not send cost. That's actually the **right** outcome for dev1's purpose — validating the probe primitive under the hardest-possible signal-to-noise ratio. It's *not* the right outcome if we want a real send-cost number — for that we'd want to amortize: `let s = now(); for _ in 0..N { send } probe.record(s.elapsed() / N)`. The free-form primitive can already express that; it's just cleaner with scoped sugar. That doesn't block dev1.

**2. Probe ownership model.** Simplest MVP: **one probe = one thread's histogram**, no sharing. Each probe lives wherever `record()` is called from. Two threads → two probes, each owned by its thread. No locks, no atomics. This also naturally handles the travel-time case (consumer thread owns the probe, stamps `now - sent_at`). Cross-thread *sharing* of a single probe can come later if a use case forces it — doesn't seem urgent.

**3. Surface area for dev1.** Bare minimum:
- `struct Probe { name: String, hist: Histogram<u64> }`
- `fn new(name: &str) -> Self`
- `fn record(&mut self, ns: u64)`
- `fn report(&self)` — prints a mini band-histogram (reuse `print_report` layout, or a trimmed variant)

~30–50 lines in `src/probe.rs`. No registry, no globals. Benches that use probes own them as fields and call `report()` at end of `run`. Harness stays unchanged.

**4. Naming for the probed variant.** `probe-mpsc-2t` as CLI name → a whole `probe-*` family. Alternative: `mpsc-2t-probed` suffix. I lean prefix (`probe-*`) — groups all probed benches alphabetically in the startup listing, makes the "show me all probe variants" story natural. Your call.

**5. What's instrumented.** You said "send in both" — reading that as *two probes*, one around `req_tx.send()` on the main thread and one around `resp_tx.send()` on the worker thread. That's a good shape because it exercises cross-thread recording from day one (each thread owns its own probe, reports merge only at print time). If instead you meant "two probes on the same thread," it'd be less informative for validating the threading story.

**6. Report integration.** Bench's `run` fn prints the existing band-histogram report, then prints each probe's mini-report below. Harness doesn't need to know probes exist. Clean separation — probed and unprobed variants share the harness, just differ in what `run` prints at the end.

79	    // intercept gives framing. Cancels TSC pipelining of the framing pair.

87	    } else {
88	        0.0
89	    };
90	    let framing_per_sample_ns = (min_low as f64 - N_LOW as f64 * loop_per_iter_ns).max(0.0);

94	        loop_per_iter_ns,
95	        cal_min_low_ns: min_low,
96	        cal_min_high_ns: min_high,

**What's actually going on:** `std::sync::mpsc` under unpinned placement runs in two distinct modes:

**Per-call breakdown (unadjusted):** the probe includes the framing (~11 ns) but *not* the cost of the record itself (histogram insert happens *after* `elapsed()` captures the end timestamp).

- **Probe-vs-probe comparisons stay fair** — both are inflated by the same 11 ns, so the ratio is unchanged.
