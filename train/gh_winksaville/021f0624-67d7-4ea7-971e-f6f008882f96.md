Yes — that's an architectural inversion worth naming. Big deal, not a tweak.

**Old**: Bench drives the harness. One `step()`, one histogram. Harness owns the loop; workload is passive.

**New**: Application drives itself. Benches become **probes** — named observers attached to lifecycle points. Runtime threads messages through them; each probe accumulates its own histogram. Harness registers probes, runs the app for D seconds, collects and reports all of them.

Things that fall out almost for free:

- **Probes align with runtime API boundaries** — `get_msg`, `send_msg`, handler entry/exit, drop. The runtime already owns those seams.
- **Old Bench is the degenerate case**: one outermost probe. Either adapt it or let it coexist.
- **Per-thread accumulation, merge at end.** For -2t, producer and consumer write to their own histograms; harness merges pre-report. No hot-path locking.
- **Overhead calibration shifts.** Current `inner` amortizes timer-pair framing per sample. With per-op probes, each `record()` is its own timer pair — framing is per-probe-call, calibration still applies but at a different granularity.
- **Naming**: "bench" is overloaded now. `Probe` / `Meter` / `Span` — I lean `Probe` for its observational feel.

One concrete ergonomic choice to pin later: `probe.record(ns)` (caller times) vs `let _g = probe.start(); … drop(_g)` (probe times itself via RAII). Both fine; RAII is ergonomic for contiguous spans, `record()` composes for non-contiguous ones like travel time.

> AGENT

Right — those are meaningfully different shapes, not just stylistic variants:

**Type 1 — Scoped probe.** Owns both endpoints of a contiguous block. Two sub-flavors:
- `probe.measure(|| ...)` — closure-wrapped, returns the inner value. Cleanest for functions/blocks.
- `let _g = probe.scope();` — RAII guard. Handles early-return paths without lifting them into a closure.

Both are defensible; I'd pick *one* to avoid API sprawl. Closure form is simpler if benches never early-return; RAII is more general.

**Type 2 — Free-form probe.** Caller captures endpoints separately and reports the delta. Critical for *cross-boundary* timings that can't be wrapped in a single scope — travel time being the archetype: producer stamps `send_at`, consumer computes `now - send_at` and `probe.record(delta)`.

Knock-ons worth flagging:

1. **Travel-time probes impose a message shape requirement.** Either `Message` carries a `sent_at: Instant` field (free if runtime pools messages), or there's a side-channel timestamp map. The message-field route is cheaper and local.

2. **Cross-thread recording.** Type-2 probes routinely `record()` from a thread that isn't the one that started the span. So probes need either per-thread histograms merged at the end (fast, no locking) or a concurrent recorder. Per-thread is almost always the right answer for microbench work.

3. **Probe overhead compounds.** Each probe call is one `Instant::now()` pair (~10 ns on rdtsc-backed `minstant`). Six probes around a single message = 12 timer reads per round-trip. For sub-µs workloads, probes can rival the thing being measured. Implications: good per-probe calibration needed, plus a way to enable/disable probes per run (compile-time feature or runtime flag) so we can compare "measured" vs "instrumented" numbers — which is itself iiac-perf's mission.

Nice catch — the band histogram is revealing a bimodal distribution, and the band-boundary shift between the two benches is the tell.

**What's actually going on:** `std::sync::mpsc` under unpinned placement runs in two distinct modes:

- **Fast path** (~400-520 ns): both threads hot on adjacent/sibling cores, the receiver spinning, send→recv is just channel enqueue + cache coherence.
- **Slow path** (~5,500-8,000 ns): receiver parked, send has to `futex_wake` the kernel scheduler, wake+migrate+run is measurably slower.

Transitions between modes are rare, which is why the bands that straddle the crossover have huge `first`-to-`last` ranges (~5,000 ns).

**The percentile shift your eye caught:** the crossover lands in *different bands* in each bench because the fast:slow *ratio* is different.

Yes, correct — and it's ~11 ns per `record()` call, not just one `now()`.

**The mechanics:** each probe measurement is bracketed by two `minstant::Instant::now()` calls (the `let s = now()` at the start and the `now()` inside `.elapsed()` at the end). The *framing* — the fixed overhead of that pair — is exactly what the harness calibrates as `framing_per_sample`. From your run: **11.12 ns**. Each probe sample overstates the measured workload by approximately that amount.

**Per-call breakdown (unadjusted):** the probe includes the framing (~11 ns) but *not* the cost of the record itself (histogram insert happens *after* `elapsed()` captures the end timestamp).

**Implications:**
- **Probe-vs-probe comparisons stay fair** — both are inflated by the same 11 ns, so the ratio is unchanged.
- **Probe-vs-true-workload** overstates by ~11 ns per sample.
- **For your producer-consumer numbers specifically**: mean 3,638 ns → true workload ≈ 3,627 ns. Barely changes the story.
- **For sub-µs workloads**, 11 ns becomes significant (as dev0 anticipated).

This is exactly the "dev3+ territory" the dev0 design note flagged — probe overhead subtraction in an adjusted column.
