876	the reasoning was that they hid a field read without
877	collapsing the per-arm match in `main.rs`. That argument

906	call sites:

910	  `to_params` succeed).

935	script-parseable mode (which already uses `-L`).

937	### Why no closure
938	
939	A closure in `fn main()` was the prior iteration's shape;
940	this one promotes `sb_ide` to a global function so both
941	the trait's default `dispatch` (via `crate::sb_ide`) and
942	`main`'s unported arms can call it. A closure local to
943	`fn main()` would not be reachable from the trait module.
944	
945	### Why peek methods take `&Self::Params` (not `&self`)
946	
947	The chrome data is naturally a Params concept (the
948	clap-free domain struct each subcommand operates on),
949	not an Args concept. Reading the peek off `Params` means
950	the trait's default `dispatch` can be entirely
951	clap-free; only `to_params` straddles the Args→Params
952	boundary.
953	
954	A minor consequence: chrome runs *after* `to_params`
955	rather than before, so a `to_params` failure suppresses
956	the banner. See `### Session chrome: order shift`.

> AGENT

One thing you're missing: `sb_ide` does two distinct things — print banner *and* call `finalize::surface_previous_failures()`. The first is reasonably per-subcommand (chid/desc/list/show suppress with `-L`); the second is cross-cutting — every interactive run should surface prior-run failures, else the failure log silently bit-rots. Today both are uniformly off only when `is_detached_exec`. If a subcommand skips `sb_ide` to opt out of banner, it also loses failure-surfacing — that's a regression, not a feature.

Cleanest fix that still gets you what you want: every subcommand calls `sb_ide` as line 1 of `run`, drop both peeks from the trait. Trait shrinks to type + `to_params` + `run` + default `dispatch` (no chrome). 11 of 12 call `sb_ide(...)`; finalize handles its detached branch inside its own `run`. `sb_ide` moves out of `main.rs` into a util module so subcommands can `use` it. Tradeoff: forgetting the call in a new subcommand drops both banner and failure-surfacing — a process load (code review catches it), not an architecture concern.

Alternative if you want the per-subcommand truly-optional semantics: split `sb_ide` into `print_banner()` (opt-in per subcommand) + `surface_previous_failures()` (always called by `dispatch`, gated only on `is_detached_exec` which still needs to come from somewhere — back to a single peek on the trait). Trade simpler trait for fragmented chrome — I'd lean the first option.

> AGENT

`matches!` is a macro that returns `bool` — `true` iff the value matches the pattern, with optional guard.

Decomposed:
- `cli.command` — the parsed CLI subcommand enum.
- `Commands::Finalize(ref f)` — pattern: matches only when the variant is `Finalize`, binding the inner `FinalizeArgs` to `f` *by reference* (the `ref` keyword borrows rather than moves the inner value out of `cli.command`, which would otherwise consume it).
- `if f.exec` — guard: tightens the match to also require `f.exec == true`.

So `is_detached_exec` is `true` precisely when the current invocation is `vc-x1 finalize` *with* the hidden `--exec` flag — i.e., we are the detached child re-invoking itself to do the squash/push work. Every other variant (and `Finalize` *without* `--exec`, i.e., the user-facing parent that's about to spawn the child) yields `false`.

In `sb_ide(suppress_banner, is_detached_exec)` this gates *both* banner and `surface_previous_failures()` off, since the detached child is a backgrounded process whose stdout/stderr the user isn't watching.
