1	# Cycle protocol
2	
3	## Cycles
4	
5	A cycle has three phases:
6	
7	- **[Preparation](#preparation)** (`X.Y.Z-0`) — the cycle's
8	  first commit. Sets up the cycle:
9	  - Backfill the previous cycle's chores `Commits:` ref.
10	  - Bump `Cargo.toml` to `X.Y.Z-0`.
11	  - Pick up a `## Todo` item (typically via `## Priorities`)
12	    into `## In Progress` (bold title + succinct problem
13	    statement + plan ladder).
14	  - Open the [chores section](#chores-sections).
15	- **[Work-N](#work-n)** (`X.Y.Z-1`, `X.Y.Z-2`, …) — the
16	  commits that implement the change. As many as the change
17	  needs; each runs through the
18	  [per-commit flow](#per-commit-flow).
19	- **[Close-out](#close-out)** (bare `X.Y.Z`) — the cycle's
20	  last commit. Bookkeeping only:
21	  - Move the picked-up item to a one-line entry in
22	    `## Done`.
23	  - Move the `## In Progress` block into the
24	    [chores section](#chores-sections).
25	  - Optionally update `notes/README.md` if functionality
26	    changed.
27	
28	A cycle's commits are published to the project remote
29	either incrementally or as one batch at close-out; the
30	result must always be published at close-out. See
31	[Pushing](#pushing).
32	
33	**Sub-cycles.** When a Work commit's scope grows enough to
34	warrant its own ladder, it subdivides — `X.Y.Z-3.0`
35	Preparation, `X.Y.Z-3.1` / `X.Y.Z-3.2` Work, `X.Y.Z-3`
36	Close-out. The same three-phase shape applies recursively
37	at every depth. See [Numbering](#numbering) for the
38	suffix rule and [Sub-cycle ladders](#sub-cycle-ladders)

121	  (new flags, new subcommands, changed behavior).
122	
123	Whether to **squash** the cycle into one commit before the
124	publishing push, or push as-is, is decided at push time —

127	## Numbering
128	
129	The version suffix on each commit encodes its phase —
130	the **final identifier `0` marks a Preparation**:
131	
132	- `X.Y.Z-0` — Preparation
133	- `X.Y.Z-1`, `X.Y.Z-2`, … — Work commits
134	- `X.Y.Z` — Close-out (bare version, no suffix)
135	
136	Disambiguation:
137

139	  Preparation.

141	  identifier `0`).

143	**Nesting.** Sub-cycles append another level, recursively:
144	
145	- `X.Y.Z-3.0` — Preparation of the `-3` sub-cycle
146	- `X.Y.Z-3.1`, `X.Y.Z-3.2` — its Work
147	- `X.Y.Z-3` — its Close-out
148	- `X.Y.Z-3.1.0` — Preparation of the `-3.1` sub-sub-cycle
149

151	`-3.2`, `-3`); one that grows a Preparation later adds
152	`-3.0` without renumbering siblings.
153	
154	Bump `Cargo.toml` at the start of each phase so `vc-x1 -V`
155	reports the active phase at build time.

157	## Per-commit flow
158	
159	Every commit (Preparation, each Work commit, Close-out) goes
160	through:
161	
162	1. **Mark this commit `(current)`** as the first edit in
163	   `notes/todo.md > ## In Progress`.
164	2. **Do the work** (see [Iterative work](#iterative-work)
165	   for the loop-and-squash technique).
166	3. **Flip this commit `(current)` → `(done)`** in `## In
167	   Progress` — before the cargo cycle and the commit.
168	4. **Cargo cycle** (skip-able for purely-docs commits; full
169	   cycle mandatory at close-out):
170	   1. `cargo fmt`
171	   2. `cargo clippy --all-targets -- -D warnings`
172	   3. `cargo test`
173	   4. `cargo install --path . --locked`
174	   5. (re-test if anything substantive changed)
175	5. **Work review.** Stop *before* writing any description;
176	   tell the user "ready to commit." The user reviews the
177	   changes and we iterate until complete.
178	6. **Write the commit description** — see
179	   [Commit description](#commit-description).
180	7. **Commit Description review.** Show the title + body
181	   and stop. The user reviews the description. Iterate.
182	8. **Commit.** `jj commit -m "title" -m "body" -R .` for
183	   the app repo, `-R .claude` for the bot repo (`-R` last
184	   keeps the verb visible):
185	
186	   ```
187	   jj commit -m \
188	   "<type>: <short description> (<version>)" \
189	   -m "<intro paragraph>
190	
191	   - file1: gist
192	   - file2: gist
193	
194	   ochid: /.claude/<chid>" \
195	   -R .
196	   ```
197	
198	**Two overrides apply:**
199	
200	- **Deviation or question** — any time the work deviates
201	  from the agreed plan, or a question arises, stop and
202	  surface it; don't push through.
203	- **ESC-ESC** — the user can interrupt at any point to pull
204	  a review or question forward.

251	## Reviewing changes
252	
253	Work review looks at the **uncommitted working-copy diff**,
254	on the way to commit. The user opens diffs in their

270	## Pushing
271	
272	### Policy
273	
274	Push is **discretionary** during the cycle (backup,
275	progress visibility) and **mandatory at close-out** —
276	the cycle's result must be published.
277	
278	### Shape at close-out push
279	
280	Decide the shape and get user approval before pushing —
281	the choice is hard to undo once on the target. Surface
282	the options, wait for the user.
283	
284	- **Squash to one commit** — single entry on the target.
285	  Right for straightforward changes where the Work-N is
286	  focused on one or two files.
287	- **Merge non-ff** — `main` gains a merge commit
288	  (`X.Y.Z`); cycle commits stay reachable via two
289	  parents. `jj log -r ..@ -n <N>` shows the trapezoidal
290	  shape. Set up: `jj rebase -r <tip> --onto <prev>
291	  --onto <sub-tip>` where `<prev>` is the previous
292	  cycle's closed-out commit (current main tip). Two
293	  `--onto` → `<tip>` becomes a merge of `<prev>` +
294	  `<sub-tip>`.
295	- **Keep separate** — one commit per cycle entry on
296	  `main`. Use when the decomposition itself is
297	  informative. Each chores section keeps its own header /
298	  `Commits:` ref; no consolidation churn.
299	
300	Set up squash/merge before invoking `vc-x1 push`; use
301	`jj git push` directly for non-standard shapes.
302	
303	### vc-x1 push wrapper
304	
305	`vc-x1 push <bookmark>` wraps per-push mechanics. See
306	`vc-x1 push --help` for current flags.
307	
308	**Current limitation**: only fully supports the

317	### .claude cadence
318	
319	**Cadence**: one push = one `.claude` commit, paired
320	with every code commit in that push.
321	
322	The `.claude` working copy accumulates session data
323	across the cycle; its change ID stays stable across
324	snapshots, `jj describe`, and the finalize commit, so
325	code-side `ochid:` trailers resolve.
326	
327	`.claude` is a linear journal — all session work lives
328	on `main`, regardless of the app-side bookmark. **Do not
329	create or maintain `.claude` bookmarks that mirror
330	app-side branches** — risks the bot steering session
331	pushes to the wrong remote ref.

333	### Bot communication at the reviews
334	
335	Use plain prose — no insider jargon ("Gate N signal",
336	"Checkpoint N", etc.):
337	
338	- **At Work review** — summarize what changed and stop.
339	  "Work complete. Please review."

351	After `vc-x1 finalize` launches (mid-session per-push or

402	## Iterative work
403	
404	When work for a single commit (the **target**) benefits
405	from incremental review, loop:
406	
407	1. `jj new -R .` — fresh empty `@` on top of the target.
408	2. Make the next round of changes.
409	3. User reviews the round (see
410	   [Reviewing changes](#reviewing-changes)).
411	4. `jj squash -R .` folds into the target and creates a
412	   new empty `@`.
413	5. If not done, go to step 2.
414	
415	Same jj mechanics as a
416	[sub-cycle ladder](#sub-cycle-ladders), but at
417	single-commit scope — the cycle's version suffix
418	doesn't change.

420	## Sub-cycle ladders
421	
422	When a Work commit subdivides into a sub-cycle (see
423	[Numbering](#numbering) for suffix nesting), its Work
424	commits typically live as a local jj `@` chain and
425	**collapse into the sub-cycle's Close-out** before the
426	parent cycle continues. Ladder commits are scratch —
427	for review and bisection only.
428	
429	### Per-Work-commit contract within a ladder
430	
431	For each Work commit in the ladder:
432	
433	1. `jj new -R .` — create a fresh empty `@`.
434	2. Do the commit's work.
435	3. Run `cargo test --bins`. **Non-negotiable** — build
436	   and clippy alone miss regressions until a later
437	   commit runs the full suite, raising bisection cost.
438	4. `jj describe -m "..." -m "..." -R .` — working title
439	   only (no version suffix); the sub-cycle Close-out
440	   collects everything into one final commit with the
441	   `(X.Y.Z-N)` marker.
442	
443	### Navigating the ladder
444	
445	Common moves:
446	
447	- `jj log -r '<base>::' -R .` — see the whole ladder
448	  from its base.
449	- `jj edit -r <prefix> -R .` — jump `@` to any ladder
450	  commit by chid prefix; useful for bisection.
451	- `jj edit @-- -R .` — quick-jump back two commits.
452	- `jj diff -r <chid> -R .` — review one commit in
453	  isolation.
454	
455	Modifications to any ladder commit rewrite it in place;
456	descendants auto-rebase.
457	
458	### Close-out: squash the ladder
459	
460	When all ladder Work commits are done and tests pass:
461	
462	```
463	jj squash --from "<base>..@-" --into @ -u -R .
464	```
465	
466	`<base>` is the parent of the first ladder commit; `-u`
467	keeps `@`'s description and discards the sources'.
468	After squash, history is linear: `<base> → @`;
469	intermediate commits are auto-abandoned.
470	
471	Then `vc-x1 push <bookmark>` as for any other commit.
472	
473	For N = 1 the squash is a no-op (`<base>..@-` is empty
474	when `@-` is `<base>`); push the single commit directly.
475	
476	### Recovery
477	
478	If a ladder commit goes wrong, back out without losing
479	prior commits:
480	
481	- **Discard the current commit.** `jj abandon @ -R .`
482	  drops it; you get a fresh empty `@` on the same
483	  parent.
484	- **Edit an earlier commit.** `jj edit -r <chid> -R .`,
485	  make corrections, then `jj edit -r <last-ladder-chid>`
486	  to return. Descendants auto-rebase.
487	- **Discard the entire ladder.** `jj op log -R .` shows
488	  the op history; `jj op restore <op-id> -R .` reverts
489	  to that point. Full undo — removes *all* ladder work
490	  after the chosen op. Use only to start over.
