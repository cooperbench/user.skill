2	
3	This protocol uses [Prose form](../AGENTS.md#prose-form). It
4	contains instructions on how a commit cycle accomplished.
5	
6	## Cycles
7	
8	A cycle has three phases:
9	
10	- **[Preparation](#preparation)** (`X.Y.Z-0`) — the cycle's
11	  first commit. Sets up the cycle:
12	  - Backfill the previous cycle's chores `Commits:` ref.
13	  - Bump `Cargo.toml` to `X.Y.Z-0`.
14	  - Pick up a `## Todo` item (typically the top-ranked,
15	    #1) into `## In Progress` (bold title + succinct problem
16	    statement + plan ladder).
17	  - Open the [chores section](#chores-sections).
18	- **[Work-N](#work-n)** (`X.Y.Z-1`, `X.Y.Z-2`, …) — the
19	  commits that implement the change. As many as the change
20	  needs; each runs through the
21	  [per-commit flow](#per-commit-flow).
22	- **[Close-out](#close-out)** (bare `X.Y.Z`) — the cycle's
23	  last commit. Bookkeeping only:
24	  - Move the picked-up item to a one-line entry in
25	    `## Done`.
26	  - Move the `## In Progress` block into the
27	    [chores section](#chores-sections).
28	  - Optionally update `notes/README.md` if functionality
29	    changed.
30	
31	A cycle's commits are published to the project remote
32	either incrementally or as one batch at close-out; the
33	result must always be published at close-out. See
34	[Pushing](#pushing).
35	
36	**Sub-cycles.** When a Work commit's scope grows enough to
37	warrant its own ladder, it subdivides — `X.Y.Z-3.0`
38	Preparation, `X.Y.Z-3.1` / `X.Y.Z-3.2` Work, `X.Y.Z-3`
39	Close-out. The same three-phase shape applies recursively
40	at every depth. See [Numbering](#numbering) for the
41	suffix rule and [Sub-cycle ladders](#sub-cycle-ladders)
42	for the local-ladder mechanics.

44	## Chores sections
45	
46	A **chores section** is a `##` section in
47	`notes/chores/chores-NN.md` recording one cycle:
48	
49	- One section per cycle is the default.
50	- Per-commit sections (like 0.55.0's four) are a
51	  deliberate alternative.
52	
53	The phrase **"Open" the chores section** means append a
54	`##` header to the current `notes/chores/chores-NN.md`
55	with the cycle's anticipated close-out title (e.g.
56	`## refactor: foo bar (X.Y.Z)`). The body is empty;
57	content arrives at close-out (see [Close-out](#close-out)).
58	
59	Fuller chores conventions (content rules, header sync,
60	design subsection pattern, `Commits:` formatting) live in
61	AGENTS.md [Chores conventions](../AGENTS.md#chores-conventions).
62	
63	## Preparation
64	
65	The cycle's first commit (`X.Y.Z-0`):
66

68	  `Commits:` ref** — see
69	  [Chores commit references](../AGENTS.md#chores-commit-references).
70	- **Bump the version** in `Cargo.toml` to `X.Y.Z-0`.
71	- **Update `Cargo.lock`** to match — run `cargo build`
72	  (or `cargo check`) so the lockfile's `vc-x1` version
73	  tracks `Cargo.toml` in the same commit.
74	- **Move a `## Todo` item** (if the cycle has one) into
75	  `## In Progress` and the todo item should have:
76	  - A **bold title line** — that will be the chores
77	    section header, minus the `## ` prefix.
78	  - A **succinct problem statement**; add if one is needed
79	  - A **plan ladder**.
80	- **Open the [chores section](#chores-sections)** —
81	  append a `##` header with the cycle's anticipated
82	  close-out title.
83	
84	## Work-N
85	
86	The cycle's work commits (`X.Y.Z-1`, `X.Y.Z-2`, …)
87	implement the change. As many as needed:
88	
89	- Each commit runs through the

91	- **Interim pushes** are optional (backup, progress
92	  visibility).
93	- Close-out is the only mandatory push (see
94	  [Pushing](#pushing)).
95	- **Subdivide into a sub-cycle** if a Work commit's
96	  scope grows enough (see
97	  [Sub-cycle ladders](#sub-cycle-ladders)).

99	## Close-out

101	The cycle's last commit (bare `X.Y.Z`) does bookkeeping
102	only — the commit body describes that bookkeeping, not

106	  one-line entry (with a chores `[N]` ref) in `## Done`.
107	- **Move the `## In Progress` block into the
108	  [chores section](#chores-sections)** (the title-only
109	  placeholder opened during Preparation):

111	    `## In Progress` (drop the bold title line — the

122	  (new flags, new subcommands, changed behavior).
123

128	## Numbering
129	
130	The version suffix on each commit encodes its phase —
131	the **final identifier `0` marks a Preparation**:
132	
133	- `X.Y.Z-0` — Preparation
134	- `X.Y.Z-1`, `X.Y.Z-2`, … — Work commits

136	
137	Disambiguation:
138

140	  Preparation.

142	  identifier `0`).

147	- `X.Y.Z-3.1`, `X.Y.Z-3.2` — its Work

149	- `X.Y.Z-3.1.0` — Preparation of the `-3.1` sub-sub-cycle

152	`-3.2`, `-3`); one that grows a Preparation later adds
153	`-3.0` without renumbering siblings.

155	Bump `Cargo.toml` at the start of each phase so `vc-x1 -V`
156	reports the active phase at build time.

158	## Per-commit flow
159	
160	Every commit (Preparation, each Work commit, Close-out) goes
161	through:
162	
163	1. **Mark this commit `(current)`** as the first edit in
164	   `notes/todo.md > ## In Progress`.
165	2. **Do the work** (see [Iterative work](#iterative-work)
166	   for the loop-and-squash technique).

271	## Pushing
272	
273	### Policy
274	
275	Push is **discretionary** during the cycle (backup,
276	progress visibility) and **mandatory at close-out** —
277	the cycle's result must be published.
278	
279	### Shape at close-out push
280	
281	At close-out the cycle's *work* is done; its *published
282	shape* is the remaining choice, made at push time. Surface
283	the options and get user approval before pushing — once on
284	the target, changing shape is a remote rewrite (force-push,
285	needs approval), so choose deliberately.
286	
287	- **Squash to one commit** — single entry on the target.
288	  Right for straightforward changes where the Work-N is
289	  focused on one or two files.
290	- **Merge non-ff** *(current default)* — `main` gains a
291	  merge commit (`X.Y.Z`); cycle commits stay reachable via
292	  two parents. `jj log -r ..@ -n <N>` shows the trapezoidal
293	  shape. See [Merge non-ff recipe](#merge-non-ff-recipe)
294	  for the full setup sequence.
295	- **Keep separate** — one commit per cycle entry on
296	  `main`. Use when the decomposition itself is
297	  informative. Each chores section keeps its own header /
298	  `Commits:` ref; no consolidation churn.
299	
300	Set up squash/merge before invoking `vc-x1 push`; use
301	`jj git push` directly for non-standard shapes.
302	
303	### Merge non-ff recipe
304	
305	Setting up a [Merge non-ff](#shape-at-close-out-push)
306	close-out is a fixed sequence. `<closeout>` is the cycle's
307	close-out commit, `<prev>` the previous cycle's close-out
308	(the current `main` tip), `<work-tip>` the cycle's last
309	Work commit:
310	
311	1. **Rebase the close-out into a merge** — `jj rebase -r
312	   <closeout> --onto <prev> --onto <work-tip>`.
313	   - `-r <closeout>` keeps the `<closeout>` commit in place.
314	   - `--onto <prev>` becomes its first parent (trunk).
315	   - `--onto <work-tip>` becomes the second parent.
316	
317	   Together these make `<closeout>` a merge of
318	   `<prev>` + `<work-tip>`, forming a trapezoidal commit.
319	2. **Use `jj new <merge>`** to add an empty `@` above the
320	   merge. The rebase left `@` *on* the now-content-bearing
321	   merge, which git/IDE diff views show as uncommitted;
322	   `jj new` restores the clean empty `@` on top.
323	3. **Push** — `jj git push --bookmark main -R .`.
324	
325	**Post-hoc caveat.** If the cycle was already pushed
326	[Keep separate](#shape-at-close-out-push) its commits are
327	immutable: the rebase needs `--ignore-immutable` and the
328	push force-updates `main`.
329	The standard sequence assumes the merge is set up *before*
330	the close-out push.
331

335	`vc-x1 push --help` for current flags.

346	### .claude cadence
347	
348	**Cadence**: one push = one `.claude` commit, paired
349	with every code commit in that push.
350	
351	The `.claude` working copy accumulates session data
352	across the cycle; its change ID stays stable across
353	snapshots, `jj describe`, and the finalize commit, so
354	code-side `ochid:` trailers resolve.
355	
356	`.claude` is a linear journal — all session work lives
357	on `main`, regardless of the app-side bookmark. **Do not
358	create or maintain `.claude` bookmarks that mirror
359	app-side branches** — risks the bot steering session
360	pushes to the wrong remote ref.
361	
362	Ending a session: if the user runs `/exit` there will be
363	session information created, which we don't worry about.
364	The user can close the terminal instead and `@` will
365	remain empty — this behavior was verified in 0.64.0.
366	
367	### Bot communication at the reviews
368	
369	Use plain prose — no insider jargon ("Gate N signal",
370	"Checkpoint N", etc.):
371	
372	- **At Work review** — summarize what changed and stop.
373	  "Work complete. Please review."
374	- **At Commit Description review** — present `$TITLE`
375	  and `$BODY` explicitly; ask permission to commit/push.
376	  Don't spell out the full `vc-x1 push ... --title ...
377	  --body ...` invocation by default.
378	- **At Post close-out review** — surface the shape
379	  options (squash / merge / keep) and the push target;
380	  wait for the user's choice before any `jj squash` /
381	  `jj rebase` / `jj git push` invocation.
382	
383	### After push or finalize: stop and wait
384	
385	After you **push** (cross the remote boundary) or launch
386	**finalize** on the `.claude` repo (`vc-x1 finalize --repo
387	.claude --squash --push <bookmark> --delay 10 --detach`) — by
388	hand or via the `vc-x1 push` wrapper — you **MUST NEVER**
389	proceed (next step, edit, tool call, text output) until the
390	user explicitly directs you to continue. **Even when the next
391	step seems obvious — wait.** Treat push-or-finalize as a hard
392	stop for the whole turn.
393	
394	`vc-x1 push` performs both as its tail stages — `push-app`
395	then the detached `vc-x1 finalize` on `.claude` — so there is
396	no gap left to speak in once the push is invoked. Put **all**
397	closing words *before* invoking it; do not purposely emit anything
398	after the tool returns.
399	
400	Why (`.claude` is the live journal finalize snapshots →
401	squashes → pushes):
402	
403	- **`--detach`**: lets the tool return immediately so the
404	  harness can keep flushing the *trailing* session-data — the
405	  tool call's own transcript and any words emitted *before*
406	  the invoke — into the snapshot.
407	- **`--delay 10`**: gives the harness time to complete that
408	  flush before the snapshot is taken. It is **not** time for
409	  the bot to do more work.
410	- **silence**: the bot must not summarize or perform any work
411	  after the tool returns.
412	
413	**Known slip**: the bot has emitted a summary after launching
414	finalize. There is no "harmless" closing line — if it's worth
415	saying, say it *before* the invoke.
416	
417	### Recovery
418	
419	- **If push exits before `finalize-claude`** (e.g.
420	  failure between `push-app` and `finalize-claude`), run
421	  finalize by hand:
422	
423	  ```
424	  vc-x1 finalize --repo .claude --squash --push <bookmark> --delay 10 --detach --log /tmp/vc-x1-finalize.log
425	  ```
426	
427	- **Run finalize again if `@` is non-empty** after the
428	  finalize's squash-and-commit (also desirable after
429	  extra activity by the bot's agents).
430	  - Why: finalize snapshots `.claude` at `--delay`, but the
431	    bot keeps writing session data while it runs — the tool's
432	    own invocation plus the bot's closing response land
433	    *after* the snapshot.
434	  - Safe to repeat: bot session data is append-only, so a
435	    re-run never conflicts or overwrites. (This could
436	    change; it is not under the user's control.)
437	  - Fix: run `vc-x1 finalize --repo .claude --squash --push
438	    <bookmark> --delay 10 --detach` another time to capture
439	    that tail; one extra pass is generally enough.
440	    - Verified 0.64.0: two finalizes were executed and
441	      we purposely used the bot again and the second finalize
442	      captured everything.
443	  - No guarantees: events outside the bot's control can leave
444	    `@` non-empty — e.g. the bot's back end may decide to
445	    squash/consolidate session data, which can take minutes
446	    and land after the snapshot. The remedy is the same: just
447	    run finalize again. This is why a single pass is never
448	    guaranteed to leave `@` empty.
449	- **Clear push's saved state** after any out-of-band
450	  recovery — `rm .vc-x1/push-state.toml` or `vc-x1 push
451	  <bookmark> --restart` — otherwise push resumes from a
452	  stale stage.
453	- **Late code-repo tweak after `push-app` succeeded**
454	  (e.g. updating AGENTS.md or memory) requires `jj
455	  squash --ignore-immutable` and a re-push; that is a
456	  remote rewrite and needs explicit approval like any
457	  push.

459	## ochid trailers
460	
461	A **chid** is jj's change ID — a permanent identifier
462	that survives rebases and describes (see
463	[`jj-revsets.md`](jj-revsets.md)). An **ochid** trailer
464	on a commit body links it to its counterpart in the
465	other repo via that counterpart's chid, written as a
466	workspace-root-relative path. See
467	[`forks-multi-user.md`](forks-multi-user.md) for the
468	multi-line trailer design (multi-user / forking).
469	
470	- **Code-side commits** each carry one
471	  `ochid: /.claude/<.claude-chid>` — the `.claude`
472	  change ID.
473	- **The `.claude` commit** has one `ochid: /<code-chid>`
474	  per code commit in that push. More than one occurs on
475	  Merge non-ff close-out (one ochid per Work commit in
476	  the cycle).
477	
478	Use `vc-x1 chid -s code,bot -L` to capture the change
479	IDs (first line app, second `.claude`).

481	## Iterative work
482	
483	When work for a single commit (the **target**) benefits
484	from incremental review, loop:
485	
486	1. `jj new -R .` — fresh empty `@` on top of the target.
487	2. Make the next round of changes.
488	3. User reviews the round (see
489	   [Reviewing changes](#reviewing-changes)).
490	4. `jj squash -R .` folds into the target and creates a
491	   new empty `@`.
492	5. If not done, go to step 2.
493	
494	Same jj mechanics as a
495	[sub-cycle ladder](#sub-cycle-ladders), but at
496	single-commit scope — the cycle's version suffix
497	doesn't change.
498	
499	## Sub-cycle ladders
500	
501	When a Work commit subdivides into a sub-cycle (see
502	[Numbering](#numbering) for suffix nesting), its Work
503	commits typically live as a local jj `@` chain and
504	**collapse into the sub-cycle's Close-out** before the
505	parent cycle continues. Ladder commits are scratch —
506	for review and bisection only.
507	
508	### Per-Work-commit contract within a ladder
509	
510	For each Work commit in the ladder:
511	
512	1. `jj new -R .` — create a fresh empty `@`.
513	2. Do the commit's work.
514	3. Run `cargo test --bins`. **Non-negotiable** — build
515	   and clippy alone miss regressions until a later
516	   commit runs the full suite, raising bisection cost.
517	4. `jj describe -m "..." -m "..." -R .` — working title
518	   only (no version suffix); the sub-cycle Close-out
519	   collects everything into one final commit with the
520	   `(X.Y.Z-N)` marker.
521	
522	### Navigating the ladder
523	
524	Common moves:
525	
526	- `jj log -r '<base>::' -R .` — see the whole ladder
527	  from its base.
528	- `jj edit -r <prefix> -R .` — jump `@` to any ladder
529	  commit by chid prefix; useful for bisection.
530	- `jj edit @-- -R .` — quick-jump back two commits.
531	- `jj diff -r <chid> -R .` — review one commit in
532	  isolation.
533	
534	Modifications to any ladder commit rewrite it in place;
535	descendants auto-rebase.
536	
537	### Close-out: squash the ladder
538	
539	When all ladder Work commits are done and tests pass:
540	
541	```
542	jj squash --from "<base>..@-" --into @ -u -R .
543	```
544	
545	`<base>` is the parent of the first ladder commit; `-u`
546	keeps `@`'s description and discards the sources'.
547	After squash, history is linear: `<base> → @`;
548	intermediate commits are auto-abandoned.
549	
550	Then `vc-x1 push <bookmark>` as for any other commit.
551	
552	For N = 1 the squash is a no-op (`<base>..@-` is empty
553	when `@-` is `<base>`); push the single commit directly.
554	
555	### Recovery
556	
557	If a ladder commit goes wrong, back out without losing
558	prior commits:
559	
560	- **Discard the current commit.** `jj abandon @ -R .`
561	  drops it; you get a fresh empty `@` on the same
562	  parent.
563	- **Edit an earlier commit.** `jj edit -r <chid> -R .`,
564	  make corrections, then `jj edit -r <last-ladder-chid>`
565	  to return. Descendants auto-rebase.
566	- **Discard the entire ladder.** `jj op log -R .` shows
567	  the op history; `jj op restore <op-id> -R .` reverts
568	  to that point. Full undo — removes *all* ladder work
569	  after the chosen op. Use only to start over.

2	
3	Captures design discussion about two related but separable
4	concerns:
5	
6	1. **Forking** a dual-repo workspace — working on an older

9	   multiple humans, multiple bot sessions, code-side merges.
10	
11	Both surface the same underlying tension: the code repo has
12	the classic git/jj DAG (branches, merges, rebases), while the
13	bot repo is fundamentally an append-only journal of
14	conversations that should never be rewritten.
15	
16	For the *content* of the bot repo (vendor identity, format
17	versioning, multi-bot conventions, vendor-subdir directory
18	layout), see the companion file
19	[`bot-data-formats.md`](bot-data-formats.md).

22	the bot thinks, not implemented. Treat as a design reference,
23	not a status doc.
24	
25	## Forking with the bot side staying linear
26	
27	### The asymmetric situation
28	
29	When work needs to happen on an older code-side base — e.g.,
30	0.41.1 work branched off 0.41.0 while 0.42.0 is in flight on
31	main — the code repo can fork without difficulty. That's a
32	normal git/jj branch.
33	
34	The bot repo can't fork the same way: each session is a linear
35	conversation, and rewriting an existing session line would
36	falsify the historical record. The conversation that happened
37	is the conversation that happened; it doesn't get re-played
38	from a different branch base.
39	
40	### chid stability across rebase
41	
42	jj's two-id model is built for this scenario. Each commit has
43	both:
44	
45	- `commit_id` — git SHA, changes on rewrite.
46	- `change_id` — stable across `describe` / `rebase` /
47	  `squash-into-self`.
48	
49	`ochid:` trailers carry change_ids. So when a code-side branch
50	later rebases on top of another branch, change_ids are
51	preserved and ochid trailers in both directions still resolve.
52	
53	The bot thinks the only operations that break this are
54	`jj squash` (folding two commits into one — collapses two
55	change_ids into one) and `jj abandon` (removing a commit —
56	loses the change_id entirely). Pure rebase is safe.
57	
58	### Why not time-based linkers
59	
60	Time isn't a stronger primitive than change_id:
61	
62	- Clock skew between processes / repos breaks ordering.
63	- Time still doesn't survive rewrites any better than
64	  change_id does — you'd still need a stable identifier baked
65	  into the trailer that matches some property of the
66	  counterpart commit.
67	- change_id is jj's intended stability primitive — that's
68	  literally the job it exists to do.
69	
70	If the change_id scheme ever shows weakness, the bot thinks
71	the answer is jj-side hygiene (don't `squash`-collapse during
72	rebase) rather than switching primitives.
73	
74	### Partner bookmarks
75	
76	The chosen technique for forking the code side while keeping
77	the bot side linear: **partner bookmarks**.
78	
79	When a code-side branch needs to advance independently, create
80	a bookmark of the same name on the bot side starting at the
81	*current* bot HEAD — not at the historical bot commit paired
82	with the code-side branch base. The two bookmarks share a name
83	and advance together via `vc-x1 push`, but each carries its
84	own repo's state.
85	
86	Other names considered and rejected:
87	
88	- **mirror** — implies symmetric content. The bookmarks are
89	  not mirrors; they hold different content with no
90	  point-by-point correspondence.
91	- **tandem** — captures cooperation, but slightly less common
92	  in software vocabulary.
93	- **paired** — bland; "pair" can imply matching halves.
94	- **disjoint** / **asymmetric** — describe a property of the
95	  relationship, not a label for the technique.
96	- **yoked** — accurate metaphor but obscure.
97	
98	**partner** won because it conveys cooperation without
99	implying duplication. Always subject to change as we live
100	with the term.
101	
102	The asymmetric ordering between code and bot history (rebased
103	main commits on the code side will eventually point at bot
104	commits that come *before* their partner-branch pairs in bot
105	history) is a cosmetic wrinkle, not a correctness problem —
106	change_ids resolve regardless of position.
107	
108	### Recovery anchor
109	
110	The original main HEAD — the commit being "branched away
111	from" — should stay put, not be rewritten or rewound. It's
112	the recovery anchor for the operation. If the partner-branch
113	work goes wrong, main is still where it was, and recovery is
114	`jj abandon` on the new branch's commits.

130	
131	Each session is one append-only chain. The bot repo is a
132	forest of those chains; never merged. No bot-side merge
133	commits at all. Code-side has a DAG (merges, branches);
134	bot-side is a forest. The mapping is the multi-ochid trailer
135	set on each code commit, fanning out to the contributing
136	chain tips.
137	
138	The bot thinks this is cleaner than "bot side mirrors code
139	side topology" because:
140	
141	- Each conversation is a wire-format record of what was
142	  actually said. Merging two conversations into one commit
143	  would falsify that record.
144	- "Never rewrite bot commits" becomes an enforceable rule —
145	  change_ids on the bot side are automatically stable.
146	- Storage and sync stay simple — appending only, no merge
147	  conflict resolution on the bot side ever.
148	
149	### Multi-line ochid trailer
150	
151	Standard git trailer convention allows multiple values for
152	the same key. Just emit `ochid:` once per pointer:
153	
154	```
155	ochid: /.claude/abc123
156	ochid: /.claude/def456
157	ochid: /.claude/ghi789
158	```
159	
160	Single-pointer commits stay backward compatible — they're
161	just the N=1 case. No version bump needed; existing parsers
162	either already accept repeated trailers or are easy to
163	extend.
164	
165	### When multi-ochid actually applies
166	
167	- **Code-side merge with no extra bot work** — N ochids =
168	  the merge parents' contributing tip change_ids (one per
169	  parent). Possibly with de-duplication if parents share
170	  ancestry.
171	- **Code-side merge with conflict-resolution session** —
172	  N parents' ochids + the resolution session's tip ochid.
173	  If user A and user B merge into M and user C resolves the
174	  conflict, M has 3 ochids: A's tip, B's tip, C's session
175	  tip.
176	- **Single-user single-session** — still 1 ochid. Same as
177	  today.
178	- **Code rebase** — ochids unchanged (change_ids are
179	  stable). Same as today. Multi-user rebases work the same
180	  as single-user.
181	
182	### Staged fork integration
183	
184	How a contributed cycle's worth of changes enters a
185	downstream repo, keeping the as-is record separate from the
186	integration work:
187	
188	- **As-is acceptance.** A contributed set of changes lands
189	  first in a dedicated branch *exactly as submitted* — no
190	  merge, no squash, no tweak. The contributor's `ochid:`
191	  trailers are preserved verbatim; the branch is a faithful
192	  record of what was contributed.
193	- **Integration as separate steps.** Merging, squashing, or
194	  tweaking that work onto the target line happens
195	  afterward, as one or more separate steps on an
196	  intermediate branch. Each is its own cycle and may add
197	  its own bot session.
198	- **Resulting ochid set.** An integrated commit therefore
199	  carries a *set* of ochids — the contributor's original
200	  pointer(s) plus any integration-session pointer(s): the
201	  [multi-line ochid trailer](#multi-line-ochid-trailer)
202	  applied to the fork case rather than the octopus-merge
203	  case.
204	
205	The contributing bot repos live in different locations
206	(different users, different remotes), so each ochid in the
207	set must name *which* bot repo as well as the chid. Three
208	representations, in increasing indirection:
209	
210	- **Workspace-relative path** — `/.claude/<chid>`,
211	  `/.claude-alice/<chid>`. Today's form; resolves only
212	  repos under the local workspace root.
213	- **Full URL** — `https://github.com/alice/bot#<chid>`
214	  (see [Per-user bot repos via URL-shaped
215	  ochid](#per-user-bot-repos-via-url-shaped-ochid)).
216	  Self-contained, no external table; verbose, exposed to
217	  link rot.
218	- **`.vc-config.toml` repo index** — a tuple
219	  `(repo-index, chid)` where `repo-index` keys a
220	  repo-location table declared once in `.vc-config.toml`.
221	  The trailer stays short, and relocating a repo is a
222	  one-line config edit instead of rewriting every trailer.
223	  Cost: indirection — the trailer is meaningless without
224	  the config, so a commit inspected outside its workspace
225	  (a raw `git show` elsewhere) can't resolve it.
226	
227	The bot thinks index and URL forms are complementary, not
228	rivals — index for repos the project already tracks in
229	`.vc-config.toml`, URL for one-off external contributors —
230	and a resolver accepting all three (path, URL, index) is
231	the one-rule dispatch the URL-shaped section already
232	describes, with a third arm.
233	
234	### Per-user vs shared bot repo
235	
236	Open question worth deciding before code lands.
237	
238	- **Shared bot repo** (today's model extended): one
239	  `.claude/` repo holds all sessions across all users. Push
240	  from any user appends a chain. Pros: viewer sees
241	  everything in one place; cross-references resolve locally.
242	  Cons: every user pulls every other user's session data on
243	  sync — could be heavy. Permissions are coarse.
244	- **Per-user bot repos**: each user has their own
245	  `.claude-<user>/` repo, ochid trailers carry a user
246	  qualifier (`ochid: /.claude-alice/abc123`). Pros:
247	  lightweight sync, natural permissions. Cons: viewer needs
248	  to know all the bot-repo URLs to show full context;
249	  offline viewing breaks if you don't have the relevant
250	  user's repo.
251	
252	The bot thinks **shared** is the default with a per-project
253	escape hatch — most teams want the cross-references to
254	"just work." The qualifier in ochid (the path component
255	after the leading `/`) already encodes either model:
256	`/.claude/<chid>` for shared, `/.claude-alice/<chid>` for
257	per-user. The trailer format itself is forward-compatible.
258	
259	### Per-user bot repos via URL-shaped ochid
260	
261	Per-user bot repos become practical for distributed
262	projects (open-source, multi-org) when ochid trailers can
263	qualify by URL rather than only workspace-relative path.
264	This generalizes the per-user model in the section above
265	from "co-located teams sharing a workspace" to "anyone on
266	the public internet."
267	
268	**Trailer shape.** Existing path form is
269	workspace-root-relative (`/.claude/<chid>` for shared,
270	`/.claude-alice/<chid>` for per-user-in-shared-workspace).
271	URL form generalizes the qualifier to a remote repo:
272	
273	```
274	ochid: https://github.com/alice/bot-sessions#<chid>
275	ochid: git@github.com:alice/bot-sessions.git#<chid>
276	```
277	
278	Parser dispatch is one rule: if the qualifier parses as a
279	URL, fetch over the network; otherwise resolve relative
280	to workspace root. Existing path-form trailers stay the
281	N=1 backward-compatible case. No schema versioning
282	needed.
283	
284	**Link rot is the load-bearing problem.** A contributor
285	can publish their bot repo, get merged, then later make
286	it private or delete it. The ochid URL 404s; bot context
287	is lost. The bot thinks this is a real-but-not-
288	catastrophic leak — the commit's code and
289	`Signed-off-by:` line remain authoritative; bot context
290	is a nice-to-have for understanding patch development,
291	not a load-bearing semantic. Direct analogue: dead URLs
292	in academic citations, mailing-list links in older
293	kernel commit messages. Annoying for archaeology, not
294	fatal.
295	
296	**Mitigations, in order of practical adoption:**
297	
298	1. **Project-side mirroring at merge time.** When a
299	   maintainer accepts a PR, project tooling fetches the
300	   contributor's bot repo at the referenced chid and
301	   mirrors to a project-namespace archive (e.g.
302	   `bot-archives/<contributor>-<date>-<chid>.jsonl`).
303	   Future ochid resolution falls back to the mirror if
304	   the original URL 404s. The bot thinks this is the
305	   only mitigation most projects would actually adopt —
306	   cheap, obvious upside, no friction for contributors.
307	   Same pattern as LKML's permanent archive.
308	2. **Cryptographic stapling.** Embed a hash of the bot
309	   repo's tip at submission time:
310	   `ochid: <url>#<chid>;sha256=<hash>`. Tamper-detection
311	   stays sound even if retrieval fails; doesn't recover
312	   data. Adds maintenance burden to trailer parsing.
313	3. **CI-enforced live ochid at merge.** Project CI
314	   fetches the URL, verifies it resolves with parseable
315	   content, before allowing merge. Doesn't prevent
316	   later lock/delete but ensures the merge moment was
317	   sound. Contentious in open-source culture (gates
318	   contributors on infra they don't own).
319	
320	**Opt-out via project policy.** A no-bot-context commit
321	isn't a leak — it's a project policy choice. A project
322	that wants bot transparency mandates each commit carry
323	≥1 `ochid:` trailer or an explicit
324	`No-bot-context: <reason>` trailer. Enforceable in CI,
325	identical pattern to existing `Signed-off-by:`.
326	Contributors who want privacy decline that project's
327	contribution norms; their commits go elsewhere or omit
328	the trailer where the project allows.
329	
330	**Cross-bot interop bonus.** Once URL-shaped, the
331	trailer doesn't have to point at a Claude Code repo.
332	Codex, Cursor, Aider, custom in-house tools — anyone
333	whose bot leaves a publishable session record can host
334	their own bot repo and emit ochid trailers in the same
335	format. The trailer becomes "where to find the AI
336	session that produced this commit," not "where to find
337	the Claude Code session." Strictly bigger ecosystem
338	play with no extra design cost.
339	
340	**Implication for shared-central scaling.** URL-shaped
341	per-user repos potentially short-circuit the
342	size/threshold problem documented below. Each
343	contributor pays for their own bot repo; project pays
344	for an opt-in mirror archive sized per its policy. The
345	"50 devs share one ~15G bot repo" problem becomes "50
346	devs each maintain their own ~300M bot repo, project
347	mirrors selectively."
348	
349	Trade-off: shared-central keeps cross-references local
350	and fast; per-user-via-URL needs a network fetch (or a
351	warm mirror) to resolve any non-local trailer. Pick by
352	project shape — small co-located teams favor shared;
353	distributed open-source favors per-user-via-URL.
354	
355	### Bot-side commit immutability
356	
357	Codify "never rewrite bot commits" as a hard rule. The
358	reason: change_ids on the bot side need to be permanently
359	stable for ochid trailers from the code side to resolve
360	forever. Even `jj describe` (description-only) changes the
361	commit_id, which doesn't break change_ids but does signal
362	that bot commits are mutable in a way they shouldn't be.
363	
364	Trade: any commit-level metadata fix has to be done by
365	appending a new commit, not amending the existing one.
366	Awkward but correct.
367	
368	### Bot-repo size and scaling thresholds
369	
370	Concrete measurement on a single-developer vc-x1 project
371	(2026-05-07, after `cargo clean`):
372	
373	- Code repo (excluding `.claude`): ~4M
374	- Bot repo (`.claude`): 311M
375	- Ratio: ~78:1 bot-to-code
376	
377	Cause: every Claude Code session writes a UUID-named
378	`.jsonl` file. Content is mostly unique per session —
379	git/jj packs each file's append history well, but
380	cross-file dedup is weak. So bot-repo bytes scale roughly
381	linearly with total session count.
382	
383	Linear extrapolation to shared-central multi-user (the bot
384	thinks this is a reasonable upper bound; actual savings
385	from cross-session dedup are small):
386	
387	- 5 devs: ~1.5G
388	- 20 devs: ~6G
389	- 50 devs: ~15G
390	
391	Rough operational thresholds:
392	
393	- **≤ ~10 users:** shared-central is fine.
394	- **~10-50 users:** shared-central starts hurting
395	  (multi-minute initial clone; noticeable `vc-x1 sync`
396	  pulls).
397	- **> ~50 users or > ~10G bot repo:** mitigations become
398	  necessary.
399	
400	### Monotonic-growth asymmetry
401	
402	Bot-repo size only grows. Once a session jsonl is
403	committed, the bot-side immutability rule keeps it
404	forever. This is by design (historical record), but it
405	means the bot repo has no analog of `cargo clean`:
406	code-repo working bytes can be reclaimed (build artifacts
407	come back on `cargo build`); bot-repo bytes are permanent.
408	
409	Sizing assumptions for shared-central scaling are a
410	one-way ratchet, not a steady-state cost.
411	
412	### Mitigation menu (when thresholds approach)
413	
414	None worth building preemptively. Listed so trigger points
415	have known responses:
416	
417	1. **Bot-repo pruning/archiving.** Move closed-out
418	   sessions (older than N months, or tied to commits no
419	   longer in any active branch) to an archive repo.
420	   Active bot repo stays small; archive fetched on demand
421	   when older history is referenced. The bot thinks this
422	   is the cheapest big win — recent sessions are the hot
423	   set, old ones are cold.
424	2. **Sparse fetch by trailer-referenced sessions.** When
425	   fetching the code repo, derive the set of bot-side
426	   change_ids referenced by ochids in the fetched range
427	   and fetch only those bot commits. Requires git/jj
428	   sparse-fetch + a trailer-walking step. Heavier to
429	   build but decouples clone cost from bot-repo size.
430	3. **Per-user bot repos.** The structural alternative —
431	   see "Per-user vs shared bot repo" above. Viable when
432	   shared-central pruning/sparse-fetch isn't enough.
433	4. **LFS for `.jsonl`.** Probably overkill — LFS targets
434	   binary blobs, not append-only text. Listed only
435	   because it's a known git escape hatch.
436	
437	### Tracking trigger
438	
439	Concretely measurable: the 311M baseline is the current
440	benchmark. When the shared-central bot repo crosses ~1G
441	or starts dominating clone time noticeably, that's the
442	design trigger for pruning. User count alone is not the
443	right signal; bot-repo size is.
444	
445	## Future-direction notes
446	
447	Two alternatives to the partner-bookmark technique that may
448	be worth considering once we live with the current scheme:
449	
450	### Always keep the bot repo on main
451	
452	Instead of creating a partner bookmark on the bot side for
453	each code-side branch, the bot side could be locked to a
454	single bookmark — `main` — for the entire lifetime of the
455	project. Every push would advance bot main, regardless of
456	what bookmark the code side is on.
457	
458	The bot thinks this aligns with "bot history is one linear
459	journal" more strongly than partner bookmarks do. Partner
460	bookmarks introduce *parallel* bot bookmarks even though the
461	bot history under them is still linear; an always-main
462	discipline removes that parallelism entirely.
463	
464	Trade: requires push / finalize / sync to support asymmetric
465	bookmark names per side (see next note).
466	
467	### Multi-bookmark-name support in push / finalize / sync
468	
469	Today, `vc-x1 push <bookmark>` advances the same bookmark
470	name on both code and bot sides. The "always-on-main"
471	discipline above (and other asymmetric workflows) requires
472	push / finalize / sync to take separate bookmark arguments
473	per side, e.g.:
474	
475	```
476	vc-x1 push --code-bookmark init-clone-refactor --bot-bookmark main
477	vc-x1 push -B init-clone-refactor              # bot defaults to main
478	vc-x1 push init-clone-refactor                  # both, today's behavior
479	```
480	
481	The bot thinks the right shape lands once `--scope` is
482	fully wired across the dual-repo commands — `--scope`
483	already handles "which side does this command apply to,"
484	and adding per-side bookmark arguments is a natural
485	extension.
486	
487	## Open questions worth thinking about
488	
489	- **Conflict resolution sessions: how do they get
490	  authored?** When user C resolves a merge conflict, does
491	  their bot session start a fresh chain rooted "from
492	  nowhere," or branch off one of the contributing chains?
493	  The chain-rooting question affects how the viewer renders
494	  it.
495	- **De-duplication on octopus merges.** If parents share
496	  ancestry, you'll get redundant ochids. Trim to unique
497	  tips? Keep all? The bot thinks trim, but worth deciding.
498	- **Bot-side bookmark scheme.** Per-session bookmark?
499	  Per-user-per-feature? Naming convention matters because
500	  bookmarks are how `jj git push` decides what to send.
501	- **Viewer concerns.** "Show me the sessions that
502	  contributed to this commit" is straightforward (read the
503	  trailers, walk back in each chain to the relevant range).
504	  "Show me the code commits this session contributed to" is
505	  the inverse and needs an index, since change_ids don't
506	  carry forward references. Probably build the index from a
507	  one-time scan of code-side trailers.
508	- **Migration story for existing repos** with single-ochid
509	  trailers — they're already valid in the multi-ochid
510	  scheme (N=1 case), so probably no migration needed. Worth
511	  confirming on the parser side.

28	## Root cause
29	
30	`cargo install` ignores `Cargo.lock` by default and re-resolves
31	from scratch, picking the newest semver-compatible version of
32	every dep independently.
33	
34	- The lockfile happens to pin one `winnow` that satisfies all
35	  the gix-* crates simultaneously.
36	- A fresh resolve picks two: `0.7.x` for one part of the gix
37	  graph, `1.0.x` for another. `gix-object` and `gix-actor` get
38	  compiled against different `winnow`s, so their `ErrMode<E>`
39	  types don't match even though they look identical.
40	
41	The smoking gun in `cargo install` output is the
42	`Locking N packages to latest …` line — that's cargo
43	announcing it just did a fresh resolve.
44	
45	## The asymmetry
46	
47	| command | reads `Cargo.lock`? | re-resolves? |
48	| --- | --- | --- |
49	| `cargo build` / `cargo test` / `cargo run` | yes | only if `Cargo.toml` changed |
50	| `cargo build --locked` (etc.) | yes | never; errors if it would need to |
51	| `cargo install` (default) | **no** | always, from scratch |
52	| `cargo install --locked` | yes | never; errors if it would need to |
53	
54	So build/test pass against the lockfile's dep graph, then
55	`cargo install` silently produces a binary built from a
56	different (and possibly broken) graph.
57	
58	## Workaround
59	
60	`cargo install --path . --locked`. Cargo has **no stable config
61	key or env var** to make `--locked` the default for
62	`cargo install`. Verified against the [cargo config
63	reference](https://doc.rust-lang.org/cargo/reference/config.html):
64	`[install]` only controls the install root directory; nothing
65	toggles lockfile behavior.
66	
67	The discipline therefore lives in the project's pre-commit
68	checklist (CLAUDE.md step 4) and in shell aliases
69	(e.g. `alias ci='cargo install --locked'`).

157	## Why `jj log` shows fewer commits than `gitk`
158	
159	If you're coming from git, jj's log output can be surprising compared to
160	tools like `gitk --all`.
161	
162	jj tracks *changes* (identified by change IDs), not individual git commits.
163	When you rewrite a change (`jj describe`, `jj rebase`, `jj squash`, etc.),
164	jj creates a new git commit and keeps the old one under `refs/jj/keep/*` as
165	undo history. `gitk --all` sees all of these obsolete commits; `jj log` only
166	shows the current version of each change.
167	
168	## Useful commands
169	
170	| Command | Description |
171	|---------|-------------|
172	| `jj log` | Show recent visible commits (default revset) |
173	| `jj log -r ::@` | Show **all** ancestors of the working copy |
174	| `jj log -r 'all()'` | Show all non-hidden commits (needed if you have multiple heads/branches) |
175	| `jj st | Show the status of the Working and Parent commits |
176	| `jj st -r <chid> | Status of the commit, <chid> such as `@`, `@-`, `xyz` |
177	| `jj show | Show the Working commit, -r @ |
178	| `jj show -r <chid> | Show the commit, <chid> such as `@`, `@-`, `xyz` |
179	| `jj evolog -r <chid>` | Show the evolution history of a single change |
180	| `jj op log` | Show operation history (each rewrite operation) |
181	
182	
183	In a single-branch workflow, `jj log -r ::@` and `jj log -r 'all()'` give
184	the same result. Use `all()` when you have multiple branches or heads.

224	### Why `jj log` shows fewer commits than `gitk`
225	
226	If you're coming from git, jj's log output can be surprising compared to
227	tools like `gitk --all`.
228	
229	jj tracks *changes* (identified by change IDs), not individual git commits.
230	When you rewrite a change (`jj describe`, `jj rebase`, `jj squash`, etc.),
231	jj creates a new git commit and keeps the old one under `refs/jj/keep/*` as
232	undo history. `gitk --all` sees all of these obsolete commits; `jj log` only
233	shows the current version of each change.
234	
235	### Useful commands
236	
237	| Command | Description |
238	|---------|-------------|
239	| `jj log` | Show recent visible commits (default revset) |
240	| `jj log -r ::@` | Show **all** ancestors of the working copy |
241	| `jj log -r 'all()'` | Show all non-hidden commits (needed if you have multiple heads/branches) |
242	| `jj st | Show the status of the Working and Parent commits |
243	| `jj st -r <chid> | Status of the commit, <chid> such as `@`, `@-`, `xyz` |
244	| `jj show | Show the Working commit, -r @ |
245	| `jj show -r <chid> | Show the commit, <chid> such as `@`, `@-`, `xyz` |
246	| `jj evolog -r <chid>` | Show the evolution history of a single change |
247	| `jj op log` | Show operation history (each rewrite operation) |
248	
249	
250	In a single-branch workflow, `jj log -r ::@` and `jj log -r 'all()'` give
251	the same result. Use `all()` when you have multiple branches or heads.
252	
253	## Cross-repo Linking with Git Trailers
254	
255	Commits in each repo use [git trailers](https://git-scm.com/docs/git-interpret-trailers)
256	to cross-reference their counterpart in the other repo. The `ochid`
257	(Other Change ID) trailer contains a workspace-root-relative path
258	and jj changeID:
259	
260	```
261	ochid: /.claude/xvzvruqo   # points to a .claude repo change
262	ochid: /wtpmottv            # points to an app repo change
263	```
264	
265	Paths always start with `/` (the workspace root, i.e. vc-x1).
266	Each repo has a `.vc-config.toml` that identifies its location
267	within the workspace, so tools can resolve these paths locally.
268	
269	For full details see:
270	- [Git trailer convention](./notes/chores-01.md#git-trailer-convention)
271	  — [ochid (Other Change ID)](./notes/chores-01.md#ochid-other-change-id)
272	  — [ChangeID path syntax](./notes/chores-01.md#changeid-path-syntax)
273	  — [.vc-config.toml](./notes/chores-01.md#vc-configtoml)
