15	/// or the spin-spin fast path when both ends stay hot on the same
16	/// CCX.
17	pub struct StdMpsc2Thread {
18	    req_tx: mpsc::Sender<u64>,
19	    resp_rx: mpsc::Receiver<u64>,
20	    worker: Option<thread::JoinHandle<()>>,
21	    counter: u64,
22	}
23	
24	impl StdMpsc2Thread {
25	    /// Spawn the echo worker, optionally pinning it to `worker_cpu`.
26	    pub fn new(worker_cpu: Option<usize>) -> Self {
27	        let (req_tx, req_rx) = mpsc::channel::<u64>();
28	        let (resp_tx, resp_rx) = mpsc::channel::<u64>();
29	        let worker = thread::spawn(move || {
30	            pin::pin_current(worker_cpu);
31	            while let Ok(v) = req_rx.recv() {
32	                if resp_tx.send(v).is_err() {
33	                    break;
34	                }
35	            }
36	        });
37	        Self {
38	            req_tx,
39	            resp_rx,
40	            worker: Some(worker),
41	            counter: 0,
42	        }
43	    }
44	}

48	        "std::sync::mpsc round-trip (2 threads)"
49	    }

52	        self.counter = self.counter.wrapping_add(1);
53	        self.req_tx.send(self.counter).unwrap();
54	        let v = self.resp_rx.recv().unwrap();

Feasibility confirmed — it works, and the numbers are interesting. Here's the assessment.

## TL;DR

**iceoryx2 benches are very feasible.** A prototype in the scratchpad compiles and runs today with iceoryx2 0.9.2 on your toolchain (Rust 1.96.1), single-process, in both configurations:

- **1t loopback** (same thread: publish then receive): **~259 ns/iter**
- **2t round-trip** (main → echo worker → main, two services, spin-receive): **~947 ns/iter**

Both map directly onto the existing bench shapes — `ice-1t`/`ice-2t` would look almost exactly like `mpsc-1t`/`mpsc-2t` (`step()` = send + spin-until-receive), and a `TProbe2` variant would work the same way `tp2-pc` does.

## What the prototype showed

- The API fits the `Bench` trait cleanly: `NodeBuilder` → `service_builder(name).publish_subscribe::<u64>()` → publisher/subscriber. The 2t version uses two services (req/resp) with the worker opening its own node in the same process — this worked without issue, confirming intra-process pub/sub is supported through the normal `ipc::Service` path (it goes through real shared memory even within one process, which is exactly what makes it an interesting data point next to the planned `zc-ring` benches).
- `subscriber.receive()` is **non-blocking only** — there's no parking recv. The bench must spin, so `ice-2t` measures the spin-spin fast path; there's no wake-cost variant unless you add iceoryx2's event/listener mechanism (possible, but a separate bench).
- `send_copy` copies the payload into a loaned shm sample; the zero-copy path (`loan_uninit` + write in place + `send`) is also available and would be the fairer comparison against `zc-ring` later.

## Caveats

- **Dependency weight**: pulls ~79 crates (serde, postcard, several iceoryx2-* subcrates). Build cost ~16 s cold in release. Not trivial, but contained.
- **System residue**: runs leave a persistent global management segment in `/dev/shm` (`iox2_..._node.global_mgmt`) and `/tmp/iceoryx2/{services,nodes}` dirs. On clean exit services are torn down; after a crash, stale resources can require cleanup (iceoryx2 has APIs and an `iox2` CLI for this). The bot thinks this is acceptable for a bench but worth a note in the bench doc comment, since a Ctrl-C'd run could make the next run's `open_or_create` behave differently.
- Service names are global to the machine — bench names should be distinctive (e.g. `iiac-perf-ice-2t-req`) to avoid colliding with other iceoryx2 users.
- A cosmetic startup warning ("No config file was loaded") prints once; suppressible via config or by accepting it.

The prototype lives at `scratchpad/ice-proto/src/main.rs` if you want to look. If you want to proceed, the natural shape is a version-bumped step adding `ice-1t`/`ice-2t` (or `tp2`-probed variants) to the registry — single-step or multi-step, your call.

> AGENT

I dug into the iceoryx2 source — a config file is one option, but there's a cleaner one. The warning comes from `Config::global_config()`, which lazily searches three places, in priority order:

1. `./config/iceoryx2.toml` — **cwd-relative**, so it only works when you happen to run from a directory containing it
2. `~/.config/iceoryx2/iceoryx2.toml` — per-user
3. `/etc/iceoryx2/iceoryx2.toml` — system-wide

If none exists it warns and uses `Config::default()` — so the warning is purely cosmetic; the defaults it falls back to are exactly what a stock config file would contain.

**My recommendation: no file — pass the config in code instead.** `NodeBuilder` has a `.config(&Config)` method, and `global_config()` (the only warning site) is only ever reached when a node is built *without* an explicit config. So:

```rust
NodeBuilder::new()
    .config(&iceoryx2::config::Config::default())
    .create::<ipc::Service>()
```

in the three places we build nodes kills the warning with identical behavior, and keeps the bench hermetic — results won't silently change because a machine happens to have a `~/.config/iceoryx2/iceoryx2.toml` lying around, which for a benchmark is arguably a feature: everyone who runs `iiac-perf` measures the same iceoryx2 configuration. A config file gives the opposite: per-machine state that the bench binary picks up invisibly (and the cwd-relative variant wouldn't even work for your installed binary unless you run from the repo root).

63	            .create::<ipc::Service>()

75	        let worker_stop = Arc::clone(&stop);

84	                .subscriber_builder()
85	                .create()

88	                .publisher_builder()
89	                .create()
90	                .expect("resp publisher");

92	                if let Some(sample) = req_rx.receive().expect("worker receive") {
93	                    resp_tx.send_copy(*sample).expect("worker send_copy");
94	                } else {

96	                }
97	            }
98	        });

101	        // published before the worker's subscriber connects is
102	        // silently dropped — and a lost first request would leave
103	        // step() spinning forever. Re-ping until an echo arrives,

1	# iiac-perf
2	
3	A general-purpose latency microbenchmark harness for Rust. Each
4	bench runs against a wall-clock time budget with auto-sized loop
5	counts, reports a percentile-band histogram in nanoseconds, and
6	subtracts calibrated apparatus overhead (timer-pair framing +
7	loop-per-iter) so the output reflects the workload, not the
8	measurement loop.
9	
10	Highlights:
11	
12	- Time-based runs (`-d SECONDS` per bench, `-D SECONDS` total)
13	  with auto-sized outer/inner loop counts.
14	- Band-based histogram (min→p1, p1→p10, …, p99→max) with count,
15	  mean, range, and an adjusted-mean column.
16	- Per-thread CPU pinning (`--pin`) with independent calibration
17	  pinning (`--no-pin-cal`), so the cal environment stays stable
18	  regardless of where bench threads land.
19	- Plug in new workloads by implementing the `Bench` trait and
20	  registering in `src/benches/`.
21	
22	The first benches measure Inter-Intra Application Communication
23	— function calls, async calls, channels, serde — which is what
24	seeded the project name. The harness itself is workload-agnostic.
25	
26	## Design (0.2.0)
27	
28	Design a Rust app that can measure the cost of various (IIAC) techniques.
29	By IIAC I mean all communication techniques between and within
30	applications such as regular function calls vs async function calls vs
31	channels vs serde/deser of json or zero-copy messaging using io_uring and
32	potentially any other technique. It would include between threads or
33	processes or apps on the same computer or between apps on the same LAN or
34	between apps over a WAN.
35	
36	Ideally I'd like to be able to see a histogram of the range of times of the
37	send and receive costs, not just the mean/average of 10^3 or 10^6 invocations.
38	So the cost of the work should or could be something near-zero such as just
39	echoing the input, but maybe there is value in doing some constant but

41	need to be aware of is that if we make the work too simple the compiler could
42	just keep things in registers which would not be representative of "real" work.

Is there a way to make the tests more comparable, that is the whole purpose, thoughts?

> AGENT

Good question — this gets at the heart of what the harness is for. The core problem: the 2t benches currently differ in **two** dimensions at once — transport (mpsc vs iceoryx2 shm) *and* wait policy (park/wake vs spin) — so the 8,027 ns vs 632 ns comparison says nothing clean about either. My thoughts on fixing that:

**Think of it as a 2×2 matrix: {transport} × {wait policy}.** Today we have only the diagonal — mpsc/park and ice/spin. Comparability comes from filling in the other two cells:

1. **`mpsc-2t-spin`** (cheap, high value): same mpsc round-trip but both ends spin on `try_recv()` instead of blocking in `recv()`. That's exactly the shape of the ice benches — non-blocking receive + `spin_loop` — so `mpsc-2t-spin` vs `ice-ps-2t` becomes a pure transport comparison: in-process channel queue vs shared-memory queue, same scheduler behavior (none). This is a ~30-line bench reusing the `mpsc-2t` structure. The bot thinks this lands somewhere in the hundreds of ns, and the gap to `ice-ps-2t` would then be the honest "cost of going through shm" number.

2. **`ice-ps-2t-wait`** (more work, second priority): iceoryx2 has an event mechanism (`Listener`/`Notifier`, `WaitSet`) for blocking waits. A variant where the worker parks on a listener and the publisher notifies would compare directly against today's `mpsc-2t` — both then price wake latency. More API surface to learn, and it changes the send path (send + notify), so it's a real second bench, not a flag.

3. **Pin for the recorded tables**: unpinned numbers wobble with thread placement (same CCX vs cross-CCX on the 3900X can differ substantially). For any table we record as "the" comparison, run `--pin 0,1` (and optionally `--pin 0,12` for the SMT-sibling case). The harness already supports this; it's just measurement discipline.

What already *is* comparable and can stay: all round-trips echo a `u64`, and the 1t pair (`mpsc-1t` 23 ns vs `ice-ps-1t` 250 ns) is a fair same-thread transport comparison today.

My recommendation: ship 0.10.0 as-is (its chores note already flags the caveat), then make `mpsc-2t-spin` + pinned comparison tables the next step — likely 0.11.0, single-step or with `ice-ps-2t-wait` as a second dev step if you want the full matrix. The existing todo items (`crossbeam-1t/2t`, `flume`, `tokio-mpsc`) would eventually slot into the same spin/park matrix, so the convention set here propagates.

Nothing is wrong — the numbers reconcile. Here's the full picture:

**iceoryx2's own benchmark, run on your 3900X** (v0.9.2, `--bench-all`): **250 ns one-way latency**, i.e. ~500 ns round-trip. Our `ice-ps-2t` measures 629 ns round-trip. Same ballpark; the ~130 ns delta has identifiable causes visible in their benchmark source:

1. **They report one-way** (`elapsed / (iterations × 2)`) — if you saw "250 ns" in their marketing and compared to our 629 ns, that's a 2× definitional difference right there.
2. **They never write the payload** in default mode — `loan_slice_uninit` + `assume_init` and send, payload untouched. It measures pure signaling. Ours writes and reads a real `u64` via `send_copy`.
3. **They run pinned at realtime priority 255**; ours ran unpinned at normal priority.
4. **They reuse the loan-based zero-copy path**; ours pays `send_copy`'s loan+copy each step (trivial for 8 B, but not zero).

**On "claim to fame":** iceoryx2's performance story is about *inter-process* communication, where the competition is unix sockets and message queues at 10–20 µs round-trip — it beats those by ~20×. And critically, its latency is **payload-size-independent**: their 250 ns number is with 8 KiB samples. `mpsc` moving 8 KiB would copy it twice per hop; iceoryx2 wouldn't move a byte. What it was never going to win is an 8-byte ping-pong against an in-process channel, where `mpsc` is a single atomic queue op in one address space (~120 ns RT) while iceoryx2 does offset translation, multi-subscriber connection management, and ref-counted sample lifecycle — the price of crossing process boundaries at all.

So the matrix conclusion stands, properly framed: for tiny in-process messages, spin-mpsc wins on transport; iceoryx2's ~630 ns buys process-boundary capability and size-independence that mpsc simply doesn't have. A payload-size sweep (8 B vs 8 KiB vs 1 MiB) would make that trade visible in our own tables — arguably the most honest "comparability" improvement left.

If you want, follow-ons for the todo: (a) switch the ice benches to the loan-based zero-copy send path (closer to their method, and it's the API a perf-sensitive user would actually use), (b) payload-size variants. Both are measurement-fidelity work, not bug fixes — our bench was correct, just measuring a slightly different (and honest) thing.
