193	### Why `jj log` shows fewer commits than `gitk`
194	
195	If you're coming from git, jj's log output can be surprising compared to
196	tools like `gitk --all`.
197	
198	jj tracks *changes* (identified by change IDs), not individual git commits.
199	When you rewrite a change (`jj describe`, `jj rebase`, `jj squash`, etc.),
200	jj creates a new git commit and keeps the old one under `refs/jj/keep/*` as
201	undo history. `gitk --all` sees all of these obsolete commits; `jj log` only
202	shows the current version of each change.
203	
204	### Useful commands
205	
206	| Command | Description |
207	|---------|-------------|
208	| `jj log` | Show recent visible commits (default revset) |
209	| `jj log -r ::@` | Show **all** ancestors of the working copy |
210	| `jj log -r 'all()'` | Show all non-hidden commits (needed if you have multiple heads/branches) |
211	| `jj st | Show the status of the Working and Parent commits |
212	| `jj st -r <chid> | Status of the commit, <chid> such as `@`, `@-`, `xyz` |
213	| `jj show | Show the Working commit, -r @ |
214	| `jj show -r <chid> | Show the commit, <chid> such as `@`, `@-`, `xyz` |
215	| `jj evolog -r <chid>` | Show the evolution history of a single change |
216	| `jj op log` | Show operation history (each rewrite operation) |
217	
218	
219	In a single-branch workflow, `jj log -r ::@` and `jj log -r 'all()'` give
220	the same result. Use `all()` when you have multiple branches or heads.
221	
222	## Cross-repo Linking with Git Trailers
223	
224	Commits in each repo use [git trailers](https://git-scm.com/docs/git-interpret-trailers)
225	to cross-reference their counterpart in the other repo. The `ochid`
226	(Other Change ID) trailer contains a workspace-root-relative path
227	and jj changeID:
228	
229	```
230	ochid: /.claude/xvzvruqo   # points to a .claude repo change
231	ochid: /wtpmottv            # points to an app repo change
232	```
233	
234	Paths always start with `/` (the workspace root, i.e. vc-x1).
235	Each repo has a `.vc-config.toml` that identifies its location
236	within the workspace, so tools can resolve these paths locally.
237

293	ring for readers seeing the code out of context.

348	composes the commit message (via `--title`/`--body` or `$EDITOR`),
349	prompts for message approval, then commits both repos → advances

351	local mutation window roll both repos back via `jj op restore`;
352	after `push-app` succeeds the remote boundary is crossed and
353	recovery is forward-only.

356	Single-step and multi-step changes are of equal importance: a
357	single-step change is one `push` invocation; a multi-step change
358	is one `push` per `X.Y.Z-N` commit plus one for the final release
359	commit. Each step gets its own commit, its own push, and its own
360	finalize — so dev markers land on the remote and in `.claude` as
361	they happen rather than being batched until the end.

364

369	vc-x1 push main --dry-run                            # preview (no side effects)
370	vc-x1 push main --from commit-app                    # resume from specific stage

372	vc-x1 push main --restart                            # clear saved state; start fresh

302

311	  `desc.lines().next().unwrap_or("")` — empty desc → empty title).
312	
313	Bare `// OK` is not used (reads like a truncated comment).
314	Abbreviations (e.g. `SE`) are not used because they require a decoder
315	ring for readers seeing the code out of context.

318	`#[allow(clippy::unwrap_used)]` so the site stays silent if we enable

320	
321	```rust
322	let max = stderr_level.unwrap_or(LevelFilter::Info); // OK: default verbosity when -v/-vv absent

324	
325	match matches.len() {

336	correct test behavior.

366	
367	**Prerequisite — one-time per repo:**
368	
369	- `.gitignore` must include `/.vc-x1` so push's in-progress
370	  state files (`.vc-x1/push-state.toml`) don't get committed.
371	  Push warns at preflight if the entry is missing.
372	- The target bookmark must have a tracking remote
373	  (`jj bookmark track <bookmark>@origin -R .`). `jj git fetch`
374	  creates remote bookmarks as non-tracking by default; push
375	  currently surfaces this as a raw jj error at `push-app` after
376	  commits are locally made, so confirm tracking is set up
377	  before the first push in a new clone.
378	
379	**Use `vc-x1 push <bookmark>` — it wraps the full flow in one
380	command with two interactive approval gates.** Push runs
381	preflight (sync + fmt + clippy + test), prompts for review,
382	composes the commit message (via `--title`/`--body` or `$EDITOR`),
383	prompts for message approval, then commits both repos → advances
384	bookmarks → pushes app → finalizes `.claude`. Failures inside the
385	local mutation window roll both repos back via `jj op restore`;
386	after `push-app` succeeds the remote boundary is crossed and
387	recovery is forward-only.
388	
389	**Run this flow after every step** — not only at session end.
390	Single-step and multi-step changes are of equal importance: a
391	single-step change is one `push` invocation; a multi-step change
392	is one `push` per `X.Y.Z-N` commit plus one for the final release
393	commit. Each step gets its own commit, its own push, and its own
394	finalize — so dev markers land on the remote and in `.claude` as
395	they happen rather than being batched until the end.
396	
397	### Run `vc-x1 push`
398	
399	```
400	vc-x1 push main                                      # interactive (review + $EDITOR)
401	vc-x1 push main --title "..." --body "..."           # flags skip $EDITOR
402	vc-x1 push main --yes --title "..." --body "..."     # full non-interactive
403	vc-x1 push main --dry-run                            # preview (no side effects)
404	vc-x1 push main --from commit-app                    # resume from specific stage

406	vc-x1 push main --restart                            # clear saved state; start fresh
407	```
408	
409	The two approval gates are surfaced by push itself:
410	
411	1. **Review** — push prints `jj diff --stat` for both repos and
412	   prompts `[y/N]`. Approve = "the work is done right".
413	2. **Message** — push either uses `--title`/`--body` (non-editor
414	   path) or opens `$EDITOR` on a template. Approve = "the message
415	   reads right".
416	
417	Both titles and bodies are the **same** across the two commits;
418	per-repo `ochid:` trailers are appended by push itself. See
419	`## Commit Message Style` for body structure.

421	For the full flag list and stage machine, see `vc-x1 push --help`
422	and `notes/chores-05.md > Add push subcommand (0.37.0)`.

474	
475	After `vc-x1 finalize` is launched — **whether mid-session per-step

489	between finalize and the next explicit instruction.

491	Exceptions to this rule may emerge later but are not authorized at
