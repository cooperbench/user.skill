## Custom Profile Support — Analysis

### The core tension

Cargo requires custom profiles to be **declared** in `Cargo.toml` (with at least `inherits = "dev"` or `inherits = "release"`). You can't conjure a profile purely from `--config` flags. So tspec can never be the *sole* source of profile definitions — `Cargo.toml` must declare them.

### What tspec can cleanly own

Two separate concerns:

1. **Profile selection** — which profile to build with (`--profile NAME`)
2. **Profile overrides** — tweaking settings like opt-level, lto, codegen-units

tspec is already good at (2) via `cargo.config.profile.release.opt-level = "z"` etc. — these become `--config` args that override whatever `Cargo.toml` says.

### Proposed approach: tspec selects and overrides, Cargo.toml defines

| Responsibility | Where |
|---|---|
| Profile **definition** (`inherits`, existence) | `Cargo.toml` |
| Profile **selection** (which one to use) | tspec `cargo.profile` |
| Profile **overrides** (opt-level, lto, etc.) | tspec `cargo.config.profile.NAME.*` |

This means:
- Change `cargo.profile` from a `Debug`/`Release` enum to a **string** (or add `Custom(String)`)
- `"debug"` → no flag (cargo default), `"release"` → `--release`, anything else → `--profile <name>`
- Lift the restriction in `validate_config_profiles` to allow custom profile names in `cargo.config.profile.*`
- Update binary path resolution (`find_paths.rs`) to look in `target/<profile-name>/` for custom profiles (cargo uses the profile name as the directory, with `dev` mapping to `debug`)
- `ts set cargo.profile` validation accepts any string (or at least any valid cargo profile name)

### Why this avoids the "two places" problem

The user defines the profile structure in `Cargo.toml` once (this is unavoidable — cargo demands it). tspec just **points at** a profile and optionally **tweaks** it. No duplication. The common case (`debug`/`release`) needs nothing in `Cargo.toml` at all. Only when you want a truly custom profile (like `release-small` or `bench`) do you need a `Cargo.toml` entry — and that's a cargo requirement, not a tspec one.

### Implementation scope

This is fairly contained:
1. `types.rs` — change `Profile` enum to string (or add variant)
2. `cargo_build.rs` — emit `--profile <name>` instead of `--release`
3. `find_paths.rs` — resolve profile name to target subdirectory
4. `ts_cmd/edit.rs` — relax validation for `cargo.profile` and `cargo.config.profile.*`
5. `types.rs` — relax `validate_config_profiles`
6. Tests
