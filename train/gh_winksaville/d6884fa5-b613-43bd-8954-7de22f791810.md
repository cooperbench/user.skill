Yes on consistency, with one big caveat on "fastest": `--pin 0,12` on your 3900X is the **SMT-sibling pair** — logical CPUs 0 and 12 are the same physical core. That's why this run is so fast: the ring's cache lines live in the L1/L2 that both hyperthreads share, so a "cross-thread" hop never leaves the core. You're seeing 35 ns adjusted trimmed vs ~100 ns for two real cores (`--pin 0,1`, your earlier tier-comparison numbers). So for optimizing an algorithm:

- **Pinning buys you repeatability**, which is the thing that matters for A-vs-B: no migrations, stable cache topology, tight stdev (your `stdev min-p99` dropped to 3 ns — that's publication-grade consistency in the body of the distribution).

Easy — and there's a version that's *better* than deriving names from the floats: derive **both** the floats and the names from a tiny structural description, so nothing ever parses a float back into a name.

The insight is that the boundary set is already generative: `min`, then z-tail K = 4→2, then deciles 1→9, then n-tail K = 2→10 (0.99 *is* `n2`, so the high loop starts at 2), then `max`. About 50 lines total:

```rust
struct Boundary { pct: f64, zpn: String, frac: String }

fn boundaries() -> Vec<Boundary> {
    let mut v = vec![Boundary { pct: 0.0, zpn: "min".into(), frac: "min".into() }];
    for k in (2..=Z_DEPTH).rev() {                       // z4, z3, z2
        v.push(Boundary { pct: 10f64.powi(-k), zpn: format!("z{k}"), frac: frac_low(k) });
    }
    for d in 1..=9 {                                     // p10 .. p90
        v.push(Boundary { pct: d as f64 / 10.0, zpn: format!("p{d}0"), frac: format!("0.{d}0") });
    }
    for k in 2..=N_DEPTH {                               // n2 (=0.99) .. n10
        v.push(Boundary { pct: 1.0 - 10f64.powi(-k), zpn: format!("n{k}"), frac: frac_high(k) });
    }
    v.push(Boundary { pct: 1.0, zpn: "max".into(), frac: "max".into() });
    v
}
```

with `frac_high(k)` = `"0."` + k nines `_`-grouped in threes, `frac_low(k)` = `"0."` + (k−1 zeros + `"1"`) grouped — pure string building, no `log10`, no float-printing edge cases. > AGENT

The `p10` first row isn't fast samples going missing — it's a consequence of how bands are populated combined with how lumpy this workload is.

## The mechanism (`harness.rs:384-398`)

The report doesn't slice by rank. It walks each **recorded histogram bucket** (a distinct value) and drops the *whole* bucket into one band, chosen by the bucket's **midpoint rank**:

```
mid_rank = (cumulative + count/2) / sample_count
idx      = first boundary whose pct > mid_rank
```

A band row prints only if it caught at least one bucket (`band_count[i] == 0` → skipped, line 413). A bucket is never split across bands.

## Applied to your run

`zcr-spin-1t` resolves to a handful of discrete values. The smallest is **5.2 ns**, and it alone holds **98,954** of the 4,832,761 samples. Its midpoint rank:

```
(0 + 98,954/2) / 4,832,761  =  49,477 / 4,832,761  ≈  0.01024
```

Now walk the sub-p10 boundaries — `z4`=0.0001, `z3`=0.001, `z2`=0.01, `p10`=0.10:

- 0.01024 is **not** < 0.0001, 0.001, or 0.01 …
- it **is** < 0.10 → the 5.2 ns bucket lands in the **p10** band.

So `z4`/`z3`/`z2` catch no bucket and are suppressed; `p10` is the first non-empty band. And indeed the `p10` row shows `first == last == 5.2 ns`, `range 0.0` — a single bucket.

## Why it "just missed"

The fast tail (`z4`/`z3`/`z2`, the sub-1% region) can only populate if some bucket's *midpoint rank* falls below 0.01 — i.e. the fastest discrete value must account for less than ~1% of samples. Here the fastest value is ~2% of the run, and its midpoint sits at 1.024% — a hair past the `z2` = 1% line. Had 5.2 ns held fewer than ~94,000 samples (mid-rank < 0.01), it would have landed in `z2` and you'd have seen a `z2` row instead.

This is the flip side of what the README notes for the slow tail ("a band only prints when it has samples"): a distribution this concentrated at its floor can't subdivide its *fast* tail, because one indivisible bucket already overshoots the z-boundaries. The `-d 1` short run doesn't change this — even at `-d 30` the floor bucket stays ~2%, so `p10` remains the first row for this bench.

- **raw** (`zcr_raw_2t.rs:91-100`) is the naive "call the fallible API in a loop" pattern:
  ```rust
  loop { match self.resp_rx.reserve_slot::<Msg>() { Ok(..)=>.., Err(Empty)=>spin_loop() } }
  ```
  Every iteration re-runs `reserve_slot` (`consumer.rs:71-72`), which loads **both** indices: `consumer_idx` (Relaxed) *and* `producer_idx` (Acquire).

- **with** / **spin** call `reserve_slot_with` (`consumer.rs:104-133`), whose whole point is to hoist the caller-owned index out of the retry loop. Its own doc says it:

  > `consumer_idx` is ours and loaded once; only `producer_idx` is re-read per attempt.

So on the waiting side, **raw redundantly re-loads its own `consumer_idx` on every spin; with/spin load it once and spin only on the peer's `producer_idx`.** That's the entire code delta.

And `reserve_slot_spin` *is* `reserve_slot_with(policy::spin)` (`consumer.rs:144`) — which is why **with and spin are statistically identical** (mean 114.8 vs 115.0, trimmed stdev 7.46 vs 7.19). They're the same code path with a different-shaped closure.

## Why the redundant load costs you ~30 ns and widens the body

Two facts rule out the usual suspects:
- `producer_idx` and `consumer_idx` are each `CacheAligned` on **separate cache lines** (`lib.rs:78-79`, "Header spanning four cache lines"), so this is **not** false sharing between the two indices.
- The extra load is Relaxed and on main's *own* line — cheap in isolation.

**We think** the mechanism is: a relaxed **atomic** load can't be hoisted or coalesced out of a loop by LLVM (atomics are treated conservatively), so raw genuinely issues that second load every spin. That makes each spin iteration longer and, more importantly, changes *when* main samples the peer's `producer_idx` relative to the worker's `commit` store landing. The wait is a tight race against a cross-core store becoming visible; a looser, longer spin body samples that store later and less regularly — so you get both a higher mean and a *multi-modal* body (raw's 120/129/130/140/150 in ~10 ns steps ≈ one Zen2 cross-core coherence hop each, vs with/spin collapsing to 100/109/110). The tails (`n3`+) are dominated by scheduler/OS effects and look ~the same across all three, as expected.

That is precisely the cost this bench family was built to expose — your doc comment on `zcr_raw_2t.rs:22-24` frames it as "isolates API-tier cost under real cross-core traffic." raw = the hand-rolled retry that re-reads the owned index; `_with`/`_spin` = the same retry with that read hoisted.

## To confirm it's the extra load and not something else

A couple of cheap checks if you want certainty:
- **Disassembly**: `objdump`/`cargo asm` the two `step()` inner loops — raw's should show two `mov`s from the header (both indices), with/spin one. That nails the "non-hoistable extra load" claim directly.
- **perf**: `perf stat -e mem_inst_retired.all_loads,cache-references iiac-perf -d 10 zcr-raw-2t` vs `zcr-with-2t` — raw should retire measurably more loads per call.
- **Pin them**: `--pin 0,1` (same-CCX) vs `--pin 0,12` (SMT siblings). If the gap scales with cross-core hop cost, it shrinks on SMT siblings and grows across CCDs — consistent with the coherence-timing story; if it stayed constant it'd argue for pure per-spin instruction cost instead.
