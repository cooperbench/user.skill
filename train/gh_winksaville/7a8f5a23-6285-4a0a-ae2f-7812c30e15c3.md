The issue is that you're recording the total time for `INNER_ITERATIONS` calls into the histogram, but you want the per-call time. The histogram doesn't know about inner iterations — it just stores whatever values you give it.

The simplest approach: **divide before recording**.

```rust
hist.record(elapsed_ns / INNER_ITERATIONS).unwrap();
```

This gives you the average per-call time for each batch of inner iterations, which is what you actually want in the histogram. The division by 10 effectively gives you ~0.1ns resolution improvement since you're averaging out the timer quantization noise.

The tradeoff: you lose visibility into per-call variance *within* each inner loop batch — you're recording the mean of each batch. But for measuring timer overhead where calls are nearly identical, that's fine. The outer loop (10M iterations) still captures variance across batches.

An alternative if you want even more precision: increase `INNER_ITERATIONS` further (e.g., 100) so the division gives you sub-nanosecond averages. But note that `hdrhistogram` stores `u64` values, so sub-1ns results will be truncated to 0. If you want sub-nanosecond reporting, you could record in **picoseconds** instead:

```rust
let elapsed_ps = (start.elapsed().as_nanos() as u64) * 1000;
hist.record(elapsed_ps / INNER_ITERATIONS).unwrap();
```

Should I say "invocations" or "calls" also, how to add the 1,000 commas

> AGENT

"calls" is more natural for functions. For the commas, you can use the `num-format` crate or just format it yourself. But the simplest approach for a constant like this is to use a separator-formatting trick with Rust's standard library — unfortunately `std::fmt` doesn't support digit grouping natively.

Easiest options:

1. **Simple helper function:**
```rust
fn fmt_commas(n: u64) -> String {
    let s = n.to_string();
    let mut result = String::new();
    for (i, c) in s.chars().rev().enumerate() {
        if i > 0 && i % 3 == 0 { result.push(','); }
        result.push(c);
    }
    result.chars().rev().collect()
}
```

2. **Use the `thousands` or `num-format` crate** — adds a dependency for one line of output though.

Given this is a small tool, the helper function is probably the right call. Up to you.

A few useful metrics and how to check them:

**Dependency tree** — how much does it pull in?
```
cargo tree -p <crate>
```

**Binary size impact** — before/after adding the dep:
```
cargo bloat --release --crates
```

**Compile time impact:**
```
cargo build --timings --release
```
Generates an HTML report showing per-crate compile times.

**Source size / complexity** — check on crates.io or `lib.rs` for:
- Lines of code
- Number of transitive dependencies
- Download size

For something like `thousands` (digit grouping), it's tiny — zero dependencies, ~100 lines. `num-format` is heavier with more features and a few deps.

For a one-liner in a small tool, the helper function avoids the question entirely. But if you're curious, try `cargo tree` and `cargo bloat` on your project — they're the most concrete answers to "what did this dependency actually cost me."
