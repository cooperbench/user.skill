I dug into how the report labels work. Here's what `min..n2` actually is and why the `min` looks orphaned.

## What the label means

The trimmed summary rows (`mean min..n2`, `stdev min..n2`) report stats over the **non-tail** samples — everything from the global minimum up to the p99 boundary (`n2` ≡ p99), excluding the top-1% tail bands (`n3 … max`). It's a **boundary-to-boundary range**:

- `min` = `boundaries()[0]` (`bands.rs:109-113`) — the floor of the whole histogram, pct 0.0
- `n2` = the p99 boundary — the upper cut of the trim (`harness.rs:372`)

Both `min` and `n2` are real entries in the boundary ladder, so as a *range of boundaries* the label is correct and stable.

## Why it looks wrong

Band **rows** are labeled by their **upper** boundary (`harness.rs:419`, `label: bounds[i + 1]`). So the row loop starts at `bounds[1]` — meaning `min` (`bounds[0]`) is **never** printed as a row label. The first visible row is `z4`/`z3`/whatever the smallest non-empty band is. So a reader scanning row names for `min` won't find it, and `min..n2` reads as referencing a row that isn't there.

Your instinct — "make `min` be what the first row displays" — would actually be **wrong** semantically: the trim genuinely includes all the sub-`z4` samples down to the true minimum, so labeling the floor `z4` (or whatever the first row is) would imply those samples are excluded, and it'd be *unstable* (changes with which bands are populated per run).

So the range endpoints are right; the friction is purely that `min` is a lower-boundary name in a table that only ever prints upper-boundary names.

**The deciding factor isn't a universal rule — it's which edge you name the band by.** They should match:

- Computing/binning tools (numpy, language ranges) label by the **lower** edge or use anonymous numeric bins, so left-closed `[lower, upper)` is their default.
