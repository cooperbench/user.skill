**Delegation-to-OS pattern (the majority):**
- **Criterion.rs** — no pinning. Docs recommend `taskset` + setting CPU governor externally.
- **Google Benchmark** (C++) — no pinning. Same guidance.
- **hyperfine** — no pinning. Users wrap with `taskset` or `nice`.
- **wrk / wrk2** — no pinning. External.
- **iai / iai-callgrind** — N/A; deterministic counter-based, affinity is irrelevant.
- **nanobench / picobench** — no pinning.

- **fio** — `--cpus_allowed=0-5` + `--cpus_allowed_policy={shared,split}` to distribute I/O worker threads. I/O benchmarking is topology-sensitive enough that external taskset can't express thread-to-queue mappings.
- **perf(1)** — `-C 0,1` (kernel tracing tool, not a benchmark per se, but same family).
- **stress-ng** — `--taskset` flag, but it's a thin wrapper around the syscall.
- **sysbench** — thread count but no direct pin; users use taskset.

**Why most delegate:** `taskset -c 0,1 ./bench` pins the whole process and works for single-thread benches. "Do one thing well" — benchmark tools measure, OS tools place.

**Why we benefit from built-in for *this* tool:** `taskset` sets a process-wide CPU mask; within that mask, the kernel still migrates threads freely. **Design comparison**: our `--pin` is closest to `fio`'s model — list of CPUs treated as a pool, positional assignment to threads, wrap-around for oversubscription. That's a well-trodden shape for per-thread pinning when the tool cares about placement topology.

Not kernel magic — the bench characteristics make placement nearly irrelevant for this workload. Here's what's happening:

**This is a purely synchronous round-trip** — at any moment, exactly one of the two threads can run (the other is parked waiting for a message). There's no concurrent work to exploit, so "having two cores" doesn't help.

**Where the time actually goes** (look at `time`'s output):
- Unpinned `sys`: 2.97s, pin 0,0 `sys`: 3.48s, pin 0,1 `sys`: 3.55s
- ~70% of runtime is in the kernel, not in user code

That kernel time is **`futex_wake` + `futex_wait`** — the primitives crossbeam-channel uses to park/unpark threads on an empty queue. Each round-trip does ~2 park/unpark pairs. The syscall itself is ~1µs on Linux; cache coherency across cores is ~100ns. **So syscall overhead dominates, not placement.**

**Comparing the two pinned cases in detail:**

| config | what happens | cost |
|---|---|---|
| `--pin 0,0` | Thread A sends, parks → kernel context-switches to B (same CPU, L1/L2 stays hot) → B recvs/sends/parks → switch back to A | 2× ctx switch on same core, **cache warm**, no cross-CPU traffic |
| `--pin 0,1` | A sends, parks → B wakes on CPU 1 (IPI + cross-core cache-line transfer) → B sends/parks → A wakes on CPU 0 (same in reverse) | 2× cross-CPU wake, cache line bounces CPU 0↔1 (~50ns/bounce) |

Both pay ~2× (wake cost). One pays context-switch, the other pays cache transfer. On Zen 2 these come out roughly equal, as you saw.

**Why unpinned is *slower* even though it has "more CPUs":** without pinning, the scheduler migrates threads between CCXs (3900X has 4 CCXs of 3 cores; cross-CCX L3 is 2–3× intra-CCX). Add random migration-induced cold caches, and you pay more than pinning costs. The "80 ns min" you saw is a lucky alignment where neither thread had to park; irrelevant to mean.

**When placement *would* matter:** asymmetric work (producer faster than consumer), batched sends (many messages between wakes, so cache coherency dominates over syscall), or lock-free spin-based channels (no syscalls, pure cache-line traffic). For those, `--pin 0,1` would decisively beat `--pin 0,0`.

**Takeaway for this tool:** the current MPSC round-trip is **syscall-bound**, not communication-bound. A future `spsc-spin-2t` or `crossbeam-bounded-2t` bench with spin-polling would likely show dramatic placement differences.

Two things here. Let me take them in order.

## Why pinning kills min+p1

The fast path requires **both threads to be simultaneously running and spinning** inside crossbeam's spin-before-park window (a few hundred ns). Pinning doesn't guarantee that — it only restricts *which CPUs* each can run on. The scheduler decides *when*.

- **Unpinned**: 24 CPUs available, the load balancer aggressively keeps both threads runnable. When main sends, worker is often already spinning, picks up within ~50 ns (cache line transfer). Fast path ~20 % of the time.
- **`--pin 0,1`** (different CPUs): both threads *can* run concurrently, but the scheduler treats each CPU's idle state independently. After main's send, main parks (its own spin window expires before worker's response arrives). The scheduler sees CPU 0 idle and may let it idle. By the time worker's response arrives, main must wake via `futex_wake` — syscall path.
- **`--pin 0,0`** (same CPU): only one thread runs at a time, every handoff is a context switch by definition. No possible fast path.

The fix for "pinning + fast path" would be either:
1. **`SCHED_FIFO` priority** — keeps pinned threads hot, preempts background work. Removes scheduler latency.
2. **Spin-forever channel** — no parking at all, burn 100 % CPU. Dedicated-benchmark mode only.
3. **Adjust crossbeam's spin window** — longer spin before park buys more fast-path hits at the cost of CPU burn when idle.

So pinning trades variance (great) for fast-path access (gone). To get both, you need priority tuning or a different channel type.

## Your design — ring-buffer + intrusive overflow list

This is a sound, well-known pattern (intrusive lock-free queues show up in RT kernels, network stacks, high-throughput middleware). A few things to think about:

**The "never-block, never-allocate" part works because:**
- Ring is lock-free CAS on head/tail — fast common case, bounded space
- Overflow list is a lock-free Treiber stack or Michael-Scott queue with the `next` pointer embedded in the message — no new allocation at send, since caller already owns the message

**Design questions worth pinning down early:**

1. **SPSC, MPSC, MPMC?** Complexity jumps a lot between these. MPSC overflow is easier than MPMC because only one consumer touches the list's head.

2. **Overflow ordering**: LIFO (stack, trivial CAS) or FIFO (queue, needs M-S or similar)? LIFO is cheaper but breaks sequence. Probably FIFO for a "messaging" system.

3. **Fast path vs overflow path**: consumer has to drain ring first, then check overflow, or interleave? If you always drain ring first, overflow messages wait behind potentially newer ring messages — a priority-inversion of sorts.

4. **Memory reclamation**: who owns the message after send? If the receiver takes ownership, the sender can't reuse — no ABA issue. If senders reuse (e.g. pre-allocated pool), you need epoch-based reclamation or hazard pointers to avoid ABA on the overflow list's `next` pointer.

5. **Single `next` pointer**: if the message is ever enqueued to more than one list (e.g. overflow + a "pending ack" list), one pointer isn't enough. Make sure the lifecycle is strictly "owned by ring OR owned by overflow OR owned by consumer" — never more than one.

6. **Message sizing**: intrusive pointer is at a fixed offset (`next: AtomicPtr<Self>`), so messages need a common header type. Fine if all messages derive from `trait Message` with that header.

7. **The "never-block" guarantee**: technically the overflow list's CAS loop can still retry, but that's spin, not block. Make sure "never block" means "no OS-level park", not "no contention spin".

**Crates to look at / compare against:**
- `crossbeam-queue::SegQueue` — unbounded lock-free but allocates segments
- `rtrb` — realtime-safe ring, SPSC bounded, no overflow
- LMAX Disruptor — different philosophy (back-pressure + prefetch), worth studying for the ring-buffer discipline

That step function is the **crossbeam spin-window cliff**. Look across all runs:

| run | p10 | p20 | gap |
|---|---|---|---|
| `-d 0.5` | 701 ns | 6,351 ns | **9×** |
| `-d 1` | 6,151 ns | 6,575 ns | 1× (both slow) |
| `-d 5` | 861 ns | 6,231 ns | **7×** |
| `-d 10` | 551 ns | 6,043 ns | **11×** |

There's essentially **nothing between ~1 µs and ~5 µs**. The distribution is bimodal with a desert in between. That's because there are exactly two outcomes for each recv:

1. **Spin catches it** (~100–900 ns): the receiver was already spinning when the message arrived. Cost = cache-line transfer + a few instructions. No syscall.
2. **Spin misses, thread parks** (~6,000+ ns): the spin window expired, `futex_wait` was called, sender must `futex_wake` the receiver. Cost = two syscalls + scheduler + cache reload.

There's no mechanism that produces a 2–5 µs result — it's binary. Either the spin window catches the message or it doesn't. The step between p10 and p20 is literally the boundary between "spin hit" and "spin miss" populations.

The `-d 1` run where p10 is already at 6,151 ns just means that run had fewer spin-hits (< 10% fast-path fraction that time — scheduler luck).

This is actually a fingerprint of crossbeam-channel's internal spin-then-park implementation. A channel with a different strategy (longer spin, adaptive spin, or no spin) would show a different shape at exactly this boundary.

> AGENT

Both are real — they're measuring different things:

**Unpinned** measures "MPSC round-trip cost on a shared system where the scheduler does what it wants." That's the realistic deployment scenario — your actor system won't own dedicated cores in production. The bimodal distribution (fast spin-hit ~200 ns, slow park/unpark ~7 µs) is genuinely what a consumer of this channel would experience.

**Pinned** measures "MPSC round-trip cost with deterministic thread placement." That's the *channel's intrinsic cost* with scheduler noise removed. The unimodal 3.5–9.2 µs distribution is the true park/unpark cost of crossbeam-channel on Zen 2 at L3-shared core distance.

Which one to care about depends on the question:

| question | use |
|---|---|
| "How fast is this channel?" | pinned — isolates the mechanism |
| "What will my app actually see?" | unpinned — includes scheduler reality |
| "Is my channel better than crossbeam?" | pinned — apples-to-apples |
| "Should I pin threads in production?" | compare both — the answer is "it depends on your p99 budget" |

For your actor system design, the pinned run is probably the more useful baseline — it tells you the floor cost of a round-trip through the synchronization primitive. Your custom ring-with-no-park channel should beat the 3.5 µs min-p1 pinned number since it eliminates the `futex_wake` entirely.

For bursty workloads that's the real argument for pinning — not "is it faster" but **"is it predictable."** A burst arrives, you need to drain N messages. Unpinned: some drain at 400 ns, some at 7 µs — your tail latency is dominated by which mode the scheduler happened to be in when the burst hit. Pinned: every message costs ~5.6 µs ± 1.3 µs, you can budget for it.

For your actor system this means: if you're targeting deterministic latency (which a state-machine-based actor system with explicit back-pressure implies you are), **pin your threads**. Accept the slightly higher floor (3.5 µs vs 200 ns best-case) in exchange for knowing exactly what you'll get. The unpinned fast path is a gift from the scheduler you can't rely on.

**Why was it hard?** Your expectation was fine — you wanted symmetric bands. The difficulty was that **percentiles are points, bands are ranges**, and we were trying to shoehorn a range into a point label. "p99" is a single boundary value at the 99th percentile. When you associate a *band* with it, you have to choose: does p99 own the band *below* it (90→99% = 9%) or *above* it (99→100% = 1%)? Neither choice gives both tails as 1% simultaneously. The symmetric display only worked once we stopped pretending rows are points and made them explicitly ranges (min-p1, p99-max).

**Single-value labels?** Honestly, I don't think a good one exists — which is probably why you don't see one you like either. The candidates:

| approach | example labels | problem |
|---|---|---|
| upper boundary | p1, p10, ..., p99, max | back to the asymmetry confusion |
| lower boundary | min, p1, ..., p90, p99 | same problem, other end |
| midpoint percentile | p0.5, p5, p15, ..., p95, p99.5 | awkward, unfamiliar |
| band fraction | 1%, 9%, 10%, ..., 9%, 1% | duplicates (many 10%s) |
| descriptive | bottom-1%, low-9%, ..., top-1% | verbose, not standard |

The range label (min-p1, p1-p10, ..., p99-max) is the only one that's both unambiguous and symmetric. It's a little wider but it's honest — a band IS two boundaries, and pretending otherwise is what caused all the confusion.
