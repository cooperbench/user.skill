> AGENT

Strong direction. (site_id, start_tsc, end_tsc, userinfo) is the minimum information that's still useful — raw TSC + deferred math is the right call for hot-path overhead, and userinfo as an opaque slot keeps the probe layer ignorant of application semantics.

Three things worth pinning down before the API locks:

1. **Buffer policy.** Entries accumulate unboundedly; in production you probably want a pluggable strategy — ring buffer for "what just happened?" vs bounded+drain for full traces. This shapes the API more than anything else: does `record()` block, overwrite, or return `Err` when full?

2. **userinfo shape.** Generic `<U>` is fast and type-safe but pins one type per probe. A fixed-size POD slot (`[u8; N]`) keeps records uniform across actors with different needs and avoids heap allocation. `Box<dyn Any>` is dead in the hot path.

3. **TSC portability.** Invariant TSC is safe on modern x86 *if* the thread is pinned (mpsc-2t already does this); unpinned threads see small backward jumps across cores. Decide now whether the primitive abstracts the time source (x86 `rdtscp`, aarch64 `cntvct_el0`, `Instant` fallback) or starts x86-only.

For the actor msg-handler shape specifically, a scope-guard API (`let _g = tprobe.scope(SITE); ...`) fits exactly — one scope per invocation, can't forget the `end`. Worth making that primary and exposing manual `start`/`end` only as an escape hatch.

One fork worth thinking about for the id shape, given drain-to-outside:

**A — slot reservation.** `start()` writes start_tsc into a buffer slot with a sentinel end, returns `(slot, generation)`. `end(id)` writes end_tsc into the slot. Drain has to skip open slots → head-of-line blocking when one scope is slow; ring overwrite of an open slot needs the generation to detect.

**B — id carries start.** `TprobeRecId = (site_id, start_tsc)` (~16 bytes, no slot). `end(id, userinfo)` appends one complete record at close time. Buffer only ever holds complete records → drain is trivial, no head-of-line, no staleness. Cost: userinfo must be supplied at `end()` rather than written incrementally.

For drain-to-outside, B is meaningfully simpler. Worth a serious look before defaulting to A.

Also: should `end(id)` detect double-end? Extra branch in the hot path vs. letting a real bug class survive — decide now, not later.

Agreed auto-scope is preferred, but not always possible and the start/end are the basic elements. Remeber also these can be nested and not necessarily symetrical (i.e. start1 start2 end1 start3 end3 end2). Ideally, somehow, the site_id is auto generated at compile time and the user does nothing :)

> AGENT

Non-symmetric nesting strengthens option B: each `end(id, userinfo)` appends one complete record independently, so arbitrary interleaving just works. Option A's slot model gets awkward — a ring buffer with multiple open slots has to decide which to evict when overwriting, and without stack discipline you can't just walk a reservation stack.

For auto site_id at zero cost, a const hash of `file!()/line!()` via a thin macro:

```rust
macro_rules! tp_start {
    () => { $crate::start(const { $crate::site_hash(file!(), line!()) }) }
}
```

The id is a `u64` computed at compile time — no runtime registration, no `OnceLock` branch. For symbolic reports (so output says `"foo.rs:123"` not `0xabc...`), the same macro can also emit `(hash, file, line)` into an `inventory`/`linkme` distributed slice; runtime uses the hash, report phase walks the slice to resolve names. Both are free in the hot path.

Guard then falls out as sugar on top — `let _g = scope!();` expands to `Guard(start!())` with `Drop` calling `end` — same primitive underneath, no duplicate machinery.

One caveat: `file!()` is stable within a build but may vary between builds (CI vs. local checkout paths). Fine in-process; worth knowing if you ever want to compare ids across builds — in which case you'd normalize paths relative to `CARGO_MANIFEST_DIR` before hashing.

> AGENT

My guess: small but likely measurable — maybe 1–3 ns off the 11.12. `minstant::Instant::now()` compiles down to essentially `rdtsc` + TSC→ns mul-shift on x86, usually well-inlined. Storing raw TSC ticks skips the mul-shift (~1–2 cycles) and any wrapper call that didn't fully inline — but can't skip the two `rdtsc`s themselves, and those dominate the 11 ns. If you see >3 ns reduction, minstant has a non-inlined boundary worth a second look; <1 ns means the conversion was already effectively free and you've hit the hardware floor for two back-to-back `rdtsc`s.

One implementation wrinkle: `Probe`'s histogram is bounded at 60 s in nanoseconds. Raw TSC ticks at ~3.8 GHz push ~228 B ticks for 60 s — still u64-safe but beyond the histogram max. Either re-bound in ticks, or subtract-and-store the delta in ticks but convert the bound by the calibrated freq. The delta subtract is 1 cycle — same order as the mul-shift — so keep measuring.

> DEVELOPER

Is raw TSC u64 or u128?

> AGENT

u64. `core::arch::x86_64::_rdtsc()` returns `u64` (the instruction fills EDX:EAX → 64 bits). At 4 GHz it rolls over after ~146 years, so no practical overflow — no need for u128.

> DEVELOPER

is minstant::Instance::now() just the TSC?

> AGENT

On x86_64 with invariant TSC, yes — `minstant::Instant::now()` is essentially a thin wrapper around `rdtsc`. The returned `Instant` carries the raw u64 TSC value; the conversion to nanoseconds is deferred to `.elapsed()` / `.duration_since()`, where the mul-shift happens.

So the cost breakdown for the current pair is:
- `Instant::now()` → `rdtsc` (the big cost)
- `Instant::now()` → `rdtsc`
- `.elapsed()` → subtract + mul-shift to `Duration`
- `.as_nanos()` → cheap cast

Switching to raw TSC buys you the mul-shift (~1–3 cycles). Both `rdtsc`s stay.

Caveat: if invariant TSC isn't detected at startup, minstant falls back to `std::time::Instant`, which is `clock_gettime` via vDSO — much slower (~20–30 ns). Worth checking `minstant::is_tsc_available()` at process start if you care.

> AGENT

Good call on CPUID — two relevant leaves, depending on what you want:

1. **CPUID.80000007h:EDX[bit 8]** — "Invariant TSC" bit. Binary yes/no. The canonical check on both Intel and AMD; set iff the TSC runs at a constant rate regardless of P/C-state transitions. This is the strict validation for what we need.

2. **CPUID.15h** (Intel only) — "TSC and Core Crystal Clock Info". Returns the TSC frequency as a rational (`ECX * EBX / EAX`) when `EBX != 0`. Gives us the TSC frequency directly, which would let us skip the ~10 ms `ticks_per_ns()` calibration. AMD doesn't enumerate this way — it has its own family-specific MSRs.

Recommendation:
- Use `CPUID.80000007h:EDX[bit 8]` as the authoritative invariant-TSC check, alongside (or in place of) the `/proc/cpuinfo` `constant_tsc` string match. CPUID is portable across OSes and direct; `/proc/cpuinfo` is Linux-only and indirect.
- `CPUID.15h` is a nice-to-have for replacing our calibration with an exact frequency on Intel — but gated to Intel and needs `EBX != 0`, so we'd still need the calibration fallback for AMD/old Intel.

Which scope do you want?
- **(a)** Just swap `/proc/cpuinfo` for the CPUID invariant-TSC check.
- **(b)** (a) + use `CPUID.15h` when available to skip calibration.
- **(c)** Both checks (belt-and-suspenders: `/proc/cpuinfo` AND CPUID).

Current bench output looks right, by the way: tp-pc p99 ≈ 11,195 ns (default ns mode) vs 42,079 tk (`-t`), ratio ≈ 3.76 — consistent with a ~3.76 GHz boosted 3900X.

> DEVELOPER

I go for direct, but eventually I want this on ARM and RISC-V, how does that effect things?>

> AGENT

ARM and RISC-V are actually simpler than x86 here — both have architecturally invariant counters.

**AArch64.** The generic timer (`CNTVCT_EL0`) is monotonic and fixed-rate by ARMv8 spec — no "is it invariant?" check needed or possible. Frequency via `CNTFRQ_EL0` (direct register read, no calibration). Tick read: inline `mrs` asm.

**RISC-V.** The `time` CSR is spec-guaranteed monotonic and constant-rate. Frequency comes from platform info (device tree / SBI) or calibration — no CPUID equivalent. Read via `rdtime`.

Implication: the CPUID-based gate is x86-specific. On ARM/RISC-V the runtime validation is a no-op — the ISA itself is the guarantee.

Concrete proposal:

1. **Abstract the time source.** Probes call `tsc::read_ticks()`, `tsc::ticks_per_ns()`, `tsc::require_ok()`. Arch-specific impls live behind `#[cfg(target_arch = ...)]`.
2. **Rename `tsc` → arch-neutral** name (`clock`, `cycles`, or `ticks`). "TSC" is x86 jargon that'll be misleading on ARM/RISC-V.
3. **x86_64 path now:** CPUID 0x80000007:EDX[8] for invariance; optional 0x15 for frequency.
4. **Non-x86 arches:** `compile_error!("unimplemented for this target_arch")` until an impl lands. Explicit refusal, no silent success.

Also: `tp_pc.rs` currently calls `core::arch::x86_64::_rdtsc()` directly — that becomes `tsc::read_ticks()` too, so the bench stops being arch-specific.

This way, adding ARM/RISC-V later is "write one file" rather than "refactor the probes."

# iiac-perf

A general-purpose latency microbenchmark harness for Rust. Each
bench runs against a wall-clock time budget with auto-sized loop
counts, reports a percentile-band histogram in nanoseconds, and
subtracts calibrated apparatus overhead (timer-pair framing +
loop-per-iter) so the output reflects the workload, not the
measurement loop.

Highlights:

- Time-based runs (`-d SECONDS` per bench, `-D SECONDS` total)
  with auto-sized outer/inner loop counts.
- Band-based histogram (min→p1, p1→p10, …, p99→max) with count,
  mean, range, and an adjusted-mean column.
- Per-thread CPU pinning (`--pin`) with independent calibration
  pinning (`--no-pin-cal`), so the cal environment stays stable
  regardless of where bench threads land.
- Plug in new workloads by implementing the `Bench` trait and
  registering in `src/benches/`.

The first benches measure Inter-Intra Application Communication
— function calls, async calls, channels, serde — which is what
seeded the project name. The harness itself is workload-agnostic.

## Design (0.2.0)

Design a Rust app that can measure the cost of various (IIAC) techniques.
By IIAC I mean all communication techniques between and within
applications such as regular function calls vs async function calls vs
channels vs serde/deser of json or zero-copy messaging using io_uring and
potentially any other technique. It would include between threads or
processes or apps on the same computer or between apps on the same LAN or
between apps over a WAN.

Ideally I'd like to be able to see a histogram of the range of times of the
send and receive costs, not just the mean/average of 10^3 or 10^6 invocations.
So the cost of the work should or could be something near-zero such as just
echoing the input, but maybe there is value in doing some constant but
variable amount of work to verify it's in-consequential. One thing I think we
need to be aware of is that if we make the work too simple the compiler could
just keep things in registers which would not be representative of "real" work.

We should start simple, like comparing normal and async function calls and
later expand to other techniques.

## Usage

```
iiac-perf [BENCH...] [-d SECONDS] [-o OUTER] [-i INNER]
```

`BENCH` is one or more registered bench names, or `all` for every
registered bench. **With no arguments, `iiac-perf` prints the
available list and exits — that's the source of truth for which
benches the current build registers.**

Flags (also visible via `-h` / `--help`):
- `-d`, `--duration SECONDS` — target wall-clock seconds per bench
  (default `5.0`); the outer loop runs until this time is reached
  (inner auto-sizes). See chores `0.3.1-dev1` for the empirical
  study behind the default — longer (`-d 30`+) gives
  publication-grade stability. Mutually exclusive with `-D`.
- `-D`, `--total-duration SECONDS` — target total wall-clock seconds
  across all requested benches; budget is split equally per bench
  (e.g. `-D 30` with 6 benches → 5 s each). Mutually exclusive with
  `-d`.
- `-o`, `--outer N` — override outer loop count (forces count-based
  mode instead of time-based; inner still adapts).
- `-i`, `--inner N` — override inner loop count per histogram sample.
  `inner=1` measures single-call latency (each sample = one step).
  Higher inner measures back-to-back / burst rate (each sample = N
  steps averaged, hides per-call jitter and parking costs).
- `--pin CORES` — pin bench threads to logical CPUs. `CORES` is a
  comma-separated list with optional ranges: `0,1`, `0-5`, `0,3-5,7`.
  Treated as a **core pool** indexed positionally with wrap-around, so
  thread `i` gets `pool[i % pool.len()]`. Examples:
  - `--pin 0,1` pins a 2-thread bench to logical CPUs 0 and 1.
  - `--pin 0,0` co-locates two threads on the same CPU
    (oversubscription — measures contention).
