Why use c.repo.as_deref() and c.scop.as_ref() is that a clippy suggestion?

> AGENT

Driven by the function signature, not directly a clippy lint (though clippy would steer you there if you wrote it the verbose way).

`resolve_repos` takes `Option<&Path>` (not `Option<&PathBuf>`) and `Option<&Scope>` — the canonical Rust convention is that APIs accept the unsized-borrowed form (`&Path`, `&str`, `&[T]`) rather than the owned-borrowed form (`&PathBuf`, `&String`, `&Vec<T>`) so they're maximally general. To turn each field into what the signature wants:

- `c.repo: Option<PathBuf>` → `Option<&Path>`: needs `.as_deref()`. `PathBuf : Deref<Target = Path>`, so `Option::as_deref` exists for `Option<PathBuf>` and gives `Option<&Path>` in one call. Same idiom as `Option<String> → Option<&str>` via `.as_deref()`.
- `c.scope: Option<Scope>` → `Option<&Scope>`: just `.as_ref()`. `Scope` is a plain enum, no `Deref` impl — there's nothing to deref through, so `as_deref()` wouldn't even compile.

So the asymmetry isn't arbitrary — it tracks "does this type have a natural `Deref` target?": `PathBuf` does (`Path`), `Scope` doesn't. The clippy lint `option_as_ref_deref` would flag `c.repo.as_ref().map(|p| p.as_path())` and suggest `c.repo.as_deref()`, but writing it directly skips that step.

Alternative I considered and rejected: signature as `repo: Option<&PathBuf>` so both call sites use `.as_ref()`. Symmetric but worse — `&PathBuf` is the less-idiomatic borrowed form (parallel to taking `&Vec<T>` instead of `&[T]`).
