Agreed on 1 & 2. On the "new terminal" angle — actually the child *can* write to a terminal, just not through inherited pipes. Cleaner options:

**Option A: Reconnect via `/dev/tty`**

The parent opens `/dev/tty` (the user's current terminal) before detaching and passes that fd to the child as stdout/stderr. The terminal stays alive independently of the parent process — so even after the parent returns, the child's writes land in the same terminal the user is looking at. No new window, no GUI dependency.

```rust
let tty = std::fs::OpenOptions::new().read(true).write(true).open("/dev/tty").ok();
match tty {
    Some(f) => { cmd.stdout(Stdio::from(f.try_clone()?)).stderr(Stdio::from(f)); }
    None    => { cmd.stdout(Stdio::null()).stderr(Stdio::null()); } // piped (bot) case
}
```

When `/dev/tty` can't open (Claude Code's Bash tool, cron, CI), fallback to null + log file.
