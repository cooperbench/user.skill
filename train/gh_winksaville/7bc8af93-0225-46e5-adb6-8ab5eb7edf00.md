```rust
impl Execute for CleanCmd {
    fn execute(&self, project_root: &Path) -> Result<ExitCode> {
        let mut args: Vec<OsString> = Vec::new();
        if let Some(pkg) = &self.package {
            args.push("-p".into());
            args.push(pkg.into());
        }
        execute_cargo_subcommand("clean", &args, project_root)
    }
```

Here are my thoughts:

## What's different about Ts

`Ts` is the only command that's structurally different in two ways:

1. **CLI shape**: It's a nested subcommand group (`Ts { command: TsCommands }`) vs. a newtype (`Build(BuildCmd)`). Every other variant wraps a struct.

2. **project_root**: All 5 ts_cmd functions call `find_project_root()` internally. The Execute trait passes it in from main.rs. So there's a mismatch — either TsCmd ignores the parameter (like VersionCmd does with `_project_root`), or you thread it through all 5 functions.

3. **Logic in main.rs**: The assignment-parsing for `ts set` (lines 75-78) lives in main.rs, which is out of place — it's command-specific logic sitting in dispatch code.

## What it buys you

**Uniform main.rs** — the 36-line `Ts` arm collapses to `cmd.execute(&find_project_root()?)`, matching every other command. Dispatch becomes a mechanical list.

**Encapsulation** — the inner match and the assignment parsing move into `TsCmd::execute()`, closer to where they belong.

## What it doesn't buy you

**No abstraction gain** — there's no polymorphic dispatch (`Box<dyn Execute>`, iteration). It's a static enum match either way, so the uniformity is cosmetic.

**The project_root question is awkward** — you either:
- Pass it in and ignore it (wasteful call, `_project_root` smell)
- Pass it in and thread it through all 5 ts_cmd functions (the right thing, but touches every file in `ts_cmd/`)
- Pass it in and use it only partially (inconsistent)

## My take

Worth doing as a consistency cleanup, **but pair it with threading `project_root` through the ts_cmd functions**. All 5 already call `find_project_root()` on their first line — replacing that with a parameter is mechanical and eliminates redundant work. Without that second step, you're just moving code around while adding an unused parameter, which is arguably worse than the status quo.
