34	This is using jujustiu, jj + git and we'll see how it goes. Below is my

38	Every plan must start with a version bump. Choose the approach based on scope:

40	- **Single-step** (recommended for mechanical/focused changes): bump directly to
41	  `X.Y.Z`, implement in one commit. Simpler history.
42	- **Multi-step** (for exploratory/large changes): bump to `X.Y.Z-devN`, implement
43	  across multiple commits, final commit removes `-devN`.

50	3. Final commit removes `-devN`, updates todo/chores — this is the "done" marker
51

53	prior commits. This keeps the git history readable and makes it easy to see which
54	commits were exploratory vs final.

71	### Design decisions recorded here
72	
73	- Handler takes `&[u8]`; runtime owns the `PooledMsg`.
74	  - Runtime receives `Signal::User(PooledMsg)` off the channel.
75	  - Hands the handler `&*pooled` for the duration of `handle_message`.
76	  - Drops the `PooledMsg` after the handler returns; buffer goes back to the pool.
77	  - Pool traffic is one `get` + one `put` per dispatched message — exactly the cost goalzc exists to measure against goal2's unit-`Message` baseline.
78	  - Passing `PooledMsg` by value into the handler would let a clever actor reuse the incoming buffer (avoiding pool churn).
79	    - Rejected: `&[u8]` matches the shape of real zerocopy receivers and is the cleaner cross-validation target.
80	- Fixed-size buffers (`MAX_SIZE`) for the MVP.
81	  - Simpler pool (`Vec<Vec<u8>>`).
82	  - Matches a ping-pong workload where every message is the same size.
83	  - Size-classed sub-pools are future work; mentioned here explicitly so the extension isn't lost.
84	- Lazy pool allocation.
85	  - Pool starts empty; `get_msg` allocates a fresh `Vec<u8>` if the free list is empty.
86	  - Steady state settles to 2 buffers for ping-pong after the first couple of dispatches.
87	  - Pre-populating a fixed capacity is a micro-optimization that distorts first-dispatch latency (already dropped by warmup); deferred.
88	- `--size N` CLI flag, not a compile-time const.
89	  - goalzc is a benchmark; size sensitivity is exactly what a reader wants to sweep.

102	## Pool + PooledMsg (0.5.0-1)
103	
104	Implements the fixed-capacity buffer pool that `RuntimeZC`
105	will use to ship zerocopy messages between actors. The
106	shipped shape deviates from the `0.5.0-0` plan in several
107	ways — all decided during review of successive design cuts:
108	
109	- Constructor takes explicit byte / count: `Pool::new(msg_size: u32, msg_count: u32)`. Pre-allocates `msg_count` buffers of `msg_size` bytes each; no lazy growth, no global `MAX_SIZE` const.
110	- `get_msg` returns `Result<PooledMsg<S>, PoolError>` rather than panicking. Two variants: `SizeTooLarge { requested, max }` and `NoMsgs`.
111	- Buffers are `Box<[u8]>` (fixed-size allocation) plus a separate `len: usize` on `PooledMsg` for the logical message length, instead of `Vec<u8>`'s redundant `cap` field.
112	- The free list lives behind a `BufRefStore` trait so different concurrency strategies (Mutex, lock-free queue, ring buffer, hand-rolled atomics, …) can be benchmarked against each other. The default is `MutexLifo`.
113	- `Pool` and `PooledMsg` are generic over `S: BufRefStore`, with `MutexLifo` as the default type — ordinary call sites write `Pool::new(64, 128)` unchanged.
114	- A `BufRef` type alias documents the `Option<Box<[u8]>>` niche-optimization idiom in one place.
115

153	### Design decisions recorded here
154	
155	- `BufRefStore` trait + generic `Pool<S>` rather than a hardcoded backend.
156	  - Primary motivation: the user wants to swap concurrency strategies and benchmark them — Mutex baseline today, lock-free `ArrayQueue`, ring buffers, hand-rolled atomics later.
157	  - Generic-with-default (`S: BufRefStore = MutexLifo`) keeps the common call site unchanged (`Pool::new(64, 128)`) while letting benchmarks opt into other backends with `Pool::<X>::new(64, 128)`.
158	  - Trait surface stays minimal: `from_buffers` / `get` / `ret` / `len` / `size`. No "ordering" or "is_lockfree" methods; ordering is implementation-defined and `Pool` treats buffers as fungible.
159	  - Dyn-dispatch via `Box<dyn BufRefStore>` was considered and rejected for benchmark fidelity — a `dyn` indirection in the hot path would contaminate the very thing we're trying to compare.
160	- `BufRef = Option<Box<[u8]>>` alias.
161	  - Documents the "safe null/non-null pointer" idiom in one place rather than re-explaining at each use site.
162	  - Used in `PooledMsg.buf` (nullable transiently during `Drop::drop`) and as `BufRefStore::get`'s return (signaling empty store).
163	- Fixed-capacity pre-allocation rather than lazy growth.
164	  - Supersedes the `0.5.0-0` plan's "starts empty, grows on demand" design.
165	  - Makes `NoMsgs` a real, testable condition — back-pressure is exposed instead of hidden behind silent allocation.
166	  - Steady-state behavior for ping-pong is unchanged (two buffers cycling).
167	- `Result<PooledMsg, PoolError>` rather than panic on misuse.
168	  - Supersedes the `0.5.0-0` plan's panic on `size > MAX_SIZE`.
169	  - `NoMsgs` is a runtime condition; a benchmark hitting exhaustion should not crash, it should report saturation.
170	  - `SizeTooLarge` follows the same shape for one error path.
171	- `Box<[u8]>` + separate `len` rather than `Vec<u8>`.
172	  - `Vec`'s `cap` field is dead weight when capacity is fixed at `msg_size`; `Box<[u8]>` is `(ptr, len)` only.
173	  - `Vec` also implies "growable", which is misleading here.
174	  - `len` lives on `PooledMsg` instead of in the store, so the store treats buffers as identical fixed-size allocations.
175	- `Option<Box<[u8]>>` inside `PooledMsg` so `Drop` can move the inner `Box` out.
176	  - Niche-optimized to a single pointer at runtime (no discriminant tag).
177	  - `None` only observed transiently inside `Drop::drop`; `Deref` / `DerefMut` can't see it.
178	  - `unsafe` alternatives (`ManuallyDrop` + a destructor) would shave the `unwrap`s but add unsafety; not worth it.
179	- `BufRefStore::size()` returns the constant store capacity.
180	  - Distinct from `len()` (current count), which fluctuates as buffers go in flight.
181	  - Cached at `from_buffers` time so `MutexLifo::size()` is O(1) lock-free.
182	  - Test `pool_size_is_constant_and_matches_store` validates the invariant.
183	  - Future-proofs the multi-size sub-pool extension: `Pool::size()` already sums "across sub-stores" (one for now).
184	- `msg_size` / `msg_count` typed as `u32`.
185	  - Matches the user's requested shape: explicit byte-range and count limits at the type level.
186	  - Internally converted to `usize` for `Vec` / slice APIs; widening on every platform actor-x1 targets.
187	  - `get_msg(size: usize)` stays `usize` for clean interop with slice/`Vec` lengths; if `size > u32::MAX` the `SizeTooLarge` guard catches it.
188	- `is_empty` as a default-impl trait method.
189	  - Required by clippy's `len_without_is_empty` lint when a type / trait exposes `len()`.
190	  - Default body `len() == 0` is correct for any conforming impl; concrete impls can override if they have a faster path.
191	- No zeroing on drop.
192	  - Slots `0..new_size` of a reused buffer carry residual bytes from the previous occupant.
193	  - For ping-pong workloads the next consumer either overwrites or ignores those bytes — benign.
194	  - Real applications crossing trust domains would need an explicit `zeroize`-on-drop step; documented in the module-level comment.
195	- No `Default for Pool`.
196	  - There's no sensible default for `msg_size` / `msg_count`; every caller has to choose.

198	## ActorManager + RuntimeZC: split catalog from transport (0.5.0-2)
199	
200	Adds the multi-threaded zerocopy actor runtime, split across two
201	modules with disjoint responsibilities:
202	
203	- `actor_manager.rs` — actor model surface. `ActorZC` / `ContextZC` traits + `ActorManager<S>` catalog. Defines *what* an actor is and how the catalog addresses them.
204	- `runtime_zc.rs` — message-moving infrastructure. `RuntimeZC<S>` with `run` and `run_no_probe` entry points. One consumer of the actor model surface above; future transports (M:N scheduler, alternative channels) would be peers.
205	
206	The shipped shape deviates from the `0.5.0-0` plan in four ways,
207	all decided during review:
208	
209	- Two types instead of one — `ActorManager<S>` (catalog) + `RuntimeZC<S>` (transport). The runtime moves messages; the manager holds instances and assigns ids; they only touch through `take_actors` + `probe_name_prefix` when `run` is called.
210	- Two files instead of one — actor model surface lives in `actor_manager.rs`, transport in `runtime_zc.rs`. Reinforces the type-level split at the file level so future growth on either side (control-plane manager-actors; alternative transports) lands cleanly.
211	- Direct instance registration rather than factory closures. `ActorZC: Send` is on the trait, so the factory pattern's "don't require Send" benefit is moot; `mgr.add(PingPong { peer: 1 })` reads cleaner than `mgr.add_actor(|| PingPong { peer: 1 })`.
212	- Initial messages live in the app, not the runtime. `run(&mut mgr, initial_messages, …)` takes them as a parameter; neither manager nor runtime stores them. The benchmark / app is what knows "ping-pong needs one seed message".

228	### Design decisions recorded here
229	
230	- Generic `ActorZC<S>` / `ContextZC<S>` over the store backend.
231	  - Pool is generic over `S` since `0.5.0-1`; static dispatch all the way down preserves benchmark fidelity.
232	  - Type-erasure in `ContextZC::send` would add a vtable hop per send, contaminating the measurement.
233	  - Default `S = MutexLifo` keeps ergonomic call sites unannotated.
234	- Handler takes `msg: &[u8]`; runtime owns the inbound `PooledMsg<S>`.
235	  - The runtime's `actor_loop` calls `actor.handle_message(&mut ctx, &msg)` then `drop(msg)` — buffer returns to the pool one channel hop later, predictably and once per dispatch.
236	- Two run methods rather than one with a `bool probe_enabled` parameter.
237	  - A runtime branch on every dispatch would itself be a cost goalzc might want to measure or eliminate.
238	  - Function-pointer dispatch (`ActorLoopFn`) monomorphizes cleanly per `R`.
239	- Caller-supplied `Pool<S>`.
240	  - Lets the app build initial messages from the same pool the runtime uses.
241	  - Lets tests inspect `free_len` after shutdown to verify drain.
242	  - Lets `goalzc-crit` keep the pool across `iter_custom` calls (long-lived) while the runtime is rebuilt each call.
243	- `Send` bound on `ActorZC` (not `ContextZC`).
244	  - Actors get moved into spawned threads; must be `Send`.
245	  - `ContextZC` lives only inside one thread (constructed per-recv inside `actor_loop`); no `Send` needed.
246	- `let _ = sender.send(...)` in `MultiCtxZC::send` — closed channel drops the message silently.
247	  - The `Err(SendError(SignalZC::User(msg)))` case drops the `SignalZC`, which drops the inner `PooledMsg`, which returns the buffer to the pool — no leak.
248	- Drain assertion as part of the test contract.
249	  - `pool_is_full_after_shutdown` codifies "every PooledMsg that was ever in flight returns to the pool by the time `run` joins".
250	  - Non-obvious because it depends on `Drop for PooledMsg`, mpsc receivers dropping queued messages on close, and main-thread senders being dropped before join.
251	  - Codifying it now means a future change that breaks one of those steps gets caught immediately.
252	
253	### Future direction (noted, not built today)
254	
255	- `ActorManager` itself becomes an `ActorZC` for control-plane work — a sibling actor on the same Runtime that handles "register a new actor at runtime", "lookup by name", "drain probes", etc.
256	- Multiple manager-actors for separate concerns (GUI, CLI, log drain, probe collect) all running on one Runtime.

278	    mut actor: Box<dyn ActorZC<S> + Send>,

302	            }
