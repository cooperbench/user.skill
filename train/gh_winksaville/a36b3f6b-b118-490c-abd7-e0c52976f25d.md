**Defining framing (and overhead) so we're precise**

These are the two things calibration actually produces:

- **Framing** (`framing_ticks`, per-scope): the cost of one `rdtsc` pair — the `start_tsc = rdtsc()` + `end_tsc = rdtsc()` bracket — plus whatever hardware bias that pair produces. Both are in the `Overhead` struct. Today we subtract only framing.

**"Subtract all overhead" — what's possible**

Three categories, by whether we can separately measure them:

1. **Framing** — measurable, unambiguous apparatus cost. Subtract. (Already doing this.)
2. **Loop-per-iter** — measurable, but it's the cost of the *calibration's* empty loop. The real dispatch loop has its own per-iter scaffolding (loop branch, counter increment) that's similar to `black_box(1)`, so subtracting this is a close-enough proxy — biased slightly low because the real loop doesn't contain the `black_box` itself. One more thing, add a todo suggesting the possibility of using Linkme or Inventory for creating a "benchmark" app using tprobe. This would allow multiple benchmarks without changes to main(), IIUC.  This also might be useful for creating "actor" applications. thoughts

> AGENT

Added. Thoughts on the idea:

**Strong fit for a benchmark harness.** Both `linkme` (distributed slice via linker) and `inventory` (ctor-based) let a file drop in a `bench!` macro invocation and have the runner pick it up with zero `main` edits. That's the same ergonomic as criterion-rs. With `tprobe` providing the measurement primitive, a small runner loops over the registered entries, sets up warmup/calibration/pin config once, and reports each benchmark's band table. Very clean.

**Partial fit for actors.** Registration works for *discovery* — "enumerate every `Actor` type the binary knows about" is exactly what distributed slices give you — but actor construction still needs runtime config (id, name, channel endpoints, thread placement). So linkme/inventory replaces the "hand-written registry lookup table" but doesn't replace the wiring in `main` / runtime setup. Worth using if we find ourselves editing a registry table every time we add an actor; not a silver bullet for the whole init problem.

**Tradeoffs to validate before committing hard:**

- `linkme` relies on linker section magic. Works on x86_64 Linux out of the box but can break under aggressive strip/LTO or unusual link modes. Worth a smoke test across `--release` + whatever flags we normally run.
- `inventory` uses static constructors (via `ctor`). Broader platform support, pays a small init-time cost, and has had historical issues when the whole-binary reachability analysis elides unused statics — a registration in a test-only file can silently not register. Usually fine in a binary crate, just something to verify.
- Both lose the "you can see every registered item by grepping `main.rs`" property, which some people dislike on maintainability grounds. Matter of taste.

**My take**: do it for the benchmark harness first (clear win), evaluate from there whether the actor side is worth it (probably a smaller win).

Nothing for me to do with those thoughts beyond the todo entry — I didn't commit to the approach, just flagged it for later.

Same shape. The per-scope structure — rdtsc, inner loop, rdtsc — matches exactly. Two deliberate differences in what's around it:

- **Inner body**: calibration runs `black_box(1u64)` (apparatus only); runtime runs `handle_message` (work). That's the whole point — calibration measures what the apparatus adds on top of an almost-empty inner.
- **Outer reduction**: calibration takes the `min` across outer iterations to pin down the floor; runtime records every scope because it wants the full distribution. If the inner-loop body diverged structurally from the runtime's — say, calibration missed a loop counter increment that the runtime pays — the fit would be biased. If you'd like I can add a note in `overhead-model.md` spelling out this structural correspondence; it's currently implicit.

**The `let Self { … } = self;` destructuring in `run_for`**

It's Rust's idiom for **split-borrow** (a.k.a. disjoint-borrow). It lets the borrow checker see three independent `&mut` bindings (`actors`, `queue`, `probe`) instead of a single `&mut self`.

The inner loop needs to do three things simultaneously:
1. `&mut actors[dst]` — pick the actor.
2. `&mut queue` — pass into `SingleCtx` so `handle_message` can enqueue new messages.
3. `probe.start/end_batch` — straddle the batch with rdtsc calls.

With plain `self.actors[dst]` + `self.queue` + `self.probe`, borrow-chk can't always prove those paths are disjoint when they're used together across the inner loop (the compiler's partial-borrow inference is per-expression, not across nested scopes and closures). The destructure flattens `self` into three independent bindings with no common aliasing; each can be borrowed mutably at will.

Concretely, without it this line would fail:

```rust
let actor = &mut self.actors[dst as usize];
let mut ctx = SingleCtx { queue: &mut self.queue };  // second &mut self — error
```

With the destructure, `actors` and `queue` are already separate roots:

```rust
let actor = &mut actors[dst as usize];
let mut ctx = SingleCtx { queue };  // reborrow of the `queue` binding
```

No `self` involved after the destructure, so nothing for the borrow checker to reject.

The runtime.rs struct docstring at line 64 (`"field-split-borrows actors and queue"`) already names the pattern, but doesn't explain it. I can add an inline comment on the `let Self { … } = self;` line noting the reason, if that would help readers.

Same display-precision story as the "0 ns" on means, with a minor twist from how range is computed.

**Range formula:** `range = last - first + 1`. That's an *inclusive count of integer tick values* spanned, not a true span. When all the band's samples fall on a single tick (tight distribution — hdrhistogram's 0.1%-relative buckets collapse close values into one), `first == last` and `range = 1 tk`. In ticks mode you see that 1; in ns mode, 1 tk / ~3.78 tk/ns ≈ 0.26 ns, which zero-decimal formatting shows as `0 ns`.

So `range = 0 ns` is communicating "all samples in this band sat on the same tick bucket" — which is exactly the shape the renderer notes elsewhere (`A stdev min-p99 near 0 alongside a couple of dense bands is a strong signal that the underlying distribution is spike-heavy`). The ticks-mode view preserves the signal; the ns-mode view rounds it away.

The `+1` is slightly confusing on its own — e.g. a band holding only the value 5 shows `range = 1` when zero-width would arguably read more naturally. But changing the semantics is its own small decision (different meaning, changes nothing about the stored data) and is out of scope for 0.3.0-3.

> AGENT

That's a real memory bug, and it's the biggest limitation in the current `TProbe` design. Let me quantify.

**What happened.** `TProbe` stores a `Record { site_id, start_tsc, end_tsc, batch }` — 32 bytes — on every `end_batch` call, into an unbounded `Vec<Record>`. The records aren't drained until `report()` runs at the end of the measurement. At `goal1 60 --inner 10` with ~111M msg/s × 60s / 10 = **669M records = ~21 GB**.

Your run matches: the first 60-ish seconds fit until the process hit RAM limits, then swap kicked in and dragged throughput down. The report you captured was actually produced — which means the drain (670M hdrhistogram inserts) did eventually complete, just painfully.

**Design rationale (and its limit).** The `tprobe.rs` docstring says explicitly: *"No delta math, histogram ingestion, or tick→ns conversion happens on the hot path."* That's a deliberate trade — keep `end_batch` to just `rdtsc + Vec::push` so the probe doesn't distort what it measures. It works great for short windows (≤5 s at typical rates) and falls over for long ones. iiac-perf upstream has the same shape.

**Options.** None are in scope for 0.3.0-3 — this is its own thing:

(a) **Hard cap + warning.** Bound `records` at e.g. 16M (~512 MB), stop recording past the cap, print "measurement truncated: N scopes dropped". Simplest. Preserves hot-path cost exactly. Only gets partial data on long runs.

(b) **Periodic drain at threshold.** When `records.len()` hits N, drain inline, clear, keep going. Memory bounded. Introduces measurement gaps during drain (a few ms every few hundred ms at the scale that matters) — visible in the `p99-max` tail.

(c) **Inline drain, no buffer.** `end_batch` computes `per_event = (delta + batch/2)/batch` and calls `hist.record` directly. Memory fully bounded; measurement is continuous. Adds ~15–20 ns to the hot path. Real cost — at the probe's own ~5 ns reported-mean range, this doubles what we're measuring, which is bad for accuracy.

(d) **Skinnier record.** Store just a `u64` per-event tick value (8 bytes). 4× memory reduction. Still unbounded. 60s at inner=10 becomes 5.4 GB instead of 21 GB — closer but not fixed.

(e) **Just document the measurement-window limit in the README.** Note that window × rate / inner should stay under some memory budget. Cheapest; no code change. Users avoid the trap but the trap remains.

My lean: **(a) + a todo for (b) or (c) later**. Hard cap with a clear truncation message stops the OOM right now and costs nothing on the hot path; the right long-term fix (b/c/hybrid) can be evaluated once we've instrumented the drain cost empirically.

Worth adding to todo and getting through the 0.3.0 ladder first, or fit into 0.3.0-3 before push? Also — do you want to proceed with pushing 0.3.0-3 as-is (the memory issue is pre-existing, not a regression), then tackle this?

**20 s, unpinned**
- Hot bands cluster at ~2,550–2,700 tk.
- Mean 2,910 / 2,922 tk. Mean min-p99 2,860 / 2,845 tk.
- `p99-max` goes up to **4.15 M ticks** (≈1 ms) on actor 0.

**1 s, unpinned**
- Hot bands cluster at ~2,430 tk.
- Mean 2,201 / 2,210 tk. Mean min-p99 2,144 / 2,149 tk.
- `p99-max` maxes at 340 k ticks (≈90 µs).

Two things are moving:

1. **Shift in the hot bucket.** The ~250-tick (~65 ns) shift between the 1 s and 20 s hot clusters is dominated by OS thread migration on your unpinned 3900X. The 3900X splits 12 cores across 4 CCX complexes of 3 cores each; whenever the scheduler bounces either actor thread to a different CCX, every ping-pong that follows has to pay a cross-complex cache-coherence round-trip (~500–1500 ns extra). A 1 s run might keep both threads on one CCX by luck; a 20 s run gives the scheduler many chances to move them.

2. **Tail weight.** Even `mean min-p99` is dragged up a bit by near-tail events (p90-p99 values 5,095–5,815 tk, way above the hot cluster). 20 s accumulates a lot more of those than 1 s.

The README already documents this specifically (*"--pin tightens stdev but can raise the mean"*). Ask your goal2 runs to `--pin 0,1` (same-CCX pair on the 3900X) and you should see:
- Reproducible hot bucket across 1 s / 20 s runs.
- `mean min-p99 stdev` drops sharply.
- Mean possibly slightly higher than unpinned-luck (because you've removed best-case intra-CCX placement variance), but *predictably* so.

How would we determine the "precision" we are able to measure

> AGENT

Precision of a tprobe measurement is the product of several floor sources. Worth separating the sources from the measurement technique.

**The floors (smallest things we can discriminate):**

- **Hardware tick resolution.** 1 TSC tick ≈ 0.27 ns on a 3.7 GHz box. Nothing below this exists.
- **Apparatus framing noise.** Calibration fits `framing_ticks` with some noise — we've observed 21 → 29 tick swings run-to-run (~2 ns on this box). That noise directly dirties `adj mean`.
- **OoO rdtsc coalescing.** Back-to-back `rdtsc` pairs with nothing serializing between them can measure 0–1 ticks even when real work happened; the p1-p10 OoO cluster at inner=1 is this.
- **hdrhistogram bucket width.** 3 sig figs = 0.1 % relative. At 20 tk, bucket width ≈ 1 tk; at 2,000 tk, ≈ 2 tk. Below ~1,000 tk, quantization is essentially exact.
- **Unmeasurable systemic noise.** Cache misses, context switches, interrupts. Shows up in `p99-max` tail; handled by preferring `mean min-p99` for A/B work.

**The empirical technique (and what we're missing today):**

For a given configuration the right measurement is the *run-to-run* stdev of `mean min-p99`. Something like:

```
for _ in 1..=30; do goal1 2 -i 1000 -p 0 >> runs.txt; done
# parse out mean min-p99, compute sample stdev
```

The single-run `stdev min-p99` tells us within-run noise; the cross-run stdev tells us the measurement's repeatability. Those aren't the same number — pinning typically tightens within-run noise more than cross-run noise. A/B-significant difference is roughly `2 × cross_run_stdev`.

On your 3900X I'd expect:
- goal1 `-i 1000`: cross-run stdev ~0.2–0.5 ns on mean min-p99 (≈10% of the signal).
- goal1 `-i 1`: cross-run stdev ~1–2 ns (adj mean picks up the calibration-framing swing).
- goal2 pinned same-CCX: cross-run stdev ~30–100 tk on mean min-p99 (≈2–5%).

**What we could build (if worth it):**

A `--repeat N` flag that runs the full measurement N times internally, reports per-run summary lines plus a cross-run stdev/mean on `mean min-p99` (and `adj mean min-p99`). Single command, right number for A/B. Small feature — ~30–50 lines across the binaries, no probe-API change needed since it just loops the existing `run(warmup, measurement)` sequence.
