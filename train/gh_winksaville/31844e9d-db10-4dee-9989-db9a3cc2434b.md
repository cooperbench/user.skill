1. **Reads the spec file path** from `TSPEC_SPEC_FILE` environment variable (set by tspec before invoking cargo)

   ```rust
   println!("cargo:rerun-if-changed={spec_file}");
   ```

```rust

    Err(_) => return, // Not building via tspec, nothing to do
```

Now I have the full picture. Here's the core tension:

## The Problem

`tspec compare` runs `plain_cargo_build_release()` (`cargo_build.rs:149-180`) which is deliberately a bare `cargo build --release` — no spec, no `TSPEC_SPEC_FILE` env var. Your rlibc-x apps define their own `_start` and need linker args like `-nostartfiles` to avoid the duplicate symbol.

## Why `tspec_build::emit_linker_flags()` alone won't fix it

Looking at `tspec-build/src/lib.rs:31-33`:

```rust
let spec_file = match std::env::var("TSPEC_SPEC_FILE") {
    Ok(path) => path,
    Err(_) => return, // Not building via tspec, nothing to do
};
```

It's a **no-op** when `TSPEC_SPEC_FILE` isn't set. And the baseline build doesn't set it. So adding a `build.rs` that only calls `tspec_build::emit_linker_flags()` would make `tspec build` work (it already does), but `cargo build --release` (the compare baseline) would still fail.

## The real issue

These apps **fundamentally cannot link** without `-nostartfiles` (or whatever the critical arg is). That's not build tuning — it's a structural requirement. There are a few paths forward:

**Option A — Split mandatory vs. tuning args.** The `build.rs` unconditionally emits the must-have args, and `tspec_build` adds the optimization/tuning args from the spec:

**Option C — Both.** Option B as a resilience improvement in tspec, and Option A for repos like rlibc-x where a baseline comparison is actually useful.

My recommendation is **Option A for rlibc-x** (the mandatory linker args belong in `build.rs` since they're required for the package to exist, not optional tuning) and **Option B as a general tspec improvement** so compare degrades gracefully for projects where no baseline is possible.
