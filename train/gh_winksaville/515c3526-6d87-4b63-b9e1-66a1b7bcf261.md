Not quite — Cargo's default is conservative. A few notes:

**How Cargo interprets the version string:**
- `"0.39.0"` isn't a pin; it's sugar for `^0.39.0` (caret req). For `0.x.y` semver, each minor bump is treated as breaking, so `^0.39.0` = `>=0.39.0, <0.40.0`. That's why 0.40 is excluded.
- `"0.39"` gives the identical constraint — both are caret-equivalent for 0.x.
- `"0.40"` would allow 0.40.x but still not 0.41.
- Once a crate hits 1.0, `"1"` auto-tracks 1.x.y (minor bumps are non-breaking by semver), which is where "auto-track" actually kicks in.

**Why you don't get automatic drift even within the allowed range:** `Cargo.lock` is checked in (correct for a binary) and pins exact versions. `cargo build` reads the lockfile; `cargo update` is what refreshes it.

**Idiomatic for a binary like vc-x1:**
1. Keep `Cargo.lock` committed (already done).
2. Specify the minimum compatible version in `Cargo.toml` — style in this project is mostly `"0.4"` / `"4.6"` (major.minor). `jj-lib = "0.39.0"` is the outlier with an explicit patch — worth trimming to `"0.39"` for consistency.
3. Bump the `Cargo.toml` string and run `cargo update -p <crate>` when you're ready for a new minor — don't rely on implicit drift.

**To pick up jj-lib 0.40.0** right now: change `jj-lib = "0.39.0"` → `jj-lib = "0.40"`, then `cargo update -p jj-lib`, then test. `cargo install` is one of the few commands that proactively compares installed/resolving versions against the registry and flags a mismatch. `cargo build`, `cargo check`, `cargo test` do not — they use what `Cargo.lock` says and don't hit the registry unless something's missing. So yes, you have to look.

**On-demand ways to check:**
- `cargo update --dry-run` — shows what would update *within* your semver constraints (e.g. 0.4.0 → 0.4.7), without touching the lockfile.
- `cargo update --dry-run --breaking` — newer cargo; shows updates that would *require* editing `Cargo.toml` (e.g. 0.39 → 0.40, the jj-lib case).
- `cargo outdated` — third-party subcommand (`cargo install cargo-outdated`). Classic tool; splits output into "compatible" vs "latest" columns.
- `cargo audit` — security-focused (`cargo install cargo-audit`); flags deps with known CVEs via the rustsec advisory DB.

Common practice is to run one of these manually on a cadence (weekly, monthly) or wire them into CI — there's no passive nag from cargo proper during normal builds.
