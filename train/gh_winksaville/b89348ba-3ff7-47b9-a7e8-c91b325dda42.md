1	# Versioning
2	
3	How this project versions its commits and the running
4	artifact. The scheme — the cycle step-numbering and the
5	unique-per-commit aim — is generic and shared across projects:
6	this file is copied **verbatim**, with
7	[Recording the version-of-record](#recording-the-version-of-record)
8	covering each medium by conditional rather than per-project
9	edits.
10	
11	## Terms
12	
13	Three names, used as defined here across
14	[AGENTS.md](../AGENTS.md),
15	[cycle-protocol.md](cycle-protocol.md), and the notes files:
16	
17	- **version** — the per-commit version (e.g. `0.3.0-5.3.0`),
18	  written with `-` in prose, ladders, chores, todo, and commit
19	  talk; its suffix encodes the cycle phase (see
20	  [Step numbering](#step-numbering)).
21	- **version-of-record** — the authoritative stored copy of the
22	  version, in the project's manifest (see
23	  [Recording the version-of-record](#recording-the-version-of-record));
24	  a built or running artifact derives from it.
25	- **versioning** — the topic: this scheme as a whole.
26	
27	## Recording the version-of-record
28	
29	Where the version-of-record lives, how it's stored and
30	surfaced, and how often it changes — pick the case that fits
31	your medium:
32	
33	- **Manifest** — where the version-of-record is stored:
34	  - if Rust, `Cargo.toml` `[package].version`
35	  - if Python, `pyproject.toml` `[project].version` (or the
36	    committed config it's sourced from)
37	  - otherwise wherever the medium records it (a generic
38	    `version.toml`, a book's frontmatter, …) — add the case as
39	    needed
40	- **Notation** — how the `-` form is stored:
41	  - if the format allows `-` (TOML `version.toml`, `Cargo.toml`),
42	    store it verbatim
43	  - if it bars `-` (PEP 440's local segment, e.g. a Python
44	    project), remap to `+` — `0.3.0-5.3.0` → `0.3.0+5.3.0`: same
45	    version, just the stored spelling
46	- **Reporter** — how a built artifact surfaces the
47	  version-of-record:
48	  - if a CLI app, `<cli-app> -V`
49	  - if a TUI/GUI, add to Help/About or display on the title
50	- **Cadence** — how often to bump: see
51	  [Unique per commit](#unique-per-commit-preference-not-requirement);
52	  this project follows the per-commit preference.
53	
54	## Unique per commit (preference, not requirement)
55	
56	Our general notion is that the version-of-record should change
57	on **every commit**, so a built or running artifact identifies
58	the exact commit it came from.
59	
60	- This is a preference, **not** a hard requirement. A project
61	  following the cycle protocol may bump less often — once per
62	  cycle, only at release, and so on. Record the choice in
63	  [Recording the version-of-record](#recording-the-version-of-record)
64	  if it differs.
65	- It is achievable because the cycle's versions (below) are
66	  **pre-assignable**, unlike the git SHA, which a commit cannot
67	  contain (see the cycle protocol's
68	  [Commits backfill](cycle-protocol.md#commits-backfill)).
69	
70	## Step numbering
71	
72	The cycle (Preparation -> Work -> Close-out; see
73	[cycle-protocol.md](cycle-protocol.md)) encodes each commit's
74	phase in the version suffix — the **final identifier `0` marks
75	a Preparation**:
76	
77	- `X.Y.Z-0` — Preparation
78	- `X.Y.Z-1`, `X.Y.Z-2`, … — Work commits
79	- `X.Y.Z` — Close-out (bare version, no suffix)
80	
81	**Preparation is optional.** A lightweight cycle — no ladder,
82	no setup commit — skips `-0` and starts at `-1` (its first
83	Work commit). The same holds at every level: a sub-cycle
84	needing no Preparation omits its `.0` (see Nesting). One that
85	grows a Preparation later adds the `0` step without
86	renumbering siblings.
87	
88	Disambiguation:
89	
90	- `-10` — Work commit #10 (final identifier `10`), not a
91	  Preparation.
92	- `-1.0` — Preparation of the `-1` sub-cycle (final
93	  identifier `0`).
94	
95	**Nesting.** Sub-cycles append another level, recursively:
96	
97	- `X.Y.Z-3.0` — Preparation of the `-3` sub-cycle
98	- `X.Y.Z-3.1`, `X.Y.Z-3.2` — its Work
99	- `X.Y.Z-3` — its Close-out
100	- `X.Y.Z-3.1.0` — Preparation of the `-3.1` sub-sub-cycle
101	
102	Bump the version-of-record at the start of each phase, so the
103	active phase is recorded — and, per the preference above,
104	every commit carries a distinct version.
105

157	## Why `jj log` shows fewer commits than `gitk`
158	
159	If you're coming from git, jj's log output can be surprising compared to
160	tools like `gitk --all`.
161	
162	jj tracks *changes* (identified by change IDs), not individual git commits.
163	When you rewrite a change (`jj describe`, `jj rebase`, `jj squash`, etc.),
164	jj creates a new git commit and keeps the old one under `refs/jj/keep/*` as
165	undo history. `gitk --all` sees all of these obsolete commits; `jj log` only
166	shows the current version of each change.
167	
168	## Useful commands
169	
170	| Command | Description |
171	|---------|-------------|
172	| `jj log` | Show recent visible commits (default revset) |
173	| `jj log -r ::@` | Show **all** ancestors of the working copy |
174	| `jj log -r 'all()'` | Show all non-hidden commits (needed if you have multiple heads/branches) |
175	| `jj st` | Show the status of the Working and Parent commits |
176	| `jj st -r <chid>` | Status of the commit, `<chid>` such as `@`, `@-`, `xyz` |
177	| `jj show` | Show the Working commit (`-r @`) |
178	| `jj show -r <chid>` | Show the commit, `<chid>` such as `@`, `@-`, `xyz` |
179	| `jj evolog -r <chid>` | Show the evolution history of a single change |
180	| `jj op log` | Show operation history (each rewrite operation) |
181	
182	
183	In a single-branch workflow, `jj log -r ::@` and `jj log -r 'all()'` give
184	the same result. Use `all()` when you have multiple branches or heads.
185	
186	## Revsets
187	
188	Revsets (sets of revisions) are how jj addresses commits. A
189	revision is identified by `@`, a chid, or a cid, and revsets are
190	built from those identifiers plus the operators `-`, `+`, `..`,
191	and `::`. There is a complete language available — see
192	`jj help -k revsets`. The [`substep-test.sh`](substep-test.sh)
193	script scaffolds the example repo used below.
194	
195	Summary:
196	
197	- A revision (rev) is used for addressing/referring to commits.
198	- jj supports a change_id (chid) and commit_id (cid).
199	  - The chid is permanent and doesn't change.
200	  - The cid is the SHA of the current commit and changes with any
201	    change to it or its ancestors.
202	- A revset is a set of revisions.
203	- In many jj commands revsets can address multiple commits.
204	- There is one root commit; chid=zzz sha=0 owner=root.
205	- The root commit never has content nor description.
206	- There can be multiple independent lineages of commits off root():
207	  - to create:
208	    - `jj new 'root()'`
209	    - `git switch --orphan <name>`
210	  - to see these:
211	    - `jj log -r 'roots(~root())'`
212	    - `git log --all --max-parents=0 --oneline`
213	
214	The examples below show these primitives in action.

568	   alone miss regressions until a later commit runs the full

596

322	Approval of a plan that *includes* a push does not authorize
323	the push itself; stop and ask again at the moment of pushing.
324	
325	**Default is interactive; an explicit scoped delegation waives
326	the gates.** The gates above — per-push approval, the
327	commit-description review (show title+body and stop), and the
328	hard stop after push/finalize — are the *interactive default*.
329	They yield when the user **explicitly** delegates a complete,
330	bounded task and authorizes carrying it through ("do all of X
331	and push each step, don't check in"). The bot then proceeds
332	through that task's commits and pushes without stopping, and
333	continues past each push to the next step. Conditions:
334	
335	- **Explicit grant** — never inferred from a task merely being
336	  well-scoped; the user's words must authorize unattended
337	  completion.
338	- **Bounded goal** — covers the named task only; does not carry
339	  to the next task or a vaguer follow-on.
340	- **Still transparent** — report each commit/push as it lands
341	  (title + outcome) so the user can catch up.
342	- **When in doubt, ask** — ambiguous authorization falls back to
343	  per-push approval.

345	### Shape at close-out push
346	
347	At close-out the cycle's *work* is done; its *published
348	shape* is the remaining choice, made at push time. Surface
349	the options and get user approval before pushing — once on
350	the target, changing shape is a remote rewrite (force-push,
351	needs approval), so choose deliberately.
352	
353	- **Squash to one commit** — single entry on the target.
354	  Right for straightforward changes where the Work-N is
355	  focused on one or two files.
356	- **Merge non-ff** *(current default)* — `main` gains a
357	  merge commit (`X.Y.Z`); cycle commits stay reachable via
358	  two parents. `jj log -r ..@ -n <N>` shows the trapezoidal
359	  shape. See [Merge non-ff recipe](#merge-non-ff-recipe)
360	  for the full setup sequence.
361	- **Keep separate** — one commit per cycle entry on
362	  `main`. Use when the decomposition itself is
363	  informative. Each chores section keeps its own header /
364	  `Commits:` ref; no consolidation churn.
365	
366	Set up squash/merge before invoking `vc-x1 push`; use
367	`jj git push` directly for non-standard shapes.
368	
369	### Merge non-ff recipe
370	
371	Setting up a [Merge non-ff](#shape-at-close-out-push)
372	close-out is a fixed sequence. `<closeout>` is the cycle's
373	close-out commit, `<prev>` the previous cycle's close-out
374	(the current `main` tip), `<work-tip>` the cycle's last
375	Work commit:
376	
377	1. **Rebase the close-out into a merge** — `jj rebase -r
378	   <closeout> --onto <prev> --onto <work-tip>`.
379	   - `-r <closeout>` keeps the `<closeout>` commit in place.
380	   - `--onto <prev>` becomes its first parent (trunk).
381	   - `--onto <work-tip>` becomes the second parent.
382	
383	   Together these make `<closeout>` a merge of
384	   `<prev>` + `<work-tip>`, forming a trapezoidal commit.
385	2. **Use `jj new <merge>`** to add an empty `@` above the
386	   merge. The rebase left `@` *on* the now-content-bearing
387	   merge, which git/IDE diff views show as uncommitted;
388	   `jj new` restores the clean empty `@` on top.
389	3. **Push** — `jj git push --bookmark main -R .`.
390	
391	**Post-hoc caveat.** If the cycle was already pushed
392	[Keep separate](#shape-at-close-out-push) its commits are
393	immutable: the rebase needs `--ignore-immutable` and the
394	push force-updates `main`.
395	The standard sequence assumes the merge is set up *before*
396	the close-out push.

412	### .claude cadence
413	
414	**Cadence**: one push = one `.claude` commit, paired
415	with every code commit in that push.
416	
417	The `.claude` working copy accumulates session data
418	across the cycle; its change ID stays stable across
419	snapshots, `jj describe`, and the finalize commit, so
420	code-side `ochid:` trailers resolve.
421	
422	`.claude` is a linear journal — all session work lives
423	on `main`, regardless of the app-side bookmark. **Do not
424	create or maintain `.claude` bookmarks that mirror
425	app-side branches** — risks the bot steering session
426	pushes to the wrong remote ref.
427	
428	Ending a session: if the user runs `/exit` there will be
429	session information created, which we don't worry about.
430	The user can close the terminal instead and `@` will
431	remain empty.

449	### After push or finalize: stop and wait
450	
451	After you **push** (cross the remote boundary) or launch
452	**finalize** on the `.claude` repo (`vc-x1 finalize --repo
453	.claude --squash --push <bookmark> --delay 10 --detach`) — by
454	hand or via the `vc-x1 push` wrapper — you **MUST NEVER**
455	proceed (next step, edit, tool call, text output) until the
456	user explicitly directs you to continue. **Even when the next
457	step seems obvious — wait.** Treat push-or-finalize as a hard
458	stop for the whole turn.
459	
460	`vc-x1 push` performs both as its tail stages — `push-app`
461	then the detached `vc-x1 finalize` on `.claude` — so there is
462	no gap left to speak in once the push is invoked. Put **all**
463	closing words *before* invoking it; do not purposely emit anything
464	after the tool returns.
465	
466	Why (`.claude` is the live journal finalize snapshots →
467	squashes → pushes):
468	
469	- **`--detach`**: lets the tool return immediately so the
470	  harness can keep flushing the *trailing* session-data — the
471	  tool call's own transcript and any words emitted *before*
472	  the invoke — into the snapshot.
473	- **`--delay 10`**: gives the harness time to complete that
474	  flush before the snapshot is taken. It is **not** time for
475	  the bot to do more work.
476	- **silence**: the bot must not summarize or perform any work
477	  after the tool returns.
478	
479	**Known slip**: the bot has emitted a summary after launching
480	finalize. There is no "harmless" closing line — if it's worth
481	saying, say it *before* the invoke.

483	### Recovery
484	
485	- **If push exits before `finalize-claude`** (e.g.
486	  failure between `push-app` and `finalize-claude`), run
487	  finalize by hand:
488	
489	  ```
490	  vc-x1 finalize --repo .claude --squash --push <bookmark> --delay 10 --detach --log /tmp/vc-x1-finalize.log
491	  ```
492	
493	- **Run finalize again if `@` is non-empty** after the
494	  finalize's squash-and-commit (also desirable after
495	  extra activity by the bot's agents).
496	  - Why: finalize snapshots `.claude` at `--delay`, but the
497	    bot keeps writing session data while it runs — the tool's
498	    own invocation plus the bot's closing response land
499	    *after* the snapshot.
500	  - Safe to repeat: bot session data is append-only, so a
501	    re-run never conflicts or overwrites. (This could
502	    change; it is not under the user's control.)
503	  - Fix: run `vc-x1 finalize --repo .claude --squash --push
504	    <bookmark> --delay 10 --detach` another time to capture
505	    that tail; one extra pass is generally enough.
506	  - No guarantees: events outside the bot's control can leave
507	    `@` non-empty — e.g. the bot's back end may decide to
508	    squash/consolidate session data, which can take minutes
509	    and land after the snapshot. The remedy is the same: just
510	    run finalize again. This is why a single pass is never
511	    guaranteed to leave `@` empty.
512	- **Clear push's saved state** after any out-of-band
513	  recovery — `rm .vc-x1/push-state.toml` or `vc-x1 push
514	  <bookmark> --restart` — otherwise push resumes from a
515	  stale stage.
516	- **Late code-repo tweak after `push-app` succeeded**
517	  (e.g. updating AGENTS.md or memory) requires `jj
518	  squash --ignore-immutable` and a re-push; that is a
519	  remote rewrite and needs explicit approval like any
520	  push.

522	## Iterative work
523	
524	When work for a single commit (the **target**) benefits
525	from incremental review, loop:
526	
527	1. `jj new -R .` — fresh empty `@` on top of the target.
528	2. Make the next round of changes.
529	3. User reviews the round (see
530	   [Reviewing changes](#reviewing-changes)).
531	4. `jj squash -R .` folds into the target and creates a
532	   new empty `@`.
533	5. If not done, go to step 2.
534	
535	Same jj mechanics as a
536	[sub-cycle ladder](#sub-cycle-ladders), but at
537	single-commit scope — the version
538	doesn't change.

540	## Sub-cycle ladders
541	
542	A **ladder** is a series of steps — a cycle's Work
543	commits, built as a local jj `@` chain. The structure is
544	recursive:
545	
546	- A **step** is one Work commit.
547	- Any step can subdivide into its **own ladder** of steps
548	  (a sub-cycle). The version suffix nests to match —
549	  `…-3`, then `…-3.1`, `…-3.2`; see [Numbering](#numbering).
550	- You **return** from a subdivision by **closing out**
551	  that ladder: its steps are collected back under one
552	  Close-out, then the enclosing ladder continues.
553	
554	While a ladder is being built its steps are provisional —
555	working titles, rewritten in place — there to sub-divide
556	the work into pieces you can review in isolation. At each
557	close-out you decide whether to squash the steps into one
558	commit or push them as-is (see [Pushing](#pushing)).
559	
560	### Per-step contract
561	
562	For each step in the ladder:
563	
564	1. `jj new -R .` — create a fresh empty `@`.
565	2. Do the step's work.
566	3. Run the fast validation (Rust example: `cargo test
567	   --bins`). **Non-negotiable** — for code, build and clippy
568	   alone miss regressions until a later step runs the full
569	   suite, by which point it's harder to tell which step
570	   introduced them.
571	4. `jj describe -m "..." -m "..." -R .` — a provisional
572	   title: the final description supersedes it if the
573	   ladder is squashed at Close-out, but it stands if the
574	   ladder is pushed unsquashed — so keep it presentable.
575	
576	### Navigating the ladder
577	
578	Common moves:
579	
580	- `jj log -r '<base>::' -R .` — see the whole ladder
581	  from its base.
582	- `jj edit -r <prefix> -R .` — jump `@` to any ladder
583	  step by chid prefix; handy for tracking down which
584	  step caused a problem.
585	- `jj edit @-- -R .` — quick-jump back two steps.
586	- `jj diff -r <chid> -R .` — review one step in
587	  isolation.
588	
589	Modifications to any ladder step rewrite it in place;
590	descendants auto-rebase.
591	
592	### Close-out: squash or push as-is
593	
594	When all ladder steps are done and tests pass,
595	decide whether to squash (per [Pushing](#pushing)).
596	
597	To **squash** into one commit:
598	
599	```
600	jj squash --from "<base>..@-" --into @ -u -R .
601	```
602	
603	`<base>` is the parent of the first ladder step; `-u`
604	keeps `@`'s description and discards the sources'.
605	After squash, history is linear: `<base> → @`;
606	intermediate steps are auto-abandoned.
607	
608	For N = 1 the squash is a no-op (`<base>..@-` is empty
609	when `@-` is `<base>`); push the single step directly.
610	
611	To **push as-is**, skip the squash and leave the chain
612	intact — each ladder step ships as its own commit, so
613	give every one a presentable description first.
614	
615	Either way, finish with `vc-x1 push <bookmark>` as for
616	any other commit.
617	
618	### Recovery
619	
620	If a ladder step goes wrong, back out without losing
621	prior steps:
622	
623	- **Discard the current step.** `jj abandon @ -R .`
624	  drops it; you get a fresh empty `@` on the same
625	  parent.
626	- **Edit an earlier step.** `jj edit -r <chid> -R .`,
627	  make corrections, then `jj edit -r <last-ladder-chid>`
628	  to return. Descendants auto-rebase.
629	- **Discard the entire ladder.** `jj op log -R .` shows
630	  the op history; `jj op restore <op-id> -R .` reverts
631	  to that point. Full undo — removes *all* ladder work
632	  after the chosen op. Use only to start over.
633
