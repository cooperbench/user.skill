Three good threads — let me take them in order.

## 1. `From` (init) vs `TryFrom` (finalize) — is the asymmetry wrong?

It's actually the *principled* split, not an accident: `From` is for total conversions, `TryFrom` for fallible ones — that's literally what the two traits are for.
- `InitParams::from(&InitArgs)` is just moving/cloning already-validated leaf values — it genuinely cannot fail.
- `FinalizeParams::try_from(&FinalizeArgs)` parses the composite `--squash` value and canonicalizes `--repo` — it genuinely can.

Forcing `TryFrom` everywhere would mean `impl TryFrom<&InitArgs> for InitParams { type Error = Infallible; … }` — an `Error` type that can't be constructed. That's the recognized anti-pattern, not the cure.

And here's the thing that defuses most of the "inconsistency" worry: **std already gives you `TryFrom` for free wherever you `impl From`** (blanket `impl<T, U: Into<T>> TryFrom<U> for T`, `Error = Infallible`). So `InitParams::try_from(&args)` *already compiles* — the dispatch code can be uniform if we want it to be, without touching the trait impls. (Whether `main.rs` actually writes `.try_from()` for the infallible ones — meh, you'd end up `match`ing or `.expect()`ing an unreachable `Err`, which is uglier than just `.from()`. I'd leave init's dispatch arm as `.from()`.)

**My recommendation:** keep the split; codify the rule in `ARCHITECTURE.md` so it reads as a rule, not a quirk — *"boundary conversion is `impl From<&XArgs>` when the conversion is total (moving/cloning leaf values), `impl TryFrom<&XArgs>` when it does fallible normalization — parsing a composite flag value, canonicalizing a path, etc."* That's the one decision that gates finishing this cycle (see bottom).

## 2. `--repo` in init vs finalize — could `options_flags` handle both?

Not as *one* leaf — they're three different flags wearing the same name:
- **init's `--repo`** (`RepoOption`) — *where to create* the new repo: `remote` (URL prefix) / `local` (parent dir for fixture bares).
- **finalize's `--repo`** — *which existing jj repo to operate on* (a `PathBuf`, default `.`).
- **the multi-repo `-R`/`--repo` list** in `CommonArgs` / `sync` — *which repos to query*.

Different domains → different help, defaults, value semantics. They can't collapse. But `options_flags` already has the mechanism for "same spelling, different help/defaults": the **"Pattern A escape hatch"** in its README. So "options_flags handles both" really means "each gets its own leaf there" (e.g. a `TargetRepoOption` for the finalize-style one) — which is exactly point 3.

## 3. Move `--squash` (and the rest of `FinalizeArgs`) into `options_flags`?

- **`--delay` / `--detach` / `--exec`** — finalize-only today. The `options_flags` discipline is "promote to a leaf when a second consumer appears" — so leave these inline until one does. Pre-emptively leaf-ifying single-use flags adds indirection for no reuse.
