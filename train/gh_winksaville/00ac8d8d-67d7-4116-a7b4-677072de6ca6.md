80	### Flags
81	
82	- **`<duration_s>`** — positional, required; measurement window
83	  in seconds.
84	- **`-w` / `--warmup <SECS>`** — default 0.5; run the same
85	  dispatch loop with the probe active for this long, then clear
86	  the probe at the boundary so only steady-state data reaches
87	  the report. Set to 0 for quickest iteration; raise to 10 s or
88	  more for reference measurements where you want the CPU fully
89	  settled.
90	- **`-i` / `--inner <N>`** *(goal1 only)* — default 1, ≥1;
91	  dispatches per probe scope. Larger values amortize the probe's
92	  two-`rdtsc` apparatus cost and give the histogram meaningful
93	  dynamic range. goal2 fixes `inner=1` because its per-channel
94	  queue holds at most one message.
95	- **`-t` / `--ticks`** — display probe values as raw ticks
96	  instead of nanoseconds.
97	- **`-d` / `--decimals <N>`** — fractional precision of numeric
98	  cells in the band table. Omit for a mode-aware default
99	  (0 for ticks, 1 for ns) — typically what you want. Pass an
100	  integer N to force N decimals in either mode (e.g. `-d 2`
101	  for 2-decimal ns, `-d 0` for integer ns).
102	- **`-p` / `--pin <CORES>`** — pin threads to logical CPUs. goal1 uses
103	  the first core in the list; goal2 pins actor `i` to
104	  `cores[i % len]`. Accepts comma lists and ranges: `--pin 5`,
105	  `--pin 0,1`, `--pin 0-3`, `--pin 0,0` (oversubscribe).
106	
107	### Typical invocations
108	
109	```
110	# Short iterative smoke, no warmup:
111	goal1 0.1 -w 0 -i 1000
112	
113	# Full measurement with pinning:
114	goal1 2 -i 1000 -p 0
115	
116	# Goal2 with actors on separate cores (same complex):
117	goal2 1 -p 0,1
118	```

120	## Reading the band table
121	
122	The `tprobe` block is a 12-row percentile histogram with four
123	summary rows. Every row renders every run, even when a band
124	holds no data — a zero row is distinguishable from a missing row.
125	
126	### Header
127	
128	```
129	tprobe: <name> [count=N]
130	```
131	
132	`<name>` identifies the probe (`goal1.dispatch`,
133	`goal2.dispatch.actor0`, …). `count=N` is the number of **scopes**
134	drained into the histogram, not total dispatches — at `--inner
135	1000` one scope covers 1,000 dispatches, so `count` here is
136	`(total_messages / inner)`. Total dispatch count is in the summary
137	line above.
138	
139	### Rows
140	
141	Twelve percentile bands in order: `min-p1`, `p1-p10`, …, `p90-p99`,
142	`p99-max`. Each row covers the samples whose rank in the sorted
143	distribution falls within that percentile range.
144	
145	### Columns
146	
147	- **first** — lowest value observed in the band.
148	- **last** — highest value observed in the band.
149	- **range** — `last - first + 1`; width of the band's value range.
150	- **count** — number of samples in the band.
151	- **mean** — average value within the band. Raw, unadjusted —
152	  same hardware-tick deltas the probe recorded.
153	- **adj mean** — same mean, minus the per-event apparatus
154	  correction from calibration (clamped at 0). See the
155	  `apparatus:` line for the correction amount and
156	  [`crates/tprobe/notes/overhead-model.md`](crates/tprobe/notes/overhead-model.md)
157	  for the formal model.
158	
159	### Summary rows
160	
161	- **mean / stdev** — whole-histogram statistics, including the
162	  `p99-max` tail. `adj mean` on the `mean` row applies the
163	  per-event correction the same way as the band rows; `stdev`
164	  leaves the `adj mean` column blank because standard deviation
165	  is shift-invariant.
166	- **mean min-p99 / stdev min-p99** — same statistics excluding
167	  `p99-max`. Useful for A/B-ing code changes because the tail can
168	  be dominated by rare outliers (OS preemption, lock contention,
169	  interrupts) that drown signal in the body of the distribution.
170	  Same raw-vs-adj treatment as the `mean` / `stdev` pair.
171	
172	### Why a band can be all zeros
173	
174	The renderer walks `hdrhistogram` buckets and assigns each bucket
175	to one band by its cumulative mid-rank. A tight distribution has
176	most samples in a handful of buckets, and each bucket lands
177	entirely in one band — so neighboring bands show zeros even
178	though they'd nominally hold ~10% of the data. It's a display
179	artifact, not missing data: the samples are visible in the
180	adjacent non-zero band. A `stdev min-p99` near 0 alongside a
181	couple of dense bands is a strong signal that the underlying
182	distribution is spike-heavy.
183	
184	### The `apparatus:` line
185	
186	```
187	apparatus: framing=21 tk (5.54 ns); loop_per_iter=0.93 tk (0.24 ns); per-event at inner=1000 = 1 tk (0.26 ns)
188	```
189	
190	Reports the fitted overhead model from calibration.
191	
192	- **`framing`** — hardware floor cost of the probe's two-`rdtsc`
193	  pair, paid once per scope. Measured as the intercept of a
194	  two-point fit on empty `black_box(1)` scopes.
195	- **`loop_per_iter`** — per-iteration cost of the calibration's
196	  empty inner loop (one `black_box(1)` per iter). Measured as
197	  the slope of the same fit.
198	- **`per-event at inner=N`** — the per-event correction shown in
199	  the band-table's `adj mean` column: `framing / N +
200	  loop_per_iter`, rounded to the nearest tick. Amortizes toward
201	  `loop_per_iter` as `inner` grows.
202	
203	Calibration runs unconditionally (~10 ms wall-clock); the
204	histogram still stores raw per-event values, and this correction
205	is applied only in the `adj mean` display column. See
206	[`crates/tprobe/notes/overhead-model.md`](crates/tprobe/notes/overhead-model.md)
207	for the derivation and the unmeasurable-overhead category.
208	
209	### The `pinning:` line
210	
211	```
212	pinning: actor0→core0, actor1→core4
213	```
214	
215	Shows what `--pin` produced for each workload thread;
216	`none (unpinned)` means the OS is free to schedule threads
217	anywhere.

219	## The bot's understanding
220	
221	A handful of recurring patterns in the output, with the bot's
222	best read of why the numbers look the way they do. Specific
223	numbers below are from an AMD Ryzen 3900X at ~3.7 GHz — compare
224	your own numbers to your own baseline, not to these.
225	
226	### goal1 raw vs `adj mean`, and how `inner` changes it
227	
228	The probe's two-`rdtsc` framing has a real cost (~5 ns on modern
229	x86) that contaminates every stored scope delta — the histogram
230	stores this raw value, so the `mean` column shows it. At
231	`inner=1` the full framing lands on every per-event sample,
232	pushing `mean` to ~10 ns; the `adj mean` column applies the
233	`framing + loop_per_iter` correction and reports ~4 ns —
234	approximately the true `handle_message` cost. At `inner=1000`
235	framing is amortized to ~0.02 ns per event, so `mean` and
236	`adj mean` both land at ~5 ns (they agree because the correction
237	is tiny at this batch size). The two regimes converge on the
238	same work-alone cost, just via different paths: low `inner`
239	relies on the correction, high `inner` shows it directly.
240	
241	### goal2 is ~900× slower than goal1 `--inner 1000`
242	
243	goal1 `--inner 1000`: ~5 ns per event (~200 M msg/s).
244	goal2 `--inner 1`: ~1–1.5 µs per event (~0.25 M msg/s).
245	The bot thinks the gap is dominated by:
246	
247	- **`mpsc`'s `Mutex` + condvar wake** on every send and recv —
248	  even a fast bounded mpsc pays this on every cross-thread
249	  hand-off.
250	- **Two context switches per round-trip** — one per channel
251	  hand-off, so a ping-pong cycle of (A send → B recv → B send →
252	  A recv) crosses the scheduler four times.
253	- **Cache-line bouncing** — the shared channel metadata and the
254	  message migrate between the two actors' L1 caches each round.
255	
256	An unbounded lock-free mpsc would close some of this; the
257	context-switch floor is fundamental to any "block, wake, run"
258	channel pattern.
259	
260	### `--pin` tightens `stdev` but can raise the mean
261	
262	Pinning eliminates OS thread-migration noise — a thread landing
263	on a different core than the previous message's cache
264	warmed — so `stdev min-p99` drops (on this box: 246 ns → 80 ns,
265	about 3× tighter). But pinning also *forces* placement, which
266	can be worse than what the OS would have chosen. On this 3900X
267	(12 cores split across 4 CCX complexes of 3 cores each),
268	`--pin 0,4` puts the two actors on different CCX complexes, so
269	every ping-pong round forces a cross-complex cache coherence
270	transfer — the mean rises from ~630 ns to ~1,500 ns. `--pin 0,1`
271	(same CCX) keeps the mean near unpinned while still tightening
272	the stdev.
273	
274	This isn't a flaw; it's the intended trade. Pinning gives you
275	control over what you measure — pick cores that match the
276	scenario you care about (best-case same-complex, worst-case
277	cross-socket, etc.).
278	
279	### The `p99-max` tail occasionally spikes to tens of µs or ms
280	
281	Almost always an OS interrupt, scheduler preemption, or a rare
282	lock contention sneaking into a probe scope. The probe sees real
283	events the system experiences, so the measurement is honest —
284	they just aren't what you typically want to compare across
285	runs. `mean min-p99` excludes this tail and is usually the
286	right comparator for A/B work.
287	
288	### Numbers travel with the hardware
289	
290	- **Framing** is ~20–50 ticks regardless of clock speed
291	  (pipeline cost in cycles, not time).
292	- **goal1 per-event cost at large `inner`** scales with clock
293	  frequency.
294	- **goal2 latency** depends heavily on CPU topology (single
295	  socket vs NUMA), cache architecture, and scheduler tuning.
296	
297	If the numbers on your box differ from those above, that's
298	expected; consistency run-to-run and sensitivity to
299	`--pin` / `--inner` / `--warmup` are the invariants worth
300	trusting.

458	### Why `jj log` shows fewer commits than `gitk`
459	
460	If you're coming from git, jj's log output can be surprising compared to
461	tools like `gitk --all`.
462	
463	jj tracks *changes* (identified by change IDs), not individual git commits.
464	When you rewrite a change (`jj describe`, `jj rebase`, `jj squash`, etc.),
465	jj creates a new git commit and keeps the old one under `refs/jj/keep/*` as
466	undo history. `gitk --all` sees all of these obsolete commits; `jj log` only
467	shows the current version of each change.
468	
469	### Useful commands
470	
471	| Command | Description |
472	|---------|-------------|
473	| `jj log` | Show recent visible commits (default revset) |
474	| `jj log -r ::@` | Show **all** ancestors of the working copy |
475	| `jj log -r 'all()'` | Show all non-hidden commits (needed if you have multiple heads/branches) |
476	| `jj st | Show the status of the Working and Parent commits |
477	| `jj st -r <chid> | Status of the commit, <chid> such as `@`, `@-`, `xyz` |
478	| `jj show | Show the Working commit, -r @ |
479	| `jj show -r <chid> | Show the commit, <chid> such as `@`, `@-`, `xyz` |
480	| `jj evolog -r <chid>` | Show the evolution history of a single change |
481	| `jj op log` | Show operation history (each rewrite operation) |
482	
483	
484	In a single-branch workflow, `jj log -r ::@` and `jj log -r 'all()'` give
485	the same result. Use `all()` when you have multiple branches or heads.
486	
487	## Cross-repo Linking with Git Trailers
488	
489	Commits in each repo use [git trailers](https://git-scm.com/docs/git-interpret-trailers)
490	to cross-reference their counterpart in the other repo. The `ochid`
491	(Other Change ID) trailer contains a workspace-root-relative path
492	and jj changeID:
493	
494	```
495	ochid: /.claude/xvzvruqo   # points to a .claude repo change
496	ochid: /wtpmottv            # points to an app repo change
497	```
498	
499	Paths always start with `/` (the workspace root, i.e. vc-x1).
500	Each repo has a `.vc-config.toml` that identifies its location
501	within the workspace, so tools can resolve these paths locally.
502	
503	For full details see:
504	- [Git trailer convention](./notes/chores-01.md#git-trailer-convention)
