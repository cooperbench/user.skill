Same binary, so that's not code — it's thread placement. The 3900X has two CCDs with four separate L3 complexes (CCXs); the demo spawns two scoped threads and lets the scheduler place them. When producer and consumer land on the same CCX the head/tail/slot cache lines bounce through a shared L3 and you get ~17 ns; when they land on different CCDs the transfer goes over the Infinity Fabric and it balloons toward ~70. Good news and bad news. I checked the pool API (`src/pool.rs`) — the answer is: **not possible with the current public API, but it's two small methods away**, and those two methods are a deliberately scoped slice of Todo #1 (descriptor queues).

What the composed flow needs, and what exists:

- **A second pool handle on the consumer thread** — ✅ exists. `Pool::attach` (`src/pool.rs:174`) gives another handle over the same region, and the contract already allows it: one handle allocates, any handle frees.
- **Getting a descriptor out of a `BufSlot`** — ❌ missing. The buffer index (`idx`, `src/pool.rs:321`) is private, and the guard's only exits are `free()` or leak. There's no `into_idx(self) -> u32` that says "I'm converting my ownership into a descriptor."
- **Rebuilding a `BufSlot` from a descriptor** — ❌ missing. The attached consumer handle has no `from_idx(idx) -> BufSlot` — no way to mint a guard (or even a `&T`) from an index it received.

So the demo shape would be: producer `pool.alloc::<Msg>()` → write `seq` → `slot.into_idx()` → send the `u32` through the SPSC ring as the message; consumer reads the `u32` from the ring → `pool.from_idx::<Msg>(idx)` → assert → `free()`. The ring's commit/reserve Release/Acquire already transfers visibility of the payload writes, so the ordering story is sound; `from_idx` bounds-checks the index and is `unsafe` only because ownership transfer ("this idx came from `into_idx` and wasn't duplicated") can't be proven by types — exactly the trust posture the design doc already prescribes for descriptors arriving through shared memory.

Without those methods there's no honest version: you could FIFO the guards through a `VecDeque` (1t) or a std channel (2t) alongside the ring, but then the side channel is doing the real ownership transport and the ring is decoration.

Note this is the intentionally-small version of Todo #1: full descriptor queues carry `(pool id, buffer offset)` with a per-process pool registry and provenance headers, so any message travels over any queue. **1. Descriptor shape: index, not byte offset — `Desc { pool_id: u32, buf_idx: u32 }` (8 bytes, POD).**
The design doc says "(pool id, buffer offset)", but the doc's real requirement is "offsets only, everywhere" — meaning *no pointers* in shared structures, because each process maps the pool at a different address. A buffer **index** satisfies that just as well as a byte offset, and it's strictly simpler: it's what the free-stack and `BufSlot.idx` already use, validation is one comparison (`idx < buf_count`), and the receiver computes the address as `bufs + idx * buf_size` from its own attached geometry. A byte offset would need bounds *and* divisibility checks to prove it lands exactly on a buffer boundary. Both u32s match the pool's existing u32 index space; 8 bytes rides easily in a 64-byte ring slot.

**2. Pool-id source: assigned by a per-process registry at register time.**
The open question was coordinator-assigned vs derived-from-shm-identity — that's the *cross-process* question, and it stays open. In-process, the registry just hands out the next table slot: `registry.register(pool) -> PoolId`. The registry is fixed-capacity (const-generic array, no_std-friendly, no allocation), holding one `Pool` handle per id. That handle is a resolver/freer handle, which the pool contract already permits — "at most one attached handle allocates, any handle may free" — so the allocating thread keeps its own `Pool` while the registry holds another over the same region.

**3. Resolve-side validation: full, always.**
A descriptor arriving through shared memory is untrusted (same posture as ring geometry): unknown `pool_id` → error; `buf_idx >= buf_count` → error; `T` geometry mismatch → same `check_type` panic as `alloc` (programming error, not hostile input). A hostile descriptor can produce a garbage-but-valid `T` or a double-free-shaped protocol violation — never UB from the resolve itself.

**4. The ownership contract — this is the one real `unsafe`:**
- `registry.into_desc(slot: BufSlot<T>) -> Desc` — **safe**. Consumes the guard (identifying the pool by the guard's header address, O(N) over a tiny table), returns the descriptor. Ownership doesn't vanish — it's now *carried by the descriptor*, exactly the "in-flight" buffer state the usage model reserved.
- `unsafe registry.resolve::<T>(desc: Desc) -> Result<BufSlot<T>, Error>` — **unsafe**, and this is the honest core: resolving mints a guard that acts as `&mut T`. The types can't prevent you from resolving the same descriptor twice (two owners, aliased `&mut`) or resolving a descriptor you invented. The caller's contract: *this descriptor came from `into_desc` and is being resolved exactly once, ownership transferred through a channel with proper ordering* (the ring's commit→reserve Release/Acquire provides that). All the bounds validation in #3 still runs — `unsafe` covers only what validation can't check: uniqueness of ownership.

The flow then reads: `pool.alloc` → write → `registry.into_desc` → ring `reserve_slot::<Desc>`/commit → … → ring reserve/release → `registry.resolve` → read → `free()` (or forward it over another queue — that's the "any message over any queue" payoff).

Depends which sense of "type" — the answer is "one signature, many machine types, our choice of how to accept them":

**One signature.** All three wait points (alloc/`Exhausted`, producer/`Full`, consumer/`Empty`) take the same shape: `FnMut(u32) -> bool`. **Three ways the API can accept that**, and this is the real design choice:

- `impl FnMut(u32) -> bool` (generic) — monomorphized: each distinct closure stamps out its own specialized copy of `alloc_with`, fully inlined, zero overhead. The spin policy compiles to literally the loop we write by hand today. Cost: one copy of the function per distinct policy in the binary.
- `&mut dyn FnMut(u32) -> bool` (trait object) — one shared copy of the function, closure called through an indirect call. A hair slower per retry, but retries are the slow path anyway. This is the code-size-friendly option if an embedded target ever cares.
- `fn(u32) -> bool` (plain function pointer) — no captures allowed, so no deadline-carrying policies, but the canned ones (`policy::spin`) are just ordinary `fn`s and coerce to this.

I'd take `impl FnMut(u32) -> bool` in the public API — it's the idiomatic zero-cost choice, and it accepts all three kinds above (plain `fn`s and capturing closures alike). If binary bloat ever shows up on an embedded build, an internal `dyn` core with a thin generic wrapper gets one copy without changing the API.
