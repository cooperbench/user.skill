> AGENT

Yes — your original understanding was right: SMT is a CPU hardware feature. Simultaneous Multithreading is when one physical core presents two (or more) hardware threads that genuinely execute at the same time, sharing the core's pipelines and its L1/L2 caches. Intel's brand name for it is Hyper-Threading; some AMD and POWER chips have it too. The Cortex-A76 cores in your Pi 5 simply don't implement it — each core is one hardware thread, which is why `thread_siblings_list` shows only `0` and the demo skips that row.

So "use it if available, don't require it" is exactly what the demo already does — it's not that a knob is off; the hardware shape (two threads truly concurrent on one core, sharing L1/L2) doesn't exist on this machine. The only software substitute is pinning both threads to the same CPU and letting the scheduler alternate them, and the probe I ran right before your interrupt shows why that's not a useful stand-in: two spin-waiting threads timesharing cpu 0 managed about **8,000 msgs/sec (~125 µs/msg)** — roughly 1000× slower than the ~8.5M msgs/sec cross-core runs, because each handoff waits out a scheduler timeslice instead of a cache-line transfer. The five same-core lines at 1M messages each would take ~10 minutes and would be measuring the Linux scheduler, not the ring.

My recommendation: keep the skip as correct behavior on non-SMT hardware, and just make the message self-explanatory — e.g. `skipped, CPU has no SMT (1 thread/core)` — so it reads as "this machine lacks the feature" rather than as an error.
