> AGENT

Here's my analysis — **no fundamental blockers, but there's an interesting design tension**:

### What cargo profiles control

Cargo profiles (`[profile.release]`, `[profile.dev]`, custom profiles) set things like `opt-level`, `lto`, `codegen-units`, `panic`, `strip`, `debug`, `incremental`, `overflow-checks`, etc.

### The overlap problem

tspec already controls many of the same knobs, but via **RUSTFLAGS**:
- `rustc.opt_level` → `-C opt-level=N`
- `rustc.lto` → `-C lto=true`
- `rustc.codegen_units` → `-C codegen-units=N`
- `rustc.panic` → `-C panic=abort`
- `strip` → `-C strip=symbols`

These work, but RUSTFLAGS applies to **all** crates in the dependency graph (including build scripts and proc macros), which can cause unnecessary rebuilds and occasional issues. Cargo profiles, by contrast, are scoped properly — `[profile.release]` only applies to normal builds, not build scripts.

### The `--config` approach

Since Cargo ~1.63, you can pass `--config 'profile.release.opt-level=3'` on the command line. This means tspec could inject profile overrides **without touching Cargo.toml**. This is the cleanest path.

### So the real question is: overlap vs migration

There are two approaches:

1. **Add `[profile]` as a new section** alongside existing `[rustc]` fields — users choose which mechanism to use. Simpler to implement, but the overlap (`rustc.opt_level` vs `profile.release.opt-level`) is confusing and could conflict.

2. **Migrate the overlapping fields** from RUSTFLAGS to `--config` profile overrides — `rustc.opt_level`, `rustc.lto`, `rustc.codegen_units`, `rustc.panic`, and `strip` would all be applied as profile settings instead. The `[rustc]` section would retain only `build_std` and `flags` (things that genuinely need RUSTFLAGS). This is cleaner long-term but is a breaking change to spec semantics.

### No blockers

The answer is **no, there's no reason we can't do this**. The `--config` flag gives us a clean mechanism. The main decision is whether profiles are additive (option 1) or replace the overlapping RUSTFLAGS approach (option 2).
