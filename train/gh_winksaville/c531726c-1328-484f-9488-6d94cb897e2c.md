> AGENT

That combination — inter- **and** intra-process, zero-copy, `no_std` — is a niche no existing crate fills cleanly, as far as I know:

- **iceoryx2** — inter-process (and same-process works), but firmly `std`: it needs an OS for shm files, named concepts, etc. Their roadmap mentions bare-metal ambitions, but today it's not `no_std`.
- **bbqueue** — genuinely `no_std` (built for embedded/DMA), zero-copy grant-based SPSC ring. But its producer/consumer handles contain regular pointers into one address space, so it's intra-process only; you can't drop it into shared memory across processes as-is.
- **heapless::spsc**, **rtrb**, **ringbuf** — same story: good rings, but either not cross-process-safe (pointers, not offsets) or not `no_std` (rtrb).

The reason it's rare: cross-process safety requires the ring's state to be **offset-based and position-independent** (the region maps at different addresses in each process) and all coordination to go through atomics in the shared region. Most `no_std` rings assume a single address space; most shm crates assume `std`.

So the honest recommendation is a small hand-rolled core:

- A `no_std` SPSC ring crate of your own: header (atomic read/write indices) + payload area, all offset-addressed, operating on any `&mut [u8]`/raw region you give it. Zero-copy via grant-style APIs (write-in-place, read-in-place) like bbqueue's.
- Thin `std` adapters for the bench: intra-process = a `Box<[u8]>` shared between threads; inter-process = the same bytes in a `memfd`/`shm_open` region via `memmap2`.

That gives you one code path benched in both configurations with TProbe2, which is a nicer experiment anyway — same ring, only the memory substrate changes. And it's very much in this project's spirit (measuring the primitive itself rather than a framework).

If you'd rather start from an existing crate and adapt, **bbqueue** is the best donor — its grant API is the right shape; the work would be converting its handle state to offsets-in-region. But I'd guess writing a minimal SPSC ring from scratch is less work than retrofitting bbqueue.

what about google's zerocopy

> AGENT

`zerocopy` is complementary, not competing — it solves a different half of the problem.

What it is: Google's safe-transmutation crate. You derive `FromBytes` / `IntoBytes` / `KnownLayout` / `Immutable` on your message types, and it lets you reinterpret a `&[u8]` as `&YourType` (and back) with zero copying and no `unsafe`, with compile-time layout checks. It's fully `no_std` and has no dependencies to speak of.

What it is **not**: a transport. It has no ring buffer, no shared memory, no synchronization, no producer/consumer — it just makes "these bytes in place *are* my struct" safe.

So in the design from the last message, zerocopy slots in perfectly as the payload layer:

- The hand-rolled `no_std` SPSC ring moves raw byte grants through the region (intra- or inter-process).
- `zerocopy` types those bytes: producer writes via `IntoBytes`, consumer reads via `FromBytes::ref_from_bytes` directly on the grant slice — no serialization step, no copy, and the compiler enforces that the type is actually safe to view that way (no padding leaks, no invalid bit patterns, pointer-free).

That last point matters for the cross-process case specifically: `FromBytes` types are by construction valid for any bit pattern and can't contain references — which is exactly the "position-independent, offset-only" discipline the shared region needs. Using zerocopy on the payload makes that constraint compiler-checked instead of convention.

So the stack I'd suggest: **own `no_std` ring (transport) + zerocopy (typed in-place access) + memmap2 in the std bench harness (inter-process substrate)**, with TProbe2 instrumenting the ring operations. Everything below the harness stays `no_std`.

vc-x1 0.66.0-0

Dual-repo commit+push+finalize in one resumable command.

Collapses today's manual Commit-Push-Finalize Flow into a
single subcommand with two interactive approval gates and a
state machine with persistent progress so interruptions can
resume without re-doing completed stages.

Stages: preflight (fmt/clippy/test) → review (approve diff)
→ message ($EDITOR / --title+--body, approve text) →
commit-app → commit-claude (skipped if clean) → bookmark-both
→ push-app → finalize-claude. Failures in commit-app /
commit-claude / bookmark-both roll both repos back via
`jj op restore` to the snapshot recorded before commit-app.
After push-app succeeds the remote boundary is crossed and
recovery is forward-only.

Non-interactive use: pass both --title and --body plus --yes
to skip the review gate. Saved state carries title/body
across resumes so only the first invocation needs them.

Usage: vc-x1 push [OPTIONS] [BOOKMARK]

Arguments:
  [BOOKMARK]
          Bookmark to advance in both repos (positional form of `--bookmark`).
          
          Accepting a positional lets the common case read as `vc-x1 push main`
          without the `--bookmark` ceremony; `--bookmark` is kept as an alias
          for scripts and for composition with other args. The two forms
          conflict if both supplied.

Options:
      --bookmark <BOOKMARK>
          Bookmark to advance in both repos (flag form; see positional)

  -V, --version
          Print the `vc-x1 X.Y.Z` banner as the first line, then continue. With
          no subcommand, prints the banner and exits.
          
          Replaces clap's auto-version (which would exit after printing): the
          banner now rides along with normal subcommand execution rather than
          gating it, so scripts can capture the version *and* the command's
          output in one invocation.

      --restart
          Clear any saved state file and start from stage 1

  -v, --verbose...
          Verbose output: -v debug, -vv trace

      --from <STAGE>
          Explicit stage to jump to (advanced / debug use)

          Possible values:
          - preflight:       Run fmt / clippy / test / install / retest
          - review:          Present diff for the first approval gate
          - message:         Compose / edit the commit message; present for
