Good question — these are **two completely unrelated things that happen to share the name "matches."** The `!` is the giveaway.

## `matches!(...)` is a standard-library macro

`matches!` is a built-in Rust macro (from `std`), nothing to do with your `matches` closure. The trailing `!` is Rust syntax for *macro invocation* — `println!`, `vec!`, `assert!`, and `matches!` are all macros, not functions or closures.

`matches!(expr, pattern)` expands to a boolean: "does `expr` match this pattern?" It's shorthand for a `match`:

```rust
matches!(e.kind(), ErrorKind::TimedOut | ErrorKind::WouldBlock)
```

is exactly equivalent to:

```rust
match e.kind() {
    ErrorKind::TimedOut | ErrorKind::WouldBlock => true,
    _ => false,
}
```

So that line reads: *"if the error kind is TimedOut **or** WouldBlock, take this arm (and `continue`)."* The `|` inside is pattern-alternation, not bitwise-or.

## Your closure is `matches` (no `!`)

The closure parameter `mut matches: F where F: FnMut(&str) -> bool` is *invoked* like a function — `matches(line)` — with **no `!`**. That's the predicate deciding whether a received reply line is the one you're waiting for.

## They never interact

In that `read` block you're looking at, the closure `matches` is **not** used at all — that block is purely about draining bytes off the wire. The `matches!` macro there is just classifying the I/O error. Your closure `matches(...)` gets called later in the loop, once a full line has been assembled, to test that line against the caller's predicate.

So:

| Token | What it is | Used for |
|---|---|---|
| `matches!(x, P)` | std macro | pattern-test → bool, here classifying the error kind |
| `matches(line)` | your `FnMut` closure | testing whether a reply line is the expected one |

## On your buffer guess

> I assume the closure passed is capturing `let mut buf`

No — `buf` is a local `read` buffer owned by `read_reply` itself, passed by `&mut` to `reader.read(&mut buf)`. The caller's closure captures whatever *it* needs to recognize the reply (e.g. the expected register prefix like `"VNRRG,01"`), and it only ever receives an assembled line as its `&str` argument. The two are independent.

The name collision is unfortunate — `matches!` the macro shadowing the visual look of your `matches` closure is purely coincidental. Want me to look at renaming the closure parameter (e.g. `is_match` / `accept`) to remove the confusion?

It's neither exact nor arbitrary-contains — it's a **prefix match** (`starts_with`), and the actual terminating condition is a bit richer than the closure alone. Two layers:

**1. The caller's closure** is always a prefix test. Every call site passes something like:
```rust
|l| l.starts_with("$VNWRG,75")
|l| l.starts_with("$VNWRG,06")
|l| l.starts_with("$VNWNV")
```
So a line is accepted if it *begins with* that register prefix — not an exact string equality, and not a substring-anywhere search. (And remember `read_reply` already slices `candidate` from the last `$`, so the prefix is anchored to the start of the real reply, not to stray leading bytes.)

**2. `transact` wraps your closure with an error escape hatch** (line 769):
```rust
read_reply(port, deadline, |l| accept(l) || l.starts_with("$VNERR"))?
```
So the line that `read_reply` returns is accepted if **either**:
- your prefix matches, **or**
- it's a `$VNERR` device-error reply.

Then `transact` checks for `$VNERR` after the fact (line 772) and turns it into an error. That's how a wrong/rejected command terminates promptly instead of waiting out the whole deadline.

Here's exactly what each bench mode writes, read from the code (`bench_binary` at 1100, `bench_ascii` at 1177). Both are **save-and-restore** — nothing persists to flash, and every write reverts at the end.

## Binary bench (`--bin`) — always touches **two** registers

1. **Reads reg 7** (`VNRRG,07`) — to remember the current ASCII rate (`prev_hz`) for restore. Read, not a change.
2. **Writes reg 75** (`VNWRG,75,<port>,<divisor>,01,<mask>`) — configures Binary Output 1: serial port, divisor (`800/hz`), rate-divisor-group `01`, and the field bitmask. This is where a `$VNERR` lands if it won't fit.
3. **Writes reg 7 = 0** (`VNWRG,07,0`) — silences ASCII async so only the binary stream is measured.
4. *(measure)*
5. **Restore:** reg 75 back off (`VNWRG,75,0,...`), reg 7 back to `prev_hz`.

So `--hz` only affects the **reg-75 divisor**. Reg 7 is always forced to 0 during measurement regardless of `--hz`, then restored.

## ASCII bench (no `--bin`) — reg 7, and reg 6 only if `--type`

1. **Reads reg 7** — remember `prev_hz`.
2. **If `--type` given:** read reg 6 (remember `prev_type`), then **write reg 6** (`VNWRG,06,<t>`) to set the message preset. Skipped entirely without `--type`.
3. **Writes reg 7 = `<hz>`** (`VNWRG,07,<hz>`) — the rate under test; `$VNERR` here = won't fit at this baud.
4. *(measure)*
5. **Restore:** reg 7 → `prev_hz`, and reg 6 → `prev_type` if it was changed.

## Summary

| Register | Binary bench | ASCII bench |
|---|---|---|
| **7** (async rate) | read, set to 0, restored | read, set to `--hz`, restored |
| **75** (binary output) | set from `--hz`/`--fields`/`--serial-port`, restored off | untouched |
| **6** (ASCII msg type) | untouched | set **only** if `--type`, restored |

The invariant in both: **read-remember reg 7 first, restore last**, so a bench never leaves the device's async rate changed — which is why your 50 Hz ASCII setting survived the binary bench unchanged.
