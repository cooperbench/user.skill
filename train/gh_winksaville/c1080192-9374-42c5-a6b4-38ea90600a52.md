46	## Releasing
47	
48	**`cargo install` lockfile gotcha.** If you install your project's
49	binary with `cargo install --path .`, also pass `--locked`. By
50	default `cargo install` ignores `Cargo.lock` and re-resolves
51	dependencies from scratch, so it can silently build the binary from
52	a different — possibly broken — dependency graph than `cargo build`
53	/ `cargo test` ran against.
54	
55	| command | reads `Cargo.lock`? | re-resolves? |
56	| --- | --- | --- |
57	| `cargo build` / `test` / `run`  | yes     | only if `Cargo.toml` changed |
58	| `cargo build --locked` (etc.)   | yes     | never; errors if it would need to |
59	| `cargo install` (default)       | **no**  | always, from scratch |
60	| `cargo install --locked`        | yes     | never; errors if it would need to |
61	
62	There's no stable cargo config knob to make `--locked` the default
63	for `cargo install`, so the discipline lives in the per-commit cargo
64	cycle and shell aliases (e.g. `alias ci='cargo install --locked'`).
65	
66	The trade-off is predictable-as-tested (`--locked`) vs picking up
67	upstream fixes via fresh resolves (default). Either is defensible —
68	pick what fits your project, then edit this section and the
69	per-commit cargo cycle to match. Background:
70	[cargo#7169](https://github.com/rust-lang/cargo/issues/7169),
71	[cargo#9436](https://github.com/rust-lang/cargo/issues/9436).

2	
3	This protocol uses [Prose form](../AGENTS.md#prose-form). It
4	contains instructions on how a commit cycle is accomplished.
5	
6	## Cycles
7	
8	A cycle has three phases:
9	
10	- **[Preparation](#preparation)** (`X.Y.Z-0`) — the cycle's
11	  first commit. Sets up the cycle:
12	  - Backfill the previous cycle's chores `Commits:` ref.
13	  - Bump `Cargo.toml` to `X.Y.Z-0`.
14	  - Pick up a `## Todo` item (typically the top-ranked,
15	    #1) into `## In Progress` (bold title + succinct problem
16	    statement + plan ladder).
17	  - Open the [chores section](#chores-sections).
18	- **[Work-N](#work-n)** (`X.Y.Z-1`, `X.Y.Z-2`, …) — the
19	  commits that implement the change. As many as the change
20	  needs; each runs through the
21	  [per-commit flow](#per-commit-flow).
22	- **[Close-out](#close-out)** (bare `X.Y.Z`) — the cycle's
23	  last commit. Bookkeeping only:
24	  - Move the picked-up item to a one-line entry in
25	    `## Done`.
26	  - Move the `## In Progress` block into the
27	    [chores section](#chores-sections).
28	  - Optionally update `notes/README.md` if functionality
29	    changed.
30	
31	A cycle's commits are published to the project remote
32	either incrementally or as one batch at close-out; the
33	result must always be published at close-out. See
34	[Pushing](#pushing).
35	
36	**Sub-cycles.** When a Work commit's scope grows enough to
37	warrant its own ladder, it subdivides — `X.Y.Z-3.0`
38	Preparation, `X.Y.Z-3.1` / `X.Y.Z-3.2` Work, `X.Y.Z-3`
39	Close-out. The same three-phase shape applies recursively
40	at every depth. See [Numbering](#numbering) for the
41	suffix rule and [Sub-cycle ladders](#sub-cycle-ladders)
42	for the local-ladder mechanics.
43	
44	## Chores sections
45	
46	A **chores section** is a `##` section in
47	`notes/chores/chores-NN.md` recording one cycle:
48	
49	- One section per cycle is the default.
50	- Per-commit sections (one section per commit) are a
51	  deliberate alternative.
52	
53	The phrase **"Open" the chores section** means append a
54	`##` header to the current `notes/chores/chores-NN.md`
55	with the cycle's anticipated close-out title (e.g.
56	`## refactor: foo bar (X.Y.Z)`). The body is empty;
57	content arrives at close-out (see [Close-out](#close-out)).
58	
59	Fuller chores conventions (content rules, header sync,
60	design subsection pattern, `Commits:` formatting) live in
61	AGENTS.md [Chores conventions](../AGENTS.md#chores-conventions).
62	
63	## Preparation
64	
65	The cycle's first commit (`X.Y.Z-0`):
66	
67	- **Backfill the previous cycle's chores section
68	  `Commits:` ref** — see
69	  [Chores commit references](../AGENTS.md#chores-commit-references).
70	- **Bump the version** in `Cargo.toml` to `X.Y.Z-0`.
71	- **Update `Cargo.lock`** to match — run `cargo build`
72	  (or `cargo check`) so the lockfile's `vc-x1` version
73	  tracks `Cargo.toml` in the same commit.
74	- **Move a `## Todo` item** (if the cycle has one) into
75	  `## In Progress` and the todo item should have:
76	  - A **bold title line** — that will be the chores
77	    section header, minus the `## ` prefix.
78	  - A **succinct problem statement**; add if one is needed
79	  - A **plan ladder**.
80	- **Open the [chores section](#chores-sections)** —
81	  append a `##` header with the cycle's anticipated
82	  close-out title.
83	
84	## Work-N
85	
86	The cycle's work commits (`X.Y.Z-1`, `X.Y.Z-2`, …)
87	implement the change. As many as needed:
88	
89	- Each commit runs through the
90	  **[per-commit flow](#per-commit-flow)**.
91	- **Interim pushes** are optional (backup, progress
92	  visibility).
93	- Close-out is the only mandatory push (see
94	  [Pushing](#pushing)).
95	- **Subdivide into a sub-cycle** if a Work commit's
96	  scope grows enough (see
97	  [Sub-cycle ladders](#sub-cycle-ladders)).
98	
99	## Close-out
100	
101	The cycle's last commit (bare `X.Y.Z`) does bookkeeping
102	only — the commit body describes that bookkeeping, not
103	what happens post-squash:
104	
105	- **Move the picked-up item** from `## In Progress` to a
106	  one-line entry (with a chores `[N]` ref) in `## Done`.
107	- **Move the `## In Progress` block into the
108	  [chores section](#chores-sections)** (the title-only
109	  placeholder opened during Preparation):
110	  - Cut the problem statement + plan ladder out of
111	    `## In Progress` (drop the bold title line — the
112	    chores `##` header already carries that string).
113	  - Paste under the chores `##` header.
114	  - Sync the chores header to the **final** commit title
115	    if the cycle's scope shifted; update every anchor
116	    back-reference.
117	  - Add an `### As-built ladder` listing the cycle's
118	    commits; optional `### Outcome` notes.
119	  - Replace `## In Progress` with
120	    `_No cycle currently in progress._`.
121	- **Update `notes/README.md`** if functionality changed
122	  (new flags, new subcommands, changed behavior).
123	
124	Whether to **squash** the cycle into one commit before the
125	publishing push, or push as-is, is decided at push time —
126	see [Pushing](#pushing).
127	
128	## Numbering
129	
130	The version suffix on each commit encodes its phase —
131	the **final identifier `0` marks a Preparation**:
132	
133	- `X.Y.Z-0` — Preparation
134	- `X.Y.Z-1`, `X.Y.Z-2`, … — Work commits
135	- `X.Y.Z` — Close-out (bare version, no suffix)
136	
137	Disambiguation:
138	
139	- `-10` — Work commit #10 (final identifier `10`), not a
140	  Preparation.
141	- `-1.0` — Preparation of the `-1` sub-cycle (final
142	  identifier `0`).
143	
144	**Nesting.** Sub-cycles append another level, recursively:
145	
146	- `X.Y.Z-3.0` — Preparation of the `-3` sub-cycle
147	- `X.Y.Z-3.1`, `X.Y.Z-3.2` — its Work
148	- `X.Y.Z-3` — its Close-out
149	- `X.Y.Z-3.1.0` — Preparation of the `-3.1` sub-sub-cycle
150	
151	Sub-cycles needing no Preparation omit `.0` (`-3.1`,
152	`-3.2`, `-3`); one that grows a Preparation later adds
153	`-3.0` without renumbering siblings.
154	
155	Bump `Cargo.toml` at the start of each phase so `vc-x1 -V`
156	reports the active phase at build time.
157	
158	## Per-commit flow
159	
160	Every commit (Preparation, each Work commit, Close-out) goes
161	through:
162	
163	1. **Mark this commit `(current)`** as the first edit in
164	   `notes/todo.md > ## In Progress`.
165	2. **Do the work** (see [Iterative work](#iterative-work)
166	   for the loop-and-squash technique).
167	3. **Flip this commit `(current)` → `(done)`** in `## In
168	   Progress` — before the cargo cycle and the commit.
169	4. **Cargo cycle** (skip-able for purely-docs commits; full
170	   cycle mandatory at close-out):
171	   1. `cargo fmt`
172	   2. `cargo clippy --all-targets -- -D warnings`
173	   3. `cargo test`
174	   4. `cargo install --path . --locked`
175	   5. (re-test if anything substantive changed)
176	5. **Work review.** Stop *before* writing any description;
177	   tell the user "ready to commit." The user reviews the
178	   changes and we iterate until complete.
179	6. **Write the commit description** — see
180	   [Commit description](#commit-description).
181	7. **Commit Description review.** Show the title + body
182	   and stop. The user reviews the description. Iterate.
183	8. **Commit.** `jj commit -m "title" -m "body" -R .` for
184	   the app repo, `-R .claude` for the bot repo (`-R` last
185	   keeps the verb visible):
186	
187	   ```
188	   jj commit -m \
189	   "<type>: <short description> (<version>)" \
190	   -m "<intro paragraph>
191	
192	   - file1: gist
193	   - file2: gist
194	
195	   ochid: /.claude/<chid>" \
196	   -R .
197	   ```
198	
199	**Two overrides apply:**
200	
201	- **Deviation or question** — any time the work deviates
202	  from the agreed plan, or a question arises, stop and
203	  surface it; don't push through.
204	- **ESC-ESC** — the user can interrupt at any point to pull
205	  a review or question forward.
206	
207	## Commit description
208	
209	[Conventional Commits](https://www.conventionalcommits.org/)
210	with a version suffix:
211	
212	```
213	<type>: <short description> (<version>)
214	```
215	
216	### Title
217	
218	- ≤50 chars total (version suffix counts).
219	- Common types: `feat`, `fix`, `refactor`, `test`,
220	  `docs`, `chore`.
221	- Favor terse phrasings.
222	
223	### Body
224	
225	[Prose form](../AGENTS.md#prose-form) (intro + bullets),
226	wrap ≤72. Bullet content differs per repo:
227	
228	- **App-repo body**: file-by-file. One bullet per file
229	  changed (file plus a one-line gist). Sub-bullets for
230	  files with multiple distinct changes:
231	
232	  ```
233	  - path/to/file1
234	    - first distinct change
235	    - second distinct change, wrapping to next line
236	       with continuation indented 5
237	  ```
238	
239	  The file-by-file list is the source of truth for the
240	  cycle's mechanical change record. Chores carries the
241	  narrative + design, not a copy of it. Promote any
242	  "why" beyond one sentence to a chores `###` subsection.
243	
244	- **Session-repo (`.claude`) body**: bullets describe
245	  in-session activity rather than code changes.
246	
247	### Trailer
248	
249	`ochid:` as the last line of the body — see
250	[Cross-repo linking (ochid trailers)](../AGENTS.md#cross-repo-linking-ochid-trailers)
251	in AGENTS.md for the convention.
252	
253	For breaking changes, use the hyphenated `BREAKING-CHANGE:`
254	trailer key. `BREAKING CHANGE:` (with a space) is the only
255	space-separated key the Conventional Commits spec allows; the
256	hyphenated form is also valid and avoids the space ambiguity.
257	
258	## Reviewing changes
259	
260	Work review looks at the **uncommitted working-copy diff**,
261	on the way to commit. The user opens diffs in their
262	editor (Zed, VSCode); jj commands are for terminal:
263	
264	- `jj diff` — working-copy diff (uncommitted)
265	- `jj diff -r @-` — diff of the previous commit
266	- `jj diff --from <X> --to <Y>` — any two revisions
267	- `jj show -r <X>` — description + diff for one rev
268	
269	Don't `jj edit -r @-` to view a past commit — that marks
270	it mutable and shifts `@`; use `jj diff -r @-` or
271	`jj show -r @-`.
272	
273	See [Sub-cycle ladders](#sub-cycle-ladders) for the
274	close-out squash recipe and recovery; revset primitives
275	are in [`jj-tips.md`](jj-tips.md#revsets).
276	
277	## Pushing
278	
279	### Policy
280	
281	Push is **discretionary** during the cycle (backup,
282	progress visibility) and **mandatory at close-out** —
283	the cycle's result must be published.
284	
285	### Shape at close-out push
286	
287	At close-out the cycle's *work* is done; its *published
288	shape* is the remaining choice, made at push time. Surface
289	the options and get user approval before pushing — once on
290	the target, changing shape is a remote rewrite (force-push,
291	needs approval), so choose deliberately.
292	
293	- **Squash to one commit** — single entry on the target.
294	  Right for straightforward changes where the Work-N is
295	  focused on one or two files.
296	- **Merge non-ff** *(current default)* — `main` gains a
297	  merge commit (`X.Y.Z`); cycle commits stay reachable via
298	  two parents. `jj log -r ..@ -n <N>` shows the trapezoidal
299	  shape. See [Merge non-ff recipe](#merge-non-ff-recipe)
300	  for the full setup sequence.
301	- **Keep separate** — one commit per cycle entry on
302	  `main`. Use when the decomposition itself is
303	  informative. Each chores section keeps its own header /
304	  `Commits:` ref; no consolidation churn.
305	
306	Set up squash/merge before invoking `vc-x1 push`; use
307	`jj git push` directly for non-standard shapes.
308	
309	### Merge non-ff recipe
310	
311	Setting up a [Merge non-ff](#shape-at-close-out-push)
312	close-out is a fixed sequence. `<closeout>` is the cycle's
313	close-out commit, `<prev>` the previous cycle's close-out
314	(the current `main` tip), `<work-tip>` the cycle's last
315	Work commit:
316	
317	1. **Rebase the close-out into a merge** — `jj rebase -r
318	   <closeout> --onto <prev> --onto <work-tip>`.
319	   - `-r <closeout>` keeps the `<closeout>` commit in place.
320	   - `--onto <prev>` becomes its first parent (trunk).
321	   - `--onto <work-tip>` becomes the second parent.
322	
323	   Together these make `<closeout>` a merge of
324	   `<prev>` + `<work-tip>`, forming a trapezoidal commit.
325	2. **Use `jj new <merge>`** to add an empty `@` above the
326	   merge. The rebase left `@` *on* the now-content-bearing
327	   merge, which git/IDE diff views show as uncommitted;
328	   `jj new` restores the clean empty `@` on top.
329	3. **Push** — `jj git push --bookmark main -R .`.
330	
331	**Post-hoc caveat.** If the cycle was already pushed
332	[Keep separate](#shape-at-close-out-push) its commits are
333	immutable: the rebase needs `--ignore-immutable` and the
334	push force-updates `main`.
335	The standard sequence assumes the merge is set up *before*
336	the close-out push.
337	
338	### vc-x1 push wrapper
339	
340	`vc-x1 push <bookmark>` wraps per-push mechanics. See
341	`vc-x1 push --help` for current flags.
342	
343	**Current limitation**: only fully supports the
344	[Keep separate](#shape-at-close-out-push) shape; other
345	shapes need manual jj steps. Improvements tracked /
346	planned:
347	
348	- N:1 code↔bot for Merge non-ff (`## Todo` entry P1).
349	- Symmetric squash (planned, to be captured in `-2`).
350	- Per-repo bookmark names (planned).
351	
352	### .claude cadence
353	
354	**Cadence**: one push = one `.claude` commit, paired
355	with every code commit in that push.
356	
357	The `.claude` working copy accumulates session data
358	across the cycle; its change ID stays stable across
359	snapshots, `jj describe`, and the finalize commit, so
360	code-side `ochid:` trailers resolve.
361	
362	`.claude` is a linear journal — all session work lives
363	on `main`, regardless of the app-side bookmark. **Do not
364	create or maintain `.claude` bookmarks that mirror
365	app-side branches** — risks the bot steering session
366	pushes to the wrong remote ref.
367	
368	Ending a session: if the user runs `/exit` there will be
369	session information created, which we don't worry about.
370	The user can close the terminal instead and `@` will
371	remain empty.
372	
373	### Bot communication at the reviews
374	
375	Use plain prose — no insider jargon ("Gate N signal",
376	"Checkpoint N", etc.):
377	
378	- **At Work review** — summarize what changed and stop.
379	  "Work complete. Please review."
380	- **At Commit Description review** — present `$TITLE`
381	  and `$BODY` explicitly; ask permission to commit/push.
382	  Don't spell out the full `vc-x1 push ... --title ...
383	  --body ...` invocation by default.
384	- **At Post close-out review** — surface the shape
385	  options (squash / merge / keep) and the push target;
386	  wait for the user's choice before any `jj squash` /
387	  `jj rebase` / `jj git push` invocation.
388	
389	### After push or finalize: stop and wait
390	
391	After you **push** (cross the remote boundary) or launch
392	**finalize** on the `.claude` repo (`vc-x1 finalize --repo
393	.claude --squash --push <bookmark> --delay 10 --detach`) — by
394	hand or via the `vc-x1 push` wrapper — you **MUST NEVER**
395	proceed (next step, edit, tool call, text output) until the
396	user explicitly directs you to continue. **Even when the next
397	step seems obvious — wait.** Treat push-or-finalize as a hard
398	stop for the whole turn.
399	
400	`vc-x1 push` performs both as its tail stages — `push-app`
401	then the detached `vc-x1 finalize` on `.claude` — so there is
402	no gap left to speak in once the push is invoked. Put **all**
403	closing words *before* invoking it; do not purposely emit anything
404	after the tool returns.
405	
406	Why (`.claude` is the live journal finalize snapshots →
407	squashes → pushes):
408	
409	- **`--detach`**: lets the tool return immediately so the
410	  harness can keep flushing the *trailing* session-data — the
411	  tool call's own transcript and any words emitted *before*
412	  the invoke — into the snapshot.
413	- **`--delay 10`**: gives the harness time to complete that
414	  flush before the snapshot is taken. It is **not** time for
415	  the bot to do more work.
416	- **silence**: the bot must not summarize or perform any work
417	  after the tool returns.
418	
419	**Known slip**: the bot has emitted a summary after launching
420	finalize. There is no "harmless" closing line — if it's worth
421	saying, say it *before* the invoke.
422	
423	### Recovery
424	
425	- **If push exits before `finalize-claude`** (e.g.
426	  failure between `push-app` and `finalize-claude`), run
427	  finalize by hand:
428	
429	  ```
430	  vc-x1 finalize --repo .claude --squash --push <bookmark> --delay 10 --detach --log /tmp/vc-x1-finalize.log
431	  ```
432	
433	- **Run finalize again if `@` is non-empty** after the
434	  finalize's squash-and-commit (also desirable after
435	  extra activity by the bot's agents).
436	  - Why: finalize snapshots `.claude` at `--delay`, but the
437	    bot keeps writing session data while it runs — the tool's
438	    own invocation plus the bot's closing response land
439	    *after* the snapshot.
440	  - Safe to repeat: bot session data is append-only, so a
441	    re-run never conflicts or overwrites. (This could
442	    change; it is not under the user's control.)
443	  - Fix: run `vc-x1 finalize --repo .claude --squash --push
444	    <bookmark> --delay 10 --detach` another time to capture
445	    that tail; one extra pass is generally enough.
446	  - No guarantees: events outside the bot's control can leave
447	    `@` non-empty — e.g. the bot's back end may decide to
448	    squash/consolidate session data, which can take minutes
449	    and land after the snapshot. The remedy is the same: just
450	    run finalize again. This is why a single pass is never
451	    guaranteed to leave `@` empty.
452	- **Clear push's saved state** after any out-of-band
453	  recovery — `rm .vc-x1/push-state.toml` or `vc-x1 push
454	  <bookmark> --restart` — otherwise push resumes from a
455	  stale stage.
456	- **Late code-repo tweak after `push-app` succeeded**
457	  (e.g. updating AGENTS.md or memory) requires `jj
458	  squash --ignore-immutable` and a re-push; that is a
459	  remote rewrite and needs explicit approval like any
460	  push.
461	
462	## Iterative work
463	
464	When work for a single commit (the **target**) benefits
465	from incremental review, loop:
466	
467	1. `jj new -R .` — fresh empty `@` on top of the target.
468	2. Make the next round of changes.
469	3. User reviews the round (see
470	   [Reviewing changes](#reviewing-changes)).
471	4. `jj squash -R .` folds into the target and creates a
472	   new empty `@`.
473	5. If not done, go to step 2.
474	
475	Same jj mechanics as a
476	[sub-cycle ladder](#sub-cycle-ladders), but at
477	single-commit scope — the cycle's version suffix
478	doesn't change.
479	
480	## Sub-cycle ladders
481	
482	When a Work commit subdivides into a sub-cycle (see
483	[Numbering](#numbering) for suffix nesting), its Work
484	commits typically live as a local jj `@` chain and
485	**collapse into the sub-cycle's Close-out** before the
486	parent cycle continues. Ladder commits are scratch —
487	for review and bisection only.
488	
489	### Per-Work-commit contract within a ladder
490	
491	For each Work commit in the ladder:
492	
493	1. `jj new -R .` — create a fresh empty `@`.
494	2. Do the commit's work.
495	3. Run `cargo test --bins`. **Non-negotiable** — build
496	   and clippy alone miss regressions until a later
497	   commit runs the full suite, raising bisection cost.
498	4. `jj describe -m "..." -m "..." -R .` — working title
499	   only (no version suffix); the sub-cycle Close-out
500	   collects everything into one final commit with the
501	   `(X.Y.Z-N)` marker.
502	
503	### Navigating the ladder
504	
505	Common moves:
506	
507	- `jj log -r '<base>::' -R .` — see the whole ladder
508	  from its base.
509	- `jj edit -r <prefix> -R .` — jump `@` to any ladder
510	  commit by chid prefix; useful for bisection.
511	- `jj edit @-- -R .` — quick-jump back two commits.
512	- `jj diff -r <chid> -R .` — review one commit in
513	  isolation.
514	
515	Modifications to any ladder commit rewrite it in place;
516	descendants auto-rebase.
517	
518	### Close-out: squash the ladder
519	
520	When all ladder Work commits are done and tests pass:
521	
522	```
523	jj squash --from "<base>..@-" --into @ -u -R .
524	```
525	
526	`<base>` is the parent of the first ladder commit; `-u`
527	keeps `@`'s description and discards the sources'.
528	After squash, history is linear: `<base> → @`;
529	intermediate commits are auto-abandoned.
530	
531	Then `vc-x1 push <bookmark>` as for any other commit.
532	
533	For N = 1 the squash is a no-op (`<base>..@-` is empty
534	when `@-` is `<base>`); push the single commit directly.
535	
536	### Recovery
537	
538	If a ladder commit goes wrong, back out without losing
539	prior commits:
540	
541	- **Discard the current commit.** `jj abandon @ -R .`
542	  drops it; you get a fresh empty `@` on the same
543	  parent.
544	- **Edit an earlier commit.** `jj edit -r <chid> -R .`,
545	  make corrections, then `jj edit -r <last-ladder-chid>`
546	  to return. Descendants auto-rebase.
547	- **Discard the entire ladder.** `jj op log -R .` shows
548	  the op history; `jj op restore <op-id> -R .` reverts
549	  to that point. Full undo — removes *all* ladder work
550	  after the chosen op. Use only to start over.

157	## Why `jj log` shows fewer commits than `gitk`
158	
159	If you're coming from git, jj's log output can be surprising compared to
160	tools like `gitk --all`.
161	
162	jj tracks *changes* (identified by change IDs), not individual git commits.
163	When you rewrite a change (`jj describe`, `jj rebase`, `jj squash`, etc.),
164	jj creates a new git commit and keeps the old one under `refs/jj/keep/*` as
165	undo history. `gitk --all` sees all of these obsolete commits; `jj log` only
166	shows the current version of each change.
167	
168	## Useful commands
169	
170	| Command | Description |
171	|---------|-------------|
172	| `jj log` | Show recent visible commits (default revset) |
173	| `jj log -r ::@` | Show **all** ancestors of the working copy |
174	| `jj log -r 'all()'` | Show all non-hidden commits (needed if you have multiple heads/branches) |
175	| `jj st` | Show the status of the Working and Parent commits |
176	| `jj st -r <chid>` | Status of the commit, `<chid>` such as `@`, `@-`, `xyz` |
177	| `jj show` | Show the Working commit (`-r @`) |
178	| `jj show -r <chid>` | Show the commit, `<chid>` such as `@`, `@-`, `xyz` |
179	| `jj evolog -r <chid>` | Show the evolution history of a single change |
180	| `jj op log` | Show operation history (each rewrite operation) |
181	
182	
183	In a single-branch workflow, `jj log -r ::@` and `jj log -r 'all()'` give
184	the same result. Use `all()` when you have multiple branches or heads.
185	
186	## Revsets
187	
188	Revsets (sets of revisions) are how jj addresses commits. A
189	revision is identified by `@`, a chid, or a cid, and revsets are
190	built from those identifiers plus the operators `-`, `+`, `..`,
191	and `::`. There is a complete language available — see
192	`jj help -k revsets`. The [`substep-test.sh`](substep-test.sh)
193	script scaffolds the example repo used below.
194	
195	Summary:
196	
197	- A revision (rev) is used for addressing/referring to commits.
198	- jj supports a change_id (chid) and commit_id (cid).
199	  - The chid is permanent and doesn't change.
200	  - The cid is the SHA of the current commit and changes with any
201	    change to it or its ancestors.
202	- A revset is a set of revisions.
203	- In many jj commands revsets can address multiple commits.
204	- There is one root commit; chid=zzz sha=0 owner=root.
205	- The root commit never has content nor description.
206	- There can be multiple independent lineages of commits off root():
207	  - to create:
208	    - `jj new 'root()'`
209	    - `git switch --orphan <name>`
210	  - to see these:
211	    - `jj log -r 'roots(~root())'`
212	    - `git log --all --max-parents=0 --oneline`
213	
214	The examples below show these primitives in action.
215

244	### Referencing commits with relative revsets
245	
246	```
247	$ jj log -r @
248	@  vktlnyvm count 1
249	$ jj log -r @-
250	○  nvwytkrw base | count 0
251	$ jj log -r @--
252	◆  zzzzzzzz root() 00000000
253	$ jj log -r @+
254	○  wxtmosqz count 2
255	$ jj log -r @++
256	○  tkpvsrop count 3
257	$ jj log -r @+++      # empty — nothing that far out
258	$ jj log -r @---      # empty
259	$ jj log -r @..
260	○  tkpvsrop count 3
261	○  wxtmosqz count 2
262	$ jj log -r @::
263	○  tkpvsrop count 3
264	○  wxtmosqz count 2
265	@  vktlnyvm count 1
266	$ jj log -r ..@
267	@  vktlnyvm count 1
268	○  nvwytkrw base | count 0
269	$ jj log -r ::@
270	@  vktlnyvm count 1
271	○  nvwytkrw base | count 0
272	◆  zzzzzzzz root() 00000000
273	```
274	
275	#### Interpretation
276	
277	- `@-` and `@--` resolve to single revisions: parent and
278	  grandparent of @. `@+` and `@++` are children. The blank output
279	  for `@+++` and `@---` is the empty revset — there is no revision
280	  that far away in this chain.
281	- `@..` and `@::` are ranges going outward from @ toward
282	  descendants:
283	  - `@..` is the *open* form: descendants of @, **excluding** @
284	    itself (here: count 2 and count 3).
285	  - `@::` is the *closed* form: descendants of @, **including** @
286	    itself (here: @=count 1, count 2, count 3).
287	- `..@` and `::@` are ranges going inward from some implicit start
288	  toward ancestors of @:
289	  - `..@` includes @ and its ancestors but **excludes** the root
290	    commit (here: @=count 1, base=count 0).
291	  - `::@` includes the root commit as well.
292	
293	Mnemonic: `..` and `::` both produce ranges; `::` includes the
294	implicit endpoint (root or visible heads), `..` excludes it. The
295	named operand is always part of the result on the target side; on
296	the source side it depends on which dot-form is used (excluded by
297	`..`, included by `::`).

300	
301	```
302	$ jj log -r v          # unambiguous prefix of vktlnyvm
303	@  vktlnyvm count 1
304	$ jj log -r vktln
305	@  vktlnyvm count 1
306	$ jj log -r w+         # w matches wxtmosqz, + takes its child
307	○  tkpvsrop count 3
308	$ jj log -r w--
309	○  nvwytkrw base | count 0
310	$ jj log -r w..
311	○  tkpvsrop count 3
312	$ jj log -r ..w
313	○  wxtmosqz count 2
314	@  vktlnyvm count 1
315	○  nvwytkrw base | count 0
316	$ jj log -r w::
317	○  tkpvsrop count 3
318	○  wxtmosqz count 2
319	$ jj log -r ::w
320	○  wxtmosqz count 2
321	@  vktlnyvm count 1
322	○  nvwytkrw base | count 0
323	◆  zzzzzzzz root() 00000000
324	```
325	
326	#### Interpretation
327	
328	- `v` and `vktln` both resolve to chid `vktlnyvm` because they are
329	  unambiguous prefixes within this repo — no other chid starts
330	  with those letters.
331	- `w+` resolves in two stages: `w` matches `wxtmosqz` (count 2) by
332	  prefix, then `+` takes its child, giving count 3.
333	- `w--` grandparent of w.
334	- `w..` descendants of w, excluding w.
335	- `..w` ancestors of w, not including root.
336	- `::w` ancestors of w, including root.
337	- `w::` descendants of w, including w.
338	
339	Prefix rule: jj rejects ambiguous prefixes. If two chids both
340	start with the same letters, the prefix must be lengthened until
341	exactly one chid matches.

343	## Cross-repo Linking with Git Trailers
344	
345	Commits in each repo use [git trailers](https://git-scm.com/docs/git-interpret-trailers)
346	to cross-reference their counterpart in the other repo. The `ochid`
347	(Other Change ID) trailer contains a workspace-root-relative path
348	and jj changeID:
349	
350	```
351	ochid: /.claude/xvzvruqo   # points to a .claude repo change
352	ochid: /wtpmottv            # points to an app repo change
353	```
354	
355	Paths always start with `/` (the workspace root, i.e.
356	vc-template-x1). Each repo has a `.vc-config.toml` that
357	identifies its location within the workspace, so tools can
358	resolve these paths locally.
359	
360	For the full convention — path syntax, per-commit mechanics, and
361	`.vc-config.toml` — see
362	[Cross-repo linking (ochid trailers)](../AGENTS.md#cross-repo-linking-ochid-trailers).
