   223→/// Apply spec parameters to a cargo command
   224→pub fn apply_spec_to_command(
   225→    cmd: &mut Command,
   226→    spec: &Spec,
   227→    workspace: &Path,
   228→    release: bool,
   229→    expanded_target_dir: Option<&str>,

   269→
   270→    // If no profile in spec but release flag passed, use release
   271→    if !has_profile && release {

   273→    }

   276→    let mut rustc_flags: Vec<String> = Vec::new();
   277→
   278→    // Handle high-level panic mode (rustc -C flag)

   280→        && let Some(panic_value) = panic_mode.rustc_panic_value()
   281→    {
   282→        rustc_flags.push(format!("-C panic={}", panic_value));

Great question. Let me lay out the granularity levels that actually exist in Rust/cargo today:

**Level 1: Workspace** — applies to everything
- `RUSTFLAGS` env var (affects all crates compiled)
- `cargo --config 'profile.release.opt-level=3'`
- `.cargo/config.toml` settings

**Level 2: Package** — per-dependency profile overrides
- `[profile.release.package.foo]` in workspace `Cargo.toml`
- Only supports: `opt-level`, `codegen-units`, `overflow-checks` (subset!)
- This is how you say "compile `regex` at opt-level 2 but my code at opt-level 3"

**Level 3: Crate/target** — not really a distinct level in cargo
- A package's targets (lib, bin, examples) all share the same profile settings
- No way to say "compile my lib at O3 but my bin at Oz"

**Level 4: Function** — very limited, mostly nightly
- Stable: `#[inline]`, `#[inline(always)]`, `#[inline(never)]`, `#[cold]`, `#[target_feature(enable = "avx2")]`
- Nightly: `#[optimize(size)]`, `#[optimize(speed)]` — this is the closest to what you're describing
- No per-function panic strategy, LTO, codegen-units, etc.

**Level 5: Block** — nothing exists here

So the honest answer is: **cargo's narrowest granularity is per-package** (level 2), with a restricted subset of options. Rustc itself doesn't offer per-file control. The function-level attributes on nightly (`#[optimize]`) are the closest thing to your "compile this block with option=x" vision, but they only cover optimization strategy, not the full profile.

Given this reality, tspec's sections should probably map to:

| Section | Controls | Mechanism | Granularity |
|---|---|---|---|
| `[cargo]` | Profile settings, target, unstable flags | `--config`, `--target`, `-Z` | Package (via cargo) |
| `[rustc]` | Raw codegen flags cargo can't express | `RUSTFLAGS` / `-C` flags | Workspace* |
| `[linker]` | Link-time args, version scripts | `build.rs` / `-C link-arg` | Package |

*`RUSTFLAGS` is actually workspace-wide — it affects all crates in the build, including dependencies. That's a real footgun today.

This reframes the overlap problem: moving `opt_level`, `lto`, `codegen_units` into `[cargo.profile.*]` is strictly better because cargo applies them per-package, while `RUSTFLAGS` bleeds into dependencies. The `[rustc]` section should be reserved for things cargo profiles genuinely can't express (raw `-C` flags, experimental options).

> AGENT

Now I can answer precisely. Here's the flow for `tspec compare` on a workspace:

**For each package**, it calls `build_package()` which does this in order:

1. **Load the spec** — `load_spec(path)` parses the `.ts.toml`
2. **Linker** (`[linker]`) — applied **first**, before cargo runs. If `linker.args` is non-empty and no user `build.rs` exists, tspec *generates a temporary `build.rs`* with `cargo:rustc-link-arg-bin=<name>=<arg>` directives. This is per-binary scoped.
3. **Cargo command** (`[cargo]`) — applied as CLI args to the `cargo build` invocation:
   - `cargo.profile` → `--release` (or nothing for debug)
   - `cargo.target_triple` → `--target <triple>`
   - `cargo.target_json` → `-Z json-target-spec --target <path>`
   - `cargo.unstable` → `-Z <flag>` each
   - `cargo.target_dir` → `--target-dir <path>`
4. **Rustc** (`[rustc]`) — applied **last**, all collected into a single `RUSTFLAGS` env var:
   - `opt_level` → `-C opt-level=N`
   - `panic` → `-C panic=abort`
   - `lto` → `-C lto=true`
   - `codegen_units` → `-C codegen-units=N`
   - `flags` → passed through raw
   - `build_std` → actually a cargo `-Z` flag, not rustc

**The scope problem:**

```
[cargo]   → scoped to THIS package's cargo invocation  ✓
[linker]  → scoped to THIS package's binary             ✓
[rustc]   → RUSTFLAGS bleeds into ALL dependencies       ✗
```

So when you run `tspec compare -w` on a workspace with packages A and B, each having different specs:
- Package A's `[rustc]` settings (via RUSTFLAGS) affect A **and all of A's deps**
- Package B's `[rustc]` settings affect B **and all of B's deps**
- If A and B share deps, whichever builds second may use cached artifacts from the first (with the wrong RUSTFLAGS), unless target-dir isolation saves you

This is why moving `opt_level`, `lto`, `codegen_units`, `panic` from `[rustc]` into `[cargo.profile.*]` (via `cargo --config`) matters — cargo profiles are properly scoped per-package. The `[rustc]` section should shrink to only truly raw flags that have no cargo profile equivalent.

Now let me look at `apply_spec_to_command` again to see how both panics interact.

Looking at `cargo_build.rs:278-283` and `cargo_build.rs:300-307` — the global `panic` (PanicMode) emits `-C panic=abort` into RUSTFLAGS, and then `rustc.panic` (PanicStrategy) *also* emits `-C panic=abort` into RUSTFLAGS. If both are set, you'd get duplicate `-C panic=` flags. There's no conflict detection.

Now on your RUSTFLAGS vs `--config` question — you're right to push back. Let me be precise:

**Without per-package overrides, they're effectively the same scope.** `cargo --config 'profile.release.opt-level=3'` applies to the target package AND all its dependencies, just like `RUSTFLAGS="-C opt-level=3"` does. The blast radius is identical.

The real differences are:

1. **Per-package targeting exists** with `--config` (e.g., `profile.release.package.serde.opt-level=2`) — RUSTFLAGS has no equivalent. We don't use this today but it's the path to dependency tspecs.
2. **Settings with no `-C` flag** — `debug`, `overflow-checks`, `incremental`, `split-debuginfo` can only be set via profiles, not RUSTFLAGS.
3. **Fingerprinting** — cargo understands `--config` profile changes and recompiles correctly. RUSTFLAGS changes also trigger recompiles, but cargo treats it as a blunt "rebuild everything" signal.

So they're not different in blast radius today. `--config` is better because it's more expressive and it's the only path to per-dependency control. But I overstated the scope difference in the notes.

**Two types with different variants:**

| | Global `PanicMode` | `rustc.panic` `PanicStrategy` |
|---|---|---|
| Values | `unwind`, `abort`, `immediate-abort` | `abort`, `unwind`, `immediate-abort` |

- Global `panic` already covers all three cases correctly
- `rustc.panic` can't handle `immediate-abort` properly (misses the cargo `-Z` flag)
