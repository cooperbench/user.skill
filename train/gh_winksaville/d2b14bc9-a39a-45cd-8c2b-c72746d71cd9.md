You're right about the coupling, and it's worth naming precisely what's fused. In the current design `reserve_slot` does three things at once:

1. **Allocates message memory** — the message lives in the ring slot itself.
2. **Assigns queue position** — the reservation is the ring head; your message's FIFO order is fixed at reserve time, not send time.
3. **Starts a publication window** — the `WriteSlot` guard exclusively borrows the `Producer`, so while you hold an unsent message, you can't send *anything else*.

So "get a message" and "send it now" aren't just implied to be the same act — the borrow structure enforces it. You can abandon (drop the guard uncommitted), but you can't hold message A while sending B, and you can't reserve two and commit them in a different order. The index protocol (`producer_idx` is a single monotone counter) fundamentally can't express "slot 5 committed, slot 4 still pending" — in-order commit is baked into what makes the SPSC ring simple and correct.

That points at the fix being a **layer, not a rework of the ring**. The classic decomposition (DPDK mempool + ring, io_uring's registered buffers) is:

- **Pool** — a set of fixed-size message buffers with alloc/free. "Get a message" = take a buffer from the pool. Hold it as long as you like, fill it incrementally, or free it unsent. No queue position implied.
- **Queue** — the existing ring, but carrying small *descriptors* (buffer indices/offsets) instead of message payloads. "Send" = reserve_slot + write the index + commit, which is now a short, immediate act — the coupling that's currently a bug becomes fine, because reserve-to-commit is momentary.

And the pleasing part: in an SPSC setting the pool can itself be a second instance of the exact ring you already built — a **free ring** flowing consumer→producer (returning buffer indices) opposite the **message ring** flowing producer→consumer. Two rings + a buffer region: still zero-copy (payload bytes are written once, in the pooled buffer, never moved), still lock-free SPSC, and get/hold/send/never-send are fully decoupled. Ownership of a buffer is always unambiguous: it's either in the free ring, held by the producer, in the message ring, or held by the consumer.

The current `reserve_slot` API stays legitimate as the primitive underneath — it's the right interface *for the ring*; it was wrong only as the interface *for messaging*. The alternative — teaching the ring itself out-of-order commit (per-slot sequence numbers, Disruptor-style) — buys less and costs the simplicity of the two-counter protocol.

**"Simply mark it available" implies searching.** A per-buffer available flag makes *free* trivial but moves the cost to *alloc*: the allocator has to scan for a set flag, which is O(pool size) and touches cold lines. **LIFO's real win here is working-set size.** Your cache instinct is right, and it's worth noting *why* it beats the alternatives: a FIFO free-ring cycles through every buffer in the pool before reusing one — maximum working set, every allocation touches the coldest possible memory. **A shared stack is still an MPSC object — but a friendly one.** My "the free path is an MPSC queue" was about the concurrency shape (many pushers, one popper), not about FIFO order; a stack satisfies it fine. Concretely it's a Treiber stack: free = CAS the head offset to your buffer; alloc = pop the head. Two properties make our case the *easy* case:

- **Single popper kills ABA.** The classic Treiber hazard needs concurrent poppers. With exactly one allocator popping (the pool owner), a node at head can't be removed out from under the popper's CAS — pushes just retry it. No hazard pointers, no epochs.
- **Validation is tractable.** Cross-process, the head and next-links are untrusted, so the popper bounds-and-alignment-checks each offset before following it. A corrupt peer can lose buffers or cycle the list (allocator should cap pops per attempt), but can't make the allocator read outside the pool.

Compared to per-freeer return rings, the stack is one structure instead of N, needs no freer registration, and gets the LIFO hot-reuse that rings can't. Cost: one CAS per free/alloc — contended only when frees genuinely collide, which SPSC-phase never does.

So the free path settles as: **intrusive LIFO free-stack per pool, offset-linked, single-popper Treiber, validated pops**. That replaces both earlier options, and it also decouples nicely from the MPSC-ring roadmap item — the pool no longer waits on it.

Why attach after init, why not have init imply attaching?

> AGENT

`init` doesn't need a follow-up attach — it already implies it. `Pool::init` returns a fully usable `Pool` handle (same for `Ring::init`): the initializing side never calls `attach` at all. The two functions aren't sequential steps; they're **two doors into the same handle** for two different parties:

- **`init`** — for the region's creator. It has the memory as `&mut [u8]`, so the borrow checker *proves* exclusive access: nobody else can be watching while the header is half-written. That proof is what lets `init` be a safe function, and it returns the ready handle directly.
- **`attach`** — for everyone else: the other process (or a later re-mapping) joining a region someone else already initialized. It can't take `&mut [u8]`, because a genuinely shared `MAP_SHARED` mapping is never exclusively borrowed — a peer may be writing at any moment. Hence the raw pointer, the header validation (magic/version/geometry, which `init` doesn't need — it just wrote those), and the `unsafe` contract about mapping liveness.

So the asymmetry in signatures is the design: `init` = create + attach fused, safe by exclusivity; `attach` = join, unsafe because only the caller can vouch for the mapping.

The tempting third shape — one `open_or_create` that inits if the region looks fresh, attaches otherwise — is the one I'd argue against. "Looks fresh" means checking `magic`, and two processes racing through that check both conclude "fresh" and both initialize: a TOCTOU race the current handshake deliberately doesn't have to handle, because *who initializes* is the caller's topology decision (embedded: startup code before spawning; Linux: the creator of the shm fd inits before passing it). Making that race safe would need a CAS claim on `magic` and defined loser semantics — machinery that buys convenience, not capability. If it's ever wanted, it belongs as a third door built on the existing two, not a replacement for them.

`0.6.0-3 docs: message pool usage model` is ready to commit — and since the point of this rung is agreement, here's the model it pins down (new `### Usage model: roles and buffer lifecycle` in the messaging-layer section):

**Roles** (per object; one thread may hold several across objects — a typical sender is a pool's allocator plus a ring's producer):
- **Ring**: exactly one producer, one consumer, ever; one reserved slot at a time per endpoint.

> AGENT

Hypothesis confirmed: **8.7 ns of our 9.9 ns is just the two CASes.** The pool's round-trip is one `compare_exchange` to pop (alloc) and one to push (free), and on x86 a `lock cmpxchg` costs ~18–25 cycles *even with zero contention* — the lock prefix's ordering guarantees aren't free. Everything else we do (bounds checks, link read, the 16-byte write) fits in the remaining ~1 ns.

Now the other side: glibc's malloc fast path (tcache) is a **thread-local** free list — plain loads and stores, *zero atomic instructions*. Your "same memory each time" intuition is correct and it's true for both allocators (both LIFO-reuse the same hot chunk, L1-resident); the difference is that malloc's bookkeeping is private by construction while ours is shared by design. We pay the "a peer in another process might free into this pool right now" tax on every single operation, even in a single-threaded loop where no peer exists. Same-speed-as-malloc means the entire cost of being cross-process-capable is two locked instructions — honestly, a good deal.

And there's a well-trodden road to beating malloc if we ever want it, because malloc itself shows the trick: **put a private cache in front of the shared structure** — exactly tcache-over-arenas:

- The allocator handle keeps a small thread-private list; alloc/free hit it with plain load/store (~1–2 ns).
- Refill/flush moves buffers between the private list and the shared CAS stack **in batches** — one CAS amortized over N messages instead of per message. (Batch-pop of a linked stack does need care — you can't atomically take N nodes without walking — but batch *push* is one CAS, and refill can pop a few at a time.)
- The shared free-stack stays the cross-process truth; the cache is pure per-handle optimization, invisible to the protocol.
