Before implementing, let me lay out the design choices since the chores entry was high-level:

**Proposed shape**:

1. **Trait name & location**: `pub trait Runtime<S: BufRefStore>` in `runtime_zc.rs`. No naming conflict — legacy types are `SingleThreadRuntime`/`MultiThreadRuntime` (in `runtime.rs`).

2. **Trait surface** (minimal, matches what consumers actually call):
   ```rust
   pub trait Runtime<S: BufRefStore> {
       fn startup(&mut self, mgr: &mut ActorManager<S>, initial: Vec<(u32, PooledMsg<S>)>, pin: &[usize]) -> Handle<S>;
       fn pool(&self) -> &Pool<S>;
   }
   ```
   - `Handle<S>` stays a concrete return type. Making it a trait too adds an associated type with no current consumer needing it — out of scope per CLAUDE.md "don't design for hypothetical future requirements".
   - `RuntimeZC::new(pool)` stays as an inherent constructor (not a trait method).

3. **Inherent methods**: move `startup` and `pool` to **trait-only** (drop the inherent versions). Consumers `use actor_x1::runtime_zc::Runtime;` to bring them in scope — that's what "reach through the trait" means concretely. Without the import, code won't compile, so the seam is real, not nominal. Legacy `run` / `run_probed` stay inherent (they go in `-6`).

4. **`SignalZC::ClearProbe → ClearCount`** rename — internal only, no external impact.

5. **Touched consumers**: `goalzc.rs`, `goalzc-crit.rs`, `runtime_zc.rs` tests — add `use ... Runtime;` import; behavior unchanged.

Sound right, or do you want a different trait shape (e.g., add a `Handle` trait too, or keep methods inherent + duplicate on the trait)?
