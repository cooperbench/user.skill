   518→## Known Caveats
   519→
   520→### 1. Redundant Transcript Data Across Commits
   521→
   522→Each checkpoint stores the **full session transcript** up to that point. If a session results in multiple commits (Scenarios 3, 4, 5, 6), each checkpoint contains overlapping transcript data.
   523→
   524→**Example**: Session with 3 commits
   525→- Checkpoint 1: transcript lines 1-100
   526→- Checkpoint 2: transcript lines 1-200 (includes 1-100 again)
   527→- Checkpoint 3: transcript lines 1-300 (includes 1-200 again)
   528→
   529→**Trade-off**: This simplifies checkpoint retrieval (each is self-contained) at the cost of storage efficiency.
   530→
   531→### 2. Token Usage Sums Are Misleading
   532→
   533→Each checkpoint's `metadata.json` contains cumulative token usage for the entire session up to that point. Summing token counts across multiple checkpoints from the same session **double-counts tokens**.
   534→
   535→**Example**:
   536→- Checkpoint 1: 10,000 tokens (session total so far)
   537→- Checkpoint 2: 25,000 tokens (session total so far)
   538→- Naive sum: 35,000 tokens ❌
   539→- Actual usage: 25,000 tokens ✓
   540→
   541→**Correct approach**: Use the token count from the **last checkpoint** of a session, or track incremental deltas separately.
   542→
   543→### 3. Stashed Files Lose Shadow Content
   544→
   545→As described in Scenario 5, if files are stashed and other files are committed first, the stashed files lose their content in the shadow branch. They remain tracked by filename in `FilesTouched`, but subsequent checkpoints won't have the original file content preserved.
   546→
   547→### 4. No Per-File Prompt Attribution
   548→
   549→Checkpoints don't explicitly tag which prompt created which file. To determine this, you must parse the transcript and correlate `tool_use` entries with preceding `user` messages. The `files_touched` list in metadata is cumulative across all prompts.
   550→
   551→### 5. Carry-Forward Checkpoints Include Full Transcript
   552→
   553→When files are carried forward (Scenario 4), `CheckpointTranscriptStart` is reset to 0. This means each carry-forward checkpoint includes the **entire transcript**, not just new content since the last checkpoint.
   554→
   555→**Impact**: For long sessions with many partial commits, checkpoint storage grows linearly with session length × number of commits.
   556→
   557→### 6. Crash Before HandleTurnEnd Leaves Provisional Transcripts
   558→
   559→In Scenarios 2 and 3 (Claude commits during turn), checkpoints are saved with "provisional" transcripts during PostCommit. The full transcript is written at HandleTurnEnd (Stop hook).
   560→
   561→If the session crashes or is killed before the Stop hook fires:
   562→- Checkpoints exist with partial transcripts
   563→- `TurnCheckpointIDs` in session state tracks which need finalization
   564→- Next session start does **not** automatically finalize orphaned checkpoints
   565→
   566→### 7. Two Different Content-Aware Checks
   567→
   568→The system uses two separate content-aware checks with different purposes:
   569→
   570→**A. Overlap Detection** (`filesOverlapWithContent`) - Determines if commit should be linked to session:
   571→- Only applies to **newly created files**
   572→- Modified files (existed in parent) **always count as overlap**
   573→- Used in PrepareCommitMsg/PostCommit for non-ACTIVE sessions
   574→- **Purpose**: Prevent linking commits where user reverted session content
   575→
   576→**B. Carry-Forward Detection** (`filesWithRemainingAgentChanges`) - Determines which files to carry forward:
   577→- Applies to **all committed files**
   578→- Compares committed content hash vs shadow branch hash
   579→- Hash mismatch = partial commit, file carried forward
   580→- **Purpose**: Enable splitting changes within a file across commits (Scenario 7)
   581→
   582→### 8. Carry-Forward Content Superseded by New Prompts
   583→
   584→When files are carried forward and then a new prompt modifies the same file:
   585→- The shadow branch gets the **new** content (from the new prompt's SaveChanges)
   586→- The carried-forward content is overwritten
   587→- Subsequent commits compare against the **new prompt's content**, not the original carried-forward content
   588→
   589→**Example**:
   590→1. Prompt 1: Agent writes 100 lines to file A
   591→2. User commits 50 lines via `git add -p`
   592→3. Carry-forward: A (with 100 lines) goes to new shadow branch
   593→4. Prompt 2: Agent adds 50 more lines to A (now 150 lines total in worktree)
   594→5. SaveChanges: Shadow branch now has A with 150 lines
   595→6. User commits: Comparison is against 150 lines, not original 100 lines
   596→
   597→This is correct behavior - the shadow branch reflects the **current combined state** of the session's work.
   598→
   599→### 9. Automatic Cleanup During Normal Operations
   600→
   601→Most orphaned data is cleaned up automatically:
   602→
   603→- **Shadow branches**: Deleted after condensation if no other sessions reference them
   604→- **Session states**: Cleaned up during session listing when shadow branch no longer exists (and session is not ACTIVE, has no `LastCheckpointID`)
   605→

   607→
   608→```bash
   609→entire clean          # Preview orphaned items
   610→entire clean --force  # Delete orphaned items
   611→```
