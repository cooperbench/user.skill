   ```go
   func GetByAgentType(agentType AgentType) (Agent, error) {
       registryMu.RLock()
       defer registryMu.RUnlock()
   ```

   **Problem**: This creates agent instances for **every** agent until it finds a match. The old map lookup was O(1), this is O(n) with unnecessary instantiations.
   
   **Suggestion**: Build a reverse map on registration:
   ```go
   var typeToFactory = make(map[AgentType]Factory)
   
   func Register(name AgentName, factory Factory) {
       registryMu.Lock()
       defer registryMu.Unlock()
       registry[name] = factory
       
       // Build reverse lookup
       ag := factory()
       typeToFactory[ag.Type()] = factory
   }
   
   func GetByAgentType(agentType AgentType) (Agent, error) {
       registryMu.RLock()
       defer registryMu.RUnlock()
       
       if factory, ok := typeToFactory[agentType]; ok {
   ```

Excellent question! Let me explain why the mutex might not be strictly necessary in this case.

## Current Registration Pattern

Looking at the code, **all `Register()` calls happen in `init()` functions**:

```go
// claudecode/claude.go
func init() {
    agent.Register(agent.AgentNameClaudeCode, NewClaudeCodeAgent)
}

// geminicli/gemini.go
func init() {
    agent.Register(agent.AgentNameGemini, NewGeminiCLIAgent)
}
```

## Why the Mutex Might Be Unnecessary

Go guarantees that:
1. **All `init()` functions complete before `main()` starts**
2. **`init()` functions run in a single goroutine** (though order within a package is deterministic by source file name)
3. **After initialization, the registry is never modified** - it's read-only

So technically, once `main()` starts and the CLI begins calling `GetByAgentType()`, there are **no concurrent writes**, only concurrent reads. **Go maps ARE safe for concurrent reads** as long as there are no concurrent writes.

## Why Keep the RWMutex Anyway?

Despite the above, keeping the `RWMutex` is still good practice:

### 1. **Race Detector Compliance**
Even though there's no actual race, Go's race detector can be conservative about map access. The mutex makes it explicit that this is thread-safe.

### 2. **Future-Proofing**
If someone later adds dynamic agent registration (e.g., plugin system, hot reload), the mutex is already in place. Without it, that would be a subtle bug.

### 3. **Low Overhead**
`RWMutex.RLock()` is **very cheap** when there are no writers:
- Just an atomic increment/decrement
- No actual blocking if no writers are active
- Multiple readers can hold it simultaneously

### 4. **Documents Intent**
The mutex signals to future maintainers: "This is shared mutable state that could be accessed concurrently."

## Could You Remove It?

**Yes, you could safely remove the mutex** for the current implementation because:
- All writes happen before `main()` (in `init()`)
- All reads happen after `main()` starts
- No concurrent writes ever occur

But I'd recommend **keeping it** because:
- The performance cost is negligible
- It's defensive programming
- It makes the code more obviously correct to readers and tools

## Alternative: Make It Truly Immutable

If you wanted to optimize further, you could make the registry immutable after init:

```go
var (
    registryMu sync.RWMutex
    registry   = make(map[AgentName]Factory)
    registryFrozen atomic.Bool  // Set to true after init
)

func Register(name AgentName, factory Factory) {
    if registryFrozen.Load() {
        panic("cannot register agents after initialization")
    }
    registryMu.Lock()
    defer registryMu.Unlock()
    registry[name] = factory
}

func GetByAgentType(agentType AgentType) (Agent, error) {
    // No lock needed if frozen - but race detector might still complain
    // So keep the RLock anyway
    registryMu.RLock()
    defer registryMu.RUnlock()
    // ...
}
```

But honestly, this adds complexity for minimal gain. **The current approach with RWMutex is the sweet spot** - simple, safe, and performant enough.

## TL;DR

The `registryMu` is **probably not strictly necessary** given that all writes happen in `init()`, but it's **good defensive programming** with negligible cost that prevents future bugs and makes the code obviously thread-safe.
