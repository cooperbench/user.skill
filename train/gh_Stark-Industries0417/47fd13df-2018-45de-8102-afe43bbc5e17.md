### FINDING 2: TOCTOU Race in Backup Logic (Severity: LOW)

**File:** `/Users/soph/Work/entire/devenv/cli/cmd/entire/cli/strategy/hooks.go`, lines 142-180

**Description:** The install logic performs a check-then-act sequence:

1. Line 147: `backupExists := fileExists(backupPath)` -- checks if backup exists
2. Line 149: `existing, existingErr := os.ReadFile(hookPath)` -- reads hook content
3. Line 160: `os.Rename(hookPath, backupPath)` -- renames hook to backup

Between step 1 and step 3, another process (e.g., a concurrent `entire enable`, another hook manager like husky, or a concurrent git operation) could create or remove the backup file or modify the hook file.

Specific race scenarios:
- **Backup overwrite:** Between `fileExists(backupPath)` returning false and `os.Rename(hookPath, backupPath)`, another process could create a backup at `backupPath`. The `os.Rename` would silently overwrite it, losing the other process's backup.
- **Hook change:** Between `os.ReadFile(hookPath)` and `os.Rename(hookPath, backupPath)`, the hook file content could change. The backed-up content would differ from what was read.

**Impact:** In practice, this race window is extremely narrow and would require highly unusual concurrent operations on git hooks. Git hooks are typically modified during interactive setup, not in hot paths. The risk is LOW.

**Recommendation:** For full correctness, use `os.Link` + `os.Remove` or `os.Rename` with `O_EXCL`-style atomicity guarantees. Alternatively, use `os.OpenFile` with `O_CREATE|O_EXCL` to create the backup file, then copy content, to ensure no overwrite. Given the LOW risk, this is an advisory finding.

### 1. Architecture Overview

The branch `soph/better-git-hook-handling` (single commit `5a500772`) modifies `/Users/soph/Work/entire/devenv/cli/cmd/entire/cli/strategy/hooks.go` to add hook chaining behavior. Previously, `InstallGitHook` would silently overwrite any existing git hooks. The new design:

The `hookSpec` struct and `buildHookSpecs` function were introduced to eliminate the previous pattern of per-hook inline `fmt.Sprintf` blocks, consolidating hook definitions into a data-driven loop.

**Test coverage.** The test file grew from zero hook-specific tests (on main) to 16 test functions covering:

This is thorough coverage.

**Single Responsibility Principle**: Upheld. `buildHookSpecs` generates content, `InstallGitHook` handles the install orchestration (backup, chaining, writing), `generateChainedContent` handles chaining logic, `RemoveGitHook` handles teardown. Each function has a clear singular purpose.

### 4. Risk Analysis

**4a. Race condition on concurrent installs.**

If two processes call `InstallGitHook` simultaneously for the same hook that has an existing custom script:

1. Process A reads the hook, sees it is not ours, checks `!backupExists` -> true
2. Process B reads the hook, sees it is not ours, checks `!backupExists` -> true  
3. Process A renames hook to `.pre-entire`
4. Process B tries to rename hook to `.pre-entire` -- the hook file no longer exists at the original path. `os.Rename` fails with ENOENT.

The current code returns the error, which is a reasonable outcome. The backup file from process A is intact. Process B's partial failure leaves `installedCount` at whatever hooks succeeded before this one. The function returns early with that count and the error. On a subsequent install attempt, the code would see our hook is already installed (from process A) and the backup exists, so it would add the chain call correctly.

**Assessment**: Low risk. Concurrent `entire enable` in the same repo is an unusual scenario, and the failure mode is benign -- a retryable error with no data loss.

**4b. Partial failure during install.**

If writing a hook file fails mid-loop (e.g., disk full), the function returns `installedCount` (hooks written so far) and the error. Some hooks will have been installed, some not. On retry, the already-installed hooks are idempotent (content comparison in `writeHookFile`), and the failed ones will be attempted again.

**Assessment**: Clean. The idempotent `writeHookFile` ensures retries converge.

**4c. State desync between hook and backup.**

The critical invariant is: if `.pre-entire` backup exists, the main hook must contain the chain call; if no backup exists, no chain call. Consider these scenarios:

- **User manually deletes the backup**: The main hook still has the chain call, which runs `if [ -x ... ]` on a nonexistent file. The `-x` test fails, the chain block is a no-op. Functionally correct but leaves dead code. On next `InstallGitHook`, `backupExists` is false, and `hookExists` is true with our marker, so the hook is regenerated without the chain call. **4d. Exit code propagation in chain call.**

The generated chain call does NOT propagate the exit code of the backed-up hook:

## Research Summary: Git Hook Installation Strategies When Pre-Existing Hooks Exist

### 1. Husky (npm, 50k+ GitHub stars)

**Approach: `core.hooksPath` redirection (avoids `.git/hooks` entirely)**

- Husky v9 (2024+) sets `core.hooksPath` to `.husky/_`, which redirects all hook resolution away from `.git/hooks` entirely.
- Hook scripts are plain shell files in the `.husky/` directory, committed to the repository.
- **Does NOT back up existing hooks.** When `core.hooksPath` is set, Git simply ignores `.git/hooks` -- existing hooks there stop running silently.
- **Does NOT chain to existing hooks.** There is no forwarding mechanism.
- **Cleanup/uninstall:** Remove the `core.hooksPath` config setting; `.git/hooks` hooks resume working.
- **Known problem:** This approach [clobbers git-lfs hooks](https://github.com/mastodon/mastodon/issues/24884), because git-lfs installs into `.git/hooks` which Husky bypasses entirely.

**Takeaway:** Husky's approach is the simplest but the least cooperative. It sidesteps the conflict rather than solving it.

Sources: [Husky docs](https://typicode.github.io/husky/), [Husky GitHub](https://github.com/typicode/husky), [Husky v9 blog](https://itenium.be/blog/dev-setup/git-hooks-with-husky-v9/), [Husky core.hooksPath issue #1574](https://github.com/typicode/husky/issues/1574)

---

### 2. pre-commit (Python, 12k+ GitHub stars)

**Approach: Backup to `.legacy` suffix + chain execution**

- When `pre-commit install` finds an existing hook that it did not create, it renames it to `<hook-name>.legacy` (e.g., `pre-commit.legacy`).
- The installed hook script runs the `.legacy` hook **first**, then runs pre-commit's hooks. Both execute sequentially.
- Uses an `is_our_script()` function that checks for a hash identifier inside the hook file to determine ownership.
- The `--overwrite` / `-f` flag skips the backup and replaces the hook outright.
- **Uninstall** (`pre-commit uninstall`) restores `.legacy` hooks back to their original names.
- This has been the behavior [for over a decade](https://github.com/pre-commit/pre-commit/issues/3450) according to the maintainer.

**Naming convention:** `<hook-name>.legacy`

**Takeaway:** This is the closest parallel to your `.pre-entire` approach. The pattern is: rename existing hook with a suffix, install your own hook, and chain-call the backup.

Sources: [pre-commit.com](https://pre-commit.com/), [pre-commit issue #3450](https://github.com/pre-commit/pre-commit/issues/3450), [DeepWiki analysis](https://deepwiki.com/pre-commit/pre-commit/2.1.2-install-and-uninstall)

### 3. Lefthook (Go, 5k+ GitHub stars)

**Approach: Backup to `.old` suffix (no chaining)**

- When `lefthook install` finds an existing hook file, it renames it by appending `.old` (e.g., `pre-commit.old`).
- Lefthook does **NOT** chain to the `.old` hook. The backup exists purely for manual recovery.
- Lefthook writes to `.git/hooks` directly (does not use `core.hooksPath`).
- Known conflicts arise when other hook managers like Husky are present, especially when `core.hooksPath` is set globally.
- Early versions simply overwrote hooks; the `.old` backup was added later in response to [user requests](https://github.com/Arkweid/lefthook/issues/75).

**Naming convention:** `<hook-name>.old`

**Takeaway:** Lefthook backs up but does not chain. This is safer than overwriting but less complete than pre-commit's approach.

Sources: [Lefthook GitHub](https://github.com/evilmartians/lefthook), [Lefthook issue #75](https://github.com/Arkweid/lefthook/issues/75), [Lefthook issue #1248](https://github.com/evilmartians/lefthook/issues/1248)

### 4. Overcommit (Ruby, 3.9k GitHub stars)

**Approach: Backup to `old-hooks/` directory + restore on uninstall**

- When `overcommit --install` runs, pre-existing hooks are moved into a `.git/hooks/old-hooks/` directory.
- The `--force` flag overwrites hooks without backup.
- **Uninstall** (`overcommit --uninstall`) restores hooks from `old-hooks/` back to their original locations.
- Overcommit does **NOT** chain to old hooks during execution -- it is an all-or-nothing replacement.
- A [bug in Ruby 2.5](https://github.com/sds/overcommit/issues/554) with the `preserve_old_hooks` method revealed the fragility of the directory-based approach.

**Naming convention:** Moved to `old-hooks/` subdirectory (preserving original filenames).

**Takeaway:** Uses a directory instead of a suffix, but fundamentally the same pattern as Lefthook (backup without chain).

Sources: [Overcommit GitHub](https://github.com/sds/overcommit), [Overcommit issue #138](https://github.com/sds/overcommit/issues/138), [Overcommit issue #554](https://github.com/sds/overcommit/issues/554)

### 5. git-lfs

**Approach: Refuse to install if hook exists**

- `git lfs install` fails with "Hook already exists: pre-push" if a pre-push hook already exists.
- The `--force` flag overwrites without backup.
- The `--manual` flag prints instructions for users to manually merge git-lfs commands into existing hooks.
- Does NOT back up, chain, or coexist automatically.

**Takeaway:** git-lfs takes the most conservative approach -- it refuses rather than risking data loss. This creates friction that users must resolve manually.

Sources: [git-lfs issue #2865](https://github.com/git-lfs/git-lfs/issues/2865), [git-lfs issue #2363](https://github.com/git-lfs/git-lfs/issues/2363)

### 6. `core.hooksPath` (Git 2.9+)

**When is it preferred?**

- `core.hooksPath` is the modern approach for **team-shared hooks** where hooks are committed to the repository (e.g., in a `.githooks/` directory).
- It is NOT appropriate for tools that install hooks on behalf of the user (like Entire CLI), because:
  - Setting `core.hooksPath` **globally disables** all `.git/hooks` hooks across all repositories.
  - It creates conflicts with other tools (git-lfs, other hook managers) that expect `.git/hooks` to work.
  - It is a global setting that affects the user's entire Git workflow.
- Writing to `.git/hooks` directly is still the correct approach for per-repository tool hooks.

Sources: [Git documentation](https://git-scm.com/docs/githooks), [DataCamp guide](https://www.datacamp.com/tutorial/git-hooks-complete-guide)

### 7. Hook Directory Pattern (`hook.d`)

- GitLab server hooks support `<hook-name>.d/` directories where multiple scripts are executed alphabetically.
- This is a **server-side** feature in GitLab, not a native Git feature.
- Git itself supports only one script per hook event -- there is no native `hook.d` support in client-side Git.
- Several community tools ([git-hooks](https://git-hooks.github.io/git-hooks/), [sane-git-hooks](https://github.com/herriojr/sane-git-hooks)) implement this pattern as wrappers.
- **Not a standard approach** for CLI tools that need to coexist with other tools.

Sources: [GitLab server hooks docs](https://docs.gitlab.com/administration/server_hooks/), [sane-git-hooks](https://github.com/herriojr/sane-git-hooks)

### Known Pitfalls of Backup-and-Chain

Based on research across all tools, the following pitfalls exist:

| Pitfall | Description | Mitigation |
|---------|-------------|------------|
| **stdin forwarding** | Hooks like `pre-push` and `pre-receive` receive data via stdin. If the chain wrapper reads stdin first, the chained hook receives empty stdin. | Pipe stdin through or use `tee`. The Entire CLI currently uses `"$@"` for argument forwarding but does not explicitly handle stdin (this is fine for the hooks it manages -- `prepare-commit-msg`, `commit-msg`, `post-commit`, `pre-push` -- since only `pre-push` uses stdin, and Entire's pre-push hook does not consume stdin). |
| **Exit code propagation** | If the chained hook fails (non-zero exit), the wrapper must decide whether to abort. | Entire CLI uses `if [ -x ... ]; then ... fi` which propagates the exit code of the chained hook. For hooks where Entire uses `|| true`, the chain call exit code is also swallowed, which is consistent. |
| **Argument forwarding** | Some hooks receive arguments ($1, $2, etc.) that must be forwarded correctly. | Entire CLI uses `"$@"` which correctly handles all argument forwarding including spaces in arguments. |
| **Concurrent tool installations** | If two tools both use the backup pattern, Tool B may back up Tool A's hook (which contains Tool A's chain call to the original). This creates a chain: Tool B -> backup (contains Tool A -> original). | Entire CLI handles this via `scanForMovedHooks()` which cleans up hooks with the Entire marker that were moved by other tools. |
| **Circular chaining** | If Tool A backs up and chains to a hook that was itself installed by Tool B, and Tool B also chains back, an infinite loop can occur. | The marker-based detection (`entireHookMarker`) prevents Entire from backing up its own hooks. |
| **Backup overwrite** | If the tool is re-installed, it might overwrite the backup with the tool's own hook. | Entire CLI explicitly checks `if !backupExists` before creating a backup -- it will never overwrite an existing `.pre-entire` file. |

### Assessment of Entire CLI's Approach

The Entire CLI's backup-and-chain pattern with `.pre-entire` suffix is **well-aligned with industry best practices**, and in several areas it is more thorough than the industry norm.

**Strengths relative to other tools:**

1. **Backup + chain is the gold standard.** Only pre-commit implements the same complete pattern (backup + automatic chain execution + restore on uninstall). Lefthook and Overcommit back up but do not chain. Husky does neither. Entire CLI matches the most comprehensive approach in the ecosystem.

2. **Tool-specific suffix (`.pre-entire`) is correct.** Pre-commit uses `.legacy`, Lefthook uses `.old` -- both are generic names that could collide if multiple tools use the same convention. Using a tool-specific suffix like `.pre-entire` is more robust and is the same pattern used in the `.pre-husky` convention (as demonstrated in the test `TestRemoveGitHook_CleansUpMovedHooks`).

3. **Marker-based ownership** (`entireHookMarker`) for both install and uninstall is the same approach used by pre-commit (`is_our_script()`), and prevents accidentally removing hooks installed by other tools.

4. **Idempotent installation** (checking if content matches before writing) is a best practice that most tools implement.

5. **Backup protection** (never overwriting an existing `.pre-entire` file) prevents data loss from repeated installations.

6. **Moved-hook cleanup** (`scanForMovedHooks`) is a unique feature that handles the case where another tool moves Entire's hooks aside -- this is not something I found in any other tool.

**One area to consider:**

- The chained hook runs **after** Entire's hook. Pre-commit runs the legacy hook **first**. There is no universal standard for ordering, and running Entire's hook first makes sense since Entire's hooks are non-destructive metadata operations. However, for `commit-msg` hooks where Entire uses `|| exit 1`, if Entire's hook fails, the chained hook never runs. This is intentional and correct (if Entire determines the commit should be aborted, chained hooks should not run).

**Overall verdict:** The `.pre-entire` backup-and-chain approach is a mature, well-tested pattern that matches or exceeds what the most sophisticated tool in the space (pre-commit) does.
