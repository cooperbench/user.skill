### What the Bug Was

The commit introduced logic that reused `PendingCheckpointID` from session state when adding checkpoint trailers to new commits. The intention was to ensure idempotent checkpoint IDs across prepare-commit-msg hook invocations. However, this caused a bug where **consecutive commits during the same session would all get the same checkpoint ID**, because `PendingCheckpointID` (set by PostCommit after condensation) would persist and be reused for subsequent commits.

### Session Log Summary (Checkpoint cff7f96ad60a)

The checkpoint contains **2 sessions** that led to this commit:

**Session 0** (planning/setup):
- Resolved merge conflicts from parent branch
- Ran `/github-pr-review`
- Pushed and created draft PR

**Session 1** (implementation - context continued):
- Implemented ENT-258: "Mid-turn commits from Claude don't receive Entire-Checkpoint trailers"
- Used TDD approach fixing 3 compounding bugs:
  1. **Path format mismatch** - transcript returns absolute paths, git returns repo-relative
  2. **PostCommit early-return** - BaseCommit wasn't updated when no trailer found
  3. **SaveChanges clearing PendingCheckpointID** - broke deferred condensation
- **During testing**, discovered a 4th issue: the integration test `TestShadow_FullTranscriptCondensationWithIntermediateCommits` failed because PendingCheckpointID was being reused across commits
- **Partial fix applied**: Changed `condenseAndUpdateState` to clear `PendingCheckpointID` after condensation, and updated `handleAmendCommitMsg` to fall back to `LastCheckpointID`
- **But the bug remained**: The `PrepareCommitMsg` and `addTrailerForAgentCommit` functions still checked `PendingCheckpointID` first before generating a new ID

### The Fix (Current Branch)

Commit `28ecf4e4` removes the `PendingCheckpointID` reuse in both locations, always generating fresh checkpoint IDs. Idempotency for hook re-runs is handled by checking if the commit message already has a trailer (not by reusing old IDs).

     5→## Git Operations
     6→
     7→### Amending Commits with `-m` Flag
     8→
     9→When you amend a commit using `git commit --amend -m "new message"`, the `-m` flag replaces the entire message including any `Entire-Checkpoint` trailer.     10→

    12→

    14→

    17→### Git GC Can Corrupt Worktree Indexes
    18→
    19→When using git worktrees, `git gc --auto` can corrupt a worktree's index by pruning loose objects that the worktree's index cache-tree references. This manifests as:
    20→
    21→```
    22→fatal: unable to read <hash>
    23→error: invalid sha1 pointer in cache-tree of .git/worktrees/<n>/index
    24→```
    25→
    26→**Root cause:** Checkpoint saves use go-git's `SetEncodedObject` which creates loose objects.     27→
    28→**Impact:**
    29→- `git status` fails in the affected worktree
    30→- Staged changes in the worktree are lost
    31→
    32→**Recovery:**
    33→```bash
    34→# In the affected worktree:
    35→git read-tree HEAD
    36→```
    37→This rebuilds the index from HEAD. Any previously staged changes will need to be re-staged.
    38→
    39→**Prevention:** Disable auto-GC and run it manually after commits (when indexes are clean):
    40→```bash
    41→git config gc.auto 0
    42→```
    43→

**The fix completely changed the multi-commit-per-turn behavior.** Before the fix, all commits within a single turn shared the same checkpoint ID, matching the intent that "multiple commits in a single prompt should be part of the same checkpoint ID." 1. **Same turn, second commit** (ACTIVE_COMMITTED + GitCommit) → reuse PendingCheckpointID
2. **New turn after prior commit** (IDLE/ACTIVE with stale PendingCheckpointID) → generate fresh ID

Here's the full picture. Let me map out what each phase does on GitCommit:

| Phase | GitCommit Action | Condensation |
|-------|---------|-------------|
| **IDLE** | `ActionCondense` | Immediate |
| **ACTIVE** | `ActionMigrateShadowBranch` | **Deferred** to TurnEnd |
| **ACTIVE_COMMITTED** | `ActionMigrateShadowBranch` | **Deferred** to TurnEnd |
| **ENDED** | `ActionCondenseIfFilesTouched` | Immediate |

Two phases already condense immediately. The deferred path only exists for ACTIVE and ACTIVE_COMMITTED — and it's the source of all the complexity.

Here's what the deferred approach requires that per-commit condensation would eliminate:

**Code that exists solely for deferred condensation:**

1. **`PendingCheckpointID` field** — the entire lifecycle (set in PostCommit `ActionMigrateShadowBranch` at line 707, consumed by `handleTurnEndCondense` at line 1483, cleared by `condenseAndUpdateState` at line 805). This was the bug source.

2. **`ACTIVE_COMMITTED` phase** — its primary purpose is signaling "condensation was deferred." Without deferred condensation, ACTIVE + GitCommit could just condense and stay ACTIVE. That's a full phase (and its ~40 lines of transition logic at lines 222-259) that could be removed.

3. **`handleTurnEndCondense` function** (lines 1465-1535) — 70 lines as a separate condensation entry point that partially duplicates PostCommit's condensation logic.

4. **Two-pass processing in PostCommit** (lines 649-739) — Pass 1 dispatches condense/discard, Pass 2 runs deferred migrations. The two-pass design exists because migrations must happen after condensations read the old shadow branch. With per-commit condensation, there's no migration — just condense, delete, done.

5. **`migrateShadowBranchIfNeeded`** — shadow branch renaming from old BaseCommit to new BaseCommit. With per-commit condensation, the old branch is condensed and deleted; the next `SaveChanges` creates a fresh one at the new BaseCommit.

6. **PrepareCommitMsg reuse logic** — the need to distinguish "same turn, reuse PendingCheckpointID" vs "new turn, generate fresh" disappears. Always generate fresh.

**What per-commit condensation would look like:**

```
State machine (simplified):
  IDLE    + GitCommit → IDLE    + [ActionCondense]        (unchanged)
  ACTIVE  + GitCommit → ACTIVE  + [ActionCondense]        (was: → ACTIVE_COMMITTED + Migrate)
  ENDED   + GitCommit → ENDED   + [ActionCondenseIfFiles]  (unchanged)
  
  ACTIVE_COMMITTED phase: removed entirely
  
PrepareCommitMsg: always generate fresh ID (current fix behavior — already correct!)
PostCommit: always condense (one code path, no two-pass)
TurnEnd: no condensation needed (just ACTIVE → IDLE)
```

**The tradeoff:**
- Each commit gets its own metadata entry instead of one shared entry per turn
- Slightly more git operations during active turns (condensation in PostCommit hook)

**But from a code complexity perspective, per-commit condensation is significantly simpler.** It eliminates `PendingCheckpointID`, the `ACTIVE_COMMITTED` phase, `handleTurnEndCondense`, the two-pass PostCommit, and shadow branch migration — all of which exist solely to support deferral. And notably, the current fix on this branch (`28ecf4e4`) already implements half of it by always generating fresh IDs.

### 1. Motivation and Problem Statement

The current architecture defers condensation when an agent is ACTIVE during a commit. This creates a complex lifecycle:

- The shadow branch must be migrated to the new HEAD (two-pass PostCommit)
