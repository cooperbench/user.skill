# Bug Report Template Research: Open Source Best Practices

## Raw Templates from Well-Regarded Projects

### 1. GitHub CLI (`cli/cli`) -- Markdown format, CLI-specific

**Source:** `github.com/cli/cli/.github/ISSUE_TEMPLATE/bug_report.md`

```markdown
---
name: "\U0001F41B Bug report"
about: Report a bug or unexpected behavior while using GitHub CLI
title: ''
labels: bug
assignees: ''
---

### Describe the bug

A clear and concise description of what the bug is. 

### Affected version

Please run `gh version` and paste the output below.

### Steps to reproduce the behavior

1. Type this '...'
2. View the output '....'
3. See error

### Expected vs actual behavior

A clear and concise description of what you expected to happen and what actually happened.

### Logs

Paste the activity from your command line. Redact if needed.

<!-- Note: Set `GH_DEBUG=true` for verbose logs or `GH_DEBUG=api` for verbose logs with HTTP traffic details. -->
```

**Notable patterns:** Combined "expected vs actual" into one section. Mentions the debug flag for verbose logs. Uses CLI-specific terminology ("Type this" rather than "Click on").

### 2. Go (`golang/go`) -- YAML form format

**Source:** `github.com/golang/go/.github/ISSUE_TEMPLATE/00-bug.yml`

```yaml
name: Bugs
description: The go command, standard library, or anything else
title: "import/path: issue title"
body:
  - type: markdown
    attributes:
      value: |
        Thanks for helping us improve! Please answer these questions and provide
        as much information as possible about your problem.

  - type: input
    id: go-version
    attributes:
      label: Go version
      description: |
        What version of Go are you using (`go version`)?
        Note: we only support the two most recent major releases.
      placeholder: ex. go version go1.20.7 darwin/arm64
    validations:
      required: true

  - type: textarea
    id: go-env
    attributes:
      label: "Output of `go env` in your module/workspace:"
      placeholder: |
        GO111MODULE=""
        GOARCH="arm64"
        ...
      render: shell
    validations:
      required: true

  - type: textarea
    id: what-did-you-do
    attributes:
      label: "What did you do?"
      description: "If possible, provide a recipe for reproducing the error.
        A complete runnable program is good. A link on go.dev/play is best."
    validations:
      required: true

  - type: textarea
    id: actual-behavior
    attributes:
      label: "What did you see happen?"
      description: Command invocations and their associated output, functions with
        their arguments and return results, full stacktraces for panics. Prefer
        copying text output over using screenshots.
    validations:
      required: true

  - type: textarea
    id: expected-behavior
    attributes:
      label: "What did you expect to see?"
      description: Why is the current output incorrect, and any additional context.
    validations:
      required: true
```

**Notable patterns:** Uses `type: input` for version (single-line). Pre-filled title pattern (`import/path: issue title`). Asks for `go env` output with `render: shell`. Explicitly says "Prefer copying text output over screenshots." Support policy note in the version field.

### 3. Kubernetes (`kubernetes/kubernetes`) -- YAML form format

**Source:** `github.com/kubernetes/kubernetes/.github/ISSUE_TEMPLATE/bug-report.yaml`

```yaml
name: Bug Report
description: Report a bug encountered while operating Kubernetes
labels: kind/bug
body:
  - type: textarea
    id: problem
    attributes:
      label: What happened?
      description: |

      required: true

  - type: textarea
    id: expected
    attributes:
      label: What did you expect to happen?
    validations:
      required: true

  - type: textarea
    id: repro
    attributes:
      label: How can we reproduce it (as minimally and precisely as possible)?
    validations:
      required: true

  - type: textarea
    id: additional
    attributes:
      label: Anything else we need to know?

  - type: textarea
    id: kubeVersion
    attributes:
      label: Kubernetes version
      value: |
        <details>
        ```console
        $ kubectl version
        # paste output here
        ```
        </details>
    validations:
      required: true

  - type: textarea
    id: cloudProvider
    attributes:
      label: Cloud provider
      value: |
        <details>
        </details>
    validations:
      required: true

  - type: textarea
    id: osVersion
    attributes:

        </details>

**Notable patterns:** Uses `<details>` blocks in pre-filled values to keep issues compact. Includes the exact commands users should run. Multiple environment sections (cloud provider, container runtime, plugins). Security disclosure note in the description.

| Related issues / references | 2/8 | Never |
| Search confirmation checkbox | 1/8 | When present |
| Terminal/shell information | 1/8 (Charm) | CLI/TUI specific |

### Must-Have Sections (present in nearly every template)

1. **Description / Summary** -- What is the bug?
2. **Steps to Reproduce** -- How do we trigger it?
3. **Expected Behavior** -- What should have happened?
4. **Actual Behavior** -- What happened instead?
5. **Version** -- Which version of the tool?

### Recommended Sections

6. **OS / Platform** -- Operating system and architecture
7. **Additional Context** -- Catch-all for anything else
8. **Logs / Debug Output** -- Error messages, stack traces

### Optional Sections

9. **Related Issues** -- Links to other issues/PRs
10. **Code / Config** -- Relevant configuration or source code
11. **Screenshots** -- Visual evidence (though CLI projects often say "prefer text output")

## Best Practices Synthesis

### Format: YAML Form (`.yml`) vs Markdown (`.md`)

**Strong recommendation: Use the YAML form format (`.yml`).**

- YAML forms (introduced by GitHub) provide structured input fields with validation
- Fields can be marked as `required`, preventing incomplete submissions
- `type: input` gives single-line fields (great for versions, OS)
- `type: textarea` gives multi-line fields with optional `render` for syntax highlighting
- `type: checkboxes` can enforce acknowledgments (e.g., "I searched existing issues")
- `type: dropdown` can constrain choices (e.g., severity levels)
- Projects that started with `.md` are migrating to `.yml` (Go, Kubernetes, Docker, Charm all use YAML now)

### CLI-Specific Best Practices

Based on patterns from GitHub CLI, Go, Docker CLI, Terraform, uv, and Charm:

1. **Tell users exactly which command to run for version/environment info.** Do not just say "paste your version." Say `Run \`entire version\` and paste the output below.` Every CLI project does this.

2. **Use `render: bash` or `render: shell` for command output fields.** This gives syntax highlighting in the rendered issue, making output easier to read.

3. **Ask about the shell and terminal environment.** Charm's template is the gold standard here for TUI applications -- it asks about terminal emulator, multiplexer (tmux), and SSH. For a CLI that uses `huh` forms, this is directly relevant.

4. **Provide CLI-specific reproduction step examples.** Docker uses `1. docker run ...`, Terraform uses `1. terraform init`. Show examples with your tool's actual commands.

5. **Mention debug/verbose flags.** GitHub CLI mentions `GH_DEBUG=true`, Terraform mentions `TF_LOG=trace`. If your CLI has a verbose or debug mode, tell users how to get verbose output.

6. **"Prefer text output over screenshots."** The Go project explicitly states this. For CLI tools, copy-pasteable terminal output is far more useful than screenshots.

7. **Ask whether it is reproducible in the latest version.** Both Go and Terraform ask users to upgrade first. This reduces noise from already-fixed bugs.

8. **Warn about sensitive information in logs/output.** Terraform explicitly says "Debug output may contain sensitive information. Please review it before posting publicly."

### Template Structure Best Practices

1. **Keep it short.** The best-received templates (uv, Charm, GitHub CLI) have 4-7 fields. Terraform's is the longest at ~10 fields and it risks form fatigue. React's is the shortest at effectively 4 sections.

2. **Front-load a brief thank-you and ground rules.** A markdown section at the top with a one-liner ("Thanks for reporting!") and links to security policy, support channels, or existing issue search.

3. **Use `type: input` for single-value fields.** Version strings, OS names -- these do not need a textarea. The Go and uv templates use `input` for version and it looks much cleaner.

4. **Use `placeholder` to show expected format.** uv's `placeholder: "e.g., macOS 14 arm64"` is immediately clear. Go's `placeholder: "ex. go version go1.20.7 darwin/arm64"` similarly.

5. **Set automatic labels.** Every template applies at least a `bug` label. More mature projects add triage labels (Docker: `status/0-triage`, React: `Status: Unconfirmed`).

6. **Use a `config.yml` to disable blank issues or redirect.** Kubernetes redirects support questions to discuss.kubernetes.io. Charm links to Discord. This keeps the issue tracker focused.

7. **Number your template files for ordering.** uv uses `1_bug_report.yaml`, `2_feature_request.yaml`. Go uses `00-bug.yml`, `01-pkgsite.yml`. This controls the order in the "New Issue" chooser.

### Anti-Patterns to Avoid

1. **Do not ask for too many fields.** Every additional required field reduces the submission rate. If a field is rarely useful, make it optional or remove it.
2. **Do not use HTML comments for instructions in YAML forms.** Use `type: markdown` sections instead -- they are always visible.
3. **Do not ask for screenshots as a primary input for CLI tools.** Ask for terminal output first.
4. **Do not leave the title field unconstrained.** Consider a title prefix (React: `Bug: `) or pattern (Go: `import/path: issue title`).

## Recommended Template for a CLI Tool (like Entire CLI)

Based on this research, here is what I would recommend for a Go-based CLI using Cobra and Charm `huh`, synthesized from the best patterns above. The template uses the YAML form format with 7 fields -- concise enough to not cause form fatigue, comprehensive enough to get actionable reports.

```yaml
name: Bug Report
description: Report an error or unexpected behavior in the CLI
labels: ["bug"]
body:
  - type: markdown
    attributes:
      value: |
        Thanks for taking the time to report a bug. Please fill out the form
        below with as much detail as possible.

        Before submitting, please:
        - Search [existing issues](https://github.com/entireio/cli/issues) to
          avoid duplicates
        - Try upgrading to the latest version to see if the issue is already fixed

  - type: textarea
    id: description
    attributes:
      label: What happened?
      description: |
        A clear description of the bug. Include the full error message or
        unexpected output. Please paste text output rather than screenshots.
    validations:
      required: true

  - type: textarea
    id: repro
    attributes:
      label: Steps to reproduce
      description: |
        Minimal steps to reproduce the behavior. Include the exact commands
        you ran.
      placeholder: |
        1. `entire enable`
        2. `entire session list`
        3. See error: "..."
    validations:
      required: true

  - type: textarea
    id: expected
    attributes:
      label: Expected behavior
      description: What did you expect to happen instead?
    validations:
      required: true

  - type: input
    id: version
    attributes:
      label: CLI version
      description: "Run `entire version` and paste the output."
      placeholder: "e.g., entire version 0.1.0 (abc1234)"
    validations:
      required: true

  - type: input
    id: platform
    attributes:
      label: OS and architecture
      description: "Your operating system and architecture (see `uname -orsm`)."
      placeholder: "e.g., macOS 15.2 arm64, Ubuntu 24.04 x86_64"
    validations:
      required: true

  - type: textarea
    id: environment
    attributes:
      label: Environment details
      description: |
        Any relevant environment details: shell (bash/zsh/fish), terminal
        emulator, terminal multiplexer (tmux/screen), Git version, or
        whether you are running over SSH.
      render: bash
    validations:
      required: false

  - type: textarea
    id: additional
    attributes:
      label: Additional context
      description: |
        Any other context, logs, or configuration that might help.
        If logs are long, please use a [GitHub Gist](https://gist.github.com/)
        and link it here. Review output for sensitive information before posting.
    validations:
      required: false
```

### Key Design Decisions in This Recommendation

- **7 fields total, 4 required** -- matches the conciseness of uv and Charm while covering all essential information
- **YAML form format** -- enforces required fields, prevents incomplete submissions
- **`type: input` for version and platform** -- single-line fields, cleaner presentation (pattern from Go and uv)
- **Environment details as optional** -- terminal/shell info is important for TUI bugs (Charm pattern) but not needed for every bug
- **Explicit commands to run** -- `entire version`, `uname -orsm` (pattern from every CLI project surveyed)
- **"Prefer text over screenshots"** guidance (Go pattern)
- **Gist recommendation for long output** (Terraform pattern)
- **Sensitive information warning** (Terraform pattern)
- **`blank_issues_enabled: false`** -- forces users through the template (Kubernetes pattern)

## Design Decisions

| Decision | Rationale |
|----------|-----------|
| **YAML form, not Markdown** | Enforces required fields, prevents incomplete reports |
| **8 fields, 5 required** | Balanced — covers essentials without form fatigue |
| **Dropdowns for agent + strategy** | Structured data we can filter/label on; avoids free-text inconsistency |
| **`type: input` for version/OS** | Single-line, cleaner than textarea (pattern from Go, uv) |
| **`render: bash` on logs** | Syntax highlighting for terminal output |
| **Logs as optional** | Not every bug needs them, but they're invaluable when present |
| **`blank_issues_enabled: false`** | Forces users through the template |
| **Sensitive info warning on logs** | `.entire/logs/` could contain paths/metadata |

The **agent** and **strategy** dropdowns are the Entire-specific additions — these are the two most critical dimensions for triaging bugs since behavior differs significantly between agents and strategies.

## Analysis

### Format: YAML Forms vs Markdown

| Project | Format | Why |
|---------|--------|-----|
| GitHub CLI | Markdown | Simple template, low volume |
| Go | YAML | Structured data (dropdowns, checkboxes) |
| Kubernetes | YAML | Structured, but redirects to KEP for serious features |
| Docker CLI | YAML | Structured but minimal |
| Terraform | YAML | Comprehensive structured form |
| uv | YAML | Lean structured form |
| Charmbracelet | Markdown | Default GitHub template, unchanged |
| VS Code | Markdown | Relies on bot ecosystem for structure |
| Rust | External | Redirects to forum entirely |
| urfave/cli | Markdown | Includes pre-submission checklist |

**Trend:** Newer or actively maintained projects strongly prefer YAML forms. The YAML form format provides field-level validation (`required: true`), structured input types (dropdowns, checkboxes, short input vs textarea), and a cleaner user experience. Markdown templates are either legacy or used by projects with minimal template needs.

### Best Practices for Feature Request Templates

**1. Separate Problem from Solution (Terraform pattern -- strongest recommendation)**

Terraform's approach of making "Use Cases" required and "Proposal" optional is the most effective pattern. It forces users to articulate the actual problem before jumping to their preferred solution. This is critical because:
- Maintainers can often find better solutions than what users propose
- Multiple users may report the same underlying problem with different proposed solutions
- It prevents "XY Problem" issues

**2. Ask for Concrete Examples (uv pattern)**

The uv template's "Example" field is particularly valuable for CLI tools. Asking "how would the user experience change?" naturally elicits:
- What the command invocation would look like
- What the expected output would be
- What the workflow improvement would be

**3. Include Version Information for CLI Tools (Terraform pattern)**

For CLI projects, asking for the current version with `render: shell` and a placeholder like `...output of \`entire version\`...` is highly practical. It:
- Reveals if the feature already exists in a newer version
- Helps maintainers understand the user's environment
- Uses YAML's `render: shell` attribute for proper formatting

**4. Use Structured YAML Forms Over Markdown**

YAML forms provide concrete advantages:
- **Required field enforcement** prevents incomplete submissions
- **Dropdowns** prevent free-text answers where structured data is better
- **Checkboxes** work well for "did you search first?" gates
- **Markdown blocks** allow inline guidance and routing information
- **Render hints** (`render: shell`) format code blocks automatically
- **Placeholders** guide users without cluttering the template

**5. Label Strategy**

Projects use different labeling approaches:
- **Simple:** `enhancement` (GitHub CLI, Charmbracelet, uv)
- **Workflow:** `enhancement` + `new` (Terraform) or `status/0-triage` (Docker)
- **Typed:** `kind/feature` (Kubernetes, Docker)
- **Multi-dimensional:** `type/feature, area/v3, status/triage` (urfave/cli)

For a CLI tool with manageable issue volume, `enhancement` + a triage label is a good balance.

**6. Routing Guidance for Multi-Component Projects (Terraform pattern)**

If the CLI interacts with a server, API, or plugins, include a markdown block at the top explaining where different types of requests should go. Terraform does this exceptionally well.

**7. Pre-Submission Checklist (urfave pattern)**

For projects that get duplicate feature requests, a checklist asking "Did you search first?" reduces noise. The bubbletea bug template makes this a required checkbox, which is even stronger enforcement.

### CLI-Specific Patterns Worth Adopting

**A. Command/Subcommand Context**

None of the templates above explicitly ask "which command does this relate to?" For a CLI tool with subcommands (Cobra-based), adding a dropdown of commands or asking which command area the feature relates to would help routing.

**B. Platform/Terminal Information**

The bubbletea bug template asks about terminal environment. For feature requests involving TUI elements (using Charm `huh`), knowing the terminal is sometimes relevant.

**C. Workflow Description**

The uv "Example" pattern is the most CLI-native. For a CLI tool, the ideal feature request describes the command the user wants to run and the output they expect to see. This is more useful than abstract descriptions.

### Interesting Unique Patterns

1. **Go's Experience Level Dropdown** -- Helps maintainers calibrate their response. A "Novice" requesting a feature might actually need documentation, while an "Experienced" user has likely exhausted alternatives.

2. **Go's Backward Compatibility Checkboxes** -- For CLIs that have a stability contract, understanding whether a feature would break existing behavior is critical.

3. **Terraform's "Attempted Solutions"** -- This required field is brilliant. It surfaces workarounds that might already exist (and could be documented better), and shows the user has done homework before requesting.

4. **Docker's `status/0-triage` Label** -- Embeds workflow state directly in the template. New issues automatically enter the triage pipeline.

5. **VS Code's Hidden Template Identifier** -- The `<!-- feature_request_template -->` comment enables bot automation to detect which template was used, even in markdown templates.

6. **uv's File Numbering** (`2_feature_request.yaml`) -- Controls the display order in GitHub's template picker without relying on alphabetical naming.

7. **Kubernetes' Active Redirection** -- The enhancement template's description explicitly tells users that feature requests are "unlikely to make progress as issues" and redirects them to the KEP process. This is honest and saves everyone time.

8. **Terraform's Submit Button Hint** -- The footer markdown reminds users to add a title, addressing a common UX problem with GitHub's issue form where the submit button is disabled without clear indication of why.

Push the branch and navigate to the issue template URL with a `template` query param:

```
https://github.com/entireio/cli/issues/new?template=bug_report.yml

https://github.com/entireio/cli/issues/new?template=feature_request.yml
```

The catch: **GitHub only loads issue templates from the default branch** (usually `main`). Templates on a feature branch won't render through the normal UI.

### Workarounds

1. **Temporarily change the default branch** — In repo Settings > General > Default branch, switch it to your feature branch, test the forms, then switch back. Quickest way to test.

2. **Push to a fork** — Fork the repo, push the branch as `main` on the fork, and test there. No risk to the real repo.

3. **YAML validation only** — If you just want to check for syntax errors without visual preview, GitHub will show YAML parse errors when you push. You can also validate locally:
   ```bash
   python3 -c "import yaml; yaml.safe_load(open('.github/ISSUE_TEMPLATE/bug_report.yml'))"
   ```

Option 2 (fork) is the safest for a shared repo.
