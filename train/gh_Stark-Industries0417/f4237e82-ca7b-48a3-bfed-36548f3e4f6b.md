## 2. Deferred Finalization Pattern

### How It Works (New Flow)

1. **PostCommit (ACTIVE session)**: Condenses immediately with "provisional" transcript (whatever is available at commit time)
2. **PostCommit**: Appends checkpoint ID to `state.TurnCheckpointIDs` 
3. **HandleTurnEnd (Stop hook)**: Reads full transcript from disk, calls `UpdateCommitted()` for each checkpoint ID
4. **HandleTurnEnd**: Clears `TurnCheckpointIDs` and updates `CheckpointTranscriptStart`

### Architecture Assessment: **Sound**

**Strengths:**
- **Idempotent**: Each checkpoint ID is generated fresh in PrepareCommitMsg - no reuse from previous commits
- **Fail-safe**: If HandleTurnEnd fails, the provisional transcript is still valid metadata (better than losing everything)
- **Clear ownership**: PostCommit owns condensation, HandleTurnEnd owns finalization
- **Replace semantics**: `UpdateCommitted()` replaces (not appends) the transcript - correct because all checkpoints from the same turn should have identical final transcripts

**Key Files:**
- `/Users/soph/Work/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_hooks.go` (lines 1562-1675) - HandleTurnEnd and finalizeAllTurnCheckpoints

**Potential Edge Case:**
If a user commits multiple times during a turn then crashes before Stop:
- Checkpoints have provisional transcripts (partial but valid)
- TurnCheckpointIDs is persisted to state file

The current implementation clears TurnCheckpointIDs on any failure, which is safe. Consider whether recovery should be attempted on next InitializeSession (see Suggestions).

The content-aware overlap detection distinguishes between **modified files** and **new files**:

## Modified Files (existed in parent commit)
- **Always count as overlap** regardless of content
- No hash comparison performed
- Rationale: If the file existed before the session and is being modified, the user is editing the session's work (even if they changed it further)

## New Files (didn't exist in parent commit)  
- **Hash comparison** against shadow branch
- Only counts as overlap if content matches exactly
- Rationale: Detects "reverted and replaced" scenario where user deleted session's work and wrote something completely different

## Example

```
Parent commit: has file A.txt
Session: modifies A.txt, creates B.txt (new)
User: reverts both files, writes different content

Commit check:
- A.txt: Modified file → ALWAYS overlap ✓ (even though content changed)
- B.txt: New file → compare hash → different content → NO overlap ✗
```

If user reverts a **new** file and writes completely different content, we don't want to link that commit to the session (the session's work was discarded).

But if user modifies a file that **already existed**, they're building on top of the session's edit to that file, so it should still be linked.

This means if you:
1. Have Claude modify an existing file
2. Completely rewrite that modification with different content
3. Commit

The commit **will still get a checkpoint trailer** because modified files always count as overlap. The content-aware check doesn't protect against this case - only against reverted **new** files.

Git already computes a SHA-1 hash for every file (blob) it stores:

```
"hello world!" → blob hash: a0423896973644771497bdc03eb99d5281615b51
```

The hash is computed from: `"blob " + size + "\0" + content`

2. Get `shadowFile.Hash` - the blob hash of the file in the shadow branch
3. Compare: `headFile.Hash == shadowFile.Hash`

If they match, the content is **exactly identical** (same bytes). If they differ, the content changed.

- No file content needs to be read from disk or memory
- Just comparing two 20-byte SHA-1 hashes
