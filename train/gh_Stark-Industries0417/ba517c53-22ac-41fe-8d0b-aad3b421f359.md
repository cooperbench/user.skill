   249→### Checkpoint ID Linking
   250→
   251→The checkpoint ID is the **stable identifier** that links user commits to metadata across branches.
   252→
   253→**Format:** 12-hex-character random ID (e.g., `a3b2c4d5e6f7`)
   254→
   255→**Generation:**
   256→- Manual-commit: Generated during condensation (post-commit hook)
   257→- Auto-commit: Generated when creating the commit
   258→
   259→**Usage:**
   260→
   261→1. **User commit trailer** (both strategies):
   262→   - `Entire-Checkpoint: a3b2c4d5e6f7` added to user's commit message
   263→   - Auto-commit: Added programmatically
   264→   - Manual-commit: Added by `prepare-commit-msg` hook (user can remove)
   265→
   266→2. **Directory sharding** on `entire/checkpoints/v1`:
   267→   - Path: `<id[:2]>/<id[2:]>/` (e.g., `a3/b2c4d5e6f7/`)
   268→   - First 2 chars = shard (256 possible shards)
   269→   - Remaining 10 chars = directory name
   270→
   271→3. **Commit subject** on `entire/checkpoints/v1`:
   272→   - Format: `Checkpoint: a3b2c4d5e6f7`
   273→   - Makes `git log entire/checkpoints/v1` readable
   274→
   275→**Bidirectional Lookup:**
   276→
   277→```
   278→User commit → Metadata:
   279→  1. Extract "Entire-Checkpoint: a3b2c4d5e6f7" from commit message
   280→  2. Look up metadata:
   281→     - Approach A: Read entire/checkpoints/v1 tree at a3/b2c4d5e6f7/
   282→     - Approach B: Search git log entire/checkpoints/v1 for "Checkpoint: a3b2c4d5e6f7"
   283→
   284→Metadata → User commits:
   285→  Given checkpoint ID a3b2c4d5e6f7
   286→  → Search branch history for commits with "Entire-Checkpoint: a3b2c4d5e6f7"
   287→```
   288→
   289→**Example Flow:**
   290→
   291→```
   292→                    User creates commit
   293→                           ↓
   294→           prepare-commit-msg hook adds trailer

   362→## Concurrent Sessions
   363→
   364→Multiple AI sessions can run concurrently on the same base commit:
   365→
   366→1. **Warning on start** - When a second session starts while another has uncommitted checkpoints, a warning is shown
   367→2. **Both proceed** - User can continue; checkpoints interleave on the same shadow branch
   368→3. **Identification** - Each checkpoint is tagged with its session ID; rewind UI shows session prompt
   369→4. **Condensation** - On commit, all sessions are condensed together with archived subfolders
   370→
   371→### Conflict Handling
   372→
   373→| Scenario | Behavior |
   374→|----------|----------|
   375→| Concurrent sessions (same worktree) | Warning shown, both proceed |
   376→| Orphaned shadow branch (no state file) | Branch reset, new session proceeds |
   377→| Cross-worktree conflict (state file exists) | `SessionIDConflictError` returned |
   378→
   379→### Shadow Branch Migration
   380→
   381→If user does stash → pull → apply (HEAD changes without commit):
   382→- Detection: base commit changed AND old shadow branch still exists
   383→- Action: branch renamed from `entire/<old-commit[:7]>-<worktreeHash[:6]>` to `entire/<new-commit[:7]>-<worktreeHash[:6]>`
   384→- Result: session continues with checkpoints preserved

   439→// InitialAttribution captures line-level attribution metrics at commit time.
   440→// This is a point-in-time snapshot comparing the checkpoint tree (agent work)
   441→// against the committed tree (may include human edits).
