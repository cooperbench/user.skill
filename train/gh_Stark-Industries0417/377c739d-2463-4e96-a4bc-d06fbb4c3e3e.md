     1→# Known Limitations
     2→
     3→This document describes known limitations of the Entire CLI.
     4→
     5→## Git Operations
     6→
     7→### Amending Commits with `-m` Flag
     8→
     9→When you amend a commit using `git commit --amend -m "new message"`, the `-m` flag replaces the entire message including any `Entire-Checkpoint` trailer. Git passes `source="message"` (not `"commit"`) to the prepare-commit-msg hook, so the amend-specific trailer preservation logic is bypassed.
    10→
    11→**However, the trailer is automatically restored** if `PendingCheckpointID` or `LastCheckpointID` exists in session state (set during the original condensation). This means `git commit --amend -m "..."` preserves the checkpoint link in most cases, including when Claude does the amend in a non-interactive environment.
    12→
    13→The only case where the link is lost is when `-m` is used with genuinely *new* content (no prior condensation) and `/dev/tty` is not available for the interactive confirmation prompt.
    14→
    15→**Tracked in:** [ENT-161](https://linear.app/entirehq/issue/ENT-161)
    16→
    17→### Git GC Can Corrupt Worktree Indexes
    18→
    19→When using git worktrees, `git gc --auto` can corrupt a worktree's index by pruning loose objects that the worktree's index cache-tree references. This manifests as:
    20→
    21→```
    22→fatal: unable to read <hash>
    23→error: invalid sha1 pointer in cache-tree of .git/worktrees/<n>/index
    24→```
    25→
    26→**Root cause:** Checkpoint saves use go-git's `SetEncodedObject` which creates loose objects. When the count exceeds the `gc.auto` threshold (default 6700), any git operation (e.g., VS Code or Sourcetree background fetch) triggers `git gc --auto`. GC doesn't fully account for worktree index references when pruning, so objects get deleted while the worktree index still points to them.
    27→
    28→**Impact:**
    29→- `git status` fails in the affected worktree
    30→- Staged changes in the worktree are lost
    31→
    32→**Recovery:**
    33→```bash
    34→# In the affected worktree:
    35→git read-tree HEAD
    36→```
    37→This rebuilds the index from HEAD. Any previously staged changes will need to be re-staged.
    38→
    39→**Prevention:** Disable auto-GC and run it manually after commits (when indexes are clean):
    40→```bash
    41→git config gc.auto 0
    42→```
    43→
    44→**Tracked in:** [ENT-241](https://linear.app/entirehq/issue/ENT-241)
    45→

     1→# Sessions and Checkpoints
     2→
     3→## Overview
     4→
     5→Entire CLI creates checkpoints for AI coding sessions. The system is agent-agnostic - it works with Claude Code, Cursor, Copilot, or any tool that triggers Entire hooks.
     6→
     7→## Domain Model
     8→
     9→### Session
    10→
    11→A **Session** is a unit of work. Sessions can be nested - when a subagent runs, it creates a sub-session.
    12→
    13→```go
    14→type Session struct {
    15→    ID             string
    16→    FirstPrompt    string       // Raw first user prompt (immutable)
    17→    Description    string       // Display text (derived or editable)
    18→    StartTime      time.Time
    19→    AgentType      string       // "claude-code", "cursor", etc.
    20→    AgentSessionID string       // The agent's session identifier
    21→
    22→    Checkpoints    []Checkpoint
    23→    SubSessions    []Session    // Nested sessions (subagent work)
    24→
    25→    // Empty for top-level sessions
    26→    ParentID       string       // Parent session ID
    27→    ToolUseID      string       // Tool invocation that spawned this
    28→}
    29→
    30→func (s *Session) IsSubSession() bool {
    31→    return s.ParentID != ""
    32→}
    33→```
    34→
    35→### Checkpoint
    36→
    37→A **Checkpoint** captures a point-in-time within a session.
    38→
    39→```go
    40→type Checkpoint struct {
    41→    ID        string
    42→    SessionID string
    43→    Timestamp time.Time
    44→    Type      CheckpointType
    45→    Message   string
    46→}
    47→
    48→type CheckpointType int
    49→
    50→const (
    51→    Temporary CheckpointType = iota // Full state snapshot, shadow branch
    52→    Committed                        // Metadata + commit ref, entire/checkpoints/v1
    53→)
    54→```
    55→
    56→### Checkpoint Types
    57→
    58→| Type | Contents | Use Case |
    59→|------|----------|----------|
    60→| Temporary | Full state (code + metadata) | Intra-session rewind, pre-commit |
    61→| Committed | Metadata + commit reference | Permanent record, post-commit rewind |
    62→
    63→### Session Nesting
    64→
    65→```
    66→Session (top-level, ParentID="")
    67→├── Checkpoints: [c1, c2, c3]
    68→└── SubSessions:
    69→    └── Session (ParentID=<parent>, ToolUseID="toolu_abc")
    70→        ├── Checkpoints: [c4, c5]
    71→        └── SubSessions: [...] (can nest further)
    72→```
    73→
    74→Each session - top-level or nested - has its own FirstPrompt, Description, and Checkpoints.
    75→
    76→## Interface
    77→
    78→### Session Operations
    79→
    80→```go
    81→type Sessions interface {
    82→    Create(ctx context.Context, opts CreateSessionOptions) (*Session, error)

    84→    List(ctx context.Context) ([]Session, error) // Top-level sessions only

    88→### Checkpoint Storage (Low-Level)
    89→
    90→Primitives for reading/writing checkpoints. Used by strategies.
    91→
    92→```go
    93→type CheckpointStore interface {
    94→    // Temporary checkpoint operations (shadow branches - full state)
    95→    WriteTemporary(ctx context.Context, sessionID string, snapshot TemporaryCheckpoint) error
    96→    ReadTemporary(ctx context.Context, sessionID string) (*TemporaryCheckpoint, error)
    97→    ListTemporary(ctx context.Context) ([]CheckpointInfo, error)
    98→
    99→    // Committed checkpoint operations (entire/checkpoints/v1 branch - metadata only)
   100→    WriteCommitted(ctx context.Context, checkpoint CommittedCheckpoint) error
   101→    ReadCommitted(ctx context.Context, checkpointID string) (*CommittedCheckpoint, error)
   102→    ListCommitted(ctx context.Context) ([]CheckpointInfo, error)

   104→
   105→type TemporaryCheckpoint struct {
   106→    SessionID  string
   107→    CodeTree   plumbing.Hash // Full worktree snapshot

   109→    Prompts    []string
   110→    Context    []byte
   111→}
   112→
   113→type CommittedCheckpoint struct {
   114→    ID         string
   115→    SessionID  string

   117→    Transcript []byte
   118→    Prompts    []string
   119→    Context    []byte
   120→    CreatedAt  time.Time

   154→## Storage
   155→
   156→| Type | Location | Contents |
   157→|------|----------|----------|
   158→| Session State | `.git/entire-sessions/<id>.json` | Active session tracking |
   159→| Temporary | `entire/<commit-hash>` branch | Full state (code + metadata) |
   160→| Committed | `entire/checkpoints/v1` branch (sharded) | Metadata + commit reference |
   161→
   162→### Session State
   163→
   164→Location: `.git/entire-sessions/<session-id>.json`
   165→
   166→Stored in git common dir (shared across worktrees). Tracks active session info.
   167→
   168→### Temporary Checkpoints
   169→
   170→Branch: `entire/<base-commit-hash[:7]>`
   171→
   172→Contains full worktree snapshot plus metadata overlay. **Multiple concurrent sessions** can share the same shadow branch - their checkpoints interleave:
   173→
   174→```
   175→<worktree files...>
   176→.entire/metadata/<session-id-1>/
   177→├── full.jsonl           # Session 1 transcript
   178→├── prompt.txt           # User prompts
   179→├── context.md           # Generated context
   180→└── tasks/<tool-use-id>/ # Task checkpoints
   181→.entire/metadata/<session-id-2>/
   182→├── full.jsonl           # Session 2 transcript (concurrent)
   183→├── ...
   184→```
   185→
   186→Tied to a base commit. Condensed to committed on user commit.
   187→
   188→**Shadow branch lifecycle:**
   189→- Created on first checkpoint for a base commit
   190→- Migrated automatically if base commit changes (stash → pull → apply scenario)
   191→- Deleted after condensation to `entire/checkpoints/v1`
   192→- Reset if orphaned (no session state file exists)
   193→
   194→### Committed Checkpoints
   195→
   196→Branch: `entire/checkpoints/v1`
   197→
   198→Metadata only, sharded by checkpoint ID. Supports **multiple sessions per checkpoint**:
   199→
   200→```
   201→<id[:2]>/<id[2:]>/
   202→├── metadata.json        # Checkpoint info (see below)

   242→### Checkpoint ID Linking
   243→
   244→The checkpoint ID is the **stable identifier** that links user commits to metadata across branches.
   245→
   246→**Format:** 12-hex-character random ID (e.g., `a3b2c4d5e6f7`)
   247→
   248→**Generation:**
   249→- Manual-commit: Generated during condensation (post-commit hook)
   250→- Auto-commit: Generated when creating the commit
   251→
   252→**Usage:**
   253→
   254→1. **User commit trailer** (both strategies):
   255→   - `Entire-Checkpoint: a3b2c4d5e6f7` added to user's commit message
   256→   - Auto-commit: Added programmatically
   257→   - Manual-commit: Added by `prepare-commit-msg` hook (user can remove)
   258→
   259→2. **Directory sharding** on `entire/checkpoints/v1`:
   260→   - Path: `<id[:2]>/<id[2:]>/` (e.g., `a3/b2c4d5e6f7/`)
   261→   - First 2 chars = shard (256 possible shards)
   262→   - Remaining 10 chars = directory name
   263→
   264→3. **Commit subject** on `entire/checkpoints/v1`:
   265→   - Format: `Checkpoint: a3b2c4d5e6f7`
   266→   - Makes `git log entire/checkpoints/v1` readable
   267→
   268→**Bidirectional Lookup:**
   269→
   270→```
   271→User commit → Metadata:
   272→  1. Extract "Entire-Checkpoint: a3b2c4d5e6f7" from commit message
   273→  2. Look up metadata:
   274→     - Approach A: Read entire/checkpoints/v1 tree at a3/b2c4d5e6f7/
   275→     - Approach B: Search git log entire/checkpoints/v1 for "Checkpoint: a3b2c4d5e6f7"
   276→
   277→Metadata → User commits:
   278→  Given checkpoint ID a3b2c4d5e6f7
   279→  → Search branch history for commits with "Entire-Checkpoint: a3b2c4d5e6f7"
   280→```
   281→

   283→
   284→```
   285→                    User creates commit

   287→           prepare-commit-msg hook adds trailer

     1→# Logging Architecture
     2→
     3→## Overview
     4→
     5→The CLI uses Go's `log/slog` package for structured JSON logging. All logs are written to a single file `.entire/logs/entire.log` and help debug hook execution and CLI behavior. When a session ID is known, the `session_id` attribute on each log line allows filtering by session.
     6→
     7→## Log Levels
     8→
     9→| Level | Purpose |
    10→|-------|---------|
    11→| DEBUG | Wrapper breadcrumbs (hook invoked/completed), detailed diagnostics |
    12→| INFO | Handler logs with full context - the primary level for tracing |
    13→| WARN | Unexpected conditions that don't block execution |
    14→| ERROR | Failures that prevent operation completion |
    15→
    16→## Configuration
    17→
    18→```bash
    19→# Environment variable (takes precedence)
    20→export ENTIRE_LOG_LEVEL=debug

    23→{"log_level": "debug"}

    27→
    28→Logs use a hierarchical tracing model inspired by OpenTelemetry concepts:
    29→
    30→### Identifiers
    31→
    32→| Field | Scope | Description |
    33→|-------|-------|-------------|
    34→| `session_id` | Root trace | Entire session ID, auto-added to all log entries |
    35→| `tool_use_id` | Span | Unique ID for a subagent task lifecycle |
    36→| `agent_id` | Span metadata | The subagent's ID (returned by Claude Code) |

    39→

     1→# Attribution
     2→
     3→## Overview
     4→
     5→Attribution tracks how much of a commit came from the agent vs the user. When a user commits code after working with an AI agent, the CLI calculates what percentage of the changes were agent-written vs human-written.
     6→
     7→This is captured in the `Entire-Attribution` trailer on commits:
     8→
     9→```
    10→feat: Add user authentication
    11→
    12→Entire-Checkpoint: a3b2c4d5e6f7
    13→Entire-Attribution: 73% agent (146/200 lines)
    14→```
    15→
    16→## The Challenge
    17→
    18→Attribution seems simple: diff the base commit against the final commit and count who wrote what. But there's a fundamental challenge: **the agent and user interleave their work**.
    19→
    20→A typical session looks like:
    21→
    22→1. User writes some code
    23→2. Agent runs, adds more code (checkpoint 1)
    24→3. User edits the agent's code and adds their own
    25→4. Agent runs again (checkpoint 2)
    26→5. User makes final tweaks
    27→6. User commits
    28→
    29→The checkpoint snapshots capture the worktree state at each moment, but that state includes *both* agent work and user edits made since the last checkpoint. We need to untangle these contributions.
    30→
    31→## Architecture
    32→
    33→### Data Collection
    34→
    35→Attribution data is collected at two points:
    36→
    37→**1. At prompt start** (`CalculatePromptAttribution`)
    38→
    39→Before each agent run, we capture what the user changed since the last checkpoint:
    40→- `UserLinesAdded` / `UserLinesRemoved` - aggregate counts
    41→- `UserAddedPerFile` - per-file breakdown of user additions
    42→
    43→This happens *before* the agent runs, so we can cleanly separate "user edits between prompts" from "agent work during prompt".
    44→
    45→**2. At commit time** (`CalculateAttributionWithAccumulated`)
    46→
    47→When the user commits, we calculate final attribution by:
    48→1. Summing accumulated user edits from all `PromptAttribution` records
    49→2. Adding post-checkpoint user edits (shadow → head diff)
    50→3. Calculating agent work (base → shadow minus accumulated user edits)
    51→4. Computing the final percentage
    52→
    53→### Key Files
    54→
    55→- `manual_commit_attribution.go` - Core attribution calculation logic
    56→- `manual_commit_types.go` - `PromptAttribution` struct definition
    57→- `manual_commit_hooks.go` - Hook that triggers attribution calculation on commit
    58→
    59→## Line Ownership Tracking
    60→
    61→When a user modifies code, we need to know: did they modify agent lines or their own lines?
    62→
    63→**Example problem:**
    64→1. Agent adds 10 lines
    65→2. User adds 5 lines of their own
    66→3. User removes 3 lines and adds 3 different lines (a modification)
    67→
    68→If those 3 removed lines were the user's own code, agent attribution should be unaffected. If they were agent lines, agent attribution should decrease.
    69→
    70→### Approaches Considered
    71→
    72→#### Git Blame Against Checkpoints
    73→
    74→Use git's blame to trace line ownership through checkpoint commits.
    75→

    79→    // git blame --porcelain <shadow-commit> -- <file>
    80→}
    81→```

    83→| Aspect | Assessment |
    84→|--------|------------|
    85→| Accuracy | High |
    86→| Complexity | High - requires shelling to git CLI |
    87→| Performance | Expensive at attribution time |
    88→

    90→

   124→
   125→Track aggregate ownership counts per file. Use LIFO assumption: users modify their own recent additions before touching agent code.
   126→
   127→```go
   128→// PromptAttribution includes per-file tracking
   129→type PromptAttribution struct {
   130→    UserLinesAdded   int
   131→    UserLinesRemoved int
   132→    UserAddedPerFile map[string]int  // Per-file breakdown
   133→}
   134→
   135→// When user removes lines, assume they remove their own first
   136→func estimateUserSelfModifications(
   137→    accumulatedUserAddedPerFile map[string]int,
   138→    postCheckpointUserRemovedPerFile map[string]int,
   139→) int {
   140→    var selfModified int
   141→    for filePath, removed := range postCheckpointUserRemovedPerFile {
   142→        userAddedToFile := accumulatedUserAddedPerFile[filePath]
   143→        selfModified += min(removed, userAddedToFile)
   144→    }
   145→    return selfModified
   146→}
   147→```

   149→| Aspect | Assessment |
   150→|--------|------------|
   151→| Accuracy | Medium - good for common case |
   152→| Complexity | Low |
   153→| Performance | Fast |
   154→
   155→### Why Per-File Pools
   156→
   157→1. **Solves the common case**: When users modify their own recent code (the typical pattern), attribution remains accurate
   158→
   159→2. **Sidesteps line identity problems**: We don't need to solve "which `}` was removed" - we reason at the file level
   160→
   161→3. **Reasonable assumption**: "Users modify their own recent code before agent code" matches typical editing patterns
   162→
   163→4. **Low implementation cost**: Just adds a map to `PromptAttribution`
   164→
   165→### Trade-offs Accepted
   166→
   167→- **Imprecise for adversarial cases**: If a user deliberately removes agent code while keeping their own, attribution will be slightly off
   168→- **File-level granularity**: We can't distinguish modifications within different functions of the same file
   169→
   170→These are acceptable because:
   171→- Attribution is informational, not security-critical
   172→- Users have no incentive to game attribution
   173→- Perfect accuracy would require reimplementing git-blame
   174→

    85→## Key Concepts
    86→
    87→### Sessions
    88→
    89→A **session** represents a complete interaction with your AI agent, from start to finish. Each session captures all prompts, responses, files modified, and timestamps.
    90→
    91→**Session ID format:** `YYYY-MM-DD-<UUID>` (e.g., `2026-01-08-abc123de-f456-7890-abcd-ef1234567890`)
    92→
    93→Sessions are stored separately from your code commits on the `entire/checkpoints/v1` branch.
    94→
    95→### Checkpoints
    96→
    97→A **checkpoint** is a snapshot within a session that you can rewind to—a "save point" in your work.
    98→
    99→**When checkpoints are created:**
   100→
   101→- **Manual-commit strategy**: When you make a git commit
   102→- **Auto-commit strategy**: After each agent response
   103→
   104→**Checkpoint IDs** are 12-character hex strings (e.g., `a3b2c4d5e6f7`).
   105→
   106→### Strategies
   107→
   108→Entire offers two strategies for capturing your work:
   109→
   110→| Aspect              | Manual-Commit                            | Auto-Commit                                        |
   111→| ------------------- | ---------------------------------------- | -------------------------------------------------- |
   112→| Code commits        | None on your branch                      | Created automatically after each agent response    |
   113→| Safe on main branch | Yes                                      | No - creates commits                               |
   114→| Rewind              | Always possible, non-destructive         | Full rewind on feature branches; logs-only on main |
   115→| Best for            | Most workflows - keeps git history clean | Teams wanting automatic code commits               |
