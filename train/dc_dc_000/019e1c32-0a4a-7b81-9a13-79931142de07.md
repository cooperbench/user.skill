**Verdict** The 4-table proposal is overbuilt for the first real need. I would not ship `goals + tracks + milestones + observations`. The simplest durable shape is **one journey/state table with JSONB track definitions and current cache, plus one append-only measurement table**. Keep narrative `observations` separate. Pregnancy, fitness, savings, and sobriety all need “bot-readable current state”; only some need time-series history. Milestones are not a first-class table yet: appointments already fit scheduled jobs, and deadlines/targets fit track JSON. **Per-Question Answers** 1. **Do you need 4 tables?** No. Use 2. `goal_tracks` as rows is premature unless you already need cross-goal analytics like “all kg tracks stale this week.” For prompt loading, `hot_context_solo.py` already fetches compact artifact slices and renders them directly ([hot_context_solo.py:359](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:359), [hot_context_solo.py:674](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:674)). A JSONB `tracks` plus `current_state` cache is cheaper and easier. 2. **Separate from existing observations?** Yes. Do not extend `observations`. That table is narrative, confidence/significance-scored, and surfaced by semantic relevance ([0001_init.sql:72](/Users/user_c042661f/Documents/Veas/migrations/0001_init.sql:72)). `scoring.py` explicitly scores “relationship observation” prose ([scoring.py:23](/Users/user_c042661f/Documents/Veas/app/services/scoring.py:23)). Numeric measurements should not enter that decay/scoring/rendering path. 3. **Track kind enum?** `time | value | count` is the wrong cut. It mixes derivation, unit, and semantic behavior. Use `metric_kind`: `anchor_date`, `measurement`, `rate`, `streak`, `computed`. “Sessions/week” is a rate. “Days sober” is a streak. “Gestational week” is computed from an anchor date. 4. **Is target required?** No. Target is optional per track. Sobriety has no target. Pregnancy has an expected endpoint/date, not a motivational target. Fitness and savings often have targets. Model `target` as nullable JSON per track, not a required column. 5. **Metadata everywhere?** Yes, that becomes a junk drawer. Allow JSONB only at the journey level and track definition level.
