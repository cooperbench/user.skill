**Verdict**

The 4-table proposal is overbuilt for the first real need. I would not ship `goals + tracks + milestones + observations`. The simplest durable shape is **one journey/state table with JSONB track definitions and current cache, plus one append-only measurement table**. Keep narrative `observations` separate. Pregnancy, fitness, savings, and sobriety all need “bot-readable current state”; only some need time-series history. Milestones are not a first-class table yet: appointments already fit scheduled jobs, and deadlines/targets fit track JSON.

**Per-Question Answers**

1. **Do you need 4 tables?** No. Use 2. `goal_tracks` as rows is premature unless you already need cross-goal analytics like “all kg tracks stale this week.” For prompt loading, `hot_context_solo.py` already fetches compact artifact slices and renders them directly ([hot_context_solo.py:359](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:359), [hot_context_solo.py:674](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:674)). A JSONB `tracks` plus `current_state` cache is cheaper and easier.

2. **Separate from existing observations?** Yes. Do not extend `observations`. That table is narrative, confidence/significance-scored, and surfaced by semantic relevance ([0001_init.sql:72](/Users/user_c042661f/Documents/Veas/migrations/0001_init.sql:72)). `scoring.py` explicitly scores “relationship observation” prose ([scoring.py:23](/Users/user_c042661f/Documents/Veas/app/services/scoring.py:23)). Numeric measurements should not enter that decay/scoring/rendering path.

3. **Track kind enum?** `time | value | count` is the wrong cut. It mixes derivation, unit, and semantic behavior. Use `metric_kind`: `anchor_date`, `measurement`, `rate`, `streak`, `computed`. “Sessions/week” is a rate. “Days sober” is a streak. “Gestational week” is computed from an anchor date.

4. **Is target required?** No. Target is optional per track. Sobriety has no target. Pregnancy has an expected endpoint/date, not a motivational target. Fitness and savings often have targets. Model `target` as nullable JSON per track, not a required column.

5. **Metadata everywhere?** Yes, that becomes a junk drawer. Allow JSONB only at the journey level and track definition level. For pregnancy, explicit fields in JSON should be named: `lmp_date`, `due_date`, `dating_method`, `singleton_or_multiple`, maybe `risk_notes_summary`. Do not hide core query/render state in undifferentiated metadata.

6. **Different framing?** Yes: call this `user_journeys` or `user_longitudinal_state`, not `goals`. Pregnancy is not a goal in the same sense as bench press. The umbrella still does real work: lifecycle, owner bot, topic, grouping related tracks, transitions. A flat `user_attributes` table loses that.

7. **Mid-journey starts/transitions/conflicts?** The 4-table design handles them, but with ceremony. A journey row with `started_at`, `ended_at`, `status`, `supersedes_journey_id`, and JSON anchors handles them naturally. Cross-goal conflicts should be app logic, not schema logic, until there is a real conflict policy.

8. **Load-bearing for bot reads?** The prompt wants “current state,” not raw normalization. Existing `topic_status` is already the model for current scoped state ([0022_topic_status_user_bot_state.sql:8](/Users/user_c042661f/Documents/Veas/migrations/0022_topic_status_user_bot_state.sql:8)) and is rendered directly into prompts ([hot_context_solo.py:617](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:617)). Match that: fetch active journeys by `user_id + topic_id`, render `current_state`.

**Recommended Schema**

```sql
CREATE TABLE user_journeys (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id uuid NOT NULL REFERENCES users(id),
    topic_id uuid NOT NULL REFERENCES topics(id),
    owner_bot_id text NOT NULL REFERENCES bots(id),
    kind text NOT NULL,
    label text NOT NULL,
    status text NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'paused', 'completed', 'abandoned', 'transitioned')),
    started_at timestamptz NOT NULL DEFAULT now(),
    ended_at timestamptz,
    supersedes_journey_id uuid REFERENCES user_journeys(id),

    -- Named anchors, e.g. {"lmp_date":"2026-01-01","due_date":"2026-10-08"}.
    anchors jsonb NOT NULL DEFAULT '{}'::jsonb,

    -- Definitions keyed by stable track key.
    -- Example: {"weight_gain":{"metric_kind":"measurement","unit":"kg","target":{"value":12}}}
    tracks jsonb NOT NULL DEFAULT '{}'::jsonb,

    -- Prompt-ready cache updated by tools/jobs.
    -- Example: {"gestational_week":{"value":23,"label":"23w2d","as_of":"..."}}
    current_state jsonb NOT NULL DEFAULT '{}'::jsonb,

    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_user_journeys_active_topic_user
    ON user_journeys (topic_id, user_id, updated_at DESC)
    WHERE status = 'active';

CREATE TABLE journey_measurements (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    journey_id uuid NOT NULL REFERENCES user_journeys(id) ON DELETE CASCADE,
    track_key text NOT NULL,
    observed_at timestamptz NOT NULL DEFAULT now(),
    value_numeric numeric,
    value_text text,
    source text NOT NULL DEFAULT 'user_reported'
        CHECK (source IN ('user_reported', 'computed', 'derived_from_message', 'imported')),
    supporting_message_ids uuid[] NOT NULL DEFAULT '{}',
    note text,
    created_at timestamptz NOT NULL DEFAULT now(),
    CHECK (value_numeric IS NOT NULL OR value_text IS NOT NULL)
);

CREATE INDEX idx_journey_measurements_latest
    ON journey_measurements (journey_id, track_key, observed_at DESC);
```
