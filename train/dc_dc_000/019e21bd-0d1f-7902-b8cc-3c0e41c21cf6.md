Each codebase is in a separate repo with separate deploy lifecycle. There are no codegen relationships between them, no shared schema definition file, no cross-repo CI. Humans keep them aligned by remembering to update both sides when any contract changes.

# The bugs we've hit in this single debugging session

**Bug 1 — Cross-repo deployment skew.** The orchestrator added a new gate: "worker stays in `spawning` lifecycle until it publishes `metadata.ready_for_tasks = True`". The worker-side code that publishes that flag was developed and tested via live-test branches but the merge to `origin/main` of the worker repo never happened. Result: every production pod spawned in the last week ran 8-day-old code that didn't know about the flag, sat in `spawning` forever (still heartbeating thanks to a guardian subprocess), the orchestrator's safety net for "stuck spawning" had a gate (`queued_count > 0`) that an empty queue silently disabled, so the zombie pod ran for 18.5h burning $0.69/hr. Git history shows this same contract was added 4 months earlier, immediately reverted with the message "revert: worker not updated yet," and then re-introduced later — same person, same trap.

**Bug 2 — Cross-layer contract enforcement gap.** The Postgres claim RPC requires every task to have a non-null `route_key` (column) and a `route_contract` object (inside `params` JSONB), and runs a lateral join `route_backend_claim_decision(...) ON rd.eligible` that filters out anything ineligible. The edge-function `create-task` and its resolver tree (`travelBetweenImages.ts`, `qwenImageStyle.ts`, etc.) **never built a route_contract for any task type that flows through it**. Zero resolvers had any reference to "route_contract". Result: every production-side task ever created via the edge function has `route_key = NULL`, gets categorically rejected from claims, and sits Queued indefinitely. Live-test tasks worked fine because they use a completely separate Python script path that writes the contract directly.

**Bug 3 — Dual-implementation drift across language boundary.** Within the worker (Python), `params.model_family` holds an internal classification with enum `{"ltx", "wan"}`, used by the worker's runtime for FPS / frame-step decisions. Independently, the route-key system uses a richer enum `{"wan22_i2v", "wan22_vace", "ltx2", "ltx2_distilled", "qwen", "z_image"}` to identify capabilities. Both the Python route-derivation function (`_route_model_family`) AND the TS port (`routeModelFamily`) honor `params.model_family` as an explicit override — short-circuiting before normalizing. So when the orchestrator handler in the worker writes `params["model_family"] = "wan"` (internal value) into child tasks, the TS edge function then *also* reads that and builds a route_key with `model-wan`, which is not a key the capability registry knows about. Tasks become syntactically valid but semantically un-claimable. Same root structure as Bug 2 but at the *language* boundary instead of the *layer* boundary — two implementations of the same function in different languages, each defensively respecting an override the other side wrote in the wrong namespace.

# The pattern

All three bugs share a shape: **the system has accumulated cross-boundary contracts (cross-repo, cross-layer, cross-language) faster than it has accumulated mechanisms that enforce equivalence across the boundary.** Each contract relies on a human remembering to update both sides; failure mode is silent at deploy time and produces runtime symptoms that look unrelated to the original change. The detection mechanisms that exist (orchestrator's stuck-worker timeouts, edge function's input validation, DB RPCs' eligibility filters, the worker's runtime validation of parent/child route contracts) all *log* their negative verdicts but none *escalate* — so the system sat for 18 hours with three independent detectors all noticing "this is wrong" and none refusing to proceed.

> AGENT

The right move is to stop treating “route contract” as application logic and make it a versioned protocol artifact. Three repos are acceptable only if the protocol is not owned by any one of them. Right now it is owned by memory, which is why the same bug keeps reappearing.

**Position**
Collapse the contract boundary, not necessarily every runtime. Create a dedicated `reigh-contracts` release unit and make app, worker, orchestrator, and DB consume generated artifacts from it. If the team will not fund that, merge the repos. What is not acceptable is continuing with hand-copied route logic in Python, TypeScript, SQL, and migrations.

**Source Of Truth**
Create a new repo or top-level package, preferably `banodoco/reigh-contracts`, with:

- `contracts/routes.yaml`
  Defines task types, route dimensions, aliases, allowed route model families, guidance modes, continuity cases, profiles, support state, template IDs, selector namespace/version, and backend eligibility.

- `contracts/task-params.schema.json`
  JSON Schema per task type. This explicitly separates public routing fields from worker-internal runtime fields.

- `contracts/worker-heartbeat.schema.json`
  Defines `metadata.ready_for_tasks`, `worker_git_sha`, `contract_version`, `capabilities_hash`, `worker_backend`, `worker_profile`, `selector_namespace`, `selector_version`.

- `contracts/golden-route-cases.jsonl`
  Canonical examples: task type + params -> route key + route contract + claim eligibility.

Then generate:

- `reigh-app/supabase/functions/_shared/selectedRoute.generated.ts`
- `reigh-worker/source/contracts/selected_route_generated.py`
- `reigh-app/supabase/migrations/generated_route_capabilities.sql`
- `reigh-app/supabase/migrations/generated_route_contract_validation.sql`

The current files [selectedRoute.ts](/Users/user_c042661f/Documents/reigh-workspace/reigh-app/supabase/functions/_shared/selectedRoute.ts), [template_routing.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/template_routing.py), and the capability seed migrations should become generated or thin wrappers around generated code. Nobody edits route derivation directly in app or worker repos.

**DB Owns Admission**
The DB must become the contract enforcement point, not just the place where bad tasks go to die.

Create one insertion path:

- `public.create_task_with_route_contract(...)`
- `public.create_child_task_with_route_contract(...)`

Edge functions and worker orchestrator handlers stop inserting directly into `tasks`. They pass semantic task params to the RPC. The RPC stamps:

- `tasks.route_key`
- `params.route_contract`
- `selector_namespace`
- `selector_version`
- `selected_backend`
- `selected_template_id`
- `worker_contract_version`

Then add hard DB constraints:

- `tasks.route_key IS NOT NULL`
- `params->'route_contract' IS NOT NULL`
- `tasks.route_key = params->'route_contract'->>'route_key'`
- `(selector_namespace, selector_version, selected_backend, route_key)` must exist in `route_backend_capabilities`, or the task is rejected/blocked at creation.

The current `create-task/routeContract.ts` is the right tactical patch, but architecturally it is in the wrong layer. Edge functions should not be trusted to remember route stamping. They should be clients of a DB admission API.

**Kill The Ambiguous Namespace**
`params.model_family` is currently poisoned because it means two different things. Remove it from the wire contract.

Use:

- `params.route_model_family`: public routing enum, generated schema allows only `wan22_i2v`, `wan22_vace`, `ltx2`, `ltx2_distilled`, `qwen`, `z_image`, etc.
- `params.runtime_model_family`: worker-internal runtime enum, e.g. `wan`, `ltx`.

Generated schemas should reject `params.model_family` for newly created tasks. Worker code may translate `route_model_family` to `runtime_model_family` internally, but the reverse must not leak back into task params. This directly eliminates Bug 3.

**Immutable Worker Deploys**
The RunPod startup script doing `git fetch origin main && git reset --hard origin/main` is indefensible for production. It destroys deploy provenance.

Replace it with immutable worker artifacts:

- Build worker Docker image or tarball from a commit.
- Publish with labels:
  - `worker_git_sha`
  - `contract_version`
  - `capabilities_hash`
- Orchestrator spawns a specific image digest or exact commit SHA, never “whatever main is right now.”
- Worker heartbeat must publish those same fields.
- Orchestrator refuses promotion if they do not match the selected pool contract.

If images are too expensive immediately, the one-week bridge is: orchestrator writes `required_worker_git_sha` into worker metadata/env, startup checks out that exact SHA, and exits non-zero if unavailable. Still not ideal, but better than floating `origin/main`.

**Readiness Must Have Teeth**
`metadata.ready_for_tasks` should be part of a versioned readiness protocol:

```json
{
  "readiness_protocol_version": 2,
  "ready_for_tasks": true,
  "contract_version": "2026.05.13",
  "worker_git_sha": "...",
  "capabilities_hash": "...",
  "preflight": {
    "backend_loaded": true,
    "templates_verified": true,
    "db_claim_contract_verified": true
  }
}
```

The orchestrator file [worker_state.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/worker_state.py) should make this a finite-state-machine invariant:

- `spawning` without required readiness protocol after timeout -> terminate pod, mark worker `error`.
- This timeout must not depend on `queued_count`.
- A heartbeating worker missing readiness metadata is not “almost active”; it is incompatible.
- Any detector that knows a pod is incompatible should either terminate, block, or page. Logging is not a state transition.

Bug 1 happened because the system observed enough evidence and still kept paying for the pod. That is a broken control loop, not a missing log.

**Release Pipeline**
Create a contract release train:

1. Change `reigh-contracts`.
2. Generate TS/Python/SQL.
3. Run contract conformance in all consumers:
   - TS edge tests against `selectedRoute.generated.ts`
   - Python worker tests against `selected_route_generated.py`
   - Postgres tests against generated SQL functions and capability rows
4. Build worker artifact.
5. Deploy DB migration.
6. Deploy edge functions.
7. Deploy orchestrator with required `contract_version` and worker artifact digest.
8. Canary one worker pool.
9. Promote.

Cross-repo is fine only if GitHub Actions wires these together. A contract PR should not be mergeable unless all three repos pass against the same generated contract artifact.

**Good Enough**
Good enough is not “more tests.” Good enough is:

- Generated route derivation in TS/Python/SQL from one manifest.
- DB-only task admission RPC.
- Immutable worker version selection.
- Orchestrator readiness protocol with termination on mismatch.
- Queued-but-unclaimable tasks become `Blocked` with structured reason, not immortal `Queued`.

**First Week**
Do this first:

1. Add `contracts/golden-route-cases.jsonl` and make TS, Python, and Postgres consume it in CI.
2. Add DB constraints/triggers rejecting missing or unknown route contracts on new `Queued` tasks.
3. Change RunPod startup to checkout a required SHA, not `origin/main`.
4. Require worker heartbeat fields: `ready_for_tasks`, `worker_git_sha`, `contract_version`, `capabilities_hash`.
5. Terminate stuck spawning workers regardless of queue depth.

That week does not finish the architecture, but it flips the system from silent drift to loud drift. The deeper fix is the contract release unit. Without it, this class of bug will keep returning under new names.
