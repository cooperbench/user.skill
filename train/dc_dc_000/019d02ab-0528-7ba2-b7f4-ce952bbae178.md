> AGENT

At a high level, the feature is trying to let one travel segment use three kinds of conditioning at once: - control video, like existing `ltx_control` - anchor images injected at specific frames - optional audio conditioning during generation The flow is: 1. The orchestrator reads one global `travel_guidance` config for the whole journey. 2. For each segment, it decides what part of that global guidance actually overlaps this segment. 3. For hybrid mode, it remaps global anchor frame positions onto segment-local frame positions. 4. It builds a segment-local payload: - which control video overlap applies - which anchors apply in this segment - optional audio slice for this segment 5. The segment processor turns that into generation params: - `video_prompt_type` like `VGKFI` or `PVGKFI` - `image_refs_paths` - `frames_positions` - `image_refs_strengths` - `audio_guide`, `audio_prompt_type`, `audio_scale` - `denoising_strength` for control strength 6. Those params go through the queue into the WGP orchestrator. 7. Preflight converts `image_refs_paths` into actual PIL images as `image_refs`. 8. WGP parses `frames_positions`, combines guide-video conditioning with injected-frame conditioning, and calls the vendored LTX model. 9. LTX receives: - control-video conditioning - injected anchor refs at frame positions - per-anchor strengths - optional audio conditioning The fragile parts are the boundaries between those steps: - if overlap gating is wrong, anchors never make it into any segment - if serialization is wrong, fields disappear between segment processing and generation - if WGP signatures aren’t updated, `image_refs_strengths` gets dropped - if preflight loads only some images, anchors, positions, and strengths can fall out of alignment So the whole review was basically checking one thing: does the same anchor/control/audio intent survive intact from the top-level travel config all the way into the final `wan_model.generate(...)` call?
