# The situation
During a 2-hour rollout window, the orchestrator spawned 73 GPU workers; 70 were killed before producing useful work. 1 worker rendered all 6 required outputs. Productive utilisation: 4%.

The postmortem claims THREE structural issues:

1. **Issue 1 — RunPod `spawn_failed` retried with no backoff.** 55 of 73 deaths were RunPod refusing to allocate a pod; the orchestrator just keeps asking every 30s. Fix shape: per-pool exponential backoff with a consecutive-failure counter, optionally surfaced through the existing `pause_scaling` table.

2. **Issue 2 — `_handle_early_termination` uses `task_counts.queued == 0` as its kill gate.** This is a snapshot signal answering a durable question. During brief windows where the single productive worker had just claimed a segment, `queued` momentarily dropped to 0, early-term fired, the spawning replacement got killed, the next cycle scaled up again. Fix shape: replace the snapshot gate with a more durable "capacity intent" signal — track desired across cycles; or use `total_tasks` (queued + in-progress); or extend `spawning_grace_period_sec` past one cycle.

3. **Issue 3 — Asymmetric `current_capacity` between phases.** Early-term computes `current_capacity = active + spawning`; scale-up logs `current: 1, desired: 2` in the very same cycle where a spawning worker exists. The per-cycle decision object is computed once at top-of-cycle, then early-term kills a worker, then scale-up consults a now-stale view of the world. Fix shape: re-read worker states between phases, or collapse early-term and scale-up into one symmetric controller.

The postmortem's recommendation: write one sprint brief targeting Issues 2 and 3 together (they share a fix surface — unifying capacity accounting and the gate semantics) and a smaller separate follow-up for Issue 1. Suggested megaplan profile: `thoughtful//medium` (tier-3 model coverage, default robustness, medium planner depth).

> AGENT

The postmortem is broadly right on the symptoms, but its Issue 3 explanation is too shallow. The real bug is not “we should re-read worker states between phases.” The real bug is that [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control_loop.py:116) runs two capacity controllers in one cycle: an early terminating controller at [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control_loop.py:340), then a separate scaler at [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control_loop.py:802). They use different desired-capacity formulas, different gates, and different timing assumptions. That is the design flaw.

Issue 1 is real: `spawn_failed` is retried at poll cadence with no provider/pool backoff. That is indefensible for an external allocator. It needs per-pool backoff.

Issue 2 is also real: `queued == 0` is the wrong kill gate. A worker spawn is a commitment made against prior intent; killing it because a top-of-cycle queue snapshot briefly hit zero is exactly how you build churn. `total_tasks` is better than `queued`, but still not good enough. It is still a snapshot.

Issue 3 is real, but not because re-reading state is the answer. Re-reading between phases is a patch that preserves the broken architecture. Early termination should not exist as a separate phase. Killing excess spawning workers and spawning new workers are both reconciliation actions against the same desired capacity. If they happen in different controllers, the system will keep finding ways to contradict itself.

The right split: keep Issue 1 separate operationally, but design it as part of the same reconciler. Spawn backoff is not the same bug as early-term churn, but it belongs in the same capacity-intent model. Do not ship a “2+3 fix” that leaves spawn attempts as stateless side effects.

Deep fix: introduce durable capacity intent.

Add a `worker_capacity_intents` table keyed by pool/route contract:

`pool`, `worker_backend`, `worker_profile`, `selector_namespace`, `selector_version`, `desired_capacity`, `reason`, `observed_queued`, `observed_active`, `created_at`, `updated_at`, `stable_since`, `last_scale_up_at`, `last_scale_down_at`, `consecutive_spawn_failures`, `next_spawn_allowed_at`.

Then make the controller do one reconciliation pass:

1. Fetch tasks and workers.
2. Derive observed capacity from [worker_state.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/worker_state.py:397): active, spawning, terminal, route-stale.
3. Compute desired intent once in [control/phases/scaling_decision.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control/phases/scaling_decision.py:1).
4. Persist that intent.
5. Reconcile observed capacity toward intent in [control/phases/worker_capacity.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control/phases/worker_capacity.py:1).
6. Apply hysteresis: scale down only after intent has remained lower for N seconds or N cycles; never kill a spawning worker that was created under a still-valid intent unless it exceeds a startup timeout or route contract changed.
7. Apply spawn backoff before creating workers: if `next_spawn_allowed_at > now`, skip spawning and log suppression against the intent.

This removes `_handle_early_termination` entirely. Spawning workers either count toward capacity or have an explicit state saying they do not count. There should be no special “early kill” controller. Provider failures update intent/backoff state; they do not create a blind retry loop.

Also, consolidate the duplicate control surfaces. There is old monolithic [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control_loop.py:80) and newer mixins under `control/phases/`. Pick the mixin boundary and move the real implementation there. Keeping two versions of scaling logic around is asking for another postmortem.

Megaplan profile: `premium//high`, not `thoughtful//medium`. This is production-critical control-loop work with external spend, destructive actions, and subtle state transitions. It does not need “super-premium” unless you are also redesigning task scheduling and worker claiming. But `thoughtful//medium` is too casual: the code change may be small, but the invariants matter more than the diff size. The brief should require simulation tests for the observed timeline: queued drops to zero while active work remains, spawn failures repeat, spawning grace crosses cycle boundaries, and route-stale workers drain without counting as new capacity.
