        # Implementation Plan: Pinned Shot Group Command Abstraction & Delete/Undo Fix

## Overview

Pinned shot groups couple to timeline clip state in three ways:
1. **Data coupling**: `PinnedShotGroup.clipIds` references clips in `config.clips` / `rows` / `meta`
2. **Mutation coupling**: Delete-shot-group (`buildDeleteShotGroupMutation`) bundles clip removal + group removal into a single `type: 'rows'` mutation with `pinnedShotGroupsOverride`
3. **Sync coupling**: `usePinnedGroupSync` effect watches shot image changes and auto-reconciles clip membership (add/remove/reorder clips), firing a batched `applyEdit` after a 300ms debounce

**The delete/undo regression**: When a shot group is deleted, the undo snapshot (captured in `onBeforeCommit`) correctly preserves the pre-delete `config` (clips + pinnedShotGroups). `restoreSnapshot` rebuilds the full `TimelineData` from this config. However, `usePinnedGroupSync` runs as a `useEffect` that fires whenever `data` changes. After undo restores the group and its clips, the sync effect re-evaluates the group against the current shot images. If the shot's images have changed (e.g., new generations arrived, images were regenerated, or the shot was modified between the pin and the undo), the sync effect immediately mutates the restored state — deleting clips that no longer match, or inserting new ones. This races with the undo and produces an inconsistent result that the user didn't expect.

A secondary issue: shot group operations are scattered across 4+ files with no shared command abstraction, making it hard to reason about atomicity or extend operations uniformly.

**Strategy**:
1. Extract a pure `buildShotGroupCommand` module with all shot-group mutation builders (delete, unpin, update membership)
2. Add a sync-suppression mechanism so undo/redo can restore state without being immediately overwritten by the sync effect  
3. Add focused regression tests for delete→undo→redo round-trips with pinned groups
4. Keep the existing mutation types (`type: 'rows'` with `pinnedShotGroupsOverride`) — no new mutation types needed

## Phase 2: Fix the Delete/Undo Sync Race

### Step 3: Add sync-suppression flag to prevent post-undo re-sync
**Scope:** Medium

The core fix: `usePinnedGroupSync` must not run immediately after an undo/redo restoration. The simplest structural approach is a short suppression window.

1. **Add** a `syncSuppressedUntilRef` (ref holding a timestamp or `null`) to `usePinnedGroupSync`'s arguments or as an internal mechanism. When `restoreSnapshot` is called (undo/redo/jumpToCheckpoint), set the suppression timestamp to `Date.now() + debounceMs + buffer` (e.g., 500ms total).
2. **Implementation approach**: Add a `suppressSyncRef` to the return value of `useTimelineHistory` (or a shared ref passed from `useTimelineState`). In `restoreSnapshot` (`useTimelineHistory.ts:158-170`), set `suppressSyncRef.current = Date.now()`. In `usePinnedGroupSync`'s `runSync()` (`usePinnedShotGroups.ts:201`), check if `Date.now() - suppressSyncRef.current < suppressWindowMs` and if so, skip (or re-schedule).
3. **Alternative (simpler)**: Instead of a timestamp, use a boolean `isRestoringRef` that is set to `true` before `restoreSnapshot` calls `commitData` and reset to `false` after. Pass this ref to `usePinnedGroupSync` as a `shouldSkipSync` predicate. The sync effect already checks `isInteractionActive()` — add this as an additional skip condition.
4. **Wire** the suppression ref through `useTimelineState.ts` where both `useTimelineHistory` and `usePinnedGroupSync` are composed.

        # Implementation Plan: Pinned Shot Group Command Layer

## Overview

The concrete delete/undo regression was caused by the UI issuing a shot delete as two separate commits:
1. delete the group's clips from `rows` / `meta`
2. remove the pinned-shot-group entry

Undo only restored one of those commits, so the timeline briefly had a group shell with no live clips. That path is now fixed locally by issuing a single atomic mutation.

The deeper structural issue remains: pinned shot-group operations are constructed in several places with overlapping logic and inconsistent abstraction levels. The same domain concept shows up across:
- `TimelineEditor.tsx` for delete wiring and UI handlers
- `usePinnedShotGroups.ts` for pin / unpin / membership updates
- `useSwitchToFinalVideo.ts` for switch-to-video, switch-to-images, and update-to-latest-video
- `useExternalDrop.ts` for shot-drop creation of a new pinned group
- `useTimelineTrackManagement.ts` and `useClipDrag.ts` for geometry-preserving group moves

Not all of those should be unified into one giant API. The right abstraction boundary is narrower:
- centralize **membership/mode commands** for pinned shot groups
- leave **geometry/move commands** in the drag/track-management layer, since they already operate on translated rows plus group overrides

## Strategy

1. Extract a pure `shot-group-commands` module for membership/mode mutations.
2. Move existing scattered mutation construction behind those builders.
3. Keep `applyEdit(...)` as the engine and the current mutation protocol unchanged.
4. Add regression coverage around atomic delete and command-level invariants.
5. Do **not** add sync suppression unless new repository evidence proves an actual post-undo overwrite race.

## Phase 1: Audit and Define the Command Surface

### Step 1: Formalize the command boundary
**Scope:** Small

Create `src/tools/video-editor/lib/shot-group-commands.ts` as a pure module with builders for operations that change pinned-group membership or mode:
- `buildDeleteShotGroupMutation`
- `buildUnpinShotGroupMutation`
- `buildPinShotGroupMutation` or `buildUpsertPinnedShotGroupMutation`
- `buildSwitchShotGroupToFinalVideoMutation`
- `buildSwitchShotGroupToImagesMutation`
- `buildUpdateShotGroupToLatestVideoMutation`

Keep helpers that only manipulate the `pinnedShotGroups` array pure and reusable as internal utilities if that leads to less duplication.

### Step 2: Explicitly exclude geometry-only paths
**Scope:** Small

Document in the implementation that these remain outside the new command layer for now:
- grouped drag in `useClipDrag.ts`
- grouped track movement in `useTimelineTrackManagement.ts`

Those paths already compute row geometry and `pinnedShotGroupsOverride` together; they are not the same problem as scattered membership/mode commands.

## Phase 2: Migrate the Real Call Sites

### Step 4: Move final-video mode switches onto the command module
**Scope:** Medium

Refactor `useSwitchToFinalVideo.ts` so the mutation-building logic for:
- switch to final video
- switch back to images
- update to latest video

is delegated to pure builders in `shot-group-commands.ts`, while asset registration and async concerns remain in the hook.

The goal is:
- hooks gather data and side effects
- command builders produce the final mutation payload

### Step 5: Move shot-drop group creation onto the command module
**Scope:** Medium

Refactor `useExternalDrop.ts` so the code that appends a new pinned group after dropping a shot uses the same group-upsert helper rather than manually pushing to `pinnedShotGroups`.

This keeps creation semantics aligned with pinning and mode switches.
