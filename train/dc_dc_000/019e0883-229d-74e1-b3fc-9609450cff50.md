**Prompt Wording**
Replace the current live-feed selection section with something stricter and more operational:

```text
LIVE UPDATE SELECTION BAR:

Return zero candidates unless a message clears one of these bars:

1. Release / shipped artifact:
   A concrete new tool, model, node, workflow, LoRA, dataset, script, article, or feature was released, merged, opened, or made available. The source must state what changed and who made/shared it.

2. Community contribution:
   A Banodocian shared original work that others can learn from or use: a workflow, custom node, repo, prompt technique, model, LoRA, code, tutorial, or reproducible result. Prefer items with media, links, files, reactions, or useful follow-up discussion.

3. Significant showcase:
   A finished or clearly impressive generation/demo with attached media and visible community signal. Do not post ordinary experiments, “testing X”, minor parameter chatter, or generic model/tool comparisons unless the result itself is exceptional.

4. High-signal question/request:
   Only include questions or requests if they are tied to a concrete project/release/workflow and have clear community value or strong engagement. One-off troubleshooting is not a feed item.

Do not select:
- generic ComfyUI/model/zImage chatter
- “working on X” status updates without a result, release, or reusable detail
- minor experiments without media or clear outcome
- help requests, thanks, intros, admin chatter
- old tools/projects unless there is genuinely new news
- candidates whose body would mostly repeat the title

Each accepted candidate must explain:
- what is new
- who did it or shared it
- why it matters to this community
- what source message proves it
```

Add a hard output instruction:

```text
If the best candidate would read like “someone mentioned X” or “people are discussing X”, return {"candidates": []}.
```

And for structure:

```text
Title: 6-14 words, factual, no hype, must add information not repeated verbatim in body.
Body: 1-2 sentences, 35-220 words. First sentence must not repeat the title. Credit creator/share author with **username** when known.
```

**Threshold Recommendations**
I’d tighten the code-side editorial gates to match the old standards:

- Require valid `source_message_ids`; do not fall back to the first message.
- Raise final acceptance from `confidence >= 0.75` to `>= 0.85`, except explicit releases with strong source evidence.
- For `project_update`: require a concrete artifact/action verb like `released`, `shipped`, `merged`, `published`, `open-sourced`, `shared workflow`, `new repo`, plus either media/link/file or `>= 3` reactions.
- For `showcase`: require media and `>= 5` unique reactions, matching old top-generation quality.
- For `top_creation`: preserve old standard: video attachment `.mp4/.mov/.webm`, non-NSFW, last 24h, `>= 5` unique reactors.
- For `question`/`request`: require `>= 5` reactions or `>= 3` replies and a concrete project/workflow/release context.
- Reject title/body duplication by normalized token overlap, not just prefix match. Example: reject if body’s first sentence has >70% token overlap with title.
- Enforce max public posts per run: `1` normal live update, or `2` only when both are high confidence/high priority. The prompt says 1-3, but `max_candidates=12` means the system can still flood.

**Tests To Add**
Add focused unit tests around `LiveUpdateCandidateGenerator._normalize_candidate`, `_meets_editorial_bar`, and `LiveUpdateEditor._format_feed_content`:

- Low-signal ComfyUI chatter is rejected:
  `"anyone know if zImage works in ComfyUI? working on tests"` with `0-2` reactions should produce no candidate.
- Generic long model/tool discussion is rejected even when it contains `comfyui`, `model`, or `workflow`.
- `project_update` without artifact/link/media/reactions is rejected even if `text_len >= 120`.
- Missing or invalid `source_message_ids` rejects instead of falling back to the first archived message.
- Title/body duplication is rejected or cleaned when body repeats the title semantically.
- High-signal release passes: explicit shipped/open-sourced repo or workflow, creator attribution, source id, link/media.
- Showcase passes only with media plus `>= 5` reactions.
- `top_creation` passes only for video attachment plus `>= 5` unique reactors.
- One-off help request is rejected; project call-to-action with engagement passes.
- Run-level publishing test: generator returns 5 acceptable candidates, editor posts only the top 1-2 by priority/confidence.

The core fix is to stop treating keywords as newsworthiness. The old daily summary selected for novelty, contribution, evidence, engagement, and usefulness; the live editor should encode those as hard gates, not just prompt preference.
