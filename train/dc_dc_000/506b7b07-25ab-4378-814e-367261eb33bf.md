        # Implementation Plan: Adaptive Turn Orchestration (orient-as-seed → read → consult → respond → record → schedule)

## Overview

**Goal.** Replace the rigid Phase A / Phase B agent loop with a single adaptive orchestrator driven by a small, model‑visible **TurnPlan**. A TurnPlan is an ordered checklist of *model‑bearing* steps drawn from a closed vocabulary (`read`, `consult`, `respond`, `record`, `schedule`, `done`). **Orient is runner‑side only**: the runner synthesizes a triggering preamble (charge, hot‑context signals, picked skeleton, plan checklist) into the first seed message, so it never costs an LLM call. The runner picks a default *skeleton* per trigger (quick / standard / charged / crisis / silence), injects step‑local instructions only when that step is active, and lets the agent revise the plan via an in‑memory `update_turn_plan` tool. Read‑before‑write and outbound safety stay intact, enforced at the tool dispatcher rather than by a phase split.

**Current shape.**
- `app/services/agentic.py:611` — `_run_agentic` makes two `run_phase` calls (Phase A read+respond with `read_phase_tools`; Phase B write‑only with `write_phase_tools`). Phase B seed re‑sends the conversation plus a "you sent X" recap (`app/services/agentic.py:766–782`).
- `app/services/tools/registry.py:206–213` — `_phase_allowed` keys off `ctx.phase` ("read" | "write" | "consult").
- `app/services/tools/registry.py:133–152` — `READ_PHASE_TOOLS` *includes* `send_message_part` and `consult_perspective`; the new `record` step must explicitly exclude both.
- `app/bots/base.py:17–80` — `BotSpec` exposes `phase_a_instruction` / `phase_b_instruction` and `build_phase_a_seed` / `build_phase_b_seed_message`.
- `app/services/prompts.py:95–108` — system prompt hard‑codes the "Two‑Phase Turn Shape" section.
- `app/config.py:57` — `system_prompt_version: str = "v1"` is the production default; bumping `SYSTEM_PROMPT_VERSION` alone does not change runtime behavior.

**Constraints that matter.**
- `run_phase` is generic and good — keep it. The orchestration above it is what changes.
- Outbound guardrails (`_resolve_outbound_text`, `_newer_inbound_exists`, paced send hooks, `send_message_part` interruption) must keep working.
- `bot_turns` reasoning, tool‑call accounting, spend cap, and `claim_onboarding_welcome` semantics must be preserved.
- The Phase B invariant **"no user‑facing text after the response"** is load‑bearing — the new `record` and `schedule` steps must not allow `send_message_part` or `consult_perspective`.
- Tests already pin Phase A / Phase B vocabulary — they need updates, not workarounds.

**Design hypothesis.** The cheapest elegant design is *not* to throw away phase gating. It is to:
1. Generalize phases into a tiny ordered TurnPlan over model‑bearing steps; orient lives in the runner so a quick reply costs exactly one LLM call.
2. Pre‑select a skeleton based on the triggering signal so simple turns stay one‑LLM‑call cheap.
3. Make the plan visible to the model as a checklist appended to the seed and updatable via one in‑memory tool, so the agent reasons in steps the same way the runner does (this is the "elegance" lever).
4. Keep read‑before‑write at the dispatcher (per‑write‑tool prerequisite map), not at the phase boundary, so a quick reply can skip reads entirely without losing the safety property.

**Target deliverable file.** `docs/agent-turn-orchestration-plan.md` — this plan, written by the executor.

## Phase 1: Skeleton & Contracts

### Step 1: Lay the TurnPlan contract (`app/services/turn_plan.py`, new)
**Scope:** Small
1. **Define** a `TurnStep` literal (`"read" | "consult" | "respond" | "record" | "schedule" | "done"`) — note: **no `orient` step**; orient is runner‑side. Add a `TurnPlan` dataclass: `steps: list[TurnStep]`, `current_index: int`, `completed: list[TurnStep]`, `notes: dict[str, str]` (optional per‑step rationale).
2. **Provide** five named skeletons. Each skeleton lists only LLM‑bearing steps; the runner orients before the first call:
   - `quick_reply`: `["respond", "done"]` (one LLM call total when the model emits no tool_use)
   - `standard`: `["read", "respond", "record", "done"]`
   - `charged`: `["read", "consult", "respond", "record", "schedule", "done"]` (the agent may drop `consult` / `schedule` via `update_turn_plan`)
   - `crisis`: `["respond", "record", "schedule", "done"]`
   - `silence_or_react`: `["respond", "record", "done"]` (`respond` produces a `[react: …]` directive or no text)
3. **Add** `pick_default_skeleton(trigger_metadata, charge, hot_context_signals) -> TurnPlan`. Heuristics: `crisis` charge → `crisis`; `charged` → `charged`; explicit reaction directive request or 1–2 word ack → `silence_or_react`; high‑context triggers (e.g., explicit user request to remember/update something) → `standard`; everything else → `quick_reply`. Quick‑reply is the default to keep simple turns cheap.
4. **Render** a compact checklist string for the seed:
   ```text
   Turn plan: [ ] respond · [ ] record · [ ] done
   Current step: respond
   ```
5. **Provide** an `orient_summary(trigger_metadata, charge, hot_context_signals) -> str` runner helper that produces a 1–3 line situational header (trigger kind, charge, sharing default, key signals). This is the runner's "orient" output and is concatenated into the initial seed by `BotSpec.build_initial_seed`.

### Step 2: Generalize the bot profile (`app/bots/base.py`, `app/bots/mediator.py`)
**Scope:** Small
1. **Replace** `phase_a_instruction` / `phase_b_instruction` on `BotSpec` (`app/bots/base.py:23–25`) with `step_instructions: dict[TurnStep, str]` and `skeleton_overrides: dict[str, list[TurnStep]] | None = None` (so a bot can replace specific defaults).
2. **Replace** `build_phase_a_seed` / `build_phase_b_seed_message` (`app/bots/base.py:45–80`) with two helpers:
   - `build_initial_seed(trigger_metadata, triggering_message_ids, charge, plan, orient_header) -> list[dict]` — emits one user message containing: trigger header line + `orient_header` (runner‑synthesized) + plan checklist + the `step_instructions[plan.steps[0]]` only.
   - `build_step_transition_message(plan, sent_summary | None) -> dict` — emits an updated `Turn plan: …` line plus the new current step's instructions, with `sent_summary` included only when transitioning into `record` (the model's actual outbound is what matters there).
3. **Move** the existing Phase A and Phase B prose in `app/bots/mediator.py:47–72` into a `MEDIATOR_STEP_INSTRUCTIONS` dict keyed by step. `respond` inherits the current Phase A guidance (incremental sending, reaction directive, scheduling‑machinery wording, no scratch notes); `record` inherits Phase B (state changes only, no user‑facing text). `read`, `consult`, `schedule` are short, step‑specific.
4. **Keep** `MediatorBotSpec` thin — no special build_phase_*; only override `pick_default_skeleton` if mediator‑specific tweaks are needed (initially: none).

### Step 3: Generalize the turn context (`app/services/turn_context.py`)

## Phase 2: Adaptive Orchestrator

**Scope:** Small
1. **Define** the tool schema in `tool_schemas.py` with input fields `add_steps?: list[TurnStep]`, `remove_steps?: list[TurnStep]`, `mark_done?: TurnStep`, `note?: str` and output `{plan: list[TurnStep], current: TurnStep}`.
2. **Implement** the dispatcher entry in `app/services/tools/registry.py:80–131` so it mutates `ctx.turn_plan` directly without touching the DB. It is permitted in *every* step (the agent can replan at any time).

4. **Do not** add it to `READ_PHASE_TOOLS` / `WRITE_PHASE_TOOLS`; instead extend `_step_allowed` (Step 5) to always include it. **Skip** evals capture for this tool to keep `tool_call_count` analytics clean.

### Step 5: Replace phase gating with step‑aware tool gating (`app/services/tools/registry.py`)
**Scope:** Small
1. **Define** `RECORD_READ_TOOLS = READ_PHASE_TOOLS - {"send_message_part", "consult_perspective"}` so state‑maintenance steps can confirm with reads but cannot send new user‑visible text or invoke a sub‑consult.
2. **Define** `STEP_ALLOWED_TOOLS: dict[TurnStep, set[str]]`:
   - `read`: `READ_PHASE_TOOLS - {"send_message_part"}` (consult stays out — that's its own step)
   - `consult`: current `CONSULT_PHASE_TOOLS`
   - `respond`: `{"send_message_part", "search_emojis", "check_oob"}`
   - `record`: `WRITE_PHASE_TOOLS - {scheduling tools}` ∪ `RECORD_READ_TOOLS` (explicitly **excludes** `send_message_part` and `consult_perspective` — preserves the no‑user‑facing‑text invariant)
   - `schedule`: `{"schedule_checkin","cancel_scheduled_checkin","schedule_task","update_scheduled_task","cancel_scheduled_task","list_scheduled_tasks"}`
3. **Add** a `READ_BEFORE_WRITE: dict[str, set[str]]` mapping each "must search first" write tool to the set of read tools that satisfy the prerequisite. Examples:
   - `add_memory` / `update_memory` / `supersede_memory` → `{"get_memories"}`
   - `log_observation` / `update_observation` → `{"get_observations"}`
   - `add_distillation` / `revise_distillation` → `{"get_distillations"}`
   - `create_theme` / `update_theme` → `{"list_themes","get_theme"}`
   - `add_oob` / `update_oob` / `lift_oob` → `{"get_oob","summarize_oob_topics"}`
   - `add_watch_item` / `update_watch_item` / `address_watch_item` → `{"list_watch_items"}`
4. **Track** read tool calls in `ctx.tool_call_log`. In `call_tool`, before dispatching a write tool, check `READ_BEFORE_WRITE`; if no satisfying read in this turn, return a `_tool_error` instructing the model to call the matching read first. This preserves "search before write" without needing a phase split.
5. **Replace** `_phase_allowed` with `_step_allowed(ctx)` returning `STEP_ALLOWED_TOOLS[ctx.current_step] | {"update_turn_plan"}`.

### Step 6: Rewrite the orchestrator (`app/services/agentic.py`)
**Scope:** Medium
1. **Replace** `_run_agentic` (`app/services/agentic.py:611–864`) with a step‑driven loop. Pseudocode:
   ```python
   plan = bot_spec.pick_default_skeleton(trigger_metadata, charge, hot_context)
   ctx.turn_plan = plan
   orient_header = orient_summary(trigger_metadata, charge, hot_context)
   seed = bot_spec.build_initial_seed(trigger_metadata, triggering_message_ids, charge, plan, orient_header)
   messages: list[dict] = list(seed)
   total_tool_count = 0
   while plan.current_step() != "done":
       ctx.current_step = plan.current_step()
       step_messages, step_tool_count = await run_step(
           client, ctx, system_prompt, rendered_hot_context,
           STEP_ALLOWED_TOOLS[ctx.current_step] | {"update_turn_plan"},
           messages,
           max_tool_iterations=STEP_ITERATION_CAPS[ctx.current_step],
       )
       messages = step_messages
       total_tool_count += step_tool_count
       if ctx.current_step == "respond":
           sent_summary = _resolve_outbound(step_messages, ctx, ...)  # existing post-Phase-A logic
       _advance_plan(plan, step_messages)
       if plan.current_step() != "done":
           messages.append(bot_spec.build_step_transition_message(
               plan,
               sent_summary=sent_summary if plan.current_step() == "record" else None,
           ))
   ```
   For `quick_reply` (`["respond", "done"]`), the loop runs `run_step` exactly once; if the model emits text without tool_use, that's one Anthropic `messages.create` call total — satisfying the cheap‑turn invariant.
2. **Reuse** the existing `run_phase` body as a step runner — rename to `run_step` and let the caller pass `max_tool_iterations` and the allowed tool set. The text‑extraction logic at `app/services/agentic.py:300–306` already returns final assistant text; the orchestrator captures it only after the `respond` step.
3. **Wire** outbound resolution exactly where it lives now. After the `respond` step:
   - Pull `assistant_text` from the step's last assistant message.
   - Run `_extract_reaction_directive`, `clean_user_facing_text`, `_resolve_outbound_text`, `_newer_inbound_exists` checks (`app/services/agentic.py:696–761`) **unchanged**. The fact that this happens after the `respond` step rather than at end‑of‑Phase‑A is the only structural change.
   - If `send_message_part` already delivered everything, behave as today.
4. **Compute** `sent_summary` (today: `app/services/agentic.py:768–779`) once after `respond` and pass it into `build_step_transition_message` only when transitioning into `record`. This preserves the existing accountability nudge ("you actually sent N messages: …").
5. **Keep** spend cap fallback, paced send, NewerInbound handling, and `_complete_turn` semantics. The `phase_a_sent` flag becomes `responded_to_user` and is set after `respond`.
6. **Persist** the final plan trace into `bot_turns.reasoning` alongside existing reasoning fragments. No new column required — append a single line like `Turn plan executed: respond → record (skipped: read, consult, schedule)`.
