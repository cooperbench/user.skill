        Plan:
        # Implementation Plan: Single-Segment Identity (Segment = Final Video)

## Overview

**Goal:** For shots with a single completed segment (≤2 positioned timeline images), the segment's child generation should BE the final video — consumed directly by all downstream readers (display, sharing, download, thumbnails). No copy to the parent, no drift.

**Current state:** When a single segment completes, `complete_task` creates a child generation (with the video URL) AND copies that URL to a variant on the parent generation. Consumers read from the parent via the `shot_final_videos` view. Two records, same data, maintenance hazard.

**Approach:** Modify the `shot_final_videos` view to return the child generation directly for single-child parents. Remove the parent-variant propagation for single-segment cases. Hide the SegmentOutputStrip when the single segment is already shown as the final video.

**Key architectural constraint:** The `shot_final_videos` view is the single source of truth for all final video consumers — `fetchParentGenerations`, `useShotFinalVideos`, `FinalVideoSection`, `VideoShotDisplay`. Changing the view transparently updates all consumers.

**Transition:** When a 3rd image is added and multi-segment generation runs, multiple children appear under the parent. The view then returns the parent (which gets a stitch variant from the join flow). This is automatic — no explicit "switch" needed.

## Phase 1: Database — Make the View Return Children for Single-Segment Cases

### Step 1: Create migration to update `shot_final_videos` view
**Scope:** Medium

1. **Create** new migration file `supabase/migrations/YYYYMMDD_shot_final_videos_single_segment_identity.sql`.
2. **Replace** the `shot_final_videos` view with a UNION query:
   - **Case A (single-child):** For parent generations with exactly 1 child that has a `location`, return the child generation row (joined to `shot_generations` via the parent's `generation_id` to preserve `shot_id`).
   - **Case B (multi-child or parentless):** Return parent generations as the current view does (unchanged).
3. **Add** a computed column `is_segment_identity BOOLEAN` so consumers can distinguish if needed (optional — only if UI needs to know).
4. **Index consideration:** The `COUNT(*)` subquery checking child count should be efficient with the existing `idx_generations_parent_generation_id` index. Verify with `EXPLAIN ANALYZE` on a real dataset.

Example SQL shape:
```sql
CREATE OR REPLACE VIEW shot_final_videos AS
-- Single-child parents: return the child directly
SELECT c.id, c.location, c.thumbnail_url, c.type, c.created_at, c.updated_at,
       c.params, c.starred, c.project_id, sg.shot_id
FROM generations p
JOIN shot_generations sg ON sg.generation_id = p.id
JOIN generations c ON c.parent_generation_id = p.id AND c.is_child = true
WHERE p.parent_generation_id IS NULL
  AND c.location IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM generations c2 
    WHERE c2.parent_generation_id = p.id AND c2.is_child = true AND c2.id != c.id
  )
UNION ALL
-- Multi-child or orchestrator parents: return parent as before
SELECT g.id, g.location, g.thumbnail_url, ...
FROM generations g
JOIN shot_generations sg ON sg.generation_id = g.id
WHERE g.parent_generation_id IS NULL
  AND g.type = 'video'
  AND (g.params->'orchestrator_details' IS NOT NULL
       OR EXISTS (SELECT 1 FROM generations c WHERE c.parent_generation_id = g.id))
  AND (SELECT COUNT(*) FROM generations c WHERE c.parent_generation_id = g.id AND c.is_child = true) != 1;
```

5. **Test** with SQL editor: verify single-child shots return child, multi-child shots return parent.
