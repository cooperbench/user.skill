## Problem 1: Monolithic execution
The execute step runs ALL tasks in a single agent subprocess that can last hours. This forces complex recovery machinery (incremental saves, session persistence, reconciliation, timeout recovery) and prevents the harness from observing between tasks. The harness should be the one tracking progress, not the agent.

## Solution: Batched execution with harness observation
The finalize step already produces an ordered task list with depends_on relationships. The orchestrator should:
1. Group tasks into dependency-respecting batches (independent tasks can batch together, dependent tasks sequence)
2. Run each batch as a separate agent subprocess
3. Between batches: harness runs git diff, checks what changed, updates finalize.json based on OBSERVATION not agent self-report
4. If a batch times out or fails, only that batch is lost — prior batches are already persisted

This eliminates most of the timeout recovery, incremental save, and reconciliation machinery we just built. The harness becomes the source of truth.

## Problem 2: Planning loop is a local optimizer
Critique→gate→revise is great at finding bugs within a plan but cannot question whether the plan is the right approach. Today we spent 2 iterations refining a streaming+parsing approach before a human said 'just tell the agent to save as it goes.'

## Solution: Simplicity checkpoint in the critique
Add a simplicity dimension to the critique step. The critic should ask: 'Is this the simplest approach that solves the stated problem? Could this be done with fewer steps or less machinery?' This isn't a new step — it's a new lens for the existing critique. Flag plans that add complexity beyond what the problem requires. The gate already weighs flags, so over-engineering flags naturally influence the PROCEED/ITERATE decision.

This is the KISS principle applied to the planning loop — the critic becomes the devil's advocate for simplicity, not just correctness.

## Phase 2: Task Batching Core

### Step 3: Implement dependency-respecting batch computation (`megaplan/_core.py`)
**Scope:** Medium
1. **Add** a function `compute_task_batches(tasks: list[dict]) -> list[list[str]]` that takes the task list from finalize.json and returns ordered batches of task IDs.
   - Algorithm: topological sort grouping. Tasks with no unresolved `depends_on` go in the first batch. Once a batch is "complete," tasks whose dependencies are all in prior batches form the next batch. Repeat until all tasks are scheduled.
   - Raise `ValueError` if a cycle is detected.
   - Independent tasks (no dependencies between them) land in the same batch.
   ```python
   # Example:
   # T1: depends_on=[], T2: depends_on=[], T3: depends_on=["T1"], T4: depends_on=["T1","T2"]
   # → [["T1","T2"], ["T3","T4"]]
   ```
2. **Handle** edge cases: tasks with unknown dependency IDs (warn and treat as batch-0), empty task list (return []).

### Step 4: Test batch computation (`tests/test_core.py` or `tests/test_megaplan.py`)
**Scope:** Small
1. **Test** linear chain: T1→T2→T3 → 3 batches of 1 each.
2. **Test** independent tasks: T1, T2, T3 with no deps → 1 batch of 3.
3. **Test** diamond: T1→T2, T1→T3, T2→T4, T3→T4 → [[T1],[T2,T3],[T4]].
4. **Test** cycle detection raises ValueError.
5. **Test** unknown dependency ID handled gracefully.

## Phase 3: Batched Execution Handler

### Step 5: Refactor execute prompt for per-batch execution (`megaplan/prompts.py:459-608`)
**Scope:** Medium
1. **Add** a `batch_task_ids: list[str] | None` parameter to `_execute_prompt()`.
2. **When** `batch_task_ids` is provided, modify the prompt to:
   - Include only the tasks in this batch (plus completed tasks from prior batches as read-only context).
   - Explicitly state which tasks are in scope and which are already done.
   - Tell the agent to only produce `task_updates` for the batch tasks.
3. **When** `batch_task_ids` is None, preserve the existing full-execution prompt for backward compatibility.

### Step 6: Implement batched execution loop in `handle_execute` (`megaplan/handlers.py:1571-1741`)
**Scope:** Large
1. **At entry** (after loading finalize.json, ~line 1611), call `compute_task_batches()` to get the batch plan.
2. **Loop** over batches:
   a. Build a per-batch execute prompt via updated `_execute_prompt(batch_task_ids=batch)`.
   b. Launch agent subprocess via `run_step_with_worker()`.
   c. Merge `task_updates` into `finalize_data` (reuse existing merge logic at lines 1615-1632).
   d. Run `validate_execution_evidence()` against git diff — this is the harness observation step.
   e. Write intermediate `finalize.json` after each batch (harness persistence, not agent self-report).
   f. If a batch fails/times out, stop the loop. Prior batches are already persisted.
3. **After** the loop, run the existing post-execution logic (sense-check merge, reconciliation, audit, blocking-reason checks) against the accumulated finalize_data.
4. **Record** batch execution metadata in history: number of batches planned, number completed, per-batch duration/cost.
5. **Preserve** single-batch fast path: if `compute_task_batches()` returns a single batch, run the current monolithic path to avoid unnecessary overhead.

### Step 7: Simplify timeout recovery (`megaplan/handlers.py:434-530`)
**Scope:** Medium
1. **With** batched execution, timeout recovery becomes simpler: prior batches are already persisted to finalize.json, so only the current batch is lost.
2. **Update** `_recover_execute_timeout` to only reset tasks from the current batch, not scan all tasks.
3. **Keep** the timeout recovery function for now but simplify its logic — full removal can come later once batched execution is proven stable.

### Step 8: Update execute tests (`tests/test_megaplan.py`, `tests/test_workers.py`)
**Scope:** Medium
1. **Add** a test with 2+ batches: mock worker returns batch-1 results, then batch-2 results. Verify finalize.json has all tasks updated.
2. **Add** a test where batch-2 times out: verify batch-1 tasks are persisted as done, batch-2 tasks remain pending.
3. **Add** a test with single batch (no dependencies): verify it takes the fast path (single worker call).
4. **Update** existing execute tests that mock a single worker call — ensure they still pass (the single-batch fast path should handle this).
5. **Test** that the harness observation (git diff check between batches) records findings in execution_audit.json.

## Phase 2: Task Batching Core

### Step 3: Implement dependency-respecting batch computation (`megaplan/_core.py`)
**Scope:** Medium
1. **Add** a function `compute_task_batches(tasks: list[dict], completed_ids: set[str] | None = None) -> list[list[str]]` that takes the task list from finalize.json and returns ordered batches of task IDs for *pending* tasks only.
   - `completed_ids` is the set of task IDs already done/skipped (from prior runs or earlier batches). These are treated as satisfied dependencies but are not included in any output batch.
   - Algorithm: topological sort grouping over pending tasks. A pending task's `depends_on` is satisfied if every dependency is either in `completed_ids` or in a prior batch. Tasks with all dependencies satisfied go in the current batch. Repeat until all pending tasks are scheduled.
   - Raise `ValueError` if a cycle is detected (pending tasks remain after all resolvable batches are computed).
   - Raise `ValueError` if any `depends_on` ID references a task ID not present in *either* the task list or `completed_ids`. Unknown IDs are invalid graphs.
   - Independent tasks (no dependencies between them) land in the same batch.
   ```python
   # Fresh run: all pending
   # T1: depends_on=[], T2: depends_on=[], T3: depends_on=["T1"], T4: depends_on=["T1","T2"]
   # → [["T1","T2"], ["T3","T4"]]

   # Rerun: T1 already done, T2-T4 pending
   # compute_task_batches(tasks=[T2,T3,T4], completed_ids={"T1"})
   # T2: depends_on=[] → batch 1, T3: depends_on=["T1"] → batch 1 (T1 satisfied), T4: depends_on=["T1","T2"] → batch 2
   # → [["T2","T3"], ["T4"]]
   ```
2. **Handle** edge case: empty task list returns `[]`.

## Phase 4: Batched Execution Handler

### Step 7: Implement batched execution loop in `handle_execute` (`megaplan/handlers.py:1571-1741`)
**Scope:** Large

The core design principle: the harness loops over batches, persists after each, and validates agent claims against git observation. Merge/blocking checks run only after all batches complete, so intermediate batches don't trigger incomplete-tracking blockers.

1. **At entry** (after loading finalize.json, ~line 1611):
   - Partition tasks into done/skipped (`completed_ids`) and pending.
   - Call `compute_task_batches(pending_tasks, completed_ids=completed_ids)` to get the batch plan. This correctly handles reruns where earlier tasks are already done — completed tasks satisfy dependencies without appearing in batches.
   - If result is a single batch, take the existing monolithic path (no behavior change for existing tests).
2. **Multi-batch loop:** For each batch (batch index `i` of `N`):
   a. **Snapshot** file content hashes for files currently in `git status --short` using `git diff --name-only HEAD` to capture the full set of modified-vs-HEAD paths. Store as `pre_batch_paths: set[str]`.
   b. **Build** a per-batch prompt via `_execute_batch_prompt(state, plan_dir, batch_task_ids, completed_task_ids)`.
   c. **Launch** agent subprocess via `run_step_with_worker(..., prompt_override=batch_prompt)`.
   d. **Observe** changes via `git diff --name-only HEAD` after the batch. Compute `post_batch_paths: set[str]`. The files this batch touched are `post_batch_paths - pre_batch_paths` (newly dirty) PLUS any files the agent claimed in `files_changed` that were already in `pre_batch_paths` (re-edited files). This handles the cross-batch re-edit case: if `handlers.py` was dirty before *and* after the batch and the agent claims it, the claim is accepted. If the agent claims a file that was dirty before and after but *not* in their `files_changed`, no false positive occurs.
   e. **Cross-reference** agent's claimed `files_changed` in `task_updates` against the observed set. Log discrepancies as deviations: phantom claims (agent claims a file not in the observed set and not previously dirty) and unclaimed changes (newly dirty files not claimed by any task).
   f. **Merge** `task_updates` into `finalize_data` using existing `_validate_and_merge_batch()` — scoped to this batch's tasks only.
   g. **Merge** `sense_check_acknowledgments` for this batch's sense checks into `finalize_data` using existing `_validate_and_merge_batch()` — scoped to sense checks whose `task_id` is in the current batch. This ensures sense check progress is persisted per-batch, not deferred.
   h. **Persist** `finalize.json` to disk immediately after both merges. This is the key safety property: prior batches' task updates *and* sense check acknowledgments are committed to disk before the next batch starts.
   i. **Update** `completed_task_ids` with this batch's successfully completed tasks (for use in the next batch's dependency resolution and prompt context).
   j. **Accumulate** per-batch cost/duration for history recording.
   k. **On timeout/failure:** catch `CliError(worker_timeout)` for this batch only. Prior batches are already persisted (both tasks and sense checks). Record the failure and break out of the loop — don't call `_recover_execute_timeout` (the harness already persisted prior state).
3. **After loop completes** (all batches or early exit):
   a. **Build** aggregate `execution.json` by merging all batch worker payloads: concatenate `files_changed`, `commands_run`, `deviations`, `task_updates`, `sense_check_acknowledgments` across batches. Set `output` to a summary like "Executed N/M batches. K tasks completed."
   b. **Run** existing blocking-reason checks (untracked tasks, unacked sense checks, missing evidence) against the final `finalize_data`. Since sense checks were merged per-batch, the count reflects all completed batches accurately.
   c. **Run** `validate_execution_evidence()` as the final aggregate audit.
   d. **Proceed** with existing state transition, history recording, and response building.
4. **History metadata:** Record `batches_planned`, `batches_completed`, and per-batch durations in the history entry's extra data.
