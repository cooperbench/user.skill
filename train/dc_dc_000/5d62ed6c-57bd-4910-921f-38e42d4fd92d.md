# Wire timeline drop to use the existing local-file-handle flow

Read CLAUDE.md at the repo root first — it has cross-cutting rules and points to relevant sub-docs.

## Problem

When a user drops a large file onto the **timeline**, it always uploads to Supabase Storage. It should instead use the existing local-file-handle flow (`storage_mode='local'` + `local_handle_id`, served via `useLocalMediaUrl()` with `LocalMediaPermissionOverlay` as the recovery UX) — the same way the gallery's `useDropToGeneration` already works for large files.

## What already exists (do NOT rebuild)

- **Local-handle write path**: `src/shared/lib/media/createGenerationFromFile.ts` — `createGenerationForLocalFile()` writes `storage_mode='local'` + `local_handle_id` and persists the handle via `saveHandle()` from `src/shared/lib/media/localHandleStore.ts`.
- **Threshold + browser-capability gate**: `src/features/gallery/hooks/useDropToGeneration.ts` checks file size against `IMAGE_INLINE_UPLOAD_LIMIT_BYTES` from `src/shared/lib/media/dropToGenerationConfig.ts` AND that `DataTransferItem.getAsFileSystemHandle()` is available. Use the **same** gate.
- **Resolver + permission UX**: `useLocalMediaUrl()` in `src/shared/media/localMediaResolver.ts` and `LocalMediaPermissionOverlay.tsx` already handle rendering + recovery — no changes needed there.

## What's broken

The timeline drop pipeline is a separate, older path that never got updated:

- Drop handler chain ends at `useDropActions.handleTimelineImageDrop` → calls `processDroppedImages` in `src/shared/hooks/shots/externalImageDrop.ts`.
- `processDroppedImages` only receives `File[]`. It calls `processSingleDroppedImage`, which **unconditionally** calls `createGenerationForUploadedImage`. No size check, no `getAsFileSystemHandle()` probe, no local branch.

There is also an intermediate chain of timeline drop hooks (in the travel-between-images tool) that strips/discards `DataTransferItem` info before it reaches `useDropActions`. Those hooks must be updated to capture and forward handles.

## The fix

1. **Capture the `FileSystemFileHandle` synchronously** at the timeline drop event boundary. The `DataTransferItem.getAsFileSystemHandle()` call MUST happen synchronously inside the drop handler (or its returned promises captured before any await), because `DataTransferItem` is invalidated after the event resolves. Look at how `useDropToGeneration` does this and replicate the pattern.

2. **Thread an optional `FileSystemFileHandle | null` array through** the timeline drop hooks → `useDropActions.handleTimelineImageDrop` → `ExternalImageDropVariables` → `processDroppedImages` → `processSingleDroppedImage`. The new array is parallel to `imageFiles`. Make it optional so non-timeline callers aren't broken.

3. **Branch in `processSingleDroppedImage`** using the same gate as `useDropToGeneration` — file size ≥ `IMAGE_INLINE_UPLOAD_LIMIT_BYTES` AND a handle is present. When the gate passes, call `createGenerationForLocalFile`. Otherwise keep current behavior (`createGenerationForUploadedImage`).

4. **Crop interaction (important)**: `cropFilesIfNeeded` may return a *new* `File` for a given input. If it did, the captured handle no longer corresponds to the bytes you're storing — fall back to upload in that case. Use reference equality (`processedFile === originalFile`) to detect this.

5. **Don't break callers.** The new param is optional. Other callers of `processDroppedImages` (batch drop, app-level drop, shot-creation flows) keep current behavior unchanged because they don't supply handles.

## Constraints

- Don't refactor unrelated code. Don't add new abstractions. Don't add comments explaining the change.
- Reuse existing helpers from `useDropToGeneration` if possible (e.g. the `supportsLocalFileHandles()` probe pattern). Keep the gate condition identical to what the gallery uses so behavior stays consistent.
- The `local_handle_id` is a UUID generated client-side and is the link between the DB row and the IndexedDB-persisted handle. Mirror exactly how the gallery flow generates and stores it.

        # Implementation Plan: Wire Timeline Drop to the Local-File-Handle Flow

## Overview
The timeline drop path (`useUnifiedDrop` → `useDropActions.handleTimelineImageDrop` → `useHandleExternalImageDrop` mutation → `processDroppedImages` → `processSingleDroppedImage` → `createGenerationForUploadedImage`) unconditionally uploads to Supabase Storage and never captures `FileSystemFileHandle`s. The gallery drop path (`useDropToGeneration`) already implements the local-handle flow against the same `IMAGE_INLINE_UPLOAD_LIMIT_BYTES` gate, calling `createGenerationForLocalFile` for large images.

We will: (1) capture handles synchronously at the timeline drop event, (2) thread an optional `Array<FileSystemFileHandle | null>` parallel to `imageFiles` through the timeline pipeline into `processDroppedImages`/`processSingleDroppedImage`, and (3) reuse the `useDropToGeneration` gate (`size ≥ IMAGE_INLINE_UPLOAD_LIMIT_BYTES` AND a usable handle) to branch into `createGenerationForLocalFile`. All non-timeline callers of `processDroppedImages` (`ShotListView`, `App.tsx`, `useModalImageHandlers`, shot-creation flows) keep working because the new param is optional and defaults to absent → upload path.

The crop steps complicate things: `useDropActions.handleTimelineImageDrop` calls `cropImagesToShotAspectRatio` *before* invoking the mutation, and `processDroppedImages` then calls `cropFilesIfNeeded` again. Both can return *new* `File`s. We use reference equality (`processedFile === originalFile`) at each crop boundary and null out the handle if the bytes diverged.

## Constraints
- New param everywhere is optional. No behavior change for callers that don't supply it.
- Keep the gate logic identical to `useDropToGeneration`: `file.size >= IMAGE_INLINE_UPLOAD_LIMIT_BYTES` AND `getAsFileSystemHandle()` resolves to a kind-`file` handle with `getFile`.
- Don't refactor unrelated code; don't add comments justifying the change.
- Pre-existing tsc error in `useDropToGeneration.ts` (FileSystemFileHandle missing `queryPermission`/`requestPermission` lib types) is acceptable to mirror.
