**Findings**

1. High: the plan still mixes requested state and effective state, which will create UX loss and make rehydration ambiguous. It defines `generationTypeMode` as user-authored, then says hooks should still snap it reactively and auto-clear `smoothContinuations` when unsupported. That means the system will silently overwrite user intent instead of preserving “what I wanted” vs “what this model/mode can do right now”. See [squishy-finding-lamport.md#L73](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L73), [squishy-finding-lamport.md#L124](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L124), [squishy-finding-lamport.md#L236](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L236), [squishy-finding-lamport.md#L414](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L414). Current code already mutates mode eagerly in [useStructureVideoHandlers.ts#L52](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/video/useStructureVideoHandlers.ts#L52), [useStructureVideoHandlers.ts#L84](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/video/useStructureVideoHandlers.ts#L84), [useStructureVideoHandlers.ts#L134](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/video/useStructureVideoHandlers.ts#L134), and persists mode-dependent defaults in [useVideoTravelSettingsHandlers.ts#L321](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/hooks/settings/useVideoTravelSettingsHandlers.ts#L321). If painless model addition is the goal, requested/effective split is not future work; it is the prerequisite.

2. High: the registry is not actually becoming the single source of truth for model integration. The plan keeps a static `defaultWorkerModelName` and punts “full backend model resolution” to later, but current generation still resolves actual worker model names in a separate path and task rehydration still infers selected model from string heuristics. See [squishy-finding-lamport.md#L18](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L18), [squishy-finding-lamport.md#L415](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L415), [generateVideoService.ts#L223](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideoService.ts#L223), [modelPhase.ts#L20](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/modelPhase.ts#L20), [taskDataService.ts#L111](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/taskDataService.ts#L111). As written, adding a new model still requires touching registry code, phase-selection code, and rehydration heuristics.

3. High: cross-repo standardization is still deferred even though that is the core maintainability problem. The frontend registry would encode capabilities, while the worker independently interprets continuation strategy semantics from payload, and the doc explicitly leaves a shared transport schema for later. See [squishy-finding-lamport.md#L42](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L42), [squishy-finding-lamport.md#L272](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L272), [squishy-finding-lamport.md#L417](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L417). If you add more continuation types without a shared manifest or generated schema, drift is guaranteed.

4. Medium: `model_type` remains a misleading transport name. In the proposal it still carries execution mode, while `selectedModel` and `model_name` carry model identity. That is workable today, but it is exactly the kind of naming collision that becomes painful once more model families land. - Persist `requestedExecutionMode` and `requestedSmoothContinuations` separately from `effectiveExecutionMode` and `effectiveContinuation`. Do not auto-clear the requested values.
- Make one shared contract describe `model_id`, `execution_mode`, `continuation_strategy`, `overlap_frames`, and any strategy traits the worker needs such as `requires_sequential_segments`, `requires_stitch`, `uses_video_source`, `uses_guide`, `uses_mask`.

- Treat `ContinuationConfig` as transport, but keep a richer `ContinuationSpec` in code so future strategies do not force more special-case gates.

Net: the proposal is directionally good, but the two things that actually make future model additions painless are still out of scope: preserving requested vs effective state, and having one shared client/worker schema.
