# Plan 4 — OOB guardrail + significance scoring

Authoritative spec: `mediator-bot-spec.md`. Read in prep, focusing on: "Out-of-Bounds Guardrail", "Significance Scoring", and the relevant parts of "Tools" and "Prompts".

Plans 1–3 are assumed complete. The agentic loop currently calls a pass-through `check_oob` and a stub `score_observation` returning 3. This plan replaces both with real implementations.

## Scope (in)

### OOB guardrail (real `check_oob`)
- Replace the pass-through with a real LLM call against the recipient's active OOB entries.
- Use Claude Sonnet (same model as the conversational loop), so the second check is at least as smart as the first.
- Inputs: the draft outbound, the recipient's active OOB entries, and a short sender-intent summary (the loop already has this — pass it in).
- Outputs: `{verdict: 'ok' | 'rewrite' | 'block', reason: string, suggested_rewrite: string | null, checker_failed: bool}`.
- On `rewrite`: the loop receives the suggestion as a tool result and decides whether to accept or re-draft. Document the contract.
- On `block`: the message doesn't send; the loop is told why so it can produce an alternative or stay silent.
- Belt-and-suspenders: the LLM also has OOB context in the main loop's hot context (already wired in Plan 3). The duplication is intentional — keep both.

### Failure mode
- On checker timeout or error:
  - For `firm` and `hard` OOB → fail closed (don't send, queue for retry, surface in admin).
  - For `soft` OOB only → fail open with a logged warning.
- The `checker_failed` flag travels on the result so the loop can react.

### OOB countersummary (on demand)
- Compute on demand, not stored. When asked, read the partner's active OOB entries and produce a topic-level summary that strips identifying detail — categories of sensitive content only, never quotes or paraphrases.
- Output shape: counts plus topic clusters, e.g., `"three entries related to family history, two related to past relationships"`.
- If the OOB owner has only one entry on a niche topic, the summary stays vague ("one entry related to a personal matter").
- This logic lives in a function the main loop calls when the user asks "what topics has she asked you not to share?". The system prompt's countersummary language guidance was set in Plan 3; this plan supplies the function it relies on.

### Significance scoring (real `score_observation`)
- Replace the stub with a Claude Haiku call (latest — default `claude-haiku-4-5-20251001`).
- Focused single-shot prompt that includes the five anchor examples inline (1=Trivial, 2=Minor, 3=Notable, 4=Significant, 5=Core) per spec.
- Output: `{score: int (1-5), reason: string}`.
- The score is stored on the observation alongside `scoring_prompt_version` (bump from `v0-stub` to `v1`).
- Failure mode: per spec, write the observation without a score and flag for re-scoring during weekly housekeeping (the housekeeping pass is in Plan 5; here, just leave `significance` null and add a `needs_rescoring=true` note in metadata or via status).

### Re-scoring support
- A small CLI/admin function `rescore_observations(prompt_version_threshold)` that finds observations scored under an older prompt version and re-scores them. Not auto-run, but available for manual invocation when the prompt evolves.

## Scope (out, deliberately)

- Admin UI for OOB management (Plan 6).
- Conversational OOB management ("don't bring up X again") — already handled by the natural-language flow in Plan 3 via `add_oob`/`lift_oob` tools; no changes here.
