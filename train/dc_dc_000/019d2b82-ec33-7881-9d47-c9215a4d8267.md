        # Implementation Plan: Model Benchmarking Harness

## Overview

The hermes-agent repo has a mature eval pipeline in `evals/` that orchestrates megaplan phases (plan → critique → gate → finalize → execute → review) via subprocess calls to the `megaplan` binary. Each phase runs a Hermes worker session with a specific model, producing JSON artifacts in `.megaplan/plans/<name>/`.

The benchmark harness needs to test **each model on each phase independently** — not a full pipeline run. This means: for each (model, eval, phase) triple, we init a megaplan workspace, run just that one phase, and score the output. The existing `run_megaplan_loop()` handles the full pipeline; we'll reuse `_megaplan_command()`, `_megaplan_env()`, `config_phase_model_args()`, `prepare_workspace()`, and `check_build()` but bypass the loop.

**Key constraint:** The megaplan binary requires `init` before any phase can run, and later phases (critique, execute, review) require artifacts from earlier phases. We can't truly run phases in isolation without providing their input artifacts. The plan below addresses this with **canned fixtures** — pre-generated artifacts from a reference model run.

**Repo shape:**
- `evals/run_evals.py` — existing megaplan loop, workspace prep, subprocess runner
- `evals/config.py` — `EvalConfig` dataclass, `load_config()`
- `evals/scoring.py` — `check_build()`, `run_eval_ts()`, tool bucketing
- `evals/audit.py` — `EvalAudit`, `PhaseRecord`
- `evals/configs/default.json` — reference config format

### Step 2: Build per-phase scoring functions (`evals/benchmark/scoring.py`)
**Scope:** Medium

1. **Implement** scoring dimensions as a dataclass:
   ```python
   @dataclass
   class PhaseScore:
       json_valid: int          # 0/1 — response parses as JSON
       json_in_content: int     # 0/1 — JSON in content, not reasoning
       required_keys: int       # 0/1 — all required keys present
       tool_use: int            # 0/1 — used appropriate tools
       web_search: int          # 0/1 — used web_search (bonus)
       build_pass: int | None   # 0/1 or None — execute only
       eval_pass: int | None    # 0/1 or None — execute only

       model: str
       eval_name: str
       duration_seconds: float

   ```

2. **Implement** phase-specific validators:
   - `score_plan(response, trace) → PhaseScore` — checks for `success_criteria`, `assumptions`, plan markdown, file_read tool usage

   - `score_execute(response, trace, workspace) → PhaseScore` — checks for file_write/edit tool calls, runs `check_build()` and `run_eval_ts()`
   - `score_review(response, trace) → PhaseScore` — checks for `review_verdict`/`verdict`, `task_verdicts` list

   - plan: `success`, `state` + plan markdown file exists
   - critique: `open_flags`, `success`, `next_step`
   - execute: `success`, `state` (+ tool calls for file modifications)
   - review: `review_verdict` or `verdict`, `success`

## Validation Order
1. **Cheapest first:** Unit tests for scoring functions (Step 7) — no API calls needed.
2. **Single-cell test:** Run one model × one eval × one phase (e.g., `gpt-4.1-mini` × `agent-025` × `plan`) to validate the full path.
3. **Single-model sweep:** Run one model across all phases and evals (12 tests).
4. **Full benchmark:** All 10 models × 3 evals × 4 phases = 120 tests.
