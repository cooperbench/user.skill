# Implementation Plan: Non-Deferrable Stale Subjective Reviews

## Problem Summary

Stale subjective reviews are blocked from the execution queue by 5+ independent guards that all assume subjective work should yield to objective work. Each guard has been individually patched, but the underlying architecture — subjective and objective items sharing lifecycle gates designed for objective-only flow — keeps producing new blockage paths.

## Design Principle

**Stale subjective reviews are non-deferrable.** If a dimension is stale, its `subjective::` ID MUST be present in `queue_order`. The only valid exclusion is an explicit user skip. No gate, guard, lifecycle signal, or phase cleanup may remove or prevent injection of a stale review.

**Execution ordering:** Stale reviews sit after workflow/triage synthetics but before objective items. During workflow/triage phases, workflow/triage items are the active execution work; stale reviews become the active execution items once those phases drain. This is by design — the user specified this priority ordering.

### Step 2: Always run phase resolution (even mid-cycle)
**File:** `desloppify/engine/_plan/sync/pipeline.py` (lines 188-250)
**Risk:** Low — phase resolution is cheap (inspects queue_order).

**Problem addressed:** When objective items keep the queue non-empty, the early return at line 189 skips phase resolution. Stale IDs get injected by Step 1, but the lifecycle phase stays at its old value (e.g., EXECUTE). The snapshot then sees EXECUTE phase and puts stale items in backlog instead of execution items.

**Current structure:**
```python
# Early return blocks EVERYTHING including phase resolution
if not live_planned_queue_empty(plan) and not force_rescan:
    return result

result.auto_cluster_changes = ...
result.communicate_score = ...
result.create_plan = ...
result.triage = ...
result.lifecycle_phase = _resolve_reconcile_phase(...)  # blocked!
result.phase_cleanup_pruned = prune_synthetic_for_phase(...)  # blocked!
```

**New structure:**
```python
# Heavy reconciliation only at queue boundaries
if live_planned_queue_empty(plan) or force_rescan:
    result.auto_cluster_changes = ...
    result.communicate_score = ...
    result.create_plan = ...
    result.triage = ...

# Phase resolution and cleanup ALWAYS run
result.lifecycle_phase = _resolve_reconcile_phase(plan, state, result=result, policy=policy)
result.lifecycle_phase_changed = set_lifecycle_phase(plan, result.lifecycle_phase)
if result.lifecycle_phase_changed:
    _log_gate_changes(plan, "sync_lifecycle_phase", {"phase": result.lifecycle_phase})
result.phase_cleanup_pruned = prune_synthetic_for_phase(plan, result.lifecycle_phase)
if result.phase_cleanup_pruned:
    _log_gate_changes(...)
```

**Why this is safe:** `_resolve_reconcile_phase` checks `result.workflow_injected_ids` and `result.triage` — both are empty/None on the mid-cycle path, so the function just inspects `queue_order` for prefix matching. When stale `subjective::` items are present (without workflow/triage items), it returns `LIFECYCLE_PHASE_ASSESSMENT_POSTFLIGHT`. When workflow items also exist, it returns `LIFECYCLE_PHASE_WORKFLOW_POSTFLIGHT` — this is correct because the user specified stale reviews come AFTER workflow/triage.

**Validation:** `python -m pytest desloppify/tests/plan/test_reconcile_pipeline.py -q` — `test_reconcile_plan_noops_when_live_queue_not_empty` will need updating (the result will now have a lifecycle_phase set even mid-cycle).

### Step 3: Remove `SUBJECTIVE_PREFIX` from phase cleanup
**File:** `desloppify/engine/_plan/sync/phase_cleanup.py` (lines 21-28)
**Risk:** Low — subjective lifecycle is managed exclusively by `sync_subjective_dimensions`.

**Problem addressed:** `prune_synthetic_for_phase()` strips all `subjective::` IDs when entering WORKFLOW_POSTFLIGHT, TRIAGE_POSTFLIGHT, REVIEW_POSTFLIGHT, or EXECUTE. Under the new design, this undoes the injection from the same reconcile pass — stale IDs are injected by sync and then immediately stripped by cleanup.

**Before:**
```python

    if phase == LIFECYCLE_PHASE_WORKFLOW_POSTFLIGHT:
        return (SUBJECTIVE_PREFIX,)
    if phase in {LIFECYCLE_PHASE_TRIAGE_POSTFLIGHT, LIFECYCLE_PHASE_REVIEW_POSTFLIGHT}:
        return (SUBJECTIVE_PREFIX, WORKFLOW_PREFIX)
    if phase == LIFECYCLE_PHASE_EXECUTE:
        return (SUBJECTIVE_PREFIX, WORKFLOW_PREFIX, TRIAGE_PREFIX)
    return ()
```

**After:**
```python
def _phase_prefixes(phase: str) -> tuple[str, ...]:
    if phase == LIFECYCLE_PHASE_WORKFLOW_POSTFLIGHT:
        return ()
    if phase in {LIFECYCLE_PHASE_TRIAGE_POSTFLIGHT, LIFECYCLE_PHASE_REVIEW_POSTFLIGHT}:
        return (WORKFLOW_PREFIX,)
    if phase == LIFECYCLE_PHASE_EXECUTE:
        return (WORKFLOW_PREFIX, TRIAGE_PREFIX)
    return ()
```

**Why this is correct:** Subjective ID lifecycle (inject when stale/unscored, prune when resolved) is already fully managed by `sync_subjective_dimensions`, which runs unconditionally on every reconcile (Step 1). Phase cleanup removing them was redundant and, under the new design, actively harmful. Workflow and triage synthetic cleanup is unaffected.

### Step 4: Make stale items non-deferrable in `dimensions.py`
**File:** `desloppify/engine/_plan/sync/dimensions.py` (lines 237-325)
**Risk:** Medium — this is the core behavioral change.

**Changes to `sync_subjective_dimensions()`:**

1. **Remove `cycle_just_completed` parameter** from the function signature entirely.

2. **Split injectable_ids into stale (non-deferrable) and under-target (deferrable):**
   ```python
   stale_injectable = stale_ids - skipped_ids
   under_target_injectable = under_target_ids - skipped_ids
   ```

3. **Deferral only applies to under-target IDs.** Use `is_mid_cycle(plan)` (already computed) as the cycle gate for under-target deferral:
   ```python
   objective_backlog = has_objective_backlog(state, policy)
   should_defer_ut = objective_backlog and mid_cycle
   escalated = False
   if should_defer_ut and under_target_injectable:
       escalated = _update_deferral(plan, state,
           injectable_ids=under_target_injectable,
           stale_ids=set(),          # stale never deferred
           under_target_ids=under_target_ids,
           skipped_ids=skipped_ids,
       )
   else:
       _clear_defer_meta(plan)
   ```

4. **Prune pass — stale always kept, under-target conditionally evicted:**
   ```python
   ut_evicting = should_defer_ut and not escalated
   if ut_evicting:
       keep_ids = stale_injectable | (set() if mid_cycle else unscored_ids)
   else:
       all_injectable = stale_injectable | under_target_injectable
       keep_ids = all_injectable if mid_cycle else (unscored_ids | all_injectable)
   _prune_subjective_ids(order, keep_ids=keep_ids, pruned=result.pruned)
   ```

5. **Stale injection uses `_promote_subjective_ids` for correct positioning AND repositioning.** This reuses the existing helper which handles both inserting new items and moving existing mispositioned items to after workflow/triage, before objective:
   ```python
   # Capture existing set before promote to track new injections
   existing_before = set(order)

   # Stale: always promote to correct position (after workflow/triage, before objective)
   if stale_injectable:
       _promote_subjective_ids(order, sorted(stale_injectable))
       for sid in sorted(stale_injectable):
           if sid not in existing_before:
               result.injected.append(sid)

   # Under-target: inject or promote based on escalation
   if escalated:
       _promote_subjective_ids(order, sorted(under_target_injectable))
   elif not ut_evicting and under_target_injectable:
       _inject_subjective_ids(order, inject_ids=under_target_injectable, injected=result.injected)
   ```

6. **Update docstring** to reflect the new invariant: stale = non-deferrable, always promoted; under-target = deferrable.

## Display-Layer Suppression: `_suppressed_same_cycle_refresh` (out of scope)

`build_subjective_items()` in `synthetic.py:261-279` contains a display-layer filter that suppresses stale items from the snapshot's `postflight_assessment_items` when ALL of: (a) the lifecycle phase is workflow or triage, (b) the dimension's refresh_reason starts with `review_issue_`, and (c) the assessment timestamp is after the latest trusted audit.

**This does NOT violate the plan's invariant.** The stale ID remains in `queue_order` (non-deferrable). The suppression only hides the item from the snapshot's execution list during workflow/triage phases. Once workflow/triage items are resolved and the phase transitions to ASSESSMENT_POSTFLIGHT, the suppression no longer applies and the stale review surfaces as the active execution item.

**This is consistent with the user's ordering spec.** The user specified "stale reviews should appear AFTER workflow/triage synthetics but BEFORE objective items." During workflow/triage phases, `_resolve_reconcile_phase` returns WORKFLOW_POSTFLIGHT or TRIAGE_POSTFLIGHT (line 100-106), and the execution items are the workflow/triage items. The stale review waits its turn. This is the intended priority ordering — not a bug.

**Why not fix it anyway?** Removing this suppression would surface stale reviews as postflight_assessment_items during workflow phases, but the phase would still be WORKFLOW_POSTFLIGHT (workflow wins in phase resolution), so the snapshot's execution items would still be workflow items. The stale review would appear in `backlog_items` instead — a marginal visibility improvement that doesn't change when the user can act on it. It's a separate UX concern, not part of the systemic queue-membership bug.
