## Main Phase

### Step 1: Author the note (`tmp/hashchain-note.md`)
**Scope:** Small

1. **Create** `tmp/hashchain-note.md` with the following structure, in this order:
   - `# Hash Chains` — single H1 title.
   - **Intro paragraph (~40 words):** define a hash chain as a sequence of entries where each entry stores the SHA-256 hash of the previous entry, cryptographically linking them. Note the genesis entry's `prev_hash` is conventionally all zeros.
   - **Code example** — exactly one fenced code block (```` ```json ````) showing two consecutive entries:
     ```json
     { \"id\": 0, \"data\": \"user_login\", \"prev_hash\": \"0000...00\" }
     { \"id\": 1, \"data\": \"file_read\",  \"prev_hash\": \"a3f1...9c\" }  // = sha256(entry 0)
     ```
     Use truncated hashes (`\"a3f1...9c\"`) so the reader isn't tempted to verify them. Add an inline comment making the linkage explicit.
   - **What it detects (~60 words):** tampering with any past entry. Editing entry N changes its hash, which breaks entry N+1's `prev_hash`, and the mismatch cascades through every subsequent entry. A verifier walks the chain once, recomputing hashes — O(n).
   - **What it does NOT detect (~80 words):** explicitly enumerate all three failure modes from the brief, in this order:
     1. **Truncation of the tail** — chopping off the last K entries leaves a still-valid shorter chain; the chain itself doesn't know its expected length.
     2. **Replacement of the whole chain** — an attacker controlling storage can rebuild the chain from scratch with different contents; every `prev_hash` will be internally consistent.
     3. **Out-of-band modification with full rewrite** — same root cause: if the attacker can recompute every downstream hash after editing, the chain re-validates.
     One-sentence mitigation: pin the latest hash somewhere the attacker can't rewrite (signed checkpoint, external witness, append-only/WORM store, public ledger).
   - **Use case (~50 words):** audit/event logs. Servers append security events (logins, privilege changes, file accesses), each chained to the previous one. A periodic checkpoint of the head hash is signed and shipped off-host. After an incident, you can prove no historical entry was edited unless the attacker rewrote every event since.
   - Target prose body: ~250 words (acceptable 225–275, code block excluded).

2. **Self-check** before saving: file is fully self-contained (no external links, no images, no repo-specific paths) and renders as plain CommonMark.
