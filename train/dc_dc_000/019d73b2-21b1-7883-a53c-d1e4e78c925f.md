        # Implementation Plan: Fix Planning Lifecycle — Real In-Progress State, Status Enrichment, Doc Parity

## Overview

Megaplan's planning lifecycle has four honest gaps:

1. **No in-progress indicator**: When a worker (plan, prep, critique, etc.) is running, `state.json` still shows the *previous* completed state (e.g. `initialized`). Status reports the plan as idle when it's actively working. There is no `active_step` concept.

2. **Status is anemic**: `handle_status` (`cli.py:82-95`) returns `state`, `iteration`, `next_step`, `valid_next`, and artifact list. It doesn't expose session metadata, cost accumulation, last step duration, or whether a worker is currently running.

3. **`watch` is documented but unimplemented**: README:91, `instructions.md:116` both reference `megaplan watch --plan <name>`. No parser entry, no handler, no implementation exists.

4. **Standard/light planning collapses investigation into a black box**: Heavy robustness runs `init → prep → plan`. Standard overrides `initialized` to skip directly to `plan` (`workflow.py:76-78`). This means the planning agent silently does all codebase investigation inside the plan step with no visible prep artifact and no way to inspect what it found before the plan is generated.

5. **Subagent command reference is stale**: `claude_subagent_appendix.md:247-273` omits `list`, `watch` (which doesn't exist anyway), and the step-editing commands that `instructions.md` documents.

### Design constraint
The idea explicitly says: "Do not force execute-style checkpointing or batch semantics onto planning." The fix should be lightweight metadata — not task tracking, batch numbering, or progress percentages applied to planning phases.

## Phase 1: Active-Step Metadata and Status Enrichment

### Step 1: Add `active_step` field to state types (`megaplan/types.py`)
**Scope:** Small
1. **Add** an `ActiveStep` TypedDict at `megaplan/types.py:~52`:
   ```python
   class ActiveStep(TypedDict, total=False):
       step: str           # "plan", "prep", "critique", etc.
       started_at: str     # ISO UTC timestamp
       session_key: str    # session key being used
       agent: str          # "claude", "hermes", "codex"
   ```
2. **Add** `active_step: NotRequired[ActiveStep]` to `PlanState` at `megaplan/types.py:111`.

### Step 2: Write active_step before worker, clear on completion/error (`megaplan/handlers.py`)
**Scope:** Medium
1. **Add** a helper `_set_active_step(plan_dir, state, step, agent)` that writes the `active_step` field and calls `save_state`.
2. **Call** `_set_active_step` at the start of each handler that invokes `_run_worker` — before the worker call. Key handlers: `handle_plan` (`:667`), `handle_prep` (`:713`), `handle_critique` (`:734`), `handle_revise`, `handle_gate`, `handle_finalize`, `handle_execute`, `handle_review`.
3. **Clear** `active_step` in `_finish_step` (`:174`) after the worker completes — `state.pop("active_step", None)`.
4. **Clear** `active_step` in the `except` path of `_run_worker` (`:145-149`) via `record_step_failure` or directly, so a crashed worker doesn't leave stale metadata. Note: if the process is killed, the field will remain — status should handle staleness (see Step 3).
5. **Determine** the agent string before the worker call. Currently `_run_worker` returns the agent; we need it before. The agent selection logic is in `workers.py:run_step_with_worker`. Factor out `resolve_agent(step, state, args)` that returns the agent string without running the worker, or read it from the args/state config. The simplest approach: `args.agent or state["config"].get("agents", {}).get(step, "claude")` — check the exact logic in `run_step_with_worker`.

### Step 3: Enrich `handle_status` to surface active_step and session metadata (`megaplan/cli.py:82-95`)
**Scope:** Small
1. **Add** `active_step` to the status response when present in state — exposes what's currently running.
2. **Add** a staleness check: if `active_step` is present but `started_at` is older than a reasonable threshold (e.g. 2 hours), mark it as `"possibly_stale": true` so the consumer knows to investigate rather than trusting it blindly.
3. **Add** `sessions` summary to status: map of session keys to their `last_used_at` timestamps, so the consumer can see what sessions are active.
4. **Add** `last_step` summary: the most recent `history` entry's step name, result, and duration_ms, giving a "what just happened" signal.
5. **Add** `total_cost_usd` from `state["meta"].get("total_cost_usd", 0)`.

### Step 4: Update tests for active_step and enriched status (`tests/test_megaplan.py`)
**Scope:** Medium

## Overview

Megaplan's planning lifecycle has four honest gaps:

1. **No in-progress indicator**: When a worker (plan, prep, critique, etc.) is running, `state.json` still shows the *previous* completed state (e.g. `initialized`). Status reports the plan as idle when it's actively working. There is no `active_step` concept.

2. **Status is anemic**: `handle_status` (`cli.py:82-95`) returns `state`, `iteration`, `next_step`, `valid_next`, and artifact list. It doesn't expose session metadata, cost accumulation, last step duration, or whether a worker is currently running.

3. **`watch` is documented but unimplemented**: README:91, `instructions.md:116` both reference `megaplan watch --plan <name>`. No parser entry, no handler, no implementation exists.

4. **Standard/light planning collapses investigation into a black box**: Heavy robustness runs `init → prep → plan`. Standard overrides `initialized` to skip directly to `plan` (`workflow.py:76-78`). This means the planning agent silently does all codebase investigation inside the plan step with no visible prep artifact and no way to inspect what it found before the plan is generated.

5. **Subagent command reference is stale**: `claude_subagent_appendix.md:247-273` omits `list` and `watch` from the command reference. Phase routing instructions only show `prep` for heavy.

### Design constraint
The idea explicitly says: "Do not force execute-style checkpointing or batch semantics onto planning." The fix should be lightweight metadata — not task tracking, batch numbering, or progress percentages applied to planning phases.

### Key verified facts
- **Prep is already consumed by planning**: `_plan_prompt()` (`prompts/planning.py:87`) calls `_render_prep_block(plan_dir)` which reads `prep.json` from disk (`prompts/_shared.py:124-252`). Adding prep to standard/light will produce an artifact that the plan step actually reads. (Settles FLAG-002/scope.)
- **`resolve_agent_mode()` is side-effect-free**: `workers.py:1142-1227` resolves agent, mode, refreshed, and model from args/config without running any worker. It can be called before `_run_worker` to populate `active_step`. (Settles FLAG-001/correctness.)
- **Status response consumers are additive**: The subagent reads `state`, `next_step`, `valid_next` from status output by name. Adding new fields is non-breaking. (Settles callers-1.)
- **Execute already calls `resolve_agent_mode` early**: `handle_execute` (`handlers.py:1069`) resolves agent before dispatch. Active-step can be set between resolution and dispatch. (Settles callers-2 for execute.)
- **Tiny critique stubs without calling `_run_worker`**: `handle_critique` (`handlers.py:741-791`) takes a fast path that creates a stub critique. Active-step must only be set on the real-worker path, not the stub path. (Settles all_locations.)

## Overview

Megaplan's planning lifecycle has four honest gaps:

1. **No in-progress indicator**: When a worker (plan, prep, critique, etc.) is running, `state.json` still shows the *previous* completed state (e.g. `initialized`). Status reports the plan as idle when it's actively working. There is no `active_step` concept.

2. **Status is anemic**: `handle_status` (`cli.py:82-95`) returns `state`, `iteration`, `next_step`, `valid_next`, and artifact list. It doesn't expose session metadata, cost accumulation, last step duration, or whether a worker is currently running.

3. **`watch` is documented but unimplemented**: README:91, `instructions.md:116` both reference `megaplan watch --plan <name>`. No parser entry, no handler, no implementation exists.

4. **Standard/light planning collapses investigation into a black box**: Heavy robustness runs `init → prep → plan`. Standard overrides `initialized` to skip directly to `plan` (`workflow.py:76-78`). This means the planning agent silently does all codebase investigation inside the plan step with no visible prep artifact and no way to inspect what it found before the plan is generated.

5. **Subagent command reference is stale**: `claude_subagent_appendix.md:247-273` omits `list` and `watch` from the command reference. Phase routing instructions only show `prep` for heavy.

## Overview

Megaplan's planning lifecycle has four honest gaps:

1. **No in-progress indicator**: When a worker (plan, prep, critique, etc.) is running, `state.json` still shows the *previous* completed state (e.g. `initialized`). Status reports the plan as idle when it's actively working. There is no `active_step` concept.

2. **Status is anemic**: `handle_status` (`cli.py:82-95`) returns `state`, `iteration`, `next_step`, `valid_next`, and artifact list. It doesn't expose session metadata, cost accumulation, last step duration, or whether a worker is currently running.

3. **`watch` is documented but unimplemented**: README:91, `instructions.md:116` both reference `megaplan watch --plan <name>`. No parser entry, no handler, no implementation exists.

4. **Standard/light planning collapses investigation into a black box**: Heavy robustness runs `init → prep → plan`. Standard overrides `initialized` to skip directly to `plan` (`workflow.py:76-78`). This means the planning agent silently does all codebase investigation inside the plan step with no visible prep artifact and no way to inspect what it found before the plan is generated.

5. **Subagent command reference is stale**: `claude_subagent_appendix.md:247-273` omits `list` and `watch` from the command reference. Phase routing instructions only show `prep` for heavy.

### Design constraint
The idea explicitly says: "Do not force execute-style checkpointing or batch semantics onto planning." The fix should be lightweight metadata — not task tracking, batch numbering, or progress percentages applied to planning phases.

### Key verified facts
- **Prep is already consumed by planning**: `_plan_prompt()` (`prompts/planning.py:87`) calls `_render_prep_block(plan_dir)` which reads `prep.json` from disk (`prompts/_shared.py:124-252`). Adding prep to standard/light will produce an artifact that the plan step actually reads. (Settles FLAG-002/scope.)
