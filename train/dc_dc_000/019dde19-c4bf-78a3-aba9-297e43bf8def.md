## Scope (in)

### OOB guardrail (real `check_oob`)
- Replace the pass-through with a real LLM call against the recipient's active OOB entries.
- Use Claude Sonnet (same model as the conversational loop), so the second check is at least as smart as the first.
- Inputs: the draft outbound, the recipient's active OOB entries, and a short sender-intent summary (the loop already has this — pass it in).
- Outputs: `{verdict: 'ok' | 'rewrite' | 'block', reason: string, suggested_rewrite: string | null, checker_failed: bool}`.
- On `rewrite`: the loop receives the suggestion as a tool result and decides whether to accept or re-draft. Document the contract.
- On `block`: the message doesn't send; the loop is told why so it can produce an alternative or stay silent.
- Belt-and-suspenders: the LLM also has OOB context in the main loop's hot context (already wired in Plan 3). The duplication is intentional — keep both.

### Failure mode
- On checker timeout or error:
  - For `firm` and `hard` OOB → fail closed (don't send, queue for retry, surface in admin).
  - For `soft` OOB only → fail open with a logged warning.
- The `checker_failed` flag travels on the result so the loop can react.

### OOB countersummary (on demand)
- Compute on demand, not stored. When asked, read the partner's active OOB entries and produce a topic-level summary that strips identifying detail — categories of sensitive content only, never quotes or paraphrases.
- Output shape: counts plus topic clusters, e.g., `"three entries related to family history, two related to past relationships"`.
- If the OOB owner has only one entry on a niche topic, the summary stays vague ("one entry related to a personal matter").
- This logic lives in a function the main loop calls when the user asks "what topics has she asked you not to share?". The system prompt's countersummary language guidance was set in Plan 3; this plan supplies the function it relies on.

### Significance scoring (real `score_observation`)
- Replace the stub with a Claude Haiku call (latest — default `claude-haiku-4-5-20251001`).
- Focused single-shot prompt that includes the five anchor examples inline (1=Trivial, 2=Minor, 3=Notable, 4=Significant, 5=Core) per spec.
- Output: `{score: int (1-5), reason: string}`.
- The score is stored on the observation alongside `scoring_prompt_version` (bump from `v0-stub` to `v1`).
- Failure mode: per spec, write the observation without a score and flag for re-scoring during weekly housekeeping (the housekeeping pass is in Plan 5; here, just leave `significance` null and add a `needs_rescoring=true` note in metadata or via status).

### Re-scoring support
- A small CLI/admin function `rescore_observations(prompt_version_threshold)` that finds observations scored under an older prompt version and re-scores them. Not auto-run, but available for manual invocation when the prompt evolves.

        # Implementation Plan: Plan 4 — OOB Guardrail + Significance Scoring

## Overview

Plan 4 replaces two stubs in the agentic loop with real LLM-backed implementations:

- `app/services/tools/read_tools.py:278` — `check_oob` is a hard-coded `OOBVerdict.ok` and must become a real Sonnet call against the recipient's active OOB entries.
- `app/services/tools/write_tools.py:65` — `score_observation_stub` returns `3` flat; replace with a Haiku call. `SCORING_PROMPT_VERSION` (`write_tools.py:56`) bumps `v0-stub` → `v1`.

It also adds:
- An OOB countersummary helper, computed on demand, with deterministic vague-up behavior for single-entry niche topics.
- A manual re-scoring helper for observations stored under an old `scoring_prompt_version` or failed scoring sentinel.

The critique flags do not show that the plan targets the wrong files or root cause. They identify two integration gaps in the proposed wiring: the delivery-time rewrite path would auto-send a checker rewrite instead of returning control to the loop, and the fail-closed policy used an existing `withheld` state without the required retry/admin surface. The revised approach keeps the same root implementation targets, but changes downstream behavior so final delivery-time rewrites block instead of auto-send, and adds a minimal retry/admin-review persistence path without building a full scheduler or admin UI.

The Anthropic client setup, two-phase loop, spend-cap recording, prompt-cache pattern, and `tool_calls`/`bot_turns` audit already exist (`app/services/agentic.py`); reuse them end-to-end. Both new LLM calls record cost against provider `text` via `app/services/spend.py:9`, since the current provider caps are `text|vision|transcription`.

## Constraints & Touch Points

- `CheckOOBInput`/`CheckOOBOutput` schemas already exist (`tool_schemas.py:344-361`), including `triggering_oob_ids` and `checker_failed`.
- The agentic-loop `check_oob` tool owns the `rewrite` contract: on `rewrite`, the model receives `suggested_rewrite` as a tool result and decides whether to accept it, redraft, stay silent, or call `send_outbound` with different content.
- The delivery-time hook in `app/services/messaging.py:67-73` must remain a last-resort safety layer, but it must not auto-send a final checker rewrite. A final `rewrite` verdict is treated as withheld for review/retry with the suggested rewrite preserved.
- `hooks.check_oob = None` semantics stay intact: `None` skips the delivery-time hook, preserving existing test fixtures and local bypass behavior.
- Observations table has no `metadata` column (`migrations/0001_init.sql:72`). Use `significance IS NULL` plus sentinel `scoring_prompt_version='v1-failed'` to flag for re-scoring; no observation migration is needed.
- A full async scheduler remains out of scope, but the requested fail-closed retry/admin surface is satisfied by persisting retryable withheld outbound metadata in a minimal queue/review table. Plan 5 can consume it, and Plan 6 can build UI over it.
- Existing tests rely on the dict-shape `{verdict, rewrite}` for `hooks.check_oob` (`tests/test_send_outbound.py:185-196`, `tests/test_agentic.py:270-274,326-369`); preserve that adapter shape while changing `messaging.py` behavior for `rewrite`.
