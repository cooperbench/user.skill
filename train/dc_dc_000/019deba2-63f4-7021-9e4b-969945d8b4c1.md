        # Implementation Plan: Phase 3 Mixed-Mode Hype Pipeline

## Overview
ArtAgents currently keeps the hype workflow in `artagents/pipeline.py`, which is both the package command router and the 15-step hype orchestrator. The current pipeline split is not only file organization: `build_steps()` filters steps from hardcoded `STEP_ORDER` based on `args.video` and `args.audio`, and arrange/cut/refine still use `is_all_generative_arrangement()` as a mode boundary.

The latest critique does not point to the wrong code or a different root cause. It points to two selector-spec bugs in the current plan: `generative_visuals_enabled` cannot be a static requirement for selecting arrange, because source-cut opt-out still needs arrange to run; and downstream `rendered_video` facts must be explicitly aligned with the current render manifest, which currently provides `video`. This revision fixes those details directly.

To avoid confusing future registry behavior, the manifest field should be named `clip_kinds_supported` rather than `produces_for`. It still satisfies the requested design call: each pipeline-stage executor declares which runtime clip kinds it participates in. A separate `pipeline_requirements` field declares runtime facts needed for selection, such as `source_video`, `source_audio`, `transcript`, and `render_requested`. Capability relevance and artifact availability stay separate.

Mixed-mode remains the Phase 3 behavior change: source-video/source-audio briefs expose generative visual candidates by default so a single brief can produce mixed timelines. The compatibility opt-out is `--no-generative-effects`, which affects command construction and pool exposure only. It must not affect whether arrange itself is selected.

Dry-run remains mandatory. Top-level hype `--dry-run` will parse, prepare lightweight run metadata and the copied brief, compute the selected step plan, write `<out>/hype.plan.json`, and never call `run_step()` or launch child executors. Tests must patch the moved orchestration owner’s `run_step` and assert it is not called.

`GENERATIVE_IMAGE` will be represented as runtime `ClipClassifiedKind.IMAGE` plus pool/asset provenance showing the clip came from a generative pool entry. This matches Phase 2 and avoids schema package changes or a persisted `clip.kind` field.
