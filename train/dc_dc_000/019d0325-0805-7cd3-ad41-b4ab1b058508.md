**Findings**

- High: the rust-detector migration cleanup does not actually evict old `queue_order` entries after reclassification. `_demoted_auto_cluster_issue_ids()` only removes IDs when the persisted policy is still `ephemeral_autopromote` ([auto_cluster.py:149](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/auto_cluster.py#L149)), but the sync path rewrites existing rust clusters to `execution_status=review` and `execution_policy=planned_only` before eviction runs ([auto_cluster_sync_issue.py:157](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/auto_cluster_sync_issue.py#L157)). In the realistic migrated state, eviction returns nothing; I reproduced that locally with the current helpers. The new test only covers an artificial `review + ephemeral_autopromote` cluster state, so it misses the real regression ([test_queue_metadata.py:135](/Users/user_c042661f/Documents/desloppify/desloppify/tests/plan/test_queue_metadata.py#L135)).

- Medium: the non-execute `Blocked:` counts are using all in-scope objective items, not the queue-driven executable set. `explain_queue()` reads `snapshot.objective_in_scope_count` for workflow/triage/review/assessment gates ([policy.py:79](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/policy.py#L79), [policy.py:104](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/policy.py#L104)), but once a plan has queue items, only `queue_order` objectives are actually executable ([schema/__init__.py:310](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/schema/__init__.py#L310)). The snapshot already exposes `planned_objective_count` for that narrower number ([snapshot.py:749](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L749)). As written, `--explain` will overstate what is “blocked behind triage/workflow” on queue-driven plans.

- Medium: the execute-phase backlog summary is mislabeled. `explain_queue()` reports `len(snapshot.backlog_items)` as `Backlog: N items (not in queue_order)` ([policy.py:81](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/policy.py#L81), [policy.py:102](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/policy.py#L102)), but `backlog_items` includes review, assessment, scan, workflow, and triage items as well as objective backlog ([snapshot.py:652](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L652)). That means the explanation can blame `queue_order` for items that are actually hidden by phase/lifecycle rules instead.

Implementation otherwise tracks the plan reasonably well: `auto_queue` precedence is wired correctly, `deferred` is recognized, backlog/next share the preamble path, and the new tests pass.
