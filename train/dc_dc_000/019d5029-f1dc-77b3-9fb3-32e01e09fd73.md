The flow:

1. SETUP CONVERSATION: Agent talks to user to understand:
   - What command to run each iteration
   - What success looks like (measurable criteria)
   - What the agent is allowed to change (code, config, etc.)
   - What NOT to change (test assertions, external APIs, etc.)
   - What to optimize for (pass rate, cost, speed)
   This produces a loop_spec.json — a living document updated each iteration.

2. LOOP SPEC (loop_spec.json): Persists across iterations:
   - goal, success_criteria, allowed_changes, constraints
   - command to run
   - current_best (best result so far)
   - known_issues (list, updated each iteration)
   - tried_and_failed (so we don't repeat)
   - iteration_count, total_cost, total_duration
   - status: running | paused | done

3. EACH ITERATION:
   a. Run the command (subprocess, capture stdout/stderr/exit code)
   b. Agent reads results + loop_spec
   c. Agent analyzes: what failed? why? better or worse than last time?
   d. Agent decides: fix something, adjust config, or ask user?
   e. If fixing: spawn sub-agent to do the actual work (code edits, config changes)
   f. Update loop_spec with learnings
   g. Decide: continue loop, pause for user input, or done?

4. SUB-AGENTS for deep work:
   - "Investigate failure X" — reads logs, traces, code, reports findings
   - "Fix issue Y" — edits code, runs tests, verifies fix
   - "Optimize Z" — adjusts config, benchmarks, reports improvement
   These are the same pattern as megaplan's execute phase — focused work with tools.

5. STRUCTURED FEEDBACK per iteration:
   iteration_result.json:
   - iteration_number
   - command_output (truncated)
   - results_summary (pass/fail counts, scores)
   - comparison_to_previous (better/worse/same, what changed)
   - issues_found (new issues this iteration)
   - fixes_applied (what was changed and why)
   - decision (continue/pause/done)
   - reasoning (why this decision)

6. STOP CONDITIONS (strong bias to continue):
   - Success criteria met
   - Max iterations reached
   - Same error N times with no progress
   - Cost/time budget exceeded
   - User says stop
   Default: keep going

        # Implementation Plan: MegaLoop — Iterative Agent Loop

## Overview

Build a minimal iterative agent loop (`megaloop/`) that automates the observe → analyze → fix → rerun cycle currently done manually with evals. The project already has rich documentation (`MEGALOOP.md`), JSON schemas for loop phases (`.megaplan/schemas/loop_plan.json`, `loop_execute.json`), and proven subprocess/artifact patterns in `evals/run_evals.py` and `evals/parallel.py`. No `megaloop/` directory exists yet — this is greenfield.

**Target:** ~500 lines across 5 files. The LLM does the thinking; the code manages state and subprocess calls.

**Key constraint:** This runs *inside* a Claude Code conversation. The "agent" is the LLM in the main thread making tool calls. Sub-agents are launched via the `Agent` tool. The loop code provides the state management, subprocess execution, and structured artifacts — the intelligence is the LLM calling these functions.

## Phase 1: Core Data Structures and State

### Step 1: Create `megaloop/spec.py` — Loop Spec management (~80 lines)
**Scope:** Small
1. **Define** `LoopSpec` as a dataclass with all fields from MEGALOOP.md spec (`megaloop/spec.py:1`):
   - `goal`, `command`, `success_criteria: list[str]`, `allowed_changes: list[str]`, `constraints: list[str]`
   - `philosophy: dict` (approach, priorities, style)
   - `optimize_for: list[str]`
   - `current_best: dict` (metrics + iteration number)
   - `known_issues: list[str]`, `tried_and_failed: list[str]`
   - `iteration_count: int`, `total_cost: float`, `total_duration: float`
   - `status: str` (running | paused | done)
   - `max_iterations: int` (default 50)
   - `max_stuck_count: int` (default 3)
2. **Implement** `load_spec(path) -> LoopSpec`, `save_spec(spec, path)` using JSON serialization (follow `evals/config.py` pattern — `asdict()` for save, `LoopSpec(**data)` for load).

## Phase 2: Loop Runner and Agent Logic

5. **Implement** `build_fix_prompt(spec: LoopSpec, diagnosis: str, fix_description: str) -> str`:

## Design Decision: Agent Integration Model

The key architectural question is how the LLM agent interacts with the loop. Two options:

**Option A (Recommended for v1): Loop-as-library.** The Python code manages state and runs commands. The agent (in a Claude Code conversation) calls these functions via tool use or imports. The "analyze → decide → fix" steps are the agent making tool calls, not Python code calling an LLM API. This keeps the code minimal and leverages Claude Code's existing agent infrastructure.

**Option B: Loop-as-service.** The Python code calls an LLM API directly (via litellm/openai client). This makes it standalone but adds API key management, prompt engineering in code, and response parsing complexity. Not appropriate for v1.

With Option A, `megaloop run` is really a helper that runs the command, saves output, and prints what the agent needs to analyze. The agent conversation drives the actual loop.
