## Full spec

**Motivation.** Today, gates can only recommend PROCEED / ITERATE / ESCALATE. When a plan has an unresolvable constraint tension (like M1's RQ-first vs store-first architectural conflict), the only path is ESCALATE — but the human gets only the gate's rationale, no structured decision context. The MVP tiebreaker CLI produces that context manually. This milestone makes the harness recognize when tiebreaker should run and route automatically — with enough guardrails that it doesn't burn tokens on false positives.

**Core changes**

### 1. Iteration-pressure signal (compute in evaluation.py / gate_signals.py)

For each open flag, compute:
```
{flag_id, fuzzy_group_id, iterations_open, addressed_then_reopened_count, rationale_similarity_to_prior}
```

`fuzzy_group_id` is assigned by embedding similarity on the flag's `concern` text — flags with >0.85 cosine similarity belong to the same fuzzy_group. This catches 'bootstrap race' flags labeled with different IDs across iterations but semantically the same concern. Use a small local embedding model (or an API call if that's already how critique works); make the similarity threshold configurable.

`addressed_then_reopened_count` counts transitions: flag went from `open` to `addressed` and back to `open`. That's the strongest signal of loop failure.

This table is rendered into the gate prompt context as a plain-text section.

### 2. Extend gate schema and prompt

`megaplan/schemas.py`:
```python
GATE_RECOMMENDATION = Literal['PROCEED', 'ITERATE', 'ESCALATE', 'TIEBREAKER']

class GateOutput(TypedDict):
    recommendation: GATE_RECOMMENDATION
    rationale: str
    flag_resolutions: list[FlagResolution]
    tiebreaker_question: NotRequired[str]   # required iff recommendation == TIEBREAKER
    tiebreaker_flag_ids: NotRequired[list[str]]  # which flags this resolves
    tiebreaker_fuzzy_group_id: NotRequired[str]  # which group this resolves
```

`megaplan/prompts/gate.py` gets a new section:
> 'If any fuzzy_group shows `addressed_then_reopened_count >= 2` OR has >=2 member flags across >=2 iterations, consider whether it reflects an *unresolvable constraint tension* (architectural/philosophical — requires a human call -> TIEBREAKER) versus a *plan-quality issue* (the plan writer hasn't tried hard enough -> ITERATE). Recommend TIEBREAKER only for the former; cite specific flag IDs and iterations in your rationale.'

### 3. Harness validates TIEBREAKER recommendation

In `handlers.py` `handle_gate`:
- If gate returns `recommendation: TIEBREAKER`, check that at least one fuzzy_group has `addressed_then_reopened_count >= 2` OR spans >=2 iterations.
- If no such group exists, reject the recommendation and re-prompt the gate once with: 'You recommended TIEBREAKER but no flag shows mechanical recurrence signal. Either identify specific flag(s) with iteration history or pick ITERATE.'
- If re-prompt still says TIEBREAKER without signal, force-demote to ITERATE and log `tiebreaker_rejected_no_signal`.

### 4. New plan states

`megaplan/types.py`:
```python
PlanState = Literal[
    ..., 'critiqued', 'gated', 'finalized', 'executed', 'reviewed', 'done',
    'tiebreaker_pending',  # NEW — tiebreaker recommended, researcher/challenger running

```

Transitions:
- `critiqued` -> (gate emits TIEBREAKER, validation passes) -> `tiebreaker_pending`
- `tiebreaker_pending` -> (tiebreaker runs) -> `tiebreaker_ready`
- `tiebreaker_ready` -> (human runs `megaplan tiebreaker decide`) -> `critiqued` (with settled flag resolution injected)

### 5. New CLI: `megaplan tiebreaker decide`


### 7. Guardrails

- **Budget per plan.** `plan_config.max_tiebreakers_per_plan` (default 2). Counted in the plan's state metadata. Exceeded -> gate's TIEBREAKER force-demoted to ESCALATE with rationale 'tiebreaker budget exhausted'.
- **Cost ceiling.** Tiebreaker run has a wall-clock (default 30m) and token (default 150k) budget. Exceeded -> abort, emit partial output, force-demote to ESCALATE.
- **Domain blocklist.** `plan_config.tiebreaker_blocklist: list[str]` (default []). Concerns with category in blocklist skip tiebreaker.
- **Spec-level opt-out.** Idea file front-matter field `allow_tiebreaker: false` disables the entire mechanism for the plan.
- **Tiebreaker refusal.** Researcher can emit `decision_not_ripe: true` with reason; harness treats as abort without consuming a tiebreaker budget slot.

## Overview

megaplan (v0.17.0) has a manual tiebreaker CLI (researcher→challenger→synthesis in `megaplan/tiebreaker.py`) but no automatic triggering. This work adds: (1) iteration-pressure computation to detect recurring flags, (2) a `TIEBREAKER` gate recommendation with validation guardrails, (3) new plan states `tiebreaker_pending`/`tiebreaker_ready`, (4) a `tiebreaker decide` subcommand, (5) settled-decision immunity in critique, (6) budget/audit tracking, and (7) tests.

**Key simplification from spec:** The spec suggests embedding-based fuzzy grouping. The codebase already has `_jaccard_similarity` (word-overlap, `megaplan/_core/registries.py:114`) used for debt matching. We'll reuse this for flag grouping instead of introducing an embedding model — simpler, zero new dependencies, and the spec says "use whatever critique already uses for text similarity." The threshold (default 0.5 for debt) can be tuned separately for flag grouping (default 0.6).

**Constraint:** `_apply_flag_updates` (`flags.py:97`) overwrites `raised_in` on re-raise (line 130), so a flag's transition history isn't preserved in a single field. We'll reconstruct history by scanning all `critique_v{N}.json` artifacts + the flag registry, which is read-only and doesn't require schema changes to FlagRecord.

### Summary

4. **Tiebreaker:** Separate orchestrator for architectural questions; researcher → challenger → synthesis pipeline
