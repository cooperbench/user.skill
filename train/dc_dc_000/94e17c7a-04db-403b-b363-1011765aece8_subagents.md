68	  tagged_by_bot_id text NOT NULL REFERENCES bots(id),

154	## 5. Bot participants shape and bindings
155	
156	### Participants shape
157	
158	```python
159	participants_shape: Literal["solo", "dyad"]   # future: "group"
160	```
161	
162	- **Solo**: serves one user. `about_user_id` always that user. No partner concept. No pair-level status.
163	- **Dyad**: serves two users. Each turn picks `user_in_context` (whoever just messaged). Writes can specify `about_user_id = A`, `B`, or `NULL` (shared). Pair-level status supported.
164	
165	This single config decides whether the bot needs partner handling, shared-mode artifacts, dyadic crisis escalation, bridge candidates.
166	
167	### Enforcement, not aspiration (§19.3, §19.14)
168	
169	"Solo bot never picks shared" is not an invariant unless tools reject illegal scopes. Tool entry points validate against `TurnContext.participants_shape` and `TurnContext.binding`:
170	
171	- Solo bot calling a write with `about_user_id != bound_user.id` → rejected.
172	- Solo bot calling a write with `about_user_id = NULL` (shared) → rejected.
173	- Dyadic bot calling a write with `about_user_id` outside the bound dyad → rejected.
174	
175	Tool registry has *participant-shape-specific contracts*. Bridge tools, in-person redirect, partner-perspective tools are only registered for dyadic bots — not "registered everywhere and gated by prompt language." Solo bots literally cannot call them.
176	
177	### Bindings (data)
178	
179	```sql
180	CREATE TABLE dyads (
181	  id          uuid PRIMARY KEY,
182	  created_at  timestamptz NOT NULL DEFAULT now()
183	);
184	
185	CREATE TABLE dyad_members (
186	  dyad_id   uuid NOT NULL REFERENCES dyads(id),
187	  user_id   uuid NOT NULL REFERENCES users(id),
188	  PRIMARY KEY (dyad_id, user_id)
189	);
190	
191	CREATE TABLE bot_bindings (
192	  id         uuid PRIMARY KEY,
193	  bot_id     text NOT NULL REFERENCES bots(id),
194	  user_id    uuid REFERENCES users(id),   -- set for solo
195	  dyad_id    uuid REFERENCES dyads(id),   -- set for dyad
196	  created_at timestamptz NOT NULL DEFAULT now(),
197	  CHECK ((user_id IS NOT NULL) <> (dyad_id IS NOT NULL))
198	);
199	```
200	
201	The current implicit "dyad in settings" becomes an explicit `dyads` row in migration. Adding a second bot is then a new `bot_bindings` row.
202	
203	### Defaults on writes
204	
205	- **Solo bot**: `about_user_id` defaults to the bound user, validation enforces it.
206	- **Dyadic bot**: `about_user_id` defaults to `user_in_context`. Agent can explicitly set partner or NULL when warranted, subject to authorization (§6).

247	
248	Each `BotSpec` declares scopes explicitly:

254	    allow_cross_topic_peek: bool                    # status counts of other topics
255	    allow_cross_topic_status_injection: bool        # see §7.4
256	
257	@dataclass(frozen=True)

259	    topics: frozenset[str]                         # always contains primary

264	
265	This replaces the previous "agent can fully override `topic_ids`" rule, which was unconstrained write authority masquerading as flexibility (§19.11).
266	
267	### 6.4 Enforcement points
268	
269	- **Read tools** consult `ctx.read_scopes` before filtering.
270	- **Write tools** consult `ctx.write_scopes` before INSERT. Cross-topic writes require non-empty `reason`.

272	- **`consult_perspective`** clones `ctx` *preserving scopes*. Consult inherits the same authorization (§19.7).

335	## 8. Tool scope and write authorization
336	
337	### 8.1 Reads
338	
339	Every read tool grows an optional `scope` argument:
340	
341	```python
342	scope: Literal["own", "all"] | str = "own"   # "topic:<slug>"
343	```
344	
345	Resolution against `ctx.read_scopes`:
346	
347	- `"own"` (default): filter by `ctx.primary_topic_id` via `artifact_topics`.
348	- `"all"`: allowed only if `ctx.read_scopes.topics == "all"`.
349	- `"topic:<slug>"`: allowed only if slug is in `ctx.read_scopes.topics` or `topics == "all"`.
350	
351	Cross-topic reads are **explicit**, never auto-expanded on empty results. The agent opts in and the reason appears in `tool_calls.arguments`.
352	
353	### 8.2 Writes — gated by `write_scopes` (§19.11)
354	
355	Writes accept `topic_slugs: list[str]` defaulting to `[ctx.primary_topic_slug]`. The set is intersected with `ctx.write_scopes.topics` at the tool boundary; if non-trivially intersected (the agent asked to write to a topic it's not authorized for), the tool rejects.
356	
357	Cross-topic writes (any topic other than primary) require a non-empty `reason`. The reason is stored in every created `artifact_topics` row.
358	
359	This is the durable rule: **default own topic, allow configured cross-topic writes, record why every cross-topic tag exists.** Not "agent freely overrides."
360	
361	### 8.3 The cross-topic peek block (in hot context)
362	
363	For each other topic the served user(s) have activity in, when `peek` is enabled:
364	
365	```
366	[topic: career]
367	  Status (Maya, 3d ago by coach): "Looking for a new role — anxious about timeline."
368	  Counts for Maya: memories=12, watch_items=3, themes=2, recent_observations=5 (last 14d)
369	  Counts for Liam: memories=4,  watch_items=0, themes=1, recent_observations=1
370	```
371	
372	Rules:
373	
374	- Counts **per-user**, not pooled.
375	- Window fixed and stated (proposal: 14 days).
376	- Status headline verbatim only when `allow_cross_topic_status_injection` is true; otherwise summarized to "status present" or omitted.
377	- Contents not in the peek — agent must read explicitly.

470	## 12. Channels, routing, and user identity
471	
472	The doc previously punted user identity to "phase 4+." That was wrong (§19.16, §19.18) — multi-transport breaks identity before the second bot is useful. Identity lands in phase 0/1.
473	
474	### 12.1 Channels
475	
476	A **channel** is any addressable inbound surface a bot listens on. Today: a Discord bot account or a phone number. Tomorrow: a Discord mention in a guild channel, a Slack app, etc.
477	
478	```sql
479	CREATE TABLE channels (
480	  id         uuid PRIMARY KEY,
481	  bot_id     text NOT NULL REFERENCES bots(id),
482	  transport  text NOT NULL,                      -- 'discord' | 'whatsapp' | …
483	  address    text NOT NULL,                      -- bot account id, phone number, …
484	  guild_id   text,                               -- transport-specific
485	  channel_id text,
486	  config     jsonb NOT NULL DEFAULT '{}'::jsonb,
487	  UNIQUE (transport, address, guild_id, channel_id)
488	);
489	```
490	
491	The routing primitive: `resolve_bot(inbound_event) -> bot_id`. Channels table is the lookup; keys are transport-specific. No code path assumes 1:1.
492	
493	### 12.2 User identity across transports
494	
495	Today `users.phone` is reused for Discord ids (`discord.py:176` vs `migrations/0001_init.sql:10`). For multi-bot, a single human may reach the coach via Discord and the mediator via WhatsApp; we need a way to know "same person."
496	
497	```sql
498	CREATE TABLE user_identities (
499	  user_id    uuid NOT NULL REFERENCES users(id),
500	  transport  text NOT NULL,
501	  address    text NOT NULL,
502	  verified_at timestamptz,
503	  created_at timestamptz NOT NULL DEFAULT now(),
504	  PRIMARY KEY (transport, address)
505	);
506	```
507	
508	Sender resolution at inbound becomes: `(transport, address)` lookup against `user_identities`, returning `user_id`. The legacy `users.phone` column is migrated to a `(transport='legacy', address=<phone>)` row in phase 0 and the field is no longer load-bearing.
509	
510	Account-linking (a human verifying "this Discord id and that WhatsApp number are me") is a workflow we don't build yet but the schema is ready for. Until linking happens, two transport identities are two `user_id`s. The risk of writing memories/OOB/feedback under duplicate humans is real and the schema lets us merge later without rewriting encrypted blobs.
511	
512	### 12.3 Inbound flow
513	
514	1. Webhook receives event; extract transport identity.
515	2. `resolve_bot(event) -> bot_id`.
516	3. Sender resolution → `user_id` via `user_identities`.
517	4. Resolve `bot_spec`; resolve `binding` from `bot_bindings`.
518	5. For dyadic: confirm sender is a dyad member; set `user_in_context`.
519	6. For solo: confirm sender is the bound user.
520	7. Inbound `messages` row stamped with `bot_id`, `topic_id`, `user_in_context`, `channel_id`.
521	8. Burst coalesce by `(user_id, bot_id)`.
522	9. Construct `TurnContext` with all scope fields populated (§6.1).
523	10. `bot_turns` created with `bot_id`, `topic_id`, version pins.

```sql
CREATE TABLE topic_status (
  id                       uuid PRIMARY KEY,
  topic_id                 uuid NOT NULL REFERENCES topics(id),
  dyad_id                  uuid REFERENCES dyads(id),    -- set when pair-level
  user_id                  uuid REFERENCES users(id),    -- set when per-user
  headline                 text NOT NULL,
  body                     text NOT NULL,
  last_updated_at          timestamptz NOT NULL DEFAULT now(),
  last_updated_by_bot_id   text NOT NULL REFERENCES bots(id),
  CHECK ((user_id IS NOT NULL) <> (dyad_id IS NOT NULL))
);
CREATE UNIQUE INDEX topic_status_user_key
  ON topic_status (topic_id, user_id) WHERE user_id IS NOT NULL;
CREATE UNIQUE INDEX topic_status_dyad_key
  ON topic_status (topic_id, dyad_id) WHERE dyad_id IS NOT NULL;
```

**Constraint:** Pair-level rows keyed by `(topic_id, dyad_id)` (not `(topic_id, NULL)`); prevents collision across multiple dyads.

**Write rules:**
- Solo bot: per-user statuses only for bound user.
- Dyadic bot: per-user statuses for either partner + pair-level status (`dyad_id` set, `user_id` NULL).

**Tool:** `set_topic_status(scope, headline, body)` where `scope = "user:<id>" | "pair"`. Topic implicit from `ctx.primary_topic_id`.

**Injection policy (§7.4):** Gated by `ctx.read_scopes.allow_cross_topic_status_injection`:
- `peek` or `all`: sees own topic's statuses + cross-topic statuses.
- `forbidden`: sees only own topic's statuses.

#### `user_bot_state` (implicit schema from prose)
- `user_id` uuid NOT NULL REFERENCES users(id)
- `bot_id` text NOT NULL REFERENCES bots(id)
- `onboarding_state` — migrated from `users.onboarding_state` for each (user, bot) pair
- `paused` boolean — per-(user, bot) pause state (read path in S2a, write path deferred)
- (Likely) PRIMARY KEY `(user_id, bot_id)`

**Usage:** Onboarding per bot (replaces global `users.onboarding_state`). Pause/resume per (user, bot) — additive to global `system_state.is_paused` kill switch.

### §12.2 — User identity backfill semantics

```sql
-- Backfill from users.phone to user_identities
INSERT INTO user_identities (user_id, transport, address, created_at)
SELECT id, 'legacy', phone, now()
FROM users
WHERE phone IS NOT NULL;
```

**Rule:** Existing `users.phone` → `(transport='legacy', address=<phone>)` rows in `user_identities`. The `legacy` transport signals pre-migration identity.

**Audit requirement:** If any row contains both a phone and a Discord id, both must become identity rows. Audit before backfill.

**Future:** Account-linking (verifying "this Discord id and that WhatsApp number are me") is a workflow to build later. Schema ready now. Until linking, two transport identities = two `user_id`s (duplicate-human risk).
