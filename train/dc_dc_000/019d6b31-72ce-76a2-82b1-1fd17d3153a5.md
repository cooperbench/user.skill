Today we've shipped a launch-time key probe that filters dead keys upfront, but it doesn't solve the steady-state problem: - A key that becomes exhausted mid-run still kills its owning worker permanently. - The parent `run_parallel_workers` process hangs forever once all workers die — it never exits, so the cron's `restart_dead()` can't detect the condition via "process absent." - Cron's `restart_dead()`, when it does fire, spawns a new parent without killing the old one, leaking orphan processes each cycle. - Worker count is static — if the pool shrinks from 5 healthy keys to 2, we still try to run 4 workers and 2 of them thrash on dead keys. Worker subprocesses no longer receive a fixed key — they use the megaplan key pool's existing LRU+cooldown logic. Parent dynamically scales target worker count to `min(configured_max, alive_key_count)` at launch and re-scales if capacity changes significantly mid-run. Explicit non-goal: we are NOT building a long-running key health daemon with RPC.
