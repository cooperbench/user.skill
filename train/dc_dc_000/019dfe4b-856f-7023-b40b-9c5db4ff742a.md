**Findings**

1. [hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:370) renders recent and trigger messages with only `sent_at` UTC/DB ISO values. Even though `Current time` includes Berlin local date/time, each message lacks `sent_at_local`, `local_date`, `local_weekday`, or `is_today_local`. Near midnight, the model has to mentally convert every message to decide whether it is “today.”

2. [hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:596) labels the section `Recent messages`, not “Recent messages in local time,” and [conversation load](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:540) omits `period_start`/`period_end` in rendering. Counts are probably computed correctly for local day via Postgres timezone bounds, but the rendered prompt doesn’t show the local day window, so the model cannot reconcile counts with raw UTC timestamps.

3. [tools/read_tools.py](/Users/user_c042661f/Documents/Veas/app/services/tools/read_tools.py:265) `search_messages` only accepts an absolute `DateRange`. There is no schema-level way to ask “messages from today in the current user’s timezone.” The model must compute Berlin UTC bounds itself, which is fragile around DST and midnight.

4. [tools/read_tools.py](/Users/user_c042661f/Documents/Veas/app/services/tools/read_tools.py:415) `recent_activity` uses a rolling UTC `days` window, not local calendar days. Its output period is UTC start/end only, so it is not reliable for “today” or “yesterday” in Berlin.

5. [scheduled_job_handlers.py](/Users/user_c042661f/Documents/Veas/app/services/scheduled_job_handlers.py:160) scheduled-task trigger context includes `scheduled_for` only in stored/UTC form. The job turn will also get hot-context current local time, but the task payload itself does not say “this fired at 09:00 Europe/Berlin on Wednesday,” which matters for recurring tasks and user-facing phrasing.

6. [scheduled_task_recurrence.py](/Users/user_c042661f/Documents/Veas/app/services/scheduled_task_recurrence.py:90) recurring scheduled tasks advance in UTC. A daily task first scheduled for 09:00 Berlin will drift to 10:00 local across DST start, and weekly weekday logic is based on the UTC date rather than the user’s local calendar day. The recurrence schema has no timezone/local-time anchor.

7. [hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:165) conversation-load SQL uses `$2` as a timezone name directly. `_temporal_context` safely falls back to UTC for invalid zones, but the SQL path does not; a bad user timezone can error instead of producing UTC-safe local context.

**Concrete Changes**

Add local message metadata in hot context and read-tool outputs:

- `sent_at_utc`
- `sent_at_local`
- `local_date`
- `local_weekday`
- `local_time`
- `local_day_label`: `today`, `yesterday`, or ISO date
- `is_today_local`

Render recent/trigger messages like:

```text
- local=2026-05-07 00:12 Thursday (today, Europe/Berlin) utc=2026-05-06T22:12:00+00:00 inbound ...
```

Render conversation-load bounds:

```text
- local_period_start: 2026-05-07T00:00:00+02:00
- local_period_end: 2026-05-08T00:00:00+02:00
- utc_period_start: ...
- utc_period_end: ...
```

Add schema/query support so the model does not calculate day bounds:

- Extend `SearchMessagesInput` with `local_day: date | Literal["today", "yesterday"] | None` and optional `timezone`, defaulting to current user timezone.
- Or add a `DateRangePreset` with `preset="today" | "yesterday" | "last_7_local_days"` and `timezone`.
- Convert local-day bounds server-side using `ZoneInfo` or Postgres `AT TIME ZONE`.
- Add the same local-period capability to `recent_activity`, or rename the current tool behavior as rolling UTC to avoid ambiguity.

For scheduled tasks:

- Store recurrence timezone and local wall-clock anchor in scheduled-task context, e.g. `timezone`, `local_time`, `local_weekdays`.
- Compute next daily/weekly occurrence in that timezone, then convert to UTC for `scheduled_for`.
- Add trigger context fields: `scheduled_for_utc`, `scheduled_for_local`, `timezone`, `local_date`, `local_weekday`, `local_time`.
- Add those fields to `ScheduledTaskRow` so `list_scheduled_tasks` shows local fire time.

Prompt additions:

- In the `Current time`/scheduling section, say: “Treat `today` and `yesterday` as calendar days in the current user’s timezone. Prefer local-day fields from hot context/tools over interpreting UTC timestamps yourself.”
- In partner-perspective/search guidance, say: “When asking about today’s messages, use the local-day search option rather than hand-computing UTC bounds.”
