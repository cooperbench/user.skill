        # Implementation Plan: Unified Timeline Sync System

## Overview

The video editor's timeline persistence has four mechanisms — versioned saves, 30s polling, realtime event invalidation, and asset registration — that don't coordinate. Three root causes drive all observed bugs:

1. **Unstable poll discriminator**: `shouldAcceptPolledData()` compares `TimelineData.signature`, which is `JSON.stringify(resolvedConfig)` including signed asset URLs that change every read. Every poll produces a different signature regardless of whether persisted data changed. This causes polling to accept and replace local data on every cycle — including clobbering in-memory asset patches during uploads.

2. **Version advancement without data adoption**: The standalone `configVersionRef` effect (line 97-101) advances the version ref from polled data even when `shouldAcceptPolledData()` rejects the data (e.g., during local edits). This decouples version tracking from data state, silently skipping conflict detection when the local save later uses the advanced version as `expectedVersion`.

3. **Non-atomic asset registration**: `registerAsset()` does read-modify-write on the `asset_registry` JSONB column. Concurrent uploads race; last write wins.

### Constraints
- Same-user multi-tab, not multi-user collab. Last-write-wins after conflict retry is acceptable.
- AI agent uses the versioned RPC concurrently — it participates in conflict detection already.
- Realtime events only include `{id, projectId, eventType}` — no `config_version`. Own-write suppression must happen at the polling layer.
- Typical file drop is 1-3 files. No batch RPC needed.

### Key Files
| File | Role |
|------|------|
| `useTimelineSave.ts` | Core save orchestration, polling sync, version tracking |
| `timeline-save-utils.ts` | `shouldAcceptPolledData()` decision function |
| `timeline-data.ts` | `buildTimelineData()`, `assembleTimelineData()`, signature computation |
| `config-utils.ts` | `getConfigSignature()`, `resolveTimelineConfig()` |
| `SupabaseDataProvider.ts` | RPC calls, asset registration |
| `useAssetOperations.ts` | Hook-level upload + register wrappers |
| `useTimelineRealtime.ts` | Realtime subscription + conflict dialog state |
| Migration SQL | Versioned save RPC, new atomic asset RPC |

## Phase 1: Fix the Poll Discriminator

### Step 1: Add a stable `configSignature` to `TimelineData` (`timeline-data.ts`, `config-utils.ts`)
**Scope:** Medium

The current `signature` field is `JSON.stringify(resolvedConfig)` which includes signed asset URLs. It's used for two purposes: (a) poll change detection, and (b) save deduplication. Only (a) needs stability; (b) can keep using the full signature.

1. **Add `getStableConfigSignature()`** in `config-utils.ts` that computes a signature from only the persisted config + asset registry structure (no resolved URLs):
   ```typescript
   export const getStableConfigSignature = (
     config: TimelineConfig,
     registry: AssetRegistry,
   ): string => JSON.stringify({ config, registry });
   ```

2. **Add `stableSignature` field** to the `TimelineData` type in `timeline-data.ts`. Compute it in `assembleTimelineData()` from the `config` and `registry` params (which don't contain signed URLs).

3. **Keep `signature`** (the resolved one) — it's still used for re-render optimization and save deduplication. The new `stableSignature` is only for poll comparison.

### Step 2: Switch `shouldAcceptPolledData()` to use stable signature (`timeline-save-utils.ts`, `useTimelineSave.ts`)
**Scope:** Small

1. **Update `shouldAcceptPolledData()`** to accept and compare `stableSignature` instead of `signature`:
   ```typescript
   export function shouldAcceptPolledData(
     editSeq: number,
     savedSeq: number,
     polledStableSig: string,
     lastSavedStableSig: string,
   ): boolean {
     if (savedSeq < editSeq) return false;
     return polledStableSig !== lastSavedStableSig;
   }
   ```

2. **Update callers in `useTimelineSave.ts`** (lines 474-478, 487-490): pass `polledData.stableSignature` and `lastSavedSignature.current`.

3. **Update `lastSavedSignature` ref** — set it from `stableSignature` instead of `signature` at lines 197 and 338.

4. **Update the registry sync effect** (lines 506-548): use `stableSignature` for the comparison at line 527 instead of `signature`.

## Phase 2: Fix Version Tracking

### Step 3: Remove standalone configVersionRef effect, unify version updates (`useTimelineSave.ts`)
**Scope:** Small

The effect at lines 97-101 advances `configVersionRef` from polled data even when the poll-sync path rejects the data (because `savedSeq < editSeq`). This lets a later save skip conflict detection by using an advanced version that doesn't match the local data's lineage.

1. **Delete the standalone effect** (lines 97-101 entirely). `configVersionRef` must only change in two places:
   - **On successful save** (line 173): `configVersionRef.current = nextVersion` — already correct.
   - **When accepting polled data** (line 496): `configVersionRef.current = polledData.configVersion` — already correct, and only runs when `shouldAcceptPolledData()` returns true.

2. **In the conflict retry path** (line 213): `configVersionRef.current = loaded.configVersion` — already correct (we're about to retry the save).

3. **In `reloadFromServer()`** (line 568): `configVersionRef.current = loadedTimeline.configVersion` — already correct (explicit user action).

4. **Verify** no other code path writes to `configVersionRef` by grep. The version ref and the data must always move in lockstep.

### Step 4: Add version guard to polling acceptance (`useTimelineSave.ts`)
**Scope:** Small

Even with the stable signature, add a defense-in-depth version check to prevent accepting stale polls.

1. **In the polling sync effect** (line 484, inside the `setTimeout` callback), add before accepting:
   ```typescript
   if (polledData.configVersion < configVersionRef.current) {
     return; // Stale poll response, ignore
   }
   ```

2. This handles the edge case where a save completes and bumps `configVersionRef` between the outer check and the deferred `setTimeout(…, 0)` callback.

## Phase 3: Suppress Own-Write Echoes During Asset Operations

### Step 5: Add pending-ops tracking to suppress polling during uploads (`useTimelineSave.ts`, `useAssetOperations.ts`)
**Scope:** Medium

Asset operations write to `asset_registry` via `provider.registerAsset()` (called directly or from inside `provider.uploadAsset()`). These writes trigger realtime events → query invalidation → poll refetch. Since asset operations use `save: false` (no `editSeqRef` increment), `shouldAcceptPolledData` sees `savedSeq >= editSeq` and accepts the stale poll, clobbering the local in-memory patch.

1. **Add `pendingOpsRef = useRef(0)`** in `useTimelineSave.ts`. Expose via the return object.

2. **Extend `shouldAcceptPolledData()`** with a `pendingOps` parameter:
   ```typescript
   export function shouldAcceptPolledData(
     editSeq: number, savedSeq: number,
     polledStableSig: string, lastSavedStableSig: string,
     pendingOps: number,
   ): boolean {
     if (savedSeq < editSeq) return false;
     if (pendingOps > 0) return false;
     return polledStableSig !== lastSavedStableSig;
   }
   ```

3. **Wrap `uploadAsset()` and `registerAsset()` in `useAssetOperations.ts`** with pending-ops tracking. These are the two hook-level entry points that cover all write paths:
   - `uploadAsset()` calls `provider.uploadAsset()` which internally calls `provider.registerAsset()` (SupabaseDataProvider.ts:262)
   - `registerAsset()` calls `provider.registerAsset()` directly
   - `useExternalDrop` calls `uploadAsset()` from `useAssetOperations`
   - `useAssetManagement.registerGenerationAsset()` calls `registerAsset()` from `useAssetOperations`

   ```typescript
   // In useAssetOperations.ts
   const uploadAsset = useCallback(async (file: File) => {
     pendingOpsRef.current += 1;
     try {
       return await provider.uploadAsset(file, { ... });
     } finally {
       pendingOpsRef.current -= 1;
     }
   }, [provider, pendingOpsRef]);
   ```
   Same pattern for `registerAsset()`.

4. **Pass `pendingOpsRef`** from `useTimelineSave` through `useTimelineData` to `useAssetOperations`. Check the existing prop threading to find the cleanest path.

### Step 6: Track last-written config version for own-write echo detection (`useTimelineSave.ts`)
**Scope:** Small

When a save succeeds, the subsequent poll will include our own data. If we've already updated `configVersionRef` and `lastSavedSignature` from the save success handler, the stable signature comparison should already match (since config didn't change). But as defense-in-depth:

1. **Add `lastWrittenVersionRef = useRef(0)`** in `useTimelineSave.ts`.

2. **Set it on save success** (line 173): `lastWrittenVersionRef.current = nextVersion`.

3. **In the polling sync effect**, if `polledData.configVersion === lastWrittenVersionRef.current`, just update `lastSavedSignature` without replacing data:
   ```typescript
   if (polledData.configVersion === lastWrittenVersionRef.current) {
     lastSavedSignature.current = polledData.stableSignature;
     return; // Own echo, no data replacement needed
   }
   ```

## Phase 4: Atomic Asset Registration

### Step 7: Create `upsert_asset_registry_entry` RPC (`supabase/migrations/`)
**Scope:** Small

1. **Create migration** with an atomic single-key merge RPC:
   ```sql
   create or replace function public.upsert_asset_registry_entry(
     p_timeline_id uuid,
     p_asset_id text,
     p_entry jsonb
   )
   returns void
   language sql
   security invoker
   set search_path = public
   as $$
     update public.timelines
     set
       asset_registry = jsonb_set(
         coalesce(asset_registry, '{"assets": {}}'::jsonb),
         array['assets', p_asset_id],
         p_entry
       ),
       updated_at = timezone('utc', now())
     where id = p_timeline_id;
   $$;

   grant execute on function public.upsert_asset_registry_entry(uuid, text, jsonb)
     to authenticated, service_role;
   ```

2. **Deploy**: `npx supabase db push --linked`.

### Step 8: Update `SupabaseDataProvider.registerAsset()` to use atomic RPC (`SupabaseDataProvider.ts`)
**Scope:** Small

1. **Replace** the read-then-write implementation (lines 212-237) with:
   ```typescript
   async registerAsset(timelineId: string, assetId: string, entry: AssetRegistryEntry): Promise<void> {
     const { error } = await getSupabaseClient().rpc('upsert_asset_registry_entry', {
       p_timeline_id: timelineId,
       p_asset_id: assetId,
       p_entry: entry,
     });
     if (error) throw error;
   }
   ```

2. The `loadAssetRegistry()` call is removed — no more read step.
