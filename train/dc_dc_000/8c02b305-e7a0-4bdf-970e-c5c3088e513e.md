> AGENT

Yes. The shot's settings are fetched twice through completely different paths:

1. **`useListShots`** — `select('*')` from `shots` table, which includes the `settings` JSON column. This data is available synchronously when you click a shot.
2. **`useShotSettings` → `useAutoSaveSettings` → `useToolSettings`** — a separate query that fetches the same `shots.settings` column, parses out the tool-specific slice, and runs through the cascade resolution.

The second fetch doesn't know about the first. It starts from scratch with hardcoded defaults, goes through idle → loading → ready, and only then has what was already sitting in memory from the list query.

The "optimistic defaults" fix I just added is a bandaid — it threads data from path 1 into path 2's initial state. But the real issue is that these are two independent data pipelines for the same row, with no shared cache layer between them.

Here's what I found. The settings pipeline has three layers of abstraction stacked on top of each other, and the core problem is that **two completely independent data pipelines fetch the same DB column**.

## The Two Pipelines

| | **Pipeline 1: Shot List** | **Pipeline 2: Tool Settings** |
|---|---|---|
| **Hook** | `useListShots` | `useToolSettings` |
| **Query** | `SELECT * FROM shots` | 3 parallel queries: `SELECT settings FROM users`, `projects`, `shots` |
| **Query Key** | `['shots', projectId, ...]` | `['toolSettings', toolId, projectId, shotId]` |
| **Returns** | Raw `shot.settings` JSON | Cascade-merged `{...defaults, ...user, ...project, ...shot}` |
| **Available** | Instantly on click | After idle → loading → ready |

When you click a shot, Pipeline 1 already has the settings in memory. Pipeline 2 starts from scratch — fetches the same `shots.settings` row again, plus user and project settings for cascade merge, then goes through a state machine.

## The Abstraction Stack

Pipeline 2 is 3 layers deep:

1. **`useToolSettings`** — cascade fetch (user → project → shot) + deep merge + React Query
2. **`useAutoSaveSettings`** — wraps #1 with local state, status machine (idle/loading/ready/saving/error), debounced auto-save, entity-change handling, edit versioning, race protection, unmount flush
3. **`useShotSettings`** — wraps #2 with session inheritance (sessionStorage), localStorage cross-shot persistence, apply-from-shot, apply-project-defaults, advancedMode special handling

Each layer adds real functionality, but the result is that reading a value that's already in memory goes through: React Query fetch → cascade merge → state machine → inheritance check → normalization → context provider → domain hook.

## What the Cascade Actually Does

The cascade merge (`{...defaults, ...userSettings, ...projectSettings, ...shotSettings}`) is meant to fill in missing fields. For a shot that already has settings saved, the shot-level values win for every field that's set. The cascade only matters for:
- **New shots** with no saved settings (inherits from project/user defaults)
- **Fields never set** at the shot level (rare in practice — the save writes the full object)

## Possible Streamlining

The cleanest fix that doesn't require restructuring the whole settings system:

**Seed the React Query cache from Pipeline 1 data.** When navigating to a shot, pre-populate the `['toolSettings', toolId, projectId, shotId]` cache entry from `shotToEdit.settings`. This makes Pipeline 2's fetch resolve instantly from cache (no loading phase, no flash), while preserving all the write/save/debounce machinery.

This is a one-line change in the right place, vs the optimistic-defaults bandaid I added which threads data through a new parameter.

When you click a shot in the list, `useListShots` has already fetched that shot's full row from the DB — including `settings`. So the correct `generationMode` is sitting in memory.

But the editor doesn't use that data. It calls `useShotSettings`, which calls `useToolSettings`, which fires a fresh `useQuery` with a different cache key. That query starts from scratch — empty cache, shows hardcoded defaults (`timeline`), fetches the DB, then finally resolves to the real value (`batch`). That's the flash.

The fix: right before `useShotSettings` runs, `useSeedSettingsCache` takes the settings that are already in memory on the shot object and writes them into the React Query cache under the key that `useToolSettings` is about to look up. So when `useQuery` runs, it finds data already there — cache hit, no loading state, no flash. The real background fetch still happens, but the UI never shows wrong defaults.

One line version: we connect the data that Pipeline 1 already has to the cache that Pipeline 2 is about to read from.
