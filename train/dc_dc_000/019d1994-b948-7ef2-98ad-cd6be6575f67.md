        # Implementation Plan: `megaplan step` CLI for plan step management

## Overview

Add a `megaplan step` command with `add`, `remove`, and `move` subcommands that operate directly on plan markdown files (`plan_v*.md`). The command parses `## Step N:` sections with fence-aware boundary detection, performs the requested edit, preserves `plan_v*.meta.json` fields, bumps the plan version via `plan_versions`, and resets state to `STATE_PLANNED` so the plan re-enters the critique loop.

**Current repo shape:** The CLI (`cli.py`) uses `argparse` with subparsers. Commands dispatch through `COMMAND_HANDLERS` (`megaplan/cli.py:310`). Plan markdown is parsed for validation in `validate_plan_structure` (`megaplan/evaluation.py:95`) using `_strip_fenced_blocks` (`megaplan/evaluation.py:83`). Plan versioning uses `next_plan_artifact_name` (`megaplan/handlers.py:290`) and `plan_versions` records. The `_override_replan` handler (`megaplan/handlers.py:1073`) implements the state-reset-to-PLANNED pattern. Meta JSON carries `questions`, `success_criteria`, `assumptions`, and `structure_warnings`.

**Key constraints:**
- Section parsing must be fence-aware (code blocks can contain `##` headers).
- After edit, structural validation must pass before committing the new version.
- Meta fields carry forward from the previous version.
- State resets to `STATE_PLANNED` with `last_gate` cleared (same as replan).

**Versioning rule:** `megaplan step` edits use **same-iteration subversioning** via `next_plan_artifact_name(plan_dir, state["iteration"])`, producing files like `plan_v1a.md` if `plan_v1.md` already exists. The iteration counter is NOT incremented — iteration bumps belong to worker-generated content (plan/revise). This matches the existing `handle_plan` rerun pattern (`megaplan/handlers.py:434-435`, `442-445`) and is consistent with `test_plan_rerun_keeps_iteration_and_uses_same_iteration_subversion` (`tests/test_megaplan.py:128-140`).

**Step add scaffold:** `step add` generates a minimal validator-compliant section body containing one numbered substep placeholder and one backticked file reference, so the result passes `validate_plan_structure` without additional user input:
```markdown
## Step N: User's description
**Scope:** Small
1. **TODO** Fill in implementation details (`path/to/file`).
```

## Step 1: Build fence-aware section parser (`megaplan/evaluation.py`)
**Scope:** Medium — this is the core primitive everything else depends on.

1. **Implement** `parse_plan_sections(plan_text: str) -> list[PlanSection]` after `_strip_fenced_blocks` (`megaplan/evaluation.py:93`). `PlanSection` is a simple dataclass with fields: `id` (`"S1"` or `None` for non-step sections), `heading` (full heading text), `start_line` (0-based inclusive), `end_line` (exclusive), `body` (raw text including heading).
2. **Reuse** the fence-tracking pattern from `_strip_fenced_blocks` (`megaplan/evaluation.py:83-92`) but instead of stripping, track `inside_fence` state while scanning for `^##\s+Step\s+\d+:\s+` and `^##\s+` boundaries. Only match headings when `inside_fence is False`. Non-step `##` headings (Overview, Execution Order, etc.) become sections with `id=None`. Content before the first `##` heading (the H1 title + any preamble) becomes a leading section with `id=None, heading=""`.
3. **Add** `reassemble_plan(sections: list[PlanSection]) -> str` that joins `section.body` values back into a complete markdown document.
4. **Add** `renumber_steps(sections: list[PlanSection]) -> list[PlanSection]` that updates `id` fields and heading text (`## Step 1: ...` → `## Step 2: ...`) for step sections only, preserving non-step sections unchanged. Uses `re.sub(r"^##\s+Step\s+\d+:", f"## Step {n}:", heading)` on each step section's heading and first line of body.

```python
@dataclass
class PlanSection:
    id: str | None        # "S1", "S2", ... or None for non-step sections
    heading: str          # "## Step 1: Audit the code" or "" for preamble
    start_line: int
    end_line: int
    body: str             # Full text including heading line
```

## Step 2: Implement step manipulation logic (`megaplan/handlers.py`)
**Scope:** Medium

1. **Add** `handle_step(root, args) -> StepResponse` at end of `megaplan/handlers.py`. Dispatches to `_step_add`, `_step_remove`, `_step_move` based on `args.step_action`.
2. **`_step_add(plan_dir, state, args)`:** Parse latest plan via `parse_plan_sections`. Build a scaffold section:
   ```python
   body = f"## Step 0: {description}\n**Scope:** Small\n1. **TODO** Fill in implementation details (`path/to/file`).\n\n"
   section = PlanSection(id="S0", heading=f"## Step 0: {description}", start_line=0, end_line=0, body=body)
   ```
   Insert after the `--after` step (or after the last step section if `--after` omitted). Renumber, reassemble, validate, commit.
3. **`_step_remove(plan_dir, state, args)`:** Parse latest plan, find and remove the named step section. Reject if only one step remains. Renumber, reassemble, validate, commit.
4. **`_step_move(plan_dir, state, args)`:** Parse latest plan, extract the named step, insert it after the `--after` target. Renumber, reassemble, validate, commit.
5. **Common "commit" helper** `_commit_step_edit(plan_dir, state, plan_text, action_summary)`:
   - Use `next_plan_artifact_name(plan_dir, state["iteration"])` for same-iteration subversioning (produces `plan_v1a.md` etc.). Do NOT increment `state["iteration"]`.
   - Run `validate_plan_structure(plan_text)` — raise `CliError("structure_error", ...)` if the critical step-section issue is present.
   - Write new `plan_v{N}*.md`.
   - Read previous `plan_v*.meta.json`, carry forward `questions`, `success_criteria`, `assumptions` into new meta. Set `structure_warnings` from the fresh validation. Add `"step_edit": action_summary` field.
   - Append to `state["plan_versions"]` with the new file and hash.
   - Set `state["current_state"] = STATE_PLANNED`, clear `state["last_gate"]`.
   - Record edit in `state["history"]` via `append_history`.
   - `save_state(plan_dir, state)`.
6. **Allowed states:** `{STATE_PLANNED, STATE_CRITIQUED, STATE_GATED, STATE_FINALIZED}` — matching `_override_replan`'s set plus `STATE_PLANNED` itself.
