        # Implementation Plan: Unify References and Generations

## Overview

**Current state:** References and generations are completely separate entities. The `resources` table stores style-reference images independently (with image URLs in JSONB `metadata`). When a user clicks "Add to references" on a generation, the system *re-downloads* the image, *re-uploads* it to 3 new storage paths (original, aspect-processed, thumbnail), and creates a `resource` record with no link back to the generation. The gallery (`ShotImageManager`) shows generations; the reference grid (`ReferenceGrid`) shows references — they never overlap.

**Goal:** Every image in the system is a generation. Resources become a thin metadata/settings layer pointing to a generation via `generation_id`. Uploaded references create a generation record, then a resource pointing to it. "Add as reference" from the gallery just creates a resource pointing to the existing generation (no re-upload). The gallery shows both generated and uploaded-reference images mixed together.

**Key constraints:**
- Resources are user-scoped (`user_id`) and can be public. Generations are project-scoped (`project_id`). This tension must be resolved for cross-project reference sharing.
- The `ReferenceImage` pointer (stored in project settings) currently points to `resourceId`. This indirection stays — pointer → resource → generation.
- Hydration currently resolves image URLs from `resource.metadata.styleReferenceImage`. Post-refactor, it resolves from `generation.location` (with resource metadata as fallback during migration).
- Supabase safety: migrations via `npx supabase db push --linked`, edge functions deployed individually.

## Phase 1: Data Model Changes — DB Migration + Types

### Step 1: Add `generation_id` column to resources table (`supabase/migrations/`)
**Scope:** Small
1. **Create migration** `supabase/migrations/YYYYMMDD000000_add_generation_id_to_resources.sql`:
   - `ALTER TABLE resources ADD COLUMN generation_id UUID REFERENCES generations(id) ON DELETE CASCADE;`

## Phase 6: Cascade Deletes

### Step 9: Implement cascade delete logic
**Scope:** Medium
1. **Generation → Resource (DB cascade):** Already handled by Step 1's FK: `REFERENCES generations(id) ON DELETE CASCADE`. Deleting a generation automatically deletes any resource pointing to it.
2. **Resource → Generation (app-level):** When deleting a reference via `handleDeleteReference` in `useReferenceResourceMutations.ts:97-143`:
   - After deleting the resource, check if the resource had a `generation_id`.
   - If the generation's `type` is `'uploaded-reference'` (it was created solely as a reference), delete the generation too.
   - If the generation's `type` is something else (it was AI-generated and later added as a reference), do NOT delete the generation — only remove the resource link.
   - This distinction prevents deleting a user's gallery image when they remove it as a reference.
3. **Clean up `shot_generations`**: Deleting the generation will cascade to `shot_generations` via existing FK. For app-level resource deletion of uploaded references, the generation deletion handles this.
4. **Clean up project settings**: The existing pointer cleanup in `handleDeleteReference` already handles removing the `ReferenceImage` pointer and updating `selectedReferenceIdByShot`.

## Phase 7: Migration of Existing Data

### Step 10: Backfill migration for existing resources (`supabase/migrations/`)
**Scope:** Large
1. **Create migration** that for each `resource` with `type = 'style-reference'` and `generation_id IS NULL`:
   - Creates a `generations` row using the resource's metadata URLs:
     - `location` ← `metadata->>'styleReferenceImageOriginal'` (or `styleReferenceImage`)
     - `thumbnail_url` ← `metadata->>'thumbnailUrl'`
     - `type` ← `'uploaded-reference'`
     - `project_id` — **Problem:** resources don't have `project_id`. They're user-scoped. We need to pick a project. Options:
       - Look at `ProjectImageSettings` to find which projects reference this resource, and use the first one.
       - Create the generation in a "default" or first project for the user.
       - Leave `generation_id` null for resources that can't be cleanly attributed to a project (migration runs later when more info is available).
   - Updates `resource.generation_id` to point to the new generation.
   - Creates `shot_generations` entries for each shot that uses this reference (requires reading `ProjectImageSettings`).
2. **This is the hardest step** — the project attribution problem (see Question 2) may require a multi-phase approach: DB migration creates generations, then a client-side migration (similar to existing legacy migrations in `src/shared/components/ImageGenerationForm/hooks/legacyMigrations/`) fills in `shot_generations` when a project is loaded.
3. **Alternative simpler approach**: Skip the DB-level backfill entirely. Add a client-side migration hook (like the existing `useResourceMigration.ts` pattern) that runs when a project loads:
   - For each reference pointer in the project's settings, check if the linked resource has `generation_id`.
   - If not, create a generation from the resource metadata, update the resource, and create `shot_generations` entries.
   - This is lazy and per-project, avoiding the project attribution problem.
