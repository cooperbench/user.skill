**Findings**

1. The migration plan is mostly accurate on the core active app scope, but it is app-scope filtered, not full worker-capability filtered. It says 17 task types are migration scope and 19 are dropped as unused: [migration-vibecomfy.md](/Users/user_c042661f/Documents/reigh-workspace/docs/migration-vibecomfy.md:407). The worker still actively dispatches the dropped specialized handlers, including `extract_frame`, `rife_interpolate_images`, `create_visualization`, `magic_edit`, `inpaint_frames`, and raw `comfy`. If stale DB rows, admin tools, retries, or direct emitters can enqueue them, Comfy workers need WGP fallback or explicit rejection.

2. `dispatch_manifest.py` is not a safe source of truth for specialized handlers. It only lists `travel_orchestrator`, `extract_frame`, `travel_segment`, and `individual_travel_segment`, while `TaskRegistry.dispatch` has 14 specialized keys. Migration code should use the registry table or a corrected manifest. Sources: [dispatch_manifest.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/dispatch_manifest.py:3), [task_registry.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/task_registry.py:1441).

3. The doc’s “Seam B” description overstates `rife_interpolate_images` as a child-generation/queue-seam handler. The handler accepts `task_queue` but does not submit a `GenerationTask`; it directly calls the RIFE media helper and writes/uploads an interpolated mp4. Sources: [migration-vibecomfy.md](/Users/user_c042661f/Documents/reigh-workspace/docs/migration-vibecomfy.md:290), [rife_interpolate.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/rife_interpolate.py:17), [rife_interpolate.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/rife_interpolate.py:82).

4. I found no active `video_enhance` or FILM task handler in `reigh-worker`. The actual interpolation task is `rife_interpolate_images`, plus the underlying RIFE helper used by travel/guide-video code. The doc’s note that FILM/video_enhance is “a different worker task type” is not supported by this worker codebase. Sources: [migration-vibecomfy.md](/Users/user_c042661f/Documents/reigh-workspace/docs/migration-vibecomfy.md:177), [task_registry.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/task_registry.py:1504), [travel_guide.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/media/video/travel_guide.py:38).

5. Thumbnail handling is not a task type or dispatch handler. It is a completion/upload side effect for video outputs: existing poster or first-frame extraction, then base64 or signed upload thumbnail propagation. The migration plan mentions thumbnail parity, which is correct, but it should stay scoped to completion/upload behavior rather than VibeComfy templates. Sources: [task_status.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/core/db/task_status.py:40), [task_status.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/core/db/task_status.py:297), [task_status.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/core/db/task_status.py:402).

6. `qwen_image_hires` is a real direct-queue worker branch, but the plan treats it as unused/skippable after app filtering. That is fine for app migration, but not full queue-contract preservation. Also, catalog says empty prompt is allowed for `qwen_image_hires` and `annotated_image_edit`, while `db_task_to_generation_task` currently rejects empty prompts for both before reaching their handlers. Sources: [task_types.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/task_types.py:125), [task_conversion.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/task_conversion.py:21), [task_conversion.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/task_handlers/tasks/task_conversion.py:127).

**Bottom Line**

The migration plan is good for current app-emitted routes, including travel/join stitching, but it under-specifies the worker’s broader dispatch behavior: unknown fallback dispatch, stale narrow manifest, native media utilities, and completion-time thumbnails. The most important non-Wan2GP correction is that there is no worker-side `video_enhance`/FILM handler here; actual interpolation is RIFE, and it is native media processing, not a VibeComfy/WGP queue seam.
