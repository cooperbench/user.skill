## Overview

The travel task system spans three repos (reigh-app create-task, reigh-worker GPU execution, reigh-app complete_task) with massive payload duplication, dead parameters, inconsistent naming, and a complex 3-tier parameter precedence that makes the system hard to understand. The goal is to clean this up while preserving all existing behavior exactly.

**Current state:**
- `composeTaskFamilyPayload` spreads orchestrator_details at top level AND nests them under `orchestrator_details` — double copy in every orchestrator task
- The worker then copies the entire `orchestrator_payload` into every segment as `orchestrator_details` — triple nesting
- `individual_segment_params` duplicates ~15 fields already at top level
- `orchestrator_utils.py` extracts ~28 fields, many never used downstream
- Frame count has 4 field names: `num_frames`, `segment_frames_target`, `segment_frames_expanded[idx]`, `video_length`
- Dead params: `openai_api_key`, `params_json_str`, `regenerate_anchors`, `image_variant_ids`, `chain_segments`, `structure_guidance` (in orchestrator input), `stitch_config`
- Dead contract fields: `generation_routing`, `sibling_lookup`, `segment_regen_mode` stored but never consumed
- Legacy alias `full_orchestrator_payload` still checked as fallback

**Constraints:**
- All existing task creation/execution/completion paths must produce identical behavior
- In-flight tasks in the database have current payload structure — backward compatibility required during transition
- Worker-created passthrough path for `individual_travel_segment` must continue to work
- `task_view_contract` and `family_contract` are read by the frontend for display — must be preserved
- `orchestration_contract` fields like `orchestrator_task_id`, `run_id`, `parent_generation_id`, `child_order`, `shot_id` are actively consumed during completion — must be preserved
- The turbo_mode path (wan_2_2_i2v → API orchestrator) must continue to work
- `complete_task` reads `orchestrator_details.segment_frames_expanded[idx]`, `base_prompts_expanded[idx]`, etc. — segment-indexed arrays in orchestrator_details must remain accessible

**Approach:** 6 phases, each a separate PR, ordered from safest to most impactful. Each phase is independently shippable and testable.

        # Implementation Plan: Travel Task Parameter Cleanup

## Overview

The travel task system spans three repos (reigh-app create-task, reigh-worker GPU execution, reigh-app complete_task) with massive payload duplication, dead parameters, inconsistent naming, and a complex 3-tier parameter precedence that makes the system hard to understand. The goal is to clean this up while preserving all existing behavior exactly.

**Current state:**
- `composeTaskFamilyPayload` spreads orchestrator_details at top level AND nests them under `orchestrator_details` — double copy in every orchestrator task. This helper is shared by travel, individual_travel_segment, AND join_clips resolvers.
- The worker copies the entire `orchestrator_payload` into every segment as `orchestrator_details` — triple nesting.
- `individual_segment_params` duplicates ~15 fields already at top level. This namespace is read by 10+ frontend components/hooks and complete_task handlers.
- `orchestrator_utils.py` `extract_orchestrator_parameters()` extracts ~28 fields. It is called by magic_edit.py and task_conversion.py in addition to the travel segment handler — it is NOT travel-only.
- Frame count has 4 field names: `num_frames`, `segment_frames_target`, `segment_frames_expanded[idx]`, `video_length`.
- Dead params confirmed: `openai_api_key`, `params_json_str`, `regenerate_anchors`, `image_variant_ids` (never forwarded to payload).
- Fields sent by frontend but silently dropped by resolver (pre-existing gap, not addressed in this cleanup): `chain_segments`, `stitch_config`, `structure_guidance`.
- Dead contract fields: `generation_routing`, `sibling_lookup`, `segment_regen_mode` stored but never consumed at runtime (only by debug CLI tool).
- Legacy alias `full_orchestrator_payload` still read as fallback in 15+ locations across reigh-app and reigh-worker — cannot be removed, only standardized in writes.

**Constraints:**
- All existing task creation/execution/completion paths must produce identical behavior.
- In-flight tasks in the database have current payload structure — backward compatibility via read-side fallbacks (strategy A: always fall back to old field names).
- Worker-created passthrough path for `individual_travel_segment` must continue to work.
- `task_view_contract` and `family_contract` are read by the frontend for display — must be preserved.
- `orchestration_contract` fields like `orchestrator_task_id`, `run_id`, `parent_generation_id`, `child_order`, `shot_id` are actively consumed during completion — must be preserved.
- `composeTaskFamilyPayload()` is shared across travel, individual_travel_segment, and joinClips resolvers — changes to it affect all three.
- `extract_orchestrator_parameters()` is shared across magic_edit, task_conversion, and travel segment handler — field pruning must consider all callers.
- `individual_segment_params` is read by `taskParamsUtils.ts`, `taskPayloadSnapshot.ts`, `travelPayloadReader.ts`, `segmentImages.ts`, `variantSourceImages.ts`, `segmentDataTransforms.ts`, `usePendingGenerationTasks.ts`, `useLoadVariantImages.ts`, `taskParamNormalizer.ts`, `generation-handlers.ts` — cannot be renamed or restructured without updating all readers.
- The turbo_mode path (wan_2_2_i2v → API orchestrator) must continue to work.
- `complete_task` reads `orchestrator_details.segment_frames_expanded[idx]`, `base_prompts_expanded[idx]`, etc. — segment-indexed arrays in orchestrator_details must remain accessible.

**Backward compatibility strategy:** Fallback-first (strategy A). All field reads keep existing fallback chains. New writes use canonical names. Old names are never removed from read paths — they naturally die out as old tasks complete. No payload_version field needed. No coordinated deploys needed.

**Approach:** 5 phases, each a separate PR, ordered from safest to most impactful. Each phase is independently shippable and testable.
