# Seinfeld dataset-build — medium sprint
**Profile:** `thoughtful//medium` · **Robustness:** standard · **Vendor:** config default

Make the Seinfeld LoRA dataset pipeline genuinely good: human-gated, iteration-friendly, vocab-change-aware, and source-diverse. Build the generic `builtin.human_review` primitive in Astrid as part of the same sprint — it's the missing piece both for this project and for several future ones.

## Background

## What v0 got right (do not change)

- Bucket-fill state file (`state.json`) — resumable forward
- Search query templates per bucket (`BUCKET_QUERIES`) inside `run.py`
- Per-video subdir with downloaded mp4 + scenes.json + per-scene `.judge.json`
- Cut clips + `.caption.json` land in `accepted/<bucket>/`
- VLM judge runs in `fast` mode, caption runs in `best` mode (cost discipline)
- `builtin.visual_understand --response-schema` is the right pattern for vocabulary-locked outputs — don't fork it

## What v0 got wrong (this sprint fixes)

Observed concretely on the v0 run:
1. **Source concentration.** 5 of 15 jerrys_apt clips came from one source video; multiple monks_diner clips from one compilation. The bucket-fill loop has no per-source cap.
2. **No human review step.** Caption errors and judge false-positives ship into the final manifest. Some captions describe a frame, not the motion in the clip. The reviewer is the natural place to catch this.
3. **Vocab drift is silent.** Editing `vocabulary.yaml` does nothing to existing artifacts — captions and judgements stay frozen against the old vocab. The user has no signal that a re-run is needed.
4. **Schemas are hand-written.** `bucket_judge.json` and `caption.json` were generated by Claude from `vocabulary.yaml`. The two will drift; the yaml is the only source of truth that should be edited.
5. **Rejection has no feedback loop.** Even if there were a reviewer, a "reject — watermark" decision doesn't inform the next collection round. The same source channel will be queried again next run.
6. **Phase-level rewind is manual.** To re-judge with a tighter prompt, the user has to delete every `*.judge.json` by hand AND clear `state.json` to un-process the video ids. There is no `--redo judge` or equivalent.

## What to build

Five primitives + one integration. All sized for ~1 week. Listed in dependency order, but the agent can re-sequence within reason.

### 1. `builtin.human_review` — generic human-gate executor

**Location:** `astrid/packs/builtin/human_review/{executor.yaml,run.py,STAGE.md}`

A single Python file (~120 LOC plus tests) that spins up a local HTTP server, opens the browser at a free port, and blocks until the page POSTs to `/submit`. Generic — must be reusable by any orchestrator that needs a human in the loop. Not Seinfeld-specific in any way.

Required CLI surface:
- `--html PATH` — single HTML file OR directory served as `/`
- `--data PATH` — JSON file, served as `/data.json` (read-only mount)
- `--serve PREFIX=DIR` — repeatable static mount (e.g. `--serve /clips=runs/seinfeld-dataset/accepted`)
- `--state PATH` — JSON file for partial saves; `POST /save` writes to it (per keypress, resumable)
- `--out PATH` — JSON file written on `POST /submit`; server exits 0 after write
- `--response-schema PATH` (optional) — JSON schema that validates `/submit` body strictly; mirror the `visual_understand --response-schema` contract
- `--port N` — explicit port, or `0` for auto (default 0)
- `--no-open` — skip auto-browser-launch (for headless CI / scripted use)
- `--timeout S` — exit nonzero if no submit by deadline; default unlimited

Contract details to decide during planning:
- How does `/save` interact with `/submit`? (Suggested: `/submit` body wins; `/save` is best-effort recovery state.)
- Should the server require a per-session token to reject drive-by POSTs from other localhost processes? (Suggested: yes — auto-generated, printed once on launch, embedded as a query param in the page URL.)
- How are errors surfaced to the page? (Suggested: HTTP 4xx with a JSON `{error, detail}` body the page can render.)

### 2. Seinfeld `review.html`

**Location:** `astrid/packs/seinfeld/dataset_build/review.html` (single file, inline JS/CSS, ~80–120 LOC)

Consumes `/data.json` (the provisional manifest), plays one clip at a time from `/clips/<bucket>/<id>.mp4`, displays caption + judge confidence below. Hotkey-driven, no clicks required for the happy path:
- `Y` / `Space` / `→` — accept, advance
- `N` / `X` — reject, advance
- `←` — go back
- `1`–`4` — tag a reject reason (`watermark | wrong_scene | wrong_character | bad_motion`); applies to most-recent reject
- `E` — open inline caption-edit overlay (saves a corrected caption alongside the decision)
- `Enter` — when all reviewed, `POST /submit` with the full decision set

Black background, large video, minimal chrome. Progress bar `X / N reviewed`. Decisions auto-`POST /save` on every keypress.

Output schema (validated by `--response-schema`):
```json
{
  "decisions": {
    "<clip_id>": {
      "decision": "accept" | "reject",
      "reject_reason": null | "watermark" | "wrong_scene" | "wrong_character" | "bad_motion",
      "edited_caption": null | "<string>",
      "reviewed_at": "<iso8601>"
    }
  },
  "completed_at": "<iso8601>"
}
```

### 3. Content-addressed artifact freshness

**Goal:** changing `vocabulary.yaml` or a judge prompt makes the pipeline re-run only the affected phases on the next invocation, without manual file deletion or a `--redo` flag.

**Approach:** each artifact (scenes.json, per-scene judge.json, per-scene caption.json, per-clip mp4) carries a small `.meta.json` sidecar recording the hash of its inputs. On re-run, before invoking a step, the orchestrator computes the expected hash from current inputs and compares — stale → regenerate.

Hash inputs per phase:
- `scenes.json`: hash(source video bytes) — almost never invalidates
- `judge.json`: hash(scene window + judge schema content + judge prompt template + vocab version)
- `caption.json`: hash(scene window + caption schema content + caption prompt template + vocab version)
- `cut clip mp4`: hash(source video bytes + scene start/end + ffmpeg encode options)

`vocab version` is a hash of `vocabulary.yaml` contents (skip whitespace/comments). The phase boundary is the level we hash at — don't go finer.

User-facing behavior on re-run after a vocab edit:
```
vocab: v1 (hash a8c3...) → v2 (hash f912...)
  judge.json stale: 30 → regenerate ($0.06 est)
  caption.json stale: 30 → regenerate ($0.45 est)
  scenes.json fresh, mp4 fresh — keep
proceed? [Y/n]
```

The cheap `--redo <phase>` flag is **NOT in scope** if content-addressing works — it becomes redundant. Drop it.

### 4. Vocabulary → schemas generator

**Location:** `astrid/packs/seinfeld/vocab_compile.py` (or wherever fits Astrid conventions — judgment call)

Reads `vocabulary.yaml`, writes `schemas/bucket_judge.json` and `schemas/caption.json`. Runs automatically as the first step of `dataset_build/run.py` so the schemas are always derived. `vocabulary.yaml` is the only file the user edits. Generated schemas carry a `// generated from vocabulary.yaml@<hash>` header.

Bucket-judge schema is derived from `scenes` + `characters`. Caption schema is derived from `scenes` + `characters` (with per-character outfit enums) + `shot_types` + the `caption_template` string.

### 5. Source-diversity cap + reject-reason feedback

**In `dataset_build/run.py`:**
- New flag `--max-clips-per-source N` (default 3). The bucket-fill loop tracks `clips_per_source_video[vid]` in `state.json` and stops accepting from a video once it hits cap, even if the bucket isn't full. This is a one-line change; the value is observable behavior.
- After human review completes, the orchestrator reads `human_review.final.json` and:
  - **Filters** the final manifest to only `decision == "accept"` clips
  - **Records** rejected source-video ids → `state.json["denylist_source_videos"]` (any reject with reason `watermark` or `wrong_scene` triggers this for the whole source video)
  - **Top-up:** if reject count brings any bucket under target, re-run the bucket-fill loop with denylist applied, then re-open the reviewer on the new clips only. Cap: 2 top-up rounds max per invocation.
- Reject reasons inform a single judge-prompt extension at the start of each iteration: lines like *"In prior rounds you frequently mis-accepted watermark overlays as valid Seinfeld scenes. Reject any frame with a channel logo or text overlay in the corners."* Build this from a small static map of reason → prompt-extension; not generated by an LLM.

### 6. Orchestrator integration

**In `dataset_build/run.py`:**
The driver should chain:
```
generate schemas → bucket-fill (with cap + denylist) →
  write provisional manifest → invoke builtin.human_review →
  read decisions → maybe top-up (≤2 rounds) →
  write final manifest
```

Plus modes:
- Default: run all phases as needed (content-addressing skips fresh ones automatically).
- `--review-only`: skip collection, open reviewer on existing provisional manifest. Useful for re-reviewing.
- `--no-review`: stop at provisional manifest. Useful for headless / CI.
- `--top-up-rounds N` — override the default 2 cap.

Resumability invariants (must hold across all modes):
- Interrupt mid-collection → re-run picks up at next video
- Interrupt mid-review → re-run opens reviewer at next unreviewed clip
- Interrupt during top-up → re-run resumes the top-up round
- Edit `vocabulary.yaml` mid-flight → re-run invalidates and re-runs affected phases only

**Profile:** `thoughtful//medium` · **Robustness:** standard · **Vendor:** config default

Make the Seinfeld LoRA dataset pipeline genuinely good: human-gated, iteration-friendly, vocab-change-aware, and source-diverse. Build the generic `builtin.human_review` primitive in Astrid as part of the same sprint — it's the missing piece both for this project and for several future ones.

## Background

## What v0 got right (do not change)

- Bucket-fill state file (`state.json`) — resumable forward
- Search query templates per bucket (`BUCKET_QUERIES`) inside `run.py`
- Per-video subdir with downloaded mp4 + scenes.json + per-scene `.judge.json`
- Cut clips + `.caption.json` land in `accepted/<bucket>/`
- VLM judge runs in `fast` mode, caption runs in `best` mode (cost discipline)
- `builtin.visual_understand --response-schema` is the right pattern for vocabulary-locked outputs — don't fork it

## What v0 got wrong (this sprint fixes)

Observed concretely on the v0 run:
1. **Source concentration.** 5 of 15 jerrys_apt clips came from one source video; multiple monks_diner clips from one compilation. The bucket-fill loop has no per-source cap.
2. **No human review step.** Caption errors and judge false-positives ship into the final manifest. Some captions describe a frame, not the motion in the clip. The reviewer is the natural place to catch this.
3. **Vocab drift is silent.** Editing `vocabulary.yaml` does nothing to existing artifacts — captions and judgements stay frozen against the old vocab. The user has no signal that a re-run is needed.
4. **Schemas are hand-written.** `bucket_judge.json` and `caption.json` were generated by Claude from `vocabulary.yaml`. The two will drift; the yaml is the only source of truth that should be edited.
5. **Rejection has no feedback loop.** Even if there were a reviewer, a "reject — watermark" decision doesn't inform the next collection round. The same source channel will be queried again next run.
6. **Phase-level rewind is manual.** To re-judge with a tighter prompt, the user has to delete every `*.judge.json` by hand AND clear `state.json` to un-process the video ids. There is no `--redo judge` or equivalent.

## What to build

Five primitives + one integration. All sized for ~1 week. Listed in dependency order, but the agent can re-sequence within reason.

### 1. `builtin.human_review` — generic human-gate executor

**Location:** `astrid/packs/builtin/human_review/{executor.yaml,run.py,STAGE.md}`

A single Python file (~120 LOC plus tests) that spins up a local HTTP server, opens the browser at a free port, and blocks until the page POSTs to `/submit`. Generic — must be reusable by any orchestrator that needs a human in the loop. Not Seinfeld-specific in any way.

Required CLI surface:
- `--html PATH` — single HTML file OR directory served as `/`
- `--data PATH` — JSON file, served as `/data.json` (read-only mount)
- `--serve PREFIX=DIR` — repeatable static mount (e.g. `--serve /clips=runs/seinfeld-dataset/accepted`)
- `--state PATH` — JSON file for partial saves; `POST /save` writes to it (per keypress, resumable)
- `--out PATH` — JSON file written on `POST /submit`; server exits 0 after write
- `--response-schema PATH` (optional) — JSON schema that validates `/submit` body strictly; mirror the `visual_understand --response-schema` contract
- `--port N` — explicit port, or `0` for auto (default 0)
- `--no-open` — skip auto-browser-launch (for headless CI / scripted use)
- `--timeout S` — exit nonzero if no submit by deadline; default unlimited

Contract details to decide during planning:
- How does `/save` interact with `/submit`? (Suggested: `/submit` body wins; `/save` is best-effort recovery state.)
- Should the server require a per-session token to reject drive-by POSTs from other localhost processes? (Suggested: yes — auto-generated, printed once on launch, embedded as a query param in the page URL.)
- How are errors surfaced to the page? (Suggested: HTTP 4xx with a JSON `{error, detail}` body the page can render.)

### 2. Seinfeld `review.html`

**Location:** `astrid/packs/seinfeld/dataset_build/review.html` (single file, inline JS/CSS, ~80–120 LOC)

Consumes `/data.json` (the provisional manifest), plays one clip at a time from `/clips/<bucket>/<id>.mp4`, displays caption + judge confidence below. Hotkey-driven, no clicks required for the happy path:
- `Y` / `Space` / `→` — accept, advance
- `N` / `X` — reject, advance
- `←` — go back
- `1`–`4` — tag a reject reason (`watermark | wrong_scene | wrong_character | bad_motion`); applies to most-recent reject
- `E` — open inline caption-edit overlay (saves a corrected caption alongside the decision)
- `Enter` — when all reviewed, `POST /submit` with the full decision set

Black background, large video, minimal chrome. Progress bar `X / N reviewed`. Decisions auto-`POST /save` on every keypress.

Output schema (validated by `--response-schema`):
```json
{
  "decisions": {
    "<clip_id>": {
      "decision": "accept" | "reject",
      "reject_reason": null | "watermark" | "wrong_scene" | "wrong_character" | "bad_motion",
      "edited_caption": null | "<string>",
      "reviewed_at": "<iso8601>"
    }
  },
  "completed_at": "<iso8601>"
}
```

### 3. Content-addressed artifact freshness

**Goal:** changing `vocabulary.yaml` or a judge prompt makes the pipeline re-run only the affected phases on the next invocation, without manual file deletion or a `--redo` flag.

**Approach:** each artifact (scenes.json, per-scene judge.json, per-scene caption.json, per-clip mp4) carries a small `.meta.json` sidecar recording the hash of its inputs. On re-run, before invoking a step, the orchestrator computes the expected hash from current inputs and compares — stale → regenerate.

Hash inputs per phase:
- `scenes.json`: hash(source video bytes) — almost never invalidates
- `judge.json`: hash(scene window + judge schema content + judge prompt template + vocab version)
- `caption.json`: hash(scene window + caption schema content + caption prompt template + vocab version)
- `cut clip mp4`: hash(source video bytes + scene start/end + ffmpeg encode options)

`vocab version` is a hash of `vocabulary.yaml` contents (skip whitespace/comments). The phase boundary is the level we hash at — don't go finer.

User-facing behavior on re-run after a vocab edit:
```
vocab: v1 (hash a8c3...) → v2 (hash f912...)
  judge.json stale: 30 → regenerate ($0.06 est)
  caption.json stale: 30 → regenerate ($0.45 est)
  scenes.json fresh, mp4 fresh — keep
proceed? [Y/n]
```

The cheap `--redo <phase>` flag is **NOT in scope** if content-addressing works — it becomes redundant. Drop it.

### 4. Vocabulary → schemas generator

**Location:** `astrid/packs/seinfeld/vocab_compile.py` (or wherever fits Astrid conventions — judgment call)

Reads `vocabulary.yaml`, writes `schemas/bucket_judge.json` and `schemas/caption.json`. Runs automatically as the first step of `dataset_build/run.py` so the schemas are always derived. `vocabulary.yaml` is the only file the user edits. Generated schemas carry a `// generated from vocabulary.yaml@<hash>` header.

Bucket-judge schema is derived from `scenes` + `characters`. Caption schema is derived from `scenes` + `characters` (with per-character outfit enums) + `shot_types` + the `caption_template` string.

### 5. Source-diversity cap + reject-reason feedback

**In `dataset_build/run.py`:**
- New flag `--max-clips-per-source N` (default 3). The bucket-fill loop tracks `clips_per_source_video[vid]` in `state.json` and stops accepting from a video once it hits cap, even if the bucket isn't full. This is a one-line change; the value is observable behavior.
- After human review completes, the orchestrator reads `human_review.final.json` and:
  - **Filters** the final manifest to only `decision == "accept"` clips
  - **Records** rejected source-video ids → `state.json["denylist_source_videos"]` (any reject with reason `watermark` or `wrong_scene` triggers this for the whole source video)
  - **Top-up:** if reject count brings any bucket under target, re-run the bucket-fill loop with denylist applied, then re-open the reviewer on the new clips only. Cap: 2 top-up rounds max per invocation.
- Reject reasons inform a single judge-prompt extension at the start of each iteration: lines like *"In prior rounds you frequently mis-accepted watermark overlays as valid Seinfeld scenes. Reject any frame with a channel logo or text overlay in the corners."* Build this from a small static map of reason → prompt-extension; not generated by an LLM.

### 6. Orchestrator integration

**In `dataset_build/run.py`:**
The driver should chain:
```
generate schemas → bucket-fill (with cap + denylist) →
  write provisional manifest → invoke builtin.human_review →
  read decisions → maybe top-up (≤2 rounds) →
  write final manifest
```

Plus modes:
- Default: run all phases as needed (content-addressing skips fresh ones automatically).
- `--review-only`: skip collection, open reviewer on existing provisional manifest. Useful for re-reviewing.
- `--no-review`: stop at provisional manifest. Useful for headless / CI.
- `--top-up-rounds N` — override the default 2 cap.

Resumability invariants (must hold across all modes):
- Interrupt mid-collection → re-run picks up at next video
- Interrupt mid-review → re-run opens reviewer at next unreviewed clip
- Interrupt during top-up → re-run resumes the top-up round
- Edit `vocabulary.yaml` mid-flight → re-run invalidates and re-runs affected phases only

Repo shape:
- Astrid packs at `astrid/packs/<pack>/<name>/` with `executor.yaml` + `run.py` + `STAGE.md` (`docs/creating-tools.md`).
- Executor discovery via `astrid/core/executor/registry.py` (directory scan over pack dirs — `astrid/packs/builtin/pack.yaml` is metadata only, no per-executor entry required; verified by sibling executors like `human_notes`, `editor_review`).
- HTTP server analog: `astrid/packs/builtin/render/run.py` (`ThreadingHTTPServer` + `_pick_free_port` + Range support). NOTE: the upstream `SimpleHTTPRequestHandler.translate_path` is CWD-based; the new executor needs its own `do_GET` dispatcher to handle `--serve PREFIX=DIR` prefix→directory routing.
- `--response-schema` analog: `astrid/packs/builtin/visual_understand/run.py`.
- `jsonschema>=4.0` is already pinned (`pyproject.toml`) and imported across the codebase — use it directly, no fallback.
- Seinfeld pack at `astrid/packs/seinfeld/` (gitignored). v0 `dataset_build/run.py` already drives `state.json` + `processed_video_ids`, and contains a hardcoded `_pyenv_env()` (~line 51) injecting `PYENV_VERSION=3.11.11` — to be parameterized in this sprint (see Step 8).
- Tests under `tests/`, pytest-style. `builtin.human_review` is checked in; `astrid/packs/seinfeld/` and `runs/` stay gitignored.

Hard constraints: keep `builtin.human_review` generic (no Seinfeld leakage); no machine-specific paths in builtin executors; ~1 week budget — resist abstraction creep.

## Phase 1: `builtin.human_review` primitive

### Step 1: Scaffold the executor (`astrid/packs/builtin/human_review/`)
**Scope:** Small
1. **Create** `executor.yaml` mirroring `astrid/packs/builtin/visual_understand/executor.yaml` shape — id `builtin.human_review`, `argv: ["{python_exec}", "-m", "astrid.packs.builtin.human_review.run", ...]`, declare CLI args (`--html`, `--data`, `--serve`, `--state`, `--out`, `--response-schema`, `--port`, `--no-open`, `--timeout`).
2. **Create** `STAGE.md` per convention (purpose, CLI contract, examples).
3. **No** `pack.yaml` edit needed — discovery is directory-scan (confirmed: `astrid/packs/builtin/pack.yaml` is `id/name/version` only).
4. **Verify**: `python3 -m astrid executors list | grep human_review` and `python3 -m astrid executors inspect builtin.human_review --json`.

### Step 2: Implement the HTTP server (`astrid/packs/builtin/human_review/run.py`)
**Scope:** Medium
1. **Adopt** `ThreadingHTTPServer` + `_pick_free_port` pattern from `astrid/packs/builtin/render/run.py`. Bind to `127.0.0.1`.
2. **Custom handler** (do NOT delegate to `SimpleHTTPRequestHandler.translate_path`): single `do_GET`/`do_POST` dispatcher that:
   - Builds an ordered route table at server-init: `[("/data.json", serve_file --data), ("/state.json", serve_file --state if exists else 404), ("<prefix>/", serve_static DIR) for each --serve, ("/", serve --html file-or-dir)]`.
   - Each static handler resolves the path **inside** the configured DIR using `Path.resolve()` + a `is_relative_to` check to block `..` traversal.
   - Range request support implemented directly on the handler (lift the Range parsing from `render/run.py`); used for both `--html` (if a dir) and `--serve` mounts so mp4 seeking works.
3. **Routes:**
   - `GET /` → `--html` (file or dir index)
   - `GET /data.json` → `--data` (read-only)
   - `GET /state.json` → `--state` contents if file exists; HTTP 404 otherwise (**this is the resumability hook for the page to reload partial decisions**)
   - `GET <prefix>/...` for each `--serve PREFIX=DIR`
   - `POST /save` → writes body verbatim to `--state` (atomic: write tmp + rename); 204
   - `POST /submit` → strict `jsonschema.validate` against `--response-schema` if present; on pass write `--out` (atomic) and signal shutdown, return 204; on fail return 400 with `{error, detail}` and **do not** touch `--state` or `--out`
4. **Session token:** auto-generated at startup, printed once to stdout, embedded as `?token=` in opened URL. All POSTs and `GET /state.json` require matching token header (`X-Session-Token`) or query param; mismatch → 403. (Static `--serve` GETs do not require token, so `<video>` tags work without JS-injected headers.)
5. **Browser launch:** `webbrowser.open` unless `--no-open`. Always also print the full URL with token to stdout. **Important:** stdout must remain unbuffered (`flush=True` on prints) so an orchestrator that streams pipes can show the URL before browser launch completes.
6. **Schema validation:** `import jsonschema` directly (already a hard dep). No fallback path.
7. **Timeout:** if `--timeout S` and no submit by deadline, exit nonzero.
8. **Lifecycle:** foreground process, blocks until `/submit` or timeout.

### Step 3: Smoke-test the primitive (`tests/test_human_review.py`)
**Scope:** Small
1. **Test 1 — round-trip:** spawn executor as subprocess with `--no-open`, stub `review.html` and `data.json`. Parse URL+token from stdout. POST `/submit` with valid body → verify `--out` written, server exits 0.
2. **Test 2 — schema rejection:** POST malformed body → expect 400, `--out` not written, `--state` not mutated.
3. **Test 3 — token enforcement:** POST without token → 403.
4. **Test 4 — state resume:** Write a `--state` file, then `GET /state.json` with token → returns the file contents byte-for-byte. (Closes FLAG-002 / issue_hints-1.)
5. **Test 5 — `--serve` prefix routing:** Configure `--serve /clips=<tmpdir>`, GET `/clips/foo.mp4` returns file bytes; GET `/clips/../etc/passwd` returns 403/404.

## Phase 2: Seinfeld vocab-driven schemas + reviewer UI

### Step 4: Vocabulary → schemas generator (`astrid/packs/seinfeld/vocab_compile.py`)
**Scope:** Small
1. **Read** `vocabulary.yaml`, derive `schemas/bucket_judge.json` (from `scenes` + `characters`) and `schemas/caption.json` (from `scenes` + `characters` with per-character outfit enums + `shot_types` + `caption_template`).
2. **Embed** `$comment: "generated from vocabulary.yaml@<hash>"` in each output schema (valid JSON; consumed by humans, ignored by validators).
3. **Expose** `compute_vocab_hash(yaml_text) -> str` — sha256 over canonicalized YAML (strip comments + trailing whitespace before hashing). Deterministic across runs.
4. Inline pre-step inside `dataset_build/run.py`; not promoted to its own executor.

### Step 5: Seinfeld reviewer page (`astrid/packs/seinfeld/dataset_build/review.html`)
**Scope:** Medium
1. **Single file**, inline JS/CSS, ~80–120 LOC. Black background, large video, minimal chrome, progress counter.
2. **Hotkeys:** `Y/Space/→` accept, `N/X` reject, `←` back, `1`–`4` reject reason (last reject), `E` edit-caption overlay, `Enter` submit when complete.
3. **Resume on load:** fetch `/data.json` AND `/state.json` (token from `location.search`). If `/state.json` returns 200, merge into in-memory decisions and **seek the cursor to the first unreviewed clip**. If 404, start at index 0. (Closes FLAG-002 / issue_hints-1.)
4. **Network:** every keypress → `POST /save` (debounced ~250ms, includes token); on completion → `POST /submit` matching the brief's output schema.
5. **Output schema:** `astrid/packs/seinfeld/dataset_build/review.schema.json`, passed to `human_review --response-schema`.

## Phase 3: Content-addressed freshness + orchestration

### Step 6: Sidecar metadata + freshness check (`astrid/packs/seinfeld/dataset_build/run.py`)
**Scope:** Medium
1. **Sidecar path:** `_artifact_meta_path(p) = p.with_suffix(p.suffix + '.meta.json')`. Body: `{"phase": str, "inputs_hash": str, "vocab_version": str|null, "judge_prompt_hash": str|null, "written_at": iso8601}`.
2. **Cheap source-video fingerprint** (closes correctness-2): `_video_fingerprint(path)` = sha256 of `(size_bytes, mtime_ns, first_1_MiB_bytes)`. Used wherever "hash(source video bytes)" appears below — never full read.
3. **Phase-scoped hash inputs** (closes FLAG-001 / correctness-1, correctness-3):
   - `scenes.json`: sha256(`_video_fingerprint(source)` + scene-detection-version constant)
   - `judge.json`: sha256(parent `scenes.json` content hash + scene index + judge schema bytes + judge prompt template + **`judge_prompt_hash`** + vocab_hash). `judge_prompt_hash` includes the reject-reason map but is scoped per-phase — only judge.json sidecars are affected when the reason map changes; caption.json sidecars stay fresh.
   - `caption.json`: sha256(parent `scenes.json` content hash + scene index + caption schema bytes + caption prompt template + vocab_hash). Does **not** include `judge_prompt_hash`.
   - cut clip mp4: sha256(`_video_fingerprint(source)` + scene_start + scene_end + ffmpeg arg string)
4. **`is_fresh(artifact, expected_inputs_hash)`** → True iff sidecar exists with matching `inputs_hash`.
5. **Cost preview:** before stale judge/caption phases, print counts + dollar estimate (hardcoded model-rate constants near the top of `run.py` if no shared price table exists). TTY-only prompt `proceed? [Y/n]`; skipped under `--no-prompt` or non-TTY (auto-proceed with the estimate printed).

### Step 7: Source-diversity cap + reject feedback (`astrid/packs/seinfeld/dataset_build/run.py`)
**Scope:** Medium
1. **Flag** `--max-clips-per-source N` (default 3). Track `clips_per_source_video[vid]` in `state.json`; bucket-fill stops accepting from a video once it hits cap.
2. **`state.json["denylist_source_videos"]`** populated post-review for any clip rejected with reason `watermark` or `wrong_scene` (entire source video excluded next round).
3. **Reject-reason → judge-prompt-extension map:** small static dict (≤6 entries) in `run.py`. Active reasons are sorted, joined, and hashed into `judge_prompt_hash` (Step 6.3) — NOT vocab_hash. Caption sidecars unaffected.
4. **Top-up loop** (closes callers-2): after review, for each bucket below target, re-run bucket-fill with denylist + extensions. After collection, the orchestrator **writes a filtered sub-manifest** to `runs/seinfeld-dataset/topup-round-N.manifest.json` containing only the newly-cut clips, AND writes a fresh empty `topup-round-N.state.json`. The reviewer is invoked with `--data <topup-round-N.manifest.json> --state <topup-round-N.state.json> --out <topup-round-N.final.json>`. Cap at `--top-up-rounds N` (default 2).

### Step 8: Orchestrator wiring + modes + pyenv parameterization (`astrid/packs/seinfeld/dataset_build/run.py`, `orchestrator.yaml`, `STAGE.md`)
**Scope:** Medium
1. **Parameterize pyenv** (closes issue_hints-2): replace hardcoded `PYENV_VERSION=3.11.11` in `_pyenv_env()` with `os.environ.get("ASTRID_DATASET_BUILD_PYTHON", os.environ.get("PYENV_VERSION"))`. If neither set, fall through to current interpreter (don't inject `PYENV_VERSION`). Document in `STAGE.md` that user_c042661f should `export PYENV_VERSION=3.11.11` in their shell (where it already lives), not rely on the script to set it.
2. **Subprocess invocation of `builtin.human_review`** (closes callers-1): use `subprocess.Popen` with `stdout=None, stderr=None` (inherit parent) — NOT `capture_output=True` — so the URL+token print reaches the user's terminal. Wait via `.wait()`; nonzero exit → raise.
3. **Chain** in `main()`: vocab_compile → bucket-fill (cap + denylist + reason extensions) → write provisional manifest → invoke `builtin.human_review` → read decisions → top-up loop (≤N rounds, each with its own scoped manifest + state + final files) → write final `manifest.json` (only `decision == accept` from union of all rounds, with provenance: source_url, search query, judge confidence, reviewer decision, reviewer reason, edited caption).
4. **Modes:** `--review-only` (skip collection, reviewer on existing provisional), `--no-review` (stop at provisional), `--top-up-rounds N`, `--no-prompt`.
5. **Resumability:** mid-collection via `state.json`; mid-review via `--state` partial file + `GET /state.json` (Step 5.3); mid-top-up via per-round state files (each round's files act as the resume marker).
6. **Update** `STAGE.md` and `orchestrator.yaml` to document new flow + flags.
