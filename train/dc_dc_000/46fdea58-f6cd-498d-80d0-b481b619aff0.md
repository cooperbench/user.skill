57	    the baseline doc is accurate" or "confirm behavior is correct" will
58	    be tagged `human` by the audit agent too — the audit uses the same
59	    natural-language reasoning the reviewer uses, so it has the same
60	    error modes. There is no ground-truth capability check.
61	  - (2) relies on a human noticing a ratio in CLI output. In autonomous
62	    loop mode there is no human in that loop. The surface is invisible
63	    exactly when it matters.
64	  - (3) is the only real defense, but it only fires if review
65	    independently decides the criterion *was* machine-checkable — which
66	    requires the reviewer to do exactly the verification the executor
67	    skipped, on a criterion the executor was told to skip. The reviewer
68	    prompt today already shrugs on verification calls (see M0: it failed
69	    rather than waived). There is no reason to believe it will correctly
70	    second-guess a `human` tag.
71	
72	  Net: the gaming path is "author pastes CLAUDE.md bullets, audit
73	  rubber-stamps them as `human`, review honors the tag, plan ships
74	  `approved_with_deferrals`." The proposal makes the M0 problem worse
75	  by giving authors a blessed loophole where before they were at least
76	  forced to write machine-verifiable specs or eat failures.
77	
78	**3. Conflation of "author intent" and "executor capability" — this is
79	the real root.** The proposal frames the problem as three overlapping
80	issues: plan-gate/review-gate conflation, missing authorship feedback,
81	underspecified `waived`. I claim these are three symptoms of one root
82	cause: *megaplan has no model of what the configured executor can
83	actually do*. The author, the audit, the reviewer, the gate — all four
84	subsystems reason about "can this be verified" with natural-language
85	prompts, none has a structural capability check. Option (f) — worker
86	capability profiles with a static criterion linter — is the only path
87	proposed that attacks the root. The proposal defers (f) as "bigger
88	design problem" and ships three scaffolding-layer patches instead. But
89	(a), (b), and (e) are each a weak proxy for the capability check that
90	(f) would make ground-truth. Shipping the proxies first means when (f)
91	lands in v0.18 it has to either deprecate `verified_by` (schema churn
92	for every existing plan) or coexist with it (two sources of truth about
93	the same fact, with conflict-resolution logic nobody wants to write).
94	
95	**4. The audit (b) is the right idea in the wrong place with no teeth.**
96	The proposal runs `audit_criteria` after finalize, before execute, and
97	surfaces results as *advisory* critique flags. Two problems. First,
98	advisory flags at this stage have no resolution gate — finalize has
99	already closed, critique/gate has already run. The flags go into
100	`verifiability.json` and... what? The text says "the author (or gate)
101	can override by explicitly setting `verified_by`" but gate has already
102	happened by then. Second, running it post-finalize is too late: the
103	whole point of an authorship feedback loop (frame 2 in the motivation)
104	is to catch bad specs *before* the container burns a run. The audit
105	should run pre-critique, its results should be first-class critique
106	flags (not a new advisory category), and a `must` criterion flagged as
107	unreachable should be a blocking flag that gate has to resolve. As
108	specified, (b) writes a JSON file that nothing reads.
109	
110	**5. The `waived_unverifiable` soft-block counter has a boundary bug.**
111	The proposal says a `must` criterion marked `waived_unverifiable` is a
112	soft block at `>= 1` by default — effectively a hard block for `must`.
113	Fine. But the existing review logic (prompts/review.py:500-504) already
114	says a `must` that fails means `needs_rework`. If `waived_unverifiable`
115	on `must` triggers `needs_rework` at N=1, it is behaviorally identical
116	to today's `fail`. The new enum buys nothing for `must`. For `should`
117	and `info` the new enum is a rename of today's `waived`. The proposal
118	expands the review schema with two new enum values that collapse to
119	existing behavior in every case except the one it shouldn't: a `must`
120	criterion that the *author* tagged `human` skips the counter entirely
121	per the review rules. So the one case where the soft-block counter
122	could catch gaming (author lies, reviewer detects it) is also the one
123	case where the proposal's review rule says the counter does not fire.
124	This is the seam where the proposal's three parts fail to compose.
125	
126	**6. Mid-plan worker-swap answer is superficially right and operationally
127	broken.** The proposal says "capability is conservatively the
128	intersection across the executing + reviewing workers. The audit runs
129	with the executor's profile; review with its own." But there is no
130	worker profile in v0.17.0 — (f) is deferred. So "runs with the
131	executor's profile" means the audit agent is told in English who the
132	executor is and guesses. In the claude-plans / codex-executes /
133	hermes-reviews topology, the audit has no way to know codex can run
134	shell but cannot observe a browser — unless a human wrote that in the
135	audit prompt. The proposal sidesteps this by making the audit advisory.
136	Advisory audits produce advisory answers. The mid-plan worker-swap case
137	is unsolved in v0.17.0; the text in the edge-cases section reads like
138	a v0.18 promise.
139	
140	**7. Migration claim is subtly wrong.** "Existing plans without
141	`verified_by`: default `container`. Same behavior as today." This is
142	back-compat for *storage* but not for *review semantics* — because the
143	review prompt gains new rules (`waived_unverifiable` soft-block
144	counter, new enum values review must learn). An existing plan with a
145	criterion that the new review rules decide is `waived_unverifiable`
146	will now route to `needs_rework` via the soft-block counter where
147	under v0.16 the same situation would have resulted in `waived` with no
148	rework. Existing in-flight plans will change verdict under v0.17.0. The
149	migration section should either gate the new review rules behind an
150	opt-in flag for legacy plans or acknowledge the behavior change.
151	
152	## Walking M0 through v0.17.0
153	
154	Run the M0 spec (`~/Documents/reigh-megaplan-dev/ideas/M0-render-telemetry.txt`)
155	through the proposed system step by step:
156	
157	1. **Init.** Spec has six bullets under "Gate criteria (for the human
158	   reviewer)". The author does not tag them (the title literally says
159	   "for the human reviewer" but the schema field is absent). All default
160	   to `container`.
161	2. **Plan → critique → gate → finalize.** No change from today; gate
162	   resolves flags normally.
163	3. **Verifiability audit (b).** New worker call. The audit reads six
164	   criteria: tsc clean, npm test baseline, production build grep,
165	   baseline doc with 5×3 interactions, overlay toggle works, warnings
166	   fire on synthetic burst. The audit agent, reasoning in natural
167	   language, will plausibly tag: tsc → container, npm test → container,
168	   build grep → container, baseline doc → **container** (it looks
169	   machine-checkable: "doc exists with ≥ 5×3 entries"), overlay toggle
170	   → human, synthetic-burst warnings → mixed or human. So the audit
171	   catches *some* of the cases — the overlay toggle, maybe the synthetic
172	   burst — but **misses the baseline doc case**, which is exactly the
173	   M0 failure (the doc's contents require browser observation to
174	   author, a fact not obvious from the criterion text). The baseline
175	   doc criterion stays `container`.
176	4. **Execute.** Same as today — codex ships the code, writes the
177	   baseline doc with the numbers it can observe (i.e., from HMR dev
178	   server, the exact thing the spec said not to use).
179	5. **Review.** Reviewer reads the baseline doc. Under v0.17.0, the
180	   `container` tag means the reviewer must pass/fail/waived_unverifiable
181	   it. The reviewer does not know the doc's numbers came from HMR (the
182	   executor did not say), so it either passes (silently wrong) or marks
183	   `waived_unverifiable` on the "5×3 interactions from non-HMR prod
184	   server" criterion (plausible, because reviewer cannot re-run the
185	   dev server). `waived_unverifiable` on a `must` soft-blocks →
186	   `needs_rework`. Same outcome as today.
187	6. **Net.** v0.17.0 as specified does **not** fix M0's primary
188	   failure. It fixes the overlay-toggle criterion (correctly deferred)
189	   and possibly the synthetic-burst one, but the motivating case —
190	   "baseline doc must capture 5×3 interactions from non-HMR prod
191	   server", the criterion that was *semantically self-contradictory* —
192	   is not caught by the audit (too subtle for a natural-language audit
193	   prompt) and is not handled differently by the reviewer (still
194	   `needs_rework`). The proposal's own success-criteria fixture (a plan
195	   with "browser renders without warnings") is a strawman easier than
196	   the real M0 case.
197	
198	The honest conclusion: v0.17.0 would fix the *easy* M0 criteria and
199	miss the *hard* one. The hard one requires the author to have known
200	the spec was malformed and tagged it `human` — which, per the
201	authorship-feedback frame (frame 2), is exactly what the author
202	*cannot* be expected to do.

204	## Alternative proposal: scoped v0.17.0 plus v0.18.0 capability contract
205	
206	Two-release sequence. v0.17.0 ships the *one* lever that most attacks
207	the motivating case, cheaply. v0.18.0 ships the capability contract
208	that makes the lever robust.
209	
210	### v0.17.0: pre-critique verifiability audit, no schema change
211	
212	- Drop (a) entirely. No `verified_by` tag on success_criteria. Zero
213	  schema change to `plan.json`/`finalize.json`.
214	- Drop (e) entirely. Review keeps today's `pass | fail | waived`
215	  enum. No `waived_unverifiable`, no `deferred_human`.
216	- Keep (b), but move it *before* critique and make it *binding*:
217	
218	  ```
219	  megaplan/verifiability.py
220	    audit_criteria(state, criteria) -> list[CriterionAudit]
221	      # called from handlers._run_critique pre-prompt
222	      # each CriterionAudit: {criterion_idx, verdict, rationale}
223	      # verdict ∈ {machine_verifiable, unverifiable_needs_rewrite,
224	      #            unverifiable_human_only}
225	  ```
226	
227	  Results become first-class critique flags (category:
228	  `verifiability`, severity: blocking if `unverifiable_needs_rewrite`,
229	  noted if `unverifiable_human_only`). The existing gate → revise
230	  loop resolves them: the author either rewrites the criterion to be
231	  machine-verifiable or explicitly accepts the tradeoff with rationale
232	  (the strict-gate v0.14 rubber-stamp check applies, so "it's fine"
233	  won't clear it).
234	
235	- No new terminal states, no new CLI commands, no `human_verifications.json`,
236	  no `approved_with_deferrals` label. A plan either has machine-verifiable
237	  criteria (passes review) or it doesn't (fails review, as today).
238	
239	This is ~150 LOC: one new file (`verifiability.py`), one hook in
240	`handlers._run_critique`, one new flag category in `prompts/critique.py`,
241	and tests. It attacks frame 2 (authorship feedback) directly, which is
242	the frame with the largest M0-class payoff. It does not attack frames 1
243	and 3 — but frames 1 and 3 are mostly downstream consequences of frame
244	2 going unaddressed.
245	
246	### v0.18.0: worker capability profile (formerly option f)
247	
248	- Each worker declares a capability blob in `megaplan/workers.py`:
249	  ```python
250	  @dataclass
251	  class WorkerCapabilities:
252	      can_run_shell: bool
253	      can_read_build_output: bool
254	      can_observe_browser: bool
255	      can_observe_runtime_logs: bool
256	      can_run_tests: bool
257	      ...
258	  ```
259	- The verifiability audit from v0.17.0 is upgraded: instead of a
260	  free-form natural-language "is this reachable", it emits a set of
261	  required capabilities per criterion and the harness does a pure-Python
262	  set-subset check against the executor's declared profile. Ground
263	  truth, no prompt-drift.
264	- Review uses the same profile: a criterion whose required caps are
265	  not a subset of the *reviewer's* caps is automatically `waived`
266	  with a concrete "reviewer lacks cap X" evidence string. No new enum.
267	- Mid-plan worker swap becomes principled: the harness computes the
268	  intersection at finalize time and surfaces it in `plan.json`'s
269	  meta.
270	
271	This is the real fix. Deferring it to v0.18 is fine — the v0.17.0
272	audit is small enough that re-plumbing it when v0.18 lands is ~1 day
273	of work, and meanwhile the advisory-only prompt-based audit catches
274	the easy M0-class cases at authorship time, which is the highest-ROI
275	slice.
