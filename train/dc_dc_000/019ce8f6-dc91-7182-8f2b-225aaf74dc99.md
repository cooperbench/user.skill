⏺ OK, now I have a solid understanding of the architecture. Let me think through the
  design decisions MacHatter1 raises.

  ---
  1. What should check receive? (requires= mechanism)

  MacHatter1 suggests a small context object with explicit requires=("dep_graph",) rather
  than the full LangRuntimeContract. This is a reasonable instinct but I think the wrong
  trade-off here.

  The existing pattern is clear: every DetectorPhase.run already receives (Path,
  LangRuntimeContract). The contract is a Protocol — detectors already just use what they
  need and ignore the rest. Adding a second, framework-specific context object creates two
   parallel "what detectors receive" interfaces.

  The requires= idea is good, but it should be metadata on the ScannerRule that controls
  whether the rule runs, not what it receives. The actual check function should just get
  (Path, LangRuntimeContract) like everything else:

  ScannerRule(
      id="use_server_in_client",
      extensions=[".tsx", ".jsx"],
      requires=frozenset({"dep_graph"}),  # skip if lang.dep_graph is None
      check=check_use_server_in_client,   # receives (Path, LangRuntimeContract)
      ...
  )

  The framework_phases() factory would then filter: if lang.dep_graph is None and the rule
   requires dep_graph, skip it and emit a coverage warning. This is exactly how the
  existing system handles capability gaps (see detector_coverage / coverage_warnings on
  the contract).

  Bottom line: Don't invent a new context type. Use the existing contract. Use requires=
  as a gate, not a data-shaping mechanism.

  2. Detection output shape: "present" vs "primary"

  MacHatter1 wants present_frameworks (list with scores) rather than primary_framework
  (single winner). He's right — but with a nuance.

  Real repos do have multiple frameworks (Next.js + Prisma, Django + Celery + DRF). The
  detection layer should return all detected specs. But I'd keep it simpler than "scores":

  @dataclass
  class DetectedFramework:
      spec_id: str           # "nextjs", "django"
      evidence: list[str]    # ["package.json: next@14.2", "next.config.mjs exists", "app/
   dir"]

  No scores. Binary present/absent with evidence for debugging. The reason: framework
  detection is mostly deterministic (does package.json list next?), not probabilistic.
  Scores add complexity without adding signal.

  If you need exclusivity (e.g. "this is Create React App, not Next.js"), handle it at the
   spec level with an excludes= field:

  FrameworkSpec(
      id="create-react-app",
      excludes={"nextjs", "remix"},  # CRA scanners don't apply if Next.js is present
      ...
  )

  This is simpler than priority/exclusivity groups and handles the actual cases that come
  up.

  3. Fixers

  MacHatter1 says start with "obviously safe, local, deterministic" fixes. Agreed, and the
   existing FixerConfig / FixResult pattern already supports this cleanly. A framework
  spec could optionally include fixers:

  ScannerRule(
      id="error_boundary_use_client",
      ...,
      fixer=FixerConfig(
          label="Add 'use client' to error boundaries",
          run=add_use_client_directive,
      ),
  )

  No new types needed — just reuse FixerConfig. The key constraint is that framework
  fixers should be file-local (no cross-file transforms). Anything that requires
  understanding the module graph or moving files stays as a finding.

  4. Tool integrations / slow=True

  MacHatter1 wants next lint to reuse the existing ToolSpec / make_tool_phase() plumbing.
  This is correct. The tool_integration field in your proposed FrameworkSpec should just
  produce a DetectorPhase via make_tool_phase():

  FrameworkSpec(
      id="nextjs",
      ...,
      tools=[
          ToolSpec(
              label="Next.js lint",
              cmd="npx next lint --format json",
              fmt="eslint",
              id="nextjs_lint",
              tier=2,
          ),
      ],
  )

  Then framework_phases() calls make_tool_phase() for each, exactly like generic_lang
  does. The slow field already exists on DetectorPhase and --skip-slow already filters on
  it. No new mechanism needed.

  5. React: library vs framework

  MacHatter1 suggests treating React as "library rules" rather than a framework. I think
  this is a taxonomy distraction that doesn't need to be resolved in the type system.

  The spec layer doesn't actually care whether something is a "framework" or a "library" —
   a FrameworkSpec is just "a set of scanner rules gated on a detection condition." React
  fits that shape perfectly:

  - Detection: react in package.json
  - Scanner rules: context nesting, hook bloat, state sync
  - Extensions: .tsx, .jsx, .ts, .js

  If you want a label for display purposes, add an optional kind: str = "framework" field
  (values: "framework", "library", "platform"). But don't let it affect behavior.

  Summary of recommendations

  ┌────────────────────┬──────────────────────────────────────────────────────────────┐
  │      Question      │                        Recommendation                        │
  ├────────────────────┼──────────────────────────────────────────────────────────────┤
  │ What should check  │ (Path, LangRuntimeContract) — same as every other detector.  │
  │ receive?           │ requires= gates execution, doesn't shape the interface.      │
  ├────────────────────┼──────────────────────────────────────────────────────────────┤
  │ Detection output   │ List of DetectedFramework (id + evidence). No scores. Binary │
  │ shape              │  detection. Use excludes= for mutual exclusion.              │
  ├────────────────────┼──────────────────────────────────────────────────────────────┤
  │ Fixers             │ Reuse FixerConfig. Attach to ScannerRule. File-local only.   │
  ├────────────────────┼──────────────────────────────────────────────────────────────┤
  │ Tool integrations  │ Reuse ToolSpec / make_tool_phase(). No parallel system.      │
  ├────────────────────┼──────────────────────────────────────────────────────────────┤
  │ React library vs   │ Don't distinguish in the type system. Same spec shape.       │
  │ framework          │ Optional kind label for display.                             │
  └────────────────────┴──────────────────────────────────────────────────────────────┘

  The overarching theme: don't invent new mechanisms when the existing ones already work.
  The framework layer should be a thin spec-to-DetectorPhase adapter, exactly like
  tree-sitter is.

Yes, mostly.

MacHatter1’s reply is basically: the overall direction is right. Framework support should be a horizontal, spec-driven layer like tree-sitter or tool specs, not something that forces JS and TS plugins to import each other. From the Next.js work, he thinks the design needs three things: shallow checks that can be shared across `.js/.jsx/.ts/.tsx`, an optional way for specs to derive small bits of framework context such as `app_roots` vs `pages_roots`, and shared helpers for subtle directive parsing so checks like `'use server'` don’t fire on comments or string literals.

On the open questions, his position is: rules should be able to declare required capabilities like `dep_graph`, missing capabilities should show up as coverage/confidence degradation rather than silently disappearing, fixers should start with only obviously safe local edits, and framework-run tools like `next lint` should reuse the existing tool plumbing and `slow` handling. He also prefers detection to return all frameworks that appear to be present, not just one “primary” framework, and he sees React as a good second migration target even if it is treated more like “library rules” than a framework.

My only real nuance is on the rule input shape. I agree with explicit `requires=...`, but I would avoid inventing a second parallel runtime interface unless it is extremely thin. The current architecture already standardizes phases around `DetectorPhase.run(path, lang)` and `LangRuntimeContract` in [types.py](/Users/user_c042661f/Documents/desloppify/desloppify/languages/_framework/base/types.py), and the generic/spec-to-phase adapter already exists in [core.py](/Users/user_c042661f/Documents/desloppify/desloppify/languages/_framework/generic_support/core.py). So I’d keep the new framework layer as a thin adapter over those primitives, not a separate subsystem.
