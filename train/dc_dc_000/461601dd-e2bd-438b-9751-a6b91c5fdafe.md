Yes, worth tackling — but it's a real refactor, not a quick one. Today the pipeline is a hardcoded state machine in `_core/workflow.py:35-81` with named states (`STATE_PLANNED`, `STATE_CRITIQUED`, etc.) and transitions selected by the gate's recommendation. Robustness levels are basically preset variants of that machine. To get arbitrary composition (your "plan → 4 critiques → revise → 2 critiques from perspective B → revise → 2 from C") you need to flip the model: **the workflow is data, the state machine is just a cursor over it.**

The concrete complexities, ranked by how much they bite:

1. **Step identity vs. workflow position.** Right now `revise` is "the thing that runs when state=CRITIQUED + gate=ITERATE". In your world `revise` runs N times in N different positions. Steps need stable IDs (`critique`, `revise`) plus per-invocation parameters (`perspective: "security"`, `checks: [...]`, `iteration: 2`). State becomes "step index + run id," not a named enum.

2. **Critique perspectives don't exist yet.** `parallel_critique.py` already fans out checks in parallel, but "perspective" isn't a parameter — the checks are derived from audits/forms config + robustness level. To do "2 critiques from a different perspective" you need perspective as a first-class input to the critique step (prompt variant, check selector, or persona). This is probably the single most valuable primitive to add and the easiest one in isolation.

3. **Gate is fused to critique.** Today `critique → gate → (revise|proceed|tiebreaker)` is one indivisible loop. If you want critiques without gating (just "collect 2 more opinions then revise"), or gating over merged outputs of multiple critique rounds, gate needs to become an optional, parameterized step that takes "which critique artifacts to consider" as input.

4. **Artifact addressing.** Steps currently read sibling files by convention (`gate.py` knows where `critique_vN.json` lives). If a workflow has 8 critique runs, downstream steps need an explicit manifest — "critiques [3,4,5] feed this revise" — not implicit "load latest." A simple run-keyed artifact dir + a `manifest.json` mapping step_id → outputs solves this.

5. **Auto-driver loop.** `auto.py` reads state and calls "next step." It needs to read the workflow definition + cursor instead. Small change once 1–4 are in place.

6. **Profiles and robustness become recipes.** `tiny`/`light`/`standard`/`robust` stop being branches inside `workflow.py` and become saved workflow YAML/JSON files. This is mostly mechanical and actually simplifies things.

## The shape of the refactor

Three layers, introduced in order, each leaving the old flow intact.

**Layer A — Step primitives.** Wrap each existing handler in a thin `Step` interface: `id`, `kind` (`plan`/`critique`/`revise`/`gate`/`finalize`/`execute`/`review`/`tiebreaker`), `params` (perspective, check set, agent override), `inputs` (which prior artifacts to read), `outputs` (what files it writes). Steps stay pure-ish: state + params + inputs → artifacts + state delta. The handlers in `megaplan/handlers/*` already mostly fit this shape — this phase is mechanical extraction.

**Layer B — Workflow as data.** A workflow is an ordered list of step instances with conditional edges. YAML/JSON in `megaplan/data/workflows/`. Crucially, conditional edges are needed — not just sequences — because gate routes (`ITERATE`/`PROCEED`/`TIEBREAKER`/`ESCALATE`) and review's rework loop have to be expressible. Format roughly: each step declares `on_result: {iterate: <step_id>, proceed: <step_id>}`. Loops are just back-edges with a bounded counter.

**Layer C — Workflow runner / cursor.** Replaces `infer_next_steps()` in `_core/workflow.py:250`. Tracks `(workflow_id, step_index, run_id)` in `state.json`. Old `current_state` field stays populated as a derived view ("kind of last step") so legacy reporting and any external readers don't break.

## Migration sequence — keeping flow active at every step

**Phase 0: extract Step interfaces, no behavior change.** Each handler gets a `Step` wrapper. CLI commands still call handlers directly. Pure refactor; existing tests are the regression suite. Reversible.

**Phase 1: ship the most interesting primitive — parameterized critique.** Add `perspective` and `run_index` to the critique step. Existing callers pass defaults (`perspective=None`, `run_index=0`). Artifact filenames suffix `run_index` only when `>0`, so old plans/tests load unchanged. Expose `--perspective` on `megaplan critique`. This alone unlocks your "2 more critiques from a different perspective" flow without touching the state machine — you just call `megaplan critique --perspective=security` repeatedly.

**Phase 2: introduce the workflow runner alongside the hardcoded machine.** Add a `--workflow <path>` flag. If absent, use the existing `_core/workflow.py` table (untouched). If present, drive from the YAML. Express `standard` robustness as `data/workflows/standard.yaml` and run the existing test suite against both code paths to confirm parity. This is the highest-risk phase — most of the work is in correctly translating gate/tiebreaker/review-rework conditional edges. Keep both paths alive until parity is proven.

**Phase 3: migrate robustness presets to workflow files.** `tiny.yaml`, `light.yaml`, `standard.yaml`, `robust.yaml`, `superrobust.yaml`. `--robustness=light` becomes "load `light.yaml`." Old code path removed only after all five pass parity.

**Phase 4: delete the hardcoded WORKFLOW table.** Everything now routes through the runner. `_core/workflow.py` shrinks to a YAML loader.

## Things that need careful handling

- **Conditional routing.** Gate's recommendation, tiebreaker's outcome, and review's rework loop all branch the flow. Workflow format must support `on_result: {key: step_id}`, not just sequential `next`.
- **Resume semantics with mixed CLI invocations.** A user running `megaplan critique` mid-workflow expects "advance the cursor if next step is a critique; otherwise tell me what to run." Resolution: cursor wins when it exists; fall back to old state-name inference for plans created before the runner shipped.
- **Artifact addressing.** Steps currently read sibling files by convention (`gate.py` knows where `critique_vN.json` is). With repeated critique runs and arbitrary ordering, we need a `manifest.json` mapping `step_id → output_paths` so `gate` can be told "consider critiques [3,4,5]" explicitly. This can land in Phase 0 as a write-only manifest (old readers still use convention) and become the read source in Phase 2.
- **Status display.** `megaplan status` currently prints named states. Add a workflow-aware view: "step 4 of 9: critique (perspective=security, run 2)." Old format stays as fallback for plans without a cursor.
- **Auto-driver.** `megaplan/auto.py`'s loop reads `current_state` and calls the next handler. Becomes "ask the runner for next step." Trivial change once Phase 2 lands.
