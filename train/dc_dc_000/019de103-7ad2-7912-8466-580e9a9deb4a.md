        # Implementation Plan: Lock Down Sensitive OOB Exposure

## Overview
The repository already has a focused OOB safety layer, but the audit finding points at two gaps:

- The delivery/read-tool checker in `app/services/oob_check.py:106` only loads OOB rows where `owner_id == recipient_id`, so final outbound checks do not currently protect current-user-owned OOB entries when sending to the partner.
- Several non-checker surfaces expose `sensitive_core` directly: hot context rendering in `app/services/hot_context.py:294`, the `get_oob` read tool in `app/services/tools/read_tools.py:272`, the `OOBRow` schema in `tool_schemas.py:317`, and the admin OOB table in `app/routers/admin.py:198`.

The simplest fix is not a storage migration. Keep raw `sensitive_core` available only where it is necessary for safety decisions or owner management writes, and return/render a safe representation everywhere a topic/count/shareable view is enough.

## Main Phase

### Step 1: Tighten checker scope without broad schema churn (`app/services/oob_check.py`, `app/services/hooks.py`, `app/services/tools/read_tools.py`, `tool_schemas.py`)
**Scope:** Medium
1. **Replace** `_active_oob_entries(pool, recipient_id)` with a helper that can load active OOB for one owner or a set of owner IDs, preserving raw `sensitive_core` only inside checker/countersummary internals.
2. **Extend** `check_oob_with_policy` to accept an optional `protected_owner_ids: list[UUID] | None`. Default to `[recipient_id]` for compatibility, but include all supplied owners in the checker payload.
3. **Update** `CheckOOBInput` to include optional `protected_owner_ids` with a description that final delivery checks should pass both dyad users when available.
4. **Wire** the read-tool `check_oob` wrapper to pass `args.protected_owner_ids` through.
5. **Update** comments that currently say recipient-only, especially `tool_schemas.py:352`, so future readers understand the checker may inspect both recipient-owned and sender/partner-owned OOB entries.

### Step 2: Make final outbound checks dyad-aware (`app/services/agentic.py`, `app/services/messaging.py`)
**Scope:** Medium
1. **Thread** the partner/current-user owner set into the final pre-send check in `app/services/agentic.py:241` and `_resolve_outbound_text`, using the `TurnContext` users already available in `_run_agentic`.
2. **Update** `send_outbound` in `app/services/messaging.py:74` to accept optional `protected_owner_ids`; when omitted, keep current recipient-only behavior for non-agentic callers.
3. **Pass** both `[user.id, partner.id]` from the agentic final-send path so the last safety gate protects both current-user and partner-owned active OOB before any provider send.
4. **Keep** hard/firm failure semantics unchanged: if any included hard/firm OOB is present and the checker fails, the outbound blocks/withholds; soft-only failures still fail open with warning.

### Step 3: Reduce direct `sensitive_core` exposure in hot context and read tools (`app/services/hot_context.py`, `app/services/tools/read_tools.py`, `app/services/tools/common.py`, `tool_schemas.py`)
**Scope:** Medium
1. **Change** hot context rendering so `## Active OOB` lists only `id`, clipped owner id, severity, and safe shareable/context/topic text. Do not render `core=` in `app/services/hot_context.py:294`.
2. **Preserve** `sensitive_core` in the in-memory `HotContext.active_oob` rows only if downstream code still needs it; otherwise remove it from `build_hot_context` selection and row dict. Prefer removing it if tests confirm the rendered prompt is the only consumer.
3. **Replace** `OOBRow.sensitive_core` with a safe field such as `safe_summary` or `protected_summary`, plus `shareable_context`, `severity`, `status`, and dates.
4. **Update** `get_oob` in `app/services/tools/read_tools.py:260` to select only safe fields or derive `safe_summary` from `shareable_context`/severity. The read tool should no longer return raw `sensitive_core` to the LLM.
5. **Leave** `AddOOBInput` and `UpdateOOBInput` unchanged because write tools need to create/update the protected core.

### Step 4: Redact admin OOB list by default (`app/routers/admin.py`, `tests/test_admin.py`)
**Scope:** Small
1. **Update** `/admin/oob` at `app/routers/admin.py:196` to omit raw `sensitive_core` from the default table and show a safe column instead, such as `shareable_context` or `[protected]` when no shareable text exists.
2. **Do not** add a raw reveal endpoint unless a product decision explicitly requires one; the audit scope asks to reduce exposure where safe representation is sufficient.
3. **Add** an admin test proving the OOB page renders, escapes content, includes safe context/severity, and does not include a seeded raw sensitive core string.

### Step 5: Add focused leakage and behavior tests (`tests/test_oob_check.py`, `tests/test_agentic.py`, `tests/test_hot_context.py`, `tests/test_tools.py`, `tests/test_admin.py`)
**Scope:** Medium
1. **Add** an OOB checker unit test where the recipient has no OOB but the protected owner set includes the sender/current user; assert the checker call includes that current-user-owned entry and can return `block` or `rewrite`.
2. **Add** an agentic final-send test proving a partner-owned and current-user-owned OOB row are both considered before send, and a leak from either owner prevents provider delivery or forces a safe rewrite.
3. **Update** existing hot context tests that currently assert raw OOB remains in the rendered prompt; the new assertion should be that OOB metadata remains while raw `sensitive_core` is absent.
4. **Update** read-tool tests so `get_oob` returns safe representation and does not serialize raw `sensitive_core`.
5. **Retain** existing hard/firm behavior tests in `tests/test_oob_check.py:84` and soft fail-open tests so the safety policy does not regress while scope expands.

## Execution Order

2. Wire `agentic.py` and `messaging.py` after the checker supports multiple protected owners.

4. Update tests last where expectations intentionally change from raw-core visibility to safe representation.
