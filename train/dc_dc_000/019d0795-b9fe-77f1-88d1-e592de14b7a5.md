**Findings**

- High: continuation capability is modeled at the model level, but at least one strategy is really execution-mode-specific. In the plan, WAN advertises `guide_overlap_masked` as a general supported strategy and the toggle becomes visible whenever a model has any continuation strategy ([squishy-finding-lamport.md:42](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:42), [squishy-finding-lamport.md:210](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:210)). Current UI intentionally only shows it for WAN+`vace` ([MotionControlBasicTab.tsx:160](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/MotionControlBasicTab.tsx:160)). If you flatten that to `supportedContinuationStrategies.length > 0`, you can produce invalid combinations like `model_type: 'i2v'` plus `guide_overlap_masked`. I would move continuation support to a `(model, executionMode)` matrix or make it a resolver predicate, not a raw model flag.

- High: the doc says “standardize data between client and worker,” but it still leaves two separate sources of truth. The frontend gets `ModelSpec`, while the worker separately derives `GenerationPolicy` and hardcodes strategy behavior ([squishy-finding-lamport.md:15](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:15), [squishy-finding-lamport.md:234](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:234)). That removes `isLtxModel()` sprawl, but not drift. If this is meant to scale to “more models with different continuation types,” you want a shared transport-level schema or manifest for `model id -> execution modes -> continuation modes -> guidance modes`, even if each repo projects that into its own runtime types.

- High: `ContinuationConfig` is marked canonical, but the contract-first read path is not updated in the plan. Current task readback goes through `TravelBetweenImagesReadContract` and snapshot readers, which do not contain any continuation field today ([taskFamilyContracts.ts:34](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/core/taskFamilyContracts.ts:34), [taskDataService.ts:98](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/taskDataService.ts:98)). The plan only mentions top-level payload/task rehydration ([squishy-finding-lamport.md:142](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:142), [squishy-finding-lamport.md:224](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:224)). If `continuation_config` is truly canonical, it also needs to flow through `read_contract`, the contract readers, and likely individual segment payload state if segment regen is expected to remain correct.

- Medium: the requested-vs-effective boundary is still muddy, which will hurt UX. The doc calls `smoothContinuations` and `generationTypeMode` “intent” ([squishy-finding-lamport.md:69](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:69)), but current code already auto-mutates `generationTypeMode` from structure guidance ([useStructureVideoHandlers.ts:52](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/video/useStructureVideoHandlers.ts:52), [useVideoTravelSettingsHandlers.ts:321](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/hooks/settings/useVideoTravelSettingsHandlers.ts:321)) and clamps frames when SC is enabled ([useVideoTravelSettingsHandlers.ts:213](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/hooks/settings/useVideoTravelSettingsHandlers.ts:213)). I’d explicitly split `requestedSmoothContinuations` from `effectiveContinuation`, and do the same for execution mode if you want the UI to stay understandable when models/guidance force constraints.

- Medium: backward-compatible rehydration is underspecified. The doc says “set `smoothContinuations = true` if `continuation_config` is present” ([squishy-finding-lamport.md:224](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:224)), but old tasks with chained segments will not have that field. If you want old frontend/new worker and old task/new frontend stories to stay intact, rehydration should also infer continuation from legacy `chain_segments` plus overlap, not just the new object.

- Medium: there is internal drift in the proposal that suggests the abstraction boundary is not fully settled. `ModelSpec` as written has no `defaultTravelMode` ([squishy-finding-lamport.md:18](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:18)), but later the plan uses `spec.defaultTravelMode` / `getModelSpec(m).defaultTravelMode` ([squishy-finding-lamport.md:198](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:198), [squishy-finding-lamport.md:348](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:348)). The resolver signature also omits guidance inputs, while the example call passes extra runtime context ([squishy-finding-lamport.md:101](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:101), [squishy-finding-lamport.md:159](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md:159)). I’d tighten this before coding.

**Recommended Shape**

- Keep the three-layer idea, but make layer boundaries stricter:
  - Shared transport contract: `ExecutionMode`, `ContinuationStrategy`, `ContinuationConfig`, versioned and consumed by both repos.
  - Client catalog: labels, defaults, UI affordances, resolution tiers, LoRA family.
  - Resolver: `intent + model + guidance presence/kind -> effective execution policy`.
  - Worker policy parser: consume only transport fields, not client-only flags.

- Replace `supportedContinuationStrategies: ContinuationStrategy[]` with something closer to:
  - `supportedExecutionModes`
  - `continuationSupportByExecutionMode`
  - `guidanceSupportByExecutionMode`
  That avoids the WAN `i2v`/`vace` ambiguity and will scale better when a future model supports multiple continuation mechanisms.

- Make `continuation_config` canonical everywhere, not just on write:
  - task payload
  - family read contract
  - task snapshot readers
  - apply-settings rehydration
  - segment regeneration state

The good parts are the direction toward a resolver, the decision to stop deriving payload fields from `isLtxModel()`, and the frame-quantization check. Those are the parts I would keep. The main thing I would change is making execution-mode compatibility and cross-repo source-of-truth explicit before implementation.
