## Main Phase

### Step 1: Confirm `cm-cli` invocation and exit semantics
**Scope:** Small
1. **Decide invocation form.** The vendored docs (`vendor/ComfyUI/docs/custom_nodes.md:199`) describe `cm-cli.py` as a script *inside the cloned ComfyUI-Manager dir*, while comfy-cli shells out to it. The pip-installed `comfyui_manager>=4.1,<5` package is what `runpod_corpus_matrix.py:91` puts on the runtime, but its console-script name is not documented in this repo. I will probe for cm-cli in this order at runtime, all using `shutil.which` against the discovered Python:
   1. `<sys.executable_dir>/cm-cli` (entry-point installed alongside the embedded venv's python).
   2. `shutil.which("cm-cli")` (system PATH).
   3. Module form: `[<python>, "-m", "comfyui_manager.cm_cli"]` if `python -c "import comfyui_manager.cm_cli"` succeeds.
   If none resolve, fall back to clone+pip. **Question:** the precise console-script name from `comfyui_manager>=4.1,<5` should be confirmed against the live package on a runpod box; the plan documents `cm-cli` and provides the module fallback so we still work if the binary name differs.
2. **Decide install verb.** Per brief: `cm-cli install <name>`. We will not pin a version (cm-cli will resolve latest), then immediately read the resulting `install_dir`'s git HEAD to populate `InstallResult.git_commit_sha` and the lockfile pin. This preserves the existing semantics: lockfile gets a concrete SHA after install.
3. **Output.** Capture stdout/stderr, surface them via `InstallResult.error` only on non-zero exit. No log-scraping for status.
