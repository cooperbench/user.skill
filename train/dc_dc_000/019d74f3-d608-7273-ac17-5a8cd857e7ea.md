> DEVELOPER

Does thsi npoint ot a deeper strutural issue?

> AGENT

Yes, a bit.

This specific bug was a local UI mistake, but it exposed a structural fault line in the video editor:

- Shot groups are stored separately from clips as `pinnedShotGroups`.
- The timeline only renders a shot group if its `clipIds` still map to live clips.
- The UI was allowed to mutate those two layers in separate commits.

That means the system can enter valid-by-types but invalid-by-behavior intermediate states: “group exists, clips don’t” or the reverse. Undo then becomes fragile because history replays those partial states exactly.

So the deeper issue is not “React stale state” so much as weak transactional boundaries around multi-part edits.

I would frame it like this:

- History itself is basically fine.
- The data model is a little split-brain: `rows/meta` and `pinnedShotGroups` must stay in sync.
- The editor currently relies on callers to remember when an operation must be atomic.

That’s why this happened.

The fix I made closes this one path, but the broader improvement would be to move shot-group operations behind a single command/mutation layer so callers cannot accidentally do two-step edits. In practice that means things like “delete shot”, “switch to final video”, “switch back to images”, “deconstruct shot”, and maybe some drag operations should all go through dedicated helpers instead of ad hoc `applyEdit(...)` sequences.

So: yes, it points to a real structural issue, but not necessarily a rewrite-level one. It’s more “the editor needs stricter atomic mutation APIs for shot-group operations.”

> AGENT

The right abstraction is a small domain command layer for shot-group operations, not more ad hoc `applyEdit(...)` calls.

Right now [`applyEdit`](\/Users\/user_c042661f\/Documents\/reigh-workspace\/reigh-app\/src\/tools\/video-editor\/hooks\/useTimelineCommit.ts#L188) is a low-level state primitive. - `rows`
- `meta`
- `clipOrder`
- `pinnedShotGroups`

So the correct abstraction is:

- One user intent
- One domain operation
- One atomic commit

Concretely, I’d recommend a `shotGroupOperations` or `timelineCommands` module with functions like:

- `deleteShotGroup(...)`
- `deconstructShotGroup(...)`
- `switchShotGroupToFinalVideo(...)`
- `switchShotGroupToImages(...)`
- `moveShotGroup(...)`
- `syncShotGroupWithShotImages(...)`

Each command should:

- accept `currentData`
- enforce invariants
- return exactly one mutation payload for `applyEdit`
- decide whether it is `semantic`, transaction-scoped, etc.

The key invariant should be explicit:

- if a clip id is listed in a pinned shot group, that clip must exist
- destructive shot operations must update clips and group membership in the same commit
- no caller should manually “delete clips, then unpin” as two separate actions

- `applyEdit` remains the engine
- command helpers become the public API for anything shot-related

- more effect-based reconciliation
