Does thsi npoint ot a deeper strutural issue?

> AGENT

Yes, a bit. This specific bug was a local UI mistake, but it exposed a structural fault line in the video editor: - Shot groups are stored separately from clips as `pinnedShotGroups`. - The timeline only renders a shot group if its `clipIds` still map to live clips. - The UI was allowed to mutate those two layers in separate commits. That means the system can enter valid-by-types but invalid-by-behavior intermediate states: “group exists, clips don’t” or the reverse. Undo then becomes fragile because history replays those partial states exactly. So the deeper issue is not “React stale state” so much as weak transactional boundaries around multi-part edits. I would frame it like this: - History itself is basically fine. - The data model is a little split-brain: `rows/meta` and `pinnedShotGroups` must stay in sync. - The editor currently relies on callers to remember when an operation must be atomic. That’s why this happened. The fix I made closes this one path, but the broader improvement would be to move shot-group operations behind a single command/mutation layer so callers cannot accidentally do two-step edits. In practice that means things like “delete shot”, “switch to final video”, “switch back to images”, “deconstruct shot”, and maybe some drag operations should all go through dedicated helpers instead of ad hoc `applyEdit(...)` sequences. So: yes, it points to a real structural issue, but not necessarily a rewrite-level one. It’s more “the editor needs stricter atomic mutation APIs for shot-group operations.”
