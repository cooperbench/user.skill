# Implementation Plan: Real-Time Event Pipeline

## Intent Summary
Build a streaming event processing service that consumes from Kafka, transforms events using declarative rules stored in DynamoDB, and fans out to S3, Elasticsearch, and webhook sinks — with at-least-once delivery (idempotent writes), backpressure handling, and a dead-letter queue.

---

## Phase 0: Project Skeleton & Local Dev Environment
**Goal:** Runnable project with local dependencies, zero business logic.

1. Initialize a Python project (or Go — see assumptions) with `pyproject.toml` / `go.mod`.
2. Create a `docker-compose.yml` with: Kafka (+ Zookeeper or KRaft), DynamoDB Local, Elasticsearch, LocalStack S3, and a simple webhook echo server (e.g., `httpbin`).
3. Write a smoke-test script that produces 10 events to Kafka, confirms they arrive on the topic.
4. Add CI config (GitHub Actions) that boots the Docker Compose stack and runs the smoke test.

**Validation:** `docker compose up && ./smoke_test.sh` passes green.

---

## Phase 1: Kafka Consumer with Partition-Level Parallelism
**Goal:** Consume events reliably with manual offset management.

1. Implement a consumer group wrapper using `confluent-kafka-python` (or equivalent).
2. Support consuming from multiple topics, configured via YAML/env.
3. Use manual offset commits — only commit after downstream processing confirms.
4. Add per-partition consumer metrics: lag, throughput, last-committed offset.
5. Write integration test: produce N events, consume all N, verify offset commits.

**Validation:** Consumer drains a topic of 10k events with no duplicates or drops (verified by event ID set comparison).

---

## Phase 2: Transformation Rule Engine
**Goal:** Load rules from DynamoDB, apply them to events.

1. Define the rule schema: field mappings, filters (include/exclude by field value), static enrichment (add fixed fields). Store as versioned JSON in DynamoDB with a `version` field and `updated_at` timestamp.
2. Build a `RuleEngine` class:
   - `load_rules(topic: str) -> list[Rule]` — fetches from DynamoDB.
   - `apply(event: dict, rules: list[Rule]) -> dict | None` — returns transformed event or `None` if filtered out.
3. Implement periodic hot-reload: a background thread polls DynamoDB every 30s (configurable), swaps the rule set atomically.
4. Unit tests with mocked DynamoDB (moto): rule CRUD, versioning, filter logic, field mapping.
5. Integration test: insert rules into DynamoDB Local, produce events, verify transformed output matches expectations.

**Validation:** Rule changes in DynamoDB are reflected in processing within the reload interval. Filtered events produce no downstream output.

---

## Phase 3: Sink Abstraction & S3 Sink
**Goal:** Define the sink interface; implement the first concrete sink.

1. Define a `Sink` protocol/ABC:
   ```
   async def write(self, batch: list[Event]) -> WriteResult
   async def flush(self) -> None
   async def close(self) -> None
   ```
2. Implement `S3Sink`:
   - Buffers events in memory up to a size/time threshold (e.g., 5MB or 60s).
   - Writes batches as newline-delimited JSON to S3, partitioned by date/hour.
   - Idempotency: include a deterministic batch ID in the S3 key (hash of event IDs in batch) — re-uploading the same batch overwrites the same key.
3. Integration test against LocalStack S3.

**Validation:** 10k events end up in S3 with correct partitioning; re-running the same batch does not create duplicate objects.

---

## Phase 4: Elasticsearch Sink
**Goal:** Bulk-index events into Elasticsearch.

1. Implement `ElasticsearchSink`:
   - Uses the `_bulk` API for batch writes.
   - Idempotency: use event ID as the Elasticsearch document `_id` — upsert semantics.
   - Configurable index pattern (e.g., `events-YYYY.MM.DD`).
2. Handle partial bulk failures: retry failed items, send to DLQ after N retries.
3. Integration test against Docker Elasticsearch.

**Validation:** 10k events indexed; re-indexing the same events produces no duplicates (document count unchanged).

---

## Phase 5: Webhook Sink
**Goal:** Async HTTP delivery with retries and circuit breaking.

1. Implement `WebhookSink`:
   - Async HTTP POST using `aiohttp` / `httpx`.
   - Exponential backoff retries (configurable: max retries, base delay, max delay).
   - Circuit breaker: after N consecutive failures, open circuit for M seconds, then half-open probe.
   - Timeout per request (configurable, default 10s).
2. Events that exhaust retries go to the DLQ.
3. Test with the echo server from Phase 0; test failure modes by toggling the echo server on/off.

**Validation:** Events delivered to healthy endpoint; events routed to DLQ when endpoint is down beyond retry budget; circuit breaker prevents flood of requests to a down endpoint.

---

## Phase 6: Fan-Out, Backpressure & DLQ
**Goal:** Wire everything together with backpressure and dead-lettering.

1. Implement `FanOutDispatcher`:
   - For each consumed event: transform → dispatch to all configured sinks concurrently.
   - Each sink has a bounded async queue (configurable depth, e.g., 10k events).
   - When any sink queue reaches high-water mark, pause Kafka consumption (`consumer.pause()`).
   - Resume when all queues drop below low-water mark.
2. Implement `DeadLetterQueue`:
   - A dedicated Kafka topic (e.g., `pipeline.dlq`).
   - Stores the original event, the failure reason, the sink that failed, and a timestamp.
   - Optionally: a simple CLI tool to inspect/replay DLQ events.
3. Offset management: only commit offsets for events that have been acknowledged by ALL sinks (or routed to DLQ).
4. Integration test: produce 10k events with one sink artificially slow → verify backpressure pauses consumption, all events eventually delivered, no data loss.

**Validation:** Zero event loss under backpressure. DLQ contains exactly the events that failed all retries. Offsets are not committed ahead of delivery.

---

## Phase 7: Configuration, Observability & Operability
**Goal:** Production-ready configuration and monitoring.

1. YAML-based configuration file:
   - Kafka: brokers, topics, consumer group, auth.
   - DynamoDB: table name, region, endpoint override.
   - Sinks: enable/disable each, per-sink config (S3 bucket, ES index pattern, webhook URLs).
   - Backpressure: queue depths, high/low watermarks.
   - DLQ: topic name, retry limits.
2. Prometheus metrics:
   - `events_consumed_total`, `events_transformed_total`, `events_filtered_total`
   - Per-sink: `events_written_total`, `events_failed_total`, `write_latency_seconds`
   - `dlq_events_total`
   - `consumer_lag` (per partition)
   - `backpressure_paused_seconds_total`
3. Structured JSON logging (with correlation IDs / event IDs).
4. Health check endpoint (HTTP `/health`) reporting consumer connectivity, sink status, queue depths.
5. Graceful shutdown: flush all sink buffers, commit final offsets, then exit.

**Validation:** Prometheus `/metrics` endpoint exposes all listed metrics. Health check returns degraded status when a sink is unreachable. Graceful shutdown loses zero in-flight events.

---

## Phase 8: End-to-End Integration Test Suite
**Goal:** Confidence that the full pipeline works under realistic conditions.

1. Full Docker Compose stack + pipeline binary.
2. Test scenarios:
   - Happy path: 100k events, all sinks healthy → all events in S3, ES, and webhook log.
   - Transformation filtering: 50% of events filtered → correct counts downstream.
   - Sink failure: webhook down for 30s → backpressure kicks in, events eventually delivered or DLQ'd.
   - Rule hot-reload: change rules mid-stream → new rules apply within reload interval.
   - Idempotency: restart pipeline mid-batch → no duplicate events in sinks.
3. Performance baseline: measure throughput (events/sec) and p99 latency on a known hardware profile.

**Validation:** All test scenarios pass. Throughput baseline documented.

## Open Questions

1. **Language choice:** Python (faster to prototype, weaker concurrency) vs. Go (better concurrency primitives, stronger for this workload) vs. Java/Kotlin (native Kafka client, richest exactly-once support)? Plan assumes Python but Go may be more appropriate.
2. **Deployment target:** Bare containers? Kubernetes with auto-scaling? This affects how partition rebalancing and horizontal scaling are handled.
3. **Authentication:** Does Kafka require SASL/SSL? Does the webhook sink need auth headers (Bearer tokens, HMAC signatures)?
4. **Multi-tenancy:** Is this a single pipeline instance per use case, or a shared platform where multiple teams define their own rules and sinks?
5. **Event schema:** Are events schema'd (Avro/Protobuf with a schema registry) or free-form JSON? Schema enforcement affects the transformation engine design.
6. **DLQ replay:** Is a CLI tool sufficient, or do you need an automated retry/replay mechanism?
7. **Ordering guarantees:** Must events maintain per-partition ordering through to sinks, or is unordered fan-out acceptable?
