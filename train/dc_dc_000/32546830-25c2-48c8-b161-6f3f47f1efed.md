A `pack.yaml` gives you (a) a clean discovery anchor — find a `pack.yaml`, walk siblings for `*.yaml` manifests — (b) a home for pack-level metadata (name, version, author, `allow_generative_visuals`, dependencies on other packs), and (c) lets `_builtin` be a real pack with the same code path as user packs, eating its own dog food. **One thing I'd *not* change:** filename-as-kind (`executor.yaml` / `orchestrator.yaml` / `element.yaml`). You could collapse to a single `artagent.yaml` with `kind:` inside — more uniform — but you'd lose the "glob tells you what it is, no parsing required" property, and authors lose the at-a-glance read. Filename-as-kind is the cheaper signal and matches the convention you already have. So the truly clean version is: `runtime/` for framework, `packs/<name>/pack.yaml` as the anchor, and manifest filename keeps signalling kind. Beyond that I think you're into bikeshedding.
