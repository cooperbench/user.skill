> AGENT

**Strongest Approval**

The plan is directionally right: making packs real, manifest-owned, schema-validated, and Git-backed is the correct long-term product shape. The strongest architectural choice is sequencing contract and validation before install/runtime. That prevents Astrid from accidentally becoming an arbitrary “run code from repos” plugin loader with undocumented behavior. The pack abstraction also cleanly supports a future ecosystem: discoverability, docs, agent legibility, reproducible examples, and eventual registry/governance all need the manifest boundary this plan establishes.

**Biggest Concerns Ranked**

1. **Sandboxing is too late.**  
   Sprint 8 makes security feel optional, but Git-installed packs are executable code with declared secrets. Even if full container sandboxing waits, the security model must be designed before Sprint 3 install and Sprint 4 runtime. Otherwise install UX, dependency handling, secret passing, filesystem assumptions, and runtime APIs will harden around unsafe defaults.

2. **Versioning is under-specified.**  
   `version` and `astrid_version` exist, but the plan does not define lockfiles, pinned Git refs, update semantics, compatibility enforcement, migration policy, or what happens when a pack changes manifests between installs. Without this, reproducibility and support will degrade quickly.

3. **Governance and trust are missing from the product model.**  
   The plan treats all GitHub repos as equivalent. Astrid needs a trust model: local/dev packs, installed third-party packs, blessed/curated packs, and built-ins should not have the same affordances. This affects warnings, secrets, update prompts, namespace collisions, and agent recommendations.

4. **Dependency handling cannot remain purely informational for long.**  
   Declaring Python/npm/system dependencies without an execution environment or install strategy will create “validated but unrunnable” packs. That is acceptable for Sprint 1, but by install/runtime the plan needs a clear stance: isolated venv per pack, project env, user-managed only, or containerized.

5. **The agent index arrives too late.**  
   Agent legibility is core to the product, not polish. If Sprint 3 makes installed packs visible in list/search/inspect before the agent-facing summary contract exists, discovery metadata may ossify around human CLI needs instead of agent decision-making.

6. **Migration burden is acknowledged but not owned.**  
   Existing built-ins are “legacy-compatible” early, but there is no dedicated compatibility matrix or deprecation plan. The risk is a permanent dual world: built-ins with historical quirks and external packs with stricter rules.

**Concrete Changes To The Plan**

1. Add a **Sprint 0 architecture decision pass** before Sprint 1:
   - trust tiers: built-in, local workspace, installed third-party, curated
   - security posture for install/run
   - version/update semantics
   - dependency execution model
   - migration/deprecation policy

2. Move “sandbox strategy” from optional Sprint 8 into an early **Security Model** deliverable. Full sandbox implementation can stay later, but install/runtime must be designed around future isolation.

3. Require installs to pin a Git commit and write an install record, e.g. `~/.astrid/packs.lock`, containing pack id, source URL/path, resolved commit, pack version, Astrid compatibility, install time, and validation schema version.

4. Enforce `astrid_version` compatibility in v1. Do not merely warn. A plugin ecosystem with soft compatibility checks becomes unmaintainable.

5. Decide now that `provides` is generated from declared roots, not manually authored. Manual inventories will drift and create governance ambiguity.

6. Split dependency declarations into:
   - `requires`: validation/runtime blockers
   - `suggests`: optional capabilities
   - `managed_by`: `user`, `astrid`, or `container`

7. Pull a minimal agent summary contract into Sprint 1 or 2. Even before `packs agent-index`, manifests should include “normal entrypoints,” “do not use for,” and “required context” fields.

8. Add a dedicated **Migration Sprint** before rich ecosystem hardening: convert one real built-in pack fully, document incompatibilities, and establish deprecation warnings for legacy resolver paths.

My position: approve the plan, but only if security, versioning, and trust are promoted from future hardening into foundational architecture. Otherwise the sprint sequence will create exactly the plugin-surface debt it is trying to avoid.
