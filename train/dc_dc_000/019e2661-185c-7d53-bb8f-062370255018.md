**Findings**

1. **Trust/sandboxing is treated as both prerequisite and deferred work.** The plan correctly says security, trust, versioning, and update semantics must be designed before install/runtime ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:327)), but real hardening is pushed to Milestone 6/Sprint 8+ ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:430)). That is risky because Git install makes arbitrary executable code first-class in Sprint 4. Before implementation, the doc should explicitly define the v1 threat model: installed packs are trusted code, what confirmation means, what secrets are passed, whether subprocesses inherit the full environment, and what “trust summary” must show.

2. **Runtime contract is still too vague for the central abstraction.** `runtime: {type: python-cli, entrypoint, callable}` is directionally right ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:164)), but not enough to implement reliably. The plan later notes callable shape, argv/env behavior, output conventions, exit codes, and error wrapping are needed ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:335)), but that should be promoted into the manifest contract section. Without it, `PackResolver` risks becoming a path resolver while every runner still makes local assumptions.

3. **Install/update semantics need atomicity details.** The plan says copy/clone, validate, then activate ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:608)), and later says updates support rollback ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:646)). Missing: active pointer model, install staging directory, lockfile format, concurrent command behavior during update/uninstall, whether rollback restores dependencies/docs/examples too, and how broken active records are recovered. Add these before coding install.

4. **The namespace model is underpowered for public Git packs.** Bare `id: my_project` is fine for local experiments, but Git-backed install quickly collides across users. The doc acknowledges stronger namespacing only as a caution ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:342)). I would force an explicit decision: v1 either uses local unique IDs with collision rejection only, or supports a source-qualified identity separately from CLI aliases. Do not let Git URL identity, pack id, installed folder name, and CLI prefix blur together.

5. **PackResolver is coherent but potentially over-broad for v1.** Resolving pack roots, docs, schemas, runtime files, examples, assets, and revisions in one abstraction ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:303)) is reasonable, but “assets” and installed revisions could pull it toward lifecycle/state concerns. Keep v1 resolver read-only and deterministic: discover packs, resolve component manifests, resolve paths relative to pack root. Put install records/revisions behind a separate installed-pack store.

6. **Scaffolding arrives too late relative to validation.** Sprint 1 includes `packs new`, but component scaffolding waits until Sprint 5 ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:663)). That creates a long phase where builders can create valid empty packs but not easily create valid runnable components. Move minimal `executors new` and `orchestrators new` earlier, at least enough to exercise Milestone 1 end to end.

7. **External elements are correctly delayed, but element identity is unresolved.** Existing docs say executor/orchestrator ids are pack-qualified while element ids stay bare by kind ([docs/creating-tools.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/creating-tools.md:116)). Git-backed external elements make bare IDs collision-prone. Before external element work, decide whether timeline references become pack-qualified, aliasable, or collision-rejected. This is more important than the registry mechanics.

8. **Agent index generation from Markdown is a trap unless bounded.** The doc says generated from manifests, `STAGE.md`, and pack docs ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:197)). That can produce unstable summaries. For v1, structured fields should dominate; Markdown can be linked or excerpted only by explicit headings/size limits.

9. **Validation may accidentally execute untrusted code.** “Runtime entrypoints import or load successfully” ([docs/git-backed-packs-plan.md](/Users/user_c042661f/Documents/reigh-workspace/Astrid/docs/git-backed-packs-plan.md:271)) can run arbitrary import-time code during validation. For Git packs, validation should first do static path/schema checks; any import/runtime proof should be clearly labeled executable and covered by trust confirmation.

**Concrete Doc Changes**

Add a “V1 Non-Negotiable Decisions” section covering threat model, namespace identity, runtime contract, install atomicity, and resolver/store boundaries.

Move runtime callable details into “Component Manifest Contracts” with one complete executor and orchestrator manifest example.

Split `PackResolver` from `InstalledPackStore`.

Move minimal component scaffolding into Milestone 1 or Sprint 1/2.

Define element ID policy before external element implementation.

Replace “import or load successfully” with static validation plus optional trusted runtime smoke test.

**Verdict**

The plan is coherent and mostly sequenced in the right direction: validate, resolve deterministically, then install. The main risk is that it gestures at the hard product contracts while scheduling implementation around them. Tighten the trust, runtime, namespace, and atomic install decisions before writing code, and v1 becomes much more implementable.
