Short version: we should not reinvent this. Comfy already has the core pieces; VibeComfy mostly needs to stop tearing the runtime down when we want warm generations. What I found: - VibeComfy’s current `embedded` path opens `Comfy(...)`, queues one workflow, then exits the async context in [vibecomfy/runtime/run.py](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/vibecomfy/runtime/run.py:108). That is inherently a cold-ish one-shot mode. - VibeComfy’s managed server path starts `comfyui serve`, queues once, then terminates the process in [vibecomfy/runtime/server.py](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/vibecomfy/runtime/server.py:16). Also not warm. - External server mode already has the right shape: if we keep one Comfy server alive and submit repeated prompts to it, Comfy’s own `current_loaded_models` model cache and execution cache can persist between jobs. - Upstream Comfy exposes `POST /free` and the newer prefixed `POST /api/free`; both accept `{"unload_models": true, "free_memory": true}`. `unload_models` calls Comfy’s model unload path, while `free_memory` also resets executor cache. Source: ComfyUI [`server.py`](https://github.com/Comfy-Org/ComfyUI/blob/master/server.py#L1016-L1025), [`main.py`](https://github.com/Comfy-Org/ComfyUI/blob/master/main.py#L341-L358). - Comfy’s CLI already has memory policy flags we should lean on: `--highvram` keeps models in GPU memory, `--disable-smart-memory` makes Comfy offload more aggressively, and `--cache-none` reduces RAM/VRAM by disabling node result reuse. Source: ComfyUI [`cli_args.py`](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/cli_args.py#L115-L160). - Comfy’s model manager tracks `current_loaded_models`, loads/reuses models, unloads clones, and frees models under pressure. Source: ComfyUI [`model_management.py`](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py#L499-L716). The pragmatic design I’d use: 1. Add a long-lived runtime/session mode in VibeComfy that keeps a managed Comfy server process open across generations. 2. Default warm behavior: do nothing after each generation. Let Comfy keep models/execution cache warm. 3. Add explicit flush: call `POST /api/free` with `unload_models` and optionally `free_memory`. 4. On model switch: either let Comfy’s smart memory handle it, or proactively flush before queueing if VibeComfy detects a different model fingerprint. 5. Expose server memory flags, probably starting with `--highvram`, `--reserve-vram`, and cache policy. Avoid `--cache-none` for warm mode unless the user is memory constrained. So the key shift is: warm mode should be process/session lifecycle, not workflow graph logic. Comfy already knows how to cache and unload; VibeComfy should give users control over when the Comfy process stays alive and when `/api/free` is called.
