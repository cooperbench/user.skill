**Core Concept**
A custom node should be a small installable package with:

```text
custom_nodes/
  gpt-image-generate/
    node.yaml
    SKILL.md
    run.py
    adapter.py        # optional
    requirements.txt  # optional
    tests/
```

`node.yaml` is the machine contract. `SKILL.md` is the human/agent usage doc. `run.py` is the executable implementation. `adapter.py` exists when the wrapped tool does not naturally match the standard input/output shape.

A node should not need to be imported into the main app process. The app calls it through a stable protocol, usually JSON over stdin/stdout or HTTP from a worker process.

**Standard Node Contract**
Every node should expose:

```yaml
id: artagents.gpt_image.generate
name: GPT Image Generate
version: 0.1.0
description: Generate one or more image assets from prompts.
runtime: python
entrypoint: run.py
category: image
inputs:
  prompt:
    type: text
    required: true
  size:
    type: enum
    values: ["1024x1024", "1536x1024", "1024x1536"]
    default: "1024x1024"
  n:
    type: integer
    default: 1
outputs:
  images:
    type: image[]
  manifest:
    type: json
side_effects:
  writes_files: true
  network: true
permissions:
  env:
    - OPENAI_API_KEY
```

The actual execution request should look like:

```json
{
  "run_id": "abc123",
  "node_id": "artagents.gpt_image.generate",
  "inputs": {
    "prompt": "A clean editorial still of a red triangle on white",
    "size": "1024x1024",
    "n": 1
  },
  "context": {
    "workdir": "runs/custom/abc123",
    "env_file": "this.env"
  }
}
```

And every node returns the same envelope:

```json
{
  "status": "success",
  "outputs": {
    "images": [
      {
        "type": "image",
        "path": "runs/custom/abc123/image_001.png",
        "mime": "image/png"
      }
    ],
    "manifest": {
      "type": "json",
      "path": "runs/custom/abc123/manifest.json"
    }
  },
  "logs": [],
  "metrics": {
    "duration_sec": 12.4
  }
}
```

**Canonical Data Types**
I’d keep the first version strict:

```text
text
json
image
image[]
audio
video
video[]
timeline
assets_manifest
transcript
file
file[]
```

Internally, everything should be file-backed. Even text/json can be inline for convenience, but large media should always be referenced by path. That fits ArtAgents well because the repo already works through inspectable artifacts in `runs/`.

**Live Install / No Reboot**
For “install any curated node and use it live,” I’d avoid importing node code into the main process.

Use this model:

1. Main app has a `NodeRegistry`.
2. Registry scans:
   - built-in nodes
   - curated remote index
   - locally installed `custom_nodes/*/node.yaml`
3. Installing a node downloads/copies the node folder and installs dependencies into that node’s own environment.
4. The registry reloads metadata immediately.
5. Execution happens in a separate worker process.

That gives hot installation without rebooting the main app because new code is discovered as metadata and launched out-of-process.

For process strategy:

```text
MVP: spawn one process per node run
Later: persistent warm workers per node/runtime
Later: remote worker pool / queue
```

Per-run spawning is slower but simpler and safer. Persistent workers matter once startup time hurts.

**Curated Node Store**
A curated registry can just be a JSON index at first:

```json

    {
      "id": "artagents.gpt_image.generate",

      "source": "https://github.com/...",
      "sha256": "...",
      "categories": ["image", "generation"],
      "verified": true
    }
  ]
}
```

The app should support:

```text
list available nodes

uninstall node
update node
enable/disable node
show node docs
run node
validate node
```

Curated means the registry only lists reviewed nodes. Users can still sideload local nodes, but those should be marked untrusted.

**Adapters**
Adapters are important. Many useful scripts will not naturally accept your standard JSON envelope.

So a node can be one of two things:

1. **Native node**: accepts standard JSON request and returns standard JSON response.
2. **Wrapped node**: adapter translates standard inputs into CLI args, runs the existing tool, then converts outputs back into the standard response.

Example: `generate_image.py` already wants CLI args like `--prompt`, `--out-dir`, `--manifest`. A `gpt-image-generate` node adapter would map:

```text
inputs.prompt -> --prompt
context.workdir -> --out-dir
outputs.manifest -> --manifest
```

This lets you reuse existing ArtAgents tools without rewriting them.

**LLM-Generated Adapters**
I’d allow LLM-generated adapters, but only as a dev workflow, not silent runtime magic.

Good workflow:

```text
User selects script -> system inspects argparse/help/schema -> LLM proposes node.yaml + adapter.py -> validation runs -> user/curator approves -> node becomes installable
```

The validator should check:

```text
node.yaml parses
required inputs exist
entrypoint runs --help or dry-run
sample fixture succeeds
outputs match declared schema
no unsafe permissions unless declared
```

**Main Requirements**
I’d write the first implementation requirements like this:

1. `NodeRegistry` can discover installed nodes from `custom_nodes/*/node.yaml`.
2. `NodeRunner` can execute a node in a separate Python subprocess with a standard JSON request.
3. Every node returns a standard JSON response with typed outputs.
4. `NodeInstaller` can install curated nodes from a local/remote index.
5. Nodes can declare dependencies, permissions, inputs, outputs, docs, and version.
6. Node installs/reloads do not require restarting the main app.
7. Existing ArtAgents CLIs can be wrapped through adapters.
8. All outputs are file-backed under `runs/custom/<run_id>/`.
9. A validator can test a node before it becomes enabled.
10. The UI/API can list, install, enable, run, and inspect nodes.

```text
artagents/nodes/builtin/gpt_image_generate/
```

Start with local curated nodes only. No remote marketplace yet. Once local install/run works, add a curated index.

The key design choice: keep the node runtime boring and strict. The creative flexibility lives inside adapters and node packages; the host app only understands schemas, files, subprocesses, and typed outputs.

```yaml

    type: video
    required: false
    when_missing: allow
  shots:
    type: shots
```

```text

allow
omit_arg
skip_node
degrade
```

**Output Modes**

Some nodes create outputs. Some replace outputs. Some mutate existing files. The schema needs to say which.

```yaml
outputs:
  timeline:
    type: timeline
    path: hype.timeline.json
    mode: create_or_replace
  assets_manifest:
    type: assets_manifest
    path: hype.assets.json
    mode: create_or_replace
```

For `refine`:

```yaml
outputs:
  report:
    type: json
    path: refine.json

    path: hype.timeline.json

    type: assets_manifest
    path: hype.assets.json
    mode: mutate
  metadata:
    type: metadata
    path: hype.metadata.json
```

Output modes:

```text
create
create_or_replace
mutate
append
directory
side_effect
```

```text
mtime
content
```

**Adapters**

Adapters convert node envelope to implementation-specific invocation.

```yaml
adapter:
  type: cli
  arg_map:
    --pool: inputs.pool.path
    --arrangement: inputs.arrangement.path
    --brief: inputs.brief.path
    --out: context.output_dir
    --video: inputs.video.path?
```

For more complex cases:

```yaml
adapter:
  type: python
  path: adapter.py
```

Rule of thumb:

```text
simple CLI -> declarative arg_map
weird CLI / multiple outputs / generated files -> adapter.py
```

**Graph Schema**

A graph is separate from nodes:

```yaml
id: artagents.graph.hype_cut
name: Hype Cut
inputs:
  video:
    type: video
    required: false
  audio:
    type: audio
    required: false
  brief:
    type: text_file
    required: true

nodes:
  - id: transcribe
    uses: artagents.transcribe
    inputs:
      audio: graph.inputs.audio || graph.inputs.video
    outputs:
      transcript: run.source.transcript

  - id: scenes
    uses: artagents.scenes
    condition:
      exists: graph.inputs.video
    inputs:
      video: graph.inputs.video
    outputs:
      scenes: run.source.scenes

  - id: shots
    uses: artagents.shots
    condition:
      exists: nodes.scenes.outputs.scenes
    inputs:
      video: graph.inputs.video
      scenes: nodes.scenes.outputs.scenes
    outputs:
      shots: run.source.shots
```

The graph gives you Comfy-like composability while preserving current CLI compatibility.

**Elegant Rule**

A node should be boring:

```text
typed inputs in
typed outputs out
declared side effects
declared cache behavior
declared runtime
```

A graph should be smart:

```text
routing
conditions
loops
fan-out/fan-in
cache reuse
human/AI decisions
```

That separation is what lets ArtAgents internal stages, Moirae, image generation, visual understanding, and future Comfy-style custom nodes all live in the same system without every node becoming a tiny bespoke orchestrator.

**Recommended Node Shape**

A node should be a folder:

```text
nodes/
  moirae_demo_video/
    node.py
    SKILL.md
    requirements.txt
    README.md        # optional
    tests/           # optional
```

The important simplification: **the schema should live in code**, not in hand-authored JSON.

Example:

```python
# nodes/moirae_demo_video/node.py

from artagents.nodes import node, Input, Output, Requirements

@node(
    id="external.moirae.demo_video",
    name="Moirae Demo Video",
    description="Render a scripted terminal demo video from a Moirae screenplay.",
    requirements=Requirements(
        python=["moirae"],
        binaries=["asciinema", "agg", "ffmpeg"],
    ),
)
def run(
    screenplay: Input.file,
    out: Output.video = "video.mp4",
    skin: str | None = None,
) -> Output:
    return subprocess_node(
        [
            "python",
            "-m",
            "moirae",
            screenplay.path,
            "-o",
            out.path,
            *(["--skin", skin] if skin else []),
        ],
        outputs={"video": out},
    )
```

Then the registry imports the node module and derives the schema from the decorated function.

This gives you:
- code as source of truth
- typed inputs/outputs
- no duplicated JSON schema
- easy adapters
- easy custom behavior
- a natural place for docs and tests

**Requirements**

I would not install requirements every time a node launches. That is slow, flaky, and dangerous.

Use this model:

```text
install/enable time:
  create or sync node environment

run time:
  use existing environment
```

Best default: **one isolated uv environment per external node**.

```text
.artagents-node-envs/
  external.moirae.demo_video/
    pyproject.toml / uv.lock / .venv
  external.some_other_node/
    .venv
```

Why per-node envs:
- avoids dependency conflicts
- lets nodes use weird versions
- makes uninstall/update clean
- safer than polluting the main ArtAgents env

Use `uv` because it is fast and deterministic:

```bash
uv venv .artagents-node-envs/external.moirae.demo_video
uv pip install -r nodes/moirae_demo_video/requirements.txt
```

Or better, for folder nodes:

```bash
uv pip install -e nodes/moirae_demo_video
```

If a node has no requirements, it can run in the main env.

**Common Env vs Per-Node Env**

I’d support both, but default to per-node.

```python
Requirements(
    mode="isolated",  # default for external nodes
    python=["moirae", "pillow", "pyyaml"],
    binaries=["ffmpeg"],
)
```

For built-in ArtAgents nodes:

```python
Requirements(mode="host")
```

So:
- built-in nodes use the ArtAgents environment
- external nodes get isolated uv envs
- advanced users can opt into shared env for simple/local trusted nodes

**When To Install**

Use explicit lifecycle commands:

```bash
python pipeline.py nodes discover
python pipeline.py nodes install external.moirae.demo_video
python pipeline.py nodes validate external.moirae.demo_video
python pipeline.py nodes run external.moirae.demo_video ...
```

On first run, you can offer auto-setup:

```text
Node external.moirae.demo_video is not installed.
Run setup now? [y/N]
```

But for automation, make it explicit:

```bash
python pipeline.py nodes run external.moirae.demo_video --auto-install
```

No hidden install by default.

**Simpler Structure**

I’d simplify the implementation around three concepts:

```text
NodeSpec     metadata derived from code
NodeRuntime  how to prepare/execute it
NodeRegistry where nodes are found
```

Directory layout:

```text
artagents/nodes/
  __init__.py
  api.py          # @node, Input, Output, Requirements
  registry.py
  runtime.py
  cli.py
  builtins/
    transcribe.py
    scenes.py
    render.py
  curated/
    moirae_demo_video/
      node.py
      SKILL.md
      requirements.txt
```

Actually, for built-ins we do not need one file per stage immediately. We can have:

```text
artagents/nodes/builtins/pipeline_steps.py
```

where each existing step is registered from `pipeline.py`.

**Schema**

The user-facing schema can be generated from code.

Internal dataclass:

```python
@dataclass
class NodeSpec:
    id: str
    name: str
    version: str
    kind: Literal["built_in", "external"]
    inputs: list[PortSpec]
    outputs: list[PortSpec]
    requirements: Requirements
    cache: CachePolicy
    execution: ExecutionPolicy
```

But authors should not write that manually unless they want to.

For custom nodes, this should be enough:

```python
@node(id="external.foo", name="Foo")
def run(image: Input.image, prompt: str) -> Outputs:
    ...
```

If a node needs more control:

```python
@node(
    id="external.foo",
    cache=Cache.none(),
    requirements=Requirements(
        mode="isolated",
        python=["opencv-python"],
        binaries=["ffmpeg"],
    ),
)
def run(...):
    ...
```

**Outputs**

Outputs should be code objects, not raw strings:

```python
def run(prompt: str, out_dir: RunDir) -> Outputs:
    image = out_dir / "image.png"
    ...
    return Outputs(
        image=Artifact.image(image),
        manifest=Artifact.json(out_dir / "manifest.json"),
    )
```

That is much cleaner than `path_template="{out}/video"` everywhere.

**External Node Folder Contract**

A folder node should only need:

```text
node.py required
SKILL.md optional but strongly recommended
requirements.txt or pyproject.toml optional
```

Discovery rule:
- scan configured node roots
- any folder containing `node.py` is a candidate
- import in a controlled subprocess to read metadata
- cache discovered specs

Example:

```text
custom_nodes/
  moirae/
    node.py
    SKILL.md
    requirements.txt
```

**Important Safety Detail**

Do not import untrusted node code into the main process just to inspect it.

Use a metadata subprocess:

```bash
python -m artagents.nodes.inspect_node custom_nodes/moirae
```

That subprocess imports `node.py`, extracts the `NodeSpec`, prints JSON, exits.

Main process receives JSON only.

Then execution also happens in a subprocess.

> DEVELOPER

nice, do you need to delete it from wherewhere? Why are there a refresh button?

> AGENT

No, nothing meaningful needs deleting from “wherewhere” unless you mean the cached catalog/git checkouts.

There are two separate things:

1. `__pycache__`
I already deleted generated Python cache folders from `artagents/nodes`, `artagents/conductors`, and `tests`. They are just local runtime artifacts and can always be deleted safely.

2. Banodoco catalog/git cache
When a catalog node/conductor is loaded, its git repo is cloned into a repo-local cache, roughly:

```text
.artagents/banodoco-nodes/
.artagents/banodoco-conductors/
```

You do **not** need to delete these normally. They exist so listing/installing catalog entries doesn’t reclone every time.

The “refresh button” is actually a CLI flag:

```bash
--banodoco-refresh
```

It means: throw away/refetch the cached checkout for catalog entries and reload from the pinned ref. It’s useful when:

- the catalog row changed
- a branch/source ref points somewhere new
- the local cached clone got corrupted
- you are testing catalog changes

If every catalog target is pinned to an immutable `commit_sha`, refresh is rarely needed. It’s mostly a manual escape hatch, not something users should hit every run.

> DEVELOPER

Is that split elegant?

> AGENT

Yes, the split is mostly elegant:

- Normal path: use the cache automatically.
- Escape hatch: `--banodoco-refresh` when developing or recovering from stale/corrupt cache.
- No hidden auto-updates: catalog entries are pinned, so installed behavior stays predictable.
- Separate caches for nodes vs conductors: clear ownership, simpler debugging, no accidental id collisions.

The one thing I’d tighten: rename the user-facing wording from “refresh” to something more explicit if it ever becomes a UI button. For CLI, `--banodoco-refresh` is fine. In UI, I’d call it **Re-fetch catalog source** or **Update cached source**, because “refresh” could sound like reloading the list, not recloning the git-backed manifest.

I would not delete the cache automatically on every launch. That would make the system slower, more network-dependent, and less deterministic.

> DEVELOPER

Why do we even need to do that? Why not poll live?

> AGENT

Polling live is fine for the **catalog list**. It is not enough for the **code source**.

There are two layers:

1. **Catalog metadata**
   “What curated nodes/conductors exist?”
   
   This can be fetched live every time from Banodoco. Cheap, small JSON, fine to poll.

2. **Executable source**
   “What code/manifest do I actually run?”
   
   This is a git repo checkout. You usually do not want to reclone or refetch it every time because it is slower, can fail offline, and can silently change behavior if the ref is mutable.

So the elegant split is:

```text
Poll catalog live -> discover curated entries
Use pinned cached source -> run deterministic code
Refresh source only when requested -> update local checkout
```

If every install target is pinned by `commit_sha`, then polling live gives you current catalog membership while cached source remains stable. When the catalog points to a new commit, the cache key changes and it fetches that new source automatically. In that case `--banodoco-refresh` is mostly for branch/tag/source_ref development or cache repair.

If we only support immutable `commit_sha` for curated catalog entries, we could almost remove refresh from normal UX entirely. It becomes a hidden/dev command, not a user-facing button.
