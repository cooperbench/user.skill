> DEVELOPER

Why do we even need to do that? Why not poll live?

> AGENT

Polling live is fine for the **catalog list**. It is not enough for the **code source**. There are two layers: 1. **Catalog metadata** “What curated nodes/conductors exist?” This can be fetched live every time from Banodoco. Cheap, small JSON, fine to poll. 2. **Executable source** “What code/manifest do I actually run?” This is a git repo checkout. You usually do not want to reclone or refetch it every time because it is slower, can fail offline, and can silently change behavior if the ref is mutable. So the elegant split is: ```text Poll catalog live -> discover curated entries Use pinned cached source -> run deterministic code Refresh source only when requested -> update local checkout ``` If every install target is pinned by `commit_sha`, then polling live gives you current catalog membership while cached source remains stable. When the catalog points to a new commit, the cache key changes and it fetches that new source automatically. In that case `--banodoco-refresh` is mostly for branch/tag/source_ref development or cache repair. If we only support immutable `commit_sha` for curated catalog entries, we could almost remove refresh from normal UX entirely. It becomes a hidden/dev command, not a user-facing button.
