# Background

We just landed a 3-line quick fix on branch `megaplan/m1b-m1c-stores` that removes redundant double-writes from `src/tools/video-editor/hooks/useTimelineSelection.ts`. The wrapper was calling both the store action AND a `setSelectedClipId` pass-through that routed to `setTimelineSelectedClipId` → `selectTimelineClip(id, undefined)`, which silently reset multi-select to single-select. Marquee + cmd+click multi-select are now functional.

The bug is fixed but the underlying smell that produced it is intact: the selection store has three overlapping entry points with subtly-different semantics, one of which (`setTimelineSelectedClipId`) masquerades as a `useState` setter while actually clobbering the whole selection. The wrapper layer (`useTimelineSelection`) still has the pre-refactor "split state" shape (multi-select set + useState-style primary id) even though M1b/M1c collapsed those into a single Zustand store.

# Goal

Eliminate the structural trap permanently so this class of bug cannot reappear, even if a future refactor wires the surfaces back together. This megaplan plans the cleanup ONLY — the bug fix is already applied. The cleanup should ship in the same PR as the quick fix but as a separate commit so the fix is revertable independently.

# Implementation Plan: Eliminate the `setTimelineSelectedClipId` Trap

## Overview

The 3-line bug fix on `megaplan/m1b-m1c-stores` removed a redundant double-write inside `useTimelineSelection.selectClip` that was silently routing every multi-select action through `selectTimelineClip(id, undefined)` and collapsing selection to one clip. The trap that produced the bug — a store action shaped like a `useState` setter that secretly *replaces* multi-selection — is still present.

This cleanup ships in the same PR as the fix but as a **separate commit** so the fix remains revertable. Scope is video-editor only. Every actual caller of `setSelectedClipId` passes either a literal clipId or `null` (verified by grep — no `(prev) => …` updaters), so the `Dispatch<SetStateAction<…>>` shape is deleted, not renamed.

### Behavioral invariant preserved (gallery sync)

Today, every editor-internal selection mutation **preserves gallery selection** (via `useTimelineMultiSelect`'s `{ clearGallery: false }` wrappers at `src/shared/state/selectionStore.ts:780-789`, plus explicit `{ clearGallery: false }` at `useTimelineCommit.ts:187,190`). Gallery → timeline-clear flows the *other* direction, driven by gallery-side actions in `selectGalleryItem`/`selectGalleryItems`. Removing the multi-select adapter would invert this default for drag/marquee/programmatic paths — that is **not** in scope for this cleanup. **The adapter stays.** Only the trap method (`setSelectedClipId`) is removed from both store and wrapper surfaces. Each remaining adapter call gets a one-line JSDoc making the "editor-internal mutations preserve gallery" rule explicit.

### Target store API (final shape) — including the gallery-default asymmetry

`src/shared/state/selectionStore.ts` exposes exactly five timeline-selection write entry points. **Note the asymmetry between `selectTimelineClip`/`selectTimelineClips` (gallery cleared by default, opt-OUT via `{clearGallery: false}`) and `clearTimelineSelection` (gallery preserved by default, opt-IN via `{clearGallery: true}`).** This was verified at `src/shared/state/selectionStore.ts:462, 492, 405`. The asymmetry already exists in the codebase and is out of scope to normalize, but the JSDoc must call it out so future readers do not assume parallelism.

| Action | Resets `selectedClipIds`? | Preserves multi-select? | Gallery default | How to override |
|---|---|---|---|---|
| `selectTimelineClip(id, opts?, syncOpts?)` | yes if `!opts.toggle`; toggles when `opts.toggle` | only via `opts.toggle` | **clears** gallery | `{clearGallery: false}` to preserve |
| `selectTimelineClips(ids, syncOpts?)` | yes — replaces with `ids` | no (replace verb) | **clears** gallery | `{clearGallery: false}` to preserve |
| `clearTimelineSelection(syncOpts?)` | yes — empties | no | **preserves** gallery (opt-in to clear) | `{clearGallery: true}` to also clear |
| `addTimelineClips(ids)` | no — additive | yes | no gallery sync | n/a |
| `pruneTimelineSelection(validIds)` | filters | yes | no gallery sync | n/a |

Deleted: `setTimelineSelectedClipId`, the `setSelectedClipId` field on `useTimelineSelectionStore`, the `TimelineSetSelectedClipId` type alias, and the `replaceTimelineSelection` alias on the editor-ops surface. `useTimelineMultiSelect`'s `selectClip` / `selectClips` / `clearSelection` wrappers (the ones that fix `clearGallery: false`) **remain intact**.

### Target wrapper (`useTimelineSelection`)

Thin to **derivations + refs only**: `selectedClip`, `selectedTrack`, `selectedClipHasPredecessor`, `resolvedConfig`, `selectedClipIds`, `selectedClipIdsRef`, `additiveSelectionRef`, `primaryClipId`, `isClipSelected`, `pruneSelection`. All mutation methods (`selectClip`, `selectClips`, `addToSelection`, `clearSelection`, `replaceTimelineSelection`, `setSelectedClipId`) are removed. `useTimelineState.ts` pulls mutators directly from `useTimelineMultiSelect()` (which still applies the `{ clearGallery: false }` rule).
