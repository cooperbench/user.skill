        # Implementation Plan: Megaplan Observability & Operator UX

## Overview

Megaplan currently has four monitoring commands (`status`, `progress`, `watch`, `audit`) that overlap in confusing ways, no guidance shown to operators about *how* to monitor after launching a step, and solid duplicate-launch prevention via file locking that already works. The working tree already contains uncommitted changes (stale-step orphan detection, Codex retry logic, light-robustness workflow changes) that this plan must build on top of.

**Goal:** Make `watch` the primary monitoring path (unifying status + progress), surface a `monitor_hint` in every step-launch response so operators know what to run, and tighten the active-step guard so the harness instructions prevent launching over a running step.

**Constraints:**
- The existing `status` and `progress` commands must remain available (backwards compatibility for scripts/instructions).
- The file-lock based duplicate prevention already works at the process level — the gap is at the *instructions* level where the orchestrating agent may not check before launching.
- All changes must pass the existing test suite plus new coverage.

## Main Phase

### Step 1: Add `monitor_hint` to step-launch responses (`megaplan/handlers.py`)
**Scope:** Small
1. **Add** a `monitor_hint` field to the response dict built by `_finish_step()` (`megaplan/handlers.py:247`). The hint should read: `"Monitor this plan with: megaplan watch --plan <name>"`, using the actual plan name from state.
2. **Also add** the hint to the error response in `plan_lock` when a step is already running (`megaplan/_core/state.py:168-173`), so operators told "plan is locked" also get the monitoring command.
3. **Verify** the hint appears in the JSON output by running a targeted unit test.

### Step 2: Update instructions to surface monitoring on launch and prefer `watch` (`megaplan/data/instructions.md`)
**Scope:** Small
1. **Update** the Commands section (`instructions.md:98-103`) to lead with `watch` as the primary monitoring command instead of listing all four equally.
2. **Add** a short "Monitoring" subsection after the existing execution polling guidance (`instructions.md:56-66`) that tells the orchestrating agent: after launching any step, use `megaplan watch --plan <name>` to track it; check `active_step` in status before launching a new step.
3. **Add** explicit pre-launch guidance: "Before running any step command, check `megaplan status --plan <name>`. If `active_step` is present and not `stale`/`orphaned`, do NOT launch another step — wait or use `megaplan watch` to monitor the running step."

### Step 3: Add pre-launch active-step check in CLI handlers (`megaplan/handlers.py`)
**Scope:** Medium
1. **Add** a pre-launch check in `_run_worker()` (`megaplan/handlers.py:138-176`): before acquiring the lock, read the current state's `active_step`. If it exists and is not stale, raise a `CliError("step_already_running", ...)` with the monitor hint. This catches the case where the *same process* (or a process that can read state) tries to launch over a running step without waiting for the lock to block.
2. **Note:** The file lock already prevents true concurrent execution. This check provides a better error message *before* hitting the lock, and catches cases where state wasn't cleared (e.g., agent crashed without releasing lock but state still shows active).

### Step 4: Update and add tests (`tests/test_megaplan.py`, `tests/test_workers.py`)
**Scope:** Medium
1. **Add** a test that `_finish_step()` responses include a `monitor_hint` field with the expected watch command.
2. **Add** a test that the `plan_locked` error response includes the monitor hint.
3. **Verify** existing tests still pass, especially `test_handle_status_reports_observability_fields` which already checks orphan/recovery hints.
4. **Run** the full test suite: `python -m pytest tests/ -x`.
