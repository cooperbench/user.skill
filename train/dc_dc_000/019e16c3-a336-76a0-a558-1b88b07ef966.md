## 18. Verification Addendum

### 18.1 `distillations` about-whom

`distillations` are neither `about_user_id` nullable like memories/observations nor pair-only like themes. They are evidence/provenance-scoped via `source_user_ids uuid[] NOT NULL CHECK (cardinality(source_user_ids) > 0)` (`migrations/0015_distillations.sql:16`). Core columns are: `id`, `content`, encrypted content, `confidence`, `status`, `sensitivity`, `visibility`, `shareable_summary`, `source_user_ids`, related memory/observation/theme/message arrays, revision links/counts, and timestamps (`migrations/0015_distillations.sql:6-30`). Tool code enforces `source_user_ids` stay inside `ctx.user`/`ctx.partner`, not “about whom” (`app/services/tools/write_tools.py:568-576`), and inserts `source_user_ids` directly (`app/services/tools/write_tools.py:939-956`). Read filtering is also by `source_user_id = ANY(source_user_ids)` (`app/services/tools/read_tools.py:654-656`). Plan needs a fourth about/provenance shape.

### 18.2 `bridge_candidates` end-to-end

Schema is explicitly dyadic: `source_user_id`, `target_user_id`, `kind`, lifecycle `status`, `sensitivity`, `source_message_ids`, summaries, sent message, timestamps (`migrations/0013_bridge_candidates.sql:3-18`). `partner_path` later classifies the bridge route, defaulting historical rows to `message_partner` (`migrations/0016_partner_bridge_paths.sql:3-17`). Proposed by `create_bridge_candidate`; it requires `source_user_id == ctx.user.id` and both users in the current dyad (`app/services/tools/write_tools.py:273-286`, `app/services/tools/write_tools.py:504-506`). Status auto-derives `ready` only for opt-in low/medium source material, otherwise `pending` (`app/services/tools/write_tools.py:291-302`). Target surfacing happens in hot context only where `target_user_id = current user`, `source_user_id = partner`, `status='ready'`, and `partner_path='message_partner'` (`app/services/hot_context.py:424-438`). Target can only mark visible candidates `addressed` or `declined` (`app/services/tools/write_tools.py:348-371`). Immediate sending is source-side only and sends to `ctx.partner` (`app/services/tools/write_tools.py:437-487`). Multi-bot breaks unless bridge rows gain dyad/bot/topic scope: current code assumes the same bot has both partners in one `ctx`.

### 18.3 `scheduled_jobs` vs `scheduled_tasks`

There is no `scheduled_tasks` table. The active table is `scheduled_jobs` (`migrations/0001_init.sql:98-107`). Migration 0017 only adds `scheduled_task` as a `scheduled_jobs.job_type` plus indexes (`migrations/0017_scheduled_tasks.sql:3-24`). The worker claims and dispatches rows from `scheduled_jobs` only (`app/services/scheduled_jobs.py:104-138`). `scheduled_task` is an agent-managed job subtype handled by `handle_scheduled_task` (`app/services/scheduled_job_handlers.py:160-169`) and created/listed/updated/cancelled through `scheduled_jobs` rows (`app/services/tools/write_tools.py:1337-1374`, `app/services/tools/write_tools.py:1404-1472`). Recommendation: add `bot_id` and `topic_id` to `scheduled_jobs`; do not model `scheduled_tasks` as a parallel table.

### 18.4 `hot_context` coupling

`build_hot_context(pool, user, partner: User, ...)` is not partner-optional (`app/services/hot_context.py:173-179`). Passing `None` breaks immediately at `_user_profile(pool, partner)` (`app/services/hot_context.py:180-181`). Dyad assumptions are pervasive: OOB pulls both owners (`app/services/hot_context.py:227-235`), memories use `[user.id, partner.id]` plus shared NULL (`app/services/hot_context.py:248-258`), messages query either participant (`app/services/hot_context.py:328-339`), sharing defaults require both users (`app/services/hot_context.py:340-343`), distillations filter both source ids (`app/services/hot_context.py:344-360`), bridges require partner-as-source (`app/services/hot_context.py:424-438`), and render always emits “Your Partner” plus partner sharing defaults (`app/services/hot_context.py:581-608`). `TurnContext` also types `partner: User` (`app/services/turn_context.py:16-22`). A solo builder should be separate.

### 18.5 Prompt renderer coupling

The prompt opens as a relationship mediator between `{partner_a_name}` and `{partner_b_name}` (`app/services/prompts.py:7-12`). The renderer requires both `partner_a` and `partner_b` strings (`app/services/prompts.py:435-443`) and blindly replaces both placeholders (`app/services/prompts.py:464-471`). Large sections are dyad-only: cross-thread sharing, partner perspective, bridge candidates, in-person redirection, and crisis escalation to partner (`app/services/prompts.py:122-133`, `app/services/prompts.py:166-186`, `app/services/prompts.py:217-222`, `app/services/prompts.py:335-370`). Split solo vs dyadic renderers; making `partner` optional in this renderer would leave too much dead policy.

### 18.6 OOB delivery-time guardrail

Delivery-time OOB runs before `send_outbound` delivery via `_call_oob_hook(pool, content, user.id, protected_owner_ids)` (`app/services/messaging.py:338-366`) and for incremental parts at the same point (`app/services/messaging.py:193-228`). The default hook calls `check_oob_with_policy` (`app/services/hooks.py:13-25`). Scope defaults to recipient only when `protected_owner_ids` is omitted (`app/services/oob_check.py:106-109`, `app/services/oob_check.py:175-180`); agentic turns currently pass both dyad ids (`app/services/agentic.py:725-741`). The check fetches active OOB by owner/status only, no topic filter (`app/services/oob_check.py:112-124`). Adding `topic_ids IS NULL OR $bot_topic = ANY(topic_ids)` is moderate: schema first, then thread `bot_topic` through `send_outbound`, `_call_oob_hook`, hook contract, and `_active_oob_entries`. It is a separate Anthropic model call, not in-process logic (`app/services/oob_check.py:191-221`).

### 18.7 Outbound transport coupling

Transport is globally selected from `settings.messaging_provider` (`app/config.py:26`). `send_outbound` branches inline on provider and directly calls `discord.send_text` or `whatsapp.send_text/send_template` (`app/services/messaging.py:370-399`). Incremental sending is Discord-only and returns `not_enabled` for any other provider (`app/services/messaging.py:155-168`). There is no sender interface. Per-bot outbound is moderate, not trivial: introduce a transport/channel object, move provider/window/template behavior behind it, and stamp message rows with bot/channel.

## Findings That Change The Plan

- `distillations` need explicit provenance-vs-about modeling; the current table does not fit the doc’s two existing about-whom categories.
- `scheduled_tasks` should be removed from the schema plan as a separate concept; it is a `scheduled_jobs` subtype.
- Solo support is not a signature tweak. Hot context, prompt rendering, turn context, and bridge tools are structurally dyadic.
- Bridge candidates need `dyad_id` plus likely `bot_id/topic_id`; current source/target-only rows will leak semantics across bots.
