## 18. Verification Addendum ### 18.1 `distillations` about-whom `distillations` are neither `about_user_id` nullable like memories/observations nor pair-only like themes. They are evidence/provenance-scoped via `source_user_ids uuid[] NOT NULL CHECK (cardinality(source_user_ids) > 0)` (`migrations/0015_distillations.sql:16`). Core columns are: `id`, `content`, encrypted content, `confidence`, `status`, `sensitivity`, `visibility`, `shareable_summary`, `source_user_ids`, related memory/observation/theme/message arrays, revision links/counts, and timestamps (`migrations/0015_distillations.sql:6-30`). Tool code enforces `source_user_ids` stay inside `ctx.user`/`ctx.partner`, not “about whom” (`app/services/tools/write_tools.py:568-576`), and inserts `source_user_ids` directly (`app/services/tools/write_tools.py:939-956`). Read filtering is also by `source_user_id = ANY(source_user_ids)` (`app/services/tools/read_tools.py:654-656`). Plan needs a fourth about/provenance shape. ### 18.2 `bridge_candidates` end-to-end Schema is explicitly dyadic: `source_user_id`, `target_user_id`, `kind`, lifecycle `status`, `sensitivity`, `source_message_ids`, summaries, sent message, timestamps (`migrations/0013_bridge_candidates.sql:3-18`). `partner_path` later classifies the bridge route, defaulting historical rows to `message_partner` (`migrations/0016_partner_bridge_paths.sql:3-17`). Proposed by `create_bridge_candidate`; it requires `source_user_id == ctx.user.id` and both users in the current dyad (`app/services/tools/write_tools.py:273-286`, `app/services/tools/write_tools.py:504-506`). Status auto-derives `ready` only for opt-in low/medium source material, otherwise `pending` (`app/services/tools/write_tools.py:291-302`). Target surfacing happens in hot context only where `target_user_id = current user`, `source_user_id = partner`, `status='ready'`, and `partner_path='message_partner'` (`app/services/hot_context.py:424-438`). Target can only mark visible candidates `addressed` or `declined` (`app/services/tools/write_tools.py:348-371`). Immediate sending is source-side only and sends to `ctx.partner` (`app/services/tools/write_tools.py:437-487`). Multi-bot breaks unless bridge rows gain dyad/bot/topic scope: current code assumes the same bot has both partners in one `ctx`. ### 18.3 `scheduled_jobs` vs `scheduled_tasks` There is no `scheduled_tasks` table. The active table is `scheduled_jobs` (`migrations/0001_init.sql:98-107`). Migration 0017 only adds `scheduled_task` as a `scheduled_jobs.job_type` plus indexes (`migrations/0017_scheduled_tasks.sql:3-24`). The worker claims and dispatches rows from `scheduled_jobs` only (`app/services/scheduled_jobs.py:104-138`). `scheduled_task` is an agent-managed job subtype handled by `handle_scheduled_task` (`app/services/scheduled_job_handlers.py:160-169`) and created/listed/updated/cancelled through `scheduled_jobs` rows (`app/services/tools/write_tools.py:1337-1374`, `app/services/tools/write_tools.py:1404-1472`).
