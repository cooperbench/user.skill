# Plan 2 — WhatsApp ingestion + media + 24h window

Authoritative spec: `mediator-bot-spec.md`. Read it in prep. This plan builds the inbound and outbound messaging layer end-to-end, including media transcription/vision and the 24-hour window outbound helper. It must be ready to feed messages into the (not-yet-built) agentic loop and to receive draft outbounds back from it.

Plan 1's foundation is assumed complete: tables, config, DB session, FastAPI skeleton, phone whitelist helper.

## Scope (in)
### Inbound webhook
- `GET /whatsapp/webhook` for Meta verification (verify-token check, echo `hub.challenge`).
- `POST /whatsapp/webhook` that:
  1. Validates the `X-Hub-Signature-256` header against the app secret. Reject 401 on mismatch.
  2. Returns `200` immediately (Meta requires fast ack).
  3. Hands the payload to an async background worker for processing.
- Phone-number whitelist enforced before persistence; non-whitelisted senders are dropped with a log line.
- Idempotent persistence: dedup by `whatsapp_message_id` (UNIQUE constraint already exists). Re-deliveries are no-ops.
- Persist text, voice, image, and "other media" (document, sticker, etc.) inbound messages into `messages` with correct `direction='inbound'`, `processing_state='raw'`, charge left null until classified by the loop.
- Edit webhook: locate the prior message by `whatsapp_message_id`, append prior content into `edit_history` JSONB, update `content`, set `edited_at`.
- Delete webhook: set `deleted_at`. After 24h grace, a small periodic task replaces `content` with `[deleted]` while preserving the row (the periodic task can land here as a stub job that Plan 5's worker will actually run — define it now).

### Voice notes
- Fetch audio from WhatsApp media endpoint (authenticated via the WhatsApp token).
- Send to Groq Whisper for transcription.
- Store both the audio URL and the transcript on the message row (transcript goes in `content`; audio URL in `media_url`; `media_type='voice'`; `media_duration_seconds` populated).
- Failure: keep audio, leave transcript null, set `processing_state='expired'`. The bot's handling of "couldn't transcribe" is in Plan 3 — for now just produce the right state and an outbound draft is not generated by this layer.
- Twice-fail give-up logic: if transcription fails twice for the same audio, mark and stop retrying.

### Images
- Fetch image from WhatsApp media endpoint.
- Send to OpenAI vision API (current latest vision-capable model).
- Store image binary in Supabase Storage (private bucket); store the analysis text on `media_analysis` JSONB.
- Failure modes per spec: vision API failure → `media_analysis` null, message still processable. Vision daily cap hit → mark "image analysis unavailable today" in metadata so Plan 3's loop can degrade gracefully.

### Multi-message debouncing / coalescing
- Per-sender 10-second timer on inbound. New messages reset it; total cap 30s from first message.
- On expiry, mark all messages in the burst as a single processing unit (introduce a coalesce-id on `messages` or pass the burst as a list to the loop trigger — pick the cleanest approach and document it).
- The agentic-loop trigger is invoked once per burst. The loop itself is in Plan 3; here, the trigger is a function call into a stub `run_agentic_turn(burst, user)` that this plan provides as an interface contract (Plan 3 fills in the body).
- Mid-processing arrivals: allow current turn to finish; the new message starts the next turn's bucket. No mid-reasoning interruption.

### Outbound + 24h window
- Single helper `async send_outbound(user, content, template_fallback)` used by all outbound paths.
- Decides at send-time: if `now - user.last_inbound_at < 24h`, send free-form; otherwise send the named template with the supplied parameters. If neither is possible (rare edge case the spec calls out), defer and log on `bot_turns.reasoning` (the bot_turns row will have been created by Plan 3 — accept a `bot_turn_id` arg for this).
- Approved templates (define them so they're ready to submit to Meta on day one): `weekly_summary`, `escalation`, `checkin_nudge`, `pause_confirmation`, `media_failure`. Provide template specs (parameters, copy) in a single Python module so they're reviewable.
- `send_outbound` writes the outbound `messages` row before calling Meta; on Meta failure, retry with exponential backoff up to 3 attempts; after that, log the failure and surface it (admin view in Plan 6).

### Restart recovery
- On startup: scan messages with `processing_state='raw'` older than 30s with no `bot_turns` row → re-trigger their burst.
- `bot_turns` rows older than 5 minutes with `completed_at IS NULL` → mark `failure_reason='crashed'`, re-trigger the originating message's burst.
- `scheduled_jobs` recovery is in Plan 5.

## Overview

Plan 1 already gave us: FastAPI skeleton (`app/main.py`), `asyncpg` pool lifespan (`app/db.py`), env-backed settings (`app/config.py`), the `messages` / `bot_turns` / `users` schema (`migrations/0001_init.sql`), `record_llm_cost` (`app/services/spend.py`), and `is_allowed_phone` (`app/services/whitelist.py`). There is no task queue, no `messages` row writer, no WhatsApp client, no media pipeline, and no outbound helper yet — Plan 2 builds all of that in-process using `asyncio.create_task`.

Constraints driving design:

- Webhook MUST ack within ~5s, so all fetch/transcribe/analyze work runs in a background task spawned from the request handler, not in the request itself.
- Idempotency leans on the existing `messages.whatsapp_message_id` UNIQUE; we never need a separate dedup table.
- The `triggering_message_ids: list[UUID]` signature is the contract with Plan 3, so burst coalescing passes a list rather than adding a coalesce-id column (keeps the migration surface flat).
- `last_inbound_at` is not on `users`; we read it as `MAX(sent_at)` over inbound messages on the fly. No schema change.
- Transcription/vision retry counters are ephemeral state; we store them on `messages.media_analysis` (jsonb already exists) under a reserved key like `_pipeline.attempts` rather than adding a column.
- Hooks reserved for later plans (`check_oob`, `paused_for_user`) live as module-level callables defaulting to pass-through / `False`, so Plans 3–5 just rebind them.
