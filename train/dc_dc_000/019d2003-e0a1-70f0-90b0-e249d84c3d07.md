## Overview

The viewer app (`viewer/`) uses React Query with 1-second polling to sync `timeline.json` from disk. Local edits go through `applyTimelineEdit` → `commitData` → debounced save (500ms). A signature-based guard in a `useEffect` (line 279 of `useTimelineData.ts`) is supposed to prevent polled data from overwriting unsaved local changes, but two race conditions allow stale server data to clobber optimistic updates:

1. **The `commitData` dependency problem:** `commitData` depends on `selectedClipId` and `selectedTrackId` (line 232). When a clip is selected during a move (which is every move), `commitData` is recreated, causing the polling `useEffect` to re-fire. Combined with React Query's structural sharing and timing, this creates windows where stale data is applied.

2. **No "pending edits" guard:** The polling effect only checks `signature !== lastSavedSignature`. During the 500ms debounce window (and while the save is in-flight), there's no mechanism to suppress polling updates. If `loadTimelineJson` resolves the config with a slightly different registry than `saveMutation.onSuccess` uses, signatures can differ, triggering an overwrite.

3. **Text clips:** May have an additional issue in the move handler where `buildRowTrackPatches` or the `materializeData` round-trip doesn't preserve text clip `hold` metadata correctly.

The inline text editing feature adds a double-click → contenteditable overlay on `OverlayEditor.tsx`, wired to the same `onOverlayChange` that handles position/size changes.

- `viewer/src/tools/video-editor/hooks/useTimelineData.ts` — state management, polling, save

## Step 1: Add a pending-edits guard to suppress stale polling (`useTimelineData.ts`)
**Scope:** Small — core fix for issues 1 and 2

1. **Add a `hasPendingEdits` ref** (around line 111) that tracks whether local changes exist that haven't been saved to disk yet:
   ```typescript
   const hasPendingEdits = useRef(false);
   ```

2. **Set `hasPendingEdits = true` in `commitData`** when `save` option is true (the default), at line ~229:
   ```typescript
   if (options?.save ?? true) {
     hasPendingEdits.current = true;
     scheduleSave(nextData);
   }
   ```

3. **Clear `hasPendingEdits = false` in `saveMutation.onSuccess`** (line ~150), AFTER updating `lastSavedSignature`:
   ```typescript
   lastSavedSignature.current = getConfigSignature(...);
   hasPendingEdits.current = false;
   ```

4. **Guard the polling useEffect** (line 279-283) to skip when edits are pending:
   ```typescript
   useEffect(() => {
     if (timelineQuery.data && !hasPendingEdits.current && timelineQuery.data.signature !== lastSavedSignature.current) {
       commitData(timelineQuery.data, { save: false, updateLastSavedSignature: true });
     }
   }, [commitData, timelineQuery.data]);
   ```

5. **Also guard the asset registry effect** (line 285-302) with the same `hasPendingEdits.current` check, since it can also overwrite local state.

6. **Also clear `hasPendingEdits` in `saveMutation.onError`** so the editor doesn't get permanently stuck ignoring polls.

**Why this works:** The ref is synchronously set before the save debounce starts and cleared only after the save succeeds and `lastSavedSignature` is updated. During the entire window (edit → debounce → save → success), polling cannot overwrite local state.

## Step 2: Stabilize `commitData` to avoid unnecessary effect re-fires (`useTimelineData.ts`)
**Scope:** Small — defense-in-depth for issues 1 and 2

1. **Move `selectedClipId` and `selectedTrackId` reads inside `commitData` to refs** instead of closing over the state values. This prevents `commitData` from being recreated every time selection changes, which avoids re-triggering the polling and asset registry effects unnecessarily.

   At line ~128, add:
   ```typescript
   const selectedClipIdRef = useRef(selectedClipId);
   selectedClipIdRef.current = selectedClipId;
   const selectedTrackIdRef = useRef(selectedTrackId);
   selectedTrackIdRef.current = selectedTrackId;
   ```

   Then in `commitData`, replace `selectedClipId` and `selectedTrackId` with `selectedClipIdRef.current` and `selectedTrackIdRef.current`, and remove them from the dependency array.

2. **Verify** that `commitData`'s dependency array becomes `[scheduleSave]` only, dramatically reducing how often the polling effect re-runs.

## Overview

The viewer app (`viewer/`) uses React Query with 1-second polling to sync `timeline.json` from disk. Local edits go through `applyTimelineEdit` → `commitData` → debounced save (500ms). A signature-based guard in a `useEffect` (`useTimelineData.ts:279`) is supposed to prevent polled data from overwriting unsaved local changes, but race conditions allow stale server data to clobber optimistic updates.

**Root causes identified:**

1. **No pending-edits guard on polling.** The polling effect at `:279` only checks `signature !== lastSavedSignature`. During the debounce window and while saves are in-flight, there is nothing suppressing poll-driven overwrites. Meanwhile, `commitData` depends on `selectedClipId`/`selectedTrackId` (`:232`), causing the polling effect to re-fire on every selection change.

2. **Text clips** likely suffer the same polling race but more visibly due to the `hold`-based duration model. The round-trip through `rowsToConfig` → `configToRows` needs verification.

3. **Inline text editing** requires a double-click handler on `OverlayEditor.tsx` overlays, but the overlay container currently sets `pointerEvents: "none"` when no clip is selected (`:331`), blocking click-through to child overlay divs entirely.

**Key files:**

## Step 1: Replace `hasPendingEdits` boolean with a monotonic edit counter (`useTimelineData.ts`)
**Scope:** Small — core fix for issues 1 and 2

The save flow allows overlapping requests: `scheduleSave` can queue a second save while a first is in-flight (`:188-197`). A single boolean would be cleared by whichever `onSuccess` fires first, even if newer edits exist. A monotonic counter solves this.

1. **Add counter refs** near line 111:
   ```typescript
   const editSeqRef = useRef(0);    // incremented on every local edit
   const savedSeqRef = useRef(0);   // the editSeq that was last sent to save
   ```

2. **Increment `editSeqRef` in `commitData`** when `save` is true (the default), at line ~229:
   ```typescript
   if (options?.save ?? true) {
     editSeqRef.current += 1;
     scheduleSave(nextData);
   }
   ```

3. **Capture the seq when the save fires** — modify `scheduleSave` (`:188-198`) to snapshot the current `editSeqRef` into the data passed to `saveTimeline`:
   ```typescript
   const scheduleSave = useCallback((nextData: TimelineData) => {
     setSaveStatus("dirty");
     if (saveTimer.current) {
       clearTimeout(saveTimer.current);
     }
     const seq = editSeqRef.current;
     saveTimer.current = setTimeout(() => {
       saveTimer.current = null;
       savedSeqRef.current = seq;
       void saveTimeline(nextData);
     }, 500);
   }, [saveTimeline]);
   ```

4. **In `saveMutation.onSuccess`** (`:142-157`), only clear the guard if the save matches the latest edit:
   ```typescript
   onSuccess: (_value, savedConfig) => {
     const current = dataRef.current;
     if (!current) return;
     setSaveStatus(savedSeqRef.current >= editSeqRef.current ? "saved" : "dirty");
     setRenderDirty(true);
     lastSavedSignature.current = getConfigSignature(resolveTimelineConfig(savedConfig, current.registry));
   },
   ```

5. **In `saveMutation.onError`** (`:154-156`), do NOT clear any guard — just mark status. The edit counter stays ahead of the saved counter, so the polling guard remains active. Schedule a retry:
   ```typescript
   onError: () => {
     setSaveStatus("error");
     // Re-schedule save for the current local state so edits aren't lost
     const current = dataRef.current;
     if (current) {
       scheduleSave(current);
     }
   },
   ```

6. **Guard the polling useEffect** (`:279-283`) — skip when local edits are ahead of the last completed save:
   ```typescript
   useEffect(() => {
     if (timelineQuery.data
         && editSeqRef.current === savedSeqRef.current
         && timelineQuery.data.signature !== lastSavedSignature.current) {
       commitData(timelineQuery.data, { save: false, updateLastSavedSignature: true });
     }
   }, [commitData, timelineQuery.data]);
   ```

7. **Guard the asset registry effect** (`:285-302`) with the same `editSeqRef.current === savedSeqRef.current` check.

**Why this works:** `editSeqRef` advances on every local edit. `savedSeqRef` advances only when a save fires. `onSuccess` compares them — it only declares "saved" when the counters match. Polling is blocked whenever the counters diverge. An out-of-order or failed save cannot prematurely unblock polling because the counter comparison is always checked fresh from the refs.

A signature-based guard in a `useEffect` (`useTimelineData.ts:279`) is supposed to prevent polled data from overwriting unsaved local changes, but race conditions allow stale server data to clobber optimistic updates.

**Scope:** Small — core fix for issues 1 and 2

The save flow allows overlapping requests: `scheduleSave` can queue a second save while a first is in-flight (`:188-197`). A monotonic counter tracks whether the latest save has completed for the latest edit.

1. **Add counter refs** near line 111:
   ```typescript

   const savedSeqRef = useRef(0);   // advanced ONLY in onSuccess to the seq that was saved
   ```

2. **Increment `editSeqRef` in `commitData`** when `save` is true (the default), at line ~229:
   ```typescript

     editSeqRef.current += 1;
     scheduleSave(nextData);
   }
   ```

3. **Capture the seq into the save closure, but do NOT advance `savedSeqRef` yet** — modify `scheduleSave` (`:188-198`) to capture the current edit seq and pass it through:
   ```typescript

     setSaveStatus("dirty");
     if (saveTimer.current) {
       clearTimeout(saveTimer.current);
     }
     const seq = editSeqRef.current;
     saveTimer.current = setTimeout(() => {
       saveTimer.current = null;
       void saveTimeline(nextData, seq);
     }, 500);
   }, [saveTimeline]);
   ```

4. **Modify `saveTimeline` to forward the seq** to the mutation context so `onSuccess` can read it:
   ```typescript
   const saveTimeline = useCallback(async (nextData: TimelineData, seq: number) => {
     setSaveStatus("saving");
     await saveMutation.mutateAsync(nextData.config, {
       onSuccess: (_value, savedConfig) => {
         const current = dataRef.current;
         if (!current) return;
         // Advance savedSeqRef ONLY here, after the POST succeeds
         savedSeqRef.current = seq;
         setSaveStatus(seq >= editSeqRef.current ? "saved" : "dirty");
         setRenderDirty(true);
         lastSavedSignature.current = getConfigSignature(
           resolveTimelineConfig(savedConfig, current.registry)
         );
       },
     });
   }, [saveMutation]);
   ```
   Remove the existing `onSuccess` from the `useMutation` options (`:142-153`) since it's now passed per-call.

5. **In `saveMutation.onError`** (`:154-156`), do NOT advance `savedSeqRef`. The counter gap persists so the polling guard stays active. Schedule a retry:
   ```typescript
   onError: () => {
     setSaveStatus("error");
     const current = dataRef.current;
     if (current) {
       scheduleSave(current);
     }
   },
   ```

6. **Guard the polling useEffect** (`:279-283`) — skip when local edits are ahead of the last *completed* save:
   ```typescript
   useEffect(() => {
     if (timelineQuery.data
         && savedSeqRef.current >= editSeqRef.current
         && timelineQuery.data.signature !== lastSavedSignature.current) {
       commitData(timelineQuery.data, { save: false, updateLastSavedSignature: true });
     }
   }, [commitData, timelineQuery.data]);
   ```

7. **Guard the asset registry effect** (`:285-302`) with the same `savedSeqRef.current >= editSeqRef.current` check.

**Why this works:** `editSeqRef` advances on every local edit. `savedSeqRef` advances ONLY in `onSuccess` — never at dispatch time. During the entire window from edit → debounce → HTTP POST → success, `editSeqRef > savedSeqRef`, so any poll landing during that window is blocked. An out-of-order completion for an older seq advances `savedSeqRef` but it's still `< editSeqRef`, so polling stays blocked. Only when the save for the latest edit succeeds does `savedSeqRef >= editSeqRef` become true.
