In [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:852), `participants_shape == "solo"` sets `partner = None`, then calls `build_hot_context_solo`. In [hot_context_solo.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:256), it loads only the current user, checks `has_dyad_partner`, then sets `partner_user = {}` at line 263. The renderer prints `partner_share` and `partner_sharing_state` under “You” at [hot_context_solo.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:687), but never renders partner id/name. Tante Rosi’s prompt adapter also explicitly ignores dyadic inputs: [tante_rosi.py](/Users/user_c042661f/Documents/Veas/app/bots/tante_rosi.py:32).

Smallest safe fix: in `build_hot_context_solo`, call `resolve_dyad_partner`, fetch only partner identity fields from `users` plus that partner’s `user_bot_state.partner_share` for this bot, and render a minimal `## Your Partner` block. Do not pull partner memories, messages, distillations, pregnancy facts, or shareable summaries. The minimum prompt-visible fact should be: partner exists, name/id/timezone maybe, and partner sharing state.

**2. Technical Design**

I would build a new tool, not extend `schedule_checkin`. Existing `schedule_checkin` accepts arbitrary `user_id` in [tool_schemas.py](/Users/user_c042661f/Documents/Veas/tool_schemas.py:1410), and the implementation schedules exactly that id at [write_tools.py](/Users/user_c042661f/Documents/Veas/app/services/tools/write_tools.py:1658). That is the wrong surface for “only my dyad partner.” A new `schedule_partner_checkin` can have no free target user id:

`delay | local_when | when`, `nudge_note`, `reason`, `requested_by_user: bool` or `source: explicit_user_request | bot_judgment`.

Backend resolution must use `resolve_dyad_partner` from [partner_sharing.py](/Users/user_c042661f/Documents/Veas/app/services/partner_sharing.py:119), never names or supplied ids. If no dyad partner, reject with `no_dyad_partner`. If the user says “[REDACTED],” the tool can ignore the name except maybe validate it against the resolved partner name for UX.

`scheduled_jobs.context` should include:
`kind=partner_nudge`, `originating_user_id`, `originating_user_name`, `originating_bot_id`, `dyad_id`, `source`, `nudge_note`, `reason`, `privacy_boundary`, and maybe `originating_message_ids` for audit only. Do not include raw originator text.

I would implement this as a `scheduled_task`, not a `checkin`, unless the product explicitly wants it to supersede the recipient’s own pending check-in. Current `checkin` scheduling supersedes every pending check-in for that user at [checkins.py](/Users/user_c042661f/Documents/Veas/app/services/checkins.py:33), backed by one pending check-in per user at [0004_plan5_scheduled_jobs.sql](/Users/user_c042661f/Documents/Veas/migrations/0004_plan5_scheduled_jobs.sql:105). A partner nudge should not erase [REDACTED]’s unrelated reminder. `scheduled_task` already carries arbitrary briefs and fires into `run_agentic_job` with context at [scheduled_job_handlers.py](/Users/user_c042661f/Documents/Veas/app/services/scheduled_job_handlers.py:144).

Opt-out: treat the recipient partner’s `partner_share='opt_out'` as a hard block for partner-originated nudges in this bot. Pending should also block for autonomous nudges; for explicit requests, I’d still block and say the partner has not enabled that kind of cross-partner touch. The originator’s `opt_out` means the note cannot reveal their private content; explicit request allows a minimal operational note, but not a summary of what they said.

Add a unique/rate-limit index for pending partner nudges, probably expression-based on `(user_id, bot_id, context->>'kind', context->>'originating_user_id') WHERE status='pending' AND job_type='scheduled_task'`. Also add a softer daily limit in code per `(dyad_id, bot_id, target_user_id)` to prevent repeated autonomous nudges. Existing due-claim indexes are fine: [scheduled_jobs.py](/Users/user_c042661f/Documents/Veas/app/services/scheduled_jobs.py:108).

When it fires, the recipient’s hot context receives trigger metadata because scheduled handlers pass `context` into `run_agentic_job` [scheduled_job_handlers.py](/Users/user_c042661f/Documents/Veas/app/services/scheduled_job_handlers.py:149). The prompt should see `kind=scheduled_task`, `context.kind=partner_nudge`, `nudge_note`, and originator name. If this needs cleaner rendering, add a small “Partner nudge” block in solo hot context based on trigger metadata.

Scope: add tool to schedule phase. It writes in the current bot/topic scope, but targets the partner user id. That exception must be explicit in the tool implementation, because `check_write_scope` only verifies topic scope, not target user authorization.

**3. Prompt Design**

This should be a shared prompt slot across bots, like [partner_sharing.py](/Users/user_c042661f/Documents/Veas/app/bots/prompts/partner_sharing.py:6), with per-bot optional phrasing. The rules should say:

Handle “check on [REDACTED]” by acknowledging partner identity, naming the boundary, and using `schedule_partner_checkin` only if partner nudges are allowed. Never imply access to [REDACTED]’s private thread unless hot context actually contains shareable material.

Use judgment sparingly: distress, meaningful silence near a known event, asymmetric load, or practical support needs. Do not use it to triangulate conflict, apply pressure, or make the bot central.

`opt_out` blocks. `pending` blocks autonomous nudges and should usually prompt for the sharing choice instead.

`nudge_note` must be recipient-safe: “Pom asked me to check how you’re doing today” is acceptable; “Pom says you are being cold and he is spiraling” is not. If the reason depends on private material, store that only in audit `reason`, not recipient-facing note.

**4. Edge Cases**

Both partners nudging same day is fine if rate-limited per target and surfaced neutrally. Do not merge notes in a way that reveals bidirectional private state.

Pending: block. This is a cross-partner action, not ordinary self scheduling.

Recipient opt-out: refuse cleanly: “I know [REDACTED] is your partner, but I can’t initiate that kind of check-in in her thread unless she has enabled it.”
