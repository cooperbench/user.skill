Here is a comprehensive summary of the full plan/triage process in desloppify. --- ## Plan Architecture Overview The plan system manages a prioritized work queue stored in `.desloppify/plan-{lang}.json`. The queue (`queue_order`) is a list of item IDs that can be real issue IDs, or synthetic IDs representing workflow checkpoints. The plan also tracks clusters (groups of related issues), skipped items, commit records, and triage metadata. --- ## Queue Item Types The queue contains four distinct ID namespaces: - **Real issue IDs** — actual findings from scans (e.g., `review::abc123`, `concerns::def456`) - **`subjective::<slug>`** — subjective dimension reviews (architecture, naming conventions, etc.) requiring human judgment - **`triage::<stage>`** — triage workflow checkpoints (`triage::observe`, `triage::reflect`, `triage::organize`, `triage::commit`) - **`workflow::<id>`** — onboarding workflow steps (`workflow::score-checkpoint` / `workflow::communicate-score`, `workflow::create-plan`, `workflow::import-scores`) --- ## Lifecycle Phases ### Phase 1: Onboarding (First-Run) When desloppify is first run on a codebase: 1. **Unscored subjective dimensions** are injected at the front of the queue unconditionally (`sync_unscored_dimensions`). These are dimensions like "naming conventions" or "architecture" that need a human score before any objective issue fixing makes sense. Each appears as `subjective::<dim-slug>`. 2. Once all unscored dimensions are complete (all have scores), **`workflow::communicate-score`** (formerly `workflow::score-checkpoint`) is injected — a prompt to review the current strict score before proceeding. 3. If there is an objective backlog and triage is not pending, **`workflow::create-plan`** is injected — a prompt to run `plan triage` and establish the working plan. ### Phase 2: Triage (When Review Issues Appear) Triage is triggered when `sync_triage_needed` detects that new open review/concerns issues exist that weren't present in the last triage snapshot. It injects the 4 triage stage IDs at the front of the queue. A banner is shown: `TRIAGE MODE — review issues need analysis before fixing. Run: desloppify plan triage` ### Phase 3: Normal Execution Once triage is complete, real issue IDs and stale subjective dimensions populate the queue. The user works through them via `desloppify next` and `desloppify plan resolve`. **Stale subjective dimensions** (`sync_stale_dimensions`) are re-injected: - At the back of the queue when no objective issues remain (mid-cycle) - At the front after a full cycle completes (post-cycle priority) --- ## The 4-Stage Triage Workflow This is the core of the plan's triage process.
