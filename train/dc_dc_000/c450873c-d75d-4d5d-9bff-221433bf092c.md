# Planning Assistant — Discord Bot Spec (Arnold)

A planning assistant for a single user that helps work epics to PM-handoff fidelity. The bot — named **Arnold** — maintains a body (the living deliverable), drives a flexible checklist of planning-process steps, investigates code from configured public GitHub codebases, generates images, and can request second opinions from non-Anthropic models. Primary surface is a **Discord bot** (resident mode); Arnold is also callable from any agentic process via CLI / Python / HTTP (invocation mode — see Execution Modes). The user can interact via text or voice messages; the user gives intent through natural language; Arnold runs operations end-to-end.

An epic is **planned** (handoff-ready) when the body is at PM-handoff fidelity AND it has been organized into 2-week sprints, each marked `queued` (ready to start, with execution order) or `pending` (deliberately deferred). "Planned" is the bot's terminal state — a downstream PM (or you in PM mode) takes each queued sprint and breaks it into its own plan when ready to execute.

## The unit: an "epic"
An epic = one goal-directed planning exploration that produces a **body** (the living deliverable doc) plus a **sprint breakdown**. Lifecycle states: `shaping` → `sprinting` → `planned` (terminal), with `paused`/`archived` off to the side.

## Generation — the `shaping` phase
The bot doesn't free-form write a plan. It maintains a **checklist** (spec lines 630–672) seeded with ~18 process items: validate premise → clarify goal/scope → surface non-technical critical question → identify principles → constraints → codebase research → structural design → behavioral details → scope reduction → pruning → disambiguation → failure modes → pre-mortem → PM-handoff readiness → elegance → second opinion → sequencing → sprint org.

Two important properties:
- **It's a guide, not a contract.** The bot adds, drops, reorders, and *re-runs* items as the epic evolves. Religious adherence is called out as a failure mode.
- **Each item has its own working depth** — the system prompt includes specific question banks per item (lines 676–800) so "scope reduction" and "elegance pass" mean concrete things, not vibes.

As items get worked, the **body** (markdown doc with structured sections like Goal / Principles / Constraints / Deliverable / Open Questions) is edited via `edit_epic`. Code investigations land in `code_artifacts`; images can be referenced into the body by key.

## Solidification — the gates and lock-in
There's no single "solidify" button. It's a state machine with **server-side gates** in `edit_epic` (lines 556–574):

**`shaping → sprinting` gate:**
- Body >500 chars with at least Goal + Deliverable
- Open checklist items are either materially worked or there are <3 left
- (default-on) recent second opinion exists

**`sprinting` then runs sprint shaping** (lines 1096–1134): bot proposes PM-task-level breakdown (~2-week chunks, items sized so a PM scopes each into 3–10 coder tasks), user pushes back, refines.

**`sprinting → planned` gate** — this is the real "solidification":
- Every sprint is `queued` (with unique `queue_position`) or `pending` (with optional `pending_reason`)
- All checklist items `done`/`skipped`/`superseded`
- Body at PM-handoff fidelity
- **Open-decisions lockdown scan**: a server-side regex sweeps the body for `TBD`, `to be decided`, `figure out later`, `we'll see`, `tunable`, etc. Matches inside the Open Questions section are fine; matches anywhere else block the transition. This is the spec's mechanical answer to "are decisions actually made?"
- (default-on) recent second opinion against the PM-handoff rubric

**The lock-in itself is a two-beat ritual in one turn** (line 1114+):
1. Bot asks "ready to lock these in?" — requires unambiguous affirmative ("yes"/"go ahead"); "I think so, but…" doesn't count.
2. Immediately proposes a queue/pend default (first sprint `queued` at position 1, others `pending`), user adjusts in natural language ("queue 1 and 2, pend 3", "do sprint 3 first"), bot prompts for `pending_reason` per pended sprint.

Once every sprint is `queued` or `pending`, the epic flips to `planned`. There is deliberately **no separate "finalized" intermediate state** — locking in *is* the queue/pend assignment.

## Escape hatches
- **Force-through**: user can bypass any gate; logged as a `forced_handoff` event with the list of bypassed conditions.
- **Re-opening**: a `planned` epic stays planned, but you can re-queue/re-pend sprints, reorder, or add a new sprint (bumps state back to `sprinting` for the addition, then back to `planned`).

## The mental model
Generation is *checklist-driven exploration that shapes a body*. Solidification is *a gated state machine where each transition is guarded by content checks (size, sections, lockdown regex) plus an explicit user affirmative*. The lockdown regex is the cleverest piece — it's the spec's way of detecting "you said you decided this but you actually punted" without needing the model to grade itself.
