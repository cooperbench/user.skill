Read-only review done. Recommendation: **do not introduce generic `user_journeys` yet**. For a first fitness/family-friend bot, `goals + measurements + progress summaries` is close, but the real minimum is: 1. **Bot/topic** - Add a solo `BotSpec`, e.g. `fitness` / `wellness`. - `primary_topic_slug="fitness"`, `participants_shape="solo"`. - `read_scopes={"own"}`, `allow_cross_topic_peek=True`, no cross-topic writes. - Reuse `hot_context_solo`, scheduling, per-bot pause/sharing, partner identity/nudge machinery. 2. **Goals** - Use existing primitives first: - `memories`: durable facts like injuries, equipment, dietary preferences, goals. - `themes`: broad domains like “building consistency”, “training around family life”, “confidence with food”. - `watch_items`: concrete follow-ups like “ask how Monday run went”. - `topic_status`: compact current fitness snapshot. - Do not create a `goals` table unless the product needs UI editing, status transitions, or multiple concurrent quantified goals. 3. **Measurements / logs** - This is the only possible new abstraction, but keep it narrow. - If “low-key progress” means conversational tracking, **do not add measurements yet**. Let raw messages be the log, and periodically summarize into `topic_status` / distillations. - If the bot must answer “show my trend for weight / workouts per week / 5k time”, add a small per-feature `fitness_measurements` table, not generic `user_journeys`. - Minimal shape: `user_id`, `metric_key`, `value_numeric`, `value_text`, `unit`, `observed_at`, `source_message_ids`, `note`, `created_by_bot_id`. 4. **Progress summaries** - Reuse `topic_status` for “where we are now”. - Reuse `distillations` for tentative synthesized progress narratives. - Use scheduled recurring `schedule_task` for weekly/monthly reflection/check-in summaries. - Avoid a separate `progress_summaries` table unless summaries need independent lifecycle, export, or UI history. What is missing from just “goals, measurements, progress summaries”: - **Cadence**: already handled by `scheduled_task` recurrence and `watch_items`. - **Constraints/preferences**: store as `memories` and OOB where sensitive. - **Workout/eating events**: don’t model every event as a durable artifact; raw messages plus summaries are enough at first. - **Family/friend sharing**: reuse per-bot `partner_share`, `dyad_shareable` summaries, and `schedule_partner_checkin`. Do not invent family/group participant state for v1. - **Safety/health caveat**: prompt-level boundaries, not schema. Bottom line: ship the bot as a new solo `BotSpec` on a `fitness` topic using the existing artifact stack. Add **only** a tiny `fitness_measurements` append-only table if numeric trend queries are truly required. Avoid reviving `user_journeys` until there are at least two or three bots with the same structured tracking needs.
