# Implementation Plan: `plan_checkpoint` Progression Event

## Context

The progression log (`progression.jsonl`) currently captures score snapshots redundantly across multiple event types:
- `scan_complete` — includes `scores`, `dimension_scores`, `prev_scores`, deltas
- `subjective_review_completed` — includes `scores`, `dimension_scores`
- `triage_complete` — includes `scores`
- `execution_drain` — includes `scores`

The idea: when plan mode finishes processing all subjective reviews and is about to transition toward execution, that's the canonical "take stock" moment. A single `plan_checkpoint` event should capture the comprehensive state snapshot, and the scattered `scores` fields in other events can eventually be thinned out.

## Trigger Point

The natural trigger is **after `mark_subjective_review_completed()` succeeds and the subsequent `reconcile_plan()` completes** in `app/commands/review/importing/plan_sync.py` (lines 275-291). This is the exact moment the subjective review queue is cleared. The reconciliation has already run, so we have the final display phase and lifecycle mode.

Today, a `subjective_review_completed` event is already emitted at this point (line 479-500). The new `plan_checkpoint` event would fire immediately after it.

## Files to Change

### 1. `desloppify/engine/_state/progression.py` — Add event builder

Add `build_plan_checkpoint_event()` with signature:

```python
def build_plan_checkpoint_event(
    state: dict[str, Any],
    plan: dict[str, Any],
    *,
    phase_before: str | None,
    trigger: str,
) -> dict[str, Any]:
```

**Payload fields:**
- `scores` — `_scores_snapshot(state)` (overall, objective, strict, verified_strict)
- `dimension_scores` — `_dimensions_snapshot(state)` (per-dimension score + strict)
- `plan_start_scores` — `plan.get("plan_start_scores", {})` (baseline reference)
- `previous_plan_start_scores` — `plan.get("previous_plan_start_scores", {})` (for delta context)
- `open_count` — `_open_issue_count(state)`
- `queue_summary` — counts of items by prefix in `queue_order` (objective, subjective, workflow, triage)
- `trigger` — what caused this checkpoint (extensible for future triggers)
- `resolved_since_last` / `skipped_since_last` — from execution log via `_execution_log_ids_since`

Reuses existing snapshot helpers — no new pure functions needed. Add to `__all__`.

### 2. `desloppify/app/commands/review/importing/plan_sync.py` — Fire the event

# Implementation Plan: `plan_checkpoint` Progression Event (v2)

## Context

The progression log (`progression.jsonl`) captures score snapshots redundantly across `scan_complete`, `subjective_review_completed`, `triage_complete`, and `execution_drain`. This adds a single canonical `plan_checkpoint` event — the primary progression record for "where are we now" — designed to eventually replace those scattered score fields.

## Revised Trigger Point

**Flag 1 fix:** The v1 plan hooked into `transition.subjective_review_marked`, which fires on any trusted import with covered keys — too broad. The correct boundary is when the reconcile pipeline's `sync_communicate_score_needed()` auto-resolves `workflow::communicate-score`. That function internally calls `_subjective_review_current_for_cycle()` (workflow.py:252-281), which is the repo's actual "current cycle no longer owes subjective review" predicate. It checks: no unscored dims, postflight scan matches current scan count OR review already marked complete, and no stale/under-target dims.

**Concretely:** The checkpoint fires in `plan_sync.py` after `save_plan()` (addressing Flag 2), gated on:
1. `transition.reconcile_result.communicate_score` is not None AND has `auto_resolved` — meaning `sync_communicate_score_needed()` fired this pass
2. This ensures reconciliation ran, scores were rebaselined, and the plan was saved before the event is logged

**Why `communicate_score.auto_resolved` is the right signal:** This is already the system's canonical "review boundary crossed" indicator. It gates on `_subjective_review_current_for_cycle`, only fires once per cycle (sentinel `previous_plan_start_scores` prevents re-fire), and only runs during reconciliation (which requires `was_boundary_ready` or `live_planned_queue_empty`). The checkpoint piggybacks on existing correctness guarantees.

**Also fire from scan path:** The same `sync_communicate_score_needed` runs inside `reconcile_plan()` during `reconcile_plan_post_scan()` (plan_reconcile.py:368-373). Add the same gated checkpoint emission after `save_plan()` at line 394. This handles cases where the scan itself is what crosses the boundary (e.g., postflight scan reveals no unscored dims remain).

# Implementation Plan: `plan_checkpoint` Progression Event (v3)

## Context

The progression log (`progression.jsonl`) captures score snapshots redundantly across `scan_complete`, `subjective_review_completed`, `triage_complete`, and `execution_drain`. This replaces those scattered score fields with a single canonical `plan_checkpoint` event — the sole score checkpoint in the progression log. The `scores` field is removed from all four existing event types (no production code reads it) and consolidated into `plan_checkpoint`.

## Trigger Point

The checkpoint fires in the **review import path only** (`plan_sync.py`), after `save_plan()`, gated on `reconcile_result.communicate_score.auto_resolved` being truthy.

**Why this is the correct boundary:** `sync_communicate_score_needed()` internally calls `_subjective_review_current_for_cycle()` (workflow.py:252-281) — the repo's actual "current cycle no longer owes subjective review" predicate. It checks: no unscored dims, postflight scan matches current scan count OR review already marked complete, and no stale/under-target dims. It only fires once per cycle (`previous_plan_start_scores` sentinel prevents re-fire), and only runs during reconciliation (which requires `was_boundary_ready` / `live_planned_queue_empty`).

**Why review-path only:** The scan path (`plan_reconcile.py`) has ordering complexities that make correct checkpoint emission non-trivial: `_clear_plan_start_scores_if_queue_empty()` can clear `plan_start_scores` and `previous_plan_start_scores` between reconciliation and save, and `save_plan()` failures are swallowed. The review path has neither of these problems — `save_plan()` is unconditionally called when dirty (and `communicate_score.auto_resolved` implies dirty), and no post-reconcile logic clears the rebaseline fields. Scan-path emission is deferred to a follow-up that can properly address the field ordering.

**Why review-path is the right first ship:** The original idea describes "when we're in plan mode and finish processing all subjective reviews" — that's the review import completing, not a scan. The scan path is a secondary trigger for edge cases where scans cross the boundary; the review path is the primary, natural moment.

# Implementation Plan: `plan_checkpoint` Progression Event (v4)

## Context

The progression log (`progression.jsonl`) captures score snapshots redundantly across `scan_complete`, `subjective_review_completed`, `triage_complete`, and `execution_drain`. This adds a single canonical `plan_checkpoint` event — the primary progression record for "where are we now" — designed as THE score checkpoint that will replace those scattered fields.

**Scope decision on score removal:** The user wants `plan_checkpoint` to be the sole canonical score checkpoint, with `scores` fields eventually removed from the other events. However, removing those fields requires checkpoint coverage on *all* paths that cross the review boundary — including the scan path. Since this PR ships review-path checkpoint only (scan-path has known ordering issues), the existing `scores` fields must remain until scan-path coverage is added in a follow-up. This PR establishes `plan_checkpoint` as canonical-by-design; the follow-up that adds scan-path emission will also strip scores from the other events.

## Trigger Point

The checkpoint fires in the **review import path only** (`plan_sync.py`), after `save_plan()`, gated on `reconcile_result.communicate_score.auto_resolved` being truthy.

**Why this is the correct boundary:** `sync_communicate_score_needed()` internally calls `_subjective_review_current_for_cycle()` (workflow.py:252-281) — the repo's actual "current cycle no longer owes subjective review" predicate. It checks: no unscored dims, postflight scan matches current scan count OR review already marked complete, and no stale/under-target dims. It only fires once per cycle (`previous_plan_start_scores` sentinel prevents re-fire), and only runs during reconciliation (which requires `was_boundary_ready` / `live_planned_queue_empty`).

**Why review-path only:** The scan path (`plan_reconcile.py`) has ordering complexities: `_clear_plan_start_scores_if_queue_empty()` can clear rebaseline fields between reconcile and save, and `save_plan()` failures are swallowed. The review path has neither problem. Scan-path emission is deferred to a follow-up.

# Implementation Plan: `plan_checkpoint` — The Canonical Score Checkpoint (v4)

## Context

The progression log (`progression.jsonl`) captures score snapshots redundantly across `scan_complete`, `subjective_review_completed`, `triage_complete`, and `execution_drain`. This replaces all of them with a single canonical `plan_checkpoint` event — the sole score checkpoint in the progression log.

## Core Idea: Gate communicate-score on subjective queue presence

The key design decision: **`sync_communicate_score_needed()` should only auto-resolve on the scan path when there are no subjective items in the queue.** This means:

- **Subjective items in queue** → communicate-score does NOT auto-resolve during scan reconciliation → it resolves later via the review import path → checkpoint fires from the clean review path
- **No subjective items in queue** → communicate-score auto-resolves during scan reconciliation → checkpoint fires from the scan path

This ensures every boundary crossing is covered by a checkpoint, and the common case (subjective reviews exist) always goes through the review path which has no ordering issues.
