        # Implementation Plan: VibeComfy Template Porting Workbench

## Overview
The remaining critique still does not show that the workbench is aimed at the wrong subsystem or root cause. The correct target remains a first-class `vibecomfy port ...` workflow over the existing conversion, schema, node-pack, model-asset, and ready-template machinery. The final refinements are execution details: use the actual default check mode for `scripts/sync_agent_skill.py`, and keep positional widget mapping based on widget-only order rather than raw `object_info` input order, because `object_info` includes link-only inputs that do not correspond to `widgets_values` positions.

The first useful slice is a package-level `vibecomfy.porting` workbench plus a discoverable CLI surface. `port check` should be the obvious cheap preflight before manual Python-template editing or expensive RunPod validation. `port convert` should emit Python-esque VibeWorkflow scratchpads by default, and ready-template-shaped modules only when `--ready-id` is supplied. Existing `vibecomfy convert`, `doctor`, `fetch`, and ready-template materialization contracts should remain compatible unless they explicitly opt into the new workbench APIs.

## Phase 1: Foundation - Report Shape, Source Loading, and Helper Semantics

### Step 1: Add a porting report model (`vibecomfy/porting/report.py`)
**Scope:** Medium
1. Define dataclasses for `PortReport`, `PortIssue`, `PortArtifact`, `NodePackSuggestion`, `AssetCandidate`, and `AssetCheckResult` with stable JSON serialization.
2. Include source id/path, detected workflow shape, source hash, normalized API node count, emitted Python path, output mode (`scratchpad` or `ready_template`), helper-node diagnostics, custom-node suggestions, unresolved runtime class types, model asset candidates, schema issues, widget alias observations, and recommended next commands.
3. Keep issue severities aligned with current validation concepts: `error`, `warning`, and `info`.

### Step 2: Centralize helper/UI-node classification (`vibecomfy/porting/helpers.py`, `vibecomfy/workflow.py`)
**Scope:** Medium
1. Move the helper-node class set and helper-resolution diagnostics into a reusable module that knows about `Note`, `MarkdownNote`, `SetNode`, and `GetNode`.
2. Add a diagnostic pass that inspects the original IR before compile and reports unresolved `GetNode` / `SetNode` broadcasts instead of letting compile silently skip dangling helper references.
3. Expose a helper-stripped runtime class view for downstream diagnostics so custom-node pack inference does not treat `Note`, `MarkdownNote`, `SetNode`, or `GetNode` as missing installable node packs.
4. Keep `VibeWorkflow.compile("api")` behavior compatible: resolved helper broadcasts still rewrite to direct links; helper nodes still do not survive into API prompts.

### Step 3: Add porting-only model asset analysis without changing legacy extractor contracts (`vibecomfy/porting/assets.py`, `vibecomfy/model_assets.py`)
**Scope:** Medium
1. Keep `extract_from_raw_workflow(...)` returning only URL-bearing dictionaries with `name`, `url`, and `subdir`, so existing `doctor` and `fetch` callers remain safe.
2. Add a new porting-only analyzer that merges URL-bearing assets from UI workflow `properties.models`, normalized API prompts, loaded scratchpad/ready-template metadata, and `READY_REQUIREMENTS`.
3. Add API-shaped filename discovery in the porting analyzer as `AssetCandidate` records with optional `url`, not as return values from `extract_from_raw_workflow(...)`.
4. Mark filename-only candidates without URLs as actionable warnings in the port report rather than passing them to legacy fetch/download code.
5. Factor shared subdir/name normalization helpers only if useful, while preserving the public behavior of `extract_from_raw_workflow(...)` and `entries_from_scratchpad_path(...)`.

## Phase 2: Python Emission and Compatibility Boundaries

### Step 4: Move reusable emission primitives without forcing ready-template semantics (`vibecomfy/porting/emitter.py`, `tools/format_as_python.py`, `tools/convert_ready_templates.py`)
**Scope:** Large
1. Extract reusable `_node(...)`-style emission primitives from `tools/format_as_python.py` into package code.
2. Preserve explicit node IDs, deterministic ordering, `_extras` for non-identifier inputs, registered input handling, and current override behavior.
3. Split package emission into two explicit modes:
   - `emit_scratchpad_python(...)`: default for `port convert`, emits `PORT_METADATA` or equivalent provenance, uses `WorkflowSource(... source_type="scratchpad")`, and does not require `READY_METADATA["ready_template"]`.
   - `emit_ready_template_python(...)`: used only when `--ready-id` is supplied or by ready-template tooling, emits `READY_METADATA`, `READY_REQUIREMENTS`, and `WorkflowSource(... source_type="ready_template")`.
4. Keep `tools/format_as_python.py` and `tools/convert_ready_templates.py` as compatibility wrappers around the ready-template emission mode.
5. Do not change the established `vibecomfy convert` contract in `vibecomfy/commands/convert.py`; the new explicit Python materialization behavior belongs to `vibecomfy port convert` first.

### Step 5: Preserve both conversion contracts (`vibecomfy/scratchpad_loader.py`, `vibecomfy/commands/convert.py`, `vibecomfy/commands/port.py`)
**Scope:** Medium
1. Leave existing lightweight scratchpad rendering available for compatibility.
2. Implement `port convert` without `--ready-id` as true scratchpad emission: `build()` returns a `VibeWorkflow` with scratchpad provenance and no ready-template metadata requirement.
3. Implement `port convert --ready-id kind/name` as ready-template candidate emission: `build()` returns a `VibeWorkflow` with ready-template metadata and structured requirements.
4. Default examples and docs to `out/scratchpads/...` so promotion to `ready_templates/` remains intentional.
5. Validate emitted Python by importing it, calling `build()`, compiling API, and running schema validation when available.
