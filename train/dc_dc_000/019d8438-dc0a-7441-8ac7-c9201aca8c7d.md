        # Implementation Plan: Atomic Timeline Config + Asset Registry Save

## Overview

Config (`timelines.config`) and asset registry (`timelines.asset_registry`) live on the same DB row but are saved via two independent RPCs. This creates a window where config references an unregistered asset (or vice versa). The fix: a new Supabase RPC that atomically updates both columns with version checking, wired through SupabaseDataProvider and useTimelinePersistence.

**Key insight from code review:** The load path is already joint (loadTimelineJsonFromProvider does `Promise.all` for both). The stableSignature already incorporates both config and registry. Only the *save* path is split. Individual asset registrations via `useAssetOperations.registerAsset()` must remain independent — they're fire-and-forget one-off operations from upload flows. The atomic save targets the periodic auto-save in `useTimelinePersistence.doSave()`, which saves config+registry together.

**Scope:** The config_version counter already gates config saves. The atomic RPC will bump config_version when *either* config or registry changes, maintaining one monotonic version. The poll sync and conflict retry paths need minor adjustments to carry registry through the atomic save, but the overall architecture stays the same.

## Phase 1: Database — New Atomic RPC

### Step 1: Create migration with `update_timeline_versioned` RPC
**Scope:** Small
1. **Create** `reigh-app/supabase/migrations/YYYYMMDDHHMMSS_add_atomic_timeline_save.sql` with a new RPC `update_timeline_versioned` that:
   - Accepts `p_timeline_id uuid`, `p_expected_version integer`, `p_config jsonb`, `p_asset_registry jsonb`
   - Updates both `config` and `asset_registry` columns atomically
   - Bumps `config_version = config_version + 1` with optimistic concurrency check (`WHERE config_version = p_expected_version`)
   - Returns `config_version` (same pattern as existing `update_timeline_config_versioned` in `20260326100000`)
   - Uses `security invoker` and `set search_path = public`
   - Grants execute to `authenticated` and `service_role`
2. **Do NOT** drop or modify `update_timeline_config_versioned` or `upsert_asset_registry_entry` — they remain for backward compatibility and one-off asset registrations.

```sql
create or replace function public.update_timeline_versioned(
  p_timeline_id uuid,
  p_expected_version integer,
  p_config jsonb,
  p_asset_registry jsonb
)
returns table (config_version integer)
language sql
security invoker
set search_path = public
as $$
  update public.timelines
  set
    config = p_config,
    asset_registry = p_asset_registry,
    config_version = timelines.config_version + 1,
    updated_at = timezone('utc', now())
  where timelines.id = p_timeline_id
    and timelines.config_version = p_expected_version
  returning timelines.config_version;
$$;

grant execute on function public.update_timeline_versioned(uuid, integer, jsonb, jsonb) to authenticated;
grant execute on function public.update_timeline_versioned(uuid, integer, jsonb, jsonb) to service_role;
```
