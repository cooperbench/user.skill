## Overview
Megaplan Cloud currently has the right separation for this sprint: cloud launch and provider behavior live under `megaplan/cloud/`, while chain milestone orchestration lives in `megaplan/chain.py`. The incident maps to five concrete touch points: the Dockerfile/template install path, cloud-chain launch preflight, chain base branch handling, idea-path resolution/provenance output, and Railway CLI scoping.

This should be one coherent hardening pass, not a redesign. Preserve local and ssh provider behavior, keep unit tests provider-free, and prefer explicit template/preflight helpers over project-local `cloud.yaml` workarounds.

## Phase 1: Runtime Image And Install Correctness

### Step 1: Harden the durable cloud Dockerfile (`megaplan/cloud/templates/Dockerfile`)
**Scope:** Small
1. Add `unzip` to the base apt package list because Bun’s installer needs it.
2. Add a clear runtime-agent install block for Bun and `@dexh/shannon@0.0.2` after Node/npm is installed.
3. Symlink `bun`, `shannon`, `codex`, and `claude` into `/usr/local/bin` from their actual install locations so non-interactive Railway shells and tmux sessions see stable commands.
4. Keep this in the built-in template, not in `cloud.yaml` snippets, because Claude routes are a supported Megaplan runtime path.

### Step 2: Refresh template tests (`tests/test_cloud_template.py`, `tests/test_cloud_docker_build.py`, `tests/fixtures/cloud/Dockerfile.v0.19.0`)
**Scope:** Small

3. Keep the existing golden test so accidental install drift remains visible.

## Phase 2: Agent Dependency Preflight

### Step 3: Add chain runtime dependency resolution helpers (`megaplan/chain.py` or new `megaplan/cloud/preflight.py`)
**Scope:** Medium
1. Build a pure helper that resolves each milestone’s effective phase map from `profile` plus `phase_model`, using the same profile primitives already available in `megaplan/profiles/__init__.py`.
2. Return a structured summary per milestone: label, profile, explicit phase overrides, resolved phase map, required agents, and runtime commands.
3. Map `claude` routes to Shannon runtime requirements: `shannon`, `bun`, `claude`, and `tmux`. Map `shannon` explicitly the same way. Map `codex` to `codex`. Map `hermes` to its provider/env requirements rather than a shell binary when applicable.
4. Include a warning field explaining that `cloud.yaml agents.default` only configures default agent routing and does not override explicit chain `profile` or `phase_model` selections.

### Step 4: Wire cloud launch preflight before remote start (`megaplan/cloud/cli.py`)
**Scope:** Medium
1. Before `_ensure_repo_checkout()` and uploads in `_run_chain_wrapper`, load the chain spec and run the dependency resolver.
2. For local prerequisites, validate chain spec path and idea path resolution before any provider command.
3. For remote prerequisites, execute one compact remote check after repo checkout and before tmux launch, e.g. `command -v shannon bun claude codex tmux`, based only on dependencies actually required by the resolved phase maps.
4. Check required env/secrets from `cloud.yaml` and provider settings before launch. At minimum block missing configured secrets; for resolved agents, report the env vars commonly required by that route (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, provider keys for Hermes/direct providers) without trying to authenticate live APIs.
5. Emit a precise `agent_deps_missing` or `cloud_preflight_failed` JSON error listing missing commands/env and the resolved phase map summary.

### Step 5: Add preflight tests (`tests/test_cloud_chain_wrapper.py`, optional new `tests/test_cloud_preflight.py`)
**Scope:** Medium
1. Test that a `profile: premium` chain resolves Claude/Shannon dependencies even when `cloud.yaml agents.default: codex`.
2. Test that missing remote `shannon`/`bun`/`claude`/`codex`/`tmux` blocks launch before starting the tmux chain session.
3. Test that the error message explicitly says `agents.default` does not override explicit profile/phase-model routing.
4. Test a pure Codex chain only requires `codex` and `tmux`.

## Phase 3: Branch-Isolated Chain Correctness

### Step 6: Add `base_branch` to chain spec parsing (`megaplan/chain.py`, `megaplan/cloud/templates/chain.yaml.example`)
**Scope:** Medium
1. Add `ChainSpec.base_branch: str = "main"` and parse optional top-level `base_branch` from YAML.
2. Reject empty or non-string `base_branch` values.
3. Include `base_branch` in status formatting and JSON summaries so provenance can report it.
4. Update the example chain spec to document the field.

### Step 7: Use base branch for git refresh, milestone branches, and PR base (`megaplan/chain.py`)
**Scope:** Medium
1. Replace `_refresh_main()` with a branch-parameterized helper such as `_refresh_base_branch(root, base_branch, ...)` while keeping the old behavior defaulting to `main`.
2. Use `base_branch` in `git fetch origin <base>`, `git checkout <base>`, and `git pull --ff-only origin <base>`.
3. Pass `base_branch` into milestone branch creation so new milestone branches are created from `base_branch`, not hardcoded `main`.
4. Pass `base_branch` into PR creation as `gh pr create --base <base_branch>`.
5. Keep `--no-git-refresh` as a developer escape hatch, but it should no longer be necessary for setup-branch chains.

### Step 8: Propagate cloud repo branch into chain base branch (`megaplan/cloud/cli.py`)
**Scope:** Medium
1. When `megaplan cloud chain` uploads a chain spec, ensure the remote spec has `base_branch` set to `cloud.yaml repo.branch` unless the chain spec already declares `base_branch`.
2. Prefer a structured YAML rewrite into the uploaded copy over mutating the user’s local spec file.
3. Launch `megaplan chain start --spec ...` against that uploaded normalized spec.
4. Record `base_branch` in the local marker file beside `remote_spec` and `started_at`.

### Step 9: Add branch tests (`tests/test_chain.py`, `tests/test_cloud_chain_wrapper.py`)
**Scope:** Medium

2. Update refresh tests to verify fetch/checkout/pull use the configured base.
3. Test milestone branch creation uses the base branch as the start point.
4. Test PR creation passes `--base <base_branch>`.
5. Test cloud-chain upload injects `repo.branch` as `base_branch` when absent and preserves an explicit chain `base_branch` when present.

## Phase 4: Cloud Chain Path And Launch UX

### Step 10: Make `--idea-dir` robust for repo-relative paths (`megaplan/cloud/cli.py`)
**Scope:** Small

4. Add tests for repo-relative idea paths and the duplicate-path failure case.

### Step 11: Print launch status and provenance (`megaplan/cloud/cli.py`, `megaplan/chain.py`)
**Scope:** Medium

2. Include: remote spec path, current milestone if known, chain base branch, repo URL/branch/workspace, Megaplan ref/install source, resolved phase map summary, uploaded idea count, and tmux/session status.
