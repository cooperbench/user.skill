> DEVELOPER

Does that all make sense? Can you just sense check that once more because it seemed very easy and quick. Was our codebase already very well structured before, why was that so easy?

> AGENT

Yes, it makes sense, but with an important caveat: this was easy because I only cut the first and most obvious seam, not because the whole app is now fully multi-bot.

Why it was easy:

- The core runner was already centralized in `agentic.py`. There was one obvious place where every turn goes through Phase A, delivery, then Phase B.
- Prompt rendering was already a function, `render_system_prompt(...)`, not scattered across the codebase.
- Tools were already centralized behind `READ_PHASE_TOOLS`, `WRITE_PHASE_TOOLS`, `call_tool`, and `to_anthropic_tools`.
- The transport layer was already separate enough: Discord ingestion/sending is mostly outside the agent loop.
- Settings already flowed through `get_settings()`, so adding `BOT_ID` was straightforward.

So the codebase already had good bones. The specific problem was that the generic runner still imported mediator-specific things directly. I moved those choices into a `BotSpec`.

What this does **not** solve yet:

- Different bots still share the same database model: users, partners, memories, observations, OOB, themes, etc.
- `partner_of(...)` still assumes exactly one partner, which is mediator-specific.
- Hot context is still mediator-shaped.
- Tool schemas and implementations are still global, though a bot can now choose subsets.
- Discord currently seeds/catches up configured partner users, not arbitrary bot/user groups.
- Prompt version storage still stores only `system_prompt_version`, not explicitly `bot_id`.

So: yes, the seam is real, but it is the outer agent-runner seam. It makes the runner stop knowing “I am the mediator bot.” It does not yet make the whole application fully tenant/multi-bot aware.

If your next bots are structurally similar enough, this may be sufficient for the next step. If they need different relationship models, different hot context, different user resolution, or different persistence, the next seam should probably be a broader runtime/profile object that owns:

`resolve_context`, `build_hot_context`, `render_prompt`, `read_tools`, `write_tools`, and possibly `on_turn_complete`.

The reason I kept this small is that it gets the existing bot-specific prompt/tools/tasks out of the runner without forcing a speculative abstraction before we know how different the next bots really are.

> DEVELOPER

So let's say if I want to add another bot that basically kind of has a different system prompt and different persona, and it still kind of records observations, memories, and partners, but they're more specific to me as opposed to our relationship. Would that all plug in nicely or how would you think about that?

> AGENT

Mostly yes, but I’d think about it as “same engine, different bot profile, same memory substrate” rather than a totally separate bot yet.

For the bot you described, the current seam should plug in reasonably well if:

- It still talks over Discord DMs.
- It still has a small known user set.
- It still benefits from `memories`, `observations`, `watch_items`, maybe `themes`.
- It can tolerate the current two-phase shape: respond first, then write state.
- It can use the existing tools, maybe with a narrower subset.
- “Partner” can either still mean the other person, or can be mostly ignored by the prompt/tools.

The thing that would not plug in cleanly is the current assumption that every user exists in a dyad. `partner_of(...)` still finds exactly one other user and the hot context/system prompt include relationship/cross-thread concepts. For a “personal Peter bot,” that is probably the next seam to cut.

I’d probably model it like this:

```text
app/bots/
  mediator.py        # relationship bot
  personal.py        # your personal bot
  base.py            # common BotSpec contract
```

The personal bot would define:

- its own system prompt/persona
- its own Phase A instruction
- its own Phase B instruction
- a tool subset, probably:
  - read: `search_messages`, `get_memories`, `get_observations`, `list_watch_items`, maybe `recent_activity`
  - write: `add_memory`, `update_memory`, `log_observation`, `update_observation`, `add_watch_item`, `schedule_checkin`, etc.
- maybe no OOB/bridge/escalation tools unless they still make sense

But before doing that cleanly, I’d add one more abstraction: make `BotSpec` own context building. Right now `agentic.py` still does this:

```python
partner = await partner_of(active_pool, user)
hot_context = await build_hot_context(active_pool, user, partner, ...)
```

For a personal bot, that should become something like:

```python
runtime_context = await bot_spec.build_turn_context(...)
system_prompt = bot_spec.render_system_prompt(runtime_context)
hot_context = bot_spec.render_hot_context(runtime_context)
```

That would let the mediator bot keep dyad/partner/cross-thread behavior, while the personal bot can say: “my subject is Peter; memories and observations are about Peter; no partner perspective unless explicitly configured.”

So the answer is: the work I just did is the right first step, but for your proposed bot I would make one more seam before adding it. The current `BotSpec` extracted prompt/tools/tasks. The next seam should extract “what world does this bot think it is operating in?” Mediator world is a dyad. Your personal bot world is probably a user-centric memory/journal/assistant world.
