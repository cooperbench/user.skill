Design and implement a process monitoring/observation mechanism for MegaLoop.

## Problem

MegaLoop currently runs a command, waits for it to complete, then analyzes the output. But many real workloads are long-running (training runs, eval suites, deploy pipelines) where you want to CHECK IN periodically — read logs, check metrics, decide whether to continue or kill early.

The agent needs a way to: (1) launch a process, (2) periodically observe its output/logs/artifacts while it runs, (3) decide based on observations whether to let it continue, kill it early, or intervene.

## Design questions to resolve

1. **Wait/sleep mechanism**: Should the loop use a sleep-then-check pattern? A tool that blocks for N seconds then returns control? A polling loop? What's the right primitive for an agentic system that needs to observe a process over time?

2. **Observation strategy**: How does the agent read partial output? Options: tail the log file, read the last N lines of stdout, check for specific artifact files, poll a metrics endpoint. What's the right abstraction?

3. **Break conditions**: How does the agent decide to break? LLM-judged (read the output, decide if it looks stuck/diverging/done)? Metric-based (extract a number, compare to threshold)? Both?

4. **Skill integration**: The megaloop skill doc drives the orchestration. How should the observation/monitoring phase integrate with the existing plan→execute cycle? Is it a sub-phase of execute? A separate phase? A tool the execute sub-agent uses?

5. **Implementation**: What's the minimal code to add to megaplan/loop/ to support this? A new tool? A modification to run_execute_phase? A wrapper around subprocess that yields control periodically?

## What to learn from

- The existing megaplan/loop/engine.py run_execute_phase which currently runs subprocess to completion
- The /loop skill doc pattern for how the agent drives the loop
- autoresearch's pattern of fixed time budgets (5 min) — they just wait for completion but cap the time
- Common patterns in agentic systems for process monitoring (poll loops, callback hooks, signal files)

## Constraints

- Must work within Claude Code's tool execution model (the agent calls tools, tools return results)
- Should be minimal — extend the existing loop infrastructure, don't rebuild it
- The agent should be able to check in at configurable intervals
- Must handle both fast processes (seconds) and slow ones (hours)

        Idea:
Design and implement a process monitoring/observation mechanism for MegaLoop.

## Problem

MegaLoop currently runs a command, waits for it to complete, then analyzes the output. But many real workloads are long-running (training runs, eval suites, deploy pipelines) where you want to CHECK IN periodically — read logs, check metrics, decide whether to continue or kill early.

The agent needs a way to: (1) launch a process, (2) periodically observe its output/logs/artifacts while it runs, (3) decide based on observations whether to let it continue, kill it early, or intervene.

## Design questions to resolve

1. **Wait/sleep mechanism**: Should the loop use a sleep-then-check pattern? A tool that blocks for N seconds then returns control? A polling loop? What's the right primitive for an agentic system that needs to observe a process over time?

2. **Observation strategy**: How does the agent read partial output? Options: tail the log file, read the last N lines of stdout, check for specific artifact files, poll a metrics endpoint. What's the right abstraction?

3. **Break conditions**: How does the agent decide to break? LLM-judged (read the output, decide if it looks stuck/diverging/done)? Metric-based (extract a number, compare to threshold)? Both?

4. **Skill integration**: The megaloop skill doc drives the orchestration. How should the observation/monitoring phase integrate with the existing plan→execute cycle? Is it a sub-phase of execute? A separate phase? A tool the execute sub-agent uses?

5. **Implementation**: What's the minimal code to add to megaplan/loop/ to support this? A new tool? A modification to run_execute_phase? A wrapper around subprocess that yields control periodically?

## What to learn from

- The existing megaplan/loop/engine.py run_execute_phase which currently runs subprocess to completion
- The /loop skill doc pattern for how the agent drives the loop
- autoresearch's pattern of fixed time budgets (5 min) — they just wait for completion but cap the time
- Common patterns in agentic systems for process monitoring (poll loops, callback hooks, signal files)

- Must work within Claude Code's tool execution model (the agent calls tools, tools return results)
- Should be minimal — extend the existing loop infrastructure, don't rebuild it
