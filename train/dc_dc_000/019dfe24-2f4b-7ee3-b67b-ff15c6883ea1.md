**Findings**

1. **Adaptive step insertion can put needed steps too late.**  
   [turn_plan.py](/Users/user_c042661f/Documents/Veas/app/services/turn_plan.py:85) `TurnPlan.add_steps()` always inserts before `done`, not after the current step or before the next semantically relevant step. If `read` adds `consult`, it lands after `respond/record/schedule`; if `respond` adds `read`, it runs after the response. That means `update_turn_plan` cannot reliably grant a step the tools/context it realized it needed.  
   Suggested fix: support insertion positions, e.g. `before_step="respond"` / `after_current=true`, or encode canonical ordering so `consult` inserted from `read` runs before `respond`.

2. **`quick_reply` and `crisis` can start in `respond` without enough tool access.**  
   [turn_plan.py](/Users/user_c042661f/Documents/Veas/app/services/turn_plan.py:13) starts `quick_reply` at `respond` and `crisis` at `respond`; [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:223) limits `respond` to `send_message_part`, `search_emojis`, and `check_oob`. If classification is too light, the model cannot call `search_messages`, `get_oob`, `get_bot_actions`, etc. before answering, and adding `read` via `update_turn_plan` would happen too late because of issue 1.  
   Suggested fix: either start more skeletons with `read`, allow safe read tools during pre-send `respond`, or add a planning/orient step that can revise the plan before any response step.

3. **`schedule` lacks the read surface needed to avoid duplicate or poorly grounded scheduling.**  
   [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:214) defines `SCHEDULE_TOOLS` as only schedule/list scheduled-task tools, and [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:230) gives `schedule` no `list_watch_items`, `search_messages`, or general read tools. The prompt says scheduling should be non-duplicative, but `list_scheduled_tasks` only covers `scheduled_task` rows, not check-ins/watch items. Hot context includes open watch items, but it can be dropped under budget pressure in [hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:654).  
   Suggested fix: allow at least `list_watch_items` in `schedule`, add a read/list tool for pending check-ins, and consider `READ_BEFORE_WRITE` requirements for `schedule_checkin` / `schedule_task`.

4. **Actual sent-summary is only explicitly handed to `record`, not `schedule`.**  
   [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:839) builds the actual sent summary after final send/OOB rewrite/reaction handling, but [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:850) only passes it when the next step is `record`; [base.py](/Users/user_c042661f/Documents/Veas/app/bots/base.py:81) also only appends it for `record`. `schedule` may need to know whether the user was actually told “I’ll check in later,” especially if `record` was removed or the final text was rewritten/withheld.  
   Suggested fix: pass the sent summary to all post-respond transitions, or store it on `TurnContext` and include it in both `record` and `schedule` step transition messages.

5. **Read-before-write enforcement is present but too coarse for some writes.**  
   [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:235) enforces reads by tool name only. For `update_theme`, either `list_themes` or `get_theme` satisfies the guard, so the model can update a specific theme after only seeing a summary list. Scheduling writes have no read-before-write guard at all.  
   Suggested fix: make guards operation-specific: require `get_theme` for `update_theme`, keep `list_themes` acceptable for `create_theme`, and add schedule-specific duplicate checks/read requirements.
