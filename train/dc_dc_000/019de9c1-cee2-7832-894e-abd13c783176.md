When the main conversational agent calls it, the orchestrator spawns a small bounded subagent (the "consult") that runs its own LLM loop using only the existing read-phase tools (no writes, no outbound sends, no escalations) and returns a structured advisory result back into the main agent's tool_use/tool_result chain. ## Repository Findings

Inspected the relevant repo paths:

- `tool_schemas.py` is the single source of truth for tool input/output Pydantic models and `TOOL_REGISTRY`.
- `app/services/tools/registry.py` owns `TOOL_DESCRIPTIONS`, `TOOL_DISPATCH`, `READ_PHASE_TOOLS`, `WRITE_PHASE_TOOLS`, `to_anthropic_tools()`, and `call_tool()` phase gating.
- `app/services/agentic.py` already has a reusable `run_phase()` loop, Anthropic client creation, spend-cap checks, cost recording, message/tool result plumbing, and hot-context rendering passed into the LLM phase.
- `TurnContext` currently does not carry `hot_context_rendered`, so the consult tool needs a small context extension.
- `evals.capture.record_tool_call()` already supports arbitrary `phase` strings, so inner consult calls can be tagged with `phase="consult"` once `TurnContext.phase` and registry gating allow it.
- Read tools enforce privacy/OOB context through `ctx.user`, `ctx.partner`, `protected_owner_ids`, and cross-thread sharing defaults.
- **Important asymmetry (flag-1):** `app/services/tools/read_tools.py::check_oob` only consults `args.protected_owner_ids`; it does **not** fall back to `ctx.protected_owner_ids`. The schema (`tool_schemas.py::CheckOOBInput`) documents that omission collapses to recipient-only. So a consult subagent that calls `check_oob` without explicitly passing the parent turn's protected owner IDs would silently weaken OOB enforcement. The plan below adds a consult-phase argument-defaulting step that closes this gap, scoped to the consult dispatch path so main-agent behavior is unchanged.

## Step 4: Close The OOB-Inheritance Gap For Consult Calls (addresses flag-1)

The consult subagent must inherit the parent turn's `protected_owner_ids` even when the model omits them from a tool call. We do this in the consult dispatch path only, so main-agent behavior is unchanged.

In `app/services/tools/registry.py`, add a small helper used **only when** `ctx.phase == "consult"`:

```python
_CONSULT_OWNER_INJECTING_TOOLS = {"check_oob"}

def _inject_consult_defaults(name: str, raw_args: dict[str, Any], ctx: TurnContext) -> dict[str, Any]:
    if ctx.phase != "consult":
        return raw_args
    if name in _CONSULT_OWNER_INJECTING_TOOLS and ctx.protected_owner_ids:
        merged = dict(raw_args or {})
        existing = merged.get("protected_owner_ids")
        if not existing:
            merged["protected_owner_ids"] = [str(uid) for uid in ctx.protected_owner_ids]
        else:
            seen = {str(x) for x in existing}
            for uid in ctx.protected_owner_ids:
                if str(uid) not in seen:
                    existing.append(str(uid))
                    seen.add(str(uid))
            merged["protected_owner_ids"] = existing
        return merged
    return raw_args
```

In `call_tool()`, after the `_phase_allowed` check and before `input_model.model_validate(raw_args)`, replace:

```python
args = input_model.model_validate(raw_args)
```

with:

```python
args = input_model.model_validate(_inject_consult_defaults(name, raw_args, ctx))
```

Notes:

- Scope: only `check_oob` needs this today, since other read tools either don't accept `protected_owner_ids` (e.g. `search_messages`, `recent_activity` — they read from `ctx.user`/`ctx.partner` directly) or already source protections from `ctx`. The set is a named constant so future tools can be added explicitly rather than by accident.
- The defaulting is additive: if the consult model passes a partial list, we union rather than overwrite, so it cannot strip protections; if it passes none, we inject the parent's full list.
- This change must not affect main read/write phases — guarded by the `ctx.phase == "consult"` check.

Add a focused test in `tests/test_tools.py` (or the new consult test file) that calls `call_tool("check_oob", {"content": ..., "recipient_id": ...}, ctx_with_consult_phase_and_protected_ids)` and asserts `check_oob_with_policy` was invoked with the inherited `protected_owner_ids`.

- No migration or new `consultations` table is added.
- No consult path can send messages, mutate DB state via write tools, escalate, or call itself recursively.

## Assumptions

- `TurnContext` can be extended with `phase="consult"` and `hot_context_rendered` without disrupting existing read/write tests.
- Parameterizing the existing `run_phase()` loop is preferred over duplicating agentic loop logic.
- Advisory JSON can be parsed from the consult model's final text and validated with Pydantic.
- Consult read tools should share the parent `turn_id` for observability.
- `check_oob` is the only read tool whose privacy posture today depends on a caller-supplied `protected_owner_ids`; other read tools derive privacy scope from `ctx`. If that ever changes, `_CONSULT_OWNER_INJECTING_TOOLS` is the named extension point.

## Open Questions

- Should `consult_model` have separate pricing fields if it may differ materially from `conversational_model`, or is the existing text LLM pricing acceptable for now?
- Should consult output allow empty `suggested_moves` / `caveats`, or require at least one item for successful advisory records?
