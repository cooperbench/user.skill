        Idea:
Drop-to-Generation feature. When user drags an image or video file anywhere over the app, show a new small drop zone above the GenerationsPane's control tab (the pane handle). Dropping there uploads the file as a new generation. For files >=50MB, keep the file local via FileSystemHandle persisted in IndexedDB, and only upload when a worker or timeline agent actually needs the bytes — the gallery displays the local file via blob URL in the meantime. Milestones: (1) Global drag detection + chip above pane tab (UI only, no drop action yet). (2) <50MB path — drop uploads via existing image/video uploaders + creates a generation with no shot attachment. (3) >=50MB path — FileSystemHandle + IndexedDB persistence, local-mode generation rows, thumbnail-only upload. (4) Media resolution — gallery displays local-mode generations via blob URL, with permission re-grant UX. (5) Lazy upload at task-build time for local-mode generations, with storage_mode flip. (6) Fallback path for browsers without FileSystemHandle API (Firefox/Safari force upload with warning). Research context already gathered — see arguments passed to megaplan-skill for concrete paths/lines (GenerationsPane.tsx, PaneControlTab.tsx, panesStore.ts, externalImageDrop.ts, imageUploader.ts, videoUploader.ts, storagePaths.ts, MediaGallery/types.ts). Key design decisions to flag as questions: (a) split threshold images 25MB / videos 100MB vs unified 50MB; (b) project-scoped vs user-scoped local handles; (c) precedence vs inner tool drop zones (stopPropagation); (d) handle invalidation when source file moves/renames; (e) whether to always upload small downsized thumbnails for local-mode gallery display without handle permission. Risks to call out: FileSystemHandle permission lifecycle (prompt state across reloads), Chromium-only API coverage, blob URL lifetime in React, lazy-upload failure modes mid-task-build, concurrent worker consumption of same local handle.
