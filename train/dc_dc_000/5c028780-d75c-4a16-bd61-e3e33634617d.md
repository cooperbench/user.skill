736	    direction = row["direction"] if "direction" in row else None
737	    sender_id = row["sender_id"] if "sender_id" in row else None
738	    recipient_id = row["recipient_id"] if "recipient_id" in row else None

742	        return recipient_id
743	    return sender_id or recipient_id

746	def _render_partner_pregnancy_state(
747	    partner_user: dict[str, Any], partner_name: str, clip_limit: int = 240
748	) -> str | None:
749	    """Render the one-line partner pregnancy summary for dyad hot context.
750	
751	    Per §4.1: this is the ONLY pregnancy data surfaced to the mediator.
752	    Never auto-bridges symptoms, themes, weight, or observations.
753	
754	    Returns None when there is nothing to render (no pregnancy, ended >90d,
755	    or data-corruption).
756	    """
757	    from datetime import date
758	
759	    pregnancy_edd = partner_user.get("pregnancy_edd")
760	    if pregnancy_edd is None:
761	        return None
762	
763	    pregnancy_ended_at = partner_user.get("pregnancy_ended_at")
764	
765	    # --- Ended pregnancy -------------------------------------------------
766	    if pregnancy_ended_at is not None:
767	        pregnancy_outcome = partner_user.get("pregnancy_outcome")
768	        if pregnancy_outcome is None or pregnancy_outcome not in ("loss", "termination"):
769	            return None
770	
771	        # Compute days since ended_at.
772	        if hasattr(pregnancy_ended_at, "date"):
773	            ended_date = pregnancy_ended_at.date()
774	        elif isinstance(pregnancy_ended_at, date):
775	            ended_date = pregnancy_ended_at
776	        else:
777	            return None
778	
779	        _today = date.today()
780	        days_ago = (_today - ended_date).days
781	        if days_ago > 90:
782	            return None
783	
784	        partner_label = _clip(partner_name, clip_limit)
785	        return (
786	            f"- {partner_label}'s pregnancy ended recently "
787	            f"(loss, {days_ago} days ago). Handle with care."
788	        )
789	
790	    # --- Active pregnancy ------------------------------------------------
791	    pregnancy_dating_basis = partner_user.get("pregnancy_dating_basis")
792	    if pregnancy_dating_basis is None:
793	        return None
794	
795	    try:
796	        weeks, days = _ga(pregnancy_edd)
797	    except (ValueError, TypeError):
798	        return None
799	
800	    edd_str = pregnancy_edd.isoformat() if hasattr(pregnancy_edd, "isoformat") else str(pregnancy_edd)
801	    partner_label = _clip(partner_name, clip_limit)
802	
803	    return f"- {partner_label} is currently {weeks}w{days}d pregnant (EDD {edd_str})."

And are there any premium and beddings approaches that are more expensive but very high quality?

Yes — three tiers of "premium" worth knowing about, and the most impactful one isn't actually a bigger embedding model:

1. **Bigger embedding model** (5-10× cost, modest gain). `text-embedding-3-large` ($0.13/1M), Voyage `voyage-3-large` (~$0.18/1M), Google `gemini-embedding-001` — all measurably better than `-3-small`, especially on multilingual text (so worth considering if Tante Rosi users write in German). Drop-in replacement. Maybe a 5-15% recall improvement on hard queries. Cost is still trivial at your volume.

2. **Reranking on top of cheap embeddings** (much higher impact than #1). Retrieve top-30 with cheap embeddings, then run them through a cross-encoder reranker (Cohere Rerank 3, Voyage `rerank-2`, or open-source BGE-reranker) to re-score to top-5. Rerankers actually compare query↔doc with attention, where embeddings just compare two pre-computed vectors. Typical gain is 20-40% on retrieval benchmarks — bigger than going from small→large embeddings. Cost is per-query (~$0.001-0.002 per reranked batch), so unlike embeddings the bill scales with turns, not corpus size. At 100 users × 30 turns/day, ~$1-3/day. This is what I'd reach for first if quality matters.

3. **Anthropic's contextual retrieval** (premium write-time, free query-time). Before embedding each artifact, prepend an LLM-generated one-sentence "this is about X in the context of Y" gloss, then embed. Published ~35% improvement, stacks with reranking. The cost is one cheap LLM call (Haiku) per artifact at write/update time, and unchanged query cost. Best fit if you want to invest once and have it pay off forever. Stacks with both #1 and #2.

Order of operations if you wanted to go premium: cheap embedding + rerank (biggest bang for buck) → add contextual retrieval if you want more → upgrade the embedding model last (smallest lift). # Megaplan tickets

Tickets are short, repo-scoped notes on problems, bugs, or "we should look at this" observations against a codebase. They live as committed `.md` files under `<repo>/.megaplan/tickets/` and (when a cloud store is configured) mirror to `tickets` / `ticket_epics` tables. Tickets are inert until folded into an epic — they capture problems, not work.

## When to file a ticket

Reach for `megaplan ticket new` when:
- During epic or plan execution you notice an **out-of-scope problem** that should be tracked but isn't blocking the current task.
- The user explicitly asks you to **capture an observation** ("file a ticket for that", "make a note of this for later").
- You want to log a rough edge or potential bug whose fix would be its own piece of work.

Do **not** use tickets for:
- Guidance/corrections to *how the tooling itself behaves* — that's `megaplan feedback` (a separate, plan-scoped concept).
- In-flight task state — that's the executor's own checklist.
- General notes or chat — write them in the conversation.

## Filing

```bash
megaplan ticket new "<title>" -b "<body>" [--tags tag1,tag2]
```

Conventions:
- `-b "..."`, `--edit` (open `$EDITOR`), and `-` (read body from stdin) are mutually exclusive; one is required.
- `ticket new` prints **only the ULID** on stdout on success (logs go to stderr). Capture it for piping.
- `--tags` is comma-separated. Tags are freeform; common ones: `bug`, `refactor`, `tech-debt`, `observability`, `docs`, `cross-repo`.
- `source` is auto-derived: if `MEGAPLAN_TURN_ID` is set (the agent is running under a megaplan-launched worker), `source=agent` and the turn id is recorded; otherwise `source=human`.
- The repo is resolved from cwd via its root commit SHA (`git rev-list --max-parents=0 HEAD`). Identity survives rename / transfer / remote change.

Multi-line body via stdin:
```bash
cat <<'EOF' | megaplan ticket new "Title here" --tags tag1,tag2 -
First paragraph of the body.

More detail in a second paragraph.
EOF
```

## What to put in the body

Tickets feed the **planner** at epic-prep time — the planner reads open tickets and uses them to shape new plans. A ticket that records only the conclusion forces the planner to re-derive the reasoning from scratch (or skip the ticket because it can't tell whether the framing still holds). A ticket that records the reasoning is picked up as durable context.

Aim for these sections when the ticket is non-trivial:

- **Goal / problem** — what's wrong or what we want, one paragraph.
- **Shape** — the proposed direction, concrete enough to argue with.
- **Decisions already made** — every choice that was settled in the discussion that produced the ticket, with a one-line *why*. Examples: "default runtime is OrbStack on Mac, because of bind-mount perf"; "credentials passed in via env vars, not auto-read from host, because that's the point." Capture these so the planner inherits them as settled, not as questions to reopen.
- **Alternatives considered and rejected** — only include rejections that *shaped* the chosen direction (i.e. a planner reading later might otherwise reopen that path). Each with a one-line *why not*. Skip obvious or tangential rejections — they're noise.
- **Constraints / what must keep working** — invariants the fix has to respect.
- **Open questions** — decisions deliberately deferred (call these out explicitly so they don't get mistaken for settled ones).

"Decisions already made" is the single most valuable section. A ticket without it forces the planner to re-derive the reasoning from scratch.

Skip sections that don't apply. For a small bug report, the goal + a repro is enough. The bar is: *would a planner reading this in three months have what they need to act, or would they have to ask the original author?*

## Editing and linking

Unlike `ticket new`, **`ticket edit --body` does NOT accept `-` for stdin** — passing `-` will land a literal `-` as the body. For multi-line edits, use one of:
- `--body "$(cat file.md)"` to inline a file's contents
- `--edit` to open the current body in `$EDITOR`

`link ... --resolves` marks the join with `resolves_on_complete=true`. When the linked epic transitions to `done`, the ticket auto-flips to `addressed` and gets a `resolution_note` referencing the epic. Idempotent — re-running on an already-addressed ticket is a no-op.

## Modes

Megaplan runs in one of two modes; tickets work transparently in both:

- **Local-only** (no cloud store configured) — `.md` files on disk are the sole source of truth. `codebase_id` will be `null` in frontmatter; identity is computed on demand from the repo's root SHA.
- **Cloud-configured** (`SUPABASE_DB_URL` or megaplan config points at a store) — every operation writes the `.md` file **and** mirrors to the `tickets` / `ticket_epics` tables. Auto-registers the codebase on first ticket if needed.

You do not need to detect the mode yourself; the CLI dispatches based on whether a store is configured.
