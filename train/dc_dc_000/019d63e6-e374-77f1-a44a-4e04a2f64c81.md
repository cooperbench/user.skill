        # Implementation Plan: Redesign Orchestrator Subagent Prompt

## Overview

The orchestrator subagent prompt (`megaplan/data/claude_subagent_appendix.md`) is the instructions given to a Claude Code subagent that autonomously runs the megaplan workflow. It's ~157 lines encoding the full state machine, phase rules, safeguards, breakpoints, and resume protocol in one dense block.

**Problem:** The prompt duplicates content from `instructions.md` (which is prepended via `bundled_global_file`), mixes concerns (routing logic, error handling, breakpoint format, session rules), and buries critical instructions in walls of text — making it unreliable for LLM execution.

**Approach:** Redesign the appendix as a well-structured prompt with clear sections, explicit decision trees per robustness level, and separation of "always do" vs "conditionally do" rules. The appendix should complement `instructions.md` (not duplicate it) since both are concatenated into the final skill file.

**Constraints:**
- The prompt is a markdown file loaded verbatim via `_claude_subagent_appendix()` and appended to the skill
- Template variables `{IDEA}`, `{PROJECT_DIR}`, `{AUTO_APPROVE}`, `{AUTO_APPROVE_FLAG}`, `{ROBUSTNESS}` are filled by the outer skill at launch time
- The prompt must work with the actual CLI commands and state machine in `workflow.py`
- LLM judgment is intentional — the goal is clarity, not programmatic rigidity

### Step 2: Redesign the prompt structure (`megaplan/data/claude_subagent_appendix.md`)
**Scope:** Large — this is the core deliverable
1. **Write** the redesigned prompt with these clearly separated sections:

   **Section 1: Role & Mission** (~5 lines)
   - One-paragraph role definition: you are the autonomous megaplan runner
   - Template variables block (project, idea, mode, robustness)
   - Prime directive: operate through CLI, check status after every phase, follow orchestrator_guidance

   **Section 2: Startup Protocol** (~10 lines)
   - Exact init command
   - Capture plan name
   - First status check

   **Section 3: Phase Routing by Robustness Level** (~25 lines)
   - Three separate, explicit flowcharts (not prose):
     - **Light:** `plan → critique → revise → finalize → execute` (no gate, no review, no iteration)
     - **Standard:** `plan → critique → gate → [revise → critique → gate]* → finalize → execute → review`
     - **Heavy:** `prep → plan → critique → gate → [revise → critique → gate]* → finalize → execute → review`
   - Decision tree for gate outcomes: PROCEED → finalize, ITERATE → revise (loop), ESCALATE → breakpoint
   - Explicit note: at light robustness, revise routes directly to finalize (skips gate)

   **Section 4: After Every Phase (Always Do)** (~10 lines)
   - Run `megaplan status --plan <name>`
   - Check `notes_count` — if > 0, read notes and treat as authoritative
   - Use `next_step`/`valid_next` for routing, `orchestrator_guidance` after gate
   - This section is short and emphasized because it's the most critical operational rule

   **Section 5: Breakpoints — When and How to Stop** (~20 lines)
   - Table or list of breakpoint types with exact trigger conditions:
     - `GATE_ESCALATE`: gate returned ESCALATE
     - `EXECUTE_APPROVAL`: finalize succeeded + review mode
     - `PHASE_ESCALATE`: phase failed after fresh retry
     - `EXECUTE_ESCALATE`: 3 consecutive execute calls with no new completions
   - Exact breakpoint output format with example
   - Explicit: in auto-approve happy path, never break out

   **Section 6: Resume Protocol** (~10 lines)
   - After receiving SendMessage: re-read status, apply user input
   - After relaunch (kill-and-inject): start from CLI state + notes, not memory
   - Decision mapping: approval → execute, gate answer → continue/override/replan/abort

   **Section 7: Safeguards** (~10 lines)
   - Non-execute phase failure: retry once with `--fresh`, then PHASE_ESCALATE
   - Same error twice → force `--fresh` on next retry
   - Execute no-progress: 3 consecutive calls without new completions → EXECUTE_ESCALATE

   **Section 8: Overrides & Tools** (~10 lines)
   - When to use each override (add-note, force-proceed, replan, abort)
   - Step editing commands

   **Section 9: Execution Details** (~10 lines)
   - Auto-approve vs review mode flags
   - Per-batch execution protocol
   - Session rules (persistent default, --fresh, --ephemeral)

   **Section 10: Completion Format** (~5 lines)
   - Exact output template

   **Section 11: Outer Skill Handling** (~10 lines)
   - How the outer skill launches, relays breakpoints, handles kill-and-inject

2. **Remove** content that duplicates `instructions.md` — especially the full command reference (already in instructions.md lines 97-117), detailed phase rules (lines 29-34), and override descriptions (lines 65-76).

3. **Apply** prompt engineering best practices:
   - Use numbered lists for sequential procedures, bullet lists for options
   - Bold key terms and command names
   - Use `> IMPORTANT:` callouts for the 2-3 most critical rules
   - Keep each section self-contained so the LLM can reference it without reading the whole prompt
   - Put the most important operational rule (check status after every phase) early and repeated
