## What it is

MegaLoop automates the run → observe → diagnose → fix → run again cycle. It's NOT a literal while loop — it's an agentic process where the loop state machine drives the agent through phases, and sub-agents do the deep work. The main thread stays high-level: reading summaries, updating the plan, dispatching workers.

## Key design requirements

1. Two phases: plan and execute, cycling. The first plan phase captures the loop spec (goal, command, success criteria, allowed changes, optimization strategy, bug-finding approach, philosophy). Subsequent plan phases UPDATE the spec based on what the last execution found. Execute runs the command, observes results, spawns sub-agents to investigate/fix, and produces structured iteration results. Then back to plan.

2. State machine grounding. The loop spec is a living document — it captures the goal, how we measure success, what strategies to use, known issues, tried-and-failed approaches, current best results. This is continuously updated as we iterate. It's the compressed context that makes iteration 50 as informed as iteration 1.

3. Sub-agents for all deep work. The main thread orchestrates. Sub-agents investigate failures, fix code, compare results. Reuse megaplan's existing worker dispatch (run_step_with_worker with Claude/Codex/Hermes routing).

4. Strong bias to continue. The default is to keep going. Only pause for genuine decision points (risky changes, genuinely stuck, goal met).

5. Git integration. Commit before each fix. If results are worse, revert. Branch tip = best known state. Like autoresearch.

        # Implementation Plan: MegaLoop — Iterative Agent Loop

## Overview

MegaLoop automates the **run → observe → diagnose → fix → run again** cycle as a two-phase (plan/execute) agentic loop inside the megaplan codebase. The loop spec is a living JSON document that captures compressed context — goal, success criteria, strategies, known issues, tried-and-failed approaches — keeping iteration N as informed as iteration 1.

**Current repo shape:** megaplan is a ~3,500-line Python package with a 7-phase planning pipeline (plan → critique → gate → finalize → execute → review), three-way worker dispatch (Claude/Codex/Hermes via `run_step_with_worker`), atomic I/O, session management, and a CLI built on argparse subparsers. MegaLoop will live alongside this as a `megaplan/loop/` subpackage, reusing workers, I/O, and CLI patterns but with its own simpler state machine.

**Key constraints:**
- Two phases cycling (plan → execute → plan → ...), not megaplan's seven
- Sub-agents for deep work; main thread orchestrates via summaries
- Git integration: commit before fix, revert if worse
- Strong bias to continue — only pause for genuine decision points
- Minimal new code — intelligence in prompts, not Python

**Worker integration strategy (addresses type-mismatch-planstate and prompt-override-bypass):** The loop does NOT pass `LoopState` directly to `run_step_with_worker`. Instead, a thin adapter function `run_loop_worker` in `megaplan/loop/engine.py` (1) builds the prompt via `megaplan/loop/prompts.py`, (2) constructs a minimal PlanState-shaped dict with the two fields workers actually access at runtime (`config.project_dir` and `sessions`), (3) passes `prompt_override` to bypass the prompt builder dispatch tables, and (4) uses new `STEP_SCHEMA_FILENAMES` entries for `loop_plan`/`loop_execute` to satisfy the schema lookup at `workers.py:668`/`717`. This avoids touching shared worker code while keeping the loop self-contained.

**Patterns borrowed from autoresearch:** Single measurable goal, git as experiment log, program.md-style spec as agent instructions, keep/revert based on metric, radical simplicity.

**Patterns borrowed from MEGALOOP.md vision:** Setup conversation → structured spec, per-iteration structured results, spec as compressed history, sub-agents for depth, conversation checkpoints.

## Phase 1: Foundation — Types, State, Spec Format

### Step 1: Define the loop spec and state types (`megaplan/loop/types.py`)
**Scope:** Small
1. **Create** `megaplan/loop/__init__.py` (empty) and `megaplan/loop/types.py`.
2. **Define** `LoopSpec` TypedDict — the living document:
   ```python
   class LoopSpec(TypedDict, total=False):
       goal: str                    # What we're trying to achieve
       command: str                 # The command to run each iteration
       success_criteria: list[str]  # How we know we're done
       allowed_changes: list[str]   # Files/dirs the agent may edit
       strategy: str                # Current optimization approach
       philosophy: str              # Guiding principles for the agent
       known_issues: list[str]      # Issues discovered so far
       tried_and_failed: list[str]  # Approaches that didn't work
       current_best: dict           # Best result so far (metric, iteration, commit)
       iteration_budget: int        # Max iterations before pausing
       time_budget_seconds: int     # Per-iteration time limit for command
   ```
3. **Define** `LoopState` TypedDict:
   ```python
   class LoopState(TypedDict, total=False):
       name: str
       phase: str                   # "plan" | "execute"
       iteration: int
       spec: LoopSpec
       history: list[IterationResult]
       created_at: str
       config: PlanConfig           # Reuse megaplan's PlanConfig (provides project_dir)
       sessions: dict[str, SessionInfo]  # Provides session tracking for workers
       status: str                  # "running" | "paused" | "done" | "failed"
       pause_reason: str
   ```
   **Note:** `config` and `sessions` are structurally compatible with PlanState's fields of the same names. This is intentional — it allows the adapter in Step 3 to extract these two fields for worker dispatch without transformation.
4. **Define** `IterationResult` TypedDict:
   ```python
   class IterationResult(TypedDict, total=False):
       iteration: int
       command_output: str          # Truncated stdout/stderr
       command_exit_code: int
       metric_value: float | str | None
       diagnosis: str               # Sub-agent's analysis
       fix_description: str         # What was changed
       fix_commit: str              # Git commit SHA
       outcome: str                 # "improved" | "regressed" | "unchanged" | "error"
       reverted: bool               # True if fix was reverted
       files_changed: list[str]
       duration_seconds: float
       cost_usd: float
   ```

## Phase 2: Core Loop Engine

### Step 3: Implement the loop state machine and worker adapter (`megaplan/loop/engine.py`)
**Scope:** Medium
1. **Create** `megaplan/loop/engine.py` with these functions:
   - `init_loop(name, goal, command, project_dir, args) -> LoopState` — creates initial state, persists to `.megaplan/loops/{name}/state.json`
   - `run_loop_worker(step, state, plan_dir, args, root) -> WorkerResult` — **the adapter function** that bridges LoopState to the worker dispatch:
     ```python
     def run_loop_worker(step: str, state: LoopState, plan_dir: Path, args, root: Path) -> WorkerResult:
         # Build prompt from loop's own prompt system
         prompt = build_loop_prompt(step, state)
         # Construct minimal PlanState-shaped dict with the 2 fields
         # that run_claude_step/run_codex_step actually access at runtime:
         #   state["config"]["project_dir"] (workers.py:667, 716)
         #   state["sessions"] (workers.py:671, 719)
         shim_state: dict = {
             "config": state["config"],      # PlanConfig with project_dir
             "sessions": state["sessions"],   # Session tracking
         }
         result, agent, mode, refreshed = run_step_with_worker(
             step, shim_state, plan_dir, args,
             root=root, prompt_override=prompt,
         )
         # Update session tracking back into LoopState
         if result.session_id:
             key = session_key_for(step, agent)
             state["sessions"][key] = {"id": result.session_id, ...}
         return result
     ```
     **Why this works:** `prompt_override` bypasses the prompt builder dispatch tables (`workers.py:681`, `723`), so `create_claude_prompt`/`create_codex_prompt` are never called. The schema lookup at `workers.py:668`/`717` uses the new `STEP_SCHEMA_FILENAMES` entries from Step 2. The only PlanState fields accessed at runtime are `config` and `sessions`, which the shim provides. The `state["idea"]` accesses at `workers.py:257`/`295`/`327` are only in mock functions — these need mock payloads registered (see Step 8).
   - `run_plan_phase(state, plan_dir, args, root) -> LoopState` — calls `run_loop_worker("loop_plan", ...)`, parses the spec update from the response, merges into `state.spec`.
   - `run_execute_phase(state, plan_dir, args, root) -> LoopState` — runs the command, captures output, calls `run_loop_worker("loop_execute", ...)` to diagnose/fix, manages git commit/revert.
   - `should_continue(state) -> bool` — checks: goal met? budget exhausted? agent requested pause?
   - `run_loop(state, plan_dir, args, root) -> LoopState` — the outer driver: alternates plan/execute phases until `should_continue` returns False.
2. **Git integration** in `run_execute_phase`:
   ```python
   # Before fix: commit current state
   git_commit(project_dir, f"megaloop: pre-fix checkpoint (iteration {n})")
   # Dispatch fix sub-agent via adapter
   result = run_loop_worker("loop_execute", state, ...)
   # After fix: commit the fix
   fix_sha = git_commit(project_dir, f"megaloop: fix iteration {n}")
   # Re-run command, compare metric
   if metric_worse(new_result, state["spec"]["current_best"]):
       git_revert(project_dir, fix_sha)
       result["reverted"] = True
   ```
3. **Sub-agent routing** defaults to Claude for `loop_plan`, Codex for `loop_execute` (matching megaplan's pattern), configurable via `--agent` and `--phase-model`.

### Step 4: Implement git helpers (`megaplan/loop/git.py`)
**Scope:** Small
1. **Create** `megaplan/loop/git.py` with thin wrappers:
   - `git_commit(project_dir, message) -> str | None` — stages all changes in `allowed_changes` paths, commits, returns SHA. Returns None if nothing to commit.
   - `git_revert(project_dir, commit_sha) -> None` — `git revert --no-edit <sha>`.
   - `git_current_sha(project_dir) -> str` — returns HEAD SHA.
   - `parse_metric(output, pattern) -> float | None` — extracts a numeric metric from command output using a regex or last-line convention.
2. **Constraint:** Only stage files matching `spec["allowed_changes"]` globs — never `git add -A`.

### Step 5: Build prompts for plan and execute phases (`megaplan/loop/prompts.py`)
**Scope:** Medium
1. **Create** `megaplan/loop/prompts.py` with prompt builders:
   - `build_loop_prompt(step, state) -> str` — dispatches to `build_plan_prompt` or `build_execute_prompt` based on step name.
   - `build_plan_prompt(state) -> str` — includes: goal, current spec, last N iteration results (compressed), what's been tried, what's worked. Asks the agent to update the spec and decide the next action.
   - `build_execute_prompt(state, command_output) -> str` — includes: goal, spec, command output, allowed changes. Asks the agent to diagnose the issue and fix it.
2. **Context management:** The spec IS the compressed history. The prompt includes the spec (always) plus the last 3-5 iteration results (recent context). Older results are only represented through their impact on the spec (known_issues, tried_and_failed, current_best).
3. **These prompts are self-contained** — they are NOT registered in megaplan's `_CLAUDE_PROMPT_BUILDERS` / `_CODEX_PROMPT_BUILDERS` dispatch tables. They are passed via `prompt_override` through the adapter in Step 3.

## Phase 2: Core Loop Engine

### Step 3: Implement the loop state machine and worker adapter (`megaplan/loop/engine.py`)
**Scope:** Medium
1. **Create** `megaplan/loop/engine.py` with these functions:
   - `init_loop(name, goal, command, project_dir, args) -> LoopState` — creates initial state, persists to `.megaplan/loops/{name}/state.json`
   - `run_loop_worker(step, state, plan_dir, args, root) -> WorkerResult` — **the adapter function** that bridges LoopState to the worker dispatch:
     ```python
     def run_loop_worker(step: str, state: LoopState, plan_dir: Path, args, root: Path) -> WorkerResult:
         # Build prompt from loop's own prompt system
         prompt = build_loop_prompt(step, state)
         # Construct minimal PlanState-shaped dict with the 2 fields
         # that run_claude_step/run_codex_step actually access at runtime:
         #   state["config"]["project_dir"] (workers.py:667, 716)
         #   state["sessions"] (workers.py:671, 719)
         shim_state: dict = {
             "config": state["config"],      # PlanConfig with project_dir
             "sessions": state["sessions"],   # Session tracking
         }
         result, agent, mode, refreshed = run_step_with_worker(
             step, shim_state, plan_dir, args,
             root=root, prompt_override=prompt,
         )
         # Update session tracking back into LoopState
         if result.session_id:
             key = session_key_for(step, agent)
             state["sessions"][key] = {"id": result.session_id, ...}
         return result
     ```
     **Why this works:** `prompt_override` bypasses the prompt builder dispatch tables (`workers.py:681`, `723`), so `create_claude_prompt`/`create_codex_prompt` are never called. The schema lookup at `workers.py:668`/`717` uses the new `STEP_SCHEMA_FILENAMES` entries from Step 2. The only PlanState fields accessed at runtime are `config` and `sessions`, which the shim provides. The `state["idea"]` accesses at `workers.py:257`/`295`/`327` are only in mock functions — these need mock payloads registered (see Step 8).
   - `run_plan_phase(state, plan_dir, args, root) -> LoopState` — calls `run_loop_worker("loop_plan", ...)`, parses the spec update from the response, merges into `state.spec`.
   - `run_execute_phase(state, plan_dir, args, root) -> LoopState` — runs the command, captures output, calls `run_loop_worker("loop_execute", ...)` to diagnose/fix, manages git commit/revert.
   - `should_continue(state) -> bool` — checks: goal met? budget exhausted? agent requested pause?
   - `run_loop(state, plan_dir, args, root) -> LoopState` — the outer driver: alternates plan/execute phases until `should_continue` returns False.
2. **Git integration** in `run_execute_phase`:
   ```python
   # Before fix: commit current state
   git_commit(project_dir, f"megaloop: pre-fix checkpoint (iteration {n})")
   # Dispatch fix sub-agent via adapter
   result = run_loop_worker("loop_execute", state, ...)
   # After fix: commit the fix
   fix_sha = git_commit(project_dir, f"megaloop: fix iteration {n}")
   # Re-run command, compare metric
   if metric_worse(new_result, state["spec"]["current_best"]):
       git_revert(project_dir, fix_sha)
       result["reverted"] = True
   ```
3. **Sub-agent routing** defaults to Claude for `loop_plan`, Codex for `loop_execute` (matching megaplan's pattern), configurable via `--agent` and `--phase-model`.

**Scope:** Medium
