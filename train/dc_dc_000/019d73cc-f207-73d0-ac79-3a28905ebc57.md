        # Implementation Plan: Fix Planning Lifecycle — Real In-Progress State, Status Enrichment, Doc Parity

## Overview

Megaplan's planning lifecycle has four honest gaps:

1. **No in-progress indicator**: When a worker (plan, prep, critique, etc.) is running, `state.json` still shows the *previous* completed state (e.g. `initialized`). Status reports the plan as idle when it's actively working. There is no `active_step` concept.

2. **Status is anemic**: `handle_status` (`cli.py:82-95`) returns `state`, `iteration`, `next_step`, `valid_next`, and artifact list. It doesn't expose session metadata, cost accumulation, last step duration, or whether a worker is currently running.

3. **`watch` is documented but unimplemented**: README:91, `instructions.md:116` both reference `megaplan watch --plan <name>`. No parser entry, no handler, no implementation exists.

4. **Standard/light planning collapses investigation into a black box**: Heavy robustness runs `init → prep → plan`. Standard overrides `initialized` to skip directly to `plan` (`workflow.py:76-78`). This means the planning agent silently does all codebase investigation inside the plan step with no visible prep artifact and no way to inspect what it found before the plan is generated.

5. **Subagent command reference is stale**: `claude_subagent_appendix.md:247-273` omits `list` and `watch` from the command reference. Phase routing instructions only show `prep` for heavy.

### Design constraint
The idea explicitly says: "Do not force execute-style checkpointing or batch semantics onto planning." The fix should be lightweight metadata — not task tracking, batch numbering, or progress percentages applied to planning phases.

### Key verified facts
- **Prep is already consumed by planning**: `_plan_prompt()` (`prompts/planning.py:87`) calls `_render_prep_block(plan_dir)` which reads `prep.json` from disk (`prompts/_shared.py:124-252`). Adding prep to standard/light will produce an artifact that the plan step actually reads. (Settles FLAG-002/scope.)
- **`resolve_agent_mode()` is side-effect-free**: `workers.py:1142-1227` resolves agent, mode, refreshed, and model from args/config without running any worker. It can be called before `_run_worker` to populate `active_step`. (Settles FLAG-001/correctness.)
- **Status response consumers are additive**: The subagent reads `state`, `next_step`, `valid_next` from status output by name. Adding new fields is non-breaking. (Settles callers-1.)
- **Execute already calls `resolve_agent_mode` early**: `handle_execute` (`handlers.py:1069`) resolves agent before dispatch. Active-step can be set between resolution and dispatch. (Settles callers-2 for execute.)
- **Tiny critique stubs without calling `_run_worker`**: `handle_critique` (`handlers.py:741-791`) takes a fast path that creates a stub critique. Active-step must only be set on the real-worker path, not the stub path. (Settles all_locations.)

### Step 2: Wire active_step lifecycle around worker execution (`megaplan/handlers.py`, `megaplan/workers.py`)
**Scope:** Medium

The approach: call `resolve_agent_mode()` before the worker runs (it's already side-effect-free per `workers.py:1142`), set `active_step`, then pass the resolved tuple through to `run_step_with_worker` via its existing `resolved` parameter so the agent isn't resolved twice.

1. **Add** a helper `_set_active_step(plan_dir, state, step, agent)` in `handlers.py` that sets `state["active_step"]` and calls `save_state(plan_dir, state)`.
2. **Add** a helper `_clear_active_step(state)` that does `state.pop("active_step", None)` (no save — the caller saves).
3. **Refactor** `_run_worker` (`handlers.py:135-149`) to accept an optional `resolved` tuple and pass it through to `run_step_with_worker`:
   ```python
   def _run_worker(
       step, state, plan_dir, args, *, root, iteration=None,
       resolved=None,
   ):
       failure_iteration = state["iteration"] if iteration is None else iteration
       try:
           return worker_module.run_step_with_worker(
               step, state, plan_dir, args, root=root, resolved=resolved,
           )
       except CliError as error:
           record_step_failure(plan_dir, state, step=step, iteration=failure_iteration, error=error)
           raise
   ```
4. **In `_finish_step`** (`handlers.py:174`), add `_clear_active_step(state)` before the existing `save_state` call at line 213. This ensures active_step is cleared atomically with the state update on success.
5. **In the `except` path of `_run_worker`**, add `_clear_active_step(state)` before `record_step_failure` so failures also clear the marker. `record_step_failure` already calls `save_state`.
6. **Instrument each handler** that calls `_run_worker` — resolve agent first, set active_step, pass resolved through. For each handler:

   - **`handle_plan`** (`handlers.py:667`): Add before line 672:
     ```python
     resolved = worker_module.resolve_agent_mode("plan", args)
     _set_active_step(plan_dir, state, "plan", resolved[0])
     ```
     Change `_run_worker` call to pass `resolved=resolved`.

   - **`handle_prep`** (`handlers.py:713`): Same pattern — resolve, set, pass.

   - **`handle_critique`** (`handlers.py:734`): The handler has two paths:
     - **Tiny stub path** (line 741-791): No worker runs, so do NOT set active_step. The stub path already resolves the agent at line 771 for history recording. No active_step needed.
     - **Real worker path** (line 792+): Agent is already resolved at line 794 (`agent_type, mode, refreshed, model = resolve_agent_mode("critique", args)`). Set active_step after resolution, before the parallel or sequential worker dispatch.

   - **`handle_revise`**: Same resolve-set-pass pattern as plan/prep.

   - **`handle_gate`**: Same pattern.

   - **`handle_finalize`**: Same pattern.

   - **`handle_execute`** (`handlers.py:1055`): Agent is already resolved at line 1069. Add `_set_active_step(plan_dir, state, "execute", agent)` after the resolution and rework-refresh check (after line 1072), before the dispatch call. `_clear_active_step` happens in the dispatch functions' success path — both `dispatch_execute_one_batch` and `dispatch_execute_auto_loop` call `_finish_step` or `save_state` at the end. Add `_clear_active_step(state)` before their final `save_state` calls, or wrap the dispatch in try/finally in `handle_execute`.

   - **`handle_review`**: Same resolve-set-pass pattern. Review has multiple branches (parallel vs sequential, needs_rework vs approved) but all ultimately go through `_finish_step` or explicit `save_state`. `_clear_active_step` in `_finish_step` covers the normal path; add it to the error/exception paths.

7. **Safety net**: For handlers where active_step might leak on unexpected exceptions, wrap the worker invocation section in a `try/finally` that ensures `_clear_active_step` is called. The `finally` only clears in-memory; the next `save_state` (in `_finish_step` or error recording) persists it.
