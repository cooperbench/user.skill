## Phase 1: Schema And Shared State

### Step 1: Add onboarding schema and user model support (`migrations/0005_plan6_ops.sql`, `app/models/user.py`, `tests/conftest.py`)
**Scope:** Small
1. Create a forward migration adding `users.onboarding_state text NOT NULL DEFAULT 'pending'` with a check constraint for `pending|welcomed|seeded|complete`.
2. Add targeted indexes only if queries need them; no broad indexing is needed for two users.
3. Extend `upsert_user`/`fetch_user_by_id` only where needed without changing the frozen `User` dataclass unless runtime code needs the field frequently.
4. Update `FakePool` user rows to default `onboarding_state='pending'` and handle updates/selects used by onboarding and admin tests.

### Step 2: Add welcome-message constants and first-inbound gate (`app/services/onboarding.py`, `app/services/inbound.py`, `app/services/messaging.py` if needed)
**Scope:** Medium
1. Add a short `WELCOME_MESSAGE` constant in a dedicated `app/services/onboarding.py` module.
2. In `process_inbound`, after whitelist user upsert and before/after inbound insert, check `users.onboarding_state`; for `pending`, call `send_outbound(pool, user, WELCOME_MESSAGE)` and update state to `welcomed`.
3. Keep this independent from the coalescer so the welcome is immediate and the normal agentic turn still processes the user’s message.
4. Make the state transition idempotent with a conditional update such as `WHERE id=$1 AND onboarding_state='pending'`, so webhook retries cannot send duplicate welcomes.
5. Add tests for first whitelisted inbound sends once, sets `welcomed`, and duplicate delivery does not send again.

### Step 3: Put onboarding state in hot context (`app/services/hot_context.py`, `tests/test_hot_context.py`)
**Scope:** Small
1. Extend `_user_profile` to select `onboarding_state` with a fallback for test rows.

3. Add a focused hot-context test proving the state is visible to the prompt.

## Phase 3: Feedback And WhatsApp Reactions

### Step 7: Handle WhatsApp reaction webhooks (`app/services/inbound.py`, `tests/fixtures/whatsapp/reaction_*.json`, `tests/test_whatsapp_webhook.py`)

## Phase 4: Spend Caps And Graceful Degradation

### Step 8: Add spend threshold warnings (`app/services/spend.py`, `app/routers/admin.py`, `tests/test_spend.py`)
**Scope:** Medium

2. Log a distinguished `WARNING` exactly once per provider/day after crossing the threshold. The simplest durable implementation is to add columns to `llm_spend_log` such as `warned_80_at timestamptz`; if avoiding schema churn is preferred, admin can infer warning state from totals, but “once” logging is harder.
3. Update the admin Spend page to show recent per-provider totals, caps, percent used, and an 80% warning marker.
4. Add unit tests for under threshold, crossing threshold, and already-warned behavior.

### Step 9: Make all provider caps enforced at call sites (`app/services/agentic.py`, `app/services/transcription.py`, `app/services/vision.py`, `app/services/scoring.py`, `app/services/oob_check.py`, `tests/test_llm_phase.py`, `tests/test_media.py`)
**Scope:** Medium
1. Text: keep the existing pre-call checks in `_create_message_with_retry`, but update `_run_agentic` so `SpendCapExceeded` before any outbound sends one graceful message once: “I’m running into limits today, will catch up tomorrow.” Then mark/leave the triggering messages so they can be recovered or queued without repeated spam.
2. Vision: verify the existing cap behavior remains in place and add a test that the downstream assistant context leads to the “describe it” fallback if not already covered.
3. Transcription: add `is_under_cap(pool, 'transcription')` before `_groq_transcribe`; on cap hit, update the message content to the documented fallback text or media metadata, enqueue the coalescer so the assistant can respond conversationally, and do not call Groq.
