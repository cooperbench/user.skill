        # Implementation Plan: VibeComfy Template Porting Workbench

## Overview
VibeComfy already has the raw pieces of a template-porting workflow: `convert`, `validate`, `doctor`, schema-backed validation, model asset extraction, node pack install planning, generated ready-template rendering in `tools/format_as_python.py`, and WanAnimate-specific regression tests. The first useful slice should not be a separate app or a raw JSON runner. It should promote these scattered checks into a first-class CLI/tooling path that imports a Comfy workflow, emits a Python VibeWorkflow scratchpad/ready-template, preserves provenance, and reports the failures that currently cost RunPod time: missing node packs, bad/missing model URLs, unresolved helper nodes, positional widget alias drift, and missing required schema inputs.

The simplest approach is to build a package-level `vibecomfy.porting` workbench and a `vibecomfy port ...` CLI command that reuses existing code rather than inventing a second converter. `tools/format_as_python.py` is the current best emitter, but because it lives under `tools/`, the reusable core should move into package modules while the old tool remains as a thin compatibility driver.

## Phase 1: Foundation — Shared Port Report and Python Emission

### Step 1: Add a porting report model (`vibecomfy/porting/report.py`)
**Scope:** Medium
1. Define small dataclasses for `PortReport`, `PortIssue`, `PortArtifact`, and `AssetCheckResult` with stable JSON serialization.
2. Include fields for source path/id, detected workflow shape, source hash, normalized API node count, emitted Python path, custom-node pack suggestions, unresolved class types, model assets, schema issues, helper-node rewrites, and widget alias observations.
3. Keep issue severities aligned with existing validation semantics: `error`, `warning`, `info`.

### Step 2: Move reusable emitter logic into package code (`vibecomfy/porting/emitter.py`, `tools/format_as_python.py`)
**Scope:** Medium
1. Extract the reusable portions of `tools/format_as_python.py` into package code, preserving deterministic output, explicit node IDs, `_node(...)` helper behavior, `_extras` for non-identifier inputs, and `READY_METADATA` / `READY_REQUIREMENTS` emission.
2. Keep `tools/format_as_python.py` and `tools/convert_ready_templates.py` as wrappers around the package API so existing workflows still work.
3. Reuse `tools/_widget_schema.py` by moving it to `vibecomfy/porting/widget_schema.py` or exposing a package import path, then update old tool imports.

### Step 3: Add a workbench orchestrator (`vibecomfy/porting/workbench.py`)
**Scope:** Medium
1. Implement `analyze_source(...)` to load a workflow via `load_workflow_json`, `normalize_to_api`, and `convert_to_vibe_format`, using `get_schema_provider("auto")` when available.
2. Implement `emit_python_scratchpad(...)` that writes a Python-esque VibeWorkflow scratchpad, not a wrapper that re-loads the original JSON at runtime.
3. Preserve provenance in `READY_METADATA`: source path/id, source hash, original shape, conversion timestamp or converter version, source workflow id when known, and whether schema was available.
4. Populate `READY_REQUIREMENTS` from inferred requirements plus extracted structured model assets.

## Phase 2: Diagnostics — Catch Current Failure Classes Before RunPod

### Step 4: Custom node pack inference (`vibecomfy/porting/workbench.py`, `vibecomfy/node_packs_install.py`)
**Scope:** Small
1. Reuse `missing_class_types_for_workflow(...)` and `missing_packs_for_workflow(...)` to report installable packs and unresolved class types.
2. Include pack repo, pip packages, and matched classes in the port report.
3. Surface unresolved classes as hard errors for `port check` and warnings for `port convert --allow-unresolved`.

### Step 5: Model asset inference and HEAD checks (`vibecomfy/model_assets.py`, `vibecomfy/porting/assets.py`)
**Scope:** Medium
1. Reuse `extract_from_raw_workflow(...)` and `entries_from_scratchpad_path(...)` to collect structured model assets.
2. Add an opt-in URL checker using `httpx.Client().head(..., follow_redirects=True)` with deterministic timeout and no download body.
3. Report status codes, redirected final URL, missing URL fields, duplicate asset targets, and license-gated/404 cases as actionable report entries.
4. Keep HEAD checks disabled in normal unit tests and local conversion unless `--head-check-models` is passed.

### Step 6: Helper-node resolution diagnostics (`vibecomfy/workflow.py`, `vibecomfy/porting/workbench.py`)
**Scope:** Medium
1. Keep existing compile-time stripping/rewriting for `Note`, `MarkdownNote`, `SetNode`, and `GetNode`.
2. Add a report pass that counts removed UI-only nodes and lists unresolved `GetNode` / `SetNode` references whose broadcast source cannot be resolved.
3. Treat dangling helper rewrites as `error` because they create links to absent runtime nodes.
4. Add a narrow helper classification extension point for future reroute/broadcast nodes without changing runtime compile behavior for unknown classes.

### Step 7: Positional widget alias detection (`vibecomfy/porting/widget_aliases.py`, `vibecomfy/ingest/normalize.py`, `vibecomfy/workflow.py`)
**Scope:** Large
1. Centralize positional widget alias logic so `normalize_to_api`, `VibeWorkflow.compile`, and the Python emitter use the same mapping source.
2. Prefer schema-derived input order from `object_info` when available; fall back to the committed static widget schema for offline operation.
3. Add a diagnostic pass that compiles the workflow, compares emitted input names against schema inputs, and reports unresolved `widget_N` inputs where a required named input is missing.
4. Move the existing Wan/WanAnimate aliases out of the private `_POSITIONAL_WIDGET_ALIASES` map in `workflow.py` into the shared module, preserving current behavior.

### Step 8: Schema preflight integration (`vibecomfy/schema/validate.py`, `vibecomfy/commands/validate.py`, `vibecomfy/commands/doctor.py`)
**Scope:** Medium
1. Reuse existing `missing_required_input`, `unknown_input`, `unknown_class_type`, `invalid_link_shape`, and type mismatch checks in the port report.
2. Add optional `--port-report` or shared formatter support so `validate` / `doctor` can show the same actionable categories without duplicating logic.
3. Keep `validate` focused and cheap; make the fuller workbench report the new `port check` path.

## Phase 3: CLI and Live Validation Loop

### Step 9: Add explicit CLI entry points (`vibecomfy/commands/port.py`, `vibecomfy/commands/__init__.py`)
**Scope:** Medium
1. Register a new explicit command module in `COMMANDS`.
2. Add `python -m vibecomfy.cli port check <workflow> [--json] [--head-check-models]` to analyze without writing.
3. Add `python -m vibecomfy.cli port convert <workflow> --out out/scratchpads/name.py [--json] [--head-check-models]` to emit Python and include the report.
4. Add `--ready-id kind/name` for users intentionally creating a ready-template-shaped module under `ready_templates/`.
5. Return nonzero for hard errors: unresolved class types, unresolved helper broadcasts, schema-required missing inputs, failed Python build, or failed emitted scratchpad validation.

### Step 10: Wire into the run/RunPod preflight (`vibecomfy/commands/run.py`, `scripts/runpod_corpus_matrix.py`)
**Scope:** Medium
1. Before queueing a workflow, keep existing `workflow.validate(schema_provider=...)` as the hard gate.
2. Add a cheap port-report summary to `doctor` and RunPod matrix logs so future failures show whether they are model URL, custom-node, schema, or helper-node problems.
3. Do not make network HEAD checks mandatory for `run`; keep them opt-in via `port check --head-check-models` and in targeted preflight jobs.
4. In RunPod corpus matrix logs, copy the emitted scratchpad and port report next to the existing convert/validate logs.

## Phase 4: Battle Tests and Documentation

### Step 11: Add focused unit and CLI tests (`tests/test_porting_workbench.py`, `tests/test_cli.py`, `tests/test_workflow_core.py`, `tests/test_schema.py`)
**Scope:** Medium
1. Test a simple fixture based on `image/z_image` or a tiny synthetic workflow: check report shape, provenance, Python emission, import/build, compile, and validate.
2. Test the current WanAnimate production-parity template id `video/wanvideo_wrapper_22_wan_animate_preprocess_kijai`: helper nodes must not survive compiled API, no dangling links to removed nodes, node packs include WanAnimate/SAM/KJ/VHS requirements, and model assets include detection assets.

### Step 12: Document the first slice and roadmap (`docs/template_porting_workbench.md`, `docs/adding_templates_models.md`)
**Scope:** Small
1. Document the new import → convert → check → validate loop.
2. Show the recommended commands for a source workflow, a generated scratchpad, a ready-template candidate, and the WanAnimate battle test.
3. Record the remaining roadmap: richer source discovery, broader helper-node catalog, schema snapshots per node-pack version, automatic PR-ready manifest edits, and optional CI job for URL HEAD checks.

        # Implementation Plan: VibeComfy Template Porting Workbench

## Overview
The critique does not show that the idea is targeting the wrong subsystem. The root cause is still that VibeComfy has the needed pieces split across `convert`, `doctor`, schema validation, node-pack planning, model asset extraction, and ready-template generation. The plan should stay centered on a first-class `vibecomfy port ...` workflow, but the implementation order must change: helper/UI nodes must be diagnosed separately from custom-node pack inference, model asset extraction must cover API-shaped sources as well as UI workflows, widget alias migration must include the parity tools, and existing `convert` behavior must remain compatible.

The first useful slice is a package-level `vibecomfy.porting` workbench plus a discoverable CLI surface. It should make `port check` the obvious cheap preflight before manual Python-template editing or expensive RunPod validation, while `port convert` emits Python-esque VibeWorkflow scratchpads/ready-template candidates rather than relying on the original JSON as the steady-state artifact. Existing lightweight `convert` and ready-template materialization paths should be preserved unless explicitly routed through the new porting command.

## Phase 1: Foundation — Report Shape, Source Loading, and Helper Semantics

### Step 1: Add a porting report model (`vibecomfy/porting/report.py`)
**Scope:** Medium
1. Define dataclasses for `PortReport`, `PortIssue`, `PortArtifact`, `NodePackSuggestion`, and `AssetCheckResult` with stable JSON serialization.
2. Include source id/path, detected workflow shape, source hash, normalized API node count, emitted Python path, helper-node diagnostics, custom-node suggestions, unresolved runtime class types, model assets, schema issues, widget alias observations, and recommended next commands.
3. Keep issue severities aligned with current validation concepts: `error`, `warning`, and `info`.

### Step 2: Centralize helper/UI-node classification (`vibecomfy/porting/helpers.py`, `vibecomfy/workflow.py`)
**Scope:** Medium
1. Move the helper-node class set and helper-resolution diagnostics into a reusable module that knows about `Note`, `MarkdownNote`, `SetNode`, and `GetNode`.
2. Add a diagnostic pass that inspects the original IR before compile and reports unresolved `GetNode` / `SetNode` broadcasts instead of letting compile silently skip dangling helper references.
3. Expose a helper-stripped runtime class view for downstream diagnostics so custom-node pack inference does not treat `Note`, `MarkdownNote`, `SetNode`, or `GetNode` as missing installable node packs.
4. Keep `VibeWorkflow.compile("api")` behavior compatible: resolved helper broadcasts still rewrite to direct links; helper nodes still do not survive into API prompts.

### Step 3: Expand model asset extraction coverage (`vibecomfy/model_assets.py`, `vibecomfy/porting/assets.py`)
**Scope:** Medium
1. Keep existing UI-workflow extraction from node `properties.models`.
2. Add API-shaped extraction from node class types and input fields using the same subdir rules already used for structured requirements.
3. Merge assets from raw UI JSON, normalized API prompts, loaded scratchpad/ready-template metadata, and `READY_REQUIREMENTS` without duplicates.
4. Mark assets inferred from filenames without URLs as actionable warnings so API prompt sources are not falsely reported as having complete URL provenance.

## Phase 2: Python Emission and Compatibility Boundaries

### Step 4: Move reusable ready-template emitter logic without breaking current callers (`vibecomfy/porting/emitter.py`, `tools/format_as_python.py`, `tools/convert_ready_templates.py`)
**Scope:** Large
1. Extract reusable `_node(...)`-style Python emission from `tools/format_as_python.py` into package code.
2. Preserve explicit node IDs, deterministic ordering, `_extras` for non-identifier inputs, `READY_METADATA`, `READY_REQUIREMENTS`, registered input handling, and current override behavior.
3. Keep `tools/format_as_python.py` and `tools/convert_ready_templates.py` as compatibility wrappers around the package emitter.
4. Do not change the established `vibecomfy convert` contract in `vibecomfy/commands/convert.py`; the new explicit Python materialization behavior belongs to `vibecomfy port convert` first.

### Step 5: Preserve both conversion contracts (`vibecomfy/scratchpad_loader.py`, `vibecomfy/commands/convert.py`, `vibecomfy/commands/port.py`)
**Scope:** Medium
1. Leave existing lightweight scratchpad rendering available for compatibility.
2. Implement `port convert` as the path that emits explicit Python VibeWorkflow construction from a loaded source workflow.
3. Support ready-template-shaped output with `--ready-id kind/name`, but default examples and docs to `out/scratchpads/...` so promotion to `ready_templates/` remains intentional.
4. Validate emitted Python by importing it, calling `build()`, compiling API, and running schema validation when available.

## Phase 3: Diagnostics — Catch Current Failure Classes Before RunPod

### Step 6: Add the workbench orchestrator (`vibecomfy/porting/workbench.py`)
**Scope:** Large
1. Implement `analyze_source(...)` to load ready ids, scratchpads, raw JSON paths, and indexed workflow references through existing loader/normalizer paths.
2. Preserve provenance in `READY_METADATA`: source path/id, source hash, original shape, source workflow id when known, converter version, and whether schema was available.
3. Run helper diagnostics before custom-node inference.
4. Run custom-node pack inference against the helper-stripped runtime class view, while reporting unresolved helper broadcasts separately as helper errors.
5. Reuse `workflow.validate(schema_provider=...)` for schema issues and include formatted `missing_required_input`, `unknown_input`, `unknown_class_type`, `invalid_link_shape`, and type mismatch results in the report.

### Step 7: Custom node pack inference (`vibecomfy/porting/workbench.py`, `vibecomfy/node_packs_install.py`)
**Scope:** Small
1. Reuse `resolve_node_packs(...)` / `missing_packs_for_workflow(...)` concepts, but pass only runtime-relevant class types after helper filtering.
2. Include pack name, repo, pip packages, and matched classes in the port report.
3. Treat unresolved runtime class types as hard `port check` errors.
4. Treat known helper/UI classes as helper diagnostics, never as missing custom-node packs.

### Step 8: Model URL HEAD checks (`vibecomfy/porting/assets.py`)
**Scope:** Medium
1. Add opt-in URL checking with `httpx.Client().head(..., follow_redirects=True)` and a deterministic timeout.
2. Report status code, final redirected URL, missing URL fields, duplicate asset targets, and license-gated/404 cases.
3. Do not download model bodies.
4. Keep HEAD checks disabled in ordinary tests, `validate`, `doctor`, and `run` unless `--head-check-models` is explicitly passed.

### Step 9: Positional widget alias detection and shared schema source (`vibecomfy/porting/widget_schema.py`, `vibecomfy/porting/widget_aliases.py`, `vibecomfy/ingest/normalize.py`, `vibecomfy/workflow.py`, `tools/_compile_equivalence.py`)
**Scope:** Large
1. Move the committed widget schema and `resolve_widget_name(...)` into package code.
2. Update `normalize_to_api`, `VibeWorkflow.compile`, the package emitter, `tools/format_as_python.py`, `tools/convert_ready_templates.py`, and `tools/_compile_equivalence.py` to use the same package-level widget schema/alias source.
3. Prefer schema-derived input order from `object_info` when available; fall back to the committed static widget schema when offline.
4. Add a diagnostic pass that compares compiled API inputs against schema inputs and reports unresolved `widget_N` inputs where a required named input is missing or where parity tooling would otherwise see false drift.
5. Move existing Wan/WanAnimate positional aliases out of private workflow-only state while preserving current behavior.

## Phase 4: CLI, Discoverability, and Live Validation Loop

### Step 10: Add explicit CLI entry points (`vibecomfy/commands/port.py`, `vibecomfy/commands/__init__.py`)
**Scope:** Medium
1. Register `port` as an explicit command in `COMMANDS`.
2. Add `python -m vibecomfy.cli port check <workflow> [--json] [--head-check-models]` for no-write preflight.
3. Add `python -m vibecomfy.cli port convert <workflow> --out out/scratchpads/name.py [--json] [--head-check-models] [--ready-id kind/name]` for explicit Python output.
4. Make command help explain when to use `port check`, `port convert`, `doctor`, `validate`, `nodes install-plan`, and `--head-check-models`.
5. Return nonzero for hard errors: unresolved runtime class types, unresolved helper broadcasts, schema-required missing inputs, failed Python build, failed emitted scratchpad validation, or failed model HEAD checks when the user requested them.

### Step 11: Wire the live validation loop without making network checks mandatory (`vibecomfy/commands/doctor.py`, `vibecomfy/commands/run.py`, `scripts/runpod_corpus_matrix.py`)
**Scope:** Medium
1. Keep existing `workflow.validate(schema_provider=...)` as the hard gate before queueing runtime prompts.

**Scope:** Medium

2. Update authoring and template docs so humans and agents start with `port check` before manual template editing or RunPod validation.
3. Update failure/live-validation docs to map common failures to commands: schema issues to `port check`/`validate`, custom nodes to `nodes install-plan`, model URLs to `port check --head-check-models`, and Python materialization to `port convert`.
4. Update AGENTS.md or the synced skill guidance so agents know when to use the porting workbench.
5. Ensure command help text mirrors the docs so discoverability is present in both CLI and repository guidance.

- Simple plans: use `## Main Phase` with `### Step N:` sections underneath.
