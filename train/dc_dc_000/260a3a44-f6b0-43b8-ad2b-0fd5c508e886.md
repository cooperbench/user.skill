80	## Step Rules
81	- `plan`: inspect the repository first; produce the plan plus `questions`, `assumptions`, and `success_criteria`. 84	- `gate`: read the response, warnings, and `orchestrator_guidance`. (Skipped at light robustness.)
85	- `revise`: show the delta, flags addressed, and flags remaining. At light robustness, routes to `finalize`; otherwise loops back through `critique` and `gate`.
86	- `review`: judge success against the success criteria and the user's intent, not plan elegance. Only block on `must` criteria failures. `should` failures are flagged but don't require rework. `info` criteria are waived.

162	## Bakeoff
163	`megaplan bakeoff run` runs the same idea through multiple profiles concurrently, each in its own git worktree, each driven autonomously by `megaplan auto`. Use it when the user wants to compare profiles head-to-head on the same task (e.g., "run this with kimi and standard side-by-side").
164	Supports `--mode code` (default) and `--mode doc` / `--mode metaplan` (alias). For doc-mode bake-offs, `--output <relative/path>` is required and is threaded into each profile's `megaplan init`; merge brings the chosen profile's doc artifact back to main instead of applying a code patch. Joke mode is not yet supported.
165	Requires a clean main worktree by default — pass `--allow-dirty` when there are unrelated uncommitted changes you want to keep on main. Those changes stay on main and are NOT copied into the worktrees, since worktrees branch off the current commit's SHA.
166	The idea must be a file (`--idea-file <path>`), not an inline string. Write the idea to a file first.
167	Bakeoff is inherently autonomous (it spawns `megaplan auto`), so the execution-mode question doesn't apply to bakeoff runs. `--robustness` is forwarded to each profile's `init`. When a project-layer `.megaplan/profiles.toml` exists, it's automatically copied into each worktree so project-only profiles resolve.
168	Lifecycle:
169	- `megaplan bakeoff run --idea-file <path> --profiles <p1> <p2> [--mode code|doc|metaplan] [--output <relative/path>] [--exp-id <id>] [--detach] [--robustness <level>] [--allow-dirty]` — kicks off N concurrent profile runs. Without `--detach` it streams a live status table every 5s and blocks until all profiles finish; with `--detach` it returns immediately and the user polls via `status`. `--output` is required with `--mode doc|metaplan` and rejected with `--mode code`.
170	- `megaplan bakeoff status [--exp <id>]` — current state of each profile (running / completed / crashed).
171	- `megaplan bakeoff tail [--exp <id>]` — tail the per-profile auto logs.
172	- `megaplan bakeoff compare --exp <id> [--judge <model>]` — collect metrics across profiles; with `--judge`, an LLM judge ranks the outputs.
173	- `megaplan bakeoff pick --exp <id> --profile <name> --rationale "..."` — record the human-selected winner.
174	- `megaplan bakeoff merge --exp <id>` — merge the chosen profile's worktree back to main.
175	- `megaplan bakeoff resume --exp <id>` — resume unfinished profile runs.
176	- `megaplan bakeoff abandon --exp <id>` — discard worktrees but keep audit data.

293	## 3. Phase Routing by Robustness
294	Use the workflow below exactly.
295	
296	Light robustness:
297	- `init -> prep -> plan -> critique -> revise -> finalize -> execute -> done`
298	- There is no `gate`.
299	- There is no `review`.
300	- `prep` may return `skip: true`; that still counts as the visible prep phase.
301	- After the light `revise`, the CLI moves to `gated`, so the next command is `finalize`.
302	- After `execute`, the CLI will end the run.
303	
304	Standard robustness:
305	- `init -> prep -> plan -> critique -> gate`
306	- Then follow the gate decision tree below.
307	- `prep` may return `skip: true`; do not skip the command yourself.
308	- When you reach `gated`, run `finalize`.
309	- Then run `execute`.
310	- Then run `review`.
311	- If `review` returns `needs_rework`, the workflow becomes `finalized -> execute -> review` again until review passes or the CLI reaches its cap.
312	
313	Robust robustness:
314	- `init -> prep -> plan -> critique -> gate`
315	- `prep` may still return `skip: true`, but the phase remains visible in the CLI state/history.
316	- Uses 8 critique checks (vs 4 for standard) and enables parallel critique.
317	- After that, robust follows the same gate, finalize, execute, and review behavior as standard.
318	
319	Superrobust robustness:
320	- Same as robust, but also enables parallel review (review checks split across concurrent subagents).
321	
322	Gate decision tree for standard, robust, and superrobust:
323	- Condition 1: `gate_unset`
324	  Trigger: state is `critiqued` and `valid_next` includes `gate`.
325	  Action: run `megaplan gate --plan <name>`.
326	- Condition 2: `gate_iterate`
327	  Trigger: the latest gate recommendation is `ITERATE`, so `valid_next` includes `revise` but not `override force-proceed`.
328	  Action: run `megaplan revise --plan <name>`, then continue back through `critique` and `gate`.
329	- Condition 3: `gate_escalate`
330	  Trigger: the latest gate recommendation is `ESCALATE`, so `valid_next` offers `override add-note`, `override force-proceed`, or `override abort`.
331	  Action: stop with `BREAKPOINT: GATE_ESCALATE`.
332	- Condition 4: `gate_proceed_blocked`
333	  Trigger: the latest gate recommendation is `PROCEED`, but preflight still blocked execution, so state stays `critiqued` and `valid_next` offers `revise` plus `override force-proceed`.
334	  Action: do not finalize yet. Use `orchestrator_guidance` plus `preflight_results` to fix the blocking checks through `revise`. On iteration 1, the guidance text may stay generic, so inspect `preflight_results` yourself before revising. If the blocker cannot be resolved safely without a user decision, stop with `BREAKPOINT: GATE_BLOCKED`.
335	- Condition 5: `gate_proceed`
336	  Trigger: the latest gate recommendation is `PROCEED` and preflight passed, so state becomes `gated`.
337	  Action: run `megaplan finalize --plan <name>`.
338	
339	Review routing for standard, robust, and superrobust:
340	- If `review` succeeds, the run is done.
341	- If `review` returns `needs_rework`, the CLI moves back to `finalized` with `next_step` set to `execute`.
342	- When that happens, run `execute` again, then `review` again.
343	- This rework loop is capped by the CLI at 3 `needs_rework` cycles. If the cap is hit, the CLI force-proceeds to done and records the issue.

345	## 4. After Every Phase
346	After every phase command, immediately run:

388	## 6. Safeguards
389	Non-execute safeguards:
390	- If any non-execute phase fails, returns unusable output, or clearly lands in a bad session state, retry that same phase once with `--fresh`.
391	- If the exact same error appears twice in a row for the same phase, the next retry must use `--fresh`.
392	- If the phase still fails after the required fresh retry, stop with `BREAKPOINT: PHASE_ESCALATE`.
393	
394	Execute safeguards:

396	- Forward progress means new completed tasks, a completed batch, or a state advance that clearly moves the run closer to done.
397	- If you hit 3 consecutive `execute` attempts without forward progress, stop with `BREAKPOINT: EXECUTE_ESCALATE`.
398	- If `execute` times out or is blocked, retry up to that same 3-attempt cap.
399	
400	Review safeguards:
401	- `needs_rework` is a normal workflow branch, not a phase failure.
402	- If `review` returns `needs_rework`, do not break out. Follow the rework loop and run `execute` again from `finalized`.
403	- If `review` returns blocked instead of a real verdict, the CLI keeps the run in `executed` with `next_step` set to `review`.
404	- If `review` returns blocked or otherwise unusable output, treat that as a review-phase problem and apply the non-execute retry rule.
