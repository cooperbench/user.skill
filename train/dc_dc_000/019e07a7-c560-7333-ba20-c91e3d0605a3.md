        # Implementation Plan: Agentic Live-Update Editor

## Overview
Replace the 07:00 UTC daily batch summary with a live editor that incrementally maintains a current community update in Discord and persistence. The current path is centered on `SummarizerCog.run_daily_summary()` in `src/features/summarising/summariser_cog.py`, which calls the broad batch pipeline `ChannelSummarizer.generate_summary()` in `src/features/summarising/summariser.py`. Storage and admin/health tooling currently assume `daily_summaries`, through `src/common/db_handler.py`, `src/common/storage_handler.py`, `src/features/health/health_check_cog.py`, `src/features/admin_chat/tools.py`, and `scripts/discord_tools.py`.

The simplest durable approach is not to edit the monolithic batch function in place. Add a live-update service beside it, reuse the existing message retrieval, formatting, moderation, media persistence, and DB wrappers where possible, then switch scheduling/admin health to the new live-update contract while leaving manual batch commands available during rollout.

## Phase 1: Define the Live Summary Contract

### Step 1: Audit reusable summarizer internals (`src/features/summarising/summariser.py`, `src/features/summarising/subfeatures/news_summary.py`)
**Scope:** Medium
1. **Extract** the reusable parts of `ChannelSummarizer.generate_summary()` into narrower methods if needed: active-channel selection, channel history loading, summary generation/verification, media filtering, Discord formatting, media persistence, and short-summary generation.
2. **Keep** behavior changes out of the extraction step. The goal is to make live editing call existing logic without copying the 400-line batch pipeline.
3. **Add** focused tests around any extracted pure/helper behavior, especially JSON summary enrichment and formatting inputs.

### Step 2: Choose and implement persistence compatibility (`src/common/db_handler.py`, `src/common/storage_handler.py`)
**Scope:** Medium
1. **Add** explicit live-summary persistence methods such as `get_live_summary_state`, `upsert_live_summary_state`, and `record_live_summary_revision`.
2. **Prefer** a new Supabase table/model for live state if schema migrations are available in the repo; otherwise add wrapper methods that can initially store compatible rows in `daily_summaries` with a clear discriminator in the existing fields.
3. **Preserve** reads for existing `daily_summaries` until admin tools and downstream scripts are migrated.
4. **Document** any required Supabase schema change in the same style as this repository uses for operational DB changes, since no migration directory was visible in the inspected tree.

## Phase 2: Build the Live Editor

### Step 3: Add the live-update service (`src/features/summarising/live_update_editor.py`)
**Scope:** Large
1. **Create** a `LiveUpdateEditor` class responsible for maintaining one current editable summary per guild/day or per configured summary channel.
2. **Implement** a cheap change detector that reads newly archived messages since the last processed timestamp and skips work when there is no meaningful new activity.
3. **Generate** incremental candidate updates through `NewsSummarizer`, using the previous live summary as context so the agent edits the existing update rather than regenerating the full day blindly.
4. **Moderate and format** output with existing `filter_summary_media()` and `NewsSummarizer.format_news_for_discord()` before publishing.
5. **Persist** every accepted revision with source message IDs, processed timestamp, summary message IDs, short summary, dev-mode flag, and guild ID.

### Step 4: Publish by editing Discord messages (`src/features/summarising/live_update_editor.py`, `src/common/discord_utils.py` if needed)
**Scope:** Medium
1. **Post** the first live update to the configured summary channel when no editable message exists.
2. **Edit** existing bot-authored summary messages on subsequent updates instead of posting a new daily digest.
3. **Handle** Discord length limits by maintaining a stable ordered set of bot messages for the live update, adding/removing tail messages only when the formatted content crosses message boundaries.
4. **Avoid** forum-channel posting unless current support is confirmed; keep the existing batch behavior of skipping unsupported forum destinations.

### Step 5: Replace scheduled daily execution (`src/features/summarising/summariser_cog.py`, `main.py`)
**Scope:** Medium
1. **Stop** starting `run_daily_summary` as the default 07:00 UTC loop.
2. **Start** a live-update loop in `SummarizerCog` with a configurable interval, for example every 15 minutes, after bot readiness and archive startup conditions are satisfied.
3. **Rename or repurpose** commands carefully: keep `summarynow` as an owner/admin manual trigger, but make it run one live-editor pass by default.
4. **Keep** an explicit legacy/manual batch command or flag only if operators still need the old backfill/combine behavior during migration.
5. **Update** CLI flags in `main.py`: deprecate `--combine-only` and `--clear-today-summaries` for live mode, or make their behavior explicit and non-ambiguous.

## Phase 3: Compatibility and Operations

### Step 6: Update health checks (`src/features/health/health_check_cog.py`)
**Scope:** Small
1. **Replace** `_check_daily_summary()` with a live-summary freshness check after the configured live editor start time.
2. **Verify** the latest live summary state has been updated recently and has at least one Discord message ID or persisted revision.
3. **Keep** the alert actionable, e.g. no live update generated in the last N minutes despite recent message activity.

### Step 7: Update admin tools (`src/features/admin_chat/tools.py`, `scripts/discord_tools.py`)
**Scope:** Medium
1. **Add** or rename admin tooling from `get_daily_summaries` to a live-summary-aware tool such as `get_live_summaries`.
2. **Keep** a compatibility wrapper for `get_daily_summaries` during rollout if external prompts or operators still call it.
3. **Update** the tool schema descriptions in `src/features/admin_chat/tools.py` and the admin agent tool list in `src/features/admin_chat/agent.py` so the agent no longer describes summaries as daily-only.
4. **Update** `scripts/discord_tools.py::summaries()` to read the new live state or include both old daily rows and live revisions clearly.

### Step 8: Preserve downstream summary consumers (`src/features/summarising/summariser.py`, `scripts/send_social_picks.py`, `scripts/test_social_picks.py`)
**Scope:** Medium
1. **Check** social-picks behavior that currently reads today’s summary via `get_summary_for_date()`.
2. **Route** social picks to the latest live summary state so the DM workflow still works after the batch main summary is removed.
3. **Keep** top generations, top art sharing, and speaker welcome behavior only if product intent still wants them in the live update; otherwise isolate them behind manual/admin commands rather than posting them every live pass.

## Phase 4: Tests and Validation

### Step 9: Add focused unit tests (`tests/`)
**Scope:** Medium
1. **Add** tests for live state persistence wrapper behavior with mocked Supabase clients.
2. **Add** tests for Discord edit chunking: first publish posts messages, later publish edits existing messages, overflow creates stable extra messages, shrink removes or blanks stale tail messages according to the chosen implementation.
3. **Add** tests for the live loop decision: no new source messages skips LLM calls and Discord edits.
4. **Add** tests for health/admin compatibility functions using mocked table responses.

### Step 10: Run validation (`pytest`, targeted checks)
**Scope:** Small
1. **Run** cheap targeted tests first for the new live editor and persistence wrappers.
2. **Run** existing scheduler/admin/health-related tests to catch regressions.
3. **Run** the full test suite after wiring is complete.
4. **Run** import/compile checks if the full suite cannot cover Discord cog loading.

        # Implementation Plan: Agentic Sequential Live-Update Editor

## Overview
The critique shows the prior plan targeted the wrong product shape: it treated the replacement as an in-place editable digest, while the settled requirement is an agentic scheduled editorial loop that appends public live-update feed items to the configured summary channel. The root cause is broader than `SummarizerCog.run_daily_summary()` itself: the current system combines scheduling, 24-hour batch summarization, Discord posting, daily-summary persistence, health checks, admin tools, and top-creations posting into one daily flow.

This revision replaces the daily batch flow with a new live editorial pipeline: scheduled runs inspect newly archived messages, investigate author/context signals, generate auditable candidates, suppress duplicates, record decisions, update watchlist/editorial memory, and append accepted updates as sequential feed items. `daily_summaries` becomes legacy/migration input only. Active live-flow state must use new Supabase tables added through the canonical `../supabase/migrations/` path.

## Phase 1: Foundation — Schema, Contracts, and Legacy Boundaries

### Step 1: Confirm runtime touch points and legacy boundaries (`src/features/summarising/summariser_cog.py`, `main.py`, `src/features/summarising/summariser.py`)
**Scope:** Small

### Step 2: Add canonical live-editor migrations (`../supabase/migrations/`)
**Scope:** Large
1. **Create** an idempotent Supabase migration for live-editor tables instead of storing active state in `daily_summaries`.
2. **Add** tables for auditable state:
   - `live_update_runs`: run ID, guild ID, summary/live channel ID, trigger type, status, started/finished timestamps, checkpoint range, model metadata, error details.
   - `live_update_candidates`: candidate ID, run ID, update type, title/body/media/source message IDs, author-context snapshot, duplicate key, score/priority, raw agent output.
   - `live_update_decisions`: decision ID, candidate ID, decision status, reason, duplicate match, human/agent actor metadata.
   - `live_update_feed_items`: accepted candidate ID, Discord channel ID, Discord message ID, posted content, posted timestamp, dev mode.
   - `live_editor_memory`: durable editorial notes, watchlist items, topic state, author/project context, suppression windows, last-seen checkpoints.
3. **Add** indexes and uniqueness constraints for duplicate suppression, especially `(guild_id, duplicate_key)` or a bounded active duplicate key table/window.
4. **Treat** `daily_summaries` as read-only legacy input for migration/admin history, not as active live-flow storage.

### Step 3: Add storage and DB wrappers (`src/common/storage_handler.py`, `src/common/db_handler.py`)
**Scope:** Medium

2. **Add** a checkpoint query built around persisted messages after a stored timestamp/message ID, using or extending `DatabaseHandler.get_messages_after(...)` rather than reusing `get_channel_history()` with its 24-hour and per-channel threshold assumptions.
3. **Keep** existing `store_daily_summary`, `get_summary_for_date`, and `summary_exists_for_date` intact for legacy tooling until migration is complete.

## Phase 2: Agentic Editorial Pipeline

### Step 4: Add the live editor service (`src/features/summarising/live_update_editor.py`)
**Scope:** Large
1. **Create** `LiveUpdateEditor` with one public entrypoint such as `run_once(trigger: str)`.
2. **Load** the current checkpoint, watchlist, editorial memory, recent accepted feed items, and duplicate suppression state at the start of each run.
3. **Fetch** newly archived messages by guild/checkpoint, including thread/forum context where available.
4. **Record** every run in `live_update_runs`, including skipped runs when there is no new material.

### Step 5: Implement author-context investigation (`src/features/summarising/live_update_editor.py`, `src/common/db_handler.py`)
**Scope:** Medium
1. **Resolve** author context for candidate-worthy messages from existing member/profile tables and recent message history.
2. **Attach** context snapshots to candidates so decisions are auditable without relying on future mutable profile data.
3. **Capture** project/topic continuity from `live_editor_memory` and recent accepted feed items before prompting the agent.

### Step 6: Generate candidates and decisions (`src/features/summarising/live_update_editor.py`, `src/features/summarising/subfeatures/news_summary.py` or new prompt module)
**Scope:** Large
1. **Add** agent prompts/helpers for multiple update types, such as news item, project progress, release/resource, question needing attention, correction/follow-up, and creation spotlight.
2. **Produce** structured candidate JSON with source message IDs, update type, proposed public text, media references, duplicate key, confidence/priority, and rationale.
3. **Persist** all candidates before filtering so rejected and duplicate outcomes remain auditable.
4. **Run** decision logic that accepts, rejects, defers, or marks duplicate candidates, with an explicit decision reason for each.
5. **Update** watchlist/editorial memory after decisions, including topics to revisit, topics to suppress, and author/project notes.

### Step 7: Suppress duplicates (`src/features/summarising/live_update_editor.py`, `src/common/storage_handler.py`)
**Scope:** Medium
1. **Compute** stable duplicate keys from source IDs, normalized topic/project identifiers, URLs, and update type.
2. **Check** duplicate keys against recent candidates, decisions, feed items, and editorial memory before posting.
3. **Persist** duplicate decisions with a pointer to the matched prior candidate/feed item.
4. **Test** that repeated scheduled runs over the same source messages do not post another feed item.
