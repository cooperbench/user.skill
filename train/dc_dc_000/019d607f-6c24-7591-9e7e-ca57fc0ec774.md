## Overview

The effect wrapping system has three independent code paths that construct effect component trees:
1. **`wrapWithClipEffects`** (`effects/index.tsx:116`) — used by `VisualClip` and `TextClip` for render-time clip wrapping
2. **`EffectLayerSequence`** (`compositions/EffectLayerSequence.tsx:21`) — wraps children with continuous effects during effect-layer time ranges
3. **`makePreviewComposition`** → `wrapPreviewEffect` (`components/EffectCreatorPanel.tsx:157`) — wraps preview content in the effect creator dialog

Key disagreements:
- `wrapWithClipEffects` omits `effectFrames` for continuous effects; `EffectLayerSequence` passes `effectFrames=durationInFrames`; preview passes `effectFrames=durationInFrames` for continuous.
- Each path independently calls `registry.getSchema()`, `validateAndCoerceParams()`, and constructs `EffectErrorBoundary` wrappers.
- `PREVIEW_FPS=30` is only used as a fallback when `timelineFps` is absent.

Built-in continuous effects (`continuous.tsx`) don't actually use `effectFrames` at all — they only use `durationInFrames` and `intensity`. Built-in entrances use `effectFrames` for spring/interpolation duration. Built-in exits use `effectFrames` for exit timing. So for continuous effects, `effectFrames` is irrelevant to built-ins but may matter for custom effects.

## Phase 3: Audit and fix code quality issues

### Step 6: Audit `registerAsync` for race conditions (`hooks/useEffectRegistry.ts`)
**Scope:** Small
1. **Issue:** `useEffectRegistry` fires `registry.batch(async () => { ... })` inside a `useEffect`. If `dbEffects` or `resourceEffects` change rapidly, multiple batch calls can overlap because the previous async batch isn't cancelled. The old registry instance is replaced by `replaceEffectRegistry(registry)` on every render (line 29), but the `useEffect` might still be running registrations on a stale registry.
2. **Fix:** The `useMemo(() => new DynamicEffectRegistry(BUILT_INS), [])` creates the registry once and never changes (empty deps), and `replaceEffectRegistry` is called synchronously during render, so the global always points to the current one. The real issue is that `useEffect` re-fires when `dbEffects`/`resourceEffects` change, potentially running concurrent `batch()` calls. Add an `AbortController`-style guard: track a `stale` boolean set in the effect cleanup that short-circuits registration if the effect has been superseded.
3. **Implement** the fix:
   ```ts
   useEffect(() => {
     let stale = false;
     const drafts = Object.entries(draftEffects);
     const db = dbEffects ?? [];
     const resources = resourceEffects ?? [];
     // ...
     void registry.batch(async () => {
       for (const [name, code] of drafts) {
         if (stale) return;
         await registry.registerAsync(name, code);
       }
       // ... same pattern for db and resources
     });
     return () => { stale = true; };
   }, [dbEffects, draftEffects, registry, resourceEffects]);
   ```
