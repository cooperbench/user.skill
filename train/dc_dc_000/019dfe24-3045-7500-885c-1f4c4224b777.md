**Findings**

1. **Standard/charged turns still force extra LLM steps even when no tools are needed.**  
   [turn_plan.py](/Users/user_c042661f/Documents/Veas/app/services/turn_plan.py:13) makes `standard` and `charged` run `read -> respond -> record -> schedule -> done`. Even if `read`, `record`, and `schedule` make no tool calls, [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:741) still invokes a model step for each. From an over-eager-agent perspective, this prevents many tool calls but not unnecessary token use.  
   **Recommendation:** make `standard` closer to `read -> respond -> done` by default, and add `record`/`schedule` only from explicit signals, or let the runner skip empty post-response steps deterministically unless the trigger had concrete write/schedule signals.

2. **`update_turn_plan` can become a cheap-looking state-update habit.**  
   It is always available via [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:233), omitted from visible tool-call recording at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:295), and not counted as a tool call in [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:313). It still costs model/tool iterations, but observability makes it look free. `TurnPlan.add_steps` also permits duplicate steps at [turn_plan.py](/Users/user_c042661f/Documents/Veas/app/services/turn_plan.py:85).  
   **Recommendation:** count/log plan updates separately, cap to one per turn unless needed, reject note-only calls, and dedupe added steps.

3. **Consult gating is inconsistent.**  
   The main adaptive prompt says consult only when explicitly requested at [prompts.py](/Users/user_c042661f/Documents/Veas/app/services/prompts.py:275), but the tool description still says to consult before “charged, ambiguous, or possibly one-sided” responses at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:65). The consult step also allows broad read tools via [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:212), so a consult step can become an extra read pass.  
   **Recommendation:** align the tool description with the explicit-request rule, and restrict `consult` to `consult_perspective` plus maybe `check_oob`, not the full read surface.

4. **Scheduling duplicate prevention is prompt-only.**  
   Schedule tools are allowed in the schedule step at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:214), but `READ_BEFORE_WRITE` does not require `list_scheduled_tasks` before `schedule_checkin` or `schedule_task` at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:235). Since `standard`/`charged` always include `schedule`, an eager agent can create duplicate follow-ups without first checking.  
   **Recommendation:** require `list_scheduled_tasks` before schedule creation when there are open watch items, scheduled-task turns, or any non-user-explicit follow-up.

5. **Record step has a very large read/write surface.**  
   `record` allows all record writes plus most read tools at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:229). The mediator instruction says to record any justified state changes at [mediator.py](/Users/user_c042661f/Documents/Veas/app/bots/mediator.py:72), and the prompt says primitives can co-exist and “write to all that apply” at [prompts.py](/Users/user_c042661f/Documents/Veas/app/services/prompts.py:93). This can invite multi-write behavior for ordinary charged messages.  
   **Recommendation:** add a stronger threshold: no durable write unless the turn contains explicit facts, explicit preference/boundary changes, repeated pattern evidence, or a concrete future item.

6. **Read-before-write enforcement is too broad in one way and too narrow in another.**  
   It only checks whether any required read tool appeared anywhere in `ctx.tool_call_log` at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:324), not whether the read was relevant to the entity being written. But it also omits durable writes like `update_user_style_notes`, bridge candidates, scheduling, feedback, and media explanations.  
   **Recommendation:** enforce narrower prerequisites per write type, ideally with read result ids or query metadata. Add missing gates where duplicate or privacy risk is meaningful.

7. **Partner-perspective prompting can defeat the “read only when needed” goal.**  
   The opt-in partner prompt says to keep the partner perspective live “frequently” and “read the partner’s side yourself” using several tools at [prompts.py](/Users/user_c042661f/Documents/Veas/app/services/prompts.py:357). That pushes an eager agent toward searches even when hot context is enough.  
   **Recommendation:** reword to “use hot context first; read partner-side tools only when the current reply needs grounded partner context not already present.”

8. **`check_oob` may cause redundant preflight checks.**  
   The prompt says every outbound must pass through `check_oob` at [prompts.py](/Users/user_c042661f/Documents/Veas/app/services/prompts.py:111), and `check_oob` is exposed during `respond` at [registry.py](/Users/user_c042661f/Documents/Veas/app/services/tools/registry.py:223), while the runner also resolves final outbound text before sending at [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:773).  
   **Recommendation:** if final send paths already enforce OOB, remove `check_oob` from normal respond tool availability and reserve it for bridge drafts, sensitive partner paraphrases, or direct-send tools that need model-visible preflight.

Overall: the system has useful hard tool allow-lists and read-before-write checks, but it mostly controls *which* tools can be used per step, not *whether the step should run*. The biggest token-use win is making post-response `record`/`schedule` conditional instead of default for standard and charged turns.
