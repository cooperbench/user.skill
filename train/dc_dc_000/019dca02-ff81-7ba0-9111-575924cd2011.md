> AGENT

Your “additive only” conclusion is directionally right, but slightly underpowered. I would not ship a central doctor or broad model registry now. I would ship **one structural spine**: live-runtime validation around `/object_info`, plus better execution telemetry. Everything else should stay local until it repeatedly hurts.

The mistake I’d push back on: treating “object_info-as-validator” as merely additive lint. It is more fundamental than that. In this domain, the live Comfy runtime is the contract. If VibeComfy generates or mutates workflow API JSON, then validating against the runtime before submission is not optional hygiene; it is the boundary between “we know this graph is submit-shaped” and “we are debugging ghosts on GPUs.”

**My Position**

Ship now, in this order:

1. **`/object_info` pre-submit validation**
   Validate node classes, input names, required fields, enums/ranges where available, and link shapes. Do not rewrite the whole materializer yet. But make this a real validation layer, not a soft warning buried in logs.

2. **Execution watchdog**
   Log current node id/class, elapsed time, last progress event, and VRAM if available. On timeout, dump enough state to distinguish “slow node,” “stalled runtime,” “missing event stream,” and “OOM-ish behavior.”

3. **Delete or sharply constrain generic CLI overrides**
   Generic `--prompt` / `--steps` across heterogeneous workflow families is a trap. Keep them only where the target mapping is explicit. For non-image/video/audio custom families, require named workflow parameters or family-aware routing.

4. **Add real fixture media**
   `speech_smoke.wav`, non-silent guide video with audio, and maybe a short known-good talking-head fixture if those workflows need audiovisual structure. This is not “structural architecture”; it is test data correctness.

Defer:

- **Full object_info-driven materializer rewrite**
- **Central model alias registry**
- **Per-workflow input contract system**
- **Big pre-flight doctor**
- **Any gatekeeping megaplan-style “must pass before matrix can run” framework**

**Which Fixes Earn Their Place Independent Of Growth**

Two do: `/object_info` validation and watchdog telemetry.

They are not justified by corpus size. They are justified by epistemology. Without them, you cannot tell whether failures are caused by your JSON, the fork, custom node behavior, missing assets, bad fixtures, or runtime stalls. That means every red workflow becomes folklore.

The fixture fix also earns its place because silent audio/video is not a neutral fixture. It changes behavior. If an audio node chokes on silence, you have not tested the workflow; you have tested an edge case.

Deleting generic overrides earns its place because it removes a known footgun. A convenience flag that silently mutates the wrong node is worse than no flag.

**Triggers For Registry Or Doctor**

Do not use “corpus is growing” as the trigger. That is too vague and will rationalize bureaucracy.

Use these triggers:

- **Model registry trigger:** same model-path or alias issue causes failures in **three separate workflow families** or consumes **more than one maintenance session** after already being documented.
- **Per-workflow contract trigger:** at least **three workflows require non-obvious fixture semantics** that cannot be inferred from node classes, and fixture mismatch causes false incompatibility reports.
- **Doctor trigger:** matrix runs repeatedly fail late for issues that could have been detected upfront, specifically:
  - missing node classes,
  - missing model files,
  - invalid input names,
  - bad link shape,
  - preview/output-only nodes known to break API execution.

I’d make the threshold concrete: if two matrix runs in a row waste GPU time on preflight-detectable errors, build the doctor. Not before.

Also, the doctor should report, not govern. No hard-halt framework unless the failure is definitively submit-invalid. “Warnings” must not block runtime experiments.

**Failure Mode Of Additive Only**

The real failure mode is not that you lack elegance. It is that local mitigations become an unindexed pile of tribal exceptions.

Specifically:

- Model staging becomes repeated yak-shaving across packs.
- Fixture requirements live in docs instead of execution metadata, so new workflows get tested with plausible-but-wrong inputs.
- Every matrix run rediscoveres the same missing-node/model/schema problems.
- The incompatibility doc starts mixing three categories: true fork incompatibilities, local generation bugs, and environment setup drift.
- Eventually a green workflow turns red after an ecosystem shift, and nobody can tell whether the local mitigation is obsolete, incomplete, or accidentally bypassed.

That is the strongest argument against you: additive-only can preserve knowledge, but it can also strand knowledge in prose and logs where automation cannot use it.

**Stronger Position I’d Defend**

Build a **thin runtime-contract layer**, not a platform.

Ship:

1. `/object_info` validation as the authoritative schema check.
2. Watchdog telemetry as the authoritative runtime-observability check.
3. Explicit override targeting; remove universal overrides where ambiguous.
4. Correct fixture library for known modality needs.
5. Keep `hiddenswitch_incompatibilities.md`, but require each entry to label root cause: `local_bug`, `fixture_gap`, `runtime_observability`, `model_layout`, `fork_behavior`, or `custom_node_contract`.

Defer central registries and doctors until the triggers fire.

That position is less conservative than “additive only” because it admits one real structural layer: live-runtime contract validation. But it rejects speculative centralization. The right architecture here is not a grand registry. It is a tight feedback loop: validate submit shape before GPU, observe execution during GPU, document incompatibility category after GPU.
