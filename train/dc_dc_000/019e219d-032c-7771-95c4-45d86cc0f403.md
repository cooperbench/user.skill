> AGENT

**1. Where The Redesign Helps**

The redesign genuinely fixes the transport-level failures. Native `tool_use` makes the multi-JSON-block parser bug structurally impossible. It also kills the specific “I watchlisted X” but no DB write failure, because watch/watch-update/post are all the same kind of action now: a tool call. If the model only narrates intent, nothing happens, and there is no parallel candidate channel pretending otherwise.

It also makes the agent’s conceptual job easier. The current system asks Claude to juggle candidates, decisions, duplicate state, editorial memory, feed items, and watchlist tools. The proposed “topic + state transition” model is much closer to how an LLM will naturally reason.

What becomes merely improbable, not impossible: wrong outlet choice, missing `sections`, skipped dedupe search, unstable keys, and under-investigated posts. Those remain behavioral problems unless the app enforces them.

**2. Where It Moves The Problem**

`sections` being optional is the biggest red flag. Claude already ignored a hard `examples` rule with app-enforced language. Renaming `examples` to `sections` and moving the rule into a shorter prompt does not fix that. If `post_topic(media=[...])` is valid for a multi-author cluster, Claude will eventually produce a wall of media again. The schema needs to make the simple path invalid when `source_message_ids.length >= 3` or distinct authors >= 2, or the dispatcher must reject/repair it.

`search_topics before posting` will not be consistent if it is prompt-only. Claude will skip it when the topic feels obviously new, when there are many clusters, or when it is trying to minimize turns. The failure mode is predictable: duplicate `topic_key`s for the same story, duplicate live-feed posts, and later confusion because history is split across two topic rows.

`topic_key` freedom is also fragile. Claude will not reliably converge on the same slug across runs: `omninft-lora-ltx23`, `omninft-ltx-2-3-lora`, and `gleb-omninft-lora-test` are all plausible. Search-first helps only if it happens and the query is good. A unique constraint on exact key does not protect semantic duplicates.

Removing `editorial_checklist` is mostly good. The checklist is self-attestation cargo cult: models learn to say “yes” to gates. But the checklist was also acting as an app-side tripwire for missing duplicate/context/evidence work. Do not replace it with trust. Replace it with tool-surface invariants.

**3. Agent-Side Blind Spots**

The doc underestimates token budgeting. “All watching topics” sounds clean until the watchlist grows. Claude will skim, overfit to recent source messages, and fail to re-evaluate older watched topics unless the payload ranks due/last-call items aggressively.

You also lose reasoning trace visibility. Tool args are cleaner than prose, but they hide near-misses: “I considered posting X but didn’t” disappears unless you log thinking summaries or add an explicit audit/notes mechanism.

Multi-author detection is not free. The model can see source authors, but unless the cluster object exposes `distinct_author_count` or the tool validates it, Claude must infer structure from raw message lists. That is exactly the kind of bookkeeping LLMs do unreliably.

Concurrent clusters in one turn are another weak spot. With 5 candidate topics, Claude may search one or two, then post the rest from confidence. Agentic search gets worse as topic count rises.

**4. What I’d Change**

Require sequence in code, not prose. Make `post_topic` and `watch_topic` require `search_topics_result_id` or `matched_topic_key/null` produced by an actual prior `search_topics` call. No search token, no write.

Split `post_topic` into two tools: `post_simple_topic` and `post_sectioned_topic`. The dispatcher should reject `post_simple_topic` if source count or author count crosses the multi-section threshold. Better yet, pass source message IDs through a validator that computes distinct authors server-side.

Add `propose_topic_key(source_message_ids, search_result_id)` or generate canonical keys app-side from normalized creator/artifact/date. Do not let slugging be purely agent-authored identity.

Keep a lightweight `model_notes` field, but do not depend on it. Add structured fields like `evidence_message_ids`, `community_signal_message_ids`, and `dedupe_basis`.

Use Anthropic tool choice to force at least one decision-tool phase after read tools, but do not rely on tool choice alone for ordering. The dispatcher should enforce ordering.

**5. Prediction**

First bug: duplicate posts. Symptom: same story posted twice under different topic keys. Diagnosis: Claude skipped `search_topics` or searched with a narrow query and invented a new slug.

Second bug: sectionless multi-author posts. Symptom: one live-feed message with 8-12 media links and weak attribution. Diagnosis: `sections` was optional and no server-side validator blocked simple rendering.

Third bug: watched topics silently rot. Symptom: due watch topics remain unchanged across runs despite new related messages. Diagnosis: the model focused on fresh source messages, did not connect them to watched topics, and “leave it” produced no auditable action.

Ship the redesign direction, but not as described. The architecture is agent-friendlier; the enforcement story is still too prompt-driven.
