**1. Where The Redesign Helps** The redesign genuinely fixes the transport-level failures. Native `tool_use` makes the multi-JSON-block parser bug structurally impossible. It also kills the specific “I watchlisted X” but no DB write failure, because watch/watch-update/post are all the same kind of action now: a tool call. If the model only narrates intent, nothing happens, and there is no parallel candidate channel pretending otherwise. It also makes the agent’s conceptual job easier. The current system asks Claude to juggle candidates, decisions, duplicate state, editorial memory, feed items, and watchlist tools. The proposed “topic + state transition” model is much closer to how an LLM will naturally reason. What becomes merely improbable, not impossible: wrong outlet choice, missing `sections`, skipped dedupe search, unstable keys, and under-investigated posts. Those remain behavioral problems unless the app enforces them. **2. Where It Moves The Problem** `sections` being optional is the biggest red flag. Claude already ignored a hard `examples` rule with app-enforced language. Renaming `examples` to `sections` and moving the rule into a shorter prompt does not fix that. If `post_topic(media=[...])` is valid for a multi-author cluster, Claude will eventually produce a wall of media again. The schema needs to make the simple path invalid when `source_message_ids.length >= 3` or distinct authors >= 2, or the dispatcher must reject/repair it. `search_topics before posting` will not be consistent if it is prompt-only. Claude will skip it when the topic feels obviously new, when there are many clusters, or when it is trying to minimize turns. The failure mode is predictable: duplicate `topic_key`s for the same story, duplicate live-feed posts, and later confusion because history is split across two topic rows. `topic_key` freedom is also fragile. Claude will not reliably converge on the same slug across runs: `omninft-lora-ltx23`, `omninft-ltx-2-3-lora`, and `gleb-omninft-lora-test` are all plausible. Search-first helps only if it happens and the query is good. A unique constraint on exact key does not protect semantic duplicates. Removing `editorial_checklist` is mostly good.
