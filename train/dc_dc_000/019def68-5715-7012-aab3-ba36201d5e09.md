        # Implementation Plan: Packs Layout Migration With No Compatibility Shims

## Overview
ArtAgents currently has framework code and registered content mixed under `artagents/executors/`, `artagents/orchestrators/`, and `artagents/elements/`. Registries discover built-ins by scanning those same directories, command manifests import modules from those directories, tests import many executor modules directly, and Remotion aliases point at `artagents/elements/bundled` plus `.artagents/elements/*`.

The migration should split framework code from content:

- `artagents/core/executor/`, `artagents/core/orchestrator/`, `artagents/core/element/` hold registry, schema, folder, runner, CLI/API/install code.
- `artagents/packs/<pack>/pack.yaml` marks a pack.
- `artagents/packs/<pack>/<thing>/executor.yaml|orchestrator.yaml|element.yaml` holds registered content.
- Qualified ids are mandatory. Bare names are rejected, with no aliasing or fallback resolution.
- Old content import paths are removed, not shimmed.

Important repo finding: the working tree is not at the exact count in the brief. Current CLI discovery reports 34 executors and 5 orchestrators, because in-flight threads/iteration work adds `iteration.prepare`, `iteration.assemble`, and `builtin.iteration_video`. The plan treats “land in-flight threads first” as a hard prerequisite, then migrates whatever content is on trunk after that lands.
