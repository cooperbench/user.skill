        # Implementation Plan: Scalable Workers + Multi-Model Eval Runs

## Overview

The SWE-bench eval harness (`evals/parallel.py`) currently splits tasks into N contiguous chunks at launch and assigns them statically to workers. This plan adds two capabilities:

1. **Dynamic worker scaling** — New workers can join mid-run and pick up unclaimed tasks from a shared manifest file.
2. **Multi-model concurrent runs** — Multiple model configs can run the same 500 tasks simultaneously with isolated results/predictions directories, by encoding the model config in `run_name`.

**Current state**: `parallel.py` calls `_split_tasks()` to divide all tasks into N chunks, writes per-worker temp configs with `evals_to_run` pre-populated, and spawns subprocesses. There is no shared state file — task assignment is purely positional.

**Key constraint**: A 5-worker run (PID 56575) is currently generating patches. The manifest system must be backwards-compatible (no manifest = current chunking behavior).

## Phase 1: Shared Task Manifest

### Step 1: Design and implement the manifest module (`evals/manifest.py`)
**Scope:** Medium

1. **Create** `evals/manifest.py` with a `TaskManifest` class that manages a JSON manifest file at `{results_root}/_task_manifest.json`.

2. **Manifest schema**:
   ```json
   {
     "version": 1,
     "created_at": "2026-03-28T12:00:00Z",
     "total_tasks": 500,
     "tasks": {
       "astropy__astropy-12907": {"status": "claimed", "worker": "worker-0", "claimed_at": "..."},
       "django__django-11099": {"status": "pending"},
       "django__django-11179": {"status": "done", "worker": "worker-2", "claimed_at": "...", "done_at": "..."}
     }
   }
   ```

3. **Implement** these methods on `TaskManifest`:
   - `create(manifest_path, all_tasks) -> TaskManifest` — Initialize manifest with all tasks as `pending`. Uses `fcntl.flock` for atomic writes.
   - `load(manifest_path) -> TaskManifest` — Load existing manifest.
   - `load_or_create(manifest_path, all_tasks) -> TaskManifest` — Load if exists, create if not.
   - `claim_batch(worker_id, batch_size) -> list[str]` — Atomically claim up to `batch_size` pending tasks. Read-lock, filter pending, write-lock, update status. Returns list of instance_ids.
   - `mark_done(instance_id)` — Mark a task as done (called after prediction is written).
   - `unclaimed_tasks() -> list[str]` — Return all `pending` task IDs.
   - `summary() -> dict` — Return counts: pending, claimed, done.

4. **File locking**: Use `fcntl.flock(LOCK_EX)` on a separate `.lock` file adjacent to the manifest. This ensures multiple `parallel.py` invocations can safely read/write the manifest concurrently. Keep lock duration minimal (read JSON, update, write, unlock).

5. **Batch claiming**: Workers claim tasks in small batches (e.g., 10 at a time) rather than all at once. This allows new workers to interleave fairly. The batch size should be configurable via `--claim-batch-size` (default 10).

### Step 2: Integrate manifest into the per-task eval loop (`evals/run_evals.py`)
**Scope:** Medium

1. **Modify** `run_all_evals()` (`evals/run_evals.py`) to support manifest-driven task iteration:
   - Add a `manifest_path` parameter (optional, `None` means legacy behavior).
   - When `manifest_path` is set, instead of iterating `config.evals_to_run` as a static list, use a loop: `while tasks := manifest.claim_batch(worker_id, batch_size)`, process each batch, then `mark_done()` each completed task.
   - When `manifest_path` is `None`, use current behavior (iterate `config.evals_to_run`).

2. **Pass** `manifest_path` and `worker_id` through the worker temp config as new optional fields:
   - `"manifest_path": "/abs/path/to/_task_manifest.json"`
   - `"worker_id": "worker-0"`
   - `"claim_batch_size": 10`

### Step 3: Update parallel.py to create and use the manifest (`evals/parallel.py`)
**Scope:** Medium

1. **Modify** `run_parallel_workers()`:
   - After resolving `all_tasks`, call `TaskManifest.create(results_root / "_task_manifest.json", all_tasks)`.
   - Remove the `_split_tasks()` call and static `evals_to_run` assignment from `_write_worker_config()`.
   - Instead, write `manifest_path` and `worker_id` into each worker's temp config.
   - Workers will self-serve tasks from the manifest at runtime.

2. **Update** `_write_worker_config()`:
   - Remove `tasks` parameter; add `manifest_path` parameter.
   - Set `evals_to_run = []` (empty = "get tasks from manifest").
   - Add `manifest_path`, `worker_id`, `claim_batch_size` to the config dict.

3. **Backwards compatibility**: If `manifest_path` is absent from a worker config, `run_all_evals()` falls back to iterating `config.evals_to_run` as today. The existing running workers (PID 56575) are unaffected — they use pre-existing temp configs without manifest fields.

### Step 4: Add a "join" mode to parallel.py (`evals/parallel.py`)
**Scope:** Medium

1. **Add** a new entry point `join_parallel_run(config_path, run_name, new_workers)`:
   - Loads the existing manifest at `results/{run_name}/_task_manifest.json`.
   - Checks `manifest.summary()` to see how many tasks are still pending.
   - Spawns `new_workers` additional worker subprocesses, each with a unique `worker_id` (starting from the next available, e.g., `worker-5` if 0-4 exist).
   - Workers claim from the same manifest — no overlap with existing workers.
   - Does NOT re-run scoring or combine predictions (the original orchestrator handles that).

2. **CLI integration** (`evals/run_evals.py`):
   - Add `--join` flag: `--join RUN_NAME` to join an existing run.
   - Add `--add-workers N` to specify how many workers to add.
   - When `--join` is set, call `join_parallel_run()` instead of `run_parallel_workers()`.

3. **Worker ID allocation**: Read existing `_worker_logs/` directory to find the highest existing worker ID, then start numbering from `max_id + 1`.

### Step 5: Validate Phase 1 (`tests/test_manifest.py`)
**Scope:** Small

1. **Unit tests** for `TaskManifest`:
   - `test_create_and_load` — create manifest, reload, verify all tasks pending.
   - `test_claim_batch` — claim N tasks, verify they're marked claimed, re-claim returns different tasks.
   - `test_concurrent_claims` — use `multiprocessing` to simulate 3 workers claiming simultaneously, verify no overlaps.
   - `test_mark_done` — claim then complete, verify status transitions.
   - `test_unclaimed_after_partial_claims` — verify correct count.

2. **Integration test**: Spawn 2 workers via `run_parallel_workers()` on a small task list (5 tasks), verify manifest reflects all done and no duplicates in predictions.

## Phase 2: Multi-Model Concurrent Runs

### Step 6: Encode model config in run_name (`evals/run_evals.py`, `evals/parallel.py`)
**Scope:** Small

1. **Convention**: The `run_name` already supports arbitrary strings. Multi-model runs use descriptive names like:
   - `swebench-verified-qwen-glm`
   - `swebench-verified-opus-gpt`

2. **No code changes needed** for this — `run_name` already namespaces `results_root`, `predictions_dir`, `_worker_logs`, and worker subdirs. Each model config gets its own config JSON file with a different `run_name` and `models` dict.

3. **Document** the convention: each model config should have its own config file (e.g., `evals/configs/swebench-qwen-glm.json`, `evals/configs/swebench-opus-gpt.json`) with distinct `run_name` values. Each gets its own `parallel.py` invocation and its own manifest.

### Step 7: Verify isolation of concurrent multi-model runs
**Scope:** Small

1. **Audit** shared resources that could conflict:
   - `workspace_dir`: Each config should specify a unique `workspace_dir` (e.g., `evals/workspaces-qwen-glm`). The current code derives per-worker workspace as `{workspace_dir}/../workspaces-{i}`, which would collide if two runs share the same base. **Fix**: Change workspace derivation to include `run_name` or use the config's `workspace_dir` directly as the base.
   - SWE-bench source repo: Read-only after setup, safe to share.
   - Docker: SWE-bench scoring uses instance-specific containers, safe to run concurrently.
   - `.hermes` home: Each worker already gets its own `_hermes_home`, but the parent derivation uses the workspace path, so unique workspace_dirs keep these separate.

2. **Fix** workspace collision (`evals/parallel.py:60`):
   - Change `worker_workspace = Path(config.workspace_dir).expanduser().resolve().parent / f"workspaces-{i}"` to use `results_root` or a run-name-scoped base to prevent collisions between concurrent model runs.
   - E.g., `worker_workspace = Path(config.workspace_dir).expanduser().resolve() / f"worker-{i}"` (derive from the config's own workspace_dir, not its parent).

### Step 8: End-to-end validation
**Scope:** Small

1. **Dry-run test**: Create two config files with different `run_name` and `models`, each with `evals_to_run` set to 2 tasks. Launch both via separate `parallel.py` invocations. Verify:
   - Separate manifest files created under each `results/{run_name}/`.
   - No workspace directory collisions.
   - Separate prediction files and summaries.
   - Workers from run A never claim tasks from run B's manifest.

## Execution Order

1. **Step 1** (manifest module) first — self-contained, testable in isolation.
2. **Step 5** (manifest tests) immediately after Step 1 — validate before integrating.
3. **Steps 2-3** (integration into run_evals + parallel.py) — wiring the manifest into the existing flow.
4. **Step 4** (join mode) — depends on Steps 1-3 being solid.
5. **Steps 6-7** (multi-model) — mostly convention + one workspace fix, low risk.
6. **Step 8** (e2e) — final validation.

5. Full-scale: 5+5 workers on 500 tasks, verify all tasks completed exactly once.

        # Implementation Plan: Scalable Workers + Multi-Model Eval Runs

## Overview

The SWE-bench eval harness (`evals/parallel.py`) currently splits tasks into N contiguous chunks at launch and assigns them statically to workers. This plan adds two capabilities:

1. **Dynamic worker scaling** — New workers can join mid-run and pick up unclaimed tasks from a shared manifest file.
2. **Multi-model concurrent runs** — Multiple model configs can run the same 500 tasks simultaneously with isolated results/predictions directories, by encoding the model config in `run_name`.

**Current state**: `parallel.py` calls `_split_tasks()` to divide all tasks into N chunks, writes per-worker temp configs with `evals_to_run` pre-populated, and spawns subprocesses. There is no shared state file — task assignment is purely positional. Predictions are written by each worker to `workspace_path.parent / "_swebench_predictions"` (`evals/benchmarks/swe_bench.py:247`), but the orchestrator reads from `results_root / "_swebench_predictions"` (`evals/parallel.py:38`) — these are different directories (a pre-existing bug). Results isolation comes from per-worker `run_name` nesting (`parallel.py:159`).

**Key constraint**: A 5-worker run (PID 56575) is currently generating patches. The manifest system must be backwards-compatible (no manifest = current chunking behavior). Settled decisions from v1: fcntl file locking (SD-001), batch size 10 (SD-002), separate invocations per model config (SD-003), backwards-compat via optional fields (SD-004).

## Phase 1: Foundation — Config Schema + Manifest Module

### Step 1: Extend EvalConfig with manifest fields (`evals/config.py`)
**Scope:** Small

1. **Add** three optional fields to `EvalConfig` (`evals/config.py:31`):
   ```python
   manifest_path: str = ""          # Path to shared task manifest (empty = legacy mode)
   worker_id: str = ""              # e.g. "worker-0" (empty = not a manifest worker)
   claim_batch_size: int = 10       # Tasks to claim per batch from manifest
   predictions_dir: str = ""        # Shared predictions output dir (empty = derive from workspace)
   ```
   These are optional with empty/default values, so existing configs and the running PID 56575 workers load without error. `load_config()` uses `EvalConfig(**payload)` (`config.py:92`) — with `slots=True`, unknown keys would raise `TypeError`, but these are now known fields.

### Step 2: Implement the manifest module (`evals/manifest.py`)
**Scope:** Medium

1. **Create** `evals/manifest.py` with a `TaskManifest` class managing a JSON file at `{results_root}/_task_manifest.json`.

2. **Manifest schema**:
   ```json
   {
     "version": 1,
     "created_at": "2026-03-28T12:00:00Z",
     "total_tasks": 500,
     "tasks": {
       "astropy__astropy-12907": {"status": "claimed", "worker": "worker-0", "claimed_at": "..."},
       "django__django-11099": {"status": "pending"},
       "django__django-11179": {"status": "done", "worker": "worker-2", "claimed_at": "...", "done_at": "..."}
     }
   }
   ```

3. **Implement** these methods on `TaskManifest`:
   - `create(manifest_path, all_tasks) -> TaskManifest` — Initialize manifest with all tasks as `pending`.
   - `load(manifest_path) -> TaskManifest` — Load existing manifest.
   - `load_or_create(manifest_path, all_tasks) -> TaskManifest` — Load if exists, create if not.
   - `claim_batch(worker_id, batch_size) -> list[str]` — Atomically claim up to `batch_size` pending tasks. Returns list of instance_ids.
   - `mark_done(instance_id, worker_id) -> None` — Mark a task as done.
   - `unclaimed_count() -> int` — Count of pending tasks.
   - `all_done() -> bool` — True if no tasks are pending or claimed.
   - `done_task_ids() -> set[str]` — Return set of instance_ids with status `done` (used for filtering predictions).
   - `summary() -> dict` — Return counts: pending, claimed, done.
   - `next_worker_id() -> str` — Scan existing worker IDs in the manifest, return `worker-{max+1}`.

4. **File locking**: Use `fcntl.flock(LOCK_EX)` on a `.lock` file adjacent to the manifest. Every read-modify-write operation (claim_batch, mark_done) acquires the exclusive lock, reads current JSON, mutates, writes, releases. Keep lock duration minimal.

### Step 3: Validate manifest module (`tests/test_manifest.py`)
**Scope:** Small

   - `test_concurrent_claims` — use `multiprocessing` to simulate 3 workers claiming simultaneously, verify no overlaps.
   - `test_mark_done` — claim then complete, verify status transitions.
   - `test_all_done` — verify transitions from not-done to done.
