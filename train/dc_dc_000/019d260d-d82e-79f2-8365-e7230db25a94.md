        # Implementation Plan: Video Editor Timeline Engineering Cleanup

## Overview

`useTimelineEditing.ts` (947 lines) is the central editing hook for the video editor timeline. It mixes six distinct concerns: library move/resize callbacks, external drag-drop indicators, file upload orchestration, asset registration, clip mutations, and DOM management. The remaining items target inline styles on drop indicators, fragile event-ordering between `ClipAction` and `useClipDrag`, a shared mutable `ActionDragState` ref with no coordination, and a height-calculation hack in `EditorPaneTab` that duplicates logic from `getEffectivePaneHeights`.

**Key constraint:** The timeline library (`@xzdarcy/react-timeline-editor`) controls move/resize via callbacks that return `boolean | undefined` to accept/reject changes. These return-value contracts must be preserved exactly.

## Phase 2: Behavioral Improvements

### Step 7: Replace shared mutable `ActionDragState` ref with coordinated state
**Scope:** Medium-High
1. **Create** `src/tools/video-editor/hooks/useActionDragState.ts` that encapsulates the `Record<string, ActionDragState>` ref behind a small API:
   ```ts
   interface ActionDragCoordinator {
     ref: MutableRefObject<Record<string, ActionDragState>>;
     startDrag(clipId: string, state: ActionDragState): void;
     updatePosition(clipId: string, start: number, end: number): void;
     getLatest(clipId: string): ActionDragState | undefined;
     clear(clipId: string): void;
   }
   ```
2. **Update** `useLibraryCallbacks.ts` and `useClipDrag.ts` to use the coordinator API instead of direct ref mutation.
3. The coordinator is the single writer for `latestStart`/`latestEnd`, eliminating the implicit race between library callbacks and pointer-move handlers. When `crossTrackActive` is true, library callbacks write to `initialStart/initialEnd` only; `useClipDrag` owns `latestStart/latestEnd`.
4. **Validate:** Build passes; cross-track drag works correctly; no stale state after rapid drag sequences.

### Step 8: Clean up `ClipAction` stopPropagation (`ClipAction.tsx`)
**Scope:** Small
1. **Remove** `onPointerDown` stopPropagation (line 45). The capture-phase listener in `useClipDrag` (line 425) fires first regardless, so this stopPropagation only prevents bubbling to the timeline library — which is already handled by pointer capture in `useClipDrag`.
2. **Keep** `onClick` stopPropagation (needed to prevent timeline background deselection).
3. **Keep** `onDoubleClick` stopPropagation (same reason).
4. **Add a comment** on the remaining stopPropagation calls explaining why they're needed.
5. **Validate:** Click-to-select, double-click-to-open-asset, and drag-to-move all work. Verify no spurious timeline background click events fire.

### Step 9: Fix `EditorPaneTab` generation pane height hack (`EditorPaneTab.tsx:41–43`, `PanesContext.tsx:87–121`)
**Scope:** Medium
1. **Problem:** `EditorPaneTab` manually subtracts `effectiveGenerationsPaneHeight` from `effectiveEditorPaneHeight` (lines 41–43), duplicating logic that `getEffectivePaneHeights` already handles. This can double-compress the editor pane.
2. **Fix:** Extend `getEffectivePaneHeights` to accept `isGenerationsPaneVisible: boolean` and only allocate generations height when visible. Return `effectiveEditorPaneHeight` that already accounts for the generations pane when both are active.
3. **Update** `PanesProvider` to pass visibility state into `getEffectivePaneHeights`.
4. **Remove** the hack in `EditorPaneTab.tsx` lines 41–43 — just use `effectiveEditorPaneHeight` directly.
5. **Update** existing tests in `src/shared/contexts/__tests__/PanesContext.test.tsx` to cover the visibility-aware calculation.
6. **Validate:** Editor pane at various viewport sizes with generations pane open/closed. No double compression. The `Math.max(200, ...)` floor is now only in one place (`getEffectivePaneHeights`).
