- Historical failure/block examples: [.megaplan/plans/implement-a-human-like-20260501-1604/state.json](/Users/user_c042661f/Documents/Veas/.megaplan/plans/implement-a-human-like-20260501-1604/state.json:266) has `execute` result `blocked`, `duration_ms: 2620412`; same file has review JSON parse failures at lines 321 and 330.
- Finalize validation failures appear in [.megaplan/plans/implement-the-simplest-20260502-1531/state.json](/Users/user_c042661f/Documents/Veas/.megaplan/plans/implement-the-simplest-20260502-1531/state.json:120) and `.megaplan/plans/implement-the-new-20260505-1748/state.json`.

3. I did not find a reliable persisted per-output activity timestamp.
- `execution_trace.jsonl` records `item.started` / `item.completed`, command text, output, exit code, file changes, and agent messages, but the JSON events generally do not have event timestamps.
- Some trace files include raw non-JSON log lines with timestamps, so they are not a clean activity ledger.
- Current durable signal is effectively `active_step.started_at`, completed `history[].timestamp + duration_ms`, session `last_used_at`, lock held-ness, and artifact mtimes/content.

4. Smallest useful extension:
- Add optional fields to `active_step`: `last_activity_at`, `last_activity_kind`, maybe `last_activity_detail`.
- Update them at low-risk existing write points: active step start, progress/batch checkpoint write, `execution_trace` item completion, raw output write, receipt write.
- Add a failure artifact per failed attempt, e.g. `attempt_failure_<phase>_v<iteration>_a<attempt>.json`, containing `phase`, `iteration`, `attempt`, `run_id`, `session_id`, `started_at`, `failed_at`, `duration_ms`, `error_type`, `message`, `raw_output_file`, `stdout_tail`/`stderr_tail`, and relevant artifact hashes.
- Also append/maintain `latest_failure` in `state.json`; the type already allows it, but these local plan states do not show it populated.

5. Caveats from actual shapes:
- Do not treat `.plan.lock` existence as active work; every sampled plan has the file, often stale. Use `fcntl` held-ness.
- `active_step` can be left behind even when `current_state` is not obviously running.
- Receipts are success-biased in local artifacts; failed attempts often only appear in `history` with `raw_output_file` and `message`.
- Profiles are partly persisted as resolved `config.phase_model`; built-in profile TOMLs exist under `/Users/user_c042661f/Documents/megaplan/megaplan/profiles`, but `codex-kimi-deepseek-med` was present in state and not in those built-ins, so recovery should trust persisted `phase_model` over re-resolving a possibly missing profile name.
- Execution batch/receipt `metrics` can be huge and heterogeneous; watchdog logic should avoid parsing deep batch payloads for liveness unless it only needs mtime or a small top-level checkpoint marker.
