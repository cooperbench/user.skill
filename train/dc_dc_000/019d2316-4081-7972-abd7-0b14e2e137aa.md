Incremental execution persistence for megaplan

## Problem
Currently, run_command() in workers.py uses subprocess.run() with capture_output=True, which buffers all output in memory. If the execute step times out (now 2 hours) or crashes, ALL work is lost — the execution.json, finalize.json updates, and task tracking are never written to disk.

The executor agent (claude or codex) does real work during execution — it modifies files in the project repo, runs tests, fills out task_updates with executor_notes, etc. But the tracking of that work (which tasks are done, what commands were run, sense check acknowledgments) only gets persisted AFTER the subprocess finishes successfully. If it times out, the actual code changes exist in the repo but the megaplan tracking state is lost.

## Goal
Make the execute step save progress incrementally so that:
1. As the executor fills out task_updates and sense_check_acknowledgments, those are written to a persistent progress file immediately
2. If the process times out or crashes, the progress file captures whatever was completed
3. The system can resume/re-run execute and pick up where it left off (it already has re-run guidance in the prompt for done tasks)

## Key constraints
- The executor agent returns a single JSON blob at the end via --json-schema (claude) or -o output_path (codex). We can't change how claude/codex emit their final structured output.
- For codex: it already writes to an output file (-o), but only at completion.
- For claude: output comes on stdout as a JSON envelope, only at completion.
- The execute step already handles re-execution gracefully — _execute_prompt checks for done/pending tasks in finalize.json and generates re-run guidance.

## Approach to explore
Since we can't change how the agents emit structured output, the incremental persistence should focus on:

1. Streaming stdout/stderr to a progress file — Replace subprocess.run() with subprocess.Popen() for the execute step, tee-ing output to both an in-memory buffer AND a file on disk (execution_progress.jsonl or similar in plan_dir). This captures the agent's thinking/work-in-progress even on timeout.

2. Progress file in plan_dir — Write a execution_progress.txt (or .jsonl) that captures raw agent output as it streams. On timeout, this file has whatever the agent produced. The handler can then attempt to parse partial results from it.

3. Timeout recovery — When handle_execute catches a timeout CliError, instead of just re-raising, check for the progress file and attempt to extract any completed task_updates from the agent's output so far. Update finalize.json with whatever was completed.

4. The re-run path already works — Since _execute_prompt already generates re-run guidance for done vs pending tasks, if we can persist partial task completion on timeout, the next execute run will correctly focus on remaining work.

## Files involved
- megaplan/workers.py — run_command() needs a streaming variant for execute; timeout handling needs to capture partial output
- megaplan/handlers.py — handle_execute() needs timeout recovery logic to parse partial progress
- megaplan/prompts.py — Already handles re-execution, may need minor tweaks

        # Implementation Plan: Incremental Execution Persistence

## Overview
`run_command()` in `workers.py:80` uses `subprocess.run(capture_output=True)`, which buffers all stdout/stderr in memory. If the execute step times out (2h) or crashes, the structured JSON output is lost entirely — even though the executor agent has already modified files in the project repo. The `handle_execute()` handler at `handlers.py:1226` catches the `CliError` from timeout but only has access to whatever partial stdout `TimeoutExpired` captured (often empty for buffered output), so it re-raises without persisting any progress.

The goal is to stream executor output to disk during execution, so that on timeout we can salvage partial `task_updates` and `sense_check_acknowledgments` from the agent's raw output, merge them into `finalize.json`, and allow the existing re-execution path (`prompts.py:399-418`) to pick up where things left off.

Key constraints:
- Cannot change how claude/codex emit structured output (single JSON blob at end)
- The structured payload itself won't appear until completion, but the agent's conversational output often contains task completion signals we can mine
- Codex already writes to an output file via `-o`, but only at process end
- The re-execution prompt path already works — it checks `finalize.json` for done/pending tasks

## Phase 1: Streaming Infrastructure

### Step 1: Add `run_command_streaming()` to workers.py (`megaplan/workers.py:80`)
**Scope:** Medium
1. **Add** a new function `run_command_streaming()` alongside the existing `run_command()`. It uses `subprocess.Popen()` with `stdout=PIPE, stderr=PIPE` and reads output line-by-line, writing each line to both an in-memory buffer and a progress file on disk.
2. **Accept** a `progress_path: Path | None` parameter. When provided, output is tee'd to that file. When `None`, behavior is identical to `run_command()`.
3. **Handle** `TimeoutExpired` — on timeout, `Popen.kill()` the process, flush the progress file, and raise `CliError("worker_timeout", ...)` with `extra={"raw_output": <buffered_content>, "progress_path": str(progress_path)}`.
4. **Keep** `run_command()` unchanged — only the execute step needs streaming.
   ```python
   def run_command_streaming(
       command: list[str],
       *,
       cwd: Path,
       stdin_text: str | None = None,
       timeout: int | None = WORKER_TIMEOUT_SECONDS,
       progress_path: Path | None = None,
   ) -> CommandResult:
   ```

### Step 2: Wire streaming into `run_claude_step` and `run_codex_step` for execute (`megaplan/workers.py:510`, `megaplan/workers.py:542`)
**Scope:** Small
1. **Add** a `progress_path` parameter to `run_claude_step()` and `run_codex_step()`, defaulting to `None`.
2. **When** `step == "execute"` and a `progress_path` is provided, call `run_command_streaming()` instead of `run_command()`.
3. **Update** `run_step_with_worker()` at `workers.py:663` to accept and pass through `progress_path`.

## Phase 2: Progress Extraction

### Step 3: Add progress extraction utilities (`megaplan/workers.py` or new `megaplan/progress.py`)
**Scope:** Medium
1. **Add** `extract_partial_task_updates(raw_output: str) -> list[dict]` — scans the raw agent output for task completion signals. The executor prompt tells the agent to return `task_updates` with specific fields; the agent's conversational output typically mentions task IDs and status changes as it works. This function uses regex/heuristic parsing to find:
   - Lines like `"task_id": "T1"` paired with `"status": "done"` in JSON-like fragments
   - JSON objects that partially match the `task_updates` schema
   - Falls back to empty list if nothing parseable is found
2. **Add** `extract_partial_sense_checks(raw_output: str) -> list[dict]` — similar extraction for sense check acknowledgments.
3. **Keep extraction conservative** — only extract items where both the ID and status/note are clearly present. Better to under-extract than to fabricate progress.

### Step 4: Add `merge_partial_progress()` helper (`megaplan/handlers.py`)
**Scope:** Small
1. **Add** a function that takes extracted partial task updates and merges them into `finalize.json` data, using the same field-merge logic as the existing `_validate_and_merge_batch()` but with relaxed validation (no blocking on incomplete coverage since this is a recovery path).
2. **Write** the updated `finalize.json` to disk so the re-execution path can find it.

## Phase 3: Timeout Recovery

### Step 5: Add timeout recovery to `handle_execute()` (`megaplan/handlers.py:1240`)
**Scope:** Medium
1. **Modify** the `except CliError` block at `handlers.py:1242` to detect `error.code == "worker_timeout"`.
2. **On timeout**, before re-raising:
   - Read the progress file from `plan_dir / "execution_progress.txt"`
   - Call `extract_partial_task_updates()` and `extract_partial_sense_checks()` on the raw output
   - If any progress was extracted, merge into `finalize.json` via `merge_partial_progress()`
   - Write updated `finalize.json` and `final.md` to disk
   - Record the partial progress in the step failure history entry
   - Still re-raise the error (the caller decides whether to re-run)
3. **Pass** `progress_path=plan_dir / "execution_progress.txt"` when calling `run_step_with_worker()`.

### Step 6: Update `run_step_with_worker()` to pass progress_path (`megaplan/workers.py:663`)
**Scope:** Small
1. **Accept** an optional `progress_path` parameter in `run_step_with_worker()`.
2. **Pass** it through to `run_claude_step()` or `run_codex_step()`.

## Phase 4: Tests

### Step 8: Integration test timeout recovery (`tests/test_megaplan.py`)

Incremental execution persistence for megaplan

## Problem
Currently, run_command() in workers.py uses subprocess.run() with capture_output=True, which buffers all output in memory. If the execute step times out (now 2 hours) or crashes, ALL work is lost — the execution.json, finalize.json updates, and task tracking are never written to disk.

The executor agent (claude or codex) does real work during execution — it modifies files in the project repo, runs tests, fills out task_updates with executor_notes, etc. But the tracking of that work (which tasks are done, what commands were run, sense check acknowledgments) only gets persisted AFTER the subprocess finishes successfully. If it times out, the actual code changes exist in the repo but the megaplan tracking state is lost.

## Goal
Make the execute step save progress incrementally so that:
1. As the executor fills out task_updates and sense_check_acknowledgments, those are written to a persistent progress file immediately
2. If the process times out or crashes, the progress file captures whatever was completed
3. The system can resume/re-run execute and pick up where it left off (it already has re-run guidance in the prompt for done tasks)

## Key constraints
- The executor agent returns a single JSON blob at the end via --json-schema (claude) or -o output_path (codex). We can't change how claude/codex emit their final structured output.
- For codex: it already writes to an output file (-o), but only at completion.
- For claude: output comes on stdout as a JSON envelope, only at completion.
- The execute step already handles re-execution gracefully — _execute_prompt checks for done/pending tasks in finalize.json and generates re-run guidance.

## Approach to explore
Since we can't change how the agents emit structured output, the incremental persistence should focus on:

1. Streaming stdout/stderr to a progress file — Replace subprocess.run() with subprocess.Popen() for the execute step, tee-ing output to both an in-memory buffer AND a file on disk (execution_progress.jsonl or similar in plan_dir). This captures the agent's thinking/work-in-progress even on timeout.

2. Progress file in plan_dir — Write a execution_progress.txt (or .jsonl) that captures raw agent output as it streams. On timeout, this file has whatever the agent produced. The handler can then attempt to parse partial results from it.

3. Timeout recovery — When handle_execute catches a timeout CliError, instead of just re-raising, check for the progress file and attempt to extract any completed task_updates from the agent's output so far. Update finalize.json with whatever was completed.

4. The re-run path already works — Since _execute_prompt already generates re-run guidance for done vs pending tasks, if we can persist partial task completion on timeout, the next execute run will correctly focus on remaining work.
