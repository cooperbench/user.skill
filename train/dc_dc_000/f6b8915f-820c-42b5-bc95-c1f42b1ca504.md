## The Core Problem

The current approach copies data at task-completion time (`complete_task` → `handleVariantOnChild` → creates a variant on the parent). This is a **point-in-time snapshot** that immediately starts drifting:

- User regenerates the segment → parent variant is stale
- User changes params → parent doesn't know
- User adds a 3rd image → orphaned propagated variant still sitting on the parent
- User deletes/reorders images → `propagated_from_child` reference may be broken

You're fighting a losing battle syncing two copies of the same data.

## The Better Approach: Present, Don't Copy

Instead of duplicating segment data onto the parent at the task level, **have the UI treat the single child segment as the final video**. No copy, no sync — just a different lens on the same data.

The natural place for this is **`useSegmentOutputsForShot`** (or a thin wrapper around it), because that's where the parent/child distinction is already being made. Specifically:

### What changes:

**1. `useSegmentOutputsForShot` gains image-count awareness**

When `images.length <= 2`, instead of returning the parent generation as the "final video," return the single completed child segment. All its params (phase config, LoRAs, motion, prompts, guidance) come along for free because you're showing the actual object.

**2. `FinalVideoSection` shows the segment directly**

It already takes `parentGenerations` — if the hook hands it the child segment instead, it just works. The video URL, thumbnail, params are all there. Regeneration triggers would target the segment task, not a join task.

**3. `SegmentOutputStrip` hides when `images.length <= 2`**

Simple guard in `TimelineTrackPrelude.tsx`. The strip is redundant when the segment IS the final video.

**4. Remove (or gate) the backend propagation**

The `single_segment_propagation` logic in `generation-handlers.ts:353-388` either gets removed or gated behind `images.length > 2` (though the backend may not easily know the image count — another reason to do this client-side).

### Why this works for transitions:

- **User adds a 3rd image**: `images.length` crosses the threshold, hook stops treating child as final video, SegmentOutputStrip appears, normal multi-segment join flow resumes. The parent generation container is still there.
- **User removes images back to ≤2**: Hook switches back, segment becomes the final video again. No data migration needed.
- **User regenerates the segment**: The child generation updates, and since the UI is pointing at the actual child (not a copy), it updates automatically.
- **All transformations stay in sync**: There's nothing to sync — there's only one source of truth.

### Why client-side, not task-level:

| | Task-level (current) | Client/hook-level (proposed) |
|---|---|---|
| **Reactivity** | One-shot at completion | Live — reacts to image count changes |
| **Sync** | Needs manual propagation for every param | No sync needed — single source |
| **Transition** | Stale copies linger when images change | Clean switch based on current state |
| **Complexity** | Backend needs to know about UI state (image count) | Frontend already has image count |

- **Standard** (default for megaplan): cross-cutting changes touching many subsystems, unfamiliar codebase areas, ambiguous requirements, changes with high breakage risk, or anything where the plan itself needs debate.
- **Heavy**: high-stakes changes where getting it wrong is expensive — security-critical code, data migrations, public API changes. Uses the same visible `prep` phase but with 8 critique checks instead of 4.

Default to standard unless the task is clearly simple enough for light. Do not ask the user to choose robustness — pick it yourself based on the above. Only ask execution mode (auto-approve or review) when using megaplan.

## Step Rules
- `plan`: inspect the repository first; produce the plan plus `questions`, `assumptions`, and `success_criteria`. Each criterion is `{"criterion": "...", "priority": "must|should|info"}`. `must` = hard gate (reviewer blocks), `should` = quality target (reviewer flags but doesn't block), `info` = human reference (reviewer skips).
- `prep`: make repository investigation explicit before planning. Respect `skip: true` when the task is already concrete enough.
- `critique`: surface concrete flags with concern, evidence, category, and severity; reuse open flag IDs; call out scope creep. Also validate that success criteria priorities are well-calibrated — `must` criteria should be verifiable yes/no, subjective goals should be `should`.
- `gate`: read the response, warnings, and `orchestrator_guidance`. (Skipped at light robustness.)
- `revise`: show the delta, flags addressed, and flags remaining. At light robustness, routes to `finalize`; otherwise loops back through `critique` and `gate`.
- `review`: judge success against the success criteria and the user's intent, not plan elegance. Only block on `must` criteria failures. `should` failures are flagged but don't require rework. `info` criteria are waived.
