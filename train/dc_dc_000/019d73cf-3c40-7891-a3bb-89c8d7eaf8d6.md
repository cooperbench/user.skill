The payments part is now a shared Solana payout subsystem used by grants and admin-triggered payouts. At a high level: - `PaymentService` creates payment ledger rows, confirms them, executes them, and recovers safely after restarts: [payment_service.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/payments/payment_service.py) - `SolanaProvider` is the chain adapter that validates wallet/address/balance, submits the SOL transfer, and confirms chain status: [solana_provider.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/payments/solana_provider.py) - The database holds three main payment-side tables: - `wallet_registry` - `payment_channel_routes` - `payment_requests` in [payments.sql](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/sql/payments.sql) How the flow works: - A producer creates a payment request. - The payment starts in `pending_confirmation`. - Once the intended recipient confirms, it moves to `queued`, then `processing`, then `submitted`, then either `confirmed`, `failed`, or `manual_hold`. - If submission or confirmation becomes ambiguous, it fails closed into `manual_hold` instead of retrying blindly. Current producers: - `GrantsCog` uses it for ArcCompute microgrants: [grants_cog.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/grants/grants_cog.py) - `AdminChatCog` uses it for admin-triggered payouts with stored-wallet or wallet-collection flow: [admin_chat_cog.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/admin_chat/admin_chat_cog.py) Admin-triggered payout flow: - Admin says to pay a user an amount in SOL. - If the user already has a verified wallet, the bot uses it. - Otherwise the bot asks that exact user for a wallet in-channel. - Bot sends a tiny fixed test payment first. - After the test confirms, bot asks the recipient to confirm the final payout. - Then it queues the real payment. Safety properties: - no auto-resend after ambiguous submission - recipient identity is enforced on confirmation - payment and wallet tables are excluded from broad admin DB querying - manual review path exists via `manual_hold` Weakest current spot: - admin-triggered payouts do not yet have a hard max-amount cap, so large amounts rely on the admin/agent getting the number right.
