        Plan:
        # Implementation Plan: X/Twitter OAuth Feedback Section

## Overview
Add a `/assorted/feedback` section to an existing React SSR + Express + Supabase personal website. Users sign in with X (Twitter) OAuth, submit text + image feedback, and see a reverse-chronological listing. The site owner can respond to each entry. Feedback from users with <100 followers is flagged.

**Current stack:** React 19 / React Router 6 / Express SSR / Vite / Supabase (Postgres + Storage) / Tailwind CSS / Railway deployment. No auth system exists today — Supabase is used only for posts (read-only with anon key). The `@supabase/supabase-js` SDK is **not** installed; all DB access goes through a thin REST wrapper (`src/lib/supabase.ts`).

---

## Step 1: Install Supabase JS SDK
**Scope:** Small
1. **Add** `@supabase/supabase-js` as a production dependency. The existing REST wrapper is too low-level for auth flows (session management, OAuth redirects, storage uploads). The SDK will handle auth, realtime tokens, and the Storage API.
2. **Create** `src/lib/supabase-client.ts` — a browser-side singleton using the public anon key (already injected via `window.__APP_CONFIG__`). This is separate from the existing server-side `supabase.ts`.

## Step 2: Configure X OAuth in Supabase Dashboard
**Scope:** Small (manual / no code)
1. In the Supabase dashboard, enable the **Twitter** auth provider under Authentication → Providers.
2. Create a Twitter/X developer app at developer.x.com, obtain API Key + Secret, set the callback URL to `https://<supabase-url>/auth/v1/callback`.
3. Enter the credentials in the Supabase Twitter provider config.
4. **Verify** by calling `supabase.auth.signInWithOAuth({ provider: 'twitter' })` from the browser console on the dev server.

## Step 3: Create Supabase database table & storage bucket
**Scope:** Small
1. **Create migration** `supabase/migrations/YYYYMMDD_create_feedback_table.sql`:
   ```sql
   create table feedback (
     id uuid default gen_random_uuid() primary key,
     user_id uuid references auth.users(id) not null,
     x_username text not null,
     x_user_id text not null,
     x_avatar_url text,
     x_followers_count int,
     is_suspicious boolean generated always as (x_followers_count < 100) stored,
     feedback_text text not null,
     image_paths text[] default '{}',
     owner_response text,
     owner_response_at timestamptz,
     created_at timestamptz default now()
   );

   alter table feedback enable row level security;

   -- Anyone can read all feedback
   create policy "Public read feedback" on feedback
     for select using (true);

   -- Authenticated users can insert their own feedback
   create policy "Auth users insert own feedback" on feedback
     for insert with check (auth.uid() = user_id);

   -- Only service role (server) can update (for owner responses)
   -- No RLS policy for update = only service_role can update
   ```
2. **Create storage bucket** `feedback-images` (public read, authenticated upload) via migration or dashboard.
3. **Run** the migration against the hosted Supabase instance.

## Step 4: Add types and data-fetching lib
**Scope:** Small
1. **Add types** to `src/types/index.ts`:
   ```ts
   export interface FeedbackEntry {
     id: string;
     x_username: string;
     x_avatar_url: string | null;
     x_followers_count: number | null;
     is_suspicious: boolean;
     feedback_text: string;
     image_paths: string[];
     owner_response: string | null;
     owner_response_at: string | null;
     created_at: string;
   }
   ```
2. **Add** `{ page: 'feedback'; feedback: FeedbackEntry[] }` variant to the `InitialData` union.
3. **Create** `src/lib/feedback.ts` with:
   - `getFeedbackList()` — server-side fetch (service role) returning `FeedbackEntry[]` ordered by `created_at desc`.
   - `submitFeedback(supabase, text, images)` — client-side: uploads images to storage, inserts row.
   - `getPublicImageUrl(path)` — resolves storage paths to public URLs.

## Step 5: Add server route for `/assorted/feedback`
**Scope:** Small
1. **Update** `src/server.ts`:
   - Add `/assorted/feedback` to the pathname matching block (~line 117-143).
   - Fetch feedback list server-side and pass as initial data: `{ page: 'feedback', feedback: await getFeedbackList() }`.
   - Add `'feedback': 'Feedback - POM'` to `PAGE_TITLES` (~line 28).
2. **Add** an API endpoint `POST /api/feedback/respond` (Express JSON body) for the owner to submit responses. This endpoint checks a secret token (env var `OWNER_SECRET`) since there's no admin auth system. It updates `owner_response` and `owner_response_at` on the feedback row.

## Step 6: Build the Feedback page components
**Scope:** Large — this is the bulk of the UI work.

### 6a: Auth hook — `src/hooks/useAuth.ts`
- Wraps Supabase auth: `signInWithTwitter()`, `signOut()`, `user`, `loading`.
- Extracts X metadata (username, avatar, followers) from `user.user_metadata`.

### 6b: Feedback list page — `src/pages/Feedback.tsx`
- **Header** with "Feedback" tab active.
- **Sign-in button** (if not authed): "Sign in with X to submit feedback".
- **Submission form** (if authed): textarea + image upload (max 3 images, max 5MB each) + submit button. Shows the user's X handle.
- **Feedback list** in reverse chronological order:
  - Each entry shows: X avatar, `@username` linking to `x.com/username`, timestamp, first N lines of text (truncated), suspicious badge if applicable.
  - If owner response exists: show first 5 lines, truncated.
  - Click to expand full text + full response + images.
- Use existing patterns from other pages (Header, container layout, Tailwind classes).

### 6c: Feedback detail expanded view
- Full feedback text, all attached images displayed inline, owner response (full).
- This can be an expand-in-place pattern (like cards on the home page) or a separate detail route. Recommend expand-in-place to match existing UX patterns.

## Step 7: Wire up routing
**Scope:** Small
1. **Update** `src/App.tsx` (~line 93): add route for `/assorted/feedback` → `<FeedbackPage>`.
2. **Update** `src/data/assorted-content.ts` (~line 56): add entry to `ASSORTED_DIRECTORY_ITEMS`:
   ```ts
   { href: '/assorted/feedback', name: 'Feedback', description: 'Submit praise or criticism' }
   ```

## Step 8: Owner response mechanism
**Scope:** Medium
1. **Option A (recommended — simple):** A small client-side form visible only when a specific query param + secret is present (e.g., `?owner_key=xxx`). This avoids building an admin auth system. The form calls `POST /api/feedback/respond` with the secret.
2. **Option B:** Separate admin page with its own auth. More work, overkill for a personal site.
3. The response form appears inline below each feedback entry when in "owner mode".

## Step 9: Environment variables & deployment
**Scope:** Small
1. **Add** to Railway environment:
   - `OWNER_SECRET` — random string for owner response auth.
   - Twitter OAuth creds are in Supabase dashboard, not in the app env.
2. **Update** `.env.example` with the new var.
3. **Build & deploy** — `npm run build` should pick up new files automatically.

## Step 10: Validation & testing
**Scope:** Medium
1. **Manual E2E flow:**
   - Visit `/assorted/feedback`, verify empty state renders.
   - Click "Sign in with X", complete OAuth flow, verify redirect back.
   - Submit feedback with text only → verify it appears in the list.
   - Submit feedback with images → verify upload and display.
   - Create a test account with <100 followers → verify suspicious badge.
   - Use owner secret to post a response → verify it displays.
2. **Unit tests** (`src/pages/__tests__/Feedback.test.tsx`):
   - Renders feedback list from initial data.
   - Truncation behavior for long text.
   - Suspicious badge shown when `is_suspicious` is true.
