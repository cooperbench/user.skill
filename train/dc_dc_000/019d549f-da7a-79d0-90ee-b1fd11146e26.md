## Overview

Two resilience gaps in the megaplan hermes worker:

1. **Content fallback**: The MiniMax→OpenRouter fallback only triggers on API exceptions, not on garbage responses (parse failures, validation failures). When `parse_agent_output()` raises `CliError("worker_parse_error")` or `validate_payload()` raises `CliError("parse_error")`, the code doesn't retry with the fallback provider — it just dies.

2. **Checkpoint resume**: The eval runner code (`evals/run_evals.py`) **does not exist in this repo**. The workspace directory structure described in the brief doesn't exist either. This feature cannot be implemented without the eval runner. See questions below.

### Current code shape

- `hermes_worker.py:run_hermes_step()` (line 254–506): The fallback is in the `except Exception` block (lines 421–464) around `agent.run_conversation()`. After that, `parse_agent_output()` (line 469) and `validate_payload()` (line 482) can raise `CliError` with no fallback path.

- `parallel_critique.py:_run_check()` (line 78–156): Same pattern — fallback on exception from `agent.run_conversation()` (lines 112–130), then `parse_agent_output()` (line 131) and `clean_parsed_payload` (line 140) and a payload structure check (lines 142–147) can raise with no fallback.

- Both files have duplicated model-resolution and fallback logic. `parallel_critique.py` has a cleaner `_resolve_model()` helper + `_make_agent()` factory already.

### Design for Fix 1

The simplest approach: **wrap the entire run+parse+validate sequence** in the try/except, not just the API call. Currently the structure is:

```python
try:
    result = agent.run_conversation(...)
except Exception:
    # fallback only here

payload = parse_agent_output(...)  # can raise CliError
validate_payload(...)              # can raise CliError
```

Change to:

```python
def _run_with_fallback(run_fn, model, agent_kwargs):
    try:
        return run_fn(model, agent_kwargs)
    except (CliError, Exception) as exc:
        # try fallback provider if available
        ...
        return run_fn(fallback_model, fallback_kwargs)
```

This way, if the primary provider returns garbage that fails parsing or validation, the fallback triggers automatically. The fallback re-runs the entire call (new agent, new API call, new parse+validate), which is correct.

**Generalization**: The brief says this should work for ANY provider, not just MiniMax. The current fallback is MiniMax-specific (checks `model.startswith("minimax:")`). To generalize, we need a fallback provider config. The simplest approach: any model with a direct API key also gets OpenRouter as fallback (since OpenRouter routes to most providers). This keeps the existing MiniMax behavior and extends it.
