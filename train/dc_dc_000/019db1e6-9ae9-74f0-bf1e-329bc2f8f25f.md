# Implementation Plan: Drop-to-Generation

## Overview
Add a global OS file-drop affordance that creates new gallery generations. A small chip appears above the `GenerationsPane` control tab whenever the user drags a file anywhere over the app. Dropping on the chip uploads the file as a new generation (no shot attachment). For files at or above a size threshold, the file is kept local via a `FileSystemHandle` persisted to IndexedDB; only a small thumbnail is uploaded for gallery display, and the full bytes are uploaded lazily when a worker actually needs them.

**Repository shape that matters:**
- Global DnD today lives in `src/app/App.tsx:62-78` (a @dnd-kit `DndContext`). `useAppExternalDrop.ts:74-115` consumes `isExternalFile`/`externalFile` from dnd-kit draggable data — this feature introduces a parallel, truly native-OS drop path (listeners on `window`), because @dnd-kit does not observe OS drag-ins with only bytes (no dnd-kit active).
- `GenerationsPane.tsx:49-90` renders `PaneControlTab` (`src/shared/components/PaneControlTab.tsx:92+`) at `bottom` with dynamic height/horizontal offsets from `panesStore`. A new chip needs the same horizontal offset math.
- Existing external-image upload helper: `src/shared/hooks/shots/externalImageDrop.ts:112-153` (`createGenerationForUploadedImage`) — we will extract/reuse the "upload + insert generations row + insert primary variant" subset and drop the shot-attachment step for this feature.
- Uploaders: `imageUploader.ts:189-249`, `videoUploader.ts:185-235`. Storage convention: `storagePaths.upload(userId, filename)`.
- Generation row: `src/domains/generation/types/generationRow.ts:9-28` — today there is **no** `storage_mode`, `local_handle_id`, or similar field. Phase 3 adds one via migration.
- No existing IndexedDB / FileSystemHandle usage (`Grep` on `FileSystemHandle`, `showOpenFilePicker`, `storage_mode`, `local_mode` returns zero matches in `src/`). Entire local-persistence layer is new.

**Constraints that matter:**
- Worker/edge pipeline (unified_task_creation + worker fetch) must keep working for existing remote-mode generations — local-mode is additive, detected at task-build time.
- Existing inner-tool drop zones (e.g., shot-group droppables in the shots pane) must keep functioning. The global chip is the only new native-OS drop target; other OS-file drops still fall through to dnd-kit's external-file synth path where it exists.
- Supabase safety rules from `CLAUDE.md`: deploy edge fns individually, `db push --linked` only, no `db reset`.
- Motion/design: chip matches existing pane tab styling (zinc-900/95 surface, bottom side, smooth transitions).

## Phase 1: Global drag detection + chip above pane tab (UI only)

### Step 1: Add a global OS-drag store slice (`src/shared/state/dragOverlayStore.ts` — new)
**Scope:** Small
1. **Create** a zustand store with `{ isDraggingFiles: boolean, setDragging: (v) => void }`. Keep it separate from `panesStore` so pane rendering does not re-render on every drag event.
2. **Export** typed hook `useIsDraggingFiles()` returning the boolean.
3. **Rationale** for a dedicated store: the dragover event fires at high frequency; co-locating with pane state would thrash subscribers.

### Step 2: Add a window-level drag listener (`src/app/hooks/useGlobalFileDragDetection.ts` — new)
**Scope:** Medium
1. **Attach** `dragenter`/`dragover`/`dragleave`/`drop` listeners on `window` via `useEffect`. Gate all state flips on `event.dataTransfer?.types?.includes('Files')` so internal dnd-kit drags do not trigger the chip.
2. **Debounce** the "leave" flip with a counter (`enter`/`leave` events nest weirdly on child boundaries) — track depth and flip to false only when depth returns to 0.
3. **Preserve default** behaviors outside the chip; do NOT `preventDefault` on document-level dragover except over the chip itself (so inner tool drop zones still work).
4. **Mount** the hook once in `AppInternalContent` in `src/app/App.tsx:32`.

### Step 3: Build the drop chip component (`src/features/gallery/components/GenerationsPane/components/GenerationsDropChip.tsx` — new)
**Scope:** Medium
1. **Render** a small pill positioned directly above the `PaneControlTab` — match existing tab horizontal offset formula from `GenerationsPane.tsx:53-57` (`isShotsPaneLocked ? shotsPaneWidth : 0 - isTasksPaneLocked ? tasksPaneWidth : 0`).
2. **Visibility:** only when `useIsDraggingFiles()` is true AND the user is not on the Image Generation page (match `GenerationsPaneTab` early-return at line 45-47).
3. **Styling:** `fixed`, z-index one layer above `UI_Z_LAYERS.GENERATIONS_PANE` (use a new constant `GENERATIONS_DROP_CHIP` in `src/shared/lib/uiLayers.ts`), `bottom: effectiveGenerationsPaneHeight + tabHeight + gap`. Copy surface look from the tab (`bg-zinc-900/95`, rounded, border).
4. **Content:** icon (lucide `ImagePlus` or `Upload`) + label "Drop to add as generation". Hover state darkens + label grows. No drop handler wired yet — purely visual, chip intercepts `dragover` with `preventDefault` so OS shows a copy cursor, but drop is a noop toast for this phase ("Drop-to-generation coming soon" — dev-only, removed at end of Phase 2).
5. **Mount** from `GenerationsPane.tsx` sibling to `GenerationsPaneTab`.

### Step 4: Sanity-check in browser
**Scope:** Small
1. **Start** dev server (`npm run dev`), drag an image from desktop over the app — chip appears over the pane tab; drags inside the app (dnd-kit) do NOT trigger it.
2. **Verify** horizontal offset updates when shots/tasks panes lock/unlock.
3. **Verify** chip is suppressed on the `/tools/image-generation` route.

## Phase 3: Local-handle persistence for large files

### Step 8: DB migration for local-mode generations (`supabase/migrations/<timestamp>_generations_storage_mode.sql` — new)
**Scope:** Small
1. **Add** columns to `public.generations`:
   - `storage_mode text not null default 'remote'` with `check (storage_mode in ('remote','local','uploading'))`.
   - `local_handle_id uuid` (nullable — points to a row in a new `local_media_handles` table).
   - `local_file_name text`, `local_file_size bigint`, `local_file_mime text` — denormalized so gallery can render without opening the handle.
2. **Create** `local_media_handles` (user-scoped, not project-scoped per assumption): `id uuid pk`, `user_id uuid not null`, `created_at timestamptz default now()`. (Actual `FileSystemHandle` blob lives in browser IndexedDB, keyed by this id; the row is just a server-side anchor so multiple generations can reference one handle if the same file is dropped twice.)
3. **RLS** on `local_media_handles`: user can select/insert/delete own rows only.
4. **Deploy** with `npx supabase db push --linked`.

### Step 9: IndexedDB handle store (`src/shared/lib/media/localHandleStore.ts` — new)
**Scope:** Medium
1. **Implement** a thin wrapper over the `indexedDB` browser API (no new npm dep — inline ~80 LOC) with:
   - `saveHandle(id: string, handle: FileSystemFileHandle): Promise<void>`
   - `loadHandle(id: string): Promise<FileSystemFileHandle | null>`
   - `deleteHandle(id: string): Promise<void>`
   - `listHandleIds(): Promise<string[]>`
2. **Permission helpers**:
   - `ensurePermission(handle, mode: 'read' | 'readwrite' = 'read'): Promise<'granted' | 'denied' | 'prompt'>` — calls `handle.queryPermission` and, only inside a user gesture, `handle.requestPermission`.
3. **Store name:** `reigh.local-media-handles`, single object store keyed by id.

### Step 10: Extend drop handler for >=threshold path (`src/features/gallery/hooks/useDropToGeneration.ts`, `src/shared/hooks/shots/externalImageDrop.ts`)
**Scope:** Medium
1. **On drop**, attempt `event.dataTransfer.items[i].getAsFileSystemHandle()` (feature-detect; Chromium only). If available AND file >= threshold:
   - Generate a small thumbnail from the `File` (already available via `generateClientThumbnail` for images; for video, use first-frame canvas capture helper — add one if missing, ~30 LOC).
   - Upload **only the thumbnail** to Supabase.
   - Insert a `local_media_handles` row (server), then `saveHandle(row.id, handle)` to IndexedDB.
   - Insert a `generations` row with `storage_mode='local'`, `local_handle_id`, `local_file_{name,size,mime}`, `thumbnail_url=<uploaded thumb>`, `location=null`.
2. **No primary variant row** is inserted until the bytes exist in Supabase (Phase 5 does that during lazy upload). Gallery variant consumers must tolerate the absence — Phase 4 audits this.
3. **Toast** gracefully if `getAsFileSystemHandle` is missing → Phase 6 fallback hook takes over (forced upload with warning).

### Step 11: Unit tests for handle store (`src/shared/lib/media/localHandleStore.test.ts` — new)
**Scope:** Small
1. **Test** save/load/delete/list using `fake-indexeddb` (check if already in devDeps; if not, add). One test per method.

## Phase 4: Gallery resolves local-mode media via blob URL

### Step 12: Audit where gallery resolves media URLs (`src/features/gallery/**`, `src/shared/media/**`)
**Scope:** Small
1. **Grep** for `location`, `thumbnail_url`, and `public_url` usage in gallery/MediaGallery rendering paths. Identify the single chokepoint (likely a resolver in `MediaGallery/` or a thumbnail hook).

### Step 13: Local-mode media URL resolver (`src/shared/media/localMediaResolver.ts` — new, + resolver chokepoint edits)
**Scope:** Medium
1. **Implement** `useLocalMediaUrl(generation): { url: string | null, state: 'ready' | 'needs-permission' | 'missing' | 'resolving' }`:
   - If `storage_mode !== 'local'`, return `{ url: generation.location, state: 'ready' }` (passthrough).
   - Otherwise load handle from IndexedDB by `local_handle_id`.
   - `queryPermission` → if `granted`, `handle.getFile()` → `URL.createObjectURL(file)`, memoize by generation id, set state `ready`.
   - If `prompt`, do NOT auto-request; return `needs-permission` so UI can render a "Click to re-grant access" overlay on the tile.
   - If handle missing (user cleared browser data / different device), return `missing` with a CTA to re-drop or upload.
2. **Revoke** blob URLs on unmount / generation id change. Use a single module-level registry keyed by generation id so multiple tiles rendering the same generation share one URL.
3. **For thumbnails**, always prefer `thumbnail_url` (already uploaded in Phase 3) over the local blob for list views; only open the handle for fullscreen/lightbox views. This avoids permission prompts for browsing.
4. **Wire** the resolver at the single chokepoint identified in Step 12.

### Step 14: Permission re-grant UX (`src/features/gallery/components/GenerationsPane/components/LocalMediaPermissionOverlay.tsx` — new)
**Scope:** Small
1. **Overlay** rendered on local-mode tiles when resolver state is `needs-permission`. Click triggers `handle.requestPermission({ mode: 'read' })` inside the user gesture and re-runs the resolver.
2. **Overlay** for `missing` state: "File moved or browser data cleared — drop again to restore or [Upload anyway]". Upload-anyway triggers lazy upload (Phase 5 function).

## Phase 5: Lazy upload at task-build

### Step 15: Identify task-build entry points (`src/domains/generation/hooks/tasks/**`, unified task creation)
**Scope:** Small
1. **Read** the unified task creation path (per CLAUDE.md, `docs/structure_detail/unified_task_creation.md` documents it). Find where a generation's `location` / `public_url` is passed into task params/worker payload. That is the single place where a local-mode generation must be upgraded to remote-mode before proceeding.

### Step 16: Materialization helper (`src/shared/lib/media/materializeLocalGeneration.ts` — new)
**Scope:** Medium
1. **Implement** `materializeLocalGeneration(generationId): Promise<{ location: string }>`:
   - Load generation row. If `storage_mode === 'remote'`, return `{ location }` passthrough.
   - If `storage_mode === 'uploading'`, await via a single-flight `Promise` registry keyed by generation id (prevents concurrent workers from uploading the same file twice).
   - Flip row to `storage_mode='uploading'` (optimistic, but row-level — accept the race; worst case two workers both upload, last write wins on `location`).
   - Load handle from IndexedDB → `handle.getFile()` → route through `uploadImageToStorage` or `uploadVideoToStorage` by mime.
   - Insert the primary `generation_variants` row deferred from Phase 3 with `is_primary=true`, `variant_type=ORIGINAL`.
   - Update `generations.location`, `storage_mode='remote'`, null out `local_*` columns.
   - Optionally `deleteHandle(local_handle_id)` + delete the `local_media_handles` row. (Configurable — keep by default so the user's original stays re-usable.)
   - Return `{ location }`.
2. **Failure modes:**
   - Permission denied → surface error, flip row back to `local`, propagate failure to caller so task build can abort with a clear message.
   - Handle missing → same, with a different error code so UI can prompt "drop again or upload from disk".
   - Network failure → flip back to `local`, toast, let caller retry.

### Step 17: Gate task-build on materialization (task-build touchpoint identified in Step 15)
**Scope:** Medium
1. **Intercept** the point where generation inputs are collected for a task. For every input generation, if `storage_mode === 'local'`, `await materializeLocalGeneration(id)` first. Show a progress toast ("Uploading original before sending to worker…") with per-file progress piped through.
2. **Cancellation:** if the user cancels the task, abort the upload (abort controller through `imageUploader`/`videoUploader`).

### Step 18: Integration test for lazy upload (`src/shared/lib/media/materializeLocalGeneration.test.ts` — new)
**Scope:** Small
1. **Mock** Supabase client + IndexedDB (`fake-indexeddb`). Create a local generation, call materialize, assert row flips to `remote` with a `location`.
2. **Test** single-flight: two concurrent materialize calls for the same id should issue one upload.

## Phase 6: Fallback for browsers without FileSystemHandle

## Execution Order
1. Phase 1 (UI-only) first — cheapest, unblocks visual review of the drop affordance.
2. Phase 2 (<threshold path) next — exercises the full "drop → generation row → gallery refresh" loop with zero local-handle complexity.
3. Phase 3 (DB migration + IDB wrapper + large-file drop) before Phase 4 — need rows to resolve.
4. Phase 4 (gallery resolver) before Phase 5 — gallery must render local-mode tiles before we lazy-upload them.
5. Phase 5 (task-build lazy upload) is the most risk-laden — land after gallery UX is stable.
6. Phase 6 (fallback) last — small surface area, protects non-Chromium users once everything else works.

6. **Phase 6:** browser matrix smoke test (Chromium / Firefox / Safari).
7. **Broader:** `npm run typecheck` after each phase; existing test suite after Phase 3 and Phase 5.
