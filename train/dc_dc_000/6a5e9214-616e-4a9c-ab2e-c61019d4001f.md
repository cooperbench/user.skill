        # Implementation Plan: Initialize Wan2GP submodule after clone/pull in worker install commands

## Overview
`banodoco/Reigh-Worker.git` now embeds `Wan2GP/` as a git submodule. The two places that provision/refresh that repo — the install/run command builder in `reigh-app/src/shared/components/SettingsModal/commandUtils.ts` and the RunPod bootstrap script `reigh-worker-orchestrator/gpu_orchestrator/runpod/worker_startup.template.sh` — use `git clone --depth 1` + `git pull --ff-only` (or `git reset --hard origin/main`) which do not populate submodules. The fix is to insert `git submodule update --init --recursive` after the sync step in every branch, using the shell dialect appropriate to that branch. Changes must be left staged, not committed.

Constraints:
- Three shell dialects in `commandUtils.ts` (bash `&&` chain, PowerShell newline, cmd `&&` chain joined on one line).
- `worker_startup.template.sh` has two entry paths (fresh clone vs existing dir) that both converge at `git reset --hard origin/main` (L261), so one submodule call after the reset block is sufficient and simpler than duplicating at the clone site.
- Depth-1 clones still work with `git submodule update --init --recursive`; the submodule fetch is independent.
- The fallback `Headless-Wan2GP` dir has no submodule; running the command there is a harmless no-op, but the post-update verification must account for that path (no `Wan2GP/` expected there).
- **Fail fast** in the RunPod script: soft-failing the submodule update would recreate the exact bug being fixed (empty `Wan2GP/`, worker import crash later with a worse error signal). The update must either succeed or abort startup with a clear message.
- No commit — leave staged only.

### Step 3: Insert submodule update + verification into the RunPod bootstrap (`reigh-worker-orchestrator/gpu_orchestrator/runpod/worker_startup.template.sh`)
**Scope:** Small
1. **Locate** the git sync block at `worker_startup.template.sh:249-266`. Both the fresh-clone path (L185) and the existing-dir path converge here after `cd "$WORKDIR"` (L241), so a single submodule update after the reset covers both.
2. **Add** immediately after the `git reset --hard origin/main` block (after L263) and before the `AFTER_COMMIT` capture at L265. **Do not soft-fail this step** (unlike the surrounding `git fetch` / `git reset` pattern): if the submodule never populates, `Wan2GP/` stays empty and the later dependency/worker checks at L319-345 only verify `torch`/`dotenv`/`fastapi`/`worker.py`, not `Wan2GP/`. That silent gap is exactly the bug we are fixing.
   Use the following structure — attempt the update with a timeout, then validate that `Wan2GP/` is populated. If either step fails on a worker-repo tree that declares the submodule, abort startup:
   ```sh
   echo "=== GIT SUBMODULE SYNC ===" >> "$LOG_FILE" 2>&1
   SUBMODULE_UPDATE_OK=1
   timeout 300 git submodule update --init --recursive >> "$LOG_FILE" 2>&1 || SUBMODULE_UPDATE_OK=0

   if [ -f .gitmodules ] && grep -q 'path = Wan2GP' .gitmodules; then
       if [ "$SUBMODULE_UPDATE_OK" != "1" ] || [ ! -d Wan2GP ] || [ -z "$(ls -A Wan2GP 2>/dev/null)" ]; then
           echo "❌ Wan2GP submodule is missing or empty after submodule update; refusing to start worker" >> "$LOG_FILE" 2>&1
           echo "❌ Wan2GP submodule is missing or empty after submodule update; refusing to start worker" >&2
           exit 1
       fi
       echo "✅ Wan2GP submodule populated" >> "$LOG_FILE" 2>&1
   else
       echo "ℹ️  No Wan2GP submodule declared in this tree; skipping verification" >> "$LOG_FILE" 2>&1
   fi
   ```
   Rationale:
   - `timeout 300` (vs `30` for `git fetch`) — submodule fetch is heavier; a depth-1 fetch of Wan2GP can take meaningfully longer than a shallow main-repo fetch.
   - Gating the verification on `.gitmodules` containing `path = Wan2GP` means the legacy `Headless-Wan2GP` fallback directory (no submodules) skips the check cleanly, as does any future branch that drops the submodule.
   - Writing the failure message to **both** the log file and stderr ensures the RunPod console surfaces the root cause immediately instead of letting the worker crash later on an import error.
3. **Do not** add a second submodule call at L185 after the clone; the reset block runs unconditionally for both paths, so one insert is sufficient and avoids duplication.
