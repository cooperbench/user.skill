The First Contact change is the cleanest example of the pattern. The same lever works in lots of other places. Let me name where I think it pays off most, ranked by likely savings × frequency:

**High-value candidates for conditional inclusion:**

**Lower-value (keep always):**

- Role/Identity, Operating Principles, Stance On Assessments, Relational Voice, Frameworks, Five Knowledge Primitives, Output Style. These are identity/voice — they shape every reply.

**Mechanism.** Same pattern as First Contact: pull each conditional section into its own constant, replace it with a `{section_name}` placeholder, pass the relevant signals (channel, charge, partner state, current state, is_burst, transcription_source) into `render_system_prompt`, and assemble.

The orchestration cost is a single function that takes the turn's signals and returns the dict of which sections to include — clean to test, easy to reason about.

**Honest tradeoffs:**
- **Prompt cache.** If you cache the system prompt, more variance = lower cache hit rate. The wins from a shorter prompt have to beat the cache miss cost. Worth measuring before going wide.
- **Behavior surprise.** If the section about "X" only loads when X is detected, the model can't proactively notice X starting to apply. For most candidates above (channel, transcription, burst) the signal is reliable. For things like "closure signals" the signal is fuzzier and removing the section may make closure less likely to fire. So I'd be conservative there.
- **Eval drift.** Each conditional means more axes of behavior to keep evals on. Worth adding evals for both branches when you flip a section conditional.

**My recommendation for next move:** do (1) Cross-Thread Sharing branches and (5) Discord-only guidance first. Both have clean signals, both are large blocks, and both shrink the common-case prompt meaningfully without ambiguity. Then measure cache hit-rate before going further.
