        Idea:
Refactor the video editor timeline drag system (useClipDrag.ts and related) to be elegant and well-engineered. The current system has these problems we've identified:

1. **Two competing pointer event systems**: useClipDrag bolts a capture-phase document listener on top of the timeline library's own pointer system, coordinated via a fragile string-mutex gestureOwner ref. If either side fails to release ownership, the other is permanently locked out.

2. **Pointer capture + React re-renders = race condition**: setPointerCapture pins events to a DOM element, but React can replace that element during re-render, silently releasing capture and potentially orphaning the session.

3. **The button element fights you**: Native button focus, activation, click synthesis, and drag behavior all interfere with the custom pointer system. stopPropagation() on pointerdown creates asymmetry between capture and bubble phases.

4. **Session lifecycle is optimistic**: Every pointerdown creates a mutable DragSession with 20+ fields. Cleanup relies on pointerup/pointercancel always firing with matching pointerId. Leaked sessions leave listeners on window, pendingOps stuck > 0, and gestureOwner stuck.

5. **600-line effect closure with 15 ref-of-ref indirections**: The entire drag system lives in one useEffect that never re-runs. Every changing value is smuggled through refs (selectedClipIdsRefRef, pendingOpsRefRef, etc.). Nothing is statically traceable.

6. **DragSession is a grab-bag**: Mixes pointer tracking, DOM references, input classification, gesture state, and event handlers in one mutated object.

The well-engineered version should have:
- **Single event coordinator** instead of two competing systems
- **AbortController pattern** for atomic listener cleanup (no leaked sessions)
- **No pointer capture** — just window listeners + coordinator state machine
- **div role=button instead of button** — same a11y, no native behaviors to fight
- **Explicit state machine**: idle → pending → dragging → idle, with each transition having exactly one set of side effects
- **Derived values, not accumulated mutations**: ghost position and snap as pure functions of (dragState, pointerPosition, timelineData)
- **No pendingOps counter** — just read dragState !== idle

        # Implementation Plan: Refactor Timeline Drag System to State Machine

## Overview

The video editor's clip drag system (`useClipDrag.ts`, 759 lines) has accumulated significant complexity: a capture-phase document listener competing with `useMarqueeSelect`'s bubble-phase handler, pointer capture that races with React re-renders, a native `<button>` element whose behaviors fight the custom pointer system, a 24-field mutable `DragSession` object, and 15 ref-of-ref indirections smuggling values into a never-re-running `useEffect`.

The refactor replaces this with: an explicit state machine (`idle → pending → dragging → idle`), `AbortController`-based listener cleanup, `div[role=button]` instead of native button, no pointer capture, and a consolidated ref pattern. The two hooks (`useClipDrag` + `useMarqueeSelect`) remain separate — they are genuinely different gestures with different state shapes — coordinated via the single `gestureOwner` ref that already serves this purpose.

**Key constraint**: `pendingOpsRef` is shared with resize operations in `TimelineCanvas`, external-drop-utils, and asset operations. It cannot be replaced with a simple `isDragging` boolean. We keep `pendingOpsRef` as the external interface but make useClipDrag's lifecycle airtight. This is an intentional divergence from the brief's "no pendingOps counter" wording — the counter serves a broader system.

**Key constraint**: All 17 tests in `useClipDrag.test.tsx` define the behavioral contract. Tests fire `pointerDown` directly on clip/label elements and `pointerMove`/`pointerUp` on `window`.

**Listener strategy**: The refactored useClipDrag will listen on the `timeline-wrapper` element in **bubble phase** instead of the current capture-phase document listener. This requires removing `stopPropagation()` from three surfaces: (1) ClipAction's `<button>` pointerdown, (2) the shot-group label's pointerdown in TimelineCanvas, and (3) the overflow trigger's pointerdown in ClipAction. Each removal is safe because the events need to reach the wrapper; the overflow trigger needs a new ignore selector since it's inside `.clip-action`.

**Architecture decision**: useClipDrag and useMarqueeSelect remain separate hooks. The brief's "single event coordinator" is satisfied by `gestureOwner` being the single coordination point. Merging them into one hook would create a god-hook, not a simpler system — they manage genuinely different gestures with different state.

**Consumer contract**: `dragSessionRef` is consumed by three systems: (1) tests check `clipId`, `draggedClipIds`, `groupDragEntry`; (2) `useMarqueeSelect` checks truthiness to yield; (3) `TimelineCanvas.tsx:701` checks `dragSessionRef?.current !== null` to hide shot-group overlays during drag. The backward-compatible adapter must satisfy all three.

## Overview

The video editor's clip drag system (`useClipDrag.ts`, 759 lines) has accumulated significant complexity: a capture-phase document listener competing with `useMarqueeSelect`'s bubble-phase handler, pointer capture that races with React re-renders, a native `<button>` element whose behaviors fight the custom pointer system, a 24-field mutable `DragSession` object, and 15 ref-of-ref indirections smuggling values into a never-re-running `useEffect`.

The refactor replaces this with: an explicit state machine (`idle → pending → dragging → idle`), `AbortController`-based listener cleanup, `div[role=button]` instead of native button, no pointer capture, and a consolidated ref pattern. The two hooks (`useClipDrag` + `useMarqueeSelect`) remain separate — they are genuinely different gestures with different state shapes — coordinated via the single `gestureOwner` ref that already serves this purpose.

**Key constraint**: `pendingOpsRef` is shared with resize operations in `TimelineCanvas`, external-drop-utils, and asset operations. It cannot be replaced with a simple `isDragging` boolean. We keep `pendingOpsRef` as the external interface but make useClipDrag's lifecycle airtight. This is an intentional divergence from the brief's "no pendingOps counter" wording — the counter serves a broader system.

**Key constraint**: All 17 tests in `useClipDrag.test.tsx` define the behavioral contract. Tests fire `pointerDown` directly on clip/label elements and `pointerMove`/`pointerUp` on `window`.
