        Idea:
# InboundScope refactor — eliminate bot_id leaks across the inbound→outbound path

## Why this exists

The Veas codebase is being extended from a single-bot mediator (Véas) to a multi-bot platform. The second bot, Tante Rosi (German pregnancy coach, solo-shape, Discord-only), keeps misrouting: messages sent to Rosi get processed and replied by Véas, with the wrong persona, language, and topic.

We've now patched the *same shape of bug* three times in rapid succession:

1. `app/services/inbound.py::_resolve_scope` had `bot_id: str = "mediator"` as a silent default → inbound rows tagged with the wrong bot. (Fixed in commit `5a38d7f`.)
2. `app/main.py` constructed a single `app.state.coalescer` with `bot_id="mediator"` captured in closures used as the dispatch callback. The burst data structure already carried the correct per-event bot_id, but the closure ignored it. (Fixed in commit `f29bc03` by moving to `app.state.coalescers: dict[str, BurstCoalescer]` and resolving topic via `get_bot_spec(bot_id) + primary_topic_id_for(pool, spec)`.)
3. `app/services/recovery.py`, `app/services/vision.py`, `app/services/transcription.py` still hardcode `bot_id='mediator'` in their own outbound calls. (Not yet fixed.)

After both patches (1) and (2) were on `main`, the user reports the wrong bot is **still responding**. So there is at least one more leak we haven't characterised yet, plus the three known hardcodes above.

**This is no longer a patching problem — it's a structural one.** Each fix surfaces another instance of the same shape because `bot_id` was bolted onto a codebase that was written assuming a single mediator. It rides through the system as a loose parameter: sometimes a function arg, sometimes a closure capture, sometimes a DB column, sometimes a default. The boundary between "this code knows its bot" and "this code looks it up" is fuzzy and inconsistent.

## What we want

Introduce a single explicit **`InboundScope`** dataclass (frozen) that:

- Is constructed **once** at each gateway boundary (Discord `_handle_message`, Discord `_handle_reaction_add`, Discord `catch_up_recent_messages`, WhatsApp router).
- Carries **all per-event identity**: `bot_id`, `transport`, `user_id` (sender), `topic_id`, `channel_id`, `binding_id`, `dyad_id` (None for solo-shape bots like Rosi).
- Threads explicitly through every downstream code path: `process_inbound` → coalescer → burst dispatch → agentic turn → LLM tools → outbound (text, voice, image) → DB writes.
- **Replaces** the existing loose `bot_id` kwarg pattern. No function below the gateway accepts `bot_id` as an optional kwarg with a `"mediator"` default. Forgetting to pass scope becomes a type error.

The existing `ResolvedScope` NamedTuple in `app/services/inbound.py` (around line 161) is the seed of this — it already has `(bot_id, topic_id, channel_id, binding_id, dyad_id)`. **Promote it to a frozen dataclass, add `transport` and `user_id`, rename to `InboundScope`, and make it the universal carrier.**

There is also an existing `app/services/turn_context.py` — investigate during prep whether it already plays a related role and whether it should be merged with / replaced by `InboundScope`, or whether they have distinct responsibilities (per-event identity vs per-turn execution context).

## Done looks like

1. **Defined**: `InboundScope` dataclass exists in one canonical location (probably `app/services/inbound.py` or a new `app/services/scope.py`). Frozen, fully typed, no defaults.
2. **Threaded**: every function from gateway → outbound takes scope (or scope-derived values) explicitly. Audited list of touched files includes at minimum:
   - `app/services/discord.py` (gateway handlers: `_handle_message`, `_handle_reaction_add`, `catch_up_recent_messages`)
   - `app/routers/whatsapp.py` (WA webhook → constructs `InboundScope(bot_id="mediator", transport="whatsapp", ...)` explicitly — single-WA-bot is fine for now)
   - `app/services/inbound.py` (`process_inbound`, `_resolve_scope`)
   - `app/services/debouncer.py` (coalescer: `add(scope, ...)`, burst carries scope, on_complete callback uses `burst.scope` not closure)
   - `app/services/agentic.py` and/or `app/services/turn_context.py` (agentic turn takes scope)
   - `app/services/tools/*` (LLM tools: `send_text`, distillation tools, etc. — take scope or scope-derived bot_id/topic_id, no defaults)

## Constraints / invariants to preserve

- **Don't break Véas.** Véas is in production and being used. The refactor must preserve current dyadic-mediator behavior end-to-end.
- **Don't break WhatsApp.** WA is currently mediator-only; the WA router must continue to work with `InboundScope(bot_id="mediator", transport="whatsapp", ...)`.
- **Don't change DB schemas** in this refactor. The `bot_id` column already exists on messages, channels, etc. The refactor is code-only.
- **Don't change the LLM prompts** for either bot (other than threading the right one for the right turn). Persona templates already exist in `app/services/prompts.py` and `app/services/prompts_solo.py`.
- **Don't break the per-bot Discord gateway architecture** introduced earlier. Each bot has its own `DiscordClient`, `DiscordGatewayBot`, and `DiscordPacer`. These are correctly per-bot already — the leak is downstream of the gateway, not at the gateway.
- **Don't introduce a global / thread-local for scope.** Scope flows through arguments, period. The whole point is to make implicit identity explicit.

## Known unknowns the prep phase should resolve

A. **What is the actual relationship between `app/services/turn_context.py` and `_resolve_scope`?** Is `TurnContext` already the abstraction we want, just incomplete? B. **What is the agentic turn entry point?** Probably `app/services/agentic.py`. Map its signature today and what it would look like with `scope` threaded through. C. **What is the actual fourth leak the user is still seeing?** With patches (1) and (2) both on `main` and Rosi still misrouting, there must be at least one more code path the bot identity is being silently overwritten in. Trace a single inbound DM to Rosi from gateway to outbound and identify where bot_id flips to "mediator". Candidates: the agentic turn (B above), one of the three known hardcodes (recovery/vision/transcription), the OOB check (`oob_check.py`), or something not yet enumerated. **Find it before designing the refactor in detail; the location may inform the abstraction.**

D. **Coalescer shape decision**: after `f29bc03`, `app.state.coalescers` is a per-bot dict. Is per-bot the right model going forward, or should we collapse to one coalescer whose bursts carry scope and route by `burst.scope.bot_id`? Trade-off: per-bot isolation (current) is simpler but each bot needs its own loop overhead; single coalescer is leaner but the dispatch closure must read from burst, not lexical scope. Recommend the simpler-to-reason-about option; document the choice.

E. **`hot_context_solo.py` and `prompts_solo.py` already exist.** Confirm they are wired to be picked correctly when `scope.dyad_id is None`, or document what needs to change. Solo-shape must work for Rosi out of the box after this refactor — that's the whole point.

F. **The OOB delivery-time guardrail** (`app/services/oob_check.py`): how is it currently scoped? If it's global-to-recipient, it could suppress Rosi's reply because Véas just sent a message to the same user. Needs to be bot-aware. Prep should determine the current shape and the cleanest fix.

G. **Recovery path**: `recovery.py` runs at startup and replays missed messages. It has no live gateway event to scope from, so scope must be **reconstructed from DB state**. Prep should propose a helper signature like `scope_from_message_row(pool, row) -> InboundScope` and verify all needed fields are recoverable from the schema.

H. **`seed_weekly_reflections` working-tree-only import in `app/main.py:24`** — this rename is in the user's uncommitted working tree but not in any commit. Railway works because `railway up` uploads the working tree, but a fresh checkout (CI, worktree, anyone else) cannot import `app.main`. **The execute phase must commit this rename or otherwise reconcile** so the refactor PR is testable from a fresh checkout. Don't ignore this — it will block testing.
