        # Implementation Plan: Effects System Standardization — Looping & Unification

## Overview

The effects system has three registries (entrance, exit, continuous) with 27 total effects across 4 files. The two goals are:
1. **Looping**: Continuous effects run linearly 0→1 and don't loop. Some should.
2. **Unification**: Many entrance/exit effects are conceptual inverses but are separate implementations. We want one pool of effects usable in any role.

### Current state

- **Entrances** (11): Use `getNormalizedProgress(frame, effectFrames)` → progress 0→1 over effectFrames at clip start
- **Exits** (6): Use `getExitProgress(frame, durationInFrames, effectFrames)` → progress 0→1 over effectFrames at clip end, then apply inverse transforms
- **Continuous** (10): Run over full clip. 5 non-audio (ken-burns, float, glitch, slow-zoom, drift) + 5 audio-reactive
- **Key insight**: Float and glitch are already inherently looping (sin/modulo), but ken-burns, slow-zoom, and drift are linear 0→1 with no loop

### Design decision: progress-based unification

The core realization is that entrance and exit effects differ only in **when and how** progress is calculated, not in **what they animate**. A `fade` effect is "opacity goes from 0→1 as progress goes 0→1" regardless of whether it's entrance or exit. The timing wrapper handles direction.

**Proposed architecture**: A `ProgressEffect` renders given a `progress: number` (0→1). A thin timing layer converts this to entrance (progress at start), exit (1-progress at end), or continuous (progress over duration, with optional looping). Effects register once with metadata about supported roles and defaults.

Effects like `meteorite` that are inherently directional remain entrance-only — they register with `roles: ["entrance"]` and are filtered in the UI.

## Phase 1: Foundation — Types, Progress Abstraction, Loop Config

### Step 1: Add loop config to types (`shared/types.ts`)
**Scope:** Small
1. **Add** `loop?: boolean | number` to `ClipContinuous` (line 39). Boolean true = ping-pong loop, number = loop period in seconds. Default behavior: `false` for progressive effects, inherently looped effects ignore this.
2. **Add** unified effect metadata type:
   ```typescript
   type EffectRole = "entrance" | "exit" | "continuous";
   type EffectMetadata = {
     roles: EffectRole[];  // Which roles this effect supports
     loop?: "none" | "oscillate" | "inherent";  // Default loop behavior
   };
   ```
3. **Update** `CustomEffectEntry.category` to `category?: EffectRole | EffectRole[]` for custom effects that work in multiple roles.

### Step 2: Create progress-based effect abstraction (`shared/effects/progress-effects.ts`)
**Scope:** Medium
1. **Define** the core `ProgressEffect` type:
   ```typescript
   type ProgressEffectProps = {
     progress: number;        // 0→1, timing-adjusted
     children: ReactNode;
     intensity?: number;
     audioData?: AudioReactivityResult;
   };
   type ProgressEffect = FC<ProgressEffectProps>;
   ```
2. **Implement** the `EffectTimingWrapper` component that:
   - For **entrance**: calculates `progress = clamp(frame / effectFrames, 0, 1)` 
   - For **exit**: calculates `progress = clamp((frame - (duration - effectFrames)) / effectFrames, 0, 1)`, passes `1 - progress` to the effect (reversal)
   - For **continuous**: calculates `progress = frame / durationInFrames`, applies looping transform if configured:
     - `loop: true` or `"oscillate"` → ping-pong: `1 - Math.abs(2 * (progress % 1) - 1)` 
     - `loop: number` → same but over `loopPeriodFrames` instead of full duration
3. **Implement** spring-based timing variant for entrance effects that want spring physics (e.g., slide-up, bounce) — the wrapper passes spring-computed progress instead of linear.

### Step 3: Port simple reversible effects to progress-based (`shared/effects/progress-effects.ts`)
**Scope:** Medium  
Port effects that are natural entrance/exit pairs into single progress-based definitions:

| Unified name | Current entrance | Current exit | Animation |
|---|---|---|---|
| `fade` | FadeEntrance | FadeOutExit | opacity: progress |
| `zoom` | ZoomInEntrance | ZoomOutExit | scale: lerp(small, 1, progress) |

| `dissolve` | (new) | DissolveExit | blur + opacity: lerp(blurred, clear, progress) — now also available as entrance |

1. **Each** progress effect is a simple function: takes progress 0→1, returns a styled `AbsoluteFill` wrapping children.

## Key Design Decisions

### Why not full "one pool" UI?
The brief suggests one pool with entrance/exit/continuous as application modes. But keeping three dropdowns (filtered from one registry) is better because:
- Users still think in terms of "how should it enter" / "how should it exit" — the mental model stays clear
- No extra "mode" selector needed — the slot determines the role
- More options appear in each dropdown (net gain) without UI restructuring

### Why progress-based instead of just "reverse" flag?
A `reverse: boolean` on the existing components would be simpler, but:
- Each effect would need internal branching on `reverse`
- Exit timing calculation would still be duplicated in each component
- Looping requires the same timing abstraction — progress-based serves both goals

### Looping semantics by effect type
| Effect | Default loop | With `loop: true` |
|---|---|---|
| ken-burns | `false` — progressive pan+zoom | Ping-pong: zoom in then back out |
| slow-zoom | `false` — progressive zoom | Ping-pong: zoom in then back out |
| drift | `false` — progressive drift | Ping-pong: drift right then left |
| float | inherent (sin wave) | N/A, already oscillates |
| glitch | inherent (modulo cycle) | N/A, already cycles |
| audio-* | inherent (driven by audio) | N/A, driven by audio data |

### Flip axis discrepancy
Currently FlipEntrance uses `rotateY` and FlipExit uses `rotateX`. Unifying to `rotateY` is the right call — the Y-axis flip (like turning a card) is the more natural "flip" motion. This is a minor visual change for existing exit clips using `flip`.
