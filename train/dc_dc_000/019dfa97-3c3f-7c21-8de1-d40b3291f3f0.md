        # Implementation Plan: VibeComfy Memory-Profile MVP

## Overview
The latest critique identifies two real boundary issues, not just plan phrasing. First, the implementation must not target `reigh-worker/source/models/comfy` as if it were the VibeComfy adapter: that code is a legacy raw-ComfyUI path that starts Comfy directly and queues raw workflow dictionaries, not `VibeWorkflow` or `SessionConfig`. Second, `reigh-worker` cannot directly import VibeComfy Python objects because `reigh-worker` is Python 3.10-only and has no VibeComfy dependency, while `vibecomfy` requires Python 3.11+. The revised plan therefore keeps the concrete `MemoryProfile` implementation inside VibeComfy and defines the worker-facing contract as numeric CLI/config protocol only: pass profile numbers across the boundary, let VibeComfy resolve them.

The core VibeComfy work remains the same: implement a concrete `MemoryProfile` overlay from `docs/migration-vibecomfy.md`, wire it through `SessionConfig`, embedded configuration, managed-server argv, session defaults, one-shot server startup, per-run CLI overrides, ready-template smokes, restart documentation, and profile 1/3 measurement artifacts. The key precedence rule is now explicit: workflow metadata is resolved first; a CLI `--memory-profile` override is applied after that resolution and overwrites profile-controlled low-level fields for that run.

External behavior is limited to integer profiles 1-5. Public labels must follow the migration contract: Low RAM, High RAM, Low VRAM, Very Low VRAM, and Minimum. Internal names may be descriptive, but public output and telemetry must preserve the integer/profile-label contract.

## Phase 1: Foundation — Concrete Profile Overlay

### Step 1: Add `MemoryProfile` (`vibecomfy/vibecomfy/memory_profile.py`)
**Scope:** Medium
1. Implement a small immutable profile abstraction accepting only integer values `1..5`.
2. Encode the Sprint 1 mapping from `docs/migration-vibecomfy.md` directly in one place:
   - Profile 1: `{"vram_policy": "high", "cache_policy": "smart"}`
   - Profile 2: `{"vram_policy": "high", "cache_policy": "lru:32"}`
   - Profile 3: `{"vram_policy": "normal", "cache_policy": "smart"}`
   - Profile 4: `{"vram_policy": "low", "cache_policy": "classic", "reserve_vram_gb": 2.0}`
   - Profile 5: `{"vram_policy": "low", "cache_policy": "lru:1", "disable_smart_memory": True, "reserve_vram_gb": 4.0}`
3. Provide helpers for parsing CLI/config values, returning `to_session_overrides()`, serializing `memory_profile` telemetry, and exposing public display labels.
4. Add an override helper such as `apply_to_session_config(config, *, override_existing: bool)` or `SessionConfig.with_memory_profile_override(profile)` so callers can choose normal config precedence or CLI override precedence without mutating workflow metadata.
5. Do not add graph or string patching here. The Sprint 1 profile overlay is a `SessionConfig` concern.

### Step 2: Wire `SessionConfig` Normal Precedence (`vibecomfy/vibecomfy/runtime/session.py`)
**Scope:** Medium
1. Add `memory_profile: int | None` to `SessionConfig` while preserving current behavior when unset.
2. Update `SessionConfig.from_dict()` and `from_workflow_metadata()` to accept `memory_profile`, validate it through `MemoryProfile`, and overlay profile-derived fields before explicit lower-level typed fields are applied.
3. Preserve normal config precedence inside config parsing: explicit low-level typed values such as `reserve_vram_gb` or `cache_policy` win over profile-derived fields when they appear in the same config object; raw HiddenSwitch keys carry through as today.
4. Ensure `_embedded_configuration_for_session()` and `_comfy_server_argv()` do not duplicate profile logic. They should consume resolved `SessionConfig` fields and naturally emit embedded Comfy `Configuration` values and managed-server argv.
5. Include `memory_profile` and resolved display label in run metadata emitted by `_run_metadata()` so profiling evidence can be grouped later.

### Step 3: Add Explicit CLI Override Precedence (`vibecomfy/vibecomfy/runtime/session.py`, `vibecomfy/vibecomfy/runtime/run.py`)
**Scope:** Medium
1. Add a clear API for per-run CLI override precedence that starts from an already resolved `SessionConfig` and then overwrites the profile-controlled fields with `MemoryProfile.to_session_overrides()`.
2. Use this API only for explicit CLI/runtime overrides, never for normal metadata parsing.
3. Add tests proving workflow metadata such as `{"reserve_vram_gb": 12, "cache_policy": "none"}` can remain authoritative during normal parsing, but `--memory-profile 4` applied afterward overwrites those controlled fields for the run.

## Phase 2: VibeComfy CLI And Runtime Paths

### Step 4: Add Process Defaults (`vibecomfy/vibecomfy/commands/session.py`)
**Scope:** Medium
1. Add `--memory-profile {1,2,3,4,5}` to `vibecomfy session start`.
2. Persist `memory_profile` into daemon `config.json` and construct `ServerSession(SessionConfig.from_dict(config_dict))` as today, relying on the profile overlay to resolve effective fields.
3. Extend session CLI tests so every profile `1..5` persists and resolves through daemon config without changing unset defaults.

### Step 5: Fix One-Shot Managed Server Plumbing (`vibecomfy/vibecomfy/runtime/server.py`, `vibecomfy/vibecomfy/runtime/run.py`)
**Scope:** Medium
1. Change `comfy_server()` to accept an optional `SessionConfig` for managed one-shot startup instead of always constructing `SessionConfig(port=8188)` internally.
2. Pass a resolved config from `run()` when `vibecomfy run --runtime server` starts a managed local server with no `--server-url` and no active session.
3. Add tests proving `run --runtime server --memory-profile N` reaches managed-server argv/config, not only metadata.

### Step 6: Add Per-Run Override Policy (`vibecomfy/vibecomfy/commands/run.py`, `vibecomfy/vibecomfy/runtime/run.py`)
**Scope:** Medium
1. Add `--memory-profile {1,2,3,4,5}` to `vibecomfy run`.
2. For `--runtime embedded`, resolve `SessionConfig.from_workflow_metadata(workflow)` first, then apply the CLI memory profile via the explicit override API from Step 3 before constructing `EmbeddedSession`.
3. For `--runtime server` or `auto` that starts a new managed server, resolve workflow/default config first, then apply the CLI memory profile before spawning the managed server.
4. For an already-running managed session discovered by `find_active_session()` or an explicit `--server-url`, reject restart-required profile overrides with exit code `2` and a clear message telling the user to restart/start a session with that profile. Do not silently record metadata-only and do not claim the override won.
5. Preserve ordinary run behavior when no profile override is passed.

## Phase 3: Worker-Facing Numeric Protocol Boundary

### Step 7: Define The Worker Boundary Without Direct Imports (`reigh-worker/source/`, `vibecomfy` CLI docs/tests)
**Scope:** Medium
1. Do not import `vibecomfy.memory_profile`, `SessionConfig`, or any VibeComfy Python module from `reigh-worker`.
2. Do not place VibeComfy profile logic in `reigh-worker/source/models/comfy`; that path is legacy raw-ComfyUI and not a VibeComfy adapter.
3. Add or update only a narrow Python 3.10-compatible helper at an explicit VibeComfy adapter boundary, for example `reigh-worker/source/runtime/vibecomfy_profile.py` or the actual future VibeComfy backend adapter module, that resolves process default plus per-task `override_profile` into a numeric `--memory-profile N` CLI argument or equivalent JSON/env field.
4. Keep the worker helper numeric-only: validate `-1` or `1..5`, choose the effective number, and pass it over the subprocess/CLI/config protocol. VibeComfy remains the only codebase that maps profile numbers to `SessionConfig` fields.
5. If no VibeComfy backend adapter exists yet, add only this pure numeric helper and tests; do not introduce a full backend or retrofit the legacy raw-ComfyUI handler.
6. Preserve WGP process flags and defaults: do not rename or remove `--wgp-profile`, and do not mutate WGP globals from the VibeComfy helper.

## Phase 4: Template Smokes And Measurement Evidence

3. Document how to run the smoke locally or on a GPU worker. If the implementation environment lacks a GPU, the code/tests still verify artifact schema, and the actual data collection remains an explicit human/GPU validation item.

## Phase 5: Documentation And Tests

### Step 10: Restart And Mapping Documentation (`vibecomfy/docs/runtime_lifecycle.md`, `vibecomfy/docs/runtime_surface.md`)
**Scope:** Small
1. Document that profile changes affect process-level Comfy model-management knobs and therefore require a new embedded session or managed-server restart.
2. Document the exact behavior for `vibecomfy run --memory-profile` across embedded, new managed server, discovered active session, and explicit external server URL.
3. Include the concrete profile-to-`SessionConfig` mapping table in VibeComfy docs.
4. Document the reigh-worker boundary: workers pass numeric profiles to VibeComfy through CLI/config protocol and must not import VibeComfy Python objects under the current Python-version constraints.

### Step 11: Focused Verification Suite (`vibecomfy/tests/`, `reigh-worker/tests/`)
**Scope:** Medium
1. Add `vibecomfy/tests/test_memory_profile.py` for parsing, mapping, invalid values, labels, telemetry, normal metadata precedence, and explicit CLI override precedence.
2. Extend `vibecomfy/tests/test_runtime_session.py` for embedded config and managed-server argv round-trips across profiles `1..5`.
3. Extend `vibecomfy/tests/test_session_cli.py` for process-default persistence.
4. Extend `vibecomfy/tests/test_run_command.py` and/or runtime run tests for embedded/new-server success, active/external-server rejection, and CLI override winning over workflow metadata.
5. Add narrow `reigh-worker` unit tests for the numeric helper only: no VibeComfy imports, no legacy `source/models/comfy` modification, `override_profile=-1` uses the process default, and `override_profile in 1..5` emits one-run numeric profile protocol data.
