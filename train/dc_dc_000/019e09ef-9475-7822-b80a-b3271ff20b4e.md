> AGENT

Read-only inspection complete. Recommendation: keep both target routes fail-closed. I would not promote either on the current templates/adapters.

**Wan i2v first/last**

Not safe. The route is explicitly unsupported in [template_routing.py](/tmp/reigh-worker/source/task_handlers/tasks/template_routing.py:232), and the current Wan 2.2 I2V scratchpad only materializes one image input. More importantly, it replaces both sampler `image_embeds` edges with `WanVideoEmptyEmbeds` in [vibecomfy_adapter.py](/tmp/reigh-worker/source/models/comfy/vibecomfy_adapter.py:1039), so the Kijai `WanVideoImageToVideoEncode` output is not actually driving the samplers.

VibeComfy’s I2V template has the right core node shape for first/last support: `WanVideoImageToVideoEncode` node `89`, samplers `27` and `90`, and `image_embeds=wanvideoimagetovideoencode.out(0)` in [wanvideo_wrapper_22_14b_i2v_kijai.py](/tmp/vibecomfy/ready_templates/video/wanvideo_wrapper_22_14b_i2v_kijai.py:184). But it only wires `start_image`; no `end_image` is exposed. Wan2GP/Kijai-compatible first/last behavior requires `start_image` and `end_image` into `WanVideoImageToVideoEncode`, `fun_or_fl2v_model=False`, and preserving node `89` as the `image_embeds` source. The local Wan2GP/Kijai notes call out the key behavior: pixel-space `[start | zeros | end]`, masks for first and last frame, and `end_=True` VAE mode in [KIJAI_SVI_IMPLEMENTATION.md](/tmp/reigh-worker/docs/KIJAI_SVI_IMPLEMENTATION.md:20).

Recommended patch: add a dedicated first/last Wan I2V scratchpad/template path that materializes `start_image` and `end_image`, resizes both, connects `end_image` to node `89`, and removes the `WanVideoEmptyEmbeds` replacement for this route. Then flip [template_routing.py](/tmp/reigh-worker/source/task_handlers/tasks/template_routing.py:232) to `VIBECOMFY_SUPPORTED` with `video/wanvideo_wrapper_22_14b_i2v_kijai` only after a static graph test confirms samplers `27`/`90` consume node `89`.

**Wan VACE Uni3C first/last**

Not safe. The route is explicitly unsupported in [template_routing.py](/tmp/reigh-worker/source/task_handlers/tasks/template_routing.py:328). The VACE template supports first/last VACE conditioning via `WanVideoVACEStartToEndFrame` node `111`, `WanVideoVACEEncode` node `56`, and three Euler sampler phases in [wanvideo_wrapper_22_14b_vace_cocktail.py](/tmp/vibecomfy/ready_templates/video/wanvideo_wrapper_22_14b_vace_cocktail.py:99). The scratchpad patches start/end/control video into those VACE nodes in [vibecomfy_adapter.py](/tmp/reigh-worker/source/models/comfy/vibecomfy_adapter.py:899).

But Uni3C is a separate WGP path. The worker injects `use_uni3c`, `uni3c_guide_video`, strength/window/cache/frame-policy fields, and `uni3c_blackout_last_frame` in [task_registry.py](/tmp/reigh-worker/source/task_handlers/tasks/task_registry.py:1243). The VibeComfy scratchpad does not read or apply any `uni3c_*` params; it can only route a video into VACE `control_images`. VibeComfy’s registered WanVideoWrapper node classes include VACE nodes, but no Uni3C node or loader in [node_packs.py](/tmp/vibecomfy/vibecomfy/node_packs.py:16). Mapping Uni3C to VACE control video would be a semantic mismatch.

Recommended patch: no promotion patch yet. Add real Comfy Uni3C support first: node pack/model assets, template nodes that apply Uni3C control to the Wan/VACE sampling path, scratchpad mapping for all `uni3c_*` fields, and tests proving `uni3c_blackout_last_frame` behavior with an end anchor. Until then, keep this route fail-closed.
