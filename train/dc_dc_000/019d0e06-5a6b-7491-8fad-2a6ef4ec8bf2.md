# Implementation Plan: Fix Lifecycle Phase Ordering

## Root Cause Analysis (revised)

The bug has **one root cause with a downstream symptom**:

### Root cause: `_resolve_reconcile_phase()` disagrees with `_ordered_postflight_phase()`

The repo already has **two phase-ordering implementations** that disagree:

1. **`_resolve_reconcile_phase()`** (pipeline.py:91-128) — persists the lifecycle phase. Checks workflow → triage → subjective → fallback. **Wrong order.**
2. **`_ordered_postflight_phase()`** (snapshot.py:362-378) — determines the visible queue phase. Checks assessment → workflow → triage → review. **Correct order.**

When stale reviews coexist with `workflow::communicate-score` or `triage::observe` in `queue_order`, the snapshot builder correctly reports `assessment_postflight` for display, but the persisted phase is stuck at `workflow_postflight` or `triage_postflight`.

### Downstream symptom: `_suppressed_same_cycle_refresh()` reads the persisted phase

`_suppressed_same_cycle_refresh()` (synthetic.py:261-279) suppresses stale reviews when `current_lifecycle_phase(plan)` is in `{WORKFLOW, WORKFLOW_POSTFLIGHT, TRIAGE, TRIAGE_POSTFLIGHT}`. Because the persisted phase is wrong, stale reviews that should be visible get suppressed. **Fixing the persisted phase automatically fixes the suppression** — when the persisted phase is `assessment_postflight`, the suppression check returns False at line 264 and the stale review appears normally.

### What does NOT need fixing

- **Queue ordering** (`_promote_subjective_ids`, `normalize_queue_workflow_and_triage_prefix`): The snapshot builder already has its own display ordering that works correctly. The `queue_order` list in the plan is a task registry, not a display order. No reordering needed.
- **Workflow eviction**: Workflow items can stay in `queue_order`. They just shouldn't dominate the persisted phase when stale reviews are pending. The existing `_subjective_review_current_for_cycle()` gate (workflow.py:279) already prevents new workflow injection when stale items exist.
- **Suppression logic**: Automatically resolved by fixing the persisted phase.
- **Phase cleanup**: `_phase_prefixes(ASSESSMENT_POSTFLIGHT)` returns `()` (no pruning), which is correct — both stale subjective and queued workflow items should survive.

### Out of scope: legacy coarse-phase display path

`_sticky_postflight_phase()` (snapshot.py:455-493) handles plans that still have a coarse persisted phase (`workflow`, `triage`, `review`). When persisted phase is coarse `workflow`, it prefers workflow items over assessment in display ordering. This is **not part of the fix** because:

1. `_resolve_reconcile_phase()` always writes **fine-grained** phases. Once reconcile runs on a legacy plan, it overwrites the coarse phase with the correct fine-grained one.
2. The snapshot builder (line 329-335) delegates fine-grained phases to `_ordered_postflight_phase()`, which already has the correct ordering. The `_sticky_postflight_phase()` path is only reached for un-reconciled legacy plans.
3. Since the fix targets `_resolve_reconcile_phase()`, any plan that goes through reconcile will have the correct fine-grained phase persisted, and the legacy path will no longer apply.

If legacy coarse-phase plans that have never been reconciled are a real concern, `_sticky_postflight_phase()` can be aligned in a follow-up. But the reconcile pipeline is the standard migration path, and the fix ensures it writes the right value.

```python
def _resolve_reconcile_phase(plan, state, *, result, policy):
    order = [item for item in plan.get("queue_order", []) if isinstance(item, str)]

    # 1. Pre-review workflow always wins (scan data / deferred disposition first)
    pre_review_in_queue = any(item in PRE_REVIEW_WORKFLOW_IDS for item in order)
    pre_review_injected = bool(
        result.workflow_injected_ids
        and result.workflow_injected_ids & PRE_REVIEW_WORKFLOW_IDS
    )
    if pre_review_in_queue or pre_review_injected:
        return LIFECYCLE_PHASE_WORKFLOW_POSTFLIGHT

    # 2. Subjective reviews beat post-review workflow AND triage
    #    (matches _ordered_postflight_phase: assessment first)
    subjective_ids = [item for item in order if item.startswith("subjective::")]
    if subjective_ids:
        unscored_ids = set(getattr(policy, "unscored_ids", ()) or ())
        if any(item in unscored_ids for item in subjective_ids):
            return LIFECYCLE_PHASE_REVIEW_INITIAL
        return LIFECYCLE_PHASE_ASSESSMENT_POSTFLIGHT

    # 3. Post-review workflow
    if result.workflow_injected_ids or any(item.startswith("workflow::") for item in order):
        return LIFECYCLE_PHASE_WORKFLOW_POSTFLIGHT

    # 4. Triage — now below both subjective and workflow
    if result.triage and (result.triage.injected or result.triage.deferred):
        return LIFECYCLE_PHASE_TRIAGE_POSTFLIGHT
    if any(item.startswith("triage::") for item in order):
        return LIFECYCLE_PHASE_TRIAGE_POSTFLIGHT

    # 5. Fallback logic (unchanged from lines 114-128)
    triage_snapshot = build_triage_snapshot(plan, state)
    if (
        triage_snapshot.triage_has_run
        and not triage_snapshot.has_triage_in_queue
        and not triage_snapshot.is_triage_stale
        and bool(triage_snapshot.live_open_ids)
    ):
        return LIFECYCLE_PHASE_REVIEW_POSTFLIGHT

    persisted = current_lifecycle_phase(plan)
    if persisted:
        return persisted
    if open_review_ids(state):
        return LIFECYCLE_PHASE_REVIEW_POSTFLIGHT
    return LIFECYCLE_PHASE_SCAN
```

**The ordering now matches `_ordered_postflight_phase()`:** assessment → workflow → triage → review. The two phase-ordering implementations agree.
