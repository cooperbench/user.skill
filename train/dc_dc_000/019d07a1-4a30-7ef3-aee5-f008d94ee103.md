**Findings**
1. Static `workerModelName` in the proposed `ModelSpec` is the wrong abstraction. The doc makes it a static fact in [squishy-finding-lamport.md:18](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L18), but the current frontend already resolves the backend model late from execution context, not just selected model, in [modelPhase.ts:20](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/modelPhase.ts#L20). WAN already has multiple execution profiles there, so baking `workerModelName` into the static registry will reopen branching as soon as you add another variant.

2. The plan still leaves “effective mode” outside the resolver, so it does not really create a single source of truth. The resolver only takes `{ smoothContinuations, generationTypeMode }` and explicitly says guidance-based snapping stays outside in [squishy-finding-lamport.md:103](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L103), but the UI and payload decisions depend on effective mode in [squishy-finding-lamport.md:214](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L214). Today that logic is already split across [useStructureVideoHandlers.ts:52](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/video/useStructureVideoHandlers.ts#L52), [MotionControlBasicTab.tsx:160](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/MotionControlBasicTab.tsx#L160), and [requestBody.ts:117](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/requestBody.ts#L117). There is also an internal contradiction: earlier the doc says snapping should be guidance-kind-based, later it says `useStructureVideoHandlers.ts | spec.defaultTravelMode` in [squishy-finding-lamport.md:359](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L359).

3. `ContinuationConfig` is underspecified and internally inconsistent as the “canonical” client/worker contract. The doc says the worker falls back to `frame_overlap` for legacy payloads in [squishy-finding-lamport.md:160](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L160), but the worker sketch actually falls back to hardcoded `10` in [squishy-finding-lamport.md:261](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L261). The current shared payload still makes pair-scoped `frame_overlap` required in [taskTypes.ts:136](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/travelBetweenImages/taskTypes.ts#L136) and [payloadBuilder.ts:151](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/travelBetweenImages/payloadBuilder.ts#L151). I checked the local worker too: it currently quantizes base frames and overlaps first in [orchestrator.py:952](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L952), then adds overlap later for sequential VACE in [orchestrator.py:1945](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L1945). Without separate requested vs effective continuation state, users will end up in hidden-but-still-set states.

6. The registry duplicates capability truth that already exists elsewhere. `supportedGuidanceModes` in the proposed spec duplicates logic already centralized in [travelGuidance.ts:48](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/travelGuidance.ts#L48) and mirrored on the worker by `TravelGuidanceConfig`. If the goal is painless model addition, this should be shared/generated, not hand-maintained in two or three places.

**What I’d Change**
1. Keep the three-layer idea, but change the layers:
   `ModelFamilySpec`: static family facts only. No `workerModelName`.
   `GenerationIntent`: pure user-authored state, including `smoothContinuationsRequested`, requested mode, guidance kind, structure-video presence, advanced/turbo flags.
   `ResolvedExecutionPlan`: the only runtime authority, containing `backendModelName`, `effectiveTravelMode`, `effectiveGuidanceKind`, `continuation { requested, enabled, strategy, overlapFrames, transport }`, and `limits { maxSegmentFrames, frameStep }`.

2. Make one resolver own all effective behavior. UI, payload building, timeline limits, toggle visibility, and worker policy should all read the same resolved plan, not raw `selectedModel` plus ad hoc mode rules.

3. For the payload, either add a real `execution_plan` object or at minimum make `continuation_config` richer:
   `enabled`
   `strategy`
   `overlap_frames`
   `transport`
   Then derive `chain_segments` from that, and keep `frame_overlap` as a compatibility mirror only.

4. For UX, do not just hide unsupported smooth continuation. Keep a requested flag and an effective flag. If the request becomes unsupported, either auto-clear it or show it disabled with a reason.

Bottom line: the registry direction is good, but the current doc still standardizes by “model family + scattered exceptions.” To make future model additions painless, standardize around a resolved execution plan that both client and worker consume. No code changes made.
