        # Implementation Plan: Discord Presence Pacing

## Overview
Discord currently keeps a persistent Gateway websocket in `app/services/discord.py`, identifies without an explicit presence, and therefore appears online/green for the whole connected session. That connection must stay up so DMs remain reliable; the fix should change Gateway presence, not disconnect the bot.

The critique does not point to the wrong root cause. The plan is still correctly targeted at Gateway presence plus centralized typing integration. The missing pieces are two invariants the implementation must make explicit: typing-critical online upgrades must bypass anti-flap throttling, and REST typing must be suppressed when the manager cannot prove an active Gateway sender can update presence first.

Recommended approach: add a centralized `DiscordPresenceManager` owned by `DiscordGatewayBot` and passed into `DiscordPacer`. It sends Discord Gateway presence updates (`op: 3`) and includes an initial invisible presence in Identify. Official Discord Gateway docs list `invisible` as shown offline and `online` as the active state: https://docs.discord.com/developers/events/gateway-events#update-presence and opcode 3 as Presence Update: https://docs.discord.com/developers/topics/opcodes-and-status-codes#gateway-gateway-opcodes.

Presence is global to the bot, so the manager should maintain global holds rather than per-DM state. Typing paths call a hard `ensure_online_for_typing(...)` method before any REST typing request. That method must either synchronously confirm/send online presence or return false so the caller skips the typing indicator. Non-typing activity can request softer, delayed transitions so the bot feels present during conversation without flapping on every message.

The execute phase should write this plan document to `docs/discord-presence-pacing-plan.md` exactly.

3. State model:
   - `default`: invisible/offline-looking baseline.
   - `hard_online_until`: hard online deadline used for typing-critical work.
   - `soft_online_until`: optional believable activity window for inbound/reaction/send tails.
   - `current_status`: last status successfully sent or included in Identify.

   - `message_sent()` for after-send tail.
   - `reaction_sent()` for reaction tail.
   - `close()` to cancel background tasks.
5. `ensure_online_for_typing(...)` must bypass `min_transition_gap_s`, update `hard_online_until`, and synchronously send online presence if the current status is not already online.
6. If no active sender is attached, `ensure_online_for_typing(...)` must return `False` without pretending presence changed. Callers must skip REST typing in that case.
7. Internally, recompute desired status from active holds and schedule one delayed downgrade to default. Avoid one task per event when a single reschedulable downgrade task works.
8. Do not emit redundant presence updates when desired status already matches `current_status`, except that `ensure_online_for_typing(...)` may refresh the hard hold deadline without sending a duplicate update.
9. In `docs/discord-presence-pacing-plan.md`, include the state machine table:

| Event | Desired behavior |
| --- | --- |
| Gateway connect | Identify as `invisible`; stay connected. |
| Inbound DM | Maybe go `online` after bounded jitter for a short window, unless already online. Subject to anti-flap gap. |
| Bot typing pulse | Force `online` before `send_typing`; bypass anti-flap gap; hold through visible typing plus tail. |
| Gateway sender detached | Typing-critical calls return false; REST typing is skipped until a sender reattaches. |
| Thinking/composing typing loop | Maintain hard online hold across pulses when sender is attached. |
| Send message | Stay online for randomized after-send tail, then return invisible. |
| Reaction-only response | Brief online tail around reaction, without long green presence. |
| Idle/no conversation | Return to `invisible`; no green status. |

## Risks
1. Discord may rate-limit excessive presence updates. Mitigation: suppress duplicates, use `min_transition_gap_s` for soft transitions and downgrades, and schedule downgrades instead of toggling per event.
2. Presence is global, not per-DM. Mitigation: short bounded holds and one centralized state machine.
3. If a websocket reconnects during a delayed downgrade, a stale task might send to the old socket. Mitigation: sender attach/detach with a generation token.
4. If low-level direct sends bypass `DiscordPacer`, typing could appear while invisible. Mitigation: wire `send_text`/`send_typing` through the same manager or add tests that fail on this ordering.
5. If `invisible` is rejected by Discord for a bot Identify or update, fallback should be a config-only rollback, not disconnecting the Gateway.
6. During Gateway reconnects, the user may not see typing indicators. This is acceptable because the stronger requirement is not sending typing unless online presence can be guaranteed.

## Questions
1. Should the default status be strictly `invisible`, or is `idle` acceptable if Discord ever rejects bot `invisible` updates?
2. Should scheduled/proactive messages use the same after-send online tail, or should only live DM conversations affect presence?
3. Should operators see presence transitions and skipped typing during reconnect in logs, or is test coverage plus Discord behavior enough?

## Assumptions
1. The bot can send `invisible` in Identify and Gateway Presence Update payloads, based on Discord’s official Gateway docs.
2. Staying connected to the Gateway while invisible preserves DM receipt reliability.
3. Presence behavior should only apply when `MESSAGING_PROVIDER=discord`; other providers remain unchanged.
4. No database migration is needed because this is runtime state and configuration only.
5. The existing `pacing_events` table remains for conversation pacing decisions; presence transitions can be logged but do not need persistence.
6. Skipping typing during Gateway reconnects is preferable to sending typing when online presence cannot be guaranteed.
