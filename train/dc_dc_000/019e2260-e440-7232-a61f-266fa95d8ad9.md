The core diagnosis is real, but the brief has a couple of code-level misstatements that are dangerous enough to fix before spending harness time.

**Code Match**
The “two independent capacity controllers” claim is fair. Runtime enters `_handle_early_termination` before scaling decision/execution in [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/control_loop.py:109). Early termination computes `current_capacity = active + spawning`, then `early_desired` from `task_counts.total * scale_down_multiplier`, min GPUs, and idle buffer at [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/control_loop.py:362). Later, `_calculate_scaling_decision` calls `calculate_scaling_decision_pure` when `use_new_scaling_logic` is enabled at [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/control_loop.py:802). That is a second controller with different action math.

The `queued == 0` gate is exactly real: early-term skips only when `task_counts.queued > 0`; if queued is zero, it can terminate eligible spawning workers at [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/control_loop.py:377).

The brief is slightly wrong on `calculate_scaling_decision_pure`. It does use queued coverage for spawn actions: `workers_covering_tasks = idle + spawning`, `uncovered_tasks = queued - workers_covering_tasks`, then `spawn_for_tasks = uncovered_tasks` at [worker_state.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/worker_state.py:588). It also uses a busy-worker buffer for proactive floor at [worker_state.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/worker_state.py:594). But `desired_workers` itself is still populated from the legacy `total_workload * scale_up_multiplier`, `busy + idle buffer`, and `min_active_gpus` block at [worker_state.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/worker_state.py:616). So change the brief from “computes desired from queued coverage” to “emits spawn actions from queued coverage while retaining legacy desired fields for observability/scale-down.” That distinction matters.

The duplicate path claim is also real, but sharper than the brief says. `control_loop.py` is the actual production path; `main.py` imports `OrchestratorControlLoop` from it. The `control/phases/` mixins duplicate large chunks, including early termination, but are only directly exercised by tests. They are not an alternative active runtime path today. So do not let megaplan waste time “choosing” without this fact: default deletion target should be the unused mixin duplication, unless the plan first converts production to mixins.

One loud correction: brief line 37 says the scaling decision is “computed once at top-of-cycle, mutated by early-term, then consumed.” That is false for current code. The scaling decision is computed after early termination. The stale part is `task_counts` from phase 1, plus the fact that early-term mutates DB/worker list before a different formula runs. Fix this wording. The architecture is still broken, but that explanation is wrong.

**Acceptance Criteria**
Tests A and D are good. D is not invented terminology: `is_route_stale` is a real derived state based on `worker_contract_version` and route contract compatibility in [worker_state.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator/gpu_orchestrator/worker_state.py:83).

Test B is under-specified and probably internally inconsistent. With `next_spawn_allowed_at = now() + min(2^N * 30s, 600s)`, “four failures over four cycles” and “successful spawn on cycle 5 after backoff window” only works if the test controls the clock and advances past the cooldown. Require a fake clock and assert exact `next_spawn_allowed_at` values after each failure.

Test C’s “2 cycles” is arbitrary but acceptable as a first guardrail. It should be justified as “two observed reconciler snapshots with stable desired ≤ effective,” not merely “two loop iterations,” because duplicate Railway replicas or delayed cycles make cycle count slippery. Better: stable_since plus at least `2 * orchestrator_poll_sec`, with tests covering both clock time and snapshots.

Missing invariants:
- No spawn action may execute unless a durable intent/action row exists first, or idempotency is still weak.
- Authoritative mode must be single-writer per pool per cycle, probably advisory lock or lease, not just deduped audit rows.
- Shadow mode must never call RunPod or update worker status, including failure/backoff side effects.
- `spawn_failed` backoff must be keyed by pool/route contract, not global.
- Existing spawning workers at cutover must be adopted from current workers table, not require prior intent rows.

**Shadow Mode**
The shadow plan is directionally realistic, but currently too hand-wavy. The existing controller mutates state in `_handle_early_termination`, `_handle_spawning_workers`, cleanup, and scale execution. A shadow reconciler can work only if the brief pins its position in the cycle. I would require: run shadow `OBSERVE→PLAN→ADMIT→RECORD` after lifecycle probing but before legacy early-term/scale execution, or run it from an explicit immutable snapshot captured before legacy capacity actions. Otherwise divergence data will be contaminated by legacy mutations.

Also, `system_logs source_type='orchestrator_shadow'` will currently violate the DB check constraint. The existing SQL allows only `orchestrator_gpu`, `orchestrator_api`, and `worker`. The migration must alter that constraint or use `source_type='orchestrator_gpu'` with metadata tag `shadow_intended_action`.

Twenty-four hours is not enough as a standalone gate. Make it “at least 24h and at least N meaningful capacity events.” The smoking-gun scenario may not appear in normal traffic within a day. Require replay against captured production logs/table snapshots as a pre-cutover gate, then use shadow as live confidence, not the only proof.

**Scope**
The out-of-scope list is mostly right. Cross-pool rebalancing, UI, worker-side code, and config-system replacement should stay out. Keeping `min_active_gpus`, `machines_to_keep_idle`, and buffer inputs is fine, but the brief must require the planner to define the one authoritative desired/action formula exactly. You can avoid “simplifying” those knobs while still specifying how they compose.

The app-side debug touch is load-bearing for rollout visibility, so it belongs in scope exactly as written.
