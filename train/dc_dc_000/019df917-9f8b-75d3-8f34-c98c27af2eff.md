> AGENT

There are two related “chaining” concepts in Megaplan: **1. `--from-doc` chaining** Use this when one Megaplan output should feed the next run. Example: ```bash megaplan init --mode metaplan --output docs/design.md "Design the migration" megaplan init --mode code --from-doc docs/design.md "Implement the migration" ``` If the doc has a `## Settled Decisions` section, Megaplan imports those decisions into the next plan. `load_bearing: true` becomes a hard `must` success criterion; `false` becomes informational context. **2. `megaplan chain` milestone chaining** This runs a sequence of separate Megaplan plans from a YAML spec. The spec looks roughly like: ```yaml seed: plan: existing-plan-name milestones: - label: m1 idea: /workspace/ideas/M1.txt - label: m2 idea: /workspace/ideas/M2.txt on_failure: abort: stop_chain on_escalate: abort: stop_chain ``` Then: ```bash megaplan chain start --spec chain.yaml megaplan chain status --spec chain.yaml ``` How it works: it optionally drives a seed plan first, then initializes each milestone from its idea file, runs it through the normal `megaplan auto` loop until terminal state, records progress in `chain_state.json`, and moves to the next milestone. If interrupted, rerunning resumes from that state file. So the short version: `--from-doc` chains context/decisions between plans; `megaplan chain` chains whole milestone plans sequentially with resumable state.

> AGENT

What makes sense depends on the intended chain semantics. I’d define them explicitly like this: **Recommended Model** A chain should be a linear stack by default. ```text main -> chain/<run>/m1 -> chain/<run>/m2 -> chain/<run>/m3 ``` Each milestone builds on the exact result of the previous milestone, because otherwise it is not really a chain. It is just a batch of unrelated plans. **Concrete Behavior** For each milestone: 1. Start M1 from current `origin/main`. 2. Create/check out its configured branch, e.g. `megaplan/m1-foundation-store`. 3. Run the Megaplan plan there. 4. Commit the result if there are changes. 5. Push the branch. 6. For M2, create its branch from M1’s final commit, not from `main`. 7. Repeat. So M2 sees M1’s code. M3 sees M1 + M2. That matches what humans expect from “milestone chain.” **Failure Behavior** If a milestone fails or escalates: - `stop_chain`: stop on the current branch and preserve state. - `retry_milestone`: reset/retry that milestone branch from its parent branch. - `skip_milestone`: questionable for stacked chains, because M3 may depend on M2. I’d either discourage it or make it mean “base next milestone on the last successful milestone.” **Branch Field** The existing `branch:` field should stop being informational. It should control the actual branch name. If absent, derive one: ```text megaplan/<chain-name>/<index>-<label> ``` **State File** `chain_state.json` should record more than just the plan name: ```json { "current_milestone_index": 1, "current_plan_name": "...", "base_ref": "origin/main", "last_successful_branch": "megaplan/chain/m1", "last_successful_sha": "...", "current_branch": "megaplan/chain/m2" } ``` That makes resume deterministic. **Main Branch Refresh** The current `git checkout main && git pull` before every milestone should change. It should happen only once at chain start, unless explicitly requested. Good default: ```text refresh main once -> run stacked branches from that fixed base ``` Optional mode: ```yaml base: refresh: per_milestone ``` But per-milestone refresh should not be the default for a chain. **PR Strategy** At the end, there are two reasonable options: - Open one PR from the final branch containing the whole chain. - Open stacked PRs, one per milestone, where M2 targets M1, M3 targets M2. For most autonomous work, I’d default to one final PR and optionally support stacked PRs later. So the core fix is: make chain preserve and advance a branch cursor. Current code advances a milestone index, but not a git base. That is the missing concept.
