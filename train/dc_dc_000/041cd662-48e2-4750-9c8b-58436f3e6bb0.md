## What a pack actually is

Discovery is dead simple (astrid/core/pack.py:43-64): walk `astrid/packs/`, take every subdir that has a `pack.yaml`. Content inside is found by `rglob` for `orchestrator.yaml` / `executor.yaml` (pack.py:146-153). The manifest itself is tiny — just `id`, `name`, `version`, optional `metadata` (pack.py:67-86).

So the model is: **a pack is a folder of orchestrator/executor folders, with a near-empty marker file at the root.**

## Where the abstractions feel off

**1. The taxonomy is muddled.** You currently have:
- `builtin/` — 40+ orchestrators in one pack (the kitchen sink)
- `external/` — adapters to 3rd-party services (RunPod, Vibecomfy, Fal, Moirae)
- `seinfeld/` — a topic bundle with its own model-training subworld
- `iteration/`, `upload/` — small topic bundles
- `local/` — "scratch pack" with just `elements/effects`

It's not obvious *why* `iteration` is its own pack but `render`/`scenes`/`cut` are inside `builtin`. Or why `youtube` is in `upload` while RunPod is in `external`. A first reader can't predict where a new orchestrator should land. The packs feel like organic accretion, not a designed namespace.

**2. "Pack" conflates two very different things.** `builtin` and `external` are infra-shipped-with-astrid. `seinfeld` and `local` are user/project content. Same primitive, very different lifecycles. There's no concept of "this pack is mine, that pack is the platform's" — they all live in the same tree and ship together.

**3. There is no installation.** `packs_root()` is hardcoded to `astrid/packs/` (pack.py:43-44). To add a pack you commit a folder into the astrid Python package. orchestrator.yaml references its runtime as `astrid.packs.builtin.event_talks.run` — a literal Python dotted path inside the astrid namespace (event_talks/orchestrator.yaml). So:
   - A pack physically cannot live outside the astrid package without breaking imports.
   - There's no pip-installable pack format, no entry-point registry, no `astrid pack install ...`.
   - "Custom packs" today = "fork astrid and add a folder."

If long-term you want a community/user-pack story, the import-path coupling is the wall you'll hit first.

**4. The manifest is too anemic for what packs do.** `pack.yaml` declares nothing about its content — no required python deps, no declared orchestrators, no inter-pack dependencies, no capability tags. Discovery is *all* by file convention. This is fine for a small in-repo tree but unsuitable for "someone publishes a pack" and surprisingly fragile (a typo'd `pack.yml` just silently isn't a pack — discover_packs returns it as nothing, no warning).

**5. The flat-YAML parser is a footgun.** `_parse_flat_yaml` (pack.py:169-190) is custom and only supports `key: value`. No lists, no nested dicts, no multiline. Anyone writing a "normal-looking" YAML will get cryptic indentation errors. Either commit to JSON or use a real YAML lib — this in-between state is the worst of both.

Right now you're encoding the plan-v2 schema by hand in every template.

# Codex (GPT-5 / 5.4) agent launcher

Codex is installed on this machine as the `codex` CLI (`/Users/user_c042661f/.nvm/versions/node/v20.19.4/bin/codex`). ## When to use Codex

- **Second-opinion root-cause analysis.** Cascade of bugs, already explored by Claude — get Codex to look at the same evidence and rank root causes independently.
- **Adversarial code review.** Before shipping a non-trivial change, have Codex try to break it.
- **Delegated implementation.** When Claude Code has mapped out the fix but the user wants another model to do the writing (and Claude to verify).
- **Cross-checking Claude's diagnosis.** Especially when user asks "are you sure?" — Codex is a genuinely independent take, not an echo.

Don't use Codex for tasks where you already have the answer — it's not faster, and it's not free (contributes to the user's OpenAI quota).

## Model selection

Default to calling `codex exec` with **no `-m` flag** — the user's `~/.codex/config.toml` already pins the model. If you need to override, read the exact model string from that config file first.

## Basic invocation (non-interactive)

```bash
codex exec --sandbox read-only "PROMPT_HERE"
```

- `--sandbox read-only` — safe for analysis tasks (no file writes)
- `--sandbox workspace-write` — lets Codex modify files in the current project
- `--sandbox danger-full-access` — full shell access (avoid unless explicitly requested)
- `-m gpt-5-5.4` — pin the model explicitly
- `-c key=value` — one-off config override
- Output goes to stdout; the final response is the tail after Codex's own trace output

For a long prompt, write it to a file first and `cat` it in:

```bash
cat > /tmp/codex_prompt.md <<'EOF'
...your prompt here...
EOF
codex exec --sandbox read-only "$(cat /tmp/codex_prompt.md)" 2>&1 | tail -200
```

## Running in background

Long Codex sessions (multi-file implementations, deep analysis) should be backgrounded via the `run_in_background` parameter of the Bash tool. Tail the output file when the notification arrives:

```bash
codex exec --sandbox workspace-write "$(cat /tmp/codex_prompt.md)"
# set run_in_background: true in the Bash tool call
```

## Writing effective Codex prompts

Codex starts with zero conversation context. Like any subagent, the prompt must be self-contained:

- Name the working directory explicitly.
- List the exact files/paths to read, not "the relevant files."
- State the desired output format (diff, ranked list, schema proposal, etc.).
- Cap the response length ("under 600 words").
- For adversarial tasks, tell Codex to be opinionated — otherwise it will hedge.
- If you want Codex to write code, specify sandbox `workspace-write` and which files it's allowed to touch.

## Using `codex exec review` for PR-style reviews

```bash
codex exec review [--pr <n>] [--against <ref>] [prompt]
```

This is the non-interactive form of `/codex:review`. It produces a structured review against the current branch or a specified PR.

## Managing long sessions

- `codex exec resume` — continue a previous session
- `codex resume --last` — resume interactively
- Codex persists sessions under `~/.codex/`; they can be forked with `codex fork`

## Applying Codex-generated diffs

This runs `git apply` on the last diff Codex generated.

# Megaplan tickets

Tickets are short, repo-scoped notes on problems, bugs, or "we should look at this" observations against a codebase. They live as committed `.md` files under `<repo>/.megaplan/tickets/` and (when a cloud store is configured) mirror to `tickets` / `ticket_epics` tables. Tickets are inert until folded into an epic — they capture problems, not work.

## When to file a ticket

Reach for `megaplan ticket new` when:
- During epic or plan execution you notice an **out-of-scope problem** that should be tracked but isn't blocking the current task.
- The user explicitly asks you to **capture an observation** ("file a ticket for that", "make a note of this for later").
- You want to log a rough edge or potential bug whose fix would be its own piece of work.

Do **not** use tickets for:
- Guidance/corrections to *how the tooling itself behaves* — that's `megaplan feedback` (a separate, plan-scoped concept).
- In-flight task state — that's the executor's own checklist.
- General notes or chat — write them in the conversation.

## Filing

```bash
megaplan ticket new "<title>" -b "<body>" [--tags tag1,tag2]
```

Conventions:
- `-b "..."`, `--edit` (open `$EDITOR`), and `-` (read body from stdin) are mutually exclusive; one is required.
- `ticket new` prints **only the ULID** on stdout on success (logs go to stderr). Capture it for piping.
- `--tags` is comma-separated. Tags are freeform; common ones: `bug`, `refactor`, `tech-debt`, `observability`, `docs`, `cross-repo`.
- `source` is auto-derived: if `MEGAPLAN_TURN_ID` is set (the agent is running under a megaplan-launched worker), `source=agent` and the turn id is recorded; otherwise `source=human`.
- The repo is resolved from cwd via its root commit SHA (`git rev-list --max-parents=0 HEAD`). Identity survives rename / transfer / remote change.

Multi-line body via stdin:
```bash
cat <<'EOF' | megaplan ticket new "Title here" --tags tag1,tag2 -
First paragraph of the body.

More detail in a second paragraph.
EOF
```

## What to put in the body

Tickets feed the **planner** at epic-prep time — the planner reads open tickets and uses them to shape new plans. A ticket that records only the conclusion forces the planner to re-derive the reasoning from scratch (or skip the ticket because it can't tell whether the framing still holds). A ticket that records the reasoning is picked up as durable context.

Aim for these sections when the ticket is non-trivial:

- **Goal / problem** — what's wrong or what we want, one paragraph.
- **Shape** — the proposed direction, concrete enough to argue with.
- **Decisions already made** — every choice that was settled in the discussion that produced the ticket, with a one-line *why*. Examples: "default runtime is OrbStack on Mac, because of bind-mount perf"; "credentials passed in via env vars, not auto-read from host, because that's the point." Capture these so the planner inherits them as settled, not as questions to reopen.
- **Alternatives considered and rejected** — only include rejections that *shaped* the chosen direction (i.e. a planner reading later might otherwise reopen that path). Each with a one-line *why not*. Skip obvious or tangential rejections — they're noise.
- **Constraints / what must keep working** — invariants the fix has to respect.
- **Open questions** — decisions deliberately deferred (call these out explicitly so they don't get mistaken for settled ones). If a question was *discussed* without landing on an answer, talk through the options that were considered — name each one, give the case for it, and the case against. Don't reduce them to a bare list; the next planner needs the reasoning, not just the labels. Recovering the option set later is harder than recovering the conclusion — without it, the next planner restarts the discussion from zero.

"Decisions already made" is the single most valuable section. A ticket without it forces the planner to re-derive the reasoning from scratch.

Skip sections that don't apply. For a small bug report, the goal + a repro is enough. The bar is: *would a planner reading this in three months have what they need to act, or would they have to ask the original author?*

### Searching across repos

`ticket search` is the cross-cutting reader. Defaults:

- **Scope** — current repo. Pass `--all-projects` to scan every known repo (locally: the auto-maintained `~/.config/megaplan/known_repos.json` registry; cloud: every codebase). Pass `--project PATH|owner/name|name` (repeatable) to scope to specific repos.
- **Keywords** — multiple positional args. Default is **OR** (any keyword matches). Pass `--all` to require all keywords. Match is case-insensitive substring across **title, body, tags, and resolution_note**.
- **Sort** — `--sort {created,edited,length,title}`; `--asc` flips to ascending. Default: created, descending.
- **Snippets** — human output shows a 120-char snippet around the first match. `--no-snippet` to hide.

Examples:

```bash

# Same, but require BOTH terms:
megaplan ticket search stderr timeout --all

# Across every repo on this machine, only open, sorted by longest body first:
megaplan ticket search redis --all-projects --status open --sort length --json

# Scoped to two specific repos:
megaplan ticket search auth --project ~/Documents/reigh-app --project banodoco/megaplan
```

Unlike `ticket new`, **`ticket edit --body` does NOT accept `-` for stdin** — passing `-` will land a literal `-` as the body. For multi-line edits, use one of:
- `--body "$(cat file.md)"` to inline a file's contents
- `--edit` to open the current body in `$EDITOR`

`link ... --resolves` marks the join with `resolves_on_complete=true`. When the linked epic transitions to `done`, the ticket auto-flips to `addressed` and gets a `resolution_note` referencing the epic. Idempotent — re-running on an already-addressed ticket is a no-op.

## Modes

Megaplan runs in one of two modes; tickets work transparently in both:

- **Local-only** (no cloud store configured) — `.md` files on disk are the sole source of truth. `codebase_id` will be `null` in frontmatter; identity is computed on demand from the repo's root SHA.
- **Cloud-configured** (`SUPABASE_DB_URL` or megaplan config points at a store) — every operation writes the `.md` file **and** mirrors to the `tickets` / `ticket_epics` tables. Auto-registers the codebase on first ticket if needed.

You do not need to detect the mode yourself; the CLI dispatches based on whether a store is configured.
