# Implementation Plan: Use DebugCard at emission sites and silence plumbing chatter

## Overview

`DebugCard` (`source/core/log/debug_card.py:24`) renders aligned label/value rows. Today it is already used *implicitly* by `debug_block()` (`source/core/log/core.py:137`), which wraps any `Mapping` in a card. It is used *explicitly* only in `source/core/log/lifecycle.py:95,248` and `source/models/wgp/model_ops.py:171`. So the real work requested by the idea is not "start using the class" — it is:

1. Push raw multi-line debug strings at the six emission sites named in the idea (travel/join orchestrator, segment processor, task processor, wgp orchestrator, task conversion) through `DebugCard`/`debug_block` so output lines up and reads as one block.
2. Enforce a "2+ rows or don't bother" rule on cards so trivial single-row cards stop printing a title bar with one value.
3. Delete / silence the specific chatter lines enumerated in the idea.
4. Fold `[PAYLOAD_ORDER_DEBUG]` and `[FRAME_DEBUG]` raw strings into the existing `SEGMENTS` card in `source/task_handlers/travel/orchestrator.py`.
5. Replace the per-site `log_ram_usage()` f-strings with a single card that accumulates snapshots for a run, rendered once at the end (or per phase).

The debug surface area lives almost entirely in `source/task_handlers/travel/orchestrator.py` (~14 `debug_block` calls plus raw `debug_anomaly` noise), `source/task_handlers/travel/segment_processor.py`, `source/task_handlers/join/orchestrator.py`, `source/task_handlers/queue/task_processor.py`, `source/models/wgp/orchestrator.py`, `source/task_handlers/tasks/task_conversion.py`, plus `source/task_handlers/travel/debug_utils.py` for RAM. No tests assert log contents (only `tests/test_debug_card.py` covers rendering), so the blast radius is small.

Constraints: cards are debug-level (gated by `_debug_mode`); nothing in this plan should change what the non-debug user sees. Essential/progress/warning lines stay untouched.
