        # Implementation Plan: Rollback for Optimistic Asset Registry Updates

## Overview

Three sites in the video-editor hooks follow the same fire-and-forget optimistic pattern:
1. Call `patchRegistry(assetId, entry, src)` — updates in-memory `dataRef.current` via `commitData` with `save: false`
2. Call `registerAsset(assetId, entry)` — async server persist, errors only logged

On `registerAsset` failure, the local registry shows an asset the server doesn't know about. The fix: capture the previous registry entry (if any) before patching, and on failure, call `patchRegistry` again with the old state (or remove the entry entirely for new assets) and show an error toast.

**Key insight:** `patchRegistry` already calls `commitData` with `save: false`, so using it to revert is safe — it won't trigger a save cycle. For brand-new assets (no prior entry), rollback means restoring the registry state *without* the new key, which requires a slightly different approach since `patchRegistry` can only add/update entries, not remove them. However, examining the three call sites:
- `useAssetManagement.registerGenerationAsset` — creates a new asset and returns the `assetId` to the caller, which then uses it to build clips. The caller has already used this assetId. Reverting the *registry entry* back won't undo clip references, but it will surface the broken state. The simplest approach: on failure, patch the entry with an error marker or just leave it (the asset URL is still valid locally) and show the toast. Actually — the simplest and most correct approach is: **don't remove the asset from registry** (the local URL is fine), just show the error toast so the user knows the persist failed. The asset still works locally; it just won't survive a page reload.
- `useStaleVariants.updateAssetToCurrentVariant` — updates an *existing* entry. Here we should revert to the old entry.
- `useSwitchToFinalVideo.registerFinalVideoAsset` — creates a new asset, similar to useAssetManagement.

For the two "new asset" sites, a full rollback (removing the asset key from registry + undoing the clip edit) is complex and disproportionate — the user just took an action, removing it from the UI would be confusing. The pragmatic approach: show an error toast on all three. For `useStaleVariants` where we're *updating* an existing entry, also revert to the previous entry so the stale state is accurately shown again.
