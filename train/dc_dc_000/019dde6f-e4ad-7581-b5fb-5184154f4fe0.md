# Plan 6 — Onboarding + admin view + audit + feedback + ops finalization

Authoritative spec: `mediator-bot-spec.md`. Read in prep, focusing on: "Onboarding", "Operations", "Feedback Loop", and the admin/audit-related references throughout (especially `get_bot_actions` and the "why did you tell her that?" use case).

Plans 1–5 are assumed complete. The system is functionally end-to-end. This plan adds the operator-facing surfaces, the onboarding behavior, and the polish that makes the system usable for the two real partners.

## Scope (in)

### Onboarding (light, conversational)
- Welcome message: warm, explanatory; sets expectations (reflection and mediation assistant, not a therapist; will get things wrong; please correct me; how the basics work). Keep copy short and WhatsApp-conversational. Stored as a constant; sent on first inbound from each whitelisted user (via `send_outbound`; uses free-form within the 24h window which is guaranteed since the user just messaged in).
- Natural early seeding: the system prompt already (from Plan 3) instructs gentle one-or-two contextual questions in the first conversations. This plan adds:
  - A `users.onboarding_state` enum column (`pending` | `welcomed` | `seeded` | `complete`) — migration on top of Plan 1's schema. Only used to gate the welcome message and inform the loop's prompt-side hot context (e.g., "user is in early conversations — be upfront about thin context").
  - Hot context includes `onboarding_state` so the loop adjusts behavior without needing extra logic.
- Acknowledge thin context: nothing to implement beyond the prompt guidance already in Plan 3 + the onboarding_state hint.

### Admin view ([REDACTED], read-only)
- Single FastAPI router at `/admin`, [REDACTED] via Basic Auth or session cookie (admin password from env per Plan 1).
- Pages (server-rendered, simple HTML — no SPA needed):
  - **Recent turns**: list of `bot_turns` newest first, paginated. Click into a turn to see prompt snapshot, reasoning, model version, triggering message, final outbound, and all `tool_calls` rows for that turn.
  - **Recent messages**: both threads, newest first, with charge level and processing state. Edit history visible.
  - **Themes**: titles, descriptions, status, sentiment, health, last_active_at, last_reinforced_at.
  - **Memories**: filterable by user, status. Show supersession chain.
  - **Watch items**: filterable by owner and status; due_at visible.
  - **Observations**: filterable by user/theme/min-significance; supporting messages clickable.
  - **OOB entries**: severity, content, status, review_at.
  - **Scheduled jobs**: pending/fired/cancelled with type, scheduled_for, fired_at.
  - **Spend**: recent days of `llm_spend_log` per provider, with cap line drawn.
  - **Escalations**: distinguished `bot_turns` rows where `escalate_to_partner` was called.
- All views are read-only — no admin actions in v1 (the spec explicitly says admin is for debugging without writing SQL). If the user wants a manual escalation toggle later, it can be added.

### Audit endpoint (`get_bot_actions`)
- Already implemented as a tool in Plan 3 for the loop. Verify it answers "why did you tell her that?" correctly: given a date_range and target_type, returns the relevant turns with reasoning and the outbound content.
- Add a thin admin route that exposes the same query for human inspection.

### Feedback loop
- `log_feedback` tool already exists from Plan 3. Verify it's wired:
  - Conversational feedback recognized in the loop ("that was helpful", "no, that's wrong") and logged via the tool.
  - Source set to `'conversational'`.
- WhatsApp reaction webhook integration: register the reaction events in the webhook handler from Plan 2 (this is a small extension; reactions arrive as a different webhook payload type). On reaction: locate the assistant message by ID, write a `feedback` row with `source='reaction'`, `target_type='message'`, sentiment derived from the emoji (👍/❤️ → positive, 👎 → negative, others → mixed).
- Admin view shows recent feedback grouped by sentiment.

### Operations polish
- **Monitoring**: document the external uptime + cron-ping setup (README ops section). Add a `/health/deep` endpoint that checks DB, Anthropic API reachability (lightweight ping, cached for 60s), and returns a JSON summary. Real alerting is external.
- **Backups**: Supabase has automated backups; document the tested-restore procedure. Add a small script that pulls a fresh dump and writes a checksum file — operators run it quarterly.
- **Staging path**: ability to test prompt changes against past message logs without sending output. Implement as a CLI: `python -m app.staging replay --prompt-version <name> --since <date> --user <id>` that runs the loop in a dry-run mode against historical messages, printing what it WOULD have sent and written. Does not call `send_outbound` or write to DB.
- **Daily LLM spend cap enforcement**: Plan 1 plumbed the helpers; now wire them into the actual call sites. Each Anthropic / OpenAI / Groq call checks `is_under_cap(provider)` first and degrades gracefully:
  - Conversational LLM cap hit → respond once with "I'm running into limits today, will catch up tomorrow" and queue silently.
  - Vision cap hit → fall back to "I see you sent an image — can you describe it?" (already wired in Plan 2; just verify cap check is in place).
  - Transcription cap hit → "I can't transcribe right now — can you send it as text?".
- **Alerts at 80% of cap**: when a per-provider per-day spend crosses 80%, log a distinguished WARNING line; surface the warning in the admin view's Spend page. External alerting is out of scope.
