        # Implementation Plan: Refactor Edit Mode Ownership Out of useInpainting

## Overview

Edit mode state is currently owned by `useInpainting` (a domain-specific paint/annotate/text hook), but 6+ modes exist (text, inpaint, annotate, reposition, img2img, enhance, upscale). Two bridge functions (`toInpaintingEditMode`) narrow the wide type to the narrow 3-mode type, and `as` casts widen it back. This creates lossy round-trips, type confusion, and inverted ownership.

**Core insight**: `useInpainting` only ever checks `editMode === 'annotate'` and `editMode === 'inpaint'` internally — all other modes already fall through to "no strokes, not annotate mode." The narrowing in `toInpaintingEditMode` (mapping unknown modes → 'text') is functionally identical to just passing the wide type through. So we can delete the bridge entirely and pass the canonical type directly.

**Three type definitions to unify:**
- `inpainting/types.ts`: `EditMode = 'text' | 'inpaint' | 'annotate'` (narrow)
- `editSettingsTypes.ts`: `EditMode = 'text' | 'inpaint' | 'annotate' | 'reposition' | 'img2img' | 'enhance'` (wide)
- `ImageEditCanvasContext.tsx`: `ImageEditMode = 'inpaint' | 'annotate' | 'reposition' | 'img2img' | 'text' | 'upscale' | null` (wider, different members)

**Constraints**: No behavioral changes. All modes must continue working. The persistence layer already uses the wide type correctly.

## Overview

Edit mode state is currently owned by `useInpainting` (a domain-specific paint/annotate/text hook), but 7 modes exist (text, inpaint, annotate, reposition, img2img, upscale, enhance). Two bridge functions (`toInpaintingEditMode`) narrow the wide type to a 3-mode subset, and `as` casts widen it back. This creates lossy round-trips, type confusion, and inverted ownership.

**Core insight**: `useInpainting` only ever checks `editMode === 'annotate'` and `editMode === 'inpaint'` internally — all other modes fall through to "no strokes, not annotate mode." The narrowing bridge is redundant.

**Three type definitions to unify → one canonical type:**
- `inpainting/types.ts`: `EditMode = 'text' | 'inpaint' | 'annotate'` (narrow — delete)
- `editSettingsTypes.ts`: `EditMode = 'text' | 'inpaint' | 'annotate' | 'reposition' | 'img2img' | 'enhance'` (wide — promote to canonical, fix members)
- `ImageEditCanvasContext.tsx`: `ImageEditMode = 'inpaint' | 'annotate' | 'reposition' | 'img2img' | 'text' | 'upscale' | null` (wider — replace with `EditMode | null`)

**enhance vs upscale decision**: Investigation confirms `'enhance'` is **never set at runtime for images** — the UI calls `setEditMode('upscale')`. `'enhance'` only exists as a `VideoEditSubMode` (separate type system). The canonical `EditMode` will replace `'enhance'` with `'upscale'`. No normalization migration is needed because `DEFAULT_EDIT_SETTINGS.editMode` is `'text'`, `useLastUsedEditSettings` defaults to `'text'`, and no code path ever persists `'enhance'` as an image editMode.

**Ownership change**: Both production callers of `useInpainting` already pass `editMode` as a controlled prop. The `editMode` prop will become **required** (not optional), and the fallback `useState` inside useInpainting will be removed. This completes the ownership transfer to the orchestrator/persistence layer.

**Downstream scope**: Beyond the bridge functions, two additional files have local edit-mode unions/casts that must be updated: `useStrokeOverlayDrawing.ts` (inline 5-member union) and `MediaDisplayWithCanvas.tsx` (`as` cast to same union). Two others use `editMode: string` (GenerateButton, useRepositionGestureHandlers) — these are loose but type-compatible and don't require changes.

**Constraints**: No behavioral changes. All modes must continue working exactly as they do now.
