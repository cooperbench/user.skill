        # Implementation Plan: Audio Waveform Visualization on Timeline Clips

## Overview

Add waveform visualizations to audio clips (and video clips with audio) on the video editor timeline. When a clip has audio, render a small amplitude-over-time waveform inside the clip's visual rectangle in the timeline UI.

**Current state:** Clips render as styled buttons (ClipAction.tsx) with an icon, label, and optional thumbnail. Audio clips show a music note icon but no waveform. The existing AudioAnalysisProvider does per-frame FFT analysis for audio-reactive effects, but it operates at the Remotion composition level (not the timeline UI) and produces per-frame data, not a compact waveform summary.

**Approach:** Create a standalone hook that fetches audio files and extracts amplitude samples using the Web Audio API (`decodeAudioData`), then render those samples as an SVG/canvas waveform overlay inside ClipAction. This avoids coupling to the AudioAnalysisProvider (which is composition-scoped) and avoids adding `@remotion/media-utils` as a new dependency.

**Key constraint:** The timeline is div-based (not HTML5 Canvas). Each clip is a `<button>` rendered by ClipAction. The waveform will be rendered as an absolutely-positioned SVG or mini-canvas inside the clip button.

## Phase 1: Waveform Data Extraction

### Step 1: Create `useWaveformData` hook (`reigh-app/src/tools/video-editor/hooks/useWaveformData.ts`)
**Scope:** Medium
1. **Create** a new hook: `useWaveformData(src: string | undefined, options: { from?: number; to?: number; speed?: number; numBuckets: number })` → returns `{ waveform: number[] | null; loading: boolean }`.
2. **Implementation:**
   - Fetch the audio/video file URL via `fetch()` + `decodeAudioData()` (same pattern as `AudioAnalysisProvider.tsx:233-243`).
   - Downsample the decoded PCM buffer into `numBuckets` RMS amplitude values (each 0-1, normalized to peak).
   - Respect `from`/`to` trim and `speed` to only analyze the audible portion.
   - Cache decoded `AudioBuffer` by URL (module-level `Map<string, Promise<AudioBuffer>>`) to avoid redundant fetches when multiple clips share the same source.
   - Use `useEffect` with cleanup (abort controller) to cancel in-flight fetches on unmount/prop change.
   - `numBuckets` will be driven by clip pixel width (e.g., 1 bucket per 2-3px).
3. **Edge cases:**
   - If `src` is undefined or fetch fails, return `null` waveform gracefully (no error thrown).
   - Video files with embedded audio: `decodeAudioData` handles these natively (extracts audio track from container).
   - Very short clips: clamp minimum buckets to 2.

### Step 2: Add `WaveformOverlay` component (`reigh-app/src/tools/video-editor/components/TimelineEditor/WaveformOverlay.tsx`)
**Scope:** Medium
1. **Create** a lightweight component that takes `waveform: number[]` and renders an SVG polyline/path.
2. **Visual design:**
   - Absolutely positioned, fills the clip area (`inset-0`).
   - Semi-transparent fill (e.g., `fill="currentColor"` with `opacity-20` to `opacity-30`), so clip label/icon remain readable.
   - Mirror the waveform vertically (top half + bottom half) for the classic waveform look, or use a single-sided bar/area chart for compactness given the ~32px row height.
   - Use `pointer-events-none` so it doesn't interfere with click/drag/resize handlers.
3. **SVG approach** (preferred over canvas for simplicity in a div-based layout):
   - Generate a single `<path>` element with `M/L` commands.
   - ViewBox scales to waveform length, CSS scales to clip dimensions.
   - Memoize the path string to avoid re-rendering on every frame.

## Phase 2: Integration into Timeline UI

### Step 3: Wire waveform into ClipAction (`reigh-app/src/tools/video-editor/components/TimelineEditor/ClipAction.tsx`)
**Scope:** Medium
1. **Add props** to `ClipActionProps`:
   - `audioSrc?: string` — resolved URL for the clip's audio source.
   - `clipWidth?: number` — pixel width of the clip on the timeline (for bucket count).
2. **Render** `WaveformOverlay` inside the clip button, after the thumbnail/icon area but behind the label:
   - Only render when `audioSrc` is truthy (clip has audio).
   - Pass `numBuckets = Math.max(2, Math.floor(clipWidth / 3))`.
   - Pass `from`, `to`, `speed` from `clipMeta`.
3. **Update** `areClipActionPropsEqual` to include the new props.
4. **Determine audio eligibility:**
   - Audio tracks (`clipMeta.track.startsWith('A')` or track kind is `'audio'`): always show waveform.
   - Visual tracks with audio: show waveform if the asset is a video file (has audio track). This requires knowing whether the asset is a video — check file extension or asset type from the registry.

### Step 4: Pass `audioSrc` and `clipWidth` from TimelineCanvas/TimelineEditor
**Scope:** Small-Medium
1. **In** the `getActionRender` callback (defined in `TimelineEditor.tsx` and passed to `TimelineCanvas`), resolve the audio source URL:
   - For audio clips: use `resolvedConfig` to get `clip.assetEntry?.src`.
   - For video clips: same — `decodeAudioData` will extract the audio track.
   - For text/effect-layer clips: don't pass audioSrc.
2. **Compute** `clipWidth` from `(action.end - action.start) * pixelsPerSecond` — this is already calculated in `TimelineCanvas.tsx:198-199`. Pass it through to the render callback.
3. **Thread** `pixelsPerSecond` to the render callback if not already available (check current `getActionRender` signature).

### Step 5: Verify and test
**Scope:** Small
1. **Manual verification:**
   - Add an audio clip to the timeline → waveform appears.
   - Add a video clip with audio → waveform appears.
   - Add a text/effect clip → no waveform.
   - Resize/zoom the timeline → waveform re-renders with appropriate bucket count.
   - Trim a clip (adjust from/to) → waveform shows only the trimmed portion.
   - Muted clip → waveform still visible (it shows shape, not playback state).
2. **Run existing tests** to ensure no regressions:
   - `npx vitest run --reporter verbose` (or project-specific test command) on video-editor tests.
3. **Performance check:** Open a timeline with 10+ audio clips. Verify no jank — waveform extraction should happen once per unique URL and be cached.

## Execution Order
1. Step 1 (hook) → Step 2 (overlay component) → Step 3 (wire into ClipAction) → Step 4 (pass data from parent) → Step 5 (verify).
2. Steps 1 and 2 can be developed in parallel since they have no dependencies on each other.

## Validation Order
1. After Step 2: render WaveformOverlay in isolation with mock data to verify SVG output.
2. After Step 4: full integration test with real audio clips on the timeline.
3. Step 5: run existing test suite + manual smoke test.

## Key Design Decisions

- **SVG over canvas:** The timeline is div-based. An inline SVG inside the clip button is simpler than managing a separate canvas element per clip, and it inherits CSS colors/opacity naturally.
- **Separate hook vs. reusing AudioAnalysisProvider:** AudioAnalysisProvider is tightly coupled to Remotion composition rendering (per-frame, requires fps/totalDuration, mixed across all clips). The timeline UI needs per-clip waveform data independent of playback. A standalone hook is cleaner.
- **No new dependency:** `decodeAudioData` from the Web Audio API is sufficient. `@remotion/media-utils`'s `getAudioData` ultimately does the same thing. No need to add a dependency.
- **Single-sided vs. mirrored waveform:** Given the ~32px row height, a single-sided area chart (bars from bottom) may be more readable than a mirrored waveform. The component should support both — start with mirrored (classic look) and adjust based on visual testing.
