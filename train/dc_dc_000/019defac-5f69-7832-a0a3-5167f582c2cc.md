        # Implementation Plan: Project + ProjectTimeline

## Overview
Add a persistent project layer without changing executor/orchestrator bodies or the shared `@banodoco/timeline-schema`. The repo already has clean choke points: `artagents/pipeline.py` dispatches top-level CLI commands, `artagents/core/orchestrator/cli.py` parses canonical orchestrator runs, `artagents/core/orchestrator/runner.py` executes them, and `artagents/timeline.py` owns validation/loading/saving for existing `hype.timeline.json` and `hype.assets.json`.

The simplest durable approach is to add a new `artagents/core/project/` module for project state and materialization, then wire it only at CLI and runner boundaries. Existing `--out` behavior remains ad hoc and existing executor outputs stay unchanged.

## Phase 1: Project Skeleton + CLI

### Step 1: Add project paths and schema (`artagents/core/project/paths.py`, `schema.py`)
**Scope:** Medium
1. Implement `projects_root()` using `ARTAGENTS_PROJECTS_ROOT` or `~/Documents/reigh-workspace/artagents-projects/`.
2. Implement slug validation shared by CLI and path resolution.
3. Define lightweight stdlib schemas/validators for:
   - `project.json`
   - `sources/<source_id>/source.json`
   - `runs/<run_id>/run.json`
   - project `timeline.json`
4. Reuse existing ULID helpers from `artagents/threads/ids.py` for run ids.

### Step 2: Add project persistence APIs (`artagents/core/project/project.py`, `source.py`, `run.py`, `timeline.py`)
**Scope:** Medium
1. Implement create/load/show helpers around the fixed layout.
2. Ensure `create` writes `project.json`, empty `timeline.json`, and creates `sources/` and `runs/`.
3. Keep writes atomic enough for local CLI use: write JSON with temp file + replace.
4. Make error messages name the next command, for example `python3 -m artagents projects create <slug>`.

### Step 3: Add project CLI (`artagents/core/project/cli.py`, `artagents/pipeline.py`)
**Scope:** Medium
1. Add top-level dispatch in `artagents/pipeline.py` for `projects` or `project`.
2. Add help text to `_print_entrypoint_help()`.
3. Initial commands:
   - `projects create <slug> [--title ...]`
   - `projects show --project <slug>`
   - `projects source add --project <slug> --path PATH [--id SOURCE_ID] [--kind video|audio|image]`
   - `projects timeline show --project <slug>`
4. Every command prints a project header before command output.
5. State-changing project commands require `--project`, except `create`, where the slug is the project identity.

## Phase 2: ProjectTimeline + Source-Only Materialization

### Step 4: Implement project timeline placement schema (`artagents/core/project/timeline.py`)
**Scope:** Medium
1. Validate placements with fields: `id`, `track`, `at`, `from`, `to`, `source`, `entrance`, `exit`, `transition`, `effects`, `params`.
2. Model `source` as `{ "kind": "source" | "run", ... }` while keeping it distinct from existing TimelineConfig clips.
3. Validate numeric ranges: `at >= 0`, `from >= 0`, `to > from` when present.
4. Validate refs exist in the project before saving.

### Step 5: Materialize source-only timelines (`artagents/timeline.py`, `artagents/core/project/materialize.py`)
**Scope:** Medium
1. Add `materialize_project_timeline(project_dir) -> tuple[TimelineConfig, AssetRegistry]` in `artagents/timeline.py` or a project module re-exported from `timeline.py`.
2. For source placements, create standard TimelineConfig clips using the source asset entry and placement timing/effects.
3. Generate an asset registry with stable asset keys for source refs.
4. Call existing `validate_timeline()` on the materialized TimelineConfig.
5. Save materialized outputs through CLI, for example `projects materialize --project <slug> --out <dir>` writing `hype.timeline.json` and `hype.assets.json`.

### Step 6: Add placement editing CLI (`artagents/core/project/cli.py`)
**Scope:** Medium
1. Add `projects timeline place-source --project <slug> --source <source_id> --track v1 --at 0 --from 0 --to 5`.
2. Add `projects timeline remove --project <slug> <placement_id>`.
3. Add deterministic JSON output with `--json` for tests.
4. Ensure errors include the next useful command, such as `projects source add --project <slug> ...`.

## Phase 3: Run Integration

### Step 7: Wire `--project` into orchestrator runs (`artagents/core/orchestrator/cli.py`, `artagents/core/orchestrator/runner.py`)
**Scope:** Medium
1. Add `project: str | None` to `OrchestratorRunRequest`.
2. Add `--project` to `python3 -m artagents orchestrators run`.
3. If `--project` is set and `--out` is absent, mint a run id and set `request.out` to `<project>/runs/<run_id>` before invoking the unchanged runtime.
4. Preserve explicit `--out` behavior for ad hoc and compatibility cases.
5. After completion, write project-level `runs/<run_id>/run.json` with project metadata and pointers to existing output files.
6. If runtime output includes `hype.timeline.json`, `hype.assets.json`, or `hype.metadata.json`, mirror or copy them to the project run canonical names `timeline.json`, `assets.json`, `metadata.json` without modifying original executor outputs.

### Step 8: Add `--project` to hype direct CLI (`artagents/orchestrators/hype/run.py`)
**Scope:** Medium
1. Add `--project` as an alternative to `--out` in `build_parser()` and `resolve_args()`.
2. Resolve `--project` to a minted project run directory before current path normalization.
3. Keep all downstream step commands unchanged so the pipeline still writes the same `hype.*.json` files under the chosen output directory.
4. Add tests proving `--out` output files remain byte-for-byte compatible for the same inputs/dry-run plan path.

### Step 9: Materialize run placements (`artagents/core/project/materialize.py`, `artagents/core/project/cli.py`)
**Scope:** Medium
1. Add `projects timeline place-run --project <slug> --run <run_id> --clip <clip_id> --track v1 --at 0`.
2. Resolve `kind: run` placements by loading the run’s `timeline.json` and `assets.json`.
3. Copy the referenced run clip into the materialized TimelineConfig, overriding `id`, `track`, `at`, `from`, `to`, entrance/exit/transition/effects/params when supplied by the placement.
4. Prefix/namespace asset keys from run assets to avoid collisions.
5. Validate the final materialized TimelineConfig with existing `validate_timeline()`.
