        # Implementation Plan: Fix Timeline Save Concurrency (Last-Write-Wins with Version Refresh)

## Overview

The timeline save system uses optimistic locking via `update_timeline_config_versioned` (SQL RPC that bumps `config_version` only when `expected_version` matches). The recent commit `8a50a533` added 406 recovery, but it has three remaining failure modes:

1. **No save serialization.** Nothing prevents overlapping `saveTimeline` calls. Two concurrent saves use the same `configVersionRef` — one succeeds, the other 406s. During rapid edits or move operations, this is common.
2. **Retry goes through debounce.** The 406 handler calls `scheduleSave` (500ms debounce), which can be cleared by new edits arriving during the timer, causing the retry to never fire.
3. **`savedSeqRef` stays stale after 406.** Since `savedSeqRef` only updates in `onSuccess`, a 406 leaves `savedSeq < editSeq` permanently true, which blocks `shouldAcceptPolledData` and prevents polling from ever syncing the version.

The fix: serialize saves (one in-flight at a time), retry 406s immediately (bypass debounce) with a capped retry count, and ensure `savedSeqRef` recovers even if all retries fail.

**Files touched:**
- `src/tools/video-editor/hooks/useTimelineSave.ts` — primary changes
- `src/tools/video-editor/lib/timeline-save-utils.ts` — extract retry helper (optional, for testability)

**Not touched (no changes needed):**
- `SupabaseDataProvider.ts` — already correctly throws `TimelineVersionConflictError` on 406
- `update_timeline_config_versioned` SQL — the RPC is correct; the bug is client-side

## Main Phase

### Step 1: Add save serialization guard (`useTimelineSave.ts`)
**Scope:** Small
1. **Add** `isSavingRef = useRef(false)` and `pendingSaveRef = useRef<{data: TimelineData, seq: number} | null>(null)` alongside the existing refs (~line 69-74).
2. **Guard** `saveTimeline` (~line 150): if `isSavingRef.current` is true, stash the request in `pendingSaveRef` and return early. After any save completes (success or final error), check `pendingSaveRef` and drain it.
3. **Set** `isSavingRef.current = true` at the start of `saveTimeline`, `false` in a `finally` block (or after both success and error paths).

This eliminates the primary source of unnecessary 406s — two concurrent saves racing with the same version number.

### Step 2: Immediate retry on 406, bypass debounce (`useTimelineSave.ts`)
**Scope:** Medium
1. **Add** `conflictRetryRef = useRef(0)` and a constant `MAX_CONFLICT_RETRIES = 3`.
2. **Replace** the `onError` handler for version conflicts (~lines 108-120). Instead of calling `scheduleSaveRef.current(...)` (which debounces 500ms and can be preempted):
   - Fetch fresh version via `provider.loadTimeline(timelineId)`
   - Update `configVersionRef.current`
   - If `conflictRetryRef.current < MAX_CONFLICT_RETRIES`, increment retry count and call `saveTimeline(dataRef.current, editSeqRef.current)` directly (no debounce)
   - If retries exhausted, fall through to error state and let polling recover
3. **Reset** `conflictRetryRef.current = 0` on successful save (~line 160, inside `onSuccess`).
4. **Reset** `conflictRetryRef.current = 0` at the start of each new user-initiated save (inside `scheduleSave` when the timer fires, before calling `saveTimeline`).

This ensures 406 recovery is immediate and not susceptible to debounce clearing.

### Step 3: Fix `savedSeqRef` stall after unrecoverable 406 (`useTimelineSave.ts`)
**Scope:** Small
1. **In the 406 error handler**, after retries are exhausted (or if `loadTimeline` itself fails), set `savedSeqRef.current = editSeqRef.current`. This unblocks `shouldAcceptPolledData` so the 30s polling can sync the version.
2. **Rationale:** The user's local edits are "lost" from the server's perspective if all retries fail, but polling will pull the server state and `configVersionRef` will be updated. The next user edit will trigger a fresh save attempt with the correct version. This is better than the current deadlock where the UI shows "error" forever and polling never fixes it.

### Step 4: Handle pending save drain after conflict retry (`useTimelineSave.ts`)
**Scope:** Small
1. **After** a successful conflict retry (or any successful save), check `pendingSaveRef`. If a newer save was queued while the retry was in-flight, drain it. This ensures that if the user edited during the retry cycle, those edits are saved with the now-correct version.
2. **Wire** the drain into the `finally` block alongside `isSavingRef.current = false`.

### Step 5: Add dev-only logging for conflict recovery (`useTimelineSave.ts`)
**Scope:** Small
1. **Add** `console.log('[TimelineSave] ...')` statements (gated behind `import.meta.env.DEV` or not — per project convention, debug logs are dev-only and stripped in prod):
   - When a 406 is detected: log expected vs actual version
   - When retry fires: log attempt number
   - When retry succeeds: log final version
   - When retries exhausted: log warning
2. This makes the concurrency model observable for future debugging.

### Step 6: Validate with manual testing
**Scope:** Medium
1. **Cheapest validation first:** Open the timeline editor, move clips around rapidly. Observe that save status cycles `dirty → saving → saved` without getting stuck on `error`.
2. **Simulate concurrent writer:** Open two tabs on the same timeline. Edit in tab A, then edit in tab B before tab A's save completes. Both should eventually reach `saved` status.
3. **Verify polling still works:** After an AI agent writes to the timeline (external writer), the editor should pick up the change within 30s without a manual reload.
4. **Verify no regressions:** Normal editing (add clip, move clip, delete clip, change effects) should save without errors.

## Execution Order
1. Step 1 (serialization) first — it reduces 406 frequency and makes the retry logic simpler to reason about.
2. Steps 2-4 together — they form the retry/recovery mechanism.
3. Step 5 (logging) last — it's independent.
4. Step 6 after all code changes.
