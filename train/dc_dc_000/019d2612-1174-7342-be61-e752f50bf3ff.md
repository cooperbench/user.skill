## Overview

The OverlayEditor (`src/tools/video-editor/components/PreviewPanel/OverlayEditor.tsx`) handles preview-canvas clip manipulation (move, resize). Three bugs need fixing, one of which is a critical string-matching error, one is a new feature (edge crop), and one is a DOM cleanup issue in timeline drag.

**Key finding:** The `DragMode` type is `'move' | 'resize-nw' | 'resize-ne' | 'resize-sw' | 'resize-se'` and the drag handler uses `state.mode.includes('e')` etc. to detect resize directions. But **`'move'.includes('e')` is `true`** because the string "move" contains the letter "e". This causes every move operation to also apply east-resize logic, changing the clip's width.

**Secondary finding:** Drag deltas are computed in screen pixels (`event.clientX - startMouseX`) but applied directly to composition-space coordinates. This means move/resize speed doesn't match cursor speed when the preview is scaled.

**Crop feature:** No crop data model exists yet. `ClipMeta` and `TimelineClip` have no crop fields. This requires type additions, new edge handles in the overlay, and Remotion composition support.

## Phase 1: Fix Move & Resize Bugs (OverlayEditor.tsx)

### Step 1: Fix the string-matching bug (`OverlayEditor.tsx:219-232`)
**Scope:** Small — the root cause of issue #1.

1. **Replace** the `state.mode.includes('e')` / `'s'` / `'w'` / `'n'` checks with exact suffix/prefix matching. The modes are `'resize-nw'`, `'resize-ne'`, `'resize-sw'`, `'resize-se'`. Use `state.mode.endsWith('e')`, `state.mode.endsWith('w')`, `state.mode.startsWith('resize-n')`, `state.mode.startsWith('resize-s')` — or better, guard all resize branches with `state.mode !== 'move'` first, then use `includes`.

   ```typescript
   // Before (buggy):
   if (state.mode.includes('e')) { ... }

   // After (option A — clearest):
   if (state.mode !== 'move') {
     if (state.mode.includes('e')) { ... }
     if (state.mode.includes('s')) { ... }
     if (state.mode.includes('w')) { ... }
     if (state.mode.includes('n')) { ... }
   }
   ```

2. **Validate** by moving a clip and confirming width/height remain unchanged in the committed patch.

### Step 2: Fix coordinate-space mismatch (`OverlayEditor.tsx:205-237, 249-262`)
**Scope:** Small — secondary bug causing move/resize to feel sluggish or fast depending on zoom.

1. **Convert** screen-space deltas to composition-space before applying to bounds. The conversion factor is `compositionWidth / layout.width` for X and `compositionHeight / layout.height` for Y.

   ```typescript
   const scaleX = compositionWidth / layout.width;
   const scaleY = compositionHeight / layout.height;
   const deltaX = (event.clientX - state.startMouseX) * scaleX;
   const deltaY = (event.clientY - state.startMouseY) * scaleY;
   ```

2. **Challenge:** `layout` is React state, but the mousemove handler is set up in a `useEffect`. Need to either capture layout in a ref or compute the scale at drag start and store it in `dragState`. Storing `scaleX`/`scaleY` in the dragState ref (computed at `startDrag` time from current `layout`) is cleanest — avoids stale closures.

3. **Update `startDrag`** (`OverlayEditor.tsx:249-262`) to capture `scaleX`/`scaleY` in the dragState ref. Update the dragState type to include these fields.

### Step 3: Validate move and resize behavior
**Scope:** Small

1. **Test manually:** Move a clip — should translate 1:1 with cursor, width/height unchanged.
2. **Test manually:** Corner-resize — should scale width/height, position anchored at opposite corner.
3. **Regression check:** Text clip move/resize, text editing double-click still works.

## Phase 3: Fix Timeline Ghost Artifact

### Step 8: Audit ghost/indicator cleanup paths (`useClipDrag.ts`, `useTimelineEditing.ts`)
**Scope:** Small

1. **Trace** all exit paths from drag operations:
   - `useClipDrag.ts`: `handlePointerUp` (line 353), `handlePointerCancel` (line 385), `handleBlur` (line 421), effect cleanup (line 431). All call `clearSession`.
   - `useTimelineEditing.ts`: `onTimelineDragLeave` (line 650), `onTimelineDrop` (line 657). Both call `clearDropIndicator`.

2. **Identify** the gap: If a drag starts but the `dragover` event sequence is interrupted (e.g., dropping outside the timeline, pressing Escape, or the component unmounting mid-drag), indicators may orphan because:
   - HTML5 `dragleave` fires on the element boundary but may not fire if the drop happens on a child element or outside the window.
   - `useClipDrag` appends elements to `document.body` — if the effect cleanup runs (line 431) it calls `clearSession(dragSessionRef.current)` which should clean up, BUT if `dragSessionRef.current` is already null (because `handlePointerUp` cleared it), the orphaned DOM nodes from a *previous* session won't be found.

3. **Specific suspects:**
   - The `deferDeactivate` path (line 157-162) delays cleanup by one RAF — if a new drag starts in that window, the old ghost could linger.
   - `clearDropIndicators` (line 121) removes indicator elements but only nulls `session.indicator` — if the session ref is already cleared, the DOM nodes are leaked.

### Step 9: Harden cleanup (`useClipDrag.ts`)
**Scope:** Small

1. **Add a safety sweep** — before creating new indicators, query and remove any stale `drop-indicator-*` and `cross-track-ghost` elements from `document.body`. This is a defensive pattern for DOM elements appended outside React's tree.

   ```typescript
   // At the start of ensureIndicator or handlePointerDown:
   document.querySelectorAll('.cross-track-ghost, .drop-indicator-row, .drop-indicator-line, .drop-indicator-ghost, .drop-indicator-label')
     .forEach(el => el.remove());
   ```

2. **Also clean up in `useTimelineEditing.ts`** `ensureDropIndicator` — before creating a new indicator root, remove any stale `[data-drop-indicator]` elements.

3. **Add effect cleanup** in `useTimelineEditing.ts` — the `clearDropIndicator` call should also run on unmount if it isn't already.
