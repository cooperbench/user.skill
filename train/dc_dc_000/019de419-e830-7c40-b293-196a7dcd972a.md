        # Implementation Plan: Human-Like Discord Conversation Pacing

## Overview
Veas already has the core pieces for this: Discord gateway ingestion in `app/services/discord.py`, fixed burst coalescing in `app/services/debouncer.py`, the two-phase agentic lifecycle in `app/services/agentic.py`, reaction directives after Phase A, OOB guards in `agentic.py` and `messaging.py`, and focused tests around Discord, debouncing, lifecycle, and OOB.

The best pragmatic implementation is not to rewrite the agentic turn. Add a pacing layer between inbound coalescing and `run_agentic_turn`: deterministic signals decide obvious wait/answer cases, a small LLM judgement handles ambiguous react/silence/answer choices, and the full agentic turn remains the only path for substantive text. This preserves safety/OOB behavior while making Discord feel less message-in/reply-out.

I attempted to inspect `resident_chat_runtime` through plain `python` and `uv run`; plain Python could not import it, and `uv` failed in this sandbox before import. The implementation should verify its exact Gateway callback API locally before editing, but the repo evidence is enough to plan the touch points.

## Phase 1: Foundation — Configuration, Types, Observability

### Step 1: Add pacing settings (`app/config.py`, `.env.example`)
**Scope:** Small
1. Add explicit config for Discord pacing, with conservative defaults:
   - `discord_pacing_enabled: bool = True`
   - `discord_pacing_idle_seconds`, `discord_pacing_max_wait_seconds`
   - `discord_pacing_typing_hold_seconds`, `discord_pacing_min_reply_delay_seconds`, `discord_pacing_max_reply_delay_seconds`
   - `discord_pacing_llm_enabled: bool = True`
   - `discord_pacing_model`, defaulting to the cheap judgement model already used for scoring unless product preference says otherwise.
2. Keep existing WhatsApp/meta behavior unchanged unless `messaging_provider == "discord"`.

### Step 2: Create a pacing event audit trail (`migrations/0008_discord_pacing.sql`, `tests/conftest.py`)
**Scope:** Medium
1. Add a `pacing_events` table with `user_id`, `message_ids uuid[]`, `provider`, `decision`, `reason`, `deterministic_signals jsonb`, `llm_judgment jsonb`, `created_at`, and optional `acted_at`.
2. Add indexes for recent events by user/time and message ids if needed.
3. Update `FakePool` in `tests/conftest.py` to support inserting/selecting pacing events for unit tests.

## Phase 2: Pacer Core

### Step 3: Implement the pacer module (`app/services/pacer.py`)
**Scope:** Large
1. Define `PacingDecision` values: `wait`, `react`, `silence`, `answer`.
2. Define a structured `PacingSignals` object from programmatic inputs: burst size, elapsed time, last inbound age, max charge, user-is-typing state, duplicate/fragment-like messages, question marks, explicit commands, media presence, and provider.
3. Add deterministic hard gates:
   - `/pause` and `/resume` stay outside pacing.
   - `crisis` should answer via the full agentic path, with only minimal delay and no silence/react-only decision.
   - `charged` may wait briefly for continuation, but should not be silently dropped unless LLM gives a clear reason and the event is recorded.
   - If Discord says the user is typing, wait/extend up to the configured maximum.
4. Add `judge_pacing_decision(...)` for ambiguous routine/notable bursts. Use a tiny JSON-only prompt that can choose `react`, `silence`, or `answer`, with a one-sentence reason and optional emoji from a tight allowlist.
5. Enforce tasteful reaction behavior in code, not only prompt text: sparse emoji allowlist, no repeated reactions to every message, no reaction on crisis, and no reaction if provider is not Discord.

### Step 4: Extend burst coalescing into pacing (`app/services/debouncer.py`)
**Scope:** Medium
1. Extend `BurstCoalescer` to accept an optional `pacer` or `should_fire` callback.
2. On idle expiry, ask the pacer whether to fire, wait, react, silence, or answer.
3. For `wait`, reschedule without losing the current batch, capped by `max_seconds`/`discord_pacing_max_wait_seconds`.
4. For `answer`, call the existing `on_burst_complete(message_ids, user)`.
5. For `react` or `silence`, mark the inbound messages processed and record the pacing event without running the full agentic turn.
6. Preserve `add_burst(...)` recovery behavior so old raw messages can still be flushed directly during startup recovery.

## Phase 3: Discord Typing And Human-Like Delivery

### Step 5: Wire Discord typing-start signals (`app/services/discord.py`)
**Scope:** Medium
1. Verify whether `resident_chat_runtime.discord_gateway.GatewayCallbacks` supports typing callbacks.
2. If supported, register `on_typing_start`; if not, detect `TYPING_START` in `DiscordGatewayBot._run_once` before/around `dispatch_payload`.
3. Track per-user/channel typing timestamps in the pacer so the coalescer can pause/extend while the user is composing.
4. Remove the current unconditional `asyncio.create_task(_send_typing_after_delay(...))` from `_handle_message`; typing should come from the pacing/delivery layer, not every inbound message.

### Step 6: Make typing indicators feel human (`app/services/discord.py`, `app/services/messaging.py`, `app/services/pacer.py`)
**Scope:** Medium
1. Before a full answer is sent, schedule typing only after the pacer has decided to answer.
2. Do not send typing while the user is currently typing.
3. Add start/stop/start-like behavior by delaying the initial typing call and optionally sending another typing event for longer generated replies.
4. Keep `discord.send_text(...)` safe as a low-level helper, but avoid duplicate typing calls when the pacer has already handled typing.

## Phase 4: Agentic Integration And Prompt Updates

### Step 7: Add pre-turn pacing context (`app/services/agentic.py`, `app/services/prompts.py`)
**Scope:** Medium
1. Let `run_agentic_turn(...)` accept optional `trigger_metadata` or pacing metadata, or pass it into `_run_agentic(...)` so Phase A knows why the turn was fired.
2. Include pacing context in the Phase A seed: burst summary, whether the pacer waited, whether the user stopped typing, and any pacer reason.
3. Tighten prompt language around not over-questioning, silence being acceptable, reaction sparseness, and answering the whole burst rather than each line.
4. Keep existing OOB checks unchanged for all outbound text.

### Step 8: Preserve and improve reaction behavior (`app/services/agentic.py`, `app/services/pacer.py`)
**Scope:** Small
1. Keep existing `[react: emoji]` support after Phase A for cases where the full agentic turn naturally chooses a reaction.
2. Add pre-turn pacer reactions only for simple, low-risk acknowledgements where a full LLM turn is unnecessary.
3. Record both pacer reactions and agentic reactions in `bot_turns.reasoning` or `pacing_events.reason`, depending on which path chose them.

## Phase 5: Tests And Docs

### Step 9: Add focused pacing tests (`tests/test_pacer.py`, `tests/test_debouncer.py`)
**Scope:** Large
1. Test deterministic decisions: crisis answers, typing waits, max wait eventually answers, routine thanks can react/silence when LLM says so, and unsupported providers answer normally.
2. Test burst behavior: multi-message bursts remain one unit; a typing event extends the window; a second message before expiry is included in the same decision.
3. Test observability: every wait/react/silence/answer decision writes a `pacing_events` row with signals and reason.

### Step 10: Update Discord and lifecycle tests (`tests/test_discord.py`, `tests/test_agentic_lifecycle.py`, `tests/test_oob_check.py`)
**Scope:** Medium
1. Update Discord tests to assert typing is not sent immediately on every inbound message.
2. Add typing-start gateway tests once the callback/dispatch shape is confirmed.
3. Add lifecycle tests proving pacer metadata reaches Phase A when an answer is fired.
4. Keep OOB tests passing unchanged, proving all text still goes through existing outbound guards.

### Step 11: Document behavior (`README.md` or a focused docs section)
**Scope:** Small
1. Document the pacing decisions, config knobs, and expected Discord UX.
2. Include operator notes for tuning idle/max waits and disabling LLM pacing judgement.

        # Implementation Plan: Human-Like Discord Conversation Pacing

## Overview
Veas already has the right core surfaces: Discord gateway ingestion in `app/services/discord.py`, fixed burst coalescing in `app/services/debouncer.py`, the two-phase agentic lifecycle in `app/services/agentic.py`, outbound/OOB delivery in `app/services/messaging.py`, media enqueue paths in `app/services/transcription.py` and `app/services/vision.py`, startup wiring in `app/main.py`, and recovery in `app/services/recovery.py`.

The critique does not show that the original plan targeted the wrong root cause. The root cause is still that Discord has only fixed burst coalescing plus immediate/provider-level typing, with no pre-turn pacing policy. The flags show missing execution touch points: low-level Discord typing must be parameterized, the pacer must be constructed in startup, LLM judgement must use spend accounting, callback metadata must have an explicit path into the agentic turn, per-user preference storage must be concrete, and media/recovery callers need explicit behavior. This revision keeps the same architecture but tightens those gaps.

The implementation should add a Discord-first pacing layer before the full agentic turn. Deterministic signals handle obvious wait/answer safety cases, a small spend-accounted LLM judgement handles ambiguous routine/notable cases, and substantive text remains in the existing agentic/OOB-protected path. Wait/react/silence/answer decisions get durable observability even when no `bot_turns` row is created.

## Phase 1: Foundation — Configuration, Preferences, Observability

### Step 1: Add global pacing settings (`app/config.py`, `.env.example`)
**Scope:** Small
1. Add conservative Discord pacing settings:
   - `discord_pacing_enabled: bool = True`
   - `discord_pacing_idle_seconds`
   - `discord_pacing_max_wait_seconds`
   - `discord_pacing_typing_hold_seconds`
   - `discord_pacing_min_reply_delay_seconds`
   - `discord_pacing_max_reply_delay_seconds`
   - `discord_pacing_llm_enabled: bool = True`
   - `discord_pacing_model`, defaulting to the existing cheap judgement model unless product tuning chooses otherwise.
2. Gate behavior on `messaging_provider == "discord"` so WhatsApp/meta behavior stays unchanged.
3. Add bounded min/max validation in code, not only documentation, so per-user overrides cannot create extreme sleeps.

### Step 2: Add per-user pacing preferences (`migrations/0008_discord_pacing.sql`, `app/models/user.py`, `tests/conftest.py`)
**Scope:** Medium
1. Add `users.pacing_preferences jsonb NOT NULL DEFAULT '{}'::jsonb` in the new migration.
2. Define the supported preference keys in code, for example `idle_seconds`, `max_wait_seconds`, `typing_hold_seconds`, `llm_pacing_enabled`, `reaction_style`, and `answer_bias`.
3. Implement a small preference resolver that merges global settings with `users.pacing_preferences`, clamps unsafe values, and falls back cleanly for users with `{}`.
4. Update `FakePool` user rows and user fetch helpers so tests can store and read pacing preferences.

### Step 3: Create durable pacing observability (`migrations/0008_discord_pacing.sql`, `tests/conftest.py`)
**Scope:** Medium
1. Add a `pacing_events` table with `user_id`, `message_ids uuid[]`, `provider`, `decision`, `reason`, `deterministic_signals jsonb`, `llm_judgment jsonb`, `preferences_snapshot jsonb`, `source`, `created_at`, and optional `acted_at`.
2. Add indexes for recent events by user/time and message ids.
3. Update `FakePool` to support inserting pacing events and reading them in tests.
4. Record events for every terminal decision (`react`, `silence`, `answer`) and for meaningful waits/extensions.

## Phase 2: Pacer Core And Cost Controls

### Step 4: Implement the pacer module (`app/services/pacer.py`)
**Scope:** Large
1. Define `PacingDecision` values: `wait`, `react`, `silence`, and `answer`.
2. Define `PacingSignals` from real message rows and runtime state: burst size, elapsed time, last inbound age, max charge, current Discord typing state, source (`live`, `media`, `recovery`, `catch_up`), media presence, question/direct-request indicators, fragment-like content, repeat reactions, and provider.
3. Fetch message rows by `message_ids` inside the pacer so text, charge, media type, and stale/recovered status are based on persisted data rather than caller guesses.
4. Add deterministic hard gates:
   - `/pause` and `/resume` remain handled before pacing in `app/services/inbound.py`.
   - `crisis` always answers through the full agentic path, with no silence or reaction-only decision.
   - `charged` may wait briefly for continuation but cannot be reaction-only; silence requires explicit LLM justification and a recorded event.
   - Media-derived messages from transcription/vision answer after coalescing and should not be pre-turn reacted/silenced.
   - Recovered or catch-up messages bypass human typing/reaction behavior and answer immediately or enter the existing recovery flow.
   - If Discord says the user is typing, wait/extend up to the configured cap.
5. Enforce reaction taste in code: small allowlist, cooldown by recent `pacing_events`, no reactions for crisis/media/recovered messages, no repeated reaction-only responses in a short window.

### Step 5: Add spend-accounted LLM pacing judgement (`app/services/pacer.py`, `app/services/spend.py` or a shared cost helper)
**Scope:** Medium
1. Before any pre-turn LLM call, check `is_under_cap(pool, "text")`; if not under cap, skip LLM pacing and choose deterministic `answer` or defer only through the existing spend-cap behavior.
2. After the LLM judgement call, record cost with the same pricing rules used by agentic turns. Prefer extracting a shared helper from `app/services/agentic.py` rather than duplicating private cost math.
3. Use a JSON-only prompt for ambiguous routine/notable live Discord bursts. Allowed output fields: `decision`, `reason`, `emoji`, and `confidence`.
4. Validate the LLM decision against deterministic gates before acting. Invalid or unsafe judgement falls back to `answer` and records the fallback reason.

## Phase 3: Coalescer, Callback Metadata, And Startup Wiring

### Step 6: Extend burst coalescing without breaking legacy callers (`app/services/debouncer.py`)
**Scope:** Medium
1. Keep the existing `on_burst_complete(message_ids, user)` path intact for tests and non-paced use.
2. Add optional constructor dependencies: `pacer`, `on_paced_burst_complete`, and default `source="live"` support for `add(...)`.
3. Keep `add(user_id, message_id, user)` backward compatible; add optional keyword metadata such as `source="live"` so recovery/media callers can be explicit.
4. On idle expiry, if no pacer is configured, call the legacy callback exactly as today.
5. If a pacer is configured, ask it for a decision. For `wait`, reschedule the same burst without losing message ids. For `answer`, call `on_paced_burst_complete(message_ids, user, pacing_metadata=...)`. For `react`/`silence`, mark messages processed and do not run the full agentic turn.
6. Preserve `add_burst(...)` as direct callback behavior for crash recovery of already-formed batches.

### Step 7: Add an agentic metadata entry point (`app/services/agentic.py`)
**Scope:** Medium
1. Add `run_agentic_turn_with_metadata(triggering_message_ids, user, *, pacing_metadata)` as the explicit callback target for paced answers.
2. Delegate to `_run_agentic(..., trigger_metadata={"kind": "inbound", "pacing": pacing_metadata})` so Phase A sees why the pacer answered.
3. Keep `run_agentic_turn(...)` unchanged for current callers.
4. In the Phase A seed, include compact pacing context: decision reason, wait count/duration, user typing stopped/expired, burst size, source, and any preference override that mattered.
5. Tighten prompt language around whole-burst response, avoiding over-questioning, sparse reactions, and acceptable silence while preserving the existing OOB rules.

### Step 8: Wire the live app construction (`app/main.py`)
**Scope:** Medium
1. Construct a `DiscordPacer` or equivalent only when `messaging_provider == "discord"` and pacing is enabled.
2. Pass `pool`, `settings`, the pacer, and `run_agentic_turn_with_metadata` into `BurstCoalescer` during startup.
3. Store the pacer on `app.state.discord_pacer` so `DiscordGatewayBot`, recovery, and tests can share typing state.
4. Keep the old `BurstCoalescer(on_burst_complete=run_agentic_turn)` construction for non-Discord or pacing-disabled providers.
5. Add startup tests or app-lifespan tests proving the production construction actually attaches the pacer for Discord.

## Phase 4: Discord Typing And Delivery

### Step 9: Wire Discord typing-start state (`app/services/discord.py`)
**Scope:** Medium
1. Verify the exact `resident_chat_runtime.discord_gateway.GatewayCallbacks` API during implementation.
2. If it supports typing callbacks, register `on_typing_start`; otherwise, detect `TYPING_START` in `DiscordGatewayBot._run_once` before or around `dispatch_payload`.
3. On typing start, update the pacer’s per-user/channel typing timestamp and do not enqueue a message.
4. Remove the current unconditional `_send_typing_after_delay(...)` task from `_handle_message`; the pacer owns typing UX.
5. Add tests that a partner message is ingested without immediate typing and that typing-start events update pacer state.

### Step 10: Parameterize low-level Discord typing (`app/services/discord.py`, `app/services/messaging.py`, `app/services/agentic.py`)
**Scope:** Medium
1. Change `discord.send_text(to, body)` to accept a keyword such as `send_typing_indicator: bool = True`.
2. Change `send_outbound(...)` to accept a matching Discord typing option and pass it through only for the Discord provider.
3. When an outbound is sent from a paced agentic turn, pass `send_typing_indicator=False` because the pacer already handled typing timing.
4. Leave default low-level typing enabled for non-paced Discord sends such as pause confirmations or operational messages, unless a caller explicitly opts out.
5. Add tests proving paced sends do not call `send_typing` twice and non-paced Discord sends still can emit typing.

### Step 11: Make answer typing feel human (`app/services/pacer.py`, `app/services/discord.py`)
**Scope:** Medium
1. After the pacer chooses `answer`, delay within configured min/max bounds before starting typing.
2. Suppress typing while the user is still typing; if they resume typing during the answer delay, wait until the typing hold expires or the max wait cap is reached.
3. For longer answer generation, optionally refresh Discord typing once using the existing REST typing endpoint; do not loop indefinitely.
4. Record typing wait/started/suppressed facts in `pacing_events.deterministic_signals` or associated reason text.

## Phase 5: Media, Recovery, And Catch-Up Paths

### Step 12: Make non-text media paths explicit (`app/services/transcription.py`, `app/services/vision.py`, `app/services/inbound.py`)
**Scope:** Medium
1. Pass `source="media"` when transcription or vision enqueues a processed inbound message into the coalescer.
2. Ensure media-derived bursts can coalesce with nearby text from the same user, but cannot be pre-turn silenced or reaction-only.
3. Include media indicators in `PacingSignals` so the answer path can tell Phase A that the trigger included voice/image/document context.
4. Add tests where voice/image analysis joins a text burst and produces one answer decision.

### Step 13: Make recovery and catch-up behavior explicit (`app/services/recovery.py`, `app/services/discord.py`)
**Scope:** Medium
1. Keep `coalescer.add_burst(...)` as direct recovery behavior for known crashed grouped turns.
2. Pass `source="recovery"` for old raw messages recovered by `recover_on_startup(...)`; the pacer should answer without live typing/reaction/silence behavior.
3. Pass `source="catch_up"` for Discord catch-up messages ingested by `catch_up_recent_messages(...)`; stale offline history should not receive reaction-only or human typing indicators.
4. Add tests proving recovered/catch-up raw messages are not delayed by user-typing state and do not trigger reactions.

### Step 15: Update integration-adjacent tests (`tests/test_discord.py`, `tests/test_agentic_lifecycle.py`, `tests/test_send_outbound.py`, `tests/test_oob_check.py`)

3. Add lifecycle tests proving pacing metadata reaches Phase A and paced outbound disables duplicate low-level typing.

### Step 16: Document pacing behavior (`README.md` or a focused docs section)
