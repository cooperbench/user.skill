        # Implementation Plan: Incremental Agent-Led Discord Sending

## Overview
Design and document a lightweight architecture for incremental Discord sends in `docs/incremental-agent-sending-plan.md`. The current repo has a two-phase agent lifecycle in `app/services/agentic.py`: Phase A reads and produces one final user-facing text, that text is OOB-checked and sent through `app/services/messaging.py`, then Phase B writes state using a seed of what was sent. Discord delivery is currently a provider branch inside `send_outbound`, backed by `app/services/discord.py`, and Discord-specific conversational pacing already exists around `run_agentic_turn_with_metadata` and `before_paced_send`.

The critique does not point to a wrong root cause. The root cause is still that the runtime has no first-class actual-send primitive during Phase A. The plan did need two concrete corrections: the primitive must be wired through the repo's Anthropic tool schema/registry path, and idempotency cannot depend on an optional model-supplied key.

The architecture to document is not paragraph splitting. It should add a first-class incremental-send contract: the agent can intentionally emit send actions while it reasons, the runtime records the actual send ledger after provider acknowledgement, Phase A can continue with an accurate transcript of sent content, interruption checks run between send opportunities, and Phase B is seeded from the actual send ledger rather than the model's planned text.

The likely implementation touch points are `app/services/agentic.py`, `app/services/messaging.py`, `app/services/discord.py`, `app/services/prompts.py`, `tool_schemas.py`, `app/services/tools/registry.py`, migrations under `migrations/`, fake DB support in `tests/conftest.py`, lifecycle tests in `tests/test_agentic_lifecycle.py`, transport tests in `tests/test_send_outbound.py`, and focused Discord transport tests if needed.

## Main Phase

### Step 1: Confirm Current Constraints For The Document (`docs/incremental-agent-sending-plan.md`)
**Scope:** Small
1. **Author** a short "Current shape" section in `docs/incremental-agent-sending-plan.md` that grounds the plan in these existing contracts:
   - `app/services/agentic.py` currently runs Phase A to completion before any outbound send and Phase B after send.
   - `send_outbound` in `app/services/messaging.py` already handles OOB checks, pause withholding, provider retry, row state changes, provider message IDs, and onboarding claim after successful provider acknowledgement.
   - `tool_schemas.py` and `app/services/tools/registry.py` are required for any Anthropic-visible tool; adding only runtime code in `agentic.py` would leave `send_message_part` unavailable or phase-rejected.
   - `run_agentic_turn_with_metadata` already supports Discord pacing context and a `before_paced_send` callback, so incremental sends should fit beside pacing rather than replace it.
2. **State** why a naive paragraph splitter is insufficient: it cannot know semantic send boundaries, cannot adapt to tool results, cannot expose an accurate sent-so-far ledger to the model, and risks Phase B writing from planned content instead of delivered content.

### Step 2: Define The Incremental Send Primitive And Tool Exposure (`docs/incremental-agent-sending-plan.md`)
**Scope:** Medium
1. **Document** a new runtime primitive in `docs/incremental-agent-sending-plan.md`, tentatively named `send_message_part`, exposed only in the Phase A/read loop for Discord-capable turns.
2. **Specify** the required tool wiring for a future implementation:
   - add the tool schema and description in `tool_schemas.py`.
   - add the dispatch handler and Phase A allowlist entry in `app/services/tools/registry.py`.
   - ensure the handler rejects use outside read/Phase A and returns a structured tool result instead of leaking provider details.
3. **Specify** that each call accepts intentional user-facing content plus optional metadata such as `part_kind` and `semantic_boundary`, but does not accept raw hidden reasoning.
4. **Require** the runtime to assign a stable `part_key` even when the model does not provide one. A model-supplied `client_part_key` can be accepted as a hint, but the idempotency contract must be enforced by a runtime-generated key derived from `turn_id`, ordered send attempt index, and/or tool call id.
5. **Define** the tool result returned to the agent as the authoritative sent ledger entry:
   ```json
   {
     "status": "sent",
     "message_id": "...",
     "provider_message_id": "...",
     "content": "actual delivered text",
     "part_index": 1,
     "part_key": "turn-id:part-1",
     "sent_so_far": ["..."]
   }
   ```
6. **Call out** that Discord is the first target transport because it has no WhatsApp 24-hour template constraint and better supports conversational incremental delivery; non-Discord providers can keep the current single-send path until explicitly enabled.

### Step 3: Design The Actual-Send Ledger And Idempotency Model (`docs/incremental-agent-sending-plan.md`)
**Scope:** Medium
1. **Author** a persistence section in `docs/incremental-agent-sending-plan.md` proposing minimal durable state for incremental sends:
   - extend `messages` with `bot_turn_id`, `part_index`, and `part_key` if that keeps the design simple, or introduce a small outbound ledger table only if the schema review shows `messages` should stay transport-neutral.
   - keep every actual user-visible part as a normal outbound `messages` row so hot context, audit, Phase B, onboarding, and admin surfaces can reason from the same source of truth.
2. **Require** a unique durable idempotency constraint, such as `(bot_turn_id, part_key)` or `(bot_turn_id, part_index)`, before provider delivery is attempted.
3. **Define** idempotency gates:
   - duplicate runtime `part_key` within a turn returns the already-recorded ledger entry and does not call Discord again.
   - retry after provider acknowledgement but before tool-result delivery re-reads the ledger before sending.
   - provider failure leaves an `expired` or withheld row that is not treated as sent content.
   - if provider acknowledgement succeeds but the process crashes before returning the tool result, recovery can rebuild `sent_so_far` from processed outbound rows tied to the turn.
4. **Make** the ledger the only source for "what has actually been sent so far"; model draft text, omitted keys, and failed attempts must not feed Phase B as delivered content.

### Step 4: Preserve Safety And Lifecycle Guarantees (`docs/incremental-agent-sending-plan.md`)
**Scope:** Medium
1. **Document** the OOB flow in `docs/incremental-agent-sending-plan.md`: every `send_message_part` routes through the same final delivery guardrail as `send_outbound`; OOB `block`/`rewrite` is returned to the agent as a tool result, and the runtime never marks blocked/rewrite-withheld text as sent.
2. **Document** interruption handling: before each provider send, check global pause, per-user pause, and whether newer inbound messages have arrived for the same user after the turn started; if interrupted, return a structured `interrupted` result and stop Phase A without further sends.
3. **Document** onboarding semantics: `claim_onboarding_welcome` should remain tied to actual provider-acknowledged sends or successful Discord reactions, not model intent or withheld rows.
4. **Document** Phase B seeding: replace `You sent: <assistant_text>` with an actual ledger summary such as `You actually sent 2 Discord messages: ...`; if interrupted after one part, Phase B writes only from that one delivered part plus the interruption context.

### Step 5: Describe Agent Loop Integration Without Overbuilding (`docs/incremental-agent-sending-plan.md`)
**Scope:** Medium
1. **Author** a control-flow section in `docs/incremental-agent-sending-plan.md` showing the smallest viable integration in `app/services/agentic.py`:
   - keep the existing two-phase shape.
   - in Phase A, include `send_message_part` in the allowed tool set only when Discord incremental mode is enabled and the registry exposes it.
   - after each send tool result, append the result to the Anthropic transcript so the model can continue naturally with `sent_so_far` visible.
   - when Phase A ends, send any final non-empty returned text through the same primitive, or require the model to use the primitive and treat final text as unsent fallback depending on the chosen policy.

3. **Keep** transport-specific behavior at the edge: `app/services/messaging.py` can host a lower-level `send_outbound_part` helper, while `agentic.py` owns turn ledger assembly and Phase B seeding.
