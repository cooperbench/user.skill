I have drafted a design doc at **`docs/longitudinal-state.md`** for a new "user journeys" abstraction — durable, structured user state that evolves over weeks/months (pregnancy week, weight tracking, fitness progress). Read the full doc first.

Your job: **stress-test the doc against three concrete use cases** and report where it bends, breaks, or over-builds. Be opinionated. Push back hard if the design is too complex or too loose for the actual needs.

## The three use cases the doc must accommodate

### Use case 1 — Tante Rosi (pregnancy coach)

A new solo-shape bot. The user is the pregnant person. She needs the bot to know and use:

- **Gestational week** — currently 17w2d, advances with time, no manual updates
- **Due date** — could come from LMP (last menstrual period) initially, then corrected by a dating scan at ~12 weeks
- **Weight gain from baseline** — a track the user reports periodically; recommended range 10–14kg total
- **Upcoming appointments** — 12-week scan, 20-week scan, glucose tolerance test, etc. (already fits existing `scheduled_tasks`, the doc does NOT propose a separate milestones table)
- **Trimester** — derived label, not a track per se
- **Loss / miscarriage handling** — a `status='lost'` value exists in the doc specifically so a pregnancy ending in miscarriage isn't lumped with `'abandoned'`
- **Postpartum transition** — at birth, pregnancy journey gets `status='transitioned'` and a new journey (kind='postpartum') gets `supersedes_journey_id` pointed at it
- **Sensitivity** — pregnancy is special-category health data; sharing with partner via mediator bot must be deliberate, never auto-bridged

Test: does the doc handle these naturally, including the LMP→dating-scan correction (anchor mutation that retroactively shifts everything else)?

### Use case 2 — Weight-loss coach

A solo-shape coach bot tracking a single user's weight-loss arc:

- Baseline weight (e.g. 85kg) at a baseline date
- Target weight (e.g. 75kg) by an optional target date
- Weekly weigh-ins, user-reported
- Progress derived: delta from baseline, % to target, trend over 4 weeks, "stale" if no weigh-in in 2× cadence
- "Plateau" detection (informally — bot notices and brings it up)
- Eventual `status='completed'` when target hit and held; `status='abandoned'` if user drops out

Test: is the single-track shape modeled cleanly? Does `current_state` carry enough for the bot to render "down 2.9 of 10, trending down, last weighed 2 days ago"?

### Use case 3 — Fitness coach

A solo-shape coach bot tracking a composite fitness program:

- **Frequency** — target 3 sessions/week (a *rate*, computed over a rolling 4-week window from per-session events)
- **Bench press** — measured each gym session, working from 60kg toward 80kg
- **5k time** — measured at occasional time trials, working from 27:30 toward 25:00
- **Program type** — anchor metadata, e.g. "ppl_3day" (push/pull/legs 3 days/week)
- **Bulk → cut cycles** — modeled as separate journeys chained via `supersedes_journey_id`, not as a phase within one journey

Test: does the doc cleanly support multiple parallel tracks of different `metric_kind` within one journey? Is the `rate` semantic well-defined? Does the per-session "value=1" measurement convention work, or is there a cleaner way?

## What to assess

For each use case, answer concretely:

1. Does the schema in the doc fully accommodate this case, or does it bend?
2. Is the `metric_kind` taxonomy (`measurement | rate | computed | anchor_date`) sufficient for this case? Anything missing?
3. Are the JSON shapes in the doc (anchors, tracks, current_state) tight enough to validate against, or are they loose hand-waves?
4. Does the recompute discipline hold? Specifically — what mutations trigger recompute, and have we forgotten any?
5. Is the render contract for this case prompt-ready, or does the bot still have render-time work?

Then cross-cutting:

6. **Naming.** Is `user_journeys` right? Should it be `tracked_arcs`, `user_state_arcs`, or something else? Does any of the three cases feel awkward under "journey"?
7. **Boundary with existing artifacts.** Will bots accidentally use `themes`/`observations`/`distillations` for things that should be journeys, or vice versa? Where's the line?
8. **Over-engineering.** Is anything in the doc speculative or premature? Specifically critique `lost` status, the cron tick recomputer for time-derived tracks, and the kind registry's responsibilities.
9. **Under-specification.** Where would a junior engineer implementing this make wrong assumptions because the contract is hand-wavy? Be specific about which JSON fields, which tool semantics, which edge cases.
10. **Migration plan realism.** Doc estimates ~600-900 lines + medium-effort sprint. Plausible or optimistic?

**Verdict**

The doc mostly holds up for weight loss and the simple parts of pregnancy, but it breaks first on time-derived cache invalidation and pregnancy anchoring. The schema says `current_state` is prompt-ready, yet stale flags, gestational age, rate windows, and denormalized scheduled-task milestones all change without journey-table mutations. Also, the pregnancy example models both `lmp_date` and `due_date` but computes gestational week from LMP, which becomes wrong or inconsistent after a dating-scan correction unless the doc defines a canonical gestational anchor. The design is viable, but it needs tighter contracts before code.

**Per-Use-Case Findings**

1. **Tante Rosi / Pregnancy**

The umbrella-plus-measurements shape fits: `pregnancy` as `kind`, `gestational_week` as computed, `weight_gain` as measurement, and appointments staying in `scheduled_tasks` are sensible ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:245)). `lost` and `transitioned` also fit the emotional and lifecycle needs ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:80)).

The weak point is LMP to dating-scan correction. The doc says anchor mutation is in-place ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:105)), but the example computes gestational age from `lmp_date` while separately storing `due_date` and `dating_method` ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:251)). After scan correction, does code mutate `lmp_date`, mutate only `due_date`, or switch `from_anchor`? A junior engineer could easily leave gestational week tied to stale LMP. Use a canonical `gestational_age_anchor_date` or `estimated_due_date` plus `dating_basis`, and keep original LMP as provenance.

Privacy is also under-modeled. “Never bridged” is currently an open question ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:357)), not a contract. Given existing hot context has explicit sharing-default behavior and bridge sections ([app/services/hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:737), [app/services/hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:865)), journeys need an explicit sensitivity/visibility rule.

2. **Weight-Loss Coach**

This is the strongest case. A single `weight` measurement track with baseline and target anchors is clean ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:289)). `current_state` can render “down 2.9 of 10, 29%, trending down” if recomputer fills `delta_from_baseline`, `progress_pct`, `trend_4w`, and `last_observed_at` ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:308)).

But stale status exposes the recompute bug. The doc only cron-recomputes active journeys with `computed` or `rate` tracks ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:189)). A weekly weigh-in track becomes stale merely because time passes. So every active journey with any cadenced track needs periodic recompute, not just computed/rate.

Plateau detection does not need another `metric_kind`; it is derived state. The doc should define the output shape, e.g. `plateau: {detected: true, window: "P4W", reason: "..."}`. `completed` also needs a hold rule: target hit once is not “hit and held.”

3. **Fitness Coach**

Multiple parallel tracks work naturally in JSON: frequency, bench, and 5k live under one journey ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:321)). `program_type` as anchor metadata is fine, and bulk/cut as separate chained journeys matches `supersedes_journey_id`.

The `rate` semantic is too loose. “value=1 per event” ([docs/longitudinal-state.md](/Users/user_c042661f/Documents/Veas/docs/longitudinal-state.md:132)) works, but it is awkward for gym sessions that also contain bench measurements. You will either log duplicate rows for one session or lose the ability to connect “this bench result happened during this workout.” Add either `measurement_group_id` / `event_id`, or define a lightweight `event_count` metric kind. Also specify rolling-window math: last 28 days divided by 4, calendar weeks, or normalized by program age for the first 4 weeks.

**Cross-Cutting Findings**

6. **Naming.** `user_journeys` is acceptable. `tracked_arcs` is more precise but colder. None of the three use cases feels awkward enough to justify churn.

7. **Boundary with artifacts.** The doc’s distinction at line 8 is right, but implementation needs prompt/tool guidance: numeric, target-bearing, time-series state goes to journeys; narrative interpretation goes to memories/observations/distillations. Existing tools are topic-scoped through `artifact_topics` ([app/services/tools/write_tools.py](/Users/user_c042661f/Documents/Veas/app/services/tools/write_tools.py:801)); journeys use direct `topic_id`, so the boundary must be explicit.

8. **Over-engineering.** `lost` pays rent for pregnancy. The cron tick is not over-engineered; it is under-scoped. The kind registry is justified, but “renderer per kind” plus five write tools and three read tools is already more than minimal.

9. **Under-specification.** Missing: JSON schemas per kind, timezone/date rules, measurement update/delete behavior, duplicate measurement handling, status transition invariants, scheduled-task mutation recompute, visibility/sensitivity, target range progress math, and rate-window math.

10. **Migration realism.** 600-900 lines is optimistic. The migration pattern needs RLS like `topic_status` ([migrations/0022_topic_status_user_bot_state.sql](/Users/user_c042661f/Documents/Veas/migrations/0022_topic_status_user_bot_state.sql:63)), tool schemas, registry entries, hot-context budget behavior in both renderers ([app/services/hot_context_solo.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context_solo.py:728)), tests, and scheduled recompute plumbing. I’d expect 1.2k-1.8k lines for production quality.

**Concrete Revisions**

Must fix before code:
- Define canonical pregnancy dating anchors and scan correction semantics.
- Expand recompute triggers to cadenced measurement tracks and scheduled-task changes.
- Add per-kind JSON schemas for anchors, tracks, and `current_state`.
- Make privacy/visibility a hard contract, not an open question.
- Specify `rate` math and whether session events need grouping.

Nice to clarify:
- Add plateau and completion-hold output shapes.
- Define measurement correction/update/delete tools or explicitly forbid them initially.
- Add render examples for lost pregnancy, stale weight, and mixed fitness tracks.

**Anything I’d Cut Entirely**

Cut `anchor_date` as a `metric_kind` unless you have an immediate renderer need. Due dates and appointment dates already fit anchors or `scheduled_tasks`; making them tracks blurs the model without adding much.
