**Verdict**

Revision 2 is much stronger, but not ready as a build contract. The original conceptual holes are mostly closed, especially dating, recompute, and `anchor_date`. The remaining blockers are implementation-shape problems: `visibility` is in the wrong place, gestational-week formula semantics are muddled, write-tool signatures do not match the new measurement-group contract, and privacy gating is described at prose level without the SQL/read-tool contract a senior engineer would need.

**Q1: Were Earlier Critiques Fixed?**

- **Pregnancy dating ambiguity: resolved.** The doc now makes `estimated_due_date` canonical and demotes `lmp_date` to provenance in clear terms (`docs/longitudinal-state.md:136`, `docs/longitudinal-state.md:146`, `docs/longitudinal-state.md:148`). The scan correction flow is explicit: patch EDD, set `dating_basis='scan'`, keep LMP unchanged, recompute (`docs/longitudinal-state.md:156`-`159`).

- **Recompute scope too narrow: resolved.** Recompute now runs after measurements, anchor/track updates, status changes, scheduled-task mutations, and a cron tick for every active journey (`docs/longitudinal-state.md:266`-`274`). The stale-flip test is also specified (`docs/longitudinal-state.md:280`-`282`).

- **Rate semantics loose: partially resolved.** Window numerator/denominator semantics are now precise (`docs/longitudinal-state.md:195`-`206`), and event grouping is described (`docs/longitudinal-state.md:208`-`216`). But the canonical write-tool table still declares `log_journey_measurement(journey_id, track_key, value, observed_at?, note?, source?)` with no `measurement_group_id` or `with_group` (`docs/longitudinal-state.md:309`-`311`), contradicting the grouping section and worked example (`docs/longitudinal-state.md:555`-`557`).

- **Privacy left open: partially resolved.** There is now a hard contract with explicit visibility states and redacted reads (`docs/longitudinal-state.md:327`-`340`). But locating `visibility` in `current_state.meta` is a design problem, not just an implementation detail.

- **Per-kind JSON schemas missing: partially resolved.** Anchors, tracks, statuses, and visibility defaults are now formal enough for registry validation (`docs/longitudinal-state.md:342`-`413`). Current-state shapes are still mostly examples rather than normative schemas, especially `plateau`, `completion_progress`, and fitness rate output (`docs/longitudinal-state.md:497`-`508`, `docs/longitudinal-state.md:542`-`546`).

- **Cut `anchor_date` from `metric_kind`: resolved.** The enum excludes it (`docs/longitudinal-state.md:169`-`177`), and the doc explicitly says planned dates belong in anchors or `scheduled_tasks` (`docs/longitudinal-state.md:191`).

**Q2: New Problems**

- **`visibility` should be top-level.** The doc says it lives at `current_state.meta.visibility` for queryability (`docs/longitudinal-state.md:340`), but visibility-gated reads need SQL-level filtering before rendering or joining measurements. JSONB querying is possible, but making access control depend on a recomputed cache is the wrong boundary. Add `visibility text NOT NULL CHECK (...)` to `user_journeys`, index it with active-topic reads, and optionally mirror it into `current_state.meta` for rendering.

- **Gestational-week formula is incoherent.** Generic computed tracks define `formula='weeks_until'` (`docs/longitudinal-state.md:175`-`177`), while pregnancy says `gestational_week` uses `weeks_until` “and then subtracted from 40” (`docs/longitudinal-state.md:364`). The earlier prose gives the real formula (`docs/longitudinal-state.md:156`). A junior implementer could reasonably implement either “weeks until due” or “gestational week.” Use a specific formula name like `gestational_age_from_edd`, or make `weeks_until` output a separate `weeks_until_due` track.

- **`superseded_by` is YAGNI unless v1 supports corrections.** The doc admits v1 exposes no correction tool (`docs/longitudinal-state.md:87`), yet schema, indexes, and recompute paths already account for supersession (`docs/longitudinal-state.md:68`-`74`, `docs/longitudinal-state.md:268`). Either ship `correct_measurement` now with constraints preventing cross-journey/cross-track supersession, or drop the column until needed.

- **Redacted stubs are under-specified.** The privacy section says self-only returns `{kind, status, started_at}` (`docs/longitudinal-state.md:333`-`334`), while the open question’s stub includes owner text (`docs/longitudinal-state.md:563`). It also does not define whether same-owner bot sees full state, whether raw measurements are always blocked unless `fully_shared`, or what read tools return field-by-field.

- **Scheduled-task hook looks too heavy for v1.** A nullable `journey_id` on `scheduled_tasks` plus enqueue hooks is a cross-cutting migration for one denormalized `next_milestone` cache (`docs/longitudinal-state.md:248`-`250`, `docs/longitudinal-state.md:276`-`278`). For Rosi v1, compute next milestone at render/recompute time from anchors or existing tasks, or omit it until task linkage has more than one use case.

**Q3: Over-Specification**

Cut or defer the future-bot detail from the v1 implementation contract. Fitness event grouping, `measurement_group_id`, `rolling_28d`, `calendar_month`, and the v2 `log_journey_event` mention are mostly for a future fitness bot (`docs/longitudinal-state.md:195`-`216`). Weight-loss plateau and completion-progress examples are also future-facing (`docs/longitudinal-state.md:505`-`508`). `fully_shared` is probably fine as an enum value, but its measurement-level access implications need a real read contract or it should wait. The scheduled-task-link migration and `superseded_by` are the biggest speculative additions.

**Q4: Go/No-Go**

**No-go as written, but close.** Before handing to implementation, specify these exactly:

- SQL: add `user_journeys.visibility`, `CHECK`, default, and read indexes.
- Tooling: add `update_journey_visibility(journey_id, visibility)` or include visibility in `create_journey`.
- Tooling: update `log_journey_measurement` signature to include `measurement_group_id?` / `with_group?`, or remove grouping from v1.
- Formula: replace pregnancy’s `weeks_until` special case with `gestational_age_from_edd`.
- Privacy: define exact read-tool return shapes for owner, same-topic non-owner, and fully shared reads.
- Tests: add visibility SQL/read-tool tests, not just hot-context snapshot tests.

After those edits, this is likely ready for a senior engineer.
