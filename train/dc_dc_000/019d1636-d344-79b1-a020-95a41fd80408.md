If a developer has partially staged a docs file (staged v1, working tree has v2), the hook will bundle the working-tree version. If partial staging becomes an issue in practice, the hook can be made index-aware later.

### Step 2: Create the pre-commit hook script
**File:** `.githooks/pre-commit` (new file, must be executable)

```bash
#!/usr/bin/env bash
# Auto-sync docs/*.md → desloppify/data/global/ before commit.
# Only runs the sync if any docs/*.md files are staged.

staged_docs=$(git diff --cached --name-only -- 'docs/*.md')

if [ -z "$staged_docs" ]; then
    exit 0
fi

# Sync copies from working tree into data/global.
make sync-docs

# Stage all changes in data/global — including deletions from renamed/removed docs.
git add -A desloppify/data/global/
```

Key design decisions:
- **Scoped trigger:** Only syncs when `docs/*.md` files are in the staged changeset. Commits that don't touch docs skip this entirely.
- **`git add -A` (not glob):** Stages additions, modifications, AND deletions in `data/global/`. This correctly handles `docs/` renames and deletions — `make sync-docs` deletes all `*.md` then recopies, so any file removed from `docs/` will be gone from `data/global/` and `git add -A` will stage that removal.
- **Working-tree-vs-index tradeoff (accepted):** `make sync-docs` copies from the working tree, not the index. If a developer has partially staged a docs file, the hook bundles the working-tree version. The user has explicitly accepted this tradeoff: partial staging of standalone prose files is near-zero probability, and the CI pytest guard catches any real mismatch post-push.

### Step 3: Add `make install-hooks` target and wire into setup targets
**File:** `Makefile` (edit existing)

Add `install-hooks` to the `.PHONY` list.

Add after the `sync-docs` target:

```makefile
install-hooks:
	mkdir -p .git/hooks
	cp .githooks/pre-commit .git/hooks/pre-commit
	chmod +x .git/hooks/pre-commit
	@echo "Git hooks installed."
```

Wire `install-hooks` into existing setup targets by adding it as a dependency:

```makefile
install-ci-tools: install-hooks
	$(PIP) install --upgrade pip
	$(PIP) install -e . pytest mypy ruff import-linter build twine pyyaml

install-full-tools: install-hooks
	$(PIP) install --upgrade pip
	$(PIP) install -e ".[full]" pytest ruff
```

This means any developer running `make tests`, `make ci`, or either install target automatically gets the hook installed — no separate step needed. The `install-hooks` target is idempotent (cp overwrites, chmod is a no-op if already set).

**CI note:** CI runs `install-ci-tools` which will now run `install-hooks`. This is harmless — the hook only fires during `git commit`, which CI doesn't do. The `mkdir -p .git/hooks` and `cp` are fast no-ops in terms of CI impact.

### Step 4: Keep existing pytest guard unchanged
`test_bundled_sync.py` stays as-is (now tracked per Step 1). It's the CI safety net for `--no-verify` bypasses.
