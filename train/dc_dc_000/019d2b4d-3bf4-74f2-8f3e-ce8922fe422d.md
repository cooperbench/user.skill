        # Implementation Plan: Fix Track Reordering Bugs & Add Drag-to-Reorder

## Overview

The video editor timeline has a track label sidebar where users can reorder tracks using up/down arrow buttons. Three bugs exist, plus a UX improvement request:

1. **Bug: Cross-kind boundary stall** — The up button on the first audio track (e.g., index 2 in `[V1, V2, A1]`) is *not disabled* (`trackIndex !== 0` and `sameKindCount > 1` could both be true for A1 at index 2 with 2 audio tracks), but `handleReorderTrack` silently returns because the adjacent track at `index - 1` is visual. The button appears clickable but does nothing.
2. **Bug: Audio tracks can't move up** — Same root cause. The disable condition uses `trackIndex === 0` (global index), but audio tracks are never at global index 0. The *effective* first audio track should use its position within its kind group, not the global array.
3. **Feature: Replace arrow buttons with drag handle** — Use `@dnd-kit/sortable` (already installed) to enable drag-to-reorder within each kind group.

**Key constraint:** `sortTracksByKind` in `timeline-data.ts:320` enforces visual-before-audio ordering on load. The reorder logic must maintain this invariant — tracks can only reorder within their kind group.

**Key files:**
- `src/tools/video-editor/components/TimelineEditor/TrackLabel.tsx` — UI buttons, will become drag handle
- `src/tools/video-editor/hooks/useTimelineTrackManagement.ts:286` — `handleReorderTrack` logic
- `src/tools/video-editor/components/TimelineEditor/TimelineEditor.tsx:217` — track list rendering loop
- Existing pattern: `src/tools/join-clips/components/SortableClip.tsx` — uses `useSortable` + `GripVertical`
- App-level `DndContext` already exists in `src/app/App.tsx:58`

## Phase 1: Fix Reorder Bugs (cheap validation first)

### Step 1: Fix disabled-state logic in TrackLabel (`TrackLabel.tsx`)
**Scope:** Small
1. **Fix** the up/down button disabled conditions (`TrackLabel.tsx:201,214`). Currently they use `trackIndex` (global) which doesn't account for kind grouping. Replace with kind-relative index:
   - Up disabled: track is the first of its kind (kind-relative index === 0) OR `sameKindCount <= 1`
   - Down disabled: track is the last of its kind (kind-relative index >= sameKindCount - 1) OR `sameKindCount <= 1`
2. **Approach:** Pass a new prop `kindIndex` (position within same-kind group) from TimelineEditor instead of relying on `trackIndex` for disable logic. Alternatively, compute it inline: up disabled when `trackIndex === 0 || (trackIndex > 0 && /* prev track is different kind */)` — but the cleanest fix is passing `kindIndex`.
3. **Update** TimelineEditor (`TimelineEditor.tsx:217-234`) to compute and pass `kindIndex` for each track.

### Step 2: Fix `handleReorderTrack` to skip across kind boundaries (`useTimelineTrackManagement.ts`)
**Scope:** Small
1. **Update** `handleReorderTrack` (`useTimelineTrackManagement.ts:286-308`) to find the correct swap target — the next/previous track *of the same kind* rather than just `index + direction`. When direction is -1, scan backwards for the previous same-kind track; when +1, scan forwards.
2. **Example:** In `[V1, V2, A1, A2]`, moving A1 down should swap with A2 (index 3), and A2 up should swap with A1 (index 2). Moving V2 down should NOT swap with A1 — it's already at the bottom of visual tracks.

### Step 3: Validate bug fixes manually
**Scope:** Small
1. **Test** with configurations: `[V1, A1]` (single of each — buttons should all be disabled), `[V1, V2, A1, A2]` (both kinds can reorder within group), `[V1, V2, V3, A1]` (visual reorder works, audio button disabled).
2. **Verify** the buttons enable/disable correctly AND clicking them produces the correct swap.

## Phase 2: Drag-to-Reorder

### Step 4: Add `SortableContext` wrapper to track list (`TimelineEditor.tsx`)
**Scope:** Medium
1. **Wrap** the track label list (`TimelineEditor.tsx:217-234`) with `SortableContext` from `@dnd-kit/sortable` using `verticalListSortingStrategy`.
2. **Separate** visual and audio tracks into two `SortableContext` groups so dragging is constrained within kind. Each group gets its own `SortableContext` with the IDs of tracks in that group.
3. **Add** `onDragEnd` handler that extracts `active.id` and `over.id`, computes the new track order, and calls a new `handleReorderTracks` (plural) that accepts a full reordered track array. This avoids the directional swap entirely for drag operations.
4. **Note:** The app-level `DndContext` in `App.tsx` already exists. We may need to ensure the track drag events don't conflict with clip drag events (`useClipDrag`). Use a unique `id` prefix (e.g. `track-${track.id}`) for sortable items to distinguish from clip drags. Check if the app-level `onDragEnd` needs to be aware of track drags, or if we should use a nested `DndContext` for track reordering specifically to isolate it.

### Step 5: Convert TrackLabel to sortable item (`TrackLabel.tsx`)
**Scope:** Medium
1. **Add** `useSortable` hook to TrackLabel, following the pattern in `SortableClip.tsx:86-96`.
2. **Replace** the up/down arrow buttons (`TrackLabel.tsx:196-221`) with a `GripVertical` drag handle that receives `{...attributes, ...listeners}` from `useSortable`.
3. **Apply** `transform` and `transition` styles from `useSortable` to the root element.
4. **Remove** the `onReorder` prop and related `ArrowUp`/`ArrowDown` imports since drag replaces directional buttons.
5. **Keep** the drag handle in the hover overlay area where the arrows currently live, maintaining the existing show-on-hover UX pattern.

### Step 6: Add `handleMoveTrack` for drag-end reordering (`useTimelineTrackManagement.ts`)
**Scope:** Small
1. **Add** a new `handleMoveTrack(activeId: string, overId: string)` callback that:
   - Finds both tracks in `resolvedConfig.tracks`
   - Validates they're the same kind (should always be true given SortableContext grouping)
   - Uses `arrayMove` from `@dnd-kit/sortable` to reorder
   - Calls `applyResolvedConfigEdit` with the new track array
2. **Export** this from the hook and wire it into the drag-end handler in TimelineEditor.
3. **Remove** the old `handleReorderTrack` (directional swap) if no longer used.

### Step 7: Handle DndContext nesting / event isolation
**Scope:** Small
1. **Decide** between using the app-level `DndContext` or a nested one. Since the app-level `DndContext` handles shot/clip DnD with `closestCenter` and overlay, a **nested `DndContext`** scoped to the track list is safer — it prevents track drags from triggering clip DnD handlers and vice versa.
2. **Wrap** the track label container in its own `DndContext` with `closestCenter` collision detection and `PointerSensor` (with activation constraint of ~5px distance to avoid accidental drags on click).

### Step 8: Visual polish and final validation
**Scope:** Small
1. **Add** subtle drag feedback — `isDragging` opacity reduction (same as `SortableClip.tsx:101`).
2. **Ensure** the track list scroll container (`TimelineEditor.tsx:211-215`) still syncs scroll position with the timeline canvas during and after drag.
3. **Test** edge cases: single track of a kind (no drag target), dragging first visual track, dragging last audio track, many tracks with scroll.
