# Background

We just landed a 3-line quick fix on branch `megaplan/m1b-m1c-stores` that removes redundant double-writes from `src/tools/video-editor/hooks/useTimelineSelection.ts`. The wrapper was calling both the store action AND a `setSelectedClipId` pass-through that routed to `setTimelineSelectedClipId` → `selectTimelineClip(id, undefined)`, which silently reset multi-select to single-select. Marquee + cmd+click multi-select are now functional.

The bug is fixed but the underlying smell that produced it is intact: the selection store has three overlapping entry points with subtly-different semantics, one of which (`setTimelineSelectedClipId`) masquerades as a `useState` setter while actually clobbering the whole selection. The wrapper layer (`useTimelineSelection`) still has the pre-refactor "split state" shape (multi-select set + useState-style primary id) even though M1b/M1c collapsed those into a single Zustand store.

# Goal

Eliminate the structural trap permanently so this class of bug cannot reappear, even if a future refactor wires the surfaces back together. This megaplan plans the cleanup ONLY — the bug fix is already applied. The cleanup should ship in the same PR as the quick fix but as a separate commit so the fix is revertable independently.

# Specific objectives

1. **Disambiguate the three entry points** in `src/shared/state/selectionStore.ts`:
   - `selectTimelineClips(set, syncOptions)` — replaces multi-selection
   - `selectTimelineClip(id, opts, syncOptions)` — single or toggle
   - `setTimelineSelectedClipId(updater, options)` — masquerades as primary-id setter, actually resets selection. **THIS IS THE TRAP.**

   Either rename `setTimelineSelectedClipId` so it stops looking like a `useState` setter, or split it into `setPrimaryClipId` (pure primary update, no reset) + `selectSingleClip` (replaces selection with one). Pick whichever leaves the cleanest contract for callers.

2. **Decide the fate of `useTimelineSelection`**. Post-M1b/M1c, the wrapper is a thin layer over the store but still presents `Dispatch<SetStateAction<string | null>>` semantics. Options:
   - Kill it; have callers use the store hooks directly.
   - Thin it to JUST derivations (`selectedClip`, `selectedTrack`, `selectedClipHasPredecessor`, `resolvedConfig` from `useDerivedTimeline`) and drop all selection-mutation methods.

3. **Update `useTimelineCommit.ts:117`**. This is where `setSelectedClipId` is created with the deceptive setState-style signature. It needs to either disappear (callers go direct) or be renamed to match the new contract.

4. **Document semantics inline** so the next refactor doesn't reintroduce the trap. JSDoc on each store action stating exactly what it resets and what it preserves.
