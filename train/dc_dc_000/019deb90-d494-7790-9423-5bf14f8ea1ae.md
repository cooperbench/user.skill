## Design constraints (non-negotiable)

1. **Reigh compatibility** — `clip.kind` is NEVER persisted. Reigh's clip allowlist (`reigh-app/src/tools/video-editor/lib/serialize.ts:8-42`) is closed and throws on unknown clip keys. All kind-based dispatch is runtime-only on the ArtAgents side. The Phase 2 `classified_kind` is a `TimelineClipView` property, not a JSON field.
2. **Backwards-compat user-facing CLI** — `python3 -m artagents --video X.mp4 --brief brief.txt`, `--audio X.wav --brief brief.txt`, and `--brief brief.txt --target-duration 28` (pure-generative) all keep working. They become hints that influence which clips get added to the timeline; behind the scenes they all converge on one path.
3. **Step capability discovery is manifest-driven** — each `executor.yaml` declares `produces_for: [VIDEO, AUDIO, ...]` (or equivalent shape — name is a design call). The pipeline computes the union of needed steps over all timeline clips, then runs only those. No hardcoded STEP_ORDER as the source of truth (it can remain as a topological-order hint).
4. **Topological order preserved** — current pipeline ordering (`transcribe → scenes → quality_zones → shots → triage → scene_describe → quote_scout → pool_build → pool_merge → arrange → cut → refine → render → editor_review → validate`) has real dependencies; manifest-driven discovery must produce the same order when the same step set is needed.
5. **Schema package unchanged** — clip kinds are runtime-derived. No `@banodoco/timeline-schema` changes.

        # Implementation Plan: Phase 3 Mixed-Mode Hype Pipeline

## Overview
ArtAgents currently keeps the hype workflow in `artagents/pipeline.py`, which is both the package command router and the 15-step hype orchestrator. The current pipeline split is not only file organization: `build_steps()` filters steps from hardcoded `STEP_ORDER` based on `args.video` and `args.audio`, and arrange/cut/refine still use `is_all_generative_arrangement()` as a mode boundary.

The critique points to the real root cause: mixed-mode cannot be discovered from the final timeline before arrange has run. The revised approach avoids that circular dependency by treating CLI inputs and brief context as pre-arrange capability intent. A source-video run with a brief is allowed to use generated visual candidates by default, so mixed-mode is unlocked without adding a new required CLI flag. Source/audio inputs still select source-analysis steps; generative candidates select image/effect-capable arrange/cut/render steps. No runtime kind is persisted to Reigh JSON.

Dry-run is now a mandatory part of the plan. Top-level hype `--dry-run` will parse, prepare run directories and the copied brief, compute the selected step plan, and emit the commands/artifact paths without launching child executors. It is the smoke path for source-video, audio-only, and pure-generative invocations.

`GENERATIVE_IMAGE` will be represented as runtime `ClipClassifiedKind.IMAGE` plus pool/asset provenance showing the clip came from a generative pool entry. This matches Phase 2 and avoids schema package changes or a persisted `clip.kind` field.

**Scope:** Medium

3. Sort selected steps by `metadata.pipeline_step_order`; use the old `STEP_ORDER` only as a compatibility/topological fallback, not the source of truth for inclusion.
4. Apply manifest conditions and available runtime inputs before selecting transcript-dependent stages. 5. Define `--from` semantics against the computed selected set: skip selected steps before `X`; if `X` is known globally but absent from this computed run, error with a message naming the active selected steps.
6. Keep `--skip` validation against known pipeline step names, then remove skipped steps after dynamic selection.

It points to missing glue in the proposed manifest-driven selector: clip-kind capability (`produces_for`) cannot also mean runtime artifacts exist. The revised approach separates those concerns with two manifest-level concepts: `produces_for` for clip capability relevance and `pipeline_requirements` for required runtime facts such as `source_video`, `source_audio`, `transcript`, and `render_requested`. The selector becomes manifest-driven without guessing from optional inputs that are currently marked optional for executor dry-runs.

Mixed-mode also needs a compatibility decision. Phase 3 will intentionally make generative visual candidates available by default for source-video briefs so a single source brief can produce mixed timelines. To preserve source-cut behavior for callers that need it, add a top-level opt-out `--no-generative-effects`. Existing source-only tests should be rewritten to use that opt-out, while new tests assert the new default mixed-mode path.

Dry-run remains mandatory. Top-level hype `--dry-run` will parse, prepare lightweight run metadata and the copied brief, compute the selected step plan, write `<out>/hype.plan.json`, and never call `run_step()` or launch child executors. Tests must patch the moved orchestration owner’s `run_step` and assert it is not called.

`GENERATIVE_IMAGE` will be represented as runtime `ClipClassifiedKind.IMAGE` plus pool/asset provenance showing the clip came from a generative pool entry. This matches Phase 2 and avoids schema package changes or a persisted `clip.kind` field.
