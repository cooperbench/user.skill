## Concrete items to fix

### 1. `[PanesBoot]` render loop in `src/shared/state/panesStore.ts`

**Symptom:** Runtime console shows `[PanesBoot] PanesStoreBootstrapBoundary render` → `useBootstrapPanesStore render` → `effect fires (bootstrapInput changed identity)` → `bootstrap APPLY set()` → repeat. Endless loop visible in `localhost-1777161431011.log` at the project root.

**Cause:** `useBootstrapPanesStore` has a `useEffect` keyed on `bootstrapInput`. The `bootstrapInput` reference changes identity on every render (likely an inline object literal or a useMemo with unstable deps), so the effect fires constantly, triggering `bootstrapPanesStore(...)` → `set()` → re-render → new identity → repeat.

**Fix:** Stabilize the `bootstrapInput` reference. Either memoize it correctly with primitive deps, or compare by value inside the effect before calling `set()`. After fixing the loop, **remove the debug `console.log` lines** at panesStore.ts:406, 522, 528, 541 (they were diagnostic instrumentation; loop is gone, logs aren't needed).

### 2. Z-index consolidation between TasksPane and GenerationsPane

**Symptom:** TasksPane content is `z-100001` (inline literal in `src/features/tasks/components/TasksPane/TasksPane.tsx`). GenerationsPane is `z-100013` (from `UI_Z_LAYERS` in `src/shared/lib/uiLayers.ts`). When GenerationsPane is open/locked, it covers the bottom of TasksPane, making content there visible-but-unreachable. Just patched superficially by shortening TasksPane's `bottom` when GenerationsPane is open — but the underlying inconsistency remains.

**Fix:**
- Add a `TASKS_PANE_CONTENT` entry to `UI_Z_LAYERS` placed appropriately relative to `GENERATIONS_PANE`, `LIGHTBOX_MODAL`, and `TASKS_PANE_TAB_*`. Document the chosen value with a one-line comment explaining the ordering.
- Replace the inline `zIndex: 100001` in `TasksPane.tsx` with the new `UI_Z_LAYERS` constant.
- Verify the layering still works: TasksPane content above MediaLightbox (per the existing code comment), TasksPane content's stacking with respect to GenerationsPane should match the UX intent (probably TasksPane content above GenerationsPane, so the bottom-strip workaround in TasksPane's `bottom: ...` style can be removed too).

### 3. `AgentChatContext` bridge default = noop violates CLAUDE.md

**Symptom:** `useAgentChatBridge()` returns a default value with `replaceSelectedTimelineClips: noopReplace` when no `VideoEditorProvider` is mounted. This silently swallows attachment-removal attempts when AgentChatPanel renders on routes where the video editor isn't mounted. CLAUDE.md explicitly forbids this pattern: "Required-provider hooks must throw when their context is missing. Do not hide missing providers behind default objects with no-op setters."

**Fix:** This is nuanced because the bridge has a real use case: AgentChatPanel renders globally on all tool routes (`/tools`, `/shots`, `/art`), but `VideoEditorProvider` only mounts on `/tools/video-editor`. So the bridge legitimately HAS no real value on other routes.

Two acceptable resolutions — pick whichever is least intrusive:
- (a) Split `useAgentChatBridge` into two: `useAgentChatBridgeRequired` (throws) and `useAgentChatBridgeOptional` (returns null). Update AgentChatPanel callsites to use the optional variant and gate behavior on whether the bridge is available (e.g., disable attachment X clicks when bridge is null).
- (b) Replace the noop with a real failure mode: e.g., warn in dev when removal is called but no provider is registered, AND still update local UI state so the chip disappears (managing attachment state inside AgentChatPanel as a fallback when no bridge override is registered).

Choose the resolution that requires the fewest callsite changes while satisfying CLAUDE.md's spirit (no silent failures).

### 4. `panesStore` subscription consolidation in TasksPane

**Symptom:** TasksPane currently does ~10 individual `usePanesStore((state) => state.X)` calls. Each one is a separate subscription that triggers an independent re-render. Render budget shows TasksPane at 6/5 (over budget) in the log. My recent edit added 3 more subscriptions (`isGenerationsPaneLocked`, `isGenerationsPaneOpen`, `effectiveGenerationsPaneHeight`) which compound the issue.

**Fix:** Consolidate the panesStore reads in TasksPane into a single `usePanesStore` call that returns a tuple/object via shallow equality (`zustand/shallow`). One subscription, one re-render per actual state change. Pattern reference: see how the OLD AgentChat.tsx used `usePanesStore((state) => ({ ... }), shallow)` — the same pattern can apply here.

### 5. TimelineSync silent rejection logging in `src/shared/hooks/usePollSync.ts:166`

**Symptom:** Log shows `[TimelineSync] poll rejected Object` 15+ times with NO error context. The rejected reason is logged as `Object` (something like `console.warn('...', err)` where err's toString returns `[object Object]`).

**Fix:** Update the log call at usePollSync.ts:166 to print the actual error properties: status code, message, stack if dev. Use `console.error('[TimelineSync] poll rejected', { error: err?.message, status: err?.status, ...err })` or similar. Don't change the polling behavior; only improve diagnosability.

This will help diagnose why generations aren't showing in the UI on the user's current dev session — but the actual fix for "generations not showing" is OUT OF SCOPE for this run (different surface area). We just want better logging here.
