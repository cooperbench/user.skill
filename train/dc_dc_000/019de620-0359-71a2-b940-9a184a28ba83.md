        # Implementation Plan: Discord Typing/WPM Pacing Throttler

## Overview
The plan is still targeting the right root cause: Discord outbound text already passes through centralized pacing hooks, but the final provider send can still happen too quickly because composition duration is not consistently length-based across final and incremental bubbles. No gate flags indicated the wrong code path or a need for a new architecture.

Veas already has the right insertion points: Discord-specific pacing lives in `app/services/pacer.py`, final sends route through `app/services/agentic.py` into `app/services/messaging.py`, incremental bubbles route through `app/services/tools/read_tools.py` into `send_outbound_part`, and live Discord wiring supplies `before_paced_send` from `app/main.py`. The implementation should strengthen deterministic timing in `DiscordPacer`, keep newer-inbound checks at the existing pre-provider-send boundary, and avoid prompt or conversation-policy changes.

## Main Phase

### Step 1: Confirm Existing Hook Boundaries (`app/main.py`, `app/services/agentic.py`, `app/services/tools/read_tools.py`, `app/services/messaging.py`)
**Scope:** Small
1. **Confirm** live Discord turns install `before_paced_send` in `app/main.py:67` and call `DiscordPacer.perform_send_typing` before provider send at `app/main.py:78`.
2. **Preserve** final-send newer-inbound checks before paced send and after paced wait in `app/services/agentic.py:702` and `app/services/agentic.py:711`.
3. **Preserve** incremental newer-inbound checks before paced send and after paced wait in `app/services/tools/read_tools.py:116` and `app/services/tools/read_tools.py:143`.
4. **Leave** `app/services/messaging.py` provider-agnostic except for existing provider dispatch and `before_provider_send` invocation; non-Discord providers should not gain pacing sleeps.

### Step 2: Add Minimal Composition Settings (`app/config.py`, `app/models/user.py`)
**Scope:** Small
1. **Add** one app-level jitter setting near `app/config.py:65`, for example `discord_pacing_answer_typing_jitter_ratio`, with a conservative default and bounds.
2. **Keep** existing app/user settings for chars/sec, min, max, visible pulse duration, off-gap duration, and pulse-gap caps as the main control surface.
3. **Do not add** per-user jitter preferences unless implementation reveals an existing preference pattern that makes it trivial; app-level jitter is enough for this bakeoff.
4. **Update** `tests/test_config.py` for the new setting. Avoid storage/preference test churn unless `app/models/user.py` actually changes.

### Step 3: Centralize Composition Duration (`app/services/pacer.py`)
**Scope:** Medium
1. **Extend** `answer_typing_delay_s` at `app/services/pacer.py:294` or replace it with a helper that computes composition duration from `answer_chars_per_s`, `answer_typing_min_s`, `answer_typing_max_s`, and jitter.
2. **Inject** randomness through `DiscordPacer.__init__`, such as a `random_uniform` callable, so tests can force exact jitter values without patching global `random`.
3. **Apply** the helper to final sends, incremental first bubbles, and incremental next bubbles. Incremental next should still honor `discord_multi_message_delay_s` and `discord_pacing_incremental_typing_pulse_min_gap_s`, but should not use only a fixed short pulse for longer content.
4. **Record** useful timing context in pacing event snapshots, such as `composition_s`, `send_kind`, and `part_index`, without changing the database schema.

### Step 4: Reuse One Pulse Runner for Final and Incremental Sends (`app/services/pacer.py`)
**Scope:** Medium
1. **Refactor** `_perform_answer_typing_after_user_wait` at `app/services/pacer.py:407` into a reusable composition pulse runner.
2. **Emit** a typing pulse quickly once paced send begins, then wait for the computed composition duration before allowing provider send.
3. **For long messages**, cycle through visible typing, `typing_stop` event, short off-gap, and restart typing while respecting `discord_pacing_typing_visible_s` and `discord_pacing_typing_pulse_min_gap_s`.
4. **Treat** `answer_typing_max_s` as the hard composition-duration cap before off-gap embellishment; if off-gaps are included in wall-clock wait, keep them bounded and covered by tests so a capped message does not grow unexpectedly.

### Step 5: Keep Stale-Turn Interruptions Enforced (`app/services/agentic.py`, `app/services/tools/read_tools.py`)
**Scope:** Small
1. **Keep** final sends using `before_provider_send` so any paced wait happens before inserting/sending the outbound provider message.
2. **Keep** incremental sends using `before_provider_send` so `send_message_part` can return `interrupted` if a new inbound appears after paced wait.
3. **Add tests** where fake pacer sleep inserts a newer inbound during the wait and assert no Discord provider send is made.

### Step 6: Add Focused Tests (`tests/test_pacer.py`, `tests/test_agentic_lifecycle.py`, `tests/test_send_outbound.py`)
**Scope:** Medium
1. **Add pacer unit tests** for composition duration: short content clamps to min, long content clamps to max, chars/sec affects duration, and jitter is deterministic under injected randomness.
2. **Extend long-message pulse tests** in `tests/test_pacer.py` to assert multiple `typing_start` events, `typing_stop` gaps, and expected waited time.
3. **Update incremental pacing tests** around `test_incremental_followup_typing_uses_short_gap` to prove follow-up bubbles use length-based composition and still preserve the configured inter-bubble rhythm.
4. **Add interruption coverage** for final and incremental paths, using fake clocks/sleeps and fake provider sends rather than real Discord.

### Step 7: Validate the Change
**Scope:** Small
1. **Run** `pytest tests/test_pacer.py` first.
2. **Run** targeted lifecycle/provider tests touched by interruption coverage: `pytest tests/test_agentic_lifecycle.py tests/test_send_outbound.py`.
3. **Run** config tests if settings changed: `pytest tests/test_config.py`.
4. **Run** the full suite with `pytest` after targeted tests pass.
