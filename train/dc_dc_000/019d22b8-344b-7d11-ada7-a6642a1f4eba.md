## Step 2: Fix bottom pane handle position when editor pane is active
**Scope:** Medium

**Root cause:** The `BottomPaneStrategy` (`BottomPaneStrategy.ts:12-14`) positions the control tab at `bottom: 0px` and uses `translateY(-dimension)` when visible. But it ignores the editor pane entirely. The *control tab*'s position is correct for the generations pane alone—the problem is that `GenerationsPaneSurface` caps its height when editor is visible (`GenerationsPane.tsx:95-98`), using `effectiveHeight = Math.min(generationsPaneHeight, window.innerHeight - editorPaneHeight)`. However, the `PaneControlTab` at line 52 still passes the *uncapped* `generationsPaneHeight` as `paneDimension`.

**Fix:**
1. **In `GenerationsPane.tsx`**, compute `effectiveHeight` at the `GenerationsPaneTab` level too (or lift it into the controller), and pass it as `paneDimension` instead of `pane.generationsPaneHeight`.
   - `GenerationsPaneTab` (line 52): Change `paneDimension: pane.generationsPaneHeight` → `paneDimension: effectiveGenerationsHeight` where `effectiveGenerationsHeight` accounts for the editor pane.
   - This requires the tab component to access `isEditorPaneLocked/isEditorPaneOpen/editorPaneHeight` from `usePanes()`, same as `GenerationsPaneSurface` already does at line 93.

2. **Verify** the `BottomPaneStrategy` transform: `translateY(-effectiveHeight)` should now place the handle at the top edge of the actual pane surface.

## Step 3: Fix scroll within bottom pane when both top and bottom panes are locked
**Scope:** Medium

**Root cause:** Two potential issues:
- (a) The `GenerationsPaneSurface` inner content div (`GenerationsPane.tsx:116-119`) has `pointer-events-none` when `isPointerEventsEnabled` is false during animation. If the generation pane re-animates when editor locks, this could temporarily block interaction. Verify with a console log.
- (b) The `effectiveHeight` calculation (`GenerationsPane.tsx:95-98`) uses `window.innerHeight - editorPaneHeight` — if this is too small, the scrollable content area collapses and nothing is scrollable. Check if the inner flex container with `h-full` and `overflow-y-auto` has non-zero height.
- (c) The editor pane surface (`EditorPaneTab.tsx:83-98`) sits at `z-index: 59` while GenerationsPane is at `z-index: 100`. The editor shouldn't overlap the generations pane. But the `PaneControlTab` for the editor uses `z-[101]`/`z-[102]` which *could* create a stacking context that captures pointer events at the top of the viewport.

**Fix:**
1. **Ensure `effectiveHeight` correctly accounts for the editor pane** (tied to Step 2 fix).
2. **Add `overflow-y-auto` or `overflow-hidden`** to the outer generations pane div if not already present—it currently only has it on the inner gallery container.
3. **Test scrolling** after the height fix from Step 2 is applied—the scroll issue may resolve itself once the pane dimensions are correct.

## Step 4: Fix tasks pane unlock / "duplicate pane" feel when editor is active
**Scope:** Medium

**Root cause analysis:** The lock setter in `usePaneLockPolicyState.ts:59-86` has two issues:

1. **Persistence saves only a delta** (`usePaneLockPolicyState.ts:77`): When unlocking tasks, `savePaneLocks({ tasks: false })` is called. The `useUserUIState.update()` function at `useUserUIState.ts:432-468` does `mergeSettingRecords(currentValue, patch)` which *shallow-merges* the patch into the current DB value. This should work correctly for the merge itself.

2. **The real issue—`onToggleLock` closure is stale in `useTasksPaneSlidingPane.ts:21-23`:**
   ```ts
   onToggleLock: () => {
     setIsTasksPaneLocked(!isTasksPaneLocked);
   }
   ```
   This captures `isTasksPaneLocked` from the render closure. If the value doesn't update between clicks (e.g., due to debounced persistence), `!isTasksPaneLocked` toggles to the *same* value. The `createPaneLockSetter` at line 65 has `if (prev[lockKey] === isLocked) return prev;` which no-ops.

3. **Tablet exclusive lock conflict** (`usePaneLockPolicyState.ts:41-50`): The tablet normalization at load time doesn't include `editor` in its `newLocks` object (line 46-49 creates `{ shots, tasks, gens }` without `editor`). If the user is on tablet, loading saved locks with both editor and tasks locked would produce `{ shots: false, tasks: true, gens: false }` — missing the `editor` key entirely, which could corrupt state.

**Fix:**
1. **In `useTasksPaneSlidingPane.ts`**, change from toggle to explicit set:
   ```ts
   onToggleLock: () => setIsTasksPaneLocked(!isTasksPaneLocked),
   ```
   The `toggleLock` in `useSlidingPane.ts:213-230` already supports `force` parameter and calls `onToggleLock()` only when the state needs to change. But the issue is that `onToggleLock` itself uses a potentially stale closure value. Better: pass the *desired* lock state directly instead of toggling:
   - Option A: Change `useSlidingPane`'s `onToggleLock` to `onSetLock: (locked: boolean) => void` so it can pass the desired state.
   - Option B (simpler): Keep the toggle pattern but ensure `useTasksPaneSlidingPane` uses a ref or functional callback.

2. **Fix tablet `newLocks` object** in `usePaneLockPolicyState.ts:46-49`: Add `editor` key to the normalization object.

3. **Verify** the `programmaticOpen` state isn't keeping TasksPane visually open after unlock. In `useTasksPaneSlidingPane.ts:25-28`, when `onOpenChange(false)` fires, it sets `isTasksPaneOpenProgrammatic` to false. But check if `isTasksPaneOpenState` in `usePaneLockPolicyState.ts:31` is also cleared when tasks unlock—line 81-83 only sets it true on lock, never false on unlock.

## Step 5: Fix the `isTasksPaneOpenState` not clearing on unlock
**Scope:** Small

**Root cause:** In `usePaneLockPolicyState.ts:81-83`:
```ts
if (lockKey === 'tasks' && isLocked) {
  setIsTasksPaneOpenState(true);
}
```
When tasks are *locked*, `isTasksPaneOpenState` is set true. But when *unlocked*, it's never set false. This means `isTasksPaneOpen` stays true in PanesContext, feeding `programmaticOpen: isTasksPaneOpenProgrammatic` into `useTasksPaneSlidingPane`, which feeds into `useSlidingPane`. The pane stays open because `isOpen = isLocked || programmaticOpen || hoverOpen` — `programmaticOpen` is still true.

However, the `onOpenChange` callback in `useTasksPaneSlidingPane.ts:25-28` should handle this:
```ts
onOpenChange: (open) => {
  if (!open && isTasksPaneOpenProgrammatic) {
    setIsTasksPaneOpenProgrammatic(false);
  }
}
```

The `useSlidingPane.ts:41-47` fires `onOpenChange` when `isOpen` changes. But if `isLocked` goes false and `programmaticOpen` is still true, `isOpen` stays true (line 21), so `onOpenChange(false)` never fires. This is the **"duplicate pane" feeling**—the pane appears unlocked but stays open.

**Fix:** In `usePaneLockPolicyState.ts`, clear `isTasksPaneOpenState` when tasks are unlocked:
```ts
if (lockKey === 'tasks') {
  setIsTasksPaneOpenState(isLocked);
}
```

## Step 1: Centralize editor-aware generations height in `PanesContext.tsx`
**Scope:** Medium

**Problem:** The editor-aware `effectiveHeight` is computed ad-hoc in `GenerationsPaneSurface` (`src/features/gallery/components/GenerationsPane/GenerationsPane.tsx:95-98`), but three other consumers still use the raw `generationsPaneHeight`:

**Fix:**

   ```ts
   const editorVisible = locks.editor || isEditorPaneOpenState;
   ```

3. **Update `src/shared/hooks/layout/useBottomOffset.ts:17`**: Replace `generationsPaneHeight` with `effectiveGenerationsPaneHeight`.

**Problem:** When the editor pane reduces the generations pane's available height, the flex scroll chain breaks.    className={cn(

## Step 3: Fix tasks pane unlock stuck-open state (`usePaneLockPolicyState.ts`)
**Scope:** Small

**Problem:** In `src/shared/contexts/usePaneLockPolicyState.ts:81-83`, `isTasksPaneOpenState` is set `true` when tasks lock but never cleared on unlock:

```ts
if (lockKey === 'tasks' && isLocked) {
```

**Fix:**
1. **In `src/shared/contexts/usePaneLockPolicyState.ts:81-83`**, change:
   ```ts
   if (lockKey === 'tasks' && isLocked) {
     setIsTasksPaneOpenState(true);
   }
   ```
   to:
   ```ts
   if (lockKey === 'tasks') {
     setIsTasksPaneOpenState(isLocked);
   }
   ```
   This clears `isTasksPaneOpenState` on unlock, allowing the pane to close.

2. **Fix tablet lock normalization** in `src/shared/contexts/usePaneLockPolicyState.ts:44-50`: The `newLocks` object is missing the `editor` key. Change:

   ```ts
   newLocks = {
     shots: firstLocked === 'shots',
   ```

   ```ts
   newLocks = {
   ```
