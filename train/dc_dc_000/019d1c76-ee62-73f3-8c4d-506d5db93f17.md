        # Implementation Plan: GPU Worker Model-Affinity Task Scheduling with Warm Preference Period

## Overview

The system has **passive model affinity** infrastructure already built but **non-functional** due to a payload key mismatch. The goal is to fix this, activate warm-preference claiming, and add SQL-level starvation protection.

### What exists
- **SQL RPC** `claim_next_task_service_role` (4-arg overload, migration `20260121000000:75-206`): Accepts `p_same_model_only`. When true, filters to tasks matching `workers.current_model`. Has model-affinity ordering (matching model = priority 0, others = priority 1, then `created_at ASC`).
- **Edge function** `claim-next-task` (`reigh-app/supabase/functions/claim-next-task/index.ts:57,82-88`): Parses `same_model_only` from request body, passes it as `p_same_model_only` to the 4-arg RPC.
- **Worker model registration** edge function `update-worker-model` (`index.ts:76`): Expects `current_model` in request body.
- **Model preloading**: Orchestrator passes `--preload-model` to workers when no tasks pending (`startup_script.py:42`). Worker loads model at `queue_lifecycle.py:71-72`, setting `queue.current_model`.
- **3-arg overload** (migration `20260121170000`): Simpler claim function without `p_same_model_only`. The edge function never calls this one.
- **Overload trap prior art**: Migration `20260212000000` documents the pattern — `CREATE OR REPLACE` with a different signature creates a new overload rather than replacing. Must explicitly `DROP FUNCTION` the old signature first.

### What's broken
- **Critical bug**: `generation_helpers.py:62` sends `"model": new_model` but edge function reads `"current_model"` — so `workers.current_model` is always NULL, making all affinity logic a no-op.

### What's needed
1. Fix the model registration payload (1-line bug fix).
2. Worker sends `same_model_only=true` on every claim call.
3. SQL function adds `p_max_task_wait_minutes` parameter with starvation protection: when any eligible queued task is older than this threshold, **both** the WHERE filter and the ORDER BY switch to pure FIFO, ignoring model preference entirely. This implements the user's rule: "ignore same_model_only and claim the oldest task regardless."
4. Migration must DROP the old 4-arg signature before creating the 5-arg version (per repo overload-trap pattern in `20260212000000`).
5. Pass `max_task_wait_minutes` through edge function and worker for flexibility.
6. Wire config through orchestrator startup script.

### Design per user notes
Starvation protection lives in the SQL function via a `p_max_task_wait_minutes` parameter. When `p_same_model_only=true` but **any** eligible queued task has been waiting longer than this threshold, the function ignores both the model filter AND the model-preference ordering — it claims the oldest task regardless. One parameter, one place.

## Step 2: SQL migration — add `p_max_task_wait_minutes` with starvation bypass (`reigh-app`)
**Scope:** Medium — 1 new migration file

1. **Create migration** `reigh-app/supabase/migrations/YYYYMMDDHHMMSS_add_max_task_wait_to_claim.sql`.

2. **Explicitly DROP the old 4-arg signature** before creating the 5-arg version. This follows the repo pattern from `20260212000000_drop_old_claim_next_task_user_pat_overload.sql:13` which documents the overload trap:
   ```sql
   -- Drop the old 4-parameter overload to avoid PostgREST ambiguity.
   -- CREATE OR REPLACE with a different signature creates a new overload,
   -- not a replacement. See 20260212000000 for prior art.
   DROP FUNCTION IF EXISTS public.claim_next_task_service_role(TEXT, BOOLEAN, TEXT, BOOLEAN);
   ```

3. **Create the 5-arg function** with the new `p_max_task_wait_minutes` parameter:
   ```sql
   CREATE OR REPLACE FUNCTION claim_next_task_service_role(
     p_worker_id TEXT,
     p_include_active BOOLEAN DEFAULT FALSE,
     p_run_type TEXT DEFAULT NULL,
     p_same_model_only BOOLEAN DEFAULT FALSE,
     p_max_task_wait_minutes INT DEFAULT 5
   )
   ```

4. **Add a variable** to detect whether any starving task exists:
   ```sql
   DECLARE
     -- ... existing declares ...
     v_has_starving_task BOOLEAN := FALSE;
   ```
   After the `eligible_users` CTE but before the `ready_tasks` CTE, check if any eligible queued task exceeds the threshold:
   ```sql
   -- Check for starving tasks (any eligible task older than threshold)
   IF p_same_model_only AND v_worker_model IS NOT NULL THEN
     SELECT EXISTS(
       SELECT 1
       FROM tasks t
       JOIN projects p ON t.project_id = p.id
       WHERE t.status = 'Queued'::task_status
         AND all_dependencies_complete(t.dependant_on)
         AND EXISTS (SELECT 1 FROM eligible_users eu WHERE eu.user_id = p.user_id)
         AND (p_run_type IS NULL OR get_task_run_type(t.task_type) = p_run_type)
         AND t.created_at < (NOW() - (p_max_task_wait_minutes || ' minutes')::interval)
     ) INTO v_has_starving_task;
   END IF;
   ```

   **Implementation note:** This requires restructuring from a single CTE chain to a two-phase approach: first compute `eligible_users` in a CTE, then run the starvation check, then compute `ready_tasks`. The cleanest way is to use a temporary table or PL/pgSQL variable for `eligible_users`, or simply inline the starvation check as a subquery. The preferred approach: keep the single-CTE structure but make both the WHERE filter and ORDER BY conditional on `v_has_starving_task`. Since we need to compute `v_has_starving_task` before the CTE runs, we'll split into two steps:
   - First: compute `eligible_users` as a CTE and check for starving tasks.
   - Then: use the result in the main claim query.

5. **Modify the `ready_tasks` CTE** — both WHERE and ORDER BY are conditional on `v_has_starving_task`:

   **WHERE clause** (replaces lines 159-163):
   ```sql
   AND (
     NOT p_same_model_only
     OR v_worker_model IS NULL
     OR v_has_starving_task                          -- bypass model filter entirely
     OR get_task_model(t.params) = v_worker_model
   )
   ```

   **ORDER BY** (replaces lines 137-145):
   ```sql
   ROW_NUMBER() OVER (
     ORDER BY
       CASE
         WHEN v_has_starving_task THEN NULL           -- no model preference
         WHEN v_worker_model IS NOT NULL
              AND get_task_model(t.params) = v_worker_model
         THEN 0
         ELSE 1
       END NULLS LAST,
       t.created_at ASC
   ) as rn
   ```
   When `v_has_starving_task` is true, the CASE returns NULL for all rows. `NULLS LAST` puts them all in the same tier, so the tiebreaker `t.created_at ASC` determines order — pure FIFO, oldest first. This guarantees the starving task (the oldest one) is claimed.

6. **Copy the rest of the function body verbatim** from `20260121000000:75-206`: `eligible_users` CTE, `all_dependencies_complete()`, `get_task_run_type()`, atomic UPDATE with `generation_started_at`, RETURNING clause.
