## Overview

The megaplan harness has runtime policy data (expected durations, polling intervals) for every phase, but this information is only surfaced when a user explicitly polls `status`. The goal is to: (1) announce expected duration at phase start, (2) compute phase-aware progress in status responses, (3) avoid misleading "no progress" for completion-only phases, and (4) fold `watch` into `status` since it adds no capability beyond merging the progress payload.

**Current state:** `build_monitor_hint` (execution.py:70-71) returns a static string pointing to `megaplan watch`. Every handler injects this via `_record_step_and_respond` (handlers.py:253). `handle_watch` (cli.py:329-340) is just `_build_status_payload + _build_progress_payload` merged. Non-execute phases are `completion_only` — they produce zero intermediate artifacts.

**Key constraint:** The JSON response contract is additive-safe but removal-breaking. `watch` must remain as an alias. Progress signals for non-execute phases can only be time-elapsed-vs-expected, not artifact-based.

## Phase 1: Duration Hints and Monitor Hint Update

### Step 1: Add `format_duration_hint` helper (`megaplan/_core/phase_runtime.py`)
**Scope:** Small

   - Convert seconds to human units (e.g., `"30s–15m"`, `"5–120m"`).
   - For execute (where `expected_max_seconds` is None/unbounded), use phrasing like `"Expected duration: at least 5 minutes (depends on task count)."`.

## Phase 2: Phase-Aware Progress in Status

### Step 4: Add `phase_progress_summary` to `_build_active_step` (`megaplan/cli.py:209-251`)
**Scope:** Medium
1. **Inside** `_build_active_step`, after computing `age_seconds` and enriching with `build_phase_observability`, add two new fields:
   - `progress_pct`: For completion-only phases, compute `min(95, int(age_seconds / expected_max * 100))`. Cap at 95% since completion is discrete. For execute phase, skip this (batch progress is the real signal).
   - `phase_progress_summary`: A human-readable string:
     - For completion-only phases (all non-execute): `"critique running (3m12s elapsed, typically completes within 15m)"`.
     - For execute phase: `"execute running (12m elapsed, check progress for batch-level detail)"`.
   - When health is "stale": `"critique stale (18m elapsed, expected max 15m) — see recovery_hint"`.
2. **When no `started_at`** is available (rare edge case), set `phase_progress_summary` to `"<step> active (start time unknown)"` and omit `progress_pct`.

### Step 5: Fold progress data into status for execute phase (`megaplan/cli.py:254-299`)
**Scope:** Small
1. **In** `_build_status_payload`, after building `active_step`, check if the current state indicates execution has started (finalize.json exists or state is `executing`/`executed`).
2. **If so**, compute `_build_progress_payload` and attach it as a `progress` sub-object on the status response, plus promote the top-level batch/task counts.
3. This makes `status` a superset of `watch` for execute phases, while keeping the response lean for non-execute phases.

## Overview

The megaplan harness has runtime policy data (expected durations, polling intervals) for every phase, but this information is only surfaced when a user explicitly polls `status`. The goal is to: (1) announce expected duration for the next step in completion responses, (2) add phase-aware progress summaries to `status`, (3) avoid misleading "no progress" for completion-only phases, and (4) fold `watch` into `status`.

**Architecture insight from critique:** megaplan is a blocking CLI. Non-execute phases block until completion — `_run_worker` (handlers.py:139-169) calls `set_active_step`, runs the worker synchronously, then `_finish_step` (handlers.py:202-260) builds the response. There is no mid-phase emission path. The "phase-start announcement" must therefore happen in the **completion response of the previous step** via a new `next_step_runtime` field, not in `monitor_hint` (which fires post-completion). For execute (per-batch mode), between-batch responses already provide natural polling guidance.

**Consumers:** Orchestrators (Claude, Codex subagents) read JSON responses. `status` is polled by orchestrators and humans. `progress` is execute-specific batch/task detail. `watch` adds nothing beyond merging status+progress.

**Key constraint:** JSON contract is additive-safe, removal-breaking. `watch` stays as alias. No `executing` state exists — during execute, state remains `finalized` until completion.

**`build_monitor_hint` approach:** The critique showed 6 call sites. Rather than adding parameters to all of them, we keep the signature as `build_monitor_hint(plan_dir: Path) -> str` and only change its output text from referencing `watch` to referencing `status`. Duration info goes in the new `next_step_runtime` response field instead.

**Monitoring contract after this change:**
- `status` = full plan state, active_step with progress summary, and execute progress when relevant. The one command to check.
- `progress` = kept as-is for backward compat. Execute-specific batch/task detail.
- `watch` = thin alias to `status` (returns identical payload with `step: "watch"`).
