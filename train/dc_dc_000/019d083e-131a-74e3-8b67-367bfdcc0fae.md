> AGENT

The clean data-flow model here is: the overlap belongs to the successor segment, and freshness is checked against the predecessor’s current primary variant.

**What The Flow Should Be**
- At generation time, the UI already decides whether continuation is on and how many overlap frames apply. Batch travel writes `continuation_config.overlap_frames` in [requestBody.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/requestBody.ts#L101), and individual segment tasks write `continuation_config` plus `frame_overlap_from_previous` in [segmentSettingsUtils.ts](/Users/user_c042661f/Documents/reigh/src/shared/components/SegmentSettingsForm/segmentSettingsUtils.ts#L168).
- The important boundary fact is on segment `B`, not segment `A`: “`B` contains `N` prepended frames sourced from predecessor variant `V`.”
- Join ordering should come from the current slot layout, which is already derived from `pair_shot_generation_id` first and `child_order` second in [segmentSlotAssignment.ts](/Users/user_c042661f/Documents/reigh/src/shared/hooks/segments/segmentSlotAssignment.ts#L48). That tells you which segments are adjacent now.
- Freshness for boundary `A -> B` should then be: `B.continuation_predecessor_variant_id === A.primary_variant_id` and `B.overlap_frames > 0`.
- If that check fails, you do not have a trustworthy overlap boundary, so that edge falls back to VACE.

**Main Gaps In The Current Plan**
- Part 1 only enriches params when a new child generation row is inserted in [generation-child.ts](/Users/user_c042661f/Documents/reigh/supabase/functions/complete_task/generation-child.ts#L197). But a common regen path does not insert a new generation; it adds a variant onto the existing child in [generation-child.ts](/Users/user_c042661f/Documents/reigh/supabase/functions/complete_task/generation-child.ts#L75). Since variants are created independently in [generation-core.ts](/Users/user_c042661f/Documents/reigh/supabase/functions/complete_task/generation-core.ts#L155), the plan as written misses the “existing segment got a new primary variant” case.
- Related: the join handler currently fetches only `generations.id, location` in [useJoinSegmentsHandler.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/actions/useJoinSegmentsHandler.ts#L135). Even if you add `generations.params`, that can still be stale after a variant promotion. For freshness you need the successor’s current primary variant params, not just the generation row.
- So the durable contract should be variant-scoped: stamp `continuation_predecessor_variant_id` onto the variant being created, and at join time fetch `generation.primary_variant_id` plus `primary_variant.params`. The generation row can mirror it if convenient, but should not be the source of truth.
- The proposed explicit `travel_stitch` task also has a completion-routing hole. Stitch tasks only attach back to the parent through `orchestrator_task_id` in [generation-handlers.ts](/Users/user_c042661f/Documents/reigh/supabase/functions/complete_task/generation-handlers.ts#L140). With only `parent_generation_id`, routing in [generation.ts](/Users/user_c042661f/Documents/reigh/supabase/functions/complete_task/generation.ts#L150) will fall through from `variant_on_parent` into `child_generation`, which is the wrong final shape for a joined output.

**What I’d Change**
- Store boundary metadata on every created segment variant, not only on first generation insert.
- Read boundary metadata from the successor’s current primary variant during join.
- Keep adjacency logic in the frontend from slot order; keep freshness logic from explicit metadata; do not let the worker infer either.
- For the crossfade worker path, pass an explicit per-boundary array aligned to slot order. Even if v1 stays all-crossfade-or-all-VACE, model it as boundary data now.
- Either give explicit-clips stitch tasks a real orchestration contract, or teach `complete_task` to treat stitch tasks with direct `parent_generation_id` as “variant on parent” without requiring `orchestrator_task_id`.

That gives each layer one job:
- task creation decides overlap intent,
- completion records which predecessor variant actually fed the overlap,
- join decides whether the current adjacency is still fresh,
- worker just executes the chosen join mode.
