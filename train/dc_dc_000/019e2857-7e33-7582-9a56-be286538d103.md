> AGENT

I reviewed the doc and the relevant publisher/social code. The main critique: the desired product is smaller than the proposed architecture. Build the post-live-update social review first, with a tiny shared tool contract, and defer the general agent runtime.

Key simplifications:

- Defer `src/common/agent_loop` runner work from Phase 1. The doc’s proposed runtime/types in [docs/agent-loop-standardisation-and-live-update-social-plan.md](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/agent-loop-standardisation-and-live-update-social-plan.md:111) are a lot of surface area before proving the social loop.
- Start from `TopicEditor._publish_created_topics` / `_publish_topic`; successful publish results already expose `topic_id`, `status`, and `discord_message_ids` in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:2520) and [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:2967).
- Keep a small dedicated `live_update_social_runs` table. Skip `live_update_social_decisions` unless multiple decisions per run become real.
- Add `live_update_social` to `SocialSourceKind`, but note the proposed request is incomplete: `XProvider` currently requires `source_context.metadata["user_details"]` or X posting fails in [x_provider.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/sharing/providers/x_provider.py:29).
- Do not rely on `duplicate_policy` alone. `SocialPublishService` persists it but does not enforce it; existing duplicate checks live in caller paths like [sharer.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/sharing/sharer.py:153). Add explicit social-run/publication checks before enqueueing.

**Minimal Phased Plan**

1. **Draft-only social review**
   - Trigger best-effort after TopicEditor publish result `status in {"sent", "partial"}`.
   - Store one `live_update_social_runs` row with `topic_id`, `guild_id`, `discord_message_ids`, `source_message_ids`, `decision`, `draft_text`, `selected_media_refs`, `error_message`, metadata.
   - Input should be the topic summary plus re-rendered `publish_units`; do not scrape Discord.
   - Decisions for now: `skip`, `draft_only`, `needs_human_review`.

2. **Tiny standardisation**
   - Add only a minimal tool spec/helper for the new loop: name, schema, handler, side-effect kind.
   - Add a conformance test that advertised social-loop tools have handlers.
   - Do not migrate TopicEditor or AdminChat onto this yet.

3. **Media-aware draft**
   - Reuse existing topic source metadata and `render_topic_publish_units`.
   - Resolve only media already referenced by the topic/source metadata.
   - Call image/video understanding only when selected media exists or when the topic is clearly visual.
   - If media resolution/understanding fails, record why and fall back to text-only draft or `needs_human_review`.

4. **Queue mode via existing publisher**
   - Extend `SocialSourceKind`.
   - Build `SocialPublishRequest` with `source_kind="live_update_social"`, `legacy_shared_post_policy={"enabled": False}`, no Discord announcement policies, and required X `user_details`.
   - Use `SocialPublishService.enqueue`; the existing scheduled worker already executes queued rows in [sharing_cog.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/sharing/sharing_cog.py:69).
   - Duplicate guard: existing run for topic/platform, plus existing queued/succeeded `social_publications` for the primary live-update message/source kind.

5. **Later polish**
   - Add threads, quote/reply decisions, content-level duplicate similarity, native service thread support, and broader runtime extraction only after draft/queue results look good.

**Defer Or Simplify**

- Defer full `AgentLoopRunner`, `AgentLoopPolicy`, recorder abstraction, provider-neutral response model, and migration of TopicEditor/AdminChat.
- Defer broad shared tools like `search_messages`, `get_reply_chain`, `inspect_message` unless the first social prompt demonstrably needs them.
- Simplify decision enum: no `publish_now`, `publish_thread`, `reply_to_existing_post`, or `quote_existing_post` in the first rollout.
- Simplify media model: use plain dict refs compatible with current `publish_units` first; create `MediaRef` only when two callers need it.
- Lower `LIVE_UPDATE_SOCIAL_MAX_TURNS=20`; draft/queue review should be more like 3-5 turns with a hard terminal decision.
