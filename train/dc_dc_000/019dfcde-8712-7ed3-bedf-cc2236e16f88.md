        # Implementation Plan: Sprint 7 Orchestrator Image, Pools, and Artifact Contract

## Overview
The prior revisions correctly moved claim rejection, task-count demand, artifact paths, telemetry, and readiness into their authoritative boundaries. The latest critique identifies one remaining root-boundary gap: route-aware `task-counts` and `claim-next-task` can only be authoritative if every queued task has a selected route contract. Today, route metadata is produced in worker Python for some worker-created tasks, but frontend/API-created tasks flow through `reigh-app/supabase/functions/create-task` without a TypeScript route resolver/stamper. That means consuming route fields in counts and claims would still be unreliable unless task creation derives or stamps those fields for every origin.

This revision adds route-contract production at the task-creation boundary before route-aware counts and claim filtering. The plan remains aligned with the sprint goal: one coinstalled WGP/VibeComfy image, explicit backend/profile/selector contracts, stale-worker prevention before claim, route-aware pool sizing and rollback reserve, preflight-gated readiness, testable artifact lifecycle, and queryable telemetry through Supabase heartbeat/system logs.
