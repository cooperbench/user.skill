Named stages are defined as `Transition` targets in the workflow state machine: `/Users/user_c042661f/Documents/megaplan/megaplan/_core/workflow.py:40–86`

**Canonical pipeline stages:**
- `prep` (optional, only if `with_prep=True`)
- `plan`
- `critique`

- `gate`
- `tiebreaker`, `tiebreaker-run`, `tiebreaker-decide` (conditional on gate TIEBREAKER)

- `execute`

**Not enumerated:** Stages are tracked per **iteration** (per loop cycle in `plan` → `critique` → `revise` → `gate` cycles); the `iteration` field increments per loop, but stage history is stored in `history[]` (dicts with phase/timestamp).

- Plans stored as `state.json` in plan trees at `~/.megaplan/<project>/plans/<plan-name>/` or user-specified paths

- Artifacts (plan.json, critique.json, execution.json, review.json, etc.) live as sibling files in the plan directory

**SQLite/PostgreSQL (DB Mode via Supabase):**
- Table: `plans` at `/Users/user_c042661f/Documents/megaplan/supabase/migrations/202605040000_megaplan_dbstore_foundation.sql:48–71`
- Columns: id, name, epic_id, sprint_id, revision, idea, current_state, iteration, config (jsonb), meta (jsonb), last_gate (jsonb), active_step, clarification, latest_finalize, latest_review, latest_execution, latest_failure, created_at, updated_at

**4. CLI Surface**

Existing subcommands (megaplan/cli.py circa line 450+):
- `list` — list active plans with filter options
- `init <idea>` — create new plan
- `<step>` — run a phase (plan, prep, critique, gate, finalize, execute, review, revise, tiebreaker-run, tiebreaker-decide)

**No precedent for per-run metadata I/O** (config, notes, but not user feedback). A `megaplan feedback <run-id>` command would fit naturally alongside `list`, `resume`, and step utilities. **Design recommendation**: Add optional `feedback` field (JSONb dict or list of rating records) to the `Plan` model, default to `None` or `{}`. Backwards-compatible because existing plans will deserialize it as absent. Migrations can add a nullable column to the plans table.

**6. Tickets Module**
