# Implementation Plan: Real-Time Event Pipeline

## Overview

A Python-based streaming event processing service that consumes from Kafka, transforms events using declarative rules from DynamoDB, and fans out to S3, Elasticsearch, and webhook sinks with at-least-once delivery, backpressure handling, and dead-letter queuing.

**Language:** Python 3.11+ (matching the existing project runtime)
**Key libraries:** confluent-kafka, boto3 (DynamoDB + S3), elasticsearch-py, httpx (async webhooks), asyncio

**Goal:** Prove we can consume and produce Kafka messages locally before writing any business logic.

### Steps

1. **Initialize project structure**

   event_pipeline/
   ├── pyproject.toml
   ├── pipeline/

   │   ├── config.py          # Pydantic settings (broker, topics, sink configs)
   │   ├── consumer.py        # Kafka consumer wrapper
   │   ├── transform.py       # Rule engine
   │   ├── sinks/
   │   │   ├── __init__.py
   │   │   ├── base.py        # Abstract sink interface
   │   │   ├── s3.py

   │   │   └── webhook.py
   │   ├── backpressure.py    # Bounded buffer + pause/resume
   │   ├── dlq.py             # Dead-letter queue handler
   │   ├── rules.py           # DynamoDB rule loader with hot-reload
   │   └── metrics.py         # Prometheus metrics

   - Buffer sizes, retry counts, DLQ topic

4. **Implement `consumer.py`** — thin wrapper around `confluent_kafka.Consumer`:
   - Subscribe to configured topics
   - Expose `pause()` / `resume()` for backpressure
   - Manual offset commit after sink acknowledgement
   - Assign one consumer per partition (configurable parallelism via consumer group)

5. **Validation checkpoint:** Run `docker-compose up`, produce 10 messages with `confluent_kafka.Producer`, consume and print them. Pass = messages printed in order.

## Phase 2: Transformation Rule Engine

**Goal:** Load declarative rules from DynamoDB, apply them to events, and handle malformed rules gracefully.

### Steps

6. **Define rule schema** (JSON in DynamoDB):
   ```json
   {
     "rule_id": "r-001",
     "version": 3,
     "active": true,
     "filter": {"field": "event_type", "op": "eq", "value": "purchase"},
     "mappings": [
       {"source": "$.user.id", "target": "$.customer_id"},
       {"source": "$.amount", "target": "$.total", "transform": "cents_to_dollars"}
     ],
     "enrichments": [
       {"target": "$.processed_at", "value": "{{now_iso}}"}
     ]
   }
   ```

7. **Implement `rules.py`** — DynamoDB rule loader:
   - `load_rules()`: scan table, cache in memory, return `list[Rule]`
   - Background thread reloads every N seconds (configurable, default 30s)
   - Version field enables rule updates without ambiguity
   - Log warnings for malformed rules, skip them (don't crash)

8. **Implement `transform.py`** — rule application engine:
   - `apply_rules(event: dict, rules: list[Rule]) -> dict | None`
   - Filter step: evaluate filter predicates; if no rule matches, pass through or drop (configurable)
   - Mapping step: JSONPath-based field extraction and remapping
   - Enrichment step: inject computed fields (timestamps, UUIDs)
   - Returns `None` if event is filtered out; raises `TransformError` for malformed events (routed to DLQ)

9. **Validation checkpoint:** Unit tests — load rules from DynamoDB Local, transform 5 sample events, assert output shapes. Include a malformed-rule test that verifies the rule is skipped with a warning.

## Phase 3: Sink Implementations

**Goal:** Implement all three sinks behind a common interface with idempotency.

### Steps

10. **Define `base.py` sink interface:**
    ```python
    class Sink(ABC):
        async def write_batch(self, events: list[Event]) -> WriteResult: ...
        async def health_check(self) -> bool: ...
        async def close(self) -> None: ...
    ```

11. **Implement `s3.py`** — batched S3 writer:
    - Buffers events in memory until batch size (default 1000) or time window (default 60s)
    - Writes as newline-delimited JSON to `s3://{bucket}/{topic}/{date}/{partition}-{offset}.jsonl`
    - Idempotency: S3 PutObject with deterministic key (partition + offset range) — re-upload is a no-op
    - Uses boto3 with LocalStack endpoint override for local dev

12. **Implement `elasticsearch.py`** — bulk ES writer:
    - Batches events, uses `_bulk` API
    - Document ID = event ID (idempotent upsert)
    - Configurable index name pattern (e.g., `events-{date}`)
    - Retry transient 429/5xx errors with exponential backoff

13. **Implement `webhook.py`** — async HTTP poster:
    - Uses `httpx.AsyncClient` with connection pooling
    - Posts events individually (or micro-batched if endpoint supports it)
    - Idempotency header: `X-Event-ID` — receiver is expected to deduplicate
    - Circuit breaker: after N consecutive failures, open circuit for M seconds, then half-open probe
    - Configurable timeout, max retries, backoff

14. **Validation checkpoint:** Integration test per sink — write 100 events, read them back, assert count and content match. For webhooks, use a local HTTP server that records requests.

## Phase 4: Backpressure & Flow Control

**Goal:** Prevent any slow sink from causing unbounded memory growth or Kafka consumer lag spiraling.

### Steps

15. **Implement `backpressure.py`**:
    - `BoundedBuffer(max_size)` per sink — asyncio.Queue with configurable capacity
    - When any buffer exceeds high-water mark (80% full): signal consumer to `pause()` affected partitions
    - When buffer drains below low-water mark (50%): signal consumer to `resume()`
    - Expose current buffer depths as Prometheus gauges

16. **Wire consumer → buffers → sinks** in main event loop:
    ```
    Consumer → [transform] → fan-out to N buffers → N sink writers (async tasks)
    ```
    - Each sink writer drains its buffer independently
    - Consumer polls only when all buffers are below high-water mark

17. **Validation checkpoint:** Load test — produce 10k events/sec, throttle one sink (add 500ms latency to webhook), verify: (a) consumer pauses, (b) other sinks continue draining, (c) no OOM, (d) consumer resumes when backlog clears.

---

## Phase 5: Dead-Letter Queue & Error Handling

**Goal:** Events that fail transformation or exhaust sink retries land in a DLQ rather than being silently dropped.

### Steps

18. **Implement `dlq.py`**:
    - DLQ destination = dedicated Kafka topic (`{topic}.dlq`)
    - Envelope: `{"original_event": ..., "error": ..., "sink": ..., "timestamp": ..., "attempts": N}`
    - Produce to DLQ topic with the original event's key (preserves ordering per key)

19. **Integrate DLQ into pipeline:**
    - `TransformError` → DLQ immediately
    - Sink write failure after max retries → DLQ with sink name and error details
    - Circuit-breaker open events → DLQ (don't block the pipeline)

20. **Validation checkpoint:** Force failures (malformed event, webhook 500s that exhaust retries), verify events appear in DLQ topic with correct envelopes.

## Phase 6: Observability & Operational Readiness

**Goal:** Make the pipeline operable in production.

### Steps

21. **Implement `metrics.py`** — Prometheus metrics via `prometheus_client`:
    - `events_consumed_total` (counter, by topic)
    - `events_transformed_total` / `events_transform_errors_total`
    - `events_written_total` (counter, by sink)
    - `events_dlq_total` (counter, by reason)
    - `sink_buffer_depth` (gauge, by sink)
    - `sink_write_latency_seconds` (histogram, by sink)
    - `rule_reload_timestamp` (gauge)
    - `consumer_lag` (gauge, by partition)

22. **Structured logging** — JSON logs via `structlog`:
    - Log every DLQ event at WARN
    - Log circuit breaker state changes at WARN
    - Log rule reload success/failure at INFO/ERROR
    - Log consumer pause/resume at INFO

23. **Health endpoint** — lightweight HTTP server (aiohttp or FastAPI) on `/health`:
    - Returns 200 if consumer is connected and all sinks pass health check
    - Returns 503 with details if any component is unhealthy

24. **Validation checkpoint:** Run pipeline for 5 minutes under load, verify Prometheus metrics are non-zero and health endpoint returns 200.

## Phase 7: End-to-End Integration Test

**Goal:** Prove the entire pipeline works as a unit.

### Steps

25. **Write E2E test:**
    - Start all services via docker-compose
    - Seed DynamoDB with 3 rules (one filter, one mapping, one enrichment)
    - Produce 1000 events to Kafka (mix of event types)
    - Wait for pipeline to process
    - Assert: S3 contains expected files with correct event counts, ES index has correct documents, webhook receiver got expected POSTs, DLQ has expected error events
    - Assert: no events lost (consumed = written + filtered + DLQ'd)

26. **Idempotency test:**
    - Restart the pipeline mid-stream (kill and restart consumer)
    - Assert: sinks contain no duplicate events (S3 keys are unchanged, ES doc count is unchanged, webhook receiver deduplicates by event ID)

## Assumptions

- **Python is acceptable** for this service. If throughput needs exceed ~50k events/sec sustained, Go or Java would be more appropriate for the consumer/transform layer.
- **Kafka is already deployed** (or will be) — this plan does not cover Kafka cluster provisioning.
- **DynamoDB is the chosen rule store** — not a config file, not a relational DB. Rules are expected to change infrequently (not per-event).
- **All events are JSON.** Binary/Avro/Protobuf events would require a deserialization layer not covered here.
- **Webhook receivers are expected to be idempotent** on `X-Event-ID`. The pipeline cannot guarantee exactly-once to non-idempotent webhooks.
- **Single-region deployment.** Multi-region or cross-DC replication is out of scope.
- **No authentication/authorization layer** for the pipeline itself (no multi-tenant rule isolation). This can be layered on later.

## Open Questions

1. **Event schema:** Is there a fixed schema for incoming events, or must the pipeline handle arbitrary JSON? This affects whether we can validate events at ingestion time.
2. **Rule authoring UI:** Who creates/edits rules in DynamoDB? Is there an admin API or UI needed, or are rules managed via CLI/scripts?
3. **Ordering guarantees:** Is per-partition ordering sufficient, or do any sinks require global ordering? Per-partition is straightforward; global ordering across partitions would require a fundamentally different architecture.
4. **S3 file format:** Is newline-delimited JSON acceptable, or is Parquet/Avro needed for downstream analytics? This changes the S3 sink significantly.
5. **Deployment target:** Kubernetes (Deployment + HPA), ECS, bare EC2? This determines how health checks, scaling, and rolling deploys work.
6. **Webhook endpoint count:** Are there 2-3 fixed webhooks, or could there be hundreds? High fan-out to many webhooks changes the concurrency and circuit-breaker model substantially.
