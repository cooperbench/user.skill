Orchestrator selected-pool totals and stale-route lifecycle live in `reigh-worker-orchestrator/gpu_orchestrator/database.py` and `reigh-worker-orchestrator/gpu_orchestrator/worker_state.py`. ## Main Phase

### Step 1: Pin the canary trigger and patch boundary (`reigh-worker/source/task_handlers/tasks/template_routing.py`, `reigh-app/supabase/functions/_shared/selectedRoute.ts`)
**Scope:** Small
1. **Confirm** the canary evidence before editing code: route cohort, route key or task type, selector namespace/version, selected backend, worker pool, affected task IDs or log refs, observed failure, and whether non-RayWorker routes share any touched app/completion/billing path.
2. **Classify** the patch as exactly one primary boundary: selector map/route key, Section 3A support-report metadata, worker claim guard, task-count selected-pool visibility, orchestrator pool/stale-worker behavior, completion, billing, or worker adapter behavior.
3. **Reject** patches that are only dashboard/readiness/runbook presentation work. Sprint 11A may update rollback notes tied to behavior changes, but Sprint 11B owns dashboard-only and runbook-only work.

### Step 2: Patch selector contracts with explicit mirror rules (`reigh-worker/source/task_handlers/tasks/template_routing.py`, `reigh-app/supabase/functions/_shared/selectedRoute.ts`)
**Scope:** Medium
1. **Keep WGP selectable** by preserving WGP-safe route contracts for unsupported, missing, malformed, or explicitly WGP-only routes. Do not replace cohort promotion with a broad backend switch.
2. **Mirror runtime route-contract fields** between Python and TypeScript when a patch changes route key derivation, support state, selected template ID, selected profile, selector namespace/version handling, route run ID, or worker contract version.
3. **Handle Section 3A metadata deliberately**: if the patch changes `SECTION3A_ROUTE_SUPPORT_MAP` `disposition` or `blocking_reason` semantics in Python, either add the equivalent TypeScript support-report metadata and tests, or document in the patch why the metadata is worker-only and not part of app route-contract behavior.
4. **Add focused tests** for the exact patched route in `reigh-worker/tests/test_template_routing.py` and edge route tests near `reigh-app/supabase/functions/create-task/routeContract.test.ts` or a colocated `_shared/selectedRoute` test if TypeScript mirror behavior changes.

### Step 3: Patch claim and task-count behavior without overstating aggregate counts (`reigh-worker/source/core/db/task_claim.py`, `reigh-app/supabase/functions/claim-next-task/index.ts`, `reigh-app/supabase/functions/task-counts/index.ts`, `reigh-worker-orchestrator/gpu_orchestrator/database.py`)
**Scope:** Medium
1. **Treat `claim-next-task` as the execution isolation gate**. Validate that claim requests and RPC arguments carry `worker_backend`, `worker_profile`, `selector_namespace`, `selector_version`, and `worker_contract_version`, and that mismatched tasks cannot be executed by the wrong selected backend.
2. **Treat `task-counts` aggregate `totals` as legacy/global visibility unless SQL/RPCs are explicitly changed**. Route-aware scaling should use `route_totals` plus orchestrator `selected_pool_totals`, not aggregate `totals`, unless the patch also updates the count/breakdown RPC signatures and SQL implementation to route-filter aggregates.
3. **If selected-pool counts are touched**, update or add tests for both the edge route-demand output and orchestrator selected-pool aggregation in `reigh-worker-orchestrator/tests/gpu_orchestrator/test_route_aware_task_counts.py`.
4. **If aggregate route filtering is required by the trigger**, include the SQL/RPC migration or function change in the same patch and test that aggregate counts and selected-pool counts agree for the selected route while other route cohorts remain excluded.

### Step 4: Patch worker/orchestrator lifecycle only when live evidence points there (`reigh-worker-orchestrator/gpu_orchestrator/worker_state.py`, `reigh-worker-orchestrator/gpu_orchestrator/control_loop.py`)
**Scope:** Medium
1. **Limit changes** to route-stale detection, selected-pool capacity accounting, stale worker drain/termination behavior, or route metadata written during worker spawn when those exact behaviors match the canary evidence.
2. **Keep drain-first behavior**: active route-stale workers finish current work; idle route-stale workers become terminable and are not counted as healthy capacity for the new selector.
3. **Test exact lifecycle behavior** in `reigh-worker-orchestrator/tests/test_route_stale_worker_state.py` and any selected-pool scaling test that covers the changed capacity path.

### Step 5: Patch completion or billing shared paths only with non-RayWorker protection (`reigh-app/supabase/functions/complete_task/`, `reigh-app/supabase/functions/calculate-task-cost/`, `reigh-app/supabase/functions/_shared/billing.ts`)
**Scope:** Medium
1. **Touch these paths only** if the canary trigger is a completion/billing regression or the required selector/claim patch necessarily changes completion metadata consumed by these paths.
2. **Preserve idempotency and sub-task billing ownership**: `complete_task` should skip child task cost triggers where parent/orchestrator billing owns cost, and `calculate-task-cost` should remain spend-ledger idempotent.
3. **Prove active non-RayWorker routes remain green** with `reigh-worker/scripts/dual_run_compare/tests/test_non_rayworker_fixtures.py` and relevant edge tests such as `complete_task/billing.test.ts`, `_shared/billing.test.ts`, and `calculate-task-cost/index.test.ts`.

### Step 6: Update rollback notes for the repo whose behavior changed (`reigh-app/tasks/canary-rollback-app.md`, `reigh-worker/tasks/canary-rollback-worker.md`, `reigh-worker-orchestrator/tasks/canary-rollback-orchestrator.md`)
**Scope:** Small
1. **Update `reigh-app/tasks/canary-rollback-app.md`** whenever app-owned selector, route stamping, claim, task-count, completion, billing, or non-RayWorker route behavior changes.
2. **Update `reigh-worker/tasks/canary-rollback-worker.md`** whenever worker route selection, worker claim guard, adapter behavior, or worker-local WGP/VibeComfy execution behavior changes.
3. **Update `reigh-worker-orchestrator/tasks/canary-rollback-orchestrator.md`** whenever selected-pool orchestration, worker pool identity, route-stale lifecycle, scaling, or worker spawn route metadata changes.
4. **Keep rollback notes behavior-specific**: include selector env vars, worker pool identity, route contract version, expected stale-route drain behavior, and the emergency selector flip back to WGP. Do not add dashboard/readiness-only content.

### Step 7: Prove the patch with targeted then broader checks (`reigh-worker/tests/`, `reigh-worker-orchestrator/tests/`, `reigh-app/supabase/functions/`)
**Scope:** Medium
1. **Run cheapest focused tests first** based on touched files:
   - `cd reigh-worker && python -m pytest tests/test_template_routing.py tests/runtime/test_worker_preflight.py`
   - `cd reigh-worker-orchestrator && python -m pytest tests/test_route_stale_worker_state.py tests/gpu_orchestrator/test_route_aware_task_counts.py`
   - `cd reigh-app && npx vitest run --config config/testing/vitest.edge.config.ts supabase/functions/create-task/routeContract.test.ts supabase/functions/complete_task/billing.test.ts supabase/functions/_shared/billing.test.ts supabase/functions/calculate-task-cost/index.test.ts`
2. **Validate claim gates when claim or task-count behavior is touched** by adding/running focused tests that prove a worker cannot execute a task selected for a different backend, selector namespace/version, profile, or worker contract version.
3. **Run non-RayWorker evidence checks** whenever completion, billing, app claim, app task-count, or shared app surfaces are touched:
   - `cd reigh-worker && python -m pytest scripts/dual_run_compare/tests/test_non_rayworker_fixtures.py`
4. **Finish with the smallest broader suite** for each repo touched, such as `cd reigh-app && npm run test:edge:unit`, `cd reigh-worker && python -m pytest tests/test_template_routing.py`, and `cd reigh-worker-orchestrator && python -m pytest tests` if orchestrator shared lifecycle logic changed.

## Execution Order
1. Start from live canary evidence and choose exactly one primary patch boundary.
2. Patch selector/route-contract mirrors before changing claim or scaling behavior.
3. Validate claim gating before using task-count results as operational confidence.
4. Patch lifecycle/claim code before completion/billing code unless the canary trigger is explicitly completion/billing.
5. Update the rollback note for every repo whose runtime behavior changed.
6. Run focused tests before broader suites.

## Validation Order
1. Verify the failing canary trigger is directly covered by a focused regression test.
2. Verify WGP remains selectable and explicit VibeComfy unsupported routes fail closed without fallback execution.
3. Verify claim responses and claim guards preserve selector namespace/version, backend, profile, and worker contract fields.
4. Verify task-count validation uses selected-pool `route_totals`/`selected_pool_totals`, or prove aggregate route filtering only if the SQL/RPC layer was changed.
5. Verify shared completion/billing changes do not regress active non-RayWorker fixture/oracle coverage.
6. Verify rollback notes include `reigh-app`, `reigh-worker`, and/or `reigh-worker-orchestrator` artifacts according to the changed behavior and identify selector flip back to WGP.
