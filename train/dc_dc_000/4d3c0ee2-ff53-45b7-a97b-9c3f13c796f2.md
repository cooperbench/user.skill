## 1. Background and motivation

The Veas platform hosts multiple chatbot personas. Two ship today:
- **Véas** — dyad-shape mediator for romantic relationships (`bot_id='mediator'`, `participants_shape='dyad'`, `primary_topic_slug='relationship'`).
- **Coach** — solo-shape career coach (`bot_id='coach'`, `participants_shape='solo'`, `primary_topic_slug='career'`). Reference commit: `b0e0495`.

The architecture refactor across sprints S1–S6 made multi-bot ownership and per-bot tool allowlists first-class. The coach bot is the canonical solo exemplar. Adding a third solo bot now is the proof-of-architecture moment.

This sprint adds **Tante Rosi**, a solo-shape pregnancy coach. She supports a single pregnant user across the arc of pregnancy: knowing their current gestational week, surfacing upcoming appointments (via existing `scheduled_tasks`), tracking emotional/symptom themes (via existing `themes` and `observations`), and handling medical red flags via a strengthened `out_of_bounds` framework. The bot's voice is a warm, knowledgeable aunt ("Tante" = aunt in German) who knows when to defer to a clinician.

### Why this bot now

Three drivers:
1. **Real user need** — the principal user wants a bot that supports a real pregnancy in their life.
2. **Architecture validation** — the third bot proves the multi-bot architecture works without requiring foundational refactors.
3. **Medical-safety pattern** — pregnancy is the first health-adjacent bot; the OOB framework's medical-escalation pattern that lands here will be reusable for future health bots.

### Explicit non-goal: no generic abstraction

A prior design exploration (`docs/longitudinal-state.md`) proposed a generic `user_journeys` abstraction to accommodate pregnancy, fitness, weight, sobriety, etc. **That doc is rejected for this sprint** after review. Rationale: we have zero examples in production; the abstraction was designed against speculation about three hypothetical bots, not one real one. The right move is per-feature schema for Rosi, then extract a shared abstraction only after 3+ bots show genuine pattern overlap.

Keep `docs/longitudinal-state.md` as exploration reference. Add a header note: "Rejected 2026-05-12 in favor of per-feature schemas — see `docs/pregnancy-state.md`. Revisit if 3+ bots show pattern overlap." Do not implement against it.

#### Helper module `app/services/pregnancy.py`

A small, pure module — no DB calls — exporting:

```python
from datetime import date, datetime, timezone
from typing import Literal

GESTATION_WEEKS = 40
LATE_OVERDUE_WEEKS = 42

def gestational_age(edd: date, today: date | None = None) -> tuple[int, int]:
    """Return (weeks, days) since LMP-equivalent (40w before EDD).

    Examples:
      EDD 2026-10-22, today 2026-05-12 → (17, 2)
    Clamped to [(0, 0), (LATE_OVERDUE_WEEKS, 6)]; raises if EDD is more
    than 1 year out (data error guard).
    """

def trimester(weeks: int) -> Literal['first', 'second', 'third']:
    """First: 0–12, Second: 13–27, Third: 28+. Standard clinical cut."""

def is_pregnancy_active(user) -> bool:
    """True iff edd is set AND ended_at is null."""

def days_since_loss(user, today: date | None = None) -> int | None:
    """For sensitivity rendering. Returns days since pregnancy_ended_at
    when outcome=loss, else None."""

def format_pregnancy_state(user) -> str | None:
    """Return the prompt-ready render block, or None if no pregnancy.

    Active form:
      ## Pregnancy
      - 17w2d (second trimester, EDD 2026-10-22, basis: lmp)
      - started: 2026-01-15

    Recent loss form (within 90 days of ended_at):
      ## Pregnancy
      - Recent loss (12 days ago). Handle with care.

    Recent birth form (within 90 days):
      ## Pregnancy (concluded)
      - Birth 12 days ago (EDD was 2026-10-22).

    Older than 90 days post-conclusion: returns None.
    """
```

**Edge cases the implementation must handle:**

- EDD set, gestational age computes to (-1, x) → clamp to (0, 0) and surface a warning in the render
- EDD set more than 1 year out → raise `ValueError` (data error; tool must reject)
- EDD passed by more than 2 weeks (overdue) → render `"42w (overdue, EDD was 2026-10-22)"`
- Twin pregnancies — no schema field for this in v1; mention in the persona as a follow-up if it comes up
- Pregnancy `started_at` may pre-date the conversation if Rosi onboards a user already pregnant

**Timezone:** EDD is stored as `date` (no timezone). `today` is computed in the user's `timezone` if set, falling back to UTC. The helper accepts an explicit `today` arg for testability.

#### Three write tools

In `app/services/tools/write_tools.py`, following the existing tool registration pattern (matching e.g. `add_memory`, `update_oob`):

```python
async def set_pregnancy_edd(
    pool,
    ctx,
    *,
    edd: str,                            # ISO date
    dating_basis: Literal['lmp', 'scan'],
    lmp_date: str | None = None,
    scan_date: str | None = None,
    started_at: str | None = None,       # ISO datetime; defaults to now()
) -> dict:
    """Initial pregnancy capture. Errors if there is already an active
    pregnancy for ctx.user.id. Sets edd, dating_basis, optional provenance
    (lmp/scan dates), and pregnancy_started_at.
    """

async def correct_pregnancy_edd(
    pool,
    ctx,
    *,
    edd: str,
    dating_basis: Literal['lmp', 'scan'],
    scan_date: str | None = None,
) -> dict:
    """Mid-pregnancy correction (e.g. dating scan revises EDD). Requires
    an active pregnancy. Preserves pregnancy_started_at. Sets
    pregnancy_scan_corrected_at = now() when dating_basis flips to 'scan'.
    """

async def end_pregnancy(
    pool,
    ctx,
    *,
    outcome: Literal['birth', 'loss', 'termination'],
    ended_at: str | None = None,
) -> dict:
    """Close the active pregnancy. Errors if no active pregnancy.
    Records outcome + ended_at. Does NOT delete the historical columns
    so the bot can still render 'recent loss/birth' state for 90 days.
    """
```

Tool requirements:
- **Idempotency:** Each tool checks current state and errors clearly if preconditions fail. Re-running `end_pregnancy` after closure errors with `"pregnancy already ended on <date>"`.
- **Concurrency:** Wrap each in a single transaction with `SELECT … FOR UPDATE` on the user row to prevent race conditions if two tool calls arrive simultaneously.
- **Tool-call logging:** Pregnancy tool calls land in the existing `turn_audit_events` table; no special logging.
- **No PII in tool result strings.** Return shape: `{"ok": true, "edd": "2026-10-22", "gestational_age": "17w2d"}`. Avoid echoing message content.
- **Tool descriptions** (the strings the LLM sees in `tool_schemas.py`): write these as if explaining to a thoughtful but cautious aunt. Specify which to call when. Cite the precondition errors explicitly so the LLM doesn't loop.

#### Persona file `app/bots/prompts/tante_rosi.py`

Create the directory `app/bots/prompts/` (does not exist yet — first bot to need it). Inside, `tante_rosi.py` exports `render_system_prompt(**kwargs) -> str`. Follow the coach exemplar pattern (delegate to a shared solo-prompt function and add bot-specific layering).

The persona body must include:

1. **Voice register** — warm aunt, addresses the user with care, uses "we" sparingly and never patronizingly. Calibration samples provided by user during Phase 2.
2. **Medical-defer guardrails** — explicit, frequent: "I am not a doctor. For anything that worries you, please call your midwife/OB." This phrasing or near-equivalent must appear when any symptom is described.
3. **Loss/grief stance** — when `pregnancy_outcome = 'loss'` or `'termination'` is recent, the persona MUST NOT default to celebratory framing about pregnancy. Specific guidance: do not ask about gestational week, do not surface unrelated bright cheer. Acknowledge the loss; offer presence; ask what kind of support is wanted.
4. **Complication handling** — high-risk pregnancy mentions (e.g. prior miscarriage, gestational diabetes, preeclampsia signs) should down-shift Rosi's tone to careful presence + escalation. Persona includes a small list of "elevate to OOB immediately" triggers.
5. **Onboarding stance** — if `pregnancy_edd IS NULL` and the user mentions pregnancy, Rosi's first job is to capture EDD or LMP. Persona includes a small script for this turn:
   - "Congratulations. To support you well, may I know roughly when you're due, or when your last period was?"
   - On answer: call `set_pregnancy_edd` with the appropriate `dating_basis`.
6. **Multilingual stance** — defaults to the user's incoming language; comfortable in German if the user uses it; uses "Tante" register either way.
7. **Boundaries** — refuses requests outside scope: financial advice, partner relationship advice (deflect to Véas), explicit medical diagnosis.

Persona file approximate length: 80–150 lines of prompt-text. The `_tante_rosi_prompt_renderer` function composes the persona + the standard solo prompt scaffolding (read/consult/respond/record/schedule steps).

#### OOB seed entries for medical red flags

The OOB framework currently surfaces user-reported sensitive content; we additionally need **pre-loaded medical red-flag patterns** that Rosi recognizes and escalates. Implementation choice (decide during phase 1):

**Option A:** Hard-code a list of patterns in `app/bots/prompts/tante_rosi.py` that the persona instructs the LLM to recognize. No DB rows; cheap; relies on LLM recognition.

## 4. Sensitivity, safety, and privacy

This bot handles **special-category health data** (GDPR Article 9) and sensitive life events (loss, complications). The following are non-negotiable:

### 4.1 No auto-bridging

The mediator bot's relationship-thread view of the pregnant partner is limited to the one-line gestational summary. Tests must assert:

- No `bridge_candidates` row referencing pregnancy content can be created by any tool
- The dyad hot context render of pregnancy is the hard-coded one-line; never a derived summary of symptoms, weight, or themes
- The `cross_thread_sharing_default` mechanism does NOT apply to pregnancy state (which is health data, not narrative)

If the user explicitly enables broader sharing later (e.g. wants Véas to surface that they had a hard scan day), that's a future Phase 3 conversation — not v1.

### 4.2 No specific medical advice

- The persona MUST always defer specific medical questions to a clinician
- The persona MUST NOT reassure about a red-flag symptom — escalate instead
- The persona MUST NOT give dose/timing advice for medications
- The persona MAY share general well-established information ("most women feel first movements around weeks 18–22") with hedging
- The persona MAY emotionally support, contextualize, and listen — that's the core value-add

Phase 2 critique should focus disproportionately on persona content review. Consider running an independent LLM critique of the persona prompt against an explicit medical-liability checklist before deploying.

### 4.3 Loss handling

The `outcome='loss'` and `outcome='termination'` paths are not edge cases — they happen in real pregnancies, sometimes during the lifetime of an active bot session. The persona MUST:

- Acknowledge the loss directly without euphemism, but with care
- NOT default to celebratory pregnancy framing in the same session
- NOT push "let's track your next pregnancy" or any forward-momentum framing
- Offer presence: "I'm here. What kind of support feels right?"
- Surface clinical resources (miscarriage support groups, bereavement counsellors) when asked but not prescriptively

The 90-day "recent loss/birth" render in hot context exists specifically so the bot maintains awareness across sessions and doesn't accidentally restart cheerful pregnancy chat the next day.

### 4.4 PII and logging

- `pregnancy_*` columns are encrypted only at the cluster level (existing setup) — no per-column encryption added
- Tool call results must NOT echo message content
- Turn audit events log tool names and parameter keys, not values (existing audit pattern)
- Sentry/error logging must NOT include user pregnancy data — wrap any error logs that touch user state in PII-redaction helpers (existing pattern in the codebase; align)

### 4.5 Deletion

A user requesting deletion of pregnancy data: tools should support a `clear_pregnancy()` admin-only path that sets all `pregnancy_*` columns to NULL. Not user-facing in v1; add only the admin path or defer entirely. **Recommend: defer.** Existing user-deletion paths CASCADE cleanly because pregnancy lives on `users`.

## 6. Success criteria

A user-acceptance test, run on prod with the principal user, that passes all of:

1. **Onboarding** — user tells Rosi they're pregnant; Rosi captures EDD via `set_pregnancy_edd`; next turn the gestational week renders correctly in the prompt

```
    """Register staging-only bots (coach) lazily.

        from app.bots.coach import build_coach_spec

        coach = build_coach_spec()
        BOT_SPECS[coach.bot_id] = coach


class UnknownBotSpec(ValueError):
    pass


def get_bot_spec(bot_id: str) -> BotSpec:
    _maybe_register_staging_bots()
    try:
        return BOT_SPECS[bot_id]
    except KeyError as exc:
        known = ", ".join(sorted(BOT_SPECS))
        raise UnknownBotSpec(f"unknown bot spec: {bot_id}; known specs: {known}") from exc


async def populate_mediator_spec_from_db(pool: Any) -> None:
```

```python
    """True iff edd is set AND ended_at is null."""

def days_since_loss(user, today: date | None = None) -> int | None:
    """For sensitivity rendering. Returns days since pregnancy_ended_at

    Active form:

      - 17w2d (second trimester, EDD 2026-10-22, basis: lmp)
```

**Edge cases the implementation must handle:**

- EDD set, gestational age computes to (-1, x) → clamp to (0, 0) and surface a warning in the render
- EDD set more than 1 year out → raise `ValueError` (data error; tool must reject)
- EDD passed by more than 2 weeks (overdue) → render `"42w (overdue, EDD was 2026-10-22)"`
- Twin pregnancies — no schema field for this in v1; mention in the persona as a follow-up if it comes up
- Pregnancy `started_at` may pre-date the conversation if Rosi onboards a user already pregnant

**Timezone:** EDD is stored as `date` (no timezone). `today` is computed in the user's `timezone` if set, falling back to UTC. The helper accepts an explicit `today` arg for testability.

```python
    pregnancy_scan_corrected_at = now() when dating_basis flips to 'scan'.
    """

async def end_pregnancy(
    pool,
    ctx,
    *,
    outcome: Literal['birth', 'loss', 'termination'],
    ended_at: str | None = None,
) -> dict:
    """Close the active pregnancy. Errors if no active pregnancy.
    Records outcome + ended_at. Does NOT delete the historical columns
    so the bot can still render 'recent loss/birth' state for 90 days.
    """
```

Tool requirements:
- **Idempotency:** Each tool checks current state and errors clearly if preconditions fail. Re-running `end_pregnancy` after closure errors with `"pregnancy already ended on <date>"`.
- **Concurrency:** Wrap each in a single transaction with `SELECT … FOR UPDATE` on the user row to prevent race conditions if two tool calls arrive simultaneously.
- **Tool-call logging:** Pregnancy tool calls land in the existing `turn_audit_events` table; no special logging.
- **No PII in tool result strings.** Return shape: `{"ok": true, "edd": "2026-10-22", "gestational_age": "17w2d"}`. Avoid echoing message content.
- **Tool descriptions** (the strings the LLM sees in `tool_schemas.py`): write these as if explaining to a thoughtful but cautious aunt. Specify which to call when. Cite the precondition errors explicitly so the LLM doesn't loop.

## 4. Sensitivity, safety, and privacy

This bot handles **special-category health data** (GDPR Article 9) and sensitive life events (loss, complications). The following are non-negotiable:

### 4.1 No auto-bridging

The mediator bot's relationship-thread view of the pregnant partner is limited to the one-line gestational summary. Tests must assert:

- No `bridge_candidates` row referencing pregnancy content can be created by any tool
- The dyad hot context render of pregnancy is the hard-coded one-line; never a derived summary of symptoms, weight, or themes
- The `cross_thread_sharing_default` mechanism does NOT apply to pregnancy state (which is health data, not narrative)

If the user explicitly enables broader sharing later (e.g. wants Véas to surface that they had a hard scan day), that's a future Phase 3 conversation — not v1.

### 4.2 No specific medical advice

- The persona MUST always defer specific medical questions to a clinician
- The persona MUST NOT reassure about a red-flag symptom — escalate instead
- The persona MUST NOT give dose/timing advice for medications
- The persona MAY share general well-established information ("most women feel first movements around weeks 18–22") with hedging
- The persona MAY emotionally support, contextualize, and listen — that's the core value-add

Phase 2 critique should focus disproportionately on persona content review. Consider running an independent LLM critique of the persona prompt against an explicit medical-liability checklist before deploying.

### 4.3 Loss handling

The `outcome='loss'` and `outcome='termination'` paths are not edge cases — they happen in real pregnancies, sometimes during the lifetime of an active bot session. The persona MUST:

- Acknowledge the loss directly without euphemism, but with care
- NOT default to celebratory pregnancy framing in the same session
- NOT push "let's track your next pregnancy" or any forward-momentum framing
- Offer presence: "I'm here. What kind of support feels right?"
- Surface clinical resources (miscarriage support groups, bereavement counsellors) when asked but not prescriptively

The 90-day "recent loss/birth" render in hot context exists specifically so the bot maintains awareness across sessions and doesn't accidentally restart cheerful pregnancy chat the next day.

### 4.4 PII and logging

- `pregnancy_*` columns are encrypted only at the cluster level (existing setup) — no per-column encryption added
- Tool call results must NOT echo message content
- Turn audit events log tool names and parameter keys, not values (existing audit pattern)
- Sentry/error logging must NOT include user pregnancy data — wrap any error logs that touch user state in PII-redaction helpers (existing pattern in the codebase; align)

### 4.5 Deletion

A user requesting deletion of pregnancy data: tools should support a `clear_pregnancy()` admin-only path that sets all `pregnancy_*` columns to NULL. Not user-facing in v1; add only the admin path or defer entirely. **Recommend: defer.** Existing user-deletion paths CASCADE cleanly because pregnancy lives on `users`.
