        # Implementation Plan: Model Profile System

## Overview

Add `--profile <name>` to every CLI entry point that already accepts `--phase-model`. A profile is a named TOML map from phase → `agent:model` spec that expands into the same `phase_model` list the CLI already consumes. The existing per-phase resolution logic at `megaplan/workers.py:1615-1651` does not change; profiles are a preset *loader* that feeds data into that path with the correct precedence: ad-hoc `--phase-model` > `--profile` > `--hermes` > agent default.

Three config layers are merged in order: built-ins shipped in `megaplan/profiles/*.toml` (lowest) → user `~/.config/megaplan/profiles.toml` → project `.megaplan/profiles.toml` (highest). A later layer replaces the full profile with the same name (no per-field merging — keep it simple; every layer writes a complete profile).

Python is already 3.11+ (pyproject.toml:9), so stdlib `tomllib` covers reads. No TOML writer needed — `config profiles` is read-only (list + show); users edit the TOML by hand. No new dependencies.

Repo shape to respect:
- CLI parsers duplicate the `--hermes` / `--phase-model` block by hand at six call sites (see Step 4). Match existing style — do not refactor to a shared helper unless trivial.
- `DEFAULT_AGENT_ROUTING` at `megaplan/types.py:305-318` is the canonical phase-key list. The brief mentions `tiebreaker_orchestrator` and `tiebreaker_synthesis`; neither exists as routing keys today (see Question 1). Validate against whatever set we settle on.
- JSON is the existing config format (`megaplan/_core/io.py:229`). Profiles use TOML per brief; keep them in a separate file so the main config path is unaffected.
