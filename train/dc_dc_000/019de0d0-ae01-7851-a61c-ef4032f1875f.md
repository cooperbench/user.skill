> AGENT

I compared `planning-bot-spec.md` against the repo as it exists in `/Users/user_c042661f/Documents/arnold-v2`. Short version: the repo is much further along than an early scaffold. It contains implementations for most of sprints 1a through 6, but it is not exact spec parity. The biggest gaps are production architecture mismatch, incomplete callable API surface, Discord image posting, missing attachment passing, missing HTTP/FastAPI layer, missing `set_typing`, and verification not currently runnable in this shell without fixing the Python/test environment.

**Overall Status**
The implementation broadly covers:
- Core `agent_kit` loop, ports, envelope, tool registry, tool audit, SQLite store.
- CLI invocation and Discord resident entry points.
- Supabase store/blob adapters and migrations.
- Editorial body/checklist/history tools.
- Multi-epic routing, message search, response policy, reference resolution.
- Sprint shaping/gating/queue-pend lifecycle.
- GitHub codebase research/cache/artifact tools.
- Image objects, OpenAI image generation, user-upload ingestion.
- Second-opinion flow with OpenAI adapter and scoring parser.

But the actual architecture is more synchronous and library-adapter based than the spec’s “Python 3.12+, FastAPI, asyncpg” architecture. `pyproject.toml` declares Python `>=3.11` and dependencies include `psycopg`, `supabase`, `discord.py`, `groq`, `openai`, `anthropic`, and `httpx`, but not FastAPI/asyncpg: [pyproject.toml](/Users/user_c042661f/Documents/arnold-v2/pyproject.toml:10).

**Major Matches**
- The transport-agnostic loop exists as `run_turn`, with per-epic locking, inbound message creation, hot context, model calls, tool execution, mid-turn checks, envelope return, and external-request ledger recording: [loop.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/loop.py:40).
- The envelope schema is implemented with `completed`, `blocked_on_caller`, `errored`, and `aborted` outcomes, plus `state_delta`, events, questions, and error shape: [envelope.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/envelope.py:17).
- The SQLite migration set creates the core spec tables and adds `epic_locks` for cross-mode concurrency: [001_core.sql](/Users/user_c042661f/Documents/arnold-v2/agent_kit/store/migrations/sqlite/001_core.sql:3).
- Tool audit wrapping is real and transactional around local mutations/tool-call rows, with external effects queued/settled through `external_requests`: [tool_kit.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/tool_kit.py:81).
- Editorial core exists: `create_epic`, `edit_epic`, `revert`, and `render_epic`, including derived title/goal validation and `expected_diff`: [editorial.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/tools/editorial.py:86).
- Body parsing supports `#` title, `##` sections, fenced-code awareness, section editing, outline, search, and unified diffs: [body.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/body.py:29).
- Sprint mode is implemented with server-side gates, lockdown phrase scan, queued/pending checks, pending reasons, PM-handoff fidelity, and force paths in `edit_epic`: [gating.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/gating.py:29).
- Codebase research is implemented with GitHub REST-style tools, cache/artifact support, add/remove/list, tree/file/search/analyze, excerpt saving, and body marking: [code.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/tools/code.py:124).
- Image generation and image object management are implemented, including `generate_image`, reference keys, regeneration deactivation, blob writes, `view_image`, `send_image`, and metadata updates: [images.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/tools/images.py:91).
- Second opinion is implemented with `request_second_opinion`, OpenAI external call, structured parsing, persisted row, proposed checklist items, and low-score metadata: [second_opinion.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/tools/second_opinion.py:41).

**Important Gaps / Mismatches**
- Callable API is incomplete. The CLI has `arnold turn` and `arnold resident`, but no `--attach` support and no HTTP/FastAPI callable API: [cli.py](/Users/user_c042661f/Documents/arnold-v2/arnold/cli.py:23).
- The spec says resident `send_image` posts an actual image file to Discord. The tool passes `files`, but `DiscordTransport.post_message` explicitly discards them with `del files`, so resident image sends currently post only text/caption: [discord.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/transport/discord.py:120).
- Invocation `send_image` is supposed to add an `attached_image` event to the envelope. The actual event enum only allows `tool_call`, `activity`, `turn_start`, and `turn_end`, so this spec behavior is absent: [envelope.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/envelope.py:18).
- `set_typing` is specified but not implemented. `rg` finds no tool registration for it; communication tools are `send_message`, `set_activity`, and `defer_to_caller`.
- Non-whitelisted Discord DM logging differs from acceptance criteria: spec says category `system`; code logs category `application`: [discord.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/transport/discord.py:90).
- Status message formatting is close but not exact. Spec says “Currently:” and final “Done. N tool calls.” Actual uses `Activity:` and counts only the recent tool-call list passed in, which is loaded as the last 3 calls: [resident.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/resident.py:288).
- The spec’s architecture pins Python 3.12+, FastAPI, and asyncpg. Actual package metadata says Python `>=3.11`, has no FastAPI/asyncpg, and uses sync adapters plus `supabase`/`psycopg`: [pyproject.toml](/Users/user_c042661f/Documents/arnold-v2/pyproject.toml:10).
- `defer_to_caller` is supposed to be invocation-only and resident-mode error/no-op. The tool exists, but I did not see mode enforcement in the loop/tool registry itself; it likely depends on tool implementation behavior.
- The read-tool list is not exact. Actual has `get_epic`, `get_section_names`, `get_body_outline`, `search_in_body`, `get_history`, `get_epic_at_time`, `get_recent_turns`, `search_tool_calls`, `list_epics`, `search_epics`, `search_messages`; I did not see separate `get_checklist`, `get_sprints`, or `recent_messages` tools, though `get_epic` includes sprints and hot context includes recent messages: [editorial_reads.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/tools/editorial_reads.py:120).
- The SQLite migrations have two files numbered `008`: `008_codebase_research.sql` and `008_second_opinions.sql`. The loader sorts by filename and records by name, so it may work, but the numbering is sloppy and differs from the Supabase sequence, where second opinions is `008` and codebase research is `009`: [sqlite.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/store/sqlite.py:60).
- The external request idempotency formula intentionally diverges from the spec for system/model calls by adding `system_seq`; the code comments call this out as a deliberate extension: [ledger.py](/Users/user_c042661f/Documents/arnold-v2/agent_kit/ledger.py:1).

**Bottom Line**
This repo is a substantial implementation of the spec, roughly covering sprints 1a-6 in breadth. It is not production-spec-complete. The highest-priority parity fixes are: install/use the correct test environment, implement actual Discord file upload for `send_image`, add CLI attachment passing, add or explicitly drop the HTTP/FastAPI callable API, implement `set_typing`, align status/whitelist behavior with acceptance criteria, and resolve the missing exact read tools or document their consolidation into `get_epic`/hot context.
