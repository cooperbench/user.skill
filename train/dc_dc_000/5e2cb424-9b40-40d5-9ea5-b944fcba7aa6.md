1127	    <h2 class="section-heading">Key Findings</h2>
1128	    <ul class="body-list">
1129	        <li><strong>Different models for different steps.</strong> Using the same model for every phase reinforces blind spots. When we split planning (GLM-5.1) and critique (MiniMax-M2.7) across different model families, the critique model consistently caught issues the planning model was blind to \u2014 particularly around edge cases and API misuse. Using Qwen 3.5 for all phases including critique produced a 50% pass rate vs 81% with the split approach.</li>
1130	        <li><strong>Separate detection from judgment.</strong> Early critique versions let the model explain away concerns ("this diverges from the hint but seems fine"). In one concrete case, the critique identified the wrong API being used <em>twice</em> but didn't flag it because it rationalised the divergence. Telling the model to flag any difference and letting a downstream gate decide acceptability fixed this class of failure entirely.</li>
1131	        <li><strong>Template files over freeform JSON.</strong> MiniMax-M2.7 had a 75% failure rate producing structured JSON as its final text response. Writing a template file to disk and having the model fill it in via tool calls dropped failures to near zero. The same model that couldn't emit valid JSON could reliably read, modify, and write files.</li>
1132	        <li><strong>Formatting and tool-use failures can likely be fine-tuned away.</strong> A significant portion of our retry cost comes from models producing malformed output or misusing tools \u2014 not from getting the actual task wrong. These are systematic, predictable failure modes that feel almost certain to respond well to targeted fine-tuning. Models fine-tuned for structured output adherence and reliable tool execution within a harness like this would likely see substantially higher first-pass success rates.</li>
1133	        <li><strong>Deterministic overrides can deadlock LLM pipelines.</strong> The orchestrator was overriding the gate's PROCEED decision whenever blocking flags remained, forcing infinite critique\u2192revise loops. Some flags were structurally unresolvable (referencing tests injected by the eval harness). The gate LLM correctly judged these as acceptable tradeoffs, but the handler's mechanical flag-count check overruled it every time. The fix: trust the LLM's informed decision over deterministic heuristics.</li>
1134	        <li><strong>Multi-agent handoff interfaces are a rich bug source.</strong> The critique-gate interface went through five rounds of debugging: findings not reaching the gate, flag ID collisions, status lookup keyed on the wrong field, resolution data not wired through the artifact, severity defaults creating spurious blockers. Schema correctness does not guarantee wiring correctness.</li>
1135	        <li><strong>Scoring infrastructure needs its own reliability engineering.</strong> "Did the test fail or did the scorer fail?" must be answerable with evidence. Our scorer grew to 772 lines with auto-restart, 12 error categories, exponential backoff, and a structured human review framework \u2014 because scoring ambiguity turned out to be a bigger source of noise than model quality.</li>
1136	    </ul>
