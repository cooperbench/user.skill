        # Implementation Plan: VibeComfy Template Porting Workbench

## Overview
VibeComfy already has the raw pieces of a template-porting workflow: `convert`, `validate`, `doctor`, schema-backed validation, model asset extraction, node pack install planning, generated ready-template rendering in `tools/format_as_python.py`, and WanAnimate-specific regression tests. The first useful slice should not be a separate app or a raw JSON runner. It should promote these scattered checks into a first-class CLI/tooling path that imports a Comfy workflow, emits a Python VibeWorkflow scratchpad/ready-template, preserves provenance, and reports the failures that currently cost RunPod time: missing node packs, bad/missing model URLs, unresolved helper nodes, positional widget alias drift, and missing required schema inputs.

The simplest approach is to build a package-level `vibecomfy.porting` workbench and a `vibecomfy port ...` CLI command that reuses existing code rather than inventing a second converter. `tools/format_as_python.py` is the current best emitter, but because it lives under `tools/`, the reusable core should move into package modules while the old tool remains as a thin compatibility driver.

## Phase 1: Foundation — Shared Port Report and Python Emission

### Step 1: Add a porting report model (`vibecomfy/porting/report.py`)
**Scope:** Medium
1. Define small dataclasses for `PortReport`, `PortIssue`, `PortArtifact`, and `AssetCheckResult` with stable JSON serialization.
2. Include fields for source path/id, detected workflow shape, source hash, normalized API node count, emitted Python path, custom-node pack suggestions, unresolved class types, model assets, schema issues, helper-node rewrites, and widget alias observations.
3. Keep issue severities aligned with existing validation semantics: `error`, `warning`, `info`.

### Step 2: Move reusable emitter logic into package code (`vibecomfy/porting/emitter.py`, `tools/format_as_python.py`)
**Scope:** Medium
1. Extract the reusable portions of `tools/format_as_python.py` into package code, preserving deterministic output, explicit node IDs, `_node(...)` helper behavior, `_extras` for non-identifier inputs, and `READY_METADATA` / `READY_REQUIREMENTS` emission.
2. Keep `tools/format_as_python.py` and `tools/convert_ready_templates.py` as wrappers around the package API so existing workflows still work.
3. Reuse `tools/_widget_schema.py` by moving it to `vibecomfy/porting/widget_schema.py` or exposing a package import path, then update old tool imports.

### Step 3: Add a workbench orchestrator (`vibecomfy/porting/workbench.py`)
**Scope:** Medium
1. Implement `analyze_source(...)` to load a workflow via `load_workflow_json`, `normalize_to_api`, and `convert_to_vibe_format`, using `get_schema_provider("auto")` when available.
2. Implement `emit_python_scratchpad(...)` that writes a Python-esque VibeWorkflow scratchpad, not a wrapper that re-loads the original JSON at runtime.
3. Preserve provenance in `READY_METADATA`: source path/id, source hash, original shape, conversion timestamp or converter version, source workflow id when known, and whether schema was available.
4. Populate `READY_REQUIREMENTS` from inferred requirements plus extracted structured model assets.

## Phase 2: Diagnostics — Catch Current Failure Classes Before RunPod

### Step 4: Custom node pack inference (`vibecomfy/porting/workbench.py`, `vibecomfy/node_packs_install.py`)
**Scope:** Small
1. Reuse `missing_class_types_for_workflow(...)` and `missing_packs_for_workflow(...)` to report installable packs and unresolved class types.
2. Include pack repo, pip packages, and matched classes in the port report.
3. Surface unresolved classes as hard errors for `port check` and warnings for `port convert --allow-unresolved`.

### Step 5: Model asset inference and HEAD checks (`vibecomfy/model_assets.py`, `vibecomfy/porting/assets.py`)
**Scope:** Medium
1. Reuse `extract_from_raw_workflow(...)` and `entries_from_scratchpad_path(...)` to collect structured model assets.
2. Add an opt-in URL checker using `httpx.Client().head(..., follow_redirects=True)` with deterministic timeout and no download body.
3. Report status codes, redirected final URL, missing URL fields, duplicate asset targets, and license-gated/404 cases as actionable report entries.
4. Keep HEAD checks disabled in normal unit tests and local conversion unless `--head-check-models` is passed.

### Step 6: Helper-node resolution diagnostics (`vibecomfy/workflow.py`, `vibecomfy/porting/workbench.py`)
**Scope:** Medium
1. Keep existing compile-time stripping/rewriting for `Note`, `MarkdownNote`, `SetNode`, and `GetNode`.
2. Add a report pass that counts removed UI-only nodes and lists unresolved `GetNode` / `SetNode` references whose broadcast source cannot be resolved.
3. Treat dangling helper rewrites as `error` because they create links to absent runtime nodes.
4. Add a narrow helper classification extension point for future reroute/broadcast nodes without changing runtime compile behavior for unknown classes.

### Step 7: Positional widget alias detection (`vibecomfy/porting/widget_aliases.py`, `vibecomfy/ingest/normalize.py`, `vibecomfy/workflow.py`)
**Scope:** Large
1. Centralize positional widget alias logic so `normalize_to_api`, `VibeWorkflow.compile`, and the Python emitter use the same mapping source.
2. Prefer schema-derived input order from `object_info` when available; fall back to the committed static widget schema for offline operation.
3. Add a diagnostic pass that compiles the workflow, compares emitted input names against schema inputs, and reports unresolved `widget_N` inputs where a required named input is missing.
4. Move the existing Wan/WanAnimate aliases out of the private `_POSITIONAL_WIDGET_ALIASES` map in `workflow.py` into the shared module, preserving current behavior.

### Step 8: Schema preflight integration (`vibecomfy/schema/validate.py`, `vibecomfy/commands/validate.py`, `vibecomfy/commands/doctor.py`)
**Scope:** Medium
1. Reuse existing `missing_required_input`, `unknown_input`, `unknown_class_type`, `invalid_link_shape`, and type mismatch checks in the port report.
2. Add optional `--port-report` or shared formatter support so `validate` / `doctor` can show the same actionable categories without duplicating logic.
3. Keep `validate` focused and cheap; make the fuller workbench report the new `port check` path.

## Phase 3: CLI and Live Validation Loop

### Step 9: Add explicit CLI entry points (`vibecomfy/commands/port.py`, `vibecomfy/commands/__init__.py`)
**Scope:** Medium
1. Register a new explicit command module in `COMMANDS`.
2. Add `python -m vibecomfy.cli port check <workflow> [--json] [--head-check-models]` to analyze without writing.
3. Add `python -m vibecomfy.cli port convert <workflow> --out out/scratchpads/name.py [--json] [--head-check-models]` to emit Python and include the report.
4. Add `--ready-id kind/name` for users intentionally creating a ready-template-shaped module under `ready_templates/`.
5. Return nonzero for hard errors: unresolved class types, unresolved helper broadcasts, schema-required missing inputs, failed Python build, or failed emitted scratchpad validation.

### Step 10: Wire into the run/RunPod preflight (`vibecomfy/commands/run.py`, `scripts/runpod_corpus_matrix.py`)
**Scope:** Medium
1. Before queueing a workflow, keep existing `workflow.validate(schema_provider=...)` as the hard gate.
2. Add a cheap port-report summary to `doctor` and RunPod matrix logs so future failures show whether they are model URL, custom-node, schema, or helper-node problems.
3. Do not make network HEAD checks mandatory for `run`; keep them opt-in via `port check --head-check-models` and in targeted preflight jobs.
4. In RunPod corpus matrix logs, copy the emitted scratchpad and port report next to the existing convert/validate logs.

## Phase 4: Battle Tests and Documentation

### Step 11: Add focused unit and CLI tests (`tests/test_porting_workbench.py`, `tests/test_cli.py`, `tests/test_workflow_core.py`, `tests/test_schema.py`)
**Scope:** Medium
1. Test a simple fixture based on `image/z_image` or a tiny synthetic workflow: check report shape, provenance, Python emission, import/build, compile, and validate.
2. Test the current WanAnimate production-parity template id `video/wanvideo_wrapper_22_wan_animate_preprocess_kijai`: helper nodes must not survive compiled API, no dangling links to removed nodes, node packs include WanAnimate/SAM/KJ/VHS requirements, and model assets include detection assets.
3. Test positional widget alias diagnostics with a fake schema provider so no Comfy runtime is required.
4. Test model HEAD checks with `httpx.MockTransport` or injected client behavior, not real network.
5. Add CLI smoke tests for `port check --json` and `port convert --out ... --json`.

### Step 12: Document the first slice and roadmap (`docs/template_porting_workbench.md`, `docs/adding_templates_models.md`)
**Scope:** Small
1. Document the new import → convert → check → validate loop.
2. Show the recommended commands for a source workflow, a generated scratchpad, a ready-template candidate, and the WanAnimate battle test.
3. Record the remaining roadmap: richer source discovery, broader helper-node catalog, schema snapshots per node-pack version, automatic PR-ready manifest edits, and optional CI job for URL HEAD checks.

## Execution Order
1. Create the report model and package emitter first so the CLI can be thin.

3. Add `port convert` after emitted Python can import/build/validate in tests.
4. Add optional network HEAD checks only after offline report behavior is stable.
5. Wire `doctor` / RunPod logs after the report shape is settled.
6. Finish with docs and the WanAnimate regression path.

## Phase 1: Foundation - Report Shape, Source Loading, and Helper Semantics

### Step 1: Add a porting report model (`vibecomfy/porting/report.py`)
**Scope:** Medium

2. Include source id/path, detected workflow shape, source hash, normalized API node count, emitted Python path, output mode (`scratchpad` or `ready_template`), helper-node diagnostics, custom-node suggestions, unresolved runtime class types, model asset candidates, schema issues, widget alias observations, and recommended next commands.

### Step 2: Centralize helper/UI-node classification (`vibecomfy/porting/helpers.py`, `vibecomfy/workflow.py`)
**Scope:** Medium

**Scope:** Medium
