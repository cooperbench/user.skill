1. Add a general `agent_task` scheduled job type.
2. Store its brief in `scheduled_jobs.context`, for example:

   run_agentic_job(user, {

   ```text
   Trigger: kind=scheduled_task.

   ```
5. The loop remains the same two-phase loop:
   - Phase A: read context and optionally send user-facing output.
   - Phase B: write memories/observations/watch items/scheduled tasks/etc.

    "every": 3,

}

Scheduled task = give the agent a brief later.

> DEVELOPER

So can you tell definitively when a step has just stopped writing, you know, so it's stopped doing tool calls or stopped doing stuff? And is that like a reliable signal that something's gone wrong? How would we implement this into a pipeline?

> AGENT

Yes, you can tell definitively that a step has stopped writing **to the streams you observe**. You cannot prove the model/provider is doing no internal work, but for pipeline reliability that distinction usually does not matter after a threshold.

The reliable signal is:

```text
last_observed_activity_at
```

Update it whenever the worker emits any of:

- stdout/stderr bytes
- structured tool progress events
- tool call start/finish
- model stream delta / thinking delta, if exposed
- artifact file write/update
- heartbeat message from the worker

Then classify:

```text
running + recent activity = healthy
running + no activity for N seconds = idle
idle past hard threshold = wedged or too slow to trust
process exited + no final artifact = failed
process exited + final artifact = completed
```

It is not a perfect “something is wrong” signal. Some valid tasks have long quiet periods: a big test suite, a long compile, a slow provider response, or a model thinking silently without streaming. But it is a very good **operational liveness** signal if thresholds are phase-specific.

Implementation shape:

```python
@dataclass
class StepAttempt:
    step: str
    pid: int
    started_at: datetime
    last_activity_at: datetime
    last_activity_kind: str
    status: Literal["running", "idle", "stale", "failed", "completed"]
```

Wrap every worker subprocess with an activity monitor:

```python
async def run_step(cmd):
    proc = await asyncio.create_subprocess_exec(
        *cmd,
        stdout=PIPE,
        stderr=PIPE,
    )

    activity = ActivityState(now())

    async def read_stream(stream, name):
        while chunk := await stream.read(4096):
            activity.touch(kind=name)
            forward(chunk)

    async def watchdog():
        while proc.returncode is None:
            idle_s = (now() - activity.last_activity_at).total_seconds()

            if idle_s > HARD_IDLE_SECONDS:
                proc.terminate()
                await sleep(KILL_GRACE_SECONDS)
                if proc.returncode is None:
                    proc.kill()
                raise IdleTimeout(idle_s)

            await sleep(5)

    await gather(read_stream(proc.stdout, "stdout"),
                 read_stream(proc.stderr, "stderr"),
                 watchdog())
```

Better version: workers should emit explicit heartbeat events even during long non-streaming calls:

```json
{"event":"heartbeat","phase":"critique","waiting_on":"provider","elapsed_s":420}
```

Then the watchdog distinguishes:

```text
no bytes at all for 10 minutes = likely wedged
heartbeats but no model output = provider/model slow
tool running with heartbeat = tool slow, maybe okay
```

Pipeline policy should be step-aware:

```text
plan/critique/revise/finalize:
  soft idle: 3 min
  hard idle: 10 min
  retry same model once
  then fallback model

execute:
  soft idle: 5 min
  hard idle: 20-30 min
  require child tool heartbeat for long tests/builds

review:
  soft idle: 3 min
  hard idle: 10 min
```

Recovery policy:

```text
attempt 1 idle timeout:
  mark attempt failed_idle
  rerun same step same model

attempt 2 same model idle timeout:
  reroute to configured fallback model

fallback idle timeout:
  stop and surface blocker
```

For your exact stuck critic, this would have produced:

```text

fallback: rerun critique with codex:medium
```

So yes: “stopped writing” is measurable and useful. It should not be treated as instant proof of failure, but it should absolutely drive timeout, retry, fallback, and audit behavior in the pipeline.

> DEVELOPER

So what's a good generalised way to handle this?

> AGENT

A good generalized approach is to treat every pipeline step as a **supervised attempt** with three independent signals:

```text
1. process state: running/exited
2. output activity: last byte/event/artifact write
3. semantic completion: expected artifact exists and validates
```

Then recovery is policy-driven, not ad hoc.

**Core Model**
Each step attempt should write a small state record:

```json
{
  "step": "critique",
  "attempt": 2,
  "model": "hermes:moonshotai/kimi-k2.6",
  "status": "running",
  "started_at": "...",
  "last_activity_at": "...",
  "last_activity_kind": "tool_result",
  "expected_artifacts": ["critique_v1.json"],
  "recovery_policy": "critique_default"
}
```

Activity means any observable forward motion: stdout/stderr, structured tool event, model stream chunk, heartbeat, or artifact update.

**Health States**

```text
healthy: running and recent activity
quiet: running, no activity past soft threshold
stale: running, no activity past hard threshold
orphaned: state says running but no process/lock owns it
failed: process exited without valid artifact
completed: process exited and artifact validates
```

**Recovery Ladder**
Use the same ladder for all phases, with per-phase thresholds:

```text
1. Wait while healthy.
2. Warn/mark quiet after soft idle.
3. Gracefully interrupt after hard idle.
4. Kill after grace period.
5. Mark attempt as failed_idle.
6. Retry same step once with same model.
7. If same failure repeats, reroute to fallback model.
8. If fallback fails, stop with a clear blocker.
```

The fallback should be explicit in config:

```toml
[recovery.critique]
soft_idle_seconds = 180
hard_idle_seconds = 600
kill_grace_seconds = 30
same_model_retries = 1
fallbacks = ["codex:medium", "claude"]

[recovery.execute]
soft_idle_seconds = 300
hard_idle_seconds = 1800
same_model_retries = 0
fallbacks = []
```

**Important Detail**
Silent work can be legitimate, especially during long tests or provider calls. So workers should emit heartbeats:

```json
{"event":"heartbeat","step":"critique","waiting_on":"model","elapsed_s":420}
```

That converts “no visible output” into “known wait state.” The watchdog can then use different thresholds for:

```text
no output, no heartbeat: suspicious
heartbeat waiting_on=model: provider slow
heartbeat waiting_on=tool: tool slow
artifact updating: healthy
```

**Completion Rule**
Never trust process exit alone. A step is complete only when its expected artifact exists and validates against schema. This prevents “model printed something but didn’t produce usable JSON” from poisoning the pipeline.

**For Megaplan Specifically**
I’d add:

- Per-attempt `last_activity_at`
- Stream/activity watchdog in the subprocess runner
- Structured `attempt_failure.json`
- Configured phase fallback models
- Automatic stale retry/fallback before requiring human intervention
- Status output that says exactly:
  ```text
  critique attempt 2 idle_timeout after 612s without output;
  rerouting from kimi-k2.6 to codex:medium
  ```

That gives you a general mechanism that handles hung model calls, bad tool loops, silent subprocesses, orphaned locks, and malformed artifacts without special-casing this Kimi critic failure.

Yes, the actual `.megaplan` data supports the approach, with one adjustment: Megaplan already has **coarse stale/orphan detection**, but it lacks **durable activity detection**.

What exists today:
- `state.json` has `active_step.started_at`, `step`, `agent`, `run_id`, optional `model`.
- `status` computes useful runtime health like `lock_held`, `stale`, `orphaned`, `recommended_action`.
- `history[]` records completed/failed phase results, `duration_ms`, output artifact, raw output file, error message.
- `.plan.lock` exists for many plans, so existence is meaningless; held-ness via `fcntl` is the real signal.
- `execution_trace.jsonl` has rich event streams for execute phases, but generally lacks timestamps per event.

What does not exist:
- No reliable persisted `last_activity_at`.
- No clean per-output stream activity ledger for plan/critique/revise/finalize.
- No consistent failed-attempt artifact for hung/stale attempts.
- No enough data to distinguish:
  ```text
  alive and actively streaming
  alive but waiting on provider
  alive but wedged
  process gone but active_step left behind
  ```

Concrete local examples:
- `implement-general-agent-20260505-1941`: `active_step=critique`, stale/orphaned after Kimi hung.
- `implement-general-agent-20260505-1938`: stale `active_step=plan`, no lock held.
- `implement-the-simplest-20260502-1531`: stale `active_step=execute`, no lock held.
- `implement-a-human-like-20260501-1604`: history has blocked/error attempts, including invalid JSON review failures.

So the generalized recovery design is valid, but should be implemented as an extension to the current model, not a replacement.

The pipeline should use three signals:

```text
1. active_step.started_at: wall-clock age
2. active_step.last_activity_at: output/activity idle age
3. lock/process/artifact validity: ownership and semantic completion
```

And recovery should be:

```text
if lock not held + active_step old:
  mark orphaned, clear or rerun same step

if lock held + last_activity_at too old:
  mark idle/stale, terminate after grace

if same model idles twice:
  reroute using persisted config.phase_model override, not profile re-resolution

if process exits but artifact missing/invalid:
  record failed_attempt and retry/fallback based on policy
```

The important caveat from the data: don’t parse giant execution batch payloads deeply for liveness. Use top-level event appends, artifact mtimes, and explicit activity touches. For execute, `execution_trace.jsonl` is the right place to add timestamps; for critique/plan/finalize, the runner needs to touch `active_step.last_activity_at` whenever it forwards stream output or writes raw/model output.
