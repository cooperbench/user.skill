The pack abstraction is coherent only at the namespace/layout level, not as an installable extension boundary. `discover_packs()` only scans immediate children of the repo-local `astrid/packs` directory and requires `pack.id == folder name` [astrid/core/pack.py:43]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/pack.py:43), [astrid/core/pack.py:47]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/pack.py:47), [astrid/core/pack.py:74]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/pack.py:74). There is no search path, entry point, package registry, or external pack install command in the runtime path. A third party installs a new pack today by putting a folder inside this repo, realistically by forking or vendoring into `astrid/packs`. `pack.yaml` is doing a small but real job: it marks discoverable roots, gives the id/name/version, and enforces namespace ownership. Registries validate that `builtin.foo` lives in pack `builtin` before registration [astrid/core/orchestrator/registry.py:144]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/orchestrator/registry.py:144), [astrid/core/orchestrator/registry.py:147]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/orchestrator/registry.py:147). But the six manifests are just id/name/version, no capabilities, dependencies, compatibility, import roots, asset roots, or author/install metadata. So it is closer to a namespace marker than a package manifest. `rglob` inside a pack is defensible for authoring ergonomics, but too loose for a stable plugin boundary. Executors/orchestrators are found by any matching manifest anywhere except hard-coded excluded parts [astrid/core/pack.py:125]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/pack.py:125), [astrid/core/pack.py:146]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/pack.py:146). That makes layout forgiving, but discovery semantics become accidental. A stray fixture `orchestrator.yaml` can become product surface unless excluded. For packs meant to be installed by others, explicit top-level indexes or declared content roots would age better. The migration is visibly half-done. Folder orchestrators support both manifests and `orchestrator.py` extraction [astrid/core/orchestrator/folder.py:34]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/orchestrator/folder.py:34), [astrid/core/orchestrator/folder.py:61]( /Users/user_c042661f/Documents/reigh-workspace/Astrid/astrid/core/orchestrator/folder.py:61). Same id, two resolution systems, different behavior. Taxonomy is partly defensible but leaky. `external` is runtime-boundary based; `upload` is destination based; `iteration` is workflow-domain based; `seinfeld` is project-specific; `builtin` is a junk drawer.
