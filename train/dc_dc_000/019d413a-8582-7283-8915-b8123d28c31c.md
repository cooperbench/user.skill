        # Implementation Plan: Finalize Self-Validation & Structured Review Rework Items

## Overview

The megaplan pipeline's handoff quality between finalize→execute→review has two gaps:

1. **Finalize phase** produces task lists but never self-validates them — no check that all plan tasks are covered, no mechanical verification that required fields are populated meaningfully, and no detection of orphan tasks (tasks in finalize that don't appear in the plan).

2. **Review phase** captures issues as flat `string[]`, losing the task-level association and evidence linkage that `_inject_feedback()` needs to produce actionable rework notes. The current feedback injection truncates issues to 60 chars each.

**Repo shape:** Schemas live at `.megaplan/schemas/`. The megaplan CLI binary owns the phase prompts (not editable here), but the schemas control the structured output the LLM must produce. `_inject_feedback()` in `evals/run_evals.py:358-390` processes review responses for rework cycles.

**Constraint:** We can't edit megaplan's internal prompts, only the schemas and `run_evals.py`. The schemas themselves serve as implicit prompt engineering — the field names, descriptions, and structure guide the LLM's output.

## Phase 1: Schema Changes

### Step 1: Add `validation` field to finalize schema (`.megaplan/schemas/finalize.json`)

**Scope:** Medium

1. **Add** a new `validation` object to the `properties` of the finalize schema, containing:
   - `plan_coverage` (array of objects): Each entry maps `{plan_task_id, finalize_task_id, status}` — forces the LLM to explicitly map every plan task to a finalize task.
   - `mechanical_checks` (array of objects): Each entry is `{task_id, check, result, detail}` — forces per-task checks like "files_changed is non-empty for done tasks", "evidence_files exist for done tasks".
   - `orphan_tasks` (array of strings): Task IDs in finalize that don't correspond to any plan task. Should normally be empty; forces explicit acknowledgment.
   - `coverage_complete` (boolean): Explicit assertion that all plan tasks are accounted for.

2. **Add** `validation` to the `required` array.

3. **Design rationale for anti-rubber-stamping:** The key to making self-checks meaningful is forcing *enumeration* rather than *assertion*. The LLM must list each plan task and its corresponding finalize task (not just say "all covered"). The `mechanical_checks` array forces per-task evidence rather than a single "all good" boolean. Field names are chosen to be self-documenting since we can't edit the prompts.

### Step 2: Add `rework_items` to review schema (`.megaplan/schemas/review.json`)

**Scope:** Medium

1. **Add** a new `rework_items` array to the `properties`, with items being objects:
   - `task_id` (string, required): Which finalize task this issue relates to
   - `issue` (string, required): What's wrong
   - `expected` (string, required): What correct behavior looks like
   - `actual` (string, required): What was observed
   - `evidence_file` (string): File path supporting the finding

2. **Keep** `issues` in the schema for backward compatibility but remove it from `required`. Add a `description` or `deprecated` note in the field (JSON Schema supports `description`).

3. **Add** `rework_items` to the `required` array.

## Phase 2: Feedback Injection Update

### Step 3: Update `_inject_feedback()` to format structured rework items (`evals/run_evals.py:358-390`)

**Scope:** Medium

1. **Add** handling for the `rework_items` key in the response dict (lines 371-374 area). When `rework_items` is present and non-empty, format each item as a structured block:
   ```
   [rework] task: {task_id}
     issue: {issue}
     expected: {expected}
     actual: {actual}
     evidence: {evidence_file}
   ```

2. **Fall back** to the existing `issues` string handling when `rework_items` is absent (backward compat with older review outputs).

3. **Increase** the per-item truncation from 60 chars to something more useful (200 chars per field) since the structured format gives better signal.

### Step 4: Validate the changes with existing tests (`tests/`)

**Scope:** Small

1. **Check** for existing tests that exercise `_inject_feedback()` or the schema files.
2. **Run** any existing test suite to verify nothing breaks.
3. **Add** a unit test for the new `_inject_feedback()` structured rework formatting if no coverage exists — test that when `rework_items` is present, the formatted note contains all structured fields, and when only `issues` is present, the old behavior is preserved.

## Overview

The megaplan pipeline's handoff quality between finalize→execute→review has two gaps:

1. **Finalize phase** produces task lists but never self-validates — no check that plan steps map to finalize tasks, no structural completeness checks, no orphan detection.

2. **Review phase** captures issues as flat `string[]`, losing task-level association and evidence linkage needed for actionable rework notes.

**Critical architectural correction from v1:** The `.megaplan/schemas/*.json` files in the project directory are **generated artifacts** — `_core.py:287-293` overwrites them from the internal `SCHEMAS` dict on every runtime layout setup. The actual source of truth is the `megaplan` package itself:

- **Schema definitions:** `../megaplan/megaplan/schemas.py` (internal `SCHEMAS` dict)
- **Prompt builders:** `../megaplan/megaplan/prompts.py` (finalize: ~870-928, review: ~1273-1439)
- **Worker validation & mocks:** `../megaplan/megaplan/workers.py` (required-key checks: ~60-63, ~219-225; mock payloads: ~436-479, ~553-579)
- **Handler responses:** `../megaplan/megaplan/handlers.py` (finalize: ~1299-1303; review response forwarding: ~1417-1526)
