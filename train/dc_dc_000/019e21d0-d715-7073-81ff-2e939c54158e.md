> AGENT

v5 did not cut too much. It is structurally ready for Phase 1, but I would not start Day 1 until four doc-level fixes are made.

Dropping `search_result_id` is correct. The old/current system already proves that self-attested gates rot: [live_update_prompts.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_prompts.py:292) spends pages telling the model not to mix JSON/tool/final turns, and [live_update_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_editor.py:1816) still has to re-check duplicate state, confidence, checklist fields, and substance. A `search_result_id` requirement would become another ritual. The substantive invariant belongs where v5 puts it: every `post_simple_topic`, `post_sectioned_topic`, and `watch_topic` write runs canonical-key/alias/similarity detection server-side.

But v5 needs one missing mechanism: a collision override path. If the dispatcher returns “possible match” as a tool error, the agent needs a typed way to say “false positive, create new topic anyway” with `ignored_collision_topic_ids` and `reason`, logged to `topic_transitions`. Without that, similarity false positives can trap the agent in retry loops. Conversely, false negatives remain possible, so Phase 1 must explicitly test adversarial near-duplicates, not only slug drift.

Folding `topic_publications` into `topics` is acceptable for Phase 1 and probably production at current volume. The real loss is incident forensics, not normal operation. Scenario: a sectioned topic sends header + two section messages, fails on the third, retries later, and Discord/rate-limit behavior creates duplicate or missing live messages. With only `publication_status`, `publication_error`, `discord_message_ids`, `publication_attempts`, and `last_published_at` on `topics`, you know the final/latest state but not the per-attempt sequence: which attempt sent which IDs, which exception happened before/after DB persistence, whether retry resumed or duplicated. That bites during a publishing incident. It does not justify keeping a sixth table before shadow mode. Add a clear rule: if partial-publish incidents happen twice, restore `topic_publications`.

The 5-table surface is coherent, but the doc has schema bugs. `topic_transitions` defines no `environment` or `guild_id`, then creates `transitions_action_idx ON topic_transitions (environment, action)` at [docs/live-update-editor-redesign.md](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/live-update-editor-redesign.md:164). That migration will fail. Also, v5 says rejected tool calls are captured in `topic_transitions.payload`, but `topic_id` is `NOT NULL`; a rejected create may not have a topic yet. Fix by adding `environment`, `guild_id`, nullable `topic_id`, and `status`/`error_kind` or by introducing a separate tool-call log. I prefer nullable `topic_id` plus `action='rejected_*'`.

The “9-tool” surface is also internally inconsistent: v5 lists 4 read tools plus 6 decision/decision-adjacent tools, including `record_observation`, at [docs/live-update-editor-redesign.md](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/live-update-editor-redesign.md:256). That is 10 tools. Either count it honestly or make `record_observation` dispatcher-side only. I would keep it as a tool and call the surface 10 tools.

The two “lock before Day 1” decisions are necessary but incomplete. Canonicalizer and observation retention belong there. Add three more: collision threshold/override semantics, transition logging schema for rejected calls, and `defer` audit result. The current production code treats `defer` as real via low confidence and explicit agent defer at [live_update_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_editor.py:1835). If prod has meaningful deferred rows, `pending_review` is not v2; it is Day 1 schema.

The Phase 1 shadow plan is realistic only as a focused vertical slice, not a polished replacement. One week can build schema, tool-use loop, pure renderer, trace embeds, and replay 20 windows. What pushes it to two or three weeks: native Anthropic tool-use integration through the existing wrapper, Supabase migration friction, canonicalizer tuning, trace UX, run lease/checkpoint behavior, and comparing against today’s editor when today’s output is itself noisy. Publishing off is the right constraint.

New v5 footguns from simplification: write-time collision errors need override semantics; `record_observation` is optional enough that “why didn’t it post X?” visibility may be sparse; `topic_sources UNIQUE (environment, guild_id, message_id)` forbids one message from supporting both a parent topic and a later update; and folded publication state weakens retry forensics.

Verdict: build v5. Fix the schema inconsistencies and collision override before Day 1. Do not bring back `search_result_id` or `topic_publications` yet.
