        # Implementation Plan: Fix Three Editor Pane Issues

## Overview

The editor pane (top-side `PaneControlTab` + `EditorPaneTab`) has three bugs:

1. **Pane stays locked when navigating to `/tools/video-editor`** — `EditorPaneTab` returns `null` on that route (line 74), but the lock persists in DB, so the pane reappears locked on navigation away.
2. **Content shifts down when editor pane locks** — `LayoutMainContent.tsx:40` applies `paddingTop: effectiveEditorPaneHeight` when editor pane is locked, pushing content down. The editor pane is `position:fixed` and should overlay content.
3. **Editor takes 90% of viewport even when generations pane is also locked** — `PanesContext.tsx:141` sets `editorPaneHeight = viewportHeight * 0.9` unconditionally. When both are locked, the editor should target 70%.

**Critical height-chain issue (flag step_3):** The effective height flows through two layers that both reduce for generations presence:
- `PanesContext.getEffectivePaneHeights()` compresses editor height to make room for generations (always, regardless of visibility)
- `EditorPaneTab:42-43` then subtracts `effectiveGenerationsPaneHeight` again

This double-subtraction means simply changing the ideal from 90% to 70% in PanesContext won't produce a 70% rendered pane. The fix: make `getEffectivePaneHeights` visibility-aware (only compress when both panes are actually visible) and remove the secondary subtraction in EditorPaneTab.

Key files:
- `src/shared/contexts/PanesContext.tsx` — height calculation + visibility gating
- `src/app/components/LayoutMainContent.tsx` — content shift styles
- `src/app/components/LayoutMainContent.test.tsx` — content shift test assertions
- `src/features/editor/components/EditorPaneTab.tsx` — editor pane component + route-unlock effect
- `src/shared/contexts/__tests__/PanesContext.test.tsx` — height calculation tests
