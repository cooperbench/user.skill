        # Implementation Plan: Cross-Thread Sharing Default Privacy Boundary

## Overview
The repo already has draft plumbing for `cross_thread_sharing_default`: migration `migrations/0012_cross_thread_sharing.sql`, `User.cross_thread_sharing_default`, prompt guidance in `app/services/prompts.py:187`, schema/tool registry entries, and `write_tools.update_cross_thread_sharing_default`. The missing shippable piece is enforcement: `search_messages` currently searches raw messages broadly, `recent_activity` includes every user's latest raw content, and hot context renders partner-side free-text fields without a clear privacy gate.

The simplest pass should not add `bridge_candidates`. It should add a small shared privacy helper and use it in hot context plus `search_messages` / `recent_activity`, with focused tests.

## Main Phase

### Step 1: Confirm Existing Draft Surface
**Scope:** Small
1. Verify the migration defaults users to `NULL` and constrains values to `opt_in` / `opt_out` (`migrations/0012_cross_thread_sharing.sql:1`).
2. Keep the existing write tool contract and tests unless implementation details are broken (`app/services/tools/write_tools.py:155`, `tests/test_tools.py:199`).
3. Keep the prompt text as the starting point, but make hot context more prominent for unset state instead of relying only on generic system instructions (`app/services/prompts.py:187`).

### Step 2: Add A Tiny Privacy Helper
**Scope:** Small
1. Add a focused helper module, likely `app/services/cross_thread_privacy.py`, with two concepts only:
   - `sharing_default(value) -> "unset" | "opt_in" | "opt_out"`
   - `can_expose_raw_to_viewer(owner_user_id, viewer_user_id, owner_default)`, true for the current user's own thread and for partner material only when the owner is `opt_in`.
2. Use a single redaction string for blocked raw text, e.g. `[private by default; user has not opted into cross-thread sharing]`, so tests can assert no raw leakage.
3. Do not introduce candidate tables, provenance systems, semantic classifiers, or new audit tables in this pass.

### Step 3: Filter Hot Context (`app/services/hot_context.py`)
**Scope:** Medium
1. Make unset state prominent in rendered hot context near the user profile section (`app/services/hot_context.py:310`): add a short `## Sharing defaults` section showing both defaults and a direct note when the current user is `unset`.
2. Treat partner-owned free text as bridge-private unless the partner is `opt_in`:
   - partner `style_notes` in the `Your Partner` block (`app/services/hot_context.py:320`)
   - partner/about-partner memory rows where `about_user_id == partner.id` (`app/services/hot_context.py:163`)
   - partner/about-partner observation rows where `about_user_id == partner.id` (`app/services/hot_context.py:223`)
3. Preserve current-user material, couple-level rows where `about_user_id IS NULL`, active OOB safe summaries, themes, and watch items as they are. OOB already renders `shareable_context` / `[protected]`, not `sensitive_core` (`app/services/hot_context.py:144`).
4. Keep recent-message behavior simple: current SQL already fetches the current user's thread (`app/services/hot_context.py:247`). Add a guard/redaction in rendering or construction for any row owned by the partner so future query changes cannot leak raw partner-private text accidentally.

### Step 4: Filter Read Tools (`app/services/tools/read_tools.py`)
**Scope:** Medium
1. Update `search_messages` (`app/services/tools/read_tools.py:251`) so raw hits are limited to:
   - the current user's own thread always;
   - the partner's thread only when the partner's `cross_thread_sharing_default` is `opt_in`;
   - never unrelated users.
2. If `partner_user_id` is explicitly the partner and their default is `opt_out` or `unset`, return an empty hit list rather than raw redacted rows, because `MessageHit.content` is currently a plain string and empty results are less misleading.
3. Update `recent_activity` (`app/services/tools/read_tools.py:322`) so partner rows still show safe metadata (`message_count`, `last_message_at`) but do not include raw `latest_content` in the summary unless that user's default permits exposure. For blocked rows, use a neutral summary such as `N messages this period; latest content private by default`.
4. Fetch user defaults in the read-tool query or via a small helper query; keep it dyad-scoped and avoid larger permission systems.

### Step 5: Update Tests
**Scope:** Medium
1. Extend `tests/test_hot_context.py` fixtures to include `cross_thread_sharing_default` in user profile rows (`tests/test_hot_context.py:111`) and add cases proving:
   - unset renders prominently;
   - partner private text is absent when partner is `unset` / `opt_out`;
   - partner text appears when partner is `opt_in`.
2. Add targeted `tests/test_tools.py` cases around `search_messages` and `recent_activity`:
   - `search_messages` with no explicit partner no longer returns unrelated users or non-opt-in partner-private raw messages;
   - explicit partner search returns no raw hits for `unset` / `opt_out`;
   - explicit partner search returns hits for `opt_in`;
   - `recent_activity` hides latest raw partner content unless partner is `opt_in`.
3. Adjust `tests/conftest.py` fake pool query handlers only as needed to support the new SQL shape and defaults.

## Execution Order
1. Add the privacy helper first, because hot context and read tools should share the same rule.
2. Update hot context rendering/building next, since its tests are isolated and cheap.
3. Update `search_messages` and `recent_activity` after the helper behavior is proven.
4. Update fake pool support only when a targeted test exposes an unsupported query shape.

## Overview
The repo already has draft plumbing for `cross_thread_sharing_default`: migration `migrations/0012_cross_thread_sharing.sql`, `User.cross_thread_sharing_default`, prompt guidance in `app/services/prompts.py:187`, schema/tool registry entries, and `write_tools.update_cross_thread_sharing_default`. The missing shippable piece is enforcement: `search_messages` currently searches raw messages broadly, `recent_activity` includes every user's latest raw content, and hot context renders partner-side free-text fields without a clear privacy gate.

This pass must also add a minimal bridge-candidate system. Keep it deliberately small: bridge candidates are controlled summaries that can cross the wall when raw partner material cannot. They should link to source messages and optional memories/observations, appear only as newest few summaries in hot context, and be retrievable through a small read tool. Do not build a full workflow engine, semantic classifier, or auto-delivery system in this pass.

## Main Phase

### Step 1: Confirm Existing Draft Surface
**Scope:** Small
1. Verify the migration defaults users to `NULL` and constrains values to `opt_in` / `opt_out` (`migrations/0012_cross_thread_sharing.sql:1`).
2. Keep the existing write tool contract and tests unless implementation details are broken (`app/services/tools/write_tools.py:155`, `tests/test_tools.py:199`).
3. Keep the prompt text as the starting point, but make hot context more prominent for unset state instead of relying only on generic system instructions (`app/services/prompts.py:187`).

### Step 2: Add A Tiny Privacy Helper
**Scope:** Small
1. Add a focused helper module, likely `app/services/cross_thread_privacy.py`, with two concepts only:
   - `sharing_default(value) -> "unset" | "opt_in" | "opt_out"`
   - `can_expose_raw_to_viewer(owner_user_id, viewer_user_id, owner_default)`, true for the current user's own thread and for partner material only when the owner is `opt_in`.
2. Use a single redaction string for blocked raw text, e.g. `[private by default; user has not opted into cross-thread sharing]`, so tests can assert no raw leakage.
3. Add bridge-specific visibility helpers:
   - bridge summaries are visible to the target user when status is `ready`, `offered`, `sent`, or `addressed`.
   - bridge internals/source ids remain for audit and source-side reasoning, but target-side hot context/read tools should see `shareable_summary`, not raw source text.
4. Do not introduce semantic classifiers or auto-delivery in this pass.

### Step 3: Add Minimal Bridge Candidate Storage And Tools
**Scope:** Medium
1. Add migration `0013_bridge_candidates.sql` with a compact table:
   - `id uuid primary key default gen_random_uuid()`
   - `source_user_id uuid not null references users(id)`
   - `target_user_id uuid not null references users(id)`
   - `kind text not null check in ('context','clarification','contradiction','repair','vulnerability','process')`
   - `status text not null default 'pending' check in ('pending','ready','offered','sent','declined','blocked','addressed','expired')`
   - `sensitivity text not null default 'medium' check in ('low','medium','high')`
   - `source_message_ids uuid[] not null default '{}'`
   - `related_memory_ids uuid[] not null default '{}'`
   - `related_observation_ids uuid[] not null default '{}'`
   - `internal_note text not null`
   - `shareable_summary text not null`
   - `created_at`, `updated_at`, `resolved_at`
2. Add tool schemas:
   - `create_bridge_candidate`
   - `list_bridge_candidates`
   - `update_bridge_candidate`
3. Keep tool behavior simple:
   - create defaults status from source user's sharing default: `opt_in` + low/medium => `ready`; unset/opt_out/high => `pending`; explicit OOB conflict can be represented by model choosing `blocked`.
   - list returns newest candidates involving the dyad, with target-side output limited to `shareable_summary`.
   - update can set status and revise `shareable_summary`/`internal_note` when needed.
4. Do not add `send_bridge_candidate` yet; actual sends can continue through `escalate_to_partner` after explicit user request. This keeps delivery/OOB behavior unchanged while making candidates trackable and visible.

### Step 4: Filter Hot Context (`app/services/hot_context.py`)
**Scope:** Medium
1. Make unset state prominent in rendered hot context near the user profile section (`app/services/hot_context.py:310`): add a short `## Sharing defaults` section showing both defaults and a direct note when the current user is `unset`.
2. Treat partner-owned free text as bridge-private unless the partner is `opt_in`:
   - partner `style_notes` in the `Your Partner` block (`app/services/hot_context.py:320`)
   - partner/about-partner memory rows where `about_user_id == partner.id` (`app/services/hot_context.py:163`)
   - partner/about-partner observation rows where `about_user_id == partner.id` (`app/services/hot_context.py:223`)
3. Preserve current-user material, couple-level rows where `about_user_id IS NULL`, active OOB safe summaries, themes, and watch items as they are. OOB already renders `shareable_context` / `[protected]`, not `sensitive_core` (`app/services/hot_context.py:144`).
4. Keep recent-message behavior simple: current SQL already fetches the current user's thread (`app/services/hot_context.py:247`). Add a guard/redaction in rendering or construction for any row owned by the partner so future query changes cannot leak raw partner-private text accidentally.
5. Add a compact `## Bridge candidates` section with only the newest 3 target-visible candidates for the current user. Include id, kind, status, sensitivity, and `shareable_summary`. Add one line telling the model to call `list_bridge_candidates` for more.

### Step 5: Filter Read Tools (`app/services/tools/read_tools.py`)
**Scope:** Medium
1. Update `search_messages` (`app/services/tools/read_tools.py:251`) so raw hits are limited to:
   - the current user's own thread always;
   - the partner's thread only when the partner's `cross_thread_sharing_default` is `opt_in`;
   - never unrelated users.
2. If `partner_user_id` is explicitly the partner and their default is `opt_out` or `unset`, return an empty hit list rather than raw redacted rows, because `MessageHit.content` is currently a plain string and empty results are less misleading.
3. Update `recent_activity` (`app/services/tools/read_tools.py:322`) so partner rows still show safe metadata (`message_count`, `last_message_at`) but do not include raw `latest_content` in the summary unless that user's default permits exposure. For blocked rows, use a neutral summary such as `N messages this period; latest content private by default`.
4. Fetch user defaults in the read-tool query or via a small helper query; keep it dyad-scoped and avoid larger permission systems.
5. Add `list_bridge_candidates` as a read tool so the agent can retrieve older/more candidates without loading all of them into every prompt.

### Step 6: Update Prompt Guidance
**Scope:** Small
1. Keep prompt text light. It should say:
   - If current user's sharing default is unset, ask them to choose opt-in/opt-out at the first natural opportunity and especially before bridge work.
   - Use bridge candidates to track cross-thread material rather than relaying raw private material directly.
   - Create bridge candidates in Phase B when one partner says something that clarifies, contradicts, explains, repairs, or creates a process/transparency issue for the other.
2. Avoid dumping the full policy matrix into the prompt; the code-level filters are the privacy wall.

### Step 7: Update Tests
**Scope:** Medium
1. Extend `tests/test_hot_context.py` fixtures to include `cross_thread_sharing_default` in user profile rows (`tests/test_hot_context.py:111`) and add cases proving:
   - unset renders prominently;
   - partner private text is absent when partner is `unset` / `opt_out`;
   - partner text appears when partner is `opt_in`.
2. Add targeted `tests/test_tools.py` cases around `search_messages` and `recent_activity`:
   - `search_messages` with no explicit partner no longer returns unrelated users or non-opt-in partner-private raw messages;
   - explicit partner search returns no raw hits for `unset` / `opt_out`;
   - explicit partner search returns hits for `opt_in`;
   - `recent_activity` hides latest raw partner content unless partner is `opt_in`.
3. Add bridge-candidate tests:
   - create candidate from current user to partner;
   - list newest few target-visible candidates;
   - update status to `addressed`/`declined`/`blocked`;
   - target-side list returns `shareable_summary` and not raw `internal_note` when privacy would otherwise block source material.
4. Adjust `tests/conftest.py` fake pool query handlers only as needed to support the new SQL shape and defaults.
