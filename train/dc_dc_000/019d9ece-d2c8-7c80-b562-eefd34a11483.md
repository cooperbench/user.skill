### Step 7: Insert `pushOverlay` registrations at their DOM-order position (`src/shared/state/overlayStack.ts`)
**Scope:** Small
1. **Root cause (narrow):** nested overlays (a menu containing a submenu) register via React effects in child-first order. Sibling overlays (dialog+popover, menu+dialog) register in the order the user opens them, which naturally matches DOM-mount order. The fix must preserve push-order-top for siblings but reorder only the nested case.
2. **Update** `pushOverlay` at `overlayStack.ts:173-183`: after filtering out any prior entry with the same id, find the **first existing entry whose popup element DOM-follows the new entry's popup element** (using `compareDocumentPosition`). If such an entry exists, insert the new entry **before** it. Otherwise append at the top (current behavior). Use the new entry's first popup-kind element; fall back to the first element if no popup-kind element is present; if the new entry has no elements yet, append.
   ```ts
   const newPopup = findPopupElement(nextEntry);
   const insertIndex = newPopup
     ? remainingOverlays.findIndex((o) => domFollows(findPopupElement(o), newPopup))
     : -1;
   const nextOverlays =
     insertIndex === -1
       ? [...remainingOverlays, nextEntry]
       : [...remainingOverlays.slice(0, insertIndex), nextEntry, ...remainingOverlays.slice(insertIndex)];
   ```
   where `domFollows(a, b)` returns `!!(a && b && a.compareDocumentPosition(b) & Node.DOCUMENT_POSITION_PRECEDING)` — i.e., "b precedes a" means "a follows b in DOM".
3. **Do not change `updateOverlay`** — its documented contract is "preserves ordering position", and the bug is exclusively at initial push time. Element patches arrive after the initial registration and should not reorder the stack.
4. **Why this preserves sibling behavior:** when a second sibling overlay opens (e.g., popover after dialog), its popup mounts at a DOM position **after** the dialog's popup. `domFollows(dialogPopup, popoverPopup)` is false (popoverPopup doesn't precede dialogPopup), so no existing entry DOM-follows the new popover → `insertIndex === -1` → append at the top. Same as today. The only case where the new rule deviates is when the new push's popup is DOM-earlier than an already-registered popup — i.e., the nested parent-pushes-after-child case.
5. **Verify** via the targeted overlay tests: `lightbox.test.tsx`, `hover-card.test.tsx`, `tooltip.test.tsx`, `overlayBridge.test.tsx`, `overlaySequences.test.tsx` — all must stay green. The dropdown submenu case becomes green because when `DropdownMenuContent` (parent) pushes after `DropdownMenuSubContent` (child), the parent's popup DOM-precedes the child's → parent inserts at index 0 (before submenu) → stack = `[menu, menu-submenu]`.
