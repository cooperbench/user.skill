        # Implementation Plan: Timeline Editor Performance — Eliminate Lag, Jank, and Unnecessary Re-renders

## Overview

The timeline editor (`viewer/src/tools/video-editor/`) drives a ~50-clip, ~10-track video editing UI. The context has already been split into `TimelineEditorContext` (data/editing) and `TimelinePlaybackContext` (currentTime/playback). `ClipAction` already uses `React.memo` with a custom comparator. Despite this, the monolithic `editor` context value (60+ properties in a single `useMemo` with 45 dependencies) means **any** state change — save status, render progress, selection, or an edit — invalidates the editor context and re-renders every consumer. Playback at 30fps is correctly isolated but still triggers the OverlayEditor's `activeOverlays` recomputation every frame.

**Key constraints:**
- Must not break existing functionality (drag, drop, resize, overlay editing, cross-track drag, polling sync, render)
- `@xzdarcy/react-timeline-editor` is a third-party component — we can only control what we pass to it
- Changes should be profile-driven: measure first, fix what matters

**Current bottleneck ranking (by impact on hot paths):**
1. Monolithic editor context — every edit/selection/status change re-renders all 5 consumer components
2. `getActionRender` depends on `data.meta` + `selectedClipId` — any clip edit rebuilds all clip render callbacks
3. `ClipAction` comparator uses `JSON.stringify` on entrance/exit/transition/effects for every clip, every render
4. `activeOverlays` in OverlayEditor recomputes on every playback frame with 5 dependencies
5. `TrackLabel` is not memoized, re-renders on every editor context change
6. `thumbnailMap` and `scaleCount` rebuild on every `data` / `resolvedConfig` change
7. Inline `sameKindCount` filter in TimelineEditor render path
8. `onTimelineDragOver` creates and mutates DOM (innerHTML) on every dragover event
9. `TimelineRenderer` (shared composition) creates new arrays (`.reverse()`, `.filter()`) every frame during playback

## Step 2: Split the monolithic editor context into focused contexts
**Scope:** Large — highest-impact change
**Files:** `useTimelineState.ts:120-240`, `TimelineContext.tsx`, all context consumers

The single `TimelineEditorContext` bundles data, selection, callbacks, status, and preferences into one object. Splitting into 3-4 focused contexts ensures that a save-status change doesn't re-render the TimelineEditor, and a selection change doesn't re-render the Toolbar.

1. **Define** new context slices:
   - `TimelineDataContext` — `data`, `resolvedConfig`, `isLoading`, `dataRef`, `compositionSize`, `trackScaleMap`, `preferences`
   - `TimelineSelectionContext` — `selectedClipId`, `selectedTrackId`, `selectedClip`, `selectedTrack`, `selectedClipHasPredecessor`, `setSelectedClipId`, `setSelectedTrackId`
   - `TimelineActionsContext` — all callbacks (`onChange`, `onActionMove*`, `handleDelete`, `handleDrop`, etc.) — these are stable refs that rarely change
   - `TimelineStatusContext` — `saveStatus`, `renderStatus`, `renderLog`, `renderDirty`, `renderProgress`, `startRender`
2. **Update** `TimelineContext.tsx` to provide 4 new contexts plus the existing playback context.
3. **Update** each consumer to pull from the narrowest context:
   - `TimelineEditor.tsx` → data + selection + actions
   - `Toolbar.tsx` → status + playback
   - `PreviewPanel.tsx` → data + selection + playback
   - `PropertiesPanel.tsx` → data + selection + actions + playback
   - `VideoEditorPage.tsx` → selection + status + actions + playback
4. **Keep** `useEditorContext()` as a convenience that merges all 4 for backward compatibility, but deprecate its use in components.
5. **Verify** with profiler that save-status changes no longer re-render TimelineEditor.

## Step 3: Stabilize `getActionRender` and decouple selection from clip rendering
**Scope:** Medium
**Files:** `TimelineEditor.tsx:105-124`

`getActionRender` currently depends on `data?.meta`, `selectedClipId`, `thumbnailMap`, `handleClipSelect`, `pixelsPerSecond`. This means selecting a different clip re-creates the render callback for **every** clip in the timeline.

1. **Remove** `selectedClipId` from `getActionRender` dependencies. Instead, have `ClipAction` read selection state from the new `TimelineSelectionContext` directly, or pass it via a ref.
2. **Stabilize** `data?.meta` dependency — since `meta` is a new object on every edit, use a ref (`metaRef`) and read from it inside `getActionRender` so the callback identity is stable.
3. **Move** `pixelsPerSecond` calculation into a `useMemo` (currently it's a plain `const` on line 103 — this is fine for the local value but causes `getActionRender` to have it as a dep that changes with `scaleWidth`).
4. **Result:** `getActionRender` should only need `[handleClipSelect]` as a dependency (stable callback).

## Step 4: Replace JSON.stringify in ClipAction comparator with shallow structural checks
**Scope:** Small
**File:** `ClipAction.tsx:13-15, 101-122`

`isSameStructuredValue` calls `JSON.stringify` for `entrance`, `exit`, `transition`, and `effects` on every memo comparison for every clip.

1. **Replace** `isSameStructuredValue` with a shallow key comparison for the known shapes:
   ```typescript
   const isSameEffect = (a: EffectConfig | undefined, b: EffectConfig | undefined) => {
     if (a === b) return true;
     if (!a || !b) return false;
     return a.type === b.type && a.duration === b.duration && a.easing === b.easing;
   };
   ```
2. **Add** specific comparators for `transition` (type, duration), `effects` array (length + shallow compare each).
3. **Verify** with a benchmark: create 50 clips, profile comparison time before/after.

## Step 5: Memoize OverlayEditor to avoid re-render on every playback frame
**Scope:** Medium
**File:** `OverlayEditor.tsx:108-145`

`activeOverlays` depends on `currentTime`, which changes every frame during playback. But overlays only change when the playhead crosses a clip boundary.

1. **Derive** a "visible clip set key" by computing which clips are active at `currentTime`, then only recompute overlay bounds when the set changes.
   ```typescript
   const activeClipIds = useMemo(() => {
     const ids: string[] = [];
     for (const row of rows) {
       if (!row.id.startsWith("V")) continue;
       for (const action of row.actions) {
         if (currentTime >= action.start && currentTime < action.end) ids.push(action.id);
       }
     }
     return ids.join(",");
   }, [currentTime, rows]);
   ```
2. **Split** the heavy overlay computation to only run when `activeClipIds` string changes, not on every frame.
3. **Wrap** `OverlayEditor` in `React.memo` with a comparison that treats `currentTime` changes as equal if the active clip set hasn't changed.

## Step 6: Memoize TrackLabel and stabilize its props
**Scope:** Small
**Files:** `TrackLabel.tsx`, `TimelineEditor.tsx:133-154`

`TrackLabel` re-renders on every editor context change because it's not memoized. The inline `data.tracks.filter((t) => t.kind === track.kind).length` creates a new computation per track per render.

1. **Wrap** `TrackLabel` in `React.memo`.
2. **Hoist** `sameKindCount` into a memoized map:
   ```typescript
   const kindCountMap = useMemo(() => {
     const counts: Record<string, number> = {};
     for (const t of data.tracks) counts[t.kind] = (counts[t.kind] ?? 0) + 1;
     return counts;
   }, [data?.tracks]);
   ```
3. **Pass** `kindCountMap[track.kind]` instead of computing inline.

## Step 7: Memoize TimelineRenderer for Remotion playback
**Scope:** Small
**File:** `shared/compositions/TimelineRenderer.tsx:73-99`

During playback, `TimelineRenderer` re-renders every frame. It creates new arrays with `.reverse()` and `.filter()` each time.

1. **Wrap** `TimelineRenderer` in `React.memo` with a reference-equality check on `config`.
2. **Memoize** the track grouping inside:
   ```typescript
   const visualTrackClips = useMemo(() => {
     const tracks = getVisualTracks(config);
     return [...tracks].reverse().map(track => ({
       track,
       clips: config.clips.filter(c => c.track === track.id),
     }));
   }, [config]);
   ```
3. This ensures the array allocations happen once per config change, not once per frame.

## Step 8: Optimize drag-over indicator (DOM mutation)
**Scope:** Small
**File:** `useTimelineEditing.ts:345-387`

`onTimelineDragOver` sets `innerHTML` with a template string on every dragover event (fires at ~60Hz). This causes layout thrashing.

1. **Create** the indicator elements once and reuse them, updating only `style` properties (left, top, width).
2. **Use** `requestAnimationFrame` to batch dragover updates — only apply the latest position per frame.
3. **Cache** DOM queries (`querySelector`) — store refs to edit-area and grid elements.

## Overview

The timeline editor (`viewer/src/tools/video-editor/`) drives a ~50–100 clip, ~10–12 track video editing UI. The context is already split into `TimelineEditorContext` and `TimelinePlaybackContext`, and `ClipAction` uses `React.memo` with a custom comparator. Despite this, overall interaction feels sluggish because:

1. **`VideoEditorLayout` subscribes to both editor and playback contexts** and renders `<TimelineEditor />`, `<PreviewPanel />`, and `<PropertiesPanel />` directly — so any `currentTime`, `saveStatus`, or `selectedClipId` change re-renders the entire page subtree. None of these child components are memoized.
2. **`getActionRender` is rebuilt on every edit/selection change** because it depends on `data.meta`, `selectedClipId`, `thumbnailMap`, and `pixelsPerSecond` — causing the `@xzdarcy/react-timeline-editor` library to call it for all visible clips.
3. **Overlay drag and inline text editing trigger a full timeline rebuild per mousemove/keystroke** via `onOverlayChange` → `applyTimelineEdit` → `materializeData` (rowsToConfig → resolveTimelineConfig → configToRows).
4. **`ClipAction` comparator uses `JSON.stringify`** for entrance/exit/transition/effects on every comparison for every clip.

**Key constraints:**
- Must not break existing functionality (drag, drop, resize, overlay editing, cross-track drag, polling sync, render)
- `@xzdarcy/react-timeline-editor` is a third-party component — we control only what we pass to it
- `ClipAction` must stay props-based with `React.memo` (plain React context for selection would fan out re-renders to all clips — worse than the current approach)
- Polling must remain for Python tool compatibility; ensure no-op polls don't trigger work

## Step 3: Stabilize `getActionRender` via refs (keep selection as props)
**Scope:** Medium
**File:** `TimelineEditor.tsx:105-124`

`getActionRender` currently depends on `[data?.meta, selectedClipId, thumbnailMap, handleClipSelect, pixelsPerSecond]`. When any of these change, the callback identity changes, and the timeline library re-calls it for every visible clip.

**Critical design decision:** `ClipAction` must continue receiving `isSelected` as a **prop** (not from context). If `ClipAction` read `selectedClipId` from a plain React context, every clip would subscribe and re-render on every selection change, defeating the `React.memo` comparator. The current prop-based pattern is correct — we just need to prevent `getActionRender`'s callback identity from changing on selection.

1. **Store** `data?.meta`, `selectedClipId`, `thumbnailMap`, and `pixelsPerSecond` in refs that are updated via `useLayoutEffect` (or inline assignment for simple values).
2. **Rewrite** `getActionRender` to read from refs instead of closure variables:
   ```typescript
   const metaRef = useRef(data?.meta);
   const selectedClipIdRef = useRef(selectedClipId);
   const thumbnailMapRef = useRef(thumbnailMap);
   const pixelsPerSecondRef = useRef(pixelsPerSecond);
   // update refs on each render
   metaRef.current = data?.meta;
   selectedClipIdRef.current = selectedClipId;
   thumbnailMapRef.current = thumbnailMap;
   pixelsPerSecondRef.current = pixelsPerSecond;

   const getActionRender = useCallback((action: TimelineAction) => {
     const clipMeta = metaRef.current?.[action.id];
     if (!clipMeta) return null;
     const clipWidthPx = (action.end - action.start) * pixelsPerSecondRef.current;
     const thumb = clipWidthPx >= 40 ? thumbnailMapRef.current[action.id] : undefined;
     return (
       <ClipAction
         action={action}
         clipMeta={clipMeta}
         isSelected={selectedClipIdRef.current === action.id}
         thumbnailSrc={thumb}
         onSelect={handleClipSelect}
       />
     );
   }, [handleClipSelect]); // single stable dependency
   ```
3. **Result:** `getActionRender` identity only changes when `handleClipSelect` changes (which is stable via `useCallback` with stable deps). The timeline library won't re-call it for all clips on selection or meta changes.
4. **Note:** The existing `ClipAction` `React.memo` comparator still correctly prevents unnecessary DOM updates when props haven't meaningfully changed.

## Step 4: Debounce overlay drag and text input to avoid full rebuilds per mousemove
**Scope:** Medium
**Files:** `OverlayEditor.tsx:294-360`, `useTimelineEditing.ts:253-260`

Currently, overlay drag calls `onOverlayChange` on every `mousemove` (OverlayEditor.tsx:312, 342), and text editing calls it on every keystroke (line 445). `onOverlayChange` (useTimelineEditing.ts:253) routes directly to `applyTimelineEdit`, which runs the full `materializeData` pipeline: `rowsToConfig` → `resolveTimelineConfig` → `configToRows` → `setData`. At ~60Hz during drag, this is the most direct source of interaction jank.

1. **Add local ephemeral state** to `OverlayEditor` for the drag-in-progress position. During `mousemove`, update only the local position state (which re-renders only the overlay rectangle). On `mouseup`, commit the final position via `onOverlayChange`.
   ```typescript
   const [dragOverride, setDragOverride] = useState<Record<string, Partial<ClipMeta>> | null>(null);
   ```
   During drag: `setDragOverride({ [state.actionId]: { x, y } })` — lightweight local state update.
   On mouseup: `onOverlayChange(state.actionId, dragOverride[state.actionId])` — single full rebuild.
2. **Apply the same pattern for resize** (lines 324-347): track resize dimensions locally, commit on mouseup.
3. **For text editing** (line 445): debounce `onOverlayChange` calls with a 300ms trailing debounce (text is less latency-sensitive than drag). Use local `editText` state (already exists at line 61) for immediate display, batch the timeline commit.
4. **Merge** the drag override into the rendered overlay positions so the user sees smooth movement without the full rebuild cost:
   ```typescript
   const effectiveOverlays = useMemo(() => {
     if (!dragOverride) return activeOverlays;
     return activeOverlays.map(o => {
       const override = dragOverride[o.actionId];
       if (!override) return o;
       return { ...o, x: override.x ?? o.x, y: override.y ?? o.y, width: override.width ?? o.width, height: override.height ?? o.height };
     });
   }, [activeOverlays, dragOverride]);
   ```
5. **Verify:** during overlay drag, React DevTools shows only `OverlayEditor` re-rendering (local state), not the full component tree.
