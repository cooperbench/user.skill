## Overview
Reigh already has a deliberately safe v1 sequence path: `supabase/functions/ai-generate-sequence/` generates trusted structured drafts, `src/tools/video-editor/components/SequenceCreator/SequenceCreatorPanel.tsx` invokes it, `src/tools/video-editor/sequences/` validates and materializes asset-backed params, and `src/tools/video-editor/lib/sequence-drafts.ts` inserts or replaces clips. Rendering is already split by `src/tools/video-editor/lib/renderRouter.ts`: native timelines stay on the client path, while registered themed clips route to `banodoco_render_timeline` / Banodoco workers. Timeline persistence is schema-backed through `timelines.config`, `timelines.asset_registry`, `update_timeline_versioned`, `timeline-import`, and `SupabaseDataProvider`. ArtAgents already emits Reigh-compatible `hype.timeline.json` / `hype.assets.json` and renders with its Remotion wrapper.

The critique does not show the plan targeting the wrong root cause. The additive three-lane architecture is still the right approach: keep trusted v1 safe, add richer declarative data, and isolate generated code in workers. The remaining critique is a concrete completeness gap: because `@banodoco/timeline-schema` is a local file dependency at `../../banodoco-workspace/packages/timeline-schema`, schema alignment must name the package's TypeScript schema, generated JSON schema, Python generated types, codegen scripts, and tests. That is required implementation surface for the chosen shared-schema source of truth, not unrelated scope growth.

The document at `docs/generated-sequences-architecture.md` should propose an additive architecture: preserve the current trusted sequence creator exactly as the default safe path, then add two higher-flexibility lanes behind explicit capabilities: a declarative schema-sequence lane and a generated Remotion module lane.         # Generated Sequences Architecture

## Opening

Reigh already has a safe v1 path for AI-authored animation beats: the browser editor asks `supabase/functions/ai-generate-sequence/index.ts` for trusted sequence drafts, validates the model response against a narrow draft schema, and inserts the result as ordinary timeline data. That path is intentionally data-only. The model may choose from trusted `clipType` values, `hold`, and JSON params, but it may not return TSX, imports, raw URLs, arbitrary animation references, or executable render logic.

This document plans how to add more flexible AI-generated animation sequences without weakening that baseline. The target architecture must support three levels of expressiveness over time: the existing trusted structured drafts, declarative schema-sequences that compile into normal timeline clips, and generated Remotion modules that execute only in worker render infrastructure. Those lanes are additive. The current trusted sequence creator remains the default safe editor behavior until later rollout decisions explicitly enable another lane.

The load-bearing implementation boundary today is that persisted timelines are still `TimelineConfig` plus `AssetRegistry` data. Current UI insertion code in `src/tools/video-editor/lib/sequence-drafts.ts` converts a validated draft into rows, clip metadata, clip order, and ordinary timeline edits. Current render materialization in `src/tools/video-editor/sequences/materialize.ts` resolves asset-key params into component-facing URLs at render payload time without mutating persisted params. Any new lane must preserve that persistence invariant unless a later migration explicitly changes it.

## Current-State Map

### Trusted v1 sequence authoring

- `src/tools/video-editor/components/SequenceCreator/SequenceCreatorPanel.tsx` is the browser entry point. It sends the user prompt, selected or attached clips, the allowed asset registry subset, and allowed trusted clip types to the `ai-generate-sequence` edge function.
- `supabase/functions/ai-generate-sequence/index.ts` authenticates the user, rate-limits the request, builds model messages, calls Anthropic, extracts `drafts`, attempts a JSON-only repair pass when extraction fails, then validates each raw draft before returning it to the editor.
- `supabase/functions/ai-generate-sequence/sequence-validation.ts` is the edge-side validator. It only accepts root keys `clipType`, `hold`, and `params`; rejects generated-code fields such as `code`, `component`, `jsx`, `tsx`, `imports`, `source`, and `render`; rejects animation-reference fields such as `animation`, `transition`, `entrance`, and `exit`; rejects raw URLs; and restricts asset-valued params to selected or attached registry asset keys.
- `src/tools/video-editor/sequences/validation.ts` mirrors the trusted draft contract in the frontend. It exists so the editor can reason about drafts using the same data-only assumptions as the edge function.
- `src/tools/video-editor/sequences/metadata.ts` defines the trusted sequence catalog. At the time of this map, the catalog includes `image-jump`, `section-hook`, `art-card`, `resource-card`, and `cta-card`, all under the trusted `2rp` sequence theme.
- `src/tools/video-editor/lib/sequence-drafts.ts` inserts or replaces sequence drafts as normal timeline clips. It sets `clipType`, `hold`, and `params`, updates row actions and clip order, resolves overlaps, and selects the inserted clip. It does not persist code artifacts.

### Current renderer split

- `src/tools/video-editor/lib/renderRouter.ts` owns render-button routing. `decideRenderRoute()` sends pure native clips to the existing client renderer and sends timelines containing registered theme-package clip types to `banodoco_render_timeline`.
- The native client-renderable set is `media`, `text`, `effect-layer`, `hold`, plus legacy clips with no `clipType`.
- The Banodoco route is selected when a clip `clipType` exists in `THEME_PACKAGE_REGISTRY`; mixed timelines containing both theme-package clips and media/native clips also route to Banodoco.
- `src/tools/video-editor/compositions/TimelineRenderer.tsx` separately renders actual timeline playback. It dispatches native clips to Reigh-native components, dispatches registered sequence/theme clip types through `SEQUENCE_COMPONENT_REGISTRY`, and uses `UnknownClipPlaceholderSequence` for unsupported clip types instead of silently rendering black output.

### Unknown-clip routing hazard

`decideRenderRoute()` currently treats unknown `clipType` values as media-equivalent, so the route remains `client` and the renderer relies on the loud placeholder fallback. That behavior is reasonable for mistyped or not-yet-installed theme packages, but it is unsafe as the only discriminator for generated Remotion modules. A novel generated-code clip type could accidentally stay on the client route. Generated-code routing therefore cannot be based on inventing new `clipType` strings alone; it needs explicit lane metadata and tests that prove unknown or absent clip types do not imply generated-code execution.

### Persistence and import invariants

- The editor and edge-agent persistence model is ordinary timeline JSON. `src/tools/video-editor/types/index.ts` defines `TimelineConfig` with `output`, `clips`, optional `tracks`, optional `pinnedShotGroups`, and optional theme fields, plus `AssetRegistry` as `assets: Record<string, AssetRegistryEntry>`.
- `supabase/functions/ai-timeline-agent/db.ts` persists editor/agent updates through `saveTimelineConfigVersioned()`, which calls `update_timeline_config_versioned` with a `TimelineConfig` and expected version.
- `supabase/functions/timeline-import/handler.ts` validates imported timelines against `@banodoco/timeline-schema`, checks `project_id` and `timeline_id` UUIDs, verifies project ownership, checks existing row ownership, and writes through versioned RPCs.
- `supabase/functions/timeline-import/validate.ts` treats `asset_registry` as a Reigh-specific envelope and verifies only that `asset_registry.assets` is object-shaped. Import may include an asset registry, but it still writes into the existing `timelines.config` and `timelines.asset_registry` fields.

## Canonical Timeline Contract

The generated sequence work must start by resolving the timeline contract, because every later lane compiles or publishes back into timeline JSON. The canonical persisted contract for Reigh, ArtAgents, timeline import, and worker render payloads is `@banodoco/timeline-schema`, but the package must be aligned with the Reigh persisted shape before schema-sequences or generated modules are allowed to write production timelines.

### Current mismatch

There is already a shared package dependency: Reigh imports `@banodoco/timeline-schema` from `file:../../banodoco-workspace/packages/timeline-schema` in `package.json`, `src/tools/video-editor/types/index.ts` re-exports the shared types, and `supabase/functions/timeline-import/handler.ts` validates imports with `TimelineConfigSchema.safeParse(body.timeline)`. The problem is that Reigh's local persisted type and the shared Zod schema are not identical today.

- Reigh local `TimelineConfig` in `src/tools/video-editor/types/index.ts` requires `output`, allows `theme?: string`, and allows `generation_defaults?: Record<string, unknown>`.
- The shared `TimelineConfig` in `../../banodoco-workspace/packages/timeline-schema/typescript/src/schemas.ts` currently requires `theme: z.string()`, allows `output: TimelineOutput.optional()`, and has no top-level `generation_defaults`.
- Reigh defaults in `src/tools/video-editor/lib/defaults.ts` intentionally create new timelines with `output` present and `theme`, `theme_overrides`, and `generation_defaults` absent.
- Reigh serialization in `src/tools/video-editor/lib/serialize.ts` preserves `theme`, `theme_overrides`, and `generation_defaults` when present, and its local validator allows all three top-level fields.
- The shared schema allows open `clip.generation` records, but that is not a substitute for the top-level `generation_defaults` field that Reigh currently round-trips.

This mismatch means a Reigh-valid timeline can fail shared-schema validation when `theme` is absent or `generation_defaults` is present, while a shared-schema-valid authoring timeline can omit the `output` that Reigh's persisted editor state expects. Do not build schema-sequence or ArtAgents publishing behavior on top of that split.

### Source of truth

The settled source of truth is the local shared package at `../../banodoco-workspace/packages/timeline-schema`. Reigh local types should either be generated from, inferred from, or mechanically checked against that package for the persisted boundary. Reigh may keep richer editor-only types such as `ResolvedTimelineConfig`, resolved asset entries, UI clip metadata, and drag rows, but anything saved to `timelines.config`, sent through `timeline-import`, emitted by ArtAgents, or sent to the worker render payload must validate against the aligned shared package.

The target persisted contract is:

- `clips` remains required and `clipType` remains an open string. Registry validation is a separate authoring/render concern, not a base schema concern.
- `output` is required for Reigh persisted timelines and render payloads. ArtAgents or Banodoco authoring payloads that infer output from a theme must materialize `output` before publishing into Reigh or invoking Reigh import.
- `theme` is optional for compatibility with existing Reigh timelines and pure native/media projects.
- `theme_overrides` is optional and keeps the current open block shape.
- `generation_defaults` is optional open metadata until stakeholders choose stricter semantics. While Reigh persists it, the shared schema must accept it so codegen, import validation, and ArtAgents do not drift.
- `clip.generation` remains an open per-clip record for provenance and future lane discriminants; later sections will narrow required keys for generated sequence artifacts without making the base timeline schema reject older clips.
- `pinnedShotGroups` remains optional Reigh metadata. It is part of the shared persisted contract only because Reigh already stores it in timeline config; ArtAgents may omit it.

### Local schema package surface

- TypeScript exports: `../../banodoco-workspace/packages/timeline-schema/typescript/src/index.ts`.

### Regeneration rules

- Edit the canonical TypeScript/Zod source first. For base timeline shape changes, that means `typescript/src/schemas.ts`.
- Run package codegen; do not manually edit generated outputs. The generator writes JSON Schema from Zod and then emits Python TypedDicts from the JSON Schema.
- Treat `python/banodoco_timeline_schema/timeline.schema.json`, `typescript/dist/timeline.schema.json`, and `python/banodoco_timeline_schema/generated.py` as generated artifacts. The `generated.py` header already says it is auto-generated and must not be edited by hand.
- Use `npm run build` to compile TypeScript and emit JSON Schema, then `npm run gen:python` to regenerate Python types, or use `make build` plus `make gen`.
- Use `npm run check:codegen` or `make check-codegen` as the drift gate. The script runs `npm run build:ts`, emits JSON Schema, regenerates Python types, and fails if generated files have uncommitted diffs.
- Use `make check` before accepting a schema change. It runs the codegen drift gate and the package tests.
- Any Reigh-side change that touches `TimelineConfig`, `serializeForDisk()`, `timeline-import`, ArtAgents timeline output, or worker render payloads must either include regenerated shared outputs or explicitly state that no shared schema change was required.

### Compatibility behavior

Existing Reigh timelines should not require a table migration just because the shared schema is aligned. Timelines that already contain `output`, optional `theme`, optional `theme_overrides`, optional `generation_defaults`, open `clipType`, open `params`, and optional `clip.generation` should continue to load, serialize, import, and render after alignment.

The compatibility path is:

- Reigh keeps `createDefaultTimelineConfig()` behavior: new native timelines can start without `theme` and `generation_defaults`.
- Reigh keeps read-side repair/migration for editor internals before save, but anything sent to `timeline-import` or the worker render route must be in the aligned shared schema shape.
- ArtAgents must publish Reigh-compatible timeline JSON by consuming the regenerated Python package outputs, not by maintaining its own handwritten timeline TypedDicts or JSON Schema.
- If a Banodoco authoring flow omits `output` because it expects theme materialization, it must materialize `output` before crossing the Reigh persistence/import/render boundary.
- Unknown `clipType` values remain schema-valid. Whether a clip can be authored, previewed, or rendered is decided by trusted sequence validation, schema-sequence validation, render registry checks, and the explicit generated-sequence lane metadata described later.

## Generated Sequence Artifact Discriminant

Generated sequence artifacts need an explicit discriminator in persisted clip data. The discriminator is not the clip type. The current render router treats unknown `clipType` values as client-renderable fallback so unsupported clips can surface through `UnknownClipPlaceholderSequence`; generated Remotion modules must never rely on that fallback path.

### Clip metadata contract

Use `clip.generation` as the additive metadata envelope for generated sequence provenance and routing. The base timeline schema should keep `clip.generation` open, but generated sequence validators and the render router must recognize these keys:

```ts
type SequenceLane = 'trusted_v1' | 'schema_sequence' | 'remotion_module';

type GeneratedSequenceGeneration = {
  sequence_lane?: SequenceLane;
  artifact_id?: string;
  artifact_version?: number;
  compiler_version?: string;
  source_kind?: 'trusted_draft' | 'schema_sequence' | 'remotion_module';
};
```

Lane meanings:

- `trusted_v1`: optional provenance for the current trusted sequence path. Existing v1 trusted draft clips do not need a migration and may omit `clip.generation` entirely.
- `schema_sequence`: a proposed declarative, non-code sequence artifact that compiles into normal timeline clips and params. It may link back to an artifact with `artifact_id`, but runtime rendering should still use compiled ordinary timeline data.
- `remotion_module`: a proposed generated Remotion module artifact. Any clip in this lane must include a non-empty `clip.generation.artifact_id`, and render routing must treat it as worker-only generated code.

For generated Remotion modules, the load-bearing invariant is:

```ts
clip.generation?.sequence_lane === 'remotion_module'
  && typeof clip.generation?.artifact_id === 'string'
  && clip.generation.artifact_id.length > 0
```

A clip that lacks `clip.generation.sequence_lane` is not a generated Remotion module, even when its `clipType` is unknown. A clip that sets `sequence_lane: 'remotion_module'` but omits `artifact_id` is malformed and must not silently fall back to client rendering.

### Render-router requirements

`src/tools/video-editor/lib/renderRouter.ts` must be updated before any generated Remotion module can be persisted or rendered.

- Extend `RouterClipShape` from `{ clipType?: string }` to include the minimal discriminant shape:

```ts
export interface RouterClipShape {
  clipType?: string;
  generation?: {
    sequence_lane?: unknown;
    artifact_id?: unknown;
  } | null;
}
```

- Add a helper equivalent to `isGeneratedRemotionModuleClip(clip)` that checks `clip.generation.sequence_lane === 'remotion_module'`.
- In `decideRenderRoute()`, inspect the generated-module lane before checking theme-package clip types or native clip types.
- If any clip has `sequence_lane === 'remotion_module'` and a valid `artifact_id`, return a worker route. The existing route value may remain `banodoco` if that is the worker/orchestrator route, but `RenderRouteDecision.reason` must distinguish generated module routing from theme-package routing.
- Add explicit `RenderRouteDecision.reason` values for generated modules, at minimum `generated_remotion_module` and `mixed_generated_module_and_other`.
- Add an explicit malformed-lane failure reason such as `remotion_module_missing_artifact`. This may require a new blocked/error route or an error field on `RenderRouteDecision`; either shape is acceptable only if callers cannot proceed to the client renderer.
- Keep current unknown-clip fallback behavior for clips without the generated-module lane. Unknown `clipType` plus no lane should continue to route to the existing client placeholder path.
- Keep legacy clips with absent `clipType` and no generated-module lane client-renderable.

The ordering matters. A generated module with a novel `clipType` should route by `clip.generation.sequence_lane`, not by registry membership, and not by the unknown-clip fallback branch.

### Render-router test expectations

Update `src/tools/video-editor/lib/renderRouter.test.ts` alongside the router change. Required coverage:

- Existing pure native timelines still return `route: 'client'` and `reason: 'pure_native_clips'`.
- Existing theme-package timelines still return `route: 'banodoco'` and the existing themed reasons.
- Existing mixed theme-package/native timelines still return `route: 'banodoco'` and `reason: 'mixed_themed_and_media'`.
- Legacy clips with absent `clipType` and no `generation.sequence_lane` still route to the client renderer.
- Unknown `clipType` with no `generation.sequence_lane` still routes to the client loud-placeholder fallback.
- Unknown or novel `clipType` with `generation.sequence_lane === 'remotion_module'` and a non-empty `artifact_id` routes to the worker path with a generated-module-specific `RenderRouteDecision.reason`.
- Registered theme `clipType` with `generation.sequence_lane === 'remotion_module'` and a non-empty `artifact_id` still routes as a generated module, proving lane metadata has precedence over theme registry membership.
- Mixed timelines containing at least one valid generated Remotion module and at least one native/media/theme clip route to the worker path with `reason: 'mixed_generated_module_and_other'`.
- `generation.sequence_lane === 'remotion_module'` with missing, empty, or non-string `artifact_id` never routes to `client`; the decision should be blocked or otherwise structured as an error.
- `generation.sequence_lane` values `trusted_v1`, `schema_sequence`, unknown strings, null, or absent do not trigger generated-module routing by themselves.

These tests must assert both `route` and `reason`. This is the guardrail that prevents future work from accidentally treating generated code as just another unknown clip type.

## Three-Lane Target Architecture

The target architecture has three additive lanes. All three lanes converge on the aligned timeline contract from `@banodoco/timeline-schema` and, wherever possible, persist compiled output through the existing `timelines.config` and `timelines.asset_registry` fields. They differ in what AI is allowed to author, where validation happens, and whether any generated code exists.

The lanes are:

- `trusted_v1`: the current safe structured-draft lane.
- `schema_sequence`: a proposed declarative, non-code sequence lane that compiles into ordinary timeline clips.
- `remotion_module`: a proposed generated Remotion module lane that can render custom code, but only in worker render infrastructure.

Lane choice must be explicit. A model response, editor action, import payload, or worker render payload must not infer generated-code behavior from a novel `clipType`. The current trusted path remains the default editor behavior until rollout flags and allowlists enable another lane.

### Lane 1: trusted structured drafts

The trusted lane is the existing v1 sequence creator path. It should remain as small and predictable as it is today:

- Authoring entry point: `SequenceCreatorPanel` calls `supabase/functions/ai-generate-sequence`.
- AI output shape: only `clipType`, `hold`, and `params`.
- Validation boundary: edge validation in `supabase/functions/ai-generate-sequence/sequence-validation.ts`, mirrored by frontend validation in `src/tools/video-editor/sequences/validation.ts`.
- Persistence output: ordinary row actions, clip metadata, and clip order produced by `src/tools/video-editor/lib/sequence-drafts.ts`.
- Render behavior: current registered sequence components, native media/text/effect clips, and the existing render-router split.
- Artifact behavior: no generated artifact record is required. Existing clips may omit `clip.generation` entirely, and optional provenance may use `sequence_lane: 'trusted_v1'` later without requiring migration.

This lane must not accept code, imports, JSX/TSX, HTML, raw URLs, arbitrary animation references, or unknown root keys. Do not widen the trusted validator to make schema-sequences or generated modules easier to ship. Those capabilities belong in separate lanes with separate validators and rollout controls.

Trusted lane validation stops at the data-only draft boundary. After validation, the draft is converted into normal timeline edits and follows the same persistence, undo, preview, and render behavior as any other trusted sequence clip. That is why this lane is the rollback baseline: if every proposed generated-sequence feature flag is disabled, trusted v1 should still work.

### Lane 2: declarative schema-sequences

The schema-sequence lane is the middle lane: more expressive than a trusted v1 draft, but still not code. It is a proposed JSON DSL for animation structure, timing, asset slots, text blocks, layout choices, transitions from an allowlisted vocabulary, and parameterized sequence composition. It must compile deterministically into normal timeline clips, params, registry entries, and routeable timeline data.

The schema-sequence artifact is proposed and should be stored additively. Its source can be linked from compiled clips with `clip.generation.sequence_lane: 'schema_sequence'` and, when an artifact record exists, `clip.generation.artifact_id`. Runtime rendering should not need to interpret the schema-sequence source. The renderable contract is the compiled `TimelineConfig` plus `AssetRegistry`.

The schema-sequence compiler requirements are:

- It accepts only JSON data validated against the aligned base timeline schema plus a proposed schema-sequence schema.
- It performs no `eval`, dynamic import, JSX/TSX compilation, script execution, URL fetching, or dependency resolution.
- It maps declarative operations into existing clip types, trusted sequence clip types, native effects, and registry-backed assets.
- It rejects unknown operations, unsupported transition names, missing asset keys, raw URLs, unsupported media kinds, oversized documents, impossible timing, and references outside the caller-authorized asset registry.
- It emits deterministic output for the same input, schema version, compiler version, asset registry, and timeline context.
- It records compiler version and source artifact provenance in `clip.generation` where useful, but the compiled clips must remain editable timeline data.

The validation boundary for this lane has two phases. First, validate the schema-sequence source before persistence so malformed AI output never becomes an accepted artifact. Second, validate the compiled timeline output against `@banodoco/timeline-schema` and Reigh asset-registry rules before inserting or importing it into a timeline. The compiler is not a trust boundary by itself; both input and output require validation.

Browser preview may render the compiled timeline data, show a schema-derived placeholder, or use a rendered thumbnail once available. It must not execute schema-sequence source as code because schema-sequences are intentionally data-only. If the compiler cannot produce ordinary timeline data, the editor should surface a structured validation or compilation failure instead of inserting a partially trusted clip.

### Lane 3: generated Remotion modules

The Remotion module lane is the only lane that allows generated code, and that permission exists only in worker render infrastructure. A generated module is a proposed artifact with a manifest, source or bundle reference, declared props schema, declared asset references, dependency policy metadata, validation status, and rendered preview outputs. A timeline clip enters this lane only when it has:

```ts
clip.generation?.sequence_lane === 'remotion_module'
clip.generation?.artifact_id // non-empty string
```

The Reigh browser editor must never import, bundle, evaluate, or execute generated module source. Editor surfaces may show artifact status, validation errors, thumbnails, rendered previews, a schema-derived fallback card, or a blocked-render state. They may inspect validated manifest metadata and props schema, but not run the module.

Generated module execution belongs in a worker sandbox with explicit controls:

- Load artifacts only by authenticated `artifact_id` after project ownership and timeline access checks.
- Validate the manifest before bundling or rendering.
- Enforce an import/dependency allowlist. Generated modules must not fetch arbitrary packages at render time.
- Deny arbitrary network access unless a dependency policy later allows a specific internal fetch path.
- Resolve media only through approved asset registry entries or signed storage references.
- Apply CPU, memory, duration, output-size, and wall-clock time limits.
- Run bundling/rendering in an isolated Node/Chromium/Remotion process or equivalent worker boundary, not in the web app process.
- Return structured failures for validation, bundle, dependency, asset, timeout, and render errors.
- Emit route and artifact observability so generated module failures are distinguishable from normal theme-package render failures.

Generated module clips must route through the explicit lane discriminant described in `## Generated Sequence Artifact Discriminant`. A malformed `remotion_module` clip with a missing `artifact_id` is blocked. An unknown `clipType` without the module lane still uses the existing unknown-clip placeholder behavior. A valid module-lane clip with any `clipType`, registered or novel, routes to the worker path because the lane metadata has precedence.

### Cross-lane contract

The three lanes share these contracts:

- Every accepted lane must produce or reference timeline data that validates against the aligned shared timeline schema at persistence, import, and worker-render boundaries.
- Existing timelines and trusted v1 clips require no migration to remain loadable and renderable.
- New artifact records, storage buckets, manifests, compiled previews, and lane metadata are proposed additive surfaces. They should link to timelines and clips, not replace `TimelineConfig` and `AssetRegistry` as the compiled persistence model.
- `clip.generation` is provenance and routing metadata. It is not a license for the browser editor to run code.
- Validation must happen before persistence, before timeline import, before render routing, and again inside the worker when a generated module is loaded.
- Disabling `schema_sequence` or `remotion_module` rollout flags must leave `trusted_v1` authoring, timeline loading, native preview, and existing render routes operational.

The architecture deliberately keeps lane boundaries strict. Trusted drafts stay simple; schema-sequences add declarative expressiveness without code; generated Remotion modules get maximum flexibility only after artifact validation and worker sandboxing.

## Reigh Data Model And Storage Contracts

Generated sequence support should minimize migration by keeping compiled timeline output in the existing timeline row. The current durable editor state remains:

- `timelines.config`: the persisted `TimelineConfig`.
- `timelines.asset_registry`: the persisted `AssetRegistry`.
- `timelines.config_version`: the optimistic concurrency token used by editor saves, agent saves, and `timeline-import`.

New sequence artifacts are proposed additive records around that existing row. They explain where a clip came from, how it was validated, where generated module source or bundle data lives, and what preview/render outputs exist. They do not replace `TimelineConfig`, `AssetRegistry`, row actions, clip metadata, or the versioned save path.

### Compiled timeline data

The compiled output contract is the same for all lanes:

- Trusted v1 inserts ordinary clips through the existing draft insertion flow.
- Schema-sequences compile into ordinary `TimelineConfig` clips and `AssetRegistry` entries before persistence or import.
- Generated Remotion module clips persist normal timeline placement, timing, track, and asset references in `TimelineConfig`, with lane metadata in `clip.generation`.

`clip.generation` may link a clip to a generated sequence artifact, but the clip still needs enough normal timeline data for editing, ordering, undo, import, conflict checks, and render routing. Existing timeline rows do not need backfill. Existing trusted sequence clips can continue to omit `clip.generation`.

### Proposed artifact table

Add a proposed table, for example `generated_sequence_artifacts`, with row-level security tied to project ownership. The exact migration can change, but the row contract should include:

- `id`: artifact UUID, used by `clip.generation.artifact_id`.
- `project_id`: owning Reigh project.
- `timeline_id`: nullable or required depending on whether artifacts can be drafted before insertion; once attached to a timeline, it must match the clip's timeline.
- `lane`: `trusted_v1`, `schema_sequence`, or `remotion_module`.
- `status`: `draft`, `validating`, `valid`, `compile_failed`, `bundle_failed`, `render_failed`, `ready`, or `archived`.
- `schema_version` and `compiler_version`: required for schema-sequence artifacts and useful for audit.
- `artifact_version`: monotonically increasing per artifact when a source or manifest changes.
- `source_hash`: deterministic hash of the accepted source or manifest inputs.
- `source_json`: proposed JSON payload for schema-sequences, or trusted provenance metadata for v1 if recorded.
- `manifest_json`: proposed generated module manifest, props schema, dependency policy, and declared asset references.
- `compiled_clip_ids`: optional list of clips currently linked to this artifact.
- `validation_errors`: structured errors safe to show in the editor.
- `created_by`, `created_at`, `updated_at`: audit fields.

For `trusted_v1`, artifact rows are optional provenance only. Do not require an artifact row to keep existing trusted draft clips working. For `schema_sequence`, artifact rows are useful for recompile, audit, and ArtAgents parity, but the compiled timeline remains the renderable source. For `remotion_module`, the artifact row is required because the worker must load and validate a concrete source/manifest/bundle by `artifact_id`.

### Proposed artifact storage

Add proposed storage locations for generated artifacts, separate from the existing compiled timeline fields:

- Proposed bucket or prefix for schema-sequence source JSON and compiler reports.
- Proposed bucket or prefix for generated Remotion module source, bundle artifacts, manifest snapshots, and bundle logs.
- Proposed bucket or prefix for rendered previews, thumbnails, and validation snapshots.

Storage paths should be scoped by project, timeline, artifact id, and artifact version, for example:

```text
generated-sequences/{project_id}/{timeline_id}/{artifact_id}/{artifact_version}/manifest.json
generated-sequences/{project_id}/{timeline_id}/{artifact_id}/{artifact_version}/source.tsx
generated-sequences/{project_id}/{timeline_id}/{artifact_id}/{artifact_version}/bundle/
generated-sequences/{project_id}/{timeline_id}/{artifact_id}/{artifact_version}/previews/
```

These paths are proposed, not existing files or buckets. They should be private by default. Browser editor reads should go through authenticated APIs or signed URLs for preview outputs only. Generated module source and bundles should be readable by worker infrastructure and restricted admin/debug tools, not by arbitrary browser code.

Media that becomes part of the timeline should continue to be represented in `AssetRegistry.assets`. If a generated artifact emits a poster, preview, audio stem, or intermediate media asset that is used by timeline clips, register it through the existing asset registry contract and storage conventions so render materialization can resolve it like any other asset.

### Asset registry rules

The asset registry remains the only accepted bridge from timeline data to media. New lanes must follow these rules:

- Persist asset references as registry keys or storage paths in `AssetRegistryEntry`, not raw model-returned URLs inside clip params.
- Validate that every schema-sequence or generated module asset reference exists in the caller-authorized registry before compile or render.
- Preserve duration metadata for generated video/audio assets when it is known, because existing editor timing uses clip spans and registry metadata to avoid incorrect media behavior.
- Reject artifact manifests that reference assets outside the owning project or timeline authorization boundary.
- Keep `src/tools/video-editor/sequences/materialize.ts` as the model for render-time URL materialization: persisted params stay stable, while render payloads receive resolved URLs only at the edge/client/worker boundary that needs them.

## Edge Function And Timeline Import Contracts

The current `ai-generate-sequence` edge function remains the trusted v1 authoring path. It should keep the current validation behavior and continue returning data-only drafts unless a future, explicitly gated endpoint version adds another lane.

### Proposed lane-aware edge flow

Add proposed lane-aware behavior through either a new `ai-generate-sequence-v2` edge function or an explicit `mode`/`lane` request field on a new versioned route. Do not silently change the existing v1 request contract.

The lane-aware edge flow should:

- Authenticate the user and verify project/timeline access before using selected assets or writing artifacts.
- Select a lane explicitly: `trusted_v1`, `schema_sequence`, or `remotion_module`.
- Reuse the trusted v1 validator for `trusted_v1`; do not weaken it.
- Validate schema-sequence JSON before storing it, compile it to timeline data, validate the compiled result against the aligned `@banodoco/timeline-schema`, and validate registry references before returning or importing it.
- For generated Remotion modules, persist a proposed artifact row and source/manifest storage object, enqueue validation/bundling work, and return artifact status. The edge function should not return source for browser execution.
- Attach `clip.generation.sequence_lane`, `artifact_id`, `artifact_version`, and `compiler_version` only after the artifact and compiled timeline output are valid for that lane.
- Use idempotency keys supplied by the caller for retryable artifact creation; do not rely on server-generated request ids for deduplication.
- Return structured failure codes such as `schema_validation_failed`, `asset_validation_failed`, `compile_failed`, `artifact_persist_failed`, `module_policy_failed`, and `render_route_blocked`.

The edge function can either return compiled edits to the editor for normal insertion or call `timeline-import`/versioned save infrastructure on behalf of an automated workflow. In both cases, the accepted compiled output is still `TimelineConfig` plus `AssetRegistry`.

### timeline-import requirements

`supabase/functions/timeline-import/handler.ts` is already the right persistence boundary for external publishers such as ArtAgents. New generated sequence lanes should use or preserve these requirements:

- `project_id` must be present and must be a UUID.
- `timeline_id` must be present and must be a UUID.
- The caller must authenticate with a user JWT on the current `timeline-import` path; service-role-only calls are rejected by `supabase/functions/timeline-import/index.ts`.
- The function must verify project ownership with `verifyProjectOwnership()` before writing.
- If the timeline row already exists, the row's `project_id` must match the request `project_id`.
- The request `timeline` must pass `TimelineConfigSchema.safeParse()` from the aligned `@banodoco/timeline-schema`.
- The optional `asset_registry` envelope must be object-shaped with `asset_registry.assets` as an object, and each asset entry must be an object.
- If `asset_registry` is present, writes go through `update_timeline_versioned`; otherwise writes go through `update_timeline_config_versioned`.
- `expected_version` must be honored when present. When omitted for the force path, the function reads the current `config_version` and sends that as the expected value, giving last-write-wins semantics.
- If the versioned RPC returns no rows, the response must be `409` with `error: "version_mismatch"` and the current version.
- `create_if_missing: true` may insert a new timeline row with `config_version: 1`; without it, a missing timeline remains `404`.

Generated sequence support adds only lane-specific validation around this boundary. It should not bypass `timeline-import`, `config_version`, ownership checks, or asset registry validation. A schema-sequence publish from ArtAgents and a generated module publish from a worker should both produce aligned timeline JSON and registry data before crossing this boundary.

### Import-time generated sequence validation

Add import-time checks for generated sequence metadata without making base timeline schema reject older clips:

- `clip.generation.sequence_lane === 'trusted_v1'` is accepted as provenance, but absence of that field remains valid for existing trusted clips.
- `clip.generation.sequence_lane === 'schema_sequence'` may require a valid `artifact_id` only when a source artifact is supplied or linked. The compiled timeline must be renderable without reinterpreting source.
- `clip.generation.sequence_lane === 'remotion_module'` requires a non-empty `artifact_id` and an artifact row visible to the project/timeline owner.
- Unknown lane strings should be rejected by generated-sequence validation, even if the base shared schema keeps `clip.generation` open for compatibility.
- Any lane metadata that references an artifact from another project or an unauthorized timeline must be rejected.

These checks can live in proposed helper modules used by the edge function, `timeline-import`, and worker render enqueue path. They should be tested independently of the broad shared schema parse.

## Renderer And Worker Contracts

The renderer contract has two layers: route selection in Reigh and execution in the selected renderer.

### Route selection

`src/tools/video-editor/lib/renderRouter.ts` should remain the single render-button route decision surface. It already builds `banodoco_render_timeline` payloads with `timeline_id`, materialized timeline data, `assets`, `theme_id`, `output_filename`, `user_jwt`, `project_id`, and `correlation_id`. Generated sequence support should extend that payload contract instead of creating an unrelated render path.

Route selection requirements:

- Native and legacy timelines without generated module lanes may continue to route to the client renderer.
- Registered theme-package timelines may continue to route to `banodoco_render_timeline`.
- Valid `remotion_module` clips must route to the worker/orchestrator path by lane metadata before clip type checks.
- Malformed `remotion_module` clips must produce a blocked/error decision, never a client render.
- Schema-sequence clips should route according to their compiled clip types unless they also contain a generated module lane, because schema-sequences are already compiled into ordinary timeline data.
- Route decisions must include reason values that distinguish theme-package rendering, generated module rendering, malformed module metadata, and mixed timelines.

### Worker payload and execution

The worker render payload for generated modules should include the same base data as `BanodocoRenderTimelinePayload`, plus proposed generated-artifact references:

- `timeline_id`, `project_id`, `correlation_id`, and user authorization context.
- Materialized `timeline` validated against the aligned shared schema.
- `assets` as the current asset registry envelope.
- A list of generated module artifact ids and versions required by the timeline.
- Render policy metadata, including dependency allowlist version, network policy, resource limits, and timeout.

The worker must validate the payload again before execution. It should confirm project/timeline access, validate the timeline shape, validate all module artifacts and manifests, resolve assets only through approved registry/storage paths, and fail closed when any artifact is missing, unauthorized, stale, oversized, or blocked by dependency policy.

Generated Remotion module source, bundles, and props are worker-only inputs. Browser preview and editor playback should use thumbnails, rendered preview assets, structured status, or a placeholder. The worker may render final outputs and preview outputs, then register any reusable media output through the existing asset registry when it becomes part of the timeline.

### Structured renderer failures

Renderer failures should be structured enough for rollout, support, and rollback:

- `route_blocked`: route decision rejected malformed lane metadata.
- `artifact_missing`: referenced artifact id does not exist or is not visible to the project.
- `artifact_not_ready`: artifact exists but has not passed validation/bundling.
- `manifest_invalid`: generated module manifest failed schema or policy validation.
- `asset_missing`: referenced asset registry key is absent.
- `dependency_blocked`: module import or package dependency violates policy.
- `sandbox_timeout`: bundle or render exceeded resource limits.
- `render_failed`: Remotion execution failed after validation.

These failures should be visible as artifact status and render-task telemetry, while leaving trusted v1 and schema-sequence compiled timelines operational.

## Editor UX And Migration Path

The editor rollout should preserve the current sequence creator as the safe default. `src/tools/video-editor/components/SequenceCreator/SequenceCreatorPanel.tsx` currently opens a trusted authoring surface, calls `ai-generate-sequence`, validates returned drafts, previews materialized draft params, and inserts or replaces clips through `buildInsertSequenceDraftEdit()` and `buildReplaceSequenceDraftEdit()`. That behavior remains the default mode.

### Default editor behavior

- Opening `SequenceCreatorPanel` should continue to mean trusted v1 draft generation unless an explicit feature flag and user/workspace allowlist exposes another lane.
- The existing generate/edit modes should continue to call the current `ai-generate-sequence` contract and should keep returning only trusted draft data.
- Existing insert and replace actions should keep producing ordinary timeline edits, not artifact-only records.
- Existing selected and attached media behavior should keep using allowed asset keys from the editor registry.
- Existing validation failures should stay local and actionable; new lane errors should not make trusted v1 harder to use.

Do not turn the trusted panel into a generated-code prompt box. If schema-sequences or Remotion modules share the same visual entry point later, they need an explicit lane control, separate explanatory status, and independent feature gating. A user should be able to opt into an advanced lane without changing the semantics of the trusted v1 button.

### Schema-sequence editor UX

Schema-sequences should appear as compiled data, not executable source. The editor UX should:

- Request a schema-sequence only through an explicit `schema_sequence` lane.
- Show validation and compiler status before insertion.
- Preview compiled timeline output, schema-derived placeholders, or rendered previews.
- Insert compiled clips and asset registry entries through the same timeline edit pipeline used by ordinary clips.
- Keep an optional source/artifact inspector read-only unless a dedicated schema editor is intentionally built.
- Offer "recompile" and "detach from source" actions only after artifact storage exists.

Schema-sequence source can be useful provenance, but the timeline remains editable as normal Reigh timeline data. If a user edits compiled clips directly, Reigh should not silently rewrite the source artifact. The relationship should be explicit: either the clip remains linked to the artifact with a dirty/diverged status, or the user detaches the link and keeps the timeline edit as ordinary data.

### Generated Remotion module editor UX

Generated Remotion modules should appear as worker-managed artifacts. The editor UX should:

- Request a module only through an explicit `remotion_module` lane.
- Show artifact status such as validating, bundle failed, preview ready, render ready, or blocked.
- Show thumbnails, rendered preview video, structured validation errors, or a placeholder in the browser.
- Never import, bundle, evaluate, or execute generated module source in the editor.
- Disable final render for malformed module clips, missing artifacts, or not-ready artifacts.
- Surface `artifact_id`, artifact version, and route-decision reason for debugging, but avoid making source code part of normal editing.

The editor may allow a user to remove a generated module clip, replace it with a rendered media asset, or detach it from a source artifact. Those actions should mutate normal timeline data and artifact links; they should not require a broad timeline migration.

### Migration path

Migration should be opt-in and additive:

1. Align the shared timeline schema and regenerate package outputs.
2. Keep trusted v1 unchanged and add only observability around lane metadata absence.
3. Add schema-sequence generation behind internal flags and compile results into existing timeline edits.
4. Add proposed artifact storage for schema-sequence provenance and recompile.
5. Add generated module artifacts behind a stricter allowlist, with worker-only validation and preview.
6. Add broader editor controls only after render-router, artifact, and worker failure modes are observable.

Existing rows do not need mandatory migration. Existing trusted sequence clips can continue without `clip.generation`. If Reigh later adds provenance to new trusted clips, that should happen only for new inserts or explicit backfill jobs with rollback, not as a required read-time transformation for all timelines.

Read-side compatibility should be forgiving:

- Missing `clip.generation` means legacy or trusted ordinary clip.
- `sequence_lane: 'trusted_v1'` is provenance only.
- `sequence_lane: 'schema_sequence'` should not be required for compiled schema-sequence output to render if the compiled clips are otherwise ordinary.
- `sequence_lane: 'remotion_module'` is strict and requires `artifact_id`; malformed module clips should be blocked instead of migrated silently.

Rollback should be simple. Disabling schema-sequence and module flags should hide advanced entry points, prevent new advanced artifacts, leave existing artifact-linked clips visible, and keep trusted v1 generation and ordinary timeline editing operational.

## ArtAgents Parity And Publish Path

ArtAgents already produces Reigh-compatible timeline and asset JSON. The current surfaces are:

- `artagents/timeline.py`: loads, saves, and validates `hype.timeline.json` and `hype.assets.json`; it imports shared `banodoco_timeline_schema` types and validation when available, then runs Banodoco semantic checks.
- `artagents/publish.py`: uploads non-HTTP assets to the Reigh `timeline-assets` bucket, rewrites the asset registry, fetches or accepts `expected_version`, and posts `{ project_id, timeline_id, timeline, asset_registry, expected_version, create_if_missing }` to `timeline-import`.
- `artagents/open_in_reigh.py`: manual handoff helper that explicitly warns that Reigh stores timeline data in `public.timelines` rows with `config` and `asset_registry`.
- `bin/render_remotion.py` and `remotion/src/Root.tsx`: local Remotion rendering path for ArtAgents timeline/assets JSON.
- `scripts/gen_remotion_types.py` and `remotion/src/types.generated.ts`: current Remotion type generation from `artagents.timeline`.
- `tests/test_schema_contract.py`: roundtrip and generator drift coverage for ArtAgents examples and generated types.

That is close to the target shape, but parity requires removing schema drift as a product dependency. ArtAgents must consume regenerated shared schema outputs from `../../banodoco-workspace/packages/timeline-schema`, not maintain a parallel timeline contract.

### Shared schema consumption

ArtAgents should treat the regenerated shared package as its timeline contract:

- Python validation should import `banodoco_timeline_schema.validate_timeline` and generated TypedDicts from the regenerated package.
- `artagents/timeline.py` may keep Banodoco-specific semantic checks such as effect registry checks, arrangement validation, pool validation, and transition validation, but persisted timeline shape should come from the shared package.
- Fallback TypedDicts in `artagents/timeline.py` are acceptable only for local developer bootstrapping. They must not become the authoritative contract for publish or CI.
- `scripts/gen_remotion_types.py` should either generate Remotion types from the shared schema-derived Python types or be checked against them so `remotion/src/types.generated.ts` cannot drift from Reigh's persisted shape.
- `tests/test_schema_contract.py` should fail when examples or generated types diverge from the regenerated shared schema outputs.

After schema alignment, ArtAgents should accept the same `output`, optional `theme`, optional `theme_overrides`, optional `generation_defaults`, open `clip.generation`, and asset registry envelope behavior that Reigh accepts at `timeline-import`.

### Publishing schema-sequences

For schema-sequences, ArtAgents should be able to act as an external authoring environment:

- Author or receive a schema-sequence JSON source.
- Validate the source against the proposed schema-sequence schema.
- Compile it into `hype.timeline.json` and `hype.assets.json`.
- Validate the compiled timeline with regenerated `banodoco_timeline_schema`.
- Optionally emit an artifact sidecar manifest with source hash, compiler version, schema version, and clip ids.
- Publish the compiled timeline/assets through `artagents/publish.py` and `timeline-import`.

If Reigh artifact APIs are not ready, ArtAgents can still publish compiled ordinary timeline data without requiring existing Reigh rows to migrate. Once proposed artifact storage exists, ArtAgents should create or upload the artifact first, then include `clip.generation.sequence_lane: 'schema_sequence'`, `artifact_id`, `artifact_version`, and `compiler_version` on compiled clips that need provenance.

### Publishing generated Remotion modules

Generated Remotion modules need stricter parity because local ArtAgents rendering is not the same as Reigh worker execution. ArtAgents may use `bin/render_remotion.py` for local proof renders, but publishing to Reigh must use Reigh's proposed artifact and worker contract:

- Produce a module manifest, props schema, declared asset references, dependency metadata, and source or bundle artifacts.
- Validate the manifest and asset references locally before upload.
- Upload module source/bundle/manifest through the proposed Reigh artifact API or storage path, not through direct timeline JSON alone.
- Wait for or record Reigh-side artifact validation status.
- Publish timeline clips with `clip.generation.sequence_lane === 'remotion_module'` and the Reigh artifact id/version.
- Use `timeline-import` for the compiled timeline and asset registry only after the artifact id is valid for the target project/timeline.

ArtAgents must not assume that a local generated module source path can be opened by the Reigh browser editor. Local file paths, dev-server URLs, and unsandboxed module imports are not publishable runtime contracts.

### Open-in-Reigh path

`artagents/open_in_reigh.py` is useful for manual file handoff, but generated sequence parity should prefer the real publish path:

- For production or shared projects, use `artagents/publish.py` so assets are uploaded, registry entries are rewritten, and `timeline-import` enforces ownership and version behavior.
- For schema-sequence artifacts, include a sidecar only as a reference until proposed artifact APIs exist.
- For generated Remotion modules, do not rely on manual copies; publish through artifact storage and worker validation.

The ArtAgents UX can expose "Open in Reigh" only after it knows whether the output is trusted compiled data, schema-sequence compiled data, or a generated module requiring artifact upload. The command should fail closed when module artifacts are not uploaded or validation has not passed.

### Parity acceptance criteria

ArtAgents parity is reached when:

- `artagents/timeline.py`, `artagents/publish.py`, `bin/render_remotion.py`, and `remotion/src/types.generated.ts` all agree with the regenerated shared schema.
- `hype.timeline.json` and `hype.assets.json` examples validate against both ArtAgents semantic checks and Reigh `timeline-import`.
- `artagents/publish.py` can publish compiled schema-sequence timelines with asset registry entries and version checks.
- Generated module artifacts are uploaded to proposed Reigh artifact storage before `remotion_module` clips are imported.
- No ArtAgents flow requires direct Supabase table writes, local asset paths in Reigh runtime data, hand-maintained schema forks, or browser execution of generated module source.

## Validation And Automated Test Matrix

Validation has to prove the lane boundary, the compiled persistence contract, and the cross-repo schema contract together. A test that only checks one surface is not enough for rollout if another surface can still accept stale schema output, unsafe source, a missing asset, or a cross-project artifact.

### Existing anchors to keep and extend

Reigh already has several useful anchors:

- `supabase/functions/ai-generate-sequence/index.test.ts`: edge entrypoint coverage for the trusted sequence generator.
- `supabase/functions/ai-generate-sequence/sequence-validation.ts`: trusted v1 server validator that should continue rejecting code, raw URLs, arbitrary animation refs, unknown root fields, and asset references outside the allowed registry set.
- `src/tools/video-editor/sequences/validation.test.ts`: browser-side trusted draft validator coverage.
- `src/tools/video-editor/sequences/materialize.ts`: materialization boundary for converting allowed asset keys into render-time URLs without mutating persisted params.
- `src/tools/video-editor/lib/renderRouter.test.ts`: render routing coverage, including unknown and absent clip types.
- `supabase/functions/timeline-import/handler.test.ts`: import coverage for `asset_registry`, versioned updates, `expected_version`, `version_mismatch`, create/update behavior, and ownership-sensitive calls.

The shared schema package at `../../banodoco-workspace/packages/timeline-schema` already has the release-critical drift gates:

- `package.json` scripts: `npm run build`, `npm run gen:python`, `npm run check:codegen`, and `npm test`.
- `Makefile`: `make check` runs `check-codegen` and tests.
- `scripts/check-codegen.sh`: regenerates TypeScript-derived JSON Schema and Python types, then fails when generated artifacts are stale.
- `typescript/tests/resolveTheme.test.ts` and `tests/test_materialize_output.py`: current TypeScript/Python contract tests.
- Generated outputs: `python/banodoco_timeline_schema/timeline.schema.json` and `python/banodoco_timeline_schema/generated.py`. These must be diff-checked, not manually edited.

ArtAgents already has parity anchors that should be kept in the rollout gate:

- `tests/test_schema_contract.py`: timeline/assets examples, schema roundtrips, and generated type drift.
- `tests/test_publish.py`: publish behavior around assets, tokens, `expected_version`, and `timeline-import`.
- `tests/test_render_remotion_registry.py`: local Remotion render wrapper and registry handling.
- `tests/test_open_in_reigh.py`: manual handoff behavior and guardrails.
- `tests/test_validate.py`: ArtAgents timeline validation behavior.
- `tests/test_pure_generative_pipeline.py`, `tests/test_composition_primitives.py`, and `tests/test_hype_cut_invariants.py`: pipeline and composition invariants that protect generated timeline structure.

### Required lane test matrix

Trusted v1 must stay strict:

- Positive: a known good trusted draft generated by `ai-generate-sequence` validates on the server, validates in the browser, inserts through the existing sequence draft path, persists as ordinary `TimelineConfig`, and renders without artifact records.
- Negative: `code`, `component`, `jsx`, `tsx`, `html`, `script`, `imports`, `source`, `render`, arbitrary animation refs, raw URLs, unknown root keys, and asset keys outside the allowed set are rejected in both `sequence-validation.ts` and `src/tools/video-editor/sequences/validation.test.ts`.
- Regression: adding schema-sequence or module support must not change the default `SequenceCreatorPanel` behavior or allow trusted v1 drafts to carry generated source.

Schema-sequences need compiler and import coverage:

- Positive: a valid schema-sequence source compiles deterministically into ordinary timeline JSON plus asset registry JSON, validates against regenerated `@banodoco/timeline-schema` outputs, and imports through `timeline-import`.
- Negative: malformed operations, missing required fields, oversized schemas, missing assets, raw URLs where only registry keys are allowed, unsupported media or transition declarations, schema version mismatches, and stale schema outputs are rejected before persistence.
- Determinism: the same source, compiler version, asset registry, and schema version must produce the same compiled timeline and artifact hash.
- Compatibility: compiled clips use current supported clip types, preserve ordinary render routing, and do not require existing timeline rows to migrate.

Generated Remotion modules need artifact, sandbox, and router coverage:

- Positive: a valid proposed artifact manifest with declared props, declared assets, dependency metadata, and a project-owned `artifact_id` can route to the worker path when a clip has `clip.generation.sequence_lane === 'remotion_module'`.
- Negative: missing `artifact_id`, artifact project mismatch, unsupported imports, undeclared dependencies, raw network access, raw URLs outside declared assets, missing assets, malformed props, oversized bundles/manifests, code injection through manifest fields, timeouts, memory or frame-budget failures, and failed worker validation must produce structured failures.
- Router safety: unknown clip types and absent clip types still follow the existing client/placeholder fallback unless explicit module lane metadata is present; a module-lane clip with missing or invalid artifact metadata must fail closed rather than route to the client renderer.
- Browser safety: tests should assert the editor never imports or evaluates generated module source. Browser previews may only read artifact status, thumbnails, rendered previews, placeholders, or schema-derived fallback data.

`timeline-import` remains the persistence gate:

- Positive: Reigh, ArtAgents, and future artifact APIs publish compiled output through `{ project_id, timeline_id, timeline, asset_registry, expected_version, create_if_missing }` using user JWT auth and versioned update semantics.
- Negative: invalid UUIDs, cross-user access, existing timeline rows from another project, service-role publish attempts on the user path, invalid `TimelineConfig`, invalid `asset_registry` envelope, version conflicts, stale `expected_version`, and missing ownership checks fail before writes.
- Concurrency: `version_mismatch` responses must be asserted for stale writes, and callers must not silently overwrite newer editor changes.

### Drift and CI gates

Every implementation PR for this architecture should have an explicit test gate list. The minimum gate is:

- Reigh: run the focused sequence, render router, and timeline import suites that include `supabase/functions/ai-generate-sequence/index.test.ts`, `src/tools/video-editor/sequences/validation.test.ts`, `src/tools/video-editor/lib/renderRouter.test.ts`, and `supabase/functions/timeline-import/handler.test.ts`.
- Shared schema: run `make check` or the equivalent `npm run build`, `npm run check:codegen`, `npm test`, and Python tests from `../../banodoco-workspace/packages/timeline-schema`.
- ArtAgents: run the schema/publish/render validation tests covering `tests/test_schema_contract.py`, `tests/test_publish.py`, `tests/test_render_remotion_registry.py`, `tests/test_open_in_reigh.py`, and `tests/test_validate.py`.
- Drift: fail CI if regenerated `timeline.schema.json`, `generated.py`, or ArtAgents generated Remotion types are stale after codegen.
- Security negatives: require explicit tests for code injection, raw URLs, missing assets, oversized schemas, unsupported imports, unknown clip types, stale schema outputs, timeouts, version conflicts, and cross-user access before enabling schema-sequence or generated-module flags beyond internal allowlists.

### Review rules for new tests

Tests should assert failure reasons, not only rejection booleans. The implementation needs enough structured error output to tell whether a failure came from schema validation, asset validation, artifact ownership, router selection, worker sandboxing, timeout, or optimistic-lock conflict.

Manual editor review can supplement rollout, but it cannot replace automated gates for lane selection, schema drift, ownership, import versioning, and generated-code sandbox boundaries.

## Deployment Observability Rollout And Rollback

Rollout should be staged around independent lane controls, not a single global "generated sequences" switch. The trusted v1 path is the operational baseline and should remain enabled through every schema-sequence or generated-module rollout and rollback.

### Feature flags and allowlists

Use separate controls for authoring, persistence, and rendering:

- `generated_sequences.trusted_v1.enabled`: existing safe path. This should default on and should not be coupled to advanced lane failures.
- `generated_sequences.schema_sequence.authoring_enabled`: exposes schema-sequence authoring or import entry points.
- `generated_sequences.schema_sequence.compile_enabled`: allows schema-sequence sources to compile into `TimelineConfig` and `AssetRegistry`.
- `generated_sequences.schema_sequence.import_enabled`: allows compiled schema-sequence output to call `timeline-import` with lane provenance.
- `generated_sequences.remotion_module.authoring_enabled`: exposes generated-module authoring or upload entry points.
- `generated_sequences.remotion_module.artifact_persist_enabled`: allows proposed artifact records and storage objects to be written.
- `generated_sequences.remotion_module.worker_render_enabled`: allows validated module artifacts to route to the worker path.
- `generated_sequences.remotion_module.editor_preview_enabled`: allows browser preview to show artifact status, thumbnails, rendered previews, or schema-derived fallback views. This flag must never allow browser execution of module source.

Each advanced lane should also have internal allowlists before broad rollout:

- User allowlist for early Reigh editor use.
- Project or workspace allowlist for shared test projects.
- ArtAgents publish allowlist for external schema-sequence and generated-module artifacts.
- Worker allowlist for generated-module render execution.
- Dependency-policy allowlist for generated module packages, if stakeholders choose to allow anything beyond the base Remotion/runtime set.

Allowlist failures should return structured "not enabled" responses, not fall through into trusted v1 validators or ordinary render routes.

### Shadow validation and dry runs

Before enabling writes or worker execution, run the new validators in shadow mode:

- Trusted v1 requests can record whether advanced-lane metadata is absent, malformed, or unexpectedly present without changing response behavior.
- Existing timelines can be sampled through the aligned shared schema validator to measure compatibility before making it a hard gate on new imports.
- Schema-sequence sources can be accepted in dry-run mode that validates and compiles, records the artifact hash and compiled diff summary, but does not write `timelines.config`, `timelines.asset_registry`, or proposed artifact rows.
- Generated module submissions can perform artifact dry runs: parse manifest, check declared assets, check dependency policy, compute source/bundle hashes, run static validation, and optionally execute a sandbox smoke render without publishing importable clips.
- ArtAgents can dry-run publish by producing the final `timeline-import` payload, uploaded-asset plan, artifact manifest, and expected version without mutating Reigh.

Shadow results should use the same error taxonomy as real writes. That makes a later hard gate mostly a policy change, not a new diagnostic surface.

### Observability

Every lane decision needs correlation ids that tie together editor action, edge validation, artifact persistence, import, render routing, worker execution, and ArtAgents publish. The minimum events are:

- `generated_sequence.validation`: lane, schema version, compiler version, artifact type, result, failure code, project id, timeline id, user id, and correlation id.
- `generated_sequence.artifact`: proposed artifact id, artifact version, storage object hashes, validation status, dependency policy result, asset validation result, and correlation id.
- `generated_sequence.timeline_import`: lane, expected version, resulting config version, asset registry result, ownership result, and conflict status.
- `generated_sequence.render_route`: `RenderRouteDecision.route`, `RenderRouteDecision.reason`, lane counts, malformed lane counts, artifact ids, and whether the route was blocked.
- `generated_sequence.worker_render`: artifact id/version, sandbox policy version, timeout class, dependency class, frame failure, output status, and worker/job id.
- `generated_sequence.artagents_publish`: ArtAgents run id, payload mode, schema package version or hash, generated type version/hash, dry-run status, and import response.

Dashboards should separate trusted v1 validation failures, schema-sequence schema/compiler failures, module artifact failures, timeline-import failures, render-route failures, and worker execution failures. A spike in one advanced lane should not be hidden inside ordinary render failure rates.

Render-route observability is especially important. `decideRenderRoute()` should emit or expose the reason branch for:

- pure native/client timelines;
- theme-package worker timelines;
- mixed theme and native timelines;
- valid generated module timelines;
- mixed generated module and other timelines;
- missing or invalid module artifacts;
- unknown clip type fallback with no generated lane metadata;
- safety-net blocked module branch when module rendering is disabled.

### Rollout sequence

Rollout should proceed in phases:

1. Add passive lane metadata parsing, render-route reason observability, and validation telemetry while all advanced authoring flags are off.
2. Enable shared-schema alignment and shadow validation on sampled timelines and ArtAgents examples.
3. Enable schema-sequence dry runs for internal users, without timeline writes.
4. Enable schema-sequence compile/import for allowlisted projects after drift gates and import conflict behavior are stable.
5. Enable proposed module artifact dry runs for internal users, without imported module clips.
6. Enable generated module artifact persistence for allowlisted projects, while worker rendering remains disabled.
7. Enable worker render for allowlisted projects after module manifest, dependency, asset, timeout, and route-blocking telemetry is stable.
8. Expand ArtAgents publish only after it uses regenerated shared schema outputs and can dry-run or publish through the same Reigh gates.

Stakeholders still need to choose the first advanced lane to ship. The lowest-risk route is schema-sequence dry run, because it compiles to ordinary timeline data and does not execute code.

### Rollback controls

Rollback must be independent by lane and by stage:

- Disable schema-sequence authoring without disabling existing trusted v1 drafts.
- Disable schema-sequence compile/import while preserving previously compiled ordinary timeline clips as editable timeline data.
- Disable generated module authoring while keeping artifact status pages and existing compiled timeline clips visible.
- Disable generated module artifact persistence without deleting existing proposed artifacts.
- Disable generated module worker rendering while leaving the render-router safety-net branch active.
- Disable ArtAgents advanced publish while allowing ordinary timeline/assets publish through the existing `timeline-import` contract.

Rollback should not delete timeline rows, remove `clip.generation`, rewrite existing configs, or mutate asset registries automatically. If cleanup is needed, it should be an explicit follow-up job with project scoping, dry-run output, and restore instructions.

### Safety-net render-router branch

The render router needs a safety-net branch that remains deployed even when module authoring or worker rendering is disabled. If a timeline contains `clip.generation.sequence_lane === 'remotion_module'`, the router must recognize the lane before the unknown-clip fallback. When module rendering is disabled or the artifact is invalid, the route decision should be blocked with a structured reason such as `remotion_module_disabled`, `remotion_module_missing_artifact`, or `remotion_module_artifact_invalid`.

That safety net protects rollbacks and partial deployments. A disabled generated-module lane should not cause module clips to render in the browser as unknown client clips, and it should not make trusted v1 or ordinary client timelines fail.

### Deployment acceptance criteria

The deployment plan is acceptable when:

- Trusted v1 generation, insertion, editing, preview, import, and rendering remain operational with every advanced flag disabled.
- Schema-sequence and generated-module flags can be toggled independently by lane and by stage.
- Internal allowlists exist before external ArtAgents or broad editor exposure.
- Shadow validation and artifact dry runs record the same structured failure codes as real writes.
- Render-route telemetry distinguishes unknown clip fallback from generated-module routing and blocked generated-module routing.
- Rollback can stop new advanced artifacts and worker execution without deleting existing timeline data or artifact records.

## Non-Negotiable Constraints

- The trusted v1 sequence creator remains the default path. Future schema or code lanes must be gated additions, not replacements for `SequenceCreatorPanel` and the current `ai-generate-sequence` draft flow.
- Trusted drafts remain data-only. The v1 validator must continue rejecting generated code, raw URLs, imports, arbitrary animation refs, unknown top-level fields, and asset references outside the selected or attached registry set.
- Browser editor execution must stay non-code. Generated Remotion module source must never execute in the Reigh browser editor; browser preview can use status, thumbnails, rendered previews, placeholders, or schema-derived fallback views.
- Persisted compiled output should continue to be ordinary `TimelineConfig` and `AssetRegistry` wherever possible. Proposed generated-sequence artifact records, buckets, manifests, and lane metadata must be additive links around the timeline, not a mandatory rewrite of existing timeline rows.
- Render routing for generated code must use explicit lane metadata, not only `clipType`. The current unknown-clip fallback means a new clip type alone can route to the client renderer.
- Existing render paths must remain operational during rollout and rollback. Disabling schema-sequences or generated modules must leave trusted v1 sequence drafts and native client rendering usable.
- Timeline imports and ArtAgents outputs must converge on the same timeline schema contract before broad rollout. Hand-maintained parallel schema shapes are not acceptable for generated sequence interchange.
- Any generated-code lane must execute in a worker sandbox with bounded dependencies, validated manifests, explicit asset access, timeouts, and structured failure output.
- Existing timelines require compatibility. Current rows with trusted sequence clip types must continue to load, edit, preview, import, and render without mandatory migration.

## Settled Decisions

- **SD-GENSEQ-001** — Preserve trusted v1 as the default sequence path. _load_bearing: true_
  Rationale: The existing path has a narrow validator, data-only draft output, editor insertion logic, and known render behavior. It is the safety baseline for every future lane.

- **SD-GENSEQ-002** — Keep trusted draft output data-only. _load_bearing: true_
  Rationale: The current validator explicitly rejects code, raw URLs, imports, and arbitrary animation references. Relaxing that validator would collapse the safety distinction between trusted drafts and generated modules.

- **SD-GENSEQ-003** — Route generated Remotion modules by explicit lane metadata, not novel `clipType`. _load_bearing: true_
  Rationale: `decideRenderRoute()` currently treats unknown clip types as client-renderable fallback so the loud placeholder can surface unsupported clips. Generated-code routing needs a discriminator that cannot be mistaken for ordinary unknown media.

- **SD-GENSEQ-004** — Keep compiled timeline persistence on `TimelineConfig` plus `AssetRegistry` unless a later migration explicitly changes it. _load_bearing: true_
  Rationale: Editor commits, edge-agent saves, timeline import, render payload building, and existing rows already depend on these persistence fields.

- **SD-GENSEQ-005** — Use `@banodoco/timeline-schema` as the canonical persisted timeline contract after alignment. _load_bearing: true_
  Rationale: Reigh, ArtAgents, timeline import, and worker render payloads need one shared contract. Local editor-only types may stay richer, but persisted and exchanged timeline JSON must validate against the shared package.

- **SD-GENSEQ-006** — Regenerate JSON Schema and Python types from the shared package source; never hand-edit generated schema artifacts. _load_bearing: true_
  Rationale: The package already has a Zod source, JSON Schema emitter, Python TypedDict generator, and codegen drift gate. Manual edits would recreate the drift this plan is meant to remove.

- **SD-GENSEQ-007** — Discriminate generated Remotion modules with `clip.generation.sequence_lane`, not `clipType`. _load_bearing: true_
  Rationale: The current render router intentionally treats unknown clip types as client-renderable placeholder fallback. Generated code needs explicit lane metadata so it cannot enter the browser/client render path by accident.

- **SD-GENSEQ-008** — Require `clip.generation.artifact_id` for `remotion_module` clips. _load_bearing: true_
  Rationale: The worker route needs a concrete artifact to load, validate, sandbox, and observe. A module-lane clip without an artifact id is malformed and must not render through fallback behavior.

- **SD-GENSEQ-009** — Treat generated sequence support as three additive lanes with trusted v1 as the default. _load_bearing: true_
  Rationale: The current trusted draft path is the safety and rollback baseline. Schema-sequences and Remotion modules add capability through explicit lanes instead of changing what trusted drafts are allowed to contain.

- **SD-GENSEQ-010** — Compile schema-sequences as non-code JSON into ordinary timeline data. _load_bearing: true_
  Rationale: Declarative flexibility should not require browser or worker code execution. A deterministic compiler plus input/output validation keeps this lane closer to normal timeline authoring.

- **SD-GENSEQ-011** — Execute generated Remotion modules only in a worker sandbox, never in the Reigh browser editor. _load_bearing: true_
  Rationale: Generated modules may contain code, imports, and render logic. That risk belongs behind artifact validation, dependency policy, resource limits, and worker isolation rather than in the interactive editor.

- **SD-GENSEQ-012** — Keep generated sequence artifacts additive around existing timeline persistence. _load_bearing: true_
  Rationale: `timelines.config`, `timelines.asset_registry`, and `config_version` already anchor editor saves, agent writes, imports, and render payloads. New artifact rows and storage objects should link to that model rather than replacing it.

- **SD-GENSEQ-013** — Use `timeline-import` and versioned RPC semantics for external generated sequence publishes. _load_bearing: true_
  Rationale: The import path already enforces UUID inputs, user JWT auth, project ownership, existing-row project checks, shared-schema validation, asset registry shape validation, and expected-version conflict behavior.

- **SD-GENSEQ-014** — Treat generated module artifacts as worker-render inputs, not browser editor inputs. _load_bearing: true_
  Rationale: The render payload can reference validated artifact ids and versions, but source and bundle execution must stay inside the worker boundary with manifest, asset, dependency, and resource checks.

- **SD-GENSEQ-015** — Keep `SequenceCreatorPanel` trusted-v1 by default. _load_bearing: true_
  Rationale: The current panel is the known safe editor path. Advanced schema/code lanes should be explicit opt-ins behind flags and allowlists, not changes to what the default generate action means.

- **SD-GENSEQ-016** — Do not require mandatory migration of existing timeline rows. _load_bearing: true_
  Rationale: Existing trusted clips and native timelines must continue to load and render without `clip.generation` or artifact records. New lane metadata is additive and strict only where generated modules require it.

- **SD-GENSEQ-017** — Require ArtAgents to consume regenerated shared schema outputs before publishing generated sequence artifacts. _load_bearing: true_
  Rationale: ArtAgents already publishes timeline/assets JSON into Reigh. Schema-sequence and module parity depends on using the same generated schema/types as Reigh, not a handwritten or stale local contract.

- **SD-GENSEQ-018** — Make validation and tests lane-specific, with generated lanes failing closed. _load_bearing: true_
  Rationale: Trusted drafts, schema-sequences, and generated modules have different risk boundaries. Tests must prove each boundary independently so unsafe artifacts cannot fall through to ordinary client rendering or persistence.

- **SD-GENSEQ-019** — Treat shared-schema codegen drift as a release blocker. _load_bearing: true_
  Rationale: Reigh, timeline-import, worker payloads, and ArtAgents publishing depend on the same generated schema and Python/TypeScript outputs. Stale generated files recreate the cross-repo mismatch this plan is removing.

- **SD-GENSEQ-020** — Require negative security coverage before enabling advanced lanes outside internal allowlists. _load_bearing: true_
  Rationale: Schema-sequence and generated-module rollout should not depend on manual inspection for code injection, raw URLs, missing assets, unsupported imports, timeouts, version conflicts, or cross-user access.

- **SD-GENSEQ-021** — Roll out generated sequence lanes with independent authoring, persistence, and render flags. _load_bearing: true_
  Rationale: Schema-sequences and generated modules have different risk profiles and failure modes. Independent controls allow one lane or stage to pause without breaking trusted v1 or ordinary timeline editing.

- **SD-GENSEQ-022** — Keep render-route safety handling deployed even when generated-module rollout is disabled. _load_bearing: true_
  Rationale: Disabling module generation should not make existing module-lane clips fall through to unknown client rendering. The router must still recognize and block malformed or disabled module lanes explicitly.

- **SD-GENSEQ-023** — Use shadow validation and artifact dry runs before advanced-lane writes or worker execution. _load_bearing: true_
  Rationale: The safest rollout path is to measure schema, asset, artifact, route, and sandbox failures with production-shaped telemetry before those failures can mutate timeline data or start generated-code renders.

- **SD-GENSEQ-024** — Implement schema alignment and render-router safety before enabling advanced generated lanes. _load_bearing: true_
  Rationale: Schema-sequence and generated-module work depends on a single persisted timeline contract and on route decisions that cannot mistake generated code for an unknown client-rendered clip.
