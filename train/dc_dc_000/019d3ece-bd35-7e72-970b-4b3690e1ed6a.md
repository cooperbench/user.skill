        # Implementation Plan: Consolidate Media-Lightbox Persistence Architecture

## Overview

The media-lightbox editing system has 3 competing persistence mechanisms that evolved independently:

1. **`useMediaPersistence`** (`hooks/inpainting/useMediaPersistence.ts`, 353 LOC) — Manages inpaint strokes, brush size, prompt, numGenerations, editMode, and annotationMode. Uses 3-layer persistence: in-memory Map cache → localStorage → DB (for editMode). Contains the `useLayoutEffect` dependency array landmine.

2. **`useEditSettingsSync`** (`hooks/persistence/useEditSettingsSync.ts`, 134 LOC) — Bidirectional sync glue that pipes values between `useMediaPersistence` and `useEditSettingsPersistence`. Has 3 separate effects and a render-time reset, all to shuttle the same handful of fields between two hooks that shouldn't need a middleman.

3. **`useEditSettingsPersistence`** (`hooks/persistence/useEditSettingsPersistence.ts`, 343 LOC) — Coordinates per-generation settings (via `useGenerationEditSettings`/`useAutoSaveSettings`) with "last used" user-level defaults. This hook is well-structured and already uses `useAutoSaveSettings` under the hood.

**The problem:**
- `useMediaPersistence` duplicates persistence for `editMode`, `prompt`, and `numGenerations` that `useEditSettingsPersistence` already handles via `useAutoSaveSettings`. The two systems fight over who owns these values.
- `useEditSettingsSync` exists solely to reconcile them — 134 lines of sync glue.
- The `useLayoutEffect` at `useMediaPersistence.ts:246` has state values (`inpaintStrokes`, `annotationStrokes`, `inpaintPrompt`, `inpaintNumGenerations`, `brushSize`) in its dependency array even though the effect is guarded by `prevMediaIdRef.current === media.id`. Any state change re-runs the effect; the ref guard bails out, but React still pays the cost and it's a correctness risk if the guard is ever removed.
- Hook nesting reaches 5 levels: `ImageLightbox → useImageEditOrchestrator → useManagedInpaintingState → useInpainting → useMediaPersistence`.

**The goal:** Replace the 3-hook persistence triangle with a single clean ownership model where `useEditSettingsPersistence` (already backed by `useAutoSaveSettings`) owns all persisted settings, and `useMediaPersistence` is reduced to only what it uniquely provides: stroke data caching across media switches (in-memory + localStorage). Delete `useEditSettingsSync` entirely. Fix the `useLayoutEffect` dependency array. Flatten unnecessary nesting.

**Preserved:** The 3-way context split (Canvas/Form/Status) is untouched — it's a render optimization pattern, not a persistence concern.

## Phase 1: Fix the `useLayoutEffect` Landmine (Low Risk, Immediate Value)

### Step 1: Remove state values from `useLayoutEffect` dependency array (`useMediaPersistence.ts:246`)
**Scope:** Small

1. **Inspect** the `useLayoutEffect` at `useMediaPersistence.ts:132-247`. The effect reads `inpaintStrokes`, `annotationStrokes`, `inpaintPrompt`, `inpaintNumGenerations`, `brushSize` only to save them to the cache on line 156-162 (before switching away from current media).
2. **Move** these values into refs that are updated at render time (same pattern as `statusRef` in `useAutoSaveSettings.ts:142`). Add refs like `inpaintStrokesRef`, etc. Update them at the top of the hook body.
3. **Update** the `useLayoutEffect` dependency array to `[media.id, isInpaintMode, loadEditModeFromDB, saveEditModeToDB, storageKey]` — only values that actually determine whether the effect should re-run.
4. **Inside** the effect, read from the refs instead of the closed-over state values for the cache-save on lines 156-162.

**Why this is safe:** The effect is already guarded by `prevMediaIdRef.current === media.id` — it only does real work when the media ID changes. The state values are only used to snapshot the "current" state into cache before switching. Refs give the same snapshot semantics without the re-run cost.

        # Implementation Plan: Consolidate Media-Lightbox Persistence Architecture

## Overview

The media-lightbox editing system has 3 competing persistence mechanisms that evolved independently:

1. **`useMediaPersistence`** (`hooks/inpainting/useMediaPersistence.ts`, 353 LOC) — Manages inpaint strokes, brush size, prompt, numGenerations, editMode, and annotationMode. Uses 3-layer persistence: in-memory Map cache → localStorage → DB (for editMode via `useEditModePersistence`). Contains the `useLayoutEffect` dependency array landmine.

2. **`useEditSettingsSync`** (`hooks/persistence/useEditSettingsSync.ts`, 134 LOC) — Bidirectional sync glue that pipes values between `useMediaPersistence` and `useEditSettingsPersistence`. Used by **two consumers**: `useManagedInpaintingState.ts` (lightbox) and `useInlineEditState.ts` (inline editor). Has 3 separate effects and a render-time reset.

3. **`useEditSettingsPersistence`** (`hooks/persistence/useEditSettingsPersistence.ts`, 343 LOC) — Coordinates per-generation settings (via `useGenerationEditSettings`/`useAutoSaveSettings`) with "last used" user-level defaults. Already uses `useAutoSaveSettings` under the hood.

**The problem:**
- `useMediaPersistence` duplicates persistence for `editMode`, `prompt`, and `numGenerations` that `useEditSettingsPersistence`/`useGenerationEditSettings` already handles.
- `useEditSettingsSync` exists solely to reconcile the two systems — 134 lines of sync glue.
- The `useLayoutEffect` at `useMediaPersistence.ts:246` has state values in its dependency array (landmine).
- Hook nesting reaches 5 levels deep.

**Critical ownership nuance (flag-1):** `useEditSettingsPersistence` currently treats editMode as **user-level only** — its `setEditMode` (line 206-208) only calls `updateLastUsed()` and never persists to the per-generation DB. Meanwhile, `useMediaPersistence` handles per-generation editMode persistence via `useEditModePersistence`, which reads/writes `params.ui.editMode`. However, `useGenerationEditSettings` already has a per-generation `setEditMode` (line 210-212) and its `saveGenerationSettings` (line 144-147) already writes `editMode` to both `params.ui.editSettings.editMode` AND `params.ui.editMode` for backwards compatibility. The fix is to extend `useEditSettingsPersistence.setEditMode` to also call the generation-level setter, unifying the DB write path.

**Variant-level debt (flag-3):** `useMediaPersistence` caches prompt/numGenerations per-variant in localStorage (keyed by `inpaint-data-{mediaId}-variant-{variantId}`). `useEditSettingsPersistence` is generation-keyed only. Removing prompt/numGenerations from the variant-keyed cache means variants within a generation will share the same prompt. This broadens existing DEBT-002. Stroke data remains variant-keyed.

**Two consumers (flag-2):** Both `useManagedInpaintingState.ts` (lightbox path) and `useInlineEditState.ts` (inline editor) use `useInpainting` + `useEditSettingsSync`. Both must be updated.

**The goal:** Extend `useEditSettingsPersistence` to own per-generation editMode writes (not just user-level). Reduce `useMediaPersistence` to stroke-only caching. Delete `useEditSettingsSync` by making values flow one-way from `useEditSettingsPersistence` into `useInpainting`. Update both lightbox and inline editor consumers.

**Preserved:** The 3-way context split (Canvas/Form/Status) is untouched.
