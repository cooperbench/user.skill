# Veas database — what the agent saves & how much of each

**Schema:** Production data lives in the `mediator` schema on your Supabase Postgres (not `public`). 20 tables.

The agent has a small toolbox of writes — each call goes into a typed store. Here's what each one is *for* (the agent's mental model when it chooses where to write), and the live counts:

## Long-lived knowledge stores

| Store | Count | What the agent writes here |
|---|---|---|
| **memories** | **31** | Stable facts about a person or the couple (e.g. *"[REDACTED] is pregnant"*, *"[REDACTED] previously used cannabis heavily…"*). Each ties to a `user_id` (or null = couple-level). Agent dedupes against existing memories and chooses `add` / `update` / `supersede` itself — 5 of your 31 are `superseded`. |
| **observations** | **152** | Time-stamped behavioural/emotional patterns, with `confidence` (high/medium/low) and `significance` (1–5). Softer than memories — they can be `contradicted` or `stale`. The top 2 tools by call count are `update_observation` (172) and `log_observation` (152), so this is where the agent does most of its "thinking out loud." |
| **themes** | **1** | Long-running relational domains (your one theme: *"Communication and emotional friction"*, `tender` / `improving`). Memories, observations, watch items can all link back via `related_theme_ids`. |
| **distillations** | **10** | Higher-order interpretations / hypotheses that synthesise multiple memories+observations+messages, with `visibility` (private / dyad_shareable) and `sensitivity`. Must cite supporting evidence. |
| **out_of_bounds** | 0 | Topics the agent must avoid surfacing (soft/firm/hard), per-owner. |

## Action / state stores

| Store | Count | Purpose |
|---|---|---|
| **watch_items** | **41** | Things to follow up on later — open until `addressed`, optional `due_at`. |
| **scheduled_jobs** | **86** | Future agent triggers: `checkin` (61, mostly superseded as they get rescheduled), `weekly_summary` (6), `heartbeat`, `watch_item_due`, `deferred_turn`, `scheduled_task`. |
| **bridge_candidates** | 19 | Draft cross-thread shares between the two partners, before they're sent. |
| **feedback** | 12 | User reactions/corrections on a message or turn. |

## Conversation & audit (system-written, not "agent memory")

## TL;DR of the agent's "memory" decision tree

When the agent observes something, it picks:
- **memory** if it's a *durable fact* about a person.
- **observation** if it's a *pattern* — has confidence/significance, can be contradicted.
- **theme** if it's a *long-running domain* worth grouping evidence under.
- **distillation** if it's a *synthesis/hypothesis* across multiple pieces of evidence.
- **watch_item** if it's *something to come back to*.
- **out_of_bounds** if it's a *topic to avoid surfacing*.

So in your live data, the agent has been mostly logging/refining **observations** (172 updates + 152 creations) and managing **watch_items** and **check-in scheduling**, with a smaller core of 31 memories and a single overarching theme.
