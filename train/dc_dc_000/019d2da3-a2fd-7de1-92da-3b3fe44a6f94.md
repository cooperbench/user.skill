## Problem

MegaLoop currently runs a command, waits for it to complete, then analyzes the output. But many real workloads are long-running (training runs, eval suites, deploy pipelines) where you want to CHECK IN periodically — read logs, check metrics, decide whether to continue or kill early.

The agent needs a way to: (1) launch a process, (2) periodically observe its output/logs/artifacts while it runs, (3) decide based on observations whether to let it continue, kill it early, or intervene.

## Design questions to resolve

1. **Wait/sleep mechanism**: Should the loop use a sleep-then-check pattern? A tool that blocks for N seconds then returns control? A polling loop? What's the right primitive for an agentic system that needs to observe a process over time?

2. **Observation strategy**: How does the agent read partial output? Options: tail the log file, read the last N lines of stdout, check for specific artifact files, poll a metrics endpoint. What's the right abstraction?

3. **Break conditions**: How does the agent decide to break? LLM-judged (read the output, decide if it looks stuck/diverging/done)? Metric-based (extract a number, compare to threshold)? Both?

4. **Skill integration**: The megaloop skill doc drives the orchestration. How should the observation/monitoring phase integrate with the existing plan→execute cycle? Is it a sub-phase of execute? A separate phase? A tool the execute sub-agent uses?

5. **Implementation**: What's the minimal code to add to megaplan/loop/ to support this? A new tool? A modification to run_execute_phase? A wrapper around subprocess that yields control periodically?

## What to learn from

- The existing megaplan/loop/engine.py run_execute_phase which currently runs subprocess to completion
- The /loop skill doc pattern for how the agent drives the loop
- autoresearch's pattern of fixed time budgets (5 min) — they just wait for completion but cap the time
- Common patterns in agentic systems for process monitoring (poll loops, callback hooks, signal files)

## Constraints

- Must work within Claude Code's tool execution model (the agent calls tools, tools return results)
- Should be minimal — extend the existing loop infrastructure, don't rebuild it
- The agent should be able to check in at configurable intervals
- Must handle both fast processes (seconds) and slow ones (hours)

## Overview

MegaLoop currently executes user commands synchronously via `subprocess.run()` in `_run_user_command()` (`engine.py:96`), blocking until completion or timeout. For long-running workloads (training runs, deploy pipelines), the agent needs to periodically observe partial output and decide whether to continue, kill, or intervene.

**Current flow:**
```
run_execute_phase → _run_user_command (blocks) → worker diagnoses full output → commit/revert
```

**Target flow:**
```
run_execute_phase → _run_monitored_command (streams) → periodic observations → 
  optional early-kill or continue → worker diagnoses final output → commit/revert
```

**Key constraint:** This runs through megaplan's engine, not as Claude Code tools directly. The monitoring logic lives in `engine.py` and feeds observations into prompts. The worker (LLM) only sees snapshots — the engine drives the poll loop.

**Design decisions:**
1. **Engine-driven polling** — `engine.py` uses `subprocess.Popen` + poll loop at configurable intervals. No new tools; the engine handles timing.
2. **Observation = snapshot of output + optional metric** — Each check-in captures tail of stdout/stderr and extracts metric if configured.
3. **Break conditions are two-tier** — Fast heuristic checks (metric regression, stall detection) in engine code, with optional LLM-judged observation for complex cases.
4. **Opt-in via LoopSpec** — Monitoring activates when `observe_interval` is set in the spec. Without it, behavior is identical to today.
5. **Observation log as artifact** — All snapshots are stored and available to the execute worker prompt for richer diagnosis.

## Phase 1: Foundation — Types, Monitored Subprocess

### Step 1: Extend LoopSpec with monitoring fields (`megaplan/loop/types.py`)
**Scope:** Small
1. **Add** monitoring-related fields to `LoopSpec`:
   - `observe_interval: int` — seconds between check-ins (default: no monitoring)
   - `observe_break_patterns: list[str]` — regex patterns that trigger early kill (e.g., `"CUDA OOM"`, `"NaN loss"`)
   - `observe_metric_stall: int` — kill if extracted metric hasn't improved in N consecutive observations
2. **Add** `Observation` TypedDict for individual snapshots:
   ```python
   class Observation(TypedDict, total=False):
       elapsed_seconds: int
       tail_output: str          # last N chars of combined output
       metric: float             # extracted metric at this snapshot
       action: str               # "continue" | "kill" | "stall" | "break_pattern"
   ```
3. **Add** `observations: list[Observation]` to `IterationResult`.

### Step 2: Implement `_run_monitored_command` (`megaplan/loop/engine.py`)
**Scope:** Medium
1. **Create** `_run_monitored_command(command, *, cwd, timeout, observe_interval, spec)` alongside existing `_run_user_command` (`engine.py:96`).
2. **Implementation approach:**
   - Launch process via `subprocess.Popen` with stdout/stderr piped
   - Use non-blocking reads via threads (one reader thread per pipe, appending to shared buffer) — this avoids pipe deadlocks
   - Main thread polls at `observe_interval` seconds:
     ```python
     while process.poll() is None and elapsed < timeout:
         time.sleep(min(observe_interval, remaining))
         snapshot = _take_observation(output_buffer, elapsed, spec)
         observations.append(snapshot)
         if snapshot["action"] != "continue":
             process.terminate()
             process.wait(timeout=5)
             break
     ```
   - Return same dict shape as `_run_user_command` plus `observations` list
3. **Implement** `_take_observation(buffer, elapsed, spec)` helper:
   - Extract tail of output buffer (last 4000 chars)
   - Run metric extraction via existing `_metric_for_output`
   - Check break patterns: any `observe_break_patterns` regex matches in recent output → `action="break_pattern"`
   - Check metric stall: if last N metrics are flat/worsening → `action="stall"`
   - Otherwise → `action="continue"`
4. **Handle** output buffer threading:
   ```python
   def _reader_thread(pipe, buffer: list):
       for line in iter(pipe.readline, ''):
           buffer.append(line)
       pipe.close()
   ```
   Use `threading.Thread(daemon=True)` for both stdout and stderr readers. This is a standard Python pattern for non-blocking Popen reads.

### Step 3: Add LLM-judged observation support (`megaplan/loop/engine.py`, `megaplan/loop/prompts.py`)
**Scope:** Medium — can defer to v2 if needed
1. **Add** `observe_llm_interval: int` to LoopSpec — if set, every Nth observation also calls a lightweight LLM worker for judgment.
2. **Add** `build_observe_prompt(state, observation)` to `prompts.py`:
   - Includes: goal, recent output tail, metric trend, elapsed time
   - Returns: `{"action": "continue"|"kill", "reason": "..."}`
3. **Register** `loop_observe.json` schema in `schemas.py`.
4. **In** `_run_monitored_command`, after heuristic check passes, optionally call `run_loop_worker("loop_observe", ...)` every `observe_llm_interval` observations.
5. **Note:** This step is the most complex and least necessary for v1. Heuristic-only observation (Step 2) covers the most important cases. Flag this as optional/deferrable.

## Overview

MegaLoop currently executes user commands synchronously via `subprocess.run()` in `_run_user_command()` (`engine.py:96`), blocking until completion or timeout. For long-running workloads (training runs, deploy pipelines), the agent needs to periodically observe partial output and decide whether to continue, kill, or intervene.

**Current flow:**
```
run_execute_phase → _run_user_command (blocks) → worker diagnoses full output → commit/revert
```

**Target flow:**
```
run_execute_phase → _run_monitored_command (streams) → periodic observations → 
  optional early-kill or continue → worker diagnoses final output → commit/revert
```

**Key constraint:** This runs through megaplan's engine, not as Claude Code tools directly. The monitoring logic lives in `engine.py` and feeds observations into prompts. The worker (LLM) only sees snapshots — the engine drives the poll loop.

**Design decisions:**
1. **Engine-driven polling** — `engine.py` uses `subprocess.Popen` + poll loop at configurable intervals. No new tools; the engine handles timing.
2. **Observation = snapshot of output + optional metric** — Each check-in captures tail of stdout/stderr and extracts metric if configured.
3. **Break conditions are two-tier** — Fast heuristic checks (metric regression, stall detection) in engine code, with optional LLM-judged observation for complex cases.
4. **Opt-in via LoopSpec** — Monitoring activates when `observe_interval` is set in the spec. Without it, behavior is identical to today.
5. **Observation log as artifact** — All snapshots are stored and available to the execute worker prompt for richer diagnosis.

## Phase 1: Foundation — Types, Monitored Subprocess

### Step 1: Extend LoopSpec with monitoring fields (`megaplan/loop/types.py`)
**Scope:** Small
1. **Add** monitoring-related fields to `LoopSpec`:
   - `observe_interval: int` — seconds between check-ins (default: no monitoring)
   - `observe_break_patterns: list[str]` — regex patterns that trigger early kill (e.g., `"CUDA OOM"`, `"NaN loss"`)
   - `observe_metric_stall: int` — kill if extracted metric hasn't improved in N consecutive observations
2. **Add** `Observation` TypedDict for individual snapshots:
   ```python
   class Observation(TypedDict, total=False):
       elapsed_seconds: int
       tail_output: str          # last N chars of combined output
       metric: float             # extracted metric at this snapshot
       action: str               # "continue" | "kill" | "stall" | "break_pattern"
   ```
3. **Add** `observations: list[Observation]` to `IterationResult`.

### Step 2: Implement `_run_monitored_command` (`megaplan/loop/engine.py`)
**Scope:** Medium
1. **Create** `_run_monitored_command(command, *, cwd, timeout, observe_interval, spec)` alongside existing `_run_user_command` (`engine.py:96`).
2. **Implementation approach:**
   - Launch process via `subprocess.Popen` with stdout/stderr piped
   - Use non-blocking reads via threads (one reader thread per pipe, appending to shared buffer) — this avoids pipe deadlocks
   - Main thread polls at `observe_interval` seconds:
     ```python
     while process.poll() is None and elapsed < timeout:
         time.sleep(min(observe_interval, remaining))
         snapshot = _take_observation(output_buffer, elapsed, spec)
         observations.append(snapshot)
         if snapshot["action"] != "continue":
             process.terminate()
             process.wait(timeout=5)
             break
     ```
   - Return same dict shape as `_run_user_command` plus `observations` list
3. **Implement** `_take_observation(buffer, elapsed, spec)` helper:
   - Extract tail of output buffer (last 4000 chars)
   - Run metric extraction via existing `_metric_for_output`
   - Check break patterns: any `observe_break_patterns` regex matches in recent output → `action="break_pattern"`
   - Check metric stall: if last N metrics are flat/worsening → `action="stall"`
   - Otherwise → `action="continue"`
4. **Handle** output buffer threading:
   ```python
   def _reader_thread(pipe, buffer: list):
       for line in iter(pipe.readline, ''):
           buffer.append(line)
       pipe.close()
   ```
   Use `threading.Thread(daemon=True)` for both stdout and stderr readers. This is a standard Python pattern for non-blocking Popen reads.
