# Subagent launcher (multi-model)

This skill is the umbrella for dispatching work to a model other than the one currently driving the conversation. The point is independence: a *different* model's judgement, not a parallel copy of your own.

Four pathways are wired up:

| Pathway | Model | Invocation | Has tools? | Cost source |
| --- | --- | --- | --- | --- |
| **Codex** | GPT-5.5 (configurable) | `codex exec` (CLI) | Yes — sandboxed workspace | User's OpenAI/Codex quota |
| **Claude** | Claude (Opus/Sonnet/Haiku) | `Agent` tool in Claude Code | Yes — full tool palette | User's Claude Code session |
| **DeepSeek V4 Pro** | `deepseek-v4-pro` (official API) | `curl` to api.deepseek.com | No (pure chat) | `DEEPSEEK_API_KEY` from `~/.hermes/.env` |
| **Kimi K2.5** | `kimi-k2p5` via Fireworks | `curl` to api.fireworks.ai (the megaplan "hermes" agent route) | No (pure chat) | `FIREWORKS_API_KEY` from `~/.hermes/.env` |

DeepSeek and Kimi here are **chat-only one-shots** — good for opinions, root-cause hypotheses, or judging artifacts you already have in hand. They don't write files or run commands. If you need DeepSeek or Kimi to actually *do* agentic work, dispatch a `megaplan` run with the matching profile instead (see *Agentic delegation* below).

## Picking a pathway

- **Want a second model's *judgement* on something you already understand?** → Codex (or DeepSeek/Kimi if you want a third voice or want to avoid burning OpenAI quota).
- **Want independent root-cause analysis from scratch?** → Codex (it can read the repo) or Claude (Agent tool).
- **Want a model to *implement* a fix?** → Codex with `--sandbox workspace-write`, or the Claude `Agent` tool with the `general-purpose` subagent. DeepSeek/Kimi via curl can't write files; go through `megaplan` for that.
- **Adversarial review of a Claude diagnosis?** → Codex is the highest-signal second opinion because it's the most-different model and has repo access.
- **"Jury of models" for high-stakes calls?** → Fan out the same prompt to Codex + DeepSeek + Kimi in parallel (multiple Bash tool calls in one message). Compare answers.
- **Already have the answer?** → Don't dispatch. Subagents aren't free.

## 1. Codex (GPT-5.5)

Codex is installed at `/Users/user_c042661f/.nvm/versions/node/v20.19.4/bin/codex`. The `openai/codex-plugin-cc` Claude Code plugin wraps it as `/codex:review` etc., but the underlying call is `codex exec` — invoke it directly from Bash.

**Basic invocation:**

```bash
codex exec --sandbox read-only "PROMPT_HERE"
```

- `--sandbox read-only` — analysis only, no file writes
- `--sandbox workspace-write` — let Codex modify project files
- `--sandbox danger-full-access` — full shell (avoid unless explicitly requested)
- `-m gpt-5.5` — pin the model (default; check `~/.codex/config.toml` first if you'll override)
- `-c model_reasoning_effort=medium` — `medium` is the default; bump to `high` for hard reasoning, drop to `low` for mechanical edits

For long prompts, write to a file first:

```bash
cat > /tmp/codex_prompt.md <<'EOF'
...your prompt here...
EOF
codex exec --sandbox read-only "$(cat /tmp/codex_prompt.md)" </dev/null > /tmp/codex_out.txt 2>&1
```

**Always seal stdin with `</dev/null`** when running Codex non-interactively. If stdin isn't a TTY and isn't `/dev/null`, `codex exec` will block forever at "Reading additional input from stdin..." even when the prompt is fully supplied as an argument. The process sits at 0% CPU and silently waits — no error, no timeout. See *Detecting hangs* below.

**Background long sessions** via the Bash tool's `run_in_background: true`. Pair with `timeout 600 codex exec ...` so a wedged run self-terminates instead of squatting indefinitely.

**PR-style review:**

```bash
codex exec review [--pr <n>] [--against <ref>] [prompt]
```

**Session management:**

- `codex exec resume` — continue a previous session
- `codex resume --last` — resume interactively
- `codex fork` — fork a saved session
- `codex apply` — apply Codex's last diff with `git apply`

## 2. Claude (via Claude Code `Agent` tool)

Claude subagents are dispatched through the `Agent` tool already available in this harness. They run as cleanly-scoped instances with no memory of the outer conversation — so the prompt must be self-contained.

**Subagent types worth knowing:**

- `general-purpose` — catch-all for research, multi-step tasks, code edits with full tool access.
- `Explore` — fast read-only search agent. Use it to find files / grep / "where is X defined."
- `Plan` — software-architect agent that returns step-by-step plans without writing code.
- `claude-code-guide` — Claude Code / Anthropic SDK / Claude API questions.
- `code-reviewer` — independent review of a diff or change.
- `statusline-setup`, others — see the agent list at the top of the harness prompt.

**Invocation pattern (inside this Claude Code session):**

```
Agent({
  description: "Independent root-cause review",
  subagent_type: "general-purpose",
  prompt: "<self-contained brief: working dir, files to read, what to return, response cap>"
})
```

Key prompt rules (same as any subagent):

- Name the working directory explicitly.
- List exact files/paths to read, not "the relevant files."
- State the desired output format (diff, ranked list, schema proposal).
- Cap the response length ("under 600 words").
- For adversarial tasks, tell Claude to be opinionated — otherwise it hedges.

**When to prefer Claude over Codex:** when you want the same *family* of judgement (Claude is what's already driving the conversation) but isolated from the outer context — e.g., to keep the main thread clean during a big repo sweep. For genuinely different judgement, prefer Codex or DeepSeek.

## 3. DeepSeek V4 Pro (official API)

DeepSeek V4 Pro is invoked via the official DeepSeek API at `https://api.deepseek.com`. The matching megaplan profile is `all-deepseek-pro-direct` (spec: `hermes:deepseek:deepseek-v4-pro`).

**Key facts:**

- Endpoint: `https://api.deepseek.com/v1/chat/completions` (OpenAI-compatible)
- Model name: `deepseek-v4-pro`
- API key: `DEEPSEEK_API_KEY`, sourced from `~/.hermes/.env`
- **It's a reasoning model.** Reasoning tokens count against `max_tokens`. Setting `max_tokens: 200` will exhaust the budget on reasoning and return empty `content`. Use **≥ 2000** for short answers, **≥ 16000** for analysis.

**One-shot invocation:**

```bash
set -a; source ~/.hermes/.env; set +a
curl -s -X POST https://api.deepseek.com/v1/chat/completions \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d @- <<'EOF' | python3 -c "import sys,json; d=json.load(sys.stdin); print(d['choices'][0]['message']['content'])"
{
  "model": "deepseek-v4-pro",
  "messages": [
    {"role": "system", "content": "You are an adversarial code reviewer. Be opinionated and concise."},
    {"role": "user",   "content": "..."}
  ],
  "max_tokens": 16384,
  "temperature": 0.3
}
EOF
```

For multi-paragraph prompts, build the JSON with `python3 -c` or write it to `/tmp/deepseek_req.json` and `-d @/tmp/deepseek_req.json`.

**Inspecting reasoning:** the response has `choices[0].message.reasoning_content` separately from `content`. Print `content` for the answer; sample `reasoning_content` if you want to see how it got there.

**Tools / agentic mode:** DeepSeek V4 Pro via curl has no tools — pure chat. For agentic work, run a megaplan plan with `--profile all-deepseek-pro-direct` (see *Agentic delegation*).

## Writing effective subagent prompts (universal rules)

Regardless of which pathway you use, the receiving model starts with **zero context** from your conversation. Treat every dispatch like briefing a smart colleague who just walked into the room:

- **Working directory** — name it explicitly (`/Users/user_c042661f/Documents/megaplan`).
- **Files / paths** — list exact paths, not "the relevant files."
- **Goal + why** — what you're trying to accomplish and why the answer matters.
- **What you've already ruled out** — saves the subagent re-doing your work.
- **Output shape** — diff, ranked list, JSON, prose under N words. Specify.
- **Length cap** — "under 600 words" or "respond in under 200 words."
- **Be opinionated** — for adversarial / second-opinion tasks, tell the model not to hedge. Otherwise they'll all hedge.

Long prompts (>2 KB) belong in a file (`/tmp/<task>_prompt.md`) and get loaded by `cat` or `-d @file`.

## Fan-out: judge / jury patterns

When the call is genuinely high-stakes, send the same prompt to multiple models *in parallel* and compare. From this harness, that means a single message with multiple Bash tool calls (or Agent calls) in parallel:

- Codex via `codex exec`
- DeepSeek via `curl`
- Kimi via `curl`
- Optional: a Claude `Agent` invocation as a fourth panelist

Diverging answers are signal. Convergence on a subtle judgement is much stronger evidence than any single model's confidence.

Don't fan out for routine work — it's wasteful. Reserve it for: pre-merge review of risky changes, architecture decisions you can't easily reverse, security-sensitive code paths, judging artifacts that megaplan itself produced.

## Bundles

Preconfigured fan-outs aimed at a specific kind of decision. Same problem, different lenses, run in parallel, no cross-talk.

### Agent UX bundle

Three parallel Codex subagents (GPT-5.5, `model_reasoning_effort=medium`) sense-check the same proposal from three lenses:

1. **Human user** — what's confusing, surprising, or invisible to the end person?
2. **Agent user** — would an LLM reading this cold pick the right tool / default / path?
3. **Technical abstraction** — are the boundaries clean and the abstractions load-bearing?

Use for changes that touch all three surfaces (new CLI, new API, new prompt/workflow, slash command). Skip for pure bugfixes or one-layer work.

**Briefing rules:** same unbiased problem write-up to all three; each gets only its own lens plus a note that two others are running; tell each to take a position and not hedge; cap ≤ 600 words; never show one's output to another.

```bash
cat > /tmp/agent_ux_problem.md <<'EOF'
<unbiased factual description of the proposal>
EOF

# Single message, three parallel Bash calls — one per lens:
codex exec --sandbox read-only -c model_reasoning_effort=medium "$(cat <<'EOF'
Sense-check from the **human user perspective**. Two other reviewers cover the agent-user and technical-abstraction lenses — skip their ground. Take a position, do not hedge. ≤ 600 words.

PROBLEM:
$(cat /tmp/agent_ux_problem.md)
EOF
)" 2>&1 | tail -200
# …repeat with "agent user perspective" and "technical abstraction perspective".
```

Synthesize: concerns in >1 lens are likely real; disagreement between lenses usually means the design optimizes one surface at another's expense.

## Sanity checks before dispatching

- Is there an equivalent built-in agent (Claude `Agent` with `Explore` or `general-purpose`) that would work? If yes and you don't need genuinely independent judgement, use it.
- Does the task need write access? If yes, Codex `workspace-write` or Claude `Agent` (with edit tools) — DeepSeek/Kimi curl can't write files.
- Are you re-asking what you already answered? If so, add the twist (rank these, find the flaw, argue the other side) — otherwise you're just burning tokens.
- For DeepSeek/Kimi: did you set `max_tokens` high enough that the reasoning budget won't eat the answer? Default to `16384` unless you have a reason to go lower.
- Is `~/.hermes/.env` actually sourced in your shell call? It isn't by default — prepend `set -a; source ~/.hermes/.env; set +a` whenever you're shelling out via `curl`.

## Detecting hangs / liveness checks

Every pathway has a specific way to silently wedge. Each requires a different smoke-test. If you dispatch a long-running subagent, do a liveness check **30-60 seconds after launch** — not 10 minutes in. Cheap to verify, expensive to leave running.

### Codex (`codex exec`)

**Failure mode:** blocks on stdin even when prompt is fully supplied as `argv` — sits at 0% CPU, 0.1% MEM, output file at ~39 bytes containing only the literal banner `Reading additional input from stdin...` and nothing else. Forever. No timeout, no error.

**Important — that banner string appears in healthy runs too.** Codex always prints `Reading additional input from stdin...` as its first line on launch, even when the prompt was supplied as `argv`. Presence of the string is not the signal. The signal is whether anything follows it.

**Prevention:** redirect stdin from `/dev/null`. Always. The banner still prints but the process doesn't actually block.

```bash
codex exec --sandbox read-only "$(cat /tmp/prompt.md)" </dev/null > /tmp/out.txt 2>&1
```

**Liveness check (30s post-launch):**

The differentiator is **file growth**, not file content. Healthy Codex streams output continuously and the file is many KB by 30s; wedged Codex stays at ~39 bytes (just the banner).

```bash
# Snapshot, wait, snapshot — growth is the signal:
SZ1=$(wc -c < /tmp/out.txt); sleep 5; SZ2=$(wc -c < /tmp/out.txt)
echo "growth: $SZ1 -> $SZ2"   # equal AND tiny = wedged. growing = healthy.

# Process check confirms — wedged proc has 0% CPU with minutes elapsed:
ps -o pid,stat,%cpu,etime -p $(pgrep -f "codex exec") 2>/dev/null
```

Note: healthy Codex *also* shows low `%CPU` locally (reasoning happens server-side), so CPU alone is ambiguous — pair with file-growth or banner-only check. The all-three combination (banner-only output AND 0% CPU AND minutes elapsed) is conclusive wedge.

**Recovery:** `pkill -f "codex exec"` and re-run with `</dev/null`. Wrap in `timeout 600 ...` going forward.

### DeepSeek / Kimi (curl)

**Failure modes (in order of frequency):**

1. **Reasoning ate `max_tokens`** — request returned 200 OK, `content` is empty string, `finish_reason: "length"`. Set `max_tokens` ≥ 2000 for short answers, ≥ 16000 for analysis.
2. **HTTP error masked by `curl -s`** — auth, quota, rate-limit, or 5xx. `curl -s` swallows the status; the pipe to `python3 -c "...['content']"` then throws KeyError on `error` payload, with no clue what went wrong.
3. **Server hang** — TCP open, no response. With no `--max-time`, `curl` waits indefinitely.

**Prevention pattern (use this every time, not the bare `curl -s` shown in earlier examples):**

```bash
set -a; source ~/.hermes/.env; set +a
curl -sS --fail-with-body --max-time 300 \
  -X POST https://api.deepseek.com/v1/chat/completions \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d @/tmp/req.json \
  > /tmp/raw.json
# Parse defensively — distinguish error from empty content:
python3 - <<'PY'
import json, sys
d = json.load(open('/tmp/raw.json'))
if 'error' in d:
    print('API ERROR:', d['error']); sys.exit(1)
msg = d['choices'][0]['message']
content = msg.get('content') or ''
if not content:
    print('EMPTY CONTENT. finish_reason=', d['choices'][0].get('finish_reason'),
          'reasoning_len=', len(msg.get('reasoning_content') or ''))
else:
    print(content)
PY
```

**Liveness check (30-60s post-launch for background curls):**

```bash
wc -c /tmp/raw.json                  # 0 = still waiting or network dead
pgrep -fl curl                        # process still alive?
# If raw.json has content but parse fails, inspect raw.json directly —
# the error payload is the diagnosis.
```

Healthy curl: writes nothing until the response arrives in one chunk (streaming is opt-in). So an empty file at 60s isn't necessarily wedged — but at 5+ minutes with no `--max-time` it almost certainly is. Always set `--max-time 300` so wedged curls self-terminate with a clear timeout error.

### Claude Agent (Agent tool)

**Failure modes:** much rarer than the curl/Codex paths because the Agent tool runs in-process and surfaces errors through the tool-result envelope. The two real risks:

1. **Subagent loops** — bad tool / bad prompt causes the inner agent to grind. The harness will eventually return; there's no external timeout you control.
2. **Terse prompt → shallow output** — not a hang, but the most common form of "wasted dispatch." Diagnosis: response comes back in <30s with generic hedging.

**Prevention:**

- Cap the response length explicitly (`under 600 words`, `respond in under 200 words`).
- For adversarial tasks, instruct "take a position, do not hedge."
- For exploration, prefer `Explore` subagent (fast, read-only) over `general-purpose`.

**Liveness check:** none available mid-flight — Agent tool calls are synchronous from your perspective. If an Agent dispatch is suspiciously long, the recourse is to wait or cancel the parent turn.

### megaplan

**Failure modes:** runs are multi-phase and stage at finalize-to-execute checkpoints in review mode. The "wedge" is usually waiting for human approval, not a stuck process.

**Liveness check:**

```bash
megaplan status --plan <name>   # current state + next-step runtime hint
megaplan progress --plan <name> # per-batch completion in execute
```

A genuinely stuck megaplan run is rare; an apparently stuck one is usually a gated step waiting for an override (`megaplan override force-proceed` or `replan`).

### Universal rule

**Liveness ≠ correctness.** A subagent can run for 10 minutes producing token-by-token output and still emit a useless answer. Liveness checks catch the *silent-wedge* failure mode. The *bad-output* failure mode (hedging, missed the question, hallucinated file paths) needs you to actually read the response — there's no shortcut.

## Writing effective subagent prompts (universal rules)

Regardless of which pathway you use, the receiving model starts with **zero context** from your conversation. Treat every dispatch like briefing a smart colleague who just walked into the room:

- **Working directory** — name it explicitly (`/Users/user_c042661f/Documents/megaplan`).
- **Files / paths** — list exact paths, not "the relevant files."
- **Goal + why** — what you're trying to accomplish and why the answer matters.
- **What you've already ruled out** — saves the subagent re-doing your work.
- **Output shape** — diff, ranked list, JSON, prose under N words. Specify.
- **Length cap** — "under 600 words" or "respond in under 200 words."
- **Be opinionated** — for adversarial / second-opinion tasks, tell the model not to hedge. Otherwise they'll all hedge.

Long prompts (>2 KB) belong in a file (`/tmp/<task>_prompt.md`) and get loaded by `cat` or `-d @file`.

## Fan-out: judge / jury patterns

When the call is genuinely high-stakes, send the same prompt to multiple models *in parallel* and compare. From this harness, that means a single message with multiple Bash tool calls (or Agent calls) in parallel:

- Codex via `codex exec`
- DeepSeek via `curl`
- Kimi via `curl`
- Optional: a Claude `Agent` invocation as a fourth panelist

Diverging answers are signal. Convergence on a subtle judgement is much stronger evidence than any single model's confidence.

Don't fan out for routine work — it's wasteful. Reserve it for: pre-merge review of risky changes, architecture decisions you can't easily reverse, security-sensitive code paths, judging artifacts that megaplan itself produced.

## Bundles

Preconfigured fan-outs aimed at a specific kind of decision. Same problem, different lenses, run in parallel, no cross-talk.

### Agent UX bundle

Three parallel Codex subagents (GPT-5.5, `model_reasoning_effort=medium`) sense-check the same proposal from three lenses:

1. **Human user** — what's confusing, surprising, or invisible to the end person?
2. **Agent user** — would an LLM reading this cold pick the right tool / default / path?
3. **Technical abstraction** — are the boundaries clean and the abstractions load-bearing?

Use for changes that touch all three surfaces (new CLI, new API, new prompt/workflow, slash command). Skip for pure bugfixes or one-layer work.

**Briefing rules:** same unbiased problem write-up to all three; each gets only its own lens plus a note that two others are running; tell each to take a position and not hedge; cap ≤ 600 words; never show one's output to another.

## Detecting hangs / liveness checks

Every pathway has a specific way to silently wedge. Each requires a different smoke-test. If you dispatch a long-running subagent, do a liveness check **30-60 seconds after launch** — not 10 minutes in. Cheap to verify, expensive to leave running.

### Codex (`codex exec`)

**Failure mode:** blocks on stdin even when prompt is fully supplied as `argv` — sits at 0% CPU, 0.1% MEM, output file at ~39 bytes containing only the literal banner `Reading additional input from stdin...` and nothing else. Forever. No timeout, no error.

**Important — that banner string appears in healthy runs too.** Codex always prints `Reading additional input from stdin...` as its first line on launch, even when the prompt was supplied as `argv`. Presence of the string is not the signal. The signal is whether anything follows it.

**Prevention:** redirect stdin from `/dev/null`. Always. The banner still prints but the process doesn't actually block.

```bash
codex exec --sandbox read-only "$(cat /tmp/prompt.md)" </dev/null > /tmp/out.txt 2>&1
```

**Liveness check (30s post-launch):**

The differentiator is **file growth**, not file content. Healthy Codex streams output continuously and the file is many KB by 30s; wedged Codex stays at ~39 bytes (just the banner).

```bash
# Snapshot, wait, snapshot — growth is the signal:
SZ1=$(wc -c < /tmp/out.txt); sleep 5; SZ2=$(wc -c < /tmp/out.txt)
echo "growth: $SZ1 -> $SZ2"   # equal AND tiny = wedged. growing = healthy.

# Process check confirms — wedged proc has 0% CPU with minutes elapsed:
ps -o pid,stat,%cpu,etime -p $(pgrep -f "codex exec") 2>/dev/null
```

Note: healthy Codex *also* shows low `%CPU` locally (reasoning happens server-side), so CPU alone is ambiguous — pair with file-growth or banner-only check. The all-three combination (banner-only output AND 0% CPU AND minutes elapsed) is conclusive wedge.

**Recovery:** `pkill -f "codex exec"` and re-run with `</dev/null`. Wrap in `timeout 600 ...` going forward.

### DeepSeek / Kimi (curl)

**Failure modes (in order of frequency):**

1. **Reasoning ate `max_tokens`** — request returned 200 OK, `content` is empty string, `finish_reason: "length"`. Set `max_tokens` ≥ 2000 for short answers, ≥ 16000 for analysis.
2. **HTTP error masked by `curl -s`** — auth, quota, rate-limit, or 5xx. `curl -s` swallows the status; the pipe to `python3 -c "...['content']"` then throws KeyError on `error` payload, with no clue what went wrong.
3. **Server hang** — TCP open, no response. With no `--max-time`, `curl` waits indefinitely.

**Prevention pattern (use this every time, not the bare `curl -s` shown in earlier examples):**

```bash
set -a; source ~/.hermes/.env; set +a
curl -sS --fail-with-body --max-time 300 \
  -X POST https://api.deepseek.com/v1/chat/completions \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d @/tmp/req.json \
  > /tmp/raw.json
# Parse defensively — distinguish error from empty content:
python3 - <<'PY'
import json, sys
d = json.load(open('/tmp/raw.json'))
if 'error' in d:
    print('API ERROR:', d['error']); sys.exit(1)
msg = d['choices'][0]['message']
content = msg.get('content') or ''
if not content:
    print('EMPTY CONTENT. finish_reason=', d['choices'][0].get('finish_reason'),
          'reasoning_len=', len(msg.get('reasoning_content') or ''))
else:
    print(content)
PY
```

**Liveness check (30-60s post-launch for background curls):**

```bash
wc -c /tmp/raw.json                  # 0 = still waiting or network dead
pgrep -fl curl                        # process still alive?
# If raw.json has content but parse fails, inspect raw.json directly —
# the error payload is the diagnosis.
```

Healthy curl: writes nothing until the response arrives in one chunk (streaming is opt-in). So an empty file at 60s isn't necessarily wedged — but at 5+ minutes with no `--max-time` it almost certainly is. Always set `--max-time 300` so wedged curls self-terminate with a clear timeout error.

### Claude Agent (Agent tool)

**Failure modes:** much rarer than the curl/Codex paths because the Agent tool runs in-process and surfaces errors through the tool-result envelope. The two real risks:

1. **Subagent loops** — bad tool / bad prompt causes the inner agent to grind. The harness will eventually return; there's no external timeout you control.
2. **Terse prompt → shallow output** — not a hang, but the most common form of "wasted dispatch." Diagnosis: response comes back in <30s with generic hedging.

**Prevention:**

- Cap the response length explicitly (`under 600 words`, `respond in under 200 words`).
- For adversarial tasks, instruct "take a position, do not hedge."
- For exploration, prefer `Explore` subagent (fast, read-only) over `general-purpose`.

**Liveness check:** none available mid-flight — Agent tool calls are synchronous from your perspective. If an Agent dispatch is suspiciously long, the recourse is to wait or cancel the parent turn.

### megaplan

**Failure modes:** runs are multi-phase and stage at finalize-to-execute checkpoints in review mode. The "wedge" is usually waiting for human approval, not a stuck process.

**Liveness check:**

```bash
megaplan status --plan <name>   # current state + next-step runtime hint
megaplan progress --plan <name> # per-batch completion in execute
```

A genuinely stuck megaplan run is rare; an apparently stuck one is usually a gated step waiting for an override (`megaplan override force-proceed` or `replan`).

### Universal rule

**Liveness ≠ correctness.** A subagent can run for 10 minutes producing token-by-token output and still emit a useless answer. Liveness checks catch the *silent-wedge* failure mode. The *bad-output* failure mode (hedging, missed the question, hallucinated file paths) needs you to actually read the response — there's no shortcut.

> AGENT

Honest answer: it's a *good pastiche* but it's not actually Seinfeld. A few specific reasons:

**What lands:**
- "Who's Llama? Is he opening for me at the club?" — that's real Jerry. Stand-up vocabulary leaking into civilian life is exactly how he hears the world.
- "You can't even merge with a parking spot." — real Costanza. Concrete, mean, deflates an abstraction with a specific failure.
- The puffy-shirt callback genuinely works.

**What doesn't:**

1. **"Food bank for algorithms"** is too writerly for George. George doesn't *construct* cute analogies — he reacts, panics, catastrophizes. Real Costanza is more like "Free? Nothing's free! That's how they get you!" The metaphor is something a writer's room punches up, not something a guy in a sweatshirt thinks of in real time.

2. **"Barely tolerate them at standard pitch"** and **"the one thing I asked the universe to forget"** are too literary for Jerry. His real voice is flatter and more declarative — "I don't *need* my thoughts fine-tuned. My thoughts are fine. Actually, they're not, but I'm not adjusting them."

3. **The threading itself is wrong.** Real Seinfeld dialogue is *less* connected, not more. Characters talk past each other and stay trapped in their own POV — that's where the comedy lives. The handoff structure I built is closer to Sorkin or modern half-hour writing. Seinfeld scenes have more friction and less call-and-response.

4. **No physical specificity.** Real scenes are full of cereal, the fridge, what's on TV, who's at the door. This one is all concepts, no apartment. Jerry should be eating something or staring into the open fridge during half of Kramer's speech.

5. **The closer is too tidy.** "Most closed system I know. Proprietary. Crashes every forty-five minutes." is a writer's button — it resolves the open-source thread *too cleanly*. The show would more likely end on Kramer leaving with misplaced confidence ("Giddy-up!"), or Jerry's flat resignation, or even nothing — just a beat and then somebody asking about Chinese food. Seinfeld scenes often end *un*-resolved.

6. **Kramer's "co-op! The people own the brain!"** is too political. Real Kramer is concrete-absurd, not ideological — "I got a Llama in my closet, Jerry, it's writing my Christmas cards. The thing's got *style*."

**Verdict:** funnier than 90% of internet Seinfeld parodies, but it reads like an SNL sketch *about* Seinfeld more than a Seinfeld scene. Too clean, too connected, too metaphor-rich. The actual show was messier, more material, and the characters were more locked inside themselves.

If you want me to take another pass with these notes in mind, I can — the goal would be making it *worse* in a specific way: less polished, more cereal, more talking past each other.
