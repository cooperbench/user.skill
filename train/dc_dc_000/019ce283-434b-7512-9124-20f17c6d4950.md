Unified Triage Disposition Map                                                                                                        
                                                        
 Context

 The triage workflow (observe → reflect → organize → enrich → sense-check → commit) has four semi-independent state representations
 that drift apart:

 1. Observe assessments — stages["observe"]["assessments"] (list of verdict dicts)
 2. Reflect disposition ledger — stages["reflect"]["disposition_ledger"] (list of {issue_id, decision, target})
 3. Plan state — plan["clusters"] + plan["skipped"] (only written by organize)
 4. Coverage tracking — computed on demand from clusters/skips/dismissed, ignoring observe/reflect decisions

 Observe verdicts don't change state. Reflect dispositions are a separate structure. Neither feeds directly into coverage tracking.
 The result: the tool can say "this issue is not worth doing" (observe), "this cluster is not ready" (organize), and "here is your
 next task" (queue) simultaneously without reconciling.

 Goal: One shared per-issue map that every stage writes to. Each stage builds on the last stage's concrete state, not on prose.

 Design

 New data structure: issue_dispositions

 Added to epic_triage_meta, keyed by full issue ID:

 class IssueDisposition(TypedDict, total=False):
     # Observe writes:
     verdict: str           # "genuine" | "false positive" | "exaggerated" | "over engineering" | "not worth it"
     verdict_reasoning: str
     files_read: list[str]
     recommendation: str
     # Reflect writes (genuine issues only):
     decision: str          # "cluster" | "skip"
     target: str            # cluster name or skip reason
     # Organize confirms:
     placed: bool           # cluster created & issue assigned, or skip entry created
     # Enrich confirms:
     enriched: bool         # step detail is executor-ready
     # Sense-check confirms:
     verified: bool         # verified against actual code

 Key behavior: observe auto-skip

 When observe records a non-genuine verdict (false positive, exaggerated, over engineering, not worth it), the system immediately:
 1. Sets decision: "skip" + placed: True in the disposition
 2. Creates a SkipEntry in plan["skipped"]
 3. Removes the issue from queue_order

 These issues are fully dispositioned at observe time. Reflect never sees them. Organize doesn't need to handle them. The LLM stages
 only work on genuine issues.

 Stage-by-stage data flow

 ┌─────────────┬─────────────────────────┬────────────────────────────────────────────────────────────────────────────────────────┐
 │    Stage    │          Reads          │                                 Writes to dispositions                                 │
 ├─────────────┼─────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────┤
 │ Observe     │ Issues from state       │ verdict, verdict_reasoning, files_read, recommendation. Auto-skip sets decision,       │
 │             │                         │ placed for non-genuine.                                                                │
 ├─────────────┼─────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────┤
 │ Reflect     │ Dispositions (genuine   │ decision, target for each genuine issue                                                │
 │             │ only)                   │                                                                                        │
 ├─────────────┼─────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────┤
 │ Organize    │ Dispositions + plan     │ placed: True for each issue whose cluster/skip now exists                              │
 │             │ state                   │                                                                                        │
 ├─────────────┼─────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────┤
 │ Enrich      │ Dispositions + clusters │ enriched: True for each placed issue                                                   │
 ├─────────────┼─────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────┤
 │ Sense-check │ Dispositions + clusters │ verified: True for each enriched issue                                                 │
 └─────────────┴─────────────────────────┴────────────────────────────────────────────────────────────────────────────────────────┘

 Cascade clear

 When a stage is re-run, clear disposition fields from that stage and all later stages:
 - Re-run observe → clear everything (rebuild from scratch)
 - Re-run reflect → clear decision, target, placed, enriched, verified
 - Re-run organize → clear placed, enriched, verified

 For observe specifically: also un-skip any auto-skipped issues before re-running.

**Findings**

- The shared per-issue map is the right direction, but `placed` / `enriched` / `verified` should not become persisted authoritative state. The current code correctly derives “what is actually true now” from live `clusters` and `skipped`, not from stage metadata, in both organize validation and coverage tracking; if you persist booleans, they will drift as soon as someone edits clusters or skips outside a stage rerun. See [organize_policy.py:142](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/validation/organize_policy.py#L142) and [review_coverage.py:100](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/review_coverage.py#L100). I would persist only intent/history (`verdict`, `decision`, `target`, maybe `decision_source`) and keep placement/enrichment/verification derived.

- `observe` auto-skip, as described, changes workflow semantics more than the proposal claims. Today `observe` recording only writes stage payload and later confirmation is a separate step; auto-creating skips during record would mutate `plan["skipped"]` and `queue_order` before `--confirm observe`, so confirmation would no longer be just confirmation. See [records.py:21](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/stages/records.py#L21), [observe.py:106](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/stages/observe.py#L106), and [stage_policy.py:113](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/validation/stage_policy.py#L113). If you want automation, do it on observe confirmation, not on stage record.

- The verdict taxonomy is not clean enough for “non-genuine => auto-skip.” Current prompts treat `false-positive` as factual, but `not-worth-it` and `over-engineering` are cost/strategy judgments that reflect currently owns; auto-skipping them in observe collapses the observe/reflect boundary. See [stage_prompts_instruction_blocks.py:103](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/runner/stage_prompts_instruction_blocks.py#L103) and [stage_prompts_instruction_blocks.py:189](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/runner/stage_prompts_instruction_blocks.py#L189). I would either auto-skip only `false_positive`, or split observe output into `validity` and `actionability`.

- The proposed observe-to-full-ID mapping should not reuse `_build_short_map` as-is. It silently overwrites short-hash collisions, while reflect already has a collision-aware resolver; once `issue_dispositions` is authoritative, mis-attaching one issue is expensive. Compare [evidence_parsing.py:76](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/stages/evidence_parsing.py#L76) with [reflect_accounting.py:52](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/validation/reflect_accounting.py#L52) and [reflect_accounting.py:141](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/validation/reflect_accounting.py#L141).

**Overall**

Yes: one shared per-issue disposition object is a better abstraction than the current split between ad hoc observe payloads, reflect ledger, and plan-derived coverage. The proposal is directionally correct.

I would change three things before implementing it: keep live plan state authoritative for coverage, move any auto-skip side effects to confirmation time, and narrow auto-skip to clearly factual outcomes or split the verdict model. With those changes, the design makes sense and should reduce the current drift substantially.

> AGENT

Yes, but only if you keep the layers separate.

**Overlap**

- The direct overlap is around skip semantics. Your status plan makes `issue.status` authoritative for lifecycle, and the triage-map plan wants observe/reflect to drive skip decisions. Those are compatible only if any triage-created skip goes through the same skip-to-state path.
- The risky overlap is `observe` auto-skip. Once Part A lands, auto-skip would also change state status, which means the issue stops being `open` mid-triage. That affects coverage and stage inputs immediately.
- The biggest conceptual conflict is the word “authoritative.” These should not all be authoritative for the same thing:
  - `issue.status`: lifecycle/public truth
  - `plan.skipped`: queue suppression + skip metadata
  - `issue_dispositions`: triage-stage intent/history only

If `issue_dispositions` also becomes authoritative for placement/coverage, you create a third source of truth.

**What overlaps cleanly**

- Part A of the status plan overlaps cleanly with Phase 1 of the disposition-map plan.
- Part B of the status plan is mostly separate and benefits from Part A.
- The messy overlap is Part A + disposition Phase 2 auto-skip/coverage rewrite.

**Recommendation**

Do them in this order:

1. Land Part A first: status enum, skip/state sync, reconcile migration.
2. Land Part B with it or right after.
3. Land disposition-map Phase 1 only: dual-write, no behavior change.
4. Revisit disposition Phase 2 after that, but change it:
   - auto-skip on observe confirm, not observe record
   - use the shared skip/state path
   - keep `placed/enriched/verified` derived, not persisted authority

If you want one combined PR, I’d cap it at `Part A + Part B + disposition Phase 1`. I would not combine Part A with auto-skip and coverage-authority changes in the same pass.
