**Findings**

1. The worker-side LTX continuation plan is scoped to the wrong seam. The doc puts prefix continuation into [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L278) and [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L332), but [`segment_processor.py`](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/segment_processor.py#L360) only returns guide/mask/video-prompt metadata. The actual WGP handoff is built later in [`task_registry.py`](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/tasks/task_registry.py#L852) and continuation-like payloading today uses `video_source`, not `input_video`, in [`task_registry.py`](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/tasks/task_registry.py#L901). Also, `prefix_frames_count` is not currently even pass-through-safe in [`task_conversion.py`](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/tasks/task_conversion.py#L38). So the worker change list is under-scoped.

2. The plan still conflates three different axes: model family, travel pipeline, and structure/guidance presence. Setting WAN `defaultTravelMode` to `'vace'` in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L63) conflicts with the current UX default of `'i2v'` in [`settings.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/settings.ts#L190). Using `hasStructureVideo` inside intent/resolution in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L75) is also the wrong primitive: the code explicitly avoids that because Uni3C has structure video but remains I2V in [`usePresetAutoSelect.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/hooks/settings/usePresetAutoSelect.ts#L32). Current structure handling also snaps back to I2V, not a model default, in [`useStructureVideoHandlers.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/video/useStructureVideoHandlers.ts#L53).

3. `includesMotionFields` is not a safe derived field. In the doc it comes from `allowedTravelModes.includes('vace')` in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L109), but payload inclusion in the real client is about whether the model consumes phase/motion fields at all, not whether it can do VACE. Current branching in [`requestBody.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/requestBody.ts#L78) already shows that phase config, `advanced_mode`, `num_inference_steps`, and `guidance_scale` are separate capability decisions. For extensibility, those need to be explicit capabilities, not inferred from travel mode support.

4. The frame math is still unresolved, and it is a real design issue, not just a verification item. The doc notes the WAN case is uncertain in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L356). In the worker, segment lengths are quantized first in [`orchestrator.py`](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L956), then overlap context is added later in [`orchestrator.py`](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L1945). So `77 + 10 = 87` really does miss 4N+1. If continuation becomes first-class, the policy needs to define whether quantization happens before or after overlap injection.

5. `continuation_config` is not actually “canonical” unless task rehydration understands it too. The plan mentions reading overlap in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L214), but current apply-settings extraction only reads `frame_overlap_expanded` in [`taskDataService.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/taskDataService.ts#L98). There is no rehydration of `smoothContinuations`, continuation strategy, or execution topology. “Apply settings from task” will stay lossy unless that path is included.

6. The document has a scope contradiction: it says to change `mask_builder.py` in the worker gate table in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L275), then later says `mask_builder.py` needs no changes in [`squishy-finding-lamport.md`](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L338). That usually means the policy boundaries are not fully settled yet.

**What I’d Standardize Instead**

- Keep `ModelSpec` purely static: model family, worker model name, frame step, fps, defaults, and explicit capability flags like `supportsPhaseConfig`, `supportsMotionPresets`, `supportsTurbo`, `supportsGuidanceScale`, `supportedGuidanceKinds`, `supportedContinuationKinds`.
- Keep `GenerationIntent` purely user-authored: `selectedModel`, `requestedExecutionMode`, `requestedContinuation`, `travelGuidance`, `resolutionPreference`. Do not include derived booleans like `hasStructureVideo`.
- Make `ResolvedPolicy` the single derived object used by both UI and payload assembly: `executionMode`, `continuation`, `guidance`, `payloadFlags`, and `disabledReasons`.
- Separate execution topology from continuation. I would add something like `segment_execution_mode: 'independent' | 'sequential'` rather than overloading `chain_segments` to mean “continuation on”.
- Normalize by semantic kind, not model names:
  - continuation: `none | guide_overlap_masked | prefix_video_latents`
  - guidance: `none | vace | ltx_control | uni3c | ltx_hybrid`
- For UX, preserve requested state across model switches and resolve it with reasons instead of silently rewriting it. That will make new model families much less painful.

Net: the direction is right, but I would rewrite the plan around separate axes for `execution`, `continuation`, and `guidance`. Right now the doc still mixes them, and that will make the next model addition hurt again. If you want, I can rewrite the plan doc into that shape.
