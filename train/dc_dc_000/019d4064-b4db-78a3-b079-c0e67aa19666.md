        # Implementation Plan: Frontend Batch Prompt Enhancement via OpenAI

## Overview

**Goal:** When users enable "Enhance Prompt" for batch generations in cloud mode, process prompt enhancements on the frontend via the `ai-prompt` edge function (OpenAI GPT-5-mini) instead of relying on the worker's VLM. This aligns batch behavior with the single-item flow.

**Current state:**
- **Single-item flow** (`submitSegmentTask.ts:320-327`): Calls `ai-prompt` edge function with `enhance_segment_prompt` task, stores result in metadata, submits with enhanced prompt pre-filled.
- **Batch flow** (`useGenerateBatch.ts:197`): Sends `enhance_prompt: true` boolean → `buildTravelRequestBodyV2` (line 137) → `create-task` resolver expands to empty `enhanced_prompts_expanded` array (line 171-173) → worker VLM generates prompts.
- **Worker idempotency** (`orchestrator.py:1565-1574`): Already checks for pre-existing `enhanced_prompts_expanded` in payload and skips VLM if prompts are non-empty.
- **Payload mapping** (`travelBetweenImages.ts:171-194`): `enhanced_prompts` array from frontend → `enhanced_prompts_expanded` in worker payload. If the array contains actual prompt strings, the worker will use them directly.

**Key insight:** The backend plumbing already supports pre-filled enhanced prompts. We just need to: (1) call the edge function per pair on the frontend, (2) pass the results in the `enhanced_prompts` array instead of the boolean flag.

## Phase 1: Core Enhancement Service

### Step 1: Create batch prompt enhancement utility (`reigh-app/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/enhancePromptsForBatch.ts`)
**Scope:** Medium

1. **Create** a new module that exports an `enhancePromptsForBatch` function.
2. **Signature:** Accepts an array of `{ prompt: string; numFrames: number }` (one per pair/segment), plus a concurrency limit (default ~3-5 to respect rate limits).
3. **Implementation:**
   - Use `supabase().functions.invoke('ai-prompt', { body: { task: 'enhance_segment_prompt', prompt, temperature: 0.7, numFrames } })` — identical to the call in `submitSegmentTask.ts:320-327`.
   - Process pairs in controlled parallel using a simple concurrency pool (e.g., process N at a time with `Promise.all` on slices, or a small `pLimit`-style helper).
   - On per-item failure, fall back to the original prompt (non-fatal, same as single-item flow at line 329-335).
   - Return `string[]` of enhanced prompts in pair order.

4. **Example usage:**
   ```typescript
   const enhanced = await enhancePromptsForBatch(
     pairs.map(p => ({ prompt: p.basePrompt, numFrames: p.numFrames })),
     { concurrency: 3 }
   );
   // enhanced: ["A cinematic camera...", "The scene transitions...", ...]
   ```

### Step 2: Wire batch enhancement into `useGenerateBatch.ts`
**Scope:** Medium

1. **Modify** `useGenerateBatch.ts` to intercept when `prompt.enhancePrompt` is true (currently at line 197).
2. **Before** calling `generateVideo()` (line 188), if `enhancePrompt` is true:
   - Build the per-pair prompt list from the pair config (base prompts + any per-pair overrides).
   - Call `enhancePromptsForBatch()` with those prompts.
   - Store results so they can be passed to `buildTravelRequestBodyV2`.
3. **Pass** enhanced prompts into the generation call so `requestBody.ts` can include them in the `enhanced_prompts` array field.
4. **Remove** the `enhance_prompt: true` boolean from the payload when enhanced prompts are pre-filled (the worker doesn't need the boolean if prompts are already provided).

### Step 3: Update `requestBody.ts` to accept pre-enhanced prompts (`requestBody.ts`)
**Scope:** Small

1. **Update** `buildTravelRequestBodyV2` params to accept an optional `enhancedPrompts: string[]` from the caller (in addition to the existing `pairConfig.enhancedPromptsArray` path).
2. **When** caller provides pre-enhanced prompts, set `enhanced_prompts` in the payload (line 128) and omit `enhance_prompt` boolean (line 137).
3. **Verify** `hasValidEnhancedPrompts` logic (around line 128) correctly detects the pre-filled array.

## Phase 2: UI Feedback & Persistence

### Step 4: Add loading/progress state during enhancement (`useGenerateBatch.ts`, `ShotEditorView.tsx`)
**Scope:** Small-Medium

1. **Add** a state indicator (e.g., `isEnhancingPrompts`) in `useGenerateBatch` so the UI can show feedback during the enhancement phase (which may take several seconds for many pairs).
2. **Surface** this state in the generate button area — a simple "Enhancing prompts..." label or progress indicator showing N/M pairs enhanced.
3. **Handle** cancellation: if the user navigates away or cancels during enhancement, abort gracefully.

### Step 5: Persist enhanced prompts in pair metadata (`useGenerateBatch.ts`, `pairPayload.ts`)
**Scope:** Small

1. **After** enhancement and before submission, store each enhanced prompt in the corresponding shot_generation's metadata (similar to `persistSegmentEnhancedPrompt()` in `submitSegmentTask.ts:352-359`).
2. **This ensures** the `pairPayload.ts` `extractPairOverrides` (line 24) can read `metadata.enhanced_prompt` on subsequent loads, providing UI persistence and preventing re-enhancement on retry.
3. **Verify** that `buildTimelinePairConfig` / `buildByPairConfig` in `pairPayload.ts` correctly picks up these stored prompts.

### Step 6: Validate end-to-end flow
**Scope:** Small

1. **Verify** worker idempotency: submit a batch with pre-filled `enhanced_prompts` array and confirm the worker logs `Loaded N pre-existing enhanced prompts from payload` (orchestrator.py:1572) and skips VLM.
2. **Test** edge cases:
   - Mixed state: some pairs have overridden prompts, some don't → all should be enhanced.
   - Empty/blank prompts: pairs with no prompt text should either skip enhancement or use fallback.
   - Rate limit handling: verify controlled parallelism doesn't trigger 429s from OpenAI.
   - Enhancement disabled: verify `enhance_prompt: false` skips the entire enhancement step and sends no enhanced prompts.
3. **Verify** UI shows enhanced prompts in pair metadata after generation completes and page is reloaded.

## Execution Order

1. Step 1 first (standalone utility, no side effects).
2. Steps 2-3 together (wiring the utility into the batch flow).
3. Steps 4-5 (UI polish and persistence — can be done after core flow works).
4. Step 6 last (end-to-end validation).

## Validation Order

1. Unit test `enhancePromptsForBatch` with mocked Supabase calls — verify concurrency limiting, error fallback, correct prompt ordering.
2. Integration test: submit batch with `enhancePrompt: true`, verify `enhanced_prompts` array in the outgoing request body (intercept network call).
3. End-to-end: submit to real worker, verify VLM skip in worker logs.
4. UI: verify progress feedback, metadata persistence, and reload behavior.

        # Implementation Plan: Frontend Batch Prompt Enhancement via OpenAI

## Overview

**Goal:** When users enable "Enhance Prompt" for batch generations in cloud mode, process prompt enhancements on the frontend via the `ai-prompt` edge function (OpenAI GPT-5-mini) instead of relying on the worker's VLM. This aligns batch behavior with the single-item flow.

**Current state:**
- **Single-item flow** (`submitSegmentTask.ts:320-327`): Calls `ai-prompt` edge function with `enhance_segment_prompt` task, stores result in metadata, submits with enhanced prompt pre-filled.
- **Batch flow** (`useGenerateBatch.ts:197`): Sends `enhance_prompt: true` boolean → `buildTravelRequestBodyV2` (line 137) → `create-task` resolver expands to empty `enhanced_prompts_expanded` array (line 171-173) → worker VLM generates prompts.
- **Worker idempotency** (`orchestrator.py:1565-1574`): Already checks for pre-existing `enhanced_prompts_expanded` in payload and skips VLM if prompts are non-empty.
- **Payload mapping** (`travelBetweenImages.ts:171-194`): `enhanced_prompts` array from frontend → `enhanced_prompts_expanded` in worker payload.

**Key constraint — batch prompt structure:** In batch mode, the user's prompt is stored as a single `base_prompt` string (from `promptConfig.base_prompt`, line 196 of `useGenerateBatch.ts`), while per-pair `basePrompts` are empty strings (`buildBatchPairConfig` line 204 of `pairPayload.ts`). The worker resolves this by falling back from per-segment prompts to `base_prompt` during VLM enrichment (`orchestrator.py:1591`). The frontend enhancement must use the same fallback: enhance `base_prompt` for every pair that lacks its own override.

**Key constraint — rate limiting:** The `ai-prompt` edge function uses `RATE_LIMITS.expensive` = 30 requests per 60 seconds (`rateLimit.ts:58`). Concurrency limiting alone is insufficient; the enhancement utility must also pace requests to stay under this cap.

**Settled decisions (no worker/backend changes needed):**
- Worker idempotency check at `orchestrator.py:1566` correctly skips VLM when `enhanced_prompts_expanded` contains non-empty strings.
- `create-task` resolver at `travelBetweenImages.ts:171-194` already maps `enhanced_prompts[]` → `enhanced_prompts_expanded`.
- Enhancement is blocking — all prompts enhanced before batch submission.

## Phase 1: Core Enhancement Service

### Step 1: Create batch prompt enhancement utility (`reigh-app/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/enhancePromptsForBatch.ts`)
**Scope:** Medium

1. **Create** a new module that exports an `enhancePromptsForBatch` function.
2. **Signature:**
   ```typescript
   enhancePromptsForBatch(params: {
     batchBasePrompt: string;           // The shared batch prompt (promptConfig.base_prompt)
     pairCount: number;                 // Number of image pairs
     pairOverridePrompts?: (string | undefined)[];  // Per-pair override prompts (from timeline/by-pair modes)
     numFrames: number;                 // Segment frames for the enhancement template
     textBeforePrompts?: string;        // Prefix to prepend before enhancing
     textAfterPrompts?: string;         // Suffix to append before enhancing
     onProgress?: (completed: number, total: number) => void;
   }): Promise<string[]>
   ```
3. **Prompt resolution per pair:** For each pair index, resolve the prompt to enhance as `pairOverridePrompts?.[i] || batchBasePrompt`. This mirrors the worker's fallback from per-segment prompts to `base_prompt` (`orchestrator.py:1591, 1955`). If the resolved prompt is empty/blank, use empty string in the output (skip enhancement for that pair).
4. **Rate-limited execution:**
   - Use a simple queue that processes at most **3 concurrent requests** with a **pacing delay** to stay under 30 req/60s. Concretely: after every batch of 3, wait until at least 6 seconds have elapsed since the batch started (3 req / 6s = 30 req / 60s at steady state).
   - On 429 response, retry after a 2-second backoff (single retry per item).
   - On other per-item failure, fall back to the original prompt (non-fatal, same as single-item flow at `submitSegmentTask.ts:329-335`).
5. **Edge function call** per pair — identical to single-item flow:
   ```typescript
   supabase().functions.invoke('ai-prompt', {
     body: { task: 'enhance_segment_prompt', prompt: resolvedPrompt, temperature: 0.7, numFrames }
   })
   ```
6. **Return** `string[]` of enhanced prompts in pair order (same length as `pairCount`).

### Step 2: Wire batch enhancement into `useGenerateBatch.ts` and `generateVideoService.ts`
**Scope:** Medium

1. **In `useGenerateBatch.ts`** (~line 188, before calling `generateVideo()`):
   - If `prompt.enhancePrompt` is true, call `enhancePromptsForBatch()` with:
     - `batchBasePrompt: prompt.basePrompt` (line 196)
     - `pairCount`: derived from shot image count (N images → N-1 pairs)
     - `numFrames`: from the batch video frames setting
     - `textBeforePrompts / textAfterPrompts`: from `prompt.textBeforePrompts` / `prompt.textAfterPrompts`
   - Store the returned `string[]` and pass it into `generateVideo()` via a new `preEnhancedPrompts` field on `promptConfig`.

2. **In `generateVideoService.ts`** (~line 272):
   - Accept `preEnhancedPrompts?: string[]` on `promptConfig`.
   - Pass it through to `buildTravelRequestBodyV2` via `generationParams`.

3. **In `requestBody.ts`** (`buildTravelRequestBodyV2`):
   - Accept optional `preEnhancedPrompts: string[]` in `generationParams`.
   - When present and non-empty, set `enhanced_prompts: preEnhancedPrompts` in the payload (line 128 area) and **omit** `enhance_prompt: true` boolean (line 137). The worker doesn't need the boolean when prompts are pre-filled.
   - When absent, preserve current behavior (pass `enhance_prompt` boolean as-is).

### Step 3: Add loading/progress state during enhancement (`useGenerateBatch.ts`)
**Scope:** Small

1. **Add** an `enhancementProgress` state (`{ phase: 'enhancing'; completed: number; total: number } | null`) in the generate batch hook.
2. **Wire** the `onProgress` callback from `enhancePromptsForBatch` to update this state.
3. **Surface** this state to the UI via the hook's return value so the generate button area can show "Enhancing prompts... (N/M)" during the blocking enhancement phase.
4. **Handle** cancellation: use an `AbortController` passed to the enhancement utility; abort if the component unmounts during enhancement.

## Phase 2: Persistence & Validation

### Step 4: Persist enhanced prompts in pair metadata (`useGenerateBatch.ts`)
**Scope:** Small

1. **After** enhancement returns and **before** submission, persist each enhanced prompt to the corresponding `shot_generation` row's metadata via `persistSegmentEnhancedPrompt()` (same pattern as `submitSegmentTask.ts:352-359`).
2. **Note on retry idempotency:** `buildBatchPairConfig()` (line 196-213 of `pairPayload.ts`) does **not** read shot_generation metadata — it fills `enhancedPromptsArray` with empty strings. Therefore, metadata persistence serves **UI display purposes only** (showing the user what prompt was used). It does **not** prevent re-enhancement on retry. This is acceptable because:
   - Re-enhancement is cheap (edge function, not VLM).
   - The prompts may legitimately differ on retry if the user changed the base prompt.
   - The single-item flow also re-enhances on each submission.
3. **Do not** modify `buildBatchPairConfig` to read from metadata — this would add complexity for minimal benefit and could cause stale prompt bugs if the user changes their base prompt between retries.

### Step 5: Validate end-to-end flow
**Scope:** Small

1. **Verify** worker idempotency: submit a batch with pre-filled `enhanced_prompts` array and confirm the worker logs `Loaded N pre-existing enhanced prompts from payload` (`orchestrator.py:1572`) and skips VLM.
2. **Test** edge cases:
   - **Empty base prompt:** pairs with no prompt text → skip enhancement, pass empty string.
   - **Large batch (30+ pairs):** verify pacing keeps requests under 30/min, no 429s.
   - **Per-pair overrides (timeline/by-pair mode):** each pair's override prompt is enhanced individually, not the shared base prompt.
   - **Enhancement disabled:** `enhance_prompt: false` skips the entire enhancement step and sends no enhanced prompts (current behavior preserved).
   - **Partial failure:** if some pairs fail enhancement, they fall back to original prompt, batch still submits.
3. **Verify** UI shows "Enhancing prompts..." progress and enhanced prompts appear in pair metadata after generation completes.

## Execution Order

1. Step 1 first (standalone utility, no side effects, testable in isolation).
2. Step 2 (wiring — depends on Step 1).
3. Step 3 (UI feedback — can be done alongside Step 2 but depends on Step 1).
4. Steps 4-5 (persistence and validation — after core flow works).

## Validation Order

1. Unit test `enhancePromptsForBatch` with mocked Supabase calls — verify prompt resolution fallback (`pairOverride || batchBasePrompt`), rate pacing, error fallback, correct ordering.
2. Integration test: submit batch with `enhancePrompt: true`, intercept outgoing request body, verify `enhanced_prompts` array contains actual prompts and `enhance_prompt` boolean is absent.
3. Rate limit test: simulate 30+ pair batch, verify requests are paced under 30/min.
4. End-to-end: submit to real worker, verify VLM skip in worker logs.
5. UI: verify progress feedback, metadata persistence, and reload behavior.
