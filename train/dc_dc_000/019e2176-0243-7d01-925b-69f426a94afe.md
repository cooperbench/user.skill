> AGENT

1. The graph is the wrong primitive. Use an ordered agenda/checklist with `priority`, `status`, and optional `parent_item_id`. Real conversations jump, but modeling that as a mutable graph gives Haiku too much structural authority for little benefit. The UI already admits the truth: it renders a checklist, not a graph. Keep skip/back/current-item navigation; drop “tree as graph” as the core abstraction.

2. `conversation_state` is mostly redundant. Delete it as designed. Keep durable state on the rows that own it:
   - `conversation_nodes.status`, `covered_summary`, `covered_at`
   - current node = one `conversation_nodes.status = 'active'` or latest open `node_visits`
   - current topic = derived from current node
   - speaker mapping belongs either on `conversations.speaker_map jsonb` or a small `conversation_speakers` table
   - `tracked_fields` can be `conversations.session_fields jsonb` if truly prompt-only
   - `open_threads` should be nodes/items with `kind='thread'`, not JSON in state
   - `facts_learned` should become post-session `observations`/`distillations`, or live `conversation_notes`

3. The Haiku tool surface is bloated. Cut it to four:
   - `transition_to(node_id, reason)`
   - `set_node_status(node_id, status, note)` covering mark/skip/unskip/undo
   - `add_node(parent_id, topic_id, title, opening_prompt, kind)` covering dynamic nodes and open threads
   - `note_session_fact(text, speaker_role, evidence_turn_ids)` only if live synthesis needs it

   Delete `mark_node_covered`, `skip_node`, `add_open_thread`, `close_open_thread`, `set_state_field`, and `undo_last_coverage` as separate tools. They are verbs around the same two resources: nodes and notes.

4. Keeping `conversation_topics` separate from global `topics` is correct. Do not unify them. Global `topics` are durable partitions like `pregnancy` or `relationship`; `conversation_topics` are session agenda sections. But rename it to `conversation_sections` or `conversation_agenda_sections`; calling both “topics” guarantees confusion.

5. `conversation_state.open_threads`, `facts_learned`, and `tracked_fields` are premature denormalization. It bites when you need provenance, partial updates, concurrency safety, eval replay, search, or “show me unresolved threads across sessions.” JSONB is acceptable for `speaker_map` and maybe prompt-only `tracked_fields`; it is wrong for open threads and learned facts.

6. Yes, the doc rebuilds existing concepts. `facts_learned` overlaps with `observations` and `distillations`. `open_threads` overlaps with `watch_items` if it survives beyond the session; if it is session-local, make it an agenda item. Post-session synthesis should write existing `distillations`, `observations`, and pregnancy fields from migrations `0032/0033`, not a generic longitudinal layer. Also, `tool_calls` only works cleanly if live turns create `bot_turns`; say that explicitly.

7. The one simplification I would force: replace `conversation_topics` + graph-like `conversation_nodes` + `conversation_state` with a single ordered `conversation_items` table.

Keep:

```sql
conversation_items (
  id,
  conversation_id,
  section_label,
  priority,
  parent_item_id,
  kind, -- planned | dynamic | thread
  title,
  prompt,
  status, -- pending | active | covered | skipped
  summary,
  order_hint,
  created_at,
  covered_at
)
```

That gives you checklist UI, skip/back, dynamic additions, open threads, replay, and synthesis with one abstraction. Delete the graph language and delete `conversation_state`.
