## Overview
The repository already has the Plan 1-5 backbone: FastAPI routers in `app/routers/`, the agentic loop in `app/services/agentic.py`, WhatsApp ingestion in `app/services/inbound.py`, schema migrations in `migrations/`, tool schemas and read/write tools, spend helpers, media handlers, startup recovery, and tests with a `FakePool` harness. The main gaps remain: `app/routers/admin.py` is a placeholder, `users` has no `onboarding_state`, `/health` is shallow, WhatsApp reactions are not parsed, transcription lacks a cap check, text cap failure is not graceful, staging replay does not exist, and README ops content is foundation-level.

## Phase 1: Schema And Shared State

### Step 1: Add Plan 6 schema support (`migrations/0005_plan6_ops.sql`, `app/models/user.py`, `tests/conftest.py`)
**Scope:** Medium
1. Add `users.onboarding_state text NOT NULL DEFAULT 'pending'` with a check constraint for `pending|welcomed|seeded|complete`.
2. Add durable spend-warning state to `llm_spend_log`, such as `warned_80_at timestamptz`, so 80% warning logs are emitted once per provider/day.
3. Add a deferred processing path for text-cap queueing: prefer `messages.processing_state='deferred'` plus `scheduled_jobs.job_type='deferred_turn'`, or an equivalent minimal schema that can represent “do not recover immediately; retry after cap reset.” This is required because current startup recovery requeues incomplete turns and raw messages without a next-day cap concept.
4. Add targeted indexes only where new queries need them; no broad indexing is needed for two users.
5. Extend `upsert_user`/`fetch_user_by_id` only where needed without changing the frozen `User` dataclass unless runtime code needs the field frequently.
6. Update `FakePool` user rows to default `onboarding_state='pending'` and handle the new updates/selects used by onboarding, spend warnings, deferred processing, admin, and staging tests.

### Step 2: Add atomic welcome-message gate (`app/services/onboarding.py`, `app/services/inbound.py`, `tests/test_whatsapp_webhook.py`)
**Scope:** Medium
1. Add a short `WELCOME_MESSAGE` constant in `app/services/onboarding.py`.
2. Insert the inbound message first and let that statement commit before attempting the welcome. This is mandatory because `send_outbound` checks free-form eligibility with `SELECT MAX(sent_at) FROM messages WHERE sender_id=$1 AND direction='inbound'`.
3. After inbound persistence, atomically claim the welcome with a conditional update:
   ```sql
   UPDATE users
   SET onboarding_state = 'welcomed'
   WHERE id = $1 AND onboarding_state = 'pending'
   RETURNING id
   ```
   Only the caller that receives a row sends the welcome.
4. Call `send_outbound(pool, user, WELCOME_MESSAGE)` only after the atomic claim succeeds. If the send fails, keep `welcomed`; the outbound row and send failure are already visible for admin/debugging, and webhook retries must not duplicate the welcome.
5. Keep this independent from the coalescer so the welcome is immediate and the normal agentic turn still processes the user’s message.
6. Add tests for first whitelisted inbound sends once, sets `welcomed`, duplicate redelivery does not send again, and two concurrent first-inbound calls cannot both send.

### Step 3: Put onboarding state in hot context (`app/services/hot_context.py`, `tests/test_hot_context.py`)
