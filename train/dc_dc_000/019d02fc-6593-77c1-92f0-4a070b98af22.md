**Findings**

- The plan conflates two different cluster state machines. In [staged-wobbling-babbage.md:27-30](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L27), it proposes adding `"deferred"` and `"in_progress"` to `VALID_EXECUTION_STATUSES`, but current code only models execution status as `"active"` or `"review"` in [cluster_semantics.py:18-20](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_semantics.py#L18) and [cluster_semantics.py:37-42](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_semantics.py#L37). Triage does write `execution_status="deferred"` for auto-cluster decisions at [triage/apply.py:268-276](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/triage/apply.py#L268), but `"in_progress"` currently lives in the separate cluster `status` field for epic clusters at [triage/apply.py:75-81](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/triage/apply.py#L75) and [triage/apply.py:112](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/triage/apply.py#L112). Adding `"in_progress"` as an execution status would paper over a real mismatch instead of fixing it. The likely bug is the validator in [organize_policy.py:305-307](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/validation/organize_policy.py#L305), not `cluster_semantics`.

- The proposed explain API is too weak to explain real queue visibility. In [staged-wobbling-babbage.md:64-66](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L64) the new `queue_membership_summary(plan, all_item_ids)` only sees the plan and an ID set, but actual visibility depends on snapshot partitions and phase resolution in [snapshot.py:304-359](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L304), [snapshot.py:381-452](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L381), and [snapshot.py:500-534](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L500). The code already needs a full `QueueContext` and snapshot to compute trustworthy counts in [queue_progress.py:141-165](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/helpers/queue_progress.py#L141) and [queue_progress.py:182-204](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/helpers/queue_progress.py#L182). If you implement explain off `plan + ids`, it will misclassify phase-hidden work as backlog or “not promoted.” This should hang off `QueueContext.snapshot`, not a parallel “policy” abstraction.

- The `auto_queue` idea is good, but the plan misses one durability gap: plan normalization currently has no detector context. [staged-wobbling-babbage.md:21-32](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L21) treats registry metadata as the new source of truth, but persisted clusters do not store detector, and load-time normalization calls `normalize_cluster_semantics(cluster)` without a detector in [schema/normalize.py:196-211](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/schema/normalize.py#L196). Without detector context, `normalize_cluster_semantics` falls back to string/action inspection in [cluster_semantics.py:117-132](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_semantics.py#L117). So `auto_queue` will work at creation sites that already pass `detector`, but it is not yet a fully durable semantic source. If that is acceptable, call it out explicitly; if not, persist detector or derive it during normalization.

The plan is mostly clean and well-scoped. The good part is that it avoids touching phase inference and partitions, which is the right instinct. The weak part is elegance: `policy.py` risks becoming a second source of truth unless it is purely a thin view over `QueueContext.snapshot`, and the execution-status section currently mixes unrelated concepts.

Two smaller notes:
- [staged-wobbling-babbage.md:13](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L13) references `_plan/schema.py`, but this repo uses [schema/__init__.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/schema/__init__.py).
- If you want explainability to feel complete, consider whether `backlog --explain` should share the same queue-decision block, since both surfaces go through [queue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/next/queue_flow.py).
