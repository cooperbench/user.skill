> AGENT

This plan is not ready to execute as a prod cutover sprint. Five focused days can build a rough vertical slice; it cannot safely replace the current editor, publish to prod, and preserve clean rollback.

Day 2 is a 2-3 day job. The current editor is not just 2,500 lines of sloppy glue; it has checkpointing, run audit, DB wrappers, watchlist lifecycle, duplicate state, candidate normalization, publishing, trace/debug output, and app-side rejection logic spread across [live_update_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_editor.py:114), [live_update_prompts.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_prompts.py:381), and storage wrappers. Day 2 asks for native tool-use, 10 tools, dispatcher writes, canonicalization, alias resolution, collision override semantics, idempotency, and rejection tests. That is not one day for a solo dev unless “done” means “happy path barely runs.”

Dropping `defer` is the wrong kind of fiat. Today defer is real: explicit `agent_decision=defer` and confidence `<0.75` both become `decision='deferred'` [live_update_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_editor.py:1835). The morning-after failure is not abstract. A borderline topic that should be surfaced for human judgment gets forced into one of three wrong outcomes: posted too early, watched invisibly as if it only needs more signal, or ignored with no actionable review queue. Banodoco members either see under-verified posts in `#daily-updates`, or they never see timely human-curated items because “watching” has no “POM should decide this now” semantics. Re-adding later means schema, prompt/tool surface, state machine, admin visibility, and migration changes after prod state already exists.

Highest-probability first-24h failures:

1. Duplicate or fractured topics. Symptom: members see two updates about the same release/experiment under different headlines, or a follow-up posted as a fresh story. Recovery: disable publishing, manually delete/clarify Discord posts, add aliases/merge state, tune canonicalizer. The no-fuzz canonicalizer decision makes this likely.

2. Wrong structure posts. Symptom: a multi-contributor story becomes a wall of media, or a single creator post becomes a noisy sectioned thread. Recovery: pause publishing, fix dispatcher/source-author counting, manually repost or leave an ugly feed artifact.

3. Collision false positives blocking posts. Symptom: nothing appears for legitimate new stories because the agent hits collision errors and mishandles override. Recovery: inspect `topic_transitions`, lower sensitivity or improve override loop, manually post missed items.

Rollback is not zero-cost. The old editor reads `live_update_checkpoints`, `live_update_feed_items`, `live_update_duplicate_state`, `live_update_editorial_memory`, and `live_update_watchlist` before deciding [live_update_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/live_update_editor.py:121). If the new editor does not write old checkpoint state, rollback reprocesses the whole flip window and can re-emit posts because old duplicate/feed tables know nothing about new Discord posts. If the new editor does advance the old checkpoint, rollback skips the flip window but old memory/feed/dedupe state is blind to what was publicly posted, so future follow-ups are misclassified. Either way, there is state drift.

The missing senior-dev question: what is the checkpoint and rollback contract? Before Monday, decide whether the new editor shares or owns checkpoints, and write the rollback procedure for both Discord-visible posts and old-table dedupe/memory seeding.

Bottom line: build it, yes. Ship Day 5 with no shadow mode, no defer audit, and no rollback state contract, no.
