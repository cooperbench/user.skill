> AGENT

They overlap in the UI, but they are not the same thing internally.

**Mechanical scan issues**

A scan-created mechanical issue is a real detector output stored in `state["issues"]` with kind `mechanical_finding` and origin `scan` ([issue_semantics.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_state/issue_semantics.py#L14), [issue_semantics.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_state/issue_semantics.py#L63), [issue_semantics.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_state/issue_semantics.py#L85)). On each new scan, it gets upserted by stable ID: new ones are added, previously fixed ones can be reopened if they reappear, and ignored ones are suppressed ([merge_issues.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_state/merge_issues.py#L156)). If a later scan stops reporting an open mechanical issue, desloppify does not silently mark it fixed; absence only scan-verifies an already manually resolved or wontfixed item ([merge_issues.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_state/merge_issues.py#L74), [QUEUE_LIFECYCLE.md](/Users/user_c042661f/Documents/desloppify/docs/QUEUE_LIFECYCLE.md#L31)). Mechanical changes can also mark related subjective assessments stale so they get re-reviewed ([merge.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_state/merge.py#L40)).

**Subjective review output**

This actually splits into two different artifacts:

1. `subjective_assessments`
A review import stores per-dimension scores like `naming_quality: 72` in `state["subjective_assessments"]`. Those scores are what feed the subjective part of the health score, which is currently 75% of overall ([assessments.py](/Users/user_c042661f/Documents/desloppify/desloppify/intelligence/review/importing/assessments.py#L60), [core.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_scoring/policy/core.py#L132)).

2. review findings
The same review import can also create actionable `review` or `concerns` issues in `state["issues"]`, one per concrete defect the reviewer called out ([holistic_issue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/intelligence/review/importing/holistic_issue_flow.py#L58), [holistic_issue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/intelligence/review/importing/holistic_issue_flow.py#L125)). These are queue items for triage/fixing, not the score itself.

There is also a third thing: scan-generated `subjective_review` items. Those are not defects; they are synthetic “review needed” requests created when a dimension is unassessed or stale ([shared_phases_review.py](/Users/user_c042661f/Documents/desloppify/desloppify/languages/_framework/base/shared_phases_review.py#L180)). Once an assessment for that dimension is imported, those synthetic request items are auto-fixed as “completed by review import” ([holistic_cache.py](/Users/user_c042661f/Documents/desloppify/desloppify/intelligence/review/importing/holistic_cache.py#L125)).

So the clean mental model is:

- Mechanical findings: detector says “this code artifact is bad.”
- Subjective review requests: system says “this dimension needs a review.”
- Subjective assessments: reviewer says “this dimension scores 72/100.”
- Subjective review findings: reviewer says “here are the concrete defects behind that 72.”

So yes, they all end up in one unified queue/state system, but no, they are not just duplicate versions of the same thing. The shared container is the same; the semantics are different. If you want, I can sketch the exact lifecycle of one dimension from `scan` -> `review --import` -> `plan resolve` -> `rescan`.
