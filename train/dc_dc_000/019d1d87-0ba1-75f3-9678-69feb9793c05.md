Fix how track-level settings and clip-level overrides interact.

CURRENT PROBLEM: Track scale (e.g. 0.95) creates a CSS transform scale() wrapper around all clips on that track. When a user drags a clip to set x/y position, the track scale acts as a hard boundary - you can't move the clip to the edges because the scaled-down container clips the content. The track scale and clip positioning are fighting each other.

CORRECT MENTAL MODEL: Track settings are DEFAULTS that clips inherit. Clip-level settings OVERRIDE track settings, they don't stack on top. Specifically:

1. SCALE: Track scale=0.95 means 'by default, show clips at 95% zoom'. If a clip has its own scale/size override, use THAT instead, not track_scale * clip_scale. The clip override replaces the track default.

2. POSITION: Track scale affects where content appears (centered, scaled down). But if a clip has x/y set, those coordinates should be in the full composition space (1280x720), and the clip should render at those absolute coordinates regardless of track scale.

3. FIT: Track fit=contain means 'by default, letterbox clips'. If a clip has explicit width/height, use those instead.

The key insight: track settings define the DEFAULT rendering for clips that have no overrides. Once a clip has ANY position/size override, it should render in absolute composition space, completely bypassing track scale/fit.

IMPLEMENTATION: The current approach in TimelineRenderer.tsx wraps ALL clips in a div with transform:scale(trackScale). This is wrong because it scales even overridden clips. Instead:
- Clips WITHOUT overrides: render inside the scaled track wrapper (inheriting track defaults)
- Clips WITH overrides: render in absolute composition space, bypassing the track wrapper entirely

The OverlayEditor canvas interaction should always work in composition space (1280x720). When a user drags a clip that was previously using track defaults, it should initialize the override from the clip's current visual position (accounting for the track scale) and then let the user freely position it anywhere in composition space.

ALSO FIX: The overlay drag box alignment - it needs to correctly show where the clip IS (accounting for track scale for non-overridden clips) and where it WILL BE (in composition space for overridden clips).

        # Implementation Plan: Fix Track-Default / Clip-Override Rendering Model

## Overview

**Problem:** Track scale (`transform: scale(0.95)`) wraps ALL clips in a scaled, `overflow: hidden` container. Clips with position overrides try to counteract this via a division hack (`left: clip.x / trackScale`), but they're still trapped inside the clipped container — edge positions get cut off, and the math is fragile.

**Goal:** Track settings become defaults that clips inherit. Clips with ANY position/size override render directly in composition space, completely bypassing the track scale wrapper. The overlay editor initializes drag positions correctly when transitioning a clip from "track default" to "overridden."

**Key files:**
- `shared/compositions/TimelineRenderer.tsx` — track wrapper with scale transform
- `shared/compositions/VisualClip.tsx` — visual clip rendering + division hack
- `shared/compositions/TextClip.tsx` — text clip rendering + division hack
- `viewer/src/OverlayEditor.tsx` — drag interaction + overlay box projection

**Current state:** The division-by-trackScale hack already exists in VisualClip (`:24-31`) and TextClip (`:29-31`). The OverlayEditor already distinguishes overridden vs non-overridden clips for projection (`:237`, `:319`). The fix restructures the rendering tree rather than trying to compensate within it.

## Step 1: Split clip rendering in TimelineRenderer.tsx
**Scope:** Medium  
**File:** `shared/compositions/TimelineRenderer.tsx`

1. **Modify `renderVisualTrack`** (`:13-47`) to accept only non-overridden clips. Clips with ANY of `x`, `y`, `width`, `height` defined should be excluded from the scaled wrapper.

2. **Add a new rendering path** for overridden clips. After the scaled track `AbsoluteFill`, render a sibling `AbsoluteFill` (no transform, no overflow:hidden) containing only clips with overrides. This AbsoluteFill needs:
   - Same z-ordering position as the track (so it layers correctly with other tracks)
   - `opacity: track.opacity ?? 1` still applied (track opacity is not a "default" — it's a compositing property)
   - `blendMode` still applied

3. **Concrete approach:** Refactor the `visualTracks.map(...)` loop in the `TimelineRenderer` component (`:58-61`) to, for each track:
   - Filter clips into `defaultClips` (no position override) and `overriddenClips` (has override)
   - Render `defaultClips` inside the existing scaled wrapper
   - Render `overriddenClips` in a new unscaled wrapper immediately after

4. **Key detail:** The rendering order must interleave correctly. Since tracks are rendered bottom-to-top and clips within a track are rendered in order, overridden clips from track V1 must still render below all V2 clips. Rendering the unscaled wrapper right after the scaled wrapper for each track preserves this.

## Step 4: Fix drag initialization in OverlayEditor.tsx
**Scope:** Medium  
**File:** `viewer/src/OverlayEditor.tsx`

When a clip with no override is first dragged, it needs to initialize to where the clip CURRENTLY APPEARS in composition space, not to `(0, 0, compositionWidth, compositionHeight)`. The current visual position of a non-overridden clip at track scale S centered in composition space is:
   ```
   x = (compositionWidth * (1 - S)) / 2
   y = (compositionHeight * (1 - S)) / 2
   width = compositionWidth * S
   height = compositionHeight * S
   ```
   Update the initialization block (`:204-211`) to use these values.

2. **Verify `onMouseMove`** (`:237`). The `effectiveScale` logic should now always use `effectiveScale = 1` once a clip has overrides (which happens immediately on first drag). 3. **Fix potential race:** The `needsInitialization` check reads `meta[actionId]` but `onOverlayChange` is async. Ensure `dragState.current` captures the initialized values (`startX`, `startY`, `startW`, `startH`) so the first `onMouseMove` uses correct start positions regardless of when the meta update propagates.
