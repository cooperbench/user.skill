### 4. "hidden_mutating_normalizers" - **SMOKING GUN**

This is the real one. Looking at `helpers.py`:

Functions like `_queue_order()` (lines 40-47), `_skipped_map()` (lines 50-57), `_cluster_map()` (lines 60-67), `_triage_meta()` (lines 70-77), `_execution_log()` (lines 80-87) **all mutate the plan/meta dict they receive**:

```python
def _queue_order(plan: PlanModel) -> list[str]:
    """Return normalized queue order list, seeding default if missing."""
    order = plan.get("queue_order")
    if isinstance(order, list):
        return order
    normalized: list[str] = []
    plan["queue_order"] = normalized  # ← MUTATION!
    return normalized
```

Then in `workflow.py`:

- Lines 102-106: `_state_lang_capabilities()` mutates `state["lang_capabilities"]` if it doesn't exist
- Lines 204-220: `_apply_assessment_reset()` mutates payload dicts (this one is explicit about it)
- Lines 223-252: `_reset_subjective_assessments_for_scan_reset()` directly mutates `state["reminder_history"]` (lines 243, 251)

The function names read as "getters" but they're **write operations**. Looking at the scan workflow flow (lines 257-296), these helpers are called during `prepare_scan_runtime()`, which doesn't explicitly tell the caller "this mutates state."

**Verdict**: This is a **real problem**. Function names like `_queue_order()` sound read-only. Callers see `order = _queue_order(plan)` and don't expect `plan` to be mutated as a side effect. This violates the principle of least surprise. **Legitimate design issue that could cause bugs if someone refactors assuming immutability.**

### 5. "stale_lang_marker_cache_after_plugin_reload" - **REAL BUG WAITING TO HAPPEN**

In `lang.py` lines 61-80:

```python
@_cache_once
def _lang_config_markers() -> tuple[str, ...]:
    """Collect project-root marker files from language plugins + fallback markers."""
    markers = set(EXTRA_ROOT_MARKERS)
    for lang_name in lang_api.available_langs():
        cfg = load_lang_config(lang_name)
        for marker in getattr(cfg, "detect_markers", []) or []:
            ...
    return tuple(sorted(markers))
```

This caches the **entire marker set** including dynamically loaded plugin markers. The `languages/__init__.py` exports `reload_lang_plugins()` (line 64-67) which forces rediscovery, but **`_lang_config_markers()` never gets invalidated**.

In `lang.py`, the cache is via `_cache_once` (lines 61-64) which creates an `lru_cache(maxsize=1)`. The problem:

- If code calls `reload_lang_plugins()`, the marker cache is stale
- Subsequent calls to `resolve_detection_root()` use the old markers
- A newly-loaded plugin won't be detected

**Verdict**: This is a **real, subtle bug**. It won't happen often (plugin reloads are rare in a CLI), but it's a time bomb. The fix is trivial (invalidate the cache when reloading), but the current design assumes markers never change at runtime. **Legitimate issue that could cause confusion in plugin development/testing.**
