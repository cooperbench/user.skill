Yes: `memories` and `observations` are useful, but they are not quite enough if you want the agent to build a holistic, browsable understanding over time.

I’d think of the memory model as needing four layers, not one catch-all table.

**1. Facts / Memories**

These are durable, concrete, relatively atomic things.

Examples:

- “Alex works nights on Tuesdays.”
- “Maya’s sister is visiting in May.”
- “They prefer Discord over WhatsApp.”
- “Jordan asked not to discuss money with their partner without consent.”

This maps well to your current `memories` table. The key rule: a memory should be something you can imagine being true or false later.

**2. Observations**

These are pattern-level notes with evidence, uncertainty, and scope.

Examples:

- “When logistics come up, Maya tends to shift quickly into problem-solving, while Alex seems to want emotional acknowledgment first.”
- “Alex often softens conflict with humor when the topic feels vulnerable.”
- “They seem to escalate faster when plans change late in the day.”

This maps well to your current `observations` table. These should always have confidence, significance, timestamps, and supporting message IDs. Observations are not necessarily “truth”; they are working hypotheses.

**3. Themes**

These are larger recurring domains that organize many memories and observations.

Examples:

- “Unequal mental load around planning”
- “Feeling dismissed during repairs”
- “Trust around money decisions”
- “Different needs around space after conflict”

You already have `themes`, and I think this is the closest thing to the “holistic idea of things.” Themes are what the model should browse when asking, “What is this conversation really about?”

**4. Formulations / Learnings**

This is the missing abstraction, but I would be careful with the name `learnings`. I’d probably call it `formulations`, `working_models`, or `case_notes`.

This layer is more conclusion-like than an observation, but still provisional.

Examples:

- “A useful working model is that Alex experiences delayed replies as abandonment, while Maya experiences repeated check-ins as pressure. The conflict is not just response time; it is each person’s threat system interpreting the other’s coping strategy.”
- “Their repair attempts often fail because they move to solutions before either person feels accurately understood.”
- “The central loop appears to be pursuit/withdrawal, but it shows up through scheduling and tone rather than explicit attachment language.”

This is different from an observation. An observation says, “I’ve noticed X pattern.” A formulation says, “Here is my current integrated model of why these patterns cohere.”

That distinction matters because the agent can browse it differently:

- `memories`: “What concrete facts do I know?”
- `observations`: “What patterns have I noticed?”
- `themes`: “What domains keep recurring?”
- `formulations`: “What is my best current interpretation of the dynamic?”

I would not make `learnings` a vague bucket. That will become messy fast. If you add it, make it a constrained abstraction:

```text
formulations
- id
- title
- summary
- status: active | retired | contradicted
- confidence
- scope: user | dyad | theme
- related_theme_ids
- related_memory_ids
- related_observation_ids
- supporting_message_ids
- created_at
- updated_at
- last_reinforced_at
- contradicted_by_ids / supersedes_id
```

The most important design principle: every higher-level abstraction should point down to evidence. A formulation without linked observations/messages is just model lore.

- `get_recent_messages`
- `search_messages`
- `get_memories`
- `get_observations`

```text

- active themes
- strongest formulations
- high-significance observations
- durable facts
- open watch items
- recent contradictions / stale notes
```

The prompt should communicate the memory stack as a ladder:

```text

memories = concrete facts
observations = repeated or meaningful patterns
themes = durable life domains
formulations = synthesized provisional explanations
```

- **Memory:** “What fact should I not forget?”
- **Observation:** “What pattern have I seen?”
- **Theme:** “What long-running domain does this belong to?”
- **Formulation:** “What is my current best integrated explanation of why these patterns hang together?”
- **Watch item:** “What should I follow up on later?”

- Memory: “Peter’s work schedule changes week to week.”
- Observation: “Late plan changes reliably spike conflict.”
- Theme: “Planning, reliability, and shared load.”

**Core Relationship Model**
Each primitive should relate downward to evidence and sideways to organizing concepts.

```text
messages
  -> memories
  -> observations
  -> themes
  -> distillations
  -> watch_items / bridge_candidates / feedback
```

But not everything should relate to everything.

**Memories**
A memory should relate to:

- `about_user_id`: who/what the fact is about
- `source_message_ids`: where the fact came from
- `related_theme_ids`: optional, only if the fact clearly belongs to a life domain
- `supersedes_memory_id`: when replacing an old fact

I would add `source_message_ids` to `memories`. Right now observations have `supporting_message_ids`, but memories don’t. That makes facts less auditable than patterns, which is backwards.

Example:

```text
Memory:
“Maya’s mother is having surgery in June.”

Related to:
- about_user_id: Maya
- source_message_ids: message where she said it
- related_theme_ids: caregiving/family if applicable
```

**Observations**
An observation should relate to:

- `about_user_id`: optional; use when pattern is person-specific
- `about_dyad`: implicitly or explicitly, for couple-level loops
- `supporting_message_ids`: yes, required when possible
- `related_memory_ids`: optional, if a fact grounds it
- `related_theme_ids`: yes, if it belongs to a life domain
- `supersedes_observation_id` or revision history: useful

I would add `related_memory_ids` to observations. Some observations are built from facts plus messages.

Example:

```text
Observation:
“When plans change late, Peter tends to read it as not being considered.”

Related to:
- about_user_id: Peter
- supporting_message_ids: the messages showing this
- related_theme_ids: planning/reliability/shared load
- related_memory_ids: Peter’s variable work schedule, if relevant
```

**Themes**
Themes should relate to:

- `related_memory_ids`: derived or queryable
- `related_observation_ids`: derived or queryable
- maybe `primary_user_ids` / `dyad_id` if this will ever support more than one couple
- distillations that summarize the theme

I would not over-store arrays on `themes` unless needed. Since memories and observations already point to themes, theme contents can be queried backward. But the theme table should maybe include:

```text

status
sentiment
health
first_seen_at
last_active_at
last_reinforced_at
```

Themes are containers, not evidence themselves.

**Distillations**
Distillations should relate to:

- `scope`: `user`, `partner`, `dyad`, or `theme`
- `related_theme_ids`
- `related_observation_ids`
- `related_memory_ids`
- `supporting_message_ids`, but usually fewer/direct examples
- `supersedes_distillation_id`
- `status`: `active`, `superseded`, `contradicted`, `stale`
- `confidence`
- `sensitivity`: maybe `low`, `medium`, `high`
- `visibility`: whether it is safe to use across threads, or whether OOB/cross-thread rules must gate it

The key: a distillation should mostly be related to **observations and themes**, not directly to every message. Messages are evidence; observations are interpreted evidence; themes are organization; distillations are synthesis.

Example:

```text

Related to:

- related_observation_ids: late changes spike conflict; Peter seeks explicit confirmation; Maya withdraws under pressure
- related_memory_ids: Peter’s work schedule, Maya’s family obligation if relevant
- supporting_message_ids: 2-5 exemplar messages
```

- `related_theme_ids`

```text
- related_observation_ids: repair gets delayed after logistics conflict
```
