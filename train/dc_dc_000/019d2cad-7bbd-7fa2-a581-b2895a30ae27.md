        Idea:
Add a research phase to megaplan that runs after plan and before critique. The research phase takes the plan output, identifies framework-specific APIs mentioned in it, searches for current documentation on each one, and produces a research context that feeds into the critique prompt.

The problem this solves: Models plan with stale training data. They confidently use outdated APIs (e.g., force-dynamic instead of connection(), missing cacheComponents config). The critique phase can't catch these because it has the same stale knowledge. By searching current docs after the plan is written, the critique gets fresh information to compare against.

Flow: init → plan → research → critique → gate → ...

The research phase:
1. Reads the plan output (plan_v{n}.md and plan_v{n}.meta.json)
2. Reads the project's package.json to identify frameworks and versions
3. Extracts specific API references from the plan (imports, function names, config options, directives)
4. For each API reference, searches for current documentation
5. Produces research.json with:
   - apis_found: list of {name, source_in_plan, search_query, current_docs_summary, potential_issues}
   - framework_versions: {name: version} from package.json
   - research_context: formatted text block for injection into critique prompt
6. The critique prompt includes the research context so it can flag stale APIs

Key design decisions:
- The research phase uses Hermes with web_search and web_extract tools
- It runs as a megaplan worker (same as plan/critique/execute) with its own prompt and schema
- Light robustness skips research (like it skips critique)
- The research phase should be fast — just targeted searches, not exhaustive research
- If no framework-specific APIs are found in the plan, research produces an empty context and completes instantly
- The research output persists as research.json in the plan directory
- The critique prompt builder checks for research.json and includes it if present

## Overview

Megaplan currently flows: init → plan → critique → gate → ... The plan and critique phases share the same stale training data, so the critique can't catch outdated API usage. This adds a **research** phase between plan and critique that reads the plan output, identifies framework-specific APIs, searches current documentation via Hermes web tools, and produces a research context that the critique prompt consumes.

**Repository shape:** The workflow is a state machine in `_core.py` with `WORKFLOW` and `WORKFLOW_OVERRIDES` dicts. Each phase has a prompt builder (`prompts.py`), handler (`handlers.py`), schema (`schemas.py`), and CLI registration (`cli.py`). Hermes workers already have web search/extract tools available for plan/critique/revise phases (`hermes_worker.py:52-63`).

**Key constraint:** Research must be fast — targeted searches only. Light robustness should skip research (same as it skips gate). The research output is a JSON artifact that the critique prompt conditionally includes.
