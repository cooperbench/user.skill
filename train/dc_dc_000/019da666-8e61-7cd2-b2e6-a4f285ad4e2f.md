runtime parsing\n+- `timeline-config.schema.json` export for tooling and docs\n+- TS types generated from the same source of truth\n+- a migration registry keyed by version\n+\n+### 4.2 Migration Contract\n+\n+```ts\n+export type TimelineMigration = (\n+  prev: unknown,\n+  fromVersion: number,\n+) => TimelineConfig;\n+```\n+\n+Migration error semantics:\n+\n+- Throw `TimelineMigrationError` for unknown source versions, invalid pre-migration payloads, or migrations that cannot preserve required core fields.\n+- Do not silently drop unknown core fields.\n+- Migrations may rewrite `app` payloads for known host namespaces, but only when the migration is explicitly versioned and documented.\n+\n+### 4.3 Core vs App Extensions\n+\n+The namespace rule is strict:\n+\n+- `app: Record<string, unknown>` is the only extension escape hatch.\n+- `app` is allowed at the top level, on each track, and on each clip.\n+- Unknown keys outside `app` are rejected.\n+- Host-specific payloads should use namespaced keys inside `app`, for example `app['x-reigh']`.\n+\n+Forward-compat rule:\n+\n+- A reader may preserve and round-trip unknown payloads only inside `app`.\n+- A reader must reject unknown top-level, clip, or track keys outside `app`.\n+- A reader must reject future core versions unless a registered migration exists for that version path.\n+\n+### 4.4 Serializer Reconciliation\n+\n+Current behavior is fully strict. `validateSerializedConfig()` only allows `output`, `clips`, `tracks`, and `pinnedShotGroups` at the top level, and separately rejects unknown clip and track keys (`reigh-app/src/tools/video-editor/lib/serialize.ts:98-122`).\n+\n+Chosen option: Option A\n+\n+- Whitelist a single `app` key at the top level, track level, and clip level in `@tbd/schema` and in the extracted serializer logic derived from `lib/serialize.ts`.\n+- Keep strict rejection for all other unknown keys.\n+\n+Rejected option: Option B\n+\n+- Do not loosen the serializer to accept arbitrary unknown keys everywhere.\n+- Reason: a globally loose serializer would undermine the entire premise of a versioned OSS schema, make migrations non-local, and make “hand-editable JSON with strong guarantees” materially weaker.\n+\n+### 4.5 `pinnedShotGroups` Migration\n+\n+`TimelineConfig` currently carries `pinnedShotGroups` as a top-level core field (`reigh-app/src/tools/video-editor/types/index.ts:181-186`), and the serializer writes that field back out when present (`reigh-app/src/tools/video-editor/lib/serialize.ts:124-139`). The OSS v1 schema removes it from core.\n+\n+Migration rule:\n+\n+- v0 -> v1 moves `config.pinnedShotGroups` to `config.app?.['x-reigh']?.pinnedShotGroups`\n+- The destination is namespaced under `x-reigh`\n+- The destination is not a top-level `reigh` key and not a second top-level field\n+\n+Round-trip invariant:\n+\n+- Loading a legacy reigh config, migrating it to v1, and then saving it back through the compatibility helpers must preserve the same pinned-group semantics for all current runtime callers and tests.\n+- The extracted OSS schema never re-promotes `pinnedShotGroups` into core once migrated.\n+\n+## 5.
