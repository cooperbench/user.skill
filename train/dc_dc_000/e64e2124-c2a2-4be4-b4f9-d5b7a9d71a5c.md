### THE DEADLOCK SCENARIO (COMPLETE)

The deadlock occurs when:

1. **Plan has IDs that are no longer open/alive:**
   ```
   queue_order: ["id_gone", "id_stale_resolved", "id_target"]
   state.findings:
     - "id_stale_resolved": status="fixed" (manually resolved, no scan)
     - "id_target": status="open"
     - "id_gone": (doesn't exist in state)
   ```

2. **User tries to resolve something in the plan:**
   ```bash
   desloppify plan done id_target --note "..." --attest "..."
   ```

3. **`_check_queue_order_guard()` checks if `id_target` is next:**
   - Loads plan with stale `queue_order: ["id_gone", "id_stale_resolved", "id_target"]`
   - Builds work queue → `_apply_plan_order()` silently skips `id_gone` and `id_stale_resolved`
   - Returns `[id_target_item, ...]`
   - `front_item = id_target_item` → `front_ids = {id_target}`
   - `resolved_ids = {id_target}`
   - `out_of_order = {}` → **Should NOT be blocked**

**BUT:** The issue arises when:
- There are NO matching findings for the user's patterns
- OR the queue_order becomes completely out of sync with actual open findings
- OR the user tries to resolve an ID that's further down in the queue
