        # Implementation Plan: Parallelize Critique Phase with Per-Check Sub-Agents

## Overview

The critique phase currently runs one Hermes agent that sequentially works through 4-8 checks, producing one large JSON. This is slow (~5-10 min) and fragile on weaker models (MiniMax: 75% failure rate on large structured output).

**Goal:** Split critique into N parallel sub-agents (one per check), each producing a tiny JSON for its single check, then merge results into the standard `critique_v{N}.json` format.

**Current architecture (post-template-file refactor):**
- `handle_critique()` → `_run_worker("critique")` → `run_step_with_worker()` → `resolve_agent_mode()` → `run_hermes_step()` → single `AIAgent.run_conversation()`
- `_critique_prompt()` (`prompts/critique.py:152`) builds the prompt referencing an output template file
- `_write_critique_template()` (`prompts/critique.py:83-149`) writes `plan_dir/critique_output.json` with all checks (question + guidance + empty findings)
- `run_hermes_step()` has a rich fallback chain for parsing agent output (`hermes_worker.py:256-378`): template file → final_response → summary prompt → reasoning tags → assistant messages → alternate files → last-resort summary prompt
- Session management: critique uses persistent `hermes_critic` session key (`workers.py:751-752`), with conversation history reloaded from `SessionDB` when not fresh
- Standard robustness: 4 core checks (issue_hints, correctness, scope, verification)
- Heavy robustness: 8 checks (4 core + 4 extended)

**Proposed architecture:**
- `handle_critique()` branches: if parallel eligible (Hermes agent, >1 check) → `run_parallel_critique()` in new `megaplan/parallel_critique.py`
- Parallel runner spawns N threads (one per check), each with its own AIAgent, single-check prompt, and unique template file (`critique_check_{check_id}.json`)
- Each sub-agent fills findings for its ONE check and optionally contributes `verified_flag_ids` / `disputed_flag_ids`
- Parsing reuses the existing fallback chain from `hermes_worker.py` via an extracted helper function
- Merge step concatenates check results and flag ID lists (disputed wins on conflict) into standard critique payload
- Session state: parallel agents are ephemeral; the existing `hermes_critic` session slot is not updated, preserving it for future sequential runs or iteration context
- `flags.py` synthesizes flags from flagged findings as it already does — NO separate flags agent

**Key constraints:**
- Output format identical to sequential path: `{checks: [...], flags: [...], verified_flag_ids: [...], disputed_flag_ids: [...]}`
- Must respect `resolve_agent_mode()` — only parallelize for Hermes agents
- Sub-agents do NOT go through `run_hermes_step()` (which validates against the full critique schema) — they use direct AIAgent instantiation but reuse the extracted parsing helper
- `sys.stdout = sys.stderr` redirect (`hermes_worker.py:190-192`) is process-global — redirect once before spawning threads

### Step 3: Create parallel critique runner (`megaplan/parallel_critique.py`)
**Scope:** Large — core new file
1. **Create** `megaplan/parallel_critique.py` with main entry point:
   ```python
   def run_parallel_critique(
       state: PlanState, plan_dir: Path, *, root: Path, model: str | None,
       checks: tuple[CritiqueCheckSpec, ...],
   ) -> WorkerResult:
   ```
2. **Redirect stdout once** before spawning threads (the `sys.stdout = sys.stderr` pattern), restore in `finally`.
3. **For each check**, submit to `ThreadPoolExecutor(max_workers=len(checks))`:
   - Write per-check template: `plan_dir/critique_check_{check_id}.json` via `write_single_check_template()`
   - Build single-check prompt via `single_check_critique_prompt()`
   - Create fresh `AIAgent` with same config as `run_hermes_step()` — model resolution (OpenRouter/zhipu/minimax prefix routing from `hermes_worker.py:196-205`), `enabled_toolsets=["file", "web"]`, `quiet_mode=True`, `max_tokens=8192`, fresh `SessionDB()`, unique `session_id`
   - Run `agent.run_conversation(user_message=prompt)`
   - **Parse using the extracted `parse_agent_output()`** from Step 1, passing `output_path=plan_dir/critique_check_{check_id}.json`. This gives each sub-agent the full fallback chain (template file → final_response → reasoning tags → summary prompt etc.)
   - **Clean** via `clean_parsed_payload()` from Step 1 (strip guidance/prior_findings, fill defaults)
   - Extract the single check dict from `payload["checks"][0]`, plus `verified_flag_ids` and `disputed_flag_ids`
   - Validate the check has non-empty findings via `_valid_findings()` from `checks.py:162`
   - Return `(check_dict, verified_ids, disputed_ids, cost_usd)` or raise on failure
4. **Merge** results from `futures.as_completed()`:
   - Concatenate check dicts into `checks` array, **ordered by original check order** (not completion order)
   - Union `verified_flag_ids` and `disputed_flag_ids` across sub-agents, with **conflict resolution: if a flag ID appears in both `verified` and `disputed`, it goes in `disputed` only** (conservative — keep it for human review). Implementation:
     ```python
     all_verified = set()
     all_disputed = set()
     for _, verified, disputed, _ in results:
         all_verified |= set(verified)
         all_disputed |= set(disputed)
     # Disputed wins on conflict
     all_verified -= all_disputed
     merged["verified_flag_ids"] = sorted(all_verified)
     merged["disputed_flag_ids"] = sorted(all_disputed)
     ```
   - Set `flags: []` — let `flags.py:67-85` synthesize from flagged findings
5. **Handle failures**: If any sub-agent fails, log the error and re-raise to trigger fallback to sequential in `handle_critique()`.
6. **Session state**: Do NOT update `state["sessions"]` for the parallel path. The ephemeral sub-agents don't persist sessions. The existing `hermes_critic` session slot (if any) remains untouched, available for future sequential runs.
7. **Return** `WorkerResult(payload=merged, raw_output="parallel", duration_ms=wall_clock, cost_usd=sum_of_costs, session_id=None)`.

## Design Decision: Reuse Parsing via Extraction (addresses FLAG-001)

The v2 plan described a simplified "read template or parse final_response" path for sub-agents, dropping the rich recovery logic in `hermes_worker.py:256-378`. This would be a reliability regression — models like MiniMax and GLM-5 regularly need the reasoning-tag fallback, summary prompt, and alternate file search.

**Fix:** Extract the parsing chain into `parse_agent_output()` and `clean_parsed_payload()` in `hermes_worker.py`. Both `run_hermes_step()` and the parallel runner call these same functions. Zero code duplication, identical recovery behavior.

## Design Decision: Disputed Wins on Merge Conflict

When different sub-agents return the same flag ID in both `verified_flag_ids` and `disputed_flag_ids`, `flags.py:57-65` would process verified first then disputed, leaving `verified: True` but `status: "disputed"` — an inconsistent state.

**Fix:** The merge step removes any ID from `verified` if it also appears in `disputed`. Disputed wins because it's the conservative choice — keeps the flag open for human review rather than silently clearing it.

## Design Decision: Ephemeral Sessions

Critique normally uses a persistent `hermes_critic` session (`workers.py:751-752`) for conversation history across iterations. Parallel sub-agents are one-shot — they don't need session continuity and creating N sessions per check would pollute the session store.

**Fix:** Parallel sub-agents each get a fresh UUID session (required by AIAgent constructor) but the parallel runner does NOT update `state["sessions"]`. The existing `hermes_critic` slot is left untouched. If the parallel path fails and falls back to sequential, the sequential path manages sessions normally. This means parallel critique iterations don't build on prior conversation context, but they DO get prior findings via the template file's `prior_findings` field — which is the more reliable mechanism anyway.
