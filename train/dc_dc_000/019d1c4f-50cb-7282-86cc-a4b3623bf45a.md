        Plan:
        # Implementation Plan: GPU Worker Model-Affinity Task Scheduling with Warm Preference Period

## Overview

The system already has **passive model affinity**: the `claim_next_task_service_role` SQL function prioritizes tasks matching a worker's `current_model` but will immediately claim any task if no matching one exists. The `same_model_only` flag exists but is unused by the worker.

**The goal** is to add a **warm preference period**: when a GPU worker finishes a task, it should first spend X seconds polling with `same_model_only=true` (only accepting tasks matching its loaded model). After the preference window expires without a match, it falls back to claiming any available task. This minimizes expensive model reloads (30-60+ seconds each) by keeping workers "warm" for their current model.

### Current architecture (relevant pieces)
- **Worker** (`reigh-worker/source/runtime/worker/server.py:398-488`): Infinite loop calling `get_oldest_queued_task_supabase(worker_id)` every 10s, which calls the `claim-next-task` edge function with `run_type: "gpu"` — **never passes `same_model_only`**.
- **Edge function** (`reigh-app/supabase/functions/claim-next-task/index.ts:57`): Already accepts `same_model_only` boolean and passes it to the RPC.
- **SQL RPC** (`claim_next_task_service_role` in migration `20260121000000`): Already implements `p_same_model_only` — when true, only returns tasks where `get_task_model(t.params) = v_worker_model`.
- **Model registration** (`update-worker-model` edge function + `notify_worker_model_switch` in worker): Worker already calls this before loading a new model.
- **Orchestrator** (`reigh-worker-orchestrator/gpu_orchestrator/`): Scales workers based on aggregate task counts. Currently has no per-model awareness.
- **Task counts** (`task-counts` edge function): Returns queue depth for scaling decisions. No per-model breakdown.

### Key constraint
The warm-preference period must **not starve tasks**. If all workers are warm for model A and only model B tasks are queued, workers must eventually fall back. The preference window provides a bounded wait, after which they claim anything.

## Step 2: Implement warm-preference polling loop in the worker server
**Scope:** Medium — 1 file  
**Repo:** `reigh-worker`

1. **Add config** for the warm preference window. Read from environment in the worker entrypoint or CLI args:
   ```python
   WARM_PREFERENCE_SECONDS = int(os.getenv("WARM_PREFERENCE_SECONDS", "30"))
   ```

2. **Modify** the main polling loop in `reigh-worker/source/runtime/worker/server.py` (lines 398-488). After completing a task (line 466/483), track when the worker became idle. On each poll iteration:

   ```python
   idle_since: float | None = None  # timestamp when worker last became idle

   while True:
       # Determine if we're in warm-preference window
       same_model_only = False
       if idle_since is not None:
           idle_duration = time.time() - idle_since
           if idle_duration < WARM_PREFERENCE_SECONDS:
               same_model_only = True

       task_info = get_oldest_queued_task_supabase(
           worker_id=cli_args.worker,
           same_model_only=same_model_only,
       )

       if not task_info:
           if idle_since is None:
               idle_since = time.time()  # first idle poll
           time.sleep(cli_args.poll_interval)
           continue

       idle_since = None  # reset on task claim
       # ... existing task processing ...
   ```

3. **Log transitions** between warm-preference and fallback mode:
   ```python
   if same_model_only and idle_duration >= WARM_PREFERENCE_SECONDS:
       headless_logger.info(f"[AFFINITY] Warm preference window expired after {WARM_PREFERENCE_SECONDS}s, falling back to any task")
   ```

4. **Edge case**: On first boot (no model loaded yet), `idle_since` starts as None and `same_model_only` defaults to False — worker claims any task. This is correct because the worker has no model to prefer.

**Validation:** Manual testing with `WARM_PREFERENCE_SECONDS=10` — observe logs showing warm-preference attempts followed by fallback.

2. **Create migration** `reigh-app/supabase/migrations/YYYYMMDD_add_model_breakdown_rpc.sql`:
   ```sql
   CREATE OR REPLACE FUNCTION count_queued_tasks_by_model(p_run_type TEXT DEFAULT NULL)
   RETURNS TABLE(model TEXT, task_count BIGINT)
   LANGUAGE plpgsql SECURITY DEFINER
   AS $$
   BEGIN
     RETURN QUERY
     SELECT 
       COALESCE(get_task_model(t.params), '__no_model__') as model,
       COUNT(*)::BIGINT as task_count
     FROM tasks t
     JOIN projects p ON t.project_id = p.id
     JOIN users u ON p.user_id = u.id
     WHERE t.status = 'Queued'::task_status
       AND u.credits > 0
       AND COALESCE((u.settings->'ui'->'generationMethods'->>'inCloud')::boolean, true) = true
       AND all_dependencies_complete(t.dependant_on)
       AND (p_run_type IS NULL OR get_task_run_type(t.task_type) = p_run_type)
     GROUP BY COALESCE(get_task_model(t.params), '__no_model__');
   END;
   $$;
   ```

## Overview

The system already has **passive model affinity**: the 4-arg `claim_next_task_service_role` SQL function (migration `20251222000001`) prioritizes tasks matching a worker's `current_model` but immediately claims any task if no match exists. The `same_model_only` parameter and the `update-worker-model` edge function exist but are **broken**: the worker sends `"model"` in the payload while the edge function expects `"current_model"`, so `workers.current_model` is never populated and affinity is a no-op.

**The goal** is to:
1. Fix the model registration bug so `workers.current_model` gets populated.
2. Add a **warm preference period**: after finishing a task, a worker polls with `same_model_only=true` for X seconds before falling back to claiming any available task. This minimizes model reloads (30-60+ seconds each).

### Current architecture (relevant pieces)
- **Worker polling loop** (`reigh-worker/source/runtime/worker/server.py:398-488`): Calls `get_oldest_queued_task_supabase(worker_id)` every 10s with `run_type: "gpu"` — never passes `same_model_only`. Optionally preloads a model before entering the poll loop (line 376-377).
