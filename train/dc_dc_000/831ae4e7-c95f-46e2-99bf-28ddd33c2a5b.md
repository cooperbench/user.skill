# Sequence Code-Gen — Reuse Plan & Unified UX Framing

Companion to `.megaplan/sequence-code-pipeline-feasibility.md`. That doc
audits whether the effects pipeline can be ported to sequences (verdict:
yes, ~70% reuse, 3.5–4 day MVP). This doc answers two follow-ups:

1. The user wants **one unified UX** where the agent routes between
   JSON-edit and code-edit — not two separate modes.
2. **What can we actually reuse vs. generalize vs. fork** from the
   effects pipeline at the code level.

Citations are `path:line` against the working tree at
`the project root`.

---

## 1. The unified-UX framing

The feasibility doc proposes a "Generate code" sub-modal alongside the
existing JSON-only `SequenceCreator`. The user's framing is stronger:
**single prompt box, agent decides path**. That requires three things
the existing audit doesn't cover.

### 1a. Three states a sequence-under-edit can be in

| State | Where source lives | What's editable cheaply |
|---|---|---|
| Theme-bundled | `vendor/timeline-theme-2rp/...` (build-time TSX) | Params only — code edits require redeploy or **forking to DB** |
| DB-code (new `type='sequence-component'`) | `resources.metadata.code` | Both params and code |
| JSON-only draft (current) | React state → timeline JSON on insert | Params only — there is no "code" yet |

The router has to know which state the selected clip is in *before* it
picks a path. The "fork to DB" transition (cloning a bundled component
into an editable DB resource) is the load-bearing UX moment that
doesn't exist today and isn't called out in the feasibility audit.

### 1b. Three request shapes the classifier should distinguish

- **Param-tweakable** — "slower", "use these images", "switch to
  vertical layout" *if* `layout` is already a schema field. → JSON path
  (cheap, retains `workerRender:true`).
- **Structurally-impossible-in-JSON** — "make the metric pulse on
  entry", "add a vignette behind the title", "use a custom easing curve
  mid-animation". → Code path (and if source is theme-bundled, fork-to-DB
  first).
- **Ambiguous** — "make it more dramatic". Cheapest move: try JSON
  first, offer "go deeper with code" as a follow-up.

A small classifier prompt (or a structured-output preamble on the
existing call) is enough — not a separate model. The classifier sees:
current schema, current params, user prompt → returns
`{path: 'json'|'code', reason}`. If `code` and source is theme-bundled,
the next step is the fork.

### 1c. What unifies in the UI

- Single prompt box, single Generate button.
- Side panel shows the same schema-driven editor (`SequenceParamEditor`)
  whether the user came in via JSON or code.
- A subtle badge on the result tells the user which path ran ("Edited
  params" vs "Generated component code"). Don't hide this — the
  worker-render capability flips between them and people will care
  later.
- "Edit" follow-ups can switch paths freely: a code-path result can
  still take a JSON-path follow-up if the next prompt only touches a
  known param.

### 1d. Risks specific to the unified flow

- **Worker-render asymmetry is a product issue, not a footnote.** JSON
  drafts route to `workerRender:true`; DB-code sequences must default
  `false` until the worker can compile. If a creator builds a 3-min
  film around a generated sequence and then can't render it
  server-side, that's a footgun. Surface the badge from day 1.
- **The "fork to DB" moment is the highest-friction UX in the unified
  flow.** A theme-bundled sequence is shared across the team's themes;
  cloning it into a per-user DB resource is correct but should feel
  like a deliberate user choice ("Customize this sequence for
  yourself"), not a silent drop-off.
- **Schema-vs-code drift is worse here.** If the agent flips to code
  path on Tuesday and JSON path on Wednesday for "the same" sequence,
  schemas can desync. The AST param-coverage check (feasibility doc §4
  item 1) is even more load-bearing in a unified UX than in two
  separate modes.

## 2. Reuse map — what to copy, generalize, or fork

After reading the effects pipeline end-to-end, the reuse picture is
clearer than "70%". The right answer is: copy some bits verbatim,
factor exactly three small abstractions, and explicitly *don't*
generalize others.

### Bucket 1 — copy-and-rename (don't try to be clever)

These are small enough that a shared abstraction would be more code
than two near-duplicates.

- **Edge-function skeleton.** `supabase/functions/ai-generate-effect/index.ts`
  is ~290 LOC of boilerplate (auth, rate-limit, Anthropic streaming,
  retry self-invoke at depth 1, structured response). Clone to
  `ai-generate-sequence-component/`. The streaming/SSE parsing
  (`callAnthropic`, lines 40–114) and retry self-invoke block (228–263)
  would be identical. Domain glue is just the
  `extractEffectCodeAndMeta`/`validateExtractedEffectCode` calls.
- **Edit-mode protocol.** `existingCode` round-trip
  (panel → edge → `templates.ts:159–171`). For sequences the field
  becomes `existingComponent` carrying `{code, schema, defaults}` but
  the shape and prompt-injection point are the same.
- **CreatorPanel UX skeleton.** Modal + Generate/Edit toggle + prompt
  textarea + abort controller + draft state + preview pane.
  `EffectCreatorPanel` and `SequenceCreatorPanel` are already cousins.
  Don't write `<CreatorPanel kind="effect|sequence">` — action buttons,
  asset wiring, and validation surfaces diverge enough that a generic
  shell will accumulate `if (kind === ...)` quickly.

### Bucket 2 — actually worth generalizing

These have a clean seam and you'll regret duplicating them.

- **`DynamicEffectRegistry` → `DynamicComponentRegistry<TProps>`.**
  The class (`DynamicEffectRegistry.ts`, 120 LOC) is already 90%
  domain-agnostic: subscribe/getSnapshot/version-bumping, `register`
  vs `registerAsync` with stale-pending guarding (lines 55–66),
  `batch()` for coalesced notifications, normalize-name for the
  `custom:` prefix. The only effect-specific thing is the
  `compileEffect`/`compileEffectAsync` import. Parameterize it:

  ```ts
  new DynamicComponentRegistry({
    builtIn,
    compile: (code) => tryCompileEffect(code),
    compileAsync: (code) => tryCompileEffectAsync(code),
  })
  ```

  Then `DynamicEffectRegistry` and `DynamicSequenceRegistry` become
  5-line factories.

- **The Sucrase + `new Function` compile harness.**
  `compileEffect.tsx:31–86` is one function with a hardcoded globals
  tuple. Lift to:

  ```ts
  function compileWithGlobals<TProps>(
    code: string,
    globals: Record<string, unknown>,
  ): CompileResult<FC<TProps>>
  ```

  Effects pass 8 globals; sequences pass ~14. Same Sucrase init, same
  IIFE wrapper, same `exports.default || module.exports.default ||
  module.exports` pickoff. The lazy-loaded `transformSync` cache
  (`compileEffect.tsx:6`) belongs in the shared module so Sucrase
  doesn't load twice.

- **Resources storage layer for code blobs.** `EffectMetadata`
  (`useResources.ts:80`) + `useListResources('effect', …)` + the
  create/update/delete trio is the *only* infra needed for sequence
  components. Two minimal changes:
  1. Add `'sequence-component'` to the `ResourceType` union
     (`useResources.ts:94`) and `isResourceType` (114).
  2. Define `SequenceComponentMetadata` mirroring `EffectMetadata`
     but with `{code, schemaJson, defaultsJson, clipType, themeId}`.

  No new table, no new RPC, no new RLS policy. `is_public` already
  exists (`20251207…` migration).

- **Prompt-output extraction harness.** `extractEffectCodeAndMeta`
  (`templates.ts:417–443`) implements a `// NAME / DESCRIPTION /
  PARAMS / MESSAGE` envelope around a code blob, with
  `stripMarkdownFences` + `stripRanges`. The envelope pattern is
  reusable; fields differ. Factor:

  ```ts
  parseEnvelope(text, ['NAME', 'DESCRIPTION', 'PARAMS', 'SCHEMA',
                       'DEFAULTS', 'MESSAGE'])
  ```

  Sequences need `SCHEMA` and `DEFAULTS` extra; effects don't use
  them. Auto-typo-fix (`templates.ts:425–432`) and `KNOWN_TYPOS`
  (449) are domain-specific — keep separate.

- **Retry-on-validation-failure self-invoke.** `index.ts:228–263` is a
  generic "edge function calls itself with `_retryDepth + 1` and the
  broken output as `_retryFailedCode`" pattern. Worth lifting to
  `_shared/aiCodegenRetry.ts` — otherwise the third codegen function
  will be a third copy.

### Bucket 3 — do NOT try to share

- **The system prompt.** `templates.ts`'s
  `EFFECT_COMPONENT_CONTRACT`/`AVAILABLE_GLOBALS`/`OUTPUT_RULES`/
  `VALIDATION_RULES` is a prompt-engineering artifact specific to
  entrance/exit effects and `React.createElement`-only output.
  Sequences need JSX-OK, theme-api globals, and a different model of
  what "a component" is. Sharing the prompt will produce worse output
  for both.
- **`validateExtractedEffectCode` regex set**
  (`templates.ts:458–492`). Encodes effect rules: `exports.default`,
  no imports, *requires* `React.createElement`, no `Math.random`
  outside `useMemo`, typo dictionary. Sequences want most of these
  except "requires React.createElement" (JSX is wanted) and need
  additional rules (param-coverage check, no `Date.now()`/
  `performance.now`, asset-key contract). Different rule set wearing
  the same shape — fork, or generalize as a `{rule, message}[]` and
  pass different lists.
- **`ParameterSchema` vs JSON Schema.** Effects use the custom
  `ParameterSchema` from `@/tools/video-editor/types`; sequences use
  JSON Schema (`vendor/.../schema.json`). Don't merge in MVP — let
  sequences keep JSON Schema and bridge to `SequenceParamEditor`'s
  existing reader.
- **Capability registry.** `SEQUENCE_CLIP_CAPABILITY_REGISTRY` is
  sequences-only (browserRender/workerRender/externalRender).
  Effects don't have an analogue. Keep it on the sequences side and
  force `workerRender:false` for DB-stored sequences via a
  capability builder, not via the shared registry.

### The minimum shared API to actually write

Three small modules, ~200 LOC total:

```
src/tools/video-editor/runtime-components/
  compileWithGlobals.ts          // Sucrase + new Function harness, generic
  DynamicComponentRegistry.ts    // generalized DynamicEffectRegistry
  index.ts                       // re-exports

supabase/functions/_shared/
  aiCodegenRetry.ts              // self-invoke retry helper
  promptEnvelope.ts              // parse // NAME / ... envelope, fences
```

Then:
- `DynamicEffectRegistry` becomes a 10-line factory wrapper around
  `DynamicComponentRegistry`.
- `DynamicSequenceRegistry` is the same wrapper with different globals.
- `ai-generate-effect/index.ts` shrinks ~80 LOC; the new
  `ai-generate-sequence-component/index.ts` lands at ~150 LOC instead
  of 290.

Everything else (panels, prompts, validators, schemas) stays forked.
The temptation is to generalize the prompt and validator because they
"look similar" — that's the trap. Generic surfaces are the bits that
touch *the runtime* (compilation, registration, storage), not the bits
that touch *the model* (prompts, parsing, rules).
