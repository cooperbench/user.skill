        # Implementation Plan: Fix Dead Time / Frozen Tail in Video Editor Timeline

## Overview

**Problem:** When a video clip's timeline span (`action.end - action.start`) exceeds the clip's actual playable media duration, the player shows a frozen final frame for the remaining time — "dead time." This is invisible to users because the timeline renders both playable and dead portions identically.

**Root causes identified:**
1. **Null-duration fallback on drop** — `useExternalDrop.ts:126` falls back to 5 seconds when `resolveFinalVideoDurationSeconds()` returns null. If the real video is shorter, the clip overshoots.
2. **Switch-to-final-video fallback** — `shot-group-commands.ts:331-335` falls back to `imageSpanDuration` when `getTimelineDurationFromSourceDuration()` returns null. If the image group was longer than the video, the clip overshoots.
3. **No post-hoc correction** — Once the asset registry later learns the real duration (e.g., metadata extracted asynchronously), no mechanism re-clamps the clip.
4. **No visual signal** — The clip renders at full timeline width regardless of whether `to` exceeds the registered asset duration. Users can't see the dead zone.
5. **No explicit user action** — Users have no way to say "trim this clip to its media end" or "intentionally hold the last frame here."

**Key architectural facts:**
- Clip config: `{ at, from, to, speed, hold }` in `TimelineClip` — hydrated into `TimelineAction { start, end }` via `timeline-data.ts:184-189`.
- Duration chain: `getClipDurationSeconds(clip) = getClipSourceDuration(clip) / speed`, where source duration = `hold` or `to - from`.
- Asset registry: `AssetRegistryEntry.duration` stores known media duration (may be null initially).
- Overhang = when `(to - from) > assetDuration` for a video clip (not an image/hold clip).
- The `hold` property already implements freeze-frame for images — we can reuse this concept for intentional video tail holds.

**Constraints:**
- Must not break existing clips that are correctly sized.
- Must handle the async nature of duration resolution (duration may arrive after drop).
- Resize already adjusts `speed` for visual clips rather than `to`, so resize doesn't create overhang.
- The `ClipAction` component has no current access to asset duration — it will need it for the visual indicator.

---

## Phase 1: Foundation — Overhang Detection Utility

### Step 1: Create overhang detection utility (`src/tools/video-editor/lib/overhang.ts`)
**Scope:** Small
1. **Create** a pure utility function `detectClipOverhang(clipMeta: ClipMeta, assetDuration: number | undefined): { hasOverhang: boolean; mediaEndSeconds: number; overhangSeconds: number }`.
   - For clips with `hold` property: no overhang (hold is intentional).
   - For clips with `clipType === 'hold'`: no overhang.
   - For video clips: compare `(to - from)` against `assetDuration`. If `to > assetDuration`, compute overhang.
   - Handle `from` offset: playable range = `assetDuration - from`, overhang = `(to - from) - (assetDuration - from)` = `to - assetDuration`.
2. **Create** a companion `getMediaEndFraction(clipMeta, assetDuration): number | null` that returns the fraction of timeline width where media ends (for the visual indicator). Returns null if no overhang or duration unknown.
3. **Add tests** for the utility in `src/tools/video-editor/lib/overhang.test.ts` covering: no overhang, overhang with from=0, overhang with nonzero from, hold clips (no overhang), missing duration (returns null/unknown).

### Step 2: Add `clampClipToMediaDuration` helper (`src/tools/video-editor/lib/overhang.ts`)
**Scope:** Small
1. **Add** `clampClipToMediaDuration(clipMeta: ClipMeta, assetDuration: number): Partial<ClipMeta>` — returns a meta patch that sets `to = Math.min(to, assetDuration)` and adjusts timeline duration accordingly.
2. **Add** `convertOverhangToHold(clipMeta: ClipMeta, assetDuration: number): Partial<ClipMeta>` — returns a meta patch that keeps the same total duration but splits at media end: the video portion plays normally, then a hold segment extends to the original end. Implementation note: this may need to split into two clips (video + hold), or could use a new `holdTail` property on the clip. Evaluate during implementation whether single-clip or split approach is simpler. Prefer single-clip with a `holdTail?: number` property if the renderer can handle it; otherwise split into two clips.
3. **Test** both helpers.

---

## Phase 2: Prevent Overhang on Drop and Switch-to-Final-Video

### Step 3: Improve duration fallback on shot drop (`src/tools/video-editor/hooks/useExternalDrop.ts`)
**Scope:** Small
1. **Change** the fallback at line 126 from `durationSeconds ?? 5` to a strategy that marks the clip as needing duration resolution rather than guessing. Two options (choose during implementation):
   - **Option A (preferred):** Keep the 5-second fallback for initial placement, but register a "pending duration" flag on the clip or asset entry. When the real duration resolves later (Step 4), auto-clamp.
   - **Option B:** If duration is null, still drop with 5s but immediately trigger async metadata extraction and re-clamp in a follow-up edit.
2. **Key invariant:** A dropped clip must never have `to > assetDuration` once `assetDuration` is known.

### Step 4: Auto-clamp when asset duration resolves (`src/tools/video-editor/hooks/useAssetManagement.ts` or new effect)
**Scope:** Medium
1. **Add** a reactive check: when `AssetRegistryEntry.duration` transitions from null/undefined to a positive number, scan all clips referencing that asset and clamp any that overshoot.
2. **Implementation:** This could be a `useEffect` in the editor shell or a post-mutation hook in the asset management layer. The effect watches the asset registry and, for each asset whose duration just became known, iterates clips → detects overhang → applies `clampClipToMediaDuration` patches as a single edit.
3. **Guard:** Only auto-clamp clips whose `to` exceeds the newly-known duration. Don't touch clips that were manually extended by the user (see Step 8 for explicit user action).
4. **Important:** This auto-clamp should be a silent, non-undo-able correction (or a single undoable edit), since it's fixing bad data rather than a user action.

### Step 5: Clamp on switch-to-final-video (`src/tools/video-editor/lib/shot-group-commands.ts`)
**Scope:** Small
1. **In** `buildSwitchShotGroupToFinalVideoMutation` (lines 331-335), when `getTimelineDurationFromSourceDuration()` returns null, use a more conservative fallback:
   - If `durationSeconds` is null, set `to` = `imageSpanDuration` (current behavior) BUT mark the clip for re-clamp (same mechanism as Step 4).
   - If `durationSeconds` is known, the existing `Math.min(imageSpanDuration, resolvedVideoDuration)` is correct — no change needed.
2. **In** `buildUpdateShotGroupVideoMutation` (around line 430), apply the same `Math.min` clamping.

## Phase 3: Visual Overhang Indicator in Timeline

### Step 6: Pass overhang data to clip renderer (`src/tools/video-editor/components/TimelineEditor/`)
**Scope:** Medium
1. **In** the `getActionRender` callback (used in `TrackListRenderer.tsx:135`), compute `getMediaEndFraction(clipMeta, assetDuration)` for each clip and pass it as a new prop `mediaEndFraction?: number | null` to `ClipAction`.
2. **The data flow:** `TimelineData.registry.assets[clipMeta.asset]?.duration` provides `assetDuration`. The `ClipAction` already receives `clipMeta` and `action`. Thread the asset duration through.

### Step 7: Render overhang zone in ClipAction (`src/tools/video-editor/components/TimelineEditor/ClipAction.tsx`)
**Scope:** Medium
1. **When** `mediaEndFraction` is a number between 0 and 1, render a visual overlay on the clip:
   - A semi-transparent diagonal-stripe pattern (CSS repeating-linear-gradient) covering the rightmost `(1 - mediaEndFraction) * 100%` of the clip.
   - Use `bg-amber-500/15` or similar warm warning color, consistent with the existing `ring-amber-400/80` used for resize clamping (line 124 in TrackListRenderer).
   - Add a thin vertical divider line at the `mediaEndFraction` position to clearly mark where media ends.
2. **Tooltip:** On hover over the overhang zone, show a tooltip: "Dead time — media ends here. Right-click to trim or hold."
3. **Keep it lightweight:** The overlay is a positioned `div` inside the clip element; no new components needed.

## Phase 4: Explicit User Actions for Overhang

### Step 8: Add context menu actions for overhang clips (`src/tools/video-editor/components/TimelineEditor/ClipAction.tsx`)
**Scope:** Medium
1. **In** the existing clip context menu (ClipAction already has a context menu), add two new items when the clip has overhang:
   - **"Trim to media end"** — calls `clampClipToMediaDuration` and applies as an edit. This shortens the clip's timeline span to match the media.
   - **"Hold last frame"** — calls `convertOverhangToHold` and applies as an edit. This keeps the clip's total duration but explicitly marks the tail as a freeze/hold, which removes the overhang warning (since it's now intentional).
2. **These menu items** only appear when `mediaEndFraction !== null` (clip has overhang).
3. **Wire** both actions through the existing `applyEdit` pattern used by other context menu items (delete, split, etc.).

### Step 9: Update tests and validate
**Scope:** Small
1. **Unit tests** for `overhang.ts` (Step 1 & 2 — already planned).
2. **Update** any existing tests in `shot-group-commands` that assert on duration behavior to reflect the new clamping.
3. **Manual smoke test checklist:**
   - Drop a shot with known 2s final video → clip should be 2s, no overhang indicator.
   - Drop a shot where duration resolution fails → clip drops at 5s, then auto-clamps when duration resolves.
   - Switch images to final video → clip clamps to video duration.
   - Manually resize a clip past media end → overhang indicator appears.
   - Right-click overhang → "Trim to media end" works.
   - Right-click overhang → "Hold last frame" works, overhang indicator disappears (now intentional hold).

## Open Design Decisions
- **Hold tail implementation:** Single-clip `holdTail` property vs. splitting into two clips. Single-clip is simpler for the data model but requires renderer support. Two-clip approach uses existing `hold` clip type but complicates shot groups. Recommend starting with single-clip approach and falling back to two-clip if renderer changes are too invasive.
- **Auto-clamp UX:** Should auto-clamping be silent or show a brief toast? CLAUDE.md says errors-only for toasts, so silent is preferred. But the clip visually shrinking could be surprising. Consider a brief animation or subtle highlight when auto-clamping occurs.
