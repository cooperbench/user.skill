## Implementation Plan: Parallel Observe Batches + SKILL.md Fix

### Issue 1: Parallel Observe Batches

**Current flow** (in `orchestrator.py` `_run_codex_pipeline`): For the observe stage, one call to `build_stage_prompt()` produces a single monolithic prompt containing ALL issues. This gets sent to one `run_triage_stage()` Codex subprocess. With 100+ issues, the Codex instance produces shallow analysis.

**Target flow**: Split observe into dimension-group batches. Run them in parallel via `ThreadPoolExecutor` (same pattern as review `execute_batches`). Merge batch outputs into a single observe report. Then proceed with validation and confirmation as before.

#### Step 1: Add `build_observe_batch_prompt()` to `stage_prompts.py`

Create a new function that builds a prompt for a subset of issues by dimension group:

```python
def build_observe_batch_prompt(
    batch_index: int,
    total_batches: int,
    dimension_group: list[str],
    issues_subset: dict[str, dict],
    *,
    repo_root: Path,
) -> str:
```

This function:
- Uses the same `_PREAMBLE` (with `stage="OBSERVE"`)
- Builds issue data from only `issues_subset` (not the full TriageInput)
- Uses the existing `_observe_instructions()` but with a batch-scoped prefix explaining which dimensions this batch covers
- Includes `_CLI_REFERENCE` -- but instructs the batch NOT to record the stage (the orchestrator merges and records)
- Key difference from `build_stage_prompt()`: does NOT call `desloppify plan triage --stage observe --report ...`. Instead, the batch must write its analysis to stdout / output file. The orchestrator collects all outputs.

**Critical design decision**: Observe batch subprocesses should NOT mutate `plan.json`. Instead, each batch writes its analysis to its output file. The orchestrator collects all outputs, merges them, then records the observe stage once with the merged report. This avoids race conditions on `plan.json` writes.

The prompt should instruct: "Write your analysis to stdout. Do NOT run `desloppify plan triage --stage observe`. The orchestrator will merge all batch results and record the stage."

If total issues are small (say, under 20), return a single batch to avoid unnecessary parallelism overhead.

This function:

7. Returns `(success, merged_report)`

The `BatchTask` callables are zero-arg lambdas that call `run_triage_stage()` with the batch-specific prompt, output file, and log file -- exactly the pattern review uses.

### Risks and Mitigations

- **Plan.json race condition**: Mitigated by having observe batches write to output files only, not to plan.json. The orchestrator merges and records once.
- **Batch failure handling**: If any batch fails, the whole observe stage fails (same as review). The user can re-run and confirmed stages are skipped.
- **Small issue counts**: If under ~20 issues, use a single batch to avoid unnecessary overhead. The `group_issues_into_observe_batches()` function handles this.
- **Citation rate across batches**: Each batch only sees its dimension's issues, so it can only cite those. The merge function collects all cited IDs. The validation checks against total issues, which naturally works since each batch contributes citations for its subset.
