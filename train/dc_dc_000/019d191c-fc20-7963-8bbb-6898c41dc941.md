# Migration Plan: Personal Website → React 19 + Vite + TypeScript + Tailwind CSS + Supabase

## Current State Summary

- **Server**: Custom Node.js HTTP server (`server.js`, 1254 lines) — serves SSR HTML, handles redirects, parses markdown posts
- **Frontend**: Vanilla JS (`script.js`, ~2000 lines) + vanilla CSS (`styles.css`, ~4100 lines)
- **Content**: 6 markdown blog posts with YAML frontmatter in `/posts/`
- **External services**: Supabase (weight-tracking chart), Google Fonts, Feather Icons CDN, YouTube iframe API
- **Interactive features**: 20 distinct interactive systems (see Phase 3 inventory)
- **Deployment**: Railway (NIXPACKS builder, `node server.js`)

## Architecture Decision: Vite SSR + Express

Since SSR is required for blog SEO and the site already runs on Railway as a Node server, the new stack will be:

- **Vite SSR** with two distinct server-side files:
  - `src/server.ts` — the Express HTTP server (the long-running process Railway starts). Handles redirects, static assets, and calls the render function for SSR.
  - `src/entry-server.tsx` — the React SSR render function. Exported and imported by `server.ts`; not run directly.
  - `src/entry-client.tsx` — the client hydration entry point.
- **React Router v6** for both server and client routing
- **Express** handles HTTP redirects (301s), serves static assets, and returns proper 404 status codes
- **Supabase** stores blog posts (fetched server-side via anon key + RLS for SSR) and weight measurements (fetched client-side via anon key + RLS)
- **Railway** runs `node dist/server.js` (the compiled Express server)

### File Compilation Map
| Source | Compiled Output | Role |
|--------|----------------|------|
| `src/server.ts` | `dist/server.js` | Express HTTP server — **Railway starts this** |
| `src/entry-server.tsx` | `dist/entry-server.js` | React SSR render function — imported by server.js |
| `src/entry-client.tsx` | `dist/client/assets/*.js` | Client hydration bundle |

## Phase 1: Supabase Blog Migration (Day 1–2)

### 1.1 — Design `posts` Table Schema
```sql
CREATE TABLE posts (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  slug TEXT UNIQUE NOT NULL,
  title TEXT NOT NULL,
  date TIMESTAMPTZ NOT NULL,
  draft BOOLEAN DEFAULT false,
  markdown TEXT NOT NULL,
  excerpt TEXT,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- RLS: public read for published posts, no client writes
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Public read published posts"
  ON posts FOR SELECT
  USING (draft = false);
```

### 1.2 — Write Migration Script
- Create `scripts/migrate-posts-to-supabase.ts`:
  - Read all 6 markdown files from `/posts/`
  - Parse YAML frontmatter (date, draft flag)
  - Extract title from first `#` heading
  - Generate excerpt (first paragraph, ≤30 words)
  - Derive slug from filename
  - Upsert into Supabase `posts` table
- **This script uses the service role key** (one-time admin operation)
- Run once manually; verify all 6 posts appear correctly
- Keep markdown files in repo as backup (gitignored after migration verified)

### 1.3 — Blog Data Fetching Layer
- Create `lib/posts.ts` with typed Supabase queries:
  - `getPosts()`: fetch all published posts ordered by date desc (for `/posts` listing)
  - `getPost(slug)`: fetch single post by slug with prev/next navigation
  - `renderMarkdown(content)`: process markdown with `marked`, including video path normalization and mobile video attributes
- **These functions use the anon key**, not the service role key. The RLS policy on the `posts` table ensures only published (non-draft) posts are returned. This is the correct approach for routine reads — the anon key respects RLS, which is exactly what we want.
- Functions run server-side during SSR for SEO; client receives hydrated HTML + post data as serialized props

### 1.4 — Supabase Client Configuration
- **Single shared client** using anon key (`VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`)
  - Used server-side for SSR post fetching (RLS enforces published-only)
  - Used client-side for weight chart queries (RLS enforces read-only)
- **Service role key** (`SUPABASE_SERVICE_ROLE_KEY`) used **only** in:
  - `scripts/migrate-posts-to-supabase.ts` (one-time migration)
  - Any future admin tooling (not part of the running app)
- The service role key is **never imported in app code** (`src/`), only in `scripts/`

## Phase 5: Supabase Security Hardening (Day 5–6)

### 5.1 — RLS on `measurements` Table
- Enable RLS on `measurements` table
- Create read-only row policy: `SELECT` for `anon` role (all rows readable — the weight chart displays all measurements)
- No `INSERT`/`UPDATE`/`DELETE` policies for `anon` role
- **Column restriction**: RLS operates at the row level and cannot restrict columns. To avoid exposing unexpected columns, the weight chart query will use `.select('withings_timestamp, weight_kg')` instead of `.select('*')`. This is enforced in application code (`WeightsChart.tsx`), not at the database level.

### 5.2 — RLS on `posts` Table
- Already defined in Phase 1.1: public `SELECT` where `draft = false`
- No `INSERT`/`UPDATE`/`DELETE` policies for `anon` role
- Admin writes via service role key in `scripts/` only (not in the running app)

### 5.3 — Credential Management
- **App env vars** (prefixed `VITE_`, available in both server and client bundles):
  - `VITE_SUPABASE_URL`
  - `VITE_SUPABASE_ANON_KEY`
  - These are safe to expose because RLS enforces access control. The anon key is designed to be public — it only grants permissions defined by RLS policies.
- **Admin env var** (used only in `scripts/`, never in `src/`):
  - `SUPABASE_SERVICE_ROLE_KEY` — for migration script and any future admin tooling
  - Not set in Railway (not needed at runtime); used locally only
- Add env vars to Railway project settings (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`)
- Remove hardcoded keys from source code
- Add `.env.example` documenting required vars

### 5.4 — Validate Security
- Confirm anon key cannot read draft posts (query `posts` where `draft = true` returns empty)
- Confirm anon key cannot write to any table (INSERT/UPDATE/DELETE all fail)
- Confirm `.select('withings_timestamp, weight_kg')` is used in `WeightsChart.tsx` (not `*`)
- Confirm `SUPABASE_SERVICE_ROLE_KEY` does not appear anywhere in `src/` (grep check)
- Confirm weight chart still loads and renders correctly under RLS

| Supabase post migration data loss | Keep original markdown files as backup until migration verified |
| RLS breaks weight chart | Test chart against new policies in Supabase dashboard before deploying |
