## Overview

The video editor currently has no undo/redo capability. All mutations flow through `applyTimelineEdit()` and `applyResolvedConfigEdit()` in `useTimelineSave.ts`, which immediately update state and schedule a debounced save to Supabase. The `commitData()` function is the single chokepoint where all state changes are applied — it updates `dataRef`, calls `setData()`, and triggers `scheduleSave()`.

**Architecture insight:** The `TimelineData` object (defined in `timeline-data.ts:60-73`) contains the full serializable state: `config`, `rows`, `meta`, `clipOrder`, `tracks`, `output`. This is exactly the snapshot we need for undo entries.

**Key constraint:** There are two mutation paths — `applyTimelineEdit` (row/meta level, ~85 call sites across 10 hooks) and `applyResolvedConfigEdit` (resolved config level, used by track management and agent chat). Both funnel through `commitData`. The history system must intercept at the `commitData` level to catch all mutations.

**No existing checkpoint infrastructure:** The `timelines` table stores only current config + config_version. A new table is needed for checkpoints.

## Phase 2: Core Undo/Redo Hook

### Step 4: Create `useTimelineHistory` hook (`src/tools/video-editor/hooks/useTimelineHistory.ts`)
**Scope:** Large — this is the core of the feature
1. **Implement** the hook with this interface:
   ```typescript
   interface UseTimelineHistoryResult {
     undo: () => void;
     redo: () => void;
     canUndo: boolean;
     canRedo: boolean;
     undoStackSize: number;
     redoStackSize: number;
     checkpoints: Checkpoint[];
     jumpToCheckpoint: (id: string) => void;
     createManualCheckpoint: (label?: string) => void;
   }
   ```
2. **Undo stack management:**
   - Maintain `undoStack` and `redoStack` as `useRef<UndoEntry[]>` (in-memory only, not React state — avoid re-renders on every edit).
   - `canUndo`/`canRedo` as derived state (these DO need to be React state for UI updates, but update them only when stack empties/fills).
   - Cap undo stack at 100 entries; drop oldest when exceeded.
   - On push: clear redo stack.

3. **Snapshot capture — intercept `commitData`:**
   - The hook receives `dataRef` (current state before edit) and wraps the save flow.
   - **Key approach:** Instead of wrapping `applyTimelineEdit`, create a `beforeCommit` callback that `commitData` calls before applying the new data. This avoids touching 12+ consumer files.
   - Modify `useTimelineSave.ts` to accept an optional `onBeforeCommit?: (currentData: TimelineData) => void` callback. Inside `commitData` (`useTimelineSave.ts:176`), call `onBeforeCommit(dataRef.current)` before updating state — but only when `save !== false` (skip for server reloads/polling).
   - `useTimelineHistory` provides this callback and pushes a snapshot of the current state onto the undo stack.

4. **Transaction collapsing for drags/rapid edits:**
   - Add optional `transactionId` to the `commitData` options: `{ save?: boolean; transactionId?: string }`.
   - In `useClipDrag.ts`, the drag session already has a clear start/end lifecycle. Pass a stable transaction ID (e.g., `drag-${session.id}`) for all `applyTimelineEdit` calls during a drag.
   - In the `onBeforeCommit` callback: if the new entry's `transactionId` matches the top of the undo stack, skip pushing (the pre-drag snapshot is already captured).
   - For rapid property edits (e.g., slider changes in PropertiesPanel), use a debounce approach: if two edits arrive within 300ms and have no transaction ID, collapse them (keep the older snapshot, discard the intermediate one).

5. **Undo/redo execution:**
   - `undo()`: Pop from undo stack, push current state onto redo stack, call `commitData` with `{ save: true }` to apply the snapshot and trigger a save. Use a flag (`isUndoRedo.current = true`) to skip pushing onto undo stack during the commit.
   - `redo()`: Mirror of undo — pop from redo, push current to undo, apply.
   - **Restoring state from snapshot:** Build a full `TimelineData` from the snapshot using `buildDataFromCurrentRegistry()` (from `timeline-save-utils.ts`), keeping the current `registry` and `resolvedConfig` URLs intact. The config is the source of truth; rows/meta are derivable but stored for speed.

6. **Checkpoint triggers (activity-aware):**
   - Track `lastEditTimestamp` (ref) and `editsSinceCheckpoint` (ref).
   - **Session boundary:** In `onBeforeCommit`, check if `Date.now() - lastEditTimestamp > 5 * 60 * 1000`. If so, save a checkpoint of the *current* state (pre-edit) with trigger `'session_boundary'`.
   - **Edit-distance cap:** Increment `editsSinceCheckpoint` on each commit. At 30, auto-checkpoint with trigger `'edit_distance'`.
   - **Semantic triggers:** Add a `semantic` option to `commitData` options. Pass `semantic: true` from `handleDeleteClips`, `handleRemoveTrack`, and any "clear timeline" action. The history hook creates a checkpoint before these ops.
   - **Manual:** Exposed as `createManualCheckpoint()`.

7. **Checkpoint persistence:**
   - Call `provider.saveCheckpoint()` asynchronously (fire-and-forget, don't block edits).
   - Load checkpoints on mount via `provider.loadCheckpoints()`. Store in state for the UI.
   - Prune checkpoints >24h on load. Cap at 30 — provider deletes oldest on insert.

4. **Checkpoint creation:** Leave editor idle >5 min → make edit → verify session boundary checkpoint appears in history dropdown. Make 30+ rapid edits → verify edit-distance checkpoint.
5. **Checkpoint restore:** Jump to a previous checkpoint → verify timeline fully restores. Verify undo stack is cleared after checkpoint jump.
6. **Save status:** After undo, verify save status goes to 'dirty' → 'saving' → 'saved'. Undo should trigger a real save to Supabase.
7. **Edge cases:** Undo when stack is empty (button should be disabled). Undo after page reload (stack is empty, checkpoints persist). Selection state after undo.

## Risk Notes
- **Snapshot size:** A TimelineConfig with 50 clips is ~10-20KB JSON. 100 undo entries ≈ 1-2MB. Acceptable for in-memory.
- **Registry/resolved URLs:** Undo snapshots store `config` but NOT `registry` or resolved URLs. On undo, we rebuild `TimelineData` from the snapshot config + current registry. This avoids stale signed URLs.
- **Concurrent edits:** If another tab edits the timeline during undo, the existing conflict detection dialog still applies. Undo writes through the normal save path with version checking.

## Overview

The video editor currently has no undo/redo capability. All mutations flow through `applyTimelineEdit()` and `applyResolvedConfigEdit()` in `useTimelineSave.ts`, which immediately update state and schedule a debounced save to Supabase. The `commitData()` function is the single chokepoint where all state changes are applied — it updates `dataRef`, calls `setData()`, and triggers `scheduleSave()`.

**Architecture insight:** The `TimelineData` object (defined in `timeline-data.ts:60-73`) contains the full serializable state: `config`, `rows`, `meta`, `clipOrder`, `tracks`, `output`. This is exactly the snapshot we need for undo entries.

**Key constraint:** There are two mutation paths — `applyTimelineEdit` (row/meta level, ~85 call sites across 10 hooks) and `applyResolvedConfigEdit` (resolved config level, used by track management and agent chat). Both funnel through `commitData`. The history system must intercept at the `commitData` level to catch all mutations.

**Pre-mutation snapshot problem:** Some callers (asset drops, external drops, text tool drops) mutate `dataRef.current.tracks` and `dataRef.current.rows` in-place *before* calling `applyTimelineEdit` (`useAssetManagement.ts:164-165`, `useExternalDrop.ts:171-172`, `useExternalDrop.ts:197-202`). A snapshot taken inside `commitData` would already reflect these mutations. The fix: snapshot at the `applyTimelineEdit`/`applyResolvedConfigEdit` level (before any caller-side mutations are visible), not at `commitData`.

**No existing checkpoint infrastructure:** The `timelines` table stores only current config + config_version. A new table is needed for checkpoints.

### Settled decisions (from prior review)
- Intercept at `commitData` level for the `onBeforeCommit` callback, BUT use `config`-based snapshots (derived from the last committed config, not `dataRef.current`) to avoid the pre-mutation problem.
- Undo stack is in-memory refs; checkpoints are Supabase-persisted. `canUndo`/`canRedo` are React state updated only on empty/non-empty transitions.
- `jumpToCheckpoint` clears the undo/redo stacks entirely.
- Agent chat edits via `applyResolvedConfigEdit` participate in undo.
- Client-side checkpoint cleanup (DELETE on load).

   - `jumpToCheckpoint(id)`: Find checkpoint in local state, rebuild `TimelineData` from checkpoint config, call `commitData(rebuilt, { save: true, skipHistory: true })`, clear both undo/redo stacks.
