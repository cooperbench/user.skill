Option 1 — registering the codec on pool init — is the well-engineered choice, and not by a small margin. Reasons:

1. **It fixes a latent read-side bug too.** asyncpg's default `jsonb` codec returns `str` on read, not `dict`. Yet `app/services/pacer.py:79` types `media_analysis: Mapping[str, Any]` and `app/services/tools/common.py` (via `media_analysis_text`) treats it as a dict. Either those reads are silently broken in prod, or rows happen to be `NULL` in practice. Registering a codec makes encode *and* decode symmetric — both sides become real dicts, matching the existing type annotations.

2. **Single point of convention.** Every current and future call site that touches `jsonb` Just Works. No new contributor has to know "wrap in `json.dumps` here, but the column read is already a string". The asyncpg docs explicitly recommend this pattern for jsonb columns.

Three answers, all from `app/services/vision.py`:

**1. Why doesn't it include all the text?**

The vision prompt (`MEDIA_EXPLAIN_PROMPT`, vision.py:16-23) explicitly asks for "a compact, queryable note" — a *description*, not a transcript. It tells the model to mention "screenshots/text" as part of the description, but does not ask for verbatim OCR. So a WhatsApp screenshot becomes "a conversation between you and [REDACTED], shows some back-and-forth" instead of the actual lines. Also `settings.vision_detail` controls input resolution — if it's `"low"`, OpenAI downsamples to 512×512 and fine-print text gets lost regardless of prompt.

If you want full text, the cleanest fix is to add an OCR pass (cheap: a second prompt at `detail=high` asking for verbatim transcription, stored alongside the description in `media_analysis`). Or just rewrite the prompt to demand verbatim transcription of any visible text, which would likely be ~80% as good without a second call.

**2. Why did it reply twice — once not knowing, once knowing?**

Race condition. When you send text + image in one Discord message, both items get ingested. The text item triggers an agentic turn immediately. The image item runs through `vision.handle_image` which has to download bytes + call OpenAI — takes a few seconds. The first agent turn fires *before* `media_analysis` is populated, so the LLM sees only the text and (correctly) says "no image came through". When `vision.handle_image` finishes, it calls `coalescer.add(..., source="media")` (vision.py:160-161), which enqueues a second turn. That second turn sees the now-populated `media_analysis` and replies "the image came through this time".

It's not the agent forgetting or contradicting itself — the two replies came from two separate turns with different snapshots of context.

**3. Does it store a full transcription?**

No. Only the structured `analysis` dict (vision.py:39-59): `{kind, provider, model, detail, explanation, description}`. The `explanation`/`description` fields hold whatever the prompt produced — a summary, not a transcript. Raw bytes go to Supabase storage; nothing in Postgres holds verbatim image text unless the description happened to include it.
