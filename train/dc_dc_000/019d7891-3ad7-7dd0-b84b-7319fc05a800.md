        ### Task Summary
        Clean up the parameter structures, naming, and data flow for travel orchestrator and individual travel segment tasks across reigh-app (task creation), reigh-worker (GPU execution), and reigh-app complete_task (completion handling). The current system has massive flat payloads with heavy duplication (orchestrator_details copied wholesale into every segment, individual_segment_params re-duplicating top-level fields), dead parameters (openai_api_key, params_json_str, regenerate_anchors, show_input_images), contract fields that are set but never consumed (generation_routing, sibling_lookup, segment_regen_mode), inconsistent naming (num_frames vs segment_frames_target, full_orchestrator_payload vs orchestrator_details), and a complex 3-tier parameter precedence (individual_params > segment_params > orchestrator_details) that makes it very hard to understand which value actually wins.         ### Suggested Approach
        This is a large structural refactor across 3 repos. Approach in phases:

**Phase 1: Audit and document the canonical param set.** For each task type (travel_orchestrator, travel_segment, individual_travel_segment), trace every field from creation → execution → completion. Build a spreadsheet of: field name, who sets it, who reads it, whether it's dead. This investigation work is largely done in this brief.

**Phase 2: Remove dead params.** Start with the low-risk wins: remove openai_api_key, params_json_str, regenerate_anchors from TravelBetweenImagesTaskInput. Remove show_input_images if truly unused. Remove the full_orchestrator_payload legacy alias. Remove unused contract fields (or mark them explicitly optional/deprecated).

**Phase 3: Flatten the duplication.** The biggest structural issue is triple-nesting: params have fields at top level, inside orchestrator_details, AND inside individual_segment_params. The approach should be:
- Define a clean SegmentPayload type with explicit fields (no more ad-hoc dicts)
- Stop embedding the full orchestrator_payload in every segment - only include the specific fields the segment handler actually reads
- Eliminate individual_segment_params as a separate namespace - merge its unique fields (phase_config, segment_loras, per-pair overrides) into the segment payload directly
- In the worker, replace the complex _get_param 3-source cascade with direct field access on the clean payload

**Phase 4: Normalize naming.** Pick one name per concept: num_frames (not segment_frames_target), model_name (not model), seed (not seed_to_use/seed_base). Update all three repos consistently.

**Phase 5: Make LTX vs Wan explicit.** Consider a discriminated union approach where the payload includes model_family: "ltx" | "wan" and model-specific params are in a typed sub-object rather than a flat bag where half the fields don't apply.

**Phase 6: Clean up orchestrator_utils.py.** The 30+ field extraction is a smell - most extracted fields are never used. Remove the bulk extraction, have the segment handler read only what it needs.

**Execution strategy:** Each phase should be a separate PR to minimize risk. Phase 2 (dead param removal) is safest to start with. Phase 3 (flattening) is the highest-impact but highest-risk change. All changes need end-to-end testing with both LTX and Wan models, both orchestrator-created and frontend-created segments.
