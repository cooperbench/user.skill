# Implementation Plan: Message Queue for Timeline Agent Chat

## Overview
Currently `AgentChat.tsx:675` disables the input while `isProcessing` (agent turn in flight) or `sendMessage.isPending` is true. The goal is to keep the input enabled, let the user submit additional messages, and stack them above the input as a local client-side queue with delete + reorder controls. When the active turn finishes, the next queued item auto-sends with the attachments captured at queue time. Scope is purely client-side state inside `AgentChat.tsx` (no hook/server changes); `AgentChatMessage.tsx` is untouched.

Key existing anchors:
- `handleSend` at `AgentChat.tsx:387` — sending logic, including building `attachments` from `clips` (`AgentChat.tsx:391-404`).
- `sendingRef` at `AgentChat.tsx:386` — guards re-entry.
- Input disabled flags at `AgentChat.tsx:675`.
- Input bar block (where queued items will render above the existing attachment strip) at `AgentChat.tsx:614-720`.
- Drain trigger surface: `isProcessing` (`AgentChat.tsx:184`), `sendMessage.isPending`, `optimisticMessage` clearing effect (`AgentChat.tsx:376-384`).

## Main Phase

### Step 1: Audit current send path (`AgentChat.tsx`)
**Scope:** Small
1. **Confirm** the gating that must change: input `disabled={... || isProcessing || ...}` (`AgentChat.tsx:675`) and the send button `disabled={... || isProcessing || sendMessage.isPending}` (`AgentChat.tsx:715`).
2. **Confirm** completion signal: `sendMessage.mutateAsync` resolving (`AgentChat.tsx:410`) plus `isProcessing` flipping false when `activeSession.data.status` leaves `processing|continue` (`AgentChat.tsx:184`). The drain must wait for BOTH the mutation to resolve AND the agent's turn to actually finish (otherwise the next message would be sent mid-turn and rejected/queued server-side).

### Step 2: Add queue state and types (`AgentChat.tsx`)
**Scope:** Small
1. **Add** a local type `QueuedMessage = { id: string; text: string; attachments: AgentChatAttachmentPreviewItem[] }` near the top of the component file (or alongside `RenderedTurn`).
2. **Add** `const [queue, setQueue] = useState<QueuedMessage[]>([]);` in the component, near `draft`/`optimisticMessage` (`AgentChat.tsx:139-141`).
3. **Add** an id helper: prefer `crypto.randomUUID()` (already used elsewhere in the app — fall back to `${Date.now()}-${Math.random()}` if unavailable).

### Step 3: Refactor `handleSend` to support queueing (`AgentChat.tsx:387-417`)
**Scope:** Medium
1. **Extract** the actual network-send logic into an inner helper `sendNow(text: string, attachments: QueuedMessage['attachments'])` that does `setOptimisticMessage`, `sendingRef.current = true`, `await sendMessage.mutateAsync(...)`, `clearGallerySelection()` on success, and resets `sendingRef` in `finally`. This mirrors current behavior at `AgentChat.tsx:407-416`.
2. **Rewrite** `handleSend(rawText?)`:
   - Compute `text` and the `attachments` snapshot from current `clips` exactly as today (`AgentChat.tsx:391-404`).
   - If `rawText === undefined`, clear `draft`.
   - **If currently busy** (`sendingRef.current || isProcessing || sendMessage.isPending || queue.length > 0`), append `{ id, text, attachments }` to `queue` and return. (Also enqueue if there are already queued items, to preserve order.)
   - **Else** call `sendNow(text, attachments)` directly.
3. **Important:** Removing the input's `disabled` (Step 6) means the user can press Enter while a send is in flight; the busy check above ensures those go to the queue rather than racing.
4. **Keep** voice transcription path working — it calls `handleSend(text)` (`AgentChat.tsx:174`), which will now also queue if busy. That's the desired behavior.

### Step 4: Auto-drain queue when idle (`AgentChat.tsx`)
**Scope:** Small
1. **Add** an effect that watches `[queue, isProcessing, sendMessage.isPending, optimisticMessage, activeSessionId, timelineId]`:
   ```ts
   useEffect(() => {
     if (sendingRef.current) return;
     if (isProcessing || sendMessage.isPending || optimisticMessage) return;
     if (queue.length === 0) return;
     if (!activeSessionId || !timelineId) return;
     const [next, ...rest] = queue;
     setQueue(rest);
     void sendNow(next.text, next.attachments);
   }, [queue, isProcessing, sendMessage.isPending, optimisticMessage, activeSessionId, timelineId]);
   ```
2. **Rationale for guarding on `optimisticMessage`:** It's cleared only when the matching real turn arrives (`AgentChat.tsx:376-384`), so it's a reliable "the previous send is fully reflected in turn history" signal that pairs with `!isProcessing`. Without it we could fire the next send during the small gap between mutation resolve and the user turn appearing in `activeSession.data.turns`.
3. **`sendNow` must be stable** — wrap it in `useCallback` with deps `[sendMessage, clearGallerySelection]` (and accept `text`/`attachments` as args, so it does not depend on `clips`/`draft`). Otherwise the effect will refire spuriously.

### Step 5: Render the queued-messages stack (`AgentChat.tsx`, input bar region ~`AgentChat.tsx:614`)
**Scope:** Medium
1. **Insert** a new block immediately above the existing `clips.length > 0` attachment strip (`AgentChat.tsx:615-628`), so the visual order from top to bottom is: queued messages → current selection strip → voice/error banners → input row.
2. **Render** `queue.map((item, index) => …)` as a vertical stack of pill cards. Each card shows:
   - The `text` (truncate to 2-3 lines with `line-clamp-2`).
   - A small attachment count badge if `item.attachments.length > 0` (e.g. "📎 3"). Don't render the full attachment thumbnail strip — keep it compact since these can stack.
   - **Up arrow** button (`ChevronUp` from lucide-react), disabled when `index === 0`.
   - **Down arrow** button (`ChevronDown`), disabled when `index === queue.length - 1`.
   - **Delete** button (`X`).
3. **Reorder handlers:** `moveUp(index)` and `moveDown(index)` swap adjacent items via `setQueue(prev => { const next = [...prev]; [next[i-1], next[i]] = [next[i], next[i-1]]; return next; })`. **Critical:** never allow moving index 0 up — that slot is the next-to-send and could race with the drain effect mid-swap.
4. **Delete handler:** `setQueue(prev => prev.filter(q => q.id !== id))`.
5. **Styling:** match the existing muted look used for the attachments strip (`bg-muted/50 rounded-lg px-3 py-2 text-xs`), with the row layout `flex items-center gap-2`. Keep within the input panel padding so it doesn't expand the chat width.

### Step 6: Stop blocking the input while sending (`AgentChat.tsx:667-720`)
**Scope:** Small
1. **Update** input `disabled` (`AgentChat.tsx:675`) to remove `isProcessing`. Keep `!hasTimeline`, `!activeSessionId`, `isCancelled`, `voice.isRecording`, `voice.isProcessing`. Result: typing is allowed during agent processing.
2. **Update** send button `disabled` (`AgentChat.tsx:715`) to remove `isProcessing` and `sendMessage.isPending`. Keep the `!draft.trim()` and other guards. The button should be enabled so the user can enqueue.
3. **Update** placeholder text (`AgentChat.tsx:673`) to add a third state: when busy, show e.g. `'Type to queue next message…'`.
4. **Optional `info`:** consider visually indicating the send button is "queue mode" when busy (e.g., swap `Send` icon for a different one) — defer unless requested.

### Step 7: Edge cases (`AgentChat.tsx`)
**Scope:** Small
1. **Cancel session:** when the user clicks Stop (`AgentChat.tsx:522`), clear the queue: `setQueue([])`. Otherwise queued messages would auto-fire after cancel completes / on next session activity, which is surprising.
2. **New session:** in `handleNewSession` (`AgentChat.tsx:419-426`), also `setQueue([])`. Queue is per-session by intent.
3. **Switching `activeSessionId`** via the existing auto-select effect (`AgentChat.tsx:275-300`): clear queue when `activeSessionId` actually changes. Add an effect: `useEffect(() => { setQueue([]); }, [activeSessionId])`.
4. **Error from `sendMessage`:** the existing error banner (`AgentChat.tsx:661-665`) covers it. The drain effect's guards (`!isProcessing && !sendMessage.isPending`) will naturally allow the next queued item to attempt to send after the error surfaces. **Decision needed (see questions):** do we keep draining after an error or pause? Default assumption: keep draining (matches "minimal scope").

   - **Test:** when `isProcessing` flips to false (and `optimisticMessage` clears), the first queued item triggers `sendMessage.mutateAsync` with the attachments captured at queue time, not current `clips`.
   - **Test:** delete and reorder controls update the rendered list as expected.
2. **Run** the focused suite: `npm test -- AgentChat` (or repo's jest/vitest equivalent — confirm via `package.json`).
