        # Implementation Plan: Video Editor Timeline Drag System Redesign

## Overview

The video editor timeline has accumulated three core architectural debts:

1. **Two competing drag systems** — `useClipDrag.ts` (449 LOC, pointer-based) and parts of `useTimelineEditing.ts` (963 LOC) both imperatively create DOM indicator elements. They share mutable state via `actionDragStateRef` with no clear ownership boundary.
2. **Half-used library** — `@xzdarcy/react-timeline-editor` provides drag callbacks (`onActionMove*`), but `useClipDrag` captures pointer events before the library sees them. The library callbacks exist only to maintain `actionDragStateRef` and return `false` during cross-track drags — they're coordination glue, not real delegation.
3. **God hook** — `useTimelineEditing.ts` mixes 6 concerns: library drag callbacks, resize tracking, timeline sync, external HTML5 drag-drop, asset management/upload, and clip editing commands.

### Key files
| File | LOC | Role |
|------|-----|------|
| `src/tools/video-editor/hooks/useTimelineEditing.ts` | 963 | God hook — 6 concerns |
| `src/tools/video-editor/hooks/useClipDrag.ts` | 449 | Pointer-based cross-track drag |
| `src/tools/video-editor/hooks/useTimelineData.ts` | ~200 | Data management, creates `actionDragStateRef` |

### Constraints
- The library is used for: time-scale rendering, virtualized grid layout, cursor/playhead, action resize callbacks. These must continue working.
- The library's drag callbacks (`onActionMove*`) are only needed as coordination glue for `useClipDrag`. If we fully own clip movement, these become dead code.
- Both indicator systems create the same 5-element structure (row, line, ghost, ghostLabel, label) with the same CSS classes.
- `actionDragStateRef` is written by both `useTimelineEditing` (library callbacks) and `useClipDrag` (pointer handler), with no synchronization.

## Phase 1: Unified Drop Indicators (React Portal)

### Step 1: Create `<DropIndicator>` portal component
**Scope:** Medium
1. **Create** `src/tools/video-editor/components/TimelineEditor/DropIndicator.tsx` — a React component that renders via `createPortal` to `document.body`.
2. **Props:** `{ visible: boolean; position: DropIndicatorPosition | null; reject?: boolean }` where `DropIndicatorPosition` contains `{ rowTop, rowHeight, rowLeft, rowWidth, lineLeft, lineTop, lineHeight, ghostLeft, ghostTop, ghostWidth, ghostHeight, ghostLabel, label, isNewTrack }`.
3. **Render** the same 5 elements (row highlight, position line, ghost outline, ghost label, track label) currently created imperatively, using the same CSS classes from `timeline-overrides.css`.
4. **Verify** the portal renders and is styled correctly by temporarily mounting it from `TimelineEditor.tsx` with hardcoded position values.

### Step 2: Create `useDragIndicatorState` hook
**Scope:** Small
1. **Create** `src/tools/video-editor/hooks/useDragIndicatorState.ts` — a thin hook that exposes `{ indicatorPosition, showIndicator, hideIndicator, updateIndicator }`.
2. **State:** Single `useState<DropIndicatorPosition | null>(null)`.
3. **This becomes the single source of truth** for indicator visibility and position, replacing the 5-element imperative DOM manipulation in both `useClipDrag.ts:93-133` and `useTimelineEditing.ts:156-205`.

### Step 3: Wire `<DropIndicator>` into `TimelineEditor.tsx`
**Scope:** Small
1. **Add** `useDragIndicatorState()` call in `TimelineEditorComponent` (`TimelineEditor.tsx:12`).
2. **Render** `<DropIndicator>` below the `<Timeline>` component, driven by the hook's state.
3. **Pass** `showIndicator`/`hideIndicator`/`updateIndicator` into both `useClipDrag` and the external drag handlers via context or props.

## Phase 2: Migrate Drag Systems to Declarative Indicators

### Step 4: Migrate `useClipDrag` to declarative indicators
**Scope:** Medium
1. **Replace** `ensureIndicator()` / `clearDropIndicators()` / `updateDropTarget()` (`useClipDrag.ts:93-281`) with calls to `updateIndicator(position)` and `hideIndicator()`.
2. **Keep** the floating ghost clone (`createFloatingGhost`, line 196) — this is the dragged-clip visual and is distinct from the drop indicator. It stays imperative since it's a transient clone of a specific DOM element.
3. **Remove** `DropIndicatorEls` interface and all indicator element references from `DragSession`.
4. **Test:** Drag a clip horizontally and cross-track — indicators should appear/disappear correctly.

### Step 5: Migrate external HTML5 drag to declarative indicators
**Scope:** Medium
1. **Replace** `ensureDropIndicator()` / `clearDropIndicator()` and the RAF-throttled indicator update (`useTimelineEditing.ts:156-205, 598-648`) with calls to `updateIndicator(position)` and `hideIndicator()`.

3. **Remove** `dropIndicatorRef` from `useTimelineEditing`.

## Phase 3: Resolve Library vs. Custom Drag Ownership

### Step 6: Audit library callback necessity
**Scope:** Small — research only
1. **Trace** what happens when `useClipDrag` captures the pointer (`setPointerCapture` at `useClipDrag.ts:322`): does the library still fire `onActionMoveStart`? Verify with a console.log.
2. **Trace** what `onActionMoving` returning `false` actually prevents — the library likely applies row updates via `onChange`, and `false` suppresses that.
3. **Document** which library features we depend on (resize, time-scale, virtualization, cursor) vs. which we override (move/drag).

### Step 7: Make `useClipDrag` the sole owner of clip movement
**Scope:** Medium
1. **Remove** `onActionMoveStart`, `onActionMoving`, `onActionMoveEnd` from `useTimelineEditing.ts` (lines 245-282). These only existed to populate `actionDragStateRef` for `useClipDrag` to read.
2. **Move** `actionDragStateRef` management entirely into `useClipDrag` — it already writes initial/latest values during its drag session (`useClipDrag.ts:304, 331-336`).
3. **Remove** the `onActionMoveStart`/`onActionMoving`/`onActionMoveEnd` props from the `<Timeline>` component in `TimelineEditor.tsx:202-204`.
4. **Verify** the library's internal drag handling is fully suppressed by `useClipDrag`'s pointer capture, so removing these callbacks doesn't break anything.
5. **Keep** `onChange` callback — it's used for same-row horizontal moves that don't go through cross-track path.

### Step 8: Simplify `actionDragStateRef`
**Scope:** Small
1. **Change** `actionDragStateRef` from `Record<string, ActionDragState>` to a single `ActionDragState | null` — only one clip can be dragged at a time.
2. **Remove** from `TimelineEditorContextValue` — it's now internal to `useClipDrag`.
3. **Update** `clearActionDragState` to be internal to `useClipDrag` rather than threaded through context.

## Overview

The video editor timeline has three core architectural debts:

1. **Two competing drag systems** — `useClipDrag.ts` (449 LOC, pointer-based) and parts of `useTimelineEditing.ts` (963 LOC) both imperatively create DOM indicator elements. They share mutable state via `actionDragStateRef` with no clear ownership boundary.
2. **Half-used library** — `@xzdarcy/react-timeline-editor` uses interact.js internally for drag handling. We capture pointer events before the library sees them, override its move callbacks, but still wire `onActionMove*` callbacks as coordination glue. The library and `useClipDrag` both attempt to own clip movement.
3. **God hook** — `useTimelineEditing.ts` mixes 6 concerns: library drag callbacks, resize tracking, timeline sync, external HTML5 drag-drop, asset management/upload, and clip editing commands.

### Constraints
- The library handles: time-scale rendering, virtualized grid layout, cursor/playhead, and action resize (via interact.js). These must continue working.
- The library uses interact.js for drag/resize — `setPointerCapture` does not reliably prevent interact.js from receiving events since it manages its own internal pointer listeners.
- Both indicator systems create the same 5-element structure (row, line, ghost, ghostLabel, label) with the same CSS classes.
- Both drag paths also imperatively toggle `drop-target-new-track` on the library's `editArea` element — this must be unified alongside the portal indicators.

### Library drag mechanism (verified from source)
The library's `edit_action.tsx` uses per-action `movable` (default `true`) and `flexible` (default `true`) flags:
- `enableDragging={!disableDrag && movable}` — controls interact.js drag
- `enableResizing={!disableDrag && flexible}` — controls interact.js resize
- `handleDragEnd` directly mutates `editorData` and calls `setEditorData()` → triggers `onChange`
- `handleResizeEnd` does the same for resize
- `onActionMoving` returning `false` prevents visual update but doesn't prevent `handleDragEnd` from firing

**Key insight:** Setting `movable: false` on actions disables library drag at the source while preserving resize (`flexible` is independent). This is cleaner than pointer capture coordination.

### Library drag mechanism (verified from source)
The library's `edit_action.tsx` uses per-action `movable` (default `true`) and `flexible` (default `true`) flags:
