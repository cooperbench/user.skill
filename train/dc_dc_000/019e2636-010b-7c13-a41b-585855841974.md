> AGENT

**Strongest Approval**

The plan correctly makes `pack.yaml` the owning abstraction and puts validation before install, discovery, runtime execution, and scaffolding. That is the right spine. The strongest technical move is this invariant:

`component id -> owning pack -> validated manifest -> runtime entrypoint`

That gives Astrid one resolution model instead of folder conventions, recursive scans, and special-case author paths. If enforced strictly, it will age well because packs become the namespace, trust, discovery, and runtime boundary rather than a cosmetic directory.

**Biggest Concerns Ranked**

1. `content` roots plus generated inventory is cleaner than manual `provides`.  
Manual `provides` duplicates information from component manifests and will drift. It also creates ambiguity: is a component public because it is listed, because it exists under a content root, or because its manifest says so? Pick one. The durable model is: declared roots define search space, component manifests define public components, validation generates inventory.

2. The schema boundary is under-specified.  
The plan says schemas should define runtime entrypoints, inputs, outputs, docs, and metadata, but it does not separate stable external contract from internal implementation hints. Avoid leaking Astrid internals like Python module import mechanics into user-facing schema names. The manifest should declare semantic runtime type plus entrypoint path, not encode today’s loader architecture.

3. Pack/component namespace rules need to be hard invariants, not validation niceties.  
Executors and orchestrators are already qualified as `<pack>.<name>`, while elements are shown as `effects/project-title-card`. That asymmetry will hurt discovery, override rules, inspect output, and agent reasoning. Elements also need pack identity in their public id, even if CLI display has a shorthand.

4. Runtime dependencies are a trap if treated as install metadata too early.  
Listing Python/npm/system dependencies is useful, but `packs install` must not imply environment mutation until there is an environment model. Otherwise pack install, validation, and runtime provisioning become tangled. Keep dependency declarations informational plus validate shape in v1.

5. External pack execution fights Astrid’s current source-tree assumptions more than the roadmap admits.  
Installed packs under `~/.astrid/packs` need import isolation, asset resolution, relative path semantics, and generated Remotion registry behavior. Elements are especially load-bearing because TypeScript compilation and registry generation currently assume local source layout. This deserves an explicit “pack resource resolver” abstraction, not just manifest runtime resolution.

**Concrete Changes**

1. Delete manual `provides` from v1. Replace with generated `inventory.lock.json` or inspect-time generated inventory from declared roots. If a component should not be public, mark `public: false` in its manifest or put it outside declared roots.

2. Define hard ids:
`pack.id = my_project`; executor/orchestrator ids must be `my_project.slug`; element ids should be `my_project.effects.project-title-card` or equivalent fully-qualified form. Shorthands can exist only in CLI display.

3. Add a `visibility` and `kind` invariant to component manifests. Discovery should only expose manifests under declared roots with `visibility: public` or default-public semantics explicitly documented.

4. Introduce a `PackResolver` abstraction in the plan: resolves pack root, component root, docs, schemas, runtime files, examples, and asset paths. Runtime resolution should consume this instead of raw filesystem assumptions.

5. Split manifest schema into stable contract fields and runtime adapter fields. For example: `runtime.type: python-cli`, `runtime.entrypoint: run.py`, `runtime.callable: main` if needed. Avoid names like `runtime_module` in the external contract.

6. Move element compilation/registry implications earlier. Sprint 2 or 3 should prove an installed pack element can be discovered without compiling, and Sprint 4/7 should prove it can render.

7. Make dependency provisioning explicitly out of contract for v1: validate declarations, show them in inspect/agent-index, never install them automatically.
