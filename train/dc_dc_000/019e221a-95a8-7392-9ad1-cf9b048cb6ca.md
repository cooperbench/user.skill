# The situation
During a 2-hour rollout window, the orchestrator spawned 73 GPU workers; 70 were killed before producing useful work. 1 worker rendered all 6 required outputs. Productive utilisation: 4%.

The postmortem claims THREE structural issues:

1. **Issue 1 — RunPod `spawn_failed` retried with no backoff.** 55 of 73 deaths were RunPod refusing to allocate a pod; the orchestrator just keeps asking every 30s. Fix shape: per-pool exponential backoff with a consecutive-failure counter, optionally surfaced through the existing `pause_scaling` table.

2. **Issue 2 — `_handle_early_termination` uses `task_counts.queued == 0` as its kill gate.** This is a snapshot signal answering a durable question. During brief windows where the single productive worker had just claimed a segment, `queued` momentarily dropped to 0, early-term fired, the spawning replacement got killed, the next cycle scaled up again. Fix shape: replace the snapshot gate with a more durable "capacity intent" signal — track desired across cycles; or use `total_tasks` (queued + in-progress); or extend `spawning_grace_period_sec` past one cycle.

3. **Issue 3 — Asymmetric `current_capacity` between phases.** Early-term computes `current_capacity = active + spawning`; scale-up logs `current: 1, desired: 2` in the very same cycle where a spawning worker exists. The per-cycle decision object is computed once at top-of-cycle, then early-term kills a worker, then scale-up consults a now-stale view of the world. Fix shape: re-read worker states between phases, or collapse early-term and scale-up into one symmetric controller.

The postmortem's recommendation: write one sprint brief targeting Issues 2 and 3 together (they share a fix surface — unifying capacity accounting and the gate semantics) and a smaller separate follow-up for Issue 1. > AGENT

The postmortem is broadly right about the bug class, but wrong about the most important mechanism.

The real problem is not “stale state between phases.” In [control_loop.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker-orchestrator-fix-contract/gpu_orchestrator/control_loop.py:109), scaling is calculated after `_handle_early_termination`, and early termination returns a filtered `worker_states` list. So the log sequence:

`Early termination: 2 > 1` then `SCALING UP current: 1, desired: 2`

is not proof that scale-up used a stale pre-kill snapshot. It is proof that the loop has two incompatible controllers:

- `_handle_early_termination` computes `early_desired` using total tasks and `scale_down_multiplier`.
- `calculate_scaling_decision_pure` computes desired using queued coverage plus busy-worker buffer.
- One phase kills to desired=1; a later phase spawns to desired=2.

That is worse than the postmortem says. “Re-read worker states between phases” is the wrong fix. It may clean up promotion/DB mutation drift from `_handle_spawning_workers`, but it does not solve the contradiction. The bug is semantic, not freshness.

Issue 1 is real: RunPod `spawn_failed` without per-pool backoff is irresponsible. It turns external capacity pressure into database churn and API spam.

Issue 2 is real: `queued == 0` is a bad kill gate. It asks a momentary queue snapshot to answer whether an already-authorized spawn is still justified. That is exactly how you get oscillation during workflows where one active worker drains the queue in bursts.

Issue 3 is real as a symptom, but the diagnosis in the doc is too shallow. The deeper issue is duplicate capacity ownership. Early termination should not exist as a separate controller. It is a control-theory mistake here: it consumes the same capacity variable as scale-up, uses a different desired function, and mutates workers before the main reconcile step. You can keep “cancel excess pending capacity” as an action, but only inside one reconciler that computes one desired state and emits one ordered action set.

I would not split Issues 2 and 3. They are the same architectural defect: no durable capacity intent. Issue 1 can land separately as a guardrail, but the strongest implementation folds it into the same model because spawn backoff is part of admission control.

The right fix:

Introduce a durable capacity intent layer, probably `worker_capacity_intents` or `worker_intents`, not just more booleans in `workers`.

Columns:

`id`, `pool`, `route_key`, `desired_capacity`, `reason`, `source_cycle_id`, `observed_queued`, `observed_active`, `observed_busy_workers`, `created_at`, `updated_at`, `valid_until`, `cooldown_until`, `consecutive_spawn_failures`, `last_spawn_failure_at`.

Then make one reconciler own capacity:

- New boundary: `gpu_orchestrator/control/capacity_reconciler.py`
- Keep worker lifecycle probing in `control/phases/lifecycle.py`
- Keep RunPod creation in `control/phases/worker_capacity.py` or `worker_spawner.py`
- Move desired calculation out of `_handle_early_termination` and `calculate_scaling_decision_pure` into one `CapacityPlan`

The state machine should be explicit:

`OBSERVE -> PLAN -> ADMIT -> ACT -> RECORD`

Where `PLAN` computes:

- `desired_capacity`
- `effective_capacity = active + spawning + admitted_pending`
- `excess_pending_capacity`
- `spawn_allowed_after`
- `actions = spawn | cancel_pending_spawn | terminate_idle_active | noop`

Rules:

- Never kill/cancel a spawning worker merely because `queued == 0`.
- Cancel spawning only when the current intent has dropped for N cycles or `valid_until` expires.
- Count spawning workers as capacity until they fail, time out, or are explicitly cancelled.
- Apply RunPod backoff before creating worker rows.
- Spawn failures update pool intent/backoff, not just worker termination metadata.
- Scale-down active workers only through idle timeout and min/buffer constraints.
- Delete `_handle_early_termination` as a separate phase. Replace it with `cancel_pending_spawn` emitted by the reconciler.

Also fix the lifecycle freshness issue: `_handle_spawning_workers` mutates DB but does not return updated derived state. The one reconciler should run after lifecycle reconciliation using either a refreshed state read or a returned updated state object. But that is supporting hygiene, not the core fix.

On megaplan: `thoughtful//medium` is underpowered for the fix I’d recommend. Use `premium`, not `super-premium`.

This is production-critical infrastructure with money burn and oscillatory control behavior, but it is not an apex redesign of the whole product. The correct scope is a careful controller refactor with tests around cycle traces, not a grand architecture summit. The brief should require simulation tests for the exact failure mode: queued drops to zero while active work remains, spawning exists, RunPod failures occur, and the controller must not spawn-kill-spawn every 30 seconds.
