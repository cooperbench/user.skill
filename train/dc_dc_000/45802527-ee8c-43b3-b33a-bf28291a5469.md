The first entry uses a sentinel `prev_hash` (e.g., 64 zero hex chars). Each new entry's identity is bound to all prior entries through the chained hash.

3. **Section 2 — Code-like example.** Include exactly one fenced code block (use ```` ```text ```` or ```` ```json ````) showing two consecutive entries. Use this shape (truncated hex like `a1b2...` is fine — keep it short):

   The example must make clear that `entry[2].prev_hash == entry[1].hash`.

4. **Section 3 — What it detects (~50 words).** Tampering with any past entry: changing a byte in entry N changes its hash, which breaks the `prev_hash` reference in entry N+1, cascading forward. A verifier walking the chain recomputes each hash and compares against the next entry's `prev_hash`; any single edit invalidates every subsequent link.

5. **Section 4 — What it does NOT detect (~60 words).** Cover three weaknesses concretely:
   - **Tail truncation:** dropping the last K entries leaves a still-valid prefix; the chain alone cannot tell you entries are missing.
   - **Whole-chain replacement:** an attacker who can rewrite the entire log can produce a fresh, internally consistent chain.
   - **Out-of-band modification with full rewrite:** an attacker who controls storage and can recompute every hash makes the chain re-validate.
   The fix for these is external anchoring: signed checkpoints, witnessed roots, or publishing the head hash somewhere the attacker cannot rewrite.

6. **Section 5 — One concrete use case (~40 words).** Pick exactly one and be specific.
