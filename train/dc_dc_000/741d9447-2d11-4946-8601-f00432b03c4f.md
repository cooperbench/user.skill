        # Implementation Plan: v0.17.0 Verifiability Contracts

## Overview

Megaplan currently has no model of what an executor or reviewer can actually do. Specs with human-only criteria (browser observation, runtime counts) are handed to container agents, which fail at review — wasting a full execute pass. The M0 incident is the canonical example.

This release adds **capability matching**: workers declare what they can verify, criteria declare what they require, and the harness rejects mismatches at plan time. Four guardrails (closed registry, mandatory `requires` on `must` criteria, worker discovery, complementary pre-critique audit) address the failure modes identified in the critique and losses analysis.

**Current state:** v0.16.0. Success criteria in `plan.json`/`revise.json`/`finalize.json` are `{criterion, priority}` objects. Review verdict enum is `pass | fail | waived`. State machine has 9 states, no `awaiting_human_verify`. No capability concept exists anywhere.

**Key files:**
- `megaplan/schemas.py` — JSON schemas for all step outputs
- `megaplan/types.py` — states, TypedDicts, constants
- `megaplan/_core/workflow.py` — state machine transitions

## Phase 2: Core Logic — Audit, Review Changes, CLI

### Step 5: Create verifiability audit module (`megaplan/verifiability.py`)
**Scope:** Medium
1. **Create** `megaplan/verifiability.py` with:
   - `audit_criteria(criteria: list[dict], worker_caps: dict[str, set[str]]) -> list[CriterionAudit]` — pure-Python check: for each criterion, verify `set(criterion.get("requires", [])) ⊆ union_verifies`. Return list of audit results with `{criterion_idx, verdict, rationale, missing_caps}`.
   - `classify_criteria(criteria: list[dict], worker_caps: dict[str, set[str]]) -> tuple[list[dict], list[dict]]` — split into machine-verifiable and human-deferred based on `requires` vs available capabilities.
   - Verdict enum: `machine_verifiable`, `human_only`, `unverifiable_no_worker` (requires caps no configured worker has, including human).
2. **Implement** plan-time validation: `validate_requires(criteria, registry)` checks all `requires` entries are known capability strings, and that `must` criteria have non-empty `requires` (empty only allowed with explicit opt-out — but for migration, empty is allowed with a deprecation warning).

### Step 6: Wire audit into critique phase (`megaplan/handlers.py`, `megaplan/checks.py`)
**Scope:** Medium
1. **Add** `"verifiability"` to the critique flag category enum in `megaplan/schemas.py` (the `critique.json` schema's `flags[].category` enum at `megaplan/schemas.py:205`).
2. **Hook** into `handle_critique` (`megaplan/handlers.py:861`): before the worker call, run `audit_criteria` from Step 5. Inject results as synthetic critique flags with category `verifiability`:
   - `requires` references unknown capability → blocking flag (`severity_hint: "likely-significant"`)
   - `must` criterion with empty `requires` → advisory flag (`severity_hint: "likely-minor"`, deprecation notice)
   - `requires` not satisfiable by any configured worker AND no `human_reviewer` configured → blocking flag ("criterion unreachable: no worker can verify")
   - `requires` satisfiable only by `human_reviewer` → noted flag (`severity_hint: "likely-minor"`, informational, routes to pending-human at review)
3. **These flags** enter the existing gate→revise loop: blocking verifiability flags must be resolved (rewrite criterion, add `requires`, configure a worker) before PROCEED.
