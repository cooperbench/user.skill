**Findings**

1. The Phase 1 trim is not safe as written because `video_source` is doing two jobs at once. In the current worker, the extracted predecessor clip is both the source for SVI latent extraction and the pixel prefix that WGP prepends into the segment output: [task_registry.py#L411](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/tasks/task_registry.py#L411), [any2video.py#L857](/Users/user_c042661f/Documents/Reigh-Worker/Wan2GP/models/wan/any2video.py#L857). Chaining then intentionally keeps the last 4 prefix frames as the overlap for stitching: [chaining.py#L167](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/chaining.py#L167). The stitcher assumes those first 4 frames of the current segment are duplicates of the previous segment’s tail and removes/blends them accordingly: [stitch.py#L639](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/stitch.py#L639). If you change the extracted clip to exclude the predecessor’s last 4 frames, you also change the overlap that gets stitched. That means Phase 1 would make segment N start with predecessor `[-8:-5]`, not the actual final 4 frames. This is the biggest flaw in the plan.

2. Phase 2a looks unnecessary, and its condition is likely wrong for this codepath. SVI2Pro is already patched into a sliding-window model with overlap default 4 in the worker: [task_processor.py#L402](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/queue/task_processor.py#L402). In WGP, that means `reuse_frames` becomes `sliding_window_overlap`, not `0`, whenever this path is active: [wgp.py#L6120](/Users/user_c042661f/Documents/Reigh-Worker/Wan2GP/wgp.py#L6120). Current WGP already requests `return_latent_slice` whenever `reuse_frames > 0`: [wgp.py#L6338](/Users/user_c042661f/Documents/Reigh-Worker/Wan2GP/wgp.py#L6338), and the returned value is already copied into `overlapped_latents` after generation: [wgp.py#L6847](/Users/user_c042661f/Documents/Reigh-Worker/Wan2GP/wgp.py#L6847). So the “force return_latent_slice” patch probably never fires on the path you care about. The export/save part makes sense; the forcing patch does not.

3. The proposed latent upload discovery is too loose. WGP writes outputs into a shared module-level output directory, not a task-specific temp dir: [orchestrator.py#L82](/Users/user_c042661f/Documents/Reigh-Worker/source/models/wgp/orchestrator.py#L82), [orchestrator.py#L271](/Users/user_c042661f/Documents/Reigh-Worker/source/models/wgp/orchestrator.py#L271). So `Path(status.result_path).parent.glob("latent_tail_*.pt")` can easily find stale tensors from other tasks, especially since the filename only contains `seed`. You need a deterministic mapping from the exact video output to the exact latent file.

4. The `custom_settings` transport path is actually fine. Extra task params are preserved by `TaskConfig` instead of stripped: [task.py#L74](/Users/user_c042661f/Documents/Reigh-Worker/source/core/params/task.py#L74), [task.py#L140](/Users/user_c042661f/Documents/Reigh-Worker/source/core/params/task.py#L140). `custom_settings` is explicitly forwarded into WGP params: [wgp_params.py#L238](/Users/user_c042661f/Documents/Reigh-Worker/source/models/wgp/generators/wgp_params.py#L238), [wgp_params.py#L376](/Users/user_c042661f/Documents/Reigh-Worker/source/models/wgp/generators/wgp_params.py#L376). The orchestrator only drops keys not accepted by `generate_video()`: [orchestrator.py#L922](/Users/user_c042661f/Documents/Reigh-Worker/source/models/wgp/orchestrator.py#L922). So using `custom_settings["precomputed_overlapped_latents_path"]` is a reasonable implementation choice.

5. The storage-URL convention is plausible, but it is still convention-based, not contractual. The intermediate upload helper does call `generate-upload-url` with `task_id` and returns a public `image_uploads/{storage_path}` URL: [output_paths.py#L185](/Users/user_c042661f/Documents/Reigh-Worker/source/utils/output_paths.py#L185), [output_paths.py#L295](/Users/user_c042661f/Documents/Reigh-Worker/source/utils/output_paths.py#L295). That means the latent URL derivation can work. But you should explicitly treat local predecessor paths, JSON `output_location`s, and non-storage URLs as fallback cases, not just “manual predecessor”.

**Verdict**

The core Phase 2 idea is good: export the final `overlapped_latents`, upload it, download it for the successor, and inject it before `any2video` tries to VAE-encode `prefix_video`. I do not think Phase 1 is correct in its current form, because it breaks the stitch-overlap semantics in this worker. I would also drop Step 2a entirely unless you find a real case where `latent_slice` is missing.

The corrected plan I’d trust is: keep current predecessor pixel-prefix semantics unchanged, export the already-produced final latent deterministically, load it via `custom_settings`, and revisit the “pixel fallback without FLF leakage” as a separate design that does not reuse the same clip for both motion context and stitched overlap.
