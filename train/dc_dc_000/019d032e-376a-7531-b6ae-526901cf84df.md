**Assessment**

The direction is good, but as written I would not trust this plan yet for “run once at the boundary, record structured state, and reliably show that we entered planning/postflight.”

1. The proposed hooks are command-local, not lifecycle-boundary-local. In the plan, the log is written after scan/triage/resolve/skip ([lexical-roaming-sonnet.md](/Users/user_c042661f/.claude/plans/lexical-roaming-sonnet.md#L77)), but the actual “we just entered planning mode / postflight” decision happens when `reconcile_plan()` sets `lifecycle_phase` and reports `lifecycle_phase_changed` in [pipeline.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/sync/pipeline.py#L223) and [plan_reconcile.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/scan/plan_reconcile.py#L283). If your requirement is “exactly once when leaving execution and entering planning/postflight,” this plan is hooked one layer too low.

2. The file design is not actually append-only or concurrency-safe. The proposal says append-only, but the API is `load -> append -> rewrite list` ([lexical-roaming-sonnet.md](/Users/user_c042661f/.claude/plans/lexical-roaming-sonnet.md#L50)). `safe_write_text()` is atomic for a single write, but it does not prevent lost updates from concurrent writers ([file_paths.py](/Users/user_c042661f/Documents/desloppify/desloppify/base/discovery/file_paths.py#L94)). If two commands write progression at once, one can overwrite the other.

3. Corruption handling is too destructive for a reliability feature. `load_progression()` returning `[]` on corrupt JSON ([lexical-roaming-sonnet.md](/Users/user_c042661f/.claude/plans/lexical-roaming-sonnet.md#L58)) means the next successful write silently erases the timeline. That is the opposite of what you want for preflight/postflight audit data.

4. Cross-file consistency is underspecified. Existing code already has special handling when plan and state must persist together ([override/io.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/override/io.py#L67)). Adding a third file after `save_plan()` / `save_state()` means progression can lag or diverge from persisted reality. The plan only mentions best-effort failure handling for resolve, not scan/triage/skip ([lexical-roaming-sonnet.md](/Users/user_c042661f/.claude/plans/lexical-roaming-sonnet.md#L89)).

5. It misses an important postflight boundary: subjective review completion. That transition is recorded during review import via `mark_subjective_review_completed()` in [plan_sync.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/review/importing/plan_sync.py#L251). Your proposal does not hook that path, so the progression log would still be incomplete for the full lifecycle.

6. The retention policy conflicts with the stated goal. `_MAX_ENTRIES = 200` ([lexical-roaming-sonnet.md](/Users/user_c042661f/.claude/plans/lexical-roaming-sonnet.md#L53)) is too small if you log every resolve/skip/unskip. Either this is a boundary log, or it is a command log. It cannot be both with a 200-entry cap.

7. The test plan is too unit-heavy for the risk you care about. The proposed tests only validate builders and trimming ([lexical-roaming-sonnet.md](/Users/user_c042661f/.claude/plans/lexical-roaming-sonnet.md#L101)). They do not prove “runs once,” “no duplicate entries on repeated no-op scans,” or “correct entry when phase changes to `triage_postflight`.”

**What I’d change**

Make this a lifecycle event log, not a generic action log.

- Write boundary events where phase actually changes: [plan_reconcile.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/scan/plan_reconcile.py#L308), [plan_sync.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/review/importing/plan_sync.py#L279), and [completion_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/plan/triage/completion_flow.py#L177).
- Store immutable records as `progression.jsonl`, one JSON object per line, with a lock. Do not rewrite a top-level JSON array.
- Add `schema_version`, `event_id`, `scan_count`, `phase_before`, `phase_after`, `source_action`, and a stable `cycle_id`.
- Keep command-level detail in the existing `execution_log` ([meta.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/operations/meta.py#L69)); summarize it into boundary events instead of duplicating every action.
- Add integration tests for: single phase transition emits one event, repeated scan with no transition emits none, review import emits postflight-review completion once, and triage completion emits the planning-complete boundary once.

**Bottom line**

As a “single parseable timeline artifact,” the plan is directionally right. As a “reliable preflight/postflight boundary recorder,” it is not sufficient yet. The main fix is to move from command hooks to lifecycle-transition hooks and from rewritable JSON-array storage to locked immutable event records.
