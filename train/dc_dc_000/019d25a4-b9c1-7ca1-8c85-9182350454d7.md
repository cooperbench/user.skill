Execution visibility and write safety for batched execution

## Problem 1: Orchestrator is blind during execution
The orchestrating agent runs `megaplan execute` and gets nothing back until ALL batches complete. It can't report progress to the user ('Batch 1 done, 5/7 tasks complete, starting batch 2...'). `megaplan status` only shows the plan state (finalized), not batch progress or task completion.

## Solution: Progress command + per-batch CLI mode
Two complementary approaches:
1. A `megaplan progress --plan <name>` command that reads finalize.json and reports task completion, current batch, and timing. The orchestrator can call this while execute runs in the background.
2. A `--batch N` flag on execute that runs a single batch and returns. The orchestrator calls it once per batch, getting results between each. This gives full visibility and lets the orchestrator report to the user between batches. The harness still handles batching logic (compute_task_batches), but the orchestrator drives the loop.

## Problem 2: Write safety for finalize.json
Three writers can touch finalize.json:
- The harness (between batches) — safe, sequential
- The agent (incremental saves during a batch) — prompt-based, best-effort
- Future: parallel agents within a batch — would corrupt

Currently there's no isolation. If we ever go parallel within a batch, or if the agent's incremental save races with the harness write, data is lost.

## Solution: Per-batch artifact files + merge
Instead of everyone writing to one finalize.json:
- Each batch writes to its own file: execution_batch_1.json, execution_batch_2.json
- The harness merges them into finalize.json between batches
- The agent's incremental saves go to the batch file, not finalize.json directly
- This eliminates all write races and makes batch results independently inspectable

## Problem 3: Skill instructions need timeout/progress guidance
The megaplan skill file doesn't tell the orchestrator how to handle long-running executions, check progress, or use per-batch mode. It should.

- megaplan/handlers.py — per-batch execution mode, progress reporting

## Overview
Megaplan's multi-batch execute currently runs all batches in a single `handle_execute()` call with no external visibility into progress. The orchestrator is blind until completion. Additionally, all writers (harness, agent, future parallel agents) contend on a single `finalize.json` file.

This plan adds: (1) a `progress` command for polling batch/task status mid-execution, (2) a `--batch N` flag so the orchestrator can drive batch-by-batch execution, and (3) per-batch artifact files that eliminate write contention.

**Current repo shape:**
- `handle_execute()` at `handlers.py:1885` handles both single-batch and multi-batch paths internally
- Multi-batch loop at `handlers.py:1936` writes `finalize.json` after each batch (`handlers.py:2050`)
- `_execute_batch_prompt()` at `prompts.py:614` reads `finalize.json` directly to build executor context
- `handle_status()` at `cli.py:63` returns plan state but no execution progress
- CLI parser at `cli.py:259` registers commands and flags
- `compute_task_batches()` at `_core.py:72` computes dependency-ordered batches

**Key constraints:**
- `finalize.json` is the single source of truth consumed by `handle_review()` — any batch file scheme must merge back before review
- The existing multi-batch loop in `handle_execute()` already persists after each batch (recovery on timeout) — `--batch N` extracts this pattern
- `_execute_batch_prompt()` reads `finalize.json` for the full context — batch files must be merged into it before generating the next batch's prompt

## Phase 3: Per-Batch CLI Mode

### Step 6: Add `--batch N` flag to execute (`megaplan/cli.py`, `megaplan/handlers.py`)
**Scope:** Large
1. **Add** `--batch` argument (type=int) to the execute subparser (`cli.py:288`).
2. **Add** `_handle_execute_one_batch()` to `handlers.py` — a new function that:
   - Loads `finalize.json` and computes batches via `compute_task_batches()`
   - Validates `args.batch` is in range `[1, len(batches)]`
   - Extracts the batch's task IDs from `batches[args.batch - 1]`
   - Determines `completed_task_ids` from tasks already done/skipped in finalize_data
   - Calls `_execute_batch_prompt()` to build the prompt
   - Runs the worker via `run_step_with_worker()`
   - Validates and merges results into finalize_data (reuse existing `_validate_and_merge_batch` calls)
   - Writes `execution_batch_{N}.json` (batch artifact)
   - Writes merged `finalize.json` and `final.md`
   - Runs execution evidence audit
   - Returns a response including `batch`, `batches_total`, whether more batches remain, and the batch-specific deviations
3. **Gate** in `handle_execute()`: if `args.batch` is set, delegate to `_handle_execute_one_batch()` early (before the existing single/multi-batch branching).
4. **State management:** `--batch N` should NOT transition to `STATE_EXECUTED` unless it's the final batch and all tasks are tracked. It stays `STATE_FINALIZED` between batches. The orchestrator calls `--batch 1`, `--batch 2`, etc., and the last one transitions state.
5. **History:** Each `--batch N` call appends its own history entry (one per invocation, not one aggregate).

        Idea:
Execution visibility and write safety for batched execution

## Problem 1: Orchestrator is blind during execution
The orchestrating agent runs `megaplan execute` and gets nothing back until ALL batches complete. It can't report progress to the user ('Batch 1 done, 5/7 tasks complete, starting batch 2...'). `megaplan status` only shows the plan state (finalized), not batch progress or task completion.

## Solution: Progress command + per-batch CLI mode
Two complementary approaches:
1. A `megaplan progress --plan <name>` command that reads finalize.json and reports task completion, current batch, and timing. The orchestrator can call this while execute runs in the background.
2. A `--batch N` flag on execute that runs a single batch and returns. The orchestrator calls it once per batch, getting results between each. This gives full visibility and lets the orchestrator report to the user between batches. The harness still handles batching logic (compute_task_batches), but the orchestrator drives the loop.

## Problem 2: Write safety for finalize.json
Three writers can touch finalize.json:
- The harness (between batches) — safe, sequential
- The agent (incremental saves during a batch) — prompt-based, best-effort
- Future: parallel agents within a batch — would corrupt

Currently there's no isolation. If we ever go parallel within a batch, or if the agent's incremental save races with the harness write, data is lost.

## Solution: Per-batch artifact files + merge
Instead of everyone writing to one finalize.json:
- Each batch writes to its own file: execution_batch_1.json, execution_batch_2.json
- The harness merges them into finalize.json between batches
- The agent's incremental saves go to the batch file, not finalize.json directly
- This eliminates all write races and makes batch results independently inspectable

## Problem 3: Skill instructions need timeout/progress guidance
The megaplan skill file doesn't tell the orchestrator how to handle long-running executions, check progress, or use per-batch mode. It should.

## Files involved
- megaplan/cli.py — new progress command, --batch flag
- megaplan/handlers.py — per-batch execution mode, progress reporting
- megaplan/prompts.py — update incremental save path to batch file
- megaplan skill file — usage guidance
- Tests
