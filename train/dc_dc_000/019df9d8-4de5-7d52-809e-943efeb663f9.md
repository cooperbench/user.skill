> AGENT

**Root Cause**

This is a harness bug plus executor-output sloppiness, not just a chain spec issue.

The top-level chain driver is not nested-repo aware. In `megaplan-fix/megaplan/chain.py`, `_commit_milestone_changes()` only runs top-level `git add -A`, `git diff --cached --quiet`, and `git commit` at lines 425-441. In this workspace, `.gitignore` explicitly ignores `reigh-app/` and `reigh-worker/`, and those are separate repos. So top-level commits cannot capture the real edits there. They only see top-level docs plus gitlink-like nested repo entries such as `megaplan-fix` and `reigh-app-cloud-chain`.

The execute audit has the same blind spot. `validate_execution_evidence()` in `megaplan-fix/megaplan/evaluation.py` routes to `_validate_execution_evidence_code()` lines 124-133, which runs only `git status --short` in the top-level `project_dir` at lines 229-263. It does not recurse into `reigh-app` or `reigh-worker`, and ignored nested repos stay invisible. That is why claimed nested paths were reported as “not present in git status”.

`_auto_attribute_unclaimed_paths()` made this worse. In `megaplan-fix/megaplan/execute/quality.py` lines 57-142, it assigns top-level unclaimed paths to any done task with empty `files_changed` and `commands_run`. Because top-level status only saw docs/gitlink markers, it incorrectly attributed files like `docs/megaplan-vibecomfy-chain/chain.yaml`, `megaplan-fix`, and `reigh-app-cloud-chain` to unrelated tasks that actually changed `reigh-app` and `reigh-worker`.

**T14 / SC14**

T14 did not run because execution blocked on T12 first. In `execution_batch_6.json`, T12’s task update has empty `files_changed` and empty `commands_run`, even though the aggregate `commands_run` lists the verification commands. The blocker comes from `build_blocking_reasons()` in `megaplan-fix/megaplan/execute/core.py` lines 285-310 and the final aggregate check around lines 1165-1185.

So the immediate `worker_blocked` was executor-output invalidity: T12 should have included its verification commands in `task_updates[].commands_run`. T14/SC14 pending is a consequence. The after_execute user action itself was modeled by finalize as normal task T14, which is workable but fragile: there is no harness-native after_execute user action gate beyond whatever task the finalizer invents.

**Minimal Patch Plan**

1. Add a repo discovery helper, probably in `execute/quality.py` or a new git utility:
   - detect nested repos under `project_dir` from claimed paths and/or `.git` directories
   - run `git -C <repo> status --short`
   - normalize nested paths back to workspace-relative paths like `reigh-app/...`

2. Use that helper in:
   - `evaluation._validate_execution_evidence_code()`
   - `execute.quality._capture_git_status_snapshot()` / recursive snapshot path
   - `execute.core._compute_execute_scope_drift()`
   - `chain._commit_milestone_changes()`

3. For chain commits, either:
   - fail fast if a milestone changed nested repos and no nested commit/push strategy is configured, or
   - commit/push each changed nested repo first, then commit the top-level chain metadata/gitlinks.
   
   The safer minimal behavior is fail fast with a clear error listing dirty nested repos.

4. Disable or constrain auto-attribution for nested-repo runs:
   - never attribute top-level gitlink/directory markers to tasks claiming nested files
   - if multiple unattributed tasks exist, leave it advisory instead of mutating every task with the same unrelated paths.

5. Add native after_execute handling:
   - before marking execute complete, surface `user_actions` with `phase == "after_execute"` in the response/warnings
   - optionally transition to `awaiting_human` if such actions require sign-off, instead of relying on a synthetic T14 task.

**Test Plan**

Add tests for:

- top-level repo with ignored nested `reigh-app/` and `reigh-worker/`, where nested `git status` changes are included as workspace-relative paths.
- `validate_execution_evidence()` accepts `files_changed: ["reigh-app/foo.ts"]` when only `git -C reigh-app status` sees it.
- `_auto_attribute_unclaimed_paths()` does not assign gitlink/nested-dir markers to unrelated tasks.
- `chain._commit_milestone_changes()` fails clearly when nested repos are dirty unless nested commits are explicitly supported.
- execute with `after_execute` user_actions surfaces them even without a final synthetic task.
