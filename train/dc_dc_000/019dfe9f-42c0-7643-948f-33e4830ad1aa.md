Our rendering today is already Remotion-based: [render/run.py](/Users/user_c042661f/Documents/reigh-workspace/ArtAgents/artagents/packs/builtin/render/run.py:340) builds timeline/assets/theme props, serves large media over local HTTP with range support, then calls `npx remotion render TimelineComposition`. The linked `StorePeel` example is a different visual technique inside Remotion, not a replacement for Remotion. It wraps a DOM product card in `<HtmlInCanvas>`, captures that DOM as an image each frame, then sends it through a WebGL shader for gloss/material effects before layering stickers on top. Remotion’s docs describe the core advantage pretty directly: HTML-in-canvas lets you draw a live DOM node into `<canvas>` and post-process it with Canvas 2D, WebGL, or WebGPU. Source: Remotion docs, HTML-in-canvas section: https://www.remotion.dev/docs/html-in-canvas and example repo: https://github.com/remotion-dev/html-in-canvas#storepeel Advantages for us: - Much richer visual effects on DOM-based elements: glass, CRT, blur, peel, shader distortions, lighting, masked transitions, magnifying effects. - Lets us keep authoring cards/captions/layouts as HTML/CSS/React, then treat the result like a texture. - Good fit for branded “hero” effects, thumbnails, product cards, title cards, animated UI mockups, and custom transitions. - Could make some Reigh/ArtAgents effects feel more premium without abandoning the timeline JSON model. Costs / risks: - It is still experimental. Remotion says it depends on Chrome Canary / Chrome 149+ API support, and Chrome may change or remove the API. - Rendering support starts at Remotion `4.0.455`; this repo is currently on `4.0.448`, so adopting it means a Remotion upgrade. - WebGL effects need `--gl=angle` or `--gl=swangle`, which adds environment complexity. - `<HtmlInCanvas>` cannot be nested, so it is not a clean global compositor replacement. - It is overkill for ordinary video assembly, captions, cuts, audio, and timeline validation. My recommendation: expose one normal renderer to users: the existing timeline renderer. Add HTML-in-canvas as a new class of element/transition, maybe with a manifest flag like `requires_html_in_canvas: true`, and have render detect that to add the right Remotion flags/version checks. That gives us the upside for high-end effects without making every render depend on an experimental browser path. So: both internally, one default externally. Use HTML-in-canvas when an effect truly needs canvas/WebGL post-processing; keep plain timeline-composition for the bread-and-butter render path.
