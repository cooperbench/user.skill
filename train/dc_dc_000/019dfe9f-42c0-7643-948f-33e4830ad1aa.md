> AGENT

I’d keep our current renderer as the default/canonical path, and add HTML-in-canvas as an optional effect/transition capability, not as a competing whole-renderer mode.

Our rendering today is already Remotion-based: [render/run.py](/Users/user_c042661f/Documents/reigh-workspace/ArtAgents/artagents/packs/builtin/render/run.py:340) builds timeline/assets/theme props, serves large media over local HTTP with range support, then calls `npx remotion render TimelineComposition`. The composition itself is the shared timeline renderer in [Root.tsx](/Users/user_c042661f/Documents/reigh-workspace/ArtAgents/remotion/src/Root.tsx:44), which dispatches timeline `clipType`s through the generated effect registry and normal media clips through `<Video>` / `<Img>`.

The linked `StorePeel` example is a different visual technique inside Remotion, not a replacement for Remotion. It wraps a DOM product card in `<HtmlInCanvas>`, captures that DOM as an image each frame, then sends it through a WebGL shader for gloss/material effects before layering stickers on top. Remotion’s docs describe the core advantage pretty directly: HTML-in-canvas lets you draw a live DOM node into `<canvas>` and post-process it with Canvas 2D, WebGL, or WebGPU. Source: Remotion docs, HTML-in-canvas section: https://www.remotion.dev/docs/html-in-canvas and example repo: https://github.com/remotion-dev/html-in-canvas#storepeel

Advantages for us:

- Much richer visual effects on DOM-based elements: glass, CRT, blur, peel, shader distortions, lighting, masked transitions, magnifying effects.
- Lets us keep authoring cards/captions/layouts as HTML/CSS/React, then treat the result like a texture.
- Good fit for branded “hero” effects, thumbnails, product cards, title cards, animated UI mockups, and custom transitions.
- Could make some Reigh/ArtAgents effects feel more premium without abandoning the timeline JSON model.

Costs / risks:

- It is still experimental. Remotion says it depends on Chrome Canary / Chrome 149+ API support, and Chrome may change or remove the API.
- Rendering support starts at Remotion `4.0.455`; this repo is currently on `4.0.448`, so adopting it means a Remotion upgrade.
- WebGL effects need `--gl=angle` or `--gl=swangle`, which adds environment complexity.
- `<HtmlInCanvas>` cannot be nested, so it is not a clean global compositor replacement.
- It is overkill for ordinary video assembly, captions, cuts, audio, and timeline validation.

My recommendation: expose one normal renderer to users: the existing timeline renderer. Add HTML-in-canvas as a new class of element/transition, maybe with a manifest flag like `requires_html_in_canvas: true`, and have render detect that to add the right Remotion flags/version checks. That gives us the upside for high-end effects without making every render depend on an experimental browser path.

So: both internally, one default externally. Use HTML-in-canvas when an effect truly needs canvas/WebGL post-processing; keep plain timeline-composition for the bread-and-butter render path.

> AGENT

Yes: treat these “custom nodes” as **packs**, not as loose files or random sub-repos.

The clean model is:

**1. Default built-ins live in the ArtAgents repo**
Core effects/executors/orchestrators that we trust and want everyone to have should ship under:

```text
artagents/packs/builtin/
artagents/packs/external/
artagents/packs/iteration/
...
```

These are just modules in the main repo/package. They update when ArtAgents updates. No separate install step beyond installing/updating ArtAgents.

**2. Third-party/user additions should be packs**
Someone else should publish a pack with a manifest, e.g.

```text
my-artagents-pack/
  pack.yaml
  cool_effect/
    executor.yaml
    STAGE.md
    run.py
  elements/
    effects/
      glass-card/
        element.yaml
        component.tsx
```

The important thing is that the pack has metadata ArtAgents can discover: id, name, version, description, capabilities, dependency hints, compatibility range, etc.

**3. Have a registry/catalog, not a database-heavy system**
I’d start with a simple registry file, not a full service:

```json
{
  "packs": [
    {
      "id": "banodoco.html-canvas",
      "source": "git",
      "url": "https://github.com/banodoco/artagents-html-canvas-pack",
      "ref": "v0.1.0",
      "default": true,
      "trusted": true,
      "description": "HTML-in-canvas starter effects"
    }
  ]
}
```

This can live in the ArtAgents repo first, maybe `artagents/pack-registry.json` or hosted at a stable URL later. A database can come later if pack discovery becomes social/search-heavy.

**4. Install flow**
I’d make the commands look like:

```bash
python3 -m artagents packs list
python3 -m artagents packs search html canvas
python3 -m artagents packs install banodoco.html-canvas
python3 -m artagents packs install --default
python3 -m artagents packs update
python3 -m artagents packs uninstall banodoco.html-canvas
```

Install should clone/copy packs into a managed directory, not into source-controlled `artagents/packs/builtin`:

```text
~/.artagents/packs/
  banodoco.html-canvas/
```

or repo-local if the project wants reproducibility:

```text
.artagents/packs/
  banodoco.html-canvas/
```

Then discovery order becomes something like:

1. active theme
2. repo-local `.artagents/packs`
3. user-global `~/.artagents/packs`
4. built-in `artagents/packs`
5. local scratch pack overrides

**5. Defaults**
The registry should distinguish:

- `builtin`: ships inside ArtAgents, always present
- `default`: installed by `artagents setup` or `packs install --default`
- `available`: listed/searchable, user chooses to install
- `trusted`: maintained/curated enough that we are comfortable installing by default
- `experimental`: visible, but explicit opt-in

So yes, we can have “ones we choose from that catalog are pre-installed at setup time,” but I’d avoid silently installing a lot of code on every install. Better:

```bash
python3 -m artagents setup
```

prints:

```text
Default packs:
- banodoco.html-canvas
- banodoco.thumbnail-effects
- banodoco.event-cards

Run with --apply to install/update them.
```

**6. Updating**
Installed packs should have a lockfile:

```text
.artagents/packs.lock.json
```

Example:

```json
{
  "packs": {
    "banodoco.html-canvas": {
      "url": "https://github.com/banodoco/artagents-html-canvas-pack",
      "ref": "v0.1.0",
      "resolved_sha": "abc123",
      "installed_at": "2026-05-06T..."
    }
  }
}
```

Then:

```bash
python3 -m artagents packs update
```

updates only according to policy:

- pinned `ref`: stay pinned
- semver range: update within range
- branch install: pull latest, but mark dirty/risky
- trusted default: update on `setup --apply` or explicit `packs update --default`

**7. GitHub discovery**
If someone pushes a pack to GitHub, ArtAgents should not magically know unless one of these happens:

- they run `artagents packs publish`, which opens a PR adding it to the registry
- they give someone a Git URL: `artagents packs install https://github.com/foo/bar`
- we later add GitHub search for repos/topics like `artagents-pack`, but that should be secondary

The durable path is a registry PR. That gives review, trust, compatibility metadata, and avoids executing arbitrary GitHub code just because it exists.

**8. How this applies to `html_canvas_effect`**
I’d keep the executor itself in `builtin` because it teaches ArtAgents how to scaffold the pattern.

But the actual templates could evolve into a pack:

```text
banodoco.html-canvas/
  elements/effects/glass-card/
  elements/effects/crt-screen/
  elements/transitions/cube-peel/
  templates/card/
  pack.yaml
```

Then `builtin.html_canvas_effect` could accept:

```bash
--template glass-card
--from-pack banodoco.html-canvas
```

Default install can include that pack once it’s stable.

My recommendation: implement pack install/update next, using a JSON registry plus lockfile. Do not build a database yet. Make registry entries PR-reviewed, install packs into `.artagents/packs` or `~/.artagents/packs`, and keep `builtin` for the minimal trusted core.
