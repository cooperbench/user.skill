```
megaplan tiebreaker --plan <name> --question "..." [--output tiebreaker.md]
megaplan tiebreaker --plan <name> --question-file path/to/decision.md

```

The question file or inline question states the decision, the constraints that can't all hold, and any pinned context (relevant files, patterns to consider).

**Phase flow inside the subcommand (not new top-level phases):**

1. Researcher pass — worker reads the question, the repo, the plan's current state (if any), and the critique history.         # Implementation Plan: `megaplan tiebreaker` Subcommand

## Overview

Add a `megaplan tiebreaker` command that orchestrates two independent subagent passes (researcher → challenger) to produce structured decision context for human architectural calls. The command operates on an existing plan and writes advisory artifacts alongside existing plan artifacts.

**Current repo shape:** v0.16.0. CLI commands register via `build_parser()` in `cli.py:802–952`, with complex commands (auto, chain) using the `build_*_parser()` + deferred-import pattern dispatched directly in `main()` at lines 1037–1049. Workers are dispatched through `run_step_with_worker()` (`workers.py:1477`) which resolves agent → `run_codex_step()` / `run_claude_step()`. Schemas live in `megaplan/schemas.py:SCHEMAS` dict and are written to `.megaplan/schemas/` at setup time.

**Key design decisions (resolving open questions from v1):**
1. **Agent config:** Both CLI `--agent` flag AND per-plan config via `agents.tiebreaker_researcher` / `agents.tiebreaker_challenger` are supported. This is free — `resolve_agent_mode()` at `workers.py:1424` already falls back through `--agent` → `config.agents.<step>` → `DEFAULT_AGENT_ROUTING[step]`. We just register the two step names in `DEFAULT_AGENT_ROUTING`.
2. **Artifact location:** Artifacts go directly in the plan directory (e.g., `.megaplan/plans/<name>/tiebreaker_researcher.json`), matching the existing pattern where all phase artifacts live flat in the plan dir.
3. **Status sub-subcommand:** Use argparse sub-subparsers under tiebreaker, matching the config/debt/step pattern (`cli.py:856–902`). `megaplan tiebreaker status --plan <name>`.

**Worker reuse strategy:** We call `run_step_with_worker()` directly (not `_run_worker()` from handlers.py which assumes plan-phase semantics like `set_active_step`). We pass `resolved=(agent, mode, True, model)` to pre-resolve the agent and `prompt_override` for custom prompts. Schemas are registered in `STEP_SCHEMA_FILENAMES` + `SCHEMAS` so the existing schema-loading in `run_codex_step`/`run_claude_step` works unchanged.

## Phase 2: Core Orchestration

### Step 3: Create tiebreaker orchestrator (`megaplan/tiebreaker.py`)
**Scope:** Large — main new file (~250–350 lines)
1. **Create** `megaplan/tiebreaker.py` with:
   - `build_tiebreaker_parser(subparsers)` — registers `tiebreaker` subcommand with sub-subparsers:
     - Default action `run`: `--plan` (required), `--question` / `--question-file` (mutually exclusive group, one required for `run`), `--output` (default `tiebreaker.md`), `--agent` (choices: claude, codex, hermes).
     - Sub-action `status`: `--plan` (required).
   - `run_tiebreaker_cli(root: Path, args: Namespace) -> int` — top-level dispatch that routes to `_run_tiebreaker()` or `_run_tiebreaker_status()` based on `args.tiebreaker_action`.
   - `_run_tiebreaker(root, args) -> int`:
     1. Resolve plan: `plan_dir = plans_dir(root) / args.plan`. Validate it exists.
     2. Load state: `load_plan_locked()` → read state → release lock immediately (context manager exit).
     3. Read question from `args.question` or `Path(args.question_file).read_text()`.
     4. Compute version suffix: scan `plan_dir` for `tiebreaker_researcher*.json`, derive next version (no suffix for v1, `_v2` for second run, etc.).
     5. Build researcher prompt via `researcher_prompt(question, state, plan_dir, root=root)`.
     6. Call `run_step_with_worker("tiebreaker_researcher", state, plan_dir, args, root=root, resolved=(agent, "persistent", True, model), prompt_override=prompt)` — agent resolved from `resolve_agent_mode("tiebreaker_researcher", args)`.
     7. Validate and write `tiebreaker_researcher{suffix}.json` via `atomic_write_json()`.
     8. Build challenger prompt via `challenger_prompt(question, researcher_payload, state, plan_dir, root=root)`.
     9. Call `run_step_with_worker("tiebreaker_challenger", state, plan_dir, args, root=root, resolved=(agent, "persistent", True, model), prompt_override=prompt)` — uses fresh session (separate step name = separate session key).
     10. Validate and write `tiebreaker_challenger{suffix}.json`.
     11. Render synthesis via `render_synthesis(question, researcher_payload, challenger_payload)`.
     12. Write `tiebreaker{suffix}.md` to plan_dir.
     13. Print path to synthesis file, return 0.
   - `_run_tiebreaker_status(root, args) -> int`: Check existence of `tiebreaker_researcher*.json`, `tiebreaker_challenger*.json`, `tiebreaker*.md` in plan_dir. Print status table (phase | status | file). Return 0.
   - `_next_version_suffix(plan_dir: Path) -> str`: Scan for existing `tiebreaker_researcher*.json` files, return `""` for first run, `"_v2"` for second, etc.
2. **Key detail on session independence:** The researcher step name `"tiebreaker_researcher"` and challenger step name `"tiebreaker_challenger"` produce different session keys via `session_key_for(step, agent)` in workers.py. This ensures they get separate persistent sessions automatically. The challenger's prompt includes the researcher's JSON output but has no access to the researcher's conversation history.
3. **Key detail on args namespace:** The tiebreaker parser adds `--agent`, `--fresh` (default True for both passes), and `--persist` (default True). These are read by `resolve_agent_mode()` when `resolved=` is not passed. We call `resolve_agent_mode()` ourselves for each step (researcher/challenger separately, since they could have different config routing) and pass the result as `resolved=` to `run_step_with_worker()`.
4. **Error handling:** If the researcher pass fails, bail immediately (don't attempt challenger). If the challenger fails, the researcher artifact is already written — status will show partial completion. Re-running produces a new version.
