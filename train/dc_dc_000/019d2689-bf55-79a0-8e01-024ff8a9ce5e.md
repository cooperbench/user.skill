        # Implementation Plan: Fix Large Image Rendering in Video Editor Preview

## Overview
The video editor renders visual clips via `VisualClip.tsx`, which applies absolute pixel positioning (`left`, `top`, `width`, `height`) directly to `<Img>` elements inside a Remotion `<AbsoluteFill style={{ overflow: 'hidden' }}>`. When images are sized larger than the composition (e.g., 2256×1692 on a 1920×1080 comp), no bounds validation exists — the DOM element is created at full size and clipped only by CSS overflow. Meanwhile, the `OverlayEditor` drag/resize handlers apply deltas without any position or size clamping, allowing clips to grow arbitrarily large or drift entirely off-canvas.

**Key files:**
- `src/tools/video-editor/compositions/VisualClip.tsx` — renders clips to DOM
- `src/tools/video-editor/components/PreviewPanel/OverlayEditor.tsx` — drag/resize/crop UI
- `src/tools/video-editor/components/PropertiesPanel/ClipPanel.tsx` — numeric property inputs
- `src/tools/video-editor/lib/serialize.ts` — config validation (structural only, no range checks)

**Current state:** No clamping at any layer. Crop normalization exists (0–1 range, max 99% total) but position (x, y) and size (width, height) are unconstrained.

## Phase 1: Investigate — Reproduce & Characterize the Bug

### Step 1: Reproduce the visual bug in the browser
**Scope:** Small
1. **Run** the dev server and open the video editor with a large image (≥2256×1692) on a 1920×1080 composition.
2. **Document** what "renders incorrectly" means: is it clipping artifacts, blank regions, wrong position, or rendering failure? Check both static (no drag) and drag states.
3. **Inspect** the DOM in devtools: measure the actual pixel dimensions of the `<img>` element Remotion creates. Check if it exceeds browser limits.
4. **Test thresholds**: try images at 1x, 2x, 4x, and 8x composition size to find where it breaks.

### Step 2: Check Remotion and browser canvas limits
**Scope:** Small
1. **Research** Remotion's documented rendering limits — particularly for `<Img>` with absolute positioning vs. `<canvas>`-based rendering. Key concern: does Remotion's render pipeline (for export, not just preview) have a max element size?
2. **Check** browser `<canvas>` limits: Chrome caps at ~16384×16384 for hardware-accelerated canvases, but `<Img>` elements are not canvas-based — they're DOM. The limit likely doesn't apply to preview, but **does apply to Remotion's screenshot-based render** which uses Puppeteer/Playwright to capture frames.
3. **Test** a Remotion render (export) with an oversized image to see if the export also exhibits the bug.

## Phase 2: Core Fix — Bounds Clamping

### Step 3: Add a shared bounds utility (`src/tools/video-editor/lib/clip-bounds.ts`)
**Scope:** Medium
1. **Create** a utility module with:
   ```typescript
   /** Max element dimension — stay well under browser canvas limits (16384px). */
   const MAX_ELEMENT_DIMENSION = 8192;

   /** Clamp clip bounds so the element doesn't exceed safe rendering limits.
    *  Does NOT force the clip to stay within the composition — just caps size. */
   function clampClipDimensions(
     bounds: { x: number; y: number; width: number; height: number },
     compositionWidth: number,
     compositionHeight: number,
   ): { x: number; y: number; width: number; height: number }
   ```
2. The function should:
   - Cap `width` and `height` to `MAX_ELEMENT_DIMENSION` (preserving aspect ratio).
   - Adjust `x`/`y` to keep the center point stable when clamping.
   - NOT restrict position to be within composition bounds — users should be able to position clips partially off-screen intentionally.

### Step 4: Apply clamping in `VisualClip.tsx` (render-layer defense)
**Scope:** Small (`src/tools/video-editor/compositions/VisualClip.tsx:16-59`)
1. **Import** `clampClipDimensions` and apply it in `getClipBoxStyle()` before building the CSS properties.
2. This is a **defensive** clamp — it catches any unclamped values that slip through the UI layer.
3. **Verify** that the clamp preserves the visual appearance for normal-sized clips (no visible change for clips ≤ composition size).

### Step 5: Apply clamping in `OverlayEditor.tsx` drag handlers
**Scope:** Medium (`src/tools/video-editor/components/PreviewPanel/OverlayEditor.tsx:319-430`)
1. **Move mode** (line 330-332): After applying deltaX/deltaY, clamp dimensions via `clampClipDimensions`. Position should remain free — the user drags wherever they want, but the element won't balloon past safe limits.
2. **Resize mode** (line 376-404): After computing `newWidth`/`newHeight`, cap to `MAX_ELEMENT_DIMENSION`. This prevents resizing a clip to absurd proportions.
3. **Before calling `onOverlayChange`** (lines 420-429): Run the final bounds through `clampClipDimensions` so Remotion always receives safe values.
4. **Do NOT clamp position to within composition** — partial off-screen is a valid creative choice. Only clamp dimensions.

### Step 6: Add input validation in `ClipPanel.tsx`
**Scope:** Small (`src/tools/video-editor/components/PropertiesPanel/ClipPanel.tsx`)
1. **Add** `max` attributes to width/height inputs: `max={MAX_ELEMENT_DIMENSION}`.
2. **Add** `onBlur` clamping for width/height fields to enforce the max after manual entry.
3. **Leave** x/y unconstrained (position is intentionally free).

## Phase 3: Validation

5. **Test export**: render a composition with a large image to video — no artifacts in output.
6. **Test normal clips**: confirm no regression for normally-sized clips (same size as composition or smaller).

### Step 8: Edge cases
**Scope:** Small
1. **Very small clips**: ensure `MIN_CLIP_SIZE` (20px) still works after clamping logic is added.
2. **Aspect ratio lock during resize**: verify the AR lock still works when dimensions hit the cap.
3. **Crop + large image**: crop a 4000×3000 image and verify the crop math is correct with clamped outer bounds.
