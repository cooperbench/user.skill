**Findings**
1. The plan misses the main worker gate: chained LTX requests will not currently enter the guide-building path at all. The doc says only `orchestrator.py` and maybe `segment_processor.py` need changes, but the frontend still forces LTX to `model_type: 'i2v'` in [requestBody.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/requestBody.ts#L116), and the worker only runs `TravelSegmentProcessor` for `travel_mode == "vace"` or explicit structure guidance in [task_registry.py](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/tasks/task_registry.py#L602). So [the plan](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L112) is wrong to say guide extraction “works as-is” for plain LTX smooth continuation.

2. The plan also misses stitch creation gating. It says stitch is already model-agnostic and needs no changes, but the orchestrator only creates a stitch task for `use_svi` or `(travel_mode == "vace" and chain_segments)` in [orchestrator.py](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L414). Chained LTX segments will therefore not stitch under the current worker logic. That is a critical omission in [the worker section of the doc](/Users/user_c042661f/.claude/plans/squishy-finding-lamport.md#L143).

3. The document standardizes in the wrong layer. It proposes new hardcoded overlap and frame-limit rules in UI files like [MotionControlBasicTab.tsx](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/MotionControlBasicTab.tsx#L160), [pairPayload.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/pairPayload.ts#L168), [useVideoTravelSettingsHandlers.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/hooks/settings/useVideoTravelSettingsHandlers.ts#L216), and [ShotEditorLayout.tsx](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/ShotEditorLayout.tsx#L149). That will work for one more model, but it will not make future continuation types painless. This logic wants a shared capability/policy table, not more scattered conditionals.

4. `smoothContinuations` is too weak as the long-term contract. Right now the shared request contract only has `model_type`, `frame_overlap`, `independent_segments`, and `chain_segments` in [taskTypes.ts](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/travelBetweenImages/taskTypes.ts#L136). The plan doubles down on deriving behavior directly from that boolean. That is brittle because VACE guide+mask, LTX guide+prefix, and future latent/anchor continuation modes are different worker strategies even if they are one UX toggle.

5. The doc conflates user-visible frames with worker input/context frames. Its `73` limit is sensible as a UX cap, but the worker then inflates segment frames with overlap in [orchestrator.py](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L1950). Those are different concepts and need different fields. You can already see the mismatch in restore/apply-settings: overlap is still extracted as `context` in [taskDataService.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/taskDataService.ts#L98), but the apply path ignores it with “fixed at 10 frames” in [generationSettingsService.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/generationSettingsService.ts#L76). If you implement the doc as written, UX and replayed settings will drift.

**What I’d Standardize Instead**
Use one canonical model capability registry, keyed by a stable `model_id`, not by substring checks on `model_name`. The frontend already has that shape in [settings.ts](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/settings.ts#L98); the worker still infers capabilities from `"vace"` / `"ltx2"` string matching in [segment_processor.py](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/segment_processor.py#L69).

Add a canonical `continuation` object to the shared contract, then derive legacy fields from it during migration. Something like:

```ts
type ContinuationConfig = {
  enabled: boolean;
  strategy: 'none' | 'guide_overlap_masked' | 'guide_overlap_prefix';
  overlapFrames: number;
  sequential: boolean;
  stitch: boolean;
  visibleOutputFrames: number;
};
```

Client-side, everything should read from one resolver such as `resolveContinuationPolicy(modelId, enabled)`: toggle visibility, tooltip copy, max frame limit, payload values. Worker-side, normalize once near orchestrator entry: `should_run_segment_processor`, `should_create_stitch`, `segment_input_frames`, `prefix_frames_count`, `video_prompt_type`, and any mask usage should come from that normalized continuation policy, not from `travel_mode == "vace"` branches.

**Practical Direction**
I would not ship the plan as-is. The good part is the overall UX intent: one “Smooth Continuations” toggle across models. The part I would rewrite is the contract boundary: make the toggle express user intent, make a shared model/policy registry resolve the concrete strategy, and make the worker depend on normalized continuation policy instead of `model_type` plus ad hoc model-name checks. That is what will make adding the next model painless rather than another round of `10/24/77/73` edits in five files.
