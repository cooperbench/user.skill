## Analysis: Queue Inconsistency Bug

### 1. What `plan show` reports vs. what `next`/`plan queue` show

**`plan show`** (`cmd.py:84`) reads directly from the persisted JSON:

```python
ordered = len(plan.get("queue_order", []))
```

This is a raw count of IDs in `queue_order`. It does NOT run `build_work_queue`. It does NOT apply lifecycle filtering, subjective injection logic, or the `_empty_queue_fallback`. What it prints is literally "how many IDs live in the plan JSON's `queue_order` list."

**`next` / `plan queue`** both call `build_work_queue(state, options=QueueBuildOptions(...))` which runs a full pipeline (core.py:94–145):

1. Builds issue items from state
2. Builds subjective dimension items dynamically (not from `queue_order`)
3. Builds workflow items by checking `queue_order` for `triage::*`/`workflow::*` IDs
4. Filters by impact floor
5. Separates plan-skipped items
6. Applies `_apply_lifecycle_filter` (the endgame gate)
7. Sorts
8. If queue is empty after all that, injects `workflow::run-scan` (the `_empty_queue_fallback`)

The critical distinction: **`subjective_dimension` items are generated dynamically** in `_gather_subjective_items` → `build_subjective_items`. They are NOT read from `queue_order`. Their IDs (`subjective::<slug>`) may or may not appear in `queue_order`, but the dynamic build doesn't require it — the items are synthesized from `state["dimension_scores"]` whenever score is below threshold.

### 2. The "all objective items skipped" scenario — what actually happens

When all objective issues are skipped (they're in `plan["skipped"]`), here is what `build_work_queue` sees:

- **Step 1**: `build_issue_items` returns all issues. `separate_skipped` (step 3) splits them out. After `_plan_postsort`, skipped items are re-appended only if `include_skipped=True` — otherwise the effective non-skipped list is empty for objective items.
- **Step 1 also**: `_gather_subjective_items` builds subjective items dynamically. `_is_endgame_only` is True for these when `initial_review=False`. But `_has_objective_items` (core.py:273) checks only non-skipped items in the `items` list at the point of `_apply_lifecycle_filter` — and the skipped items have already been separated before lifecycle filtering runs (step 3 happens before step 4).

So when all objective items are in `plan["skipped"]`, `_has_objective_items(items)` returns **False** because the skipped items were removed in step 3. This means `_apply_lifecycle_filter` returns all items, including endgame-only subjective items. Subjective items surface.

**This is intentional behavior** — the intent is that once you've skipped everything, you're in "endgame" mode and subjective work becomes visible. Whether skipping everything should be treated as "objective work complete" vs. "objective work still pending but deferred" is the philosophical question, but the code deliberately treats skipped-out items as if they don't exist for lifecycle purposes.

### 3. Is the subjective injection after skipping all objectives a bug?

From the code's perspective: **it's intentional but potentially surprising**. The lifecycle filter in `_apply_lifecycle_filter` (core.py:290) only considers items still in the active `items` list at filter time. Skipped items are removed in `separate_skipped` before the lifecycle filter runs. So the filter cannot tell the difference between "all objectives resolved" and "all objectives skipped."

The `SubjectiveVisibility.should_inject_to_plan` logic in `subjective_policy.py` has a distinction: it checks `has_objective_backlog`, which is computed from open issues *excluding plan-skipped IDs*. So at scan time (`sync_stale_dimensions` during `reconcile_plan_post_scan`), stale/under-target subjective IDs **will be injected into `queue_order`** when all objectives are skipped, because skipped IDs are excluded from `objective_count` (subjective_policy.py:103–119).

The disconnect the user sees is likely that `plan show` reports N items but those items don't seem like "real work."

### 4. Score frozen / `queue_remaining > 0`

The score-freezing path in `queue_progress.py:print_execution_or_reveal` (line 290–336):

### 5. `workflow::run-scan` never appearing

`workflow::run-scan` is only injected by `_empty_queue_fallback` (core.py:302–317):


This is a real gap: once the user skips all objective items and subjective items surface, there is no `workflow::run-scan` nudge to prompt them to re-scan. The subjective items have a `primary_command` of `desloppify review --prepare ...`, which is the right next action, but after completing that the user still needs to scan — and nothing prompts that.

### 6. `_clear_plan_start_scores_if_queue_empty` and the cycle-clearing logic

In `plan_reconcile.py:_clear_plan_start_scores_if_queue_empty` (line 124–145):

```python

```

`breakdown.actionable` (queue_progress.py:42–49) is `max(0, queue_total - workflow)`. It subtracts workflow items (like `workflow::run-scan`) but does **NOT** subtract subjective items. This means the plan cycle remains "active" (with a frozen start score in `plan_start_scores`) indefinitely as long as subjective items remain in `queue_order`. The user cannot complete the cycle and get a fresh scan start without either:
- Resolving the subjective items (completing the reviews)
- Force-rescanning with attestation
- Manually clearing `plan_start_scores`

### Summary of Confirmed Bugs and Design Gaps

**Bug 1 — `plan show` vs. dynamic queue counts are different quantities**

`plan show` reads `len(plan["queue_order"])`. The dynamic queue (`next`/`plan queue`) reads `build_work_queue` which includes dynamically-synthesized subjective items NOT necessarily in `queue_order`. These counts will diverge: you can have subjective items visible in `next` that are not in `queue_order`, and vice versa (items in `queue_order` that are skipped won't appear in `next`).

**Bug 2 — Score frozen in `status` but not in `next` when only subjective items remain**

`status/cmd.py:_print_score_section` line 204 gates on `queue_remaining = breakdown.queue_total` (any items including subjective). `queue_progress.py:print_execution_or_reveal` gates on `objective_remaining > 0`. These two code paths give different answers: `status` shows the score as frozen; `next`/post-scan shows it as live. This is an inconsistency.

**Bug 3 — `workflow::run-scan` never surfaces when subjective items are present**

`_empty_queue_fallback` only fires when `items` is empty. Subjective items after all objectives are skipped prevent it from firing. The user never sees the "run scan" prompt even though a scan is the appropriate next step after completing subjective reviews.

**Bug 4 — Plan cycle never clears while subjective items in queue_order**

`breakdown.actionable` only excludes `workflow_*` kinds, not `subjective_dimension`. So `_clear_plan_start_scores_if_queue_empty` never fires while any subjective items are in `queue_order`, even if those items only require reviews (not a scan to clear). The frozen plan-start score persists through the entire subjective review phase, which may span many days.

**The root cause of all four**: there are now three categories of items — objective issues, subjective dimension assessments, and workflow navigation steps — but most of the lifecycle/freezing/gating logic only has a binary model (work present vs. queue empty). The `breakdown.actionable` property partially addresses this by excluding workflow items, but does not exclude subjective items. The lifecycle filter in `build_work_queue` does filter endgame-only subjective items, but only during queue building, not during the score-freezing or plan-cycle-clearing checks.

## Summary of the inconsistency bugs

**Bug 1 — `_print_score_section` in `status/cmd.py` (line 204):** Gates frozen score on `breakdown.queue_total > 0` instead of `objective_remaining > 0`. When only subjective items remain, it still shows the frozen score. Fix: compute `objective_remaining = breakdown.queue_total - breakdown.subjective - breakdown.workflow` (mirroring the scan path logic at `queue_progress.py:318`) and gate on that.

**Bug 2 — `QueueBreakdown.actionable` (line 49, `queue_progress.py`):** Defined as `queue_total - workflow`, so it still counts subjective items as actionable work. The docstring says "use this when gating on `is there work left?`" — but that guidance is wrong for score-clearing purposes. The `_clear_plan_start_scores_if_queue_empty` function relies on this. Fix: either add a second property `objective_actionable = queue_total - workflow - subjective`, or make `actionable` subtract subjective, and update `_clear_plan_start_scores_if_queue_empty` to match the intended semantics. (Note: the scan preflight also uses `breakdown.actionable` at `preflight.py:64` — that guard probably SHOULD block on subjective remaining, so `actionable` behavior there might be correct. Two different consumers with different needs.)

**Bug 3 — `_clear_plan_start_scores_if_queue_empty` (line 137, `plan_reconcile.py`):** Relies on `breakdown.actionable == 0`. Because `actionable` includes subjective, the cycle never completes while subjective items remain in the queue, even if all objective work is done. This keeps `plan_start_scores` populated indefinitely, blocking the post-scan score reveal.

**The core tension:** The scan preflight (`preflight.py:64`) legitimately wants to block on `actionable` including subjective items — you should finish your subjective work before rescanning. But score-clearing and score-display need to distinguish "objective done, subjective pending" from "everything done." These need separate properties or explicit arithmetic at the call sites.
