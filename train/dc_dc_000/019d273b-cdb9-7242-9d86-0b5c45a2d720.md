        # Implementation Plan: Migrate ALL Task Creation Logic to Server-Side Resolvers

## Overview

**Current state:** The `create-task` edge function (`supabase/functions/create-task/`) is intentionally thin — it authenticates, checks project ownership, and INSERTs an opaque `params` blob into the `tasks` table. All validation, default application, resolution calculation, LoRA formatting, ID generation, seed normalization, and payload composition happens **client-side** across ~15 files in `src/shared/lib/tasks/` and `src/shared/lib/taskCreation/`.

**Goal:** Move all param-building logic into server-side "resolvers" inside the edge function. Clients send raw/minimal inputs; the server does validation, defaults, resolution lookup, LoRA formatting, ID generation, and final payload composition. Add batch support (N tasks from 1 request). No backward compatibility needed.

**Scope:** 6 task families in `src/shared/lib/tasks/families/` plus 4 non-family creators (travelBetweenImages, magicEdit, maskedEdit, crossfadeJoin). ~2500 lines of client-side logic to move. ~12 caller hooks/services to simplify.

**Constraints:**
- Edge function runs in Deno (Supabase Edge Functions). No access to Vite, React, or browser APIs.
- Edge function already has `supabaseAdmin` — can do DB queries (resolution lookup, parent generation, segment routing) more cleanly than client.
- Workers expect specific `params` shapes — resolver output must match current worker expectations exactly.
- Batch tasks currently fire N parallel HTTP requests; new batch support = single request → N inserts.

**Key DB queries that move server-side:**
1. `resolveProjectResolution()` — queries `projects.aspect_ratio` (already queried for ownership check — can piggyback)
2. `ensureShotParentGenerationId()` — calls RPC `ensure_shot_parent_generation`
3. `resolveSegmentGenerationRoute()` — queries `shot_generations` for child generation IDs

## Phase 1: Foundation — Edge Function Architecture

### Step 1: Design resolver interface and request schema
**Scope:** Small
1. **Define** the new request contract in `supabase/functions/create-task/resolvers/types.ts`:
   - `ResolveRequest`: `{ family: string, project_id: string, input: Record<string, unknown>, batch_count?: number }`
   - `ResolverContext`: `{ supabaseAdmin, projectId, logger }` — shared deps injected into every resolver
   - `ResolverResult`: `{ tasks: TaskInsertObject[] }` — one or more tasks to insert
   - `TaskFamilyResolver`: `(input, context) => Promise<ResolverResult>`
2. **Decision:** Keep the existing raw `{ params, task_type }` path alive during migration (feature-flagged by presence of `family` field), so families can be migrated one at a time without coordinating client+server deploys.

3. **Port** seed utilities into `resolvers/shared/seed.ts`:

### Step 3: Add batch insert support to edge function
**Scope:** Medium
1. **Modify** `supabase/functions/create-task/index.ts` to handle resolver results that produce multiple `TaskInsertObject`s.
2. **Use** `.insert(arrayOfObjects)` instead of `.insert(singleObject)` for batch — Supabase supports array insert natively.
3. **Return** `{ task_ids: string[], status: "Tasks queued" }` for batch, `{ task_id: string, status: "Task queued" }` for single — maintain backward compat on response shape.

3. **Pass** `ResolverContext` with `supabaseAdmin`, `finalProjectId`, `aspectRatio` (from the extended project query), and `logger`.

### Step 5: Validate foundation with a smoke test
**Scope:** Small

## Overview
