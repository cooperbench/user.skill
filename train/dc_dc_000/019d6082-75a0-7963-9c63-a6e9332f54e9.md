## Phase 1: Race Condition Fixes (standalone, safe)

### Step 1: Add pendingOpsRef protection to useClipResize (`hooks/useClipResize.ts`)
**Scope:** Small
1. **Inspect** `hooks/useClipResize.ts` — confirmed: no `pendingOpsRef` usage. Compare with `useClipDrag.ts` which increments on pointer down (line 432) and decrements on session clear (line 148).
2. **Add** `pendingOpsRef` to `UseClipResizeArgs` interface (line 8-11).
3. **Increment** `pendingOpsRef.current` in `onActionResizeStart` (line 25) before storing origin state.
4. **Decrement** `pendingOpsRef.current` in `onActionResizeEnd` (line 39) after `applyEdit` completes, and also on early returns (uploading- prefix, missing clipMeta).
5. **Wire** the ref through from `useTimelineState.ts` line 275-278 where `useClipResize` is called — pass `pendingOpsRef: dataHook.pendingOpsRef`.
6. **Edge case**: If `onActionResizeStart` is called for an uploading clip or hold clip (early return at lines 26-30), don't increment. Only increment when we actually store origin state.

### Step 2: Protect useExternalDrop during async operations (`hooks/useExternalDrop.ts`)
**Scope:** Small
1. **Inspect** `hooks/useExternalDrop.ts` — confirmed: no `pendingOpsRef` usage during async file upload processing.
2. **Add** `pendingOpsRef` to the hook's args interface.
3. **Increment** `pendingOpsRef.current` at the start of drop processing (when `onTimelineDrop` fires, before async work begins).
4. **Decrement** in a `finally` block after all drop processing completes (file uploads, applyEdit calls).
5. **Wire** through from `useTimelineState.ts` line 291-307.

### Step 3: Audit useAssetManagement concurrent drops (`hooks/useAssetManagement.ts`)
**Scope:** Medium
1. **Inspect** `handleAssetDrop` — confirmed: reads `dataRef.current`, may create tracks, then calls `applyEdit`. Multiple concurrent calls can race on track creation.
2. **Fix**: The issue is that `handleAssetDrop` mutates `dataRef.current` to create a track, then reads it again for the clip drop. If two calls both decide to create a track simultaneously, the second overwrites the first's track creation. 
3. **Solution**: Move the track-creation-if-needed logic into a single `applyEdit` call that handles both track creation and clip insertion atomically. If `applyEdit` already handles row+track updates, the fix is to include the new track in the same edit payload rather than mutating `dataRef` directly.
4. **Alternative simpler fix**: If the multi-drop path in `useExternalDrop` calls `handleAssetDrop` in a loop, the loop should `await` each call or at minimum ensure each `applyEdit` completes before the next starts. Check whether `applyEdit` is synchronous (updates `dataRef.current` immediately) — if so, the sequential loop may already be safe as long as we don't have fire-and-forget async between calls.

### Step 4: Audit undo/redo during save (`hooks/useTimelineHistory.ts`)
**Scope:** Small
1. **Inspect** the interaction between `onBeforeCommit` (called before each commit) and `undo`/`redo` (which themselves call `commitData`).
2. **Confirmed low severity**: The `skipHistory: true` flag on undo/redo commit prevents infinite recursion. The redo-stack-clearing issue (redo cleared by save's onBeforeCommit if save completes during undo) is a rare timing bug.
3. **Fix**: Add a guard in `onBeforeCommit` — if an undo/redo operation is in flight (track via a ref flag), skip the redo-stack clear. This prevents the save's commit from destroying the redo stack during an undo operation.

### Step 12: Replace ref-wiring with a TimelineEventBus (`hooks/useTimelineEventBus.ts`)
**Scope:** Medium
1. **Create** a tiny event bus (~30 lines) using a Map of event name → Set of listeners. Three events:
   - `saveSuccess` — currently wired via `onSaveSuccessRef` (triggers `render.setRenderDirty(true)`)
   - `beforeCommit` — currently wired via `onBeforeCommitRef` (calls `history.onBeforeCommit`)
   - `pruneSelection` — currently wired via `pruneSelectionRef` (calls `pruneSelection`)
2. **Create** via `useRef(new TimelineEventBus())` in `useTimelineState`, pass to child hooks.
3. **In useTimelineSave**: emit `beforeCommit` instead of calling `onBeforeCommitRef.current?.()`; emit `pruneSelection` instead of calling `pruneSelectionRef.current?.()`.
4. **In useTimelineState**: subscribe history.onBeforeCommit to `beforeCommit`, render.setRenderDirty to `saveSuccess`, pruneSelection to `pruneSelection`.
5. **Benefit**: Eliminates 3 mutable refs + 2 useLayoutEffect wiring blocks. Hooks declare what events they emit; subscribers are registered in one place.

### Step 13: Eliminate the dataHook adapter object (`hooks/useTimelineState.ts:86-136`)
**Scope:** Medium

Downstream hooks then destructure it again.
2. **Fix**: Change downstream hooks (`useClipEditing`, `useClipResize`, `useAssetManagement`, `useExternalDrop`, `useTimelineTrackManagement`, `useDragCoordinator`) to accept the specific values they need directly, rather than accepting `UseTimelineDataResult` sub-properties.

4. **Remove** the `UseTimelineDataResult` type from `useTimelineData.types.ts` once no hook depends on it.
5. **Benefit**: Eliminates 50 lines of pure wiring and a fragile god type.
