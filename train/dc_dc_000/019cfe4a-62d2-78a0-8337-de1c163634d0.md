**Findings**
1. High: the plan misses a whole client submission path. It focuses on the provider-backed shot editor, but the separate modal flow still builds WAN-shaped requests directly. [`BatchModeContent.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/sections/generation/BatchModeContent.tsx#L87) is only one surface; [`VideoGenerationModalSections.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/VideoGenerationModalSections.tsx#L162) and [`useVideoGenerationModalController.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/hooks/useVideoGenerationModalController.ts#L314) still assume WAN basic-phase behavior and never pass a selected LTX model. If you ship only the planned editor changes, modal submissions will stay inconsistent.

2. High: the “store per-model substate in the provider” part is underspecified and probably won’t persist the way the plan claims. The provider is just a wrapper around `useShotSettings`; it has no independent persisted model state of its own in [`VideoTravelSettingsProvider.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/providers/VideoTravelSettingsProvider.tsx#L92). The persisted schema in [`settings.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/settings.ts#L41) only has a single `selectedModel` field, and normalization only accepts `'wan-2.1' | 'wan-2.2'` in [`settings.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/settings.ts#L259). So “restore each model’s last-used settings across page navigation” needs a real persisted structure, not just provider logic.

3. Medium: the LoRA step is incomplete. The plan lists two hardcoded WAN-only modal callsites, but shared phase-config components also hardcode WAN filters, so advanced/preset flows will still show the wrong catalog under LTX. See [`ModalsSection.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/sections/ModalsSection.tsx#L43), [`VideoGenerationModal.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/VideoGenerationModal.tsx#L130), [`PhaseConfigVertical.tsx`](/Users/user_c042661f/Documents/reigh/src/shared/components/PhaseConfigSelectorModal/PhaseConfigVertical.tsx#L82), and [`PhaseConfigSection.tsx`](/Users/user_c042661f/Documents/reigh/src/shared/components/PhaseConfigSelectorModal/components/sections/PhaseConfigSection.tsx#L379). The filter utility is also WAN/Qwen/Z-Image-only today in [`filter-utils.ts`](/Users/user_c042661f/Documents/reigh/src/domains/lora/components/LoraSelectorModal/utils/filter-utils.ts#L4).

4. Medium: the FPS/frame-quantization work is broader than the plan suggests. The utility layer is globally WAN-biased in [`videoUtils.ts`](/Users/user_c042661f/Documents/reigh/src/shared/lib/media/videoUtils.ts#L3), and there are multiple shared consumers that call it without any model/fps context, not just the batch settings slider in [`BatchSettingsForm.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/BatchSettingsForm.tsx#L367). Examples include [`PairRegion.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/Timeline/PairRegion.tsx#L156), [`TimelineBottomControls.tsx`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/Timeline/TimelineContainer/components/TimelineBottomControls.tsx#L55), and [`PresetBrowseCard.tsx`](/Users/user_c042661f/Documents/reigh/src/shared/components/PhaseConfigSelectorModal/components/PresetBrowseCard.tsx#L224). Changing the helper signature alone will not make the UI correct.

5. Medium: deferring readback/model restoration is riskier than the plan frames it. The current apply-settings path still treats raw `model_name` as the source of truth in [`generationSettingsService.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/generationSettingsService.ts#L15), task extraction still misses orchestrator-side LTX params in [`taskDataService.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/applySettings/taskDataService.ts#L98), and `useSteerableMotionHandlers` still rewrites `steerableMotionSettings.model_name` from `turboMode` in [`useSteerableMotionHandlers.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/hooks/actions/useSteerableMotionHandlers.ts#L103). That means you can end up with contradictory persisted state even if submission itself works.

**Overall**
Worker-side, the plan is directionally sensible if its assumptions are true: the request builder already emits top-level travel params in [`requestBody.ts`](/Users/user_c042661f/Documents/reigh/src/tools/travel-between-images/components/ShotEditor/services/generateVideo/requestBody.ts#L82), those get copied into `orchestrator_details` in [`payloadBuilder.ts`](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/travelBetweenImages/payloadBuilder.ts#L264), and the task family already routes through `travel_orchestrator` unless `turbo_mode` flips it in [`createTravelBetweenImagesTask.ts`](/Users/user_c042661f/Documents/reigh/src/shared/lib/tasks/travelBetweenImages/createTravelBetweenImagesTask.ts#L51). So the core “send `model_name` + LTX params and let the worker do the rest” story does make architectural sense.
