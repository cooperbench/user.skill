# Plan 5 — Scheduled jobs + decay + pause/resume + crisis polish

Authoritative spec: `mediator-bot-spec.md`. Read in prep, focusing on: "Triggers" (scheduled), "Decay", "Multi-Message Handling" (restart recovery for jobs), "Pause / Resume", "Crisis Handling", "WhatsApp 24-Hour Window" for templates, and the bits of "Operations" related to scheduled jobs.

Plans 1–4 are assumed complete. The system can take messages, run the loop with real OOB and scoring, and produce outbounds. This plan adds the time-based behaviors and the global controls (pause, crisis escalation) that the spec describes.

## Scope (in)

### Scheduled-job worker
- A single async worker (background task in the FastAPI app, or a separate Railway worker process — pick whichever is cleaner; document the choice).
- Polls `scheduled_jobs` for `status='pending' AND scheduled_for <= now()` using `SELECT ... FOR UPDATE SKIP LOCKED` so two workers can't fire the same job. Each job has a unique ID for idempotency.
- On fire: invoke the appropriate handler, then mark `status='fired'`, set `fired_at`. On handler error: log and leave the job pending for one retry, then mark `status='cancelled'` with a reason.

### Job types
- `weekly_summary` — per partner. Renders the Meta-approved `weekly_summary` template ("Hi {{1}}, this week we had {{2}} conversations and touched on {{3}} ongoing things. Want to talk through anything? Just ask."). Sends via `send_outbound` (which handles 24h window). Also performs the decay housekeeping pass (below). Schedule recurrences on completion (one new job per partner per week, configurable timing per user).
- `checkin` — variable check-in (4–24h, the loop chose the timing). One pending per user max. Inserting a new one supersedes any existing pending check-in for that user (mark old one `status='superseded'`). On fire: triggers the agentic loop with a `trigger_metadata={"kind": "checkin", "context": ...}` so the loop can produce a context-aware nudge or, if outside the 24h window, send the `checkin_nudge` template.
- `watch_item_due` — fires when a watch item's `due_at` arrives. Surfaces it next time the owner is in conversation, OR creates a `checkin` job at a near-future time so the bot proactively raises it. Pick one based on whether the owner is currently in the 24h window.
- `oob_review` — when an OOB's `review_at` hits. Triggers the loop with metadata so the bot asks the owner if it's still off-limits.

### Late-job handling on restart
- On startup: scan `scheduled_jobs` with `status='pending' AND scheduled_for < now()`:
  - Less than 1h late → fire normally.
  - 1–24h late → fire with `context.delayed = true` so the bot can adjust ("I meant to send this earlier...").
  - More than 24h late → mark `cancelled` with reason `"too stale"`.
- This is in addition to message-recovery from Plan 2.

### Decay housekeeping (runs inside the weekly summary job)
- Themes with no `last_active_at` update for 6+ weeks → `dormant`.
- Themes dormant 4+ months → `resolved_by_time`.
- Observations not reinforced for 3+ months → confidence drops one level (high→medium→low). Not reinforced for 6+ months → `stale`.
- Watch items past `due_at` with no addressing for 30+ days → `expired`.
- `last_reinforced_at` (not `last_active_at`) drives observation/theme decay; verify the queries reflect that.
- Also run the re-scoring pass for observations flagged `needs_rescoring=true` from Plan 4.

### Query-level decay
- Add a `recency_weighted_score(significance, last_reinforced_at)` SQL function or app-side helper. Formula per spec: `significance / (1 + age_days / 60)` where `age_days = EXTRACT(EPOCH FROM (now() - COALESCE(last_reinforced_at, created_at))) / 86400`. ~60-day effective half-life. Pure SQL, no exp() needed.
- Update the read tools' default sorts to use it. Older content remains searchable but is deprioritized in default surfacing.

### Timezone handling
- Owner-bound scheduled jobs use the owner's `users.timezone`. The recurring `weekly_summary` fires at 09:00 in the owner's local time on the configured day.
- `schedule_checkin` writes absolute UTC instants — the agentic loop converts "in 8 hours" / "tomorrow morning" to UTC at write time using the owner's timezone (timezone-aware datetime math, not naive arithmetic).
- Heartbeat and other non-user-bound jobs use UTC.

### Pause / Resume
- `/pause` slash command (literal `/pause` in inbound text — this is the only slash command per spec): on receipt from either user:
  - Cancel all pending scheduled jobs for both users (`status='superseded'`).
  - Set a global `paused_at` flag (one row in a small `system_state` table — create the table here).
  - Send pause confirmation outbound to each partner via the `pause_confirmation` template (works inside or outside 24h window).
  - The `paused_for_user(user_id)` hook from Plan 2 now reads from `system_state` and returns True when paused.
- `/resume` from either partner:
  - Clear `paused_at`.
  - Do NOT auto-process backlog — just re-enable inbound processing.
  - Restore weekly summary scheduling (insert next `weekly_summary` jobs).

### Crisis handling polish
- The system prompt already (from Plan 3) instructs the loop to drop the mediator role and consider `escalate_to_partner`. This plan tightens the escalation flow:
  - **Concrete gate per spec:** `escalate_to_partner` may only be called when (a) the triggering message meets the `crisis` charge definition, OR (b) the user explicitly asks the bot to alert their partner. The tool input requires `is_crisis: bool` and a named `reason`. Reject any call that doesn't satisfy one of these triggers — the orchestrator validates before sending. This guard is in addition to the prompt-level instruction.
  - `escalate_to_partner` writes a distinguished `bot_turns.reasoning` entry and triggers an outbound to the OTHER partner using the `escalation` template — including outside the 24h window.
  - The `{{3}}` parameter is filled by the bot with a deliberately vague contextual line per spec ("They're going through a hard moment", etc.).
  - Logs the escalation with sufficient detail for retro audit (admin view in Plan 6 will surface it).
- For acute crisis: the bot also surfaces region/language-appropriate emergency resources directly to the affected partner in the conversational outbound. Tested with a deterministic mock LLM.

### Heartbeat upgrade
- Plan 1 left a heartbeat stub. Implement it now as a periodic `scheduled_jobs` row of type `heartbeat` that fires daily and writes a log line; alerts on its absence are external (admin doc).

## Scope (out, deliberately)
- Admin UI surfaces for jobs/escalations (Plan 6).
- Onboarding welcome flow (Plan 6).
- Feedback collection (Plan 6).
- Anything related to actual emergency resource curation — the spec is explicit that the LLM uses common sense for region/language; no static resource list to maintain here.

- `must`: Decay transitions (theme dormant/resolved_by_time, observation confidence drop/stale, watch items expired) execute correctly against synthetic time-traveled fixtures.
- `should`: `FOR UPDATE SKIP LOCKED` poll is verified by a concurrent-worker test.
- `should`: Recency-weighted sort is applied in default tool reads.
- `info`: `rescore_observations` is invoked from the housekeeping pass.

## Notes

        # Implementation Plan: Scheduled Jobs, Decay, Pause/Resume, and Crisis Polish

## Overview
The repo already has the core FastAPI lifecycle, WhatsApp inbound persistence, debounced agentic turns, outbound 24-hour template routing, scheduled check-in write tools, OOB checks, observation scoring, and a heartbeat stub. The main gap is turning `scheduled_jobs` into a real runtime system and wiring global controls around it.

I would implement the scheduler as an in-process FastAPI background task in `app/main.py`, not a separate Railway process. That is the smallest deployment change, and `SELECT ... FOR UPDATE SKIP LOCKED` still keeps it safe if Railway later runs multiple replicas. The worker logic should live in a separate service module so it can be unit-tested without app startup.

## Phase 1: Database and Configuration Foundation

### Step 1: Add Plan 5 migration (`migrations/0004_plan5_scheduled_jobs.sql`)
**Scope:** Medium
1. Add `system_state` as a singleton keyed table for `paused_at`, `paused_by_user_id`, and `updated_at`.
2. Extend `scheduled_jobs.job_type` to include `heartbeat`.
3. Add cancellation metadata to `scheduled_jobs`: `cancelled_reason text`, `attempt_count int default 0`, and optionally `last_error text`.
4. Add `needs_rescoring boolean not null default false` to `observations`, because Plan 5 references it but current code only infers rescoring from prompt version or failed scoring.
5. Add pure SQL function `recency_weighted_score(significance integer, last_reinforced_at timestamptz, created_at timestamptz)` implementing `significance / (1 + age_days / 60)`.
6. Add indexes needed by the worker and housekeeping: pending jobs, `needs_rescoring`, open watch item due dates, and singleton `system_state` policy/RLS entries consistent with existing migrations.

### Step 2: Add scheduler settings (`app/config.py`)
**Scope:** Small
1. Add conservative env-backed settings: poll interval, batch size, worker enabled flag, weekly summary day/time defaults, and heartbeat interval.
2. Keep per-user weekly timing extensible via job context first, avoiding a users table schema change unless the product owner confirms dedicated per-user fields.

## Phase 2: Scheduler Runtime

### Step 3: Create scheduled job service (`app/services/scheduled_jobs.py`)
**Scope:** Large
1. Implement `ScheduledJobWorker` with a polling loop and a one-shot `run_due_once(now=...)` entry for tests.
2. Claim pending due jobs inside a transaction using `SELECT ... FOR UPDATE SKIP LOCKED`, increment `attempt_count`, then dispatch by `job_type`.
3. On success, mark jobs `fired`, set `fired_at`, and schedule recurrence where required.
4. On first handler error, leave the job `pending` with incremented `attempt_count` and `last_error`; on second failure, mark `cancelled` with a reason.
5. Check the global pause flag before dispatch. While paused, skip normal user-bound jobs instead of firing them. Let `heartbeat` continue because it is operational, not user-facing.

### Step 4: Replace heartbeat stub (`app/main.py`)
**Scope:** Small
1. Remove the current `heartbeat_loop()` logger-only task.
2. Start the scheduled job worker in the FastAPI lifespan after `recover_on_startup()`.
3. Ensure shutdown cancels and awaits the worker task like existing background tasks.
4. On startup, seed a pending `heartbeat` row if none exists.

### Step 5: Add startup late-job recovery (`app/services/recovery.py`)
**Scope:** Medium
1. Extend `recover_on_startup()` to scan pending scheduled jobs older than `now()`.
2. More than 24h late: mark `cancelled` with reason `too stale`.
3. Less than 1h late: leave eligible for normal worker firing.
4. Between 1h and 24h late: merge `{"delayed": true}` into `context`, then leave eligible for worker firing.
5. Keep this recovery separate from raw-message recovery so tests can assert each behavior independently.

## Phase 3: Job Handlers

### Step 6: Implement weekly summary handler (`app/services/scheduled_jobs.py`, `app/services/templates.py`)
**Scope:** Large
1. Fetch the target user and compute the last-week conversation count and touched theme count with simple SQL.
2. Send through `send_outbound()` using `TemplateCall("weekly_summary", [user.name, count, theme_count])` so 24-hour-window routing stays centralized.
3. Run housekeeping in the same handler after the send attempt.
4. Schedule the next weekly summary at 09:00 in the owner’s timezone, using timezone-aware `zoneinfo` conversion to UTC.
5. Add a helper to seed/restore weekly summaries for all users, used on startup and `/resume`.

### Step 7: Implement housekeeping and decay (`app/services/decay.py`)
**Scope:** Large
1. Move periodic transitions into a focused module with `run_decay_housekeeping(pool, now=...)`.
2. Themes with no `last_active_at` update for 6+ weeks become `dormant`.
3. Dormant themes whose dormant transition is 4+ months old become `resolved_by_time`; if no `dormant_at` column is added, use `updated_at` from the dormant transition.
4. Observations use `COALESCE(last_reinforced_at, created_at)`, not `last_active_at`: 3+ months drops confidence one level, 6+ months marks `stale`.
5. Watch items open and `due_at < now() - interval '30 days'` become `expired`.
6. Call `scoring.rescore_observations()` for failed/old scores and rows flagged `needs_rescoring=true`, then clear the flag on success.

### Step 8: Implement check-in, watch item, OOB review, and heartbeat handlers (`app/services/scheduled_jobs.py`)
**Scope:** Large
1. `checkin`: call a new job-trigger entry point in `agentic.py` with `trigger_metadata={"kind":"checkin", "context": ...}`. If outside the 24-hour window and no free-form output can be sent, use `checkin_nudge` template.
2. `watch_item_due`: if the owner is inside the WhatsApp window, trigger the agentic job entry point with the watch item context; otherwise insert a near-future `checkin` and supersede any pending check-in for that user.
3. `oob_review`: trigger the agentic job entry point with metadata naming the OOB entry and `delayed` context if present.
4. `heartbeat`: write the log line, mark fired, and schedule the next daily heartbeat row.

### Step 9: Add job-triggered agentic turns (`app/services/agentic.py`, `app/services/hot_context.py`)
**Scope:** Medium
1. Add `run_agentic_job(user, trigger_metadata)` for scheduler-triggered turns without inbound message IDs.
2. Allow `bot_turns.triggered_by_message_id` to remain null and `triggering_message_ids` to be empty for scheduled triggers.
3. Extend hot context construction to accept explicit trigger metadata rather than only deriving it from message rows.
4. Keep normal inbound processing unchanged.
