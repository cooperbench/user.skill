# InboundScope refactor — eliminate bot_id leaks across the inbound→outbound path

## Why this exists

The Veas codebase is being extended from a single-bot mediator (Véas) to a multi-bot platform. The second bot, Tante Rosi (German pregnancy coach, solo-shape, Discord-only), keeps misrouting: messages sent to Rosi get processed and replied by Véas, with the wrong persona, language, and topic.

We've now patched the *same shape of bug* three times in rapid succession:

1. `app/services/inbound.py::_resolve_scope` had `bot_id: str = "mediator"` as a silent default → inbound rows tagged with the wrong bot. (Fixed in commit `5a38d7f`.)
2. `app/main.py` constructed a single `app.state.coalescer` with `bot_id="mediator"` captured in closures used as the dispatch callback. The burst data structure already carried the correct per-event bot_id, but the closure ignored it. (Fixed in commit `f29bc03` by moving to `app.state.coalescers: dict[str, BurstCoalescer]` and resolving topic via `get_bot_spec(bot_id) + primary_topic_id_for(pool, spec)`.)
3. `app/services/recovery.py`, `app/services/vision.py`, `app/services/transcription.py` still hardcode `bot_id='mediator'` in their own outbound calls. (Not yet fixed.)

After both patches (1) and (2) were on `main`, the user reports the wrong bot is **still responding**. So there is at least one more leak we haven't characterised yet, plus the three known hardcodes above.

**This is no longer a patching problem — it's a structural one.** Each fix surfaces another instance of the same shape because `bot_id` was bolted onto a codebase that was written assuming a single mediator. It rides through the system as a loose parameter: sometimes a function arg, sometimes a closure capture, sometimes a DB column, sometimes a default. The boundary between "this code knows its bot" and "this code looks it up" is fuzzy and inconsistent.

## What we want

Introduce a single explicit **`InboundScope`** dataclass (frozen) that:

- Is constructed **once** at each gateway boundary (Discord `_handle_message`, Discord `_handle_reaction_add`, Discord `catch_up_recent_messages`, WhatsApp router).
- Carries **all per-event identity**: `bot_id`, `transport`, `user_id` (sender), `topic_id`, `channel_id`, `binding_id`, `dyad_id` (None for solo-shape bots like Rosi).
- Threads explicitly through every downstream code path: `process_inbound` → coalescer → burst dispatch → agentic turn → LLM tools → outbound (text, voice, image) → DB writes.
- **Replaces** the existing loose `bot_id` kwarg pattern. No function below the gateway accepts `bot_id` as an optional kwarg with a `"mediator"` default. Forgetting to pass scope becomes a type error.

The existing `ResolvedScope` NamedTuple in `app/services/inbound.py` (around line 161) is the seed of this — it already has `(bot_id, topic_id, channel_id, binding_id, dyad_id)`. **Promote it to a frozen dataclass, add `transport` and `user_id`, rename to `InboundScope`, and make it the universal carrier.**

There is also an existing `app/services/turn_context.py` — investigate during prep whether it already plays a related role and whether it should be merged with / replaced by `InboundScope`, or whether they have distinct responsibilities (per-event identity vs per-turn execution context).

## Overview

**Goal.** Replace the loose `bot_id` kwarg/default pattern across the inbound-to-outbound path with a frozen `InboundScope` dataclass constructed at gateway or reconstruction boundaries and passed explicitly through `process_inbound` -> coalescer -> agentic turn -> tools -> outbound.
