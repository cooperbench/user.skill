> AGENT

I compared the old [`peteromallet/VibeComfy`](https://github.com/peteromallet/VibeComfy) with the local new version.

The old project was an agent-facing ComfyUI JSON/MCP toolkit: inspect UI workflow JSON, trace nodes, query paths, wire/copy/delete/set nodes, batch edit, visualize/layout, submit to a running ComfyUI server, and search a large cached node registry.

The new version is a cleaner runtime/scratchpad system: `workflow source -> VibeWorkflow -> Python scratchpad -> Comfy API dict -> run`, with embedded/server execution, validation, template indexing, GraphBuilder parity, and local run logs.

**Worth Porting**
1. **Workflow graph analysis commands**
   Port the old `trace`, `upstream`, `downstream`, `path`, `subgraph`, `values`, `diff`, and richer `analyze` behavior into the new `VibeWorkflow` layer.

   The new CLI currently has only `inspect`, `validate`, `doctor`, `run`, `logs`, source indexing, and simple list commands in [vibecomfy/cli.py](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/vibecomfy/cli.py:1). The old analysis engine has useful agent ergonomics that are missing.

2. **Readable workflow summaries**
   The old `comfy_read` style output is highly valuable: pattern, key params, variables, loops, flow, stats. This should become something like:

   ```bash
   vibecomfy analyze workflow.json
   vibecomfy explain workflow.py
   ```

   It fits the new approach well because it can operate on `VibeWorkflow` after normalization.

3. **Registry/search layer**
   The old MCP registry searched thousands of nodes with aliases like `i2v`, `controlnet`, `audio reactive`, `wan`, `ltx`, etc. The new repo has `nodes list`, `sources sync`, and runtime `/object_info` indexing, but not semantic search.

   Port the concept, not necessarily the exact cache. Best fit: build `vibecomfy nodes search "audio reactive"` over:
   - runtime `/object_info`
   - indexed custom node examples
   - curated direct templates
   - optional remote registry scrape later

4. **Better UI-to-API widget mapping**
   The old `convert_to_api_format` used `/object_info` to map `widgets_values` to real input names. The new [normalize.py](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/vibecomfy/templates/normalize.py:1) already tries `comfy.component_model.workflow_convert`, but the fallback stores unmapped widgets as `widget_0`, `widget_1`, etc. Porting the old `/object_info` fallback would make conversion much more useful when HiddenSwitch’s converter is unavailable.

5. **Dry-run edit operations**
   The old `copy`, `wire`, `set`, `delete`, and `batch --dry-run` features are useful, but they should be reimagined on top of `VibeWorkflow`, not copied as raw JSON patching. The new design explicitly says JSON is not the patching surface in [docs/vibeworkflow.md](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/docs/vibeworkflow.md:1).

**Maybe Port Later**
- `visualize` and `layout`: useful, but less core than graph analysis/search. Visualization should probably target `VibeWorkflow` and emit Graphviz/SVG from the normalized graph.
- `fetch node source from GitHub`: useful for custom node development, but it is more of an assistant/developer power feature than a first milestone runtime feature.
- Claude skill/MCP packaging: the old MCP server was valuable, but the new core should probably expose solid CLI/library APIs first, then wrap them as MCP.

**Do Not Port Wholesale**
- The old direct UI JSON editing model should not become the main editing path. It conflicts with the new architecture’s central idea: `VibeWorkflow` and Python scratchpads are the editable layer.
- The old submit/logs flow is mostly superseded. The new runtime surface is stronger because embedded mode waits for completion and returns output metadata, as described in [docs/runtime_surface.md](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/docs/runtime_surface.md:1).

**Recommended Port Order**
1. Add `vibecomfy analyze`, `trace`, `upstream`, `downstream`, `path`, and `diff` against `VibeWorkflow`.
2. Improve UI fallback normalization using runtime `/object_info`.
3. Add `vibecomfy nodes search` with alias expansion.
4. Add safe edit helpers/dry-run on `VibeWorkflow`.
5. Add visualization/MCP wrappers once the core APIs are stable.

Bottom line: the old project’s best assets are its agent-facing workflow understanding and node discovery features. The new project’s architecture is better, so those features should be ported as `VibeWorkflow` capabilities rather than by reviving the old raw JSON editor.

   `vibecomfy/nodes/search.py`
   `vibecomfy/nodes/knowledge.py`

   workflow.connect("4.0", "9.image")

   ```bash
   vibecomfy edit set workflow.py 7 steps=20 --out out/edit.py
   vibecomfy edit connect workflow.py 4.0 9.image --out out/edit.py
   ```

   For scratchpads, there is a design question: should edits output JSON, a modified scratchpad, or a patch snippet? I’d start with library methods and analysis commands before locking this down.

**What I Would Do First**
The most natural first port is **analysis**, because it plugs into the new architecture with low risk.

New flow:

```text
JSON or scratchpad -> VibeWorkflow -> analysis helpers -> CLI/MCP output
```

That avoids UI JSON coupling and immediately improves the new project.

The next port should be **better conversion using `/object_info`**, because it makes everything else more reliable. Right now fallback normalization may produce `widget_0`, `widget_1`; the old project’s schema-aware widget mapping is directly useful here.

Then add **node search** as a pluggable index over local/runtime sources.

**Suggested Internal API**
Something like this would fit:

```python
from vibecomfy.analysis import analyze, trace, upstream, downstream, diff
from vibecomfy.nodes.knowledge import NodeKnowledge
from vibecomfy.editing import WorkflowEditor
```

The CLI calls those. Future MCP calls those. Tests call those. Nothing important lives only in CLI command handlers.

**Straight Port vs Plugin**
I would not make these “plugins” at first if by plugin you mean separately loaded extension modules. That adds coordination cost before the core shape is proven.

But I would make them **plug-in shaped internally**:

- analysis accepts any `VibeWorkflow`
- node knowledge accepts index providers
- normalization can optionally use runtime schema providers
- future MCP is an adapter, not a second implementation

So: **integrated modules with adapter seams**, not a full plugin system yet.

The port order I’d choose:

1. `vibecomfy.analysis`: graph traversal and readable summaries.
2. Schema-aware normalization fallback using `/object_info`.
3. `vibecomfy nodes search/spec`.
4. `VibeWorkflow` edit helpers.
5. CLI edit commands and batch scripting.

I’d add a schema abstraction:

```text
vibecomfy/nodes/schema.py
```

Possible API:

```python
class NodeSchemaProvider:
    def get(self, class_type: str) -> NodeSchema | None:
        ...
```

Implement providers:

```text
RuntimeObjectInfoProvider       # from /object_info
LocalNodeIndexProvider          # from node_index.json
CompositeSchemaProvider         # tries several
NullSchemaProvider              # fallback
```

Then use this in:

- UI-to-API normalization
- trace formatting
- node search/spec
- validation
- edit validation

This avoids duplicating `/object_info` handling in every feature.

The port here is not “copy old converter.” It is “extract the schema-aware idea and make it part of the new conversion pipeline.”

- runtime `/object_info`
- `node_index.json`
- direct templates
- custom node examples
- maybe a future remote registry scrape
- maybe curated aliases/patterns

vibecomfy/nodes/knowledge.py
vibecomfy/nodes/search.py
vibecomfy/nodes/aliases.py

vibecomfy nodes spec KSampler

vibecomfy nodes packs

ALIASES = {

**4. Editing Layer**

But the old implementation edited ComfyUI UI JSON directly. The new docs explicitly say `VibeWorkflow` is the editable IR. So direct porting would undermine the new approach.

Possible lower-level API:

```python
workflow.add_node("KSampler", seed=1, steps=20)
workflow.delete_node("12")
workflow.copy_node("12")
workflow.connect("1.0", "2.positive")
workflow.disconnect("2.positive")
workflow.set_node_input("2", "steps", 30)

from vibecomfy.editing import WorkflowEditor

editor = WorkflowEditor(workflow)
editor.copy_node("12")
editor.connect("12.0", "15.image")
```

I slightly prefer a separate `WorkflowEditor` initially. It avoids bloating `VibeWorkflow` while the edit API is still evolving.

CLI later:

```bash
vibecomfy edit set workflow.py 12 steps=30 --out out/workflow.py
vibecomfy edit connect workflow.py 12.0 15.image --out out/workflow.py
vibecomfy edit delete workflow.py 44 --dry-run
```

The hard question is output format.

For JSON input, outputting JSON is obvious. For scratchpad input, blindly rewriting Python is not obvious. I see three possible modes:

```text
--out-json       compile edited workflow to API JSON
--out-scratchpad generate a new simple scratchpad from the edited workflow
--print-snippet  print Python calls the user can paste into the scratchpad
```

For early versions, I’d avoid AST-rewriting scratchpads. I’d do:

```bash
vibecomfy edit set scratch.py 12 steps=30 --print-snippet
```

Output:

```python
workflow.nodes["12"].inputs["steps"] = 30
```

Later, once edit patterns stabilize, add scratchpad rewriting.

**5. Adapter Layer: CLI, MCP, Skills**
The old app was very MCP-oriented. That was valuable, but MCP should be an adapter over stable library APIs.

Do this later:

```text
vibecomfy/adapters/mcp.py
```

Expose:

```text
vibecomfy_analyze
vibecomfy_trace
vibecomfy_nodes_search
vibecomfy_nodes_spec
vibecomfy_run
```

But avoid maintaining separate analysis logic in the MCP server. MCP should just call `vibecomfy.analysis` and `vibecomfy.nodes.knowledge`.

**Straight Port vs Plugin**
I would not make these external plugins right now.

A plugin system is useful when:
- third parties need to add behavior independently
- extension boundaries are stable
- the core abstractions are settled

That is not true yet. The migration itself will teach you what the abstractions should be.

But I would make the internals **plugin-shaped**:

```text
Schema providers
Knowledge providers
Runtime providers
Formatters
Analysis result objects
```

That gives you extension points without committing to a plugin system.

**Recommended Implementation Order**
I’d do it in this order because each step supports the next.

1. **Load Any Workflow Helper**

Create a single internal helper that all commands use:

```python
load_workflow_source(path_or_id: str) -> VibeWorkflow
```

It should handle:
- `.json`
- `.py` scratchpad
- template id from indexes

Right now CLI has similar logic split across commands. Analysis/edit/search will need the same loading behavior.

2. **Graph Analysis Module**

Add traversal functions over `VibeWorkflow`.

Start without schema. That gets useful commands quickly:

```bash
vibecomfy trace examples/minimal_api.json 3
vibecomfy upstream examples/minimal_api.json 3
vibecomfy downstream examples/minimal_api.json 1
```

3. **Readable Analysis Report**

Add structured result objects, not just strings:

```python

    node_count: int
    edge_count: int
    type_counts: dict[str, int]
    inputs: list[...]
    outputs: list[...]
    model_loaders: list[...]
    pipelines: list[...]
```

Then format separately.

This matters because CLI wants text, MCP may want markdown, tests want structured assertions, future UI might want JSON.

4. **Schema Provider**

Add object-info/schema abstraction.

Use it first in `normalize_to_api` fallback, then in `trace`.

5. **Node Search**

Build `NodeKnowledge` over existing `node_index.json` and maybe runtime schema. Port aliases from old search. Add CLI commands.

6. **Validation Improvements**

Once schema exists, improve `workflow.validate()`:

- missing source/target node
- edge output/input type mismatch when schema is available
- unknown class type
- missing required inputs
- likely missing model refs
- unknown exposed input targets

Add a small set:

```python

disconnect
delete_node
copy_node
```

Skip batch at first. Batch is attractive, but it locks in syntax before the primitives are mature.

After edit primitives settle, port batch scripting or replace it with Python recipe generation.

A better new-version equivalent might be:

```bash
vibecomfy recipe add-lora workflow.py --lora foo.safetensors --out recipe.py
vibecomfy recipe add-controlnet workflow.py ...
```

For agent workflows, recipes may be more useful than generic batch text.

**Important Design Choice**
The new project should probably distinguish three workflow representations explicitly:

```text
UI JSON       Imported source, preserves layout/widgets where possible
API JSON      Runtime submission format
VibeWorkflow  Editable semantic IR
Scratchpad    Human/agent-authored Python program that builds VibeWorkflow
```

Old VibeComfy blurred UI JSON and editable format. New VibeComfy should not.

So each feature should declare which representation it works on:

```text
normalize: UI/API JSON -> VibeWorkflow
compile: VibeWorkflow -> API JSON
analyze: VibeWorkflow -> report
edit: VibeWorkflow -> VibeWorkflow
render: VibeWorkflow -> scratchpad/API JSON
run: VibeWorkflow/API JSON -> outputs
```

That keeps the architecture clean.

**My Recommendation**
Do not port the old project as a compatibility layer. It would create two tools inside one repo.

Instead, treat the old repo as a feature backlog and port in this architectural order:

Node knowledge/search
Richer validation
VibeWorkflow editing primitives
Recipe/batch layer

```text
Level 1: VibeWorkflow structural validation
Current behavior: node/edge sanity.

Level 2: Schema validation
Use /object_info or cached node schemas to validate class types, required inputs, input names, and rough type compatibility.

Level 3: Runtime prompt validation
Submit/validate against ComfyUI without necessarily running full generation, if the runtime exposes that path.

Level 4: Execution validation
Actually run the workflow and confirm outputs.
```

So yes: if the goal is “can this actual Comfy workflow work?”, then schema/object-info integration should be ported very early. Probably before edit commands.

The old features worth porting first become:

1. `/object_info`-aware node schema mapping.
2. workflow trace using real input/output slot metadata.
3. validation against schema.
4. readable analysis.
5. only then editing.

Yes. If “templates” means **VibeComfy-native reusable workflows**, then they should probably be **Python scratchpad/pseudocode templates**, not raw ComfyUI JSON.

Right now the repo has two different things mixed conceptually:

```text
vendor/direct_templates/*.json   # raw imported ComfyUI UI workflows
examples/*.json                  # small API JSON smoke fixtures
```

Those are useful as **source/import corpus**, but they are not really VibeComfy-native templates.

For the new architecture, the native template should look more like:

```python
from vibecomfy import VibeWorkflow, WorkflowSource

def build():
    workflow = VibeWorkflow(
        id="flux2_text_to_image",
        source=WorkflowSource(id="flux2_text_to_image", source_type="builtin")
    )

    model = workflow.add_node("UNETLoader", unet_name="flux2.safetensors")
    clip = workflow.add_node("DualCLIPLoader", ...)
    prompt = workflow.add_node("CLIPTextEncode", text="a cinematic robot painter")
    sampler = workflow.add_node("KSampler", seed=123, steps=20)
    save = workflow.add_node("SaveImage", filename_prefix="vibecomfy")

    workflow.connect(f"{model.id}.0", f"{sampler.id}.model")
    workflow.connect(f"{prompt.id}.0", f"{sampler.id}.positive")
    workflow.connect(f"{sampler.id}.0", f"{save.id}.images")

    return workflow
```

That is the “pseudocode” layer: human/agent-editable Python that builds a `VibeWorkflow`.

I’d separate them like this:

```text
vibecomfy/templates/builtin/
  flux2_text_to_image.py
  openai_image_inpaint.py
  wan_i2v.py

vendor/direct_templates/
  raw upstream JSON imports

examples/
  tiny smoke fixtures
```

Then template loading should prefer native Python templates:

```python
workflow_from_template("flux2_text_to_image")
```

Under the hood:

```text
builtin .py template -> build() -> VibeWorkflow -> compile() -> Comfy API JSON -> run
```

Raw JSON should remain supported, but as import material:

```text
raw Comfy JSON -> normalize_to_api -> VibeWorkflow -> generated scratchpad
```

So the cleaner distinction is:

- **Raw JSON templates**: imported source workflows, not native.
- **Generated scratchpads**: conversion output under `out/`.
- **Builtin VibeComfy templates**: curated Python templates inside the package.
- **Ready templates**: only templates we have actually schema/runtime validated.

Given current validation is shallow, I would avoid calling anything “ready” until we can prove it against `/object_info` or a runtime.
