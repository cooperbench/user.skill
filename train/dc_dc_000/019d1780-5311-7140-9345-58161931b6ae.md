## Phase 0: Audit & Validate Assumptions (1–2 days)

**Goal:** Confirm the starting state before touching anything.

### Steps

1. **Catalog all tables and classify tenant scope**
   ```sql
   -- Generate table inventory with row counts
   SELECT schemaname, relname, n_live_tup
   FROM pg_stat_user_tables
   ORDER BY n_live_tup DESC;
   ```
   Classify each table as:
   - **Tenant-scoped** — needs `tenant_id` + RLS (e.g., `orders`, `users`, `invoices`)
   - **Global/shared** — no tenant_id needed (e.g., `countries`, `currencies`, `feature_flags`)
   - **Junction** — inherits tenant scope from parent FK

2. **Identify all foreign key chains** — every FK path from a tenant-scoped root must carry `tenant_id` to avoid cross-tenant joins.
   ```sql
   SELECT conrelid::regclass, confrelid::regclass, conname
   FROM pg_constraint WHERE contype = 'f';
   ```

3. **Measure table sizes and bloat** — determines backfill batch sizing.
   ```sql
   SELECT relname, pg_size_pretty(pg_total_relation_size(oid))
   FROM pg_class WHERE relkind = 'r' ORDER BY pg_total_relation_size(oid) DESC LIMIT 20;
   ```

4. **Verify PgBouncer mode** — RLS requires session variables (`SET app.current_tenant`), which only work in **session mode** or with `SET LOCAL` in **transaction mode**.
   ```bash
   grep pool_mode /etc/pgbouncer/pgbouncer.ini
   ```

5. **Check Postgres version supports RLS well**
   ```sql
   SELECT version();
   SHOW row_security;  -- should be 'on' or configurable
   ```

## Phase 1: Add `tenant_id` Column (Non-Blocking DDL)

**Goal:** Add nullable `tenant_id` column to all tenant-scoped tables without locking.

### Steps

1. **Create tenants reference table**
   ```sql
   CREATE TABLE tenants (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     name TEXT NOT NULL,
     slug TEXT UNIQUE NOT NULL,
     created_at TIMESTAMPTZ DEFAULT now()
   );
   ```

2. **Add nullable `tenant_id` to each tenant-scoped table** — `ALTER TABLE ... ADD COLUMN` with a default is non-blocking in PG 11+.
   ```sql
   -- For each tenant-scoped table:
   ALTER TABLE orders ADD COLUMN tenant_id UUID REFERENCES tenants(id);
   -- Nullable initially — enforced NOT NULL after backfill
   ```

3. **Add index CONCURRENTLY** — non-blocking index build.
   ```sql
   CREATE INDEX CONCURRENTLY idx_orders_tenant_id ON orders(tenant_id);
   ```
   For tables where tenant_id will be the leading query filter, consider composite indexes:
   ```sql
   CREATE INDEX CONCURRENTLY idx_orders_tenant_created
     ON orders(tenant_id, created_at DESC);
   ```

### Success Criteria
- [ ] Every tenant-scoped table has `tenant_id UUID` column (nullable)

## Phase 2: Online Backfill of `tenant_id` (Zero-Downtime)

**Goal:** Populate `tenant_id` for all 50M+ existing rows without locking tables or degrading performance.

### Strategy: Batched UPDATE with rate limiting

#### For tables where tenant is derivable from existing data (e.g., `orders.account_id → accounts.tenant_id`):

```sql
-- Backfill in batches of 10,000 rows
WITH batch AS (
  SELECT o.id
  FROM orders o
  WHERE o.tenant_id IS NULL
  LIMIT 10000
  FOR UPDATE SKIP LOCKED
)
UPDATE orders SET tenant_id = (
  SELECT a.tenant_id FROM accounts a WHERE a.id = orders.account_id
)
WHERE id IN (SELECT id FROM batch);
```

#### Rate limiting approach:
- Run batches of 5,000–50,000 rows (tune based on table width and I/O)
- Sleep 100–500ms between batches to cap replication lag
- Monitor `pg_stat_replication.replay_lag` — pause if lag exceeds 10s
- Run during low-traffic windows for large tables, but don't require maintenance window

#### For new rows written during backfill:
- **Dual-write approach**: Deploy app change to write `tenant_id` on INSERT/UPDATE for new rows BEFORE starting backfill. This ensures no new NULL rows are created while backfill runs.
- Sequence: deploy dual-write → start backfill → verify zero NULLs → enforce NOT NULL

### Backfill verification:
```sql
-- Must return 0 for every tenant-scoped table before proceeding
SELECT COUNT(*) FROM orders WHERE tenant_id IS NULL;
```

### Enforce NOT NULL after backfill:
```sql
-- PG 12+: add constraint as NOT VALID first (instant), then validate (non-blocking scan)
ALTER TABLE orders ADD CONSTRAINT orders_tenant_id_nn
  CHECK (tenant_id IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_tenant_id_nn;
```

### Success Criteria
- [ ] `SELECT count(*) WHERE tenant_id IS NULL` = 0 for every tenant-scoped table
- [ ] NOT NULL constraint validated on all tables
- [ ] Replication lag never exceeded 30s during backfill
- [ ] p99 application latency stayed within 20% of baseline

### Rollback
- Backfill is idempotent. If stopped, simply resume.
- NOT NULL constraint can be dropped instantly: `ALTER TABLE orders DROP CONSTRAINT orders_tenant_id_nn;`

## Phase 3: Implement Row-Level Security

**Goal:** Enforce tenant isolation at the database level so no query can cross tenant boundaries.

### Steps

1. **Create application database role** (if not already separated from superuser):
   ```sql
   CREATE ROLE app_user LOGIN;
   GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;
   -- Superuser/migration role bypasses RLS by default
   ```

2. **Enable RLS on each tenant-scoped table**:
   ```sql
   ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
   ALTER TABLE orders FORCE ROW LEVEL SECURITY;  -- enforce even for table owner

   CREATE POLICY tenant_isolation ON orders
     USING (tenant_id = current_setting('app.current_tenant')::UUID)
     WITH CHECK (tenant_id = current_setting('app.current_tenant')::UUID);
   ```

3. **Repeat for every tenant-scoped table** — script this, don't do it manually.

4. **Create a migration role** that bypasses RLS for backfills/admin:
   ```sql
   CREATE ROLE migration_user SUPERUSER LOGIN;  -- or BYPASSRLS
   ```

### Testing before enabling in production:

```sql
-- Test as app_user
SET ROLE app_user;
SET app.current_tenant = 'tenant-uuid-1';
SELECT count(*) FROM orders;  -- should only see tenant-1 rows
SET app.current_tenant = 'tenant-uuid-2';
SELECT count(*) FROM orders;  -- should only see tenant-2 rows
RESET ROLE;
```

### Success Criteria
- [ ] RLS policies active on every tenant-scoped table
- [ ] Verified: app_user with tenant-A context cannot see tenant-B rows
- [ ] Verified: queries without `app.current_tenant` set return zero rows (fail-closed)
- [ ] Verified: migration_user bypasses RLS for admin operations
- [ ] Query performance regression < 5% (RLS adds a filter, but indexes on tenant_id mitigate this)

### Rollback
- `ALTER TABLE orders DISABLE ROW LEVEL SECURITY;` — instant, per-table.

## Phase 4: Application-Layer Tenant Context Injection

**Goal:** Every database connection sets the tenant context before executing queries.

### Middleware pattern (pseudocode):

```python
# Request middleware — runs before any DB query
def tenant_middleware(request, next):
    tenant_id = resolve_tenant(request)  # from JWT, subdomain, header, etc.
    if not tenant_id:
        return 403

    with db.connection() as conn:
        conn.execute("SET LOCAL app.current_tenant = %s", [str(tenant_id)])
        # SET LOCAL scopes to current transaction — safe with PgBouncer transaction mode
        response = next(request)
    return response
```

**Critical: `SET LOCAL` vs `SET`**
- `SET LOCAL` — scoped to current transaction. **Required for PgBouncer transaction mode.**
- `SET` — scoped to session. Only safe in session-mode pooling.

### ORM integration:
- **SQLAlchemy**: Use `after_begin` event on Session to inject `SET LOCAL`.
- **Prisma**: Use `$executeRaw` in middleware.
- **TypeORM**: Use subscriber or query runner wrapper.

### Steps

1. Add tenant resolution logic (JWT claim, subdomain, API key → tenant_id)
2. Add middleware that calls `SET LOCAL app.current_tenant` at transaction start
3. Add integration tests: request with tenant-A creds only sees tenant-A data
4. Add a **fail-closed guard**: if `app.current_tenant` is not set, RLS policy returns zero rows. The app should treat an empty result from a known-populated table as an error signal.

### Success Criteria
- [ ] Every API endpoint sets tenant context before DB access
- [ ] Integration tests confirm cross-tenant isolation
- [ ] No endpoint can query without tenant context (audit via logging)
- [ ] Existing functional test suite passes (tenant-scoped to a test tenant)

### Rollback
- Revert middleware. RLS policies remain but are inert if `app.current_tenant` matches all rows (or disable RLS per Phase 3 rollback).

## Phase 5: Connection Pooling Strategy

**Goal:** Provide tenant-aware connection management without connection exhaustion.

### Recommended: Shared Pool + `SET LOCAL` (for < 500 tenants)

| Approach | Pros | Cons |
|----------|------|------|
| **Shared pool + SET LOCAL** | Simple, one PgBouncer instance, scales to many tenants | Tenant isolation is logical (RLS), not physical |
| **Per-tenant pool** | Hard isolation, easy to throttle per tenant | O(N) PgBouncer pools, connection overhead, config explosion |

**Recommendation:** Use shared pool with `SET LOCAL` unless compliance requires physical isolation.

### PgBouncer configuration for `SET LOCAL`:
```ini
[pgbouncer]
pool_mode = transaction          ; SET LOCAL works in transaction mode
max_client_conn = 1000
default_pool_size = 50
reserve_pool_size = 10
server_reset_query = DISCARD ALL ; Clean session state between transactions
```

### If per-tenant pools are required:
- Use PgBouncer with dynamically generated `[databases]` sections
- Or use pgagroal/Odyssey which support dynamic pool creation
- Limit: `default_pool_size` × tenant_count ≤ `max_connections`

### Success Criteria
- [ ] Connection pool handles peak load without exhaustion
- [ ] `DISCARD ALL` or equivalent cleans tenant state between transactions
- [ ] No connection leaks (monitor `pg_stat_activity` for idle-in-transaction)
- [ ] Load test: 100 concurrent requests across 10 tenants, p99 < baseline + 10%

## Phase 6: Phased Rollout with Rollback Checkpoints

**Goal:** Ship incrementally with the ability to back out at each step.

### Rollout sequence:

```
Phase 0: Audit           ──→ checkpoint: proceed/abort
Phase 1: Add columns     ──→ checkpoint: columns exist, app unaffected
Phase 2: Backfill        ──→ checkpoint: zero NULLs, NOT NULL enforced
  ├─ Deploy dual-write first
  ├─ Run backfill
  └─ Validate
Phase 3: Enable RLS      ──→ checkpoint: RLS active, tested
  └─ Enable per-table, one at a time (canary table first)
Phase 4: App middleware   ──→ checkpoint: tenant context set on all requests
  └─ Feature-flag: shadow mode first (log violations, don't block)
Phase 5: Pool config      ──→ checkpoint: pooling stable under load
Phase 6: Cleanup          ──→ remove feature flags, old code paths
```

### Shadow / canary strategy for Phase 3–4:
1. **Shadow mode**: Enable RLS but also run a parallel unfiltered query. Log any discrepancy. No user impact.
2. **Canary table**: Pick a low-risk, low-traffic table. Enable RLS + middleware. Monitor for 48h.
3. **Progressive rollout**: Enable remaining tables in batches of 3–5, monitoring between batches.

### Monitoring at each checkpoint:
- Application error rate (5xx)
- Query latency p50/p95/p99
- Replication lag
- Connection pool utilization
- RLS violation logs (from shadow mode)

## Open Questions

1. **Tenant resolution mechanism** — How is the tenant identified per request? (JWT claim, subdomain, API key, header?) This determines middleware design.
2. **Cross-tenant queries** — Are there any legitimate cross-tenant operations (admin dashboards, analytics, billing aggregation)? These need to bypass RLS via a privileged role.
3. **Existing multi-schema usage** — Does the database use schemas beyond `public`? RLS policies are per-table, not per-schema.
4. **Backup/restore granularity** — Does the tenant isolation requirement extend to per-tenant backup/restore? RLS doesn't help here; that needs logical partitioning or `pg_dump` with filters.
5. **Compliance requirements** — Is physical tenant isolation required (SOC2, HIPAA), or is logical isolation via RLS sufficient? This determines whether per-tenant pools/schemas are mandatory vs. optional.
6. **Data residency** — Do any tenants require data to reside in specific geographic regions? This would require a fundamentally different architecture (per-region databases).
