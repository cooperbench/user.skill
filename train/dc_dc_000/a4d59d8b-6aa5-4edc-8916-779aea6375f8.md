Two separate identities, two separate creds. Here's the breakdown for DB mode: **Who the user is** → `MEGAPLAN_ACTOR_ID` (or `--actor <id>`) - Resolved in `megaplan/store/identity.py:16`. Must already exist in the `automation_actors` table; `DBStore._get_conn` calls `SELECT set_actor(<id>)` on every connection (`megaplan/store/db.py:377`) so RLS / audit triggers know the writer. - New actors are inserted via `store.create_automation_actor(...)` — there's no CLI subcommand wrapping it; it's called from test/setup code (`megaplan/store/db.py:3850`, contract test at `megaplan/tests/store_contract.py:415`). `__bootstrap__` is reserved. **Connecting to Postgres** → `SUPABASE_DB_URL` - A full DSN, e.g. `[REDACTED]` (`megaplan/store/db.py:346`, error at `:370`). The password in the DSN is what authenticates to the DB — no service-role key involved here. **Uploading blobs** → this is where the service role key comes in - `DBStore.__init__` picks the blob backend at `megaplan/store/db.py:348-357`: - If `SUPABASE_URL` **and** `SUPABASE_SERVICE_ROLE_KEY` **and** (`SUPABASE_STORAGE_BUCKET` or `SUPABASE_BUCKET`) are all set → `SupabaseStorageBlobStore` (uses the service-role key as both `Authorization: Bearer` and `apikey` headers — `megaplan/store/blob.py:182`). - Otherwise → `LocalDirBlobStore` at `MEGAPLAN_DB_BLOB_ROOT` (default `.megaplan/db-blobs`). Rows still reference blob IDs; only the bytes live locally. So: you only need the service-role key if you want blob bytes to land in Supabase Storage. DB writes themselves work with just `SUPABASE_DB_URL` + a registered actor.
