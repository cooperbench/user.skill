Current hot-path inserts are spread across inbound messages, outbound messages, `bot_turns`, scheduled jobs, and artifact writes: inbound `messages` at [inbound.py](/Users/user_c042661f/Documents/Veas/app/services/inbound.py:161), outbound at [messaging.py](/Users/user_c042661f/Documents/Veas/app/services/messaging.py:55), turns at [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:483), deferred jobs at [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:577), scheduler seeds at [scheduled_jobs.py](/Users/user_c042661f/Documents/Veas/app/services/scheduled_jobs.py:216), and scheduled-task/check-in writes in [write_tools.py](/Users/user_c042661f/Documents/Veas/app/services/tools/write_tools.py:1367). ## Hidden dependencies

S2 secretly depends on more S4-style pause/routing work than acknowledged. Pause is global in DB [system_state.py](/Users/user_c042661f/Documents/Veas/app/services/system_state.py:23), pause supersedes every pending user-facing job globally [system_state.py](/Users/user_c042661f/Documents/Veas/app/services/system_state.py:59), and outbound checks both global pause and user pause hooks [messaging.py](/Users/user_c042661f/Documents/Veas/app/services/messaging.py:170). S5’s “per-(user, bot) pause works” (§16.5, line 801) cannot wait until S5 if S2 is already rekeying scheduled jobs and coalescing by bot.

The “transitional dual-key” rekey is implementable only with care. The coalescer’s in-memory dictionaries are all keyed by `UUID user_id` [debouncer.py](/Users/user_c042661f/Documents/Veas/app/services/debouncer.py:42), and the underlying `AsyncBurstCoalescer` key is also `user_id` [debouncer.py](/Users/user_c042661f/Documents/Veas/app/services/debouncer.py:47). You cannot just change SQL filters; active in-memory bursts from before deploy will still flush under the old key. A safe cutover needs either drain/restart semantics or a dual reader that flushes old user-key bursts and writes new `(user, bot)` bursts. Similarly, newer-inbound suppression has two copies: final-send suppression [agentic.py](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:612) and incremental send suppression [read_tools.py](/Users/user_c042661f/Documents/Veas/app/services/tools/read_tools.py:166). Both must filter by `bot_id`, but during cutover old rows may have `NULL bot_id`, so dual-key must mean `(bot_id = ctx.bot_id OR bot_id IS NULL for legacy boundary rows)`, not just “check old and new keys.”

`consult_perspective` is more work than §16.4 implies. It reconstructs a fresh `TurnContext` field-by-field [consult_perspective.py](/Users/user_c042661f/Documents/Veas/app/services/tools/consult_perspective.py:105), not a clone. Every new field added in S1 will be dropped unless S4 changes the pattern. The plan says “clone ctx preserving scopes” (§16.4, line 734); that should become “replace manual constructor with a dataclass clone helper and test all fields.”

## Migration safety concerns

The S1 validation query is wrong for OOB. §16.1 says `artifact_topics` count equals memories + themes + observations + watch_items + distillations + out_of_bounds (§16.1, lines 614–615), but S3 says global OOB is represented by no `artifact_topics` rows (§16.3, line 695). If existing OOB rows are all backfilled with topic rows, you have silently made them non-global. If they are not backfilled, the validation fails. This needs an explicit classification/backfill rule before S1.

The S1 artifact backfill is safer than a table rewrite, but still not “just additive.” Existing artifact tables have useful per-table indexes [0001_init.sql](/Users/user_c042661f/Documents/Veas/migrations/0001_init.sql:155), and distillations add several GIN indexes [0015_distillations.sql](/Users/user_c042661f/Documents/Veas/migrations/0015_distillations.sql:57). A large `artifact_topics` backfill creates a new write-amplified table and two partial indexes. Batched `UPDATE ... LIMIT 5000` is not the right shape for a pure join-table insert; use id-range or cursor-keyed `INSERT INTO artifact_topics SELECT ... WHERE id > last_id ORDER BY id LIMIT n`, with resumability and duplicate protection. Also: the design join table has no real FK to each artifact table, so orphan prevention is entirely application discipline.

The S2 `NOT NULL` flip needs a rollback rule. Once `messages.bot_id/topic_id` and `bot_turns.bot_id/topic_id` are NOT NULL (§16.2, line 656), rolling back to the old app code will break inserts immediately. The plan needs a deploy gate: after NOT NULL, old app versions are no longer valid rollback targets. Safer is add `CHECK (bot_id IS NOT NULL) NOT VALID`, validate, then set NOT NULL only after the new code has survived a full rollback window.

The byte-identical DoD is unrealistic. Hot context embeds current timestamps [hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:65), relative temporal labels [time_context.py](/Users/user_c042661f/Documents/Veas/app/services/time_context.py:98), and rendered current-time blocks [hot_context.py](/Users/user_c042661f/Documents/Veas/app/services/hot_context.py:592). A realistic check is deterministic fixture rendering with frozen `now`, fixed DB snapshot, and normalized IDs/timestamps, plus production semantic diff on section counts/order, not prompt hash equality between real turns.

## What's missing entirely

Per-sprint rollback procedures are missing. S1 needs “remove code, keep additive schema” guidance. S2 needs a hard no-rollback-after-NOT-NULL statement. S3 needs a read-path feature flag to bypass joins if latency spikes. S4 needs a way to disable `scope` exposure without disabling enforcement. S5 needs a kill switch for the solo bot by `bot_id/channel_id`.

Production observability is underdeveloped until S6 (§16.6, line 830), which is too late. S2 should already log `bot_id`, `topic_id`, `channel_id`, `binding_id` on inbound, turns, outbound, scheduled jobs, and OOB checks. S5 should not be the first time dashboards can split mediator vs solo.

The solo bot pre-flight should move to S4: bot account/phone provisioning, webhook endpoint/channel records, secrets, provider allowlists, transport-specific OOB tests, and a consenting target user with written expectations. §16.5 names provisioning lead time (§16.5, line 771), but leaves it in the riskiest sprint.

You also need an eval baseline before S3/S4, not S6. The plan defers per-bot eval scaffolding to S6 (§16.6, line 831), but mediator regressions from tool-schema changes and prompt context changes are exactly what S3/S4 can cause.

## Highest-risk single moment in the plan

The riskiest moment is S2 day 8–9: after routing is wired, hot-path inserts are stamped, in-memory coalescing and newer-inbound suppression are rekeyed, scheduled jobs start carrying bot identity, artifact writes become multi-row transactions, and then `NOT NULL` is applied (§16.2, lines 648–656). That single deploy window can break live replies, create duplicate/stale replies, orphan artifacts, or make rollback impossible. Split S2 into “stamp/rekey with nullable columns” and “constraints after soak,” or extend it.

## Verdict on whether this plan is shippable as written

Not as written. The sequencing is directionally right, but the execution plan compresses the two riskiest operational changes into S2 and underestimates S4/S5. I would ship it after these changes: split S2 constraint enforcement from rekey/stamping, fix OOB backfill semantics, replace byte-identical production hashes with frozen-snapshot diffs, move solo transport provisioning and observability earlier, and make `consult_perspective` cloning a real shared helper instead of another manual constructor.
