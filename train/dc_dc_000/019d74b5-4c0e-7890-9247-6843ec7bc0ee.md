        # Implementation Plan: Mobile and iPad Timeline Interaction Model

## Overview
The repo is still the right shape for this work: keep one editor stack and add a shared touch interaction policy rather than forking a second mobile timeline. The critique exposed two missing implementation layers, not a wrong target. First, the policy has to flow through the split editor contexts published by [VideoEditorProvider.tsx](/Users/user_c042661f/Documents/reigh-workspace/reigh-app/src/tools/video-editor/contexts/VideoEditorProvider.tsx) because shell, timeline, preview, and properties consumers read `useTimelineEditorData()` / `useTimelineEditorOps()`, not `useTimelineState()` directly. Second, gesture rules have to resolve from both device class and per-event input modality so iPad touch can differ from iPad mouse/trackpad without regressing the current desktop-style pointer behavior.

Phase 1 should lock one interaction contract across the existing editor stack. `Phone touch`: browse, scrub, and single-select by default; explicit `Select`, `Move`, `Trim`, and `Precision` modes; bottom-sheet inspector as the primary safe editing fallback; empty-canvas drag pans. `iPad touch`: browse and scrub by default, direct manipulation of the selected clip, enlarged trim handles, persistent inspector access, and long-press or overflow actions. `iPad mouse/trackpad and keyboard`: retain the current desktop pointer and shortcut model; only shared state, surfaced affordances, and persistence gating are reused.

All gesture arbitration should continue to use the existing `interactionStateRef` as the only save/poll deferral gate. The new interaction layer decides who may claim a gesture, which input source started it, and which editing mode is armed; it must not create a second persistence, selection, or sync path.
