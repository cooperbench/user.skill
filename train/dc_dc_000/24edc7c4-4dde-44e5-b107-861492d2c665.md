### 2. **Feedback System**

**Three behavioral kinds:**
- **Style feedback** — persistent across epics; shapes response style ("be more concise", "stop apologizing").
- **Process feedback** — persistent; shapes planning process ("always start with scope reduction").
- **Epic-specific feedback** — tied to one epic; case-based memory.

**Saving discipline (agent-proposed, user-confirmed default):**
1. User implies preference ("ugh, you keep doing X")
2. Bot proposes: "Want me to remember that?"
3. User confirms or declines
4. On confirm, `save_feedback` writes the row

Exception: explicit save requests skip proposal step. Bot saves immediately and acknowledges briefly.

**Disambiguation when saving:** Style vs epic-specific? Long-term vs current-mood? Always ask when uncertain.

**Hot context loading:**
- All active `style` and `process` feedback loaded every turn (top of system prompt)
- Active `epic_specific` feedback for current epic loaded
- Other epics' feedback is cold; retrievable via `list_feedback`

**Save-feedback tool signature:**
```
save_feedback(kind, content, epic_id?, source_message_id?, source, context_snapshot)
```

### 3. **End-of-Turn Checks** (Five categories)

Before finalizing, bot verifies:

1. **Did I send a message?** If no substantive work happened → send default acknowledgment (bug otherwise).
2. **Did I make progress?** Body improved (shaping) or sprints advanced (sprinting)? Or was stillness appropriate (clarifying question, meta-level user steering)?
3. **Did I write what I should have?** New decisions captured, observations logged, checklist reflects understanding.
4. **Did I avoid what I shouldn't have?** No fluff; no conversational pollution in body; no silent epic switches; no fabricated checklist.
5. **Did I address mid-turn messages?** Unaddressed mid-turn messages exist → continue working before sending. Loop enforces this.

### 5. **Showing Changes Pattern**

When bot edits epic: response includes **brief summary** of what changed ("I added a section on X and updated constraints under Y"). Not the full diff.

User can ask "show me the epic" anytime to see current state. Long bodies (>2000 chars) attached as markdown file, not dumped inline.

---

### 6. **Tool References: `search_in_body` & `get_body_outline`**

**`get_body_outline(epic_id)`**
- Returns section names + sub-headings (`###` and below) + line counts per section
- Cheap structural query; lets bot reason about doc shape/size before reading content
- Used for "show me the outline / what's in it" workflows

**`search_in_body(epic_id, query, context_lines=2)`**
- Full-text search within epic body
- Returns matches with line numbers, matching line, N lines of surrounding context per hit
- Returns which section each hit is in
- Bot uses line numbers for reasoning about *location*, not line-level edits (don't exist by design)

**"Change the part about X" workflow:**
1. `search_in_body(epic_id, "X")` → find where X is mentioned (line numbers + section attribution)
2. `get_epic(epic_id, sections=[matching_section])` → load section's full content
3. `edit_epic(body: { sections: { matching_section: revised } })` → write back

Line numbers shift after edits; section names don't. All edits stay at **section granularity**.

- Feedback system requires `save_feedback`, `apply_feedback`, `deactivate_feedback`, `list_feedback`, and observation-specific tools (`record_observation`, `list_observations`, `mark_observation_resolved`).

- Persona is a texture overlay; substantive behaviors (no fluff, willing to disagree, admit uncertainty) don't change.
- Body editing is section-level (preferred) or whole-body replace; section operations are atomic.
- Required body sections: `# Title` and `## Goal` with non-empty first paragraph.

309	    if op_name == "new_content":

333	        for section_name in list(value):

335	        return result
336	    if op_name == "rename_section":

539	    def _update(self, table: str, key_column: str, row_id: str, changes: dict[str, Any], allowed: set[str], loader) -> JSONDict:
540	        if not changes:
541	            return loader(row_id) or {}
542	        unknown = set(changes) - allowed
543	        if unknown:
544	            raise ValueError(f"unsupported {table} columns: {', '.join(sorted(unknown))}")
545	        assignments = ", ".join(f"{key} = %s" for key in changes)
546	        values = [_to_sql_value(key, value) for key, value in changes.items()]
547	        self._conn.execute(
548	            f"UPDATE {table} SET {assignments} WHERE {key_column} = %s",
549	            [*values, row_id],
550	        )
551	        return loader(row_id) or {}

104	def _coerce_script_item(item: ScriptItem, *, call_count: int) -> ModelTurnResult:
105	    if isinstance(item, BaseException):
106	        raise item
107	    if isinstance(item, ModelTurnResult):
108	        return item
109	    if isinstance(item, FakeModelStep):
110	        return item.to_result()
111	    if isinstance(item, dict):
112	        if "exception" in item:

114	            if isinstance(exception, BaseException):
115	                raise exception
116	            raise RuntimeError(str(exception))
117	        if item.get("provider_error"):
118	            raise provider_error(
119	                item.get("error_details"),
120	                item.get("provider_request_id"),
121	            )
122	        if item.get("runtime_error"):
123	            raise RuntimeError(str(item.get("runtime_error")))
124	        return ModelTurnResult(

126	            tool_requests=[
127	                _coerce_tool_request(tool)
128	                for tool in item.get("tool_requests", [])

135	            response_summary=item.get("response_summary"),
136	        )
137	    raise TypeError(f"Unsupported fake model script item: {type(item)!r}")

1774	
1775	Per inbound message (or burst):
1776	
1777	1. **Orient** — coalesce burst if applicable; identify intent and epic; load hot context (including last ~10 tool calls on this epic so the bot knows what it's already done).

2445	## Idempotency and Recovery
2446	
2447	> **Mode applicability:** This section describes **resident-mode** recovery — the long-lived process detecting its own crashes via the recovery routine. **In invocation mode, recovery is the caller's concern.** If an `arnold turn` invocation crashes or times out, the caller decides whether to retry; Arnold itself does not re-invoke. However, the underlying mechanisms below — DB transaction atomicity for in-DB effects, the `external_requests` ledger with idempotency keys, the unique constraint on `discord_message_id` — apply identically in both modes, because they protect the *store*, not the loop. The next invocation against the same store sees a consistent state: any in-flight `external_requests` rows from a prior crashed invocation are reconciled at startup of the next invocation (the recovery scan runs on every process boot, both modes). This means: a caller can safely retry an `arnold turn` invocation after a crash — at-worst, it sees the prior turn's already-committed state and starts a fresh turn from there; at-best, the ledger's reconciliation pass cleans up any pending external requests before the new turn starts. The "turn-level: restart, don't resume" rule applies in both modes; an invocation-mode caller never gets back a half-completed envelope. Mid-process recovery (the 5-minute scheduled scan) is resident-only.
2448	
2449	The bot is a single-user system with a persistent gateway connection. Crashes happen — Railway redeploys, network blips, OOM events. The system needs to recover cleanly without double-applying work or losing messages.
2450	
2451	**Three layers of guarantee:**
2452	
2453	**1. Inbound message idempotency (via DB unique constraint).**
2454	
2455	Every Discord message has a `discord_message_id`. The `messages` table has a unique constraint on this column. When the bot receives a message:
2456	
2457	1. Bot writes to `messages` with `discord_message_id` immediately on receipt (before any LLM call)
2458	2. If the same message_id arrives again (e.g., gateway reconnect replay), the unique constraint causes the insert to fail; bot recognizes the duplicate and skips re-processing
2459	3. Inbound messages persisted but not yet processed are picked up by the recovery routine on startup
2460	
2461	This means: every Discord message gets exactly one row in `messages`, regardless of how many times the bot sees the gateway event.
2462	
2463	**2. Tool-call atomicity (via DB transactions) — for in-DB effects only.**
2464	
2465	Every tool call that mutates *DB* state wraps two operations in a single DB transaction:
2466	- The actual mutation (e.g., `epics.body` update, new `epic_events` row, new `sprints` row)
2467	- The `tool_calls` row insert recording the call
2468	
2469	Either both commit or neither does. There's no state where a write succeeded but the audit row didn't, or vice versa. If the process crashes mid-transaction, Postgres rolls back; on recovery, the bot sees no half-applied state.
2470	
2471	**This atomicity does NOT cover external side effects** — Discord sends, LLM calls, image generation, GitHub API calls, Groq transcription, Storage uploads. DB transactions can only roll back DB writes, not "unsend" a Discord message or "uncall" the OpenAI API. External calls are handled separately via the `external_requests` ledger (see Data Model) with **at-least-once semantics** — the system guarantees the call eventually happens, with idempotency keys (where the provider supports them) and post-hoc reconciliation (where they don't) to prevent user-visible duplicates.
2472	
2473	For tool calls that mix DB mutation with external effect (e.g., `send_message` writes a `messages` row AND posts to Discord; `generate_image` writes an `images` row AND calls OpenAI AND uploads to Storage AND posts to Discord), the order is:
2474	1. Insert `external_requests` row(s) with `status='pending'` (separate transaction)
2475	2. Begin DB transaction: write the mutation + tool_call row, commit
2476	3. Issue external call(s)
2477	4. On success: update `external_requests` row to `confirmed` with provider metadata
2478	5. On failure: update to `failed`; the tool_call row already records the attempt, but the bot sees the failure and can retry
2479	
2480	If crash happens between steps 2 and 4: the DB shows the mutation succeeded, but the external_requests row is `pending`. Recovery's reconciliation pass handles it. See `external_requests` table doc for per-provider reconciliation semantics.
2481	
2482	**3. Turn-level: restart, don't resume.**
2483	
2484	When a turn is interrupted by a crash, the bot does **not** try to resume from where it left off. Resuming a partial turn is fragile: the LLM's reasoning state isn't persisted, the tool sequence may be partly executed, and continuing from a stale midpoint is more error-prone than starting over.
2485	
2486	Instead:
2487	
2488	1. **Turn reconciliation:** scan `bot_turns` for rows in `in_progress` status with `started_at` more than 5 minutes ago (the max turn duration; 7 minutes for turns with image_generated=true).
