 Context

 Two orchestrators independently implement the same "queue empty → what comes next?" pipeline:

 - app/commands/scan/plan_reconcile.py → _sync_post_scan_with_policy()
 - app/commands/review/importing/plan_sync.py → sync_plan_after_import()

 Both call the same gate functions in sequence (subjective dims → communicate-score → create-plan →
 triage), then resolve the lifecycle phase — but via different mechanisms and with duplicated helpers.
  The user's insight: this is ONE pipeline (scan → subjective review → fetch score → triage) that
 fires whenever the real work queue is empty, regardless of whether we're at the start or end of a
 cycle.

 Approach

 Extract the shared gate sequence into a single run_postflight_gates() function in a new
 engine/_plan/sync/pipeline.py module. Both callers shrink to: domain-specific work → call pipeline →
 display/log from results → save.

**Findings**
- High: the review-import rewrite drops current `create-plan` behavior unless you also change `_sync_review_delta`. Today `_sync_review_delta` calls `sync_plan_after_review_import()`, and that engine helper already injects triage stages ([reconcile_review_import.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/reconcile_review_import.py#L140)). `sync_create_plan_needed()` explicitly refuses to inject if any triage IDs are already in `queue_order` ([workflow.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/sync/workflow.py#L286)). The current import path avoids that by running communicate/import/create-plan before `_sync_review_delta` ([plan_sync.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/review/importing/plan_sync.py#L407)). Your proposed order runs `_sync_review_delta` first, then the pipeline, so `workflow::create-plan` can disappear. There is already a regression test for the current contract ([test_review_importing_support_direct.py](/Users/user_c042661f/Documents/desloppify/desloppify/tests/commands/review/test_review_importing_support_direct.py#L307)).

- High: the proposed import call sketch loses non-default `target_strict`. The current import flow resolves `target_strict` from config and passes it into both policy computation and auto-clustering ([plan_sync.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/review/importing/plan_sync.py#L387)). Your proposed `run_postflight_gates(...)` call for import does not pass `target_strict`, so the new pipeline would silently fall back to `DEFAULT_TARGET_STRICT_SCORE` for clustering and any threshold-sensitive queue building.

- Medium: “no behavioral changes” is not true unless you preserve the current import-side gating for subjective sync and auto-cluster. Today those only run when there was a review issue delta or imported assessment coverage ([plan_sync.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/review/importing/plan_sync.py#L251)). An unconditional pipeline call after every import will start mutating plan state on imports that previously only updated import metadata or workflow items.

- Medium: lifecycle unification via `queue_context(...).snapshot.phase` is a semantic change, not a pure extraction. The current import path resolves `review` whenever `policy.unscored_ids` is non-empty ([refresh_lifecycle.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/refresh_lifecycle.py#L96)), while the snapshot path only returns initial-review when the plan is at a fresh boundary (`plan_start_scores` empty/reset) ([snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L81)). - The overall direction is right. There is real duplication, and scan/import are clearly trying to drive the same gate family.
- If you unify lifecycle on the snapshot path, `has_postflight_review_work()` should probably not be moved at all. It becomes dead code again.

- `run_postflight_gates(...)` is getting parameter-heavy. A small `PostflightInputs` dataclass, or a lower-level engine function with thin scan/import wrappers, would keep the API tighter.
- Keep `plan_start_scores_seeded` and `plan_start_scores_cleared` mutually exclusive. The current scan code is intentionally seed-or-clear, never both.
