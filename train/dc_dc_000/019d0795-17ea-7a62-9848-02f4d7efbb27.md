I checked the plan against the actual worker code in `/Users/user_c042661f/Documents/Reigh-Worker`; the `reigh` checkout only has the app/docs, not the Python worker.

**Findings**
1. Phase 2’s “thread the latent path through chaining/orchestrator” does not match the real execution model. The orchestrator creates all `travel_segment` tasks up front, and chaining explicitly does not enqueue the next segment. That means a latent path discovered after segment N finishes cannot be injected into segment N+1 the way the plan describes without mutating DB state or encoding it in the predecessor task record. [source/task_handlers/travel/orchestrator.py#L2189](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/orchestrator.py#L2189) [source/task_handlers/travel/chaining.py#L395](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/chaining.py#L395)

2. The predecessor contract only returns a single `output_location` string today. There is no latent-path field anywhere in the edge function or Python helper, so Phase 2 needs a transport design first. If you want predecessor video + predecessor latent, you must extend this contract or store structured JSON and teach the consumer to parse it. [supabase/functions/get-predecessor-output/index.ts#L18](/Users/user_c042661f/Documents/reigh/supabase/functions/get-predecessor-output/index.ts#L18) [source/core/db/dependencies/task_dependencies_query_helpers.py#L45](/Users/user_c042661f/Documents/Reigh-Worker/source/core/db/dependencies/task_dependencies_query_helpers.py#L45)

3. The proposed latent sidecar save point in `wgp.py` is wrong. At `samples.get("latent_slice")`, there is no final `output_path` yet; filenames are only decided later when WGP saves the mp4. Even worse, travel chaining immediately moves/renames the video, so a sidecar written beside the pre-chain file would be orphaned unless you explicitly move/upload it too. [Wan2GP/wgp.py#L6848](/Users/user_c042661f/Documents/Reigh-Worker/Wan2GP/wgp.py#L6848) [Wan2GP/wgp.py#L6971](/Users/user_c042661f/Documents/Reigh-Worker/Wan2GP/wgp.py#L6971) [source/task_handlers/travel/chaining.py#L87](/Users/user_c042661f/Documents/Reigh-Worker/source/task_handlers/travel/chaining.py#L87)

4. Phase 2 as written is also local-path only. In production, predecessor outputs can be consumed on another worker/pod, so a `.latent.pt` local path is not enough; it needs upload and a durable reference. There is already an intermediate-upload helper, but the plan doesn’t use it. [source/utils/output_paths.py#L149](/Users/user_c042661f/Documents/Reigh-Worker/source/utils/output_paths.py#L149)

5. The Phase 1 code sample has an off-by-one bug. `extract_frame_range_to_video()` uses an inclusive `end_frame`, so `effective_end = pred_frames - flf_trim` would extract 10 frames, not 9, and would still include one frame too far. The safe form is `usable_end = pred_frames - trim - 1`. [source/media/video/ffmpeg_ops.py#L145](/Users/user_c042661f/Documents/Reigh-Worker/source/media/video/ffmpeg_ops.py#L145)

6. Phase 3’s proposed “replace with clean anchor/end latent after each scheduler step” is not equivalent to ComfyUI inpainting. The existing inpaint path re-injects sigma-noised source latents, not clean latents. A raw overwrite will change the denoising distribution and can easily make things worse.
