        # Implementation Plan: Fix Audio Clip Jumping-Back Bug in Timeline

## Overview

Audio clips jump back to their previous position after being dragged. The root cause is a **polling race condition**: during a drag, no guard prevents polled server data from overwriting local state. The `editSeqRef` guard only activates when `applyTimelineEdit` is called (at pointerUp), leaving the entire drag duration unprotected. `pendingOpsRef` only guards asset uploads, not drag operations.

**Key insight**: The simplest fix is to make the polling effect aware of active drags via `dragSessionRef`, which already exists and is returned from `useClipDrag`. This avoids the complexity of trying to increment/decrement `pendingOpsRef` (which has different semantics — async operations with try/finally). A drag is a synchronous UI interaction with a clear start/end, best represented by checking a ref.

**Files touched:**
- `useTimelineSave.ts` — add drag-aware poll rejection
- `useClipDrag.ts` — consolidate dual position truth
- `useTimelineData.ts` (or wherever hooks are composed) — wire dragSessionRef to save hook
- `resolve-overlaps.ts` — audit only, likely no changes needed
- `timeline-save-utils.ts` — possible update to `shouldAcceptPolledData`

## Phase 1: Core Race Condition Fix

### Step 1: Add drag-active poll rejection to `useTimelineSave.ts`
**Scope:** Small

1. **Add** a `dragSessionRef` parameter to `useTimelineSave` (or accept it via a new option). This ref is already created and managed by `useClipDrag` (`useClipDrag.ts:100`).
2. **Add** an `'active drag'` rejection reason to `getPollRejectionReason` (`useTimelineSave.ts:136-162`), checking `dragSessionRef.current !== null` before accepting polls. Place this check early (before the signature/version checks) since it's the cheapest guard.
3. **Wire** `dragSessionRef` from the composition point (likely `useTimelineData.ts:99` or wherever `useTimelineSave` and `useClipDrag` are composed together). Find this composition point and pass the ref through.

### Step 2: Consolidate dual position truth in `useClipDrag.ts`
**Scope:** Small

1. **Audit** the two position sources: `actionDragStateRef.current.latestStart` and `session.latestStart` (`useClipDrag.ts:365`). Currently the code does `actionDragStateRef.current?.latestStart ?? session.latestStart` — if `actionDragStateRef` is null (shouldn't happen during a valid drag, but the `??` implies it could), the fallback is the session value.
2. **Remove** the dual tracking. Pick one canonical source. `actionDragStateRef` carries more data (rowId, initialStart/End, latestStart/End) and is updated during pointermove with snapped positions. Make `session.latestStart` derived from or eliminated in favor of `actionDragStateRef.latestStart`. If `session.latestStart` is also used elsewhere (e.g., in `getAnchorTimeDelta`), update those call sites.
3. **Verify** `session.latestStart` is updated in the same pointermove handler as `actionDragStateRef.latestStart`. If they can diverge (e.g., one is pre-snap, one is post-snap), document which is which and ensure `handlePointerUp` uses the correct (post-snap) value.

### Step 3: Strengthen post-edit poll rejection (`useTimelineSave.ts`)
**Scope:** Small

1. **Add a cooldown** after `commitData` completes with `save: true`. Currently, once `savedSeqRef` catches up to `editSeqRef`, polling is immediately re-enabled. But the server may echo the just-saved data in the next poll response. The `shouldAcceptPolledData` signature check (`timeline-save-utils.ts:20`) handles this, but verify it's working correctly.
2. **Verify** the `completedSeqRef` vs `savedSeqRef` distinction (`useTimelineSave.ts:252,273`). The save callback updates `completedSeqRef` at line 252 and `savedSeqRef` at line 273. Check if there's a window where `savedSeqRef` is updated but the `lastSavedSignature` hasn't propagated to the next poll check. If so, add a microtask delay or use the same update point.
3. **Log** poll acceptance with drag state for debugging: when a poll is accepted, log whether a drag was recently active (within last 500ms). This aids future debugging.

## Phase 2: Overlap Resolution Audit

### Step 4: Audit `resolveOverlaps` for silent position changes (`resolve-overlaps.ts`)
**Scope:** Small

1. **Trace** the overlap resolution path: `moveClipToRow` (`useTimelineTrackManagement.ts:131-133`) calls `resolveOverlaps(placedRows, targetRow.id, clipId, current.meta)`. The result may silently change the clip's start/end and metadata (from/to).
2. **Check** whether the user gets any feedback when overlap resolution changes the clip position. If the clip is placed at time 20s but overlaps push it to 22s, this could appear as a "jump" even without a polling race. Consider whether `resolveOverlaps` should return a flag indicating whether the position was modified.
3. **Verify** that `metaPatches` from overlap resolution are correctly applied (`useTimelineTrackManagement.ts:138`). The current code merges them into the `applyTimelineEdit` call — confirm the metadata (from/to/speed) is consistent with the final resolved position.
4. **Check** `resolveGroupOverlaps` (`resolve-overlaps.ts:200`) for the multi-clip drag path. It does NOT produce metaPatches (unlike single-clip `resolveOverlaps`), meaning multi-clip drags that trigger overlap resolution lose source-time metadata adjustments. If this is a real gap, flag it for follow-up.

### Step 5: Verify with existing tests and add targeted test coverage
**Scope:** Medium

1. **Run** existing tests: `useTimelineTrackManagement.test.ts` and `useAssetOperations.test.tsx` to establish baseline.
2. **Add** a unit test for `shouldAcceptPolledData` in `timeline-save-utils.ts` covering the drag-active scenario (if the function is updated to accept a drag param).
3. **Add** a unit test for `resolveOverlaps` verifying that when a clip is placed at a position that overlaps, the returned `metaPatches` correctly adjust `from`/`to` based on the trimmed start/end and speed.
4. **Verify** the polling effect behavior by reviewing the `getPollRejectionReason` logic with the new drag guard.

3. Step 3 after Step 1 — hardens the existing guards.
4. Steps 4-5 can proceed after the core fix is landed.
