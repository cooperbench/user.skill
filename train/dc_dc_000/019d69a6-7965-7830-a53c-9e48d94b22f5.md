# Robust Review Phase for Megaplan (Heavy Mode Only)

## Context

Megaplan is a planning/execution harness with phases: prep → plan → critique → gate → (revise → critique → gate)* → finalize → execute → review. Critique already has a "robust" mode where it runs multiple focused checks in parallel (`megaplan/parallel_critique.py` + `megaplan/checks.py`), each as an independent sub-agent with its own session. We validated on ~15 random SWE-bench failures that the current single-call review phase misses ~65% of salvageable failures because it anchors to the plan's success criteria instead of the original issue text, and because it evaluates everything in one call without forced enumeration.

## Goal

Add a **robust review** mode that mirrors the robust critique architecture: multiple focused, parallel, issue-anchored checks that produce structured flags with rework directives, which feed back through the existing gate → revise/re-execute loop.

**Standard robustness mode must remain exactly as today.** This design is heavy-mode only.

## What exists today (don't break)

- `megaplan/prompts/review.py` — single-call review prompt; validates execution against finalize.json criteria/task_verdicts/sense_check_verdicts. Works well as the baseline. Keep it.
- `megaplan/prompts/critique.py` + `megaplan/parallel_critique.py` + `megaplan/checks.py` — the pattern we're mirroring. Read these to understand the architecture.
- `megaplan/handlers.py` `handle_review()` — entry point. Currently calls a single worker.
- The gate → revise/re-execute loop already exists with max iteration cap and ESCALATE semantics.
- `intent_and_notes_block(state)` contains the original issue text — crucial input for issue-anchored checks.

## What needs to exist

### 1. New check table for review

New file `megaplan/review_checks.py` mirroring `megaplan/checks.py`. Define `REVIEW_CHECKS` with these entries (core + extended tiers). Each check has `id`, `question`, `guidance`, `category`, `default_severity`, `tier`:

**Core tier (always run in heavy mode):**
- `coverage` — Enumerate every concrete failing example, symptom, or "X should Y" statement in the issue. For each, point to the specific line in the diff that addresses it. Flag any not covered. Subsumes intent/opt-in/default and accepted-changes concerns.
- `placement` — Trace the call path from the failing input to where we made the change. Is the fix at the source of the bug or a downstream consumer? Would a maintainer put it here or elsewhere?
- `parity` — Find 2–3 structurally similar classes/functions in the same module. Enumerate the methods/overrides/conventions they share. Does our new code follow the same patterns? If not, why not? (Highest new-leverage check.)
- `simplicity` — What's the smallest possible change that would make the reported issue's example work? Compare against our diff. Every extra line must justify its existence against a specific requirement in the issue.

**Extended tier (heavy mode with extended robustness):**
- `dead_guard` — For every new `if x:` / `try:` block added by the patch, trace whether the guarded branch is actually reachable given how callers invoke this function. Flag guards that never fire.
- `adjacent_calls` — What other code calls the changed function or uses the same pattern? Would the same bug affect them?
- `parser_source` — If the bug is in parsing/transformation, is the fix at the source of the bug or at a downstream consumer?
- `return_value_downstream` — For any value the patch returns or constructs in an error path, trace where it flows next. Will the downstream consumer handle it correctly?

Also include a `checks_for_robustness()` function mirroring `megaplan/checks.py`.

### 2. Mechanical pre-checks (no LLM, run before parallel review)

Add a new module `megaplan/review_mechanical.py` or inline in handlers:
- `source_touch` — Does the diff touch at least one non-test file in the package? Reject test-only diffs.
- `diff_size_sanity` — Compare diff size (lines/hunks/files) to a rough expectation from the issue (number of code snippets × ~10 lines). Flag >3x or <0.3x.
- `dead_guard_static` — For new `if x:` blocks, AST-parse the changed file, find the enclosing function, check whether `x` has a callable signature at the call site where it could be None/False. This is a heuristic; don't overreach.

These are **advisory flags**, not blocks. They populate a `pre_check_flags` array that the LLM review checks see as input.

### 3. Parallel review runner

New file `megaplan/parallel_review.py`, mirroring `megaplan/parallel_critique.py`. Same architecture: `ThreadPoolExecutor`, one agent per check, each with its own session via `SessionDB`, writes findings to a pre-populated template slot. Concurrency of 2 (same as critique). Include the MiniMax→OpenRouter fallback pattern.

Important: each check agent gets **the original issue text + the full git diff + the finalize.json artifacts**, nothing else. No plan, no critique history, no gate summary. The whole point is that these checks are anchored to the issue, not the plan.

### 4. Prompt builders for single-check review

In `megaplan/prompts/review.py`, add:
- `single_check_review_prompt(state, plan_dir, root, check, output_path)` — mirrors `single_check_critique_prompt` — single focused prompt for one check.
- `_write_single_check_review_template(plan_dir, state, check, filename)` — pre-populates the output file with the check's ID.
- `_build_review_checks_template(plan_dir, state, checks)` — builds the per-check template list.

Keep `_review_prompt()` as-is. It still runs as the "criteria_verdict" check in heavy mode.

### 5. Handler integration

In `megaplan/handlers.py` `handle_review()`:
- Read `configured_robustness(state)`
- If `standard` or `light` → run the existing single-call review unchanged
- If `heavy` → run the mechanical pre-checks, then run `parallel_review()` across REVIEW_CHECKS + the existing criteria-based review-as-check. Merge all flags into one `review.json`

The output shape adds a `checks` array alongside the existing `review_verdict`, `criteria`, `issues`, `rework_items`, `task_verdicts`, `sense_check_verdicts`, `summary`. Back-compat: existing consumers that only look at `review_verdict` / `rework_items` keep working.

### 6. Feedback loop — how flags flow back

This is the tricky part. The review runs after execute. If it raises blocking flags, where does control go?

**Decision: reuse the existing gate → revise/re-execute loop, not a new review-specific loop.**

Concretely:
- If `review_verdict == "needs_rework"` with blocking flags, the handler writes them to `rework_items` as today.
- The execute loop in `evals/run_evals.py` already handles `needs_rework` by going back to revise or re-execute based on the rework type. No new routing logic.
- Add a new field `rework_directive.source = "review_{check_id}"` so the executor knows the provenance and can prioritize.
- **Max review iterations cap at 2** (configurable). After 2 rounds of needs_rework from the review, escalate. Otherwise the same check can fire forever on tasks the model can't solve.
- Review flags **cannot re-raise concerns the gate already settled**. Before raising a coverage/placement/parity flag, the review check must check `gate.settled_decisions` — if the concern matches a settled decision, downgrade to "significant" (info) rather than "blocking". This prevents the gate-override deadlock we hit before.

### 7. Severity ladder (mirrors critique)

Each review flag has:
- `blocking` — triggers `needs_rework`, forces another revise/execute pass
- `significant` — logged, shown to gate for future iterations, doesn't auto-block
- `minor` — info only, aggregated into summary

### 8. Flag tracking across review iterations

Mirror critique's flag registry. Each review check's findings get IDs like `REVIEW-COV-001`. Status transitions open → verified → resolved across iterations, just like critique flags. Read `megaplan/_core` flag registry helpers — reuse them, don't duplicate.

### 9. Schema updates

Add a review checks schema fragment alongside the existing review schema in `schemas/` (wherever step schemas live — look at `STEP_SCHEMA_FILENAMES` in `megaplan/workers.py`). The schema should allow the existing top-level fields PLUS a new `checks` array with per-check findings.

### 10. Tests

- Unit tests for `REVIEW_CHECKS` structure and `checks_for_robustness()` behavior
- Unit test that standard robustness still calls the single-call review (regression guard)
- Unit test for mechanical pre-checks (source_touch, diff_size_sanity)
- Integration test: feed a known-bad patch through heavy review, assert it raises the expected flag
- Integration test: feed a known-good patch through heavy review, assert no blocking flags

Use the existing test infrastructure patterns.

2. **Parallel focused-agent runner** (`parallel_critique.py` + `parallel_review.py`) should be refactorable to a single `parallel_phase_runner.py` that both delegate to. Not in this PR, but leave clean seams.
3. **Template-file-with-preloaded-IDs pattern** should be documented as "the preferred way to get structured output" in a short comment at the top of `parallel_review.py`.
4. **Mechanical pre-checks should be runnable standalone** so they can be reused by critique, finalize, or any other phase that wants cheap advisory checks.

Megaplan is a planning/execution harness with phases: prep → plan → critique → gate → (revise → critique → gate)* → finalize → execute → review. Critique already has a "robust" mode where it runs multiple focused checks in parallel (`megaplan/parallel_critique.py` + `megaplan/checks.py`), each as an independent sub-agent with its own session. We validated on ~15 random SWE-bench failures that the current single-call review phase misses ~65% of salvageable failures because it anchors to the plan's success criteria instead of the original issue text, and because it evaluates everything in one call without forced enumeration.

## Goal

Add a **robust review** mode that mirrors the robust critique architecture: multiple focused, parallel, issue-anchored checks that produce structured flags with rework directives, which feed back through the existing gate → revise/re-execute loop.

**Standard robustness mode must remain exactly as today.** This design is heavy-mode only.

## What exists today (don't break)

- `megaplan/prompts/review.py` — single-call review prompt; validates execution against finalize.json criteria/task_verdicts/sense_check_verdicts. Works well as the baseline. Keep it.
- `megaplan/prompts/critique.py` + `megaplan/parallel_critique.py` + `megaplan/checks.py` — the pattern we're mirroring. Read these to understand the architecture.
- `megaplan/handlers.py` `handle_review()` — entry point. Currently calls a single worker.
- The gate → revise/re-execute loop already exists with max iteration cap and ESCALATE semantics.
- `intent_and_notes_block(state)` contains the original issue text — crucial input for issue-anchored checks.

## What needs to exist

### 1. New check table for review

New file `megaplan/review_checks.py` mirroring `megaplan/checks.py`. Define `REVIEW_CHECKS` with these entries (core + extended tiers). Each check has `id`, `question`, `guidance`, `category`, `default_severity`, `tier`:

**Core tier (always run in heavy mode):**
- `coverage` — Enumerate every concrete failing example, symptom, or "X should Y" statement in the issue. For each, point to the specific line in the diff that addresses it. Flag any not covered. Subsumes intent/opt-in/default and accepted-changes concerns.
- `placement` — Trace the call path from the failing input to where we made the change. Is the fix at the source of the bug or a downstream consumer? Would a maintainer put it here or elsewhere?
- `parity` — Find 2–3 structurally similar classes/functions in the same module. Enumerate the methods/overrides/conventions they share. Does our new code follow the same patterns? If not, why not? (Highest new-leverage check.)
- `simplicity` — What's the smallest possible change that would make the reported issue's example work? Compare against our diff. Every extra line must justify its existence against a specific requirement in the issue.

**Extended tier (heavy mode with extended robustness):**
- `dead_guard` — For every new `if x:` / `try:` block added by the patch, trace whether the guarded branch is actually reachable given how callers invoke this function. Flag guards that never fire.
- `adjacent_calls` — What other code calls the changed function or uses the same pattern? Would the same bug affect them?
- `parser_source` — If the bug is in parsing/transformation, is the fix at the source of the bug or at a downstream consumer?
- `return_value_downstream` — For any value the patch returns or constructs in an error path, trace where it flows next. Will the downstream consumer handle it correctly?

Also include a `checks_for_robustness()` function mirroring `megaplan/checks.py`.

### 2. Mechanical pre-checks (no LLM, run before parallel review)

Add a new module `megaplan/review_mechanical.py` or inline in handlers:
- `source_touch` — Does the diff touch at least one non-test file in the package? Reject test-only diffs.
- `diff_size_sanity` — Compare diff size (lines/hunks/files) to a rough expectation from the issue (number of code snippets × ~10 lines). Flag >3x or <0.3x.
- `dead_guard_static` — For new `if x:` blocks, AST-parse the changed file, find the enclosing function, check whether `x` has a callable signature at the call site where it could be None/False. This is a heuristic; don't overreach.

These are **advisory flags**, not blocks. They populate a `pre_check_flags` array that the LLM review checks see as input.

### 3. Parallel review runner

New file `megaplan/parallel_review.py`, mirroring `megaplan/parallel_critique.py`. Same architecture: `ThreadPoolExecutor`, one agent per check, each with its own session via `SessionDB`, writes findings to a pre-populated template slot. Concurrency of 2 (same as critique). Include the MiniMax→OpenRouter fallback pattern.

Important: each check agent gets **the original issue text + the full git diff + the finalize.json artifacts**, nothing else. No plan, no critique history, no gate summary. The whole point is that these checks are anchored to the issue, not the plan.

### 4. Prompt builders for single-check review

In `megaplan/prompts/review.py`, add:
- `single_check_review_prompt(state, plan_dir, root, check, output_path)` — mirrors `single_check_critique_prompt` — single focused prompt for one check.
- `_write_single_check_review_template(plan_dir, state, check, filename)` — pre-populates the output file with the check's ID.
- `_build_review_checks_template(plan_dir, state, checks)` — builds the per-check template list.

Keep `_review_prompt()` as-is. It still runs as the "criteria_verdict" check in heavy mode.

### 5. Handler integration

In `megaplan/handlers.py` `handle_review()`:
- Read `configured_robustness(state)`
- If `standard` or `light` → run the existing single-call review unchanged
- If `heavy` → run the mechanical pre-checks, then run `parallel_review()` across REVIEW_CHECKS + the existing criteria-based review-as-check. Merge all flags into one `review.json`

The output shape adds a `checks` array alongside the existing `review_verdict`, `criteria`, `issues`, `rework_items`, `task_verdicts`, `sense_check_verdicts`, `summary`. Back-compat: existing consumers that only look at `review_verdict` / `rework_items` keep working.

### 6. Feedback loop — how flags flow back

This is the tricky part. The review runs after execute. If it raises blocking flags, where does control go?

**Decision: reuse the existing gate → revise/re-execute loop, not a new review-specific loop.**

Concretely:
- If `review_verdict == "needs_rework"` with blocking flags, the handler writes them to `rework_items` as today.
- The execute loop in `evals/run_evals.py` already handles `needs_rework` by going back to revise or re-execute based on the rework type. No new routing logic.
- Add a new field `rework_directive.source = "review_{check_id}"` so the executor knows the provenance and can prioritize.
- **Max review iterations cap at 2** (configurable). After 2 rounds of needs_rework from the review, escalate. Otherwise the same check can fire forever on tasks the model can't solve.
- Review flags **cannot re-raise concerns the gate already settled**. Before raising a coverage/placement/parity flag, the review check must check `gate.settled_decisions` — if the concern matches a settled decision, downgrade to "significant" (info) rather than "blocking". This prevents the gate-override deadlock we hit before.

### 7. Severity ladder (mirrors critique)

Each review flag has:
- `blocking` — triggers `needs_rework`, forces another revise/execute pass
- `significant` — logged, shown to gate for future iterations, doesn't auto-block
- `minor` — info only, aggregated into summary

### 8. Flag tracking across review iterations

Mirror critique's flag registry. Each review check's findings get IDs like `REVIEW-COV-001`. Status transitions open → verified → resolved across iterations, just like critique flags. Read `megaplan/_core` flag registry helpers — reuse them, don't duplicate.

### 9. Schema updates

Add a review checks schema fragment alongside the existing review schema in `schemas/` (wherever step schemas live — look at `STEP_SCHEMA_FILENAMES` in `megaplan/workers.py`). The schema should allow the existing top-level fields PLUS a new `checks` array with per-check findings.

### 10. Tests

- Unit tests for `REVIEW_CHECKS` structure and `checks_for_robustness()` behavior
- Unit test that standard robustness still calls the single-call review (regression guard)
- Unit test for mechanical pre-checks (source_touch, diff_size_sanity)
- Integration test: feed a known-bad patch through heavy review, assert it raises the expected flag
- Integration test: feed a known-good patch through heavy review, assert no blocking flags

Use the existing test infrastructure patterns.

## Generalization beyond review

While implementing, keep these generalizations in mind (don't implement them now, but design so they're easy later):

1. **`checks_for_robustness()` pattern** should be extractable to a shared utility — same function body in checks.py and review_checks.py should be one function.
2. **Parallel focused-agent runner** (`parallel_critique.py` + `parallel_review.py`) should be refactorable to a single `parallel_phase_runner.py` that both delegate to. Not in this PR, but leave clean seams.
3. **Template-file-with-preloaded-IDs pattern** should be documented as "the preferred way to get structured output" in a short comment at the top of `parallel_review.py`.
4. **Mechanical pre-checks should be runnable standalone** so they can be reused by critique, finalize, or any other phase that wants cheap advisory checks.

## Out of scope for this plan

- Automatic golden-patch comparison for false-negative detection (we already have `auto_improve/check_false_negatives.py`)
- Running these checks on tasks that already passed
- A/B evaluation of which checks actually earn their spot (that's a separate measurement exercise)
- Any changes to critique, plan, execute, prep, or finalize phases
- Any changes to standard or light robustness mode
- New top-level phases between review and execute

## Success criteria

- Heavy mode review produces a `checks` array with one entry per REVIEW_CHECK
- Standard mode review produces byte-identical output to today for the same input
- Blocking flags flow through the existing rework loop without new routing logic
- Flag iteration cap prevents infinite review→re-execute loops
- Unit + integration tests pass
- Code follows the same patterns as `parallel_critique.py` and `checks.py` — a reader familiar with critique should find nothing surprising in the review code

## Overview
Heavy-mode review adds a parallel, issue-anchored check architecture mirroring robust critique. Standard/light paths stay byte-identical. Revision v2 addresses gate flags on: (a) iteration cap default (FLAG-001 / issue_hints-1), (b) dual schema sources and the new `source` rework field (FLAG-002 / correctness-1 / scope-2), (c) review flag lifecycle via `verified_flag_ids`/`disputed_flag_ids` (FLAG-003 / scope-1), (d) review-specific toolset not critique's (correctness-2), and (e) folding the legacy `_review_prompt` in as a first-class `criteria_verdict` check inside the parallel runner so every review check goes through the same mirrored architecture (issue_hints-2).

Verified facts driving the revision:
- `megaplan/types.py:289` defaults `execution.max_review_rework_cycles` to `3` — lowering to `2` is a one-line change and governs all modes the same way (standard's single-call review is unchanged in behavior, only the rework cap moves).
- Review schema is defined in **both** `.megaplan/schemas/review.json` and `megaplan/schemas.py:353-411` (`STEP_SCHEMA_REGISTRY["review.json"]`) and rework_items currently requires exactly `task_id|issue|expected|actual|evidence_file`. Both must be widened.
- `megaplan/hermes_worker.py:52-66`: `_toolsets_for_phase("review")` returns file-only; `_toolsets_for_phase("critique")` returns file+web. Review check agents must use `"review"` to avoid silently widening permissions.
- `megaplan/flags.py:53` (`update_flags_after_critique`) consumes `verified_flag_ids` / `disputed_flag_ids` to move prior flags through status transitions. Review v2 will mirror this: the per-check template includes prior `REVIEW-*` flags so a heavy-mode check can re-verify or dispute them, just like critique.
- `megaplan/prompts/critique.py:113-160` (`_build_checks_template`) already shows how to attach prior findings + flag status to a new-iteration template. We reuse that pattern for review.

# Robust Review Phase for Megaplan (Heavy Mode Only)

## Context

Megaplan is a planning/execution harness with phases: prep → plan → critique → gate → (revise → critique → gate)* → finalize → execute → review. Critique already has a "robust" mode where it runs multiple focused checks in parallel (`megaplan/parallel_critique.py` + `megaplan/checks.py`), each as an independent sub-agent with its own session. We validated on ~15 random SWE-bench failures that the current single-call review phase misses ~65% of salvageable failures because it anchors to the plan's success criteria instead of the original issue text, and because it evaluates everything in one call without forced enumeration.

## Goal

Add a **robust review** mode that mirrors the robust critique architecture: multiple focused, parallel, issue-anchored checks that produce structured flags with rework directives, which feed back through the existing gate → revise/re-execute loop.

**Standard robustness mode must remain exactly as today.** This design is heavy-mode only.

## What exists today (don't break)

- `megaplan/prompts/review.py` — single-call review prompt; validates execution against finalize.json criteria/task_verdicts/sense_check_verdicts. Works well as the baseline. Keep it.
- `megaplan/prompts/critique.py` + `megaplan/parallel_critique.py` + `megaplan/checks.py` — the pattern we're mirroring. Read these to understand the architecture.
- `megaplan/handlers.py` `handle_review()` — entry point. Currently calls a single worker.
- The gate → revise/re-execute loop already exists with max iteration cap and ESCALATE semantics.
- `intent_and_notes_block(state)` contains the original issue text — crucial input for issue-anchored checks.

## What needs to exist

### 1. New check table for review

New file `megaplan/review_checks.py` mirroring `megaplan/checks.py`. Define `REVIEW_CHECKS` with these entries (core + extended tiers). Each check has `id`, `question`, `guidance`, `category`, `default_severity`, `tier`:

**Core tier (always run in heavy mode):**
- `coverage` — Enumerate every concrete failing example, symptom, or "X should Y" statement in the issue. For each, point to the specific line in the diff that addresses it. Flag any not covered. Subsumes intent/opt-in/default and accepted-changes concerns.
- `placement` — Trace the call path from the failing input to where we made the change. Is the fix at the source of the bug or a downstream consumer? Would a maintainer put it here or elsewhere?
- `parity` — Find 2–3 structurally similar classes/functions in the same module. Enumerate the methods/overrides/conventions they share. Does our new code follow the same patterns? If not, why not? (Highest new-leverage check.)
- `simplicity` — What's the smallest possible change that would make the reported issue's example work? Compare against our diff. Every extra line must justify its existence against a specific requirement in the issue.

**Extended tier (heavy mode with extended robustness):**
- `dead_guard` — For every new `if x:` / `try:` block added by the patch, trace whether the guarded branch is actually reachable given how callers invoke this function. Flag guards that never fire.
- `adjacent_calls` — What other code calls the changed function or uses the same pattern? Would the same bug affect them?
- `parser_source` — If the bug is in parsing/transformation, is the fix at the source of the bug or at a downstream consumer?
- `return_value_downstream` — For any value the patch returns or constructs in an error path, trace where it flows next. Will the downstream consumer handle it correctly?

Also include a `checks_for_robustness()` function mirroring `megaplan/checks.py`.

### 2. Mechanical pre-checks (no LLM, run before parallel review)

Add a new module `megaplan/review_mechanical.py` or inline in handlers:
- `source_touch` — Does the diff touch at least one non-test file in the package? Reject test-only diffs.
- `diff_size_sanity` — Compare diff size (lines/hunks/files) to a rough expectation from the issue (number of code snippets × ~10 lines). Flag >3x or <0.3x.
- `dead_guard_static` — For new `if x:` blocks, AST-parse the changed file, find the enclosing function, check whether `x` has a callable signature at the call site where it could be None/False. This is a heuristic; don't overreach.

These are **advisory flags**, not blocks. They populate a `pre_check_flags` array that the LLM review checks see as input.

### 3. Parallel review runner

New file `megaplan/parallel_review.py`, mirroring `megaplan/parallel_critique.py`. Same architecture: `ThreadPoolExecutor`, one agent per check, each with its own session via `SessionDB`, writes findings to a pre-populated template slot. Concurrency of 2 (same as critique). Include the MiniMax→OpenRouter fallback pattern.

Important: each check agent gets **the original issue text + the full git diff + the finalize.json artifacts**, nothing else. No plan, no critique history, no gate summary. The whole point is that these checks are anchored to the issue, not the plan.

### 4. Prompt builders for single-check review

In `megaplan/prompts/review.py`, add:
- `single_check_review_prompt(state, plan_dir, root, check, output_path)` — mirrors `single_check_critique_prompt` — single focused prompt for one check.
- `_write_single_check_review_template(plan_dir, state, check, filename)` — pre-populates the output file with the check's ID.
- `_build_review_checks_template(plan_dir, state, checks)` — builds the per-check template list.

Keep `_review_prompt()` as-is. It still runs as the "criteria_verdict" check in heavy mode.

### 5. Handler integration

In `megaplan/handlers.py` `handle_review()`:
- Read `configured_robustness(state)`
- If `standard` or `light` → run the existing single-call review unchanged
- If `heavy` → run the mechanical pre-checks, then run `parallel_review()` across REVIEW_CHECKS + the existing criteria-based review-as-check. Merge all flags into one `review.json`

The output shape adds a `checks` array alongside the existing `review_verdict`, `criteria`, `issues`, `rework_items`, `task_verdicts`, `sense_check_verdicts`, `summary`. Back-compat: existing consumers that only look at `review_verdict` / `rework_items` keep working.

### 6. Feedback loop — how flags flow back

This is the tricky part. The review runs after execute. If it raises blocking flags, where does control go?

**Decision: reuse the existing gate → revise/re-execute loop, not a new review-specific loop.**

Concretely:
- If `review_verdict == "needs_rework"` with blocking flags, the handler writes them to `rework_items` as today.
- The execute loop in `evals/run_evals.py` already handles `needs_rework` by going back to revise or re-execute based on the rework type. No new routing logic.
- Add a new field `rework_directive.source = "review_{check_id}"` so the executor knows the provenance and can prioritize.
- **Max review iterations cap at 2** (configurable). After 2 rounds of needs_rework from the review, escalate. Otherwise the same check can fire forever on tasks the model can't solve.
- Review flags **cannot re-raise concerns the gate already settled**. Before raising a coverage/placement/parity flag, the review check must check `gate.settled_decisions` — if the concern matches a settled decision, downgrade to "significant" (info) rather than "blocking". This prevents the gate-override deadlock we hit before.

### 7. Severity ladder (mirrors critique)

Each review flag has:
- `blocking` — triggers `needs_rework`, forces another revise/execute pass
- `significant` — logged, shown to gate for future iterations, doesn't auto-block
- `minor` — info only, aggregated into summary

### 8. Flag tracking across review iterations

Mirror critique's flag registry. Each review check's findings get IDs like `REVIEW-COV-001`. Status transitions open → verified → resolved across iterations, just like critique flags. Read `megaplan/_core` flag registry helpers — reuse them, don't duplicate.
