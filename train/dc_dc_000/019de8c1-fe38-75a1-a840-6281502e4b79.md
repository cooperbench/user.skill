> AGENT

No, I would not package all executor/orchestrator skills into one runtime skill.

Better pattern:

1. Keep one small **ArtAgents entrypoint skill**
   It defines canonical concepts, commands, and hard rules:
   `orchestrators coordinate`, `executors run work`, `elements render/customize`.

2. Keep **per-executor/per-orchestrator SKILL.md files**
   Moirae, VibeComfy, render, transcribe, etc. stay local to their folder. Load them only when that executor is relevant.

3. Generate a lightweight **runtime index**
   Something like:

   ```bash
   python3 pipeline.py executors list --json
   python3 pipeline.py orchestrators list --json
   python3 pipeline.py elements list --json
   ```

   The agent sees IDs, type, description, folder, and maybe `skill_file`, but does not ingest every skill body.

4. Enforce structure in CI/doctor
   Add a repo-structure check so developers cannot accidentally put VibeComfy under `orchestrators`, revive `performers/conductors`, or create an executor folder missing `executor.yaml`, `run.py`, or `SKILL.md`.

So the answer is: **one entrypoint skill plus generated registry index, not one giant merged skill**.

A giant runtime skill would hide structural errors, bloat context, and make stale docs more likely. The source of truth should be the folder contract and manifests; the runtime skill should only route the agent to the right folder-level skill.

Short answer: `pipeline.py` is understandable historically, but it is no longer the best name for the *gateway*.

I would not rename it to `create`, though. `create` is too narrow because the same entry point also does `doctor`, `setup`, `orchestrators`, `executors`, `elements`, `audit`, and data fetching. The cleanest conceptual shape is:

```bash
python3 artagents.py ...
# or eventually:
artagents ...
```

Then `create` should be a subcommand/workflow:

```bash
python3 artagents.py create --topic "AI trying to be funny"
python3 artagents.py orchestrators run builtin.hype ...
python3 artagents.py executors run builtin.render ...
```

So my recommendation is:

- Keep `pipeline.py` for compatibility for now.
- Add a clearer alias later: `artagents.py` or a console command named `artagents`.
- Add `create` as a workflow/orchestrator, not as the whole command name.
- Eventually make `pipeline.py` a thin compatibility wrapper that prints/dispatches to the new `artagents` gateway.

On levels: yes, `artagents/executors/`, `artagents/orchestrators/`, and `artagents/elements/` being inside the package is right. They are importable runtime concepts, not docs or loose assets. The package should contain things the system can discover, validate, inspect, and run.

The parts I’d still watch:

- Top-level `bin/` is acceptable as compatibility/direct launchers, but visually noisy. Long term, the cleaner model is one gateway plus only a few necessary direct launchers.
- Top-level `agents/` is okay if external agent tooling expects it. If it is just docs/config, it should stay small.
- Any “custom nodes” or integration-specific payloads should not sit at root. They should belong under the owning executor, e.g. `artagents/executors/vibecomfy/...`, unless they are true shared third-party fixtures.
- `.artagents/elements/` is correctly separate from `artagents/elements/`: local managed/override workspace versus bundled package source.
- `artagents/pipeline.py` is now the most confusing internal name. It sounds like the whole product, but it is partly legacy hype-pipeline plumbing plus gateway support. Eventually I’d split/rename internals, but not rush it unless confusion keeps happening.

So: structure is mostly at the right level now. The biggest naming improvement would be `artagents` as the gateway and `create` as a first-class orchestrator command.
