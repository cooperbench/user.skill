## Things still wrong or ambiguous

Phase 0 is not “schema only, no behavior change.” §15 says add `bot_id`/`topic_id`, backfill, then set `NOT NULL` (§15, lines 375–396). But current inserts still write neither column: inbound `messages` inserts only direction/sender/content/etc. ([app/services/inbound.py:161](/Users/user_c042661f/Documents/Veas/app/services/inbound.py:161)), outbound inserts omit them too ([app/services/messaging.py:55](/Users/user_c042661f/Documents/Veas/app/services/messaging.py:55), [app/services/messaging.py:84](/Users/user_c042661f/Documents/Veas/app/services/messaging.py:84)), and `bot_turns` inserts only prompt/model/user fields ([app/services/agentic.py:483](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:483)). Either Phase 0 must keep nullable/defaulted columns until Phase 1 lands, or it is a behavior-changing deploy that will break writes.

The bridge-candidate story is internally inconsistent. §3 says `bridge_candidates` get single `topic_id` and `proposed_by_bot_id` (§3, line 82), but §17.M says add `dyad_id` and “decide later whether to add `topic_id`/`bot_id`” (§17, line 479). That “later” is wrong. `dyad_id` prevents cross-dyad leakage, not cross-bot or cross-topic leakage inside the same dyad. A career coach and mediator sharing a dyad cannot safely share one bridge queue without bot/topic scope.

The “solo bot: Axis A collapses” claim is only aspirational. The write schemas still expose raw `about_user_id`, `owner_user_id`, `source_user_ids`, and OOB `owner_id` with no binding-level validation ([tool_schemas.py:815](/Users/user_c042661f/Documents/Veas/tool_schemas.py:815), [tool_schemas.py:884](/Users/user_c042661f/Documents/Veas/tool_schemas.py:884), [tool_schemas.py:954](/Users/user_c042661f/Documents/Veas/tool_schemas.py:954), [tool_schemas.py:1041](/Users/user_c042661f/Documents/Veas/tool_schemas.py:1041)). “The agent never picks shared” (§2, line 62) is not a design invariant unless tools reject illegal scopes.

## Missed Couplings

`TurnContext` is the real dependency hub, and the doc under-specifies it. Today it has `user`, mandatory `partner`, message ids, phase state, OOB owners, hot context text, but no `bot_id`, `topic_id`, `binding_id`, `channel_id`, or participants shape ([app/services/turn_context.py:16](/Users/user_c042661f/Documents/Veas/app/services/turn_context.py:16)). `_run_agentic` constructs it after resolving `settings.bot_id`, `partner_of`, and global hot context ([app/services/agentic.py:678](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:678), [app/services/agentic.py:686](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:686), [app/services/agentic.py:725](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:725)). If scope is not on `TurnContext`, every tool has to rediscover it or trust the model.

The first pass noted burst coalescing, but missed newer-inbound suppression. `_newer_inbound_exists` suppresses sends by `sender_id` only ([app/services/agentic.py:612](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:612)); `send_message_part` has the same user-only query ([app/services/tools/read_tools.py:166](/Users/user_c042661f/Documents/Veas/app/services/tools/read_tools.py:166)). In a multi-bot world, a message to the finance bot can cancel the mediator’s final send unless these checks include bot/channel/thread.

Global pause is deeper than §9’s “pause/resume per `(user, bot)`.” `system_state.is_paused` reads a single `global_pause` key ([app/services/system_state.py:23](/Users/user_c042661f/Documents/Veas/app/services/system_state.py:23)); inbound pause supersedes all user-facing scheduled jobs ([app/services/inbound.py:136](/Users/user_c042661f/Documents/Veas/app/services/inbound.py:136)); the scheduler switches to heartbeat-only when globally paused ([app/services/scheduled_jobs.py:75](/Users/user_c042661f/Documents/Veas/app/services/scheduled_jobs.py:75)). Moving pause into `user_bot_state` is not a local refactor.

`consult_perspective` is also not topic-aware. It clones the same `ctx`, same `partner`, same `protected_owner_ids`, same hot context, and grants the consult-phase read tools ([app/services/tools/consult_perspective.py:105](/Users/user_c042661f/Documents/Veas/app/services/tools/consult_perspective.py:105), [app/services/tools/consult_perspective.py:139](/Users/user_c042661f/Documents/Veas/app/services/tools/consult_perspective.py:139)). If cross-topic policy is “explicit” or “forbidden,” consult must inherit that policy structurally, not just in prose.

The prompt/audit design is underspecified. `bot_turns` stores `system_prompt_version` and full `prompt_snapshot`, but no bot identity today ([app/services/agentic.py:483](/Users/user_c042661f/Documents/Veas/app/services/agentic.py:483)). Adding `bot_id` is necessary but not enough; six months from now, you will need to know `BotSpec` code version, prompt renderer version, tool schema version, and hot-context builder version for an audit question.

Onboarding is broader than state storage. There is a hard-coded mediator welcome in inbound ([app/services/inbound.py:23](/Users/user_c042661f/Documents/Veas/app/services/inbound.py:23)), a global `users.onboarding_state` in the model ([app/models/user.py:16](/Users/user_c042661f/Documents/Veas/app/models/user.py:16)), and first-contact prompt rendering keyed from that global state ([app/services/prompts.py:446](/Users/user_c042661f/Documents/Veas/app/services/prompts.py:446)). §9 mentions `user_bot_state`, but not per-bot welcome copy, first-turn behavior, or migration semantics for users already welcomed by mediator.

## Long-Term Pain Points

`topic_ids uuid[]` is the wrong durable shape for multi-topic artifacts (§2, line 56; §17, line 444). It makes “who tagged this topic, when, why, with what confidence?” impossible without rewriting the row. It also blocks per-topic lifecycle: retiring career relevance while keeping relationship relevance becomes an array edit with no audit trail. Use a join table for artifacts that can truly be multi-topic.

“One primary topic per bot” is fine only as a launch default. The doc claims future many-to-one flexibility (§4, line 109), but the write rule lets an agent fully override to any topic (§7, line 233). That is not flexibility; it is ambient write authority. The durable rule should be: default own topic, allow configured write scopes, record why cross-topic writes happened.

Per `(topic, user)` status with `NULL = pair` (§6, lines 169–182) is workable but under-modeled. It assumes “pair” means exactly one dyad, but `topic_status` has no `dyad_id`. If two dyads share `relationship`, the pair-level row collides. The table needs binding/dyad scope, not just topic/user.

“All statuses injected into every bot’s system prompt” (§6, line 197; §13, line 348) undermines `cross_topic_policy`. A bot with `"forbidden"` still sees status headlines unless status injection is also policy-gated. “Headline verbatim” in the peek (§7, line 252) is especially risky because headlines will become tiny summaries of sensitive domains.

The split-rather-than-parametrize plan for solo/dyad builders is right but incomplete. Prompt and hot context split is not enough; the tool registry, allowed tools, OOB policy, bridge tools, escalation tools, scheduler handlers, and `TurnContext` type need participant-shape-specific contracts. Otherwise solo bots will merely hide dyad affordances in prompt text while the tools remain callable.

`bot_id text` should not remain ambiguous (§17.F, line 467). Use an FK with `ON DELETE RESTRICT`. Text attribution columns without constraints will create orphaned audit rows, impossible joins, and silent typos.

## Missing Topics

The doc needs an explicit authorization model: which bot can read/write which topics, for which binding, under which participant shape. `scope="all"` (§7, line 226) is not a permission model.

It also needs channel identity and account-linking as a Phase 0/1 design concern, not Phase 4 handwaving. Current users are keyed by unique `phone` ([migrations/0001_init.sql:10](/Users/user_c042661f/Documents/Veas/migrations/0001_init.sql:10)); Discord reuses that field for Discord ids ([app/services/discord.py:176](/Users/user_c042661f/Documents/Veas/app/services/discord.py:176)). Multi-transport bots will break user identity before the second bot is useful.

Missing too: per-bot spend caps, per-bot eval baselines, admin UI filters, RLS/policy changes, deletion/export semantics across topics, and migration validation queries proving no unscoped rows remain.

## Most-Dangerous Open Question

The most dangerous open question is §17.E, cross-bot user identity. If left ambiguous, routing, bindings, privacy, status injection, and topic sharing all rest on unstable identity. Retrofitting identity merge later is expensive and privacy-sensitive: you may have already written memories, OOB, feedback, and prompt snapshots under duplicate humans. That is the kind of mistake that cannot be cleaned up with a simple migration.

## Bottom Line

The doc has the right nouns, but it still treats multi-agent as mostly “add columns and route through BotSpec.” The hard part is not bot identity; it is enforcing scope in every place the current system assumes one dyad, one transport, one global pause, one prompt family, and one conversation stream. Without binding-aware `TurnContext`, FK-backed `bot_id`, join-table topic membership, and explicit read/write authorization, this design will ship as a leaky mediator with labels, not a multi-agent platform.
