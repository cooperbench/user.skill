> AGENT

It’s a deliberate exception in the execution-queue builder.

The normal rule is in [schema/__init__.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/schema/__init__.py#L326): once the plan is tracking objective work at all, `next` stops showing the whole mechanical backlog and only shows objective IDs that are explicitly in `plan["queue_order"]`. If the plan has tracked objective IDs via clusters/overrides but no queued IDs yet, it returns an empty executable set. That is why non-autofix mechanical findings drop out of `next` and wait for planning.

Autofix items get a special bypass in [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L116) and [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L298). `_auto_promoted_autofix_ids()` scans `plan["clusters"]` for auto-clusters whose `action` contains `desloppify autofix ...`, and unions those member IDs into `explicit_queue_ids` even if `queue_order` is empty. That is the whole trick.

Those autofix clusters exist because post-scan auto-clustering groups issues and assigns an action string from detector metadata. The chain is:
[auto_cluster_sync_issue.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/auto_cluster_sync_issue.py#L171) creates/updates clusters,
[cluster_strategy.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_strategy.py#L101) makes the action `desloppify autofix <fixer> --dry-run`,
and detectors like `unused`/`logs` are marked `action_type="auto_fix"` in [catalog_entries.py](/Users/user_c042661f/Documents/desloppify/desloppify/base/registry/catalog_entries.py#L7).

What the user sees in `next` is then cleaned up by cluster collapse: the promoted member issues are collapsed back into one cluster card with an autofix hint in [plan_order.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/plan_order.py#L152) and [plan_order.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/plan_order.py#L206). There’s a direct regression test for the behavior in [test_sync_split_modules_direct.py](/Users/user_c042661f/Documents/desloppify/desloppify/tests/engine/test_sync_split_modules_direct.py#L720).

One nuance: “auto_fix detector” is not enough by itself. If a detector also has `needs_judgment=True`, `grouping_key()` returns `None` in [cluster_strategy.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_strategy.py#L13), so it won’t become one of these auto-promoted autofix clusters.

So the short version is:
1. Non-autofix mechanical work is backlog-first once a plan exists.
2. Autofix auto-clusters are explicitly promoted into the execution queue.
3. `next` then renders that promotion as a single autofixable batch.

> DEVELOPER

so do they just end up active queue items like the subjective analysis flagged issues? Or are they injected?

> AGENT

Not injected into `plan["queue_order"]`.

They do become active execution items for `next`, but via snapshot-time promotion, not plan injection. The path is in [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L116) and [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L298): autofix cluster members are added to `explicit_queue_ids` in memory when the cluster is `auto` and its action is a `desloppify autofix ...` command. Then `next` treats them as execution items for that run, and cluster collapse turns them back into one batch card.

So the model is:

- Autofix clusters: active in `next`, but not injected into `queue_order`.
- Workflow/triage items: actually injected into `queue_order`.
- Subjective dimensions/review work: mostly surfaced by lifecycle partitions, not by this autofix promotion path.

If you want the precise distinction:
- “Injected” means persisted into the living plan.
- Autofix promotion is ephemeral: computed from `plan["clusters"]` each time the queue snapshot is built.

> DEVELOPER

but why aren't they just work_items that are default shown like the subjective issues?

> AGENT

Because they belong to different queue phases.

Subjective work is treated as lifecycle work, so the snapshot builder creates dedicated partitions for it and can surface it without `queue_order`. That happens in [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L153), [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L193), and [snapshot.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/snapshot.py#L218):
- initial subjective review can become the whole execution queue
- postflight subjective review can become the whole execution queue
- workflow and triage also have their own partitions

Mechanical findings are different. They are objective execution work, and objective execution is backlog-first once a plan exists. That rule is in [schema/__init__.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/schema/__init__.py#L326). Because the high-value defect was narrow.

The real fragility was:
- autofix promotion depended on action-string matching
- cluster rendering independently repeated the same inference

That can be fixed cleanly by making cluster semantics explicit. Once that data exists, the affected callers become simple.

- fix the semantic lie at the data source
- remove the most brittle string sniffing
- avoid redesigning unrelated queue semantics in the same change

That is usually the more beautiful move in a live codebase: make one truth explicit, propagate it through the few places that need it, and stop before the refactor becomes a theory project.

> DEVELOPER

What would you do to make it holsitically elegant?

> AGENT

I’d make one stronger abstraction boundary: `queue semantics` should be a first-class normalized model, not something reconstructed from plan IDs, item kinds, detector metadata, and cluster fields in different places.

Holistically elegant would look like this:

1. Define one canonical semantic shape for anything that can appear in queue resolution.
   For example:
   - `domain`: `objective | subjective | workflow | triage`
   - `visibility_policy`: `planned_only | lifecycle_required | ephemeral_autopromote`
   - `action_type`: `auto_fix | refactor | manual_fix | reorganize | review`
   - `source`: `state_item | synthetic_item | cluster`

2. Normalize into that shape exactly once.
   - state work items normalize when queue items are built
   - clusters normalize when plan loads / clusters sync
   - workflow/triage items normalize when synthetic items are created

3. Make queue selection operate only on that model.
   Then `build_queue_snapshot()` stops caring about:
   - prefix checks
   - command substrings
   - detector-specific special cases
   - whether something came from a cluster or issue

   It just asks:
   - is this lifecycle-required?
   - is this explicitly planned?
   - is this eligible for ephemeral execution?
   - does it count toward objective backlog?

4. Separate raw plan persistence from resolved execution semantics.
   - `plan.json` remains the durable source of intent/history
   - queue resolution produces a fully normalized in-memory execution model
   - rendering and ranking consume only that resolved model

That would make the system more elegant because each layer would have one job:

- state/plan: persistence
- normalization: semantics
- snapshot: lifecycle gating and visibility
- ranking/rendering: presentation

What I would not do is flatten subjective and autofix into one behavior model. The elegant system still keeps that distinction. The difference is that the distinction becomes explicit in normalized semantics instead of being spread across ad hoc rules.

So the next real step toward holistic elegance would be:
- introduce a small normalized queue-semantic object for built queue items
- migrate `workflow::` / `triage::` prefix logic behind that
- keep raw string IDs only as persistence identifiers, not as behavioral signals

That would be the point where the queue starts to feel architecturally finished rather than just cleaned up.
