        # Implementation Plan: Fix Pane System Structural Issues

## Overview

The pane system uses `position: fixed` elements positioned via CSS transforms (strategy pattern in `src/shared/hooks/panePositioning/strategies/`). Four panes exist: editor (top), generations (bottom), tools/shots (left), tasks (right). Each has a `PaneControlTab` (the handle) that also uses the position strategies.

Three bugs are reported, all on **desktop** when multiple panes are locked simultaneously—a scenario that became possible after the editor (top) pane was recently added.

**Key files:**
- Position strategies: `src/shared/hooks/panePositioning/strategies/{Top,Bottom,Left,Right}PaneStrategy.ts`
- Control tab: `src/shared/components/PaneControlTab.tsx`
- Lock policy: `src/shared/contexts/usePaneLockPolicyState.ts`
- Pane context: `src/shared/contexts/PanesContext.tsx`
- Pane components: `src/features/gallery/components/GenerationsPane/GenerationsPane.tsx`, `src/features/editor/components/EditorPaneTab.tsx`, `src/features/tasks/components/TasksPane/TasksPane.tsx`

## Step 1: Centralize editor-aware generations height in `PanesContext.tsx`
**Scope:** Medium

**Problem:** The editor-aware `effectiveHeight` is computed ad-hoc in `GenerationsPaneSurface` (`src/features/gallery/components/GenerationsPane/GenerationsPane.tsx:95-98`), but three other consumers still use the raw `generationsPaneHeight`:
- `GenerationsPaneTab` passes raw height as `paneDimension` → wrong handle position (Bug 1)
- `src/shared/hooks/layout/useBottomOffset.ts:17` returns raw height → side pane handles offset incorrectly
- `src/app/components/LayoutMainContent.tsx:41` uses raw height for `paddingBottom` → main content padding wrong

**Fix:**
1. **Add `effectiveGenerationsPaneHeight`** to `src/shared/contexts/PanesContext.tsx`. Compute it in the `PaneLayoutContext` value using the existing `editorPaneHeight` and lock/open state already available in `PanesProvider`:
   ```ts
   const editorVisible = locks.editor || isEditorPaneOpenState;
   const effectiveGenerationsPaneHeight = editorVisible
     ? Math.min(generationsPaneHeight, Math.max(window.innerHeight - editorPaneHeight, 120))
     : generationsPaneHeight;
   ```
2. **Export it** through the `PaneLayoutContextType` interface and `usePanes()` hook (`src/shared/contexts/PanesContext.tsx:60-69`).
3. **Update `src/shared/hooks/layout/useBottomOffset.ts:17`**: Replace `generationsPaneHeight` with `effectiveGenerationsPaneHeight`.
4. **Update `src/app/components/LayoutMainContent.tsx:41`**: Replace `generationsPaneHeight` with `effectiveGenerationsPaneHeight` in the `paddingBottom` calculation.
5. **Update `GenerationsPaneTab`** in `src/features/gallery/components/GenerationsPane/GenerationsPane.tsx:52`: Pass `effectiveGenerationsPaneHeight` as `paneDimension` instead of `pane.generationsPaneHeight`.
6. **Simplify `GenerationsPaneSurface`** in `src/features/gallery/components/GenerationsPane/GenerationsPane.tsx:91-98`: Remove the local `effectiveHeight` computation and use `effectiveGenerationsPaneHeight` from `usePanes()` instead.

## Step 2: Fix scroll within generations pane when editor pane is active (`GenerationsPaneGallery.tsx`)
**Scope:** Small

**Problem:** When the editor pane reduces the generations pane's available height, the flex scroll chain breaks. The inner wrapper at `src/features/gallery/components/GenerationsPane/GenerationsPane.tsx:115-119` uses `flex flex-col h-full`, and the gallery scroller at `src/features/gallery/components/GenerationsPane/components/GenerationsPaneGallery.tsx:61-63` uses `flex-grow overflow-y-auto`. Without `min-h-0` on the flex parent, the child's intrinsic content size prevents it from shrinking below its content, so `overflow-y-auto` never activates.

**Fix:**
1. **Add `min-h-0`** to the inner flex wrapper in `src/features/gallery/components/GenerationsPane/GenerationsPane.tsx:116`:
   ```tsx
   className={cn(
     'flex flex-col h-full min-h-0',
     ...
   )}
   ```
2. **Verify** that the `GenerationsPaneControls` header (`flex-shrink-0`) and `GenerationsPaneGallery` scroller (`flex-grow overflow-y-auto`) now correctly partition the reduced height.

## Step 3: Fix tasks pane unlock stuck-open state (`usePaneLockPolicyState.ts`)
**Scope:** Small

**Problem:** In `src/shared/contexts/usePaneLockPolicyState.ts:81-83`, `isTasksPaneOpenState` is set `true` when tasks lock but never cleared on unlock:
```ts
if (lockKey === 'tasks' && isLocked) {
  setIsTasksPaneOpenState(true);
}
```
This feeds `programmaticOpen: true` into `useSlidingPane` via `src/features/tasks/components/TasksPane/hooks/useTasksPaneSlidingPane.ts:24`. When `isLocked` goes false, `isOpen` in `useSlidingPane` (`src/shared/hooks/useSlidingPane.ts:21`) remains `true` because `programmaticOpen` is still `true`. The `onOpenChange(false)` callback at `src/shared/hooks/useSlidingPane.ts:41-47` never fires, so the programmatic state never clears. The pane appears unlocked but stays visually open.

**Fix:**
1. **In `src/shared/contexts/usePaneLockPolicyState.ts:81-83`**, change:
   ```ts
   if (lockKey === 'tasks' && isLocked) {
     setIsTasksPaneOpenState(true);
   }
   ```
   to:
   ```ts
   if (lockKey === 'tasks') {
     setIsTasksPaneOpenState(isLocked);
   }
   ```
   This clears `isTasksPaneOpenState` on unlock, allowing the pane to close.

2. **Fix tablet lock normalization** in `src/shared/contexts/usePaneLockPolicyState.ts:44-50`: The `newLocks` object is missing the `editor` key. Change:
   ```ts
   newLocks = {
     shots: firstLocked === 'shots',
     tasks: firstLocked === 'tasks',
     gens: firstLocked === 'gens',
   };
   ```
   to:
   ```ts
   newLocks = {
     shots: firstLocked === 'shots',
     tasks: firstLocked === 'tasks',
     gens: firstLocked === 'gens',
     editor: firstLocked === 'editor',
   };
   ```
