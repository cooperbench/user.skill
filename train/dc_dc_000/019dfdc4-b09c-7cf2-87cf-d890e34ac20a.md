        # Implementation Plan: Element Manifest v1 Interop Layer

## Overview
Reigh currently stores custom sequence components as `SequenceComponentMetadata` on `sequence-component` resources, with top-level fields such as `code`, `schemaJson`, `defaultsJson`, `controlsManifest`, `assetSlots`, `clipType`, `themeId`, and DB/resource identity flowing through `src/features/resources/hooks/useResources.ts`, `src/tools/video-editor/lib/sequence-component-catalog.ts`, `src/tools/video-editor/sequences/SequenceComponentRegistryContext.tsx`, and SequenceCreator save/load paths.

ArtAgents elements are file-backed definitions with an `element.yaml`/JSON-like manifest plus `component.tsx`, currently shaped around `id`, `kind`, `schema`, `defaults`, `metadata`, `dependencies`, descriptions, keywords, pack/source provenance, and catalog lookup. The lightest viable Reigh change is not a UI rewrite or DB migration. It is a TypeScript-only canonical manifest contract plus adapters that synthesize the manifest from existing Reigh metadata and can map parsed ArtAgents element manifests into that same contract.

## Main Phase

### Step 1: Define the canonical manifest type (`src/tools/video-editor/sequences/elementManifest.ts`)
**Scope:** Medium
1. Add a new `ElementManifestV1` type with `version: 1` and the requested shared blocks:
   - `id`: stable element id, usually Reigh resource id or clipType-derived id.
   - `kind`: support at least `sequence-component`, plus ArtAgents-style `effect`, `animation`, `transition` as string-compatible values.
   - `runtime`: runtime family and component/code references, including Reigh inline TSX code and ArtAgents file component path when available.
   - `contract`: `schemaJson`, `defaultsJson`, `controlsManifest`, `assetSlots`, and dependency data.
   - `catalog`: label/name, description, short description, keywords, and `whenToUse` when present.
   - `provenance`: source system (`reigh-db`, `artagents-file`, etc.), resource id, pack id, user/creator metadata, public/editable flags, and timestamps when available.
   - `compatibility`: Reigh `clipType`, `themeId`, `clipTypeAliases`, browser/worker capability hints, and ArtAgents `kind`/`packId` compatibility data.
2. Keep the type intentionally JSON-serializable and dependency-free. Do not introduce YAML parsing in Reigh for v1 unless a caller already provides parsed data.
3. Export small helper types for adapter inputs, especially `ArtAgentsElementManifestLike` for parsed ArtAgents `element.yaml` data and optional component path/code.

### Step 2: Add Reigh import/export adapters (`src/tools/video-editor/sequences/elementManifest.ts`)
**Scope:** Medium
1. Implement `sequenceComponentMetadataToElementManifest(metadata, options)` that maps top-level Reigh fields into the canonical manifest while preserving existing meanings:
   - `metadata.code` -> `runtime.component.code` or equivalent inline component slot.
   - `metadata.schemaJson` and `metadata.defaultsJson` -> `contract`.
   - `metadata.controlsManifest` and `metadata.assetSlots` -> `contract`.
   - `metadata.clipType` and `metadata.themeId` -> `compatibility.reigh`.
   - resource id/public/user data from `SequenceComponentResource` options -> `id`/`provenance`.
2. Implement `elementManifestToSequenceComponentMetadata(manifest, options)` that reconstructs a Reigh-compatible `SequenceComponentMetadata` from a manifest. Existing top-level aliases must remain populated, because current UI/runtime code reads them directly.
3. Implement `artAgentsElementManifestToElementManifest(input, options)` for parsed ArtAgents manifests. Map ArtAgents `schema`, `defaults`, `metadata`, `pack_id`, `dependencies`, `description`, `short_description`, and `keywords` into the canonical shape. If ArtAgents has no Reigh `clipType`, derive a deterministic compatibility alias such as `artagents:<kind>:<id>` only in the returned manifest, not as a persisted Reigh clipType unless the caller explicitly asks.
4. Add a conservative conflict rule: when both manifest fields and legacy top-level Reigh fields exist, the adapter should prefer the existing top-level Reigh fields for runtime compatibility and expose the nested manifest as derived interop metadata.

### Step 3: Extend metadata compatibility without migrating data (`src/features/resources/hooks/useResources.ts`)
**Scope:** Small
1. Add optional `elementManifest?: ElementManifestV1` to `SequenceComponentMetadata`.
2. Keep `controlsManifest`, `assetSlots`, `schemaJson`, `defaultsJson`, `code`, `clipType`, and `themeId` as top-level fields. Do not remove or rename them.
3. Avoid DB migrations. Existing saved resources without `elementManifest` should continue to load exactly as they do now.

### Step 4: Thread manifest synthesis through runtime/catalog surfaces (`src/tools/video-editor/lib/sequence-component-catalog.ts`, `src/tools/video-editor/sequences/SequenceComponentRegistryContext.tsx`, `src/tools/video-editor/sequences/registry.ts`)
**Scope:** Medium
1. In the sequence component catalog type, expose a derived manifest helper or add `elementManifest` to `SequenceComponentResource` only through the existing metadata shape. Avoid changing catalog behavior or indexing semantics.
2. In `SequenceComponentRegistryContext.tsx`, when building `DynamicSequenceComponentEntry`, continue to use current top-level fields for compile and asset-slot behavior, but optionally attach or derive manifest metadata if useful for downstream inspection.
3. If `DynamicSequenceComponentEntry` gets a `manifest?: ElementManifestV1` field, update tests and keep existing consumers compatible.
4. Keep `resolveSequenceClipEntry`, `resolveClipCapabilityDescriptor`, and materialization semantics unchanged except for optional manifest pass-through. DB entries must still resolve by `custom:` prefix stripping and retain browser-only capabilities.

### Step 5: Save/export manifests from SequenceCreator without UI redesign (`src/tools/video-editor/components/SequenceCreator/SequenceCreatorPanel.tsx`, `src/tools/video-editor/components/SequenceCreator/sequenceGenerationService.ts`)
**Scope:** Medium
1. In the save path where `SequenceComponentMetadata` is assembled, call `sequenceComponentMetadataToElementManifest` after constructing metadata, then store it as `metadata.elementManifest` while keeping all existing top-level aliases.
2. For loaded library components, do not require `elementManifest`; synthesize it on demand from existing metadata.
3. Do not change editor controls, insert/replace behavior, smoke rendering, asset-slot defaulting, or `custom:` clipType compatibility.

### Step 6: Add focused unit tests (`src/tools/video-editor/sequences/elementManifest.test.ts`, existing sequence tests)
**Scope:** Medium
1. Add tests for Reigh export:
   - A full `SequenceComponentMetadata` with `controlsManifest`, `assetSlots`, DB/resource id, `clipType`, and `themeId` maps into all manifest blocks.
   - Export does not mutate metadata and preserves top-level alias values.
2. Add tests for Reigh import:
   - A manifest round-trips back into `SequenceComponentMetadata` with `code`, `schemaJson`, `defaultsJson`, `controlsManifest`, `assetSlots`, `clipType`, and `themeId` present at top level.
3. Add tests for ArtAgents import:
   - A parsed `text-card`-style manifest with `id`, `kind`, `schema`, `defaults`, `metadata`, `pack_id`, descriptions, keywords, and dependencies maps into canonical `runtime`/`contract`/`catalog`/`provenance`/`compatibility` blocks.
4. Update `src/tools/video-editor/sequences/registry.test.ts` or add a small new test if `DynamicSequenceComponentEntry` carries the optional manifest.
5. Add a SequenceCreator save-path test only if the existing tests already make this cheap; otherwise keep the proof at adapter/unit level to avoid brittle UI churn.
