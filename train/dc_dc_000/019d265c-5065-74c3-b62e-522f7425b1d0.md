## Overview

`handlers.py` (2723 lines) contains three execute paths that duplicate merge/observe/blocking logic with subtle inconsistencies and two critical bugs. The goal is one execute path, one recovery mechanism, no dead code, no duplication, with ~800 lines extracted into `megaplan/execution.py`.

**Key architectural insight:** The three paths differ along two axes: (1) prompt generation (full vs batch-scoped) and (2) post-processing (merge scope, artifact names, aggregate construction, response shape). The plan unifies post-processing into a single `_run_and_merge_batch()` core, while keeping prompt selection as a thin caller concern.

**Rerun semantics (FLAG-001 resolution):** `handle_execute` computes pending batches via `compute_task_batches(pending_tasks)`. When ≤1 pending batch, it uses `_execute_prompt` (full scope, all tasks in merge). When >1 pending batch, it uses `_execute_batch_prompt` per batch (scoped merge). The `--batch N` CLI uses global batch numbering via `compute_global_batches`. These are different entry points into the same `_run_and_merge_batch()` core — the caller decides prompt and merge scope, the core handles git observation, worker invocation, merge, artifacts, and evidence checks.

**Aggregate/timeout semantics (FLAG-002 resolution):** The auto-loop calls `_run_and_merge_batch()` iteratively and accumulates duration/cost/traces itself, then builds one aggregate `execution.json` and one history entry — preserving current behavior including the timeout case where aggregate is always written. `_handle_execute_one_batch` (--batch N) calls the same core once and writes its own per-batch history entry.

**Constraints:** 310 existing tests are the validation gate. No prompt changes needed.
