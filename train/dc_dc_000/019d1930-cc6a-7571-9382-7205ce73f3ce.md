## Current State

## Strategy: Keep Global CSS for Complex/Decorative, Use Tailwind for Layout & Utility

### Guiding Principles

1. **Don't rewrite what works** — Complex, stateful, animated, or highly decorative CSS stays in styles.css
2. **Use Tailwind where it shines** — Layout (flex/grid), spacing, responsive adjustments, and simple utility patterns move to component-level Tailwind classes
3. **Single source of truth for tokens** — Design tokens (colors, fonts, spacing, shadows) live in `tailwind.config.ts` and are referenced by both Tailwind utilities and CSS custom properties
4. **Incremental migration** — Convert one component at a time; visual regression checks after each

---

## Phase 0: Foundation — Design Tokens Bridge (1 step)

### Step 0.1: Create CSS custom properties from Tailwind config

Add a `base` layer in `src/tailwind.css` that generates CSS custom properties matching the Tailwind theme. This lets styles.css reference the same tokens without duplication.

```css
@tailwind base;
@tailwind components;
@tailwind utilities;

@layer base {
  :root {
    --color-background: #fbf8ef;
    --color-text: #2f2f2f;
    --color-muted: #6b7280;
    --color-border: #d8d4c7;
    --font-sans: 'Inter', sans-serif;
    --font-display: 'Space Grotesk', sans-serif;
    --font-mono: 'Space Mono', monospace;
    --shadow-sm: 0 2px 8px rgba(0, 0, 0, 0.03);
    --shadow-md: 0 4px 12px rgba(0, 0, 0, 0.06);
    --shadow-lg: 0 6px 15px rgba(0, 0, 0, 0.1);
  }
}
```

Then update `tailwind.config.ts` to reference these variables so both systems stay in sync. Gradually replace hardcoded hex values in styles.css with `var(--color-*)` references.

**Validation**: Site renders identically before and after.

## Anti-Patterns to Avoid

- **Don't use @apply extensively** — It defeats the purpose of Tailwind and creates a hidden dependency layer. Only use for genuinely reusable patterns that appear in 5+ places.
- **Don't duplicate styles** — If it's in Tailwind, remove it from CSS. If it's in CSS, don't also add Tailwind classes.
- **Don't fight Tailwind for complex states** — Anything involving ::before/::after with content, complex nth-child selectors, or multi-step animations stays in CSS.
- **Don't migrate .post-content children** — These styles target rendered markdown HTML where you can't add classes. Keep as CSS descendant selectors, possibly scoped with @layer.

## Strategy: Keep Global CSS for Complex/Decorative + JS-Coupled, Use Tailwind for Layout & Utility on JSX-Owned Surfaces

### Guiding Principles

1. **Don't rewrite what works** — Complex, stateful, animated, or highly decorative CSS stays in styles.css
2. **Respect JS-selector contracts** — Classes queried by legacy JS are frozen; restyle but never rename or remove them
3. **Use Tailwind where it shines** — Layout (flex/grid), spacing, responsive adjustments on JSX-owned surfaces
4. **Single source of truth for tokens** — CSS custom properties defined in a server-loaded stylesheet, referenced by both Tailwind theme and styles.css
5. **Incremental migration** — One component per commit, gated by automated visual regression tests
6. **Raw HTML surfaces migrate last** — `dangerouslySetInnerHTML` pages (Home, Assorted routes) must be converted to JSX before Tailwind classes can apply

## Anti-Patterns to Avoid

- **Don't rename frozen classes** — Any class in the Step 0.3 list must keep its original name. Add Tailwind alongside, never instead.
- **Don't add Tailwind to `dangerouslySetInnerHTML` surfaces** — These render static HTML strings; Tailwind classes there won't work until converted to JSX.
- **Don't define shared tokens in client-only stylesheets** — CSS custom properties go in `styles.css` (server-loaded), not `tailwind.css` (client bundle).
- **Don't use `@apply` extensively** — Only for patterns appearing in 5+ places.
- **Don't duplicate styles** — If it's in Tailwind, remove it from CSS and vice versa.
- **Don't fight Tailwind for complex states** — ::before/::after, nth-child, multi-step animations stay in CSS.

- **Don't overestimate the initial shrinkage** — Phase 2 migrates ~50–70 lines of layout CSS; the big reduction comes in Phase 4 after JSX conversion
