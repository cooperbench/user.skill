Yes. `--wgp-profile` is visible in the worker.

It is parsed in [source/runtime/worker/server.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/runtime/worker/server.py:251), and for WGP backend it mutates Wan2GP globals:

- `wgp_mod.force_profile_no = cli_args.wgp_profile`
- `wgp_mod.default_profile = cli_args.wgp_profile`

See [server.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/runtime/worker/server.py:679).

**What It Does For Wan2GP**

Wan2GP treats profile as the memory/offload strategy selector. In [Wan2GP/wgp.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/Wan2GP/wgp.py:3526):

- `force_profile_no` overrides the default profile globally.
- per-task `override_profile` can override it.
- `compute_profile()` picks task override unless it is `-1`.

Then `init_pipe()` changes the actual runtime behavior in [Wan2GP/wgp.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/Wan2GP/wgp.py:3547):

- profiles `2/4/5`: set explicit model/text-encoder/offload budgets.
- profile `3`: sets `budgets["*"] = "70%"`.
- profiles `3/4` with dual transformers: pins transformer memory.
- profile `3.5`: maps to MMGP profile `3` but disables pinned memory.
- profile `4.5`: maps to MMGP profile `4` and disables async transfers.
- finally calls `offload.profile(... profile_no=mmgp_profile ...)`, which is the real MMGP offload plan.

So `--wgp-profile 3` is not a quality knob. It is mostly VRAM/RAM residency, offload, cache, and transfer behavior. Wan2GP’s UI labels call the profiles roughly: 1 high RAM/high VRAM fast, 2 high RAM/low VRAM, 3 low RAM/high VRAM, 4 low RAM/low VRAM recommended, 5 fail-safe minimum.

**What Exists For VibeComfy Already**

There is already a numeric compatibility protocol in the worker: [source/runtime/vibecomfy_profile.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/runtime/vibecomfy_profile.py:1). It emits:

```bash
--memory-profile N
```

The VibeComfy adapter appends that to `vibecomfy.cli run --runtime embedded` in [source/models/comfy/vibecomfy_adapter.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/models/comfy/vibecomfy_adapter.py:461).

It resolves from:

- process default env: `VIBECOMFY_MEMORY_PROFILE`
- per-task `override_profile`
- for some Wan routes, default `3`

See [vibecomfy_adapter.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/models/comfy/vibecomfy_adapter.py:2270).

On the VibeComfy side, this is implemented in `/Users/user_c042661f/Documents/reigh-workspace/vibecomfy`:

- [vibecomfy/memory_profile.py](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/vibecomfy/memory_profile.py:16) maps profiles 1-5 to session config:
  - `1`: `highvram`, smart cache
  - `2`: `highvram`, `cache_lru=32`
  - `3`: `normalvram`, smart cache
  - `4`: `lowvram`, classic cache, reserve 2GB VRAM
  - `5`: `lowvram`, `cache_lru=1`, reserve 4GB VRAM, disable smart memory
- [vibecomfy/runtime/session.py](/Users/user_c042661f/Documents/reigh-workspace/vibecomfy/vibecomfy/runtime/session.py:815) translates that into embedded Comfy configuration / server CLI args.

There is also WanVideo-specific adaptation in the worker: `_wan_i2v_blocks_to_swap()` maps profile to WanVideo block swapping:

- profile `1/2`: `0`
- profile `3` or unset: `20`
- profile `4`: `30`
- profile `5`: `35`

See [vibecomfy_adapter.py](/Users/user_c042661f/Documents/reigh-workspace/reigh-worker/source/models/comfy/vibecomfy_adapter.py:2291).

**The Gap**

`--wgp-profile` itself is currently WGP-facing. In VibeComfy backend, the equivalent process-level knob is `VIBECOMFY_MEMORY_PROFILE`, not `--wgp-profile`.

So to “feed a similar thing into VibeComfy” cleanly, I’d do one of these:

1. Runtime/env path, no code change:
   ```bash
   REIGH_BACKEND=vibecomfy VIBECOMFY_MEMORY_PROFILE=3 python run_worker.py ...
   ```

2. Compatibility bridge, small code change:
   when `REIGH_BACKEND=vibecomfy` and `--wgp-profile N` is supplied, set `VIBECOMFY_MEMORY_PROFILE=N` if it is not already set. That makes existing launch scripts keep working.

Concretely, add near backend/profile resolution in `server.py`:

```python
if _uses_vibecomfy_backend() and cli_args.wgp_profile and "VIBECOMFY_MEMORY_PROFILE" not in os.environ:
    os.environ["VIBECOMFY_MEMORY_PROFILE"] = str(cli_args.wgp_profile)
```

Then the existing VibeComfy adapter path will automatically pass `--memory-profile N` to `vibecomfy.cli run`.

My read: the conceptual replication is already mostly done. The missing piece is aliasing the legacy worker flag `--wgp-profile` into the VibeComfy protocol so old launch commands don’t silently lose the intended memory profile.
