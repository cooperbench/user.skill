**What’s Right**
- The core premise is sound: keep `TopicEditor`, `AdminChatAgent`, and `LiveUpdateSocialAgent` as separate product loops while sharing runtime mechanics. The doc states this well in [docs/agent-loop-standardisation-and-live-update-social-plan.md](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/agent-loop-standardisation-and-live-update-social-plan.md:96).
- A shared `AgentTool` / registry is the right replacement for today’s drift-prone split between `TOPIC_EDITOR_TOOLS` and dispatch code in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:143), plus the admin chat `if/elif` dispatcher in [tools.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/admin_chat/tools.py:4555).
- Moving provider response normalization out of `TopicEditor` is correct. Today DeepSeek is converted into Anthropic-like blocks in [deepseek_client.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/common/llm/deepseek_client.py:35), while `TopicEditor` still owns extraction and assistant-message reconstruction in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:920) and [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:3220).
- Starting with recorder adapters instead of generic `agent_runs` tables is the right migration path. `TopicEditor` already has a meaningful run lifecycle in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:437), and storage has topic-editor-specific lease behavior in [storage_handler.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/common/storage_handler.py:913).

**Boundary Issues**
- Keep `src/common/agent_loop` narrow. It should own turn sequencing, provider adapters, tool call/result protocol, limits, and event emission. It should not know topics, Discord, social publishing, media semantics, or table names.
- Split `AgentTool` into two concepts: a portable `ToolSpec` with schema/side-effect metadata, and a loop-bound `ToolBinding` with handler, dependency requirements, argument injection, and auth context. Otherwise “shared registry” will become a global service locator.
- Do not put media resolution inside `agent_loop`. Existing media abstractions belong in something like `src/common/media_refs.py` or `src/features/summarising/publish_units.py`. The current canonical media-ref shape already exists in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:3700); preserve that as identity, and create a separate `ResolvedMedia` result. The doc’s proposed `MediaRef(..., url=...)` at [line 425](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/agent-loop-standardisation-and-live-update-social-plan.md:425) mixes stable identity with ephemeral resolution.
- Keep `SocialPublishService` as transport, not policy. The social agent should decide draft/media/target/action; the service should validate route, create durable publication records, and call providers.

**Over/Under-Specified**
- Over-specified: the initial shared package layout and type list in the doc are fine as a sketch, but `AgentLoopPolicy` risks becoming a god abstraction. Prefer concrete hooks: `build_initial_messages`, `inject_tool_args`, `on_text_without_tools`, `should_stop`, `classify_result`, `finalize`.
- Over-specified: social terminal decisions include both intent and transport mode (`publish_now`, `enqueue_post`, `publish_thread`). The environment mode in [line 530](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/agent-loop-standardisation-and-live-update-social-plan.md:530) should gate execution. The model decision should be more like `skip | draft | approve_post | needs_review`, with runtime converting that into draft/queue/publish.
- Under-specified: tool result contracts. `TopicEditor._tool_result_content` currently truncates read results to 2000 chars in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:930). Shared tools need typed result envelopes with truncation metadata, not just stringified JSON.
- Under-specified: idempotency. `TopicEditor` has DB-backed and in-process replay around write tools in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:994). The shared runtime needs an explicit idempotency contract for write/publish tools, or social posting retries will duplicate.
- Under-specified: async/sync boundaries. `TopicEditor` calls many sync DB methods inside an async loop; admin chat tools are mostly async. The registry should support async handlers and optionally wrap sync handlers deliberately.

**Implementation Risks**
- The plan says the social input packet should include the same `publish_units` Discord used, but successful structured publishes currently build them in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:2868) and then omit them from the returned successful result in [topic_editor.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/summarising/topic_editor.py:2967). You’ll need to persist or reconstruct them from topic summary plus source metadata.
- Queued social media is the biggest practical risk. `SocialPublishService.enqueue` serializes `media_hints` into `request_payload` in [social_publish_service.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/sharing/social_publish_service.py:147), but X posting expects local files via `media_hints` in [x_provider.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/sharing/providers/x_provider.py:48). Existing admin scheduled direct posts preserve temp downloads in [tools.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/admin_chat/tools.py:2061), which is not durable across deploys/restarts. Live-update social queueing should store media refs and resolve/download at execution time, or upload durable files to storage.
- The example live-update `SocialPublishRequest` will fail for X unless provider identity metadata is supplied. `XProvider` requires `user_details` in source metadata in [x_provider.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/features/sharing/providers/x_provider.py:29). The plan’s request at [line 475](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/docs/agent-loop-standardisation-and-live-update-social-plan.md:475) uses `user_id=0` and no `user_details`.
- Duplicate protection cannot rely only on preflight reads. Current DB helpers mostly dedupe by Discord `message_id` in [db_handler.py](/Users/user_c042661f/Documents/banodoco-workspace/brain-of-bndc/src/common/db_handler.py:2164). For topic-level duplicate safety, add a dedicated `topic_id` column or unique index on `live_update_social_runs(topic_id, platform, action)` and/or `social_publications` source metadata columns. JSON-only checks will be brittle and race-prone.
- Loop-level thread publishing is okay for immediate posting, but weak for queue mode. Reply chaining requires the first provider ref before later posts can be queued. If queued threads matter, introduce a native thread/group publication model rather than repeated independent service calls.

**Concrete Recommendations**
1. Build `common.agent_loop` around the new `LiveUpdateSocialAgent` first; do not migrate `TopicEditor` and `AdminChatAgent` immediately.
2. Extract existing media-ref and publish-unit functions from `topic_editor.py` before adding new social media logic.
3. Model `MediaRefIdentity` separately from `ResolvedMedia`; never persist Discord CDN URLs as the source of truth.
4. Add durable queued-publication media resolution before enabling `LIVE_UPDATE_SOCIAL_MODE=queue`.
5. Add social run/publication unique constraints for `topic_id` before any autonomous posting.
6. Make provider/account context explicit for bot-owned live updates instead of borrowing admin-chat `user_details`.
7. Keep `draft_social_post`, `skip_social_post`, and `record_social_decision` loop-specific; share only transport and low-level read/media tools.
