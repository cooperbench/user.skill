> AGENT

**Diagnosis:** Yes, this is structural. The project has several competing version authorities: `package.json` says `engines.node >=20.9.0`, `.nvmrc` says `20.18.0`, dependencies in `package-lock.json` require `^20.19.0 || >=22.12.0`, `nixpacks.toml` asks Nix for `nodejs_20` which resolves to old `20.6.1`, Railway Dashboard can override with `NIXPACKS_NODE_VERSION`, and there is also a `pnpm-lock.yaml` despite `packageManager: npm@10.8.2`. That is the deeper problem: runtime, package manager, lockfile, local dev, and deploy build are not governed by one enforceable contract.

Attempts 1-4 were mostly avoidable architectural drift. They were poking at Nixpacks behavior without a known source of truth for Node installation. Attempt 4 specifically exposed a platform boundary: `railway.toml` variables are deploy/runtime config, not necessarily build tool inputs. Reverting to baseline was a reasonable stabilization move. Setting `NIXPACKS_NODE_VERSION=20` in Dashboard was the right kind of iteration, because it tested the actual Railway/Nixpacks mechanism. The new `npm ci` failure is useful signal: you moved past “toolchain missing/wrong Node” into “dependency install itself fails.”

I would pick **A: switch to a hand-written Dockerfile with an explicit Node version**, probably `node:20.19.x` or newer Node 22 LTS if the app builds cleanly. For this app, Nixpacks is now adding more mystery than leverage. You do not need a complex platform buildpack for a Vite app. A small Dockerfile gives you one build/runtime image, one Node version, one package manager, and reproducible local verification with `docker build`. The maintenance cost is low compared with the time already spent chasing Nixpacks resolution behavior.

The cost of staying fragile is not theoretical. You just spent roughly an hour on one deploy class, with 5-7 failed deploys. If this happens once a week, that is 4-8 engineering hours/month plus broken confidence in deploys. If a bad deploy reaches users, the blast radius is the whole frontend: blank app, broken asset serving, failed healthcheck, or a restart loop. Even when Railway protects production by failing the build, the team still pays in blocked releases and context loss.

Recommended sequence:

1. First, get the actual `npm ci` error from Railway logs. Do not redesign around an unknown install failure.

2. Then standardize the contract: one package manager, delete the stale lockfile if unused, set `engines.node` and `.nvmrc` to the same concrete family, at least `20.19.x`.

3. Replace Nixpacks with a minimal Dockerfile and require `docker build .` or CI `npm ci && npm run build` before deploy. The important shift is that production stops being discovered by Railway at deploy time.
