        # Implementation Plan: Believable Discord Typing Behavior

## Overview
The repository already has most of the right seams for this: `app/services/pacer.py` owns pacing and typing pulse policy, `app/main.py` wires the live Discord pacer into the coalescer and agentic turn, `app/services/agentic.py` passes `before_paced_send` into final sends and incremental tool sends, `app/services/tools/read_tools.py` owns `send_message_part`, and `app/services/messaging.py` suppresses Discord's default pre-send typing when paced typing is active.

The critique does not show that the plan targeted the wrong code or root cause. It confirms the right boundary is the existing paced-send hook, but the hook contract is currently too coarse: every final or incremental send calls the same `before_paced_send(answer_text)` path, and `perform_answer_typing` can sleep for a full answer-sized delay even when a later `send_message_part` should only get a short inter-bubble pause or no new typing pulse. The revised plan therefore keeps the same lightweight architecture, but explicitly adds send-context to the hook so first/final sends and later incremental parts can be paced differently.

The goal is one continuous composition session: start typing early only for live Discord turns while the agent is actually composing, stop or pause naturally before visible sends, keep `send_message_part` chains from accumulating robotic full-answer delays, pause when the user types, and rely on the existing per-user pulse gap to avoid API spam.

## Main Phase

### Step 1: Document the Current Lifecycle (`docs/believable-discord-typing-plan.md`, `app/main.py`, `app/services/debouncer.py`, `app/services/pacer.py`)
**Scope:** Small
1. In `docs/believable-discord-typing-plan.md`, describe the existing live flow: `BurstCoalescer.add` starts initial typing during coalescing, `_handle_ready_burst` stops that task before deciding, `_run_paced_agentic_turn` starts thinking typing for live answers, and `before_paced_send` stops thinking typing before answer pacing.
2. Call out the current guardrails already present in `DiscordPacer`: per-user `_last_bot_typing_at`, `typing_state` suppression while the user types, visible/off gaps, and persisted `pacing_events` for observability.
3. Note that Discord typing indicators are pulse-based and expire automatically; there is no explicit stop endpoint, so “stop” means stop sending pulses and let the active indicator lapse.
4. Record the key current flaw: `send_message_part` calls the same paced-send hook before every part, while `perform_answer_typing` computes a full text-based delay. Without a contextual hook, later message bubbles can wait too long and may wait with no visible typing pulse because the pulse gap has not elapsed.

### Step 2: Define the Lightweight Target State (`docs/believable-discord-typing-plan.md`, `app/services/pacer.py`)
**Scope:** Small
1. In `docs/believable-discord-typing-plan.md`, specify one typing controller concept implemented inside `DiscordPacer`, not as a new service: reuse `perform_initial_typing_until_stopped`, `perform_thinking_typing_until_stopped`, and `perform_answer_typing`, but tighten thresholds, skip rules, and incremental-send behavior.
2. Require typing to begin early only for live Discord inbound work. Catch-up, recovery, media-derived non-live work, reactions, silence, and WhatsApp sends should not emit Discord typing pulses.
3. Require a small-message skip threshold for answer typing: do not run full answer typing for very short final text or tiny incremental parts unless there has been no visible typing cue and the reply would otherwise feel abrupt.
4. Keep the existing pulse-min-gap as the hard anti-spam limiter. No code path should bypass `_send_bot_typing_pulse` for paced typing.
5. Treat multi-part replies as one composition session. The first visible part may use normal answer pacing; later parts should use bounded inter-part pacing, not a repeated full answer delay.

### Step 3: Plan the Pacer API Changes (`docs/believable-discord-typing-plan.md`, `app/services/pacer.py`, `app/config.py`)
**Scope:** Medium
1. In `docs/believable-discord-typing-plan.md`, propose adding focused helper methods in `DiscordPacer` rather than broad rewrites:
   - `should_type_for_answer(answer_text, preferences, *, send_kind, part_index=None, already_typing_visible=False)` for tiny-message and incremental-part suppression.
   - `perform_send_typing(user, channel_id, text, *, send_kind, part_index=None, already_typing_visible=False)` as the public paced-send entry point used by `before_paced_send`.
   - `wait_until_user_stops_typing(user, channel_id, preferences, reason)` to share the current user-typing wait loop between thinking and answer typing.
2. Define `send_kind` values narrowly, for example `final`, `incremental_first`, and `incremental_next`. Avoid a generic enum that implies unsupported future channels.
3. For `incremental_next`, cap pacing to a short bounded pause based on `discord_multi_message_delay_s` and pulse eligibility. It must not call full `answer_typing_delay_s` for each later part.
4. If a later incremental part is substantial and the pulse gap has elapsed, allow one typing pulse before sending. If the pulse gap has not elapsed, do not sleep out the full answer delay just to preserve a typing illusion.
5. Keep config additions minimal. Prefer existing `discord_multi_message_delay_s`, `discord_multi_message_min_chars`, `discord_pacing_answer_typing_min_s`, `discord_pacing_typing_pulse_min_gap_s`, and `discord_pacing_thinking_typing_start_s`. Add a new setting only if tests prove current settings cannot express the incremental cap clearly.
6. Preserve persisted events for `typing_start`, `typing_wait`, and `typing_stop`; add `typing_skip` only if it materially helps debugging and does not create noisy storage.

### Step 4: Plan Agentic Hook Contract Changes (`docs/believable-discord-typing-plan.md`, `app/main.py`, `app/services/agentic.py`, `app/services/turn_context.py`)
**Scope:** Medium
1. In `docs/believable-discord-typing-plan.md`, specify that `_run_paced_agentic_turn` remains the orchestration boundary for live Discord typing. It should start thinking typing as soon as a live answer decision begins, and it must always stop the task in `finally`.
2. Replace the coarse `before_paced_send(answer_text)` contract with a contextual callback such as `before_paced_send(text, *, send_kind, part_index=None)`. Update `TurnContext.before_paced_send` typing accordingly.
3. Keep backwards impact small by adapting only the current callers in `agentic.py` and `read_tools.py`; do not introduce a new service or transport abstraction.
4. Keep `send_typing_indicator=False` in `agentic.py` whenever pacing context is present so `discord.send_text` does not also emit its default pre-send typing indicator.
5. For final non-incremental sends, call the hook with `send_kind="final"` before the provider send.
6. Track whether a thinking pulse was actually visible in `_run_paced_agentic_turn` if needed, and pass that into the pacer entry point so tiny final replies can skip redundant answer typing after an already-visible composition pulse.

### Step 5: Plan Incremental Message Part Behavior (`docs/believable-discord-typing-plan.md`, `app/services/tools/read_tools.py`, `app/services/messaging.py`)
**Scope:** Medium
1. In `docs/believable-discord-typing-plan.md`, define the intended `send_message_part` rhythm: the first part may stop thinking typing and use normal bounded answer pacing; later parts use `discord_multi_message_delay_s` plus optional short/pulse-only pacing.
2. Update `send_message_part` to pass contextual metadata into `ctx.before_paced_send`: `send_kind="incremental_first"` for part index 1 and `send_kind="incremental_next"` for part index 2 and beyond.
3. Keep the existing `discord_multi_message_delay_s` as the natural inter-part gap, but ensure it checks `_newer_inbound_exists` after sleeping, as it already does.
4. Keep `before_provider_send` in `send_outbound_part` as the hook execution point immediately before the provider call. Do not add Discord typing calls inside `messaging.py`; it should stay provider-delivery-focused.
5. Ensure `send_message_part` interruption remains authoritative: if `_newer_inbound_exists` returns true, no typing pulse and no message part should be sent.
6. Explicitly prevent repeated full answer delays for chained parts. A three-part reply should not sleep up to `answer_typing_max_s` before each bubble.

### Step 6: Plan User-Typing Pause Semantics (`docs/believable-discord-typing-plan.md`, `app/services/pacer.py`, `app/services/discord.py`)
**Scope:** Small
1. In `docs/believable-discord-typing-plan.md`, specify that gateway `TYPING_START` events continue to call `pacer.mark_user_typing`; do not poll Discord or add new transport state.

3. Cap user-typing waits with `max_typing_wait_s` so the bot does not hang indefinitely if Discord typing events keep arriving or fail to clear.
4. For incremental sends, re-check user typing after the inter-part delay and before the provider send; if a newer inbound exists, return `interrupted` without typing or sending.
