The file must be a single self-contained markdown document with this structure and content:

1. **Title line:** `# Hash Chains` (H1).

2. **Section 1 — Definition (~50 words).** Explain that a hash chain is an append-only sequence of entries where each entry stores the cryptographic hash (e.g., SHA-256) of the previous entry alongside its own payload. The first entry has a sentinel `prev_hash` (e.g., 32 zero bytes / `\"0\"*64`). Each new entry's identity is bound to all prior entries through this chained hash.

3. **Section 2 — Code-like example.** Include exactly one short fenced code block (use ```text``` or ```json```) showing two consecutive entries with a `prev_hash` field. Example shape:
   ```text
   entry[1] = { \"seq\": 1, \"payload\": \"user_login\",  \"prev_hash\": \"0000...0000\", \"hash\": \"a1b2...\" }
   entry[2] = { \"seq\": 2, \"payload\": \"user_logout\", \"prev_hash\": \"a1b2...\",     \"hash\": \"c3d4...\" }
   ```
   Truncated hex (e.g., `a1b2...`) is fine — keep the block short. The example must make clear that `entry[2].prev_hash == entry[1].hash`.

4. **Section 3 — What it detects (~50 words).** Tampering with any past entry: changing a byte in entry N changes its hash, which breaks the `prev_hash` reference in entry N+1, cascading forward. A verifier walking the chain recomputes each hash and compares against the next entry's `prev_hash`; any single edit invalidates every subsequent link.

5. **Section 4 — What it does NOT detect (~60 words).** Be concrete about three weaknesses:
   - **Tail truncation:** dropping the last K entries leaves a still-valid prefix; the chain alone cannot tell you entries are missing.
   - **Whole-chain replacement:** an attacker who can rewrite the entire log can produce a fresh, internally consistent chain.
   - **Out-of-band modification with full rewrite:** if the attacker controls storage and can recompute every hash, the chain re-validates.
   The fix for these is external anchoring: signed checkpoints, witnessed roots, or publishing the head hash somewhere the attacker cannot rewrite.

6. **Section 5 — One concrete use case (~40 words).** Pick one and be specific. Recommended: **Certificate Transparency logs** — public append-only logs of issued TLS certificates where browsers and monitors verify the Merkle/hash structure to detect mis-issued certificates. (Acceptable alternates: Git commit history, Bitcoin block headers, audit/event logs in compliance systems. Pick exactly one; do not enumerate.)
