**Findings**

1. The new `policy.py` helper is at risk of reintroducing the exact ambiguity this plan is trying to remove. In [staged-wobbling-babbage.md](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L41) the proposed `should_auto_queue(detector)` is detector-based, but the real source of truth today is cluster-level semantics: explicit `execution_policy` wins in [cluster_semantics.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_semantics.py#L81), and manual clusters are deliberately created as `planned_only` in [operations/cluster.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/operations/cluster.py#L78). If explain/counting logic leans on detector metadata instead of persisted cluster semantics, manual `unused`/`logs` clusters will be reported as auto-queued even when they are not.

2. The `--explain` proposal currently looks terminal-only, but `next`/`backlog` already have JSON, markdown, and `--output` surfaces. The plan only calls out terminal wiring in [staged-wobbling-babbage.md](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L72), while the current payload contract lives in [output.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/next/output.py#L115). If you do not add a queue-level explanation field to the payload, `next --explain --format json` and `--output` will silently diverge from terminal behavior.

3. The insertion point is slightly off. The plan lists a change in [staged-wobbling-babbage.md](/Users/user_c042661f/.claude/plans/staged-wobbling-babbage.md#L158) for `backlog/cmd.py`, but backlog already routes through the shared queue flow; the actual shared render split is the empty vs non-empty paths in [queue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/next/queue_flow.py#L343). I would explicitly say “render the preamble in both `_render_empty_queue_view()` and `_render_non_empty_queue()`” and drop the `backlog/cmd.py` touch unless you discover a real need.

Overall, the plan is mostly clean and the scope is disciplined. The core metadata change is good; the main thing I would tighten is making “explainability” consume persisted cluster semantics end-to-end, not a new detector-level shortcut.

**Findings**

1. The new `auto_queue` lookup is not backward-compatible with existing registry doubles and currently breaks the test suite. `_auto_cluster_execution_status()` dereferences `meta.auto_queue` unguarded in [auto_cluster_sync_issue.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/auto_cluster_sync_issue.py#L37), and `infer_cluster_execution_policy()` makes the same assumption in [cluster_semantics.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_plan/cluster_semantics.py#L94). Current result: `./.venv/bin/python -m pytest -q desloppify/tests/engine/test_sync_split_modules_direct.py desloppify/tests/plan/test_reconcile_pipeline.py` fails with `AttributeError: 'types.SimpleNamespace' object has no attribute 'auto_queue'`. This needs a defensive `getattr(meta, "auto_queue", False)` or updated test/runtime contracts everywhere.

2. `backlog --explain` is not actually using the plan data, so the “shared queue-level preamble” is incomplete on backlog surfaces. `_plan_data_for_view()` intentionally returns `None` when `show_plan_context=False` in [queue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/next/queue_flow.py#L290), but both the terminal header and JSON payload pass `plan_data` into explain rendering in [queue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/next/queue_flow.py#L195) and [queue_flow.py](/Users/user_c042661f/Documents/desloppify/desloppify/app/commands/next/queue_flow.py#L163). That means backlog explain output cannot report auto-queued vs triage-promoted counts even though `plan_for_queue` is available.

3. The explain output still overstates which auto-queue detectors are active. `_auto_queue_detector_names()` in [policy.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/policy.py#L70) returns every detector with `auto_queue=True`, and `explain_queue()` prints that global list in [policy.py](/Users/user_c042661f/Documents/desloppify/desloppify/engine/_work_queue/policy.py#L98). In the current code, a plan with only an active `unused` auto-cluster renders `Auto-queued: 1 clusters (logs, unused — auto_queue=True)`. That is misleading, which matters here because the whole feature is supposed to improve traceability.

**Notes**

I did not find a semantic problem with the Rust-detector narrowing in the current tree; the latest `cluster_semantics` change now makes detector metadata authoritative when the detector is known.

Verification I ran: the targeted command suites passed, but the targeted engine/plan suite above still has the `auto_queue` regression. I did not run the full test suite.
