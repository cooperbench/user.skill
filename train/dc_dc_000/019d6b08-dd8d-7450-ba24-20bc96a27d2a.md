# Pre-flight Key Probe and Key-Aware Worker Distribution

## Context

We recently spent hours diagnosing a 10-task SWE-bench experiment that "collapsed due to quota exhaustion" — only to discover that 3 of our 5 Z.AI API keys were actually healthy. The dead keys were pinned to specific workers by the launch-time distribution, so those workers spun on 429s and died, while the alive keys sat underused. A 5-second `chat/completions` probe with `max_tokens: 1` would have told us the truth immediately.

This plan adds a pre-flight key probe to the eval launch sequence and makes the worker distribution **key-aware**: it skips dead keys, reassigns workers to healthy ones from the pool, and refuses to launch any workers if no healthy keys remain.

## Project directory

`/Users/user_c042661f/Documents/hermes-agent` — this is a hermes-agent change, not a megaplan change. The megaplan editable install is unaffected.

## Goal

A lightweight, proactive key-health system that runs at launch and (optionally) on-demand for diagnostics.

**Behavior:**

1. Before workers spawn, probe every key in `auto_improve/api_keys.json` via a 1-token `chat/completions` call.
2. Classify each key as **alive**, **exhausted** (429), **invalid** (401/403), or **unreachable** (timeout/network). Capture the reset time from exhausted-key error responses when available.
3. Distribute only **alive** keys to workers. If the number of alive keys is less than the requested worker count, scale the worker count down to `len(alive_keys)` and warn loudly.
4. If **zero keys are alive**, refuse to launch at all. Exit with a clear error and a table of per-key status.
5. Expose the same probe as a standalone CLI: `python -m auto_improve.probe_keys` — prints the status table, exits 0 if any key is alive, exits 1 otherwise. This is the diagnostic operators can run from the cron runbook when the cron reports stall or widespread 429s.

## What exists today

- `auto_improve/api_keys.json` — the Z.AI key pool. JSON array of `{"key": "<value>", ...}` entries. Source of truth.
- `megaplan/key_pool.py` — megaplan's in-subprocess key pool. Reads the same JSON file, handles LRU selection, cooldown on 429s. **Do not modify** — this runs inside megaplan subprocesses and is already working. The probe is a separate layer.
- `evals/parallel.py` — the parallel worker launcher. Already has a "Megaplan pre-flight check" step around the worker-spawn logic and already does a "Distributing N API keys across M workers" step. This is where the new probe integrates.
- `~/.hermes/.env` — contains Z.AI base URL and possibly additional keys via `ZHIPU_API_KEY` (and `_1`, `_2`, etc.). The probe must check both sources, matching the same resolution order as `megaplan/key_pool.py::_collect_key_values` and `_load_api_keys_json`.
- The 1-char probe proof-of-concept has already been validated interactively:
  ```python
  # POST https://api.z.ai/api/coding/paas/v4/chat/completions
  # body: {"model": "glm-5.1", "messages": [{"role":"user","content":"hi"}], "max_tokens": 1}
  # 200 -> alive, 429 -> exhausted, 401 -> invalid, timeout -> unreachable
  ```

        # Implementation Plan: Pre-flight Key Probe and Key-Aware Worker Distribution

## Overview
Adds a launch-time health probe for Z.AI API keys plus a CLI diagnostic. `evals/parallel.py` currently loads `auto_improve/api_keys.json` and distributes entries round-robin across workers (`evals/parallel.py:494`, `evals/parallel.py:524-579`), with no check that keys are actually alive. When keys are exhausted, workers pinned to those keys spin on 429s. The plan wires a `probe_all_keys()` step between the existing megaplan pre-flight (`evals/parallel.py:491`) and key distribution (`evals/parallel.py:525`), filters the pool to alive keys, scales worker count down if fewer alive keys than workers, and refuses to launch if zero are alive.

Note: The brief references `megaplan/key_pool.py` as a template for env-var resolution, but that file lives in the external editable `megaplan/` install (not in this repo) — we will mirror the `ZHIPU_API_KEY`, `ZHIPU_API_KEY_1`, ... pattern without importing from megaplan, keeping the probe module self-contained.

### Step 2: Create `auto_improve/probe_keys.py`
**Scope:** Medium
1. **Define** `KeyStatus` dataclass with fields `key`, `provider`, `status` (Literal of `"alive"`/`"exhausted"`/`"invalid"`/`"unreachable"`), `detail`, `reset_at: str | None`, `masked_key`. Mask = `key[:8] + "..." + key[-4:]` (falls back gracefully for short keys).
2. **Implement** `load_candidate_keys(provider="zhipu") -> list[str]`:
   - Read `auto_improve/api_keys.json` (list-of-dicts or list-of-strings tolerated).
   - Parse `~/.hermes/.env` for `ZHIPU_API_KEY` and `ZHIPU_API_KEY_<N>` (N=1..16), simple line-based parser — no dotenv dep.
   - Dedupe preserving first-seen order.
3. **Implement** `probe_key(key, *, provider="zhipu", timeout=15.0) -> KeyStatus` using `urllib.request`:
   - POST `https://api.z.ai/api/coding/paas/v4/chat/completions` with headers `Authorization: Bearer <key>`, `Content-Type: application/json`, body `{"model": "glm-5.1", "messages": [{"role":"user","content":"hi"}], "max_tokens": 1}`.
   - 200 → `alive`; `HTTPError` 429 → `exhausted` (read body, regex `r"reset at ([0-9T :\-\.]+)"` for `reset_at`); 401/403 → `invalid`; `socket.timeout` / `URLError` / other exceptions → `unreachable`.
   - Always populate `detail` with a short summary (status code or exception class) and never include the raw key.
4. **Implement** `probe_all_keys(provider="zhipu", *, concurrency=8, timeout=15.0) -> list[KeyStatus]` using `concurrent.futures.ThreadPoolExecutor`; preserve input order by mapping index → future.
5. **Implement** `alive_keys(results) -> list[str]` — filters for `status == "alive"` and returns raw key strings.
6. **Implement** `format_status_table(results, *, assignments: dict[str,str] | None = None) -> str`:
   - Columns: key (masked), worker (from `assignments` or blank), status (with ✓/✗ glyph), detail (truncated to 60 chars), reset_at.
   - Assert-by-construction: raw key substring must never appear in the rendered string.
7. **Implement** `main(argv=None) -> int` with `argparse`:
   - Flags: `--provider` (default `zhipu`, choices include `zhipu`), `--concurrency` (default 8), `--timeout` (default 15.0), `--json` (dump list of KeyStatus dicts, masking the key).
   - Prints table to stdout, exit 0 if any alive else 1.
   - Add `if __name__ == "__main__": sys.exit(main())` and make sure `python -m auto_improve.probe_keys` works.
8. **Out of scope for this module:** MiniMax probing. Leave `provider` dispatch as a single-branch `if provider != "zhipu": raise NotImplementedError` so the extension point is obvious.

### Step 3: Integrate into `evals/parallel.py` (`evals/parallel.py:507-610`)
**Scope:** Medium
1. **Import** `from auto_improve.probe_keys import probe_all_keys, KeyStatus, format_status_table`.
2. **After** `_preflight_check_megaplan()` (`evals/parallel.py:518`) and **before** the `_load_api_keys()` call (`evals/parallel.py:525`):
   - Load `api_keys` via `_load_api_keys()` first.
   - Build `raw_keys = [entry["key"] for entry in api_keys]`.
   - Call `results = probe_all_keys("zhipu")` — but only over the `raw_keys` subset (so `base_url` pairing is preserved). Extend `probe_all_keys` to accept an optional explicit `keys: list[str] | None` override, OR add a thin helper `probe_keys(keys: list[str], ...)` used by both `probe_all_keys` and the parallel integration. Prefer the helper split to keep the CLI's "load from disk" behavior untouched.
   - Print one status line per key using masked form: `  [alive] 6a254d67... (worker slot: w0)` or `  [exhausted] 637742fa... reset 2026-04-08 11:55:35`.
3. **Filter** `api_keys` to the entries whose `key` is in `alive_keys(results)`. Call this `alive_entries`.
4. **If** `len(alive_entries) == 0`: raise `RuntimeError` with the full `format_status_table(results)` and a prefix line `"No alive API keys — refusing to launch workers."`. This propagates up and aborts the run before any worker spawns.

6. **Replace** the existing `api_keys` variable used by the loop with `alive_entries`, so the existing assignment at `evals/parallel.py:560` (`api_keys[idx % len(api_keys)]`) naturally picks only alive keys.
7. **Leave** the rest of the worker-env wiring at `evals/parallel.py:558-579` untouched.

## Context

We recently spent hours diagnosing a 10-task SWE-bench experiment that "collapsed due to quota exhaustion" — only to discover that 3 of our 5 Z.AI API keys were actually healthy. The dead keys were pinned to specific workers by the launch-time distribution, so those workers spun on 429s and died, while the alive keys sat underused. A 5-second `chat/completions` probe with `max_tokens: 1` would have told us the truth immediately.

This plan adds a pre-flight key probe to the eval launch sequence and makes the worker distribution **key-aware**: it skips dead keys, reassigns workers to healthy ones from the pool, and refuses to launch any workers if no healthy keys remain.

## Project directory

`/Users/user_c042661f/Documents/hermes-agent` — this is a hermes-agent change, not a megaplan change. The megaplan editable install is unaffected.

## Goal

A lightweight, proactive key-health system that runs at launch and (optionally) on-demand for diagnostics.

**Behavior:**

1. Before workers spawn, probe every key in `auto_improve/api_keys.json` via a 1-token `chat/completions` call.
2. Classify each key as **alive**, **exhausted** (429), **invalid** (401/403), or **unreachable** (timeout/network). Capture the reset time from exhausted-key error responses when available.
3. Distribute only **alive** keys to workers. If the number of alive keys is less than the requested worker count, scale the worker count down to `len(alive_keys)` and warn loudly.
4. If **zero keys are alive**, refuse to launch at all. Exit with a clear error and a table of per-key status.
5. Expose the same probe as a standalone CLI: `python -m auto_improve.probe_keys` — prints the status table, exits 0 if any key is alive, exits 1 otherwise. This is the diagnostic operators can run from the cron runbook when the cron reports stall or widespread 429s.
