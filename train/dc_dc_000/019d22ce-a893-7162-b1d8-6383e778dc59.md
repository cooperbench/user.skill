        # Implementation Plan: Harden Execute→Review Evidence Pipeline

## Overview

**Goal:** When a plan reaches DONE, `finalize.json` contains complete, auditable, programmatically-verified evidence of what was done and whether it checks out.

**Current state:** The pipeline already has good structural bones — executor returns `task_updates` with `executor_notes`, reviewer fills `reviewer_verdict` and `sense_check` verdicts, coverage gaps block state transitions. But three gaps remain:

1. **Evidence is flat, not per-task.** `files_changed` and `commands_run` live at the top level of `execution.json`, not tied to individual tasks. A reviewer can't mechanically verify "task T3 claims to have changed `foo.py`" against the diff.
2. **No programmatic validation.** Executor claims are trusted at face value. Nobody checks whether `files_changed` entries actually appear in the git diff, or whether `executor_notes` reference real files.
3. **Sense-check acknowledgments are one-directional.** The executor sees sense checks as "nudges" (`prompts.py:380`) but never formally acknowledges them. The reviewer is the first agent to produce verdicts.

**Constraints:** No new CLI flags, no interactive prompts, enforcement is automatic. Happy path should feel invisible.

2. **Check 1 — files_changed vs git diff:** Run `git diff --name-only` against the project directory. Compare the union of all per-task `files_changed` against the actual diff. Flag:
   - Files claimed changed but not in diff ("Phantom file claim: executor says T2 changed `foo.py` but it is not in the git diff").
   - Files in diff but not claimed by any task ("Unclaimed change: `bar.py` appears in git diff but no task claims it").
3. **Check 2 — executor_notes reference real artifacts:** For each task's `executor_notes`, extract file-like tokens (simple regex for paths with extensions). Check whether those paths exist in the repo. Flag non-existent references.
4. **Check 3 — sense-check coverage:** Verify every sense_check has `executor_acknowledged: true`. Flag unacknowledged checks.
5. **Return** the findings list. Each finding is a human-readable string the reviewer can act on.

        # Implementation Plan: Harden Execute→Review Evidence Pipeline

## Overview

**Goal:** When a plan reaches DONE, `finalize.json` contains complete, auditable, programmatically-verified evidence of what was done and whether it checks out.

**Current state:** The pipeline has good structural bones — executor returns `task_updates` with `executor_notes`, reviewer fills `reviewer_verdict` and `sense_check` verdicts, coverage gaps block state transitions. Three gaps remain:

1. **Evidence is flat, not per-task.** `files_changed` and `commands_run` live at the top level of `execution.json`, not tied to individual tasks.
2. **No programmatic validation.** Executor claims are trusted at face value. Nobody checks whether claimed files actually appear in git status.
3. **Sense-check acknowledgments are one-directional.** The executor sees sense checks as "nudges" (`prompts.py:380`) but never formally acknowledges them.
