        # Implementation Plan: Note Injection Flow for Subagent Mode

## Overview

Megaplan's subagent architecture has 3 layers: (1) Main conversation (outer skill, talks to user), (2) Orchestrator subagent (runs the megaplan workflow loop), (3) Worker subagents/CLI calls (run individual phases). The appendix at `megaplan/data/claude_subagent_appendix.md` already specifies both injection modes at a high level but lacks implementation detail for the outer skill's behavior and doesn't resolve how "kill just the worker" would work mechanically.

**Key finding from primitives analysis:** Claude Code's `SendMessage` delivers messages to an agent, but if the agent is blocked on a synchronous tool call (Bash running `megaplan critique`, or a nested Agent running a worker), the message queues until the tool completes. This means you **cannot interrupt a running phase** via SendMessage alone. `TaskStop` kills the entire agent — there's no way to target a child tool call. Therefore, "kill just the worker without killing the orchestrator" is **not feasible with current primitives**.

**Design decision:** Implement two modes:
- **Option A (inject-at-boundary):** User adds note via CLI, orchestrator picks it up between phases. Zero interruption.
- **Option B (kill+relaunch):** Main conversation TaskStops the orchestrator entirely, injects note, relaunches a fresh orchestrator that resumes from disk state. The state-on-disk architecture already supports this.

No new CLI commands are needed — `megaplan override add-note` and `megaplan status` already provide everything. The work is in the **prompt instructions** (outer skill behavior, orchestrator protocol) and a small CLI enhancement to surface injection readiness.

## Design Rationale: Why Not "Kill Just the Worker"?

The user's idea explored whether the main conversation could kill just the current worker (layer 3) without killing the orchestrator (layer 2). After analyzing Claude Code primitives:

- **SendMessage** can't interrupt a blocked tool call. If the orchestrator is waiting on `megaplan critique` (a Bash call), SendMessage queues.
- **TaskStop** kills an entire agent — no way to target a child Bash process or nested Agent.
- **Background Bash + poll loop** — The orchestrator could run phases as background Bash commands and poll for completion, checking for kill signals between polls. This would work mechanically but adds enormous complexity: the orchestrator prompt would need PID management, signal file handling, and poll timing logic. It transforms a clean sequential flow into a complex concurrent one, all to save ~30 seconds of phase restart time.
- **Nested Agent per phase** — The orchestrator could launch each phase as a nested Agent. But the main conversation still can't TaskStop the nested agent (doesn't know its ID, and TaskStop targets are scoped to the calling agent).

**Conclusion:** Kill+relaunch of the entire orchestrator is the right primitive. It's simple, reliable, and the state-on-disk architecture was designed for exactly this. The cost (restarting a subagent, re-reading status) is ~5 seconds. The alternative (background Bash polling) would add 50+ lines of prompt complexity for negligible user benefit.
