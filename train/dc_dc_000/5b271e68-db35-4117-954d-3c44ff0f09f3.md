Yes to both — they're different surfaces. ## Save to reigh-app (canonical, shared) When you edit a *reigh-app* project (UUID), it writes to Supabase: - `python3 -m artagents projects edit <project_id> <timeline_id> add-clip ...` - `python3 -m artagents projects edit <project_id> <timeline_id> move-clip ...` - `python3 -m artagents projects edit <project_id> <timeline_id> set-theme ...` These flow through `SupabaseDataProvider.save_timeline` → `update_timeline_config_versioned` RPC with `expected_version`. Reigh-app sees them immediately. **Same data, both tools edit it.** The worker (`banodoco_worker`) writes the same way when a `delegateToBanodocoAgent` task fires. ## Save locally (cache + provenance) Local-project verbs still work, fully offline: - `python3 -m artagents projects create <slug>` — creates `<projects_root>/<slug>/` - `python3 -m artagents projects source add <slug> <source_id> --file ...` — adds local asset - `python3 -m artagents projects show <slug>` — inspects local state These write to disk only. Use cases: - Solo authoring without Supabase - Cache of run/source provenance (AA tracks which generation produced which clip) - Pre-publish iteration before pushing to a reigh-app project ## How they relate A local project can carry an optional `project_id` (reigh-app UUID) stored in `project.json`. That's the link — local provenance maps to a remote canonical timeline. Sources/runs you generate locally produce clips that, when written via the worker or `edit`, land on the reigh-app timeline carrying `source_uuid` so reigh-app preserves the provenance. In practice: **local for development/exploration, remote for shipping**. Both work today.
