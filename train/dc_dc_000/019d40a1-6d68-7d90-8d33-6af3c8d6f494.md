        # Implementation Plan: Structured Critique Template for Megaplan

## Overview

The current megaplan critique phase produces free-form flags — the critic can raise any concern with any structure. This works but leads to essay-length critiques that drift in scope. The goal is to replace the open-ended critique with a **structured 5-check template** where each check is a specific, focused question the critic must answer. If a check reveals an issue, it becomes a flag; otherwise it's marked clean. This constrains critique to exactly 5 dimensions, prevents essay writing, and produces machine-parseable results that flow cleanly into gate/revise.

### Current state
- **Critique schema**: `.megaplan/schemas/critique.json` — free-form `flags[]` array with `id`, `concern`, `category`, `severity_hint`, `evidence`, plus `verified_flag_ids` and `disputed_flag_ids`
- **Gate schema**: `.megaplan/schemas/gate.json` — reads flags, produces `PROCEED`/`ITERATE`/`ESCALATE`
- **Revise schema**: `.megaplan/schemas/revise.json` — takes flag IDs, produces revised plan
- **Megaplan CLI**: External Python package at `/Users/user_c042661f/.pyenv/versions/3.11.11/bin/megaplan` (separate from this repo)

### The 5 checks
1. **callers** — Does the plan account for all callers of modified functions/APIs?
2. **all_locations** — Does the plan cover all locations that need changes (not just the obvious one)?
3. **conventions** — Does the plan follow existing codebase conventions (naming, patterns, structure)?
4. **issue_hints** — Does the plan align with hints/constraints from the issue description?
5. **scope** — Is the scope right — not over-engineered, not under-specified?

### Key constraint
The megaplan CLI source lives outside this repo. The brief specifies `schemas.py`, `prompts.py`, `handlers.py` — these need to be created somewhere the megaplan CLI can load them. **See questions below** for where exactly.

### Step 2: Define the structured critique schema (`schemas.py`, `.megaplan/schemas/critique.json`)
**Scope:** Small
1. **Create** `schemas.py` with a Python dataclass or Pydantic model:
   ```python
   @dataclass
   class CritiqueCheck:
       id: str          # one of: callers, all_locations, conventions, issue_hints, scope
       flagged: bool     # True if this check found an issue
       concern: str      # Empty string if not flagged; 1-2 sentences if flagged
       evidence: str     # Empty string if not flagged; file:line citations if flagged

   @dataclass
   class StructuredCritique:
       checks: list[CritiqueCheck]  # exactly 5, one per check ID
       # Backward compat: derived flags list for gate/revise
       @property
       def flags(self) -> list[dict]:
           return [asdict(c) for c in self.checks if c.flagged]
   ```
2. **Update** `.megaplan/schemas/critique.json` to match the new structure while keeping `flags`, `verified_flag_ids`, `disputed_flag_ids` as derived/optional fields for backward compat with gate.

### Step 3: Write the critique prompt template (`prompts.py`)
**Scope:** Small
1. **Create** `prompts.py` with a `STRUCTURED_CRITIQUE_PROMPT` that:
   - Presents the plan text
   - Lists exactly 5 checks with clear definitions
   - Instructs: "For each check, set `flagged: true` only if you found a concrete issue. Provide evidence with file:line citations. Do NOT flag speculative or minor concerns."
   - Enforces the output schema (JSON matching `StructuredCritique`)
   - Caps each concern at 2 sentences max
2. **Example prompt structure:**
   ```
   You are reviewing a plan. Answer exactly 5 checks:

   1. CALLERS: Does the plan account for all callers of functions it modifies?
   2. ALL_LOCATIONS: Does it cover every file/location that needs changes?
   3. CONVENTIONS: Does it follow existing codebase conventions?
   4. ISSUE_HINTS: Does it align with the issue description's hints and constraints?
   5. SCOPE: Is the scope appropriate — not over-engineered, not too narrow?

   For each: set flagged=true ONLY with concrete evidence. No essays.
   ```

### Step 4: Wire the handler conversion (`handlers.py`)
**Scope:** Medium
1. **Create** or update `handlers.py` with a `convert_structured_critique_to_flags()` function that:
   - Takes a `StructuredCritique` output
   - Converts flagged checks into the existing `flags[]` format that gate and revise expect
   - Maps check IDs to categories: `callers`→correctness, `all_locations`→completeness, `conventions`→maintainability, `issue_hints`→correctness, `scope`→completeness
   - Sets `severity_hint` to `likely-significant` for all flagged checks (they passed the concrete-evidence bar)
2. **Ensure** gate.json and revise.json schemas remain untouched — they consume flags the same way.
3. **Update** the critique phase handler to:
