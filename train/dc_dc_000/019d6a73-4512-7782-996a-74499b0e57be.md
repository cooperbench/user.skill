# Lift Standard Review Quality via Mechanical Pre-checks, Flag Re-verification, and Critique Re-tiering

## Context

Megaplan has three robustness modes: `light`, `standard`, `heavy`. Heavy mode just shipped a new parallel `run_parallel_review` with 4 focused LLM checks + mechanical pre-checks. Standard mode still runs a single `_review_prompt()` call that anchors to `finalize.json` (what the plan said to do), not the original issue. We've validated that the questions standard mode SHOULD be asking are already present in the critique phase (`megaplan/checks.py`) but are gated to extended tier or run only against the plan, not the post-execute diff.

This plan is a targeted, **cheap** lift of standard mode quality. No new LLM calls in standard mode. Light mode stays exactly as today. Heavy mode mechanical pre-checks are preserved.

## Goal

Three changes that make standard-mode critique and review materially more thorough without adding API cost:

1. **Run mechanical pre-checks in both standard and heavy review**, not only heavy. Attach as context in standard; auto-block clear failures.
2. **Add a "re-verify critique flags against the final diff" section** to the standard `_review_prompt()` so the single review call re-checks whether pre-execute concerns were actually resolved by the post-execute code.
3. **Re-tier critique checks**: promote `all_locations` and `callers` from extended to core, demote `criteria_quality` from extended-core ordering (or remove from core if it's there). Standard-mode critique becomes substantially more thorough at zero extra cost per check since it's a swap, not an addition.

## What exists today (don't break)

- `megaplan/handlers.py::handle_review` — branches on robustness. Standard path runs the legacy single-call worker. Heavy path calls `run_pre_checks` then `run_parallel_review`. The heavy branch at ~line 1251 calls `run_pre_checks(plan_dir, state, Path(state["config"]["project_dir"]))`.
- `megaplan/review_mechanical.py::run_pre_checks` — returns a list of advisory flag dicts. Runs instantly (no LLM). Safe to call multiple times.
- `megaplan/prompts/review.py::_review_prompt` — the single-call standard review prompt. Produces criteria/task_verdicts/sense_check_verdicts/review_verdict/rework_items. Must stay byte-identical in light mode but can gain new sections in standard mode.
- `megaplan/checks.py::CRITIQUE_CHECKS` — 8 critique checks with `tier` in {"core", "extended"}. Standard robustness runs core only via `checks_for_robustness("standard")`. Heavy runs all 8.
- `megaplan/_core/flags.py` (or wherever flag registry lives) — the flag registry with open/verified/disputed status per flag. Already accessible from review.
- `.megaplan/schemas/review.json` and `megaplan/schemas.py` — review schema. Already widened in the previous robust-review megaplan to accept `pre_check_flags`. The standard review payload must remain backward compatible.

## What needs to exist

### 1. Run mechanical pre-checks in standard mode too

In `megaplan/handlers.py::handle_review`, move the `run_pre_checks(plan_dir, state, Path(state["config"]["project_dir"]))` call out of the heavy branch and run it **unconditionally** before both the standard and heavy review paths.

- For heavy: keep the existing flow — `pre_check_flags` becomes the input to `run_parallel_review`, gets merged into `merged_payload["pre_check_flags"]`.
- For standard: after `run_pre_checks` returns, filter for **blocking** flags (clear failures like `source_touch` reporting a test-only diff, or `dead_guard_static` reporting an unreachable guard in a new source branch). If any blocking flag exists, short-circuit: write a minimal `review.json` with `review_verdict="needs_rework"`, populate `rework_items` with one entry per blocking mechanical flag, set `pre_check_flags` to the full list, and skip the LLM review call entirely. This is a free auto-block.
- For standard with no blocking mechanical flags: attach `pre_check_flags` to the existing review payload as context for the single review call. Pass them into `_review_prompt` as an extra block so the LLM can see them when scoring criteria. Populate `payload["pre_check_flags"]` from the returned worker result.
- Light mode: do NOT run mechanical pre-checks. Light mode stays exactly as today.

Decide which pre-check findings are "blocking" via a helper:
- `source_touch` with severity `significant` and "only touches test-like files" detail → blocking
- `dead_guard_static` with `UNREACHABLE` in the id → blocking (requires a new severity tier or id marker since current implementation only reports parse failures)
- `diff_size_sanity` → never blocking (advisory only)

If the distinction is hard to make cleanly, the simpler alternative is: in standard mode, all mechanical flags are advisory only and attached as prompt context; no auto-blocking. Auto-blocking can come in a later PR. Implementer's call — pick the simpler option if the blocking logic requires more than a single-function helper.

### 2. Re-verify critique flags against final diff in standard review

In `megaplan/prompts/review.py::_review_prompt`, add a new section between the existing requirements block and the JSON shape spec. The new section should:

- Read the flag registry via `load_flag_registry(plan_dir)`.
- Filter for flags with status `open`, `verified`, or `disputed` (not `resolved`).
- For each such flag, include its id, concern text, severity, and current status in the prompt.
- Instruct the model: "For each flag below that was raised during critique, verify whether the final diff actually addresses the concern. A flag is resolved if the final diff contains code that directly addresses the concern. If a flag is not resolved in the final diff, add a `rework_item` referencing the flag id and explaining what's still missing. Do not trust pre-execute promises — check the diff itself."
- The output `rework_items` gain a new optional field `flag_id` pointing to the critique flag id. Existing `source` field should be set to `"review_flag_reverify"` for any rework item synthesized this way.

Schema impact: add optional `flag_id` field to rework_items shape in both `.megaplan/schemas/review.json` and `megaplan/schemas.py`. Keep it optional so existing payloads still validate.

The new prompt section only runs if there are open/verified/disputed flags in the registry; if the registry is empty or all resolved, the section is omitted entirely (keeps the standard prompt byte-identical for plans without critique flags, which is important for the existing byte-identical regression test in `tests/test_handle_review_robustness.py`).

This must not change light mode. Light mode doesn't run critique at all and has no flag registry, so a "no flags → no section" gate handles this automatically.

### 3. Re-tier critique checks

In `megaplan/checks.py`, in `CRITIQUE_CHECKS`:

- Promote `all_locations` from `tier="extended"` to `tier="core"`.
- Promote `callers` from `tier="extended"` to `tier="core"`.
- Demote `criteria_quality` from `tier="core"` to `tier="extended"` (if it's core — verify first). The reasoning: `criteria_quality` is about whether success criteria are well-formed, which is plan hygiene. `all_locations` and `callers` are about whether the plan actually solves the bug, which is more important for standard mode.

This is a **net-zero change** in number of checks per mode:
- Standard robustness was running 4 core checks, will still run 4 (swap `criteria_quality` out, swap `all_locations` in). Net neutral, and if `callers` is also promoted, standard gains one check — verify against the brief's "no new cost per check" claim and either: (a) accept a 1-check increase in standard (minor cost bump), or (b) also demote one more current core check to keep count at 4. The simpler choice is (a) — 5 core checks in standard is fine.
- Heavy robustness is unchanged in total count (still 8 checks, same set, just different tier labels).

Update `megaplan/checks.py:140-144` (or wherever the `checks_for_robustness()` function lives) — no code change should be needed since it filters by tier; only the tier labels on the check entries change.

Update any tests that assert the specific set of core checks to match the new tiering.
