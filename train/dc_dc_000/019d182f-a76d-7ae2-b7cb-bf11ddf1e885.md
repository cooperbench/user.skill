        User intent summary:
Replace the 8-phase lifecycle state machine with a minimal 2-mode system (plan/execute) where the fine-grained pipeline position within plan-mode is derived from queue contents rather than persisted as an explicit phase. This fixes the stuck-phase bug where stale subjective items in queue_order cause _resolve_reconcile_phase to return assessment_postflight indefinitely, preventing transition to execute. The core insight: the persisted phase is redundant with — and often contradicts — the actual queue state. By deriving phase from queue contents at read time (rather than computing and persisting it at reconcile time), the circular dependency between sync_subjective_dimensions (which writes queue_order) and _resolve_reconcile_phase (which reads queue_order to determine phase) is eliminated. The snapshot display layer's separate phase computation (_phase_for_snapshot) would collapse into the same derivation, removing the current dual-phase-system divergence.

Original idea:
Simplify the lifecycle phase system to be as minimal as possible. Current state: 8+ phases, circular dependencies, broken transitions. The system presents work items in order via 'desloppify next'. There are two kinds of work: plan-work (reviews, scans, workflow, triage — must happen in a specific pipeline order) and execution-work (fixing code issues). Plan-work happens at the start and again when the execution queue empties. Within plan-work there's a pipeline: review dimensions → postflight scan → workflow items → strategist → triage. Each stage's completion triggers the next. The bug: phase gets stuck in assessment_postflight and never transitions to execute because stale subjective items keep being re-injected into queue_order. Goal: find the simplest possible model. Maybe just 2 persisted modes (plan/execute) with pipeline position derived from queue contents. Maybe even simpler. Investigate the actual code, understand what complexity is truly load-bearing, and propose the minimal solution.
