        # Implementation Plan: Make pair_shot_generation_id the Single Source of Truth for Segment Positioning

## Overview

The segment position system currently has three competing position identifiers:
- **`pair_shot_generation_id`** — stable FK to `shot_generations`, survives timeline edits (the correct design)
- **`child_order`** — integer column on `generations`, drifts when images are reordered/removed
- **`segment_index`** — integer in task `params` JSONB, semantically identical to `child_order`, equally stale

The goal is to make `pair_shot_generation_id` the sole routing identifier. The `child_order`/`segment_index` values should be kept for display ordering and predecessor chaining but never used to **route** a segment to a timeline slot.

### Key constraint: Predecessor lookup
`get-predecessor-output` uses `child_order - 1` to find the previous segment for continuation chaining. This is a **sequential ordering** need, not a position-routing need. `child_order` is still valid for "what's the segment before me in generation order" — the problem is only when it's used to **match a segment to a timeline slot**. We must not break chaining.

### Key constraint: Worker-created segments
When the orchestrator spawns individual segment tasks, the worker may not have `pair_shot_generation_id` in its input. The orchestrator stores `pair_shot_generation_ids` in `orchestrator_details` and should distribute them to each individual segment task. We need to ensure this always happens.

3. **Keep `segment_index`** as input field — it's still needed for `child_order` on the created generation (sequential ordering) and for `is_first_segment` logic (line 308). Just stop using it for lookup.

### Step 3: Remove child_order fallback from completion handler (`generation-child.ts`)

3. **Keep `childOrder`** in the generation insert (line 288) — it's used for predecessor chaining and display ordering, not routing.

## Phase 3: Harden the Predecessor Lookup

### Step 6: Add pair_shot_generation_id awareness to predecessor lookup (`get-predecessor-output/index.ts`)
**Scope:** Medium  
1. **Read** lines 136–179 fully. The current approach finds the previous segment by `parent_generation_id + (child_order - 1)`. This works when child_order is sequential and stable — which it is for *within a single generation run* (the orchestrator assigns them 0, 1, 2, ...).
2. **The risk**: if a segment is re-generated after timeline edits, its `child_order` may not match the original sequence. **However**, predecessor lookup is only called during task execution (not after edits), so the child_order assigned at task creation time is correct for that run.
3. **Decision**: Keep the `child_order`-based predecessor lookup for now — it's correct within a single orchestration run. Add a comment documenting this invariant. If we later support cross-run predecessor lookup, we'd need to use `pair_shot_generation_id` + timeline ordering.

## Overview

The segment position system has three competing position identifiers:
- **`pair_shot_generation_id`** — stable FK to `shot_generations`, survives timeline edits (the correct design)
- **`child_order`** — integer column on `generations`, drifts when images are reordered/removed
- **`segment_index`** — integer in task `params` JSONB, semantically identical to `child_order`, equally stale

The goal is to make `pair_shot_generation_id` the sole routing identifier. `child_order`/`segment_index` remain for sequential ordering and predecessor chaining only.

### Architecture of the problem

The position data flows through four layers, each with its own index-based fallback:

1. **Orchestrator fan-out** (`reigh-worker/source/task_handlers/travel/orchestrator.py:2021–2075`): The Python orchestrator worker builds per-segment payloads with `segment_index: idx` and `child_order: idx` but does **not** extract `pair_shot_generation_id` from the `orchestrator_details.pair_shot_generation_ids` array. Individual segments never receive their own `pair_shot_generation_id` at the top level.

2. **Task creation resolver** (`individualTravelSegment.ts:146–162`): When `pair_shot_generation_id` is absent (which it always is for orchestrator-created segments, per above), falls back to `eq("child_order", input.segment_index)`.

3. **Task completion normalizer** (`taskParamNormalizer.ts:59–61, 106–109`): Reconstructs `pair_shot_generation_id` from `orchestrator_details.pair_shot_generation_ids[segmentIndex]` — still index-based. `generation-handlers.ts:287–292` repeats this pattern.

4. **Frontend slot assignment** (`segmentSlotAssignment.ts:68–76`): Falls back to `childOrder` when `pairShotGenId` is absent.

**Root cause**: The orchestrator never distributes per-segment `pair_shot_generation_id` values, so every downstream layer compensates with index-based fallbacks.

### Settled decisions (from v1)
- `pair_shot_generation_id` is the correct single source of truth for slot routing.
- `child_order` is retained for sequential ordering and predecessor chaining.
- `child_order`-based predecessor lookup (`get-predecessor-output`) is correct within a single orchestration run — no change needed.
- Segments without `pair_shot_generation_id` should be unslotted, not silently misrouted.
