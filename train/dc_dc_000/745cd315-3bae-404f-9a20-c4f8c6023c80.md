Thinking through this — there's a lot tangled together, so let me separate the pieces and flag where the complexity actually lives.

## The two distinct halves

**Prep phase (offline, cheap):** Generate a structured plan from steering + the user's existing longitudinal state / distillations. This is a one-shot Opus call. Tractable.

**Live phase (real-time, expensive):** Streaming ASR + routing + TTS in a loop with sub-second responsiveness expectations. This is where 80% of the engineering lives, and almost none of it is LLM work.

## Prep doc structure

A "tree" is the intuitive metaphor but real conversations aren't trees — people loop back, jump siblings, abandon threads. I'd structure the prep artifact as:

- **Topics** (flat list with priority/must-cover flags)
- **Nodes** per topic: opening line, 2-3 follow-up probes, "if they say X then Y" branches, "exit" transitions to related topics, a "stuck" fallback
- **Global state** the bot tracks: covered topics, open threads to return to, facts learned mid-conversation
- Stored as JSON keyed by node ID so the live system can route by ID rather than re-parsing prose

This is a **graph with annotations**, not a strict tree. The LLM uses it as a map, not a script.

## Live phase — the real complexity

Pieces, in order of how much they'll bite:

1. **Latency.** Opus takes 3-8s for a real answer. That's death for a voice conversation where humans expect <1s response. Options:
   - Pre-generate the likely next 1-2 utterances at each node during quiet moments and cache them (speak cached, refine in background if user said something unexpected)
   - Use Haiku for fast in-the-moment routing decisions and reserve Opus for the prep doc + post-session synthesis
   - Worth being explicit: "same model as here" works for prep, but probably not for live turn-taking. Flagging because you said Opus throughout.

2. **Turn-taking is not a fixed interval.** A "every 5s transcribe + speak if silent" loop will feel robotic. Better pattern: client-side VAD (voice activity detection) sends an event when the user stops speaking; the server reacts to *that*. The periodic timer is a fallback, not the primary trigger. Streaming ASR (Deepgram, AssemblyAI, OpenAI Realtime) gives partial transcripts continuously so you're not waiting 5s.

3. **Voice model.** For "feels live" you want sub-300ms TTS start. Cartesia Sonic, ElevenLabs Flash, or OpenAI Realtime (which bundles ASR+TTS+turn detection — worth seriously considering as it collapses 3 layers into 1).

4. **Routing on every tick.** Each ASR update → ask the model: "still on current node? jump to sibling? branch deeper? improvise off-tree?" This is a state machine where the LLM is the transition function. Needs to be a small fast call with a compact tree summary in context, not the whole prep doc.

5. **Barge-in and interruption.** User talks while bot is talking. Need to detect and cut TTS off mid-sentence. Hardest UX problem in voice agents. OpenAI Realtime handles this; rolling your own is painful.

6. **Bad ASR cascading.** One mistranscription routes you to the wrong node and the conversation derails. Mitigation: don't switch nodes on a single utterance; require confidence or accumulation.

## Interface

Keep the UI dumb: a single page with the live transcript on the left, current node + next-3-likely nodes on the right, a manual "skip / steer / pause" set of buttons. WebSocket to backend. Don't try to render the full graph visually — that's a UI rabbit hole and not load-bearing for v1.

## Recommended MVP cut

Don't build the whole thing at once. Suggested order:

1. **Prep doc only** — Opus generates the JSON graph from steering + user state. Render it as a readable plan. No live audio yet. This alone is useful (the user reads the prep doc before a real human conversation).
2. **Live transcript + visual tree highlighting** — browser captures mic, streaming ASR shows transcript, server tracks current node and highlights it. No bot speech yet. This validates routing logic.
3. **Bot speaks via TTS** — add voice output, starting with a "press space to make the bot speak the next suggested line" manual trigger.
4. **Autonomous turn-taking** — VAD + silence detection + barge-in.

Each stage is shippable and de-risks the next.

## The tradeoff to decide first

**Build on OpenAI Realtime (or a similar end-to-end voice agent API)** vs **assemble your own pipeline (Deepgram + Opus + Cartesia)**. Realtime is dramatically less work and handles turn-taking/barge-in for you, but you lose Opus's reasoning quality on routing decisions and the model isn't Claude. Your own pipeline keeps Opus in the loop but you'll spend weeks on latency and turn-taking that don't add user value.

My read: use Opus for prep + post-session synthesis where its quality matters, and accept a faster model (Haiku, or even GPT-4o via Realtime) for the in-the-moment routing where latency dominates. Worth pushing back on if you disagree.

## 1. The living prep doc + Haiku tool use

Right call. The prep doc becomes a **stateful tree the bot mutates as it traverses**. Haiku gets a small set of tools, each one a DB write:

- `mark_node_covered(node_id, summary)` — main checkmark action
- `transition_to(node_id, reason)` — explicit move; updates `current_node_id`
- `add_open_thread(text)` — "we should come back to X"
- `close_open_thread(thread_id, resolution)`
- `note_fact(text, attributed_to_speaker)` — surfaces things to fold into distillations later
- `add_dynamic_node(parent_id, title, opening_prompt)` — for off-tree improvisation that the user steers into
- `skip_node(node_id, reason)` — explicit "won't cover this"

Each call returns the updated state slice so Haiku's next turn sees its own writes. Tool calls also get logged to your existing `tool_calls` table for free auditability.

**Critical design choice:** Haiku must call `transition_to` *before* generating the spoken utterance, not after. Otherwise the routing decision and the words drift apart and you get a coverage log that doesn't match what was actually said. Enforce this in the prompt and the tool ordering.

## 2. DB schema — abstractions

The cleanest cut is **plan / state / history** as three separate concerns:

```
conversations
  id, user_id, started_at, ended_at, mode ('steered'|'open'),
  steering_text, status ('prepping'|'live'|'ended'|'synthesized')

conversation_topics            -- the "plan", from Opus prep
  id, conversation_id, label, priority ('must'|'should'|'optional'),
  status ('pending'|'in_progress'|'covered'|'skipped'),
  covered_at, order_hint

conversation_nodes             -- tree nodes under topics
  id, conversation_id, topic_id, parent_node_id (nullable),
  kind ('planned'|'dynamic'),    -- planned came from Opus, dynamic from Haiku tool
  title, opening_prompt, follow_ups (jsonb), exit_hints (jsonb),
  status ('pending'|'active'|'covered'|'skipped'),
  covered_at, covered_summary, order_hint

conversation_state             -- one row per conversation, mutable
  conversation_id (PK),
  current_node_id, current_topic_id,
  open_threads (jsonb),         -- [{id, text, opened_at, status}]
  facts_learned (jsonb),        -- [{text, attributed_to, ts}]
  speaker_map (jsonb)           -- {speaker_0: 'primary', speaker_1: 'partner', ...}

transcript_turns               -- append-only history
  id, conversation_id, ts, speaker_label, speaker_role,
  text, asr_confidence, was_routing_input (bool),
  active_node_id_at_turn         -- snapshot of where we were when this was said

node_visits                    -- audit log of tree traversal
  id, conversation_id, node_id, entered_at, exited_at, transition_reason
```

Three things worth calling out about this shape:

**Why split topics from nodes:** topics are the user-facing "did we talk about X" granularity. Nodes are the bot's internal navigation granularity. A topic gets marked covered when its required nodes are covered — that's a derived calculation, not a separate field to drift. Mirrors your existing `topics`/`topic_status` split.

**Why `conversation_state` as one mutable row vs. event-sourced:** Haiku needs to read current state cheaply on every turn (sub-100ms ideally). One row per conversation, updated in place, beats reconstructing from events. The `transcript_turns` + `node_visits` + `tool_calls` tables give you the history if you ever need to replay.

**Why `active_node_id_at_turn` on each transcript turn:** lets you reconstruct "what was the bot thinking when the user said X" post-hoc, which is gold for evals and debugging routing mistakes. Cheap column, huge analytical value.

## How it connects to your existing world

- `distillations`: post-session, an Opus job reads `transcript_turns` + `conversation_state.facts_learned` for one conversation and writes/updates distillations for that user. Single direction — distillations are output, not input.
- `topics` (existing global table): probably *not* the same as `conversation_topics`. Conversation topics are scoped to one session's plan; the existing `topics` table is the user's long-running theme list. The post-session synthesis is where conversation topics may bubble up into long-running topics. Keep them separate.
- `tool_calls`: Haiku's tool calls flow into this table you already have. Free audit log.

## Things I'd flag

- **Dynamic nodes are unbounded.** If the bot can keep adding off-tree nodes, the tree grows during the session and Haiku's prompt context grows with it. Cap it (e.g. max 10 dynamic nodes per session) or summarize older covered nodes when the tree gets big.
- **Tool-call vs. utterance race condition.** What if Haiku calls `mark_node_covered` but then the user says "wait no, that wasn't what I meant"? Need an `undo_last_coverage` tool or treat coverage as a soft signal that's revisited at end-of-session.
- **Pre-prep vs. live divergence.** When the user goes wildly off-script, do you re-prompt Opus mid-session to extend the plan? Or just let Haiku add dynamic nodes and accept the prep doc was wrong? My instinct: let it ride during the session, re-prompt Opus only if explicitly requested ("regenerate plan"). Cheaper and less jarring.

# Multi-Agent Architecture

Plan for evolving from a single mediator bot into a platform hosting many agents — each with its own identity, prompt, tool surface, participants shape, and data partition — while letting agents intentionally reach across partitions when it matters.

Design briefing. Two verification passes against the codebase are preserved as §19 (Codex read-only) and §20 (Codex gpt-5.5 high adversarial). The body integrates their findings as the actual design. Next step will be refactoring into phase sprints.

---

## 1. Core mental model

```
Channel (any addressable inbound surface)
  └─ Bot           (identity, prompt, tools, participants shape, persona)
        └─ Binding (which user or dyad this bot serves)
              └─ Topic   (the data partition; primary topic per bot)
                    └─ Knowledge artifacts (memories, themes,
                                            watch items, observations,
                                            distillations, OOB, status, …)
```

First-class concepts:

- **Channel** — transport surface a bot listens on (Discord bot account, phone number, future). Resolves inbound to a bot. No 1:1 assumption.
- **Bot** — agent identity with code-defined behavior. Has a *participants shape* (solo or dyad) and a primary topic.
- **Binding** — which user(s) a bot serves. Solo bot binds to one user; dyadic bot binds to a dyad.
- **Topic** — the data partition for accumulated knowledge.

Two principles drive everything:

1. **Partition = topic, attribution = bot.** Knowledge artifacts filter by topic; who recorded what is a separate column.
2. **Scope must be enforced, not requested.** Every tool call carries scope on `TurnContext`; every read and write is validated against the bot's authorization at the tool boundary, not by trusting the model.

The codebase already has a non-trivial scoping axis ("about whom"); multi-agent introduces a second, orthogonal axis ("topic"). They compose.

## Why this exists

Some bots need to track a user's structured, evolving state over weeks or months: a pregnancy (gestational week, weight gain, scan dates), a fitness program (weights, frequency, race times), a weight-loss arc, a savings target, a sobriety streak. The existing artifact tables (`memories`, `themes`, `observations`, `distillations`, `watch_items`, `out_of_bounds`) capture narrative and emotional content. ## Writing effective subagent prompts (universal rules)

Regardless of which pathway you use, the receiving model starts with **zero context** from your conversation. Treat every dispatch like briefing a smart colleague who just walked into the room:

- **Working directory** — name it explicitly (`/Users/user_c042661f/Documents/megaplan`).
- **Files / paths** — list exact paths, not "the relevant files."
- **Goal + why** — what you're trying to accomplish and why the answer matters.
- **What you've already ruled out** — saves the subagent re-doing your work.
- **Output shape** — diff, ranked list, JSON, prose under N words. Specify.
- **Length cap** — "under 600 words" or "respond in under 200 words."
- **Be opinionated** — for adversarial / second-opinion tasks, tell the model not to hedge. Otherwise they'll all hedge.

Long prompts (>2 KB) belong in a file (`/tmp/<task>_prompt.md`) and get loaded by `cat` or `-d @file`.

## Fan-out: judge / jury patterns

When the call is genuinely high-stakes, send the same prompt to multiple models *in parallel* and compare. From this harness, that means a single message with multiple Bash tool calls (or Agent calls) in parallel:

- Codex via `codex exec`

Don't fan out for routine work — it's wasteful. Reserve it for: pre-merge review of risky changes, architecture decisions you can't easily reverse, security-sensitive code paths, judging artifacts that megaplan itself produced.

362	Notes on the schema choices:
363	
364	- **`conversations.topic_id`** links a session to the long-running global `topics` table when relevant — that's how the post-session synthesis knows where to deposit distillations. Nullable because some sessions don't map cleanly to a single existing topic.

366	- **`conversation_state` is one row updated in place**, not event-sourced. Haiku reads it on every turn — needs to be cheap. The history lives in `transcript_turns`, `node_visits`, and `tool_calls`.
367	- **`active_node_id` on each transcript turn** is critical for replay/evals — lets you reconstruct routing context for any utterance after the fact.
368	- **`tool_calls`** (already exists) captures every Haiku tool invocation. Free audit log of every routing decision.
369	- **`prep_doc_summary` is denormalized** onto `conversations` so the user can scroll through past sessions without joining a tree.

381	## Open questions / things to decide
382	
383	1. **TTS choice**. OpenAI is faster to integrate and instructable on tone, but only has preset voices. ElevenLabs has voice cloning (a consistent "Tante Rosi" voice across sessions). Trade-off: if Rosi's identity matters as a voice, ElevenLabs. If "warm and grandmotherly" is enough, OpenAI.
384	2. **Dynamic node cap**. How many `add_dynamic_node` calls per session before we cut Haiku off? Suggest 10; revisit after observing real sessions.
385	3. **Re-prep mid-session**. If the user goes wildly off-script, do we trigger a fresh Opus run to extend the plan, or just let Haiku improvise with dynamic nodes? Default: improvise. Re-prep is a manual button (v2).
386	4. **Where does prep doc live during the session?** Three options: (a) JSONB column on `conversations` (simple, but mutates a wide row a lot); (b) reconstruct from `conversation_topics` + `conversation_nodes` each turn (clean but a join per turn); (c) reconstruct once into orchestrator memory at session start, persist mutations to the structured tables, prompt-cache the reconstructed blob. **Lean (c).**
387	5. **Coverage soft-signal vs hard.** If Haiku marks a node covered but the user later contradicts, do we have `undo_last_coverage`, or do we just let the post-session synthesis re-judge? Suggest: include the tool, also have synthesis re-judge.
388	6. **Partner consent / dyadic sessions.** If both partners are present, both need to have agreed to live transcription. UI flow + DB flag for consent state needed before shipping dyadic.
389	7. **Persistence of audio.** Do we store the raw audio or only the transcript? Privacy-favored default: transcript only, audio discarded after Deepgram finalization. Confirm.
390	8. **Auth surface.** The web UI needs auth — presumably the same identity as the Discord user. Mechanism (magic link? Discord OAuth?) is unspecified.
391	
392	## Staged rollout
393	
394	Don't build it all at once. Each stage is independently shippable and de-risks the next.
395	
396	1. **Prep doc only.** Opus generates and persists the JSON plan. Render it as a readable markdown plan in the UI. No live audio. This alone is useful — the user reads the prep doc before a real human conversation.
397	2. **Transcript-only live mode.** Browser captures mic, Deepgram streams to a backend that persists `transcript_turns`. UI shows live transcript + tree state with the current node highlighted by a manual click. No bot speech. Validates ASR, diarization, schema.
398	3. **Manual bot turns.** A "speak next" button triggers one Haiku call; bot responds with TTS. Validates Haiku tools + tree mutation + post-session synthesis.
399	4. **Autonomous turn-taking.** Client VAD + silence fallback + barge-in. The full feature.
400	
401	Each stage adds one new dependency category, so failures are isolated to that stage's surface.
