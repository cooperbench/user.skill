# Plan 5 — Scheduled jobs + decay + pause/resume + crisis polish

Authoritative spec: `mediator-bot-spec.md`. Read in prep, focusing on: "Triggers" (scheduled), "Decay", "Multi-Message Handling" (restart recovery for jobs), "Pause / Resume", "Crisis Handling", "WhatsApp 24-Hour Window" for templates, and the bits of "Operations" related to scheduled jobs.

Plans 1–4 are assumed complete. The system can take messages, run the loop with real OOB and scoring, and produce outbounds. This plan adds the time-based behaviors and the global controls (pause, crisis escalation) that the spec describes.

## Scope (in)

### Scheduled-job worker
- A single async worker (background task in the FastAPI app, or a separate Railway worker process — pick whichever is cleaner; document the choice).
- Polls `scheduled_jobs` for `status='pending' AND scheduled_for <= now()` using `SELECT ... FOR UPDATE SKIP LOCKED` so two workers can't fire the same job. Each job has a unique ID for idempotency.
- On fire: invoke the appropriate handler, then mark `status='fired'`, set `fired_at`. On handler error: log and leave the job pending for one retry, then mark `status='cancelled'` with a reason.

### Job types
- `weekly_summary` — per partner. Renders the Meta-approved `weekly_summary` template ("Hi {{1}}, this week we had {{2}} conversations and touched on {{3}} ongoing things. Want to talk through anything? Just ask."). Sends via `send_outbound` (which handles 24h window). Also performs the decay housekeeping pass (below). Schedule recurrences on completion (one new job per partner per week, configurable timing per user).
- `checkin` — variable check-in (4–24h, the loop chose the timing). One pending per user max. Inserting a new one supersedes any existing pending check-in for that user (mark old one `status='superseded'`). On fire: triggers the agentic loop with a `trigger_metadata={"kind": "checkin", "context": ...}` so the loop can produce a context-aware nudge or, if outside the 24h window, send the `checkin_nudge` template.
- `watch_item_due` — fires when a watch item's `due_at` arrives. Surfaces it next time the owner is in conversation, OR creates a `checkin` job at a near-future time so the bot proactively raises it. Pick one based on whether the owner is currently in the 24h window.
- `oob_review` — when an OOB's `review_at` hits. Triggers the loop with metadata so the bot asks the owner if it's still off-limits.

### Late-job handling on restart
- On startup: scan `scheduled_jobs` with `status='pending' AND scheduled_for < now()`:
  - Less than 1h late → fire normally.
  - 1–24h late → fire with `context.delayed = true` so the bot can adjust ("I meant to send this earlier...").
  - More than 24h late → mark `cancelled` with reason `"too stale"`.
- This is in addition to message-recovery from Plan 2.

### Decay housekeeping (runs inside the weekly summary job)
- Themes with no `last_active_at` update for 6+ weeks → `dormant`.
- Themes dormant 4+ months → `resolved_by_time`.
- Observations not reinforced for 3+ months → confidence drops one level (high→medium→low). Not reinforced for 6+ months → `stale`.
- Watch items past `due_at` with no addressing for 30+ days → `expired`.
- `last_reinforced_at` (not `last_active_at`) drives observation/theme decay; verify the queries reflect that.
- Also run the re-scoring pass for observations flagged `needs_rescoring=true` from Plan 4.

### Query-level decay
- Add a `recency_weighted_score(significance, last_reinforced_at)` SQL function or app-side helper. Formula per spec: `significance / (1 + age_days / 60)` where `age_days = EXTRACT(EPOCH FROM (now() - COALESCE(last_reinforced_at, created_at))) / 86400`. ~60-day effective half-life. Pure SQL, no exp() needed.
- Update the read tools' default sorts to use it. Older content remains searchable but is deprioritized in default surfacing.

### Timezone handling
- Owner-bound scheduled jobs use the owner's `users.timezone`. The recurring `weekly_summary` fires at 09:00 in the owner's local time on the configured day.
- `schedule_checkin` writes absolute UTC instants — the agentic loop converts "in 8 hours" / "tomorrow morning" to UTC at write time using the owner's timezone (timezone-aware datetime math, not naive arithmetic).
- Heartbeat and other non-user-bound jobs use UTC.

### Pause / Resume
- `/pause` slash command (literal `/pause` in inbound text — this is the only slash command per spec): on receipt from either user:
  - Cancel all pending scheduled jobs for both users (`status='superseded'`).
  - Set a global `paused_at` flag (one row in a small `system_state` table — create the table here).
  - Send pause confirmation outbound to each partner via the `pause_confirmation` template (works inside or outside 24h window).
  - The `paused_for_user(user_id)` hook from Plan 2 now reads from `system_state` and returns True when paused.
- `/resume` from either partner:
  - Clear `paused_at`.
  - Do NOT auto-process backlog — just re-enable inbound processing.
  - Restore weekly summary scheduling (insert next `weekly_summary` jobs).

### Crisis handling polish
- The system prompt already (from Plan 3) instructs the loop to drop the mediator role and consider `escalate_to_partner`. This plan tightens the escalation flow:
  - **Concrete gate per spec:** `escalate_to_partner` may only be called when (a) the triggering message meets the `crisis` charge definition, OR (b) the user explicitly asks the bot to alert their partner. The tool input requires `is_crisis: bool` and a named `reason`. Reject any call that doesn't satisfy one of these triggers — the orchestrator validates before sending. This guard is in addition to the prompt-level instruction.
  - `escalate_to_partner` writes a distinguished `bot_turns.reasoning` entry and triggers an outbound to the OTHER partner using the `escalation` template — including outside the 24h window.
  - The `{{3}}` parameter is filled by the bot with a deliberately vague contextual line per spec ("They're going through a hard moment", etc.).
  - Logs the escalation with sufficient detail for retro audit (admin view in Plan 6 will surface it).
- For acute crisis: the bot also surfaces region/language-appropriate emergency resources directly to the affected partner in the conversational outbound. Tested with a deterministic mock LLM.

### Heartbeat upgrade
- Plan 1 left a heartbeat stub. Implement it now as a periodic `scheduled_jobs` row of type `heartbeat` that fires daily and writes a log line; alerts on its absence are external (admin doc).
