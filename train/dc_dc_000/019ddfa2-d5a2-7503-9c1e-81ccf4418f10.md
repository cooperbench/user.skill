> DEVELOPER

should orchestaors be allowed to run nodes code? Should nodes be allowed run orchestaors? Should orchestarors be allowd from other orchestaors? What is ACTUALLY the distinction between them practically?

> AGENT

Practically, the distinction should be about **control responsibility**, not packaging.

**Node**
A node is an executable unit with a narrow contract:

```text
inputs -> work -> outputs
```

It should be mostly unaware of the wider workflow. It may call libraries and subprocesses, but it should not decide the broader production sequence.

Examples:
`transcribe`, `scenes`, `shots`, `render_card`, `render_talk_body`, `validate_video`.

**Orchestrator / Conductor**
A conductor decides:

```text
which nodes run, in what order, with what shared context, retries, skips, cache policy, and artifact layout
```

Examples:
`hype_cut`, `event_talks`, `podcast_clips`, `social_pack`.

The clean rule set I’d use:

1. **Conductors can run nodes**
   Yes. That is their main job.

2. **Nodes should not run conductors**
   No, not directly. If a node needs a whole workflow, it is probably not a node. Make it a conductor step or call a smaller node instead.

3. **Conductors can run other conductors, but explicitly**
   Yes, with guardrails. This is useful for composition:
   `event_talks` might call a `render_cards` conductor or a `transcript_analysis` conductor.

   But make it visible in metadata as a child conductor dependency, not hidden in arbitrary code.

4. **Nodes can run other nodes only rarely**
   Usually no. A node should not secretly orchestrate a mini-pipeline. If it must, either:
   - split it into multiple nodes and move sequencing into a conductor, or
   - mark it as a composite node, but that is a smell.

The practical distinction:

```text
Node = leaf work unit
Conductor = workflow controller
```

A stricter runtime model:

```text
Conductor -> Node          allowed
Conductor -> Conductor     allowed, declared
Node -> Node               discouraged / only internal implementation detail
Node -> Conductor          disallowed
```

Why this matters:

- Scheduling: conductors create run graphs; nodes execute graph leaves.
- Caching: nodes cache outputs; conductors cache workflow state and decisions.
- UI: nodes appear as capabilities; conductors appear as workflows/templates.
- Debugging: conductor run contains step runs; node run contains logs/artifacts.
- Reuse: nodes should be reusable across conductors without dragging workflow assumptions.
- Safety: preventing nodes from launching conductors avoids recursive or invisible workflows.

So the actual test is:

> Does this thing decide a workflow, or does it perform one bounded operation?

If it decides sequencing, branching, retries, child runs, or cross-step artifact policy, it is a conductor. If it turns declared inputs into declared outputs, it is a node.

> AGENT

Yes: dry-run is **an orchestrator/conductor behavior**, not a separate conductor.

A conductor has two modes:

```text
run     -> execute the workflow
dry-run -> plan/describe the workflow without executing it
```

So `dry-run` should live in the conductor runner contract, like:

```python
ConductorRunRequest(dry_run=True)
```

For `builtin.hype`, dry-run should produce the step plan. For `builtin.event_talks`, dry-run should produce the resolved event command. Later, a richer conductor engine could return a structured graph instead of just argv lines.

**Cleanup Plan**
1. **Extract Shared Primitives**
   Move reusable schema concepts out of `artagents.nodes.schema` into a neutral module, probably:

   ```text
   artagents/contracts.py
   ```

   or:

   ```text
   artagents/components/schema.py
   ```

   Move/alias:
   - `NodePort` -> `PortSpec`
   - `NodeOutput` -> `OutputSpec`
   - `CachePolicy`
   - `CommandSpec`
   - `IsolationMetadata`

   Then both nodes and conductors import from shared contracts. Keep backward-compatible aliases in `nodes.schema`.

2. **Fix Built-In vs Curated Semantics**
   Right now `builtin.hype` and `builtin.event_talks` live under `conductors/curated/`, which is semantically odd.

   Prefer:

   ```text
   artagents/conductors/builtin.py
   artagents/conductors/builtin/hype.py
   artagents/conductors/builtin/event_talks.py
   artagents/conductors/curated/
   ```

   Or, if folder-copyability matters more:

   ```text
   artagents/conductors/bundled/hype/
   artagents/conductors/bundled/event_talks/
   ```

   Then IDs can still be `builtin.hype`, but discovery code is honest about source.

3. **Make Conductor Run UX Less Awkward**
   Keep generic `--out` available, but do not require it for every conductor.

   Better CLI:

   ```bash
   python3 pipeline.py conductors run builtin.hype -- --brief brief.txt --out runs/x --target-duration 28
   python3 pipeline.py conductors run builtin.event_talks -- ados-sunday-template --out runs/event/talks.json
   ```

   The conductor runtime can derive `request.out` from passthrough args when needed, or use a default like `runs/<conductor-slug>`.

4. **Separate Dry-Run Output From Shell Printing**
   Make dry-run return a structured plan:

   ```json
   {
     "steps": [
       {
         "key": "arrange",
         "kind": "node",
         "node_id": "builtin.arrange",
         "command": [...]
       }
     ]
   }
   ```

   CLI can still print shell commands, but the internal object should be workflow-shaped.

5. **Tighten Runtime Contract**
   Conductor runtime should explicitly support:

   ```python
   plan(request) -> ConductorPlan
   run(request) -> ConductorRunResult
   ```

   For now `dry_run=True` calls `plan()`. This makes “planning” a first-class conductor responsibility.

6. **Document Call Rules**
   Encode the practical rules in docs/tests:

   ```text
   conductor -> node: allowed
   conductor -> conductor: allowed if declared
   node -> conductor: disallowed
   node -> node: discouraged unless internal implementation detail
   ```

7. **Eventually Replace Legacy Bridge With Real Scheduling**
   `builtin.hype` currently delegates to legacy `pipeline.py`. That is fine now. The eventual excellent version would have the conductor actually schedule node runs through `run_node()` using its declared `child_nodes`.

   That can be phase two. Do not do it in the same cleanup unless you want a larger refactor.

I’d do this in two passes: first shared contracts + source layout + CLI UX, then structured conductor plans. The legacy bridge can stay until the conductor engine is mature.
