## Goal
Remove the silent implicit-acceptance of unresolved blocking flags when the gate recommends PROCEED. Make the gate either resolve every blocking flag explicitly, or pick ITERATE / ESCALATE. Reject rubber-stamp rationale on accept_tradeoff actions, not just on dispute actions.

## Motivation
The current gate logic (v0.13) has two related problems:
1. The gate prompt tells the agent "you may resolve at most 3 flags explicitly per gate call. Any remaining blocking flags are implicitly accepted as tradeoffs if you recommend PROCEED." (prompts/gate.py, around lines 105-114)
2. The handler enforces this by silently auto-marking unresolved blocking flags as accept_tradeoff (handlers.py, around lines 621-635 inside _apply_gate_outcome).
3. The rubber-stamp check (handlers.py around lines 600-607) only validates dispute.evidence — it accepts any accept_tradeoff.rationale including boilerplate.

Net effect: a gate PROCEED can ship with 5 unresolved blocking flags, silently auto-accepted, with zero resistance from the system. The human reviewing the PR sees them in accepted_tradeoffs but the agent was never forced to reason about each one.

## Exact changes

### Change 1: prompts/gate.py
Replace the block that currently reads roughly:
  "You may resolve at most 3 flags explicitly per gate call. Any remaining
  blocking flags are implicitly accepted as tradeoffs if you recommend PROCEED.
  If a flag is structurally unresolvable (e.g., references infrastructure
  outside the repo), you should still PROCEED — do not loop indefinitely
  on flags that cannot be addressed."

with strict language:
  "If you recommend PROCEED, you MUST provide a flag_resolutions entry for
  every blocking flag. There is no implicit acceptance. If you cannot
  resolve every blocking flag, choose ITERATE (send back for revision)

  (infrastructure outside the repo, product decision required) are ESCALATE,
  not PROCEED with a non-answer.

  For each blocking flag:
  - dispute: critique is factually wrong. Evidence must cite specific
    file/line/doc — generic statements like 'handled correctly' are invalid.
  - accept_tradeoff: concern is real but accepted as a known limitation.

        # Implementation Plan: v0.14.0 — Strict Flag Resolution at the Gate

## Overview
The gate currently has two leniency holes: (1) unresolved blocking flags are silently auto-accepted as tradeoffs when the gate says PROCEED, and (2) `accept_tradeoff` resolutions bypass the rubber-stamp check that `dispute` resolutions must pass. This change enforces that every blocking flag must be explicitly resolved for a PROCEED to stand, rejects boilerplate `accept_tradeoff` rationale, and introduces a one-shot reprompt before auto-downgrading to ITERATE.

Key files: `megaplan/prompts/gate.py`, `megaplan/handlers.py`, `tests/test_megaplan.py`, `pyproject.toml`, `CHANGELOG.md`.

The branch `gate-strict-flag-resolution` already exists (current branch).

### Architectural decision: reprompt lives in `handle_gate`, not `_apply_gate_outcome`

FLAG-001 showed that `prompt_override` replaces the entire gate prompt, so a short reprompt message would lose all gate context (instructions, schema, signals, flags). The fix: the reprompt loop lives in `handle_gate` where we have access to `args`, `root`, and can build a full reprompt. `_apply_gate_outcome` stays a pure decision function — it returns the list of `blocking_unresolved` flag IDs so the caller can decide whether to reprompt. This keeps `_apply_gate_outcome` signature unchanged and avoids threading `args`/`root` into it.

### Architectural decision: debt recording moves after outcome

FLAG-002 showed that `_record_gate_debt_entries` is called before `_apply_gate_outcome`, so a PROCEED that gets auto-downgraded to ITERATE would still write debt. Fix: move the call to after `_apply_gate_outcome`, and only record debt when the final recommendation is still PROCEED.

### Architectural decision: derive debt from `flag_resolutions`

FLAG-003 showed that under strict resolution, the `accepted_tradeoffs` fallback path (reading `gate_summary["unresolved_flags"]`) disappears because successful PROCEEDs won't have unresolved flags. Fix: after validating `flag_resolutions`, build synthetic `accepted_tradeoffs` entries from `flag_resolutions` items with `action: accept_tradeoff`, and merge them into `worker.payload["accepted_tradeoffs"]` before debt recording. This ensures debt is always tracked for accepted tradeoffs regardless of whether the LLM populated the separate field.

### Step 4: Build reprompt loop in `handle_gate` (`megaplan/handlers.py:987-1038`)
**Scope:** Medium
1. **Update** the `_apply_gate_outcome` call at line 1011 to unpack the new fourth return value (`blocking_unresolved_ids`).
2. **Add reprompt logic** after `_apply_gate_outcome` returns:
   - If `blocking_unresolved_ids` is non-empty:
     - Build a full reprompt: call the appropriate prompt builder (`create_claude_prompt` / `create_codex_prompt` / `create_hermes_prompt` for "gate") using the existing `resolve_agent_mode` result to pick the right builder. Then **append** a reprompt addendum listing the missing flag IDs:
       ```
       \n\nREPROMPT: Your previous response left N blocking flag(s) unresolved: {ids}.
       You MUST provide a flag_resolutions entry for each, or change your recommendation
       to ITERATE or ESCALATE. There is no implicit acceptance.
       ```
     - Pass this full prompt as `prompt_override` to `_run_worker("gate", ...)`.
     - Rebuild `gate_summary` from the new worker result (call `build_gate_artifact` again).
     - Re-run `_apply_gate_outcome` with the new `gate_summary`.
     - If `blocking_unresolved_ids` is STILL non-empty:
       - Mutate `gate_summary["recommendation"]` to `"ITERATE"`.
       - Append to `gate_summary["rationale"]`: `" [Auto-downgraded from PROCEED: N blocking flag(s) not resolved after reprompt]"`.
       - Set `gate_summary["passed"] = False`.
       - Set `gate_summary["reprompted"] = True`.
       - Set `result = "blocked"`, `next_step = "revise"`, update `summary`.
     - If resolved on reprompt: use the new result/next_step/summary. Set `gate_summary["reprompted"] = True`.
3. **Move** `_record_gate_debt_entries` call to AFTER the reprompt logic, so it only runs on the final recommendation. Guard it: only call when `gate_summary["recommendation"] == "PROCEED"` (the function already checks this internally, but being explicit at the call site prevents confusion).
4. **Derive debt from resolutions**: Before calling `_record_gate_debt_entries`, build synthetic `accepted_tradeoffs` from the final `gate_summary["flag_resolutions"]` entries with `action: accept_tradeoff`:
   ```python
   resolution_tradeoffs = [
       {"flag_id": r["flag_id"], "concern": r.get("rationale", ""), "subsystem": ""}
       for r in gate_summary.get("flag_resolutions", [])
       if r.get("action") == "accept_tradeoff"
   ]
   existing = worker.payload.get("accepted_tradeoffs", [])
   existing_ids = {t.get("flag_id") for t in existing if isinstance(t, dict)}
   for rt in resolution_tradeoffs:
       if rt["flag_id"] not in existing_ids:
           existing.append(rt)
   worker.payload["accepted_tradeoffs"] = existing
   ```
   This ensures `_record_gate_debt_entries` sees complete tradeoff data regardless of whether the LLM populated `accepted_tradeoffs`.
5. **Re-write `gate.json`** after all mutations: `_write_json_artifact(plan_dir, "gate.json", gate_summary)` unconditionally after the reprompt/outcome logic, before `_store_last_gate`. This replaces the initial write at line 1007 — move the initial write down or add a final re-write. Simplest: keep the initial write (needed for intermediate state if worker crashes) and always re-write after outcome.
