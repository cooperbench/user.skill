# Implementation Plan: Partner Bridge Paths

## Overview

Add a `partner_path` field to `bridge_candidates` (values: `message_partner`, `coach_in_person`, `casual_share`, `hold_for_context`, `ask_permission`, `do_not_bridge`) and rewire prompt/hot-context/tooling so the agent can express how a bridge should be carried, separately from whether the row is sendable. The existing immediate-send mechanism (`send_bridge_candidate` for `ready` rows) is preserved; `message_partner` is a non-sending path that keeps a ready bridge surfaced in the target partner's hot context until it is substantively addressed.

Key constraints:
- Existing migrations are immutable (`0013_bridge_candidates.sql`, `0015_distillations.sql` already landed). Add a new migration `0016_partner_bridge_paths.sql`.
- Existing local distillation edits (`migrations/0015_distillations.sql`, distillation-related changes in `tool_schemas.py`, `read_tools.py`, `write_tools.py`, `registry.py`, `common.py`) must remain untouched.
- Brief: do **not** auto-create historical bridges; for the new column, default existing rows to `message_partner` and leave any deeper backfill to a documented manual/script path.
- Resolve the `escalate_to_partner` conflict between `prompts.py:171` (uses it on accepted bridge offers) and `prompts.py:135 / 200–207` (crisis-only) by routing accepted bridge offers through `create_bridge_candidate` (`partner_path=message_partner`) or `send_bridge_candidate` for explicit immediate-send.
- Hot context restricts to actionable target-facing partner bridges (status `ready`, `partner_path=message_partner`), supports multiple, excludes `sent`/`addressed` by default.
- **Visibility (from FLAG-002):** target-side reads (`list_bridge_candidates`, `bridge_candidate_visible_to_target`) must also factor in `partner_path`. A `ready` row of a non-`message_partner` path is internal source-side bookkeeping and must NOT be exposed to the target. `sent` and `addressed` rows remain visible regardless of path (they were delivered or explicitly resolved).

### Step 1: Add the schema migration (`migrations/0016_partner_bridge_paths.sql`)
**Scope:** Small
1. **Create** a forward-only migration that:
   - `ALTER TABLE bridge_candidates ADD COLUMN IF NOT EXISTS partner_path text NOT NULL DEFAULT 'message_partner'` with a CHECK constraint enumerating the six values (`message_partner`, `coach_in_person`, `casual_share`, `hold_for_context`, `ask_permission`, `do_not_bridge`).
   - Adds a partial index `idx_bridge_candidates_target_ready_message_partner ON bridge_candidates (target_user_id, created_at DESC) WHERE status='ready' AND partner_path='message_partner'` to back the hot-context query.
2. **Document** in a SQL comment that historical rows default to `message_partner` and that no historical bridges are auto-created; operators wanting to re-classify older rows should run an ad-hoc UPDATE.
