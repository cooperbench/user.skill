## Context

- **sphinx-9711**: `adjacent_calls` correctly flagged *"The same lexicographic string-comparison bug also exists in application.py:226 and application.py:405."* — real unfixed adjacent sites. Review verdict: **approved**, rework_items: **0**.

- **4 of 7 flagged findings across all 4 reviews were "test-referenced-by-plan-doesn't-exist-in-repo"** — noise that distracts the criteria-verdict worker. - **`placement` missed the matplotlib-25479 wrong-layer case** (fix in `set_cmap` when the source is `ColormapRegistry.register`). The check ran, but its findings said "this is a valid place to fix" — it didn't do the backward-trace to find where the bad state first originates.

## Goal

Three targeted fixes, ordered by validation-data impact:

1. **Severity inheritance**: when a flagged finding lacks explicit severity, inherit from the check spec's `default_severity`. Promote any flagged finding with inherited `likely-significant` severity to a rework item. ## What needs to exist

### 1. Severity inheritance in `_synthesize_review_rework_items`

In `megaplan/handlers.py`, locate `_synthesize_review_rework_items` (or whatever private helper produces rework items from review checks — look near the heavy-review branch of `handle_review`). The current logic is roughly:

```python
for check in payload.get("checks", []):
    check_id = check.get("id")
    check_def = review_checks.get_check_by_id(check_id) if check_id else None
    for finding in check.get("findings", []):
        if not finding.get("flagged"):
            continue
        severity = finding.get("severity", "")
        if severity != "likely-significant":
            continue
        # ... promote to rework item
```

Change it to inherit from the check spec when the finding's severity is missing or empty:

```python
for check in payload.get("checks", []):
    check_id = check.get("id")
    check_def = review_checks.get_check_by_id(check_id) if check_id else None
    for finding in check.get("findings", []):
        if not finding.get("flagged"):
            continue
        severity = (finding.get("severity") or "").strip()
        if not severity and check_def is not None:
            severity = check_def.default_severity
        if severity != "likely-significant":
            continue
        # ... promote to rework item (unchanged)
```

That's it — a small, local change. The key insight is: **if a finding is explicitly flagged and the check spec's default is `likely-significant`, then any reasonable LLM interpretation of "flagged but no severity" is "blocking." Inheriting is the right default.**

An even safer variant: inherit the default severity ALWAYS when the finding is flagged, unless the finding explicitly overrides with `likely-minor`. This means any `flagged: true` becomes a rework candidate unless the LLM explicitly de-escalates it. Implementer's call between these two variants — the safer one is marginally more aggressive, the stricter one preserves finer-grained LLM control. Pick the safer one (inherit-always-unless-overridden) and document the rationale in a comment.
