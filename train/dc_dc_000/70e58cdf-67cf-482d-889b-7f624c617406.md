**Partitioning Strategy**:

The snapshot creates 7 partitions of the queue for different lifecycle phases:

1. **Objective items** (issues that count toward backlog):
   - Filtered by `counts_toward_objective_backlog()` → mechanical_defect only
   - Further split by plan status:

3. **Postflight review items** (assessment requests + assessed subjective + executable review findings):
   - `subjective_postflight_items`, `assessment_request_items`, `executable_review_items`
   - Conditions: triage is current, not stale, has run at least once

4. **Scan items** (workflow:: items):
   - `build_deferred_disposition_item()`, `build_run_scan_item()`

5. **Postflight workflow items** (score checkpoints, create-plan, import-scores, communicate-score):
   - Built via `_workflow_partitions()`
   - Only in PHASE_WORKFLOW_POSTFLIGHT

6. **Triage items** (triage:: stages):
   - Built via `build_triage_stage_items()`
   - Only in PHASE_TRIAGE_POSTFLIGHT

7. **Execution items** (what to work on right now):
   - Phase-dependent; set by `_execution_items_for_phase()`

```python
        return REVIEW_DEFECT
    if detector == "concerns":
        return REVIEW_CONCERN
    if detector in {subjective_review, subjective_assessment, holistic_review}:
        return ASSESSMENT_REQUEST
    if detail.get("concern_verdict") == "confirmed":
        return REVIEW_CONCERN
    return MECHANICAL_DEFECT

def infer_work_item_origin(detector, detail=None) -> str:
    if detector == "review":
        return REVIEW_IMPORT_ORIGIN
    if detector == "concerns":
        return REVIEW_IMPORT_ORIGIN if verdict=="confirmed" else SCAN_ORIGIN
    if detector in {subjective_review, subjective_assessment, holistic_review}:
        return SYNTHETIC_TASK_ORIGIN
    return SCAN_ORIGIN
```

**Natural Sort Key** (`_natural_sort_key()` in ranking.py):

Determines baseline priority when no plan ordering:

```
Rank -3: INITIAL_REVIEW subjective dimensions (unassessed)
  Sort by: (score, id)

Rank -1: TRIAGE_STAGE items (workflow stages)
  Sort by: (is_blocked, stage_index, id)

Rank 0:  CLUSTER items
  Sort by: (action_type_priority, -member_count, id)
  Priorities: auto_fix=0, refactor=1, manual_fix=2, reorganize=3

Rank 1:  ISSUE items (individual + assessed subjective)
  Sort by: (-estimated_impact, confidence, -review_weight, -detail.count, id)
  
  For subjective issues:
    Sort by: (-estimated_impact, subjective_score, id)
```

**Item Sort Key** (`item_sort_key()` in ranking.py):

Final sort combining plan position + natural ranking:

```
If _plan_position is set:
  (_TIER_PLANNED, plan_pos, blocked, stage_idx, id)  [for stages]
  (_TIER_PLANNED, 0, plan_pos, id)                   [for others]

Else:
  (_TIER_NEW if _is_new else _TIER_EXISTING, *_natural_sort_key())
```

```python
impact = per_point * headroom
```

### 9. KEY ARCHITECTURAL INSIGHTS

**Explicit Semantics Over String Sniffing**:
- Cluster behavior is driven by explicit `action_type` and `execution_policy` fields
- String matching on commands is a **fallback** only, not the primary source of truth
- `normalize_cluster_semantics()` writes canonical fields at load time

**Synthetic Item IDs Are Fixed**:
- Workflow items use hardcoded IDs: `workflow::create-plan`, `workflow::score-checkpoint`, etc.
- Triage stages use fixed IDs: `triage::observe`, `triage::reflect`, etc.
- Subjective items use dynamic IDs: `subjective::{dimension_key}` (slugified)

**Queue Snapshot Is the Single Source of Truth**:
- All partitioning logic lives in `build_queue_snapshot()`
- Phase determination is deterministic and based on item presence
- Execution items are phase-dependent (only one phase active at a time)

**Plan-Aware Sorting**:
- Items get `_plan_position` and `_is_new` stamped during finalization
- Single sort pass using `item_sort_key()` produces final order
- Plan-tracked items sort first, then existing by natural rank, then new by natural rank

**No Regex/Prefix Checks on IDs**:
- `scope_matches()` in helpers uses simple prefix checks (`id.startswith(scope)`) for `::` patterns
- No regex inference from ID structure
- Cluster names (e.g., `auto/...`) are for display; semantics are in explicit fields

**Backward Compat Strategy**:
- Old fields (issue_kind, origin aliases) are read and normalized
- New canonical fields (work_item_kind, execution_policy) are written alongside
- Data migration happens at load time, not at query time
