# Local-only generations as worker task inputs

Read CLAUDE.md at the repo root first — it has cross-cutting rules and points to relevant sub-docs (especially `task_worker_lifecycle.md`, `unified_task_creation.md`, `storage_uploads.md`, `edge_functions.md`).

## Background

The app now supports `storage_mode='local'` generations (see `src/shared/lib/media/createGenerationFromFile.ts` → `createGenerationForLocalFile()`). The bytes live in the user's browser via a `FileSystemFileHandle` persisted in IndexedDB; the DB row carries `local_handle_id` instead of a `location` URL.

Today, when a user takes a generation and uses it as **input** to a worker task (travel, refine, masked-edit, etc.), the app puts a Supabase Storage URL into task params and the worker fetches it via HTTP. For local-only generations, that URL doesn't exist — and the worker has no way to reach into the browser.

This task wires those local-only generations through to the worker correctly, with a tiered strategy.

## Design

Implement a **per-input** resolution layer that runs at task-create time. For each input that references a generation:

1. If `storage_mode === 'remote'` (or absent / 'uploading' that has materialized) → use existing URL behavior. No change.
2. If `storage_mode === 'local'`:
   - **Detect whether a local worker is reachable** via a healthcheck (e.g. `GET http://localhost:<configured-port>/health` with a short timeout, ~250ms). Cache the answer for the duration of the task-creation call (don't re-probe per input).
   - **If local worker reachable**: read the file bytes from the FileSystemFileHandle, write them to a known shared dir (e.g. `~/.reigh-local-files/<local_handle_id>.<ext>`), and put a `file://` URL pointing at that path into the task params. The worker's `download_utils.py` already handles `file://` URLs (verify this — `reigh-worker/source/utils/download_utils.py` around line 60), so no worker changes should be needed. The materialized file is the "duplicate" per user wording.
   - **If no local worker**: upload the file bytes to Supabase Storage on demand. Reuse the existing upload helper in `src/shared/lib/media/imageUploader.ts`. Put the resulting public URL into task params. Mark the generation row with the new `location` (or a sibling `materialized_location`) so a second use of the same input doesn't re-upload — idempotent.

## Mixed inputs

A single task can reference both local-only and remote generations as inputs. The resolver MUST operate per-input, not per-task. After resolution, the task params contain a uniform set of URL strings (mix of `https://...` and `file://...`) — the worker doesn't know or care which inputs were originally local.

## Cleanup ("delete the duplicate after")

After task completion, the duplicate created during resolution must be cleaned up so we don't accumulate orphaned copies:

- **Local-worker `file://` materialization**: when the task completes, the file at `~/.reigh-local-files/<handle_id>.<ext>` is no longer needed. Delete it. Implement this in the `complete_task` edge function path OR via a worker-side cleanup hook OR via an app-side post-completion handler — whichever is most natural given the existing complete-task lifecycle. The original FileSystemFileHandle in the browser is untouched; we only delete the materialized copy.
- **Remote-worker upload-on-demand**: this is more nuanced. If we keep the uploaded copy, the generation effectively becomes remote-mode, defeating the user's local choice. Recommended: keep the upload only for the duration of the task (idempotency caching) and delete it after task completion. Update the generation row to remove the cached URL. Same lifecycle hook as above. If the user uses the same local generation as input again later, we re-upload (small cost, preserves intent).

The lifecycle hook should look at the resolved task params, identify which entries were materializations of local generations (mark them at creation time so cleanup knows), and clean each up. Don't touch generations that were natively remote.

## Detection of local worker

The localhost healthcheck endpoint and port: check existing reigh-worker server entrypoint (`reigh-worker/source/runtime/worker/server.py`) for the actual healthcheck route + port. If none exists, you'll need to add a tiny `/health` endpoint to the worker (returns 200 OK + JSON `{ok:true}`). Keep this minimal.

The app also needs to know which port to probe — read it from an env var (`VITE_LOCAL_WORKER_HEALTHCHECK_URL` or similar), default to a sensible value. Don't hard-code.

If the healthcheck fails (timeout, connection refused), fall back to remote behavior. Don't surface an error to the user — silent fallback is correct UX.

## Where to put the resolution layer

There's a unified task-creation path in `src/shared/lib/tasks/`. Look for the common entry point (probably a hook like `useCreateTask` or a shared `createTask` helper). The resolver should run there, immediately before the create-task edge function call. Sub-doc `unified_task_creation.md` is authoritative — read it first.

For tasks that build their own params (e.g. `src/shared/lib/tasks/travelBetweenImages/segmentImages.ts`, `src/shared/lib/tasks/imageEditing/buildMaskedEditTaskParams.ts`), the resolver needs a hook into each. Consider whether the resolver runs at the very end of param assembly (one place to plug in) or whether each task builder calls it explicitly. The first option is simpler and harder to forget.

## What NOT to do

- Do NOT make the worker do FileSystemFileHandle deserialization. Browser handles can't cross processes.
- Do NOT eagerly upload all local files at drop time. That defeats the point — only materialize on USE.
- Do NOT add a "this will be uploaded to cloud, OK?" prompt. The fallback should be silent. (We can add UX later if needed.)

# Implementation Plan: Local-Only Generations as Worker Task Inputs

## Overview

Today, `createTask.ts:193` calls `materializeTaskInputGenerations`, which uploads any local-mode generation referenced in task input to Supabase Storage and **permanently** converts the generation to remote (clears `local_handle_id`, `storage_mode → 'remote'`). The brief asks for a tiered, **non-destructive** resolution layer:

1. Local generation + local worker reachable → POST file bytes to the worker's `/ingest`, get back a path, expose as `file://` URL the worker consumes.
2. Local generation + no worker → upload bytes to Supabase Storage **temporarily** (preserving `storage_mode='local'`), pass URL through.
3. Either way: clean up the materialized artifact after task completion.

The resolver runs **per-input** in the existing single client entry point (`createTask`). Server-side family resolvers continue reading `generations.location`; we just ensure that location is populated (with the right kind of URL) before the edge call. Materialization records are written into a new `tasks.materialized_inputs` JSONB column so the `complete_task` handler can undo them.

**Critical scope note**: `reigh-worker/` lives in a separate repo. The `/health`, `/ingest`, and `/cleanup` HTTP endpoints required by this design are deliverables in that repo, not this one — this plan tracks them as a parallel work item but the code lives elsewhere. The browser **cannot** write to `~/.reigh-local-files/` directly (no general filesystem write API), so the worker must accept ingestion over HTTP.

> AGENT

I reviewed the plan against the actual codebase and flagged five concerns, two of them likely-significant:

- **FLAG-001 / FLAG-002 (correctness, significant)**: The plan's central premise — that updating `generations.location` lets server-side resolvers read the resolved URL — does not match how this codebase works. URLs (`image_url`, `mask_url`, `start_image_url`, `end_image_url`) are baked into `taskParams.input` by client callers from `getMediaUrl(media)` BEFORE `createTask` runs, and resolvers like `maskedEdit.ts` pass them straight through. For `storage_mode='local'`, `transformGeneration` returns `LOCAL_GENERATION_MEDIA_SENTINEL_URL`, so callers like `createInpaintingTaskWorkflow.ts` already throw "Missing source media URL" before `createTask` is even called. The resolver needs to either rewrite URL strings inside `taskParams.input` or hook into each task-builder upstream.
- **FLAG-003 (correctness, minor)**: Setting `location='file://...'` while keeping `storage_mode='local'` creates a hybrid state that bypasses `transformGeneration`'s sentinel gate but is invisible to the rest of the UI; raw `location` readers could misinterpret it.
- **FLAG-004 (correctness, minor)**: Cleanup race when two tasks share the same local generation — plan's idempotency cache is "should", not "must".
- **FLAG-005 (completeness, minor)**: CORS missing from the worker-repo contract for browser→localhost POSTs.
