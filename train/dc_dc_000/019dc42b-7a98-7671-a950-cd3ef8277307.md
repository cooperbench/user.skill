Short answer: **not reliably in the strongest sense**. DataClaw currently tracks a single session-level `model` field, not a per-message or per-turn model. That means it is good for “roughly what model was this session associated with,” but not guaranteed for “exactly which model powered every assistant response.” What I found: - Claude: reads the first assistant `message.model` it sees. Good if Claude logs include it, but ignores later model changes. [claude.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/claude.py:576>) - Codex: reads `payload.model` from `turn_context`; if absent, falls back to `model_provider-codex` or `codex-unknown`. This is the weakest for exact model identity if Codex logs only provider. [codex.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/codex.py:280>) - Gemini: reads the first `msg_data.model`. Same first-model limitation. [gemini.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/gemini.py:513>) - OpenCode: reads `providerID/modelID`, which is pretty solid if present. [opencode.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/opencode.py:288>) - Cursor: reads `modelInfo.modelName` if present. Good when Cursor stores it. [cursor.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/cursor.py:314>) - OpenClaw: handles explicit `model_change` entries and message model fallback, but still exports only one session-level model. [openclaw.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/openclaw.py:181>) - Custom: requires `model`, so it is only as accurate as the supplied data. [custom.py](</Users/user_c042661f/Documents/dataclaw/dataclaw/parsers/custom.py:134>) So: **we track source/harness reliably, and model decently when the harness logs it, but we do not currently track model provenance or model changes reliably.** The production-ready fix would be to add fields like: ```json { "model": "best session-level normalized model", "model_source": "codex.turn_context.model", "model_confidence": "exact", "model_observed_values": ["gpt-5.4", "gpt-5.5"], "messages": [ { "role": "assistant", "model": "gpt-5.4", "content": "..." } ] } ``` That would let the README/model breakdown still use a clean session-level model, while preserving exact per-turn evidence where available.
