## Overview

Three interconnected issues in the viewer editor need to be fixed together:

1. **Canvas overlay misalignment**: The drag/resize overlay box is offset from the actual rendered clip because the OverlayEditor receives full-resolution composition dimensions (1280x720) while the Remotion Player renders at `PREVIEW_SCALE = 0.5` (640x360). Clip coordinates (e.g., `x=100`) render at 100px in the 640-wide Remotion composition but the overlay projects them as `100 * (layoutWidth/1280)` — roughly half the correct position, causing the box to appear shifted toward top-left.

2. **Clip-level overrides ignored by track scale**: `TimelineRenderer.tsx:23` wraps each visual track in `transform: scale(trackScale)`, which applies even when clips have explicit `x/y/width/height` overrides. A clip positioned at `x=100` in composition space actually renders at `100 * trackScale` due to the parent transform.

3. **ClipPanel UI disorganized**: All settings are in a flat list without section groupings, headers, or collapsibility.

**Key constraint**: All three systems share coordinates — editing position in the panel, dragging on the canvas, and rendering in Remotion must all agree.

**Repository shape**: Viewer is in `viewer/src/`, shared Remotion compositions in `shared/compositions/`, shared types in `shared/types.ts`. Coordinates are stored in `timeline.json` in canonical composition space (1280x720).

## Step 1: Fix PREVIEW_SCALE coordinate mismatch (`viewer/src/RemotionPreview.tsx`, `viewer/src/App.tsx`, `viewer/src/OverlayEditor.tsx`)
**Scope:** Small — single constant change + prop threading

The root cause: `RemotionPreview.tsx:12` sets `PREVIEW_SCALE = 0.5`, making the Remotion composition 640x360. Clip coordinates in `timeline.json` are in canonical 1280x720 space. `VisualClip.tsx` applies `left: clip.x` directly in the reduced composition space, placing the clip at the wrong position. The overlay uses 1280 for its projection, creating a second mismatch.

**Approach**: Set `PREVIEW_SCALE = 1`. This makes the Remotion composition match canonical coordinate space (1280x720), so `left: clip.x` is correct. The Player handles CSS scaling to fit the container automatically. The overlay already receives `compositionSize.width` (1280) and projects correctly against the Player's DOM rect.

1. **Change** `PREVIEW_SCALE` from `0.5` to `1` in `RemotionPreview.tsx:12`.
2. **Verify** the overlay box now aligns with the rendered clip by opening the viewer, selecting a clip with position overrides (e.g., `clip-3` on V3 with `x:61, y:-59`), and confirming the drag box matches the visual.

**Risk**: Slightly heavier preview rendering. If preview performance degrades noticeably, the fallback is Step 1b (below).

### Step 1b (contingency): Scale-aware overlay instead of PREVIEW_SCALE=1

Only needed if preview performance is unacceptable with `PREVIEW_SCALE=1`:

## Step 2: Clip-level position overrides bypass track scale (`shared/compositions/TimelineRenderer.tsx`, `shared/compositions/VisualClip.tsx`)
**Scope:** Medium — rendering logic change in shared components

Currently `TimelineRenderer.tsx:23` applies `transform: scale(${track.scale ?? 1})` to the entire track `AbsoluteFill`. This scales ALL clips, even those with explicit position overrides. A clip at `x=100, width=400` with `trackScale=0.8` actually renders at 80px wide 320px — not what the user set.

**Approach**: When a clip has position overrides, counteract the track scale so its coordinates are in canonical composition space.

1. **In `VisualClip.tsx`**, modify `getClipBoxStyle` to accept the track scale and, when `hasPositionOverride` is true, divide coordinates by track scale to counteract the parent transform:
   ```typescript
   const trackScale = track.scale ?? 1;
   if (fit === "manual" || hasPositionOverride) {
     return {
       position: "absolute",
       left: (clip.x ?? 0) / trackScale,
       top: (clip.y ?? 0) / trackScale,
       width: (clip.width ?? 320) / trackScale,
       height: (clip.height ?? 240) / trackScale,
       objectFit: "cover",
       opacity: clip.opacity ?? 1,
     };
   }
   ```
   This counteracts the parent's `transform: scale(trackScale)` so net positioning matches canonical space.

2. **Verify** in the viewer: a clip with `x=100, width=500` on a track with `scale=0.8` should appear at exactly `x=100, width=500` in the composition, not scaled down.

3. **Verify** in Remotion Studio render: the same clip renders identically (Studio also uses the same `TimelineRenderer`).

## Step 3: Overlay projection must account for override-vs-inherited state (`viewer/src/OverlayEditor.tsx`)
**Scope:** Small — adjust overlay coordinate projection for overridden clips

After Step 2, overridden clips render in canonical composition space (their coordinates are effectively unscaled). But the overlay's `getTrackProjection` still multiplies by `trackScale`:

```typescript

```

For clips with position overrides, the overlay should project WITHOUT trackScale (since the clip already counteracts it in rendering).

1. **Modify** the overlay rendering loop (`OverlayEditor.tsx:303-311`) to compute projection per-clip:
   - If the clip has position overrides → use `trackScale=1` for projection (since the clip cancels out the track scale).
   - If the clip inherits track defaults → use the actual `trackScale`.

2. **Similarly update** drag delta conversion (`OverlayEditor.tsx:236-237`) to use the correct per-clip projection during drag.

   ```typescript
       position: "absolute",
       left: (clip.x ?? 0) / trackScale,
       top: (clip.y ?? 0) / trackScale,
       width: (clip.width ?? 320) / trackScale,
       height: (clip.height ?? 240) / trackScale,

       opacity: clip.opacity ?? 1,

   ```

2. **In `TextClip.tsx`**, apply the same compensation (`TextClip.tsx:20-38`). `TextClip` does not receive a `track` prop currently — it needs one. Thread it through:

     ```typescript
     const trackScale = track.scale ?? 1;
     ```
