- FULL ROOT CAUSE ANALYSIS:

The render storm is NOT from continuous polling (30s interval is fine). The issue is that when ANY data update happens (poll, realtime, or user edit), the entire chain creates new object references:

1. useTimelineQueries: refetchInterval 30s + realtime invalidation
2. usePollSync: creates new TimelineData object via buildTimelineData()
3. useTimelineCommit: setData(nextData) → new data reference
4. useDerivedTimeline: resolvedConfig = useMemo(() => data?.resolvedConfig, [data]) — busted every time data ref changes
5. RemotionPreview: receives new config ref → Remotion Player remounts/re-renders composition tree

But 50+/sec means it's not just the 30s poll. Something is causing data to change MUCH more frequently. Likely candidates:
- The Player's own frameupdate events propagating back through onTimeUpdate → state changes → re-renders
- Or some other state change in the parent that cascades

THE FIX (simplest, most targeted):
In useDerivedTimeline.ts:19, use a structural comparison to preserve the resolvedConfig reference when the content hasn't changed. TimelineData already has a `signature` and `stableSignature` field — use stableSignature as the memo key instead of the data object itself:

```ts
// BEFORE:
const resolvedConfig = useMemo(() => data?.resolvedConfig ?? null, [data]);

// AFTER:  
const resolvedConfig = useMemo(() => data?.resolvedConfig ?? null, [data?.stableSignature]);
```

This way, even if `data` gets a new reference, `resolvedConfig` stays the same as long as the content (stableSignature) hasn't changed.

Check what stableSignature includes — it should cover clips, tracks, output settings, and registry. If it does, this is the fix.
