## 改善提案

### 1. RepositoryをReader/Writerに分離する（前記事の処方箋3と直接対応）

前の記事では「Repositoryが太い」ことを問題として処方箋を提示していましたが、この記事の `domain/order/repository.go` は分離されていません。

**現在のコード:**
```go
type Repository interface {
    FindByID(ctx context.Context, id OrderID) (*Order, error)
    Save(ctx context.Context, order *Order) error
}
```

**前記事の原則を適用した改善案:**
```go
// domain/order/repository.go
type OrderReader interface {
    FindByID(ctx context.Context, id OrderID) (*Order, error)
}

type OrderWriter interface {
    Save(ctx context.Context, order *Order) error
}
```

するとUseCaseの依存が最小化されます:
- `PlaceOrderUseCase` → `OrderWriter` のみに依存（Findは不要）
- `CancelOrderUseCase` → `OrderReader` + `OrderWriter` に依存

これは「The bigger the interface, the weaker the abstraction」の実践例として、この記事のコードサンプル内で示せる機会です。

### ⚠️ 設計上の問題：`CodedError.Unwrap()` の意図が不明確

```go
func (e *CodedError) Unwrap() error {
    return e.sentinel
}
```

この `sentinel` は `errors.New(message)` で生成されており、`CodedError.Error()` と同じメッセージを持つ別のエラーオブジェクトです。つまり `Unwrap()` をたどると「同じメッセージの無名エラー」が出てきます。

これにより2つの問題が生じます。

1つ目は、`errors.Unwrap(err)` で取り出した値をログに出すと同じメッセージが重複して見えること。2つ目は、`HandleError` は `errors.As` で `*CodedError` を判定しているのに、なぜ `Unwrap()` が必要なのか記事中に説明がなく、読者が混乱します。`Unwrap()` を持たせる具体的なユースケースを示すか、不要なら削除すべきです。

と書かれていますが、`codes.go` で定義されているのは `ErrInvalidFormat` であり、`ErrInvalid` というシンボルはコード中に存在しません。前回の `ErrConflict` の修正と同様、表の変数名が実装と一致していない問題が残っています。

> DEVELOPER

## 問題の構造

「変換場所の判断基準」セクションは、本来2つのパターンを表で整理した上で、それぞれの ✅ コード例を並べるべきでした。しかし実際には：

- 表の1行目（Repository層で変換）→ コード例なし
- 表の2行目（Interactor層で変換）→ ✅ コード例あり

という非対称な構成になっており、「変換すべきでないケース」のコードが再掲されているだけで、セクション冒頭で推奨した「Repository層での変換」のコードが示されていません。

読者は「変換場所の判断基準」セクションの ✅ コードだけ読むと、「インフラ層は変換せずにラップして返すのが正しい」と理解してしまいます。記事全体の主張と正反対の印象を与えるため、このセクションには `FindByID` のような Repository層での変換例も ✅ として明示的に追加するのが適切です。

> DEVELOPER

## 矛盾の整理

**「教科書の主張と実務のギャップ」セクション**では、このパターンを「合理的」として推奨しています：

```go
// Repository層でgorm固有エラー → ドメインsentinel errorに変換
if errors.Is(result.Error, gorm.ErrRecordNotFound) {
    return nil, model.ErrTaskNotFound  // ← ドメインのsentinel error
}
```

**「変換場所の判断基準」セクション**の判断表には：

| 条件 | 変換場所 | 例 |
|---|---|---|
| エラーの意味が1対1で対応する | **Repository層** | 「レコードなし」→「タスクが見つからない」 |

と書かれているので、ここまでは一貫しています。

ところが、その直後に示されている ✅ コード例は：

```go
// ✅ インフラ層は事実を返す（変換しない）
return fmt.Errorf("failed to save user: %w", result.Error)

// ✅ Interactor層でビジネス判断する
if isDuplicateKeyError(err) {
    return apperror.ErrDuplicateEntry
}
```

これは「**インフラ層は変換せず、Interactorで判断する**」パターンのコードであり、判断表の1行目（Repository層で変換）とは**逆のパターン**のコードです。

### ⚠️ 軽微：`errors.As` と `*CodedError` のポインタ設計の注意点

`Unwrap()` を削除したことで `CodedError` はシンプルになりましたが、`codes.go` の定義が：

```go
var ErrNotFound = newCodedError("RES001", ...)  // *CodedError
```

という**ポインタ型の package-level 変数**になっています。`HandleError` では：

```go
var coded *apperror.CodedError
errors.As(err, &coded)
```

と「型」で判定しているため、`ErrNotFound` でも `ErrInvalidFormat` でも同じく `*CodedError` として一致します。これは意図通りの設計ですが、記事を読んだ読者が `errors.Is(err, apperror.ErrNotFound)` のような「値」での判定を試みると動作しない（`fmt.Errorf("%w", apperror.ErrNotFound)` でラップした場合など）ため、一言補足があると親切です。

> DEVELOPER

### ⚠️ 残っている問題：「エラーの流れ全体像」の表の内容が確認できない

# ドキュメントレビュー

引数で指定された Markdown 記事ファイルの文章品質をレビューし、問題を指摘したうえで自動修正する。

## 入力

 に対象ファイルのパスが渡される（例: `articles/978121945958ed.md`）。パスが渡されない場合は「対象ファイルを指定してください（例: /review-doc articles/xxx.md）」とだけ返して終了すること。

## レビュー手順

### Step 1: 記事を読み込む

対象ファイルを Read ツールで全文読み込むこと。

### Step 2: 以下の 4 観点でレビューする

#### 観点 A: 冗長・繰り返し

- 同じ主張が複数箇所で繰り返されていないか
- 削れる前置き・つなぎ表現はないか（「〜がある。それは〜である。」のような回りくどい表現）
- 1 文が長すぎないか（目安: 80 文字超は分割を検討）

#### 観点 B: 論理構成・流れ

- セクション間の論理的なつながりが自然か
- 見出し階層が適切か（h2 → h3 の飛び越しがないか）
- 結論が導入の問いに対応しているか

#### 観点 C: 読者価値密度

- 各セクションに具体例・数値・コード例など「読んで良かった」と思える情報があるか
- 抽象的な主張だけで終わっているセクションはないか
- 読者が次のアクションを取れる情報が含まれているか

#### 観点 D: 文体の統一

- 記事全体が敬語（ですます調）で統一されているか
- 箇条書き内で「である」調が混在していないか
- 見出し直下の地の文とリスト項目で文体が揺れていないか

### Step 3: 指摘を出力する

以下のフォーマットで指摘を一覧表示すること。

```markdown
## レビュー結果: <ファイル名>

### 観点 A: 冗長・繰り返し

- [ ] L<行番号>: <指摘内容>（<改善案の要約>）

### 観点 B: 論理構成・流れ

- [ ] L<行番号>: <指摘内容>（<改善案の要約>）

### 観点 C: 読者価値密度

- [ ] L<行番号>: <指摘内容>（<改善案の要約>）

### 観点 D: 文体の統一

- [ ] L<行番号>: <指摘内容>（<改善案の要約>）

### 総評

<全体の品質に関する 2〜3 行のコメント>
```

指摘がない観点は「問題なし」とだけ記載すること。

### Step 4: 自動修正を適用する

指摘のうち、意味を変えずに改善できるもの（冗長表現の削除、文の分割など）は Edit ツールで自動修正すること。修正を適用したら、修正箇所のサマリーを出力すること。

内容の追加や構成の大幅な変更が必要な指摘は、修正案を提示するにとどめ、自動修正しないこと。

### Step 5: lint を実行する

修正後に以下を順に実行し、エラーがあれば修正すること。

```bash
npx prettier --write <対象ファイル>
npx markdownlint-cli2 <対象ファイル>
npx textlint <対象ファイル>
```

## 制約

- フロントマター（title, emoji, topics, published など）は変更しないこと
- 技術用語・固有名詞はそのまま残すこと
- 修正は最小限にとどめ、筆者の文体を尊重すること
- published の値は変更しないこと

## 前提：Go の interface に関する思想

まず根拠となる一次情報源を整理します。

### Rob Pike（Go の作者）

> The bigger the interface, the weaker the abstraction.
>
> — [Go Proverbs](https://go-proverbs.github.io/)

interfaceが大きいほど、抽象化としての力は弱くなるという原則です。

### Go 標準ライブラリの実態

Go 標準ライブラリに含まれるinterfaceの大半が1〜2メソッドです。

| interface | メソッド数 | パッケージ |
|-----------|-----------|-----------|
| `io.Reader` | 1 | io |
| `io.Writer` | 1 | io |
| `fmt.Stringer` | 1 | fmt |
| `error` | 1 | builtin |
| `sort.Interface` | 3 | sort |
| `http.Handler` | 1 | net/http |

これは偶然ではなく、設計原則です。

### Jack Lindamood の記事（Go コミュニティで広く参照される）

> Accept interfaces, return structs.

interfaceは**利用側が定義する**もので、提供側が事前に定義するものではないという考え方です。

出典: [Preemptive Interface Anti-Pattern in Go](https://medium.com/@cep21/preemptive-interface-anti-pattern-in-go-54c18ac0668a)

### Go 公式 Wiki

> Interfaces in Go are different from, say, Java: in Go, you don't explicitly declare that a type implements an interface. Instead, a type implicitly satisfies an interface if it possesses the necessary methods.

> Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values.

出典: [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments#interfaces)

## 現在のプロジェクトの分析

上記を踏まえて、プロジェクトを3つの観点で分析します。

### 観点1：Input Port は「本当に必要か」

現在の構成:

```go
// usecase/port/input/analysis_input_port.go
type AnalyzeSecurityInputPort interface {
    AnalyzeSecurity(ctx context.Context, input *AnalyzeConversationInput) (*SecurityAnalysisOutput, error)
}
```

これを実装するのは `analyzeSecurityInteractor` の1つだけです。そしてこのinterfaceを使うのは Handler と、`analyzeConversationInteractor` です。

**Go の思想に従うなら：**

Input Port interface は**利用側**（Handler や他の Interactor）が定義するべきです。`usecase/port/input/` という専用ディレクトリは不要になります。

```go
// interface/rest/handler/analysis_handler.go
// Handler が必要な分だけ定義
type securityAnalyzer interface {
    AnalyzeSecurity(ctx context.Context, input *usecase.AnalyzeConversationInput) (*usecase.SecurityAnalysisOutput, error)
}

type AnalysisHandler struct {
    analyzer securityAnalyzer  // interface
}
```

```go
// usecase/analyze_conversation_interactor.go
// 別の Interactor が必要な分だけ定義
type securityAnalyzer interface {
    AnalyzeSecurity(ctx context.Context, input *AnalyzeConversationInput) (*SecurityAnalysisOutput, error)
}

type analyzeConversationInteractor struct {
    securityAnalyzer securityAnalyzer
}
```

`analyzeSecurityInteractor` は struct のまま。どちらの interface も暗黙的に満たします。

**メリット：**
- `usecase/port/input/` ディレクトリが不要になる
- 各利用者が本当に必要なメソッドだけに依存する
- Interactor の追加時に interface ファイルを編集する必要がない

**ただし注意点があります。** DI コンテナ（`uber-go/dig`）で `dig.As(new(InputPort))` のように interface 型で登録している場合、この変更は DI の設計にも影響します。段階的な移行が必要です。

### 観点2：Output Port は「残すべき」

一方、Output Port は Go の思想に従っても**残す価値があります**。

```go
// usecase/port/output/llm_port.go
type LLMRiskAnalyzerPort interface {
    AnalyzeRisk(ctx context.Context, conversation string) (*RiskAnalysisResult, error)
}
```

理由は明確です。Output Port は**実装が差し替わる可能性が高い**からです。実際にプロジェクトでキーワードマッチングからLLMベースの分類に移行した実績があります。

Go の「Accept interfaces, return structs」の原則は、**テストやモックのためだけに interface を作るな**という意味であり、**実際に複数の実装が存在する**場合は interface を定義する正当な理由があります。

ただし、配置場所は議論の余地があります。Go の思想に厳密に従うなら、Output Port も利用側（Interactor）で定義すべきです。しかし、Output Port は**複数の Interactor から共有される**ことが多く、共有 interface を1箇所で定義する方が重複を避けられます。これは実用上のトレードオフです。

### 観点3：Repository interface は「domain に残すべき」

Repository interface は現在 `domain/repository/` に配置されています。これは Go の思想とは異なりますが、**DDD の原則としては正しい**配置です。

```go
// domain/repository/analysis_result_repository.go
type AnalysisResultRepository interface {
    FindByConversationID(ctx context.Context, id string) (*model.AnalysisResult, error)
    FindAll(ctx context.Context, filter *model.AnalysisFilter) ([]*model.AnalysisResult, int64, error)
    Save(ctx context.Context, result *model.AnalysisResult) error
    GetStatistics(ctx context.Context, filter *model.StatisticsFilter) (*model.AnalysisStatistics, error)
}
```

メソッド数は4〜8個と、Go 標準の interface より大きいです。しかし、Repository は**集約のライフサイクル管理**という1つの責務に集中しており、メソッドが多くても凝集度は高いです。

**改善の余地があるとすれば**、Query 系と Command 系の分離です。

```go
// 書き込み（Command）
type AnalysisResultWriter interface {
    Save(ctx context.Context, result *model.AnalysisResult) error
}

// 読み取り（Query）
type AnalysisResultReader interface {
    FindByConversationID(ctx context.Context, id string) (*model.AnalysisResult, error)
    FindAll(ctx context.Context, filter *model.AnalysisFilter) ([]*model.AnalysisResult, int64, error)
    GetStatistics(ctx context.Context, filter *model.StatisticsFilter) (*model.AnalysisStatistics, error)
}

// 両方必要な場合は合成
type AnalysisResultRepository interface {
    AnalysisResultWriter
    AnalysisResultReader
}
```

これにより、読み取りしか行わない Interactor は `AnalysisResultReader` だけに依存できます。既存の CQRS 記事で書かれた考え方と一致します。

## 改善の優先順位

| 優先度 | 改善内容 | 理由 |
|--------|---------|------|
| 高 | Input Port を廃止し、利用側で interface を定義する | Go の思想に最も反している部分。効果が大きい |
| 中 | Repository を Reader / Writer に分離する | CQRS との整合性。段階的に実施可能 |
| 低 | Output Port の配置場所を検討する | 現状でも機能している。実装差し替えの実績もある |

**全部を一度に変える必要はありません。** 最もインパクトが大きいのは Input Port の廃止です。ここを変えるだけで、Go の「Accept interfaces, return structs」の恩恵を受けられます。

```go
type Repository interface {
```

**前記事の原則を適用した改善案:**
```go
// domain/order/repository.go
type OrderReader interface {
    FindByID(ctx context.Context, id OrderID) (*Order, error)
}

type OrderWriter interface {
    Save(ctx context.Context, order *Order) error
}
```

# Smart Commit with Gitmoji

Execute the following steps non-interactively:

## Branch Management

- If currently on `main` or `master` branch, create and checkout a new feature branch with a descriptive name
- If on any other branch, proceed with commit on current branch (no branch creation)
- If no changes are detected, exit without doing anything

## Change Analysis & Commit

1. **Review all changes** using `git status` and `git diff --staged` (or `git diff` if nothing staged)
2. **Stage changes** if not already staged using `git add .` or selective staging
3. **Analyze the changes** to understand:
   - Type of changes (new feature, bug fix, refactor, etc.)
   - Scope of changes (which files/components affected)
   - Impact and purpose of the changes

## Commit Message Creation

```
<gitmoji> <type>: <concise description>

<optional detailed explanation if needed>
```

- **Body**: Explain "what" and "why", not "how"

### 1. 依存性逆転の原則を破っている（最も根本的な批判）

```
// infrastructure/postgres/job_repository.go
return nil, model.ErrTaskNotFound  // ← Infra層がDomain層に依存している
```

依存の方向は `Infrastructure → Domain` になっており、これはクリーンアーキテクチャの依存方向として一見正しく見えます。しかし問題は**ドメイン層のエラー定義の変更がインフラ層に波及する**ことです。`model.ErrTaskNotFound` をリネームしたり削除したりすると、インフラ層のコードも変更が必要になります。

### 2. 「見つからない」が本当にドメインの概念かは文脈次第

**「見つからない」はアプリケーション層の関心事ではないか？**

- ドメインモデル自体は「自分が存在するか否か」を知らない。エンティティは存在しているときにしかインスタンス化されない
- 「存在しないIDで検索したとき何を返すか」はリポジトリの利用者（Interactor）が決めることであり、DBの制約をドメインエラーに変換する判断はInteractor層が持つべきという考え方もある

実際、DDDの文脈では `Repository` が `null` や `Option` 型を返し、Interactorが「見つからなかった場合」の処理を決めるパターンも一般的です。

### ⚠️ 設計上の問題：`CodedError.Unwrap()` の意図が不明確

```go
func (e *CodedError) Unwrap() error {
    return e.sentinel
}
```

この `sentinel` は `errors.New(message)` で生成されており、`CodedError.Error()` と同じメッセージを持つ別のエラーオブジェクトです。つまり `Unwrap()` をたどると「同じメッセージの無名エラー」が出てきます。

### ⚠️ 軽微：`errors.As` と `*CodedError` のポインタ設計の注意点

`Unwrap()` を削除したことで `CodedError` はシンプルになりましたが、`codes.go` の定義が：

```go
var ErrNotFound = newCodedError("RES001", ...)  // *CodedError
```

という**ポインタ型の package-level 変数**になっています。`HandleError` では：

```go
var coded *apperror.CodedError
errors.As(err, &coded)
```

と「型」で判定しているため、`ErrNotFound` でも `ErrInvalidFormat` でも同じく `*CodedError` として一致します。これは意図通りの設計ですが、記事を読んだ読者が `errors.Is(err, apperror.ErrNotFound)` のような「値」での判定を試みると動作しない（`fmt.Errorf("%w", apperror.ErrNotFound)` でラップした場合など）ため、一言補足があると親切です。

# Smart Commit with Gitmoji

Execute the following steps non-interactively:

## Branch Management

- If currently on `main` or `master` branch, create and checkout a new feature branch with a descriptive name
- If on any other branch, proceed with commit on current branch (no branch creation)
- If no changes are detected, exit without doing anything

## Change Analysis & Commit

1. **Review all changes** using `git status` and `git diff --staged` (or `git diff` if nothing staged)
2. **Stage changes** if not already staged using `git add .` or selective staging
3. **Analyze the changes** to understand:
   - Type of changes (new feature, bug fix, refactor, etc.)
   - Scope of changes (which files/components affected)
   - Impact and purpose of the changes

## Commit Message Creation

Create a commit message following this format:

```
<gitmoji> <type>: <concise description>

<optional detailed explanation if needed>
```

### Gitmoji Selection Guide

Choose the most appropriate gitmoji from <https://gitmoji.dev/> based on change type:

**Common Patterns:**

- ✨ `:sparkles:` - New features
- 🐛 `:bug:` - Bug fixes
- 🎨 `:art:` - Code structure/format improvements
- ⚡️ `:zap:` - Performance improvements
- 📝 `:memo:` - Documentation updates
