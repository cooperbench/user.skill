    17→# CQRSとは何か（1分でおさらい）
    18→
    19→**Command Query Responsibility Segregation（コマンドクエリ責務分離）**
    20→
    21→| 種別 | 役割 | 状態変化 |
    22→|------|------|---------|
    23→| Command | データを変更する処理 | あり |
    24→| Query | データを読み取る処理 | なし |
    25→
    26→この2つの経路を**明確に分離する**アーキテクチャパターンです。
    27→
    28→---
    29→
    30→# 誤解1：「CQRSを導入するとユースケースがなくなる」
    31→
    32→## ❌ よくある誤解
    33→
    34→```
    35→CQRSを入れる
    36→  → ユースケースをCommandとQueryに置き換える
    37→  → UseCaseクラスは不要になる
    38→```
    39→
    40→## ✅ 正しい理解
    41→
    42→**ユースケースという概念はなくならない。**
    43→ユースケースを「書き込み系（Command）」か「読み込み系（Query）」かに**振り分けるだけ**です。
    44→
    45→```
    46→業務要件（ユースケース）
    47→        ↓ 分類する
    48→
    49→  データを変える？
    50→  ┌──────┴──────┐
    51→  Yes            No
    52→  ↓              ↓
    53→Command        Query
    54→（注文する）   （注文一覧を見る）
    55→```
    56→
    57→ユースケースが先にあって、CQRSはその**実装方針の話**です。

   109→# 誤解3：「Query側もRepositoryを使う」
   110→
   111→## ❌ よくある実装
   112→
   113→```typescript
   114→// QueryでもRepositoryを使って集約を取得し、DTOに詰め替える
   115→class GetOrderListUseCase {
   116→  execute(): OrderListDTO[] {
   117→    const orders = this.orderRepository.findAll() // ← 集約を全件取得
   118→    return orders.map(order => ({                  // ← DTOに詰め替え
   119→      orderId: order.id.value,
   120→      customerName: ???, // ← 別集約の情報が取れない...
   121→      totalAmount: order.totalAmount,
   122→    }))
   123→  }
   124→}
   125→```
   126→
   127→これではN+1問題が起きたり、集約の境界をまたいだデータが取れなかったりします。
   128→
   129→## ✅ CQRSの正しいアプローチ
   130→
   131→**Repository（集約を返す）** と **QueryService（DTOを返す）** を使い分ける。
   132→
   133→```typescript
   134→// ✅ Command側：Repositoryを使う（従来通り）
   135→class PlaceOrderUseCase {
   136→  execute(command: PlaceOrderInput): void {
   137→    const order = Order.place(command.items, command.customerId)
   138→    this.orderRepository.save(order) // ← 集約の永続化
   139→  }
   140→}
   141→
   142→// ✅ Query側：QueryServiceを使う（CQRSの新しいやり方）
   143→class GetOrderListUseCase {
   144→  execute(): OrderListDTO[] {
   145→    return this.orderQueryService.findAll() // ← DTOを直接返す
   146→  }
   147→}
   148→```
   149→
   150→| | Repository | QueryService |
   151→|--|------------|-------------|
   152→| 返すもの | 集約（DomainModel） | DTO（画面用データ） |
   153→| 役割 | 集約の保存・復元 | 画面に必要な形でデータ取得 |
   154→| JOINの制約 | 集約の境界を守る | 自由にJOINしてOK |
   155→| DDDの制約 | 受ける | 受けない |

   159→# 誤解4：「QueryServiceはインフラ層に置く」
   160→
   161→## ❌ よくある誤解
   162→
   163→```
   164→QueryServiceはSQLを書くのでインフラ層に置く
   165→  → アプリケーション層からインフラ層を直接参照する
   166→  → 依存関係が壊れる 🚨
   167→```
   168→
   169→## ✅ 正しい理解
   170→
   171→**RepositoryパターンとまったくなるRuleです。**
   172→
   173→```
   174→【Repository】                    【QueryService】
   175→
   176→application/                      application/
   177→└── IOrderRepository.ts           └── IOrderQueryService.ts
   178→      （インターフェース）                （インターフェース定義）
   179→
   180→infrastructure/                   infrastructure/
   181→└── MySQLOrderRepository.ts       └── MySQLOrderQueryService.ts
   182→      （実装：SQLを書く）                （実装：SQLを書く）
   183→```
   184→
   185→インターフェースはアプリケーション層に、実装はインフラ層に。**SQLを書くクラスは必ずインフラ層**です。
   186→
   187→```typescript
   188→// ✅ application層：インターフェースを定義（SQLは知らない）
   189→interface IOrderQueryService {
   190→  findAll(): OrderListDTO[]
   191→  findById(id: string): OrderDetailDTO | null
   192→}
   193→
   194→// ✅ application層：インターフェースにだけ依存
   195→class GetOrderListUseCase {
   196→  constructor(
   197→    private queryService: IOrderQueryService // ← インターフェース
   198→  ) {}
   199→
   200→  execute(): OrderListDTO[] {
   201→    return this.queryService.findAll()
   202→  }
   203→}
   204→
   205→// ✅ infrastructure層：SQLの詳細はここだけ
   206→class MySQLOrderQueryService implements IOrderQueryService {
   207→  findAll(): OrderListDTO[] {
   208→    return this.db.query(`
   209→      SELECT o.id, c.name as customer_name, o.total, COUNT(i.id) as item_count
   210→      FROM orders o
   211→      JOIN customers c ON o.customer_id = c.id
   212→      JOIN order_items i ON o.id = i.order_id
   213→      GROUP BY o.id, c.name, o.total
   214→    `)
   215→  }
   216→}
   217→```

   221→# 誤解5：「依存の方向はHandler→UseCase→Domain→Infraの一方向」
   222→
   223→## ❌ よくある誤解
   224→
   225→```
   226→Handler → UseCase → Domain → Infrastructure（一方向に依存）
   227→```
   228→
   229→## ✅ 正しい理解
   230→
   231→**「呼び出しの流れ」と「依存の方向」は別物**です。
   232→
   233→```
   234→【呼び出しの流れ】（あなたの理解は正しい！）
   235→Handler → UseCase → Domain → Infrastructure
   236→
   237→【依存の方向】（Infraだけ逆転する）
   238→Handler → UseCase → Domain ← Infrastructure
   239→                      ↑
   240→               インターフェースを定義
   241→               Infrastructureが実装（依存性逆転）
   242→```
   243→
   244→この仕組みによって「MySQLをPostgreSQLに変えても、Domainは一切変更不要」という状態が実現できます。

   282→# コードサンプル全体像
   283→
   284→## Domain層
   285→
   286→```typescript
   287→// domain/order/Order.ts（集約ルート）
   288→export class Order {
   289→  private constructor(
   290→    public readonly id: OrderId,
   291→    private customerId: CustomerId,
   292→    private items: OrderItem[],
   293→    private status: OrderStatus,
   294→  ) {}
   295→
   296→  static place(customerId: CustomerId, items: OrderItem[]): Order {
   297→    if (items.length === 0) {
   298→      throw new Error('注文には1つ以上の商品が必要です')
   299→    }
   300→    return new Order(OrderId.generate(), customerId, items, OrderStatus.PENDING)
   301→  }
   302→
   303→  cancel(): void {
   304→    if (this.status !== OrderStatus.PENDING) {
   305→      throw new Error('この注文はキャンセルできません')
   306→    }
   307→    this.status = OrderStatus.CANCELLED
   308→  }
   309→}
   310→
   311→// domain/order/IOrderRepository.ts（インターフェース）
   312→export interface IOrderRepository {
   313→  findById(id: OrderId): Promise<Order | null>
   314→  save(order: Order): Promise<void>
   315→}
   316→```
   317→
   318→## Application層
   319→
   320→```typescript
   321→// application/query-services/IOrderQueryService.ts（インターフェース）
   322→export interface IOrderQueryService {
   323→  findAll(): Promise<OrderListDTO[]>
   324→  findById(id: string): Promise<OrderDetailDTO | null>
   325→}
   326→
   327→export type OrderListDTO = {
   328→  orderId: string
   329→  customerName: string
   330→  totalAmount: number
   331→  itemCount: number
   332→  status: string
   333→  createdAt: Date
   334→}
   335→
   336→// application/usecases/PlaceOrderUseCase.ts（Command系）
   337→export class PlaceOrderUseCase {
   338→  constructor(
   339→    private readonly orderRepository: IOrderRepository // ← Domain I/Fに依存
   340→  ) {}
   341→
   342→  async execute(input: PlaceOrderInput): Promise<void> {
   343→    const order = Order.place(
   344→      new CustomerId(input.customerId),
   345→      input.items.map(i => new OrderItem(i.productId, i.quantity, i.price))
   346→    )
   347→    await this.orderRepository.save(order)
   348→  }
   349→}
   350→
   351→// application/usecases/GetOrderListUseCase.ts（Query系）
   352→export class GetOrderListUseCase {
   353→  constructor(
   354→    private readonly queryService: IOrderQueryService // ← Application I/Fに依存
   355→  ) {}
   356→
   357→  async execute(): Promise<OrderListDTO[]> {
   358→    // DomainModelを経由しない！
   359→    return this.queryService.findAll()
   360→  }
   361→}
   362→```
   363→
   364→## Infrastructure層
   365→
   366→```typescript
   367→// infrastructure/repositories/MySQLOrderRepository.ts
   368→export class MySQLOrderRepository implements IOrderRepository {
   369→  async findById(id: OrderId): Promise<Order | null> {
   370→    const row = await this.db.query(
   371→      'SELECT * FROM orders WHERE id = ?', [id.value]
   372→    )
   373→    if (!row) return null
   374→    return this.reconstruct(row) // ← 集約として復元
   375→  }
   376→
   377→  async save(order: Order): Promise<void> {
   378→    await this.db.query(
   379→      'INSERT INTO orders ...' // ← 集約の永続化
   380→    )
   381→  }
   382→}
   383→
   384→// infrastructure/query-services/MySQLOrderQueryService.ts
   385→export class MySQLOrderQueryService implements IOrderQueryService {
   386→  async findAll(): Promise<OrderListDTO[]> {
   387→    // 自由にJOINしてDTOを直接返す！集約の制約を受けない
   388→    const rows = await this.db.query(`
   389→      SELECT
   390→        o.id as orderId,
   391→        c.name as customerName,
   392→        o.total_amount as totalAmount,
   393→        COUNT(i.id) as itemCount,
   394→        o.status,
   395→        o.created_at as createdAt
   396→      FROM orders o
   397→      JOIN customers c ON o.customer_id = c.id
   398→      JOIN order_items i ON o.id = i.order_id
   399→      GROUP BY o.id, c.name, o.total_amount, o.status, o.created_at
   400→    `)
   401→    return rows
   402→  }
   403→}
   404→```

   408→# 依存関係のまとめ図
   409→
   410→```
   411→Presentation
   412→    ↓ 依存
   413→Application（UseCase + I/F定義）
   414→    ↓ 依存（Command系のみ）
   415→Domain（集約 + Repository I/F）
   416→    ↑ 依存（implements）
   417→Infrastructure（Repository実装 + QueryService実装）
   418→```
   419→
   420→**ポイント：インフラ層だけが上位層のインターフェースを実装する（依存性逆転）**
   421→

   423→
   424→# 段階的な導入推奨
   425→
   426→一気に全部やらず、スモールスタートが鍵です。
   427→
   428→```
   429→Step 1: UseCaseをCommand系・Query系に分類するだけ
   430→        → コード変更なし、意識だけ変える
   431→
   432→Step 2: Query側でRepositoryを使わず、QueryServiceを導入
   433→        → DBは共通、Event Sourcingなし
   434→
   435→Step 3: 必要になったらReadモデル用DBを分離（オプション）
   436→        → パフォーマンス要件が出てきたとき
   437→```

   441→# まとめ
   442→
   443→| 誤解 | 正しい理解 |
   444→|------|-----------|
   445→| ユースケースがなくなる | ユースケースの概念は残る。Command/Queryに分類するだけ |
   446→| 名前をCommand/Queryに変える必要がある | チームで統一すればどちらでもOK。混在がNG |
   447→| Query側もRepositoryを使う | QueryServiceを使い、DTOを直接返す |
   448→| QueryServiceはインフラ層に置く | I/Fはアプリケーション層、実装がインフラ層 |
   449→| 依存は全て一方向 | 呼び出しと依存の向きは別。Infraだけ依存が逆転する |
   450→
   451→**「DB分離」や「Event Sourcing」をセットにしない軽量CQRSから始めると、むしろ「どこに何を書くか」のルールが明確になり、チームの混乱が減ります。**

|\n|------|------|---------|\n| Command | データを変更する処理 | あり |\n| Query | データを読み取る処理 | なし |\n\nこの2つの経路を**明確に分離する**アーキテクチャパターンです。\n\n---\n\n# 誤解1：「CQRSを導入するとユースケースがなくなる」\n\n## ❌ よくある誤解\n\n```\nCQRSを入れる\n  → ユースケースをCommandとQueryに置き換える\n  → UseCaseクラスは不要になる\n```\n\n## ✅ 正しい理解\n\n**ユースケースという概念はなくならない。**\nユースケースを「書き込み系（Command）」か「読み込み系（Query）」かに**振り分けるだけ**です。\n\n```\n業務要件（ユースケース）\n        ↓ 分類する\n\n  データを変える？\n  ┌──────┴──────┐\n  Yes            No\n  ↓              ↓\nCommand        Query\n（注文する）   （注文一覧を見る）\n```\n\nユースケースが先にあって、CQRSはその**実装方針の話**です。\n\n---\n\n# 誤解2：「ユースケースの名前をCommand/Queryに変える必要がある」\n\n## ❌ よくある誤解\n\n```\nPlaceOrderUseCase.ts → PlaceOrderCommand.ts に名前を変える\nGetOrderListUseCase.ts → GetOrderListQuery.ts に名前を変える\n```\n\n## ✅ return this.orderQueryService.findAll()\n  }\n}\n```\n\n**重要なのは、チームで命名規則を統一すること。**\n混在が一番の混乱を生みます。\n\n```\n❌ 混在している状態（最悪）\n├── PlaceOrderUseCase.ts   // なんでUseCaseなの？\n├── CancelOrderCommand.ts  // PlaceOrderUseCase {\n  execute(command: PlaceOrderInput): void {\n    const order = Order.place(command.items, command.customerId)\n    this.orderRepository.save(order) // ← 集約の永続化\n  }\n}\n\n// ✅ 誤解4：「QueryServiceはインフラ層に置く」\n\n## ❌ よくある誤解\n\n```\nQueryServiceはSQLを書くのでインフラ層に置く\n  → アプリケーション層からインフラ層を直接参照する\n  → 依存関係が壊れる 🚨\n```\n\n## ✅ IOrderQueryService.ts\n      （インターフェース）                （インターフェース定義）\n\ninfrastructure/                   infrastructure/\n└── MySQLOrderRepository.ts       └── MySQLOrderQueryService.ts\n IOrderQueryService {\n  findAll(): OrderListDTO[] {\n    return this.db.query(`\n      SELECT o.id, c.name as customer_name, o.total, COUNT(i.id) as item_count\n      FROM orders o\n      JOIN 誤解5：「依存の方向はHandler→UseCase→Domain→Infraの一方向」\n\n## ❌ よくある誤解\n\n```\nHandler → UseCase → Domain → Infrastructure（一方向に依存）\n```\n\n## ✅     17→# CQRSとは何か（1分でおさらい）
    18→
    19→**Command Query Responsibility Segregation（コマンドクエリ責務分離）**
    20→
    21→| 種別    | 役割                 | 状態変化 |
    22→| ------- | -------------------- | -------- |
    23→| Command | データを変更する処理 | あり     |
    24→| Query   | データを読み取る処理 | なし     |

    26→この2つの経路を**明確に分離する**アーキテクチャパターンです。

    32→## ❌ よくある誤解
    33→

    41→

    45→業務要件（ユースケース）
    46→        ↓ 分類する
    47→
    48→  データを変える？
    49→  ┌──────┴──────┐
    50→  Yes            No
    51→  ↓              ↓
    52→Command        Query
    53→（注文する）   （注文一覧を見る）

   141→class GetOrderListUseCase {

   144→  }

    22→# CQRSとは何か（1分でおさらい）
    23→
    24→**Command Query Responsibility Segregation（コマンドクエリ責務分離）**
    25→
    26→> CQRSの核心は「情報を更新するモデルと、情報を読み取るモデルを分けられる」という考え方です。
    27→> ただし、**多くのシステムでCQRSは不必要なリスクと複雑性を加える**ことにも注意が必要です。
    28→>
    29→> — Martin Fowler, [CQRS](https://martinfowler.com/bliki/CQRS.html)
    30→
    31→| 種別 | 役割 | 状態変化 |
    32→|------|------|---------|
    33→| Command | データを変更する処理 | あり |
    34→| Query | データを読み取る処理 | なし |
    35→
    36→この2つの経路を**明確に分離する**アーキテクチャパターンです。
    37→
    38→:::message alert
    39→CQRSはすべてのシステムに適用すべきパターンではありません。
    40→Martin Fowlerも「複雑なドメインを持つ一部の状況でのみ有効」と述べています。
    41→小規模なCRUDアプリケーションへの導入は、逆に複雑性を高める可能性があります。
    42→:::
    43→
    44→---
    45→
    46→# CQRSのルーツ：CQS原則
    47→
    48→CQRSはBertrand Meyerが提唱した**CQS（Command Query Separation）原則**をアーキテクチャレベルに昇華させたものです。
    49→
    50→> CQSの基本的な考え方は、オブジェクトのメソッドを2つのカテゴリに明確に分類することです。
    51→> - **Query**：結果を返し、システムの状態を変更しない（副作用なし）
    52→> - **Command**：システムの状態を変更するが、値を返さない
    53→>
    54→> — Martin Fowler, [CommandQuerySeparation](https://martinfowler.com/bliki/CommandQuerySeparation.html)
    55→
    56→---
    57→
    58→# 誤解1：「CQRSを導入するとユースケースがなくなる」
    59→
    60→## ❌ よくある誤解
    61→
    62→```
    63→CQRSを入れる
    64→  → ユースケースをCommandとQueryに置き換える
    65→  → UseCaseクラスは不要になる
    66→```
    67→
    68→## ✅ 正しい理解
    69→
    70→**ユースケースという概念はなくならない。**
    71→ユースケースを「書き込み系（Command）」か「読み込み系（Query）」かに**振り分けるだけ**です。
    72→
    73→```
    74→業務要件（ユースケース）
    75→        ↓ 分類する
    76→
    77→  データを変える？
    78→  ┌──────┴──────┐
    79→  Yes            No
    80→  ↓              ↓
    81→Command        Query
    82→（注文する）   （注文一覧を見る）
    83→```
    84→
    85→ユースケースが先にあって、CQRSはその**実装方針の話**です。
    86→

    89→# 誤解2：「ユースケースの名前をCommand/Queryに変える必要がある」
    90→
    91→## ❌ よくある誤解
    92→
    93→```
    94→PlaceOrderUseCase.ts → PlaceOrderCommand.ts に名前を変える
    95→GetOrderListUseCase.ts → GetOrderListQuery.ts に名前を変える
    96→```
    97→
    98→## ✅ 正しい理解
    99→
   100→名前はどちらでも問題ありません。**本質は名前ではなく、中の実装ルール**です。
   101→
   102→```typescript
   103→// 名前はUseCaseのままでもCQRSとして正しい
   104→class GetOrderListUseCase {
   105→  execute(): OrderListDTO[] {
   106→    // ← Domainモデルを経由しない（Query的な実装）
   107→    return this.orderQueryService.findAll()
   108→  }
   109→}
   110→```
   111→
   112→**重要なのは、チームで命名規則を統一すること。**
   113→混在が一番の混乱を生みます。
   114→
   115→```
   116→❌ 混在している状態（最悪）
   117→├── PlaceOrderUseCase.ts   // なんでUseCaseなの？
   118→├── CancelOrderCommand.ts  // なんでCommandなの？
   119→└── GetOrderListQuery.ts   // なんでQueryなの？
   120→
   121→✅ UseCase に統一（既存プロジェクトへの導入に推奨）
   122→├── PlaceOrderUseCase.ts
   123→├── CancelOrderUseCase.ts
   124→└── GetOrderListUseCase.ts
   125→
   126→✅ Command/Query に統一（新規プロジェクトに推奨）
   127→commands/
   128→├── PlaceOrderCommand.ts
   129→└── CancelOrderCommand.ts
   130→queries/
   131→├── GetOrderListQuery.ts
   132→└── GetOrderDetailQuery.ts
   133→```

   137→# 誤解3：「Query側もRepositoryを使う」
   138→
   139→DDDにおけるRepositoryは、**集約（Aggregate）の永続化・復元**のために存在します。
   140→
   141→> Repositoryは集約ルートのみに対して提供し、クライアントをドメインモデルに集中させ、
   142→> オブジェクトのストレージとアクセスをRepositoryに委譲する。
   143→>
   144→> — Eric Evans, [Domain-Driven Design（2003）p.151](https://fabiofumarola.github.io/nosql/readingMaterial/Evans03.pdf)
   145→
   146→## ❌ よくある実装
   147→
   148→```typescript
   149→// QueryでもRepositoryを使って集約を取得し、DTOに詰め替える
   150→class GetOrderListUseCase {
   151→  execute(): OrderListDTO[] {
   152→    const orders = this.orderRepository.findAll() // ← 集約を全件取得
   153→    return orders.map(order => ({                  // ← DTOに詰め替え
   154→      orderId: order.id.value,
   155→      customerName: ???, // ← 別集約の情報が取れない...
   156→      totalAmount: order.totalAmount,
   157→    }))
   158→  }
   159→}
   160→```
   161→
   162→これではN+1問題が起きたり、集約の境界をまたいだデータが取れなかったりします。
   163→
   164→## ✅ CQRSの正しいアプローチ
   165→
   166→**Repository（集約を返す）** と **QueryService（DTOを返す）** を使い分けます。
   167→
   168→```typescript
   169→// ✅ Command側：Repositoryを使う（従来通り）
   170→class PlaceOrderUseCase {
   171→  execute(command: PlaceOrderInput): void {
   172→    const order = Order.place(command.items, command.customerId)
   173→    this.orderRepository.save(order) // ← 集約の永続化
   174→  }
   175→}
   176→
   177→// ✅ Query側：QueryServiceを使う（CQRSの新しいやり方）
   178→class GetOrderListUseCase {
   179→  execute(): OrderListDTO[] {
   180→    return this.orderQueryService.findAll() // ← DTOを直接返す
   181→  }
   182→}
   183→```
   184→
   185→| | Repository | QueryService |
   186→|--|------------|-------------|
   187→| 返すもの | 集約（DomainModel） | DTO（画面用データ） |
   188→| 役割 | 集約の保存・復元 | 画面に必要な形でデータ取得 |
   189→| JOINの制約 | 集約の境界を守る | 自由にJOINしてOK |
   190→| DDDの制約 | 受ける | 受けない |

   194→# 誤解4：「QueryServiceはインフラ層に置く」
   195→
   196→## ❌ よくある誤解
   197→
   198→```
   199→QueryServiceはSQLを書くのでインフラ層に置く
   200→  → アプリケーション層からインフラ層を直接参照する
   201→  → 依存関係が壊れる 🚨
   202→```
   203→
   204→## ✅ 正しい理解
   205→
   206→これはRepositoryパターンとまったく同じ構造です。
   207→
   208→```
   209→【Repository】                    【QueryService】
   210→
   211→application/                      application/
   212→└── IOrderRepository.ts           └── IOrderQueryService.ts
   213→      （インターフェース）                （インターフェース定義）
   214→
   215→infrastructure/                   infrastructure/
   216→└── MySQLOrderRepository.ts       └── MySQLOrderQueryService.ts
   217→      （実装：SQLを書く）                （実装：SQLを書く）
   218→```
   219→
   220→インターフェースはアプリケーション層に、実装はインフラ層に。**SQLを書くクラスは必ずインフラ層**です。
   221→
   222→```typescript
   223→// ✅ application層：インターフェースを定義（SQLは知らない）
   224→interface IOrderQueryService {
   225→  findAll(): OrderListDTO[]
   226→  findById(id: string): OrderDetailDTO | null
   227→}
   228→
   229→// ✅ application層：インターフェースにだけ依存
   230→class GetOrderListUseCase {
   231→  constructor(
   232→    private queryService: IOrderQueryService // ← インターフェース
   233→  ) {}
   234→
   235→  execute(): OrderListDTO[] {
   236→    return this.queryService.findAll()
   237→  }
   238→}
   239→
   240→// ✅ infrastructure層：SQLの詳細はここだけ
   241→class MySQLOrderQueryService implements IOrderQueryService {
   242→  findAll(): OrderListDTO[] {
   243→    return this.db.query(`
   244→      SELECT o.id, c.name as customer_name, o.total, COUNT(i.id) as item_count
   245→      FROM orders o
   246→      JOIN customers c ON o.customer_id = c.id
   247→      JOIN order_items i ON o.id = i.order_id
   248→      GROUP BY o.id, c.name, o.total
   249→    `)
   250→  }
   251→}
   252→```

   256→# 誤解5：「依存の方向はHandler→UseCase→Domain→Infraの一方向」
   257→
   258→これは**依存性逆転の原則（DIP）** に関わる重要な誤解です。
   259→
   260→> 最も柔軟なシステムとは、ソースコードの依存関係が具体的な実装ではなく、
   261→> 抽象（インターフェース）だけを参照するものである。
   262→>
   263→> — Robert C. Martin, Clean Architecture
   264→
   265→> 高レベルモジュールは低レベルモジュールに依存してはならない。
   266→> 両者とも抽象に依存すべきである。
   267→>
   268→> — Robert C. Martin, Agile Software Development: Principles, Patterns, and Practices
   269→> （[Wikipedia: Dependency inversion principle](https://en.wikipedia.org/wiki/Dependency_inversion_principle) より）
   270→
   271→## ❌ よくある誤解
   272→
   273→```
   274→Handler → UseCase → Domain → Infrastructure（一方向に依存）
   275→```
   276→
   277→## ✅ 正しい理解
   278→
   279→**「呼び出しの流れ」と「依存の方向」は別物**です。
   280→
   281→```
   282→【呼び出しの流れ】（直感的な理解として正しい）
   283→Handler → UseCase → Domain → Infrastructure
   284→
   285→【依存の方向】（Infraだけ逆転する）
   286→Handler → UseCase → Domain ← Infrastructure
   287→                      ↑
   288→               インターフェースを定義
   289→               Infrastructureが実装（依存性逆転）
   290→```
   291→
   292→この仕組みによって「MySQLをPostgreSQLに変えても、Domainは一切変更不要」という状態が実現できます。

   330→# コードサンプル全体像
   331→
   332→## Domain層
   333→
   334→```typescript
   335→// domain/order/Order.ts（集約ルート）
   336→export class Order {
   337→  private constructor(
   338→    public readonly id: OrderId,
   339→    private customerId: CustomerId,
   340→    private items: OrderItem[],
   341→    private status: OrderStatus,
   342→  ) {}
   343→
   344→  static place(customerId: CustomerId, items: OrderItem[]): Order {
   345→    if (items.length === 0) {
   346→      throw new Error('注文には1つ以上の商品が必要です')
   347→    }
   348→    return new Order(OrderId.generate(), customerId, items, OrderStatus.PENDING)
   349→  }
   350→
   351→  cancel(): void {
   352→    if (this.status !== OrderStatus.PENDING) {
   353→      throw new Error('この注文はキャンセルできません')
   354→    }
   355→    this.status = OrderStatus.CANCELLED
   356→  }
   357→}
   358→
   359→// domain/order/IOrderRepository.ts（インターフェース）
   360→export interface IOrderRepository {
   361→  findById(id: OrderId): Promise<Order | null>
   362→  save(order: Order): Promise<void>
   363→}
   364→```
   365→
   366→## Application層
   367→
   368→```typescript
   369→// application/query-services/IOrderQueryService.ts（インターフェース）
   370→export interface IOrderQueryService {
   371→  findAll(): Promise<OrderListDTO[]>
   372→  findById(id: string): Promise<OrderDetailDTO | null>
   373→}
   374→
   375→export type OrderListDTO = {
   376→  orderId: string
   377→  customerName: string
   378→  totalAmount: number
   379→  itemCount: number
   380→  status: string
   381→  createdAt: Date
   382→}
   383→
   384→// application/usecases/PlaceOrderUseCase.ts（Command系）
   385→export class PlaceOrderUseCase {
   386→  constructor(
   387→    private readonly orderRepository: IOrderRepository // ← Domain I/Fに依存
   388→  ) {}
   389→
   390→  async execute(input: PlaceOrderInput): Promise<void> {
   391→    const order = Order.place(
   392→      new CustomerId(input.customerId),
   393→      input.items.map(i => new OrderItem(i.productId, i.quantity, i.price))
   394→    )
   395→    await this.orderRepository.save(order)
   396→  }
   397→}
   398→
   399→// application/usecases/GetOrderListUseCase.ts（Query系）
   400→export class GetOrderListUseCase {
   401→  constructor(
   402→    private readonly queryService: IOrderQueryService // ← Application I/Fに依存
   403→  ) {}
   404→
   405→  async execute(): Promise<OrderListDTO[]> {
   406→    // DomainModelを経由しない！
   407→    return this.queryService.findAll()
   408→  }
   409→}
   410→```

   412→## Infrastructure層
   413→
   414→```typescript
   415→// infrastructure/repositories/MySQLOrderRepository.ts
   416→export class MySQLOrderRepository implements IOrderRepository {
   417→  async findById(id: OrderId): Promise<Order | null> {
   418→    const row = await this.db.query(
   419→      'SELECT * FROM orders WHERE id = ?', [id.value]
   420→    )
   421→    if (!row) return null
   422→    return this.reconstruct(row) // ← 集約として復元
   423→  }
   424→
   425→  async save(order: Order): Promise<void> {
   426→    await this.db.query('INSERT INTO orders ...')
   427→  }
   428→}
   429→
   430→// infrastructure/query-services/MySQLOrderQueryService.ts
   431→export class MySQLOrderQueryService implements IOrderQueryService {
   432→  async findAll(): Promise<OrderListDTO[]> {
   433→    // 自由にJOINしてDTOを直接返す！集約の制約を受けない
   434→    const rows = await this.db.query(`
   435→      SELECT
   436→        o.id           AS orderId,
   437→        c.name         AS customerName,
   438→        o.total_amount AS totalAmount,
   439→        COUNT(i.id)    AS itemCount,
   440→        o.status,
   441→        o.created_at   AS createdAt
   442→      FROM orders o
   443→      JOIN customers c ON o.customer_id = c.id
   444→      JOIN order_items i ON o.id = i.order_id
   445→      GROUP BY o.id, c.name, o.total_amount, o.status, o.created_at
   446→    `)
   447→    return rows
   448→  }
   449→}
   450→```

   454→# 依存関係のまとめ図
   455→
   456→```
   457→Presentation
   458→    ↓ 依存
   459→Application（UseCase + I/F定義）
   460→    ↓ 依存（Command系のみ）
   461→Domain（集約 + Repository I/F）
   462→    ↑ 依存（implements）
   463→Infrastructure（Repository実装 + QueryService実装）
   464→```
   465→
   466→**ポイント：インフラ層だけが上位層のインターフェースを実装する（依存性逆転）**

   470→# 段階的な導入推奨
   471→
   472→一気に全部やらず、スモールスタートが鍵です。
   473→
   474→```
   475→Step 1: UseCaseをCommand系・Query系に分類するだけ
   476→        → コード変更なし、意識だけ変える
   477→
   478→Step 2: Query側でRepositoryを使わず、QueryServiceを導入
   479→        → DBは共通、Event Sourcingなし
   480→
   481→Step 3: 必要になったらReadモデル用DBを分離（オプション）
   482→        → パフォーマンス要件が出てきたとき
   483→```
