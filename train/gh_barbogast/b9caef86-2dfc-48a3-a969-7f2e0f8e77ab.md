> DEVELOPER

Right now there are several go files in the root folder. What's common practice to organize go files?

> AGENT

Go's convention is deliberately flexible, but the two common approaches for a project this size are: **1. Flat (current approach)** — everything in one package. Perfectly idiomatic for small-to-medium Go programs. The standard library does this within each package. Descriptive filenames (`drive_auth.go`, `drive_folders.go`) act as the organising principle. No import complexity. **2. Subpackages** — move cohesive groups of files into subdirectories, each with their own package name. For example, a `drive/` package containing `auth.go`, `folders.go`, `upload.go`. The root package then imports `drive` and calls `drive.Client(...)`, `drive.ListFolder(...)` etc. For this project specifically, there's a Wails constraint worth noting: the `App` struct and its methods must stay in the root `main` package because that's what Wails scans to generate frontend bindings. So `app.go`, `pdf.go`, and `main.go` are stuck in root regardless. The Drive code has no such constraint — it could move to a `drive/` subpackage cleanly. Whether that's worth doing depends on how much the Drive code grows. Right now it's three small files; if Drive Upload mode ends up with 10+ files, a subpackage starts to make more sense. **Recommendation:** stay flat for now. If Drive Upload grows significantly during Steps 2–9, revisit. Moving files is low-effort in Go since there are no circular dependency pitfalls at this scale.

> DEVELOPER

Is it possible to have all go files in a subfolder? Like `src` or `backend`?

> AGENT

Not in a Wails project, unfortunately. Wails runs `go build .` at the module root and expects the `main` package to be there. Moving `main.go` to a subfolder would break the Wails build — there's no config option in `wails.json` to point it elsewhere. The practical alternative is the subpackage approach: keep `main.go` and `app.go` thin at the root (they have to be there for Wails), and move everything else into subdirectories. For example, the Drive code could live in `drive/` with no Wails dependency, and `app.go` just calls into it. The root stays small; the bulk of the logic moves out.

> DEVELOPER

How does the code in drive_folders.go and drive_upload.go authenticate against Google Drive?

> AGENT

Through `driveService()` in `drive_folders.go`, which calls `DriveClient()` in `drive_auth.go`. `DriveClient` loads the cached token from disk (or runs the OAuth flow if none exists) and returns an `*http.Client` configured with that token. `driveService` wraps that client in a `*drive.Service`, which is what the API calls in `drive_folders.go` and `drive_upload.go` use. > DEVELOPER

But doesn't that make it hard to see where a symbol came from? From which file it was imported?

> AGENT

Yes, it can. But Go's convention is that **files within a package are not meant to be independent units** — the package as a whole is the unit. You're supposed to think of all the files in a package as one logical thing, not as modules that depend on each other. In practice it's rarely a problem because: - **IDEs handle it** — "Go to definition" jumps straight to the file and line, so you never actually need to know which file a symbol lives in - **Files stay small** — the convention is to split files by concern (`drive_auth.go`, `drive_folders.go`) so the name of the file gives you a strong hint anyway - **`grep` works** — `grep -r "DriveClient" .` finds it instantly The tradeoff is real though. In languages like TypeScript or Python, explicit imports document dependencies between files. In Go that documentation doesn't exist at the file level — only at the package level. If you find a call to `driveService()` in `drive_upload.go`, you know it's in the same package somewhere, but not which file without searching.
