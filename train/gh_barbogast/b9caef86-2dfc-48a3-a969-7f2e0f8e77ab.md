1	# Paper Scan Processor
2	
3	A desktop application for post-processing PDF files containing batches of scanned documents. The app has two modes: **Merge** and **Split**.
4	
5	## Tech stack
6	
7	- **Desktop framework**: Wails
8	- **Backend**: Go
9	- **Frontend**: TypeScript + React
10	- **UI components**: Mantine + `@mantine/dropzone`
11	- **Virtualization**: TanStack Virtual
12	- **Drag-and-drop**: dnd-kit
13	- **State**: Zustand
14	- **PDF manipulation**: pdfcpu
15	- **PDF rendering** (thumbnails): `mutool` (system install, called as subprocess)
16	
17	## Common elements
18	
19	Both modes include a thumbnail panel and a page detail panel, and support the same per-page editing operations.
20	
21	### Thumbnail panel
22	
23	A vertically scrolling strip of page thumbnails. Width is user-adjustable via a drag handle; thumbnails scale to fill the panel width. Rendering is on-demand and virtualized — only visible thumbnails (plus a small overscan buffer) are rendered at any given time.
24	
25	The Go backend exposes a per-page render method returning a base64-encoded PNG; the frontend requests thumbnails as they scroll into view (`mutool draw` subprocess).
26	
27	#### Keyboard shortcuts
28	
29	| Key                    | Action                                     |
30	| ---------------------- | ------------------------------------------ |
31	| `R`                    | Rotate selected page clockwise 90°         |
32	| `Shift+R`              | Rotate selected page counter-clockwise 90° |
33	| `Delete` / `Backspace` | Toggle skip on the selected page           |
34	| `←` / `→`              | Select previous / next page                |
35	
36	### Page detail panel
37	
38	Shows the currently selected page at reading resolution. Selecting a thumbnail updates it.
39	
40	Supports:
41	
42	- **Pan**: drag to pan.
43	- **Zoom**: scroll wheel or trackpad pinch to zoom in/out.
44	- **Navigate**: `←` / `→` to move to the previous/next page.
45	
46	Implemented with `react-zoom-pan-pinch`.
47	
48	### Page editing
49	
50	Individual pages can be edited in both modes before export or merge:
51	
52	- **Rotation**: pages can be rotated in 90° increments (clockwise or counter-clockwise).
53	- **Skip**: pages can be marked as skipped — excluded from the output but remaining visible in the thumbnail view (greyed out). A page is skipped by clicking a skip icon that appears on hover, or via keyboard shortcut.
54	- **Reorder**: pages can be reordered by dragging thumbnails to a new position.
55	
56	## Mode: Merge
57	
58	For scanners that can only scan one side at a time. The user scans all front pages as one PDF and all back pages as another, then uses Merge mode to interleave them into a single PDF.
59	
60	### Workflow
61	
62	1. The user loads two PDF files, labelled **File A** and **File B**.
63	2. The user selects which file contains the first page (**First page in: File A / File B**).
64	3. A **Reverse File B** checkbox controls whether File B is reversed before interleaving. This should be checked when the paper stack was flipped between scans (the typical case, when scanning one side at a time), causing the second-scanned pages to be in reverse order.
65	4. The app interleaves the pages: A1, B1, A2, B2, etc.
66	5. The user saves the merged result as a new PDF file on disk.
67	
68	The merged PDF can then be opened in Split mode for further processing.
69	
70	### Unequal page counts
71	
72	If File A and File B have different page counts, the app shows a warning before proceeding: "File A has X pages, File B has Y pages. The extra Z page(s) will be appended at the end." The user can cancel or continue. The extra pages from the longer file are appended in order after the interleaved section.

> AGENT

Good question to think through before committing. Here's my honest take on both:

---

**Is a custom implementation worth it vs. browser Drive?**

Yes, but only for a specific user profile: someone who regularly files many scanned documents into a structured Drive hierarchy. The key advantages over browser Drive:

- **Remembered folder mappings** — the high-friction part of Drive in a browser is navigating to the right nested folder every time. A mapping that says "files in subfolder `invoices` → `My Drive / Finance / Invoices / 2026`" eliminates that.
- **Local lifecycle management** — browser Drive gives you no way to delete or archive the local source file after upload. That step currently requires a separate trip to Finder.
- **No app-switching** — the whole scan-then-file workflow stays in one place.
- **Conflict detection before upload** — browser Drive silently creates duplicates.

If the user only uploads a few files occasionally, browser Drive is fine. If they're filing 10–30 documents per session into organized folders, a custom tool pays off quickly.

---

**Additional features worth considering**

- **Folder presets / bookmarks** — saved named shortcuts (e.g. "Smith 2026", "Invoices") so the user doesn't navigate the tree each time; more ergonomic than just "recently used"
- **Batch folder assignment** — select multiple files and assign them all to the same Drive folder in one action, useful when a batch all belongs to one client
- **Group by local subfolder** — if files are already organized into local subfolders (which Split mode creates), auto-group them and assign a Drive folder per group rather than per file
- **Duplicate detection** — warn if a file with the same name already exists at the target Drive location, before uploading
- **Archive-to-folder option** — rather than delete source files, offer to move them to a local archive folder (e.g. `~/Documents/Archived Scans/2026-07`) as a safer alternative to permanent deletion
- **Upload queue with retry** — individual file retry on failure without restarting the whole batch (already in the spec for Split mode, but more important here since batches could be larger)
- **"Open in Drive" after upload** — a quick link to open the destination folder in the browser once done

---

**One structural question worth resolving early**: if Drive Upload becomes its own mode, does Split mode lose all Drive awareness? The cleaner workflow would be: Split exports to local disk only, then Drive Upload handles filing. That separation makes both modes simpler and makes Drive Upload useful for files that didn't come from the scan processor at all.

In a Wails/Go app, opening a URL for OAuth uses the OS default browser — Chrome in your case. The standard flow is:

1. Go opens the system default browser to Google's auth URL (via `open` on macOS)
2. The user authenticates in Chrome (likely already signed in to Google there)
3. Google redirects to a `localhost` callback URL
4. The Go backend's local HTTP server catches the callback and stores the token

This is actually the better approach — no credentials flow through the app's own webview, and the user doesn't have to sign in again if Chrome already has a Google session. > DEVELOPER

But this means that the credentials are stored on my hard drive in plain sight without any protection - right?

> AGENT

Yes, that's right — both files sit as plain JSON in `~/Library/Application Support/paper-scan-processor/`.

**`drive_credentials.json`** (client ID + secret) — the risk here is moderate. For a Desktop app OAuth credential, the client secret isn't truly secret: Google acknowledges that desktop apps can't keep secrets, and anyone who extracts it can only use it to build their own OAuth flow (they'd still need a user to sign in). So leaking it isn't catastrophic, just mildly bad practice.

**`drive_token.json`** (access + refresh token) — this is the sensitive one. Anyone who gets the refresh token has persistent access to your Drive until you revoke it in your Google account. It's protected only by macOS filesystem permissions (readable only by your user), which is the same protection as your SSH keys, browser cookies, and keychain-adjacent files. So it's not "in plain sight" in the sense that any process running as you can read it — but that's true of most credentials on a personal Mac.

**If you want stronger protection**, the right move is to store the token in the macOS Keychain instead of a plain JSON file. That would mean the token is encrypted at rest and requires your login password (or Touch ID) to unlock. It's not much extra code — the `zalando/go-keyring` package handles it with one function call. Worth adding before the feature ships, but not essential for the spike.

Because our Drive tests are interactive integration tests mixed into the same package as the unit tests. When you run `go test` without `-run`, Go runs all tests — but `TestDriveAuthenticate` blocks waiting for a browser callback if the token isn't cached, which hangs the suite. > DEVELOPER

Right now there are several go files in the root folder. What's common practice to organize go files?

> AGENT

Go's convention is deliberately flexible, but the two common approaches for a project this size are:

**1. Flat (current approach)** — everything in one package. Perfectly idiomatic for small-to-medium Go programs. The standard library does this within each package. Descriptive filenames (`drive_auth.go`, `drive_folders.go`) act as the organising principle. No import complexity.

**2. Subpackages** — move cohesive groups of files into subdirectories, each with their own package name. For example, a `drive/` package containing `auth.go`, `folders.go`, `upload.go`. The root package then imports `drive` and calls `drive.Client(...)`, `drive.ListFolder(...)` etc.

For this project specifically, there's a Wails constraint worth noting: the `App` struct and its methods must stay in the root `main` package because that's what Wails scans to generate frontend bindings. So `app.go`, `pdf.go`, and `main.go` are stuck in root regardless.

The Drive code has no such constraint — it could move to a `drive/` subpackage cleanly. Whether that's worth doing depends on how much the Drive code grows. Right now it's three small files; if Drive Upload mode ends up with 10+ files, a subpackage starts to make more sense.

**Recommendation:** stay flat for now. If Drive Upload grows significantly during Steps 2–9, revisit. Moving files is low-effort in Go since there are no circular dependency pitfalls at this scale.

> DEVELOPER

Is it possible to have all go files in a subfolder? Like `src` or `backend`?

> AGENT

Not in a Wails project, unfortunately. Wails runs `go build .` at the module root and expects the `main` package to be there. Moving `main.go` to a subfolder would break the Wails build — there's no config option in `wails.json` to point it elsewhere.

The practical alternative is the subpackage approach: keep `main.go` and `app.go` thin at the root (they have to be there for Wails), and move everything else into subdirectories. For example, the Drive code could live in `drive/` with no Wails dependency, and `app.go` just calls into it. The root stays small; the bulk of the logic moves out.

> DEVELOPER

How does the code in drive_folders.go and drive_upload.go authenticate against Google Drive?

> AGENT

Through `driveService()` in `drive_folders.go`, which calls `DriveClient()` in `drive_auth.go`. `DriveClient` loads the cached token from disk (or runs the OAuth flow if none exists) and returns an `*http.Client` configured with that token. `driveService` wraps that client in a `*drive.Service`, which is what the API calls in `drive_folders.go` and `drive_upload.go` use.

So the dependency chain is:

```
DriveFindFolder / DriveListFolder / DriveUploadFile
  → driveService()
    → DriveClient()
      → token from disk (or OAuth flow)
```

> DEVELOPER

So each go file implicitely imports all exports from the same package?

> AGENT

Yes. All files in the same package share a single namespace — there are no imports between them. `drive_folders.go` can call `DriveClient()` and `driveService()` defined in `drive_auth.go` directly, as if they were in the same file. > DEVELOPER

But doesn't that make it hard to see where a symbol came from? From which file it was imported?

> AGENT

Yes, it can. But Go's convention is that **files within a package are not meant to be independent units** — the package as a whole is the unit. You're supposed to think of all the files in a package as one logical thing, not as modules that depend on each other.

In practice it's rarely a problem because:

- **IDEs handle it** — "Go to definition" jumps straight to the file and line, so you never actually need to know which file a symbol lives in
- **Files stay small** — the convention is to split files by concern (`drive_auth.go`, `drive_folders.go`) so the name of the file gives you a strong hint anyway
- **`grep` works** — `grep -r "DriveClient" .` finds it instantly

The tradeoff is real though. In languages like TypeScript or Python, explicit imports document dependencies between files. In Go that documentation doesn't exist at the file level — only at the package level. If you find a call to `driveService()` in `drive_upload.go`, you know it's in the same package somewhere, but not which file without searching.
