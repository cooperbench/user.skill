2	
3	A desktop application for post-processing PDF files containing batches of scanned documents. The app has two modes: **Merge** and **Split**.
4	
5	## Tech stack
6	
7	- **Desktop framework**: Wails

14	- **PDF manipulation**: pdfcpu

17	## Common elements
18	
19	Both modes include a thumbnail panel and a page detail panel, and support the same per-page editing operations.
20	
21	### Thumbnail panel
22	
23	A vertically scrolling strip of page thumbnails. Width is user-adjustable via a drag handle; thumbnails scale to fill the panel width. Rendering is on-demand and virtualized — only visible thumbnails (plus a small overscan buffer) are rendered at any given time.
24	
25	The Go backend exposes a per-page render method returning a base64-encoded PNG; the frontend requests thumbnails as they scroll into view (`mutool draw` subprocess).

56	## Mode: Merge
57	
58	For scanners that can only scan one side at a time. The user scans all front pages as one PDF and all back pages as another, then uses Merge mode to interleave them into a single PDF.
59	
60	### Workflow
61

63	2. The user selects which file contains the first page (**First page in: File A / File B**).
64	3. A **Reverse File B** checkbox controls whether File B is reversed before interleaving. This should be checked when the paper stack was flipped between scans (the typical case, when scanning one side at a time), causing the second-scanned pages to be in reverse order.
65	4. The app interleaves the pages: A1, B1, A2, B2, etc.
66	5. The user saves the merged result as a new PDF file on disk.
67

## Step 9: Reorder pages

### The core design question

A split point in `useOutputFiles` is currently keyed by the original-PDF page number that starts each segment (`firstPage`). This turns out to be a good foundation for reordering: original page numbers are stable identifiers even as display positions change, so split points naturally travel with their anchor pages when you drag them around. No need to re-key `useOutputFiles`.

---

### Frontend — medium complexity

**New state in `SplitMode`:** `pageOrder: number[]` — a permutation of `[1..pageCount]`, initially in order. Display position `i` shows original page `pageOrder[i]`.

**`buildItems()` in `SplitMode/ThumbnailPanel.tsx`:** currently iterates `for page = 1..pageCount`. Switch to iterating `pageOrder`. A gap is a split point if the next display position's original page (`pageOrder[displayIndex + 1]`) is the `firstPage` of a segment in `outputFiles`.

**`useOutputFiles.toggle()`:** currently receives `afterPage` (original page number). After reordering, clicking the gap after display index `i` should toggle `pageOrder[i + 1]` as the `firstPage`. The caller (`handleToggleSplitPoint`) computes this before calling `toggle`.

**`selectedPage`:** stays as an original page number. Scrolling-to-index uses `pageOrder.indexOf(selectedPage)` instead of `selectedPage - 1`.

**dnd-kit drag and drop:** dragging thumbnails within a virtualized list. This is the main implementation effort. dnd-kit's `SortableContext` with a custom drag overlay works well here, but requires either disabling virtualization during drags or using `DragOverlay` to render the dragged item outside the virtualizer. The latter is cleaner: the item disappears from its slot and floats as an overlay until dropped. On drop, update `pageOrder`.

**Total frontend work:** ~150–200 lines touched/added across `SplitMode/index.tsx`, `SplitMode/ThumbnailPanel.tsx`, and `PageThumbnail.tsx` (drag handle). `useOutputFiles` is unchanged.

---

### Backend — low complexity

`ExportSplit` currently takes `firstPage` per segment and reconstructs split boundaries. With reordering, the frontend already knows the exact ordered list of original pages per segment. The cleanest change: replace `OutputFileSpec.FirstPage` with `Pages []int` (ordered original-page numbers for that segment). The backend then just maps each `page` → its single-page PDF file, skips pages not in the list, applies rotations, and calls `MergeCreateFile` with the pages in order.

This removes the `splitAfter` reconstruction logic from `ExportSplit` entirely. The fast path (`SplitByPageNrFile`) is retired for the skip/reorder case — the explode-then-reassemble path already handles it, and reordering always goes through that path. If there are no skips and no reorder (i.e. `pageOrder` is identity), the fast path can still be used.

**Total backend work:** ~30–40 lines in `app.go` and `pdf.go`.

---

### UX — medium complexity

One decision to make up front: **what happens at the boundary between two segments when you drag a page across a split point?**

- The split point is keyed to whichever original page is currently first in the next segment. If you drag that page away, the split point travels with it, and the page that was previously second in the segment becomes the new first — automatically becoming a new "anchor" for the split.
- This is the most intuitive behavior ("split points belong to pages, not gaps") and it falls out naturally from the `firstPage`-keyed design.

Other UX details:
- A drag handle icon on each thumbnail (visible on hover) is the affordance. Drag from the handle, not the whole thumbnail, to avoid conflicting with click-to-select.
- The page label should update in real time as you drag (dnd-kit's `DragOverlay` handles this).
- The keyboard reorder shortcut (not in spec yet) could be deferred.

---

### Risk / open questions

1. **dnd-kit + TanStack Virtual:** there's a known friction between sortable drag-and-drop and virtualized lists — the dragged item leaving the virtualizer's render window causes it to disappear. The `DragOverlay` pattern (render a clone outside the virtualizer) solves this but adds some boilerplate.
2. **The fast-path backend:** currently `splitPDF` has a fast path when there are no skips (uses `SplitByPageNrFile` directly). With reordering, detecting "identity order" to keep the fast path is a minor extra condition — probably not worth the complexity, just always use the explode path.

> AGENT

Yes, it's feasible. The gap exists because headers aren't registered droppable targets — when the drag overlay is over a header, `onDragOver` fires with `over = null` and the last valid position is locked in. You can place a page as the *last* page of a segment (drop on the page before a split), but you can't explicitly target "first page of the next segment" by dropping on the header itself.

**The fix**: use dnd-kit's `useDroppable` to register each header as a drop target with a distinct ID like `"header-1"`. In `handleDragOver`, detect header IDs and compute the correct `arrayMove` index: find where the target segment starts in the current `draggingOrder` (using `splitPoints`), then move the active page to that display index.

The tricky part is computing "where does segment N start?" as `draggingOrder` mutates during the drag. Something like:


**Complexity**: medium — about 30–40 lines. You need a `DroppableHeader` component wrapping `OutputFileHeader`, wiring its `setNodeRef` from `useDroppable`, and a branch in `handleDragOver` to dispatch to different logic when `over.id` is a header vs a page.
