> DEVELOPER

But: api.RotateFile is able to rotate multiple pages within a PDF file. Couldn't this be used instead of splitting the PDF into single-page files before rotation?

> AGENT

Yes. After splitting into segments (the existing fast path), you'd iterate over each segment, translate the rotated original page numbers to segment-local page numbers, group them by rotation value, and call `api.RotateFile` once per distinct value. Since pdfcpu accepts a page-selection slice (`[]string{"1", "3"}` etc.), you can target specific pages within a multi-page segment. That would unify both paths — always split with `SplitByPageNrFile`, then optionally rotate in-place on the segments — eliminating the single-page explosion, the `pages/` subdir, and the re-merge. It also makes the special case redundant (a segment with no rotated pages just gets zero `RotateFile` calls). The only added complexity is translating original page numbers to segment-local ones and grouping by degree, which is straightforward given the `files[i].FirstPage` values. Want to switch to that approach?

> DEVELOPER

> AGENT

The only tradeoff is that you're copying the entire input PDF even if only one page is rotated, whereas the segment approach would only touch affected segments.
