Does Rust have libraries for editing PDFs with native interfaces?

> AGENT

Short answer: **not really, not in pure Rust.** The Rust PDF ecosystem is thin. What exists: - **lopdf** — read/write PDF objects at a low level. Can merge and manipulate pages, but it's working with raw PDF internals. No rendering. - **printpdf** — creates PDFs from scratch. Not for editing existing ones. - **pdf** crate — primarily a reader. For rendering thumbnails (which this app needs), pure Rust has nothing production-ready. The viable options both involve FFI wrappers around C/C++ libraries: - **pdfium-render** — Rust bindings to Google's PDFium (the Chrome PDF engine). Solid for rendering pages to bitmaps and reading structure. Editing support is more limited. - **mupdf-sys / mupdf bindings** — wraps MuPDF, which is the most capable C library for this use case (render, edit, split, rotate). But the Rust bindings are community-maintained and not as mature as the library itself. The irony is that **Python's PyMuPDF** (also wrapping MuPDF) is far more ergonomic and battle-tested than the Rust MuPDF bindings, even though you're calling the same underlying C library in both cases. **Bottom line:** Rust doesn't give you a PDF advantage over Python here — you'd be wrapping a C library either way, and Python wraps MuPDF better. Rust's real argument for this app is performance and the UI layer (Tauri), not PDF manipulation specifically. Does that change how you're thinking about the stack?

How would you then handle PDFs when using Rust?

> AGENT

The practical answer is you'd call out to an external tool — **`pdftk`** or more likely **`ghostscript`** or **`mutool`** (MuPDF's CLI) as a subprocess. For this app's operations: - **Split**: `mutool poster` or `pdftk input.pdf cat 1-3 output part1.pdf` - **Merge/interleave**: `pdftk A=fronts.pdf B=backs.pdf shuffle A B output merged.pdf` - **Rotate**: `pdftk input.pdf rotate 1-endeast output rotated.pdf` - **Render thumbnails**: `mutool draw -o thumb%d.png -r 72 input.pdf` Rust orchestrates the work — builds the command, spawns the process, handles errors — and the CLI tool does the actual PDF manipulation. **The tradeoffs:** - These tools are mature and reliable, handling malformed PDFs gracefully - But you're now requiring the user to have `pdftk`/`mutool` installed, or you bundle the binary with your app - Bundling works fine on desktop (Tauri does this), but it's extra packaging work - Subprocess calls add latency vs. in-process library calls — probably fine for this workload **The honest reframe:** if PDF manipulation is being delegated to an external binary anyway, the language choice for the app shell matters less. Python calling `mutool` is just as valid as Rust calling `mutool`, and Python's process-spawning ergonomics (`subprocess`, `pathlib`) are excellent. This is the strongest argument for **TypeScript + a bundled `mutool`** — you get the best UI tooling and the same PDF backend as the Rust approach.
