```
1	# Paper Scan Processor
2	
3	A desktop application for post-processing PDF files containing batches of scanned documents. The app has two independent modes: **Merge** and **Split**.
4	
5	## Tech stack
6	
7	- **Desktop framework**: Wails
8	- **Backend**: Go
9	- **Frontend**: TypeScript + React
10	- **UI components**: Mantine + `@mantine/dropzone`
11	- **Virtualization**: TanStack Virtual
12	- **Drag-and-drop**: dnd-kit
13	- **State**: Zustand
14	- **PDF manipulation**: pdfcpu
15	- **PDF rendering** (thumbnails): bundled `mutool` binary (subprocess)
16	
17	## Mode: Merge
18	
19	For scanners that can only scan one side at a time. The user scans all front pages as one PDF and all back pages as another, then uses Merge mode to interleave them into a single PDF.
20	
21	### Merge workflow
22	
23	1. The user loads two PDF files — one containing front pages, one containing back pages.
24	2. The user selects which file contains the first page (i.e. designates which is "fronts" and which is "backs").
25	3. A **Reverse back pages** checkbox controls whether the back PDF is reversed before interleaving. This should be checked when the paper stack was flipped between scans (the typical case), causing backs to be in reverse order.
26	4. The app interleaves the pages: front 1, back 1, front 2, back 2, etc.
27	5. The user saves the merged result as a new PDF file on disk.
28	
29	The merged PDF can then be opened in Split mode for further processing.
30	
31	## Mode: Split
32	
33	### Split workflow
34	
35	1. The user loads an input PDF via a file picker dialog or by dragging and dropping a file onto the app window.
36	2. The app displays all pages of the input PDF as thumbnails in a main panel.
37	3. The user defines split points by clicking in the gaps between page thumbnails. A visual divider appears at each split point; clicking again removes it. Dividers can also be repositioned by dragging them to a different gap. Each divider marks where a new output file begins.
38	4. The user sets a global filename template using `{date}` (today's date as `YYYY-MM-DD`) and `{name}` (a per-file label). Example: `{date} {name}` → `2026-06-12 invoice.pdf`. The app prefills the filename for each output file using this template. The user can then edit any individual file's name before exporting.
39	5. The user sets a global output folder (an existing folder on the local filesystem, or a Google Drive folder if Drive integration is enabled). This folder is used as the destination for all output files. A sidebar panel lists each output file as a row, aligned with its pages. For each output file, the user can adjust:
40	   - The prefilled filename (editable)
41	   - The destination folder (overridable per file)
42	6. The user clicks Export. Before splitting, the app checks for filename conflicts at each destination. If any conflict is found, the export is aborted and an error message identifies the conflicting files. Once resolved, the app splits the input PDF and writes (or uploads) each output file. Afterwards, the app prompts the user to keep, move, or delete the input file.
43	
44	## Error handling
45	
46	- Local file write errors are shown inline in the affected output file's sidebar row.
47	
48	## Page editing
49	
50	- **Rotation**: individual pages can be rotated in 90° increments (clockwise or counter-clockwise).
51	- **Skip**: individual pages can be marked as skipped — they are excluded from the export but remain visible in the thumbnail view (greyed out). A page is skipped by clicking a skip icon that appears on the thumbnail on hover, or via keyboard shortcut.
52	- **Reorder**: pages can be reordered by dragging thumbnails to a new position.
53	
54	## Keyboard shortcuts
55	
56	| Key | Action |
57	|-----|--------|
58	| `R` | Rotate selected page clockwise 90° |
59	| `Shift+R` | Rotate selected page counter-clockwise 90° |
60	| `Space` | Toggle a split point after the selected page |
61	| `Delete` / `Backspace` | Toggle skip on the selected page |
62	| `Tab` | Move focus to the next filename input field in the sidebar |
63	
64	## Google Drive integration (optional)
65	
66	- Authentication uses Google OAuth via a browser window, triggered the first time Drive is enabled. Credentials are stored locally and reused in future sessions.
67	- When Drive is enabled, each output file row in the sidebar shows a Drive folder field. Clicking it opens a folder browser modal that displays the user's Drive folder tree. The user navigates the tree and selects a destination folder. The selected path is shown in the row (e.g. `My Drive / Clients / Smith / 2026`).
68	- The folder tree is fetched lazily — the first time the user opens the folder browser in a session.
69	- The folder browser shows a **recently used folders** list at the top for quick access. This list persists across sessions.
70	- The global output folder setting can be set to a Drive folder, which prefills all output file rows. Individual rows can be overridden.
71	- After export, each output file is uploaded to its designated Drive folder. If an upload fails, the affected row shows an inline error message and a Retry button; other uploads are unaffected.
72	- When Drive is enabled, the local subfolder name for each output file is derived automatically from the Drive folder path (see Local folder sorting below).
73	
74	## Local folder sorting
75	
76	Each output file can be assigned a subfolder name. The file is then saved to `[output folder] / [subfolder] / filename.pdf` rather than directly into the output folder.
77	
78	When Drive is enabled, the subfolder name is derived automatically from the innermost component of the Drive folder path (e.g. `My Drive / Clients / Smith / 2026` → subfolder `2026`). When Drive is disabled, the user enters the subfolder name manually in the sidebar.
79	
80	If two or more output files in the same batch share the same subfolder name, the app prefixes the parent folder name to disambiguate. If the parent name is also shared, it walks further up the hierarchy until uniqueness is achieved. Examples:
81	- `Clients / Smith / 2026` and `Clients / Jones / 2026` → `Smith - 2026` and `Jones - 2026`
82	- `Clients / Smith / 2026` and `Archive / Smith / 2026` → `Clients - Smith - 2026` and `Archive - Smith - 2026`
83	
84	(When Drive is disabled and names are entered manually, the user is responsible for avoiding conflicts — no automatic disambiguation applies.)
85	
86	To ensure disambiguation is fully deterministic, **the output folder must be empty when the input PDF is opened**. The app enforces this and shows an error if the folder is not empty.
87	
88	## Persisted settings
89	
90	The following settings are saved across sessions:
91	- Last-used output folder
92	- Filename template
93	
94	## Future / out of scope for v1
95	
96	- **Insert pages from another PDF**: allow the user to pull pages from a second PDF into the current document before splitting. Planned for v2.
97	- **Scanning integration**: trigger a scan from within the app using OS or device APIs. Not currently planned but under consideration.
98	
```

---

**PDF split/merge**

Recommend a `_test.go` rather than a UI harness — it runs without Wails and is faster to iterate. Two things to flag:
- pdfcpu's `SplitFile` names output files `<base>_<N>.pdf`. Need to verify whether N is zero-padded (e.g. `_001` vs `_1`) — if not, lexicographic sort breaks for >9 pages.
- The spec doesn't say what to do when front/back page counts differ. Safest: append remaining pages from the longer file in order.

---

**Thumbnail panel**

The key design decision is how to get rendered images into the frontend. Two options:
- **Base64 via RPC** — `RenderPageThumbnail(path string, page, widthPx int) (string, error)` returns a base64 PNG per page. Simple, no extra server. Works well with TanStack Virtual: only call it for visible pages.
- **Temp dir + HTTP** — render a batch up front, serve via a local HTTP server. More complex setup but batching is more efficient for large files.

Recommend base64 + on-demand per-page rendering for the building block. The virtual list only requests thumbnails as they scroll into view.

The "adjustable width" detail: the panel should have a drag handle on its right edge. When the user drags it, the container width changes and thumbnails reflow (CSS: thumbnail fills container width minus padding).

---

**Detail panel**

This isn't in the current spec — you're proposing to add it. A few layout options:

- **Modal overlay** — click a thumbnail → full-screen overlay with the page. Clean, doesn't affect split-mode layout.
- **Side-by-side** — thumbnail strip narrows, detail view takes the rest of the main panel. More context but tighter layout with the sidebar already on the right.

For pan+scroll: `react-zoom-pan-pinch` (well-maintained library) handles pinch/wheel zoom + drag-to-pan cleanly. Alternative: render at 2× DPI and use `overflow: auto` — scroll to pan, no zoom. Simpler but less fluid.

```
type PageSpan struct {
	From   int
	Thru   int
	Reader io.Reader

func pageSpan(ctx *model.Context, from, thru int) (*PageSpan, error) {
	ctxNew, err := pdfcpu.ExtractPages(ctx, PagesForPageRange(from, thru), false)
	if err != nil {
		return nil, err
	}

	var b bytes.Buffer
	if err := WriteContext(ctxNew, &b); err != nil {
		return nil, err
	}

	return &PageSpan{From: from, Thru: thru, Reader: &b}, nil
}

func spanFileName(fileName string, from, thru int) string {
	baseFileName := filepath.Base(fileName)
	fn := strings.TrimSuffix(baseFileName, ".pdf")
	fn = fn + "_" + strconv.Itoa(from)
	if from == thru {
		return fn + ".pdf"
	}
	return fn + "-" + strconv.Itoa(thru) + ".pdf"
}

func splitOutPath(outDir, fileName string, forBookmark bool, from, thru int) string {
	p := filepath.Join(outDir, fileName+".pdf")
	if !forBookmark {
		p = filepath.Join(outDir, spanFileName(fileName, from, thru))
	}
	return p
}

	}

	return pdfcpu.WriteReader(outPath, ps.Reader)

func pageSpansSplitAlongBookmarks(ctx *model.Context) ([]*PageSpan, error) {
	pss := []*PageSpan{}

	if err != nil {
		return nil, err

		pss = append(pss, ps)

func pageSpans(ctx *model.Context, span int) ([]*PageSpan, error) {
	pss := []*PageSpan{}

	for i := 0; i < ctx.PageCount/span; i++ {
		start := i * span
		from := start + 1
		thru := start + span
		ps, err := pageSpan(ctx, from, thru)
		if err != nil {
			return nil, err
		}
		pss = append(pss, ps)
	}

	// A possible last file has less than span pages.
	if ctx.PageCount%span > 0 {
		start := (ctx.PageCount / span) * span
		from := start + 1
		thru := ctx.PageCount
		ps, err := pageSpan(ctx, from, thru)
		if err != nil {
			return nil, err
		}
		pss = append(pss, ps)
	}

	return pss, nil
}

		if err := writePageSpan(ctx, from, thru, path); err != nil {

		}
	}

	return nil
}

func writePageSpansSplitAlongBookmarks(ctx *model.Context, outDir string) error {

func writePageSpansSplitAlongPages(ctx *model.Context, pageNrs []int, outDir, fileName string) error {
	// pageNumbers is a sorted sequence of page numbers.
	forBookmark := false
	from, thru := 1, 0

	if len(pageNrs) < 1 {
		return errors.New("pdfcpu: split along pageNrs - missing pageNrs")
	}

	if pageNrs[0] > ctx.PageCount {
		return errors.New("pdfcpu: split along pageNrs - invalid page number sequence.")
	}

	for i := 0; i < len(pageNrs); i++ {
		thru = pageNrs[i] - 1
		if thru >= ctx.PageCount {
			break
		}
		path := splitOutPath(outDir, fileName, forBookmark, from, thru)
		if err := writePageSpan(ctx, from, thru, path); err != nil {
			return err
		}
		from = thru + 1
	}

	thru = ctx.PageCount
	path := splitOutPath(outDir, fileName, forBookmark, from, thru)
	return writePageSpan(ctx, from, thru, path)
}

// SplitRaw returns page spans for the PDF stream read from rs obeying given split span.
// If span == 1 splitting results in single page PDFs.
// If span == 0 we split along given bookmarks (level 1 only).
// Default span: 1
func SplitRaw(rs io.ReadSeeker, span int, conf *model.Configuration) (ps []*PageSpan, err error) {
	defer fault.Catch(&err)

	if rs == nil {
		return nil, errors.New("pdfcpu: SplitRaw: missing rs")
	}

	ctx, err := context(rs, conf)
	if err != nil {
		return nil, err
	}

	if span == 0 {
		return pageSpansSplitAlongBookmarks(ctx)
	}
	return pageSpans(ctx, span)
}

// Split generates a sequence of PDF files in outDir for the PDF stream read from rs obeying given split span.
// If span == 1 splitting results in single page PDFs.
// If span == 0 we split along given bookmarks (level 1 only).
// Default span: 1
func Split(rs io.ReadSeeker, outDir, fileName string, span int, conf *model.Configuration) (err error) {
	defer fault.Catch(&err)

	if rs == nil {
		return errors.New("pdfcpu: Split: missing rs")

	ctx, err := context(rs, conf)
	if err != nil {
		return err
	}

	if span == 0 {
		return writePageSpansSplitAlongBookmarks(ctx, outDir)
	}
	return writePageSpans(ctx, span, outDir, fileName)
}

// SplitFile generates a sequence of PDF files in outDir for inFile obeying given split span.
// If span == 1 splitting results in single page PDFs.
// If span == 0 we split along given bookmarks (level 1 only).
// Default span: 1
func SplitFile(inFile, outDir string, span int, conf *model.Configuration) error {
	f, err := os.Open(inFile)
	if err != nil {
		return err
	}
	if log.CLIEnabled() {
		log.CLI.Printf("splitting %s to %s/...\n", inFile, outDir)
	}

	defer func() {
		if err != nil {
			f.Close()
			return
		}
		err = f.Close()
	}()

	return Split(f, outDir, filepath.Base(inFile), span, conf)
```

There are three options:

1. **pdfcpu `ExtractContent`** — extracts raw PDF content stream operators, not plain text. Workable if our test PDFs embed markers like `(F1) Tj`, but it's low-level and verbose to parse.

2. **`mutool draw -F text`** — outputs clean text per page as a subprocess. Simple one-liner, and mutool is already a required dependency of the app anyway.

3. **Raw byte scan** — the simplest self-contained approach: add uncompressed content streams to the test PDFs with unique text markers per page (e.g. `(F1)`, `(B2)`). Since they're uncompressed, the strings appear literally in the PDF bytes and can be grepped with `bytes.Contains`. No parsing needed.

I'd recommend **option 3** for the tests: it requires no external tools or extra parsing, and since we control `minimalPDF` we can add content streams trivially. The only change is updating `minimalPDF` to accept labels per page, e.g.:
