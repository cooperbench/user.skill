Yes, a single scroll area for Merge mode is very feasible and would eliminate all that complexity. Here's the idea:

**Single virtualizer, rows of pairs.** Instead of two synced panels, one virtualizer renders `max(countA, countB)` rows. Each row has A's thumbnail on the left and B's thumbnail on the right, side by side. Scrolling is one action, naturally synchronized.

The "first page in" toggle no longer needs an offset — it just determines which column's pages get odd output numbers and which get even. The bottom-padding equalization math disappears entirely. No refs, no `syncing` flag, no `handleScrollA/B`.

The tricky parts are minor:
- When counts differ, the shorter side renders blank/empty cells for trailing rows
- The resize drag handle could live between the two columns (a single handle controlling both widths simultaneously, or each column independently)
- Selection highlight still tracks `pageA` and `pageB` independently, but they're rendered in the same item loop

**Rough structure:**
```
<div ref={scrollRef}>  // single scroll container
  {virtualItems.map(item => (
    <div style={{ display: 'flex' }}>
      <ThumbCell pdf={pathA} page={item.index + 1} ... />  // or blank
      <ThumbCell pdf={pathB} page={item.index + 1} ... />
    </div>
  ))}
</div>
```

This is cleaner, more intuitive, and the visual representation of "these two pages interleave" is more obvious to users too — you see them next to each other rather than offset.

I'd say go for it: split `ThumbnailPanel` into a simpler `SplitModePanel` (essentially what it is today minus merge-specific props) and a new `MergeModeStrip` that's purpose-built for paired rows.
