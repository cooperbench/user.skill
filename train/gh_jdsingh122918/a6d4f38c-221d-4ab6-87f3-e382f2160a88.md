## Section 3: Self-Update Mechanism Two features: a **startup version check** (passive) and a `forge update` **command** (active). --- **Startup version check:** - On every CLI invocation, spawns a background check (non-blocking, doesn't slow startup) - Hits GitHub API: `GET /repos/jdsingh122918/forge/releases/latest` - Caches the result to `~/.forge/last-update-check` with a timestamp — skips the check if less than 24h since last check - If a newer version exists, prints a one-liner after command output: ``` A new version of forge is available: v0.3.0 (current: v0.2.0) Run `forge update` to upgrade. ``` - Never blocks, never auto-downloads in this mode --- **`forge update` command:** - Uses the `self_update` crate configured against `jdsingh122918/forge` GitHub releases - Detects current binary's target triple (compiled in at build time via `env!` or `cfg!`) - Downloads the matching `forge-{target}.tar.gz` - Verifies checksum against `sha256sums.txt` - Atomically replaces the running binary (self_update handles this — writes to temp file, then renames) - Prints: `Updated forge from v0.2.0 → v0.3.0` **Flags:** - `forge update --check` — just check, don't download (same as the startup check but explicit) - `forge update --force` — re-download even if already on latest --- **Auto-update opt-in:** Configured in `~/.forge/config.toml`: ```toml [update] auto = true # default: false check_interval = 24 # hours, default: 24 ``` When `auto = true`, the startup check silently downloads and replaces the binary in the background. The *next* invocation runs the new version. No restart mid-command. --- **Build-time version embedding:** `Cargo.toml` version (`0.2.0`) is the source of truth. The binary embeds it via `env!("CARGO_PKG_VERSION")`. CI tags must match (`v0.2.0` tag builds version `0.2.0`). CI validates this — fails the build if tag and Cargo.toml version disagree.
