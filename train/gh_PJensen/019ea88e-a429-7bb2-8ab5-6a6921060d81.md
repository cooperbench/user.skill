Architecturally: I would not inline it as the “real” fix. Inlining would make the local shape smaller, but it would preserve the deeper smell: `audioWiring.js` is becoming a hand-written event switchboard where every event listener knows too much about payload shape, sound IDs, spatial lookup, priority, volume, and special cases. The better direction is probably a display-layer audio routing system: ```js { event: "interaction", when: ({ action, result }) => action === "toggleDoor", sound: ({ result }) => result === "opened" ? "door:open" : "door:close", position: ({ targetId }, ctx) => ctx.getPosition(targetId), options: { priority: 1, volume: 1.25 }, } ``` Then `audioWiring.js` installs routes, not behavior. Rules still emit semantic gameplay events; audio stays outside rules; the display/audio layer owns interpretation. That scales to filters, criteria, fallbacks, cooldowns, random variants, material/identity selectors, muffling, spatial behavior, and debug tracing without turning every `world.on(...)` into another bespoke mini-adapter. So: yes to cleaning up `world.on('interaction', ...)`, but I’d avoid “just inline it” unless you want a tiny tactical cleanup. The architectural move is to make sound routing declarative and test the routing table/resolver, not exported one-off helper functions.
