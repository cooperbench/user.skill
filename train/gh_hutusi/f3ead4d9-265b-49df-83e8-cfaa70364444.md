Found the bug. It's a race condition in `App.tsx`:

In `handleSelectFile`:
1. `setSelectedFile(node)` is called immediately → React re-renders, mounting a **new** `Editor` with `key={node.path}` and `content=""` (empty, since the file hasn't loaded yet)
2. The `read_file` Tauri invoke completes asynchronously
3. `setFileContent(body)` is called → but the `content` prop update is ignored because Tiptap's `useEditor` **only uses `content` as the initial value on mount** — it doesn't react to prop changes

The fix: defer `setSelectedFile(node)` until after the content is loaded, so when the Editor mounts with the new `key`, it already has the correct content. React 18 batches the two state updates together.

**`bun test` vs `bun run test`**

Both work, but they're subtly different:
- `bun test` — calls Bun's built-in test runner directly (idiomatic, slightly faster)
- `bun run test` — executes the `test` script from `package.json`, which itself calls `bun test`

The current validate script uses `bun test` directly, which is correct. No change needed.

**Should `bun run build` be in validate/CI?**

Worth thinking through:

| What `bun run build` catches that `tsc --noEmit` misses |
|---|
| Vite bundler resolution errors (wrong import paths that tsc doesn't resolve the same way) |
| Missing assets or CSS modules |
| Plugin errors |

My take:
- **CI — yes, add it.** It's fast (~10s), catches real bundler issues, and is standard practice. You don't want to merge a PR that passes typecheck but fails to bundle.
- **Local `validate` — optional.** `tsc --noEmit` already catches most issues. Adding build to local validate makes it slower and slightly redundant for daily use. I'd keep them separate: `validate` for quick feedback, `build` as a one-off check.

So the CI step would become:
```
bun run validate   # typecheck + lint + test
bun run build      # bundler smoke-check
```
