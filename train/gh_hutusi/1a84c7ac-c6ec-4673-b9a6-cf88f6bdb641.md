## Why it's long but okay

The file is organized into **5 clearly-separated domains**, each with their own section dividers:

The domains are **not independent**. Three functions aggregate across multiple content types:

- `getAllTags()` — combines posts + flows + notes
- `buildSlugRegistry()` — combines posts + flows + notes + series
- `buildBacklinkIndex()` — combines posts + notes + flows

Splitting into `posts.ts`, `books.ts`, `flows.ts`, `notes.ts` would require cross-imports between them to support these aggregators — which risks circular dependencies and makes the import graph messier than the current single-file approach.

## My recommendation

Leave it as-is. A monolithic data access layer is a valid pattern when the domains share state and have cross-cutting aggregations. The section dividers already give you the "split" navigation benefit without the import graph complexity.

The refactoring effort is better spent on the UI layer (which is what we've been doing) than restructuring a well-organized data layer.
