Here are the main performance bottlenecks, ranked by impact:

---

## 1. Nginx configuration (highest impact, no code changes)

This is the most likely cause of slow page transitions. The static `out/` directory needs proper Nginx config:

```nginx
# Enable gzip compression
gzip on;
gzip_types text/html text/css application/javascript application/json image/svg+xml;
gzip_min_length 1024;

# Cache _next/static/ forever (content-hashed filenames)
location /_next/static/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

# Cache other assets
location ~* \.(webp|png|jpg|svg|woff2)$ {
    add_header Cache-Control "public, max-age=86400";
}
```

Also enable **HTTP/2** in Nginx — it multiplexes the many small JS chunks Next.js generates.

Without gzip, the uncompressed JS bundles (React + Next.js runtime + mermaid + KaTeX + syntax highlighter) can easily be 3–5MB transferred.

---

## 2. Mermaid is eagerly loaded on every post page

`mermaid` is ~1.5MB minified and is statically imported in `MarkdownRenderer.tsx:2` via `Mermaid.tsx:4`. This inflates every post's JS bundle, even posts with no diagrams.

It should use `next/dynamic`:

```ts
// MarkdownRenderer.tsx
const Mermaid = dynamic(() => import('@/components/Mermaid'), { ssr: false });
```

---

## 3. KaTeX CSS loaded globally

`app/layout.tsx:13` imports KaTeX CSS on every page (~280KB unminified). It should only load on posts with `latex: true` — move it into the post page layout, conditionally.

---

## 4. react-syntax-highlighter bundle

`CodeBlock.tsx` eagerly imports 17 language grammars. Consider switching to [`shiki`](https://shiki.style/) which runs at build time (zero client-side JS for syntax highlighting) or use the lighter `react-syntax-highlighter/dist/cjs/light` build.

---

**Bottom line**: Fix Nginx compression + cache headers first — that alone will likely make the biggest visible difference. Then address the Mermaid lazy loading.

Is it better to make Mermaid configurable, just like LaTeX? What do you think?

> AGENT

It's a reasonable idea, but I'd say **no — the current lazy loading is sufficient**, and here's why the two cases are fundamentally different:

**LaTeX _must_ be opt-in** because it changes the markdown parsing pipeline — `remark-math` and `rehype-katex` are added as plugins only when `latex: true`. Without the flag, `$...$` syntax just renders as plain text. The flag is functionally necessary, not just a performance hint.

**Mermaid doesn't change parsing** — it just intercepts the standard ` ```mermaid ` code fence, which is normal markdown regardless. No plugins need to be conditionally added.

**On the performance side**, with `next/dynamic` already in place:
- The 1.5 MB Mermaid bundle is a separate JS chunk
- That chunk is only fetched by the browser when a `<Mermaid>` component actually renders (i.e., the post has a mermaid block)
- Posts with no mermaid blocks never trigger the download — the dynamic import reference in the bundle is just a tiny pointer, not the library itself

A `mermaid: true` flag would marginally reduce that pointer from the bundle of non-mermaid posts, but the practical impact is negligible compared to the DX cost of requiring authors to remember an extra frontmatter field.

**In short:** LaTeX needs a flag to work correctly; Mermaid already works efficiently without one.

> DEVELOPER

what is this difference with rewrite ?

> AGENT

Good question. Two main differences:

**Behavior visible to the client:**
- `return 301 /feed.xml` — sends an HTTP 301 immediately, client follows it. The browser/RSS reader ends up at `/feed.xml` and updates its stored URL
- `rewrite ^/feed$ /feed.xml` — by default also sends a redirect (302), but you can add `permanent` for 301. Still a redirect, so same end behavior — but more steps internally

**Performance:**
- `return` is evaluated during Nginx's rewrite phase and exits immediately — no regex engine involved
- `rewrite` always runs a regex match, even for a simple exact string like `/feed`. For a single rule it's negligible, but `return` is the idiomatic Nginx way for simple redirects

**When to use `rewrite` instead:**
- When you need to **capture groups** from the URL, e.g. `rewrite ^/rss/(.*)$ /feed.xml?tag=$1`
- When you need to **silently serve a different file** without redirecting (using `rewrite ... last` or `rewrite ... break` — no redirect sent to client)

For our case (`/feed` → `/feed.xml`) there's nothing to capture and we want an explicit redirect, so `return 301` is the right tool.

> AGENT

For this project specifically, `trailingSlash: true` is the **right choice**, and the comment in `next.config.ts` explains why:

```ts
// Set to true so pages export as slug/index.html, which coexists with
// asset directories (slug/images/) and avoids 403 errors on trailing slash
```

This is the key constraint — posts can have co-located images in a `slug/images/` folder. With `trailingSlash: false`, Next.js exports the page as `slug.html`, but then `slug/images/` is a sibling directory. Nginx sees both a file `slug.html` and a directory `slug/`, which creates ambiguity and can cause 403 errors when someone visits `/slug/`.

With `trailingSlash: true`, pages are exported as `slug/index.html`, so the page and its images live together cleanly under the same directory — no conflict.

---

**General tradeoffs (outside this project):**

| | `trailingSlash: true` | `trailingSlash: false` |
|---|---|---|
| Output | `slug/index.html` | `slug.html` |
| URLs | `/posts/my-post/` | `/posts/my-post` |
| Nginx serving | Simpler (`index` directive) | Simpler (`try_files $uri.html`) |
| SEO | Both fine if consistent | Both fine if consistent |
| Co-located assets | Works naturally | Conflicts with same-name directories |
| Common convention | Apache/traditional servers | Modern APIs and frameworks |

For a static site with co-located media (which amytis supports), `true` is the safer default. For an API-style or SPA-style site with no static assets, `false` is more conventional.

**Bottom line: keep `true` for amytis.**

> DEVELOPER

what is the default of Next.js? why?

> AGENT

The default is **`false`** (no trailing slash) — URLs like `/posts/my-post`.

**Why Next.js chose this default:**

1. **Web convention** — Most modern web apps, REST APIs, and frameworks use extensionless URLs without trailing slashes (`/about`, `/posts/my-post`). It follows the general direction of the web moving away from file-system-style URLs (`/about.html`, `/posts/my-post/`)

2. **Next.js is primarily a server framework** — When running with a Node.js/Edge server (not static export), pages are served dynamically with no concept of files or directories. There's no filesystem reason to prefer one over the other, so the cleaner-looking URL wins

3. **`trailingSlash: true` exists mainly for static export compatibility** — It was added specifically to work well with static hosts (Apache, S3, Netlify, etc.) that serve `index.html` from directories. It's an escape hatch, not the intended default

**Why this project uses `true`** — purely because of the co-located image directory constraint (`slug/images/`). Without that constraint, `false` would be the natural choice and would match Next.js's own default.

So the irony is: our current setup uses `trailingSlash: true` in Next.js but then has Nginx strip the slash — effectively working against the Next.js export structure just to get the URL appearance that Next.js itself defaults to. It works, but it's a workaround on top of a workaround.
