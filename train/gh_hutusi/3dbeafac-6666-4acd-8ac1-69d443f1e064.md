## Implementation Plan: File Read/Write (Roadmap Item 2)

### Architecture Decision: Rust Commands over JS Plugin-FS

**Recommendation: Use two new Rust `#[tauri::command]` functions (`read_file` and `write_file`) rather than `@tauri-apps/plugin-fs`.**

Rationale:
- `tauri-plugin-fs` is not yet installed — it would require adding a Rust dependency, a JS package, and registering it in `lib.rs`, plus configuring fine-grained path-scoped permissions. That is more ceremony than the task needs.
- The existing `open_workspace` command already uses `std::fs` directly in Rust. Keeping file I/O in the same pattern is consistent and simpler.
- Rust commands also give a natural place to do frontmatter stripping server-side in the future if desired (though for now stripping will happen in TypeScript, which is fine).
- The only capability change needed is adding `"core:default"` which is already present — no additional plugin permission wiring required.

The tradeoff: if you later need file watching or streaming large files, the FS plugin would be better. For this use case (reading and writing markdown files up to a few hundred KB) Rust `std::fs::read_to_string` / `std::fs::write` is perfectly appropriate.

### Step 2: Frontmatter Utility (TypeScript)

export function parseFrontmatter(raw: string): {
  frontmatter: string; // the raw "---\n...\n---\n" block, or ""
  body: string;        // everything after the frontmatter
}

/** Re-joins frontmatter and body for writing back to disk. */

The regex to match frontmatter:

```
/^---\r?\n([\s\S]*?)\r?\n---\r?\n?/
```

`parseFrontmatter` tests this regex against the start of the string. If it matches, `frontmatter` is the full match (including the delimiters), `body` is `raw.slice(match[0].length)`. If it does not match, `frontmatter` is `""` and `body` is the full raw string.

`joinFrontmatter` returns `frontmatter + body` (frontmatter already contains the trailing newline).

### Edge Cases and Gotchas

**Race condition on rapid file switching:** If the user clicks file A, then immediately file B, two `invoke("read_file")` calls are in flight. The stale response from file A must not overwrite `fileContent` for file B. Guard with a cancellation token or compare `selectedFile.path` at the time of the `await` vs. at the time the response arrives.

The simplest guard in `handleSelectFile`:

```typescript
async function handleSelectFile(node: FileNode) {
  setSelectedFile(node);
  setWordCount(0);
  setFileContent(""); // clear while loading
  const raw = await invoke<string>("read_file", { path: node.path });
  // Only apply if the selection hasn't changed by the time we get here:
  setSelectedFile(current => {
    if (current?.path === node.path) {
      const { frontmatter, body } = parseFrontmatter(raw);
      setFrontmatter(frontmatter);
      setFileContent(body);
    }
    return current;
  });
}
```

**Pending save on file switch:** When the user switches files, cancel any pending save timer for the previous file and flush it immediately, to avoid losing the last few keystrokes.

```typescript
async function handleSelectFile(node: FileNode) {
  // Flush any pending save for the previous file before switching
  if (saveTimerRef.current) {
    clearTimeout(saveTimerRef.current);
    saveTimerRef.current = null;
    // Optionally trigger an immediate save of the outgoing file here
  }
  // ... rest of load logic
}
```

For the MVP, flushing without saving is acceptable since saves fire at 750ms and users tend to pause before clicking a different file. An immediate flush-save is cleaner UX but adds complexity.

**`tiptap-markdown` and StarterKit overlap:** `StarterKit` includes all core marks/nodes. `tiptap-markdown` adds a serializer layer on top; it does not replace extensions. No conflict expected.

**Line endings:** `std::fs::read_to_string` on macOS produces `\n`. The frontmatter regex handles `\r?\n` for cross-platform correctness.

**Error handling:** `invoke("read_file")` returns a `Result<String, String>` from Rust. Wrap the call in `try/catch` on the TypeScript side and display a toast or status bar message on failure.

### Overview of the Approach

The strategy uses a `data-theme` attribute on `<html>` as the single source of truth for the active theme. CSS custom properties in `global.css` are organized into two token sets — one under `:root` (light) and one under `[data-theme="dark"]` (dark). A custom React hook (`useTheme`) manages detection of system preference, reading/writing the `localStorage` preference, and applying the attribute. The toggle button lives in the `StatusBar` because it is always visible, keeps the editor chrome minimal, and the status bar already exists as a persistent shell element.

### Step 2 — Create `src/lib/theme.ts` (the `useTheme` hook)

> Note: The existing `src/theme.ts` is a TypeScript constants file used nowhere visible in the current components — it is not a hook. The new file is placed in `src/lib/` alongside `types.ts` to match the project's lib-pattern. The name collision is avoided by the path difference.

The hook encapsulates three concerns:

**A. Reading the stored preference**

```
type ThemePreference = "light" | "dark" | "system";

```

On first load, `localStorage.getItem(STORAGE_KEY)` is read. If absent or `"system"`, the hook defers to `window.matchMedia("(prefers-color-scheme: dark)")`.

**B. Applying the `data-theme` attribute**

A helper `applyTheme(resolved: "light" | "dark")` sets `document.documentElement.setAttribute("data-theme", resolved)` or removes the attribute for light (since `:root` defaults to light, omitting the attribute is equivalent and keeps the DOM tidy). Either convention works; setting an explicit `data-theme="light"` is slightly more explicit and preferable for debugging.

**C. Watching for system changes**

```ts
const mql = window.matchMedia("(prefers-color-scheme: dark)");
mql.addEventListener("change", handler);
// cleanup: mql.removeEventListener("change", handler)
```

This listener only takes effect when the stored preference is `"system"` (or absent). When the user has manually chosen `"light"` or `"dark"`, the listener fires but the stored preference wins.

**Hook signature:**

```ts

  resolvedTheme: "light" | "dark";    // what is actually showing
  setPreference: (p: ThemePreference) => void;
}
```

`setPreference` writes to `localStorage`, recomputes the resolved theme, and calls `applyTheme`. The hook initialises with `useState(() => ...)` to read localStorage synchronously on mount (important for avoiding a re-render flash — see Step 5).

### Step 5 — Prevent Flash of Wrong Theme (FOWT)

This is the most important edge case. The React app initialises after the HTML document is parsed, which means there is a brief moment where the theme attribute has not yet been set. If the user has dark mode stored but the default CSS is light, they see a flash of light before React mounts.

**Solution: inline `<script>` in `index.html`**

Place a small synchronous script in `<head>` — before any stylesheets — that reads `localStorage` and `prefers-color-scheme` and sets `data-theme` on `<html>` immediately:

```html
<script>
  (function() {
    var pref = localStorage.getItem("ovid-theme");
    var dark =
      pref === "dark" ||
      (pref !== "light" && window.matchMedia("(prefers-color-scheme: dark)").matches);
    document.documentElement.setAttribute("data-theme", dark ? "dark" : "light");
  })();
</script>
```

This script runs synchronously before the browser paints anything. It must be placed after `<meta charset>` but before any `<link rel="stylesheet">` (though in a Vite app, stylesheets are injected by the bundler at runtime anyway — the script just needs to be in `<head>`). This pattern is the same one used by Next.js, Remix, and Docusaurus for zero-flash theming.

The script duplicates the logic from the React hook. That duplication is intentional and necessary — it is a tiny pure function with no dependencies.

## Implementation Plan: Frontmatter Parsing and Properties Panel

### 1. YAML Parsing Strategy

**Use `js-yaml` rather than a hand-rolled parser.**

Rationale:
- The Amytis frontmatter uses standard YAML — strings, booleans, ISO dates, and arrays of strings for `tags`. `js-yaml` handles all of these correctly out of the box, including the subtle edge cases (e.g., `draft: yes` parsing as a boolean, bare date strings like `2024-01-15` being coerced to `Date` objects).
- A regex/split-based hand-rolled parser can handle the happy path, but it will silently misparse multi-line values, quoted strings with colons, and inline arrays. Since the files on disk are the source of truth, a silent misparsed write would corrupt data.
- `js-yaml` is 18 KB minified, has zero runtime dependencies, and is already used inside half the Vite/Rollup ecosystem, so it will be deduplicated in the bundle anyway.
- Install: `bun add js-yaml && bun add -d @types/js-yaml`

**Parsed type.** Frontmatter values will be typed as a discriminated set of scalars:

```
type FrontmatterValue = string | boolean | number | string[] | null;
type ParsedFrontmatter = Record<string, FrontmatterValue>;
```

Dates returned by `js-yaml` as `Date` objects will be converted to ISO strings immediately on parse, so the rest of the app never sees a `Date`.

### 2. Changes to `src/lib/frontmatter.ts`

This file becomes the single source of truth for all frontmatter logic. Three additions:

**a. `parseYamlFrontmatter(raw: string): ParsedFrontmatter`**
- Extracts the YAML block between the `---` fences (already done by the regex).
- Calls `js-yaml`'s `load()` on the inner YAML text.
- Normalises `Date` objects to ISO strings.
- Returns an empty object if parsing fails or frontmatter is absent.

**b. Export `FrontmatterValue` and `ParsedFrontmatter` types.**

**c. Keep `parseFrontmatter` and `joinFrontmatter` exactly as-is** — they deal with the raw string for round-trip safety, and nothing about them needs to change.

The split between "raw string for disk" (`frontmatterRef`) and "parsed object for UI" (`parsedFrontmatter` state) is deliberate: the raw block is always written back verbatim, so reformatting or key-ordering changes by `js-yaml` can never touch the on-disk file.

### 3. State Location — `App.tsx`

**Keep parsed frontmatter as a `useState` in `App.tsx`, parallel to the existing `frontmatterRef`.**

```
const [parsedFrontmatter, setParsedFrontmatter] = useState<ParsedFrontmatter>({});
```

Reasons:
- `App.tsx` already owns all file-lifecycle state. Adding a parallel parsed view is consistent with how `fileContent` and `wordCount` are managed.
- The `PropertiesPanel` component will receive `parsedFrontmatter` as a prop — no context or external store needed at this scale.
- Frontmatter is per-file; it gets reset on file switch, which already happens in `handleSelectFile`.

The update path in `handleSelectFile`:

```
const { frontmatter, body } = parseFrontmatter(raw);
frontmatterRef.current = frontmatter;
setFileContent(body);
setParsedFrontmatter(parseYamlFrontmatter(raw)); // new line
```

Also reset in `handleOpenWorkspace` and clear when no file is selected:

```
setParsedFrontmatter({});
```

**No write-back path for now** — the properties panel is read-only in this iteration.

### 4. New Component: `src/components/PropertiesPanel.tsx`

**UI placement: inline "properties bar" above the editor, collapsible.**

Rationale given the "minimal chrome" principle:
- A right sidebar would permanently narrow the 680 px prose column, which fights the typography-first principle. It would also require a second resizable pane.
- An inline bar above the editor sits inside the `editor-wrapper` column, collapses to zero height when closed, and does not touch the prose width.
- The bar is only visible when a file is open and has frontmatter. If the file has no frontmatter at all (empty `{}`) the bar renders nothing — zero chrome for plain files.
- A small toggle button at the top-right of the editor area (or a keyboard shortcut, e.g. `Cmd+Shift+P`) collapses/expands it.

**Layout of the bar:**

The bar renders fields as a horizontal pill row for a compact footprint. Common fields get a fixed display label; unknown fields show their raw key name. The ordering convention: `title` first (if present), then `date`, `tags`, then any remaining fields alphabetically.

Field rendering rules:
- `title` — rendered as plain text (it's often redundant with the H1 but still useful to see).
- `date` — formatted as a human-readable date string using `Intl.DateTimeFormat`.
- `tags` — rendered as individual tag chips.
- `draft: true` — rendered as a "Draft" badge with a distinct background.
- All other string/number values — `key: value` as monospaced pill.
- `null` or empty array — field is skipped silently.

**Props:**

```ts
interface PropertiesPanelProps {
  frontmatter: ParsedFrontmatter;
  isOpen: boolean;
  onToggle: () => void;
}
```

The `isOpen` toggle state lives in `App.tsx` as `const [propertiesOpen, setPropertiesOpen] = useState(true)`. It persists across file switches (user preference) but defaults to open so first-time users see it.
