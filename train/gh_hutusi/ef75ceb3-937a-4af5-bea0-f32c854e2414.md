Here's the full picture:

**Why 404s happen:** `getAllTags()` normalizes all tags to lowercase when building the tag index, so `generateStaticParams()` only generates static pages for lowercase slugs (e.g., `/tags/javascript`). But `PostList.tsx` and `SeriesCatalog.tsx` generate tag links using raw frontmatter tags without lowercasing — so `tags: ["JavaScript"]` produces a `/tags/JavaScript` link that has no matching page.

**`Tag.tsx` already handles this correctly** (`tag.toLowerCase()` in the href) — `PostList.tsx` and `SeriesCatalog.tsx` just aren't using it for their inline tag links.

**My recommendation: yes, make URLs consistently lowercase** — but only at the URL level, not in the display text. Lowercasing tag names like `JavaScript` or `TypeScript` in display would be wrong; they're proper nouns. The data layer (`getPostsByTag`, `getAllTags`) already does case-insensitive matching correctly. The fix is small: add `.toLowerCase()` to the two places that are missing it.

The alternative — normalizing tags to lowercase at parse time in `markdown.ts` — would break display text and is more invasive for no benefit.

what is different posts use "React" and "react" ?

> AGENT

That works correctly. The `seen` Set is created fresh inside `addTags` for each call, so it only deduplicates within a single document's tag list. Cross-document counting is unaffected:

- Post A tags `["React"]` → `addTags` called → `counts["react"] = 1`, `display["react"] = "React"`
- Post B tags `["react"]` → `addTags` called with a **new** `seen` Set → `counts["react"] = 2`, `display["react"]` unchanged (first-seen wins)

Result: count = 2 ✓, display = "React" ✓. The fix only prevents overcounting when a *single* document has both `"React"` and `"react"` in its own tags array.

> DEVELOPER

is the Post B also shows "React"? what do you think?

> AGENT

Yes — and that's by design. The `display` map uses **first-seen casing globally across all documents**. So whichever document is processed first sets the canonical display form, and all subsequent documents with the same tag (regardless of their casing) just increment the count without changing `display`.

Whether that's the right behavior is debatable:

- **First-seen wins (current)**: deterministic but arbitrary — depends on file processing order, which is typically alphabetical by filename. "react" in `post-a.mdx` processed before `post-b.mdx` with "React" would display as "react" everywhere.
- **Most-common casing wins**: more representative but requires a two-pass approach (count all casings first, then pick the winner).
- **Prefer capitalised form**: pick whichever casing has the most uppercase — "React" beats "react". Simple and usually matches the "proper noun" intent.

In practice, **the real fix is for content authors to use consistent casing in their frontmatter**. The code already handles the URL routing correctly (always lowercase); the display form is a cosmetic choice. First-seen is good enough for most cases, and adding complexity to pick "the best" casing is probably over-engineering.

I'd leave the current behavior as-is and note it in a comment. Want me to add that clarifying comment to the code?
