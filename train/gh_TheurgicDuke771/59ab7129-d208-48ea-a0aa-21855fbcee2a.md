Repo is **public**, which removes the biggest Docker Hub drawback (image secrecy) — your source is already open, and per the project's no-creds-in-tracked-files rule secrets are injected at runtime (Key Vault / Container Apps secrets), not baked into the image. So a public image leaks nothing new. That said, there are real operational drawbacks for the **production pull path**: **Drawbacks of Docker Hub vs ACR (for the prod deploy)** 1. **Pull rate limits.** Docker Hub throttles (anon 100/6h per IP, authed-free 200/6h, tightening over time). ACA autoscaling spins up replicas + the worker + the migrate job — each a pull. Cold-start/scale-out can hit the limit and stall a rollout. ACR (and GHCR for your own images) doesn't throttle you. 2. **Auth is a stored credential, not managed identity.** ACA↔ACR uses a system-assigned MI with `AcrPull` — no secret. Docker Hub means storing a username + PAT as a Container Apps registry credential — another long-lived secret to rotate, which cuts against the "managed identity, no literals" posture in [deploy/README.md](deploy/README.md). 3. **Cross-cloud latency + outside the Azure trust boundary.** ACR co-located in your ACA region = faster pulls, no internet egress, and it sits inside Azure RBAC + Defender for Cloud vuln scanning (relevant to your pre-deploy security gate). Docker Hub pulls cross the internet and scan separately (Scout). 4. **CI rewiring.** `deploy.yml` (#379) is built around ACR (`az acr login`, `ACR_LOGIN_SERVER`/`ACR_NAME` vars). Switching means changing the login step + image refs + adding ACA registry creds for Docker Hub — modest but real rework of apply-ready scaffolding. **The angle in Docker Hub's favor** — it's vendor-neutral, which actually *aligns* with your anti-lock-in ethos (ADR 0010/0013: "Azure is one impl behind each seam"), and a neutral public registry is a natural home for the **BYOL/marketplace image** (ADR 0013) you'll want …
