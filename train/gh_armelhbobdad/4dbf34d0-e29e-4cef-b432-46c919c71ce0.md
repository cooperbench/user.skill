25	3. **Known constraint — PR opened via `GITHUB_TOKEN` may NOT trigger `quality.yaml`; the workflow MUST force-trigger checks.** Per GitHub Actions documentation (`https://docs.github.com/en/actions/using-workflows/triggering-a-workflow#triggering-a-workflow-from-a-workflow`): "When you use the repository's `GITHUB_TOKEN` to perform tasks, events triggered by the `GITHUB_TOKEN`, with the exception of `workflow_dispatch` and `repository_dispatch`, will not create a new workflow run." A `pull_request` event opened by the bot therefore SHALL NOT fire `quality.yaml` (which triggers on `pull_request: branches: ["**"]` per `.github/workflows/quality.yaml:16-18`). Without those runs, the 7 required checks (`prettier`, `eslint`, `markdownlint`, `validate (ubuntu-latest)`, `validate (windows-latest)`, `python (ubuntu-latest)`, `python (windows-latest)`) remain in `expected` state forever — `gh pr checks <pr_number>` would show them missing, and the ruleset blocks merge indefinitely. **The dev agent SHALL choose and implement ONE of the following three remediation paths** (ordered by recommended preference), document the chosen path in the Dev Agent Record, and wire it into `release.yaml`:

35	4. **Workflow waits for all 7 required status checks to conclude.** After the force-trigger step at AC #3, `release.yaml` SHALL poll `gh pr checks <pr_number>` until every check in the ruleset's `required_status_checks` list reaches `conclusion in {success, failure, skipped, cancelled, timed_out, action_required}`. The poll SHALL use a simple bash loop: `while true; do ... gh pr checks ... ; done` with a `sleep 30` between iterations and a hard timeout of 20 minutes (Story 3.2's successful alpha cut ran `quality.yaml` in ~5-8 min; 20 min gives 2.5-4× headroom for matrix-runner contention). On timeout, the workflow SHALL exit non-zero with `::error::PR <pr_number> checks did not complete within 20m. PR left open for manual inspection; re-run release.yaml after investigation.` (NOT auto-close — per epic AC "if checks fail on the bot PR, the workflow should exit and leave the PR open for manual inspection — not auto-close"). On ALL checks concluding with `success`, the workflow proceeds to AC #5. On ANY check concluding with `failure` / `action_required` / `cancelled` / `timed_out`, the workflow SHALL exit non-zero with `::error::PR <pr_number> has failing check(s). PR left open for manual inspection. Re-run release.yaml after the underlying defect is fixed on main.` AND the PR SHALL NOT be merged by this run (branch protection would block it anyway, but defense-in-depth). The 7 required check names SHALL be enumerated as a bash array at the top of the wait step — hard-coded. If the ruleset's check list ever changes, this array and `release.yaml` must be updated in lockstep (drift protection via a CI-asserted diff belongs in a follow-up hardening story; out of Story 3.4 scope).

43	8. **Tag creation moves to AFTER PR merge (ordering change).** The current `release.yaml § Create and push tag` step (lines 226-233) pushes `v<new_version>` to origin BEFORE `Push commit to main` (lines 235-237) and BEFORE the npm publish step (lines 246-255). After Story 3.4's refactor: the tag step SHALL run AFTER the PR merge completes (AC #7) and BEFORE the npm publish step. Rationale: the tag must point at a commit that is actually on `main` — if the tag is pushed before the PR merges (as today), it points at the orphaned temp-branch commit which IS on the temp branch but NOT yet on `main`. After the PR auto-merges, the bot PR's commit becomes the new `main` tip (merge-commit path preserves the SHA per AC #7); the tag pushed now points at a `main`-reachable commit. New ordering in `release.yaml`: `Commit version bump` → **[NEW]** `Push to temp branch` → `Open PR` → `Force-trigger checks` → `Wait for checks` → `Wait for approval` → `Auto-merge PR` → **[MOVED]** `Create and push tag` → `Publish to npm via OIDC trusted publishing` → `Create GitHub Release` → `Summary`. **Dependency on temp-branch commit SHA:** after the PR auto-merges via `--merge` (merge-commit), the bot's commit SHA on `main` IS the same SHA that was on the temp branch (merge-commit creates a NEW merge commit but PRESERVES the original commits underneath). The tag creation step SHALL capture this via: `git fetch origin main && NEW_COMMIT_SHA=$(git rev-parse origin/main) && git tag -a v${{ steps.version.outputs.new_version }} -m "Release v${{ steps.version.outputs.new_version }}" $NEW_COMMIT_SHA` — this anchors the tag on the merged bot commit (the parent of the merge commit), NOT on the merge commit itself. OR alternatively: anchor the tag on the merge commit directly (simpler; matches what `gh release` expects; the compare URL Generate-release-notes step at `release.yaml:217` is already "from previous_tag to HEAD" which would work either way). Dev agent decides: **recommend the merge-commit** as the tag anchor (simpler, and future `git describe --tags` from `main` returns the tag cleanly). Commit that decision into the workflow + this story's Dev Notes at implementation time.

210	### Context — why this story exists
211	
212	Story 3.2's alpha cut (2026-04-21) succeeded because it dispatched from `feat/release-workflow` and took the "Skip main push" path — the `Push commit to main` step (`release.yaml:235-237`) was NEVER exercised before Story 5.2's attempt at `v1.0.0-rc.1` on 2026-04-23. Story 5.2's first dispatch (run `24829166764`) was therefore the first time the step fired on a real `main`-dispatched cut, and it failed with `GH013: Repository rule violations`. This is a latent defect from Story 3.1 that escaped Story 3.2's validation (Story 3.2 explicitly tested the alpha/feature-branch path) and Story 3.3's merge review (merge + grep for no-double-publish verified file STATE, not workflow EXECUTION on main).
213	
214	**Generalization:** a workflow's step-level behavior is validated only when that step actually runs end-to-end. Post-v1.0.0 hardening candidate (tracked in `deferred-work.md` for now): add a lint-like CI check that greps `release.yaml` for `if: github.ref == 'refs/heads/main'` steps and flags any step that has NOT been exercised on a main-dispatched cut within the last N releases.

216	### Why Option B (PR auto-merge) was chosen over Options A / C / D
217	
218	From issue #198's analysis:
219	
220	- **Option A — custom GitHub App with ruleset-bypass rights.** Heaviest. Admits a bot as a first-class actor, bypasses ruleset. Introduces a new integration to maintain + rotate. Rejected: overkill for a user-owned repo with one maintainer.
221	- **Option B — refactor to PR auto-merge.** Chosen. No new credentials. Native GitHub pattern. Strengthens audit trail. Re-runs CI on the release commit.
222	- **Option C — PAT with bypass rights + ruleset bypass entry.** Rejected: the ruleset's `bypass_actors` list already admits `RepositoryRole: 5` (Admin); adding a user-scoped PAT would require the PAT owner to ALSO be admin, AND grant the PAT bypass — this duplicates the existing admin-bypass-via-PR rule without buying anything. And a PAT is a rotation burden.
223	- **Option D — transfer the repo to an org and use org-level rulesets with GitHub Actions global-integration bypass.** Rejected: massive blast radius (org creation, repo transfer breaks incoming links, changes the CI permissions model).
224	
225	Option B is the minimum-viable-change that resolves issue #198 without broadening surface area.

228	
229	This is the biggest unknown. GitHub's documented behavior: `GITHUB_TOKEN`-authored PR events do NOT fire downstream workflows. But the workarounds (`workflow_dispatch` re-trigger, close-and-reopen, PAT) each have caveats. Budget a real spike (Task 3) to resolve empirically; do NOT ship the refactor on assumption. If path (3.i) fails under live conditions, the refactor must be patched before Story 5.2 resumes — fall-forward, not rollback.

231	### Tag-push ordering is load-bearing for `git describe`
232	
233	Today (pre-3.4): tag push at `release.yaml:226-233` is BEFORE `Push commit to main` at `:235-237` is BEFORE `Publish to npm via OIDC trusted publishing` at `:246-255`. A future maintainer running `git describe --tags --abbrev=0` on `main` after a release expects the last tag to be reachable from `main`.
234	
235	In the pre-3.4 world, this works because `Push commit to main` runs AFTER the tag push but the tag was created at the commit that would become `main`'s new tip — so post-push, the tag IS reachable.
236	
237	Post-3.4 (per AC #8): the tag is created AFTER the PR auto-merges, anchored on `origin/main`'s new tip. `git describe --tags` from `main` returns the new tag correctly. The key subtlety: the auto-merge with `--merge` preserves the original bot commit as the parent of the merge commit; the tag MAY be anchored either on (a) the merge commit itself (simpler; `main` tip) or (b) the bot's original commit (the parent). Recommendation: anchor on the merge commit (AC #8 recommends this). A `git log vX.Y.Z^..vX.Y.Z` sanity-check after cut confirms the tag is on the expected commit.
