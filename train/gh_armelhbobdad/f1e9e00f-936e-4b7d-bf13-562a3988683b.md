🏗️ **Morgan (Module Builder):** Right — let me cut straight to the architecture. The `sidecar_path` bug is a **module configuration contract violation**. When `module.yaml` declares a config variable, the installer MUST write it to the installed `config.yaml`, period. `prompt: false` means "don't ask the user, just use the default" — it does NOT mean "skip this variable entirely." That's a clear installer bug, not an SKF bug.

**My recommendation: Option A is the only clean fix.** But here's the critical nuance — the fix lives in the **BMAD Core installer**, not in SKF itself. SKF's `module.yaml` is correctly defined. The installer is the one failing to honor `prompt: false` semantics.

Option B — workflow-level fallback — would be **technical debt wrapped in a band-aid**. You'd be duplicating resolution logic across 17 files that reference `{sidecar_path}`. And every future module that uses `prompt: false` would hit the same wall.

However — and this is important — since we're inside the SKF module repo and don't control the Core installer release cycle, we may need a **defensive workaround** in SKF's workflows until Core is patched. I'd recommend a single resolution check in the agent's `critical_actions` rather than scattering it across workflows.

🔬 **Dr. Quinn (Creative Problem Solver):** *AHA* — you've both identified two of the three legs of this bug, but there's a third one nobody's mentioned.

Look at the **agent spec** itself — `forger.agent.yaml` lines 44-45:

```yaml
critical_actions:
  - "Load COMPLETE file {sidecar_path}/preferences.yaml"
  - "Load COMPLETE file {sidecar_path}/forge-tier.yaml"
```

If `{sidecar_path}` doesn't resolve in config, these critical actions silently fail too. The agent boots up thinking it loaded preferences and tier data, but it loaded *nothing*. The agent's entire state awareness is compromised before any workflow even starts.

Now — let me map the **full impact chain**:

1. **Root cause:** Installer skips `prompt: false` variables
2. **First-order effect:** `{sidecar_path}` unresolved in config
3. **Second-order effects:**
   - Agent critical_actions fail silently → no tier awareness, no preferences
   - 7/8 workflow inits degrade silently → Quick tier fallback
   - `qmd_collections` registry lookups fail → semantic capabilities lost
   - `batch-state.yaml` path fails → batch workflows can't checkpoint
4. **Third-order effect:** User gets working output that *looks* correct but is compiled at the wrong tier with missing capabilities — **the worst kind of bug** because nothing appears broken.

The todo file lists the impacts but **misses** these:
- `batch-state.yaml` checkpoint failure in `create-skill` steps 01 and 08
- `qmd_collections` registry reads in `brief-skill` step-05, `update-skill` step-03, `audit-skill` steps 02 and 04, `create-stack-skill` step-04
- The agent-level critical_actions failure

**My three-part fix recommendation:**
1. **Core installer fix** — honor `prompt: false` (file this upstream)
2. **Defensive guard in SKF** — add sidecar_path resolution validation to the agent's init or a shared init pattern
3. **Fail-loud, not fail-silent** — every forge-tier.yaml load should follow the `analyze-source` HARD HALT pattern
