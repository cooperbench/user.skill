### 1. Missing Angles — Things Not Yet Discussed

**A. Confidence Tier for cocoindex-code results**

The system has T1 (AST), T1-low (source-read), T2 (QMD), T3 (external). Where do cocoindex-code semantic search results land? They're structurally different from all four:
- Not AST-parsed (not T1)
- Not raw source reading (not T1-low)
- Not temporal/knowledge (not T2)
- Not external docs (not T3)

**Question:** Do we need a **T1-semantic** tier? Or do we treat ccc results as discovery pointers that get validated by ast-grep into T1?

**B. QMD Registry Architecture — Does ccc Need a Registry?**

QMD has a producer/consumer/janitor model with `qmd_collections` in `forge-tier.yaml`. cocoindex-code has its own persistent index (`.cocoindex_code/cocoindex.db`). These are different state management models:
- QMD: workflow-managed collections (explicit add/remove/embed)
- ccc: daemon-managed project index (auto-incremental, persistent)

**Question:** Should ccc projects be registered in `forge-tier.yaml` alongside `qmd_collections`? Or is the daemon self-managing enough?

**C. The Rejected "Source Clone Indexing" Candidate**

`qmd-registry.md` explicitly **rejected** indexing raw source code into QMD: *"Freshness problem. A cloned repo is a snapshot pretending to be current."* cocoindex-code does exactly this — indexes source code — but solves the freshness problem via incremental indexing. Does this reopen the rejected candidate under different terms?

**D. Verification Command for Tier Detection**

`step-01-detect-and-tier.md` checks `ast-grep --version`, `gh --version`, `qmd status`. What's the verification command for ccc? `ccc --version`? `ccc status`? This needs defining.

**E. The `qmd_bridge` Conceptual Interface Pattern**

QMD and ast-grep use `qmd_bridge.*` and `ast_bridge.*` as conceptual interfaces that resolve to MCP tools or CLI at runtime. cocoindex-code would need a `ccc_bridge.*` interface following the same pattern.

**F. Collection Gate vs. Persistent Index**

The QMD Collection Gate principle says *"A new collection type is justified ONLY when a specific workflow step performs a programmatic search against it."* ccc's index isn't a collection — it's a persistent project-level index. Does the gate principle apply? Or is ccc exempt because it manages its own lifecycle?

Honest take: **yes, `ccc --version` first, then `ccc status`**. Here's why:

**The two checks answer different questions:**

| Check | Question | Failure meaning |
|---|---|---|
| `ccc --version` | Is the binary installed and executable? | ccc not installed → `{ccc: false}`, skip everything |
| `ccc status` | Is the daemon running and responsive? | Binary exists but daemon is down → recoverable |

**The practical scenario that matters:** ccc is a daemon-based tool. Unlike ast-grep (stateless binary — runs, returns, exits), ccc has a persistent process. A user can have ccc installed but the daemon stopped. If we only check `ccc status` and it fails, we'd set `{ccc: false}` and assign Forge tier — even though the tool IS available and step-01b could start the daemon via `ccc index`.

**The two-step pattern:**

```
### 7. Verify Tool: ccc

**Step A:** Run `ccc --version`
- If fails: record {ccc: false}. Skip Step B.
- If succeeds: record version string. Continue to Step B.

**Step B:** Run `ccc status`
- If daemon running: record {ccc: true, ccc_daemon: "running"}
- If daemon not running: record {ccc: true, ccc_daemon: "stopped"}
  — ccc is available but daemon needs starting. Step-01b will handle this.
- If error: record {ccc: true, ccc_daemon: "error"}
  — binary works but something is wrong. Step-01b will attempt recovery.
```

**Why this is better than `ccc status` alone:**

1. `--version` is a cheap fast-fail — sub-second, no daemon needed. If ccc isn't installed, we don't waste time trying to reach a daemon that doesn't exist
2. `status` after `--version` gives us daemon health as **actionable metadata**, not a binary pass/fail. The tier detection records `{ccc: true}` (tool available) and the daemon state tells step-01b whether it needs to start/recover the daemon
3. It's consistent with the existing pattern: ast-grep and gh use `--version` for binary verification. ccc uses `--version` for binary verification PLUS `status` for daemon health — which is appropriate because ccc has a daemon and they don't

**The one counter-argument I considered:** "Just use `ccc status` — if the binary doesn't exist, it fails anyway." True, but the error mode is ambiguous: "command not found" vs "daemon not responding" are different problems with different remediation. Separating the checks gives the report step (step-04) actionable information: "ccc installed but daemon needs starting" vs "ccc not installed."

So yes — `ccc --version` then `ccc status`. The two-step check is the right call for a daemon-based tool.
