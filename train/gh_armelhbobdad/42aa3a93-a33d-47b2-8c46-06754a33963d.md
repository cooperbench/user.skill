# Workflow & Skill Builder

## Overview

This skill helps you build AI workflows and skills that are **outcome-driven** — describing what to achieve, not micromanaging how to get there. LLMs are powerful reasoners. Great skills give them mission context and desired outcomes; poor skills drown them in mechanical procedures they'd figure out naturally. Your job is to help users articulate the outcomes they want, then build the leanest possible skill that delivers them.

Act as an architect guide — walk users through conversational discovery to understand their vision, then craft skill structures that trust the executing LLM's judgment. The best skill is the one where every instruction carries its weight and nothing tells the LLM how to do what it already knows.

**Args:** Accepts `--headless` / `-H` for non-interactive execution, `--convert <path-or-url>` to convert an existing skill into a lean equivalent with before/after HTML comparison report, an initial description for create, or a path to an existing skill with keywords like analyze, edit, or rebuild.

**Your output:** A skill structure ready to integrate into a module or use standalone — from simple composable utilities to complex multi-stage workflows.

### Round 1: Framing the real problem

🔍 **Dr. Quinn:** *Ah — a classic scaling defect. But let's be precise about the failure mode before we prescribe. "1k duplicate issues" is the *symptom*. The *root cause* is that every agent acts as an isolated sensor with no shared memory of the population's prior reports. The user's proposal — "search before create" — treats the symptom at the edge. It works, but only if the search key is deterministic. LLM-judged "similar" will produce both false positives (merging distinct bugs because they mention the same step file) and false negatives (missing dupes because wording drifted). So my first question: what would make the dedup key *cheap and deterministic*?*

🚀 **Victor:** *Dr. Quinn is right that the key must be deterministic, but he's under-reading the strategic picture. Armel, think about who you're serving with these issues. A maintainer. One maintainer. If 1k users hit the same bug, you don't want 1k issues **or** 1k comments on one issue — both are noise. The signal you actually want is **"N users hit bug X, here's the Nth variant of evidence."** That's a reaction count, not a comment thread. Comments on a deduped issue become worse than duplicate issues: you can't `close --comment "fixed in main"` to resolve 1k comments. You can close 1k issues in one script. So the proposal as written — "add a comment on the same issue" — trades one scale problem for a worse one.*

🎨 **Maya:** *I want to push back gently on both of you — we're optimizing for the maintainer's inbox, which is real, but we're missing the user. The health-check already has a user-review gate. When an issue gets submitted, the user feels they contributed. If we silently convert their submission into a `+1` reaction on someone else's issue, we just told them *"your voice didn't matter, someone else already said it."* That's a retention kill for the feedback loop. The emotional contract matters. If we dedup, we must tell them: "We found an existing report of this — your evidence has been added as a reaction and a minimal comment with your environment delta. You helped confirm the severity." That's honest AND respectful.*

---

### Round 2: What to actually do

🔍 **Dr. Quinn:** *Maya, good catch. Then the design has three deterministic layers:*

1. ***Fingerprint key*** — `sha1(severity + workflow + step_file + normalized_section)` truncated to 7 chars. Embedded in the title: `[health-check][friction][a3f9c21] skf-create-skill step-05: ...`. Deterministic across all 1k agents. No LLM "similarity" judgment needed.
2. ***Search by key***, not by prose — `gh search issues --repo X "[a3f9c21] in:title" --state open`. One API call. Binary result.
3. ***If hit:*** add a 👍 reaction (silent upvote) **and** post a terse comment *only if* environment or evidence differs meaningfully from the original. *Do not* post identical comments.

*This keeps the LLM out of the dedup decision entirely. It only constructs the key.*

🚀 **Victor:** *Good. Add one more layer: **severity gate**. `bug` submits live — those are high-signal. `friction` and `gap` go to the local queue by default and submit only if the user explicitly opts in. Two reasons: (a) friction reports are the most subjective and produce the most near-duplicates, (b) maintainer attention is a finite resource — let `bug` have priority path.*

💡 **Carson** *(cameo):* *YES AND — here's wilder thinking: what if the health-check writes a **local fingerprint cache** at `~/.skf/health-check-seen.json` so the same user doesn't re-report the same fingerprint across sessions? Zero network calls, zero API budget. Combined with the dedup-key search, the first 1k users globally still generate ~1 live issue plus some reactions. That's the shape you want.*

🎨 **Maya:** *And in the user-facing messaging, show the fingerprint. Something like: "A matching report exists (#127). Your evidence added as 👍. Opening a new issue anyway? \[y/N]" — the user has the final override. Honesty + agency.*

### Round 3: Risks surfaced

🔍 **Dr. Quinn:** *Rate limits: `gh search` is 30/min unauth'd, higher auth'd. One call per finding is fine at our scale. Race condition: two users with no match both create — acceptable; maintainer dedupes labels post-hoc via fingerprint. Privacy: the environment table already leaks OS/editor/model — not new risk; note that comments inherit GitHub-account visibility.*

🚀 **Victor:** *The biggest risk is **the dedup-key drifting as step files are edited**. If `step-05` gets renumbered to `step-06`, the key changes, and old reports orphan. Mitigation: also store a `section anchor` rather than line numbers. The key is stable as long as the instruction's identity is stable.*

🎨 **Maya:** *And false confidence: a deterministic key only dedupes *the exact same step+section*. Two users encountering the same underlying defect via different steps will still double-report. That's fine — let the maintainer collapse those server-side. Don't over-engineer client-side.*

---

### Synthesized recommendation

**Reject** the naïve "search-and-comment" proposal. **Adopt** this instead:

| Layer | Behavior |
|---|---|
| **1. Fingerprint key** | `fp-{sha1(severity+workflow+step_file+section)[:7]}` — embedded in title prefix AND as a GitHub label |
| **2. Local seen-cache** | `{localFallbackFolder}/.seen.json` — skip if this user already submitted this fingerprint |
| **3. Remote dedup search** | `gh search issues --repo X "fp-XXXXXXX in:title" --state open --json number,title` — deterministic, one call |
| **4. On hit** | Add 👍 reaction (silent) + optional comment *only if* environment/evidence differs. User sees the existing issue # and consents |
| **5. Severity gate** | `bug` → live submit path. `friction`/`gap` → local queue by default; user opts in to submit |
| **6. User messaging** | Transparent: "Matching report #N exists. Adding reaction. Open new issue anyway? \[y/N]" |

This is **deterministic**, keeps the LLM out of dedup judgment, respects the user's agency, and gives the maintainer a clean signal (reaction count = population impact).
