67	
68	### Threshold Fallback Logic — Where It Lives
69	
70	The fallback is implemented entirely in `score.md` as a new §4b between the existing §4 (Determine Result) and §5 (Next Workflow Recommendation). The logic:
71	
72	```
73	IF result == "FAIL"
74	  AND totalScore >= 80
75	  AND effective_threshold > 80
76	  AND result != "INCONCLUSIVE"  (redundant but explicit — INCONCLUSIVE is never FAIL)
77	THEN
78	  → THRESHOLD FALLBACK triggered
79	  → Generate evidence report
80	  → Override result to "PASS"
81	  → Set effective_threshold = 80 for §5/§6/§7/§8
82	  → Record threshold_fallback = true in workflow context
83	```
84	
85	The fallback does NOT fire when:
86	- Score >= effective_threshold (already PASS — no fallback needed)
87	- Score < 80 (genuine FAIL — floor not met)
88	- effective_threshold == 80 (nothing to fall back from)
89	- Result is INCONCLUSIVE (evidence-floor verdict never overridden)
90	- Post-score caps (§3d) forced FAIL with totalScore >= 80 AND effective_threshold > 80 — the fallback DOES apply here because the cap penalized the score for tooling degradation, not quality; the evidence report should note the cap was active
91	
92	### Interaction with Post-Score Caps (§3d)
93	
94	If Cap 1 or Cap 2 fired (tooling degraded, docs-only without validators), the effective_score was capped to `threshold - 1`. If the original effective_threshold was, say, 90, then effective_score was capped to 89. Since 89 >= 80, the fallback fires. The evidence report MUST note the cap in the remediation section: "Score capped due to {cap reason} — address tooling to test at the higher threshold."

205	
206	When TS runs in a pipeline with a per-pipeline threshold (e.g., deepwiki → 90%), and the score falls to 82%, TS internally falls back to 80% and reports PASS. 3	## Overview
4	
5	Pipelines chain multiple SKF workflows in sequence. The forger orchestrates the chain, passing data between workflows via filesystem artifacts and validating output contracts at each transition.

29	
30	1. **Left to right execution** — each workflow completes before the next begins
31	2. **Headless implied** — pipelines activate `{headless_mode}` automatically for all workflows in the chain (the user already committed to the sequence)
32	3. **Data forwarding** — the forger resolves output-to-input mapping between adjacent workflows (see Data Flow table)
33	4. **Circuit breakers** — if a workflow's output fails its quality check, the pipeline halts with a summary of what completed and what remains
34	5. **Error halts propagate** — if any workflow hard-halts, the pipeline stops immediately
35	6. **Progress reporting** — the forger reports completion of each workflow before starting the next

58	## Circuit Breakers
59	
60	Circuit breakers halt the pipeline when a workflow's output doesn't meet a quality threshold:
61	
62	| Workflow | Check | Default Threshold | Halt Condition |
63	|----------|-------|-------------------|----------------|
64	| AN | recommended units count | min: 1 | Zero skillable units found |
65	| CS | compilation success | must complete | Hard error during compilation |
66	| TS | completeness score | min: 60 (per-pipeline defaults apply — see init.md §1b) | Score below 80% floor (scores between 80% and per-pipeline threshold produce a fallback PASS with evidence report — pipeline continues) |
67	| AS | drift score | not CRITICAL | Critical drift found |
68	| VS | feasibility verdict | not BLOCKED | All integrations blocked |

72	### Bracket Syntax
73	
74	Brackets after a workflow code (`CODE[value]`) are parsed as follows:
75	
76	- **Circuit breaker override**: `min:N` where N is a number — e.g., `TS[min:80]` sets the threshold for that workflow
77	- **Mode flag**: `auto` — e.g., `AN[auto]` activates auto mode for that workflow. The workflow's first step reads the flag from pipeline data context and routes to the appropriate auto-mode step file.
