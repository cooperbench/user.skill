### 🏗️ Morgan (Module Builder):

Let me start with the **architectural root cause**. Looking at `module.yaml`:

```yaml
# Variables from Agent Sidecar Config:
## sidecar_path  (from forger.agent.yaml metadata.sidecar-path)
```

This comment documents the *intent* — `sidecar_path` should be propagated from the agent's `metadata.sidecar-path` into the runtime config. But the BMAD installer doesn't implement this propagation. The installer writes `skills_output_folder` and `forge_data_folder` (which have `prompt`/`default`/`result` blocks in module.yaml), but `sidecar_path` has no such block — it's just a comment.

**Missing impact the TODO doesn't cover:** This isn't just `brief-skill`. It's **every single workflow** in the module. Let me categorize the blast radius:

| Severity | Workflows | Impact |
|----------|-----------|--------|
| **Critical** | analyze-source, create-skill, create-stack-skill, update-skill, audit-skill | Hard halt or silent tier defaulting |
| **High** | brief-skill, test-skill, export-skill | Falls back to Quick tier incorrectly |
| **Medium** | setup-forge | Tries to resolve `sidecar_path` from config but can't find it |

The TODO only mentions `brief-skill`. That's **1 of 9 affected workflows**.

### 🔄 Wendy (Workflow Builder):

Morgan's right about the blast radius, but let me trace the **specific failure modes**. There are three distinct patterns:

**Pattern 1 — Hard Halt (analyze-source step-01-init):**
```markdown
- IF missing: HARD HALT — "Cannot proceed. forge-tier.yaml not found at {sidecar_path}/forge-tier.yaml"
```
If `{sidecar_path}` resolves to a literal string `{sidecar_path}`, the agent tries to read a path like `{sidecar_path}/forge-tier.yaml` — which doesn't exist. The workflow **dies immediately**.

**Pattern 2 — Silent Tier Degradation (brief-skill, create-stack-skill):**
The `forgeTierFile` frontmatter reference:
```yaml
forgeTierFile: '{sidecar_path}/forge-tier.yaml'
```
When this can't be resolved, the workflow falls through to: *"No forge tier configuration found. Defaulting to Quick tier."* This is a **silent regression** — users who ran `setup-forge` and have a valid Deep tier get demoted to Quick with no explanation.

**Pattern 3 — State Write Failure (create-skill step-08-report):**
```markdown
Update the batch checkpoint in {sidecar_path}/batch-state.yaml
```
If `sidecar_path` is unresolved, batch state never persists. A multi-skill batch run loses its checkpoint. If the session dies mid-batch, recovery is impossible.

**Bug the TODO misses:** There's also step-01-load-brief which reads `{sidecar_path}/batch-state.yaml` for resumption. With unresolved paths, batch resume is broken in both directions — writing and reading.

### 🤖 Bond (Agent Builder):

I want to flag the **agent-level resolution gap**. The `forger.agent.yaml` correctly defines:

```yaml
metadata:
  sidecar-path: "{project-root}/_bmad/_memory/forger-sidecar/"
```

And the `critical_actions` reference `{sidecar_path}` — which the BMAD runtime resolves for the agent persona because it maps `metadata.sidecar-path` → `sidecar_path` during agent activation. So when Ferris loads as an agent, `{sidecar_path}` **does** resolve.

**But here's the gap:** Workflow step files resolve variables from the **module config**, not from the agent metadata. The agent persona resolves its own variables, but step files are loaded independently. They need config-level resolution.

This means the system works **only when** the conversation started with Ferris as the active agent AND the runtime has already resolved the agent metadata. In a fresh conversation where someone directly triggers a workflow (like `BS` for brief-skill), the step file tries to resolve `{sidecar_path}` from config — and it's not there.

---

### 🏗️ Morgan:

Bond just nailed the **real regression scenario**: The installer-deployed module works fine in a Ferris-initiated conversation (agent metadata provides the variable), but fails in **direct workflow invocation**. This is a classic "works on my machine" bug — it passed testing because testers always started from the agent menu.

**My recommended fix approach:**

Add `sidecar_path` to the module.yaml as a proper config variable with installer support:

```yaml
sidecar_path:
  prompt: false
  default: "_bmad/_memory/forger-sidecar"
  result: "{project-root}/{value}"
```

Using `prompt: false` means the installer writes it automatically without asking the user. The `result` pattern matches how `skills_output_folder` and `forge_data_folder` work.

---

### 🔄 Wendy:

I agree with Morgan's approach, but I want to flag one more **undiscovered issue**. Let me check the setup-forge workflow...

Setup-forge's initialization says:
```markdown
Load config from {project-root}/_bmad/skf/config.yaml and resolve:
- skills_output_folder, forge_data_folder, sidecar_path
```

So setup-forge **expects** `sidecar_path` in the config. If it's not there, setup-forge itself can't write `forge-tier.yaml` to the correct location. This means:

1. User runs setup-forge → can't resolve sidecar_path → writes forge-tier.yaml to wrong location (or fails)
2. User runs brief-skill → can't resolve sidecar_path → can't find forge-tier.yaml → defaults to Quick

It's a **cascading failure** where the setup workflow that should *create* the tier config can't even find where to put it.

---

### 🤖 Bond:

One more thing — the trailing slash inconsistency. The agent yaml has:

```yaml
sidecar-path: "{project-root}/_bmad/_memory/forger-sidecar/"
```

Note the trailing `/`. But every workflow reference uses `{sidecar_path}/forge-tier.yaml`, which would produce a double-slash: `_bmad/_memory/forger-sidecar//forge-tier.yaml`. Most file systems handle this fine, but it's sloppy. The config value should **not** have a trailing slash.
