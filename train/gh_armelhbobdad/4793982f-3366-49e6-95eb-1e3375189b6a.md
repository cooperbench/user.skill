459	### Baseline snapshots
460	
461	The ruleset-restore snippet at the top of this document (`## Branch Protection on main § Restore from a saved baseline`) uses `gh api --method PUT .../rulesets/<id>`. That call returns `404` if the `Default` ruleset has been deleted, not merely edited. Keeping a recent `baseline-ruleset-Default-YYYYMMDD.json` on disk lets the PUT-then-POST fallback below recover from either case.
462	
463	**One-time capture pattern** — run after any maintainer-initiated change to the ruleset or to the `release` environment, **not on a schedule**:
464	
465	```bash
466	# Capture the current Default ruleset as a disaster-recovery baseline.
467	# Uses name-based lookup so the snippet survives ruleset re-creation (IDs change, names don't).
468	RULESET_ID=$(gh api repos/armelhbobdad/bmad-module-skill-forge/rulesets \
469	  --jq '.[] | select(.name=="Default") | .id')
470	gh api "repos/armelhbobdad/bmad-module-skill-forge/rulesets/$RULESET_ID" \
471	  > "_bmad-output/planning-artifacts/baseline-ruleset-Default-$(date +%Y%m%d).json"
472	
473	# Capture the release environment + its branch policy list (two separate resources).
474	gh api repos/armelhbobdad/bmad-module-skill-forge/environments/release \
475	  > "_bmad-output/planning-artifacts/baseline-env-release-$(date +%Y%m%d).json"
476	gh api repos/armelhbobdad/bmad-module-skill-forge/environments/release/deployment-branch-policies \
477	  > "_bmad-output/planning-artifacts/baseline-env-release-branch-policies-$(date +%Y%m%d).json"
478	```
479	
480	Baselines live in `_bmad-output/planning-artifacts/` (already git-tracked, not shipped with the npm package). The filename date stamp makes the freshness of the baseline obvious at a glance.
481	
482	**Ruleset-deletion recovery path — PUT-then-POST.** The canonical restore flow is:
483	
484	1. Try `PUT` first. If the ruleset exists but drifted, this reconciles it in place.
485	
486	   ```bash
487	   RULESET_ID=$(gh api repos/armelhbobdad/bmad-module-skill-forge/rulesets \
488	     --jq '.[] | select(.name=="Default") | .id')
489	   jq '{name, target, enforcement, conditions, rules, bypass_actors}' \
490	     _bmad-output/planning-artifacts/baseline-ruleset-Default-YYYYMMDD.json \
491	     > /tmp/restore.json
492	   gh api --method PUT \
493	     "repos/armelhbobdad/bmad-module-skill-forge/rulesets/$RULESET_ID" \
494	     --input /tmp/restore.json
495	   ```
496	
497	2. If the `PUT` returns `404` (ruleset was deleted, not edited), recreate via `POST`:
498	
499	   ```bash
500	   gh api --method POST \
501	     repos/armelhbobdad/bmad-module-skill-forge/rulesets \
502	     --input /tmp/restore.json
503	   ```
504	
505	The `POST` body needs the same `name`, `target`, `enforcement`, `conditions`, `rules`, and `bypass_actors` fields as the PUT — all captured by the baseline snapshot above. Try `PUT` first; on `404`, `POST` recreates with identical semantics. The ruleset gets a new id on re-creation (IDs are not stable across delete+create cycles); update any hard-coded id references in this document on the next planned edit pass.
506	
507	For the `release` environment, a deletion+restore similarly uses the two-call pattern already documented at `## Release Environment § Restore / re-apply` — feed the environment-level baseline JSON to the `PUT .../environments/release` call, then re-POST each entry from the branch-policies baseline to `.../environments/release/deployment-branch-policies`.
