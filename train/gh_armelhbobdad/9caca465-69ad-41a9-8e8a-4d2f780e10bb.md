The `skills` CLI's path heuristic treats any bare `foo/bar`-shaped argument as a GitHub `org/repo`, taking the **first two segments** as the repo and remainder as a subpath. So the *exact* example path the workflow recommends — `{skills_output_folder}/{skill-name}/{version}/{skill-name}/` — gets parsed as `https://github.com/{skills_output_folder}/{skill-name}.git (version/skill-name)` in any project where `{skills_output_folder}` is relative (which is the default: `{project-root}/skills` is typically used from cwd as `skills/`).

**Two flaws in the current copy:**
1. The fenced command `npx skills add {resolved_skill_package}` doesn't itself bake in the `./` prefix or `/` requirement — the user copies the template and replaces the placeholder however they like.
2. The instruction says "absolute path" but the example path is relative-looking (`{skills_output_folder}/...`). A user following the example verbatim hits the github-clone trap.

**Minimal fix** (one line in `summary.md`): change the template to `npx skills add ./{resolved_skill_package}` and tweak the prose so the example shows `./skills/{skill-name}/{version}/{skill-name}/`.
