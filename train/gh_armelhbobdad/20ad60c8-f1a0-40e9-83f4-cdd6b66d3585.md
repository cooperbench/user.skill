## Bug: metadata.json schema mismatch between create-skill and export-skill

### Summary

The `create-skill` workflow produces `metadata.json` with field names that don't match what `export-skill` validates against. There is no canonical schema for `metadata.json`, so the two workflows silently diverge.

### Expected (export-skill validation spec)

```json
{
  "confidence_tier": "Forge",
  "generation_date": "2026-03-13",
  "exports": ["add", "cognify", "search"],
  "skill_type": "single",
  "source_authority": "official"
}
```

### Actual (create-skill output)

| export-skill expects | create-skill template uses | cognee metadata.json has |
|---|---|---|
| `confidence_tier` | `forge_tier` | `forge_tier` |
| `generation_date` | `generated_at` | `created` |
| `exports` (array) | not in template | `public_api_exports` |
| `skill_type` | `skill_type` ✅ | missing |
| `source_authority` | `source_authority` ✅ | missing |

### Root Cause

- No canonical `metadata.json` schema exists — `agentskills-spec.md` only covers `SKILL.md` frontmatter
- `create-skill/data/skill-sections.md` defines the metadata template with different field names than `export-skill/steps-c/step-01-load-skill.md` and `step-02-package.md` validate
- The compile step (step-05) can also emit ad-hoc field names not matching either spec
- `create-stack-skill/data/stack-skill-template.md` has the same mismatches plus additional divergences (`skill_name` vs `name`, `created` vs both alternatives)

### Proposed Fix

Fix the **producer** (create-skill), not the consumer (export-skill). Export-skill is the terminal publishing gate (ADR-K) — its expectations should be authoritative.

**Files to update:**

1. **`workflows/create-skill/data/skill-sections.md`** (metadata template)
   - `forge_tier` → `confidence_tier`
   - `generated_at` → `generation_date`
   - Add `exports` array field (actual function names, not just `exports_documented` / `exports_total` counts)
   - Ensure `skill_type` and `source_authority` are always emitted

2. **`workflows/create-stack-skill/data/stack-skill-template.md`**
   - Same renames as above
   - `skill_name` → `name`
   - Align `components` and `integrations` fields with export-skill step-01 expectations

3. **Consider adding** a canonical `metadata-schema.md` reference doc to prevent future drift

### Impact

- Export-skill currently works around this by mapping alternate names, but warns about the mismatch
- Any tooling consuming `metadata.json` (audit-skill, test-skill, future registry) will hit the same issue
