## SCORING FORMULA & WEIGHTS

### **Default Contextual Mode (Stack Skills)**
```
Total Score = sum(category_weight × category_score)

| Category | Weight | Score Basis |
|----------|--------|------------|
| Export Coverage | 36% | (documented_exports / total_exports) × 100 |
| Signature Accuracy | 22% | (matching_signatures / total_documented) × 100 |
| Type Coverage | 14% | (documented_types / total_types) × 100 |
| Coherence | 18% | (reference_validity × 0.6) + (integration_completeness × 0.4) |
| External Validation | 10% | (skill-check_score + tessl_average_score) / 2 |
| **Total** | **100%** | |
```

### **Naive Mode (Individual Skills)**
When no coherence category is scored, the 18% coherence weight is proportionally redistributed:
```
| Category | Redistributed Weight |
|----------|---------------------|
| Export Coverage | 45% |
| Signature Accuracy | 25% |
| Type Coverage | 20% |
| External Validation | 10% |
| **Total** | **100%** |
```

## CATEGORY SCORE CALCULATIONS

### **1. Export Coverage (Step 03 - Coverage Check)**
```
Export_Coverage_Score = (documented_exports / total_source_exports) × 100

What it measures:
- All public API exports in source code
- Whether each export is documented in SKILL.md
- Counts based on forge tier access (local source, provenance-map, or metadata)

Tier-specific behavior:
- Forge/Deep: AST-backed export list from source
- Quick: File structure existence check only
- Provenance-map: Union of provenance-map entries + metadata.json exports
- Docs-only: Documentation completeness (has description + params + return type)
```

### **2. Signature Accuracy (Step 03 - Coverage Check)**
```
Signature_Accuracy_Score = (matching_signatures / total_documented_exports) × 100

What it measures:
- Documented function/method signatures match source signatures
- Parameter names, types, and order must match
- Return types must match

Marked as N/A in:
- Quick tier (no AST parsing)
- Provenance-map mode (string comparison only, not semantic)
- Docs-only mode (no source to compare against)
```

### **3. Type Coverage (Step 03 - Coverage Check)**
```
Type_Coverage_Score = (documented_types / total_source_types) × 100

What it measures:
- All types and interfaces referenced in exports are documented
- Type definitions are complete

Marked as N/A in:
- Quick tier (no AST parsing)
- Provenance-map mode (cannot re-verify types without live AST)
- Docs-only mode (no source to verify against)
```

### **4. Coherence Score (Step 04 - Coherence Check)**
#### **Contextual Mode Only** (Stack skills):
```
reference_validity = (valid_references / total_references) × 100
integration_completeness = (complete_patterns / total_patterns) × 100
combined_coherence = (reference_validity × 0.6) + (integration_completeness × 0.4)

What it measures:
- Cross-references in SKILL.md point to real files/skills/types
- File paths resolve correctly
- Type imports match actual source types
- Integration patterns are complete (middleware chains, plugin flows, event handlers)
- Scripts/assets directory references exist if directory is present

Weighting within coherence:
- Reference validity: 60% of coherence score
- Integration completeness: 40% of coherence score
```

#### **Naive Mode** (individual skills):
```
Coherence_Score = basic_structural_validation × 100
- Document structure (required sections present)
- Example validity (examples use documented exports)
- No broken markdown
- Scripts/assets directory consistency

NOT SCORED - weight redistributed to other categories
```

#### **Edge Cases:**
- If no integration patterns exist: combined_coherence = reference_validity alone
- If scripts/assets directory exists but no "Scripts & Assets" section: Medium severity gap
- For Deep tier: if T2-future annotations exist but Section 4b missing: Medium severity gap

### **5. External Validation Score (Step 04b - External Validators)**
```
IF both tools available:
  external_score = (skill_check_score + tessl_average_score) / 2
  
IF only skill-check:
  external_score = skill_check_score
  
IF only tessl:
  external_score = tessl_average_score

IF neither available:
  external_score = N/A (10% weight redistributed proportionally)

What skill-check measures (0-100):
- Frontmatter validity
- Description quality
- Body content limits
- Link resolution
- File formatting

What tessl measures (0-100%):
- description_score: Clarity and completeness of description
- content_score: Actionability and specificity of usage content
- average_score: Overall combined score

Note: tessl content_score < 70% triggers warning for split-body skills
(expected behavior - tessl evaluates SKILL.md body only, not references/*.md)
```

## PASS/FAIL DETERMINATION

```
Default threshold: 80%

IF score >= 80% → PASS → Recommend export-skill workflow
IF score < 80%  → FAIL → Recommend update-skill workflow

Threshold can be customized via workflow input
```

## TIER-DEPENDENT SCORING ADJUSTMENTS

### **Quick Tier**
- Skipped categories: Signature Accuracy (22%), Type Coverage (14%)
- Redistribution: Their weights proportionally added to remaining active categories
- Export Coverage based on: file/structure existence only, not content verification
- Result: Export Coverage becomes ~82%, External Validation ~18% (approximate)

### **Docs-Only Mode** (Quick tier with all [EXT:...] citations)
- Skipped categories: Signature Accuracy, Type Coverage
- Coverage denominator: Documentation completeness (self-consistency)
- Definition: "complete item" = has description + parameters + return type
- Weight redistribution: Same as Quick tier

### **Provenance-Map Mode** (State 2, any tier)
- Skipped categories: Signature Accuracy, Type Coverage
- Reason: Can only do string comparison, not semantic type verification
- Export denominator: Union of provenance-map entry names + metadata.json exports[]
- Weight redistribution: Same as Quick tier
- Degradation notice: Varies based on T1/T1-low distribution in provenance-map

### **Forge Tier (ast-grep)**
- All five categories scored with AST-backed data
- Full formula applied

### **Forge+ Tier (ast-grep + ccc)**
- Same weights as Forge
- ccc provides pre-ranking but doesn't change scoring weights
- Same formula applied

### **Deep Tier (ast-grep + gh + QMD)**
- Same weights as Forge
- Plus cross-repository reference verification
- Plus QMD-enriched coherence checks
- Full formula with maximum depth

## WEIGHT REDISTRIBUTION RULES

**When External Validation Unavailable:**
```
Redistribute 10% proportionally to:
- Export Coverage
- Signature Accuracy
- Type Coverage
- Coherence

Example (contextual mode, no external validation):
- Export Coverage: 36 ÷ 90 × 100 = 40%
- Signature Accuracy: 22 ÷ 90 × 100 = 24.4%
- Type Coverage: 14 ÷ 90 × 100 = 15.6%
- Coherence: 18 ÷ 90 × 100 = 20%
```

**When Coherence Not Scored + External Validation Unavailable:**
```
Redistribute both 18% (coherence) + 10% (external) = 28%
Total redistribution pool = 100% - 28% = 72%

Quick tier with no external validation:
- Export Coverage: 45 ÷ 90 × 100 = 50%
- Signature Accuracy: 25 ÷ 90 × 100 = 27.8%
- Type Coverage: 20 ÷ 90 × 100 = 22.2%
```

Affects scoring through:
- Signature Accuracy weighted by T1 confidence (full) vs T1-low (inferred)
- Scoring weights adjust based on confidence distribution
- Higher T1 ratio = higher score potential on signature accuracy

```
Scoring adapts per tier:
- Each tier has positive framing (not "degraded")
- Weight distribution reflects what tier can actually measure
- 80% threshold is tier-independent quality bar
- A Quick skill at 85% and Deep skill at 85% both pass

### **Source Access Protocol** (source-access-protocol.md)
```
Determines analysis_confidence which affects scoring:
- State 1 (local source): full confidence, all categories scored
- State 2 (provenance-map): signature/type accuracy N/A, redistributed
- State 3 (metadata-only): signature/type accuracy N/A, redistributed
- State 4 (remote-only): signature/type accuracy N/A, redistributed
- State 5 (docs-only): signature/type accuracy N/A, redistributed

55	### How It Works at Runtime
56	
57	1. **Trigger** — User types `@Ferris CS` (or fuzzy match like `create-skill`). The agent menu in `forger.agent.yaml` maps the trigger to the workflow path.
58	2. **Agent loads** — `forger.agent.yaml` injects the persona (identity, principles, critical actions) into the context window. Sidecar files (`forge-tier.yaml`, `preferences.yaml`) are loaded for persistent state.
59	3. **Workflow loads** — `workflow.md` presents the mode choice and routes to the first step file.
60	4. **Step-by-step execution** — Only the current step file is in context (just-in-time loading). Each step explicitly names the next one. The LLM reads, executes, saves output, then loads the next step. No future steps are ever preloaded.
61	5. **Knowledge injection** — Steps consult `skf-knowledge-index.csv` and selectively load fragments from `knowledge/` by tags and relevance. Cross-cutting principles (zero hallucination, confidence tiers, provenance) are loaded only when a step directs — not preloaded.
62	6. **Data injection** — Steps read `data/*.md` files as needed (schemas, heuristics, extraction patterns). This is deliberate context engineering: only the data relevant to the current step enters the context window.
63	7. **Templates** — When a step produces output (e.g., a skill brief or test report), it reads the template file and fills in placeholders with computed results. The template provides consistent structure; the step provides the content.
64	8. **Progress tracking** — Each step appends to an output file with state tracking. Resume mode reads this state and routes to the next incomplete step.

79	## Why Another Tool?
80	
81	AI agents guess API calls from training data. When the training data is wrong, outdated, or incomplete, they hallucinate — inventing function names, guessing parameter types, producing code that fails at runtime.
82	
83	Several approaches exist to address this, but each has a gap:
84	
85	| Approach | What it does well | Where it falls short |
86	|----------|-------------------|----------------------|
87	| Skill scaffolding (`npx skills init`) | Generates a spec-compliant skill file | The file is empty — you still have to write every instruction by hand |
88	| LLM summarization | Understands context and intent | Generates plausible-sounding content that may not match the actual API |
89	| RAG / context stuffing | Retrieves relevant code snippets | Returns fragments without synthesis — no coherent skill output |
90	| Manual authoring | High initial accuracy | Drifts as the source code changes, doesn't scale across dependencies |
91	| IDE built-in context (Copilot, Cursor) | Convenient, zero setup | Uses generic training data, not your project's specific integration patterns |
92	
93	SKF takes a different approach: it mechanically extracts function signatures, type definitions, and usage patterns from source code via AST parsing, enriches them with documentation and developer discourse, then compiles everything into version-pinned skills that comply with the [agentskills.io specification](https://agentskills.io/specification). Every instruction traces to its source — nothing is generated from training data.

292	Based on [Vercel research](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals): passive context (AGENTS.md/CLAUDE.md) achieves 100% pass rate vs 79% for active skills alone.
293	
294	Every skill generates both:
295	
296	1. **SKILL.md** — Active skill loaded on trigger with full instructions
297	2. **context-snippet.md** — Passive context, compressed index; injected into platform context files (CLAUDE.md/AGENTS.md/.cursorrules) only when `export-skill` is run. Export reads configured IDEs from `config.yaml` and writes to all target platforms in one pass.
298	
299	### Managed Context Section
300	
301	Export injects a managed section between markers:
302	
303	```markdown
304	<!-- SKF:BEGIN updated:2026-03-20 -->
305	[SKF Skills]|1 skill
306	|IMPORTANT: Prefer documented APIs over training data.
307	|
308	[cognee v0.5.5]|root: .agents/skills/cognee/
309	|IMPORTANT: cognee v0.5.5 — read SKILL.md before writing cognee code. Do NOT rely on training data.
310	|quick-start:{SKILL.md#quick-start} — add → cognify → search async workflow
311	|api: add(), cognify(), search(), memify(), config, datasets, prune, update(), session, SearchType, run_custom_pipeline(), visualize_graph()
312	|key-types:{SKILL.md#key-types} — SearchType(14 modes: GRAPH_COMPLETION default, RAG_COMPLETION, CHUNKS, CYPHER, TEMPORAL...), Task, DataPoint
313	|gotchas: all core functions are async (must await); delete() deprecated since v0.3.9 — use datasets.delete_data(); memify default pipeline changed to triplet embedding (Mar 2026)
314	<!-- SKF:END -->
315	```
316	
317	~80-120 tokens per skill (version-pinned, retrieval instruction, section anchors, inline gotchas). Root paths are platform-aware (`.claude/skills/`, `.cursor/skills/`, `.agents/skills/`). Aligned with [Vercel's research](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals) finding that indexed format with explicit retrieval instructions dramatically improves agent performance. Developer controls placement. Ferris controls content. Snippet updates only happen at `export-skill` — create and update are draft operations. An `.export-manifest.json` tracks which skills have been explicitly exported, preventing draft skills from leaking into the managed section.

12	## Agent Skills
13	
14	An agent skill is an instruction file that tells an AI agent how to use your code. Instead of the agent guessing your API from its training data, it reads the skill and gets real function names, real parameter types, and real usage patterns.
15	
16	Skills follow the [agentskills.io](https://agentskills.io) open standard, so they work across Claude, Cursor, Copilot, and other AI tools.
17	
18	**Example:** A skill for [cognee](https://github.com/armelhbobdad/oh-my-skills) tells your agent: "The function is `cognee.search()`, it takes `query_text`, `query_type`, `top_k`, and `session_id`, and it's defined at `cognee/api/v1/search/search.py:L26`." Every parameter and location is AST-verified from the actual source code.

22	## Provenance
23	
24	Provenance means every instruction in a skill traces back to where it came from. For code, that's a file and line number. For documentation, it's a URL. For developer discourse, it's an issue or PR reference. If SKF can't point to a source, it doesn't include the instruction.
25	
26	**Examples** (from a [real generated skill](https://github.com/armelhbobdad/oh-my-skills)):
27	- `[AST:cognee/api/v1/search/search.py:L26]` — extracted from source code via AST parsing (T1)
28	- `[SRC:cognee/api/v1/session/__init__.py:L8]` — read from source code without AST verification (T1-low)
29	- `[QMD:cognee-temporal:issues.md]` — surfaced from indexed developer discourse (T2)
30	- `[EXT:docs.cognee.ai/getting-started/quickstart]` — sourced from external documentation (T3)

34	## Confidence Tiers (T1/T1-low/T2/T3)
35	
36	Each piece of information in a skill carries a confidence level based on where it came from:
37	
38	- **T1 — AST extraction:** Pulled directly from source code via AST parsing. This is structural truth — the function signature actually exists in the code right now. Cited as `[AST:file:Lnn]`.
39	- **T1-low — Source reading:** Found by reading source files directly without AST parsing. The location is correct but the type signature may be inferred. Produced by Quick tier and by Forge/Forge+/Deep when ast-grep cannot parse a specific file. Cited as `[SRC:file:Lnn]`.
40	- **T2 — Evidence (Deep tier only):** Surfaced by QMD knowledge search from issues, PRs, changelogs, or documentation within the repository. Available only when QMD is installed (Deep tier). Reliable context, but not as definitive as code. Cited as `[QMD:collection:document]`. T2 has two temporal subtypes:
41	  - **T2-past** — Historical context (closed issues, merged PRs, changelogs) explaining API design decisions. Surfaces in the skill's `references/` directory.
42	  - **T2-future** — Forward-looking context (open PRs, deprecation warnings, RFCs) about upcoming changes. Surfaces in SKILL.md Section 4b (Migration & Deprecation Warnings) and `references/`.
43	- **T3 — External:** Pulled from external documentation or websites. Treated with caution and clearly marked. Cited as `[EXT:url]`.
44	
45	Forge+ semantic discovery (via cocoindex-code) does not introduce a new confidence tier — it influences *which* files are extracted, not *how* they're cited. Discovered files are verified by ast-grep (T1) or source reading (T1-low).

52	
53	Your capability tier depends on which tools you have installed. Each tier builds on the previous one:

57	- **Forge+** — Adds [cocoindex-code](https://github.com/cocoindex-io/cocoindex-code). SKF uses semantic code search to discover relevant source regions before AST extraction, improving coverage on large codebases.

CCC (cocoindex-code) enhances Deep tier when installed — ast-grep + gh + qmd + ccc gives maximum capability.

64	## Drift
65	
66	Drift happens when the source code changes but the skill instructions haven't been updated to match. A skill might still reference a function that was renamed, removed, or had its signature changed.

69	
70	**Example:** Your skill says `createUser(name: string)` but the function was renamed to `registerUser(name: string, email: string)` in the last release. That's drift.
