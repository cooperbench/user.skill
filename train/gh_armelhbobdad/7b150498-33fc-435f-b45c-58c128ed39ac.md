247	
248	**L1 — Exact-wording commitment** (NOT recommended)

250	- Operation: commit verbatim to every chalk string in `tools/cli/commands/*.js` (e.g. "`skf install` output SHALL include the line `Skill Forge — Installation Complete`")
251	- Tradeoffs:
252	  - PRO: Maximally precise — downstream parsers can regex against exact strings
253	  - CON: Every prose improvement becomes a breaking change. Fixing a typo = major bump. Unshippable
254	  - CON: Over-constrains i18n (which SKF doesn't yet do, but `{communication_language}` config suggests direction). Committing English wording forecloses locale variants
255	  - CON: The output is already ANSI-colored and structured for human terminals; parsers that depend on this break when terminals don't support colors. Building parsers against styled output is itself a footgun — exact wording pretends to make this safe when it isn't
256	  - Rejected

258	**L2 — Field-presence + exit-code semantics commitment (RECOMMENDED)**
259

262	  - PRO: Downstream tooling that needs to introspect an install should use `skf-manifest.yaml` directly (which IS committed verbatim per Path Install-Layout above) — the output format is for humans, not parsers
263	  - PRO: Improvements (better colors, better table layout, more informative messages) ship in minor releases without breaking anything
264	  - PRO: Exit-code semantics are what automation actually relies on — and those ARE committed
265	  - PRO: Matches the pragmatic approach most OSS CLIs take (git, npm, kubectl — none commit to exact output prose in their SemVer contracts)
266	  - CON: A downstream consumer who DOES try to parse `skf status` output gets no contract coverage; if they complain, the answer is "use skf-manifest.yaml, that's what it's for." Acceptable
267	  - **Recommended**
268	
269	**L3 — Exit-code-only commitment** (too narrow)
270	
271	- Operation: commit only to exit codes; say nothing about output content
272	- Tradeoffs:
273	  - PRO: Maximally flexible for SKF; nothing binds future versions
274	  - CON: Doesn't actually help downstream consumers know what to expect from the tool. A contract that says nothing about what the tool DOES (just whether it succeeded) is useless as a contract
275	  - Too narrow — L2's field-presence commitment is the minimum useful level

277	**Recommendation: L2.** Captures the information downstream consumers need (what output fields exist; what exit codes mean) without constraining future prose improvements.

Breaking changes to covered surfaces require a major-version bump; additive changes to covered surfaces are minor bumps; changes to `@internal` surfaces are free to land in any release.

31	+## Covered Surfaces
32	+
33	+The five buckets below are the entirety of the v1.0.0 public surface. Anything not explicitly listed here is `@internal` (see [§ @internal — Not Covered by SemVer](#internal--not-covered-by-semver)).

35	+### CLI Command Surface
36	+
37	+The CLI is invoked via `npx bmad-module-skill-forge <subcommand>` (one-shot) or `npm run skf:<subcommand>` (post-install). Covered:
38	+
39	+- **Subcommands**: `install`, `update`, `status`, `uninstall`. Renaming, removing, or changing the semantics of any subcommand is breaking.
40	+- **Top-level options**: `-V, --version` (prints the installed package version) and `-h, --help` (prints command help). Provided by commander as part of the entrypoint at `tools/cli/skf-cli.js`.
41	+- **Per-subcommand flags**: none are currently part of the v1.0.0 surface. Each subcommand today accepts no flags. Adding a new flag is additive (minor); removing or renaming a flag once added would be breaking.
42	+- **Exit codes**: `0` on success (including user-cancel on `install` and "nothing to do" paths on `uninstall`); `1` on unhandled failure. Intermediate exit codes are not part of the contract.
43	+- **`npm run skf:*` script aliases**: `skf:install`, `skf:update`, `skf:status`, `skf:uninstall` in `package.json` are the post-install convenience entry points. Renaming or removing any `skf:*` script is breaking. (Note: `release:*` scripts are NOT part of this contract — they are internal-to-maintainers and are being retired across Epic 4 and Epic 6.)
44	+
45	+### Programmatic API of `tools/cli/skf-cli.js`
46	+
47	+`tools/cli/skf-cli.js` is the CLI entrypoint for `npx bmad-module-skill-forge` and for `npm run skf:<subcommand>`. Though `package.json`'s `main` field points at this file (standard npm resolution for bin-like packages), it has **no programmatic export surface**. The file runs commander setup and calls `program.parse(process.argv)` as top-level side effects; it has no `module.exports` block. A `require('bmad-module-skill-forge')` from Node runs the CLI parser against the caller's `process.argv` — not a supported usage.
48	+
49	+Programmatic embedding of SKF is explicitly `@internal` at v1.0.0. If a programmatic API is ever added, it will be introduced via an explicit `module.exports` block and a minor version bump (additive).
