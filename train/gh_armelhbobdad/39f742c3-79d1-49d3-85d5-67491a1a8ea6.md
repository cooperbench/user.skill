### 🔄 Wendy (Workflow Building Master) — *leans forward, scanning the step file*

"Methodologically, yes — and honestly, I'm surprised it isn't already there. Look at the step's own structure: section 2 is **Distribution Instructions** branched by `source_authority`. That's a distribution branch, not an *installation* branch. Exporting a skill and *using* a skill are two different state transitions, and right now the step tells the user how to ship it but not how to consume it locally. That's an asymmetric flow.

My recommendation: **don't shove it into the distribution branch** — that muddles two concerns. Add a new subsection between current Section 2 (Distribution Instructions) and current Section 3 (Dry Run Reminder). Call it something like `### 2b. Install Locally` or promote it to `### 3. Local Installation` and renumber. The workflow already reads top-to-bottom as *summary → ship it → try it → what next*, so 'install locally' belongs right before 'Next Steps'.

One more thing: suppress it when `dry-run` is active. No point telling someone to `npx skills add` a path that was never written. Gate it on `if not dry-run`."

### 🎨 Maya (Design Thinking Maestro) — *jazz-hands a little*

"Ooh, I love this because it hits the **moment of highest intent**. Think about it — the user just watched their skill get forged. They're excited. They want to *try it right now in this very project*. And we're… handing them publish instructions? That's like finishing a pottery class and telling someone how to ship their bowl to a museum before letting them drink from it.

So: yes, include it — but frame it around the user's *next verb*, not ours. Don't write `Installation Instructions`. Write something like `### Try It Now` or `### Use This Skill` with the command front and center:

```
npx skills add {absolute-path-to-skill}
```

And — this is important — **resolve the path for them**. Don't say `/path/to/skill/folder`. The workflow already knows where it wrote the skill (`{skills_output_folder}/{skill-name}/...` from step-02). Pre-fill it so the user can copy-paste without thinking. Every cognitive tax at the finish line is a tax on delight.

On the npmjs link: one line, low-key, 'For other source formats (git URL, tarball, registry), see the Installation → Source Formats section at https://www.npmjs.com/package/skills.' Don't bury it, don't over-sell it. A signpost, not a billboard."

### 🏗️ Morgan (Module Creation Master) — *steepled fingers*

"Both good points. Let me add the ecosystem lens.

First — Armel, this proposal is *consistent with your own documented principle*: SKF docs link out rather than duplicate external ecosystems. You wrote that rule for a reason. So the 'should we add it?' question isn't just a yes — it's a yes *that actively reinforces an architectural commitment you've already made*.

Second — **source_authority matters here and Wendy's structural suggestion needs one refinement**. For `community` skills, the summary already tells the user 'Location: {skills_output_folder}/... — This project only.' That's exactly the case where `npx skills add <that-path>` is the *primary* distribution mechanism. For `internal`, the skill is already under the repo's `skills/` directory — team members don't need `npx skills add`, they just pull. For `official`, `npx skills add <name>` (by name, not path) is what consumers run after publish.

So the install snippet isn't actually one-size-fits-all. My take: the 'Install Locally' section should be **always shown** (because the author may want to test locally even for official skills before publishing), but the example command should use the resolved local path. The *registry-style* install (`npx skills add {skill-name}`) already lives in the 'official' distribution branch — leave it there.

And Maya is right about resolving the path. If step-02's package output folder is `{skills_output_folder}/{skill-name}/{version}/{skill-name}/`, show exactly that. No placeholders."
