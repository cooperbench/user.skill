## Le problème sans le callback Le `UsagePoller` tourne avec un intervalle fixe de **180 s** (`UsagePoller.swift:14`). Il fetch les métriques de l'API Anthropic pour le compte actif à chaque tick. Scénario sans callback, au moment d'un `/login` : 1. **t=0** : tu switches gmail → 4sh. Le monitor (tick 15 s) détecte le changement et met à jour `isActive` dans `usages.json`. 2. **t=0** : si 4sh a déjà un ancien cache, la menubar l'affiche — **mais les chiffres datent de la dernière poll** (jusqu'à 3 min). 3. **t=0 à 180 s** : le poller dort. La menubar montre potentiellement des métriques périmées pour 4sh. 4. **t=~180 s** : prochain tick du poller → fetch API → données fraîches. Pire cas : si 4sh n'avait jamais été vu, aucune métrique à afficher → `"--"` jusqu'à la prochaine poll. ## Ce que fait le callback ```swift ClaudeActiveAccountMonitor( fileManager: fileManager, onActiveAccountChanged: { [weak poller] _ in await poller?.pollOnce(force: true) } ) ``` Dans `checkOnce()`, quand je détecte un *vrai* changement (`previous != active`), j'appelle ce closure. Le closure relance **immédiatement** `poller.pollOnce(force: true)` — un fetch hors-cycle, sans attendre le prochain tick des 180 s. Le `force: true` est important : par défaut `pollOnce` skip un connector si son cache est frais (`UsagePoller.swift:61-70`). Avec `force`, il ignore cette vérification et fetch quand même. ## Pourquoi `[weak poller]` Le monitor est stocké dans `self.accountMonitor`, et il capture `poller`. Le poller est aussi stocké dans `self.poller`. Pas de cycle direct, mais `weak` reste propre pour éviter qu'un monitor zombie ne maintienne le poller en vie après un `quit()`. ## Résultat Tu passes de gmail à 4sh → dans la seconde qui suit la tick du monitor (≤15 s), le poller refetch les métriques du nouveau compte.
