In `auxilio-extension`, there is **no OAuth client *secret* anywhere** — and that's by design. It uses the browser implicit flow, which is a public-client flow that has no secret. Here's the full breakdown:

## What gets stored, and where

**1. Client ID (`WXT_OAUTH_CLIENT_ID`)** — *not secret*
- Lives in `.env` locally (`auxilio-extension/.env`), read via `import.meta.env.WXT_OAUTH_CLIENT_ID` in `lib/config.ts:13`.
- WXT **inlines it into the built JS at build time** (`.output/chrome-mv3`). So in shipped builds it's baked into the bundle — fine, because a Web OAuth client ID is public by nature.
- `.env` is gitignored (`.gitignore:18`, `.env.*` too), only `.env.example` is tracked (with the value blank). Confirmed: `git ls-files` shows only `.env.example`.

**2. Client secret** — *does not exist here*
- `lib/auth.ts:60` uses `response_type=token id_token` (OAuth implicit flow) through `chrome.identity.launchWebAuthFlow`. The redirect returns tokens directly in the URL fragment (`parseFragment`, `auth.ts:28`). No code exchange, so **no client secret is ever needed or present** in the extension.
- `wxt.config.ts:4-6` notes the same: no `oauth2` manifest key, client id read from env.

**3. The runtime tokens (`id_token` + `access_token`)** — the actual secrets at runtime
- Held only in the **background service worker** and cached in `chrome.storage.session` under the key `auxilio.tokens` (`auth.ts:19, 82`).
- `storage.session` is in-memory and cleared when the browser closes — never written to disk, never synced.
- Per the architecture (README + CLAUDE.md "Hard rule 3"), the background worker is the **only** holder of tokens/network; the content script and side panel never see them.
- Tokens auto-refresh silently (`prompt=none`, `auth.ts:91`) and are revoked + cleared on sign-out (`auth.ts:99-108`).

## Summary

| Thing | Secret? | Storage |
|---|---|---|
| OAuth client ID | No | `.env` (gitignored) → inlined into build bundle |
| OAuth client secret | — | **None — implicit flow, no secret exists** |
| `id_token` / `access_token` | Yes (runtime) | `chrome.storage.session`, background worker only |

So the only thing you keep out of git is `.env` (client ID + engine URL + magic address), and that's already handled. The "secret-holder" boundary the codebase cares about is runtime tokens staying in the background worker's `storage.session` — not a client secret, because the implicit flow deliberately avoids having one.

## The correction

**"Client-side auth is secure" is the wrong claim to anchor the doc on.** Two separate things are getting bundled under "client-side auth," and they have very different security stories:

### What's genuinely sound ✅
The *authentication decision is not client-side at all.* The extension is a conduit:
- Google authenticates the user and issues a **signed** `id_token`.
- The engine verifies that signature **server-side** — `addon-auth.ts:67` calls `verifyIdToken({ idToken, audience })`, which checks Google's signature, issuer, expiry, **and** that `aud` is on your allow-list (`AUXILIO_EXTENSION_OAUTH_CLIENT_ID`), then requires `email_verified` (`addon-auth.ts:69`).
- The client holds **no secret** (public client, implicit flow), so there's nothing on the client to steal-and-forge an identity with.

So identity **cannot be forged from the client**. That's the real security anchor, and it's correct. The doc's thesis should be *"identity is verified server-side against a Google-signed token; the client holds no secret"* — **not** *"client-side auth is secure."*

### What you should NOT call "secure" ❌
The **token-acquisition flow is the deprecated OAuth 2.0 implicit grant** — `auth.ts:60` uses `response_type=token id_token`. This matters:

1. **Implicit grant is removed in OAuth 2.1 and discouraged by the OAuth Security BCP (RFC 9700).** The sanctioned public-client flow is **Authorization Code + PKCE**. `chrome.identity.launchWebAuthFlow` supports it, and PKCE needs **no client secret** — so this is fixable without changing the "no secret" property.
2. **Consequences of implicit here:** access token comes back in the URL fragment (history/leak surface); **no refresh token**, so your "silent renewal" (`prompt=none`, `auth.ts:91`) leans entirely on Google's session cookie and breaks the moment that's gone; no sender-constraining.
3. **This is on your own roadmap to collide with.** CLAUDE.md hard-rule 7 says public/CWS distribution = OAuth verification later. "We use the implicit grant" is exactly the kind of thing a verification/security review flags.

### Risks that remain regardless of flow ⚠️
- Both tokens are **bearer** credentials — exfiltration = impersonation until expiry. Mitigations you *do* have are good and worth documenting: `storage.session` (memory-only, never disk, never synced), background-worker-only custody, content script can't see tokens. Residual risk: an XSS in the React side panel can't *read* the token but can *message the background to act*.
- The `ADDON_DEV_TRUST_EMAIL` bypass (`addon-auth.ts:47`) skips verification entirely — fine, it's gated to non-prod, but the doc must state it **must never be set in production**.

## Net verdict
For **internal-first** distribution: **reasonably secure**, because the trust anchor is server-side verification of a Google-signed token and no secret is exposed. It is **not best-practice**, and writing "client-side auth is secure" unqualified would be the kind of validation you've told me you don't want. The honest doc says: *secure-by-design where it counts (server-side verification, no secret), with one known gap (implicit → should be auth-code + PKCE) before going public.*
