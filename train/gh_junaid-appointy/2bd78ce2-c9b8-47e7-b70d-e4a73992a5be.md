## Root cause

`react-native-worklets@0.8.3` declares a **required** peer dependency on `@react-native/metro-config: "*"`, and that package is not present in `package-lock.json`. npm 10's `npm ci` enforces lock-file consistency — when a non-optional peer is missing from the tree, it bails with the cascade of "Missing X from lock file" errors you're seeing (the @react-native/*@0.85.3 + metro@0.84.4 items are what npm *would* install to satisfy that peer at latest, then their transitive deps).

I reproduced it locally with the same lock file — `npm ci --dry-run` produces the identical error. So this is not an EAS-environment issue, it's a broken lock file in the repo.

### Why it broke

The clean lock was committed at `3c34cfa Fix: regenerate package-lock.json to sync with package.json`. At that point `package.json` (look at `git show HEAD:package.json`) had **no** `react-native-worklets` and no `react-native-worklets-core`. Sometime after that you:

1. Added `react-native-worklets` + `react-native-worklets-core` (in the currently-staged change), then
2. Removed `react-native-worklets-core` again (in the unstaged change), keeping `react-native-worklets`.

The `npm install` that produced the current lock file resolved `react-native-worklets@0.8.3` itself, but never added the `@react-native/metro-config` peer to the tree. That happens when `npm install` is run with `--legacy-peer-deps`, or when npm declines to auto-install because the available peer (latest `@react-native/metro-config@0.85.3`) conflicts with the pinned `react-native@0.81.5` line. Either way, `npm ci`'s stricter consistency check on EAS won't tolerate it.

The dependency chain that drags this in is: `react-native-reanimated@4.1.1` → required peer `react-native-worklets>=0.5.0` → required peer `@react-native/metro-config: "*"`. So you can't just remove `react-native-worklets` — reanimated v4 needs it.

### Fix (recommended)

Pin `@react-native/metro-config` explicitly so the peer is satisfied at a version that matches RN 0.81.5 rather than letting npm pull the 0.85.x line:

```bash
cd field-app
rm -rf node_modules package-lock.json
npm install --save-dev @react-native/metro-config@0.81.5
# verify
npm ci --dry-run
```

Then commit the regenerated `package-lock.json` together with the `package.json` change. EAS's `npm ci` will pass after that.

### Two things to also clean up while you're in there

- The staged commit still re-adds `react-native-worklets-core` to `package.json`. Your unstaged change already removed it. Make sure whichever commit you push doesn't reintroduce it — vision-camera lists it as an *optional* peer, and you're not using frame processors per the recent log.
- Avoid running `npm install --legacy-peer-deps` going forward on this folder — that's what produced the inconsistent lock. If a future peer-dep conflict forces it, pin the peer explicitly (as above) rather than papering over it with the flag, otherwise EAS will fail the same way again.

> DEVELOPER

should I not use --legacy peer deps, is it not needed?

> AGENT

Short answer: **don't use it on this project.** It's the thing that produced the broken lock file in the first place.

What it actually does:
- npm 7+ default: when a package declares a required peer dep, npm tries to install it automatically and *fails the install if peers can't be satisfied*.
- `--legacy-peer-deps`: reverts to npm 6 behavior — npm ignores peer deps entirely. Install "succeeds" but the lock file never records the peer in the tree.

That second behavior is exactly what bit you: `react-native-worklets`' required peer `@react-native/metro-config` got silently skipped, the lock file looked fine locally, then `npm ci` on EAS (which does strict consistency checking) rejected it.

When the flag *is* legitimately useful: a transitive peer-dep conflict you genuinely cannot resolve (e.g. two libraries demanding incompatible React versions and you've decided the mismatch is safe). Even then, the cleaner move is to pin an `overrides` entry in `package.json` or add the peer explicitly — both are recorded in the lock file, so EAS stays happy.

Rule of thumb for this repo: **plain `npm install`**. If it errors on peer deps, fix the conflict (pin the peer, bump a library, add an override) rather than reaching for the flag.
