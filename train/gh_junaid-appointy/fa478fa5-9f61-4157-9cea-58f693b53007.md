Short answer: Play Store is small because it ships **split APKs** (per ABI + per density + per language) generated from an AAB. ## What's actually inflating the APK

For a vanilla Expo/RN app the big rocks are:
1. **Native libs for every ABI** (`arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`) — usually 40–60% of the APK.
2. **JS bundle + Hermes bytecode** — already optimized if Hermes is on (default in SDK 54).
3. **Resources** (drawables, fonts, locales) for every density/language.
4. **Debug symbols / unstripped libs** if you accidentally ship a dev build.

## Practical options for non–Play-Store distribution

### 1. Build per-ABI APKs (biggest win, ~50% smaller)
Almost every Android device in your warehouse is **arm64-v8a**. Ship only that.

In `android/app/build.gradle` (after `npx expo prebuild`):
```gradle

    splits {
        abi {
            enable true
            reset()
            include "arm64-v8a"   // add "armeabi-v7a" only if you have old 32-bit phones
            universalApk false
        }
    }
}
```

Or via Expo config plugin / `app.json` `expo.android.buildArchs` if you prefer not to eject. Easiest in EAS: set the env var in `eas.json`:
```json
"production": {
  "android": { "buildType": "apk" },
  "env": { "EAS_NO_VCS": "1" }
}
```
…and use a config plugin like `expo-build-properties` to set `android.enableProguardInReleaseBuilds: true` and `android.enableShrinkResources: true`.

### 2. Use `expo-build-properties` (no native editing)
Add to `app.json` plugins:
```json
["expo-build-properties", {
  "android": {
    "enableProguardInReleaseBuilds": true,
    "enableShrinkResources": true,
    "extraProguardRules": "-keep class com.facebook.hermes.** { *; }"
  }
}]
```
This turns on R8 (code shrinking) + resource shrinking. Often 10–20MB off.

### 3. Build an AAB and convert to split APKs with `bundletool`
This is **exactly what Play Store does** — locally.
```bash
eas build --profile production --platform android   # produces .aab
bundletool build-apks --bundle=app.aab --output=app.apks --mode=universal
# or, for true per-device splits:
bundletool build-apks --bundle=app.aab --output=app.apks \
  --device-spec=device.json
bundletool install-apks --apks=app.apks
```
You distribute the `.apks` set (or generate a device-specific APK for each phone model). This is the closest you'll get to Play Store size without publishing.

### 4. Profile-specific tweaks
- `production` profile in `eas.json` → `buildType: "app-bundle"` for AAB, `"apk"` for APK.
- Confirm Hermes is enabled (`jsEngine: "hermes"` in `app.json` — default).
- Drop unused locales: `android.defaultConfig.resConfigs "en", "hi"` in `build.gradle`.

## OTA updates — yes, with caveats

Expo provides **EAS Update** (free tier: 1,000 monthly active updates, plenty for an internal warehouse app). It pushes new JS bundles + assets to installed apps on next launch. **No new APK install required.**

### What OTA *can* update
- All your TypeScript/React code (screens, logic, styles)
- Images, fonts, JSON, anything in `assetBundlePatterns`
- ~95% of changes you'll typically make

### What OTA *cannot* update (requires new APK)
- `app.json` plugins or permissions
- New `react-native-*` native libraries
- Expo SDK version bump
- New-arch / Hermes flags
- Anything that changes the **runtime version**

### Setup (one-time)

**1. Install:**
```bash
npx expo install expo-updates
eas update:configure
```

**2. `app.json` — add:**
```json
"runtimeVersion": { "policy": "appVersion" },
"updates": {
  "url": "https://u.expo.dev/5428db61-c637-4123-8b90-65c1bd684799",
  "checkAutomatically": "ON_LOAD"
}
```

The `runtimeVersion: { policy: "appVersion" }` line is the key — it ties OTA compatibility to your `expo.version` in `app.json` (`0.1.0` today). Bump `version` only when you ship a new APK with native changes; OTA updates flow freely between version bumps.

**3. Publish an update:**
```bash
eas update --branch production --message "Fix scanner crash on Galaxy A05"
```
Staff phones pick it up on next app launch (or foreground, depending on `checkAutomatically`).

### Practical workflow for you

| Change type | What to do |
|---|---|
| Tweak a screen, fix a bug, change copy | `eas update --branch production` — instant rollout |
| Add `react-native-something`, change permissions, bump SDK | New APK build → resign → redistribute |
| Hotfix a bad OTA | `eas update --branch production --republish` to roll back |


## What I changed

**`app.json`** — added:
- `runtimeVersion: { policy: "appVersion" }` — ties OTA compatibility to `expo.version` (`0.1.0`). Bump it only when shipping native changes.
- `updates.url` — your EAS Update endpoint (uses existing `projectId`).
- `expo-build-properties` plugin — enables ProGuard (R8), resource shrinking, restricts ABIs to `arm64-v8a`, and adds keep-rules for Hermes / Reanimated / Vision Camera so shrinking doesn't strip them.

**`eas.json`** — three profiles, each with its own channel:
- `development` — dev-client APK on channel `development` (ignores OTA, loads from Metro).
- `preview` — release APK on channel `preview` (sideloadable; useful for stakeholder demos).
- `production` — AAB on channel `production` (for warehouse distribution via `bundletool`).

## Commands you'll use

```bash
# 1. Your dev build (one-time, then JS reloads via Metro)
eas build --profile development --platform android

# 2. Production build for staff (smallest, distributable)
eas build --profile production --platform android
# → produces an .aab; convert with bundletool:
bundletool build-apks --bundle=field-app.aab --output=field-app.apks --mode=universal --ks=<your-keystore> --ks-key-alias=<alias>
# or per-device:
bundletool build-apks --bundle=field-app.aab --output=field-app.apks
bundletool install-apks --apks=field-app.apks   # installs to connected phone

# 3. OTA update for staff phones (95% of changes — instant rollout)
eas update --branch production --message "your change description"

# 4. OTA preview to your demo phones only
eas update --branch preview --message "..."
```

## One thing you'll need to do once

When you run your first `eas build` or `eas update`, EAS will prompt to log in (`eas login`) if you aren't already, and it'll auto-create the Update branches the first time you publish. No other setup required — the `projectId` in `app.json` already binds everything.

## Gotcha to remember

Bump `expo.version` in `app.json` **every time you build a new APK with native changes** (new library, new permission, SDK upgrade). That cuts the OTA stream — old phones stop receiving updates meant for the new runtime, which is what you want. Between version bumps, OTA flows freely.

which one is better strategy, storing in utc and displaying in IST, or storing and displaying both in IST?

> AGENT

Store in UTC, display in IST. Not even close — and you're already doing it right.

## Why UTC for storage

1. **Single source of truth.** Every timestamp in the DB means exactly one moment in time. No ambiguity about which timezone a row was written in.
2. **DST and TZ-rule changes don't rewrite your past.** If India ever adopts DST (it has been proposed) or you expand to a second site in another zone, UTC rows are unaffected. IST-stored rows would silently shift meaning.
3. **Comparisons and intervals just work.** `created_at < scanned_at`, `now() - created_at`, `date_trunc('hour', ...)` — all correct without TZ math.
4. **Postgres `timestamptz` already does this.** It stores UTC internally regardless of what you send it, then converts on read using the session TZ. Fighting that is more work than going with it.
5. **Libraries assume it.** `Date` in JS, `Instant` in Java, ORMs, log shippers, Grafana — they all default to UTC. Storing IST means you're translating at every boundary.
6. **Multi-region future.** The moment you add a second site in a different zone (Bengaluru ↔ Singapore, say), IST storage forces a migration. UTC needs zero changes.

## Why IST for display

- The users are humans in IST. They don't think in UTC. Showing `09:00 UTC` on a warehouse scan that happened at 2:30pm local is confusing and error-prone.
- Reports, exports, WhatsApp messages, dashboard cards — every user-facing surface should be IST.

## When storing-in-IST is tempting (and still wrong)

- "It's simpler — no conversion." It's simpler **until** the first time DST, a second region, or a logs query bites you. The cost is paid later, all at once.
- "The Excel sheet shows IST anyway." That's a display concern. Format at the boundary; don't corrupt storage.
- "I don't want to convert on every read." A formatter call costs nanoseconds. This is not a real concern.

## The one rule that makes this clean

**Convert at the edges, never in the middle.** DB and internal APIs deal in UTC `Date` / `timestamptz`. Anything human-visible — Sheets exports, dashboard, push notifications, logs you'll actually read — goes through `formatDateTimeInIST` / `formatShortDateInIST` at the last moment. Don't let IST strings leak back into storage paths.

That's exactly the shape of the fix we just made: DB unchanged (UTC), formatters at the Sheets-write boundary. Keep doing that everywhere.

## JS/TS changes → yes, instantly via OTA

The preview APK was built with `expo-updates` wired in (`runtimeVersion: appVersion`, `updates.url` pointing at your EAS project, `channel: "preview"`). So any JS/TS edit you make — screens, hooks, logic, styles, copy, assets — can be pushed over the air:

```bash
eas update --branch preview --message "describe your change"
```

The installed app picks it up on next launch (controlled by `checkAutomatically: "ON_LOAD"`). No rebuild, no reinstall, no Metro server.

This covers ~95% of what you'll change day-to-day.

## What needs a new APK install

OTA can't update anything that's compiled into the native binary:

- `app.json` plugins (e.g. adding a new `expo-*` plugin)
- New permissions
- New `react-native-*` libraries
- Expo SDK upgrades
- `newArchEnabled`, Hermes flags
- The `runtimeVersion` itself (i.e. bumping `expo.version` in `app.json`)

For those, rerun the build and sideload the new APK.

## How to tell which path a change needs

Rule of thumb: if it's only in `src/**/*.ts(x)` or `assets/**`, it's OTA-able. If it touches `app.json`, `package.json` (new native dep), or `eas.json`, you need a rebuild.

## Quick sanity check before your first OTA

The APK you installed was built **after** we added `runtimeVersion`, `updates.url`, and `channel: "preview"` to the config — so OTA should work. To verify:

1. Make a small visible JS change (e.g. tweak a heading on Home).
2. Run `eas update --branch preview --message "test OTA"`.
3. Force-quit and reopen the app on the phone.
4. The change should appear.

If it doesn't, the APK was built before the OTA wiring landed and you'd need one more build to enable updates — but given the order we did things, that shouldn't be the case.

## One gotcha

The `runtimeVersion` policy is `appVersion`. Your current `expo.version` is `0.1.0`. Don't bump that unless you're also shipping a new APK — bumping it cuts the OTA stream for the existing installs.
