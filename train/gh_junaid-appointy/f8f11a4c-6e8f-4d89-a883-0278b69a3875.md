Two separate things. Looking at the code:

## 1. Counter freezes after inline edit — bug in `QtyStepper`

`src/design/QtyStepper.tsx:23` (same shape in `CompactStepper.tsx:22`). The race:

1. You tap the number, type a new value. `onTextChange` calls `onChange(parsed)` on each keystroke → parent `qty` updates.
2. You then tap **+** or **−**. Touch-down moves focus off the `TextInput`, so `onBlur` fires `commit()` — but `onPress` for the +/- button fires after, in the **same** render's closure.
3. `commit()` calls `onChange(parseValue(draft))` (=5).
4. `bump()` calls `onChange(clamp(value + 1))` — but `value` here is the closed-over prop from the last completed render (also 5). So it dispatches `onChange(6)`.
5. Order of `setQty` calls in the parent depends on whether blur or press flushes first. On Android, blur often resolves *after* press in practice, so the sequence becomes `setQty(6)` → `setQty(5)`. Final state: **5**. Display never moves.

Hit + again: same closure value, same outcome. Counter looks frozen.

**Fix shape:** hold the latest committed value in a ref so `bump` doesn't read a stale prop, and make `commit` a no-op if `bump` already left edit mode. Sketch:

```ts
const liveValue = useRef(value);
useEffect(() => { liveValue.current = value; });

const commit = () => {
  if (!editing) return;
  const next = clamp(parseValue(draft));
  liveValue.current = next;
  onChange(next);
  setDraft(String(next));
  setEditing(false);
};

const bump = (delta: number) => {
  haptic.tap();
  if (editing) {
    const parsed = clamp(parseValue(draft));
    if (!Number.isNaN(parsed)) liveValue.current = parsed;
    setDraft(String(liveValue.current));
    setEditing(false);
  }
  const next = clamp(liveValue.current + delta);
  liveValue.current = next;
  onChange(next);
};
```
