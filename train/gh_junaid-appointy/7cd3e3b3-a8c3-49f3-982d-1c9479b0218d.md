### Is This Necessary? Analysis

**Arguments FOR this pattern being necessary:**

1. **Offline-first architecture**: The local SQLite cache must stay in sync. When the user went offline and back online, the remote data may have changed.

2. **Multi-device scenario**: A guard receives an order on Device A, then uses Device B. Without refresh-on-focus, Device B shows stale local data.

3. **Long background**: App may have been backgrounded for hours. Data could have changed on the server.

4. **Fallback behavior**: Graceful `catch () { }` blocks mean screens still load from local cache if offline—no blank screens.

5. **Transparent sync**: Comment in HomeScreen (lines 32-35) explains it mirrors the entire flow:
   > "Mirror the screens' own load flow so the tile counts match what the user sees after tapping in: flush outbox, pull remote, replace local cache, then count from local."

**Arguments AGAINST (inefficiency concerns):**

1. **Redundant API calls**: Every tab press = full API request to `/api/inventory/stock`, `/api/inventory/orders`, etc.

2. **Network traffic**: Even over LTE, fetching large stock/order lists repeatedly wastes bandwidth.

3. **UX delay**: Initial load spinner appears every time user returns to a screen.

4. **Unused refreshControl**: Despite the refresh-on-focus pattern, screens also have pull-to-refresh (`RefreshControl`) that calls the same `load()` function—potential double-sync if user pulls while already syncing.

5. **No cache expiry**: There's no check like "only refresh if 30+ seconds old"—it's always fresh regardless of recency.
