Skill loaded. Now I have enough to answer. **Yes, `TypedChildrenFn<C>` is viable** — and it's the right call for `ClientOnly`. The component re-runs the closure when the `mounted` signal flips, so preserving the concrete view type (instead of erasing to `AnyView`) gives you static optimization and avoids `AnyView`'s vtable cost on every re-render. The standard Leptos pattern is essentially: ```rust #[component] pub fn ClientOnly<Chil, Fb>( #[prop(optional, into)] fallback: Option<TypedChildrenFn<Fb>>, children: TypedChildrenFn<Chil>, ) -> impl IntoView where Chil: IntoView + Send + 'static, Fb: IntoView + Send + 'static, ``` **Tradeoffs:** - **Win:** zero-cost view rendering, better type inference at the call site, no `AnyView` allocation per re-render. - **Cost:** two type params (because `children` and `fallback` typically differ in shape — a placeholder skeleton vs. real content). Slot composition where the caller wants `Box<dyn>` semantics gets more awkward, but for `ClientOnly` the call site always has concrete views, so it's pure upside there. - **Open question:** Leptos's `<Show fallback=...>` uses the same dual-`TypedChildrenFn` pattern internally — that's the precedent. The current spec uses `ChildrenFn` likely because it's the simpler signature, not because there's a technical reason to. **Recommendation:** update the spec to `TypedChildrenFn<Chil>` + `Option<TypedChildrenFn<Fb>>`.
