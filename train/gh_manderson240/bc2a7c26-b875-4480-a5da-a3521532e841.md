### Task 5: Fix GEMM JIT Call-Site Issue

**Objective:** Stop delegating to `ref_kernel` (which adds Python overhead). Call `aiter.get_triton_quant` and `aiter.gemm_a4w4` directly from `submission.py` while maintaining correctness.

**Dependencies:** None

**Files:** Modify `kernels/mxfp4-mm/submission.py`

**Known issue:** Calling `aiter.get_triton_quant(QuantType.per_1x32)` from `submission.py` produces different Triton JIT compilations than from `reference.py`, causing ~82% element mismatches at ~1-3% error.

**Fix strategies:**
1. **Force Triton cache invalidation** — set `TRITON_CACHE_DIR` env var or call `torch.cuda.empty_cache()` before quant
2. **Use `aiter.get_torch_quant`** instead of `get_triton_quant` — torch-based quantization may be deterministic (reference.py uses it in `generate_input`)
3. **Import quant function from reference** — `from reference import ref_kernel` works; try importing just the quant function
4. **Call `get_triton_quant` with explicit kwargs** to match the exact JIT key

**Definition of Done:**
- [ ] `custom_kernel` calls gemm_a4w4 directly (no ref_kernel delegation)
- [ ] Passes `--mode test` with 0.0 max error
- [ ] Benchmark shows improvement over 24 us baseline

**Verify:** `popcorn submit --mode test` passes; benchmark < 20 us

def get_splitk(K: int, BLOCK_SIZE_K: int, NUM_KSPLIT: int):
    # heuristics for make "EVEN_K == True" as much as possible
    NUM_KSPLIT_STEP = 2
    BLOCK_SIZE_K_STEP = 2
    SPLITK_BLOCK_SIZE = (
        triton.cdiv((2 * triton.cdiv(K, NUM_KSPLIT)), BLOCK_SIZE_K) * BLOCK_SIZE_K
    )
    while NUM_KSPLIT > 1 and BLOCK_SIZE_K > 16:
        if (
            K % (SPLITK_BLOCK_SIZE // 2) == 0
            and SPLITK_BLOCK_SIZE % BLOCK_SIZE_K == 0
            and K % (BLOCK_SIZE_K // 2) == 0
        ):
            break
        elif K % (SPLITK_BLOCK_SIZE // 2) != 0 and NUM_KSPLIT > 1:
            NUM_KSPLIT = NUM_KSPLIT // NUM_KSPLIT_STEP
        elif SPLITK_BLOCK_SIZE % BLOCK_SIZE_K != 0:
            if NUM_KSPLIT > 1:
                NUM_KSPLIT = NUM_KSPLIT // NUM_KSPLIT_STEP
            elif BLOCK_SIZE_K > 16:
                BLOCK_SIZE_K = BLOCK_SIZE_K // BLOCK_SIZE_K_STEP
        elif K % (BLOCK_SIZE_K // 2) != 0 and BLOCK_SIZE_K > 16:
            BLOCK_SIZE_K = BLOCK_SIZE_K // BLOCK_SIZE_K_STEP
        else:
            break

        SPLITK_BLOCK_SIZE = (
            triton.cdiv((2 * triton.cdiv(K, NUM_KSPLIT)), BLOCK_SIZE_K) * BLOCK_SIZE_K
        )

    # re-ensuring NUM_KSPLIT is the correct value
    NUM_KSPLIT = triton.cdiv(K, (SPLITK_BLOCK_SIZE // 2))

    return SPLITK_BLOCK_SIZE, BLOCK_SIZE_K, NUM_KSPLIT

`★ Insight ─────────────────────────────────────`
The aiter library has three quantization backends: `get_torch_quant` (pure PyTorch), `get_triton_quant` (Triton JIT), and `get_hip_quant` (AMD HIP C++). Internally, `fused_moe` uses `get_hip_quant` (not Triton) for its quantization — this is key because the GEMM JIT bug is specifically about `get_triton_quant`. The `get_torch_quant` path uses `per_1x32_f4_quant` in pure PyTorch and may be a workaround.
`─────────────────────────────────────────────────`

## Deep Research Findings

### 1. MoE Kernel (`fused_moe`) — 5 Optimization Vectors

**A. `block_size_M` parameter (HIGHEST IMPACT)**
The `fused_moe` function accepts `block_size_M` which controls the tile size along the M (token) dimension. When not set, it defaults to `-1` which triggers auto-tuning via `get_2stage_cfgs()` — which loads from a CSV tuning config file. Key insight: the auto-tuned value is optimized for the MI355X but may not be optimal for our specific E/topk/bs combinations. We can override it:
```python
fused_moe(..., block_size_M=64)   # Try 32, 64, 128
```

**B. `moe_sorting_dispatch_policy` (NEW - not in our submission)**
This parameter controls how tokens are dispatched to experts during sorting. Default is `0`. The sorting implementation has two backends: `moe_sorting_fwd` (default) and `moe_sorting_opus_fwd` (enabled via `AITER_USE_OPUS_MOE_SORTING=1`). Setting `dispatch_policy=1` or trying OPUS sorting could improve load balancing.

**C. `doweight_stage1=True` (already planned)**
Applies `topk_weights` in stage 1 instead of stage 2. This can reduce intermediate buffer memory traffic by multiplying weights before the down projection.

**D. 1-stage vs 2-stage routing**
The `get_2stage_cfgs` function decides between 1-stage and 2-stage execution based on M, inter_dim, and expert count. For MXFP4 with `q_dtype_a=fp4x2`:
- When `token > 32` and `inter_dim % 256 == 0`: uses 1-stage
- When `token <= 16` or `inter_dim % 128 != 0`: uses 1-stage
Key insight: the 1-stage path uses `fused_dynamic_mxfp4_quant_moe_sort` which fuses quantization with sorting — this should be faster for small token counts (bs=16).

**E. `expert_mask` for shared expert separation**
The `fused_moe_dp_share_expert` module shows AMD's own approach to shared expert optimization: running the shared expert as a separate dense operation. The `expert_mask` parameter enables skipping experts not present in the current EP rank. For E=257 configs, we could use `expert_mask` to mark only the 256 routed experts, then compute shared expert separately.

### 2. MLA Kernel (`mla_decode_fwd`) — 4 Optimization Vectors

**A. `NUM_KV_SPLITS` auto-tuning (HIGHEST IMPACT)**
The `get_meta_param` function in `mla.py` has an auto-tuning heuristic that selects optimal `num_kv_splits` based on CU count, batch size, and KV sequence length. Formula:
```python
# Score = gpu_utilization * compute_efficiency
score = (bs * i / ceil(bs*i, cu_num) * cu_num) * (avg_kv / (avg_kv + 84.1 * i))
# Pick i (1-16) with best score
```
**Critical finding:** In non-persistent mode, `num_kv_splits` is capped at 16 and auto-selected. In persistent mode (which we use), we pass `num_kv_splits=32` — but the auto-tuner might choose much lower values (likely 4-8 for small batches). We should try: `{4, 8, 16, 32}` per batch config.

Additionally, for FP8 dtypes, there's a `min_block_n` constraint that further limits splits:
```python
get_block_n_fp8 = {16: 128, 32: 128, 48: 64, 64: 64, 128: 32, 256: 32, 384: 32, 512: 32}
```

**B. Non-persistent mode for small batches**
Persistent mode (with metadata) has overhead for scheduling. For `bs=4` with `kvseqlen=1024`, non-persistent mode uses `get_meta_param` auto-tuning and may be faster because:
- Fewer work items to schedule
- `MAYBE_FINAL_OUT=True` enables writing directly to output (skipping reduction)
- For `nhead=16` and `max_seqlen_q=1`, reduction is optimized with `mgc=64`

To use non-persistent mode, simply don't pass the `work_meta_data` and related kwargs.

**C. `fast_mode=True` in metadata builder**
We use `fast_mode=False`. Looking at `get_mla_metadata_info_v1`:
- `fast_mode=False`: `max_work = tile_cnt * cu_num` (huge work buffer)
- `fast_mode=True`: `max_work = (batch_size + cu_num - 1) * max_qo_tiles_per_batch` (much smaller)

The `fast_mode=True` allocates significantly smaller work buffers, reducing memory overhead. This should be tried for all configs.

**D. `kv_granularity` tuning**
Currently `max(PAGE_SIZE, 16) = 16`. The persistent metadata builder accepts this. Larger values (32, 64) mean fewer, larger KV chunks per split — potentially better memory coalescing but fewer parallelism opportunities.

### 3. GEMM Kernel (`gemm_a4w4`) — 3 Optimization Vectors

**A. Use `get_torch_quant` instead of `get_triton_quant` (FIX JIT BUG)**
The reference's `generate_input` uses `get_triton_quant` but only for B (which is pre-computed and provided as input). For A quantization in `ref_kernel`, it also calls `get_triton_quant`. 

Key insight: `get_torch_quant(QuantType.per_1x32)` maps to `per_1x32_f4_quant` (pure PyTorch). `get_triton_quant(QuantType.per_1x32)` maps to `per_1x32_f4_quant_triton` (Triton JIT). The JIT bug is that Triton produces different JIT compilations from different call-sites.

**Fix strategy:** Use `get_torch_quant` for A quantization. Since B is already pre-quantized and pre-shuffled in the input, we only need to quantize A:
```python
import aiter
from aiter import QuantType, dtypes
torch_quant = aiter.get_torch_quant(QuantType.per_1x32)
A_q, A_scale_sh = torch_quant(A, shuffle=True)
out = aiter.gemm_a4w4(A_q, B_shuffle, A_scale_sh, B_scale_sh, dtype=dtypes.bf16, bpreshuffle=True)
```

**B. `gemm_afp4wfp4` Triton alternative**
The `aiter.ops.triton.gemm.basic.gemm_afp4wfp4` module has a pure-Triton FP4 GEMM with split-K support. For larger M values (64, 256), this may outperform the CK-based `gemm_a4w4` because Triton can auto-tune tile sizes. The reference even mentions it as a comment.

**C. Shape-dependent config lookup**
`gemm_a4w4` uses `get_GEMM_config(M, N, K)` which reads from a tuned CSV file. If the exact shape isn't found, it uses padded_M heuristics. For our small-M shapes (4, 16, 32), the default configs may not be optimal. We can try:
- `splitk` parameter (heuristic: `3` default, but compute_gemm_SplitK suggests 0-4)
- Pre-shuffle A as well (both A and B shuffled)
