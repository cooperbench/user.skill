   114→## 2. Domain Overview — Compound AI and Generative Retrieval Convergence
   115→
   116→### The Compound AI Paradigm (2024–2026)
   117→
   118→Compound AI Systems are defined as systems that tackle AI tasks using multiple interacting components — models, retrievers, tools, orchestrators. The Berkeley AI Research blog (2024) identified this as the defining trend: "leading results can be achieved through clever engineering, not just scaling." By 2025–2026, this is consensus: GitHub Copilot-X achieves >55% developer throughput improvement; radiology pipelines reduce report turnaround 30%. Every major AI lab has shifted from "bigger model" to "better system."
   119→
   120→The key architectural principle is **specialization through structure**: a planner decomposes tasks, a retriever fetches context, an LLM generates outputs, a verifier checks results. Each component does one thing well. The orchestration layer routes work between components.
   121→
   122→Cohezion instantiates this: CompoundExecutor (orchestrator) → SkillSelector (planner/retriever) → ExecutionOrchestrator (executor) → RetrospectionEngine (verifier/refiner) → SkillRefiner (updater). The loop is textbook compound AI architecture.
   123→_Source: [BAIR Compound AI Systems](https://bair.berkeley.edu/blog/2024/02/18/compound-ai-systems/), [Databricks Compound AI](https://www.databricks.com/glossary/compound-ai-systems)_
   124→
   125→### The Generative Retrieval Paradigm (2021–2026)
   126→
   127→Generative retrieval evolved from GENRE (2021, autoregressive entity retrieval) through DSI (2022, differentiable search index) to TIGER (2023, Semantic IDs for recommendation) to STATIC (2025, production-scale constrained decoding at 948×). The core paradigm: instead of embedding items and doing ANN search, train an LLM to autoregressively decode the item's identifier — then constrain the decoding to valid identifiers only.
   128→
   129→The "validity gap" is the central problem: unconstrained LLMs hallucinate invalid item IDs. Constrained decoding with tries (and now CSR matrices via STATIC) closes this gap completely — 100% constraint compliance in YouTube production.
   130→_Source: [TIGER NeurIPS 2023](https://arxiv.org/abs/2305.05065), [GenIR Survey TOIS 2025](https://github.com/RUC-NLPIR/GenIR-Survey)_
   131→
   132→### The Convergence
   133→
   134→The compound AI paradigm needs constrained decoding: when an LLM selects a skill, tool, or routing path from a registry, unconstrained generation produces hallucinated skill names — a validity gap identical to the one TIGER/STATIC solve. The generative retrieval paradigm needs compound loop integration: model quality alone doesn't determine business outcomes; the retrospection/refinement loop that improves models over time is what compound AI contributes.
   135→
   136→**The convergence thesis:** A compound AI system that uses constrained generative retrieval for skill/component selection would be the most reliable, efficient, and self-improving class of AI system currently architecturally feasible.

   160→
   161→The key competitive differentiator for compound AI systems in 2026 is not model quality — it's **orchestration reliability**. Systems that hallucinate tool/skill names, route to invalid destinations, or repeat ineffective paths are qualitatively worse, regardless of underlying model quality. STATIC-class constrained decoding applied to compound loop orchestration would make Cohezion's skill selection provably non-hallucinating — a differentiator no current compound AI framework offers.
   162→
   163→**Barriers to Entry for This Integration:**
   164→- STATIC's codebase is open-source ([github.com/youtube/static-constraint-decoding](https://github.com/youtube/static-constraint-decoding)) — low technical barrier
   165→- 74-skill registry is small enough that preprocessing is trivial (vs. YouTube's 20M)
   166→- Cohezion's Python/JAX-compatible stack aligns with STATIC's implementation

   187→## 5. Technical Convergence Trends
   188→
   189→### Trend 1: From Probabilistic to Deterministic Component Selection
   190→
   191→2025–2026 research consensus: probabilistic routing + deterministic enforcement is the optimal architecture. CRANE (2025) demonstrates adaptive switching between constrained and unconstrained generation based on delimiters. Grammar-Constrained Decoding (ACL 2025) shows grammar-guided generation outperforms free-form for structured outputs. The trend: use LLM reasoning to determine *what* to do, use constrained decoding to ensure *valid execution*.
   192→
   193→Cohezion currently uses probabilistic skill selection (LLM chooses from 74 skills). The upgrade: constrained decoding ensures the LLM's output is always a valid skill name, while preserving the LLM's semantic reasoning about which skill to use.
   194→_Source: [CRANE arXiv:2502.09061](https://arxiv.org/pdf/2502.09061), [Awesome LLM Constrained Decoding](https://github.com/Saibo-creator/Awesome-LLM-Constrained-Decoding)_
   195→
   196→### Trend 2: Semantic Caching with Sparse Acceleration
   197→
   198→2025 research on semantic caching converges on tiered architectures (static + dynamic) with ensemble embeddings achieving 92%+ cache hit ratios. RetrievalAttention (Berkeley/Microsoft) shows that traversing 1–3% of key vectors via ANNS is sufficient for accurate attention — 97–99% of KV pairs are never needed. SentenceKV groups by semantic similarity for further compression.
   199→
   200→Cohezion's L1/L2/L3 semantic cache (95%+ hit rate, current design) aligns with this trend. The upgrade path: replace L2 cosine similarity over all embeddings with sparse CSR-indexed lookup over the valid skill embedding space.
   201→_Source: [RetrievalAttention arXiv:2409.10516](https://arxiv.org/html/2409.10516v2), [SentenceKV arXiv:2504.00970](https://arxiv.org/abs/2504.00970)_
   202→
   203→### Trend 3: RQ-VAE Codebooks as Universal Discrete Representations
   204→
   205→The RQ-VAE architecture — residual quantization producing depth-D stacks of discrete codes — is now deployed across image generation (CVPR 2022), audio codecs (2025), motion synthesis (2025), and recommendation Semantic IDs (TIGER, SEATER, COBRA). The common thread: a continuous high-dimensional representation is discretized into a hierarchical token sequence that can be autoregressively decoded.
   206→
   207→Cohezion's FLUME VAE (256D latent space) is architecturally positioned to adopt this pattern. The upgrade: add residual quantization layers to FLUME VAE output, producing Journey IDs (analogous to Semantic IDs) that can be constrained-decoded to valid journey states.
   208→_Source: [RQ-VAE CVPR 2022](https://arxiv.org/abs/2203.01941), [TIGER NeurIPS 2023](https://arxiv.org/abs/2305.05065)_
   209→
   210→### Trend 4: Self-Evolving Compound Systems with Retrospection
   211→
   212→The 2025 self-evolving agent landscape (Darwin Gödel Machine, AlphaEvolve, WebRL) converges on a shared pattern: execute → observe → retrospect → refine → execute. Retroformer (ICLR 2024) formalizes this as policy gradient optimization over retrospective evaluations. Self-Refine (Madaan et al.) shows 30% error reduction in code benchmarks.
   213→
   214→Cohezion's RetrospectionEngine → SkillRefiner loop is this pattern. The upgrade: use constrained decoding output quality (valid skill hit rate, constraint compliance rate) as an additional retrospection signal — making the compound loop self-optimize toward higher constraint compliance over time.
   215→_Source: [Retroformer ICLR 2024](https://openreview.net/pdf?id=S37hOerQLB), [Self-Evolving Agents](https://github.com/EvoAgentX/Awesome-Self-Evolving-Agents)_

   219→## 6. The Six Integration Points: Cohezion × STATIC
   220→
   221→This is the core deliverable of this domain research. Each integration point is described with: the Cohezion component, the STATIC/generative retrieval pattern it parallels, the current gap, and the proposed integration.
   222→
   223→---
   224→
   225→### Integration Point 1: Skill Registry as Constrained Vocabulary
   226→
   227→**Cohezion Component:** `src/cohezion/skills/skill_registry.json` (74 registered PRIME skills) + `src/cohezion/compound/skill_selector.py`
   228→
   229→**STATIC/Generative Retrieval Parallel:**
   230→In TIGER/STATIC, the item catalog (vocabulary of valid item IDs) is the constraint set. Only items in the catalog can be generated. The trie is built from all valid Semantic ID sequences.
   231→
   232→In Cohezion, the 74 PRIME skills are the constraint set for skill selection. The LLM's task is to generate a valid skill name — but it currently does so unconstrained, risking hallucination of non-existent skill names.
   233→
   234→**Current Gap:**
   235→SkillSelector uses free-form LLM generation to choose a skill. If the LLM generates "data_pipeline_optimizer" but the registry contains "data-pipeline-optimization", the skill lookup fails silently. This is the validity gap — identical to TIGER's hallucination problem.
   236→
   237→**Proposed Integration:**
   238→Build a skill name trie from `skill_registry.json`. At skill selection time, run constrained beam search over skill names using STATIC's VNTK. The LLM's semantic reasoning determines the direction of the beam; the trie ensures the output is always a valid registered skill name.
   239→
   240→**Implementation Complexity:** Low. 74 skills = trivial trie. No TPU required; STATIC's design works on CPU for this scale. Preprocessing cost: microseconds.
   241→
   242→**Expected Impact:** Eliminates skill name hallucination entirely. Measurable metric: skill lookup failure rate → 0%.
   243→
   244→_Source: CLAUDE.md skill registry, [STATIC GitHub](https://github.com/youtube/static-constraint-decoding), [TIGER NeurIPS 2023](https://arxiv.org/abs/2305.05065)_
   245→

   247→
   248→### Integration Point 2: FLUME VAE Codebook as Journey Semantic IDs
   249→
   250→**Cohezion Component:** `src/cohezion/flume/flume_vae.py` (FLUME VAE, 256D latent space, discrete codebook)
   251→
   252→**STATIC/Generative Retrieval Parallel:**
   253→TIGER uses RQ-VAE to quantize item content embeddings into Semantic IDs (depth-D stacks of discrete tokens). STATIC constrains beam search to valid SID sequences. Together, they enable: given a user's history, generate the SID of the next item the user will interact with.
   254→
   255→Cohezion's FLUME VAE produces a 256D latent space that encodes agent trajectory state (12D universe position, coherence, phase). The codebook quantizes these trajectories into discrete tokens — structurally identical to Semantic IDs.
   256→
   257→**Current Gap:**
   258→FLUME VAE's discrete codes are currently used for trajectory reconstruction but not for autoregressive prediction with validity constraints. The compound loop doesn't use the FLUME VAE's codebook to constrain which trajectory states are reachable from the current state.
   259→
   260→**Proposed Integration:**
   261→1. Treat each valid FLUME VAE codebook entry as a Journey ID token
   262→2. Build a transition trie: given current codebook state, what codebook states are valid next states? (This encodes the physics of the 12D universe — HIHO stability constraints become trie edges)
   263→3. Use STATIC-style constrained decoding when the compound loop predicts the next journey state
   264→4. Invalid trajectory predictions (incoherent state transitions) are rejected at the trie level
   265→
   266→**Implementation Complexity:** Medium. Requires building a transition trie from observed valid state transitions in journey history. Preprocessing cost: O(|journeys| × |journey_length|).
   267→
   268→**Expected Impact:** Journey state predictions are always physically valid (HIHO coherent). Drift detection becomes proactive (invalid transitions rejected before execution). Measurable metric: coherence collapse rate → 0 for trie-constrained transitions.
   269→
   270→_Source: CLAUDE.md FLUME VAE description, [RQ-VAE CVPR 2022](https://arxiv.org/abs/2203.01941), [arXiv:2602.22647 STATIC](https://arxiv.org/abs/2602.22647)_
   271→

   273→
   274→### Integration Point 3: SemanticCache CSR Acceleration
   275→
   276→**Cohezion Component:** `src/cohezion/cache/semantic_cache.py` (L1 hash + L2 cosine + L3 vault, 95%+ hit rate)
   277→
   278→**STATIC/Generative Retrieval Parallel:**
   279→STATIC's CSR matrix is essentially a sparse similarity lookup data structure: given a current state, efficiently retrieve the valid next states. The SemanticCache's L2 cosine similarity search is also a nearest-neighbor lookup: given a query embedding, find the closest cached response.
   280→
   281→**Current Gap:**
   282→L2 cosine similarity is O(n) over all cache entries — a linear scan for every query. For a cache with thousands of entries, this becomes a bottleneck under load. RetrievalAttention (Berkeley) showed that only 1–3% of KV pairs are actually needed for accurate retrieval.
   283→
   284→**Proposed Integration:**
   285→1. Index the valid-skill embedding space as a CSR sparse matrix (skill embeddings as row vectors, similar-skill relationships as non-zero entries)
   286→2. Replace L2 linear cosine scan with CSR gather over the top-k similar embeddings
   287→3. Use the same VNTK pattern: speculative slice of B_max similar entries, mask invalid, select top-k
   288→
   289→**Implementation Complexity:** Medium. CSR matrix construction from skill embeddings is straightforward (scipy.sparse or JAX). The ANNS index (HNSW or similar) already serves as an approximate version of this.
   290→
   291→**Expected Impact:** L2 cache lookup from O(n) cosine to O(log n) or O(1) CSR gather. Measurable metric: cache lookup latency reduction at scale.
   292→
   293→_Source: CLAUDE.md SemanticCache description, [RetrievalAttention arXiv:2409.10516](https://arxiv.org/html/2409.10516v2), [SentenceKV arXiv:2504.00970](https://arxiv.org/abs/2504.00970)_

   297→### Integration Point 4: Cold-Start Skill Discovery
   298→
   299→**Cohezion Component:** `src/cohezion/compound/skill_refiner.py` + `src/cohezion/skills/` (134 .md PRIME skill files, 74 registered)
   300→
   301→**STATIC/Generative Retrieval Parallel:**
   302→STATIC's YouTube deployment demonstrated cold-start enablement: items not seen during training (new videos) could be recommended by constraining the model to a freshness allowlist. Recall@1 for cold-start items went from 0.00% to measurable.
   303→
   304→Cohezion has 134 PRIME skill files but only 74 registered. New skills added to the registry have no execution history — the compound loop has no basis to recommend them, creating a cold-start problem identical to new item recommendation.
   305→
   306→**Current Gap:**
   307→New PRIME skills are invisible to the compound loop until they accumulate history. This creates a compounding disadvantage: new skills never get recommended → never executed → never refined → never improve. The 60 unregistered skills (134 - 74) may be in this cold-start limbo.
   308→
   309→**Proposed Integration:**
   310→1. Define a "new skill freshness window" (e.g., skills created in the last 30 days)
   311→2. Build a constraint set |C_new| of fresh skills
   312→3. Periodically run compound loop iterations with the constraint set |C_new| — forcing the loop to explore new skills in appropriate contexts
   313→4. Measure exploration hit rate (did the new skill produce valid results?) as a registration criterion
   314→
   315→This mirrors YouTube's freshness constraint (last 7 days) exactly.
   316→
   317→**Expected Impact:** New skills transition from cold-start to active registry in a governed, measurable way. Measurable metric: time-to-first-execution for new skills, and skill registry growth rate.
   318→
   319→_Source: CLAUDE.md skill architecture, [STATIC YouTube deployment](https://arxiv.org/abs/2602.22647), [Generative Cold-Start Methods](https://www.emergentmind.com/topics/generative-cold-start-methods)_
   320→
   321→---
   322→
   323→### Integration Point 5: Compound Loop Beam Search
   324→
   325→**Cohezion Component:** `src/cohezion/compound/executor.py` (11-step execution pipeline) + `src/cohezion/compound/plan_executor.py`
   326→
   327→**STATIC/Generative Retrieval Parallel:**
   328→Generative retrieval uses beam search (typically beam size 20–70) to generate multiple candidate item sequences simultaneously, then selects the top-k by score. The beam search explores the possibility space; the trie constraint ensures all beams stay in valid territory.
   329→
   330→Cohezion's CompoundExecutor currently executes a single plan path. Multi-skill beam search would execute the top-B skill sequences simultaneously, then select the one with the highest coherence/alignment score — more robust, especially for ambiguous requests.
   331→
   332→**Current Gap:**
   333→Single-path execution means one bad SkillSelector decision propagates through the entire 11-step pipeline. Beam search would provide k-best alternatives, making the compound loop resilient to individual step failures.
   334→
   335→**Proposed Integration:**
   336→1. Modify PlanExecutor to generate top-B skill sequences via constrained beam search (B=3 or B=5 — far less than YouTube's B=70, appropriate for compound loop latency budget)
   337→2. Execute the top B sequences in parallel (Cohezion already supports 5 sub-agents)
   338→3. Score results via RequestAlignmentAnalyzer coherence metric
   339→4. Select the highest-scoring valid result
   340→
   341→**Implementation Complexity:** High. Requires parallel execution infrastructure for beam paths and a scoring mechanism that can compare across beams. Cohezion's existing 5-sub-agent support partially addresses parallelism.
   342→
   343→**Expected Impact:** Compound loop robustness to single-step failures. Measurable metric: first-attempt success rate (coherence > 0.5 on first execution) vs. current baseline.
   344→
   345→_Source: CLAUDE.md CompoundExecutor description, [Constrained Beam Search Recommendation](https://www.arxiv.org/pdf/2507.22224), [TIGER NeurIPS 2023](https://arxiv.org/abs/2305.05065)_

   349→### Integration Point 6: Expert Domain Lattice as Structured Trie
   350→
   351→**Cohezion Component:** Expert Domain Lattice (Architect, Engineer, Biologist, QHW, QAlgo) in `src/cohezion/swarm/cost_aware_router.py`
   352→
   353→**STATIC/Generative Retrieval Parallel:**
   354→STATIC's trie encodes a hierarchical vocabulary: each level of the trie narrows the valid output space. The Expert Domain Lattice is exactly a hierarchical routing vocabulary: top-level domain (science, engineering, biology) → specialist (QHW, QAlgo) → sub-specialist.
   355→
   356→**Current Gap:**
   357→The Expert Domain Lattice routing is currently implemented as a set of conditional branches and heuristics in the CostAwareRouter. Hallucinated domain names (a domain the router hasn't seen) cause silent fallbacks. There's no guarantee the router outputs a valid registered agent name.
   358→
   359→**Proposed Integration:**
   360→1. CSR-encode the Expert Domain Lattice as a routing trie: root → domain → specialist → sub-specialist
   361→2. At routing time, constrained decode the target agent path through the lattice
   362→3. Each step in the constrained decode narrows the valid next routing options (Architect → can't route to Biologist as a direct child, must go through the correct domain)
   363→4. Invalid routing destinations (hallucinated agent names) are rejected at the trie level
   364→
   365→**Implementation Complexity:** Low-Medium. The lattice is small (5 top-level domains, ~15 specialists). Trie construction is trivial. The CSR matrix would be tiny (<1KB).
   366→
   367→**Expected Impact:** Zero invalid routing destinations. Measurable metric: routing failure rate → 0%.
   368→
   369→_Source: CLAUDE.md Expert Domain Lattice description, [MasRouter Multi-Agent Routing](https://arxiv.org/html/2602.21227), [arXiv:2602.22647 STATIC](https://arxiv.org/abs/2602.22647)_

   429→## 8. Future Outlook — Self-Evolving Constrained Compound Systems
   430→
   431→### Near-Term (2026)
   432→
   433→**Retrospection-Driven Constraint Tuning:** The compound loop's RetrospectionEngine already measures skill coherence and identifies drift. Extending this to measure constraint compliance (did the selected skill appear in the valid vocabulary? did the routing path stay in the domain lattice?) creates a feedback signal for automatic constraint set evolution — adding new skills to the trie when they demonstrate sustained performance, pruning skills that consistently underperform.
   434→
   435→**MCP-Exposed Constrained Skill API:** Wrapping Cohezion's constrained skill selector as an MCP tool would expose it to external agents — enabling other Claude Code sessions, Gemini CLI tasks, or OpenCode agents to invoke Cohezion's skill registry with validity guarantees.
   436→
   437→### Medium-Term (2026–2028)
   438→
   439→**Journey ID Registry:** A persistent registry of valid Journey IDs (FLUME VAE trajectories that led to coherent outcomes) would enable the compound loop to constrain future trajectories to proven paths — analogous to STATIC's freshness constraint but for trajectory quality. New journeys that successfully complete with high coherence are added to the registry; failed journeys are pruned.
   440→
   441→**Cross-Session Constrained Retrieval:** As Cohezion's vault accumulates decision/experiment/pattern knowledge, the constraint trie can be built from vault content — ensuring generated skill sequences correspond to vault-validated patterns. This closes the knowledge management loop: vault knowledge informs constraints; constrained decoding enforces vault knowledge.
   442→
   443→### Long-Term (2028+)
   444→
   445→**Self-Growing Constraint Trie:** The compound loop learns which skill sequences lead to coherent outcomes and automatically extends the constraint trie with new valid paths — a generalization of STATIC's offline preprocessing toward online trie updates. The trie becomes a living record of validated compound engineering patterns.

## Executive Summary

Cohezion's compound engineering loop is a generative retrieval system operating without the constraints that make generative retrieval reliable in production. Its `SkillSelector` autoregressively selects from a 74-skill registry using open-vocabulary LLM generation — the exact validity gap that STATIC (arXiv:2602.22647) eliminates at YouTube's 20M-item scale using vectorized trie-constrained decoding. **Problem being solved:** Three compounding failure modes in the compound loop today — (1) skill name hallucination (LLM generates non-existent skill names, silently failing lookups), (2) cold-start invisibility (60 unregistered PRIME skills with no execution history are never recommended), and (3) routing failures in the Expert Domain Lattice (invalid agent names cause silent fallbacks). These are not edge cases — they are structural properties of unconstrained generation over a finite vocabulary.

### What Makes This Special

**The core insight:** Cohezion does not need to become a generative retrieval system — it already is one. The 74-skill `skill_registry.json` is an item catalog. PRIME skill names are Semantic IDs. The FLUME VAE codebook is a RQ-VAE quantization. The compound loop is a generative retrieval decoder. STATIC's open-source CSR-matrix constrained decoding is directly applicable at Cohezion's scale with trivial preprocessing cost.

**The differentiation:** No current compound AI framework (LangChain, AutoGen, CrewAI, DSPy) applies hard constraints to skill/tool selection. All use open-vocabulary generation, accepting hallucination as a runtime error to handle. Cohezion will be the first compound AI system where skill selection is provably non-hallucinating — not by filtering outputs, but by structurally constraining the generation space.

**The implementation gradient:** P0 integrations (skill name trie, cold-start freshness window) ship in 2–3 days with immediate measurable impact. P3 (compound loop beam search) delivers architectural resilience over 2–3 weeks. The six integration points are dependency-ordered: each P-level builds on the previous.
