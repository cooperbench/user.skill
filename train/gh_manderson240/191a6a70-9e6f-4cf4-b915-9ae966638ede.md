## 1. The Compound Module Is Becoming a Monolith

**79 Python files. 176 classes. 8 subdirectories.** The `compound/` module is the heart of Cohezion, but it's accumulating mass faster than it's being refactored.

`executor.py` alone is **1,123 lines** with **22 try/except blocks** and **13 lazy imports** to avoid circular dependencies. That's a code smell — when you need lazy imports *inside method bodies* to break cycles, the dependency graph has grown beyond what the module boundary can contain.

`★ Insight ─────────────────────────────────────`
Lazy imports in method bodies (lines 165, 184, 201, 219, 254-257, 315, 535, 577, 591) are a **dependency graph symptom**, not a solution. Each one is the codebase telling you "these things should be decoupled." The `CompoundExecutor` constructor takes ~18 optional parameters — it's become a God Object that orchestrates everything.
`─────────────────────────────────────────────────`

**What I'd want to see:** Extract the executor into a lean coordinator that delegates to protocol-based subsystems. The `guardrail_pipeline`, `skill_refiner`, `alignment_analyzer`, `journey_tracker`, `degradation_detector` — each accessed via lazy property — should be injected via a registry or plugin system, not wired inline.

---

## 2. 180 Bare `except Exception` Catches in Compound Alone

The "non-blocking" philosophy is correct — vault logging shouldn't crash execution. But **180 broad exception catches** means failures are silently swallowed at scale. When *everything* is non-blocking, nothing is observable.

**What I'd want to see:** A structured error budget. Categorize exceptions into:
- **Must propagate:** Correctness failures (alignment < threshold, data corruption)
- **Log and continue:** Infrastructure failures (vault offline, cache miss)
- **Aggregate and alert:** Repeated patterns (same exception 5x in 10 minutes → DegradationDetector alert)

Right now, the `DegradationDetector` monitors metrics, but it doesn't monitor *error rates from the swallowed exceptions*. That's a blind spot.

---

## 3. The API `__init__.py` Is 1,984 Lines

A single `__init__.py` file with nearly 2,000 lines of route definitions means every import of `cohezion.api` loads the entire API surface. This violates the file-size limit in your own CLAUDE.md (300 soft, 500 hard).

**What I'd want to see:** Router-based decomposition. FastAPI routers are purpose-built for this — split into `api/compound_routes.py`, `api/swarm_routes.py`, `api/mcp_routes.py`, etc., and include them in the app factory.

---

## 4. The Knowledge Compounding Loop Doesn't Close on Itself

This is the most *interesting* gap. Cohezion's compound loop is: query vault → execute → log → extract patterns. Beautiful. But the extracted patterns aren't systematically *validated* before being reused as guidance.

The `SkillRefiner` updates skill definitions. The `SkillConsensusVoter` validates selections. But there's no equivalent of **experience validation** — confirming that a pattern extracted from run N actually improves run N+1. The loop assumes compounding, but doesn't measure it.

`★ Insight ─────────────────────────────────────`
This is the difference between **accumulation** and **compounding**. Accumulation is additive (more patterns in vault). Compounding is multiplicative (each pattern makes future patterns better). Right now, the vault grows but there's no feedback signal that says "this pattern was reused and improved outcomes by X%." Adding that signal would make the compound loop truly compound.
`─────────────────────────────────────────────────`

**What I'd want to see:** A `PatternEfficacyTracker` — when vault guidance is used, tag the execution with which patterns were applied, then compare outcomes to unguideded baselines. Over time, prune patterns that don't demonstrably help.

---

## 5. Overlapping Persistence Layers

I count at least 4 persistence-related subsystems in compound alone:
- `exp_persistence/vault.py` — execution logging to vault
- `persistence.py` — session state
- `metrics_persistence.py` — metrics
- `thermal_history_persistence.py` — thermal state
- `cache_persistence.py` — cache state
- `session_manager.py` (728 lines) — checkpoints

Plus the top-level `src/cohezion/persistence/` module. And `src/cohezion/storage/`. That's **persistence scattered across 3 layers** without a unified persistence abstraction.

**What I'd want to see:** A `PersistenceGateway` protocol that all subsystems write through. One place to configure whether state goes to SurrealDB, JSONL, vault, or in-memory. Right now, each module makes its own persistence choices independently.

What's missing is **integration tests that run the actual compound loop** with a real (or in-memory) vault, proving the query → execute → log → extract cycle works end-to-end.

**What I'd want to see:** A small integration test suite that creates a vault in `/tmp`, runs 3 compound cycles, and asserts that cycle 3 performs better than cycle 1 because it benefited from guidance extracted in cycles 1-2. This would be the **proof** that compounding works.
