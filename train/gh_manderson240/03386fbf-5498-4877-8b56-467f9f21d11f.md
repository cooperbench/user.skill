   162→If a previously-passing kernel suddenly "fails", try a retry before debugging the kernel code.

# K-Search: LLM Kernel Generation via Co-Evolving World Model - Summary

## Core Innovation

K-Search introduces a paradigm shift in LLM-based GPU kernel optimization by treating Large Language Models as **co-evolving world models** rather than simple code generators. The key insight is that effective kernel optimization requires decoupling high-level algorithmic planning from low-level program instantiation.

## Step-by-Step Methodology

The system operates through three iterative phases:

1. **Action Selection**: Select the highest-priority pending optimization action from a maintained frontier, scored by the LLM world model (V-score ranging 0-1)

2. **Program Instantiation (Local Refinement)**: Generate concrete CUDA implementations via stochastic sampling until reaching a stagnation threshold (K consecutive unsuccessful attempts), isolating logical intent from implementation noise

3. **World Model Co-Evolution**: The LLM analyzes execution trajectories and updates the search state through three tree operations:
   - **Insert**: Propose new child optimization actions
   - **Update**: Recalibrate priority scores based on empirical results
   - **Prune**: Remove infeasible branches

## Key Abstractions for GPU Kernel Optimization

The framework introduces several critical abstractions:

- **Search State**: An explicit tree structure partitioned into Closed nodes (completed actions with attached programs) and Open nodes (frontier actions awaiting exploration)

- **Proposed Optimization Tuples**: (parent_program, intent_description) pairs that represent high-level strategies like "resolve bank conflicts via padding"

- **Stagnation-Bounded Local Refinement**: Prevents discarding valid strategies due to transient syntax errors by repeatedly sampling implementations until improvement plateaus

## Specific Techniques and Algorithms

**Algorithm 1 (K-Search)** implements the core loop:
```
Initialize search state with high-level actions
While budget remains:
  Select best frontier action by V-score
  Iteratively refine implementations (max K attempts without improvement)
  Update search state via LLM reasoning (Insert/Update/Prune operations)
```

The approach explicitly structures optimization as planning over a tree rather than direct program space search, enabling the model to track which optimizations compose effectively.

## Performance Results & Application Domains

**FlashInfer Kernel Suite** (primary evaluation):
- "2.10× improvement over OpenEvolve and 2.21× improvement over ShinkaEvolve" across diverse kernels
- 14.3× improvement on FP8 MoE kernels (complex irregular routing and computation)
- Applied to: GQA paged decode, MLA (multi-level attention) kernels, MoE routing kernels

**GPUMODE TriMul Competition**:
- Achieved "state-of-the-art performance...1030 µs on H100" for AlphaFold3's triangle multiplicative update kernel
- Surpassed prior human-designed and RL-based solutions using 300 iterations

**Key Technical Distinctions Observed in Generated Kernels**:
- K-Search kernels utilize deeper prefetch pipelines (loading 2+ chunks ahead vs. single double-buffering)
- Register-resident query vectors versus shared-memory staging
- Adaptive split-K parallelism based on sequence length
- Warp-level cooperation for routing instead of atomic-based persistent kernels

The methodology demonstrates that maintaining explicit reasoning about optimization strategies, rather than raw program evolution, enables discovery of "non-monotonic optimization paths" requiring coordinated multi-step structural transformations.

# Autoresearch: Architecture & Methodology

## 1. What is Autoresearch?

Autoresearch is an autonomous AI research framework that allows "an AI agent a small but real LLM training setup and let it experiment autonomously overnight." Rather than humans directly modifying code, researchers define objectives in a markdown file while AI agents iteratively improve a GPT model through automated experimentation cycles.

## 2. End-to-End Pipeline

The workflow operates in discrete cycles:

1. **Initialization**: Agent reads `program.md` (human-written research instructions)
2. **Code Modification**: Agent edits only `train.py` (model, architecture, hyperparameters)
3. **Training**: Fixed 5-minute wall-clock training run (regardless of hardware)
4. **Evaluation**: Metric computed—`val_bpb` (validation bits per byte, lower is better)
5. **Decision**: Agent keeps changes if metrics improved, discards otherwise
6. **Repetition**: Cycle repeats autonomously

This enables "approx 12 experiments/hour and approx 100 experiments while you sleep."

## 3. Tools & Models Used

- **Training Framework**: PyTorch-based single-GPU implementation
- **Base Code**: Simplified version of Karpathy's nanochat
- **Optimizer Options**: Muon + AdamW hybrid
- **Tokenization**: BPE (Byte Pair Encoding)
- **Architecture**: GPT-style transformer with configurable depth, attention patterns
- **Dataset**: OpenWebText (with TinyStories recommended for smaller systems)

## 4. Code Generation, Testing & Iteration

**Modification Scope**: The agent exclusively modifies `train.py`, which contains:
- Full GPT model implementation
- Optimizer configuration
- Training loop logic
- Hyperparameters (batch size, learning rate, dropout, etc.)

**Testing Mechanism**: Each experiment automatically trains, evaluates validation loss, and logs results. The agent itself determines whether changes constitute improvement based on `val_bpb` metrics.

## 5. Key Configuration Options

Core tuning parameters:

| Parameter | Purpose | Adjustable By |
|-----------|---------|---------------|
| `DEPTH` | Model complexity (layer count) | Agent via train.py |
| `DEVICE_BATCH_SIZE` | Tokens per GPU forward/backward | Agent via train.py |
| `TOTAL_BATCH_SIZE` | Global batch size | Agent via train.py |
| `MAX_SEQ_LEN` | Sequence length | Human via prepare.py |
| `WINDOW_PATTERN` | Attention mechanism type | Agent via train.py |
| `vocab_size` | Tokenizer vocabulary | Agent via train.py |

**Human Configuration**: Defined in `program.md`—instructions, experimental objectives, and constraints for the agent.

## 6. Results & Demonstrated Outcomes

The repository includes `progress.png` showing experimental iteration graphs, though specific numerical improvements aren't detailed in the documentation. The project demonstrates proof-of-concept with "33 Commits" tracking successful autonomous research cycles.

## Architectural Philosophy

Three core design principles:
- **Single Modification Point**: Only `train.py` changes, keeping diffs reviewable
- **Hardware-Agnostic Budgeting**: Fixed 5-minute runtime ensures fair comparisons across platforms
- **Self-Contained**: No distributed training complexity; one GPU, minimal dependencies

### Part 1: K-Search Tree Structure (ksearch_tree.py)

The K-Search tree stores optimization hypotheses as nodes. Each node represents a **strategy** (high-level optimization intent), not specific code. This is the core K-Search principle: decouple planning from implementation.

**Tree node schema:**
```python
@dataclass
class KNode:
    id: str                     # Unique node ID
    strategy: str               # Human-readable optimization intent
    parent_id: str | None       # Parent node (None for root)
    priority: float             # V in [0,1] -- world model confidence
    attempts: int               # How many times instantiated
    best_result_us: float | None  # Best microsecond timing achieved
    stagnation_count: int       # Consecutive non-improvements (K=7 threshold)
    status: str                 # "active", "exhausted", "champion"
    parameters: dict            # Concrete parameter values for this strategy
    children: list[str]         # Child node IDs
    notes: str                  # What was learned from attempts
```

**Tree operations (mapping K-Search paper Section 3):**

1. **INSERT** -- Add child node when a new optimization direction is discovered from analysis
2. **UPDATE** -- Modify priority based on execution feedback (Bayesian update)
3. **PRUNE** -- Mark as "exhausted" when stagnation_count >= K=7
4. **SELECT** -- Pick highest-priority active node for next instantiation

### Part 3: R-Zero Challenger/Solver Mapping

**Challenger role** (generates harder optimization targets): The K-Search tree itself acts as the Challenger. When a node achieves a new best, the `expand_node()` function creates child nodes that represent harder optimization targets -- tighter parameter bounds, combinations of strategies, or entirely new approaches.

**Solver role** (attempts solutions): The Ollama-powered `generator.py` acts as the Solver. Given a tree node's strategy description and parameters, it generates concrete submission.py code.

**Co-evolution:** When the Solver consistently fails on a node (stagnation), the Challenger adapts by pruning that branch and generating new strategies informed by the failure patterns. This is implemented via the `analyzer.py` module which reads the results JSONL and identifies:
- Which parameter ranges never work
- Which shape combinations are bottlenecks
- What strategies succeeded on similar problems

The question is whether aiter's `mla_decode_fwd` accepts MXFP4 dtypes. Looking at the metadata call:

If you pass `aiter_dtypes.fp4x2` as `kv_dtype`, it might work. This is the highest-leverage experiment for MLA.
