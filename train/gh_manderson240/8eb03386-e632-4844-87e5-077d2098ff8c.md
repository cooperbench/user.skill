```
## Architecture: DAG-Based Execution

A marimo notebook is modeled as a directed acyclic graph (DAG) on cells, where an edge (u, v) means cell v reads a variable defined by u. Variable definitions and references are statically inferred, with no runtime tracing, meaning there's no runtime overhead associated with the graph.

marimo creates a dataflow graph where each cell becomes a node and edges represent variable dependencies — when a cell changes, everything that depends on it updates automatically using static construction rather than runtime tracing.

## Reactive Execution Model

marimo is a reactive Python notebook: run a cell or interact with a UI element, and marimo automatically runs dependent cells (or marks them as stale), keeping code and outputs consistent.

The runtime enforces a simple rule: when a cell runs, all descendants (cells referencing its definitions) are automatically marked for execution. Unlike other reactive platforms that re-run the whole program, marimo only runs what actually needs updating.

marimo lets you configure the runtime to be lazy, marking affected cells as stale instead of automatically running them, giving you guarantees on program state while preventing accidental execution of expensive cells.

## Key Features

- **Pure Python storage**: marimo notebooks are stored as pure Python (with first-class SQL support), executable as scripts, and deployable as apps.

- **Deterministic execution**: Notebooks are executed in a deterministic order, based on variable references instead of cells' positions on the page.

- **No hidden state**: Delete a cell and marimo scrubs its variables from program memory, eliminating hidden state.

- **Batteries-included**: marimo comes with GitHub Copilot, AI assistants, Ruff code formatting, HTML export, fast code completion, a VS Code extension, an interactive dataframe viewer, and many more quality-of-life features.

- **Package management**: marimo solves reproducibility challenges with tight uv integration — dependencies get inlined at the top of notebooks following PEP 723 standards, ensuring everyone runs your code with exactly the same package versions.

- **SQL integration**: SQL cells allow building queries that depend on Python values and executing them against dataframes, databases, lakehouses, CSVs, Google Sheets, or anything else. Notebooks are still pure Python, even if they use SQL.

- **Multiple execution modes**: marimo supports pure Python storage format for Git-friendly version control, reactive execution model via static dependency analysis, and multiple execution modes (edit, run, script, WASM).

## Why It Matters: Solving the Reproducibility Crisis

Traditional notebooks have a reproducibility crisis. In 2019, a study found that of nearly 1 million Jupyter notebooks on GitHub with valid execution orders, only 24% could be re-run, and just 4% reproduced the same results. A similar 2020 study by JetBrains found that over a third of notebooks on GitHub had invalid execution histories.

## Constraints

marimo uses static analysis to build a dependency graph from variable references and definitions. Each global variable must be defined by exactly one cell, and marimo does not track object mutations (like `list.append()`).
```

# marimo MCP Server & Client Technical Details

## Starting marimo as MCP Server

**Installation methods:**
- `uv run --with="marimo[mcp]" marimo edit notebook.py --mcp --no-token`
- `uvx "marimo[mcp]" edit notebook.py --mcp --no-token`
- `pip install "marimo[mcp]"` then `marimo edit notebook.py --mcp --no-token`

**Key flags:**
- `--mcp`: Exposes the MCP server endpoint for external applications
- `--no-token`: Removes authentication (development only; remove for production)
- `--mcp-allow-remote`: Disables DNS rebinding protection for proxies/CDNs

# marimo MCP Technical Architecture

## Concurrency Bridge Design

The implementation addresses a fundamental tension: marimo's reactive runtime continuously updates when code changes, while MCP expects stable responses to incoming requests. The solution involves a **concurrency bridge that ensures each MCP call receives a consistent snapshot of the notebook without freezing the reactive engine.**

## Snapshot Consistency Guarantees

Rather than locking the entire runtime, the architecture provides isolated views of notebook state. Each MCP request captures a point-in-time representation of execution data—cell outputs, variable states, error tracebacks—without blocking the underlying reactive system from processing subsequent user interactions.

## Tool Composability Strategy

The design emphasizes composable building blocks with standardized identifiers. Tools share consistent fields like notebook session IDs, cell IDs, and data signatures, enabling downstream tools to chain outputs as inputs. This supports workflows where one tool's result feeds into another's analysis.

Key tool categories include:
- **Inspection**: notebook discovery and cell mapping
- **Data**: variable and database table access  
- **Debugging**: error extraction and analysis
- **Reference**: marimo-specific rules and constraints

## Tool Schema Design

Each MCP tool has an explicit schema expressing dynamic notebook state in machine-readable form. This prevents ambiguity and allows AI systems to build reasoning chains on solid semantics. The schema design prioritizes safety through read-only access patterns.

## AI Agent Integration Patterns

The architecture treats MCP as "structured collaboration, not automation." Agents gain reliable context via well-typed tools while humans maintain control. Multi-tool workflows enable end-to-end notebook diagnostics: auditing errors across notebooks, detecting schema drift in datasets, and auto-generating documentation from code structure.

# LLM Provider Configuration in marimo

marimo supports multiple LLM providers configured through the Settings panel or `marimo.toml`. Access your config location with `marimo config show`.

## Model Roles & Routing

Three model roles exist, specified as `provider/model`:
- **chat_model**: Chat panel functionality
- **edit_model**: Cell refactoring and AI generation
- **autocomplete_model**: Inline code completion

## Supported Providers

### OpenAI
Requires `pip install openai`
```toml
[ai.models]
chat_model = "openai/gpt-4o-mini"
edit_model = "openai/gpt-4o"

[ai.open_ai]
api_key = "sk-proj-..."
```

### Anthropic
```toml
[ai.models]
chat_model = "anthropic/claude-3-7-sonnet-latest"

[ai.anthropic]
api_key = "sk-ant-..."
```

```toml
[ai.models]
```
