## The Core Problem

An agent needs to answer two questions at any moment:

1. **"What exists?"** — What are all the raw assets and what's in them, indexed semantically?
2. **"What is the current edit?"** — What does the assembled video look like right now, described in a way I can read and reason about?

These are two distinct layers, and getting the separation right is everything.

---

## Layer 1: Asset Profiles (Pre-computed, per file)

Before any editing happens, you run an ingest pass over every source file. This produces a sidecar YAML for each asset that captures all its semantic content. These are computed once and never change (since the source files don't change).

**For audio files**, you run Whisper (or equivalent) to get a word-level transcript with timestamps. You store both the raw word timestamps and sentence-level groupings, because agents need different granularities for different tasks — word-level to find exact cut points, sentence-level to understand content:

```yaml
# asset_profiles/input.MP3.yaml
id: input-mp3
file: inputs/input.MP3
type: audio
duration_s: 98.45

transcript:
  words:
    - { start: 0.0,  end: 0.42, word: "Welcome" }
    - { start: 0.42, end: 0.61, word: "to" }
    - { start: 0.61, end: 0.89, word: "our" }
    # ...
  segments:
    - { start: 0.0,  end: 4.2,  text: "Welcome to our announcement today." }
    - { start: 4.2,  end: 9.1,  text: "We've been working on something special." }
    - { start: 9.1,  end: 14.6, text: "Let me show you what we built." }
    # ...
```

**For video files**, the challenge is that you can't run VLM on every frame — that's 60 descriptions per second for demo-one. The right approach is scene-change detection first (ffmpeg has a built-in scene change filter that marks frames where the visual content shifts significantly), then force additional keyframes every ~2-3 seconds as a floor so you never have a long gap. Each detected keyframe gets described by a VLM. If the video has audio, you also transcribe it.

```yaml
# asset_profiles/demo-one.mp4.yaml

  # ...

transcript:
  segments:
    - { start: 0.0,  end: 3.4,  text: "Okay so here's what we actually built." }
    # ...
```

**For images**, just one VLM description:

## Layer 2: The Timeline (The Edit State)

The timeline is the actual edit — it's what you're manipulating. It has separate video and audio tracks, because one of the most common things you do in video editing is lay a single continuous audio track (the voiceover) over a sequence of different video clips. Decoupling them is essential.

Each clip has four numbers: which asset, where to start within that asset, where to end within that asset, and where it sits in the final output timeline. That's all you need to describe any edit unambiguously.

```yaml
# timeline.yaml
output_resolution: "1920x1080"
output_fps: 30

video_track:
  - { clip_id: v001, asset_id: demo-two-mp4,    source_start: 0.0,  source_end: 2.0,  timeline_start: 0.0  }
  - { clip_id: v002, asset_id: demo-one-mp4,    source_start: 6.0,  source_end: 20.0, timeline_start: 2.0  }
  - { clip_id: v003, asset_id: example-image1,  source_start: 0.0,  source_end: 3.0,  timeline_start: 16.0 }

audio_track:
  - { clip_id: a001, asset_id: input-mp3,       source_start: 0.0,  source_end: 45.0, timeline_start: 0.0  }
```

This is the ground truth. When a render happens, this file is compiled to an ffmpeg command. When an agent edits the video, this file is what changes.

This is the key insight — you don't ask the agent to read the timeline YAML and cross-reference asset profiles. Instead, you generate a third artifact: a rendered text view that joins the timeline with the asset profiles, so everything the agent needs to understand the current video is in one place, ordered by time.

This is generated on-demand, never stored permanently:

## The Agent's Tool Set

With those three layers in place, the agent needs just a small set of tools:

- **`ingest_asset(file)`** — runs transcription + VLM on a file, writes asset profile
- **`view_timeline()`** — generates and returns the timeline view above
- **`search_transcript(query)`** — searches across all asset profiles' transcripts, returns matching segments with timestamps
- **`search_visual(query)`** — searches visual_segments descriptions across all profiles
- **`edit_timeline(operation)`** — modifies timeline.yaml; operations like `append_clip`, `insert_clip`, `remove_clip`, `trim_clip`, `replace_audio`
- **`render(preview=True)`** — compiles to ffmpeg and produces output (preview = lower resolution/quality for fast iteration)

The search tools are what make this fast to work with. Instead of the agent having to page through asset profiles, it asks "find where they say the word dashboard" and gets back `demo-one.mp4 @ 12.3s` immediately. Then it can clip exactly there.

## On Existing Formats

There are a few existing formats worth knowing about:

- **EDL (Edit Decision List)** — the old broadcast standard, still used, extremely terse. Designed for tape-to-tape editing. Completely unreadable to an agent (or a human).
- **OTIO (OpenTimelineIO)** — an open standard from Pixar/Apple, JSON-based, represents exactly this kind of timeline with tracks and clips. Good format, but no semantic annotation layer and requires the Python library to work with it meaningfully. Could be worth using as the underlying timeline format (rather than custom YAML) because it interops with Resolve, Premiere, etc. But it's more complexity up front.
- **FCPXML** — Final Cut Pro's XML format. Very verbose, tightly coupled to FCP's data model.

None of them have the annotation/semantic layer. That's the novel piece here — the asset profiles with pre-computed semantic metadata, and the generated timeline view that joins them. Everything else is more or less standard NLE concepts.

**Recommendation: custom YAML for now.** It's trivial to read and write, compiles cleanly to ffmpeg, and you can always export to OTIO later if you need NLE interop. The value of this system isn't in the timeline format, it's in the asset profile layer and the view generation.

---

## The Key Design Principle

**The underlying assets are never touched.** The timeline.yaml is just an instruction set that says "take these bytes from this file, these bytes from that file, assemble them in this order." Rendering always goes: `timeline.yaml + asset_profiles/` → ffmpeg command → output file. You can render infinite different outputs from the same source files by changing only the timeline.

Want to try a different cut? Change two numbers in the timeline, re-render. The original files are untouched. The asset profiles (which were expensive to generate — transcription + VLM) are reused forever. That's the right architecture.
