# Plan: Zone Classification System + TS Line Classifier

## Context

The system treats all files identically — test files, config files, generated code, production code all flow through the same detectors with the same thresholds and contribute equally to the health score. This produces two systemic false positive sources:

1. **Duplicate detection on test files** — Test files naturally share setup patterns, assertion structures, fixtures. The dupes detector (80% threshold) flags these as duplicates, flooding the Duplication dimension.
2. **Regex-based TS detection with no context filtering** — The 9 regex-based TS smell checks run on raw text with zero string/comment awareness, unlike Python which has `_build_string_line_set` + `_match_is_in_string`.

Root cause: the system has no concept of **file intent**. The fix is zone classification as a first-class architectural concept — deterministic, path-based, computed at scan time, flowing through to findings, scoring, and the LLM.

## Architecture

### Zone Taxonomy

```
PRODUCTION  — Default. Application source code. Full scoring weight.
TEST        — Test files, fixtures, stories, mocks. Excluded from score.
CONFIG      — Build configs, settings. Excluded from score.
GENERATED   — Auto-generated code. Excluded from score.
SCRIPT      — CLI tools, dev utilities. Included in score.
VENDOR      — Vendored third-party. Excluded from score.
```

### Who Classifies

The **tool** classifies — deterministic, path-pattern-based, per-language rules. No LLM involvement. Classification happens once per scan in `_generate_findings_from_lang()`. The LLM **consumes** zone metadata in query.json to reason about findings.

### Data Flow

```
find_*_files() → list[str]              # unchanged
    ↓
_generate_findings_from_lang():
  1. Build FileZoneMap(files, lang.zone_rules)    # classify once
  2. Set lang._zone_map = map                     # thread to phase runners
  3. Run phases (phase runners access lang._zone_map)
  4. Stamp f["zone"] on each finding              # alongside f["lang"]
    ↓
merge_scan() → state.json               # zone persisted per finding
    ↓
scoring: _detector_pass_rate()           # skips zone-excluded findings
    ↓
narrative/query.json                     # zone info available to LLM
```

## Implementation

### Phase 1: Zone infrastructure — NEW `desloppify/zones.py`

- `Zone` — str enum (production, test, config, generated, script, vendor)
- `ZoneRule(zone, patterns)` — dataclass: zone + list of substring patterns to match against relative paths. First match wins.
- `classify_file(rel_path, rules) → Zone` — iterate rules, return first match or PRODUCTION
- `FileZoneMap(files, rules)` — cached dict, provides `.get(path)`, `.exclude(files, *zones)`, `.counts()`
- `ZONE_POLICIES` dict — per-zone detection policy:
  - TEST: skip `dupes, single_use, orphaned, coupling, facade`; downgrade `smells, structural` confidence to "low"; exclude from score
  - CONFIG: skip `smells, structural, dupes, naming, single_use, orphaned, coupling, facade`; exclude from score
  - GENERATED/VENDOR: skip all detectors; exclude from score
  - SCRIPT: skip `coupling, single_use, orphaned, facade`; downgrade `structural` to "low"; include in score

### Phase 2: LangConfig extension — `desloppify/lang/base.py`

### Phase 6: TS line classifier — `desloppify/lang/typescript/detectors/smells.py`

Add three functions mirroring Python's approach:

- `_build_ts_line_state(lines) → dict[int, str]` — marks lines inside block comments (`/* */`) or multi-line template literals as non-code. Tracks:
  - Block comment state (opened by `/*`, closed by `*/`)
  - Template literal state (opened by backtick, closed by backtick, with `${}` nesting awareness)
  - String literals on normal lines (skip for backtick/quote tracking)

- `_find_template_close(line, start) → int` — finds closing backtick handling `${}` nesting. Returns -1 if not found on this line.

- `_ts_match_is_in_string(line, match_start) → bool` — checks if a match position falls inside `'`, `"`, `` ` ``, or `//` comment. Mirrors Python's `_match_is_in_string`.

Modify `detect_smells()` to:
1. Build `line_state = _build_ts_line_state(lines)` per file
2. Skip lines in `line_state` for regex checks
3. Check `_ts_match_is_in_string(line, m.start())` for remaining matches

No LLM involvement at all. The zones are purely deterministic — based on file path patterns.

## How classification works

Each language config defines a list of pattern rules, checked in order. First match wins:

- **generated**: paths containing `/migrations/`, `_pb2.py`, `.d.ts`, etc.
- **test**: paths containing `test_`, `.test.`, `/__tests__/`, `/fixtures/`, etc.
- **config**: paths containing `setup.py`, `vite.config`, `tsconfig`, etc.
- **script**: paths containing `/scripts/`, `/bin/`, `__main__.py`
- **vendor**: (no rules yet — available for future use)
- **production**: everything else (the default)

So `src/components/Button.tsx` → production. `src/__tests__/Button.test.tsx` → test. `vite.config.ts` → config.

## How they flow through the system

1. **At scan start** (`plan.py`): all discovered files are classified once into a `FileZoneMap` — a cached dict of `{filepath: zone}`
2. **During detection**: `phase_dupes` filters out non-production functions *before* the expensive O(n²) duplicate comparison, so test files never generate dupe findings
3. **After detection**: every finding gets a `zone` field stamped on it, and confidence gets downgraded per zone policy (e.g. smells in test files → "low" confidence)
4. **Scoring** (`scoring.py`): findings with zone in `{test, config, generated, vendor}` are skipped entirely — they don't affect the health score
5. **Display** (`show.py`): non-production findings show a `[test]` or `[config]` tag
6. **Query output**: `zone_distribution` counts go into `query.json` so the LLM *consumer* can see the breakdown and reason about it

## What it solves

The two main false positive sources:
- **Test file duplicates**: test files naturally share patterns (setup, assertions, fixtures). Before zones, these flooded the Duplication dimension. Now they're excluded from both detection and scoring.
- **TS regex smells in strings/comments**: separate from zones but implemented alongside — the new TS line classifier (`_build_ts_line_state` + `_ts_match_is_in_string`) skips regex checks inside block comments, template literals, and string literals. So `const msg = "no any here"` no longer triggers the `any_type` smell.

## False positive risks in zone classification

The classification is **substring matching on file paths**, which is inherently blunt:

- **`config.py` / `settings.py`** — any file with that name anywhere gets classified CONFIG. But `src/tools/config.py` could be production application code that *manages* configuration, not a build config file.
- **`test_` prefix** — `src/test_helpers.py` (a production utility) would be misclassified as TEST because `test_` appears in the path. It's substring, not "filename starts with".
- **`/scripts/`** — if someone has `src/scripts/` with production code, it gets SCRIPT treatment (some detectors skipped).
- **Order dependency** — generated rules run first, so `tests/migrations/test_data.py` matches GENERATED (via `/migrations/`) before it could match TEST.
- **No override mechanism** — there's no way for users to correct a misclassification for a specific file. You'd have to change the pattern rules in code.

## LLM feedback loop

**There is none.** The LLM sees zone data in query.json but has no way to say "this classification is wrong." It's fire-and-forget.

The `_compute_fp_rates` function tracks false_positive rates per (detector, zone), but that's about *detector* false positives within a zone — it doesn't catch *zone misclassification*. If a production file gets classified as test, it just silently disappears from scoring. Nobody would know.

## Downstream integration — there are gaps

Let me trace the actual code paths honestly:

**What works:**
- Zone stamps on findings — yes, flows through merge, persists in state
- Scoring exclusion — `_detector_pass_rate` skips test/config/generated/vendor findings
- Dupes filtering — test functions are excluded before the O(n²) comparison
- Display — `show` command tags non-production findings
- Backward compat — old findings without zone default to "production"

**What doesn't work or is incomplete:**

1. **Potentials are NOT adjusted.** This is the biggest gap. If you have 100 files and 20 are tests, the potentials denominator is still 100 — but only 80 files' findings count toward failures. This artificially inflates pass rates because the denominator is too large. The plan explicitly called for adjusting potentials in `_phase_smells`, `_phase_structural`, `_phase_coupling` to use `lang._zone_map.exclude(files, ...)` for file counts. 2. **`ZONE_POLICIES.skip_detectors` is defined but not enforced.** The policy says test files should skip smells, structural, etc. — but those detectors still run on test files, generate findings, stamp them with `zone=test`, and then scoring ignores them. The findings still exist in state. It's correct for scoring but wastes work and clutters the findings list.

3. **Potentials/findings mismatch for file-based detectors.** With smells, the potential is `total_files` (all files scanned). But findings from test files are excluded in scoring. So you get: potential = 100 files, but only 80 files' findings are counted. The pass rate formula `(potential - weighted_failures) / potential` is working with a mismatched denominator.
