Here's what I found after thorough research. The picture is clearer now.

## The fundamental issue

When an input inside a `position: fixed` overlay is focused on iOS Safari, the browser **always** shifts the visual viewport to keep the input above the keyboard. This is built-in behavior — it happens regardless of body scroll lock method. Fixed elements stay anchored to the layout viewport, so they appear displaced. ([source](https://www.codestudy.net/blog/how-to-make-fixed-content-go-above-ios-keyboard/))

**The body `position: fixed` hack makes things worse** because:
- It fights with iOS's keyboard viewport adjustment
- The `top: -scrollY` positioning creates misalignment when the viewport changes
- Dirty state accumulates (visual viewport offset not properly reset on close)
- Multiple sources specifically identify `position: fixed` on body as the cause of keyboard interaction issues on iOS ([source 1](https://www.jayfreestone.com/writing/locking-body-scroll-ios/), [source 2](https://medium.com/@im_rahul/safari-and-position-fixed-978122be5f29))

## Why we can't just use `touch-action: none` on body instead

The [ancestor intersection rule](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action) (which the blog post covers!) means `touch-action: none` on body would kill scrolling in the lightbox panel too — `none ∩ pan-y = none`. The panel's ancestor chain goes through body because the Portal renders as a direct child of body.

## Three approaches, ranked by soundness

### 1. Replace body scroll lock with `overflow: hidden` + `overscroll-behavior: none` (simplest)

```css
html.lightbox-open, html.lightbox-open body {
  overflow: hidden;
  overscroll-behavior: none;
}
```

No `position: fixed`, no `touch-action` on body, no scroll position save/restore. The overlay's existing touch-action coverage (backdrop: `touch-action: none`, image area: `touch-none`, panel: `overscroll-contain`) provides the primary protection. `overflow: hidden` + `overscroll-behavior: none` is the safety net.

- `overscroll-behavior` is supported Safari 16+ ([Can I Use](https://caniuse.com/css-overscroll-behavior))
- No dirty state because we're not manipulating scroll position
- Keyboard works naturally — no body positioning hack to fight with
- Risk: `overflow: hidden` was historically unreliable alone on iOS Safari ([WebKit bug #153852](https://bugs.webkit.org/show_bug.cgi?id=153852)), but `overscroll-behavior: none` (available since Safari 16) may close that gap

### 2. Height-constraint body lock ([PQINA approach](https://pqina.nl/blog/how-to-prevent-scrolling-the-page-on-ios-safari))

```css
html.is-locked, html.is-locked body {
  height: calc(var(--window-inner-height) - 1px);
  overflow: hidden;
}
```

Body is exactly viewport height minus 1px, so there's nothing to scroll. The `-1px` trick prevents iOS from detecting scrollable content. Body stays in normal flow (not fixed), so keyboard interacts normally. Still needs scroll position save/restore though.

### 3. Visual viewport tracking (our current attempt)

Viable as an add-on but fragile as a primary fix — `visualViewport.height` doesn't match layout viewport (address bar), keyboard detection via `vvTop > 0` is an assumption, and it doesn't fix the root cause.

## My recommendation

**Try approach 1 first.** It's the simplest, removes the root cause, and our overlay already has comprehensive touch-action coverage making the body scroll lock mostly redundant. If `overflow: hidden` + `overscroll-behavior: none` turns out to be insufficient on iOS, fall back to approach 2. Either way, keep the blur-on-close and revert the visual viewport tracking (it's fighting symptoms, not the cause).

2. Key Technical Concepts:

   - **`touch-action` ancestor intersection rule**: `touch-action` values are intersected across ALL ancestors, not overridden by children. `none ∩ pan-y = none`. This means `touch-action: none` on a parent kills scrolling in all descendants — must use **sibling isolation** pattern.

   - **`overscroll-behavior: contain` vs `none`**: `contain` prevents scroll chaining but allows the element's own rubber-band bounce. `none` prevents both. Neither works on elements that aren't actual scroll containers (no overflow content).
