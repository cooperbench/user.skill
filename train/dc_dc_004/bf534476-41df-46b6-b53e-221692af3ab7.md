# Plan: Standardize LoRA Handling

## Context

LoRA configuration flows through 4 independent mechanisms that each build LoRA lists differently:

1. **QwenHandler** (`source/models/model_handlers/qwen_handler.py`): 7 nearly-identical code blocks manually building `lora_names`/`lora_multipliers` arrays with duplicated Lightning LoRA download + phase format logic
2. **Travel segment handler** (`source/task_handlers/tasks/task_registry.py`): Downloads LoRA URLs, converts to WGP format, then submits to queue where `convert_to_wgp_task_impl()` re-parses through LoRAConfig (double resolution, ~80 lines of redundant code)
3. **SVI LoRA merging** (`task_registry.py` + `travel/orchestrator.py`): Raw array manipulation via `get_svi_lora_arrays()` bypassing LoRAConfig entirely
4. **Orchestrator dead code** (`travel/orchestrator.py` lines 1710-1727): Sets `lora_names`/`lora_multipliers` on segment payloads that are never read by the segment handler

A well-designed `LoRAConfig` class already exists at `source/core/params/lora.py` with `from_params()`, `from_phase_config()`, `from_segment_loras()`, `to_wgp_format()`, and `merge()`. The clean path through `download_ops.py:convert_to_wgp_task_impl()` already uses it correctly. The problem is that QwenHandler, the travel segment handler, and SVI merging all bypass it.

**Root cause of the ~7min per-generation delay found in debug log analysis:** WGP unloads LoRAs after every generation (wgp.py:6439). We added a caching patch (`wgp_patches.py:apply_lora_caching_patch`) to keep LoRAs loaded between generations. This plan standardizes the upstream LoRA configuration handling, which is a separate concern from the caching.

### Why the complexity exists (investigated, confirmed accidental)

**Double LoRA resolution:** The travel handler downloads LoRAs before queue submission, then convert_to_wgp_task_impl() would re-download (but finds them already cached). Investigation confirmed:
- `apply_phase_config_patch()` does NOT reference LoRA paths — it only patches model architecture config
- No code between download and GenerationTask submission needs resolved paths
- The travel handler doesn't pass `_parsed_phase_config` through to generation_params (unlike task_conversion.py which does) — an architectural gap that forces the queue worker to defensively re-parse

**SVI double-merge:** The orchestrator merges SVI LoRAs into `segment_payload["lora_names"]`, then the segment handler re-merges from scratch. Grep confirms `segment_payload["lora_names"]` is NEVER read by the segment handler. It builds generation_params from scratch.

**Root cause for both:** Historical layering. The queue worker was designed as a self-contained generic path. The travel handler was built as a sequential flow. They were never reconciled.

    self,
    db_task_params: Dict[str, Any],
    generation_params: Dict[str, Any],
    lightning_fname: str = [REDACTED],
    lightning_repo: str = "lightx2v/Qwen-Image-Lightning",

```

# In source/task_handlers/travel/svi_config.py
def merge_svi_into_config(
    base_config: LoRAConfig,
    svi_strength: float = None,
    svi_strength_1: float = None,
    svi_strength_2: float = None,
) -> LoRAConfig:
    """Merge SVI LoRAs into a LoRAConfig, returning a new config."""
    svi_entries = []
    for url, phase_mult in SVI_LORAS.items():
        # Scale multiplier based on svi_strength params
        scaled_mult = _scale_svi_multiplier(phase_mult, svi_strength, svi_strength_1, svi_strength_2)
        svi_entries.append(LoRAEntry(
            url=url,
            filename=os.path.basename(url),
            multiplier=scaled_mult,
            status=LoRAStatus.PENDING,
            source='svi'
        ))
    svi_config = LoRAConfig(entries=svi_entries)
    return base_config.merge(svi_config)
```

**Net effect:** ~25 lines of multiplier parsing/merging replaced with typed LoRAConfig operations at each call site. SVI LoRA URLs flow through LoRAConfig → get downloaded by `convert_to_wgp_task_impl()`.

### 1. Dict Key Flow Tracer

The single most impactful tool for Python codebases. Most architectural bugs I found involved dict keys written in one place and (not) read in another.

```
trace_dict_key("lora_names", scope="source/")

  orchestrator.py:1726  segment_payload["lora_names"] = merged_urls
  task_registry.py:609  generation_params["lora_names"] = parsed_phase_config["lora_names"]

  qwen_handler.py:262   generation_params.get("lora_names", [])

  — segment_payload consumed by _handle_travel_segment_via_queue()
  — _handle_travel_segment_via_queue never reads key "lora_names"
```

This alone would have surfaced the dead orchestrator writes instantly. The hard part is that Python dicts are untyped — you need heuristic tracing (grep for string literals + ast-level `dict[key]`/`.get(key)` patterns) rather than real type analysis. Imperfect but useful.

### 2. Call Chain Tracer with Data Passthrough

Not just "who calls whom" but "what data flows through."

```
trace_flow(
  from="task_registry.py:_handle_travel_segment_via_queue",
  to="download_ops.py:convert_to_wgp_task_impl",
  track="generation_params"
)

_handle_travel_segment_via_queue()
  → builds generation_params dict (lines 464-470)
  → downloads LoRAs, resolves to paths (lines 528-654)  ← MUTATES generation_params
  → GenerationTask(parameters=generation_params)         ← PASSTHROUGH
  → task_queue.submit_task()
  → ...queue worker picks up...
  → convert_to_wgp_task_impl(task)
    → TaskConfig.from_db_task(task.parameters)            ← RE-PARSES same data
    → downloads LoRAs, resolves to paths                  ← REDUNDANT with lines 528-654
```

This would have flagged the double resolution immediately. The key insight is tracking a *specific object* through the call chain and noting when it's transformed, then re-transformed.

### 3. Lifecycle Pair Detector

Configurable "these two operations are a matched pair" rules:

```yaml
pairs:
  - acquire: "apply_phase_config_patch"
    release: "restore_model_patches"
    scope: "function"  # must be paired within the same function/finally block
  - acquire: "os.chdir"
    release: "os.chdir"
    scope: "try-finally"
```

```
scan_unpaired_lifecycles()

⚠ task_registry.py:656
  apply_phase_config_patch(parsed_phase_config, model_name, task_id)
  — no matching restore_model_patches() in same scope
  — compare: worker_thread.py:372-525 (correctly paired in try/finally)
```

This is a simpler, more focused version of what Rust's borrow checker does. For Python you'd define the pairs manually, but the scanning is mechanical.

### 4. Semantic Duplicate Finder (Embedding-based)

Instead of AST diffing, extract a *signature* per code block:

```
For each block of 10+ lines:
  - inputs: what variables are read
  - outputs: what variables are written
  - side effects: what functions are called
  - structure: loop/branch/try pattern

Cluster by signature similarity, not syntax.
```

The 7 QwenHandler blocks all had the signature:
```
reads: db_task_params, generation_params, self.qwen_lora_dir
writes: generation_params["lora_names"], generation_params["lora_multipliers"]
calls: _download_lora_if_missing, db_task_params.get, float()
structure: if-not-exists → download; if-not-in-list → append
```

Syntactically they varied (different filenames, defaults, guard patterns). Semantically they're identical. An embedding-based approach or even a structured signature comparison would catch this where AST diff fails.

The inverse of a call graph — given a code block, what breaks if it's removed:
