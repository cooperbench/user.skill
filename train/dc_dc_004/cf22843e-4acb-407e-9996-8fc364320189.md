## Two keyboard handlers, two phases — that's the complication

There are **two independent keyboard handlers** for arrow key navigation in the form-only lightbox:

### 1. Capture-phase handler (`useLightboxNavigation.ts:87-112`)
- Registered on `document` in **capture phase** (fires first)
- Shared by ALL lightbox modes (image, video, form-only)
- Text input check: `instanceof HTMLInputElement || instanceof HTMLTextAreaElement || isContentEditable` — comprehensive
- **No `hasNext`/`hasPrevious` guard** — calls `onNext()` unconditionally, relies on `onNavigateToPair` to bail if out of bounds

### 2. Bubble-phase handler (`SegmentSlotFormView.tsx:103-125`)
- Registered on `window` in **bubble phase** (fires second)
- Only active in form-only mode
- Text input check: only `tagName === 'TEXTAREA'` — misses `<input>` elements
- **Has `hasNext`/`hasPrevious` guard** — but also handles Tab key for segment navigation

### The inconsistencies:

1. **When a `<textarea>` is focused** (prompt field): Both handlers skip arrow keys. Navigation doesn't work. This is **correct behavior** for the textarea cursor, but the user loses the ability to navigate between segments.

2. **When an `<input>` is focused** (frame count slider): The capture handler skips (it sees `HTMLInputElement`), but the bubble handler FIRES (it only checks `TEXTAREA`). This would navigate away when you're trying to edit a number input — **bad UX**.

3. **The `TEXTAREA` early-return blocks Tab too**: The bubble handler does `if (activeElement.tagName === 'TEXTAREA') return` before reaching the Tab checks. So Tab navigation between segments is broken when the prompt textarea is focused.

4. **Double-fire**: When no form field is focused, BOTH handlers fire for the same arrow key (same callback called twice). React batches the state updates so it works, but it's unnecessary.

### Why it "doesn't work" for the user

The most likely scenario: the user opens the form-only view, interacts with the prompt textarea (natural first action), then tries to press ArrowLeft/ArrowRight to navigate. Both handlers correctly skip because the textarea is focused. **Arrow keys work fine when nothing is focused** — the user just never experiences that case because they naturally interact with the form first.
