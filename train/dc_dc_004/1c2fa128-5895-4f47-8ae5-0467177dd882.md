# Plan: Fix Subjective Review Loop — Negative-Only Findings + Score Decoupling

## Context

Two design bugs were discovered in the subjective review system:

1. **Positive observations stored as penalties**: The review LLM sometimes returns compliments ("good decomposition", "well-structured") as findings. These are stored as `status="open"` with a 10x `HOLISTIC_MULTIPLIER`, penalizing the score for positive observations. There is no `kind` or `sentiment` field to distinguish positive from negative.

2. **Resolving findings immediately changes strict score**: Resolving review findings (especially as `false_positive`) immediately recalculates the score via `_recompute_stats()`. Users can "game" scores by resolving findings without actually fixing anything. The score should only change when a fresh subjective review is imported.

**Desired loop**: review → get score + findings → fix code → resolve findings → re-run review → get new score

### 3a: Expand trigger to all statuses

**File:** `desloppify/engine/state_internal/resolution.py`

Rename `_reset_subjective_assessments_after_review_fix` → `_mark_stale_assessments_on_review_resolve`.

Change the logic:
- Remove the `if status != "fixed": return` guard (line 34)
- Instead of setting `score = 0.0`, keep the current score
- Set `needs_review_refresh = True` and `refresh_reason = f"review_finding_{status}"`

```python
def _mark_stale_assessments_on_review_resolve(
    state: dict,
    *,
    status: str,
    resolved_findings: list[dict],
    now: str,
) -> None:
    """Mark subjective assessments as stale when review findings are resolved."""
    assessments = state.get("subjective_assessments")
    if not isinstance(assessments, dict) or not assessments:
        return

    touched_dimensions: set[str] = set()
    for finding in resolved_findings:
        if finding.get("detector") != "review":
            continue
        dimension = str(finding.get("detail", {}).get("dimension", "")).strip()
        if dimension:
            touched_dimensions.add(dimension)

    for dimension in sorted(touched_dimensions):
        if dimension not in assessments:
            continue
        payload = assessments.get(dimension)
        if isinstance(payload, dict):
            payload["needs_review_refresh"] = True
            payload["refresh_reason"] = f"review_finding_{status}"
            payload["stale_since"] = now
        else:
            assessments[dimension] = {
                "score": _coerce_assessment_score(payload),
                "needs_review_refresh": True,
                "refresh_reason": f"review_finding_{status}",
                "stale_since": now,
            }
```

Update the call in `resolve_findings()` (line 129) to use the new name.

Now to answer your question: **how does the agentic review loop work, simply?**

### The Loop

```
review --prepare  →  LLM reviews your code  →  import results  →  scan  →  fix code  →  resolve findings  →  re-review
```

Here's what happens at each step:

1. **`review --prepare`** — Sends your code + a system prompt to the LLM. The prompt now explicitly tells it: "only report defects, never compliments." The LLM returns two things per dimension:
   - **Assessment score** (0-100): "How good is this dimension overall?"
   - **Findings** (list): "Here are specific defects to fix"

2. **`review --import`** — Stores both pieces in state. Assessment scores go to `subjective_assessments`. Findings become `detector="review"` entries in the findings dict. A safety net now filters out any positive observations that slip through, and requires every finding to have an actionable `suggestion`.

3. **`scan`** — Recomputes all scores. **The key change**: review findings are now **invisible to the scoring engine**. The assessment score (0-100) directly drives the subjective dimension score. So if the LLM gave "naming_quality" a 75, that dimension scores 75 — regardless of how many individual findings exist.

4. **Fix code** — You work through the review findings as a task list.

5. **`resolve`** — Mark findings as `fixed`, `wontfix`, or `false_positive`. **The key change**: this no longer changes any scores. It just marks the assessment as "stale" (`needs_review_refresh: true`) and tells you to re-run the review.

6. **Re-review** — Run `review --prepare` again. The LLM sees your improved code, gives new assessment scores. *That's* what changes the score.

### Why This Matters

**Before**: Resolving findings immediately boosted your score (especially `false_positive` — free points). The LLM's compliments were stored as open findings, *penalizing* you 10x for being praised.

**After**: The score only changes when the LLM actually re-evaluates your code. Findings are a work queue, not a score lever. The assessment score is the single source of truth for each subjective dimension.
