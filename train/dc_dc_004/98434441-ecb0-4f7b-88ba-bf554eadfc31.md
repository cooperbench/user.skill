Here's what `ast` is doing across the codebase — it's used in 9 files for three broad purposes:

**1. Code smell detection** (`smells_ast.py` — the biggest user)
Parses Python source into ASTs and walks them to find ~20 structural smells that regex can't reliably catch:
- Monster functions (>150 LOC), dead/noop functions, unreachable code, constant returns
- Subprocess calls missing `timeout=`, mutable class variables, `@lru_cache` on functions reading mutable globals
- Unsafe file writes (no atomic pattern), regex backtracking risks, naive comment stripping
- Lost exception context (`raise` without `from` in except), silent except handlers
- Star imports without `__all__`, sys.exit in library code, optional parameter sprawl, loose type annotations, hardcoded path separators, vestigial parameters, callback logging

**2. Dict key tracking** (`dict_keys.py` + `dict_keys_visitor.py`)
A full `ast.NodeVisitor` subclass that walks scopes tracking which dict keys are written vs read. Catches dead writes (key set but never read), phantom reads (key read but never written — will KeyError), near-miss typos (edit distance), and overwritten keys.

**3. Module-level mutable state** (`mutable_state.py`)
Detects module-level variables initialized to mutable values (`[]`, `{}`, `set()`) that get modified from functions. Also detects stale import bindings — when another module does `from X import name` on a mutable that gets reassigned via `global`, creating a stale copy.

Plus supporting roles: **import graph building** (`deps.py` — parses imports for dependency analysis), **security detection** (`security.py` — finds shell injection, unsafe deserialization, SQL injection patterns structurally), and **cross-module architecture** (`facade.py`, `layer_violation.py`, `private_imports.py`).

In short: AST is the backbone of every detector that needs to understand code *structure* rather than just pattern-match on text. It's what separates "grep for `subprocess.run`" from "find `subprocess.run` calls that are missing a `timeout` keyword argument."

Yes, they're used together in the same pipeline, and there is some overlap. Here's how it works:

**The pipeline** (`smells.py:detect_smells`) runs three detection strategies on every file in a single pass:

1. **Regex checks** — line-by-line pattern matching (with multi-line string awareness to avoid false positives)
2. **Indentation-based multi-line checks** — `_detect_empty_except` and `_detect_swallowed_errors` walk except blocks by tracking indentation
3. **AST checks** — `_detect_ast_smells` parses the full tree

All three write into the same `smell_counts` dict, and results are merged at the end.

**Where they overlap:**

| Issue | Regex | AST |
|-------|-------|-----|
| Bare/broad except | `bare_except`, `broad_except` (regex) | `silent_except` (AST) |
| Star imports | `star_import` (regex) | `star_import_no_all` (AST — checks if target has `__all__`) |
| Error swallowing | `swallowed_error` (indentation) | `silent_except` (AST — `pass`/`continue` only) |

These aren't really duplicates though — they're complementary. The regex catches the broad pattern (`except Exception:`), while the AST version goes deeper (is the handler *actually silent*? does the star import target *actually* lack `__all__`?). The regex is a quick surface flag; the AST understands structure.

The split is pragmatic: regex is fast and catches things that are obvious from a single line. AST is slower but necessary when the answer depends on scope, control flow, or cross-node relationships (like "is there a `timeout=` keyword in this call?" or "does every return path yield the same constant?").

**2. Naming inconsistency across modules** ("entries" vs "findings" vs "results" vs "matches"; `_phase_*` vs `phase_*`; `_cmd.py` suffix on some commands but not others; "build" vs "prepare" vs "load" for context init)

The `naming` detector only catches *case convention* drift (camelCase vs snake_case). It doesn't catch:
- **Vocabulary drift** — the same concept called different things in different modules
- **Prefix convention drift** — inconsistent underscore usage for private functions
- **File naming conventions** — some files use `_cmd.py` suffix, others don't

**How to catch it:** This is fundamentally a subjective/holistic issue — it's about *consistency of intent*, not syntax. The `convention_outlier` holistic review dimension is designed for exactly this, but those 91 "unreviewed" findings mean it hasn't been run yet. Running the subjective review would likely catch most of this. Beyond that, a targeted "vocabulary consistency" detector could: (a) extract parameter names and return type annotations from function signatures, (b) cluster functions with similar signatures that use different names for the same concept (e.g., `entries: list[dict]` in one, `findings: list[dict]` in another), and flag when >3 synonyms exist for the same role. Hard to get right mechanically — probably best left to the LLM-based review.

**3. Mixed concerns / god modules** (cmd_scan doing 9 things, utils.py with 27 unrelated functions, state.py handling I/O + CRUD + merging + scoring)

The `structural` detector flags large files and complexity, but it doesn't understand *responsibility cohesion*. A file can be 400 LOC and score moderate complexity while still being a dumping ground of unrelated functions.

**How to catch it:** Two approaches:
- **Cohesion analysis** — for each file, compute how many of its functions reference each other vs. how many are independent. Low internal coupling = dumping ground. This could be done from the existing dep graph (which tracks intra-file references).
- **Semantic clustering** — group functions by the set of imports they use. If a file has 3+ distinct import clusters (e.g., some functions use `json`/`os` for I/O, others use `ast` for parsing, others use formatting helpers), flag it as mixed concerns.
- The `concerns` detector exists for TS (detects mixed hooks/utilities/types), but there's no Python equivalent. Extending it cross-language would help.

**5. Return type inconsistency** (some phase runners return `list[Finding]`, others return `list[dict]`)

No detector catches this. The `annotation_quality` smell flags *missing* annotations and bare types, but not *inconsistent* return types across functions that serve the same role.

**6. Dual/legacy registries** (DETECTOR_TOOLS still exported alongside canonical DETECTORS)

No detector catches backward-compatibility shims that should have been removed. The `stale_exclude` detector catches stale exclusion patterns, but nothing looks for legacy re-exports.

**How to catch it:** An "alias/shim" detector could flag module-level assignments that just rebind an import under an old name (e.g., `DETECTOR_TOOLS = detector_tools()` right next to the canonical `DETECTORS`). This is a form of dead code that the current `unused` detector misses because the symbol *is* imported somewhere.

**7. Specific untested security checks** (insecure_cookie, unverified_jwt_decode, edge_function_missing_auth have zero tests)

The `test_coverage` detector flags files that lack test coverage, but it works at the *file* level. It found smells_ast.py and dict_keys_visitor.py need more tests. But it can't see that *specific checks within a tested file* have no exercising test.

**How to catch it:** This is hard to do mechanically without actual code coverage data (like `coverage.py`). The test_coverage detector could be enhanced to: (a) integrate with `coverage.py` if a `.coverage` file exists, (b) for security detectors specifically, cross-reference the list of check names (from the registry) against test function names that contain those check names.

**8. BaseException catches** (move.py, utils.py, fixers/common.py use `except BaseException` for cleanup)

The `broad_except` smell catches `except Exception:` but not `except BaseException:`. The regex pattern is `r"^\s*except\s+Exception\s*(?:as\s+\w+\s*)?:"` — it literally only matches the word "Exception".

**How to catch it:** Simple fix — extend the regex to also match `BaseException`: `r"^\s*except\s+(?:Exception|BaseException)\s*(?:as\s+\w+\s*)?:"`. Or better, add a separate `base_exception_catch` smell since the guidance differs (BaseException is almost never correct even for cleanup).

**9. File I/O without `_read_file_text()`** (36+ files using raw `Path.read_text()` instead of the cached utility)

No detector catches "you have a utility function but aren't using it." This is a form of API misuse within the project.

**How to catch it:** A "preferred API" or "internal convention" detector. Config-driven: you declare `{"prefer": "utils._read_file_text", "over": "Path.read_text", "in": "desloppify/"}` and it flags violations. This is essentially a project-specific lint rule. Could also be done as an extension to the existing smell system — a `preferred_api` smell that's configurable per project.
