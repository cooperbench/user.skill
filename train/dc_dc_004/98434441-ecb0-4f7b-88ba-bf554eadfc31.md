what's the ast module actually doing?

> AGENT

Here's what `ast` is doing across the codebase — it's used in 9 files for three broad purposes: **1. Code smell detection** (`smells_ast.py` — the biggest user) Parses Python source into ASTs and walks them to find ~20 structural smells that regex can't reliably catch: - Monster functions (>150 LOC), dead/noop functions, unreachable code, constant returns - Subprocess calls missing `timeout=`, mutable class variables, `@lru_cache` on functions reading mutable globals - Unsafe file writes (no atomic pattern), regex backtracking risks, naive comment stripping - Lost exception context (`raise` without `from` in except), silent except handlers - Star imports without `__all__`, sys.exit in library code, optional parameter sprawl, loose type annotations, hardcoded path separators, vestigial parameters, callback logging **2. Dict key tracking** (`dict_keys.py` + `dict_keys_visitor.py`) A full `ast.NodeVisitor` subclass that walks scopes tracking which dict keys are written vs read. Catches dead writes (key set but never read), phantom reads (key read but never written — will KeyError), near-miss typos (edit distance), and overwritten keys. **3. Module-level mutable state** (`mutable_state.py`) Detects module-level variables initialized to mutable values (`[]`, `{}`, `set()`) that get modified from functions. Also detects stale import bindings — when another module does `from X import name` on a mutable that gets reassigned via `global`, creating a stale copy. Plus supporting roles: **import graph building** (`deps.py` — parses imports for dependency analysis), **security detection** (`security.py` — finds shell injection, unsafe deserialization, SQL injection patterns structurally), and **cross-module architecture** (`facade.py`, `layer_violation.py`, `private_imports.py`). In short: AST is the backbone of every detector that needs to understand code *structure* rather than just pattern-match on text. It's what separates "grep for `subprocess.run`" from "find `subprocess.run` calls that are missing a `timeout` keyword argument."

Yes, they're used together in the same pipeline, and there is some overlap. Here's how it works: **The pipeline** (`smells.py:detect_smells`) runs three detection strategies on every file in a single pass: 1. **Regex checks** — line-by-line pattern matching (with multi-line string awareness to avoid false positives) 2. **Indentation-based multi-line checks** — `_detect_empty_except` and `_detect_swallowed_errors` walk except blocks by tracking indentation 3. **AST checks** — `_detect_ast_smells` parses the full tree All three write into the same `smell_counts` dict, and results are merged at the end. **Where they overlap:** | Issue | Regex | AST | |-------|-------|-----| | Bare/broad except | `bare_except`, `broad_except` (regex) | `silent_except` (AST) | | Star imports | `star_import` (regex) | `star_import_no_all` (AST — checks if target has `__all__`) | | Error swallowing | `swallowed_error` (indentation) | `silent_except` (AST — `pass`/`continue` only) | These aren't really duplicates though — they're complementary. The regex catches the broad pattern (`except Exception:`), while the AST version goes deeper (is the handler *actually silent*? does the star import target *actually* lack `__all__`?). The regex is a quick surface flag; the AST understands structure. The split is pragmatic: regex is fast and catches things that are obvious from a single line. AST is slower but necessary when the answer depends on scope, control flow, or cross-node relationships (like "is there a `timeout=` keyword in this call?" or "does every return path yield the same constant?").
