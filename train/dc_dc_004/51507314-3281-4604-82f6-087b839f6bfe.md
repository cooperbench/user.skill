## Deep Analysis: `useLightboxLayoutProps` and the Larger Structural Issue

### What Happened

Before the three contexts existed, **all data flowed through `useLightboxLayoutProps`** as a single "props highway":

```
ImageLightbox → useLightboxLayoutProps(284 inputs) → layoutProps → LightboxLayout → sub-components
```

Then `LightboxStateContext`, `ImageEditContext`, and `VideoEditContext` were added to short-circuit prop drilling for deeply-nested sub-components. But **the highway wasn't demolished** — it was supplemented with a parallel road. The result is a dual transport system where some values flow through both props AND context, some only through context, some only through props, and some are declared as inputs but flow through neither.

### Three categories of redundancy

#### Category 1: Dead Input Props (~30 props) — declared in input but never used in hook body

These are the clearest waste. They appear in `UseLightboxLayoutPropsInput` (lines 23-284) and ImageLightbox passes them in (lines 1009-1231), but they are **not referenced anywhere** in the hook body (lines 290-512). They were migrated to `ImageEditContext` but never cleaned up:

**Edit form state** (all in ImageEditContext now):
- `inpaintPrompt`, `setInpaintPrompt`, `inpaintNumGenerations`, `setInpaintNumGenerations`
- `loraMode`, `setLoraMode`, `customLoraUrl`, `setCustomLoraUrl`
- `img2imgPrompt`, `setImg2imgPrompt`, `img2imgStrength`, `setImg2imgStrength`
- `enablePromptExpansion`, `setEnablePromptExpansion`
- `qwenEditModel`, `setQwenEditModel`
- `createAsGeneration`, `setCreateAsGeneration`

**Generation status** (all in ImageEditContext now):
- `isGeneratingInpaint`, `inpaintGenerateSuccess`
- `isCreatingMagicEditTasks`, `magicEditTasksCreated`
- `isGeneratingReposition`, `repositionGenerateSuccess`
- `isGeneratingImg2Img`, `img2imgGenerateSuccess`
- `isSavingAsVariant`, `saveAsVariantSuccess`
- `hasTransformChanges`

**Mode handlers** (in context now):
- `handleExitMagicEditMode`, `handleExitInpaintMode`
- `setEditMode`, `setIsInpaintMode`
- `inpaintPanelPosition`, `setInpaintPanelPosition`

**Info panel stubs** (unused):
- `generationName`, `handleGenerationNameChange`, `isEditingGenerationName`, `setIsEditingGenerationName`

**Variant/video props** (context-only):
- `isLoadingVariants`, `setPrimaryVariant`, `deleteVariant`, `variantParamsToLoad`, `setVariantParamsToLoad`
- `isInVideoEditMode` (only used by VideoEditContext)
- All 6 `handleEnterVideo*Mode` / `handleExitVideoEditMode` handlers

#### Category 2: Dual-path props (~35 props in `LayoutEditModeProps`) — flow through BOTH props AND context

`LightboxLayoutProps` extends `LayoutEditModeProps` (35 fields: brush, annotation, reposition state). These exact same values are in `ImageEditContext`. Today:
- `LightboxLayout` reads `isInpaintMode`, `isSpecialEditMode`, `editMode` from **context** (line 62)
- `LightboxLayout` reads `isAnnotateMode`, `brushStrokes`, `isEraseMode`, `brushSize`, etc. from **props** (lines 80-104)
- `FloatingToolControls` reads from **context** (already migrated)
- `MediaDisplayWithCanvas` reads from **props only** (not migrated)

This creates a confusing inconsistency — you can't tell at a glance which source of truth to use.

Similarly, `LayoutVideoEditProps` (~10 props) overlaps with `VideoEditContext` for trim state, video duration, etc.

#### Category 3: Genuinely needed props (~80 props) — layout-specific, can't be in context

- Layout flags: `showPanel`, `shouldShowSidePanel`, `effectiveTasksPaneOpen`
- Pre-composed objects: `buttonGroupProps`, `workflowBarProps`, `controlsPanelProps`, `workflowControlsProps`, `floatingToolProps`
- Segment navigation: `adjacentSegments`, `segmentSlotMode`
- Video display refs: `trimVideoRef` (can't meaningfully contextify a ref)

#### Video stub problem

ImageLightbox passes **~30 dummy video props** (`trimState: { startTrim: 0, ... }`, `videoEditing: null`, empty handlers) because the input interface requires them. This is a code smell — the hook requires video props even for image lightbox.

### The cascading impact

The 284-input hook is the bottleneck that forces both orchestrators to be enormous:

| File | Lines | Lines dedicated to building layout props input |
|---|---|---|
| ImageLightbox.tsx | 1261 | ~220 (lines 1009-1231) |
| VideoLightbox.tsx | 1078 | ~200 (estimated) |
| useLightboxLayoutProps.ts | 513 | (the entire file) |
| **Total** | **~2850** | **~930 lines** of pure plumbing |

### Proposed Phased Plan

#### Phase 1: Remove dead props (zero behavior change)

Remove the ~30 unused props from `UseLightboxLayoutPropsInput` and the corresponding values from the call sites in ImageLightbox and VideoLightbox. This is pure dead code removal — contexts already carry these values, and the hook never reads them.

**Impact**: Input interface drops from 284 → ~250 props. ~100 lines removed from each orchestrator.

#### Phase 2: Migrate `LayoutEditModeProps` to context (eliminate dual-path)

Make `MediaDisplayWithCanvas` consume edit state from `useImageEditSafe()` instead of receiving ~20 edit props. Update `LightboxLayout`'s inline edit controls to consistently use context. Remove `LayoutEditModeProps` from `LightboxLayoutProps`.

This is the highest-value change — it eliminates the confusing dual-source pattern and removes ~35 props from the layout interface.

**Impact**: `LightboxLayoutProps` drops from ~80 fields to ~45. `useLightboxLayoutProps` input drops to ~200. Both orchestrators shrink further.

#### Phase 3: Migrate `LayoutVideoEditProps` to context

Add `trimVideoRef` and `videoEditing` to `VideoEditContext`. Have video display components consume from `useVideoEditSafe()`. Remove the video edit props from the layout interface.

This also eliminates the ~30 video stub props that ImageLightbox has to pass.

**Impact**: Input interface drops to ~170. ImageLightbox stops passing dummy video values. The interface could potentially be split into separate image/video types.

#### Phase 4: Extract `useControlsPanelProps` (eliminate pass-through)

The `controlsPanelProps` sub-object (~60 fields) is the remaining bulk. It's built by `useLightboxLayoutProps`, passed to `LightboxLayout`, then spread into `ControlsPanel`. ControlsPanel itself just routes to sub-panels that already read from context. 

Extract a `useControlsPanelProps()` hook that ControlsPanel calls directly, consuming context + receiving only the few specialized props it can't get from context (handlers, managers). This eliminates the biggest prop pass-through chain.

**Impact**: `controlsPanelProps` no longer flows through the layout. useLightboxLayoutProps input drops to ~80-100.

#### Phase 5: Evaluate eliminating `useLightboxLayoutProps` entirely

After phases 1-4, the hook would build only:
- `workflowBarProps` (~20 props, pure pass-through + renaming)
- `floatingToolProps` (6 reposition handlers)
- `workflowControlsProps` (extends workflowBarProps + 2 props)
- Conditional `showPanel` switching

At this point it's a thin memoization wrapper. It could either:
- Stay as-is (simple, works)
- Move into `LightboxLayout` directly
- Be replaced by a `WorkflowContext` if workflows need deeper access

### What I'd recommend

**Phases 1-3 are clear wins** — they remove dead code, eliminate dual-path confusion, and make both orchestrators significantly smaller. These are safe, mechanical refactors.

**Phase 4 is high-value but requires more design thought** — the question of what goes in context vs. stays as props for the specialized handlers/managers is worth discussing.

**Phase 5 is optional** — the hook at that point would be small enough to not matter.
