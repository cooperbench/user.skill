# Plan: Fix Concern Lifecycle Gaps & Consolidate Judgment Split

## Context

The concerns pipeline (mechanical → subjective bridge) works end-to-end but has 6 lifecycle gaps and a design smell. Dismissals don't stick (missing `source_finding_ids`), confirmed concerns don't auto-resolve when source findings disappear, scoring ignores concern findings, and `_JUDGMENT_DETECTORS` is a hardcoded list that duplicates information the registry should own.

## Changes

### 1. Add `needs_judgment` to DetectorMeta

**File:** `desloppify/core/registry.py`

Add `needs_judgment: bool = False` to the `DetectorMeta` frozen dataclass. Set `True` on the 19 detectors currently in `_JUDGMENT_DETECTORS`, plus `cycles`.

Add a derived view after the `DETECTORS` dict:
```python
JUDGMENT_DETECTORS: frozenset[str] = frozenset(
    name for name, meta in DETECTORS.items() if meta.needs_judgment
)
```

### 2. Replace hardcoded `_JUDGMENT_DETECTORS`

**File:** `desloppify/engine/concerns.py`

Replace the hardcoded frozenset with `from desloppify.core.registry import JUDGMENT_DETECTORS`. Delete the `_JUDGMENT_DETECTORS` constant and its comment block.

### 3. Fix dismissal storage — add `source_finding_ids`

**File:** `desloppify/intelligence/review/importing/holistic.py`

The LLM can't return `source_finding_ids` (it doesn't know them). Compute them at import time by re-running `generate_concerns()` and matching fingerprints.

In `import_holistic_findings()`, after building the dismissal store (line ~236), enrich with source IDs:
```python
from desloppify.engine.concerns import generate_concerns
current_concerns = generate_concerns(state, lang_name=lang_name)
concern_sources = {c.fingerprint: list(c.source_findings) for c in current_concerns}
for fp, entry in store.items():
    if fp in concern_sources:
        entry["source_finding_ids"] = concern_sources[fp]
```

### 4. Include fingerprint in batch payload

**File:** `desloppify/intelligence/review/prepare_batches.py`

Add `"fingerprint": c.fingerprint` to each concern dict in `batch_concerns()`. The LLM needs this to return it in dismissed verdicts so we can match them back to the right concern.

### 5. Exclude "concerns" from mechanical scoring

**File:** `desloppify/engine/_scoring/detection.py` (line 123)

Change `if detector == "review":` to `if detector in ("review", "concerns"):`.

Concern findings are scored via the design_coherence subjective assessment. Without this exclusion, they'd be double-counted in the mechanical pipeline.

### 6. Count concern findings in dimension display

**File:** `desloppify/engine/_scoring/subjective/core.py` (line 142)

Change `if finding.get("detector") == "review"` to `if finding.get("detector") in ("review", "concerns")`.

This makes confirmed concern findings visible in the dimension's issue count (display only — assessment score still drives the dimension score).

### 7. Auto-resolve stale concern findings on re-import

**File:** `desloppify/intelligence/review/importing/holistic.py`

In `_auto_resolve_stale_holistic()` (line 190), change `finding.get("detector") == "review"` to `finding.get("detector") in ("review", "concerns")`.

When the LLM re-evaluates and doesn't re-confirm a previously confirmed concern, it gets auto-resolved — same as stale review findings.

### 8. Clean up stale dismissals

**File:** `desloppify/engine/concerns.py`

Add to `generate_concerns()`: before returning, remove any dismissal entry from `state["concern_dismissals"]` whose `source_finding_ids` ALL point to findings that no longer exist as open in state. This prevents unbounded growth.

### 9. Add concerns potentials on import

**File:** `desloppify/intelligence/review/importing/holistic.py` (around line 240)

After setting "review" potentials, also set "concerns" potentials if any concern findings were imported:
```python
concern_count = sum(1 for f in review_findings if f.get("detector") == "concerns")
```
