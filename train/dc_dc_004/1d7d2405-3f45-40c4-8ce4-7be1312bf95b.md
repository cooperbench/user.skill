| **Holistic review** | `detect_holistic_review_staleness()` in `review_coverage.py:132` | `max_age_days=30` — flags stale, also flags >20% file count drift |

Now to your second question — let me talk through the holistic review process end to end.

## The holistic review loop

The idea is a **recursive feedback loop** between an AI agent and the codebase:

### Step 1: Prepare (`desloppify review --prepare --holistic`)

This gathers context about the entire codebase and outputs it to `query.json`. What the agent gets:

- **Codebase statistics** — file counts, LOC, dependency graph shape
- **Architectural signals** — god modules (with first 30 lines as excerpts), coupling metrics, cycle data
- **Convention analysis** — naming styles per directory, error handling strategies
- **Sibling behavior analysis** — for each directory, what imports are shared by ≥60% of files, and which files are outliers (this is how we'd catch "review_cmd.py doesn't call compute_narrative but every other command does")
- **Investigation batches** — 4 independent groups of files organized by dimension, each with a purpose explanation. These can be run in parallel by sub-agents
- **Workflow instructions** — step-by-step guide baked into the JSON so agents don't have to figure out what to do
- **8 dimension prompts** — specific questions to evaluate (abstraction fitness, convention outlier, cross-module architecture, etc.)
- **Narrative context** — current project phase, priorities, score trends

### Step 2: Investigate (agent reads files, evaluates dimensions)

An agent reads `query.json`, follows the workflow, and reads the files in each investigation batch. For each batch, it evaluates the relevant dimensions. The batches are:

1. **Architecture & Coupling** — god modules, import-time side effects
2. **Conventions & Errors** — naming drift, behavioral outliers, mixed error strategies
3. **Abstractions & Dependencies** — util dumping grounds, dep cycles
4. **Testing & API** — critical untested paths, API inconsistency

Small issues (missing import, wrong name) — the agent can fix directly. Cross-cutting issues get written as findings to `findings.json`.

### Step 3: Import (`desloppify review --import findings.json --holistic`)

This ingests the findings into desloppify's state and automatically generates a **remediation plan** at `.desloppify/holistic-plan.md`. The plan:

- Prioritizes findings by estimated score impact (confidence × weight)
- Shows evidence, suggested fix, files to modify, and reasoning for each
- Includes resolve commands so you can mark things done
- Explains the re-evaluate loop at the bottom

### Step 4: Act on the plan

The user (or another agent) works through the remediation plan in priority order. After fixing each issue, they run the resolve command shown.

### Step 5: Re-scan and re-evaluate

Run `desloppify scan` to update automated findings and score. Then re-run the holistic cycle from Step 1. **Key mechanism**: `merge_scan()` auto-resolves old holistic findings that aren't re-reported. So if you fixed the "base.py mixes 4 concerns" issue, the next agent review won't report it, and it silently resolves. The score updates accordingly.

### Staleness

Both per-file and holistic reviews have a **30-day expiry** built in. If the review is stale, the regular scan emits a `subjective_review` finding telling the user to re-run. If the codebase drifts >20% in file count, that also triggers staleness.

### What makes it self-evident for agents

Before these changes, an agent getting `query.json` had to independently figure out what to read and how to parallelize work. Now:
- The **workflow** field is explicit step-by-step instructions
- **Investigation batches** tell agents exactly which files to read for which dimensions
- **File excerpts** are inlined so agents don't always need to read files separately
- **Sibling behavior** data surfaces convention violations that no individual file analysis would catch
- The **system prompt** explains the finding format, quick-fix vs document guidance, and scoring model
- After import, the **remediation plan** is a standalone document that any human or agent can act on
