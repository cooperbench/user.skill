## Step 1: File discovery caching

**Problem**: `find_source_files()` calls `subprocess.run(["find", ...])` every time. During a single TS scan, `find_ts_files(src/)` is called 6+ times with identical args, `find_tsx_files(src/)` 4+ times. Each is a fresh subprocess.

**Fix**: Add `@lru_cache` to `find_source_files` in `utils.py`. Since the args are `(path, extensions_tuple, exclusions_tuple)`, we need to convert lists to tuples for hashability. The wrapper functions (`find_ts_files`, `find_tsx_files`, `find_py_files`) already pass fixed args, so they naturally become cached.

```python
from functools import lru_cache

@lru_cache(maxsize=16)
def _find_source_files_cached(path: str, extensions: tuple[str, ...],
                               exclusions: tuple[str, ...] | None = None) -> tuple[str, ...]:
    """Cached file discovery. Returns tuple for hashability."""
    args = ["find", path]
    # ... same find logic ...
    return tuple(files)

def find_source_files(path: str | Path, extensions: list[str],
                      exclusions: list[str] | None = None) -> list[str]:
    """Find all files with given extensions under a path, excluding patterns."""
    return list(_find_source_files_cached(
        str(path), tuple(extensions), tuple(exclusions) if exclusions else None))
```

**Impact**: Eliminates ~10 redundant subprocess calls per TS scan, ~5 per PY scan. Zero behavior change.

**Files**: `scripts/decruftify/utils.py`

**Fix**: Add `classify_passthrough_tier()` to `detectors/passthrough.py`:

```python
def classify_passthrough_tier(
    passthrough_count: int,
    ratio: float,
    *,
    has_spread: bool = False,
) -> tuple[int, str] | None:
    """Classify passthrough severity into (tier, confidence) or None to skip."""
    if passthrough_count >= 20 or ratio >= 0.8:
        return 4, "high"
    if passthrough_count >= 8 and ratio >= 0.5:
        return 3, "high" if ratio >= 0.7 else "medium"
    if has_spread and passthrough_count >= 4:
        return 3, "medium"
    return None
```

## Precise Answers from Official Documentation

### 1. SKILL.md YAML Frontmatter Format

**Supported fields:**
- `name` (optional): Display name; lowercase, numbers, hyphens only (max 64 chars). Defaults to directory name.
- `description` (recommended): What the skill does and when to use it. Helps Claude decide when to load it.
- `argument-hint` (optional): Hint shown in autocomplete (e.g., `[issue-number]`)
- `disable-model-invocation` (optional): Set to `true` to prevent Claude from automatically loading it. Default: `false`
- `user-invocable` (optional): Set to `false` to hide from `/` menu. Use for background knowledge. Default: `true`
- `allowed-tools` (optional): Tools Claude can use without asking permission when skill is active
- `model` (optional): Model to use when skill is active
- `context` (optional): Set to `fork` to run in a forked subagent context
- `agent` (optional): Which subagent type to use when `context: fork` is set
- `hooks` (optional): Hooks scoped to skill's lifecycle

These are the **only** supported fields. There is no `disable-model-invocation` alternative spelling; it is exactly that.

### 2. How Skill Triggering Works

**Automatic triggering (Claude-invoked):**
- Claude reads skill **descriptions** into context automatically
- When your conversation matches the description, Claude can automatically invoke the skill
- Full skill content only loads when invoked

**Manual triggering (User-invoked):**
- You type `/skill-name` to invoke directly
- Works whether or not Claude can invoke it automatically

**Control:** Use `disable-model-invocation: true` to prevent Claude from automatically invoking (you can still type `/skill-name`). Use `user-invocable: false` to hide from `/` menu and only let Claude invoke it.

**Skill descriptions are always loaded into context** so Claude knows what's available.

**No native dependency management for skills.** The documentation does **not** mention a way to specify dependencies in SKILL.md.

- Reference external scripts (Python, shell, etc.) from your skill using backticks for command execution: `` !`python script.py` ``
- Use `allowed-tools: Bash(python3:*)` permissions to allow Python execution
- Pre-install dependencies on your system before running Claude Code
- Use environment setup in `SessionStart` hooks if you need dynamic installation

- **Abstract instructions** telling Claude what the skill does

## 1. `.mcp.json` Format and Schema

**Location**: The `.mcp.json` file goes at your **project root** (not inside `.claude/`). This is confirmed by the official Claude Code docs and corroborated by a community-filed GitHub issue (#4976) that clarified the confusion.

There are three scopes for MCP configuration:

| Scope | Location | Purpose |
|-------|----------|---------|
| **Local** (default) | `~/.claude.json` (under project path key) | Private to you, current project only |
| **Project** | `.mcp.json` at project root | Checked into version control, shared with team |
| **User** | `~/.claude.json` (top-level `mcpServers` key) | Available across all your projects |

**Supported fields in `.mcp.json`**:

```json
{
  "mcpServers": {
    "server-name": {
      "type": "http",
      "url": "https://example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    },
    "local-server": {
      "command": "/path/to/executable",
      "args": ["--flag", "value"],
      "env": {
        "VAR_NAME": "value"
      }
    }
  }
}
```

The fields per server entry:
- **`type`**: Transport type -- `"http"`, `"sse"`, or `"stdio"` (stdio is implied when `command` is present)
- **`command`**: Executable path (for stdio servers)
- **`args`**: Array of command-line arguments (for stdio)
- **`env`**: Object of environment variables passed to the server
- **`url`**: URL endpoint (for http/sse servers)
- **`headers`**: HTTP headers (for http/sse servers)
- **`oauth`**: OAuth configuration object with `clientId` and `callbackPort` (for http servers needing OAuth)

**Environment variable expansion** is supported in all fields using `${VAR}` or `${VAR:-default}` syntax.

**Important**: `mcpServers` is NOT a valid field in `settings.json` -- it must go in `.mcp.json` or `~/.claude.json`.

## 3. Tool Return Types and Error Handling Best Practices

### Return Types

FastMCP tools can return these types, each auto-converted to the appropriate MCP content block:

| Python Return Type | MCP Content Type |
|---|---|
| `str` | `TextContent` |
| `dict` / Pydantic `BaseModel` | `TextContent` (JSON-serialized) + `structuredContent` |
| `bytes` | `BlobResourceContents` (base64) |
| `Image` | `ImageContent` |
| `list` | Multiple content items |
| `None` | Empty response |

**Recommendation**: Return strings for simple results. Return dicts or Pydantic models when the caller benefits from structured data. The MCP spec (revision 2025-06-18) supports `structuredContent` alongside the traditional `content` array, and FastMCP generates both automatically for dict/model returns.

### Error Handling

There are **two distinct error levels** in MCP:

1. **Protocol errors** (JSON-RPC errors): For unknown tools, invalid arguments, server crashes. These are standard JSON-RPC error responses.

2. **Tool execution errors** (`isError: true`): For business logic failures. These are returned as *successful* JSON-RPC responses with `isError: true` in the result.

In FastMCP, the recommended pattern:

```python
from fastmcp import FastMCP
from fastmcp.exceptions import ToolError

mcp = FastMCP(name="MyServer")

@mcp.tool
def divide(a: float, b: float) -> float:
    """Divide a by b."""
    if b == 0:
        raise ToolError("Division by zero is not allowed.")  # Always sent to client
    return a / b
```

- **`ToolError`**: Message always reaches the LLM client. Use for expected/actionable errors.
- **Standard exceptions** (`ValueError`, `RuntimeError`, etc.): Logged and converted to MCP error responses by default. Can be masked with `mask_error_details=True` for security.
- **`ToolResult`** object: For advanced control over the response structure (multiple content items, structured content, metadata).

## 6. Wrapping an Existing CLI: subprocess vs. Import

**Both approaches are valid**, with different tradeoffs:

**Subprocess (recommended for most CLI wrappers)**:

```python
import subprocess
from fastmcp import FastMCP

mcp = FastMCP("my-cli-wrapper")

@mcp.tool()
async def run_command(args: str) -> str:
    """Run the CLI tool with given arguments."""
    try:
        result = subprocess.run(
            ["my-cli", *args.split()],
            capture_output=True, text=True, timeout=30
        )
        return result.stdout or result.stderr
    except Exception as e:
        return f"Error: {str(e)}"
```

Pros of subprocess:
- Dependency isolation (the CLI manages its own deps)
- Works with any language's CLI tool
- No import conflicts
- Matches how the tool is normally used

**Direct import (when the CLI is a Python package)**:

```python
from fastmcp import FastMCP
from some_cli_package import core_function

mcp = FastMCP("my-wrapper")

@mcp.tool
def analyze(path: str) -> dict:
    """Analyze using the library directly."""
    return core_function(path)
```

Pros of direct import:
- Faster execution (no process spawn overhead)
- Richer return types (dicts, objects instead of string parsing)
- Better error handling (Python exceptions instead of exit codes)
- Type safety

**Recommendation**: If the CLI tool has a well-documented Python API, import directly. If it is a standalone binary, written in another language, or has complex dependency requirements, use subprocess. For your own Python CLI tools, importing the underlying functions directly is almost always better -- it avoids the overhead and fragility of parsing stdout.

Pushed. Now to your question about Python fixers:

No, we don't need to create Python versions of the existing fixers. The current fixers are all deeply TypeScript-specific:

- **unused-imports** / **unused-vars** / **unused-params** — use `tsc --noEmit` output to detect, then AST-aware TS/TSX editing to fix

Python would need entirely different tools:
- **unused imports**: `ruff` or `autoflake` already handle this natively (and better than a custom fixer)

- **dead exports**: Python doesn't have `export` — the concept is `__all__`, which is different
- **smells**: Python indentation-based parsing vs TS brace-based parsing

The `lang/python/fixers/__init__.py` placeholder we created is the right call — it makes the structure mirror cleanly and is ready for whenever Python-specific fixers are needed. But porting the TS fixers wouldn't make sense since the underlying mechanics are completely different for each language.
