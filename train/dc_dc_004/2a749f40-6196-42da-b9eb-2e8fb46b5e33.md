## Gaps in Decruftify's Detection Coverage

### 1. No Circular Dependency Detection

`deps.py` builds a full import graph with fan-in/fan-out/instability, but **never walks cycles**. Circular imports are one of the most impactful structural problems — they cause:
- Subtle runtime bugs (undefined at import time)
- Bundle splitting failures
- Cognitive overhead (which module "owns" the concept?)

The graph is already built. Finding cycles is a DFS away.

### 2. No Cross-Tool Imports

`coupling.py` catches `shared/ → tools/` (backwards coupling) and `shared/ used by 1 tool` (boundary candidates). But it completely misses **tool A → tool B** imports. If `travel-between-images/` imports from `join-clips/`, that's a coupling violation too — tools should only share through `shared/`. This is a one-line filter addition to the existing graph walk.

### 3. React Anti-Patterns (the biggest blind spot)

The tool is strong on dead code and structural metrics, but misses the React patterns that actually cause bugs and performance problems:

**a) Derived state anti-pattern** — `useState` + `useEffect` to compute state that should be `useMemo` or a plain `const`:
```tsx
const [filtered, setFiltered] = useState([]);
useEffect(() => { setFiltered(items.filter(...)) }, [items]);
// Should be: const filtered = useMemo(() => items.filter(...), [items])
```
This is detectable: find `useEffect` callbacks whose only statement is a `setState` call, where the deps match the state derivation source. This is probably the single most common React anti-pattern in production codebases.

**b) useEffect as event handler** — Effects that trigger from a state change to do something that should be inline in the handler that set the state:
```tsx
const [submitted, setSubmitted] = useState(false);
useEffect(() => { if (submitted) navigate('/done') }, [submitted]);
// Should be in onSubmit handler directly
```

**c) Unstable references in deps** — Objects/arrays/functions created in render body passed as deps to `useEffect`/`useMemo`/`useCallback`. Causes infinite re-render loops or wasted work. Pattern: a `useMemo`/`useEffect` whose deps include a variable assigned earlier in the same render via `const x = { ... }` or `const x = [...]`.

**d) Missing `key` prop or index-as-key** — `.map((..., index) => <Component key={index}` in lists that can reorder. Regex detectable.

### 4. Type System Escape Hatches

`smells.py` catches `: any` and `@ts-ignore`, but misses:

- **Type assertions (`as`)**: `foo as Bar`, especially `as any` and `as unknown as X` (double-cast). These bypass type checking and are a frequent source of runtime type errors. High signal-to-noise.
- **Non-null assertion (`!`)**: The current regex `\w+!\.` is too narrow — it misses `foo!` at end of expression, `array[i]!`, `result!.nested!.deep`. The pattern should be `\w+!(?:\.|$|\))` or similar.
- **Excessive type narrowing** — Files with many `if (typeof x === ...)` or `'field' in obj` checks suggest the type model is wrong.

### 5. Async/Promise Problems

`smells.py` catches `async` without `await`, but misses:

- **Fire-and-forget promises** — Calling an async function without `await` or `.catch()`. This silently swallows errors. Pattern: `asyncFn()` on its own line (no `await`, no `.then`, no `const x =`).
- **Sequential awaits that could be parallel**: `const a = await fetchA(); const b = await fetchB();` → should be `Promise.all`. Detectable by looking for consecutive `await` statements with no data dependency between them.
- **Missing error handling on mutations** — `useMutation` calls without `onError` callbacks. (Project-specific but high-value for this codebase.)

### 6. Orphaned Files (not just exports)

`exports.py` finds dead exports. `single_use.py` finds single-importer files. But neither finds **completely orphaned files** — files with zero importers that aren't entry points. The dep graph already has this data (`importer_count == 0`), it just needs filtering for known entry points (pages, route components, config files).

### 7. Barrel File / Re-export Bloat

No detector looks at `index.ts` files. Barrel files that re-export everything from a directory:
- Defeat tree-shaking
- Create implicit coupling (importing one thing pulls in the module graph for everything)
- Hide actual dependency relationships

Detectable: `index.ts` files where most exports are just re-exports, especially if consumers only use 1-2 of the many re-exported symbols.

### 8. Component Render Complexity

`gods.py` counts hooks. `large.py` counts LOC. `complexity.py` counts imports and effects. But nothing measures **JSX return complexity**:
- Deeply nested JSX (5+ levels of nesting)
- JSX return with many conditional branches (ternary chains, `&&` guards)
- Very long JSX returns (>100 lines of JSX) separate from total file LOC

These are readability and maintainability killers that the current scoring system doesn't capture.

### 9. Stale TODOs / FIXMEs (age-aware)

`complexity.py` counts TODOs but treats them as a generic complexity signal worth 2 points each. It doesn't:
- Extract the TODO text for review
- Check if they reference completed work
- Cross-reference with git blame to find TODOs that have been sitting for months/years
- Distinguish actionable TODOs from "TODO: nice to have someday"

A dedicated TODO detector that surfaces the actual text + age would be more useful than a count.

### 10. Inconsistent Error Handling Patterns

`smells.py` catches empty catch blocks and `console.error` without throw/return. `patterns.py` tracks error handling as complementary. But nobody detects:
- **Swallowed errors**: `catch (e) { console.error(e) }` — logged but not rethrown, not returned, not surfaced to UI. Different from empty catch but equally bad.
- **Mixed error surfaces**: Some code uses `toast.error`, some uses `handleError`, some just `console.error`. The pattern detector flags competing approaches at the area level, but doesn't flag individual files that use a non-standard approach.
- **Try/catch wrapping entire function bodies** — A sign that error handling is an afterthought rather than structured.

### 11. Duplication Detection Limitations

`dupes.py` uses text similarity (MD5 + difflib), which misses **semantic duplication**:
- Same algorithm with different variable names
- Same pattern with different types (e.g., 5 hooks that all do "fetch X, transform, set state" with different X)
- Copy-pasted JSX structures with different props

The tool also only compares top-level function bodies. It misses duplicated logic inside functions, duplicated JSX blocks, and duplicated hook patterns.

### 12. No Git History Analysis

The entire tool is snapshot-based. Adding git history would unlock:
- **Hotspots**: Files changed most frequently (high churn = high maintenance cost)
- **Change coupling**: Files that always change together (hidden dependency)
- **Complexity trends**: Is a file getting worse or better over time?
- **Abandoned code**: Files untouched for 6+ months (candidate for removal)
- **TODO age**: When was this TODO written? Has anything happened since?

### 13. Missing Hook Rule Violations

The tool detects hook counts but not hook rule violations:
- Hooks called conditionally (`if (x) { useState(...) }`)
- Hooks called in loops
- Hooks called in nested functions

These are runtime crashes, not just style issues.

## What's Actually Missing (lint-proof gaps)

Here's what no lint will catch, ordered by value, with how each fits into the existing architecture:

### 1. Circular dependencies — extend `deps.py`

**Why it matters**: Circular imports cause undefined-at-import-time bugs, defeat code splitting, and make the dep graph impossible to reason about. `eslint-plugin-import/no-cycle` would catch this but you don't have it installed, and it's notoriously slow. Your dep graph in `build_dep_graph()` already has all the data — you just never walk cycles.

**Implementation**: Add `detect_cycles()` to `deps.py`. Tarjan's SCC or a simple DFS on the `imports` adjacency list. Return each cycle as a finding. One finding per cycle (not per file in the cycle), detector=`"cycles"`, file=smallest path in cycle for stable ID.

**Integration point**: `plan.py` step 6b (reuses graph from 6a). Tier 3, high confidence.

**Effort**: Low. The graph is already built.

### 2. Cross-tool imports — extend `coupling.py`

**Why it matters**: Your ESLint `no-restricted-imports` only blocks `shared/ → tools/`. It doesn't block `tools/travel-between-images/ → tools/join-clips/`. That's an equally wrong coupling direction — tools should only share through `shared/`.

**Implementation**: Add `detect_cross_tool_imports()` alongside the existing `detect_coupling_violations()`. Same pattern — walk the graph, filter for source in `tools/A/` importing target in `tools/B/` where A != B.

**Integration point**: `plan.py` step 6b, same detector=`"coupling"`. Tier 2, high confidence.

**Effort**: Trivial. ~15 lines, mirrors `detect_coupling_violations()`.

### 3. Derived state anti-pattern — new detector `react.py`

**Why it matters**: This is the single most common React bug in production codebases, and **no lint catches it**. The pattern:

```tsx
const [filtered, setFiltered] = useState([]);
useEffect(() => { setFiltered(items.filter(...)) }, [items]);
// Should be: const filtered = useMemo(() => items.filter(...), [items])
```

`useState` + `useEffect` where the effect body's only real statement is a single `setState` call. It causes an unnecessary extra render cycle and is a correctness bug (the derived value is stale for one render frame).

**Implementation**: New detector `detectors/react.py` with multi-line analysis similar to `_detect_async_no_await()` and `_detect_dead_useeffects()` in smells.py. The pattern:
1. Find `useEffect(() => {` 
2. Extract body (you already have this logic in `_detect_dead_useeffects`)
3. Strip comments/whitespace
4. Check if the only statement(s) are `setSomething(...)` calls
5. If so, flag it with the setter name and the deps

**Integration point**: `plan.py` as a new step (or folded into step 7 smells). Detector=`"react"`, tier=3, medium confidence (some legitimate cases exist like effects that read from refs).

**Effort**: Medium. The multi-line parsing machinery already exists in `smells.py` — this is the same brace-tracking pattern with different matching logic.

### 4. Type assertions (`as`) — extend `smells.py`

**Why it matters**: `as any` and `as unknown as X` (double-cast) are type system escape hatches that hide bugs. Your config doesn't include `@typescript-eslint/consistent-type-assertions` (that's in `strict`, not `recommended`). These are higher signal than `: any` because they're active type-erasure, not just lazy annotation.

**Integration point**: Already handled — smells detector is already in the pipeline. Falls into existing tier mapping.

**Effort**: Trivial. Two lines in `SMELL_CHECKS`.

### 5. Orphaned files — new detector `orphaned.py`

**Why it matters**: Files with zero importers that aren't entry points are dead code at the file level. `exports.py` finds dead exports within live files; `single_use.py` finds single-importer files. Nobody catches zero-importer files.

**Implementation**: Walk the dep graph for `importer_count == 0`. Filter out known entry points: page components (matched by path convention `pages/*.tsx`), route config, `main.tsx`, `App.tsx`, `index.ts` barrel files, config files, `*.d.ts`. What remains is orphaned.

**Integration point**: `plan.py` step 6a area (reuses graph). Detector=`"orphaned"`, tier=2 (zero importers = high confidence they're dead), high confidence.

**Effort**: Low-medium. The data exists; the work is defining the entry point heuristic.

### 6. Swallowed errors — extend `smells.py`

**Why it matters**: `catch(e) { console.error(e); }` is functionally identical to an empty catch block — the error is logged but never propagated, returned, or shown to the user. Your existing `console_error_no_throw` partially catches this (checks if console.error is followed by throw/return), but the inverse check is higher signal: catch blocks whose **only** content is logging.

**Implementation**: New multi-line check in smells.py. Find `catch (...) {`, extract body, strip comments/whitespace, check if every statement is `console.error`/`console.warn`/`console.log`. If so, flag as "swallowed error."

**Integration point**: Existing smells pipeline. High severity (same as `empty_catch`).

**Effort**: Low-medium. Similar to `_detect_dead_useeffects` logic.

### 7. Barrel file analysis — new detector `barrels.py`

**Why it matters**: `index.ts` files that re-export everything from a directory defeat tree-shaking and create implicit coupling. If a consumer imports one thing from `shared/hooks/index.ts`, the bundler may pull in the module graph for everything that file re-exports.

**Implementation**: Find `index.ts`/`index.tsx` files. Count `export { ... } from` and `export * from` statements. Cross-reference with the dep graph to check if consumers use a small fraction of what's re-exported. Flag when: many re-exports (>10) AND average consumer uses <30% of them.

**Integration point**: `plan.py` step 6b area. Detector=`"barrels"`, tier=3, medium confidence.

**Effort**: Medium. Needs both re-export counting and consumer-usage analysis.

### 8. Git hotspots — new detector `hotspots.py`

**Why it matters**: Files changed most frequently are your highest maintenance cost. Files that always change together reveal hidden coupling. Files untouched for 6+ months are abandonment candidates. None of this is detectable from a code snapshot.

**Implementation**: Shell out to `git log --format=... --name-only` to build churn stats. Three sub-detectors:
- **Hotspot**: Files with >N commits in last 3 months (high churn)
- **Change coupling**: File pairs that appear in the same commit >M times
- **Stale**: Files with no commits in >6 months (cross-reference with dep graph — stale + low importers = dead)

**Integration point**: New step in `plan.py`. Tier 3-4 depending on signal. Could run behind `--full` flag (like dupes) since git log can be slow.

**Effort**: High. Different data source, needs git access, commit parsing, statistical thresholds.
