Found it. `moveItemsToMidpoint` in `useTimelineFrameUpdates.ts` calls `calculateDistributedFrames` and `deduplicateUpdates` but **never calls `buildAndNormalizeFinalPositions`**. The `batchExchangePositions` fallback path avoids this because it slot-assigns existing frame values sequentially, but `moveItemsToMidpoint` computes a brand-new position for the moved item and then stops, skipping the step that would shift all non-moved items to ensure the sequence starts at 0.

The `changedUpdates` filter that follows correctly picks up B and C as changed too (they had frames 50 and 100 in the DB; after normalization they'll be 0 and 50), so they'll be included in the RPC write. **Root cause:** `moveItemsToMidpoint` imported and called `calculateDistributedFrames` + `deduplicateUpdates` but skipped the third step, `buildAndNormalizeFinalPositions`, which is the one that detects "first item is no longer at frame 0" and shifts everything back. Emits update records for B→0, C→50 in addition to A→100 4. Those all flow through the existing `changedUpdates` filter and get persisted together in a single RPC
