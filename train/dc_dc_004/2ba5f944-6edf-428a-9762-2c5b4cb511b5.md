Good. The `changedUpdates` filter that follows correctly picks up B and C as changed too (they had frames 50 and 100 in the DB; after normalization they'll be 0 and 50), so they'll be included in the RPC write.

**Root cause:** `moveItemsToMidpoint` imported and called `calculateDistributedFrames` + `deduplicateUpdates` but skipped the third step, `buildAndNormalizeFinalPositions`, which is the one that detects "first item is no longer at frame 0" and shifts everything back. The function existed and was correct — it just wasn't wired up in the midpoint path.

**What the fix does:** After deduplication, it calls `buildAndNormalizeFinalPositions(uniqueUpdates, liveShotGenerations)`, which:
1. Builds the full picture of final frames (moved item's new frame + all other items' current DB frames)
2. Sorts them and detects that frame 0 is now occupied by item B (formerly at 50)
3. Emits update records for B→0, C→50 in addition to A→100
4. Those all flow through the existing `changedUpdates` filter and get persisted together in a single RPC
