> AGENT

Yes — there are a few structural issues at play here.

**1. N+1 query fan-out in `useListShots`**

The query does:
- 1 fetch for `shots`
- Then `ceil(N / 10)` sequential batches, each firing 10 parallel `shot_generations` queries

So with 30 shots: 1 + 30 = 31 queries on every mount. With 100 shots: 101 queries. This creates a connection burst on startup, which is likely what triggered the `Failed to fetch` — the browser's per-host connection limit (typically 6) gets saturated, and some requests get queued or dropped before Supabase responds.

The right fix is a single query using `.in()` on shot IDs:
```ts
supabase.from('shot_generations').select(...).in('shot_id', shotIds)
```
Then group client-side. One round-trip, no batching needed.

**2. Silent per-shot failure masks data loss**

```ts
if (sgError) {
  console.error(`Error fetching generations for shot ${shot.id}:`, sgError);
  return { shotId: shot.id, images: [] };  // ← silently returns []
}
```

When a shot's query fails, the user sees a shot with no images — indistinguishable from a legitimately empty shot. The outer query succeeds, React Query considers it done, and no retry happens for the failed shots. Real data loss is invisible.

**3. The cached token comment is a red flag**

`createSupabaseClient.ts` has a long comment explaining it bypasses `navigator.locks` because concurrent queries were queuing for 8+ seconds. That's a symptom, not just a workaround — it means the original query pattern was already generating enough concurrency to deadlock itself on auth lock acquisition. The N+1 fan-out is the root cause of that too.
