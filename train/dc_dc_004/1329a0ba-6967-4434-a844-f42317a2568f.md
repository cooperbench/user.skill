And what about the structure? Why was this so hard to find/fix?

> AGENT

Honestly, because the trailing segment state is scattered across too many places with no clear owner:

1. **`derivedEndFrame`** — computed in `ShotImagesEditor` from `shotGenerations` metadata
2. **`localEndFrame`** — local state in `ShotImagesEditor` for drag responsiveness  
3. **`trailingEndFrame`** — the merge of both, passed as a prop through 3 `React.memo` layers
4. **`metadata.end_frame` DB writes** — in `useFrameCountUpdater`, called from `useSegmentSlotMode`
5. **Drag persistence** — in `useTimelineOrchestrator`

Nobody owns the full lifecycle. The drag path happened to work because it directly calls `setLocalEndFrame`. The form path didn't because `useFrameCountUpdater` had no connection to `setLocalEndFrame` — it only knew about `loadPositions` and hoped the refetch chain would propagate.

The other structural problem is **the `preloadedImages` dual-data-path**. `useShotGenerationsData` line 152: `shotGenerations = preloadedImages || hookData.shotGenerations` — when preloaded images exist, the hook's own data is bypassed. Then there are TWO separate `useTimelinePositionUtils` instances (one in `useShotGenerationsData`, one in `Timeline.tsx`), each with their own `loadPositions`, operating on the same query key. It's very hard to reason about which data path is active and what a refetch actually updates.

Normal segments were a red herring too — they work for a different reason (they change `timeline_frame`, a direct column, and `usePositionManagement` inside `Timeline` picks that up independently). The trailing segment only changes `metadata`, which has no equivalent direct detection path.

The 1-line fix works, but the underlying structure would benefit from a clearer pattern — something like a single `useTrailingSegment` hook that owns all of: reading `end_frame` from metadata, the local optimistic state, and writing changes back.
