### The 3 Structural Issues

#### 1. Shared infrastructure exists but isn't used

`useGalleryPageState` (325 lines) + `useGalleryFilterState` (477 lines) already handle:
- Filter state with per-shot persistence
- Pagination
- Data fetching via `useProjectGenerations`
- Add-to-shot / delete / star mutations
- Query fallback when filters return 0 results
- Skeleton count estimation

`GenerationsPane.tsx` already uses `useGalleryPageState` successfully. ImageGenerationToolPage reimplements all of this manually.

**Why it wasn't used**: `useGalleryPageState` depends on `useCurrentShot` (from route context). ImageGenerationToolPage isn't inside a shot route — it gets its shot from the form's dropdown (`formAssociatedShotId`). This is a real architectural mismatch, but the fix is to make `useGalleryPageState` accept an optional `shotId` parameter rather than duplicating 600+ lines.

#### 2. UI effects mixed with business logic

Sticky header detection (lines 604-660) is a 56-line scroll/resize/RAF/ResizeObserver effect that has nothing to do with image generation. Keyboard navigation (lines 694-724) is generic gallery behavior. Scroll restoration (lines 662-682) is pagination UX. These are all inlined in the same flat component alongside data fetching and mutation logic.

#### 3. Dead code and vestigial patterns

- `isDeleting` (line 68): `useState<string | null>(null)` — never set to anything other than null
- `hasValidFalApiKey` (line 402): hardcoded `true`, but 12 lines of UI for `!hasValidFalApiKey` remain (lines 739-750)
- `formStateReady` (line 176): hardcoded `true`, but checked in an effect
- `effectiveProjectId` (lines 119-130): fallback to `window.__PROJECT_CONTEXT__` / localStorage — defensive hack that 3 other files also implement
- Lines 812-852: 40-line commented-out sticky button block
- Lines 510-511: `isGenerating` and `combinedJustQueued` are identity aliases

**Phase 3: Converge on shared gallery hook** (higher payoff, moderate risk)

Enhance `useGalleryPageState` to accept an optional `shotId` override instead of requiring `CurrentShotContext`. Then ImageGenerationToolPage can pass `formAssociatedShotId` and use the shared hook. This would:

- Ensure bug fixes to gallery logic propagate everywhere
- Align with the pattern already used by `GenerationsPane`

After all three phases, the page should be ~250-300 lines: a thin shell that composes `useGalleryPageState`, `useImageGenerationForm`, `useImageGenerationPageEffects`, and JSX.
