## Item C — Add DB trigger for auto-demote on timeline removal

**What:** Currently there are 7 explicit `demoteOrphanedVariants` call sites scattered
across three hook files:
- `useDropActions.ts` lines 149, 192, 320, 374 (after image-add drops)
- `useDeleteActions.ts` lines 141, 167 (after single/batch delete)
- `useImageManagement.ts` line 144 (after reorder)

The 2 delete-site calls (`useDeleteActions.ts`) are the most critical path and the
easiest to make automatic: when a user removes an image from the timeline, the
mutation sets `timeline_frame = NULL`. A DB trigger on this change can call
`demote_orphaned_video_variants(shot_id)` atomically, eliminating the need for
explicit demote calls after remove operations.

**New migration:** `supabase/migrations/20260224000000_auto_demote_trigger.sql`

```sql
CREATE OR REPLACE FUNCTION trigger_demote_on_timeline_remove()
RETURNS TRIGGER AS $$
BEGIN
  -- Fire demote only when an image is removed from the timeline
  -- (timeline_frame transitions from a value to NULL)
  IF OLD.timeline_frame IS NOT NULL AND NEW.timeline_frame IS NULL THEN
    PERFORM demote_orphaned_video_variants(NEW.shot_id);
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER auto_demote_on_timeline_remove
  AFTER UPDATE OF timeline_frame ON shot_generations
  FOR EACH ROW
  EXECUTE FUNCTION trigger_demote_on_timeline_remove();
```

**App change:** Remove demote calls from `useDeleteActions.ts` lines 141 and 167
(now handled by the trigger). Leave the 4 add-site calls in `useDropActions.ts`
and the 1 reorder call in `useImageManagement.ts` in place — they guard against
add/replace edge cases not covered by this trigger.

**Deploy migration:**
```
npx supabase db push --linked
```

**Risk:** Medium. DB trigger adds overhead on every timeline_frame update. The
demote RPC is idempotent (safe to call when nothing needs demoting — it just
returns 0). Overhead is a single SELECT loop over video segments per shot update,
which is acceptable given the shot sizes in this app (<30 segments typical).

## Item F — Narrow end-image validation to fix swap/reorder regression

**File:** `src/shared/hooks/segments/useSegmentOutputsForShot.ts` lines 541-547

**Bug:** When swapping or reordering images (e.g. A moves from slot 0 to slot 1, B from slot 1 to slot 0),
the video associated with A disappears instead of following A to slot 1. It reappears when
you move back. This is a render-only issue — nothing in the DB changes.

**Root cause:** The end-image validation added in the previous session fires on both:
- **Insertion between pair** (intended): insert X at slot 1 between A and B → A→B video disappears ✓
- **Swap/reorder** (unintended): swap A and B → A→B video disappears ❌

The current check:
```ts
if (endImageInTimeline && endImageInTimeline.generation_id !== endGenId) {
  derivedSlot = undefined;  // fires on both cases
}
```

**Distinguishing the cases:**

| Scenario | A slot | B (end image) new slot | endImageNewSlot > derivedSlot? | Action |
|---|---|---|---|---|
| Insert X between A and B | 0 | 2 (shifted right) | 2 > 0 ✓ | Demote |
| Swap A↔B (A goes to slot 1) | 1 | 0 (before A) | 0 > 1 ✗ | Keep |
| B removed from timeline | 0 | -1 (not found) | -1 === -1 | Demote |

The rule: only demote if the end image is now *further right* than the start image's slot
(something was inserted between them), or the end image is gone entirely. If the end image
has moved *before* the start image, this is a reorder — the video follows its start image.

**Change** (replace lines 541-547):
```ts
if (derivedSlot !== undefined && endGenId && effectiveTimelineData) {
  const endImageInTimeline = effectiveTimelineData[derivedSlot + 1];
  if (endImageInTimeline && endImageInTimeline.generation_id !== endGenId) {
    // Only demote if the end image is still AFTER this slot (X inserted between A and B)
    // or is gone entirely (end image deleted). If the end image moved BEFORE this slot
    // (swap/reorder), the video should follow its start image — ambiguous order > lost data.
    const endImageNewSlot = effectiveTimelineData.findIndex(
      item => item.generation_id === endGenId
    );
    if (endImageNewSlot === -1 || endImageNewSlot > derivedSlot) {
      derivedSlot = undefined;
      slotSource = 'STALE_END_IMAGE';
    }
  }
}
```

**Does the current simplification plan (A-E) fix this?** No. This is a separate regression
from the end-image validation code, not covered by any of items A-E.

**Risk:** The `findIndex` scan is O(n) over timeline images (typically <30). Negligible cost.
The logic carefully preserves all three cases: insertion → demote, removal → demote,
reorder/swap → keep.
