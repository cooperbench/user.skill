## Context

The `props` detector only counts interface size (flags >14 props). It can't distinguish between a form with 30 directly-used props (fine) and a routing component that receives 88 props to forward to children (problem — like ControlsPanel we just deleted). A passthrough detector catches these automatically.

## Architecture: Single file, language-specific functions

```
detectors/passthrough.py     # Shared core + TSX + Python functions
lang/typescript.py           # Calls detect_passthrough_components()
lang/python.py               # Calls detect_passthrough_functions()
```

**Dispatch**: The detector doesn't know what language is active. Each lang config's phase runner calls the right function:

```
scan → lang/typescript.py._phase_structural() → detect_passthrough_components()
scan → lang/python.py._phase_structural()     → detect_passthrough_functions()
```

**Adding a new language**: Add `detect_passthrough_X()` in `detectors/passthrough.py` using the shared `_classify_params()` core, then call it from `lang/X.py`.

## Algorithm

### Shared core: `_classify_params(params, body, passthrough_pattern_fn)`

For each param name, count total occurrences (`\bname\b`) vs passthrough occurrences (language-specific pattern). If ALL occurrences are passthrough → the param is passthrough.

Returns `(passthrough_list, direct_list)`.

### TSX: `detect_passthrough_components(path)`

**Passthrough pattern**: Same-name JSX attribute `propName={propName}`. Each match accounts for 2 occurrences (attribute name + value).

**Component extraction** from .tsx files:
- `const Foo: React.FC<...> = ({ p1, p2 }) =>`
- `const Foo = ({ p1, p2 }: Props) =>`
- `function Foo({ p1, p2 }: Props) {`
- Multi-line destructuring

**Prop extraction** from destructuring: simple names, defaults (`p = val`), aliases (`p: alias` → use local name), rest (`...rest`).

### Python: `detect_passthrough_functions(path)`

**Passthrough pattern**: Same-name keyword arg `param=param` in function calls. Also flag `**kwargs` spread.

**Function extraction** from .py files: `def func_name(p1, p2, ...):` with param extraction handling defaults, type annotations, `*args`, `**kwargs`.

Sure. There are two layers:

## 1. Language dispatch (the `lang/` system)

Each language has a config class (`lang/typescript.py`, `lang/python.py`) that defines **phases** — ordered steps like "Structural analysis", "Coupling", "Smells". Each phase is a function that receives `(path, lang_config)` and returns findings.

The scanner doesn't know what detectors exist. It just iterates the phases from whichever lang config is active:

```
scan --lang python  →  PythonConfig.phases  →  [_phase_unused, _phase_structural, ...]
scan                →  TypeScriptConfig.phases  →  [_phase_logs, _phase_unused, ..., _phase_structural, ...]
```

Each phase function decides which detectors to call internally. So `_phase_structural` in `lang/typescript.py` calls `detect_large_files`, `detect_complexity`, `detect_god_components`, `detect_prop_interface_bloat`, and now `detect_passthrough_components`. The same-named `_phase_structural` in `lang/python.py` calls the Python equivalents — `detect_god_classes` instead of `detect_god_components`, and `detect_passthrough_functions` instead of `detect_passthrough_components`.

## 2. Detector adapters (what passthrough does)

The passthrough detector itself lives in `detectors/passthrough.py` and has **no idea which language is active**. It exports three things:

| Function | Called by | What it does |
|---|---|---|
| `_classify_params()` | Both below | Shared core — counts total vs passthrough occurrences per param name. Language-agnostic: takes a `make_pattern` callback |
| `detect_passthrough_components()` | `lang/typescript.py` | TSX-specific: extracts React component signatures, uses JSX `propName={propName}` as the passthrough pattern |
| `detect_passthrough_functions()` | `lang/python.py` | Python-specific: extracts `def` signatures, uses `param=param` keyword args as the passthrough pattern |

The key insight is that **the shared core doesn't change between languages** — "count how many times a name appears total vs in a forwarding pattern" is the same algorithm. Only the pattern extraction differs:

- **TSX passthrough**: `\bname\s*=\s*\{\s*name\s*\}` (JSX attribute)
- **Python passthrough**: `\bname\s*=\s*name\b` (keyword argument)

## Adding a new language

You'd add `detect_passthrough_X()` in `detectors/passthrough.py` with its own extraction + pattern function, then call it from `lang/X.py`'s structural phase. The `_classify_params` core stays untouched.

## The three patterns in use

1. **Generic detectors** (`graph`, `orphaned`, `single_use`) — operate on an abstract dep graph. Both langs build a graph in their own way (`deps.py` vs `py/imports.py`), then pass it to the same detector. This scales perfectly.

2. **Separate implementations** (`unused`, `complexity`, `gods`, `smells`, `dupes`, `deps`) — top-level `detectors/X.py` is TS-specific, `detectors/py/X.py` is the Python version. They share no code. This works but doesn't scale — every new language means rewriting from scratch.

3. **Shared core + lang functions** (`passthrough`) — one file with a language-agnostic algorithm and language-specific wrappers. This is what we just built. It's the best pattern for detectors where the *algorithm* is the same but the *syntax matching* differs.

## Does it scale?

Honestly — **pattern 2 is the weak point**. The `detectors/py/` directory is essentially a rewrite of 6 top-level detectors. If you added Go or Rust, you'd need `detectors/go/` with another 6 reimplementations.

The detectors that would benefit most from refactoring to pattern 3 (shared core) are:
- **complexity** — the scoring algorithm is the same, only "what counts as a branch/nesting" differs per language
- **gods** — "too many methods/hooks + too many attributes/state" is language-agnostic, the extraction isn't
- **smells** — each smell rule is just a regex pattern, the framework could be shared

The ones that are genuinely language-specific (exports, deprecated, concerns, react, props interfaces) are fine staying TS-only — they detect concepts that don't exist in Python.

**What I think is genuinely elegant:**

1. **The three-layer model maps to real concerns.** Algorithms (detectors/) don't know about findings. Normalization (base.py helpers) doesn't know about parsing. Orchestration (lang/X/) doesn't contain algorithms. Each layer has one job. None should be merged or split further.

2. **Config is data, code is parsing.** A language config is mostly declarative — lists of signals, rules, thresholds, patterns. The only real *code* each language writes is extractors (how to parse functions/classes from source files) and `_phase_unused` (every language has its own lint tool). Everything else follows naturally from the data.

3. **Helpers, not hooks.** Each phase runner explicitly calls `add_structural_signal`, `merge_structural_signals`, etc. You can read any language's `__init__.py` top-to-bottom and know exactly what it does. No base-class magic, no callback registration, no override patterns to trace through. The phase runners ARE ~15-25 LOC, but they're *visible* code — that's better than hiding them behind default methods that you'd have to override.

4. **The extension story is honest.** Adding Go = write extractors (~200 LOC of genuinely unique parsing) + declare config data (~40 LOC) + thin phase wiring (~50 LOC) + unused detection (~30 LOC). The only thing you repeat between languages is the phase runner structure, and those ~15-line phase functions are so short that they read like configuration, not duplication.

**What I checked for over-engineering:**

- **Are 5 shared data types too many?** No — `FunctionInfo` and `ClassInfo` are the contracts generic algorithms need. `ComplexitySignal`, `GodRule`, `SmellRule` are the config types that make signals/rules/smells data-driven instead of code-driven. Without them you'd have loose dicts flying around.

- **Are 7 normalization helpers too many?** I considered whether `make_cycle_findings` (~7 LOC) and `make_orphaned_findings` (~7 LOC) are too trivial to extract. But consistency wins — having a helper for *every* finding type means the pattern is "always use a helper," not "use a helper sometimes, inline other times." And a third language would need those 7 lines too.

- **Is LangConfig growing too many fields?** It'll have ~26 fields with the new additions. I considered grouping (e.g., `thresholds: dict` instead of `large_threshold`, `complexity_threshold`). But `lang.large_threshold` is clearer than `lang.thresholds["large"]`. It's a configuration object — having many named fields is appropriate.

- **Should we have default phase implementations on LangConfig?** This would let languages omit phase runners entirely if they want the standard behavior. I decided against it: you'd lose visibility (phase logic hidden in base class), and customization via method overrides is harder to read than writing a short explicit function. The phase runners are already only ~15 LOC — making them zero LOC by hiding them isn't worth the indirection.

The plan doesn't try to make phase runners "configurable" via hooks or lists of extra detectors. TS's structural phase is ~5 lines longer than Python's because it adds `detect_mixed_concerns`.
