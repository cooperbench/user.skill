## Current State

The narrative engine already does a good job of **prioritizing actions** — it sorts by type (auto_fix → reorganize → refactor → manual_fix → debt_review) and then by score impact. But the guidance is essentially: "here's your top-1 action, go do it." It's sequential and single-threaded in its thinking.

There are two big opportunities for smarter nudges:

---

## When to Nudge Toward Multiple Agents

The key insight: **some categories of work are completely independent and can be parallelized safely, while others conflict.**

### Safe to parallelize (nudge toward multiple agents):

1. **Auto-fixers across different detectors** — `fix unused-imports` and `fix debug-logs` touch different lines for different reasons. An agent running each one won't conflict. If the top 2-3 actions are all `auto_fix` type but different detectors, that's a clear signal: "These 3 fixers are independent — you can run them in parallel."

2. **Refactors in disjoint file sets** — If the `structural` detector flags `src/auth/AuthManager.tsx` as a god file and `props` flags `src/dashboard/DashboardGrid.tsx` as having bloated props, those are independent refactors. When the top actions touch **non-overlapping files**, they can be parallelized.

3. **Auto-fix + manual refactor in disjoint areas** — One agent runs `fix unused-imports` across the codebase while another manually decomposes a god file. These don't typically conflict since unused imports live in many files, but the god file refactor is localized.

4. **Test coverage + everything else** — Writing tests for uncovered modules is almost always independent of all other cleanup work. If `test_coverage` shows up as an action alongside anything else, that's a "give this to a separate agent" signal.

### NOT safe to parallelize (keep sequential):

1. **Auto-fixers that cascade** — `fix debug-logs` can orphan imports, which then need `fix unused-imports`. The system already knows this (post-fix hooks). When there's a cascade dependency, the nudge should be "run these in order, not in parallel."

2. **Reorganize actions** — `move` rewires imports across files. Two concurrent `move` operations could conflict badly (both trying to rewrite the same import file). Reorganize work should be serialized.

3. **Overlapping file sets** — If `smells` and `structural` both flag the same files, refactoring them concurrently would cause merge conflicts.

### How to detect this:

The data is already there. Each action has a detector, and each finding has a `file`. You could:
- Build a file-overlap matrix between the top N actions
- Check the cascade dependencies (already modeled in post-fix hooks)
- If overlap is zero and no cascade: "These can be parallelized across agents"
- If overlap is high: "Work on these sequentially — same files involved"

---

## When to Nudge Toward Using Fixers

### Strong nudge (should be louder than today):

1. **When auto_fix actions dominate the impact** — If the top 3 actions by score impact are all auto-fixable and together account for >50% of recoverable points, the message should be emphatic: "You can recover X points automatically. Run these fixers before doing any manual work."

2. **First scan with many T1 findings** — T1 is imports and debug logs, both fully auto-fixable. On a first scan where T1 items are the majority, the nudge should be: "Start with the fixers — they'll clear the noise so you can see what actually matters."

3. **After a regression** — If a score drop is primarily driven by new findings in auto-fixable detectors, the nudge should be: "This regression is mostly auto-fixable — run `fix unused-imports` to recover."

4. **Stagnation with available fixers** — If the score is plateaued AND there are auto-fixable findings sitting there, the nudge should be more pointed: "You've been stuck at X for N scans, but there are Y auto-fixable items. That's free points."

### Softer nudge / don't nudge:

1. **When auto-fix impact is marginal** — If the remaining auto-fixable findings are all low-confidence and worth <0.5 points total, don't push fixers. The real work is elsewhere.

2. **When the user is in maintenance phase** — Score >93, everything is clean. Don't nag about 2 remaining low-confidence unused imports. The fixers might be more disruptive than helpful at this point.

3. **When wontfix debt is the real problem** — If the strict/lenient gap is the main story, fixers aren't the answer. The nudge should be toward `resolve wontfix` review, not automation.

Here's how I see it fitting together.

## The missing abstraction

The current narrative computes **what** to do (actions list) and **why** (dimensions, debt, headline). What's missing is **how** — the execution strategy. Today, the system says "here's your top action, go." That works for a single agent working sequentially, but it leaves intelligence on the table.

The data for smarter guidance already exists. It just needs one more analysis layer.

## Strategy as a natural extension of actions

The existing flow is:

```
state → phase → dimensions → debt → actions → tools → headline → reminders
```

Strategy slots in after actions, consuming them:

```
state → phase → dimensions → debt → actions → strategy → tools → headline → reminders
```

It's a pure function: `_compute_strategy(actions, findings, lang) → dict`. Same pattern as everything else in narrative.py. The strategy dict becomes a top-level key in the narrative output, flows into query.json, and the consuming LLM reads it.

## What the strategy actually computes

Two things, both derived from the same underlying analysis:

### 1. Fixer leverage

This answers: "what fraction of the work is mechanical?"

The inputs are already there — each action has a `type` ("auto_fix" vs others) and `impact` (score improvement). The computation:

```
auto_fix_count / total_open_count → coverage ratio
auto_fix_impact / total_recoverable_impact → impact ratio
```

The recommendation follows from these ratios:

- **Strong** (coverage > 40% or impact > 30%): "Run fixers first — they'll clear X of Y findings automatically, recovering ~Z pts before you touch anything manually."
- **Moderate** (coverage 15-40%): "N findings are auto-fixable. Worth running before manual work."
- **None** (coverage < 15% or no fixers): Don't mention fixers.

The important nuance: on a **first scan** with lots of T1 findings, the recommendation should be strong regardless of ratios, because T1 is the low-hanging fruit and running fixers gives the agent an immediate win + a cleaner baseline to work from. During **stagnation**, if auto-fixable findings are sitting there untouched, the nudge should be more pointed: "You've been at X for N scans but there are Y auto-fixable items sitting untouched."

### 2. Parallelism analysis (lanes)

This answers: "can this work be split across independent agents?"

The key insight is that different action types have different conflict semantics:

- **Auto-fix actions** never conflict with each other. They're surgical edits (remove an import, remove a console.log) that touch different patterns even when they hit the same file. They do have **cascade ordering** though — removing debug logs can orphan imports, so `debug-logs` should precede `unused-imports`. This is already modeled in `post_fix` hooks but currently only expressed at runtime.
- **Move/reorganize actions** always conflict with each other. Each `move` rewrites imports across the codebase. Two concurrent moves could both try to rewrite the same import statement.
- **Refactor actions** conflict when they target the same files. Decomposing `AuthManager.tsx` while also refactoring its React patterns is one job, not two.
- **Test coverage** never conflicts with anything. Writing tests is purely additive — new files, no existing edits.

So the lane computation is:

1. All auto-fix actions → one "cleanup" lane, with cascade ordering within it
2. All reorganize actions → one "restructure" lane (serialized)
3. Refactor actions → partition by file overlap into N lanes
4. Test coverage → its own lane (always independent)

For step 3, the file data is right there: each finding has a `file` field, and we can build `{detector → set of files with open findings}`. Two refactor actions whose file sets don't intersect go in different lanes. Connected components via file overlap determines the grouping.

Then: `can_parallelize = len(lanes) >= 2 and at least 2 lanes have meaningful work`.

"Meaningful work" means > 5 findings and > 1.0 pts of impact. No point suggesting parallelism for 2 trivial items.

### How lanes get expressed

Rather than a complex nested structure, I'd annotate each action with a `lane` label and add cascade ordering:

```python
# Within the existing action dict:
{"priority": 1, "type": "auto_fix", "lane": "cleanup", ...}
{"priority": 2, "type": "auto_fix", "lane": "cleanup", "after": [1], ...}
{"priority": 3, "type": "refactor", "lane": "file-health", ...}
{"priority": 4, "type": "refactor", "lane": "components", ...}
```

And the strategy dict summarizes:

```python
"strategy": {
    "lanes": {
        "cleanup": {"actions": [1, 2], "impact": 5.2, "automation": "full"},
        "file-health": {"actions": [3], "impact": 3.1, "automation": "manual"},
        "components": {"actions": [4], "impact": 2.4, "automation": "manual"},
    },
    "can_parallelize": True,
    "fixer_leverage": {"coverage": 0.61, "impact_share": 0.43, "recommendation": "strong"},
    "hint": "...",
}
```

The lane annotation on actions is lightweight — it doesn't change the existing data structure, just adds a field. An LLM that doesn't care about strategy ignores it. One that does can group by lane and reason about parallelism.

## The cascade graph

Today, cascade dependencies are implicit in `post_fix` hooks (a runtime callback). Strategy needs them as static data. Extract them:

```python
FIXER_CASCADE = {
    "debug-logs": ["unused-imports"],
    "dead-useeffect": ["unused-imports"],
}
```

This is small and unlikely to grow much. It encodes the known fact that removing code can orphan imports. The strategy computation uses this to order actions within the cleanup lane and to note it in the hint.

## When each nudge fires

### Fixer nudge

| Situation | Signal | Nudge strength |
|---|---|---|
| First scan, T1 dominates | coverage > 40% | **Strong**: "Start here — clear the noise" |
| Mid-grind, fixers untouched | coverage > 15% | **Moderate**: "N findings are mechanical" |
| Stagnation + fixers available | any coverage | **Strong**: "Free points sitting on the table" |
| Regression from auto-fixable detectors | new findings in auto_fix dets | **Strong**: "This regression is mostly auto-fixable" |
| Maintenance, <5 remaining | coverage < 15% | **None**: don't nag about 3 low-conf imports |
| Python | no fixers | **None**: never mention fixers |

### Multi-agent nudge

| Situation | Signal | Nudge |
|---|---|---|
| 2+ lanes, each >5 findings, >1.0 pts | file sets disjoint | "These touch different files — safe to work in parallel" |
| Cleanup lane + manual lane | different work types | "Run fixers while manually refactoring X" |
| test_coverage + anything | inherently independent | "Test writing is independent of cleanup" |
| All work in one detector | single lane | No parallelism nudge |
| <10 total findings | too small to split | No parallelism nudge |
| Reorganize-heavy | all moves conflict | "Work through moves sequentially" |

## What the hint looks like

The hint is one or two sentences — specific, actionable, not generic advice. Examples:

- **Fixer-first + parallel**: "3 fixers can clear 73/120 findings (+5.2 pts). Run them first, then split structural refactoring and component cleanup across separate agents — they touch different files."
- **Fixer-first, no parallel**: "61% of findings are auto-fixable. Run `desloppify fix debug-logs --dry-run` then `unused-imports` (cascade order). The remaining 47 items are all in Code quality — work through them sequentially."
- **No fixers, parallel**: "Structural work in `src/auth/` and component refactoring in `src/dashboard/` are independent — safe to parallelize across agents."
- **No fixers, no parallel**: "All 23 findings are in Organization. Work through them with `desloppify next`."
- **Stagnation + fixers**: "Score stuck at 78.3 for 4 scans, but 31 findings are auto-fixable. That's the breakthrough."

## What stays the same

- The `actions` list keeps its existing sort (type-order then impact). Strategy adds metadata but doesn't rearrange.
- `reminders` stay as-is. Strategy is higher-level than reminders — it's about overall approach, not contextual tips. The existing `auto_fixers_available` reminder becomes somewhat redundant if fixer leverage is strong, but reminder decay already handles that gracefully.
- `headline` stays focused on phase/trajectory. Strategy adds its own `hint` rather than overloading the headline.
- The terminal display in `_show_post_scan_analysis` could show the strategy hint alongside or instead of the current "Suggested next" line when a strategy exists.

## Edge cases to think about

**Partial overlap between refactors**: Two detectors flag different things in the same file — `smells` finds code issues in `utils.ts`, `structural` flags it as too large. These should be the same lane (same file = same refactoring job).

**Auto-fix as a phase, not a lane**: There's a question of whether auto-fix should be a "lane that runs in parallel with manual work" or a "phase that runs before manual work." I think **phase** is more natural. The fixers change file contents, and doing a manual refactor on a file that's about to have imports removed from it is messy. Cleaner to say: run fixers → rescan → then manual work. The parallelism recommendation applies to the manual work after fixers are done.

**The debt review action**: Doesn't belong in any lane. It's a meta-activity (reviewing wontfix decisions) that can happen anytime. Strategy can ignore it or put it in its own "housekeeping" lane.

**Regression context**: If the regression is primarily from auto-fixable detectors, the strategy hint should say so explicitly. The fixer leverage computation can check whether the regressed findings (from the diff) are in auto-fixable detectors.
