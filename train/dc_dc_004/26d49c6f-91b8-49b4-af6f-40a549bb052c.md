# Plan: `decruftify move` — move files and update all imports

## Context

When moving/renaming source files, all import references across the codebase must be updated. This is currently manual and error-prone. We already have a dependency graph (`build_dep_graph`) that knows exactly who imports each file, so we can build a reliable `move` command on top of it.

## Design

**Standalone command** (not under `fix`), since this is a refactoring tool, not a finding resolver.

```
decruftify move <source> <dest> [--dry-run] [--lang typescript|python]
```

- `source`: file to move (relative path from project root)
- `dest`: destination path (file path or directory — if directory, keeps filename)
- `--dry-run`: show what would change without modifying files
- `--lang`: auto-detected from source file extension if omitted

### 2a. Validate and resolve paths

```python
def cmd_move(args):
    source = resolve_path(args.source)  # absolute
    dest_raw = args.dest
    # If dest is a directory (or ends with /), keep source filename
    dest_path = Path(dest_raw)
    if dest_path.is_dir() or dest_raw.endswith("/"):
        dest_path = dest_path / Path(source).name
    dest = resolve_path(str(dest_path))

    # Validate source exists, dest doesn't
    if not Path(source).is_file():
        error(f"Source not found: {rel(source)}")
    if Path(dest).exists():
        error(f"Destination already exists: {rel(dest)}")
```

### 2b. Build dep graph, find importers

```python
    lang = _resolve_lang(args)  # auto-detect from extension if --lang not given
    graph = lang.build_dep_graph(Path(args.path))

    importers = graph.get(source, {}).get("importers", set())
    own_imports = graph.get(source, {}).get("imports", set())
```

### 2c. Compute import replacements for each importer

For each file that imports the source, find the exact import line and compute the new specifier.

**TypeScript logic** (`_compute_ts_replacements`):
- Find import lines referencing the source file
- For `@/` alias imports: old = `@/` + rel_to_src(old_path), new = `@/` + rel_to_src(new_path) (strip extension)
- For relative imports: old = relative(importer_dir → old_path), new = relative(importer_dir → new_path) (strip extension)
- Preserve quote style (detect `'` vs `"` in the line)

**Python logic** (`_compute_py_replacements`):
- For absolute imports: convert old path to dotted module → new dotted module
- For relative imports: recompute relative dots + module based on new location
- Both `from X import Y` and `import X` forms

### 2d. Update the moved file's own imports

When the file moves to a new directory, its own relative imports break. For each relative import in the moved file, recompute the specifier from the new location.

**TypeScript**: Only relative imports (`./`, `../`) need updating. `@/` imports are location-independent.

**Python**: Relative imports (`from .foo import bar`) need updated dot-prefix. Absolute imports are location-independent.

### 2e. Execute or dry-run

```python
    # Dry run: print all changes
    if args.dry_run:
        print(f"  Would move: {rel(source)} → {rel(dest)}")
        print(f"  Would update {len(importers)} importing files:")
        for importer, replacements in changes.items():
            for old, new in replacements:
                print(f"    {rel(importer)}: {old} → {new}")
        return

    # Execute: move file, then do all replacements
    Path(dest).parent.mkdir(parents=True, exist_ok=True)
    shutil.move(source, dest)

    for filepath, replacements in changes.items():
        content = Path(filepath).read_text()
        for old_str, new_str in replacements:
            content = content.replace(old_str, new_str)
        Path(filepath).write_text(content)
```

### Key helper: `_compute_ts_specifier`

```python
def _compute_ts_specifier(from_file: str, to_file: str) -> tuple[str, str]:
    """Compute both @/ alias and relative import specifiers for a TS file.

    Returns (alias_specifier, relative_specifier).
    """
    # @/ alias: strip SRC_PATH prefix, strip extension
    to_rel_src = Path(to_file).relative_to(SRC_PATH)
    alias = "@/" + str(to_rel_src).rsplit(".", 1)[0]  # strip .ts/.tsx
    # Handle index files: @/foo/bar/index → @/foo/bar
    if alias.endswith("/index"):
        alias = alias[:-6]

    # Relative: from_file dir → to_file, strip extension
    from_dir = Path(from_file).parent
    relative = os.path.relpath(to_file, from_dir)
    relative = relative.rsplit(".", 1)[0]  # strip extension
    if not relative.startswith("."):
        relative = "./" + relative
    if relative.endswith("/index"):
        relative = relative[:-6]

    return alias, relative
```

### Finding import lines to replace

Rather than regex-matching import syntax, do simple string replacement on the import specifier within quotes. For each importer file:

1. Compute old specifier(s) — both `@/` form and relative form from that importer's location
2. Compute new specifier(s) — same two forms for the new location
3. Read the file, find lines containing old specifier in quotes, replace with new specifier (preserving quote style)

This is safe because import specifiers are unique path strings — a specifier like `@/shared/hooks/useVideoFrameExtraction` won't appear anywhere except in import statements.

## What's wrong with the current score

The current strict score is:

```
strict_score = (fixed + false_positive) / total_findings * 100
```

This is **relative to findings discovered**, not to actual code quality. Problems:

1. **Not comparable across codebases.** A 500-file codebase with 10 findings (8 fixed) scores 80%. A 5000-file codebase with 200 findings (180 fixed) scores 90%. The first is objectively cleaner, but scores lower.

2. **Score goes DOWN when you add new detectors.** If you add a detector that finds 50 new issues, your score drops even though the code didn't change.

3. **Gaming via wontfix/false_positive.** The "lenient" score counts wontfix as addressed. Even the strict score can be gamed by liberally marking false_positive.

4. **No baseline.** There's no concept of "how bad could this be?" — the score is purely about what was found, not what's possible.

## A better model: Issue density vs. codebase size

The idea is: **score = how clean is this codebase, objectively, right now?**

For each detector, we can estimate a **maximum expected issues** based on codebase metrics:

| Detector | Unit | Reasoning |
|----------|------|-----------|
| `unused` (imports/vars) | per 1000 LOC | More code = more potential unused |
| `logs` | per file | Any file could have debug logs |
| `exports` | per file | Each file can have dead exports |
| `deprecated` | flat cap (~20) | Deprecated symbols are finite |
| `structural` (large/complex/gods) | per file | Each file could be oversized |
| `coupling` (single-use, boundary) | per file in shared/ | Shared abstractions that could be misplaced |
| `orphaned` | per file | Any file could be orphaned |
| `cycles` | per directory | Graph cycles are per-module |
| `smells` | per 1000 LOC | Code smells scale with code volume |
| `flat_dirs` | per directory | Any dir could be flat |
| `naming` | per directory | Each dir could have inconsistency |
| `patterns` | per area | Each area could have competing patterns |

Then the score would be:

```
For each detector:
  potential = estimate_potential(codebase_metrics)
  actual_open = count open findings for this detector
  detector_score = max(0, 1 - actual_open / potential)

overall = weighted_average(detector_scores, tier_weights)
score = round(overall * 100)
```

This gives you:
- **100** = zero open findings (clean codebase)
- **~80** = some issues but manageable
- **~50** = significant debt
- The score is **absolute** — same code = same score regardless of what's been fixed/wontfixed in the past
- Adding a new detector only hurts the score if it finds actual issues
- Wontfix items still count as open (they're real debt — this is the strict score)

## What counts as "potential"

Here's where I'd keep it simple. Rather than trying to model each detector's theoretical maximum, use a **codebase-size-normalized density** approach:

```python
def compute_objective_score(state: dict, codebase_metrics: dict) -> float:
    """Score = 100 - penalty, where penalty scales with issue density."""
    total_files = codebase_metrics["total_files"]
    total_loc = codebase_metrics["total_loc"]
    total_dirs = codebase_metrics["total_dirs"]
    
    # Count open findings weighted by tier
    weighted_open = 0
    for f in state["findings"].values():
        if f["status"] in ("open", "wontfix"):  # strict: wontfix = still debt
            weighted_open += TIER_WEIGHTS[f["tier"]]
    
    # Normalize: issues per file (the main scaling factor)
    # A "perfect" codebase would have 0. A typical one might have 0.5-1.0 per file.
    density = weighted_open / max(total_files, 1)
    
    # Map density to 0-100 using a reference point:
    # density=0 → 100, density=1.0 → ~50, density=2.0 → ~25
    # Using exponential decay: score = 100 * exp(-k * density)
    import math
    score = 100 * math.exp(-0.7 * density)
    
    return round(max(0, score), 1)
```

The exponential curve means:
- 0 issues/file → 100
- 0.5 issues/file → ~70 
- 1.0 issues/file → ~50
- 2.0 issues/file → ~25

## What about false_positive and resolved items?

- **false_positive**: Doesn't count as open. It's not a real issue.
- **fixed/auto_resolved**: Doesn't count as open. The issue is gone.
- **wontfix**: **Still counts in strict score.** It's acknowledged debt.
- **open**: Counts. It's an unaddressed issue.

The "lenient" score could exclude wontfix (treating accepted debt as OK). The strict score counts everything that's actually present in the code.

### Scoring: equal voice per detector, weighted by tier

The critical insight: **don't sum all potentials together**. If you do, `unused` with 5000 imports drowns out `coupling` with 50 edges.

Instead, each detector gets an independent **pass rate** (0-1), and the final score is a **tier-weighted average** of pass rates:

```python
DETECTOR_TIER = {
    "unused": 1, "logs": 1,
    "exports": 2, "deprecated": 2,
    "structural": 3, "gods": 3, "props": 3, "passthrough": 3,
    "single_use": 3, "coupling": 3, "orphaned": 3,
    "flat_dirs": 3, "naming": 3, "smells": 3, "react": 3,
    "dupes": 3, "patterns": 3,
    "cycles": 4,
}
TIER_WEIGHT = {1: 1, 2: 2, 3: 3, 4: 4}
CONFIDENCE_WEIGHT = {"high": 1.0, "medium": 0.7, "low": 0.3}

def compute_objective_score(findings, potentials, strict=True):
    by_detector = group open (+ wontfix if strict) findings by detector
    
    total_weight = 0
    total_score = 0
    
    for detector, potential in potentials.items():
        if potential <= 0:
            continue
        
        # Confidence-weighted failures
        # A "low" confidence finding = 0.3 of an issue, not 1.0
        failures = sum(
            CONFIDENCE_WEIGHT[f["confidence"]]
            for f in by_detector.get(detector, [])
        )
        
        pass_rate = max(0, (potential - failures) / potential)
        weight = TIER_WEIGHT[DETECTOR_TIER.get(detector, 2)]
        
        total_weight += weight
        total_score += pass_rate * weight
    
    return round((total_score / total_weight) * 100, 1)
```

### Why this works

Say a codebase has:
- `unused`: 3000 imports, 40 unused → 98.7% pass, weight 1
- `structural`: 400 files, 12 flagged → 97.0% pass, weight 3  
- `coupling`: 80 boundary edges, 8 violations → 90.0% pass, weight 3
- `cycles`: 1200 edges, 15 in cycles → 98.8% pass, weight 4

Score = (98.7×1 + 97.0×3 + 90.0×3 + 98.8×4) / (1+3+3+4) = **95.6**

Now fix all coupling violations (8 items):
Score becomes **97.8** (+2.2 points)

Fix all 40 unused imports instead:
Score becomes **95.7** (+0.1 points)

Fixing 8 coupling issues (T3) moves the score 20x more than fixing 40 unused imports (T1). This is correct — structural issues matter more than lint.

### Properties a mega nerd would verify

1. **Monotonic**: Fixing any issue can only increase the score. Adding a clean detector can only increase the score.
2. **Bounded**: Always 0-100. 100 = every check passed.
3. **Comparable**: Two codebases scanned with the same detectors produce directly comparable scores.
4. **Decomposable**: You can show per-detector pass rates — immediately see what's dragging you down.
5. **Volume-independent**: A detector checking 5000 things has the same influence as one checking 50 (at the same tier).
6. **Resistant to gaming**: Strict score counts wontfix as debt. Can't inflate without actually fixing.
7. **Confidence-aware**: Speculative findings (low confidence) penalize less than definitive ones.
8. **Stable**: Adding a new file without issues barely changes the score (potential goes up by 1, no new failures).

## Incremental Scan Behavior

**New files added → rescan:**
- `file_finder` discovers new files → potentials increase
- New findings may appear → failures increase
- Score adjusts: if new files are clean, score stays same or rises slightly. If new files have issues, score drops.
- This is correct — adding bad code lowers the score.

**Files deleted → rescan:**
- Files disappear from `file_finder` → potentials decrease
- Old findings auto-resolve → failures decrease
- Score adjusts naturally.

**Language-scoped scan (`--lang python`):**
- Only Python detectors run → only Python potentials update
- TS potentials remain from last TS scan
- Overall score uses both (TS may be stale — staleness warning handles this)
- Potentials should be stored per-language so they can update independently

**Path-scoped scan (`--path src/tools/video`):**
- Only a subdirectory is scanned — potentials would be artificially small
- **Decision: path-scoped scans do NOT update potentials.** Only full scans do.
- Findings are still updated (new/resolved/reopened), but potentials and objective score come from the last full scan.

**New detector added → rescan:**
- New detector checks N things → new potential appears
- If it finds 0 issues → dimension pass rate is 100% → score goes up slightly (new clean dimension)
- If it finds issues → score may drop → correct behavior

     ```python
     def detect_flat_dirs(path: Path, file_finder, threshold: int = 20) -> list[dict]:
         files = file_finder(path)
         dir_counts: Counter[str] = Counter()
         for f in files:
             parent = str(Path(f).parent)
             dir_counts[parent] += 1
         entries = []
         for dir_path, count in dir_counts.items():
             if count >= threshold:
                 entries.append({"directory": dir_path, "file_count": count})
         return sorted(entries, key=lambda e: -e["file_count"])
     ```
