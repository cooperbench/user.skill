# Plan: Redesign Incoming Task Placeholders with Task-ID Matching

## Context

The TasksPane placeholder system shows immediate UI feedback while async task creation is in flight. The current implementation uses heuristic matching (taskType + timing window) and fragile baseline arithmetic for count display. With rapid multi-batch image generation (10+ images), this causes persistent placeholders and inflated counts. We just fixed a dual-placeholder bug, but the underlying architecture is still fragile.

**Goal**: Replace heuristic matching with exact task-ID matching. Remove baseline arithmetic. Make it clean and deterministic.

---

## Architecture Changes

### New `IncomingTask` interface
```typescript
interface IncomingTask {
  id: string;              // placeholder ID
  startedAt: Date;
  taskType: string;
  label: string;
  expectedCount?: number;  // default 1
  taskIds?: string[];      // real task IDs, set after creation completes
}
```
- **Removed**: `baselineCount` (no more baseline arithmetic)
- **Added**: `taskIds` (for exact matching)

### New context API
- `addIncomingTask(task)` → id (unchanged)
- `removeIncomingTask(id)` (unchanged, for cleanup/errors)
- `resolveTaskIds(id, taskIds[])` → sets real task IDs on placeholder
- **Removed**: `completeIncomingTask` (replaced by resolve + remove)

### New TaskList matching (replaces heuristic)
```typescript
// If we know the real task IDs, hide when ANY appear in the task list
if (incoming.taskIds?.length) {
  return !incoming.taskIds.some(id => realTaskIds.has(id));
}
// No task IDs yet → always show (still creating)
return true;
```

### New count calculation (replaces baseline arithmetic)
```typescript
// Only count placeholders whose tasks haven't been created yet
const unresolvedCount = incomingTasks
  .filter(t => !t.taskIds?.length)
  .reduce((sum, t) => sum + (t.expectedCount ?? 1), 0);
return dbCount + unresolvedCount;
```

Good question. Let me look at it critically.

**The ceremony-to-signal ratio is high.** Every caller does the same 5-line dance:

```typescript
const { addIncomingTask, removeIncomingTask, resolveTaskIds } = useIncomingTasks();
// ...
const incomingTaskId = addIncomingTask({ taskType: 'upscale', label: '...' });
try {
  const result = await createImageUpscaleTask(params);
  resolveTaskIds(incomingTaskId, [result.task_id]);
} finally {
  removeIncomingTask(incomingTaskId);
}
```

That's 17 copies of the same lifecycle. We replaced one fragile mechanism with a correct one, but we didn't reduce the surface area. The beautiful version would be something like:

```typescript
const withPlaceholder = useTaskPlaceholder();

await withPlaceholder(
  { taskType: 'upscale', label: 'Upscaling...' },
  () => createImageUpscaleTask(params),
);
```

One hook owns the full lifecycle — add, resolve, refetch, remove, error handling. Callers just say "show a placeholder while this runs." The three-callback destructure, the try/finally, the `resolveTaskIds` call — all gone from 17 files.

**Other things that bug me:**

- `taskType` on `IncomingTask` is no longer used for matching — it's just display metadata now, but it's still a required field everywhere
- The `execute` return type `Promise<string[] | void>` forces callers to do `return result || undefined` — slightly awkward
- Three-step lifecycle (add → resolve → remove) for what's conceptually one thing: "placeholder until real task appears." `resolveTaskIds` could auto-schedule removal after a short delay, making the explicit `removeIncomingTask` unnecessary for the happy path

The architecture is correct now. Making it beautiful would mean collapsing the boilerplate into a single abstraction. Want me to do that?
