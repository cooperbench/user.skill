## Critical Assessment of the Subjective Dimensions

### 1. Significant Overlap Between Dimensions

Several dimensions are measuring the same things from slightly different angles, which creates **double-counting in scoring** and **confused LLM outputs** where the model has to decide which bucket a finding belongs in:

- **`contract_coherence` vs `type_safety`**: "Return type annotations that don't cover all paths" appears nearly verbatim in both. A function declared `-> str` that can return `None` is a type safety issue *and* a contract coherence issue. The LLM has to pick one, and whichever it picks penalizes only that dimension — or it reports it twice, penalizing both.

- **`authorization_consistency` vs `authorization_coherence`**: These are the same dimension at different scopes (codebase vs file). But both are in the per-file dimension set, which means for a single file review, the model is asked to evaluate auth consistency *within the file* and *across the codebase* simultaneously — but it's only looking at one file. `authorization_consistency` is essentially unanswerable in per-file mode.

- **`abstraction_fitness` vs `high_level_elegance` vs `mid_level_elegance`**: "Pass-through wrappers" and "wide options/context bag APIs" live in `abstraction_fitness`, but these are exactly the kind of thing that degrades mid-level elegance. The `skip` clauses try to delineate boundaries ("if the core issue is dependency direction, use cross_module_architecture") but this is asking the LLM to do jurisdictional routing, not quality assessment.

- **`ai_generated_debt` vs `comment_quality`**: "Restating comments" appears in both. "Docstring bloat" is ai_generated_debt; "docstring/signature divergence" is comment_quality. These are the same axis of concern (comment quality) split across a "was this AI-generated?" judgment that the model can't actually make reliably.

- **`design_coherence`** is explicitly a meta-dimension ("files accumulating issues across many dimensions") which means it's asking the model to score a score. It also overlaps with `abstraction_fitness` ("parameter lists that should be config objects") and `low_level_elegance` ("deep nesting that could be flattened").

### 2. Dimensions That Are Not Actually Subjective

Several of these are asking the LLM to do things that static analysis does better:

- **`logic_clarity`**: "Dead code paths," "always-true conditions," "identical if/else branches" — these are all mechanically detectable. An LLM reading code in a prompt window will be *less* reliable at finding these than a proper linter. You already have detectors for some of these (`unreachable_code`, `constant_return`).

- **`type_safety`**: "Return type annotations that don't cover all paths" — mypy does this. "Missing annotations on public APIs" — ruff/mypy do this. Asking an LLM to do type-checking by reading source text is asking it to do something it's bad at.

- **`dependency_health`**: "Unused dependencies," "version conflicts in lock files" — these are tool problems (pip-audit, depcheck), not LLM-judgment problems. The model can't actually read your lock file in a review prompt.

- **`initialization_coupling`**: "Import-time side effects" and "circular init dependencies" are structurally detectable. Your detector pipeline already catches circular deps via the graph module.

These dimensions dilute the review's value by spending LLM tokens on things where the model will be less accurate than your existing detectors, and they inflate the dimension count — making the scoring denominator larger while adding noise.

### 4. The Prompt Asks For Contradictory Things

The system prompt contains:

> "Score from evidence, not from a target. Do NOT anchor to 95 or any threshold"

But also:

> "IMPORT GUARD: any assessment score below 100 must include at least one finding for that same dimension with a concrete suggestion."

This creates a perverse incentive: to give an honest score of 92 on naming_quality, the model *must* manufacture a finding. If it can't think of one, it's forced to either inflate to 100 or fabricate a finding to justify the score. This is the exact anchoring-to-100 behavior the earlier instruction warned against.

### 5. Per-File Dimensions That Need Whole-Codebase Context

Several per-file dimensions can't actually be evaluated by looking at one file:

- **`cross_module_architecture`**: "Dependency direction violations repeated across multiple modules" — you can't see this from one file.
- **`convention_outlier`**: "Naming convention drift" requires knowing the codebase's conventions. Without `holistic_context`, the model has no baseline.
- **`test_strategy`**: "Critical paths with zero test coverage" — the model can't see what's tested from the production file.
- **`dependency_health`**: "Multiple libraries for same purpose" — requires seeing the whole dep graph.
- **`incomplete_migration`**: "Old and new API patterns coexisting" — needs codebase-wide view.

These should either be holistic-only or require explicit context injection that the per-file review doesn't provide.

### 6. "AI Generated Debt" Is Problematic

This dimension asks the model to identify "LLM-hallmark patterns." Three problems:

1. **Attribution is unreliable.** "Restating comments" and "defensive overengineering" are also hallmarks of junior developers, cargo-cult programming, and enterprise coding standards. Framing them as "AI generated" adds nothing to the diagnosis and creates a bias.

2. **Weight of 1.0** makes it effectively meaningless in scoring. If it's worth detecting, give it weight. If not, drop it.

3. **Overlap with `comment_quality`** (restating comments, docstring bloat) means the same issue gets reported under a more stigmatizing label.

### 7. Actionability Gradient Is Uneven

Some dimensions produce highly actionable findings ("rename `processData` to `reconcileInvoice`"). Others produce findings that are essentially architectural opinions requiring weeks of refactoring ("decomposition localizes change without surprising ripple edits"). The tool treats a 5-minute rename and a multi-sprint refactor as the same kind of output.

### Recommendations

1. **Consolidate overlapping dimensions.** Merge `contract_coherence` + `type_safety` into one. Merge the two authorization dimensions. Fold `comment_quality` into `ai_generated_debt` or vice versa. Absorb `design_coherence` into the elegance trio.

2. **Remove mechanically-detectable dimensions** from the subjective review (`logic_clarity`, parts of `type_safety`, `dependency_health`). Your detector pipeline already handles these better.

3. **Fix the import guard contradiction.** Either drop the "every sub-100 score needs a finding" rule, or accept that it forces score inflation. The current rule punishes honest scoring.

4. **Rebalance weights.** The elegance trio at 53% is unjustifiable given measurement instability. Consider flattening toward equal weights or at least bringing error_consistency, naming_quality, and the unweighted dimensions up.

5. **Scope dimensions to their review mode.** Mark which dimensions are per-file evaluable vs holistic-only, and don't include holistic dimensions in per-file reviews.

6. **Rename `ai_generated_debt`** to something pattern-focused like `ceremony_debt` or `boilerplate_noise`. The diagnosis should be about what the code does wrong, not who wrote it.

Right — I was wrong to frame it that way. The review doesn't send one LLM call per file with all 20 dimensions.

The actual flow is:

1. `desloppify review --prepare` builds a **packet** — holistic context (dep graph, coupling matrix, convention patterns, etc.) plus **investigation batches** (logical groupings of files + the dimensions relevant to that group)
