## #58 — test_coverage flags files with no testable logic

**The scoring pain is already solved.** LOC-weighted scoring means a 15-LOC barrel file or type-only file contributes `sqrt(15) ≈ 3.9` to the denominator vs `sqrt(500) ≈ 22.4` for a real module. The score impact is negligible.

**The remaining problem is noise** — hundreds of findings a user has to manually wontfix. That's real friction.

**The fix is straightforward and low-risk.** The detector already identifies barrel files at line 237 (for coverage expansion). We'd add a small pre-filter on the `scorable` set at line 110 to exclude files with no testable logic:

1. **Barrel/index files** — only contain re-exports (`export { } from` / `export * from`). Already detected via `_REEXPORT_RE`. Near-zero false positive risk.
2. **Type-only files** — `.d.ts` files in TS, or Python files where all top-level statements are class defs with no methods / type aliases / assignments to type literals. Easy to detect.
3. **Constant-only files** — files that only export `const` literals (no functions, no classes). Moderate to detect, low FP risk.

I would **not** try to auto-exclude "small React components" or "page files" — those heuristics are fuzzy and the LOC-weighting already handles the score impact. If someone's 40-LOC component has conditional rendering logic, it genuinely should be tested.

**Implementation:** Add a `_has_testable_logic(filepath, lang_name)` helper that reads the file and returns False for the three clear-cut categories above. Filter `scorable` with it. Maybe 50-80 lines of code, all in `test_coverage.py`.

**My recommendation: do it.** It's a clean, contained change that eliminates real user friction. The heuristics are conservative enough to have near-zero false positives.

---

## #50 — fragile_dict_contract

**I'd close this as out-of-scope**, or at least deprioritize it heavily. Here's why:

1. **It's a new detector category, not an enhancement.** Every other detector desloppify has detects something that's *objectively* wrong or messy — unused imports, dead exports, naming violations, missing tests. This detector flags a *code style choice* (using dicts instead of TypedDict). The code works fine; it's just fragile.

2. **The "fix" is heavy.** Every other auto-fixable detector has a straightforward remediation — delete the unused import, remove the console.log. This detector's fix is "refactor your function to use TypedDict" — that's a significant change that touches callers, type stubs, potentially serialization boundaries. It's `action_type="manual_fix"` at best.

3. **Overlap with the review system.** This is exactly the kind of thing the subjective review catches — `type_safety` and `contract_coherence` dimensions already look for "functions returning bare dict with implicit key schemas" and "should you be using a stronger type." The review system is the right tool for subjective quality judgments; the detector system is for mechanical, automatable checks.

4. **Threshold tuning is tricky.** The proposed threshold of "4+ bracket keys" sounds reasonable in the issue's examples (giant orchestrator dicts), but in practice lots of legitimate code accesses 4+ keys from a dict — config parsing, JSON response handling, DB row access. The false positive rate would be high enough to erode trust.

5. **Python-only and narrowing.** Modern Python codebases increasingly use dataclasses, Pydantic models, or TypedDict. This detector would mostly fire on legacy code that's already known to be messy.

**My recommendation: close it.** The review system's `type_safety` dimension already covers this. If someone has fragile dict contracts, `desloppify review` will catch them with much better context than a mechanical detector could.

---

## #51 monkey_patch (the remaining half)

This one's a quick win if we want to do it — the existing `mutable_state.py` already has the AST infrastructure, and monkey_patch is just "find `imported_module.attr = ...` patterns outside test files." But it's also narrow enough that I'm not sure it pulls its weight as a separate detector. It could be a sub-check inside `global_mutable_config`.

**My recommendation:** Bundle it into `mutable_state.py` as a second check if we're doing work in the area anyway, but don't prioritize it on its own.
