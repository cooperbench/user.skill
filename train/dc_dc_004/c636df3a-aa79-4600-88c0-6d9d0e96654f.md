## Reflections on the Decruftify Process

### What worked well

1. **Tier system as a workflow guide.** Having T1→T2→T3→T4 gave clear priority ordering. Clearing T1 to 100% first was satisfying and built confidence in the tooling before tackling bigger items.

2. **Detect → Fix → Scan loop.** The cycle of detect, auto-fix, rescan, verify tsc is a solid feedback loop. Score going 42→57→67 in one session is tangible progress.

3. **Dry-run + tsc verification.** Running `--dry-run` first, then fixing, then `npx tsc --noEmit` caught zero regressions across 287 files. The conservative approach (skip what you're not sure about) paid off.

### What was confusing or friction-heavy

1. **Category mismatch between detector and fixer.** The unused detector returns `category: "vars"` but the actual source patterns are wildly different — destructured props, standalone hooks, function params, dead locals. The fixer had to re-categorize at the source line level. A richer category from the detector (e.g., `destr_prop`, `standalone_hook`, `callback_param`) would make fixer logic much simpler.

2. **File path format inconsistency.** Sometimes relative (`src/...`), sometimes absolute. Had to sprinkle `Path(filepath) if Path(filepath).is_absolute() else PROJECT_ROOT / filepath` everywhere. Should standardize on one format (relative to project root).

3. **State finding IDs are fragile.** The format `detector::file::name` means if the detector changes how it reports a name, or the file moves, the finding can't be resolved. This caused the score flip-flop issue earlier (651 findings auto-resolved then reopened). The suspect-detector guard helped, but the root cause is still there.

4. **The cmd_fix function was growing uncontrollably.** Each new fixer added ~60 lines of boilerplate. Refactoring to the registry pattern was necessary but should have been the structure from the start. Lesson: build the abstraction when you add the second fixer, not the fourth.

5. **No cascading between fixers.** Removing dead exports can make symbols locally unused → next scan catches them as unused vars → need another fix round. Same with removing unused vars → may orphan imports. Only debug-logs has a cascade hook. Should we auto-chain all fixers?

### What I'd improve next

1. **Richer detector metadata.** Have `detect_unused` classify entries as `destr_prop | destr_hook_return | standalone_pure | standalone_hook | callback_param | loop_var`. This eliminates the expensive re-categorization step in the fixer.

2. **A `fix all` command** that chains fixers in dependency order: `debug-logs → unused-imports → dead-exports → unused-vars → unused-imports (cascade)`. Each step feeds the next.

3. **Better skip reporting.** Currently the fixer silently skips 432 of 675 entries. Should report *why* each was skipped (rest element, standalone hook, function param, etc.) so the user knows what remains.

4. **Fixer confidence levels.** Some fixes are 100% safe (removing `export` keyword), others are 95% safe (removing destructured prop — could break if `...rest` was added later). The fixer should tag its confidence so the user knows what to review.
