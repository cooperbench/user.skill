### Why these gaps exist — three root causes

**1. Threshold blindness.** The magic number detector uses >1000, structural uses LOC/complexity scores with high thresholds. Issues that are "medium bad" (80-150 LOC functions, numeric literals under 1000) pass through. The tool was tuned to avoid false positives at the cost of missing real problems.

**2. No architectural model.** The tool knows about files, functions, imports, and zones — but has no concept of *intended* architecture. It can't know that `detectors/` shouldn't import from `lang/*/detectors/` because that's a design rule, not a code pattern. Layer-violation detection requires declaring the architecture first.

**3. Subjective dimensions exist but aren't run by default.** The review system defines `type_safety`, `error_consistency`, `abstraction_fitness`, `contract_coherence` — but 91% of files were never reviewed. The mechanical detectors handle the easy stuff; the hard stuff is gated behind an explicit `review` command that wasn't run.

## Plan: How to close these gaps

### A. New mechanical detectors (AST-based, zero false positives)

**1. `annotation_quality` detector** — Tier 3, Code quality dimension
- AST-walk all function defs
- Flag: bare `dict` or `list` return annotations, `Callable` without signature, `-> None` missing on void functions, `detail: dict` without TypedDict
- Confidence: medium (some bare dicts are intentional)
- Action type: `manual_fix`

**2. `magic_literal` detector** — Tier 3, Code quality dimension  
- AST-walk comparisons and assignments
- Flag: numeric literals (excluding 0, 1, -1, 2) used directly in `if`/`while` conditions or as default parameter values
- Exclude: known-safe contexts (list indices, range(), enum values, test assertions)
- Confidence: low (high false-positive risk — needs tuning)
- Action type: `manual_fix`

**3. `optional_param_sprawl` detector** — Tier 3, Code quality dimension
- AST-walk function defs
- Flag: functions where >50% of params have defaults AND total params >= 5
- Confidence: medium
- Action type: `manual_fix`

**4. `layer_violation` detector** — Tier 2, new "Architecture" dimension
- Requires a config declaration: `{"layers": {"detectors": ["utils", "enums", "registry"], "lang": ["detectors", "utils", ...]}}`
- At scan time, check every import against allowed layers
- Flag: any import that crosses a layer boundary (e.g., `detectors/` importing from `lang/`)
- Confidence: high (zero ambiguity — either it crosses or it doesn't)
- Action type: `manual_fix`

### B. Enhanced existing detectors

**5. Enrich `global_mutable_config`** — currently misses reassignment without `global` keyword. Fix: also detect module-level names that appear as assignment targets inside any function in the same module (AST `Name` nodes in `Store` context matching module-level names).

**6. Lower structural thresholds for functions** — currently the `monster_function` smell is >150 LOC. Add a second tier: `long_function` at >80 LOC (complexity signal already exists at this threshold but doesn't generate a finding). Make it Tier 4 / low confidence so it doesn't overwhelm.

**7. Cross-module error handling consistency** — extend `bare_except`/`broad_except` to also scan for `sys.exit()` calls outside of CLI entry points. Flag any `sys.exit()` in non-CLI modules as a smell.

### C. Subjective review integration

**8. Default review dimensions expansion** — currently only 5 dimensions are assessed. Add `type_safety` and `contract_coherence` to the default set. These map directly to the "loose typing" and "stringly-typed API" gaps.

**9. Holistic architecture review prompt** — add a specific prompt to the holistic review that asks: "Are there import patterns that violate the intended layering? Does any shared/cross-language module depend on language-specific internals?" This covers the boundary violation case without needing a mechanical config.

**10. Auto-run file review for high-complexity files** — files with structural findings (currently 43 of them) should be auto-queued for subjective review. The mechanical detector says "this file is complex" but can't say *why* or *what to do about it*. The LLM review can.

### D. Scoring/triage improvements

**11. Wontfix decay** — 185 wontfix findings is a lot. Introduce a "wontfix review" prompt: after N scans (e.g., 10), resurface wontfix items for re-triage. Some may have become fixable after refactoring.

**12. Strict score visibility** — the health score is 95.2 but strict is 90.8. The 4.4-point gap represents wontfix/false-positive debt. Make the strict score more prominent so it's harder to ignore.
