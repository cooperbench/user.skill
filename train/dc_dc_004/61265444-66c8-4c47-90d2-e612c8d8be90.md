# `desloppify issues` — State-Backed Work Queue for Review Findings

## Context

Review findings (subjective, from `review --import`) are already in `state["findings"]` with rich detail. The current system duplicates them to `.desloppify/issues/*.md` files and tells agents `cat *.md` — stale docs, no ordering, no workflow. The agent workflow should be: **scan → discover → investigate → fix → resolve**, all backed by state.

## How it works today

1. `review --import` creates findings (detector="review", tier=3, protected from auto-resolve)
2. `_do_import` writes `.desloppify/issues/*.md` (redundant copy of state data)
3. Actions: if docs exist → top priority `cat .desloppify/issues/*.md`; if not → "run review cycle"
4. `resolve` calls `remove_issue_doc()` per finding
5. `next` calls `find_doc_for_finding()` to show doc path
6. Holistic findings (file=".") have no staleness expiry — they persist forever

### Non-file (holistic) review dimensions

These are codebase-wide findings with `file="."`, `detail.holistic=True`:

| Dimension | What it evaluates |
|-----------|-------------------|
| `cross_module_architecture` | God modules, circular deps, layer violations, hidden coupling |
| `initialization_coupling` | Import-time side effects, ordering dependencies, mutable globals |
| `convention_outlier` | Naming drift, style inconsistency across modules |
| `error_consistency` | Mixed error handling strategies (throw vs return null) |
| `abstraction_fitness` | Over/under-abstraction, wrong abstraction level |
| `dependency_health` | Dependency graph issues, transitive dependency bloat |
| `test_strategy` | Testing gaps, testing approach issues |
| `api_surface_coherence` | API consistency, interface contract issues |

They're protected from scan auto-resolve (`_IMPORT_ONLY_DETECTORS = {"review"}`), scored with `HOLISTIC_MULTIPLIER = 10.0`, and included via `path_scoped_findings` (file=="." clause).

## Design decisions

### No disk files
State is the single source of truth. No `.desloppify/issues/` directory. `desloppify issues show N` renders from state on demand.

### Investigation stored on finding
`detail.investigation` (markdown string) + `detail.investigated_at` (ISO timestamp). Optional enrichment — agents can fix directly without investigating first.

### Agent discovery: how they know to run `issues`

The existing nudge pipeline handles this — we just need to point it at `desloppify issues`:

1. **Scan's top action** (`_show_post_scan_analysis`): When review findings exist, the top action prints `Suggested next: desloppify issues — N review findings need attention`. This is what agents see immediately after scan.

2. **If they skip it**: Next scan, the action is still there. The headline still says "(N review findings pending)". The `next` command surfaces review findings at tier 3. No special "push back" mechanism needed — the existing persistence is sufficient.

3. **Reminders**: The existing `review_stale` reminder already fires after 30 days. We don't need a new "you have open review findings" reminder — the action system already surfaces this after every scan.

### Sub-agent flow: how investigation works

The `desloppify issues show N` output IS the instruction set:

- **Uninvestigated**: Output ends with "Investigate by reading the files above, then save analysis: `desloppify issues update 1 --file analysis.md`"
- **Investigated**: Output ends with "Ready to fix. When done: `desloppify resolve fixed \"<id>\"`"

An orchestrating agent (e.g., Claude Code) would:
1. Run `desloppify issues` → see the list
2. For each uninvestigated issue, spawn a sub-agent with: "Run `desloppify issues show 1`, read the related files, write detailed analysis to analysis.md, then run `desloppify issues update 1 --file analysis.md`"
3. Sub-agent does the investigation, writes back to state via the update command
4. For each investigated issue, spawn a sub-agent with: "Run `desloppify issues show 1`, fix the issue, then resolve"

### Resolve: same mechanism as everything else
`desloppify resolve fixed "<id>"` — the standard resolve command. Finding status → "fixed", disappears from `desloppify issues`. After resolve, the remaining count is printed: "N review findings remaining — run `desloppify issues`".

### Holistic finding staleness

**Problem**: Holistic findings (file=".") represent codebase-wide patterns. The codebase evolves — after 30 days these findings may no longer be relevant. Per-file findings are tied to specific code and shouldn't auto-expire.

**Mechanism**: Add `_expire_stale_holistic(state, max_age_days)` called during scan:
- Iterates open findings where `detector == "review"` and `detail.holistic == True`
- If `last_seen` is older than `max_age_days`, sets status to `"auto_resolved"` with note `"holistic review expired — re-run review to re-evaluate"`
- Default: 30 days, configurable via `state["config"]["holistic_max_age_days"]`

Per-file review findings (file != ".") are NOT expired. They persist until manually resolved.

This runs during `cmd_scan` after `merge_scan` (alongside the existing `_recompute_stats` call), not inside `merge_scan` itself (keeps merge_scan clean).
