## Phase 1: Bug Fixes (P0)

### 1a. Stable `issues` numbering — `desloppify/issues.py`
**Problem**: `_finding_weight()` returns `(weight, weight)` — identical sort keys for same-confidence findings. Dict iteration order makes numbering unstable between calls, so `issues show 8` may return a different finding than #8 in the `issues` list.

**Fix**:
- `_finding_weight()` → return `(weight, weight, finding_id)` as 3-tuple with stable tiebreaker
- `list_open_review_findings()` → sort by `(-weight, finding_id)` for deterministic order
- Update callers in `issues_cmd.py:49` (`weight, _ = ...` → `weight, _, _ = ...`) and `issues.py:118`

### 1b. State path mismatch → "No review findings" — `desloppify/commands/_helpers.py`
**Problem**: `_state_path(args)` returns `None` when `--lang` is omitted, falling through to generic `state.json`. But `review --import` writes to `state-python.json` (because `--lang` was specified). Subsequent `issues` without `--lang` loads the wrong file.

**Fix**: Add auto-detection fallback in `_state_path()` (lines 34-43), mirroring `_resolve_lang()`:
```python
lang_name = getattr(args, "lang", None)
if not lang_name:
    from ..lang import auto_detect_lang
    lang_name = auto_detect_lang(PROJECT_ROOT)
if lang_name:
    return PROJECT_ROOT / ".desloppify" / f"state-{lang_name}.json"
```

### 1c. Count mismatches — `desloppify/commands/review_cmd.py`
**Problem**: Import says "+5 new findings" but `issues` shows 13 (includes prior imports). The scope difference is not communicated.

**Fix**: Change line 162 from `"{N} review finding(s) open"` to `"{N} review finding(s) open total"`.

**1. `next` command ignores scan path (Agent 3)**

**2. Chronic reopener cross-scan stale data (Agent 3)**

Same root cause as #1. The chronic count comes from `merge_scan()` which correctly detects chronics, but when the agent scanned a *different* path, stale findings from a prior scan (from Agent 1's tmp directory) were counted as chronic. The `show --chronic` command then filtered current state correctly but found nothing matching the *current* scan path.

**Fix**: Part of #1 — once path scoping is applied consistently, chronics from foreign paths won't appear.

### Tier 2: Confusing UX

**3. Unassessed dimensions show 0% (Agents 3, 5)**

Root cause: `scoring.py:217-251` creates assessment dimensions unconditionally. When `review_assessments` has no entry for a dimension, `score = 0.0` → displays as 0%. Meanwhile mechanical dimensions with 0 potential are *omitted* (`continue` on line 203). The asymmetry creates "0% with 0 issues" which reads as broken.

**Fix options** (ranked):
- **A (Recommended)**: Hide unassessed dimensions entirely — only show them after a review fills in `review_assessments[dim_name]`. This matches mechanical dimension behavior (omitted when no data).
- **B**: Show "—" or "Not assessed" instead of "0%" for dimensions with no assessment data.

**4. No visual distinction for assessment vs mechanical dimensions (Agents 3, 5)**

The status table renders both identically. Users can't tell which dimensions need code fixes vs. re-review.

**Fix**: Add a section header or suffix:
```
  ── Mechanical Dimensions ──────────────────────
  Import hygiene     200 checks   94%  92%  ████████▒▒  T1
  ...
  ── Review Dimensions ──────────────────────────
  Naming quality      10 checks   80%  80%  ████████░░  T4
```

**5. "10 checks" is meaningless to users (Agent 5)**

The `ASSESSMENT_CHECKS = 10` constant is a dampening factor for weighted scoring, not a real check count. Displaying it confuses users who expect it to mean "10 things were checked."

**Fix**: Either hide the check count for assessment dimensions, or display the actual number of files reviewed instead.

### Tier 3: Polish

**6. Audit coverage ↔ review findings relationship (Agent 5)**

"Audit coverage" measures what % of files have been reviewed. The "Review: N findings open" line in status shows review-discovered issues. These are related but not connected in the UI.

**Fix**: Add a parenthetical to the Audit coverage row or a footnote: `"Audit coverage tracks % of files reviewed; review findings track issues found."`

**7. "missing required fields" parent label (Agent 4)**

When review import skips a finding due to invalid dimension name, the parent error says "Skipped N (missing required fields)" but the child says "invalid dimension: X". The parent label is misleading.

**Fix**: Change parent label from "missing required fields" to "validation errors" or split the count: "Skipped N (M missing fields, K invalid values)".
