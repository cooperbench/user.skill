# Fix #38: Framework File & tsconfig Alias False Positives

## Context

GitHub issue #38: `.svelte` (and `.vue`, `.astro`) files are invisible to the import graph, causing:
1. **Dead-export false positives** — exports consumed only by framework files appear unused
2. **Orphaned-file false positives** — files imported only by framework files appear orphaned
3. **Fixer damage** — `fix dead-exports` removes live exports, causing build breakage (247 errors)

Second related bug from @wynander: tsconfig `paths` aliases beyond the hardcoded `@/` → `src/` aren't resolved, causing the same false positives for projects using custom aliases.

**Key insight**: These are NOT new detectors. The existing detectors work correctly — they just need a complete picture of what's importing what. The fix belongs at the **import graph** and **reference search** layers, and should be framework-agnostic.

---

## Root Cause Analysis

There are **two independent layers** that need fixing, because the dep graph and dead-export detector use different code paths:

| Detector | How it finds references | What needs fixing |
|----------|------------------------|-------------------|
| Orphaned files | Dep graph `importer_count` | `build_dep_graph()` needs framework file edges + alias resolution |
| Dead exports | `grep_files_containing()` on `.ts/.tsx` only | `_build_reference_index()` needs to also search framework files |
| Coupling/cycles | Dep graph | Gets fixed when dep graph is fixed |
| Test coverage | Dep graph | Gets fixed when dep graph is fixed |

### Step 1: tsconfig paths parser — `deps.py`

Add `_load_tsconfig_paths()` to dynamically resolve path aliases instead of hardcoding `@/` → `src/`.

```python
_tsconfig_cache: dict[str, dict[str, str]] = {}

def _load_tsconfig_paths(project_root: Path) -> dict[str, str]:
    """Parse tsconfig.json compilerOptions.paths into {prefix: directory}.

    Returns e.g. {"@/": "src/", "@components/": "src/components/"}.
    Falls back to {"@/": "src/"} if no tsconfig found.
    """
```

**Logic:**
1. Check cache (keyed on `str(project_root)`)
2. Try `tsconfig.json` at project_root, then `tsconfig.app.json`, then `jsconfig.json`
3. If `extends` field present, load parent config and merge (child wins)
4. Extract `compilerOptions.paths` — convert `"@/*": ["./src/*"]` → `{"@/": "src/"}`
5. Handle `baseUrl` — prepend to path values if present (default `"."`)
6. If no config or no paths field: return `{"@/": "src/"}` for backwards compat

**Edge cases handled:**
- `tsconfig.json` with `references` (like Reigh) — still has `compilerOptions.paths` in root
- Multiple path targets `"@/*": ["./src/*", "./lib/*"]` — use first (matches TS behavior)
- `baseUrl: "."` vs `baseUrl: "./src"` — compose with paths correctly
- `extends: "@tsconfig/node20/tsconfig.json"` — skip if not a local file
- Malformed/missing JSON — catch `json.JSONDecodeError`/`OSError`, return fallback
- No tsconfig at all — graceful fallback, existing `@/` behavior preserved

### Step 2: Refactor alias resolution — `deps.py`

Add `_resolve_alias()` helper, replace hardcoded `@/` block in `build_dep_graph()`:

```python
def _resolve_alias(module_path: str, tsconfig_paths: dict[str, str],
                   project_root: Path) -> Path | None:
    """Resolve a tsconfig path alias to absolute path, or None if not an alias."""
    for prefix, target_dir in tsconfig_paths.items():
        if module_path.startswith(prefix):
            relative = module_path[len(prefix):]
            return (project_root / target_dir / relative).resolve()
    return None
```

In `build_dep_graph()`:
- Load paths once: `paths = _load_tsconfig_paths(PROJECT_ROOT)`
- Replace the `elif module_path.startswith("@/"):` block (lines 44-54) with:
  ```python
  else:
      target = _resolve_alias(module_path, paths, PROJECT_ROOT)
      if target:
          for ext in ["", ".ts", ".tsx", "/index.ts", "/index.tsx"]:
              ...
  ```

Update `ts_alias_resolver()` to use dynamic paths:
```python
def ts_alias_resolver(target: str) -> str:
    paths = _load_tsconfig_paths(PROJECT_ROOT)
    for prefix, target_dir in paths.items():
        if target.startswith(prefix):
            return target_dir + target[len(prefix):]
    return target
```

### Step 3: Framework file imports in dep graph — `deps.py`

**Approach**: Grep entire framework files for the same `from\s+['"]` import pattern used for `.ts/.tsx`. No script block extraction needed — false matches from HTML attributes/templates won't resolve to real `.ts/.tsx` files on disk, so they're silently dropped by the extension-try logic. This is simpler and more robust than parsing `<script>` blocks.

```python
_FRAMEWORK_EXTENSIONS = (".svelte", ".vue", ".astro")
```

Add to `build_dep_graph()` after the existing `.ts/.tsx` loop:

```python
# Also extract import edges FROM framework files (they import .ts/.tsx modules)
from ....utils import find_source_files
fw_files = find_source_files(path, list(_FRAMEWORK_EXTENSIONS))
if fw_files:
    fw_hits = grep_files(r"from\s+['\"]", fw_files)
    for filepath, _lineno, content in fw_hits:
        source_resolved = resolve_path(filepath)
        graph[source_resolved]  # ensure entry
        m = module_re.search(content)
        if not m:
            continue
        module_path = m.group(1)
        # Same resolution logic as .ts/.tsx (relative + alias)
        ...  # reuse _resolve_module() helper
```

**Why whole-file grep is safe**: The pattern `from\s+['"]([^'"]+)['"]` is specific to ES import syntax. If a template happens to contain `from "./something"`, the resolved path either:
- Doesn't exist → silently skipped (no harm)
- Does exist → extra importer edge in the **conservative direction** (prevents false orphan/dead-export)

**Refactor**: Extract the import-resolution logic from `build_dep_graph()` into a reusable `_resolve_module()` helper to avoid duplicating the relative/alias/extension-try code for framework files.

### Step 4: Expand dead-export reference search — `exports.py`

Update `_build_reference_index()` to also search framework files:

```python
def _build_reference_index(search_path: Path, names: set[str]) -> dict[str, set[str]]:
    if not names:
        return {}
    from ....utils import find_ts_files, find_source_files
    ts_files = find_ts_files(search_path)
    # Also search framework files that may use these exports
    from .deps import _FRAMEWORK_EXTENSIONS
    fw_files = find_source_files(search_path, list(_FRAMEWORK_EXTENSIONS))
    all_files = ts_files + fw_files
    raw = grep_files_containing(names, all_files, word_boundary=True)
    return {name: {resolve_path(f) for f in files} for name, files in raw.items()}
```

This is the key fix for **dead-export false positives**. The dep graph fix only helps orphaned files — dead exports use their own independent grep-based reference search.

# Subjective Analysis: What's Stopping Desloppify From Being Beautiful

Seven deep reviews, ~7,700 lines of analysis. Here's the synthesis.

---

## The Big Picture

The architecture is genuinely good. The three-layer separation (generic detectors → shared base → language plugins) holds perfectly — `detectors/` never imports from `lang/`. The zone system, the scoring model, the scan pipeline data flow — these are clean, linear, well-reasoned. The progress bars after a scan are emotionally resonant. The strict/lenient score split is a novel concept no other tool has.

But there are five systemic issues holding it back from elegance, and they compound each other.

---

## 1. The Dict Soup Problem

**This is the #1 structural weakness.**

The entire application runs on untyped dictionaries. Findings are dicts (13 string keys, accessed by name across 30+ files). State is a dict (implicit schema, no validation). Graph entries are dicts. Smell rules are dicts. The narrative output is a dict. Potentials are dicts.

```python
# This is the most-accessed data structure in the codebase.
# No TypedDict, no dataclass, no schema.
return {"id": fid, "detector": detector, "file": rfile, "tier": tier,
        "confidence": confidence, "summary": summary, "detail": detail or {},
        "status": "open", "note": None, "first_seen": now, "last_seen": now,
        "resolved_at": None, "reopen_count": 0}
```

There are 134 occurrences of `state.get()` or `state[...]` across 16 files. A typo in any key — `f["stauts"]` — would fail silently via `.get()` or crash at runtime. The `SmellRule` dataclass exists in `detectors/base.py` and is used by *zero* files. The `_compute_reminders` function is annotated as returning `list[dict]` but actually returns `tuple[list, dict]`. Nobody caught it because nothing checks.

Ironically, the codebase already has good dataclasses: `FunctionInfo`, `ComplexitySignal`, `GodRule`, `DetectorPhase`, `FixerConfig`, `ZoneRule`, `Dimension`. But these are only used at the configuration level. The runtime data — the stuff that flows through every function — is all dicts.

---

## 2. Strings As The Type System

Six different taxonomies live as bare string literals with no enforcement:

| Taxonomy | Example values | Occurrences | What breaks on typo |
|----------|---------------|-------------|-------------------|
| Confidence | `"high"`, `"medium"`, `"low"` | 111+ across 15 files | Scoring weight lookup (already happened — `"info"` was used, had no weight) |
| Status | `"open"`, `"fixed"`, `"wontfix"` | 59+ across 11 files | Finding resolution logic |
| Detector names | `"unused"`, `"smells"`, `"coupling"` | 5+ registries that must stay in sync | Silent scoring exclusion |
| Tier | `1`, `2`, `3`, `4` | Dozens of `make_finding` calls | Scoring weight, display, narrative |
| Smell IDs | `"eval_exec"`, `"async_no_await"` | Fixer lookups, narrative tools | Silent empty results |
| Action types | `"auto_fix"`, `"reorganize"` | Narrative lane computation | Silent miscategorization |

The `Zone` enum in `zones.py` proves the team knows how to use enums. It is the only one in the entire codebase.

Adding a new detector requires touching **at least 9 files** — `DETECTOR_TOOLS` in narrative.py, `DIMENSIONS` in scoring.py, `DETECTOR_NAMES` in cli.py, `DET_ORDER` in scan.py, `ZONE_POLICIES` in zones.py, the lang plugin's phases list, the detect commands registry, and the phase runner itself. Forgetting any of these is a silent failure. There is no checklist and no compile-time enforcement.

---

## 3. The Duplication Between Language Plugins

The Python and TypeScript plugins duplicate substantial code:

- **`_find_external_test_files()`** — character-for-character identical (23 lines), differing only in `"__tests__"` directory
- **`_phase_test_coverage`** — nearly identical implementations (28 lines each)
- **The signature variance block in `_phase_smells`** — 15 lines of identical `make_finding` boilerplate
- **The `prev_ch != "\\"` brace-tracking pattern** — copy-pasted 14 times across `_smell_helpers.py`, `react.py`, and the fixer files, each copy containing the same bug

The base module (`lang/base.py`) was created to share helpers and it does share some (`make_smell_findings`, `make_unused_findings`). But the most obvious candidates for sharing were left as copies. And the `commands_base.py` factory pattern — which correctly deduplicates detect command wrappers — proves the team knows how to extract shared code. They just didn't finish.

Meanwhile, the dual fixer registry (`LangConfig.fixers` vs the hardcoded `_get_fixer()` dict in `fix_cmd.py`) means the same fixer has two definitions in two places, with the fallback registry hardcoding TypeScript imports that bypass the language-agnostic plugin system.

---

## 4. Global Mutable State & The Testability Tax

Every module that imports from `utils.py` gets a `PROJECT_ROOT` frozen at import time from `Path.cwd()`. This appears in 30+ files and makes desloppify un-embeddable as a library. Every test must monkeypatch it.

The full catalog:

| Global | Impact |
|--------|--------|
| `PROJECT_ROOT` (utils.py:10) | 30+ files import it. Frozen at import time. Cannot run two scans on different roots in one process. |
| `SRC_PATH` (utils.py:12) | Derived from PROJECT_ROOT. Same problem. |
| `_extra_exclusions` (utils.py:24) | Mutable tuple. Other modules must use the `_utils_mod._extra_exclusions` workaround pattern to see updates. |
| `_zone_map` on LangConfig | Set during scan, read by later phases. Creates invisible phase ordering dependencies. |
| `_dep_graph` on LangConfig | Same — `_phase_test_coverage` must run after `_phase_coupling` or it silently rebuilds the graph. |
| `_tsconfig_cache` (deps.py:20) | Benign within a scan, but never invalidated across scans in the same process. |

The fix is mechanical but large: a `ScanConfig` context object threaded through function parameters. It would touch 30+ files and ~200 call sites. Not complex, but high-effort.

---

## 5. Performance: Every File Read 15 Times

There is **zero caching of file contents** anywhere. Each file is read from disk 14–20 times during a TypeScript scan:

- `grep_files()` in logs phase (2x), exports phase (2x), dep graph (1x), dynamic imports (2x)
- Individual detector loops in smells, react, concerns, props, patterns, extractors, complexity, large files — each reads every file independently
- Post-scan `_collect_codebase_metrics` re-reads all files for LOC

For a 1000-file codebase: **~15,000 file reads** per scan. A simple `dict` cache would reduce this to ~1,000.

The second bottleneck: `npx tsc --noEmit` (10–30 seconds) blocks all other phases. Since phases 1–5 and 8–9 are completely independent, overlapping `tsc` with CPU-bound phases via a background thread would save 10–30 seconds of wall-clock time for free.

The `_count_importers` function in `deprecated.py` is the worst per-call offender: it scans ALL files per deprecated symbol. With 50 symbols and 1000 files = 50,000 file reads for one sub-detector. The exports detector solved this exact problem with batched grep (`grep_files_containing`).

---

## The Regex Fragility Layer

Not a systemic issue, but worth documenting. The codebase has ~85 regex patterns at three risk levels:

**Actually dangerous (could corrupt auto-fixes):** The `prev_ch != "\\"` brace tracker in fixer code (`find_balanced_end`, `extract_body_between_braces`). A string ending with `\\` would miscalculate brace depth, causing the fixer to delete wrong lines. This is 14 copies of the same bug.

**Causes false negatives:** Python `mutable_default` smell misses multi-line function signatures (no `re.DOTALL`). Component prop extraction `[^}]*` fails on nested destructuring. TS function regex `[^;{]*?=>` breaks on type annotations containing braces.

**Causes false positives:** `detect_mixed_concerns` runs 5 patterns on raw content with no string/comment awareness. `detect_complexity` signal counting includes hooks in comments. `detect_context_nesting` counts provider tags inside comments. Template literals containing code-like patterns fool multiple detectors.

The string-awareness system has three tiers: full filtering (TS smell regex checks), comment-stripping only (some multi-line helpers), and nothing (concerns, complexity, react, dep graph). The "nothing" tier is where most false positives come from.

---

## The Meta-Irony

The tool that computes a health score has:

- **8 files** exceeding its own large-file threshold (`narrative.py` at 1,105 lines = 3.7x the Python threshold)
- **228 deferred imports** working around circular dependencies — the exact pattern its `deferred_import` detector flags
- **14 copies** of the same buggy brace-tracking code — the exact pattern its `dupes` detector catches
- **`get_area()`** in utils.py with hardcoded `src/tools/`, `src/shared/`, `src/pages/` paths from the original target project
- **`filepath.split("/")`** in 3 files — flagged by its own `hardcoded_path_sep` detector
- An **untested move-command rollback path** — the most dangerous operation in the tool has zero tests for its safety net

The MEMORY.md file explicitly catalogs the `prev_ch` bug, the global state pattern, the deferred imports. The codebase is honest about what's hard. It's physical evidence that code quality is a gradient, not a binary.

---

## What Would Make It Beautiful

In order of leverage:

1. **Type the runtime data.** `Finding` TypedDict (or dataclass). `State` TypedDict. `GraphEntry` TypedDict. `Confidence` enum, `Tier` IntEnum, `DetectorName` enum. This eliminates an entire class of bugs and gives IDE autocomplete everywhere.

2. **Extract shared phase code into `lang/base.py`.** `_find_external_test_files`, `_phase_test_coverage`, the signature variance block, and the common phase runner boilerplate. A third language plugin should require ~50 lines of config data and phase wiring, not 350 lines of copy-paste.

3. **Add a file content cache.** One `dict[str, str]` cleared per scan. Single highest-leverage performance optimization — halves scan time for large codebases.

4. **Extract `_track_braces()` into one shared function.** Fixes the `prev_ch` bug in one place instead of 14. Eliminates the worst duplication in the codebase.

5. **Split `narrative.py`.** Strategy/lanes/union-find → `strategy.py` (277 lines). DETECTOR_TOOLS → `scoring.py` or a `registry.py`. Reminders → standalone module. The core `compute_narrative()` stays.

7. **Lead with the coaching.** Move the headline *above* the progress bars in scan output. Show the strategy to everyone. Replace `"3x eval_exec"` with `"3 eval/exec calls — security risk"`. The narrative engine is the differentiator — right now it's an afterthought buried at the bottom of the output.
