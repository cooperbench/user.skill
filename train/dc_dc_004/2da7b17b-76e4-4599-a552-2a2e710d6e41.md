## Migration 1: jscpd → replaces `boilerplate_duplication.py`

### What changes

| Action | File |

| NEW | `desloppify/engine/detectors/jscpd_adapter.py` |
| MODIFY | `desloppify/engine/phases/shared_phases.py` |
| DELETE | `desloppify/engine/detectors/boilerplate_duplication.py` |
| ADD tests | `desloppify/tests/detectors/test_external_adapters.py` (`TestJscpdAdapter`, ~8 tests) |
| DELETE tests | `desloppify/tests/detectors/test_boilerplate_duplication.py` |

### Why jscpd is better

Custom `boilerplate_duplication.py` uses SHA1 of line-normalized 4-line sliding windows, requiring 3+ distinct files. It normalizes strings/numbers to `"STR"`/`"NUM"` — a crude tokenizer. jscpd uses proper tokenization per language, supports type-2 clones (renamed identifiers), and is battle-tested across thousands of codebases.

**NOTE:** `dupes.py` (function-level duplicate detection) is NOT replaced — jscpd is file-level and doesn't give function names, LOC context, or clustering by function signature. Keep `dupes.py`.

### jscpd invocation

```
npx jscpd <path> \
  --reporters json \
  --output <tmpdir> \
  --min-lines 4 \
  --min-tokens 50 \
  --ignore "**/node_modules/**,**/.git/**,**/__pycache__/**" \
  --silent
```

Output written to `<tmpdir>/jscpd-report.json`. Use `tempfile.TemporaryDirectory()`, clean up after parsing.

Graceful degradation: `FileNotFoundError` → `None`. `TimeoutExpired` → `None`. Bad JSON → `None`. Empty output → `[]`.

### Output format mapping

jscpd produces pairs (`firstFile`, `secondFile`) with a `fragment` string. We cluster pairs into multi-file groups by fragment hash (sha1 of `fragment.strip()[:200]`[:16]). This preserves the same output shape as `boilerplate_duplication.py`:

```python
{
    "id": str,            # sha1(fragment)[:16]
    "distinct_files": int,
    "window_size": int,   # dup["lines"]
    "locations": [{"file": str, "line": int}, ...],
    "sample": [str, ...], # fragment.splitlines()[:4]
}
```

Because the output shape is identical, `phase_boilerplate_duplication()` in `shared_phases.py` needs only one change: call `detect_with_jscpd()` instead of `detect_boilerplate_duplication()`. If result is `None`, return `[], {}`.

### ID stability note

Finding names (`entry["id"]`) will change from SHA1-of-normalized-content to SHA1-of-raw-fragment. Any existing wontfixed `boilerplate_duplication` findings will be orphaned. These are uncommon, and the improvement justifies the reset.

## Migration 3: import-linter → replaces `layer_violation.py`

### Why the current detector has no general value

`layer_violation.py` has hardcoded rules referencing `desloppify/engine/detectors/`, `desloppify/intelligence/narrative/` etc. — paths that only exist in desloppify's own codebase. When desloppify scans any other Python project, these rules never fire. The detector effectively only works for desloppify self-scans.

### import-linter approach

[import-linter](https://import-linter.readthedocs.io) reads `.importlinter` (or `setup.cfg [importlinter]` section) to enforce project-defined architectural contracts. By adopting it:

- **desloppify self-scan**: Add `.importlinter` config encoding the existing rules → detection continues
- **Other projects with `.importlinter`**: desloppify picks up their architectural violations automatically → new value
- **Other projects without `.importlinter`**: No layer violation detection (same as today, since hardcoded rules don't apply)

### import-linter output format

`lint-imports` does not have a native JSON reporter. Parse its text output. Example output:
```
Broken contract 'Engine cannot import Languages':
    desloppify/engine/detectors/coupling.py -> desloppify/languages/typescript/__init__.py
```

Parsing strategy: regex on `->` lines. Each line = one violation. Severity: always "high".

The three tools in this migration illustrate the spectrum well:

## Why most detectors are language-native

The things desloppify detects — mutable defaults, broad exceptions, layer violations, unused exports — are **language-specific concepts**. Python has `except:`, TypeScript has `as any`, Go has neither. You can't write a single tool that handles both without essentially writing two tools and gluing them together (which is what SonarQube and CodeClimate do at enormous complexity cost).

This is also why the codebase separates them architecturally:
- `engine/detectors/` — genuinely cross-language (security, test coverage, jscpd)
- `languages/python/detectors/` — Python linters (ruff, bandit, import-linter)
- `languages/typescript/detectors/` — TS-specific tools (Knip, tsc)

## The cross-language candidates

The few tools that do work across languages tend to cover **structural** rather than **semantic** properties:

- **jscpd** — structure of token sequences (language-agnostic)
- **semgrep** — pattern matching (but rules are still written per-language)
- **gitleaks / trufflehog** — secret detection (regex on text, no AST needed)
- **lizard** — cyclomatic complexity (counts decision points, works on any C-like syntax)

Notably, desloppify already uses a cross-language approach for security (the `detectors/security.py` core runs regex on file text regardless of language) and test coverage (import graph analysis with per-language adapters for the graph-building step).

## Practical implication

If you added a third language (e.g., Go), jscpd would work out of the box. Ruff and import-linter would need Go equivalents (`staticcheck`, `go vet`) with their own thin adapters — the adapter *pattern* transfers, but not the specific tools.

Desloppify is the same idea but smaller — Python is the plumbing language, and each `languages/` plugin is still Python that happens to understand another language's text format.

## The hard part is always the same two files

Regardless of language, these can't be scaffolded:

**`detectors/deps.py`** — you must correctly parse that language's import syntax into a dependency graph. Python uses AST; TypeScript shells out to tsc; Go uses `import "pkg/path"`. Getting this wrong breaks orphaned-file detection, cycle detection, and coupling analysis for everything downstream.

**`extractors.py`** — function body extraction for duplicate detection. Every language has different function syntax, scoping rules, and block structure.

These two files are genuinely language-expert work, not boilerplate.

## The value curve flattens fast

| Language tier | Examples | Depth achievable | Effort |
|---|---|---|---|
| Tier 1 (6–8 langs) | Go, Rust, Java, C#, Ruby, Swift | Deep — mature tools to wrap, concepts map cleanly | 1–2 weeks each |
| Tier 2 (10–15 langs) | Kotlin, Dart, Scala, PHP, Elixir | Medium — deps parsing is the main work | 1 week each |
| Tier 3 (15+ langs) | Haskell, Clojure, Fortran, Lua, Zig | Shallow — structural concepts don't map (no OO, different module systems) | Same effort, much less value |

By language 20 you're mostly just wrapping jscpd and an external linter with a thin adapter — which you could accomplish with a generic "shell out to tool" adapter without a full plugin.

## The maintenance problem is the real constraint

37 plugins × the number of detectors per plugin = a combinatorial surface that's hard to keep consistent. Right now desloppify has deep knowledge of Python and TypeScript. Adding Go support properly means someone needs to:
- Know what "good Go" looks like
- Know the Go tooling ecosystem (`staticcheck`, `golangci-lint`, etc.)
- Write tests that actually catch real bugs in real Go code
- Keep up with language changes

Without that domain knowledge per language, the plugins become shallow facades that flag superficial issues and miss the architectural problems desloppify is actually good at.

## Realistic path

Rather than 37 custom plugins, the higher-leverage approach might be a **generic adapter** — a `plugin_external.py` that lets any project drop in a config file pointing desloppify at their existing linter output. The custom Python and TypeScript plugins stay deep; everything else gets "good enough" via adapters to whatever native tools the project already uses. That's closer to what import-linter is already doing for layer violations.

No branching. The new plugins produce the exact same `LangConfig` type with the same interface. The pipeline calls `lang.phases`, `lang.file_finder`, `lang.build_dep_graph` — it doesn't know or care how the config was built. A Go plugin that has 2 phases (golangci-lint + go vet) is identical in structure to a Python plugin that has 8 phases; it just has fewer of them.

The only pipeline change is a 3-line addition to `get_lang()` in resolution.py: if the registry holds a pre-built `LangConfig` instance (generic plugin), return it directly instead of calling `cls()` on it. That's the only difference in control flow, and it's in the lookup, not in the scan/phase execution.

The `integration_depth` field is cosmetic — only read by the new `langs` command for display. Zero other code touches it.

So from a user perspective: `desloppify --lang go scan --path .` works exactly like `desloppify --lang python scan --path .`. Fewer findings (fewer phases), but no difference in how the tool behaves.
