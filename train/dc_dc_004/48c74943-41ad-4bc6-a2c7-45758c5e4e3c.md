## Current Architecture

**Drag flow:** `handleMouseDown` → `handleMouseMove` (tracks mouse) → `calculateDragPositions` (computes new frame map) → `handleMouseUp` (persists via `setFramePositions`)

**Core constraint function:** `shrinkOversizedGaps` in `timeline-utils.ts:90` processes all items left-to-right:
1. First item forced to frame 0
2. Each gap clamped: min 5, max 81, quantized to 4N+1

This is called at the end of every `applyFluidTimeline` call, so constraints are enforced on every drag frame (preview) and on drop (final).

**Current single-item drag** (`calculateDragPositions` line 120): Sets the dragged item to the target frame, resolves same-frame conflicts, then calls `applyFluidTimeline` which limits movement to 50 frames/step and runs `shrinkOversizedGaps`. Items only move as a side-effect of constraint enforcement — there's no intentional "push neighbors" behavior.

---

## Proposed "Push" Feature Design

### Semantics

- **Command + drag** ("push right"): The dragged item moves to the target frame. All items originally to the **right** of the dragged item shift by the same delta, preserving their relative spacing. The gap between the dragged item and its left neighbor changes freely (subject to constraints).

- **Option + drag** ("push left"): The dragged item moves to the target frame. All items originally to the **left** of the dragged item shift by the same delta. The gap between the dragged item and its right neighbor changes freely.

**Concrete example** — timeline: `A(0) B(20) C(40) D(60) E(80)`, drag C right by +15:

| Mode | A | B | C | D | E |
|---|---|---|---|---|---|
| Normal (no modifier) | 0 | 20 | 55 | 60 | 80 |
| Command (push right) | 0 | 20 | 55 | 75 | 95 |
| Option (push left) | 15 | 35 | 55 | 60 | 80 |

Then `shrinkOversizedGaps` enforces constraints — e.g. Option would force A back to 0, giving `A(0) B(20) C(40) D(60) E(80)` ... which is actually the same. So pushing left while dragging right has no real effect (A hits the frame-0 wall). The feature is most useful for directional matching: Command while dragging right opens space; Option while dragging left compresses space.

### Key Implementation Points

**1. Modifier key threading**

`handleMouseMove` receives a native `MouseEvent` which has `e.metaKey` (Command) and `e.altKey` (Option). Add a ref:
```
modifierKeysRef = useRef({ metaKey: false, altKey: false })
```
Update it in `handleMouseMove`. Read it in `calculateDragPositions`.

**2. New push calculation** (in `timeline-utils.ts`)

A new function like `applyFluidTimelinePush(positions, draggedId, targetFrame, pushMode: 'right' | 'left', ...)`:
- Calculate delta = limitedTargetFrame - originalPos of dragged item
- Set dragged item to new position
- If `'right'`: for each item with `originalPos > draggedOriginalPos`, add delta to their position
- If `'left'`: for each item with `originalPos < draggedOriginalPos`, add delta
- Call `shrinkOversizedGaps` — this handles all constraint enforcement naturally

**3. The constraints "just work"**

- `shrinkOversizedGaps` already forces first-item-at-0, so push-left can never push items below 0
- Max gap of 81 caps any over-stretched gaps from push-right
- Min gap of 5 prevents items from collapsing on top of each other
- The 50-frame-per-step movement limit in `applyFluidTimeline` already exists and would apply to the delta

**4. Determining the push group**

Use `dragState.originalFramePos` (captured at mousedown) to decide which items are "to the right" or "to the left". This stays stable throughout the drag — the push group doesn't change as you move.

**5. Live preview**

`calculateDragPreview()` already calls `calculateDragPositions` on every frame, so the push effect would be visible in real-time during drag, not just on drop.

**6. Interaction with trailing endpoint**

The trailing endpoint (`__trailing_endpoint`) is excluded from `shrinkOversizedGaps` and managed separately. For push-right, it should probably also shift by delta. For push-left, it should stay put.

### Key Observation

`applyFluidTimeline` (line 148) is effectively just `shrinkOversizedGaps` in the current drag path. This means the push feature just needs to **set more items in the map before the existing pipeline runs**. No new functions in `timeline-utils.ts` needed.

### Exact Integration

`calculateDragPositions` (line 120) already branches on multi-select at line 132-137. Push becomes a parallel branch at the same level:

```
calculateDragPositions(clientX, isPreview):
  targetFrame = calculateTargetFrame(...)
  
  if (multiSelect)       → existing applyFluidTimelineMulti path
  if (metaKey || altKey)  → NEW push path
  else                    → existing single-item path (conflict resolution + applyFluidTimeline)
```

The push path itself is just a map mutation before the existing constraint call:

```
const delta = finalPosition - dragState.originalFramePos
const newPositions = new Map(framePositions)

newPositions.set(dragState.activeId, finalPosition)

for (const [id, pos] of framePositions):
  if id === activeId or id === TRAILING_ENDPOINT_KEY: skip
  if metaKey  and pos > dragState.originalFramePos:  newPositions.set(id, pos + delta)
  if altKey   and pos < dragState.originalFramePos:  newPositions.set(id, pos + delta)

return applyFluidTimeline(newPositions, activeId, finalPosition, ..., isPreview)
                          ↓
                    shrinkOversizedGaps handles everything:
                      • first item → 0 (stops push-left from going negative)
                      • gaps > 81 → capped (stops push-right from over-stretching)

```

No conflict resolution needed in the push path — relative order is preserved since all items on one side shift by the same delta.

And what will happen when they press both keys at the same time?

> AGENT

Everything shifts by the same delta — including the dragged item. So the map becomes something like `A(15) B(35) C(55) D(75) E(95)`. Then `shrinkOversizedGaps` forces the first item back to 0 and rebuilds left-to-right preserving gaps... which puts everything exactly where it started. It's a no-op.

Benign, but potentially confusing if someone does it accidentally. Three options:

1. **Let it be a no-op** — simplest, no extra code, and it's self-evident ("nothing happened, I'll try one key")
2. **Command takes priority** — `if (metaKey) ... else if (altKey)` ordering means Command wins when both are held. Probably the most intuitive since Command is the "primary" modifier on Mac.
3. **Both-keys = move entire timeline** — skip the `shrinkOversizedGaps` first-item-at-0 constraint so the whole timeline actually slides. More complex and probably not useful.

I'd go with option 2 — it falls out naturally from `if/else if` ordering, zero extra code.

> DEVELOPER

Coud there be use-cases for doing both?

> AGENT

Thinking about it... not really, at least not one that falls naturally out of the push mechanic.

The literal result of "push both sides by the same delta" is a rigid slide of the whole timeline, which the first-item-at-0 constraint undoes. To make it meaningful you'd have to special-case it into something different — like scaling all gaps proportionally (time-stretch), or expanding space around the dragged item (push right items right AND left items left, i.e. opposite deltas). Both are interesting but they're fundamentally different operations, not a natural combination of the two push modes.

I'd stick with `if/else if` — Command wins — and not overthink it. If a "scale timeline" or "expand around item" feature ever feels needed, it can be its own thing later.
