Good question. Let me think about this structurally rather than just listing nitpicks.

**1. Kill the global mutable state.**

`_extra_exclusions` and `lang._zone_map` being set-at-scan-time module globals is the root cause of multiple bugs you've already fixed. The real fix is a `ScanContext` object that gets passed through — holds the zone map, exclusions, file cache, dep graph. Everything that's currently "set this on the module before calling these functions" becomes "here's your context." This is the single highest-leverage change.

**2. The MEMORY.md is a design doc for what the code should say instead.**

Every "Important Pattern" entry is a place where the code's API doesn't communicate its own contract. "You MUST import the module, not the variable" — that's a bug in the API, not something to memorize. "Function extractors return FunctionInfo dataclass objects (not dicts)" — if someone could confuse this, the type signatures aren't doing their job. The goal: delete half of MEMORY.md by making those lessons impossible to violate through the code's structure.

**3. Fewer, fatter language plugins.**

25+ language directories is a maintenance surface area problem. If most of them are thin wrappers around tree-sitter with the same detection phases, that's a generic plugin with per-language config, not 25 separate packages. It looks like `framework/generic.py` and `framework/treesitter/` might already be heading this direction — push harder on it until adding a language is a TOML file, not a directory.

**4. Make the detector pipeline declarative.**

Right now detectors are a mix of regex functions, AST walkers, and external tool adapters, all wired together through phase functions. If each detector were a declaration — "match this pattern, in these zones, at this confidence, producing this finding type" — the framework could handle scoring, zone filtering, and confidence weighting uniformly. The regex detectors are already almost this shape; formalize it.

**5. Tests that prove contracts, not tests that cover lines.**

The fix history suggests tests were added after bugs were found, patching specific scenarios. More valuable: property-based tests on the core pipelines. "Any finding produced by any detector has a valid confidence/status/zone." "Scoring is monotonic — resolving a finding never decreases the score." "State round-trips through save/load without loss." These catch classes of bugs, not instances.

**6. Separate the scoring engine from the CLI.**

The scoring/narrative/detection engine is genuinely interesting and reusable. The CLI, commands, rendering, and output formatting are application concerns. Right now they're interleaved — `scan_reporting_*.py` files mix computation with presentation. A clean `engine` boundary (which the directory structure already hints at) would let you test the engine in isolation and eventually expose it as a library.

---

The theme: most of the complexity isn't inherent to the problem — it's accumulated from the code not enforcing its own invariants. A `ScanContext`, declarative detectors, and a real engine/app boundary would let you delete code and constraints rather than adding more of both.
