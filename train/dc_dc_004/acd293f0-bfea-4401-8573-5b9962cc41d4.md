## Part 2: Add `package_organization` Holistic Dimension

### How the reviewing agent identifies structural problems

The agent evaluates codebase structure through five heuristics, each backed by specific context data:

#### Heuristic 1: Straggler detection (misplaced files)
**Test**: For each file at a directory level, check whether it "belongs" there.
**Signals**:
- **Import affinity**: If a file's imports come >60% from one subdirectory, it probably belongs in that subdirectory. Example: `scorecard.py` at root imports from PIL and `_scorecard_draw` — its concern is "output rendering," not "core desloppify."
- **Fan-in count**: Core files have high fan-in (many modules depend on them). Peripheral files have low fan-in. `utils.py` (83 importers) is core. `scorecard.py` (1 importer — scan.py) is peripheral.
- **Theme clustering**: If 2+ files at the same level share a narrow concern (viz, rendering, output, drawing), they should be a subpackage together.

**Context data needed**: Per-file fan-in at root level, import profile per file showing where imports come from.

#### Heuristic 2: Directory cohesion
**Test**: Do files in the same directory import similar things? Do they serve the same concern?
**Signals**:
- **Sibling import divergence**: Already computed by `conventions.sibling_behavior` — files missing shared imports across the directory.
- **Import profile variance**: If one file's imports are radically different from its siblings, it's a candidate for relocation.
- **Zone mixing**: If a directory has production files alongside test utilities, the boundary is unclear.

**Context data needed**: Already partially available. Add per-directory zone distribution.

#### Heuristic 3: Cross-code contamination (layer violations)
**Test**: Do imports flow in a clear direction? Is there leakage across architectural boundaries?
**Signals**:
- **Directory coupling matrix**: Which directories import from which others. Clean architecture has a DAG; contamination shows up as unexpected edges (e.g., a "utility" importing from a "command").
- **Bidirectional coupling**: If directory A imports from B AND B imports from A, their boundary is unclear — they may need merging or a clearer interface.

**Context data needed**: Directory-to-directory import edge counts.

#### Heuristic 4: Structural consistency
**Test**: Does the directory hierarchy have consistent depth and purpose?
**Signals**:
- **Depth variance**: Sibling directories at the same level should have similar complexity. If `lang/` has 3 nesting levels but `detectors/` is flat, either one is over/under-structured.
- **Flat directory threshold**: Directories with >10 files should have subdirectories unless all files are genuinely same-concern.
- **Single-file directories**: Unnecessary nesting — the file should move up a level.

**Context data needed**: The tree overview (from `generate_tree_text`) provides this directly.

#### Heuristic 5: Boundary clarity (the "new developer" test)
**Test**: If a new developer looks at the directory tree, can they predict what each directory contains and where to find a given feature?
**Signals**:
- **Directory name vs contents**: Does the name match what's inside? A `utils/` full of domain logic has a misleading name.
- **Describability**: Can you articulate each directory's purpose in one sentence? If not, the boundary is muddy.

**Context data needed**: Directory profiles with file lists, which the tree + profiles provide.
