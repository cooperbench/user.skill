# What's Stopping This Codebase From Being Beautiful

**Desloppify score: 83/100** — the mechanical stuff (unused imports, dead exports) is mostly handled. What's left is the harder, subjective stuff that tools can't catch. Here's what 6 deep-dive agents found, distilled into the themes that matter.

---

## 1. The Params Problem (found by 3/6 agents)

This is the single biggest architectural debt. Task params are an untyped `any` bag that stores different data in 4-6 different nested paths depending on when the task was created:

```typescript
// generation-handlers.ts — extracting ONE value requires checking 5 fallback chains
const pairShotGenId = params?.pair_shot_generation_id ||
  params?.individual_segment_params?.pair_shot_generation_id ||
  (Array.isArray(orchPairIds) && orchPairIds[segmentIndex]);
```

The `extractBasedOn()`, `extractOrchestratorRef()`, and similar functions each check 4-6 paths. This pattern repeats 10+ times across edge functions. Every new feature adds another path to check. Nobody can confidently say "where does this value come from?" without reading all paths.

**What beautiful looks like:** Normalize params to a canonical shape once at task fetch time. Use a discriminated union to identify which legacy format each task uses, then convert. Stop sniffing params to determine task routing — add an explicit `generation_route` enum to task_types.

---

## 2. The 13-Provider Tower & Context Confusion

```tsx
// App.tsx — the full nesting
<QueryClientProvider>
  <AuthProvider>
    <AuthGate>
      <UserSettingsProvider>
        <ProjectProvider>
          <RealtimeProvider>
            <ShotsProvider>
              <GenerationTaskProvider>
                <IncomingTasksProvider>
                  <PanesProvider>
                    <LastAffectedShotProvider>
                      <CurrentShotProvider>
                        <ToolPageHeaderProvider>
```

Several of these are **cache duplicates** — ShotsContext wraps `useListShots()` (a React Query hook) and re-exports it as context. GenerationTaskContext wraps a batch lookup utility used in only 2 places. These add a re-render boundary without adding value.

Worse, contexts are inconsistent about missing-provider behavior: some throw (`useProject`), some return silent no-ops (`useAIInputMode`). And `window.__PROJECT_CONTEXT__` exists as a hidden global fallback for when context isn't available — a red flag that context boundaries are wrong.

**What beautiful looks like:** Delete passthrough contexts (ShotsContext, GenerationTaskContext). Group related providers semantically. Make all hooks throw on missing provider.

---

## 3. The GenerationRow Identity Crisis

The `GenerationRow` type has four names for the same ID:
- `id` (shot_generations.id)
- `generation_id` (generations.id)
- `shotImageEntryId` (deprecated alias)
- `shot_generation_id` (deprecated alias)

The mapper creates both `location` AND `imageUrl` pointing to the same value, plus `thumbnail_url` AND `thumbUrl`. Callers can't tell if these are different things or aliases without reading the mapper. New developers regularly use the wrong one.

Timeline positioning is similarly muddled: `timeline_frame` (DB), `position` (divided by magic 50), `timelineFrame` (camelCase variant) — three names for one concept.

**What beautiful looks like:** One name per concept, everywhere. Kill deprecated aliases completely. Document "use `id` for position ops, `generation_id` for generation data" once and enforce it.

---

## 4. Race Conditions in the Backend (Critical)

The backend agent found the most concerning issues:

- **complete_task double-completion:** Between fetching task status and updating it, another call can race. The `.eq("status", "In Progress")` WHERE clause helps but generation creation happens *before* the status update — so both calls create generations, only one's status update succeeds.

- **Double billing:** `calculate-task-cost` has an idempotency check that queries the ledger, but two concurrent calls can both see "no existing entry" and both insert.

- **Cascade failure silently drops:** When an orchestrator fails and cascade-updates siblings, if the cascade query itself fails (network timeout), it's logged and silently returned. Segments stay "In Progress" forever.

- **Params mutated before generation creation:** If generation creation fails, the task stays "In Progress" but params were already mutated — inconsistent state on retry.

**What beautiful looks like:** Wrap critical multi-step operations in database transactions. Use `INSERT ... ON CONFLICT` for idempotency. Never mutate params before the operation they support succeeds.

---

## 5. The MediaLightbox Prop Explosion

`MediaGalleryItem` takes **45 props**. `MediaLightbox` takes **100+**. `SegmentSlotModeData` has **40+ optional properties** for 3+ different modes crammed into one interface.

Props are drilled through 5 layers. Many intermediate components don't use the props — they just pass them through. Adding a feature means updating every layer.

**What beautiful looks like:** Discriminated unions for mode-specific data (`TimelineMode | BatchMode | PreviewMode`). Context for cross-cutting callbacks. Composition over prop drilling:
```tsx
<MediaLightbox media={gen}>
  <MediaEditTools />      // only where needed
  <MediaShotActions />    // only where needed
</MediaLightbox>
```

## 6. Cache Invalidation Shotgun

When marking one variant as viewed, the code invalidates **7 separate query keys**. When a generation is deleted, `invalidateAllShotGenerations()` fires for ALL shots globally — if you have 1000 shots, 999 unnecessary refetches happen.

Meanwhile, ~25 hooks still use inline query keys instead of the centralized `queryKeys` registry, making it impossible to know what gets invalidated by what.

**What beautiful looks like:** Scoped invalidation that targets exactly what changed. All query keys in the registry. A lint rule preventing inline keys.

---

## 7. The Settings System's Four Layers

Settings flow through 4 independent systems: priority resolution → React Query fetching → write queue (global singleton) → auto-save hook. The write queue requires manual initialization via `setSettingsWriteFunction()` before first use — a temporal coupling that fails silently if violated.

`useAutoSaveSettings` has **12+ refs** tracking state. Entity switches (changing shots) create race conditions between the debounce timer, the ref sync effect, and the write queue's own debounce.

**What beautiful looks like:** A single SettingsManager that owns all four concerns, with one flush mechanism aware of all layers. Explicit defaults for every field (no `inferEmptyValue` guessing).

---

## 8. What's Already Beautiful (worth preserving)

The agents also called out patterns worth keeping:

1. **RealtimeConnection** — clean separation of connection lifecycle from event handling. Minimal public API. Easy to extend.

2. **typeGuards.ts** — canonical source for video detection. One function per data structure. If you need to add a format, one file to change.

3. **Error handling pipeline** — `categorizeError()` → `handleError()` with required context strings. Structured, consistent, traceable logs.

4. **Params-driven routing** in complete_task — despite the normalization issues, the concept of "params declare intent" is sound and extensible.

5. **Optimistic mutation patterns** in shot CRUD — proper `onMutate`/`onError` rollback with cache snapshots. The pattern in `useShotsCrud.ts` is textbook.

---

## The Meta-Pattern

Most issues trace to one root cause: **layers of abstraction accumulated without clear justification**. Settings have 4 layers. Data fetching has 3 scopes. Params have 6 extraction paths. IDs have 4 names.

Each layer was added for a reason (legacy support, edge case, mobile behavior), but nobody pruned the old layer when the new one arrived. The result: tracing any feature from UI to database requires understanding 5-10 files instead of 2-3.

The path to beautiful isn't adding more abstractions — it's **collapsing layers**. Normalize params once. Pick one name per concept. Delete passthrough contexts. Make the remaining code honest about what it does.
