## ImageGenerationForm.tsx: Structural Analysis

### What It Is

A ~6,000 LOC form system across 30+ files. The main orchestrator (1,069 LOC) calls 7 extracted hooks, 10+ shared hooks, has ~10 effects, and constructs 8 memoized context value objects. Previous refactoring extracted domain hooks (prompts, references, loras, etc.) and added a context system to avoid prop drilling to child components.

### The Surface Problem vs. The Real Problem

The surface problem is "1069 LOC, 22 hooks, complexity:33." But the real question is: **did the previous hook extraction actually reduce complexity, or did it just relocate it?**

The answer is: **it mostly relocated it.** Here's why:

---

### Structural Issue 1: State Ownership Inversion (the core problem)

The extracted hooks don't own their state. The main component does. The hooks are just function extractions that receive their state as props and return handlers.

**Example** — `usePromptManagement` takes 15 props:
```
associatedShotId, effectiveShotId, shotPromptSettings, noShotPrompts, 
setNoShotPrompts, noShotMasterPrompt, setNoShotMasterPrompt, promptMode, 
setPromptMode, beforeEachPromptText, setBeforeEachPromptText, 
afterEachPromptText, setAfterEachPromptText, ready, markAsInteracted, generatePromptId
```

Most of these are `[state, setter]` pairs owned by the parent. The hook could own this state internally, but it can't because...

### Structural Issue 2: `usePersistentToolState` Forces Centralized State

This is the root constraint. `usePersistentToolState` at lines 377-391 requires a flat map of `[value, setter]` tuples:

```typescript
usePersistentToolState('image-generation', { projectId }, {
  imagesPerPrompt: [imagesPerPrompt, setImagesPerPrompt],
  selectedLoras: [loraManager.selectedLoras, loraManager.setSelectedLoras],
  beforeEachPromptText: [beforeEachPromptText, setBeforeEachPromptText],
  // ... 9 more fields
});
```

This means **every piece of persisted state must be `useState`'d in the main component**, then passed down to hooks. Moving state into hooks would break persistence. This is why the hooks receive massive prop bags — they're operating on borrowed state.

**Similarly**, `useAutoSaveSettings` for shot-scoped data is called in the main component (line 365-372) and the result is threaded into `usePromptManagement` as a prop.

**Impact**: The main component can never shrink below ~500 LOC because it must declare, persist, and thread ~15 state variables, then construct 8 context value objects.

### Structural Issue 3: Duplicated Initialization

Generation source and LORAs have initialization split across two locations:

- `useGenerationSource` has its own initialization effect (lines 109-123 in the hook)
- The main component **also** has initialization effects at lines 430-476 that do similar work

This happened because LORA initialization depends on `loraManager` which is created in the main component. So the hook initializes generation source, but the parent initializes LORAs that depend on that initialization.

### Structural Issue 4: The Submission Capture Problem

`handleSubmit` (lines 219-335 of `useFormSubmission`) manually captures 18 variables into local `const` declarations to prevent stale closures in a fire-and-forget async:

```typescript
const capturedMasterPrompt = masterPromptText;
const capturedImagesPerPrompt = imagesPerPrompt;
const capturedPromptMultiplier = promptMultiplier;
// ... 15 more
```

Then it builds `referenceParams` and calls `buildBatchTaskParams` **twice** — once in the automated path, once available via `getTaskParams` for the managed path. This is fragile (miss a capture = stale closure bug) and duplicative.

### Structural Issue 5: Legacy Weight

- **402 lines of migration code** (`useLegacyMigrations`) running 5 migration scenarios with session-storage gates. This runs on every mount.
- **4 unused props** (`isGenerating`, `hasApiKey`, `apiKey`, `justQueued`) — kept for "API compatibility" but marked with `_` prefix
- **`hasApiKey` hardcoded to `true`** at line 668 but still threaded through UI as a prop
- **Legacy aliases** at lines 574-580: `currentStyleStrength = styleReferenceStrength` etc.

### Structural Issue 6: Metadata Reconstruction Anti-Pattern

`handleUpdateReferenceName` (lines 642-680) and `handleToggleVisibility` (lines 686-722) in `useReferenceManagement` both reconstruct the **entire** `StyleReferenceMetadata` object just to change one field. If a new field is added to the type, these functions silently drop it.

---

## Plan: What To Do About It

The issues form a dependency chain. The persistence layer (Issue 2) causes the state ownership inversion (Issue 1), which causes the prop bags, which cause the complexity score.

### Phase 1: Low-Risk Cleanup (removes ~100-150 LOC, no architecture change)

1. **Remove dead props and the `hasApiKey` fiction** — Delete the 4 `_`-prefixed unused props from the interface and component. Remove the `hasApiKey = true` constant and all code that conditionally checks it. This removes dead branches throughout the component tree.

2. **Remove legacy aliases** — Replace `currentStyleStrength` etc. with direct destructured names from `useReferenceManagement`. Just rename usage sites.

3. **Consolidate duplicated initialization** — The generation source + LORA initialization split across the main component (lines 430-476) and `useGenerationSource` should live in one place. Move LORA initialization into `useGenerationSource` by passing `loraManager` to it (it already receives a partial `loraManager`).

### Phase 2: Persistence Layer Refactor (the key unlock)

4. **Introduce `usePersistentToolStateV2` that accepts a hook factory** — Instead of requiring pre-declared `[value, setter]` tuples, the new API would look like:

```typescript
const { state, ready, markAsInteracted } = usePersistentToolStateV2(
  'image-generation',
  { projectId },
  (hydrated) => ({
    imagesPerPrompt: useState(hydrated?.imagesPerPrompt ?? 8),
    promptMode: useState(hydrated?.promptMode ?? 'automated'),
    // ... etc
  })
);
```

This lets hooks own their state internally while still participating in persistence. The factory pattern means hydration happens before state is created.

**Alternative** (simpler): Keep the current API but create a `useImageGenFormState` hook that calls `usePersistentToolState` **internally** and exposes a structured API. The main component just destructures from it. This is less general but faster to ship.

### Phase 3: Hook Ownership Migration (depends on Phase 2)

5. **Move state into domain hooks** — With the persistence bridge in place, each hook owns its own state:
   - `usePromptManagement` owns `promptMode`, `noShotPrompts`, `noShotMasterPrompt`, `beforeEachPromptText`, `afterEachPromptText` and calls `useAutoSaveSettings` internally
   - `useGenerationSource` already owns `generationSource`, `selectedTextModel`, `modelOverride` — just needs LORA init consolidated
   - `useReferenceManagement` already owns its local UI state — no change needed

   The main component drops from ~1069 to ~400-500 LOC (JSX + context construction + shot management + modals).

### Phase 4: Submission Simplification

6. **Replace 18 captured variables with a single form state ref** — Create a `formStateRef` that holds a snapshot of all submission-relevant values. The submission hook reads from the ref instead of capturing individual closures. This eliminates the capture block and makes the async fire-and-forget pattern safe by construction.

7. **Deduplicate `buildBatchTaskParams` + `referenceParams` construction** — The automated and managed paths both build these. Extract a `buildSubmissionParams(formState)` function that both paths call.

### Phase 5: Legacy Retirement

8. **Migrate `useLegacyMigrations` to a server-side process** — These 4 migrations handle format changes that presumably affect existing users. Once a reasonable time has passed, these could be:
   - Run as a one-time DB migration for all users
   - Or gated behind a user-level flag in the DB so they never run again after succeeding

9. **Fix the metadata reconstruction pattern** — `handleUpdateReferenceName` and `handleToggleVisibility` should use a partial update API (e.g., `updateResourceMetadata(id, { name: newName })`) instead of reconstructing the full object.

---

### Priority and Dependencies

```
Phase 1 (cleanup)         → standalone, safe, do first
Phase 2 (persistence)     → prerequisite for Phase 3
Phase 3 (hook ownership)  → the payoff — main component shrinks to ~400 LOC
Phase 4 (submission)      → standalone, can be done in parallel with 2+3
Phase 5 (legacy)          → standalone, lowest urgency
```

Phase 1 is pure wins with zero risk. Phase 2+3 is the structural fix but requires careful work since the persistence layer is used by every tool. Phase 4 and 5 are independent improvements.
