# Plan: Concerns Detector — Mechanical → Subjective Bridge

## Context

Mechanical detectors find low-level signals (monster functions, high param counts, duplication clusters) but can't judge whether those signals represent real design problems. The existing subjective review (LLM-based) *could* judge them, but it doesn't receive pre-computed signals — it has to notice patterns on its own and often misses them.

**Goal:** Create a pipeline where mechanical findings generate structured "potential concerns," which are evaluated by the LLM during the review step. Confirmed concerns become findings that follow the normal reconciliation lifecycle.

## Architecture

### Core Concept: Concerns are Ephemeral, Verdicts are Persistent

- **Concern generators** are pure functions: `(state, lang_name) -> list[Concern]`
- Concerns are computed on-demand from current state — never stored in state
- Only LLM-confirmed concerns become persistent `Finding` objects via review import
- Dismissed concerns are tracked to avoid re-evaluation

### Data Flow

```
scan → mechanical findings in state
           ↓
review --prepare → concern generators read state
           ↓           → build "Design Coherence" investigation batch
           ↓           → include in review packet (query.json)
           ↓
LLM evaluates each concern → confirms/dismisses
  + provides overall "Design coherence" assessment score (0-100)
           ↓
review --import → confirmed → findings (detector="concerns")
               → dismissed → tracked in state["concern_dismissals"]
               → assessment → state["subjective_assessments"]["design_coherence"]
```

### Why Not Store Concerns in State?

Concerns are derived data — they're a view over existing findings. Storing them would create a sync problem (stale concerns when findings change). Computing them on-demand means they're always current.

### Scoring Model: Assessment-Based (like other subjective dimensions)

The LLM evaluates all concerns and provides:
- An overall **"Design coherence" assessment score** (0-100) — this drives the dimension score
- Individual **concern verdicts** (confirmed/dismissed) — these become informational findings

This is identical to how existing subjective dimensions work: the assessment score is authoritative, findings are tracked for visibility and resolution, but don't directly lower the score. This avoids needing a synthetic "potential" denominator and keeps the scoring model consistent.

### Step 2: Concern Generators (initial set)

**File:** `desloppify/engine/concerns.py`

Each generator is a private function called by `generate_concerns()`:

| Generator | Trigger | Question for LLM |
|-----------|---------|-------------------|
| `_god_functions` | `smells` findings with `smell_id=monster_function` and LOC > 120 | "What are the distinct responsibilities? How should this be decomposed?" |
| `_param_bloat` | `structural` findings where `detail.signals` mentions params > 10 | "Should these parameters be grouped into a config/context object? Which ones belong together?" |
| `_finding_cluster` | Files with open findings from 4+ different detectors | "This file has problems across {N} dimensions. Is it doing too many things? Should it be split?" |
| `_deep_nesting` | `structural` findings where nesting depth > 6 | "Can this nesting be reduced with early returns, guard clauses, or extraction?" |

Each generator:
1. Filters `state["findings"]` for relevant open findings
2. Groups/analyzes patterns
3. Checks against `state.get("concern_dismissals", {})` — skip if fingerprint matches and source findings unchanged
4. Returns `Concern` objects

### Architecture
- **Concerns are ephemeral** — computed on-demand from state, never stored
- **Fingerprint-based dismissal** — dismissed concerns stay suppressed until underlying findings change
- **Assessment-driven scoring** — identical to other subjective dimensions (LLM assessment score is authoritative)
- **Confirmed concerns** become `detector="concerns"` findings via standard review import
- **Best-effort integration** — concern generation failures don't block scan or review

> AGENT

**Scan** produces mechanical findings (monster functions, high params, deep nesting, etc.) stored in state.

**`review --prepare`** calls `generate_concerns(state)` which reads those findings and synthesizes `Concern` objects — ephemeral, never stored. These get bundled into a "Design Coherence" investigation batch in query.json alongside the standard batches, with specific questions for the LLM to evaluate.

**LLM reviews** each concern and returns either:
- `concern_verdict: "confirmed"` → becomes a `detector="concerns"` finding in state
- `concern_verdict: "dismissed"` → fingerprint stored in `state["concern_dismissals"]`
- Plus an overall `design_coherence` assessment score (0-100) that drives the dimension score

**`review --import`** handles both verdict types. Dismissed concerns are suppressed on future `generate_concerns()` calls — but only while their source findings haven't changed. If the underlying mechanical findings change, the fingerprint shifts and the concern resurfaces.

**Scoring** works identically to other subjective dimensions: the assessment score is authoritative, confirmed concern findings are tracked for visibility but don't independently lower the score.

**CLI surface**: `scan` prints a concern count line; `show concerns` renders each concern with evidence and the question the LLM would evaluate.
