## Analysis: Making Decruftify Language-Agnostic

### What we're really dealing with

The tool has **three layers of specificity**:

| Layer | Examples | Count |
|-------|----------|-------|
| **Universal concepts** | large files, duplication, cycles, naming | ~7 detectors |
| **Language-specific** | import syntax, unused detection, export syntax | ~5 detectors |
| **Framework/codebase-specific** | React hooks, useQuery, tools/shared coupling | ~7 detectors |

### The core tension

The detectors aren't just "find X pattern" — they're deeply intertwined with **how** they find things:

- **File discovery**: `find_ts_files()` / `find_tsx_files()` hardcoded everywhere
- **Import parsing**: `deps.py` builds a graph from `import/from` syntax — Python uses totally different import syntax
- **Unused detection**: shells out to `tsc` — Python equivalent would be `pylint`, `pyflakes`, or AST walking
- **"Structural" signals**: gods/concerns/props are meaningfully different concepts in Python (god classes vs god components, mixed concerns means something different without JSX)

### What Python equivalents actually look like

| React/TS Detector | Python Equivalent | Same concept? |
|---|---|---|
| `gods.py` (hook count) | God classes (method count, attribute count) | Same smell, totally different detection |
| `concerns.py` (JSX + data) | Mixed concerns (DB queries + HTTP handlers + business logic in one file) | Same smell, different signals |
| `props.py` (>14 props) | Functions with >7 params, or dataclasses with >14 fields | Same smell, different syntax |
| `react.py` (useState+useEffect sync) | No direct equivalent — maybe mutable class state anti-patterns? | Different smell entirely |
| `unused.py` (via tsc) | via pyflakes/pylint/ruff | Same concept, different tool |
| `exports.py` (dead exports) | `__all__` members never imported, or public functions never called externally | Conceptually similar, very different detection |
| `deps.py` (import graph) | Python import graph (`import X`, `from X import Y`) | Same concept, different parsing |
| `smells.py` (any, ts-ignore, dead useEffect) | bare except, type: ignore, mutable default args, global state | Same category, totally different patterns |
| `coupling.py` (tools→shared) | Package boundary violations (whatever your structure is) | Needs config, not hardcoding |

### The key design question

There are really **two approaches**:

#### Option A: Language profiles (plugin system)

```
detectors/
  base.py          # abstract detector interface
  large.py         # already generic
  dupes.py         # already generic
  naming.py        # already generic
languages/
  typescript/
    file_discovery.py   # find .ts/.tsx files
    import_parser.py    # parse TS imports
    unused.py           # tsc-based
    smells.py           # TS-specific smells
    structural.py       # gods, concerns, props
  python/
    file_discovery.py   # find .py files
    import_parser.py    # parse Python imports
    unused.py           # ruff/pyflakes-based
    smells.py           # Python-specific smells
    structural.py       # god classes, param bloat
```

Each language provides a **profile** — a bundle of:
1. **File discovery** (extensions, exclusions)
2. **Import parser** (for dep graph, cycles, coupling, orphans, single-use)
3. **Unused detector** (language tool integration)
4. **Export/public API detector**
5. **Smell catalog** (language-specific patterns)
6. **Structural signals** (what "god object" means in this language)

The generic detectors (large, dupes, naming, dep graph algorithms) stay shared and consume the profile's primitives.

#### Option B: Forked detector sets (simpler)

Just have `--lang python` swap which detector modules get loaded. Python gets its own `gods.py`, `smells.py`, etc. — they share the same *output format* (findings with tiers) but not implementation.

Shared infrastructure:
- State management (unchanged)
- Scoring (unchanged)
- CLI commands (unchanged)
- Fixers (need per-language versions too)

### My recommendation: Option B with a thin abstraction layer

Here's why:

1. **The detectors share almost no implementation.** Python unused detection (ruff) shares zero code with TS unused detection (tsc). Python import parsing shares zero code with TS import parsing. A plugin interface would be ceremony over substance.

2. **What they DO share is the pipeline.** The scan→normalize→merge→score→fix flow is 100% generic. `state.py`, `plan.py`'s orchestration, all commands — these don't care what language produced the findings.

3. **The abstraction you need is small:**
   - A `Language` config object: extensions, exclusions, source root
   - A `find_source_files(lang)` replacing `find_ts_files()`
   - Import parser interface (returns edges) for the dep graph
   - Detector registry keyed by language

4. **Fixers are language-specific anyway.** Removing a Python import looks nothing like removing a TS import. You'd need separate fixer implementations regardless.

### What actually changes

**Stays identical:**
- `state.py` — findings are already language-agnostic dicts
- `cli.py` — just add `--lang` flag, everything else works
- All commands (`scan`, `status`, `show`, `next`, `resolve`, `ignore`, `fix_cmd`, `plan_cmd`)
- Scoring, matching, ignore patterns
- `large.py`, `dupes.py`, `naming.py` — already generic (just need file discovery swapped)

**Needs a thin abstraction:**
- `utils.py` — `find_source_files(lang)` instead of `find_ts_files()`. `grep()` needs to accept extensions.
- `deps.py` — import parser becomes pluggable (TS parser vs Python parser), but graph algorithms stay shared
- `plan.py` — detector list becomes language-dependent (skip `react.py` for Python, add `python_smells.py`)

**Needs Python-specific implementations:**
- `detectors/python/` — god classes, unused (via ruff), smells (bare except, mutable defaults, etc.), structural
- `fixers/python/` — remove unused imports (via ruff --fix or manual), etc.

**Gets dropped for Python:**
- `react.py`, `gods.py` (hook-based), `concerns.py` (JSX-based), `props.py` (Props interface-based)
- Fixers: `useeffect.py`, `params.py` (underscore prefix is already Python convention!)

### The `--lang` UX

Simplest approach: detect from the directory, or explicit flag.

```bash
decruftify scan                    # auto-detect from package.json / pyproject.toml / etc.
decruftify scan --lang python      # explicit
decruftify scan --lang typescript  # explicit
```

State files would be per-language (`.decruftify/state-python.json`) so you could track both in a monorepo.

### Estimated scope

| Work item | Effort |
|-----------|--------|
| Abstract file discovery + grep | Small — mostly parameterizing extensions |
| Pluggable import parser for dep graph | Medium — Python import parsing is its own thing (`import X`, `from X import Y`, relative imports, `__init__.py`) |
| Python unused detector (ruff integration) | Small — ruff already outputs structured findings |
| Python smells catalog | Medium — need to curate Python-specific smells |
| Python structural detectors (god class, etc.) | Medium — different signals than React |
| Python fixers | Medium — import removal, unused var removal |
| CLI --lang flag + detector registry | Small |
| **Total** | **~1 solid day of work** |

### What I'd do first

1. Extract the **thin abstractions** (file discovery, import parser interface) without changing any behavior for TS
2. Build the **Python import parser** (it's the linchpin — dep graph powers 5+ detectors)
3. Port the **easy generic detectors** (large, dupes, naming, unused via ruff)
4. Build **Python-specific detectors** (god class, smells)
5. Port **fixers** last (they're nice-to-have; the scan/track/score loop is the core value)

The key insight: **the value of decruftify is the tracking/scoring pipeline, not the detectors themselves.** The detectors are inputs. Making the pipeline language-agnostic is easy because it already almost is — it just needs the detector registry to be parameterized.
