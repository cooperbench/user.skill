# Preloading System Consolidation Plan

## Problem Statement

The preloading system has:
1. **Duplicate tracking**: `PreloadingService.loadedImageIds` duplicates `imageLoadTracker`
2. **Legacy global cache**: `window.videoGalleryPreloaderCache` is separate from everything
3. **Scattered files**: Code spread across 6+ locations
4. **No centralized cache cleanup**: React Query cache + tracker cleanup not coordinated

## Goals

1. Single source of truth for "what's loaded"
2. One directory for all preloading code
3. Eliminate `window.videoGalleryPreloaderCache`
4. Centralized cache cleanup on project switch / deletion

## Non-Goals

- Don't touch `useProgressiveImage`, `useProgressiveImageLoading` (they work, different concerns)
- Don't rename hooks unnecessarily
- No backwards compatibility exports needed

---

## How Caching Relates to Preloading

These are complementary systems with different responsibilities:

| System | What It Stores | Who Controls It |
|--------|---------------|-----------------|
| **React Query** | Generation metadata (IDs, URLs, settings) | Our code via staleTime/gcTime |
| **Load Tracker** | Which images have been preloaded (IDs/URLs only) | PreloadingService |
| **Browser Cache** | Actual image bytes | Browser (we trigger loads) |
| **PreloadQueue** | Pending preload tasks | PreloadingService |

**Coordination on events:**

| Event | React Query | Load Tracker | PreloadQueue |
|-------|-------------|--------------|--------------|
| Page navigation | Prefetch adjacent pages | Track loaded images | Queue new images |
| Project switch | Clear old project queries | Clear all | Clear pending |
| Generation deleted | Invalidate queries | Remove from tracker | N/A |
| Disconnect | Keep cache | Keep tracker | Clear queue |

The `PreloadingService` coordinates all of this in one place.

### Phase 4: Centralize Cache Cleanup

**In service.ts `onProjectChange()`:**
```typescript
onProjectChange(projectId: string | null) {
  // 1. Clear preload queue
  this.queue.clear();

  // 2. Clear tracker
  tracker.clearAll();

  // 3. Clean up React Query cache for old project
  if (this.previousProjectId) {
    this.cleanupProjectQueries(this.previousProjectId);
  }

  this.previousProjectId = projectId;
}

// React Query cleanup helper
private cleanupProjectQueries(projectId: string) {
  // Remove unified-generations queries for the old project
  // These can be large and we don't need them across project switches
  queryClient.removeQueries({
    predicate: (query) =>
      query.queryKey[0] === 'unified-generations' &&
      query.queryKey[2] === projectId,
  });
}
```

**Note:** React Query has its own `gcTime` (garbage collection time) but we proactively clear on project switch because:
1. Stale data from old project is useless
2. Frees memory faster than waiting for gc
3. Prevents showing stale images if user returns to same project

## Key Considerations

### 1. How Ref Storage Interacts with Tracker Limits

Current tracker has limits:
- Mobile/low memory: 100 IDs, 150 URLs
- Desktop: 300 IDs, 500 URLs

When limits are hit, `evictOldestEntries` removes old entries. If we store element refs in the URL entries, evicted entries lose their refs → browser may garbage collect those images.

**But**: Video gallery's `TARGET_CACHED_IMAGES` is 12 (mobile) or 48 (desktop) - well under the tracker limits. So in practice, video gallery refs won't get evicted.

### 2. Queue API Change

Current:
```typescript
queue.add(url, priority): Promise<void>
```

Needs to become:
```typescript
queue.add(url, priority): Promise<HTMLImageElement>
```

This is a breaking change to the queue's public API. The preloader is the only consumer, so it's contained, but worth noting.

### 3. Two Types of Tracking

The tracker tracks:
- **By ID** - `loadedImagesById` (for generation IDs)
- **By URL** - `loadedImagesByUrl` (for progressive loading, preload checks)

Video gallery preloading only has URLs at preload time (it fetches from `shot_generations` but doesn't pass IDs through). So it uses URL tracking exclusively.

The `hasLoadedImage()` function handles both:
```typescript
// URL string → checks loadedImagesByUrl
hasLoadedImage("https://...")

// Object with ID → checks loadedImagesById  
hasLoadedImage({ id: "gen-123" })
```

This works for both systems.

### 4. Shot-Specific State Doesn't Fit in Tracker

`useVideoGalleryPreloader` tracks:
- `preloadedPagesByShot[shotId]` → Set of preloaded page numbers
- `hasStartedPreloadForProject[projectId]` → Boolean

These are domain-specific (shots, pages). They should stay as local refs in the hook, not in the generic tracker.

### 5. The Custom Event

`useThumbnailLoader` listens for `'videogallery-cache-updated'` to know when to re-check cache status. Options:

a) **Keep the event** - `useVideoGalleryPreloader` dispatches it after `preloadingService.preloadImages()` returns
b) **Use service subscription** - `useThumbnailLoader` subscribes to service events

Option (a) is simpler and keeps video-gallery-specific code together.

### 6. Race Condition on Project Switch

Current flow:
1. User switches project
2. `ProjectContext` calls `preloadingService.onProjectChange(newProjectId)`
3. Service clears tracker (including refs)
4. `useThumbnailLoader` might still be checking old URLs

The tracker clear is synchronous, so any subsequent `hasLoadedImage()` calls will return false. This is correct behavior - we want the new project to start fresh.
