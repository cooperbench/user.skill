# Assessment-Based Review Scoring

## Context

Review findings currently work like other detectors: each finding is a weighted failure counted against the "Design quality" dimension. This creates a perverse incentive — a thorough review that finds 5 issues tanks the score, while a sloppy review that finds 0 gets 100%. The user wants the reviewer to **assess** each dimension directly (0-100), and those assessments drive the score. Findings become a work queue only, not score penalties.

## Current vs Proposed Model

**Current (penalty-based):**
```
reviewer finds 3 issues → 3 weighted failures → pass_rate = (potential - failures) / potential
```

**Proposed (assessment-based):**
```
reviewer assesses "naming_quality: 75/100" → pass_rate = 0.75
findings = work items for `desloppify issues`, don't affect score
fix issues → re-review → "naming_quality: 90/100" → score improves
```

## Design: Each Assessment = Its Own Scoring Dimension

Each assessed review dimension becomes a **first-class scoring dimension** (tier 4), exactly like "Import hygiene" or "Code quality". They appear individually in `dimension_scores`, contribute independently to the overall health score, and are extensible — add a new review dimension to the prompt and it auto-appears as a scoring dimension.

**How it integrates with the existing system:**
- `DIMENSIONS` list: rename "Design quality" → "Review coverage", remove "review" from its detectors. It becomes `Dimension("Review coverage", 4, ["subjective_review"])` — purely coverage tracking.
- "review" is no longer in ANY dimension. Review findings don't affect any failure-based score.
- `compute_dimension_scores()` processes the DIMENSIONS list as before, then **appends** assessment dimensions
- `compute_objective_score()` iterates the results dict unchanged — it doesn't care where entries came from
- Clean separation: mechanical dimensions from DIMENSIONS list, assessment dimensions from `state["review_assessments"]`

**Checks per dimension** (for sample dampening):
- New constant `ASSESSMENT_CHECKS = 10` — each assessed dimension gets 10 checks
- `sample_factor = 10/200 = 0.05`, `effective_weight = 4 × 0.05 = 0.2` per dimension
- 5 assessed dimensions → total weight 1.0 (comparable to one typical detector dimension)
- 15 assessed dimensions → total weight 3.0 (proportional to the quality signals provided)
- This means: **assess more → review matters more** — the "add more and more" extensibility

**Backward compatibility:** If `state["review_assessments"]` is missing/empty, "review" detector falls through to penalty-based scoring within "Design quality" as before. Old state files and old-format imports (bare array) work unchanged.

## How both review types work

There are two kinds of review, each producing assessments + findings:

**Holistic review** (`review --prepare --holistic`):
- Looks at the **whole codebase** structure — architecture, coupling, conventions
- Dimensions: `cross_module_architecture`, `initialization_coupling`, `convention_outlier`, `error_consistency`, `abstraction_fitness`, `dependency_health`, `test_strategy`, `api_surface_coherence`
- Assessment: "cross_module_architecture: 65/100" (codebase-wide judgment)
- Findings: "cli.py exports shared helpers used by 13 modules" (work item, file=".")

**Per-file review** (`review --prepare`):
- Looks at a **sample of individual files** (top 50 by priority) for code quality
- Dimensions: `naming_quality`, `comment_quality`, `error_consistency`, `convention_outlier`, `abstraction_fitness`, `logic_clarity`, `contract_coherence`, `initialization_coupling`, `logging_quality`, `type_safety`, `cross_module_architecture`
- Assessment: "naming_quality: 80/100" (based on the 50 files reviewed — a sampling-based judgment, like how a real code reviewer assesses a codebase after reviewing a PR)
- Findings: "src/foo.ts: variables x, y, z are poorly named" (work item, specific file + line)

**Both produce the same outputs:**
```json
{
  "assessments": {"naming_quality": 75, "comment_quality": 85, ...},
  "findings": [{"file": "src/foo.ts", "dimension": "naming_quality", ...}]
}
```

**Both feed the same pipeline:**
- Assessments → stored in `state["review_assessments"]` → become scoring dimensions
- Findings → stored in `state["findings"]` → appear in `desloppify issues`

**Overlap handling:** Some dimensions appear in both (e.g., `cross_module_architecture`). Holistic assessment overwrites per-file for overlapping dimensions, since holistic has the full codebase view. Per-file assessments fill in dimensions holistic doesn't cover.

**Re-review cycle:**
1. Fix issues from `desloppify issues`
2. Re-run `desloppify review --prepare [--holistic]`
3. Re-import → new assessments overwrite old → dimension scores update → overall health improves

## Key behaviors

1. **No assessments = old behavior.** Fall through to penalty-based scoring. Old state files work.
2. **Findings are work items only.** Still stored in `state["findings"]`, still visible via `desloppify issues`, still resolvable. Just don't count as failures.
3. **Resolve doesn't change score.** Score is driven by assessments, not finding status. Agent needs to re-review after fixing.
4. **Holistic overwrites per-file.** Same dimension assessed by both → holistic wins (broader view).
5. **subjective_review unchanged.** The review_coverage detector (flags unreviewed/stale files) stays penalty-based in "Design quality".
6. **Extensible.** Add a new review dimension to the prompt → it auto-appears as a scoring dimension. No code changes needed. More dimensions assessed → more weight in overall score.
