# Plan: Fix Inconsistent Segment Generation After Keyframe Replacement

## Why it's inconsistent

When the user replaces a keyframe (delete → add new image), there are two issues, one of which is timing-dependent.

### Root cause 1 (inconsistent): Race condition in `waitForPendingMutations`

`generateVideoService.ts` calls `waitForPendingMutations` before fetching fresh `shot_generations` data. The current implementation:

```ts
// ~ line 225 of generateVideoService.ts
const pendingMutations = mutationCache.getAll().filter(m => m.state.status === 'pending');
if (pendingMutations.length > 0) {
  await new Promise(resolve => setTimeout(resolve, 1000)); // flat 1-second sleep
}
```

**The race:**
- User adds new image B' → `addImageToShotMutation` starts (status = `pending`)
- User clicks "Generate All" quickly → `waitForPendingMutations` detects pending mutation → sleeps 1 second
- On a fast connection, the insert completes in ~200ms → the 1-second wait is more than enough → `fetchFreshShotGenerations` sees new image ✓
- On a slow connection (or DB under load), the insert takes >1 second → sleep expires, mutation still in-flight → `fetchFreshShotGenerations` misses the new image → task created with wrong/missing `pairShotGenerationIds` → wrong number of segments silently created ✗

Additionally, if the user clicks Generate AFTER the mutation completes (common case), no pending mutations are detected → no sleep at all → works fine. This explains why it usually works.

**This is the primary source of inconsistency.** Fast connection = almost always works. Slow connection = fails occasionally.

### Root cause 2 (consistent, confusing UX): demote fires at wrong time

`demote_orphaned_video_variants` is called after DELETE but that's too early — at that point the old `shot_generations` row still exists with the same `generation_id`, so the mismatch check is a no-op. The demote only becomes meaningful after the NEW image is added (now a different `generation_id` occupies the position), but `demoteOrphanedVariants` is never called after ADD. Old segments remain visible in their slots, making it unclear which pairs need regeneration.

This is consistent (always happens) but not a hard blocker — "Generate All" still works, just after seeing confusing stale thumbnails.

## Fix 1 — Proper mutation draining (fixes the inconsistency)

**File:** `src/tools/travel-between-images/components/ShotEditor/services/generateVideoService.ts`

Replace the 1-second heuristic with a polling loop on `queryClient.isMutating()`:

```ts
async function waitForPendingMutations(queryClient: QueryClient, timeoutMs = 5000): Promise<void> {
  const start = Date.now();
  while (queryClient.isMutating() > 0) {
    if (Date.now() - start > timeoutMs) break;
    await new Promise(resolve => setTimeout(resolve, 50));
  }
}
```

`queryClient.isMutating()` returns the count of currently running mutations. The loop polls every 50ms and exits when all mutations settle or the 5-second timeout is hit. This guarantees `fetchFreshShotGenerations` sees fully committed data.

## Fix 2 — Call demoteOrphanedVariants after image add (fixes the UX confusion)

**File:** `src/tools/travel-between-images/components/ShotEditor/hooks/useDropActions.ts`

After `addImageToShotMutationRef.current.mutateAsync` resolves in both `handleTimelineGenerationDrop` and `handleBatchGenerationDrop`, call `demoteOrphanedVariants(shotId, 'image-add')`. Also add it to the file/batch drop paths.

`useDemoteOrphanedVariants` should be imported and referenced via a ref (same pattern as `useDeleteActions.ts`).

**Why this fixes it**: After the new image lands, `demote_orphaned_video_variants` now detects `current_gen_id ≠ stored_gen_id` and clears `location`/`thumbnail_url`/`primary_variant_id` on stale segments. Slots that need regeneration show as blank rather than showing wrong old video.
