## Is this codebase beautiful? 

**No, but it's closer than most.** There's real craft here — some parts are genuinely elegant, and the overall direction is clearly towards something good. But it's not beautiful yet because it's caught between two states: the messy reality of rapid product evolution and the clean architecture it's clearly aspiring to. Let me break down what's working and what's not.

---

### What IS beautiful

**The provider composition pattern** — `AppProviders.tsx` is 55 lines of clarity. `composeProviders()` is elegant, the ordering is deliberate, and a new developer instantly understands the dependency tree.

**ShotsContext** — 85 lines. Does one thing. Handles project transitions gracefully. Memoizes correctly. This is the Platonic ideal for your contexts.

**The params-driven routing in `complete_task`** — Instead of a giant switch on task type, callers declare intent via params at task creation time. The edge function just reads the params and routes. This is a genuinely good architectural decision that eliminated an entire category of coupling.

**Query key organization** — 12 domain-specific modules, centrally aggregated, hierarchically structured with `as const`. Clean, discoverable, consistent.

**Type safety discipline** — Only 12 `as any` casts in 1,500+ files. That's exceptional for a codebase this size. The team clearly values type safety and hasn't taken shortcuts.

**Tool registration manifest** — `tools/index.ts` with `toolsManifest` and `toolsUIManifest` is a nice pattern that separates settings concerns from UI display concerns.

---

### What prevents beauty

**1. The shared/ boundary is fiction**

The biggest structural problem. `shared/` is supposed to be tool-agnostic reusable code, but it's riddled with tool-specific logic:

- `shared/components/JoinClipsSettingsForm/` — an entire tool-specific form in shared
- `shared/hooks/useShareGeneration.ts` — hardcoded `travel_between_images` setting key access
- `shared/lib/tasks/travelBetweenImages/` — 881 lines of travel-tool task builders
- `shared/lib/tasks/joinClips.ts` — 442 lines of join-clips task builders
- `shared/lib/joinClipsDefaults.ts` — with a comment admitting the boundary problem:
  > *"Join Clips defaults — shared so that both shared/lib/tasks/ and tools/join-clips/ can import without creating a backwards shared → tools dependency."*

The root cause is that task creation logic needs to be shared (called from hooks that live in shared), but the task params are inherently tool-specific. This creates a gravitational pull that drags tool logic into shared. **The abstraction boundary needs rethinking** — either task creation moves into tools (and shared hooks call into tools via indirection), or you accept that `shared/lib/tasks/` is actually a "task creation" module that's tool-aware by design and stop pretending it's generic.

**2. Two god objects masquerading as clean architecture**

- **`ImageLightbox.tsx`** (772 lines, 45+ props) — This component handles viewing, editing, inpainting, repositioning, upscaling, variant navigation, shot management, and image-to-image generation. It's been "refactored" by extracting logic into hook factories (`useImageLightboxEnvironment`, `useImageLightboxEditing`, etc.), but those hooks are tightly coupled to this one component. It's distributed complexity, not reduced complexity.

- **`useShotEditorController.ts`** (906 lines, 43 parameters, imports 17 hooks) — This is the travel tool's brain. It orchestrates images, LoRAs, settings, segments, generation, structure, audio, dimensions, and naming. Comments like "Currently unused" and "PERF FIX" reveal years of accretion. A new developer would need to read ~350 lines just to understand what state is being assembled.

Both of these need to be genuinely decomposed — not "extract hooks that are only used here" but "identify the 3-4 actual concerns and give each its own component/context boundary."

**3. `window.__GLOBALS__` as architecture escape hatches**

```typescript
window.__PROJECT_CONTEXT__ = { selectedProjectId, projects }
window.__AUTH_MANAGER__ = ...
window.__VISIBILITY_MANAGER__ = ...
window.__DATA_FRESHNESS_MANAGER__ = ...
```

These indicate real holes in the React context tree. `useProjectGenerations` falls back to reading `window.__PROJECT_CONTEXT__` when projectId isn't passed as a prop. This is the kind of thing that works until it doesn't — race conditions, stale data, impossible-to-debug state mismatches. Beautiful code doesn't need escape hatches.

**4. The settings system is over-layered**

~1,276 lines across three interconnected hooks (`useToolSettings`, `useAutoSaveSettings`, `useDebouncedSettingsSave`), plus a write queue, a resolution service, a fetch service, and a context provider. The shot→project→user→defaults resolution is conceptually clean but the implementation has accreted layers:

- Module-level deduplication state
- localStorage reads to avoid navigator.lock contention  
- A global write queue with coalescing
- Debounce logic extracted into its own 293-line hook

Each layer solves a real problem, but the stack has become hard to reason about as a whole.

**5. 398 migrations with recent emergency clusters**

The recent timeline drag feature required **7 migrations in 2 days** (Feb 18-20), including one that created functions referencing non-existent columns, immediately followed by an emergency fix migration. This reveals:
- No pre-deploy schema validation (migration 175000 broke because it referenced `generations.shot_id` which doesn't exist)
- Triggers fighting each other (BEFORE UPDATE triggers blocking user drag operations, requiring emergency drops)
- 43 triggers total, with unclear interaction semantics

The migration count itself isn't the problem — it's that the DB layer has become complex enough that changes are unpredictable.

**6. 94 shared hooks without clear organization**

Five variant hooks (`useVariants`, `useLoadVariantImages`, `useMarkVariantViewed`, `usePromoteVariantToGeneration`, `useToggleVariantStar`) that could be methods on one domain hook. Fourteen settings-related hooks. Eight generation hooks. They're all at the same level in `shared/hooks/` with no namespace or grouping beyond a few subdirectories. The naming is fine but the flat structure means you're scanning a list of 94 items to find what you need.

**7. PanesContext doing too much**

259 lines managing 3 pane lock states, 3 open states, 3 dimensions, active task tracking, mobile-specific exclusive locking, and persistence — mixing UI state, business logic, and Supabase calls in one context. Compare to ShotsContext (85 lines, one concern) and the gap is obvious.

---

### The pattern

The codebase has a clear **quality gradient**: recent abstractions (params routing, query keys, provider composition) are elegant; older/more-trafficked code (lightbox, shot editor, settings) has accreted complexity. The team knows what good looks like — ShotsContext proves that — but the highest-traffic code hasn't been brought up to that standard yet.

The single biggest thing preventing beauty: **the shared/ boundary doesn't reflect the actual dependency graph.** Tool-specific logic has leaked in, and the workarounds (window globals, defaults moved to shared, hardcoded tool names in shared hooks) are symptoms of a structural problem, not individual mistakes. Solving that would cascade into fixing most of the other issues — the god objects exist partly because so much logic needed to be "shared," and the settings complexity exists partly because settings resolution crosses the tool/shared boundary in awkward ways.
