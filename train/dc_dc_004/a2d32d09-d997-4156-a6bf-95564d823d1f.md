## Step 2: TreeSitterLangSpec Data Structure

### `desloppify/languages/framework/treesitter/__init__.py`

```python
@dataclass(frozen=True)
class TreeSitterLangSpec:
    """Per-language tree-sitter configuration."""
    grammar: str                    # tree-sitter grammar name (e.g., "go", "rust")

    # Function extraction (S-expression queries)
    function_query: str             # captures: @func (full node), @name, @body
    comment_node_types: frozenset[str]  # e.g., {"comment", "line_comment", "block_comment"}
    string_node_types: frozenset[str] = frozenset()  # for normalization awareness

    # Import extraction
    import_query: str = ""          # captures: @import (full node), @path
    resolve_import: Callable | None = None  # (import_text, source_file, scan_path) -> abs_path | None

    # Class extraction
    class_query: str = ""           # captures: @class (full node), @name

    # Logging/debug patterns to strip during normalization (regexes)
    log_patterns: list[str] = field(default_factory=lambda: [
        r"^\s*(?:fmt\.Print|log\.)",          # Go
        r"^\s*(?:println!|eprintln!|dbg!)",   # Rust
        r"^\s*(?:puts |p |pp )",              # Ruby
        r"^\s*(?:print\(|NSLog)",             # Swift
        r"^\s*(?:System\.out\.|Logger\.)",    # Java
        r"^\s*console\.",                      # JS-like
    ])
```

Each language provides its own spec instance. The `function_query`, `import_query`, and `class_query` are tree-sitter S-expression queries that use standard captures (`@func`, `@name`, `@body`, `@import`, `@path`, `@class`).

## Step 3: Generic Function Extractor

### `desloppify/languages/framework/treesitter/_extractors.py`

**Input**: file path + TreeSitterLangSpec
**Output**: `list[FunctionInfo]` (same dataclass used by Python/TS extractors)

Algorithm:
1. Parse file with `tree_sitter_language_pack.get_parser(spec.grammar)`
2. Run `spec.function_query` via `language.query()` to get all function nodes
3. For each captured `@func` node:
   - `name` = text of `@name` capture
   - `line` = `func_node.start_point[0] + 1` (1-indexed)
   - `end_line` = `func_node.end_point[0] + 1`
   - `loc` = `end_line - line + 1`
   - `body` = source bytes from `func_node.start_byte` to `func_node.end_byte`
   - `normalized` = body with comment nodes removed (see `_normalize.py`), blank lines stripped, log lines stripped
   - `body_hash` = `md5(normalized.encode()).hexdigest()`
   - `params` = extract parameter names from function's parameter list child node
4. Filter: skip if `len(normalized.splitlines()) < 3` (matches Python/TS extractors)

### `_normalize.py` — AST-aware normalization


This is more accurate than regex-based comment stripping because tree-sitter knows exactly where comments are, even in tricky cases (comments inside strings, multi-line comments, etc.).

### Parameter extraction

Walk the function node's children to find the parameter list node (usually `parameters`, `parameter_list`, or `formal_parameters`). For each parameter child, extract the identifier name. This handles destructuring, default values, and type annotations automatically since we just need the name node.

## Step 5: Generic Dep Graph Builder

### `desloppify/languages/framework/treesitter/_imports.py`

**Input**: scan path + TreeSitterLangSpec + file list
**Output**: `dict[str, dict[str, Any]]` (same format as Python/TS dep graphs)

Algorithm:
1. For each source file:
   - Parse with tree-sitter
   - Run `spec.import_query` to get import nodes
   - For each `@path` capture, extract import text
   - Call `spec.resolve_import(import_text, source_file, scan_path)` to resolve to absolute file path
   - Skip if `resolve_import` returns `None` (external package)
2. Build graph dict: for each file, populate `imports` set and `importers` set
3. Call existing `finalize_graph()` from `graph.py` to add counts

### Per-language import resolvers

Each language gets a `resolve_import` function. Categories:

**Relative path imports** (straightforward):
- **Ruby**: `require_relative "./foo"` → resolve `./foo.rb` relative to source
- **Elixir**: `import MyApp.Module` → resolve to `lib/my_app/module.ex`
- **Lua**: `require("foo.bar")` → try `foo/bar.lua` relative to scan path

**Project-local imports** (need to understand project structure):
- **Go**: `import "myproject/pkg/foo"` → resolve relative to `go.mod` module path
- **Rust**: `use crate::module` → resolve to `src/module.rs` or `src/module/mod.rs`
- **Java**: `import com.example.Foo` → resolve to `com/example/Foo.java` relative to source root
- **Kotlin**: same as Java
- **Swift**: no file-level imports (module-based) — resolver returns None
- **C/C++**: `#include "local.h"` → resolve relative to source, skip `<system.h>`
- **PHP**: `use App\Models\User` → resolve via PSR-4 (autoload mapping in composer.json)

**Not feasible** (return None for all):
- **Haskell**: module system is build-tool-dependent
- **Scala**: similar to Java but with SBT complications
- **Clojure**: namespace-based, build-tool-dependent
- **Bash**: `source ./script.sh` is easy, but PATH-based sourcing is not

For the first implementation, focus on the **easy wins**: Go, Rust, Ruby, Java, Kotlin, C/C++ relative includes, Lua. Others return `None` and the dep graph stays empty for them (coupling phases produce no findings, which is correct — better than wrong).

```python
        extract_fn = make_ts_extractor(treesitter_spec)
```

## Improvements to existing tree-sitter integration

1. **Parse tree caching**: Currently each phase (functions, imports, classes) re-parses every file. We could cache parse trees per-file during a scan, like the existing `enable_file_cache()` pattern in utils.py. Would cut parse time by 2-3x for languages that run multiple phases.

2. **AST-based complexity**: Right now `_make_structural_phase()` uses indent-based nesting depth from `phases_common.py`. Tree-sitter can give exact nesting depth by walking the AST for block nodes (`if`, `for`, `while`, `match`, etc.) — more accurate, especially for languages with different bracket styles.

3. **God class detection**: We extract classes via `ts_extract_classes()` but don't currently feed that into a god class detector for generic plugins. The Python/TS plugins do this. Could count methods per class using tree-sitter.

4. **Better import resolution for existing languages**:
   - **Haskell**: Could resolve `import Data.Map` → local modules if the project uses Cabal/Stack
   - **Bash**: Could resolve `source ./foo.sh` and `. ./bar.sh`
   - **Perl**: Could resolve `use MyApp::Module` → `lib/MyApp/Module.pm`
   - **Zig**: Could resolve `@import("foo.zig")` to local files

5. **Tree-sitter-powered smell detection**: Instead of regex patterns, use AST queries for things like:
   - Empty catch/except blocks (cross-language)
   - Unused parameters (compare declared params to body references)
   - Magic numbers in function bodies
   - Deep nesting (exact AST depth vs indent-heuristic)

6. **Cross-language dead export detection**: For languages with export syntax (Go exported = capitalized, Rust `pub`, etc.), tree-sitter can identify exports and cross-reference with importers from the dep graph.

7. **Naming convention detection**: Tree-sitter captures function/class/variable names. Could detect naming convention mismatches (e.g., camelCase function in a snake_case codebase) generically.
