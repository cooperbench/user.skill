# Plan: Narrative Enforcement, Generic Reminders, and Badge Integration

## Context

1. **No enforcement** — SKILL.md weakly says "read query.json" but doesn't make it a MUST. The LLM (me) might just parse terminal output and never read the narrative. No terminal nudge points to query.json.

2. **No generic reminders** — Some things should be called out every time regardless of phase (auto-fixers available? rescan after fix? score above 90 → add badge to README?). Currently nothing surfaces these.

3. **Missing badge.py** — `desloppify/badge.py` exists on the remote `main` branch but is missing from this branch (`fix/windows-cross-platform`). It generates `scorecard.png` after each scan and recommends adding it to README. The scan.py on main already calls `generate_scorecard()` and shows the README suggestion. This feature needs to be pulled onto this branch.

Additionally, the narrative should integrate with the badge: when strict > 90, the narrative should recommend adding the scorecard badge to the README (if it's not already there).

### 2. Add `reminders` list to narrative output

Add a new `_compute_reminders()` function in `narrative.py` that returns a list of contextual reminders. These are generic things that should be surfaced every time, computed from the current state:

```python
def _compute_reminders(state, diff, lang, phase, debt, actions) -> list[dict]:
```

Each reminder has `{"type": str, "message": str, "command": str | None}`.

**Always-on reminders (when applicable):**
- `auto_fixers_available` — When there are open findings with auto-fixers AND the fixer hasn't been run recently: "N findings are auto-fixable. Run `desloppify fix <fixer> --dry-run`."
- `rescan_needed` — After a fix or resolve: "Rescan to verify — cascading effects may create new findings."
- `badge_recommendation` — When strict >= 90 and README doesn't reference scorecard.png: "Score is above 90! Add the scorecard to your README: `<img src=\"scorecard.png\" width=\"400\">`"
- `wontfix_growing` — When debt trend is "growing": "Wontfix debt is growing. Review stale decisions: `desloppify show --status wontfix`"
- `stagnant_nudge` — When any dimension is stuck for 3+ scans: "{Dimension} has been stuck for {N} scans. Try a different approach."
- `dry_run_first` — When the top action is auto_fix: "Always --dry-run first, review changes, then apply."

The reminders list goes into the narrative dict and into query.json.

### 4. Add terminal nudge line

After every command's `_write_query()`, print a short reminder that nudges the LLM to read query.json. This goes in `_write_query()` itself in `cli.py` so it's automatic:

```python
def _write_query(data: dict):
    QUERY_FILE.parent.mkdir(parents=True, exist_ok=True)
    QUERY_FILE.write_text(json.dumps(data, indent=2, default=str) + "\n")
    # Nudge LLM to read the structured output
    import sys
    print(f"  → query.json updated", file=sys.stderr)
```

This is minimal (1 line, stderr) but gives the LLM a visible signal.

## ast-grep vs desloppify: Practical Comparison

### What ast-grep is

A Rust-based structural code search tool using tree-sitter. It matches AST patterns rather than text. Think "grep but for syntax trees." It has a Python library (`ast-grep-py`) that works well.

### Head-to-head results on our codebase (71 Python files)

| Detector | Our approach | Our results | ast-grep results | Winner |
|----------|-------------|-------------|-----------------|--------|
| **Unused imports** | ruff subprocess (F401) | 2 | Can't do (needs scope analysis) | **Us** |
| **Monster function** | AST `end_lineno - lineno` | 1 (178 LOC) | 1 (177 LOC) | **Tie** |
| **Global keyword** | regex `^\s+global\s+\w+` | 1 | 1 | **Tie** |
| **Deferred imports** | AST: import inside FunctionDef | 110 | 205 (15 `import` + 190 `from`) | **ast-grep** (more) |
| **Large files** | line count | 10 (threshold 300) | 3 (threshold 500) | Same (different thresholds) |
| **Complexity: params** | regex param counting | 6 high-param fns | 6 high-param fns | **Tie** |
| **Complexity: nesting** | indentation counting | 10 files | Can't do (no counting) | **Us** |
| **Bare except** | regex `^\s*except\s*:` | 0 | 0 | Tie |
| **Broad except** | regex `^\s*except\s+Exception` | 0 | 0 | Tie |
| **Mutable defaults** | regex `def\s+\w+\([^)]*=\s*\[\]` | 0 | 0 | Tie |
| **f-string no expr** | Not detected | 0 | **10 findings** | **ast-grep** (new) |
| **Nested try** | Not detected | 0 | **1 finding** | **ast-grep** (new) |
| **Import cycles** | Tarjan's SCC on dep graph | Yes | Can't do (single-file) | **Us** |
| **Orphaned files** | Dep graph importer_count=0 | Yes | Can't do (single-file) | **Us** |
| **Duplicates** | Hash + difflib similarity | Yes | Can't do | **Us** |
| **Coupling** | Dep graph path analysis | Yes | Can't do | **Us** |

### Key findings

**1. ast-grep can't do the hard stuff.** Our most valuable detectors — unused (ruff), cycles, orphaned, coupling, duplicates — all require either cross-file analysis, scope analysis, or graph algorithms. ast-grep is purely syntactic, single-file, no scope. These are non-starters.

**2. ast-grep found things we missed.** Two categories we don't detect:
- **f-strings with no interpolation** (10 instances) — `f"plain string"` should just be `"plain string"`. Easy win, low severity.
- **Nested try blocks** (1 instance) — structural smell we don't look for.

**3. Deferred imports: ast-grep found more (205 vs 110).** Our AST-based detector found 110, ast-grep found 205. The difference: our detector specifically filters to only count distinct functions (grouping multiple imports per function into one finding with a count), while ast-grep counts every individual import statement. Our approach is actually better for reporting — "4 deferred imports in `_resolve_lang`" is more actionable than 4 separate findings.

**4. The `inside` gotcha is a real problem.** Without `stopBy: "end"`, the `inside` rule doesn't traverse through intermediate blocks (if/for/with/etc.). My first run returned 0 deferred imports because of this. This is an easy mistake to make and the error is silent (just returns fewer results). Our regex/AST approaches don't have this footgun.

**5. Pattern fragments don't work for many Python constructs.** `except Exception:`, `except:`, and other clause-level patterns can't be parsed as standalone code. You have to fall back to `kind` + `regex` rules, which is basically regex with extra steps. For Python, this negates much of the "structural matching" advantage.

**6. The Python library is alpha-quality.** The `not` keyword conflicts with Python (`not_` workaround), the `field` parameter on `has` rules is underdocumented, and error messages are cryptic Rust backtraces.

### Where ast-grep could add value

The sweet spot is **new smell patterns that are structural but don't need scope/cross-file analysis**:

- f-strings with no expressions (found 10)
- Nested try blocks (found 1)
- `== None` instead of `is None` (0 in our codebase, but a real smell)
- `== True`/`== False` comparisons
- Empty function bodies (dead stubs)
- Class definition inside function (found 0, but detectable)

These could be added as ast-grep-based smells in our existing detector. But honestly, most of these are also easy to detect with Python's built-in `ast` module or even regex — and we already have the infrastructure for that.

### Should we use it?

**For Python: No.** The cost-benefit doesn't work out.
- Our regex + `ast` module + ruff approach covers everything ast-grep can do, plus everything it can't (scope, cross-file, metrics).
- Adding ast-grep as a dependency adds complexity and a Rust binary/wheel for marginal gains (f-string no-expr, nested try).
- The Python library is alpha, has keyword conflicts, and the `stopBy` gotcha is a correctness risk.
- We could just add the 2 new smell patterns (f-string, nested try) using our existing regex/AST infrastructure.

### 1.1 No Atomic Writes -- Data Loss Risk
**File:** `/user_c042661f/Documents/desloppify/desloppify/state.py:39-40`

`Path.write_text()` truncates the file first, then writes. tmp.write(json.dumps(state, indent=2, default=str) + "\n")
```python
tmp.flush()
os.fsync(tmp.fileno())
tmp.close()
os.replace(tmp.name, str(p))
```

# The Synthesis: Systems Rigor Meets Design Clarity

Both reviewers agree on more than they disagree. The architecture is sound, the ambition is genuine, and the language plugin system is well-designed. Where they diverge is on *what to fix first* — correctness vs. coherence. Here's how to balance them.

## Where Both Agree (Do These First)

**1. Kill the dual scoring system.**
The systems engineer flags that `TIER_WEIGHTS` is defined twice in two files, the legacy `_weighted_progress` creates a parallel code path, and the empty-codebase-scores-100 edge case. The artistic engineer says the user sees four numbers on one line and doesn't know which to care about, and showing a "legacy" score with a warning that it's unreliable teaches distrust.

*Resolution:* Remove the legacy scoring fallback. One score. If potentials aren't available, show only findings count. This reduces code surface, eliminates the duplication, and simplifies the user experience in one move.

**2. Fix the `_extra_exclusions` import binding bug.**
This is the systems engineer's most important find — it's a live correctness bug. Python `from X import Y` binds at import time, so `set_exclusions()` in utils.py rebinds the name in utils but `unused.py` still sees the original empty tuple. `--exclude` is silently broken for Python unused import detection.

*Resolution:* Change `unused.py` to import the module and access the attribute: `from ....utils import utils; ... utils._extra_exclusions`. Or better, pass exclusions explicitly as a parameter.

**3. Make state persistence robust.**
Non-atomic writes + no corruption recovery = data loss risk. This is the kind of thing you don't notice until it bites you, and then you lose all historical data. The artistic engineer didn't flag this because it's invisible to the user experience — until it isn't.

*Resolution:* Write-to-temp-then-rename, plus `try/except JSONDecodeError` with a warning on load.

## Where They Productively Disagree

**4. The narrative: dossier vs. story.**
The systems engineer treats the narrative as data infrastructure — it should be typed, well-structured, and complete. The artistic engineer says it's *too* complete: "A good coach says one thing." Both are right at different layers.

*Resolution:* Keep the full dossier in `query.json` (the LLM needs it), but radically simplify what prints to the terminal. The scan should show: diff one-liner, score delta, headline. That's it. `status` is the dashboard. `next` is the action. The narrative data layer stays rich; the presentation layer gets sparse.

**5. SKILL.md: programming vs. micromanaging.**
The artistic engineer says SKILL.md tries to control how the LLM talks ("When auto-fixers exist, ask why they haven't been run") and that's patronizing. The systems engineer doesn't comment on this, but the untyped dict problem they flag is related — the LLM is interpreting unstructured data guided by prescriptive prose instead of self-describing typed data.

*Resolution:* Strip the behavioral prescriptions from SKILL.md. Keep the command reference and data schema. Give the LLM data with clear semantics (rename "potentials" to "checks", use typed fields), and trust it to frame the conversation. The `reminders` field stays but becomes advisory context, not a script.

**6. Reminder decay.**
The artistic engineer notes reminders have no learning curve — "Always --dry-run first" shows up every single time. The systems engineer doesn't address this, but would probably note that implementing decay requires tracking state (which reminders have been shown, how many times).

*Resolution:* Simple approach: add a `reminder_history` to state tracking which reminder types have been shown. After 3 occurrences, suppress. Don't over-engineer this — a counter per type is sufficient.

## The Ideal Balance

The systems engineer is right that **correctness comes before polish**. The import binding bug means `--exclude` is silently broken. Non-atomic writes mean data loss. These undermine user trust in ways no amount of narrative coaching can fix.

The artistic engineer is right that **simplicity is the highest form of sophistication**. 19 concepts, four numbers on one line, and a SKILL.md that scripts the LLM's personality — these are the things that make a tool feel *heavy* instead of *helpful*.

The ideal sequence:

1. **Fix the bugs** (P0 systems): atomic writes, corruption recovery, `_extra_exclusions`, `QUERY_FILE` path
2. **Simplify the interface** (P0 artistic): kill dual scoring, sparse scan output
3. **Improve accuracy** (P1 systems): eval_exec lookbehind, iterative Tarjan's, multi-line imports
4. **Refine the feel** (P1 artistic): `next` as star, SKILL.md cleanup, rename potentials
5. **Performance and architecture** (P2-P3 systems): content cache, exclusion matching, TypedDict migration
6. **Polish** (P2-P3 artistic): emotional tone, reminder decay, concept consolidation

The systems engineer keeps you from shipping broken software. The artistic engineer keeps you from shipping software nobody wants to use. The answer is: fix what's broken, then simplify what's confusing, then optimize what's slow. In that order.

- **TypeScript**: `*.test.ts`, `*.spec.ts`, `*.test.tsx`, `*.spec.tsx`, `__tests__/`, `*.stories.tsx`

| Approach | Effort | Tradeoff |
|----------|--------|----------|

| **Run test files at a higher threshold** (e.g. 0.95 vs 0.80) | Medium | Catches truly identical tests while suppressing structural similarity |

## The Root Problem

Desloppify treats the codebase as a flat surface. Every file is a string path. Every finding has equal weight. The system has **no concept of intent** — it doesn't know *what kind of code* it's looking at.

This produces false positives not as a bug but as an architectural inevitability. You can't distinguish "deliberate repetition in tests" from "copy-paste in production" when your data model doesn't carry the distinction.

## Four Root Causes

### 1. File identity is discarded at discovery

`find_py_files()` and `find_ts_files()` return bare path strings. The path *contains* rich semantic information — is this a test? config? generated? — but it's never extracted. By the time `detect_duplicates()` receives a `FunctionInfo`, it literally cannot tell test code from production code because the dataclass has no field for it.

### 2. The homogeneity assumption

Every detector runs on every file with identical thresholds. `_ts_extract_functions` filters `node_modules` and `.d.ts` but not `.test.ts`, `.spec.ts`, or `__tests__/`. The dupes detector's only suppression heuristic is "skip pairs where both functions are <8 LOC." There's no concept of "these two functions are in test files and share a common test pattern."

The scoring system amplifies this — a test-file false positive degrades the Duplication dimension score identically to a real production duplicate. The narrative system then pushes the user toward fixing duplicates that aren't problems.

### 3. The parser asymmetry

Python detectors use `ast.parse` — a real parser with `_build_string_line_set` and `_match_is_in_string` to filter false positives. TypeScript detectors use regex on raw text with **zero context filtering** for the simple checks (`any_type`, `hardcoded_url`, `magic_number`, etc.). The brace-tracking helpers handle strings for their specific constructs, but the simple regex checks do not. This creates a structural false positive floor for TS that Python doesn't have.

### 4. The feedback void

When users mark `false_positive`, the status is recorded but never fed back. The next scan produces the same class of false positive. The system doesn't track per-detector FP rates, doesn't suggest ignore patterns, doesn't adjust confidence. Every scan is as naive as the first.

## The Trust Equation

This is the design insight that ties it together: **every false positive costs more trust than a true positive earns**. When a user sees 30 duplicate findings and 25 are test files, they don't think "5 real issues found." They think "this tool doesn't understand my codebase." And when an LLM agent sees those findings, it confidently refactors test utilities that were deliberately duplicated for isolation.

## The Design Principle That's Missing

**Quiet confidence**: A credible tool would rather say nothing than say something wrong. Precision is the primary constraint; recall is secondary. Miss a real issue? The next scan catches it. Report a false positive? Trust erodes permanently.

## The Architectural Fix

Both perspectives agree on the same structural change — **zone classification as a first-class concept**:

| Layer | Change | What it solves |
|-------|--------|----------------|
| **File discovery** | Return `FileInfo(path, zone, lang)` instead of bare strings. Zone = production/test/config/generated/story. Classified once, flows everywhere. | RC1 |
| **Detection policy** | `(detector, zone)` → threshold overrides. `(dupes, test)` → skip or threshold=0.95. `(smells, test)` → suppress hardcoded_url, magic_number. | RC2 |
| **Finding metadata** | `make_finding()` gets a `zone` field. Scoring applies zone-aware confidence dampening. | RC2 + scoring |
| **TS line classifier** | Pre-pass that marks each line as code/comment/string/template, like Python's `_build_string_line_set`. Applied to all regex-based TS checks. | RC3 |
| **Feedback loop** | Track FP rate per `(detector, zone)`. After threshold, auto-suggest ignore rules or confidence downgrade. | RC4 |

The key insight: **zone classification should happen once and flow through as metadata, not be replicated as ad-hoc filtering in every detector.** The `LangConfig` already has `entry_patterns`, `exclusions`, etc. It needs a `classify_zone(path) → str` method that all downstream consumers inherit.

This isn't bolting on a test-file filter. It's giving the system a model of intent so it can reason about what kind of code it's looking at — which is what a good engineer does instinctively and what the tool currently cannot do at all.
