## Registry entries (registry.py:111-118)

Two detector names in the `# ── Subjective review` section:

| Detector | Display | Dimension | Action Type | Purpose |
|---|---|---|---|---|
| `review` | "design review" | Review coverage | refactor | Per-file AI findings imported back into state |
| `subjective_review` | "subjective review" | Review coverage | manual_fix | Tracks which files still need review |

## How it works

The system is split into **two layers**:

### 1. Per-file review (`review.py`)
- **11 dimensions**: naming_quality, comment_quality, error_consistency, convention_outlier, abstraction_fitness, logic_clarity, contract_coherence, initialization_coupling, logging_quality, type_safety, cross_module_architecture
- `prepare_review()` gathers codebase context (naming vocabulary, error conventions, module patterns, import graph, sibling conventions) and selects priority files based on blast radius + existing findings
- Outputs a structured prompt + file batches for an AI agent — **no LLM calls happen in this module**
- Agent returns findings + per-dimension **assessments** (0-100 scores) that feed into scoring
- `import_review_findings()` merges agent output back into state as `detector="review"` findings

### 2. Holistic (codebase-wide) review (`review.py:1088+`)
- **8 dimensions**: cross_module_architecture, initialization_coupling, convention_outlier, error_consistency, abstraction_fitness, dependency_health, test_strategy, api_surface_coherence
- Looks at patterns **across** files — god modules, sibling behavior outliers, mixed error strategies, util dumping grounds, etc.
- Builds 4 parallelizable investigation batches
- Holistic findings have no single `file` — stored as `file="."` with `detail.related_files`

### 3. Review coverage detector (`detectors/review_coverage.py`)
- Runs every scan — flags production files that are **unreviewed**, **stale** (>30 days), or **changed** since last review
- Also checks if a holistic review is needed (never run, stale, or >20% file count drift)

### 4. Issues work queue (`issues.py`)
- Lists open review findings sorted by weight
- Supports investigation notes on findings
- Auto-expires stale holistic findings after 30 days

The key insight: the programmatic detectors (unused, smells, security, etc.) use regex/AST analysis. The subjective detectors **prepare structured context and prompts** for an external AI agent, then import its structured JSON findings back into the same state/scoring pipeline. The review coverage detector then tracks freshness so the system knows when to re-review.

## New holistic dimensions worth adding

### 1. `incomplete_migration`
**The half-finished refactor problem.** Old pattern + new pattern coexisting indefinitely.

- Two HTTP clients (axios in old code, fetch in new code)
- Some files use the new logger, others still use `console.log`
- Partial TypeScript migration (`.js` and `.ts` siblings doing the same thing)
- Deprecated wrapper still called by 40% of the codebase
- Compatibility shims that outlived their purpose (nobody calls the old way anymore)

**Context to gather**: detect file pairs where old+new patterns coexist. Count usages of deprecated symbols vs their replacements. Find `@deprecated`/`# deprecated` markers and measure caller counts. Look for pattern A dominant in recent files, pattern B dominant in older files.

### 2. `domain_language_consistency`
**Same concept, different words across modules.** This is semantic, not syntactic — distinct from `convention_outlier` which catches camelCase vs snake_case.

- One module calls it `user`, another calls it `account`, a third calls it `member` — all meaning the same entity
- `create` vs `add` vs `insert` vs `new` used interchangeably for the same operation
- A type defined in two places with different field names for the same data
- API calls it `projectId`, DB calls it `project_id`, state calls it `activeProject`
- Function `getUser` in one module, `fetchUser` in another, `loadUser` in a third — all hitting the same endpoint

**Context to gather**: extract noun/verb vocabulary per module boundary. Cluster synonyms. Compare type/interface field names across modules that clearly represent the same domain entity (detected via import chains).

### 3. `configuration_coherence`
**Where do the knobs live?**

- Defaults buried 4 layers deep in implementation code instead of at the boundary
- Same timeout value hardcoded in 6 different files (not a constant)
- Mix of mechanisms: some things read env vars, some read a config file, some are CLI args, some are hardcoded — no pattern to which is which
- Environment-specific behavior (`if process.env.NODE_ENV === 'production'`) scattered throughout business logic instead of at init
- Feature flags with no cleanup strategy — toggle code accumulating with no way to know what's still experimental

**Context to gather**: find all env var reads, config file reads, hardcoded magic numbers/strings. Map which mechanism each module uses. Detect duplicate literal values across files (candidate constants). Find `if (env === 'production')` patterns and where they live.

### 4. `data_flow_integrity`
**Multiple sources of truth for the same data.**

- Same entity fetched independently by sibling components instead of shared
- Derived state computed differently in different places (subtotal calculated two ways)
- Cache invalidation in one layer but not another (stale reads)
- Transform/normalize happening at 3 different points in the pipeline
- Write paths that update one store but not another (eventual consistency that never converges)

**Context to gather**: trace entity types through the import graph. Find where the same type is constructed/modified. Detect parallel fetch calls for the same resource. Look for duplicate transformation logic on the same data shape.

### 5. `boundary_discipline`
**Is logic in the right layer?** Overlaps slightly with `cross_module_architecture` (which catches god modules and circular deps) but focuses on *where responsibilities live*.

- Business rules in UI components (validation logic in a React component instead of a shared validator)
- Data access logic in API handlers instead of a repository/service layer
- Presentation formatting in the data layer (date formatting in a model)
- Authorization checks in some endpoints but not sibling endpoints
- Cross-cutting concerns (auth, logging, rate limiting) implemented ad-hoc per module instead of as middleware/decorator

**Context to gather**: classify files by layer (presentation/business/data/infra). Detect business-logic keywords (validate, calculate, authorize) in presentation-layer files. Find sibling endpoint handlers with inconsistent middleware stacks. Look for the same concern (auth check, input validation) implemented inline in some places and as shared middleware in others.

### 6. `observability_gap`
**Can you debug this in production?**

- Critical paths (payment, auth, data migration) with zero logging
- Async flows with no correlation ID — can't trace a request across modules
- Error messages that say "something went wrong" with no context
- Inconsistent log levels: one module logs every function entry at INFO, neighbor logs nothing
- Missing cleanup/finally blocks on resource acquisition (connections, file handles, locks)

**Context to gather**: map logging density per module. Find high-importer files with zero log statements. Detect try/catch blocks with no logging in the catch. Find async chains and check for correlation ID propagation. Compare log-statement density across sibling modules.

### 7. `concurrency_model`
**Mixed async paradigms fighting each other.** (Mostly relevant to TS/JS, but Python has similar issues with threads vs asyncio.)

- Callbacks, Promises, and async/await all in the same codebase with no migration direction
- `setTimeout` used for synchronization instead of proper awaiting
- Fire-and-forget promises (no `.catch`, no `await`) — errors silently swallowed
- Shared mutable state accessed from concurrent paths without protection
- Missing cancellation propagation (user navigates away but HTTP requests keep going)

**Context to gather**: count callback vs Promise vs async/await usage per module. Find unhandled promise patterns. Detect `setTimeout`/`setInterval` used as synchronization. Find shared mutable module-level state accessed from async functions.

## Security: Holistic dimensions

### `authorization_consistency`
**The RLS gap problem — not that policies are weak, but that coverage is uneven.**

- Tables with RLS enabled vs. tables without — the gap *is* the vulnerability. `users` has RLS, but `user_settings` or `user_tokens` doesn't
- Junction/association tables missing policies (`team_members` has RLS, `team_invites` doesn't)
- SELECT policy exists but UPDATE/DELETE don't — partial CRUD coverage
- Policy conditions that diverge across related tables: user can read their `orders` but not the `order_items` within those orders
- Supabase-specific: some queries go through anon key (RLS enforced), others use service role (RLS bypassed) — and the split doesn't follow a clear pattern
- API endpoint siblings where some check auth middleware and others don't
- Permission granularity mismatch: some endpoints check role, some check specific permission, some check nothing

**What to look for**: "show me every table/endpoint and its auth coverage" — the interesting signal is the *gaps between siblings*, not any single missing policy.

**Context to gather**: enumerate all tables referenced in queries, map which have RLS policies vs which are accessed via service role. Enumerate all API route handlers, map which use auth middleware. Flag siblings with inconsistent coverage.

### `trust_boundary_integrity`
**User input flowing to dangerous sinks across module boundaries — invisible in any single file.**

- Frontend computes a value (price, permission, discount), backend trusts it without re-validating
- External API response deserialized and passed straight to DB write in another module
- File upload content type trusted from the client, used in a different module to determine processing
- URL parameters passed through 3 modules before hitting an SQL query — each module assumes "someone else validated"
- Internal service-to-service calls with no authentication (implicit network trust)

**Context to gather**: trace data provenance across the import graph. Find entry points (API handlers, event listeners) and trace parameters through function calls to sinks (DB queries, shell commands, file writes, HTML rendering). Flag paths where no validation happens between source and sink.

### `secret_lifecycle`
**Not "is there a hardcoded secret" (the per-file detector catches that) — but "is the overall secret management strategy coherent?"**

- Some secrets in env vars, some in a config file, some in a secrets manager — no principle governing which goes where
- API keys with no rotation strategy (same key in prod for 2 years)
- Service account credentials shared across environments (staging key = prod key)
- Secrets loaded at module scope (cached forever) vs. fetched per-request (inconsistent staleness)
- `.env.example` drifted from actual `.env` — new devs get a broken setup or skip required secrets

**Context to gather**: inventory all secret access patterns (env var reads, secrets manager calls, config file reads). Map which mechanism each module uses. Detect drift between `.env.example` and actual secret references in code.

## LLM Hallmarks: `ai_generated_debt`

This one is rich. The telltale signs that code was generated by an LLM and pasted in without cleanup. These are individually small but *systemically* they bloat and obscure a codebase.

### Restating comments
The single biggest tell. Comments that add zero information:

```python
# Increment the counter
counter += 1

# Check if the user exists
if user is not None:

# Return the result
return result
```

Also: step-by-step numbered narration (`// Step 1: Validate input`, `// Step 2: Process data`, `// Step 3: Return result`) — reads like an LLM explaining its thinking process.

**Signal**: comment tokens overlap with the tokens on the immediately following line. High comment-to-code ratio with low information density.

### Nosy debug logging
Trace-level logging that an LLM adds "to be helpful":

```typescript
console.log('Entering processOrder');
console.log('order:', JSON.stringify(order, null, 2));
// ... 5 lines of actual logic ...
console.log('Order processed successfully');
console.log('result:', JSON.stringify(result, null, 2));
```

- Entry/exit bracketing: `Entering X` / `Exiting X`
- Logging every parameter on function entry
- `JSON.stringify(x, null, 2)` dumps of entire objects
- Sequential logs that should be one structured log event
- Debug logs left in production code paths (not behind a debug flag or log level)

**Signal**: log density per function. Functions with >2 console.log/print statements per 10 LOC. Entry/exit log pairs.

### Defensive overengineering
Code that protects against things that can't happen:

```typescript
// TypeScript: value is typed as string, not string | undefined
if (value !== undefined && value !== null && value !== '') {
  // ... use value
}
```

- Try-catch wrapping calls that can't throw (pure math, string concat)
- Null checks on values guaranteed non-null by the type system or control flow
- Fallback defaults that can never be reached (`value ?? 'default'` where value is always set 3 lines above)
- Input validation on internal functions only called from one already-validated site
- `|| []` / `|| {}` on values that are initialized as arrays/objects and never reassigned

**Signal**: ratio of guard clauses to actual logic. Null checks on non-nullable types. Try-catch density on non-I/O code.

### Structural tells
- `const result = doThing(); return result;` instead of `return doThing();` — the "explaining my work" pattern
- Wrapper functions that add nothing (call another function with identical args)
- Single-use helper extracted into its own function "for clarity" but called once, 3 lines away
- Overly generic names: `processData`, `handleEvent`, `doOperation`, `performAction`
- Configuration objects with 8 optional fields, 7 of which are never set
- Identical error handling blocks copy-pasted instead of extracted
- Variable declared, immediately assigned, never reassigned — could be `const` with initializer, or just inlined

### Docstring bloat
```python
def add(a: int, b: int) -> int:
    """Add two integers together.
    
    This function takes two integer parameters and returns their sum.
    It is used to perform addition operations.
    
    Args:
        a: The first integer to add.
        b: The second integer to add.
        
    Returns:
        The sum of a and b as an integer.
    """
    return a + b
```

**Signal**: docstring-to-function-body ratio. Docstrings longer than the function they describe. Docstring that restates the function name and parameter names without adding domain context.

### Emoji / marker pollution
- `// ✅ Success!`, `// 🔥 Hot path`, `// 🚀 Performance optimization`
- `// NOTE:`, `// IMPORTANT:` before obvious code
- Section dividers that break a 20-line function into 4 "sections"

## Context-gathering approach for `ai_generated_debt`

This one is actually partially automatable with heuristics:

1. **Comment analysis**: tokenize each comment and the following line of code, compute overlap ratio. Flag files where >30% of comments restate the code.
2. **Log density**: count log statements per function. Flag functions with >2 logs per 10 LOC.
3. **Guard density**: count null checks, try-catch blocks, and fallback defaults. Compare to type annotations — if a value is typed non-nullable but checked for null, flag it.
4. **Docstring ratio**: for functions with docstrings, compute docstring LOC / body LOC. Flag when >1.0 on functions with <10 lines of body.
5. **Name genericity**: score function names against a "generic verbs" list (process, handle, do, manage, execute, perform). High density = LLM smell.

The holistic angle: which *modules* or *directories* look like they were bulk-generated? A few restating comments is fine — but if an entire directory has 40% comment-to-code ratio with high token overlap, that's a cleanup target.
