## Test Coverage Detector: Synthesis of Two Minds

### Where they agree (the bedrock)

Both perspectives converge on several crucial points:

1. **Don't just count lines** — Static analysis can't do runtime coverage, so don't pretend it can. Both independently arrived at **test file mapping via imports + naming conventions** as the primary signal, using the dep graph that already exists.

2. **Zone system is the foundation** — Production files are the denominator. Test files are the input. Config/generated/vendor/script zones are excluded. The infrastructure already handles this.

3. **Assertion density and mock ratio matter more than existence** — A test file with zero assertions is worse than no test file (false confidence). Both propose counting `expect()`, `assert`, `patch()`, `jest.mock()` etc.

4. **Reuse the dep graph** — The coupling phase already builds it. Cache it on `LangConfig` (like `_zone_map`), consume it in the coverage phase.

5. **Per-file findings, not a single percentage** — Findings like `untested_module` fit the existing model perfectly. Potential = production file count.

### Where they diverge (the interesting tension)

| Question | Engineer | Artist |
|---|---|---|
| **What tier?** | Tier 3 (like Code quality) | Tier 4 (like Dependency health) |
| **Primary metric** | Three formal metrics: FTR, MTM, TTC | "Test Need Score" = importers x complexity x (1 - coverage) |
| **Headline finding** | "Untested module (247 LOC, 12 functions)" | "Critical untested: payments.py (imported by 28 files)" |
| **Quality findings** | Confidence "low", cautious | Front-and-center — shallow tests are *worse* than none |
| **Summary** | Machine-precise aggregate metrics | "3 high-risk files need tests" |
| **Snapshot tests** | Mentioned as false positive risk | Dedicated anti-pattern detector |
| **Git history** | Not considered (pure static) | "Test-to-code change correlation" as strongest signal |

### The unified design

**Core principle from the artist, rigor from the engineer:**

> Measure **test need** (what's dangerous without tests), not just **test existence** (what has a test file). Present findings as risk, not as guilt. Weight by blast radius.

**The algorithm** (engineer's structure, artist's priorities):

```
For each production file:
  1. Check: does any test file import it? (import analysis — precise)
  2. Check: does a test file match by naming convention? (heuristic — fallback)
  3. Check: is it transitively reachable from a test? (dep graph BFS — permissive)
  4. Compute blast_radius = importer_count from dep graph
  5. Compute complexity from existing complexity detector data
  6. test_need = blast_radius * complexity_factor * (1.0 - coverage_depth)
  
  Where coverage_depth:
    0.0 = no test reference at all
    0.3 = only transitive coverage
    0.7 = direct test file, but low assertion density
    1.0 = direct test file with meaningful assertions
```

**Finding tiers** (the artist's insight resolves the engineer's tier question):

| Finding | Tier | Confidence | When |
|---|---|---|---|
| `no_tests` (entire codebase) | 2 | high | Zero test files found |
| `untested_critical` | 2 | high | Production file, 0 tests, blast_radius >= 10 |
| `untested_module` | 3 | high | Production file, 0 tests, blast_radius < 10 |
| `transitive_only` | 3 | medium | Only transitively tested |
| `shallow_tests` | 3 | medium | Test exists but assertion_density < 1 per test fn |
| `over_mocked` | 3 | low | mock_count > assertion_count |
| `snapshot_heavy` | 3 | low | snapshot_assertions > 50% of all assertions |
| `assertion_free_test` | 3 | medium | Test function with zero assertions |

**Tier 4** for the dimension itself (artist wins this argument). Coverage is the slowest thing to improve. With `MIN_SAMPLE` dampening, a codebase with 5 production files won't get wrecked. But at scale, the tier-4 weight ensures it matters.

**Narrative integration** (the artist's strongest contribution):

- Never show a raw percentage as the headline
- Always frame as "highest-risk untested files" with specific names
- Phase-aware messaging: first_scan gets empathy, regression gets curiosity, maintenance gets gentle nudges
- The coaching guidance: "add test files for the highest-risk untested modules — start with the most-imported production files"

**What to defer** (both agree these are v2):

- Git history / churn analysis (requires shelling out to `git log`, expensive)
- Coverage.json / Istanbul integration (nice but optional)
- Function-level coverage (expensive AST analysis for marginal gain over file-level)
- Test name quality analysis (interesting but hard to get right)

The artist: **Never let the number become the goal.** The blast-radius weighting ensures that testing one critical file moves the score more than testing ten trivial ones, which is the behavior you actually want to incentivize.
