それなら、かなり本命ですね。`403` なら「通ったけど拒否された」です。 今回の流れに照らすと、候補は主に 2 つです。 1. **Preview Deployment Protection / Vercel protection 側** - `callbackBaseUrl` や proxy の向き先が preview URL だと、protection bypass がないリクエストは `403` になりえます。 - 実際、コードにも preview 保護回避の文脈があります。 2. **proxy / internal route 側の認可** - mediator secret - OIDC audience / issuer - 想定ホスト - internal route の認可条件 - これらがズレると `403` になりえます。 ただ、今回さっき見た最新 retry では proxy ログ上 - `authorized: true` - `upstreamStatus: 200` が出ていたので、**少なくとも最新 run の proxy auth そのものは通っています**。 なので `zrlp5-1779282752978-a8ef52cea385` の `403` は、 - 以前の run の preview protection 問題 - もしくは callback/proxy の古い認可失敗 である可能性が高いです。 次にやるべきことは、その `403` の**対象 URL**を特定することです。 ここが分かれば一気に絞れます。 見たいのはログの: - request path - host - status 403 の route - response body か message もしそのログ行の詳細が取れるなら、 - `/api/internal/runs/callback` への 403 なのか - `/api/internal/codex-chatgpt-proxy/...` への 403 なのか - preview root への 403 なのか を見れば原因はかなり確定できます。 短く言うと: - `403` は重要な手がかり - でも **最新 retry の proxy auth 成功とは矛盾するので、古い失敗要因の可能性が高い** - いま必要なのは `403` の **URL/path 特定** そのログ詳細があれば、次でかなり断定できます。
