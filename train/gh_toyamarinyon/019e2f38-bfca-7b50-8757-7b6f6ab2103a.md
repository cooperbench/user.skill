# Selected text: ## Selection 1 GitHub mediator をどこまで transparent にするか」 ## My request for Codex: 具体的にどういうことですか？

> AGENT

「GitHub mediator をどこまで transparent にするか」は、要するに **sandbox 内の agent に GitHub API / git をどれくらい“そのまま”使わせるか** です。 大きく 3 段階あります。 **1. Transparent Forwarding** sandbox から GitHub っぽいリクエストをそのまま mediator に流して、mediator が `Authorization: Bearer <GITHUB_TOKEN>` を付けて GitHub に転送します。 例: ```http POST /api/internal/mediator/github/repos/toyamarinyon/rhapsody/issues/8/comments ``` mediator はこれを upstream の ```http POST https://api.github.com/repos/toyamarinyon/rhapsody/issues/8/comments ``` に近い形で転送する。 利点は、既存の `gh` CLI や GitHub API client が使いやすいことです。agent 側の実装も薄い。 欠点は、リクエスト body の意味まで mediator が深く理解しない限り、「これは本当にこの run に許可していい操作か？」の判定が荒くなります。特に GraphQL mutation や git push は危ないです。 **2. Operation-Level API** GitHub API をそのまま通さず、Rhapsody 専用 API にします。 例: ```http POST /api/internal/mediator/github/issue-comment { "run_id": "run_...", "body": "Completed. PR: ..." } ``` mediator 側が「この run の issue にコメントする」という操作として処理します。sandbox は `owner/repo/issue_number` を自由に指定できない。 利点は安全性と監査性です。 欠点は、agent が `gh` や通常の GitHub API をそのまま使えず、Rhapsody 専用 wrapper/tool が必要になります。 **3. Hybrid** 操作ごとに分けます。私の推しはこれです。 たとえば: | 操作 | 方針 | |---|---| | issue comment 作成 | operation-level 寄り | | PR 作成/更新 | operation-level または strict REST allowlist | | label/status 更新 | operation-level | | GitHub REST read | transparent でもよい | | GraphQL read | transparent でもよいが query 制限あり | | GraphQL mutation | allowlist 必須 | | git fetch/clone | transparent でもよい | | git push | repo-scoped transparent、ただし post-run verification 必須 | 問題の中心は、**transparent にするほど agent は自然に動けるけれど、mediator が安全に拒否できる範囲は狭くなる**ことです。 特に `git push` は典型です。HTTP としては GitHub への `git-receive-pack` ですが、中身は packfile なので mediator が「どの branch に何を push しているか」をきれいに検査しにくい。だから許すなら、事前に完全防御するより、 - token を repo scope に絞る - workflow で branch prefix を指定する - run 後に PR の head/base/repo を検証する - 変な push があれば run を failed/policy violation にする という設計になります。 なので ADR で決めたいのは、「agent の互換性を優先して GitHub API を GitHub っぽく見せるのか」「安全性を優先して Rhapsody の明示的な操作 API に閉じるのか」、そしてその境界線です。
