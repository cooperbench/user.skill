# AGENTS.md

Rhapsody is a Next.js application for a Vercel-native agent scheduler/runner. It is derived from
[Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/), but the target
architecture is GitHub Projects + Workflow SDK + Vercel Sandbox rather than a long-running local
daemon.

## Project Direction

- Treat [docs/SPEC.md](docs/SPEC.md) as the working product/engineering specification.
- Treat [docs/ORIGINAL_SPEC.md](docs/ORIGINAL_SPEC.md) as the unmodified Symphony reference spec.
- Design human-facing surfaces as extensions of familiar development practice, while optimizing the
  machinery behind them for agents and automation. Rhapsody exists to help humans develop with
  coding agents, so branch names, PRs, issue comments, dashboards, logs, and operator workflows
  should remain readable and unsurprising to developers. Code is also a human-facing surface:
  even when it implements agent-optimized data structures, protocols, mediation, sandboxing,
  retries, and verification, its naming, module boundaries, and control flow should stay readable
  and understandable to human maintainers. The product facade should feel familiar; the internal
  contracts should be explicit and structured for agents; the implementation should make both
  legible.
- Prefer Vercel-native primitives:
  - Workflow SDK for durable scheduler/runner workflows.
  - Vercel Sandbox for isolated agent execution.
  - Vercel Cron and GitHub webhooks for triggers.
  - A durable store for claims, runs, attempts, events, and dashboard projections.
- Use GitHub Projects v2 as the first issue tracker, not Linear.
- Keep the initial target narrow: GitHub Issues in a configured ProjectV2 board. Add PRs, draft
  issues, and other trackers later.

## Near-Term Work

1. Define the config shape for GitHub Project, scheduler, sandbox, and agent settings.
2. Add a GitHub Project tracker client that can resolve project/field IDs and normalize ProjectV2
   items into Rhapsody work items.
3. Add durable claim/run/attempt/event persistence.
4. Add a Workflow SDK scheduler workflow that polls GitHub Projects and starts runner workflows.
5. Add a runner workflow skeleton that creates a Vercel Sandbox and runs a simple command.
6. Add dashboard/API endpoints for state, item detail, run detail, and manual refresh.

## Engineering Notes

- Do not rely on in-memory state for scheduler correctness; Vercel Functions are not daemon
  processes.
- Agent commands must run inside a Vercel Sandbox workspace, not directly in the Vercel Function
  environment.
- Secrets should be passed through documented environment or brokered access patterns and must not
  be logged.
- Project status, claims, and retries must be idempotent because Cron, webhooks, and manual refresh
  can overlap.
- Keep docs updated as implementation decisions become concrete.

公式情報ベースだと、2026-05-27 時点で Vercel Sandbox は Pro/Enterprise では主に `Active CPU`, `Provisioned Memory`, `Data Transfer`, `Sandbox Creations`, `Storage` が課金対象です。たとえば Pro/Enterprise は Active CPU が `$0.128/hour`、Provisioned Memory が `$0.0424/GB-hour`、Data Transfer が `$0.15/GB` とされています。長時間 runner や並列実行、依存 install が多いと効きます。  
[Vercel Sandbox pricing](https://vercel.com/docs/vercel-sandbox/pricing)

一方 Codex Cloud は、OpenAI 側の hosted container で repo を clone して task を実行します。CLI からも `codex cloud exec --env ENV_ID "..."` で投入でき、Cloud Tasks は Codex の usage/credits 側で消費されます。OpenAI docs では Cloud Tasks / Code Review は `GPT-5.3-Codex` で動き、目安として Cloud Task が `~25 credits / message` とされています。  
[Codex pricing](https://developers.openai.com/codex/pricing), [Codex cloud CLI](https://developers.openai.com/codex/cli/features#working-with-codex-cloud)

なので、コスパ面ではこういう整理です。

**Codex Cloud に寄せると安くなりそうなケース**

- builder が主に Codex の推論・編集・PR 作成をするだけ
- sandbox 内で重い build/test を長時間回さない
- task 単位で GitHub branch / PR に成果物が残れば十分
- runner の詳細ログや実行環境制御を多少あきらめられる
- ChatGPT Business/Enterprise/Pro の Codex allowance や credits をうまく使える

**Vercel Sandbox を残した方がよさそうなケース**

- 任意コマンドを完全に Rhapsody 側で制御したい
- build/test/e2e/preview 起動まで runner 内で確実にやりたい
- stdout/stderr、exit code、artifact、timeout、retry を自前で厳密に扱いたい
- Codex 以外の agent/backend も同じ実行基盤に乗せたい
- Codex Cloud の task API/CLI の実験的部分に依存したくない

私なら、Rhapsody の設計としては **Vercel Sandbox を完全削除するより、builder backend を差し替え可能にする** のがよいと思います。

```ts
builder: {
  backend: "vercel-sandbox" | "codex-cloud"
}
```

そして初期実装では `codex-cloud` を「cheap/default path」にする。重い検証や特殊な実行だけ `vercel-sandbox` に逃がす。これがコストと制御性のバランスがよさそうです。

大事な注意点は、Codex Cloud は「Rhapsody が実行環境を所有する」のではなく「OpenAI の task 実行に委譲する」形になることです。だから Rhapsody 側の run/attempt/event model は、`externalTaskId`, `environmentId`, `submittedAt`, `githubBranch`, `pullRequestUrl`, `lastObservedStatus` みたいな外部実行追跡モデルに少し寄せる必要があります。

今の整理だと、こうですね。

```text
planner / implementation judgment / curator
  -> Vercel Sandbox + codex exec
  -> Rhapsody が環境・ログ・実行を握る

builder
  -> Codex Cloud
  -> OpenAI 側の hosted task に委譲して、branch/PR/diff を成果物として受け取る
```

この分離はよいと思います。builder は「一番時間がかかる」「並列に流したい」「成果物は最終的に GitHub branch/PR でよい」ので、Codex Cloud と相性がいいです。一方、実装前判断や curator は Rhapsody 内部の状態、issue graph、候補比較、ログ、追加ツール実行に近いので、Vercel Sandbox + Codex の制御性を残すのが合っています。

設計としては `agent role` ごとに backend を持たせるのがよさそうです。

```ts
agents: {
  planner: { backend: "vercel-sandbox-codex" },
  builder: { backend: "codex-cloud" },
  curator: { backend: "vercel-sandbox-codex" }
}
```

Builder の run model は少し変えて、Rhapsody が直接 stdout を読むのではなく、外部 task を追跡する形にします。

```text
builder attempt
  status: queued | submitted | running | completed | failed | timed_out
  backend: codex-cloud
  externalTaskId?
  codexEnvironmentId
  submittedPrompt
  githubBranch?
  pullRequestUrl?
  lastObservedAt
  observedSummary?
```

最初の実装はかなり薄くできます。

1. Builder backend interface を切る
2. 既存 builder を `vercelSandboxCodexBuilder` に退避
3. `codexCloudBuilder` を追加
4. `codex cloud exec --env <env> --attempts <n> <prompt>` で submit
5. 返ってくる情報、または GitHub 側の branch/PR/comment を durable store に保存
6. dashboard では「remote Codex task」として表示する

懸念は `codex cloud` CLI が docs 上では Experimental な点です。なので最初は builder のみ experimental flag 付きで入れて、失敗時に既存の Vercel Sandbox builder へ fallback できる形がいいです。

```text
builder.backend = "codex-cloud"
builder.fallbackBackend = "vercel-sandbox-codex"
```

これはかなり良い方向だと思います。Rhapsody が全部の compute を抱えるより、「判断・編成・検証は Rhapsody、長い実装作業は Codex Cloud」に寄せる方が、プロダクトとしても人間に説明しやすいです。
