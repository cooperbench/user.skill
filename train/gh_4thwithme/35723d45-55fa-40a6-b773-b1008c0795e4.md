Not inherently hard, but the complexity depends on scope.

**Easy parts:**

- **Tool orchestration** — sandboxing, permission models, cancellation, timeouts

- **Terminal quirks** — different emulators, Unicode handling, resize events, mouse support

**The real challenge isn't the TUI or the LLM — it's the agent runtime.** Reliable tool execution, error recovery, and context management are where 80% of the complexity lives.

A basic "chat + run shell commands" TUI: a weekend project. A production-grade agentic environment (like Claude Code): months of engineering on edge cases.

94	## The Loop
95	
96	1. **Check server is alive**, then **write HTML** to a new file in `screen_dir`:
97	   - Before each write, check that `$STATE_DIR/server-info` exists. If it doesn't (or `$STATE_DIR/server-stopped` exists), the server has shut down — restart it with `start-server.sh` before continuing. The server auto-exits after 30 minutes of inactivity.
98	   - Use semantic filenames: `platform.html`, `visual-style.html`, `layout.html`
99	   - **Never reuse filenames** — each screen gets a fresh file
100	   - Use Write tool — **never use cat/heredoc** (dumps noise into terminal)
101	   - Server automatically serves the newest file
102	
103	2. **Tell user what to expect and end your turn:**
104	   - Remind them of the URL (every step, not just first)
105	   - Give a brief text summary of what's on screen (e.g., "Showing 3 layout options for the homepage")
106	   - Ask them to respond in the terminal: "Take a look and let me know what you think. Click to select an option if you'd like."
107	
108	3. **On your next turn** — after the user responds in the terminal:
109	   - Read `$STATE_DIR/events` if it exists — this contains the user's browser interactions (clicks, selections) as JSON lines
110	   - Merge with the user's terminal text to get the full picture
111	   - The terminal message is the primary feedback; `state_dir/events` provides structured interaction data
112	
113	4. **Iterate or advance** — if feedback changes current screen, write a new file (e.g., `layout-v2.html`). Only move to the next question when the current step is validated.
114	
115	5. **Unload when returning to terminal** — when the next step doesn't need the browser (e.g., a clarifying question, a tradeoff discussion), push a waiting screen to clear the stale content:
116	
117	   ```html
118	   <!-- filename: waiting.html (or waiting-2.html, etc.) -->
119	   <div style="display:flex;align-items:center;justify-content:center;min-height:60vh">
120	     <p class="subtitle">Continuing in terminal...</p>
121	   </div>
122	   ```
123	
124	   This prevents the user from staring at a resolved choice while the conversation has moved on. When the next visual question comes up, push a new content file as usual.
125	
126	6. Repeat until done.

246	## Browser Events Format
247	
248	When the user clicks options in the browser, their interactions are recorded to `$STATE_DIR/events` (one JSON object per line). The file is cleared automatically when you push a new screen.

256	The full event stream shows the user's exploration path — they may click multiple options before settling. The last `choice` event is typically the final selection, but the pattern of clicks can reveal hesitation or preferences worth asking about.

## 2. Streaming

Yes, streaming is fully supported in two ways:

**A. Message-level streaming (default):** The `query()` return is an `AsyncGenerator<SDKMessage>`. You iterate with `for await` and receive complete messages as they arrive (assistant messages, tool use, results, system events).

**B. Token-level streaming:** Set `options.includePartialMessages: true` to receive `SDKPartialAssistantMessage` events containing raw Anthropic stream events (`BetaRawMessageStreamEvent`):

```typescript
type SDKPartialAssistantMessage = {
  type: "stream_event";
  event: BetaRawMessageStreamEvent;  // from Anthropic SDK
  parent_tool_use_id: string | null;
  uuid: UUID;
  session_id: string;
};
```

**C. Streaming input (multi-turn):** Pass an `AsyncIterable<SDKUserMessage>` as the `prompt` parameter for interactive multi-turn conversations. Use `query.streamInput()` to send additional messages.

## 4. Session Management

Sessions are persisted as JSONL files at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` (the cwd path with non-alphanumeric chars replaced by `-`).

- `resume?: string` -- resume a specific session by ID

### 2. Keyboard input and hotkeys

**`useInput(handler, options)` hook** -- the primary API:

```jsx
import {useInput} from 'ink';

The `key` object exposes: `leftArrow`, `rightArrow`, `upArrow`, `downArrow`, `return`, `escape`, `ctrl`, `shift`, `tab`, `backspace`, `delete`, `pageUp`, `pageDown`, `meta`.

For Ctrl+key combos: `key.ctrl` is `true` and `input` contains the letter. The `render()` function accepts `exitOnCtrlC: true|false` to control whether Ctrl+C auto-exits.

**Focus management:** `useFocus({ id, autoFocus, isActive })` makes components focusable (Tab/Shift+Tab cycles). `useFocusManager()` exposes `focusNext()`, `focusPrevious()`, `focus(id)` for programmatic control.

### 3. Scrollable views

**No built-in scroll component**, but two strategies exist:

**A) `<Static>` component (built-in)** -- renders items permanently above the interactive area. Good for chat logs / completed tasks. Items are rendered once and never re-rendered:

```jsx
<Static items={messages}>
  {msg => <Box key={msg.id}><Text>{msg.text}</Text></Box>}
</Static>
<Box><TextInput ... /></Box>  {/* stays at bottom */}
```

**B) `ink-scroll-view` (v0.3.6)** -- community package, actively maintained (Feb 2026). Full-featured:

```jsx
import { ScrollView, ScrollViewRef } from 'ink-scroll-view';

const scrollRef = useRef<ScrollViewRef>(null);
useInput((input, key) => {
  if (key.upArrow) scrollRef.current?.scrollBy(-1);
  if (key.downArrow) scrollRef.current?.scrollBy(1);
  if (key.pageDown) {
    const h = scrollRef.current?.getViewportHeight() || 1;
    scrollRef.current?.scrollBy(h);
  }
});

<Box height={20} overflow="hidden">
  <ScrollView ref={scrollRef}>
    {items.map(i => <Text key={i.id}>{i.text}</Text>)}
  </ScrollView>
</Box>
```

Ref methods: `scrollTo(offset)`, `scrollBy(delta)`, `scrollToTop()`, `scrollToBottom()`, `getScrollOffset()`, `getContentHeight()`, `getViewportHeight()`, `remeasure()`, `remeasureItem(index)`. Also has a `ControlledScrollView` variant for full external state control.

Related: `ink-scroll-list` (focus-managed list), `@byteland/ink-scroll-bar` (visual scrollbar).

### 5. Streaming text updates

**Yes, handles efficiently.** Ink is a React renderer -- just update state and it re-renders. The reconciler diffs output and only repaints changed portions. For streaming LLM responses:

```jsx
const [text, setText] = useState('');
// On each chunk:
setText(prev => prev + chunk);
// Component just renders:
<Text>{text}</Text>
```

The `<Static>` component is specifically designed for append-only output (completed messages), while the dynamic area below it handles the currently-streaming message. This is exactly the pattern Claude Code uses.

`console.log` interception (`patchConsole: true` by default) ensures external output doesn't conflict with Ink's rendering.

### 6. Known limitations for complex TUI layouts

- **No CSS Grid** -- only Flexbox. Multi-column layouts require nested `<Box>` with `flexDirection="row"`.
- **No native scroll** -- must use `overflow="hidden"` + manual offset management or `ink-scroll-view`.
- **`<Text>` cannot contain `<Box>`** -- text and layout are strictly separated. All visible text must be wrapped in `<Text>`.
- **No `position: absolute/fixed`** -- everything flows in flexbox. No overlays or floating panels natively (you can simulate with `display: none` toggling).
- **`<Static>` is append-only** -- once rendered, items cannot be updated or removed. Only new items trigger renders.
- **Terminal size awareness** -- `measureElement()` only works after first render; terminal resize requires manual handling via `stdout.on('resize')`.
- **`minWidth`/`minHeight`** don't support percentages (Yoga limitation).
- **No mouse support** built-in.

For sidebars: use `flexDirection="row"` with fixed `width` on sidebar + `flexGrow={1}` on main. Works well.
For tabs: use `ink-tab` (see below) or roll your own with `display="none"` toggling.

### 8. Ink + Zustand compatibility

**Fully compatible.** Zustand v5.0.12 peer-depends on `react >= 18.0.0`. Since zustand is just a React-compatible external store using `useSyncExternalStore`, it works with any React renderer including Ink. No DOM dependency whatsoever.

```jsx
import { create } from 'zustand';
import { render, Text } from 'ink';

const useStore = create((set) => ({
  messages: [],
  addMessage: (msg) => set((s) => ({ messages: [...s.messages, msg] })),
}));

const App = () => {
  const messages = useStore((s) => s.messages);
  return <Text>{messages.length} messages</Text>;
};
```

This is a natural fit -- zustand handles state outside React's tree, Ink handles rendering. No conflicts.
