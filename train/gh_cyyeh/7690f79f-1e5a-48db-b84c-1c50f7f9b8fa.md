### 2. Where the Incomplete Chunked Read Error is Caught

**Location:** `/Users/cyyeh/Desktop/duckdb-data-agent/backend/app/agent.py`, lines 307-315

The error handling is in the streaming loop that reads SSE events from the sidecar:

```python

    line_iter = response.aiter_lines().__aiter__()

        except httpx.RemoteProtocolError:  # <--- CATCHES INCOMPLETE CHUNKED READ
            # Sidecar closed the connection before sending a
            # proper chunked-encoding terminator.  This is
            # benign — the sidecar's Express handler calls
            # res.end() in its finally block and the
            # connection can tear down before the last chunk
            # delimiter reaches us.  Treat it as end-of-stream.
```

**Why it happens:**
- The sidecar's Express HTTP response handler (`res.end()`) is called in a `finally` block (sidecar line 344)
- The TCP connection can tear down before the HTTP/1.1 chunked encoding terminator reaches the backend
- `httpx.RemoteProtocolError` is raised instead of `StopAsyncIteration`
- The fix treats this as normal end-of-stream instead of a hard error

## Current Situation

The `httpx.RemoteProtocolError` (incomplete chunked read) happens because of a **race condition at stream end** — the sidecar's `res.end()` in the `finally` block tears down the TCP connection before the chunked encoding terminator reaches the backend. This is **benign** — all meaningful data has already been streamed.

## Can the Server Reconnect and Retry?

**Short answer: Yes, it's technically possible but probably unnecessary for the current error.**

### Why it's unnecessary for this specific error

The incomplete chunked read fires **after** the sidecar has finished its work. The `finally` block runs because the agent SDK loop completed (or errored). So there's no more data to get — retrying would just start a new query.

### Where retry WOULD help

If you're seeing the **second warning** ("stream ended without result message"), that means the sidecar finished but never sent a `result` event. This could happen if:
- The sidecar crashed mid-stream
- The SDK timed out (60s idle timer in `server.ts:71-96`)
- A genuine network interruption

### Retry feasibility for mid-stream failures

The pieces are already there:
1. **Session resumption** — the sidecar accepts `session_id` for resuming Claude Agent SDK sessions
2. **Container stays alive** — containers live for `CONTAINER_MAX_LIFETIME_SECONDS` (600s)
3. **The `/query` endpoint is stateless per-request** — you can POST again

The hard part is:
- **Deduplication** — the backend tracks streaming state (`has_thinking`, `subagent_chart_specs`, `tool_names`, etc.) that would need to handle replayed messages
- **Frontend SSE stream** — the client is already receiving events, so retried events could cause duplicate UI elements
