# Plan: Add fallback model rewrite for unmapped models

## Context

The Claude Agent SDK's WebFetch tool internally uses `claude-haiku-4-5-20251001`. When all models are configured to route through OpenAI (e.g., `openai/gpt-5.2-2025-12-11@sonnet`), only `sonnet` is in `MODEL_REWRITES`. The haiku model passes through unchanged, and Bifrost fails with `"provider is required"` because the bare model name lacks a provider prefix and no Anthropic API key is configured.

**Goal**: Add a `FALLBACK_MODEL` env var so any unmatched model gets rewritten to a configured fallback (e.g., an OpenAI model).

## Files to modify

1. **`backend/app/config.py`** — Add `FALLBACK_MODEL` config
2. **`backend/app/proxy.py`** — Use fallback in `rewrite_model_in_body()`
3. **`backend/tests/test_proxy.py`** — Add tests for fallback behavior
4. **`backend/.env.example`** — Document the new env var

## Implementation

### 1. `backend/app/config.py`
- Add `FALLBACK_MODEL = os.getenv("FALLBACK_MODEL", "")` after the existing model configs (~line 36)

### 2. `backend/app/proxy.py`

- In `rewrite_model_in_body()`, accept a `fallback` parameter (default `""`)

### 2. Which Built-in Tools Use Anthropic Models Internally

**WebFetch (Claude Code / Agent SDK version) -- Uses Claude Haiku 3.5 internally**

This is the only built-in tool with publicly confirmed internal model usage. According to the detailed analysis at [Inside Claude Code's Web Tools: WebFetch vs WebSearch](https://mikhail.io/2025/10/claude-code-web-tools/):

- The Claude Code WebFetch tool has a multi-stage pipeline. After fetching a URL and converting it to markdown, it runs an **"LLM pass"** where a **"small, fast model"** (identified as **Haiku 3.5**) processes the content.
- This internal Haiku model receives the page content along with the user's query and produces a concise answer, which is then returned to the main agent (Sonnet/Opus).
- The Haiku model runs with an **empty system prompt** and is constrained to answer only from the provided content, with strict limits on quotation length (max 125 characters) and copyright compliance.
- This design serves two purposes: (1) it keeps the main context window compact by summarizing rather than injecting full web pages, and (2) it adds a security layer against prompt injection since an attacker's instructions must survive Haiku's summarization before reaching the main model.

**Important distinction**: The Claude Code / Agent SDK WebFetch tool (which uses Haiku internally) is different from the **Claude API server-side `web_fetch` tool** (`web_fetch_20250910` / `web_fetch_20260209`). The API-level web fetch tool returns the full document content directly to the calling model without an intermediate LLM pass -- it is the calling model itself that processes the content. The API documentation at [Web fetch tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool) confirms it has no additional charges beyond standard token costs, indicating no secondary model invocation.

**All Other Built-in Tools -- No internal model usage**

Based on my thorough review of the official documentation for each tool:

- **Web Search** (both API and Agent SDK versions): The server executes searches via a search provider and returns encrypted results. - **Code Execution**: Runs in a sandboxed Linux container with pre-installed Python libraries. No internal model -- it is pure code execution infrastructure. Source: [Code execution tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)

- **Memory**: A client-side tool where your application handles all file I/O. Claude makes tool calls, and your code executes them. No internal model. Source: [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

   175→## Security
   176→
   177→### Bifrost LLM Gateway
   178→
   179→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   180→
   181→Instead, a [Bifrost](https://github.com/maximhq/bifrost) LLM gateway service manages API keys centrally and routes requests to LLM providers:
   182→
   183→```
   184→Sidecar Container
   185→  → ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic
   186→  → ANTHROPIC_API_KEY=placeholder
   187→        ↓
   188→Bifrost Gateway (/anthropic)
   189→  → ignores client-sent key
   190→  → injects the real provider API key
   191→  → forwards request to provider (Anthropic, OpenAI, Bedrock, etc.)
   192→```
   193→
   194→**How it works:**
   195→
   196→1. Bifrost runs as a Docker Compose service with real API keys stored in `bifrost/config.json` (referencing environment variables).
   197→2. Sidecar containers receive a placeholder `ANTHROPIC_API_KEY` and point `ANTHROPIC_BASE_URL` to Bifrost's native `/anthropic` endpoint.
   198→3. Bifrost injects the real provider API key when forwarding requests upstream. The Claude Agent SDK works unchanged since Bifrost speaks native Anthropic Messages API.
   199→4. Additional providers (OpenAI, Bedrock, Vertex, etc.) can be added to `bifrost/config.json` or via Bifrost's Web UI. Use provider prefixes in model names (e.g., `openai/gpt-4o-mini`) to route subagent requests to different providers. See [`bifrost/config.example.json`](bifrost/config.example.json) for configuration examples.
   200→
   201→The sidecar container only ever holds a placeholder string. Even if a tool call reads the environment, it cannot obtain any real API key.

   293→
   294→Browser-based end-to-end tests are driven by YAML scenario files using [Playwright](https://playwright.dev/). Define test scenarios declaratively — the runner handles browser automation, structural DOM assertions, and LLM-as-judge semantic verification.

   303→
   304→```
   305→ANTHROPIC_API_KEY=your-key-here
   306→```
   307→
   308→**Run tests** (requires `make dev` running in another terminal):
   309→
   310→```bash

   324→```bash
   325→BASE_URL=http://localhost:10000 make e2e-test
   326→```
   327→
   328→**Writing scenarios:** Add YAML files to `e2e/scenarios/`. Each file contains a list of scenarios with sequential steps:
   329→
   330→```yaml
   331→scenarios:
   332→  - name: "Upload CSV and query"
   333→    steps:
   334→      - action: upload_file
   335→        file: ./test-data/sales.csv
   336→      - action: send_message
   337→        input: "Show total sales by region"
   338→      - action: wait_for_response
   339→      - action: verify
   340→        expected:
   341→          contains: ["north", "south"]
   342→          has_chart: true
   343→      - action: verify_llm
   344→        criteria: "Response shows sales by region with numeric values"
   345→        pass_threshold: 0.7
   346→```
