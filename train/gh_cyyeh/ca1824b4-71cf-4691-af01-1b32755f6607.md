**Cons:** Extra network hop, still maintaining proxy code.

# LiteLLM /v1/messages Endpoint Guide

## URL Pattern & Setup

The endpoint is accessed via: `http://0.0.0.0:4000/v1/messages`

You configure it in a `config.yaml` file with model definitions:

```yaml
model_list:
  - model_name: my-model
    litellm_params:
      model: openai/gpt-4
      api_key: os.environ/OPENAI_API_KEY
```

Then start the proxy: `litellm --config /path/to/config.yaml`

## Model Routing

LiteLLM uses the Anthropic Messages API format as a universal interface. When you specify a model in your request, the proxy translates it to the appropriate provider. For example, the same request format works for:

- Anthropic Claude models
- OpenAI GPT models
- Google Gemini
- Vertex AI
- AWS Bedrock

The configuration file maps your logical model names to actual provider models, handling authentication and parameter translation automatically.

## Key Limitations

"**Guardrails apply to input and output text (non-streaming only)**" — real-time streaming responses bypass guardrail filtering.

The endpoint requires standard Anthropic message format with `model`, `max_tokens`, and `messages` fields. While most major providers are supported, specific advanced features of individual providers may not translate perfectly across the unified interface.

# LiteLLM Anthropic Passthrough Overview

## URL Pattern

The passthrough works by replacing the base URL. Replace:
- **Original:** `https://api.anthropic.com`
- **With:** `http://0.0.0.0:4000/anthropic` (or your proxy's base URL)

Any path after `/anthropic` is treated as a provider-specific route. For example:
- `/anthropic/v1/messages`
- `/anthropic/v1/messages/count_tokens`
- `/anthropic/v1/messages/batches`

## Authentication

The system supports two approaches:

1. **Direct API key:** Replace your Anthropic bearer token with "bearer anything" when using the proxy
2. **Virtual keys:** Generate proxy-managed virtual keys for better security without exposing raw API credentials

## Configuration

Minimal setup required:
1. Set `ANTHROPIC_API_KEY` environment variable
2. Start LiteLLM proxy: `litellm`
3. Make requests to the proxy endpoint

For batch cost tracking specifically, define models in `proxy_config.yaml`:
```yaml
model_list:
  - model_name: claude-sonnet-4-5-20250929
    litellm_params:
      model: anthropic/claude-sonnet-4-5-20250929
      api_key: os.environ/ANTHROPIC_API_KEY
```

## Key Features

The proxy provides "all Anthropic endpoints (including streaming)" with support for cost tracking, logging, and end-user tracking—enabling seamless drop-in replacement functionality.

Current: Backend creates ephemeral UUID tokens → proxy.py validates → swaps for real API key.
New: Backend passes `LITELLM_MASTER_KEY` to sidecar containers as `ANTHROPIC_API_KEY`. LiteLLM validates the master key. Real provider API keys live only in LiteLLM's config/env.

   148→## Security
   149→
   150→### Credential Proxy
   151→
   152→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   153→
   154→Instead, the backend runs a built-in reverse proxy at `/anthropic` that sits between Claude Code and `api.anthropic.com`:
   155→
   156→```
   157→Sidecar Container
   158→  → ANTHROPIC_BASE_URL=http://host:8000/anthropic
   159→  → ANTHROPIC_API_KEY=<short-lived UUID token>
   160→        ↓
   161→FastAPI proxy (/anthropic/{path})
   162→  → validates UUID token
   163→  → swaps it for the real ANTHROPIC_API_KEY
   164→  → forwards request to api.anthropic.com
   165→```
   166→
   167→**How it works:**
   168→
   169→1. Before each agent session, the backend mints a random UUID token with a 10-minute TTL.
   170→2. The token is injected into the sidecar container environment as `ANTHROPIC_API_KEY`; the real key is never exposed.
   171→3. The proxy validates every inbound request against the token store and substitutes the real key before forwarding upstream.
   172→4. When the session ends, the token is explicitly revoked in a `finally` block, regardless of success or error.
   173→5. A background task runs every 60 seconds to sweep any tokens that outlived their TTL.
   174→
   175→The sidecar container only ever holds a single-session UUID. Even if a tool call reads the environment, all it gets is a temporary token scoped to that conversation.
   176→
   177→### Container Isolation
   178→
   179→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   180→
   181→**Architecture:**
   182→
   183→```
   184→Browser
   185→  │
   186→  ▼
   187→FastAPI Backend (host)
   188→  ├── Chat route ──► ContainerManager ──► Docker SDK
   189→  │                       │
   190→  │                       ▼
   191→  │               ┌──────────────────────┐
   192→  │               │  gVisor Sandbox      │
   193→  │               │                      │
   194→  │               │  Sidecar Container   │
   195→  │               │  (Node.js + Claude)  │
   196→  │               │                      │
   197→  │               │  POST /query → SSE   │
   198→  │               └──────┬───────────────┘
   199→  │                      │
   200→  ├── /anthropic ◄───────┘  (credential proxy)
   201→  ├── /mcp/sse   ◄───────┘  (DuckDB MCP bridge)
   202→  │
   203→  └── DuckDB (per-user, disk-persisted)
   204→```
   205→
   206→The data flow for a chat message is:
   207→
   208→1. Frontend sends a chat message to the FastAPI backend.
   209→2. Backend mints a short-lived UUID token via the credential proxy and spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`.
   210→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   211→4. Claude CLI talks to the host credential proxy (`/anthropic`) for Anthropic API access (using the UUID token, never the real key).
   212→5. Claude CLI's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   213→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   214→7. On session end, the container is stopped and removed; the UUID token is revoked.
   215→
   216→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, the Agent SDK, and the `@anthropic-ai/claude-code` CLI (required by the SDK internally). Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   217→
   218→**MCP SSE bridge:** The backend exposes the DuckDB `execute_sql` tool at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`). Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized Claude CLI reaches DuckDB on the host without any direct database access inside the container.
