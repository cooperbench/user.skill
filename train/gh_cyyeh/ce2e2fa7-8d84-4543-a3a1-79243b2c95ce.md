## Claude Agent SDK TypeScript - Summary

### 1. **Installation and Setup**
```bash
npm install @anthropic-ai/claude-agent-sdk
```
- Single npm package for all Agent SDK functionality
- Works with Node.js, Bun, and Deno runtimes (auto-detected or configurable via `executable` option)

### 2. **Core Concepts and API**

The SDK provides three main functions:

- **`query()`** - Primary function for interacting with Claude Code. Creates an async generator that streams messages as they arrive.
- **`tool()`** - Creates type-safe MCP tool definitions using Zod schemas.
- **`createSdkMcpServer()`** - Creates an in-process MCP server with custom tools.

All interactions are streaming-based, returning `AsyncGenerator<SDKMessage>` with additional helper methods.

### 3. **How to Create an Agent**

Basic agent creation using `query()`:

```typescript
import { query } from "@anthropic-ai/claude-agent-sdk";

const result = await query({
  prompt: "Your task here",
  options: {
    model: "claude-opus-4.6", // or claude-sonnet-4.5, claude-haiku-4.5
    tools: { type: "preset", preset: "claude_code" }, // Use Claude Code's default tools
    systemPrompt: {
      type: "preset",
      preset: "claude_code"
    }
  }
});

// Stream through messages
for await (const message of result) {
  console.log(message);
}
```

## Implementation Plan: Migrate to Claude Agent SDK with Bun Server

### 1. Architecture Overview

**Current**: Browser calls Anthropic API directly via `@anthropic-ai/sdk` with `dangerouslyAllowBrowser: true`. DuckDB-WASM executes SQL in the browser. No server.

**Target**: Bun server runs the Claude Agent SDK's `query()` function. A WebSocket connects client and server. When the agent invokes `execute_sql`, the server sends the SQL to the client over WebSocket, the client runs it in DuckDB-WASM, and sends the result back. The server relays streaming text events to the client over the same WebSocket.

The key architectural challenge: the Agent SDK defines tools via MCP using `tool()` and `createSdkMcpServer()`. Tool handlers run server-side. But DuckDB is in the browser. The solution is to make the tool handler send a WebSocket message to the client and `await` the response using a Promise that resolves when the client replies.

### 3. WebSocket Protocol Design

Shared protocol types (in `/home/cyyeh/repos/ts-projects/duckdb-web/shared/protocol.ts`):

```typescript
// Client -> Server messages
export type ClientMessage =
  | { type: 'init'; apiKey: string; tables: TableInfo[] }
  | { type: 'chat'; text: string; conversationId: string }
  | { type: 'sql_result'; requestId: string; result: SqlResult }
  | { type: 'sql_error'; requestId: string; error: string }
  | { type: 'abort'; conversationId: string };

// Server -> Client messages
export type ServerMessage =
  | { type: 'text_chunk'; text: string }
  | { type: 'tool_call'; toolCallId: string; sql: string }
  | { type: 'tool_result'; result: ToolCallResult }
  | { type: 'sql_request'; requestId: string; sql: string }
  | { type: 'done' }
  | { type: 'error'; message: string };

export interface SqlResult {
  columns: string[];
  rows: Record<string, unknown>[];
  rowCount: number;
}
```

Message flow:

1. Client opens WebSocket, sends `init` with API key and table metadata.
2. Client sends `chat` with user message text.
3. Server starts Agent SDK `query()`, streams events.
4. When the agent calls `execute_sql`, the MCP tool handler:
   - Generates a unique `requestId`
   - Sends `sql_request` to client via WebSocket
   - Creates a Promise and stores the resolver in a `Map<string, {resolve, reject}>`
   - Awaits the Promise
5. Client receives `sql_request`, runs SQL in DuckDB-WASM, sends `sql_result` or `sql_error` back.
6. Server resolves the pending Promise, tool handler returns result to Agent SDK.
7. Server sends `text_chunk` for streaming text, `tool_call`/`tool_result` for UI updates, and `done` when complete.

    'execute_sql',
    'Execute a SQL query against the user\'s DuckDB database. Returns JSON rows.',
    { sql: z.string().describe('The SQL query to execute') },

          }

      });

      const truncatedRows = result.rows.slice(0, MAX_RESULT_ROWS);

        rows: truncatedRows,

  const { apiKey, tables } = ws.data;

    name: 'duckdb-tools',
    tools: [executeSqlTool],
  });

  try {
    const conversation = query({
      prompt: userText,

        model: 'claude-sonnet-4-20250514',

        allowedTools: ['mcp__duckdb-tools__execute_sql'],

        maxTurns: 10,
        abortController: controller,
        env: { ANTHROPIC_API_KEY: apiKey },
        includePartialMessages: true,
      },
    });

    for await (const message of conversation) {
      if (message.type === 'stream_event') {

        if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
          sendMessage(ws, { type: 'text_chunk', text: event.delta.text });

      } else if (message.type === 'result') {

      }

    sendMessage(ws, { type: 'error', message: msg });

  }

  const msg: ClientMessage = JSON.parse(typeof rawMessage === 'string' ? rawMessage : rawMessage.toString());

  switch (msg.type) {
    case 'init':
      ws.data.apiKey = msg.apiKey;
      ws.data.tables = msg.tables;
      break;

    case 'chat':
      runAgentQuery(ws, msg.text);
      break;

    case 'sql_result': {
      const pending = ws.data.pendingSql.get(msg.requestId);
      if (pending) {
        ws.data.pendingSql.delete(msg.requestId);
        pending.resolve(msg.result);
      }
      break;
    }

    case 'sql_error': {
      const pending = ws.data.pendingSql.get(msg.requestId);
      if (pending) {
        ws.data.pendingSql.delete(msg.requestId);
        pending.reject(new Error(msg.error));
      }
      break;
    }

    case 'abort':
      ws.data.abortController?.abort();
      break;
  }

### 12. Potential Challenges and Mitigations

**Challenge 1: Agent SDK spawns a subprocess.** The Claude Agent SDK may spawn Claude Code as a subprocess rather than running in-process. If that is the case, the `env` option passes the API key to that subprocess. The MCP server approach with `createSdkMcpServer()` uses the `type: "sdk"` config which runs in-process, so the tool handler has access to the WebSocket reference.

**Challenge 2: Session management for multi-turn.** The Agent SDK's `resume` option requires a session ID. We must capture it from the `SDKSystemMessage` on first query and store it in connection state. If the WebSocket disconnects and reconnects, the session is lost. Consider adding reconnection logic that re-initializes.

**Challenge 3: Error handling for dropped WebSocket.** If the client disconnects while a `sql_request` is pending, the tool handler's Promise will hang. The 30-second timeout handles this, but we should also clean up pending promises in the WebSocket `close` handler.

**Challenge 4: The `query()` function's prompt is a string, not a conversation.** For multi-turn, rely on `resume` + `continue` rather than passing message history. This is a change from the current approach that manually builds `conversationMessages[]`.

**Challenge 5: Streaming granularity.** The Agent SDK's `SDKPartialAssistantMessage` contains `RawMessageStreamEvent` from the Anthropic SDK, which includes `content_block_delta` events with `text_delta`. This is the same event structure the current `agentService.ts` already handles, so the client-side rendering code (`MessageBubble.tsx`, segment logic in `AgentContext.tsx`) should work with minimal changes.
