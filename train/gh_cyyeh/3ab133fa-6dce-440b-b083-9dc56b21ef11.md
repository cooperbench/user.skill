## Root Cause Found **Phase 1 complete.** I've traced the data flow and identified the root cause. ### The Bug In `MessageBubble.tsx:160-164`, the `streamingRemainder` calculation determines what un-segmented text to show during streaming: ```typescript const segmentedText = message.segments! .filter((s) => s.type !== 'tool') // BUG: only excludes 'tool' segments .map((s) => s.text || '') .join(''); const remaining = message.content.slice(segmentedText.length); ``` The filter `.filter((s) => s.type !== 'tool')` excludes only `tool` segments, but **`subagent_start` and `subagent_end` segments also have `text` fields** (the subagent prompt and result text respectively) that are **not part of `message.content`**. `message.content` only contains text accumulated via `onTextChunk` (thinking + answer text from SSE). But `segmentedText` includes: - Thinking text (from `onTextChunk` - correct) - `subagent_start.text` = the subagent prompt (NOT from `onTextChunk`) - `subagent_end.text` = the subagent result (NOT from `onTextChunk`) This inflates `segmentedText.length` beyond `message.content.length`, so `.slice()` returns an empty string. The streaming answer text is never displayed. It only appears all at once when `onDone` fires and creates the finalized `answer` segment. ### Fix Change the filter to only include segments whose text actually comes from `onTextChunk`:

> AGENT

The fix uses an allowlist (`thinking` or `answer`) instead of a denylist (`!== 'tool'`), so only segments whose text was accumulated via `onTextChunk` — and thus exists in `message.content` — are counted in the offset calculation. This applies equally to both subprocess and container modes since the bug is purely in the frontend rendering logic.
