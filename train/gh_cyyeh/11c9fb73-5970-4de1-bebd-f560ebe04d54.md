## Research Findings: Conversation History Save & Load

Based on my analysis of the codebase, here's how conversation history is saved and loaded:

### 1. **Backend Database Schema (memory_store.py)**

The backend uses SQLite with two main tables:

**conversations table:**
- `id` (PRIMARY KEY)
- `user_id` (defaults to "default")
- `title` (nullable - set from first message preview)
- `created_at` 
- `updated_at`

**messages table:**
- `id` (PRIMARY KEY)
- `conversation_id` (FOREIGN KEY → conversations.id with CASCADE delete)
- `role` ("user" or "assistant")
- `content` (the full message text)
- `metadata` (JSON - stores sql_queries and chart_specs)
- `created_at`
- `sort_order` (maintains message ordering)

### 2. **Backend Conversation Persistence (agent.py)**

**When saving messages:**
- **User messages** are persisted immediately when received:
  ```python
  if conversation_id:
      memory_store.add_message(conversation_id, "user", message)
  ```
  Location: `agent.py` lines 195-200

- **Assistant messages** are persisted ONLY at the very end of streaming (line 634-640):
  ```python
  if conversation_id and assistant_text_parts:
      meta = assistant_metadata if (assistant_metadata["sql_queries"] or assistant_metadata["chart_specs"]) else None
      memory_store.add_message(conversation_id, "assistant", "".join(assistant_text_parts), metadata=meta)
  ```

**Critical Issue:** The assistant message is saved as a single concatenated string from `assistant_text_parts` which contains only the plain text answer. This means:
- Tool results, thinking blocks, and intermediate subagent outputs are NOT captured
- Only the final concatenated text response is stored
- The `metadata` field stores SQL queries and chart specs, but NOT the structured format of how they were presented

### 3. **Backend API Endpoints (conversations.py)**

- **POST `/api/conversations`** - Creates a new conversation
- **GET `/api/conversations`** - Lists all conversations (sorted by updated_at DESC)
- **GET `/api/conversations/{id}`** - Loads a specific conversation with all messages
- **PUT `/api/conversations/{id}`** - Renames a conversation
- **DELETE `/api/conversations/{id}`** - Deletes a conversation (CASCADE deletes messages)

### 4. **Frontend Load Flow (ConversationContext.tsx)**

When clicking a conversation in the sidebar:

1. **selectConversation()** is called (line 52-65):
   ```typescript
   const res = await fetch(`/api/conversations/${id}`);
   const conv: Conversation = await res.json();
   const chatMessages: ChatMessage[] = (conv.messages || []).map((msg) => ({
     id: msg.id,
     role: msg.role as 'user' | 'assistant',
     content: msg.content,
     segments: msg.role === 'assistant' ? [{ type: 'answer' as const, text: msg.content }] : undefined,
   }));
   return chatMessages;
   ```

2. **The problem is on line 62:**
   - For assistant messages, it ALWAYS creates a single segment: `{ type: 'answer', text: msg.content }`
   - This assumes the entire assistant message is just plain text
   - Since the backend only stored plain text (without tool results, thinking, etc.), there's no data to reconstruct

3. **In App.tsx (line 56-59):**
   ```typescript
   const handleConversationSelect = useCallback(async (id: string) => {
     const messages = await conversation.selectConversation(id);
     loadMessages(messages);
   }, [conversation, loadMessages]);
   ```
   
4. **In AgentContext.tsx (line 612-616):**

   ```
   - This just sets the loaded messages into state
   - No reconstruction of segments or structured content happens

### 5. **Frontend Message Display (AgentPanel.tsx)**

The chat UI renders using `segments` from loaded messages, but since the assistant message was saved as plain text and reconstructed as a single `{ type: 'answer', text: content }` segment, users only see:
- User message: ✓ (stored and loaded correctly)
- Assistant message: ✓ (plain text only - no tool results, thinking, or charts)

### **Root Cause Summary**

The issue stems from a mismatch between:
1. **What gets saved**: Only plain text + JSON metadata (SQL queries, chart specs)
2. **What should be saved**: The full structured format including tool results, thinking blocks, subagent interactions
3. **What gets loaded**: Plain text only, reconstructed as a single "answer" segment
4. **What should be displayed**: All intermediate steps and structured content

**The solution would require:**
1. Saving the complete `segments` array structure to the database (as JSON)
2. OR reconstructing segments from metadata on load (parsing SQL queries and chart specs back into structured segments)
3. Modifying how assistant messages are serialized and deserialized

event_name = "answer" if has_tool_calls else "thinking"

**Phase 3: Hypothesis**
