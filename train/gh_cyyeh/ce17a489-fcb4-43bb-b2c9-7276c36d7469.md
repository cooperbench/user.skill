Here's the full picture:

**The two warnings are cause-and-effect:**

1. **`RemoteProtocolError`** (line 314 in `agent.py`) — The sidecar calls `res.end()` in its `finally` block (line 469 in `server.ts`) which closes the HTTP connection. The chunked transfer-encoding terminator doesn't always arrive before the TCP connection tears down, so httpx raises `RemoteProtocolError`.

2. **`Sidecar stream ended without result message`** (line 588 in `agent.py`) — Because the stream was cut short, the Python side never received the `result` message that the SDK emits at the very end of its iteration.

**Why the sidecar ends without sending a `result` message:**

The sidecar only forwards `result` if the SDK's `for await` loop (line 338 in `server.ts`) yields it. Several scenarios can prevent this:

- **SDK idle timeout** (line 330-333) — If the CLI subprocess hangs for >120s between messages, the `AbortController` fires. The `AbortError` is silently swallowed (line 454), so no error SSE event is written either. The `finally` block runs `res.end()`, and the Python side sees a premature close with no result.
- **CLI subprocess crash** — If the Claude CLI process exits unexpectedly, the async iterator may end without yielding a `result` message.
- **Client disconnect race** — If the browser/frontend disconnects, `abortController.abort()` fires (line 153), which can terminate the SDK query before `result` is yielded.

**The most likely intermittent cause** is the **idle timeout** (default 120s). If a long-running tool call or API response takes longer than `SDK_IDLE_TIMEOUT_MS`, the sidecar aborts the query cleanly (no error event sent to the client), and the Python backend sees the connection close without a result.

They are **completely different things** operating at different layers:

| | `SDK_IDLE_TIMEOUT_MS` | `CONTAINER_IDLE_TIMEOUT_SECONDS` |
|---|---|---|
| **Default** | 120,000ms (2 min) | 300s (5 min) |
| **Where** | Inside the sidecar (`server.ts:105`) | Backend container manager (`container_manager.py`) |
| **What it watches** | Time between SDK messages *within a single query* | Time since the *last query request* to the container |
| **What it does** | Aborts the current Claude CLI subprocess if it hangs | Stops/removes the entire Docker container |
| **Scope** | Per-request | Per-container (across all requests) |

**`SDK_IDLE_TIMEOUT_MS`** (2 min) — If the Claude CLI subprocess inside the sidecar goes 120s without yielding any message (e.g., stuck on MCP connection, broken session resume), the sidecar aborts that query. This is the one that can cause your error.

**`CONTAINER_IDLE_TIMEOUT_SECONDS`** (5 min) — If no new `/query` requests arrive at the sidecar container for 5 minutes, the backend's container manager stops and removes the Docker container entirely. This is a resource cleanup mechanism.

They're independent — but if `CONTAINER_IDLE_TIMEOUT_SECONDS` fires and kills the container *during* an active query, that would also cause the `RemoteProtocolError` you're seeing (the TCP connection dies). However, that scenario should be prevented by the `touch()` call that resets idle on every request.

Now I have the full picture. Here's the answer:

**Yes, `CONTAINER_IDLE_TIMEOUT_SECONDS` must be larger than `SDK_IDLE_TIMEOUT_MS` — and by a significant margin.** Here's why:

`touch()` is called **only once** at the start of a query (line 231 in `agent.py`). It's never called again during the query. So `last_activity` reflects when the query *started*, not when the last SDK message arrived.

A single query can run for a long time:
- `maxTurns: 20` in the sidecar
- Each turn can take up to `SDK_IDLE_TIMEOUT_MS` (120s) between messages
- Total worst case: many minutes of active streaming

Meanwhile, `cleanup_expired()` runs periodically in the background loop and kills any container where `last_activity < now - idle_timeout_seconds`. If the query takes longer than `CONTAINER_IDLE_TIMEOUT_SECONDS` from its start, **the container gets killed mid-query** — which is exactly your error.

**Recommended defaults:**

| Setting | Current | Recommended | Rationale |
|---|---|---|---|
| `SDK_IDLE_TIMEOUT_MS` | 120,000 (2 min) | **120,000 (2 min)** | Fine — if no message for 2 min, the CLI is stuck |
| `CONTAINER_IDLE_TIMEOUT_SECONDS` | 300 (5 min) | **900 (15 min)** | Must comfortably exceed the longest possible query |

5 minutes is too tight. A multi-turn query with tool calls (SQL, charting) can easily exceed that. 15 minutes gives enough headroom while still reclaiming idle containers reasonably fast.

**Alternatively**, a more robust fix would be to call `touch()` during the query (e.g., on each SSE event received), not just at the start. That way `CONTAINER_IDLE_TIMEOUT_SECONDS` truly measures "time since last activity" rather than "time since query started." Want me to implement that?
