### Design Decisions and Trade-offs

1. **No shared SearchInput component:** The codebase currently has no shared components for inputs -- even the ResultsTable search is fully inline. Creating a shared component would be premature abstraction for 3 nearly identical but contextually different inputs. Each component owns its search state, styling, and behavior. If a fourth panel needs search later, that would be a good time to extract a shared component.

2. **Toggle-based search (icon click to reveal input) vs always-visible search:** The requirement specifies a search icon that toggles the input. This conserves vertical space in the narrow sidebar. When the search is closed, the filter text is cleared so no hidden filter state confuses the user.

3. **Filter clears on tab switch (Tables tab):** Since the Tables tab search state lives in `Sidebar.tsx` alongside the tab state, adding a `useEffect` to clear search when switching away prevents stale filters. The Skills and Memories panels do not need this -- their state is local and will be destroyed/recreated if the component unmounts on tab switch (which it does, since the tab rendering is conditional with `?:` ternary).

4. **Active button indicator:** The `--active` modifier on the search icon button uses `var(--color-accent-secondary)` and its shadow, matching the existing focus ring pattern. This provides a clear visual indicator that search is active.

5. **Memories filtering preserves category structure:** When filtering memories, empty categories still show their "No X saved yet" messages rather than being hidden entirely. This preserves the consistent three-section layout and avoids layout jumps.

6. **`autoFocus` on the search input:** When the user clicks the search icon, the input appears and immediately receives focus. This avoids requiring a second click to start typing.
