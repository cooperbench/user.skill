## **WHERE THE BREAK IS**

### **Primary Issue: Missing Volume Mount in Sidecar Container**

When `container_manager.create()` is called (line 108), it checks:
```python
skills_host_path = os.environ.get("SKILLS_HOST_PATH", "")
```

**If this env var is empty or unset, the skills volume is NOT mounted:**
```python
volumes = {}  # Remains empty!
if skills_host_path:  # This condition is False
    # Volume mount code never executes
```

Then later:
```python
**({"volumes": volumes} if volumes else {}),  # Empty dict, no volumes added
```

**Result:** The sidecar container has no `/app/skills` directory. When the sidecar starts and calls `discoverSkills()`, it finds `/app/skills` doesn't exist and returns an empty Set.

### **Root Cause: Environment Variable Not Propagating**

The `docker-compose.yml` sets:
```yaml
SKILLS_HOST_PATH: ${SKILLS_HOST_PATH:-./skills}
```

This shell variable substitution happens **when docker-compose is invoked**, but:
1. If the host environment doesn't have `SKILLS_HOST_PATH` set, it defaults to `./skills`
2. However, this becomes a **string literal** in the YAML passed to the backend container
3. The Python backend reads from `os.environ`, which may not have received this variable correctly during container startup
4. If `.env` file doesn't explicitly set `SKILLS_HOST_PATH`, it won't be available

### **Secondary Issue: Sidecar Dockerfile Comment**

In `sidecar/Dockerfile` (line 37), there's a comment:
```dockerfile
# Skills are volume-mounted at runtime at /app/skills/
```

But there's no code ensuring the directory exists or checking if it's mounted. If the mount fails silently, the directory simply doesn't exist.
