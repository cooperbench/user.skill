Here are **3 approaches** for building the export feature:

---

### Approach A: DOM Cloning + Inline Everything (Recommended)

Capture the live DOM of `.agent-panel__messages`, clone it, then:
1. Inline all computed CSS (from `getComputedStyle`) or gather the app's CSS stylesheets and embed them in a `<style>` tag
2. Serialize Plotly charts as-is (the `<div>` with data attributes) and include a `<script>` tag loading Plotly.js from CDN (or inline the minified Plotly bundle)
3. `<details>` elements for thinking blocks work natively in HTML - no JS needed
4. Wrap everything in a standalone HTML document and trigger a download via `Blob` + `URL.createObjectURL`

**Pros:** Faithful to the rendered output. `<details>` collapsibility is free (native HTML). Plotly interactivity preserved via CDN script.
**Cons:** Plotly.js CDN adds ~3MB dependency (but loads on-demand when opened). Computed styles can be verbose if inlined per-element.

**Optimization:** Instead of per-element computed styles, extract the actual CSS from the app's stylesheets (they're loaded in the page) and embed just those rules.

---

### Approach B: Re-render from Message Data (React → Static HTML)

Instead of cloning the DOM, take the `messages` array from `AgentContext`, and re-render them to HTML using a dedicated export template:
1. Iterate over messages/segments and produce HTML directly (markdown → HTML via a lightweight renderer)
2. Embed CSS rules matching the app's theme
3. Include Plotly data/layout as inline JSON, with a script that calls `Plotly.newPlot()` on load

**Pros:** Cleaner output, no DOM mutation. Full control over what's included.
**Cons:** Duplicates rendering logic (must match `MessageBubble` output). More code to write and maintain. Markdown rendering needs a separate library or re-implementation.

---

### Approach C: html2canvas / dom-to-image Screenshot

Use a library like `html2canvas` to capture the conversation as an image or PDF.

**Pros:** Simple, one library call.
**Cons:** No interactivity at all (static image). Charts lose zoom/hover. Thinking blocks can't expand/collapse. Large conversations produce huge images. Doesn't meet the "full interactivity" requirement.

---

**My recommendation: Approach A.** It's the most pragmatic - the DOM already has the correct rendered output, `<details>` gives you collapsibility for free without any JS, and Plotly charts can be re-activated with a single CDN script tag. The main work is gathering CSS and serializing the DOM cleanly.

## Design Section 3: Plotly Chart Re-initialization

Plotly charts rendered by `react-plotly.js` create `<div>` elements with internal state that gets lost when we clone the DOM. To restore interactivity:

1. **Before cloning:** For each Plotly chart container in the conversation, extract the data/layout/frames using `Plotly.Plots?.getSubplotData` or by reading the `__data` attribute on the Plotly div (react-plotly.js stores data on the element's `.data` and `.layout` properties)

This approach keeps the chart data as JSON in the HTML and lets the CDN-loaded Plotly.js re-render them with full interactivity (zoom, pan, hover tooltips).

**1. XSS via `clone.outerHTML` injected raw into the HTML template (line 156)**

```ts
${clone.outerHTML}
```

`clone` is a deep copy of the live DOM. The live DOM's text content was rendered safely by React (via `ReactMarkdown`, JSX text nodes, etc.), so the *text nodes* are safe. However, `outerHTML` serialises the entire element tree including all attribute values. If any attribute in the rendered DOM was set from user-controlled data (e.g. `data-*`, `href`, `src`, `title`, or event handler attributes that a compromised dependency or a future code change could introduce), those will be emitted verbatim into the outer HTML string without escaping, and the browser will parse them again in the exported file.

More concretely: the live DOM is rendered by React, which does sanitise JSX props, but `cloneNode(true)` + `.outerHTML` produces a raw HTML string. Any attribute value that contains `"` or `>` will break the surrounding attribute context. For a concrete example, if a message's content causes a `title` attribute to contain `"><script>`, the exported file will have an XSS vector. While React prevents this in the rendered JSX, third-party libraries (e.g. `react-markdown` rendering user-supplied markdown) can produce `<a href="javascript:...">` links in their output — `cloneNode` captures those verbatim.

This is an **important** (not critical) issue only because the exported file is a local download opened by the same user; there is no server-side injection vector. But if users share exported HTML files (which is the whole point of an export feature), any `javascript:` href in a user-supplied markdown link survives into the exported file and becomes clickable.

**Recommendation:** Either run the clone through a DOM sanitiser (e.g. DOMPurify) before calling `.outerHTML`, or at minimum strip `javascript:` hrefs from all anchor elements in the clone before serialisation.

---

**2. `chartsJSON` injected raw into a `<script>` block (line 160)**

```ts
var charts = ${chartsJSON};
```

`chartsJSON` is the result of `JSON.stringify(charts)`, where `charts` is extracted from Plotly's live DOM properties (`.data`, `.layout`). If any string value inside those objects contains `</script>`, the browser's HTML parser will terminate the script block early, breaking the export and potentially opening an injection vector in the exported file.

This is a **well-known** pitfall with embedding JSON inside `<script>`. The fix is to escape the forward slash in the closing tag:


Without this, a chart whose data contains the literal string `</script>` (possible if label/hover text comes from user data) will produce a broken or exploitable exported file.

**Recommendation:** Apply the escaping above before embedding `chartsJSON`.

    80→#### Per-Subagent Model Routing
    81→
    82→You can route each agent (orchestrator, SQL subagent, chart subagent) to a different LLM provider by using the `@suffix` syntax:
    83→
    84→```
    85→ORCHESTRATOR_MODEL=openai/gpt-4o@sonnet
    86→REDACTED@haiku
    87→REDACTED@haiku
    88→```
    89→
    90→The format is `real_model@sdk_alias`. The SDK alias (after `@`) is the model name the Claude Agent SDK sees; the real model (before `@`) is what the backend proxy rewrites it to before forwarding to Bifrost. This lets you use any provider Bifrost supports (OpenAI, Bedrock, etc.) while keeping the SDK configuration unchanged.
    91→
    92→**How it works:**
    93→
    94→1. The SDK sends requests using the alias (e.g. `sonnet`, `haiku`).
    95→2. A lightweight reverse proxy on the backend (`/anthropic/*`) intercepts these requests.
    96→3. The proxy rewrites the `model` field to the real provider model (e.g. `openai/gpt-4o`) and forwards the request to Bifrost.
    97→4. Bifrost routes the request to the correct provider.
    98→
    99→Without `@suffix`, model values are used as-is (direct Anthropic routing).
   100→
   101→#### Default Tool Model
   102→
   103→The Claude Agent SDK's built-in tools (e.g. WebFetch) internally use their own Anthropic models (e.g. `claude-haiku-4-5-20251001`). When routing all traffic through a non-Anthropic provider, these models are not in the rewrite map and will fail because they lack a provider prefix.
   104→
   105→Set `DEFAULT_TOOL_MODEL` to catch any model not matched by the per-agent rewrites:
   106→
   107→```
   108→DEFAULT_TOOL_MODEL=openai/gpt-4o-mini
   109→```
   110→
   111→Any request whose model does not match a configured rewrite is rewritten to this value before forwarding to Bifrost. When empty (default), unmatched models pass through unchanged.

   188→## Security
   189→
   190→### Bifrost LLM Gateway
   191→
   192→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   193→
   194→Instead, a [Bifrost](https://github.com/maximhq/bifrost) LLM gateway service manages API keys centrally and routes requests to LLM providers:
   195→
   196→```
   197→Sidecar Container
   198→  → ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic
   199→  → ANTHROPIC_API_KEY=placeholder
   200→        ↓
   201→Bifrost Gateway (/anthropic)
   202→  → ignores client-sent key
   203→  → injects the real provider API key
   204→  → forwards request to provider (Anthropic, OpenAI, Bedrock, etc.)
   205→```
   206→
   207→**How it works:**
   208→
   209→1. Bifrost runs as a Docker Compose service with real API keys stored in `bifrost/config.json` (referencing environment variables).
   210→2. Sidecar containers receive a placeholder `ANTHROPIC_API_KEY` and point `ANTHROPIC_BASE_URL` to Bifrost's native `/anthropic` endpoint.
   211→3. Bifrost injects the real provider API key when forwarding requests upstream. The Claude Agent SDK works unchanged since Bifrost speaks native Anthropic Messages API.
   212→4. Additional providers (OpenAI, Bedrock, Vertex, etc.) can be added to `bifrost/config.json` or via Bifrost's Web UI. Use provider prefixes in model names (e.g., `openai/gpt-4o-mini`) to route subagent requests to different providers. See [`bifrost/config.example.json`](bifrost/config.example.json) for configuration examples.
   213→
   214→The sidecar container only ever holds a placeholder string. Even if a tool call reads the environment, it cannot obtain any real API key.
   215→
   216→### Container Isolation
   217→
   218→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   219→
   220→**Architecture:**
   221→
   222→```
   223→Browser
   224→  │
   225→  ▼
   226→FastAPI Backend (host)
   227→  ├── Chat route ──► ContainerManager ──► Docker SDK
   228→  │                       │
   229→  │                       ▼
   230→  │               ┌──────────────────────┐
   231→  │               │  gVisor Sandbox      │
   232→  │               │                      │
   233→  │               │  Sidecar Container   │
   234→  │               │  (Node.js + Claude)  │
   235→  │               │                      │
   236→  │               │  POST /query → SSE   │
   237→  │               └──────┬───────────────┘
   238→  │                      │
   239→  │              ├──► Bifrost Gateway (:8080/anthropic)  (LLM routing)
   240→  ├── /mcp/sse   ◄───────┘  (DuckDB MCP bridge)
   241→  │
   242→  └── DuckDB (per-user, disk-persisted)
   243→```
   244→
   245→The data flow for a chat message is:
   246→
   247→1. Frontend sends a chat message to the FastAPI backend.
   248→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, configured to route LLM calls through the Bifrost gateway.
   249→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   250→4. Claude CLI talks to the Bifrost gateway (`/anthropic`) for LLM API access (using a placeholder key; Bifrost injects the real key).
   251→5. Claude CLI's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   252→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   253→7. On session end, the container is stopped and removed.
   254→
   255→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, the Agent SDK, and the `@anthropic-ai/claude-code` CLI (required by the SDK internally). Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   256→
   257→**MCP SSE bridge:** The backend exposes the DuckDB `execute_sql` tool at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`). Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized Claude CLI reaches DuckDB on the host without any direct database access inside the container.
