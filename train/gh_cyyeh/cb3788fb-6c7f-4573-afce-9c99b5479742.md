- All conversation history is stored **in React component state** only (`messages` array in `AgentContext.tsx`)

  - `sessionIdRef`: tracks the current Claude Agent SDK session ID
  - `pendingHistoryRef`: holds history context when editing/deleting messages

**Backend Conversation History Handling**
- The backend does NOT persistently store conversation history
- Conversation history is passed **request-by-request** from the frontend as a parameter:
  - In `ChatRequest` model: `conversation_history: list[dict] = []`
  - Contains `[{"role": "user"|"assistant", "content": "..."}]` tuples

  - On retry, it prepends conversation history to the prompt (lines 349-354)

# Comprehensive Survey: Memory Capabilities in the Claude Agent SDK

## 1. Overview of the Ecosystem

The Claude Agent SDK (formerly Claude Code SDK) is available in two languages:

- **Python**: `claude-agent-sdk` on [PyPI](https://pypi.org/project/claude-agent-sdk/) (latest: v0.1.44)
- **TypeScript**: `@anthropic-ai/claude-agent-sdk` on [npm](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk)

The SDK provides the same tools, agent loop, and context management that power Claude Code, programmable as a library. Memory and context persistence are addressed through multiple complementary mechanisms at different layers of the stack.

## 2. Session Management (Agent SDK Layer)

**Source**: [Session Management - Claude API Docs](https://platform.claude.com/docs/en/agent-sdk/sessions)

The Agent SDK has first-class session management for maintaining conversation state across multiple interactions.

### Session Creation and ID Capture

When you call `query()`, the SDK automatically creates a session. The first message emitted is a `system` message with `subtype: "init"` containing the `session_id`:

**Python:**
```python
from claude_agent_sdk import query, ClaudeAgentOptions

session_id = None
async for message in query(
    prompt="Help me build a web application",
    options=ClaudeAgentOptions(model="claude-opus-4-6"),
):
    if hasattr(message, "subtype") and message.subtype == "init":
        session_id = message.data.get("session_id")
```

**TypeScript:**
```typescript
import { query } from "@anthropic-ai/claude-agent-sdk";

let sessionId: string | undefined;
for await (const message of query({
  prompt: "Help me build a web application",
  options: { model: "claude-opus-4-6" }
})) {
  if (message.type === "system" && message.subtype === "init") {
    sessionId = message.session_id;
  }
}
```

### Session Resumption

Sessions can be resumed using the `resume` option. The SDK automatically loads the full conversation history and context:

```python
async for message in query(
    prompt="Continue where we left off",
    options=ClaudeAgentOptions(resume=session_id),
):
    print(message)
```

By default, sessions are persisted to disk at `~/.claude/projects/` and can be resumed across different execution contexts.

### Session Forking

Sessions can be forked to create independent conversation branches using `fork_session=True` (Python) / `forkSession: true` (TypeScript):

| Behavior | `fork_session=False` (default) | `fork_session=True` |
|----------|-------------------------------|---------------------|
| Session ID | Same as original | New ID generated |
| History | Appends to original | Creates new branch |
| Original Session | Modified | Preserved unchanged |
| Use Case | Continue linear conversation | Branch to explore alternatives |

### ClaudeSDKClient (Interactive Sessions)

For bidirectional, stateful conversations, the `ClaudeSDKClient` maintains context across multiple `query()` calls within a single session lifecycle:

```python
async with ClaudeSDKClient(options=options) as client:
    await client.query("First message")
    async for msg in client.receive_response():
        print(msg)
    await client.query("Follow-up message")  # retains context
    async for msg in client.receive_response():
        print(msg)
```

## 3. Memory Tool (Claude API Layer)

**Source**: [Memory Tool - Claude API Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

The Memory Tool is a client-side tool (type: `memory_20250818`) that enables Claude to store and retrieve information across conversations through a file-based memory directory. It was launched in beta on September 29, 2025.

### How It Works

- Claude automatically checks the `/memories` directory before starting tasks
- Claude creates, reads, updates, and deletes files in that directory
- The tool operates **client-side**: your application executes the file operations locally
- You control where and how data is stored (filesystem, database, cloud storage, encrypted files, etc.)

### Supported Operations

| Command | Description |
|---------|-------------|
| `view` | Show directory contents or file contents with optional line ranges |
| `create` | Create a new file |
| `str_replace` | Replace text in a file |
| `insert` | Insert text at a specific line |
| `delete` | Delete a file or directory |
| `rename` | Rename or move a file/directory |

### Basic Usage

```python
import anthropic

client = anthropic.Anthropic()
message = client.messages.create(
    model="claude-opus-4-6",
    max_tokens=2048,
    messages=[{"role": "user", "content": "Help me debug this function..."}],
    tools=[{"type": "memory_20250818", "name": "memory"}],
)
```

### SDK Helpers

The Anthropic client SDKs provide memory tool helpers:
- **Python**: Subclass `BetaAbstractMemoryTool` to implement custom backends
- **TypeScript**: Use `betaMemoryTool` helper

Reference examples:
- Python: [examples/memory/basic.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/examples/memory/basic.py)
- TypeScript: [examples/tools-helpers-memory.ts](https://github.com/anthropics/anthropic-sdk-typescript/blob/main/examples/tools-helpers-memory.ts)

### Supported Models

Claude Opus 4.6, Opus 4.5, Opus 4.1, Opus 4, Sonnet 4.6, Sonnet 4.5, Sonnet 4, and Haiku 4.5.

### Built-in Prompting Guidance

When the memory tool is enabled, Claude automatically receives this protocol:

```

1. Use the `view` command to check for earlier progress.
2. ... (work on the task) ...
```

## 4. Context Management Mechanisms

There are three distinct strategies for managing growing conversation context, operating at different layers.

### 4a. Server-Side Compaction (Recommended)

**Source**: [Compaction - Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/compaction)

Server-side compaction automatically summarizes older conversation context when approaching the context window limit. It is the primary recommended strategy.

- **Beta header**: `compact-2026-01-12`
- **Strategy type**: `compact_20260112`
- **Default trigger**: 150,000 input tokens (minimum 50,000)
- **Supported models**: Claude Opus 4.6, Sonnet 4.6
- **ZDR eligible**: Yes

Key features:
- Returns a `compaction` block containing the summary in the response
- All content before the compaction block is automatically dropped on subsequent requests
- Supports `pause_after_compaction` for injecting preserved messages
- Custom summarization instructions via the `instructions` parameter
- Works with prompt caching

```python
response = client.beta.messages.create(
    betas=["compact-2026-01-12"],
    model="claude-opus-4-6",
    max_tokens=4096,
    messages=messages,
    context_management={
        "edits": [{"type": "compact_20260112",
                    "trigger": {"type": "input_tokens", "value": 100000}}]
    },
)
```

### 4b. Context Editing (Tool Result Clearing + Thinking Block Clearing)

**Source**: [Context Editing - Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)

Context editing provides fine-grained control over what gets cleared from conversation history.

- **Beta header**: `context-management-2025-06-27`

**Tool Result Clearing** (`clear_tool_uses_20250919`):
- Clears oldest tool results chronologically when token threshold is exceeded
- Replaces cleared results with placeholder text
- Configurable: `trigger` (default 100K tokens), `keep` (default 3 tool uses), `clear_at_least`, `exclude_tools`, `clear_tool_inputs`

**Thinking Block Clearing** (`clear_thinking_20251015`):
- Manages `thinking` blocks from extended thinking
- Default: keeps only the last assistant turn's thinking blocks

### 4c. Client-Side SDK Compaction

Available via the `tool_runner` method in both Python and TypeScript SDKs. Generates a summary and replaces conversation history client-side.

```python
runner = client.beta.messages.tool_runner(
    model="claude-opus-4-6",
    max_tokens=4096,
    tools=[...],
    messages=[...],
    compaction_control={"enabled": True, "context_token_threshold": 100000},
)
```

**Note**: Server-side compaction is recommended over client-side SDK compaction due to better token usage calculation and less integration complexity.

### Combining Memory Tool with Context Editing

The memory tool and context editing are designed to work together. When context approaches the clearing threshold, Claude receives an automatic warning to preserve important information to memory files before tool results are cleared. You can also exclude memory tool calls from being cleared:

```python
context_management={
    "edits": [{"type": "clear_tool_uses_20250919", "exclude_tools": ["memory"]}]
}
```

## 6. Multi-Session Memory Pattern for Long-Running Agents

**Source**: [Effective Harnesses for Long-Running Agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

Anthropic describes a structured memory pattern for projects spanning multiple agent sessions:

1. **Initializer Session**: Sets up memory artifacts before substantive work begins, including:
   - A progress log (tracking what has been done and what comes next)
   - A feature checklist (defining scope)
   - A reference to initialization scripts

2. **Subsequent Sessions**: Open by reading memory artifacts to recover full project state in seconds.

3. **End-of-Session Update**: Before a session ends, it updates the progress log with what was completed and what remains.

This pattern uses the memory tool's file-based storage to create `claude-progress.txt` and `features_list.json` files that function as persistent state documentation.

| **MCP Memory Servers** | Agent SDK + MCP | Developer-controlled | Cross-session | Via integration | Custom memory backends |

---

## 9. Key Limitations and Gaps

1. **No built-in vector store**: The SDK does not include a built-in vector database or embedding-based retrieval. You must bring your own via MCP servers or custom implementations.

2. **Memory tool is client-side**: All storage is your responsibility. The API only makes tool calls; your application must implement the actual file/database operations.

3. **No automatic cross-session memory**: Sessions resume via explicit session IDs. There is no automatic "remember this user" across independent sessions without using the memory tool or external storage.

4. **Compaction loses detail**: Compaction replaces full history with summaries, which can lose precise details from early in the conversation. Not ideal for tasks requiring exact recall.

5. **Server-side compaction model limitation**: The same model is used for both the task and summarization; you cannot specify a cheaper model for server-side compaction summaries (though client-side compaction supports this).
