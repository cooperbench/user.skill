## Bifrost Architecture & 400 Error Analysis

Based on my thorough exploration of the bifrost directory and codebase, here's what I found:

### 1. What is Bifrost?

**Bifrost is a high-performance open-source LLM gateway** (written in Go, Docker image `maximhq/bifrost:latest`) that replaces the previous custom credential proxy (`proxy.py`). It:

- Manages API keys centrally for multiple LLM providers (Anthropic, OpenAI, Bedrock, Vertex, etc.)
- Routes requests based on provider prefixes (e.g., `openai/gpt-4o-mini`)
- Provides weighted load balancing and automatic failover across keys
- Speaks native Anthropic Messages API on its `/anthropic` endpoint
- Runs as a Docker Compose service on port 8080 (exposed to 8081)
- Has a Web UI at `http://localhost:8081` for configuration and monitoring

### 2. Overall Architecture

```
Sidecar Container (TypeScript + Claude Agent SDK)
    ↓ (ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic)
    ↓ (ANTHROPIC_API_KEY="placeholder")
    ↓
Bifrost Gateway (/anthropic endpoint)
    ↓ (injects real API key from config.json)
    ↓
Anthropic / OpenAI / Bedrock / other providers

Backend (FastAPI)
    ├── /anthropic/* proxy route (backend/app/proxy.py)
    │   └── Rewrites model names using @suffix syntax
    │   └── Forwards to Bifrost at http://bifrost:8080/anthropic
    │
    ├── /mcp/sse (for DuckDB tool calls, NOT routed through Bifrost)
    │
    └── Container spawn
        └── Passes BIFROST_BASE_URL and BACKEND_BASE_URL to sidecar
```

### 3. How POST /anthropic/v1/messages Requests are Handled

**Request Flow:**

1. **Sidecar sends request** to `ANTHROPIC_BASE_URL/v1/messages` (with placeholder key)
   - SDK in sidecar (`sidecar/src/server.ts`) calls Claude Agent SDK's `query()` function
   - The SDK internally generates a POST to `/v1/messages`

2. **Backend proxy intercepts** (`backend/app/proxy.py`, line 19: `@router.api_route("/{path:path}"`)
   - Matches any request to `/anthropic/*`
   - Strips HTTP headers that shouldn't be forwarded (host, content-length, transfer-encoding, etc.)
   - **Optionally rewrites the `model` field in the request body** using `MODEL_REWRITES` dict (lines 22-42)
     - This happens if `ORCHESTRATOR_MODEL` or subagent models use the `@suffix` syntax
     - Example: `openai/gpt-4o@sonnet` → SDK sends "sonnet", proxy rewrites to "openai/gpt-4o"

3. **Backend forwards to Bifrost** (line 62)
   - Builds upstream request to `http://bifrost:8080/anthropic/{path}`
   - Streams the response back with status code intact (line 83)

4. **Bifrost injects real API key** (from `bifrost/config.json`)
   - Config file contains provider definitions with API key references like `env.ANTHROPIC_API_KEY`
   - Bifrost reads from environment variables and injects the real key
   - Forwards to the provider's actual API

5. **Response flows back** through proxy → sidecar → frontend

### 4. What Could Cause 400 Status Code Response

A 400 (Bad Request) error from Bifrost can occur from several sources:

#### **From Sidecar Validation** (line 60 of `sidecar/src/server.ts`):
```typescript
if (!body.message || !body.system_prompt) {
  res.status(400).json({ error: "message and system_prompt are required" });
  return;
}
```
- Missing `message` or `system_prompt` in the sidecar's `/query` POST body

#### **From Bifrost Configuration Issues**:
1. **Missing API key in config.json**
   - Bifrost config references `env.ANTHROPIC_API_KEY` but the env var is not set
   - Bifrost returns 400 when it can't inject a real key

2. **Invalid provider configuration**
   - Malformed `bifrost/config.json` (JSON syntax errors, missing required fields)
   - Schema validation errors against Bifrost's schema: `https://www.getbifrost.ai/schema`

3. **Custom provider misconfiguration** (lines 33-49 in `bifrost/config.example.json`):
   ```json
   "custom_provider_config": {
     "base_provider_type": "openai"  // Must be "openai" for OpenAI-compatible APIs
   }
   ```
   - Missing or invalid `base_provider_type`
   - Invalid `base_url` for custom providers

#### **From Proxy Model Rewriting**:
- **Rewrite failure**: The `rewrite_model_in_body()` function (lines 22-42 of `proxy.py`) parses the request body as JSON. If:
  - The body is not valid JSON
  - The `model` field is missing or not a string
  - Then the rewrite is silently skipped, and the original model name is sent to Bifrost
  - If the model doesn't exist in Bifrost's config, Bifrost returns 400

- **@suffix conflicts** (README.md, line 100):
  - If `ORCHESTRATOR_MODEL=haiku` and `REDACTED@haiku`
  - Both resolve to `haiku` after proxy rewriting
  - Proxy cannot distinguish orchestrator from subagent traffic → 400 from Bifrost (invalid model)

#### **From Upstream (Bifrost → Provider)**:
- Bifrost forwards a 400 from Anthropic/OpenAI unchanged (line 83 of `proxy.py`)
- Could be due to:
  - Invalid API key (wrong format, expired, disabled)
  - Unsupported model name
  - Invalid request body (missing `messages`, `max_tokens`, etc.)
  - Rate limit hit (actually 429, not 400)

   168→async def stream_chat(
   169→    message: str,
   170→    session_id: str | None = None,
   171→    db: Database | None = None,
   172→    conversation_history: list[dict] | None = None,
   173→    langfuse_session_id: str | None = None,
   174→    backend_session_id: str | None = None,
   175→) -> AsyncIterator[str]:
   176→    """Stream agent chat responses as SSE events via containerized sidecar."""
   177→    from app.container_manager import container_manager
   178→    if container_manager is None:
   179→        raise RuntimeError("Docker is not available. Container mode requires Docker.")
   180→    if db is None:
   181→        raise ValueError("db must be provided")
   182→
   183→    import httpx
   184→    import asyncio
   185→
   186→    query_message = _build_message_with_history(message, conversation_history)
   187→    system_prompt = build_system_prompt(db)
   188→
   189→    # Pass Langfuse credentials to the container so the sidecar's
   190→    # TypeScript Langfuse SDK can create traces directly.
   191→    env: dict[str, str] = {
   192→        "ANTHROPIC_API_KEY": "placeholder",
   193→        "ANTHROPIC_BASE_URL": f"{BACKEND_BASE_URL}/anthropic",
   194→    }
   195→    if LANGFUSE_ENABLED:
   196→        env["LANGFUSE_PUBLIC_KEY"] = LANGFUSE_PUBLIC_KEY
   197→        env["LANGFUSE_SECRET_KEY"] = LANGFUSE_SECRET_KEY
   198→        env["LANGFUSE_BASE_URL"] = LANGFUSE_BASE_URL
   199→
   200→    # Use the backend session ID (X-Session-ID header) for both:
   201→    # 1. MCP SSE URL — so the container queries the correct DuckDB instance
   202→    # 2. Container lifecycle key — so the same container is reused across
   203→    #    requests from the same browser tab (the Claude agent session_id
   204→    #    changes after the first response, which would orphan the container)
   205→    stable_session = backend_session_id or session_id or "default"
   206→
   207→    try:
   208→        # Send SSE keepalive immediately so the HTTP response starts and
   209→        # intermediate proxies (Vite, nginx) don't drop the idle connection
   210→        # before we've finished the blocking Docker container creation.
   211→        yield ": keepalive\n\n"
   212→
   213→        # container_manager.create() is synchronous (blocking Docker API call).
   214→        # Run it in a thread executor so the event loop stays responsive and
   215→        # can continue flushing keepalives to the client during startup.
   216→        # gVisor (runsc) containers can take 10-30 seconds to spin up.
   217→        loop = asyncio.get_event_loop()
   218→        create_future = loop.run_in_executor(None, container_manager.create, stable_session, env)
   219→
   220→        max_create_wait = 60.0
   221→        elapsed = 0.0
   222→        while not create_future.done():
   223→            await asyncio.sleep(2.0)
   224→            elapsed += 2.0
   225→            if elapsed >= max_create_wait:
   226→                create_future.cancel()
   227→                raise RuntimeError(f"Container creation timed out after {max_create_wait:.0f}s")
   228→            yield ": keepalive\n\n"
   229→        info = await create_future
   230→
   231→        # Wait for container to be ready
   232→        for attempt in range(10):
   233→            try:
   234→                async with httpx.AsyncClient(timeout=httpx.Timeout(5.0)) as check_client:
   235→                    resp = await check_client.get(f"{info.url}/health")
   236→                    if resp.status_code == 200:
   237→                        break
   238→            except Exception:
   239→                pass
   240→            yield ": keepalive\n\n"
   241→            await asyncio.sleep(1)
   242→        else:
   243→            raise RuntimeError("Sidecar container failed health check after 10 attempts")
   244→
   245→        payload: dict = {
   246→            "message": query_message,
   247→            "session_id": session_id,
   248→            "system_prompt": system_prompt,
   249→            "model": ORCHESTRATOR_MODEL_SDK,
   250→            "mcp_server_url": f"{BACKEND_BASE_URL}/mcp/sse?session_id={stable_session}",
   251→            "env": {
   252→                "ANTHROPIC_API_KEY": "placeholder",
   253→                "ANTHROPIC_BASE_URL": f"{BACKEND_BASE_URL}/anthropic",
   254→            },
   255→            "agents": {
   256→                name: {
   257→                    "description": agent_def.description,
   258→                    "prompt": agent_def.prompt,
   259→                    "tools": agent_def.tools,
   260→                    "model": agent_def.model,
   261→                }
   262→                for name, agent_def in build_subagent_definitions(db).items()
   263→            },
   264→        }
   265→        if langfuse_session_id:
   266→            payload["langfuse_session_id"] = langfuse_session_id
   267→        # Pass original message & history separately for Langfuse trace metadata
   268→        if conversation_history:
   269→            payload["original_message"] = message
   270→            payload["conversation_history"] = conversation_history
   271→
   272→        has_tool_calls = False
   273→        has_thinking = False
   274→        done_sent = False
   275→        waiting_for_user = False
   276→        tool_names: dict[str, str] = {}
   277→        tool_sqls: dict[str, str] = {}
   278→        # Track subagent text output from intermediate assistant messages.
   279→        # The TypeScript SDK's Task tool_result contains only metadata (agentId,
   280→        # usage), not the subagent's actual output.  The real output arrives in
   281→        # assistant messages whose parent_tool_use_id matches the Task tool ID.

   287→            async with client.stream("POST", f"{info.url}/query", json=payload) as response:

   298→                            line = await line_iter.__anext__()
   299→                    except StopAsyncIteration:
   300→                        break

   306→                    try:
   307→                        msg = json.loads(raw)
   308→                    except json.JSONDecodeError:
   309→                        continue
   310→
   311→                    msg_type = msg.get("type")
   312→                    # --- Token-level streaming events from SDK ---
   313→                    if msg_type == "stream_event":
   314→                        event = msg.get("event", {})
   315→                        event_type = event.get("type", "")
   316→                        stream_parent = msg.get("parent_tool_use_id")

   331→                                    # complete assistant message for the
   332→                                    # subagent's final turn).
   333→                                    if is_subagent_event:
   334→                                        subagent_texts[stream_parent] = subagent_texts.get(stream_parent, "") + text
   335→                                    else:
   336→                                        event_name = "answer" if has_tool_calls else "thinking"
   337→                                        yield f"event: {event_name}\ndata: {json.dumps({'text': text})}\n\n"
   338→
   339→                        elif event_type == "content_block_start":
   340→                            block = event.get("content_block", {})
   341→                            block_type = block.get("type")
   342→                            if block_type == "thinking":
   343→                                if not is_subagent_event:
   344→                                    has_thinking = True
   345→                            elif block_type == "text":
   346→                                if has_thinking and not is_subagent_event:
   347→                                    yield f"event: thinking_done\ndata: {json.dumps({})}\n\n"

   349→                                if not is_subagent_event:
   350→                                    has_thinking = False
   351→                                    has_tool_calls = True

   353→                    # --- Complete assistant message (contains tool_use blocks) ---
   354→                    elif msg_type == "assistant":
   355→                        message_obj = msg.get("message", {})
   356→                        parent_tool_use_id = msg.get("parent_tool_use_id")

   359→                        # These carry the real subagent output (e.g. chart JSON)
   360→                        # that the Task tool_result metadata lacks.
   361→                        if parent_tool_use_id and parent_tool_use_id in tool_names:
   362→                            text_parts = []
   363→                            for block in message_obj.get("content", []):
   364→                                if block.get("type") == "text" and block.get("text"):

   367→                                subagent_texts[parent_tool_use_id] = "\n".join(text_parts)

   371→                            block_type = block.get("type")
   372→                            if block_type == "tool_use":
   373→                                has_tool_calls = True

   395→                                if "ask_user_question" in tool_name:

    79→#### Per-Subagent Model Routing
    80→
    81→You can route each agent (orchestrator, SQL subagent, chart subagent) to a different LLM provider by using the `@suffix` syntax:
    82→
    83→```
    84→ORCHESTRATOR_MODEL=openai/gpt-4o@sonnet
    85→REDACTED@haiku
    86→REDACTED@haiku
    87→```
    88→
    89→The format is `real_model@sdk_alias`. The SDK alias (after `@`) is the model name the Claude Agent SDK sees; the real model (before `@`) is what the backend proxy rewrites it to before forwarding to Bifrost. This lets you use any provider Bifrost supports (OpenAI, Bedrock, etc.) while keeping the SDK configuration unchanged.
    90→
    91→**How it works:**
    92→
    93→1. The SDK sends requests using the alias (e.g. `sonnet`, `haiku`).
    94→2. A lightweight reverse proxy on the backend (`/anthropic/*`) intercepts these requests.
    95→3. The proxy rewrites the `model` field to the real provider model (e.g. `openai/gpt-4o`) and forwards the request to Bifrost.
    96→4. Bifrost routes the request to the correct provider.
    97→
    98→Without `@suffix`, model values are used as-is (direct Anthropic routing).
    99→
   100→> **Warning:** The `@suffix` must NOT match the `ORCHESTRATOR_MODEL`'s Anthropic model name. For example, `ORCHESTRATOR_MODEL=haiku` with `REDACTED@haiku` will conflict because the proxy cannot distinguish orchestrator traffic from subagent traffic when both resolve to the same model name.

   175→## Security
   176→
   177→### Bifrost LLM Gateway
   178→
   179→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   180→
   181→Instead, a [Bifrost](https://github.com/maximhq/bifrost) LLM gateway service manages API keys centrally and routes requests to LLM providers:
   182→
   183→```
   184→Sidecar Container
   185→  → ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic
   186→  → ANTHROPIC_API_KEY=placeholder
   187→        ↓
   188→Bifrost Gateway (/anthropic)
   189→  → ignores client-sent key
   190→  → injects the real provider API key
   191→  → forwards request to provider (Anthropic, OpenAI, Bedrock, etc.)
   192→```
   193→
   194→**How it works:**
   195→
   196→1. Bifrost runs as a Docker Compose service with real API keys stored in `bifrost/config.json` (referencing environment variables).
   197→2. Sidecar containers receive a placeholder `ANTHROPIC_API_KEY` and point `ANTHROPIC_BASE_URL` to Bifrost's native `/anthropic` endpoint.
   198→3. Bifrost injects the real provider API key when forwarding requests upstream. The Claude Agent SDK works unchanged since Bifrost speaks native Anthropic Messages API.
   199→4. Additional providers (OpenAI, Bedrock, Vertex, etc.) can be added to `bifrost/config.json` or via Bifrost's Web UI. Use provider prefixes in model names (e.g., `openai/gpt-4o-mini`) to route subagent requests to different providers. See [`bifrost/config.example.json`](bifrost/config.example.json) for configuration examples.
   200→
   201→The sidecar container only ever holds a placeholder string. Even if a tool call reads the environment, it cannot obtain any real API key.
   202→
   203→### Container Isolation
   204→
   205→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   206→
   207→**Architecture:**
   208→
   209→```
   210→Browser
   211→  │
   212→  ▼
   213→FastAPI Backend (host)
   214→  ├── Chat route ──► ContainerManager ──► Docker SDK
   215→  │                       │
   216→  │                       ▼
   217→  │               ┌──────────────────────┐
   218→  │               │  gVisor Sandbox      │
   219→  │               │                      │
   220→  │               │  Sidecar Container   │
   221→  │               │  (Node.js + Claude)  │
   222→  │               │                      │
   223→  │               │  POST /query → SSE   │
   224→  │               └──────┬───────────────┘
   225→  │                      │
   226→  │              ├──► Bifrost Gateway (:8080/anthropic)  (LLM routing)
   227→  ├── /mcp/sse   ◄───────┘  (DuckDB MCP bridge)
   228→  │
   229→  └── DuckDB (per-user, disk-persisted)
   230→```
   231→
   232→The data flow for a chat message is:
   233→
   234→1. Frontend sends a chat message to the FastAPI backend.
   235→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, configured to route LLM calls through the Bifrost gateway.
   236→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   237→4. Claude CLI talks to the Bifrost gateway (`/anthropic`) for LLM API access (using a placeholder key; Bifrost injects the real key).
   238→5. Claude CLI's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   239→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   240→7. On session end, the container is stopped and removed.
   241→
   242→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, the Agent SDK, and the `@anthropic-ai/claude-code` CLI (required by the SDK internally). Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   243→
   244→**MCP SSE bridge:** The backend exposes the DuckDB `execute_sql` tool at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`). Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized Claude CLI reaches DuckDB on the host without any direct database access inside the container.
   245→

   247→
   248→- [Docker](https://docs.docker.com/get-docker/)

   251→> **Note:** gVisor requires **Linux** (kernel 4.14.77+, x86_64 or ARM64). It is not available on macOS or Windows. You still get container isolation (filesystem, process, network, capability drop, read-only rootfs) — only gVisor's syscall interception layer is absent.
