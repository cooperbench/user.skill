### 9. KEY DESIGN INSIGHTS

1. **Model names are provider-prefixed**: The format is `provider/model-id` (e.g., `openai/gpt-5.2-2025-12-11`), not just `haiku`. This allows Bifrost to route to the correct provider.

2. **Subagent names vs. model names are different**:
   - **Subagent names**: `sql-analyst`, `chart-builder` (used for UI display and routing to the right agent)
   - **Model names**: `openai/gpt-5.2-2025-12-11` (used to select which LLM processes the agent's prompt)

3. **Bifrost provides the routing layer**: The backend and sidecar don't know about real API keys. They only know:
   - Model names with provider prefixes
   - `ANTHROPIC_BASE_URL` pointing to Bifrost's `/anthropic` endpoint
   - Bifrost handles key management and multi-provider routing

4. **Frontend never sees model names**: The UI displays subagent names (`sql-analyst`, `chart-builder`) for identification, not the model IDs. The actual model used is metadata that could be added to traces but isn't shown in the UI.

5. **Unprefixed names default to Anthropic**: If you use `haiku` without a prefix, Bifrost assumes you mean the Anthropic provider (equivalent to `anthropic/haiku`).

6. **All three models are independent**: The orchestrator model, SQL subagent model, and chart subagent model can each use different providers in the same conversation.

Yes, that's a limitation of the Claude Agent SDK. The `AgentDefinition.model` only accepts:

- `"sonnet"` → maps to a specific Claude Sonnet model
- `"opus"` → maps to a specific Claude Opus model
- `"haiku"` → maps to a specific Claude Haiku model
- `"inherit"` → uses the orchestrator's model

These are all **Claude model aliases**. There's no way to pass an arbitrary model string like `openai/gpt-4o-mini` for a subagent.

So your options are:

1. **Same model everywhere** (`"inherit"`) — orchestrator and subagents all use `ANTHROPIC_MODEL` (e.g., `openai/gpt-5.2-2025-12-11`). This is what we just implemented.

2. **Mix Claude models only** — e.g., orchestrator uses `sonnet`, subagents use `haiku`. But these are Claude-only aliases — they can't point to OpenAI models even through Bifrost.

3. **Mix providers by architecture change** — instead of using the SDK's built-in agent system, you could implement subagents as separate HTTP calls from the backend (bypassing the SDK's Task tool entirely). Each call could use a different model via Bifrost. This is more work but gives full flexibility.

# Provider Configuration Options Analysis

Based on the documentation provided, here are the available methods for injecting additional parameters into provider requests:

## Documented Parameter Injection Methods

### 1. **Passthrough Extra Parameters** (Primary Method)
The documentation explicitly supports passing custom parameters via the `extra_params` field with the `x-bf-passthrough-extra-params` header:

> "Enable passthrough mode for extra parameters. When enabled, any parameters in the `extra_params` field (or provider-specific extra parameter fields) will be merged directly into the request sent to the provider"

**Usage:**
```json
{
  "model": "openai/gpt-4o-mini",
  "messages": [{"role": "user", "content": "Hello!"}],
  "extra_params": {
    "custom_param": "value",
    "another_param": 123,
    "nested_param": {"nested_key": "nested_value"}
  }
}
```

**Key Constraints:**
- Only works with JSON requests (not multipart/form-data)
- Nested parameters merge recursively with existing structures

This is a limitation of the current architecture. Here's why:

## The problem

```
Claude Agent SDK  →  Anthropic API format  →  Bifrost  →  OpenAI API format
```

The Claude Agent SDK **only speaks Anthropic API format**. It doesn't have a way to pass OpenAI-specific body parameters like `reasoning_effort`. Bifrost translates the request format, but it can only forward what it receives.

## Bifrost does support it — but the SDK can't use it

Bifrost has an `extra_params` passthrough mechanism:

```json
{
  "model": "openai/gpt-5.2-2025-12-11",
  "messages": [...],
  "extra_params": {
    "reasoning_effort": "medium"
  }
}
```

This requires the `x-bf-passthrough-extra-params` header and `extra_params` in the request body. But the Claude Agent SDK doesn't expose any way to inject custom fields or headers into its API calls.

## Practical options

1. **Don't use thinking models** — Use a non-reasoning OpenAI model (e.g., `gpt-4o`) where `reasoning_effort` isn't needed.

2. **Use Anthropic extended thinking instead** — If you switch `ANTHROPIC_MODEL` to a Claude model (e.g., `claude-sonnet-4-6`), the SDK natively supports Anthropic's extended thinking/budget tokens.

3. **Bypass the SDK for subagents** — Build a custom subagent system that calls Bifrost directly (option 3 from our earlier discussion), where you fully control the request body.

In short: as long as the Claude Agent SDK is in the request path, you're limited to parameters the Anthropic API supports. OpenAI-specific parameters like `reasoning_effort` can't be injected.
