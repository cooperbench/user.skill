   189→## Security
   190→
   191→### LiteLLM Proxy
   192→
   193→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass provider API keys (e.g., `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the keys.
   194→
   195→Instead, a [LiteLLM](https://docs.litellm.ai/) proxy container sits between the sidecar and LLM providers:
   196→
   197→```
   198→Sidecar Container
   199→  → ANTHROPIC_BASE_URL=http://litellm:4000
   200→  → ANTHROPIC_API_KEY=<LiteLLM master key>
   201→        ↓
   202→LiteLLM Proxy (Docker container, port 4000)
   203→  → validates master key
   204→  → routes to correct provider (Anthropic, OpenAI, Google, etc.)
   205→  → injects real provider API keys from its config
   206→```
   207→
   208→**How it works:**
   209→
   210→1. The LiteLLM proxy runs as a Docker container with all real provider API keys configured in `litellm_config.yaml` (read from environment variables).
   211→2. Sidecar containers receive only the `LITELLM_MASTER_KEY` — a shared authentication key for the proxy, not a real provider credential.
   212→3. LiteLLM validates the master key, routes the request to the correct provider based on the model name, and injects the real API key.
   213→4. Even if a tool call reads the sidecar's environment, it only gets the LiteLLM master key, which is useless outside the Docker network.
   214→
   215→This also enables multi-provider support: add any LiteLLM-supported provider to `litellm_config.yaml` without changing application code.
   216→
   217→### Container Isolation
   218→
   219→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   220→
   221→**Architecture:**
   222→
   223→```
   224→Browser
   225→  │
   226→  ▼
   227→FastAPI Backend (host)
   228→  ├── Chat route ──► ContainerManager ──► Docker SDK
   229→  │                       │
   230→  │                       ▼
   231→  │               ┌──────────────────────┐
   232→  │               │  gVisor Sandbox      │
   233→  │               │                      │
   234→  │               │  Sidecar Container   │
   235→  │               │  (Node.js + Claude)  │
   236→  │               │                      │
   237→  │               │  POST /query → SSE   │
   238→  │               └──────┬───────────────┘
   239→  │                      │
   240→  │   LiteLLM Proxy ◄───┘  (LLM API gateway)
   241→  ├── /mcp/sse   ◄──────┘  (DuckDB MCP bridge)
   242→  │
   243→  └── DuckDB (per-user, disk-persisted)
   244→```
   245→
   246→The data flow for a chat message is:
   247→
   248→1. Frontend sends a chat message to the FastAPI backend.
   249→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, passing the LiteLLM master key.
   250→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   251→4. The sidecar talks to the LiteLLM proxy for LLM API access (using the master key, never real provider keys). LiteLLM routes the request to the configured provider.
   252→5. The sidecar's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   253→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   254→7. On session end, the container is stopped and removed.
   255→
   256→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, the Agent SDK, and the `@anthropic-ai/claude-code` CLI (required by the SDK internally). Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   257→
   258→**MCP SSE bridge:** The backend exposes the DuckDB `execute_sql` tool at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`). Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized Claude CLI reaches DuckDB on the host without any direct database access inside the container.
   259→
