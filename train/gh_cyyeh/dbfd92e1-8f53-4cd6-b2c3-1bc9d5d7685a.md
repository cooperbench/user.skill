    96→DEFAULT_TOOL_MODEL=                # optional, fallback model for SDK built-in tools (see below)
    97→MAX_TOTAL_SIZE_BYTES=524288000      # optional, max upload size in bytes (default: 500 MB)
    98→```

   100→> `ANTHROPIC_API_KEY` and `ORCHESTRATOR_MODEL` are only needed for the AI agent. The SQL playground works without them, but both require the backend running.
   101→
   102→#### Per-Subagent Model Routing
   103→
   104→You can route each agent (orchestrator, SQL subagent) to a different LLM provider by using the `@suffix` syntax:
   105→
   106→```
   107→ORCHESTRATOR_MODEL=openai/gpt-4o@sonnet
   108→REDACTED@haiku
   109→```
   110→
   111→The format is `real_model@sdk_alias`. The SDK alias (after `@`) is the model name the Claude Agent SDK sees; the real model (before `@`) is what the backend proxy rewrites it to before forwarding to Bifrost. This lets you use any provider Bifrost supports (OpenAI, Bedrock, etc.) while keeping the SDK configuration unchanged.
   112→
   113→**How it works:**
   114→
   115→1. The SDK sends requests using the alias (e.g. `sonnet`, `haiku`).
   116→2. A lightweight reverse proxy on the backend (`/anthropic/*`) intercepts these requests.
   117→3. The proxy rewrites the `model` field to the real provider model (e.g. `openai/gpt-4o`) and forwards the request to Bifrost.
   118→4. Bifrost routes the request to the correct provider.
   119→
   120→Without `@suffix`, model values are used as-is (direct Anthropic routing).
   121→
   122→#### Default Tool Model
   123→
   124→The Claude Agent SDK's built-in tools (e.g. WebFetch) internally use their own Anthropic models (e.g. `claude-haiku-4-5-20251001`). When routing all traffic through a non-Anthropic provider, these models are not in the rewrite map and will fail because they lack a provider prefix.
   125→
   126→Set `DEFAULT_TOOL_MODEL` to catch any model not matched by the per-agent rewrites:
   127→
   128→```
   129→DEFAULT_TOOL_MODEL=openai/gpt-4o-mini
   130→```
   131→
   132→Any request whose model does not match a configured rewrite is rewritten to this value before forwarding to Bifrost. When empty (default), unmatched models pass through unchanged.
   133→
   134→> **Warning:** The `@suffix` must NOT match the `ORCHESTRATOR_MODEL`'s Anthropic model name. For example, `ORCHESTRATOR_MODEL=haiku` with `REDACTED@haiku` will conflict because the proxy cannot distinguish orchestrator traffic from subagent traffic when both resolve to the same model name.

   214→## Security
   215→
   216→### Bifrost LLM Gateway
   217→
   218→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   219→
   220→Instead, a [Bifrost](https://github.com/maximhq/bifrost) LLM gateway service manages API keys centrally and routes requests to LLM providers:
   221→
   222→```
   223→Sidecar Container
   224→  → ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic
   225→  → ANTHROPIC_API_KEY=placeholder
   226→        ↓
   227→Bifrost Gateway (/anthropic)
   228→  → ignores client-sent key
   229→  → injects the real provider API key
   230→  → forwards request to provider (Anthropic, OpenAI, Bedrock, etc.)
   231→```
   232→
   233→**How it works:**
   234→
   235→1. Bifrost runs as a Docker Compose service with real API keys stored in `bifrost/config.json` (referencing environment variables).
   236→2. Sidecar containers receive a placeholder `ANTHROPIC_API_KEY` and point `ANTHROPIC_BASE_URL` to Bifrost's native `/anthropic` endpoint.
   237→3. Bifrost injects the real provider API key when forwarding requests upstream. The Claude Agent SDK works unchanged since Bifrost speaks native Anthropic Messages API.
   238→4. Additional providers (OpenAI, Bedrock, Vertex, etc.) can be added to `bifrost/config.json` or via Bifrost's Web UI. Use provider prefixes in model names (e.g., `openai/gpt-4o-mini`) to route subagent requests to different providers. See [`bifrost/config.example.json`](bifrost/config.example.json) for configuration examples.
   239→
   240→The sidecar container only ever holds a placeholder string. Even if a tool call reads the environment, it cannot obtain any real API key.
   241→
   242→### Container Isolation
   243→
   244→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   245→
   246→**Architecture:**
   247→
   248→```
   249→Browser
   250→  │
   251→  ▼
   252→FastAPI Backend (host)
   253→  ├── Chat route ──► ContainerManager ──► Docker SDK
   254→  │                       │
   255→  │                       ▼
   256→  │               ┌──────────────────────┐
   257→  │               │  gVisor Sandbox      │
   258→  │               │                      │
   259→  │               │  Sidecar Container   │
   260→  │               │  (Node.js + Claude)  │
   261→  │               │                      │
   262→  │               │  POST /query → SSE   │
   263→  │               └──────┬───────────────┘
   264→  │                      │
   265→  │              ├──► Bifrost Gateway (:8080/anthropic)  (LLM routing)
   266→  ├── /mcp/sse   ◄───────┘  (DuckDB MCP bridge)
   267→  │
   268→  └── DuckDB (per-user, disk-persisted)
   269→```
   270→
   271→The data flow for a chat message is:
   272→
   273→1. Frontend sends a chat message to the FastAPI backend.
   274→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, configured to route LLM calls through the Bifrost gateway.
   275→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   276→4. The agent talks to the Bifrost gateway (`/anthropic`) for LLM API access (using a placeholder key; Bifrost injects the real key).
   277→5. The agent's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   278→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   279→7. On session end, the container is stopped and removed.
   280→
   281→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, and the Agent SDK. Containers run with a read-only root filesystem, all Linux capabilities dropped, no Docker socket access, and a non-root user. The host `skills/` directory is bind-mounted read-only at `/app/.claude/skills/` (the project-level path) so the SDK's built-in Skill tool can discover and invoke them.
   282→
   283→**MCP SSE bridge:** The backend exposes tools at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`): `execute_sql` for DuckDB queries, `render_chart` for chart generation, `ask_user_question` for interactive clarification, `create_skill` for agent-driven skill creation, and `save_memory` / `recall_memories` / `forget_memory` for persistent agent memory. Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized agent reaches DuckDB on the host without any direct database access inside the container.
