## Root Cause

The issue is in `MessageBubble.tsx` line 308 — the streaming answer text display has a `!hasAnswer` guard that breaks on the current branch.

**What changed**: The current branch introduced `phaseRef` in `AgentContext.tsx`. After `onThinkingDone`, when a tool call or subagent starts, accumulated text is now pushed as `{ type: 'answer' }` segments instead of `{ type: 'thinking' }` (as on main):

```ts
// current branch (AgentContext.tsx, e.g. line 127)
const segType = phaseRef.current === 'answer' ? 'answer' : 'thinking';
segmentsRef.current.push({ type: segType, text: currentTextRef.current });
```

**The cascading problem**:

1. Orchestrator writes "Let me query the data..." → text accumulates in buffer
2. Orchestrator calls the subagent → `onToolCall`/`onSubagentStart` fires → text gets committed as an **answer** segment
3. Now `hasAnswer = true` (line 171: `message.segments!.some((s) => s.type === 'answer')`)
4. Subagent runs and completes → orchestrator writes final answer ("Here are the results...")
5. This text accumulates in `textBufferRef` → `currentTextRef` → `message.content` as `streamingRemainder`
6. **But line 308 checks `isInAnswerPhase && !hasAnswer`** — since `hasAnswer` is now `true`, the streaming remainder is **never displayed**
7. The text only appears all at once when `onDone` fires and commits it as a final answer segment

**On main**, text was always pushed as `thinking`, so `hasAnswer` stayed `false` during streaming, and the `streamingRemainder` displayed correctly in the answer section.

## Fix

Remove `!hasAnswer` from line 308 in `MessageBubble.tsx`. The `streamingRemainder` is only computed when `message.isStreaming` (line 160), so it's already `undefined` for completed messages — no risk of double-display.
