### 4. Key Architectural Patterns

**Credential Proxy Pattern:**
- UUID tokens with 10-minute TTL minted per agent session
- Sidecar receives UUID token instead of real API key
- Backend reverse proxy at `/anthropic` validates token and swaps for real key
- Tokens auto-revoked on session end or TTL expiry

**MCP SSE Bridge Pattern:**
- Backend exposes DuckDB tools over HTTP via MCP SSE protocol
- Sidecar connects back to `/mcp/sse?session_id={id}` endpoint
- Tool results routed to correct per-user DuckDB instance

**Per-User Session Isolation:**
- Client-generated `X-Session-ID` header (UUID)
- Each session gets isolated DuckDB instance on disk
- SessionManager tracks all active sessions
- TTL-based cleanup (300 seconds)
- Sessions survive idle timeouts, deleted only on explicit tab close

**Subagent Architecture:**
- Orchestrator delegates to specialized subagents
- **sql-analyst**: Writes and executes SQL queries (model: Haiku by default)
- **chart-builder**: Generates Plotly visualizations (model: Haiku by default)
- Intermediate subagent messages filtered from main output (agent mode only)

    80→
    81→You can route each agent (orchestrator, SQL subagent, chart subagent) to a different LLM provider by using the `@suffix` syntax:

    84→ORCHESTRATOR_MODEL=openai/gpt-4o@sonnet

    89→The format is `real_model@sdk_alias`.     92→

    95→3. The proxy rewrites the `model` field to the real provider model (e.g. `openai/gpt-4o`) and forwards the request to Bifrost.
    96→4. Bifrost routes the request to the correct provider.
    97→
    98→Without `@suffix`, model values are used as-is (direct Anthropic routing).

   175→## Security
   176→
   177→### Bifrost LLM Gateway
   178→
   179→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   180→
   181→Instead, a [Bifrost](https://github.com/maximhq/bifrost) LLM gateway service manages API keys centrally and routes requests to LLM providers:
   182→
   183→```
   184→Sidecar Container
   185→  → ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic
   186→  → ANTHROPIC_API_KEY=placeholder
   187→        ↓
   188→Bifrost Gateway (/anthropic)
   189→  → ignores client-sent key
   190→  → injects the real provider API key
   191→  → forwards request to provider (Anthropic, OpenAI, Bedrock, etc.)
   192→```
   193→
   194→**How it works:**
   195→
   196→1. Bifrost runs as a Docker Compose service with real API keys stored in `bifrost/config.json` (referencing environment variables).
   197→2. Sidecar containers receive a placeholder `ANTHROPIC_API_KEY` and point `ANTHROPIC_BASE_URL` to Bifrost's native `/anthropic` endpoint.
   198→3. Bifrost injects the real provider API key when forwarding requests upstream. The Claude Agent SDK works unchanged since Bifrost speaks native Anthropic Messages API.
   199→4. Additional providers (OpenAI, Bedrock, Vertex, etc.) can be added to `bifrost/config.json` or via Bifrost's Web UI. Use provider prefixes in model names (e.g., `openai/gpt-4o-mini`) to route subagent requests to different providers. See [`bifrost/config.example.json`](bifrost/config.example.json) for configuration examples.
   200→
   201→The sidecar container only ever holds a placeholder string. Even if a tool call reads the environment, it cannot obtain any real API key.
   202→
   203→### Container Isolation
   204→
   205→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   206→
   207→**Architecture:**
   208→
   209→```
   210→Browser
   211→  │
   212→  ▼
   213→FastAPI Backend (host)
   214→  ├── Chat route ──► ContainerManager ──► Docker SDK
   215→  │                       │
   216→  │                       ▼
   217→  │               ┌──────────────────────┐
   218→  │               │  gVisor Sandbox      │
   219→  │               │                      │
   220→  │               │  Sidecar Container   │
   221→  │               │  (Node.js + Claude)  │
   222→  │               │                      │
   223→  │               │  POST /query → SSE   │
   224→  │               └──────┬───────────────┘
   225→  │                      │
   226→  │              ├──► Bifrost Gateway (:8080/anthropic)  (LLM routing)
   227→  ├── /mcp/sse   ◄───────┘  (DuckDB MCP bridge)
   228→  │
   229→  └── DuckDB (per-user, disk-persisted)
   230→```
   231→
   232→The data flow for a chat message is:
   233→
   234→1. Frontend sends a chat message to the FastAPI backend.
   235→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, configured to route LLM calls through the Bifrost gateway.
   236→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   237→4. Claude CLI talks to the Bifrost gateway (`/anthropic`) for LLM API access (using a placeholder key; Bifrost injects the real key).
   238→5. Claude CLI's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   239→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   240→7. On session end, the container is stopped and removed.
   241→
   242→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, the Agent SDK, and the `@anthropic-ai/claude-code` CLI (required by the SDK internally). Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   243→
   244→**MCP SSE bridge:** The backend exposes the DuckDB `execute_sql` tool at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`). Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized Claude CLI reaches DuckDB on the host without any direct database access inside the container.
