# Plan: Add docker-compose.yml and update Makefile/README

## Context

The project currently has individual Dockerfiles for the main app and sidecar, but no docker-compose file to orchestrate them together. Users must manually build images, create Docker networks, and manage container isolation setup. A `docker-compose.yml` will simplify running all services (app + sidecar) with a single command.

## Design

### Architecture

The sidecar is **not a static service** — it's spawned on-demand per-session by the backend's `ContainerManager` via the Docker SDK. So docker-compose will:

1. **Build** both images (app + sidecar)
2. **Run** only the app service
3. **Provide** the Docker socket so the app can spawn sidecar containers dynamically
4. **Create** the `agent-sandbox` network shared between app and sidecar containers

The sidecar service in docker-compose exists only for image building (using `profiles` to prevent it from starting).

### `PROXY_BASE_URL` routing

When the backend runs inside a docker-compose container, sidecar containers need to reach it via the Docker network. Using `container_name: duckdb-data-agent` gives the app a fixed hostname, so `PROXY_BASE_URL=http://duckdb-data-agent:10000`.

### Docker socket access

The app container runs as `appuser` (non-root). To access `/var/run/docker.sock`, we use `group_add` with a configurable `DOCKER_GID` env var (defaults to `0` which works on macOS Docker Desktop; Linux users set it to their host's docker group GID).

## Changes

### 1. Create `docker-compose.yml` (new file)

```yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    image: duckdb-data-agent:latest
    container_name: duckdb-data-agent
    ports:
      - "${APP_PORT:-10000}:10000"
    env_file:
      - backend/.env
    environment:
      CONTAINER_ENABLED: "true"
      CONTAINER_IMAGE: duckdb-agent-sidecar:latest
      CONTAINER_NETWORK: agent-sandbox
      PROXY_BASE_URL: http://duckdb-data-agent:10000
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    group_add:
      - "${DOCKER_GID:-0}"
    networks:
      - agent-sandbox
    restart: unless-stopped

  sidecar:
    build:
      context: ./sidecar
      dockerfile: Dockerfile
    image: duckdb-agent-sidecar:latest
    profiles:
      - build
    # Never started directly — exists only so `docker compose build`
    # produces the sidecar image. The app spawns sidecar containers
    # on-demand via Docker SDK.

networks:
  agent-sandbox:
    name: agent-sandbox
    driver: bridge
```

Key design decisions:
- `profiles: [build]` on sidecar: `docker compose build` builds it, `docker compose up` doesn't start it
- `container_name: duckdb-data-agent`: fixed hostname for sidecar→backend communication
- `env_file` + `environment`: .env provides API keys, environment block overrides container-specific settings
- `networks.agent-sandbox.name: agent-sandbox`: ensures the network name matches what ContainerManager expects (no project prefix)

   137→## Security
   138→
   139→### Credential Proxy
   140→
   141→When the agent runs, the backend spawns a Claude Code subprocess via the Anthropic Agent SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that subprocess's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   142→
   143→Instead, the backend runs a built-in reverse proxy at `/anthropic` that sits between Claude Code and `api.anthropic.com`:
   144→
   145→```
   146→Claude Code subprocess
   147→  → ANTHROPIC_BASE_URL=http://127.0.0.1:{PORT}/anthropic
   148→  → ANTHROPIC_API_KEY=<short-lived UUID token>
   149→        ↓
   150→FastAPI proxy (/anthropic/{path})
   151→  → validates UUID token
   152→  → swaps it for the real ANTHROPIC_API_KEY
   153→  → forwards request to api.anthropic.com
   154→```
   155→
   156→**How it works:**
   157→
   158→1. Before each agent session, the backend mints a random UUID token with a 10-minute TTL.
   159→2. The token is injected into the subprocess environment as `ANTHROPIC_API_KEY`; the real key is never exposed.
   160→3. The proxy validates every inbound request against the token store and substitutes the real key before forwarding upstream.
   161→4. When the session ends, the token is explicitly revoked in a `finally` block, regardless of success or error.
   162→5. A background task runs every 60 seconds to sweep any tokens that outlived their TTL.
   163→
   164→The subprocess only ever holds a single-session UUID. Even if a tool call reads the environment, all it gets is a temporary token scoped to that conversation.
   165→

   167→
   168→For additional defense in depth, the backend can run each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar") instead of a bare subprocess. This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.

+### Docker Compose
+
+Docker Compose builds both images (app + sidecar) and runs the app with [container isolation](#container-isolation-optional) enabled. The sidecar image is built but not started as a service — the app spawns sidecar containers on-demand via the Docker SDK.
+
+**Prerequisites:** [Docker](https://docs.docker.com/get-docker/) and [Docker Compose](https://docs.docker.com/compose/install/) (included with Docker Desktop).
+
+**Build all images:**
+
+```bash
+make compose-build
+```
+
+**Start the app:**
+
+```bash
+make compose-up
+```
+
+Open http://localhost:10000 to use the app.
+
+**Stop the app:**
+
+```bash
+make compose-down
+```
+
+**Notes:**
+
+- **Linux users:** Set `DOCKER_GID` to your host's docker group GID so the app container can access the Docker socket:
+  ```bash
+  DOCKER_GID=$(getent group docker | cut -d: -f3) make compose-up
+  ```
+  On macOS with Docker Desktop, the default (`0`) works out of the box.
+- **Custom port:** Set `APP_PORT` to expose the app on a different host port (e.g., `APP_PORT=8080 make compose-up`).
+- **Disable container isolation:** Remove the `CONTAINER_ENABLED` override from the `environment` block in `docker-compose.yml` (or set it to `"false"`) to fall back to subprocess mode.
