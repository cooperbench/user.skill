---

## Approach 1: DuckDB Native Readers (Recommended)

DuckDB has built-in readers for all four formats:
- `read_csv_auto()` — already in use
- `read_json_auto()` — handles array-of-objects JSON
- `read_parquet()` — native Parquet support
- DuckDB has a `spatial` extension with Excel support, but it's limited. Instead, use **openpyxl** (Python) to read Excel → write temp CSV per sheet → load via `read_csv_auto()`.

**Trade-offs:**
- Leverages existing DuckDB infrastructure
- Minimal new dependencies (just `openpyxl` for Excel)
- Parquet and JSON are zero-dependency via DuckDB
- Excel conversion adds a small processing step but keeps DuckDB as the single data engine

## Approach 2: Pandas as Middleware

Use pandas to read all formats, then load DataFrames into DuckDB via `duckdb.from_df()`.

**Trade-offs:**
- Adds a heavy dependency (pandas + numpy)
- Doubles memory usage (pandas DataFrame + DuckDB copy)
- More code to maintain
- Overkill when DuckDB reads most formats natively

## Approach 3: DuckDB Extensions Only

Use DuckDB extensions for everything, including the `spatial` extension for Excel (`.xlsx` via GDAL).

**Trade-offs:**
- No Python dependencies
- But the spatial extension is heavy and unreliable for Excel
- Limited Excel support (no multi-sheet, poor type detection)
- Extension availability varies by platform

---

**My recommendation: Approach 1.** DuckDB handles CSV/JSON/Parquet natively with excellent auto-detection. For Excel, `openpyxl` is lightweight and handles multi-sheet workbooks well. This minimizes dependencies while covering all formats reliably.

#### SUGGESTION -- Edge Case in Extension Extraction Logic

**File:** `/Users/cyyeh/Desktop/duckdb-data-agent/frontend/src/components/FileUpload.tsx`, line 24

```typescript
const ext = f.name.toLowerCase().slice(f.name.lastIndexOf('.'));
```

There is a subtle bug here: `toLowerCase()` is called on `f.name`, but `lastIndexOf('.')` is also called on the original `f.name` (not the lowercased version). This is harmless because `lastIndexOf('.')` returns a numeric index and the `.` character is unaffected by case conversion, so the index is the same in both strings. However, the code would be clearer and more robust if written as:

```typescript
const lower = f.name.toLowerCase();
const ext = lower.slice(lower.lastIndexOf('.'));
```

A more significant edge case: if a file has no extension at all (e.g., a file named `"data"`), `lastIndexOf('.')` returns `-1`, and `slice(-1)` returns the last character of the filename (e.g., `"a"`). This would not match any supported extension and would correctly be rejected, so the behavior is safe, but the reason is non-obvious. A small guard would improve readability:

```typescript
const dotIdx = lower.lastIndexOf('.');
const ext = dotIdx >= 0 ? lower.slice(dotIdx) : '';
```
