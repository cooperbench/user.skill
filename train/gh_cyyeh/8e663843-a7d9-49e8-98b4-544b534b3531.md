## Approach 1: LiteLLM in the Credential Proxy (Recommended)

**How it works:** Modify the existing `/anthropic/{path}` proxy route in `proxy.py`. Instead of blindly forwarding to `api.anthropic.com`, detect whether the configured model is non-Anthropic (using LiteLLM's model naming). If so, use `litellm.acompletion()` to translate the Anthropic Messages API request → target provider format, get the response, and translate it back → Anthropic Messages API response format. The Claude Agent SDK never knows the difference.

**Pros:**
- Minimal changes — only `proxy.py` and `config.py` touched
- Claude Agent SDK, sidecar, and frontend stay untouched
- LiteLLM handles 100+ providers and streaming
- Existing credential isolation pattern preserved

**Cons:**
- Some Anthropic-specific features (prompt caching, extended thinking, PDF input) won't work with non-Anthropic models
- Streaming translation adds a small latency layer
- Debugging is harder — errors from other providers need to be translated to Anthropic error format

## Approach 2: LiteLLM Proxy Server Mode

**How it works:** LiteLLM has a built-in proxy server (`litellm --model gpt-4o`). Run it as an embedded ASGI sub-app inside FastAPI, or as a subprocess. Point the credential proxy at LiteLLM instead of `api.anthropic.com`.

**Pros:**
- LiteLLM handles all translation, streaming, retries, and error mapping
- Battle-tested proxy implementation
- Supports model fallbacks, rate limiting, spend tracking out of the box

**Cons:**
- Heavier dependency (LiteLLM proxy has many sub-dependencies)
- More complex deployment (subprocess or sub-app management)
- Less control over the translation behavior

## Approach 3: Direct LiteLLM Library Calls (No Proxy Translation)

**How it works:** Add a new "local agent mode" that bypasses the sidecar entirely. Build a Python agent loop using `litellm.acompletion()` directly in the backend for non-Anthropic models. Keep the Claude Agent SDK path for Anthropic models.

**Pros:**
- Cleanest integration — no response format translation hacks
- Full control over tool use and agent loop for each provider
- Can optimize prompts per provider

**Cons:**
- Major new code path — duplicates agent orchestration logic
- Two different agent loops to maintain
- Subagent delegation would need reimplementation

---

## Design Section 1: Architecture Overview

## Design Section 3: Request/Response Translation

This is the core of the gateway. A new module `backend/app/gateway.py` handles the bidirectional translation using LiteLLM.

**Non-streaming flow:**
1. Receive Anthropic Messages API request body (`model`, `messages`, `system`, `tools`, `max_tokens`, etc.)
2. Convert to OpenAI-compatible format (LiteLLM's internal standard) — messages, tools, system prompt
3. Call `litellm.acompletion(model="gpt-4o", messages=[...], tools=[...])`
4. Convert the OpenAI-format response back to an Anthropic Messages API response (`content` blocks with `type: "text"` / `type: "tool_use"`, `stop_reason`, `usage`, etc.)
5. Return as JSON HTTP response

**Streaming flow:**
1. Same request translation
2. Call `litellm.acompletion(model="gpt-4o", ..., stream=True)`
3. Convert each OpenAI streaming chunk to Anthropic SSE events:
   - Emit `message_start` with message metadata
   - Convert `choices[].delta.content` → `content_block_delta` with `text_delta`
   - Convert `choices[].delta.tool_calls` → `content_block_start` + `content_block_delta` with `input_json_delta`
   - Emit `message_delta` with `stop_reason` and final `usage`
   - Emit `message_stop`
4. Yield as `text/event-stream` response

**Tool use round-trip (critical path):**
- **Request direction:** Anthropic `tools` array (name, description, input_schema) → OpenAI `tools` array (function name, description, parameters). Straightforward mapping.
- **Response direction:** OpenAI `tool_calls` (function name, arguments as JSON string) → Anthropic `tool_use` content blocks (name, input as parsed object, unique `id`).
- **Tool results:** Anthropic `tool_result` messages (with `tool_use_id`) → OpenAI `tool` role messages. LiteLLM handles this natively.
