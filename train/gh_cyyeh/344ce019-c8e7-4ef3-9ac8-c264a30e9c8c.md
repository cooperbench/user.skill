After thorough review, I found a **bug in the delete flow**. Here's my analysis:

## Edit Flow - Works Correctly

The edit flow is solid:
1. `editMessage` (line 298) builds `conversationHistory` from messages before the edit point
2. `messages` is correctly in `editMessage`'s dependency array (line 531), so it's always current
3. Calls `runAgentEditLoop` → `POST /api/chat/edit` → backend uses `session_id=None` (fresh session)
4. New Langfuse session ID is generated via `generateUUID()`
5. On completion, the new session ID is stored in `sessionIdRef`

## Delete Flow - Has a Stale Closure Bug

The delete itself works correctly (`deleteMessage` at line 534):
- Stores remaining messages in `pendingHistoryRef` (a ref, always current)
- Clears `sessionIdRef.current = null`

**But `sendMessage` has a stale closure problem.** At line 295, the dependency array is:
```
[isStreaming, flushText, refreshTables, userSessionId]
```

`messages` is **not** in the dependency array. After a delete triggers a re-render, `sendMessage` is not recreated, so it still closes over the **pre-delete** messages. On line 78-80, `history` is built from this stale `messages` value.

Then on line 94:
```javascript
history.length > 0 ? history : pendingHistory,
```

The stale `history` (which includes deleted messages) has `length > 0`, so it takes precedence over the correct `pendingHistory` from the ref.

**Result**: After deleting a message, the next send carries the **full pre-delete** conversation history to the backend, including messages that should have been removed.

## Fix

The fix is simple — prefer `pendingHistory` (from the ref, always correct) when it's available:
