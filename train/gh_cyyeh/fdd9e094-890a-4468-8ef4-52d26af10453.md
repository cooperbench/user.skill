## Claude Agent SDK Architecture: Detailed Summary

### Versions

- **Python SDK** (`claude-agent-sdk`): `0.1.44` (`pyproject.toml` line 16)
- **TypeScript SDK** (`@anthropic-ai/claude-agent-sdk`): `0.2.63` (package.json), bundling Claude Code CLI `v2.1.63`

---

### 1. SDK Core Concepts

Both SDKs are thin wrappers around the **Claude Code CLI** subprocess. The SDKs do not call the Anthropic API directly — instead, they spawn a `claude` binary as a subprocess, communicate with it over stdin/stdout using a JSON streaming protocol, and expose its message stream to the caller.

**Python SDK — Key Classes:**

- **`query(prompt, options)`** (`claude_agent_sdk/query.py`): The main entry point. An `async` generator that yields `Message` objects. Internally creates an `InternalClient`, which creates a `SubprocessCLITransport` and a `Query` object.

- **`ClaudeSDKClient`** (`claude_agent_sdk/client.py`): Higher-level bidirectional client for interactive multi-turn conversations. Supports `connect()`, `query()`, `receive_messages()`, `interrupt()`, `set_permission_mode()`, `disconnect()`, and is an async context manager.

- **`ClaudeAgentOptions`** (`claude_agent_sdk/types.py`, line 716): Dataclass holding all config — system prompt, MCP servers, tool lists, model, hooks, agents, sandbox settings, etc.

- **`AgentDefinition`** (`types.py`, line 43): Dataclass for subagent configuration:
  ```python
  @dataclass
  class AgentDefinition:
      description: str
      prompt: str
      tools: list[str] | None = None
      model: Literal["sonnet", "opus", "haiku", "inherit"] | None = None
  ```

**TypeScript SDK — Key Exports:**

- **`query({ prompt, options })`** (`sdk.d.ts`, line 1397): Returns a `Query` object that implements `AsyncGenerator<SDKMessage, void>`. This is what the sidecar uses directly.

- **`AgentDefinition`** (TypeScript, `sdk.d.ts`, line 34): Richer than the Python type; adds `disallowedTools`, `mcpServers`, `criticalSystemReminder_EXPERIMENTAL`, `skills`, and `maxTurns` fields.

- **`Options`** (`sdk.d.ts`, line 635): The options object passed to `query()`, covering `agents`, `allowedTools`, `hooks`, `mcpServers`, `model`, `systemPrompt`, `resume`, `maxTurns`, `includePartialMessages`, `abortController`, `env`, `permissionMode`, and more.

---

### 2. Transport Layer (Python SDK Internals)

**`SubprocessCLITransport`** (`_internal/transport/subprocess_cli.py`):

- Finds the `claude` CLI binary (searches bundled path, `PATH`, common npm locations)
- Builds a CLI command array via `_build_command()` with all options materialized as CLI flags:
  - `--output-format stream-json` — output is newline-delimited JSON
  - `--input-format stream-json` — input is also newline-delimited JSON (streaming)
  - `--system-prompt`, `--model`, `--max-turns`, `--allowedTools`, `--mcp-config`, `--resume`, `--permission-mode`, `--include-partial-messages`, `--setting-sources`, `--plugin-dir`, etc.
- Agents are **not** passed as CLI flags — they are sent via the **initialize control request** over stdin (see below)
- `connect()` spawns the subprocess with `stdin=PIPE`, `stdout=PIPE`
- `write(data)` / `end_input()`: write JSON lines to stdin
- `read_messages()`: async iterator over stdout lines, buffering partial JSON

**Control Protocol (Python `_internal/query.py`):**

The SDK uses a bidirectional **control protocol** over the subprocess's stdin/stdout. On startup:

1. SDK sends an `initialize` control request via stdin:
   ```json
   {"type": "control_request", "request_id": "req_1_xxxx", "request": {"subtype": "initialize", "hooks": {...}, "agents": {...}}}
   ```
2. CLI responds with a `control_response` containing supported commands, models, etc.
3. Then the SDK writes the user message as a JSON object: `{"type": "user", "message": {"role": "user", "content": "..."}, ...}`

During the session, the CLI can send **control requests** back to the SDK:
- `can_use_tool` — asks the permission callback whether to allow a tool
- `hook_callback` — invokes registered hook callbacks
- `mcp_message` — routes MCP JSON-RPC to in-process SDK MCP servers

### 3. Tool System

Tools are **not defined in the SDK itself** — the SDK exposes tools that exist in the Claude Code CLI (built-ins) and via MCP servers.

**MCP (Model Context Protocol) — External Tool Servers:**

The project uses a single SSE MCP server registered at `/mcp/sse`. It is defined in `backend/app/mcp_sse.py` and exposes 3 tools:

| Tool | Description |
|---|---|
| `mcp__duckdb-data-agent__execute_sql` | Executes SQL against DuckDB, returns JSON with columns/rows/rowCount |
| `mcp__duckdb-data-agent__ask_user_question` | Pauses the agent, prompts the user with options, waits for response |
| `mcp__duckdb-data-agent__render_chart` | Accepts Plotly `data` + `layout`, validates non-empty traces, returns `chart_spec` JSON |

### 4. Subagent/Task System

Subagents are dispatched via the **`Task` built-in tool** in the Claude Code CLI. When the orchestrator calls `Task(subagent_type="sql-analyst", prompt="...")`, the CLI:
1. Looks up the registered agent definition for `"sql-analyst"`
2. Spins up a sub-session with that agent's system prompt, tool restrictions, and model
3. Runs the subagent to completion
4. Returns the result (metadata only — the actual text output is in intermediate messages)

**Subagent definitions** are registered at session init time. In `agent.py`, `build_subagent_definitions()` creates:
```python
"sql-analyst": AgentDefinition(
    description="Use this agent for complex data exploration...",
    prompt=sql_prompt,
    tools=["mcp__duckdb-data-agent__execute_sql"],
    model=SQL_SUBAGENT_MODEL_SDK,   # "inherit" by default
)
```

These are serialized and sent to the sidecar in the `/query` POST payload (`agent.py`, lines 246-254):
```python
"agents": {
    name: {
        "description": agent_def.description,
        "prompt": agent_def.prompt,
        "tools": agent_def.tools,
        "model": agent_def.model,
    }
    for name, agent_def in build_subagent_definitions(db).items()
}
```

The sidecar converts them to `AgentDefinition` objects and passes them to the SDK (`server.ts`, lines 182-195). The SDK sends them to the CLI via the `initialize` control request.

**Critical SDK Quirk (from project memory):**

The Task `tool_result` contains only metadata (`agentId`, `usage`, `duration_ms`), NOT the subagent's final text. The actual output is in:
- `msg.tool_use_result.content` on the `UserMessage` object (Python SDK `types.py`, line 648)
- Intermediate `AssistantMessage` events with `parent_tool_use_id` set to the Task tool's ID

The backend handles this by tracking `subagent_texts` keyed by `parent_tool_use_id` (`agent.py`, lines 279-281) and accumulating text from streaming `stream_event` events and `assistant` messages.

### 5. Extensibility Points — Where a "Skills" System Could Hook In

The SDK has several explicit extensibility mechanisms:

**A. Hook System (Most Relevant)**

Hooks are callbacks registered for specific lifecycle events. The full `HookEvent` list (from `types.py`, lines 162-172 and `sdk.d.ts`):

```python
HookEvent = (
    "PreToolUse" | "PostToolUse" | "PostToolUseFailure" |
    "UserPromptSubmit" | "Stop" | "SubagentStop" | "PreCompact" |
    "Notification" | "SubagentStart" | "PermissionRequest"
    # TypeScript adds: SessionStart, SessionEnd, Setup, TeammateIdle,
    # TaskCompleted, Elicitation, ElicitationResult, ConfigChange,
    # WorktreeCreate, WorktreeRemove
)
```

Hooks are configured in `ClaudeAgentOptions.hooks` / `Options.hooks`:
```python
hooks={
    "PreToolUse": [HookMatcher(matcher="execute_sql", hooks=[my_pre_tool_callback])],
    "PostToolUse": [HookMatcher(hooks=[my_post_tool_callback])],
    "SubagentStart": [HookMatcher(hooks=[my_subagent_start_callback])],
}
```

Hook callbacks receive `HookInput` (typed per event, e.g. `PreToolUseHookInput` has `tool_name`, `tool_input`, `tool_use_id`) and return `HookJSONOutput` which can:
- `continue_: False` — block/stop execution
- `decision: "block"` — block a tool call
- `hookSpecificOutput.permissionDecision: "deny"` — deny tool permission
- `hookSpecificOutput.additionalContext` — inject additional context

A skills system could register a `UserPromptSubmit` hook to pre-process the user's prompt (e.g. insert skill context), or a `PreToolUse`/`PostToolUse` hook to observe or modify tool calls.

**B. `can_use_tool` Permission Callback**

```python
async def my_permission_check(tool_name, input, context) -> PermissionResult:
    if tool_name == "dangerous_tool":
        return PermissionResultDeny(message="Not allowed")
    return PermissionResultAllow()

options = ClaudeAgentOptions(can_use_tool=my_permission_check)
```

This is called before every tool invocation and can allow, deny, or modify tool input (`updated_input`).

**C. Custom Agent Definitions (Skills as Subagents)**

The `agents` dict in `ClaudeAgentOptions`/`Options` is a natural place to register skills as specialized subagents. The TypeScript SDK's `AgentDefinition` even includes a `skills` field (line 63):
```typescript
skills?: string[];  // Array of skill names to preload into the agent context
```
This is not yet present in the Python SDK `0.1.44`, suggesting skills are a newer TypeScript-side feature.

**D. Plugin System**

`ClaudeAgentOptions.plugins` accepts a list of `SdkPluginConfig`:
```python
plugins=[{"type": "local", "path": "/path/to/plugin"}]
# Maps to --plugin-dir CLI flag
```

**E. SDK MCP Servers (In-Process Tools)**

`create_sdk_mcp_server()` creates in-process tool servers. This is the most direct extensibility point for adding new tools without a separate subprocess.

**F. Custom Transport**

The `query()` and `ClaudeSDKClient` both accept a custom `transport: Transport` parameter, allowing the entire subprocess communication layer to be replaced.

## Claude Code Skills System: Technical Architecture

### 1. What Are Skills?

Skills are **modular, self-contained packages** that extend Claude's capabilities by providing specialized knowledge, workflows, and tools. They are essentially "onboarding guides" or "process documentation" for specific domains or tasks. Skills transform Claude from a general-purpose assistant into a domain-specialized agent equipped with procedural knowledge.

Skills fall into three conceptual types:
- **Technique**: Concrete methods with steps (e.g., `condition-based-waiting`, `root-cause-tracing`)
- **Pattern**: Ways of thinking about problems (e.g., `flatten-with-flags`, `test-invariants`)
- **Reference**: API docs, syntax guides, tool documentation

And two behavioral types:
- **Rigid**: Must be followed exactly (e.g., TDD, verification-before-completion, systematic-debugging)
- **Flexible**: Adapt principles to context (e.g., brainstorming, patterns)

The skill itself indicates which type it is via its content.

---

### 2. Skill File Format

Every skill lives in its own directory and requires a `SKILL.md` file:

```
skill-name/
├── SKILL.md              # Required - main skill definition
├── scripts/              # Optional - executable scripts (Python/Bash/etc.)
├── references/           # Optional - reference docs loaded into context as needed
├── examples/             # Optional - example files
└── assets/               # Optional - files for output (templates, images, etc.)
```

**SKILL.md structure:**

```markdown
---
name: skill-name-with-hyphens
description: Use when [specific triggering conditions and symptoms]
version: 1.0.0          # optional
license: MIT            # optional
---

# Skill Name

## Overview
Core principle in 1-2 sentences.

## When to Use
[Flowchart if decision is non-obvious]

## Core Pattern / Quick Reference / Implementation
...

## Common Mistakes
...
```

**Frontmatter rules (from `writing-skills/SKILL.md`):**
- Only `name` and `description` are required (the plugin-dev marketplace also allows `version` and `license`)
- Max 1024 characters total in frontmatter
- `name`: Letters, numbers, hyphens only — no parentheses or special chars
- `description`: Written in third person, describes ONLY when to use (triggering conditions), NOT what the skill does. Start with "Use when..." (Superpowers style) or "This skill should be used when..." (Anthropic plugin-dev style)
- The description is critical for Claude Search Optimization (CSO) — Claude reads descriptions to decide which skills to load

From `/Users/cyyeh/.claude/plugins/cache/claude-plugins-official/superpowers/4.3.1/lib/skills-core.js`, the frontmatter parser is simple: it reads only `name` and `description` key-value pairs from between `---` delimiters.

### 3. How Skills Are Loaded

Skills use a **three-level progressive disclosure** loading system:

1. **Metadata level** (always in context): `name` + `description` from YAML frontmatter (~100 words). These are injected into the context so Claude knows which skills exist.
2. **SKILL.md body** (when skill triggers): Full skill content loaded when Claude invokes the Skill tool (< 5k words).
3. **Bundled resources** (on demand): Scripts, references, and assets — loaded only as needed.

**Session-start injection**: The superpowers plugin uses a `SessionStart` hook to inject the content of `using-superpowers/SKILL.md` directly into the system prompt context at session start. This is done via `/Users/cyyeh/.claude/plugins/cache/claude-plugins-official/superpowers/4.3.1/hooks/session-start`, which outputs JSON:

This establishes the meta-skill that teaches Claude how to use ALL other skills.

**Skill discovery (from `skills-core.js`):**
