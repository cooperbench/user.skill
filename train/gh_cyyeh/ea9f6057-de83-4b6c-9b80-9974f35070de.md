## Design Section 2: Anthropic-to-TensorZero Translation Layer The adapter (`llm_proxy.py`) must translate between two API formats: **Anthropic Messages API (incoming from SDK):** ```json POST /v1/messages { "model": "claude-sonnet-4-6", "max_tokens": 8192, "messages": [{"role": "user", "content": "..."}], "system": "...", "stream": true, "tools": [...], "metadata": {...} } ``` **TensorZero Inference API (outgoing to gateway):** ```json POST /inference { "function_name": "chat", "input": { "messages": [{"role": "user", "content": [{"type": "text", "value": "..."}]}] }, "stream": true, "params": { "chat_completion": { "max_tokens": 8192 } } } ``` **Translation responsibilities:** 1. **Request translation**: Convert Anthropic message format → TensorZero input format 2. **Streaming translation**: Convert TensorZero SSE events → Anthropic SSE events (content_block_delta, message_start, message_delta, etc.) 3. **Model mapping**: Map Anthropic model names → TensorZero function/variant names 4. **Tool forwarding**: Pass tool definitions through to the provider 5. **Error mapping**: Convert TensorZero errors → Anthropic error format **Model name mapping strategy:** - The sidecar sends model names like `claude-sonnet-4-6`, `haiku`, etc. - The adapter maps these to TensorZero function names defined in `tensorzero.toml` - A model mapping config (env var or config file) handles the translation **What stays the same:** - UUID session token mechanism (validation before forwarding) - `/v1/models` passthrough for SDK discovery - Streaming response format back to sidecar

## Design Section 4: Error Handling & Provider Feature Gaps **Provider-specific feature gaps:** The Claude Agent SDK uses Anthropic-specific features that not all providers support: - **Extended thinking** — Anthropic only - **Tool use with specific schemas** — varies by provider (TensorZero handles translation) - **System prompts** — universal but format differs - **Streaming event types** — differ between providers **Error handling strategy:** 1. **Unsupported features**: If a request uses Anthropic-specific features (e.g., `thinking` blocks) and the target model doesn't support them, the adapter strips those fields and logs a warning. It does NOT fail the request. 2. **Provider errors**: TensorZero returns provider-specific errors. The adapter maps them to Anthropic error format (400/401/429/500) so the SDK handles them gracefully. 3. **TensorZero down**: If TensorZero is unreachable, return a 502 with clear error message. The sidecar's existing error handling surfaces this to the user. 4. **Streaming interruptions**: Same pattern as current proxy — per-request httpx client, cleanup on disconnect. **Model fallback:** - TensorZero handles routing/fallback natively via the `routing` array in config - Example: `routing = ["anthropic", "aws_bedrock"]` — if Anthropic API is down, falls back to Bedrock **What this design intentionally does NOT do:** - Does not translate between provider-specific features (thinking blocks, caching) - Does not guarantee feature parity across providers — some features only work with Anthropic - Does not add request-level model switching from the frontend (future enhancement)
