Now I understand the root cause. The `data/` directory is in `.gitignore`, so it doesn't exist after cloning. On Linux, when Docker creates it via the bind mount `./data:/app/data`, it's created as `root:root`. The container's `appuser` (UID 1000) can't write to it, causing the sqlite3 error.

Here's what's happening and the fix:

**Root cause**: `data/` is gitignored, so after cloning the repo it doesn't exist. On Linux, Docker's bind mount (`./data:/app/data`) creates the directory as `root:root`. The container's `appuser` (UID 1000) can't write to it, so `sqlite3.connect()` fails. (macOS Docker Desktop doesn't have this issue because its VM layer remaps file ownership.)

**Fixes applied**:

1. **`Makefile:55`** — Added `mkdir -p data` before `docker compose up`, so the directory is created by your host user (matching `APP_UID`) before Docker touches it.

2. **`backend/app/memory_store.py:34-40`** — Added a writability check in `_ensure_dir` that gives a clear error message instead of the cryptic sqlite3 error.

**Quick fix for your running instance**: On the Linux host, run:

```bash
mkdir -p data
docker compose down && docker compose up
```

Or if you want to fix it without restarting:

```bash
sudo chown $(id -u):$(id -g) data
docker compose restart app
```
