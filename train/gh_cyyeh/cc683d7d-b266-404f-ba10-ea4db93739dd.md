   190→## Security
   191→
   192→### LiteLLM Proxy
   193→
   194→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass provider API keys (e.g., `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the keys.
   195→
   196→Instead, a [LiteLLM](https://docs.litellm.ai/) proxy container sits between the sidecar and LLM providers:
   197→
   198→```
   199→Sidecar Container
   200→  → ANTHROPIC_BASE_URL=http://litellm:4000
   201→  → ANTHROPIC_API_KEY=<LiteLLM master key>
   202→        ↓
   203→LiteLLM Proxy (Docker container, port 4000)
   204→  → validates master key
   205→  → routes to correct provider (Anthropic, OpenAI, Google, etc.)
   206→  → injects real provider API keys from its config
   207→```
   208→
   209→**How it works:**
   210→
   211→1. The LiteLLM proxy runs as a Docker container with all real provider API keys configured in `litellm_config.yaml` (read from environment variables).
   212→2. Sidecar containers receive only the `LITELLM_MASTER_KEY` — a shared authentication key for the proxy, not a real provider credential.
   213→3. LiteLLM validates the master key, routes the request to the correct provider based on the model name, and injects the real API key.
   214→4. Even if a tool call reads the sidecar's environment, it only gets the LiteLLM master key, which is useless outside the Docker network.
   215→
   216→This also enables multi-provider support: add any LiteLLM-supported provider to `litellm_config.yaml` without changing application code.
   217→
   218→### Container Isolation
   219→
   220→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   221→
   222→**Architecture:**
   223→
   224→```
   225→Browser
   226→  │
   227→  ▼
   228→FastAPI Backend (host)
   229→  ├── Chat route ──► ContainerManager ──► Docker SDK
   230→  │                       │
   231→  │                       ▼
   232→  │               ┌──────────────────────┐
   233→  │               │  gVisor Sandbox      │
   234→  │               │                      │
   235→  │               │  Sidecar Container   │
   236→  │               │  (Node.js + Claude)  │
   237→  │               │                      │
   238→  │               │  POST /query → SSE   │
   239→  │               └──────┬───────────────┘
   240→  │                      │
   241→  │   LiteLLM Proxy ◄───┘  (LLM API gateway)
   242→  ├── /mcp/sse   ◄──────┘  (DuckDB MCP bridge)
   243→  │
   244→  └── DuckDB (per-user, disk-persisted)
   245→```
   246→
   247→The data flow for a chat message is:
   248→
   249→1. Frontend sends a chat message to the FastAPI backend.
   250→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, passing the LiteLLM master key.
   251→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   252→4. The sidecar talks to the LiteLLM proxy for LLM API access (using the master key, never real provider keys). LiteLLM routes the request to the configured provider.
   253→5. The sidecar's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   254→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   255→7. On session end, the container is stopped and removed.
   256→
   257→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, the Agent SDK, and the `@anthropic-ai/claude-code` CLI (required by the SDK internally). Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   258→
   259→**MCP SSE bridge:** The backend exposes the DuckDB `execute_sql` tool at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`). Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized Claude CLI reaches DuckDB on the host without any direct database access inside the container.
   260→
   261→**Prerequisites:**
   262→
   263→- [Docker](https://docs.docker.com/get-docker/)

   265→
   266→> **Note:** gVisor requires **Linux** (kernel 4.14.77+, x86_64 or ARM64). It is not available on macOS or Windows. On non-Linux hosts (e.g., macOS with Docker Desktop), set `CONTAINER_RUNTIME=runc` to use Docker's default runtime instead. You still get container isolation (filesystem, process, network, capability drop, read-only rootfs) — only gVisor's syscall interception layer is absent. For production multi-tenant deployments, use a Linux host with gVisor for full sandboxing.
