## Approach Comparison

Here are 3 approaches for the E2E test runner architecture:

### Approach A: Pure Playwright Test Runner (Recommended)

**How it works:** A standard Playwright test project (`e2e/`) with a custom YAML-driven test generator. Playwright's `test.describe` dynamically creates tests from YAML scenarios at runtime. LLM-as-judge verification calls the Anthropic API directly.

**Pros:**
- Native Playwright reporting (HTML, JSON, CI-compatible)
- Parallel execution out of the box
- Rich browser debugging (traces, screenshots, video)
- `npx playwright test` is the standard, well-documented workflow
- Easy to add to CI/CD later

**Cons:**
- Requires Node.js (already have it for frontend)
- YAML parsing + dynamic test generation adds a small abstraction layer

### Approach B: Python pytest-playwright

**How it works:** Use `pytest-playwright` in the backend's Python environment. A pytest plugin reads YAML files and generates parametrized test cases. LLM-as-judge uses the existing `anthropic` Python SDK.

**Pros:**
- Stays in the Python ecosystem (backend is Python)
- Can reuse existing pytest infrastructure

**Cons:**
- `pytest-playwright` is less mature than Playwright's native JS runner
- Loses native Playwright features (trace viewer integration, codegen)
- Mixing browser tests into the backend test suite can be messy

### Approach C: Custom Script Runner

**How it works:** A standalone Python/TS script that reads YAML, uses Playwright's library API (not the test runner), drives the browser, and produces a custom report.

**Pros:**
- Maximum control over execution and reporting
- No test framework dependency

**Cons:**
- Reinvents parallel execution, retries, reporting
- No ecosystem tooling (trace viewer, HTML report, CI integration)
- More code to maintain

---

**My recommendation: Approach A (Pure Playwright Test Runner).** It gives you the best developer experience — native HTML reports, screenshot/video on failure, trace debugging, parallel execution, and a clean `make e2e-test` entry point. Since your frontend is already Node.js, there's no new runtime dependency.

## Section 3: Test Runner Architecture

**`scenario-runner.spec.ts`** — the core engine:

```typescript
// Dynamically generates Playwright tests from YAML files
// At import time: glob all YAML files in scenarios/
// For each scenario: test.describe(scenario.name, () => { ... })
// For each step: execute the action, then run verifiers
```

**Execution flow:**
1. Playwright loads `scenario-runner.spec.ts`
2. It reads all `*.yaml` files from `e2e/scenarios/`
3. Each scenario becomes a `test.describe` block
4. Each step becomes a sequential action inside the test
5. Structural `verify` steps run assertions immediately
6. `verify_llm` steps call the Anthropic API with the page content + criteria, parse a pass/fail score

**LLM-as-judge flow:**
1. Extract the visible text content from the response area
2. Send to Claude with a prompt: "Given this page content, does it satisfy: {criteria}? Score 0.0-1.0"
3. Parse the score, compare to `pass_threshold`
4. Fail the test with the LLM's reasoning if below threshold

**Configuration (`playwright.config.ts`):**
- `baseURL`: from `BASE_URL` env var, default `http://localhost:5173`
- Retries: 0 (agent responses are non-deterministic, retries won't help)
- Timeout: 60s per test (agent responses can be slow)
- Reporter: `html` (generates `results/` report) + `list` (terminal output)
- Screenshots: on failure
- Video: off by default (configurable)

**Makefile integration:**
```makefile

    cd e2e && npx playwright test

e2e-report:
    cd e2e && npx playwright show-report results
```

   362→    case 'verify_llm':

   367→async function uploadFile(page: Page, filePath: string, scenariosDir: string): Promise<void> {
   368→  const absolutePath = path.resolve(scenariosDir, '..', filePath);
   369→  const fileInput = page.locator('.file-upload__input');
   370→  await fileInput.setInputFiles(absolutePath);
   371→  // Wait for upload to complete — sidebar table entry appears
   372→  await page.locator('.sidebar__table-name').first().waitFor({ state: 'visible', timeout: 15_000 });

   376→  const textarea = page.locator('.chat-input__textarea');

   391→  await page.locator('.message-bubble__typing').waitFor({ state: 'hidden', timeout: effectiveTimeout });
   392→}

   394→async function clickElement(page: Page, selector: string): Promise<void> {

   491→
   492→**Files:**
   493→- Create: `e2e/lib/llm-judge.ts`
   494→
   495→**Step 1: Create `e2e/lib/llm-judge.ts`**
   496→
   497→```typescript
   498→import Anthropic from '@anthropic-ai/sdk';
   499→import { VerifyLlmStep } from './types';
   500→
   501→let client: Anthropic | null = null;
   502→
   503→function getClient(): Anthropic {
   504→  if (!client) {
   505→    client = new Anthropic();
   506→  }
   507→  return client;
   508→}
   509→
   510→export interface JudgeResult {
   511→  pass: boolean;
   512→  score: number;
   513→  reasoning: string;
   514→}
   515→
   516→export async function runLlmJudge(
   517→  pageContent: string,
   518→  step: VerifyLlmStep
   519→): Promise<JudgeResult> {
   520→  const threshold = step.pass_threshold ?? 0.8;
   521→  const anthropic = getClient();
   522→
   523→  const response = await anthropic.messages.create({
   524→    model: 'claude-haiku-4-5-20251001',
   525→    max_tokens: 512,
   526→    messages: [
   527→      {
   528→        role: 'user',
   529→        content: `You are an E2E test judge. Given the page content below, evaluate whether it satisfies the criteria.
   530→
   531→<page_content>
   532→${pageContent}
   533→</page_content>
   534→
   535→<criteria>
   536→${step.criteria}
   537→</criteria>
   538→
   539→Respond in exactly this JSON format:
   540→{"score": 0.0 to 1.0, "reasoning": "brief explanation"}`,
   541→      },
   542→    ],
   543→  });
   544→
   545→  const text = response.content[0].type === 'text' ? response.content[0].text : '';
   546→  const jsonMatch = text.match(/\{[\s\S]*\}/);
   547→
   548→  if (!jsonMatch) {
   549→    return { pass: false, score: 0, reasoning: `Failed to parse LLM judge response: ${text}` };
   550→  }
   551→
   552→  const parsed = JSON.parse(jsonMatch[0]) as { score: number; reasoning: string };
   553→
   554→  return {
   555→    pass: parsed.score >= threshold,
   556→    score: parsed.score,
   557→    reasoning: parsed.reasoning,
   558→  };
   559→}

## 4. Suggestions (Nice to Have)

### 4.1 -- Consider separating unit test config from E2E test config

The current `testDir: '.'` approach means `yaml-loader.test.ts` (a pure unit test) runs alongside browser-based E2E scenarios. This works but has a side effect: Playwright will attempt to launch a browser for the yaml-loader tests even though they do not use one. Consider either:
- Moving `yaml-loader.test.ts` into a Playwright "project" with `use: {}` (no browser)
- Or keeping `testDir: './tests'` and referencing the unit test via a separate npm script

### 4.2 -- `innerText()` is called twice in `runStructuralVerify`

**File:** `/Users/cyyeh/Desktop/duckdb-data-agent/.claude/worktrees/e2e-playwright/e2e/lib/verifiers.ts`, lines 10 and 17

```typescript
if (expected.contains) {

  ...
}
if (expected.not_contains) {
  const text = await lastAssistant.innerText();  // second call (identical)

```

Extracting `innerText()` once at the top of the function (when either `contains` or `not_contains` is set) would avoid a redundant DOM evaluation. This is a minor performance point but also reduces flakiness if content changes between the two calls.

### 4.3 -- Greedy regex in LLM judge could match too much

**File:** `/Users/cyyeh/Desktop/duckdb-data-agent/.claude/worktrees/e2e-playwright/e2e/lib/llm-judge.ts`, line 49

```typescript
const jsonMatch = text.match(/\{[\s\S]*\}/);
```

The `[\s\S]*` pattern is greedy and will match from the first `{` to the last `}` in the entire response. If the LLM wraps its response in markdown (e.g., `` ```json { ... } ``` followed by "Hope this helps!}") ``), the regex could capture garbage. A non-greedy version `\{[\s\S]*?\}` or a more targeted pattern would be more robust, though in practice with `max_tokens: 512` and a focused prompt, the current pattern is unlikely to fail.

### 4.4 -- `navigate` action does not wait for load state

**File:** `/Users/cyyeh/Desktop/duckdb-data-agent/.claude/worktrees/e2e-playwright/e2e/lib/actions.ts`, lines 54-55

```typescript
async function navigate(page: Page, urlPath: string): Promise<void> {
  await page.goto(urlPath);
}
```

The scenario runner calls `page.waitForLoadState('networkidle')` only on the initial navigation (line 25 of scenario-runner.spec.ts). A `navigate` action mid-scenario will not wait for the page to settle. Adding `await page.waitForLoadState('networkidle')` after `goto` would make `navigate` steps more reliable.

### 4.5 -- Missing `default` branch in `executeStep` switch

**File:** `/Users/cyyeh/Desktop/duckdb-data-agent/.claude/worktrees/e2e-playwright/e2e/lib/actions.ts`, lines 6-20

The switch statement handles all known `Step` action types including `verify`/`verify_llm` (as no-ops). TypeScript's discriminated union provides compile-time exhaustiveness, so there is no runtime risk. However, since the YAML data is `unknown` cast to `Step`, a `default` case that throws `Error: Unknown action: ${(step as any).action}` would catch YAML authoring mistakes that slip past validation.
