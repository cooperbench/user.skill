### Overview

Skills are reusable instruction sets that guide the agent to perform specific workflows. They are stored as markdown files in a directory structure and can be invoked via slash commands (`/skill-name`) in the chat input, through the sidebar "Use" button, or combined with user messages.

**File Format:** Each skill lives in its own directory with a `SKILL.md` file:

skills/

└── hi/

**File Format - SKILL.md:** YAML frontmatter + markdown content
```yaml

name: skill-name
description: What this skill does
disabled: false  # optional
metadata:
  builtin: true  # optional, marks as built-in (undeletable)

Instructions for the agent...
```

**Hook Enforcement** (lines 60-79):
```typescript
const skillAllowlistHook: HookCallbackMatcher = {
  matcher: "Skill",
  hooks: [
    async (input) => {
      const currentSkills = discoverSkills();
      const skillName = (input.tool_input as Record<string, unknown>).skill;
      if (skillName && !currentSkills.has(skillName)) {
        return {
          hookSpecificOutput: {
            permissionDecision: "deny",
            permissionDecisionReason: `Skill "${skillName}" is not in the allowlist.`,
          },

      return {};
    },
  ],
};
```

**Key Points:**
- `PreToolUse` hook blocks any Skill tool calls not in the allowlist
- Skill restriction added to system prompt to prevent model hallucination
- Disabled skills are excluded from discovery → cannot be invoked
- Multiple skills in one message trigger multiple Skill tool calls

    92→#### Per-Subagent Model Routing
    93→
    94→You can route each agent (orchestrator, SQL subagent) to a different LLM provider by using the `@suffix` syntax:
    95→
    96→```
    97→ORCHESTRATOR_MODEL=openai/gpt-4o@sonnet
    98→REDACTED@haiku
    99→```
   100→
   101→The format is `real_model@sdk_alias`. The SDK alias (after `@`) is the model name the Claude Agent SDK sees; the real model (before `@`) is what the backend proxy rewrites it to before forwarding to Bifrost. This lets you use any provider Bifrost supports (OpenAI, Bedrock, etc.) while keeping the SDK configuration unchanged.
   102→
   103→**How it works:**
   104→
   105→1. The SDK sends requests using the alias (e.g. `sonnet`, `haiku`).
   106→2. A lightweight reverse proxy on the backend (`/anthropic/*`) intercepts these requests.
   107→3. The proxy rewrites the `model` field to the real provider model (e.g. `openai/gpt-4o`) and forwards the request to Bifrost.
   108→4. Bifrost routes the request to the correct provider.
   109→
   110→Without `@suffix`, model values are used as-is (direct Anthropic routing).
   111→
   112→#### Default Tool Model
   113→
   114→The Claude Agent SDK's built-in tools (e.g. WebFetch) internally use their own Anthropic models (e.g. `claude-haiku-4-5-20251001`). When routing all traffic through a non-Anthropic provider, these models are not in the rewrite map and will fail because they lack a provider prefix.
   115→
   116→Set `DEFAULT_TOOL_MODEL` to catch any model not matched by the per-agent rewrites:
   117→
   118→```
   119→DEFAULT_TOOL_MODEL=openai/gpt-4o-mini
   120→```
   121→
   122→Any request whose model does not match a configured rewrite is rewritten to this value before forwarding to Bifrost. When empty (default), unmatched models pass through unchanged.
   123→
   124→> **Warning:** The `@suffix` must NOT match the `ORCHESTRATOR_MODEL`'s Anthropic model name. For example, `ORCHESTRATOR_MODEL=haiku` with `REDACTED@haiku` will conflict because the proxy cannot distinguish orchestrator traffic from subagent traffic when both resolve to the same model name.

To add other providers (OpenAI, Bedrock, etc.), edit `bifrost/config.json` — see [`bifrost/config.example.json`](bifrost/config.example.json) for multi-provider examples. You can also configure providers via Bifrost's Web UI at `http://localhost:8081` (or `$BIFROST_PORT`). Note that you still need to set api keys and model names in `backend/.env`.

   199→## Security
   200→
   201→### Bifrost LLM Gateway
   202→
   203→When the agent runs, the backend spawns a sidecar container via the Docker SDK. A naive approach would pass `ANTHROPIC_API_KEY` directly into that container's environment — but any tool or shell command the agent executes could then read and exfiltrate the key.
   204→
   205→Instead, a [Bifrost](https://github.com/maximhq/bifrost) LLM gateway service manages API keys centrally and routes requests to LLM providers:
   206→
   207→```
   208→Sidecar Container
   209→  → ANTHROPIC_BASE_URL=http://bifrost:8080/anthropic
   210→  → ANTHROPIC_API_KEY=placeholder
   211→        ↓
   212→Bifrost Gateway (/anthropic)
   213→  → ignores client-sent key
   214→  → injects the real provider API key
   215→  → forwards request to provider (Anthropic, OpenAI, Bedrock, etc.)
   216→```
   217→
   218→**How it works:**
   219→
   220→1. Bifrost runs as a Docker Compose service with real API keys stored in `bifrost/config.json` (referencing environment variables).
   221→2. Sidecar containers receive a placeholder `ANTHROPIC_API_KEY` and point `ANTHROPIC_BASE_URL` to Bifrost's native `/anthropic` endpoint.
   222→3. Bifrost injects the real provider API key when forwarding requests upstream. The Claude Agent SDK works unchanged since Bifrost speaks native Anthropic Messages API.
   223→4. Additional providers (OpenAI, Bedrock, Vertex, etc.) can be added to `bifrost/config.json` or via Bifrost's Web UI. Use provider prefixes in model names (e.g., `openai/gpt-4o-mini`) to route subagent requests to different providers. See [`bifrost/config.example.json`](bifrost/config.example.json) for configuration examples.
   224→
   225→The sidecar container only ever holds a placeholder string. Even if a tool call reads the environment, it cannot obtain any real API key.
   226→
   227→### Container Isolation
   228→
   229→The backend runs each Claude Code session inside a **gVisor-sandboxed Docker container** ("sidecar"). This provides code execution sandboxing, multi-tenant isolation, and a hardened boundary between the agent and the host system.
   230→
   231→**Architecture:**
   232→
   233→```
   234→Browser
   235→  │
   236→  ▼
   237→FastAPI Backend (host)
   238→  ├── Chat route ──► ContainerManager ──► Docker SDK
   239→  │                       │
   240→  │                       ▼
   241→  │               ┌──────────────────────┐
   242→  │               │  gVisor Sandbox      │
   243→  │               │                      │
   244→  │               │  Sidecar Container   │
   245→  │               │  (Node.js + Claude)  │
   246→  │               │                      │
   247→  │               │  POST /query → SSE   │
   248→  │               └──────┬───────────────┘
   249→  │                      │
   250→  │              ├──► Bifrost Gateway (:8080/anthropic)  (LLM routing)
   251→  ├── /mcp/sse   ◄───────┘  (DuckDB MCP bridge)
   252→  │
   253→  └── DuckDB (per-user, disk-persisted)
   254→```
   255→
   256→The data flow for a chat message is:
   257→
   258→1. Frontend sends a chat message to the FastAPI backend.
   259→2. Backend spins up a gVisor container (or reuses an existing one for the session) via `ContainerManager`, configured to route LLM calls through the Bifrost gateway.
   260→3. Backend sends the query to the sidecar's `POST /query` endpoint. The sidecar calls the Claude Agent SDK's `query()` function with `includePartialMessages: true` for token-level streaming, configured with the host's MCP SSE endpoint.
   261→4. The agent talks to the Bifrost gateway (`/anthropic`) for LLM API access (using a placeholder key; Bifrost injects the real key).
   262→5. The agent's `execute_sql` tool calls reach the host DuckDB via the **MCP SSE bridge** (`/mcp/sse?session_id=...`), which routes each connection to the correct per-user DuckDB instance through the existing `SessionManager`.
   263→6. The sidecar streams SSE events back to the backend, which forwards them to the frontend.
   264→7. On session end, the container is stopped and removed.
   265→
   266→**Sidecar container:** The `sidecar/` directory contains a TypeScript HTTP server (`src/server.ts`) that uses the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) with `includePartialMessages: true` for true token-level streaming. The Docker image (`sidecar/Dockerfile`) bundles Node.js 20, Python 3.12, and the Agent SDK. Containers run with a read-only root filesystem, all Linux capabilities dropped, no volume mounts, no Docker socket access, and a non-root user.
   267→
   268→**MCP SSE bridge:** The backend exposes tools at `/mcp/sse` using the MCP protocol's SSE transport (`backend/app/mcp_sse.py`): `execute_sql` for DuckDB queries, `render_chart` for chart generation, `ask_user_question` for interactive clarification, and `create_skill` for agent-driven skill creation. Each SSE connection requires a `session_id` query parameter to route tool calls to the correct per-user DuckDB instance. This is how the containerized agent reaches DuckDB on the host without any direct database access inside the container.
   269→
   270→**Prerequisites:**
   271→
   272→- [Docker](https://docs.docker.com/get-docker/)
   273→- [gVisor (runsc)](https://gvisor.dev/docs/user_guide/install/) (Optional) runtime installed and registered with Docker
   274→
   275→> **Note:** gVisor requires **Linux** (kernel 4.14.77+, x86_64 or ARM64). It is not available on macOS or Windows. On non-Linux hosts (e.g., macOS with Docker Desktop), set `CONTAINER_RUNTIME=runc` to use Docker's default runtime instead. You still get container isolation (filesystem, process, network, capability drop, read-only rootfs) — only gVisor's syscall interception layer is absent. For production multi-tenant deployments, use a Linux host with gVisor for full sandboxing.
   276→

   278→
   279→1. Build the sidecar image and create the Docker network:
   280→
   281→   ```bash
   282→   docker compose build
   283→   make sidecar-network
   284→   ```
   285→
   286→2. Install gVisor by following the [official guide](https://gvisor.dev/docs/user_guide/install/).
   287→
   288→3. Start the app:

   295→
   296→| Variable | Default | Description |
   297→|----------|---------|-------------|
   298→| `CONTAINER_IMAGE` | `duckdb-agent-sidecar:latest` | Sidecar Docker image |
   299→| `CONTAINER_RUNTIME` | `runc` | Docker runtime (runc for non-gVisor, runsc for gVisor) |
   300→| `CONTAINER_MEMORY_LIMIT` | `512m` | Memory limit per container |
