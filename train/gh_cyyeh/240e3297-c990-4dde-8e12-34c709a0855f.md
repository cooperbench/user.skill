## Data Flow Summary

```
1. Backend receives orchestrator's Task tool_call with subagent_type: "sql-analyst"
                    ↓
2. emit subagent_start SSE event
                    ↓
3. Subagent executes internally (execute_sql tool)
   - parent_tool_use_id filters out these internal events
   - Text accumulated in subagent_texts dict
   - Tool IDs stored but tool_call NOT emitted
                    ↓
4. Subagent completes, Task tool_result arrives
                    ↓
5. emit subagent_end SSE event
                    ↓
6. Frontend receives events:
   - onSubagentStart: creates 'subagent_start' segment
   - toolResult callbacks (if any): create 'tool' segments
   - onSubagentEnd: creates 'subagent_end' segment with result text
                    ↓
7. MessageBubble renders thinking block:
   - Shows "SQL Analyst working..." (subagent_start segment)
   - Shows tool execution table/results (tool segments)
   - Shows any text result from subagent (subagent_end text segment)
```

## Key Architectural Decisions

1. **Parent Tool Use ID Filtering**: The `is_subagent_event` check prevents internal subagent tool calls from being streamed to the frontend, avoiding duplicate UI elements and "Executing..." hangs.

2. **Text Accumulation**: Subagent text is accumulated in `subagent_texts` dict during streaming and sent via `subagent_end` event instead of as individual streaming events.

3. **Tool Call Skipping for Subagents**: Internal tool calls (execute_sql inside sql-analyst) skip the `tool_call` event emission but still store tool_names for reference. This prevents frontend from showing "Executing..." for tools whose results the SDK won't yield.

4. **Segment-Based Rendering**: The frontend uses a `ContentSegment` union type that allows mixing of thinking, tool results, subagent indicators, and final answers in a unified structure.

5. **Thinking Block Filtering**: Subagent events are shown in the thinking/expandable block when there's no final answer yet, but hidden once the answer starts streaming.

### Conclusion

Agent mode had **no `sql_queries` field** in subagent_end events because:
1. SQL queries executed inside subagents happened in a local subprocess with no visibility to the stream
2. The backend only had access to the final text output from `tool_use_result.content`

1. Processing all SDK events from the remote sidecar as JSON
2. Using `parent_tool_use_id` to attribute tool calls to their parent Task
3. Accumulating SQL statements in `subagent_sqls` dict
4. Emitting them in the `subagent_end` event for full visibility
