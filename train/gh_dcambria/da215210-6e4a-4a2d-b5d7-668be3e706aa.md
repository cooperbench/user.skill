- Há **2.649 URLs com status `pending`** na tabela `wp_wpr_rocket_cache` + **25 em progresso simultâneo**
- O slow log mostra `PreloadUrl.php:167 usleep()` — o preloader faz `curl_exec()` de cada URL e usa `usleep()` como throttle, mas 25 workers simultâneos fazendo curl interno = **25 PHP-FPM workers consumidos apenas pelo preload**
- O ActionScheduler dispara `rocket_preload_job_preload_url` — hoje tem 491 ações na fila, e o WP-Cron `rocket_preload_process_pending` roda a cada minuto
- O `action_scheduler_run_queue` também roda **a cada minuto**, disparando o ActionScheduler do TEC junto

**Problema concreto:** O preload está competindo com requests reais de usuários por workers PHP-FPM. Com `pm.max_children=55`, se 25 estão fazendo preload, restam 30 para o tráfego real. Sob carga do CloudFront, isso satura.

---

## Vetor 2 — WPML `usort` / `tribe_events_is_new_install` a cada request

**O que está acontecendo:**
- O slow log registra `usort()` em `install.php:14` → `tribe_events_is_new_install()` → chamado no hook `after_setup_theme` **a cada request**
- `tribe_events_is_new_install()` chama `get_option()` e faz um `usort()` no array de versões instaladas do TEC — isso acontece no bootstrap do WP, antes do cache funcionar
- Separadamente: WPML `maybe_populate_cache()` faz queries no Aurora para `icl_translations` quando o cache Redis miss ocorre — e o slow log de hoje mostra `serialize()` custoso no `object-cache.php` para objetos grandes do WPML

---

## Abordagens propostas

**Para o Vetor 1 (Preload):**

**A. Limitar concorrência do preload + janela horária** — Reduzir `pm.max_children` reservado para preload via configuração no WP Rocket (limite de batch) e agendar o preload para madrugada via WP-Cron customizado. **Mais simples, sem risco.**

**B. Separar PHP-FPM em dois pools** — Pool `wordpress` para tráfego real (prioridade alta) e pool `wordpress-cron` para WP-Cron/preload (limite de workers). Garante isolamento total. Mais trabalho de configuração.

**C. Desativar preload por sitemap, manter preload on-access** — O WP Rocket já faz preload quando uma página é visitada. O preload ativo por sitemap é redundante num site com alto tráfego CloudFront. Zero custo computacional.

**Para o Vetor 2 (WPML + TEC bootstrap):**

**A. mu-plugin para cachear `tribe_events_is_new_install()`** — Wrapping com transient de 24h para evitar o `usort()` a cada request. Simples, cirúrgico.

**B. Atualizar TEC** — O `usort()` em `install.php:14` é comportamento de versão antiga. Verificar se versão atual resolve.

**C. Pre-warming do cache WPML via WP-CLI agendado** — Forçar `icl_translations` cache antes do pico de tráfego diário.

- Vetor 1: **Opção C** (desativar sitemap preload) — o site tem tráfego CloudFront alto o suficiente para o preload on-access cobrir tudo. Imediato, sem risco.
- Vetor 2: **Opção B** (verificar versão TEC) + **A** como fallback se update não resolver.

**PROBLEMA:** `get_transient()` retorna `false` tanto para "transient expirado/inexistente" quanto para um valor genuíno `false` armazenado. A guard `if ( false !== $cached )` está correta para o hit/miss. O risco real está em **o que é armazenado na primeira chamada**.

Quando `previous_ecp_versions` não existe no banco, o TEC passa `$default = []` como valor inicial, mas `tribe_get_option()` pode retornar `false` se a option não existir na tabela (o `get_option()` interno retorna `false` para options ausentes — e o TEC só substitui pelo default depois).
