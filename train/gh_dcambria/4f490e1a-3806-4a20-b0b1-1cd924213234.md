## 2) Análise da "página 404 que lista posts"

**Não era nem 404 nem archive normal — era uma archive REAL gerada pelo WP** quando a URL `.css` foi mal-interpretada como uma rota WordPress.

**O que aconteceu, passo a passo:**

A URL pedida pelo navegador foi:
```
/wp-content/cache/min/1/wp-content/elementor-cache/elementor/css/post-49005.css?ver=1777684818
```

1. **nginx** procurou o arquivo no filesystem → não existe (arquivo do WP Rocket Minify foi deletado/expirou)
2. nginx tem fallback `try_files ... /index.php?$args` (padrão WordPress) → passou ao WP
3. O WordPress fez o parsing da URL. **`.css` no path NÃO impede o WP de tentar resolver rewrite rules** — o parser só olha o path como string
4. O WP tentou casar a URL contra rewrite rules. Como a URL tem múltiplos segmentos com slugs aleatórios (`cache`, `min`, `1`, `wp-content`, etc.), nenhuma rewrite específica casou
5. O WP caiu no fallback de **archive genérica** — `WP_Query` foi inicializada como uma listagem de posts (post type default `post`)
6. `the_archive_title()` retornou **"Arquivos"** (i18n PT-BR de "Archives" — fallback genérico quando nenhum tipo de archive especifico — author, date, taxonomy — foi detectado)
7. O `archive.php` do Hello Elementor renderizou o loop de últimos posts

**Provas técnicas:**

```html
<h1 class="entry-title">Arquivos</h1>          ← the_archive_title() default
<article class="post">...</article>             ← loop em post type 'post'
href="...post-49005.css/page/2/?ver=..."        ← paginação archive ativa (max_num_pages > 1)
```

O regex só pega `/wp-content/uploads/YYYY/` ou `/wp-content/uploads/YYYY/MM/` — **não cobre `/wp-content/cache/...`**.

**Análise do que provocou o incidente:**

Olhando v1.2.0 que enviei, a regra problemática:

```php
if ( preg_match( '#(?:^|/)wp-content/(?:cache|elementor-cache)/#', $request_path ) ) {
    global $wp_query;
    $wp_query->set_404();
    status_header( 404 );
    nocache_headers();
    exit;
}
```

Hipótese: O `parse_request` roda em **todo request que cai no PHP**. WordPress + WP Rocket + Elementor fazem **subrequests internos** (via `wp_remote_get`, REST, admin-ajax) com URLs contendo `/wp-content/cache/` em headers/refer. Mas o regex bate em `$_SERVER['REQUEST_URI']` — então só pega URL da request HTTP.

Mais provável: **o problema é a regra `is_post_type_archive('post') || is_archive()` no template_redirect** combinada com o fato de que **muitas pages legítimas hoje são detectadas como `is_archive()` por algum plugin** (JetEngine listings, TEC events archive, WPML, etc.). O `set_404()` em template_redirect está sendo chamado para pages legítimas, e algum plugin que escuta o 404 entra em loop.

Mas isso não explica timeout de 60-360s — é mais consistente com **deadlock em redis/db**. O `wp_query->set_404()` chamado depois que o WP_Query já carregou pode causar reprocessing custoso.

**Conclusão:** A v1.2.0 tem um bug **nessa segunda regra do template_redirect**. A primeira regra (404 para `/wp-content/cache/*` no parse_request) **provavelmente é OK** — nada de errado óbvio nela.
