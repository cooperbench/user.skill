# Plano: rsync wp-content local → produção

## Contexto

Sincronizar o diretório `wp-content/` do ambiente local Docker para o servidor de produção EC2, transferindo apenas arquivos faltando ou desatualizados (sem sobrescrever o que já está igual no remoto).

## Comando rsync

```bash
rsync -avz --checksum \
  --exclude='cache/' \
  --exclude='uploads/' \
  --exclude='debug.log' \
  --exclude='advanced-cache.php' \
  --exclude='object-cache.php' \
  --exclude='db.php' \
  --exclude='sunrise.php' \
  --exclude='upgrade/' \
  --exclude='upgrade-temp-backup/' \
  --exclude='elementor-exports/' \
  --exclude='ewww/' \
  --exclude='mu_temp/' \
  --exclude='wp-rocket-config/' \
  /Users/dcambria/scripts/server-tools/v2/docker-dev/sites/concertacao/wordpress/wp-content/ \
  concertacaoamazonia.com.br-prod-sa:/var/www/concertacaoamazonia.com.br/wp-content/
```

## O que será transferido (incluído)

- `themes/` — child theme hello-elementor-child (CSS, functions.php, etc.)
- `mu-plugins/` — mu-plugins customizados do Bureau
- `plugins/` — plugins instalados
- `languages/` — arquivos de tradução
- `elementor/` — templates e configurações Elementor
- `index.php` — arquivo de proteção

## O que será excluído (não transferido)

| Diretório/arquivo | Motivo |
|---|---|
| `cache/` | Cache gerado dinamicamente no servidor |
| `uploads/` | Mídia de produção — não sobrescrever |
| `debug.log` | Log local não deve ir para prod |
| `advanced-cache.php` / `object-cache.php` / `db.php` / `sunrise.php` | Gerados por plugins no servidor (WP Rocket, Redis, HyperDB) |
| `upgrade/` / `upgrade-temp-backup/` | Temporários de atualização |
| `elementor-exports/` / `ewww/` / `mu_temp/` / `wp-rocket-config/` | Dados locais/temporários |

## Flags

- `-a` — archive mode (preserva permissões, timestamps, links simbólicos)
- `-v` — verbose (mostra o que está sendo transferido)
- `-z` — compressão durante transferência
- `--checksum` — compara por checksum, não apenas por data/tamanho (garante que só transfere o que realmente mudou)

## t3.xlarge — Adequada ou superdimensionada?

**Veredicto: superdimensionada em RAM, mas adequada em CPU — com ressalvas.**

| **Disponível** | **12 GB livres** |

Com 12 GB livres e sem swap sequer necessário, **uma t3.large (8 GB) seria suficiente** — ainda sobraria ~3 GB de margem. A única razão para manter 16 GB seria se `pm.max_children` fosse aumentado significativamente (>80 workers).

---

### CPU (4 vCPUs): adequada, mas com pressão real nos picos

- **CPU idle agora: apenas 15–20%** com 76% de utilização média
- **%steal de 1–5%**: o hypervisor está roubando CPU ocasionalmente — sinal de que a instância está trabalhando no limite em picos
- **Load average 1.4–1.9** com apenas 4 vCPUs: já próximo de saturação
- PHP-FPM atingiu `pm.max_children=50` duas vezes hoje — o gargalo **não é falta de RAM, é falta de CPU/workers**

O problema é que ao atingir 50 workers com 290 MB cada, o consumo chegaria a ~14,5 GB — aí a RAM faria sentido. Mas a CPU esgota antes da RAM.

---

### Tráfego (contexto)

- ~4.000–6.000 requests/hora no pico (horário noturno/madrugada — provavelmente crawlers/bots)
- Horário real de uso humano parece ser diurno, ainda sem dados completos de hoje
- 34.000 requests com status 200 no log atual

### Recomendação

| Opção | Custo relativo | Adequação |
|---|---|---|
| **t3.medium** (2 vCPUs / 4 GB) | ~25% do atual | Insuficiente — CPU seria o gargalo |
| **t3.large** (2 vCPUs / 8 GB) | ~50% do atual | RAM OK, mas CPU pode ser gargalo |
| **t3.xlarge** atual (4 vCPUs / 16 GB) | 100% | CPU adequada, RAM desperdício |
