> DEVELOPER

Shouldn't the websocket already be handling this tho? Why am i not getting events from the web socket?

> AGENT

Good question. The WS itself works fine — `subscribeToUpdates` clients do receive `sessions_updated`. But look at what triggers that broadcast in `server.ts`:

```js
// server.ts:1133
const poller = setInterval(async () => {
  // queries the DB for max event ID across all repos
  if (changed) broadcast();
}, 500);  // was 2000
```

The WS message is **only sent** after this poller detects a DB change. So the chain is:

```
hook fires → writes to SQLite → server poller wakes up (up to 2s) → broadcasts WS → SessionDetail fetches
```

The WS subscription is not the bottleneck — it's the 2-second polling gap on the server side before the broadcast even goes out. The WS is just a delivery mechanism for a signal that itself has up to 2s latency.

That's why I reduced the server poller from 2000ms → 500ms, which fixes the WS delay for all clients.

The 500ms client-side poll I added in `SessionDetail` for `isLive` sessions is a belt-and-suspenders fallback — if for some reason the WS broadcast is missed (reconnecting, etc.), the session detail will still refresh within 500ms. But the server-side change is the primary fix.
