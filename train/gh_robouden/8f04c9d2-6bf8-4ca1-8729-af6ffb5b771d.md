    34→
    35→## Real-time Data Access
    36→
    37→The Safecast MCP server provides access to real-time radiation data from fixed sensors (Pointcast, Solarcast, bGeigieZen, etc.) through dedicated tools. These tools query the `realtime_measurements` table in the PostgreSQL database to retrieve the most current readings from active sensors.
    38→
    39→### Real-time Tools
    40→- `list_sensors`: Discover active fixed sensors by location or type
    41→- `sensor_current`: Get the latest reading(s) from specific sensors or geographic areas
    42→- `sensor_history`: Pull time-series data from fixed sensors over date ranges
    43→- `device_history`: Access both historical bGeigie data and real-time sensor data for a specific device
    44→
    45→> **Note**: Real-time data tools require a database connection to access the `realtime_measurements` table. These tools will fall back to the Safecast REST API if no database is configured.
    46→
    47→## Tool Reference
    48→
    49→### query_radiation
    50→
    51→Find radiation measurements near a geographic location. Returns measurements within a specified radius, sorted by most recent.
    52→
    53→| Parameter | Type | Required | Default | Description |
    54→|-----------|------|----------|---------|-------------|
    55→| `lat` | number | Yes | | Latitude (-90 to 90) |
    56→| `lon` | number | Yes | | Longitude (-180 to 180) |
    57→| `radius_m` | number | No | 1500 | Search radius in meters (25 to 50,000) |
    58→| `limit` | number | No | 25 | Max results (1 to 10,000) |
    59→
    60→**Example**: Find measurements within 5km of Fukushima Daiichi:
    61→```json
    62→{"name": "query_radiation", "arguments": {"lat": 37.42, "lon": 141.03, "radius_m": 5000}}
    63→```
    64→
    65→Each result includes: `id`, `value` (dose rate in uSv/h), `captured_at`, `location` (lat/lon), `device_id`, `detector`, `track_id`, `has_spectrum`, and `distance_m`.

   307→
   308→### Structured Runtime Logging
   309→
   310→The server includes comprehensive structured logging for monitoring AI tool usage and performance. The logging system is implemented via:
   311→
   312→- **`main.go`**: `instrument()` wrapper function that wraps each tool handler to capture execution metrics
   313→- **`duckdb_client.go`**: `LogQueryAsync()` function that asynchronously writes logs to DuckDB's `mcp_query_log` table
   314→
   315→The logging system:
   316→
   317→- Records timestamps, tool names, parameters, result counts, and query durations
   318→- Provides asynchronous logging that doesn't block tool execution
   319→- Stores logs in DuckDB for fast analytics via the `query_analytics` tool
   320→- Supports optional persistent storage via `DUCKDB_PATH` environment variable
   321→
   322→This enables better observability into how tools are being used and helps identify performance bottlenecks.

   345→| GET | `/api/track/{id}` | Get measurements from a track |
   346→| GET | `/api/device/{id}/history` | Device history (bGeigie + fixed sensors) |
   347→| GET | `/api/sensors` | List active fixed sensors |
   348→| GET | `/api/sensor/{id}/current` | Latest reading from a sensor |
   349→| GET | `/api/sensor/{id}/history` | Time-series from a sensor |
   350→| GET | `/api/spectra` | Browse gamma spectroscopy records |
   351→| GET | `/api/spectrum/{marker_id}` | Full spectroscopy channel data |
   352→| GET | `/api/stats` | Aggregate radiation statistics |
   353→| GET | `/api/info/{topic}` | Reference information (units, safety levels, etc.) |

   355→| GET | `/docs/doc.json` | Raw OpenAPI spec |

   562→## Deployment
   563→
   564→Pushing to `main` automatically builds and deploys to **simplemap.safecast.org** (the map server) via GitHub Actions (only when Go source files, `go.mod`/`go.sum`, or the workflow itself change).
   565→
   566→> **Note**: The MCP server runs on the same server as the database for optimal performance (localhost connections eliminate network latency). See [MIGRATION_TO_MAP_SERVER.md](MIGRATION_TO_MAP_SERVER.md) for migration details.
   567→
   568→### How it works
   569→
   570→1. GitHub Action cross-compiles the Go binary
   571→2. Uploads it to the map server via rsync
   572→3. Creates `.env` file with localhost database connection
   573→4. Restarts the MCP server via systemd
   574→5. Configures Apache proxy for `/mcp-http`, `/docs/`, and `/api/` endpoints
   575→6. Runs a health check against the `/mcp-http` endpoint
   576→
   577→### Setting up secrets
   578→
   579→The GitHub Action requires two repository secrets. Go to **Settings** > **Secrets and variables** > **Actions** and add:
   580→
   581→| Secret | Description |
   582→|--------|-------------|

**No, CloudFront cannot route SSH traffic.** Here's why and what your alternatives are:

## Why CloudFront Can't Handle SSH

CloudFront is a **Layer 7 (Application Layer) CDN** designed exclusively for HTTP/HTTPS:

- **Protocols supported:** HTTP and HTTPS only
- **Ports:** Only 80 (HTTP) and 443 (HTTPS)
- **SSH operates on:** Port 22 (Layer 4 TCP protocol)
- **CloudFront's purpose:** Cache and deliver web content, not arbitrary TCP traffic

When you try to SSH to a CloudFront domain:
```bash
ssh root@simplemap.safecast.org  # Port 22
# DNS → CloudFront IPs (listening only on ports 80/443)
# CloudFront: "I don't accept connections on port 22" → Connection refused
```

## Alternative Solutions

### Option 1: SSH Subdomain (Recommended)

Create a separate DNS A record that bypasses CloudFront:

```bash
# In Route53, add a new record:
ssh.simplemap.safecast.org → 65.108.24.131 (A record, NOT CloudFront alias)

# Then you can SSH with:
ssh root@ssh.simplemap.safecast.org
```

**Pros:**
- ✅ Clean, memorable hostname
- ✅ No extra cost
- ✅ Simple to set up

**Cons:**
- ❌ Different hostname for SSH vs web
- ❌ No geographic routing

### Option 2: AWS Network Load Balancer (NLB)

Use an NLB to route TCP traffic (including SSH):

```
User → NLB (Port 22) → EC2 Instance (65.108.24.131:22)
```

**Pros:**
- ✅ Can use domain name for SSH
- ✅ Health checks and failover
- ✅ Can handle multiple backends

**Cons:**
- ❌ **Cost:** ~$16-20/month for the NLB alone
- ❌ Added complexity
- ❌ Overkill for a single server

### Option 3: AWS Global Accelerator

Route TCP traffic globally with anycast IPs:

**Pros:**
- ✅ Global routing optimization
- ✅ Handles SSH and other TCP protocols

**Cons:**
- ❌ **Very expensive:** $0.025/hour + data transfer (~$18/month minimum)
