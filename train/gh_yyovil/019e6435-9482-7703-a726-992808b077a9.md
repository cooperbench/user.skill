> AGENT

Because startup path resolution is doing real-world reliability work, not just “find `codex`”. `codexBinary()` is caching `ResolveCodexBinary()` so we only resolve once, thread-safe. `ResolveCodexBinary()` is defensive for cases where plain `exec.LookPath("codex")` is not enough: - non-interactive/sanitized environments where `PATH` differs from your shell - Windows installs where the executable may be `codex.cmd`/`codex.exe` - installs in non-standard locations (`~/.cargo/bin`, npm global bins, AppData npm) - absolute fallback to `"codex"` if discovery fails, instead of hard failure at callsite So even though your Linux/macOS shell usually has `codex`, plugin runtime may not, and tests can stub `resolvedBinary` directly for determinism. In short: this is robust launch behavior for mixed environments, not overengineering.

> AGENT

Not quite. In theory, yes — if the running process always inherits a consistent `PATH` that contains `codex`, then `exec.LookPath("codex")` is enough. In practice, Better-AO runs as a process in a non-interactive/runtime environment where PATH can differ from your terminal shell. That’s why the resolver is defensive: - shell startup files don’t run (no `PATH` additions from `~/.bashrc`/`~/.zshrc`) - different installers place `codex` in `~/.npm/bin`, `~/.cargo/bin`, AppData/npm, etc. - Windows has `codex.exe`/`codex.cmd` variants and PATHEXT behavior - tests/CI can run with minimal envs or altered PATH So it isn’t just “pretzel” logic; it’s resilience to environment variance, while still allowing plain PATH path when available.
