## Why the wait exists When the entrypoint runs: ```typescript createProgram() .parseAsync() // returns a rejected promise .catch((err) => { // this handler is queued as a microtask ... }); ``` `.catch()` on a rejected promise doesn't run immediately — it schedules the handler as a **microtask**. So right after `await import("../src/index.js")` returns, the `.catch()` callback hasn't executed yet. Without the wait, `console.error` and `process.exit` haven't been called and the assertions fail. ## How `setTimeout(r, 0)` helps `setTimeout` queues a **macrotask**. The event loop drains all microtasks before processing the next macrotask. So by the time the `setTimeout` callback fires: ``` 1. import completes 2. .catch() handler runs (microtask) ← this is what we need 3. setTimeout callback fires (macrotask) ← this is where we assert ``` ## Did I "know" it would be enough? Honestly — no guarantee. `setTimeout(0)` works here because there's only one microtask (the `.catch()` handler) between the import and the assertion. But this is relying on an implementation detail of how Node.js schedules promise callbacks. If the handler did something that created additional async work (another `await`, another `.then()`), `setTimeout(0)` might not be enough. The `setTimeout(50)` in the re-throw test is even worse — it's just a "hope 50ms is enough" guess. There's no principled reason it's 50 and not 10 or 200. This is exactly why Copilot's suggestion is better — it sidesteps the problem entirely by never creating real async work.
