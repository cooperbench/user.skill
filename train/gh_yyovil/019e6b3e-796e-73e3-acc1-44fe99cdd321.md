Here’s the exhaustive design space I’d consider, filtered around 4 open projects and “how do I jump from Project A’s board to Project D’s board?”

**1. Board Row Under Each Project**
```text
Project A
  Board
  Orchestrator
  Workers
Project B
  Board
  ...
```
Flow: click `Project D > Board`.  
Cost: 1 click if expanded, 2 if collapsed.  
This is the cleanest tree-navigation model. Board is a destination like terminal/orchestrator, not an action.

**2. Board Icon On Each Project Row**
```text
Project A        [board icon]
Project B        [board icon]
Project C        [board icon]
Project D        [board icon]
```
Flow: click Project D’s board icon.  
Cost: 1 click.  
Fastest, but less explicit. Works if Kanban is a secondary affordance; weaker if Board is a primary view.

**3. Project Row Itself Opens Board**
```text
Project D
```
Flow: click `Project D`.  
Cost: 1 click.  
Very efficient, but overloaded. It makes the project row both expand/select/navigate unless you split expand chevron from row click. Good if “project overview = board” is the core mental model.

**4. Expanded Project Has Pinned Primary Board**
```text
Project D
  Board   <- always first, selected by default
  Orchestrator
  Workers
```
Flow: click `Project D` to expand/select, or click `Board`.  
Cost: 1-2 clicks.  
Similar to option 1, but Board becomes the default project destination. This is probably best if the product wants project boards to be the main hub.

**5. Sidebar Root Board Plus Project Switcher Inside Board**
```text
Board
Projects...
```
Then board page has project tabs/dropdown.
Flow: click `Board`, choose `Project D`.  
Cost: 2 clicks unless the board page has visible project tabs and Project D is one click.  
This works if the board is workspace-level and comparing projects matters. It is weaker for “jump directly to D’s board.”

**6. Topbar Board Button Plus Project Context**
```text
[Project selector]        [Board]
```
Flow: select Project D, click Board.  
Cost: 2 clicks, plus hidden context risk.  
I’d avoid unless the app becomes topbar-driven with a very strong global project selector.

**7. Topbar Segmented View With Project Sidebar Selection**
```text
Sidebar selects Project D
Topbar: Terminal | Board | Canvas
```
Flow: click Project D, click Board.  
Cost: 2 clicks.  
This is understandable but slower. It only makes sense if users often switch “view mode” for the currently selected project, like IDE panes.

**8. Command Palette / Quick Switcher**
```text
Cmd+K -> "Project D Board"
```
Flow: keyboard shortcut, type/select.  
Cost: fast for power users, bad as the only path.  
Good supplemental option, not the primary placement.

**9. Workspace Board With Swimlanes Per Project**
```text
Board
  Project A lane
  Project B lane
  Project C lane
  Project D lane
```
Flow: no navigation; scroll/filter to Project D.  
Cost: 0-1 click, but board density explodes.  
Good if users need cross-project visibility more than per-project focus. Bad if each project has many sessions.

**10. Board Drawer / Overlay From Project Row**
Flow: click Project D board icon, board opens in main or side panel.  
Cost: 1 click.  
Useful if board is a quick inspection surface. Bad if board is a full working view.

My shortlist after this:

1. **Visible `Board` row under each project** if Board is a real destination.
2. **Project row opens Board by default** if Board is the project homepage.
3. **Board icon on each project row** if you care most about one-click switching and can accept a smaller affordance.
4. **Workspace board with project swimlanes** if the board’s purpose is cross-project overview rather than project-specific work.

I’d discard the current topbar button for this use case. It does not scale cleanly to 4 open projects because project identity becomes implicit.
