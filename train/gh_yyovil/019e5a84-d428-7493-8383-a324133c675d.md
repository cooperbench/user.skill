   Define the contract in `.proto`, generate Go and TypeScript.
   Very strong contract sharing, but overkill unless this app is moving toward RPC-style APIs.

> AGENT

Yes, **OpenAPI could definitely help**, but mostly for the normal HTTP endpoints.

In this repo right now you have:

- `GET /api/workspace` -> returns workspace JSON
- `POST /api/sessions/{sessionID}/ide` -> command-style HTTP endpoint
- `GET /api/sessions/{sessionID}/terminal` -> WebSocket terminal stream

OpenAPI is a good fit for the first two. It can define request params, response bodies, errors, and generate frontend types/clients from that.

It is a weaker fit for the terminal endpoint, because that is not really “request -> JSON response”. It upgrades to a WebSocket and then streams terminal I/O. OpenAPI can document the handshake URL/query params, but it is not ideal for the actual live stream protocol. For that, WebSocket-specific docs or AsyncAPI fit better.

RPC is also valid. For this stack, I’d consider **ConnectRPC** before classic gRPC or tRPC:

- `tRPC`: great for TypeScript backend + TypeScript frontend, not a natural fit for Go.
- `gRPC-web`: works, but heavier.
- `ConnectRPC`: good Go + browser TypeScript story, protobuf contracts, generated clients.

A practical architecture would be:

```text
ConnectRPC / OpenAPI:
  GetWorkspace
  OpenSessionIDE
  ListPlugins
  StartSession
  StopSession

WebSocket:
  AttachTerminal
  terminal input/output stream
  resize events
```

So the strongest answer is: **OpenAPI helps if you want to keep REST. ConnectRPC helps if you want a more typed command/query API. Either way, keep terminal streaming as WebSocket unless you are doing a larger protocol redesign.**

For `better-ao` today, I’d lean:

```text
small app / few endpoints: keep current generator or OpenAPI
growing typed API: ConnectRPC + WebSocket for terminal
```

That hybrid is probably the cleanest long-term shape.
