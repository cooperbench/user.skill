- **The server even trusts the client's record bytes.** `publishRecord` checks base64 and *optionally* that `publicKey` derives to the ipnsName (`ipns.service.ts:79-83`), but never verifies the Ed25519 signature, and it **self-increments the sequence number** (`ipns.service.ts:246`) instead of reading it from the signed record — which is the root of the sequence-divergence the API agent flagged (acknowledged in the comment at `:543`).

So the social edge is a caching/routing convenience, not a security boundary — and it isn't even sufficient for real revocation, since Bob still physically holds the key (revoking a write-share requires rotating the IPNS key, which the rotation path already does anyway). **The write-share graph can be blinded too.** My "blind reads only" middle option was built on a false premise — scratch it.

The linchpin that makes full blinding safe is one protocol change: **have the server verify the IPNS record signature against the ipnsName and key the canonical record by ipnsName, not userId.** Once the publish path is cryptographically self-authorizing, the server has no need for `recipient_id` on writes — and the *same* change fixes the sequence-integrity bug. Your two stated areas — privacy and protocol hardening — converge on this single change.

That opens a clean target: **capability-based shares** where the server stores no owner→recipient edge. The owner hands the recipient `{ipnsName + ECIES-wrapped key(s)}` out-of-band — the invite/URL-fragment primitive already exists for link shares — and the server just relays opaque per-ipnsName records and wrapped blobs. Revocation = key rotation (already required). The one thing the edge gave you "for free" is recipient-side discovery ("what's shared with me?"), which now needs somewhere to live.
