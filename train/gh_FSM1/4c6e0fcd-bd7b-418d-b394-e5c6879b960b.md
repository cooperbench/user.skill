   179→### Pattern 3: Ephemeral Key Bridge (Claim Flow)
   180→
   181→**What:** The core cryptographic flow for claiming an invite link
   182→**When to use:** When recipient authenticates and claims the invite
   183→
   184→```typescript
   185→// Client-side claim flow (runs in browser after auth)
   186→async function claimInvite(token: string, ephemeralPrivKeyHex: string): Promise<void> {
   187→  // 1. Fetch invite metadata from server
   188→  const invite = await fetchInviteByToken(token);
   189→
   190→  // 2. Get recipient's own vault keypair
   191→  const vaultKeypair = useAuthStore.getState().vaultKeypair;
   192→  const ephemeralPrivKey = hexToBytes(ephemeralPrivKeyHex);
   193→
   194→  // 3. Unwrap the key using ephemeral private key
   195→  const plaintextKey = await unwrapKey(hexToBytes(invite.encryptedKey), ephemeralPrivKey);
   196→
   197→  // 4. Re-wrap with recipient's own public key
   198→  const reWrappedKey = await wrapKey(plaintextKey, vaultKeypair.publicKey);
   199→  plaintextKey.fill(0); // zero sensitive data
   200→
   201→  // 5. Re-wrap child keys similarly
   202→  const childKeys = [];
   203→  for (const ck of invite.encryptedChildKeys ?? []) {
   204→    const plainChildKey = await unwrapKey(hexToBytes(ck.encryptedKey), ephemeralPrivKey);
   205→    const reWrapped = await wrapKey(plainChildKey, vaultKeypair.publicKey);
   206→    plainChildKey.fill(0);
   207→    childKeys.push({
   208→      keyType: ck.keyType,
   209→      itemId: ck.itemId,
   210→      encryptedKey: bytesToHex(reWrapped),
   211→    });
   212→  }
   213→
   214→  // 6. Zero ephemeral key from memory
   215→  ephemeralPrivKey.fill(0);
   216→
   217→  // 7. Send claim to server (creates Share + ShareKey records via Phase 14 infra)
   218→  await claimInviteApi(token, {
   219→    encryptedKey: bytesToHex(reWrappedKey),
   220→    childKeys,
   221→  });
   222→}
   223→```

   241→### Anti-Patterns to Avoid
   242→
   243→- **Storing ephemeral private key on server:** The entire point of the ephemeral key bridge is that the server never sees the ephemeral private key. It lives only in the URL fragment.
   244→- **Using a new NestJS module for invites:** Invites are tightly coupled to shares. Keep them in `SharesModule` to reuse `SharesService.createShare()` during claim.
   245→- **Creating a separate table for invite child keys:** Use JSONB column on the invite table -- invites are short-lived (7 days) and child keys are deleted with the invite on claim. No need for normalized storage.
   246→- **Omitting CREATE TABLE migration:** Per learnings from Phase 14 staging deployment, ALWAYS create a migration file. `synchronize: true` in dev hides missing migrations.

   259→## Common Pitfalls
   260→
   261→### Pitfall 1: HashRouter Fragment Collision
   262→
   263→**What goes wrong:** URL format `app.cipherbox.cc/invite/:token#ephemeralKey` fails because HashRouter uses `#` for routing. The entire path after `#` is the hash route.
   264→**Why it happens:** The app uses `HashRouter` (confirmed in `apps/web/src/routes/index.tsx:9`), not `BrowserRouter`.
   265→**How to avoid:** Use `/#/invite/:token?key=<ephemeralPrivKeyHex>` format. The `?key=` portion is within the hash fragment and parsed by React Router's `useSearchParams()`.
   266→**Warning signs:** URL parsing returns undefined for the ephemeral key, or the route doesn't match.
   267→
   268→### Pitfall 2: Missing CREATE TABLE Migration
   269→
   270→**What goes wrong:** ShareInvite table doesn't exist in staging/production, migration that modifies it fails.
   271→**Why it happens:** `synchronize: true` in dev auto-creates tables from entities, hiding the missing migration. Only fails when `synchronize: false` in staging/production.
   272→**How to avoid:** ALWAYS create a migration file with `CREATE TABLE IF NOT EXISTS` for new entities. Use timestamp BEFORE any migration that modifies the table.
   273→**Warning signs:** Staging deployment fails with "relation does not exist" error.
   274→**Reference:** `.learnings/2026-02-22-staging-migration-missing-create-table.md`
   275→
   276→### Pitfall 3: Entity Registration in AppModule
   277→
   278→**What goes wrong:** TypeORM doesn't recognize the new entity, queries fail at runtime.
   279→**Why it happens:** New entity must be added to BOTH the module's `TypeOrmModule.forFeature()` AND the `entities` array in `app.module.ts`.
   280→**How to avoid:** Add `ShareInvite` to:
   281→
   282→1. `apps/api/src/shares/shares.module.ts` line 9: `TypeOrmModule.forFeature([Share, ShareKey, ShareInvite, User])`
   283→2. `apps/api/src/app.module.ts` line 28: import and add to entities array (line 69-82)
   284→
   285→### Pitfall 4: Ephemeral Key Memory Leaks
   286→
   287→**What goes wrong:** Ephemeral private key stays in memory after claim, potential security risk.
   288→**Why it happens:** Key is parsed from URL into a Uint8Array but never zeroed after use.
   289→**How to avoid:** Always `.fill(0)` ephemeral key material in a `finally` block after claim completes. Follow same pattern as `ShareDialog.tsx:368-370` (zeroing itemFolderKey).
   290→**Warning signs:** Phase 14 security review already flagged similar issues with navigation stack key zeroing.
   291→
   292→### Pitfall 5: OpenAPI Client Not Regenerated
   293→
   294→**What goes wrong:** New invite endpoints exist on the server but the web app has no typed client functions to call them.
   295→**Why it happens:** Must run `pnpm api:generate` after adding/modifying controllers, but it's easy to forget.
   296→**How to avoid:** Run `pnpm api:generate` after implementing any new controller endpoints. Commit the generated files in `apps/web/src/api/`.
   297→**Reference:** `.claude/CLAUDE.md` API Development Workflow section.
   298→
   299→### Pitfall 6: Invite Lookup Must Not Require Authentication
   300→
   301→**What goes wrong:** The GET endpoint to fetch invite metadata (for the landing page) requires JWT auth, but the user hasn't authenticated yet.
   302→**Why it happens:** The `SharesController` uses `@UseGuards(JwtAuthGuard)` at the class level (line 41).
   303→**How to avoid:** Create the GET invite endpoint WITHOUT `JwtAuthGuard`. Only the CLAIM endpoint requires authentication. Options:
   304→
   305→1. Create a separate `InvitesController` without class-level auth guard
   306→2. Use `@Public()` decorator on the GET endpoint (if NestJS module supports it)
   307→3. Create a minimal unauthenticated controller dedicated to invite lookup
   308→
   309→### Pitfall 7: Race Condition on Single-Claim
   310→
   311→**What goes wrong:** Two recipients click the same link simultaneously, both claim successfully.
   312→**Why it happens:** Read-check-write pattern without locking.
   313→**How to avoid:** Use database-level atomic update: `UPDATE share_invites SET status = 'claimed', claimed_by = :userId, claim_count = claim_count + 1 WHERE token = :token AND status = 'active' AND claim_count < max_claims`. Check `affected === 1`.

   554→## Claim Flow Architecture Detail
   555→
   556→### Server-Side Claim Logic
   557→
   558→The claim endpoint should:
   559→
   560→1. **Validate invite** -- token exists, status is 'active', not expired
   561→2. **Atomic status update** -- `UPDATE ... SET status='claimed', claimed_by=:userId WHERE status='active'` to prevent race conditions
   562→3. **Create Share record** -- reuse parts of `SharesService.createShare()` but with different inputs (no recipientPublicKey lookup needed since we have userId)
   563→4. **Create ShareKey records** -- from the re-wrapped child keys sent by the client
   564→5. **Return shareId** -- client navigates to shared content
   565→
   566→### Client-Side Claim Logic
   567→
   568→After authentication on the invite page:
   569→
   570→1. Parse `token` from URL params and `key` from search params
   571→2. Fetch invite to verify it's still active (lightweight check)
   572→3. Get recipient's vault keypair from auth store
   573→4. Unwrap `invite.encryptedKey` with ephemeral private key
   574→5. Re-wrap with recipient's public key
   575→6. Do the same for all `encryptedChildKeys`
   576→7. POST claim with re-wrapped keys
   577→8. Navigate to `/files` or directly to the shared item via `/shared`

   579→## Open Questions
   580→
   581→1. **Should the invite GET endpoint return encrypted_key?**
   582→   - What we know: The client needs the encrypted key ciphertext to unwrap it after auth. But the GET endpoint is unauthenticated.
   583→   - What's unclear: Should we return encrypted_key in the public GET (since it's useless without the ephemeral private key), or require a second authenticated GET?
   584→   - Recommendation: Return encrypted_key in the public GET. It's encrypted with the ephemeral key and completely useless without the fragment. This avoids an extra round-trip after auth. The only "leakage" is that someone with the server token can see there IS an invite, which is already implied by the token existing.
   585→
   586→2. **Tab state persistence in ShareDialog**
   587→   - What we know: The ShareDialog resets all state on close (lines 215-228).
   588→   - What's unclear: Should the active tab be remembered between opens?
   589→   - Recommendation: Reset to "Direct Share" tab on close (consistent with existing reset behavior).
   590→
   591→3. **Self-claim prevention**
   592→   - What we know: Phase 14 prevents self-sharing (line 45-47 in shares.service.ts).
   593→   - What's unclear: Should we prevent the sharer from claiming their own invite link?
   594→   - Recommendation: Yes, check `invite.sharerId !== claimerId` in the claim endpoint. Same self-share prevention pattern.
