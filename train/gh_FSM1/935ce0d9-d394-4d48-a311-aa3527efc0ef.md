## Vuln 1: Missing Public Key-to-IPNS Name Binding in Signature Verification — `packages/sdk-core/src/ipns/index.ts:190-204`

- **Severity:** HIGH
- **Category:** crypto_verification_bypass
- **Confidence:** 9/10

**Description:** The client verifies that the Ed25519 signature returned by the server is valid for the returned `pubKey`, but never verifies that `pubKey` actually corresponds to the `ipnsName` being resolved. IPNS names are cryptographically derived from the public key via `deriveIpnsName()` (available in `@cipherbox/crypto`). Without this binding check, an untrusted server can substitute its own keypair and the client accepts the forged record as `signatureVerified: true`.

This directly undermines the zero-knowledge trust model — the entire purpose of IPNS signature verification is to prevent the untrusted server from tampering with resolve results.

**Exploit Scenario:**
1. Client calls `resolveIpnsRecord("k51abc...")` to resolve a folder's IPNS name
2. Compromised server generates a fresh Ed25519 keypair (`attackerPrivKey`, `attackerPubKey`)
3. Server creates a valid IPNS record pointing to a previously-captured legitimate CID (replay/downgrade) or garbage CID (denial), signs it with `attackerPrivKey`
4. Server returns `{ signatureV2: <valid sig>, data: <attacker CBOR>, pubKey: base64(attackerPubKey) }`
5. Client verifies: "Is this signature valid for this pubKey?" — **YES**, because the signature genuinely matches the attacker's key
6. Client trusts the CID. While AES-256-GCM prevents plaintext forgery, the attacker can replay stale encrypted blobs (rolling back filesystem state), serve garbage causing decryption errors, or downgrade sequence numbers causing the client to overwrite newer data

The identical vulnerability also exists in the web app at `apps/web/src/services/ipns.service.ts:155-165`. No caller of `resolveIpnsRecord` performs the binding check — all trust the return value unconditionally.

**Recommendation:** After verifying the signature, derive the expected IPNS name from the returned public key and compare it to the requested name. `deriveIpnsName` is already exported from `@cipherbox/crypto` and used elsewhere in the SDK:

```typescript
import { deriveIpnsName } from '@cipherbox/crypto';

// After signature verification passes:
const pubKeyBytes = Uint8Array.from(atob(response.pubKey), (c) => c.charCodeAt(0));
const derivedName = await deriveIpnsName(pubKeyBytes);
if (derivedName !== ipnsName) {
  throw new Error('IPNS public key does not match requested name - possible key substitution');
}
```

Additionally, consider having callers enforce `signatureVerified === true` rather than ignoring it — currently the boolean is returned but never checked, meaning the server can also bypass verification by simply omitting signature fields from the response.
