### Root Cause: Race condition between upload completion flash and file visibility

The bug is in `/Users/michael/Code/cipher-box-worktree-parallel/apps/web/src/components/file-browser/FileList.tsx`, lines 147-153:

```typescript
const completingNames = new Set(
  uploadEntries.filter((e) => e.status === 'complete').map((e) => e.filename)
);
const filteredItems = items.filter(
  (item) => !(item.type === 'file' && completingNames.has(item.name))
);
```

This "Pitfall 5" dedup filter removes **real** file rows from the DOM when their name matches a completing upload entry. The upload entry stays in `'complete'` status for 1 second (green flash) before being auto-removed.

The race unfolds as follows:

1. SDK `uploadFile()` completes and synchronously emits `folder:updated`, which updates the Zustand folder store (adding the real file to the children list)
2. After `uploadFile()` returns, `setFileStatus(uploadId, 'complete')` is called
3. If React processes the folder store update (step 1) in a **separate render cycle** before the upload status update (step 2), the real file row briefly appears in the DOM **without** the dedup filter active (upload status is still `'uploading'`)
4. The E2E test's `waitForItemToAppear()` resolves at this moment because it found `.file-list-item:not(.upload-inline-row)` with the matching name
5. React then processes step 2 in a second render cycle -- the upload status becomes `'complete'`, and the dedup filter now **removes the real file row** from the DOM
6. The immediate `isItemVisible()` check runs during this 1-second flash period and returns `false`

### Why Previous Fix Was Incomplete

PR #413 (`e2932af90`) correctly identified and fixed the strict mode violation (both upload row and real row matching the same locator) by adding `:not(.upload-inline-row)` to E2E selectors. But it didn't address the dedup filter race where the real row is temporarily **removed from the DOM entirely** while the completing upload row exists.

### Why the Failures Are Intermittent

The `d206e19` run (between the two failing runs) passed because the bug depends on React's render batching timing. When both state updates happen to be batched in a single render cycle, the dedup filter is active from the start and the real file never appears until the flash period ends -- so `waitForItemToAppear` correctly waits past the flash. The bug only manifests when React processes them in separate render cycles.

### Suggested Fixes

**Option A (Preferred -- Fix the app code):** In `FileList.tsx`, instead of filtering out real file rows during the completion flash, filter out the **upload rows** when a real file with the same name exists. This reverses the dedup logic so the real file is always shown:

```typescript
// Instead of filtering real items when upload is completing,
// filter upload entries when real items already exist
const realFileNames = new Set(
  items.filter((item) => item.type === 'file').map((item) => item.name)
);
const filteredUploadEntries = uploadEntries.filter(
  (e) => !(e.status === 'complete' && realFileNames.has(e.filename))
);
```

This way the real file row is never removed from the DOM. The upload flash row just disappears immediately when the real file appears, which is visually fine.

**Option B (Fix the E2E tests):** Replace the `isItemVisible` instant check after upload with `waitForItemToAppear` to tolerate the 1-second dedup window:

```typescript
// Instead of:
expect(await fileList.isItemVisible(file.name)).toBe(true);

// Use:
await fileList.waitForItemToAppear(file.name, { timeout: 5000 });
```

This would work but masks the underlying app issue where files briefly disappear from the UI after upload.

**Option C (Fix both):** Apply Option A (the proper fix) and also make the E2E tests more robust with Option B as a defense-in-depth measure.
