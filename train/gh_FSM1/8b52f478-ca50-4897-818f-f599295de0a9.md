    16→## Decision 1: `folder_ipns` Stays Authoritative (Not Advisory)
    17→
    18→### What was considered
    19→
    20→Making `folder_ipns` "advisory" — IPNS resolution via self-hosted Someguy becomes the primary source of truth, with the DB demoted to a performance cache.
    21→
    22→### What `folder_ipns` does today (6 roles)
    23→
    24→1. **CID cache** — `latestCid` stores the most recent CID per IPNS name. Fallback when network resolution fails.
    25→2. **Sequence number tracking** — `sequenceNumber` is the authoritative counter for optimistic concurrency. The API checks `expectedSequenceNumber` against the DB value and returns 409 Conflict on mismatch.
    26→3. **TEE key storage** — `encryptedIpnsPrivateKey` + `keyEpoch` hold IPNS private keys wrapped with TEE public key for republishing.

    33→Three of the six roles have **hard blocking dependencies** on server-side state:
    34→
    35→- **TEE republishing** needs `encryptedIpnsPrivateKey` from this table. No alternative server-side storage exists. This column must stay.

    38→

    47→## Decision 2: IPNS Resolution Keeps DB-First Strategy (Not DHT-First)
    48→
    49→### The concession
    50→
    51→A milestone called "IPFS Infrastructure" might suggest moving IPNS resolution to be DHT-primary — resolve via self-hosted Someguy/Kubo first, fall back to DB only on failure. The scoping discussion explicitly chose the opposite: **DB-first with async DHT verification**.
    52→
    53→### Current flow (before v1.1)
    54→
    55→```text
    56→resolveRecord()
    57→  -> DelegatedRoutingClient.resolve() -> delegated-ipfs.dev (primary, 10s timeout)
    58→  -> folder_ipns DB query (fallback on 502/timeout)
    59→  -> Compare sequence numbers, return highest
    60→```
    61→
    62→### v1.1 flow (IPNS-02)
    63→
    64→```text
    65→resolveRecord()
    66→  -> folder_ipns DB query (primary, <5ms)
    67→  -> Return DB result immediately to caller
    68→  -> Async: Kubo DHT resolve via self-hosted Someguy (background)
    69→     -> If DHT has higher sequence number, update DB cache
    70→     -> If DHT fails, no-op (DB is authoritative for our own records)
    71→```
    72→
    73→### Why DB-first instead of DHT-first
    74→
    75→1. **Latency:** DB query completes in <5ms. DHT resolution, even self-hosted, has a median of 0.3-0.4s (ProbeLab data) and a long tail. Users should never wait for the DHT on the hot path.
    76→2. **DB is already correct for our own records.** Every publish writes to `folder_ipns` atomically. The DB always has the latest CID that _we_ published. The only scenario where DHT has a fresher value is if another node published for the same IPNS name — which doesn't happen in CipherBox's architecture.
    77→3. **Graceful degradation is free.** If Someguy/Kubo is down, nothing changes — the DB result is already returned. No timeout, no retry, no user-visible degradation (IPNS-04).
    78→4. **Async verification catches staleness.** The background DHT check is a consistency audit, not a user-facing operation. If a TEE republish advanced the sequence number and the DB hasn't caught up, the async check self-heals.
    79→
    80→### What this means for "IPFS-native"
    81→
    82→This is a pragmatic concession: the DB remains the primary source of truth for IPNS resolution, not IPFS.
