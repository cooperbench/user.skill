this seems like a vital architectural decision - what are the pros/cons of each approach? Are there any hidden foot guns in any of the approaches?

> AGENT

Great question — this deserves a proper analysis. Let me walk through each approach with the actual codebase mechanics:

---

### Option A: New `uploadFiles()` batch method on SDK

**How it works:** SDK gets a new method accepting multiple files. It runs encrypt+pin in parallel internally, collects all FilePointers, then does ONE folder metadata update + ONE IPNS publish.

**Pros:**
- Clean consumer API — web app just calls `client.uploadFiles(folder, files, onProgress)`
- SDK controls the full pipeline: consistency, cleanup, state updates
- Folder tree is updated atomically (single mutation to `this.folderTree`)
- `withOperation()` serialization works naturally (one batch = one operation)

**Cons:**
- Progress callback shape changes — need per-file callbacks inside a batch (current signature is single `(percent) => void`)
- SDK grows more complex — partial failure handling, per-file cancellation within a batch
- Rust SDK needs a mirrored `upload_files()` for desktop parity

**Foot guns:**
- **Stale children race window**: The batch reads `folder.children` at the start, then encrypt+pin runs for potentially minutes. If another device publishes new children via sync during that window, the batch publish overwrites them. Single `uploadFile()` has the same race but a much shorter window. **Mitigation:** Re-read folder metadata just before the final publish, merge new children.
- **Memory**: If all files encrypt concurrently before any are pinned, memory spikes (3x 100MB = 300MB of ciphertext buffered). Need pipeline-style: encrypt file → pin immediately → free ciphertext → next slot.

---

### Option B: Decompose into primitives (`encryptAndPin()` + `batchRegisterFiles()`)

**How it works:** SDK exposes two new lower-level methods. Web app orchestrates: call `encryptAndPin()` N times in parallel, collect results, then call `batchRegisterFiles()` once.

**Pros:**
- Maximum flexibility — web app controls concurrency, progress, cancellation
- Each SDK method is simple and does one thing
- Easiest path to Web Worker encryption later (wrap `encryptAndPin` in a Worker message)

**Cons:**
- Breaks SDK encapsulation — consumers must understand the encrypt→pin→register→publish pipeline
- Every consumer (web, desktop, tests, future mobile) reimplements the orchestration logic

**Foot guns:**
- **Orphaned CIDs**: If `encryptAndPin()` succeeds for 5 files but `batchRegisterFiles()` fails (or the tab crashes before it's called), you have 5 pinned CIDs that no folder references. The SDK can't clean these up because it doesn't know about them. The **consumer** must track and clean up orphans.
- **SDK state divergence**: After `encryptAndPin()`, the SDK's internal `folderTree` doesn't know about the new files. If sync fires between encrypt and register, the SDK may overwrite or conflict. The consumer is responsible for coordinating with SDK internals it shouldn't know about.
- **Sequence number conflicts**: `batchRegisterFiles()` needs to read+increment the folder's IPNS sequence number. If anything else publishes to that folder between the encrypt and register calls, the sequence number is stale → publish fails.

---

### Option C: Keep `uploadFile()`, batch at web layer

**How it works:** Web app calls existing `uploadFile()` concurrently for each file.

**Foot guns — this option is essentially broken for the stated goal:**
- `uploadFile()` is wrapped in `withOperation()` which **serializes** all SDK operations. Concurrent calls would just queue, making it sequential again.
- Even if serialization is bypassed, concurrent calls would race on `folder.children`: File 1 reads `[A,B]`, adds C → publishes `[A,B,C]`. File 2 reads `[A,B]`, adds D → publishes `[A,B,D]`. **One file is silently lost.**
- Still does N IPNS publishes, defeating the main goal.

**Verdict:** Not viable for what this phase aims to achieve.

---

### My recommendation

**Option A (batch method on SDK)** is the safest path. The foot guns in Option B (orphaned CIDs, state divergence, sequence number conflicts) all stem from splitting an operation that needs to be atomic across two consumer-coordinated calls. Option A keeps atomicity inside the SDK where it belongs.

The stale-children race in Option A is solvable with a re-read-before-publish strategy, and the memory concern is solved by pipelining (encrypt→pin→free, not encrypt-all→pin-all).

### 5. Desktop SDK feature equivalence

This was your added area. What's the concern here — should the Rust SDK get a matching `upload_files()` batch method in this phase, or is this about ensuring the desktop app benefits from the same parallelism?

> DEVELOPER

Mainly I wanted to understand whether the desktop app would also benefit from this addition to the rust SDK.

> AGENT

Here's the picture:

**The desktop app upload model is fundamentally different from the web app.**

- **Desktop (FUSE):** Files arrive one-at-a-time through filesystem `release()` callbacks. When you copy 10 files to the mount, macOS/Windows calls `write()` → `release()` for each file individually. Each `release()` triggers encrypt → upload → folder metadata update. There's no moment where the FUSE layer "knows" 10 files are coming as a batch.

- **Web app:** The drop handler receives `File[]` — it knows the full batch upfront, which is what enables the "encrypt+pin N files, then publish folder metadata once" optimization.

**So: a Rust `upload_files()` batch method would exist in the SDK crate, but the FUSE layer wouldn't naturally use it** — it doesn't have batch context. The desktop app would only benefit if we added a write-coalescing layer (e.g., "buffer all releases within a 500ms window, then batch-publish folder metadata once"). That's a meaningful change to the FUSE architecture and probably its own phase.

**Bottom line:** This phase should focus on the TypeScript SDK `uploadFiles()` method and the web app pipeline. The Rust SDK can get a matching `upload_files()` for API parity, but wiring it into the FUSE layer is separate work.
