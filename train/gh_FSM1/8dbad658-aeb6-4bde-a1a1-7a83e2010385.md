### Verification approach

Each test verifies via multiple channels:

### Why Node.js over k6

k6 uses a custom Go-based JS runtime that doesn't support the full Node.js crypto ecosystem (Web Crypto API, @noble/*, eciesjs). The SDK packages are pure TypeScript/ESM. Porting them to k6 would be significant work. Node.js with concurrent CipherBoxClient instances is the natural fit.

### Client Pool Design

Each "virtual user" is a CipherBoxClient with its own test account (created via test-login). The pool:
1. Creates N accounts in parallel at startup
2. Initializes N vaults + N CipherBoxClient instances
3. Distributes workload assignments
4. Collects per-operation metrics via callbacks (`onOperationStart`/`onOperationEnd`)
5. Tears down all accounts after scenario completes

Uses `Promise.allSettled` for concurrency (not worker_threads) since the bottleneck is network I/O, not CPU. Each client gets its own token via `getAccessToken` closure — the `setApiClientConfig` singleton only needs to be set once since all clients share the same `baseUrl` (the token is per-request via the closure).

### Metrics Collection

```typescript
interface OperationMetrics {
  operation: string;       // e.g., "uploadFile", "createFolder", "ipns:publish"
  count: number;
  errors: number;
  latency: { p50: number; p95: number; p99: number; max: number };
  throughputOpsPerSec: number;
  bytesTransferred?: number;  // for upload/download
}
```

Collect via `client.on()` event handler (`operation:start`, `operation:end`, `error`) — already built into CipherBoxClient. Supplement with `performance.now()` wrappers for higher-level scenario timings.

The throttler serves two purposes that are getting conflated:

1. **Abuse protection** — preventing anonymous/malicious clients from hammering the API
2. **Backpressure** — preventing legitimate clients from overwhelming a single node

For load testing, you want to remove (1) while preserving (2). If you bypass the throttler entirely with a secret header, your load tests can't tell you when the system is actually overloaded — you've removed the signal.

When you horizontally scale prod (multiple API nodes behind a load balancer), the throttle limits should scale with the cluster — either per-node limits (which naturally grow with node count) or a distributed rate limiter (Redis-backed, which you already have). - **Staging**: "Does a single node handle the expected per-node share of traffic without errors?" → throttle should reflect single-node capacity, not be bypassed
- **Prod**: "Does the cluster handle peak aggregate traffic?" → needs the actual cluster

No, there's no deep technical reason. Here's what's happening:

The singleton exists because of **orval's code generation pattern**. Orval generates standalone functions like `ipnsControllerPublishRecord()` that import `customInstance` from `../../instance.ts`. The call chain is:
```
CipherBoxClient.createFolder()
  → sdk-core.updateFolderMetadataAndPublish()
    → sdk-core.createAndPublishIpnsRecord()
      → api-client.ipnsControllerPublishRecord()  ← generated, calls customInstance()

```

The `CipherBoxClient` already has its own `getAccessToken` and `apiUrl` in its config. But `sdk-core` calls the generated functions directly without passing those through — it just imports `ipnsControllerPublishRecord` and calls it, relying on the singleton being configured.
