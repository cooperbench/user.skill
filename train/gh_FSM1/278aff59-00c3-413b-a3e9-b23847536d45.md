Here's what I found:

**No smoking gun from external sources.** FUSE-T's wiki doesn't document SMB-specific limitations, and there's no open GitHub issue about SMB rename. The release notes for recent versions (1.0.40-1.0.49) don't mention rename fixes either.

**However**, from reading the code I have a strong hypothesis about the cause. There are two likely culprits:

### 1. `access()` UID mismatch (most likely)
Our `access()` callback at `operations.rs:2360` does this:
```rust
if req.uid() != attr.uid {
    reply.error(libc::EACCES);
    return;
}
```
When the SMB backend is active, FUSE-T's SMB server may send requests with a **different UID** than the one we set on inodes (from `getuid()`). The macOS SMB client likely calls `access()` to check write permission on the parent directory before attempting rename — if that returns EACCES, the client gives up with EPERM and our `rename()` callback is never reached.

### 2. SMB protocol-level permission check
The macOS SMB client may check reported file attributes (permissions, ownership) from `getattr()` and decide the user doesn't have write access to the parent directory, rejecting the rename client-side.

**What I'd suggest next:**
- Add debug logging to `access()` to confirm whether it's being called during rename attempts and what UIDs come through
- If confirmed, make `access()` more permissive for the SMB backend (since this is a single-user local mount, strict UID checking isn't necessary)
- Test whether that unblocks rename

Want me to go ahead and implement the fix? It should be pretty targeted — just relaxing the `access()` UID check.
