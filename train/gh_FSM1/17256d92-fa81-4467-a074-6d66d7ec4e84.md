ok, one thing I wanted to discuss is how we migrate data on staging.

> AGENT

The core question is whether to preserve existing pinned content on staging or start fresh. A few options:

1. **Clean slate** — `docker volume rm` + fresh pebbleds init. All existing pinned CIDs are lost. Staging users would need to re-upload. Simplest path.

2. **Kubo datastore migration** — Kubo has `ipfs repo migrate` but flatfs→pebbleds isn't a standard migration path. There's `ipfs-ds-convert` which can convert between datastore backends, but it's not always reliable for large repos.

3. **Pin export/reimport** — `ipfs pin ls --type recursive` before the switch, then re-pin all CIDs after. Only works if content is still available from the network (or you keep the old volume mounted read-only).

4. **Parallel cutover** — Spin up a second IPFS container with pebbleds alongside the existing one, re-pin content to the new instance, then swap.

Given staging is a test environment — is a clean slate acceptable, or is there data on staging you need to preserve?

If this were production I would definitely be going for the parallel cutover route. How much work would it be to add handling for this to the staging deployment script?

> AGENT

The deploy workflow is fairly straightforward — it SSHes into the VPS, copies files, and runs `docker compose up -d`. Here's what a parallel cutover would involve:

**Moderate work — roughly a single plan's worth:**

1. **Add `ipfs-new` service** to `docker-compose.staging.yml` alongside existing `ipfs`:
   - Fresh volume (`ipfs_staging_new`), pebbleds profile
   - Different ports (5002/8081 internally, still localhost-bound)

2. **Pin migration script** — iterate `ipfs pin ls` on old node, re-pin each CID to new node:
   ```bash
   docker exec ipfs-old ipfs pin ls --type=recursive -q | while read cid; do
     docker exec ipfs-new ipfs pin add "$cid"
   done
   ```
   This works because both nodes share the same Docker network and can fetch from each other via bitswap.

3. **API switchover** — update `IPFS_LOCAL_API_URL` from `http://ipfs:5001` to `http://ipfs-new:5001` in `.env`, restart API.

4. **Cleanup** — remove old service + volume after confirming everything resolves.

5. **Deploy workflow change** — minimal. The workflow already copies the compose file and runs `up -d`. Adding a migration step between "pull" and "up" would be a few lines in the SSH heredoc.

**The risk is low** because:
- Both nodes coexist on the same Docker network
- Bitswap handles content transfer automatically
- The API only talks to one node at a time (no dual-write needed)
- Rollback = flip the env var back to old node

The main question is whether to bake this into the deploy workflow as a reusable migration step, or do it as a one-time manual procedure on the VPS.
