708	  return new Promise((resolve, reject) => {

714	    let unlisten: UnlistenFn | null = null;
715	    let timeout: ReturnType<typeof setTimeout> | null = null;

718	      if (unlisten) {

720	        unlisten = null;
721	      }
722	      if (timeout) {
723	        clearTimeout(timeout);
724	        timeout = null;
725	      }
726	    };
727	
728	    const nonce = crypto.randomUUID();
729	    const state = crypto.randomUUID();
730	
731	    // Start the OAuth callback server and open the popup
732	    (async () => {
733	      try {
734	        // Start temporary localhost HTTP server for OAuth callback
735	        const { port, event_name: eventName } = await invoke<{
736	          port: number;

> AGENT

There's the problem. The Rust backend uses `option_env!("VITE_API_URL")` at compile time (step 3), but `VITE_API_URL` is a Vite convention — it's not automatically passed to the Rust compiler. The `pnpm tauri build` command doesn't forward `.env` vars to `cargo build`, so `option_env!("VITE_API_URL")` resolves to `None` and it falls back to `http://localhost:3000`.

The CI workflow sets `VITE_API_URL` as a process-level env var which `option_env!` picks up during compilation. But locally, those vars are only in `apps/desktop/.env` which Vite reads but Cargo doesn't.

You can test it by rebuilding with the env var exported:

```
VITE_API_URL=https://api-staging.cipherbox.cc pnpm --filter desktop build
```

But the real fix should ensure this works reliably. The simplest option: change the fallback from `localhost:3000` to the staging URL since that's the default target anyway. Want me to do that, or would you prefer a different approach?
