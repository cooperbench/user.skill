in terms of ipfs nodes, could you not use a public ipfs gateway as the tool intends? or are the local pins and ipns names not resolvable from public ipfs gateways?

> AGENT

Good question. The local pins and IPNS names are **not resolvable from public gateways** because:

1. **IPFS pins** — Your local Kubo node isn't connected to the public DHT in a way that makes content discoverable. Pins on a local/private Kubo instance aren't announced to the public network unless the node is publicly reachable and participating in the DHT.

2. **IPNS records** — The SDK publishes IPNS records through the CipherBox API, which writes them to the local Kubo node + DB cache. These records are only propagated to the public DHT if your Kubo node is connected to the public IPFS network and has completed the DHT publish. For a test vault created seconds before the recovery attempt, there's no time for propagation.

So for E2E testing, recovery.html **must** reach the same Kubo instance that holds the pins and IPNS records. The options remain:

1. **Configure Kubo CORS** on `192.168.133.12` — then the browser can reach Kubo directly
2. **Add an IPFS content proxy** to the CipherBox API (e.g. `GET /ipfs/cat/:cid`) so the browser can fetch content through `localhost:3000` which already has CORS configured
3. **Skip locally** — the test validates the recovery.html structure/flow; actual IPFS resolution is an infrastructure concern better tested in a controlled CI environment

Which approach do you prefer? Option 1 is the quickest (two `ipfs config` commands + restart), option 2 is more robust long-term.

Mock-ipns-routing makes sense for CI. Here's why:

**What mock gives you:**
- Deterministic, no DHT propagation delays (IPNS publishes resolve instantly)
- No dependency on external network or public IPFS
- Fast, isolated, reproducible runs
- Simulates the delegated routing API contract (`/routing/v1/ipns/:name`) that production uses

**What someguy would give you:**
- More realistic routing path (actual DHT interaction with Kubo)
- Kubo's gateway could resolve IPNS names directly (would've avoided this recovery test issue)
- But: adds another Docker service, slower (DHT propagation), potential flakiness from network timing

**The tradeoff:** 99% of your E2E tests resolve IPNS through the CipherBox API, which has the DB cache. They never hit the gateway directly. The mock is perfect for that path — fast and reliable.

The recovery.html test is the one outlier because it's a standalone tool that talks to gateways directly, bypassing the API. Pointing its IPNS resolution at the API (PR #364) is the right fix — it tests the actual recovery flow while working within CI's infrastructure.

**Bottom line:** Keep mock-ipns-routing for CI. The only scenario where someguy would matter is testing real DHT propagation, which is better suited for a staging environment integration test than CI.
