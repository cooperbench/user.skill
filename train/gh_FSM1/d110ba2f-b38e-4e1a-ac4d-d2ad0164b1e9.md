> DEVELOPER

I had a quick question about the subfolder ipns keys - are these random so that a folder can be shared with another user (in the next phase) allowing them to update the folder metadata (children) without exposing any other keys? am I interpretting this correctly?

> AGENT

Yes, you're interpreting it correctly. Each subfolder gets its own **independently generated IPNS keypair** (Ed25519). The key design properties:

1. **Independent keypair per folder** — the subfolder's `ipnsPrivateKey` is generated fresh (random), not derived from the parent. This means possessing it gives write access to *only* that folder's IPNS record (i.e., updating its children list).

2. **Stored encrypted in parent metadata** — the parent's decrypted metadata contains `ipnsPrivateKeyEncrypted` for each child folder (line 320 of TECHNICAL_ARCHITECTURE.md). So you need the parent's `folderKey` to decrypt it.

3. **Sharing-ready isolation** — as the spec explicitly notes on line 498: *"This design enables future per-folder sharing (v2+)."* In a sharing scenario, you'd give the recipient:
   - The subfolder's `folderKey` (to decrypt the metadata)
   - The subfolder's `ipnsPrivateKey` (to publish updated metadata)
   - The subfolder's `ipnsName` (to resolve it)
   
   And they could read/write that subtree without ever seeing the parent folder's keys, the root folder key, or any sibling folder keys.

So yes — the per-folder IPNS keys are random/independent specifically to enable granular sharing boundaries. Each folder is a self-contained "unit of access" with its own encryption key (`folderKey`) and its own publish authority (`ipnsPrivateKey`).

It is mentioned — line 416 has a note explaining that subfolder IPNS keys are randomly generated (not HKDF-derived), with the keypair ECIES-wrapped in the parent's metadata.

Section 14 documents HKDF derivations specifically (deterministic key → IPNS keypair). Only three things use that pattern:

| IPNS Key | Derivation |
|---|---|
| **Vault root** | HKDF(privateKey, "cipherbox-vault-ipns-v1") |
| **Device registry** | HKDF(privateKey, "cipherbox-device-registry-ipns-v1") |
| **Per-file** | HKDF(privateKey, "cipherbox-file-ipns-v1-{fileId}") |

Subfolder IPNS keys are the odd one out — they're randomly generated Ed25519 keypairs, stored ECIES-encrypted in the parent folder's metadata (`ipnsPrivateKeyEncrypted`). > AGENT

Great question — you're spotting a real asymmetry in the design. Let me lay out the tradeoff:

**Why folders are random:** Exactly as you identified — a random IPNS keypair can be handed to another user (ECIES-wrapped with their publicKey), giving them independent publish authority over that folder's children list. The key is stored encrypted in the parent metadata, so it's still recoverable through the hierarchy.

**Why files are deterministic:** The main benefit is **self-sovereign recovery** — from just a recovery phrase, you can derive `privateKey → HKDF → every file IPNS key` without needing to traverse the folder tree first. No stored key to lose. It also simplified TEE republishing (TEE can re-derive file IPNS keys without storing them).

**Your point is valid though.** If you wanted write-sharing on a file (let another user upload new content and publish to the file's IPNS), you'd need to give them the file's IPNS private key. While that's cryptographically safe (HKDF is one-way — they can't reverse it to get your secp256k1 key), it's architecturally awkward: deterministic derivation implies "only the owner can derive this."

That said, the current roadmap has this noted in STATE.md:

> Read-only sharing only (no multi-writer IPNS) — Unsolved problem, deferred to v3

The deeper issue with multi-writer IPNS isn't just key distribution — it's that IPNS uses **monotonic sequence numbers**. Two writers publishing concurrently would create conflicting records (whoever publishes with the higher sequence number wins, and the other's update is silently lost). That's the "unsolved problem."

So the deterministic design was a deliberate simplification for v1-v2 where only the owner ever publishes. If/when multi-writer becomes a goal in v3, switching file IPNS keys to random (stored in parent metadata like folder keys) would be part of that larger rework — alongside solving the sequence number conflict problem.
