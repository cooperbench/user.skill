229	### Pitfall 4: Memory Leak from Uncleared Timers
230	
231	**What goes wrong:** User navigates away while upload is in progress. Completion flash timers fire on unmounted components.
232	**Why it happens:** `setTimeout` callbacks run regardless of component lifecycle.
233	**How to avoid:** Use `useRef` to track timer IDs and `useEffect` cleanup to clear them on unmount. This pattern is already used in the existing `UploadModal.tsx`.
234	**Warning signs:** React "Cannot update a component that is not mounted" warnings in console.
235	
236	### Pitfall 5: Duplicate File Entries During Swap
237	
238	**What goes wrong:** Both the upload-in-progress virtual entry AND the real file appear simultaneously in the file list during the swap window.
239	**Why it happens:** The real file appears in `children` (from IPNS sync) while the upload row is still showing the green completion flash.
240	**How to avoid:** During the merge in `FileList`, skip real files whose name matches an active upload entry that is in `complete` or `swapping` state. The upload row takes visual precedence until it finishes its animation and is removed.
241	**Warning signs:** Duplicate rows with the same filename in the file list.
242	
243	### Pitfall 6: Progress Bar Causing Excessive Re-renders
244	
245	**What goes wrong:** Axios progress events fire many times per second. If each progress update triggers a re-render of the entire `FileList`, performance degrades.
246	**Why it happens:** Zustand store update -> all subscribers re-render.
247	**How to avoid:** Use fine-grained selectors. `UploadListItem` should subscribe to only its own file's progress: `useUploadStore(s => s.files.get(fileId)?.progress)`. The `FileList` component subscribes to only the _set of upload file IDs_ (for merging), not their progress values.
248	**Warning signs:** Jank during upload, React DevTools showing frequent `FileList` re-renders.

450	## Open Questions
451	
452	1. **Retry mechanism for failed uploads**
453	   - What we know: D-09 specifies retry button. The existing `upload.service.ts` has `withRetry()` with exponential backoff for individual IPFS calls, but no retry at the per-file level from the UI.
454	   - What's unclear: Should retry re-encrypt the file from the original `File` object, or cache the encrypted blob? Caching encrypted data avoids re-encryption cost but increases memory usage.
455	   - Recommendation: Re-encrypt from scratch on retry. The `File` object reference is kept in the closure of `useDropUpload.handleFileDrop`. For retry to work, the file ID and original `File` reference need to be stored somewhere accessible. The simplest approach: store the `File` reference in `PerFileUpload` (it's already in memory during the upload loop). The upload loop should continue past failed files and let the user retry individually.
456	
457	2. **Upload entries for duplicate/replacement files**
458	   - What we know: `useDropUpload` handles duplicate files separately (encrypts + uploads to IPFS but doesn't register in folder). These show up in the `pendingReplacements` array for the `ReplaceFileDialog`.
459	   - What's unclear: Should duplicate file uploads also show inline progress rows?
460	   - Recommendation: Yes, show inline progress for duplicate uploads too. They go through the same encrypt+upload pipeline. After upload completes, the `ReplaceFileDialog` appears for the user to decide. The inline row can transition to `complete` state normally since the file is uploaded (just not registered yet).
461	
462	3. **SharedFileBrowser upload integration**
463	   - What we know: `SharedFileBrowser` has its own upload mechanism that doesn't use `UploadModal` or `useUploadStore`. It uses a direct file input + SDK `uploadFile()`.
464	   - What's unclear: Should shared folder uploads also get inline progress?
465	   - Recommendation: Out of scope for this phase. The SharedFileBrowser is a separate component with its own state management. Inline progress for shared folders can be a follow-up.
