> AGENT

Honestly, I think the risk is narrow but real, and the fix is cheap enough that "is it worth the churn" barely applies.

**The actual gap:** If you trigger the workflow after a feature PR merges but before release-please's PR is merged, you'd stage an unversioned commit. The E2E gate catches functional regressions but won't catch that semantic problem — you'd end up with a staging deployment that doesn't correspond to any release.

**In practice** that window is small since you'd typically wait for the release PR, as you just did. But it's exactly the kind of thing that bites you once at 11pm when you're rushing.

**My suggestion:** Don't go back to the old input-based approach. Instead, add a single validation step in `resolve-main` that confirms a release tag exists on HEAD. Something like:

```yaml
- id: main
  run: |
    SHA=$(git rev-parse HEAD)
    if ! git tag --points-at "$SHA" | grep -qE '^(cipher-box-v|@cipherbox/)'; then
      echo "::error::No release tag found on main HEAD ($SHA). Wait for release-please to merge."
      exit 1
    fi
    echo "sha=$SHA" >> "$GITHUB_OUTPUT"
```

That gives you the old safety guarantee (only stage released code) with the current simplicity (no manual tag selection). Three lines, fast-fail, clear error message.

The full CI vs staging-E2E stringency gap is a separate concern — if the staging pipeline is missing checks you care about, that's worth tightening regardless of how the SHA is resolved.
