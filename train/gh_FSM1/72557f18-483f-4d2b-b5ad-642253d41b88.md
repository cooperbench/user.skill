Here's the breakdown of `folder_ipns` and what "advisory" means: ### What `folder_ipns` does today (6 roles) 1. **CID cache** — `latestCid` stores the most recent CID for each IPNS name. When delegated-ipfs.dev fails (502) or returns stale data, the DB is the fallback. 2. **Sequence number tracking** — `sequenceNumber` is the authoritative counter for optimistic concurrency. On every publish, the API checks `expectedSequenceNumber` against the DB value and returns 409 Conflict on mismatch. This prevents two devices from overwriting each other. 3. **TEE key storage** — `encryptedIpnsPrivateKey` + `keyEpoch` hold the IPNS private key wrapped with the TEE public key. The TEE batch republisher reads these to re-sign and republish records every 3-6 hours so they don't expire from the DHT. 4. **TEE republish scheduling** — The republish service queries `folder_ipns` to find all records that need republishing. 5. **User folder enumeration** — `getAllFolderIpns(userId)` lists all a user's IPNS names. 6. **Resolve fallback** — `resolveRecord()` always checks both the network AND the DB, preferring whichever has the higher sequence number (`ipns.service.ts:326-336`). ### What "make it advisory" would mean The idea is: instead of `folder_ipns` being the **authoritative** source for CIDs and sequence numbers, IPNS resolution (via self-hosted Someguy) becomes primary, and the DB becomes a **performance cache** that's nice to have but not required. **What would change:** - Resolve would try Someguy/Kubo DHT first, fall back to DB only on failure - Sequence number could be read from the IPNS record itself rather than the DB - Theoretically, a user with BYO-IPFS + reliable IPNS wouldn't need the DB rows at all **What CANNOT change (blocking dependencies):** - **TEE republishing** — The TEE needs `encryptedIpnsPrivateKey` from this table.
