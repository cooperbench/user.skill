    20→
    21→## Core Idea: IPNS Inbox with CRDT Content Model
    22→
    23→### Share Discovery via Deterministic IPNS Address
    24→
    25→Derive a per-recipient IPNS "inbox" address from their public key:
    26→
    27→```text
    28→inbox_ipns_privkey = HKDF(recipient_pubkey, info="share-inbox")

    33→- Recipients resolve their own inbox IPNS to discover shares
    34→- Content encrypted so only recipient can decrypt
    35→- Server never sees the sharing graph
    36→
    37→### Why CRDTs Solve the Write-Conflict Problem
    38→
    39→The naive IPNS inbox has a fundamental issue: IPNS is last-writer-wins, so concurrent shares from different users overwrite each other. CRDTs (Conflict-free Replicated Data Types) turn this weakness into a feature:
    40→
    41→- **G-Set (Grow-only Set):** Share invitations are append-only — new shares are added, never removed from the inbox. A G-Set merges concurrent additions without conflict.
    42→- **OR-Set (Observed-Remove Set):** If revocation needs to remove entries, OR-Set supports both add and remove with deterministic conflict resolution.
    43→- Each write includes the full CRDT state. Concurrent writers produce valid states that merge on read.
    44→
    45→### Cross-Cutting Benefit
    46→
    47→The same CRDT-over-IPNS pattern applies to other conflict-prone areas:
    48→
    49→- **Folder metadata sync** — concurrent edits from multiple devices
    50→- **Device registry** — multiple devices registering simultaneously
    51→- **Share inbox** — multiple sharers publishing to the same recipient
    52→- **Any future multi-writer state**
    53→
    54→Solving this once gives all features coordination-free merging.

    58→### Write Access Control
    59→

    42→| Feature                                       | Why Requested                                                                               | Why Problematic                                                                                                                                                                                                                                                                                                                                                                                         | Alternative                                                                                                                                                                                                  |
    43→| --------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
    44→| Full database elimination (zero DB)           | Philosophical purity -- "everything on IPFS." Sounds clean.                                 | Auth-method-to-userId mapping requires indexed, queryable storage. IPFS is content-addressed immutable blobs -- not a database. Refresh tokens need server-side revocation. Session management needs server state. Forcing these into IPFS adds complexity without improving privacy (auth data is inherently server-known).                                                                            | Keep auth tables (users, auth_methods, refresh_tokens) in PostgreSQL. Migrate everything else to IPFS/IPNS. The remaining DB is ~3 tables with no crypto material.                                           |
    45→| IPNS PubSub as primary resolution             | Faster than DHT after subscription (instant updates vs seconds). Sounds like the speed fix. | Only works when both publisher and resolver are connected to common PubSub peers. Not persistent -- if resolver was offline during publish, it misses the update and falls back to DHT. Adds connection overhead (6 connections per subscription by default). CipherBox has potentially thousands of IPNS names per user (folders + files). PubSub subscription per name is not feasible at that scale. | Use DHT via self-hosted Someguy as primary. PubSub is useful for real-time collab (future) but not for general IPNS resolution at CipherBox's scale.                                                         |
    46→| CRDT-based IPNS for all metadata (v1.1 scope) | Solves multi-writer conflicts once as a horizontal concern. Theoretically clean.            | CRDTs require all writers to have the IPNS private key. For folder metadata, only the owner (and write-sharing recipients) should publish. CRDTs add state size growth (monotonic), compaction complexity, and merge semantics that must be correct across TypeScript and Rust implementations. Premature optimization for a problem that optimistic concurrency already solves.                        | Keep optimistic concurrency (sequence number checks) for v1.1. Research CRDTs for share inbox only (the one true multi-writer case). Implement in v1.2+ if research validates.                               |
    47→| Client-direct IPFS upload as default          | True decentralization -- client talks directly to IPFS without server relay.                | Breaks quota tracking (server cannot meter what it does not relay). Breaks conflict detection (server cannot check sequence numbers on bypassed publishes). CORS issues with Kubo API. User's IPFS node may be behind NAT/firewall. Client needs to handle Kubo API directly -- fragile and version-dependent.                                                                                          | Server-relay as default. BYO-IPFS uses server-relay to user's configured node (server proxies to user's endpoint). Client-direct is an opt-in advanced mode with explicit "quota tracking disabled" warning. |
    48→| DNSLink as IPNS alternative                   | Human-readable names, fast resolution, well-supported.                                      | Requires DNS infrastructure management per user. TXT record propagation is slow (minutes to hours). Not self-sovereign -- depends on DNS provider. Does not support the per-folder/per-file IPNS keypair model (would need a DNS record per folder). Not feasible at CipherBox's scale of IPNS names.                                                                                                   | Keep IPNS for all mutable pointers. DNSLink is useful for public web content, not for per-user encrypted vaults with thousands of mutable pointers.                                                          |

   103→## Feature Deep Dives
   104→
   105→### 1. Self-Hosted IPNS Resolution
   106→
   107→**Current state:** `DelegatedRoutingClient` points at `https://delegated-ipfs.dev/routing/v1`. This is a public good endpoint maintained by the IPFS Foundation, backed by Someguy. It proxies to the Amino DHT and IPNI (cid.contact indexer). Known issues: 502 errors, rate limiting (429), stale records due to caching.
   108→
   109→**Recommendation: Self-host Someguy alongside Kubo.**
   110→
   111→Someguy is the same software powering `delegated-ipfs.dev`. Self-hosting it gives:
   112→
   113→- Full control over caching, rate limits, and availability
   114→- Same DHT and IPNI backends, but without shared public infrastructure load
   115→- Docker deployment: `ghcr.io/ipfs/someguy:latest`
   116→- Minimum resources: runs alongside existing Kubo node, shares its DHT participation
   117→- Configuration via environment variables (endpoints, caching, DHT toggles)
   118→
   119→**Architecture:**
   120→
   121→```text
   122→Client -> CipherBox API -> Self-hosted Someguy -> Amino DHT / IPNI
   123→                        -> DB cache (fallback, sequence-number-aware)
   124→```
   125→
   126→**Fallback chain:**
   127→
   128→1. Self-hosted Someguy (primary)
   129→2. DB-cached CID (always fresh for own publishes)
   130→3. delegated-ipfs.dev (emergency fallback, best-effort)
   131→
   132→**Performance expectations (from ProbeLab Week 07, 2026):**
   133→
   134→- DHT lookup: 0.3-0.4s median across regions
   135→- Self-hosted avoids public endpoint queuing -- expect lower variance
   136→- Kubo 0.34+ default IPNS TTL: 5 minutes (down from 1 hour) -- faster propagation
   137→
   138→**Complexity:** MEDIUM
   139→
   140→- Docker Compose addition for Someguy
   141→- Update `DELEGATED_ROUTING_URL` env var
   142→- Update `DelegatedRoutingClient` for fallback chain
   143→- Scrape Someguy's Prometheus metrics
   144→
   145→**Confidence:** HIGH -- Someguy is the reference implementation for Routing V1. Self-hosting is explicitly documented.
   146→
   147→### 2. Move rootFolderKey to IPFS Vault Record
   148→
   149→**Current state:** `vaults` table stores `encryptedRootFolderKey` (ECIES-wrapped with user's publicKey) and `encryptedRootIpnsPrivateKey`. The IPNS private key is deterministically derivable via HKDF, so only `encryptedRootFolderKey` truly needs storage.
   150→
   151→**Recommendation: Embed ECIES-wrapped rootFolderKey in the IPFS blob pointed to by the root vault IPNS record.**
   152→
   153→**New bootstrap flow:**
   154→
   155→1. Login with Web3Auth, derive secp256k1 keypair
   156→2. Derive root IPNS private key via HKDF (deterministic, no storage needed)
   157→3. Resolve root IPNS name to get CID
   158→4. Fetch IPFS blob at CID
   159→5. Blob contains: `{ encryptedRootFolderKey: <ECIES>, metadata: <AES-GCM encrypted FolderMetadata> }`
   160→6. Unwrap rootFolderKey with privateKey
   161→7. Decrypt FolderMetadata with rootFolderKey
   162→
   163→**Migration strategy:**
   164→
   165→- New blob format versioned (per METADATA_EVOLUTION_PROTOCOL)
   166→- Dual-read period: client checks IPFS blob first, falls back to DB vault record
   167→- Lazy migration: on next folder metadata publish, client writes new-format blob
   168→- After migration period, `vaults.encrypted_root_folder_key` column becomes nullable/deprecated
   169→- Recovery tool updated for new blob format
   170→
   171→**What stays in DB:** `vaults` table retains `owner_id`, `root_ipns_name`, and timestamps. The `owner_public_key` column stays (needed for share ECIES wrapping lookups). Crypto material columns become nullable.
   172→
   173→**Risk:** IPNS resolution failure during login is a hard blocker. Mitigated by:
   174→
   175→- DB-cached CID fallback (server stores latest CID in `folder_ipns` table)
   176→- Self-hosted Someguy improving baseline reliability
   177→- Client retries with exponential backoff
   178→
   179→**Complexity:** HIGH
   180→
   181→- New IPFS blob envelope format
   182→- Metadata schema version bump
   183→- Migration path (dual-read, lazy migration)
   184→- Recovery tool update
   185→- Desktop app (Rust) must parse new format
   186→- E2E test updates for new login flow
   187→
   188→**Confidence:** MEDIUM -- The approach is sound, but the migration path has edge cases (what if user never logs in during dual-read period? stale recovery tools?).
   189→
   190→### 3. BYO-IPFS Node Support
   191→
   192→**Current state:** `IpfsProvider` interface (`pinFile`, `unpinFile`, `getFile`) with single `LocalProvider` implementation pointing at the server's Kubo instance via env var `IPFS_LOCAL_API_URL`.
   193→
   194→**Recommendation: Add a `RemotePinningProvider` implementing `IpfsProvider` against the IPFS Pinning Service API standard, configured per-user.**
   195→
   196→**The IPFS Pinning Service API** is a vendor-agnostic OpenAPI spec. Endpoints:
   197→
   198→- `POST /pins` -- Pin by CID (with origins hint for faster retrieval)
   199→- `GET /pins` -- List pins with filtering
   200→- `GET /pins/{requestid}` -- Status of specific pin
   201→- `DELETE /pins/{requestid}` -- Unpin
   202→- Auth: Bearer token per service
   203→
   204→**Supported services:** Filebase, Pinata (partial -- no IPNS), web3.storage, IPFS Cluster, any self-hosted Kubo with pinning API enabled.
   205→
   206→**Architecture (server-relay mode -- recommended default):**
   207→
   208→```text
   209→Client -> CipherBox API -> Provider Router -> LocalProvider (default)
   210→                                           -> RemotePinningProvider (user's node)
   211→```
   212→
   213→**Per-user configuration model:**
   214→
   215→- New `user_ipfs_config` table or extend vault settings:
   216→  - `pinning_endpoint_url` (e.g., `https://api.filebase.io/v1`)
   217→  - `pinning_auth_token` (encrypted at rest with server key -- or ECIES-wrapped with user's publicKey for zero-knowledge)
   218→  - `provider_type` enum: `default` | `pinning-api` | `kubo-direct`
   219→- Settings UI: endpoint URL, auth token, "test connection" button
   220→
   221→**Key design decisions:**
   222→
   223→1. **Server-relay vs client-direct:** Server-relay because:
   224→   - Quota tracking works (server meters bytes relayed)
   225→   - Conflict detection works (server sees all publishes)
   226→   - No CORS issues
   227→   - User's auth token stored server-side (encrypted)
   228→   - Tradeoff: server sees encrypted blobs transit (acceptable -- data is already encrypted client-side)
   229→
   230→2. **Dual-pin strategy:** Pin to BOTH default node AND user's node. User's node is "additional persistence," not replacement. Ensures CipherBox can still serve the data if user's node goes down.
   231→
   232→3. **IPNS implications:** IPNS publishing still goes through self-hosted Someguy/DHT, not user's node. IPNS is a naming layer, independent of pinning. User's node provides content persistence, not name resolution.
   233→
   234→4. **Quota tracking:** When BYO-IPFS is configured, server-side quota is advisory ("you have X bytes on our node"). User's node quota is user's problem.
   235→
   236→**Complexity:** HIGH
   237→
   238→- New provider implementation against Pinning Service API
   239→- Per-user configuration storage
   240→- Provider routing logic (which user gets which provider)
   241→- Settings UI
   242→- "Test connection" flow
   243→- Error handling for unreachable user nodes
   244→- Dual-pin logic
   245→
   246→**Confidence:** MEDIUM -- The Pinning Service API is well-specified, but per-user provider routing in a NestJS DI context needs careful design. Zero-knowledge storage of auth tokens (ECIES-wrapped) adds crypto complexity.
   247→
   248→### 4. Database Minimization (Beyond rootFolderKey)
   249→
   250→**Current DB tables and migration analysis:**
   251→
   252→| Table                     | Rows Per User     | Contains Crypto?                                              | Can Move to IPFS?                                          | Recommendation                                |
   253→| ------------------------- | ----------------- | ------------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------- |
   254→| `users`                   | 1                 | No                                                            | No -- auth identity                                        | KEEP                                          |
   255→| `auth_methods`            | 1-5               | No                                                            | No -- auth lookup                                          | KEEP                                          |
   256→| `refresh_tokens`          | 1-10              | No                                                            | No -- session management                                   | KEEP                                          |
   257→| `vaults`                  | 1                 | Yes (`encryptedRootFolderKey`, `encryptedRootIpnsPrivateKey`) | Partially -- crypto to IPFS, metadata stays                | MIGRATE crypto columns                        |
   258→| `folder_ipns`             | N (folders+files) | Yes (`encryptedIpnsPrivateKey`)                               | Partially -- CID cache useful, TEE keys needed server-side | KEEP as cache, make optional                  |
   259→| `pinned_cids`             | N (files)         | No                                                            | Could derive from IPFS pin list                            | DEFER -- `ipfs pin ls` is slow for large sets |
   260→| `shares`                  | N (shares)        | Yes (`encryptedKey`)                                          | Theoretically via CRDT inbox                               | KEEP for v1.1, research CRDT for v1.2         |
   261→| `share_keys`              | N (per-share)     | Yes (`encryptedKey`)                                          | Same as shares                                             | KEEP for v1.1                                 |
   262→| `share_invites`           | N (pending)       | Yes                                                           | Same as shares                                             | KEEP for v1.1                                 |
   263→| `ipns_republish_schedule` | N (folders)       | No                                                            | No -- TEE coordination needs server-side scheduling        | KEEP                                          |
   264→
   265→**What realistically moves to IPFS in v1.1:**
   266→
   267→1. `vaults.encryptedRootFolderKey` and `vaults.encryptedRootIpnsPrivateKey` -> IPFS blob
   268→2. `folder_ipns.latestCid` becomes advisory cache, not authoritative source
   269→3. `folder_ipns.encryptedIpnsPrivateKey` stays -- TEE needs server-accessible copy
   270→
   271→**What stays in DB and why:**
   272→
   273→- Auth tables: Indexed lookups required for login flow
   274→- Shares: Complex query patterns (list by recipient, filter by status, revocation state)
   275→- Pinned CIDs: Quota tracking requires fast aggregation queries
   276→- Republish schedule: TEE coordination requires server-side cron state
   277→- Folder IPNS: Sequence numbers needed for conflict detection; CID cache needed for IPNS fallback
   278→
   279→**Realistic v1.1 DB state after migration:**
   280→
   281→- Auth-only: `users`, `auth_methods`, `refresh_tokens` (3 tables, no crypto)
   282→- Vault metadata: `vaults` with crypto columns nullable (1 table, crypto migrated)
   283→- IPFS operations: `folder_ipns`, `pinned_cids`, `ipns_republish_schedule` (3 tables, operational cache)
   284→- Sharing: `shares`, `share_keys`, `share_invites` (3 tables, unchanged)
   285→
   286→**Reality check:** The goal of "reduce database to auth-only" is aspirational for v1.1. Realistically, v1.1 can eliminate crypto from `vaults` and make `folder_ipns` an advisory cache. Full share migration requires CRDT research. Full `pinned_cids` elimination requires alternative quota tracking.
   287→
   288→**Complexity:** Per-table varies (see table above). Overall: HIGH for rootFolderKey migration, LOW for making `folder_ipns` advisory, VERY HIGH for share migration (deferred).
   289→
   290→**Confidence:** MEDIUM -- rootFolderKey migration is well-understood. The gap between "auth-only DB" and "realistic v1.1" is significant.

Here's the breakdown of `folder_ipns` and what "advisory" means:

### What `folder_ipns` does today (6 roles)

1. **CID cache** — `latestCid` stores the most recent CID for each IPNS name. When delegated-ipfs.dev fails (502) or returns stale data, the DB is the fallback.

2. **Sequence number tracking** — `sequenceNumber` is the authoritative counter for optimistic concurrency. On every publish, the API checks `expectedSequenceNumber` against the DB value and returns 409 Conflict on mismatch. This prevents two devices from overwriting each other.

3. **TEE key storage** — `encryptedIpnsPrivateKey` + `keyEpoch` hold the IPNS private key wrapped with the TEE public key. The TEE batch republisher reads these to re-sign and republish records every 3-6 hours so they don't expire from the DHT.

4. **TEE republish scheduling** — The republish service queries `folder_ipns` to find all records that need republishing.

5. **User folder enumeration** — `getAllFolderIpns(userId)` lists all a user's IPNS names.

6. **Resolve fallback** — `resolveRecord()` always checks both the network AND the DB, preferring whichever has the higher sequence number (`ipns.service.ts:326-336`).

### What "make it advisory" would mean

The idea is: instead of `folder_ipns` being the **authoritative** source for CIDs and sequence numbers, IPNS resolution (via self-hosted Someguy) becomes primary, and the DB becomes a **performance cache** that's nice to have but not required.

**What would change:**
- Resolve would try Someguy/Kubo DHT first, fall back to DB only on failure
- Sequence number could be read from the IPNS record itself rather than the DB
- Theoretically, a user with BYO-IPFS + reliable IPNS wouldn't need the DB rows at all

**What CANNOT change (blocking dependencies):**
- **TEE republishing** — The TEE needs `encryptedIpnsPrivateKey` from this table. No alternative storage exists server-side. This column must stay.
- **Optimistic concurrency** — The 409 conflict check compares sequence numbers atomically in PostgreSQL. Moving this to "resolve IPNS first, then compare" introduces race conditions (two clients resolve the same stale value, both think they're current). The DB check is inherently stronger.
- **Republish scheduling** — The republish cron queries this table to find what needs republishing.

### My assessment

Making `folder_ipns` truly "advisory" is mostly blocked by TEE republishing and concurrency checking — both of which fundamentally need server-side state. You'd be investing effort into a change that can't fully deliver because 2 of the 3 critical columns (`encryptedIpnsPrivateKey`, `sequenceNumber`) must remain authoritative.

The practical gain is small: `latestCid` already works as a "best-of-both" cache (line 326-336 picks the fresher source). Switching from "DB fallback" to "IPNS primary" is essentially just reordering the resolution chain, which the Someguy work already improves.

**Recommendation:** Skip this for v1.1. The Someguy self-hosting already improves IPNS reliability enough that the DB fallback triggers less often. The table stays as-is — it's pulling its weight across all 6 roles.
