Yep — classic issue. The default `GITHUB_TOKEN` used by Release Please won't trigger other workflows on the PR it creates. Two options, from easiest to most proper: ### Option 1: Use a PAT (easiest) Create a fine-grained PAT with `contents: write` + `pull-requests: write` scopes, add it as a repo secret (e.g., `RELEASE_PLEASE_TOKEN`), then: ```yaml - uses: googleapis/release-please-action@v4 with: config-file: release-please-config.json manifest-file: .release-please-manifest.json token: ${{ secrets.RELEASE_PLEASE_TOKEN }} ``` ### Option 2: GitHub App (more proper, no expiry) Create a GitHub App with the same permissions, install it on the repo, then use `actions/create-github-app-token` to mint a short-lived token: ```yaml steps: - uses: actions/create-github-app-token@v1 id: app-token with: app-id: ${{ vars.RELEASE_PLEASE_APP_ID }} private-key: ${{ secrets.RELEASE_PLEASE_APP_KEY }} - uses: googleapis/release-please-action@v4 with: config-file: release-please-config.json manifest-file: .release-please-manifest.json token: ${{ steps.app-token.outputs.token }} ``` **Option 1** is a 2-minute fix. The only downside is PATs expire and are tied to a user account. **Option 2** is better long-term but takes ~10 minutes to set up the GitHub App. Want me to apply either of these?
