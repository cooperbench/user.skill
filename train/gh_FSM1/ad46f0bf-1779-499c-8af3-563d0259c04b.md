No workflow needed here; I already dug through the code, so this is just me explaining it. ## The background you need first CipherBox stores your encrypted files on IPFS. IPFS addresses content by **CID** (a hash of the bytes), but a CID changes every time the content changes — so it's useless as a stable "pointer to my folder." That's what **IPNS** is for: - An **IPNS name** is derived from a keypair. An **IPNS record** says *"this name currently points to CID `Z`, at sequence number `N`,"* and it's **signed** by the owner's private key. - Anyone can verify that signature against the name (the public key). That's the proof the record genuinely came from the legitimate owner. - In CipherBox, the **server relays** publish/resolve (it's zero-knowledge — the client signs). The server *also* keeps a DB row tracking the latest CID + sequence per name. So a read works like: resolve the IPNS name → server returns `{cid, sequenceNumber, signature…}` → client fetches encrypted metadata at that CID → decrypts. **The trust model (this is the key sentence):** *"DB CID is authoritative; signature verification is defense-in-depth (Medium)."* In the normal case you trust the server's DB. The **whole reason to verify signatures at all** is to defend against a **compromised/malicious server, a MITM relay, or a bug** that hands back the *wrong* CID. The user's own signature is what catches that. If verification is sloppy, it gives false confidence — "security theater."
