## The background you need first

CipherBox stores your encrypted files on IPFS. IPFS addresses content by **CID** (a hash of the bytes), but a CID changes every time the content changes — so it's useless as a stable "pointer to my folder." That's what **IPNS** is for:

- An **IPNS name** is derived from a keypair. An **IPNS record** says *"this name currently points to CID `Z`, at sequence number `N`,"* and it's **signed** by the owner's private key.
- Anyone can verify that signature against the name (the public key). That's the proof the record genuinely came from the legitimate owner.
- In CipherBox, the **server relays** publish/resolve (it's zero-knowledge — the client signs). The server *also* keeps a DB row tracking the latest CID + sequence per name.

So a read works like: resolve the IPNS name → server returns `{cid, sequenceNumber, signature…}` → client fetches encrypted metadata at that CID → decrypts.

**The trust model (this is the key sentence):** *"DB CID is authoritative; signature verification is defense-in-depth (Medium)."* In the normal case you trust the server's DB. The **whole reason to verify signatures at all** is to defend against a **compromised/malicious server, a MITM relay, or a bug** that hands back the *wrong* CID. The user's own signature is what catches that. If verification is sloppy, it gives false confidence — "security theater."

With that, here are the four problems this phase fixes.

---

## Problem 1 — Verification only happens at 1 of ~9 places (a coverage hole)

The Rust desktop app (the FUSE mount) resolves IPNS names in ~9 different code paths: reading folder metadata, resolving a file pointer, reading recycle-bin metadata, doing a three-way merge on conflict, parent-folder merge, etc. **Only ONE of those paths checks the signature today** (the folder-key descent). The other ~8 just trust whatever CID the server returns.

So a tampering server could feed bad records to those 8 paths and the desktop app wouldn't notice. (The web/JS side already does this right — every resolve funnels through one function that verifies. Rust doesn't.)

**Fix:** make one wrapper, `resolve_ipns_verified`, that resolves *and* verifies together, and route all ~9 sites through it. Now every site verifies "by default."

**The option I asked you about** is the natural follow-up: *once every site verifies, what does a site DO when verification fails?*
- **Uniform fail-closed** — any failure → hard error, refuse to proceed, everywhere. Strongest, but one bad/edge record could wedge a folder read or a conflict-merge (i.e., break the mount).
- **Tiered (my rec)** — hard-fail only at the security-critical folder-key-descent site (it's the one already audited — a swapped *folder key* would let an attacker redirect your whole subtree). At the other read/merge sites: log a warning + emit a metric, but proceed using the DB-authoritative CID. You get full *coverage/visibility* without turning a "Medium" defense-in-depth check into an availability cliff.
- **Uniform allow-and-flag** — never hard-fail anywhere (even key-descent loses its current hard-fail). Maximum uptime, weakest enforcement — probably too soft.

---

## Problem 2 — The signature is checked, but not *what it covers* (the "swap gap")

This is the subtle, highest-value one. The signature proves *"the owner signed **a** record."* But the code today verifies the signature **without confirming the signed content matches the cid/sequence the server actually returned.**

Concretely: the signature covers a CBOR blob that says *"I point to CID `Z`, sequence `N`."* The server returns JSON `{cid:"Z", sequenceNumber:N, signature:…}`. Today the code checks the signature is valid for the name — but **never decodes the signed CBOR to confirm it actually says `Z` and `N`.** The client then uses the *top-level JSON* `cid`, which isn't bound to what was signed.

So a malicious server can take a **genuinely-signed** record (signed CBOR = "points to CID `OLD`") and return it with the JSON `cid` field swapped to a different value. Signature check passes (it's a real signature), but the CID the client fetches is **not the one that was signed.** That's the gap PR #529 explicitly left open.

**Fix:** decode the signed CBOR and compare its embedded cid/sequence to the response's cid/sequence. **The option:** when they *don't* match —
- **Hard tamper-fail (my rec)** — a mismatch means someone altered the response; that's an unambiguous tamper signal, so reject. (This is the case where "security theater vs. real security" lives — binding is what makes the signature actually mean something.)
- **Allow-and-flag** — log/flag but proceed on the DB CID. Softer, but a mismatch is hard to explain as anything *but* tampering, so flagging-only is weak here.

---

## Problem 3 — Publish-time sequence check has a hole when CAS is omitted (a "wedge" risk)

The **sequence number** is a version counter that prevents rollback/replay (you can't go from seq 10 back to seq 5). The server tracks the latest in its DB.

On publish, a client *can* pass `expectedSequenceNumber` — a compare-and-swap ("I expect current seq = N; reject otherwise"). When CAS is passed, the server validates the embedded sequence properly. **But several publish paths don't pass CAS** (file IPNS records, vault init, per-file). When CAS is omitted, the server accepts *any* embedded sequence.

The hole: a first publish without CAS could embed a **huge** sequence (say 999) in the signed record, while the server's DB stores "1." Now every future record must embed >999 to satisfy IPNS-level anti-rollback — but the client, following the DB ("you're at 1, sign 2"), signs 2, which is rejected as a rollback. **The name is wedged/bricked.** It's niche (the client has to deliberately sign a high first sequence), hence Low severity, but it's a real hardening gap.

**Fix:** validate the embedded sequence against the DB baseline *even without CAS* — but carefully, because this exact class of tightening **broke 48 of 89 E2E tests** before. **The option (the strictness dial):**
- **Strict DB+1** — enforce embedded === DB+1 (with first-publish 0/1 tolerance). Tightest, highest regression risk on the non-CAS paths.
- **Anti-rollback floor only (my rec)** — reject embedded < DB sequence, allow >=.
