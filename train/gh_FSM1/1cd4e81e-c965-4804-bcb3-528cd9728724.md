## Metadata-Embedded Sharing: Schema Impact

If `readers`/`writers` lived in the IPFS metadata, you'd be adding something like:

```typescript
// In FolderMetadata
readers?: Array<{
  pubKey: string;           // recipient secp256k1 pubkey
  encryptedFolderKey: string; // folderKey re-wrapped for this recipient
}>;
writers?: Array<{ ... }>;
```

...and similarly in `FileMetadata` with `encryptedFileKey`.

### Evolution Protocol Classification

**Additive (non-breaking)** — *if* done correctly:
- `readers?: Array<...>` is optional, defaults to `undefined` (omitted)
- Old clients ignore unknown fields, so they'd simply not see the ACL
- No version bump needed on FolderMetadata or FileMetadata
- Default of "no readers array = owner-only access" preserves existing behavior

So from a pure schema evolution standpoint, it's actually clean — optional field, sensible default.

### But the real costs are architectural, not schema-related

**1. Pervasive tree updates.** Sharing a folder means re-encrypting and re-publishing metadata for *every* node in the subtree — every subfolder, every file. A 100-file folder share = 100+ IPNS publishes.

**2. Revocation is illusory.** IPFS is immutable. Old CIDs with the old `encryptedFolderKey` persist forever. Revoking a reader means re-keying every file in the subtree (new folderKeys, new fileKeys, re-encrypt all content). The server-side approach just deletes a DB row.

**3. Metadata bloat.** Each reader adds ~130 bytes (65-byte pubkey + ~65-byte ECIES ciphertext). 10 readers on every node in a 1000-file vault = ~130KB of pure ACL overhead, re-published on every sync.

**4. Race conditions.** Two devices sharing the same folder with different recipients simultaneously — both read the current metadata, append their reader, publish. One write overwrites the other. The server-side approach handles this with database transactions.

### What the current approach trades away

The server-side `shares`/`share_keys` tables mean the server **knows the sharing graph** — who shared what with whom. It doesn't know *content*, but it knows relationships. Your original design would have hidden even that from the server.

That's the real trade-off: **privacy of the social graph** vs. **operational simplicity**.

### If you wanted to revisit this

The path would be:
1. Add `readers?` / `writers?` as optional fields (additive, no version bump)
2. Dual-platform implementation required (TypeScript + Rust per Section 4.3/4.4)
3. Recovery tool update needed (Section 7 — affects folder traversal / key discovery)
4. The hard part isn't the schema — it's the tree-wide re-keying on revocation and the concurrent-write conflict resolution
