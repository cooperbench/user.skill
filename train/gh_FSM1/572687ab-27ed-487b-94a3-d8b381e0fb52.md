how feasible is it to cover all the major mfa flows in the e2e testing? This would probably necessitate usage of wallet login, rather than bypassing auth using the test flags, but since this is quite easily achievable, that shouldn't stop any testing. since the e2e tests currently execute against their own databases, the userId provided to w3auth is unique each time the test suite is run, so we can use a consistent keypair for the tests, but individual runs will still result in different keys being generated by web3auth

> AGENT

This is quite feasible, and honestly a high-value addition. Here's my assessment based on the current state of things:

## What exists today

**Test infrastructure already supports the hard parts:**
- Mock wallet (`@johanneskares/wallet-mock`) does real ECDSA signing + real SIWE verification — TC09-TC12 prove this works
- Multi-account helpers (`createTestAccounts()`) create isolated browser contexts — exactly what cross-device simulation needs
- Device approval backend is fully implemented with comprehensive unit tests, but **zero E2E coverage**
- The test-login bypass is great for file operations but fundamentally can't test MFA because it skips Core Kit entirely

## MFA flows that are testable

| Flow | Feasibility | Notes |
|------|-------------|-------|
| Enable MFA (`enableMFA()`) | High | Real Core Kit call, captures recovery phrase, converts 2/2→2/3 |
| Device approval (request → poll → approve) | High | Two browser contexts, same user. Backend is solid. |
| Recovery phrase restore on new device | High | New context without device share, input mnemonic |
| MFA status detection in UI | High | `getKeyDetails()` reads threshold/factor count |
| Approval request expiration (5min TTL) | Medium | Needs time manipulation or patient waiting |
| Rate limiting on auth endpoints | Medium | Throttle decorators already in place |
| Factor key ECIES encryption correctness | Low | Better as unit/integration test |

## Why wallet login is the right approach

Your intuition is correct. The key insight is:

- **Consistent secp256k1 keypair** (from `privateKeyToAccount`) → same wallet address every run
- **Unique `userId`** per run (backend creates new user) → unique `verifierId` for Core Kit
- Core Kit maps `(verifier="cipherbox-identity", verifierId=userId)` → fresh DKG key shares each run
- So MFA state (threshold, device shares, recovery) is clean per test — no teardown needed

This means you can do the full lifecycle in one test:
1. Wallet login (context A) → Core Kit initializes with 2/2 default
2. `enableMFA()` → threshold becomes 2/3, device share in localStorage, recovery phrase captured
3. New browser context B (same wallet, same user, but no localStorage) → login triggers "new device" flow
4. Context A sees pending approval → approves with ECIES-encrypted factor key
5. Context B polls, gets factor, reconstructs key, reaches `/files`

## Practical concerns

**Network dependency** is the main risk. Every Core Kit operation hits Web3Auth's Sapphire Devnet nodes (key generation, share retrieval, `enableMFA`). This adds:
- ~5-15s latency per Core Kit operation
- Flakiness if devnet is slow/down
- A full MFA cycle test could take 30-60s

**Mitigations:**
- Tag MFA tests separately (`test.describe('mfa', ...)`) so they can run independently from fast smoke tests
- Use generous timeouts for Core Kit operations
- Retry policy for network transients (Playwright's `test.retry`)
- Run them in CI on a schedule rather than every PR, if speed matters

**The one thing to watch**: after `enableMFA()`, the `hashedShare` (cloud custodial factor) is deleted. If a test fails mid-flow, that user's Core Kit state on devnet is "MFA-enabled" with no way to reset. But since userId is unique per run, this is a non-issue — the next run gets a fresh user.

## What you'd need to build

1. **A wallet-login E2E helper** — similar to `loginViaTestEndpoint()` but driving the real wallet→SIWE→Core Kit flow. Most of the pieces exist in `LoginPage` and the mock wallet setup from `wallet-login.spec.ts`.

2. **Core Kit interaction helpers** — `page.evaluate()` wrappers to call `enableMFA()`, `getKeyDetails()`, `inputFactorKey()`, capture the recovery mnemonic from the UI.

3. **Cross-device test fixtures** — a pattern for "context A is existing device, context B is new device" using the multi-account infrastructure (but same user, different contexts).

4. **Device approval polling helper** — wait for pending request in context A, respond, verify context B unblocks.

## Bottom line

Highly feasible. The infrastructure is 80% there. The wallet mock + multi-context helpers handle the hard parts. The main investment is wiring up Core Kit interactions through `page.evaluate()` and building the cross-device test choreography. Network latency makes these slower tests, but they'd cover flows that are currently completely untested E2E — and these are exactly the flows most likely to break from subtle integration issues.
