This is useful context. Here's the picture:

## Current Bottleneck Profile

Each `uploadFile` today makes **3 Kubo pin calls** through the API (~1.37s each with pebbleds), totaling ~4-5s server-side. IPFS pinning is ~95% of upload endpoint time. The staging VPS plateaus at ~23-28 ops/s throughput and starts erroring at 200 concurrent clients.

## What Changes for BYO Users

For a **BYO+Kubo** user in external-only mode, the API call chain per upload drops from:

| Step | Current (CipherBox-only) | BYO+Kubo External |
|------|--------------------------|-------------------|
| 1. Pin ciphertext | POST /ipfs/upload (~1.37s) | **Eliminated** (direct to user's Kubo) |
| 2. Pin file metadata | POST /ipfs/upload (~1.37s) | **Eliminated** |
| 3. IPNS publish (file) | POST /ipns/publish-batch (~50ms) | Same (~50ms) |
| 4. Pin folder metadata | POST /ipfs/upload (~1.37s) | **Eliminated** |
| 5. IPNS publish (folder) | POST /ipns/publish (~50ms) | Same (~50ms) |
| 6. Register CID | N/A | POST /ipfs/register-cid (~5ms) |
| **Total API time** | **~4.2s** | **~105ms** |

That's roughly a **40x reduction** in per-upload API time for BYO+Kubo users. The three heaviest operations (Kubo pins) vanish entirely from CipherBox's perspective.

## Capacity Implications

If the current staging instance handles ~200 concurrent users doing uploads at ~4.2s API time each, and BYO+Kubo users consume only ~105ms of API time per upload, the theoretical capacity for BYO-only users on the same hardware is dramatically higher — possibly **2,000-4,000+** concurrent users, since:

- The Kubo node (the actual bottleneck) is no longer involved
- DB writes (IPNS upserts + CID registration) are cheap
- Redis/connection pool pressure is minimal for these lightweight calls

The real ceiling shifts from "Kubo pin throughput" to "PostgreSQL write throughput + API HTTP connection handling" — which is a much higher ceiling on a 4 vCPU / 8GB staging box.

## Mixed-Mode Complexity

The interesting benchmarking question is the **mixed workload**: what happens when you have, say, 150 CipherBox-only users + 500 BYO users simultaneously? The BYO users' lightweight API calls still compete for HTTP connections and DB pool slots with the heavy CipherBox-only upload pipeline. You'd want to benchmark:

1. **Pure BYO baseline** — how many BYO+Kubo users until the DB/API layer becomes the bottleneck?
2. **Mixed ratio sweep** — e.g., 200 CB-only + N BYO users, increase N until errors appear
3. **PSA vs Kubo BYO** — PSA external-only still uses CipherBox as transient relay, so it's nearly identical to the current load profile (slightly worse actually, since there's an extra unpin after PSA confirms)

## What I'd Suggest for Benchmarking

The existing load test harness in `tests/load/` already has the client pool and metrics infrastructure. You'd need:

**New scenarios:**
- `byo-upload-throughput` — N clients configured with external+Kubo mode, doing uploads that hit only register-cid + IPNS publish
- `mixed-byo-cipherbox` — ratio sweep of CipherBox-only vs BYO clients
- `byo-migration-load` — TEE migration jobs running alongside normal uploads (migration reads from one node, writes to another — puts load on TEE worker, not the API, but the DB tracking updates add some pressure)

**New metrics to capture:**
- Per-user-type latency breakdown (BYO vs CB-only)
- DB connection pool utilization under mixed load
- TEE worker queue depth during migrations

The hardest part is that BYO scenarios need an actual external Kubo node for the client to pin to. In CI, you'd need a second Kubo instance (or a mock) that the SDK talks to directly. Do you already have thoughts on how to handle that in the test environment, or should we mock the external node?

That makes a lot of sense. The whole value proposition is users pinning to real external infrastructure — testing against a mock Kubo would just be measuring localhost HTTP overhead, which tells you nothing about the actual user experience.

And it gives you two things a mock can't:

1. **Realistic SDK-side latency** — how long does a `KuboProvider.pin()` to Pinata actually take from the client? That's the latency the user _feels_, even though CipherBox's API barely notices.

2. **The PSA transient relay path under load** — does the "upload to CipherBox → PSA pinByCid → wait for pinned → unpin from CipherBox" chain hold up when 50 users do it simultaneously? That flow still hammers your Kubo node for the relay step, so it's the one path where BYO+PSA users _don't_ free up capacity.

The test matrix I'd think about:

| Scenario | Client path | CipherBox API load | External provider |
|----------|------------|-------------------|-------------------|
| BYO+Kubo external-only | SDK → Pinata Kubo endpoint | register-cid + IPNS only | Pinata (dedicated gateway) |
| BYO+PSA external-only | SDK → CipherBox relay → Pinata PSA | Full upload + unpin | Pinata PSA |
| Dual-pin + Kubo | SDK → CipherBox + Pinata | Full upload + register-cid | Pinata |
| Mixed (CB-only + BYO) | Both paths | Mixed | Pinata |

The practical concern is Pinata's rate limits on their end. Their free tier is 500 API requests/day which wouldn't survive a single load test run. A paid plan or a dedicated test account with higher limits would be needed. Worth checking if they have a developer/testing tier — or if you'd want to use Filebase as an alternative since they're more generous with CORS and have both PSA and S3 endpoints.

One thing worth separating: the **capacity benchmark** (how many BYO users can CipherBox handle?) can actually be done with a lightweight mock that just returns realistic CIDs with realistic latency. You don't need Pinata for that — you just need the CipherBox API calls to be realistic. But the **integration benchmark** (does the full BYO flow work end-to-end at scale?) absolutely needs a real provider. They answer different questions and I'd probably frame them as separate test scenarios in the harness.
