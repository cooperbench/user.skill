## TEE Worker Duplication Analysis

The TEE worker (`tee-worker/`) is ~1,410 lines across 14 source files. It reimplements several things that already exist in the shared packages:

### Direct Duplications

| TEE Worker Code | Shared Package Equivalent | Severity |
|---|---|---|
| `ipns-signer.ts` — IPNS record creation (60 LoC) | `@cipherbox/core` `createIpnsRecord()` — same libp2p conversion, same marshaling | **High** — identical logic, maintenance divergence risk |
| `key-manager.ts` — ECIES decrypt/encrypt (92 LoC) | `@cipherbox/crypto` `unwrapKey()` / `wrapKey()` / `reWrapKey()` | **High** — reimplements ECIES wrapping with its own `eciesjs` import |
| Kubo/PSA provider interaction in `migration-worker.ts` | `@cipherbox/sdk-core` already has `KuboProvider`, `PsaProvider`, `testConnection()` | **High** — completely parallel provider implementations |
| Connection test protocol detection (`connection-test.ts`, 244 LoC) | `sdk-core` `testConnection()` does the same Kubo→PSA probe | **Medium** — TEE version adds SSRF protection but duplicates protocol logic |
| `hexToBytes`/`bytesToHex` utility usage | `@cipherbox/crypto` exports these | **Low** — minor but unnecessary |

### What's Legitimately TEE-Specific

- **`tee-keys.ts`** — secp256k1 key derivation via HKDF or Phala dstack (TEE hardware). No equivalent needed elsewhere.
- **`ssrf-validation.ts`** — SSRF protection for user-provided URLs. TEE-specific security concern.
- **`decryptWithFallback()`** — epoch-aware decryption with grace period. Could be extracted but only TEE uses it today.
- **Express routes/middleware** — TEE-specific HTTP API surface.

### The Core Problem

The TEE worker has **zero dependencies on any `@cipherbox/*` package**. It vendors its own copies of `eciesjs`, `@noble/*`, `ipns`, `@libp2p/crypto`, and `multiformats` — all of which are already dependencies of `@cipherbox/crypto` and `@cipherbox/core`. This means:

1. **Bug fixes must be applied twice** (e.g., if IPNS record creation changes)
2. **Security patches in crypto libs** need updating in two places
3. **The provider protocol implementations can diverge** silently
4. **No shared types** — the TEE worker defines its own interfaces for everything

### Recommended Plan 0: TEE Worker Shared Package Integration

**Goal:** Make the TEE worker consume `@cipherbox/crypto`, `@cipherbox/core`, and `@cipherbox/sdk-core` instead of rolling its own.

1. **Add workspace dependencies** — `@cipherbox/crypto`, `@cipherbox/core`, `@cipherbox/sdk-core` to `tee-worker/package.json`
2. **Replace `ipns-signer.ts`** with calls to `@cipherbox/core`'s `createIpnsRecord()` (add configurable lifetime parameter)
3. **Replace ECIES operations** in `key-manager.ts` with `@cipherbox/crypto`'s `wrapKey()`/`unwrapKey()`/`reWrapKey()`
4. **Replace provider interactions** in `migration-worker.ts` with `@cipherbox/sdk-core`'s `KuboProvider`/`PsaProvider`
5. **Replace connection test** protocol detection with `sdk-core`'s `testConnection()`
6. **Keep TEE-specific code** — key derivation, SSRF validation, Express routes, epoch fallback logic
7. **Remove vendored crypto deps** — `eciesjs`, `@noble/*`, `ipns`, `@libp2p/crypto`, `multiformats`

This would cut the TEE worker by ~400+ lines and, more importantly, ensure a single source of truth for crypto and provider logic.

This confirms my thinking. Here's my honest assessment:

**NestJS for the TEE worker would be a net negative.** Here's why:

### The TEE worker has fundamentally different design goals than the API

The TEE worker runs inside a **Confidential Virtual Machine**. Its core value proposition is being a small, auditable, minimal attack surface that handles sensitive key material. NestJS would work against every one of those goals:

| Concern | Express (current) | NestJS |
|---------|-------------------|--------|
| **Dependencies** | ~5 runtime deps | ~30+ (reflect-metadata, rxjs, class-transformer, iterare, etc.) |
| **Docker image size** | Small | Significantly larger |
| **Cold start** | Milliseconds | Seconds (DI container init) |
| **Audit surface** | ~1,400 lines to review | Framework internals + decorators + DI |
| **Attack surface** | Minimal | Much larger supply chain |

For **5 routes and 1 middleware**, NestJS is a sledgehammer for a thumbtack.

### What the API actually shares that's reusable

The API's instrumentation is:
- `prom-client` for Prometheus metrics
- NestJS built-in Logger (`console.log` equivalent)
- An HTTP metrics interceptor (NestJS-specific decorator pattern)

None of this requires NestJS to reuse. The useful patterns are:
1. **`prom-client`** -- add directly to Express, ~30 lines for a metrics middleware
2. **Metric naming convention** (`cipherbox_*` prefix) -- just follow the same convention
3. **Republish batch histogram** -- the API already tracks `cipherbox_republish_batch_duration_seconds`; the TEE worker could emit the same metric name for Grafana correlation

### What I'd actually recommend instead

If you want better observability on the TEE worker without NestJS:

1. **Add `prom-client`** to the TEE worker (single dep, already used by API)
2. **Add a simple Express metrics middleware** (~30 lines) mirroring the API's `HttpMetricsInterceptor` patterns
3. **Add a `GET /metrics` route** so Prometheus can scrape the CVM
4. **Replace `console.log` with a tiny structured logger** (even just a 10-line wrapper that outputs JSON with timestamp/level/message)

This gives you the same observability as NestJS would, with zero framework overhead, and the metrics are compatible with the API's Grafana dashboards.
