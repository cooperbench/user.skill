### #1 — Critical, confirmed data-loss bug
In the file 409 conflict merge:
```ts
const winner = localWins ? updatedMetadata : remoteMeta;
const loser  = localWins ? remoteMeta : updatedMetadata;
...
const { versions: mergedVersions } = mergeVersions(
  [...(winner.versions ?? []), loserAsVersion],
  remoteMeta.versions,   // ← bug: should be loser.versions
  maxVersions,
);
```
`remoteMeta.versions` only equals the loser's history in the **local-wins** case. When **remote wins** (`localWins === false`), `loser` is the *local* metadata — so the second arg should be `loser.versions`. As written, the local writer's prior version history is silently dropped (only its *current* content survives as `loserAsVersion`). `mergeVersions` dedupes by CID, so passing `remoteMeta.versions` twice just re-merges remote's own list. One-line fix: `remoteMeta.versions` → `loser.versions` (symmetric, correct in both directions).

This is the exact data-loss class Phase 44 set out to prevent.

### #4 — The test that should have caught it
`file.test.ts:237` ("preserves local loser cid as VersionEntry when remote is newer") asserts only that the loser's *current* CID becomes a version — with empty local `versions`, so the dropped-history bug passes. CodeRabbit's suggested test (non-empty local history + remote wins) catches it.

### #2 / #3 — Lower impact than CR's "major"
`is409` is defined in `errors.ts` and imported **directly** from `'../errors'` by `file/index.ts` and `folder/index.ts`. No external package consumes it, so omitting it from `index.ts` breaks nothing today — it's a consistency gap vs the SUMMARY's "re-exports all three" claim, not a functional bug. `is409` is also indirectly exercised by every 409 conflict test, though it has no dedicated unit test.
