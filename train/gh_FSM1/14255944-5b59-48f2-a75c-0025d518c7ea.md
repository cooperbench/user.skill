Interesting idea. Let me think through the mechanics and the tradeoffs.

## The core concept

If I understand correctly: derive a deterministic IPNS address from the recipient's public key, use it as an "inbox" that sharers can publish to, with the content (share invitations + encrypted keys) readable only by the recipient via ECIES.

```
inbox_ipns_privkey = HKDF(recipient_pubkey, info="share-inbox")
inbox_ipns_name    = derive_public(inbox_ipns_privkey)
```

The recipient can always derive their own inbox address (they know their own public key), resolve the IPNS, and decrypt the invitations.

## What it solves

The main win over the current Phase 14 approach: **the server no longer knows the share graph**. Right now the `shares` table reveals who shared with whom, even though the keys are encrypted. With an IPNS inbox, share discovery is fully peer-to-peer — the API never sees the relationship.

## The problems I see

**1. Write conflicts (biggest issue).** Since the IPNS private key is derivable by anyone who knows the recipient's public key, *any* sharer can publish to the inbox. IPNS is last-writer-wins. If Alice and Bob both share with Charlie at roughly the same time, one overwrites the other's invitation. You'd need a read-modify-write pattern (resolve current inbox, append, republish), but there's no atomic CAS on IPNS — it's inherently racy.

**2. Spam / overwrite attacks.** Anyone who knows the recipient's public key (which is effectively public information in Web3Auth) can derive the inbox IPNS key and either spam it with junk or wipe it entirely. The recipient can't distinguish "inbox was wiped by attacker" from "I have no shares." The content is encrypted so they can't read it, but they can destroy it.

**3. Sender authentication.** The encrypted invitations need to be signed by the sharer, otherwise the recipient can't verify who sent each invitation. That's solvable (wrap each invitation in a sign-then-encrypt envelope) but adds protocol complexity.

**4. Revocation.** Currently revocation is a DB flag (`revoked_at`). With the inbox model, the sharer would need to update the inbox to remove the invitation — but the recipient may have already cached the decrypted keys. Revocation becomes eventual at best.

## A refinement: per-pair ECDH channels

Instead of one inbox per recipient, derive a per-pair channel:

```
shared_secret      = ECDH(sharer_privkey, recipient_pubkey)
channel_ipns_priv  = HKDF(shared_secret, info="share-channel")
```

Both parties can derive the same IPNS key (ECDH is symmetric). This solves the write-conflict and spam problems — only the sharer and recipient can write to the channel. But it kills discovery: the recipient would need to try ECDH with every known public key to find new channels, which requires a registry of public keys somewhere (i.e., the server again).

## The fundamental tension

CipherBox already leaks *that* a share exists (the share graph) but not *what* is shared (encrypted keys). The IPNS inbox approach trades that metadata leak for:
- IPNS reliability problems (we already fight 502s on resolve)
- Write-conflict complexity
- Loss of real-time discovery
- Harder revocation

For a technology demonstrator, I think the current centralized approach is the right call — it's the pragmatic tradeoff. But if you wanted to push the zero-knowledge boundary further, I'd suggest a **hybrid**: use the API for share *notification* only (a flag that says "you have new shares, check your inbox") and put the actual key material on the IPNS inbox. That way the server knows the graph but never touches key material at all — which is actually pretty close to what Phase 14 already does, just with the key storage moved off the DB.

The interesting question is what "solving IPNS" actually looks like. A few directions:

**CRDTs as the content model.** The write-conflict problem isn't really an IPNS problem — it's a data model problem. If the inbox (or folder metadata, or any shared state) is a conflict-free structure like a G-Set or OR-Set, then concurrent IPNS publishes don't conflict — they merge on read. Two sharers both append to the inbox, the reader merges both. That pattern applies equally to folder metadata conflicts you've already dealt with.

**Self-hosted IPNS resolution.** The 502s from delegated-ipfs.dev are a dependency risk, not a protocol limitation. Running your own IPNS resolution (even as a lightweight service alongside the API) gives you control over reliability without giving up the decentralized data model. The API becomes infrastructure, not a source of truth.

**Append-only DAG instead of mutable record.** Instead of IPNS pointing at a single CID that gets overwritten, point it at the head of a linked list. Each new share appends a node that references the previous head. Readers walk the chain. Writers only need to know the current head CID, not the full state. Race conditions produce forks, but since each node is self-contained and signed, readers can merge forks.

The CRDT angle feels like the most leverage to me — it turns the fundamental weakness (no coordination) into a feature (coordination-free merges). And it's the same solution pattern for folder metadata, share inboxes, and device registries.
