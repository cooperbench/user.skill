Brief's back. Here's the synthesis.

## SEED-001 verdict: concept is sound, prize is small

**Workload is barely-there.** TEE worker does one thing — signs IPNS records on a `0 */6 * * *` cron (4 runs/day). Healthy run is well under a minute; even a fully-degraded run caps ~10 min. Records carry a **48h EOL** but republish every 6h → **8× margin**. Effective duty cycle: **~4–10 active min/day out of 1440 (<1%)**. You're paying always-on to do <1% work, so the motivation is real.

**Key continuity — the make-or-break — is favorable.** The worker persists *no* private key; keys are deterministically derived per epoch via dstack `getKey()` bound to the CVM **app_id**. So:
- **`stop`/`start` preserves app_id → identical `teePublicKey` re-derives.** Safe.
- The landmine is **destroy+recreate into a *new* app_id** → every epoch's key changes → all previously ECIES-wrapped IPNS keys become **permanently undecryptable**. This is documented as a CRITICAL rule in `docker-compose.phala.yml`.
- Bonus: there's **zero attestation/quote verification anywhere in the repo** — clients just trust the `teePublicKey` the API serves. So quote-instability across boots is a non-issue *today*.

**Cold-start is irrelevant to the deadline.** Even a 20–25 min cold-start (large image) sits inside a 48h freshness window with ~47h of slack. Latency only matters because it lengthens the billable window and adds orchestration.

**Cost reality check.** Phala bills per-second, no monthly minimum (small $0.06/hr ≈ $43/mo, medium $0.12/hr ≈ $86/mo). A **stopped** CVM stops compute charges but **still bills storage** (~$0.10/GB/mo); only DELETE halts that. Net ~85–95% compute reduction — **but on one staging-sized CVM that's likely single-digit dollars/month.** And on-demand adds a real new failure surface: the republisher can now be *asleep* when needed (the DB backoff state machine + 48h margin make a missed wake degrade gracefully, but it's still new risk + orchestration the API doesn't have today).

## My recommendation

Sequenced by risk-adjusted value:

1. **Now, zero-risk: downsize the always-on CVM** if it isn't already `small`. Captures most of the dollars, no orchestration, no key risk.
2. **Two ~30-min spikes** before any build: (a) on a throwaway TDX CVM, derive `getKey()` → `stop`→`start` → re-derive, assert identical `teePublicKey`; (b) measure real `phala cvms start`→`/health`-ready time and whether `start` re-pulls.
3. **If spikes pass → Option A (stop/start same CVM)** behind the existing DB-backoff safety net. The API cron grows a start→poll-health→republish→stop sequence (and needs Phala API creds — none exist in CI today).
4. **Reject** destroy/recreate (key-bricking risk for ~$0.10/GB savings) and custom serverless/scale-to-zero (Phala has no first-party feature; not worth the surface at this scale).
