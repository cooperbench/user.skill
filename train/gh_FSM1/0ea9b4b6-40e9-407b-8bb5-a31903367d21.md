> AGENT

## Phase 13 File Versioning — Schema Change Analysis

### What Changed

An optional `versions: VersionEntry[]` array was added to `FileMetadata` in both TypeScript (`packages/crypto/src/file/types.ts`) and Rust (`apps/desktop/src-tauri/src/crypto/folder.rs`). Each `VersionEntry` holds full crypto context (cid, fileKeyEncrypted, fileIv, size, timestamp, encryptionMode) so each past version is independently decryptable.

### No Database Migrations Needed (Correct)

No DB migrations were created — and none were needed. The `versions` array lives entirely inside the client-encrypted `FileMetadata` blob stored in per-file IPNS records. The server never sees or indexes version data, consistent with the zero-knowledge architecture.

### Backward Compatibility — Handled Well

Both directions work correctly:

- **Old client reads new metadata**: The `versions` field is unknown and ignored by JSON parsing. TypeScript's optional typing (`versions?: VersionEntry[]`) and the validator's conditional check (lines 155-169 of `metadata.ts`) handle this gracefully.
- **New client reads old metadata**: Both TypeScript and Rust (`#[serde(default)]`) default missing `versions` to `None`/`undefined`. UI conditionally renders only when versions exist. Recovery tool checks `Array.isArray()` before processing.
- **Serialization cleanliness**: Rust uses `#[serde(skip_serializing_if = "Option::is_none")]` so metadata without versions doesn't emit `"versions": null`.

### Guidelines Followed

- Followed the `encryptionMode` precedent from the finalized specs: additive optional field, default to old behavior if missing
- Finalized spec docs correctly left untouched per CLAUDE.md rules
- No new API entities or endpoints needed (versioning is purely client-side)
- Encryption keys per-version (each version has its own `fileKeyEncrypted` and `fileIv`)
- MAX_VERSIONS_PER_FILE=10 cap addresses the metadata size concern flagged in research

### Potential Gaps

1. **`FileMetadata.version` not bumped** — It stays at `'v1'` despite the structural addition. Defensible since the field is additive/optional, but the `version` field becomes useless for feature detection. If a future change needs to know whether a client supports versioning, there's no metadata-level indicator.

2. **No formal metadata schema evolution protocol** — The frozen tech architecture docs provide no guidance on adding fields to encrypted metadata. The `encryptionMode` pattern (optional field + default) was followed implicitly but isn't documented as a reusable pattern anywhere.

3. **No "living" spec for current FileMetadata shape** — The finalized docs are frozen at v1.11.1 (2026-01-20) and Phase 13 completed 2026-02-19. The only source of truth for the actual current schema is the code itself.

### Verdict

The schema change was handled correctly for the immediate need — backward compatibility works in both directions, no unnecessary migrations, encryption isolation per version. The gaps are more about long-term schema governance (no version bump, no evolution protocol, no living spec) rather than functional correctness.

ok, and if I understand it correctly, the encrypted vault keys are stored for usage in the tee republishing service?

> AGENT

Not quite. The `EncryptedVaultKeys` are for the **user's own session recovery** — when you log in on a new session/device, you decrypt them with your secp256k1 private key (derived from Web3Auth) to recover your root folder key and root IPNS private key.

The TEE republishing service uses a **separate** set of encrypted IPNS keys — those are encrypted with the **TEE's public key** (not the user's), so the TEE enclave can decrypt them in hardware, sign fresh IPNS records, and immediately discard the plaintext. That's the `encryptedIpnsPrivateKey` field on the `folder_ipns` table rows, wrapped with `teePublicKey`.

In short:

| Encrypted Key | Encrypted To | Purpose |
|---|---|---|
| `EncryptedVaultKeys.encryptedIpnsPrivateKey` | User's secp256k1 pubkey | User recovers root IPNS key on login |
| `folder_ipns.encryptedIpnsPrivateKey` | TEE public key | TEE republishes IPNS records every 3h |

Two different wrappings of IPNS private keys, for two different consumers.

> DEVELOPER

but i thought that since this root ipns key was being deterministically derived, we could just get it that way?

> AGENT

You're right. The root IPNS key **is** deterministically derived via HKDF from the user's secp256k1 private key (salt `"CipherBox-v1"`, info `"cipherbox-vault-ipns-v1"`). So storing `encryptedIpnsPrivateKey` in `EncryptedVaultKeys` is technically redundant — you could just re-derive it on every login from the Web3Auth private key.

The field that actually **needs** to be stored is `encryptedRootFolderKey` — that's a randomly generated 32-byte AES key that can't be derived from anything. Without it, you lose access to your entire folder tree.

So `EncryptedVaultKeys` exists primarily for the root folder key. The IPNS private key is there as a historical artifact from before deterministic derivation was introduced (Phase 12.3.1 already removed `rootIpnsPublicKey` for the same "it's derivable" reasoning, but the private key was kept).

It could be cleaned up — but it's harmless redundancy and provides a small convenience (skip the HKDF derivation step on login). Not worth a breaking change to remove it.
