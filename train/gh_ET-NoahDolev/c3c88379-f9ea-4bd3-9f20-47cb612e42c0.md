# Investigation Report: Structured Fields / Mapping Panel Issues

## Executive Summary

The "modification panel" (structured fields editor) shows **raw text instead of grounded SNOMED/UMLS concepts**, has **missing relations and values**, and has **no OMOP relation integration**. After a thorough investigation of the frontend, backend, DB schema, pipeline code, and MLFlow tracing, I identified **5 root causes** spanning the full stack. The core problem is a **format mismatch** between what the AI pipeline produces and what the frontend expects, compounded by the grounding pipeline not enriching field_mappings with concept codes.

---

## Issues Reported

| # | Symptom | Severity |
|---|---------|----------|
| 1 | Failure to ground concepts with UMLS or SNOMED | High |
| 2 | Raw text instead of defined concepts | High |
| 3 | No relation or values in the modification panel | High |
| 4 | No OMOP relations visible | Medium |

## Root Cause Analysis

### ROOT CAUSE 1: Field Mapper Produces Flat Values, Frontend Expects Typed Objects

**Location:**
- Backend: `services/protocol-processor-service/src/protocol_processor/tools/field_mapper.py:120-132`
- Frontend: `apps/hitl-ui/src/components/CriterionCard.tsx:194-232`

**Problem:**

The Gemini-powered `field_mapper.py` produces field_mappings like:

```json
{
  "entity": "Abstinence duration",
  "relation": ">=",
  "value": "6",       // <-- FLAT STRING
  "unit": "months"    // <-- SEPARATE FIELD
}
```

But the frontend's `buildInitialValues()` (Priority 1 path, line 197-231) expects a **typed value object**:

```json
{
  "entity": "Abstinence duration",
  "relation": ">=",
  "value": {                        // <-- OBJECT with type discriminator
    "type": "standard",
    "value": "6",
    "unit": "months"
  }
}
```

When `buildInitialValues` reads the stored field_mappings, it checks `rawVal.type` (line 203). Since `value` is a flat string `"6"` (not an object), all three branches (`range`, `temporal`, `standard`) fail, and `value` defaults to `{ type: 'standard', value: '', unit: '' }` — **empty**.

**Impact:** All AI-generated field mappings lose their **value and unit** when displayed in the modification panel.

---

### ROOT CAUSE 2: Relation Operators Don't Match Frontend Enum

**Location:**
- Backend: `services/protocol-processor-service/src/protocol_processor/tools/field_mapper.py:106-107` (prompt instructs Gemini to use `<, >, >=, <=, =, has, is, within, not`)
- Frontend: `apps/hitl-ui/src/components/structured-editor/constants.ts:12-27` (accepts `=, !=, >, >=, <, <=, within, not_in_last, contains, not_contains`)

**Problem:**

The field mapper prompt tells Gemini to emit relations like `has`, `is`, `not`. But the frontend's `RelationOperator` type only accepts: `=`, `!=`, `>`, `>=`, `<`, `<=`, `within`, `not_in_last`, `contains`, `not_contains`.

When the backend produces `"relation": "has"` or `"relation": "is"`, the frontend casts it to `RelationOperator | ''` at line 200/227. Since `"has"` is not a valid `RelationOperator`, it falls through to an empty string `''`, meaning:

1. The RelationSelect dropdown shows "Select relation..." (empty)
2. The ValueInput is **conditionally hidden** (line 234: `{relationCategory && (...)}`) — if relation is empty, no value/unit inputs render at all

**Impact:** Entities with `has`/`is`/`not` relations show as **no relation selected** and **no value fields**.

---

### ROOT CAUSE 3: Entity Grounding Codes Not Propagated to Stored field_mappings

**Location:**
- Backend: `services/protocol-processor-service/src/protocol_processor/tools/field_mapper.py:120-131`
- Backend: `services/protocol-processor-service/src/protocol_processor/nodes/persist.py:162-174`

**Problem:**

The field_mapper does include `entity_concept_id`, `entity_concept_system`, and `omop_concept_id` in its output (lines 126-129). However, there are two failure modes:

1. **Grounding confidence < 0.5**: The agentic retry loop may fail after 3 attempts, leaving `entity.selected_code = None` and `entity.selected_system = None`. The field_mapper then produces `entity_concept_id: null` and `entity_concept_system: null`.

2. **field_mappings key naming mismatch**: The field_mapper stores `entity_concept_id` and `entity_concept_system`, but the frontend's `buildInitialValues` reads `entity_code` and `entity_system` (lines 225-226):
   ```typescript
   entity_code: fm.entity_code ? String(fm.entity_code) : undefined,
   entity_system: fm.entity_system ? String(fm.entity_system) : undefined,
   ```

   So even when grounding succeeds, the concept codes stored as `entity_concept_id`/`entity_concept_system` are **never read** by the frontend because it looks for `entity_code`/`entity_system`.

**Impact:** The green "SNOMED: 418633004" badge **never appears** for AI-generated mappings. Entities show as raw text only.

### ROOT CAUSE 4: OMOP Concept IDs Are Stored But Never Displayed

**Location:**
- Backend: `services/protocol-processor-service/src/protocol_processor/tools/field_mapper.py:128` (stores `omop_concept_id`)
- Frontend: `apps/hitl-ui/src/components/structured-editor/types.ts:41-47` (no `omop_concept_id` field)
- Frontend: `apps/hitl-ui/src/components/FieldMappingBadges.tsx` (no OMOP rendering)

**Problem:**

The field_mapper correctly stores `omop_concept_id` in each mapping dict. But:
1. The frontend `FieldMapping` TypeScript interface has no `omop_concept_id` field
2. `FieldMappingBadges` only renders `entity_code` + `entity_system` as a badge
3. There is no UI component that shows OMOP concept IDs or OMOP vocabulary relationships
4. The `AtomicCriterion` table has `omop_concept_id`, `unit_concept_id`, and `value_concept_id` columns, but these are **never served to the frontend** in the API response

**Impact:** OMOP concepts are invisible in the UI even when they exist in the database.

### ROOT CAUSE 5: buildInitialValues Priority 2 Path Has Entity-Threshold Index Mismatch

**Location:**
- Frontend: `apps/hitl-ui/src/components/CriterionCard.tsx:250-286`

**Problem:**

When there are no stored field_mappings (Priority 1 fails), the code falls back to Priority 2: inferring mappings from `criterion.entities` + `criterion.numeric_thresholds`. It matches entities to thresholds **by array index** (line 259):

```typescript
const matchedEntity = measurableEntities[i];
```

This assumes the i-th threshold corresponds to the i-th measurable entity (Lab_Value/Biomarker/Demographic). If the extraction pipeline produces 3 entities but only 1 threshold, or if entities and thresholds are in different orders, the match is wrong or missing.

Additionally, non-measurable entities (Condition, Medication, Procedure) at lines 288-303 are added with **empty relation and empty value** — they appear as raw text labels with no structured data.

**Impact:** Fallback mapping construction produces misaligned or empty mappings.

### The Problem Is Not the DB
The data in the DB is likely correct (grounding codes are persisted in Entity records and AtomicCriterion records). The problem is:
1. The `field_mappings` dicts stored in `criteria.conditions` use **different key names** than the frontend expects
2. The `field_mappings` value format is **flat** (string) not **typed** (object with type discriminator)
3. AtomicCriterion data (which has OMOP IDs) is **never included in the API response** for the review endpoint
