## Research Report: Parameterizing Generated (Non-Executed) SQL Strings

### 1. Is f-string interpolation in generated-but-not-executed SQL still a security risk?

**Short answer: Yes, it is a meaningful risk, though the severity is lower than direct execution. The risk is real enough to warrant mitigation.**

There are three distinct threat vectors to consider:

#### a) Second-Order / Deferred Execution Risk
The most concrete risk is exactly what you alluded to: the generated SQL is designed to be "ready-to-run" (the module docstring on line 63 says "SQL string ready for execution against an OMOP CDM v5.4 database"). This is textbook [second-order SQL injection](https://portswigger.net/kb/issues/00100210_sql-injection-second-order) -- data that is stored safely in one context is later used unsafely in another. When a user or downstream system copy-pastes and executes this SQL, any injected payload activates. As [PortSwigger notes](https://portswigger.net/kb/issues/00100210_sql-injection-second-order), second-order injection succeeds precisely because "the data is deemed to be safe, since it was previously placed into the database safely."

#### b) LLM Output as Untrusted Data
The values originate from LLM output. Research from [arXiv (2308.01990)](https://arxiv.org/pdf/2308.01990) and [arXiv (2503.05445)](https://arxiv.org/abs/2503.05445) demonstrates that LLM-based text-to-SQL systems can be manipulated to produce SQL injection payloads. The [OWASP LLM Top 10](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) explicitly states: "LLM-generated text should always be treated as untrusted data" and "apply the same security controls you'd use for untrusted user data." The fact that the values pass through a database first (SQLModel typed fields) provides some defense but is not sufficient on its own.

#### c) The Specific Code's Actual Risk Level
Looking at the actual interpolation points in `/Users/noahdolevelixir/Code/medgemma-hackathon/services/api-service/src/api_service/exporters/evaluation_sql_builder.py`:

- **Line 158**: `concept_id` -- This is already validated by `get_concept_id()` which forces `int()` conversion (lines 27-28 of `concept_utils.py`). An `int` cannot contain SQL injection payloads. **This interpolation is safe.**

- **Line 168**: `atomic.value_numeric` -- Typed as `float | None` in the SQLModel with `sa_column=Column(Float, nullable=True)`. Python `float` values cannot contain SQL injection characters. However, there are edge cases: `float('inf')`, `float('-inf')`, and `float('nan')` are valid Python floats that would produce invalid SQL (`inf`, `-inf`, `nan`). **This is safe from injection but could produce invalid SQL.**

- **Line 170**: `atomic.unit_concept_id` -- Typed as `int | None` with `sa_column=Column(Integer, nullable=True)`. An `int` cannot contain injection payloads. **This interpolation is safe.**

## Research Report: LangGraph State Management with Large Binary Data

### 1. Best Practices for Handling Large Binary Data in LangGraph State

**The LangGraph documentation does not provide explicit, dedicated guidance on handling large binary data (like PDF bytes) in graph state.** However, several patterns emerge from official sources and the architecture itself:

**Recommended pattern: External storage with reference keys.** The consistent recommendation from the LangGraph ecosystem is to **avoid storing large payloads directly in state**. Instead:
- Store the binary data in an external system (e.g., S3, a file store, or LangGraph's own `Store` interface).
- Keep only a reference key (like a URL, S3 key, or Store namespace/key) in the graph state.
- Fetch the data on demand in the node that needs it.

This is documented conceptually in the [LangGraph persistence documentation](https://docs.langchain.com/oss/python/langgraph/persistence), where the `Store` interface is described as a way to persist data that lives outside the checkpoint cycle. The Store supports `put()` with `index=False` to store data without embedding it, making it retrievable but not semantically searchable -- suitable for binary blobs.

**Example pattern:**
```python
class PipelineState(TypedDict):
    pdf_ref: str | None        # S3 key or Store namespace/key
    extracted_text: str | None
    # ... other fields

# In your ingestion node:
def ingest_pdf(state: PipelineState, *, store: BaseStore):
    # Store PDF bytes externally
    store.put(("pdfs", state["run_id"]), "raw", {"data": pdf_bytes}, index=False)
    return {"pdf_ref": f"pdfs/{state['run_id']}/raw"}

# In your extraction node:
def extract_text(state: PipelineState, *, store: BaseStore):
    item = store.get(("pdfs", state["run_id"]), "raw")
    pdf_bytes = item.value["data"]
    # ... process
```

Source: [LangGraph Persistence - Store Memories](https://docs.langchain.com/oss/python/langgraph/persistence)

---

### 2. Whether There Is a Way to Exclude Certain Fields from Checkpointing

**No. LangGraph does not provide a mechanism to exclude specific state fields from checkpointing.** There is no `exclude`, `transient`, or `@no_checkpoint` annotation available on TypedDict fields.

The checkpointing system operates at the **channel level**: every key in your `TypedDict` state corresponds to a channel, and every channel's value is serialized into the checkpoint. The `SerializerProtocol` (defaulting to `JsonPlusSerializer`) is applied uniformly to all channel values. There is no per-field opt-out.

However, the architecture does provide these related mechanisms:

- **Primitive inlining**: Values that are `None`, `str`, `int`, `float`, or `bool` are stored inline in the checkpoint JSONB column rather than in the separate `checkpoint_blobs` table. This means setting a field to `None` stores only a lightweight inline value rather than a blob.
- **Custom serializers**: You can implement a custom `SerializerProtocol`, but this applies to all channels uniformly -- it does not allow per-field exclusion.

Source: [LangGraph Checkpoint Serializer Protocol](https://docs.langchain.com/oss/python/langgraph/persistence), [PostgresSaver source](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/langgraph/checkpoint/postgres/__init__.py)

---

### 3. Whether Clearing a Field (Setting to None) Prevents Re-serialization in Subsequent Checkpoints

**Yes, this does help significantly -- but perhaps not in the way you might initially assume.**

The critical architectural detail comes from the [LangGraph v0.2 blog post](https://blog.langchain.com/langgraph-v0-2/):

> The Postgres checkpointer implements write-side optimization by **"storing each channel value separately and versioned so that each new checkpoint only stores the values that changed."**

Here is how it works in practice:

1. **Channel versioning**: Each channel has a version tracked in `channel_versions`. When a node updates a channel, the version is incremented (via `get_next_version()`). Only channels with new versions trigger a blob upsert.

2. **Blob deduplication**: The `checkpoint_blobs` table is keyed by `(channel, version)`. The PostgresSaver's `put()` method filters: `blob_versions = {k: v for k, v in new_versions.items() if k in blob_values}` -- only blobs whose versions changed are upserted.

3. **The None optimization**: When you set `pdf_bytes = None` in a node's return value, this triggers a version increment for that channel. The new version's blob entry stores `type="empty"` with `blob=NULL`. In all subsequent checkpoints (where `pdf_bytes` remains `None` and no node touches it), the channel version does not change, and **no new blob is written** for that channel.

**Practical impact for your scenario (10MB PDF, 6 nodes):**

| Strategy | Storage per run |
|---|---|
| Never clear `pdf_bytes` | ~10MB x 1 blob (due to dedup) + lightweight checkpoint references at each step |
| Clear after node 2 | ~10MB x 1 blob (version 1) + 1 NULL blob (version 2) + lightweight refs |

The key insight: **even without clearing, the Postgres checkpointer does not duplicate the 10MB blob at every node transition.** It stores the blob once at the version when it was written, and subsequent checkpoints reference that same version. Your "60MB for 6 nodes" concern is largely mitigated by the blob deduplication in the Postgres checkpointer.

However, clearing still has value because:
- It reduces the data that must be **deserialized** when loading a checkpoint (the blob is not fetched if `type="empty"`).
- It reduces memory pressure in the running graph process.
- If using `InMemorySaver` or `SqliteSaver` (which may not have the same deduplication), clearing is even more important.

Source: [LangGraph v0.2 Blog](https://blog.langchain.com/langgraph-v0-2/), [DeepWiki: Checkpointing Architecture](https://deepwiki.com/langchain-ai/langgraph/4.1-checkpointing), [PostgresSaver source on GitHub](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/langgraph/checkpoint/postgres/__init__.py)

---

### 4. Recommended Patterns for "Pass-Through" Data Needed Only Between Two Specific Nodes

LangGraph does not have a first-class "ephemeral channel" or "edge-scoped data" concept. All state fields persist across the full graph execution. However, several patterns address this need:

**Pattern A: Clear after consumption (simplest)**
```python
class State(TypedDict):
    pdf_bytes: bytes | None
    extracted_text: str | None

def extract_node(state: State):
    text = extract_text_from_pdf(state["pdf_bytes"])
    return {"pdf_bytes": None, "extracted_text": text}  # Clear after use
```
This is the most common pattern. After the consuming node processes the data, it returns `None` for that field. Subsequent checkpoints will store a lightweight `NULL` blob for that channel.

**Pattern B: External store (recommended for large data)**
```python
def ingest_node(state: State, *, store: BaseStore):
    store.put(("temp", state["thread_id"]), "pdf", {"bytes": pdf_bytes}, index=False)
    return {"pdf_available": True}

def extract_node(state: State, *, store: BaseStore):
    item = store.get(("temp", state["thread_id"]), "pdf")
    text = extract_text_from_pdf(item.value["bytes"])
    store.delete(("temp", state["thread_id"]), "pdf")  # Clean up
    return {"pdf_available": False, "extracted_text": text}
```
The binary data never enters the checkpoint cycle at all.

**Pattern C: Graph durability mode "exit"**
For pipelines where you only need the final result (no mid-run resumption), you can use `durability="exit"` mode, which writes a checkpoint only at the end of the run, omitting intermediate checkpoints entirely. This was mentioned in the [LangGraph checkpointing best practices](https://sparkco.ai/blog/mastering-langgraph-checkpointing-best-practices-for-2025) as a strategy to reduce checkpoint data volume.

**Pattern D: Subgraph isolation**
If the PDF processing is a self-contained pipeline within a larger graph, you can model it as a subgraph with its own state schema. The parent graph never sees `pdf_bytes`; only the subgraph's state includes it, and the subgraph returns only the extracted result.

   143→def _score_candidates(
   144→    entity_text: str, candidates: list[dict[str, Any]]
   145→) -> list[dict[str, Any]]:
   146→    """Score and sort candidates by fuzzy string similarity to *entity_text*.
   147→
   148→    Uses ``difflib.SequenceMatcher`` ratio as the base score, with a bonus
   149→    for exact case-insensitive substring containment.
   150→
   151→    Args:
   152→        entity_text: The original entity text to match against.
   153→        candidates: List of candidate dicts, each with at least a
   154→            ``"match_text"`` key containing the string to compare.
   155→
   156→    Returns:
   157→        The same candidate dicts augmented with a ``"score"`` key, sorted
   158→        in descending order of score.
   159→    """
   160→    entity_lower = entity_text.lower().strip()
   161→
   162→    for candidate in candidates:
   163→        match_text = candidate.get("match_text", "").lower().strip()
   164→
   165→        # Base score: SequenceMatcher ratio
   166→        base_score = SequenceMatcher(None, entity_lower, match_text).ratio()
   167→
   168→        # Bonus for exact substring containment (either direction)
   169→        bonus = 0.0
   170→        if entity_lower in match_text or match_text in entity_lower:
   171→            bonus = 0.15
   172→
   173→        # Bonus for exact match
   174→        if entity_lower == match_text:
   175→            bonus = 0.25
   176→
   177→        candidate["score"] = min(base_score + bonus, 1.0)
   178→
   179→    # Sort by score desc, then by length similarity (prefer match_text
   180→    # closest in length to entity_text) as tiebreaker.
   181→    entity_len = len(entity_lower)
   182→
   183→    def _sort_key(c: dict[str, Any]) -> tuple[float, int]:
   184→        match_len = len(c.get("match_text", "").strip())
   185→        return (c["score"], -abs(match_len - entity_len))
   186→
   187→    candidates.sort(key=_sort_key, reverse=True)
   188→    return candidates

   164→async def _ground_entity_with_retry(
   165→    entity: dict[str, Any],
   166→    router: TerminologyRouter,
   167→    criterion_text: str,

   169→    """Ground a single entity with agentic retry loop (max 3 attempts).
   170→
   171→    Implements the MedGemma agentic reasoning loop:
   172→    1. Initial grounding via TerminologyRouter + MedGemma
   173→    2. If low confidence, ask MedGemma 3 questions (valid? derived? rephrase?)
   174→    3. Retry with reformulated query (up to 2 more attempts, 3 total)
   175→    4. After 3 failed attempts, mark for expert_review
   176→

   178→        entity: Entity dict with text, entity_type, criterion_id.

   189→    candidates = await router.route_entity(entity_text, entity_type)

   200→            )

   203→                "Entity '%s' (type=%s) returned zero candidates from all APIs",
   204→                entity_text[:50],
   205→                entity_type,
   206→            )

   209→    result = await medgemma_decide(entity, candidates, criterion_text)

   217→        and attempt < 3

   221→        reasoning_result = await agentic_reasoning_loop(
   222→            entity={**entity, "_previous_query": current_query},

   247→            )

   254→        )

   256→
