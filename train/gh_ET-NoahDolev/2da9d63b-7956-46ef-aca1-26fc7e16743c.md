## 1. Overall Architecture

### System Identity

This is **ElixirTrials** — a mono-repo for an AI-powered clinical trial protocol processing system. The core mission: upload clinical trial protocol PDFs, extract inclusion/exclusion criteria using Gemini, ground extracted medical entities to standardized terminology (UMLS, SNOMED, RxNorm, ICD-10, LOINC, HPO) using MedGemma + ToolUniverse, and present results to human reviewers in a dashboard.

### Services and How They Connect

There are only **two backend services** (consolidated from a prior 3-service architecture):

**`services/api-service`** (FastAPI orchestrator)
- Entry point: `/services/api-service/src/api_service/main.py`
- Handles all REST API endpoints (protocols, criteria, entities, reviews, search, auth)
- Manages the PostgreSQL database via SQLModel/Alembic
- Runs an **outbox processor** background task that watches for `protocol_uploaded` events and dispatches them to the pipeline
- On startup: initializes DB, configures MLflow, registers the outbox handler `handle_protocol_uploaded` from the protocol-processor-service

**`services/protocol-processor-service`** (LangGraph pipeline — colocated, not a separate HTTP service)
- Entry point: `/services/protocol-processor-service/src/protocol_processor/main.py` (just exports `get_graph()`)
- Implements a **5-node LangGraph StateGraph** pipeline
- Imported directly by the API service (not a separate microservice over HTTP)
- Triggered by the outbox processor via `trigger.handle_protocol_uploaded()`

### Supporting Components

| Component | Location | Role |
|---|---|---|
| `apps/hitl-ui` | React/Vite frontend | HITL dashboard for reviewing extracted criteria and approving/rejecting entity groundings |
| `libs/shared` | `/libs/shared/src/shared/models.py` | SQLModel ORM models: `Protocol`, `CriteriaBatch`, `Criteria`, `Entity`, `Review`, `AuditLog`, `OutboxEvent`, `User` |
| `libs/inference` | `/libs/inference/` | LLM loaders, prompt factories, agent infrastructure (Jinja2 templates, lazy singletons) |
| `libs/events-py` | `/libs/events-py/` | `EventEnvelope`, `OutboxProcessor`, `persist_with_outbox()` — the transactional outbox pattern |
| `libs/data-pipeline` | `/libs/data-pipeline/` | ETL utilities |
| `libs/evaluation` | `/libs/evaluation/` | Offline benchmarks and metrics |
| `libs/model-training` | `/libs/model-training/` | LoRA fine-tuning, distillation |

### Data Flow Summary

```
Browser → POST /protocols/upload (API-service)
       → creates Protocol record in PostgreSQL
       → persists OutboxEvent(protocol_uploaded) atomically

OutboxProcessor (background task in API-service)
       → polls OutboxEvent table
       → calls handle_protocol_uploaded(payload) in thread executor

handle_protocol_uploaded()
       → generates unique thread_id = {protocol_id}:{uuid4}
       → stores thread_id in protocol.metadata_["pipeline_thread_id"]
       → invokes asyncio.run(_run_pipeline(graph, state, config, payload))

5-Node LangGraph Pipeline:
  ingest → extract → parse → ground → persist
       → updates protocol.status through: extracting → grounding → pending_review
       → protocol lands in pending_review when done

Browser/HITL UI → GET /protocols, GET /reviews/batches/{id}/criteria
              → Review and approve/reject criteria and entities
```

## 3. What is a "Protocol" and How It Gets Processed End-to-End

### What is a Protocol?

A **Protocol** is a clinical trial protocol PDF. It is the primary domain object. Each protocol has:
- A UUID `id`
- A `title` (derived from filename)
- A `file_uri` (GCS path `gs://...` or local path `local://...`)
- A `status` that progresses through a defined state machine
- Optional `quality_score`, `page_count`, `error_reason`, `metadata_` (JSONB)

**Protocol Status State Machine:**

```
uploaded
  → pending (if circuit breaker tripped)
  → extracting (ingest_node sets this)
  → grounding (parse_node sets this)
  → pending_review (persist_node sets on success) ← terminal success
  → extraction_failed (on ingest/extract/parse error)
  → grounding_failed (persist_node sets on total grounding failure)
  → dead_letter (after repeated failures)
  → archived (manual or lazy archival of dead-letter protocols)
  → complete (after human review is done)
```

### End-to-End Processing

**Step 1 — Upload (API endpoint):**
- `POST /protocols/upload` generates a signed GCS URL (or local URL in dev), creates a `Protocol` record in the DB, and atomically persists a `OutboxEvent` with `event_type=protocol_uploaded` using `persist_with_outbox()`.
- `POST /protocols/{id}/confirm-upload` optionally computes PDF quality score (text extractability, page count) from base64-encoded PDF bytes.

**Step 2 — Outbox Trigger:**
- The `OutboxProcessor` background task polls the `outboxevent` table for pending events.
- On finding a `protocol_uploaded` event, it calls `handle_protocol_uploaded(payload)` in a thread executor.

**Step 3 — 5-Node LangGraph Pipeline** (`services/protocol-processor-service/src/protocol_processor/`):

The graph definition is in `/services/protocol-processor-service/src/protocol_processor/graph.py`. State is defined by `PipelineState` (TypedDict) in `state.py`. The graph uses a **PostgresSaver** checkpointer for fault-tolerant retry.

**Node 1 — `ingest_node`** (`nodes/ingest.py`):
- Fetches PDF bytes from GCS or local filesystem via `fetch_pdf_bytes(file_uri)`
- Updates protocol status to `"extracting"` in DB
- Returns `{"pdf_bytes": ..., "status": "processing"}`

**Node 2 — `extract_node`** (`nodes/extract.py`):
- Calls `extract_criteria_structured(pdf_bytes, protocol_id, title)` in `tools/gemini_extractor.py`
- Uploads PDF to Gemini File API; calls Gemini with structured output using `ExtractionResult` schema
- Returns extraction as a JSON string `extraction_json`

**Node 3 — `parse_node`** (`nodes/parse.py`):
- Parses `extraction_json` into `ExtractionResult` Pydantic model
- Creates `CriteriaBatch` and `Criteria` DB records
- Concurrently decomposes each criterion's text into discrete medical entities via `decompose_entities_from_criterion()` (another Gemini call)
- Updates protocol status to `"grounding"`
- Returns `{"batch_id": ..., "entities_json": ..., "pdf_bytes": None}` (clears PDF bytes from state)

**Node 4 — `ground_node`** (`nodes/ground.py`):
- Skips `Consent` entity types explicitly
- Routes all other entities in parallel (up to 4 concurrent) via `TerminologyRouter`
- `TerminologyRouter` reads `config/routing.yaml` to map entity type → terminology APIs:
  - `Medication` → RxNorm, UMLS
  - `Condition` → ICD-10, SNOMED, UMLS
  - `Lab_Value` → LOINC, UMLS
  - `Biomarker` → HPO, UMLS
  - `Procedure` → UMLS, SNOMED
  - `Phenotype` → HPO, UMLS
  - `Demographic` → UMLS, SNOMED
- All terminology APIs are accessed via the **ToolUniverse SDK** (`tools/tooluniverse_client.py`)
- `medgemma_decide()` uses MedGemma (via `langchain_google_genai`) to select the best candidate from terminology results
- **Agentic retry loop**: up to 3 attempts per entity; if low confidence, MedGemma reformulates the query
- After 3 failed attempts, entity is marked for `expert_review`
- Writes grounding decisions to `AuditLog`
- Error accumulation: individual failures don't abort the pipeline
- Returns `{"grounded_entities_json": ..., "errors": [...]}`

**Node 5 — `persist_node`** (`nodes/persist.py`):
- Creates `Entity` DB records for each grounded result
- Maps `selected_system` → correct Entity code field (`umls_cui`, `snomed_code`, `rxnorm_code`, etc.)
- Updates `Criteria.conditions` JSONB with `field_mappings`
- Sets `CriteriaBatch.status = "entities_grounded"`
- Sets `Protocol.status`:
  - `"pending_review"` if any entities succeeded (partial success is OK)
  - `"grounding_failed"` if ALL entities failed
- Writes a `protocol_status_change` `AuditLog` entry
- Applies **review inheritance** if this was a re-extraction (fuzzy matches prior human reviews to new criteria)

**Retry / Re-extraction:**
- `POST /protocols/{id}/retry`: resumes from the last LangGraph PostgresSaver checkpoint (reads `pipeline_thread_id` from `protocol.metadata_`)
- `POST /protocols/{id}/re-extract`: archives existing batches (preserving reviewed criteria for inheritance), then fires a new `protocol_uploaded` outbox event triggering the full pipeline again

## 4. MLflow Integration

MLflow is deeply integrated throughout the system for tracing and observability. MLflow version: `3.9.0` (Docker image); `3.8.1+` in Python deps.

**MLflow Server:**
- Runs as a Docker container: `ghcr.io/mlflow/mlflow:v3.9.0`
- Default port: `5001` (host) → `5000` (container)
- Backend store: `sqlite:///mlflow/mlflow.db` (inside container volume)
- Artifacts: `/mlflow/artifacts`

**API Service Integration** (`services/api-service/src/api_service/main.py`):
- On startup: sets `mlflow.set_tracking_uri(tracking_uri)`, `mlflow.set_experiment("protocol-processing")`, enables `mlflow.langchain.autolog()`
- `MLflowRequestMiddleware` (`middleware.py`): pure ASGI middleware (avoids BaseHTTPMiddleware thread issues) that wraps every HTTP request in an MLflow span with method, path, status code, and latency

**Pipeline Tracing** (`services/protocol-processor-service/src/protocol_processor/`):

- `trigger.py` wraps the entire pipeline in an `mlflow.start_span("protocol_pipeline", span_type="CHAIN")` span capturing inputs (protocol_id, title, file_uri) and outputs (status, errors). On pipeline failure, it force-closes the trace as `ERROR` via `MlflowClient().end_trace()`.
- Each of the 5 nodes uses the `pipeline_span(name, span_type)` context manager from `tracing.py` to create child spans:
  - `ingest_node` → CHAIN span
  - `extract_node` → LLM span
  - `parse_node` → CHAIN span
  - `ground_node` → TOOL span
  - `persist_node` → CHAIN span

**`tracing.py`** provides a graceful no-op fallback `_NoOpSpan` when MLflow is not configured (e.g., in unit tests), so all node code is MLflow-safe regardless of configuration.

**Orphan Trace Cleanup** (`trigger.py`):
- On module import (service startup), `_cleanup_orphan_traces()` searches for `IN_PROGRESS` traces older than 1 hour and closes them as `ERROR`. This handles crash recovery from prior runs.

**MLflow Management:**
```bash
make mlflow-clear       # Delete all MLflow runs/traces
                        # → runs scripts/clear_mlflow_traces.py
```

**Known Limitation:**
MLflow ContextVars don't propagate across `asyncio.create_task()` / `asyncio.gather()` boundaries. The current `_run_pipeline()` initializes MLflow inside the `asyncio.run()` context (not before it) to ensure ContextVars are bound to the correct event loop. LangGraph node `await` calls preserve context; parallel tasks via `asyncio.gather()` in the ground node may detach child spans.
