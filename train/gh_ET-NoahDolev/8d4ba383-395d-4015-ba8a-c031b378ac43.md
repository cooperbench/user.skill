## Root Cause Analysis

There are **two distinct bugs** conspiring to hide traces.

### Bug 1 (Primary): Experiment name mismatch — traces land in the wrong experiment

`main.py` lifespan configures MLflow **once at startup**:
```python
mlflow.set_experiment("protocol-processing")   # fixed name
```

But `trigger._run_pipeline()` calls `_ensure_mlflow()` inside **every** `asyncio.run()` invocation, which calls:
```python
mlflow.set_experiment(f"protocol-processing-{ts}")  # different, timestamped name
```

Because `mlflow.set_experiment()` mutates **global** process-wide state (not ContextVar-based), this permanently overrides the active experiment for the entire process after the first pipeline invocation. All subsequent `mlflow.start_span()` calls — including from `MLflowRequestMiddleware` — log to `"protocol-processing-20260224-XXXXXX"`, not to `"protocol-processing"`. If you look in the MLflow UI under `"protocol-processing"`, you'll find nothing.

### Bug 2 (Secondary): `asyncio.run()` event-loop isolation — `AsyncPostgresSaver` bound to stale event loop

`graph.py` stores the graph and checkpointer as **module-level singletons** (`_graph`, `_checkpointer`). On the first call, `get_graph()` creates an `AsyncPostgresSaver` via `__aenter__()` inside the first `asyncio.run()`. When `asyncio.run()` exits it **closes** that event loop. On subsequent pipeline invocations, `asyncio.run()` creates a *new* event loop, but the singleton `AsyncPostgresSaver` still holds connections bound to the now-closed first loop. This causes silent errors in Postgres checkpointing that can abort node execution — which would also prevent spans from being flushed.

### Why the logs appear but traces don't

The console logs (`INFO:protocol_processor.nodes.ground`) are emitted by Python's standard logger — completely independent of MLflow. The pipeline *does* run and ground entities; it's just that the resulting MLflow spans are being written to a timestamped experiment the user hasn't looked at, or are silently dropped due to Bug 2.

---

**Fix 1 — Remove `_ensure_mlflow()` from `_run_pipeline()`**

MLflow is already fully configured in `main.py` lifespan. `_ensure_mlflow()` inside the pipeline is redundant AND harmful because it creates a conflicting experiment. Remove it from `_run_pipeline()`:

# trigger.py — _run_pipeline()

class _EnvironmentVariable:
    """
    Represents an environment variable.
    """

    def __init__(self, name, type_, default):
        if type_ == bool and not isinstance(self, _BooleanEnvironmentVariable):
            raise ValueError("Use _BooleanEnvironmentVariable instead for boolean variables")
        self.name = name
        self.type = type_
        self.default = default

    @property
    def defined(self):
        return self.name in os.environ

    def get_raw(self):
        return os.getenv(self.name)

    def set(self, value):
        os.environ[self.name] = str(value)

    def unset(self):
        os.environ.pop(self.name, None)

    def is_set(self):
        return self.name in os.environ

    def get(self):
        """
        Reads the value of the environment variable if it exists and converts it to the desired
        type. Otherwise, returns the default value.

        if (val := self.get_raw()) is not None:

                return self.type(val)

                raise ValueError(f"Failed to convert {val!r} for {self.name}: {e}")

    def __format__(self, format_spec: str) -> str:

def start_span(
    name: str = "span",
    span_type: str | None = SpanType.UNKNOWN,
    attributes: dict[str, Any] | None = None,
    trace_destination: TraceLocationBase | None = None,
) -> Generator[LiveSpan, None, None]:
    """
    Context manager to create a new span and start it as the current span in the context.

    This context manager automatically manages the span lifecycle and parent-child relationships.
    The span will be ended when the context manager exits. Any exception raised within the
    context manager will set the span status to ``ERROR``, and detailed information such as
    exception message and stacktrace will be recorded to the ``attributes`` field of the span.
    New spans can be created within the context manager, then they will be assigned as child
    spans.

    .. code-block:: python
        :test:

        import mlflow

        with mlflow.start_span("my_span") as span:
            x = 1
            y = 2
            span.set_inputs({"x": x, "y": y})

            z = x + y

            span.set_outputs(z)
            span.set_attribute("key", "value")
            # do something

    When this context manager is used in the top-level scope, i.e. not within another span context,
    the span will be treated as a root span. The root span doesn't have a parent reference and
    **the entire trace will be logged when the root span is ended**.


    .. tip::

        If you want more explicit control over the trace lifecycle, you can use
        the `mlflow.start_span_no_context()` API. It provides lower
        level to start spans and control the parent-child relationships explicitly.
        However, it is generally recommended to use this context manager as long as it satisfies
        your requirements, because it requires less boilerplate code and is less error-prone.

    .. note::

        The context manager doesn't propagate the span context across threads by default. see
        `Multi Threading <https://mlflow.org/docs/latest/tracing/api/manual-instrumentation#multi-threading>`_
        for how to propagate the span context across threads.

    Args:
        name: The name of the span.
        span_type: The type of the span. Can be either a string or
            a :py:class:`SpanType <mlflow.entities.SpanType>` enum value

        self._display_handler = get_display_handler()

        # A flag to cache the failure of exporting spans so that the client will not try to export
        # spans again and trigger excessive server side errors. Default to True (optimistically
        # assume the store supports span-level logging).
        self._should_export_spans_incrementally = True

    def export(self, spans: Sequence[ReadableSpan]) -> None:
        """
        Export the spans to the destination.

        Args:
            spans: A sequence of OpenTelemetry ReadableSpan objects passed from
                a span processor. All spans (root and non-root) are exported.
        """

        if self._should_export_spans_incrementally:
            self._export_spans_incrementally(spans)

        self._export_traces(spans)

    def _export_spans_incrementally(self, spans: Sequence[ReadableSpan]) -> None:
        """
        Export spans incrementally as they complete.

        Args:
            spans: Sequence of ReadableSpan objects to export.
            manager: The trace manager instance.
        """
        if is_databricks_uri(self._client.tracking_uri):
            _logger.debug(
                "Databricks tracking server only supports logging spans to UC table, "
                "skipping span exporting."
            )
            return

                self._async_queue.put(
                    task=Task(
                        handler=self._log_spans,
                        args=(experiment_id, spans_to_log),
                        error_msg="Failed to log spans to the trace server.",
                    )
                )
            else:

        self, spans: Sequence[ReadableSpan]

            if mlflow_span := manager.get_span_from_id(mlflow_trace_id, span_id):

## Corrected Root Cause Analysis

### The actual problem: `_ensure_mlflow()` runs **after** the TracerProvider is already initialized

In MLflow 3.x, the `TracerProvider` is initialized **once** (via `do_once`) on the **first call to `mlflow.start_span()`**. That first call happens in `MLflowRequestMiddleware` — for the very first HTTP request the server handles, before any pipeline has run.

When the TracerProvider is initialized by the middleware, it calls `_get_span_processors()` which creates a `MlflowV3SpanExporter`. The exporter stores the `tracking_uri` at creation time. Crucially, the **active experiment** is determined lazily at span-start time via `_get_experiment_id()`, not at TracerProvider creation time. This part is fine.

**But the real bug is this:** `pipeline_span()` in `tracing.py` calls `mlflow.start_span()` which (for root spans) determines the experiment by calling `_get_experiment_id()` → reads `_active_experiment_id` (global). The `_active_experiment_id` was set by `_ensure_mlflow()` to the timestamped experiment just before `graph.ainvoke()`.

**So the traces DO go to the timestamped experiment. They are "ingest_node", "extract_node", "parse_node", "ground_node" etc. — not labeled "extraction trace" or "grounding trace".**

What you're seeing in the MLflow UI:
- **"api calls"** = HTTP request traces from `MLflowRequestMiddleware` that ran AFTER `_ensure_mlflow()` changed `_active_experiment_id` globally (now ALL spans go to the timestamped experiment)
- **"protocol_id"** = the `protocol_id` tag on the pipeline node traces (`mlflow.update_current_trace(tags={"protocol_id": ...})`), visible in the trace list's tag column
- **"no traces"** = the pipeline node traces ARE there but named `ground_node`, `extract_node`, `parse_node` — not recognizable as "grounding/extraction traces" without knowing to look for those span names

Remove `_ensure_mlflow()` from `_run_pipeline()` entirely — it's already done at startup in `main.py`. This eliminates the split between the "protocol-processing" startup experiment and the per-process-launch timestamped one. Everything lands in one consistent "protocol-processing" experiment.
