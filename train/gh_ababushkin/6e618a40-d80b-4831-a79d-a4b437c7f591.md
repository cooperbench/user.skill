## Problem

The contract + worked file-set from <issue id="baa17af9-84fe-4edc-b366-b87248fea8b6">ABA-281</issue> use a **four-level** hierarchy: deliverable → capability → node → task, with `capability → label-class`. Two things are wrong with that:

* A label is **stateless** (name + colour, no done-state, no target), yet each `_capability.md` asserts a `completion.form: the-capability-spec` with a real criterion — a stateful claim mapped onto an artefact that can't hold or check it.
* It's **asymmetric**: deliverables also carry a completion criterion and get a milestone (stateful, descriptive); capabilities — same kind of object — get only a tag.

Root cause: four plan layers squeezed into a tracker's three *stateful* nesting levels (milestone / issue / sub-issue) + stateless labels. The squeeze landed at the capability layer.

## Decision (confirmed)

Collapse to **three levels** — deliverable → node → task — and make `capability` a **polymorphic node *type*** (a peer of `story`/`spike`/`adr`/…), completion form `the-capability-spec`. A capability-node is just a spec-shaped node broken into task-slices.

Result: layers map 1:1 to **milestone / issue / sub-issue**. No structural label layer (labels stay available for *orthogonal* tagging — theme/area — just not for the hierarchy). The squeeze disappears; so does the stateless-label type mismatch.

This tightens the polymorphic-node thesis the contract already argues, rather than fighting it.

## Scope of change

**Contract —** `docs/delivery-shape-contract.md`

* "Four layers" table → three layers (deliverable / node / task); drop `label-class` as a structural mapping.

172	## Constraints on the contract
173	
174	- **Grounded story form only.** A `story` node uses a recognised template — Cohn
175	  ("As a [role], I want [capability], so that [benefit]") or a job story
176	  ("When [situation], I want to [motivation], so I can [outcome]"). A custom "so… so…" chain is
177	  not permitted: it hides the role and the benefit, the two things acceptance criteria are checked
178	  against. See `N02`/`N04`/`N05`/`N06`/`N08` for the Cohn form in use.
179	- **External windows, never effort-in-days.** The optional `external_window` field carries *only*
180	  genuine external constraints — a deprecation notice period, a legal or compliance deadline, a
181	  canary soak time, an embargo. It must **never** carry an effort or duration estimate in
182	  days/weeks (agentic P8: effort is measured in slices and gates, not calendar time). Every node in
183	  the worked example is `external_window: none` because this initiative has no external constraint;
184	  the appendix types (`deprecation`, `compliance`, `slo` soak) are where the field goes non-`none`.
185	  Sizing lives in the **appetite** (issue count = node count) and in **task granularity**, not in a
186	  per-node time field.
187	- **Tool-agnostic templates.** This contract and any template it ships name no tracker, language, or
188	  runtime. An emitted plan (the example) may name concrete tools in its prose and in `maps_to`
189	  values; the contract describes only the artefact classes those tools implement.
190	- **Select and delegate; never re-author.** `delivery-shape` picks the node `type` and points
191	  `delegates_to` at the owning rule/skill. The discipline of each type lives at its source. If a
192	  node's completion criterion starts duplicating Rule C5 or the ADR template inline, that is drift —
193	  link instead.

197	## Walkability contract (what a deterministic reader may rely on)
198	
199	This is the half of the kill condition the gate issue tests with an actual walk-script. A reader
200	may assume, without parsing prose:
201	
202	1. **Layers are directory depth.** `D*/` = deliverable, `D*/C*/` = capability, `D*/C*/N*.md` = node.
203	2. **Front-matter is the source of structured truth.** Every layer file opens with a `---` YAML
204	   block carrying at least `layer`, `id`, and (for nodes) `type` + `completion.form`.
205	3. **The manifest is countable.** milestones = `D*` directories; issues = `N*.md` files;
206	   sub-issues = `- [ ]`/`- [x]` lines inside node files; labels = `C*` directories.
207	4. **The oracle is the README.** The derived manifest is correct iff its counts equal the
208	   hand-count manifest in the root README; a mismatch means drift or a non-deterministic layout.
209	
210	If a reader cannot satisfy 1–4 mechanically, the standalone-markdown premise has failed and the
211	seam must be re-shaped before the skill is built (the initiative kill condition).

213	## Design notes / alternatives considered
214	
215	- **File-per-node vs section-per-node.** Chosen: one file per node, structure carried by directory
216	  depth + front-matter. Rejected: nodes as `##` sections inside a capability file with fenced
217	  metadata blocks — fewer files, but it forces the reader to parse headings and extract fenced
218	  blocks, which is more fragile than reading front-matter from a known file path. If a future
219	  walk-script finds front-matter parsing insufficient, section-per-node is the documented fallback —
220	  but the burden is on showing front-matter failed first.
221	- **Derived vs hand-maintained manifest.** Chosen: derive the manifest from structure; keep only a
222	  hand-count *oracle* in the README. Rejected: a checked-in manifest file enumerating every
223	  milestone/issue/sub-issue — a second source of truth that drifts from the files it indexes.
224	- **Capability → label vs parent-issue.** Chosen: label-class, so the tracker manifest stays a clean
225	  three-count (milestones / issues / sub-issues) and capabilities are a grouping tag, not a counted
226	  artefact. An adapter that prefers parent-issues can still map the same `C*` directory.
