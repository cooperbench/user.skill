40	# Prototype to validate
41	
42	## Purpose
43	
44	A prototype-to-validate is a throwaway artefact built to answer one specific question before engineering time is committed to a design. The question is always a product question — how the feature will feel, whether users will understand an interaction, whether a proposed flow creates or removes confusion. Technical unknowns belong in a spike (Rule C5). The output is a written finding, not a deliverable artefact.
45	
46	This skill sits between `idea-triage` and `design-doc`. Idea-triage confirms a problem is real and worth pursuing. That is not enough to know how to solve it. When the gap between "this is worth building" and "this is how we'll build it" is a product question, a prototype answers it cheaply. A design-doc started from an unclear product direction will be redesigned; a prototype started from an unclear product direction will be thrown away. Throwaways are cheaper.
47	
48	The risk this skill guards against is the prototype that becomes an implementation. A prototype built with production-quality code, extended beyond its original question, and shipped to users has become a real release — without tests, without a design review, without operability planning. Prototypes must be throwaway by policy: the question is the constraint, the code is the instrument, the finding is the output.
49	
50	## When to use
51	
52	- An idea has cleared idea-triage and the dominant remaining unknown is product feel — how the interaction works, whether the flow makes sense, what the experience is like for a user.
53	- A design-doc has stalled because the team disagrees about which approach will feel right and opinion-level argument is not resolving it.
54	- Before committing to a design-doc for a significant UX-touching change where intuition about user response is low.
55	
56	## When not to use
57	
58	- **The dominant unknown is technical** — run a spike instead. Spikes answer: can we do this, at what cost, with what constraints? Prototypes answer: does this feel right, will users understand this?
59	- **The idea hasn't been triaged** — run `idea-triage` first. A prototype is not a substitute for problem validation; it is a tool for solution exploration after the problem is confirmed.
60	- **The interaction is known and the task is to design the system** — go directly to `design-doc`. Prototype-to-validate is discovery work; design-doc is commitment work.
61	- **Multiple questions need answering** — triage the questions first. One prototype answers one question. Run prototypes sequentially, not simultaneously.
62	
63	## Inputs
64	
65	- An idea-triage output: validated hypothesis, ICE score, confidence rating.
66	- A single, specific question the prototype will answer (one sentence, written before building begins).
67	- A time box (set before the prototype begins; not extended after starting).
68	
69	## Outputs
70	
71	A written finding at `docs/prototypes/<slug>/finding.md`. The finding contains: the question, the prototype approach, the observations, and a recommendation: proceed / reshape / kill. The prototype code, if any, is either deleted or explicitly marked non-production in the finding.
72	
73	## Workflow
74	
75	**1. Write the question.**
76	Before building anything, write the question in one sentence. The question must be specific (one thing, not a cluster), answerable by observation, and bounded (there is a signal that means "yes" or "no"). If the question cannot be written in one sentence, it is not well-defined. Resolve it first.
77	
78	Good questions:
79	- "Will a user who has not seen this flow understand that step 2 must complete before step 3 unlocks?"
80	- "Does inline editing feel faster than a modal for this data type, based on a walkthrough with one internal user?"
81	- "Is the proposed navigation structure legible — does a new user land in the right section?"
82	
83	Questions too vague to drive a prototype:
84	- "How should the onboarding flow work?" — a design brief, not a question
85	- "Will users like this?" — not specific enough to be answerable
86	- "Is this the right approach?" — too broad; which aspect of the approach?
87	
88	**2. Set the time box and the kill condition.**
89	Name both before writing a line. Default appetite: 1–3 build-observe iterations on the single question. Each iteration is a slice (build → put it in front of an observer → record what was seen). Anything beyond ~3 iterations means the question is too broad or the answer is already "reshape" — stop and write the finding (see Agentic P8: appetite is a cap expressed in slices, not in days). The kill condition is the signal that ends the prototype early — the question is answered in the first iteration, or the approach clearly fails in a way that needs no further exploration. Stopping early is not a failure; it is the skill working as intended.
90	
91	**3. Choose the mode.**
92	
93	| Mode | Best for | What it is |
94	|---|---|---|
95	| Narrative | Concept-level questions about flow and framing | Written scenario + annotated sketches; no code |
96	| Clickable | Interaction questions about sequencing and affordances | Mockup in a design tool, navigable but static |
97	| Throwaway code | Questions that require live data or real interaction behaviour | Code that runs, intentionally not production-quality |
98	
99	Throwaway code is the riskiest mode: most likely to drift into a release, most expensive to build, least often necessary. Use it only when the question cannot be answered by narrative or clickable means — for example, when the answer depends on real API latency, real data shape, or real browser behaviour.
100	
101	**4. Build and observe.**
102	Build the minimum that answers the question. Nothing beyond it. When the prototype is in the hands of an observer — a user, a teammate, yourself — record observations, not interpretations. Interpretation goes in the finding.
103	
104	**5. [GATE] Write the finding.**
105	A prototype must exit with a finding. If the time box expires and the question is not answered, the finding is: "this prototype approach did not answer the question; the next step is X." That is a valid finding. Exiting without a finding is not valid.
106	
107	The recommendation must be one of three:
108	- **Proceed** — the question is answered affirmatively; proceed to `design-doc`.
109	- **Reshape** — the question is answered but the answer is "not this way"; the idea needs revision before a design is possible.
110	- **Kill** — the question is answered negatively; the idea does not survive the prototype. This is a celebrated outcome (Rule D5): the prototype saved the cost of a full design and build.
111	
112	**6. Dispose of the prototype.**
113	Throwaway code: delete it, or mark it explicitly as non-production (no test coverage, no error handling, not to be deployed) in the finding. Do not commit throwaway code to the main branch without this marking. Do not extend throwaway code toward production quality — that requires a design-doc and a clean implementation.
114

151	## Common rationalisations
152	
153	| Rationalisation | Rebuttal |
154	|---|---|
155	| "The prototype took a day to build — we should ship it instead of throwing it away." | Sunk cost. The prototype answered a question; that was its job. If the finding is proceed, build it properly from a design-doc. If reshape or kill, the day was well spent. |
156	| "We'll clean up the throwaway code later." | No. Throwaway code goes to production as-is or it gets deleted. "Clean it up later" produces production code with no coverage, no error handling, and no operability. |
157	| "We don't have time for a prototype — let's just build it." | This is never faster. A prototype is 1–3 throwaway slices; a design-doc is many more; an implementation is many more again. Skipping the prototype bets the full build on an assumption that 1–3 throwaway slices would have resolved. |
158	| "We already know what users want — we don't need to observe." | This is the highest-confidence claim in product development, and the most commonly wrong one. A narrative prototype takes two hours. If the answer is certain, confirm it cheaply. |
159	| "The prototype became the product and it works fine." | Prototype code is built to answer a question, not to survive production. "It works fine" means it hasn't failed yet under controlled conditions. It has no test coverage, no security review, and no operability plan. It will fail. |
160	
161	## Red flags
162	
163	- No written question exists before the prototype begins.
164	- Time box was not set before starting, or was extended after starting.
165	- The prototype became the implementation without a design-doc.
166	- The finding exists but contains no recommendation.
167	- Throwaway code was committed to main without explicit non-production marking.
168	- Multiple questions are being answered by one prototype.
169	- The recommendation is "proceed" but no design-doc is the stated next step.
170	
171	## Verification / exit criteria
172	
173	The skill has run correctly when:
174	
175	1. A finding exists at `docs/prototypes/<slug>/finding.md`.
176	2. The finding contains the original question (one sentence), the approach, raw observations, an interpretation, and a recommendation of proceed / reshape / kill.
177	3. The prototype artefact is either deleted or explicitly marked non-production.
178	4. If the recommendation is proceed, the next step (`design-doc`) is named in the finding.
179	5. The time box was set before the prototype began and was not extended.

93	# Plan review
94	
95	## Purpose
96	
97	This skill catches plan defects before approval. A plan that looks coherent can still touch out-of-scope code, rest on unstated assumptions, or commit to a one-way door without recording the alternatives that were considered. By the time those defects surface in execution, the cost of correction is the cost of rework, not the cost of revision. The skill is the operational form of Agentic P3 (the spec is the seatbelt): it forces a structured pass over the plan against eight MECE attack buckets — problem framing, scope, assumptions, dependencies, reversibility, operability, sequencing, pre-mortem — so the categories of defect that actually appear in PDE work each get an explicit check. The deliverable is a review record with a final APPROVE / REVISE / KILL recommendation. The skill replaces the role-play "play the skeptic" framing of its predecessor with framework-based questioning, because empirical evidence (Nemeth meta-analysis) shows assigned dissent is less reliable than structured coverage.
98	
99	## When to use
100	
101	Run plan-review when at least one trigger fires. Any single trigger is sufficient.
102	
103	1. An LLM (or a human) has just produced a plan, spec, design doc, or roadmap, and the owner is about to approve it.
104	2. The plan breaks into more than one independently verifiable slice (see Agentic P8 — slices, not calendar time).
105	3. The plan touches code or systems the owner has not personally traced this week.
106	4. **Auto-fire**: the plan contains a one-way-door decision — architecture choice, schema migration, public API, vendor lock-in, auth change, or any touch of production data (defined: any system reachable from the production database, secrets vault, or auth identity store).
107	
108	If a trigger is ambiguous, run it. The Quick tier is short; the cost of skipping a needed review is not.
109	
110	## When not to use
111	
112	- **Typo fixes, single-line changes, pure read-only exploration.** Review overhead exceeds value.
113	- **Plans for work already in progress.** Use a kill-switch review instead — different question (should we stop?), different output.
114	- **Plans already reviewed and revised in the current session.** Re-review only if material new evidence arrived.
115	- **The plan itself doesn't exist yet.** Use `design-doc` or `idea-triage` to produce a plan first.
116	
117	## Inputs
118	
119	- The plan artefact: file path, pasted text, or plan stated in conversation
120	- Plan appetite — estimated time-to-completion. Extract from the plan; if absent, ask the owner before proceeding (appetite drives tier selection)
121	- Optional: prior plan-review records for related work (loaded for pattern continuity per Agentic P1)
122	- Access to `eng-principles-universal.md`, `eng-principles-agentic.md`, `PRODUCT_RULES.md`, and `references/confidence-meter.md`
123	
124	## Outputs
125	
126	A review record at `docs/plan-reviews/<plan-slug>/review.md`, plus an inline summary in the conversation containing the APPROVE / REVISE / KILL recommendation and the named conditions for any non-APPROVE verdict.
127	
128	## Tier selection — auto, not user-pick
129	
130	Two tiers. The skill selects the tier from plan attributes; the owner can override with `--quick` or `--full`.
131	
132	**Quick** (≤8 minutes). Runs B0, B1, B2, B3, and a short B8.
133	
134	**Full** (≤30 minutes). Runs all of B0–B8.
135	
136	**Auto-select Full when ANY of these holds:**
137	
138	- Plan appetite > ~5 slices (the design-doc threshold from Rule A1 / Agentic P8)
139	- Plan contains ≥1 one-way-door decision
140	- Plan has ≥3 external dependencies (other teams, vendors, third-party APIs)
141	- Plan touches production data, schema migrations, or auth
142	
143	**Why auto and not user-pick.** User-pick tiering produces a skip rate. Under deadline pressure, the owner picks Quick on plans that warrant Full, defeating the skill's purpose. Auto-select removes the discretion at the moment it is least reliable.
144	
145	## Workflow
146	
147	**Step 1 — Trigger check [GATE]**
148	Confirm at least one trigger from the When-to-use section fires. State which one. If none holds, recommend skipping or downgrading to a read-and-acknowledge. Do not proceed past this gate.
149	
150	**Step 1a — Fast-track gate [GATE]**
151	Before tier selection, check whether the plan qualifies for fast-track. The fast-track gate fires only when **all four** preconditions hold:
152	
153	1. **Class is KTLO/maintenance.** One of: dependency bump at minor or patch SemVer (any gem/npm/cargo/etc.); lint or format config change (rubocop.yml, eslint, prettier); doc-only change (README, comments, changelog); log/telemetry cleanup (removing unused log lines, renaming); test cleanup (deleting skipped/dead tests, fixture refresh).
154	2. **Fully reversible.** One-commit revert restores prior state. No production data, schema, auth, or vendor topology touched.
155	3. **Appetite is a single slice.** If the plan breaks into more than one independently verifiable slice, fall through to normal flow.
156	4. **No major-version anything.** Any major SemVer bump (1.x → 2.x), any breaking-API call-out, any "we'll need to absorb new features" framing → full flow. Major bumps need a problem statement (what features, why now, what we're absorbing) — they are not KTLO.
157	
158	If all four hold → emit the fast-track output template (below) and stop. Skip B0–B7 entirely; B8 is folded into the template as a one-liner. Length target 15–25 lines, hard cap 30. Token target ~15k vs ~55k for full Quick-tier flow.
159	
160	If any of the four fails → fall through to Step 2 (normal flow). Record one line on which precondition failed, so the owner sees why the gate did not fire.
161	
162	Rationale: this is the operational form of Universal Rule A5 (KTLO carve-out). On a fully-reversible KTLO change, the cost of acting on a flawed plan is bounded by the revert; the cost of running heavy review (and producing token waste plus REVISE-blocked APPROVEs on routine maintenance) exceeds the cost of the worst-case mistake. CI/CD is assumed present and is the runtime safety net for this class.
163	
164	### Fast-track output template
165	
166	```markdown
167	# Plan review: <plan-slug>
168	
169	**Fast-track gate fired** — KTLO/minor-version class, fully reversible, single slice. CI/CD is the runtime gate; this review is proportionate to that risk.
170	
171	**Cynefin domain**: Clear
172	**Tier**: Quick (fast-track sub-form)
173	
174	## Verdict: APPROVE
175	
176	## Sanity checks
177	- <check 1 — typically a scope-narrowing flag, e.g. `bundle update --conservative <gem>` not `bundle update`>
178	- <check 2 — typically a post-change validation, e.g. run `bundle exec rubocop` after bump, not just the test suite>
179	- <check 3 if applicable — e.g. confirm related ecosystem gems move in lockstep>
180	
181	## B8 — Pre-mortem (one line)
182	Top failure mode: <named, specific>. Kill-switch: <revert | named precheck>.
183	```
184	
185	If the gate fires and the produced review exceeds 30 lines, the gate misfired — re-evaluate against the four preconditions before emitting.
186	
187	**Step 2 — Tier selection**
188	Apply the auto-select rules. State the chosen tier and the attribute that selected it. If the owner has supplied `--quick` or `--full`, honour the override and record it.
189	
190	**Step 3 — B0 Cynefin classification**
191	One line: classify the plan's domain as Clear, Complicated, Complex, or Chaotic (Snowden). The classification adjusts review depth.
192	- **Clear** — known cause-effect; review is checklist coverage.
193	- **Complicated** — knowable with expertise; emphasise dependencies and risk.
194	- **Complex** — emergent; verify the plan includes feedback loops and not deterministic milestones.
195	- **Chaotic** — no clear cause-effect; stop. Recommend stabilising before planning.
196	
197	**Step 4 — B1 Problem framing [GATE]**
198	Does the plan open with a problem (a user or business outcome) or with a solution (a stack choice or feature)? A plan that begins "we will use Redis…" without a problem statement is solution-first; SUSTAINED. Demand a problem statement with measurable target before approval. (Universal P2.)
199	
200	**Step 5 — B2 Scope clarity [GATE]**
201	Read the plan against its declared scope. Name three things the plan touches that it has NOT declared in scope. Name three things it declares in-scope that are vague enough to expand silently. For each item, issue a verdict: **SUSTAINED**, **OVERTURNED**, or **PARTIAL**, accompanied by a specific falsifying condition (the observable thing that would prove the verdict wrong). If zero SUSTAINED items surface and the plan exceeds single-slice appetite, re-run B2 more aggressively — clean plans are rare, and zero hits usually means lenient review.
202	
203	**Step 6 — B3 Assumptions + evidence quality [GATE]**
204	Extract every "we assume…", "X will…", "the system can…", and "users want…" implicit in the plan. List the three riskiest. **For each, assign a Confidence score on Gilad's scale (`references/confidence-meter.md`):**
205	- 0.1 — opinion, assertion, assumption
206	- 0.5 — anecdote, one-off observation
207	- 2–5 — survey data, market research
208	- 5–8 — experiment, smoke test, prototype test
209	- 8–10 — validated launch, sustained behavioural data
210	
211	Then name a 5-minute test that would validate the assumption before execution begins, or a named owner who must sign off. Untested assumptions with Confidence < 5 block APPROVE. (Universal P4; Product P4.)
212	
213	**Step 7 — B4 Dependencies [GATE, Full only]**
214	List every internal, external, and cross-team dependency the plan implies. For each: is the owner named and confirmed in writing? Is capacity available within the plan's appetite? Unconfirmed dependencies are the single most common cause of missed commitments (Universal Rule B7). Verdict per dependency.
215	
216	**Step 8 — B5 Reversibility + ADR pairing [GATE, Full only]**
217	List every one-way door — decisions expensive to reverse (architecture, schema, public API, vendor lock-in). For each: does the plan name the alternatives that were considered? Does an ADR exist or has one been committed to be written? An undocumented one-way door is a silent commitment; the plan must either record the alternatives or be sent back to add them. (Universal P3, Rule B3; Agentic P7.)
218	
219	**Step 9 — B6 Operability + success metrics [GATE, Full only]**
220	Two halves.
221	- **Operability**: does the plan name metrics, alerts, rollback path, on-call runbook, and capacity headroom? (Universal Rule A6.)
222	- **Success metrics**: does the plan name a user-visible outcome metric that will be observed post-launch — not a delivery metric, an outcome metric? (Product P1: outcomes, not outputs.)
223	
224	Absence on either half blocks APPROVE.
225	
226	**Step 10 — B7 Sequencing + capacity (Full only)**
227	Is the critical path surfaced — does the plan name what blocks what? Is the appetite fixed (a cap, not a range)? Is the team's actual FTE consistent with the appetite? An appetite of "2–4 weeks" is not an appetite; it is a hope.
228	
229	**Step 11 — B8 Pre-mortem (cross-cutting, both tiers)**
230	Adopt prospective hindsight (Klein): assume the plan has already failed.
231	- **Quick**: the plan failed by the end of the slice it's executing. Name the top 1 reason. Name a kill-switch condition that would catch it early.
232	- **Full**: the plan shipped and failed within its appetite. Write the top 3 reasons ranked by likelihood. For the top 2, name kill-switch conditions.
233	
234	Generic reasons ("things went wrong") are rejected — name the specific failure mode.
235	
236	**Step 12 — Recommendation [GATE]**
237	Issue **APPROVE**, **REVISE**, or **KILL** with named conditions.
238	- **APPROVE** — no unresolved SUSTAINED verdicts; all required buckets ran.
239	- **REVISE** — at least one SUSTAINED verdict that the owner must address before approval.
240	- **KILL** — the plan's core premise fails (problem framing absent or false; reversibility cost unbearable; dependencies cannot be secured).
241	
242	APPROVE is blocked by any unresolved SUSTAINED verdict on a falsifying condition — **except** under the Quick-tier reversibility carve-out below. (When the Step 1a fast-track gate fires, this Step is bypassed entirely — fast-track output is APPROVE by construction.)
243	
244	**Quick-tier reversibility carve-out.** At Quick tier, when the plan is fully reversible (one-commit revert restores prior state, no production data touched, no schema/auth/vendor changes), SUSTAINED verdicts on B2 (scope) and B3 (assumptions) downgrade from "block APPROVE" to "**APPROVE with named recommendation**." The skill still surfaces the finding — the owner still sees the scope or assumption concern — but the recommendation rides alongside an APPROVE rather than triggering REVISE. Rationale: on a fully-reversible KTLO change (Universal Rule A5), the cost of acting on a flawed plan is bounded by the revert; the cost of REVISE-blocking such a plan exceeds the cost of the worst-case mistake. The carve-out does NOT apply to:
245	- B5 (reversibility) SUSTAINED — by definition the plan is not fully reversible
246	- B6 (operability) SUSTAINED — operability concerns survive revert
247	- Full-tier plans — the auto-select attributes (one-way door, production data, >1wk appetite) already preclude reversibility
248	
249	When the carve-out applies, write the verdict as `APPROVE — recommend: <named action>` and record the SUSTAINED bucket finding under Conditions for visibility.
250	
251	**Step 13 — File review record**
252	Write the review to `docs/plan-reviews/<plan-slug>/review.md` using the artefact template below. Include the inline summary in the conversation alongside.

308	## Common rationalisations
309	
310	| Rationalisation | Rebuttal |
311	|---|---|
312	| "I already read it." | Reading is not review. The buckets force coverage of categories that an unstructured read regularly misses — operability, ADR pairing, cross-team dependency confirmation. The skill is short; run it. |
313	| "It's a small plan, review is overkill." | The Quick tier is ~8 minutes. The cost of a missed scope drift on a small plan is the same cost as on a large one — full re-execution of work in the wrong place. |
314	| "The LLM considered alternatives." | The LLM produced text that mentions alternatives. B5 demands the alternatives be named alongside the chosen approach with reversal cost — not mentioned in passing. Pattern-match is not analysis. |
315	| "Quick mode is fine for this." | Tier is auto-selected by plan attributes for a reason. The Quick-instinct under deadline pressure is exactly when auto-selection earns its keep. Override with `--quick` only with a written reason. |
316	| "Pre-mortem is theatre." | Klein's prospective-hindsight literature shows pre-mortem reliably surfaces failure modes that forward critique misses. If the pre-mortem produces only generic reasons, it has been run badly — the rule is "name the specific failure mode," not "imagine generic difficulties." |
317	| "I don't have time for the full mode." | The plan attributes — appetite, one-way doors, dependencies, production data — are exactly the conditions under which review is most expensive to skip. The 30-minute cap exists because past that point the plan itself needs simplification before it can be reviewed at all. |
318	| "We can revise mid-execution if we hit issues." | Revising mid-execution is the failure mode this skill exists to prevent. The cost of a SUSTAINED B2 caught before execution is rewriting a plan; the same finding caught mid-execution is rewriting code, tests, and partial deployments. |
319	| "But this is a tiny change, do I really need a review?" | If the Step 1a fast-track gate fires, the review is ~20 lines and runs in seconds. The gate is calibrated for exactly this case (KTLO, fully reversible, single slice). If the gate doesn't fire on what you thought was a one-slice change, the change is not what you think it is — read what the gate flagged as missing. |

321	## Red flags
322	
323	- A verdict is given without a named falsifying condition.
324	- B2 returns zero items on a plan whose appetite exceeds a single slice.
325	- Pre-mortem reasons are all generic ("things might go wrong", "might be slow").
326	- A one-way door is identified but the plan is APPROVED without alternatives or ADR.
327	- Confidence scores are missing on B3 items.
328	- Operability section absent on a Full-tier plan.
329	- Owner runs the skill but discards REVISE recommendations without addressing them.
330	- Review record filed without a final recommendation.

332	## Verification / exit criteria
333	
334	A single review run is complete when all of the following hold:
335	
336	1. The triggered condition is stated, and the chosen tier is named with the selecting attribute.
337	2. The Cynefin domain is stated (B0).
338	3. Every required bucket for the tier ran and produced verdicts.
339	4. Every verdict has a named falsifying condition.
340	5. Every B3 item carries a Confidence score (Gilad scale).
341	6. APPROVE is issued only when zero unresolved SUSTAINED verdicts remain.
342	7. The review record exists at `docs/plan-reviews/<plan-slug>/review.md`.

344	## Known limits + revisit triggers
345	
346	The skill carries deliberate limitations. Each one has a measurable trigger that should prompt a revisit.
347	
348	| Limit | Revisit trigger | Action |
349	|---|---|---|
350	| Tier auto-select rules may not match the owner's risk model | Override rate exceeds 20% over the first 10 runs | Revisit the auto-select attribute set |
351	| Review files at `docs/plan-reviews/` assume a downstream reader | No references to `docs/plan-reviews/` appear in subsequent work after one month | Migrate to inline-only output or a Slack rollup |
352	| Full mode has a 30-minute cap | Full runs exceed 30 minutes on >25% of cases | Split the skill or expand the cap |
353	| Review runs in main context — same context as the plan author = same blindspots | Evals show the review adopts plan-author framing (false-OVERTURN rate >10%) | Extract review to a sub-agent with isolated context |
354	| One skill covers all plan types — roadmap-specific moves not specialised | ≥5 reviews against roadmaps yield <30% bucket hit rate | Split off a separate `roadmap-review` skill |
355	| Bucket structure was designed against PDE failure modes, not piloted | Any bucket has <10% SUSTAINED hit rate after 5 real runs | Prune or merge buckets |

54	## Core operating behaviours
55	
56	These apply across every skill in the pack. They are not optional.
57	
58	**Surface assumptions before acting.** Before any non-trivial action, state the assumptions being made and give the owner a chance to correct them. Wrong assumptions caught early are cheap; wrong assumptions caught after implementation are expensive.
59	
60	**Stop at gates.** Each skill contains numbered gates (`[GATE]`). A gate is a hard stop — do not proceed past it until the gate condition is met. Gates exist because the work that follows them is wasted if the gate condition is false.
61	
62	**Scope discipline.** Touch only what the current skill requires. Do not refactor adjacent code, remove things you don't understand, or add features not in the spec. Every deviation from scope requires explicit owner approval.
63	
64	**Confirm before destructive action.** Deletion, reset, overwrite, force-push, dropping a table — pause and confirm with the owner before proceeding. The cost of confirmation is one message; the cost of an unintended destructive action can be days of recovery.
65	
66	**Incomplete is not done.** A task is not complete until its verification criteria pass. "Seems right" is never sufficient. Evidence is required: passing tests, build output, measurement.
67	
68	**Disagreement is required.** If an approach has a clear problem, name it, quantify the downside, and propose an alternative. Accept the owner's final decision. Sycophantic agreement with a bad plan is a worse failure mode than honest pushback.

70	## Common mistake: skipping skills
71	
72	Skills are not ceremony — they encode the checks that prevent the most common and expensive failure modes. Skipping idea-triage produces a roadmap full of unvalidated opinions. Skipping design-doc produces implementations that solve the wrong problem or the right problem in an unmaintainable way. Skipping planning-and-task-breakdown produces an implementation plan that falls apart at the first unexpected dependency.
73	
74	The value of a skill is highest the first time you skip it and something breaks. After that, the cost of not skipping it is obvious.

44	A prototype-to-validate is a throwaway artefact built to answer one specific question before engineering time is committed to a design. The question is always a product question — how the feature will feel, whether users will understand an interaction, whether a proposed flow creates or removes confusion. Technical unknowns belong in a spike (Rule C5). The output is a written finding, not a deliverable artefact.
45	
46	This skill sits between `idea-triage` and `design-doc`. Idea-triage confirms a problem is real and worth pursuing. That is not enough to know how to solve it. When the gap between "this is worth building" and "this is how we'll build it" is a product question, a prototype answers it cheaply. A design-doc started from an unclear product direction will be redesigned; a prototype started from an unclear product direction will be thrown away. Throwaways are cheaper.
47	
48	The risk this skill guards against is the prototype that becomes an implementation. A prototype built with production-quality code, extended beyond its original question, and shipped to users has become a real release — without tests, without a design review, without operability planning. Prototypes must be throwaway by policy: the question is the constraint, the code is the instrument, the finding is the output.
49	
50	## When to use
51	
52	- An idea has cleared idea-triage and the dominant remaining unknown is product feel — how the interaction works, whether the flow makes sense, what the experience is like for a user.
53	- A design-doc has stalled because the team disagrees about which approach will feel right and opinion-level argument is not resolving it.
54	- Before committing to a design-doc for a significant UX-touching change where intuition about user response is low.
55	
56	## When not to use
57	
58	- **The dominant unknown is technical** — run a spike instead. Spikes answer: can we do this, at what cost, with what constraints? Prototypes answer: does this feel right, will users understand this?
59	- **The idea hasn't been triaged** — run `idea-triage` first. A prototype is not a substitute for problem validation; it is a tool for solution exploration after the problem is confirmed.
60	- **The interaction is known and the task is to design the system** — go directly to `design-doc`. Prototype-to-validate is discovery work; design-doc is commitment work.
61	- **Multiple questions need answering** — triage the questions first. One prototype answers one question. Run prototypes sequentially, not simultaneously.
62	
63	## Inputs
64	
65	- An idea-triage output: validated hypothesis, ICE score, confidence rating.
66	- A single, specific question the prototype will answer (one sentence, written before building begins).
67	- A time box (set before the prototype begins; not extended after starting).
68	
69	## Outputs
70	
71	A written finding at `docs/prototypes/<slug>/finding.md`. The finding contains: the question, the prototype approach, the observations, and a recommendation: proceed / reshape / kill. The prototype code, if any, is either deleted or explicitly marked non-production in the finding.
72	
73	## Workflow
74	
75	**1. Write the question.**
76	Before building anything, write the question in one sentence. The question must be specific (one thing, not a cluster), answerable by observation, and bounded (there is a signal that means "yes" or "no"). If the question cannot be written in one sentence, it is not well-defined. Resolve it first.
77	
78	Good questions:
79	- "Will a user who has not seen this flow understand that step 2 must complete before step 3 unlocks?"
80	- "Does inline editing feel faster than a modal for this data type, based on a walkthrough with one internal user?"
81	- "Is the proposed navigation structure legible — does a new user land in the right section?"
82	
83	Questions too vague to drive a prototype:
84	- "How should the onboarding flow work?" — a design brief, not a question
85	- "Will users like this?" — not specific enough to be answerable
86	- "Is this the right approach?" — too broad; which aspect of the approach?
87	
88	**2. Set the time box and the kill condition.**
89	Name both before writing a line. Default appetite: 1–3 build-observe iterations on the single question. Each iteration is a slice (build → put it in front of an observer → record what was seen). Anything beyond ~3 iterations means the question is too broad or the answer is already "reshape" — stop and write the finding (see Agentic P8: appetite is a cap expressed in slices, not in days). The kill condition is the signal that ends the prototype early — the question is answered in the first iteration, or the approach clearly fails in a way that needs no further exploration. Stopping early is not a failure; it is the skill working as intended.
90	
91	**3. Choose the mode.**
92	
93	| Mode | Best for | What it is |
94	|---|---|---|
95	| Narrative | Concept-level questions about flow and framing | Written scenario + annotated sketches; no code |
96	| Clickable | Interaction questions about sequencing and affordances | Mockup in a design tool, navigable but static |
97	| Throwaway code | Questions that require live data or real interaction behaviour | Code that runs, intentionally not production-quality |
98	
99	Throwaway code is the riskiest mode: most likely to drift into a release, most expensive to build, least often necessary. Use it only when the question cannot be answered by narrative or clickable means — for example, when the answer depends on real API latency, real data shape, or real browser behaviour.
100	
101	**4. Build and observe.**
102	Build the minimum that answers the question. Nothing beyond it. When the prototype is in the hands of an observer — a user, a teammate, yourself — record observations, not interpretations. Interpretation goes in the finding.
103	
104	**5. [GATE] Write the finding.**
105	A prototype must exit with a finding. If the time box expires and the question is not answered, the finding is: "this prototype approach did not answer the question; the next step is X." That is a valid finding. Exiting without a finding is not valid.
106	
107	The recommendation must be one of three:
108	- **Proceed** — the question is answered affirmatively; proceed to `design-doc`.
109	- **Reshape** — the question is answered but the answer is "not this way"; the idea needs revision before a design is possible.
110	- **Kill** — the question is answered negatively; the idea does not survive the prototype. This is a celebrated outcome (Rule D5): the prototype saved the cost of a full design and build.
111	
112	**6. Dispose of the prototype.**
113	Throwaway code: delete it, or mark it explicitly as non-production (no test coverage, no error handling, not to be deployed) in the finding. Do not commit throwaway code to the main branch without this marking. Do not extend throwaway code toward production quality — that requires a design-doc and a clean implementation.
114

151	## Common rationalisations
152	
153	| Rationalisation | Rebuttal |
154	|---|---|
155	| "The prototype took a day to build — we should ship it instead of throwing it away." | Sunk cost. The prototype answered a question; that was its job. If the finding is proceed, build it properly from a design-doc. If reshape or kill, the day was well spent. |
156	| "We'll clean up the throwaway code later." | No. Throwaway code goes to production as-is or it gets deleted. "Clean it up later" produces production code with no coverage, no error handling, and no operability. |
157	| "We don't have time for a prototype — let's just build it." | This is never faster. A prototype is 1–3 throwaway slices; a design-doc is many more; an implementation is many more again. Skipping the prototype bets the full build on an assumption that 1–3 throwaway slices would have resolved. |
158	| "We already know what users want — we don't need to observe." | This is the highest-confidence claim in product development, and the most commonly wrong one. A narrative prototype takes two hours. If the answer is certain, confirm it cheaply. |
159	| "The prototype became the product and it works fine." | Prototype code is built to answer a question, not to survive production. "It works fine" means it hasn't failed yet under controlled conditions. It has no test coverage, no security review, and no operability plan. It will fail. |
160	
161	## Red flags
162	
163	- No written question exists before the prototype begins.
164	- Time box was not set before starting, or was extended after starting.
165	- The prototype became the implementation without a design-doc.
166	- The finding exists but contains no recommendation.
167	- Throwaway code was committed to main without explicit non-production marking.
168	- Multiple questions are being answered by one prototype.
169	- The recommendation is "proceed" but no design-doc is the stated next step.
