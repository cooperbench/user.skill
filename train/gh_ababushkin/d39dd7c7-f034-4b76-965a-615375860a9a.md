Content sections, in order:

2. **Triage by layer.** Identify which PR/layer owns each comment (a comment on PR 3 about a line introduced in PR 1 still gets fixed in PR 1).

4. **Propagate with restack.** `gt restack` to walk parent SHAs upstream so every higher layer points at the new bottom-layer commit.
5. **Force-push the stack.** `gt submit --stack` pushes all amended layers in one shot. Verify with `gh pr view {N} --json headRefOid` that the GitHub head SHA matches local.

9	## The initiative model
10	
11	An **initiative** is a time-bounded, goal-oriented body of work with a stated success criterion and a bounded appetite. It is not a repo alias, not a backlog, and not a feature list.
12	
13	An initiative is ready to enter a cycle when it can answer all six of these fields:
14	
15	```
16	Goal:           For [who], we want to [solve problem / achieve outcome].
17	Key results:    1. [committed|aspirational] — [observable state — binary pass/fail,
18	                      fitness function firing, or measurable delta]
19	                   baseline: [current value/state]
20	                   target:   [value/state we expect at the end]
21	                   window:   [when this is judged — "by end of cycle", "within 30 days"]
22	                   source:   [where the evidence lives — file path, log, Linear query]
23	                2. [committed|aspirational] — [observable state]
24	                   baseline: ...  target: ...  window: ...  source: ...
25	                3. [committed|aspirational] — [observable state]
26	                   baseline: ...  target: ...  window: ...  source: ...
27	                (3–5 KRs total; each verifiable by inspecting the system —
28	                 no "improve X" / "better Y" / "run N times" language)
29	Affected repos: [list]
30	Appetite:       ~[N] issues  (not days or weeks)
31	Kill condition: [observable state that says "the bet didn't work, walk away"]
32	Project type:   [1: methodology | 2: personal product | 3: utility skill pack |
33	                 4: research/thesis | 5: equity research | 6: production]
34	```
35	
36	The format is OKR-shaped: the Goal is the Objective (qualitative, what we want to achieve), and Key results are the 3–5 observable states that must be true for the initiative to be Done. KRs are written so a future agent (or you on a fresh session) can verify each by looking at the system — no "improve X" / "better Y" language. Each KR carries four sub-fields (baseline / target / window / source) and a `[committed|aspirational]` tag that sets the grading bar at cycle close.
37	
38	If any of the six fields can't be filled, the initiative is not ready. Create it as a Draft in Linear but don't assign it to a cycle.

41	
42	| Size | Issue count | Notes |

44	| Too small | < 5 | Not an initiative — create a standalone issue or put it in the ops slot |

46	| Medium | 9–12 | One full cycle slot |
47	| Large | 13–15 | Full cycle slot; very little room for anything else |

51	
52	| State | Meaning |

54	| **Draft** | Idea exists; goal or criterion not yet written |

57	| **Done** | Success criterion observed (or definitively ruled out) — not just issues closed |
58	| **Paused** | Deprioritised mid-cycle; carries over with a note on why |
59	| **Canceled** | Kill condition triggered, or initiative definitively ruled out mid-cycle; one-sentence reason recorded |

74	
75	A cycle is 3–4 working days of focused work plus 1 planning day.

115	- They surface mid-flight as non-initiative work (bugs, one-offs)

196	## What this model replaces
197

1	# Graphite stack review — handling reviewer comments
2	
3	This runbook covers what to do when a reviewer leaves comments on a Graphite-stacked PR series. It applies whenever you have two or more PRs linked by `gt` and at least one comment has arrived that requires a code change.
4	
5	---
6	
7	## 1. Fetch the reviewer's comments
8	
9	Pull the raw review comments for each PR in the stack:
10	
11	```
12	gh api repos/{owner}/{repo}/pulls/{N}/comments
13	```
14	
15	Run this command once per PR number in the stack (bottom to top). The response is a JSON array; each element has `path`, `line`, `body`, and `diff_hunk`. Collect all comments before triaging — a comment on PR 3 may describe a line that was introduced in PR 1.
16	
17	---
18	
19	## 2. Triage by layer
20	
21	For each comment, identify which layer actually introduced the changed line:
22	
23	1. Note the `path` and `line` from the comment.
24	2. Run `git log --all --oneline -- <path>` across the stack to see which branch first touched that file.
25	3. Assign the comment to the branch (layer) where the line was introduced, regardless of which PR number the reviewer left it on.
26	
27	A comment left on PR 3 about a line introduced in PR 1 is a PR-1 fix — make the change there, not in PR 3.
28	
29	---
30	
31	## 3. Amend bottom-up
32	
33	Work layer by layer, starting from the lowest layer that has comments:
34	
35	1. Check out the target layer: `gt checkout <bottom-branch>`
36	2. Make the fix in the working tree.
37	3. Stage and amend: `git commit --amend --no-edit`
38	4. Stay on that layer until the commit is complete before moving to the next layer.
39	
40	Do not cascade upward manually. Restack handles parent-SHA propagation in the next step.
41	
42	---
43	
44	## 4. Propagate with restack
45	
46	After amending every affected layer, run:
47	
48	```
49	gt restack
50	```
51	
52	`gt restack` walks the stack from the amended layer upward, rebasing each higher layer onto the new parent SHA. Every branch in the stack will point at the correct, amended history when it completes.
53	
54	If restack reports a conflict, resolve it in the working tree, stage the resolution, and run `gt restack --continue`.
55	
56	---
57	
58	## 5. Force-push the stack
59	
60	Push all amended layers to GitHub in one command:
61	
62	```
63	gt submit --stack
64	```
65	
66	After the push, verify that GitHub's head SHA matches your local branch for each PR:
67	
68	```
69	gh pr view {N} --json headRefOid
70	git rev-parse <branch-name>
71	```
72	
73	The two SHAs must match. A mismatch means the push didn't land cleanly — re-run `gt submit --stack` and check for push-protection errors before assuming success.
