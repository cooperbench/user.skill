### 8. **The Root Design Issue**

The fundamental problem is a **race condition between agent state transition and orchestrator PR assembly:**

- **Agent owns:** Marking Done via Linear MCP
- **Orchestrator owns:** PR submission via Graphite
- **Gap:** Once agent marks Done, the orchestrator cannot revert it, but the PR assembly can still fail

If the prompt required the agent to:
1. Write `.drain-handoff.json` BEFORE marking Done, AND
2. The orchestrator verified the file exists and is valid before allowing Done

...then the orchestrator could enforce that successful PR assembly precedes the Done transition. Currently, the order is inverted—Done happens first, PR assembly second.

The two other halt paths (worker crash `:678`, not-Done `:862`) already revert via `_revert_to_pre_halt_state`; the graphite-failure path was the one that forgot. So "Done" silently meant "agent finished," not "PR exists."

**Fix applied** (`drain_cycle/orchestrator.py`, graphite-failure block). On a stacked-PR submission failure for an already-Done issue, the orchestrator now:
- reverts the issue out of Done back to its pre-spawn state (same `_revert_to_pre_halt_state` call shape as the not-Done path),
- posts a blocker comment naming the failure (`"Reverted from Done: stacked PR submission failed — …. Worktree preserved for re-run."`),
- builds `halt_reason` from the *effective* state and appends a `revert … failed` suffix if the revert itself errored,
- records the effective state (not the stale Done) in the run-log.

The worktree with committed work is still preserved on disk, so a re-run resumes via the existing resume directive and re-attempts the PR. Now **Done guarantees a PR exists.**
