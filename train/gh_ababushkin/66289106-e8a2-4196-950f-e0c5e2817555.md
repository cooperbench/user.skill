> AGENT

Three distinct directions, each with a different tradeoff:

---

**1. `/pde-cycle-close` skill**
Claude-invokable at the end of each cycle. It calls `list_projects` filtered by `createdAt` within the cycle window, runs the rubric against each description (count KR blocks, check all 4 sub-fields, verify commit/aspirational labels), and outputs a pass/fail table. KR3 gets a separate prompt: "did you write a retro note into this project? paste it now." Purely Markdown + Linear MCP — fits the existing stack. The downside is it's manual: you have to remember to invoke it.

**2. A `stop-the-line` hook on `/initiative-shape`**
Runs immediately after the skill creates the Linear project — reads the description back via `get_project`, scores it against the rubric, and blocks (or warns) if it fails. This catches KR1/KR2 failures at creation time rather than at retro time. Proactive rather than retrospective. The tradeoff: it only covers initiatives created by the skill, not ones created another way, and it can't measure KR3 (which is a cycle-level signal).

**3. A standalone Python script hitting the Linear REST API**
Runs outside Claude Code — cron, CI, or manual. Parses description markdown with a regex for `**KR` blocks and sub-fields, writes a JSON report. Advantage: no Claude dependency, portable, can be committed to the repo and version-controlled. Disadvantage: you'd need to set up Linear API credentials and a runner, which is overhead for a personal workspace.

---

My recommendation: **option 1 first, option 2 later**. The skill gives you a fast feedback loop with no infrastructure; once the rubric is stable (KR2 is consistently passing), add the hook so it self-enforces at creation time. Option 3 is only worth it if you want to automate across cycles without invoking Claude.

Want me to build option 1?

how long do i need to have this skill active for before i know the initiative was successful

> AGENT

Your KRs already answer this — the window is **4 cycles** across all three. At ~4-5 working days per cycle, that's roughly 3–4 calendar weeks from the moment the updated skill lands.

But the signal arrives unevenly:

- **KR1** — visible after the first initiative created with the new skill. You know immediately whether it's producing ≥3 KRs.
- **KR2** — needs 5 initiatives to exist (so the "last 5" sample is meaningful). At 3 initiatives per cycle, that's cycle 2 before the rubric pass rate is real.
- **KR3** — needs 3 retros. Earliest you can call it is cycle 3.

The kill condition also tells you when to bail early: if KR2 fails for **2 consecutive cycles** after the skill update, you don't wait for cycle 4 — you re-shape.

So in practice: check after cycle 2 (KR1 + early KR2 signal), check at cycle 3 (KR3 becomes gradeable), and call the initiative Done or Paused at the cycle 4 retro.
