1	# delivery-shape — plan-artefact contract
2	
3	The schema for a **delivery plan**: the set of cross-referenced markdown files that turn one
4	committed initiative into an ordered, verifiable delivery hierarchy — deliverable → node → task —
5	that a human reads top-down and a deterministic reader walks bottom-up into a tracker manifest.
6	
7	This contract was **read off a worked example**, not designed in the abstract:
8	[`examples/delivery-plans/top-down-delivery-planning/`](../examples/delivery-plans/top-down-delivery-planning/).
9	Read that example alongside this spec — every rule here points at a node that demonstrates it.
10	
11	> **Tool-agnostic by rule.** This contract names no tracker, language, or runtime. It describes
12	> *file-set structure* and *tracker-artefact classes* (milestone-class / issue-class /
13	> sub-issue-class). Binding those classes to a concrete tracker is the **adapter's** job and lives
14	> in another repo. Emitted plans (the example) may name concrete tools; this contract may not.
15	
16	---
17	
18	## The three layers
19	
20	| Layer | Lives as | Tracker-artefact class | Completion criterion |
21	|-------|----------|------------------------|----------------------|
22	| **Deliverable** | a directory `D*/` with `_deliverable.md` | milestone-class | its served KR is observed |
23	| **Node** | a file `N*.md` | issue-class | **type-dependent** (see vocabulary) |
24	| **Task** | a `- [ ]` / `- [x]` line inside a node | sub-issue-class | the checkbox + its description |
25	
26	A node is **polymorphic**: it is not always a user story. It carries whichever completion
27	criterion its work calls for — a story carries acceptance criteria, a spike carries a decision and
28	a stop condition, a capability carries its own spec, and so on. This is the central claim the
29	example exists to prove. (A capability is one of these node types, not a separate structural
30	layer — see *Design notes* for why the earlier four-layer model was collapsed.)

34	## Schema element 1 — Directory layout
35	
36	Directory nesting **is** the hierarchy. Depth encodes layer; nothing else needs to:
37	
38	```
39	<initiative-slug>/
40	├── README.md                  initiative root: goal + KRs + how-to-read + tree + hand-count manifest
41	├── D<n>-<slug>/               deliverable      → milestone-class
42	│   ├── _deliverable.md        the deliverable's own front-matter + statement
43	│   ├── N<nn>-<slug>.md        node             → issue-class
44	│   └── …
45	└── …
46	```
47	
48	Rules:
49	
50	- **Numeric prefixes** (`D1`, `N03`) give a deterministic reading and walking order. Pad node
51	  numbers (`N01`) so lexical sort = intended sort past nine nodes.
52	- **Layer-header files** are underscore-prefixed (`_deliverable.md`) so they sort
53	  first within their directory and are unambiguously the layer object, not a node.
54	- **Node files** are the only `N*.md` files; one node per file.
55	- The **root `README.md`** is the single top-down entry point: it carries the goal + KRs verbatim
56	  (read top-down starts at the outcome, not at task 1), the rendered tree, and the **hand-count
57	  manifest** the walk-script must reproduce.
58	
59	## Schema element 2 — Cross-reference convention
60	
61	**Relative paths + directory hierarchy + front-matter back-links.** Three reinforcing signals, no
62	hand-maintained index:
63	
64	- **Down** — a parent links to each child by relative path (`_deliverable.md` lists its
65	  nodes; `README.md` renders the whole tree).
66	- **Up** — every file's front-matter carries `parent:` (the enclosing layer) so a reader that
67	  starts at any node can climb without scanning directories.
68	- **To the bet** — every deliverable and node carries `serves_kr:` naming the KR it serves, so the
69	  outcome trace is explicit at every layer, not inferred from position.
70	
71	The **manifest is derived, never authored**: a walk-script reconstructs milestone/issue/sub-issue
72	counts from the directory structure + front-matter. The hand-count in the README exists only as
73	the oracle the derived manifest is checked against. (A hand-maintained manifest file was
74	considered and rejected — it is a second source of truth that drifts; see *Design notes*.)
75	
76	## Schema element 3 — Per-node tags (front-matter)
77	
78	Every layer file opens with YAML front-matter. The load-bearing tags:
79	
80	```yaml
81	layer:        deliverable | node                   # which layer this file is
82	id:           D1 | N03                              # stable within the plan
83	type:         <node-type>                          # NODE FILES ONLY — the polymorphic node discriminator (see vocabulary); `capability` is one of these types
84	title:        <one line>
85	parent:       <relative path or id of enclosing layer>
86	serves_kr:    KR<n>                                # deliverable↔KR and node↔KR trace
87	maps_to:      <tracker-artefact class>             # milestone/issue/sub-issue class
88	skeleton:     true | (absent)                      # NODE-LEVEL: is this the walking-skeleton node?
89	external_window: <external constraint> | none      # see constraints — never effort-in-days
90	completion:
91	  form:       <completion-criterion form>          # the type-appropriate form (see vocabulary)
92	  criterion:  <the observable criterion, by form>
93	delegates_to: <rule or skill that owns this node type's discipline>
94	```
95

97

99	2. **deliverable↔KR** — `serves_kr:` on each `_deliverable.md` (and echoed on nodes). Every
100	   deliverable serves exactly one KR; this is the outcome spine.
101	3. **completion-criterion** — `completion.form` + `completion.criterion`, shaped by `type`.
102	4. **task↔skeleton flag** — at the **task** level, the walking-skeleton/foundational task is marked
103	   with a leading `` `skeleton` `` tag inside its checklist line. At the **node** level, the node
104	   that *is* the initiative's walking skeleton carries `skeleton: true` in front-matter. Foundational
105	   / toolchain work is **folded into** the skeleton task's description — never a silent setup task
106	   before it (mirrors `planning-and-task-breakdown`'s walking-skeleton-first rule). There is no
107	   `foundational` node type: foundational work is a property of the skeleton **task**, not a node.
108	
109	Task lines are the sub-issue layer. A task is `- [ ] ` or `- [x] `; an optional leading
110	`` `skeleton` `` code-span marks it as the walking-skeleton/foundational task. Example:
111	`` - [ ] `skeleton` — walk the tree, read front-matter, print counts (toolchain folded in) ``.

216	## Design notes / alternatives considered
217	
218	- **File-per-node vs section-per-node.** Chosen: one file per node, structure carried by directory
219	  depth + front-matter. Rejected: nodes as `##` sections inside the `_deliverable.md` file with
220	  fenced metadata blocks — fewer files, but it forces the reader to parse headings and extract fenced
221	  blocks, which is more fragile than reading front-matter from a known file path. If a future
222	  walk-script finds front-matter parsing insufficient, section-per-node is the documented fallback —
223	  but the burden is on showing front-matter failed first.
224	- **Derived vs hand-maintained manifest.** Chosen: derive the manifest from structure; keep only a
225	  hand-count *oracle* in the README. Rejected: a checked-in manifest file enumerating every
226	  milestone/issue/sub-issue — a second source of truth that drifts from the files it indexes.
227	- **Four structural layers vs three.** Chosen: three — deliverable → node → task, mapping 1:1 to
228	  milestone / issue / sub-issue. Rejected: a fourth `capability` layer mapped to a label. A label is
229	  *stateless* (name + colour, no done-state, no target), yet a capability asserts a real completion
230	  criterion — a stateful claim a label can't hold or check; and the mapping was asymmetric
231	  (deliverables, the same kind of object, get a stateful milestone). The fix folds `capability` into
232	  the polymorphic node vocabulary as a node *type* (completion form `the-capability-spec`): a
233	  capability that carries its own irreducible spec is a node, broken into task-slices, sitting beside
234	  the `story` / `spike` / … nodes under its deliverable. Labels remain available for *orthogonal*

46	# Planning and task breakdown
47	
48	## Purpose
49	
50	This skill takes an accepted design doc and produces an ordered task list where each task is small enough to complete and verify independently. 51	
52	The goal is not comprehensiveness — it is clarity and verifiability. A task list that looks thorough but whose tasks are too big to verify will not survive contact with implementation. Every task must answer: "how do I know this is done?"
53	
54	## When to use
55	
56	- A design doc has been accepted and implementation is ready to begin.
57	- A well-scoped spec exists for a change that doesn't meet the Rule A1 design-doc trigger, but is complex enough that sequencing and acceptance criteria are non-obvious.
