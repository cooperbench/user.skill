1	# Linear workflow — initiative model
2	
3	This document is the canonical governance model for how work is tracked in Linear when using the workflow-hooks pack. It applies to any repo in the workspace that loads this pack.
4	
5	> **Cross-pack note:** The six-field initiative shape definition and the `/initiative-shape` skill are canonical in the Shaper pack. If the Shaper pack is installed alongside this one, defer to Shaper for initiative authoring and use this document for the tracker mechanics (cycle model, issue workflow, project conventions). If Shaper is not installed, use the inline fallback in the [Capturing a shaped initiative in Linear](#capturing-a-shaped-initiative-in-linear) section below.
6	
7	---
8	
9	## The initiative model
10	
11	An **initiative** is a time-bounded, goal-oriented body of work with a stated success criterion and a bounded appetite. It is not a repo alias, not a backlog, and not a feature list.
12	
13	An initiative is ready to enter a cycle when it can answer all six of these fields:
14	
15	```
16	Goal:           For [who], we want to [solve problem / achieve outcome].
17	Key results:    1. [committed|aspirational] — [observable state — binary pass/fail,
18	                      fitness function firing, or measurable delta]
19	                   baseline: [current value/state]
20	                   target:   [value/state we expect at the end]
21	                   window:   [when this is judged — "by end of cycle", "within 30 days"]
22	                   source:   [where the evidence lives — file path, log, Linear query]
23	                2. [committed|aspirational] — [observable state]
24	                   baseline: ...  target: ...  window: ...  source: ...
25	                3. [committed|aspirational] — [observable state]
26	                   baseline: ...  target: ...  window: ...  source: ...
27	                (3–5 KRs total; each verifiable by inspecting the system —
28	                 no "improve X" / "better Y" / "run N times" language)
29	Affected repos: [list]
30	Appetite:       ~[N] issues  (not days or weeks)
31	Kill condition: [observable state that says "the bet didn't work, walk away"]
32	Project type:   [1: methodology | 2: personal product | 3: utility skill pack |
33	                 4: research/thesis | 5: equity research | 6: production]
34	```
35	
36	The format is OKR-shaped: the Goal is the Objective (qualitative, what we want to achieve), and Key results are the 3–5 observable states that must be true for the initiative to be Done. KRs are written so a future agent (or you on a fresh session) can verify each by looking at the system — no "improve X" / "better Y" language. Each KR carries four sub-fields (baseline / target / window / source) and a `[committed|aspirational]` tag that sets the grading bar at cycle close.
37	
38	If any of the six fields can't be filled, the initiative is not ready. Create it as a Draft in Linear but don't assign it to a cycle.
39	
40	### Initiative size
41	
42	| Size | Issue count | Notes |
43	|---|---|---|
44	| Too small | < 5 | Not an initiative — create a standalone issue or put it in the ops slot |
45	| Small | 5–8 | One cycle slot with room left for other initiatives |
46	| Medium | 9–12 | One full cycle slot |
47	| Large | 13–15 | Full cycle slot; very little room for anything else |
48	| Too large | > 15 | Split into two initiatives before committing |
49	
50	### Initiative lifecycle
51	
52	| State | Meaning |
53	|---|---|
54	| **Draft** | Idea exists; goal or criterion not yet written |
55	| **Ready** | All six fields confirmed — Goal + Key results (with sub-fields + tags) + Affected repos + Appetite + Kill condition + Project type; can enter a cycle |
56	| **Active** | Assigned to the current cycle; work in progress |
57	| **Done** | Success criterion observed (or definitively ruled out) — not just issues closed |
58	| **Paused** | Deprioritised mid-cycle; carries over with a note on why |
59	| **Canceled** | Kill condition triggered, or initiative definitively ruled out mid-cycle; one-sentence reason recorded |
60	
61	**Done ≠ all issues closed.** An initiative closes when the key results are observed (or definitively ruled out) — not when its issue list reaches zero. An initiative that shipped everything but the KRs didn't hold is not Done; it is Paused for a retrospective.
62	
63	### Creating an initiative
64	
65	If the Shaper pack is installed, use the `/initiative-shape` skill — it enforces the six-field check (including the verification rubric gate) before creating the Linear project.
66	
67	If Shaper is not installed, follow the [Capturing a shaped initiative in Linear](#capturing-a-shaped-initiative-in-linear) procedure below, filling the six fields manually before calling the Linear API.
68	
69	Direct creation without filling all six fields is permitted only for: maintenance buckets, ops slots, and one-off standalone issue groupings.
70	
71	---

73	## Cycle model
74	
75	A cycle is 3–4 working days of focused work plus 1 planning day.
76	
77	### Cycle composition
78	
79	Every cycle has **exactly four slots**:
80	
81	| Slot | Type | Goal/criterion required? |
82	|---|---|---|
83	| Initiative 1 | Goal-oriented | Yes |
84	| Initiative 2 | Goal-oriented | Yes |
85	| Initiative 3 | Goal-oriented | Yes |
86	| Ops slot | Maintenance | No |
87	
88	The ops slot is not an initiative. It exists for: bug fixes, compliance items, emergent issues, one-offs, and KTLO work. Ops slot issues either have no project assigned, or live in the team's **ops container project** — a perpetual Backlog-state project named e.g. "Ops — bugs, maintenance, emergent" that holds ops work. The container project carries no Goal and no Key Results because it is not an initiative — it exists only because MCP tooling can't clear an issue's project assignment, so issues created via Claude Code need a non-initiative home.
89	
90	**Do not add a 4th initiative.** The ops slot is not a buffer for overflow from the three initiative slots; it is a deliberate reservation for non-initiative work that would otherwise eat into initiative time unplanned. The ops container project is not an initiative either — it doesn't get a Goal, KRs, or appetite, and it never enters the Done state.
91	
92	### Cycle planning
93	
94	On planning day:
95	1. Confirm 3 initiatives are in Ready state (six-field check passes for each: Goal + Key results with sub-fields + Affected repos + Appetite + Kill condition + Project type).
96	2. Identify the ops slot: pull 2–5 issues from the team backlog (bugs, maintenance, one-offs) into the cycle as standalone issues.
97	3. For each initiative, confirm which issues in its backlog will be worked this cycle. Do not try to clear the entire initiative backlog in one cycle — prioritise by what moves a Key Result.
98	4. Assign all confirmed issues to the cycle.
99	
100	### Cycle close
101	
102	At cycle end, for each initiative:
103	- If all key results hold (or were definitively ruled out): mark initiative Done. Write one sentence in the Linear project description noting what was observed.
104	- If the work shipped but KRs didn't hold yet: note this; either carry the initiative into the next cycle (Active) or pause it for a retrospective.
105	- If the initiative is being killed: mark Cancelled with a one-sentence reason. This is a normal outcome, not a failure.
106	
107	---
108	
109	## Backlog
110	
111	**Backlog = team issues with no project assigned, plus issues in the ops container project.**
112	
113	Issues enter the backlog when:
114	- They don't belong to any current initiative
115	- They surface mid-flight as non-initiative work (bugs, one-offs)
116	- An initiative is killed and its remaining issues are descoped
117	
118	Issues leave the backlog at cycle planning: either assigned to an initiative project, pulled into the ops slot for the current cycle, or explicitly deferred to a future cycle.
119	
120	The backlog is not the idea bank. The idea bank holds unvalidated product hypotheses. The backlog holds concrete issues that are ready to be worked but not yet assigned.
121	
122	---

124	## Issue workflow
125	
126	### On start
127	
128	- Move to **In Progress** via `mcp__claude_ai_Linear__save_issue`.
129	- If the issue isn't yet in the current cycle and you intend to ship it this cycle, assign it to the current cycle.
130	- Every issue must be either (a) assigned to an initiative project, or (b) explicitly in the ops slot — meaning either no project assigned, or in the ops container project. An issue with neither an initiative nor an ops home is untracked — don't let this happen.
131	- If the issue names a delegate (a `Delegates to` / `▶ On pickup` line), invoke that skill **before writing code** to expand the node into its build tasks — `planning-and-task-breakdown` for build stories, the named skill otherwise. 132	
133	### On completion
134	
135	Before an issue moves to **Done**:
136

138	2. **Summary comment** — Post a short comment on the Linear issue via `mcp__claude_ai_Linear__save_comment` with the review summary (count of findings by severity, plus what was fixed vs deferred).

142

144	
145	Leave In Progress. Add a blocker comment naming the blocker explicitly. Don't silently park work.

152	- **Bug or one-off** (< 5 issues, no sustained goal): create the issue on the team backlog. If it's urgent, pull it into the current cycle's ops slot.

157	
158	- **Project name**: goal or problem name, not a solution name and not a repo name.
159	  - Good: "Equity analysis report — usability for non-analysts"

196	## What this model replaces
197	
198	The previous model used repo-named Linear projects (e.g. "PDE skill pack", "Equity skill pack") as de-facto issue containers. 199	
200	The new model uses:
201	- **Projects** = initiatives (goal + key results + appetite)
202	- **Team backlog** = issues not yet assigned to an initiative
203	- **Cycles** = sprint cadence pulling 3 initiatives + 1 ops slot

2	
3	This rule applies to every issue, regardless of tracker. Before any piece of work is declared done, the following steps must run in order.

7	## The gate
8

11	3. **Commit + push** — Commit the reviewed version and push to the remote branch. Work that exists only locally is not done.
12	
13	The gate is sequential: Review → Fix → Commit + push. Skipping or reordering is not permitted.
14	
15	---
16	
17	## Rationale
18	
19	The gate exists because "compiles and tests pass" is not the same as "correct, maintainable, and safe to merge." Critical findings left unaddressed become production incidents; unreviewed pushes bypass the only asymmetric-judgement checkpoint in an agentic workflow. The gate makes the review step non-negotiable and its output visible (via the completion summary posted by the caller).
20	
21	---
22	
23	## Caller responsibilities
24	
25	After the gate completes, the caller (the issue workflow, the skill, the human) is responsible for:
26	- Posting a completion summary that states the count of findings by severity and what was fixed vs deferred.
27	- Transitioning the work item to its terminal state in the tracker.
28	
29	These steps are tracker-specific and are documented in the tracker's workflow rules (e.g. `linear-workflow.md`).

# Exec: pickup

## Purpose

Take a freshly-picked Linear issue all the way to a finished PR with a full review trail. This skill reads the issue, writes a handoff envelope, and then delegates each step — breakdown, build, review, verify, finish — to its owning `exec:*` skill by name. It inlines no procedure; the named delegation is the whole of each step. The issue's acceptance criteria travel inside `pickup-envelope.json` from pickup to the spec-compliance persona in `exec:review`, re-typed by no one and lost by no one.

## When to use

- A Linear issue is assigned and a worktree is open.
- A drain-cycle supervisor prompt points here as its single execution pointer.
- A worker picking up an issue fresh wants the complete execution path without improvising.

## Do not use when

- **Only reviewing a diff** — use `exec:review` directly.
- **Only finishing an already-built PR** — use `exec:finish` directly.
- **Shaping or planning** — use `shape:delivery`, `shape:initiative`, or `shape:plan-review`.
- **Exploratory spikes or design work** — use `shape:design`; this skill assumes the work is broken down and ready to build.

## Inputs

- **Issue ID** — a Linear issue identifier (e.g. `ABA-363`)
- **Worktree path** — where the issue branch is checked out
- **Branch name** — the git branch for this issue
- **Parent branch** — `main`, or the parent branch in the stack if this work stacks on another issue

## Outputs

- **`pickup-envelope.json`** at the worktree root — the handoff carrier for every downstream step
- An ordered task list from `exec:breakdown`, each task carrying a `done_when` clause
- Delegations to `exec:build`, `exec:review`, `exec:verify`, and `exec:finish`
- On blocked: a Linear comment naming the blocker; issue left In Progress

## Workflow

### 1. Gate: read the issue

Load the issue from Linear (`mcp__claude_ai_Linear__get_issue`) and extract `issue_id`, `body_md`, `ac_checklist[]` (every Done-when / acceptance line, verbatim), `labels[]`, and `blocked_by[]`. If the issue cannot be read, halt with a comment naming the failure.

### 2. Gate: check for blockers

If `blocked_by[]` is non-empty, invoke `shape:stop-the-line`: post a comment naming each blocker, leave the status In Progress, and halt. Do not proceed to breakdown.

### 3. Rebase onto the parent branch

Determine the parent branch — `main` by default, or the parent branch in the stack if this work stacks on another issue — and rebase the worktree branch onto it before any build begins. Building on a stale base produces conflicts at finish; rebase at pickup, on fresh context, instead. Record the chosen parent in `parent_branch`.

### 4. Write the envelope

Write `pickup-envelope.json` (see Artefact template) to the worktree root. This file is the contract — every downstream skill reads it; none re-reads the Linear issue.

### 5. Gate: invoke `exec:breakdown`

Delegate to `exec:breakdown`, passing the envelope. It returns an ordered task list, each task carrying `id`, `done_when` (one verifiable clause), `model_tier`, and `axes` (RC·SC·HS·SR·OR). If it returns no tasks or any task lacks `done_when`, halt and comment naming the gap.

### 6. Build each slice with `exec:build`

For each task in order, delegate to `exec:build` with the task and the envelope path. `exec:build` owns the RED → GREEN → commit loop, including `exec:debug` on a stuck red loop and `exec:simplify` on green. Do not advance until the task's `done_when` is satisfied and a commit exists.

### 7. Gate: invoke `exec:review`

After all slices are committed, delegate to `exec:review` with the working-tree diff and the envelope path (so the spec-compliance persona reads `ac_checklist` directly). On `NO-GO`, loop back into `exec:build` on the failing findings. Do not proceed until the verdict is `GO`.

### 8. Gate: invoke `exec:verify`

Delegate to `exec:verify` with the envelope's `ac_checklist` and the diff. A fail loops back into `exec:build`; a pass is the green light for finishing.

### 9. Invoke `exec:finish`

32	Project type:   [1: methodology | 2: personal product | 3: utility skill pack |
33	                 4: research/thesis | 5: equity research | 6: production]
34	```
35	
36	The format is OKR-shaped: the Goal is the Objective (qualitative, what we want to achieve), and Key results are the 3–5 observable states that must be true for the initiative to be Done. KRs are written so a future agent (or you on a fresh session) can verify each by looking at the system — no "improve X" / "better Y" language. Each KR carries four sub-fields (baseline / target / window / source) and a `[committed|aspirational]` tag that sets the grading bar at cycle close.
37	
38	If any of the six fields can't be filled, the initiative is not ready. Create it as a Draft in Linear but don't assign it to a cycle.
39	
40	### Initiative size
41	
42	| Size | Issue count | Notes |
43	|---|---|---|
44	| Too small | < 5 | Not an initiative — create a standalone issue or put it in the ops slot |
45	| Small | 5–8 | One cycle slot with room left for other initiatives |
46	| Medium | 9–12 | One full cycle slot |
47	| Large | 13–15 | Full cycle slot; very little room for anything else |
48	| Too large | > 15 | Split into two initiatives before committing |
49	
50	### Initiative lifecycle
51	
52	| State | Meaning |
53	|---|---|
54	| **Draft** | Idea exists; goal or criterion not yet written |
55	| **Ready** | All six fields confirmed — Goal + Key results (with sub-fields + tags) + Affected repos + Appetite + Kill condition + Project type; can enter a cycle |
56	| **Active** | Assigned to the current cycle; work in progress |
57	| **Done** | Success criterion observed (or definitively ruled out) — not just issues closed |
58	| **Paused** | Deprioritised mid-cycle; carries over with a note on why |
59	| **Canceled** | Kill condition triggered, or initiative definitively ruled out mid-cycle; one-sentence reason recorded |
60	
61	**Done ≠ all issues closed.** An initiative closes when the key results are observed (or definitively ruled out) — not when its issue list reaches zero. An initiative that shipped everything but the KRs didn't hold is not Done; it is Paused for a retrospective.
62	
63	### Creating an initiative
64	
65	If the Shaper pack is installed, use the `/initiative-shape` skill — it enforces the six-field check (including the verification rubric gate) before creating the Linear project.
66	
67	If Shaper is not installed, follow the [Capturing a shaped initiative in Linear](#capturing-a-shaped-initiative-in-linear) procedure below, filling the six fields manually before calling the Linear API.
68	
69	Direct creation without filling all six fields is permitted only for: maintenance buckets, ops slots, and one-off standalone issue groupings.
70	
71	---
72	
73	## Cycle model
74	
75	A cycle is 3–4 working days of focused work plus 1 planning day.
76	
77	### Cycle composition
78	
79	Every cycle has **exactly four slots**:
80	
81	| Slot | Type | Goal/criterion required? |
82	|---|---|---|
83	| Initiative 1 | Goal-oriented | Yes |
84	| Initiative 2 | Goal-oriented | Yes |
85	| Initiative 3 | Goal-oriented | Yes |
86	| Ops slot | Maintenance | No |
87	
88	The ops slot is not an initiative. It exists for: bug fixes, compliance items, emergent issues, one-offs, and KTLO work. Ops slot issues either have no project assigned, or live in the team's **ops container project** — a perpetual Backlog-state project named e.g. "Ops — bugs, maintenance, emergent" that holds ops work. The container project carries no Goal and no Key Results because it is not an initiative — it exists only because MCP tooling can't clear an issue's project assignment, so issues created via Claude Code need a non-initiative home.
89	
90	**Do not add a 4th initiative.** The ops slot is not a buffer for overflow from the three initiative slots; it is a deliberate reservation for non-initiative work that would otherwise eat into initiative time unplanned. The ops container project is not an initiative either — it doesn't get a Goal, KRs, or appetite, and it never enters the Done state.
91	
92	### Cycle planning
93	
94	On planning day:
95	1. Confirm 3 initiatives are in Ready state (six-field check passes for each: Goal + Key results with sub-fields + Affected repos + Appetite + Kill condition + Project type).
96	2. Identify the ops slot: pull 2–5 issues from the team backlog (bugs, maintenance, one-offs) into the cycle as standalone issues.
97	3. For each initiative, confirm which issues in its backlog will be worked this cycle. Do not try to clear the entire initiative backlog in one cycle — prioritise by what moves a Key Result.
98	4. Assign all confirmed issues to the cycle.
99	
100	### Cycle close
101	
102	At cycle end, for each initiative:
103	- If all key results hold (or were definitively ruled out): mark initiative Done. Write one sentence in the Linear project description noting what was observed.
104	- If the work shipped but KRs didn't hold yet: note this; either carry the initiative into the next cycle (Active) or pause it for a retrospective.
105	- If the initiative is being killed: mark Cancelled with a one-sentence reason. This is a normal outcome, not a failure.
106	
107	---
108	
109	## Backlog
110	
111	**Backlog = team issues with no project assigned, plus issues in the ops container project.**
112	
113	Issues enter the backlog when:
114	- They don't belong to any current initiative
115	- They surface mid-flight as non-initiative work (bugs, one-offs)
116	- An initiative is killed and its remaining issues are descoped
117	
118	Issues leave the backlog at cycle planning: either assigned to an initiative project, pulled into the ops slot for the current cycle, or explicitly deferred to a future cycle.
119	
120	The backlog is not the idea bank. The idea bank holds unvalidated product hypotheses. The backlog holds concrete issues that are ready to be worked but not yet assigned.
121	
122	---
123	
124	## Issue workflow
125	
126	Linear is authoritative for issue status. Local task lists are fine for within-session bookkeeping; they never replace updating the Linear issue itself.
127	
128	### On start
129	
130	- When picking up work, prefer issues already in the current cycle. If you start something not in the cycle, decide explicitly whether to pull it in or defer — don't silently expand cycle scope.
131	- Move to **In Progress** via `mcp__claude_ai_Linear__save_issue`.
132	- If the issue isn't yet in the current cycle and you intend to ship it this cycle, assign it to the current cycle.
133	- Every issue must be either (a) assigned to an initiative project, or (b) explicitly in the ops slot — meaning either no project assigned, or in the ops container project. An issue with neither an initiative nor an ops home is untracked — don't let this happen.
134	- If the issue names a delegate (a `Delegates to` / `▶ On pickup` line), invoke that skill **before writing code** to expand the node into its build tasks — `planning-and-task-breakdown` for build stories, the named skill otherwise. Issues with no delegate, and `ktlo` issues, carry no breakdown step.
135	
136	### On completion
137	
138	Before an issue moves to **Done**:
139	
140	1. **Review → Fix → Commit + push** — follow the gate in `rules/code-review.md` exactly.
141	2. **Summary comment** — Post a short comment on the Linear issue via `mcp__claude_ai_Linear__save_comment` with the review summary (count of findings by severity, plus what was fixed vs deferred).
142	3. **Done** — Transition to Done via `mcp__claude_ai_Linear__save_issue`.
143	
144	Status updates happen at the moment of state change — not batched at the end of a session.
145	
146	### Blocked
147	
148	Leave In Progress. Add a blocker comment naming the blocker explicitly. Don't silently park work.
149	
150	### New work surfaced mid-flight
151	
152	Two cases:
153	
154	- **Initiative-shaped** (5+ issues, clear goal): create a new Linear project. If Shaper is installed, use `/initiative-shape`; otherwise follow the [Capturing a shaped initiative in Linear](#capturing-a-shaped-initiative-in-linear) procedure. Slot it into the next cycle explicitly — don't silently expand the current cycle's scope.
155	- **Bug or one-off** (< 5 issues, no sustained goal): create the issue on the team backlog. If it's urgent, pull it into the current cycle's ops slot.
156	
157	---
158	
159	## Linear project conventions
160	
161	- **Project name**: goal or problem name, not a solution name and not a repo name.
162	  - Good: "Equity analysis report — usability for non-analysts"
163	  - Bad: "stock-review", "stock-explain feature", "agent-skills-workflow v2"
164	- **Project description**: always uses the six-field initiative format (goal / key results with sub-fields / affected repos / appetite / kill condition / project type).
165	- **Project state**: Planned until it enters a cycle; In Progress when active; Completed or Cancelled on close.
166

169	## Capturing a shaped initiative in Linear
170	
171	This procedure records a fully shaped initiative in Linear. It is called:
172	- By `/initiative-shape` (Shaper pack) as its final capture step.
173	- Directly when Shaper is not installed and the six fields have been filled manually.
174	
175	**Precondition:** All six fields are complete and verified (Goal, Key results with sub-fields, Affected repos, Appetite, Kill condition, Project type). Do not call this procedure with partial fields.
176	
177	If the Shaper pack is installed, the canonical six-field shape definition and the verification rubric live in Shaper's `initiative-shape` skill. Refer there for what constitutes a valid field. If Shaper is not installed, use the format shown in the [initiative model section](#the-initiative-model) above as the inline fallback.
178	
179	### Steps
180	
181	1. **Create the Linear project** via `mcp__claude_ai_Linear__save_project`:
182	   - `name`: the initiative goal name (not a repo name, not a solution name)
183	   - `description`: the full six-field block, formatted exactly as shown in the initiative model section
184	   - `state`: `"planned"` (do not set to active until it enters a cycle)
185

187	   - Assign each to the project created in step 1
188	   - Leave cycle unset (cycle assignment happens at planning day)
189	   - Set status to `"Backlog"`
190	
191	3. **Confirm** by reading back the project (`mcp__claude_ai_Linear__get_project`) and verifying the description persisted correctly.
192	
193	### After capture
194	
195	The project is in Draft or Planned state. It enters a cycle at planning day after the six-field check passes again at that time (context may have changed). Do not auto-assign to the current cycle on creation.
196

198	
199	## What this model replaces
200	
201	The previous model used repo-named Linear projects (e.g. "PDE skill pack", "Equity skill pack") as de-facto issue containers. These were not initiatives — they had no goal sentences, no key results, and no appetite. Work was tracked by repo rather than by outcome, making cross-repo initiatives invisible and preventing meaningful cycle planning.
202	
203	The new model uses:
204	- **Projects** = initiatives (goal + key results + appetite)
205	- **Team backlog** = issues not yet assigned to an initiative
206	- **Cycles** = sprint cadence pulling 3 initiatives + 1 ops slot
