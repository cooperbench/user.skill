<title>drain-cycle: a live run is uninspectable — `active.json` marker + `status` command</title>
<description>
## Problem

A running `drain-cycle` is hard to observe. Mid-issue there is almost no signal: the run-log gains an entry only when an issue *finishes*, the orchestrator prints only three sparse stderr lines, and there's no way to inspect from a second terminal or when the run was launched detached. The operator cannot tell a working run from a hung/runaway one.

## Change

Builds on the streamed worker (<issue id="eb62c999-a798-4055-9d3c-7993542fbdf8">ABA-236</issue>), so the live view is **token-aware**:

1. **Active-issue marker** (`drain_cycle/progress.py`) — the orchestrator writes `~/.drain-cycle/active.json` just before each spawn and clears it as soon as the worker returns (try/finally over done/halt/timeout/breach). Lives **above** `runs/` so `grade`'s `runs/*.json` glob never sees it. Carries: `pid`, `cycle_id`, `run_log_path`, `issue{identifier,title,repo,worktree_path}`, `model`, `started_at`, `index`, `total`, and a live `progress` block updated on every stream event (`turns`, `cumulative_tokens`, `peak_context_tokens`, `cost_usd`, `elapsed_seconds`, `last_event_at`).
2. `drain-cycle status` (`drain_cycle/status.py`) — reads the marker from any terminal: which issue, repo, model, `[index/total]`, elapsed, turns, and **tokens (cumulative + peak) with cost shown together** against the configured caps (e.g. `12.4M / 8M ⚠`). Detects a stale marker (pid gone → crashed/killed) and a no-marker state (points at `grade`).
3. **Compact stderr progress line** per stream event for terminal-watching, e.g. `ABA-205 · turn 42 · 8.1M tok (peak 180k) · $12.30 · 14m`.

## Acceptance criteria

* `drain-cycle status` during a run shows the current issue, repo, model, elapsed, turns, cumulative + peak tokens, and cost — vs caps.
* `drain-cycle status` with no run prints a no-active-run message and exits 0.
* A stale marker (pid not alive) is reported as such, not as a live run.
* Marker written before spawn, removed after the worker returns on every exit path.
* `grade` output is unaffected by the marker file.
* New tests for `progress`, `status`, the orchestrator marker lifecycle, and the `status` CLI dispatch; full suite green.

## Recommended worker model

**Sonnet** — moderate, well-specified.

## Files

`drain_cycle/progress.py` (new), `drain_cycle/status.py` (new), `drain_cycle/orchestrator.py` (marker write/clear + index/total), `drain_cycle/cli.py` (`status` dispatch + usage), `tests/`, `README.md`, `docs/design-decisions.md` (marker-location decision).

Depends on the streamed worker (<issue id="eb62c999-a798-4055-9d3c-7993542fbdf8">ABA-236</issue>) for the live token feed.

311	class _UsageAccumulator:
312	    """Reconstruct session usage from the streamed events.
313	
314	    Per-turn usage is keyed by ``message.id`` so a turn emitted once per
315	    content block is counted once; the last copy wins (later events carry
316	    the more complete snapshot). The ``result`` event overwrites the
317	    session-summary fields each time it is seen.

320	    main thread after it is joined — but the join is bounded, so a group
321	    member that escaped the kill (e.g. via ``setsid``) could keep the
322	    reader alive past the join. The lock makes the concurrent case safe
323	    rather than a ``dictionary changed size during iteration`` crash.
324	    """
325	
326	    def __init__(self) -> None:
327	        self._lock = threading.Lock()
328	        self._turns: dict[str, dict[str, int]] = {}
329	        self._anon = 0
330	        self.cost_usd: float | None = None
331	        self.num_turns: int | None = None
332	        self.session_id: str | None = None
333	        self.is_error: bool | None = None
334	
335	    def feed(self, event: dict[str, Any]) -> None:
336	        event_type = event.get("type")
337	        if event_type == "assistant":
338	            self._feed_assistant(event)
339	        elif event_type == "result":
340	            self._feed_result(event)
341	
342	    def _feed_assistant(self, event: dict[str, Any]) -> None:
343	        message = event.get("message")
344	        if not isinstance(message, dict):
345	            return
346	        usage = message.get("usage")
347	        if not isinstance(usage, dict):
348	            return
349	        message_id = message.get("id")
350	        turn = {field: _coerce_int(usage.get(field)) for field in _TOKEN_FIELDS}
351	        with self._lock:
352	            if isinstance(message_id, str):
353	                key = message_id
354	            else:
355	                key = f"_anon-{self._anon}"
356	                self._anon += 1
357	            self._turns[key] = turn
358	
359	    def _feed_result(self, event: dict[str, Any]) -> None:
360	        with self._lock:
361	            self.cost_usd = event.get("total_cost_usd")
362	            self.num_turns = event.get("num_turns")
363	            self.session_id = event.get("session_id")
364	            self.is_error = event.get("is_error")

366	    def cumulative(self) -> int:
367	        """Live billed-token total across turns — the per-issue token cap is
368	        compared against this on every poll, so it reads under the lock and
369	        stays cheap (no peak-context / per-component breakdown)."""
370	        with self._lock:
371	            turns = list(self._turns.values())
372	        return sum(turn[field] for turn in turns for field in _TOKEN_FIELDS)

## Why this exists

Today, executing a Linear cycle is manual: launch Claude per issue, watch it run, approve permissions, update Linear, repeat. ## 10. Headless workers inherit project-scoped config by symlink

The operator noticed entire.io's checkpointing didn't take effect during a headless drain. The hypothesis was that the worker's worktree cwd (`.worktrees/<id>`) diverges from an interactive session at the repo root. A reproduction run confirmed the divergence and sharpened the cause (below); the resolution is to symlink the repo's project-scoped config into each worktree at spawn, restoring parity.

**What was observed (claude 2.1.150).** Running `claude -p --debug-file <path>` from the repo root vs. from a fresh `git worktree` of the same repo, then diffing the debug logs:

| | Repo root | Worktree |
|---|---|---|
| Settings files watched | user `~/.claude/settings.json` + **project** `.claude/settings.json` + `.claude/settings.local.json` | **user only** |
| Project `.claude/settings.json` | loaded | "Broken symlink or missing file encountered" |
| entire.io hooks | SessionStart + SessionEnd fire ("Entire CLI will link this conversation to your next commit") | **absent — zero references** |
| User-scoped plugins (crit, hookify, agent-skills, security-guidance) | "Registered 7 hooks from 15 plugins" | **identical: "Registered 7 hooks from 15 plugins"** |

**The cause is project-scoped registration in a gitignored file — not cwd alone, and not plugins generally.** entire registers its hooks in the project-scoped `.claude/settings.json`. That file is gitignored (`.gitignore` ends with `.claude`). A `git worktree` is a fresh checkout of *tracked* files only, and git reports the worktree directory as its own `--show-toplevel`, so Claude Code resolves the project root to the worktree and finds no `.claude/` there. User-scoped plugins and MCP servers — registered under `~/.claude/` — are cwd-independent and load identically in both, which is why the symptom looked like "some plugins" rather than "all hooks": only the project-scoped ones drop out. The original hypothesis (worktree cwd) was right that cwd is involved, but the operative mechanism is the gitignored project-settings file, not cwd by itself; were `.claude/settings.json` tracked, the worktree checkout would carry it.

**Reproduction step (one-shot).** From a target repo with project-scoped hooks registered in `.claude/settings.json`:

claude -p --debug-file /tmp/root.debug.log --model claude-sonnet-4-6 \
  --max-budget-usd 0.50 "Reply with exactly: ok"

# Fresh worktree — the worker's actual cwd
git worktree add -b repro .worktrees/repro main
( cd .worktrees/repro && claude -p --debug-file /tmp/worktree.debug.log \
    --model claude-sonnet-4-6 --max-budget-usd 0.50 "Reply with exactly: ok" )
git worktree remove --force .worktrees/repro && git branch -D repro

# Diff the loaded settings/hooks. The worktree run is missing the project
# settings file and any hook registered in it.
grep -iE 'settings.json|Registered .* hooks|<your-plugin-name>' /tmp/root.debug.log

The same capture is wired into the worker as an opt-in: `DRAIN_CYCLE_DEBUG=1 drain-cycle` passes `--debug-file` to every spawned session, landing one `<run-log-stem>-<issue>.debug.log` per issue beside the run log in `~/.drain-cycle/runs/`. It is off by default — the diagnostic is for one-shot investigation, not steady-state overhead, and debug output goes to the file rather than stderr so the usage parser's stream is unaffected.

**Decision — symlink a configurable set of project config into each worktree.** The earlier hesitation was upstream of the mechanism: it wasn't obvious headless checkpointing was even *wanted*, since a `drain-cycle` worktree is a throwaway branch. That resolved in favour of wanting it — the checkpoint links a session to the commit it produces, and that commit is pushed to `main` before the worktree is removed, so the link outlives the branch. The operator wants the same project tooling headless as interactively.

After `worktree.add`, the orchestrator calls `worktree.link_project_config`, which symlinks the repo's real project-config entries into the new worktree. Because each link points at the live dir, the worker reads *and writes* the repo's actual config exactly as a non-worktree run does — so a stateful hook like entire's checkpointing works and persists. Teardown needs no special handling: `git worktree remove` deletes the worktree directory and its symlinks but not the link targets, so the repo's real `.claude/` and `.entire/` survive.

This depends on a precondition: every configured path must be gitignored in the target repo.
