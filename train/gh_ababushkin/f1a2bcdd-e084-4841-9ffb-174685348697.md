<title>Recalibrate /stock-signal GARP thresholds per profit_stage × ai_layer</title>
<description>
## Problem

`/stock-signal` uses a single universal PEG/PS threshold band to assign GARP verdicts (PASS / WATCH / CAUTION / FAIL). The thresholds are calibrated for a small-cap GARP screen (PEG ≤ \~2 = PASS), which systematically mis-classifies:

* **Mature mega-caps** (GOOG, AMZN, META at scale): structurally can't grow earnings >10%/yr from a $1T+ base, so PEG sits at 3–4 indefinitely — the universal gate treats this as CAUTION even when the qualitative read is healthy.
* **Premium-multiple quality compounders** (ASML monopoly, NFLX pricing power, [ADYEN.AS](<http://ADYEN.AS>) European moat): the market correctly pays a premium for durability that PEG can't see.

Result: 5 of 7 COVERAGE.md tickers get `model_ready=NO` for structural rather than informational reasons. <issue id="0b887766-037e-4080-abe7-a7f76eeecde8">ABA-130</issue> ships the immediate bypass for covered tickers; this issue fixes the underlying mis-calibration so the gate works correctly for *all* tickers.

## Approach (multi-slice)

**Slice 1 — Calibration design.** Decide the segmentation (likely `profit_stage × ai_layer`, possibly with a market-cap bucket overlay) and pick new PEG/PS bands per cohort with documented rationale. Inputs: historical PEG/PS distributions over 5–10y for representative names in each cohort (mega-cap incumbents, infrastructure picks-and-shovels, application SaaS, emerging growth). Output: a threshold table in a design note. Load-bearing slice — without this the implementation is guessing.

**Slice 2 — Implementation.** Replace universal threshold constants in `/stock-signal` with a profile-keyed lookup. Preserve old thresholds as the fallback when profile is unknown. Update `qualitative_note` generation to reference the cohort and the band that fired.

**Slice 3 — Verification + docs.** Re-run signal on all 7 covered tickers plus 2–3 off-coverage controls (one EMERGING, one outside-tech). Confirm verdicts now align with qualitative reality. Update DESIGN.md + `/stock-signal` SKILL.md with the new bands and rationale. Remove the coverage-bypass note from <issue id="0b887766-037e-4080-abe7-a7f76eeecde8">ABA-130</issue> once the recalibration carries the load.

## Sequencing with playbook layer

The playbook layer (<issue id="89e1f4f4-8b04-4c5b-9931-7f4f837de45f">ABA-110</issue>/111/112) lands per-ticker overrides (WACC, growth ceiling, terminal margin, scenarios). It could absorb per-ticker threshold overrides too. Two paths:

1. **Recalibrate first, playbooks override later.** Universal thresholds get better for everyone; playbooks fine-tune for specific names. Recommended — recalibration helps off-coverage tickers too, which playbooks won't.
2. **Skip recalibration, let playbooks carry it.** Cheaper but leaves the gate mis-calibrated for the long tail of off-coverage tickers users actually run on.

Default to path 1 unless <issue id="89e1f4f4-8b04-4c5b-9931-7f4f837de45f">ABA-110</issue>/111/112 land sooner than expected.

* Off-coverage spot checks: at least one EMERGING and one out-of-band ticker still get the gate enforced correctly.
* Coverage-bypass shim from <issue id="0b887766-037e-4080-abe7-a7f76eeecde8">ABA-130</issue> can be removed; covered tickers should now pass naturally.

467	## 9. Tech-Specific Rules
468	
469	**SBC stripping (mandatory):**
470	- SBC is step zero before any earnings calculation. Always retrieve `Stock Based Compensation` from `get_financials` and compute per-share SBC before applying any multiple.
471	- Never list SBC alongside other one-offs. It is its own line item in the output.
472	- Never skip SBC stripping on grounds that SBC is "immaterial" — always check, always compute or report N/A with reason.
473	
474	**AI layer classification:**
475	See decision tree and examples in Section 4, Step 2. Classification is pure qualitative reasoning — no MCP call required.
476	
477	**TAM penetration and AI optionality:**
478	
479	TAM penetration check fires only for INFRASTRUCTURE companies. AI optionality flag fires only for INCUMBENT companies. Neither fires for APPLICATION, MODEL, or N/A layers.
480	
481	TAM penetration rules:
482	- Use the company's annualised data centre / AI hardware revenue as the numerator. If segment detail is unavailable from `get_financials`, use the most recent publicly reported figure and flag it as an estimate.
483	- Use $150–400B as the 2025–2026 data centre GPU TAM range; pick a stated point estimate and state it explicitly. Do not assert precision — this is a qualitative estimate.
484	- Penetration > 50%: Qualitative = FLAG (or FAIL if primary lens = CAUTION). State "TAM ceiling risk."
485	- Penetration 30–50%: Qualitative unchanged; note "approaching ceiling."
486	- Penetration < 30%: Qualitative unchanged; note "meaningful runway."
487	- Always output the TAM/Optionality line for INFRASTRUCTURE companies.
488	
489	AI optionality rules:
490	- Use TTM capex from `get_financials` as the base. Qualitatively estimate the AI-attributed fraction; state the fraction and its basis explicitly.
491	- Apply a 5× revenue multiple on AI capex as the premium proxy. Always state this assumption.
492	- AI optionality premium % = (AI capex × 5) ÷ market cap × 100.
493	- The percentage must always be a computed number in the output. Never omit it, never write N/A, never write "not applicable."
494	- Premium > 20%: Qualitative = FLAG. State "AI capex implies a significant unverified optionality premium; buyer should verify AI monetisation path."
495	- Premium ≤ 20%: Qualitative unchanged. Note "AI investment appears proportionate to core business value."
496	- Always output the TAM/Optionality line for INCUMBENT companies.
497	
498	**Three-lens valuation hierarchy:**
499	- For ESTABLISHED companies: use PEG as the primary signal lens when available. Fall back to P/S if PEG = N/A. Never silently switch lenses — always state which lens is active and why.
500	- For EMERGING companies: P/S is always the primary lens. PEG is never applicable. P/E is never applicable. State this explicitly in the output.
501	- The fallback chain is: PEG → P/S. There is no P/E-only lens — P/E only appears as an intermediate step in computing clean forward P/E for the PEG numerator.
502	
503	**Pre-profit / EMERGING rules:**
504	- Never apply P/E or PEG to EMERGING companies — mathematically undefined or misleading.
505	- Rule of 40 is the primary supplementary filter for EMERGING SaaS (not yet implemented).
506	- P/S is the primary ratio for EMERGING at all times.
507	
508	**Track:**
509	- Growth track is the default for all tech companies.
510	- Yield track is dormant. Do not apply it unless the user explicitly requests it and the thesis is genuinely income-oriented.

524	
525	| Rationalisation | Rebuttal |
526	|---|---|
527	| "SBC is small for this company so I'll skip stripping it" | SBC stripping is mandatory step zero in every run. The amount is always noted. Skipping it silently is the exact failure mode the rule exists to prevent. |
528	| "P/E is negative but this company clearly has earnings" | If yfinance returns a negative or null P/E, classify as EMERGING. A negative P/E signals something unusual — the pre-profit path is the safe default. |
529	| "I'll apply PEG to this pre-profit company because it has a useful forward estimate" | PEG requires positive trailing earnings. For EMERGING companies PEG is undefined. Use P/S only. |
530	| "The stub fields are not computed so I'll just omit them from the SIGNAL OUTPUT block" | Every field must appear every run. Omitting a field breaks the output contract that `/stock-model` depends on. Use the placeholder text. |
531	| "MODEL_READY = YES because the signal looks good even though stub fields are pending" | If any of Clean EPS, Rule of 40, or AI layer are pending, MODEL_READY is at most CONDITIONAL. The condition line must explain what needs confirming. |
532	| "PEG is available so I can skip P/S entirely" | P/S must always be fetched and reported. P/S is the fallback lens and is always present in the output block regardless of whether PEG is computed. |
533	| "I'll use a raw P/E from yfinance as my PEG numerator" | The PEG numerator is clean forward P/E — computed from NTM EPS minus per-share SBC. Never use reported P/E directly as the PEG numerator. |
534	| "g is small so I'll round up to avoid a very high PEG" | Compute g exactly and report the result honestly. A very high PEG is a valid signal — do not adjust it. |
535	| "I'll infer the AI layer from my training data rather than computing it" | AI layer classification is a qualitative filter requiring current context. In the stub, output the placeholder. Do not hallucinate a classification. |
536	| "I'll look up AI layer from a hardcoded table" | Classification is qualitative reasoning, not a lookup. Apply the decision tree and state your reasoning. The output is only as good as the argument you make. |
537	| "A report file already exists for this ticker today, I'll skip writing" | Always write. The user may be re-running with updated data or correcting a prior run. Read-modify-write if the file exists. |
538	| "yfinance returned null for P/S — I'll estimate from sector average" | Forbidden. Fire the Manual Input Protocol (`skills/_shared/MANUAL_INPUT_PROTOCOL.md`) and ask the user to paste the value. Ask, don't assume. |

543	| "SBC per share looks tiny — probably a unit mismatch but I'll proceed anyway" | yfinance returns SBC in raw dollars (not thousands or millions) and shares outstanding in units. 544	| "I'll skip the TAM/optionality check since it's qualitative anyway" | These checks are required for INFRASTRUCTURE and INCUMBENT companies respectively. The AI optionality premium percentage must be present and non-null for every INCUMBENT. Skipping a qualitative check because it's qualitative is the exact failure mode it was designed to prevent. |
545	| "The AI optionality premium percentage is hard to estimate so I'll write N/A" | The percentage must always be a computed number. Estimate AI capex fraction from context, apply the stated 5× proxy, divide by market cap. State your assumptions. N/A is never acceptable for this field on INCUMBENT companies. |
546	| "The TAM estimate is uncertain so I'll omit the TAM/Optionality line" | Uncertainty is exactly why this is a qualitative note rather than a precise metric. State the range ($150–400B), pick a point estimate, state your assumption, and compute the penetration. The output must include the line. |
547	| "RDDT has a positive P/E so I'll mark MODEL_READY: YES" | RDDT is in its first profitable year (transition year). 549	| "Clean EPS is negative so Qualitative must be FAIL and MODEL_READY = NO" | Not when SBC is the sole cause and the company is GAAP-profitable + FCF-positive. 7	## Architecture Overview
8	
9	```
10	/stock-equity    → Router        orchestrates full chain or dispatches to sub-skills
11	/stock-screen    → Screen        fast go/no-go; two variants by profit stage
12	/stock-signal    → Signal        GARP signal analysis; outputs MODEL_READY flag
13	/stock-model     → Model         conviction-building model; two variants by profit stage
14	/stock-timing    → Timing        when-to-act overlay; standalone invocation
15	```
16	
17	Two routing dimensions are inferred before any skill executes:
18	- **Profit stage**: established (>2yr FCF history) vs emerging/pre-profit
19	- **Track**: growth (almost always) vs yield (rare edge case)
20	
21	Router infers both from user phrasing and available data. States its inference. Does not ask.

25	## Namespace Convention
26	
27	All skills in this pack are namespaced under the `stock-` prefix (e.g. `/stock-screen`, `/stock-signal`, `/stock-timing`, `/stock-model`, `/stock-equity`).
28	
29	**Reason:** Generic command names (`/model`, `/review`, `/init`, `/ship`) collide with built-in Claude Code commands and with other installed skill packs. The `stock-` prefix gives the pack a stable, conflict-free namespace. The decision was taken pre-M5 (ABA-71) — `/model` would have shadowed both the built-in model-switcher and `agent-skills:model`. The convention was originally a `stock:` colon-style namespace; ABA-114 switched to `stock-` because the bare slug after the colon (e.g. `model`) still showed up in the loaded-skill list and confused triggering.
30	
31	**Rule:** Every new skill added to this pack MUST use the `stock-` prefix in its SKILL.md `name:` frontmatter field. References to skills in `CHARTER.md`, `DESIGN.md`, `CLAUDE.md`, and other skill descriptions MUST also use the prefixed form. Report JSON schema keys (`stages.screen`, `stages.signal`, etc.) are NOT prefixed — they are JSON keys, not invocations.

81	## Skill Authoring Conventions
82	
83	Each skill file (`skills/*.md`) follows the structure defined in the project brief's "What Each Skill Brief Should Cover" section:
84	
85	1. Identity (name, command, one-sentence purpose)
86	2. Methodology (named approach, source attribution)
87	3. Input schema (required inputs + data-gap handling per field)
88	4. Execution phases: GATHER → VALIDATE → COMPUTE → THRESHOLD → OVERRIDE → OUTPUT
89	5. Output schema (exact fields, every run)
90	6. Data fetching behaviour
91	7. Invocation patterns
92	8. Dependencies
93	9. Tech-specific rules (SBC, AI layer, TAM)
94	10. Override rules (IF/THEN blocks)
95	
96	**Universal rules applied in every skill:**
97	- SBC stripping is step zero before any earnings calculation — never listed alongside other one-offs
98	- AI layer classification (infrastructure / application / model) is applied in qualitative filters
99	- Skills web-search for all inputs before prompting the user
100	- Skills state what they found and what they assumed

104	## Data Layer
105	
106	### MCP Servers
107	
108	**`mcp/yf/` — yfinance (Yahoo Finance)**
109	
110	Primary source for M1 valuation ratios. Free, no API key. Returns TTM ratios via `Ticker.info`.
111	
112	Tools exposed:
113	- `get_ratios(ticker)` → P/E, P/S, EV/EBITDA, P/FCF, EV/Revenue (TTM)
114	
115	Future tools (M2+, if yfinance proves sufficient or before adding paid sources):
116	- `get_financials(ticker, period)` → income / balance sheet / cashflow
117	- `get_estimates(ticker)` → analyst EPS / revenue consensus
118	- `get_earnings_history(ticker, n)` → surprises
119	- `get_analyst_targets(ticker)` → buy/hold/sell distribution
120	
121	If yfinance is too fragile or coverage gaps appear, candidates are Finnhub (free tier, 60 req/min) or a paid FMP plan.
122	
123	**M2 feasibility spike outcome (ABA-47, 2026-05-12).** Probed 10 surfaces × NVDA/META/RDDT. yfinance 1.3.0 covers more than expected — including direct `Stock Based Compensation` rows in cashflow, NTM EPS/revenue consensus, price targets, and multi-year B/S + CF for Piotroski. Three scope changes locked in:
124	
125	- **SUE/PEAD (ABA-28):** `earnings_history` only returns 4 quarters, not 8. v1 SUE uses 4-quarter window; 8-quarter backfill deferred.
126	- **Revision momentum (ABA-29):** `eps_revisions` exposes 7d/30d up/down counts only. v1 uses 7d/30d directly; 60/90d deferred. `upgrades_downgrades` is stale on META (latest 2024-09-30) so it is not used as a primary source.
127	- **Revenue segments (ABA-12):** absent from yfinance entirely. Routed to EDGAR; blocked on EDGAR MCP build.
128	- **Guidance text (ABA-31):** absent from yfinance. v1 substitutes NTM consensus for guidance; transcript/8-K extraction is Later.
129	
130	No third-party source needed for v1. Full feasibility table at `mcp/yf/spike/FEASIBILITY.md`.
131	
132	**`mcp/edgar/` — SEC EDGAR**
133	
134	Authoritative source for: 10-K, 10-Q, 20-F filings, **revenue segments** (primary — yfinance has no segments surface), operating lease obligations, MD&A and risk-factor text, 8-K guidance press releases. Also used as a cross-check on yfinance SBC/capex/D&A when divergence is material.
135	
136	Tools to expose:
137	- `search_filings(ticker, form_type)` → list of recent filings with accession numbers
138	- `get_filing_facts(ticker, concept)` → specific XBRL fact (e.g. StockBasedCompensation)
139	- `get_filing_text(accession_number, section)` → raw text of a filing section (MD&A, Risk Factors)
140	
141	**Scraping layer (no MCP — direct web search)**
142	
143	Used only for: earnings call transcripts (Motley Fool, Seeking Alpha free pages). Skills use the built-in web search tool directly. No separate MCP needed.
144	
145	### Data Priority Chain
146	
147	Source priority is **per-field**, not global. Routing below reflects the ABA-47 spike (2026-05-12):
148	
149	```
150	Ratios (P/E, P/S, EV/EBITDA, P/FCF, EV/Rev, TTM):
151	  1. yfinance  →  2. EDGAR (derived)  →  3. user-provided
152	
153	SBC, capex, D&A, multi-year B/S + CF (Piotroski inputs), FCF history:
154	  1. yfinance (Stock Based Compensation row + cashflow/balance_sheet 4-5y)
155	     →  2. EDGAR XBRL facts (cross-check on material divergence)
156	
157	Revenue segments, operating lease obligations:
158	  1. EDGAR XBRL facts (yfinance does not surface segments)  →  2. drop in v1 if EDGAR blocked
159	
160	Forward / consensus estimates (NTM EPS, NTM revenue, price targets, recs):
161	  1. yfinance (earnings_estimate / revenue_estimate / analyst_price_targets / recommendations_summary)
162	     →  2. user-provided if degraded
163	
164	Earnings surprise history (SUE input):
165	  1. yfinance earnings_history (4-quarter window — v1 scope)
166	
167	EPS revision counts (revision momentum input):
168	  1. yfinance eps_revisions (7d/30d only — v1 scope)
169	     ✗ upgrades_downgrades is unreliable per-ticker (META stale); not used as primary
170	
171	Guidance text, MD&A, risk factors:
172	  1. EDGAR filing text (M2 task)  →  2. web search (transcripts)  →  3. drop and substitute consensus
173	
174	Transcripts, news, qualitative context:
175	  1. Web search  →  2. user-provided
176	```
177	
178	When a skill cannot resolve an input from sources 1–3, it states the gap, uses the most recent available data as a placeholder, sets `CONFIDENCE = MEDIUM` or `LOW`, and asks the user to confirm before proceeding.

182	## Playbook Layer
183	
184	For supported tickers (see `COVERAGE.md`), `/stock-model` loads ticker-specific overrides from `playbooks/TICKER.md` (uppercase ticker symbol; period-suffixed exchange codes preserved verbatim, e.g. `playbooks/ADYEN.AS.md`). Off-coverage tickers run with generic ESTABLISHED / EMERGING defaults. Implementation tracked in ABA-112; blocked by ABA-110 + ABA-111 (correctness fixes must land first so playbook overrides modulate a trustworthy base).
185	
186	**File format.** Markdown with YAML frontmatter.
187	
188	Frontmatter — machine-readable overrides consumed by `/stock-model`:
189	- `base_wacc` — overrides the MIP-asked default (suppresses the WACC question)
190	- `growth_ceiling` — overrides the generic 18% fallback ceiling on base Y2-Y5 CAGR (see ABA-111)
191	- `terminal_margin` — overrides the SBC-stripped TTM margin as the Y5 anchor (see ABA-110)
192	- `scenario_axes` — optional per-scenario overrides (used when the catalyst structure demands discrete outcomes vs smooth scenarios, e.g. "TikTok divested" as a binary)
193	- `narrative.{bear,base,bull}` — replace generic per-scenario one-liners with thesis-grounded narratives
194	- `failure_modes` — surfaced in output as a separate `Monitor:` section
195	- `confidence_anchor` — playbook-set max confidence (e.g. cap NVDA at MEDIUM until customer concentration risk is resolved)
196	
197	Body — human-reference content: business architecture, segment splits, capex-cycle position, active catalysts, sell-side disagreement axes, historical reset-and-recover priors, failure-mode commentary.
198	
199	**Loader behaviour in `/stock-model`** (implementation in ABA-112):
200	
201	1. After GATE passes, before GATHER, check `playbooks/TICKER.md`.
202	2. Absent: emit `No playbook for TICKER — using generic ESTABLISHED/EMERGING logic.` and proceed unchanged.
203	3. Present: load frontmatter, surface `Playbook loaded: playbooks/TICKER.md (last updated YYYY-MM-DD). Overrides applied: [list].` Apply overrides per the hierarchy below; record audit trail in `stages.model.playbook` JSON block.
204	
205	**Override hierarchy.** Playbook beats generic default; runtime user override (e.g. `--wacc=9.0`) beats playbook.
206	
207	**Audit trail.** Every playbook-sourced field appears in `stages.model.playbook.overrides_applied` with the source named. Confidence cap from playbook is the binding cap when stricter than the runtime-derived value. Silent application of any override is forbidden — the OUTPUT block names every overridden field.

211	## Data Contracts Between Skills
212	
213	### Screen → Signal
214	Screen passes PASS-rated tickers as natural language context. No structured schema required — the router re-states the ticker when dispatching.
215	
216	### Signal → Model
217	Signal must emit a structured output block before Model will execute. Required fields:
218	
219	```
220	SIGNAL OUTPUT
221	  Ticker:          [TICKER]
222	  Company:         [Name]
223	  Profit stage:    [ESTABLISHED | EMERGING]
224	  Track:           [GROWTH | YIELD]
225	  AI layer:        [INFRASTRUCTURE | APPLICATION | MODEL | INCUMBENT | N/A]
226	  
227	  Clean EPS (TTM): [$ or N/A]
228	  SBC stripped:    [YES | N/A]
229	  PEG ratio:       [x or N/A — reason if N/A]
230	  P/S ratio:       [x]
231	  Rule of 40:      [score or N/A]
232	  
233	  Qualitative:     [PASS | FLAG | FAIL] — [one-line reason]
234	  
235	  Signal:          [BUY | WATCH | CAUTION]
236	  MODEL_READY:     [YES | CONDITIONAL | NO]
237	  Condition:       [if CONDITIONAL — what the user must confirm]
238	```
239	
240	Model reads this block from context. If it is absent, Model states it cannot proceed and instructs the user to run `/stock-signal [ticker]` first.

348	
349	**Stack:** Vite + React. No backend. Reads report JSON from `reports/` directory (loaded via `fetch` in development, or bundled in future if needed).
350	
351	**Report viewer behaviour:**
352	- Opens the most recently written report JSON by default
353	- Navigation tabs: Screen | Signal | Model | Timing | Summary

356	- Verdict badges: green (BUY / PASS / ACT NOW), amber (WATCH / CONDITIONAL / WAIT FOR CATALYST), red (CAUTION / SKIP / WAIT FOR BETTER ENTRY)
357	- Export button: saves current view as a PDF-ready print layout

363	npm run build     # dist/ for static serving
364	```

392	## Testing Strategy
393	
394	**Methodology validation (primary):** Run each skill against three known reference tickers and manually verify the output matches the expected methodology:
395	- NVDA — established profitable tech, AI infrastructure, large capex
396	- META — established profitable tech, incumbent with AI optionality
397	- RDDT — emerging/pre-profit, recent IPO, limited FCF history
398	
399	**MCP integration tests:** Unit test each tool function against live API responses with known tickers. Snapshot the response schema so regressions in the API structure are caught.
400	
401	**Signal contract test:** Run `/stock-signal NVDA`, capture the output block, confirm all required fields are present and correctly typed before invoking `/stock-model NVDA`.
402	
403	**SBC stripping test:** For a ticker with a known large SBC line (e.g. Salesforce CRM), verify that clean EPS diverges from reported EPS by the expected amount.
404	
405	**UI smoke test:** After any report JSON is written, confirm the UI renders without console errors and all tabs display data.
406	
407	**Coverage backtesting (future, ABA-NEXT):** Quarterly historical replays of `/stock-signal` and `/stock-model` against the supported tickers (`COVERAGE.md`). Grade IV-range coverage of subsequent price action, verdict accuracy, and dominant-driver stability across time. Feeds methodology drift back into the skills per `CHARTER.md` → *Operating Principle* (5).
