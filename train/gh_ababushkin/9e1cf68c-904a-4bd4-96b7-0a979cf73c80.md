<issue identifier="ABA-338">
<title>Watch mode: live tmux pane for spawned Claude sessions</title>
<description>
## What

Add `--watch` / `-w` flag to `drain-cycle` that, for each issue run, writes a human-readable activity log (assistant text, tool call names, tool result sizes) and — when inside a tmux session — opens a split pane tailing it live.

## Why

Spawned sessions are completely invisible. When the operator's terminal crashed mid-run, the drain continued blind with no way to tell if Claude was stuck, misbehaving, or burning budget on the wrong thing. The existing progress meter tells you *how much* happened (turns/tokens/cost), not *what* happened. This closes that gap without requiring interactive control of the subprocess.

## Definition of done

* `drain-cycle --watch` (or `-w`) accepted by CLI; zero-arg invocation unchanged
* When `$TMUX` is set: a split pane opens per issue tailing the watch log; replaced when the next issue starts; final pane left open for scrollback
* When `$TMUX` is not set: one-time warning printed, watch log still written (operator can `tail -f` manually)
* Watch log written to `~/.drain-cycle/runs/<run-stem>-<issue-id>.watch.log`
* Log format: timestamped turn headers, assistant prose, `→ ToolName(key=val)` lines, `← N chars` tool result lines, `=== done: N turns, $X.XX ===` footer
* All existing streaming / token-counting / breach-monitoring behaviour preserved — no change to the `--output-format stream-json` pipeline
* Tests cover: watch log content written correctly from stream-json events; non-tmux path writes log without crashing; pane open/close lifecycle

## Assumptions

* Sequential issue execution (already true — orchestrator is single-threaded)
* macOS `tail -f`: watch log file must be touched before pane opens
* `tmux` on `$PATH` when `$TMUX` is set
* Unknown stream-json content block types are silently skipped (forward-compat graceful degradation)

## Key risks

* Line-buffered writes in the reader thread add minor latency — must not slow the JSON parsing path measurably
* `tmux split-window` failures must be caught and swallowed; a broken tmux must not crash the drain run
* Stream-json schema changes in future Claude CLI versions could silently degrade the watch log (acceptable — degrades to empty turns, not a crash)

## Implementation sketch

Four files: `worker.py` (watch log writing in `_drain_stream`), `runlog.py` (add `watch_path()` beside `debug_path()`), `orchestrator.py` (tmux pane lifecycle, pass `watch_log` to worker), `cli.py` (`--watch` flag).
</description>

267	def _monitor(
268	    proc: subprocess.Popen[str],
269	    accumulator: _UsageAccumulator,
270	    *,
271	    started: float,
272	    token_limit: int | None,
273	    time_limit_seconds: float | None,
274	    poll_interval_seconds: float,
275	) -> Breach | None:
276	    """Wait for the session, returning the per-issue cap it breaches (if any).
277	
278	    With both caps off there is nothing to watch for, so we block on the
279	    process directly. Otherwise we wake every ``poll_interval_seconds`` to
280	    compare the live cumulative-token tally and elapsed wall-clock against
281	    the caps; the first crossed cap is returned for the caller to kill on.
282	    Returns ``None`` when the session exits on its own first.
283	    """
284	    if token_limit is None and time_limit_seconds is None:
285	        proc.wait()
286	        return None
287	    while True:
288	        try:
289	            proc.wait(timeout=poll_interval_seconds)
290	            return None
291	        except subprocess.TimeoutExpired:
292	            pass
293	        if token_limit is not None:
294	            observed = accumulator.cumulative()
295	            if observed >= token_limit:
296	                return Breach("per-issue", "token", token_limit, observed)
297	        if time_limit_seconds is not None:
298	            elapsed = time.monotonic() - started
299	            if elapsed >= time_limit_seconds:
300	                return Breach("per-issue", "time", time_limit_seconds, elapsed)

320	def _drain_stream(
321	    stream: TextIO | None,
322	    accumulator: _UsageAccumulator,
323	    sink: TextIO,
324	    on_progress: Callable[[int, int, int, float | None], None] | None = None,
325	) -> None:
326	    """Read the worker's merged output line by line until EOF.
327	
328	    Recognised JSON object events feed the usage accumulator; everything
329	    else (non-JSON diagnostics, JSON that isn't an object) is echoed to
330	    ``sink`` so the operator keeps the visibility a captured pipe would
331	    otherwise hide. ``on_progress`` is called once per new turn (deduplicated
332	    by message id) with a live usage snapshot.
333	    """
334	    if stream is None:
335	        return
336	    last_message_id: str | None = None
337	    try:
338	        for line in stream:
339	            line = line.rstrip("\n")
340	            if not line:
341	                continue
342	            try:
343	                event = json.loads(line)
344	            except json.JSONDecodeError:
345	                _echo(sink, line)
346	                continue
347	            if isinstance(event, dict):
348	                accumulator.feed(event)
349	                if on_progress is not None and event.get("type") == "assistant":
350	                    mid = (event.get("message") or {}).get("id")
351	                    if mid != last_message_id:
352	                        last_message_id = mid
353	                        snap = accumulator.live_snapshot()
354	                        on_progress(*snap)
355	            else:
356	                _echo(sink, line)
357	    finally:
358	        try:
359	            stream.close()
360	        except OSError:
361	            pass

375	class _UsageAccumulator:
376	    """Reconstruct session usage from the streamed events.
377	
378	    Per-turn usage is keyed by ``message.id`` so a turn emitted once per
379	    content block is counted once; the last copy wins (later events carry
380	    the more complete snapshot). The ``result`` event overwrites the
381	    session-summary fields each time it is seen.
382	
383	    All mutation happens on the reader thread and all reads happen on the
384	    main thread after it is joined — but the join is bounded, so a group
385	    member that escaped the kill (e.g. via ``setsid``) could keep the
386	    reader alive past the join. The lock makes the concurrent case safe
387	    rather than a ``dictionary changed size during iteration`` crash.
388	    """
389	
390	    def __init__(self) -> None:
391	        self._lock = threading.Lock()
392	        self._turns: dict[str, dict[str, int]] = {}
393	        self._anon = 0
394	        self.cost_usd: float | None = None
395	        self.num_turns: int | None = None
396	        self.session_id: str | None = None
397	        self.is_error: bool | None = None
398	
399	    def feed(self, event: dict[str, Any]) -> None:
400	        event_type = event.get("type")
401	        if event_type == "assistant":
402	            self._feed_assistant(event)
403	        elif event_type == "result":
404	            self._feed_result(event)
405	
406	    def _feed_assistant(self, event: dict[str, Any]) -> None:
407	        message = event.get("message")
408	        if not isinstance(message, dict):
409	            return
410	        usage = message.get("usage")
411	        if not isinstance(usage, dict):
412	            return
413	        message_id = message.get("id")
414	        turn = {field: _coerce_int(usage.get(field)) for field in _TOKEN_FIELDS}
415	        with self._lock:
416	            if isinstance(message_id, str):
417	                key = message_id
418	            else:
419	                key = f"_anon-{self._anon}"
420	                self._anon += 1
421	            self._turns[key] = turn
422	
423	    def _feed_result(self, event: dict[str, Any]) -> None:
424	        with self._lock:
425	            self.cost_usd = event.get("total_cost_usd")
426	            self.num_turns = event.get("num_turns")
427	            self.session_id = event.get("session_id")
428	            self.is_error = event.get("is_error")
429	
430	    def cumulative(self) -> int:
431	        """Live billed-token total across turns — the per-issue token cap is
432	        compared against this on every poll, so it reads under the lock and
433	        stays cheap (no peak-context / per-component breakdown)."""
434	        with self._lock:
435	            turns = list(self._turns.values())
436	        return sum(turn[field] for turn in turns for field in _TOKEN_FIELDS)
437	
438	    def live_snapshot(self) -> tuple[int, int, int, float | None]:
439	        """Current ``(turns, cumulative_tokens, peak_context_tokens, cost_usd)``.
440	
441	        Called from the reader thread after each new assistant turn. Reads
442	        under the lock so the main-thread monitor cannot see a torn state.
443	        """
444	        with self._lock:
445	            turn_count = len(self._turns)
446	            turns_list = list(self._turns.values())
447	            cost = self.cost_usd
448	        cumulative = sum(t[f] for t in turns_list for f in _TOKEN_FIELDS)
449	        peak = max(
450	            (
451	                t["input_tokens"]
452	                + t["cache_read_input_tokens"]
453	                + t["cache_creation_input_tokens"]
454	                for t in turns_list
455	            ),
456	            default=0,
457	        )
458	        return turn_count, cumulative, peak, cost
459	
460	    def usage(self) -> dict[str, int]:
461	        totals = {field: 0 for field in _TOKEN_FIELDS}
462	        peak_context = 0
463	        with self._lock:
464	            turns = list(self._turns.values())
465	        for turn in turns:
466	            for field in _TOKEN_FIELDS:
467	                totals[field] += turn[field]
468	            context = (
469	                turn["input_tokens"]
470	                + turn["cache_read_input_tokens"]
471	                + turn["cache_creation_input_tokens"]
472	            )
473	            peak_context = max(peak_context, context)
474	        return {
475	            **totals,
476	            "cumulative": sum(totals.values()),
477	            "peak_context": peak_context,
478	        }
479	
480	    def summary(self) -> tuple[float | None, int | None, str | None, bool | None]:
481	        """Read the result-event fields under the lock, as a snapshot."""
482	        with self._lock:
483	            return self.cost_usd, self.num_turns, self.session_id, self.is_error

# Implementation Plan: Watch Mode (ABA-338)

## Overview

Add `--watch`/`-w` to `drain-cycle`. When active, each issue's Claude session produces a human-readable activity log beside the run log (`<stem>-<issue-id>.watch.log`). If `$TMUX` is set, a split pane tails it live. The feature threads through four files in bottom-up dependency order: `runlog.py` → `worker.py` → `orchestrator.py` → `cli.py`.

## Architecture Decisions

- **`_WatchWriter` class in `worker.py`**: encapsulates turn counter, per-message-id dedup, and line-buffered file I/O — keeps `_drain_stream` a thin dispatcher
- **Touch-before-tail**: watch log is created before `tmux split-window` runs so `tail -f` has a file to open immediately (per macOS `tail -f` assumption in the spec)
- **Pane lifecycle in `_run()`**: prior pane killed at the *start* of each new issue (not end of previous); final pane left open for scrollback
- **One-time warning in `cli.py`**: printed to stderr when `--watch` set but `$TMUX` is not set; log still written
- **`tmux` failures are swallowed**: `FileNotFoundError`, non-zero exit, any `OSError` — drain run must not crash
- **No change to stream-json pipeline**: watch writing is a side-channel; existing token accounting and `on_progress` callback are unaffected

<title>Watch mode: live tmux pane for spawned Claude sessions</title>
<description>
## What

Add `--watch` / `-w` flag to `drain-cycle` that, for each issue run, writes a human-readable activity log (assistant text, tool call names, tool result sizes) and — when inside a tmux session — opens a split pane tailing it live.

## Why

Spawned sessions are completely invisible. When the operator's terminal crashed mid-run, the drain continued blind with no way to tell if Claude was stuck, misbehaving, or burning budget on the wrong thing. The existing progress meter tells you *how much* happened (turns/tokens/cost), not *what* happened. This closes that gap without requiring interactive control of the subprocess.

## Definition of done

* `drain-cycle --watch` (or `-w`) accepted by CLI; zero-arg invocation unchanged
* When `$TMUX` is set: a split pane opens per issue tailing the watch log; replaced when the next issue starts; final pane left open for scrollback
* When `$TMUX` is not set: one-time warning printed, watch log still written (operator can `tail -f` manually)
* Watch log written to `~/.drain-cycle/runs/<run-stem>-<issue-id>.watch.log`
* Log format: timestamped turn headers, assistant prose, `→ ToolName(key=val)` lines, `← N chars` tool result lines, `=== done: N turns, $X.XX ===` footer
* All existing streaming / token-counting / breach-monitoring behaviour preserved — no change to the `--output-format stream-json` pipeline
* Tests cover: watch log content written correctly from stream-json events; non-tmux path writes log without crashing; pane open/close lifecycle

## Assumptions

* Sequential issue execution (already true — orchestrator is single-threaded)
* macOS `tail -f`: watch log file must be touched before pane opens
* `tmux` on `$PATH` when `$TMUX` is set
* Unknown stream-json content block types are silently skipped (forward-compat graceful degradation)

## Key risks

* Line-buffered writes in the reader thread add minor latency — must not slow the JSON parsing path measurably
* `tmux split-window` failures must be caught and swallowed; a broken tmux must not crash the drain run
* Stream-json schema changes in future Claude CLI versions could silently degrade the watch log (acceptable — degrades to empty turns, not a crash)

## Implementation sketch

Four files: `worker.py` (watch log writing in `_drain_stream`), `runlog.py` (add `watch_path()` beside `debug_path()`), `orchestrator.py` (tmux pane lifecycle, pass `watch_log` to worker), `cli.py` (`--watch` flag).

### Important Issues

**`_open_watch_pane` captures the original pane ID, not the new pane — `orchestrator.py:52-63`**

`split-window -d` creates a new pane without changing the active pane. The subsequent `display-message -p "#{pane_id}"` (no `-t` flag) reports the *current* active pane — the one the operator was in before the split, not the newly created tail pane. When `_close_watch_pane` is called with this ID it kills the operator's working pane and leaves the tail pane orphaned.

The fix is to use `split-window`'s `-P -F` flags to print the new pane's ID directly, eliminating the second subprocess and the race:

```python
result = subprocess.run(
    ["tmux", "split-window", "-d", "-P", "-F", "#{pane_id}", f"tail -f {watch_log}"],
    check=True,
    capture_output=True,
    text=True,
)
return result.stdout.strip()
```

The test in `test_orchestrator_watch.py:182-231` (`test_tmux_pane_opened_and_prior_pane_killed_on_next_issue`) fakes `display-message` responses with incrementing counters but never asserts that the killed pane ID matches the one returned from `split-window`, so it does not catch this bug.

**`_WatchWriter` file handle leaks on breach/kill — `worker.py:464-474`**

`_WatchWriter._file` is only closed inside `_feed_result`. When the session is killed (token or time breach) before a `result` event arrives, `_feed_result` is never called and the file stays open until GC. `_drain_stream`'s `finally` block (`worker.py:368-372`) closes only `proc.stdout`. For a long multi-issue drain under token pressure (common), this accumulates one open file handle per breach.

Fix: add explicit cleanup in `_drain_stream`'s `finally` block, or give `_WatchWriter` a `close()` method and call it after `reader.join()` in `run_issue`:

### Suggestions

**Unquoted path in tmux shell command — `orchestrator.py:53`**

```python
["tmux", "split-window", "-d", f"tail -f {watch_log}"],
```

tmux passes the final argument to `sh -c`, so a path containing spaces (e.g. when `$HOME` contains a space) would split incorrectly. In practice `~/.drain-cycle/runs/` and issue IDs never contain spaces, so this is low-risk for a personal tool. The fix if desired is `shlex.quote(str(watch_log))`.

**Redundant `touch()` — `worker.py:184` and `orchestrator.py:435`**

The orchestrator touches the watch log file before opening the pane (`orchestrator.py:435`), and the worker touches it again at line 184. The double touch is harmless but the worker's touch is unreachable benefit — the pane is already open and `tail -f` is already following the file. The `test_watch_log_file_touched_before_session` test verifies the worker's touch, but the real constraint (the file must exist before `tail -f` opens) is satisfied by the orchestrator's touch. No behavior impact.

**`tool_result.content` string shorthand reports 0 chars — `worker.py:456-461`**

The Anthropic Messages API allows `tool_result.content` to be a plain string (shorthand). The current code does `result_content = block.get("content") or []`, which if `content` is a non-empty string, assigns the string to `result_content`. Then `for c in result_content if isinstance(c, dict)` yields nothing (string chars are not dicts), so `size = 0`. The log would show `← 0 chars` for a string-content result. The claude CLI may normalize this before emitting stream-json, making it moot in practice, but the test helper `_user_tool_result` always wraps in a list so this path is untested.

**`_WatchWriter` args are individually truncated, not the whole line — `worker.py:438-443`**

Each `f"{k}={repr(v)}"[:_WATCH_INPUT_MAX]` truncates per key-value pair to 80 chars. A tool with 10 arguments produces a line up to ~800 chars + name. This is intentional (you still see all args) but worth noting: the result can be much wider than a terminal. No functional issue.
