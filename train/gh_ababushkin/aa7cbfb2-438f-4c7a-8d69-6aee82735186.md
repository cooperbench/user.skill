## Phase 1: Directions

Here are the meaningful variations, grounded in what exists:

---

**Direction A — Structured event log with Rich** *(closest to what you described)*
Each orchestrator event becomes a timestamped, labeled line. Startup emits a rendered table of what's about to run (identifier, title, model, estimated order). During a run, the orchestrator emits labeled lines (`[orchestrator]`, `[worker:ABA-362]`, `[graphite]`) that interleave with the agent's output stream. Completion emits a summary block (issues done/halted, total cost, next action if halted). Uses `rich` for color and structure; degrades gracefully to plain text if not a TTY. All output goes to stderr so stdout stays pipeable.

**Direction B — Prefixed log protocol (no deps)**
Every line has a machine-readable prefix: `ORCH|2026-06-10T12:03:09|INFO|picked ABA-362: N03...`. Structured enough to `grep ORCH|HALT` after the fact, zero new deps, works perfectly in tmux scroll. Less pretty but maximally grep-able and no risk of Rich's rendering breaking in headless runs. The startup plan becomes a `PLAN|` block, completion a `DONE|` or `HALT|` block.

**Direction C — Phase-separated sections**
The run output is divided into clearly marked sections: `=== PLAN ===`, `=== ABA-362 ===`, `=== SUMMARY ===`. Each section has a header and footer with timing/cost. The agent's raw output is indented under its section header. This makes post-mortem reading very easy (visual anchors), works perfectly as a scrollback, and requires zero deps. The tradeoff: less live-update friendly than A, no per-line timestamps.

**Direction D — Separate orchestrator log file**
Instead of interleaving with agent output, the orchestrator writes its own structured log to `~/.drain-cycle/runs/<cycle>-orch.log`. The terminal shows only the agent's stream (unchanged). You `tail -f` the orch log in a second pane for orchestrator state. This is the Unix-purist approach — clean separation of concerns, but it requires two panes to get the full picture.

**Direction E — `drain-cycle status` as the live view**
Keep the run output minimal; invest in making `drain-cycle status` into a rich live dashboard (think `watch -n1 drain-cycle status`). The startup "plan" is stored in the active marker; `status` renders it. This maximizes info density for the watching case without touching the log stream at all.
