## Phase 1 — Variations

Through different lenses:

1. **Inversion** — Don't split at the end; split the *commit history during the build*. Have the worker skill commit in reviewable slices as it works (one logical change per commit), so the final skill just maps commits→stacked PRs mechanically. The "too hard to pre-shape" problem was about predicting cuts *before* building — but the worker knows the cuts *while* building.

2. **Simplification (10x simpler)** — The skill produces a **split plan only** (a JSON: ordered list of `{pr_title, body, commit_shas}`). The orchestrator still runs `gt`, but now driven by data the agent computed, not by guessing boundaries. Smallest possible change to today's code.

3. **Full handoff** — The skill owns the *entire* tail: decompose → `gt track`/`gt submit` per slice → write PR bodies → return a manifest of PR URLs in `.drain-handoff.json`. Orchestrator just reads URLs and posts to Linear. `graphite.py` shrinks to near-nothing.

4. **Constraint removal** — If gt auth/init weren't operator-owned preconditions, the skill could fully self-provision. It can't (dangerously-skip-permissions can't do `gt auth`'s browser flow) — so any design must *detect* missing preconditions and fail with a clear message rather than a cryptic `gt submit` abort.

5. **Expert lens** — A reviewer doesn't want N tiny PRs *and* a fat one; they want a stack where **PR #1 is the skeleton, each subsequent PR is independently reviewable and green**. That means each slice must build+pass tests on its own — which is a real constraint on how you cut, and something only verification-aware tooling can guarantee.

6. **Combination** — Merge this with your existing `/code-review-and-quality` step: the review already partitions the diff into concerns. Feed *that partition* into the splitter instead of re-deriving boundaries.

## Phase 2 — Converge

Three coherent directions emerge:

**A. Post-hoc splitter skill (your literal proposal).** Skill runs after verify, looks at the single fat branch diff, decides PR boundaries, drives `gt`, writes bodies.
- *Value:* High — directly kills the fat-PR pain, no change to how work is built.
- *Hardest part:* Splitting an *already-squashed* set of changes into independently-green commits is genuinely hard. If the worker made one big commit, the skill has to re-slice a diff into commits that each compile — error-prone.
- *Bet:* That an agent can reliably reconstruct clean commit boundaries from a finished diff.

**B. Slice-during-build + mechanical map (variations 1+2).** Worker commits in reviewable slices; final skill maps commits→PRs and emits a plan; orchestrator executes gt.
- *Value:* High and *more robust* — boundaries are decided when context is richest (mid-build), each commit is green by construction.
- *Hardest part:* Disciplining the worker to commit in slices; updating the worker prompt + handoff schema.
- *Bet:* That worker-time commit discipline is more reliable than post-hoc re-slicing. I think this bet is **much safer** than A's.

**C. Harden-in-place.** Keep gt in Python, wrap in retry/recovery, don't move to a skill.
- *Value:* Low for your stated goal — doesn't address fat PRs at all, only fragility. You explicitly ruled this owner out.

**My honest read:** Your instinct to move gt into a skill is right for the *fragility* problem. But for the *fat-PR* problem, **B beats A**. The reason pre-shaping felt "too hard" is that you were trying to predict PR cuts at *planning* time. A swings to the other extreme — reconstructing cuts at *post-build* time from a flattened diff, which is arguably harder. B hits the sweet spot: decide boundaries *during* build, when the agent has the most context and each slice is naturally green.

The skill you envisioned still exists in B — but its job shrinks from "re-slice a mystery diff" to "turn an already-sliced commit history into a clean stack with good descriptions, driving gt with a recovery loop." That's a skill that can actually be reliable.

"Slice-during-build" is the core mechanism in the revised ticket. Here's what it means, concretely.

## The problem it solves

A drain worker picks up one Linear issue, works in a worktree, and ends with a finished diff. Today that whole diff becomes **one branch → one PR**. If the issue was coarse (3–5 logical changes), you get one fat PR that's painful to review.

The question is: *when do you decide where the PR boundaries are?* There are three possible moments:

| When | What it means | Verdict |
|------|---------------|---------|
| **Before build** (pre-shaping) | At planning time, cut the issue into sub-issues that each become a PR | You tried this — too hard. You can't predict the right cuts before you've seen the code. |
| **After build** (post-hoc re-slice) | Take the one finished diff and chop it into PRs at the end | Arguably *harder* — you're reverse-engineering boundaries out of a flattened blob, and each piece has to still compile. |
| **During build** (slice-during-build) | As the worker writes the code, it commits each logical change as its own git commit | The sweet spot. |

## What slice-during-build actually is

It's a **commit discipline imposed on the worker**: instead of doing all the work and making one big `git commit` at the end, the worker commits **one logical change at a time** as it goes.

So a worker handling "add rate-limiting to the API" might produce:

```
commit 1: add RateLimiter class + unit tests
commit 2: wire RateLimiter into the request middleware
commit 3: add config knobs + docs
```

Each commit is **independently green** — it builds and passes tests on its own. The worker also records the intended commit→PR mapping in `.drain-handoff.json`.

## Why this makes the rest trivial

Because the slicing already happened *during* the build, the finishing skill no longer has to be clever. It just **maps each commit (or group of commits) to a PR in the stack** — a mechanical step:

```
commit 1 → PR #1 (base)
commit 2 → PR #2 (stacked on #1)
commit 3 → PR #3 (stacked on #2)
```

Compare that to post-hoc re-slicing, where the skill would have to take one giant diff and *guess* how to split it into pieces that each compile — far more error-prone.

## The key insight

**Boundaries are cheapest to draw at the moment of maximum context** — while the agent is actively writing the code and knows exactly which lines belong to which logical change. Before the build, that context doesn't exist yet; after the build, it's been flattened away. Slice-during-build captures it at the one moment it's available for free.

## The bet (and the flagged risk)

The whole approach rests on one assumption: that a `--dangerously-skip-permissions` worker will *actually* commit in clean slices without a human nudging it. If it doesn't — if it just makes one big commit anyway — you're back to the hard post-hoc re-slice problem. That's exactly why the ticket keeps post-hoc re-slicing as an explicit (secondary, logged) fallback, and why `slice-discipline` is the first task: you want to validate that bet early.
