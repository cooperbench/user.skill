> AGENT

"Slice-during-build" is the core mechanism in the revised ticket. Here's what it means, concretely. ## The problem it solves A drain worker picks up one Linear issue, works in a worktree, and ends with a finished diff. Today that whole diff becomes **one branch → one PR**. If the issue was coarse (3–5 logical changes), you get one fat PR that's painful to review. The question is: *when do you decide where the PR boundaries are?* There are three possible moments: | When | What it means | Verdict | |------|---------------|---------| | **Before build** (pre-shaping) | At planning time, cut the issue into sub-issues that each become a PR | You tried this — too hard. You can't predict the right cuts before you've seen the code. | | **After build** (post-hoc re-slice) | Take the one finished diff and chop it into PRs at the end | Arguably *harder* — you're reverse-engineering boundaries out of a flattened blob, and each piece has to still compile. | | **During build** (slice-during-build) | As the worker writes the code, it commits each logical change as its own git commit | The sweet spot. | ## What slice-during-build actually is It's a **commit discipline imposed on the worker**: instead of doing all the work and making one big `git commit` at the end, the worker commits **one logical change at a time** as it goes. So a worker handling "add rate-limiting to the API" might produce: ``` commit 1: add RateLimiter class + unit tests commit 2: wire RateLimiter into the request middleware commit 3: add config knobs + docs ``` Each commit is **independently green** — it builds and passes tests on its own. The worker also records the intended commit→PR mapping in `.drain-handoff.json`. ## Why this makes the rest trivial …
