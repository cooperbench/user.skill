# Worker session invokes `/shape:task` before implementation on `verify`-flow tickets

## What

The drain-cycle worker session for `verify`-flow tickets invokes `/shape:task` as the first step before any implementation begins, and includes the Task Shaper output in the implementer's prompt context.

## Why

Without this wiring, the Task Shaper skill exists but is never invoked by the worker — the role doesn't participate in the drain flow and the AC enrichment never reaches the implementer.

## Assumptions

* The worker session can prepend a shaping step before handing off to the implementer.
* The Task Shaper output format is stable (the `/shape:task` skill issue is done first).
* Non-verify-flow drains are unchanged.
* On a §14 resume, the worker checks the Linear issue body for an existing Task Shaper output block; if found, it uses that block as context and skips re-invoking `/shape:task`. This is the mechanism that makes [ABA-326](https://linear.app/ababushkin/issue/ABA-326/ta[REDACTED_SK])'s dual-write the durable artefact. See design decision §17.

## Key Risks

* The shaping step adds latency and token cost per ticket; if material, `limits.yml` overrides may be needed (addressed in M5).
* If `/shape:task` surfaces irresolvable AC gaps, the skill flags them and returns (it does not hang or halt the worker). The worker passes the flagged gaps through to the implementer's context — the implementer proceeds with explicit awareness of the gaps rather than silently.

## Definition of Done

* A `verify`-labelled drain invokes `/shape:task` before the implementer begins.
* The implementer's prompt context includes the Task Shaper output.
* A non-verify-flow drain does not invoke `/shape:task`.
* The run-log entry includes evidence that the shaping step ran.
* A resumed verify-flow drain (§14) skips the `/shape:task` invocation if a Task Shaper output block already exists in the Linear issue body, and uses the existing block as implementer context.

### 4. **Shape:task Skill Reference**

**File:** `/Users/anton/src/drain-cycle/docs/design-decisions.md` §17

**What it is:** A per-ticket task-shaping skill that runs *inside* the worker session before the implementer begins (not a pre-drain planning step).

**Input:**
- Linear issue identifier
- Fetches current issue body, title, AC from Linear at invocation time
- Does NOT read prior planning artefacts

**Output (tripartite):**
1. **Enriched AC checklist** - AC items made concrete, implicit contracts surfaced, gaps flagged
2. **Sizing decision** - `single-stack` (all work on one branch) OR `N-stacks` (N justified), based on whether implementation reaches Done in one PR stack
3. **Per-stack task list** - One ordered task list per stack, as context for implementer

**Dual-write:**
- (a) Returned to calling worker for in-session context
- (b) Appended to Linear issue body in stable, delimited format
- Linear write is authoritative: resumed workers read the block from issue body instead of re-running the skill

**Key design choice:** Runs inside each worker session (not pre-drain planning gate) to preserve the single-invocation promise. A worker that invokes `/shape:task` itself is self-contained for drain, single-ticket re-run, or resume (§14) scenarios with no prior planning artefact required.

**Related:** `/shape:planning-and-task-breakdown` is the whole-project shaping skill for design docs; the two coexist at distinct scopes.

### 5. **§14 Resume Logic**

**File:** `/Users/anton/src/drain-cycle/docs/design-decisions.md` §14 + `/drain_cycle/orchestrator.py` lines 454-492

**Core mechanism:**

1. **`worktree.ensure()` replaces `worktree.add()`** (lines 500 in orchestrator.py):
   - If a worktree already exists at `repo/.worktrees/<identifier>`, it is reused as-is (no git command runs)
   - Dirty index, staged/untracked files, gitignored config symlinks all survive untouched
   - Otherwise falls through to `add()` (fresh worktree)
   - Returns `WorktreeHandle(path, resumed: bool)` flag

2. **Resume directive in prompt** (lines 30-44 in prompt.py):
   - When `resumed=True`, `_resume_directive(identifier)` prepends to preamble:
   ```
   Resuming issue {identifier}: this worktree carries prior committed work...
   Run `git log --oneline main..HEAD` and `git status` first to read what is already done,
   then continue from that point — do not restart from scratch.
   ```
   - Inserted as first line of preamble (after `---` separator) so agent reads it before procedure

3. **Resume cap enforcement** (lines 468-492 in orchestrator.py):
   - **Policy check fires BEFORE any worktree manipulation or Linear state change**
   - `limits.max_resume_attempts` (default 3) allows up to N resumes *after* initial attempt (N+1 total halts before refusal)
   - `_resume_attempts(cycle_id, identifier)` counts prior non-Done entries for the issue across cycle run-log files
   - If `prior_halts > max_resume_attempts`: no-spawn halt, no Linear state change, no worktree mutation—allows operator to intervene
   - Cap-halt entry written so KR1 grading sees the refused attempt; halt line names the cap

4. **Why the order matters:**
   - Repo resolution → resume-cap check → `worktree.ensure()` → `link_project_config()` → `set_state()` → spawn
   - Each step is no-op until previous succeeds
   - Resume-cap check comes BEFORE `ensure()` to avoid mutating state before refusal

5. **Run-log entry shape:**
   - Resumed halts use same shape as first-attempt halts (identical `final_linear_state`, `worktree_path`, `halt_reason` template)
   - Cap-halt uses `exit_code=-1` (no-spawn sentinel)
   - KR1 grading and cap-counting both read `final_linear_state` per entry—no split schema

98	def _plan(issues: list[dict[str, Any]]) -> ExecutionPlan:
99	    """Topological sort over ``issues`` respecting blocks/blocked-by.
100	
101	    Returns an ``ExecutionPlan`` with ``order`` (runnable, topo-sorted by
102	    ``(sortOrder, id)`` tiebreak) and ``deferred`` (issues skipped because
103	    an external unresolved blocker exists, or because a blocking issue in
104	    the drain was itself deferred — cascade).
105	
106	    Raises ``DependencyCycleError`` when the intra-set blocks graph contains
107	    a cycle (self-loops included).
108	    """
109	    P: set[str] = {i["id"] for i in issues}
110	    by_id: dict[str, dict[str, Any]] = {i["id"]: i for i in issues}
111	
112	    # Build de-duped intra-P edges: blocker_id → set of blocked_ids
113	    children: dict[str, set[str]] = {i["id"]: set() for i in issues}
114	    # Per-issue unique set of intra-P blocker ids (for cascade check + in-degree)
115	    intra_blockers: dict[str, set[str]] = {i["id"]: set() for i in issues}
116	    indegree: dict[str, int] = {i["id"]: 0 for i in issues}
117	
118	    for issue in issues:
119	        for blocker in issue.get("blockers", []):
120	            bid = blocker["id"]
121	            if bid in P:
122	                if bid not in intra_blockers[issue["id"]]:
123	                    intra_blockers[issue["id"]].add(bid)
124	                    indegree[issue["id"]] += 1
125	                    children[bid].add(issue["id"])
126	
127	    # Kahn's algorithm: ready = in-degree-0 issues, sorted by (sortOrder, id)
128	    ready: list[dict[str, Any]] = sorted(
129	        [i for i in issues if indegree[i["id"]] == 0],
130	        key=lambda i: (i["sortOrder"], i["id"]),
131	    )
132	
133	    order: list[dict[str, Any]] = []
134	    deferred: list[dict[str, Any]] = []
135	    deferred_ids: set[str] = set()
136	
137	    while ready:
138	        issue = ready.pop(0)
139	        iid = issue["id"]
140	
141	        # Cascade: any intra-P blocker already deferred → defer this too
142	        cascade_blocker = next(
143	            (by_id[bid] for bid in intra_blockers[iid] if bid in deferred_ids),
144	            None,
145	        )
146	        if cascade_blocker is not None:
147	            deferred.append({
148	                "issue": issue,
149	                "blocker_identifier": cascade_blocker["identifier"],
150	                "blocker_state_type": cascade_blocker["state"]["type"],
151	            })
152	            deferred_ids.add(iid)
153	        else:
154	            # External unresolved blocker → defer
155	            ext_blocker = next(
156	                (
157	                    b for b in issue.get("blockers", [])
158	                    if b["id"] not in P and b["state_type"] not in _RESOLVED_STATE_TYPES
159	                ),
160	                None,
161	            )
162	            if ext_blocker is not None:
163	                deferred.append({
164	                    "issue": issue,
165	                    "blocker_identifier": ext_blocker["identifier"],
166	                    "blocker_state_type": ext_blocker["state_type"],
167	                })
168	                deferred_ids.add(iid)
169	            else:
170	                order.append(issue)
171	
172	        # Decrement children regardless (deferred nodes still unblock their children
173	        # in the graph so cycle detection remains accurate)
174	        for child_id in children[iid]:
175	            indegree[child_id] -= 1
176	            if indegree[child_id] == 0:
177	                child = by_id[child_id]
178	                # Insert maintaining (sortOrder, id) order
179	                idx = 0
180	                key = (child["sortOrder"], child["id"])
181	                while idx < len(ready) and (ready[idx]["sortOrder"], ready[idx]["id"]) <= key:
182	                    idx += 1
183	                ready.insert(idx, child)
184	
185	    cycle_nodes = [i for i in issues if indegree[i["id"]] > 0]
186	    if cycle_nodes:
187	        raise DependencyCycleError([i["identifier"] for i in cycle_nodes])
188	
189	    return ExecutionPlan(order=order, deferred=deferred)
