67	# Design doc
68	
69	## Purpose
70	
71	This skill produces a structured design document before any non-trivial implementation begins. It is the operational form of universal Principle 2 (design starts with the problem, not the stack): the seven-section structure mandated by Rule A2 makes solution-first approaches structurally incomplete. An agent or engineer cannot finish the artefact without working through Problem, Context, Constraints, Alternatives, and Operability in that order. The skill governs when a design doc is required (Rule A1), what structure it must follow (Rule A2), and which sections are hard rejections when absent (Rule A6). The deliverable is the document reviewers evaluate before any code is written — not the code itself.
72	
73	## When to use
74	
75	At least one Rule A1 trigger must fire. Any single trigger is sufficient:
76	
77	1. The work will take more than four weeks of engineering time.
78	2. The capability will be used by parties outside the team building it.
79	3. The change has meaningful impact on users, operational cost, or compliance posture.
80	
81	If a trigger is ambiguous, default to writing the doc. A short, fast doc costs less than a build that starts on a misunderstood problem.
82	
83	## When not to use
84	
85	- **None of the three triggers fire** — write a short ADR instead (Rule A3). A design doc for sub-threshold work is overhead; an ADR is the right fit.
86	- **The problem is not yet understood** — run a `spike` first, then return here. Writing a design doc for an undefined problem produces a document about the solution you assumed, not the problem you have.
87	- **Change is purely additive, clearly reversible, and has no shared-interface surface** — proceed directly to implementation. Not every shipped line needs a design doc.
88	
89	## Inputs
90	
91	- A problem description or feature request, however rough
92	- Named stakeholders and affected users
93	- Known constraints — functional and non-functional
94	- A rough scope estimate that suggests at least one Rule A1 trigger fires
95	- Prior design docs and ADRs for related capabilities (loaded per Agentic P1)
96	- Access to `rules/eng-principles-universal.md` (Rules A1, A2, A4, A5, A6, B2, B3)
97	
98	## Outputs
99	
100	Artefact path: `docs/design-docs/<kebab-case-name>/design-doc.md`
101	
102	The output is a complete design doc following the Rule A2 structure. Every section is present. The Operability section is fully populated. The document is ready for review before implementation begins.
103	
104	## Workflow
105	
106	**Step 1 — Trigger check [GATE]**
107	Verify at least one Rule A1 condition holds. State which one. If none holds, stop — recommend an ADR. If the problem itself is not yet understood, stop — recommend a spike. Do not proceed past this gate without naming the trigger condition.
108	
109	**Step 2 — Context load**
110	Load prior design docs and ADRs for related work. Load `eng-principles-universal.md` Rules A1, A2, A4, A5, A6, B2, B3. Load `eng-principles-agentic.md` P1, P3. Name each artefact loaded. This step is the operational form of Agentic P1: context is the asset; loading it is the work.
111	
112	**Step 3 — Problem section [GATE]**
113	Draft the Problem section first. No solution language appears until this section is complete. The problem statement names the affected users, describes current behaviour, and states the desired behaviour. Each of those three elements must be present before proceeding. A problem statement that slides into solution language ("users can't do X, so we should build Y") is sent back for rewrite. Proceed only when the problem is stated in problem terms.
114	
115	**Step 4 — Context and constraints**
116	Document background, history, and related prior decisions. Link relevant ADRs. State what has been tried before. State any inherited constraints. Then list non-functional requirements with numbers and units (Rule A4): latency at p95, availability SLO, throughput target, cost envelope, error budget, security posture. For each NFR, name its fitness function — the automated check that will verify it continuously (Rule A5). "Fast," "reliable," and "scalable" are not NFRs.
117	
118	**Step 5 — Alternatives**
119	List at least two alternatives, including the "do nothing" option. For each: a description, the blast radius if this option turns out to be wrong, and the reversal cost (Rule B3). One approach listed is an incomplete design doc. If you cannot describe what is wrong with the alternatives, you cannot explain why the recommended approach is right.
120	
121	**Step 6 — Recommended approach**
122	State the recommendation. Explain why it beats the named alternatives on the named constraints. This section comes after alternatives because the problem shapes the recommendation — not the reverse.
123	
124	**Step 7 — Consequences**
125	Name positive and negative consequences. Explicitly state whether a walking skeleton should precede the full build (Rule B2). A walking skeleton is the minimal end-to-end implementation — one request path wired through every real component in the real deployment environment. Pre-skeleton estimates are uncalibrated. If the path to production is already clear and integration risks are fully known, note that explicitly.
126	
127	**Step 8 — Operability plan [GATE]**
128	Complete every sub-field: metrics (what to graph), structured logs (what to emit), traces (spans to instrument), alerts (thresholds and on-call routing), rollback plan (steps and time estimate), capacity headroom, known failure modes with mitigations, upstream and downstream dependency failure modes. A skeletal or absent Operability section means the doc is not ready for review. This gate does not pass until every sub-field has content. This section is authored with the people who will operate the system — not written in isolation and delivered to them later (Rule A6).
129	
130	**Step 9 — Open questions**
131	List every unresolved question. Each question has an owner and a resolution deadline. An open questions section with no owners or dates is not an open questions section; it is a list of known unknowns being politely ignored.
132	
133	**Step 10 — Review hand-off**
134	Share the completed document for review before any implementation begins. Implementation begins only after the design doc is accepted. Sharing a draft with known incomplete sections is not a hand-off; it is a draft in progress.

91	## Purpose
92	
93	This skill catches plan defects before approval. A plan that looks coherent can still touch out-of-scope code, rest on unstated assumptions, or commit to a one-way door without recording the alternatives that were considered. By the time those defects surface in execution, the cost of correction is the cost of rework, not the cost of revision. The skill is the operational form of Agentic P3 (the spec is the seatbelt): it forces a structured pass over the plan against eight MECE attack buckets — problem framing, scope, assumptions, dependencies, reversibility, operability, sequencing, pre-mortem — so the categories of defect that actually appear in PDE work each get an explicit check. The deliverable is a review record with a final APPROVE / REVISE / KILL recommendation. The skill replaces the role-play "play the skeptic" framing of its predecessor with framework-based questioning, because empirical evidence (Nemeth meta-analysis) shows assigned dissent is less reliable than structured coverage.

37	# Prototype to validate
38	
39	## Purpose
40	
41	A prototype-to-validate is a throwaway artefact built to answer one specific question before engineering time is committed to a design. The question is always a product question — how the feature will feel, whether users will understand an interaction, whether a proposed flow creates or removes confusion. Technical unknowns belong in a spike (Rule C5). The output is a written finding, not a deliverable artefact.
42	
43	This skill sits between `idea-triage` and `design-doc`. Idea-triage confirms a problem is real and worth pursuing. That is not enough to know how to solve it. When the gap between "this is worth building" and "this is how we'll build it" is a product question, a prototype answers it cheaply. A design-doc started from an unclear product direction will be redesigned; a prototype started from an unclear product direction will be thrown away. Throwaways are cheaper.
44	
45	The risk this skill guards against is the prototype that becomes an implementation. A prototype built with production-quality code, extended beyond its original question, and shipped to users has become a real release — without tests, without a design review, without operability planning. Prototypes must be throwaway by policy: the question is the constraint, the code is the instrument, the finding is the output.
46	
47	## When to use
48	
49	- An idea has cleared idea-triage and the dominant remaining unknown is product feel — how the interaction works, whether the flow makes sense, what the experience is like for a user.
50	- A design-doc has stalled because the team disagrees about which approach will feel right and opinion-level argument is not resolving it.
51	- Before committing to a design-doc for a significant UX-touching change where intuition about user response is low.
52	
53	## When not to use
54	
55	- **The dominant unknown is technical** — run a spike instead. Spikes answer: can we do this, at what cost, with what constraints? Prototypes answer: does this feel right, will users understand this?
56	- **The idea hasn't been triaged** — run `idea-triage` first. A prototype is not a substitute for problem validation; it is a tool for solution exploration after the problem is confirmed.
57	- **The interaction is known and the task is to design the system** — go directly to `design-doc`. Prototype-to-validate is discovery work; design-doc is commitment work.
58	- **Multiple questions need answering** — triage the questions first. One prototype answers one question. Run prototypes sequentially, not simultaneously.
59	
60	## Inputs
61	
62	- An idea-triage output: validated hypothesis, ICE score, confidence rating.
63	- A single, specific question the prototype will answer (one sentence, written before building begins).
64	- A time box (set before the prototype begins; not extended after starting).
65	
66	## Outputs
67	
68	A written finding at `docs/prototypes/<slug>/finding.md`. The finding contains: the question, the prototype approach, the observations, and a recommendation: proceed / reshape / kill. The prototype code, if any, is either deleted or explicitly marked non-production in the finding.
69	
70	## Workflow
71	
72	**1. Write the question.**
73	Before building anything, write the question in one sentence. The question must be specific (one thing, not a cluster), answerable by observation, and bounded (there is a signal that means "yes" or "no"). If the question cannot be written in one sentence, it is not well-defined. Resolve it first.
74	
75	Good questions:
76	- "Will a user who has not seen this flow understand that step 2 must complete before step 3 unlocks?"
77	- "Does inline editing feel faster than a modal for this data type, based on a walkthrough with one internal user?"
78	- "Is the proposed navigation structure legible — does a new user land in the right section?"
79	
80	Questions too vague to drive a prototype:
81	- "How should the onboarding flow work?" — a design brief, not a question
82	- "Will users like this?" — not specific enough to be answerable
83	- "Is this the right approach?" — too broad; which aspect of the approach?
84	
85	**2. Set the time box and the kill condition.**
86	Name both before writing a line. Default: half a day to two days. Anything beyond three days is a design project, not a throwaway prototype. The kill condition is the signal that ends the prototype early — the question is answered in the first hour, or the approach clearly fails in a way that needs no further exploration. Stopping early is not a failure; it is the skill working as intended.
87	
88	**3. Choose the mode.**
89	
90	| Mode | Best for | What it is |
91	|---|---|---|
92	| Narrative | Concept-level questions about flow and framing | Written scenario + annotated sketches; no code |
93	| Clickable | Interaction questions about sequencing and affordances | Mockup in a design tool, navigable but static |
94	| Throwaway code | Questions that require live data or real interaction behaviour | Code that runs, intentionally not production-quality |
95	
96	Throwaway code is the riskiest mode: most likely to drift into a release, most expensive to build, least often necessary. Use it only when the question cannot be answered by narrative or clickable means — for example, when the answer depends on real API latency, real data shape, or real browser behaviour.
97	
98	**4. Build and observe.**
99	Build the minimum that answers the question. Nothing beyond it. When the prototype is in the hands of an observer — a user, a teammate, yourself — record observations, not interpretations. Interpretation goes in the finding.
100	
101	**5. [GATE] Write the finding.**
102	A prototype must exit with a finding. If the time box expires and the question is not answered, the finding is: "this prototype approach did not answer the question; the next step is X." That is a valid finding. Exiting without a finding is not valid.
103	
104	The recommendation must be one of three:
105	- **Proceed** — the question is answered affirmatively; proceed to `design-doc`.
106	- **Reshape** — the question is answered but the answer is "not this way"; the idea needs revision before a design is possible.
107	- **Kill** — the question is answered negatively; the idea does not survive the prototype. This is a celebrated outcome (Rule D5): the prototype saved the cost of a full design and build.
108	
109	**6. Dispose of the prototype.**
110	Throwaway code: delete it, or mark it explicitly as non-production (no test coverage, no error handling, not to be deployed) in the finding. Do not commit throwaway code to the main branch without this marking. Do not extend throwaway code toward production quality — that requires a design-doc and a clean implementation.

> AGENT

Good catch — and you're right that the current framing under-specifies it. Let me think about it honestly.

**The clean version.** P8 actually defines two units, not one:
- **Slice** = the agent's work-decomposition unit. Independently verifiable. Captures "how many distinct things has the agent built."
- **Gate** = the human's attention unit. A proceed/stop checkpoint with explicit pass criteria. Captures "how many times does the human have to engage."

These diverge. A 1-slice migration with a one-way-door schema decision is 1 slice but ~3 gates (design review, run-the-migration approval, post-migration verification). A 10-slice cosmetic refactor might be 10 slices and 1 gate (review the final diff).

**Where the current sweep is honest, and where it leans.** The slice-based thresholds I just wrote (>5 slices for design-doc, single-slice for fast-track) all implicitly assume *one gate per slice* — which is fine for verification-granularity reasoning but does undercount the human-attention cost of high-gate-density work. A "single slice, 5 permission prompts, 2 architectural decisions" plan would still hit the fast-track gate today, and arguably shouldn't.

**Three ways to fix this, in increasing rewrite cost:**

1. **Sharpen the slice definition** to say "a slice is bounded by *one* human gate by default; if a single end-to-end change requires multiple human decisions, count each as its own slice." This means slice-count becomes a proxy for human attention, not just agent verification granularity. Smallest change, but stretches "slice" past Cockburn's original meaning.

2. **Add gates as a co-equal threshold dimension.** Fast-track becomes "1 slice *and* ≤1 gate." Design-doc triggers become ">5 slices *or* >N gates *or* any one-way door." Honest, but doubles the threshold vocabulary everywhere.

3. **Leave slices as agent-effort, treat one-way doors / production-touch / un-traced-code as the human-attention proxies we already have.** The current triggers already do most of this — design-doc fires on any one-way door regardless of slice count; plan-review fast-track excludes production data, schema, auth. The argument would be: human attention is already gated by these orthogonal triggers, not by slice count.

My read: option 3 is closest to what the sweep already does, but P8 itself should be explicit that **gates carry the human-attention load**, and slice thresholds are a proxy that breaks down when gate-density is high. That's a one-paragraph addition to P8, not a rewrite.

Want me to draft the P8 amendment before we commit, or hold the sweep as-is and treat this as a follow-up?
