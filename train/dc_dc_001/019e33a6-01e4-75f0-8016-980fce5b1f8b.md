- 直接生成 K1 tile blockmask，格式复用 `stage1_k1_blockmask`
- 第二段 K1 已经有读取点：[flash_fwd_kernel.h](/user_4813494d/openbmb/kernels/infllmv2_cuda_impl/csrc/flash_attn/src/flash_fwd_kernel.h:1706)，`fwdIterator(..., true)` 会读 `params.stage1_k1_blockmask`

如果要 exact K2 probability topk，这个插入点不够：第一段结束前没有最终 denom；要 exact 就必须存 logits/score 或重扫 K2，这会回到“额外 stage1 overhead”的问题。

如果走 split-stage1，还需要额外输出：

- `float* stage1_row_max`
- `float* stage1_row_sum`
- shape 应按 adjusted q 保存，大致 `[num_heads_k, total_q_adjusted]`
- 第一段在 [flash_fwd_kernel.h](/user_4813494d/openbmb/kernels/infllmv2_cuda_impl/csrc/flash_attn/src/flash_fwd_kernel.h:1691) 后写出
- 第二段 kernel 读回后执行 K1 `softmax_rescale_gt()` 等价逻辑

**4. 风险与最可能高收益方案**

主要风险：

- in-kernel exact topk 尤其 `topk=768` 很不划算，会爆 register/shared memory，降低 occupancy。
- 第一段 K2 pass 里没有最终 normalized K2 probability；exact K2 score 需要最终 denom，免费拿不到。
- `stage1_blockmax` 虽然 exact，但仍然计算完整 K1 pass，只是把 pool 融进写回；`hdim16_reduce_blockmax()` 还有 atomic/sync，慢是合理的。
- K1 mask 粒度是 64 个 K1 token；如果 K2 candidate 过宽，`fwdIterator` 跳过的 tile 不够多，收益会被 mask 生成成本吃掉。
- mask 输出需要清零/初始化，且 skipped `p` 必须是 `-inf`，否则 topk 会错。

最可能高收益方案：

单 kernel fused candidate：在现有 stage1 第一段 K2 pass 中生成粗粒度 K1 tile mask，第二段 K1 pass 立即用这个 mask。不要追 exact K2 topk；先做 block/tile-level candidate，目标是减少 K1 GEMM tile 数，同时避免第二次 `varlen_fwd_stage1`。

split-stage1 是备选：第一 kernel 输出 K2 denom + candidate/mask，第二 kernel masked K1。它比当前“两次 stage1”少一次完整 K2 score stage1，但多一次 kernel launch和 row_max/row_sum 写读。对长 prefill 可能仍有价值，但优先级低于单 kernel fused mask。
