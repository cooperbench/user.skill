## 高并发下 spec decode 加速缩水：根因分析 ### 核心矛盾 Spec decode 的加速收益来源于： ``` speedup ≈ mean_accept_len / (t_draft + t_verify) ``` 但这个公式成立的前提是 **target model 处于 memory-bandwidth-bound 状态**（单 req decode 时就是这样）。高并发打破了这个前提： | 维度 | 低并发 (bs=1) | 高并发 (bs=N) | |---|---|---| | Target decode 瓶颈 | HBM bandwidth-bound | 逐渐 compute-bound | | Spec 的本质收益 | 用 draft compute 掩盖 bandwidth latency | Draft overhead 纯是附加负担 | | Accept_len 分布 | 可最大化利用 tree | 不同 req accept_len 不同 → padding waste | | Draft forward 成本 | 轻量 (bs=1, memory-bound) | bs=N 后 draft 自身也变 compute-bound | **一句话**：spec decode 优化的是 per-request latency，不优化 throughput。高并发时 GPU 已计算饱和，draft 的额外 forward 是纯开销。 --- ### 当前系统的额外问题 针对 MiniCPM-SALA + EAGLE-3： 1. **Draft model 有 GLA layers**：GLA 的 state propagation 在高 bs 下可能还在走 sequential mode，draft forward 随 bs 几乎线性增长 2. **Tree verify 的 padding 浪费**：bs=N 时每个 req 有不同 dtn，verify 的 attention 需要对齐到 max_dtn，低 accept_len req 的空位是废计算 3. **KV cache 带宽争用**：Draft KV + Target KV + GLA state 三者同时压 HBM，高并发时带宽墙提前到来 --- ### 突破性方向（按实现 ROI 排序） **P0（立即可做）：Adaptive spec bypass** 监控当前 batch size，超过阈值时跳过 draft，直接 target-only decode： ```python # 伪代码：在 forward_batch_generation 入口 if len(batch.reqs) > SPEC_BYPASS_BS_THRESHOLD: return self.target_only_forward(batch) ``` 高并发时 spec 的净收益已经是负的，bypass 直接省掉 draft forward + verify overhead。阈值需要 bench 标定（大概 bs=16-32 左右开始得不偿失）。 **P1（需要实验）：Draft GLA 切 chunk-parallel scan** 当前 draft GLA 在 bs>1 时如果走 sequential scan，时间复杂度 O(bs × seq_len)。GLA 支持 chunk-parallel mode，高并发下可以以 chunk 为单位做并行扫描，draft throughput 能显著提升。需要检查 `fused_chunk_gla` vs `chunk_gla` 的 dispatch 逻辑。 **P2（架构级突破）：Medusa-style speculation heads** 不用独立 draft model，直接在 target model 最后几层上挂若干 MLP speculative heads（Medusa V1 思路）。高并发友好的核心原因： - 没有独立 draft forward，spec candidate 和 target forward 合并在一次 pass 里 - KV cache 只有一份（target），无争用 - bs 扩大时 spec heads 的 compute 和 target 线性同步，没有 "double forward" 问题 缺点是需要训练 spec heads，且 MiniCPM-SALA 的混合架构（GLA + Attention）让 spec heads 的 context 取哪层是个设计问题。 **P3（系统级）：Disaggregated prefill-decode + spec** 把 spec decode 限定在 decode-only 阶段，prefill 和 decode 分离到不同资源（单 GPU 上通过时间片轮转）。这样 spec decode 永远只看 decode batch，batch size 相对可控，可以维持低 bs 的高 accept_rate。 --- ### 最快见效的建议 先做 **adaptive bypass**——在 `eval/start_eagle.sh` 里加一个 `EAGLE_SPEC_MAX_BS=24` 的阈值，超过就 fallback target-only。这是一个保守但立即有效的做法，能确保高并发时不因 spec overhead 反而变慢，低并发时继续享受 spec 加速。
