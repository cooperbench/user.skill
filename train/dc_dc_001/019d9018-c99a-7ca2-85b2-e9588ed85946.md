以下结论只基于静态阅读，没跑测试或 benchmark。当前默认 EAGLE-3 配置是 `spec_steps=1, topk=2, dtn=3`，见 [start_eagle.sh](/user_4813494d/openbmb/eval/start_eagle.sh#L17) 和 [start_eagle.sh](/user_4813494d/openbmb/eval/start_eagle.sh#L33)。同时 `topk>1` 会被 spec v2 直接拦住，所以这条默认线上路径实际是 spec v1，不走 overlap scheduler，见 [server_args.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/server_args.py#L2096)。

**1. 关键路径**
1. 调度入口先把 decode batch 从 `ScheduleBatch` 变成 `ModelWorkerBatch`，再变成 `ForwardBatch`。spec v2 的开关在 `ScheduleBatch.is_spec_v2` 和 `prepare_for_decode()`，但当前 `topk=2` 下默认走不到，见 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1933) 和 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1939)。

2. draft 侧先做候选展开。v1 路径在 `_draft_preprocess_decode()` 里分配 speculative KV slot、必要时复制 page tail，然后 `draft()`/`draft_forward()` 产出 tree 候选，见 [eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L446)、[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L595)、[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L678)。但当前 `spec_steps=1` 时不会 capture `EAGLEDraftCudaGraphRunner`，所以“draft 树展开图”不是当前主热路径，见 [eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L298)。

3. tree materialization 由 `build_tree_kernel_efficient()` 生成 `tree_mask / positions / retrieve_*`。v2 已经能把 `tree_mask` 和 `position` 直接写进 target verify buffer，见 [eagle_utils.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L47) 和 [eagle_worker_v2.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker_v2.py#L313)。

4. target verify 是当前最关键的 graph 路径。`CudaGraphRunner` 在 EAGLE/EAGLE3 下直接把 capture 模式改成 `TARGET_VERIFY`，`num_tokens_per_bs=dtn`，见 [cuda_graph_runner.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/cuda_graph_runner.py#L275)。replay 时会先 padding、拷贝静态 buffer、重建 attn metadata，然后 replay 图，见 [cuda_graph_runner.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/cuda_graph_runner.py#L843) 和 [cuda_graph_runner.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/cuda_graph_runner.py#L919)。

5. MiniCPM target verify 内部又分两条。标准注意力层走 FlashInfer prefill-wrapper verify 路径，专门维护 verify workspace 和 `verify_kv_*` buffer，见 [minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1509)、[minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1766)、[minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L2037)。24 层 GLA 在 `TARGET_VERIFY` 下走 fused recurrent verify，把每步中间状态写到 `intermediate_ssm`，accept 后再做 state scatter，见 [hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1807) 和 [hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1525)。

6. verify 完成后，`EagleVerifyInput.verify()` 会做 accept/reject、KV compact/free，再进入 next-round draft extend；这一步本身也可能走 draft-extend graph，见 [eagle_info.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py#L216)、[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L754)、[eagle_draft_extend_cuda_graph_runner.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_draft_extend_cuda_graph_runner.py#L374)。

**2. 最重要的优化点**
1. 让 `topk>1` 的 EAGLE-3 真正走通 spec v2 / overlap。收益最高，因为当前默认 `topk=2` 正好把 v2 卡死，现有 `plan_stream + replay_prepare + direct-write verify buffers` 基础设施已经在，但没有闭环。复杂度高。风险是 grammar、page-size>1 和 overlap scheduler 的正确性耦合很深。关键引用：[server_args.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/server_args.py#L2096)、[eagle_worker_v2.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker_v2.py#L66)、[eagle_info_v2.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info_v2.py#L214)。

2. 把 GLA verify 从“线性串行”改成“树感知 state 管理”。这是 accept length 的最大语义瓶颈；现在 topk>1 时 sibling branch 共享线性状态，标准注意力的 tree mask 无法修复 24 层 GLA 的污染。收益很高，既可能提 accept，也可能让更激进的 `topk/spec_steps` 变得可用。复杂度高。风险在 `intermediate_ssm`、`mamba_track`、rollback 语义非常容易出错。关键引用：[hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1807)、[hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1525)、[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L856)。

3. 消掉 draft -> verify -> draft-extend 的 KV slot 分配和搬运抖动。现在 v1 一轮里会分配 draft slots、可能复制 page tail、verify 前释放 draft slots、再给 target verify 重新分配、verify 后还要 compact/move accepted KV。收益中高，尤其在并发和 `page_size>1` 下会直接打到 HBM 带宽和 allocator 压力。复杂度中高。风险是预留过多 slot 会抬高常驻显存，page 对齐逻辑也容易错。关键引用：[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L462)、[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L758)、[eagle_info.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py#L104)、[eagle_info.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py#L463)。

4. 把 tree metadata 和 verify metadata 的 buffer ownership 收敛成一套。现在 v2 只把 `tree_mask/position` 直接写进 target verify buffer，但 `retrieve_*` 仍是临时分配；同时 v1/v2 都依赖 `skip_attn_backend_init` 和多次改写 `batch.forward_mode/spec_info/out_cache_loc`。收益中高，更多体现在稳定性和尾延迟，而不是单次 kernel 时间。复杂度中。风险是重构面广，但这是后续继续做 overlap、KV arena、graph 专用化的基础。关键引用：[base_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/base_attn_backend.py#L60)、[eagle_utils.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L47)、[cuda_graph_runner.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/cuda_graph_runner.py#L843)、[tp_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/tp_worker.py#L423)。

5. 给 EAGLE 单独收窄 cuda-graph capture 集和 padding 策略。现在 graph batch size 来自通用 spec 规则，target verify、draft extend、draft multi-step 共享一套大而保守的 capture 形状；而当前默认 `spec_steps=1` 下，真正热的是 target verify，不是 multi-step draft graph。收益中等，但很实在，主要是减少 capture 时间、静态 buffer 占用和 padding 浪费，给 `max_running_requests` 留更多空间。复杂度中。风险是 capture 形状过窄会增加 eager fallback。关键引用：[server_args.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/server_args.py#L1002)、[cuda_graph_runner.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/cuda_graph_runner.py#L189)、[input_buffers.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/input_buffers.py#L35)、[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L298)。

**3. 我对优先级的判断**
如果只做一件事，先做 `topk>1 spec v2`。这是当前配置和当前代码最明显的“架构收益被开关挡住”。

如果只做一件偏内核/语义的事，先做 GLA tree-aware verify。这个点最可能直接提高 accept length，也最可能决定 EAGLE-3 能不能继续把 `topk` 往上推。
