> AGENT

## `max_seq_len` 是什么 它不是一个统一概念，**3 个层面要分清**，不然会搞混： ### 1. 模型层面 — `max_position_embeddings`（硬上限） ``` config.json: max_position_embeddings = 524288 (512K) ``` RoPE 设计上能编码的最大 position。**超过这个就是 OOD**，模型没见过、外推会乱。这是 ceiling，改不了（除非换 base / YaRN 拉伸）。 ### 2. Server 层面 — `--context-length`（运行时上限） **SGLang server 的硬约束**：一个请求 `prompt_tokens + max_new_tokens` 不能超过它，超了直接 reject（HTTP 400 "context length exceeded"），KV cache 也按这个尺寸预分配。 - 如果命令行**没传** `--context-length`（`start_eagle.sh` 就是这种）→ **默认 = `max_position_embeddings` = 524288** - 也决定了 KV pool 大小，间接影响能塞下多少并发请求 ### 3. 客户端脚本层面 — eval 里的 `--max-seq-len=262144` **只是 eval 脚本的内部常量**，干两件事： ```python max_prompt_len = min(args.max_seq_len - 65536 - 300, 128000) # 算给自己看 print(f"[full-eval-live] max_prompt_len={max_prompt_len}") # print 完就完事 ``` **没传给 server，也没用来截断 prompt**。注释里写"Keep aligned with toolkit/eval_model.py"——意思是要和官方评测工具的同名常量保持一致，是个"声明性"配置，不是 enforcement。 --- ### 三者关系 ``` [模型硬上限] 524288 (RoPE 设计极限,改不了) ↓ ≤ [server --context-length] 默认 524288 (start_eagle 没传 → 取模型默认) ↓ ≤ [eval --max-seq-len] 262144 (脚本自己的"心理上限",仅用来推导 max_prompt_len) ↓ -65536-300 ↓ 又 cap 128000 [max_prompt_len] 128000 (但未生效,只 print) ``` ### 实际影响 - **eval（150 条）**：input max 127738 + max_tokens 65536 = 193274 < 524288 → 全部能跑，没人会被 server reject - **bench/data_full/cunlimited**：16 条 prompt > 256K，其中部分 = 524288 → 顶到模型硬上限，**server context length 默认就是 524288**，所以不会 reject，但加上 completion 就会超 → 实际 bench 时这些 sample 的 `max_tokens` 是按 dataset 自带 `completion_tokens` 设的（custom dataset 模式），加起来也接近/等于 524288，会卡边界 ### 你常会想问的两个误区 - ❌ "eval 的 `--max-seq-len=262144` 限制了 server" → **不**，eval 这个参数完全没传给 server - ❌ "把 server `--context-length` 调大能让模型支持更长" → **不**，模型硬上限是 `max_position_embeddings`，调大 server 参数只会让 server 接受请求，但模型 RoPE 编码到 524288 之外就开始外推/废掉 简单记：**`--context-length` 是 server 的闸门，`max_position_embeddings` 是模型的脑子**。
