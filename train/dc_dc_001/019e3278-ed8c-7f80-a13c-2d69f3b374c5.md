**1. 当前 Prefill 数据流和关键参数**

- 目标模型配置是 32 层，其中 `minicpm4` sparse standard attention 层是 8 层：0,9,16,17,22,28,29,30；其余 24 层是 `lightning-attn` GLA。[config.json](/user_4813494d/models/openbmb/MiniCPM-SALA-gptq46-calib90-90k-NVFP4-det/config.json:34)
- sparse 配置：`block_size=64`、`window_size=2048`、`topk=64`，代码里实际 `sparse_topk = 64 + 2048/64 = 96`，所以 stage2 每行最多看 `96*64=6144` token。[config.json](/user_4813494d/models/openbmb/MiniCPM-SALA-gptq46-calib90-90k-NVFP4-det/config.json:89)，[minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py:412)
- `dense-as-sparse` 会把 `dense_len` 置 0，长 prefill 走全 sparse 快路径。[minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py:417)
- `HybridLinearAttnBackend` 统一初始化 full sparse backend 和 SimpleGLA backend；standard 层分发到 `MiniCPMSparseBackend.forward_extend`，lightning 层分发到 `SimpleGLAAttnBackend.forward_extend`。[attention_registry.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/attention_registry.py:237)，[hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py:1751)
- standard sparse prefill 主链路：`MiniCPMAttention.forward` 做 FP4 QKV 投影 → `RadixAttention` → `MiniCPMSparseBackend.forward_extend` 保存 KV → 压缩 K1/K2 → stage1 选 topk blocks → 生成/直写 FlashInfer metadata → 用 FlashInfer decode wrapper 做 row 化 sparse stage2。[minicpm.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py:926)，[minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py:1315)
- 关键点：all-sparse prefill 下 `sparse_max_seq_len_q=1`，所以 FlashInfer 侧判断成 decode-style，而不是 dense prefill wrapper；这也是 `extend_sparse_fa` 实际用 decode wrapper 的原因。[minicpm_sparse_utils.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py:1690)，[minicpm_attention_kernels.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_attention_kernels.py:637)
- GLA prefill 主链路：`MiniCPMLightningMixer.forward` 做 QKV 投影，默认脚本开启 OOP fused q/k norm + rope，然后 `SimpleGLAAttnBackend.forward` 在 `seq_len >= 64` 时走 `chunk_simple_gla`，最后 fused `o_norm+sigmoid+mul` 和 `o_proj`。[minicpm.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py:1058)，[hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py:2266)

**3. 仍慢或有研究空间的位置**

- MLP 仍是最大块之一。文档指出 gate_up BF16 中间态约 512MB/chunk，真正高 ROI 是做 SM120 dense-only `gate_up_swiglu_fp4` epilogue，直接从 accumulator 生成 FP4 activation+scale，绕过 BF16 gate_up 写回/读回。[current.md](/user_4813494d/openbmb/docs/prefill/current.md:432)
- sparse stage2 仍贵：当前是 per-token/head-group row 化后用 FlashInfer decode wrapper。page64、blocksplit、Triton direct 已试过但没穿透 wall；下一步更像是 KV/block layout 或 custom block-sparse stage2 kernel，而不是再调 wrapper 参数。[current.md](/user_4813494d/openbmb/docs/prefill/current.md:397)
- stage1 不能靠缩 topk/candidate 做近似。文档明确硬边界：候选集合/截断 topk 默认破坏一致性；高收益只能是 exact fused `score→pool→topk` CUDA/C++ 重写。[current.md](/user_4813494d/openbmb/docs/prefill/current.md:25)，[current.md](/user_4813494d/openbmb/docs/prefill/current.md:345)
- GLA 简单调参空间基本枯竭：`chunk_simple_gla` 被记录为接近下限，替换 chunk kernel/API 的尝试有不一致或更慢；可能的研究方向是形状特化等价 kernel或改变 qkv/layout。[current.md](/user_4813494d/openbmb/docs/prefill/current.md:276)
- host 侧还有空间：history 里的 nsys 显示 CUDA graph instantiate、cudaDeviceSynchronize、cuLibraryLoadData 和 Python/scheduler metadata 占比不小；这类优化更偏 runtime/调度，不是单个 kernel 替换。[history.md](/user_4813494d/openbmb/docs/prefill/history.md:117)
- `chunked-prefill-size=16384` 已记录为端到端更慢，不能作为直接扩 chunk 的方向。[current.md](/user_4813494d/openbmb/docs/prefill/current.md:328)
