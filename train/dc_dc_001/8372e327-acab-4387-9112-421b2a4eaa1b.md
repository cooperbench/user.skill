EKF是什么 王司马要做ekf

> AGENT

EKF 是 Extended Kalman Filter，扩展卡尔曼滤波器。 ## 干什么用的 它是一个**传感器融合算法**。这个项目里有两个传感器：GNSS 给位置 (x, y)，IMU 给航向和加速度。两个传感器各有缺点——GNSS 更新慢、有跳变噪声；IMU 更新快但会漂移。EKF 的作用就是把两者融合成一个比单独用任何一个都更准的状态估计 `[x, y, yaw, speed]`。 ## 怎么工作的 每帧两步： **Predict（预测）**：用 IMU 的角速率和加速度，按运动学公式往前推一步——"根据上一帧的状态和 IMU 读数，我猜这一帧车应该在哪"。推的过程中不确定性会增大（协方差变大）。 **Update（更新）**：拿 GNSS 的实际测量位置和预测位置比较，算出差值（新息），然后按一个权重（卡尔曼增益）修正预测值——"GNSS 说我实际在这里，和我的预测差了这么多，那我修正一下"。修正后不确定性降低（协方差变小）。 卡尔曼增益是自动算的：GNSS 噪声大时更信 IMU 预测，IMU 累积漂移大时更信 GNSS 量测。 ## 为什么叫"扩展" 标准卡尔曼滤波要求系统是线性的，但车辆运动学方程 `x += v·cos(yaw)·dt` 是非线性的。EKF 的做法是对非线性方程在当前状态点做一阶泰勒展开（算雅可比矩阵），近似成线性，然后套标准卡尔曼流程。项目代码里 predict 函数中那个 `jacobian` 矩阵就是干这个的。 ## 和这个项目的关系 EKF 是整个攻防实验的核心目标——攻击打的就是送进 EKF 的传感器数据，让融合结果出错，进而让控制器做出错误决策。Phase 4 的实验还发现，有些 IMU 攻击打不坏纯 GNSS 直定位，但能打坏 EKF，说明融合过程本身也引入了额外的脆弱性。

你是问为什么选这几种攻击方式、现实中有什么对应？ ## GNSS 欺骗（GPS Spoofing） 现实中已经有成熟的攻击手段。攻击者用一个信号发射器广播伪造的 GPS 信号，功率比真卫星信号强，接收机会锁定到假信号上。 - **恒定偏置**对应的场景：攻击者发射一组固定偏移的伪信号，让接收机持续认为自己在偏移后的位置。这是最简单的 spoofing 方式。 - **渐进漂移**对应的场景：攻击者先发射和真信号一致的伪信号让接收机锁定（叫 lock-and-drag），然后慢慢偏移。这种方式更隐蔽，因为每帧变化很小，不容易被突变检测器发现。 这两类已经在实际中被演示过，包括对无人机、船舶、Tesla 等的 GPS 欺骗实验。 ## IMU 攻击 IMU 内部是 MEMS 陀螺仪和加速度计，物理上可以被声波/超声波/电磁干扰影响。 - **航向偏置**对应的场景：通过电磁干扰让磁力计（compass）产生恒定偏差，或者直接篡改 IMU 通信总线上的数据。 - **陀螺仪偏置**对应的场景：用特定频率的声波/超声波让 MEMS 陀螺仪谐振，产生持续的角速率偏差。这个已有论文实验验证过。 IMU 攻击比 GNSS 欺骗难度更高，需要更近的物理距离，所以项目实验结果也反映了这一点——IMU 攻击的致效门槛（10°~30°）远高于 GNSS 攻击（不到 1 米就能打坏）。 ## 联合攻击 同时攻击 GNSS 和 IMU。现实意义在于：如果防护机制靠跨传感器一致性检测（GNSS 说的位置和 IMU 积分出来的位置对不上就报警），单独攻击一个传感器容易被抓到。联合攻击可以让两个传感器的篡改结果"自洽"，绕过一致性检测。 ## 攻击参数量级的依据 Phase 3 扫描范围不是随便选的： - GNSS 偏置 0~10m：民用 GPS 精度本身就有几米误差，攻击偏置在这个量级内最有实际意义，太大了不现实（车明显跑偏司机就能感知到） - GNSS 漂移 0.1~2.0 m/s：对应渐进欺骗的典型速率 - IMU 航向 0°~30°：超过 30° 的航向偏差攻击成本太高且太容易被检测 这些范围覆盖了从"刚好能被检测到"到"必然致效"的整个区间，Phase 4 PSO 再在临界区间里精确搜索最小有效攻击。

不完全一样，但刻意对齐了。项目里实际有**三套控制器**： ## 1. 官方控制器 (`official_pid`) 直接实例化 CARLA 自带的 `LocalPlanner`，读真值位姿，只作为对照基线。PID 增益参数传的和我们自己控制器一样的值（`kp=1.95, ki=0.05, kd=0.2` 等），保证对比公平： ```118:143:src/graduate_phase1/runtime/carla/routing.py planner = LocalPlanner( vehicle, opt_dict={ "dt": config.carla.fixed_delta_seconds, // ... PID 参数和我们自己的控制器用同一组配置 "K_P": config.waypoint_pid.kp, "K_I": config.waypoint_pid.ki, "K_D": config.waypoint_pid.kd, // ... }, ) ``` ## 2. 我们的 waypoint PID 控制器 (`pid_waypoint`) `WaypointPIDVehicleController`，这是实际做攻防实验用的主控制器。**和官方的区别：** **相同的地方：** - 都是 waypoint 队列 + PID 的思路 - 横向用航向偏差做 PID，纵向用速度偏差做 PID - PID 增益参数用同一组值 - 转向限幅（`steer_rate_limit = 0.1`） **不同的地方：** - 官方控制器输入是 `vehicle.get_transform()` 真值位姿，我们的输入是 EKF 输出的估计状态 - 官方控制器内部自己管 waypoint 队列和目标点选择，我们的用自己实现的 `WaypointPlan.target()` 来选目标点 - 我们加了转向速率限制（每帧最多变化 0.1），官方没有这个 ## 3. Stanley 控制器 (`stanley`) `VehicleController`，备选方案，和官方完全不同的横向控制算法（Stanley 法而不是 PID）。Phase 1 试过之后没有作为主控制器使用，实际攻防实验用的都是 `pid_waypoint`。 ## 怎么证明"一样" Phase 1 benchmark 里跑 `official_pid` 时，同时挂了一个 shadow controller（`WaypointPIDVehicleController`），两个控制器用同样的真值输入，逐帧比较输出的 steer/throttle/brake。最终 18 条路线的跟踪误差差值 0.0003m，说明两者在真值输入下行为基本一致。 所以准确说法是：**控制算法思路一样（waypoint + PID），参数一样，但实现是独立的，不是直接调用官方代码。** 独立实现的目的是能接受 EKF 输出作为输入，而不是绑死在真值位姿上。

测试流程是给一个起点和终点吗？ 然后在中间制造攻击

> AGENT

对，就是这样。具体流程： **1. 给定起点和终点。** 在地图的 spawn points 里指定一对索引，比如 Town03 的 `80 → 219`。 **2. 规划路线。** 用 CARLA 的 `GlobalRoutePlanner` 在高精地图上算出从起点到终点的 waypoint 序列，这条路线在整个实验过程中固定不变。 **3. 车开始跑。** 同步模式每帧 0.05 秒，传感器采集 → EKF 融合 → 控制器跟踪路线 → 施加控制量，循环执行。 **4. 攻击在中途触发。** 由 `AttackConfig` 的 `t_start` 控制什么时候开始。比如 Phase 3 扫描统一设的 `t_start = 3.0` 秒——前 3 秒正常跑（让车起步稳定），第 3 秒之后开始篡改传感器数据。`duration` 控制持续多久，设 `-1` 就是一直持续到结束。 **5. 终止条件。** 三种情况之一就停： - 到达终点（距终点 < 4 米） - 发生碰撞或驶出道路 - 跑满最大步数（比如 2200 步 = 110 秒仿真时间） **6. 记录结果。** 每帧的真值位姿、EKF 估计、原始/篡改传感器数据、控制量、跟踪误差全部写入 CSV，最后输出 summary（完成率、碰撞次数、最大跟踪误差、首次失效时刻等）。 Phase 3 和 Phase 4 就是批量重复这个流程——同一条路线跑几百次，每次换不同的攻击参数配置，最后汇总出失效率曲线。
