# SGLang SOTA Performance

## Overview

Use this skill as the top-level optimization loop for one model at a time.
It composes two lower-level skills:

- `llm-serving-auto-benchmark`: search and compare best deployment commands across SGLang, vLLM, and TensorRT-LLM.
- `llm-torch-profiler-analysis`: capture or analyze torch-profiler traces and produce kernel, overlap-opportunity, and fuse-pattern tables.

This skill's goal is not "run one benchmark." Its goal is a reproducible
SGLang improvement loop: tune every framework fairly, prove whether SGLang is
behind, explain the gap with profiler evidence, patch SGLang, and re-run the
same model workload until the result is SOTA for the target environment.

Treat "SOTA" as "best observed, reproducible performance under the recorded
model, workload, hardware, framework commits, precision, and SLA." Do not claim
global SOTA without enough external evidence.

## Motivation

Replace intermediate state buffers with last_steps for speculative decoding. All conv and SSM states are now lazily updated inside their kernels based on last_steps, removing state-copy sync operations during post-target-verification and simplifying the update path.

## Modifications

### Speculative Decoding State Management

* Replaced usage of `intermediate_states_buffer` and `intermediate_conv_window_cache` with a new `last_steps` tensor, which tracks the last accepted step index for each sequence in speculative decoding. This change is reflected in both the Triton kernel and the Python wrapper functions, streamlining state tracking.
* Updated speculative state update logic in `update_mamba_state_after_mtp_verify` to set `last_steps` directly, removing the need to scatter intermediate states into caches which is slow due to cpu<->gpu sync

### Triton Kernel and Interface Changes

* Modified Triton kernel signatures and logic to accept `last_steps_ptr` instead of intermediate state buffers, and adjusted stride calculations to support the new state layout.
* Updated stride and shape calculations in convolution state handling to support the new speculative decoding state layout.

### Hybrid Linear Attention Backend

* Refactored the hybrid linear attention backend to use `last_steps` for speculative decoding, removing references to intermediate state caches and updating the logic for state updates and acceptance.

### Mamba Radix Cache
* This PR maintains full backward compatibility with existing Mamba radix/prefix caches. As long as the last_steps tensor is transferred from the radix cache when initializing a new sequence’s Mamba cache, both SSM state updates and convolution state reconstruction will remain correct.

## 一、PR #12892 的真正做法（从实际 diff 还原）

PR 不是简单消除 state copy，而是**数据结构级改造**：

| 维度 | 旧 (`main`) | 新 (PR #12892) |
|---|---|---|
| SSM state | 两份：`ssm_states[L, N, HV, K, V]` + `intermediate_ssm[L, N, dtn, HV, K, V]` | 合并为一份 `ssm_states[L, N, dtn, HV, K, V]` |
| Conv state | `conv_states[L, N, dim, K-1]` + 每 verify 一次 `conv_states.clone()` | `conv_states[L, N, dtn, dim, K-1]`，不 clone |
| Post-verify 后处理 | `ssm_states[:, idx, :] = intermediate_ssm[:, idx, last_steps]` + conv 同款（两次大 D2D scatter） | 一条 `mamba_caches.last_steps[idx] = accepted_indices`（纯 index 赋值） |
| Kernel 读起始 state | 直接读 `ssm_states[idx]` | 读 `ssm_states[idx] + last_steps[idx]*HV*K*V`，kernel 里 lazy 定位 |

**省的不是 verify 内的写入**，verify 阶段 kernel 照样每步写一份；**省的是 post-verify 的 D2D scatter + 它隐含的 CPU↔GPU sync**，以及 conv 的 `clone()`。

## 二、映射到我们 SimpleGLA 路径

`demo-sala/.../hybrid_linear_attn_backend.py`：

**结构上完全同构**：
- `spec_cache.intermediate_ssm[cache_idx, :bs, :dtn]`（L2014）= PR 的 `intermediate_states_buffer`
- `HybridLinearAttnBackend.update_mamba_state_after_mtp_verify`（L1632-1699）= PR 改掉的 scatter 热点，我们还**多跑一次 mamba_track 路径**（L1680-1699，给 prefix cache 用的，我们本地特有）
- EAGLE verify 完调用点：`eagle_worker.py:989`

**差异 1：我们已经做了一半**

`simple_gla_decode_update_fwd`（`simple_gla_decode_kernel.py:220`）docstring 明说："removes the surrounding `state[indices].contiguous()` gather and `state[indices] = final_state` index_put"——这就是 decode 路径的 "state in-kernel 读写"。**方向一致，但只覆盖 decode，不覆盖 target_verify**。

**差异 2：我们 verify kernel 已经别名到最终 buffer**

L2011-2014：
```python
# ht_buf aliases intermediate_ssm slice directly — kernel writes into final destination
ht_buf = intermediate_ssm[cache_idx, :batch_size, :draft_token_num]
```
→ verify 阶段 kernel 写的已经是 "最终目的地"；但 `intermediate_ssm` 和 `temporal` 仍是**两份独立张量**，post-verify 那条 scatter 还在。

**差异 3：GLA 无 conv1d**

`SimpleGLAAttnBackend._init_track_conv_indices` 直接 return None。所以：
- `conv_states.clone()` 省不到——**我们本来就没有**
- `intermediate_conv_window` scatter 对 GLA layer 是空操作（`has_conv=False`）
- PR 里 conv1d_triton kernel stride 改造那 179 行**完全不用搬**

→ **我们能吃到的只有 SSM 那半边收益**，不是完整 9.47%。

## 三、具体能省的三处（按收益估）

**1. `update_mamba_state_after_mtp_verify` 主 scatter（L1669）** ⭐⭐⭐

每次 verify 做一次 `ssm_states[:, dst, :] = intermediate_ssm[:, src, last_steps].to(...)`

粗估量：24 GLA layers × bs × 16 heads × 128 × 128 × 4B = **24 MB × bs** per verify。bs=8 → 192 MB D2D → ~190 µs @ HBM ~1TB/s。单 verify 占比不大，累计到 e2e 能量化。

**2. `mamba_track` 二次 scatter（L1691）** ⭐⭐

我们本地特有，prefix cache 用。同样大小再来一遍。PR #12892 不碰这块，需要我们自己套同一个 `last_steps` 协议改。

**3. CPU↔GPU sync** ⭐

`valid_mask = accepted_steps >= 0` + `.to(torch.int64)` 的布尔 index + advanced indexing 容易触发 host 同步。PR 作者原话 "removing state-copy sync operations"——他们观测到了这类 sync。我们这边需要 profile 确认。

## 四、预估收益

PR 数据点：H200 × Qwen3-80B-FP8 × (topk=1, steps=3, dtn=4) → +9.47%

我们场景：
- 模型 4B（小 20×），每 decode 步基础时间短 → scatter 相对占比**更大**
- 但 GLA 无 conv → 只吃一半 → 回补
- dtn=5 vs 4 → intermediate 略大 → 略回补
- 加上我们自有的 mamba_track 路径也搬的话 → 再回补

**粗估：3-7% e2e**。要 profile 才能定死。

## 五、风险（为什么 PR 还 open）

1. **上游 PR 状态 OPEN**：`hebiao064` 标 "Changes requested"，未 merge；方案还在审。合进来的最终版本可能和当前 diff 差异不小
2. **CUDA graph capture**：`ssm_states` 扩一维（加 `dtn`）意味着 stride 变、capture buffer 布局要跟着改。**我们 demosala-rollback 的回退原因就是"draft CUDA graph capture 有观察到明显退化"**——这类数据结构改造正是 capture 退化的高危来源
3. **Radix cache 兼容**：`MambaPool.SpeculativeState` 层级要多传 `last_steps`；radix 保存/恢复路径要跟着改
4. **mamba_track 不是 upstream 功能**：我们得自己把 track 路径也切到 `last_steps` 语义，或者接受 track 那半边仍旧 scatter

## 六、建议——两步走

**Step 1（低风险、大部分收益）**：先只改 post-verify 路径

不动 `MambaPool` 数据结构，只改 `update_mamba_state_after_mtp_verify`：
- 把 `accepted_steps >= 0` 的 mask + `.to(int64)` 换成 device-only 的等价计算（避 sync）
- 把两次大 scatter 换成延迟写：存 `last_steps` 张量，verify 读 `intermediate_ssm[idx, last_steps]` 起步
- `intermediate_ssm` 数据结构保留

收益估 2-5%，改动局限在两个文件（`hybrid_linear_attn_backend.py` + 一个 kernel 的 base offset），**CUDA graph capture 不变**，风险可控。

**Step 2（高风险、剩余收益）**：合并 buffer，扩 `ssm_states` 的 `dtn` 维

这步才需要碰 `memory_pool.py` 和 CUDA graph layout。等 upstream PR 定稿、确认最终方案不踩 capture 地雷再做。
