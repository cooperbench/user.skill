**1. 已有能力边界**

- `demo-sala` 里正式可用的 sparse prefill 主线已经比较完整：K 压缩 + InfLLMv2 stage1 打分 + pool/topk + FlashInfer sparse stage2。关键代码在 [minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py)、[minicpm_sparse_utils.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py)、[minicpm_attention_kernels.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_attention_kernels.py)。
- FlashInfer wrapper 已有生产级优化：plan cache、cross-forward buffer refresh、direct topk -> FlashInfer indices。direct 路径在 [minicpm_sparse_stage2.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_stage2.py)，但强依赖 `block_size=64`、all-sparse fast path、page size 1 的当前 KV 布局。
- `kernels/infllmv2_cuda_impl/` 是完整 InfLLMv2 CUDA extension，不只是 bench。它有 stage1、varlen sparse attention、KV-cache fwd/bwd、blockmask/topk 转换，见 [infllmv2_sparse_attention.py](/user_4813494d/openbmb/kernels/infllmv2_cuda_impl/infllm_v2/infllmv2_sparse_attention.py) 和 [setup.py](/user_4813494d/openbmb/kernels/infllmv2_cuda_impl/setup.py)。边界是：主要覆盖 bf16、hdim 64/128、FlashAttention 派生路径；SM120 可编译，但 paged KV 对 page/block 连续性要求与当前 `page_size=1` 生产布局冲突。
- GLA 相关主要是 decode / verify 路径资产，不是 prefill 主瓶颈。当前可复用的是 SimpleGLA decode、target verify state copy、tree-aware verify 等，见 [hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py) 和 [simple_gla_decode_kernel.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/simple_gla_decode_kernel.py)。
- FP4/NVFP4 正式路径在 [modelopt_quant.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/quantization/modelopt_quant.py)：FlashInfer/CUTLASS FP4 GEMM、cuDNN GLA qkv 特化、Marlin decode threshold、fused activation quant input。`kernels/experiments/` 和 `bench/kernels/` 里还有 GEMV、FP8 decode、b12x、blockscale epilogue等原型，但多数是研究/bench 资产。

**2. 能迁入 demo-sala 的资产**

- 已经迁入且应保留默认的：FlashInfer plan cache、direct topk -> FlashInfer metadata、stage1 actual maxlen/direct pool、InfLLMv2 full-chunk trait guard、GLA qkv cuDNN exact-shape gate。
- 可作为受控实验迁入的：InfLLMv2 native stage2，但必须先解决 page layout、causal 语义、`nheads_k=2`、长上下文验证；否则不能替换 FlashInfer stage2。
- 可迁入测试体系的：`bench/kernels/` 和 `bench/infllmv2/` 里的 sparse stage1/stage2、FlashInfer metadata、FP4 backend microbench，适合变成回归 bench，而不是直接进提交包 runtime。
- 暂不建议迁入正式默认：b12x FP4 backend、NVFP4 GEMV/FP8 decode、page64 double-wrapper、Triton direct stage2、fast prefill stage1、fuse-topk。它们要么收益不足，要么语义/稳定性风险还没压住。

**3. 潜在高收益 prefill 方向**

- 最高收益方向是 MLP `gate_up` epilogue：把 `gate_up GEMM -> BF16 中间张量 -> SwiGLU -> FP4 quant` 融成 SM120 dense-only `gate_up_swiglu_fp4`，直接产出 down GEMM 的 FP4 activation + scale。`docs/prefill/current.md` 里已经指出 full chunk 会产生约 512MB BF16 中间读写，这是当前最值得攻的 prefill kernel 点。
- Sparse stage2 方向：降低 FlashInfer sparse stage2 register pressure，或让 wrapper 选择低寄存器变体。这个方向收益可能是几个百分点级别，但实现风险比重写 stage2 低。
- InfLLMv2 native stage2：如果能让当前 KV cache 以 block-contiguous/page>=256 的形式被它消费，并证明 causal/virtual-batch 语义一致，可能减少 FlashInfer plan/metadata/gather 开销。
- Stage1 融合方向：把 hdim16 reduce、max_pool、topk 更紧地融合，直接输出 topk。当前 stage1 仍是长上下文热点，但这里不能牺牲 topk 精确性，工程难度较高。

**4. 主要工程风险**

- 精度语义风险最大：prefill sparse causal 语义、FlashInfer virtual-batch 行为、InfLLMv2 varlen causal 行为、topk 顺序、pooling layout 都可能让答案漂移。
- KV layout 风险：当前生产是 page size 1，InfLLMv2 paged KV 和 page64 原型都更偏连续 block/page 假设，直接替换容易错。
- CUDA graph / wrapper 状态风险：FlashInfer wrapper 缓存内部 buffer 地址，plan cache 和 cross-forward refresh 一旦处理不严，会出现跨请求污染或 stale metadata。
- SM120/CUDA13 工具链风险：cuDNN FP4 只在严格 shape gate 下安全；b12x/CuTe DSL/AOT cache、FlashInfer 版本、平台 wheel pin 都可能导致本地可跑但提交环境失败。
- FP4/NVFP4 数值风险：任何 fused epilogue、GEMV、FP8 decode 都会改变 rounding/scale 路径，必须用 no-spec/spec 一致性、公开集 accuracy、长上下文混合 batch 一起验。
