**我的理解**
现在这条 `K=1 Medusa` 路径的核心问题，不是单一的 accept rate 不够，而是“bonus token 的第二步成本，被当前实现提前且平均地摊给了所有请求”。仓库文档其实已经把症状写出来了：`Smax` 退化、根因是高并发下 verify 成本接近翻倍，而 accept 只带来大约 `1.4x` 的 token gain，见 [medusa-optimization-notes.md](/user_4813494d/openbmb/docs/medusa-optimization-notes.md#L108) 和 [technical-notes.md](/user_4813494d/openbmb/docs/technical-notes.md#L196)。

我读代码后的判断是，这个结论在实现层面是成立的，而且问题比文档里写得更“结构性”：

- 当前 Medusa decode 会对每个请求都构造 `[verified_id, draft_0]`，然后统一走一次 `TARGET_VERIFY`，见 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L428)。这意味着第二步 bonus 的计算成本，是“全员先付”，不是“命中者再付”。
- GLA 这边在 `TARGET_VERIFY` 模式下，真的是按 `draft_token_num` 逐步循环执行，并保存每一步中间状态，见 [hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1659)。对 `K=1` 来说，就是 24 层 recurrent 状态机对所有请求硬跑 2 步，这个税非常重。
- FlashInfer verify replay 还有明显的 CPU/for-loop 元数据开销：每轮重建 `kv_indptr`、逐请求 flatten `kv_indices`、再 `plan()` 一次，见 [minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L2033)。高并发下这部分会被放大。
- Medusa 自己补的 sparse slot 分配也是 Python 循环 + `.item()` + 单 token alloc，见 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L619)。而普通 decode 走的是更成体系的 bulk 分配路径，见 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1996) 和 [common.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/mem_cache/common.py#L505)。
- 还有一个很实际的放大器：混合 `Marlin/CUTLASS` 的阈值是按 `M` 判的，见 [modelopt_quant.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/quantization/modelopt_quant.py#L1342)。Medusa verify 把很多层的 `M` 从 `bs` 变成了 `2bs`，会更早把 decode 从 Marlin 优势区推到 CUTLASS 区。

**我认为最对的方向**
1. 主方向不是“继续一遍 verify 两个 token”，而是改成 `2-pass selective verify`。
第一遍对所有请求只做 `verified_id` 的正常 decode，拿到 `target_pred_0` 和下一轮 hidden state；第二遍只对“draft 命中”的子集再跑 bonus token。这会把第二步成本从“固定全量成本”改成“条件子集成本”。这是我现在最看好的方向。

2. 在 `2-pass` 基础上，再做“请求级”动态 spec，而不是“batch 级”开关。
不是按 `bs` 关 spec，而是按每个请求的 draft 置信度、entropy、或者在线 EMA accept 预估，决定它要不要进入 bonus 路径。这个方向和仓库笔记里提到的 token/embedding conditioning、Hydra/Speculator 一脉相承，见 [medusa-optimization-notes.md](/user_4813494d/openbmb/docs/medusa-optimization-notes.md#L136)。

3. 系统侧要把 Medusa verify 从“通用慢路径”改成“decode 专用快路径”。
我重点盯三块：
- verify 的 paged alloc 不该继续走泛化 `alloc_token_slots`
- sparse `k1/k2` 分配要改成 bulk/vectorized
- verify metadata replay 要尽量去 CPU、去 per-request loop、去重复 `plan`
这些是纯实现税，去掉后小 `bs` 和高并发都会受益。

4. 训练侧提高 accept 率是增益项，不是根治项。
像 token embedding conditioning、顺序依赖 head、KL/LK loss 都值得做，但如果 runtime 还是“全员先付第二步”，那 accept 从 `0.40` 拉到 `0.50` 也不够漂亮。训练侧应该放在 runtime 结构改完之后继续叠加。

**方案排序**
我现在会这样排优先级：

1. `2-pass selective verify`
目标：把“bonus 成本”变成“命中者成本”。

2. Medusa verify 专用 runtime 快路径
目标：删掉 CPU replay / generic alloc / Python sparse loop 这些系统税。

3. 请求级 confidence gating
目标：提高第二遍 bonus pass 的有效密度。

4. 训练侧提升 accept
目标：在新 runtime 上继续放大利润。

> AGENT

我仔细看完之后，结论很明确:

`2-pass selective verify` 值得做，而且方向是对的；但如果只是把现在这一套 `TARGET_VERIFY` 粗暴拆成两次前向，收益会被吃掉。真正该做的是:

第一遍用“正常 1-token decode”跑全 batch。  
第二遍只对“draft 命中”的子集，再跑一次“正常 1-token decode”。

也就是说，它名字虽然叫 `2-pass selective verify`，但落地不应该是“两次 verify”，而应该是“`decode(all)` + `decode(accepted-subset)`”。

**先用人话讲清现在的代码在干嘛**
当前 Medusa 的 K=1 其实是这样跑的：

- 每个请求先有一个已经确认的 token，叫 `verified_id`
- Medusa head 基于上轮 hidden state 猜一个 `draft_0`
- 然后代码把每个请求都拼成 `[verified_id, draft_0]`
- 接着让 target model 对全 batch 一次性把这两个位置都算出来
- 算完以后才知道哪些请求的 `draft_0` 真命中，哪些没命中

这个行为就在 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L416) 和 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L450)。

问题是：第二个 token 的计算成本，现在是“所有请求先一起付”，不是“只有命中的请求才付”。

这就是高并发下 spec 变难看的根因。

**为什么高并发会掉**
因为这条 verify 路径不只是多一个 token 那么简单，它还触发了几层额外成本：

- GLA 在 `TARGET_VERIFY` 下会按 `draft_token_num` 逐步循环，K=1 也就是全 batch 硬跑 2 步，并保存中间 state，见 [hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1659)。
- verify 结束后还要做 mamba/GLA rollback，见 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L487) 和 [hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1373)。
- KV 也是先按 `draft_token_num` 全分配，再把没用上的 free 掉，见 [eagle_info.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py#L872) 和 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L497)。
- FlashInfer 的 verify replay 还有明显的 CPU metadata 编排和 re-plan 成本，见 [minicpm_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L2033)。
- 乘法维度也会从 `bs` 变成 `2*bs`，更容易把量化线性层从 Marlin 优势区推到 CUTLASS，见 [modelopt_quant.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/quantization/modelopt_quant.py#L1342)。

所以当前实现不是“命中才赚 bonus”，而是“全员先交二步税，命中的人再领 bonus”。

**2-pass 为什么对**
如果改成两遍：

- Pass 1: 全 batch 只吃 `verified_id`
- 比较 `draft_0` 和 target 的 `pred_0`
- Pass 2: 只有命中的请求再吃 `draft_0`

那成本结构就从：

- 现在：所有请求固定跑 2 步

变成：

- 以后：所有请求跑 1 步 + 命中子集再跑 1 步

如果 accept rate 是 `a`，那 GLA 这块的核心成本就从接近 `2x` 变成接近 `1 + a`。  
`a=0.4` 时，大致就是 `1.4x`，这比现在健康很多。

而且它还有两个附带好处：

- 第二遍只跑 accepted subset，GEMM 的 `M` 变小，不会像现在一样直接把全 batch 扩成 `2*bs`
- 不需要“先多分配，再 rollback/free”，状态语义更干净

**这里最关键的实现判断**
我现在最确定的一点是：

不要把 `2-pass` 实现成“两次 `TARGET_VERIFY`”。  
那样虽然逻辑上也叫两遍，但你还在走 verify 慢路径，很多税还在。

更好的落地应该是：

- Pass 1 用真正的 `DECODE`
- Pass 2 对 accepted subset 也用真正的 `DECODE`

这样 K=1 就不再需要：
- intermediate GLA state rollback
- over-allocate 后 free unused KV
- verify metadata replay 这一整条慢路径

本质上，K=1 的 `2-pass` 已经不太像传统 verify 了，更像“先确认 base token，再对命中的请求补跑 bonus token”。

**难点在哪**
难点不在数学，而在状态拼接：

1. rejected 请求  
Pass 1 后就结束。  
它本轮只新增一个 token，也就是 `target_pred_0`。

2. accepted 请求  
Pass 2 再跑一次。  
它本轮新增两个 token：
先是 `draft_0`，再是 `target_pred_after_draft_0`。

3. worker 和 scheduler 的接口要保持一致  
当前 Medusa 的约定是：
- bonus token 由 worker 直接 append
- 最后那个 token 由 scheduler 统一 append

这个约定已经写死在 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L537) 和 [scheduler_output_processor_mixin.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/scheduler_output_processor_mixin.py#L402)。

所以 `2-pass` 最自然的做法是：
- accepted 请求的 `draft_0` 继续在 worker 内 append
- 返回给 scheduler 的 `next_token_ids`
  - rejected 是 `pred_0`
  - accepted 是 `pred_after_draft_0`

这样外部契约基本不变。

4. hidden state 要按请求合并回主 batch  
- rejected 用 Pass 1 的 hidden
- accepted 用 Pass 2 的 hidden

5. accepted subset 不能直接把主 batch 原地 `filter_batch` 掉  
因为 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L2116) 的 `filter_batch` 是原地改 batch 的。  
所以需要一个临时 sub-batch/view，而不是把主 batch 本体切坏。

**还有一个现实问题**
就算做了 `2-pass`，也别直接复用现在 `medusa_worker._forward_decode_normal()` 当最终形态。

因为它虽然用了 `DECODE` 语义，但分配路径还是手搓的：
- 手工 `alloc_token_slots`
- 手工补 sparse slot

见 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L321) 和 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L627)。

而标准 decode 是有更完整分配路径的，见 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1996)。

所以我的判断是：

`2-pass selective verify` 是主方向。  
但它最好和“Medusa 走真正 decode fast path”一起做，不然会留下一截系统税。

**我的最终判断**
这条线是可行的，而且比“高并发直接关 spec”高级得多。  
它不是在回避 spec，而是在重写 spec 的成本结构。

如果让我排优先级，我会这样排：

1. 先做 K=1 的 `decode(all) + decode(accepted-subset)` 语义设计  
2. 同时把 Medusa 的 token commit/alloc 尽量对齐标准 decode fast path  
3. 之后再叠加 confidence gating，只让高把握请求进第二遍  
4. 最后才看训练侧继续抬 accept rate

**状态语义**
先把 Medusa 这一轮开始前的真实状态讲清楚，不然后面都会绕。

在一轮 Medusa decode 开始时，每个请求其实有 3 个东西：

- `P`：已经真正写进 KV / GLA state 的前缀
- `v`：上轮 target 给出的“下一个 token”，已经返回给调度器并展示了，但这一轮开始前它还没被真正消费进状态
- `h(P)`：前缀 `P` 的最后 hidden state，用来给 Medusa head 出草稿

这就是为什么当前实现会把 `[verified_id, draft_0]` 一起送进 verify，见 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L416)。  
它本质上是在说：

- 先把 `v` 真正吃进模型
- 再顺便试着把 `draft_0` 也吃进去
- 然后看 `draft_0` 究竟对不对

所以这里最重要的认知是：

`verified_id` 不是“本轮刚生成的新 token”。  
它是“上轮已经发出，但本轮才真正 commit 到模型状态里的 token”。

**2-Pass 的精确定义**
K=1 时，我建议的语义不是“两次 verify”，而是下面这个：

1. Pass 1：全 batch 跑 `v`
输入是 `v = verified_id`。  
输出是：
- `pred0`：target 在看到 `v` 后预测的下一个 token
- `h(P+v)`：消费完 `v` 之后的 hidden state
- 同时把 `v` 真正写进 KV / GLA state

这一步应该尽量走真正的 decode 快路径，而不是当前 `TARGET_VERIFY` 慢路径。现成的参考行为就在 [_forward_decode_normal](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L300)。

2. 草稿判定
用本轮开始前的 `h(P)` 让 Medusa head 产出 `draft_0`。  
然后比较：

`draft_0 == pred0`

- 不相等：这个请求本轮没有 bonus
- 相等：这个请求进入 Pass 2

3. Pass 2：只对 accepted 子集跑 `draft_0`
这一步只对命中的请求执行。  
输入是 accepted subset 的 `draft_0`。  
输出是：
- `pred1`：target 在看到 `draft_0` 之后预测的下一个 token
- `h(P+v+draft_0)`：消费完 bonus token 之后的 hidden state
- 同时把 `draft_0` 真正写进这些请求的 KV / GLA state

4. 回填最终结果
- rejected 请求：
  - 本轮 commit 的前缀变成 `P+v`
  - 返回给调度器的最终 token 是 `pred0`
  - 下一轮草稿 hidden 用 `h(P+v)`
  - `accept_length = 0`
- accepted 请求：
  - 本轮 commit 的前缀变成 `P+v+draft_0`
  - worker 先把 `draft_0` 作为 bonus append 到 `req.output_ids`
  - 返回给调度器的最终 token 是 `pred1`
  - 下一轮草稿 hidden 用 `h(P+v+draft_0)`
  - `accept_length = 1`

这样就完全对齐了现在调度层对 Medusa 的消费方式：  
worker 先补 bonus，scheduler 再统一 append 最后一个 token，见 [scheduler_output_processor_mixin.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/scheduler_output_processor_mixin.py#L402)。

**为什么这套语义是自洽的**
因为它保留了现有 Medusa 的外部契约，只改内部成本结构。

对调度器来说，返回值还是这几个：

- `next_token_ids`
- `accept_length_per_req_cpu`
- `num_accepted_tokens`
- `logits_output.hidden_states`

只是它们的来源变了：

- rejected 的 `next_token_ids = pred0`
- accepted 的 `next_token_ids = pred1`
- rejected 的 hidden 来自 Pass 1
- accepted 的 hidden 来自 Pass 2
- `accept_length_per_req_cpu` 还是只有 `0/1`

所以 scheduler 基本不用改协议。

**这一版比当前实现少了什么税**
当前 one-pass 会：

- 全 batch 给 `[v, draft_0]` 一次性分两步 KV
- 全 batch 跑两步 GLA，并存中间 state
- verify 结束后做 rollback
- 再把没用上的 KV free 掉

对应代码在 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L434)、[medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L487)、[medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L497)、[hybrid_linear_attn_backend.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1659)。

而 `2-pass decode` 之后：

- Pass 1 只给全 batch 分 1 个 token
- Pass 2 只给 accepted 子集再分 1 个 token
- 不需要 verify rollback
- 不需要“先分两步、再释放没中的那一步”

这就是它最核心的性能来源。

**真正的难点**
1. 主 batch 和 accepted 子 batch 的关系

Pass 1 结束后，主 batch 已经整体进入 `P+v`。  
Pass 2 不能把主 batch 原地 `filter_batch()` 掉，因为那个 API 会直接改 batch 本体，见 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L2116)。

所以需要一个“临时 accepted sub-batch”：
- `reqs`
- `req_pool_indices`
- `seq_lens`
- `seq_lens_cpu`
- `sampling_info`
- 以及 decode 所需的 sparse / mamba 元数据

这个 sub-batch 只用于第二遍前向，跑完后把结果 merge 回主 batch。

2. hidden state 的合并

最终返回给下一轮 Medusa 的 hidden 必须是按原顺序拼回来的：

- rejected 位置放 Pass 1 的 hidden
- accepted 位置放 Pass 2 的 hidden

3. `seq_lens / kv_committed_len / kv_allocated_len` 的对齐

Pass 1 后全 batch 都是 `+1`。  
Pass 2 后 accepted subset 再 `+1`。

最后必须保证：
- 主 batch 的 `seq_lens`
- 每个 req 的 `kv_committed_len`
- 每个 req 的 `kv_allocated_len`
- 已 append 的 `req.output_ids`

这四个量完全一致。否则结束判定和 KV 释放会出错。

4. sparse k1/k2 分配

当前 Medusa 自己补 sparse slot 的逻辑还是 Python 循环，见 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L627)。  
如果 `2-pass` 还继续复用这条慢路径，性能会被吃掉一截。

所以更合理的是：
- Pass 1 尽量贴近标准 decode 的分配路径
- Pass 2 的 accepted subset 也走同样的 decode 分配语义

标准 decode 的分配入口在 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1996)。

- 只让 accepted subset 再 commit 1 token
- 取 `hidden_after_v_draft`

最后合并回主 batch：
- rejected:
  - `next_token_ids = pred0`
  - `accept_length = 0`
  - hidden 用 pass1
- accepted:
  - `req.output_ids.append(draft_0)`
  - `next_token_ids = pred1`
  - `accept_length = 1`
  - hidden 用 pass2
  - `seq_lens / kv_*` 再加 1

这一步只改 [medusa_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py)。

如果 two-pass 最小版先用手工 `alloc_token_slots + _alloc_sparse_for_new_positions` 跑通也可以，但第二步就该处理这件事。

重点对齐 [schedule_batch.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1996) 的 decode 分配语义：
- 1 token commit
- sparse k1/k2 同步分配
- req 级 `kv_*` 更新一致

否则系统税会吃掉一部分收益。

token = `pred1`\n+- `accept_length = 1`\n+- 下一轮 `verified_id = pred1`\n+- 下一轮 hidden = `hidden_after_v_draft`\n+\n+这样可保持与 scheduler 当前 Medusa 协议一致：\n+\n+- bonus token 由 worker 先 append\n+- scheduler 只 append 最后一个 token\n+\n+对应 scheduler 消费逻辑见 [`scheduler_output_processor_mixin.py#L399-L407`](../demo-sala/sglang/python/sglang/srt/managers/scheduler_output_processor_mixin.py)。\n+\n+## 5.
