## MiniCPM 前向栈（形状与数据流）

**整模型**（`MiniCPMSALAForCausalLM`）：`embed * scale_emb` → 各层 → `RMSNorm` → `/ scale_width` → `LogitsProcessor`。

**单层**（`MiniCPMDecoderLayer`）：Pre-MLP 与 Pre-Attn 均为 **残差 + 深度缩放**（`scale_depth / sqrt(num_hidden_layers)`）。

- **输入**：`hidden_states` 形状 `[total_tokens, hidden_size]`（与 SGLang `ForwardBatch` 一致）。
- **Attention 支路**：`residual = hs` → `input_layernorm` → `self_attn(positions, hs, forward_batch)` → `residual + attn_out * depth_scale`。
- **MLP 支路**：`residual = hs` → `post_attention_layernorm` → `mlp` → `residual + mlp_out * depth_scale`。

**`MiniCPMMLP`**：`x [T,H]` → `MergedColumnParallelLinear` → `gate_up [T, 2*intermediate_tp]` → `SiluAndMul` → `[T, intermediate_tp]` → `RowParallelLinear` → `[T,H]`。

**`MiniCPMAttention`**：`QKVParallelLinear` → `qkv.split` →（可选 RoPE）→ `RadixAttention` →（可选 `o_gate` + `sigmoid` 逐元乘）→ `o_proj`。

**`MiniCPMLightningMixer`**：`QKV` → `split` →（可选 `qk_norm`，带 `reshape`）→ RoPE（再 `reshape`）→ `q,k,v` 变为 `[T,nh,hd]` → **`unsqueeze(0)` → `[1,T,nh,hd]`** → `SimpleGLAAttnBackend.forward` → `reshape` →（可选 `o_norm`、`z_proj`×`sigmoid`）→ `o_proj`。

---

## SGLang 里与「gate_up + SiLU」相关的融合

- **标准 SwiGLU 融合**：`SiluAndMul` 即 `silu(x[..., :d]) * x[..., d:]`，CUDA 走 `sgl_kernel.silu_and_mul`（见 `activation.py`）。
- **与量化结合**：仓库里「SiLU + Mul + 量化」的融合主要在 **MoE / FP8 激活量化** 路径（如 `fp8_kernel.py` 的 `fuse_silu_and_mul`、`ep_moe/kernels.py` 的 `_silu_and_mul_post_quant_kernel`），**没有**与 `ModelOptFp4LinearMethod` 绑定的、针对 dense `gate_up → silu → down` 的现成融合模块。
- **Dense NVFP4**：`ModelOptFp4LinearMethod.apply` 仍是 **pre_scale → fp4_quantize → fp4_gemm → BF16 输出**；`MiniCPMMLP` 在 GEMM 外再调 `SiluAndMul`，与 `commandr.py` / `llama` 系一致。

### 1. Lightning 路径上密集的 `reshape` / `unsqueeze`（算子与内存开销）

`MiniCPMLightningMixer.forward` 在 norm、RoPE、后端接口之间多次拉平再还原，最后为 GLA 后端固定加 batch 维：

```319:335:/root/shared-nvme/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py

            k = self.k_norm(k.reshape(-1, self.head_dim))

        q = q.reshape(-1, self.num_heads, self.head_dim)

```

**改进**：在 `SimpleGLAAttnBackend`（`/root/shared-nvme/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py`）能接受的前提下，改为 **更少视图的连续布局**（例如 RoPE 直接接受 `[T, H, D]`，或后端内部 `unsqueeze`），可减少同步与别名断裂；`unsqueeze(0)` 若仅为 API 兼容，最适合收进 backend 一层。

### 2. NVFP4 MLP：`gate_up` GEMM → `SiluAndMul` → `down` GEMM 的两次输入量化（融合机会）

`MiniCPMMLP` 当前结构：

```83:87:/root/shared-nvme/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py

        gate_up, _ = self.gate_up_proj(x)
        x = self.act_fn(gate_up)
        x, _ = self.down_proj(x)

```

`ModelOptFp4LinearMethod.apply` 对每个 linear 都会对 **当前激活** 做 `fp4_quantize` 再 `fp4_gemm`（见 `modelopt_quant.py` 1246–1274 行附近）。因此一层 MLP 是 **两次** FP4 输入量化 + 两次 GEMM，中间夹着一次 `SiluAndMul`（BF16）。

**改进**：与 `fp8_kernel.py` 里 `fuse_silu_and_mul` 的思路对齐，若 FlashInfer/CUTLASS 或自研 Triton 能提供 **「BF16 中间 → SiLU×Mul → 直接产出 down GEMM 所需的 FP4/scale」**，可把 **激活量化 + SiLU+Mul** 并掉，减少一轮全局内存读写；这需要 **量化侧新 kernel/接口**，不是改 `minicpm.py` 一行能完成，但和仓库里已有 MoE/FP8 融合方向一致。

### 5. Lightning + `use_output_gate`：`qkv_proj` 与 `z_proj` 同输入、两次 Column GEMM


**改进**：若愿改 checkpoint 与 `load_weights` 映射，可引入 **单矩阵多输出**（类似扩展版 `QKVParallelLinear`），一次 GEMM 得到 Q、K、V、Z，再 split；数学不变，减少一次对 `hidden_states` 的完整矩阵乘。代价是工程量大，但与仓库里「fused linear」方向一致（非 MoE）。

## 小结

- **MLP**：结构上已是 **Merged `gate_up` + `SiluAndMul`**，与 SGLang 主流一致；NVFP4 下主要机会在 **量化/激活链路的算子融合**（参考 FP8/MoE 里已有 `silu` 融合模式），而非再拆 `gate`/`up`。
- **Attention**：标准 Attention 路径较直；**Lightning** 路径的 **reshape/unsqueeze** 与 **QKV+Z 双线性** 是更明显的结构与算子重复点。
