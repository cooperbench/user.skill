> AGENT

我认为这不是普通训练波动，是验证体系和线上路径没有同构。现在的 val 不能代表推理，原因至少有四个：

1. **当前 artifact/config 已经不一致**
   - `eagle/sglang_model_v3/config.json` 是 aux `[4,9,24]`。
   - 但正式 `demo-sala/data/eagle_draft/config.json` 仍是 aux `[1,10,22]`，`model.safetensors` md5 也和旧 `eagle/sglang_model/` 一致。
   - `eval/start_eagle.sh` 默认用 `eagle/sglang_model_v3`，`demo-sala/prepare_env.sh` 默认用 `demo-sala/data/eagle_draft`。
   - `eval/start_eagle.sh` 默认 `steps=3 topk=1`，`demo-sala/prepare_env.sh` 当前默认 `steps=2 topk=2`，文档又写过 `steps=2 topk=1`。

   这会直接导致“训练 val 看起来好，但正式推理没反应”。

2. **训练 val 测的是 teacher-forced top-1，不是线上 accept_len**
   `eagle/train.py` 的 `eval_ood()` 现在按真实 token 序列喂入，统计 step0/step1/... 独立命中率；但线上 EAGLE 是 draft 自回归生成，再由 target verify/rollback。真正影响速度的是：
   - `P(step0 accepted)`
   - `P(step0 and step1 accepted)`
   - 实际 `accept_len`
   - tree/chain verify 后的状态更新是否正确

   单独 step0 acc 或 teacher-forced step1 acc 都不能代表这个闭环。

3. **FP4_QAT 的 eval 和推理不一致**
   `FP4QATLinear.forward()` 只有 `self.training and FP4_QAT` 时 fake-quant；`model.eval()` 时 val 用的是 raw BF16 master weight。  
   但 `convert_to_sglang.py` 会把权重 pack 成 NVFP4，线上走 Marlin/CUTLASS。也就是说：训练 val 看的不是部署权重。

4. **`eagle/eval_ood_accept.py` 不能作为生产判断**
   这个脚本仍默认读 `eagle/sglang_model/`，而且 attention 是 simplified single-step，没有完整 KV cache/RoPE/线上 draft path。它只能当历史脚本，不能当现在 v3 的验收依据。

我建议按这个顺序解决：

1. **先冻结唯一生产配置**
   明确到底用哪套：`draft_model_path`、aux layers、`spec_steps`、`topk`、`dtn`。正式提交以 `demo-sala/prepare_env.sh` 为准。然后加一个 preflight 检查，直接 fail 掉以下情况：aux layers 不一致、draft md5 不一致、`steps/topk/dtn` 不一致、`hf_quant_config` 不符合预期。

2. **把 val 改成部署等价**
   `eval_ood()` 不能用 raw eval 权重。要么让 `FP4QATLinear` 在 eval 也走与 `convert_to_sglang.py` 一致的 NVFP4 fake-dequant，要么每次候选 ckpt 先 convert，再用 converted model 做验证。关键是 val 必须看“部署后的权重”。

3. **把指标从 acc0 改成 expected accept length**
   对 topk=1 chain，离线可以先算 prefix accept：
   - `accept>=1`: step0 match
   - `accept>=2`: step0 and step1 match
   - `accept>=3`: step0 and step1 and step2 match  
   checkpoint selection 应该看 `E[accepted_draft_tokens]`，不是只看 `ood0`。

   对 topk=2 tree，离线近似不够，必须跑实际 tree verify 或线上 server trace。

4. **加 tensor-level 等价测试**
   做一个小脚本/测试：同一个 `.pt` 样本，同一组 input/aux/position，比较：
   - train model BF16 vs SGLang draft BF16
   - train exact NVFP4 fake-dequant vs SGLang NVFP4
   - first draft token top1/topk 是否一致

   这个测试不过，就不要继续训。否则训练只是在优化另一个模型。

5. **最终验收必须跑线上路径**
   每个候选 ckpt 至少做一次：
   - convert 到临时 draft dir
   - 用正式 `demo-sala` 参数起 server
   - 跑小样本 public eval + `bench/mini_bench.sh`
   - 记录 `ori_accuracy`、tok/s、accept_len、bad case index

核心判断：现在的问题不应该先靠“再训一版”解决，而是先修验证闭环。只要 val 还不是 deployment-equivalent，任何 acc 提升都可能是虚假的。
