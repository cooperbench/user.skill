给我讲讲你的 bench 方法和流程

> AGENT

这个 bench 的目标很窄：先建立 verify 加速的快速回归尺子，不测完整吞吐，也不启动 SGLang。 它测的是 target verify 里 8 个 standard attention layer 用到的 FlashInfer dense paged-prefill kernel： ```python BatchPrefillWithPagedKVCacheWrapper.forward(causal=True) ``` 参数按 MiniCPM verify 路径对齐： - `page_size=1` - `head_dim=128` - `num_qo_heads=32` - `num_kv_heads=2` - `dtype=bf16` - paged KV 形态是 FlashInfer 的 NHD cache - `dtn` 对应一次 verify 的 draft token 数 流程是： 1. 选固定网格 默认 `quick` 跑 9 个点： ```text seq_len = 4096, 32768, 131072 dtn = 7, 9, 11 ``` 这三个 `seq_len` 分别代表 sparse 等价窗口、中长上下文、真实长上下文；三个 `dtn` 对应提交默认 / D5 / D7。 2. 每个点构造随机 q/k/v 用固定 seed 生成 bf16 tensor，只关心 kernel 时间，不关心输出语义。 3. 调一次 `wrapper.plan(...)` 这模拟 verify path 的 dense paged KV plan 形态。当前 bench 主要量 `forward` kernel，不把 plan/replay metadata 也算进去。 4. warmup 后用 `cuda.Event` 量 `forward` 默认 `warmup=20, measure=100`。每次测一个 FlashInfer forward kernel，记录 p10/p50/p90/mean。 5. 估算 8 层 standard attention 总成本 MiniCPM-SALA target 有 8 个 standard attention layer，所以输出里有： ```text estimated_8_std_layers_p50_ms = p50_ms * 8 ``` 6. 写 JSON 输出到 `verify/outputs/verify_kernel__<preset>__<tag>__<ts>.json`，包含设备、torch/flashinfer/cuda 版本、参数、环境变量、每个点结果和 summary。 常用命令： ```bash # 只验证脚本能跑 /opt/SGLang-MiniCPM-SALA/sglang_minicpm_sala_env/bin/python3 \ verify/bench_verify_kernel.py --preset smoke # 日常优化前后对比 /opt/SGLang-MiniCPM-SALA/sglang_minicpm_sala_env/bin/python3 \ verify/bench_verify_kernel.py --preset quick --tag baseline ``` 它的优点是快、稳定、复现简单，适合验证“verify attention kernel 本身有没有变快”。限制也很明确：它不测完整 verify cycle，不包含 Marlin、GLA、lm_head、draft、accept bookkeeping，也不包含 SGLang cuda graph replay 的 CPU/metadata 开销。完整线上归因仍然要用 cupti trace。

我有一个很有趣的想法 如果我们在 verify 取得了一些成功 sparse 这里 是不是也可以指导 prefill 侧的工作？

> AGENT

可以，而且很有价值，但不是“verify 赢了就照搬 prefill”。 核心判断： **verify sparse 的经验能指导 prefill 的是方法论和 metadata/kernels，不是完整路径。** 目前 sparse verify 暴露出来的规律： 1. **attention 本体会赢** 长 context 下 sparse attention 明显比 dense attention 快，这说明“少看 KV”这个方向是对的。 2. **真正拖后腿的是准备工作** `compress_k / topk / kv_indices metadata / cumsum / sort` 这些如果每层、每步重复做，收益会被吃掉。 3. **prefill 更适合摊薄 metadata 成本** verify 的 q 很小，metadata 开销很难摊；prefill 的 q 大得多，topk/metadata 如果按 chunk 复用，单位 token 成本可能更低。所以 sparse 在 prefill 侧反而可能更容易变成净收益。 但 caveat 很重要： - prefill 的瓶颈和 verify 不一样。 - prefill 里 page64 曾经离线好看，线上端到端打平，说明 wrapper/plan/cache 细节会吞收益。 - `fuse-topk` / `split-stage1` 这类 k1-only 路径不能随便用，历史已经证明语义不对。 我认为 verify 现在能反向指导 prefill 的几个明确方向： - **不要重复搬历史 compressed K**：verify 卡在这里，prefill 长 chunk 更应该避免。 - **topk 后处理要最小化**：排序、cumsum、indices 展开都要砍。 - **page64/block metadata 值得重新审**：verify 证明 `kv_indices` 展开是大账，prefill 侧同样成立。 - **所有 sparse 改造必须 profile 拆账**：只看 attention 快没意义，要看 attention + topk + compress + metadata 净收益。 - **先保语义，再优化**：topk 候选集合、causal 截断、k1+k2 scoring 不能变。 说人话：**verify 是一个放大镜。它把 sparse 的准备成本暴露得特别明显；这些成本如果在 prefill 也存在，就一定要提前设计掉。** Verify 侧砍出来的正向 kernel 和复用策略，可以作为 prefill 下一轮优化的优先级依据。
