## 背景

我在优化 OpenBMB MiniCPM-SALA（2026.02.11 发布）的推理速度。这个模型 32 层里 8 层用 InfLLM-v2 稀疏注意力，24 层用 Lightning Attention（GLA）。标准 attention 层在 seqlen≥8192 时走 InfLLM-v2 稀疏：把 K 压缩→stage1 block-level score→取**固定 top-K=64 blocks**→stage2 sparse flash attention。

我在考虑把推理时的"固定 top-K"换成"α-threshold（score ≥ α·max_score 的块全选）+ min_budget 保底"——FlashPrefill 论文里的思路。潜在好处：查询注意力分散时少算、集中时多算，自适应。

We propose InfLLM-V2, a more concise framework with zero extra parameters that more closely

Shared Key-Value Projection.
We find that using three separate sets of KV projection parameters
in NSA (Yuan et al., 2025) is unnecessary, which not only complicates the adaptation from short
to long sequences but also significantly slows down computation for short sequences. Therefore,
we propose using a single shared set of projection parameters, WK and WV , initialized with the
pretrained dense attention parameters and used for finetuning on long sequences.

3.4
EFFICIENT IMPLEMENTATION
For efficient Sparse Attention, we follow the techniques in NSA (Yuan et al., 2025) to set the group
size G of GQA to 16, a configuration well-suited for block sparse attention. More details can be
found in Appendix A. However, our profiling reveals that the computation of the compression
score, Scmp, introduces a significant performance bottleneck. A primary source of this slowdown
is the substantial I/O required to store the first-stage attention scores SC1 into the slow GPU HBM.
The amount of data that needs to be written is hqn2/sC1, where n is the full sequence length. Given
that sC1 ≪n, materializing the full attention score matrix to GPU HBM incurs a prohibitive cost.
Drawing inspiration from FlashAttention (Dao, 2024), we aim to minimize this I/O by ensuring the
attention scores remain within the fast GPU SRAM as much as possible. Our approach, Fused
Head Group Summation, is to fuse the summation over the head group, required for the second-
stage compression, directly into the SRAM-based computation loop of FlashAttention. After that,
we can only store the reduced attention scores Sshared into GPU HBM, whose size is hqn2/(sC1G).
Another challenge arises from the fact that summing over the head group dimension and performing
the online-softmax (Dao, 2024) along the sequence dimension are not commutative operations. This
conflict prevents a straightforward fusion. To overcome this, we implement a two-pass approach. In
the first pass, we compute the log-sum-exp (lse) term required for the softmax normalization within
the SRAM. In the second pass, we leverage the lse to calculate the final attention scores, perform
the summation across the head group within the SRAM, and write the reduced scores to the HBM.
The trade-off of this two-pass method is that it doubles the computational workload. Therefore,
we propose LSE Approximation to approximate the lse computation by using a coarser-grained
attention score SC2. Following Eq. (4) and Eq. (5), we change them to

Efficient Inference and Deployment
Due to strict constraints on compute, storage capacity, and power consumption of end-side devices such as
mobile devices and personal computers, how to achieve efficient inference of LLMs under limited hardware
resources has become a key technical challenge. In this section, we will introduce our inference system,
CPM.cu, and deployment system, ArkInfer.
4.1
CPM.cu: Lightweight and Efficient CUDA Inference Framework
We first develop a lightweight inference framework optimized for end-side NVIDIA chips. Beyond the basic
features, such as static memory management and kernel fusion, we implement a highly efficient speculative
sampling and integrate efficient sparse attention kernels for InfLLM v2. Speculative sampling is a critical
technique for accelerating LLM inference (Leviathan et al., 2023; Chen et al., 2023; Cai et al., 2024; Li et al.,
2024c), particularly in resource-constrained end-side devices. This approach employs a draft-then-verify
paradigm where a lightweight draft model generates candidate token sequences, which are subsequently
verified by the target LLM in parallel. The recent advances in speculative sampling, such as EAGLE-2 (Li
et al., 2024c), utilize a tree-style drafting process. By designing efficient attention kernels tailored for tree-
based speculative sampling and implementing fused verification kernels, we achieve an optimized speculative
sampling speed. We also implement an efficient InfLLM v2 sparse attention kernel within the framework.
Based on the framework, we identify that the efficiency bottleneck in speculative sampling for end-side models
lies in the language modeling head of the draft model. To address this, we propose FR-Spec (Zhao et al., 2025),
which prunes the draft model’s vocabulary based on the token frequency while preserving the full vocabulary
of the target model to maintain its generation quality. We further explore combining speculative sampling
with 4-bit quantized GPTQ (Frantar et al., 2023) models. To maintain model performance, we first explore an
improved quantization scheme, P-GPTQ, and subsequently validate the feasibility of integrating speculative
sampling with quantization in SpecMQuant (Zhang et al., 2025b) and with long-context processing.

4.1.1
Frequency-Ranked Vocabulary Construction and Draft Verification
The effectiveness of speculative sampling relies heavily on the efficiency of both the drafting and verification
phases. Recent advances such as EAGLE-2 (Li et al., 2024c) have made remarkable progress in reducing
drafting overhead through extremely lightweight architectures, by employing single-layer Transformers for the
drafting process. Contemporary models tend to adopt larger vocabularies to improve tokenization efficiency,
introducing significant computational overhead in the language modeling head, making the drafting process
slow, although it has only a single layer. Our investigation reveals that the transition from small to large
vocabulary models substantially increases drafting time, creating a new performance bottleneck that limits the
effectiveness of speculative sampling techniques.
To address this challenge, we introduce FR-Spec (Zhao et al., 2025), a frequency-ranked speculative sampling
framework that optimizes draft candidate selection through strategic vocabulary space compression. Our
approach leverages the well-documented long-tail distribution of token frequencies in natural language, where
a small subset of high-frequency tokens accounts for the majority of occurrences. By restricting the draft search
to a frequency-prioritized subset of tokens, FR-Spec reduces the computational overhead of the language
modeling head by up to 75% while maintaining the mathematical equivalence of the verification process and
preserving the correctness of the final output distribution.

P-GPTQ: Prefix-Aware Post-Training Quantization for End-side Devices
As we mentioned above, PTQ and QAT are both important approaches for model quantization. Compared
with QAT, PTQ is lighter and easier to conduct. PTQ for on-device deployment necessitates simultaneous
quantization of both weights and activations due to constrained computational resources.
Recent studies demonstrate that most LLMs exhibit massive activations (Sun et al., 2024b) at initial token
positions, substantially degrading activation quantization fidelity. To address this challenge, we follow the
PrefixQuant method (Chen et al., 2024) to isolate these initial token activation outliers. Specifically, our
solution stores initial key-value activations during preprocessing, thereby preventing excessive activation
magnitudes throughout the forward propagation of the first few input tokens.

token bias also significantly impacts the weight quantization calibration process. Building on this insight,
we develop Prefix-Aware GPTQ (P-GPTQ), an extension of the GPTQ method (Frantar et al., 2023) that
eliminates initial token interference during Hessian computation. Formally, GPTQ computes the Hessian

4.2
ArkInfer: Cross-Platform Deployment System
Beyond the challenges of limited computational resources, the fragmentation of end-side chips presents another
significant hurdle. This fragmentation necessitates adapting models to multiple platforms and chip types for
each new model release, leading to complex adaptation and deployment. This results in a great amount of
engineering effort, making it nearly impossible for models to run efficiently across all platforms.
The core of this problem lies in decoupling and efficient code reuse: How can a single technical development
and engineering effort be automatically applied across multiple platforms?
To address these pain points, we propose ArkInfer, a novel cross-platform deployment system. ArkInfer is
designed to overcome the fragmentation of end-side chips by providing highly efficient inference speed and
serving as a versatile cross-platform compatibility layer for various model applications. To achieve this, we
introduce three key solutions: (1) a cross-platform compatible architecture design, (2) reusable and efficient
speculative and constrained decoding schemes, and (3) an extensible model zoo frontend.
4.2.1
Cross-Platform Compatible Architecture Design
ArkInfer’s architectural design is fundamentally driven by the need for unified, efficient deployment across
a fragmented landscape of end-side hardware. Supporting diverse platforms such as MediaTek, Nvidia,
Qualcomm, and Rockchip, each with its native inference frameworks (e.g., NeuroPilot, Genie, RK-LLM,
TensorRT-LLM, and llama.cpp for CPU), ArkInfer seamlessly integrates these as adaptable backends.
At its core, ArkInfer implements a powerful abstraction layer. This layer features a system of adapters that
normalize the varied APIs of different backends, presenting a consistent interface to higher-level components.

Efficient Post-Training
In this section, we present our approach to post-training large models after the pre-training phase, enabling
them to leverage the world knowledge acquired during pre-training to follow user instructions. During the
supervised fine-tuning stage, we construct a diverse and comprehensive set of instructions to fully activate the
capabilities of the LLMs, ensuring a strong foundational competence. To this end, following our previous
work (Ding et al., 2023), we construct UltraChat v2, a large-scale SFT dataset covering abilities including
knowledge application, reasoning, tool use, and long context processing.
Furthermore, to enhance the model’s deep reasoning ability, we employ supervised fine-tuning augmented
with long chain-of-thought reasoning and integrate reinforcement learning techniques. The rollout process of
RL usually suffers from the unbalanced load challenge, which can lead to very inefficient computations. To
address this issue, we propose a load-balanced RL strategy – chunk-wise rollout.
In the following paragraphs, we will provide details on supervised fine-tuning and reinforcement learning
techniques used to enhance foundational capabilities and reasoning abilities.
3.1
UltraChat v2: Foundational Capability Enhanced SFT Data Generation
To improve LLMs’ core competencies, we design a synthetic data generation framework focused on task-
oriented capabilities. Guided by key capability dimensions, the framework generates high-quality QA-style
data covering a wide range of skills, providing more targeted and structured signals during post-training. We
systematically develop synthetic data tracks across five key skill areas: knowledge applications, reasoning,
instruction following, long-context processing, and tool use. Each track is tailored to the input-output patterns
and cognitive demands of its target skill, providing diverse, task-driven, and transferable training examples.
This approach helps the model improve consistently across key foundational capabilities.
3.1.1
Knowledge-Intensive Data
We begin by extracting and organizing knowledge points from domain-specific corpora, exam syllabi, and
textbook materials across various disciplines, thereby constructing a comprehensive and well-structured
knowledge framework. Based on this framework, we leverage LLMs to generate practice question-answer
pairs targeting individual knowledge points, thus forming the initial stage of a knowledge-driven QA dataset.
To further enhance the diversity and generalization capability of the data, we apply two evolution strategies to
the initial practice QA pairs: (1) Instruction evolution, which rewrites prompts in diverse ways to simulate
various questioning styles and task formulations; and (2) Answer diversity evolution, which guides the model
to generate plausible and stylistically varied answers, thereby improving the model’s robustness in knowledge
understanding and expression.

训练时确实曝光了固定 top-K 稀疏 pattern。InfLLM-v2论文（arxiv 2509.24663）明确指出 `|I|=96`（init=1, topk=63, local=32）**训练和推理使用同一固定参数**；MiniCPM-4技术报告（arxiv 2506.07900）未披露 SALA 的具体 top-K 数值，但明确描述 MiniCPM4 每 token 只看"6K tokens"上下文且该行为贯穿训练推理。因此推理时切换为 α-threshold **存在明确的训练-推理不一致风险**，模型从未经历过"选 block 数可变"的 attention pattern，随意切换有精度风险。

**证据**

1. **训练时走稀疏路径（非 dense）**：InfLLM-v2 论文 §4.1（p.7）"Long-Context Adaptation: When transitioning to long-context finetuning, we switch to INFLLM-V2 (SPARSE)."。先短序列 full-attention 预训练，再长上下文微调时切换成稀疏。MiniCPM-4 §2（p.6）同样描述先 4K 短序列预训练，再做"long-context pre-training"（从4K扩到128K），并在该阶段使用 InfLLM v2 稀疏。

2. **训练时 top-K 固定、与推理一致**：InfLLM-v2 论文 §4.1（p.7）原文："We set the selected block count |I|=96 (including |Iinit|=1, |Itopk|=63, and |Ilocal|=32) **for both training and inference**." 唯一区别是 dense_len 阈值以下（短序列）退化为 full attention，无需 top-K。

3. **dense_len 阈值（短序列降级机制）**：InfLLM-v2 §3.2（p.4-5）"InfLLM-V2 can thus dynamically switch between dense and sparse attention patterns based on the input sequence length." 即 seqlen < 所选 K 个 block 覆盖 token 总数时退化为 dense。MiniCPM-SALA 的 `dense_len=8192` 是具体部署参数，**两篇论文均未出现"8192"这个数字本身**，推测来自模型配置文件或内部设定，论文没提。

## 1) Block Score & Mean-K Vector

The method computes block importance scores to identify which attention blocks contribute most to predictions. The **mean-K vector** represents average attention patterns within each block, enabling efficient pattern discovery without computing full attention matrices during prefilling.

344	    '''
345	    filter blocks
346	    '''

371	    # hi = tl.minimum(curr_tiles_len, query_tile_index * Q_TILE_SIZE + Q_TILE_SIZE)

448	@triton.jit
449	def _flash_block_sparse_varlen(
450	    Q_ptr, K_ptr, V_ptr, O_ptr, index_ptr, valid_ptr, scale,
451	    stride_qm, stride_qh, stride_qd,
452	    stride_kn, stride_kh, stride_kd,
453	    stride_vn, stride_vh, stride_vd,
454	    stride_om, stride_oh, stride_od,
455	    stride_indexl,
456	    stride_validl,
457	    cu_seqlens_ptr,
458	    cu_tile_seqlens_ptr,
459	    cu_tile_2_seqlens_ptr,
460	    total_seq_len, 
461	    num_q_heads, num_k_heads,
462	    Q_TILE_SIZE: tl.constexpr, K_TILE_SIZE: tl.constexpr,
463	    BLOCK_SIZE: tl.constexpr,
464	    D_HEAD: tl.constexpr
465	):
466	    query_tile_index = tl.program_id(0).to(tl.int64)
467	    offset_zh = tl.program_id(1).to(tl.int64)
468	
469	    offset_batch = offset_zh // num_q_heads
470	    group_size = num_q_heads // num_k_heads
471	    index_group_size = BLOCK_SIZE // Q_TILE_SIZE
472	    '''
473	    BLOCK_SIZE >= Q_TILE_SIZE
474	    BLOCK_SIZE >= K_TILE_SIZE
475	    only support key_len == query_len
476	    '''
477	    offset_q_heads = offset_zh % num_q_heads
478	    offset_k_heads = offset_q_heads // group_size
479	
480	    start_token_idx = tl.load(cu_seqlens_ptr + offset_batch)
481	    end_token_idx = tl.load(cu_seqlens_ptr + offset_batch + 1)
482	    curr_seq_len = end_token_idx - start_token_idx
483	
484	    if query_tile_index * Q_TILE_SIZE >= curr_seq_len:
485	        return
486	    
487	    Q_base_ptr = Q_ptr + start_token_idx * stride_qm + offset_q_heads * stride_qh
488	    K_base_ptr = K_ptr + start_token_idx * stride_kn + offset_k_heads * stride_kh
489	    V_base_ptr = V_ptr + start_token_idx * stride_vn + offset_k_heads * stride_vh
490	    O_base_ptr = O_ptr + start_token_idx * stride_om + offset_q_heads * stride_oh
491	    
492	    start_tile_idx = tl.load(cu_tile_seqlens_ptr + offset_batch)
493	
494	    valid_base_ptr = valid_ptr + (total_seq_len * offset_q_heads + start_tile_idx) * stride_validl
495	
496	    valid_start = tl.load(valid_base_ptr + (query_tile_index // index_group_size) * stride_validl)
497	    valid_end = tl.load(valid_base_ptr + ((query_tile_index // index_group_size) + 1) * stride_validl)
498	
499	    index_base_ptr = index_ptr + valid_start * stride_indexl
500	
501	    offset_q = query_tile_index * Q_TILE_SIZE + tl.arange(0, Q_TILE_SIZE)
502	    offset_dim = tl.arange(0, D_HEAD)
503	
504	    q_mask = (offset_q[:, None] < curr_seq_len) & (offset_dim[None, :] < D_HEAD)
505	    q = tl.load(
506	        Q_base_ptr + offset_q[:, None] * stride_qm + offset_dim[None, :] * stride_qd,
507	        mask=q_mask,
508	        other=0.0
509	    )
510	
511	    sm_scale = scale * 1.4426950408889634
512	
513	    m_i = tl.full((Q_TILE_SIZE,), float("-inf"), dtype=tl.float32)
514	    l_i = tl.full((Q_TILE_SIZE,), 1.0, dtype=tl.float32)
515	    acc = tl.zeros((Q_TILE_SIZE, D_HEAD), dtype=tl.float32)
516	
517	    lo = 0
518	    hi = valid_end - valid_start
519	
520	    block_index = tl.load(index_base_ptr + lo * stride_indexl, mask=(lo < hi), other=0)
521	
522	    for i in range(lo, hi):
523	        next_block_index = tl.load(index_base_ptr + (i+1) * stride_indexl, mask=(i+1 < hi), other=0)
524	        key_start_index = block_index * BLOCK_SIZE
525	        key_end_index = (block_index + 1) * BLOCK_SIZE
526	
527	        is_diagonal_block = (block_index == (query_tile_index // index_group_size))
528	
529	        for j in range(key_start_index, key_end_index, K_TILE_SIZE):
530	            k_index = j + tl.arange(0, K_TILE_SIZE)
531	            k_j = tl.load(
532	                K_base_ptr + k_index[:, None] * stride_kn + offset_dim[None, :] * stride_kd,
533	                mask=(k_index[:, None]<curr_seq_len) & (offset_dim[None, :]<D_HEAD),
534	                other=0.0
535	            )
536	            v_j = tl.load(
537	                V_base_ptr + k_index[:, None] * stride_vn + offset_dim[None, :] * stride_vd,
538	                mask=(k_index[:, None]<curr_seq_len) & (offset_dim[None, :]<D_HEAD),
539	                other=0.0
540	            )
541	
542	            qk = tl.dot(q, tl.trans(k_j))
543	            if is_diagonal_block:
544	                dist = offset_q[:, None] - k_index[None, :]
545	                causal_mask = (dist >= 0)
546	                qk = tl.where(causal_mask, qk, float('-inf'))
547	            qk *= sm_scale
548	            m_i_new = tl.maximum(m_i, tl.max(qk, axis=1))
549	            qk -= m_i_new[:, None]
550	            p = tl.exp2(qk) 
551	            # if is_diagonal_block:
552	            #     p = tl.where(causal_mask, p, 0.0)
553	            lij = tl.sum(p, 1)
554	            alpha = tl.exp2(m_i - m_i_new)
555	            alpha_mask = (alpha != alpha)
556	            alpha = tl.where(alpha_mask, 1.0, alpha)
557	            acc *= alpha[:, None]
558	            l_i = l_i * alpha + lij
559	            p = p.to(v_j.dtype) 
560	            acc += tl.dot(p, v_j)
561	            m_i = m_i_new
562	        block_index = next_block_index
563	
564	    l_rec = 1 / l_i[:, None]
565	    acc = acc * l_rec
566	
567	    o_offset_m = query_tile_index * Q_TILE_SIZE + tl.arange(0, Q_TILE_SIZE)
568	    o_offset_d = tl.arange(0, D_HEAD)
569	
570	    o_mask = (o_offset_m[:, None] < curr_seq_len) & (o_offset_d[None, :] < D_HEAD)
571	    tl.store(
572	        O_base_ptr + o_offset_m[:, None] * stride_om + o_offset_d[None, :] * stride_od,
573	        acc.to(q.dtype),
574	        mask=o_mask
575	    )

## 1) Block Score计算算法

**Mean-K向量的作用**：论文利用"语义相似性"假设，将块内所有token的key向量平均化为单一代理向量 k̄。根据AM-GM不等式，"平均池化的key向量与查询的交互作用为块级重要性的下界估计"。

**Q·mean_K的具体实现**：通过"融合2D归约核"在单次传递中完成：
- 对每个查询块加载池化key块
- 计算 m_{I,J} = max_{q_i∈TileI}(q_i·k_J)（局部最大值）
- 累加 S_{I,J} = ∑_{q_i∈TileI} exp(q_i·k_J - m_{I,J})

## 2) α参数选取理由与消融

论文未明确阐述α=0.1的理论依据。消融策略采用"观察4K序列下的计算密度，通过调节α维持约70%密度"。表9显示不同模型的α值：Llama为0.18，Qwen2.5为0.08，Qwen3为0.12。

## 3) 注意力参数配置

根据附录A的配置：
- **Attention sinks**：256个token
- **本地窗口**：512个token  
- **块大小**：统一128

## 6) 绕过排序的机制

"Max-based Dynamic Thresholding"采用单次max归约替代排序。对查询块I，计算 thresh_I = α·max_J(Score_{I,J})，仅需"单遍max归约而非全局排序"，直接按阈值筛选块。

# FlashPrefill: Key Technical Details

## 1. **Hyperparameter α Configuration (Table 9)**
The threshold factor α varies by model to maintain ~70% computational density at 4K context:
- Llama-3.1-8B: α=0.18
- Qwen2.5-7B: α=0.08  
- Qwen3-30B: α=0.12

## 2. **Pattern Discovery via Mean-Pooled Keys**
The paper argues three sparsity patterns are captured through "uniformly distributed queries" interacting with averaged key blocks:

- **Vertical** (column-wise invariance): "specific anchor tokens attract significant attention regardless of query position"
- **Slash** (translational symmetry): "diagonal motifs emerge from local syntactic dependencies"
- **Block-sparse** (spatial contiguity): "uniform sampling ensures high probability of intersection with dense clusters"

The mechanism uses "average-pooled keys" as "block-level proxies," relying on "semantic locality and local coherence" within blocks.

## 3. **Dynamic Thresholding vs. Sorting**
Core innovation: "thresh_I = α·max_J≤I(Score_I,J)" requires only "a single-pass max-reduction instead of computationally expensive global sorting," bypassing the latency of Top-k/Top-p methods.

## 4. **Benchmark Results**
**RULER (128K context, Qwen3-30B):** 85.20/100 score with 18.67× speedup  
**InfiniteBench:** FlashPrefill maintains near-full performance across tasks  
**End-to-end TTFT:** 5.02× speedup at 128K on Qwen3-30B

## 5. **Key Difference from FlexPrefill**
FlashPrefill eliminates the "high overhead associated with local sorting in Top-kk or cumulative summation in Top-pp strategies," instead using dynamic max-based thresholding that "effectively eliminates the time overhead."

## 1. Pattern 发现机制的算法细节

**mean-K 如何涵盖三种 pattern：**
FlashPrefill 的 `compute_mean_vector` kernel（`flashprefill_native_forward.py` 第22-67行）对每个 K block 内所有 token 做 mean pooling，得到一个代理向量 k̄。`compute_block_score` kernel（第88-188行）然后用整个 Q block（而非单 query）与 k̄ 做点积，结合双层 max reduce（先 token 维度，再跨 block）产生 block-level score。论文 HTML 版给出的理论解释：

- **Vertical pattern**（anchor token 无论 query 位置都被 attend）：k̄ 会因这些 token 在语义上强于邻居而在 mean 中权重大，block score 自然偏高
- **Slash pattern**（对角线局部依赖）：local syntactic dependencies 保证 Q block 内各 token 与对应 K block 的 score 有平移对称性，mean-K 捕获了该"带内"信号
- **Block-sparse**：mean-K 对一个大块内的稠密聚类做了有效摘要

结论：三种 pattern **不是分别检测**，而是通过 mean-K 的统一代理实现隐式涵盖。代码里没有任何 vertical/slash 的显式分类逻辑。

**α=0.1 的来源（论文 Table 9 ablation）：**
论文以"4K 序列下约 70% 计算密度"作为目标校准 α，不同模型取不同值：Llama-3.1-8B α=0.18，Qwen2.5-7B α=0.08，Qwen3-30B α=0.12。代码 `patch_qwen2_5_vl.py` 第16行硬编码了 α=0.1（介于 Qwen 两档之间）。论文有 ablation 但未公开具体 per-α 精度曲线。

**attention_sink=2、window=4、last_n_full=2 的选取：**
论文附录 A 中：sink=256 tokens（对应 block_size=128 时约 2 blocks），window=512 tokens（约 4 blocks），last_n_full 是最后 2 个 query block 强制 full attention（`deal_output_score` 第370行：`mask_last_full = (q_ids >= M - last_n_blocks_full)`）。原因是最后几个 query block 是因果末端，其 K range 天然稀疏（valid K 很少），直接 full 代价低且能防止输出截断。

## 3. 与前作的差异

**MInference（arXiv 2407.02490）：**
核心思路是识别三种 attention head pattern（A-shape/Vertical-Slash/Block-Sparse），然后**离线 profile** 每个 head 的最优 pattern（需跑一遍 calibration），inference 时根据 head 类型用对应的稀疏索引构建策略。不支持 dynamic per-query adaptation，索引在 per-head 层面是固定的。

**XAttention（arXiv 2503.16428）：**
用 K matrix 的**反对角线 sum**（从左下到右上的对角线之和）作为 block 重要性代理，理论依据是反对角线对应 Q·K^T 中 query-key 距离固定的"等距带"，其和是 block attention mass 的有效近似。与 FlashPrefill mean-K 的差异：mean-K 是对 K block 做空间平均后再做点积（O(d) 操作），antidiagonal sum 是直接对 QK 矩阵做结构化 sum reduce（需要先算 QK）。mean-K 避免了计算完整 QK，代价更低。

**FlexPrefill（arXiv 2502.20766，ICLR 2025 Oral）：**
用 Jensen-Shannon 散度判断当前 query 应用哪种 pattern，然后用**累积注意力分数（Top-p）** 动态选 K index——即从高到低累加到占总质量 p% 为止。需要 partial sort 或 scan 操作，复杂度 O(N log N) 或 O(N)。FlashPrefill 相对它的核心贡献是**max-based dynamic thresholding bypass sorting**：对 query block I，仅做一次 max reduce 得 max_J(Score_{I,J})，然后用 `score >= α * max` 做 mask——这是 O(N) 无排序的线性 scan，在 `deal_output_score` 第359-384行对应 `mask_score = score >= (max_val * alpha)` 逻辑，varlen 版在 `compute_block_max_varlen` kernel 第392行 `out_tile_mask = (sc_tile >= alpha * m_i[:, None])` 直接在 Triton kernel 内完成，完全 GPU-fused 无需任何 sort。

## 5. 实现细节 cross-check

**`K_STRIDE` 与 `BLOCK_SIZE` 的关系：**
`FlashPrefill.forward` 第415行强制 `assert block_size == k_stride`，两者在当前实现中**恒等**（均为128）。`K_STRIDE` 是 mean-K 的 pooling 步幅，`BLOCK_SIZE` 是 FA block 尺寸。`compute_block_score` 里的 `num_stride_per_block = BLOCK_SIZE // K_STRIDE = 1`，实际上每个 mean-K block 就是一个 FA block。

**`mask_last_full = (q_ids >= M - last_n_blocks_full)` 的原因：**
最后 N 个 query block 处于序列末尾，其可 attend 的 K block 数量天然很少（最多等于自身 block index + 1），做 full attention 实际计算量与稀疏相当，且可以避免 mask 后输出被切断（特别是 decode 首 token 对应的最后一个 prefill token）。

**varlen 版与 native 版的差异：**

预期收益：短序列（如8K）不再强制选64块（当前固定64 blocks × 64 tokens = 4096 tokens），而是按内容动态减少，稀疏率从固定约50%变为内容自适应，可降低 stage2 FA 耗时。但关键风险是：MiniCPM-SALA 是用固定 top-K=64 训练的，α-threshold 若选块数<64可能会有精度损失，需 ablation 验证 α（建议从 α=0.1~0.3 扫）。

**第二点（实现代价低）：不排序，直接用 mask 填充 topk_idx**

`block_score.topk()` 内部有 partial sort，O(N log K)。改为：`max_val * alpha` mask 后用 `torch.where + sort` 只排有效 index，当实际选块数远小于 64 时有效减少排序工作量。这在当前 `deal_output_score` 的 `torch.compile` 版等价于去掉 `topk` 预筛选、直接用 max_val 做 threshold。在序列长度 > 64K 时（num_blocks >> 64），这个 sort 省略有效果，但在我们当前 mini_bench 的序列长度下（多为 2K-8K）收益有限。
