**Roofline Model**
Current 8192-token chunk costs are roughly:

| Component | 128K / 16 chunks | 524K / 64 chunks | Scaling |
|---|---:|---:|---|
| MLP FP4 GEMM | ~2.1s | ~8.5s | linear |
| GLA path | ~1.5s | ~6.1s | linear |
| sparse stage2 | ~1.3s | ~5.4s | linear |
| sparse stage1 | ~0.7s | ~10.8s | quadratic over chunks |
| GPU-ish subtotal | ~5.7s | ~30.8s | mixed |

Expected wall: ~6.8-7.5s at ~128K, ~35-45s at 524K if host/API overhead stays similar. The key scaling risk is sparse stage1: terminal chunk grows from ~83ms at 128K to ~332ms at 524K.

**Quantitative Hypotheses**
1. MLP FP4 GEMM is register/occupancy limited, not HBM limited. Existing nsys notes show NVFP4 CUTLASS at 168 regs/thread, ~19% occupancy. The high-value MLP target is not cuDNN backend switching; it is eliminating the BF16 gate/up materialization. Current path writes a 512MB BF16 intermediate per layer at full chunk, then rereads it for SwiGLU+FP4 quant. Plausible gain: 15-30ms/chunk, or ~1-2s over 524K.

2. GLA has little simple headroom left. Current docs show GLA cumulative improvement to ~96ms/chunk, with `chunk_simple_gla` lower bound around 27.6ms/chunk and already bandwidth-bound. Plausible remaining simple-tuning gain: <1% wall. Larger gains require layout/kernel redesign, not flags.

3. Sparse stage2 is memory/indirection plus register limited. Production shape is ~16K row-wise virtual batches, topk 96 x 64 = 6144 KV tokens per row, bf16 KV. Current per sparse layer is ~9.8-10.3ms, 8 layers ~84ms/chunk. Low-register FlashInfer variant remains a plausible 3-5% wall hypothesis; page64 and two-wrapper variants already failed to cross wall-clock noise.

4. Sparse stage1 becomes the long-context bottleneck. Using the 131K calibration of ~10.38ms/layer, stage1 total rises ~15x from 128K to 524K. At 524K it likely exceeds MLP as a single component. The only promising direction is an exact fused stage1 pipeline: score -> pool -> topk, avoiding full score materialization where semantics allow.

5. Host/CUDA API overhead is still material at 128K. Prior nsys showed only ~40% GPU busy in a 5s window, with large `cudaGraphInstantiateWithFlags`, sync, and lazy library load costs. At 524K, GPU work grows enough that the percentage should fall, but absolute overhead can still add several seconds over 64 chunks.
