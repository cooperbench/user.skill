```
Unlike existing n-gram matching methods, SAM-Decoding finds the exact longest suffix match, achieving an average time complexity of O(1) per generation step of SAM update and suffix retrieval. # Arctic Inference Hybrid Speculator Overview
```

```
## Architecture

Arctic Inference combines two complementary speculation approaches:

**1. Suffix Decoding (for repetitive sequences)**
Uses "a compact suffix tree" to match repeating patterns from historical outputs and current prompts, operating at "20 microseconds per speculated token" on CPU. No draft model required.

**2. LSTM-Speculator (for non-repetitive sequences)**
A lightweight neural network using "standard LSTM gates (forget, input, output, cell)" that predicts next tokens from the base model's hidden states.

The system selects between approaches dynamically:

1. Generate candidate tokens using Suffix Decoding
2. Score candidates using empirical likelihood from historical patterns
```

```
# SAM-Decoding: Key Technical Details

## (1) Static vs. Dynamic SAM

**Static SAM**: A suffix automaton built offline from a text corpus. It's constructed by concatenating multiple strings with special symbols (EOS tokens) and remains fixed during inference.

**Dynamic SAM**: Built and expanded incrementally during generation from the current text sequence (user prompts + generated tokens). As the paper states: "For the current text sequence, we create and expand a dynamic suffix automaton incrementally as generation progresses."

## (2) Building and Updating Per Step

**Construction**: Uses Blumer's algorithm with linear time complexity O(L). The static SAM is precomputed offline.

**Per-step updates**: For accepted tokens, the dynamic SAM undergoes two operations:
- State transfer using the Transfer algorithm
- Expansion using the Expand function (detailed in Algorithm 2)

Each node records `min_endpos`—"the earliest position of all substrings corresponding to that node in the reference string."

## (3) Dispatch Rule Between SAM and Auxiliary Draft

The selection uses matching lengths l₁ (static) and l₂ (dynamic):

> "We use the draft from the static automaton only if l₁ > l₂ + l_bias"

The paper prioritizes dynamic drafts and defaults `l_bias = 5`. For auxiliary methods, a fixed virtual match length `l_threshold` (also 5) determines when to switch from SAM to methods like EAGLE-2 or Token Recycling.

## (4) Draft Length Selection

The draft size is set to **40 tokens by default**, reduced to **16 for code datasets**. Ablation studies (Figure 7) show performance peaks at draft size 40; larger sizes degrade efficiency.

## (5) Pseudocode

**Algorithm 1 (State Transfer)**: Iterates through link edges while no matching next edge exists, then transitions via the next edge. Average complexity is O(1).

**Algorithm 2 (Expand)**: Incrementally adds new states and updates suffix links when expanding the dynamic automaton.

**Algorithm 4 (Prim's Algorithm)**: Constructs tree-structured drafts from static SAM using top-k successors weighted by frequency.
```

```
## Metric

The AL reported in `offline_inference/spec_decode.py` takes into account only when the draft was made for a sequence. Assume

* the vanilla model takes 10 forward pass to output 10 token
* With SD
  * a drafter model drafts 2 tokens, i.e., K=2
  * drafter has 100% AR, i.e., the draft is accepted by target when drafter drafts
  * drafter was able to draft only during 1st 2 forward pass, i.e., 3 (K+1=2+1) token produced in 1st fwd pass and again 3 tokens produced in 2nd fwd pass. The remaining 4 tokens i.e., (10-3-3), we produced as 1 token at a time and took 4 fwd pass.

The current formula for AL will measured it as 3, i.e., K+1. However, my intuition is that AL should be measured as how many tokens are accepted in forward pass normalized across sequence generation. A sequence normalized AL would be = num of total token generated / num of fwd pass = 10 / (2+4) = 10/6 = 1.66. This sequence normalized AL is more realistic in the sense that it gives the expected speedup from SD assuming zero overhead and inefficiency from the SD method. This correction is important to make. Without this, ngram will have much higher AL than Eagle on datasets like Instruct Coder but TPOT doesn't reflect that. The current AL computation is more like computing precision whereas to get navigate which method is better just by looking at AL and assuming zero overhead, we need sequence normalized AL.

This PR estimates the sequence normalized AL by finding how many total tokens are generated, how many of them were generated by SD, how many times draft was made and how many tokens were generated without SD. More specifically,

```
num_tokens_generated_without_sd = total_tokens_generated - (num_drafts + num_accepted_tokens)
seq_normalized_acceptance_length = (total_tokens_generated) / (num_drafts + num_tokens_generated_without_sd)
```

In some cases, `num_tokens_generated_without_sd` is negative. This is because of boundary condition where we have <K tokens to predict and we predict K tokens and all K were accepted but the final output has <K tokens. This error is bounded by fraction of `((K-1)*num of samples / num of samples * output len per sample) = ((K-1)/output len per sample)`. Not all samples will run into this boundary condition therefore this is an upper bound and for K=5 and output len 256 this is \~1.5%. Empirically, this was found to be <1% in below benchmarks. Therefore, the impact of this estimation is very negligible on the final results.
```

```
## Analysis

### Impact on AL

The sequence normalized AL of `ngram-eagle` is much higher for editing task since:

* when input is equal to output: it uses ngram draft and hence is better than eagle and equal to ngram in this region
* when input is not same as output: it uses eagle draft and hence is better than ngram and equal to eagle in this region<br>Therefore, overall the AL is much better for `ngram-eagle`

### Overhead:

`ngram-eagle` has similar overhead as `eagle` since drafter has to run. Its overhead is higher than `ngram` as ngram doesnt need to run any drafter auto-regressively.

### Performance analysis on Datasets

* MTBench: perf neutral compared to eagle on general tasks like MTBench. This is achieved by setting higher min_prompt_lookup which increases precision at the cost of lower ngram drafts
* Blazedit: perf is better than eagle or ngram because AL of ngram-eagle is higher than that of ngram or eagle. This higher AL covers the drafting cost of eagle. It is understandable why ngram-eagle has higher AL than eagle for editing task. Comparing with ngram, the ngram-eagle approach benefits from ngram's match when input is same as output. However, when the input and output dont match, ngram will have 0 AL whereas ngram-eagle will have non-0 AL thanks to eagle. This makes the average AL higher for ngram-eagle compared to ngram

Empirically, sequence normalized AL on Blazedit when the edit distance norm is bw \[0.1, 0.25\] as reported above in Benchmarks section:

* eagle: 2.46
* ngram: 2.96 (AL precision was 4.59 but ngram doesnt draft always so seq norm AL is 2.96)
* ngram-eagle: 4.04

### Theoretical Analysis

This in line with my theoretical calculation of AL of ngram-eagle if we change edit distance norm.<br>Precision AL means the AL when the draft was made. vLLM computes AL in this manner which is not complete information hence in the PR I introduced a new metric in offline inference called sequence normalized AL which represents the AL across a seq which gives the expected speedup from SD assuming 0 draft overhead and implementation inefficiency. More detail on the metric is in the PR.

When input is same as output, it will follow ngram's AL and when it diverges it will follow eagle's AL.

* The formula for ngram-eagle AL is `=1000/((edit_norm*1000/eagle_AL) + ((1-edit_norm)*1000/ngram_AL))` .
* The forumula for est ngram AL is `=1000/((edit_norm*1000/1) + ((1-edit_norm)*1000/ngram_AL))`<br>The numerator is 1000 tokens and denominator is the num of steps needed to produce them. The assumption of 1000 tokens doesnt matter since it gets canceled
```

```
## SGLang Ngram Speculative Decoding

SGLang supports ngram-based speculative decoding which retrieves draft tokens from an ngram cache built from previously generated tokens, and then verifies them with the target model.

### Key Features:

- To use NGRAM speculative decoding, you need to use `--speculative-algorithm NGRAM` (CUDA-only).
- Ngram speculative decoding only supports CUDA, does not support `--enable-dp-attention`, and disables the overlap scheduler and mixed chunked prefill.
- NGRAM is a pattern-based "draft" with no draft model weights that predicts from recent text patterns, which is the easiest to try on smaller GPUs and shines on repetitive/structured outputs.

### Configuration Example:
```

## 1. 先把"短前缀走 retrieval"重新定义清楚

正确的语义：
- **派发依据不是"上下文长短"，而是"最近 k 个 token 的后缀能不能在自己的序列前文里匹配上"**。
- 实操参数：`prompt_lookup_min`（如 2）≤ match_len ≤ `prompt_lookup_max`（如 5）。
- 你说"输出内容里重复成分不少"完全正确 —— ngram 命中的高发区就是：实体/术语复读、列表/项目符号、JSON/Markdown 格式 token、prompt 里给的关键词在答里被复读、引文回扣等。

## 2. SAM[EAGLE-3] 的算法（学术版）

```
state: dynamic SAM, 只在当前 (prompt + output) 上增量构建
每个 decode step:
  l_dyn = SAM 用最近 token 串查到的最长后缀匹配长度
  if l_dyn >= l_threshold (默认 5):
      draft = SAM_retrieval(取匹配点后 L 个 token, L 默认 40, 代码任务用 16)
  else:
      draft = EAGLE_3_propose(...)
  target.verify(draft)
  SAM.expand(accepted_tokens)   ← 只 append 自己刚生成的，不写跨请求语料库
```

**关键点**：SAM 论文里 "static SAM" 是建在外部语料库上的；"dynamic SAM" 是 per-request 的。我们只用 **dynamic SAM**，符合你"不实现跨 response 的 suffix 存"的约束。

## 3. vLLM PR #24344 的派发（工程版，更简单粗暴）

## 4. 关键风险：SGLang 现成的 ngram drafter **违反**你的约束 ⚠️

```python

    self.ngram_cache.batch_put(batch_tokens)   # ← 把当前 batch 所有 req 的 token 灌到全局 cache
```

## 5. 落地方案

### 5.1 派发策略选 vLLM 风格（不是 SAM 风格）

理由：(a) 工程简单、零阈值调参；(b) 跟你们现在 EAGLE-3 chain verify 兼容性好；(c) 命中失败的请求继续走 EAGLE-3 没有损失。

### 5.2 in-context lookup 的最小实现

每 decode step，对 batch 里每条 req 独立做：

```python
def inctx_ngram_lookup(token_ids: list[int], k_min: int, k_max: int, draft_len: int):
    """在 token_ids 自身里找 token_ids[-n:] 的最长后缀匹配，n ∈ [k_min, k_max]。
    命中则返回匹配位置后续 draft_len 个 token；否则返回 None。"""
    for n in range(k_max, k_min - 1, -1):
        if len(token_ids) <= n:
            continue
        suffix = token_ids[-n:]
        # 在 token_ids[:-1] 里搜 suffix（不能匹配到自己当前位置）
        # 用 KMP 或者直接 numpy/torch.unfold；O(L) per req
        hit = find_last_occurrence(token_ids[:-1], suffix)
        if hit is not None:
            start = hit + n
            return token_ids[start : start + draft_len]
    return None
```

复杂度 O(L · (k_max − k_min))/req/step。对 8K-16K 上下文，纯 Python 跑一次也就 ~1ms 级，足够；如果想再省可以拿 C++ 简单写一份（apoorvumang/prompt-lookup-decoding 有现成实现可参考）。

# ngram + EAGLE-3 结合 — 7 个工程难点和解法

## 难点 1：EAGLE-3 draft 是有状态的，ngram 是无状态的

EAGLE-3 draft head 第 k 步的输入 = `(token_emb_{k-1}, draft_head_hidden_{k-1})`。它 chain 跑 K 步要靠自己产出的 hidden 续命。ngram 命中后直接拷贝 K 个 token，**没有 draft hidden**。

**解法**：不需要补。EAGLE-3 的 draft state 只在 EAGLE 自己 chain 内部需要。ngram 这一轮 verify 完之后，下一轮 decode step **重新初始化**的 draft state 来自 `forward_draft_extend_after_decode` —— 它读的是 **target verify 输出的 fused hidden**，不依赖于"上一步是不是 EAGLE propose 的"。所以 ngram 跳过 EAGLE draft 一步，下一步 EAGLE 重启时拿到的 hidden 是干净的 target hidden，完全正常。

**唯一注意**：在 `verify()` 里收集 hidden state 时，**不要按"哪些 req 跑过 draft"过滤**，要把 ngram req 的 hidden 也收下来。看 `eagle_worker.py:681` 的 `forward_draft_extend_after_decode(batch)` —— 这个函数遍历的是 batch.spec_info.verified_id（被 accept 的 token），无论 draft 来源都要喂。

## 难点 2：target verify 怎么同时处理两种 draft

最简单：**统一成 chain，长度可以异构**。

你们当前 dynamic spec mode 已经是 chain verify + per-req draft_len（D5 → 5, D7 → 7, NO_SPEC → 0）。加 ngram 就是再多两档：

| 状态 | draft 来源 | draft_len |
|---|---|---|
| NO_SPEC（大 BS） | 无 | 0 |
| D5 + ngram_miss | EAGLE | 5 |
| D5 + ngram_hit | ngram 拷贝 | ngram_K（建议 7~10） |
| D7 + ngram_miss | EAGLE | 7 |
| D7 + ngram_hit | ngram 拷贝 | ngram_K（建议 7~10） |

target verify 端的 ragged 拼接逻辑不变。EAGLE draft 的 forward 这一步对 ngram_hit 的 req **整个跳过**（不进 EAGLE batch）。

## 难点 3：ngram 命中的 draft_len 应该比 EAGLE_K 大

这是和 EAGLE-1/2 不一样的关键收益点。

- 对 EAGLE-1（chain，AL≈2.5）：ngram_K=5 命中 vs EAGLE_K=3 → ngram 直接多吃 2 token。
- 对 EAGLE-3（chain，AL≈5）：ngram_K=5 命中只能持平，没赚。

但 ngram 命中时**几乎全 accept**（来源就是同序列内的复读），所以可以把 ngram_K 拉到 **8~10** —— 比 EAGLE-3 D7 还长。这是 ngram + EAGLE-3 区别于 ngram + EAGLE-1/2 的关键设计点。

`verify cost` 在 chain 模式下是 O(K)（target 一次 forward 多算 K 个位置），D7 → ngram_K=10 增加 +43% verify cost。如果命中率 30% 且 ngram 命中时 AL 接近满档，加权下来仍然净赚。

## 难点 4：什么时候触发 ngram lookup

vLLM 是无脑每步都查。对 EAGLE-3 baseline 强的场景，更聪明的策略：

```
if 上一步 EAGLE accept_len >= 5:
    # EAGLE 跑得很好，别打扰
    skip_ngram = True
else:
    # EAGLE 没接好（停在某种 pattern 上），让 ngram 试一下
    skip_ngram = False
```

这种 conditional dispatch 论文里没人做过，但理论上能把 ngram overhead 进一步压低。

## 难点 5：ngram 命中和 EAGLE 命中"互相吃前缀"

设想 EAGLE chain 跑出 `[A, B, C, D, E]`，ngram 也匹配出 `[A, B, F, G, H]`。如果只是简单二选一会浪费信息。

**SAM 论文的做法**：保留两个 candidate，verify 时取 max acceptance length。但这需要 tree verify。

**vLLM #24344 的做法**：完全二选一（ngram 命中就只用 ngram，不跑 EAGLE forward —— 因为 EAGLE forward 本身就有 cost）。简单但保守。

**对你们项目的建议**：先做 vLLM 风格的二选一。tree merge 在 chain verify 框架下需要改 verify kernel，不值得。

## 难点 6：dynamic spec mode 的 BS 档位需要重新调

加 ngram 后，"是否值得 spec" 的临界 BS 变了。

- 原来 NO_SPEC 阈值是基于"EAGLE draft cost vs accepted token 收益"算的；
- 加 ngram 后，ngram 命中的 req 是 **零 draft cost**（不跑 EAGLE forward），所以即使在比 NO_SPEC 阈值更大的 BS 下也仍然值得 spec —— **但只 spec ngram_hit 的部分**。

可以新增一档：

| BS | 行为 |
|---|---|
| 超大（原 NO_SPEC） | 仍 NO_SPEC，连 ngram 也不查（避免 batch 异构带来的 verify 开销） |
| 大（新增 NGRAM_ONLY） | 只查 ngram，命中 → spec K=10；不命中 → 单步 decode（不跑 EAGLE）|
| 中（D5） | ngram hit → K=10；ngram miss → EAGLE D5 |
| 小（D7） | ngram hit → K=10；ngram miss → EAGLE D7 |

这个 NGRAM_ONLY 档是 ngram + EAGLE-3 比 EAGLE-3 alone 最可能赚到的窗口 —— **大 BS 下 EAGLE draft cost 已经盖不住，但 ngram 几乎零成本**。

## ngram 命中规则

每个 decode 位置 t，输入是当前 sequence `S = prompt + output[:t]`，参数 `k_min, k_max, K`：

```
1. for n in [k_max, k_max-1, ..., k_min]:        # 从长到短试
       query = S[-n:]                             # 最近 n 个 token (= 后缀)
       hit_pos = S[:-1].rfind(query)              # 在前文里找最后一次出现
       if hit_pos != -1:
           draft = S[hit_pos+n : hit_pos+n+K]     # 拷贝匹配点之后的 K 个 token
           return draft                            # 命中
2. return None                                     # 没命中,fallback 到 EAGLE
```

**关键设计**：
- "最长匹配优先"（先试 k_max 再降到 k_min）—— 越长的 query 命中后续越靠谱
- query 长度有下限 k_min，避免 1-gram / 2-gram 这种几乎到处都能匹配的假命中
- 命中后 **直接复制**，不做任何概率/打分

**acceptance length 怎么估**（离线版）：
baseline 真实续写就是 ground truth：
```
accept_len = 最长前缀使 draft[i] == output[t+i]
```
greedy 上限。

## 字符级具体例子

decode 到第二个 `"我需要"` 时：
- query = `"我需要"` (3 char)
- 前文里 `"嗯，我现在需要..."` 出现过 `"我需要"`
- hit_pos 之后的字符 = `"解读用户..."` → 这就是 draft
- 实际 baseline 续写 = `"仔细阅读..."` → **不匹配，accept_len = 0**

但下一个位置 `"我需要仔细阅读这些"`，再往后到 `"这些报错信息..."` 时：
- query = `"报错信息"` (4 char)
- 前文出现过 `"报错信息，并给出..."`
- draft = `"，并给出..."`
- 真实续写 = `"，"` 然后岔开了
- **accept_len = 1**

可以看到一个矛盾：query 在前文有重复，**但 query 之后的 token 不一定重复** —— 这就是 ngram 在通用对话上命中率/AL 都不高的原因。

**找到问题了 — 字符级 probe 有根本性高估**：

看 t=277~284 连续 8 个位置，**都"满档命中 20 字符"，且都指向同一个源**。原因：`with_defaults` 这个标识符在原文 hit_pos=158 处出现过，所以模型从 t=277 开始**一次性 token 生成 `with_defaults(undefined_vars_linter=...)` 一整段**。但字符级 probe 把这一段 token 拆成 N 个独立的 char 位置，**每个位置都被计了一次命中** —— 实际上 token 维度上这只是 1 次命中。

也就是说：

| 度量 | 命中率 | 实际含义 |
|---|---|---|
| 字符级（当前 79%） | 高估 | 每个 token 占 K 个字符，K-1 个虚假命中 |
| token 级（真实） | 未知 | 这才是 ngram drafter 实际工作的粒度 |

字符 → token 的 inflation 比 = 平均 token 长度，MiniCPM 词表上中文 token ≈ 1.5~2 char、英文/代码 token ≈ 3~5 char，混合大概 **2.5 char/token**。粗暴折算：

- 字符级 hit_rate 79% → token 级估计 **30~50%**（命中"块"的密度不会随粒度等比例缩，但虚假命中会消失）
- 字符级 AL=12~16 chars → token 级 AL **5~8 tokens**

这些是上限估计，实际更低（因为 tokenizer 的边界会让"看起来在前文有的串" tokenize 后未必和原串切法一致）。

**两个事实**：

1. 字符级数字**不能直接用**，原因不是 bug 是粒度。
2. 但 79% 字符级命中说明这个数据集**确实重复度高**（代码题、报错引用、术语复读密集），所以 token 级即使打 4 折也还有 ~30%，**不是没戏**。

## 但有 3 个 caveat 必须诚实说清

**1. AL_p99 都满档（K=15 时 p99=15）很反直觉**：
正常分布应该是 AL 随 K 增大慢慢饱和（一些 hit 长一些短）。这里却是"几乎所有命中都直接吃满 K"，说明数据里命中的重复段往往 >> K 长 —— 这跟前面 sample 1 里 `with_defaults(undefined_vars_linter=...)` 反复引用的模式吻合。看起来不是 bug，而是数据集本身就这样。

**2. "ngram 命中时 100% 跳过 EAGLE draft" 是乐观假设**：
工程上要让这条路真正零 EAGLE cost，必须 per-req 派发（命中的 req 跳过 EAGLE forward）。如果走"safety net"模式（ngram + EAGLE 都跑，verify 时择优），EAGLE cost 没省，加速幅度会打很大折。`avg_AL=8.42` 打折后可能只剩 1.4-1.6×。

**3. Lookup CPU overhead 没算**：
每 verify step 一次 `str.rfind`，O(L) 复杂度。长上下文 + batch=16 累积 0.5-2 ms/step。Target verify 5-10 ms/step，overhead 占 10-30%。2.11× 打 8 折 → **实际 1.6-1.8×**。

## 还有一个隐藏的 caveat

**中位数样本 avg_AL=4.11**，跟你的 EAGLE-3 baseline 4.0 基本一样 → **半数 task ngram 几乎不贡献**。

token-weighted avg_AL=9.61 看着很猛，但是因为**前 8 个长样本贡献了 60% 的总 token**，把平均数完全主导了。

## 对工程决策的判断

**取决于 SOAR 怎么算分**：

- **按 token throughput**（总产出 token / 总耗时）→ token-mean 主导 → 理论上限 **1.4-1.6× speedup**（扣完 lookup overhead 和工程实现）
- **按 task 平均 TPOT**（每条 task 独立计时再平均）→ sample-mean 主导 → 提升 ~**5-15%**，工程不值
- **按 worst-case task**（最慢的题打底）→ 长 task 通常是 bottleneck，ngram 在长 task 上猛，**反而帮最大**

## 还有一个隐患

文件名 `speed_bench_cunlimited` 说明这是 **context unlimited** 版（应该还有 `_c1`、`_c8` 版本），输出长度没 cap，给 ngram 极大优势。如果实际 SOAR 评测有 `max_tokens` cap（比如 2K），长 task 的高命中率会显著萎缩，整体收益向 sample-mean 那个 5-15% 靠拢。

**方案 A：per-req 拆 batch（hit/miss 两个 sub_batch 分别 draft）** — **排除**

## 方案 B 具体落地

### 改动 1：新模块 `sglang/srt/speculative/ngram_inctx.py`

per-req 的 in-context lookup，**不共享 state、不跨 request 存**。

```python
class InCtxNgramLookup:
    """每个 req 独立, batch 维度纯函数. 输入 req.origin_input_ids + req.output_ids,
    输出 K 个 token 或 None. 无任何持久 cache."""

    def __init__(self, k_min: int, k_max: int, K: int):
        self.k_min, self.k_max, self.K = k_min, k_max, K

    def lookup_one(self, ids: list[int]) -> Optional[list[int]]:
        # 用 token id -> chr(id + 0x10000) 映射 + str.rfind, 复用 probe 已验证算法
        if len(ids) < self.k_max + 1: return None
        s = "".join(chr(i + 0x10000) for i in ids)
        for n in range(self.k_max, self.k_min - 1, -1):
            p = s.rfind(s[-n:], 0, len(s) - n)
            if p != -1:
                end = p + n
                if end + self.K > len(ids):
                    return None  # 命中位置后续不够 K, 跳过
                return ids[end : end + self.K]
        return None

    def batch_lookup(self, batch) -> list[Optional[list[int]]]:
        # 可以 thread pool 并行, 也可以 ctypes / cython 加速.
        # 第一版 Python 单线程, 测出来再决定要不要 C 化.
        return [self.lookup_one(req.origin_input_ids + req.output_ids) for req in batch.reqs]
```

### 改动 4：lookup 与 EAGLE forward 的时序

`draft()` 内目前是顺序 GPU forward。ngram lookup 是 CPU 工作，可以**和 EAGLE GPU forward 并行**：
- 在 EAGLE `draft_forward` 提交 kernel 之后、`build_tree_kernel_efficient` 之前，开 thread 跑 `batch_lookup`
- EAGLE GPU forward 通常 1-3ms，ngram lookup CPU 全 batch 0.5-2ms，能完美 overlap
- 用 `concurrent.futures.ThreadPoolExecutor` 单 thread 即可（lookup 函数已经是纯 CPU + 无 GIL 释放的 str.rfind，CPU 单核够）

### 改动 5：MARS theta 对 ngram chain 的处理

EAGLE-3 verify 走 MARS rejection（你们 `eagle_info.py` 有 `mars_theta` 字段）。ngram chain 上的 token 没有 draft probability —— 简化处理：**ngram chain 强制走 greedy accept**（target argmax == draft token 就 accept，否则 reject）。

接入：`EagleVerifyInput.verify()` 里 ngram chain 节点的 prob 字段填一个 sentinel，verify kernel 见 sentinel 时走 greedy 分支。
