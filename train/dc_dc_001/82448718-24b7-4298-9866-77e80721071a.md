## 三、两种 Attention 类型的 Linear 层详细对比

### 3.1 标准 Attention 层 (`MiniCPMAttention`, mixer_type=`minicpm4`)

配置参数：`num_attention_heads=32, num_key_value_heads=2, head_dim=128`

| Linear 层 | 类型 | 输入维度 | 输出维度 | 参数量 | 备注 |
|---|---|---|---|---|---|
| `qkv_proj` | `QKVParallelLinear` | 4096 | 4096+256+256=**4608** | 18.9M | Q=32h×128, K=2h×128, V=2h×128 (GQA) |
| `o_proj` | `RowParallelLinear` | 4096 | 4096 | 16.8M | |
| `o_gate` | `ColumnParallelLinear` | 4096 | 4096 | 16.8M | `attn_use_output_gate=true` |

权重文件中的名称：`q_proj.weight`, `k_proj.weight`, `v_proj.weight`, `o_proj.weight`, `o_gate.weight`

**注意**：标准层使用 GQA（Grouped Query Attention），K/V 只有 2 个头（256 维），远小于 Q（4096 维）。

### 3.2 Lightning Attention 层 (`MiniCPMLightningMixer`, mixer_type=`lightning-attn`)

配置参数：`lightning_nh=32, lightning_nkv=32, lightning_head_dim=128`

| Linear 层 | 类型 | 输入维度 | 输出维度 | 参数量 | 备注 |
|---|---|---|---|---|---|
| `qkv_proj` | `QKVParallelLinear` | 4096 | 4096+4096+4096=**12288** | 50.3M | Q/K/V 全部 32h×128（无 GQA） |
| `o_proj` | `RowParallelLinear` | 4096 | 4096 | 16.8M | |
| `z_proj` | `ColumnParallelLinear` | 4096 | 4096 | 16.8M | `use_output_gate=true` |

额外 Norm 层（非 Linear，不需要量化）：
- `q_norm`：RMSNorm(128)（`qk_norm=true`）
- `k_norm`：RMSNorm(128)
- `o_norm`：RMSNorm(4096)（`use_output_norm=true`）

权重文件中的名称：`q_proj.weight`, `k_proj.weight`, `v_proj.weight`, `o_proj.weight`, `z_proj.weight`, `q_norm.weight`, `k_norm.weight`, `o_norm.weight`

**关键差异**：Lightning 层的 K/V 投影是 **4096→4096**（32 个 KV 头），比标准层的 **4096→256**（2 个 KV 头）大 **16 倍**！QKV 总参数 50.3M vs 18.9M。

### 3.3 MLP（两种层共享相同结构）

| Linear 层 | 类型 | 输入维度 | 输出维度 | 参数量 |
|---|---|---|---|---|
| `gate_up_proj`（fused） | `MergedColumnParallelLinear` | 4096 | [16384, 16384]=**32768** | 134.2M |
| `down_proj` | `RowParallelLinear` | 16384 | 4096 | 67.1M |

权重文件中的名称：`gate_proj.weight`, `up_proj.weight`, `down_proj.weight`

加载时 `gate_proj` + `up_proj` 被合并到 `gate_up_proj`。

## 六、应量化的 Linear 层清单

每层的可量化 Linear 权重如下：

**标准 Attention 层（8层）每层 5 个 Linear**：
- `self_attn.q_proj.weight` → [4096, 4096]
- `self_attn.k_proj.weight` → [256, 4096]
- `self_attn.v_proj.weight` → [256, 4096]
- `self_attn.o_proj.weight` → [4096, 4096]
- `self_attn.o_gate.weight` → [4096, 4096]
- `mlp.gate_proj.weight` → [16384, 4096]
- `mlp.up_proj.weight` → [16384, 4096]
- `mlp.down_proj.weight` → [4096, 16384]

**Lightning Attention 层（24层）每层 5+3 个 Linear**：
- `self_attn.q_proj.weight` → [4096, 4096]
- `self_attn.k_proj.weight` → [4096, 4096]
- `self_attn.v_proj.weight` → [4096, 4096]
- `self_attn.o_proj.weight` → [4096, 4096]
- `self_attn.z_proj.weight` → [4096, 4096]
- `mlp.gate_proj.weight` → [16384, 4096]
- `mlp.up_proj.weight` → [16384, 4096]
- `mlp.down_proj.weight` → [4096, 16384]

总共可量化 Linear：8×8 + 24×8 = **256 个 Linear 层**。

## 七、Demo-Quant 量化方案分析

`demo-quant/quantize_gptq.py` 的做法：

1. **方法**：RTN（Round-To-Nearest）W4A16，**不是**真正的 GPTQ（无校准数据、无 Hessian 矩阵）
2. **量化范围**：所有 9 种 Linear 后缀全部量化（`q_proj, k_proj, v_proj, o_proj, o_gate, z_proj, gate_proj, up_proj, down_proj`）
3. **默认参数**：`bits=4, group_size=1024`
4. **输出格式**：伪 GPTQ 格式（qweight, scales, qzeros, g_idx），SGLang 原生支持
5. **非权重文件**：原样复制 .json/.py/.model/.txt
6. **精度转换**：所有非量化张量从 bf16 转 fp16
7. **不量化**：embedding、lm_head、所有 norm 层
8. **已知问题**：CLAUDE.md 明确标注 "RTN 量化精度差，不直接使用"

## 十、量化策略关键观察

1. **Lightning 层占比大**：24/32 层是 Lightning Attention，且每层参数更多（285M vs 254M），约占总 Linear 参数的 **78%**
2. **Lightning 层 KV 维度特殊**：K/V 都是 4096 维（32 头 × 128），不像标准层只有 256 维（2 头 GQA）。NVFP4 量化 [4096, 4096] 的矩阵效率很好（对齐 blocksize）
3. **标准层的小 KV 权重**：k_proj/v_proj 只有 [256, 4096]，矩阵太小可能不适合 FP4 量化（可考虑跳过或保持 fp16）
4. **output gate 层**：标准层的 `o_gate` 和 Lightning 层的 `z_proj` 作用是 sigmoid 门控，对精度可能敏感
5. **embed + lm_head 各约 600MB**：不量化这两个就已经占用 ~1.2GB，量化 Linear 层后模型可缩至约 6-7GB（FP4）
