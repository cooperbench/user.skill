# 容器云 sm_120 GPU 性能测量方法学调研 ## A. 可重复性的根本来源 ### 频率波动下哪些数字"可信" GPU 在没有 user_4813494d 锁频时，SM clock 由硬件 power management 状态机（GPC clock domain）根据温度、功耗、利用率动态调整。Blackwell consumer SKU（如 RTX 6000D）继承了 Ada/Hopper 的 GPC PLL 行为：从 base clock 到 boost clock 之间能浮动 20-40%，且**热降频拐点比数据中心卡（H100/A100）低得多**——后者 power limit 600W、TDP 设计裕量大；consumer 卡热敏感，连续 30 秒 GEMM 就能触发降频。 可信 vs 不可信的本质区分基于 **是否对 frequency 解耦**： - **wall-time（μs）**：不可信，直接正比于 1/freq。频率从 2.6 GHz 跌到 2.0 GHz，同一 kernel 慢 30%，但你测到的"慢"不是 kernel 变差。 - **cycle count（来自 `clock64`）**：可信。cycle 是 SM domain 内基于 clock edge 计数，频率改变只改变 cycle 的物理时间长度，不改变完成同一段 work 需要的 cycle 数。**指令完成需要 N 个 cycle 是硬件 pipeline 决定的，与外部时钟无关**。 - **SASS instruction count**：完全可信，编译期决定，与运行时无关。 - **theoretical occupancy**：可信（编译期 register/shared mem footprint 决定）；achieved occupancy 不可信（依赖 stall pattern，受 memory 子系统影响）。 - **HBM bandwidth utilization 比例**：在共享物理机环境**部分可信**——HBM 是设备私有的，邻居容器不直接竞争同一张卡的 HBM 通道，但**PCIe 带宽、CPU host memory 带宽、L2 cache pollution 受跨容器影响**。 为什么 cycle 不随频率变化？现代 GPU pipeline 的 issue rate、warp scheduler decision、memory transaction 粒度都以 SM clock cycle 为时间单位定义。HMMA tensor core 指令需要固定的 8/16 cycles 完成，无论 clock 是 1 GHz 还是 3 GHz。频率改变的是这些 cycle 在 wall-clock 时间轴上的密度。 ### "相对差异比绝对值可靠"的破例 这个论断**条件成立**。两次运行在同一频率附近时，比值消除了 frequency factor。但破例场合： 1. **A 和 B 触发不同的 frequency tier**。比如 A 是 memory-bound 不发热，跑在 boost clock；B 是 compute-bound 把 SM 烧热，10 秒后降频。此时 A/B 比值反而扭曲——B 看起来比真实情况更差。 2. **不同 kernel 占用不同 power budget**。即使瞬时频率相同，DVFS 状态机的 sticky behavior 让前一个 kernel 的功耗历史影响当前 kernel 的频率。 3. **JIT / autotuning 缓存命中差异**。第一次跑触发 cubin 编译；第二次直接加载。这不是 kernel 性能差异，是基础设施差异。 ### A/B 对照消除什么 **能消除**：宏观环境 noise（房间温度、风扇 RPM 漂移、其他容器低频次活动）、host CPU 频率漂移、长时间尺度的 driver 状态。 **不能消除**： - # GEMM Kernel 调优的第一性原理思维框架 ## 0. 思维方式的根本转变 在任何具体 kernel 之前，先确立一条铁律：**性能不是"调出来"的，是从硬件物理常数和算法数学结构里"算出来"的**。每一行 kernel 代码都应该可以追溯到某个物理常数或某个数学不变量。如果一个改动你说不出它影响了哪个常数、哪个 traffic、哪个 latency，那它就是迷信。 下面建立这条推导链。 --- ## A. 硬件物理常数链 — RTX 6000D 为例 ### A.1 把硬件抽象为一组常数 任何 GPU 在 GEMM 视角下都可以归为下面 14 个物理常数。RTX 6000D（GB202, sm_120）填进去： **计算面** - N_SM = 156（SM 数） - f_clk = 2.43 GHz（boost 时钟） - N_TC/SM = 4（每 SM Tensor Core 数量，Blackwell consumer 4 个） - W/SM = 64（warp slot 上限，每 SM 最多并发 warp） - T/W = 32（warp 宽度，所有 NVIDIA GPU 不变） - mma_throughput(dtype) — Tensor Core 在 dtype 下每 SM 每 cycle 的 FMA 数；FP4 dense 通常是 BF16 的 8× **内存面** - BW_HBM = HBM3 带宽，约 1.8 TB/s（实测 SOL 通常 1.5–1.6 TB/s） - C_L2 ≈ 96 MB，BW_L2 远大于 BW_HBM - Reg_File/SM = 64K × 32-bit = 256 KB（reg 总池） - Reg/Thread_max = 255（硬上限，nvcc/ptxas 不能突破） - SMEM/SM ≈ 100 KB 可用，SMEM/CTA 上限 99 KB - N_Banks_SMEM = 32（每 bank 4 byte，每 cycle） - L_HBM ≈ 400–600 cycle（global load round-trip） - L_SMEM ≈ 20–30 cycle（ldmatrix/ldsm round-trip） - L_MMA ≈ 16–32 cycle（视 dtype） ### A.2 常数之间的关系（这是关键，不是死记） **Occupancy 三约束**（active warps per SM 的上限取三者最小值）： W_active ≤ min( W/SM, Reg_File/SM ÷ (Reg/Thread × T/W), SMEM/SM ÷ SMEM/CTA × Warps/CTA ) 代入 RTX 6000D：若 Reg/Thread = 128，则 reg 限制下 W_active ≤ 256K ÷ (128×32) = 64，正好不卡 reg。若 Reg/Thread = 168，W_active ≤ 256K ÷ (168×32) ≈ 48，掉到 48/64 ≈ 75% occupancy。 **SMEM stage 约束**： SMEM/CTA ≥ stages × (tileM × tileK + tileN × tileK) × bytes_per_elem 这一条决定 stages 不能无限大。 ### A.3 硬约束 vs 软目标 - **硬约束**（违反就编译/运行失败）：Reg/Thread ≤ 255，SMEM/CTA ≤ 99 KB，TMA 16-byte 对齐，warp = 32，mma shape 固定（FP4 是 m16n8k64 / m16n8k128） - **软目标**（影响速度但不致命）：occupancy 数字、bank conflict 数、stage 数、cluster size、L2 hit rate 第一性原理的第一步：**先用硬约束把设计空间砍掉 90%**，剩下的才是软目标博弈。 --- ## B. Marlin（arxiv 2408.11743）的工作流 Marlin 的立项动机不是"GPTQ 已有，做个 kernel"，而是**作者观察到 W4A16 在 batch=1 已被 ExLlama 等 kernel 解决，但 batch≥4 的 serving 场景没有任何 kernel 在 ideal 4× memory speedup 上拿到接近的实测**。这是工作流的第一步：**用一张图把"理论上限 vs 现状"画出来，找到 gap**——4× memory 节省理论换 4× 端到端，但当时实测在 batch 4 已经掉到 1.5–2×。Gap 就是项目的存在依据。 第二阶段是 **Section 3 的硬件分析**。作者不直接进 kernel 设计，而是先列 Ampere SM 的资源帐：寄存器/SMEM 容量、async copy 带宽、tensor core 吞吐、L2 命中率上限。这一阶段的产出是一个"**约束方程**"：要达到 4× 内存上限，每条 dequant→matmul 的 cycle 必须被 weight load 完全 overlap，这反推出 pipeline depth 与 SMEM partition 的下界。这个约束方程是后续所有设计选择的"裁判"。 第三阶段是 **Section 4 的设计选择**。这里关键不是"async pipeline / weight reshuffle / lock-free atomic 各做了什么"，而是**每个选择都有一个明确的 alternative 被否决，否决理由都来自第二阶段的约束方程**： - async pipeline 的 alternative 是经典 double buffer，被否决因为 Ampere `cp.async` 的 latency 在 4-stage 以下吞吐打不平 dequant 开销； - weight reshuffle 的 alternative 是 runtime permute，被否决因为 ldmatrix 模式下 lane → element 映射决定了离线重排是 0 cost 而 runtime 是 N cost； - lock-free atomic（partial sum 直写 global）的 alternative 是 split-K + reduction kernel，被否决因为 reduction kernel 在 batch≤32 时 launch overhead 占比会破坏 scaling 曲线。 第四阶段是 **Section 5 的 evaluation methodology**。这是最容易被读者跳过但最有方法论价值的部分：reference baseline 选 cuBLAS FP16 而不是 FP16 GEMM 上限，因为目标是"端到端在 vLLM 里替换 FP16"；metric 不只是 TFLOPS，而是"**相对 FP16 的 speedup 在 batch 1/4/16/64 的曲线**"，因为 W4A16 的卖点就是"batch 越大越掉"——必须证明它不掉；形状选择覆盖 LLaMA-7B/13B/70B 的所有 GEMM shape，并且**显式列出哪几个形状 sub-optimal 以及为什么**（典型是 K 维度小的 attention out_proj）。 **踩坑沉淀**：作者在脚注承认 striped K partition 的实现初版有 race，是先观察到大 batch 数值偏差才回头加 atomic 屏障；此外 reshuffle layout 的设计经过至少两轮迭代——第一版用 row-major 4-bit packing，发现 ldmatrix 不能直接消费，必须按 mma 指令的 lane layout 反推 packing 顺序。 --- ## B.
