3	## 一个 loss 函数的小考：从 KL 到接受率
4	
5	---
6	
7	### 作者介绍
8	
9	**王致尧**：队长，华中科技大学人工智能专业大四本科生。
10	
11	**武显瑾**：队友，华中科技大学人工智能专业大四本科生。

14	
15	很高兴再次和队友拿下本周冠军
16	
17	---
18	
19	## 01 推测解码的训练目标到底是什么
20	
21	推测解码（Speculative Decoding）的核心机制是：draft 模型预测若干 token，target 模型在单次 forward 中并行 verify。每个 draft token 是否被接受，依据的是经典的 importance sampling 接受规则——给定 target 分布 `p` 与 draft 分布 `q`，token `x` 被接受的概率是 `min(1, p(x)/q(x))`。把这一规则在 `q` 上求期望得到一个简洁的 closed form：
22	
23	```
24	α(p, q) = Σ_x min(p(x), q(x))
25	```
26	
27	α 是 token 期望接受率的精确表达式，也是 speculative decoding 论文里直接挂钩 wall-clock 加速比的物理量。**推测解码 draft 训练真正希望最大化的，就是 α。**
28	
29	那为什么大家训练 draft 时不直接优化 α，而是用 KL 散度？
30	
31	---
32	
33	## 02 EAGLE 的原始 loss
34	
35	EAGLE（Li et al., arXiv:2401.15077）的原始训练 loss 由两项组成：
36	
37	```
38	L = L_reg + w_cls · L_cls,   w_cls = 0.1
39	L_reg = SmoothL1(h_draft, h_target)        # hidden state regression
40	L_cls = CE(p_target, p_draft)              # 输出分布的 cross-entropy
41	```
42	
43	第一项约束 draft 中间表示与 target 中间表示接近，第二项约束 draft 的输出 token 分布与 target 一致。EAGLE-3 进一步把第一项去掉，只保留输出分布层面的拟合，本质上就是 `−Σ p_target · log p_draft`，也就是常说的 plogp loss（KL 与 CE 在分类问题里只差一个常数项）。
44	
45	KL 是一个非常合理的训练目标——它和 α 共享全局最优解：当 `q ≡ p` 时 KL 取最小值 0，同时 `α = 1`。**问题在 "共享全局最优" 这件事其实没什么用**：小 draft 模型的容量远不足以让 `q = p`，训练过程必然停在某个局部最优，而 KL 的局部最优和 α 的局部最优**并不是同一个点**。
46	
47	---
48	
49	## 03 一个会被反复忽略的恒等式
50	
51	LK Losses 这篇论文（arXiv:2602.23881, 2026.02）给出了一个让人愣一下的恒等式：
52	
53	```
54	α(p, q) = 1 − TV(p, q)
55	```
56	
57	其中 `TV(p, q) = (1/2) · Σ_x |p(x) − q(x)|` 是 total variation distance。证明只用一行代数：
58	
59	```
60	Σ_x min(p, q) = Σ_x [p − (p − q)_+] = 1 − Σ_x (p − q)_+ = 1 − TV(p, q)
61	```
62	
63	这条恒等式说明：**最大化 acceptance rate 等价于最小化 TV distance**。TV 是个连续可微（在概率单形上）、有大量数值稳定实现的散度。直接把 KL 换成 TV 作为训练 loss，就是论文 LK^TV 的形式：
64	
65	```
66	L_LK^TV = TV(p, q)
67	```
68	
69	论文的对比实验里有一个非常直观的例子：用一个 1 个参数的"draft"去拟合 mixture-of-Gaussian 的 target。KL 优化收敛后接受率 50.2%，TV 优化收敛后接受率 60.2%——同样的模型容量，仅仅换 loss 函数就拿到 +10pp 接受率。
70	
71	---
72	
73	## 04 LK^λ：自适应混合
74	
75	只用 TV 在工程上有个小问题——训练早期 `q` 与 `p` 几乎不重叠时，TV 接近上界 1，梯度信号弱且 "扁平"。KL 在分布差异大时反而能给出更密集的梯度（penalty 随对数发散）。
76	
77	论文给的折中是一个自适应混合（LK^λ）：
78	
79	```
80	L_LK^λ = λ · KL(p ‖ q) + (1 − λ) · TV(p, q)
81	λ = exp(−η · sg[α])
82	```
83	
84	`sg` 是 stop-gradient——λ 本身不参与反传。直观地：
85	
86	- 训练初期 α ≈ 0，λ ≈ 1，loss 退化为 KL，提供密集梯度做 warm-up
87	- 训练后期 α 上升，λ → 0，loss 平滑过渡到 TV，直接对齐接受率
88	
89	整条切换由 α 自身控制，没有需要手调的 schedule。
90	
91	---
92	
93	## 05 落地观察
94	
95	LK^λ 在工程上几乎是零成本切换——计算复杂度与 KL 同阶，不引入额外 forward / backward。SpecForge（SGLang 官方 EAGLE 训练框架）的 PR #492 提供了开箱即用的实现。我们在 MiniCPM-SALA 的 EAGLE draft 训练中把 loss 从 plogp 换成 LK^λ，acceptance length 有可测量提升，与论文报告的趋势一致。
96	
97	值得说明的是，**LK^λ 不是"魔法"**。论文 ablation 里给出的提升幅度（接受长度 +5~15%，覆盖 4 种 draft 架构、6 个 target、8B~685B 参数规模）是稳定的工程改进，而不是数量级跃迁。它的价值在于：以一个简洁的数学观察（`α = 1 − TV`）把训练目标和推理 metric 直接对齐，并提供一个不需要手调超参的自适应 schedule。
98	
99	对我们来说，这件事的启发更多是方法论层面的：**当看到"标准做法"和"真正想优化的指标"之间存在间接代理关系时，先去检查这层代理是不是必要的**。很多时候——比如这次——绕过代理回到第一性原理只需要一行代数。

21	## 01 量化：FourOverSix 自适应 block scale 选择
22	
23	### NVFP4 格式与标准量化的局限
24	
25	我们的基础量化路线是 GPTQ + NVFP4（FP4 E2M1 格式），decode 阶段使用 Marlin 做 W4A16 推理。NVFP4 的可表示值为 `{0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6}`，最大绝对值为 6。
26	
27	标准 NVFP4 量化时，每个 block 的权重会被归一化到 `[-6, 6]` 的完整 FP4 表示范围（即以 M=6 为上界缩放）。这个设计有一个结构性问题：FP4 在 `[4, 6]` 区间只有一个可表示值（6 本身），而在 `[2, 4]` 区间有两个（3 和 4）。当权重的最大值映射到 6 附近时，`66%~100%` 这段范围内的值都只能用 6 来表示，量化误差集中爆发。
28	
29	### FourOverSix 算法
30	
31	**FourOverSix**（Jack Cook, Junxian Guo, Guangxuan Xiao, Yujun Lin, Song Han；MIT + NVIDIA 联合工作，arXiv:2512.02010）提出：对每个量化 block 自适应地在两种归一化上界之间选择——M=6 或 M=4。
32	
33	当选择 M=4 时，block 的权重被缩放到 `[-4, 4]` 范围。此时 `[2, 4]` 区间内有三个可表示值（2、3、4），分布更均匀，对集中分布的 block 量化误差更小。代价是放弃了 FP4 的 `(4, 6]` 区间，对少数极大值的表示能力略有下降。
34	
35	选择规则是：对每个 block 分别用 M=6 和 M=4 量化一次，计算二者的反量化均方误差（MSE），取误差更小者：
36	
37	```python
38	# M=4 对应的 block scale 约为 M=6 时的 1.5 倍
39	scale_m4 = fp8(scale_m6.float() * 1.5)
40	mse_m6 = ((W_block - dequant(W_block, scale_m6)) ** 2).mean()
41	mse_m4 = ((W_block - dequant(W_block, scale_m4)) ** 2).mean()
42	final_scale = scale_m4 if mse_m4 < mse_m6 else scale_m6
43	```
44	
45	输出格式与标准 NVFP4 完全相同（4-bit 权重 + FP8 block scale），推理 kernel 无需任何修改，吞吐零损耗。
46	
47	### 我们的集成与实测
48	
49	我们将自适应 scale 选择嵌入 GPTQ 量化流程，在每个 block 的 scale 估算之后、GPTQ 权重优化迭代之前执行，使后续的 GPTQ 优化在已确定的 M 值框架下进行，避免二者冲突。
50	
51	实测发现，**约 40–43% 的 blocks 最终选择了 M=4**，MLP 层（gate/up/down proj）的占比明显高于 Attention 层的 QKV 投影。这符合直觉：MLP 权重经过更强的正则，分布较集中；QKV 权重包含更多离群值，M=6 的大范围更有优势。启用 FourOverSix 后，我们在各类评测任务上观测到稳定的量化精度提升。

55	## 02 推测解码：Medusa 在混合注意力架构上的适配
56	
57	### 推测解码的核心逻辑
58	
59	推测解码（Speculative Decoding）的基本思路是：用一个轻量 draft 预测若干后续 token，再让主模型并行 verify，从而在保证输出分布不变的前提下，以一次 verify 的代价换取多个 token 的产出。
60	
61	**Medusa**（Tianle Cai, Yuhong Li, Zhengyang Geng, Hongwu Peng, Jason D. Lee, Deming Chen, Tri Dao；ICML 2024）的核心创新是：**不引入独立的 draft model**，而是在主模型最后一层的 hidden state 上直接附加若干轻量预测头，每个头负责预测后续第 k 个位置。
62	
63	### Medusa Head 的结构
64	
65	每个 Medusa head 是一个带残差连接的单层变换，结构极其轻量：
66	
67	```
68	p_t^(k) = softmax( W₂⁽ᵏ⁾ · ( SiLU(W₁⁽ᵏ⁾ · hₜ) + hₜ ) )
69	```
70	
71	其中 `W₁` 是一个 `d×d` 的线性层，`W₂` 是投影到词表的输出层（复用主模型 LM Head 权重初始化），`hₜ` 是主模型最后一层的 hidden state。**W₁ 初始化为全零**，使得训练初期 Medusa head 的预测与主模型完全一致，训练过程更稳定。
72	
73	### Tree Attention Verify
74	
75	K 个 head 各自取 top-s 个候选，通过笛卡尔积构建一棵候选树（例如两个头各取 top-2，得到 4 条候选路径）。Verify 时，所有候选节点在**一次主模型 forward** 中并行处理，通过修改 attention mask 保证每个节点只能 attend 到其在树中的前驱路径，而非全部候选。验证完成后取最长的接受前缀，完成一次"以一次 forward 的代价验证多条候选"的推测解码循环。
76	
77	### MiniCPM-SALA 适配：GLA State 管理
78	
79	MiniCPM-SALA 是混合注意力架构，除标准 Multi-Head Attention 外，还有大量 GLA（Gated Linear Attention）递推层。GLA 的每步输出依赖一个递推 state `hₜ`：
80	
81	```
82	hₜ = exp(−γ) · hₜ₋₁ + kₜ · vₜᵀ
83	```
84	
85	这给 tree verify 引入了不同于标准 KV cache 的状态管理问题：树中的 sibling 分支必须从**同一 parent state** 出发，而非线性继承前一候选的 state，否则会引入错误的历史依赖。我们针对 verify 路径做了专门的 GLA state 分叉处理，确保混合架构下 tree verify 的语义正确性。
86	
87	此外，Medusa head 的训练数据分布与线上推理场景的匹配度对 accept rate 影响显著。我们基于验证集分布特征对训练数据做了加权采样，使训练集分布向实际推理场景对齐，accept rate 相比随机采样有可测量的提升。
88	
89	### 实验结果
90	
91	Medusa K=1 在 MiniCPM-SALA 上的 verify overhead 约为 0.39 ms，远低于一次正常 decode step 的耗时。各并发级别下 decode 阶段端到端吞吐均有稳定正向收益。

21	## 01 推测解码简要回顾
22	
23	大模型 decode 阶段受 memory bandwidth 约束，每生成一个 token 需将全部权重矩阵从显存搬运一次，计算单元利用率极低。推测解码（Speculative Decoding）针对这一瓶颈，由轻量 draft 模型预先生成 K 个候选 token，再由 target 模型在单次 forward 中并行 verify，在保证输出分布严格不变的前提下，单次 forward 可产出多个 token。
24	
25	实际收益取决于 draft 每个候选的生成代价、候选被 target 接受的比例（accept rate）、以及 verify K 个候选引入的额外耗时，三者共同决定推测解码在具体部署条件下是否具有正收益。
26	
27	---
28	
29	## 02 Medusa：在主模型上附加预测头
30	
31	**Medusa**（Cai et al., ICML 2024）不引入独立 draft model，而是在 target 最后一层 hidden state 上附加 K 个轻量 MLP head，第 k 个 head 预测后续第 k 个位置的 token 分布：
32	
33	```
34	p_t^(k) = softmax( W₂⁽ᵏ⁾ · ( SiLU(W₁⁽ᵏ⁾ · h_t) + h_t ) )
35	```
36	
37	W₁ 初始化为零矩阵，训练初期各 head 输出与主模型等价，有利于收敛稳定性。Verify 阶段，各 head 的 top-s 候选经笛卡尔积构成候选树，配合 tree attention mask 在单次 forward 中完成验证。这一设计的工程优势在于参数增量小、无需 draft 自回归推理、训练流程简洁。
38	
39	但 Medusa 的结构性上限也源于此：各 head 独立预测，第 2 个 head 无法获知第 1 个 head 的预测结果，不存在 head 间共享的递推上下文。每个 head 本质上是对同一 hidden state 的浅层映射，预测位置越远精度衰减越显著。同时，K 增大时候选树规模指数膨胀，verify 开销的增长速率超过 accept rate 的提升。
40	
41	我们在 MiniCPM-SALA 上实现了 Medusa K=1，端到端取得正向收益，但随着 head 数量增加，accept rate 曲线迅速趋于平坦——这反映的是该架构固有的容量上限，而非实现层面的问题。
42	
43	---
44	
45	## 03 EAGLE：自回归 draft 模型
46	
47	**EAGLE**（Li et al., arXiv:2401.15077）在 draft 架构上做了根本性变更：draft 本身是一个自回归模型，输入为 target 的 hidden state 而非 token embedding。draft 接收 target 中间层已压缩的语义特征，以远小于 target 的参数量逼近其输出分布。与 Medusa 不同，draft 自身执行 K 步自回归推理，每步以上一步的输出作为输入，因此具备连贯的递推上下文——而这正是 Medusa 各 head 之间所缺乏的。
48	
49	从 Medusa 迁移至 EAGLE 后，accept rate 上限有实质性提升。
50	
51	---
52	
53	## 04 长上下文下的 accept rate 衰减
54	
55	我们在实测中观察到一个一致的现象：推测解码在长上下文条件下 accept rate 呈系统性下降。这并非某一种 draft 架构的特有问题，而是多个机制叠加的结果。
56	
57	其一是位置编码外推。draft 模型的训练通常以较短上下文为主（受训练成本约束），当推理时序列长度显著超出训练分布，位置嵌入进入外推区间，draft 的内部表示与训练阶段产生偏离，预测精度随之下降。
58	
59	其二是 draft KV 误差累积。draft 自回归执行 K 步推理时，每步均依赖前序步骤生成的 KV cache。短上下文条件下，这些 KV 与 target 之间的偏差尚在 verify 的容忍范围内；长上下文条件下 KV 序列增长，各步的微小偏差沿序列方向逐步放大，K 步执行完毕时 draft 的内部状态可能已显著偏离 target。
60	
61	---
62	
63	## 05 高并发下推测解码的收益回归
64	
65	推测解码的收益随 batch size 增大而递减，batch 足够大时转为负收益——这一点在学术文献中已有讨论（Sequoia, SpecInfer 等），但在工程部署中仍然容易被忽视。
66	
67	小 batch 条件下 GPU 计算资源严重闲置，target 处理 1 个 token 与处理 K+1 个候选的耗时差异极小，瓶颈在于 memory bandwidth 而非算力，verify 的边际代价接近零。中等 batch 条件下 GPU 利用率提升，verify 产生实际的算力开销，target 单次 forward 需并行处理 batch × (K+1) 个 token，额外耗时与 token 产出增益逐渐接近平衡点。大 batch 条件下 GPU 接近 compute-bound，forward 耗时与 token 总量近似线性，推测解码以 batch × (K+1) 的计算开销换取 ≤ K 个额外 token，当 accept rate 不足以覆盖该开销时，关闭推测解码反而是端到端更优的选择。

152	## 5. 五条独立根因（文献支撑）
153	
154	每条根因都有独立验证，在我们场景中可叠加。消除任一不足以解决全部。
155	
156	### 5.1 RoPE 位置外推失效
157	
158	**机制**：EAGLE-3 draft `rope_theta` 默认 10000，训练序列约 2048 tokens；推理 130K prompt 使位置编码在 64-100× 外推。
159	
160	**文献**：
161	- LongSpec (ACL 2025, arXiv:2502.17421) §4.3："EAGLE drafter's position indices... up to 2048 during training vs 200K+ at inference, a 100× extrapolation"
162	- SpecPV："RoPE theta 10000 causes phase collapse beyond 8K position"
163	- YaRN (ICLR 2024)：NTK 公式 `theta_eff = theta * s^(d/(d-2))`；s=64 (130K/2K) 时 theta 应 ~700K
164	
165	**验证**：rope_theta=1M 实测 vlong adj_al +44.9%，已落产，详见 [`experiments.md`](experiments.md) §1。
166	
167	### 5.2 训练位置分布偏斜
168	
169	**机制**：短序列样本数量多 → 小位置（0-2K）过度训练，大位置（>2K）覆盖极少。draft 在大位置 token 的 next-token 预测分布漂移。
170	
171	**文献**：
172	- LongSpec §4.3 图 5：draft 训练数据按位置绘制的频率直方图，2K 处陡降；EAGLE 在 position > 2K 的 acceptance 曲线下坠
173	- 提出 **Anchor-Offset Indices (AOI)**：前 4 个 token 锚定 [0,1,2,3]，后续从随机 offset（0-30K）开始连续递增。2K shard 覆盖 30K 位置空间，收敛 **3.93×**
174	
175	**已落地**：v4 / v2mix_20k 训练已实装 AOI（cap=144000），见 [`training.md`](training/pipeline.md) §1.3。
176	
177	### 5.3 Target Hidden State 分布漂移
178	
179	**机制**：超长上下文下 attention sink 被 InfLLM-v2 sparse 放大，中间层 feature 分布与短上下文训练时不同。Draft 的 fc 层（12288 → 4096）接收协变量漂移的输入。
180	
181	**文献**：
182	- OWL (EMNLP 2025, arXiv:2510.07535)：LSTM drafter 只消费最后 1 token hidden（不依赖 prefix hidden），LongSpecBench acceptance 4.00 vs EAGLE-3 1.28
183	- QuantSpec (2025) §3.1：target SnapKV KV 压缩后 acceptance 89% → 80%
184	
185	### 5.4 InfLLM-v2 Sparse / Draft Dense 注意力不对称
186	
187	**机制**：>`dense_len=8192` 后 target 8 个 standard attention 层走 InfLLM-v2 sparse（top-K block），draft 始终 dense。Target 的 KV 视野与 draft 完全不同。
188	
189	**文献**：QuantSpec §3.1 / OWL §2 明确将此归类为独立于 RoPE extrapolation 的 attention regime mismatch。
190	
191	### 5.5 Draft 训练数据领域覆盖不足
192	
193	**机制**：Draft 在特定 prompt 类型（多跳推理、专有名词、自我修正）上 top-k 漏掉 target argmax。本质纯训练分布盲区。
194	
195	**实证**：idx 17 pre-EOS 65/133 步 al==0，60 步是 "target IN hot_set, NOT in draft top-2"（draft 词表覆盖到了 target token，但 draft 预测排名不够高）。
196	
197	OWL 长上下文测试集（history, finance, law）EAGLE-3 acceptance 1.28，LSTM drafter 4.00。
198

199	### 淘汰方向
200	
201	#### ❌ SMART（arXiv:2604.09731）— batch=1 无收益，淘汰
202	
203	**结论**：SMART 的核心价值是在大 batch compute-bound 场景防止树过展开的负收益。**batch=1 baseline 2.20× vs SMART 2.17×**，与 baseline 持平甚至微负。
204	
205	我们的场景（bs=1 decode，64 并发但 spec 在 decode 路径是独立请求逐个验证）不符合 SMART 的设计假设。
206	
207	#### ❌ Cactus（arXiv:2604.04987）— T=0 greedy 不兼容，淘汰
208	
209	**结论**：Cactus 接受规则 `gamma* = min{q(n) + sqrt(2δ·q(n)·(1-q(n))), 1}`，其中 q(n) 是 target 对 draft token n 的概率。
210	
211	在 T=0 greedy 下：target argmax token n* 的 q(n*)=1，其余 q(n≠n*)=0，因此：
212	- n = n*（draft 猜对）：gamma*=min{1+0,1}=1，接受
213	- n ≠ n*（draft 猜错）：gamma*=min{0+0,1}=0，拒绝
214	
215	**退化为精确 exact-match**，与当前 `verify_tree_greedy` 行为完全等价，零额外收益。
216	
217	### 确认候选方向
218	
219	#### ✅ GOOSE — 各向异性推测树（arXiv:2604.02047, 2026.04）
220	
221	**Greedy 兼容**：设计目标就是 T=0 greedy。核心定理不依赖概率分布，只需估算每个候选来源的 acceptance rate，可从离线统计或 in-context 滑窗获取。
222	
223	**核心机制**：观察到两种 token 来源（n-gram context match vs. 统计预测）的接受率中位数差距 **6×**（范围 2–18×）。最优树应该各向异性：高接受率的 context-matched token 形成深链（spine），低接受率统计预测 token 作为宽分支。
224	
225	**实验结果**：5 个 LLM（7B–33B）比 balanced-tree baseline 提升 **12–33%**。deepresearch 长 pattern 是高接受率 n-gram 的典型场景，在我们的 workload 上预期偏高端。
226	
227	**工程成本**：
228	- PLD n-gram lookup：prefix lookup deduplication，需维护 `{ngram_key → token_id}` 的 LRU 缓存
229	- Bigram adjacency matrix：按 token 对统计条件概率，可从 eval dataset 离线预计算，约 32000×32000 稀疏矩阵（热词覆盖 99%）
230	- 树构建逻辑嵌入 draft generation 步骤，约 200–300 行 Python + 离线统计脚本
231	
232	#### ✅ RACER — AC 自动机检索树（arXiv:2604.14885, 2026.04）
233	
234	**Greedy 兼容**：论文主实验均为 T=0，AC 自动机匹配是确定性操作，完全兼容。
235	
236	**核心机制**：用 Aho-Corasick 自动机索引已生成 token 序列，快速检索当前 prefix 对应的历史续写 candidates。LRU 淘汰控制内存使用。与 logits draft tree 融合：ngram 候选走检索分支，logits 候选走标准 EAGLE draft 分支。
237	
238	**实验结果**：deepresearch 长文本 MAT（Mean Accepted Tokens）提升 **+0.5–0.76**。特别适合长重复 pattern（deepresearch 中"根据搜索结果…"类模板），是 EAGLE 的互补而非竞争。
239	
240	**工程成本**：CPU-only，不占 GPU 时间。约 **400 行 Python**，嵌入现有 draft generation 流程（`eagle_worker.py` draft 阶段前插入 AC lookup）。是候选中实现成本最低的。
241	
242	#### ✅ BanditSpec — 自适应推测步数（arXiv:2505.15141, 2026）
243	
244	**Greedy 兼容**：信号 = accept_length（整数），与概率分布无关。UCB 臂选择是纯整数运算。完全兼容 greedy。
245	
246	**核心机制**：每个请求维护独立 UCB 多臂老虎机，arms = `{dtn=3, dtn=5, dtn=7}`。每完成一个 verify step，reward = accept_length，更新对应 arm 的 UCB 统计量，下一步选择 UCB 值最大的 arm。
247	
248	**为什么对我们有效**：
249	- vlong bucket（p_tok≥50K）当前 avg_al=0.40，dtn=5 等效效率只有 **8%**（每 5 token verify 成本只换 0.4 token 进展）
250	- 若 BanditSpec 学会在 vlong 收敛到 dtn=3，效率提升到 **13%（+63% 相对）**
251	- 编程 bucket（avg_al~2.5）dtn=5 效率 50%，dtn=7 可能更好；UCB 自动发现最优
252	
253	**工程成本**：约 **100 行 Python**，`eagle_worker.py` 中增加 per-req state dict `{rid → UCBArm}`。per-req overhead 极低（一次加法+比较）。是候选中**实现成本最低**的。

- ngram 命中：直接构造一条 chain verify 分支，跳过 draft model forward。
- ngram 未命中：保持原 EAGLE-3 draft path。
- 命中和未命中可以混在同一个 decode batch，最终合并成一个 `EagleVerifyInput` 交给 target verify。
- 提交包默认开启 routing，关闭周期统计日志；CUDA graph 仍保持开启。

提交包指 `demo-sala/` 比赛提交路径。`eval/start_eagle.sh` 只作为本地对齐验证入口，最终平台消费的是 `demo-sala/prepare_env.sh` 导出的 server 参数和环境变量。

关键设计：

1. 每个 req 在 `origin_input_ids + output_ids` 上做最长后缀 lookup。
2. lookup 命中时，构造线性 chain：`verified_id + draft_tokens[:K]`。
3. lookup 未命中时，按 miss indices 建 sub-batch，走原 EAGLE draft。
4. hit/miss rows 合并到一个 `EagleVerifyInput`，target verify 一次完成。
5. `forward_draft_extend_after_decode` 按实际 accept length 扩展 token budget，支持 ngram 接受长度大于 EAGLE nominal steps。

未采用现有 `NGRAMWorker`，因为它维护全局 `NgramCache`，会跨 response 存 suffix；本路线只做 request-local lookup。

## CUDA Graph 稳定性修复

复现过的崩溃：

```text
torch.AcceleratorError: CUDA error: an illegal memory access was encountered
```

表面栈落在 `_build_ngram_chain_verify_input()` 的 `torch.tensor(...)`，但开启同步定位后，真实触发点在 draft CUDA graph replay。

根因判断：

- dynamic spec 的 D5 和 D7 规格不同。
- 旧实现共享一个 draft decode attention backend。
- D5/D7 都可能 capture `bs=1`，FlashInfer backend 内部 per-bs CUDA graph metadata/wrapper 被后一次 capture 覆盖。
- D5 graph replay 可能拿到 D7 backend metadata，造成 multistep KV index layout 和 graph capture 不一致。

修复：

- D5 / D7 分别创建 draft decode attention backend。
- D5 / D7 分别 capture CUDA graph，runner 绑定 capture 时的 backend。

165	## 3. NVFP4 forward GEMM (sm_120)
166	
167	**Status**：integrated 2026-05-07，`EAGLE_NVFP4_FORWARD=1` 默认开。
168	
169	**Effect**：+14% throughput（11.9k → 13.6k tok/s on bs=1，11.8k → 13.0k on bs=4）；peak GPU memory −480 MB。
170	
171	### 3.1 设计
172	
173	旧 trainer 是 fake STE QAT：weight forward 时 round 到 FP4 grid，但 GEMM 仍 bf16。最终 RTN export 误差近零，但训练全程付 bf16 代价。
174	
175	sm_120 有 native NVFP4 tensor cores，training shape microbench 显示 `flashinfer.mm_fp4(use_nvfp4=True, backend="cutlass")` ~5× bf16。
176	
177	Custom autograd Function — forward 4-bit, backward STE：
178	
179	```python
180	class _NVFP4LinearFn(autograd.Function):
181	    forward:  quantize(x) → mm_fp4(xq, wq, ...)   # 真 4-bit GEMM
182	    backward: grad_x = grad_out @ w               # bf16 master
183	              grad_w = grad_out.T @ x             # bf16 master
184	```
185	
186	master bf16 weight 全程保留；quantization 仅 forward；optimizer 看到标准 bf16 grads。
187	
188	### 3.2 NVFP4 scale convention（per `sgl-kernel/tests/test_fp4_gemm.py`）
189	
190	```
191	gs = (E4M3_max * FP4_max) / amax = 2688 / amax    # 乘到 input
192	alpha = 1 / (gs_a * gs_b)                          # descales output
193	```
194	
195	不带这个，amax 小（~0.011 的 q/k/v_proj after `init_mlp_from_target`）会触 e4m3 underflow，`mm_fp4` 返回 NaN 整 block。`x` 和 `w` 各自 per-tensor 量化、各有 gs，`alpha` 每层 call 计算。
196	
197	### 3.3 Quantize-once cache (TTT loop)
198	
199	`fp4_quant_freeze(model)` 在 `Eagle3ModelV4.forward` 起始一次性预算 `(wq, wsf, w_gs)`，3-step TTT 复用 cached packed weight 不再 3× re-quant。`fp4_quant_unfreeze(model)` 在 backward return 前清 cache。
200	
201	### 3.4 lm_head 默认排除
202	
203	```
204	EAGLE_NVFP4_EXCLUDE_LM_HEAD=1   # default
205	```
206	
207	vocab 投影最敏感；FP4 噪声在 32k-vocab logits 上漏进每个 token 的 softmax。`=0` 只用于 GEMM-side win benchmark。
208	
209	`fc`（aux_hidden → hidden adapter）是 plain `nn.Linear`，从不走 FP4：aux_hidden 已在 target 侧 NVFP4 存储，再 FP4 一遍会复合误差（match `convert_to_sglang` deploy-side convention）。

211	### 3.5 Backend choice
212	
213	bench (M=4095/16380, real model magnitudes — `eagle/training/sala_draft/bench_fp4_backends.py`)：
214	
215	| Backend | q_proj 4095 | down_proj 4095 | q_proj BS=4 | NaN-stable |
216	|---|---|---|---|---|
217	| bf16 baseline | 2.00 ms | 3.99 ms | 7.77 ms | yes |
218	| **flashinfer cutlass** | **0.53 ms** | **1.05 ms** | **2.06 ms** | **yes** |
219	| flashinfer cudnn | 0.28 ms | 0.51 ms | 1.04 ms | **NaN at N=256** |
220	| sgl-kernel cutlass | 0.60 ms | 1.19 ms | 2.06 ms | yes |

## week10 提纲：**用 4K 训练序列教 draft 看 144K 上下文 — AOI 与训练流水线**

### 01 长上下文 acceptance 退化的训练侧根因

- 引入：上几周讲了量化、Medusa→EAGLE 演进、loss 函数（LK^λ）。这周接着讲 **draft 训练数据本身的位置分布**。
- 现象：EAGLE-3 在长上下文（>8K prompt）下 acceptance 显著下降，是已发表的普遍现象（OWL EMNLP 2025、LongSpec ACL 2025）。
- 原因不止是 RoPE 外推那种"频率周期"问题，还有一层更朴素的："训练时 draft 几乎没在大 position 上更新过权重"。
- 数据：常规训练语料按位置画频率直方图，**2K 处陡降**（LongSpec 图 5），大于 2K 的位置训练样本极少，draft 在那些位置的 next-token 分布自然漂移。

### 02 AOI：用 4K 序列扫 144K 位置空间

- LongSpec（arXiv:2502.17421）的核心算法（4 行）：
  ```
  P ← [0, 1, ..., N-1]
  o ← RandomInt(0, MAX_LEN - N)
  P[4:] += o
  return RoPE(q, P)
  ```
- 直觉：前 4 个 token 是 attention sink（StreamingLLM 的经典观察），保留原 position；其余整体随机右移。一条 4K 训练样本就能让 draft 看到 [offset, offset+4K] 的任意一段位置编号。
- 论文 ablation：Multi-News τ 3.20→3.36（+5%），训练收敛 **3.93×**。我们的 `AOI_CAP=144000`，匹配 bench 实测最大 ~137K position（×1.05 余量）。
- **关键约束**：draft 的 RoPE base 必须与 target 完全一致；AOI 只动 position_ids，不动 RoPE θ。

### 03 我们的扩展：sequence packing 下的 per-segment AOI

这是 LongSpec 论文没写的工程问题。
- 背景：我们用 FFD bin packing 把变长样本塞进 4096 budget（提升 GPU 利用率）。一条 packed sequence 里有多个 doc。
- 朴素 AOI 在 packed sequence 上的破坏：全序列共用一对 (sink, offset)，document 边界两边的 position 数字连续，attention 会把跨 doc 的 token 误当成同一上下文里的相邻位置。
- 我们的实现（`eagle/training/sala_draft/packing.py:aoi_position_ids_packed`）：**每段独立采样 sink + offset**，配合两件事
  - `document_ids` + cross-doc attention mask（doc 边界硬切断）
  - `mask_segment_tail`：每段尾部 `n_pad=TTT_STEPS` 个位置从 loss 里剔除（左移到下段会污染监督）
- 21 个 packing test 通过，covers boundary 切换、TTT shift、sink ≥ seg_len 退化、cross-doc mask 正确性。

### 04 配套的训练流水线优化

四条都是 profile 驱动的工程改动，单独看小，叠起来把 v2 prod 训练 step 时间从 8.06h（5000 step）压到 6.39h（同 step 数）。

| 优化 | 收益（实测） |
|---|---|
| **NVFP4 forward GEMM** (sm_120 flashinfer cutlass) | +14% throughput；W4A4 真 4-bit GEMM ~5× bf16；master bf16 + STE backward |
| **Async prefetcher** (CPU pinned + main-thread H2D) | load_wait **4.17s → 26ms** |
| **LR cosine + 5% warmup** (vs 旧 warmup→plateau) | step 1750 之后 OOD 还能继续爬（0.716→0.7571） |
| **AdamW fused=True + wd 排除 norm/bias** | 每步省 50–100ms；标准 LLM 配置 |

每条配一句"为什么这个 hack 在 SALA 上能 work"的注解（NVFP4 配 sm_120 native tensor core / pin_memory 让 DMA 与 forward 并行 / cosine 让 LR 在 plateau 后还能下沉 / norm 不该 weight-decay）。

### 05 落地

- 表格对比 v5(`det_prefill`) → `v2mix_20k_s3500_ood757`：OOD step0 **0.7530 → 0.7571** (+0.41%)，IND step0 0.689。
- 训练时间：5000 step planned，3500 step best 提前停（3.7h）。
- 提交包：`demo-sala/data/eagle_draft/` 替换为本次 ckpt，与 `start_eagle.sh` 默认对齐。

### 06 收尾（一句话）

AOI 的启发：**当训练样本和推理样本在某个隐藏维度（位置编号）上分布严重不匹配时，与其等数据自然补齐，不如直接改 position 让 4K 样本扮演 144K 样本**。一行随机 offset，把位置覆盖度从 2K 推到 144K。
