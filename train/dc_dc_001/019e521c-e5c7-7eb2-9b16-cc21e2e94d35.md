这个边界修复说的是：

line91 的 prompt 进 chat template 后已经到 `524183` tokens，而 `context_len=524288`，只剩大约 `105` token 空间。真实生成 `max_tokens=90` 理论上还能 admit，但 EAGLE-3 speculative decode 会额外走 draft / verify / tree / KV / mamba 状态，实际在 prefill 完后进入 D7 verify 时可能越过边界，触发 CUDA illegal memory access。

所以 `SGLANG_EAGLE_CONTEXT_GUARD_TOKENS=256` 的作用是：当序列已经贴近 context 上限时，强制 `NO_SPEC`，并跳过 draft KV 更新。它不是 prefill 优化，也不应该算收益；它只是保证这个极限边界 shape 能做真实生成 smoke，不让验证通道在 decode/spec 处炸掉。

关于 profile 为什么不用 `max_tokens=1`：你说得对，**prefill-only profile 应该用 `max_tokens=1`**。

我这里把两个事情混在了一起：

1. **prefill-only 诊断/profile**
   应该用 `max_tokens=1`，但 server 配置必须保持生产形态：EAGLE dynamic spec、ngram、MARS 都在场。这样隔离 prefill wall，用来选攻击面。

2. **真实生成边界 smoke**
   line91 因为只剩约 105 token，不能跑 `max_tokens=200`，所以用 `max_tokens=90` 验证真实线上生成路径是否还能返回。这一步暴露了 EAGLE context-tail bug，于是才加了 guard。

这次 64.78s profile 数字是从 `max_tokens=90` 那次请求里截到的 prefill forward 聚合，prefill 段本身已经完整落盘，所以热点分布可参考；但作为工作流表达，它确实不应该写成“prefill profile 首选 max_tokens=90”。正确记录应该是：

- **攻击面 profile**：`line91 max_tokens=1`，生产配置不关 spec/ngram/MARS。
- **边界真实生成 smoke**：`line91 max_tokens=90`，用于验证 context-tail + EAGLE guard。
- guard 不计入 prefill 收益，只保证后续真实生成验证不被边界 bug 阻断。
