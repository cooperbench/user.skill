## 1. `max_position_embeddings` 524288 → 1024：对位置 0..511 的 RoPE 有没有影响？

**在你当前配置下：没有影响（逐索引相等）。**

### 数学

标准 MiniCPM RoPE（`MiniCPMRotaryEmbedding`）里，对偶维频率为

\[
\omega_i = \theta^{-2i/d},\quad i=0,2,\ldots,d-2,\quad \theta=\texttt{rope\_theta}=10000
\]

（实现里用 `inv_freq = 1 / (base ** (arange(0, dim, 2) / dim))`，等价。）

位置 \(p\) 上的相位为 \(\phi_{p,i} = p \cdot \omega_i\)，再经 `torch.cat((freqs, freqs), dim=-1)` 拼成与 LLaMA 一致的 128 维 embedding，最后 `cos`/`sin`。**这些量只依赖 \((p,\theta,d)\)，与缓存总行数 `max_position_embeddings` 无关**——`max_position_embeddings` 只决定预先算多少行 `[0, L_cache-1]`，不改变第 \(p\) 行的公式。

`MiniCPM-SALA` 的 `config.json` 里 **没有** `rope_scaling`，Lightning 侧走的是基类 `MiniCPMRotaryEmbedding`，不会触发 LongRoPE/NTK 等「用 `max_position_embeddings` 改频率」的路径：

```2144:2150:/root/shared-nvme/openbmb/models/MiniCPM-SALA/modeling_minicpm_sala.py
    def _init_rope(self):
        if self.config.rope_scaling is None:
            self.rotary_emb = MiniCPMRotaryEmbedding(
                self.head_dim,
                max_position_embeddings=self.config.max_position_embeddings,
                base=self.config.rope_theta,
            )
```

缓存构造为 `t = arange(seq_len)` 与 `inv_freq` 的外积，第 \(p\) 行即 \(p\) 固定：

```567:577:/root/shared-nvme/openbmb/models/MiniCPM-SALA/modeling_minicpm_sala.py
    def _set_cos_sin_cache(self, seq_len, device, dtype):
        self.max_seq_len_cached = seq_len
        t = torch.arange(
            self.max_seq_len_cached, device=device, dtype=self.inv_freq.dtype
        )
        freqs = torch.outer(t, self.inv_freq)
        # Different from paper, but it uses a different permutation in order to obtain the same calculation
        emb = torch.cat((freqs, freqs), dim=-1)

        self.register_buffer("cos_cached", emb.cos().to(dtype), persistent=False)
        self.register_buffer("sin_cached", emb.sin().to(dtype), persistent=False)
```

**推论**：只要校准里 `seq_len≤1024`、且**不会**在 forward 里把 `seq_len` 传到大于当前缓存长度而又与「短缓存」混用，则对任意 \(p\in[0,511]\)，缩短 `max_position_embeddings` **不会**改变 \(\cos/\sin\) 的数学定义；与「建 524288 行长表再取第 \(p\) 行」逐元素一致（仅 CPU/GPU 等非本质数值差异仍可能存在，与表长无关）。

**何时会有影响**：若启用 `rope_scaling`（如 longrope），频率/缩放会显式依赖 `max_position_embeddings` / `original_max_position_embeddings`，那时**所有位置**的表都可能改变，不再适用「只缩短表长」的结论。

## 2. `awq_lite` 收集什么统计量？512 token vs 50K+ 会怎样？

源码在 `model_calib.py` 的 `awq_lite`（你指定文件已读）。

### 2.1 AWQ-lite 专用的「activation scale」——**不是分布，也不是 amax**

缓存阶段：

```721:722:/root/shared-nvme/conda/envs/soar/lib/python3.10/site-packages/modelopt/torch/quantization/model_calib.py
    def get_act_scale(x):
        return x.abs().contiguous().view(-1, x.shape[-1]).mean(0).to(torch.float32)
```

对形状 `(..., C_in)` 的线性层输入：先展平除最后一维外所有维成「token 维」，对 **每个输入通道** 算 **所有 token 上 `|x|` 的算术平均**（L1 均值），得到长度 `C_in` 的向量；再按步数累加并除以 `num_cache_steps`（约 846 行）。

**因此**：这是 **per input channel 的 mean(|activation|)**，不是完整直方图/分位数，也不是 max。

权重侧 `get_weight_scale`：按块对 `|W|` 归一并对输出通道维求平均（703–719 行），得到 **per-input-channel** 的权重尺度，用于和 `act_scale` 一起做 \(\alpha\) 网格上的 `get_scale`（724–736 行），再用 **层输出 MSE** 选 \(\alpha\)（739–744、789–803 行）。

### 2.2 同一轮缓存 forward 里还有 **max 校准**（amax）

```822:829:/root/shared-nvme/conda/envs/soar/lib/python3.10/site-packages/modelopt/torch/quantization/model_calib.py
    enable_stats_collection(model)
    forward_loop(model)

    # Call max_calibrate to load the amax values collected during the caching mode forward pass
    # This will also perform distributed amax sync for input_quantizers
    max_calibrate(model, lambda model: None)
```

`MaxCalibrator.collect` 对张量做 **reduce 后的绝对最大值**，并在多步间取 **逐元素 max**（`max.py` 63–83 行）。NVFP4 各 quantizer 的 axis 决定是 per-tensor 还是 per-channel amax，但本质都是 **观测到的最大绝对值上界**，在 `axis=-1` 时才是「每通道 amax」。

### 2.3 512 vs 50K+：**精确能说清的后果**

- **数据覆盖**：`quantize_nvfp4.py` 里 `truncation=True, max_length=512`（52–57 行），校准 forward **从未出现位置索引 ≥512 的 token**；`get_act_scale` / `MaxCalibrator` 的统计 **完全不包含** 长序列中段、尾段的激活。
- **若真实推理在长上下文下某些通道出现更大 `|x|`**：max 校准会 **系统性低估 amax** → 静态尺度偏紧 → 更多饱和/clipping → **量化误差变大**（这是机制上的结论，不是「也许」）。
- **mean(|x|) 用于 AWQ 的 \(\alpha\) / pre_quant_scale**：若长序列上各通道均值与短序列前 512 token 不同，**平滑尺度与大尺度 outlier 的折衷会偏掉**，同样会推高重构误差。

**不能**从代码推出「精度一定掉多少点子」——但能确定：**校准统计是短前缀上的 L1 均值 + 全域 max（在该前缀内）**，与 50K–127K 评测长度存在 **分布与幅值覆盖缺口**。

## 3. Lightning Attention：第 512 步与第 50000 步的递归状态 / AWQ

### 状态是否「本质不同」

**是。** 递归/分块线性注意力（HF 里 Lightning 用 `chunk_simple_gla` / `fused_recurrent_simple_gla`，见 `modeling_minicpm_sala.py` 49–50 行及 `attn_fn`）在第 \(t\) 步的输出与缓存状态 \(\;h_t\) 是 **前 \(t\) 个 token 的递归函数**；\(t_1=512\) 与 \(t_2=50000\) 时，除非输入序列在前缀上特例等价，一般 **\(h_{512}\neq h_{50000}\)**。这不是实现细节，而是递推定义。

SGLang 侧 Lightning/Mamba 类后端同样维护 `ssm_states` / `final_state` 并在 chunk 间更新（例如 `chunk_gated_delta_rule`、`fused_recurrent_simple_gla` 等，见 `hybrid_linear_attn_backend.py` 搜到的片段）。

### 对 AWQ 激活统计的含义（定量说法）

1. **校准永远只看到「序列长度 ≤512」时、各层在位置 `<512` 上的状态轨迹**，**看不到**「已在 5 万 token 上滚动后的状态 + 第 50000 token 的层输入」这类样本。
2. 因此，**依赖递归深度/历史长度才出现的激活幅值与相关性**，不会进入 `get_act_scale` 的均值，也不会进入若未触发的 tail 位置的 amax —— **长上下文专用的大激活 outlier 在校准里可能从未被 max 捕捉到**。

这不是推测「可能有细微差别」，而是：**统计支撑集不包含 \((\text{长历史}, \text{高位移})\) 的联合**，与第 2 问同属 **覆盖缺口**，在 Lightning 层上额外多了一层 **状态维度上的缺失**。

## 4. 32GB 上更长序列校准：RoPE + AWQ-lite 显存估算

### 4.1 RoPE 缓存（按你给的维度）

单块缓存元素数：`max_pos × 128`。`float32` 字节：`max_pos × 128 × 4`。

若 **\(N_\text{buff}\)** 个独立缓存（脚本里写 64；**HF 实现里**：8 个 minicpm4 层 `attn_use_rope=false` 不建 RoPE，`config.json` 里 **24 个** `lightning-attn`，每层 `cos_cached`+`sin_cached` → **48** 块）：

| \(N_\text{buff}\) | `max_pos` | 合计 (GiB, 按 1024³) |
|-------------------|-----------|------------------------|
| 48 | 524288 | \(48 × 524288 × 128 × 4 / 10^9 ≈ 12.88\) |
| 64 | 524288 | \(64 × 524288 × 128 × 4 / 10^9 ≈ 17.18\) |
| 48 | 1024 | \(48 × 1024 × 128 × 4 / 10^3 ≈ 25.2\) **MB** |
| 64 | 8192 | \(64 × 8192 × 128 × 4 / 10^9 ≈ 0.27\) **GiB** |
| 64 | 65536 | \(\approx 2.15\) **GiB** |

你当前 `max_pos = max_length*2 = 1024` 时，**仅 RoPE  float32 缓存在「64 缓冲」假设下约 33.6MB 量级**，与 `quantize_nvfp4.py` 里把 524288 缩到 1024 以避免 **约十几 GB** 级别缓存的动机一致（具体用 48 还是 64 只差约 25%）。

### 4.2 AWQ-lite **额外**显存（相对「同一形状的一次 forward」）

- **每量化 Linear** 上 `AWQLiteHelper`：`act_scale` 形状 `(C_in,) float32`，`weight_scale` 同阶；`loss` 字典约 `⌊1/alpha_step⌋+1` 个 scalar（默认 `alpha_step=0.1` → 11 个 float）（666–678 行）。相对 **权重+激活** 可忽略（每层 ~10⁴–10⁵ 字节级）。
- **不**像 GPTQ-lite 那样存 Hessian（那是 `O(C_in²)`，见同文件 `hessian_state`）；awq_lite **没有**这类大型累积矩阵。
- **搜索阶段**（864–866 行第二次 `forward_loop`）：对每个命中模块的 forward，在 **一层**内对 \(\alpha\) 循环做多次 `\_forward_no_awq` 并累加 MSE（789–803），是 **时间**换 **不重算图外大缓冲**；峰值仍然接近 **单次前向激活峰值 × 少量临时张量**，不会按层数倍增 Hessian。

**结论**：拉长校准序列时，**首要看**的是：`[B,L,4096]`、`[B,L,16384]` 级激活、KV cache、以及 FLA chunk 中间结果带来的 **\(O(L)\)** 项；**awq_lite 自身常驻附加项相对很小**。

48GB 级别粗算（batch=1，bf16，**单个大张量上界**）：  
- residual：`L × 4096 × 2` B。`L=65536` → **0.5 GiB** 量级/张。  
- FFN up 中间：`L × 16384 × 2`，同 L → **2.0 GiB** 量级/张。  

再叠加 **权重**（你方约 19 GiB bf16 mini）、**48/64 路 RoPE 满长表 ~13–17 GiB**、优化器/碎片：这就是为什么 **满 `max_pos` + 长 `L` 在 32GB 上容易顶满**；把 RoPE 缩到 `max_length*2` 主要省的是 **表长×缓冲个数** 那项。

**可行方向（只分析、不改代码）**：提高 `max_length` 同时保持 **`max_position_embeddings` 仅略大于所用 `L`**（例如 `2^⌈log2 L⌉` 对齐），可把 RoPE 额外显存压到上表中的「MB～几 GiB」档；再配合 **gradient_off/cpu_offload**、更小 batch、或分段校准（多段 forward 累加 calibrator，取决于 ModelOpt 是否允许）去扛 **\(O(L)\)** 激活项。

### 小结表

| 问题 | 精确结论 |
|------|----------|
| RoPE 0..511 | 无 `rope_scaling` 时，表长不改变第 \(p\) 行公式，**0..511 与全长度表一致** |
| AWQ-lite 统计 | **per-channel mean(\|x\|)** + 同步的 **max(amax) 校准**；**不是**一般意义下的完整幅度分布 |
| 512 vs 长文 | **未覆盖长位置/长尾幅值** → amax/均值可偏 → **量化动态范围风险** |
| Lightning 状态 | \(t=512\) 与 \(t=50000\) 的递归状态一般 **不同**；校准 **缺长历史状态** → AWQ 对「深递归」激活支撑不足 |
| 显存 | RoPE：\(N_\text{buff}×max\_pos×128×4\) B（48→~12.9GiB@524k，64→~17.2GiB@524k）；awq_lite **附加为每模块小向量 + 与单次前向相当的临时** |
