greedy-only 场景做 lm_head + argmax 专用路径，避免完整 logits 物化 这个怎么理解

> AGENT

可以理解成：当前 verify 为了做“贪心接受判断”，算得太完整了。 现在路径大概是： ```text target verify forward -> 得到 bs*dtn 个 hidden states -> lm_head: hidden @ vocab_weight.T -> 生成完整 logits: [bs*dtn, vocab_size] -> torch.argmax(logits, dim=-1) -> EAGLE verify_tree_greedy 比较 target_predict 和 draft tokens ``` 但在 greedy-only verify 里，真正需要的是： ```text 每个 verify node 的 argmax token id ``` 也就是只需要 `target_predict`，不需要完整 `[bs*dtn, vocab]` logits 矩阵。 所以“`lm_head + argmax` 专用路径”就是把： ```python logits = lm_head(hidden_states) # 大矩阵，完整写出 target_predict = torch.argmax(logits) ``` 改成一个 verify-only kernel 或专用算子： ```python target_predict = fused_lm_head_argmax(hidden_states, lm_head_weight) ``` 它边算 vocab projection，边做 max-reduction，只输出 token id，避免把完整 logits 写到显存、再读回来做 argmax。 为什么这可能高收益： - `bs=8, dtn=5` 时，每步 verify 要对约 `40` 个 hidden 做 vocab projection。 - 如果 vocab 很大，完整 logits 是 `[40, vocab]`，还通常会转成 float，显存写读和 GEMM 都不便宜。 - 现在 hotspot 已经明确在 `EV_target_forward`，不是 rollback。lm_head/argmax 是 target verify forward 里少数可以“按 verify 语义裁剪”的部分。 但它不是无条件可用，只适合很窄的安全条件： - greedy sampling； - 无 grammar mask； - 无 return_logprob / top_logprobs； - 无 custom logit processor； - 无会改变排序的 logit bias / penalty； - softcap/logit_scale 如果是单调变换，argmax 不变，可以跳过或融合； - downstream 不再需要完整 `logits_output.next_token_logits`。 实现上不是简单改一行，而是要改 contract：让 target verify forward 能返回 `target_predict`，`eagle_info.verify()` 直接吃 `target_predict`，只有需要 logprob/grammar/sampling 时才 fallback 到完整 logits 路径。这个是高收益但高风险路线，需要严格和当前完整 logits 路径做 token-level 一致性对比。
