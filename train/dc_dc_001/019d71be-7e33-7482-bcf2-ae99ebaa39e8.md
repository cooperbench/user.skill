**结论**

真正的 Medusa 和真正的 EAGLE，本质上都不是你们现在这条 `top1` 链式 verify。

你们当前主线是“工程化简化版 Medusa”：
在 [`medusa_worker.py#L113`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L113) 把 `topk` 固定成 `1`，在 [`medusa_worker.py#L301`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L301) 每个 head 直接 `argmax`，再在 [`medusa_worker.py#L304`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L304) 把 verify 输入拼成线性序列 `[verified_id, draft_0, draft_1, ...]`。[`eagle_info.py#L828`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py#L828) 也明确写了 Medusa 这里是 “flat (sequential) draft tokens”。这不是论文意义上的 tree Medusa。

真正的 Medusa 应该是：多头提出多候选，借助 tree attention / tree verify，在一轮 target forward 里验证多条分支，然后选最长可接受前缀。真正的 EAGLE / EAGLE-2 也是树，只是 EAGLE-2 更强调 dynamic draft trees；EAGLE-3 强调多层特征融合和训练期模拟，但在线 verify 如果 `topk>1`，仍然需要 branch-aware 的树式语义。官方来源可对照：
[Medusa paper](https://proceedings.mlr.press/v235/cai24b.html),
[Medusa repo](https://github.com/FasterDecoding/Medusa),
[EAGLE repo](https://github.com/SafeAILab/EAGLE),
[EAGLE paper](https://proceedings.mlr.press/v235/li24bt.html).

**为什么你们会退化成 top1**

因为 MiniCPM-SALA 不是纯 Transformer，而是 hybrid attention。标准 attention 在 [`minicpm_backend.py#L973`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L973) 的 `TARGET_VERIFY` 下走 dense prefill；但 GLA 在 [`hybrid_linear_attn_backend.py#L1636`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1636) 是逐 step recurrent rollout，并在 [`hybrid_linear_attn_backend.py#L1373`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1373) 回滚到 accepted step。对 linear attention，真正的树验证不是“补一个 mask”就够了，而是要维护每个分支自己的 recurrent state、父子跳转和回滚语义。

更关键的是，当前活跃的 `SimpleGLAAttnBackend` verify 路径本质上是平铺 `draft_token_num` 顺序跑，并不消费树分支语义；`retrieve_next_token/sibling` 这种 branch metadata 在同文件别的 recurrent 路径里有部分支持，但你们现在这条 SimpleGLA 主路径没有把“真树”跑通。也就是说：

- `eagle_utils.py` 的树构造和 greedy verify 本身没问题，见 [`eagle_utils.py#L47`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L47) 和 [`eagle_utils.py#L161`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L161)
- 但在你们这类 hybrid linear attention 模型上，真正困难的不是树 mask，而是 branch-aware state evolution

**关于 EAGLE 还是 Medusa 的真正判断**

对你们这个仓库，真正结论很明确：

1. 主线不该回到“真树 Medusa / 真树 EAGLE”。
原因不是理念不对，而是 hybrid linear attention 下 verify 状态机成本太高，且当前实现基础并不支持完整树分支语义。

2. 当前最合理的主线仍然是 `Medusa K=1 / top1 chain verify`。
这和仓库已有结论一致：[`technical-notes.md#L197`](/user_4813494d/openbmb/docs/technical-notes.md#L197) 认为 `K=1` 对 MiniCPM-SALA 最优，收益来自更低的 GLA verify 开销，而不是更高的树覆盖率。

3. EAGLE-3 现在不适合作为主线。
不是树没实现，而是训练分布不对。[`technical-notes.md#L142`](/user_4813494d/openbmb/docs/technical-notes.md#L142) 已经把根因定得很清楚：draft 是 BF16 hidden 上训练的，服务时 target 是 NVFP4，hidden distribution mismatch 直接把 accept rate 打没了。没有“对量化后 hidden 重新训练/蒸馏”，EAGLE-3 不该继续押主线。

4. 你们现在真正该优化的是 verify 等价性，不是把树做复杂。
当前最危险的点仍然是：
`dense verify vs sparse decode` 的语义差异，
以及 hybrid attention verify 的状态回滚一致性。
这也和 [`spec-decode-accuracy-investigation.md#L25`](/user_4813494d/openbmb/docs/spec-decode-accuracy-investigation.md#L25) 的判断一致。

**最终建议**

如果目标是比赛和可落地速度收益：
继续走 `Medusa K=1 + batched TARGET_VERIFY`，不要急着回真树。

如果目标是研究“真正 EAGLE / Medusa”：
先别在 MiniCPM-SALA 上做。
先在纯 Transformer target 上把 tree verify 跑通，再回头设计 linear attention 的 branch-state cache、parent/sibling transition 和 rollback。

如果目标是继续投 EAGLE：

纯源码结论，不做 benchmark：

**结论**
对“这套实现”要分两层说。

1. 对通用 `HybridLinearAttnBackend` 框架来说，真 tree verify 不是完全没做。
2. 但对你们现在的 MiniCPM-SALA 主线来说，真 tree verify 现在不能算成立，因为它实际绑定的是 `SimpleGLAAttnBackend`，而这条主执行路径仍是线性 rollout，不是 branch-aware rollout。

**为什么 MiniCPM-SALA 现在不成立**
[`minicpm.py#L236`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py#L236) 的 lightning mixer 明确写死依赖 `SimpleGLAAttnBackend`，而且在 [`minicpm.py#L383`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py#L383) 直接断言 backend 必须是它。注册逻辑也一样，在 [`attention_registry.py#L237`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/attention_registry.py#L237) 里，`minicpm_hybrid_config` 会选 `SimpleGLAAttnBackend`。

而 `SimpleGLAAttnBackend` 的 verify 主路径在 [`hybrid_linear_attn_backend.py#L1636`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1636) 开始，是把 `(bs, draft_token_num)` 按 step 顺序跑：
[`hybrid_linear_attn_backend.py#L1658`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1658) 到 [`hybrid_linear_attn_backend.py#L1704`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1704) 每一步都是 `current_state -> next_state`，然后按 `step` 存进 `intermediate_ssm`。这条路径没有消费 `retrieve_next_token`、`retrieve_next_sibling`、`retrieve_parent_token`。所以它表达的是“一条链”，不是“一棵树”。

回滚也还是 step 语义。[`hybrid_linear_attn_backend.py#L1373`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1373) 的 `update_mamba_state_after_mtp_verify()` 最终只按 `accepted_steps` 从 `intermediate_ssm[:, req, step]` 取状态。这在链式 verify 下成立，但在 `SimpleGLA` 主路径里，没有任何 branch-aware 状态演化。

**哪些地方其实已经为真树铺了路**
外层 speculative 数据结构是有的。

[`eagle_utils.py#L47`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L47) 会构建 `custom_mask / retrive_index / retrive_next_token / retrive_next_sibling`。
[`hybrid_linear_attn_backend.py#L255`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L255) 在 `topk > 1` 时，会把这些树元数据挂进 `ForwardMetadata`，并分配 `retrieve_parent_token` buffer。

更重要的是，GDN/Mamba 那条 hybrid 路径确实把树语义一路传进 recurrent kernel：
[`hybrid_linear_attn_backend.py#L1028`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1028) 的 `causal_conv1d_update(...)` 收 `retrieve_next_token / retrieve_next_sibling / retrieve_parent_token`，
[`hybrid_linear_attn_backend.py#L1089`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1089) 的 `fused_recurrent_gated_delta_rule_update(...)` 也收 `retrieve_parent_token`。

底层 kernel 也不是假的。
[`causal_conv1d_triton.py#L560`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/mamba/causal_conv1d_triton.py#L560) 注释已经明确是 EAGLE tree custom attention mask 场景。
[`fused_recurrent.py#L330`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/fla/fused_recurrent.py#L330) 也明确写了 parent-token 语义，并在 [`fused_recurrent.py#L439`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/fla/fused_recurrent.py#L439) 左右按 parent state 取中间状态继续递推。

连回滚的步号在 EAGLE worker 里也考虑了树。[`eagle_worker.py#L812`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L812) 对 `topk > 1` 不是简单用 `accept_length - 1`，而是从 `accepted_indices` 算出“最后接受节点在本请求 verify 展开中的相对 offset”，再传给 [`eagle_worker.py#L846`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L846) 的回滚。

- 仍然按 node topological order 遍历
- 但每个 node 从 `parent` 对应 intermediate state 出发
- 用它做 correctness 对拍

我认为这个可以做，但**只能当验证器**，不能当正式性能实现。

---

**怎样兼容 CUDA graph**

这里我反而比较乐观，因为你们现有框架已经把 graph 最麻烦的东西处理掉一大半了。

已有基础：

- 固定 shape 的 `retrieve_next_token / sibling / parent` buffer 已预分配：
  [`hybrid_linear_attn_backend.py#L450`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L450)
- verify 的 `query_start_loc` 也是固定模板：
  [`hybrid_linear_attn_backend.py#L480`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L480)
- replay 阶段已经会根据 batch size 把 metadata copy 进固定 buffer：
  [`hybrid_linear_attn_backend.py#L532`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L532)

所以只要你新增的 `SimpleGLA tree kernel` 满足两点，graph 就能兼容：

1. **不在 forward 里分配新 tensor**
2. **所有 tree metadata 都从预分配 buffer 读**

也就是说，graph 兼容不是主要风险。  
**主要风险是 kernel 逻辑正确性，不是 graph。**

---

**最关键的实现决定**

### 1. `retrieve_parent_token` 必须变成显式输入
别再依赖某条 backend “顺手生成”。

我建议直接在树构造阶段产出它：
- 最好在 `build_tree_kernel_efficient()` 就直接返回
- 这样所有 hybrid backend 都吃同一种 tree metadata

### 2. verify 的 intermediate state 必须按 node 存，不按 step 存
你们现在 `SimpleGLA` 是按 `step` 写：
- `intermediate_ssm[..., step]`

要改成：
- `intermediate_ssm[..., node_idx]`

因为真树里同深度 sibling 不是一个“step”能唯一表达的。

### 3. rollback 继续复用 `accepted node offset`
这点你们 EAGLE 已经走在正确方向上了：
[`eagle_worker.py#L812`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py#L812)

这意味着：
- 不需要推翻 rollback 框架
- 只需要保证 `accepted_steps` 的语义从“链式 step”变成“verify flatten 后的 node offset”

---

**我对性能的判断**

我不保守地说：**如果做成 kernel 版，不会比你们现在的链式 verify 更糟很多，甚至很可能更好。**

原因：

- 现在 `SimpleGLA` verify 本来就是逐 step recurrent，没有吃到 tree 的结构红利
- 真树 kernel 至少可以避免“把 sibling 强行串成链”带来的错误状态推进
- 对 `topk>1`，树化后可以真正复用 prefix branch，而不是伪装成线性序列

当然，它不会像纯 Transformer 那样巨赚，因为 linear attention 仍然是 recurrent。
但它会把你们从“只有 top1 链式可用”推进到“topk>1 在语义上成立”。

这一步值钱。

---

**我明确建议的执行顺序**

1. 先不碰 Medusa
2. 先把 EAGLE 的 target-side tree verify 在 `SimpleGLA` 上做通
3. 用 `topk=2` 作为第一目标，不要一上来 `topk=8`
4. 等 tree verify 内核稳定后，再讨论 Medusa 树化 proposal

原因：

- EAGLE 现在的 tree 外壳已经更完整
- Medusa 现在还只是 flat proposal，树化前置改动更多
- `topk=2` 足够验证 parent-aware kernel 设计是否正确，也更利于 graph 和 debug

> AGENT

我的判断更明确一点：

**相对目前版本，真 tree verify 有价值，但我不会把它当成一个 2x 级别的提速项目。**
如果只改 target-side verify，而不同时把 drafter 做强，我会把预期放在：

- 保守：`0% 到 10%`
- 合理：`10% 到 20%`
- 乐观上限：`20% 到 35%`

这里说的是**相对你们当前 top1 / batched TARGET_VERIFY 版本**，不是相对 nospec baseline。  
这不是 benchmark，是基于代码路径和架构约束的工程估计。

**为什么提升不会特别夸张**

因为你们现在已经吃到了 speculative 的一大块红利：  
不是“并行树”本身，而是“把多个 verify token 一次送进 target”。

真 tree verify 相对当前版本新增的收益，只剩下两件事：

1. 同样的 verify node 预算下，树比链更容易命中更长前缀
2. 可以把 compute 预算花在更有价值的分叉上，而不是死走一条错路径

但对 MiniCPM-SALA，这个额外收益会被一件事强烈压住：

- **24/32 层是 Lightning / SimpleGLA**
- 它本质上还是 recurrent per-node update
- 就算你把 verify 变成真树，**每个 active node 仍然要付一次状态递推成本**

也就是说：

- 对 Transformer，tree verify 的收益同时来自“更好的候选结构”+“target 端并行验证多个 node”
- 对你们这个 hybrid model，第二部分只有 MLP / 普通 attention / QKV 这些 dense 部分能吃满
- `SimpleGLA` 这一大块只能吃到“正确分支组织”的收益，吃不到特别强的并行红利

一句话就是：

**你们现在缺的不是“能不能并行算更多 node”，而是“这些 recurrent node 算得值不值”。**

---

**所以 tree verify 的真实收益来源是什么**

不是 kernel 本身更快，而是**acceptance 更高**。

可以把吞吐粗略写成：

- 当前版本：`Throughput_now ~ (1 + E[a_chain]) / C_chain`
- 真树版本：`Throughput_tree ~ (1 + E[a_tree]) / C_tree`

而这里：

- `C_tree` 不会比 `C_chain` 小很多
- 在 `SimpleGLA` 上，很多时候它还会略大
- 所以你真正能赚的，是 `E[a_tree] > E[a_chain]`

因此：

**真 tree verify 的项目价值，本质上取决于它能把 acceptance 提高多少。**

如果 acceptance 只涨一点，收益就很有限。  
如果 acceptance 明显上涨，它才值。

---

**我对这个项目的更真实预期**

如果你只是把现在的 `SimpleGLA` verify 改成 parent-aware tree kernel，但 drafter 不变，我会预期：

- 大概率是一个 **中等收益项目**
- 更像 `+10% 到 +20%`
- 不像一个“做完立刻翻倍”的项目

如果你同时做两件事：

1. 真 tree verify
2. 更适合 quantized target 的 drafter

那它才可能靠近我上面说的乐观区间。

---

**有没有更好的解决方案**
有，而且我认为**比“直接把当前 SimpleGLA 改成 naive tree kernel”更值得认真考虑**。

### 方案 1：STree 这类面向 SSM / hybrid 的 tree-scan 思路
这是我认为长期更好的方向。

原因：

- 你们现在如果直接做 parent-aware SimpleGLA，本质还是“每个 node 一次 recurrent update”
- STree 这类方法的核心思想，不是单纯让 tree 成立，而是**让树上的状态传播更适合 SSM / recurrent target**
- 它解决的是“树在 recurrent model 上怎么扫”，不是“把 Transformer 的 tree attention 搬过来”

这类思路对你们更贴题，因为你们的难点从来不是 tree mask，而是 **state propagation**

来源：
[STree](https://arxiv.org/abs/2505.14969)

### 方案 2：做动态浅树，不做固定深树
对 recurrent target，我更倾向：

- 宽度放在前 1 到 2 层
- 深度不要太深
- 优先让 user_4813494d 附近多分支，而不是一口气展开很多层

原因：

- recurrent cost基本按 node 数涨
- 深树很容易把算力花在后面低命中率节点上
- 对 linear attention，这种浪费比 Transformer 更痛

所以如果你要真做 tree，我的建议不是“大树”，而是：

- `small dynamic tree`
- `wide near user_4813494d, shallow overall`

这会比固定 `topk=4, depth=4` 更靠谱。

### 方案 3：继续强化当前小 K batched verify
如果目标是 ROI，不是研究完整性，我甚至觉得一个很现实的判断是：

**先把当前 K=1 / K=2 路线做得极致，可能比完整 tree verify 更赚。**

因为它的好处是：

- graph 已经更稳定
- 状态语义简单
- 代码路径短
- 很多开销已经被 batched TARGET_VERIFY 吃掉了

如果 drafter 质量还能继续抬，当前路径未必输给“代价很高的真树”。

### 方案 4：ReDrafter 风格的动态树思路，但要为 recurrent target 重写 verify
这个方向有启发，但不能直接拿来。

原因：

- ReDrafter 的价值在于“动态树 + recurrent drafter”
- 但它的 target 假设还是更接近普通 LLM
- 对你们来说，有启发的是“动态树资源分配”，不是它现成的 verify 实现

来源：
[ReDrafter](https://arxiv.org/abs/2403.09919)

---

**我给你的实际建议**

如果你问我现在该怎么排优先级，我会这么排：

1. **不要把预期放成 tree verify 会大幅超过当前版本**
   更现实的预期是 `+10% 到 +20%`，好一点 `+20% 到 +35%`

2. **如果做 tree verify，不要做大而全**
   先做：
   - `topk=2`
   - 浅树
   - graph-compatible
   - node-budget 固定

3. **从长期上看，最好解不是 naive parent-aware SimpleGLA，而是 STree 式 state propagation**
   也就是：
   - 不只是“让树能跑”
   - 而是“让 recurrent state 在树上跑得划算”

4. **如果资源有限，我会优先做 stronger drafter + current batched verify，而不是先赌完整 tree kernel**
   因为 tree kernel 的投入高，但回报更像增量优化，不像压倒性方案

真 tree verify 值得做，但**更像一个 10% 到 30% 档位的上限拓展项目**，不是颠覆当前版本的方案。  
对 `linear attention 仍然是 recurrent` 这个核心约束，**更好的长期答案不是 naive tree kernel，而是 STree / dynamic shallow tree 这种专门面向 recurrent state propagation 的方案**。
