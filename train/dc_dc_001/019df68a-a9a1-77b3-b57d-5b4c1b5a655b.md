你说得对。我刚才那句“`SEQ_LEN_MAX=16K` 所以 32K/64K 训练不到”说错了，至少表达错了。 AOI 是 **Anchor-Offset Indices**：训练窗口长度可以还是 2K/8K/16K，但 position ids 不按 `[0..S)` 训练，而是保留前 `sink=0..4` 个 anchor token 在低位置，后面的 token 加随机 offset，比如落到 50K、100K、144K 位置段。目的就是让 draft 在训练时见到长上下文的 RoPE 位置分布，解决“训练都在低 position，推理在 50K-130K”导致 accept_len 崩的问题。 所以你们做的不是“真的用 64K attention 训练每一步”。更准确是： - **训练计算窗口最长 16K**，这是显存/TTT/RoPE cache 的约束。 - **AOI 把这个 16K 窗口投到长 position 区间**，cap 现在是 144K。 - **64K shard 的作用**是提供长上下文分布、长 CoT/multi-doc 内容、以及目标模型在长 prefill 条件下的 hidden/logit 采集来源，不是让 trainer 每个 batch 都跑完整 64K self-attn。 - 因此我应该质疑的是“64K shard 被采集后，训练脚本有没有正确从长 shard 中取窗口/切片”，而不是说“16K 截断就说明 64K shard 没意义”。 我们实际在做的是：v3 选层/NVFP4/新配比失败后，v4 回到 v2 的 `[1,10,22] + bf16 + 老配比`，只加训练侧改动：chat template、73440/73441/unk vocab force include、response-only mask、cross-doc mask、AOI、LK^λ。目标是把 EAGLE-3 draft 的长上下文 acceptance 拉回来，而不是单纯训一个更低 loss 的 draft。 已经做了的事实是： - build 端已经生成 971 条 prompt，含 2K/8K/16K/32K/64K 档。 - vocab cache 已生成，`{0,73440,73441}` 已 force include。 - collect 只成功了 600 条 2K short shard，8K+ OOM 阻塞。 - train_v4 在这 600 条 short shard 上跑了 50 step smoke，AOI/LK/mask 路径至少能跑通。 我前面抓到的 post-EOS 没实现、convert 还是 v3，这些仍然是真问题。但我把 `SEQ_LEN_MAX=16K` 当成“64K shard 训练设计错误”的判断不对；正确问题应改成：**如果后面采到 64K shard，trainer 是否按预期从长 shard 中训练 16K AOI 窗口，而不是永远拿 prefix。**
