读完了。下面是我对这个项目的理解，以及它和我们 EAGLE 栈结合的可行性判断。 ## SSD 的核心机制（基于代码而非 README） `speculator_async.py` + `draft_runner.py` 揭示的真实结构： 1. **draft 独占 GPU + 自循环**。`DraftRunner.draft_loop()` 在独立 rank 上阻塞 `recv_cmd()`，接收 `PREFILL/SPEC/EXIT` 三种命令；target 多卡 TP，draft 单卡。 2. **核心 trick = 提前枚举多个 recovery_token 的可能性**。`hit_cache_and_respond()` 用 `(seq_id, last_accepted_idx, recovery_token)` 做 cache key — draft 在不知道真正 verify 结果时，**对多个候选 recovery_token 各展开一棵 K 深 × F 宽的 tree**，target 回来真实 recovery_token 后查表命中即返回（`async_fan_out` 就是这个 F；`speculate_k` 是 K）。 3. **glue decode + tree decode 两段式**：先用真实 rec + K spec 跑 K+1 长度 attention 抽 prenorm/logits（"glue"），再 `get_forked_recovery_tokens_from_logits` 从每个深度 topk 出 F 个分支跑 tree。 4. **EAGLE 模式其实没有完全异步**。看 `_service_spec_request`：`dist.recv(target_recovery_activations, src=0)` 仍是阻塞同步 — 因为 EAGLE draft 必须依赖 target hidden states，依赖链断不开。它的 EAGLE 路径主要靠 tree fan-out + cache 拿收益，不是靠"消除 drafting overhead"。 ## 和我们当前 EAGLE-3 chain verify 的对比 | 维度 | 当前 (`spec_steps=3, topk=2, dtn=7`) | SSD | |---|---|---| | Draft/target 物理位置 | 同卡同进程串行 | 分卡分进程 NCCL | | Tree 形状 | EAGLE-3 chain（topk=2 浅 tree） | F=3 / K=7 深宽 tree | | Cache | 单步 plan cache | recovery-token branching cache | | Dynamic spec | NO_SPEC/D5/D7 按 batch 切换 | 无 | ## 可借鉴的具体方向（按性价比排序） **P0 — 先 profile 再说。** 当前 EAGLE step 里 draft forward 占 step time 多少？我猜 < 15%（draft 484MB FP4 vs target ~15B FP4）。如果 draft 时间本来就很小，SSD 把它藏到 target verify 后面的天花板就很低 — 这一步不做，后面都是空谈。 **P1 — 抄它的 buffer 工程**（低风险、确定收益）。`speculator_async.py` 里 `_alloc_handshake_bufs` 预分配所有 host↔device tensor、`temps_as_int64.view(...).to(torch.int64)` 把 float 塞进 int64 burst 减一次 dist.send 调用。我们 chain verify 每步现有不少 `torch.tensor(device=cuda)` / `.tolist()` 同步点，可以同款预分配。这部分和 SSD 的算法无关，只是 PyTorch 工程。 **P2 — Tree shape 调整**（中等改动）。SSD 默认 `--k 7 --f 3`，意思是 7 步 × 3 分支。我们 `spec3 × topk2` 是更窄的 tree。同 verify cost 下试 `spec2 × topk4` 或 `spec4 × topk2`，看 accept length。这不需要套 SSD 框架，SGLang EAGLE-3 自带 tree attention。 **P3（探索性）— Recovery-token branching cache**。verify 完成前预先对 top-N 可能的 accepted_len × top-M 可能的下一 token 各跑一棵小 tree。EAGLE 这条路被 hidden_states 依赖卡住了 —— 这正是 SSD 自己也没解决干净的地方。只有 vanilla draft（非 EAGLE）才能真异步起来。 **不推荐 P4 — 真把双 process + NCCL 搬过来**。单卡 sm_120 没有"另一套 SM"给你藏 latency，draft 和 target 抢同一个 SM pool；提交包又是单卡假设，工程量大且收益不确定。 ## 一句话总结 **算法层面**它对我们没有银弹（核心 trick 在 EAGLE 上就退化了，单卡部署又用不上物理异步）；**工程层面**有几个具体的 buffer 预分配和 fused NCCL 模式值得抄；**最有用的启发**反而是"recovery_token 是个好的 cache key"这个观察，可能可以用在我们的 dynamic spec 切换逻辑里。 要不要我先做 P0 — 在当前 b12x EAGLE-3 路径里加一个 profile，量一下 draft forward 占 step time 的比例？这一步定了后面所有方向的天花板。
