我看了这个 PR。这是 QQQ paper（HandH1998 团队）2024-07 提交到 IST-DASLab/marlin 的 W4A8 Marlin GEMM 实现，**至今仍 OPEN 未合并**。

## 它做了什么

- 加了一份独立的 `w4a8_marlin_cuda_kernel.cu`（961 行新 CUDA），不是改老 kernel
- **W4(INT4) × A8(INT8) → 走 IMMA**（int8 tensor core），不再 dequant 到 fp16 再 HMMA
- Bench 在 A100；图里给的是相对 cuBLAS fp16 的 speedup
- 思想见 QQQ paper §3.3：weight per-channel INT4 + activation per-token INT8 动态量化，scales 在最后 epilogue 处合并

## 能不能用到我们项目

**结论：不能直接用，但思路对 sm_120 也不适用。**

三个硬卡点：

1. **dtype 不匹配 — 致命**。我们的 weights 是 **NVFP4（FP4 E2M1 + per-block FP8 scale + per-tensor global scale）**，不是 INT4。QQQ W4A8 假设的是 INT4 weight + INT8 IMMA，整套 dequant pipeline 是整数域的 shift/add。要用就得：
   - 重新量化到 INT4（丢掉 NVFP4 的 FP8 group scale 精度优势，需要重做整个 GPTQ + FourOverSix 校准）
   - 或者写一个全新 kernel：FP4 dequant → INT8 量化 → IMMA，理论可行但等于自研

2. **A100 sm_80 → sm_120 没人测过**。Blackwell 上 IMMA throughput 相对 HMMA 没有 A100 那样的明显优势（sm_120 FP4 / FP8 tensor core 才是真正堆性能的地方）。Hopper/Blackwell 时代主流 W4A8 路线已经转向 FP8 activation（CUTLASS NVFP4 + FP8 epilogue），不是 INT8。

3. **decode mem-bound 收益小**。如我上一条所说，我们 decode M≤48 Marlin 实测 ~30.6µs/call 已贴 sol（weight 流量主导）。QQQ 图里 W4A8 加速主要发生在 **大 batch / prefill 形状**（M≥128 起飞），那时 compute-bound，IMMA 吞吐才能兑现。我们 prefill 不走 Marlin。

## 哪些可以借鉴

PR 里有一点值得抄：**`bench_w4a8.py` 的 microbench 框架** —— 跨 M 扫 cuBLAS / FP16 Marlin / W4A8 Marlin 三条曲线找 crossover。这个方法论我们已经在 `docs/gemm/marlin.md` 用类似形式跑过 Marlin vs b12x crossover（结论 M=48）。

**真要继续榨 decode**，按 `docs/gemm/todo.md` 的方向（kernel 内 SASS 重排、dequant prefetch）比换量化档位现实得多。换 W4A8 的工程量 ≈ 重做整条量化栈，且收益在我们的 shape/硬件上理论不显著。

100	    # （vLLM PR #34577：dequant_fp8_scales<nv_bfloat162> 的 5→8 bit exponent widening bug）
101	    if scale_factor is None:
102	        scale_factor = _nvfp4_compute_scale_factor(marlin_scales)
103	    if scale_factor > 1.0:
104	        marlin_scales = (marlin_scales.float() * scale_factor).to(torch.half)
105	
106	    # 转换 exponent bias：FP16 exponent bias=15，FP8-S0E5M3 bias=16，差值=1
107	    # 乘以 2^7 后以 int16 左移1位，再视作 float8_e4m3fn
108	    marlin_scales = (marlin_scales * (2**7)).view(torch.int16) << 1
109	    marlin_scales = marlin_scales.view(torch.float8_e4m3fn)
110	    marlin_scales = marlin_scales[:, 1::2].contiguous()
111	
112	    return marlin_scales, scale_factor

115	def nvfp4_marlin_process_global_scale(global_scale: torch.Tensor) -> torch.Tensor:
116	    """预调整 global scale 的 exponent bias 供 Marlin kernel 使用。"""
117	    assert global_scale.dtype in [torch.half, torch.bfloat16], (
118	        f"global_scale dtype 必须是 half 或 bfloat16，实际为 {global_scale.dtype}"
119	    )
120	    fp4_exponent = 2
121	    target_exponent = 5 if global_scale.dtype == torch.half else 8
122	    exponent_bias = 2 ** (target_exponent - 1) - 2 ** (fp4_exponent - 1)
123	    return global_scale * (2.0 ** (exponent_bias - 7))

173	def prepare_fp4_layer_for_marlin(
174	    layer: torch.nn.Module,
175	    weight_attr: str = "weight",
176	    weight_scale_attr: str = "weight_scale",
177	    weight_global_scale_attr: str = "weight_global_scale",
178	) -> None:
179	    """将 NVFP4 linear 层权重原地重打包为 Marlin 格式。"""
180	    logger.warning_once(
181	        "当前 GPU 不原生支持 FP4 计算，使用 Marlin kernel 做 FP4 weight-only 推理。"
182	    )
183	
184	    part_size_n = layer.output_size_per_partition
185	    part_size_k = layer.input_size_per_partition
186	    param_dtype = layer.params_dtype
187	
188	    weight = getattr(layer, weight_attr)
189	    assert weight.shape == (part_size_n, part_size_k // 2), (
190	        f"期望 {weight_attr} shape ({part_size_n}, {part_size_k // 2})，"
191	        f"实际 {weight.shape}"
192	    )
193	
194	    device = weight.device
195	    layer.marlin_workspace = marlin_make_workspace(device)

197	    # 权重重打包：NVFP4 原始布局 → Marlin tile 布局
198	    perm = torch.empty(0, dtype=torch.int, device=device)
199	    qweight = weight.data.view(torch.int32).T.contiguous()
200	    del weight
201	    marlin_qweight = gptq_marlin_repack(
202	        b_q_weight=qweight,
203	        perm=perm,
204	        size_k=part_size_k,
205	        size_n=part_size_n,
206	        num_bits=4,
207	    )
208	    del qweight
209	    setattr(layer, weight_attr, torch.nn.Parameter(marlin_qweight, requires_grad=False))

217	        size_n=part_size_n,
218	        group_size=FP4_MARLIN_GROUP_SIZE,

224	    weight_global_scale = getattr(layer, weight_global_scale_attr)
225	    weight_global_scale = weight_global_scale.to(param_dtype)
226	    weight_global_scale = nvfp4_marlin_process_global_scale(weight_global_scale)
227	    weight_global_scale = weight_global_scale / scale_factor
228	    setattr(layer, weight_global_scale_attr, torch.nn.Parameter(weight_global_scale, requires_grad=False))

## 关键事实：NVFP4 在原版 Marlin 里**根本不存在**

原版 IST-DASLab/marlin 只支持 INT4 (`kU4`/`kU4B8`)。**我们用的 NVFP4 Marlin 是 sgl-kernel/vLLM 自己加的扩展**，在原 Marlin 流水线里塞了一条 FP4 dequant 路径：

- **dispatch**：`gptq_marlin.cu:442` 单独一条 `FP4_GET_IF(sglang::kFE2M1f)`，与 INT4 的 `COMMON_GET_IF` 并列，强制 `group_blocks==1`
- **weight dequant**：`dequant.h:357-424` 软件 bit-trick，`MASK = 0x70007000` 抽 FP4 的 sign+exp+mantissa，shift 到 fp16/bf16 位置，再乘 `2^BIAS_OFFSET` 修正 exponent bias
- **scale dequant**：`dequant_fp8_scales`（dequant.h:442）把 FP8(S0E5M3) per-group scale 转 bf16
- **global_scale**：`marlin_template.h:1367` epilogue 处再乘一次

但流水线主体是 **W4A16**：
- MMA 指令：`marlin_template.h:89,95,116,131` 都是 `mma.sync.aligned.m16n8k16.row.col.f32.{f16|bf16}.{f16|bf16}.f32` —— **HMMA(bf16) 张量核**
- activation 全程 bf16，FP4 weight 在 register 里 dequant 成 bf16 后喂 HMMA

所以 "NVFP4 Marlin" 在框架视角下 = **"在 Marlin pipeline 里加 FP4→bf16 dequant 路径，复用 HMMA"**。这跟 QQQ PR #31 的思路同构 —— QQQ 是加 INT4→INT8 路径复用 IMMA。

## 那么 NVFP4 A8 在 Marlin 里可行吗？

**理论上可以做，工程上是个新 kernel，不是参数调整。**

需要 cherry-pick 三件事：

| 模块 | 现状 (W4A16) | 需改造 (W4A8) |
|---|---|---|
| weight dequant 出口 | FP4 → bf16 (bit-trick) | FP4 → fp8 e4m3 (bit-trick 改 mask/shift) |
| MMA 指令 | `m16n8k16 f32.bf16.bf16.f32` | `m16n8k32 f32.e4m3.e4m3.f32`（sm_120 FP8 tensor core） |
| activation 入口 | bf16 直接进 | bf16 → fp8 per-token quant + scale stash |
| accumulator | fp32 | fp32（不变） |
| epilogue | × global_scale × act_scale | × global_scale × act_scale_per_token |

硬件 ISA 在 sm_120 上**完全支持** FP8 MMA，我之前说"ISA 不允许"是错的。真正的约束是：

1. **没人写过**。sgl-kernel/vLLM 现有 `kFE4M3fn` 路径是 W8A16（FP8 weight + bf16 activation），不是 W4A8。QQQ 的 W4A8 是 INT 域，跟我们 FP 域不同套 dequant 数学。
2. **decode 是 mem-bound，A8 收益在 compute-bound 形状**。M≤48 weight 流量主导（4096×4096 weight = 8MB vs activation 8×4096 = 16KB），把 activation 从 bf16 砍半到 fp8 对总带宽影响 <0.2%。
3. **fp8 量化 epilogue 会引入新的精度损失链**：per-token act_scale + per-group weight_scale + global_scale 三重缩放，需要重新校准。

## 实际收益估计

- **M=1 decode**：理论几乎没有（已贴 sol 下界，weight bandwidth 决定）
- **M=8~48**：可能 5~15%，因为这个范围已经开始 compute matter，FP8 tensor core peak 是 BF16 的 2×。但需要看 dequant→FP8 的内开销能不能 hide
- **M>48**：我们走 b12x CUTLASS NVFP4 W4A4，已经是 FP4 双侧 MMA，更快，不该走 Marlin
- **工程量**：参考 QQQ PR 是 +961 行 CUDA + +148 行 bench + +182 行 test。在我们 fork 上做约同规模

## 建议

如果真要碰，路线是：fork sgl-kernel Marlin，把 `dequant<*, kFE2M1f, *>` 出口加一个 `→fp8_e4m3` 版本，把 `m16n8k16 bf16` MMA 换成 `m16n8k32 e4m3`，activation 入口加 per-token fp8 quant。但 **decode 收益预期低**，按 ROI 不如继续按 `docs/gemm/todo.md` 的方向（dequant SASS 重排、ldsm 调优）。
