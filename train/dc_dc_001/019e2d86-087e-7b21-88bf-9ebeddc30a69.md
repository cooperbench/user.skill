**关键差异**
1. SpecForge 是通用框架：先 regenerate 文本，再 online 训练或 offline 生成 hidden states；支持多 server 地址、FSDP/TP/USP、模板解析、VLM、tracker。见 [training.md](/tmp/specforge/docs/basic_usage/training.md:5) 和 [regenerate_train_data.py](/tmp/specforge/scripts/regenerate_train_data.py:97)。
2. 我们是 SALA 专用：prompt 只到 assistant header，target 在生产 SGLang decode 路径生成，并由 hook 一次性存 `prompt_last + generated` 的 aux hidden、topK logits、logsumexp、mask。见 [collect.py](/user_4813494d/openbmb/eagle/pipelines/target_regen/collect.py:1)。
3. SpecForge 训练 loss 是 full draft-vocab soft target 的 LogSoftmaxLoss；我们用 topK + full logsumexp 的 `LK^lambda` acceptance proxy，更贴近 spec acceptance。见 [train.py](/user_4813494d/openbmb/eagle/training/sala_draft/train.py:197)。
4. SpecForge 默认 TTT 长度 7；我们当前训练 TTT=3，生产 D7 属于 stretch。见 [train.py](/user_4813494d/openbmb/eagle/training/sala_draft/train.py:122)。
5. 我们有 SpecForge 没有的 SALA 特化：AOI 长上下文位置、cross-doc packing、segment tail mask、NVFP4 forward GEMM、production quantized target/hook 对齐。

**我们做得好的**
- 数据采集更贴近真实部署：不是 HF forward，不是纯 prefill，走量化 target + SGLang server hook，能暴露生产 decode/runtime 差异。
- 采集校验很严：长度、mask、prompt-last、generated prefix、hook 文件清理都有 gate。见 [collect.py](/user_4813494d/openbmb/eagle/pipelines/target_regen/collect.py:163)。
- 训练目标更工程化：response-only mask、AOI、LK loss、topK sparse target，和 MiniCPM-SALA 的长上下文/提交包目标更一致。
- packing 做得好：per-segment doc id、AOI、tail mask，解决短样本 padding 浪费，同时避免跨样本污染。见 [packing.py](/user_4813494d/openbmb/eagle/training/sala_draft/packing.py:1)。

**主要不足**
- 扩数基础设施弱于 SpecForge：`collect.py` 只有单 `api-base`，没有官方那种多 server 地址调度；resume 也偏手工，缺全局 manifest。
- 数据源配比固定且池子偏小。现在 20K 可行，但 100K+ 时默认 `max_stem_zh/max_open_code/max_codeforces` 会卡住，需要引入更多源并按 token/domain 而不是样本数配比。
- 存储会先爆：脚本估算约 `25.4KB/token`，4096 tokens 最坏接近 100MB/sample；100K 最坏约 10TB，实际也可能 5TB 级。继续 flat `.pt` per sample 会遇到 inode/IOPS/索引成本。
- 评估选择仍偏 proxy：`OOD step0` 有用，但不能替代 D5/D7 runtime accept、公开集 accuracy、no-spec/spec 一致性。
- sparse topK=128 可能限制大规模收益。官方 full logits/target-head 路线没有这个截断；我们至少应记录 topK mass 并 A/B K=256/512。
- 多轮能力弱：我们的 target_regen 基本是 first user prompt；SpecForge 会逐个 user turn regenerate，保留 history。

**建议路线**
1. 先补规模化采集层：多 `api-base`、`--resume` 按 `source_id/rid` 跳过、atomic save、manifest、source/length/EOS/topK-mass 统计、分 shard 目录。
2. 先做 `100K` pilot，不直接上 500K。保持 20K prod 为 baseline，新增样本必须 source_id 去重，重建 vocab cache。
3. 数据混合改成“token budget + domain budget”：reasoning/STEM/code/general chat/long-context 分桶，按 heldout accept gap 动态调权。
4. 存储改造优先级很高：至少分组目录 + manifest；更好是 aux_hidden NVFP4 压缩、topK values fp16、indices int32，或 shard container，避免百万 `.pt`。
5. 训练侧先保 TTT=3 扩数，另开小实验做 TTT=5、EMA、HASS scheduled self-prediction。不要把这些和 100K 扩数混在一个变量里。
6. 每个候选必须跑四个 gate：`OOD step0/1/2`、public accuracy、D5/D7 accept/speed、no-spec/spec 输出一致性。

我建议下一步先落一个 `v2mix_100k` 的可复现数据计划和采集 manifest，再开始跑。当前工作区没有 `eagle/data` / `eagle/weights` 实物，所以这次没有复算真实长度分布或训练曲线，也没有改代码。

结论：先做 **100k v2mix_plus pilot**，不要直接 300k。SALA EAGLE3 这里最重要的不是原始 assistant 质量，而是 **prompt 分布 + target-regenerated continuation 与生产 target 对齐**。SpecForge 的核心实践也是 target regeneration；我们当前管线已经遵循这点，只是需要把 prompt 池、holdout、过滤和验收做得更系统。

**固定不变项**
- target 仍用 `/user_4813494d/models/openbmb/MiniCPM-SALA-gptq46-calib90-90k-NVFP4-det`
- aux layers 仍 `[1,10,22]`
- `temperature=0.0`，不要用 SpecForge 示例里的 `0.8`；我们服务是 greedy/spec verify，训练目标应贴生产。
- `generate_tokens=4095`，保存窗口仍是 `prompt_last + generated[:4095]`
- `EAGLE3_TOP_K=128` 先不动；只记录 topK mass，低了再单独 A/B K=256。
- 训练仍 `SEQ_LEN_MAX=4096`、`TTT_STEPS=3`、packing on、NVFP4 forward on。

依据：现有 prompt 只发 user/system prefix，assistant 由 target 生成；collect 保存 prompt-last + generated rows，见 [build_prompts.py](/user_4813494d/openbmb/eagle/pipelines/target_regen/build_prompts.py:1) 和 [collect.py](/user_4813494d/openbmb/eagle/pipelines/target_regen/collect.py:1)。SpecForge 也明确建议用 target regenerate 对齐 draft/target 分布。

| Chinese R1 / reasoning | 40k | 继续主力，但从 60% 降到 40%，避免 R1 腔过重 |
| ShareGPT 中文真实多轮 | 20k | `common_zh` + `computer_zh(fixed)` 优先，`unknow_zh` 限量 |
| STEM/math 中文 | 18k | `stem_zh` + `numina_math`，补知识/推理覆盖 |
| code | 15k | `open_code_reasoning` + `codeforces`，保留现有代码收益 |
| long/context-like | 5k | 长 prompt、总结、检索式、多文档类 |
| edge/general | 2k | dolphin/英文/安全拒答少量覆盖 |

300k 总量建议：

| domain | count |
|---|---:|
| Chinese R1 / reasoning | 90k |
| ShareGPT 中文真实对话 | 75k |
| STEM/math | 60k |
| code | 45k |
| long/context-like | 20k |
| edge/general/bilingual | 10k |

ShareGPT 中文这批本地可用中文去重约 133k，适合作为“真实用户 prompt 分布”来源；官方卡也强调真实复杂场景和多轮对话。`common_zh_70k`、`computer_zh_26k(fixed)` 优先，`unknow_zh_38k` 只抽 20-30%，因为翻译腔、幻觉和 jailbreak 类样本更多。

**Prompt 构造**
- 训练主线仍取 **first user prefix**：system + first user，遇到第一个 assistant 立即截断。这和当前 `first_user_prefix()` 一致。
- 多轮不要直接把原始 ShareGPT assistant 历史塞进 prompt 作为大比例数据。更好的做法是 SpecForge 风格：先用 target 顺序 regenerate 历史 turn，再从 regenerated conversation 中抽第 k 个 user prefix。
- 100k：first-turn 85%，target-regenerated multi-turn prefix 15%。
- 300k：first-turn 65-70%，target-regenerated multi-turn prefix 30-35%。
- 多轮截断规则：保留 system、当前 user 完整内容；从最老 turn 开始删，不能在当前 user 中间硬截。所有同一 `conversation_id` 派生 prompt 必须进同一个 train/val split。

**长度分桶**
按 `prompt_n_tokens` 控制，而不是只按样本数：

| bucket | 100k ratio | 300k ratio |
|---|---:|---:|
| 8-128 | 10% | 8% |
| 129-512 | 35% | 30% |
| 513-1024 | 25% | 25% |
| 1025-2048 | 20% | 22% |
| 2049-4096 | 10% | 15% |

先不要把主训练 prompt cap 拉到 16k。可以另做 5k-10k long-prompt slice，用更低 `MAX_RUNNING` 采集，看 OOD long accept 是否真涨；否则容易只增加采集成本。

**去重与过滤**
- exact dedupe：`normalized_prompt_text` hash，跨所有 source 做，不只 `source_id`。
- near dedupe：按中文 char 5-gram / SimHash，Jaccard >0.85 只留一个。
- split dedupe：先按 `conversation_id/source_id` 分 train/val/OOD，再展开 turns，避免多轮泄漏。
- prompt filter：空、乱码、角色不交替、assistant-first、只有 system、prompt token 超限、`input == "-"` 这类弱指令直接丢。
- ShareGPT filter：`common_zh`、`computer_zh(fixed)` 优先；`continue` 文件不算新增；`unknow_zh` 低权重。
- collect 后 filter：`n_generated_tokens <64` 不计入主训练；blank/repetition/special-token 异常丢；记录 `topK_mass`、draft-vocab hit rate、generated length 分布。

**Holdout**
- 100k：IND 1k，OOD 至少 512。
- 300k：IND 2k-3k，OOD 1k。
- 保留现有 `ood_bench64` 只做可比性，不要只用它选 ckpt；新增 OOD 分成 `zh_chat`、`code`、`math`、`long_context` 四桶。
- OOD 只从未参与训练的数据源/会话抽，近重复也排掉。

**采集参数**
继续：

```bash
EAGLE3_TOP_K=128 MEM_FRACTION_STATIC=0.55 MAX_RUNNING=24 PORT=30000 \

```

磁盘要提前算清：当前 20k 约 1036GB；100k 约 5.2TB observed、10.4TB worst-case；300k 约 15.5TB observed、31TB worst-case。`aux_hidden` 占 96.8%，短期不要上 NVFP4 压缩，除非先做 10k A/B，因为历史上压缩路径有过 acc 负反馈。

**训练与验收**
- 100k：重建 vocab cache；先跑 6k-10k steps，`eval_every=500`。
- 300k：只在 100k e2e 正收益后做；跑 12k-18k steps。
- ckpt 选择不只看 OOD0：同时看 OOD step1/2、public accuracy、D5/D7 accept、no-spec/spec 一致性。
- 接受门槛：相对当前 `v2mix_20k_s3500_ood757`，OOD0 至少不低于 0.7571，最好 +0.003；public `ori_accuracy` 不下降；`bench/mini_bench.sh` S1/S8/Smax 不回退。
- 最终必须跑：`eval/run_public_eval_full.py`、`bench/mini_bench.sh`、D5/D7 accept bucket 分析、no-spec vs spec 输出一致性。

**主要风险**
- 只扩大 Chinese R1 会提高离线 acc，但实测 chat/code/long accept 可能不涨。
- 原始 ShareGPT assistant 历史直接入 prompt 会制造 target/history mismatch；多轮最好先 target-regenerate history。
- 300k 最大风险是磁盘和 I/O，不是 prompt 数量。
- OOD64 太小，容易被选择性过拟合。
- topK=128 对长尾/高熵 token 可能不够，先记录 mass 再决定是否扩 K。
