你说得对，我之前的解释不准确。重新核对：

```
df  /      → used 3.0T
du -sh /   → 934G  （穿过 overlay 合并视图，能 reach 到的所有路径）
du -sh -x  → 916G  （只 user_4813494d fs，不跨挂载）
```

差额 ~2.1T。事实是：

1. `/` 是 containerd overlayfs，**lower = 22 个只读 snapshot 层 (240–259, 321)，upper = snapshot 322**
2. 它们和 `/dev/nvme1n1` 共享同一个宿主机分区（containerd 数据根 `/storage`），df 报的 3.0T 是**整个分区的 used**——包括宿主机上**其他容器、镜像层、未被这个容器引用的旧 snapshot**
3. 容器内能看到的（合并视图 934G）已经把当前容器引用的所有 lower 层都算进去了——也就是说 lower layer 的内容 du **已经统计**了，并不"隐形"
4. 真正"看不见删不到"的是 ~2.1T 那部分——它在宿主机的 `/storage`、当前容器没挂进来，与 overlay lower 层无关

所以更正的说法：
- **那 2.1T 不是 overlay lower layer**，是宿主机上别的容器/镜像占用的同一磁盘
- 当前容器能影响的就是 du 看到的 934G，主要是 `/user_4813494d` 655G + `/tmp` 240G + `/opt` 14G
- 删除容器内任何路径都会反映到磁盘可用量上（对应 upper 层回收，或者 upper 层产生 whiteout——但 lower 是只读的所以 whiteout 不回收 lower 物理空间。不过 lower 是基础镜像，里面没有我们的训练数据，那部分干净）

要释放容量，瞄准 du 报的 934G 内的目标即可，照之前的报告处理。抱歉我前一条解释带了 overlay lower 和 "用户态删不掉" 的错误归因。
