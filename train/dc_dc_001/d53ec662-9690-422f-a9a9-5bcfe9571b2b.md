## 代码里已看到的问题（摘要）

### 1. 双重 contiguous / 额外 layout 变换（stage1）

`infllmv2_attn_stage1` 先对 `q,k,v` 做 `maybe_contiguous`，再 reshape/transpose 后对 `q` 再次 `.contiguous()`；C++ 只要求最后一维连续（`stride(-1)==1`），与 Python 侧一致，但 **NSA 的 q 展开仍会强制至少一次大块拷贝**。

```548:560:/root/shared-nvme/openbmb/kernels/infllmv2_cuda_impl/infllm_v2/infllmv2_sparse_attention.py
    q, k, v = [maybe_contiguous(x) for x in (q, k, v)]
    ...
    q = q.reshape(total_q, nheads_k, nheads_per_group, head_dim)
    q = q.transpose(1, 2).reshape(total_q * nheads_per_group, nheads_k, head_dim).contiguous()
```

`max_pooling_1d_varlen` 又对 `input` 做 **整 tensor `contiguous()`**；若 stage1 输出已是连续布局则是 no-op，否则多一次读写过 HBM。

```83:92:/root/shared-nvme/openbmb/kernels/infllmv2_cuda_impl/infllm_v2/max_pooling_1d.py
    assert input.dtype == torch.float16 or input.dtype == torch.bfloat16
    ...
    input = input.contiguous()
    cu_seqlens_q = cu_seqlens_q.contiguous()
```

### 2. Host 同步（`.item()`）

`max_pooling_1d_varlen_v2` 在 assert 里用 `cu_seqlens_q[-1].item()`，**每次调用都会触发 D→H 同步**（若走 v2 路径会伤 Graph/低延迟 decode）。当前 SGLang 侧用的是 `max_pooling_1d_varlen`，但 v2 仍是扩展里已存在的坑。

```211:213:/root/shared-nvme/openbmb/kernels/infllmv2_cuda_impl/infllm_v2/max_pooling_1d.py
    assert cu_seqlens_q[-1].item() == total_q, f"total_q mismatch: {cu_seqlens_q[-1].item()} vs {total_q}"
```

（训练/自定义算子 backward 里还有 `torch.cuda.synchronize()`，对 **推理 ROI 很低**，见 `infllmv2_sparse_attention.py` 346–348 行附近。）

### 3. 次优 launch：`max_pooling_1d_varlen_kernel` 里按 batch 线性扫

每个 `(global_q, head)` block 用 **for 循环扫整个 `batch_size`** 找所属 batch，复杂度 **O(batch_size × total_q × heads)** 的额外工作，prefill 批较大时浪费明显；更合理的是 **二分** 或 **预计算每条 query 的 batch_idx**（一次小 kernel 或 CPU 侧已知 batch 划分时直接传入）。

```43:54:/root/shared-nvme/openbmb/kernels/infllmv2_cuda_impl/csrc/max_pooling_1d.cuh
    // Binary search to find batch index
    for (int b = 0; b < batch_size; b++) {
        q_start = cu_seqlens_q[b];
        q_end = cu_seqlens_q[b + 1];
        ...
        if (bidq_global >= q_start && bidq_global < q_end) {
            batch_idx = b;
            break;
        }
    }
```

（注释写 “Binary search” 实际是线性扫描。）

### 4. 文档 / 注释 TODO

- `entry.cu`：`max_pooling_1d_varlen` 旁 **按真实 max 序列长度动态设置** 的 TODO（与 Graph/显存占用相关）。
- `max_pooling_1d.py`：**stride 与 HF 参数是否一致**、**output 用 `zeros_` 复用**、**max_seqlen_k 硬编码 2048（Graph）** 等 TODO/警告注释。
- `infllmv2_sparse_attention.py`：stage1 返回路径里 **causal 首 block -inf** 的 TODO（已注释）。

### 5. Stage1（Flash）路径：大中间张量

`mha_varlen_fwd_stage1` 在 `return_softmax` 时分配 `p`，K 维按 `seqlen_k_rounded` 对齐，Q 维有 `/16` 的 packed 布局，整体仍是 **整段 softmax 概率平面**，后面 pooling 只消费其中的窗口 max —— 带宽与显存占用对 **长上下文 prefill** 很敏感。

```939:941:/root/shared-nvme/openbmb/kernels/infllmv2_cuda_impl/csrc/flash_attn/flash_api.cpp
    if (return_softmax) {
        // Return tensor with shape (num_heads_k, total_q / 16, seqlen_k_rounded)
        p = torch::full({ num_heads_k, total_q / 16, seqlen_k_rounded }, 0, opts);
```

### 6. Stage1 → Pooling 融合 **是否可行**

- **可行方向**：在逻辑上 pooling 只沿 K 做 **stride 窗口 max**，且与 stage1 的 softmax 输出同一条 “score 线”；若在 Flash/stage1 内核尾部或 **紧接的轻量 kernel** 里按 block 直接写出 `out_len` 维的 pooled 特征（或直接与 topk 前处理对接），可避免 **整表 `p` 写 HBM 再读回**。
- **代价**：要摸 Flash 里 `return_softmax` 的写入布局与 NSA 的 `m_block_dim=16` 等约定，工程量大，但 **长 seq prefill 上 ROI 最高**。

## 按 ROI 排序的 3–5 条 actionable（MiniCPM decode + prefill）

1. **最高 ROI（prefill 长上下文）**：**把 stage1 的 full softmax 平面与 max-pool 沿 K 融合或缩窄输出**（例如内核内或紧随其后的 kernel 直接产出 `block_score`/`out_len`，避免 `(nheads_k, total_q, seqlen_k_rounded)` 级 BF16 张量整表读写）。对 `dense_len` 超阈值后的稀疏路径，这是带宽与显存的主矛盾。

2. **高 ROI（多 batch prefill）**：**重写 `max_pooling_1d_varlen_kernel` 的 batch 定位**：真正二分查找 `cu_seqlens_q`，或增加 `query_batch_id[total_q]`（device 上预填），去掉每线程块 O(batch) 循环。

3. **中高 ROI（显存 + 常量开销）**：**按真实 `max_context_len` / 当前 `max_seqlen_k` 动态定 `out_len`、`p`/`score` 的 K 维 padding**（落实 `entry.cu` / Python 里关于 Graph 与硬编码的 TODO），减少 `torch.full`/`torch.zeros` 体积与无效计算；注意与平台 CUDA Graph 约束一起设计。

4. **中等 ROI（链路上小头）**：**减少 contiguous 往返**：保证 stage1 输出 layout 与 pooling 输入一致（或改 pooling 接受 `stride(-1)==1` 的约束与指针算术），避免 score 上多一次隐式 copy；同时审视 `infllmv2_attn_stage1` 里 q 的 reshape 能否与上游布局对齐以减少 `.contiguous()`。

5. **decode 侧（已有 split_stage1 时次要但仍可做）**：在 **小块 `block_score` 上把 pooling + `topk` 合成单个小 kernel**（或专用 warp/warp-level topk），降低 launch 与 PyTorch `topk` 调度开销；decode 主路径若已走 `split_stage1` 的 matmul+softmax，这一项收益小于 prefill 的融合与 pooling 修复。

---

**说明**：`csrc/entry.cu` 里的 `topk` / `topk_to_uint64` 主要服务 **带 blockmask 的 varlen_fwd**；MiniCPM `compressed_attention` 里 topk 是 **`block_score.topk`（PyTorch）**，与 C 扩展 `topk` 不是同一条调用链，除非你们在别处改用 InfLLM 的 topk。
