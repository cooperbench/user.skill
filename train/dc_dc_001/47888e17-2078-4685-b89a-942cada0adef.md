45	### plan() 内部 nsys 抓取
46	
47	用 `nsys profile -t cuda,nvtx --capture-range=cudaProfilerApi` + `SGLANG_MINICPM_CUDA_PROFILER=1` + `SGLANG_MINICPM_NVTX=1`（`MiniCPMModel.forward` 加 `cudaProfilerStart/Stop` 控制窗口）：

53	### 根因
54	
55	1. **plan() baseline = 纯 CPU 时间**：不是 GPU/driver 慢，而是 flashinfer `_cached_module.plan(...)` C++ 函数在做 work-split 决策的 CPU 计算。

plan cache 的实现位于 `demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_attention_kernels.py:275-600`，它是 `FlashInferKernel` 这个类的成员状态（`_plan_cache_key` / `_plan_last_layer_id` / `_plan_cached_indptr_bytes` / `_plan_cached_lpl_bytes`）。

调用链只有一条：

- `attention_registry.py:190` `minicpm_flashinfer` → `MiniCPMSparseBackend`
- `MiniCPMSparseBackend` 内部构造 `FlashInferKernel` → 才会进到带 plan cache 的 `forward`

而 `attention_registry.py:23` 里的普通 `flashinfer` 走的是 `FlashInferAttnBackend`（`flashinfer_backend.py`），跟 `FlashInferKernel` 完全是两套代码，不经过 `_plan_cache_*` 分支，所以 plan 复用完全失效。

另外更根本的问题：MiniCPM 的 8 个 standard layer 依赖 `minicpm_backend` 里的 InfLLM-v2 稀疏链路（compress_k → stage1 block_score → stage2 topk → sparse FA），普通 `flashinfer` 后端不认识这套稀疏元数据，切过去等于把稀疏一起丢了，plan cache 本身要优化的 8× `begin_forward` 场景也不会出现。

## 评估结果：`--attention-backend flashinfer` 上几乎没落地空间

### 关键差异：stock flashinfer 里 `plan()` 只调用 1 次/forward

读 `flashinfer_backend.py`：

- `FlashInferAttnBackend.init_forward_metadata()`（line 420）每个 forward batch 入口调 **一次** `indices_updater_prefill.update(...)`（line 487）或 `indices_updater_decode.update(...)`（line 422）
- `update()` 内部最终落到 `call_begin_forward()`（line 1339），对 `wrapper_ragged.begin_forward` + `wrapper_paged.begin_forward` 各调一次（line 1393 / 1427）
- 之后模型 32 层 attention 每层只在 `forward` 阶段走 `wrapper.run(q, k, v)`，**不再 call plan**

这跟 `minicpm_backend` 的根本区别：MiniCPM 稀疏路径里每个 standard layer 的 `kv_indices`（topk 选出来的 page 列表）都不一样，必须每层 `begin_forward`；stock flashinfer 是稠密 attention，32 层共享同一份 paged KV，所以一次 plan 就够了。

### 我们 MiniCPM plan cache 的两条优化映射过去：

| 优化 | 对应 stock flashinfer | 可行性 |
|---|---|---|
| §3 layer 间复用（commit 259b82d） | 不存在 8× 放大 | **已经是 1× 了，没的省** |
| §4 chunk 间复用（commit e99478e） | chunked prefill 每 chunk 仍跑一次 `init_forward_metadata` → `begin_forward` | **理论可做，但 ROI 存疑** |

### chunk-间复用为什么 ROI 存疑

1. **CPU 23ms baseline 不具普适性**：我们的 23ms 来自 flashinfer 稀疏 topk 的 work-split；stock 稠密 paged 的 plan 内部计算量完全不是一回事，需要先 profile 才能知道它在 prefill wall time 里占多少。
2. **byte-equal 条件更严**：chunked prefill 下 `kv_indptr[-1]` 每 chunk 递增（新 token append 进 KV cache），严格 byte-compare 不会命中；得退化成"前缀相等 + 总 token 数 ≤ 之前"这种软匹配，前提是 flashinfer dense plan 的 work split 只依赖 `max_kv_len / bs / heads / dtypes`，这点要翻 flashinfer C++ 源码确认。
3. **已有 fast path**：`flashinfer_backend.py:1111-1138` 里 stock SGLang 已经接了个 `fast_decode_plan` 跳 plan 的机制（`partial` 替换 `wrapper.begin_forward`），说明社区早发现了 decode 侧的 plan 开销，自己改之前先看这条现有路径能不能扩到 prefill。

### 更根本的实际问题

MiniCPM-SALA 必须走 `minicpm_flashinfer` 才能撑 128K（稀疏链路里 compress_k → stage1 → stage2 topk 是全局稠密 prefill 绝对负担不起的 48K+ 上下文）。`--attention-backend flashinfer` 在当前模型上等于**扔掉稀疏**，在 SOAR 场景里根本跑不起来。

所以我的建议：

- 如果目的是"MiniCPM 想切到 stock flashinfer" → 方案不成立，切过去稀疏就没了，prefill 直接炸
- 如果目的是"把这套 plan cache 回馈给上游/其它模型" → 先在 stock flashinfer 上跑一次 `SGLANG_MINICPM_PROFILE` 同类插桩，看 `begin_forward` 占 prefill wall 比例再说；**<5% 就别做**

要我在 stock flashinfer 的 `call_begin_forward` 前后加一对 `torch.cuda.synchronize + perf_counter` 插桩，跑一把 128K chunked prefill 拿到实测占比吗？
