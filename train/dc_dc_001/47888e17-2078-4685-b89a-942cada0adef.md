## 评估结果：`--attention-backend flashinfer` 上几乎没落地空间 ### 关键差异：stock flashinfer 里 `plan()` 只调用 1 次/forward 读 `flashinfer_backend.py`： - `FlashInferAttnBackend.init_forward_metadata()`（line 420）每个 forward batch 入口调 **一次** `indices_updater_prefill.update(...)`（line 487）或 `indices_updater_decode.update(...)`（line 422） - `update()` 内部最终落到 `call_begin_forward()`（line 1339），对 `wrapper_ragged.begin_forward` + `wrapper_paged.begin_forward` 各调一次（line 1393 / 1427） - 之后模型 32 层 attention 每层只在 `forward` 阶段走 `wrapper.run(q, k, v)`，**不再 call plan** 这跟 `minicpm_backend` 的根本区别：MiniCPM 稀疏路径里每个 standard layer 的 `kv_indices`（topk 选出来的 page 列表）都不一样，必须每层 `begin_forward`；stock flashinfer 是稠密 attention，32 层共享同一份 paged KV，所以一次 plan 就够了。 ### 我们 MiniCPM plan cache 的两条优化映射过去： | 优化 | 对应 stock flashinfer | 可行性 | |---|---|---| | §3 layer 间复用（commit 259b82d） | 不存在 8× 放大 | **已经是 1× 了，没的省** | | §4 chunk 间复用（commit e99478e） | chunked prefill 每 chunk 仍跑一次 `init_forward_metadata` → `begin_forward` | **理论可做，但 ROI 存疑** | ### chunk-间复用为什么 ROI 存疑 1. **CPU 23ms baseline 不具普适性**：我们的 23ms 来自 flashinfer 稀疏 topk 的 work-split；stock 稠密 paged 的 plan 内部计算量完全不是一回事，需要先 profile 才能知道它在 prefill wall time 里占多少。 2. **byte-equal 条件更严**：chunked prefill 下 `kv_indptr[-1]` 每 chunk 递增（新 token append 进 KV cache），严格 byte-compare 不会命中；得退化成"前缀相等 + 总 token 数 ≤ 之前"这种软匹配，前提是 flashinfer dense plan 的 work split 只依赖 `max_kv_len / bs / heads / dtypes`，这点要翻 flashinfer C++ 源码确认。 3. **已有 fast path**：`flashinfer_backend.py:1111-1138` 里 stock SGLang 已经接了个 `fast_decode_plan` 跳 plan 的机制（`partial` 替换 `wrapper.begin_forward`），说明社区早发现了 decode 侧的 plan 开销，自己改之前先看这条现有路径能不能扩到 prefill。 ### 更根本的实际问题 MiniCPM-SALA 必须走 `minicpm_flashinfer` 才能撑 128K（稀疏链路里 compress_k → stage1 → stage2 topk 是全局稠密 prefill 绝对负担不起的 48K+ 上下文）。`--attention-backend flashinfer` 在当前模型上等于**扔掉稀疏**，在 SOAR 场景里根本跑不起来。 所以我的建议： -
