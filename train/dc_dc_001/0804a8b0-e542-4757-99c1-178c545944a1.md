"叠加比乘法多赚" 方向对，幅度不知道** Draft 步更 launch-bound、sync 密度更高——这两个定性论点站得住，我上条列的代码证据（`TASK_FIND_NGRAM`、`TASK_TARGET_VERIFY_GREEDY`、`spec_decode_class`）也是真的。但"多赚多少"我没法告诉你，因为这恰好就是 baseline 用不用 CUDA Graph 的强函数： - Eager baseline：draft 步确实是 launch 重灾区，叠加后 MPK 多赚明显 - CUDA Graph baseline + 每种 K 一份 graph：MPK 还是赢，但赢在"不用多份 graph 占显存 / 不用 re-capture"，不在"省 launch" - CUDA Graph Conditional（CUDA 12.4+，有 if/else）：差距进一步缩小 --- ## 站得住的部分 以下是不依赖我编的数字、靠代码和物理论证都能撑住的： 1. **方向上两者正交、能相乘**：spec decode 砍"每 token 几次 forward"，MPK 砍"每次 forward 的固定开销"，确实不在同一个乘法因子上。 2. **Spec decode 让 MPK 的 host-sync 消除更重要**：spec decode 一个 iteration 的 sync 点数量本来就比普通 decode 多 5~7 倍，每次 sync 开销几十 μs 到几百 μs（取决于是否涉及 cudaMemcpyAsync + stream sync）。这个省不掉，CUDA Graph 也救不了（Graph 能消 launch 不能消 D2H memcpy）。 3. **动态接受长度 + CUDA Graph 确实互相打架**：要么多份 graph 要么退回 eager。MPK 的 task graph 把 qo_indptr 当 runtime meta tensor，天然不受影响。这点是真优势。 4. **MPK 有一等公民的 spec decode 原语**：代码里那些 `TASK_FIND_NGRAM_*`、`TASK_TARGET_VERIFY_GREEDY`、MTP decode kernel 是实锤，不是我编的。 5. **sm_120 跑 MPK 会 fallback 到 Ampere path**：`tasks/blackwell/` 全部 sm_100a 门槛、Hopper 路径走 WGMMA 要 sm_90a，sm_120 两头都不靠。这个结论靠代码证据，稳。 --- ## 你真要知道收益几何，只有测 抽象讨论到这里就是天花板了。具体数字只能测。如果你真要做决策，最小代价的 A/B： 1. **先测 baseline**：你现有 CUTLASS prefill + Marlin decode 在 sm_120 上，**开 CUDA Graph** 和**不开**的 decode ITL 分别是多少。这两个数的差距决定了 MPK 还有多少可剃。 2. **纯 spec decode POC**：上一个 prompt-lookup 或 Eagle-2，用**你现有 stack**，不动 MPK，测平均接受长度 K 和实际 ITL 改善。这个数定 spec decode 这条维度的真实收益。 3. **MPK POC**：只拿 decode 部分（不动 prefill），先跑通 Ampere fallback，测 decode ITL。这个数定 MPK 这条维度的真实收益。 4. **叠加**：两个都上再测一次。叠加后的数字减去前两者，剩下的差就是"叠加带来的额外收益"。 这四次测出来的数比我任何理论分析都有用。 --- ## 一句话 上一条里**方向和机制是对的，数字是示意**。方向对你决定"要不要投入"够用，数字要投入之前必须自己测一遍，尤其要搞清楚你 baseline 是不是已经在吃 CUDA Graph 的红利——如果是，MPK 能给你的剃刀比我画的窄。
