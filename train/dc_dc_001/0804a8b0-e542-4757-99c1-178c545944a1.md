46	## How MPK Works
47	Once you've imported the Mirage package, you can instantiate a persistent kernel using the following API:
48	```python
49	import mirage as mi
50	mpk = mi.PersistentKernel(
51	    world_size=world_size,
52	    mpi_rank=rank,
53	    num_workers=96,
54	    num_local_schedulers=48,
55	    num_remote_schedulers=0,
56	    meta_tensors=[step, tokens],
57	    profiler_tensor=profiler_tensor,
58	)
59	```
60	* `world_size` and `mpi_rank`: number of GPUs and current GPU rank.
61	* `num_workers`, `num_local_schedulers`, `num_remote_schedulers`: the number of workers, local schedulers, and remote schedulers. They must match the number of physical SMs (`num_workers` + (`num_local_schedulers` + `num_remote_schedulers`) / 4).
62	* The megakernel currently requires two meta tensors: `step` is an array of integer tracking the current decoding step, and is incremented by MPK after each decoding iteration; `tokens` is a tensor of shape [`num_requests`, `seq_length`] storing prompts and MPK generated tokens.
63	
64	To attach an existing `PyTorch.Tensor`:
65	```python
66	x = mpk.attach_input(torch_tensor=torch_tensor, name="torch_tensor_name")
67	```
68	* `name` is used by MPK to refer to the tensor in the generated megakernel in CUDA.
69	
70	To allocate a new tensor:
71	```python
72	y = mpk.new_tensor(
73	    dims=(batch_size, hidden_size),
74	    dtype=mi.bfloat16,
75	    name="embed_out",
76	    io_category="cuda_tensor",
77	)
78	```
79	* `dims` and `dtype` specify the dimensions and data type of the tensor. 
80	* `name` is used by MPK to refer to this new tensor in the megakernel. 
81	* `io_category` indicates how the tensor is allocated and must be `cuda_tensor` or `nvshmem_tensor` (the latter is required for remote GPU access, e.g., during all-reduce).
82	
83	### Defining the Computation Graph
84	You can compose the LLM’s computation graph by chaining fused operations. For example: `rmsnorm_linear_layer` fuses an RMSNorm layer and a Linear layer in the megakernel.
85	```python
86	mpk.rmsnorm_linear_layer(
87	    input=x,
88	    weight_norm=w_norm,
89	    weight_linear=w_qkv,
90	    output=attn_in,
91	    grid_dim=(96, 1, 1),
92	    block_dim=(128, 1, 1),
93	)
94	```
95	* `weight_norm` and `weight_linear` are the weight tensors for RMSNorm and Linear.
96	* `input` and `output` are the input and output tensors of this fused layer. 
97	* `grid_dim` and `block_dim` specifies the number of thread blocks (i.e., number of tasks in the task graph) and number of thread within each thread block. To minimize latency, it is suggested that the total number of thread blocks is a multiplier of the number of workers to avoid outliers.
98	
99	### Compilation & Execution
100	Once the computation graph is defined, compile it with:
101	```python
102	mpk.compile()
103	```
104	Then, run the optimized megakernel as:
105	```python
106	mpk()
107	```

46	## How MPK Works
47	Once you've imported the Mirage package, you can instantiate a persistent kernel using the following API:
48	```python
49	import mirage as mi
50	mpk = mi.PersistentKernel(
51	    world_size=world_size,
52	    mpi_rank=rank,
53	    num_workers=96,
54	    num_local_schedulers=48,
55	    num_remote_schedulers=0,
56	    meta_tensors=[step, tokens],
57	    profiler_tensor=profiler_tensor,
58	)
59	```
60	* `world_size` and `mpi_rank`: number of GPUs and current GPU rank.
61	* `num_workers`, `num_local_schedulers`, `num_remote_schedulers`: the number of workers, local schedulers, and remote schedulers. They must match the number of physical SMs (`num_workers` + (`num_local_schedulers` + `num_remote_schedulers`) / 4).
62	* The megakernel currently requires two meta tensors: `step` is an array of integer tracking the current decoding step, and is incremented by MPK after each decoding iteration; `tokens` is a tensor of shape [`num_requests`, `seq_length`] storing prompts and MPK generated tokens.
63	
64	To attach an existing `PyTorch.Tensor`:
65	```python
66	x = mpk.attach_input(torch_tensor=torch_tensor, name="torch_tensor_name")
67	```
68	* `name` is used by MPK to refer to the tensor in the generated megakernel in CUDA.
69	
70	To allocate a new tensor:
71	```python
72	y = mpk.new_tensor(
73	    dims=(batch_size, hidden_size),
74	    dtype=mi.bfloat16,
75	    name="embed_out",
76	    io_category="cuda_tensor",
77	)
78	```
79	* `dims` and `dtype` specify the dimensions and data type of the tensor. 
80	* `name` is used by MPK to refer to this new tensor in the megakernel. 
81	* `io_category` indicates how the tensor is allocated and must be `cuda_tensor` or `nvshmem_tensor` (the latter is required for remote GPU access, e.g., during all-reduce).

83	### Defining the Computation Graph
84	You can compose the LLM’s computation graph by chaining fused operations. For example: `rmsnorm_linear_layer` fuses an RMSNorm layer and a Linear layer in the megakernel.
85	```python
86	mpk.rmsnorm_linear_layer(
87	    input=x,
88	    weight_norm=w_norm,
89	    weight_linear=w_qkv,
90	    output=attn_in,
91	    grid_dim=(96, 1, 1),
92	    block_dim=(128, 1, 1),
93	)
94	```
95	* `weight_norm` and `weight_linear` are the weight tensors for RMSNorm and Linear.
96	* `input` and `output` are the input and output tensors of this fused layer. 
97	* `grid_dim` and `block_dim` specifies the number of thread blocks (i.e., number of tasks in the task graph) and number of thread within each thread block. To minimize latency, it is suggested that the total number of thread blocks is a multiplier of the number of workers to avoid outliers.

85	## Layer API: TBGraph Partition Scheme
86	
87	Each layer method (e.g., `rmsnorm_layer`, `linear_layer`, `moe_w13_linear_layer`) builds a **TBGraph** that describes how the global tensors are sliced into per-task tiles. This section explains every parameter.
88	
89	### `CyTBGraph` constructor
90	
91	```python
92	tb_graph = TBGraph(CyTBGraph(grid_dim, block_dim, forloop_range, reduction_dimx))
93	```
94	
95	| Parameter | Meaning |
96	|---|---|
97	| `grid_dim` | `(x, y, z)` — number of task instances in each dimension. Total tasks = `x * y * z`. |
98	| `block_dim` | `(threads, 1, 1)` — threads per task. Must be `(128,1,1)` Ampere, `(256,1,1)` Hopper/Blackwell. |
99	| `forloop_range` | Number of forloop iterations (always **1** in MPK — see note below). |
100	| `reduction_dimx` | Tile size for the reduction dimension (always **64** in MPK). |
101	
102	### `tb_graph.new_input()` — registering a tensor
103	
104	```python
105	tb_graph.new_input(dtensor, input_map, forloop_dim, store_in_dmem)
106	```
107	
108	Called for **every** tensor the task touches — both inputs and outputs. The first `num_inputs` calls register inputs; the remaining register outputs. This ordering must match `num_inputs`/`num_outputs` in `graph.cc`'s `task_config` tuple.
109	
110	#### `input_map`: the partition tuple
111	
112	A 3-element tuple `(mx, my, mz)` that maps **grid dimensions → tensor dimensions**:
113	
114	| `input_map.x` value | Meaning |
115	|---|---|
116	| `-1` | `grid_dim.x` does **not** partition this tensor. Every task sees the full extent of every dimension. |
117	| `0` | `grid_dim.x` partitions **tensor dimension 0**. Task at grid position `gx` sees the slice `[gx * dim[0]/grid_x : (gx+1) * dim[0]/grid_x]` along dim 0. |
118	| `1` | `grid_dim.x` partitions **tensor dimension 1**. Same slicing logic on dim 1. |
119	| `2` | `grid_dim.x` partitions **tensor dimension 2**. |
120	
121	`input_map.y` and `input_map.z` work identically for `grid_dim.y` and `grid_dim.z`.
122	
123	**In short:** the value tells you *which tensor dimension* that grid axis splits. `-1` means "don't split by this grid axis."
124	
125	#### `forloop_dim` (vestigial in MPK)
126	
127	In the Mirage superoptimizer, `forloop_dim` and `forloop_range` together control tiled reduction loops within a TBGraph. However, **in MPK `forloop_range` is always 1**, which makes `forloop_dim` a no-op — the dimension division (`dim / 1`) and stride multiplier (`* 1`) have no effect regardless of what value you pass.
128	
129	MPK task kernels handle their own internal tiling and reduction directly in CUDA (e.g., looping over the K dimension in a matmul). The TBGraph forloop mechanism is not used. You'll see various `forloop_dim` values in existing layer methods (e.g., `1`, `2`, `-1`), but they're all equivalent when `forloop_range=1`. By convention, existing code sets `forloop_dim` to the "reduction dimension" of the operation, but this is cosmetic.
130	
131	#### `store_in_dmem`
132	
133	- `True` — the per-task tensor slice lives in **device (global) memory**. Should be set to **True** for all MPK tensors.
134	
135	### Annotated example: `moe_w13_linear_layer`
136	
137	```python
138	def moe_w13_linear_layer(self, input, weight, moe_routing_indices,
139	                         moe_mask, output, grid_dim, block_dim):

141	    # input:              (batch_size, hidden_size)                        2D bf16
142	    # weight:             (num_experts, 2*intermediate_size, hidden_size)  3D bf16
143	    # moe_routing_indices:(num_experts, batch_size)                        2D int32
144	    # moe_mask:           (num_experts + 1,)                               1D int32
145	    # output:             (batch_size, num_experts_per_tok, 2*inter_size)  3D bf16
146	
147	    tb_graph = TBGraph(CyTBGraph(grid_dim, block_dim, 1, 64))
148	
149	    #                       tensor,              input_map,    forloop_dim*, store_in_dmem
150	    #  (* forloop_dim is vestigial in MPK — has no effect when forloop_range=1)
151	
152	    tb_graph.new_input(input,               (-1, -1, -1),  1,           True)
153	    #  → No partition on any grid axis. Every task sees full (batch, hidden).
154

156	    #  → grid_dim.y partitions dim 1 (the 2*intermediate_size axis).
157	    #    Each task handles 2*inter_size / grid_dim.y rows of the weight matrix.

173	### How partitioning connects to task pointers
174	
175	At runtime, the partition tuple is resolved during task graph generation (`src/threadblock/graph.cc`). For each task instance (one grid coordinate), the code generator computes a **byte offset** from the tensor's base pointer:
176	
177	```
178	per_task_ptr = base_ptr
179	             + blockIdx.x * stride_for(input_map.x)
180	             + blockIdx.y * stride_for(input_map.y)
181	             + blockIdx.z * stride_for(input_map.z)
182	```
183	
184	These offsets are baked into the `TaskDesc` at init time (via JSON → `FullTaskDesc` → `TaskDesc`). The task kernel receives pre-offset pointers in `task_desc->input_ptrs[i]` and `task_desc->output_ptrs[i]` — this is why tasks are **blockIdx-agnostic**.

234	## Phase 4: Runtime Initialization
235	
236	### Key file: `include/mirage/persistent_kernel/persistent_kernel.cuh`
237	
238	**`init_persistent_kernel()`** sets up the full runtime state:
239	
240	1. **Meta-tensor mapping** — stores 10 meta-tensor pointers in `global_runtime_config` (step, tokens, input_tokens, output_tokens, num_new_tokens, prompt_lengths, qo_indptr, paged_kv_indptr, paged_kv_indices, paged_kv_last_page_len).
241	
242	2. **NVSHMEM init** (if multi-GPU) — calls `nvshmemx_init_attr()`, creates NVSHMEM teams for cross-GPU communication.
243	
244	3. **Call generated `_init_persistent_kernel()`** — this loads the JSON task graph via `construct_task_graph()`, allocates GPU memory for intermediate tensors, and populates the `all_tasks`, `all_events`, `first_tasks` vectors.
245	
246	4. **Allocate runtime queues on GPU**:
247	   - `worker_queues[2 * num_workers]` — per-worker task queues (local + remote). Each is a circular buffer of `TaskId` with length `per_worker_queue_len` (1024).
248	   - `sched_queues[num_schedulers + 1]` — per-scheduler event queues + one global broadcast queue. Circular buffers of `EventId`.
249	   - `worker_queue_last_ready_task_id[2 * num_workers]` — atomic counters for queue tail.
250	   - `sched_queue_last_ready_event_id[num_schedulers + 1]` — atomic counters for event queue tail.
251	   - `all_event_counters[num_events]` — atomic counters tracking how many times each event has been triggered.
252	   - `all_event_num_triggers[num_events]` — how many triggers each event needs before it's considered "ready".
253	
254	5. **Copy task/event data to GPU** — `all_tasks`, `all_events`, `first_tasks` are copied to device memory.
255	
256	6. **Set kernel attributes** — sets `cudaFuncAttributeMaxDynamicSharedMemorySize` for worker and scheduler kernels.
257	
258	7. **Create streams and events** — separate CUDA streams for workers and schedulers (split mode), plus synchronization events.
259	
260	8. **Call `init_request_resources()`** — launches `init_kernel` which initializes per-request state (step counters, page queues for MODE_OFFLINE/MODE_ONLINE).

264	## Phase 5: Runtime Execution
265	
266	### Key file: `include/mirage/persistent_kernel/persistent_kernel.cuh`
267	
268	### Launch: `launch_persistent_kernel(stream)`
269	
270	1. **`prepare_kernel<<<>>>`** — resets all queue pointers and event counters to zero. Seeds the initial `EVENT_END_OF_TASK_GRAPH` event to scheduler[0], which kicks off the first iteration.
271	
272	2. **Kernel launch** (two modes):
273	   - **Split mode** (`split_worker_scheduler = true`): launches `worker_kernel` and `scheduler_kernel` as separate kernels on separate streams. Workers get `WORKER_NUM_THREADS` threads per block; schedulers get 32 threads (1 warp). Synchronized via CUDA events. This is now the default mode.
274	   - **Unified mode**: launches a single `persistent_kernel` where blocks `[0, num_workers)` run `execute_worker()` and remaining blocks run `execute_scheduler()`.
275	
276	### Worker loop: `execute_worker()`
277	
278	Each worker thread block runs an infinite loop:
279	
280	1. **Fetch tasks** — polls `worker_queue_last_ready_task_id[worker_id]` using `ld_acquire` until new tasks appear. Loads a batch of `TaskDesc` from the queue into shared memory (using `cp.async` for efficiency).
281	
282	2. **Wait for dependencies** — if `task_desc->dependent_event != EVENT_INVALID_ID`, polls the event counter `all_event_counters[event_index]` until it reaches `num_triggers * iteration_num`. For NVSHMEM events, uses `nvshmem_signal_wait_until`.
283	
284	3. **Execute task** — calls `_execute_task(task_desc, runtime_config)` which dispatches to the generated kernel code based on `(task_type, variant_id)`.
285	
286	4. **Signal completion** — atomically increments `all_event_counters[trigger_event_index]`. If this was the final trigger for that event, enqueues the event to the appropriate scheduler's queue.
287	
288	5. **Terminate** — when a `TASK_TERMINATE` task is received, the worker returns.
289	
290	### Scheduler loop: `execute_scheduler()`
291	
292	Each scheduler runs on a single warp (32 threads, only thread 0 active). Up to 4 schedulers can share one SM (4 warps):
293	
294	1. **Fetch events** — polls `sched_queue_last_ready_event_id[sched_id]` for new events.
295	
296	2. **Process event by type**:
297	   - `EVENT_LAUNCH_TASKS` / `EVENT_LAUNCH_MASSIVE_TASKS`: enqueue the task range `[first_task_id, last_task_id)` to worker queues in round-robin fashion.
298	   - `EVENT_LAUNCH_DEPENDENT_TASKS`: similar but increments `iteration_num` (for cross-iteration dependencies).
299	   - `EVENT_END_OF_TASK_GRAPH`: calls `prepare_next_batch()` to set up the next inference iteration (finalize previous batch, allocate KV cache pages, load new tokens). If `prepare_next_batch` returns false (no more work), calls `terminate_schedulers()`.
300	   - Termination event: enqueues `TASK_TERMINATE` to all workers and returns.
301	
302	3. **Task assignment** — each scheduler owns a range of workers (`my_first_worker` to `my_last_worker`). It round-robins task assignments within this range, using local counters to track queue positions.
303	
304	### Serving modes
305	
306	`prepare_next_batch()` (defined per mode via `#ifdef`):
307	- **MODE_OFFLINE**: processes all requests in a fixed batch. Finishes previous tokens, allocates KV cache pages, sets up input_tokens for next step.
308	- **MODE_ONLINE**: supports dynamic request arrival. Checks for new requests via `next_request_id`.
309	- **MODE_ONLINE_NOTOKEN**: online mode without explicit token tracking.

314	
315	The `task_graph.json` file is the key intermediate artifact between code generation and runtime. Generated by `print_task_graph()` in `runtime.cc`, loaded by `construct_task_graph()` at init time.

328	          "offset": 0,                // byte offset from base
329	          "dims": [128, 4096],

252	### block_dim Must Match WORKER_NUM_THREADS
253	
254	```
255	Ampere (SM80/86/89):   block_dim = (128, 1, 1)

258	```

260	Defined in `include/mirage/persistent_kernel/tasks/common/worker_config.h`. 262	### TBGraph Operator Order
263	
264	`bgraph.operators` is ordered exactly as `tb_graph.new_input()` was called. The first `num_inputs` entries are inputs; the remaining `num_outputs` are outputs. The split in `register_my_op_task` must match this exactly.

267	
268	`grid_dim.x * grid_dim.y * grid_dim.z` = total number of task instances. Each becomes one thread block assigned to one worker SM. 271	
272	`register_task_variant()` deduplicates by the generated code string. Two calls with the same template parameters produce the same code string and share a `variant_id`. You don't need to manage this manually.

52	## API Reference
53	
54	### `PersistentKernel.get_default_init_parameters()` (classmethod)
55	
56	Returns a dict with safe defaults for test mode. You **must** set `params["test_mode"] = True` — it is not in the defaults.
57	
58	Commonly overridden keys:
59	
60	| Key | Default | When to override |
61	|---|---|---|
62	| `test_mode` | (not present) | **Always** set to `True` |
63	| `num_workers` | 1 | Set from `mirage.get_configurations_from_gpu(0)` |
64	| `num_local_schedulers` | 4 | Set from `mirage.get_configurations_from_gpu(0)` |
65	| `max_num_batched_tokens` | 1 | Set to your test's batch size if the task kernel uses this compile-time constant |
66	| `max_num_batched_requests` | 1 | Same as above |
67	| `use_cutlass_kernel` | False | Set `True` if your layer uses CUTLASS-based kernels |
68	| `meta_tensors` | `{}` | Some layers need stubs (e.g., `qo_indptr_buffer`) — see multi-layer example |
69	
70	### `mirage.get_configurations_from_gpu(rank)`
71	
72	Returns `(num_workers, num_schedulers)` tuned for the GPU at the given rank. Always use this rather than hardcoding — the values depend on SM count and architecture.
73	
74	### `pk.attach_input(tensor, name)`
75	
76	Registers a PyTorch CUDA tensor with the computation graph. Returns a `DTensor` for use in layer calls.
77	
78	- Call for **every** tensor — inputs, weights, AND outputs.
79	- Output tensors are modified **in-place** when the kernel runs.
80	- Tensor must be **contiguous** (row-major / C-order).
81	- Name must be **unique** across all attached tensors.
82	
83	### `pk.compile(output_dir=None)`
84	
85	Generates CUDA code, compiles with nvcc, loads the resulting `.so` module.
86	
87	- **Set `output_dir`** to save `test_rank0.cu` and `task_graph_rank0.json` — essential for debugging compilation errors or incorrect results.
88	- Compilation can be slow (1–10+ minutes) depending on which task kernels are instantiated.
89	
90	### `pk.run_test_mode()`
91	
92	Launches the compiled task graph **once** on the current CUDA stream.
93	
94	- Only available when `test_mode=True`.
95	- Must be called **after** `compile()`.
96	- **Does not synchronize** — call `torch.cuda.synchronize()` afterward before reading output tensors.
97	
98	### `pk.finalize()`
99	
100	Frees GPU resources (queues, events, task/event storage). Call when done.

102	## Multi-Layer Pipeline Example
103	
104	`tests/runtime_python/test_mode/test_qwen3_mlp_testmode.py` demonstrates chaining multiple layers:
105	
106	```python
107	# Gate+Up linear → SiLU-Mul → Down+Residual  (Qwen3 dense MLP)
108	
109	# Attach weights separately, then shuffle for interleaved gate/up layout
110	w_gate_dt = pk.attach_input(w_gate, name="w_gate")
111	w_up_dt   = pk.attach_input(w_up, name="w_up")
112	w_gatedup_dt = pk.shuffle_tensors(
113	    inputs=[w_gate_dt, w_up_dt],
114	    shuffled_dim=0,
115	    num_groups=num_tasks // 2,
116	    name="w_gatedup",
117	)
118	
119	# Layer 1: Gate+Up fused linear
120	pk.linear_layer(input=input_dt, weight=w_gatedup_dt, output=mlp_mid_dt,
121	                grid_dim=(num_tasks, 1, 1), block_dim=block_dim)
122	
123	# Layer 2: SiLU activation * element-wise multiply
124	pk.silu_mul_layer(input=mlp_mid_dt, output=silu_out_dt,
125	                  grid_dim=(num_tasks // 2, 1, 1), block_dim=block_dim)
126	
127	# Layer 3: Down projection + residual add
128	pk.linear_with_residual_layer(input=silu_out_dt, weight=w_down_dt,
129	                              residual=residual_dt, output=mlp_out_dt,
130	                              grid_dim=(hidden_size // 64, 1, 1), block_dim=block_dim)
131	```
132	
133	**Key pattern:** intermediate tensors (`mlp_mid`, `silu_out`) are pre-allocated and attached via `attach_input` so they can be inspected after execution if needed.
134	
135	**Meta-tensor stubs:** some layers (e.g., `linear_with_residual_layer`) may reference `qo_indptr_buffer` at compile time. Pass a minimal stub:
136	```python
137	params["meta_tensors"] = {
138	    "qo_indptr_buffer": torch.zeros(batch_size + 1, dtype=torch.int32, device="cuda")
139	}
140	```

142	## Constraints
143	
144	- **One execution pass** — the task graph runs once and terminates. No iteration, no `prepare_next_batch`.
145	- **Meta-tensors optional** — pass `{}` or minimal stubs. Missing pointers become null; the kernel must not dereference them.
146	
147	## Debugging Tips
148	
149	**Compilation fails:**
150	- Check `<output_dir>/test_rank0.cu` for the generated code. Search for your task name in the `_execute_task()` function.
151	- Check `<output_dir>/task_graph_rank0.json` for the task graph. This file might be extremely long, dont read it in a raw fashion. Use `scripts/parse_task_graph.py` to read the task graph.
152	
153	**Incorrect dimension splitting:**
154	- The MPK layers require `input_map` for each associated tensor to specify how dimensions are split across the grid. If the grid or block dimensions don't divide the tensor dimensions correctly, the kernel may read/write out of bounds, causing NaNs or incorrect results.
155	
156	**Incomplete task attributes:**
157	- Ensure all required attributes for each task are correctly specified in the compilation logic, in `runtime.cc`. Missing or incorrect attributes can lead to undefined behavior or compilation errors.

## 一、先把 MPK 的本质说清楚

MPK 做的事一句话：**把整个 LLM 一次 forward（所有 layer + 所有算子 + AllReduce）编译成一个常驻 GPU 的 CUDA kernel**。

它的执行模型不是 "launch kernel A → launch kernel B"，而是：

- **Worker + Scheduler 共驻 GPU**。`worker_kernel` 和 `scheduler_kernel` 在两条 stream 上各起一次，然后就不退出。B200 上 148 个 SM，`MAX_NUM_WORKERS=160` 就是为 Blackwell 放宽的上限（`runtime_header.h:82`）。
- **任务图驱动**。每个"算子×tile"是一个 `TaskDesc`（16 字节对齐，`input_ptrs[7]/output_ptrs[3]` + 8 字节 metadata），算子之间靠 `EventDesc` 的 trigger 计数器相连。Scheduler 只占 1 个 warp（一个 SM 能塞 4 个 scheduler），纯事件驱动地往 worker 循环队列里派活。
- **连 decode loop 本身都在 GPU**。`prepare_next_batch` 是设备函数（`persistent_kernel.cuh:189/350/378` 三种 mode），包括 KV 分页、推进 step、检测 EOS、甚至在线新请求注入（`next_request_id`）都在 kernel 里做，CPU 从 decode 循环里彻底退出来。
- **编译产物就两个**：`test.cu`（里面有一个巨型 `_execute_task(task_type, variant_id)` switch）+ `task_graph.json`。nvcc 编完变成 `__mirage_launcher` Python 扩展。

这带来四个相对于"kernel-per-op"框架（SGLang / vLLM 现状）的本质收益：

1. **消灭 kernel launch bubble**：LLaMA-8B decode 一步大概 200+ kernel launch，MPK 是 1 次。
2. **消灭 host→device 往返**：continuous batching 的调度决策、spec decode 的 verify、sampling，全都在设备侧推进。
3. **跨算子 tile 级流水**：RMSNorm 的第 i 个 tile 完成就能 trigger Linear 的第 i 个 tile，不是整层 barrier。L2 命中率非常高。
4. **多卡通信变成普通事件**：NVSHMEM event encode 在 EventId 高位（`EVENT_NVSHMEM_TAG = 0x1e00...`），一次 AllReduce 就是一个 event 依赖，不再需要额外 kernel。

## 二、放到 SGLang 上下文里

SGLang 的分层大致是：**RadixAttention + 结构化生成（前端）** → **continuous batching / chunked prefill / zero-overhead scheduler（Python 调度层）** → **FlashInfer / Triton / CUTLASS kernel（执行层）**。它单算子已经很快了（FlashInfer sm100、DeepGEMM 都用上了），剩下的瓶颈在两个地方：

- **算子之间**：CUDA Graph 能缓解，但遇到动态 shape、MoE、spec decode、新请求进入立刻 fallback 到 eager，小 batch decode 的 ITL（inter-token latency）马上劣化。
- **step 之间**：zero-overhead scheduler 是把 Python 调度和上一步 GPU 执行重叠，但本质上每个 decode step 仍然是"CPU 发一串 launch"。

MPK 正好切进这个缺口。它**不是跟 SGLang 竞争的另一个推理框架**，它是 SGLang 执行层的下位替代：

| SGLang 现在负责 | 不动 |
|---|---|
| Request 级：prefix cache、结构化解码、约束、路由 | 继续 |
| Batch 级：continuous batching、chunked prefill | 继续 |
| **Step 级：把一层层算子 issue 出去** | **→ 交给 MPK，一个 `mpk()` 调用代替** |

工程上 SGLang 只需要维护 MPK 那 10 个 meta tensor（`step / tokens / qo_indptr / paged_kv_*` …），调度决策写到 `paged_kv_indices_buffer` 等等，kernel launch 就变成"通知 MPK 新一个 iteration 开始"。`MODE_ONLINE` 里 `prepare_next_batch` 已经有"检测新请求进入并注入 batch"的逻辑（`persistent_kernel.cuh:291`），这正是 continuous batching 的 GPU 侧对应。

**对 SGLang 的具体价值**：

- **小 batch、低延迟场景**（agentic、code completion、streaming chat）：MPK paper 宣称 1.2–6.7× latency 下降，这类场景 SGLang 打不满 TensorCore，MPK 的"跨算子流水"能直接把 MLP 的 down_proj tail 吃掉。
- **Spec decode / MTP**：MPK 原生支持（`tasks/speculative_decoding/`、`mla_mtp_decode_sm100`），状态机在 task graph 里表达，比 SGLang 里手写的 draft/target 协同更干净。
- **CUDA Graph 的真·替代**：动态 request 进入不需要 re-capture。
- **MoE 场景（DeepSeek V3、Qwen3-30B-A3B）**：`moe_w13_fp8_layer`、`moe_mul_sum_add_layer` 这套原语和 SGLang 的 DeepEP / fused MoE 路线天然对齐。

**对 SGLang 接入的阻力**：

- **算子覆盖**。SGLang 要支持的模型族比 MPK demo 大一个量级（Gemma、Phi、Mixtral、各种 LoRA/量化变体），每种都要写对应 arch 的 task（`/add-mpk-model` + `/add-mpk-task`）。
- **编译时间**。每次 `max_num_batched_tokens / page_size / max_seq_length` 变化都要重新 nvcc 编译一次（这些是编译期 macro），单次 1~10+ 分钟。适合 production 固定配置，不适合快速 A/B。
- **Prefix cache 语义**。SGLang 的 RadixAttention 用的是虚拟指针复用 KV 页，MPK 的分页管理是硬编码在 `prepare_next_batch` 里的，对接要把这部分改通。

**落地路径建议**：把 MPK 作为 SGLang 的一个 backend，优先在 "固定模型 + 固定 max batch + B200 部署" 这个子集上替换执行层，以 DeepSeek V3 + MLA + FP8 MoE 为首发用例（对应的 MPK 代码最全）。

## 三、放到 Blackwell（SM100 / B200、GB200）上下文里

Blackwell 对软件栈抛了几个全新的硬件语义：

1. **TMEM（Tensor Memory）**：SMEM 之外的一级片上存储，用来放 tcgen05 的 accumulator，把寄存器压力彻底卸下来。
2. **tcgen05 UMMA**：新 tensor core 指令，`cta_group::1` 单 SM，`cta_group::2` 两个 SM 成对（pair-SM / 2-SM cluster）合并成更大 tile，算力和带宽近乎翻倍。
3. **FP4/FP8 block-scaled MMA**：`tcgen05.mma.cta_group::1.kind::mxf8f6f4.block_scale`（见 `sm100_utils.cuh:138`），每组元素共享一个 scale，硬件原生。
4. **更大 SMEM + 更多 SM**：B200 228KB/SM × 148 SM（代码里 `MAX_DYNAMIC_SHARED_MEMORY_SIZE` 就是按 207KB 预算的）。
5. **Cluster + DSMEM**：跨 SM 共享 SMEM、跨 SM barrier（`ClusterTransactionBarrier`）。

这些特性把"kernel-per-op"的软件栈挤得非常难受：

- SM 从 H100 的 132 涨到 148，**kernel launch bubble 相对变大**。
- tcgen05 算得太快，**data movement 立刻成瓶颈**，必须跨算子做 producer/consumer 流水（上一 kernel 的 epilogue 和下一 kernel 的 prologue 之间根本没时间互相等待）。
- 要打满 `cta_group::2`（pair-SM MMA），**必须跨 SM 同步**，而每个算子独立 kernel 的模型下，这种同步成本太高，跨算子复用这种 cluster 状态几乎不可能。
- FP4/FP8 block-scale 把 quantize → group GEMM → activation → group GEMM 这条链路的 **kernel 融合空间放到前所未有的大**。

**MPK 在 Blackwell 上相当于是为这些特性量身打造的调度框架**：

- 项目里已经有一整个 `tasks/blackwell/`：`linear_fp8_sm100*`（FP8 + UMMA + TMA + TMEM 一条龙）、`fp8_group_gemm_sm100`（MoE grouped GEMM，**用 ClusterTransactionBarrier 和 pair-SM 协作**）、`mla_decode_sm100`、`mla_sm100_2sm`（MLA 直接用 2-SM cluster，这是 DeepSeek V3 在 B200 上延迟最优路径之一）、`topk_sigmoid_sm100`、`per_token_group_quantize_fp8` 等等。
- MPK 的 **task → event → worker** 调度粒度 = Blackwell 的 **producer/consumer warp specialization** 粒度。DMA warp 用 TMA 预取下一个 tile，MMA warp 跑 tcgen05，epilogue warp 回写 —— 这种模式在每算子独立 kernel 时只能在单个算子内部做，MPK 能把它跨算子延伸（上一层的 epilogue 直接喂下一层的 DMA prefetch）。
- **L2 驻留**。Blackwell L2 非常大，MPK 整次 decode 是一个 kernel，activation 几乎从不落 HBM。传统模型每一层的 QKV activation 在 kernel 边界会被赶出 L2，MPK 不会。
- **TMEM 的复用**：tcgen05 accumulator 在 TMEM 里，持久 kernel 语义下 TMEM 的生命周期能跨"算子"边界，省一轮 TMEM→SMEM→TMEM 的搬运（`linear_sm100_mpk.cuh` 里已经这样做）。

**一句话概括：**MPK 的"一个 kernel 跑完整个 forward"这种激进设计，**在 Hopper 上已经能赢，但在 Blackwell 上才把硬件优势完全吃到**。因为 Blackwell 的 tcgen05 / TMEM / pair-SM / FP4 block-scale 这四样都要求软件能跨 SM、跨算子、跨时间片地协作调度，而传统栈（cudaGraph、eager mode、一算子一 kernel）的调度粒度全都太粗了。

---

## 总结（TL;DR）

- **SGLang 视角**：MPK 是它 kernel 执行层的下位替换。SGLang 保留请求/批次调度和 prefix cache，MPK 把整个 step 级执行吞下去。最大价值在**小 batch 低延迟场景**、**spec decode / MTP**、**MoE 推理**。代价是 nvcc 编译时间和每个模型都要写 task，适合生产固定配置部署而非快速迭代。
- **Blackwell 视角**：Blackwell 的新硬件语义（tcgen05 / TMEM / pair-SM / FP4 block-scale）本质上都在**惩罚跨算子无法协作的软件栈**。MPK 的持久 megakernel + task graph 是少数能把这些特性完全吃到的执行模型，`tasks/blackwell/` 已经有 FP8 grouped GEMM、MLA 2-SM、block-scaled GEMM 等关键算子落地。
- **两者交集**：在 B200/GB200 上跑 SGLang 的 DeepSeek V3 / Qwen3-MoE，MPK 是我看到的**最有潜力把 decode ITL 砍一半以上**的技术路径，这也正是 MPK 团队在 `demo/deepseek_v3/` 和 `tests/runtime_python/blackwell/` 下面铺的最重的方向。

## 前置最关键的一点：sm_120 ≠ sm_100

RTX PRO 6000 Blackwell 是 **GB202，compute capability 12.0**。它虽然也叫"Blackwell"，但在指令层面和 B200 差距巨大：

| 特性 | sm_100 (B200/GB200) | sm_120 (RTX PRO 6000 / RTX 50 系) |
|---|---|---|
| tcgen05 MMA (UMMA) | ✅ | ❌ |
| TMEM（张量内存） | ✅ | ❌ |
| Pair-SM / cta_group::2 | ✅ | ❌ |
| DSMEM cluster barrier | ✅ | 降级 |
| TMA | ✅ | ✅（和 Hopper 类似） |
| FP4/FP8 block-scale MMA | ✅ 硬件原生 | 通过不同指令路径 |

然后看 MPK 的 blackwell 代码路径：

- `persistent_kernel.py` 编译命令写死 `-gencode=arch=compute_100a,code=sm_100a` 和 `-DMIRAGE_GRACE_BLACKWELL`；
- `tasks/blackwell/*.cuh` 里用的是 `tcgen05.mma.cta_group::1.kind::mxf8f6f4.block_scale`、`ClusterTransactionBarrier`、`cute::UMMA::SmemDescriptor`、`mla_sm100_2sm`（双 SM 合作）——**这些 PTX 指令在 sm_120 上根本不存在，不是降级问题，是直接编译不过/运行非法指令**。
- 代码里还有显式断言，例如 `assert self.target_cc == 100, "FP8 group GEMM requires SM100 (Blackwell)"`。

**结论**：在 sm_120 上，MPK 的 Blackwell 路径**一条都用不上**。你实际上会 fallback 到 **Ampere 路径**（`tasks/ampere/`，compute_80/86/89），因为 Hopper 路径依赖 WGMMA（`sm_90a`），sm_120 同样不支持。这意味着你丢失的东西非常多：

- 没有 TMA（Ampere 路径用 `cp.async`）
- 没有 5th gen tensor core
- 没有大 SMEM 预算（`MAX_DYNAMIC_SHARED_MEMORY_SIZE` 掉回 99KB～163KB 档）

**换句话说：要在 sm_120 上发挥出新硬件 70% 的能力，你得自己给 MPK 加一条 `tasks/sm120/` 代码路径**，至少把 TMA 用起来，把 5th-gen tensor core 指令（mma.sync 的新变种 + FP8/FP4）接进来。这不是一个晚上的工作。

## 和推测解码能不能叠加？能。而且是 MPK 最能打的场景之一。

MPK 本身就自带推测解码子模块：`tasks/speculative_decoding/`、`python/mirage/mpk/speculative.py`、`TASK_TARGET_VERIFY_GREEDY=114`、`TASK_FIND_NGRAM_PARTIAL/GLOBAL`，还有 MLA-MTP 专用 decode kernel。

**为什么天然契合**（这些理由跟架构无关，在 sm_120 上同样成立）：

1. **accept/reject 不再需要 host 介入**。传统 spec decode 的标准流程是：draft N 步 → 回 host 拿到 N 个 token → 发 verify kernel → 回 host 算接受长度 → 调整 KV 和 step → 进下一轮。每轮至少 2 次 CPU/GPU 同步。MPK 把 verify 做成一个 task，acceptance 长度写进 device 上的 `step[]`，`prepare_next_batch` 下一轮读这个 step 决定下一步 qo_indptr —— **整条 draft→verify→commit 链路零 host 参与**。
2. **可变接受长度不再打破 CUDA Graph**。这是传统栈上 spec decode 最难受的点：每轮接受 1~K 个 token 会让 qo_indptr、paged_kv_indices 改变，CUDA Graph 要么每种长度都 capture 一份（膨胀），要么 fallback 到 eager（延迟翻倍）。MPK 的 task graph 直接把 qo_indptr 做成运行时读取的 meta tensor，不 re-capture。
3. **draft 和 target 可以共存一个 megakernel**。MTP / Eagle 风格的 single-model draft 尤其适合——draft head 就是 target 的一个分支，task graph 里就是一条额外的边。
4. **draft step 的 kernel 碎**。draft 模型通常更小（甚至只是 target 的一个 head），单步更 launch-bound。MPK 消除 launch bubble 在 draft step 上的相对收益比 target step 更大。

**在 sm_120 + 单卡 + 不考虑缓存的约束下，收益估计**：

- 单 user、低延迟、小 batch 场景：**有显著收益**。
- 原因：你排除 L2 驻留优势之后，MPK 只剩两个核心卖点——**消除 kernel launch 开销**和**消除 decode 循环的 host 同步**。而 spec decode 正好把这两项的绝对量都放大：每个 iteration 有 draft N 步 + verify 1 步 ≈ (N+1)× 原本的 launch 次数，host 同步次数也至少翻倍。
- 量级感：sm_120 这一代 148~188 SM 级别，decode step 单 layer kernel launch bubble 大约 3~6μs（取决于 driver 状态），每层 6~8 个 kernel、32 层、N=4 draft step，一个 iteration 被 launch 吃掉的时间大约是 **2~5ms**。对 50~80 token/s 的目标（decode latency 12~20ms/token），这是 **20~30% 的剃刀**。
- 但相对 Blackwell 路径还能用的情况，绝对值是打折的（因为你是 Ampere fallback）。

## 你的 CUTLASS prefill + Marlin decode 自定义 kernel

能不能"适配进 MPK"，要分两部分回答：**架构上能，但代价不对称，而且 prefill 和 decode 两侧收益差异巨大**。

### 硬约束先列清楚（你的 kernel 要改写成 task 的前提）

1. **blockIdx 无关**。Marlin 和 CUTLASS 都大量用 `blockIdx.x/y` 算 tile 坐标，MPK 的 worker 的 blockIdx 是 worker ID 不是 tile ID。**你必须把 tile 坐标推到 codegen 期**：在 `task_register.cc` 里生成代码，把 tile 坐标烘进 `TaskDesc->input_ptrs[i]` 的 offset。对 Marlin 这种 tile 结构单调的 kernel，改写量中等；对 CUTLASS prefill 那种有复杂 swizzling / split-K / stream-K 的 kernel，改写量很大。
2. **block_dim 被 runtime 固定**。sm_120 走 Ampere fallback → `block_dim = (128,1,1)`。你的 Marlin 如果用 256 thread 版本，要么换 128 thread 版本（存在，但更慢），要么给 MPK 加个 sm_120 路径顺手把 worker 配成 256 thread。
3. **动态 SMEM 预算有限**。Ampere 路径的 `MAX_DYNAMIC_SHARED_MEMORY_SIZE` 在 sm_80 档是 163KB - 3KB reserved，sm_120 会走 compute_80/86/89 中的哪个 gencode 取决于 setup.py——很可能是 99KB。Marlin 的大 tile 版本可能塞不下。
4. **没有独立 grid launch**。Marlin kernel 通常按 M/N 分 grid，MPK 里这个 grid 要映射到 `(grid_dim_x, grid_dim_y, grid_dim_z)` 并通过 `input_map` 告诉 MPK 怎么切 tensor。

### Decode 侧（Marlin）——**建议试，收益实在**

Marlin 本身已经在 W4/W8 decode 上是 SOL（接近硬件极限），MPK 不会让你的 Marlin kernel 本身变快。**收益来自 Marlin 和它周围那堆小算子**：

```
rmsnorm → qkv(Marlin) → rope → paged_attn → o_proj(Marlin) → 
rmsnorm → gate_up(Marlin) → silu_mul → down(Marlin) → residual
```

每层这条链子上，Marlin 占大头（比如 70%），其他 6~8 个 kernel 占 20~30%。这 20~30% 在 sm_120 这种算力很强的卡上主要是 **launch 开销 + bandwidth-bound 的小 kernel**。MPK 把这些压进一个 kernel，还能在 warp specialization 下让 norm 和下一层 Marlin 的 prologue 重叠。**量级上 10~25% 的 decode latency 下降是现实的**，叠加 spec decode 之后这部分被进一步放大（因为 draft 步这种 overhead 占比更高）。

工程成本：把 Marlin decode kernel wrap 成一个 MPK task，最难的就是 blockIdx 改写 + SMEM 预算核对。如果你只是要一个"W4 decode GEMM 作为 MPK task"，工作量我估计 1~2 周内可控。

### Prefill 侧（CUTLASS）——**不建议迁**

原因和 decode 完全相反：

- Prefill 是 **compute-bound**。一个 CUTLASS prefill GEMM kernel 本身占 1~几 ms，kernel 边界的 launch/同步只占 1~3%。消灭这 3% 的收益极小。
- Stream-K / Split-K / Persistent Grid CUTLASS kernel 的 tile scheduling 逻辑通常深度依赖 grid 全局协同和 atomic counter，改写成 MPK task 要重造一遍调度器。
- MPK 对 prefill 的 multi-token attention 有自己的 task（`multitoken_paged_attention*`），但你的 CUTLASS prefill 八成是一整套自定义融合（attention + 前后算子），迁移是重写。

**更务实的做法**：prefill 走你现有的 CUTLASS（eager 或 CUDA Graph），decode 走 MPK。MPK 的 `MODE_ONLINE` 正好是这种"每次 decode 一个 iteration"的语义，你 host 侧把 prefill 做完，把 KV 和 step 灌进 MPK 的 meta tensor，然后 `mpk()` 做纯 decode。

---

## 把所有约束叠一起的最终答案

你的场景 = **sm_120 单卡 + 不考虑缓存收益 + Marlin decode + CUTLASS prefill + 想叠 spec decode**。

- **spec decode 叠 MPK**：技术上天然契合，收益量级 20~30% decode latency 剃刀，sm_120 上同样成立（因为靠的是 launch/sync 消除，不是架构指令）。**值得做**。
- **Marlin decode 接入 MPK 当 task**：工程成本中等（主要是 blockIdx 改写），收益 10~25% decode latency 下降，和 spec decode 叠加有复合效应。**值得试，先拿一层做 POC**。
- **CUTLASS prefill 接入 MPK**：工程成本高，收益低。**不建议**，prefill 继续用你现在的栈，MPK 只负责 decode loop。
- **sm_120 新硬件特性**：MPK 现在完全没有 sm_120 路径，你会 fallback 到 Ampere。**要吃到 sm_120 的 5th-gen tensor core + TMA，你得自己给 MPK 加一条 `tasks/sm120/`**，优先移植 TMA-based 的 linear/attention/rmsnorm，工作量是主要的长期投入点。

最后一个诚实的提醒：在"不考虑缓存"这个约束下，MPK 的优势被砍掉了大概一半（L2 跨算子复用、跨层 activation 不落 HBM 这些就是靠"缓存"的）。剩下的**纯 launch 开销 + host sync 消除**，在 sm_120 这种高算力单卡低延迟 decode 场景依然值，但 upside 没有 B200 那么戏剧性——你看到的应该是 **1.3~1.8×** decode 延迟改善而不是论文里那个 6.7×。

## 两者各自在省什么

先把两个优化砍的是哪部分时间说清楚，这是理解"叠"的前提。

**Spec decode 砍的是"生成一个 token 需要跑几次 forward"**
- 原本：1 token = 1 次 target forward（设为 T_tgt，比如 Qwen3-8B decode 一步 ~12ms）
- Spec decode：先让小模型 draft N 步（设每步 T_drf ~3ms），target 做 1 次多 token verify（约等于 T_tgt），平均接受 K 个 token（K < N）
- 每 token 平均耗时：(N·T_drf + T_tgt) / K

**MPK 砍的是"单次 forward 里被 kernel launch + host 同步吃掉的那部分时间"**
- 一个 forward = compute 时间 + launch/sync 开销
- MPK 把 launch/sync 开销压到接近 0，但不动 compute

它们砍的是**乘法里的不同因子**，所以能相乘。spec decode 把"每 token 几次 forward"从 1 压到 0.4，MPK 把"每次 forward 多少 ms"从 12 压到 9，两者都发生时单 token 时间从 12ms → 9 × 0.4 = 3.6ms。

## 拉出执行时间线看"叠"在哪里

假设 draft N=4、平均接受 K=2.5。下面用伪时间线表示一次"生成 2.5 个 token"的 iteration。

### 只有 spec decode、没有 MPK（传统栈）

```
[host] prepare draft input
[GPU ] launch draft fwd step 1   ← 30+ kernel launches
[sync] read sampled token to host
[host] prepare next draft input
[GPU ] launch draft fwd step 2   ← 30+ launches
[sync] read token
[host] ...
[GPU ] launch draft fwd step 3
[sync] read token
[GPU ] launch draft fwd step 4
[sync] read 4 tokens
[host] build verify input (qo_indptr, paged_kv_indices)
[GPU ] launch target multi-token forward  ← 30+ launches
[sync] read accept/reject mask
[host] compute K, update step[], update KV indptr
[GPU ] launch KV advance kernel
[sync] ready for next iteration
```

**问题点**：
- 4 × 30 + 30 ≈ 150 次 kernel launch
- 至少 6~7 次 host/device 同步
- draft 模型小 → 每步 compute 才 2~3ms，但 launch 开销 ~1~2ms → **draft step 是 launch-bound 重灾区**
- 接受长度 K 是动态的 → CUDA Graph 只能按长度各 capture 一份（膨胀）或直接不用（裸 eager）

### 只有 MPK、没有 spec decode

```
[host] mpk()                      ← 1 次 launch
[GPU ] 整个 forward pass 在一个 megakernel 里跑完
       (rmsnorm → qkv → rope → attn → o_proj → mlp → ... × 32 层 → sample)
       prepare_next_batch 也在设备上跑
[host] 下一次 mpk()
```

**收益**：每 step 的 ~30 次 launch 压成 1 次，host 参与为 0。但你还是**每 token 1 次 target forward**，spec decode 那部分的乘法因子没动。

### MPK + spec decode 一起用（"叠"）

```
[host] mpk()                      ← 1 次 launch
[GPU ] megakernel 内部执行 task graph:
         draft_layer_1 → draft_layer_2 → ... → draft_sample (×N)
         → build_verify_input (设备端)
         → target_layer_1 → ... → target_verify (一次多 token forward)
         → accept_reject (设备端)
         → advance_step + KV advance (设备端)
         → prepare_next_batch
[host] 读取新生成 token（可选，streaming）
```

对照一下砍掉的东西：

| 开销 | 无 MPK+spec | MPK+spec |
|---|---|---|
| kernel launch | ~150 次 | 1 次 |
| host/device sync | 6~7 次 | 0~1 次 |
| accept/reject 逻辑 | host Python | 一个 GPU task |
| 动态 K 打破 CUDA Graph | 是 | 不是（task graph 原生支持） |

---

## 为什么"叠"的收益比简单相乘还多

这是我上次没展开的点，关键：

**1. Draft 模型本身更 launch-bound，MPK 在 draft 步上的相对剃刀更大**

Launch 开销和 kernel compute 时间基本无关，大概固定 1~3μs × 层数。一个 Qwen3-8B 的 target forward 12ms 里 launch 占 ~2ms（17%）；但 draft 可能是一个 0.5B 的小模型，forward 2.5ms 里 launch 还是 ~2ms（**80%**）。spec decode 越是多 draft 步、draft 模型越小，MPK 的 launch 消除相对收益越爆炸。

**2. Spec decode 的 host 同步点密度远高于普通 decode**

普通 decode 一步只有 1 次 host sync（拿生成 token），spec decode 一个 iteration 有 N+2 次 sync（每个 draft step 一次 + verify 结果 + KV advance）。sync 开销是固定 μs 量级，频次越高 MPK 收益越大。

**3. 动态接受长度 + MPK 的 task graph 解锁了 CUDA Graph 原本做不到的组合**

在传统栈里，"spec decode + CUDA Graph"基本是个伪命题——每次接受 0/1/2/3/4 个 token 都让 qo_indptr 和 paged_kv_indptr 变形状。所以要么不用 CUDA Graph（吃 launch 开销），要么 N+1 份 graph（capture 开销爆炸 + 显存）。**MPK 的 task graph 把 qo_indptr 当 runtime 读的 meta tensor，天然不在乎它变**。也就是说：在没有 MPK 的世界里，你其实**不得不**在"用 CUDA Graph"和"用 spec decode"之间二选一，MPK 让你两个都要。

**4. MPK 代码里 spec decode 是一等公民**

不是后贴的功能，是内建的：
- `TASK_TARGET_VERIFY_GREEDY = 114`（verify 是一种 task type）
- `TASK_FIND_NGRAM_PARTIAL/GLOBAL`（prompt-lookup draft，完全零 compute 的 draft）
- `mla_mtp_decode_sm100`（DeepSeek V3 style MTP 的专用 decode kernel）
- `python/mirage/mpk/speculative.py` 里 `spec_decode_class`

具体形态取决于你用哪种 spec decode：

| 变体 | 和 MPK 的契合度 |
|---|---|
| Prompt lookup (n-gram) | ★★★★★ draft 本来就是字符串匹配，在 MPK 里就是两个 task，零额外 compute |
| Eagle / Medusa (draft head) | ★★★★☆ draft head 和 target 共享层，一个 megakernel 同时搞定 |
| MTP (DeepSeek V3 原生多 token) | ★★★★★ 原生支持，有专用 kernel |
| 独立 draft model (Llama-1B → Llama-70B) | ★★★☆☆ 可以做，但 draft 和 target 需要是两个 megakernel 或一个巨大的联合 megakernel，编译时间会爆 |

## 落回你 sm_120 单卡不考虑缓存的场景

"叠 MPK" 在你的场景里的具体含义是：

1. **你先把 MPK 的 Ampere fallback 路径跑通**（因为 sm_120 的 blackwell path 用不了），把纯 decode 的 megakernel 搭出来。
2. **在这个 megakernel 里接入一种 spec decode**。推荐顺序：
   - 先上 **prompt lookup (`TASK_FIND_NGRAM_*`)**，投入最少、draft 零 compute，纯赚 kernel launch 消除。
   - 再上 **Eagle / MTP**（看你的 target 模型是否有）。
3. **你的 Marlin decode kernel 作为 MPK task 接入 qkv/o_proj/gate_up/down 这四个大 GEMM**，其余（rmsnorm、silu_mul、rotary、attention）用 MPK 现成的 Ampere task。

三者都到位之后，每 token 时间的改进大概是这样叠的（拍脑袋数量级，你自己 profile 校准）：

```
baseline (eager + Marlin)                          :  12.0 ms/token
+ MPK (launch + sync 消除)                          :   9.5 ms/token   (-20%)
+ spec decode (K=2.5, N=4, draft head)             :   3.8 ms/token   (-60%)
+ 两者同时                                          :   2.8 ms/token   (-77%)
                                                      ^ 这里比 9.5 × 0.4 = 3.8 还低
                                                      因为 draft step 上 MPK 的剃刀更狠
```

最后那一档的 **3.8 → 2.8** 就是"叠加"里那部分"比乘法多赚的"，来自于上面说的第 1、2、3 点——draft 更 launch-bound、sync 密度更高、动态 K 原生支持。

## 一句话总结

"叠 MPK" = **把 spec decode 的那些 host 来回、draft 步的 launch 碎片、动态接受长度带来的 graph 失效，全部塞进 MPK 的 task graph 里在 GPU 侧一次做完**。两者砍的是乘法的不同因子所以相乘；而 draft 步恰好是 launch-bound 重灾区、spec decode 恰好是 host-sync 重灾区，所以 MPK 的剃刀在 spec decode 场景下比在普通 decode 场景下锋利得多，这就是"叠"比"加"更值的原因。

## 站得住的部分

以下是不依赖我编的数字、靠代码和物理论证都能撑住的：

1. **方向上两者正交、能相乘**：spec decode 砍"每 token 几次 forward"，MPK 砍"每次 forward 的固定开销"，确实不在同一个乘法因子上。

3. **动态接受长度 + CUDA Graph 确实互相打架**：要么多份 graph 要么退回 eager。MPK 的 task graph 把 qo_indptr 当 runtime meta tensor，天然不受影响。这点是真优势。
4. **MPK 有一等公民的 spec decode 原语**：代码里那些 `TASK_FIND_NGRAM_*`、`TASK_TARGET_VERIFY_GREEDY`、MTP decode kernel 是实锤，不是我编的。
5. **sm_120 跑 MPK 会 fallback 到 Ampere path**：`tasks/blackwell/` 全部 sm_100a 门槛、Hopper 路径走 WGMMA 要 sm_90a，sm_120 两头都不靠。这个结论靠代码证据，稳。
