可选路径：EAGLE3 多层 Draft Head（需算法创新）

EAGLE3 通过轻量 Draft Head 利用目标模型隐藏状态预测候选 token，再由目标模型一次性验证。Head 参数量极小（几十 MB），满足 2GB 限制。

Lightning Attention 兼容性挑战： SALA 部分层使用 Lightning Attention（Gated Delta Rule 线性注意力），其递推计算本质上不支持树状因果掩码，传统树验证机制无法直接生效。SGLang 已有初步集成（hybrid_linear_attn_backend.py 中处理了 is_target_verify 模式），但选手仍可能需要在算法层面创新，鼓励创新方案。

工作流程：

训练 EAGLE3 Head： 参考 EAGLE 仓库，用 SALA 收集隐藏状态训练 Draft Head，权重作为提交物。
模型适配： 参考 llama_eagle3.py 为 SALA 创建 EAGLE3 模型文件。
解决 Lightning Attention 验证问题： 核心难点，需修改验证逻辑适配线性注意力层。
启动验证： --speculative-algorithm EAGLE3 --speculative-draft-model-path <path> --speculative-num-draft-tokens 5。

137	                req_to_token_pool=self.req_to_token_pool,
138	                token_to_kv_pool_allocator=self.token_to_kv_pool_allocator,
139	                is_multi_layer_eagle=True,
140	            )
141	
142	        embed, head = self.target_worker.model_runner.model.get_embed_and_head()
143	
144	        if self.speculative_algorithm.is_eagle3():
145	            # most cases EAGLE3 models don't share lm_head
146	            # but some models (e.g. nvidia/gpt-oss-120b-Eagle3) shares

151	                self.draft_model_runner.model.set_embed_and_head(embed, head)
152	            else:
153	                self.draft_model_runner.model.set_embed(embed)
154	
155	            # grab hot token ids

168	            for i in range(self.speculative_num_steps):
169	                self.mtp_model_runner(i).model.set_embed_and_head(embed, head)

174	                backup_disable_cuda_graph
175	            )
176	        self.draft_tp_context = (
177	            draft_tp_context if server_args.enable_dp_attention else empty_context
178	        )
179	        with self.draft_tp_context(
180	            self.mtp_model_runner(0).tp_group
181	        ), speculative_moe_backend_context():

183	            self.init_cuda_graphs()

187	            (), dtype=torch.int64, device=self.device
188	        )

232	    def forward_batch_generation(self, batch: ScheduleBatch) -> GenerationBatchResult:
233	        """Run speculative decoding forward.
234	
235	        NOTE: Many states of batch is modified as you go through. It is not guaranteed that
236	        the final output batch have the same state as the input.
237	
238	        Args:
239	            batch: The batch to run forward. The state of the batch is modified as it runs.
240	        Returns:
241	            A tuple of the final logit output of the target model, next tokens accepted,
242	            the batch id (used for overlap schedule), and number of accepted tokens.
243	        """
244	        if batch.forward_mode.is_extend() or batch.is_extend_in_batch:
245	            logits_output, next_token_ids, seq_lens_cpu = self.forward_target_extend(
246	                batch
247	            )
248	            with self.draft_tp_context(
249	                self.mtp_model_runner(0).tp_group
250	            ), speculative_moe_backend_context():
251	                self.forward_draft_extend(
252	                    batch, logits_output.hidden_states, next_token_ids, seq_lens_cpu
253	                )
254	            return GenerationBatchResult(
255	                logits_output=logits_output,
256	                next_token_ids=next_token_ids,
257	                num_accepted_tokens=0,
258	                can_run_cuda_graph=False,
259	            )
260	        else:
261	            with self.draft_tp_context(
262	                self.mtp_model_runner(0).tp_group
263	            ), speculative_moe_backend_context():
264	                spec_info = self.draft(batch)
265	            logits_output, verify_output, model_worker_batch, can_run_cuda_graph = (
266	                self.verify(batch, spec_info)
267	            )
268	
269	            with self.draft_tp_context(
270	                self.mtp_model_runner(0).tp_group
271	            ), speculative_moe_backend_context():
272	                # NOTE: We should use `check_forward_draft_extend_after_decode`
273	                # when DP attention is enabled, but it is slow. Skip it for now.
274	                if (
275	                    self.server_args.enable_dp_attention
276	                    or batch.spec_info.verified_id.shape[0] > 0
277	                ):
278	                    # decode is not finished
279	                    self.forward_draft_extend_after_decode(batch)
280	
281	            return GenerationBatchResult(
282	                logits_output=logits_output,
283	                next_token_ids=verify_output.verified_id,
284	                num_accepted_tokens=sum(verify_output.accept_length_per_req_cpu),
285	                can_run_cuda_graph=can_run_cuda_graph,
286	            )

288	    def check_forward_draft_extend_after_decode(self, batch: ScheduleBatch):
289	        local_need_forward = batch.spec_info.verified_id.shape[0] > 0
290	        if not self.server_args.enable_dp_attention:
291	            return local_need_forward
292	
293	        global_need_forward = torch.tensor(
294	            [
295	                (local_need_forward),
296	            ],
297	            dtype=torch.int64,
298	        )
299	        torch.distributed.all_reduce(
300	            global_need_forward, group=get_tp_group().cpu_group
301	        )
302	        global_need_forward_cnt = global_need_forward[0].item()
303	        need_forward = global_need_forward_cnt > 0
304	        return need_forward

346	    def draft(self, batch: ScheduleBatch):
347	        # Parse args
348	        if batch.forward_mode.is_idle():
349	            self._draft_preprocess_idle(batch)
350	        else:
351	            self._draft_preprocess_decode(batch)
352	
353	        spec_info = batch.spec_info
354	        assert isinstance(spec_info, EagleDraftInput)
355	
356	        spec_info.capture_hidden_mode = CaptureHiddenMode.LAST
357	        spec_info.num_tokens_per_batch = self.topk
358	        spec_info.num_tokens_for_logprob_per_batch = self.topk
359	        batch.return_hidden_states = False
360	
361	        # Get forward batch
362	        model_worker_batch = batch.get_model_worker_batch()
363	        assert model_worker_batch.capture_hidden_mode == CaptureHiddenMode.LAST
364	        forward_batch = ForwardBatch.init_new(
365	            model_worker_batch, self.mtp_model_runner(0)
366	        )
367	        forward_batch.can_run_dp_cuda_graph = False
368	        forward_batch.return_hidden_states_before_norm = True
369	
370	        # Parse args
371	        assert isinstance(spec_info, EagleDraftInput)
372	        topk_p, topk_index, hidden_states = (
373	            spec_info.topk_p,
374	            spec_info.topk_index,
375	            spec_info.hidden_states,
376	        )
377	
378	        # Return values
379	        score_list: List[torch.Tensor] = []
380	        token_list: List[torch.Tensor] = []
381	        parents_list: List[torch.Tensor] = []
382	
383	        # Forward multiple steps
384	        scores = None
385	        input_ids, hidden_states, scores, tree_info = select_top_k_tokens(
386	            0, topk_p, topk_index, hidden_states, scores, self.topk
387	        )
388	        if self.speculative_num_steps == 1:
389	            score_list.append(tree_info[0])
390	            token_list.append(tree_info[1])
391	            parents_list.append(tree_info[2])
392	        else:
393	            for i in range(self.speculative_num_steps):
394	                score_list.append(tree_info[0][:, :, i].unsqueeze(-1))
395	                token_index = tree_info[1][:, i].unsqueeze(-1)
396	                token_list.append(token_index)
397	                if i == 0:
398	                    parents_list.append(tree_info[2])
399	                else:
400	                    parents_list.append(
401	                        torch.full(
402	                            (tree_info[2].size(0), 1),
403	                            i,
404	                            dtype=torch.long,
405	                            device=self.device,
406	                        )
407	                    )
408	
409	        parent_list, top_scores_index, draft_tokens = organize_draft_results(
410	            score_list, token_list, parents_list, self.speculative_num_draft_tokens
411	        )
412	
413	        if batch.forward_mode.is_idle():
414	            return EagleVerifyInput.create_idle_input(
415	                self.topk,
416	                self.speculative_num_steps,
417	                self.speculative_num_draft_tokens,
418	            )
419	
420	        (
421	            tree_mask,
422	            position,
423	            retrive_index,
424	            retrive_next_token,
425	            retrive_next_sibling,
426	            draft_tokens,
427	        ) = build_tree_kernel_efficient(
428	            spec_info.verified_id,
429	            parent_list,
430	            top_scores_index,
431	            draft_tokens,
432	            batch.seq_lens,
433	            batch.seq_lens_sum,
434	            self.topk,
435	            self.speculative_num_steps,
436	            self.speculative_num_draft_tokens,
437	        )
438	
439	        return EagleVerifyInput(
440	            draft_token=draft_tokens,
441	            custom_mask=tree_mask,
442	            positions=position,
443	            retrive_index=retrive_index,
444	            [REDACTED],
445	            retrive_next_sibling=retrive_next_sibling,
446	            retrive_cum_len=None,
447	            spec_steps=self.speculative_num_steps,
448	            topk=self.topk,
449	            draft_token_num=self.server_args.speculative_num_draft_tokens,
450	            capture_hidden_mode=CaptureHiddenMode.FULL,
451	            seq_lens_sum=forward_batch.seq_lens_sum,
452	            seq_lens_cpu=forward_batch.seq_lens_cpu,
453	        )

459	    def verify(self, batch: ScheduleBatch, spec_info: EagleVerifyInput):
460	        spec_info.prepare_for_verify(batch, self.page_size)
461	        batch.return_hidden_states = False
462	        batch.forward_mode = (
463	            ForwardMode.TARGET_VERIFY
464	            if not batch.forward_mode.is_idle()
465	            else ForwardMode.IDLE
466	        )
467	        batch.spec_info = spec_info
468	
469	        model_worker_batch = batch.get_model_worker_batch(
470	            seq_lens_cpu_cache=spec_info.seq_lens_cpu
471	        )
472	        assert model_worker_batch.capture_hidden_mode == spec_info.capture_hidden_mode
473	        model_worker_batch.return_hidden_states_before_norm = True
474	
475	        if batch.has_grammar:
476	            retrieve_next_token_cpu = spec_info.retrive_next_token.cpu()
477	            retrieve_next_sibling_cpu = spec_info.retrive_next_sibling.cpu()
478	            draft_tokens_cpu = spec_info.draft_token.view(
479	                spec_info.retrive_next_token.shape
480	            ).cpu()
481	
482	        # Forward
483	        batch_result = self.target_worker.forward_batch_generation(
484	            model_worker_batch, is_verify=True
485	        )
486	        logits_output, can_run_cuda_graph = (
487	            batch_result.logits_output,
488	            batch_result.can_run_cuda_graph,
489	        )
490	
491	        vocab_mask = None
492	        if batch.has_grammar:
493	            # Generate the logit mask for structured output.
494	            # Overlap the CPU operations for bitmask generation with the forward pass.
495	            vocab_mask = generate_token_bitmask(
496	                batch.reqs,
497	                spec_info,
498	                retrieve_next_token_cpu,
499	                retrieve_next_sibling_cpu,
500	                draft_tokens_cpu,
501	                batch.sampling_info.vocab_size,
502	            )
503	
504	            if vocab_mask is not None:
505	                assert spec_info.grammar is not None
506	                vocab_mask = vocab_mask.to(spec_info.retrive_next_token.device)
507	                # NOTE (sk): otherwise, this vocab mask will be the one from the previous extend stage
508	                # and will be applied to produce wrong results
509	                batch.sampling_info.vocab_mask = None
510	
511	        if self.enable_nan_detection:
512	            detect_nan(logits_output)
513	
514	        spec_info.hidden_states = logits_output.hidden_states
515	        res: EagleVerifyOutput = spec_info.verify(
516	            batch,
517	            logits_output,
518	            self.token_to_kv_pool_allocator,
519	            self.page_size,
520	            vocab_mask,
521	        )
522	
523	        # Post process based on verified outputs.
524	        # Pick indices that we care (accepted)
525	        logits_output.next_token_logits = logits_output.next_token_logits[
526	            res.accepted_indices
527	        ]
528	        logits_output.hidden_states = logits_output.hidden_states[res.accepted_indices]
529	
530	        if self.target_worker.model_runner.hybrid_gdn_config is not None:
531	            accepted_length = (
532	                torch.tensor(
533	                    res.accept_length_per_req_cpu,
534	                    device=logits_output.hidden_states.device,
535	                    dtype=torch.int64,
536	                )
537	                + 1
538	            )
539	
540	            # If topk > 1, we need to use retrieve_next_token and retrieve_next_sibling to handle the eagle tree custom attention mask
541	            # res.accepted_indices.shape[0] > 0 skips DP attn idle batch
542	            if spec_info.topk > 1 and res.accepted_indices.shape[0] > 0:
543	                # accepted_indices=[0,2,3,4,5,7,9,10,11], accepted_length=[4, 3, 2], cumulative_accepted_lengths=[4, 7, 9]
544	                # first_token_indices_per_req=prepend(0, accepted_indices[cumulative_accepted_lengths[:-1]]) = [0, 5, 10]
545	                # last_token_indices_per_req=accepted_indices[cumulative_accepted_lengths - 1] = [4, 9, 11] (last token ID of each req)
546	                # max_relative_indices_per_req = [4,4,1]; those are the per-req spec-decoding step offsets that contain the correct mamba caches
547	                cumulative_accepted_lengths = torch.cumsum(accepted_length, dim=0)
548	                req_start_positions = torch.cat(
549	                    [
550	                        torch.zeros(
551	                            1,
552	                            dtype=cumulative_accepted_lengths.dtype,
553	                            device=cumulative_accepted_lengths.device,
554	                        ),
555	                        cumulative_accepted_lengths[:-1],
556	                    ]
557	                )
558	                first_token_indices_per_req = res.accepted_indices[req_start_positions]
559	                last_token_indices_per_req = res.accepted_indices[
560	                    cumulative_accepted_lengths - 1
561	                ]
562	                max_relative_indices_per_req = (
563	                    last_token_indices_per_req - first_token_indices_per_req
564	                )
565	            else:
566	                max_relative_indices_per_req = accepted_length - 1
567	            self.target_worker.model_runner.attn_backend.update_mamba_state_after_mtp_verify(
568	                max_relative_indices_per_req, self.target_worker.model_runner.model
569	            )
570	
571	        if batch.return_logprob:
572	            add_output_logprobs_for_spec_v1(batch, res, logits_output)
573	
574	        # Prepare the batch for the next draft forwards.
575	        batch.forward_mode = (
576	            ForwardMode.DECODE if not batch.forward_mode.is_idle() else ForwardMode.IDLE
577	        )
578	        batch.spec_info = res.draft_input
579	
580	        return logits_output, res, model_worker_batch, can_run_cuda_graph

582	    def forward_draft_extend(
583	        self,
584	        batch: ScheduleBatch,
585	        hidden_states: torch.Tensor,
586	        next_token_ids: torch.Tensor,
587	        seq_lens_cpu: Optional[torch.Tensor],
588	    ):
589	        """Run draft model extend. This API modifies the states of the batch.
590	
591	        Args:
592	            batch: The batch to run.
593	            hidden_states: Hidden states from the target model forward
594	            next_token_ids: Next token ids generated from the target forward.
595	        """
596	        batch.spec_info = EagleDraftInput(
597	            hidden_states=hidden_states,
598	            verified_id=next_token_ids,
599	            num_tokens_per_batch=1,
600	            num_tokens_for_logprob_per_batch=1,
601	        )
602	        batch.return_hidden_states = False
603	        batch.spec_info.prepare_for_extend(batch)
604	        batch.spec_info.capture_hidden_mode = CaptureHiddenMode.LAST
605	        model_worker_batch = batch.get_model_worker_batch(
606	            seq_lens_cpu_cache=seq_lens_cpu
607	        )
608	        forward_batch = ForwardBatch.init_new(
609	            model_worker_batch, self.mtp_model_runner(0)
610	        )
611	        forward_batch.return_logprob = False
612	        forward_batch.return_hidden_states_before_norm = True
613	        topk_p_list = []
614	        topk_index_list = []
615	        for step in range(self.speculative_num_steps):
616	            logits_output, _ = self.mtp_model_runner(step).forward(forward_batch)
617	            if self.enable_nan_detection:
618	                detect_nan(logits_output)
619	            probs = torch.softmax(logits_output.next_token_logits, dim=-1)
620	            topk_p, topk_index = fast_topk(probs, self.topk, dim=-1)
621	            topk_p_list.append(topk_p)
622	            topk_index_list.append(topk_index)
623	            pt = 0
624	            if forward_batch.extend_seq_lens is not None:
625	                for i, extend_len in enumerate(forward_batch.extend_seq_lens):
626	                    input_ids = forward_batch.input_ids[pt : pt + extend_len]
627	                    forward_batch.input_ids[pt : pt + extend_len] = torch.cat(
628	                        (input_ids[1:], topk_index[i].reshape(1))
629	                    )
630	                    pt += extend_len
631	
632	        assert isinstance(forward_batch.spec_info, EagleDraftInput)
633	        assert forward_batch.spec_info is batch.spec_info
634	        forward_batch.spec_info.topk_p = torch.cat(topk_p_list, dim=1)
635	        forward_batch.spec_info.topk_index = torch.cat(topk_index_list, dim=1)
636	        has_finished, unfinished_req_index = False, []
637	        for i, req in enumerate(batch.reqs):
638	            if req.finished():
639	                has_finished = True
640	            else:
641	                unfinished_req_index.append(i)
642	        if has_finished:
643	            unfinished_index_device = torch.tensor(
644	                unfinished_req_index,
645	                dtype=torch.int64,
646	                device=batch.spec_info.topk_p.device,
647	            )
648	            batch.spec_info.filter_batch(
649	                unfinished_index_device, has_been_filtered=False
650	            )

666	            hidden_size = (
667	                self.model_config.hidden_size * 3

669	                else self.model_config.hidden_size

673	                hidden_size=hidden_size,

677	            )

75	def _build_slope_tensor(nheads: int) -> torch.Tensor:
76	    """Build ALiBi slope tensor - matches MiniCPM implementation.
77	
78	    This function computes the Attention with Linear Biases (ALiBi) slopes
79	    used in Simple GLA for decay calculation. The slopes are computed using
80	    a geometric progression with power-of-2 optimization.
81	
82	    Args:
83	        nheads: Number of attention heads
84	
85	    Returns:
86	        slopes: Tensor of shape (nheads,) containing ALiBi slopes
87	    """
88	    def get_slopes(n):
89	        def get_slopes_power_of_2(n):
90	            start = 2 ** (-(2 ** -(math.log2(n) - 3)))
91	            ratio = start
92	            return [start * ratio**i for i in range(n)]
93	
94	        if math.log2(n).is_integer():
95	            return get_slopes_power_of_2(n)
96	        else:
97	            closest_power_of_2 = 2 ** math.floor(math.log2(n))
98	            return (
99	                get_slopes_power_of_2(closest_power_of_2)
100	                + get_slopes(2 * closest_power_of_2)[0::2][: n - closest_power_of_2]
101	            )
102	
103	    slopes = torch.tensor(get_slopes(nheads))
104	    return slopes

62	    """Save post-norm hidden states during EXTEND for Medusa training.
63	
64	    For long sequences (>4096 tok), only saves the LAST 4096 tokens.
65	    This ensures hidden states carry long-context (sparse attention) information.
66	    """
67	    global _medusa_counter
68	    if not _os.path.isdir(_MEDUSA_COLLECT_DIR):
69	        return
70	    if forward_batch.forward_mode != ForwardMode.EXTEND:
71	        return
72	    seq_lens = forward_batch.extend_seq_lens_cpu
73	    if seq_lens is None:
74	        return
75	    pt = 0
76	    with _medusa_lock:
77	        for seq_len in seq_lens:
78	            start = pt + max(0, seq_len - _MEDUSA_MAX_TOKENS)

### 三、核心难点分析

#### 难点1：没有 SALA-specific EAGLE3 模型文件 ⚠️ 必须创建

`llama_eagle3.py` 是为 LLaMA 设计的：
```python
self.fc = torch.nn.Linear(hidden_size_in * 3, config.hidden_size)
self.midlayer = LlamaDecoderLayer(config, 0, ...)  # 标准注意力
```

SALA 需要类似结构，但：
- 目标 hidden_state 的维度：SALA `hidden_size=4096`，所以 fc 输入 `4096*3=12288`
- draft 内部可以用**标准注意力**（不需要 Lightning Attention，是独立的小模型）
- 需要创建 `minicpm_sala_eagle3.py`，继承 `LlamaForCausalLMEagle3` 基本可以直接复用

#### 难点2：3层隐状态从哪些层取 ⚠️ 需要实验

EAGLE3 论文取 target 的 3 个不同层的隐状态 concatenate 后输入 draft head。
SALA 有 32 层，标准 Attention 在 `[0,9,16,17,22,29,30,31]`。

推荐取**最后3层标准Attention** `[29, 30, 31]` 的 hidden_state，或者最后3层（无论类型）。
已有机制：`CaptureHiddenMode.FULL` + `return_hidden_states_before_norm=True` 已捕获全部隐状态。

#### 难点3：SimpleGLA TARGET_VERIFY 不支持树形导航 ⚠️ topk>1 时的关键缺陷

当前 SimpleGLA TARGET_VERIFY（lines 1636-1711）是**线性链**实现：
```python
current_state = initial_state
for step in range(draft_token_num):
    o_s, current_state = fused_recurrent_simple_gla(...)  # 状态单向流动
```

这对 **topk=1 线性链**完全够用。
但 topk>1 时，树形验证要求：每个节点的初始 state = 其父节点的 state，而不是上一个线性步骤的 state。

GDN 层通过 `retrieve_parent_token` 参数已解决此问题。**SimpleGLA 没有等价机制。**

#### 难点4：训练 EAGLE3 Draft Head ⚠️ 需要收集数据

已有 `medusa/collect_data.py` 可以参考，但需要修改为：
1. 捕获3个特定层的 hidden_state（而非最后一层）
2. 对应的 next_token（target token）作为label
3. 训练一个标准的 EAGLE3 decoder（已有 `llama_eagle3.py` 参考）

### 六、过去失败的根因（来自 CLAUDE.md Negative Results）

> EAGLE-3 spec decode → ~0% accept — BF16-trained draft vs NVFP4 target mismatch

## Medusa 线性链 + 树形投机解码 完整技术方案

### 一、先质疑两个假设（揪头发）

**假设1：K>1 线性链需要大量改动** — **错误**

代码已经支持 K>1。`num_heads = server_args.speculative_num_steps or 3`，`num_draft_tokens = num_heads + 1`。GLA 状态回滚逻辑（`intermediate_ssm[cache_idx, :batch_size, step]` + `update_mamba_state_after_mtp_verify`）对任意 K 都正确。**唯一缺失：K>1 的训练权重**。

**假设2：SimpleGLA 不支持 TARGET_VERIFY** — **部分正确**

SimpleGLA TARGET_VERIFY **线性链**已完整实现（`hybrid_linear_attn_backend.py:1636-1711`）。不支持的只是**树形节点的父状态路由**（topk>1 时每个节点应从其父节点的 state 出发，而不是上一个线性步骤）。

---

### 二、关键技术障碍精确定位

#### 障碍A：SimpleGLA 树形状态路由（topk>1 的核心问题）

当前代码（线性链）：
```python
# hybrid_linear_attn_backend.py:1683-1704
current_state = initial_state  # 从提交状态出发
for step in range(draft_token_num):
    o_s, current_state = fused_recurrent_simple_gla(
        initial_state=current_state,  # 永远是上一步的状态 ← 线性假设
    )
    intermediate_ssm[cache_idx, :batch_size, step] = current_state
```

树形场景下的正确逻辑：
```
step=0 (d0_a): parent=-1, 从 committed state 出发 → state_0a
step=1 (d0_b): parent=-1, 从 committed state 出发 → state_0b  
step=2 (d1_aa): parent=0, 从 state_0a 出发 → state_1aa
step=3 (d1_ab): parent=0, 从 state_0a 出发 → state_1ab
step=4 (d1_ba): parent=1, 从 state_0b 出发 → state_1ba
...
```

需要的修改：按 `retrieve_parent_token` 索引 `intermediate_ssm` 获取父状态。

#### 障碍B：`retrieve_parent_token` 未被计算

需要：在 MedusaWorker draft 阶段，从树结构中推导出 `retrieve_parent_token`。

#### 障碍C：`MedusaVerifyInput` 无树形支持

`MedusaVerifyInput.topk=1`，没有 `custom_mask`、`retrive_index`、`retrive_next_token`、`retrive_next_sibling`。树形验证需要切换到 `EagleVerifyInput`。

#### 障碍D：CUDA Graph 与树形验证不兼容

**改动2：计算 `retrieve_parent_token`**

`build_tree_kernel_efficient` 输出的树结构（`retrive_next_token`, `retrive_next_sibling`）是**子→兄弟**方向的遍历索引，不直接给出父指针。需要从树构建阶段推导。

**关键实现**：在调用 `build_tree_kernel_efficient` 前，保留每个 draft token 的父节点信息，然后在 `EagleVerifyInput` 中增加 `retrieve_parent_token` 字段（或在 `_forward_metadata` 中计算）：

```python
# 在 EagleVerifyInput 上增加可选字段（或存入 batch）
# retrieve_parent_token[i, j] = step j 的父 step 索引，request i
# 对线性链：retrieve_parent_token[i, j] = j-1，-1表示使用committed state

def compute_retrieve_parent_token(retrive_next_token, retrive_next_sibling, bs, dtn):
    """从 next_token/sibling 反推 parent_token。
    
    树的遍历顺序由 build_tree_kernel_efficient 决定（BFS），
    next_token[i, p] = p 的第一个子节点在 draft_tokens 中的位置
    sibling[i, p] = p 的下一个兄弟节点位置
    
    parent_token[i, j] = j 的父节点位置（-1 表示 user_4813494d/committed）
    """
    device = retrive_next_token.device
    parent = torch.full((bs, dtn), -1, dtype=torch.int32, device=device)
    
    # 利用 next_token 关系：next_token[i, p] = c 意味着 parent[i, c] = p
    # 利用 sibling 关系：next_token[i, p] 的下一个兄弟 sibling[i, c] 也有 parent[i, sibling[i,c]] = p
    for step in range(dtn - 1):
        child_idx = retrive_next_token[:, step]  # (bs,) child of step `step`
        valid = child_idx >= 0
        parent[valid, child_idx[valid]] = step
        
        # 追踪同层兄弟
        sib = retrive_next_sibling[:, step]
        while (sib >= 0).any():
            valid_sib = sib >= 0
            parent[valid_sib, sib[valid_sib]] = step
            sib = torch.where(valid_sib, retrive_next_sibling[:, sib.clamp(0)], -1)
    
    return parent
```

注意：这是 CPU 上的操作（树规模小，≤15节点），性能可接受。

## 树形 Draft 是什么，意义在哪里

### 先从线性链理解问题

当前 Medusa K=1 的流程：

```
目标模型已确认的 token: [..., T]
Medusa 预测: d0 (argmax)

验证序列: [T, d0]
目标模型验证: T → 预测 P0

若 d0 == P0: 接受，输出 [d0, 目标校正]  ✓
若 d0 != P0: 拒绝，输出 [目标校正]      ✗
```

K=3 线性链：

```
草稿: [d0, d1, d2]（头0预测d0，头1预测d1，头2预测d2）

验证序列: [T, d0, d1, d2]

接受规则（级联）:
  d0 接受 → 再看 d1
  d0 被拒 → d1,d2 直接丢弃（无论对错）
```

**致命弱点**：d0 被拒时，d1 和 d2 完全浪费。即使 d1 猜对了，因为 d0 错了也白搭。

---

### 树形 Draft 解决的核心问题

**核心思想**：与其押注一条路，不如同时押多条路，其中一条被接受就赢了。

```
                    T（已确认）
                   / \
              d0_a    d0_b      ← Head0 top-2 候选
             /  \    /  \
         d1_a d1_b d1_c d1_d   ← Head1 top-2 候选（共4个）
        / \  / \  / \  / \
       ...                      ← Head2 top-2 候选（共8个）
```

topk=2, K=3 时，树有 1+2+4+8 = **15 个节点**，一次 forward 验证。

**验证逻辑**：
```
目标模型对每个节点做预测:
  T → 预测 P_user_4813494d
  
若 P_user_4813494d == d0_a: 走左分支
  d0_a → 预测 P_0a
  若 P_0a == d1_a: 继续左...
  若 P_0a == d1_b: 继续右...
  
若 P_user_4813494d == d0_b: 走右分支（d0_a 虽然错了，d0_b 救场！）
  ...
```

关键：**任何一条从根到叶的路径，只要节点匹配就能接受**。

---

### 用数字说话

假设每个 token 的接受概率 = 50%（greedy 匹配）：

| 方案 | 每步期望 token 数 | 计算方式 |
|------|------|------|
| K=1 线性 | 1.50 | 1 + 0.5 |
| K=3 线性 | 1.875 | 1 + 0.5 + 0.25 + 0.125（需全部串联） |
| K=3 topk=2 树形 | **~3.2** | 树上有多条路径，任一路径接受就计数 |

为什么树形好这么多？

线性链被拒链断，后面全废。树形**允许从备选分支救场**：

```
线性链 d0 被拒 → 0 个额外 token
树形 d0_a 被拒 → d0_b 可能还在 → 不损失那条分支的后续
```

---

### 形象类比

**线性链**：买彩票，买一张，号码错一位全输。

**树形**：同时买15张彩票（共享一次对奖），只要有一张前N位对上就赢。

代价：目标模型 forward 一次要处理 15 个 token（而不是 4 个），但 GEMM 在 M=15 时的代价比 M=1 大不了 2x（带宽限制，不是计算限制）。

---

### 为什么对 SALA 有意义

SALA 的 decode 瓶颈是 Lightning Attention 的 GLA 递推计算（串行，不能并行），**每多一个 token 就多一次递推**。

树形 verify 里，所有 15 个节点**一次 forward 完成**（利用中间 state 缓存，每个节点从父节点的 state 出发）。开销约 = 线性 K=3 的 4x，但平均接受 token 数约 3.2x（线性链 1.875x）。

**净收益为正**。

---

### 一句话总结

> 线性链是单线押注，拒一个全输；树形是并行下注，多条路径同时验证，任何一条对就赢——代价只是一次稍胖的 forward，收益是大幅提升每步输出 token 数。

## 可行性分析

### 哪里"简单"

**对标准 attention（8层）**：每条序列是独立 batch element，正常扩 batch_size，不需要 custom_mask，代码几乎不用改。

**对 SimpleGLA（24层）**：每条序列从**相同的 committed state** 出发，各自独立地递推，不需要 parent-state 路由。

```python
# 当前 TARGET_VERIFY（线性链）:
initial_state → step0 → step1 → step2 → step3

# 并行多序列:
initial_state → [seqA_step0 → seqA_step1 → seqA_step2 → seqA_step3]
                [seqB_step0 → seqB_step1 → seqB_step2 → seqB_step3]
                [seqC_step0 → seqC_step1 → seqC_step2 → seqC_step3]
```

**每条链仍然线性递推**，不需要树形的 parent-state 跳转。这是关键——SimpleGLA 的修改量**极小**。

### 哪里"麻烦"

**问题1：序列从哪里来？**

如果3条序列由同一个 head 生成（greedy），它们都是同一个 token，没意义。必须来自不同来源：
- 方案A：同一个 head 的 top-1/top-2/top-3（等价于 topk=3 但不建树，只取线性链）
- 方案B：不同的 head 预测同一个 depth（每个 head 预测下一个 token，独立成链）
- 方案C：temperature sampling 生成多条（有随机性）

**方案B 最适合 Medusa**：3 个 head 各预测 d0，选各自 top-1，形成 3 条独立链：

```
head0 → [d0_h0, d1_h0, d2_h0]  (head_i 预测 depth_i 的 top1)
head1 → [d0_h1, d1_h1, d2_h1]  (重新训练：head_i 也预测 depth 0)
head2 → [d0_h2, d1_h2, d2_h2]
```

但这需要**重新设计 head 的职责**，不再是"head_i 预测 depth_i"，而是"N个 head 各自独立预测完整序列"。训练目标变了。

**问题2：开销是线性的，收益是亚线性的**

```
N 条序列 × K+1 tokens = N×(K+1) tokens per forward

但接受的 token 数 ≤ K+1（最多取最好的一条）
```

举例：N=3，K=3，每 head 接受率 50%：
- 单链期望：1 + 0.5 + 0.25 + 0.125 = **1.875**
- 3条并行，取最好：P(至少一条接受d0) = 1-0.5³ = 87.5%，但 d1 的接受要求 d0 也对，条件概率更复杂
- 实际期望约 **2.5-3.0**，但 forward 代价 = 3倍

净收益：`3.0 / 3.0 = 1.0x`——**几乎没有加速**！

### 为什么树形更高效

```
树形（topk=2, K=3）: 15个节点，1次 forward
期望接受: ~3.2 tokens

并行3链（K=3）: 12个节点，1次 forward  
期望接受: ~2.5 tokens（但代价相同数量级）
```

树形更好是因为：**树的不同路径共享前缀的计算**（d0_a 的 GLA state 被 d1_aa 和 d1_ab 复用），并行多链**完全不共享**（3条链各算各的）。

## 但有一个场景你的方案确实有价值

**"宽而浅"的验证**：只验证 depth=1（下一个 token），但验证多个候选。

```
候选: [d0_a, d0_b, d0_c, d0_d, d0_e]  ← 5个候选
目标验证: 哪个候选 == 目标预测的 next token

forward: verified + 5个候选 = 6 tokens
期望：P(任一命中) = 1 - (1-p)^5，p=token概率
```

**这等价于 top-K 采样验证**，代价很低（6 tokens），接受率可以很高（如果 top-5 能覆盖 90% 概率质量）。

缺点：每步最多只接受 1 个 token，没有"链式加速"。

| 方案 | 实现难度 | SimpleGLA改动 | 预期加速比 |
|------|------|------|------|

## 37% 接受率下的数学

### 线性链期望 token/step

```
p = 0.37

K=1: 1 + 0.37                         = 1.370
K=2: 1 + 0.37 + 0.137                 = 1.507
K=3: 1 + 0.37 + 0.137 + 0.051        = 1.558
K=5: 1 + 0.37 + ... + 0.007          = 1.584
K=∞:                                   = 1.587  ← 极限
```

**增量收益**：K=1→K=3 多 0.19 token/step，K=3→K=∞ 多 0.03 token/step。K=3 之后基本枯竭。

### 和开销对比

从实测推算：K=1（验证 2 token）开销约 1.12x 单 decode。  
假设每增加 1 token 开销 +0.06x（SALA 带宽限制，固定开销大）：

| K | 验证 token 数 | 开销估算 | E[token] | 解码加速比 |
|---|---|---|---|---|
| 0 | 1 | 1.00x | 1.00 | 1.00x |
| 1 | 2 | 1.12x | 1.37 | **1.22x** |
| 2 | 3 | 1.18x | 1.51 | **1.28x** |
| 3 | 4 | 1.24x | 1.56 | **1.26x** |
| 5 | 6 | 1.36x | 1.58 | 1.16x |

**甜点在 K=2～3，加速比 1.26～1.28x。**  
K=3 之后边际接受收益 < 边际开销增加，继续加深是反效果。

---

### 树形在 37% 下值得吗？

树形 topk=2, K=3（15 个节点）：

```
每层接受率: 1 - (1-0.37)^2 = 60.3%
E[token] = 1 + 0.603 + 0.364 + 0.220 = 2.19
验证开销: 1 + 14×0.06 = 1.84x
解码加速比: 2.19 / 1.84 = 1.19x
```

**结论：树形 topk=2 K=3 比线性链 K=2（1.28x）还差！**

原因：15个节点的开销涨幅（14个额外token）远超接受率从1.51提升到2.19的收益。

树形在高接受率下才划算。**p=37% 时树形的盈亏平衡点大约在 topk=1（即退化成线性链）。**

```
树形盈利需要: E[token_tree] / overhead_tree > E[token_linear] / overhead_linear

topk=2 K=3 两边比值: 2.19/1.84 = 1.19  vs  1.51/1.18 = 1.28

树形亏损。要让树形 > 线性，需 p ≥ 55% 左右。
```

## 根因：Medusa 破坏了草稿的因果一致性

### Medusa 的架构缺陷

所有 head 从**同一个 hidden state**（上一个已确认 token）出发：

```
已确认序列: [..., A]
hidden_state = target_model(A)

Head_0: P(B | hidden_state)       → 预测 B = "nice"
Head_1: P(C | hidden_state)       → 预测 C = ???
Head_2: P(D | hidden_state)       → 预测 D = ???
```

**Head_1 预测 C 时，它不知道 B 是什么。**

它实际上在计算的是：

```
Head_1 ≈ E_{B}[P(C | A, B)]   ← 对所有可能的 B 取期望
```

这是对所有可能下一个 token 的**边缘分布**，不是条件分布。

---

### EAGLE 的正确方式

EAGLE 的 draft model 是**自回归的**：

```
Step 1: 从 hidden_state(A) 预测 d0 = "nice"
Step 2: 从 hidden_state("nice") 预测 d1 = "today"   ← 知道 d0 是 "nice"！
Step 3: 从 hidden_state("today") 预测 d2 = "it's"   ← 知道 d0,d1！
```

EAGLE 预测的是真实条件分布：`P(d_k | A, d_0, d_1, ..., d_{k-1})`

---

### 用一个具体例子说明差距

上文是 "The weather is"，目标模型分布：

```
P("nice" | context) = 60%
P("bad"  | context) = 30%
P("hot"  | context) = 10%

P("today" | context, "nice") = 80%   ← 条件概率，差异很大
P("today" | context, "bad")  = 5%
P("day"   | context, "nice") = 15%
P("day"   | context, "bad")  = 70%
```

**Medusa Head_1 看到的**（没有 d0 的信息）：
```
P("today") ≈ 0.6×80% + 0.3×5% + 0.1×? ≈ 49.5%
P("day")   ≈ 0.6×15% + 0.3×70% + ...  ≈ 30%

Head_1 预测 "today"（最高概率）
```

**场景：d0="nice" 被接受了（60%概率），target 验证 d1：**
- Target 看到 "nice"，预测 P("today" | "nice") = 80%
- Medusa 预测的是 "today"（基于边缘分布 49.5%）
- 这次恰好对了，但 head_1 预测到的是"平均情况"

**场景：d0="bad" 被接受了（30%概率），target 验证 d1：**
- Target 看到 "bad"，预测 P("day" | "bad") = 70%
- Medusa 仍然预测 "today"（因为边缘分布更高）
- **但正确答案是 "day" → 接受率暴跌**

---

### 接受率的数学本质

设每步真实接受率为 $p$，草稿质量缺陷系数为 $\delta < 1$：

| 方案 | 深度 k 的接受率 | 原因 |
|------|------|------|
| EAGLE | $p^k$ | 每步正确条件化，误差不累积 |
| Medusa | $p^k \times \delta^{k-1}$ | 每多一步，多一层条件缺失的惩罚 |

Medusa 的 $\delta$：head_k 看不到 head_0..k-1 的预测，相当于用错误的条件分布预测，**系统性低估了正确 token 的概率**。

实测：
```
EAGLE 典型接受率：70-85%/step
Medusa 典型接受率：30-50%/step（我们测到 37%）

差距来源：δ 累积效应，层数越深越明显
```

---

### EAGLE 为什么还不够，EAGLE3 再进一步

EAGLE 用的 hidden state 是**最后一层**的输出（before norm）。但最后一层的 hidden state 已经被 layernorm、残差等压缩过，信息损失。

EAGLE3 用**3个不同层**的 hidden state 拼接（通常是 last, last-2, last-4 层），给 draft model 更多语义层级的信息：
- 浅层：词法/语法信息
- 中层：语义信息  
- 深层：预测意图信息

效果：EAGLE3 在 LLaMA 上接受率比 EAGLE 提升 5-10 个百分点。

---

### 对 SALA 的启示

EAGLE3 之前失败的原因不是算法，而是训练数据对不上（BF16 target 收集的 hidden states vs NVFP4 推理时的 hidden states 有分布偏移）。

如果用 NVFP4 target 重新收集 hidden states 训练 EAGLE3：

```
预期接受率: 60-80%（vs Medusa 37%）

K=5 步 EAGLE3 期望:
  p=0.70: 1 + 0.7 + 0.49 + 0.34 + 0.24 + 0.17 = 2.94 token/step
  p=0.80: 1 + 0.8 + 0.64 + 0.51 + 0.41 + 0.33 = 3.69 token/step

vs 当前 Medusa K=1: 1.37 token/step
```

这就是为什么 EAGLE3 的上限比 Medusa 高得多：**不是参数量，是信息完整性**。

---

**一句话**：Medusa 每个 head 预测时"不知道"其他 head 预测了什么，用的是边缘分布而非条件分布，天花板就在那里。EAGLE 维持了草稿序列内部的因果链，接受率的瓶颈只是 draft model 的表达能力，而不是结构性缺陷。

## EAGLE Draft Head 结构设计

### 核心设计约束

Draft head 必须满足：
1. **轻量**：推理开销 << target model，否则加速失去意义
2. **自回归**：每步能看到前一步的 token embedding（这是 vs Medusa 的本质差异）
3. **接受 target hidden state**：融合目标模型的"意图"信息

---

### EAGLE（原版）结构

```
输入: [token_embedding(d_{t-1}) ‖ hidden_state_{L}(d_{t-1})]
            ↓
         fc 层: concat → hidden_size
            ↓
      1个 Transformer Decoder Layer
      (自注意力 + FFN，带 KV cache)
            ↓
         lm_head（共享 target 的 lm_head）
            ↓
         logits → top-k 采样 → d_t
```

关键点：
- **只有 1 层** Transformer，参数量 ~200-500MB（取决于 hidden size）
- 输入是 `2 × hidden_size` 的拼接（上一步 embedding + 上一步 hidden state）
- lm_head **共享** target model 的，不额外训练
- KV cache 完整支持（标准 attention，不是 Lightning Attention）

---

### EAGLE3（当前 SGLang 实现）结构

从 `llama_eagle3.py` 读出的实际实现：

```python
self.fc = Linear(hidden_size_in * 3, hidden_size)   # 3层hidden拼接
self.midlayer = LlamaDecoderLayer(...)               # 1个标准Transformer层
self.norm = RMSNorm(hidden_size)
```

```
输入: [hidden_{L}(t) ‖ hidden_{L-i}(t) ‖ hidden_{L-j}(t)]
      ← target model 3个不同深度层的hidden state
            ↓
         fc: 3×H → H
            ↓
   concat [token_embed(d_{t-1}), fc_out]
            ↓
   LlamaDecoderLayer（自注意力 + FFN）
            ↓
   RMSNorm
            ↓
   lm_head（共享或独立，视配置）
            ↓
   logits → d_t
```

EAGLE3 的改进：用 **3层 hidden state 替代 1层**，给 draft model 更多语义层次。

---

### draft head 的 Decoder Layer 内部

这是标准 Transformer 结构，但有两处特殊：

```
输入 x = [embed(d_{t-1}) ‖ fc(hidden_states_concat)]

self_attn(x):
  Q, K, V 来自 x（2H 输入，Q/K/V proj 输入维度是 2H）
  标准 causal attention（有 KV cache）
  ← 注意：QKV proj 的输入维度是 2×hidden_size

MLP(x):
  标准 FFN，intermediate_size 通常 = target 的 intermediate_size

hidden_norm(hidden_states)   ← 对 fc(hidden_states) 额外 norm
```

**QKV 输入维度 = 2H** 是 EAGLE 独特设计：
- 普通 Transformer：QKV proj 输入 H → 输出 H
- EAGLE：QKV proj 输入 2H（embedding + hidden state 的拼接）→ 输出 H
- 原因：让 attention 能同时感知 token identity 和 hidden state 信息

---

### 参数量估算（以 SALA 为例）

```
hidden_size H = 4096
intermediate_size = 16384

fc 层:     3×4096 × 4096          = 50M  参数
QKV proj:  4096×2 × (32+2+2)×128  = 95M  参数（QKV）
O proj:    32×128 × 4096          = 17M  参数
FFN:       4096 × 16384 × 2       = 134M 参数（gate+up+down）
RMSNorm:   4096                   ≈ 0
lm_head:   共享 target → 0（或 73448×4096 ≈ 300M 独立）

总计（共享 lm_head）: ~296M
总计（独立 lm_head）: ~596M
```

**远低于 2GB 限制**，满足提交要求。

---

### 三种变体对比

| 变体 | 输入信息 | 层数 | 接受率 |
|------|------|------|------|
| EAGLE | embed + 最后1层hidden | 1 | ~70% |
| EAGLE2 | embed + 最后1层hidden | 1 + 动态树剪枝 | ~75% |
| EAGLE3 | embed + 3层hidden | 1 | ~80-85% |
| Medusa | 只有最后1层hidden（无embed） | ResBlock×K | ~37% |

---

### 为什么 1 层就够？

直觉：draft head 不需要"理解"语言，只需要**在 target 的语义空间里外推一步**。Target 已经做了 32 层的深度推理，hidden state 已经携带了下一个 token 的大部分信息。Draft head 只需要：

```
"target 在这个 hidden state 下会预测什么 token"
```

1 层带 attention 的 Transformer 足以学会这个映射。加更多层参数量暴涨，但边际收益很小，且推理开销增加。

---

### 对 SALA 的适配要点

SALA 用 SimpleGLA（不是标准 attention），但 **draft head 内部完全可以用标准 attention**，因为它是独立的小模型，不需要复用 SALA 的注意力机制。

具体适配：
1. `fc` 输入：`4096 × 3 = 12288`（SALA H=4096，取3层）
2. `midlayer`：标准 LlamaDecoderLayer（有 KV cache，不是 GLA）
3. `lm_head`：**必须从 NVFP4 量化后的 target 获取**，不能用 BF16 原始权重

第3点是上次 EAGLE3 失败（~0% 接受）的根因——lm_head 的 embedding 空间与 NVFP4 target 的 hidden state 空间不对齐。
