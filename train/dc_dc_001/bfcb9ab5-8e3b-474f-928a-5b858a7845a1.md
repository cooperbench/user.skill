根据代码库的全面搜索，结论如下： --- ## Marlin 本身**没有** autotune 机制 Marlin kernel（W4A16 GPTQ）是一个**手工调过的 CUDA kernel**，内部 tile / thread block 配置是写死的： - `tile_size = 16` - `min_n_threads = 64`，`min_k_threads = 128` - `max_parallel = 16`（控制多 threadblock 并行归约） 它没有运行时 tactic 选择或离线 tune 的逻辑——kernel 的 tile 大小、pipeline stages、schedule 全部在编译时固定。Marlin 的设计哲学是：**针对 decode 小 M 场景手写一个高度优化的 kernel，让它在 L2 bandwidth 上跑满**（实测 82-97% L2 BW 饱和），而不是做通用的多候选搜索。 --- ## 有 autotune 的是 CUTLASS NVFP4（flashinfer mm_fp4） 项目里的 autotune 机制属于 **flashinfer 的 `mm_fp4(backend="cutlass")` 路径**，不是 Marlin： ### 机制 1. **候选池**：flashinfer PR #2460 为 sm_120 编译了 **6 个 tactic**（3 tile × 2 schedule）： - `128×128×128 DP/StreamK` - `128×128×256 DP/StreamK` - `256×128×128 DP/StreamK` 2. **离线 tune**（`demo-sala/tune_mm_fp4_sm120.py`）： - 对每个 (layer shape, M bucket) 组合跑全部 6 tactic - **A 策略**：加大 profiling 量（`warmup=20, repeat=100`，10× 默认） - **B 策略**：per-config validate，只有 `tuned < baseline × 0.97` 才入库（KEEP_MARGIN=3%），保证单调不回归 3. **产物**：`demo-sala/assets/mm_fp4_tune_sm120.json`（43 条入库 / 70 total） 4. **运行时加载**：`modelopt_quant.py` 导入时读 `SGLANG_FP4_TUNE_CACHE` 环境变量 → `AutoTuner.get().load_configs(path)`。cache hit 走 tuned tactic，miss 走 tactic=-1 fallback ### 收益 最显著的是 **down_proj 层**：13/14 个 M bucket 入库，M=64 达到 **3.59×**，M=128 达到 **3.55×**。但由于 `SGLANG_MARLIN_DECODE_THRESHOLD=48`，decode 小 M ≤ 48 仍走 Marlin，autotune 增益主要在 EAGLE verify（M≈256）和高并发场景兑现。 --- **总结**：Marlin = 固定 tile 手工优化，没有 autotune；CUTLASS NVFP4 = 6 tactic 离线 autotune + JSON cache + runtime load。两者通过 `SGLANG_MARLIN_DECODE_THRESHOLD` 按 M 大小分流。

数据已经非常清楚了。直接给结论： --- ## 结论：**ROI 极低，不建议做** ### 原因一：Marlin 小 M 已经撞墙 —— 带宽墙 文档 `kernels-sm120.md` §6 明确记录：Marlin 在 decode 热形状（M=1~48）已实测 **82-97% L2 带宽饱和**。这是 W4A16 的物理天花板 —— 小 M 下 GEMM 完全是 memory-bound，计算不是瓶颈。即使用 sm_120 原生指令重写，也只是换一种方式把同一条带宽管道跑满，不可能比 97% 饱和更好。 ### 原因二：sm_120 的新能力帮不到 W4A16 sm_120 相对旧架构的计算增强集中在： | sm_120 新能力 | 是否利于 W4A16 | 原因 | |---|---|---| | FP4 block-scaled MMA `m16n8k64`（1467 TFLOPS peak） | **否** | 这是 W4A4 指令，W4A16 用 BF16 MMA `m16n8k16`（~400 TFLOPS） | | Cluster / distributed shared memory | **否** | sm_120 无 distributed smem（`no programmatic multicast on this arch`） | | TMA | 理论有帮助 | 但 decode 小 M 的 weight tile 就是 L2 读一次，TMA 省的是地址计算延迟，对带宽瓶颈无实质改善 | | 更大 L2 cache | 已被 Marlin 利用 | 82-97% 说明已经在吃满 | ### 原因三：已经有更好的替代路径 当前 **三档 dispatch** 已经把每个 M 区间分给了最优 backend： ``` M ≤ 8~24 → Marlin W4A16 （带宽饱和，无可挤） M ∈ (8~24, 256] → b12x W4A4 （比 Marlin 省 32.4% kernel 时间） M > 256 → tuned CUTLASS W4A4（autotune 3.5× on down_proj） ``` b12x 已经在 M=16~256 区间全面超越 Marlin（std_o M=48 Marlin 30.8us → b12x 10.2us，**3× 差距**）。真正值得投入的方向是继续优化 b12x 和 CUTLASS 路径（还有 2.6× 到 peak 的空间），而不是回去改 Marlin。 ### 如果一定要做 唯一有微弱可能的方向是用 **TMA async + software pipelining** 重写 Marlin 的 weight load 路径，把 M=1 场景从 L2 BW 97% 推到接近 100%。但： - 绝对收益约 3% kernel 时间（从 16.5us → ~16us） - 乘以 decode GEMM 在 e2e 中的占比 → 不到 0.1% 的 e2e 吞吐改善 - 开发成本：从零手写 PTX/CUTLASS 级别的 W4A16 kernel，至少数周 **收益/成本比远不如继续挤 CUTLASS W4A4 路径**（§7.2 的 30-40 候选编译扫描，或 §7.3 的 epilogue fusion），那些方向面对的是 2.6× 到 peak 的空间。
