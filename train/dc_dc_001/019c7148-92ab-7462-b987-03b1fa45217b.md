两个脚本“逻辑上”做的是同一件事（160³ patch + 高斯加权拼回整幅体数据 + 5-fold ensemble + 同一套后处理），但它们**数值路径不一样**，而你的后处理里有**硬阈值 + 非线性连通扩张**，所以哪怕概率图只差到 1e-3 量级，也足以让最终二值 mask 变一点点，LB 就会从 57.1 跳到 57.2。 **最可能导致 57.1 vs 57.2 的核心差异（会真实改变输出）** - **softmax 精度不同** - `57.1` 强制用 FP32 做 softmax：`torch.softmax(logits.float(), ...)`（`/user_0a329be7/Downloads/kaggle/57.1.ipynb.code.py:356`） - `57.2` 直接对 AMP 下的 `logits` 做 softmax（通常是 FP16），而且马上把概率转成 FP16：`prob = torch.softmax(logits, ...)` + `prob.to(torch.float16)`（`/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:297`、`/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:298`） 这一步就会引入明显的量化/舍入差异（FP16 在 0~1 附近的分辨率大概就是 1e-3）。 - **57.2 用 float16 落盘累计 fold 概率和（并且每个 fold 都会“读 float16 → 加 → 再写回 float16”）** - `PROB_SUM_DTYPE = np.float16`（`/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:92`） - 每个 fold 更新：`mm[:] = (...) .astype(PROB_SUM_DTYPE)`（`/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:414`） 这等价于把“5 折求和”的中间结果反复量化；最后再除以 5（`/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:430`）。这会把最终 `prob_mean` 的粒度也推到 ~1e-3 级别。 - **patch 分配/累加顺序更不确定（会放大浮点“加法不结合律”的差异）** - `57.1` 用 `patch_idx % 2` 固定把 patch 分到 GPU0/1（`/user_0a329be7/Downloads/kaggle/57.1.ipynb.code.py:369`），顺序基本固定。 - `57.2` 用线程 + 队列抢任务（`/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:328` 起），哪个 GPU 处理哪个 patch、局部累加顺序更依赖调度；再叠加 `TF32=True`、`cudnn.benchmark=True`，这种“微小数值抖动”更常见。 **为什么这些 1e-3 级别的差异会变成分数差异** - 你的后处理是：`clear3 -> hyst(0.90/0.50) -> z_close(1) -> rm(100)`。其中 hysteresis 的 **0.90 / 0.50 是硬门槛**：概率从 0.8996 变 0.9004 这种级别的变化，就可能让某些体素从“弱/非种子”变成“强种子”，再被 `binary_propagation` 扩张成一片区域；后面的 close / remove_small 又会进一步产生非线性连锁变化。 - 所以 `57.2` 里“FP16 softmax + FP16 memmap 累加”的量化误差，完全可能把 mask 边界推来推去一点点，最后 LB 就差 0.1。 **如果你想验证“到底是哪一个因素在贡献这 0.1”** - 最快的消融顺序通常是：先把 `/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:297-298` 改成“softmax 用 FP32 且不落 FP16 prob”，再把 `/user_0a329be7/Downloads/kaggle/57.2.ipynb.code.py:92` 的 `PROB_SUM_DTYPE` 改成 `np.float32`（或至少“fold 全加完再 cast 一次”），看分数是否回到接近 57.1。 - 如果这样一改分数就对齐了，基本就坐实是 **FP16 量化/舍入 + 阈值敏感** 在驱动那 0.1。
