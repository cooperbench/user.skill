**本地结论**
- v2 是当前生产 draft：`eagle/sglang_model/`，数据是 20K × 2048 tok，老配比，aux `[1,10,22]`，32K draft vocab，loss 是 `plogp / KL-style CE`，没有 response-only mask 也没有 chat template；长上下文问题主要是训练分布与线上 50K-130K 偏移。[training-v2.md](/user_4813494d/openbmb/docs/eagle/training-v2.md:1), [training-v2.md](/user_4813494d/openbmb/docs/eagle/training-v2.md:7), [training-v2.md](/user_4813494d/openbmb/docs/eagle/training-v2.md:90)
- v3 做了三件事：aux 改 `[4,9,24]`、NVFP4 aux storage、200K × 2K 数据；但本地文档明确说 v3 在 long deepresearch 上劣于 v2，所以“短序列 probe CE 更低”没有转化为 e2e acceptance。[training-v3.md](/user_4813494d/openbmb/docs/eagle/training-v3.md:7), [training-v3.md](/user_4813494d/openbmb/docs/eagle/training-v3.md:28), [training-v3.md](/user_4813494d/openbmb/docs/eagle/training-v3.md:47), [training-v4.md](/user_4813494d/openbmb/docs/eagle/training-v4.md:3)
- 当前 `eagle/train.py` 是 v3 训练脚本：TTT=5、loss decay=0.8、batch effective=12，`_build_target_p()` 只把 target top-K logits scatter 到 32K draft vocab，loss 只 mask “target argmax in draft vocab”。[train.py](/user_4813494d/openbmb/eagle/train.py:54), [train.py](/user_4813494d/openbmb/eagle/train.py:383), [train.py](/user_4813494d/openbmb/eagle/train.py:489), [train.py](/user_4813494d/openbmb/eagle/train.py:497)
- v4 方向已经更贴近问题：锁回 v2 aux/data/bf16，引入 AOI、LK^lambda、response-only mask、cross-doc mask、force include `{0,73440,73441}`。但当前 v4 smoke 只跑到 2K short shards，8K+ collect 仍被 server OOM 阻塞。[training-v4.md](/user_4813494d/openbmb/docs/eagle/training-v4.md:9), [training-v4.md](/user_4813494d/openbmb/docs/eagle/training-v4.md:264), [training-v4.md](/user_4813494d/openbmb/docs/eagle/training-v4.md:308)
- 采集侧 target top-K 当前由 hook 控制：默认 256，但 v3/v4 启动脚本设为 128；这会影响 target distribution 近似质量，尤其 LK/TV 类 loss 对尾部分布更敏感。[minicpm.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py:361), [minicpm.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py:415), [start_collect.sh](/user_4813494d/openbmb/eagle/start_collect.sh:22), [start_collect_v4.sh](/user_4813494d/openbmb/eagle/train_v4/start_collect_v4.sh:17)

**外部方法判断**
- EAGLE-3 的核心是放弃 feature prediction，改 direct token prediction + multi-layer fusion + training-time test；这支持我们继续沿 EAGLE-3 训练目标做数据/loss/position 修正，而不是回 EAGLE/EAGLE-2。外部：EAGLE、EAGLE-2、EAGLE-3。
- LongSpec 直接命中长上下文 SD 痛点：短上下文训练导致长上下文 inference mismatch，并提出 novel position indices；v4 的 AOI 是正确优先级。外部：LongSpec。
- LK Losses 是 P0：直接优化 acceptance，替代 KL，无额外 forward cost；v4 已实现 LK^lambda，但建议先做 `eta=3/5` 消融。外部：LK Losses。
- FR-Spec / vocab truncation 是 P1：我们已有 32K vocab 且覆盖高，但 16K/24K 可能降低 lm_head latency；必须用 assistant spans 统计，不能全 token 统计。外部：FR-Spec。
- GTO / DVI / AdaSPEC / VSD 更像 P2：潜在收益高，但成本或工程侵入大。GTO 适合 tree/topk>1 后；DVI 适合 train-with-decode/on-policy；AdaSPEC 要 reference model；VSD 需要 path/MCMC，复现风险最高。

**优先级**
1. P0：先补齐 v4 的可运行长上下文训练闭环。最小目标不是 5K full，而是 `2K/8K/16K` 都能 collect + train + eval。当前瓶颈在 collect 8K+ OOM 和 DECODE hook 不捕获 post-EOS aux。[collect_v4.py](/user_4813494d/openbmb/eagle/train_v4/pipeline/collect_v4.py:1), [training-v4.md](/user_4813494d/openbmb/docs/eagle/training-v4.md:310)
2. P0：把评测准则从 short CE/acc 改成长上下文 acceptance。v3 已证明 probe CE 误导；aux layer 搜索要用 8K/16K/32K step-0 accept 和 public accuracy 做裁判。[survey_draft_training_methods.md](/user_4813494d/openbmb/research/longspec/survey_draft_training_methods.md:24)
3. P0：response-only + chat template + forced special vocab 保留。v4 已实现 mask 和 forced vocab，应该作为基线，不再回 raw concat。[build_prompts_v4.py](/user_4813494d/openbmb/eagle/train_v4/pipeline/build_prompts_v4.py:70), [vocab_cache_v4.py](/user_4813494d/openbmb/eagle/train_v4/pipeline/vocab_cache_v4.py:1)
4. P1：target top-K 从 128 做到 256/512 消融。128 省盘但会扭曲 target_p，LK/TV 对分布支撑集更敏感。
5. P1：vocab K 做 16K/24K/32K，而不是直接降到 16K。以 assistant-only coverage、accept_len、draft step latency 三指标决策。
6. P2：response regeneration / train-with-decode。Speculators/TorchSpec 已有再生成和在线 hidden-state 方案，本地资料也指向这条路，但对当前 SALA 最先要解决 collect 长 shard 稳定性。[response_regeneration.md](/user_4813494d/openbmb/research/lk_loss/speculators/docs/user_guide/tutorials/response_regeneration.md:1), [sglang_qwen3_8b.yaml](/user_4813494d/openbmb/research/lk_loss/TorchSpec/configs/train_with_decode/sglang_qwen3_8b.yaml:1)

**实验矩阵**
| 组 | 变量 | 配置 | 判据 |
|---|---|---|---|
| A | baseline | v2 deployed draft | public eval accuracy + 2K/8K/16K/32K accept_len |
| B | data/mask | v2 aux + chat template + response-only + forced vocab | 看是否单独修复结构 token / user-token 噪声 |
| C | loss | B + KL vs LK eta=3 vs LK eta=5 | accept_len、ori_accuracy、step0 acc |
| D | position | C + no AOI vs AOI cap 144K/200K/524K | 16K+ accept，短上下文不退化 |
| E | length | 2K only vs 2K+8K+16K vs +32K/64K | 长上下文收益和 collect 成本 |
| F | aux | `[1,10,22]`, `[2,16,29]`, `[0,16,29]`, `[0,17,30]`, `[9,16,30]` | 训练 1-2K step 后长 ctx accept，不用 probe CE |
| G | vocab | 16K/24K/32K assistant-only frequency, force `{0,73440,73441}` | coverage ≥97-99%、lm_head ms、accept |
| H | top-K label | collect top-K 128/256/512 | loss 稳定性、target_p entropy、accept |
| I | TTT | steps 3/5，decay 0.8/0.7，必要时 COD 下采样 | speedup 是否覆盖 draft cost |
| J | on-policy | prompt-only target regeneration / train-with-decode 小样本 | 分布对齐收益，作为 v5 |
