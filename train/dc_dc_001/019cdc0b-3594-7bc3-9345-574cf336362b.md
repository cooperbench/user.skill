**现状拆解**
现在实际上有 3 层：

- 登录核心：[`/root/hust-network-login`](/root/hust-network-login)
  它负责探测是否被校园网劫持、提取 portal 参数、发登录请求、循环保活。
- 调度层：[`/root/hust_auto_login.sh`](/root/hust_auto_login.sh)
  它负责按时间选择白天/夜间账号，并杀旧进程、起新进程。
- 启动层：[`/etc/init.d/hust_login`](/etc/init.d/hust_login) + `cron`
  它们负责开机和整点触发调度脚本。

这套设计的问题不是“完全错”，而是：

- 登录逻辑已经在二进制里有循环保活，外面又套一层每小时 `cron`，职责重复。
- 开机既有 `init.d`，又有 `@reboot cron`，触发重复。
- PID 文件放在 `/tmp/hust_login.pid`，靠 shell 手工维护，稳健性一般。
- 配置文件分散在 `/root/config_day.conf`、[`/root/config_night.conf`](/root/config_night.conf)、[`/root/hust_login.conf`](/root/hust_login.conf)，语义不统一。
- 账号切换策略硬编码在脚本里，后续改时间段、改账号、加第三套配置都不方便。
- 日志全打到 `/tmp/hust_login.log`，重启易丢，定位问题不够系统。

**整理目标**
我建议收敛到这几个目标：

- 只保留一个真正的守护入口
- 只保留一种开机启动方式
- 配置集中管理
- 账号切换规则显式配置化
- 不再自己手搓 PID 管理
- 日志和状态可检查

**推荐方案**
最合适的是把 `hust_login` 改成标准 `procd` 服务，让它直接托管实际进程，而不是只去调用一个 shell。

方案结构可以是：

1. 一个统一配置文件  
   比如：
   - [`/etc/hust-login/day.conf`](/etc/hust-login/day.conf)
   - [`/etc/hust-login/night.conf`](/etc/hust-login/night.conf)
   - [`/etc/config/hust_login`](/etc/config/hust_login)

2. 一个“选择配置”的轻量脚本  
   只做一件事：根据当前时间返回该用哪个配置文件。  
   不负责杀进程，不负责后台化，不负责 PID。

3. 一个标准 `procd` 服务  
   服务启动时执行：
   ```sh
   /root/hust-network-login "$(choose_config)"
   ```
   由 `procd` 做：
   - 拉起
   - 崩溃重启
   - 状态管理
   - 停止服务

4. 一个定时“切换器”  
   如果必须白天夜间切账号，那定时器只需要在切换边界重启服务一次。
   不需要每小时执行。
   例如只在：
   - `08:00`
   - `00:00`
   触发 `service hust_login restart`

这样职责就清楚了：
- 二进制负责登录和保活
- 选择脚本负责选配置
- `procd` 负责进程生命周期
- `cron` 只负责在账号切换点触发重启

**具体改进点**
我建议按优先级这么做：

1. 去掉重复开机触发  
   保留 `init.d`，删掉 `@reboot /root/hust_auto_login.sh`。  
   这是最先该收敛的。

2. 去掉“每小时整点重跑”  
   如果二进制已经每 15 秒检测并自动重登，那 `0 * * * *` 大概率不是必须。  
   除非你确认校园网要求按整点强制换账号，否则应改成只在 `00:00` 和 `08:00` 切换。

3. 用 `procd` 替代 PID 文件  
   不再写 `/tmp/hust_login.pid`，不再手工 `kill`。

4. 统一配置目录  
   把账号文件从 `/root` 挪到例如 `/etc/hust-login/`，权限设为 `600`。  
   这样语义更清楚，也便于备份。

5. 把时间规则配置化  
   别把 `8-23` 写死在脚本里。  
   比如放进 UCI 或简单配置文件里。

6. 增加一个状态检查命令  
   比如单独做个 `hust_login status` 输出：
   - 当前时间段
   - 当前使用的配置文件
   - 当前进程 PID
   - 最近一次日志结果

**我对这套系统的判断**
如果你的真实需求是：

- 白天用一个账号
- 夜间用另一个账号
- 登录成功后持续保活
- 路由器重启后自动恢复

那最佳实现不是继续堆 shell，而是：

- 保留 `hust-network-login`

- 服务谁在管
- 配置在哪
- 为什么切换
- 出问题看哪

login ok的检测逻辑是什么？

> AGENT

`login ok` 不是“刚刚执行了登录接口”这个意思，而是“当前检测结果认为网络已经通了，所以这轮检查通过了”。

源码在 [`/root/hust-network-login-master/src/main.rs`](/root/hust-network-login-master/src/main.rs)，逻辑是：

1. 先请求 `http://www.baidu.com`
2. 读取返回内容
3. 判断返回里是否包含校园网认证劫持特征：
   - `/eportal/index.jsp`
   - `top.self.location.href='http://...`

分两种情况：

- 如果**不包含**这些劫持特征  
  代码直接 `return Ok(())`  
  也就是认为“已经联网，不需要重新认证”

- 如果**包含**这些劫持特征  
  说明当前未认证  
  它才会继续：
  - 提取 `portal ip`
  - 提取 `mac`
  - 提取 `query_string`
  - 向 `/eportal/InterFace.do?method=login` 发登录请求
  - 如果返回里包含 `success`，则 `Ok(())`
  - 否则报错

主循环里是：

- `Ok(_)` 时打印 `login ok. awaiting...`
- 然后睡 `15s`
- `Err(_)` 时打印 `error! ...`
- 然后睡 `1s`

所以你现在日志里的 `login ok. awaiting...`，含义更准确地说是：

- 要么已经在线，访问百度没有被校园网重定向
- 要么刚刚触发登录且返回 `success`

它**不是严格区分这两种情况**的，统一都记成 `login ok. awaiting...`。

如果你要，我可以继续帮你把这个检测逻辑讲得更底层一点，比如它为什么用百度、这种检测有哪些误判边界。
