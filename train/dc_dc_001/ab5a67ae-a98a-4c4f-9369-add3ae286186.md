"""
Simple model copy for MiniCPM-SALA submission demo.

Usage:
    python preprocess_model.py --input /path/to/model --output /path/to/output
"""
from __future__ import annotations

import argparse
import shutil
from pathlib import Path


def main() -> None:
    parser = argparse.ArgumentParser()
    parser.add_argument("--input", required=True)
    parser.add_argument("--output", required=True)
    args = parser.parse_args()

    src = Path(args.input).resolve()
    dst = Path(args.output).resolve()

    if not src.is_dir():
        raise FileNotFoundError(f"Input model dir not found: {src}")

    dst.mkdir(parents=True, exist_ok=True)

    count = 0
    for f in sorted(src.iterdir()):
        if f.name.startswith("."):
            continue
        target = dst / f.name
        if not target.exists():
            if f.is_dir():
                shutil.copytree(f, target)
            else:
                shutil.copy2(f, target)
            count += 1

    print(f"[preprocess] done — copied {count} files from {src} to {dst}")


if __name__ == "__main__":
    main()
```

# Bug Fixes — NVFP4 推理适配

## 1. infllm_v2
本地 `soar` conda 环境已经安装 `infllm_v2`，当前代码恢复成硬导入，不再保留
`try/except` 兼容分支。

需要说明的是：当前这条已验证的 NVFP4 推理路径并没有走 MiniCPM 的稀疏 attention
backend，所以实际推理时不会调用 `infllm_v2` 的两个 kernel。它只会在 MiniCPM
稀疏路径里参与 TopK 计算。

---

## 2. SGLang 不认识 `NVFP4_AWQ` 这个名字
**文件**：`srt/layers/quantization/modelopt_quant.py` — `ModelOptFp4Config.from_config`

modelopt 导出的量化算法名是 `NVFP4_AWQ`，SGLang 只认 `NVFP4`。
在做合法性检查前加一行：`if quant_method.startswith("NVFP4"): quant_method = "NVFP4"`。

---

## 3. AWQ 的 pre_quant_scale 完全没被支持（推理乱码根因）
**文件**：`srt/layers/quantization/modelopt_quant.py`

AWQ 量化时为了降低激活的量化误差，给每个 input channel 乘了一个平滑系数
（`pre_quant_scale`），并把其倒数吸收进了权重。推理时必须对激活乘回这个系数，
否则权重和激活完全对不上，输出是乱码数字。

原版 SGLang 完全不知道有这个东西，分三处修复：

- **`from_config`**：新增 `has_pre_quant_scale` 字段，同时解析嵌套格式
  （`hf_quant_config.json`）和扁平格式（`config.json`）里的 `pre_quant_scale`
- **`create_weights`**：当 `has_pre_quant_scale=True` 时注册对应 Parameter，
  初值全 1，由 weight_loader 从 checkpoint 加载实际值
- **`process_weights_after_loading`**：把 `pre_quant_scale` 转移到 CUDA 并转
  bfloat16（防止 CUDA Graph 设备不一致，防止乘后 dtype 升为 float32 导致
  fp4_quantize 报错）
- **`apply`**：`fp4_quantize` 之前先做 `x = x * layer.pre_quant_scale`

---

## 4. load_weights 对未知 tensor 抛 KeyError
**文件**：`srt/models/minicpm.py` — `MiniCPMSALAForCausalLM.load_weights`

量化 checkpoint 里可能有 SGLang 模型图里没注册的 tensor（比如各种辅助量化参数），
原版直接 `params_dict[name]` 会 KeyError。在默认分支加一行：
`if name not in params_dict: continue`。

---

## 5. config.json 缺 AWQ 元数据（乱码的另一半原因）
**文件**：`models/MiniCPM-SALA-NVFP4/config.json`（手动补丁）

SGLang 读的是 `config.json` 里的 `quantization_config`，但 modelopt 导出时这里
没有写 `pre_quant_scale: true`，导致 Bug 3 的修复完全不生效（`has_pre_quant_scale`
始终为 False）。手动补上后乱码消失，输出恢复正常。

修复后的字段：
```json
{
  "quant_algo": "NVFP4",
  "quant_method": "modelopt",
  "group_size": 16,
  "exclude_modules": ["lm_head"],
  "pre_quant_scale": true,
  "ignore": ["lm_head"]
}
```

---

## 6. 量化导出忘记还原 `max_position_embeddings` 和 `sparse_config`
**文件**：`quantize_nvfp4.py`

校准时需要两个临时修改：① 缩小 `max_position_embeddings` 防止 RoPE 缓存 OOM；
② `sparse_config = None` 防止 `infllm_v2` 在校准 forward pass 里被调用。
之前只恢复了 `max_position_embeddings`，忘了恢复 `sparse_config`，导致：

- 量化产物的 `sparse_config = None`
- SGLang 算出 `has_sparse_attention = False`
- 无法使用 `--attention-backend minicpm_flashinfer`（官方评测默认参数）
- 评测集 80% 的题目输入超过 8192 token，全都退回全量 attention，丧失
  InfLLM-v2 稀疏注意力带来的 20× 计算量压缩

现在导出前同时恢复两个值。

## 7. 技术路径参考

### 路径一：量化加速

**GPTQ W4A16 + Marlin Kernel + FP8 KV Cache**

- 权重量化为 4-bit（W4A16），用 Marlin 高性能 GEMM Kernel 加速
- KV Cache 量化为 FP8 减少 Decode 阶段带宽瓶颈
- Lightning Attention 层使用独立线性注意力状态，优化路径不同

关键文件：

| 文件 | 说明 |
|------|------|
| `srt/models/minicpm_sala.py` | SALA 模型定义 |
| `srt/model_loader/loader.py` | 权重加载与量化映射 |
| `srt/layers/quantization/gptq.py` | GPTQ 线性层与 Marlin 调度 |
| `srt/layers/quantization/__init__.py` | 量化方法注册表 |
| `srt/layers/linear.py` | 主 Linear 层，量化方法注入点 |
| `srt/layers/quantization/kv_cache.py` | KV Cache 量化逻辑 |

### 路径二：投机采样

**EAGLE3 多层 Draft Head**

- 轻量 Draft Head 利用隐藏状态预测候选 token，参数量极小（几十 MB）
- Lightning Attention 兼容性是核心挑战：递推计算不支持树状因果掩码
- `hybrid_linear_attn_backend.py` 中已有 `is_target_verify` 初步集成

关键文件：

| 文件 | 说明 |
|------|------|
| `srt/speculative/multi_layer_eagle_worker.py` | EAGLE3 Draft Worker 主循环 |
| `srt/speculative/eagle_info.py` | Verify/Draft 数据结构 |
| `srt/models/llama_eagle3.py` | LLaMA EAGLE3 参考模板 |
| `srt/layers/attention/hybrid_linear_attn_backend.py` | 混合线性注意力 Backend |

### demo-quant 参考（仅供流程验证）

- RTN W4A16 量化（group_size=1024），精度较差，不建议直接提交
- 权重需遵循 GPTQ 格式（`qweight`, `scales`, `qzeros`, `g_idx`）+ `quantize_config.json`
- 非量化层权重统一转为 float16
- 需 patch `minicpm_backend.py` 中 bfloat16 → float16
