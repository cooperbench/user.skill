### Motivation

We propose SPECTRE (Parallel **Spec**ulative Decoding with a Multi-**T**enant **Re**mote Drafter), a novel system architecture for Speculative Decoding in SGLang , inspired by recent parallel speculative-decoding efforts such as [Pearl](https://arxiv.org/abs/2408.11850) and [SSD](https://arxiv.org/abs/2603.03251). By decoupling the tightly-bound Drafter and Verifier into independent, asynchronously communicating SGLang services (via ZMQ), SPECTRE resolves the high sequential latency and poor resource utilization of traditional implementations through two core features:

**Cross-Round Parallel Overlap**: Breaking the strict, synchronous "draft-then-verify" loop that leads to low GPU utilization, SPECTRE employs optimistic concurrency control. Assuming high draft acceptance, the Drafter generates tokens for round k+1 concurrently while the Verifier validates round k. This completely overlaps the forward passes of both models and effectively hides drafting latency.

**Drafter Dual-Mode Coexistence**: Instead of dedicating an underutilized GPU solely to the Drafter, SPECTRE treats it as a multi-tenant service. It processes internal draft requests from the Verifier alongside its own standalone user traffic within the same continuous forward batch. This maximizes GPU utilization and drastically lowers the serving cost for production environments.

## Architecture Overview

To break free from this co-located synchronous trap, SPECTRE shifts speculative decoding into a **distributed, asynchronously coordinated pipeline**.

SPECTRE keeps both sides operationally familiar:

- The **Verifier** is a standard SGLang HTTP server that handles user requests and performs token verification with the large model. It acts as the authoritative serving endpoint.
- The **Drafter** is also a standard SGLang HTTP server. However, operating in **Dual-Mode**, it accepts remote draft-generation requests from the Verifier *in addition* to serving its own standalone traffic. Both traffic streams are mixed into the same GPU batch.
- The two sides communicate over **ZMQ**, with messages serialized as `SpectreRequest` objects through a C++ pybind11 transport layer.

## Protocol Design

All communication uses a `SpectreRequest` dataclass serialized through msgpack via the C++ ZMQ layer.

### Key fields


| Field              | Type            | Description                                                                                  |
| ------------------ | --------------- | -------------------------------------------------------------------------------------------- |
| `request_id`       | `str`           | SGLang request ID (`req.rid`)                                                                |
| `spec_cnt`         | `int`           | Per-request speculative round counter used to correlate messages and discard stale responses |
| `action`           | `SpectreAction` | `DRAFT`, `FINISH`, `ABORT`, or `REJECT`                                                      |
| `spec_type`        | `SpecType`      | `DRAFT_REQUEST` or `DRAFT_RESPONSE`                                                          |
| `draft_token_ids`  | `List[int]`     | Draft tokens proposed by the Drafter                                                         |
| `input_ids`        | `List[int]`     | Full prompt token IDs, sent on `spec_cnt == 0`                                               |
| `output_ids`       | `List[int]`     | Tokens generated so far                                                                      |
| `num_draft_tokens` | `int`           | Number of draft tokens requested by the Verifier                                             |


### Action semantics


| `SpectreAction` | Direction                                   | Meaning                                             |
| --------------- | ------------------------------------------- | --------------------------------------------------- |
| `DRAFT`         | Verifier -> Drafter and Drafter -> Verifier | Normal draft request / response                     |
| `FINISH`        | Verifier -> Drafter                         | Request completed normally; Drafter cleans up state |
| `ABORT`         | Verifier -> Drafter                         | Request aborted; Drafter cleans up state            |
| `REJECT`        | Drafter -> Verifier                         | Drafter is overloaded; Verifier should back off     |

## Transport Layer

### ZMQ transport selection

`SpectreConfig` chooses the transport automatically based on `--spectre-zmq-addr`:


| `zmq-addr` value         | Transport | Rationale                                                             |
| ------------------------ | --------- | --------------------------------------------------------------------- |
| `127.0.0.1` or `0.0.0.0` | **IPC**   | Avoids unnecessary network stack overhead for same-machine deployment |
| Any other IP             | **TCP**   | Enables cross-machine communication                                   |


### Socket roles

The current design uses:

- **Verifier**: binds a **Router** socket
- **Drafter**: connects with a **Dealer** socket

This choice keeps the Verifier in a coordination role and makes it possible to extend toward one-to-many topologies, where a single Verifier can talk to multiple Drafter instances.

That matters because SPECTRE is intended to scale outward cleanly. The transport is not just point-to-point glue; it is the foundation for a future multi-drafter deployment model.

### C++ transport layer

SPECTRE uses a C++ pybind11 extension for ZMQ plus msgpack serialization. This keeps message handling predictable and efficient in the serving path, avoiding Python-level control flow overhead for every transport operation. The communication layer is kept thin, explicit, and production-friendly — it is not an additional infrastructure dependency but a narrow binding on top of well-established primitives.

## Scheduling, Fault Tolerance, and State Management

### Circuit breaker on the Verifier

The Verifier maintains a `DraftCircuitBreaker` so that Drafter failures do not stall user-visible generation.


| State       | Behavior                                                                                                              |
| ----------- | --------------------------------------------------------------------------------------------------------------------- |
| `CLOSED`    | Normal operation. Draft requests are sent every round.                                                                |
| `OPEN`      | Too many consecutive timeouts. The Verifier falls back to single-token decoding for `SPECTRE_COOLDOWN_ROUNDS` rounds. |
| `HALF_OPEN` | Cooldown expired. One probe request is sent. Success returns to `CLOSED`; failure reopens the breaker.                |


This gives SPECTRE a critical operational property: when remote drafting is unhealthy, the system degrades to standard autoregressive decoding instead of amplifying latency or deadlocking progress. SPECTRE accelerates the happy path without holding the serving stack hostage to the remote path.

### Drafter scheduling modes

Because draft tokens are highly time-sensitive, the Drafter exposes two scheduling strategies.

**Mixed mode** (default):

- Draft requests are merged into the Drafter's normal running batch.
- This maximizes overall GPU utilization.
- It works well when Drafter load is light or moderate.
- It offers no strong isolation, so under heavy load the Verifier may see occasional timeouts.

**Draft-Priority mode** (`--spectre-draft-priority`):

- The Drafter runs a dedicated draft batch for up to `--spectre-max-draft-priority-steps` steps before serving normal requests each iteration.
- This bounds draft latency more tightly.
- It protects Verifier throughput when the Drafter is busy.
- The trade-off is slightly higher tail latency for the Drafter's ordinary user traffic.

This mode split reflects an actual serving trade-off rather than hiding it: SPECTRE can optimize for utilization or for speculative responsiveness, depending on deployment goals.

## Overview of PEARL

PEARL is a parallel inference framework based on speculative decoding which utilizes pre-verify and post-verify to achieve adaptive draft length.

## Framework Design

PEARL proposes pre-verify to verify the first draft token in advance during the drafting phase, and post-verify to generate more draft tokens during the verification phase. PEARL parallels the drafting phase and the verification phase via applying the two strategies, and achieves adaptive draft length for different scenarios, which effectively alleviates the mutual waiting problem.

The transport selection table in the RFC is binary: `127.0.0.1` → IPC (same machine), other IPs → TCP (cross machine). There is no "same GPU" path. The architecture diagram shows two separate boxes; the drafter even admits a "Dual-Mode" multi-tenant role serving its **own standalone user traffic** in addition to verifier draft requests — that only makes sense when the drafter has its own dedicated GPU.

Critically, the launch example pins `--disable-overlap-schedule` **on the drafter** (not the verifier). That flag turns off SGLang's CPU/GPU pipelining of consecutive batches. The drafter disables it because SPECTRE injects ZMQ-driven control flow into each forward step (request arrival, KV rollback via `spectre_kv_rollbacker.py`), which conflicts with the existing "run one batch ahead" overlap scheduler. This is a *scheduler-level* concern, not a *cross-process GPU sharing* mechanism.

## 2. Reference papers — what they actually claim

- **PEARL** ([arXiv:2408.11850](https://arxiv.org/abs/2408.11850), ICLR'25): for 1.3B/7B targets PEARL puts both models on a single A100 (later H800 in v2), but the paper explicitly admits *"it remains a challenge to schedule the GPU resources to avoid resource competitions"* and says they "implement the parallel algorithm in accelerate, which can be further optimized." There is **no CUDA-stream / MPS / concurrent-kernel mechanism** described — the "parallel" part is algorithmic (pre-verify + post-verify reordering to remove sync points), implemented with whatever overlap `accelerate` provides on one device, which is essentially serial kernel launch with marginal stream overlap. The downstream system [nano-PEARL](https://github.com/smart-lty/nano-PEARL) is explicitly **draft-target disaggregated**: "draft and target models loaded in separate devices, avoiding load-imbalance and resource competition," with a 2-GPU quickstart.
- **"Speculative Speculative Decoding"** at `arXiv:2603.03251` — `2603` = March 2026, which is a future-dated/likely fabricated arxiv ID (RFC's own caveat: "paper link: coming soon..."). The closest real work in the same space is **MineDraft** ([2603.18016](https://arxiv.org/html/2603.18016)) which is **explicitly multi-GPU** ("draft model on a separate GPU; target uses TP across GPUs separate from drafter") and uses **cross-batch ping-pong** (alternating Batch 0/Batch 1 roles), not cross-round overlap on one request.

**Conclusion:** every prior work SPECTRE cites that demonstrates real wallclock overlap relies on either (a) separate physical GPUs, or (b) workload imbalance large enough that draft kernels coexist trivially with verify kernels.

## 3. Single-GPU technical feasibility

On one CUDA context, two streams *can* run concurrent kernels only if the GPU has SM headroom. Decode-phase target verify on a 32B-class model (or your NVFP4 32-layer MiniCPM-SALA target) **saturates SMs at moderate batch sizes**; the drafter, a 1-layer NVFP4 EAGLE head, takes single-digit SMs and could in principle co-issue on a second stream — this is the only path SGLang itself is investigating ([sglang#9961 "Support overlap-schedule for eagle worker"](https://github.com/sgl-project/sglang/issues/9961), incompatible with DP attention / PD disagg / page_size=1, marked inactive). SPECTRE does **not** take this path — it is a *separate-process* design.

Two processes on one GPU without MPS serialize at the context level (round-robin time-slicing). With **MPS** ([NVIDIA MPS](https://docs.nvidia.com/deploy/mps/index.html)) two processes' streams multiplex onto SMs — but SGLang is reported to **hang under MPS** due to CUDA-graph capture incompatibility ([sglang#22192](https://github.com/sgl-project/sglang/issues/22192)). SPECTRE relies heavily on CUDA graphs (`cuda_graph_runner.py` integration with `spectre_ntpb_options`), so MPS is currently a non-starter for SGLang. Without MPS, two-process SPECTRE on one GPU runs the verifier and drafter **sequentially** — losing exactly the overlap the design is built around.

## 4. Speedup ceiling analysis (Amdahl)

Reported SPECTRE win is **1.76×** on Qwen3-32B verifier + Qwen3-0.6B drafter — both ≈40+ GB models, almost certainly on **distinct A100/H100s** (the RFC profile screenshots show two independent timelines). On your setup, **MiniCPM-SALA target ≈ 32 dense + GLA layers in NVFP4** vs **EAGLE-3 1-layer NVFP4 draft**. The draft head is roughly **2–4% of target FLOPs** (1/32 layers, plus an extra LM head pass). Even if perfectly hidden, Amdahl caps speedup at ~1.02–1.04×. SPECTRE's 1.76× comes from **0.6B/32B ≈ 1.9% per-token cost ratio but with ~3 draft steps per round** plus the dual-mode "drafter also serves real traffic" — i.e. it's hiding a *fat* drafter that would otherwise be wasting a whole GPU. On your 1-layer EAGLE draft, that motivation evaporates: the draft is already nearly free.

## 5. Single-GPU adaptations that *could* work

If you want intra-GPU draft/verify overlap on RTX 6000D, the realistic options are:
1. **Wait for sglang#9961 / #9334** intra-process overlap-schedule for EAGLE (target-batch-K runs on stream A while draft-batch-K+1 issues on stream B). This is the right shape for your setup, not SPECTRE.
2. **CUDA-graph-fused draft+verify** (already partially what EAGLE V2 worker does) — but co-issue, not cross-round optimistic concurrency.
3. **MPS-based two-process** is blocked by sglang#22192 today; unblocking would require disabling CUDA graphs (catastrophic for decode latency) or upstream graph-capture-under-MPS fixes.

## Bottom line

**SPECTRE is architected for two-GPU (or multi-machine) deployment.** The IPC vs TCP transport choice is *machine-locality* about CPU IPC, not GPU sharing. Co-locating both processes on a single RTX 6000D would (a) lose the kernel-level overlap (no MPS-safe path under SGLang's CUDA-graph stack), (b) double model weights into 84 GB VRAM, (c) yield at most ~3% theoretical headroom on a 32-layer-vs-1-layer split — way under the ZMQ + circuit-breaker + KV-rollback overhead. **Do not adopt SPECTRE for the single-GPU MiniCPM-SALA submission.** If draft-verify overlap is the actual goal, track [sglang#9961](https://github.com/sgl-project/sglang/issues/9961) / [PR #9334](https://github.com/sgl-project/sglang/pull/9334) (intra-process EAGLE overlap-schedule) instead — that is the single-GPU-shaped equivalent.
