SPECTRE RFC: explicit deployment posture The SPECTRE RFC ([sglang#22044](https://github.com/sgl-project/sglang/issues/22044)) and its implementation PR ([sglang#22272](https://github.com/sgl-project/sglang/pull/22272)) describe a **distributed, asynchronously coordinated pipeline** with two **independent SGLang HTTP servers** (Verifier + Drafter) communicating over **ZMQ** with msgpack via a C++ pybind11 transport. The launch example uses two `python -m sglang.launch_server` processes, each `--tp 1`, on distinct ports (3008, 30000), with `--spectre-zmq-addr 127.0.0.1` selecting **IPC** transport "for same-machine deployment" — but never a single CUDA context. The transport selection table in the RFC is binary: `127.0.0.1` → IPC (same machine), other IPs → TCP (cross machine). There is no "same GPU" path. The architecture diagram shows two separate boxes; the drafter even admits a "Dual-Mode" multi-tenant role serving its **own standalone user traffic** in addition to verifier draft requests — that only makes sense when the drafter has its own dedicated GPU. Critically, the launch example pins `--disable-overlap-schedule` **on the drafter** (not the verifier). That flag turns off SGLang's CPU/GPU pipelining of consecutive batches. The drafter disables it because SPECTRE injects ZMQ-driven control flow into each forward step (request arrival, KV rollback via `spectre_kv_rollbacker.py`), which conflicts with the existing "run one batch ahead" overlap scheduler. This is a *scheduler-level* concern, not a *cross-process GPU sharing* mechanism. ## 2.
