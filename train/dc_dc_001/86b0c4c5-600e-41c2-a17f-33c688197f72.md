Reset HybridReqToTokenPool 这个怎么理解？

> AGENT

`Reset HybridReqToTokenPool` 是 SGLang 内部 **把"请求 → token 槽位"的映射池整个清空重置** 的动作，几乎总是由 `/flush_cache` 触发的。可以拆成三部分理解： **1. `ReqToTokenPool` 是什么** SGLang 用一张二维表维护"每个 request 占用了哪些 token slot（KV cache 的物理位置）"： - 行 = request 槽位（`req_pool_indices`） - 列 = 该请求当前的 token 序列 → 指向 KV cache pool 里的具体位置 decode 每生成一个 token，就在这张表里追加一格；请求结束时归还槽位。 **2. `Hybrid` 前缀的含义** 你跑的是 **hybrid 架构模型（Transformer 注意力层 + Mamba/SSM 层）**。两类层的"状态"形态不同： - 注意力层：标准 KV cache（按 token 存） - Mamba 层：SSM state（按层存一份压缩状态，不随 token 数线性增长） 所以 SGLang 用的是 `HybridReqToTokenPool`，同时管理这两种状态的槽位映射，而不是普通的 `ReqToTokenPool`。日志里你也能看到 `full token usage`（KV）和 `mamba usage`（SSM）两个独立指标，对应的就是这两块。 **3. `Reset` 在做什么** 把整张映射表清零：所有 req 槽位标记为空闲、所有指向 KV / Mamba state 的指针失效。等价于"忘记之前所有请求占用过哪里"，配合 KV pool 自身的清空，实现 `Cache flushed successfully!`。 **触发时机** - 显式调 `/flush_cache`（你这次就是） - 切换 LoRA / 重新加载权重等需要彻底清状态的场景 - 内部检测到状态不一致时的兜底 **影响** 重置之后 prefix cache 全没了，下一次请求必然 `#cached-token: 0`，要从头 prefill —— 这也解释了为什么你 flush 之后那批 `/generate` 没法复用前面那 130K 的 prompt 缓存。如果你的工作流是"长 prompt + 多次小改动续聊"，频繁 flush 会让每次都重算 prefill，代价很大。
