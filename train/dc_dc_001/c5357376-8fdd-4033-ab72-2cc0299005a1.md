---

## DeepLX 是什么

**DeepLX** 是一个用 **Go** 写的 **HTTP 翻译服务**：本机起一个 API，把请求转发到 DeepL 网页端使用的 **`https://www2.deepl.com/jsonrpc`**（`LMT_handle_texts`），从而让你像调用 API 一样翻译，而不必直接买官方 API。

入口很薄：读配置、开 Gin、监听端口。

```23:34:/home/user_0a329be7/Downloads/DeepLX/main.go
func main() {
	cfg := service.InitConfig()

	fmt.Printf("DeepL X has been successfully launched! Listening on %v:%v\n", cfg.IP, cfg.Port)
	fmt.Println("Developed by sjlleo <i@leo.moe> and missuo <[REDACTED]>.")

	// Setting the application to release mode
	gin.SetMode(gin.ReleaseMode)

	app := service.Router(cfg)
	app.Run(fmt.Sprintf("%v:%v", cfg.IP, cfg.Port))
}
```

---

## 代码结构（大致分工）

| 路径 | 作用 |
|------|------|
| `main.go` | 程序入口 |
| `service/config.go` | 监听地址、端口、Token、`dl_session`、代理等（环境变量 + 命令行） |
| `service/service.go` | Gin 路由、CORS、鉴权、各翻译接口 |
| `translate/` | 拼 JSON-RPC 请求、发 HTTP、解压响应、解析译文与备选 |

---

## 对外提供的 HTTP 接口

1. **`GET /`**  
   返回项目说明，提示用 `POST /translate`。

2. **`POST /translate`**（免费通道）  
   Body：`text`、`source_lang`、`target_lang`，可选 `tag_handling`（`html` / `xml`）。  
   内部调用 `translate.TranslateByDeepLX(..., dlSession "")`，走「免费」逻辑。

3. **`POST /v1/translate`**（Pro）  
   需要 **DeepL Pro 的 `dl_session`**：可从配置/环境变量 `DL_SESSION` 来，或请求头 `Cookie` 里带 `dl_session`。  
   代码里还检查：若 session 里含 `.` 会判为非 Pro 并拒绝。  
   有 session 时会把 `method` 标成 `Pro`。

4. **`POST /v2/translate`**  
   更接近官方 API 的形态：支持表单或 JSON（`text` / `target_lang`），成功时返回 `translations` 数组。

可选 **`TOKEN` / `-token`**：若设置了，请求需带相同 token（Query `token` 或 `Authorization: Bearer ...` / `DeepL-Auth-Key ...`），用于给自建服务加一层访问控制。

**代理**：`PROXY` 或 `-proxy`，用于访问 DeepL 时走 HTTP 代理。

---

## 翻译核心在做什么

`translate/translate.go` 里：

- 向 `www2.deepl.com/jsonrpc` 发 **JSON-RPC 2.0**，方法名为 **`LMT_handle_texts`**，并做与 TS 版类似的 **body 格式处理**（`formatPostString`、`handlerBodyMethod`）。
- 用 **`imroc/req`** 客户端并 **`SetTLSFingerprintRandomized()`**，模拟浏览器 TLS 指纹。
- 设置常见浏览器头（`Origin`/`Referer`/`User-Agent` 等），有 Pro 时带 `Cookie: dl_session=...`。
- 响应支持 **br / gzip / deflate** 解压，用 **gjson** 取 `result.texts`、备选译文等。
- 源语言可为空或 `auto`，会用 **whatlanggo** 做语言检测。
- **429** 会明确提示可能被 DeepL 临时限流。

---

## 配置默认值

- 默认监听 **`0.0.0.0:1188`**（可用 `IP`/`PORT` 或 `-ip`/`-port` 改）。

---

## 部署与工程化

仓库里有 **Dockerfile**、**compose.yaml**、**GitHub Actions**（CI/Release/Docker）、**install/uninstall** 脚本和 **systemd/plist** 示例，方便本机或服务器常驻。

---

## 使用上需要心里有数的一点

这类项目依赖 **网页端接口与行为**，DeepL 若改协议、加强风控或限 IP，服务可能不稳定；**429** 的处理在代码里已经体现。若你需要「长期、合规、可开票」的集成，官方 API 仍是更稳妥的选择；DeepLX 更适合自建、兼容各类客户端、或不想走官方计费模型的场景。

> AGENT

下面是基于你本机 **`http://127.0.0.1:8787`**（`xixu-me/deeplx` + `wrangler dev`）的并发测试结果。

---

## 1. `POST /google`（Google 翻译）

| 并发数 | 总耗时（墙钟） | 业务 `code` |
|--------|----------------|-------------|
| 40 | **约 43 ms** | 40× `200` |
| 80 | **约 1460 ms** | 80× `200` |
| 100 | **约 1525 ms** | 100× `200`，无空文件 |

结论：在本机 Worker 上，**百级并发**打 `/google` 时，本次样本里 **全部成功（200）**，尾延迟主要由外网 Google 与本地并行度决定。

---

## 2. `POST /translate`（DeepL 链路）

对 **10 路并发**、每路 **curl 超时 45s** 跑了一次：

- 约 **45s** 才全部结束（多数请求未在超时内完成）。
- 有响应的文件里出现 **`429`**、**`408`**；多路 **`0` 字节**（curl 超时未收到 body）。

说明：DeepL 走代理/上游 JSON-RPC，**并发一上来更容易触发限流或内部超时**，不适合用「纯成功率」和 Google 那条线对比；你之前大量并发把旧 worker 卡住时，需要 **`kill -9` 旧 `workerd`** 再重启 `wrangler dev`（我已在本机换过一轮端口占用问题）。

---

## 3. 若你要自己复现命令

**Google 100 并发（与本次一致）：**

```bash
BASE="http://127.0.0.1:8787"
N=100
for i in $(seq 1 $N); do
  curl -sS -m 90 -X POST "$BASE/google" -H "Content-Type: application/json" \
    -d "{\"text\":\"C$i\",\"source_lang\":\"en\",\"target_lang\":\"de\"}" \
    > "/tmp/cg_$i.json" &
done
wait
cat /tmp/cg_*.json | jq -r '.code' | sort | uniq -c
```

---

**简要结论**：测 **高并发、可重复、结果稳定**，请优先压 **`/google`**；测 **DeepL** 时把并发调低（例如 2～5）并拉长超时，否则容易看到 429/408/超时混合，这反映的是 **上游与代理策略**，不一定是 Worker 本身「扛不住并发」。

当前 **`wrangler dev` 已在 8787 上重新拉起**；若你不再需要，可在对应终端里停掉进程。若要我把同样脚本改成输出 **P50/P95 耗时**（用 `curl -w`），可以说一下目标并发和端点。
