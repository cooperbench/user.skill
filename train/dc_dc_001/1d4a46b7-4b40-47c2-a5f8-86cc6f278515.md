200	#### 3.6.1 借鉴 FlashPrefill (~/FlashPrefill) 调研
201	
202	FlashPrefill 是 MInference / FlexPrefill 改进版，提供三个与 InfLLM-v2 可直接对比的技术点：
203	
204	**(A) α-threshold 动态稀疏率**（最有价值）
205	- 当前 InfLLM-v2: **固定 top-K blocks**，所有 query 无差别算同数量 blocks
206	- FlashPrefill: `score ≥ α × max_score` + `min_budget` 保底 + sink/window/last-N-full 保护
207	- 直觉：128K prompt 里大多数 query 实际只需要 20-30 blocks，固定 top-K=64/128 过度计算
208	- 长 prompt 上潜在收益可观；但训练感知（MiniCPM-SALA 训练时稀疏率固定），需 accuracy 验证
209	- 风险：中高；首先 profile 看 InfLLM-v2 实际 block 选择分布是否真的"过度"
210	
211	**(B) 更简洁的 mean-K + block score kernel**
212	- InfLLM-v2 用 `compress_k_core_new`（可训练 pooling kernel，输出 k1+k2）+ `infllmv2_attn_stage1`（两阶段 softmax attention）
213	- FlashPrefill 用 `compute_mean_vector`（纯 mean）+ `compute_block_score`（直接 QK^T + 双层 max reduce）
214	- 可能更快，但可能掉精度（MiniCPM 的 k/k2 双路是专门训练的）
215	- 可做：microbench 对比两者在 head_dim=128, nq=32, nkv=2, seq=128K 的时延
216	
217	**(C) Kernel autotune 参数空间**
218	- FlashPrefill 的 block-sparse FA kernel 做了 (Q_TILE×K_TILE) × (warps×stages) 多维 autotune
219	- InfLLM-v2 stage2 kernel 可以借用这个 config 空间重新调优（低风险）

268	
269	**问题**: EAGLE-3 使用 NVFP4 量化 draft model 后，accept_len 从 ~1.50 降至 ~1.03，几乎无加速效果。

280	### 深度代码调研结论（2026-04-15）
281	
282	对 `eagle3_runtime_investigation.md` 6 个方向逐项验证后的修正：
283	
284	1. **方向 1 (verify replay de-plan)**: 确认高优先级。minicpm_backend L2063-2066 Python for 循环每请求 2 次 `.item()` sync，bs=64 时 128 次微同步。flashinfer_backend 已有 Triton kernel 参考实现（`create_flashinfer_kv_indices_triton`）。**核心瓶颈是 Python 循环而非 plan() 本身。**
285	2. **方向 2 (dtn=3 快速路径)**: 优先级下调。实际浪费小于预期——cache alloc/free 和 sgl_kernel build_tree 是微秒级。page_size=1 时 assign_draft_cache_locs 不执行。工程量（第二条路径+语义一致性）与收益不成比例。
286	3. **方向 3 (verify 尾部 CPU)**: 部分确认。2 次 tolist() GPU→CPU sync 是真实开销，可合并为 1 次。但 dtn=3 时 Python 循环极短（bs×2 次迭代）。
287	4. **方向 4 (SimpleGLA 带宽)**: **已完成**。fused GLA kernel 已在 Phase 3.2 实现。decode 和 verify 都是 BK=BV=64（非文档声称的 128）。无剩余优化空间。
288	5. **方向 5 (spec-v2)**: 确认前置条件未满足。多步依赖链。
289	6. **方向 6 (tree-aware)**: 确认标准 attention 也是 flat (causal=True, 无 custom_mask)。但 dtn=3 时污染影响有限（仅 2 个 sibling token）。
290	
291	**结论**: draft attention backend 当前默认切到 triton。后续不再做 flashinfer A/B，而是直接从实现差异里追原因、抽 runtime 优化灵感。
292	
293	**代码层推断**:
294	- `spec_steps=1` 时 `DraftBackendFactory.create_decode_backend()` 直接返回 `None`，backend 差异主要落在 draft extend / prefill，不在多步 draft decode
295	- triton 可能赢在省掉了 FlashInfer wrapper 的 metadata / begin_forward 一类固定开销，尤其是小 shape、高并发时更明显

## 位置与结构
- 入口：`eagle_worker_v2.py`（单层 EAGLE-3 就走这个）/ `multi_layer_eagle_worker_v2.py`
- 核心机制：启 `plan_stream`（独立 CUDA stream），draft forward 运行时，target verify 的 `prepare_for_v2_verify`（含 `init_forward_metadata` / attn_backend.plan / CUDA graph replay_prepare）在 plan_stream 并行跑。draft 完成后主 stream `wait_stream(plan_stream)`，再调 `update_verify_buffers_to_fill_after_draft` 修正依赖 draft 输出的字段（主要是 tree_mask + position）。
- 顺带打开 `disable_overlap_schedule=False`：scheduler 的 batch 构造/结果分发也与 forward 重叠。
- Backend hooks：`base_attn_backend.py:60-77`——`get_verify_buffers_to_fill_after_draft()` 返回 `[custom_mask_buf, position_buf]`，`update_verify_buffers_to_fill_after_draft()` 在主 stream 上补算。triton/flashinfer 有，`minicpm_backend` 没有（未实装）。

## 硬门槛：topk > 1 被拒
`server_args.py:2097-2110`：启用 spec-v2 时 `speculative_eagle_topk > 1` 直接 ValueError。根因在 `eagle_info_v2.py:142 prepare_for_v2_draft`：
- cache_loc 分配走 `assign_draft_cache_locs_page_size_1`（要求 `page_size=1` 且链式布局 `bs*topk*num_steps`）
- `positions = seq_lens.repeat_interleave(topk)`、没有 `build_tree_kernel_efficient` → 只支持 chain draft，不建树

## 对我们的影响
我们当前最优 `spec_steps=1 topk=3 dtn=4`，accept_len ≈ 1.50（`docs/EAGLE.md §10` break-even 1.07）。走 spec-v2 只能退到：
- `topk=1 spec_steps=1 dtn=2`：dtn 缩到 2，accept_len 上限 2，实际掉到 ~1.3，break-even 抬升。
- `topk=1 spec_steps=N dtn=N+1`：链式，memory 里已标记 "spec_steps>1 chain draft 成本线性 ×N" 终结方向。

overlap 窗口大小上限 ≈ draft forward 时长。EAGLE.md §10 实测 draft=0.5ms，verify=5ms/cycle。即使 100% 隐藏 plan 与 scheduler 开销，单 cycle 上限省 ≤0.5ms——S8 每请求 150-200 cycle，上限 ~20s 收益。实际上 plan 里一大半 CPU 构建（kv_indptr tolist + for 循环）被 3.4.1 de-Python 后，剩下可并行的 flashinfer plan kernel 更短，overlap marginal gain 再减半。

minicpm_backend 目前 target_verify plan 实际上 **不依赖 draft 输出**（kv_indptr/kv_indices/qo_indptr 只看 seq_lens+draft_token_num），理论上整个 plan 都可以挪到 plan_stream，`update_*` 可以是 no-op——但代价是接受 topk=1 的 accept_len 损失。

## 建议
**暂缓 spec-v2，先做 3.4.1 + 3.4.3**。理由：
1. topk=1 的 accept_len 损失（≥10%）几乎肯定吃掉 overlap 收益。
2. overlap 隐藏的 plan 成本，正好是 3.4.1 要去 Python 化的同一段 CPU 工作；先做 3.4.1 相当于不损失 accept_len 也能把那一段压短。
3. 若日后改 `prepare_for_v2_draft` 支持 tree（把 `build_tree_kernel_efficient` 接回来）并补 minicpm hook，才可能把当前 topk=3 配置 + overlap 同时拿下——工程量大，且依赖对 spec-v2 上游的侵入式修改。

OK，既然 topk=1 chain 是当前最优，v2 就完全在射程内了。我把 v2 的机制从头拆开讲，顺带点出几个"看起来违反直觉"的地方——这些就是你说的"有意思的行为"。

## 1. v1 和 v2 的本质区别：同步执行 vs 流水线执行

**v1（当前 EAGLE-3 路径）**：scheduler、forward、sampling、future 构造，全部在主 Python 线程上串联执行。

```
CPU:  recv_requests → build_batch → forward_thread → sampler → detokenize → loop
GPU:                                 ██████████
```

每个 cycle CPU 空闲等 GPU，GPU 空闲等 CPU，两边互相拖。

**v2（`eagle_worker_v2.py` + overlap scheduler）**：把一个 decode cycle 切成 3 段，段之间允许重叠，并且用 **独立 CUDA stream** 把 metadata 构造与 GPU forward 并行。

```
Main stream:    [Target verify forward] [Draft forward]      [Draft extend]
Plan stream:    [Verify plan/metadata]  [next Verify plan]   [Draft extend plan]
CPU scheduler:  [构造 batch N+1]         [分发 result N-1]    [recv_requests]
```

三条独立时间线。关键机制是下面 3 个。

## 2. plan_stream + "乐观 plan" 模式 ★最核心

这是 v2 最精巧的部分，在 `eagle_worker_v2.py:675` 的 verify 里：

```python
with self.plan_stream_ctx:                                    # ← 切到 plan_stream
    verify_forward_batch, can_cuda_graph = (
        verify_input.prepare_for_v2_verify(...)               # ← 调 attn_backend.plan()
    )                                                         #   / replay_prepare
# 主 stream 继续执行，此时 plan_stream 上的 kernel 正在排队
# ...这段时间主 stream 上是 draft forward 在跑...

if self.plan_stream:
    main_stream.wait_stream(self.plan_stream)                 # ← 让主 stream 等 plan 完成
    attn_backend.update_verify_buffers_to_fill_after_draft(   # ← 用真实 draft 输出修正
        verify_input, cuda_graph_bs
    )
```

注意它**没有顺序**：draft forward 还没产出 tree_mask 和 position 的时候，plan_stream 就已经用"**上一轮/占位的 tree_mask、position 内容**"去跑 `verify_wrapper.plan()` 了。

这看起来会出错，为什么能 work？—— 因为 FlashInfer 的 `plan()` 拆成两部分：
- **读取 shape、kv_indptr、kv_indices 等** → plan 时消耗
- **读取 custom_mask 本身的内容** → 在 `run()` 时才消耗

而 `kv_indptr` / `kv_indices` / `qo_indptr` 只依赖 `seq_lens` + `draft_token_num`（都是已知常量），**不依赖 draft forward 的实际输出 token**。所以大头的 plan 工作可以先跑，等 draft 完了再回头把 tree_mask/position 这几块 buffer 的**内容**更新进去——而 plan 已经记下了这些 buffer 的**指针**，指针没变，内容换了也行。

这就是 `get_verify_buffers_to_fill_after_draft` 的作用：**后端告诉 v2 "这两个 buffer 的内容还没对，draft 完你自己更新我"**。`triton_backend.py:777-788` 的实现连 update 都是空的（pass）——因为 triton 版本 verify 直接读 `custom_mask` tensor，plan 里就没用到；只有 FlashInfer 那种 plan 里会做预处理的才需要真的 update。

**对 minicpm_backend 的意义**：我们的 target_verify plan 里 kv_indptr/kv_indices 构建（`minicpm_backend.py:2277-2377`）本来就只看 seq_lens+dtn，**100% 可以挪到 plan_stream**。`update_*` 基本 no-op（chain draft 没 tree_mask；position 只是 `seq_lens.repeat_interleave(dtn)` 也能预算）。

## 3. 三段式流水线 + verify_done 事件

v2 的 decode cycle 在 `forward_batch_generation()` 里被显式切成：
- **Batch 1 — Target verify**（`verify()`）：plan_stream 做 plan，主 stream 做 target forward + sample
- **Batch 2 — Draft extend**（`_draft_extend_for_decode()`）：plan_stream 做 extend plan，主 stream 做 draft 模型 extend 以 fill 新 KV
- **Batch 3 — Draft（下一轮）**（`draft()`）：主 stream 做 draft decode forward

第 748 行有个细节：

```python
verify_done = torch.get_device_module(self.device).Event()
verify_done.record()
```

这个 CUDA event 被塞进 `next_draft_input.verify_done`。下游 scheduler / overlap thread 拿到这个 event 后，不用 CPU 阻塞 `.synchronize()`，**直接在 GPU 侧链起来**——detokenize 线程可以 `event.wait(stream)` 然后继续自己的活，让 GPU queue 自己排序。

## 4. overlap scheduler + FutureMap（`-input_ids` 大法）★最"有意思"

server_args 里 spec-v2 自动把 `disable_overlap_schedule=False`。这打开的是另一个机制：scheduler 在当前 cycle N 的 forward **还没跑完**时，就开始构造 cycle N+1 的 batch。

但 N+1 的 input_ids 依赖 N 的 accepted token，CPU 上拿不到值——怎么构造？

`overlap_utils.py:33` 的 `FutureMap`：维护一个循环 buffer，每个未决 token 用一个**负数占位符** `-i`。scheduler 照样构造 batch，只是 `input_ids` 里塞着 -1, -2, -3...。forward 要跑之前，才在 GPU 上解析：

```python
# overlap_utils.py:19
input_ids[:] = torch.where(
    input_ids < 0,
    future_token_ids_map[torch.clamp(-input_ids, min=0)],   # 从 buf 里取
    input_ids,
)
```

`torch.compile` 一下这个函数，整个解析变成一个 GPU kernel。CPU 这边**永远不需要等 token 实际值**，只要 forward 执行到这个 kernel 时 buffer 里已经写入了（前序 cycle sampler 的结果）就行。

对 EAGLE，FutureMap 升级版：buffer 里存的是整套 `topk_p / topk_index / verified_id / new_seq_lens / hidden_states` 五件套（`overlap_utils.py:80-107`）。scheduler 只记"我要用 future_indices=[5,6,7]"，GPU 侧自己去 buf 取。

这个设计的副作用：
- `batch.seq_lens` 是在前序 cycle GPU 上算出来的，**CPU 不知道值**。所以 minicpm_backend 里你看到的 `seq_lens_cpu = ...tolist()` 会被这个机制 break——scheduler 现在连 seq_lens_cpu 都不一定能提供。
- 这是为什么 PLAN.md 3.4.5 前置条件里写"CPU result path 收窄"——v2 下很多以前从 CPU 读 tensor 值的地方都得改用 GPU 侧计算。

## 5. 为什么硬性要 topk=1

`eagle_info_v2.py:142 prepare_for_v2_draft` 里：
- cache_loc 分配 `bs*topk*num_steps` flat 布局，kernel 叫 `assign_draft_cache_locs_page_size_1`——**只支持 page_size=1 的链式布局**
- `positions = seq_lens.repeat_interleave(topk)`——每请求 topk 个 position，但没有父子关系
- 没有调 `build_tree_kernel_efficient`

所以 v2 的 draft 路径只识"长度 = topk × num_steps 的链"（实际上 topk=1 时就是 num_steps 长的链，topk>1 会被 `prepare_for_v2_draft` 误当成链处理，样子对但语义错）。这是工程上的简化，不是数学上的不可能。

**对我们**：`spec_steps=3 topk=1 dtn=4` 就是 spec-v2 的原生配置——draft 模型跑 3 步自回归 chain，target 一次 verify 4 个 token。完美匹配。

## 6. 一个 pytorch 坑：record_stream

第 664 行：

```python
batch.seq_lens.record_stream(main_stream)
```

这个调用我第一次看也愣了一下。原因是 `batch.seq_lens` 可能是前一个 cycle 在**另一条 stream** 上 allocate 的。PyTorch caching allocator 会在 tensor 析构时立刻把显存 free 回池，然后被下一个 allocation 复用——但如果此时前 stream 的 kernel 还没读完这块内存，新的 writer 就会写坏旧 reader。`record_stream(main)` 告诉 allocator "主 stream 也在用这块内存，请等到主 stream 排空再 free"。

在单 stream 的 v1 里这问题不存在，v2 里 plan_stream 会 race 这些 tensor，所以必须显式声明。

## 7. 对我们工作流的总结

在你现在 topk=1 chain 这条路线上，v2 的收益来自 3 块叠加：

| 机制 | 当前 cycle 占比 | 可隐藏？ |
|---|---|---|
| scheduler 构造 batch / resolve future | ~1-2ms CPU | 全隐藏（overlap schedule） |
| target_verify plan（kv_indptr 构建 + plan kernel） | ~0.5-1ms | 90%+ 隐藏（plan_stream） |
| draft_extend plan | ~0.3ms | 全隐藏 |

按我们 bs=8 一个 cycle ~12ms 算，单 cycle 可能省 1.5-2.5ms，12-20% range。比我第一轮答的时候乐观（因为我当时假设 topk=3）。

但要落地有三关：
1. **实装 `get_verify_buffers_to_fill_after_draft` / `update_verify_buffers_to_fill_after_draft` in minicpm_backend**。对我们是幸运的：chain draft 没 tree_mask，`get_*` 返回 `[None, None]`，`update_*` = pass 就够（只要 plan 不依赖 draft 实际输出）。
2. **去掉 target_verify replay 里的 CPU tolist / Python for 循环**（即 3.4.1）。overlap schedule 下 CPU 路径不能拿 `seq_lens_cpu` 做 `for i in range(bs): ... .item()`——这会 serialize 掉 plan_stream。
3. **sample/verify 尾部 `accept_index.tolist()` 的 GPU sync 点**（3.4.3）。v2 用 `verify_done` event 想把整个 verify 结果流水下去，这个 tolist 是最后一根刺。

所以 3.4.1 + 3.4.3 + 2 个 hook 是解锁 v2 的最小套装。反过来说也能成立：**单独做 3.4.1 基本把 plan_stream 能省的 GPU 时间提前吃掉了，v2 的 marginal gain 就只剩 overlap scheduler 那部分 CPU 开销**（而这部分只有在 bs 多、请求调度密集时才显著，对我们 S1/S8 场景偏小）。

## Level 2：真正抬 accept_len 的机制 — v2 draft_extend 多吃 KV

v1 和 v2 的 draft_extend 目的一样：**verify 结束后，让 draft 模型把"已提交的新 token + bonus"喂一遍，把 draft KV cache 追到最新，并产出下一个 cycle 的 hidden_state seed**。

但两者喂的 token 数不一样：

**v1** `eagle_info.py:790`：
```python
batch.extend_lens = [x + 1 for x in batch.spec_info.accept_length_cpu]
```
每请求 **variable-length**，只喂 `accept_length + 1` 个 token（真正提交的）。

**v2** `eagle_info_v2.py:196`：
```python
batch.extend_seq_lens = [num_draft_tokens for _ in range(len(batch.seq_lens))]
batch.seq_lens = batch.seq_lens + num_draft_tokens   # 注意：加 dtn，不是 accept_length
batch.input_ids = predict   # predict 是 target 在整个 dtn 区间的 argmax
```
每请求 **fixed-length = dtn**，把 target 在**所有 dtn 位置（包括被拒绝的分支）**的 argmax 都喂进 draft。

这是个工程上为了 CUDA graph 定长捕获而做的简化——v2 的 draft extend 有 cuda graph runner，shape 必须固定。但**语义上它写了额外的 KV**。

### 为什么会抬 accept_len？

考虑 chain topk=1 dtn=3，某 cycle 接受数 accept_length = 1（只接受第一个 draft token）：

- **v1 draft_extend**：喂 2 个 token（`[accepted_d0, bonus]`），draft 在 req_to_token 的位置 `[committed..committed+1]` 写 KV。next cycle draft 读到这里为止。
- **v2 draft_extend**：喂 3 个 token（`[predict_0, predict_1, predict_2]` 中 predict_0 = accepted_d0，predict_1 = bonus，**predict_2 = target 在被拒绝位置上会继续预测的 token**）。draft 在位置 `[committed..committed+2]` 写 KV。

下一个 cycle 的 draft decode 读 KV 的 upper bound 由 `new_seq_lens = committed + accept_length` 决定——理论上**只读到 +1 位置**，位置 +2 的"幻影 token KV"应该读不到。

但：

1. **over-allocation**（`eagle_info_v2.py:100` `kv_allocated_len = kv_committed_len + 2 * ALLOC_LEN_PER_DECODE`）：v2 为流水线提前预留 slot。draft 写 `[committed..committed+dtn-1]` 都在已分配范围内。
2. **FutureMap + overlap scheduler**：`batch.seq_lens` 在 cycle 间通过 circular buffer 流转。`resolve_future` 从 buf 里解出来的 seq_lens 来自**上一 cycle verify 的最终值**。这一步如果和 `_draft_extend_for_decode` 里 `batch.seq_lens = old + dtn` 发生读写 race（同一 tensor 对象或同一 buf slot），next cycle draft 可能**看到的 seq_lens 是 old + dtn，而不是 old + accept_length**。
3. 一旦 next cycle seq_lens 被污染成 `old + dtn`，draft 就会**读进那些"幻影 KV"——它们是 draft 在 target argmax 条件下算出的 hidden_state**。

"幻影 KV" 里藏的是什么信息？**target 对未被采纳的分支上会给出的 argmax 连续预测**——这些就是 target 在这个上下文下的"真实偏好"。draft 的注意力读到这些，等于直接窥探了 target 分布的几个 step 延伸。**下一个 cycle draft 产出的 token 天然更贴 target 口味，accept_len 自然抬高**。

这就是"**有时候**抬高"的原因：race 谁赢要看调度延迟、batch 大小、verify 完成事件 (`verify_done`) 是否在 scheduler 拿到 new_seq_lens 之前落回主存。一把没赢、一把赢了，accept_len 就在两档之间抖。

### 和 SIGQUIT 的关系（虽然你说先不管，但机制是同一个）

同一 race 的另一面：draft 读了幻影 KV 导致下一步 target verify 的 `predict` 里出现越界 token / 或 draft 的 KV 写入追上了 kv_allocated_len 的上沿，触发 `assert` 或 CUDA OOB → 一个子进程被 kill → scheduler 发 SIGQUIT。

### 一个更隐秘的来源：verified_id 的 select

```python
select_index = arange(bs) * dtn + accept_lens - 1   # v2
```
选的是"最后一个被接受 token 的 hidden_state"。正常情况下 causal mask 保证 hidden_state[accept_lens-1] 只 attends 到前缀——v1 v2 值应一致。

但如果 draft_extend 的 attention backend 在 v2 下**退化成非 causal 或 tree mask 错位**（v2 专门给 `DRAFT_EXTEND_V2` 有一套 mode），就会把后面的幻影位置也 attend 进 hidden_state[accept_lens-1]。那这个 seed hidden_state 本身就被 target 信息污染了——下个 cycle 整条链 accept 率抬高，而且不需要 race，**稳定性抬高**。

检查起点：`ForwardMode.DRAFT_EXTEND_V2` 在 draft 侧 attn backend 里是怎么建 mask 的？如果 `extend_seq_lens=dtn` 但只按 causal 处理，没问题；如果出于 kvcache 写入一致性用了 full visibility，就有这个稳定泄漏。

2. **overlap scheduler 隐藏 CPU 调度开销**：scheduler 构造下一轮 batch、`resolve_future`、detokenize 全部和 forward 并行。bs 越大越值钱，S8 场景接近饱和时单 cycle 能省 1-2ms CPU。
3. **`verify_done` event 消掉 GPU→CPU sync 点**：把 `.tolist()` / `.item()` 这些硬同步变成 GPU 事件流水。这一条和 3.4.3 语义重合。

乐观估 S8 节省 15-25s（7-10%），S1 因为并发度低、scheduler 开销相对小，收益会打 4-6 折。

## 不值得依赖的部分

**accept_len 抬高那 0.2-0.5 不能算进收益**。那是 race 窗口里 draft 读到了"幻影 KV"，本质是**draft 偷看了 target 对被拒绝分支的继续预测**，等于绕过了 verify 的语义检查。后果：

- 速度表看起来快了，但**输出分布偏离 target 的真实 argmax 链**。竞赛打分里 `ori_accuracy` 会掉。Platform 79.11% 基线本来就紧。
- race 是不稳定的——mini_bench 跑两次结果可能差几秒，无法稳定复现/回归。这违反你最高指令里"每一轮必须产出可量化速度对比"。
- SIGQUIT 是同一 race 的另一面，偶发崩溃本身就把 v2 挡在可交付之外。

所以**必须先修干净再量收益**，不能拿"race 抬 accept_len"的数当 v2 的成绩。

## 必须解决的问题清单

按依赖顺序：

1. **3.4.1 先做**：TARGET_VERIFY replay 里的 Python for 循环 + `seq_lens_cpu.tolist()` + per-req `.item()`——这些会把 plan_stream 的并行能力 serialize 掉。v1 路径下 3.4.1 本身也值 -5% 左右，是独立收益。
2. **minicpm_backend 实装两个 hook**：`get_verify_buffers_to_fill_after_draft` 返回 `[None, None]`（chain 无 tree mask），`update_verify_buffers_to_fill_after_draft` = pass（我们 plan 不依赖 draft 实际输出）。这步几十行。
3. **修掉 draft_extend 幻影 KV / 变长问题**：要么照 v1 改 `extend_seq_lens` 为变长 + 手写 cuda graph pad（工程量大），要么把 `_draft_extend_for_decode` 里 `batch.seq_lens += num_draft_tokens` 改成 `+= accept_length`，同时给"多余"位置的 input_ids 填 pad_token 保形（工程量小，得测正确性）。
4. **修 FutureMap / `verify_done` 的同步点**：确保 next cycle draft 的 `seq_lens` 一定用 commit 值，不能从 `_draft_extend_for_decode` 的临时 tensor 泄漏出去。
5. **accuracy 回归**：修完后本地跑 `ori_accuracy`，确认不低于 v1 路径的 79.98%。

## 我的判断

**值得，但不是现在。** 当前应该先做 3.4.1 和 3.4.3——它们是 v2 的前置条件、同时自己也有独立收益、而且不引入 v2 的 race 复杂度。做完这两个之后，再评估 v2：

- 如果 3.4.1 已经把 verify 的 CPU 开销从 ~2ms 压到 ~0.3ms，那 v2 的 overlap 窗口能隐藏的量就剩 0.3ms 级，S8 收益摊薄到 3-5%，**可能不值那 500 行改动 + 回归风险**。
- 如果 3.4.1 撬不动（Python 同步点还是卡 1ms+），那 v2 的 overlap 就是直接 10%+ 收益，**稳赢**。

所以建议的顺序：**3.4.1 → 测量 verify 残余 CPU 开销 → 决定 v2 上不上**。不要在 3.4.1 之前碰 v2，否则两边问题纠缠在一起分不清谁出了什么问题。

你的直觉（吞吐角度有意义 + 必须先修 bug）和我结论一致，只是我想强调：**先做 3.4.1，再用数据决定 v2 的 marginal value**。
