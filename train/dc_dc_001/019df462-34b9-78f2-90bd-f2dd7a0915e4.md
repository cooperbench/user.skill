我把这三份串起来看，关系大概是：

- [collapse-analysis.md](/user_4813494d/openbmb/docs/eagle/collapse-analysis.md:7)：线上 case 的实证根因，告诉我们“到底坏在哪里”。

- [spec-survey.md](/user_4813494d/openbmb/docs/eagle/spec-survey.md:1)：候选方法原材料库，按 verify/tree/draft/SSM/long-context 分类。

最关键的背景是：我们不是普通 EAGLE 接受率低，而是 **long deepresearch + 130K prompt + MiniCPM-SALA hybrid GLA/sparse attention + 32K draft vocab** 这个组合。`collapse-analysis` 里已经排除了很多错误方向：不是 TARGET_VERIFY sparse 不等价，不是 hidden state 错配，不是 plan cache，不是单纯 topk/spec_steps 配置，v3 draft 甚至在 idx17 更糟。

**几个有趣方向**

1. **C2：post-EOS / `<unk>` loop 退 nospec**

这个方向很土，但非常对症。bench 里 `ignore_eos=True` 会强迫模型在自然结束后继续生成，尾段退化成 `<unk>` / `<|im_end|>` 循环，而这两个 token 结构上不在 draft hot set。文档量化过：miss 10.12%，其中 `<unk>` 占 89.2%，修掉结构 miss 理论上 aggregate al `1.865 -> 2.298`，约 +23%。

它不解决 long deepresearch 真弱项，但能切掉一个比赛 workload 人为制造的 spec 负收益尾巴。实现也很小：最近 K 个 commit token 命中 `{0, 73440}` 或连续 al=0，就该 req 暂时走 nospec。注意 production `ignore_eos=False` 时收益会小很多，所以这是偏 benchmark case 的工程招。

2. **位置问题：rope_theta 已做，AOI 是重训版正解**

`longcontext-analysis` 的五条根因里，RoPE 外推和训练位置分布偏斜是最干净的两条。我们已经做了 `rope_theta=1M`，全量 long context `adj_al +44.9%`，这是非常强的证据。

但 `rope_theta` 只解决“角频率外推”，不解决“draft 训练时没见过大 position”。LongSpec 的 AOI 更有意思：训练时把后续 token 的 position_ids 加随机 offset，用 2K shard 覆盖 30K+ 位置空间。这个要重训，但不是大改模型结构。对我们这种 120K-130K prompt 的 deepresearch，AOI 比单纯加数据更有针对性。

3. **MARS / relaxed verify：已经落地，但还有动态化空间**

MARS 的洞察很适合 collapse 段：文档里 collapse 的 target top1-top2 gap 明显更低，说明很多失败发生在 target 自己也犹豫的位置。MARS 接受 top2 且 margin 足够近的 token，本质是把“低置信边界处 rollback 成本”换成轻微近似。

它已经是生产方向之一，后续有趣点不是“要不要 MARS”，而是：
- D5/D7 用不同 theta；
- long-context 或 low-margin 段更激进；
- coding/short 段保守；
- 和 Traversal Verification 组合，因为 MARS 改单 token 判定，Traversal 改 tree 遍历，两者正交。

风险也明确：NVFP4 量化 logits 会影响 top2 ratio，theta 不能照搬论文。

4. **Phased Verify / FASER：先验证根，不值得就别跑完整树**

这个方向跟我们的 al=0 collapse 特别贴。很多 vlong step 一开始 user_4813494d 就不匹配，这时候还跑完整 dtn verify 是浪费。`experiments-log` 里离线算过 Phase-1 early exit，vlong bucket early-exit 很高。

难点不是想法，而是系统形态：TARGET_VERIFY CUDA graph 要支持多个 token shape，比如先跑 3 token，再按需跑剩余 token；GLA intermediate state 也要 snapshot/restore。它是“红线内、理论收益大、工程复杂中高”的方向。

5. **BanditSpec / per-request adaptive dtn**

这个我觉得很值得重视。我们的样本分布非常分裂：coding adj_al 2.3-2.8，vlong deepresearch 1.24-1.30，post-EOS 甚至接近全 0。固定 dtn 对这种混合 workload 很笨。

BanditSpec 用每个 req 自己的 accept_length 做 UCB，动态选 `{dtn=3,5,7}` 或直接 nospec。它不需要概率，不改 kernel，greedy 完全兼容。对我们的价值是把“长 prompt 弱样本少浪费 verify token，coding 强样本多吃 draft”自动化，比全局 topk/spec_steps 搜索更合理。

6. **GOOSE / RACER：给 deepresearch 加 retrieval spine**

GOOSE 和 RACER 都很有趣，因为它们不是再训一个更聪明的 draft，而是承认长文本里有大量重复模板和上下文续写模式。

- GOOSE：高接受率的 n-gram/context token 做深链 spine，低置信 logits token 做宽分支。
- RACER：AC 自动机从已生成/上下文里找历史续写，形成 retrieval tree，再和 EAGLE logits tree 融合。

这和 deepresearch 的“根据材料/搜索结果/分点总结”类模式很匹配。它也绕开了 EAGLE v2/v3 在 long hidden distribution 上不稳定的问题。工程上可能是 CPU 侧候选生成 + 现有 verify tree，风险比重训小。

7. **OWL / LongSpec 架构替换：长期治本**

OWL 的核心很直白：EAGLE 吃 full-context hidden，context 越长 hidden 越漂；OWL LSTM drafter 只消费 last-token hidden，因此长上下文 acceptance 从 EAGLE-3 的 1.28 到 4.00。这个对我们五条根因里的 hidden drift / sparse-dense mismatch 很有针对性。

但它是新 drafter 架构，训练和接 SGLang 都不小。更像下一代草稿模型，不是这轮快速优化。

8. **STree / hybrid SSM verify：这是我们独有的正确性地带**

`spec-survey` 里最重要的结论之一是：没有现成论文完整覆盖“standard attention + GLA/SSM target + 外部 EAGLE tree verify + recurrent state rollback”。STree、SpecMamba、SGLang MambaRadixCache 都只是相邻参考。

这方向不一定马上提速，但决定我们能不能安全扩大 tree、做更深 topk、做 phased verify。GLA state 不是 KV cache，不能随便部分接受；state snapshot/rollback 是基础设施。这个方向应该作为所有 tree 形态实验的正确性底座。

**我会优先排的顺序**

短期：C2、BanditSpec、Phased Verify。  
中期：GOOSE/RACER retrieval tree、MARS 动态 theta。  
长期：AOI 重训、OWL/LongSpec 新 drafter、STree 风格 GLA verify formalization。

不建议再重押：单纯 v3 draft/NLL 指标、全局 topk/spec_steps 搜索、Cactus/SMC 这类对 greedy T=0 不友好的方法。

我拉了原始材料：

- Paper: arXiv `2505.15141`, v2 2025-11-20，ICML accepted: https://arxiv.org/abs/2505.15141
- Code: `sail-sg/BanditSpec`: https://github.com/sail-sg/BanditSpec
- 本地副本：`/tmp/banditspec` 和 `/tmp/banditspec-paper`

**先说结论**

值得接入，但不要按“per-request 直接选 `{dtn=3,5,7}`”这个最理想版本上来做。我们当前 SGLang/EAGLE 路径是**每个 decode batch 一个 spec mode**，不是每个 req 一个 mode。真正 per-request dtn 会碰到 draft/verify CUDA graph、tree shape、batch tensor 对齐、GLA state buffer 的大改。

更现实的路线是：

1. 先做 **batch-level BanditSpec selector**，替换现在基于 `bs` 阈值的 `NO_SPEC/D5/D7` 规则。
2. 再做 **request stats + routing hint**，让 selector 识别 batch 里 hard req 占比。
3. 最后才考虑 mixed per-request mode，那个需要分 batch 或 batch-mask verify，工程量明显大。

**论文核心**

BanditSpec 的抽象不是只选 speculation length。它把任何 spec 超参配置都当 arm：

- draft model 可以是 arm
- tree shape 可以是 arm
- speculation length `gamma` 可以是 arm
- 甚至 nospec 也可以是 arm

每轮 spec decode 后拿到 reward，论文理论里 reward 是 accepted token length，batch serving 实验里更接近 throughput。算法主要两个：

- `UCBSpec`：适合 reward 均值相对稳定的场景，论文实验里表现更好。
- `EXP3Spec`：适合 adversarial / 非平稳场景，但实现复杂且实测不如 UCBSpec。

代码实现是 research prototype，不适合直接搬。比如 `/tmp/banditspec/generate_utils.py` 里有大量 `torch.cuda.synchronize()`，HF 自定义 forward，硬编码 `gamma<=4`。但策略层可借鉴。

**和我们现状的对应**

我们已经有一套动态 spec mode：

- `SpecMode.NO_SPEC`
- `SpecMode.MARS_D5`
- `SpecMode.MARS_D7`

入口在 [spec_mode.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/spec_mode.py:1)，现在是按 batch size 阈值切：

- 大 batch 走 `NO_SPEC`
- 中间走 `D5`
- 小 batch 走 `D7`

worker 里也已经有多 graph runner 和 mode apply 逻辑：[eagle_worker.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_worker.py:397)。

所以 BanditSpec 最自然的接入点不是 `eagle_worker.draft()` 内部，而是把 [scheduler.py](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/scheduler.py:2266) 那里：

```python
batch._spec_mode = self._spec_mode_selector.select(batch.batch_size())
```

换成 bandit-aware selector。

**推荐接入方案**

第一阶段：batch-level UCB，低风险。

arms：

- `NO_SPEC`
- `MARS_D5`
- `MARS_D7`

state：

- 每个 arm 维护 `n`, `mean_reward`
- warmup 阶段每个 arm 至少试几次
- 之后选 `mean + c * sqrt(log(t) / n)`

reward 不建议一开始用纯 accept length。我们的模式成本差很多：

- `NO_SPEC` 没 draft/verify overhead
- `D5/D7` draft token 数不同
- D7 小 batch 才有 graph
- long prompt prefill / decode 不同阶段吞吐含义不同

更合理的 reward：

```text
reward = generated_tokens / step_wall_time
```

或者折中：

```text
reward = (bs + accepted_draft_tokens) / step_wall_time
```

需要在 scheduler 或 worker result 里把当前 step duration 和 mode 一起更新回 selector。

第二阶段：加上下文特征，但仍 batch-level。

我们的 batch 不是同质的。可以加几个 cheap features 分桶维护 UCB：

- `bs_bucket`: large / mid / small
- `prompt_len_bucket`: short / long / vlong
- `recent_accept_bucket`: 最近平均 accept low / mid / high
- `post_eos_or_al0_pressure`: batch 中连续 al0 的 req 比例

这样不是全局一个 UCB，而是 `contextual-ish UCB`。不需要上复杂 contextual bandit，先做分桶字典就够。

第三阶段：per-request stats。

每个 `Req` 已经有：

- `spec_verify_ct`
- `spec_accepted_tokens`

可以加：

- recent accept EMA
- consec al0
- selected mode history

这些 stats 先用于 batch selector 决策，而不是立刻让同 batch 内不同 req 走不同 dtn。

**为什么不直接 per-request dtn**

因为当前 EAGLEWorker 一次 batch 只应用一个 `self.topk/spec_steps/dtn`，并绑定一个 `cuda_graph_runner`。`EagleVerifyInput` 的 `draft_token_num` 也是 batch-level。要同 batch 混合 D5/D7，你需要至少做一个：

- 拆成多个 sub-batch 分别 forward，调度复杂且可能损失吞吐；
- 统一捕获最大 dtn，然后对部分 req mask 掉后续 verify token，类似 BanditSpec 代码里的 batch mask；
- 做更一般的 ragged tree verify，这会碰 GLA intermediate state 和 sparse slot 生命周期。

第三条太大，第二条有意思但风险高。可以作为后续。

**值不值得**

值得，但要用“替换启发式动态路由”的方式接入，而不是大改 per-request mixed dtn。

理由：

- 我们 workload 分布确实高度分裂：coding 高 accept，vlong deepresearch 低 accept，post-EOS 近似全 0。
- 当前阈值策略只看 `bs`，看不到“这个 batch 里其实都是 hard long req”。
- 论文最核心的假设正好适用：不同 prompt / prefix 下最佳 spec 配置会变，固定配置不是最优。
- 我们已有 D5/D7/NO_SPEC graph 和 result metrics，接一个 batch-level UCB 的工程成本不高。

风险：

- UCB 探索会引入短期慢 step，benchmark 总时长如果由少数长尾决定，探索成本不能太大。
- reward 用 wall time 会有 prefill/GC/graph warmup 噪声，要只在 decode steady step 更新。
- `NO_SPEC` reward 和 spec reward口径必须统一，否则 selector 会学偏。

- **BanditSpec per-request mixed dtn 才是大改**：如果要同 batch 内不同 req 不同 dtn，才会碰 batch mask / ragged verify / GLA intermediate state / cache slot 生命周期。

这其实让 BanditSpec 更值得做：我们已经有 D5/D7/NO_SPEC 切换基础设施，不需要从零搭 runner。第一版应该就是把当前启发式 selector 改成 bandit selector。

> DEVELOPER

说人话 什么是BanditSpec 为什么做 要怎么做

> AGENT

BanditSpec 说人话就是：

**别提前拍脑袋固定“这一步猜几个 token”。每一步跑完以后，看刚才猜得值不值，再决定下一步继续大胆猜、保守猜，还是干脆不猜。**

在我们这里就是把现在的：

```text
batch size 大 → no-spec
batch size 中 → D5
batch size 小 → D7
```

改成：

```text
这类 batch 最近 D7 赚 → 选 D7
这类 batch 最近 D5 稳 → 选 D5
这类 batch 最近 spec 亏 → 选 no-spec
偶尔探索一下别的选项，防止误判
```

**为什么做**

因为我们的请求差异太大：

- 代码类：draft 猜得准，spec 很赚。
- 超长 deepresearch：draft 经常猜不中，D7/D5 可能浪费 verify。
- post-EOS / `<unk>` loop：spec 基本纯亏。
- batch 后期只剩少数长尾请求，最优策略会变。

固定一套 `D5/D7/no-spec` 阈值只能适配平均情况。BanditSpec 的价值是让系统在线学习“现在这批请求用哪个模式最划算”。

**怎么做**

第一版别做复杂 per-request。直接替换现在的 `SpecModeSelector`。

候选 arm：

```text
NO_SPEC
D5
D7
```

每个 arm 维护两个数：

```text
试过几次 n
平均收益 mean_reward
```

每个 decode step：

1. 选一个 arm。
2. 让整个 batch 走这个模式。
3. 记录这一步实际收益，比如：
   ```text
   reward = 这一步生成 token 数 / 这一步耗时
   ```
4. 更新这个 arm 的平均收益。
5. 下次用 UCB 公式选：
   ```text
   score = mean_reward + explore_bonus
   ```
   已经表现好的会被选；很久没试过的也会偶尔被探索。

**接入点**

就在现有动态切换处：

- 现在：`scheduler.py` 调 `SpecModeSelector.select(batch_size)`
- 改成：`BanditSpecModeSelector.select(batch_context)`
- 跑完 batch 后：把 `mode / token数 / 耗时 / accept_len` 回传给 selector 更新统计

worker 这边已有 D5/D7/no-spec 切换，不需要重做。

**值不值得**

值得做一个实验版。成本不大，因为底座已经有了。  
但第一版目标要务实：**batch-level 自适应 selector**，不是同一个 batch 里每个 request 不同 dtn。后者复杂很多，先别碰。

同一个 batch 里每个 request 不同dtn 一定要做这个 否则意义有限 另外 只有在bs=1的时候可以摇到d7 明白我在说什么吗

> AGENT

明白。你说的是：

**batch-level BanditSpec 意义有限，因为它只能整批一起摇。只要 batch size > 1，当前系统基本只能选 D5/no-spec；D7 只有 bs=1 才能用。这样 BanditSpec 学不到“这个 req 值得 D7，那个 req 应该 no-spec”的差异。**

这点是对的。真正有价值的是：

```text
同一个 decode batch 里：
  req A: D7
  req B: D5
  req C: no-spec
  req D: D3 / no-spec
```

而不是：

```text
整个 batch 一起 D5 或一起 no-spec
```

否则它最多只是把现在的 bs 阈值规则换成一个在线调参器，收益会很有限。

**真正要做的形态**

每个 req 自己维护 bandit state：

```text
req.bandit arms = {NO_SPEC, D5, D7}
req.reward history
req.recent_accept_len
req.consec_al0
```

每轮 decode 前，对 batch 里每个 req 独立选 arm。然后把 req 按 arm 分组：

```text
group_no_spec = [...]
group_d5 = [...]
group_d7 = [...]
```

执行上有两条路。

**方案 A：分组跑多个 sub-batch**

同一个 scheduler batch 拆成 2-3 个子 batch：

```text
run no-spec subbatch
run D5 subbatch
run D7 subbatch
merge results back
```

优点：复用现有 D5/D7/no-spec 代码，语义最干净。  
缺点：一次 decode step 变成多次 worker forward，GPU 利用率和调度复杂度要实测。D7 现在只 capture bs=1，若 D7 group 有多个 req，需要补 D7 多 bs graph，或者逐 req 跑 D7，后者大概率太亏。

**方案 B：统一按最大 dtn 跑，低 dtn req 做 mask**

比如统一按 D7 shape 组织 batch：

```text
D7 req: verify 7/9 个 draft token
D5 req: 只验证前 5/7 个，后面 mask 掉
NO_SPEC req: 只走 user_4813494d/target token，或单独 fast path
```

优点：仍是一批 forward，最像论文里的 batch-mask 思路。  
缺点：这是大改。要处理 tree mask、accept_index、KV slot、draft KV、GLA intermediate state、evict/free slots。尤其 GLA state 对 masked token 必须不能污染后续 commit。

我觉得如果目标是“真正有用”，应该走 **方案 B 的简化版**：

1. 先只支持 `{D5, D7}` 混合，不把 no-spec 混进去。
2. batch 统一用 D7 最大 shape。
3. D5 req 的 `draft_token_num` 逻辑用 per-req cutoff/mask。
4. verify kernel 接收 per-req effective dtn。
5. accept/evict/free/mamba/GLA state update 都按 effective dtn 截断。
6. no-spec 仍保持现有 batch-level 或单独 subbatch，后面再合。

这样第一版能验证核心问题：**per-req D7 是否能在 bs>1 时带来收益**。

**为什么这才配叫 BanditSpec**

因为 bandit 的 arm 必须作用在 req 上：

```text
coding req 逐步学到 D7 赚
deepresearch req 逐步学到 D5 或 no-spec
post-EOS req 逐步学到 no-spec
```

如果 arm 只作用在 batch 上，batch 里混了强弱请求，reward 会被平均掉，最后学出来的还是保守策略。

所以你的判断是对的：**要做就做 per-request dtn；batch-level 只是低成本 smoke，不是最终方案。**
