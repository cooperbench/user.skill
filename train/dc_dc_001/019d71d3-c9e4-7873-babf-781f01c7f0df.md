**结论**

真正的 Medusa 和真正的 EAGLE，本质上都不是你们现在这条 `top1` 链式 verify。

你们当前主线是“工程化简化版 Medusa”：
在 [`medusa_worker.py#L113`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L113) 把 `topk` 固定成 `1`，在 [`medusa_worker.py#L301`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L301) 每个 head 直接 `argmax`，再在 [`medusa_worker.py#L304`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py#L304) 把 verify 输入拼成线性序列 `[verified_id, draft_0, draft_1, ...]`。[`eagle_info.py#L828`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py#L828) 也明确写了 Medusa 这里是 “flat (sequential) draft tokens”。这不是论文意义上的 tree Medusa。

真正的 Medusa 应该是：多头提出多候选，借助 tree attention / tree verify，在一轮 target forward 里验证多条分支，然后选最长可接受前缀。真正的 EAGLE / EAGLE-2 也是树，只是 EAGLE-2 更强调 dynamic draft trees；EAGLE-3 强调多层特征融合和训练期模拟，但在线 verify 如果 `topk>1`，仍然需要 branch-aware 的树式语义。官方来源可对照：
[Medusa paper](https://proceedings.mlr.press/v235/cai24b.html),
[Medusa repo](https://github.com/FasterDecoding/Medusa),
[EAGLE repo](https://github.com/SafeAILab/EAGLE),
[EAGLE paper](https://proceedings.mlr.press/v235/li24bt.html).

**为什么你们会退化成 top1**

因为 MiniCPM-SALA 不是纯 Transformer，而是 hybrid attention。标准 attention 在 [`minicpm_backend.py#L973`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L973) 的 `TARGET_VERIFY` 下走 dense prefill；但 GLA 在 [`hybrid_linear_attn_backend.py#L1636`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1636) 是逐 step recurrent rollout，并在 [`hybrid_linear_attn_backend.py#L1373`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L1373) 回滚到 accepted step。对 linear attention，真正的树验证不是“补一个 mask”就够了，而是要维护每个分支自己的 recurrent state、父子跳转和回滚语义。

更关键的是，当前活跃的 `SimpleGLAAttnBackend` verify 路径本质上是平铺 `draft_token_num` 顺序跑，并不消费树分支语义；`retrieve_next_token/sibling` 这种 branch metadata 在同文件别的 recurrent 路径里有部分支持，但你们现在这条 SimpleGLA 主路径没有把“真树”跑通。也就是说：

- `eagle_utils.py` 的树构造和 greedy verify 本身没问题，见 [`eagle_utils.py#L47`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L47) 和 [`eagle_utils.py#L161`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_utils.py#L161)
- 但在你们这类 hybrid linear attention 模型上，真正困难的不是树 mask，而是 branch-aware state evolution

**关于 EAGLE 还是 Medusa 的真正判断**

对你们这个仓库，真正结论很明确：

1. 主线不该回到“真树 Medusa / 真树 EAGLE”。
原因不是理念不对，而是 hybrid linear attention 下 verify 状态机成本太高，且当前实现基础并不支持完整树分支语义。

2. 当前最合理的主线仍然是 `Medusa K=1 / top1 chain verify`。
这和仓库已有结论一致：[`technical-notes.md#L197`](/user_4813494d/openbmb/docs/technical-notes.md#L197) 认为 `K=1` 对 MiniCPM-SALA 最优，收益来自更低的 GLA verify 开销，而不是更高的树覆盖率。

3. EAGLE-3 现在不适合作为主线。
不是树没实现，而是训练分布不对。[`technical-notes.md#L142`](/user_4813494d/openbmb/docs/technical-notes.md#L142) 已经把根因定得很清楚：draft 是 BF16 hidden 上训练的，服务时 target 是 NVFP4，hidden distribution mismatch 直接把 accept rate 打没了。没有“对量化后 hidden 重新训练/蒸馏”，EAGLE-3 不该继续押主线。

4. 你们现在真正该优化的是 verify 等价性，不是把树做复杂。
当前最危险的点仍然是：
`dense verify vs sparse decode` 的语义差异，
以及 hybrid attention verify 的状态回滚一致性。
这也和 [`spec-decode-accuracy-investigation.md#L25`](/user_4813494d/openbmb/docs/spec-decode-accuracy-investigation.md#L25) 的判断一致。

**最终建议**

如果目标是比赛和可落地速度收益：
继续走 `Medusa K=1 + batched TARGET_VERIFY`，不要急着回真树。

如果目标是研究“真正 EAGLE / Medusa”：
先别在 MiniCPM-SALA 上做。
先在纯 Transformer target 上把 tree verify 跑通，再回头设计 linear attention 的 branch-state cache、parent/sibling transition 和 rollback。

如果目标是继续投 EAGLE：

  - `retrive_next_sibling`
  - verify 时在 [`EagleVerifyInput.verify()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py ) 里传给 `verify_tree_greedy_func()` 或 `tree_speculative_sampling_target_only()`。
- `hybrid_linear_attn_backend.py` 里也不是完全没考虑树。
  - 在 [`MambaAttnBackendBase._forward_metadata()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py )，如果 `forward_mode.is_target_verify()` 且 `spec_info.topk > 1`，会把 `retrive_next_token / retrive_next_sibling` 放进 `ForwardMetadata`，并额外分配一个 `retrieve_parent_token` buffer。
  - 在 CUDA graph 元数据路径 [`_capture_metadata()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py ) 和 [`_replay_metadata()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py )，也专门给 `topk > 1` 走了 tree-metadata 分支。
  - 更关键的是，在 GDN/Mamba 类 hybrid 线性注意力的 `forward_extend()` verify 分支里，`causal_conv1d_update(...)` 和 `fused_recurrent_gated_delta_rule_update(...)` 都接收了 `retrieve_next_token / retrieve_next_sibling / retrieve_parent_token`：
    - [`forward_extend()` around 1022-1105]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py )
  - 这说明“基于 parent/sibling 关系去驱动 recurrent state 演化”这件事，至少在一条 hybrid backend 路径里是被设计过的，不只是 attention mask。

2. 主路径里仍有明显“线性展开”实现，尤其是 SimpleGLA verify。

- 最关键的线性展开路径是 [`SimpleGLAAttnBackend.forward()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py ) 的 `TARGET_VERIFY` 分支。
  - 它直接把 `(bs * draft_token_num)` reshape 成 `(bs, draft_token_num)`。
  - 然后 `for step in range(draft_token_num)` 逐步 recurrent rollout。
  - 每一步只把 `current_state -> next_state` 顺序推进，并把结果写到 `intermediate_ssm[:, :, step]`。
  - 最后完全依赖 [`update_mamba_state_after_mtp_verify()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py ) 按 `accepted_steps` 把“某个 step 的中间状态”写回正式 cache。
- 这条 SimpleGLA 路径没有消费 `retrieve_next_token / retrieve_next_sibling / retrieve_parent_token`。
  - 也就是说，它默认所有 verify token 构成一条线性链，而不是树。
  - 对 `topk > 1`，虽然 metadata 层准备了 buffer，但这条主执行路径本身不理解“分叉后每个节点的 parent state 不同”。
- 因此，从当前主路径来看：
  - GDN/Mamba 风格 hybrid backend 对树语义是“部分支持”的。
  - SimpleGLA 主线 verify 仍然是“线性 token rollout + 事后按 accepted step 回滚”。

3. 真正 tree verify 在 hybrid linear attention 上“理论可行”，但当前代码只打通了半套；最难的是 branch-aware recurrent state 管理，不是 tree mask。

最难的状态点有三个：

- 每个候选节点的状态来源不是“前一个位置”，而是“它的 parent 节点”。
  - 对普通 softmax attention，这更多是 mask / KV 可见性问题。
  - 对 linear/recurrent attention，隐藏状态本身就是递推态，所以每个分支节点都需要从正确 parent 的 recurrent state 出发。
  - 这就是为什么 `retrieve_parent_token` 会被传进 recurrent kernel，而不只是传一张 mask。
- intermediate state 的索引语义必须从“step-based”升级成“node-based”。
  - 当前 `SimpleGLAAttnBackend` 的 `intermediate_ssm[cache_idx, :batch_size, step]` 是按 step 存的。
  - 真树 verify 需要按“树节点”存，或者至少能从 `retrieve_parent_token` 重建每个节点对应的 parent state。
  - 否则一旦同一深度有多个 sibling，`accepted_steps` 这种单标量就不够表达状态落点了。
- rollback / commit 也不能再只靠 `accepted_steps`。
  - 当前 [`update_mamba_state_after_mtp_verify()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py ) 用的是“每个请求一个 accepted step”。
  - 这只适用于线性链：第 0 步、第 1 步、第 2 步。
  - 真树里最终接受的是某条路径上的某个节点，不一定能表示成单纯的 `step=k`。需要“accepted node id -> parent chain -> chosen recurrent state location”这种映射。

结论压缩成一句话：

- `hybrid linear attention` 上真树 verify 不是不可能。
- 当前源码里，树 verify 的“外层数据结构”和部分 recurrent kernel 接口已经在为这件事铺路，尤其是 GDN/Mamba 那条路径。
- 但主执行路径，特别是 `SimpleGLAAttnBackend.forward()` 的 `TARGET_VERIFY`，仍然是严格线性展开。
- 所以现在的状态更像“接口层为真树预留了形状，真正难的 branch-aware recurrent state 演化和 node-level rollback 还没有在主路径跑通”。
