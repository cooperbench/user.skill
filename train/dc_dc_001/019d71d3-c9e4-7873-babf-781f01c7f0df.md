每个候选节点的状态来源不是“前一个位置”，而是“它的 parent 节点”。 - 对普通 softmax attention，这更多是 mask / KV 可见性问题。 - 对 linear/recurrent attention，隐藏状态本身就是递推态，所以每个分支节点都需要从正确 parent 的 recurrent state 出发。 - 这就是为什么 `retrieve_parent_token` 会被传进 recurrent kernel，而不只是传一张 mask。 - intermediate state 的索引语义必须从“step-based”升级成“node-based”。 - 当前 `SimpleGLAAttnBackend` 的 `intermediate_ssm[cache_idx, :batch_size, step]` 是按 step 存的。 - 真树 verify 需要按“树节点”存，或者至少能从 `retrieve_parent_token` 重建每个节点对应的 parent state。 - 否则一旦同一深度有多个 sibling，`accepted_steps` 这种单标量就不够表达状态落点了。 - rollback / commit 也不能再只靠 `accepted_steps`。 - 当前 [`update_mamba_state_after_mtp_verify()`]( /user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py ) 用的是“每个请求一个 accepted step”。 - 这只适用于线性链：第 0 步、第 1 步、第 2 步。 - 真树里最终接受的是某条路径上的某个节点，不一定能表示成单纯的 `step=k`。需要“accepted node id -> parent chain -> chosen recurrent state location”这种映射。 结论压缩成一句话： - `hybrid linear attention` 上真树 verify 不是不可能。 - 当前源码里，树 verify 的“外层数据结构”和部分 recurrent kernel 接口已经在为这件事铺路，尤其是 GDN/Mamba 那条路径。 - 但主执行路径，特别是 `SimpleGLAAttnBackend.forward()` 的 `TARGET_VERIFY`，仍然是严格线性展开。 - 所以现在的状态更像“接口层为真树预留了形状，真正难的 branch-aware recurrent state 演化和 node-level rollback 还没有在主路径跑通”。
