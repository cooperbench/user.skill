## 什么是 piecewise cudagraph

SGLang/vLLM 的一种 CUDA graph 捕获策略：用 `torch.compile`（或 fx splitter）把模型 forward 切成若干段，**只把"安全段"（纯算子图）捕获成 CUDA graph，attention 等需要变长输入/有 side effect 的部分留在 eager**，最后 stitched 起来重放。

跟传统 "full cuda graph" 的区别：
- **Full graph**：把整次 forward 全捕获成一张图（SGLang 当前 decode 路径用的就是这种，靠 `--cuda-graph-max-bs/--cuda-graph-bs`）。要求所有形状都对齐，attention backend 必须配合 padded layout。
- **Piecewise**：在 attention boundary 处切开，每段独立 capture/replay，attention 走原生路径。优点是兼容更多 backend（变长 prefill、稀疏 attention 等也能受益）；缺点是切多段后 launch overhead 比 full graph 多。

代码在 `demo-sala/sglang/python/sglang/srt/compilation/`（`backend.py`, `cuda_piecewise_backend.py`）和 `model_executor/piecewise_cuda_graph_runner.py`，开关是 server arg `--enable-piecewise-cuda-graph`（默认 `False`），相关参数还有 `--piecewise-cuda-graph-tokens / --piecewise-cuda-graph-max-tokens / --piecewise-cuda-graph-compiler`（默认 `eager`）。

## 我们有没有启用

**没有。** `eval/start_eagle.sh` 没传 `--enable-piecewise-cuda-graph`，`server_args.py:557` 默认 `False`。当前生产用的是普通 full cuda graph（decode 路径）+ eager prefill。

要不要试一下？对我们其实意义不大：
- decode 已经走 full graph，piecewise 只会增加 launch overhead；
- prefill 是变长 + 自定义稀疏 attention（InfLLM-v2，stage1/stage2 + plan cache），上 piecewise 需要先把这些 custom op 注册成 `torch.library` 可追踪的形式，目前 `minicpm_flashinfer` backend 没做这套适配，强行开会直接 `torch.compile` 失败 fallback。

如果想验证是否值得投入，建议路径是：先在纯 dense decode（关 spec）上跑 piecewise + `--piecewise-cuda-graph-compiler eager` 对比 full graph，确认没退化再考虑 prefill 段。

5. 逐 Kernel 优化分析
本节按 Transformer 每层的计算流程，逐一分析各 kernel 的优化策略及相对 TensorRT-LLM 的性能优势。我们的优化包含两个层面：一是通过激进的 kernel fusion 消除冗余的 HBM 访问和 kernel launch；二是自研 warp-specialized FP8 GEMM，在纯矩阵乘法性能上也超越了 cuBLAS（peak 996T vs 881T，快 4-14%）。TRT-LLM 使用 cuBLAS GEMM + 独立的 Norm/RoPE/Quantize kernel，两个层面的差距叠加构成了整体 1.5x 的性能优势。

5.1 QKV Projection + QKNorm + RoPE → 单个 Fused Kernel
TRT-LLM（估算）    Ours
实现    cuBLAS QKV GEMM + QKNorm kernel + RoPE kernel    单个 warp-specialized fused kernel
Kernel 数    3    1
每层耗时    ~1100μs（cuBLAS QKV ~750μs + QKNorm ~180μs + RoPE ~170μs）    720μs
加速    —    1.53x
TRT-LLM 的 QKV GEMM 输出（65536×4096×2B = 512MB）先写入 HBM，再由 QKNorm kernel 读回做归一化，再由 RoPE kernel 读回做旋转。我们将三者融合为单个 kernel，Norm + RoPE 在 GEMM epilogue 中直接操作 WGMMA 累加器，完全消除了中间结果的 HBM 往返。

5.2 O/Down Projection + Residual Add → Fused GEMM
TRT-LLM（估算）    Ours
残差融合位置    后置：fused 到下一个 RMSNorm（RMSNorm 需同时写 norm 输出和 residual 两份数据）    前置：fused 到 GEMM store（TMA reduce-add，零额外写入）
Kernel 数    1（cuBLAS GEMM，残差在后续 RMSNorm 处理）    1（Warp-specialized GEMM + TMA reduce-add）
O proj 每层耗时    ~500μs    325μs
Down proj 每层耗时    ~730μs    475μs
TRT-LLM 将残差加融合到后续的 RMSNorm kernel 中（output = RMSNorm(x + residual)），但这要求 RMSNorm kernel 同时写出两份数据（归一化结果 + 更新后的 residual），增加了 memory store 压力。我们的方案将残差加前置到 GEMM 的 TMA store 阶段：TMA reduce-add 指令在将 GEMM 结果写入全局内存时原子累加到 residual 上，与普通 TMA store 吞吐一致，完全省去了一次 residual 的额外写入。

加上我们的 warp-specialized GEMM 本身比 cuBLAS 快 4-14%（peak 996T vs 881T），两个优势叠加实现了显著加速。

5.3 SwiGLU（Gate + Up GEMM + SiLU 激活）→ Fused Gated GEMM

Kernel 数    1    1
每层耗时    ~1420μs    924μs

5.4 FlashAttention 3 + Epilogue FP8 量化

5.5 RMSNorm + Residual Add + FP8 Quantize → Fused Kernel

## 真正值得借鉴的点（按可行性排序）

### 1. TMA reduce-add 把 residual 前置到上一个 GEMM 的 epilogue（§5.2）
这点是文章里最具体、迁移成本最低的优化。我们当前 prefill 里 o_proj / down_proj 后的 residual：
- 走 `linear_method.apply` 后 `+ residual` 的独立 add，还是融在下一个 RMSNorm？
- sm_120 的 b12x / CUTLASS EVT 支持 `EpilogueWithBroadcast` + TMA store-add，至少在 prefill GEMM 上是可以做的
- **决定要不要做的关键判据**：先从 nsys 看 prefill 里独立 residual add kernel 占多少 us。`docs/prefill-deep-profiling.md` 里的 GPU busy 1980ms 没单独列 add，先确认是不是已经融了

### 2. FA3 epilogue 内 FP4 量化（§5.4）
他们把 attention 输出的 BF16→FP8 量化融进 FA epilogue。我们的对应物：
- Standard attn 走 FlashInfer + InfLLM-v2 sparse FA，输出 BF16 给 o_proj 之前**没有**做量化（NVFP4 GEMM 的 input quant 是单独 kernel）
- 如果稀疏 stage2 epilogue 能直接产出 FP4 + per-block scale，能省掉一份 (T, hidden) 的 BF16 中间结果
- 难点：NVFP4 需要 16-element block 的 scale，比 FP8 per-tensor 复杂一档；要看 InfLLM stage2 的 tile size 是否对齐 16

### 3. 方法论：用实际频率算 MFU，而不是 boost
他们写得很诚实——**H100 NVL 在 400W TDP 下持续跑会降频到 ~1GHz**，所以 92% MFU 是按 936T 算的，不是 sm_90 的 nominal peak 1979T。RTX 6000D 同样是 TDP 受限的工作站卡，我们如果按 boost clock 算 MFU 会严重低估优化空间，按持续频率算才能看清"还差多少到上限"。`docs/kernels-sm120.md` 应补一行实测持续频率。

### 4. 逐 kernel TFLOPS breakdown 表
他们那张 §4 的表（每个 kernel 占比、平均耗时、有效 TFLOPS）格式非常工整。我们的 `prefill-deep-profiling.md` 已经有 top kernel 列表，但**没把每个 GEMM 算成有效 TFLOPS**。把它算出来能立刻知道哪个 kernel 还有空间、哪个已经触顶不要再碰。

## 不能照搬的点

- **FP4 ≠ FP8**：FP8 per-tensor 单 scale，FP4 microscaling 每 16 元素一组 scale。fused norm+quant、fused gemm+quant 在 FP4 下都更复杂，参考价值有限。
- **稀疏 attention**：他们 FA3 是 dense 单 kernel；我们 InfLLM-v2 是 compress_k → block_score → stage2 sparse FA 三段，根本没法对齐到他们那种 "1 kernel attention"。
- **GLA Lightning attn**：24 层是线性 attention recurrent，不是 GEMM-bound，和他们 §4 的 GEMM-占 70% 完全不同。
- **场景**：评测里 spec decode forward 才是大头，他们的 prefill 优化对应的是 first-token latency，不是吞吐主战场。

## 我的建议

如果只挑一个动作做：**把 nsys profile 跑一次 spec-decode forward（不是 prefill）**，按他们的格式做一张 kernel-level TFLOPS 表，区分"接近峰值的"和"还有空间的"。我们 docs 里的 prefill 优化已经很深了，但 decode 路径没有同样精细的表，而 decode 才是评测的瓶颈。

如果有第二个动作：**确认 b12x decode 路径有没有把 residual 融进 GEMM epilogue**，没融的话这是一个高确定性的 win。

2. 背景与动机
2.1 问题定义
在 Transformer 的 Attention 层中，QKV 投影后通常紧跟 QKNorm（对 Q、K 做 RMSNorm）和 RoPE（旋转位置编码）。标准实现需要三次 kernel launch：

QKV GEMM：FP8 矩阵乘，输出 BF16
QKNorm：对 Q、K 分别做 RMSNorm（per-head 归一化）
RoPE：应用旋转位置编码
三个 kernel 之间存在冗余的全局内存读写：QKV GEMM 的输出写入 HBM，QKNorm 读回来处理后再写入，RoPE 再读一次。对于 M=65536、head_dim=128 的典型配置，Q 部分就有 65536×2048×2 = 256MB 的冗余往返。

2.2 硬件平台
GPU：NVIDIA H100 NVL（94GB HBM3，132 SMs，TDP 400W）
FP8 Dense Peak：1670 TFLOPS @1785MHz max boost
关键硬件特性：TMA（Tensor Memory Accelerator）、TMA Multicast、WGMMA（Warp Group Matrix Multiply-Accumulate）、128B Swizzle、异步事务屏障（mbarrier）
2.3 目标
将 QKV GEMM + QKNorm + RoPE 融合为单个 kernel，使得 Norm + RoPE 的计算完全隐藏在 GEMM 的 epilogue 中，不增加额外延迟。目标是 fused kernel 时间 ≈ 纯 GEMM 时间。

3. Kernel 架构设计
3.1 Warp-Specialized 流水线
Kernel 采用 Hopper 架构的 warp-specialized 设计，384 线程分为两组：

Producer WG（128 线程）：通过 TMA 异步加载 A、B 矩阵 tile 到 shared memory，并在 GEMM 尾部预加载 cos_sin 表
Math WG（256 线程，2 个 warp group）：执行 WGMMA FP8→FP32 累加，以及 epilogue 中的 Norm + RoPE + D 写回
两组通过 ClusterTransactionBarrier（fill/empty barrier）实现 pipeline 同步，3 级流水隐藏 TMA 延迟。

3.2 Tile 参数
BM = 256    // M 方向 tile（2 个 warp group 各处理 128 行）
BN = 128    // N 方向 tile
BK = 128    // K 方向 tile（4 次 WGMMA 64×128×32）
STAGES = 3  // 流水线级数
Shared memory 布局（占满 H100 全部 228KB）：

D buffer：BM×BN×2B = 64KB（同时复用为 cos_sin 暂存）
A stages：3×BM×BK×1B = 96KB
B stages：3×BN×BK×1B = 48KB
Barriers + padding：~1KB
cos_sin preload buffer：~19KB（可提前加载部分 cos_sin chunk，与 GEMM 计算形成 load-compute overlap）
3.3 GEMM 核心
每个 warp group 持有两组累加器（acc[64]、acc2[64]），分别处理 tile 内 128 行中的前 64 行和后 64 行。K 方向循环中，每步执行 4 次 WGMMA 64×128×32 指令：

for (uint32_t k = 0; k < BK / WGMMA::K; ++k) {
    WGMMA::wgmma(ad, bd, acc, ...);   // rows 0-63
    WGMMA::wgmma(ad2, bd, acc2, ...); // rows 64-127
}
3.4 分区缩放
根据 N 方向偏移，kernel 将输出分为 Q、K、V 三个区域，分别应用不同的 dequant scale：

if (ns < q_size)       { ds = scale_q; part = 0; }  // Q partition
else if (ns < qk_size) { ds = scale_k; part = 1; }  // K partition
else                   { ds = scale_v; part = 2; }  // V partition
仅 Q 和 K partition 需要 Norm + RoPE（part == 0 或 1），V partition 只做缩放。

4. 优化历程
4.1 基础版本：GEMM + Norm + RoPE 初版融合
起点：在 warp-specialized GEMM 的 epilogue 中加入 QKNorm + RoPE。

关键问题：BM=256 的 dual accumulator WGMMA 需要正确计算 A tile 的 shared memory descriptor 偏移。两个 warp group（wg=0, wg=1）各处理 128 行，A descriptor 基址需要偏移 wg * 128 * BK：

auto ad  = make_smem_desc(sa[0] + wg * 128 * BK, 1);       // rows wg*128 .. wg*128+63
auto ad2 = make_smem_desc(sa[0] + (wg * 128 + 64) * BK, 1); // rows wg*128+64 .. wg*128+127
Epilogue 流程：math thread 0 通过 TMA 加载 cos_sin 表到 shared memory，所有 math thread 计算 sum-of-squares + rsqrt 得到归一化因子，等待 cos_sin TMA 完成后执行 RoPE 旋转并写 D buffer。支持连续/非连续 position_ids 双路径。

结果：710-721 TFLOPS fused（M=65536, Qwen3-0.6B config），比分离实现（CUTLASS QKV + 独立 qknorm_rope）快 1.2-1.3x。

4.2 128B Swizzle 对齐（消除 Barrier）
关键优化：让 cos_sin 的 TMA 加载使用与 D buffer 相同的 128B swizzle 模式。

这样 cos_sin 数据直接写入 D buffer 的 swizzled 布局中，rope 计算后可以就地（in-place）写回 D buffer，无需额外的 barrier 同步或数据搬运。cos_sin 读取和 D 写入使用相同的 swizzle 地址计算：

uint32_t at = col / TMA_D_BN, ca = col % TMA_D_BN;
uint32_t s = ca ^ ((row % 8) * 8);  // 128B swizzle pattern
auto* ab = reinterpret_cast<__nv_bfloat16*>(base + at * BM * SW);
return ab[row * TMA_D_BN + s];
结果：758-768 TFLOPS，比上一版提升 ~7%。TMA sector 效率 100%。

4.3 BF16 RoPE + 预计算 snw + 融合 scale 到 rsqrt
三个优化合并为一次提交：

1) BF16 RoPE 旋转：将 rope 从 FP32 改为 BF16 半精度操作。BF16 ALU 吞吐是 FP32 的 2 倍（packed __nv_bfloat162），每条指令处理两个元素：

__nv_bfloat162 r0v = __hsub2(__hmul2(af, c0), __hmul2(as2, s0x));
__nv_bfloat162 r2v = __hadd2(__hmul2(as2, c0), __hmul2(af, s0x));
2) 预计算 snw：将 scale * rsqrt * norm_weight 合并为 BF16 向量，在等待 cos_sin TMA 期间预计算（完全 overlap）：

__nv_bfloat162 snw0[16];
for (uint32_t i = 0; i < 8; ++i)
    snw0[i] = __float22bfloat162_rn({sn.x * nw[i].x, sn.x * nw[i].y});
Rope 循环中只需一次 __hmul2 即可完成 norm weight 乘法，减少了关键路径上的指令数。

3) 融合 scale 到 rsqrt：将 dequant scale 融合进 RMSNorm 的 rsqrt 计算，消除独立缩放步骤：

// 原始：rsqrt(ss/dim + eps) * scale  →  两步
// 优化：scale * rsqrt(scale² * ss / dim + eps)  →  一步
float sn = ds * rsqrtf(ds * ds * ss / 128.f + eps);
结果：766-782 TFLOPS，比上一版再提升 ~2%。Norm + RoPE 的 epilogue 开销从初版的 ~80μs 降至 ~62μs（纯 GEMM ~660μs，fused ~722μs）。

4.4 Producer 预加载 cos_sin（与 GEMM 尾部重叠）
核心优化：将 cos_sin TMA 加载从 math thread 移至 producer warp group。Producer 在完成最后一个 k-block 的 A/B 加载后，立即检测 position_ids 连续性并发起 cos_sin TMA：

// Producer: 在 k-loop 结束后
if (tile_needs_norm_rope && contiguous) {
    int pf = __ldg(&position_ids[mx]);
    tma_copy<128, BM, SW>(&tma_cs, cs_bar, smem_cs, 0, pf, 1u);
    cs_bar->arrive_and_expect_tx(CS_TMA_BYTES);
}
时序分析：Producer 加载 cos_sin 与 math 的最后几步 WGMMA 重叠执行。当 GEMM 完成时，cos_sin 已在 shared memory 中就绪，math thread 直接进入 norm 计算无需等待。

D buffer 安全性：cos_sin 写入 D buffer（共用 smem 区域）。上一个 tile 的 D TMA store（64KB, ~30μs）在 producer 完成 8 个 k-block 加载（384KB, ~640μs）之前早已完成，不存在竞争。

结果：Fused kernel 每层从 ~723μs 降至 ~710μs，cos_sin 等待时间从 epilogue 关键路径中消除。

5. 总结
指标    数值
FP8 GEMM Peak    996 TFLOPS（vs cuBLAS 881T, +13%）
Fused QKV+NormRope    比分离实现快 1.17-1.62x
正确性    50⁄50 随机 batch 全部通过，cos_sim > 0.999
核心思想：将 memory-bound 的 Norm+RoPE 完全隐藏在 compute-bound 的 GEMM epilogue 中，利用 Hopper 的 TMA swizzle 实现 cos_sin 与 D buffer 共享 smem、warp-specialized producer 预加载实现与 GEMM 计算重叠。最终 fused kernel 时间 ≈ 纯 GEMM 时间，Norm + RoPE 的计算开销近乎为零。

6. 未来优化方向
当前实现仍有若干可挖掘的优化空间，受限于工程时间暂未纳入：

6.1 TMA Multicast（Cluster 级 B 矩阵广播）
Hopper 支持 cluster_size > 1 时，多个 SM 共享同一份 B tile 的 TMA 加载。对于 QKV 场景（N=4096, BN=128, 共 32 列 tile），相邻两个 SM 处理同一列不同行时，B tile 完全相同。启用 cluster_size=2 可将 B 的 TMA 带宽需求减半，对 K 较小（如 K=1024）时 memory-bound 的 shape 尤其有效。代价是需要 cluster-aware 的 tile 调度器，确保同一 cluster 内的 SM 处理相同的列 tile。

6.2 cos_sin Cache 跨 Batch 复用
在 prefill 场景中，同一 batch 内不同 sequence 若具有相同的 position_ids 分布（例如等长 sequence），其 cos_sin 值完全相同。当前实现对每个 BM=256 的 row tile 独立加载 cos_sin，即使相邻 tile 对应的 position range 存在大量重叠。可优化方向：

L2 Cache 预热：在 kernel 启动前显式 prefetch cos_sin 表到 L2，利用 L2 的 50MB 容量（cos_sin 表通常 < 1MB）实现近乎全命中
Cluster 级 cos_sin 共享：结合 TMA multicast，让同一 cluster 内的 SM 共享 cos_sin 数据，避免重复加载
6.3 非连续 Position IDs 的 Producer 预加载
当前非连续路径（跨 batch 边界的 tile）由 math thread 在 epilogue 中同步加载 cos_sin，未能与 GEMM 计算重叠。可在 producer warp group 中对非连续 tile 也做预加载——按 position_ids scatter-gather 到 smem，与 GEMM 计算重叠，消除非连续路径的额外延迟。 这篇文章对你有什么帮助 目光就放在prefill上面  不考虑decode

### 1️⃣ Fused NVFP4 QKV GEMM + qk_norm + rope（最大空间，工程量也最大）

- 省一份 (T, total_heads*D) 的 BF16 HBM 往返
- 省 1 次 kernel launch
- 对 GLA 24 层 ×2 chunk 复用，潜在收益相当可观

### 2️⃣ §4.3 三个指令级优化（triton 也能做，几天工作）

- **BF16 packed RoPE**（`__hmul2 / __hsub2 / __hadd2`）：吞吐 2× FP32
- **预计算 snw = scale × rsqrt × norm_weight**：把 rsqrt 完成后立即吸收 scale 和 norm_weight
- **scale 融进 rsqrt**：`sn = ds * rsqrtf(ds*ds * ss / dim + eps)` 一步出，省一次乘

## 不要直接照抄的部分

- **Hopper warp-specialized 模板直接搬到 sm_120**：CUTLASS 3.5+ 才稳定支持 sm_120 的 warp-specialized + TMA，且 Blackwell 的 wgmma 已被 `tcgen05.mma` 取代（CUTLASS 4.x 路径）。直接 fork 他们 H100 kernel 不能 work，必须重写到 sm_120 collective builder。

- **per-tensor scale 路径的简化**：他们 FP8 是一个 scale，我们 NVFP4 16-element block scale 一直在 epilogue 路径上，"scale 融进 rsqrt" 这种小窍门要重新推导。

## 调查结论

### 当前 kernel 路径（`demo-sala/sglang/python/sglang/srt/models/minicpm.py:147-210`）

完整数据类型流：
- **输入**：`qkv` bf16 (T, total_heads*D)，`Q_W/K_W` bf16 weights，`cos_sin_cache` **fp32** (line 782 注释 + line 158 注释)，`positions` int32
- **kernel 内全部 cast 到 fp32 计算**：line 170/176/178/186/187/191/193/195
- **store 时才转回 bf16**：line 202/206 `y.to(Q_OUT.dtype.element_ty)`

### 三项优化逐项核对

| 优化 | 当前状态 | 能否做 | 备注 |
|---|---|---|---|
| **BF16 packed RoPE** | ❌ 全 fp32（line 198 `y = xn * cos_full + sgn * x_pair * sin_full` 在 fp32） | ✅ **rope 旋转那步可以**，但 RMSNorm 的 `sum(x*x)/D` reduce **必须留 fp32**（数值稳定性） | 收益最大的就这一步 |
| **预计算 snw = scale × rsqrt × norm_weight** | ⚠️ 隐式合并（line 179 `x * rstd[:,None] * w[None,:]`），不是显式预乘成 (BM, D) 向量 | ✅ 可显式预乘，但 triton 大概率已做 CSE | 几乎没收益，cosmetic change |
| **scale 融进 rsqrt** | ❌ **不适用** | ❌ | 我们 kernel 输入是**已经 dequant 完的 bf16 qkv**，没有 GEMM dequant scale 需要吸收；MiniCPM 的 q_norm/k_norm 也没有额外 scale 因子 |

### 唯一真有意义的改动：BF16 RoPE 旋转

具体是 line 175-198，能改的最小补丁大致：


- 当前 docs/prefill.md §2.13 测出 fused 1.13 ULP < baseline 2.00 ULP（vs fp64 reference）
- bf16 ULP ≈ 2⁻⁷ ≈ 0.008，cos/sin 范围 [-1,1]、normalized x ≈ 1，乘加单次误差 ≈ 0.008
- 估计 bf16 化后 ULP 升到 **2-4 ULP**，仍在可用范围，但**必须重测 vs fp64 reference**，不能只看 cos_sim

### ROI 估算（决定是否值得做）

`docs/prefill.md` 现状：
- `gla_fused_qk_norm_rope_ms` = **7.22ms / chunk**（24 GLA 层，约 300us/层）
- 整个 GLA 部分 **120ms / chunk**，整个 chunk prefill 几百 ms

bf16 化最乐观估计：rope 旋转占 norm+rope ~40%，bf16 packed ≈ 2× → 节省 **~1.5ms / chunk**，**占整 chunk prefill < 1%**。

**结论：这是个低收益高精度风险的优化**。如果做，工程上 1 天能落（包括 ULP 测试），但端到端 wall clock 几乎看不出来。我**不推荐现在做**——上面回信里第 1 条（fused NVFP4 QKV GEMM + qknorm + rope 一锅，省 256MB HBM 往返）和第 5 条（GEMM 基线表）的预期收益是 10-50× 这个量级。
