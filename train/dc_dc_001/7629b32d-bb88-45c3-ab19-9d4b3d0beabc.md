21	## 01 量化：FourOverSix 自适应 block scale 选择
22	
23	### NVFP4 格式与标准量化的局限
24	
25	我们的基础量化路线是 GPTQ + NVFP4（FP4 E2M1 格式），decode 阶段使用 Marlin 做 W4A16 推理。NVFP4 的可表示值为 `{0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6}`，最大绝对值为 6。
26	
27	标准 NVFP4 量化时，每个 block 的权重会被归一化到 `[-6, 6]` 的完整 FP4 表示范围（即以 M=6 为上界缩放）。这个设计有一个结构性问题：FP4 在 `[4, 6]` 区间只有一个可表示值（6 本身），而在 `[2, 4]` 区间有两个（3 和 4）。当权重的最大值映射到 6 附近时，`66%~100%` 这段范围内的值都只能用 6 来表示，量化误差集中爆发。
28	
29	### FourOverSix 算法
30	
31	**FourOverSix**（Jack Cook, Junxian Guo, Guangxuan Xiao, Yujun Lin, Song Han；MIT + NVIDIA 联合工作，arXiv:2512.02010）提出：对每个量化 block 自适应地在两种归一化上界之间选择——M=6 或 M=4。
32	
33	当选择 M=4 时，block 的权重被缩放到 `[-4, 4]` 范围。此时 `[2, 4]` 区间内有三个可表示值（2、3、4），分布更均匀，对集中分布的 block 量化误差更小。代价是放弃了 FP4 的 `(4, 6]` 区间，对少数极大值的表示能力略有下降。
34	
35	选择规则是：对每个 block 分别用 M=6 和 M=4 量化一次，计算二者的反量化均方误差（MSE），取误差更小者：
36	
37	```python
38	# M=4 对应的 block scale 约为 M=6 时的 1.5 倍
39	scale_m4 = fp8(scale_m6.float() * 1.5)
40	mse_m6 = ((W_block - dequant(W_block, scale_m6)) ** 2).mean()
41	mse_m4 = ((W_block - dequant(W_block, scale_m4)) ** 2).mean()
42	final_scale = scale_m4 if mse_m4 < mse_m6 else scale_m6
43	```
44	
45	输出格式与标准 NVFP4 完全相同（4-bit 权重 + FP8 block scale），推理 kernel 无需任何修改，吞吐零损耗。
46	
47	### 我们的集成与实测
48	
49	我们将自适应 scale 选择嵌入 GPTQ 量化流程，在每个 block 的 scale 估算之后、GPTQ 权重优化迭代之前执行，使后续的 GPTQ 优化在已确定的 M 值框架下进行，避免二者冲突。
50	
51	实测发现，**约 40–43% 的 blocks 最终选择了 M=4**，MLP 层（gate/up/down proj）的占比明显高于 Attention 层的 QKV 投影。这符合直觉：MLP 权重经过更强的正则，分布较集中；QKV 权重包含更多离群值，M=6 的大范围更有优势。启用 FourOverSix 后，我们在各类评测任务上观测到稳定的量化精度提升。

55	## 02 推测解码：Medusa 在混合注意力架构上的适配
56	
57	### 推测解码的核心逻辑
58	
59	推测解码（Speculative Decoding）的基本思路是：用一个轻量 draft 预测若干后续 token，再让主模型并行 verify，从而在保证输出分布不变的前提下，以一次 verify 的代价换取多个 token 的产出。
60	
61	**Medusa**（Tianle Cai, Yuhong Li, Zhengyang Geng, Hongwu Peng, Jason D. Lee, Deming Chen, Tri Dao；ICML 2024）的核心创新是：**不引入独立的 draft model**，而是在主模型最后一层的 hidden state 上直接附加若干轻量预测头，每个头负责预测后续第 k 个位置。
62	
63	### Medusa Head 的结构
64	
65	每个 Medusa head 是一个带残差连接的单层变换，结构极其轻量：
66	
67	```
68	p_t^(k) = softmax( W₂⁽ᵏ⁾ · ( SiLU(W₁⁽ᵏ⁾ · hₜ) + hₜ ) )
69	```
70	
71	其中 `W₁` 是一个 `d×d` 的线性层，`W₂` 是投影到词表的输出层（复用主模型 LM Head 权重初始化），`hₜ` 是主模型最后一层的 hidden state。**W₁ 初始化为全零**，使得训练初期 Medusa head 的预测与主模型完全一致，训练过程更稳定。
72	
73	### Tree Attention Verify
74	
75	K 个 head 各自取 top-s 个候选，通过笛卡尔积构建一棵候选树（例如两个头各取 top-2，得到 4 条候选路径）。Verify 时，所有候选节点在**一次主模型 forward** 中并行处理，通过修改 attention mask 保证每个节点只能 attend 到其在树中的前驱路径，而非全部候选。验证完成后取最长的接受前缀，完成一次"以一次 forward 的代价验证多条候选"的推测解码循环。
76	
77	### MiniCPM-SALA 适配：GLA State 管理
78	
79	MiniCPM-SALA 是混合注意力架构，除标准 Multi-Head Attention 外，还有大量 GLA（Gated Linear Attention）递推层。GLA 的每步输出依赖一个递推 state `hₜ`：
80	
81	```
82	hₜ = exp(−γ) · hₜ₋₁ + kₜ · vₜᵀ
83	```
84	
85	这给 tree verify 引入了不同于标准 KV cache 的状态管理问题：树中的 sibling 分支必须从**同一 parent state** 出发，而非线性继承前一候选的 state，否则会引入错误的历史依赖。我们针对 verify 路径做了专门的 GLA state 分叉处理，确保混合架构下 tree verify 的语义正确性。
86	
87	此外，Medusa head 的训练数据分布与线上推理场景的匹配度对 accept rate 影响显著。我们基于验证集分布特征对训练数据做了加权采样，使训练集分布向实际推理场景对齐，accept rate 相比随机采样有可测量的提升。
88	
89	### 实验结果
90	
91	Medusa K=1 在 MiniCPM-SALA 上的 verify overhead 约为 0.39 ms，远低于一次正常 decode step 的耗时。各并发级别下 decode 阶段端到端吞吐均有稳定正向收益。

99	draft 模型通常以较短上下文为主进行训练（否则训练成本不可控）。线上推理时如果 ctx 长度大幅超出 draft 见过的训练分布，位置嵌入处于外推区间，draft 的内部表示与训练时偏离，预测精度衰减。这一点 LLaMA / Qwen / Yi 系列在自身长上下文扩展时都遇到过类似现象，rope_theta 调整是一个公开的常规手段。

101	**归因二：draft KV 误差累积**
102	draft 在 autoregressive 跑 K 步时，每一步都基于自己前几步的 KV cache。短上下文下这些 KV 与 target 的偏差还能被 verify 阶段吸收；长上下文下 KV 序列变长，误差随序列长度放大，前几步的偏差会被后几步继续放大，K 步走完时 draft 的内部状态已经离 target 较远。
103	
104	**归因三：主路径稀疏化与训练分布的不一致**
105	长上下文下 target 模型通常会切到稀疏 attention 路径（在我们的 setting 下是 InfLLM-v2 的 compress→stage1→stage2 三段式）。draft 训练时见到的 target hidden state 来自 dense attention，线上线下两个分布存在系统性偏差。这个偏差有多大、能不能通过训练侧补齐，是一个开放问题。
106	
107	**归因四：长上下文 token 分布的"局部低熵幻觉"**
108	直觉上长上下文会让后续 token 更"可预测"——上下文越多，下一 token 的不确定性越低，accept rate 应该升。但这个直觉只在 draft 训练分布与推理分布**一致**时成立。如果 draft 是在短 ctx 上训的，它对"低熵"这件事根本没有合适的先验，反而会在长 ctx 上输出过于发散的预测，accept rate 不升反降。
109	
110	四条归因里，前两条是结构性的，后两条与训练数据组织高度相关。这一块我们仍在持续迭代，现在没有可作为最终结论分享的部分。
111	
112	---
113	
114	## 06 真问题之二：高并发下推测解码的反向风险
115	
116	一个在论文里被反复提及、但部署时容易被忽略的事实：**推测解码的收益曲线随 batch size 单调下降，足够大的 batch 下会反向**。
117	
118	简单分析：
119	
120	**小 batch（1~4）**：
121	GPU 严重 underutilized。target 单次 forward 处理一个 token 和处理 K+1 个候选的耗时差距很小（被 memory-bound 阶段的权重搬运主导）。这时 verify 几乎"免费"，spec_steps 越大越赚，accept rate 是唯一限制。
122	
123	**中等 batch（8~32）**：
124	GPU 利用率开始上来，verify 不再免费——target 一次 forward 要并行处理 `batch × (K+1)` 个 token。当 K 较大时，verify 阶段的算力开销开始挤占 decode 时间，spec_steps 需要根据 accept rate 动态选择，否则容易出现"接受率没涨够、verify 时间却涨了"的反向区间。
125	
126	**大 batch（64+）**：
127	GPU 已经接近 compute-bound。此时 target 一次 forward 的耗时与 batch×token 数近似线性。spec decoding 实际上是用 `batch × (K+1)` 的算力开销，去换 `平均接受 token 数 ≤ K` 的产出。当 accept rate × K 不足以覆盖这个开销时，**关掉推测解码反而是端到端最优解**。
128	
129	也就是说，"是否启用推测解码"和"用多大 spec_steps"在生产环境里都不应该是固定参数。在线服务的 batch size 是动态变化的：低峰期接近串行，高峰期 batch 直接打满。一个用固定 spec_steps 跑一切的 server，要么牺牲低峰期的 spec 收益，要么在高峰期被 verify overhead 反向拖累。
130	
131	这是 spec decoding 论文里讨论了多年但工程落地里很少被认真处理的问题。我们在这条线上做了一些尝试，思路上是让推测解码的强度根据系统负载动态调整——具体的实现细节这里不展开，留待后续逐步分享。
132	
133	---
134	
135	## 07 总结
136	
137	回头看这一段时间在推测解码上的演进，几条经验：
138	
139	- **方法选择没有银弹**：Medusa 适合快速起步、对训练流水要求低；EAGLE 上限更高但工程代价显著上升。开发节奏紧的时候，先 Medusa 跑出可见收益、再切 EAGLE 做精，比一上来就上 EAGLE 更稳。
140	- **训练数据决定 accept rate 上限**：draft 训练数据必须由 target 自己生成，且分布要尽量贴近线上推理场景。这件事 EAGLE 论文写得很清楚，但我们一开始也偷懒踩过坑。
141	- **长上下文与高并发是两个真正难的方向**：前者是模型与数据分布问题，后者是系统调度问题，二者的工程难度都比"换一个 draft 架构"高一档。
142	
143	EAGLE-3 是我们规划里的下一步，长上下文衰减与高并发动态调度是同期会持续投入的两条线。也许第九周第十周还会有得讲。
144	
145	感谢 SOAR 2026 组委会、SGLang 与 OpenBMB 的开源工作；感谢前几支队伍开放分享的技术博客让我们少走弯路；也感谢 Claude 与 ChatGPT——作为两个完全没有 infra 背景的本科生，很多系统层面的问题是和 AI 反复对话中才一点点摸清楚的。比赛仍在继续，期待与各位选手切磋。

39	训练时 W₁ 从零开始，保证初始阶段 head 输出等价于主模型，收敛更稳。Verify 阶段，各 head 的 top-s 候选做笛卡尔积组成一棵树，配合 tree attention mask 一次 forward 验完。
40	
41	工程上很友好：参数增量小、不需要 draft 跑 autoregressive、训练简单。
42	
43	但天花板也在这：
44	
45	- 各 head 独立预测，彼此之间没有共享的 step-by-step 上下文——第 2 个 head 不知道第 1 个 head 预测了什么。本质上每个 head 都是从同一个 hidden state 做一次浅层映射，位置越靠后越吃力。

48	我们在 MiniCPM-SALA 上跑通了 Medusa K=1，端到端有正向收益。但继续加 head 的时候发现曲线很快趋平——这不是工程实现的问题，是结构本身的上限。

50	---

52	## 03 EAGLE：让 draft 自回归地跑起来
53	
54	**EAGLE**（Li et al., arXiv:2401.15077）做了一个关键改动：**draft 本身就是一个自回归的小模型**。两个设计要点：
55	
56	1. **输入是 target 的 hidden state 而非 token embedding**。draft 直接拿 target 已经压缩过的中间特征做输入，用远小于 target 的容量就能比较好地逼近 target 的输出分布。
57	2. **draft 自己跑 K 步 autoregressive**。每步的输入来自上一步的输出 hidden，draft 内部有连贯的递推上下文——这恰好是 Medusa 各 head 之间缺的东西。
58	
59	代价也很直接：
60	
61	- 需要独立训一个 draft model，存一份权重；
62	- 训练数据必须由 target 自己生成。这一点 EAGLE 原文讲得很明确——draft 要学的是 target 的输出分布，不是数据集里的"标准答案"。我们一开始想偷懒直接拿 SFT 数据训，accept rate 怎么都上不去，后来回去仔细看论文才意识到这个约束；
63	- 混合注意力架构（GLA + 标准 Attention）下，draft 的隐状态和位置编码要跟 target 对齐，verify 路径上 GLA 的递推 state 也需要正确处理。
64	
65	accept rate 上限的提升是切实的。对我们来说，从 Medusa 到 EAGLE 不是"换一个更花哨的方法"，而是从"已经摸到天花板"切换到"上方还有空间"。

69	## 04 为什么还没上 EAGLE-3
70	
71	EAGLE-3（Li et al., arXiv:2503.01840）在 EAGLE 基础上做了几项改进：
72	
73	- **多层特征融合**：draft 输入不再只取 target 最后一层，而是融合中间层特征；
74	- **training-time test**：训练时注入 autoregressive 累积误差的模拟噪声，让 draft 学会在不完美输入下也能预测；
75	- **不再复用 token embedding**：draft 完全独立于 target 的 embedding 层。
76	
77	论文的 setting 下效果明确，但放到 MiniCPM-SALA 上工程量不小。这个模型是 8 个标准 Attention 层 + 24 个 GLA 层的混合架构，"多层特征融合"意味着 draft 要同时消化两类层的输出，特征空间差异比同构模型大。training-time test 则要求数据采集管线跟线上 verify 路径严格对齐，改动不算小。
78	
79	我们目前的判断是先在 EAGLE 这一层把训练数据和混合架构适配做收敛，再考虑往上推一档。节奏上是"稳住再进"，不是能力不够，而是时间预算有限时优先保证已有收益的稳定性。
80	
81	---
82	
83	## 05 长上下文下的 accept rate 衰减
84	
85	实测中观察到一个一致的现象：**推测解码在长上下文下 accept rate 会系统性下降**。这不是某一种 draft 的问题，几条原因叠加在一起：
86	
87	**位置编码外推。** draft 训练时通常以较短上下文为主（长 ctx 训练成本太高），推理时序列长度超出训练分布后位置嵌入进入外推区间，draft 内部表示偏离训练时的分布。这一点并不新鲜，LLaMA 和 Qwen 系列做长上下文扩展时都遇到过，rope_theta 调整是常规手段。
88	
89	**draft KV 误差累积。** draft 自回归跑 K 步时，每步都依赖自己前几步的 KV cache。短上下文下偏差尚在 verify 的吸收范围之内；长上下文下 KV 序列变长、每步的微小偏差沿序列方向逐步放大，K 步跑完时 draft 的内部状态可能已经偏离 target 较远。
90	
91	**主路径稀疏化带来的分布偏移。** 长上下文下 target 会切到稀疏 attention 路径（MiniCPM-SALA 走的是 InfLLM-v2 的 compress → block scoring → top-K sparse 三段）。但 draft 训练时见到的 target hidden state 通常来自 dense attention。这两个分布之间存在系统性差异，差异有多大、训练侧能不能补齐，目前没有定论。
92	
93	**"低熵幻觉"。** 直觉上更长的上下文会让下一 token 更可预测——不确定性降低，accept rate 应该上升。但这只在 draft 的训练分布与推理分布一致时成立。如果 draft 是短 ctx 训的，面对长 ctx 时它缺乏对应的先验，输出分布反而比实际更发散，accept rate 不升反降。
94	
95	前两条是结构性的，后两条跟训练数据怎么组织直接相关。我们在这块还在迭代，暂时没有成熟到可以分享的结论。
96	
97	---
98	
99	## 06 高并发下推测解码可能反向
100	
101	还有一件在论文里讨论过、但工程上容易被忽略的事情：**推测解码的收益随 batch size 上升而衰减，batch 足够大时会变成负收益**。
102	
103	原因不复杂：
104	
105	**小 batch 时**，GPU 算力严重空闲，target 处理 1 个 token 和处理 K+1 个候选的耗时几乎相同——瓶颈在权重搬运，不在计算。这时 verify 接近免费，spec_steps 越大越赚。
106	
107	**中等 batch 时**，GPU 利用率上来了，verify 开始有真实的算力代价。target 一次 forward 要并行处理 batch × (K+1) 个 token，K 大了之后 verify 阶段的额外耗时开始跟 spec 带来的 token 产出打架。
108	
109	**大 batch 时**，GPU 接近满载。target forward 的耗时跟处理的 token 总量近似线性。推测解码相当于用 batch × (K+1) 的计算量去换 ≤ K 个额外 token——如果 accept rate 不够高，这笔账算不过来，不如直接 decode。
110	
111	问题在于在线服务的 batch size 不是固定的：低谷期只有几个请求在跑，高峰期 batch 可能打到很大。固定 spec_steps 的配置意味着你要么放弃低峰期的 spec 收益（设得小），要么承担高峰期的反向风险（设得大）。这个 tradeoff 在学术论文里被讨论得不少（Sequoia、SpecInfer 等工作都有涉及），但真正部署时如何平衡，依然是一个开放问题。
112	
113	---

121	- 长上下文的 accept rate 衰减和高并发下的反向风险，是两个比"选哪个 draft 架构"更本质的问题。前者是模型与数据的分布问题，后者是系统层面的资源分配问题。

## 01 推测解码简要回顾

大模型 decode 阶段是 memory-bound 的——每产一个 token，整张权重矩阵从显存搬一遍，计算单元大部分时间在等数据。推测解码的想法很直接：

> 用一个轻量的 draft 提前猜 K 个候选 token，再让 target 一次 forward 并行 verify。输出分布严格不变，但一次 forward 能"带出"多个 token。

收益取决于三件事：draft 每个 token 的生成代价、候选被接受的比例（accept rate）、以及 target verify 时因为多处理了 K 个候选而额外付出的时间。三项任何一个失衡，收益就会打折甚至反向。

---

## 02 Medusa：在主模型上接几个预测头

**Medusa**（Cai et al., ICML 2024）的思路是不引入独立 draft model，直接在 target 最后一层 hidden state 上挂 K 个轻量 MLP head，每个负责预测后续第 k 个位置：

```
p_t^(k) = softmax( W₂⁽ᵏ⁾ · ( SiLU(W₁⁽ᵏ⁾ · h_t) + h_t ) )
```

训练时 W₁ 从零开始，保证初始阶段 head 输出等价于主模型，收敛更稳。Verify 阶段，各 head 的 top-s 候选做笛卡尔积组成一棵树，配合 tree attention mask 一次 forward 验完。

工程上很友好：参数增量小、不需要 draft 跑 autoregressive、训练简单。

但天花板也在这：

- 各 head 独立预测，彼此之间没有共享的 step-by-step 上下文——第 2 个 head 不知道第 1 个 head 预测了什么。本质上每个 head 都是从同一个 hidden state 做一次浅层映射，位置越靠后越吃力。
- K 增大时候选树指数膨胀，verify 开销涨得比 accept rate 快。

我们在 MiniCPM-SALA 上跑通了 Medusa K=1，端到端有正向收益。但继续加 head 的时候发现曲线很快趋平——这不是工程实现的问题，是结构本身的上限。

---

## 03 EAGLE：让 draft 自回归地跑起来

**EAGLE**（Li et al., arXiv:2401.15077）做了一个关键改动：**draft 本身就是一个自回归的小模型**。两个设计要点：

1. **输入是 target 的 hidden state 而非 token embedding**。draft 直接拿 target 已经压缩过的中间特征做输入，用远小于 target 的容量就能比较好地逼近 target 的输出分布。
2. **draft 自己跑 K 步 autoregressive**。每步的输入来自上一步的输出 hidden，draft 内部有连贯的递推上下文——这恰好是 Medusa 各 head 之间缺的东西。

代价也很直接：

- 需要独立训一个 draft model，存一份权重；
- 训练数据必须由 target 自己生成。这一点 EAGLE 原文讲得很明确——draft 要学的是 target 的输出分布，不是数据集里的"标准答案"。我们一开始想偷懒直接拿 SFT 数据训，accept rate 怎么都上不去，后来回去仔细看论文才意识到这个约束；
- 混合注意力架构（GLA + 标准 Attention）下，draft 的隐状态和位置编码要跟 target 对齐，verify 路径上 GLA 的递推 state 也需要正确处理。

accept rate 上限的提升是切实的。对我们来说，从 Medusa 到 EAGLE 不是"换一个更花哨的方法"，而是从"已经摸到天花板"切换到"上方还有空间"。

## 05 长上下文下的 accept rate 衰减

实测中观察到一个一致的现象：**推测解码在长上下文下 accept rate 会系统性下降**。这不是某一种 draft 的问题，几条原因叠加在一起：

**位置编码外推。** draft 训练时通常以较短上下文为主（长 ctx 训练成本太高），推理时序列长度超出训练分布后位置嵌入进入外推区间，draft 内部表示偏离训练时的分布。

---

## 06 高并发下推测解码可能反向

还有一件在论文里讨论过、但工程上容易被忽略的事情：**推测解码的收益随 batch size 上升而衰减，batch 足够大时会变成负收益**。

原因不复杂：

**小 batch 时**，GPU 算力严重空闲，target 处理 1 个 token 和处理 K+1 个候选的耗时几乎相同——瓶颈在权重搬运，不在计算。这时 verify 接近免费，spec_steps 越大越赚。

**中等 batch 时**，GPU 利用率上来了，verify 开始有真实的算力代价。target 一次 forward 要并行处理 batch × (K+1) 个 token，K 大了之后 verify 阶段的额外耗时开始跟 spec 带来的 token 产出打架。

**大 batch 时**，GPU 接近满载。target forward 的耗时跟处理的 token 总量近似线性。推测解码相当于用 batch × (K+1) 的计算量去换 ≤ K 个额外 token——如果 accept rate 不够高，这笔账算不过来，不如直接 decode。

- draft 的训练数据必须由 target 自己生成，且分布要贴近实际推理场景。论文里写得清楚，但实际中很容易低估这件事的重要性。
- 长上下文的 accept rate 衰减和高并发下的反向风险，是两个比"选哪个 draft 架构"更本质的问题。前者是模型与数据的分布问题，后者是系统层面的资源分配问题。

21	## 01 推测解码简要回顾
22	
23	大模型 decode 阶段受 memory bandwidth 约束——每生成一个 token，全部权重矩阵需从显存搬运一次，计算单元的利用率极低。推测解码的核心思路是：
24	
25	> 由轻量 draft 模型预先生成 K 个候选 token，再由 target 模型在单次 forward 中并行 verify。在保证输出分布与原模型严格一致的前提下，单次 forward 可产出多个 token。
26	
27	最终收益由三个因素决定：draft 每个候选 token 的生成代价、候选被 target 接受的比例（accept rate）、以及 target 因并行 verify K 个候选而增加的额外耗时。三者中任一项失衡，整体收益即会下降乃至转为负值。
28	
29	---
30	
31	## 02 Medusa：在主模型上附加预测头
32	
33	**Medusa**（Cai et al., ICML 2024）不引入独立 draft model，而是在 target 最后一层 hidden state 上附加 K 个轻量 MLP head，第 k 个 head 负责预测后续第 k 个位置的 token 分布：
34	
35	```
36	p_t^(k) = softmax( W₂⁽ᵏ⁾ · ( SiLU(W₁⁽ᵏ⁾ · h_t) + h_t ) )
37	```
38	
39	W₁ 初始化为零矩阵，使训练初期各 head 的输出与主模型等价，保证收敛稳定性。Verify 阶段，各 head 的 top-s 候选经笛卡尔积构成候选树，配合 tree attention mask 在单次 forward 中完成验证。
40	
41	Medusa 的工程优势在于参数增量小、无需 draft 自回归推理、训练流程简洁。
42	
43	其结构性上限同样源于此设计：
44	
45	- 各 head 独立预测，彼此之间不存在共享的递推上下文——第 2 个 head 无法获知第 1 个 head 的预测结果。每个 head 本质上都是对同一 hidden state 的一次浅层映射，预测位置越远，精度衰减越显著。
46	- K 增大时候选树规模指数膨胀，verify 开销的增长速率超过 accept rate 的提升。
47	
48	我们在 MiniCPM-SALA 上完整实现了 Medusa K=1，端到端取得正向收益。但随着 head 数量增加，accept rate 曲线迅速趋于平坦。这并非工程实现层面的问题，而是该架构固有的容量上限。
49	
50	---
51	
52	## 03 EAGLE：自回归 draft 模型
53	
54	**EAGLE**（Li et al., arXiv:2401.15077）在 draft 架构上做了根本性变更：**draft 本身是一个自回归模型**。核心设计有两点：
55	
56	1. **输入为 target 的 hidden state 而非 token embedding。** draft 接收 target 中间层已压缩的语义特征作为输入，以远小于 target 的参数量即可有效逼近 target 的输出分布。
57	2. **draft 自身执行 K 步自回归推理。** 每步以上一步的输出 hidden state 作为输入，因此 draft 内部具备连贯的递推上下文——这正是 Medusa 各 head 之间所缺乏的。
58	
59	从 Medusa 迁移至 EAGLE 后，accept rate 上限有实质性提升。
60	
61	---
62	
63	## 04 长上下文下的 accept rate 衰减
64	
65	实测中观察到一个一致的现象：**推测解码在长上下文条件下 accept rate 呈系统性下降**。这并非某一种 draft 架构的特有问题，而是多个独立机制叠加的结果。
66	
67	**位置编码外推。** draft 模型的训练通常以较短上下文为主（受训练成本约束）。当推理时序列长度显著超出训练分布时，位置嵌入进入外推区间，draft 的内部表示与训练阶段产生偏离，预测精度随之下降。
68	
69	**draft KV 误差累积。** draft 在自回归执行 K 步推理时，每步均依赖前序步骤生成的 KV cache。短上下文条件下，这些 KV 与 target 之间的偏差尚在 verify 阶段的容忍范围内；长上下文条件下，KV 序列长度增加，各步的微小偏差沿序列方向逐步放大，K 步执行完毕时 draft 的内部状态可能已显著偏离 target。
70	
71	---
72	
73	## 05 高并发下推测解码的反向风险
74	
75	一个在学术文献中已有讨论、但工程部署时常被忽视的问题：**推测解码的收益随 batch size 增大而递减，在 batch 足够大时转为负收益**。
76	
77	**小 batch 条件下**，GPU 计算资源严重闲置，target 处理 1 个 token 与处理 K+1 个候选的耗时差异极小——瓶颈在于 memory bandwidth 而非算力。此时 verify 的边际代价接近零，spec_steps 增大即可直接转化为吞吐收益。
78	
79	**中等 batch 条件下**，GPU 利用率提升，verify 开始产生实际的算力开销。target 单次 forward 需并行处理 batch × (K+1) 个 token，verify 阶段的额外耗时与推测解码带来的 token 产出增益逐渐接近平衡。
80	
81	**大 batch 条件下**，GPU 接近 compute-bound 状态，target forward 耗时与处理的 token 总量近似线性相关。推测解码以 batch × (K+1) 的计算开销换取 ≤ K 个额外 token，当 accept rate 不足以覆盖该开销时，直接 decode 反而是端到端更优的选择。
82

84	
85	## 06 总结
86	
87	本文回顾了推测解码在 MiniCPM-SALA 上从 Medusa 到 EAGLE 的演进过程，并分析了长上下文与高并发两个场景下的核心挑战。几个结论：
88	
89	- Medusa 适合在开发周期紧迫时快速建立基线，EAGLE 的 accept rate 上限更高但工程投入相应增大。先以轻量方案验证收益、再迁移至更重的架构，是更稳健的路径。
90	- draft 的训练数据须由 target 自身生成，且分布应贴近实际推理场景。这一约束在论文中已有明确论述，但实践中容易被低估。
91	- 长上下文下的 accept rate 衰减与高并发下的反向风险，是比 draft 架构选择更为根本的问题。前者涉及模型与数据的分布匹配，后者涉及系统层面的资源分配，二者的工程难度均高于架构迁移本身。
