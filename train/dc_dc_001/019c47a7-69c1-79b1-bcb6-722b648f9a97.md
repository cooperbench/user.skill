**1) “按 shard 合并/拼接再 H2D” 是什么意思？** 这里的 *shard* 指的是一个权重分片文件，比如 text encoder 的 `model-00001-of-00004.safetensors` 这种。一个 shard 里往往有很多很多个 tensor（参数块）。 你现在的“加载到 GPU”路径基本是： - 对每个 tensor：CPU tensor →（一次 H2D copy）→ GPU tensor - 这会触发成千上万次小拷贝 + 对应的调度/同步/事件开销（尤其 DiT 这种 4000+ tensors） “按 shard 合并/拼接再 H2D”的想法是：**把一个 shard 里的很多小 tensor，先在 CPU 侧打包成少量几个大块（通常按 dtype 分组），然后用更少次数的大 H2D copy 一次性传到 GPU**。传到 GPU 后，再用切片/view 的方式把大块拆回原来的各个权重（前提是同 dtype 才能无拷贝地 view/切片）。 直观理解： - **Pinned host memory + `non_blocking=True`** pageable（unpinned）内存通常会走“先拷到内部 pinned staging buffer，再 DMA”的路径，等于多一次 CPU memcpy + 更多同步，很多场景能差 1.2x~数倍。 - **复用 pinned buffer（pinned 内存池）** 不要每次临时 pin/分配，尽量复用一批 pinned staging buffers（尤其在多次 load/offload、或流水线加载时）。 ### B. 减少“小拷贝次数”和“每 tensor 开销”（对你最关键） - **按 dtype 打包**（可落地、不会破坏数值） 因为 PyTorch 不能把一个 `uint8` 大 buffer “零拷贝 reinterpret”成任意 dtype 的 tensor，所以实务上通常是： - bf16 tensors 打包成一个 bf16 大 tensor - fp16 tensors 打包成一个 fp16 大 tensor - int8 tensors 打包成一个 int8 大 tensor 然后一次 H2D 传大块，再用 `narrow`/切片拿回每个参数视图。 - **减少 GPU allocation 次数** 很多时候“慢”不全是拷贝慢，而是： - 每个 tensor 都要 `cudaMalloc`/allocator bookkeeping（即便有 caching allocator，4000 次也很重） 成熟做法是：**预先分配少量大块 GPU buffer**，然后把每个权重放在其中的一个 slice 里（也是 flat 思路的一部分）。 > 这也解释了你之前测到 DiT pinned/unpinned 差异不明显：DiT tensor 极碎，固定开销（分配/调度/事件）可能已经主导，是否 pinned 的优势就被淹没了。 ### C. 让“加载过程”更像流水线（进一步优化） - **多线程/双缓冲预取**：CPU 线程 A 读盘+解码+pin，线程 B 做 H2D，GPU stream 异步拷贝；尽量让 PCIe 传输和 CPU 工作重叠。 - **（如果硬件/系统支持）GPUDirect Storage**：让 NVMe → GPU 直接 DMA，绕过 CPU copy。这是“终极方案”，但依赖环境，不一定可用。 --- **如果你想继续用我们现有 benchmark 推进优化** 我建议下一步做两件事（都很有信息量）： 1) 用脚本里的 `--include-alloc` 跑一次 H2D（更贴近真实 `tensor.to('cuda')` 的“分配+拷贝”总成本），看你瓶颈到底偏 allocation 还是 memcpy。 2) 我可以把 benchmark 加一个 `--pack-by-dtype` 模式：统计 DiT/text encoder 这种碎 tensor，打包后 H2D 能从 ~8–12 GB/s 拉到多少（通常会明显更接近 synthetic）。 你更想先确认“allocation 占比”（跑 `--include-alloc`），还是直接上“pack-by-dtype”看收益上限？
