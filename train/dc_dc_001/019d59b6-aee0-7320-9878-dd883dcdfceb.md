   证据最强的是 [minicpm_backend.py#L1834](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1834) 这一段 CUDA graph replay 初始化。这里每轮 decode 都在做大量 `copy_`，还显式 `torch.cuda.synchronize()`，并且对大块 `compress_k1/k2` 做 `fill_(-inf)`，见 [minicpm_backend.py#L1943](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1943) 和 [minicpm_backend.py#L1951](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1951)。
   方向是：去掉全量清空，改成只写有效区间；减少 wrapper `begin_forward` 频次；尽量移除 replay 外的全局同步；把多组 metadata 合并成更粗粒度更新。

2. **P1: 重写 sparse metadata builder，减少 Python/CPU 参与**
   [minicpm_sparse_utils.py#L902](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py#L902) 到 [minicpm_sparse_utils.py#L1441](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py#L1441) 里有很多 Python loop、`.tolist()`、CPU tensor 构造再搬回 GPU。尤其是 `build_token_mappings`、`build_sparse_prefill_metadata`、`build_sparse_decode_metadata`。这类开销在高并发 decode 下很容易盖过 kernel 本身。
   方向是：全部改成张量化前缀和、`repeat_interleave`、mask/select；能常驻 GPU 的 metadata 就别来回上下搬；decode 场景优先做增量更新，而不是每步重建。

3. **P2: 调度层 prepare_for_decode / extend 仍有明显 CPU 编排成本**
   [schedule_batch.py#L1454](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1454) 和 [schedule_batch.py#L1939](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/managers/schedule_batch.py#L1939) 里，稀疏相关 token 数、压缩长度、`cu_seqlens` 等有重复计算，且大量发生在 CPU。这个层面如果不收，后面 kernel 再快也吃不到。
   方向是：把 decode 的 sparse 长度计算改成就地增量维护；把 extend/decode 共用公式抽出来，避免重复构造 CPU 中间态。

4. **P3: MiniCPM hybrid 层让 piecewise CUDA graph 失效，值得单独攻**
   在 [model_runner.py#L2014](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/model_runner.py#L2014) 到 [model_runner.py#L2048](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/model_runner.py#L2048)，只有带 `.attn`/`.attn_mqa` 的层会被计入；但 `MiniCPMLightningMixer` 没这个接口，见 [minicpm.py#L235](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py#L235)。结果是 attention layer 数不齐时直接禁用 piecewise graph。
   如果你的模型里 hybrid/lightning 层占比不低，这会让 extend/prefill 白白退回普通路径。这个方向工程量大于 P0/P1，但潜在收益也大。

5. **P4: 最后才考虑 NVFP4 线性层再做 kernel 级融合**
   [modelopt_quant.py#L1313](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/quantization/modelopt_quant.py#L1313) 这条路里，CUTLASS 路径仍有 `pre_quant_scale` 和 `fp4_quantize` 的动态激活量化成本。这里不是没空间，但改动会更深、更风险，而且我现在不认为它是第一瓶颈。

**为什么我不建议先冲 kernel fusion**

[MiniCPMAttention.forward](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py#L213) 和 [MiniCPMDecoderLayer.forward](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/models/minicpm.py#L508) 这条主干上的 RMSNorm、SiLU+Mul、residual add 已经不算“特别松”。相反，真正肉眼可见的浪费，集中在 attention backend 外围和 batch prepare。

**我给你的结论**

如果你要我只选一个最值得深入做的方向，我会选：

1. `minicpm_backend.py` 的 sparse decode replay/metadata 更新路径  
2. `minicpm_sparse_utils.py` + `schedule_batch.py` 的 CPU/Python 元数据构造  
3. `model_runner.py` 上 MiniCPM hybrid 的 piecewise CUDA graph 支持

这三个方向比继续抠单个 matmul 或轻量 fusion，更像是现在这套代码里真正还没吃干净的性能空间。

**P0 执行链**

decode + CUDA graph 下，实际顺序是：

1. [cuda_graph_runner.py#L826](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/model_executor/cuda_graph_runner.py#L826) 先调 [minicpm_backend.py#L1834](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1834) 做 replay 前 metadata 刷新。
2. 这里会做大量 `copy_`，调用 `wrapper.begin_forward()`，然后直接 `torch.cuda.synchronize()`，见 [minicpm_backend.py#L1928](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1928) 和 [minicpm_backend.py#L1944](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1944)。
3. 图内真正执行 attention 时，每层又会先算 topk，再写 `sparse_page_table`，见 [minicpm_backend.py#L1236](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1236)。
4. 随后 [minicpm_attention_kernels.py#L328](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_attention_kernels.py#L328) 里又把 `sparse_page_table` 转成 FlashInfer 需要的 `kv_indptr/kv_indices`。

所以现在不是“一个准备阶段”，而是**replay 外先准备一半，forward 内再准备一半**。

**我现在最在意的几个点**

第一，`begin_forward()` 的位置很可疑。  
因为真正动态的 `sparse_page_table` 是图内每层算出来的，所以 replay 外的 [minicpm_backend.py#L1928](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1928) 不可能基于真实本层 topk 结果做 planning。它更像是在“刷新 wrapper 状态/地址”，不是在准备真实 page data。这个点最值得验证：**decode replay 时是否可以完全不调用 `begin_forward()`，或者至少不在每步调用。**

第二，`torch.cuda.synchronize()` 很像硬伤。  
在 [minicpm_backend.py#L1944](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1944) 这里直接全局同步，代价很大。如果 `begin_forward()` 只是刷新地址，而后续 graph replay 和这些写操作本来就在同一执行序列上，那这一步很可能可以删掉，或者至少改成更细粒度的 event/stream 依赖。

第三，`compress_k1/k2` 全量 `fill_(-inf)` 不一定都需要。  
见 [minicpm_backend.py#L1951](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1951)。常规路径下，压缩 key 的消费者主要靠 `cu_seqlens` 限定有效区间，见 [minicpm_sparse_utils.py#L511](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py#L511)。这部分大概率可以改成“只写有效前缀，不清空整块”。  
但 `split_stage1=True` 时，分支会按整块 reshape 读满 `k.shape[0]`，见 [minicpm_sparse_utils.py#L483](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py#L483)，这里不能直接删清空，要分路径处理。

第四，replay 里有两块很重的表复制。  
[minicpm_backend.py#L2027](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L2027) 和 [minicpm_backend.py#L2028](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L2028) 每步都把 `req_to_sparse_k1_token` / `k2_token` 整块拷到 metadata。这个方向很有潜力：**压缩 kernel 直接吃全局表 + `req_pool_indices`，避免物化 `k1.table/k2.table`。**

第五，`sparse_page_table -> flashinfer` 转换本身也还不够干净。  
现在的 Triton 实现是两段：一个单 CTA 顺序 cumsum，再一个 flatten kernel，见 [minicpm_sparse_kernels.py#L589](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_kernels.py#L589)。这个开销未必是第一瓶颈，但如果前面的 replay-side 刷新被砍掉，它就会变得更显眼。

**我建议的 P0 顺序**

1. 先验证 decode replay 里 `begin_forward()` 是否真需要每步调用。  
如果不需要，连带 `kv_indptr_backup` restore 和 `torch.cuda.synchronize()` 都有机会一起拿掉。

2. 再分路径处理 `compress_k1/k2` 清空。  
先只在 `split_stage1=False` 的默认路径里去掉全量 `fill_(-inf)`，风险最低。

3. 然后看 `k1.table/k2.table` 物化是否能取消。  
这是我认为比“再抠一个小 kernel”更像真增益的点。

如果你认同，我下一步就不泛谈了，直接继续做一版 **P0 细化设计**：把这三个点分别拆成“改动面、风险、验证方法、预期收益”。

**2. 真正大的点：全量清空压缩缓存**

- `compress_k2.fill_(-inf)`

- `bs=1`: 每步清 `20 MB`
- `bs=8`: 每步清 `160 MB`

- `bs=8` 这一步大概就是 `0.1~0.4 ms`
- `bs=64` 可能到 `0.8~2.5 ms`

这已经足够决定 S8/Smax 的尾部表现了。

**3. 准确度风险**

这里要分开说。

几乎不影响准确度的：

- 去掉或缩小 `compress_k1/k2` 的全量 `fill_`
- 不再物化 `k1.table/k2.table`，直接让 kernel 吃全局表 + `req_pool_indices`
- 把小 metadata 构造改成张量化/增量更新

这些本质都是 **metadata 和 buffer 管理优化**，不改 attention 数学。

但有一个例外：

- `torch.cuda.synchronize()` 在 [minicpm_backend.py#L1944](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py#L1944)

这个改动理论上也不该影响数值，但它是 **时序正确性** 风险，不是数值误差风险。删错了不会“轻微掉点”，而是可能直接读到旧 buffer，结果错得很明显。所以它不是不能动，而是验证门槛更高。

**4. 对 TPS 的预期**

我现在更保守，也更有把握：

- 只删 `torch.cuda.synchronize()`：
  - 预期 `0~1%`
  - 很可能是噪声级
- 只优化 `convert_sparse_page_table_to_flashinfer()`：
  - 预期 `<1%`
  - 不值得优先做
- 去掉默认路径下的全量 `fill_(-inf)`：
  - `S1`: 约 `1~3%`
  - `S8`: 约 `3~8%`
  - 高 batch / 长上下文极端场景：`5~12%` 有可能
- 再叠加 `k1.table/k2.table` 物化消除和小 metadata copy 收缩：
  - 总体更像 `4~10%` 的方向
  - 我不觉得这一组 P0 能单独带来 `20%+`

这里我特意说“方向”而不是“保证”，因为 `fill_` 的真实代价会受当前 batch size、stream 重叠、显存带宽占用影响。

**一个很关键的边界条件**

你们当前常用配置里 `split_stage1=false`，这个在 [bench/sglang_0404_16_custom.jsonl](/user_4813494d/openbmb/bench/sglang_0404_16_custom.jsonl) 和 [sglang_0403_8_custom.jsonl](/user_4813494d/openbmb/sglang_0403_8_custom.jsonl) 里都能看到。  
这很重要，因为 [minicpm_sparse_utils.py#L483](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_sparse_utils.py#L483) 的 `split_stage1` 分支会按整块 reshape 去读 `k.shape[0]`，那条路径不能直接删清空。也就是说：

- **默认部署路径下，清空优化是安全候选**
- **`split_stage1=true` 时，不能照搬**
