**结论先说** LongSpec 对长上下文 speculative decoding 的核心判断成立：acceptance collapse 不是单一 runtime bug，而是“位置分布偏移 + draft 有效上下文/隐状态漂移 + 长上下文 verify 成本”叠加。对你们现在“最大 input+output <= 200K，16K train window + AOI on long shards”的路线，我建议继续做 AOI，但要修两个高风险点：`AOI_CAP` 不应只覆盖 prompt 最大值，且 draft RoPE 训练/推理 theta 必须一致。 **LongSpec 复核** 1. AOI / sink-position interpolation LongSpec 不是改 RoPE 插值公式，而是改训练时 `position_ids`：保留前 4 个 attention sink，小于阈值的短样本把后续 token 平移到随机大 offset。论文伪代码是 `P[4:] += RandomInt(0, MAX_LEN-N)`；本地实现里 `sink=random.randint(0,4)`，然后 `position_ids[:, sink:] += random_offset`，见 [qwen2_glide.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2_glide.py:524) 和 [qwen2.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2.py:739)。论文明确说 target/draft RoPE base 必须一致，不能随意用 RoPE extrapolation 替代 AOI；外部来源：[LongSpec arXiv](https://arxiv.org/abs/2502.17421)、[LongSpec PDF](https://arxiv.org/pdf/2502.17421)。 2. 阶段训练 论文是三段：SlimPajama 短上下文 + AOI；ProLong-64K 长上下文；自建 long-context SFT。后两段使用 vanilla position，因为数据已经足够长。实现中短上下文 base 配置是 [qwq_glide_8gpu_slim6b.yaml](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/conf/exp/qwq_glide_8gpu_slim6b.yaml:15)，长上下文 32K 配置是 [qwq_glide_8gpu_slim6b_sinkpi-slicing_longv2-32k-zero3_5e-6-ligce-nomask.yaml](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/conf/exp/qwq_glide_8gpu_slim6b_sinkpi-slicing_longv2-32k-zero3_5e-6-ligce-nomask.yaml:15)，LongCoT 再训配置是 [longcot yaml](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/conf/exp/qwq_glide_8gpu_slim6b_sinkpi-slicing_longv2-32k-zero3_5e-6-ligce-nomask_longcot_5e-6.yaml:15)。训练超参：8x A100 80GB、CE、target frozen、短数据 lr 5e-4、长数据 lr 5e-6、1 epoch；论文附录 D。 3. 长样本阈值 本地代码里 LongSpec 只对 `input_ids.size(1) <= 1200` 的短样本启用 AOI，超过 1200 走自然位置，见 [qwen2_glide.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2_glide.py:525) 和 [qwen2.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2.py:741)。评测也过滤 `1200 < len <= context_length`，见 [inference_long-bench.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/test/inference_long-bench.py:122)。这和论文设计一致：AOI 用来把短训练样本投到长位置；真实长样本不再需要 AOI。 4. RoPE 处理 LongSpec 使用 target config 的 RoPE 实现，`Qwen2RotaryEmbedding` 支持 `rope_scaling` 和 dynamic update，见 [qwen2.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2.py:93) 和 [qwen2.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2.py:139)。AOI 只是把 altered `position_ids` 输入 `rotary_emb`，见 [qwen2_glide.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/train/models/qwen2_glide.py:547)。你们当前 v4 代码里 `ROPE_THETA=10000`，但注释说 inference config 是 `1e6`，见 [train_v4.py](/user_4813494d/openbmb/eagle/train_v4/train_v4.py:82)，这是最大风险之一。 5. 评测设置 LongSpec LongBench 使用 GovReport/QMSum/Multi-News/LCC/RepoBench-P，默认 `tree_shape=[4,16,16,16,16]`、`max_gen_len=1024`、T=0/T=1，见 [README.md](/user_4813494d/openbmb/research/longspec/LongSpec/README.md:73) 和 [inference_long-bench.py](/user_4813494d/openbmb/research/longspec/LongSpec/longspec/test/inference_long-bench.py:64)。QwQ LongCoT 本地 README 命令是 `max_gen_len=20000`，论文表述和网页写 32K 输出，见 [README.md](/user_4813494d/openbmb/research/longspec/LongSpec/README.md:87)。论文报告 AOI 消融：Multi-News τ 3.20→3.36，RepoBench-P τ 3.26→3.39；LongCoT QwQ AIME24 18.92→42.63 tok/s，τ=3.82。 **外部方法定位** - LongSpec：训练 draft + AOI + cache-free cross-attn + hybrid tree attention，最系统，但对你们是中到大型重构。来源：[paper](https://arxiv.org/abs/2502.17421)、[repo](https://github.com/sail-sg/LongSpec)。 - SpecPV：用 partial verification 降低长上下文 verify 成本，面向 300K 级上下文，代价是非严格 lossless/有轻微质量风险。来源：[SpecPV arXiv](https://arxiv.org/abs/2512.02337)。 - MagicDec / TriForce：training-free、偏长 prompt 场景；LongSpec 指出它在 LongCoT 这类短 prefix + 长输出场景会退化。来源：[MagicDec arXiv](https://arxiv.org/abs/2408.11049)。 - OWL：认为 EAGLE 类方法在长上下文下受 hidden-state quality deterioration 影响，用 LSTM drafter 减少对长 prefix hidden 的依赖。来源：[OWL arXiv](https://arxiv.org/abs/2510.07535)。 - SpecExtend / cross-model retrieval：把 retrieval candidates 接入 speculative tree，适合长文本重复模板，和 EAGLE draft 互补。来源：[SpecExtend arXiv](https://arxiv.org/abs/2505.20776)、[repo](https://github.com/jycha98/SpecExtend)。 - YaRN / position scaling：能解释你们 `rope_theta=1M` 的收益，但 LongSpec 的观点是：draft 训练时仍要保持 target/draft RoPE 语义一致。来源：[YaRN arXiv](https://arxiv.org/abs/2309.00071)。 - attention sink：AOI 保留前 4 个 sink token 的理论来源，和 StreamingLLM 现象一致。来源：[StreamingLLM arXiv](https://arxiv.org/abs/2309.17453)。 **对当前 200K / 16K Window 的建议** 1. 把 `AOI_CAP` 从 144K 提到覆盖绝对 decode position。 你们的上限是 input+output <= 200K，不只是 prompt <= 136K。当前 [train_v4.py](/user_4813494d/openbmb/eagle/train_v4/train_v4.py:45) 用 `AOI_CAP=144000`，只覆盖 prompt 最大值。建议先用 `AOI_CAP=200K` 或按真实 p99 absolute position 设 `176K/208K`，再重算 `ROPE_MAX_SEQ`。当前 RoPE cache 是 `AOI_CAP + 16K*(TTT_STEPS+2)`，见 [train_v4.py](/user_4813494d/openbmb/eagle/train_v4/train_v4.py:64)。 2. 不要以为 32K/64K bucket 已经被训练到了。 builder 产出 2K/8K/16K/32K/64K，见 [build_prompts_v4.py](/user_4813494d/openbmb/eagle/train_v4/pipeline/build_prompts_v4.py:47)，但 trainer 会 `max_len = min(max_len, SEQ_LEN_MAX)`，`SEQ_LEN_MAX=16384`，见 [train_v4.py](/user_4813494d/openbmb/eagle/train_v4/train_v4.py:375)。也就是说 32K/64K 样本训练时被截到前 16K。建议要么只 collect `--max_bucket 16384`，要么在 builder 阶段把长文 stride-slice 成多个 16K 窗口，避免白采长样本。 3. AOI 应按 sample 随机，而不是 batch 共享。 当前 `aoi_position_ids()` 对整个 batch 用同一个 sink/offset，见 [train_v4.py](/user_4813494d/openbmb/eagle/train_v4/train_v4.py:87)。LongSpec batch=大时影响不明显，但你们 batch 小、样本异质，建议每个样本独立 offset，降低位置覆盖方差。 4. 训练/推理 RoPE theta 必须对齐。 你们实测 `rope_theta=1M` 对长 context al +44.9%，见 [experiments-log.md](/user_4813494d/openbmb/docs/eagle/experiments-log.md:55)。但 v4 训练还写 `10000`，这会重新制造 train/infer mismatch。建议 v4 smoke 同时训两版：`theta=1e6` 和 `theta=1e4`，按 long bucket pre-EOS accept、短 coding accept、public eval 分数决策。 5. 长输出不要只靠 […]
