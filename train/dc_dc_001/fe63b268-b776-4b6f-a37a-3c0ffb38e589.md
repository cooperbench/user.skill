> DEVELOPER

epilogue fusion是什么

> AGENT

Epilogue fusion = 把 GEMM **输出后紧跟的 element-wise / reduction 算子塞进 GEMM kernel 末尾**，省掉中间 tensor 的 HBM 来回读写。 ### 原理 一个标准 GEMM kernel 结构： ``` mainloop: A @ B → accumulator（寄存器里的 f32 block） epilogue: accumulator → 写回 HBM（就是 output tensor） ``` CUTLASS / cuBLAS 的 epilogue 阶段本身是**可编程**的 —— 在寄存器写回 HBM **之前**，插入任意 element-wise 变换。这一步对 kernel 来说几乎免费（数据已经在寄存器），但对下游算子来说消掉了一次 HBM round-trip。 ### 两个具体例子 **1. SwiGLU 融入 gate+up GEMM** 未融合： ``` gate = x @ W_gate # [M, 16384] 写 HBM up = x @ W_up # [M, 16384] 写 HBM y = silu(gate) * up # 读两遍 HBM，写一遍 HBM down = y @ W_down ``` 融合后： ``` (gate, up) = x @ [W_gate; W_up] # 单 GEMM，epilogue 直接算 silu(gate)*up y = epilogue 输出 # 只写一遍 HBM down = y @ W_down ``` - 省掉 gate、up 两个 [M, 16384] 中间 tensor 的 write + read - M=8192 时 = 32768×16384×2B = 1 GB HBM 流量消失 **2. RoPE 融入 QKV GEMM** 未融合：QKV 先算出写 HBM，RoPE kernel 读回来做 sin/cos 旋转再写。融合后：QKV GEMM epilogue 直接在寄存器里做 RoPE 旋转，一次性写最终 q/k/v。 ### 为什么对 SALA 有价值 prefill M=8192 是 memory-bandwidth-bound 中等偏 compute，每省一次 [M, 16384] 的 HBM round-trip 就是实打实的 ms 级收益。decode M=1/8 权重带宽饱和，activation 来回不是瓶颈，收益小。 ### 为什么和 autotune 互补 - autotune 调的是 **mainloop 内部效率**（tile / stages / schedule），挤 MMA 利用率 - epilogue fusion 改的是 **GEMM 对外的 I/O 模式**，减总流量 - 两件事正交，可以并行推进，叠加收益
