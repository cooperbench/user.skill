**High-Value External Ideas**

| Idea | Source | Fit for our MiniCPM-SALA/SGLang stack |
|---|---|---|
| **Paged KV memory / block allocator discipline**: vLLM’s PagedAttention treats KV as fixed-size blocks to reduce fragmentation and enable larger continuous batches. | vLLM/PagedAttention reports 2-4x throughput gains in serving workloads: https://arxiv.org/abs/2309.06180 | Already conceptually present in SGLang. The experiment is not “port vLLM”, but tune page/block behavior, max running requests, static memory fraction, CUDA graph batch sizes, and KV pressure under long context + EAGLE3. FP4 weights help model memory, but KV remains the limiting HBM object. |
| **Radix/prefix KV reuse**: cache shared prefixes in a radix tree so repeated system prompts, few-shot contexts, RAG prefixes, or multi-turn sessions avoid recompute. | SGLang paper: https://arxiv.org/abs/2312.07104; SGLang HiCache docs: https://docs.sglang.io/docs/advanced_features/hicache_design | Strong fit if benchmark traffic has repeated prefixes or session continuity. Weak fit for public eval if every prompt is unique. Needs validation with `minicpm_flashinfer`, dense-as-sparse attention, and EAGLE3 rollback semantics. |
| **Hierarchical KV cache**: extend prefix KV reuse from GPU to CPU/remote storage. SGLang HiCache uses GPU as L1, host as L2, distributed storage as L3; LMCache exposes KV cache storage/transfer across vLLM/SGLang. | SGLang HiCache docs: https://docs.sglang.io/docs/advanced_features/hicache_design; LMCache paper: https://arxiv.org/abs/2510.09665 | Potentially high leverage for long shared prefixes, multi-round QA, or repeated document prompts. For a single isolated competition server with mostly unique prompts, likely low or negative due to CPU/IO overhead. Worth testing only with a synthetic repeated-prefix trace first. |
| **Decode-maximal / stall-free scheduling**: Sarathi-Serve keeps decodes moving while admitting prefill chunks, avoiding decode stalls caused by long prompts. | Sarathi-Serve: https://arxiv.org/abs/2403.02310 | We already use chunked prefill. The open question is scheduler interaction with EAGLE3: draft/verify batches may be more sensitive to chunk size and mixed prefill/decode admission than vanilla decode. Candidate knobs: chunk size, max prefill tokens per step, max running requests, speculative draft tokens. |
| **Prefill/decode disaggregation**: split compute-heavy prefill and memory-bandwidth-heavy decode into separate workers; transfer KV from prefill to decode. DistServe formalizes resource planning; Dynamo and SGLang now have practical implementations. | DistServe: https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf; Dynamo disagg docs: https://docs.nvidia.com/dynamo/design-docs/disaggregated-serving; SGLang PD docs: https://docs.sglang.io/docs/advanced_features/pd_disaggregation | Big upside only if the platform allows multiple GPUs/processes and KV transfer backend works. Less attractive for strict single-server/single-GPU submission. Dense-as-sparse/custom MiniCPM attention and EAGLE3 are compatibility risks. |
| **KV transfer optimization**: NIXL/Mooncake/RDMA, staging buffers, and layout-aware transfers reduce PD overhead. SGLang documents a heterogeneous-TP GPU staging buffer with 2-5x transfer-throughput improvement at high concurrency. | SGLang PD staging buffer docs: https://docs.sglang.io/docs/advanced_features/pd_disaggregation; Mooncake paper: https://arxiv.org/abs/2407.00079 | Relevant only if PD disaggregation is viable. If prefill/decode TP differs, staging buffer is directly worth trying. If same TP and same node, benefit may be smaller. |
| **KV-centric admission/routing**: Mooncake/Dynamo route requests based on KV locality and load, sometimes rejecting overload early to preserve SLOs. | Mooncake: https://arxiv.org/abs/2407.00079; Dynamo KV-aware routing: https://docs.nvidia.com/dynamo/v-0-9-0/user-guides/kv-cache-aware-routing | More production-serving than contest single endpoint. But a lightweight version could help: group/reorder local eval requests by prefix/session to increase radix hits, if request order is not semantically constrained. |
| **Preemptive/dynamic scheduling**: Orca introduced iteration-level scheduling; FastServe adds token-level preemption; Llumnix migrates live requests/KV across instances. | Orca summary: https://systems-reading.github.io/papers/2023-04-12/; FastServe: https://www.usenix.org/conference/nsdi26/presentation/wu-bingyang; Llumnix: https://arxiv.org/abs/2406.03243 | Migration is probably too invasive. But queue policy is useful: separate long-prefill jobs from decode-heavy jobs, prioritize near-finished decodes, and avoid long-context head-of-line blocking. Best as scheduler experiments, not kernel work. |
| **Speculative overlap scheduler**: SGLang has experimental Speculative Decoding V2 with overlap scheduler for EAGLE/STANDALONE. | SGLang speculative docs: https://docs.sglang.io/docs/advanced_features/speculative_decoding | Very relevant because current stack already uses EAGLE3 topk=1. This is the cleanest “beyond prefill” experiment: overlap draft/verify/runtime scheduling without changing quantization or model weights. Accuracy must be checked carefully. |
| **Selective KV offload/prefetch**: InfiniGen-style systems avoid fetching full KV from host by predicting important entries. | InfiniGen: https://arxiv.org/abs/2406.19707 | Interesting but likely too invasive for this stack. Dense-as-sparse/custom attention already changes attention semantics; selective KV fetch risks accuracy and kernel complexity. Treat as research, not first-line experiment. |
