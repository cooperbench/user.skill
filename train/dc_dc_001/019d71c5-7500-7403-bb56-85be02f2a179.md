结论如下。 1. 现在这条 Medusa 路径不是“典型 Medusa tree”，而是 `top1-only` 的扁平链式验证。 - 在 [`medusa_worker.py`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py) 里，`self.topk = 1`，`_medusa_draft()` 对每个 head 直接 `argmax`，没有保留多分支候选。 - `_forward_decode()` 把 verify 输入拼成每个请求一条固定序列 `[verified_id, draft_0, draft_1, ..., draft_{K-1}]`，然后一次 `TARGET_VERIFY` 跑完，再按“连续命中到第一个 reject”为止做 cascading acceptance。 - [`eagle_info.py`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/eagle_info.py) 里的 `MedusaVerifyInput` 也明确写了 “Unlike EAGLE's tree-based verification, Medusa uses flat (sequential) draft tokens”。 - 所以它本质上更接近“链式 multi-token guess + greedy verify”，不是原论文常见的树状候选展开。 2. verify 阶段和 hybrid linear attention 的交互是这个实现最特殊、也最脆弱的地方。 - 标准 attention 层在 [`minicpm_backend.py`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/minicpm_backend.py) 的 `TARGET_VERIFY` 下被当成 “extend/prefill 语义” 处理，走的是 FlashInfer prefill wrapper，不是平时 decode 的 sparse path。 - GLA / linear attention 层在 [`hybrid_linear_attn_backend.py`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py) 里有单独的 `TARGET_VERIFY` 逻辑：把 `bs x draft_token_num` 按 step recurrent 地跑，每一步把状态写到 `intermediate_ssm`，最后不直接提交主 state，而是等 verify 结果出来后，通过 `update_mamba_state_after_mtp_verify()` 把“最后一个被接受 step”的中间状态 scatter 回正式 temporal state。 - 这说明当前实现不是树 mask 驱动的并行树验证，而是“标准 attention 当作短 prefill，GLA 当作逐步 recurrent rollout，再回滚到 accepted step”。 3. 当前实现最关键的正确性约束有三个。 - `accepted_count == accepted_steps` 的语义必须严格正确。 - 在 [`medusa_worker.py`](/user_4813494d/openbmb/demo-sala/sglang/python/sglang/srt/speculative/medusa_worker.py) 里，`accepted_count=0` 仍表示保留 `verified_id`。 - GLA rollback 用的 `accepted_steps` 也是这个值，所以 `0` 表示回到“只吃了 verified_id”的状态，`1` 表示“verified_id + draft_0”。 - verify 路径的 cache / slot / sparse bookkeeping 必须与最终 accepted 长度完全一致。 - 代码里先为 `K+1` 个 token 全部分配 KV slot，再释放 reject 的部分，并手动补 sparse k1/k2 分配。 - 你们文档 [`spec-decode-accuracy-investigation.md`](/user_4813494d/openbmb/docs/spec-decode-accuracy-investigation.md) 和 [`medusa-spec-status-20260407.md`](/user_4813494d/openbmb/docs/medusa-spec-status-20260407.md) 都说明这里曾经/仍然是 bug 热区。 - 标准 attention 的 dense verify 语义和正常 decode 的 sparse 语义不能偏太多。 - 当前最像结构性风险的点不是 Medusa head 本身，而是 `TARGET_VERIFY` 走 dense prefill、正常 decode 走 sparse decode，这在混合 batch 和长短序列交错时可能造成 logits / hidden state 偏移。 一句话总结：你们现在的 Medusa 不是“真正的 tree Medusa”，而是 `top1` 链式 Medusa；它能工作，前提是 verify 后的状态回滚、KV/sparse bookkeeping、以及 dense verify vs sparse decode 的语义差异都被压到足够小。对 MiniCPM-SALA 这种 hybrid linear attention 模型来说，真正的风险中心已经从“draft 头是否够准”转移到了“verify 路径是否与正常 decode 严格等价”。
