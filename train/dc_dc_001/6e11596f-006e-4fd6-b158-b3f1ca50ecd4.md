## 从你给出的配置里能看出的「问题点」

### 1. 同一主机同一端口同时当 SOCKS5 和 HTTP

你写的是：

- `ALL_PROXY=socks5h://...:18080`
- `HTTP_PROXY=http://...:18080`

很多服务会在**不同端口**分别开 HTTP 代理（CONNECT）和 SOCKS5。**如果只监听其中一种协议**，就会出现：

- 另一种方式：**长时间卡住 / 超时 / 偶发失败**，看起来像「不稳定」。
- 应用程序行为不一致：有的走 `ALL_PROXY`（SOCKS），有的走 `HTTP_PROXY`。

**建议**：向服务商确认 **HTTP 与 SOCKS 各自对应的端口**；或分别用 `curl --socks5-hostname` / `curl -x http://...` 做单次验证，确认两种协议在 **18080 上是否都真的可用**。

### 2. `NO_PROXY` 过窄

只有 `localhost,127.0.0.1,::1` 时，访问内网域名、Docker 网段、`metadata` 等仍可能误走代理，表现为：**内网变慢、间歇失败**，或和直连混淆成「代理不稳」。可按环境补上内网段/域名（具体以你内网为准）。

### 3. 安全：凭据已泄露

用户名和密码出现在聊天里，**应尽快在服务商侧改密**；后续用环境文件或密钥管理，避免写进仓库或截图。

证据：

1. **本机→VPS 的纯 TCP 握手：20/20 成功，中位数 ~24ms**。链路本身可靠。
2. **经 SOCKS5 全程请求：TLS 握手需要 1.3~4.2s**。SOCKS5 的 connect 阶段（即 VPS 转发建连到目标）出现四档离散延迟（60/260/1080/1260ms），说明 **VPS→家宽→目标的链路存在严重的间歇性拥塞或丢包重传**。
3. **connect 时间的四档跳跃**（约 60ms → 260ms → 1080ms → 1260ms）非常典型的 **TCP SYN 重传**模式：首个 SYN 丢了就等 ~200ms 重传，再丢再翻倍。这说明 **VPS 到家宽之间存在显著丢包**。

---

### 四、带宽

| 测试 | 下载量 | 耗时 | 平均速率 |
|------|--------|------|----------|
| 5MB | 1.2MB (120s 超时未完成) | >120s | **~10 KB/s** |
| 20MB | 4MB (120s 超时未完成) | >120s | **~33 KB/s** |

**带宽极差**，约 **10~33 KB/s (80~264 Kbps)**，连基本的网页浏览都勉强。这是典型的家宽上行带宽限制（美国家宽上行通常只有 5~10 Mbps，但这个更像是上行被严重占用或线路质量差）。

---

### 五、HTTP 代理 vs SOCKS5

| | SOCKS5 | HTTP CONNECT |
|--|--------|-------------|
| 出口 IP 查询 | 首次成功 | **第二次就超时** |
| 常见外网 9 个站 | **全部失败** | 仅 pypi.org 成功 1 个 |
| AI 服务 7 个 | 仅 api.openai.com 成功 1 个 | **全部失败** |

**HTTP 代理模式比 SOCKS5 更不稳定**，很可能该代理软件对 HTTP CONNECT 方法的支持不完善，或家宽侧间歇断连时 HTTP 模式恢复更慢。

---

### 六、总结

| 问题 | 定位 |
|------|------|
| **不稳定的根因** | **VPS → 家宽上游**（丢包导致 TCP 重传，connect 出现 60/260/1080/1260ms 四档跳跃） |
| **带宽瓶颈** | 家宽上行，实测仅 **10~33 KB/s**，基本不可用于大文件传输 |
| **HTTP 代理** | 比 SOCKS5 更差，疑似代理软件 HTTP CONNECT 实现有 bug 或连接复用问题 |
| **本机→VPS** | 稳定，不是瓶颈 |

**建议**：这个家宽代理目前只适合偶尔的轻量 API 调用（如 SOCKS5 模式下访问 OpenAI API），不适合做日常代理使用。如果需要稳定的外网访问，建议换用 VPS 本身直出或商业代理服务。
