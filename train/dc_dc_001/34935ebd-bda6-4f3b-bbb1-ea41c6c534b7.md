## 是什么问题

这是 **“可打开的文件描述符用完了”**（Linux 里常叫 **EMFILE**，你看到的 **Error 24** 就是这个）。

含义包括：

1. **`Too many open files`**  
   Bash 在读 `/etc/bash.bashrc`、`~/.profile` 时要打开文件；若当前会话或整机的 **打开文件/句柄数已到上限**，连读配置都会失败。

2. **`libpthread.so.0: cannot open shared object file: Error 24`**  
   运行 `conda` / `python` 时，动态链接器要打开 `libpthread.so.0` 等库；同样是 **没有空闲句柄可用来打开这些 .so**，所以报 **Error 24**，不是库坏了，而是 **“连打开库文件都做不到了”**。

所以：**根因是 FD（或系统全局打开文件）耗尽**，不是单独的 pthread 或 conda 配置问题。

---

## 常见原因

| 情况 | 说明 |
|------|------|
| 某进程泄漏 FD | 长期跑的服务/训练脚本不关 socket、日志、临时文件 |
| 并发/子进程太多 | 每个进程占一批 FD，总和顶满 |
| `ulimit -n` 太小 | 软限制过低（尤其非 root、或某些容器/作业系统默认很抠） |
| 系统全局 `file-max` / `fs.file-nr` 顶满 | 整机打开文件总数到上限（相对少见，多见于大量短连接或泄漏） |

---

## 你可以怎么处理（在还能开一个终端时）

1. **看当前 shell 限制**：`ulimit -n`  
2. **临时加大（当前会话）**：`ulimit -n 65535`（若策略允许）  
3. **看谁占得多**（需 root 或看自己的进程）：  
   `lsof -u $(whoami) | wc -l`  
   或对可疑 PID：`ls /proc/<pid>/fd | wc -l`  
4. **能停就停**：关掉泄漏的服务、异常的训练/评测任务。  
5. **若已经“什么都开不了”**：往往只能 **重启有问题的会话/容器/机器**，或从 **另一路（如宿主机）** 杀进程释放 FD。

---

**总结**：这是 **打开文件/句柄数达到上限** 导致的连锁反应：Bash 读不了配置、`conda`/Python 加载不了 `libpthread` 等共享库。需要从 **提高 `ulimit`、结束泄漏进程、或重启** 几方面处理。若你愿意提供更上下文（是否在 Docker、是否在跑 SGLang/大量并发评测），可以再针对性说该查哪类进程。

## 已做的修改

### 1. `/etc/security/limits.d/90-nofile.conf`
为所有用户和 **root** 单独设置了更高的句柄上限（`*` 对 root 不生效，所以加了 `root` 行）：

- soft/hard **nofile = 1048576**

### 2. `/etc/profile.d/nofile.sh`
在登录 shell 里 **尽量** 把当前进程的 `ulimit -n` 调到更高（前提是硬限制已经由 PAM 放开）。

### 3. PAM：`common-session` 与 `common-session-noninteractive`
在两份配置里都增加了：

`session required pam_limits.so`

这样通过 **@include common-session** 的会话（不少图形/远程场景）也会读到 `limits.d`，而不只靠传统的 `login` 那条链。

---

## 你需要做的（很重要）

1. **重新登录**（退出当前 SSH / 终端再连），或 **重启**。PAM 和 profile 只对 **新会话** 生效。
2. 在新会话里检查：
   - `ulimit -n` 应接近 **1048576**（或至少明显大于 1024/4096）。

---

## 若当前终端已经「什么都报 Too many open files」

在 **新开一个** 能用的 root 终端里，对 **卡死的 shell 进程** 调大限制（把 `PID` 换成 `echo $$` 在坏终端里若还能执行一次看到的值；否则用 `ps` 找你的 bash）：

```bash
prlimit --pid=PID --nofile=1048576:1048576
```

若整台机子已经被某个进程占满句柄，需要先找到并结束该进程（例如 `lsof -p PID | wc -l` 很大的服务），否则单提 `ulimit` 也救不了动态链接失败。

---

## Docker / Podman

若你是从容器里进 shell，宿主或 `docker run` 里可能还有 **nofile 上限**，需要在创建容器时加上例如：

`--ulimit nofile=1048576:1048576`

否则容器内 PAM 配得再高也会被外层盖住。

---

**原因小结**：Error 24 / “Too many open files” 是 **进程/系统可打开文件数到上限**。现已从系统上把 **默认上限抬高**，并保证更多登录方式会走 **`pam_limits`**。你这边 **`/base/mambaforge/bin/python`** 若仍是旧路径，修好会话限制后再看 conda 是否正常；若路径写错，需改回真实的 mambaforge 安装目录。
