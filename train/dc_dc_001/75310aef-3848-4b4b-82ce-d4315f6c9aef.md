`/loop` 是一个让你把某个提示或 slash command 按固定节奏反复执行的工具。

## 两种用法

**1. 固定间隔模式**
```
/loop 5m /foo
/loop 30s 检查构建状态
```
第一个参数是间隔（`30s` / `5m` / `1h` 等），第二个是要重复执行的内容。harness 会到点就把那段提示重新喂给我一次。

**2. 动态自定节奏模式（省略间隔）**
```
/loop 盯着这个后台任务，完成就告诉我
```
不写间隔，我自己用 `ScheduleWakeup` 决定下一次什么时候醒。每轮我评估"还要不要继续 / 多久后再看"，可以根据情况收紧或放宽。

## 典型场景

- 轮询长跑任务：`/loop 2m 看看 bench 跑完没`
- 周期性维护：`/loop 10m /babysit-prs`
- 等一次性事件：动态模式更合适，事件来了就退出

## 节奏选择（动态模式）

Anthropic prompt cache TTL 是 5 分钟，所以选 `delaySeconds` 有自然分界：
- **< 270s**：缓存还热，适合频繁查状态
- **>= 1200s**：反正要付一次 cache miss，干脆睡久点
- **避开 300s 这个甜区陷阱**：付了 cache miss 又没赚到长间隔

空闲巡检默认 1200–1800s。

## 怎么停

- 固定间隔：`/loop` 不带参数，或者直接打断
- 动态模式：我不再调 `ScheduleWakeup` 就自然结束

## 区分

不要和 `/schedule` 混：`/schedule` 是 cron 风格的远程定时 agent（比如每天 9 点跑一次），跑在云端；`/loop` 是当前会话里反复唤醒同一个我。

| `/loop`（动态模式） | 反复唤醒同一个会话，自定节奏 |

## 一个最小骨架

```
.claude/commands/goal.md         # 定义目标 + 评估方式 + 改一步策略
runs/best.json                    # 当前最佳得分 + 配置
runs/history.jsonl                # 所有尝试记录
```

调用方式：
```
/loop /goal 把 mini_bench S8 提到 9.0+
```

每一轮 `/goal` 做的事：读 `best.json` → 提一个改动假设 → 改代码 → 跑 bench → 写回 history → 如果更好就更新 best → 否则回滚。`/loop` 负责持续唤醒。

## 为什么没现成的

Karpathy 那种 auto-research 的难点不在调度，而在 **可信的自动评估** 和 **搜索空间定义**。Claude Code 留这一层给用户自己定义是合理的——通用 `/goal` 没法知道你这个项目"更好"是什么意思（是 bench 数还是 mcq 准确率？是否允许显存涨？）。

## 整体形态

不是单个 slash command，是 **outer 调度 + inner trial + 状态持久化** 三层。

```
.claude/commands/
  prefill_loop.md          # outer：读 state → 推进/起新 trial → 写 state
  prefill_propose.md       # 只生成假设，不执行（人工挑）
  prefill_trial.md         # inner：跑完 6 gate 漏斗
  prefill_status.md        # 看 state + 最近 trial

runs/prefill/
  state.json               # 当前 best wall / 假设队列 / 预算
  hypotheses.jsonl         # append-only，所有提过的假设
  trials/<trial_id>/
    hypothesis.md          # 改什么 / 为什么 / 预期 ms 下降 / 风险
    profile_baseline.json
    profile_after.json
    offline.txt            # bitwise / topk diff
    online.txt             # 真实请求 debug check
    smoke.txt              # 中文输出 200 token
    bench15.jsonl          # 3 轮 wall，每轮 /flush_cache
    patch.diff             # 实际代码改动
    decision.md            # LANDED / REJECTED + 写回 prefill.md 的 patch
```

外层调用：
```
/loop /prefill_loop
```
动态模式让我自己控节奏；trial 跑 server 要 30+ 分钟，固定间隔反而碍事。

## 6-gate 漏斗（prefill_trial 内部）

每个 gate 失败 → 立刻写 `decision.md: REJECTED` + 把"为什么"以一段话形式 patch 进 `docs/prefill.md §3.x`，**这一步是关键**：把否决记入真值源，下一轮 propose 看到的就是最新的版图，避免重复提议。

| Gate | 内容 | 失败动作 |
|---|---|---|
| 0 profile-fit | 假设要打的 ms 项是否真在 profile 顶端？预期下降是否 ≥ 项目 ms 的 1.5× 阈值？ | 写 §3 "假设不打热点" |
| 1 offline-equiv | 离线 micro：bitwise diff / topk equal（启用 shape + 边界 shape） | 写 §3 "shape X 离线不一致" |
| 2 single-layer | 单层 offline bench 真的更快？ | 写 §3 "离线快但..." |
| 3 online-equiv | 起 server，发 debug 请求，命中路径打印 `bad=0` | 写 §3 "线上路径不一致" |
| 4 smoke | `mars=0, max_tokens=200`，中文 | 写 §3 "smoke 失败" |
| 5 bench15 | line 39 × 3 轮，每轮 `/flush_cache`；新 wall < best - 噪声带 | 写 §3 "离线 +X% 但 wall 打平" |
| 6 profile 复核 | 旧热点确实下降，没转新热点 | 写 §3 "热点转移到 Y" |

通过 6 gate → 写 §2.x（默认开启 + env 回退开关），更新 `state.best`，commit。

## prefill_propose.md 的核心提示

```
读 docs/prefill.md §1（当前热点）+ §2（已落地）+ §3（已否决）
读 runs/prefill/state.json 的 baseline.profile_top 和 rejected_axes

输出 3-5 个候选假设，每个带：
- title
- 打哪个 ms 项 + 该项在 profile 中的位置
- 改动机制（算法/layout/kernel/语义级，不是参数旋钮）
- 预期 ms 下降（绝对值，不是百分比）
- 与 §3 哪些条目接近，本假设和它的本质区别
- 风险等级（low/med/high）+ 主要失败模式

硬规则：
- 不接受 topk 缩限 / 候选裁剪 / 任何近似 attention

```

候选打分排队进 `state.queue`，由 `/prefill_loop` 自动取队首。

## prefill_loop.md 的核心循环

```
1. 读 state.json
2. if active_trial:
     调 /prefill_trial 推进它（gate-by-gate；一轮 wakeup 不一定跑完）
3. elif queue 为空:
     调 /prefill_propose 填队列
     如果 propose 输出全是 §3 重复 → consecutive_rejects++ → 可能 kill
4. else:
     从 queue 取第一个 → 起新 trial
5. 写 state.json
6. ScheduleWakeup(delay) 决定下次唤醒
   - active server 跑 bench：270s（cache 内）
   - 等待 trial 间空档：1800s
```

我每轮都 re-read `docs/prefill.md` —— 这是关键。你 22 条否决清单已经表达过事实在哪里。loop 每轮接进来的是**最新的** §1/§2/§3，不靠记忆累积偏见。

## 几个非平凡设计点

**为什么 propose / trial 拆开**

让你能 `/prefill_propose` 后人工挑或改，再 `/prefill_loop` 跑。auto-research 最大风险是 LLM 提一堆烂主意自己点头通过；propose 单独可审计就堵住这条路。

**docs/prefill.md 当真值源，不是 state.json**

state 是调度状态；prefill.md 是事实状态。每次 LANDED/REJECTED 把事实先写进 prefill.md，再更新 state。哪天你删 state.json 重启，loop 看 prefill.md 仍然知道 22 条什么不该做。

**单 GPU 串行**

每个 gate 切换都 `bash bench/kill_sglang.sh`。trial 之间也 kill。loop 自身不并发起子 trial。

**Monitor 规则按 CLAUDE.md 来**

每次起 server 等 ready 用 `grep -m1 "Uvicorn running on\|Traceback\|ERROR\|Killed\|OOM"`；trial 之间 `TaskStop` 旧 monitor。

**bench 噪声**

15chunk wall 噪声带按 docs 里的实测大约 ±0.05s。Gate 5 通过条件设 `new_wall < best - 0.10s`（双倍噪声），避免 §3.5 那种"打平算赢"的伪收益。

**预算和退出**

`consecutive_rejects_kill=4`：连 4 个 trial 全 reject，loop 自停。这是承认 stage1 trait / stage2 backend 都已枯竭的现实，自动 reject 是信号说当前真值源下没空间，得人工介入或换文档（比如换到 `docs/runtime.md` 的 decode 战线）。
