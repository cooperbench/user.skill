> AGENT

You can, with two HA template functions: - `_slot_number` ← `{{ state_attr(pin_used_entity_id, 'code_slot') }}` — LCM stores the slot number as a `code_slot` attribute on the event entity (the notifier already reads this from `trigger.to_state.attributes.code_slot`). - `_config_entry` ← `{{ config_entry_id(pin_used_entity_id) }}` — every HA entity carries the ID of its source config entry, and LCM-created event entities are registered to the LCM config entry by construction. The variable block would look like: ```yaml variables: pin_used_entity_id: !input pin_used_entity _slot_number: > {{ state_attr(pin_used_entity_id, 'code_slot') }} _config_entry: > {{ config_entry_id(pin_used_entity_id) }} _config_entry_title: > {{ config_entry_attr(_config_entry, 'title') }} ``` That deletes two inputs from the form. Trade-offs to weigh: 1. **Breaking change for existing automations** — the input keys disappear, so users who imported the old blueprint need to re-save (or re-import). With only #1153 just-merged this is probably very few people. 2. **Tighter coupling to LCM's attribute schema** — if `code_slot` ever gets renamed inside LCM, the blueprint silently breaks at trigger time instead of at setup time. (The notifier already has this coupling, so it's not adding a new fragility class — just expanding it.) 3. **Slightly less obvious form** — the explicit inputs document the blueprint's intent ("this is for slot N of this config entry"). Derived inputs make the form simpler but more "magical." 4. **Validation moves to runtime** — `slot_number`'s `number` selector currently does range validation at setup; with derivation, a wrong/unloaded entity surfaces as a None at trigger time. `★ Insight ─────────────────────────────────────` - The same simplification works for the `enabled_switch` input too: it's `switch.{lock}_code_slot_{N}_enabled`, and LCM exposes it on the same config entry / device.
