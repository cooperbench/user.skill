You're right to flag this. Let me answer directly:

**Yes — `not_from: unknown` blocks the first-ever trigger for a fresh entity.** Event entities in HA start at `unknown` after registration. The entity has no state until `_trigger_event` is called, so:

- **First-ever PIN use (no priors):** `unknown` → `<timestamp>` → **blocked** by `not_from: unknown`
- **After HA restart with recorder restore:** `unknown` → `<restored timestamp>` → blocked (this is the bug being fixed — `EventEntity.async_added_to_hass` at event.py:148 restores the prior timestamp from storage)
- **Normal PIN use after first one:** `<old_ts>` → `<new_ts>` → fires normally

So the trade-off the committed change makes: **users must use their lock at least once before the notifier becomes functional.** In practice that's nearly always true (the automation is set up after the lock is already in use). Worth documenting in the blueprint description, but accepting the trade-off is reasonable.

> AGENT

Good question — I need to pause the test work and address this design issue before continuing, because there's a real tension between "block restart fires" and "don't block first-ever fire."

## The state trigger can't distinguish these two cases

From the trigger's point of view, both look identical:

| Scenario | `from_state` | `to_state` |
|---|---|---|
| HA restart, recorder restores prior timestamp | `unknown` | `<timestamp>` |
| First-ever PIN use on a fresh slot | `unknown` | `<timestamp>` |

The entity is added to the state machine as `unknown` *before* `async_added_to_hass` runs (see event.py:144) — and `EventEntity.async_added_to_hass` then writes the restored state, producing a visible `unknown → <restored>` transition that the state trigger sees.

## Options (with honest trade-offs)

**1. Keep the current `not_from` approach (what's committed)**
- Standard HA pattern for this exact problem
- Blocks restart fires ✓
- Also blocks the first-ever fire on a fresh slot ✗
- Fix: document in the blueprint description that users should use their lock at least once before setting up the notifier

**2. Suppress the `unknown → restored` transition at the integration layer**
Modify `LockCodeManagerCodeSlotEventEntity.async_added_to_hass` so the restored state is written *before* the entity becomes visible to the state machine — no visible transition, so no spurious trigger. This is the cleanest fix because it removes the underlying cause rather than filtering its symptom. Requires changes to `custom_components/lock_code_manager/event.py`.

**3. `homeassistant.started` + `input_boolean` gate**
Block all automation triggers for N seconds after startup using a shared input_boolean. Doesn't fit cleanly in a blueprint and adds external entities the user has to wire up.

**4. Hybrid: keep `not_from` AND fix the integration**
The integration fix (#2) prevents the spurious trigger on restart, AND the `not_from` filter is a belt-and-suspenders backstop. First-ever fires still go `unknown → timestamp` and would still be blocked unless we *also* set an initial sentinel state.

`★ Insight ─────────────────────────────────────`
HA's `RestoreEntity` machinery always adds the entity to the state machine before restoring — so any state-trigger automation on a restoring entity will see the `unknown → restored` transition unless either (a) the trigger filters it out, or (b) the entity overrides the standard registration sequence. The committed `not_from` change picks (a); option #2 would pick (b).
`─────────────────────────────────────────────────`

My recommendation: **stick with the committed `not_from` for now** (it's the standard pattern and works for restart, which is the common case), add the tests we discussed, and **document the first-fire limitation in the blueprint description**. If the first-fire side effect bothers real users, follow up with the integration-level fix (#2).

`★ Insight ─────────────────────────────────────`
By the time a condition runs, "is the integration loaded?" is always true (the entity has a state, so something loaded it). What we actually want to distinguish is "was this a real PIN event vs. an entity-appearance artifact?" — and the signal we need is in `trigger.from_state` itself. Real PIN transitions always have a meaningful from_state; restoration/appearance transitions have `from_state=None`.
`─────────────────────────────────────────────────`

## What's available in the trigger context

| Signal | Real PIN use | Entity first-appearance (restart/reload) | Unavailable recovery |
|---|---|---|---|
| `trigger.from_state` | `<State object>` | **`None`** | `<State object>` |
| `trigger.from_state.state` | `'<old timestamp>'` or `'unknown'` (first ever) | n/a (from_state is None) | `'unavailable'` |
| `trigger.to_state` | `<State object>` | `<State object>` | `<State object>` |

So the discriminating signal is **`trigger.from_state is not none`**. That alone catches the case our `not_from: [unknown, unavailable]` misses (where Python `None ≠` the string `'unknown'`).

## Proposed condition

```yaml
conditions:
  - condition: template
    value_template: >-
      {{ trigger.from_state is not none
         and trigger.from_state.state not in ['unknown', 'unavailable'] }}
```

This checks two things:
1. **`from_state is not none`** — entity had a real prior state (not first-appearance). Blocks the LCM-reload case we just proved is broken.
2. **`from_state.state not in [...]`** — that prior state was meaningful. Belt-and-suspenders with `not_from`.

## What about the first-fire trade-off?

The condition above keeps the first-fire trade-off (because the first PIN goes `'unknown' → '<timestamp>'`). To **also fix that**, drop `'unknown'` from the condition:

```yaml
conditions:
  - condition: template
    value_template: >-
      {{ trigger.from_state is not none
         and trigger.from_state.state != 'unavailable' }}
```

This allows `'unknown' → '<timestamp>'` (real first PIN) while still blocking `None → *` (restoration) and `'unavailable' → *` (recovery). Combined with the existing `not_to: [unknown, unavailable]`, you'd actually have full coverage **without** the first-fire side effect.

Hmm — even WITH the condition, the entity_removal test fails because **variables in HA automations are computed BEFORE conditions are evaluated**. So `trigger.to_state.attributes.code_slot_name` crashes before the condition can block it.

`★ Insight ─────────────────────────────────────`
This is a real design gap in the blueprint, not just a test issue. When the entity is removed in production, the trigger fires, variables crash, and the user sees confusing error logs. The condition I added blocks the *action* but can't prevent the *variable rendering errors* that fire first. The fix: make the variables defensive (so they don't crash on edge-case trigger states), and keep the condition as a no-action guarantee.

## "Wouldn't from_state be None when entity is first created and goes from unknown to pin fired?"

No — those are **two separate state-changed events**, and the trigger only sees the second one as a `from='unknown'` transition:

| Step | When | `state_changed` event | `from_state` (in trigger) |
|---|---|---|---|
| 1 | Entity first appears | `(None, <State 'unknown'>)` | `None` ← **blocked** by condition |
| 2 | PIN fires | `(<State 'unknown'>, <State '<ts>'>)` | `<State 'unknown'>` ← **allowed** (not None, state != 'unavailable') |

Python `None` (the missing State object) only shows up for transition #1 — the entity first-appearance. By the time the PIN fires in #2, the entity already has state `'unknown'` (a real State object), so `from_state is not none` is `True` and the condition lets it through.

This is exactly what `test_notifier_fires_on_first_pin_use` verifies: entity starts at `'unknown'`, PIN fires, `captured == 1`. And TDD-verified: that test fails if I remove `not_to: unknown` from the trigger (which would let the first-appearance transition through, but the condition still catches it).
