**파일**: `/Users/johyunduk/Projects/ddong-avoid-game/src/utils/battleChannel.ts`

#### 채널 생성 및 토픽 구조
```
- battle-room:{roomCode}    — BattleMatchScene 용 (매칭 및 준비)
- battle-game:{roomCode}    — BattleGameScene 용 (게임 진행 중)

**구독 프로세스** (반드시 순서 지켜야 함):

2. `.onEvent()`, `.onPresenceJoin()`, `.onPresenceLeave()` — 리스너 등록
3. `.subscribe()` — 실제 WebSocket 연결 시작 + Presence track

**중요**: Supabase Realtime의 필수 패턴입니다. 리스너를 subscribe 전에 등록하지 않으면 이벤트를 놓칠 수 있습니다.

#### 구독 타임아웃 및 에러 처리
```typescript
// subscribe()에서 10초 타임아웃
const timeout = setTimeout(() => {
  console.warn('[BattleChannel] subscribe timeout — forcing channelReady');
  resolve(); // 강제 진행
}, 10000);

// 상태별 처리
this.channel!.subscribe(async (status) => {
  if (status === 'SUBSCRIBED') {
    clearTimeout(timeout);
    await this.channel!.track({ userId, joinedAt: Date.now() });

});

**주목점**:
- 10초 타임아웃으로 Supabase Realtime 불안정성 대응

- 채널 준비 상태를 명시적으로 체크 (`this.channelReady` flag)

### 2. 게임 시작 후 상태 동기화 방식

#### A. Presence 기반 동기화 (참가 감지)

**BattleMatchScene에서**:
- `Presence join` → 상대방 입장 감지 → 내 캐릭터 정보 재전송

```

#### B. Broadcast 이벤트 (상태 전송)

**8가지 메시지 타입**:

| 이벤트 | Payload | 발송 시기 | 수신자 처리 |
|--------|---------|---------|-----------|
| `CHAR_ANNOUNCE` | `{userId, characterId}` | 채널 연결 직후 + Presence join 시 | 상대 캐릭터 표시 |
| `READY` | `{userId, characterId}` | 준비완료 버튼 클릭 시 | `opponentReady=true` → 양쪽 준비 확인 |
| `GAME_START` | `{timestamp}` | 호스트가 양쪽 준비 확인 후 | 카운트다운 시작 |
| `SEND_POOP` | `{count}` | 특수 똥 수집 시 | 상대 화면에 빨간 똥 생성 + 경고 |
| `SCORE_UPDATE` | `{score}` | 게임 진행 중 1초마다 | 상대 생존 시간 표시 갱신 |
| `GAME_OVER` | `{userId, finalScore}` | 플레이어 사망 시 | 상대 즉시 승리 + 결과 씬 전환 |
| `REMATCH_REQUEST` | `{userId}` | 결과 씬에서 재도전 버튼 클릭 | 상대 재도전 의사 표시 |
| `RESULT_LEAVE` | `{userId}` | 결과 씬에서 메뉴로 이탈 시 | 상대 이탈 즉시 감지 |

    resolve();
  } else if (status === 'CLOSED') {

    console.warn('[BattleChannel] subscribe failed with status: CLOSED');
    clearTimeout(timeout);
    resolve();
  }
});
```

async destroy(): Promise<void> {

    await this.channel.untrack();

### 5. 게임 흐름별 채널 관리

#### 씬 흐름과 채널 토픽

```
BattleMatchScene (battle-room:{code})
  ↓ (양쪽 준비 → GAME_START 이벤트)
BattleGameScene (battle-game:{code}) — 새 채널로 변경
  ↓ (게임 오버)
BattleResultScene (battle-result:{code}) — 다시 새 채널로 변경
```

**각 씬에서의 채널 생명주기**:

1. **BattleMatchScene**:
   - `showReadyButton()` → `initChannel(code, asHost)`
   - 리스너: CHAR_ANNOUNCE, READY, GAME_START + Presence
   - 게임 시작 → 채널 동기식 정리 → BattleGameScene으로 전환

2. **BattleGameScene**:
   - `create()` → `initBattleChannel()` — **다시 새 채널 생성**
   - 리스너: SEND_POOP, SCORE_UPDATE, GAME_OVER + Presence
   - 연결 준비 전 수집된 특수 똥은 pending queue에 저장 → 연결 후 플러시
   - 게임 오버 → `shutdown()` 호출 시 동기식 정리

3. **BattleResultScene**:
   - `create()` → `initRematchChannel()` (친선전만)
   - 리스너: REMATCH_REQUEST, RESULT_LEAVE + Presence
   - 메뉴로 이탈 시 `sendResultLeave()` 후 정리

### 11. 핵심 설계 원칙

1. **Supabase 싱글턴 채널**: 씬 전환 시 `removeChannel()` 호출 필수
2. **리스너 먼저 등록**: subscribe 전에 onEvent/onPresenceJoin/onPresenceLeave 등록
3. **타임아웃 대비**: 10초 구독 타임아웃으로 무한 대기 방지
4. **강제 진행**: 연결 실패해도 게임 플레이 가능하도록 설계
5. **Presence + Broadcast**: 참가/이탈은 Presence, 상태 전송은 Broadcast
6. **5초 버퍼**: 일시적 네트워크 지연 용인 → 재접속 자동 복구
7. **Pending queue**: 채널 준비 전 데이터는 메모리에 축적 후 플러시
8. **동기/비동기 정리**: shutdown은 동기(destroyImmediate), navigate는 비동기(destroy)

`★ Insight ─────────────────────────────────────`
문제가 두 레이어에 걸쳐 있습니다. 서버 검증은 `session.start_time` 기반이고, 이 시간은 Edge Function이 **실행된 시점**에 DB에 기록됩니다. Supabase Edge Function cold start가 발생하면 실제 게임 시작 시각보다 수 초 늦게 기록되어 `elapsedSec`가 줄어듭니다. 동시에 `collectBonus`(ability + synergy)도 서버 `bonusScore`에 미반영되어 `timeBasedScore`가 부풀어 오릅니다.
`─────────────────────────────────────────────────`

## 원인 두 가지

### 1. Edge Function cold start → `elapsedSec` 과소평가

```
게임 시작 (T=0) → sessionPromise = startGameSession() 호출 → [Cold Start 10초] 
→ DB에 start_time = T+10 기록 → 플레이어 T+15에 사망

서버: elapsedSec = 15 - 10 = 5초
minRequiredSec = 150점 * 0.05 = 7.5초
5 < 7.5 → 오류!
```

Supabase 무료 티어에서 cold start가 5~15초 걸릴 수 있어 50% 버퍼가 통째로 소진됩니다. 센티넬로 짧게 게임했을 때(실드 다 닳고 빠르게 사망) 발생하기 쉽습니다.

- `coldStartDelay = 5000ms`

**Correct formula**:

adjustedElapsedSec = clientElapsedMs / 1000;

`★ Insight ─────────────────────────────────────`
`async/await`는 중단점(suspension point)을 만듭니다. `await subscribe()` 대기 중에 다른 코드(뒤로 가기, `shutdown()`)가 실행되어 `this.battleChannel = null`로 설정해버릴 수 있습니다. `await`가 끝나고 돌아왔을 때 `this.battleChannel`은 이미 null이지만 코드는 이를 모르고 계속 실행됩니다.
`─────────────────────────────────────────────────`

// initChannel (line 499)

}

**게스트가 코드 입력 후 참가 버튼을 눌렀다가 뒤로 가기를 누르면:**

1. `doJoin` → `await initChannel()` → `await subscribe()` 대기 중
2. 뒤로 가기 → `goBack()` → `await destroy()` → `this.battleChannel = null`
3. `subscribe()` 내부가 CLOSED 이벤트로 resolve
4. `initChannel`로 돌아옴 → `this.battleChannel.sendCharAnnounce()` → **null 크래시**
