`★ Insight ─────────────────────────────────────`
이 함수에서 로그인 유저 기준 최악의 경우 **DB 쿼리 5~6번**이 순차적으로 발생합니다. 특히 `COUNT(*)` 쿼리가 `score > X` 조건으로 실행되는데, `leaderboard(difficulty, year_month, score)` 복합 인덱스가 없으면 풀 스캔이 됩니다.
`─────────────────────────────────────────────────`

**병목 지점 분석:**

```
1. 메인 리더보드 쿼리 (profiles JOIN 포함)
2. ──── 병렬 ────
   userEntry 조회  |  claimed 조회  |  userPrevEntry 조회
3. ← 위 결과 받은 후 순차 실행 →
   COUNT(*) WHERE score > userEntry.score  ← 여기가 문제
4. ← 또 순차 →
   COUNT(*) prevHigherCount  |  COUNT(*) prevTotal  ← 직전 시즌도 2번 더
```

COUNT 쿼리를 인덱스 없이 실행하면 매번 풀 스캔입니다.

**가장 빠른 개선책: 복합 인덱스 추가 + COUNT → window function RPC 전환**

> AGENT

핵심은 **왕복 횟수(round-trip) 감소**입니다.

---

**기존 흐름 (로그인 유저 기준)**

```
클라이언트 → DB: 메인 리더보드 쿼리 (profiles JOIN)
             ↓ 결과 받음
클라이언트 → DB: userEntry 조회     ┐
클라이언트 → DB: claimed 조회       ├ 병렬
클라이언트 → DB: userPrevEntry 조회 ┘
             ↓ userEntry.score 받음
클라이언트 → DB: COUNT(*) WHERE score > X   ← 직렬! 앞 결과 없으면 못 보냄
             ↓
클라이언트 → DB: COUNT(*) prevHigherCount   ┐ 병렬이지만
클라이언트 → DB: COUNT(*) prevTotal         ┘ 여기까지 와야 응답 가능

총 6번, 중간에 직렬 대기 2회
```

**개선 후 흐름**

```
클라이언트 → DB: get_leaderboard_with_rank RPC     ┐ 병렬
클라이언트 → DB: claimed 조회                       │
클라이언트 → DB: get_user_season_rank RPC           ┘
             ↓ 전부 동시에 반환

총 3번, 직렬 대기 0회
```

---

**왜 RPC 안에서 빠른가**

`COUNT(*) WHERE score > X` 는 DB에서 Edge Function까지 **점수를 한 번 주고받은 다음** 다시 쿼리를 보냅니다. 네트워크 왕복이 추가됩니다.

`RANK() OVER (ORDER BY score DESC)` 는 DB가 **한 번의 정렬로** 모든 행의 순위를 동시에 계산합니다. 네트워크를 타지 않고 DB 내부에서 끝납니다.

```
기존: Edge Function이 score 받아옴 → DB에 "이 score보다 위가 몇 명?" 재질문
개선: DB가 정렬하면서 바로 rank 번호 붙임 → Edge Function은 결과만 받음
```

`★ Insight ─────────────────────────────────────`
Window Function은 이미 정렬된 결과셋을 한 번 더 스캔하는 것이라 추가 인덱스 조회 없이 순위가 나옵니다. 반면 `COUNT(*) WHERE score > X`는 인덱스를 써도 해당 범위를 별도로 스캔합니다 — 쿼리 자체의 효율 차이도 있습니다.
`─────────────────────────────────────────────────`

round-trip 감소가 도움은 되지만 **진짜 병목이 다른 곳**일 수 있습니다. 먼저 어디서 시간이 걸리는지 확인해야 합니다.

Supabase Dashboard → **Edge Functions → leaderboard-top → Logs**에서 실행 시간을 봐주세요. 아니면 직접 시간 찍어볼 수 있습니다.

가장 의심되는 원인 3가지:

---

**1. Cold Start (가장 유력)**

Edge Function이 일정 시간 호출 없으면 잠들고, 다음 호출 때 `esm.sh`에서 Supabase 클라이언트를 새로 다운받습니다. 이게 500ms~2초를 잡아먹을 수 있습니다.

확인 방법: 연속으로 두 번 호출했을 때 두 번째가 빠른지 확인. 빠르면 cold start가 원인.

---

**2. window function이 오히려 느릴 수 있음**

솔직히 말하면, 방금 만든 RPC가 메인 리더보드 조회에서는 **오히려 느릴 수도** 있습니다.

```sql
-- 기존: 인덱스 타고 상위 100개만 꺼냄 (빠름)
ORDER BY score DESC LIMIT 100

-- RPC: 전체 행 스캔 후 rank 계산, 그다음 필터 (느릴 수 있음)
RANK() OVER (ORDER BY score DESC)
```

유저 수가 많아질수록 RPC가 더 불리합니다.

---

**3. profiles JOIN**

`leaderboard JOIN profiles` — profiles 테이블 조회가 느리면 함께 느려집니다.

---
