> DEVELOPER

is there a better technology for the viewcube than the one we picked?

> AGENT

Yes. For this specific control, the better technology is probably **one small dedicated Three.js scene with raycasting**, not SVG/canvas projection math.

Why:
- A ViewCube is fundamentally a 3D object with 3D picking.
- Labels can be real face textures, so they are genuinely “burned into” the cube.
- Raycasting gives accurate face/edge/corner hit testing without hand-maintaining projected polygons.
- The cube can share the main camera quaternion, so sync is cleaner.
- Exact views can still override to face-on camera orientations.

The mistake in the previous Three.js attempt was likely not “Three.js is bad”; it was using it without a strict interaction/render contract. The right Three.js version would be:
- Orthographic mini-scene.
- One cube mesh with six canvas-texture materials.
- Separate invisible hit meshes for faces, edges, corners.
- Raycaster priority: corner > edge > face, except face label center can remain face.
- Fixed CSS size, DPR-aware renderer, no blur.
- Main camera orientation drives cube quaternion.
- ViewCube drag updates the same camera rig, then cube is just a reflection of camera state.

Alternative technologies:
- **SVG + canvas**: what we have now. Crisp and cheap, but labels/perspective/picking are custom math forever.
- **CSS 3D**: not good enough here. Text rendering and hit zones get weird.
- **Pure Canvas 2D**: possible, but picking/3D projection becomes even more hand-rolled.
- **Babylon.js**: also viable, but overkill if the app already uses Three.js.

My recommendation: replace the current ViewCube renderer with a disciplined Three.js mini-scene, keeping existing alignment/pick APIs and tests. That gives the best path to Revit-like behavior.

> DEVELOPER

but will threejs also allow the interactivity?

> AGENT

Yes. Three.js is actually better for this interactivity if implemented correctly.

It supports:
- **Face clicks** via `Raycaster` intersections on face hit meshes.
- **Edge/corner blue boxes** via separate invisible/visible hit meshes.
- **Hover states** by raycasting on pointer move and highlighting the active target.
- **Drag/orbit** by listening to pointer drag on the mini renderer and forwarding deltas to the main camera rig.
- **Exact snap views** by mapping clicked face/edge/corner meshes to the existing `alignmentForPick(...)`.
- **Burned-in labels** by drawing text into canvas textures used as cube face materials.
- **No selectable text**, because labels are texture pixels.
- **Stable label placement**, because labels live in face UV space, not DOM/SVG overlay space.

The critical design is to separate **visual cube meshes** from **interaction hit meshes**:

- Visual cube: six textured face materials, crisp labels.
- Face hit targets: six transparent planes.
- Edge hit targets: thin transparent rectangular prisms/cylinders.
- Corner hit targets: small transparent boxes/spheres.
- Raycast priority: corner first, then edge, then face.
- Hover renders blue corner/edge overlays from the selected hit target.
- Click emits the existing `ViewCubePick`.

So yes: Three.js can do all the interaction. The earlier issues were implementation discipline issues, not a limitation of Three.js.
