But here, `ray-trace` is not true ray tracing. The UI even says so: [Viewport3DLayersPanel.tsx](/Users/jhoetter/repos/bim-ai/packages/web/src/workspace/viewport/Viewport3DLayersPanel.tsx:392) describes it as “PBR + SSAO + shadows, not realtime path tracing.”

Implementation-wise, `realistic` and `ray-trace` are almost the same:

- both restore `MeshStandardMaterial`
- both show texture maps
- both use ACES tone mapping / photographic exposure
- both use the same material path

The main real renderer difference I found is only shadow filtering: [Viewport.tsx](/Users/jhoetter/repos/bim-ai/packages/web/src/Viewport.tsx:4781) switches `ray-trace` to `THREE.VSMShadowMap`, while other modes use `THREE.PCFSoftShadowMap`.

So: **conceptually they’re different, but in this app today the difference is mostly cosmetic/subtle.** I’d either rename `Ray trace` to something like `High fidelity` / `Preview+`, or remove it until there’s a real path tracing implementation.

2. Add a real path-traced preview mode that progressively refines while the camera is still.
3. Reset accumulation when the camera/model/materials change.
4. Fall back to current `ray-trace` raster mode on unsupported devices.
5. Hide/disable editor overlays during path traced rendering, or composite them separately.

The hard parts are not “drawing triangles.” They are:

- keeping selection outlines, grids, view cube, dimensions, and authoring handles usable
- performance on large BIM scenes
- progressive rendering UX, denoising/noise expectations, and mobile fallback

So I’d call it **medium-to-high complexity**, but not unrealistic. A prototype is probably a few focused days. A production-quality version that behaves well on real BIM models is more like a proper feature track.

My recommendation: rename the current mode to **High fidelity** now, then add a separate **Path trace preview** later as a still/progressive renderer, not as a normal modeling mode.

> DEVELOPER

so will i require dedicated hardware for ray-tracing? could the model be computed on a server with GPU or not?

> AGENT

You do **not** need dedicated RTX-style ray-tracing hardware as a hard requirement.

For this app there are three realistic options:

1. **Client GPU in the browser**
   This is the best near-term path. A WebGL2/WebGPU path tracer runs shader code on the user’s GPU. It does not require RT cores, but it does require a reasonably capable GPU. Integrated GPUs can work for smaller scenes, just slower/noisier.

2. **Server GPU rendering**
   Yes, absolutely possible. The BIM model can be exported or serialized to a render scene on the server, rendered on a GPU machine, then returned as an image. This is the best path for high-quality stills, heavy scenes, consistent output, or users on weak devices.

3. **Server CPU rendering**
   Also possible, but usually slower and less cost-effective for this workload. CPU rendering is fine for offline jobs if latency is acceptable, but it is not a good fit for interactive preview.

So the answer is:

- **For interactive in-browser preview:** needs GPU, but not necessarily dedicated ray-tracing hardware.
- **For high-quality render export:** server GPU is very viable.
- **For CPU only:** technically possible, but I would treat it as a fallback/offline path, not the main product direction.

A good architecture would support both: client GPU path-trace preview for quick review, and server GPU render jobs for final stills.

> AGENT

I would not require dedicated laptops. I’d design this as a tiered capability.

For normal BIM use, users should stay on the current raster viewport: shaded, realistic, high-fidelity raster. That should remain the default path for older laptops, office desktops, and weaker integrated GPUs.

For **client-side path tracing**, expectations should be:

- **Apple M-series MacBooks:** likely good for small/medium BIM scenes and progressive previews.
- **Recent Windows laptops with NVIDIA/AMD GPUs:** good, especially discrete GPUs.
- **Recent integrated GPUs:** usable for small scenes at lower resolution/sample counts, but not something to promise.
- **Older Intel MacBooks / older office laptops:** likely too slow for a good path-traced experience. They should get the raster fallback or server render.
- **Mobile/tablet:** probably fallback only, unless the scene is tiny.

The product answer is: **don’t make ray tracing a hardware requirement. Make it an enhancement.**

I’d ship it with capability tiers:

| Tier | User Hardware | Experience |
|---|---|---|
| Baseline | Any supported laptop/browser | Raster realistic/high-fidelity mode |
| Preview | Decent integrated GPU / M-series / discrete GPU | Low-res progressive path trace |
| Pro | Strong discrete GPU / newer M Pro/Max | Higher samples, better responsiveness |
| Cloud | Weak or old hardware | Server GPU render job |

The safest UX is:

- Always allow modeling/editing without path tracing.
- Detect GPU/browser capability.
- Hide or disable `Path trace preview` when it will be bad.
- Offer **server render** for final images.
- Keep the current raster mode as the universal fallback.

So, for your users: **no, they should not need dedicated laptops.** Users with better GPUs get faster previews; users on older hardware can still use the app and request cloud/server renders for final-quality images.
