### Section 3: Error Handling & Edge Cases Keeping this minimal per your preferences — only handling things that would actually break the release: **Hard stops (abort the release):** - Not on `master` branch → "Switch to master first" - Dirty working tree → "Commit or stash changes first" - Build fails → Show error, stop. Commit is already pushed, so instruct user to fix and re-run `/release` (it'll detect the version is already bumped and skip to publish) **Soft warnings (inform but continue):** - No git tags found → Use first commit as baseline, warn that changelog may be verbose - `npm view` version check fails → Warn but don't block (npm registry can be slow to update) **Resume behavior:** If a previous release attempt partially completed (version bumped + committed but not published), the skill detects this by comparing `package.json` version against the latest npm version.
