> AGENT

Good question. **It will work fine.** Here's why: better-auth stores social logins in the `account` table with `provider_id = "github"` and `account_id = <GitHub user ID>`. The GitHub user ID is the same regardless of which OAuth App was used to authenticate — it's tied to the GitHub user, not the OAuth App. So when a user signs in via the production GitHub App, better-auth creates: - A `user` row - An `account` row with `provider_id = "github"`, `account_id = "12345"` (their GitHub user ID) When the same user signs in locally via the dev GitHub App, better-auth sees the same `provider_id + account_id` combo, matches the existing account, and creates a new session for the same user. **One caveat**: The `access_token` and `refresh_token` stored in the `account` table will be from whichever OAuth App was used last. This only matters if you use the token to call GitHub's API on behalf of the user — the token from the dev app won't work for the production app's scopes and vice versa. But if you're only using GitHub for authentication (not API access), this is a non-issue. **TL;DR**: Create the second OAuth App, add its credentials to `ci`, and it'll work against the prod database with the same users.
