Good point — pulling 15MB+ rows through the API is a non-starter. Here are the realistic alternatives: ### Option A: `ALTER TABLE UPDATE` (mutation) Update `organization_id` in place on both tables: ```sql ALTER TABLE rudel.claude_sessions UPDATE organization_id = '{newOrgId}', ingested_at = now64(3) WHERE organization_id = '{oldOrgId}' ALTER TABLE rudel.session_analytics UPDATE organization_id = '{newOrgId}', ingested_at = now64(3) WHERE organization_id = '{oldOrgId}' ``` **Pros:** No data copying, no memory pressure, no temp tables. Simplest by far. **Cons:** Mutations are async — we'd need to poll `system.mutations` for completion before deleting the Postgres org. Also, mutating an ORDER BY key column means ClickHouse rewrites affected data parts (which is fine, just takes time). Need to verify this works on SharedReplacingMergeTree (ClickHouse Cloud). ### Option B: Temp table as intermediary Data stays entirely in ClickHouse, bypasses the same-table `INSERT...SELECT` limitation: ```sql CREATE TABLE rudel._migration_tmp AS rudel.claude_sessions; INSERT INTO rudel._migration_tmp SELECT * FROM rudel.claude_sessions WHERE organization_id = '{oldOrgId}'; INSERT INTO rudel.claude_sessions SELECT '{newOrgId}' AS organization_id, /* all other columns */ FROM rudel._migration_tmp; DROP TABLE rudel._migration_tmp; DELETE FROM rudel.claude_sessions WHERE organization_id = '{oldOrgId}'; -- repeat for session_analytics or let MV handle it ``` **Pros:** Data never leaves ClickHouse, works with any row size. **Cons:** Temporarily doubles storage for the migrated data. More moving parts (temp table lifecycle, explicit column listing).
