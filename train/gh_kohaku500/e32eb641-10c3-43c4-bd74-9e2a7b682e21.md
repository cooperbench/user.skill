79	### WebViewでJavaScriptが動かない
80	
81	WebViewを表示しても計算が全く動きませんでした。エラーも出ないのに何も動かない状態。しばらく悩んで調べてみると、デフォルトでJavaScriptが無効になっているとのことでした。
82	
83	```kotlin
84	webView.settings.javaScriptEnabled = true
85	```
86	
87	この1行を追加したら動きました。エラーも出ずに静かに失敗していたので、原因にたどり着くまで時間がかかりました。
88	
89	### ローカルHTMLからJSファイルが読み込めない
90	
91	`assets/js/calc.js` を `<script src="js/calc.js">` で読み込もうとしたら動かないケースがありました。
92	
93	`loadUrl("file:///android_asset/index.html")` で開くと `assets/` 配下を相対パスで参照できることがわかり、HTMLとJSをassetsにフラットに置く構成にしてから安定しました。
94	
95	### INTERNET権限は不要だった
96	
97	WebViewを使うのでINTERNET権限が必要だと思い込んでいましたが、ローカルHTMLだけなら不要でした。結果的にオフライン動作の根拠にもなったので、これはよかったと思っています。
98	
99	### 外部リンクをタップしても何も起きない
100	
101	v1.1.0でフィードバックボタン（外部URLを開く機能）を追加したところ、タップしても何も起きない問題が発生しました。エラーは一切出ません。
102	
103	原因は `WebViewClient` のデフォルト動作にありました。デフォルトの `WebViewClient` は `http://` / `https://` のURLをWebView内部で処理しようとします。ローカルHTMLからの外部リンクは `file://` スキームのコンテキストになるため、外部URLへの遷移が黙って無視されていました。
104	
105	```kotlin
106	// 修正前: 外部URLを開けない
107	webView.webViewClient = WebViewClient()
108	
109	// 修正後: http/https はシステムブラウザへ委譲
110	webView.webViewClient = object : WebViewClient() {
111	    override fun shouldOverrideUrlLoading(view: WebView, request: WebResourceRequest): Boolean {
112	        val url = request.url.toString()
113	        if (url.startsWith("http://") || url.startsWith("https://")) {
114	            startActivity(Intent(Intent.ACTION_VIEW, request.url))
115	            return true
116	        }
117	        return false  // file:// はWebView内で継続処理
118	    }
119	}
120	```
121	
122	`shouldOverrideUrlLoading` をオーバーライドして、外部URLは `Intent.ACTION_VIEW` でシステムブラウザに渡すようにしたら解決しました。`return false` の部分でローカルファイル（`file://`）は引き続きWebViewで処理されます。
123	
124	ローカルHTMLをメインコンテンツにするアーキテクチャでは、この対応が必須になります。

285	## はじめに
286	
287	「あの機械、ちょっと音が変じゃないか？」
288	
289	製造現場で何年も働いていると、この直感が身につきます。ギアボックスのうなり方、モーターの回転音、軸受の微かな異音——熟練した整備士や保全担当者は、耳と経験で「おかしい」を感知します。

292

297	## 現在の設備診断の現実
298	
299	製造業の設備診断には、大きく3つのアプローチがあります。
300	
301	**1. ベテランの感覚診断**
302	経験豊富な技術者が音・振動・熱を感覚で判断する。精度は高いが、その人がいなければ成立しない。
303	
304	**2. 専用計測器による診断**
305	Fluke、SKF、Auguryなどの専用機器とセンサーを使う。精度は高いが、機器のコストが高く、使いこなすには専門知識が必要。中小製造業には導入ハードルが高い。
306	
307	**3. スマートフォンアプリ（現状）**
308	音量を測るだけ、FFT（周波数分析）を表示するだけ——で終わっている。「この周波数が高いのは正常なのか異常なのか」が、アプリだけではわからない。
309	
310	つまり、**「安く・すぐに・誰でも」使える診断ツールが、現場には存在していない**のが現状です。

314	## 逆転の発想：「正しい音を先に計算する」
315	
316	現在の診断アプリの多くは、「実測データを積み上げてAIが異常を検知する」方式です。これには問題があります——**学習データが必要**、つまり機械を長期間観測しないと機能しない。新しく設置した機械には、すぐには使えない。
317	
318	私が考えているのは、逆のアプローチです。
319	
320	> **「仕様から理論値を先に生成して、実測と照合する」**
321	
322	モーターの極数と回転数がわかれば、出るべき周波数は計算できます。減速機のギア比がわかれば、かみ合い周波数も計算できます。**機械が「正常時に出すべき音」を先に予測する**——そこと実測のズレが、異常のサインになる。
323	
324	「AIに学習させる」のではなく、「物理モデルで予測する」。これが既存アプリとの根本的な違いです。
