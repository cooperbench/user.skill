# Long-task and task-run record protocol

Use this protocol for **tier L** tasks (see `AGENTS.md`). Tier **S** / **M**
Cursor sessions should not create run records unless the user names a run id.

Task-run records are process metadata, not product data.

The canonical schema is `agent_rules/task_run.schema.yaml`. The template is
`agent_rules/templates/task_run.template.yaml`.

## Before substantial edits (tier L)

1. Read the user prompt, the relevant skill `SKILL.md`, and any named source
   plans.
2. If the user names a run record, open it from `agent_rules/runs/` and use it.
3. If no run is named, create or select a run record for the exact plan slice
   implied by the prompt.
4. If more than one active run plausibly matches, ask which run to use.
5. Inspect current dirty state and **only** `in_progress` / `blocked` entries in
   `agent_rules/runs/INDEX.md`. Ignore stale `implemented` / `verified` YAML still
   under `runs/` until archived to `runs/closed/`. See `runs/README.md`.
6. Restate the run id, selected scope, source artifacts, acceptance criteria,
   required gates, and important assumptions.

## During work

- Keep the run record current: files changed, assumptions, open questions, plan
  deltas, deviations, gate results, recovery attempts, confidence, residual
  risk, and handoff summary.
- Do not broaden scope without recording the reason in the run record.
- Re-read source artifacts before resuming a paused run.
- If a source plan changes but scope and gates still hold, record a plan delta
  and continue.
- If acceptance criteria, scope, storage authority, gate IDs, thresholds, or
  ownership change materially, mark the run `blocked` or `superseded` and create
  a new run record after human or prompt clarification.

## Status meanings

- `pending`: run record exists but work has not started.
- `in_progress`: actively being worked.
- `blocked`: cannot proceed without a specific resolution.
- `implemented`: code or documentation exists, but verification is incomplete.
- `verified`: acceptance criteria are met and required gates passed.
- `superseded`: source plans changed enough that a new run record should own
  further work.
- `deferred`: intentionally moved out of the current selected scope.

Active statuses (kept in `agent_rules/runs/`): `pending`, `in_progress`,
`blocked`, `implemented`. Closed statuses (`verified`, `superseded`, `deferred`)
should be moved to `agent_rules/runs/closed/` once the transition is recorded.

## Gate discipline

- Process and performance gates are first-class.
- A run with passing unit tests but missing process, integration, or performance
  evidence remains `implemented`, not `verified`.
- Never mark a run `verified` without evidence for every required gate.
- If a required gate fails, try up to three times to fix or isolate the issue
  before stopping.
- Mechanical-only fixes to unrelated files are allowed only when required to
  unblock a gate; do not make semantic changes to unrelated files without
  explicit user instruction.

## Multi-agent coordination

- Active coordination records have status `pending`, `in_progress`,
  `implemented`, or `blocked`.
- Records with status `verified`, `superseded`, or `deferred` do not reserve
  paths unless explicitly resumed.
- New or resumed runs should fill `coordination.agent_label`,
  `coordination.parallel_agents_expected`, `coordination.owned_paths`,
  `coordination.owned_subsystems`, `coordination.blocked_by_active_runs`, and
  `coordination.coordination_notes`.
- Keep owned paths narrow.
- Ask before editing a path owned by another active run, unless the user
  explicitly names the same run record.

### Parallel prompt execution

Parallel execution for saved prompt batches is Codex-orchestrated by default.
Use path-owned lanes on `dev_sprint`, not branch or worktree isolation, unless
the user explicitly requests another model.

- A user request to execute a prompt batch in parallel authorizes the main Codex
  chat to act as orchestrator and delegate worker lanes.
- The orchestrator run owns the dependency graph, lane plan, worker prompts,
  integration order, prompt archival, verification, staging, and commit.
- Worker runs must set `parallel_execution.role: worker`, reference the
  orchestrator run and lane, edit only assigned `owned_paths`, and report back
  without moving prompts to `agent_rules/prompts/executed/`, staging, or
  committing.
- Lower-numbered prompts may run beside later prompts only when the prompt
  planning record explicitly proves the lanes are independent and their
  ready/dispatched owned paths do not overlap.
- Use `agent_rules/templates/parallel_prompt_worker_handoff.template.md` when
  dispatching a worker lane.
