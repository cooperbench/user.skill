## 6. NOTABLE ARCHITECTURAL DECISIONS & GAPS

**Strengths:**
1. **Stateless Horizontal Scaling**: API can run N workers (compose.prod.yml configures 2 uvicorn workers, line 51). Worker queue is database-backed, not in-memory.
2. **Atomic Job Claiming**: Lease-based ownership prevents duplicate execution across multiple worker instances.
3. **Immutable Audit Trail**: Runs, artifacts, prompts all immutable after creation. Updates are new records (graphs table has `parent_graph_id`).
4. **Cost Tracking**: Per-run and per-step LLM token/cost metrics (RunRow.total_llm_usd, RunStepRow.llm_usd).
5. **Multi-Tier Auth**: Can scale from dev (no auth) to single-key (ELIJAH_API_KEY) to multi-user (TOML registry) without code changes.
6. **Database-Centric**: Single source of truth is PostgreSQL. Artifacts are just pointers (SHA256 hashes + object keys).

**Weaknesses / Gaps:**
1. **Artifact Storage Ambiguity**: S3/MinIO environment variables are declared but never instantiated in code review. Current implementation is local filesystem only. No S3 client (boto3) dependency visible. Tests acknowledge removal ("SPI-37: MinIO removal"). **Risk**: Scaling beyond single-machine artifact storage requires implementing the S3 backend—not yet done.
2. **No Built-In Fault Tolerance**: Worker crashes during job execution do not automatically checkpoint. Job is orphaned (lease expires, then reclaimed by next worker), but partial progress is lost.
3. **Frontend is Monolithic**: All JS loaded into single page. No module bundling (Webpack/Vite). Assets are inline or from CDN. Maintenance risk as feature count grows (test suite warns: "maintainability_baseline.py" monitors per-question explorer split).
4. **Job Deduplication Only by Idempotency Key**: No content-hash-based deduplication (e.g., two identical questions submitted twice). Relies on client-side idempotency keys.
5. **Limited Observability**: Logging is per-request (X-Trace-Id middleware), but no distributed tracing (Jaeger/Datadog). LLM traces stored in DB but no UI for review.
6. **Polling-Based Queue**: Worker continuously polls DB for jobs. No push mechanism (e.g., PgNotify). Scales OK for O(100) jobs/day, but latency will degrade under high load.
7. **Single LiteLLM Instance**: LiteLLM proxy is single-instance (HA not configured). If LiteLLM fails, all LLM calls fail (but app continues if cached responses exist).

**Production Configuration:**
- compose.prod.yml: 2 API workers, 1 job worker, 1 DB, 1 LiteLLM. No Redis, no S3 defaults, no load balancer template (assumed Nginx/K8s outside).
- Health checks: Every 10s for API (20s start_period), 30s for worker (15s start_period), 5s for DB.
- Secrets: POSTGRES_PASSWORD, LITELLM_API_KEY, ELIJAH_API_KEY all required at runtime (no defaults, will fail if missing).

### 3. **Bayesian Graph Inference & Probability Calibration Engine** (18,613 LoC in core/)

The system doesn't just extract factors; it **performs exact Bayesian network inference**:

- **`bn_inference.py` (150+ lines)**: Factor-based exact inference using logistic CPD coefficients. CONDITIONAL edges are interpreted as log-odds (beta_ij = log(edge.weight)), baseline probabilities as logits (beta_i0 = logit(node.baseline_p)). The system:
  - Builds conditional probability distributions from edges
  - Marginalizes out variables via factor operations (restrict, sum_out, multiply)
  - Handles topological ordering for leaf-up inference
  - Clips probabilities to avoid numerical instability (_EPSILON = 1e-9)

- **`indicator_extraction.py`**: Claude API directly extracts causal indicators from evidence chunks, returning structured JSON defining which observable variables predict driver truth.

- **`conditional_edge_quality.py`**: LLM critic pass that grades edges on causal_validity and empirical_grounding. Not just extracting relationships, but validating them post-hoc.

- **`relationship_judgment.py`**: Evaluates whether drivers actually influence the target, not just correlates.

- **`data_model.py` (200+ lines)**: Defines the Node/Edge/BayesianGraph object model with persistence bridge to SQL and JSON backends. Tracks duplicate edge blocking, edge type constraints (CONDITIONAL, REFERENCE, INSTANTIATES), and metadata provenance.

**Concrete file paths:**
- `/core/research_driver/bn_inference.py` (factor restriction, multiplication, marginalization)
- `/core/research_driver/data_model.py` (graph object model with CPD coefficients)
- `/core/research_driver/indicator_extraction.py` (causal indicator extraction from evidence)
- `/core/research_driver/conditional_edge_quality.py` (edge quality grading)

**Why it's hard:** A competitor would need to:
1. Understand logistic CPD coefficients and how to extract them from LLM outputs.
2. Implement exact Bayesian inference (not just sampling or approximate methods).
3. Handle numerical stability in probability clipping.
4. Validate edges post-hoc and integrate feedback into the graph.

This is not a prompt tuning problem — it's a probabilistic graphical model problem. GPT-4 can't generate correct Bayesian inference code without significant scaffolding.

### 4. **Recursive Validation Harness & Tuning Authority** (fs10_validation/, 12,908 LoC)

  - raw_value and comparable_value (normalized for metric direction)

- **Authority over prompt edits** (`tuning_authority.py`, `tuning_store.py`): Database-backed tracking of which prompt variant produced which scores. Includes:

- **FS10 question ingest** (`ingest.py`, `entity_resolution.py`): Ingests resolved GJOpen questions with correct outcomes for backtesting. Entity resolution links forecasted entities (company names, dates) to ground truth answers.

**Concrete file paths:**

### 5. **Production Persistence & Dual-Mode Storage Architecture** (21,904 LoC in packages/)

The storage layer is not a simple wrapper — it's a **protocol-based abstraction** supporting:

- **`interfaces.py`**: `GraphStoreRepository` protocol (the contract). Both JSON and SQL backends implement the same interface, allowing:
  - Development with local JSON files
  - Production with Postgres + MinIO S3
  - Hot migration between modes (via `migrate.py`)

- **Dual-backend graph persistence** (`graph_store.py`, `sql_repositories.py`):
  - JSON: Atomic writes to graphs/, nodes/, edges/, questions/, summary.json
  - SQL: SQLAlchemy ORM with class-table inheritance, proper foreign keys, and PostgreSQL ENUMs

- **Job queue with lease-based polling** (`job_queue.py`): Workers claim leases on jobs, heartbeat to prove they're alive, and orphaned jobs are auto-reclaimed. Not a simple queue — handles timeout management, worker crash recovery, and distributed coordination.

- **Object storage for artifacts** (`object_store.py`): Abstracts S3/MinIO for PDF storage, with signed URLs for downloads. Run artifacts (sources.json, drivers.json, indicators_graph.json) are persisted to S3, not inline.

- **Separate question catalog** (`question_catalog.py`): Questions have their own CRUD surface, distinct from the graph store, allowing question updates without full graph rebuilds.

**Concrete file paths:**
- `/packages/storage/interfaces.py` (GraphStoreRepository protocol)

**Why it's hard:** A competitor would need to:

### 2. FAILURE HANDLING

**LLM Call Retries (Tenacity):**
- Configured in `/packages/inference/llm/runtime.py:587-594`
- **Retry strategy**: Exponential backoff (min 1s, max 20s), max 4 attempts by default, retry only on retryable exceptions
- Retryable markers defined in line 592: `retry_if_exception(self._is_retryable_exception)`
- Retried on: API connection errors, timeouts, rate-limit (429), 5xx status codes (marked at line 37: `from tenacity import ...`)

**HTTP Client Retries (Non-ArXiv):**
- Defined in `/services/worker/agents/ResearchDriver/research_agent/http_client.py:29-47`
- Max 4 attempts, exponential backoff starting 1.5s, handles 429/5xx status codes
- Used by Congress API, Metaculus, NewsAPI, OpenFDA, and other external providers

**Per-Question Retry Loop:**
- Batch pipeline retries individual questions (`research_driver_batch_pipeline.py:51-85`)
- Retryable exception types: APIConnectionError, TimeoutError, RateLimitError, ServiceUnavailableError, etc.
- Non-retryable failures (extraction failures, schema violations) are marked FAILED immediately
- Retry queue built at line 232: `retry_queue: list[tuple[int, dict[str, Any], int]] = []`

**Job-Level Failure Handling:**
- Lease-based heartbeat (`queue_runner.py:45-94`) periodically extends job lease and checks for cancellation
- Job timeout: 2× lease duration (default 3600s, configurable via QUEUE_LEASE_SECONDS at `runtime_config.py:40`)
- If worker crashes, orphan reclaim logic at `job_queue.py:119-120` picks up stale leases after 2× lease timeout
- Job failure recorded with `error_code` and `error_message` (`database.py:684-685`)

**Idempotency:**
- Jobs accept `idempotency_key` parameter (`job_queue.py:60`, `contracts/jobs.py:44`)
- Duplicates are deduplicated by `find_by_idempotency_key()` lookup (`job_queue.py:88-92`)
- **Limitation**: No per-run checkpoint/resume mechanism—if a run fails mid-pipeline, it must be re-submitted; no ability to resume from last successful step
