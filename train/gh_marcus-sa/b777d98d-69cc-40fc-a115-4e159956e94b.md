   297→- Polymorphic entity reference fields (for example: `entity_id`, `target`) MAY use `table:id`, but only when the field is explicitly documented as polymorphic.
   298→- Parse IDs exactly once at the HTTP/CLI boundary:
   299→  - fixed-table fields: `new RecordId("<known_table>", rawId)`
   300→  - polymorphic fields: parse `table:id` with table allowlist validation, then convert to `RecordId`
   301→- Never re-wrap prefixed values: reject fixed-table IDs containing `:` with a hard error instead of attempting recovery.
   302→- Never emit fixed-table IDs as `table:id` in API responses or CLI cache payloads. Emit raw IDs only.
   303→- If table context must be returned to clients, return it in a separate field (for example: `{ id: "<raw>", table: "task" }`), not by prefixing `id`.
   304→- `table:id` strings are for explicit polymorphic references only; they are not a general serialization format for all IDs.
   305→- Forbidden pattern: `new RecordId("agent_session", "agent_session:uuid")` (creates nested/mismatched IDs like `agent_session:⟨agent_session:uuid⟩`).
   306→- Any change touching ID read/write paths MUST include tests that cover:
   307→  - fixed-table round-trip (`raw -> RecordId -> raw`)
   308→  - polymorphic parse/validation (`table:id -> RecordId`)
   309→  - rejection of prefixed input in fixed-table fields.

   311→## SurrealDB KNN + WHERE Bug (v3.0)
   312→
   313→- SurrealDB v3.0 query planner silently returns empty results when a WHERE clause combines a KNN operator (`<|K, COSINE|>`, which uses the HNSW index) with a condition covered by a regular B-tree index (e.g. `workspace = $ws` when a `workspace` index exists).
   314→- Tables WITHOUT a B-tree index on the filtered field work fine with KNN + WHERE in the same clause.
   315→- Workaround: split into two steps — KNN in a `LET` subquery (HNSW index only), then filter by workspace in a second query (B-tree index only):
   316→  ```sql
   317→  -- BROKEN: both indexes conflict
   318→  SELECT ... FROM task WHERE workspace = $ws AND embedding <|20, COSINE|> $vec;
   319→
   320→  -- WORKS: separate index usage
   321→  LET $candidates = SELECT ..., workspace FROM task WHERE embedding <|20, COSINE|> $vec;
   322→  SELECT ... FROM $candidates WHERE workspace = $ws ORDER BY similarity DESC LIMIT $limit;
   323→  ```
   324→- Apply this pattern to ALL KNN queries on tables that have a regular index on the filtered field.

   326→## SurrealDB Full-Text Search (BM25)
   327→
   328→Reference: https://surrealdb.com/docs/surrealql/functions/database/search
   329→
   330→The UI entity search uses SurrealDB's built-in BM25 full-text search, not vector/KNN search. Vector search is reserved for the chat agent's `search_entities` tool where semantic similarity matters.
   331→
   332→### Setup
   333→
   334→Full-text search requires an analyzer and `FULLTEXT` indexes:
   335→```sql
   336→-- Analyzer with stemming (English snowball) and lowercase normalization
   337→DEFINE ANALYZER entity_search
   338→  TOKENIZERS blank, class, camel, punct
   339→  FILTERS snowball(english), lowercase;
   340→
   341→-- Per-field fulltext index (one index per field, not per table)
   342→DEFINE INDEX idx_task_fulltext ON task FIELDS title FULLTEXT ANALYZER entity_search BM25;
   343→```
   344→
   345→### Query syntax
   346→
   347→- Use the `@N@` match operator (N is a predicate reference number for `search::score`):
   348→  ```sql
   349→  SELECT id, title, search::score(1) AS score
   350→  FROM task
   351→  WHERE title @1@ $query
   352→  ORDER BY score DESC LIMIT 10;
   353→  ```
   354→- `search::score(N)` returns the BM25 relevance score for predicate N.
   355→- `search::highlight('<b>', '</b>', N)` returns text with matching tokens wrapped in tags.
   356→### Known limitations (SurrealDB v3.0)
   357→
   358→- `search::score()` and `@N@` do NOT work inside `DEFINE FUNCTION` — the predicate reference is lost across the function boundary. Search queries must run from the app layer. See: https://github.com/surrealdb/surrealdb/issues/7013
   359→- `@N@` does NOT work with SDK bound parameters (`$query`). The search term must be embedded as a string literal in the query. Escape single quotes before interpolation.
   360→- `BM25` without explicit parameters returns score=0. Always use `BM25(1.2, 0.75)`.

   367→
   368→Reference: https://surrealdb.com/learn/fundamentals/schemafull/define-fields
   369→
   370→- Do NOT use `.tb` on `RecordId` — it works at runtime but is not in the SDK type definition and may break on upgrade. Use `.table.name` instead (returns the same typed `Tb` string via the public API).
   371→- When using `http://` or `https://` URLs, the SDK uses HTTP transport only. It does NOT attempt WebSocket upgrade.
   372→- WebSocket is only used when the URL scheme is `ws://` or `wss://`.
   373→- To CREATE a record with a specific ID, use the SDK's `RecordId` class:
   374→  ```typescript
   375→  import { RecordId } from "surrealdb";
   376→  const record = new RecordId("table", "my-id");
   377→  await query("CREATE $record CONTENT $content;", { record, content: {...} });
   378→  ```
   379→- To SELECT a specific record by ID, use `RecordId` in the FROM clause:
   380→  ```typescript
   381→  const record = new RecordId("gladiator", id);
   382→  await query("SELECT * FROM $record;", { record });
   383→  ```
   384→- Do NOT use string-based record IDs like `table:id` in queries - use `RecordId` objects.
   385→- For optional record fields (e.g. `option<record<match>>`), omit the field instead of setting `null` - SurrealDB defaults to `NONE`.
   386→- Query results return `RecordId` objects for record references - cast directly, no string conversion needed.
   387→- Clause order: `SELECT ... FROM ... WHERE ... LIMIT ... FETCH ...` - `LIMIT` must come before `FETCH`.
   388→- **ORDER BY fields MUST be in the SELECT projection.** SurrealDB v3.0 raises a hard parse error (`Missing order idiom ... in statement selection`) when an ORDER BY field is not selected. This fails at query time, not at schema time, so it often hides until the query is actually executed. Always include every `ORDER BY` field in the `SELECT` projection. Example: `SELECT id, summary, created_at FROM decision ORDER BY created_at DESC` (not `SELECT id, summary ... ORDER BY created_at`).
   389→- Known issue: Surreal can throw `Expected a single result output when using the ONLY keyword` when a statement uses `ONLY` and returns no record output.
   390→- Workaround: force a return clause. In SDK calls that map to `ONLY` (for example `relate(...)`), use `.output("after")` so the statement returns a record.
   391→- Type query results directly. Access `RecordId.id` directly - do NOT create wrapper functions like `extractRecordId()`, `toString()`, etc:
   392→  ```typescript
   393→  const rows = await selectMany("SELECT id, name FROM gladiator WHERE totalWins > 0;") as Array<{ id: RecordId; name: string }>;
   394→  const result = rows.map((row) => ({ gladiatorId: row.id.id as string, name: row.name }));
   395→  ```
   396→- Do NOT use `FETCH` in queries if you need the raw RecordId reference. `FETCH` resolves references to full objects.
   397→- For `TYPE RELATION` tables, do NOT write edges with `CREATE`. `CREATE` produces non-relation records and will fail relation constraints. Use `RELATE` (or SDK `relate(...)`) to create actual relation edges.
   398→- For nested arrays (2D grids), use explicit type: `DEFINE FIELD grid ON match TYPE array<array<string>>;` - plain `array` silently rejects nested arrays in SCHEMAFULL mode.
   399→- Keep all Surreal tables in `schema/surreal-schema.surql` as `SCHEMAFULL`. Do NOT introduce `SCHEMALESS` tables.
   400→- In `SCHEMAFULL`, every persisted nested key must be explicitly declared. For `array<object>` fields, always define `field[*].subField` entries for all written properties.
   401→- Do NOT rely on permissive object inference for production payloads. If code writes a new key, update schema in the same change before deploy.
   402→- After schema changes, verify with `INFO FOR TABLE <table>;` in the target namespace/database to confirm nested fields are present.
