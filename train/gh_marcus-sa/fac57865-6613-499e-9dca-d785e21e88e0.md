You're making an important point. Let me clarify what's actually happening:

The predicate evaluator (`resolveDotPath`) accepts **any** dot-path string and traverses whatever object it gets. There's no restriction on what fields a policy can reference. Your example — "deny when `budget_limit.amount > 5000`" — works because `resolveDotPath` just walks the intent context object dynamically.

So the **autocomplete** question is really about **UX convenience**, not about **validation**. The field input is a free-text input where admins can type any dot-path. The autocomplete just suggests the *known* fields from `IntentEvaluationContext` to help them discover what's available.

The ADR as written is a bit misleading because it frames this as "which fields are valid" when actually:
- **Any** dot-path is valid — `resolveDotPath` handles arbitrary paths
- If a field doesn't exist on a particular intent, the predicate returns `false` (and a warning is emitted)
- The static list is just for **suggestions**, not **restriction**

This matters for your `$5K payment` example: the admin would type `budget_limit.amount`, operator `gt`, value `5000`, effect `deny`. The autocomplete helps them discover `budget_limit.amount` exists, but nothing stops them from typing `action_spec.params.payment_amount` if that's what their intents use.

Want me to update ADR-004 to clarify this distinction — that the field list is for autocomplete suggestions, not a validation allowlist? And that custom/unknown field paths are explicitly supported?
