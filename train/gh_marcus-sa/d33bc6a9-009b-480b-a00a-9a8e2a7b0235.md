> DEVELOPER

whats the difference between the context pipeline and the evaluation pipeline ?

> AGENT

Two completely separate pipelines that serve different purposes: **Context Pipeline** (`app/src/server/mcp/intent-context.ts`) - **When**: Before an agent starts working — it calls `POST /api/mcp/:workspaceId/context` with its intent (natural language description of what it plans to do) - **What it does**: Resolves the agent's intent to the right scope of knowledge graph context (task-level, project-level, or workspace-level) using entity refs, vector search, and path matching - **Output**: A context packet with tasks, decisions, constraints — so the agent knows what's relevant - **Think of it as**: "What do I need to know before I start?" **Evaluation Pipeline** (`app/src/server/intent/`) - **When**: After an agent decides to take an action — it declares an intent (e.g., "edit file X", "delete production DB") and submits it for authorization - **What it does**: 1. Policy gate (hard rules — e.g., reject destructive actions outright) 2. LLM authorizer (`authorizer.ts`) — evaluates risk score + approve/reject decision 3. Risk router (`risk-router.ts`) — routes by score: auto-approve (low), veto window (medium), reject (high) 4. Veto manager (`veto-manager.ts`) — human review window for medium-risk intents - **Output**: Intent transitions through `draft → pending_auth → authorized/pending_veto/failed` - **Think of it as**: "Am I allowed to do this?" **In short**: Context pipeline = *read* (gather knowledge), Evaluation pipeline = *write* (authorize actions).

isnt there an overlap here? shouldn't the same endpoint do both these things?

> AGENT

Good question. Let me look at what each endpoint actually receives and does to see if there's real duplication.

> AGENT

They're doing fundamentally different things at different points in time: **Context pipeline** — "Here's what you need to know" - Input: natural language intent + optional cwd/paths - Does: scope resolution (entity refs → vector search → path match → fallback), then builds a read-only context packet from the graph - Output: tasks, decisions, constraints relevant to the agent's work - Called: **before** the agent acts **Evaluation pipeline** — "Are you allowed to do this?" - Input: a structured intent record (goal, action type, target files, requester) - Does: policy gate → LLM risk assessment → risk routing (auto-approve / veto window / reject) - Output: authorization decision with risk score - Called: **when** the agent wants to take a specific action The overlap is only superficial — both take "intent" as input. But the context pipeline intent is vague ("I'm working on payment webhooks") while the evaluation pipeline intent is concrete ("edit `src/payments/stripe.ts`, delete `src/old-gateway.ts`"). Merging them would conflate two different lifecycle stages. An agent might call context once at session start, then trigger evaluation dozens of times as it takes individual actions. They have different cardinality, different inputs, and different consumers. That said — there *is* a missed connection: the evaluation pipeline doesn't use the resolved context to inform its risk assessment. If the evaluator knew "this agent is working on task X in project Y, and the file it wants to edit belongs to that project," it could make better risk judgments. But that's an enhancement to pipe context *into* evaluation, not a reason to merge the endpoints.
