Good question. Here's how I'd think about it:

**On removal → disable tools.** Set `status: "disabled"` on all tools where `source_server = $server`. Hard delete breaks `can_use` grants, `governs_tool` edges, and trace references. Disabling preserves all of that.

**On re-add → two scenarios:**

1. **Same server URL re-added**: Match the existing `mcp_server` record by URL in the workspace. If found (even if soft-deleted), re-enable it instead of creating a new one. Then discovery runs `computeSyncActions` against the disabled tools — they still have `source_server` pointing to the same record, so they get matched by name and re-enabled as "unchanged" or "update".

2. **Different URL / truly new server**: Fresh `mcp_server` record. Discovery creates new tool records. Old disabled tools remain as orphans (fine — they're invisible in the UI, grants are inert since the tools are disabled).

**The key insight**: if we soft-delete the server too (add `status` to `mcp_server`), then re-adding the same URL can resurrect the entire server + tools + grants in one operation. No orphans, no broken references.

So the implementation would be:
- `DELETE /mcp-servers/:id` → sets `mcp_server.status = "disabled"` + disables all its tools
- `POST /mcp-servers` → checks for existing disabled server with same URL in workspace first, re-enables if found
- Discovery then naturally re-enables matching tools via the existing sync logic
