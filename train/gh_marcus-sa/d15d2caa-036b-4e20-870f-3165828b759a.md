   353→
   354→- Do NOT use one universal ID string format across all API fields. ID format is field-specific and enforced.

   361→- Never emit fixed-table IDs as `table:id` in API responses or CLI cache payloads. Emit raw IDs only.
   362→- If table context must be returned to clients, return it in a separate field (for example: `{ id: "<raw>", table: "task" }`), not by prefixing `id`.

   370→## SurrealDB Query Batching
   371→
   372→- Do NOT issue multiple sequential `surreal.query()` calls when the queries share the same bound parameters. Combine them into a single `.query()` call with multiple statements separated by semicolons — this executes in one round-trip.
   373→- The SDK returns a typed tuple matching the statement order: `surreal.query<[ResultA[], ResultB[], ResultC[]]>("SELECT ...; SELECT ...; SELECT ...;", vars)`.
   374→- For `LET` + `SELECT` pairs (e.g. two-step KNN pattern), `LET` occupies result indices too: a query with `LET $a = ...; SELECT FROM $a; LET $b = ...; SELECT FROM $b;` returns results at indices `[0, 1, 2, 3]` where the `SELECT` results are at odd indices `[1, 3]`.
   375→- Multiple statements in a single `.query()` call do not trigger WebSocket concurrency issues; those only apply to multiple parallel `.query()` calls on the same connection.

   377→## SurrealDB KNN + WHERE Bug (v3.0)
   378→
   379→- SurrealDB v3.0 query planner silently returns empty results when a WHERE clause combines a KNN operator (`<|K, COSINE|>`, which uses the HNSW index) with a condition covered by a regular B-tree index (e.g. `workspace = $ws` when a `workspace` index exists).
   380→- Tables WITHOUT a B-tree index on the filtered field work fine with KNN + WHERE in the same clause.
   381→- Workaround: split into two steps — KNN in a `LET` subquery (HNSW index only), then filter by workspace in a second query (B-tree index only):
   382→  ```sql
   383→  -- BROKEN: both indexes conflict
   384→  SELECT ... FROM task WHERE workspace = $ws AND embedding <|20, COSINE|> $vec;
   385→
   386→  -- WORKS: separate index usage
   387→  LET $candidates = SELECT ..., workspace FROM task WHERE embedding <|20, COSINE|> $vec;
   388→  SELECT ... FROM $candidates WHERE workspace = $ws ORDER BY similarity DESC LIMIT $limit;
   389→  ```
   390→- Apply this pattern to ALL KNN queries on tables that have a regular index on the filtered field.

   468→
   469→Reference: https://surrealdb.com/learn/fundamentals/schemafull/define-fields

   471→- Do NOT use `.tb` on `RecordId` — it works at runtime but is not in the SDK type definition and may break on upgrade. Use `.table.name` instead (returns the same typed `Tb` string via the public API).

   484→  ```

   486→- For optional record fields (e.g. `option<record<match>>`), omit the field instead of setting `null` - SurrealDB defaults to `NONE`.

   488→- Clause order: `SELECT ... FROM ... WHERE ... LIMIT ... FETCH ...` - `LIMIT` must come before `FETCH`.

## [](#the-design-decisions-that-matter)The Design Decisions That Matter

**Why not one big repo?** Separation of concerns. The brain shouldn't depend on the tool. The catalog shouldn't contain executable logic. Mix them and you create coupling that makes the whole system fragile.

**Why Backstage format for the catalog?** It's an industry standard built exactly for this — describing what exists, who owns it, and how it relates to other things. It's human-readable, tool-agnostic, and designed to scale.

**Why symlinks instead of copies?** Real-time updates without redeployment. Edit `terraform.md` in the library, it's immediately live in `~/repos/work/terraform/`. No sync step, no drift between source and deployed config.

**Why scope skills to directories instead of loading all of them?** Token efficiency and cognitive clarity. An agent with 30 loaded skills is an agent that has to decide which one applies. An agent with 2 loaded skills knows exactly what to use.

## [](#the-mental-model-a-package-manager-for-agent-intelligence)The Mental Model: A Package Manager for Agent Intelligence

Think of it like a software package manager, but for how agents think and behave.

The difference from a traditional package manager: the "packages" here are not code. They're _instructions for how to reason_ in a given context.

## The Problem

AGENTS.md is ~500 lines loaded into every conversation. An agent fixing a chat tool gets SurrealDB migration workflow rules. An agent writing a migration gets Chat Agent Architecture docs. You're paying tokens for irrelevant context every time.

## The Approach: Split into `@`-referenced files

Claude Code already has the mechanism — `@file` references in CLAUDE.md/AGENTS.md. The agent loads the root file always, but domain-specific knowledge lives in separate files that the root file references conditionally via `@` includes.

```
AGENTS.md                          ← Core rules only (~150 lines)
  @docs/agents/surrealdb.md        ← Schema, migrations, SDK, KNN bug, BM25, protected vars
  @docs/agents/chat-agent.md       ← Chat architecture, tools, PM agent, observations
  @docs/agents/testing.md          ← DPoP test infra, acceptance tests, evals
  @docs/agents/observability.md    ← Wide events, OTel, streaming spans
  @docs/agents/extraction.md       ← Extraction schema, structured output rules
```

## What stays in the root AGENTS.md

Universal rules that apply regardless of domain:
- Git commits (`--no-verify`, `-s`)
- Data value contract (no `null`)
- TypeScript conventions
- Failure handling
- Fire-and-forget / inflight tracking
- Server architecture overview (the directory map)
- RecordId wire format contract
- Agentic design: no hardcoded modes
- No `process.env` in application code

## What moves to domain files

| File | Sections moved |
|------|---------------|
| `surrealdb.md` | Schema migration workflow, existing data migration, KNN+WHERE bug, BM25 full-text search, query batching, protected variables, SDK v2, UNIQUE index bug, EVENT webhook timing |
| `chat-agent.md` | Chat agent architecture, tools table, shared tool layer, PM subagent, observation entity |

Claude Code's `@` references are lazy — the file is loaded when the agent encounters the reference. The root AGENTS.md would reference them like:

   373→

   380→
