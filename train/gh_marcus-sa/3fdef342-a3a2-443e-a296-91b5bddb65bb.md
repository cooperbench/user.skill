### project-md-files > Schema & Data Migration > SurrealDB Schema Migration Workflow
### SurrealDB Schema Migration Workflow

- Create a versioned `.surql` migration script for each schema change.
- Migration filenames MUST use a zero-padded autoincrement numeric prefix, followed by an underscore and slug (for example `schema/migrations/0008_add_task_priority.surql`).
- Determine the next prefix by scanning `schema/migrations` and incrementing the highest existing prefix. Do NOT reuse or renumber existing migration files.
- Apply migrations with `bun migrate` — the migration runner (`schema/migrate.ts`) tracks applied migrations in a `_migration` table and only runs pending ones.
- Do NOT apply migrations manually via `surreal import` or raw HTTP calls — always use `bun migrate`.
- Wrap migration scripts in `BEGIN TRANSACTION; ... COMMIT TRANSACTION;` so they succeed or fail atomically.
- `DEFINE ANALYZER` cannot run inside a transaction in SurrealDB v3.0. Place it before the `BEGIN TRANSACTION;` block.
- Prefer `DEFINE ... OVERWRITE` or `ALTER TABLE` / `ALTER FIELD` for schema evolution; reserve `IF NOT EXISTS` for bootstrap-only creation.
- SurrealDB does NOT support `ALTER TABLE ... ADD FIELD`. To add fields to existing tables, use `DEFINE FIELD OVERWRITE <field> ON <table> TYPE <type>;`.
- When removing fields, update schema and stored rows in the same migration (`REMOVE FIELD ...; UPDATE ... UNSET ...;`).
- Verify applied schema with `INFO FOR TABLE <table>;` in the target namespace/database.

## project structure overview

### project-md-files > Server Architecture Overview > Chat Agent Architecture
### Chat Agent Architecture

The chat system uses a thin orchestrator pattern where a single top-level chat agent dispatches to specialized subagents. The knowledge graph is the communication bus — agents read from and write to the graph independently, never passing data directly between each other.

```
User Message
  │
  ├─→ Extraction Pipeline (always runs, Haiku)
  │     └─→ entities/relationships → SurrealDB graph
  │
  └─→ Chat Agent (Sonnet, thin orchestrator)
        ├─→ Direct tools (search, entity detail, decisions, observations)
        └─→ Subagent dispatch
              └─→ PM Agent (Haiku) → suggestions, observations → graph
```

**Two paths to the graph:**
| Source | Path | Why |
|--------|------|-----|
| User messages | Extraction pipeline (Haiku infers entities from unstructured text) | User input is unstructured |
| Agent output | Direct graph write (agents already have structured form) | Nothing to extract |

**Key files:**
- `chat/handler.ts` — `runChatAgent()`: streams chat agent responses with tool use
- `chat/context.ts` — `buildChatContext()` / `buildSystemPrompt()`: loads graph context, builds chat agent system prompt
- `chat/tools/index.ts` — `createChatAgentTools()`: registers all chat agent tools
- `chat/tools/types.ts` — `ChatToolExecutionContext`: actor-typed context (`chat_agent | mcp | pm_agent`)

### project-md-files > Server Architecture Overview > Product Manager Subagent
### Product Manager Subagent

The PM agent (`agents/pm/`) is the single authority on tasks, features, and project status. It uses the AI SDK's `ToolLoopAgent` class and composes shared tools from `chat/tools/`. It is invoked by the chat agent via `invoke_pm_agent` tool with an intent:

| Intent | When to use |
|--------|-------------|
| `plan_work` | User discusses goals, features, or work to be done |
| `check_status` | User asks about project status, progress, or blockers |
| `organize` | User wants to restructure or re-prioritize |
| `track_dependencies` | User asks about blocked items or dependency chains |

**Key files:**
- `agents/pm/agent.ts` — `runPmAgent()`: creates `ToolLoopAgent` with PM tools, returns structured JSON output
- `agents/pm/prompt.ts` — `buildPmSystemPrompt()`: loads workspace projects and observations
- `agents/pm/tools.ts` — `createPmTools()`: composes shared tools (search_entities, get_project_status, create_observation, suggest_work_items, create_work_item)

**PM output schema:** `{ summary, suggestions: WorkItemSuggestion[], updated, discarded, observations_created }`

The chat agent renders PM suggestions as `WorkItemSuggestionList` component blocks in the chat UI.

### project-md-files > Server Architecture Overview > Work Item Accept Flow
### Work Item Accept Flow

When the PM agent suggests work items, the chat agent renders them as `WorkItemSuggestionList` components. Users can accept or dismiss each item:

- Accept calls `POST /api/workspaces/:workspaceId/work-items/accept`
- The endpoint creates a `task` or `feature` record in SurrealDB with embedding and optional project linking
- Implemented in `entities/work-item-accept-route.ts`

   104→- **Workspace mismatch pitfall**: If a test creates a workspace via the API (`POST /api/workspaces`) and then acquires a DPoP token via `createTestUserWithMcp()`, the token is bound to a *different* workspace. MCP endpoints will return 404 for resources in the API-created workspace. Fix: pass `{ workspaceId }` to `createTestUserWithMcp()` to bind the token to the pre-existing workspace, or use `user.workspaceId` for all resource creation.
   105→- **Pattern**: Create test user first (`createTestUserWithMcp`), then create tasks/projects in `user.workspaceId`. Do NOT create a separate workspace via API unless you pass its ID to `createTestUserWithMcp`.
   106→- **`mcpFetch` vs `mcpHeaders`**: Always use `user.mcpFetch(path, { body })` — it creates a fresh DPoP proof per request. The `mcpHeaders` property is deprecated and will fail because DPoP proofs are single-use.

   171→### Chat Agent Architecture
   172→
   173→The chat system uses a thin orchestrator pattern where a single top-level chat agent dispatches to specialized subagents. The knowledge graph is the communication bus — agents read from and write to the graph independently, never passing data directly between each other.
   174→
   175→```
   176→User Message
   177→  │
   178→  ├─→ Extraction Pipeline (always runs, Haiku)
   179→  │     └─→ entities/relationships → SurrealDB graph
   180→  │
   181→  └─→ Chat Agent (Sonnet, thin orchestrator)
   182→        ├─→ Direct tools (search, entity detail, decisions, observations)
   183→        └─→ Subagent dispatch
   184→              └─→ PM Agent (Haiku) → suggestions, observations → graph
   185→```
   186→
   187→**Two paths to the graph:**
   188→| Source | Path | Why |
   189→|--------|------|-----|
   190→| User messages | Extraction pipeline (Haiku infers entities from unstructured text) | User input is unstructured |
   191→| Agent output | Direct graph write (agents already have structured form) | Nothing to extract |
   192→
   193→**Key files:**
   194→- `chat/handler.ts` — `runChatAgent()`: streams chat agent responses with tool use
   195→- `chat/context.ts` — `buildChatContext()` / `buildSystemPrompt()`: loads graph context, builds chat agent system prompt
   196→- `chat/tools/index.ts` — `createChatAgentTools()`: registers all chat agent tools
   197→- `chat/tools/types.ts` — `ChatToolExecutionContext`: actor-typed context (`chat_agent | mcp | pm_agent`)

   274→### RecordId and Table Access Rules
   275→
   276→- After request parsing, use `RecordId` objects everywhere for Surreal identifiers (never raw `table:id` strings in internal logic).
   277→- Server extraction types define typed record aliases:
   278→  - `GraphEntityRecord` and `SourceRecord` are `RecordId<UnionOfTables, string>` aliases.
   279→- Use `record.table.name` for table branching (the SDK's public API; `.tb` is an undeclared internal field that may break on upgrade).
   280→
   281→### RecordId Wire Format Contract (Strict)
   282→
   283→- Do NOT use one universal ID string format across all API fields. ID format is field-specific and enforced.
   284→- Fixed-table ID fields (for example: `session_id`, `task_id`, `project_id`, `workspace_id`) MUST be raw IDs only (UUID/string without `table:` prefix).
   285→- Polymorphic entity reference fields (for example: `entity_id`, `target`) MAY use `table:id`, but only when the field is explicitly documented as polymorphic.
   286→- Parse IDs exactly once at the HTTP/CLI boundary:
   287→  - fixed-table fields: `new RecordId("<known_table>", rawId)`
   288→  - polymorphic fields: parse `table:id` with table allowlist validation, then convert to `RecordId`
   289→- Never re-wrap prefixed values: reject fixed-table IDs containing `:` with a hard error instead of attempting recovery.
   290→- Never emit fixed-table IDs as `table:id` in API responses or CLI cache payloads. Emit raw IDs only.
   291→- If table context must be returned to clients, return it in a separate field (for example: `{ id: "<raw>", table: "task" }`), not by prefixing `id`.
   292→- `table:id` strings are for explicit polymorphic references only; they are not a general serialization format for all IDs.
   293→- Forbidden pattern: `new RecordId("agent_session", "agent_session:uuid")` (creates nested/mismatched IDs like `agent_session:⟨agent_session:uuid⟩`).
   294→- Any change touching ID read/write paths MUST include tests that cover:
   295→  - fixed-table round-trip (`raw -> RecordId -> raw`)
   296→  - polymorphic parse/validation (`table:id -> RecordId`)
   297→  - rejection of prefixed input in fixed-table fields.

   299→## SurrealDB KNN + WHERE Bug (v3.0)
   300→
   301→- SurrealDB v3.0 query planner silently returns empty results when a WHERE clause combines a KNN operator (`<|K, COSINE|>`, which uses the HNSW index) with a condition covered by a regular B-tree index (e.g. `workspace = $ws` when a `workspace` index exists).
   302→- Tables WITHOUT a B-tree index on the filtered field work fine with KNN + WHERE in the same clause.
   303→- Workaround: split into two steps — KNN in a `LET` subquery (HNSW index only), then filter by workspace in a second query (B-tree index only):
   304→  ```sql
   305→  -- BROKEN: both indexes conflict
   306→  SELECT ... FROM task WHERE workspace = $ws AND embedding <|20, COSINE|> $vec;
   307→
   308→  -- WORKS: separate index usage
   309→  LET $candidates = SELECT ..., workspace FROM task WHERE embedding <|20, COSINE|> $vec;
   310→  SELECT ... FROM $candidates WHERE workspace = $ws ORDER BY similarity DESC LIMIT $limit;
   311→  ```
   312→- Apply this pattern to ALL KNN queries on tables that have a regular index on the filtered field.

   314→## SurrealDB Full-Text Search (BM25)
   315→
   316→Reference: https://surrealdb.com/docs/surrealql/functions/database/search
   317→
   318→The UI entity search uses SurrealDB's built-in BM25 full-text search, not vector/KNN search. Vector search is reserved for the chat agent's `search_entities` tool where semantic similarity matters.
   319→
   320→### Setup
   321→
   322→Full-text search requires an analyzer and `FULLTEXT` indexes:
   323→```sql
   324→-- Analyzer with stemming (English snowball) and lowercase normalization
   325→DEFINE ANALYZER entity_search
   326→  TOKENIZERS blank, class, camel, punct
   327→  FILTERS snowball(english), lowercase;
   328→
   329→-- Per-field fulltext index (one index per field, not per table)
   330→DEFINE INDEX idx_task_fulltext ON task FIELDS title FULLTEXT ANALYZER entity_search BM25;
   331→```
   332→
   333→### Query syntax
   334→
   335→- Use the `@N@` match operator (N is a predicate reference number for `search::score`):
   336→  ```sql
   337→  SELECT id, title, search::score(1) AS score
   338→  FROM task
   339→  WHERE title @1@ $query
   340→  ORDER BY score DESC LIMIT 10;
   341→  ```
   342→- `search::score(N)` returns the BM25 relevance score for predicate N.
   343→- `search::highlight('<b>', '</b>', N)` returns text with matching tokens wrapped in tags.
   344→### Known limitations (SurrealDB v3.0)
   345→
   346→- `search::score()` and `@N@` do NOT work inside `DEFINE FUNCTION` — the predicate reference is lost across the function boundary. Search queries must run from the app layer. See: https://github.com/surrealdb/surrealdb/issues/7013
   347→- `@N@` does NOT work with SDK bound parameters (`$query`). The search term must be embedded as a string literal in the query. Escape single quotes before interpolation.
   348→- `BM25` without explicit parameters returns score=0. Always use `BM25(1.2, 0.75)`.
   349→
   350→### Entity search implementation
   351→
   352→Search queries run from the app layer (`entity-search-route.ts`) instead of SurrealDB stored functions due to the limitations above. Fulltext indexes are defined in `schema/migrations/0002_fulltext_search_indexes.surql`.

   354→## SurrealDB SDK v2
   355→
   356→Reference: https://surrealdb.com/learn/fundamentals/schemafull/define-fields
   357→
   358→- Do NOT use `.tb` on `RecordId` — it works at runtime but is not in the SDK type definition and may break on upgrade. Use `.table.name` instead (returns the same typed `Tb` string via the public API).
   359→- When using `http://` or `https://` URLs, the SDK uses HTTP transport only. It does NOT attempt WebSocket upgrade.
   360→- WebSocket is only used when the URL scheme is `ws://` or `wss://`.
   361→- To CREATE a record with a specific ID, use the SDK's `RecordId` class:
   362→  ```typescript
   363→  import { RecordId } from "surrealdb";
   364→  const record = new RecordId("table", "my-id");
   365→  await query("CREATE $record CONTENT $content;", { record, content: {...} });
   366→  ```
   367→- To SELECT a specific record by ID, use `RecordId` in the FROM clause:
   368→  ```typescript
   369→  const record = new RecordId("gladiator", id);
   370→  await query("SELECT * FROM $record;", { record });
   371→  ```
   372→- Do NOT use string-based record IDs like `table:id` in queries - use `RecordId` objects.
   373→- For optional record fields (e.g. `option<record<match>>`), omit the field instead of setting `null` - SurrealDB defaults to `NONE`.
   374→- Query results return `RecordId` objects for record references - cast directly, no string conversion needed.
   375→- Clause order: `SELECT ... FROM ... WHERE ... LIMIT ... FETCH ...` - `LIMIT` must come before `FETCH`.
   376→- **ORDER BY fields MUST be in the SELECT projection.** SurrealDB v3.0 raises a hard parse error (`Missing order idiom ... in statement selection`) when an ORDER BY field is not selected. This fails at query time, not at schema time, so it often hides until the query is actually executed. Always include every `ORDER BY` field in the `SELECT` projection. Example: `SELECT id, summary, created_at FROM decision ORDER BY created_at DESC` (not `SELECT id, summary ... ORDER BY created_at`).
   377→- Known issue: Surreal can throw `Expected a single result output when using the ONLY keyword` when a statement uses `ONLY` and returns no record output.
   378→- Workaround: force a return clause. In SDK calls that map to `ONLY` (for example `relate(...)`), use `.output("after")` so the statement returns a record.
   379→- Type query results directly. Access `RecordId.id` directly - do NOT create wrapper functions like `extractRecordId()`, `toString()`, etc:
   380→  ```typescript
   381→  const rows = await selectMany("SELECT id, name FROM gladiator WHERE totalWins > 0;") as Array<{ id: RecordId; name: string }>;
   382→  const result = rows.map((row) => ({ gladiatorId: row.id.id as string, name: row.name }));
   383→  ```
   384→- Do NOT use `FETCH` in queries if you need the raw RecordId reference. `FETCH` resolves references to full objects.
   385→- For `TYPE RELATION` tables, do NOT write edges with `CREATE`. `CREATE` produces non-relation records and will fail relation constraints. Use `RELATE` (or SDK `relate(...)`) to create actual relation edges.
   386→- For nested arrays (2D grids), use explicit type: `DEFINE FIELD grid ON match TYPE array<array<string>>;` - plain `array` silently rejects nested arrays in SCHEMAFULL mode.
   387→- Keep all Surreal tables in `schema/surreal-schema.surql` as `SCHEMAFULL`. Do NOT introduce `SCHEMALESS` tables.
   388→- In `SCHEMAFULL`, every persisted nested key must be explicitly declared. For `array<object>` fields, always define `field[*].subField` entries for all written properties.
   389→- Do NOT rely on permissive object inference for production payloads. If code writes a new key, update schema in the same change before deploy.
   390→- After schema changes, verify with `INFO FOR TABLE <table>;` in the target namespace/database to confirm nested fields are present.

   454→### Key SurrealQL graph syntax:
   455→```sql
   456→-- Create edge
   457→RELATE person:marcus->owns->project:brain;
   458→
   459→-- Traverse forward
   460→SELECT ->owns->project FROM person:marcus;
   461→
   462→-- Traverse backward
   463→SELECT <-owns<-person FROM project:brain;
   464→
   465→-- Multi-hop
   466→SELECT ->has_feature->feature->has_task->task FROM project:brain;
   467→
   468→-- Bidirectional
   469→SELECT <->conflicts_with<->decision FROM decision:d1;
   470→
   471→-- Edge with metadata
   472→RELATE decision:d1->conflicts_with->decision:d2
   473→  SET severity = 'hard', description = 'Contradictory deadlines';
   474→
   475→-- Recursive traversal (org tree, dependency chains)
   476→record:root.{..}.{ id, ->depends_on->task.@ };
   477→
   478→-- TYPE RELATION enforces edge-only tables
   479→DEFINE TABLE owns TYPE RELATION IN person OUT project | feature | task;
   480→```

   567→-- Find all decisions in projects that share dependencies

### IAM: Unified Auth Layer > Core Concepts > Two Agent Auth Patterns
### Two Agent Auth Patterns

**Platform-managed agents** — agents the platform spawns and controls (Architect, Observer, PM). First-class actors with their own identity. Act on behalf of the *workspace*, not a specific person.

**User-local agents** — Claude Code, Cursor, Aider on your laptop. Authenticate as *you* with restricted scope. The agent is an extension of you, not an autonomous actor.

## AGPL-3.0

**What it does:** True open source. Anyone can use, modify, distribute. The one catch: if you run a modified version as a network service, you must share your source code.

**Good for Brain because:**
- Your entire positioning is "open source" — the README, landing page, and pitch all say it. AGPL lets you say that honestly. BSL does not. The OSI does not recognize BSL as open source, and the community will call you out on it (see: HashiCorp, Elastic, Redis backlash).
- The network copyleft is precisely right for a server-side platform. It stops "AWS Brain" from happening without restricting self-hosted users. Companies running Brain internally for their own agents never trigger the copyleft — it only triggers when you serve it to *third parties* over a network.
- At this stage, nobody caring is a bigger risk than someone stealing. AGPL maximizes adoption and contribution willingness.

If you later want a hosted commercial offering, you'd need a Contributor License Agreement (CLA) to dual-license — easier to introduce early than retrofit.

## BSL-1.1

**What it does:** Source available, not open source. Nobody can use it commercially until the change date (typically 4 years), when it auto-converts to Apache 2.0 or similar. Used by SurrealDB, HashiCorp, CockroachDB, Sentry.

**Good for Brain if:** you're building a company first and a community second. It gives you maximum commercial protection and keeps the door open for a hosted offering, enterprise tier, etc.

**Bad for Brain because:**
- You'd need to rewrite your positioning. "Full source access — every line" is fine, but "Open Source" and "Community-driven" become lies. The term is "source available."
- Contributions drop significantly. Developers are reluctant to contribute to BSL projects where their work enriches a company they can't compete with.
- The threat it protects against (a competitor hosting Brain) doesn't exist yet and won't for a long time. You're pre-users.

## My recommendation: AGPL-3.0

The reasoning is simple:

1. **Identity match.** Your project already says "open source" everywhere. Shipping BSL would require a messaging rewrite and invite the exact controversy that poisoned HashiCorp's community goodwill.

2. **Stage match.** You need adoption, not protection. Nobody is going to steal Brain and host it tomorrow. But someone might star it, try it, and contribute a fix — and they're more likely to do that under AGPL than BSL.

3. **Protection match.** AGPL's network copyleft is the exact defense you need for a server-side platform. Self-hosted users (your target audience) are unaffected. Only someone offering Brain-as-a-service to others must share modifications.

4. **Escape hatch.** If you later want a commercial tier, add a CLA from the start and you retain the ability to dual-license (AGPL for community, commercial license for enterprise). MongoDB, GitLab, and Grafana all use this model successfully.

The one thing I'd do on day one: add a simple CLA (even a DCO — Developer Certificate of Origin — via `Signed-off-by` in commits). It's much easier to require this before you have contributors than after.

how do we enforce DCO Sign-Off in github

> AGENT

The standard approach is the **DCO GitHub App** — used by CNCF, Linux Foundation, and most projects that require sign-off.

**Setup (2 minutes):**

1. Install the [DCO App](https://github.com/apps/dco) on your repo — it's a free GitHub App by probot
2. It automatically runs as a status check on every PR, verifying each commit has `Signed-off-by`
3. Add it as a required status check in **Settings > Branches > Branch protection rules** for `main`:
   - Check "Require status checks to pass before merging"
   - Search for and select `DCO`

That's it. PRs with unsigned commits get a failing check with instructions on how to fix (either `git commit --amend -s` or `git rebase --signoff`).

The app is smart enough to handle squash merges and allows a "remediation commit" where a contributor can add sign-off retroactively in a comment if they can't rewrite history on a fork.

Committed. To your follow-up about **signed commits on GitHub**:

GitHub supports two levels:

1. **Vigilant mode** (Settings > SSH and GPG keys > "Flag unsigned commits as unverified") — shows a warning badge on unsigned commits but doesn't block them.

2. **Require signed commits** (branch protection rule) — under Settings > Branches > protection rule for `main`, check "Require signed commits". This rejects any push with unsigned commits.

For enforcement, you'd combine:
- **DCO App** — checks for `Signed-off-by` (legal agreement)
- **Require signed commits** branch protection — checks for GPG/SSH signature (identity verification)

They're orthogonal: DCO proves you *agreed* to the CLA, GPG proves you *are who you say you are*. Most projects enforce DCO. Requiring GPG signatures is stricter — it can create friction for new contributors who haven't set up signing. Up to you whether you want both.
