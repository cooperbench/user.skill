## Brain Skills × Sandbox Agent: How They Fit Together

**Core finding**: The two systems have complementary skill models that integrate cleanly through a **hybrid strategy**.

### The Two Models

- **Brain Skills** (#177): Graph-native, governed, workspace-scoped. Stored in SurrealDB with `possesses` (assignment), `skill_requires` (tool binding), `governs_skill` (policy). Activated via BM25 trigger matching.
- **Sandbox Agent Skills**: File-based `SKILL.md` bundles following the [Agent Skills spec](https://agentskills.io/specification). Configured via `setSkillsConfig()` with sources (local/github/git). Discovered natively by the agent runtime.

### Recommended Integration: Hybrid (Strategy C)

**Before session creation:**
1. Resolve agent's active skills from the graph (`possesses` edges + `status = "active"`)
2. **Materialize** each skill as a `SKILL.md` file (frontmatter from graph fields, body from `content`)
3. Call `setSkillsConfig(worktreePath, "brain-skills", { sources: [...local paths] })`
4. Call `setMcpConfig(worktreePath, "brain", ...)` (existing)

**At runtime:**
- The sandbox agent discovers and activates skills **natively** via its own heuristics (description matching)
- When the agent calls `tools/list` on Brain's MCP endpoint, Brain returns **only tools authorized by direct grants + skill-derived grants** (`can_use ∪ skill_requires`)
- Tool calls go through Brain's intent authorization + `governs_skill` policy checks

This gives you: native Agent Skills compatibility (works with Claude Code, Codex, Cursor, etc.), Brain-controlled tool gating, and policy governance — without Brain needing to control which skills the agent activates.

### What Needs Building

1. **Adapter extension**: Add `setSkillsConfig`/`deleteSkillsConfig` to `SandboxAgentAdapter` (the SDK already supports it)
2. **Skill materializer**: Generate `SKILL.md` from Brain skill records (map `skill_requires` → `allowed-tools` frontmatter)
3. **Session lifecycle hook**: Insert materialization + registration between worktree creation and `createSession`
4. **MCP tool filtering**: Extend `tools/list` to include skill-derived tool grants

Full research document: `docs/research/skills-sandbox-agent-integration.md`

### 4 Key Decisions

| # | Question | Recommendation |
|---|----------|---------------|
| D1 | Who controls activation? | Agent-native (SKILL.md) for discovery, Brain MCP for enforcement |
| D2 | SKILL.md files vs MCP context? | Default to SKILL.md; MCP context only for skills needing live graph data |
| D3 | Generate `allowed-tools`? | Yes, as hint from `skill_requires`, but enforce via MCP `tools/list` regardless |
| D4 | Script support? | Defer to follow-up — instruction-only skills cover 90% of cases |

Here's the answer:

## How Claude Code Loads Skills: It's 100% LLM-Driven

**No client-side semantic search. No BM25. No trigger matching.** The LLM decides everything.

### The Flow

1. **Session start**: Claude Code scans skill directories and builds a **catalog** of just `name` + `description` (~50-100 tokens per skill). This catalog is injected into the system prompt or embedded in the `Skill` tool's description.

2. **LLM decides**: When a user message arrives, the LLM reads the catalog and judges whether any skill is relevant. The `description` field is the **only activation signal**.

3. **LLM loads**: The LLM calls `Skill(name)` (a dedicated tool) or `Read(SKILL.md path)` to load the full instructions into context.

4. **Resources on demand**: Referenced scripts/files are loaded individually if the instructions mention them.

From the [official client implementation guide](https://agentskills.io/client-implementation/adding-skills-support):

> "Most implementations rely on the model's own judgment as the activation mechanism, rather than implementing harness-side trigger matching or keyword detection."

### What This Means for Brain Issue #177

- **Brain's BM25 triggers are orthogonal** — they don't affect the sandbox agent's skill activation. BM25 is only useful for Brain's own MCP context injection path (when Brain decides which skills to include in the MCP response).
- **The `description` field is everything** — when materializing Brain skills as SKILL.md files for sandbox agents, the description must be written for LLM comprehension ("Use when X, Y, Z"), not for keyword matching.
- **Governance happens at tool-call time**, not skill-activation time. Brain can't gate which skills the sandbox agent activates, but it controls which MCP tools are available and enforces policy at call time.
- **Description budget**: Claude Code allocates 2% of context window for skill descriptions. Too many skills = some excluded.

Updated the research document at `docs/research/skills-sandbox-agent-integration.md` with a new Section 0 covering all of this with citations.

The real question is: **SurrealDB `file` type vs `string` content field for the skill table?**

For markdown-only skills (phase 1), a `string` field is simpler and queryable — you can `SELECT content FROM skill WHERE ...` and get text back directly. The `file` type adds value when you have binary assets (images, compiled scripts), content-addressed deduplication, or large payloads.

**Where SurrealDB files would actually help**: if skills grow to include companion scripts or reference assets (the phase 2 from Section 8 of the doc). Then a `file` type for the skill body + attached asset files makes the round-trip cleaner — `skill.content` is the rendered SKILL.md, `skill.assets` are the companion files, both stored natively.

**My recommendation**: start with `content: string` for the markdown body. If/when scripts and binary assets land, evaluate SurrealDB's file support for those. The text field is the simplest thing that works for instruction-only skills, and you're already extracting description/metadata into typed fields anyway.

> AGENT

Now I get it. This changes things significantly.

**With SurrealDB files, the flow becomes:**

```
Import from skills.sh / GitHub
  → download SKILL.md raw bytes
  → store as-is: f"skills:/workspace-id/skill-name/SKILL.md".put(rawContent)
  → extract metadata into skill table fields (name, description, version)

Session setup
  → query skill files for agent's active skills
  → f"skills:/workspace-id/skill-name/SKILL.md".get()
  → write to sandbox agent filesystem via SDK
```

No parse-reserialize round-trip. The original SKILL.md is preserved byte-for-byte — frontmatter, formatting, everything. Brain just stores it and serves it back. The `skill` table holds extracted metadata for querying/governance, and the bucket holds the actual file.

This is cleaner than the `content: string` approach because:

1. **No lossy round-trip** — imported skills aren't parsed into fields then regenerated. The original file is the artifact.
2. **Companion files work naturally** — scripts, references, assets all go in the same bucket path: `f"skills:/ws/skill-name/scripts/extract.py"`
3. **Brain-authored skills** — when created through the UI/API, Brain generates the SKILL.md and stores it in the bucket. The metadata fields are the source of truth, the file is generated from them.
4. **Version chain** — new version = new file in the bucket, old version stays until pruned

The schema simplifies too. Instead of `content: string` holding the markdown body, you have a bucket reference and extracted metadata:

```sql
DEFINE BUCKET skills BACKEND "file:/data/skills";

DEFINE TABLE skill SCHEMAFULL;
DEFINE FIELD name        ON skill TYPE string;
DEFINE FIELD description ON skill TYPE string;
DEFINE FIELD version     ON skill TYPE string;
DEFINE FIELD status      ON skill TYPE string;
DEFINE FIELD workspace   ON skill TYPE record<workspace>;
DEFINE FIELD file_key    ON skill TYPE string;  -- "skills:/ws-id/skill-name/SKILL.md"
-- no content field — the file IS the content
```

> AGENT

Good challenge. Let me think through this clearly.

**Option A: Store files in SurrealDB bucket**
- Brain downloads SKILL.md → stores in bucket → extracts metadata → materializes to sandbox agent at session time

**Option B: Store source references only**
- Brain stores `{ type: "github", source: "owner/repo", ref: "v1.2", subpath: "skills/code-review" }` → extracts metadata on import → passes source config directly to `setSkillsConfig` at session time

| Concern | A: Bucket storage | B: Source references |
|---------|-------------------|---------------------|
| **Materialization** | Brain reads from bucket, writes to filesystem, registers as `local` | Brain passes source directly to `setSkillsConfig` — sandbox agent downloads it |
| **Offline/air-gapped** | Works — files are local to Brain's DB | Fails if GitHub/git is unreachable at session time |
| **Version pinning** | Snapshot at import time — immune to upstream changes | `ref` pins a tag/commit, but repo could be deleted |
| **Brain-authored skills** | Natural — generate SKILL.md, store in bucket | Needs a secondary path — where does Brain-authored content live? |
| **Skill editing via UI** | Read from bucket, edit, write back | Can't edit upstream files — need a fork or a local override path |
| **Companion files** | Stored alongside, materialized together | Handled by sandbox agent's native resolution |
| **Complexity** | Brain owns the full file lifecycle (download, store, serve, version) | Brain is a metadata layer; file lifecycle delegated to sandbox agent |
| **Storage cost** | SurrealDB stores every skill file (small — SKILL.md <5KB typically) | Near zero — just source pointers |
| **Update propagation** | Manual re-import to get upstream changes | Change the `ref` and sandbox agent fetches the new version |
| **Latency at session start** | Bucket read + filesystem write | Sandbox agent fetches from GitHub (network-dependent) |
| **SurrealDB bucket maturity** | v3.0 feature, `--allow-experimental files` flag required | No new SurrealDB features needed |

**The real question is: does Brain need to own the file, or just point to it?**

For **imported skills** (skills.sh, GitHub), option B is strictly simpler. The sandbox agent already knows how to fetch from GitHub/git. Brain is just passing through a config object. No download, no bucket, no materialization code.

For **Brain-authored skills** (created via UI/API), you need *somewhere* to store the generated SKILL.md. Options:
- A git repo Brain pushes to (workspace skill repo)
- The `content` string field on the skill table (back to the original design, but only for Brain-authored)
- A bucket (option A, but only for Brain-authored)

A hybrid could work: imported skills use source references, Brain-authored skills use a `content` field or a workspace git repo. But that's two code paths.

**My take**: Option B is the right default. The experimental bucket flag is a red flag for production. The sandbox agent already handles file resolution. Brain's value-add is governance and metadata, not file hosting. For Brain-authored skills, you'll need to solve the storage question separately — but that's a smaller problem than owning the full file lifecycle for all skills.
