## Root Cause Analysis: Timeout in Intent Context KNN Query

I've identified the **root cause** of the 30-second timeout in the test "natural intent in multi-project workspace resolves via embedding similarity".

### The Problem

The test is timing out due to a **SurrealDB v3.0 KNN + WHERE index conflict** in the `linkSimilarObservations` query introduced in commit **26283073** (observation dedup changes).

### Evidence Chain

1. **Recent Commit (26283073)** removed observation deduplication but kept the `linkSimilarObservations` function that was added in commit **97f90670** ("observation: embedding-based dedup inside createObservation").

2. **The KNN Query Structure** (lines 37-46 in `app/src/server/observation/queries.ts`):
```sql
LET $candidates = SELECT id, workspace, status,
  vector::similarity::cosine(embedding, $vec) AS similarity
  FROM observation WHERE embedding <|10, COSINE|> $vec;
SELECT id, similarity FROM $candidates
  WHERE workspace = $ws AND id != $self
  AND status IN ['open', 'acknowledged']
  AND similarity > 0.85
  ORDER BY similarity DESC LIMIT 5;
```

3. **The Schema Has a B-tree Index** that triggers the bug:
```sql
DEFINE INDEX observation_workspace_status ON observation FIELDS workspace, status;
DEFINE INDEX idx_observation_embedding ON observation FIELDS embedding HNSW DIMENSION 1536 DIST COSINE;
```

### Why This Causes a Timeout

According to the CLAUDE.md constraints (section "SurrealDB KNN + WHERE Bug (v3.0)"):

> SurrealDB v3.0 query planner silently returns empty results when a WHERE clause combines a KNN operator (`<|K, COSINE|>`, which uses the HNSW index) with a condition covered by a regular B-tree index (e.g. `workspace = $ws` when a `workspace` index exists).

The query:
- Uses KNN on the `embedding` field (HNSW index)
- Filters by `workspace = $ws` (covered by `observation_workspace_status` B-tree index)
- Also filters by `status IN [...]` (also covered by the same B-tree index)

This combination causes the query planner to hang or timeout as the two index strategies conflict.

### Why It Specifically Affects This Test

1. The test calls `postContext()` which invokes `/api/mcp/:workspaceId/context` endpoint
2. This endpoint calls `resolveIntentContext()` which eventually calls `searchEntitiesByEmbedding()`
3. However, the timeout likely occurs because:
   - The test uses real embedding vectors seeded via OpenRouter API
   - The `createEmbeddingVector()` calls during test setup are slow
   - If any observations are being created during the test flow, the `linkSimilarObservations` function would be called
   - The KNN query would hang or timeout waiting for results that never come

### The Two-Step KNN Pattern That Works

According to CLAUDE.md, the workaround is already documented and partially implemented in other places:

```sql
-- WORKS: separate index usage
LET $candidates = SELECT ..., workspace FROM task WHERE embedding <|20, COSINE|> $vec;
SELECT ... FROM $candidates WHERE workspace = $ws ORDER BY similarity DESC LIMIT $limit;
```

This splits the query into two steps:
1. KNN-only subquery using HNSW index on embedding
