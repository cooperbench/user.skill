ARGUMENTS: how does composio and litellm gateways deal with mcp auth and mcp servers ?

> AGENT

Research document written to `docs/research/mcp-gateway-auth-composio-litellm.md`.

**Key findings:**

- **Composio** = tool-as-a-service. It **is** the MCP server, wrapping 1000+ APIs behind session-scoped endpoints. Auth is fully managed via Connect Links (inline OAuth prompts) and per-user credential storage. Solves context window bloat with a **meta-tool pattern** (6 discovery/execute tools instead of exposing all schemas).

- **LiteLLM** = MCP gateway/proxy. It **aggregates external MCP servers** behind a single endpoint. Supports OAuth2 PKCE (interactive) + M2M (client_credentials) for upstream auth, plus API key-based permission management scoped by Key/Team/Org. Tool namespacing prevents collisions across servers.

- **Relevance to Brain's Tool Registry**: Brain sits between both models — it aggregates external MCP servers (like LiteLLM) but needs per-user credential management (like Composio). LiteLLM's PKCE proxy pattern maps directly to the OAuth2 callback architecture in ADR-070. Composio's meta-tool pattern could inform how Brain avoids context window explosion when exposing discovered tools to agents.

> DEVELOPER

but ho wdoes litellm actually proxy to upstream mcp servers? does it keep persistent connections?

> AGENT

**Answer: LiteLLM does NOT keep persistent connections to upstream MCP servers.**

Every operation (`list_tools`, `call_tool`) follows a **connect → initialize → operate → disconnect** cycle:

1. A fresh `MCPClient` is created per call
2. Transport context manager opens (SSE/HTTP/stdio)
3. `ClientSession` created + MCP `initialize` handshake runs
4. Single operation executes
5. Session and transport tear down

**Nothing is cached except auth tokens** — OAuth2 M2M tokens get in-memory caching with TTL, and BYOK credentials are cached 60s to avoid DB hits. But tool definitions are fetched fresh every time — `list_tools` fans out to all upstream servers in parallel with `asyncio.gather`, each creating ephemeral connections.

The `MCPServerManager.registry` is a **configuration registry** (URL, transport type, auth config, access groups), not a connection pool. `MCPClient` itself is stateless — it stores only config, holds no sockets.

This is a simpler but higher-latency design. Every tool call pays the full transport + handshake cost. For Brain's tool registry, this is worth noting — if we proxy MCP calls, we'd want to consider whether session reuse or tool caching would be worth the complexity. Updated the research doc at `docs/research/mcp-gateway-auth-composio-litellm.md` with the full source analysis.

> DEVELOPER

that sounds slow... would it make sense to keep mcp client instances cached?

> AGENT

Good. Now I have the full picture. Here's the answer:

---

**Short answer: Yes, but the right unit to cache is the `ClientSession` (transport + session), not just `MCPClient`.**

Here's why LiteLLM's approach is wasteful and what the alternatives look like:

### What happens per-call today (LiteLLM)

Every `call_tool` or `list_tools`:
1. Opens TCP/TLS connection (HTTP) or spawns subprocess (stdio)
2. MCP `initialize` handshake (capabilities negotiation)
3. Single operation
4. Tears down session + transport

For Streamable HTTP, the MCP SDK actually **supports session reuse** — the server returns a `mcp-session-id` header on initialize, and subsequent requests include it. The transport is designed for multiple operations within the same context manager scope. LiteLLM just doesn't use it that way.

### Would caching help?

| Transport | Cacheable? | Benefit | Complexity |
|-----------|-----------|---------|------------|
| **Streamable HTTP** | Yes — stateless HTTP with session ID header | Saves handshake, not TCP (httpx can pool connections anyway) | Low |
| **SSE** | Yes — long-lived EventSource connection | Saves handshake + connection setup | Medium (reconnection handling) |
| **stdio** | Yes — keep subprocess alive | Huge — avoids `npx` cold starts (often 2-5s) | Medium (process health monitoring) |

### The real question for Brain

Brain's architecture is different from LiteLLM's in a key way: **Brain is workspace-scoped, not request-scoped**. A workspace admin connects an MCP server once, and then multiple agents use it over hours/days. This makes persistent sessions much more valuable than for LiteLLM (which is a shared multi-tenant proxy).

But there are traps:

1. **Auth token rotation** — If the OAuth token used to establish the session expires, you need to reconnect with a fresh token. A cached session with a stale token will start failing silently.

2. **Server restarts** — Upstream MCP servers restart, and your cached session is dead. You need health-check + reconnect logic.

3. **Memory pressure** — Each SSE transport holds an open EventSource. If a workspace has 10 MCP servers, that's 10 persistent connections per workspace. Multiply by workspaces.

4. **stdio process leaks** — Cached subprocess connections can zombie if not monitored.

### What I'd recommend for Brain

**Don't cache raw connections. Cache at the session level with lazy connect + auto-reconnect:**

```
MCPServerConnection {
  config: MCPServerConfig          // URL, transport, auth
  session: ClientSession | null    // Lazy — created on first call
  sessionId: string | null         // For Streamable HTTP resumption
  lastUsed: timestamp              // For idle eviction
  
  async ensureConnected(): ClientSession  // Connect if null, reconnect if dead
  async disconnect(): void                // Clean teardown (DELETE for HTTP)
}
```

Scope it to workspace — one `MCPServerConnection` per `(workspace, mcp_server)` pair. Evict after idle timeout (e.g., 5 minutes). This gives you:
- First call: full connect + handshake (~same as LiteLLM)
- Subsequent calls: reuse session (skip handshake)
- Idle cleanup: no leaked connections
- Failure recovery: `ensureConnected` detects dead sessions and reconnects

This is significantly simpler than what LiteLLM does (they pay full cost every time) while avoiding the complexity of a full connection pool. The MCP protocol's session model was designed for exactly this — `mcp-session-id` exists so clients can maintain stateful sessions across multiple tool calls.

do mcp servers only support oauth 2.1 ?

> AGENT

No. The MCP spec is clear on this — **authorization is entirely OPTIONAL**, and even when implemented, OAuth 2.1 is the specified mechanism but not the only way servers authenticate in practice.

From the spec (2025-03-26):

**What the spec says:**
- Authorization is **OPTIONAL** for MCP implementations
- HTTP transports **SHOULD** conform to the OAuth 2.1 spec (not MUST)
- stdio transports **SHOULD NOT** use OAuth — they "retrieve credentials from the environment" (env vars, config files)
- When OAuth is used, **PKCE is REQUIRED** for all clients

**OAuth grant types (when used):**
- **Authorization Code** — human end-user acting through an agent (e.g., agent calls a tool backed by a user's GitHub account)
- **Client Credentials** — machine-to-machine (e.g., backend service accessing an MCP tool server)
- **Device Code** — mentioned in the TOC but for constrained devices

**What happens in the real world:**

Most MCP servers today don't implement OAuth at all. They use one of:

| Method | Example | How |
|--------|---------|-----|
| **No auth** | Local stdio servers (filesystem, git) | Trust the local process |
| **API key in env** | CircleCI MCP, many stdio servers | `CIRCLECI_TOKEN` in env |
| **Static Bearer token** | Zapier MCP (`/mcp/sk-xxx/sse`) | Token baked into URL |
| **Static headers** | Custom internal servers | `Authorization: Bearer ...` passed per-config |
| **Full OAuth 2.1** | GitHub Copilot MCP, enterprise servers | Spec-compliant PKCE flow |

LiteLLM handles this pragmatically — it supports OAuth2 (PKCE + M2M), static headers, API keys, and even AWS SigV4 for Bedrock. Composio sidesteps it entirely by being the server and managing all upstream auth itself.

**For Brain's tool registry**, this means you need to support at minimum:
1. **No auth** (local/trusted servers)
2. **Static token/API key** (the vast majority of real MCP servers today)
3. **OAuth 2.1** (the spec-compliant path, growing adoption)

The current `mcp_provider` + `mcp_account` model in the schema already handles this well — the provider defines the auth method, the account stores the credential. The question is just whether to also implement the full OAuth 2.1 discovery flow (`.well-known/oauth-authorization-server`, dynamic client registration) or handle it as manual config for now.

is Composio's approach better ? they connect directly to upstream api's instead of using mcp

> AGENT

Depends what you're optimizing for. They're solving different problems.

**Composio's model: "We ARE the MCP server"**

They wrap raw APIs (GitHub REST, Gmail API, Slack API) into MCP-compatible tool definitions. The MCP protocol is only used on the client-facing side. Upstream, it's direct HTTP calls to vendor APIs.

Advantages:
- **No MCP server dependency** — They don't need GitHub to run an MCP server. They just call `api.github.com` directly.
- **Consistent auth** — One auth model (Composio-managed OAuth) for everything, regardless of how the upstream API authenticates
- **Schema quality control** — They curate tool schemas, parameter descriptions, error handling. No dependency on upstream MCP server quality.
- **No double-proxy** — Agent → Composio → API (2 hops). Agent → Brain → MCP Server → API would be 3 hops.

Disadvantages:
- **Maintenance burden** — They have to build and maintain 1000+ API wrappers. Every API change requires an update on their side.
- **Vendor lock-in** — You're locked into Composio's tool definitions, naming, and schema choices
- **Can't use MCP-native servers** — If GitHub ships a first-party MCP server with better tools than Composio's wrapper, you can't use it
- **Lag** — New API features are only available when Composio adds them
- **SaaS dependency** — Everything routes through their cloud

**Brain's model: "We aggregate MCP servers"**

You connect to actual MCP servers that exist in the ecosystem. The value is in multi-tenancy, governance, and credential management — not in reimplementing APIs.

Advantages:
- **Ecosystem leverage** — When GitHub ships an MCP server, you just connect it. Zero wrapper code.
- **First-party quality** — The vendor knows their own API best. Their MCP server will have better edge case handling than any wrapper.
- **No maintenance** — API changes are handled by the server maintainer, not you
- **Self-hosted** — No SaaS dependency

Disadvantages:
- **MCP server quality varies wildly** — Some have great schemas, some are garbage
- **Auth fragmentation** — Every server has its own auth story (OAuth, API key, none, etc.)
- **Extra hop** — Agent → Brain → MCP Server → API
- **Ecosystem dependency** — If a service doesn't have an MCP server, you can't use it

**The honest answer for Brain:**

Composio's approach is better *for breadth* — covering 1000 integrations fast. But it's a different business. They're an integration platform. Brain is an agent coordination platform.

The real question is: **do Brain's users need 1000 integrations, or do they need 5-10 connected well?** If it's the latter (which it is — workspace admins connecting their specific tools), the MCP gateway model is better because:

1. You don't maintain API wrappers
2. You ride the MCP ecosystem — every new MCP server is instantly usable
3. Your value is governance/auth/discovery, not API translation
4. First-party MCP servers (GitHub, Stripe, etc.) are getting good fast

The worst position would be trying to do both — wrapping APIs AND proxying MCP servers. That's two systems to maintain. Pick the gateway model and let Composio (or similar) be one of the MCP servers you can connect to if someone wants their breadth.
