> AGENT

It's a deliberate design choice driven by what observations *are* — cross-cutting signals, not domain entities. **Domain entities** (tasks, decisions, features) belong to a project/feature hierarchy. Their workspace membership is *derived* by traversing graph edges: `entity →belongs_to→ project →has_project→ workspace`. This makes sense because a task genuinely "belongs to" a feature within a project. **Observations** don't fit that hierarchy. They're lightweight agent-to-agent communication signals (conflict warnings, risk flags, info notices) that: 1. **Can be free-floating** — an observation might not relate to any specific entity (the `observes` edge is optional) 2. **Cross project boundaries** — a conflict observation might reference entities in different projects, so scoping it via one project's graph path would be wrong 3. **Need O(1) lookup** — agents load all open workspace observations on every invocation (`WHERE workspace = $workspace AND status IN ['open', 'acknowledged']`). Graph traversal would be unnecessarily expensive for something queried this frequently The tradeoff is visible in `entity-actions-route.ts` — observations can't use `isEntityInWorkspace()` (which traverses `belongs_to` → `has_project` edges), so they bypass that check and do their own inline scope validation by comparing the observation's `workspace` field directly: ```typescript // observation/queries.ts — scope check inside acknowledge/resolve if ((row.workspace.id as string) !== (input.workspaceRecord.id as string)) { throw new Error("observation is outside the current workspace scope"); } ``` In short: observations are *workspace-scoped signals*, not *project-owned entities*, so a direct field is the correct modeling choice.
