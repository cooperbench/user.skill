   299→## SurrealDB KNN + WHERE Bug (v3.0)
   300→
   301→- SurrealDB v3.0 query planner silently returns empty results when a WHERE clause combines a KNN operator (`<|K, COSINE|>`, which uses the HNSW index) with a condition covered by a regular B-tree index (e.g. `workspace = $ws` when a `workspace` index exists).
   302→- Tables WITHOUT a B-tree index on the filtered field work fine with KNN + WHERE in the same clause.
   303→- Workaround: split into two steps — KNN in a `LET` subquery (HNSW index only), then filter by workspace in a second query (B-tree index only):
   304→  ```sql
   305→  -- BROKEN: both indexes conflict
   306→  SELECT ... FROM task WHERE workspace = $ws AND embedding <|20, COSINE|> $vec;
   307→
   308→  -- WORKS: separate index usage
   309→  LET $candidates = SELECT ..., workspace FROM task WHERE embedding <|20, COSINE|> $vec;
   310→  SELECT ... FROM $candidates WHERE workspace = $ws ORDER BY similarity DESC LIMIT $limit;
   311→  ```
   312→- Apply this pattern to ALL KNN queries on tables that have a regular index on the filtered field.

   314→## SurrealDB Full-Text Search (BM25)
   315→
   316→Reference: https://surrealdb.com/docs/surrealql/functions/database/search
   317→
   318→The UI entity search uses SurrealDB's built-in BM25 full-text search, not vector/KNN search. Vector search is reserved for the chat agent's `search_entities` tool where semantic similarity matters.
   319→
   320→### Setup
   321→
   322→Full-text search requires an analyzer and `FULLTEXT` indexes:
   323→```sql
   324→-- Analyzer with stemming (English snowball) and lowercase normalization
   325→DEFINE ANALYZER entity_search
   326→  TOKENIZERS blank, class, camel, punct
   327→  FILTERS snowball(english), lowercase;
   328→
   329→-- Per-field fulltext index (one index per field, not per table)
   330→DEFINE INDEX idx_task_fulltext ON task FIELDS title FULLTEXT ANALYZER entity_search BM25;
   331→```
   332→
   333→### Query syntax
   334→
   335→- Use the `@N@` match operator (N is a predicate reference number for `search::score`):
   336→  ```sql
   337→  SELECT id, title, search::score(1) AS score
   338→  FROM task
   339→  WHERE title @1@ $query
   340→  ORDER BY score DESC LIMIT 10;
   341→  ```
   342→- `search::score(N)` returns the BM25 relevance score for predicate N.
   343→- `search::highlight('<b>', '</b>', N)` returns text with matching tokens wrapped in tags.
   344→### Known limitations (SurrealDB v3.0)
   345→
   346→- `search::score()` and `@N@` do NOT work inside `DEFINE FUNCTION` — the predicate reference is lost across the function boundary. Search queries must run from the app layer. See: https://github.com/surrealdb/surrealdb/issues/7013
   347→- `@N@` does NOT work with SDK bound parameters (`$query`). The search term must be embedded as a string literal in the query. Escape single quotes before interpolation.
   348→- `BM25` without explicit parameters returns score=0. Always use `BM25(1.2, 0.75)`.
   349→
   350→### Entity search implementation
   351→
   352→Search queries run from the app layer (`entity-search-route.ts`) instead of SurrealDB stored functions due to the limitations above. Fulltext indexes are defined in `schema/migrations/0002_fulltext_search_indexes.surql`.

   358→- Do NOT use `.tb` on `RecordId` — it works at runtime but is not in the SDK type definition and may break on upgrade. Use `.table.name` instead (returns the same typed `Tb` string via the public API).
   359→- When using `http://` or `https://` URLs, the SDK uses HTTP transport only. It does NOT attempt WebSocket upgrade.
   360→- WebSocket is only used when the URL scheme is `ws://` or `wss://`.
   361→- To CREATE a record with a specific ID, use the SDK's `RecordId` class:
   362→  ```typescript
   363→  import { RecordId } from "surrealdb";
   364→  const record = new RecordId("table", "my-id");
   365→  await query("CREATE $record CONTENT $content;", { record, content: {...} });
   366→  ```
   367→- To SELECT a specific record by ID, use `RecordId` in the FROM clause:
   368→  ```typescript
   369→  const record = new RecordId("gladiator", id);
   370→  await query("SELECT * FROM $record;", { record });
   371→  ```
   372→- Do NOT use string-based record IDs like `table:id` in queries - use `RecordId` objects.
   373→- For optional record fields (e.g. `option<record<match>>`), omit the field instead of setting `null` - SurrealDB defaults to `NONE`.
   374→- Query results return `RecordId` objects for record references - cast directly, no string conversion needed.
   375→- Clause order: `SELECT ... FROM ... WHERE ... LIMIT ... FETCH ...` - `LIMIT` must come before `FETCH`.
   376→- **ORDER BY fields MUST be in the SELECT projection.** SurrealDB v3.0 raises a hard parse error (`Missing order idiom ... in statement selection`) when an ORDER BY field is not selected. This fails at query time, not at schema time, so it often hides until the query is actually executed. Always include every `ORDER BY` field in the `SELECT` projection. Example: `SELECT id, summary, created_at FROM decision ORDER BY created_at DESC` (not `SELECT id, summary ... ORDER BY created_at`).
   377→- Known issue: Surreal can throw `Expected a single result output when using the ONLY keyword` when a statement uses `ONLY` and returns no record output.
   378→- Workaround: force a return clause. In SDK calls that map to `ONLY` (for example `relate(...)`), use `.output("after")` so the statement returns a record.
   379→- Type query results directly. Access `RecordId.id` directly - do NOT create wrapper functions like `extractRecordId()`, `toString()`, etc:
   380→  ```typescript
   381→  const rows = await selectMany("SELECT id, name FROM gladiator WHERE totalWins > 0;") as Array<{ id: RecordId; name: string }>;
   382→  const result = rows.map((row) => ({ gladiatorId: row.id.id as string, name: row.name }));
   383→  ```
   384→- Do NOT use `FETCH` in queries if you need the raw RecordId reference. `FETCH` resolves references to full objects.
   385→- For `TYPE RELATION` tables, do NOT write edges with `CREATE`. `CREATE` produces non-relation records and will fail relation constraints. Use `RELATE` (or SDK `relate(...)`) to create actual relation edges.
   386→- For nested arrays (2D grids), use explicit type: `DEFINE FIELD grid ON match TYPE array<array<string>>;` - plain `array` silently rejects nested arrays in SCHEMAFULL mode.
   387→- Keep all Surreal tables in `schema/surreal-schema.surql` as `SCHEMAFULL`. Do NOT introduce `SCHEMALESS` tables.
   388→- In `SCHEMAFULL`, every persisted nested key must be explicitly declared. For `array<object>` fields, always define `field[*].subField` entries for all written properties.
   389→- Do NOT rely on permissive object inference for production payloads. If code writes a new key, update schema in the same change before deploy.
   390→- After schema changes, verify with `INFO FOR TABLE <table>;` in the target namespace/database to confirm nested fields are present.

   455→```sql
   456→-- Create edge
   457→RELATE person:marcus->owns->project:brain;

   494→### Key SurrealQL vector syntax:
   495→```sql
   496→-- Define embedding field + HNSW index
   497→DEFINE FIELD embedding ON conversation TYPE array<float>;
   498→DEFINE INDEX idx_conv_embedding ON conversation FIELDS embedding
   499→  HNSW DIMENSION 1536 DIST COSINE;
   500→
   501→-- KNN search (top 5 nearest neighbors)
   502→SELECT *, vector::similarity::cosine(embedding, $query_vec) AS similarity
   503→FROM conversation
   504→WHERE embedding <|5, COSINE|> $query_vec
   505→ORDER BY similarity DESC;
   506→
   507→-- Hybrid search (vector + full-text via RRF)
   508→LET $vs = SELECT id FROM conversation WHERE embedding <|5, COSINE|> $query_vec;
   509→LET $ft = SELECT id, search::score(1) AS score FROM conversation WHERE text @1@ 'decision about auth';
   510→RETURN search::rrf([$vs, $ft], 5);

   546→## Platform-Specific Patterns
   547→
   548→### Pattern: Extraction Pipeline Write
   549→After the LLM extracts entities from a message, write them to the graph in a single transaction:
   550→```sql
   551→BEGIN TRANSACTION;
   552→  -- Create entities
   553→  LET $task = CREATE task SET title = $title, status = 'open', owner = $owner;
   554→  LET $decision = CREATE decision SET summary = $summary, status = 'extracted', confidence = $conf;
   555→  
   556→  -- Create relationships
   557→  RELATE $decision->decided_in->$conversation;
   558→  RELATE $decision->belongs_to->$project;
   559→  RELATE $task->belongs_to->$feature;
   560→  RELATE $person->owns->$task;
   561→COMMIT TRANSACTION;
   562→```
   563→
   564→### Pattern: Cross-Project Conflict Detection
   565→Traverse the graph to find related entities across projects:
   566→```sql
   567→-- Find all decisions in projects that share dependencies
   568→SELECT 
   569→  id, summary, status,
   570→  <-belongs_to<-project AS projects,
   571→  ->conflicts_with->decision AS conflicts
   572→FROM decision
   573→WHERE status IN ['extracted', 'proposed', 'confirmed']
   574→  AND <-belongs_to<-project != $current_project;
   575→```
   576→
   577→### Pattern: Context Packet for MCP Server
   578→Build a token-budgeted context packet for coding agents:
   579→```sql
   580→-- Active decisions for a project
   581→SELECT summary, rationale, status, decided_at
   582→FROM decision
   583→WHERE <-belongs_to<-project = $project
   584→  AND status IN ['confirmed', 'proposed']
   585→ORDER BY decided_at DESC
   586→LIMIT 20;
   587→
   588→-- Dependency chain for current task
   589→SELECT 
   590→  id, title, status,
   591→  ->depends_on->task.{id, title, status} AS dependencies
   592→FROM task
   593→WHERE id = $current_task;
   594→```
