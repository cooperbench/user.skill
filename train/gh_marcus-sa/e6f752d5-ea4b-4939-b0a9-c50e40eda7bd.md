but if we use time based changes instead of vector search, how would an agent know of a relevant decision that was made 2 weeks ago by another agent?

> AGENT

That's the right challenge. Let me break down the actual retrieval paths for that scenario. ## How a 2-week-old decision reaches an agent today There are three distinct retrieval paths, only one of which relies on embeddings: **1. Graph traversal (already works, no embeddings)** If the decision is linked to the same project/feature the agent is working on, it's reachable via edges: ``` task:current →belongs_to→ feature:auth →belongs_to→ project:platform ↑ decision:use-trpc →belongs_to→ project:platform ──────┘ ``` This is how `get_project_status` and `buildChatContext()` already work — they load decisions for the current project regardless of age. This covers the majority of cases because decisions are linked to the project where they were made. **2. BM25 keyword match (already works, no embeddings)** If an agent searches for "API protocol" and the decision says "standardize on tRPC", BM25 with stemming catches "API" overlap. Won't catch pure semantic matches with zero keyword overlap, but those are rarer than you'd think in a domain-specific workspace. **3. Cross-project semantic discovery (the actual gap)** A decision in Project A ("use PostgreSQL for billing") is relevant to an agent in Project B designing analytics storage. No graph edge connects them. No keyword overlap. Only semantic similarity would find it. ## How big is that gap really? In practice, **small** — for two reasons specific to Brain's architecture: **Workspaces are bounded.** A workspace typically has dozens to low hundreds of confirmed decisions, not millions of documents. You could load *all* active decisions into a context budget scan without any search at all: ```sql SELECT id, summary, status, rationale FROM decision WHERE workspace = $ws AND status IN ['confirmed', 'proposed'] ORDER BY updated_at DESC; ``` At ~100 tokens per decision, 200 decisions = 20K tokens. That fits in a context budget window. No search needed — just load and let the LLM …

> DEVELOPER

so maybe the observer should be extended to also check workspace decisions and link cross project

> AGENT

Exactly. That's the architecturally correct solution for Brain — turn a runtime search problem into a background graph enrichment problem. Right now the Observer scans for contradictions. Extending it to also **link related decisions across projects** means: 1. Observer finds "use PostgreSQL for billing" (Project A) and "choosing storage for analytics" (Project B) 2. Creates a `relates_to` edge (or observation linking both) with reasoning: *"Both decisions concern data storage technology selection"* 3. Next time an agent loads context for Project B, the link is there via graph traversal **Why this is better than embeddings:** - **Auditable** — the edge carries the Observer's reasoning for *why* they're related, not just a similarity score - **Catches contradictions AND alignments** — embeddings only find similarity. The Observer can distinguish "these agree" from "these conflict" - **Proactive** — the link exists before any agent needs it, not computed at query time - **Graph gets smarter over time** — every Observer scan enriches the connectivity. Embeddings are stateless **What the scan would look like:** The Observer already loads workspace decisions. The new scan type would be something like "cross-project decision coherence" — for each unlinked decision, check if decisions in other projects within the same workspace share domain overlap. When found, create an edge with metadata (relationship type: `aligns_with`, `conflicts_with`, `supersedes`, `relates_to`). This also plays into the existing observation→suggestion→learning pipeline. A cross-project link that reveals a contradiction becomes an observation, which can become a suggestion ("consolidate these into a workspace-wide policy"), which can become a learning. That closes the semantic discovery gap while actually making the graph more valuable — which embeddings never did. They were a parallel retrieval path that bypassed the graph rather than enriching it.
