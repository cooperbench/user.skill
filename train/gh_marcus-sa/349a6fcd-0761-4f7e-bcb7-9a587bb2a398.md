### **5. Test Execution Flow**

**Extraction Eval Runtime:**

1. **Setup** (`setupEvalRuntime()`):
   - Creates isolated SurrealDB namespace/database (namespaced: `eval_<timestamp>_<random>`)
   - Applies full schema from `/schema/surreal-schema.surql`

2. **Per-Case Execution** (`runCase()`):
   - Check result cache (keyed by `${cacheVersion}:${model}:${caseId}:${caseHash}`)
   - If cached, return cached output
   - Otherwise:
     - Seed workspace: create workspace, project, owner person
     - Seed conversation: create message history if `context` provided
     - Seed workspace entities: create tasks/decisions/features from `workspace_seed`
     - Create user message with test input

     - Persist extraction output to SurrealDB
     - Query back entities, relations, evidence, tools
     - Build `ExtractionEvalOutput` object
     - Cache result

3. **Scoring** (`evalite`):
   - Run all 13 scorers against each case
   - Compute weighted average per case (intent-specific weights)
   - Generate HTML report with per-case scores and columns

4. **Teardown** (`teardownEvalRuntime()`):

**What fine-tuning would buy you:**
- Tighter kind classification (the task-vs-feature ambiguity you just hit)
- More consistent priority mapping from signal words
- Potentially cheaper/faster than Haiku if you go with something like Mistral 7B or Llama 3

**What's working against it right now:**

1. **Data volume** — You have 54 golden cases. Fine-tuning needs hundreds to low thousands of high-quality examples to outperform a well-prompted foundation model on structured extraction. You'd need to grow the eval set significantly first regardless.

2. **Schema instability** — You just added `priority` this session. Fine-tuned models are brittle to schema changes; every new field means retraining. With prompt-based extraction on Haiku, you just update the prompt and re-eval.

3. **The failures are ambiguous inputs, not model failures** — "We should add CSV export" genuinely reads as a feature. The fix was rewriting the golden case, not retraining the model. A fine-tuned model would learn your labeling conventions, but you'd need to establish those conventions across enough examples first.

4. **Structured output constraint** — You're already using Azure/OpenRouter structured output which constrains the output schema. The model can't hallucinate fields or malform the response. The remaining quality gap is semantic judgment (kind/priority classification), where few-shot examples in the prompt might close the gap cheaper.

**What I'd try before fine-tuning:**
- Add 2-3 few-shot examples to the extraction prompt showing the task-vs-feature boundary and priority signals — that's the cheapest intervention
- Grow the golden cases to ~100+ covering more edge cases
- If accuracy still plateaus after prompt improvements, *then* you have both the training data and the evidence that prompted Haiku can't close the gap

Fine-tuning is the right move eventually if extraction becomes a bottleneck at scale (cost per call, latency), but the eval infrastructure you have now is exactly the thing that tells you *when* you've hit that ceiling. Right now the prompt still has room.
