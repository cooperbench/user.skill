     2→

    11→
    12→Paperclip manages OpenClaw as an external execution environment via an adapter pattern:
    13→

    15→- **Transport**: WebSocket client implementing Gateway Protocol v3
    16→- **Auth**: Ed25519 device identity with challenge-response signing (v3 payload format: `v3|{deviceId}|{clientId}|{clientMode}|{role}|{scopes}|{signedAtMs}|{token}|{nonce}|{platform}|{deviceFamily}`)
    17→- **Session strategies**: `fixed` (single session key), `issue` (per-issue), `run` (per-run)

    20→
    21→Paperclip treats OpenClaw as a black box — it sends work in and gets results back. Brain can do better by becoming the gateway itself.

    25→## 2. Architecture Decision: Brain as Gateway vs. Brain as Client
    26→
    27→### Option A: Brain as Gateway Protocol Client (rejected)
    28→
    29→Brain connects to one or more external OpenClaw gateways as an `operator` role WebSocket client, monitors sessions, extracts decisions from chat, and proxies LLM calls.
    30→
    31→```
    32→OpenClaw Agent → OpenClaw Gateway → LLM Provider
    33→                      ↑
    34→                Brain (WS client, operator.read + operator.write)

    36→                      ├─ Proxy LLM calls
    37→                      └─ Evaluate exec approvals

    41→- Three moving parts (client + gateway + provider) instead of two
    42→- Two auth systems to bridge (Ed25519 device auth + Brain DPoP)
    43→- Context injection requires LLM proxy interception — extra hop, extra latency

    47→

    49→

    51→

    57→       ▼

    61→  ├─ agent       → orchestrator.assign + run

    69→- Two moving parts (client + Brain)

    72→- Trace recording is native — Brain runs the agent

   222→## 5. Auth Integration: OAuth 2.1, DPoP, and DCR
   223→
   224→### The Auth Problem
   225→
   226→Two directions of auth collapse into one when Brain is the gateway:
   227→
   228→| Direction | Old (Brain as client) | New (Brain as gateway) |
   229→|-----------|----------------------|----------------------|
   230→| Client → Gateway | Ed25519 device auth (OpenClaw) | Ed25519 device auth → Brain identity |
   231→| Client → Brain | DPoP-bound tokens (separate) | Same connection, same identity |
   232→
   233→### Device Auth → DPoP Identity Bridge
   234→
   235→When an OpenClaw client connects:
   236→
   237→1. Client sends `connect` frame with device public key
   238→2. Brain sends `connect.challenge` event with nonce
   239→3. Client signs nonce with Ed25519 private key
   240→4. Brain verifies signature
   241→
   242→Then:
   243→
   244→```
   245→Known device?
   246→  → Resolve existing Brain identity from device fingerprint
   247→  → Load workspace membership, authority scopes
   248→
   249→New device?
   250→  → DCR flow (RFC 7591):
   251→    POST /api/oauth/register (internal)
   252→    {
   253→      "client_name": "openclaw:device:<fingerprint>",
   254→      "grant_types": ["urn:ietf:params:oauth:grant-type:jwt-bearer"],
   255→      "scope": "mcp:read mcp:write",
   256→      "software_id": "openclaw-gateway:<device-id>",
   257→      "dpop_bound_access_tokens": true
   258→    }
   259→  → Create Brain identity linked to device
   260→  → Create workspace membership (member_of edge)
   261→  → Issue DPoP-bound token internally
   262→  → Return hello-ok with workspace context
   263→```
   264→
   265→After connect, the WebSocket connection carries the DPoP-equivalent auth for the session lifetime. Every method call inherits the connection's identity — no per-request DPoP proofs needed over WebSocket.
   266→
   267→### Key Reuse: Ed25519 → DPoP
   268→
   269→OpenClaw already has per-device Ed25519 keys. Brain can accept the same key for DPoP binding:
   270→
   271→- Device auth: Ed25519 sign challenge nonce → prove device identity
   272→- DPoP binding: Same Ed25519 key → JWK thumbprint in `cnf.jkt` claim
   273→- One key pair, two protocols
   274→
   275→### DCR: Automatic Agent Registration
   276→
   277→When Brain discovers agents via a gateway connection, it can auto-register each as an OAuth client:
   278→
   279→```json
   280→{
   281→  "client_name": "openclaw:agent:architect",
   282→  "grant_types": ["urn:ietf:params:oauth:grant-type:jwt-bearer"],
   283→  "scope": "mcp:read mcp:write",
   284→  "software_id": "openclaw-gateway:<gateway-id>",
   285→  "software_version": "3.0",
   286→  "dpop_bound_access_tokens": true
   287→}
   288→```
   289→
   290→Each agent gets a `client_id` + DPoP key pair. No manual `brain init` per agent.

   627→## 9. Skills as Graph-Native Behavioral Expertise
   628→
   629→### The Three Layers of Agent Competency
   630→
   631→Brain currently has two of three layers. Skills are the missing middle:
   632→
   633→| Layer | What | Example | Brain Status |
   634→|-------|------|---------|-------------|
   635→| **Tool** (MCP) | Functional capability — a stateless endpoint | `git push`, `search_entities`, `create_observation` | Exists (MCP server) |
   636→| **Skill** | Domain expertise — behavioral instructions for *how* to approach a class of work | "how to do a security audit", "how to triage issues", "how to deploy React" | **Missing** |
   637→| **Learning** | Correction/pattern — a single rule derived from past failure or success | "don't mock the DB in these tests", "use BM25 not embeddings for entity search" | Exists (`learning` table) |
   638→
   639→**Skills are not tools.** A tool gives the agent a hand. A skill tells the agent how to use its hands to bake a specific cake.
   640→
   641→**Skills are not learnings.** A learning is a reactive correction ("don't do X because Y happened"). A skill is proactive expertise ("here's how to approach security audits, step by step"). Learnings are small, always-on rules. Skills are rich instruction sets activated by intent.
   642→
   643→### How Skills Work in the Wild
   644→
   645→The `skills.sh` ecosystem (80k+ skills) and Claude Code's `/skills` both use the same model: a SKILL.md file with YAML frontmatter (metadata, triggers) and Markdown body (instructions). The agent loads the skill into its context when the trigger matches.
   646→
   647→```yaml
   648→---
   649→name: security-audit
   650→description: Systematic security audit of web applications
   651→triggers: ["security audit", "vulnerability scan", "OWASP", "pen test"]
   652→tools_required: ["grep", "read", "bash"]
   653→---
   654→
   655→## Approach
   656→
   657→1. Start with dependency audit (check for known CVEs)
   658→2. Review authentication flows for OWASP Top 10
   659→3. Check for injection points (SQL, XSS, command)
   660→4. Audit authorization boundaries
   661→5. Review secrets management
   662→...
   663→```
   664→
   665→NVIDIA OpenShell (March 2026) confirms this model at the infrastructure level — it treats skills as behavioral units that can be scanned, verified, and restricted independently of the tools they use.
   666→
   667→### Skills in Brain: Graph-Native, Governed, Evolving
   668→
   669→In Brain, a skill becomes a first-class graph node — discoverable, versionable, governed by policies, and evolved by the Observer.
   670→
   671→#### Schema
   672→
   673→```sql
   674→DEFINE TABLE skill SCHEMAFULL;
   675→DEFINE FIELD name ON skill TYPE string;
   676→DEFINE FIELD description ON skill TYPE string;
   677→DEFINE FIELD content ON skill TYPE string;                -- The instruction body (markdown)
   678→DEFINE FIELD triggers ON skill TYPE array<string>;         -- Intent-matching trigger phrases
   679→DEFINE FIELD version ON skill TYPE string;
   680→DEFINE FIELD status ON skill TYPE string
   681→  ASSERT $value IN ["draft", "active", "deprecated"];
   682→DEFINE FIELD target_agent_types ON skill TYPE array<string>; -- Which agent types can use this
   683→DEFINE FIELD workspace ON skill TYPE record<workspace>;
   684→DEFINE FIELD created_by ON skill TYPE option<record<identity>>;
   685→DEFINE FIELD created_at ON skill TYPE datetime;
   686→DEFINE FIELD updated_at ON skill TYPE option<datetime>;
   687→
   688→-- Which MCP tools this skill requires (not "is")
   689→DEFINE TABLE skill_requires TYPE RELATION IN skill OUT mcp_tool SCHEMAFULL;
   690→
   691→-- Which agents possess this skill
   692→DEFINE TABLE possesses TYPE RELATION IN identity OUT skill SCHEMAFULL;
   693→DEFINE FIELD granted_at ON possesses TYPE datetime;
   694→
   695→-- Skill version chain (like policy versioning)
   696→DEFINE TABLE skill_supersedes TYPE RELATION IN skill OUT skill SCHEMAFULL;
   697→
   698→-- Evidence: which sessions/traces/observations involved this skill
   699→DEFINE TABLE skill_evidence TYPE RELATION IN skill OUT agent_session | trace | observation SCHEMAFULL;
   700→DEFINE FIELD added_at ON skill_evidence TYPE datetime;
   701→
   702→DEFINE INDEX skill_workspace ON skill FIELDS workspace;
   703→DEFINE INDEX skill_status ON skill FIELDS status;
   704→```
   705→
   706→#### How Skills Differ from Learnings
   707→
   708→| Aspect | Learning | Skill |
   709→|--------|----------|-------|
   710→| **Size** | Single rule (1-3 sentences) | Full instruction set (paragraphs to pages) |
   711→| **Activation** | Always-on for target agents | Triggered by intent match |
   712→| **Origin** | Reactive — derived from failures/patterns | Proactive — authored expertise |
   713→| **Lifecycle** | `proposed → active → deactivated` | `draft → active → deprecated` (with version chain) |
   714→| **Injection** | Appended to system prompt (token-budgeted) | Injected into context when trigger matches task |
   715→| **Tool binding** | None | `skill_requires` edges to MCP tools |
   716→| **Governance** | Approval required (human confirms) | Policy-governed (which agents can possess which skills) |
   717→
   718→Both use JIT injection into agent prompts. The difference is *when* and *how much*:
   719→- Learnings: always loaded for matching agent types, token-budgeted to fit
   720→- Skills: loaded only when the incoming task/objective matches a trigger phrase
   721→
   722→#### Activation Flow
   723→
   724→```
   725→1. Task arrives: "Run a security audit on the auth module"
   726→
   727→2. Skill discovery (BM25 against skill.triggers + skill.description):
   728→   SELECT id, name, description,
   729→     search::score(0) + search::score(1) AS score
   730→   FROM skill
   731→   WHERE (triggers @0@ "security" OR triggers @1@ "audit")
   732→     AND status = "active"
   733→     AND workspace = $ws
   734→   ORDER BY score DESC LIMIT 3;
   735→
   736→3. Authorization check:
   737→   → Does this agent possess the skill? (possesses edge)
   738→   → Does policy allow this skill for this agent type?
   739→   → Are required MCP tools available? (skill_requires edges)
   740→
   741→4. Context injection:
   742→   → Skill content injected into system prompt
   743→   → Required MCP tools provisioned via RAR token
   744→   → Learning rules for this agent type also loaded (separate, additive)
   745→
   746→5. Execution:
   747→   → Agent works with both skill expertise AND learning corrections
   748→   → Traces recorded with skill reference for evidence
   749→
   750→6. Evolution (post-execution):
   751→   → If the skill led to a failure, Observer proposes a skill update
   752→   → New version created via skill_supersedes chain
   753→   → Old version deprecated, new version activated
   754→```
   755→
   756→#### Integration with OpenClaw via Proxy
   757→
   758→When OpenClaw agents route LLM calls through Brain's proxy, skills and tools are injected transparently. OpenClaw runs its own agent loop — Brain doesn't replace it. Brain enriches every LLM call passing through:
   759→
   760→```
   761→OpenClaw agent sends LLM request through Brain proxy:
   762→  POST /api/proxy/openai/v1/chat/completions
   763→  (bare request — no tools, no skills, no credentials)
   764→  │
   765→  ▼
   766→Brain Proxy:
   767→  ├─ 1. Identify agent (DPoP identity)
   768→  ├─ 2. Discover matching skills for current task
   769→  ├─ 3. Resolve tools: can_use ∩ skill_requires = this agent's toolset
   770→  ├─ 4. Inject tools into request's `tools` parameter
   771→  ├─ 5. Inject skill content + learnings + graph context into messages
   772→  ├─ 6. Forward enriched request to LLM provider
   773→  │
   774→  ├─ 7. LLM responds with tool_calls
   775→  ├─ 8. Proxy intercepts tool_calls
   776→  ├─ 9. Execute each tool call:
   777→  │     ├─ Policy check (governs_tool → intent evaluation)
   778→  │     ├─ Integration tools: brokered credentials (connected_account)
   779→  │     ├─ Local tools: sandboxed execution
   780→  │     └─ Trace recording
   781→  ├─ 10. Send tool results back to LLM
   782→  ├─ 11. Loop until final response
   783→  │
   784→  └─ 12. Return response to OpenClaw agent
   785→```
   786→
   787→The OpenClaw agent doesn't know about skills, tools, or credentials. It sends a bare LLM request. Brain adds everything. This means:
   788→
   789→- **OpenClaw keeps its agent loop** — no replacement needed
   790→- **Brain controls tools** — per-agent resolution via `can_use` + `skill_requires`
   791→- **Credentials never exposed** — brokered at the proxy, sanitized before return
   792→- **Policy enforcement** — every tool call through the intent system
   793→- **Works without Gateway Protocol** — any OpenClaw agent that routes LLM calls through Brain's proxy gets the full stack
   794→
   795→This is an alternative to (or complement of) the Gateway Protocol approach. The Gateway Protocol gives Brain control over session lifecycle and WebSocket streaming. The proxy approach gives Brain control over tool injection and credential brokerage. Both can coexist:
   796→
   797→| Capability | Gateway Protocol | Proxy |
   798→|-----------|-----------------|-------|
   799→| Session lifecycle | Yes | No (OpenClaw manages) |
   800→| Tool injection | Via orchestrator | Via LLM request enrichment |
   801→| Credential brokerage | Via tool execution | Via tool call interception |
   802→| Skill injection | Via context building | Via message enrichment |
   803→| Works without gateway | No | Yes |
   804→| Works with any agent | Only Gateway Protocol clients | Any agent routing LLM calls |
   805→
   806→#### Import Path: skills.sh → Brain
   807→
   808→The 80k+ skills in the `skills.sh` ecosystem are SKILL.md files. Brain can import them:
   809→
   810→```
   811→SKILL.md (YAML frontmatter + Markdown)
   812→  → Parse triggers from frontmatter
   813→  → Parse tool requirements from content
   814→  → Create skill node in SurrealDB
   815→  → Create skill_requires edges for referenced tools
   816→  → Set status = "draft" (human reviews before activation)
   817→```
   818→
   819→This makes Brain compatible with the existing skill ecosystem while adding governance, versioning, and evolution that static files lack.
   820→
   821→#### Why This Matters for the Gateway
   822→
   823→Without skills, Brain can only inject *corrections* (learnings) and *context* (decisions, observations) into agent sessions. Skills add *expertise* — the third pillar. An OpenClaw agent connecting to Brain gets:
   824→
   825→1. **Context** — what's been decided, what's blocked, what's changed (graph state)
   826→2. **Corrections** — what to avoid, what worked before (learnings)
   827→3. **Expertise** — how to approach this class of work (skills)
   828→
   829→No other gateway provides this. A standalone OpenClaw gateway gives agents tools and a sandbox. Brain gives them organizational wisdom.
