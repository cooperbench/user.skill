The LLM proxy and OpenClaw Gateway Protocol integration are **complementary layers of the same strategy**. Here's how they connect:

## The LLM Proxy IS the OpenClaw Integration Point

Your LLM proxy (`/proxy/llm/anthropic/v1/messages`) already intercepts all LLM calls between coding agents and providers. OpenClaw agents route through LLM providers too — and OpenClaw's Gateway acts as a proxy for all LLM calls and tool invocations already.

```
Current (Brain LLM Proxy):
  Claude Code → Brain Proxy → Anthropic API
                    ↓ (async)
              Knowledge Graph (traces, costs, observations)

OpenClaw Integration:
  OpenClaw Gateway → Brain Proxy → Anthropic API
                         ↓ (async)
                   Knowledge Graph (same pipeline)
```

### The integration is simpler than a full Gateway Protocol client

Instead of Brain implementing the OpenClaw Gateway Protocol (WebSocket client, protocol v3 negotiation, device pairing), you can configure **OpenClaw to use Brain as its upstream LLM provider**. OpenClaw already supports custom provider URLs:

1. **OpenClaw's `providers` config** supports custom base URLs for any model provider
2. Point OpenClaw's Anthropic provider URL at Brain's proxy: `http://brain:3000/proxy/llm/anthropic`
3. Every OpenClaw agent's LLM call now flows through Brain's pipeline — traces, cost attribution, contradiction detection, context injection, secret scanning — all for free

### What Each Layer Handles

| Concern | OpenClaw Gateway | Brain LLM Proxy | Brain Knowledge Graph |
|---------|-----------------|-----------------|----------------------|
| Agent routing & channel binding | Yes | — | — |
| Sandbox/tool policy | Yes | — | Policy graph (future) |
| LLM call observability | Basic (logs) | Full traces with cost | Graph-native audit trail |
| Cross-agent memory | No (isolated workspaces) | — | Yes (shared graph) |
| Context injection | No | Yes (ADR-046) | Decisions, learnings, observations |
| Contradiction detection | No | Yes (ADR-047) | Observations with provenance |
| Session lifecycle | Own sessions | Inactivity timeout (ADR-049) | Agent session traces |
| Cost attribution | No | Yes (per-workspace/task) | Budget policies |
| Exec approvals | Yes (Gateway Protocol) | — | Intent authorization (future) |

### Phased Integration (revised)

**Phase 1 (now)**: Configure OpenClaw to use Brain's LLM proxy as its provider URL. Zero code changes in Brain. Every OpenClaw agent gets shared memory, cost tracking, and contradiction detection immediately.

**Phase 2**: Add OpenClaw-specific identity resolution in the proxy. Parse OpenClaw's `metadata` or headers to map requests to the correct workspace/agent/session in Brain's graph. This is a small extension to the existing identity resolution in `anthropic-proxy-route.ts`.

**Phase 3**: Gateway Protocol client for the **control plane only** — exec approvals mapped to Brain's intent authorization, proactive context injection into agent sessions, fleet-wide observation surfacing. This is where the Gateway Protocol's WebSocket API adds value that the LLM proxy alone can't provide.

### Bottom Line

The LLM proxy is the **data plane** — it captures what agents think and decide. The Gateway Protocol would be the **control plane** — it manages what agents can do. You need both eventually, but the proxy gives you 80% of the value with zero new protocol work. The OpenClaw Gateway Protocol becomes valuable specifically for exec approvals and proactive agent control, which maps to Phase 3 of the proxy's intelligence roadmap.
